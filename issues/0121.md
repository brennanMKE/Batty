## Description

Tier 3 localization target. Turkey has a growing developer market and a meaningful Apple install base. Turkish is standard in Apple's localized-app set.

Depends on `#0107`.

## Acceptance criteria

- Every key in `Localizable.xcstrings` has a non-empty `tr` translation, reviewed by a native speaker.
- Launching with macOS Language & Region set to Türkçe shows the full UI translated.
- Visual sweep for string-length expansion (~10–20% longer than English; Turkish agglutinative suffixes can produce long single words in technical labels).
- `## Files changed` should list the `.xcstrings` diff.

## Notes

- Watch for the **dotted-I vs dotless-ı** case-folding gotcha — Turkish locale is the classic case where `String.lowercased()` without `locale: .init(identifier: "tr")` produces wrong results. Not relevant to the static translation strings themselves, but worth a code audit if any user-facing string in Batty is produced by case-folding runtime data.
- Sparkle ships Turkish strings.

## Root cause

Foundation issue `#0107` shipped `Batty/Localizable.xcstrings` with English source plus a handful of reference locales, but Turkish (`tr`) had no `localizations` blocks. With Turkish absent from the catalog, macOS in Türkçe falls back to the English source for every Batty-owned string.

## Fix

Populate `tr` for every key in `Batty/Localizable.xcstrings`:

- Simple keys: `Batty` (brand kept Latin), `Quit Batty?` -> "Batty'den çıkılsın mı?", `Quit` -> "Çık", `Cancel` -> "İptal".
- Plural-aware keys carry both Turkish CLDR forms (`one`, `other`), both populated with the same string because Turkish does not pluralize the noun after a numeral:
  - `Paste %lld lines?` -> "%lld satır yapıştırılsın mı?" (both forms)
  - `There %lld open terminal(s).` -> "%lld terminal açık." (both forms)
  - `%lld unseen bell event(s)` -> "%lld okunmamış zil olayı" (both forms)

Button verbs follow Apple's macOS Turkish conventions ("Çık" for Cmd-Q, "İptal" for the standard cancel button). `%lld` specifiers preserved verbatim. Native-speaker review pending.

## Files changed

- `Batty/Localizable.xcstrings` — adds the `tr` localization block (with `one`/`other` plural variants where applicable) to all 7 catalog keys.

## Gotchas

- Translations are LLM-authored. A native-speaker pass is still owed before the Turkish UI is "final"; the per-language tier-3 acceptance criterion calls for that review.
- Turkish attaches vowel-harmony suffixes to proper nouns with an apostrophe: `Batty'den` (from Batty) for the Cmd-Q confirmation. The apostrophe is required so the Latin brand stem stays visually intact when a Turkish suffix follows. A native reviewer may prefer a more direct phrasing like "Batty'den çıkılsın mı?" vs "Batty'i kapat?" — current text uses the passive interrogative form Apple favours in macOS confirmation dialogs.
- Turkish does **not** pluralize nouns after numerals (one says "5 satır", never "5 satırlar"), but CLDR still defines `one` and `other` categories. Both plural variants are populated with the same string so the catalog stays well-formed regardless of which form CLDR selects.
- Turkish has the **dotted-I vs dotless-ı** case-folding gotcha (`İ`/`i`, `I`/`ı`). The static translations themselves are fine, but any runtime `String.lowercased()` / `uppercased()` on user-visible Turkish text must pass `locale: Locale(identifier: "tr")` or it will fold incorrectly. Worth a code audit if Batty ever folds bell-event sources, session names, or theme names for display.
- Turkish strings tend to stay similar in length to English for short button labels (Çık, İptal) but agglutinative suffixes can make verb forms in sentences noticeably longer ("yapıştırılsın mı"). Watch fixed-width buttons and toolbar labels during a visual sweep.
- Sparkle's own UI ships its own Turkish strings — no work needed in this issue.
