# 0541 — A semitransparent terminal can't blur what's behind it, unlike Apple's Terminal, because the vendored libghostty stubs its window blur call

| | |
|---|---|
| **Status** | open |
| **Module** | Window / TerminalSurface / GhosttyKit |
| **Platform** | macOS |
| **First seen** | 2026-11-03 |

## Description

Once a Pane is see-through ([#0539](0539.md)), whatever is behind the window will show through sharp, with no way to blur it. Apple's Terminal can blur it. Batty has a `background-blur` config key, but setting it won't help, because the function that applies it is an empty stub in the vendored `libghostty.a`.

**This is optional polish. The user hasn't asked for it.** The #0539 planner reported it while deciding what to leave out of that issue. The user asked for see-through and an opacity control, and neither depends on blur. **It doesn't block removing `FeatureFlags.terminalBackgrounds`** unless the user says otherwise. Don't schedule it ahead of the rest of [#0372](0372.md) on the strength of this report.

## What was checked

Against the pin in `BattyKit/Package.swift`, `a2565ccf`, `Ghostty.ref` `c4e16970`, and `main` at `a7bfb741`.

- **The key exists and has a parser.** `strings` on `GhosttyKit.xcframework/macos-arm64_x86_64/libghostty.a` finds `background-blur` and `background-blur-radius`, and `nm` finds `config.Config.BackgroundBlur.parseCLI`. The wrapper exposes it as `withBackgroundBlur(_:)` (`Sources/GhosttyTerminal/Configuration/TerminalConfiguration.swift:214` in the checkout).
- **The function that applies it is empty.** `Patches/ghostty/0004-ios-fixes.sh:19-61` replaces the body of `ghostty_set_window_background_blur` with a bare `return`, and its comment gives the reason: "Disable private window blur API (App Store compliance)". The built binary matches. `otool -tv` on the arm64 slice shows only the frame setup and `ret`, four instructions:

  ```
  stp x29, x30, [sp, #-0x10]!
  mov x29, sp
  ldp x29, x30, [sp], #0x10
  ret
  ```

- **No private symbol remains.** `nm -u` on the whole fat `libghostty.a` lists no `CGS` symbol, and `strings` finds no `CGSSetWindow` or `SLSSetWindow` text.
- **Nothing calls it.** The wrapper's Swift sources don't call it, and `ghostty_set_window`, `withBackgroundBlur` and `background-blur` have no hits in `Batty/`, `BattyKit/Sources` or `BattyKit/Tests`. The function is still declared in `Headers/libghostty/ghostty.h:1288`, so it links and does nothing.
- **Apple's Terminal really does this, through a private API.** `Terminal.app` on this Mac (macOS 27.0) imports `_CGSSetWindowBackgroundBlurRadiusWithOpacityHint` and `_CGSMainConnectionID`, and has the strings `BackgroundBlur`, `BackgroundBlurInactive` and `setTerminalWindowBlur:`. That's a symbol check. The app wasn't opened.

## Two ways to get real blur

Neither is chosen here. The plan decides, and the choice may need the user.

| | **A. Call the private API from Batty** | **B. A blur layer below the terminal host** |
|---|---|---|
| Mechanism | `CGSSetWindowBackgroundBlurRadius` (the removed upstream code) or Terminal's `...WithOpacityHint` variant, declared in Batty and called with the window number | A behind-window `NSVisualEffectView` under the surface |
| Look | A blur radius, as in Terminal | A system material, with its own tint and no radius setting (from memory) |
| Scope | The whole window | Could follow the terminal rectangles, or the whole detail column |
| Main risk | Private API, which can change or break in any macOS release, and has no fallback when it does | Touches the layer `docs/view-hierarchy.md` and `docs/terminal-pane-requirements.md` guard |

Notes on each:

- **A:** the patch's stated reason is App Store compliance. Batty ships outside the App Store with a Developer ID, so that reason doesn't apply here, but the risk of OS breakage does. This is a decision for the user, because Batty would be taking on a private API. Calling it from Batty doesn't change the vendored package, which is upstream and not a fork.
- **B:** the terminal `NSView` is placed directly by `TerminalHostStore`, so SwiftUI order doesn't decide what sits above what (`docs/terminal-pane-requirements.md` §5). The plan must run that doc's §6 checklist. Nothing can be added above the pane body. #0539 measured that AppKit removes `NSThemeFrame`'s own full-window `NSVisualEffectView` when a window goes non-opaque, so there's no existing view to reuse. This layer would also compete for the band's slot with #0539's fills and [#0377](0377.md).

## Questions for the plan

- **Should the user be asked first?** This is unrequested, and option A adds a private API. Confirm it's wanted before planning in detail.
- **What's the control?** A strength slider in Settings → Appearance beside Terminal Opacity, or a simple on/off? A per-Pane or per-Session override makes little sense with a window-wide radius under option A.
- **What about a window with Panes at different opacities?** A Pane at 100 paints itself solid, so it should hide the blur, but that needs checking. The Sidebar and tab bars rely on #0539's solid chrome.
- **When does it turn off?** It has to follow #0539's see-through state, including opaque in native full screen, and has to be cleared when the window goes back to opaque.
- **Does blur change click-through at Terminal Opacity 0?** This is [#0539](0539.md)'s Open question 1, and a blur may change the answer.
- **Is the flag still there?** While `FeatureFlags.terminalBackgrounds` exists, this goes behind it, with no blur call and no setting when it's off. If it lands after that flag is gone, the plan has to decide how it stays invisible until finished, per `AGENTS.md`.

## Unverified

- **That `background-blur` has no visible effect in the running app.** This is inferred from the stub and the absence of callers. Nobody set the key and looked. Nothing here rules out another reader of the key elsewhere in libghostty's own code.
- **Whether either option works in Batty.** Neither has been tried: not the private call in a Hardened Runtime build, nor a behind-window material under the surface. The result can't be judged until #0539's see-through exists.
- **How Terminal's blur looks and what its opacity hint does.** Only the symbols and strings were checked.
- **The material and radius claims in the table,** which are from memory.

## Verification

Blur is a property of how the window server composites the window, so a unit test can't prove it. Any derived state, such as when blur is on, can be unit tested on its own. Beyond that it needs a real run over a detailed picture. Mark `resolved`, not `closed`, and say in `## Gotchas` what wasn't seen.
