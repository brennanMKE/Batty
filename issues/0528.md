# 0528 — The verification tiers have no tooling behind them: `./build.sh unit` can't split fast from slow, and the VM runner has no build-only or sharded full-suite mode

| | |
|---|---|
| **Status** | open |
| **Module** | Testing / Docs |
| **Platform** | macOS |
| **First seen** | 2026-10-19 |

## Description

Commit `01bdca32` split the issue workflow into plan, implement and review phases, and added "Verification tiers" to `issues/Issues.md`: a **fast tier** that runs on every implementation and every review, and a **full tier** for risky changes, release preflight and an umbrella's last child. The table names tools that don't exist yet:

- the fast tier runs "the fast unit tests", and the full tier adds "the slow unit tests". Nothing marks a unit test slow, and `./build.sh unit` always runs all of them;
- the "VM build-only" stage says "Until the runner has a `--build-only` flag, run the one smallest affected class instead";
- the full tier runs the whole `BattyUITests` suite "split into sequential shards each under the guest's 40-minute bound (#0518)". The runner has no way to do that, so a person or agent splits the suite by hand.

User request (2026-10-19, verbatim): "We may need organize tests into fast and slow so we can enhance the benefits of this change". "This change" is the new workflow and its fast and full tiers.

This issue covers the tooling that the tiers need, and the doc updates that name the real commands.

## Current state (verified 2026-10-19 on `main` at `01bdca32`)

### Unit tests

- `./build.sh unit` (`build.sh`, `unit)` case) runs `xcodebuild test -workspace Batty.xcworkspace -scheme "Batty (Beta)" -only-testing:BattyKitTests`. It has no notion of slow tests. `cd BattyKit && swift test` also works and runs the same 2,588 tests.
- No test in `BattyKit/Tests` uses a Swift Testing tag. The only conditional trait is `@Test(.enabled(if: getuid() != 0))` in `SessionNameToolTests.swift:126`.
- **Measured (2026-10-18/19, from the orchestrator):** `./build.sh unit` ran 2,588 tests in 289 suites, test run 28.5 s. `tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM()` reported 28.4 s, and dozens of others reported about 27.7 s.

**The slow tail is not one slow test.** Filer's investigation:

- The test is `LMStudioDashboardPaneContentTests.tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM()` (`BattyKit/Tests/BattyKitTests/LMStudioDashboardPaneContentTests.swift:686`). It spawns two `/bin/sh` children that ignore `SIGTERM`, waits on their FIFO readiness (`LMStudioSIGTERMIgnoringFixture`, `ChildProcessReadiness.waitForFIFOReady`), and awaits the `TestTeardownReapGate`. **Run alone, its whole suite of 25 tests passes in 0.396 s** (`swift test --filter LMStudioDashboardPaneContentTests`).
- A full `swift test` with `--experimental-event-stream-output` (event-stream version 0) recorded each test's start and end instants. The run took 23.5 s. 2,557 of 2,588 tests **start** within the first second. 2,486 **end** between 21 and 23 s. Only 30 end within the first second. Almost every test reports a duration of 20–23 s. Swift Testing starts nearly every test at once, and most suites are `@MainActor`, so a reported duration includes time spent queued for the main actor. Durations from the console output say nothing about which tests are slow.
- The run is not CPU-bound: 9.1 s user + 7.6 s system over 25.9 s wall.
- A 5 s `sample` of the test process, taken about 6 s into the run, shows the main thread blocked in synchronous subprocess work inside `@MainActor` tests:
  - **About 43%** of main-thread samples are in `AtlasOwnershipExperimentTests.secondSurfaceOnSameControllerAtlasDelta()`. It runs `/usr/bin/vmmap` against the test process four times, via `readDataToEndOfFile()` and `waitUntilExit()` on the main actor (`AtlasOwnershipExperimentTests.swift:48–58`, `:120–136`). This suite alone takes 4.7 s with nothing else running.
  - **About 27%** are in three `ProcessGitStatusScannerTests` worktree tests (`aWorktreeWhoseDirectoryWasRemovedIsPrunableWithAReason`, `aWorktreePathContainingASpaceIsListedIntact`, `aPlainCheckoutListsOnlyItself`). Their fixtures (`makeRepoWithOneCommit` and friends) run `git` synchronously on the main actor. The suite (27 tests) takes 5.4 s alone.
- So the tail looks like main-actor serialization: every `@MainActor` test waits behind tests that block the main thread on child processes. Moving that blocking work off the main actor, or isolating those tests, may shorten the whole run more than tagging anything as slow. This is a hypothesis from one sample. The plan should measure before choosing.

The `ProjectsUITestCase` subclasses include two classes whose names don't start with `Projects`: `AuxiliaryWindowShortcutTests` and `DemoSceneTests`.

### UI-test compile errors

- During #0524, an implementer used a nonexistent API in `BattyUITests`, and only a full VM run caught it. #0524's Gotchas say "only a VM run proves the UI tests compile".
- **That premise is only partly true.** `./build.sh ui-typecheck` (#0442, resolved) type-checks every `BattyUITests` source on the host with `swiftc -typecheck` against the real XCTest module, mirroring the target's Swift 6 settings. It ran clean on `main` in about 10 s on 2026-10-19, with deprecation warnings only. It would catch a nonexistent API. `docs/ui-testing-vm.md` documents it ("What runs where", and from `:42`). But neither the new "Verification tiers" table nor Phase 2 step 4 in `issues/Issues.md` names it, so the #0524 implementer had no prompt to run it.
- `ui-typecheck` can't catch link errors, resource or scheme problems, or anything that only `xcodebuild build-for-testing` sees. That gap is what a VM `--build-only` would close.

## Expected behavior

### 1. Unit tests: fast and full tiers

- First, find out what actually sets the unit-test wall clock. Use the event stream and a main-thread sample, not console durations. Then fix it or isolate it. Candidates from the investigation above: blocking `vmmap` and `git` work on the main actor in `AtlasOwnershipExperimentTests` and `ProcessGitStatusScannerTests`, and other `@MainActor` tests that spawn real processes. A fix must follow `AGENTS.md` "Asynchronous tests" and `docs/async-test-seams.md`: no sleeps, no polling, no timing assertions.
- Add a way to mark a unit test slow, so `./build.sh unit` runs only the fast set and a full-tier command runs everything. Options include a Swift Testing tag (`.tags(.slow)`) or an environment-gated trait (`.enabled(if:)` reading a variable). The mechanism must work under both `./build.sh unit` (`xcodebuild`; a variable reaches the runner through a `TEST_RUNNER_` prefix) and `cd BattyKit && swift test`. In both, plain invocation runs the fast set and one documented switch runs the full set.
- The full-tier command is one documented invocation, for example `./build.sh unit --full` or `./build.sh unit-full`.
- Slow tests the fast set skips are reported as skipped. They must not disappear from the count without a trace.

### 2. VM runner: build-only and sharded full suite

`tools/` is not a restricted area. `scripts/` is restricted (`AGENTS.md`), so none of this goes there.

- **`--build-only`.** Export, boot, resolve packages, run `build-for-testing`, pull `xcodebuild-build.log`, and stop. Skip the broker bootstrap and every test step. Print the compiler errors in the summary and exit non-zero on failure. The `==> RESULT:` line says it was a build-only run.
- **`--full`** (or a similar name). Run the whole `BattyUITests` suite as automatically generated sequential shards, each under the guest's 40-minute bound:
  - Discover classes from the `BattyUITests` sources, including subclasses of base test cases such as `ProjectsUITestCase`, not only direct `XCTestCase` subclasses. The runner warns about, or refuses to start with, any class the discovery can't place.
  - Keep the gated classes (`ViewGalleryTests`, `DemoSceneTests`) out of the shards, or include them only on request, matching what a plain run does today.
  - Size the shards from a recorded per-class timing, or from the last run's `xcodebuild.log`, with headroom under the bound. Fall back to a fixed split when no timing exists.
  - One VM at a time (`AGENTS.md`). The plan chooses between one boot and one build running several `test-without-building` steps, and a fresh clone per shard. The trade-off is that guest state carries over between launches within a run (#0444), against a build and boot per shard.
  - Pass each class list to `xcodebuild` as an array of separate `-only-testing:` arguments, never one string, so the 2026-10-18 word-splitting failure can't happen.
  - Summarize all shards in one place: per-shard run id or directory, `Executed N tests, with M failures` for each, a combined total, and one final `==> RESULT:` line.
- The guest log capture uses `log show --last 30m` (`tools/run-ui-tests-vm.sh`, "The app's own warnings and crashes"). On a run longer than 30 minutes, it misses the start. Under `--full`, each shard captures its own logs, or the window covers the whole run.

### 3. Optional: fast and slow UI classes

Optionally, mark UI classes fast or slow, so a plan can name a quick, representative set of classes for the fast tier. This is an open question, below. It is not a requirement.

### 4. Docs

Once the commands exist, name them in:

- `docs/ui-testing-vm.md`: the usage for `--build-only` and `--full`, the current suite size and duration (the timing note at `:368` still says 617.5 s, about 10 min), and how shards are chosen.
- `AGENTS.md` "Test strategy": the unit fast and full commands, and the UI line, which still says "60+ tests, ~10 min" (`:86`).
- `issues/Issues.md` "Verification tiers": the real fast and full commands. Add `./build.sh ui-typecheck` to the Build stage and to Phase 2 step 4, because it already exists and catches #0524's class of error. Replace the "VM build-only" stage's fallback text, and replace "split into sequential shards" with the `--full` invocation.

## Acceptance criteria

- `./build.sh unit` runs the fast unit set, and one documented command runs every unit test. `cd BattyKit && swift test` still works, with the same fast and full split.
- The unit wall-clock tail is explained in the issue from measurements, and is fixed or isolated. The before and after test-run lines are quoted.
- `tools/run-ui-tests-vm.sh --build-only` builds `BattyUITests` in the VM and reports compile errors without running any test.
- `tools/run-ui-tests-vm.sh --full` runs every non-gated `BattyUITests` class, including all `ProjectsUITestCase` subclasses, in sequential shards under the bound. It ends with one combined summary. Proof is one complete `--full` run on `main` with its run id(s) quoted.
- `docs/ui-testing-vm.md`, `AGENTS.md` and `issues/Issues.md` name the real commands and the current counts and durations.

## Open questions

1. **Slow-unit mechanism.** A tag or an environment-gated trait? `xcodebuild` and `swift test` filter tags differently, and an env-gated trait reports skipped tests in both. Which tests count as slow, and by what measure, now that console durations are known to be misleading?
2. **Fix or tag?** If moving `vmmap` and `git` off the main actor removes most of the tail, does the unit suite still need a slow tier at all? Should `AtlasOwnershipExperimentTests`, an experiment that guards a libghostty assumption, be full-tier only?
3. **Shard execution.** One VM boot with several `test-without-building` steps, or a fresh clone per shard? See #0444 for the shared-state cost.
4. **Shard sizing.** A committed per-class timing file, the last run's log, or a fixed alphabetical split?
5. **Fast UI set.** Should UI classes carry a fast or slow designation, so a plan can choose a representative fast set, or should plans keep naming classes by hand?
6. **#0518.** A working `--full` meets #0518's acceptance criterion ("or the documented sharded invocation covers the whole suite"). Should this issue resolve #0518 too, or should #0518 stay open for raising the bound or making `ViewGalleryTests` cheaper?
7. **Is `--build-only` still worth it** now that `ui-typecheck` exists? It catches less than a VM build, but costs no VM. The tiers might need only `ui-typecheck` plus `--build-only` before a `--full` run.
