# 0164 — UI test suite: tab chip rendering (width, truncation, per-tab titles)

| | |
|---|---|
| **Status** | resolved |
| **Module** | Tests / Tabs |
| **Platform** | macOS |
| **First seen** | 2026-05-20 |

## Description

Tab chip rendering bugs ([[0047]], [[0048]], [[0050]], [[0142]]) silently corrupted the tab strip's usability — chips bleeding past pane edges, identical titles across tabs, home-directory tabs locked to "~". These look minor in screenshots but compound: a user with five tabs in a narrow pane can lose access to the `+` button or to inactive chips entirely. This suite asserts the chip-layout invariants directly.

## Regressions this suite would have caught

- [[0047]] — Tab bar contents rendered past the pane's trailing edge into the adjacent pane. A test on a narrow pane asserting `tab-bar.<id>` frame width ≤ pane frame width would have caught it.
- [[0048]] — Tab chip titles didn't truncate, pushing the `+` button out of narrow panes. A test asserting `add-tab-button.<paneID>` is hit-testable in a narrow pane with many tabs would have caught it.
- [[0050]] — Tab chips all showed `user@host`. A test creating multiple tabs and asserting unique chip identifiers would have caught it.
- [[0142]] — Tab at `$HOME` always showed "~". Already covered as the override case in [[0160]] — here we add the resolver-default case (no override, home dir, assert "~" appears).

## Test cases

### Chip frame stays inside pane bounds — would catch [[0047]]

- **Multi-tab pane: tab bar width ≤ pane width.** Create 5 tabs in a single pane. Assert `tab-bar.<paneID>` frame width is ≤ `pane-terminal.<paneID>` frame width. Repeat after horizontally splitting the pane (narrower).
- **Tab bar respects neighboring pane boundary.** Two-pane horizontal split with 5 tabs in the left pane. Assert no `tab-chip.<title>` element has a frame whose right edge crosses the divider's x-coordinate.

### Add button stays reachable — would catch [[0048]]

- **`+` button hit-testable with many tabs.** Create 10 tabs in a single pane. Click `add-tab-button.<paneID>`. Assert tab count goes to 11. (XCUITest's `click()` requires the element be hit-testable; failure mode is the click missing or hitting a chip instead.)
- **Chip titles truncate when chip width drops below threshold.** After creating many tabs, assert each chip's `accessibilityLabel` (full title) differs from its displayed identifier (truncated title) — i.e. the truncation actually happened.

### Per-tab title uniqueness — would catch [[0050]]

- **Three tabs in three different cwds have three different identifiers.** Driver: create tab 1, send `cd /tmp`, wait for prompt, create tab 2, send `cd /var`, etc. Assert three unique `tab-chip.<title>` identifiers exist.
- **Two tabs in the same cwd get suffixes or remain distinct.** Document and test whatever behavior the codebase has chosen (probably a numeric suffix or distinct UUIDs in the identifier — verify the test reflects current behavior).

### Home-directory resolver — covers [[0142]] no-override case

- **A tab at `$HOME` without an override shows `~`.** Verify the formatter's home-dir special case still fires when no override exists.
- **A tab at `$HOME/subdir` shows `~/subdir` or the basename per spec.** Document and test the formatter's exact behavior here so a future "simplification" doesn't break it.

## Accessibility identifiers needed

- `add-tab-button.<paneID>` on the `+` button inside `SlidingTabBar`.
- `accessibilityLabel` on `tab-chip.<title>` set to the *full* (untruncated) title, while the identifier remains the truncated display string. This is the canonical XCUITest split — identifier is for finding, label is for assertions on content.

## Driver intents needed (from [[0158]])

- `createTab` — already in foundation vocabulary.
- `sendShellInput(text:)` — types into the focused terminal (useful here to send `cd <path>` for cwd setup).
- `narrowActivePaneTo(width:)` — resizes the active pane to a target width via the split divider, for the truncation tests. (Alternatively, the test resizes the *window* and lets layout settle.)

## Out of scope

- The visual rendering of the truncation ellipsis itself (snapshot territory).
- Animation of chip insertion / removal (manual review territory).
- Reorder gestures inside `SlidingTabBar` (third-party package; their tests).

## Acceptance criteria

- All test cases pass under `xcodebuild -scheme 'Batty (Beta)' -destination 'platform=macOS' test`.
- Each test names the regression it covers.
- The narrow-pane test runs at multiple widths (e.g. 200pt, 350pt, 600pt) to catch threshold-off-by-one bugs in the chip-width math.

## Notes

- Depends on [[0158]].
- The chip-width math lives in `PaneView` constants (`approxCharWidth`, `chipChromeWidth`, `barChromeWidth`, `chipMinWidth`, etc.). If those constants are tuned, tests may need updating; that's the right tradeoff for layout-quality coverage.
