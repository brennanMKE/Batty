## Description

Reported by the user testing the #0315 Beta build. A Pane created with
`batty pane split --view <kind>` is functionally unusable in the UI:

1. **Cannot be selected.** Clicking a non-terminal Pane does not focus it.
   `PaneContentPlaceholderView` has no tap target. This was known at #0315
   review time and recorded as an acceptable gap; it is not acceptable.
2. **Cannot be closed.** #0315 gated the tab commands (⌘W included) on
   `kind == .terminal` so they could not mutate a non-terminal Pane's
   structural tab. That gating removed the only keyboard/menu route to
   getting rid of the Pane. `batty pane close --pane <id>` still works, so
   the CLI is the sole escape hatch.
3. **Focus highlight is wrong.** The focused-Pane border does not reflect a
   non-terminal Pane correctly. Partly downstream of (1) — a Pane that
   cannot be focused cannot show focus — but verify the border/overlay path
   independently.
4. **Sizing is wrong.** The Pane does not fill its allotted split area the
   way a terminal Pane does.

## Expected behavior

A non-terminal Pane behaves like a terminal Pane for every pane-level
interaction: click to focus, visible focus border, correct size in its split
allotment, and a keyboard/menu way to close it. `docs/pane-kinds.md` §2
promises exactly this — "a Git Status pane swaps, resizes, and drags exactly
like a terminal pane."

## Notes

- The close question needs a decision: ⌘W on a non-terminal Pane should
  close the **Pane** (there is no Tab to close), which is different from its
  terminal behaviour. Confirm the menu item's title/enablement reflects that.
- Sizing and focus may share a root cause with the layout of
  `nonTerminalBody` / `PaneContentPlaceholderView`.

## Resolution notes

> 🟢 Resolved 2026-08-09 — a non-terminal Pane can now be clicked to focus, closed with ⌘W (which closes the **Pane**, since there is no Tab), shows the focus border, and paints an opaque background at the same header height as a terminal sibling.

Two of the four defects were self-inflicted by #0315 and were known at the time: the placeholder shipped with no tap target, recorded then as an "acceptable gap"; and #0315's gating of the tab commands on `kind == .terminal` removed ⌘W, which was the only UI route to closing such a Pane. Neither should have shipped.

## Fix

- **Selection** — `.contentShape(Rectangle()).onTapGesture { appStore?.focusPane(id:) }` on `nonTerminalBody`, mirroring `SessionSidebarView.PaneRow`'s outer-tap-plus-inner-Buttons pattern so the eye button and drag handle keep their own gestures.
- **Close** — `WindowRuntime.closeFocusedTab()`/`.requestCloseFocusedTab()` route to `closePane(id:refuseIfAppsLastPane: false)` when `focusedTerminalPane` is nil. That is the single choke point all three dispatch paths already use. `closeFocusedItemTitle` gives the menu item "Close Tab" for a terminal Pane and "Close Pane" otherwise, and the item is enabled again for non-terminal focus. **#0315's tab-mutation gating is untouched** — only the close routing changed.
- **Focus border** — no separate defect. The overlay is outside the kind switch and both `isPaneFocused` and `hasSiblingPanes` are kind-agnostic; it was purely downstream of never being able to focus.
- **Sizing** — the real cause was that the content area painted **no background**. A terminal Pane's opaque fill is not SwiftUI at all: `TerminalPlaceholderView` is `Color.clear`, a geometry probe, and the fill comes from the AppKit `AppTerminalView`. A typed Pane therefore sat transparent beside an opaque sibling and read as not occupying its region. `chromeBackground` now covers the whole `nonTerminalBody`, falling back to `Color(nsColor: .windowBackgroundColor)` so an unthemed session is still opaque. `nonTerminalHeaderHeight = 36` matches `SlidingTabBar`'s `barHeight` so content starts at the same y as a terminal sibling's.

## Review

Reviewer: `claude-opus-5`, two rounds.

Round 1 approved the close routing after checking `refuseIfAppsLastPane: false` rather than accepting it — the guard is XPC-only by construction, and `WindowRuntime.closeTab` has never had a last-pane refusal either, so the new branch is exactly symmetric with what ⌘W already does to a terminal Pane. It also confirmed clicks genuinely reach SwiftUI in a typed Pane's region, since `TerminalHostView.hitTest` returns `nil` with no terminal under the point — the one thing that could have made the tap fix a silent no-op at runtime.

Then it found the sizing fix was **provably a no-op**: `PaneContentPlaceholderView` already carried the identical `.frame(maxWidth:.infinity, maxHeight:.infinity)`, and the header leads with a greedy `Spacer(minLength: 0)`. It supplied the real diagnosis (the missing background) that round 2 implemented.

Round 2 verified `36` against `SlidingTabBar.swift:89`'s actual `barHeight` rather than the claim, confirmed the background composites under all four overlays rather than over them, and caught that `chromeBackground` is `nil` on an unthemed session — which would have reproduced the original symptom for a user with no theme selected.

## Gotchas

- **⌘W means something different per Pane kind.** On a terminal Pane it closes a Tab; on a non-terminal Pane it closes the Pane. The menu title changes to match, but the keystroke is overloaded.
- **A terminal Pane's fill is AppKit, not SwiftUI.** `TerminalPlaceholderView` is `Color.clear`. Any future non-terminal view must paint its own background or it will look transparent beside a terminal sibling — this is what made the Pane appear mis-sized.
- **`nonTerminalHeaderHeight = 36` duplicates `SlidingTabBar`'s default** rather than deriving from it. If the package changes its `barHeight`, the two headers drift.
- **Header and content are one flat colour** in a non-terminal Pane, unlike a terminal Pane where the tab bar reads distinctly against the terminal fill. A design question, not a defect.
