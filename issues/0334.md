# 0334 — Non-terminal Panes cannot be selected, closed, or focused, and do not size correctly

| | |
|---|---|
| **Status** | open |
| **Module** | Pane |
| **Platform** | macOS |
| **First seen** | 2026-08-09 |

## Description

Reported by the user testing the #0315 Beta build. A Pane created with
`batty pane split --view <kind>` is functionally unusable in the UI:

1. **Cannot be selected.** Clicking a non-terminal Pane does not focus it.
   `PaneContentPlaceholderView` has no tap target. This was known at #0315
   review time and recorded as an acceptable gap; it is not acceptable.
2. **Cannot be closed.** #0315 gated the tab commands (⌘W included) on
   `kind == .terminal` so they could not mutate a non-terminal Pane's
   structural tab. That gating removed the only keyboard/menu route to
   getting rid of the Pane. `batty pane close --pane <id>` still works, so
   the CLI is the sole escape hatch.
3. **Focus highlight is wrong.** The focused-Pane border does not reflect a
   non-terminal Pane correctly. Partly downstream of (1) — a Pane that
   cannot be focused cannot show focus — but verify the border/overlay path
   independently.
4. **Sizing is wrong.** The Pane does not fill its allotted split area the
   way a terminal Pane does.

## Expected behavior

A non-terminal Pane behaves like a terminal Pane for every pane-level
interaction: click to focus, visible focus border, correct size in its split
allotment, and a keyboard/menu way to close it. `docs/pane-kinds.md` §2
promises exactly this — "a Git Status pane swaps, resizes, and drags exactly
like a terminal pane."

## Notes

- The close question needs a decision: ⌘W on a non-terminal Pane should
  close the **Pane** (there is no Tab to close), which is different from its
  terminal behaviour. Confirm the menu item's title/enablement reflects that.
- Sizing and focus may share a root cause with the layout of
  `nonTerminalBody` / `PaneContentPlaceholderView`.
