## Description

#0393 found the real cause of `;2;13~` at a zsh prompt and fixes exactly one key: libghostty's *legacy* key encoder consults a hard-coded "PC style function key" table before anything else, and that table maps Shift-, Ctrl- and Cmd-modified **Return** to `CSI 27;<mod>;13~` with **no mode gate** (not `modifyOtherKeys`, not Kitty), so zsh/bash self-insert the tail. #0393's fix (branch `issue/0393`, not yet merged) rewrites Shift/Ctrl-Return to plain Return in the app's `NSEvent` monitor, only when the pty's foreground process group is a lone bash/zsh/sh-family shell. It deliberately covers nothing else. This issue is the follow-up for what it leaves out:

1. **The same unconditional pattern exists for Tab and Escape** in the same table. Ctrl-Tab (`ESC[27;5;9~`), Ctrl-Shift-Tab (`ESC[27;6;9~`), Shift-Escape (`ESC[27;2;27~`), Ctrl-Escape (`ESC[27;5;27~`) and every Cmd/Option-combination of Tab, Escape and Return in that table reach the shell as a sequence it has no binding for, and the tail lands on the command line. **Ctrl-Tab and Ctrl-Shift-Tab are worse in Batty than in upstream Ghostty.app**: Ghostty binds them to `next_tab` / `previous_tab` by default, so the encoder never sees them there; Batty's `keybind = clear` removed those bindings, Batty's own shortcut layer does not claim the chord, and the key falls straight into the table.
2. **Option-Up / Option-Down** (the second sub-case of the #0393 report) have no Batty keybind and no Ghostty default, so they fall through to the encoder as `ESC[1;3A` / `ESC[1;3B`, which stock zsh does not bind either.
3. **Over ssh** the foreground process is `ssh`, so #0393's rewrite stands down and the remote zsh still receives `ESC[27;2;13~` for Shift-Enter. That matches upstream Ghostty.app. Whether Batty should go further is an open question for the user, below.
4. **The inventory of what `keybind = clear` removes versus Ghostty's defaults, and the test matrix**, which #0393's "Scope and verification" asked for and the fix did not produce.

Not release-blocking for 1.2.0 unless the user decides otherwise: #0393 covers the reported key, and the remaining chords are less common at a prompt. Target: after 1.2.0.

## Steps to reproduce

Beta only (`./build.sh`); never the user's Prod app. With a Beta build that includes `issue/0393`:

1. Open a Pane at a plain zsh prompt (`zsh -f` gives the stock keymap; the user's oh-my-zsh prompt reproduces too).
2. Type `echo hi` and press **Ctrl-Tab**, then **Ctrl-Shift-Tab**, then **Shift-Escape**, then **Ctrl-Escape**. Observe the command line.
3. Press **Option-Up** and **Option-Down**. Observe the command line.
4. Repeat 2-3 in bash (`bash --norc`).
5. `ssh` to any host and press **Shift-Enter** at the remote zsh prompt.
6. For each step, do the same in Terminal.app and in upstream Ghostty.app and record the difference.

## Expected behavior

Acceptance criteria:

1. **No modified Tab, Escape or Return chord inserts printable text at a lone zsh/bash/sh-family prompt.** For every modifier combination of Tab, Escape and Return that `function_keys.zig` encodes unconditionally (list in Notes), either the chord performs an action Batty owns, or the shell receives bytes it handles (the plain key, or a sequence with a default readline/ZLE binding), or the chord is deliberately left as the raw sequence with that choice recorded in `docs/shortcuts.md`. The implementer picks the mechanism per chord; the Notes lay out the three candidates (extend `PlainShellKeyRewrite`, re-add targeted Ghostty keybinds, or replace `keybind = clear` with targeted unbinds).
2. **Ctrl-Tab and Ctrl-Shift-Tab are decided explicitly.** Either Batty claims them as Show Next Tab / Show Previous Tab (that restores what upstream Ghostty does and what browser-trained fingers expect; `ShortcutAction` currently puts those actions on Cmd-Shift-] / Cmd-Shift-[) or they are downgraded to plain Tab / `ESC[Z` at a plain shell prompt like #0393 did for Return. Either way they stop producing `;5;9~` / `;6;9~`. If claimed as shortcuts, they go through `ShortcutAction` / `ShortcutsStore` so they are rebindable, and `docs/shortcuts.md` is updated.
3. **Programs that asked for extended keys keep the full encoding.** Whatever is done must preserve `ESC[27;…~` / Kitty / `modifyOtherKeys` output for a foreground process that is not a lone plain shell (Claude Code, vim, nvim, less, fish), exactly as #0393's lone-group gate does. No key the user types inside a TUI changes meaning.
4. **Option-Up / Option-Down are decided explicitly**, with Terminal.app as the reference for prompt behaviour and the raw `ESC[1;3A` / `ESC[1;3B` kept for TUIs. If the answer is "history search like Terminal.app" or "plain Up/Down at a shell prompt", it goes through the same foreground-aware path, not a hard `text:` keybind that would also fire inside vim. The existing `alt+left` / `alt+right` / `super+left` / `super+right` / `super+backspace` / `alt+backspace` `text:` bindings in `TabRuntime` are reviewed under the same rule and the decision recorded (keep, because they match Ghostty's own macOS defaults; or move them into the foreground-aware path).
5. **The `keybind = clear` inventory is written down**, in the issue's `## Notes` or `docs/shortcuts.md`: every default in `Keybinds.init` at the pinned Ghostty ref, split into (a) Cmd-chords Batty genuinely wants to fall through to its menu, (b) bindings Batty re-adds, (c) bindings removed by accident with a decision each. The starting list is in Notes; the implementer verifies it against the source at the ref the build actually links.
6. **Test coverage.** Unit tests on the pure decision function (as `PlainShellKeyRewriteTests` does today) for every chord in criterion 1 and for the foreground gate; UI tests in the Tart VM modelled on `BattyUITests/ShiftEnterTests.swift` (sentinel-file pattern, `BattyUITestHarness.sentinelPath` / `waitForFile`) for at least Ctrl-Tab and Shift-Escape at the zsh prompt, plus one negative test proving a non-shell foreground process still receives the raw sequence (e.g. `cat -v` then the chord, asserting the echoed bytes). The full matrix in Notes is run by hand and the results pasted into `## Work log` before `resolved`. No sleeps in tests (AGENTS.md).
7. `./build.sh`, `./build.sh unit` and the VM UI suite pass.

## Actual behavior

At a zsh prompt in Batty Beta (and, apart from Ctrl-Tab / Ctrl-Shift-Tab, in upstream Ghostty.app):

- Ctrl-Tab → the tail of `ESC[27;5;9~` self-inserts (with the user's keymap the visible tail is of the form `;5;9~`, by the same mechanism as #0393's `;2;13~`; with the stock `zsh -f` keymap the prefix walk stops earlier and more of the sequence shows). Nothing switches tabs.
- Ctrl-Shift-Tab → same with `;6;9~`.
- Shift-Escape → `;2;27~`-style tail; Ctrl-Escape → `;5;27~`.
- Option-Up / Option-Down → `ESC[1;3A` / `ESC[1;3B` reach ZLE; stock zsh 5.9 binds only `^[[A`-`^[[D`, `^[OA`-`^[OD` and `^[[200~`, so the sequence is undefined and a tail self-inserts rather than recalling history. Exact tail and Terminal.app's behaviour to be recorded in the matrix.
- Over ssh, Shift-Enter → `;2;13~` on the remote line, unchanged by #0393.

### The table, and why it is unconditional

`src/input/function_keys.zig` is consulted first in the legacy encoder (`src/input/key_encode.zig:343-351`, inside `legacy()` at `:327`, which is the path taken whenever Kitty flags are zero, `:106`). Each `Entry` has a `modify_other_keys` gate that defaults to `.any` (`function_keys.zig:42`); `pcStyleFunctionKey` (`key_encode.zig:607-669`) skips `.set` entries when `modifyOtherKeys` mode 2 is on and `.set_other` entries when it is off (`:652-656`), but `.any` entries match regardless, needing only an exact modifier match (`:658-665`). So #0393's original hypothesis ("the terminal is in mode 2") was wrong in the right direction: these sequences come out in *every* mode.

Entries with no gate (`.any`), i.e. unconditional, at that ref:

- **Return** (`function_keys.zig:198-223`): `shift` → `ESC[27;2;13~` (`:199`); `alt+shift` `27;4`, `ctrl` `27;5`, `ctrl+shift` `27;6`, `alt+ctrl` `27;7`, `alt+ctrl+shift` `27;8`, and every `super` combination `27;9`-`27;16` (`:208-220`). Only `alt` alone is gated (`.set` → `ESC CR` at `:202`, `.set_other` → `27;3;13~` at `:205`). #0393 covers `shift`, `ctrl`, `ctrl+shift` on key codes 36 and 76 (`PlainShellKeyRewrite.strippedModifiers`, branch `issue/0393` at `80f18b09`, `BattyKit/Sources/BattyKit/Commands/PlainShellKeyRewrite.swift:41-45`); the `alt` and `super` combinations are untouched.
- **Tab** (`:171-196`): `alt+shift` `27;4;9~` (`:181`), `ctrl` `27;5;9~` (`:182`), `ctrl+shift` `27;6;9~` (`:183`), `alt+ctrl` `27;7`, `alt+ctrl+shift` `27;8`, and `super` combinations `27;9`-`27;16` (`:184-193`). `shift` (`ESC[Z`, `:173`) and `alt` (`ESC TAB`, `:174`) are gated `.set` and correct for a shell; do not touch Shift-Tab, completion menus depend on `ESC[Z`.
- **Escape** (`:225-242`): `shift` `27;2;27~` (`:226`), `alt+shift` `27;4;27~` (`:228`), `ctrl` `27;5;27~` (`:229`), `ctrl+shift` `27;6;27~` (`:230`), `alt+ctrl` `27;7`, `alt+ctrl+shift` `27;8`, `super` combinations `27;9`-`27;16` (`:231-240`). `alt` alone is `ESC ESC` (`:227`). Note Escape is where the IME exception matters: `legacy()` skips the table for Escape/Return when `event.utf8` is non-empty (`key_encode.zig:364-374`); #0393's `hasMarkedText()` guard (`PlainShellKeyRewrite.swift:82`) is the host-side equivalent and must be carried over.
- **Backspace is not affected**: every modified Backspace entry is gated `.set` or `.set_other` (`:137-165`) and the ungated ones are `ctrl` → `\x08` and plain `\x7f` (`:167-168`). Leave it alone.
- **Arrows, Home, End, Insert, Delete, PgUp, PgDn, F1-F12** use `pcStyle(...)` (`:81-104`, helper at `:280-295`), which emits the standard xterm `CSI 1;<mod>A` / `CSI n;<mod>~` forms for all 15 modifier sets (`modifiers` at `:53-69`), also ungated. These are the sequences TUIs expect, so they are correct in a TUI; at a prompt they are only a problem where the shell has no binding (Option-Up/Down below).

The modifier codes are xterm's: 2 shift, 3 alt, 4 alt+shift, 5 ctrl, 6 ctrl+shift, 7 alt+ctrl, 8 alt+ctrl+shift, 9-16 the same with super (`function_keys.zig:53-69`).

### What zsh does with them

Stock `zsh -f` on this host (zsh 5.9, `bindkey -M emacs`) binds only `^[OA`-`^[OD`, `^[[A`-`^[[D` and `^[[200~`. ZLE walks the longest bound prefix and self-inserts whatever follows the point where no binding matches, which is why the user saw `;2;13~` (their keymap binds more `^[[2…` prefixes than stock). The visible tail therefore varies by keymap; the mechanism does not.

### Why Ctrl-Tab is Batty-specific

Ghostty's defaults (`src/config/Config.zig`, `Keybinds.init` at `:6542-7311`) bind `ctrl+shift+tab` → `previous_tab` (`:6712`) and `ctrl+tab` → `next_tab` (`:6717`) in the platform-independent section, so on upstream Ghostty.app the binding consumes the chord before the encoder runs. Batty issues `keybind = clear` (`BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:319`) and re-adds seven bindings (`:320-326`), none for Tab. Batty's own `NSEvent` monitor (`Batty/BattyApp.swift:84`) matches `ShortcutAction` bindings, and that enum has no Tab or Escape chord at all (`BattyKit/Sources/BattyKit/Shortcuts/ShortcutAction.swift`; Show Previous/Next Tab are `Cmd-Shift-[` / `Cmd-Shift-]` at `:149-152`). So the chord reaches libghostty with no binding and the table encodes it. This is the one place the audit #0393 asked for ("split the inventory into what Batty wants gone and what was discarded by accident") has a concrete user-visible casualty.

### Option-Up / Option-Down

`TabRuntime.swift:324-325` bind only `alt+left` / `alt+right`. Ghostty's macOS defaults (`Config.zig:7024-7310`) bind `super+right` → `text:\x05`, `super+left` → `text:\x01`, `super+backspace` → `text:\x15`, `alt+left` → `esc:b`, `alt+right` → `esc:f` (`:7285-7309`, "Natural text editing"), and nothing for `alt+up` / `alt+down`; there is no `alt+backspace` default upstream (Batty's `:326` is its own addition, matching the table's `.set` entry at `function_keys.zig:138`). So Option-Up/Down reach the encoder in both apps. `pcStyleFunctionKey` is called with `all_mods` (`key_encode.zig:343-345`), and `macos-option-as-alt` (unset by Batty; Ghostty default `null`, `Config.zig:3449`) only affects the UTF-8 / `modifyOtherKeys` branch (`key_encode.zig:432-443`), so the arrow entries match with `alt` set and emit `ESC[1;3A` / `ESC[1;3B`. Inside a TUI that is right. At a prompt, Terminal.app's behaviour is the reference and has not been recorded yet.

### Over ssh

`AppTerminalView.foregroundPid` is `tcgetpgrp` on the pty (`BattyKit/.build/checkouts/libghostty-spm/Sources/GhosttyTerminal/Surface/TerminalSurface.swift:404-417`). With an interactive `ssh` running, that group is `ssh`, `proc_name` returns `ssh`, it is not in `plainShellNames` (`PlainShellKeyRewrite.swift:21-23`), and the event is delivered unchanged. The remote shell gets whatever the local encoder produced. Upstream Ghostty.app behaves identically. Options if the user wants more: (a) treat `ssh` (and `mosh`, `tmux`, `screen`, `docker exec`, `kubectl exec` …) as "unknown, downgrade" rather than "unknown, pass through", which would break Shift-Enter in a remote Claude Code / vim; (b) ship the fix as shell integration on the remote side (a ZLE/readline binding for `ESC[27;2;13~` → accept-line), which only reaches hosts the user configures; (c) leave it. (c) is the current behaviour and the default recommendation.

### Three candidate mechanisms

1. **Extend `PlainShellKeyRewrite`** to Tab (key code 48) and Escape (53) with the same lone-plain-shell gate, mapping Ctrl-Tab → Tab, Ctrl-Shift-Tab → Shift-Tab, Shift/Ctrl-Escape → Escape. Smallest change, consistent with #0393, keeps TUIs intact, does nothing for the `alt`/`super` combinations (which should probably stay raw).
2. **Re-add targeted Ghostty keybinds** (`ctrl+tab=next_tab` etc.). Only works for actions libghostty can perform; Batty's Tab model is not libghostty's, so `next_tab` would do nothing useful here. Not recommended for Tab; noted so it is not re-proposed.
3. **Claim Ctrl-Tab / Ctrl-Shift-Tab in `ShortcutAction`** as alternate (or new default) bindings for Show Next/Previous Tab. Matches upstream Ghostty and browsers. Needs the collision check `issues/0309.md` describes and a `docs/shortcuts.md` update.

A likely combination: 3 for Ctrl-Tab / Ctrl-Shift-Tab, 1 for Shift/Ctrl-Escape, leave `alt`/`super` combinations raw, decide Option-Up/Down from the Terminal.app comparison.

### `keybind = clear` inventory (starting point; verify against the ref the build links)

Platform-independent (`Config.zig:6542-6721`, `:7001-7023`): `ctrlOrSuper(...)` resolves to **super** on macOS (`src/input/key.zig:862-865`), so most of these are Cmd-chords on this platform: Cmd-Shift-, reload_config, Cmd-, open_config, Cmd-C / Cmd-V copy/paste (performable), Cmd-= / Cmd-+ / Cmd-- / Cmd-0 font size, Cmd-Shift-J (and variants) write_screen_file, **Shift-arrows / Shift-Home / End / PgUp / PgDn adjust_selection (performable)**, **Ctrl-Shift-Tab / Ctrl-Tab previous/next tab**, Cmd-Return toggle_fullscreen (`:7005`), Cmd-Shift-Return toggle_split_zoom (`:7012`), Cmd-Shift-P command palette. macOS-only (`:7024-7310`): Cmd-Q, Cmd-K clear_screen, Cmd-A select_all, Cmd-Z / Cmd-Shift-Z undo/redo, Cmd-Home/End/PgUp/PgDn scroll, Cmd-J scroll_to_selection, Cmd-Up/Down (+Shift) jump_to_prompt, Cmd-N / Cmd-W (+Alt/Shift) window/surface/tab close, Cmd-T, Cmd-Shift-[ / ], Cmd-D / Cmd-Shift-D splits, Cmd-[ / ] and Cmd-Alt-arrows goto_split, Cmd-Ctrl-arrows / Cmd-Ctrl-= resize/equalize splits, Cmd-F / Cmd-E / Cmd-Shift-F / **Escape (performable) end_search** / Cmd-G search, Cmd-1..9 goto_tab, and the five natural-text-editing `text:`/`esc:` bindings above. Non-Darwin blocks (`:6581-6613`, `:6722-6932`) do not apply.

Split: (a) wanted gone — every Cmd-chord Batty routes to its menu / `ShortcutAction` (`docs/shortcuts.md:270-287`); (b) re-added — Cmd-C and the five natural-text-editing bindings plus Batty's own `alt+backspace`; (c) removed by accident — **Ctrl-Tab / Ctrl-Shift-Tab**, Shift-arrow selection adjustment (performable, harmless to lose but a real Ghostty feature), the performable bare-Escape `end_search` (Batty has no libghostty search UI, so moot), Cmd-Return / Cmd-Shift-Return (Batty does not use them; with `clear` they now fall into the Return table as `27;9;13~` / `27;10;13~` unless the host swallows Cmd-chords before `ghostty_surface_key`, which the matrix should check). Items in (c) each need a one-line decision in the write-up, not necessarily a code change.

## Open questions

1. **Ctrl-Tab / Ctrl-Shift-Tab: claim as Next/Previous Tab, or just neutralise?** Claiming matches upstream Ghostty, Safari, Chrome and Terminal.app (which also switches tabs on Ctrl-Tab); it adds a non-Cmd chord to a shortcut set that is otherwise all Cmd, and takes Ctrl-Tab away from any TUI that wanted `27;5;9~` (few do; Kitty-protocol apps still get their own encoding when the foreground is not a lone shell, if the shortcut layer checks the same gate). User decision.
2. **Over ssh: leave as upstream (recommended), or downgrade for unknown foreground processes, or ship remote shell integration?** See "Over ssh" in Notes. A downgrade would break Shift-Enter in any remote Claude Code / vim and is not recommended.
3. **Option-Up / Option-Down at a prompt: what should they do?** Terminal.app's behaviour is the agreed reference but has not been recorded. If Terminal.app sends `ESC[1;3A` too, the answer may be "nothing to fix at the prompt" and this sub-case closes as a documentation note.
4. **Should the `alt`/`super` combinations of Return/Tab/Escape stay raw?** They are the least likely to be pressed by accident and some carry meaning in TUIs. Default: leave raw, document.
5. **Target release.** Proposed after 1.2.0 (`main`, next minor), since #0393 covers the reported key. If the user wants Ctrl-Tab fixed for 1.2.x, it would be fixed on `main` first and cherry-picked to `release/1.2` per AGENTS.md.
