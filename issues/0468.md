## Description

Reported by the user while testing Batty Beta built from `main` at `526c7a45`
for the 1.2.0 release: "Shift-enter looks alright but cmd-enter outputs these
characters. `;9;13~`". Shift-Return is #0393's fix working. Cmd-Return is the
same bug on a modifier #0393 deliberately left alone: libghostty encodes
Cmd-Return as `ESC[27;9;13~` (xterm modifier 9 = 1 + 8, Super/Cmd), zsh has no
binding for it, and the tail after the bound `ESC[` prefix self-inserts.

**Decided (user, 2026-10-11): Cmd-Return acts like plain Return, matching
Terminal.app.** The user's words: "cmd-enter in Apple's Terminal app just acts
like Enter. Do that." The scope is therefore: extend #0393's
`PlainShellKeyRewrite` so Cmd-Return (and Cmd-keypad-Enter) is rewritten to a
plain Return under exactly the conditions it already applies to Shift- and
Ctrl-Return — the pty's foreground process group is a lone sh-family shell, and
no IME text is marked. What a TUI such as Claude Code should receive, and what
to do about the *other* unbound Cmd-modified keys, stay open below.

**Target: 1.2.0.** The user hit this in release testing. `MARKETING_VERSION` is
already `1.2.0` on the working tree and no `release/1.2` branch exists yet
(`git branch --list 'release/*'` is empty; the newest tag is `v1.1.0`), so the
fix lands on `main` through the normal issue workflow before the release is
cut; no cherry-pick is needed.

This is the urgent 1.2.0 slice of #0462, which inventories everything
`keybind = clear` removed and already lists Cmd-Return / Cmd-Shift-Return under
"removed by accident" with the note that "with `clear` they now fall into the
Return table as `27;9;13~` / `27;10;13~` unless the host swallows Cmd-chords
before `ghostty_surface_key`, which the matrix should check"
(`issues/0462.md`, "`keybind = clear` inventory"). The user's report answers
that check: the host does not swallow it. #0462 keeps the rest of the inventory
and stays targeted after 1.2.0.

## Steps to reproduce

Beta only (`./build.sh`); never the user's Prod app.

1. Open a Pane at a zsh prompt (`zsh -f` for the stock keymap; the user's
   oh-my-zsh prompt reproduces too).
2. Type `echo hi`.
3. Press **Cmd-Return**.
4. For comparison press **Shift-Return** (runs the command since #0393) and
   **Return**.
5. Optionally, with `cat -v` running in the foreground, press Cmd-Return and
   read the echoed bytes: expected `^[[27;9;13~`.

## Expected behavior

Acceptance criteria:

1. **Cmd-Return at a lone zsh/bash/sh-family prompt runs the command**, exactly
   as plain Return and as Terminal.app does. No printable characters are
   inserted. Cmd-keypad-Enter (key code 76) behaves the same way, as #0393
   already covers for Shift and Ctrl (`PlainShellKeyRewrite.returnKeyCodes`,
   `BattyKit/Sources/BattyKit/Commands/PlainShellKeyRewrite.swift:19`).
2. **Same gate as #0393, no new gate.** The rewrite applies only when the first
   responder is `AppTerminalView`, `hasMarkedText()` is false, the foreground
   process group's leader is in `plainShellNames`, and
   `groupMemberCount == 1` (`PlainShellKeyRewrite.swift:81-91`). Everything
   else keeps the full `ESC[27;9;13~` encoding: Claude Code, vim, nvim, less,
   fish, an `ssh` session. Whether to go further for TUIs is open question 1,
   not this criterion.
3. **Shift-, Ctrl- and Ctrl-Shift-Return keep working** (#0393's
   `ShiftEnterTests` still passes) and **Option-Return is unchanged**: it is
   gated in the table (`.set` → `ESC CR`, `function_keys.zig:202`), is correct
   for a shell, and #0462 owns the Option combinations.
4. **Cmd-Shift-Return, Cmd-Option-Return, Cmd-Ctrl-Return and the other
   Super combinations of Return (`27;10`-`27;16`) are decided explicitly** in
   the work log: either rewritten to plain Return along with Cmd-Return, or left
   raw with a one-line reason. The recommendation below is to rewrite every
   Super combination of Return that `strippedModifiers` can express as "drop
   Cmd, then apply the existing Shift/Ctrl rule", and to leave combinations
   that include Option raw, since Option-Return is #0462's.
5. **No change to libghostty's config.** `keybind = clear` and the seven
   re-added bindings in `TabRuntime.swift:319-326` stay as they are; the fix is
   host-side in the `NSEvent` monitor, like #0393. A `keybind =
   super+enter=text:\r` would also hide the symptom but would fire inside every
   TUI as well, which is the choice open question 1 reserves for the user.
6. **Unit tests** in `PlainShellKeyRewriteTests` cover Cmd-Return → plain
   Return for zsh and bash, Cmd-Return left alone for `claude`, `vim`, `fish`
   and a nil process name, Cmd-Return left alone when the group has more than
   one member, Cmd-keypad-Enter, and whichever answer criterion 4 records for
   Cmd-Shift-Return. The existing
   `optionAndCommandReturnAreLeftAlone` test
   (`BattyKit/Tests/BattyKitTests/PlainShellKeyRewriteTests.swift:103-108`)
   currently pins `rewritten([.command]) == nil` and
   `rewritten([.shift, .command]) == nil`; it must be inverted or split, not
   deleted, so Option-Return keeps its guard.
7. **UI test** in the Tart VM modelled on `BattyUITests/ShiftEnterTests.swift`:
   type `touch '<sentinel>'`, press `app.typeKey(.return, modifierFlags:
   .command)`, assert `BattyUITestHarness.waitForFile(at:timeout:)` sees the
   file. Prove it fails on `main` before the fix (#0393 did this; see its
   `## Verification`).
8. `./build.sh`, `./build.sh unit` and the VM UI suite pass. `docs/shortcuts.md`
   gets a sentence under "The libghostty keybind-clear" (`docs/shortcuts.md:265`)
   saying which modified Return chords the host rewrites and why.

### Why Cmd-Return reaches the key encoder at all (every hop grepped)

1. **The `NSEvent` local monitor sees it first and passes it through.**
   `Batty/BattyApp.swift:83-84`:
   `BattyShortcuts.handle(event) ? nil : PlainShellKeyRewrite.rewrite(event)`.
   - `BattyShortcuts.handle` (`BattyKit/Sources/BattyKit/Commands/BattyShortcuts.swift:20-80`)
     builds a `ShortcutBinding` candidate; `RecorderView.specialKey(forKeyCode:)`
     does map `kVK_Return` to `.return` (`BattyKit/Sources/BattyKit/Shortcuts/RecorderView.swift:177-189`),
     but no `ShortcutAction` default binds Return with any modifier
     (`BattyKit/Sources/BattyKit/Shortcuts/ShortcutAction.swift:98-183`: the
     special-key defaults are Cmd-Option-arrows for focus and Cmd-Ctrl-arrows
     for resize, nothing else). The positional `switch` matches digits only
     (`BattyShortcuts.swift:55-77`). It returns `false`.
   - `PlainShellKeyRewrite.rewrite` (`PlainShellKeyRewrite.swift:80-96`) calls
     `strippedModifiers`, which requires the held modifiers to be a non-empty
     subset of `[.shift, .control]` (`:42-46`). Cmd fails that guard, so the
     event is returned unchanged before any `proc_*` call. This is the one
     line the fix changes.
2. **AppKit offers it as a key equivalent and nobody takes it.** Cmd-modified
   key events go through `performKeyEquivalent` before `keyDown` (general
   AppKit behaviour).
   - `AppTerminalView.performKeyEquivalent`
     (`BattyKit/.build/checkouts/libghostty-spm/Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView+Input.swift:27-96`):
     `keyIsBinding` asks `ghostty_surface_key_is_binding` (`:272-287`). Batty's
     config is `keybind = clear` plus seven bindings
     (`BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:319-326`:
     `cmd+c`, `super+left`, `super+right`, `super+backspace`, `alt+left`,
     `alt+right`, `alt+backspace`), none for Enter, so it is false. The `case
     "\r"` arm then requires `.control` (`:39-43`) and returns `false` for
     Cmd-Return.
   - **Menu bar**: `BattyCommands` key equivalents come from
     `ShortcutsStore` (`BattyKit/Sources/BattyKit/Commands/BattyCommands.swift:493-534`
     and siblings), none of which is Return. The only `.defaultAction` /
     Return equivalents in the app are sheet buttons
     (`BattyKit/Sources/BattyKit/Views/RenameTabSheet.swift:27`,
     `PasteConfirmation.swift:55`, `SessionSidebarView.swift:433`) that exist
     only while their sheet is up.
   - With no taker, AppKit delivers the event as `keyDown` to the first
     responder (general AppKit behaviour; the Cmd/Ctrl echo-dedup state in
     `performKeyEquivalent`'s `default:` arm, `AppTerminalView+Input.swift:53-73`,
     exists because exactly this double delivery happens for Cmd/Ctrl keys).
3. **The host forwards it to libghostty with Super set.**
   `AppTerminalView.keyDown` → `TerminalKeyEventHandler.handleKeyDown`
   (`TerminalKeyEventHandler@AppKit.swift:39-80`) → `buildKeyInput`, which maps
   `.command` to `GHOSTTY_MODS_SUPER` (`TerminalInputModifiers.swift:44`) and
   leaves Cmd out of `consumed_mods` (`TerminalKeyEventHandler@AppKit.swift:256-259`)
   → `ghostty_surface_key` (`Sources/GhosttyTerminal/Surface/TerminalSurface.swift:37`).
4. **libghostty's legacy encoder hits the unconditional table.** Kitty flags
   are zero at a shell prompt, so `legacy()` runs (`src/input/key_encode.zig:327`).
   It consults `pcStyleFunctionKey` first (`:343-351`, function at `:607-669`).
   The Return table (`src/input/function_keys.zig:198-223`) has
   `.{ .mods = .{ .super = true }, .sequence = "\x1b[27;9;13~" }` at `:213`
   with `modify_other_keys` left at its default `.any` (`:42`), and `.any`
   entries match in every mode (`key_encode.zig:652-656`), needing only an exact
   modifier match (`:658-665`). The IME exception (`:361-374`) skips the table
   only when the event carries committed text, which Cmd-Return does not. The
   bytes `ESC [ 2 7 ; 9 ; 1 3 ~` go to the pty.
5. **zsh self-inserts the tail.** Stock `zsh -f` binds `^[[A`-`^[[D`, `^[OA`-
   `^[OD` and `^[[200~` (#0462, "What zsh does with them"); ZLE walks the
   longest bound prefix and self-inserts the rest. With the user's keymap the
   visible tail is `;9;13~`, matching #0393's `;2;13~` mechanism exactly.

Why Ghostty.app itself never shows this: its default config binds
`ctrlOrSuper(.{}) + enter` to `toggle_fullscreen`
(`src/config/Config.zig:7005`) and `ctrlOrSuper(.{ .shift = true }) + enter`
to `toggle_split_zoom` (`:7012`), and `ctrlOrSuper` sets `super` on Darwin
(`src/input/key.zig:862-868`), so the binding consumes Cmd-Return before the
encoder runs. Batty's `keybind = clear` (`TabRuntime.swift:319`, added in #0062
to keep libghostty's Cmd-chords out of the way of the menu) removed that
binding and the key fell through into the table. The binding was never wanted
in Batty (there is no libghostty-driven fullscreen here), but removing it
exposed the table entry.

**Not affected**, for the record:

- Cmd-Left / Cmd-Right / Cmd-Backspace: Batty re-binds them to
  `text:\x01` / `\x05` / `\x15` (`TabRuntime.swift:321-323`), so
  `keyIsBinding` is true and the encoder never runs. Cmd-Shift-Backspace and
  the other Super+Backspace entries are gated `.set` → `\x7f` in normal mode
  (`function_keys.zig:142-149`): harmless.
- Cmd-Option-arrows and Cmd-Ctrl-arrows: claimed by `ShortcutAction`
  (`ShortcutAction.swift:137-148`, `:169-180`) in the monitor, before AppKit.
- Cmd-letter and Cmd-punctuation keys with no binding (Cmd-G, Cmd-J, Cmd-K,
  Cmd-Z, …): on macOS the legacy encoder emits nothing for Super+text
  (`key_encode.zig:536-547`, with tests at `:2499-2522` expecting the empty
  string). They are silent, not garbage. One edge: the `modifyOtherKeys`
  mode-2 branch (`:418-470`) runs before that return, so after an application
  has set `CSI > 4;2 m` and exited without resetting it (the "bad state" #0393
  described), an unbound Cmd-letter would emit `ESC[27;9;<codepoint>~`. That
  is a leaked-mode problem of the same shape as #0465's leaked mouse mode and
  is out of scope here.

### Implementation sketch (for the implementer; the orchestrator decides the branch)

The smallest change consistent with #0393 is in `strippedModifiers`
(`PlainShellKeyRewrite.swift:42-46`): allow `.command` in the permitted set and
subtract it along with `.shift` and `.control`, so Cmd-Return, Cmd-Shift-Return
and Cmd-Ctrl-Return all become plain Return at a lone shell prompt, while any
chord including `.option` is still returned unchanged (`held.isSubset(of:
[.shift, .control, .command])`). `rewrittenEvent` (`:64-77`) already builds a
clean `\r` event with the reduced flags, and `buildKeyInput` derives
`GHOSTTY_MODS_*` from the event's own `modifierFlags`
(`TerminalKeyEventHandler@AppKit.swift:250`), so the rewritten event
carries no Super and the encoder takes the plain `\r` entry
(`function_keys.zig:222`). The doc comment at `PlainShellKeyRewrite.swift:8-17`
names Shift and Ctrl only and must be updated.

Two things to watch:

- The event the monitor returns still goes through AppKit's key-equivalent
  pass. Without Cmd it is an ordinary keyDown, which is the path #0393's
  Shift-Return already takes, so no new routing is involved.
- `foregroundPid` comes from `ghostty_surface_foreground_pid`
  (`TerminalSurface.swift:413-417`; host doc comments there and in
  `TerminalView+Process.swift:22` still say it is always nil on "the pinned
  Ghostty 1.3.1", which is stale: #0393's `ShiftEnterTests` passes in the VM,
  so the pid is populated on the ref `main` links). Nothing to change, but
  do not be misled by those comments.

#0464 (open) proposes merging this guard's "lone plain shell" check with
`StuckMouseReportGuard`'s. This issue should not wait for it; whichever lands
second adapts.

## Decided

- **Cmd-Return at a plain shell prompt acts like plain Return**, matching
  Terminal.app (user, 2026-10-11). Mechanism: #0393's `PlainShellKeyRewrite`,
  same conditions (lone sh-family foreground process group, no marked IME
  text). This supersedes an earlier same-day decision to swallow the key.

## Open questions

1. **Should a TUI such as Claude Code receive Cmd-Return as plain Return, or
   keep the modified key (`ESC[27;9;13~`)?** The decided mechanism keeps the
   modified key for any foreground program that is not a lone plain shell,
   exactly as Shift-Return does today (Claude Code uses Shift-Return for a
   newline, and would lose that if the host flattened it). **Recommendation:
   same treatment as Shift: keep the modified key for TUIs.** A program that
   wants Cmd-Return as Enter can bind the sequence itself; a host-side
   flattening cannot be undone by the program.
2. **Should every unbound Cmd-modified key be kept from the pty?** The derived
   list above (Cmd-Escape, Cmd-Up/Down, Cmd-Shift-arrows, Cmd-Home/End/PgUp/PgDn,
   Cmd-Forward-Delete, Cmd-F-keys, and the Super combinations of Escape/Tab) is
   the candidate set for the same lone-shell treatment: drop Cmd and send the
   unmodified key, or send nothing. None was reported, and the arrow/editing
   family is at least a well-formed sequence a TUI can use. **Recommendation:
   do not expand this issue beyond Return.** Move the list to #0462's
   inventory (its criterion 1 already covers the Return/Tab/Escape table; the
   arrow/editing rows are new) and decide them there after 1.2.0, with
   Terminal.app as the reference for each. If the user wants Cmd-Escape or
   Cmd-Up/Down in 1.2.0 as well, say so and the implementer can add the key
   codes to the same rewrite; the gate and tests are shared.
3. **Cmd-Shift-Return and Cmd-Ctrl-Return** (criterion 4): rewrite with
   Cmd-Return (recommended, falls out of the one-line change) or leave raw?

## Resolution

- `PlainShellKeyRewrite.strippedModifiers` now accepts any non-empty subset of {Shift, Control, Command} and removes all three, so at a lone-shell prompt Cmd-Return, Cmd-Shift-Return and Cmd-Ctrl-Return (and keypad Enter) arrive as plain Return, matching Terminal.app. Any chord that includes Option is left unchanged.
- The gates are the same as for #0393:
  - the first responder is `AppTerminalView`;
  - no IME text is marked;
  - a single plain shell holds the foreground process group;
  - key code and modifiers are checked first.
- TUIs such as Claude Code and vim still receive the modified key. Caps Lock, numericPad and device-dependent flags pass through.
- A user's own Cmd-Return binding in Settings → Shortcuts still wins, because `BattyShortcuts.handle` runs before the rewrite. No menu item or default `ShortcutAction` uses Return.
- `docs/shortcuts.md` lists which modified Return chords the host rewrites.
- Other unbound Cmd keys (Cmd-Up/Down, Cmd-Escape, Cmd-Forward-Delete and others) are left to #0462.
