## Description

A fully passing `tools/run-ui-tests-vm.sh` run produces an `.xcresult` with zero attachments — no screen recording, no screenshot, nothing — so the suite that proves a feature works (for example the 29 CLI remote-control tests from #0413) leaves no footage of it. XCTest *does* record every UI test in the VM; it then discards the recording whenever the test passes, because every attachment is stored with `lifetime = deleteOnSuccess`, the Xcode default for system attachments. The only recordings the runner has ever returned are of tests that failed. There is no switch in the runner, the scheme, or the docs to change that, and no helper to turn an `.xcresult` into viewable `.mp4` files once it does.

Verified on 2026-10-09 against two existing result bundles in `build/ui-tests/`:

| Run | Outcome | Bundle size | `Attachments` rows | `public.mpeg-4` rows |
|---|---|---|---|---|
| `20261009-154250-31272` (CLI suite, #0413 run 5) | 29/29 passed | 1.4 MB | 0 | 0 |
| `20261006-003524-26742` (full suite) | 49 passed / 25 failed of 75 | 152 MB | 325 | 25 |

- `xcrun xcresulttool export attachments --path build/ui-tests/20261009-154250-31272/UITests.xcresult --output-path <dir>` prints `Skipped export for <test>: no matching attachments` for every one of the 29 tests and writes a 4-byte `manifest.json` (`[]`).
- `sqlite3 build/ui-tests/20261009-154250-31272/UITests.xcresult/database.sqlite3 "select count(*) from Attachments"` → `0`.
- In the failing run, `select lifetime, uniformTypeIdentifier, count(*) from Attachments group by 1,2` → `deleteOnSuccess|com.apple.dt.xctest.element-snapshot|25`, `deleteOnSuccess|public.mpeg-4|25`, `deleteOnSuccess|public.plain-text|275`. The 25 MP4 rows are all named `kXCTAttachmentScreenRecording`, and the export manifest lists exactly one MP4 per test, for exactly the 25 tests `xcresulttool get test-results tests` reports as `Failed` (`SettingsTests/testCmdCommaOpensSettings()`, `SettingsTests/testSettingsDefaultsToGeneralPane()`, …). No passing test in that run has any attachment at all.

So the mechanism is not "recording is off" — the guest records each test and keeps the file only when the test fails. The `lifetime` column is the attachment lifetime policy XCTest applies to system-generated attachments (screen recordings, UI snapshots, element hierarchies). Its value comes from the test configuration, not from test code.

### Where the setting lives (checked, not yet exercised)

- The runner invokes `xcodebuild -workspace Batty.xcworkspace -scheme 'Batty UI Tests' … build-for-testing` and then `… -resultBundlePath $GUEST_RESULTS/UITests.xcresult -only-testing:… test-without-building` (`tools/run-ui-tests-vm.sh`, the two `run_guest_step` calls around lines 461 and 478). It passes no `-testPlan` and nothing attachment-related.
- There is no `.xctestplan` anywhere in the repo (`find . -name '*.xctestplan'` outside `build/` and `.build/` finds nothing), and `xcodebuild -help` on this host (Xcode 27.0) does list `-testPlan` and `-showTestPlans`.
- `Batty.xcodeproj/xcshareddata/xcschemes/Batty UI Tests.xcscheme`'s `<TestAction>` carries only `buildConfiguration`, the debugger/launcher identifiers and `shouldUseLaunchSchemeArgsEnv`. It has no `systemAttachmentLifetime`, `userAttachmentLifetime`, or screen-capture attribute, so Xcode's defaults apply — and the result bundles above show that default is `deleteOnSuccess`.
- The summary of both bundles reports `"testPlanConfiguration" : { "configurationName" : "Test Scheme Action" }`, i.e. the scheme's own implicit configuration, consistent with no test plan being in play.

The likely fix is one of two equivalent routes, both of which set the system attachment lifetime to keep-always for the run that wants footage. Neither has been tried in this repo yet, so the implementer should verify in the VM rather than assume:

1. **A test plan** (`BattyUITests.xctestplan` or similar, referenced from the `Batty UI Tests` scheme) whose default options set the system attachment lifetime (and user attachment lifetime) to `keepAlways` and the preferred screen-capture format to screen recording, selected on the test step with `-testPlan <name>`. A second, default-lifetime plan (or no `-testPlan`) keeps today's behaviour for routine runs.
2. **Scheme-level attributes** on the `TestAction` (`systemAttachmentLifetime="keepAlways"`, `userAttachmentLifetime="keepAlways"`, plus the screen-capture format attribute) — simpler, but then there is no per-run switch short of editing the tracked `.xcscheme`, which is already a file Xcode rewrites as build residue (`BuildableName`, per `AGENTS.md`), so a test plan is the more controllable option.

Whichever route is taken, the exact attribute/key names and the accepted values on Xcode 27 should be confirmed from a scheme or test plan Xcode itself writes (toggle the setting in the scheme editor's Test → Options tab and diff), not typed from memory.

### Why default-off

The failing-run bundle above is 152 MB for 25 recordings; a full 75-test suite with every recording kept would be in the hundreds of MB per run, under the gitignored `build/ui-tests/<run-id>/` which is never pruned. Keeping recordings must be opt-in.

## Steps to reproduce

1. Commit, then `tools/run-ui-tests-vm.sh BattyUITests/CLIRemoteControlTests BattyUITests/CLIViewPaneTests` (or any class known to pass).
2. Wait for `RESULT: TEST SUCCEEDED`.
3. `xcrun xcresulttool export attachments --path build/ui-tests/<run-id>/UITests.xcresult --output-path /tmp/att`
4. `ls /tmp/att` and `sqlite3 build/ui-tests/<run-id>/UITests.xcresult/database.sqlite3 "select count(*) from Attachments"`.

## Expected behavior

- An opt-in runner switch — e.g. `BATTY_UI_KEEP_RECORDINGS=1 tools/run-ui-tests-vm.sh …` (named and shaped like the existing `BATTY_UI_FULL_APP_LOG=1`) — makes the guest's test step keep the screen recording for every test, passing or failing, so the resulting `UITests.xcresult` has one `public.mpeg-4` attachment per test executed. Off by default: a plain run still produces today's failure-only bundles.
- A small helper under `tools/` (e.g. `tools/export-ui-test-recordings.sh <path/to/UITests.xcresult> [out-dir]`) that exports the recordings from an `.xcresult` to one `.mp4` per test, named after the test (`<Class>.<testMethod>.mp4`, derived from the `manifest.json` that `xcresulttool export attachments` writes, not the random UUID filenames it uses), plus a `.poster.png` per clip via `qlmanage -t` (the recipe `issues/Issues.md` already documents for attachments). Stock macOS tools only; no new dependencies.
- `docs/ui-testing-vm.md` documents the switch, the size cost, the helper, and where the setting lives (scheme vs. test plan), next to the existing `BATTY_UI_FULL_APP_LOG` note. `tools/README.md` gets a section for the helper.
- The `.xcresult` from a switched-on run is still pulled back by the runner's existing `pull_results` tar step without changing its bounds, or the bounds are raised and the reason recorded (a 300–500 MB bundle over `tart exec … tar` may need more than the current 90 s guest alarm / 120 s host bound).

## Actual behavior

Passing tests leave no attachments. Only failed tests have a screen recording, and only because the default `deleteOnSuccess` lifetime happened not to delete it. There is no documented way to keep footage of a green run and no helper to extract clips from a bundle.

## Acceptance

- A VM run with the switch on, over a class that passes (the #0413 CLI classes are the motivating case), yields a `UITests.xcresult` whose `Attachments` table contains one `public.mpeg-4` row per test executed, and `xcrun xcresulttool export attachments` writes one MP4 per test with the test's identifier in the manifest.
- The helper exports those clips to `<Class>.<testMethod>.mp4` + `.poster.png` files from the pulled-back bundle on the host.
- A run without the switch is byte-for-byte the same invocation as today (no `-testPlan`, or the default plan) and still produces a bundle with 0 attachments for an all-pass run.
- `./build.sh unit` and `./build.sh ui-typecheck` still pass; nothing in `scripts/` is touched.

## Notes

- Relation: motivated by #0413 (the CLI remote-control suite whose footage was wanted) and #0447 (its follow-up); builds on the runner from #0412 and the opt-in environment-variable pattern from #0444 (`BATTY_UI_FULL_APP_LOG`).
- The element-snapshot and plain-text attachments (UI hierarchy dumps, `Debug description for …` texts) share the same `deleteOnSuccess` lifetime and would come along for the ride when the lifetime becomes keep-always; the helper should filter to `*.mp4` (`xcresulttool export attachments --filter`) rather than exporting everything.
- `xcresulttool export attachments` has `--test-id`, `--filter <glob>` and `--only-failures` options on Xcode 27 (`xcrun xcresulttool export attachments --help`), which is enough for the helper without parsing `database.sqlite3` directly; the sqlite queries above are diagnostic evidence, not a proposed implementation.
- The runner and the doc describe the `.xcresult` as a result artifact but never mention attachments or recordings; `docs/ui-testing-vm.md` even records (first-run table, "Prompts in the guest" row) that nothing captured a guest screenshot to check for prompts — kept recordings would answer that kind of question too.

## Gotchas

- A freshly pulled `.xcresult` has no `database.sqlite3` until xcresulttool first opens it;
  running `sqlite3` on it first creates an empty file and fails with "no such table". Run an
  xcresulttool command first, or use `sqlite3 -readonly`.
- The helper creates the output directory even when there are no recordings.
