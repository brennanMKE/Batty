## Description

An Xcode-style "Open Quickly" panel: press **Cmd-Shift-O**, type a few characters, see a fuzzy-matched list of named sessions and tabs across the current window, hit Return to jump straight to that session and tab. Xcode uses Cmd-Shift-O to match source files in a project; Batty's parallel is matching the navigable units of the multiplexer.

The killer use case: a dozen sessions are open, each with multiple tabs running different long-lived processes (`web`, `worker`, `db`, `tail-logs`, …). Cmd-Shift-O → `wor` → focus jumps to the right tab in the right session in one beat.

## Acceptance criteria

- Cmd-Shift-O from anywhere in the app opens a centered translucent sheet with a search field and a results list.
- The corpus searched is: every session name + every tab title in the current window. Result rows show `Session name › Tab title` (right-chevron separator), with the matched substring(s) highlighted in the row.
- Typing filters by case-insensitive fuzzy match (subsequence match, then ranked by tightness of match and recency of focus — recent-first feels right when the user is jumping back-and-forth between two areas).
- Up / Down arrow keys move selection; Return activates: brings the chosen session forward in the sidebar, focuses the chosen tab in its pane, and gives keyboard focus to the terminal. Esc dismisses without action.
- An empty query shows the most-recently-focused sessions/tabs ordered by recency — supports "Cmd-Shift-O, Return" as a quick toggle between two locations.
- Sessions and tabs with auto-derived titles (`#0089`) participate normally — what the sidebar / tab chip displays is what the panel searches against.

## Out of scope

- Searching panes by themselves (panes don't have user-facing names; tabs are the right granularity).
- Searching terminal content (scrollback). That's `Cmd-F`, a separate feature.
- Searching across multiple windows. Until multi-window lands (`#0027`), the corpus is the single window's content.
- Filtering by session-color tag or any other dimension. Pure name match for v1.
- Surfacing in-app commands. Those belong to the command palette (`#0126`); the two features are intentionally distinct entry points with distinct domains.

## Notes

- Xcode parallel: Cmd-Shift-O in Xcode matches *files in the project*. Batty's Cmd-Shift-O matches *places you can put your cursor*. Same keyboard shortcut, same fuzzy-find shape, different corpus.
- Related to `#0126` (command palette): both are fuzzy-find panels. Worth deciding whether they share a generic `FuzzyFinder<T>` SwiftUI component, or remain independent. Lean toward shared — the corpora differ but the row chrome, keyboard navigation, and highlight logic are identical.
- Fuzzy ranking: subsequence match is the table-stakes algorithm. For ranking, prefer contiguous matches over scattered ones (e.g. `wor` in "worker" beats `wor` in "wandering-orange"), then break ties by recency. A small Swift fuzzy-matcher (≈100 lines) is plenty — no need for an external dependency.
- Recency: track per-session and per-tab `lastFocusedAt: Date?` in the runtime store. Reset on every focus change.
- The bell feed (`#0027`) is the most-similar existing UI surface — popover with a list, click-to-jump. Match its visual style for consistency, but Open Quickly is a centered sheet (more prominent, keyboard-driven), not an anchored popover.

## Fix

- Added `openQuickly` to `ShortcutAction` (alongside `commandPalette` in `#0126`) with default binding Cmd-Shift-O. `BattyShortcuts.run` dispatches it by posting `battyToggleOpenQuickly`.
- `AppStateStore.jumpToTab(sessionID:tabID:)` (new) mirrors `jumpToBellEntry` — selects the session, focuses the containing pane, activates the tab.
- `OpenQuicklyView` (new) builds `[QuickOpenResult]` from all sessions × panes × tabs, using `TabTitleFormatter.chipTitle` for tab names (same text as chip row). Displays as `Session › Tab` rows. Fuzzy filtering and keyboard navigation via `FuzzyMatcher` (shared with `#0126`). Return calls `store.jumpToTab`; Esc dismisses.
- `SessionDetailView` listens for `battyToggleOpenQuickly` and presents the sheet.

## Gotchas

- **No recency tracking in v1.** The empty-query corpus shows sessions/tabs in sidebar order (sessions first, tabs within each session). A `lastFocusedAt: Date?` field on `SessionRuntime` and `TabRuntime` would enable true recency ordering; deferred.
- **No match highlight on result rows.** The acceptance criteria asks for matched substring highlighting. Implementing attributed-string highlighting with SwiftUI `Text` requires character-level match tracking. Deferred — the list is filtered correctly; highlight is a cosmetic improvement.
- Presentation is a macOS sheet, same note as `#0126`.

## Re-opened

**Reported by user 2026-05-18:** the fuzzy filter is wrong. With sessions named `Cat`, `Dog`, `Bird`, `Cabybara` (×3 — typo of "Capybara" but irrelevant to this bug), typing `bird` filters the list to just **`Cat`**. Expected: `Bird` should be the top (and likely only) match — `bird` is a contiguous case-insensitive substring of `Bird`.

The v1 `## Gotchas` claim that "the list is filtered correctly; highlight is a cosmetic improvement" was wrong. Filtering itself is broken.

**Where the bug likely lives:** `BattyKit/Sources/BattyKit/Util/FuzzyMatcher.swift` (the shared matcher used by both `OpenQuicklyView` and the `#0126` command palette). Possible failure modes to check, in order of likelihood:

1. Score/comparator is inverted — a higher-scoring match is being treated as worse, so the best match falls off the visible list and an arbitrary other entry surfaces. "Cat" appearing for "bird" suggests the matcher is returning *something* (otherwise the list would be empty) but the wrong entry; an inverted score would do that.
2. The matcher matches against the wrong field on each `QuickOpenResult` — e.g., always matching against the first session's name, or against a constant, or against tab content rather than display title. The shape `Cat › ~` is "Session › Tab"; `bird` matches neither `Cat` nor `~`, so the matcher is finding a subsequence in some other string and the row label is decoupled from what was actually matched.
3. The result row's display is decoupled from the underlying result identity — the matcher might return the correct *index* but the SwiftUI `ForEach` renders the wrong row label (e.g., capturing the full list by index instead of mapping the filtered results).

**How to reproduce:**

1. Create four sessions named `Cat`, `Dog`, `Bird`, `Capybara`.
2. Press **Cmd-Shift-O**.
3. Type `bird`.
4. Observe: only `Cat › ~` is shown instead of `Bird › ~`.

Verified screenshot in user-attached image; symptom is reliable.

**Acceptance criterion for the fix:** typing `bird` shows `Bird` as the only (or top-ranked) result. Add unit tests against `FuzzyMatcher` that cover this exact case plus the contiguity rules from the v1 spec (e.g., `bird` ranks `Bird` above `Bigger redbird`).

## Re-resolution

The `FuzzyMatcher` itself was correct — the bug was a combination of failure modes 2 and 3 from the Re-opened hypothesis list. `OpenQuicklyView` matched against the composite `"Session › Tab"` `displayTitle`, so an incidental subsequence hit in one field surfaced a row whose visible label was dominated by the unrelated field. Compounding this, `QuickOpenResult.id` was assigned `UUID()` and the computed `allResults` / `filteredResults` properties regenerated those UUIDs on every read, while `body` read `filteredResults` multiple times per evaluation. `LazyVStack` plus an unstable `ForEach` id and the inner `.id(idx)` left SwiftUI with no consistent identity to track, which is the exact shape of "correctly-filtered result rendered with the wrong row label."

Scoring now runs against `sessionTitle` and `tabTitle` independently and takes the max, so either field can surface a row and ties break toward higher-quality matches. The filter is extracted into a pure `OpenQuicklyFilter.apply(query:to:)` so it is testable in isolation. `QuickOpenResult.id` is derived from `tabID` (already globally unique), and `body` snapshots `filteredResults` into one local `let` that is threaded through `ForEach`, key handlers, and activation so every read in a render sees the same list.

### Files changed

- `BattyKit/Sources/BattyKit/Views/OpenQuicklyView.swift` — promoted `QuickOpenResult` to internal with `id = tabID`, added `OpenQuicklyFilter` enum holding the filter/rank logic, snapshotted `filteredResults` into a single `let` inside `body`, scrolled by result `id` instead of index.
- `BattyKit/Tests/BattyKitTests/FuzzyMatcherTests.swift` — new file; `FuzzyMatcherTests` pins the matcher's subsequence + scoring behavior, `OpenQuicklyFilterTests` pins the view-level filter against the reproduction and adjacent cases.

### Tests added

- `FuzzyMatcherTests`: subsequence and case-insensitivity, scattered subsequence, absence detection, empty-query semantics, contiguous-vs-scattered scoring, prefix-vs-interior scoring, no-match returns zero, Cat/Dog/Bird/Capybara reproduction at raw and composed-string level.
- `OpenQuicklyFilterTests`: Cat/Dog/Bird/Capybara reproduction end-to-end through `OpenQuicklyFilter.apply`, fallback `"Tab"` tab-title variant, empty-query pass-through preserves input order, query hitting only the tab title, query hitting only the session name, prefix outranking scattered interior, upper-case query against lower-case data, unmatched query returns empty, `id == tabID` stability.

### Gotchas

- Even though the matcher was already correct, the previous test suite had no `FuzzyMatcher` coverage at all — easy to over-attribute the bug to the matcher. The reproduction failed only when the filter was driven through the view's display-title path, so the regression test belongs at the `OpenQuicklyFilter` layer too.
