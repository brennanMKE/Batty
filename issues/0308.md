## Description

Hardening carved out of #0307: the `xcconfig_value()` helper in `scripts/preflight.sh` looks up keys with `grep -E "^$1"`, a prefix match — so `SU_PUBLIC_ED_KEY` would also match a hypothetical `SU_PUBLIC_ED_KEY_OLD`, and `head -1` returns whichever appears first in the file. A degenerate line holding a bare key name with no `=` also slips through sed untouched, returning the key name itself as the value. Neither behavior is a live failure — no colliding names exist in `Configuration/Build.xcconfig` or `Configuration/App.xcconfig` today, and the prefix match is unchanged from the pre-#0307 code — so this is not urgent.

## Resolution notes

> 🟢 Resolved 2026-08-08 — `xcconfig_value()`'s key match is now anchored to the assignment (`grep -E "^$1[[:space:]]*="`), so a longer-named key can no longer win and a line with no `=` no longer matches at all.

One line of `scripts/preflight.sh` plus an explanatory comment. Both reported defects close with the same anchor, exactly as the Plan proposed.

## Root cause

`grep -E "^$1"` anchored at the start of the line but not at the end of the key name, so the pattern was a prefix match. Two consequences: a decoy key sharing the prefix and ordered above the real key won via `head -1`; and a line holding a bare key name failed `sed`'s first substitution, passing the whole line through so the key name came back as its own value.

## Fix

```diff
-    grep -E "^$1" "$2" 2>/dev/null | head -1 | sed -E 's/^[^=]*=[[:space:]]*//; s/[[:space:]]*$//'
+    grep -E "^$1[[:space:]]*=" "$2" 2>/dev/null | head -1 | sed -E 's/^[^=]*=[[:space:]]*//; s/[[:space:]]*$//'
```

Requiring the assignment fixes both at once: a longer-named key no longer matches, and a line with no `=` no longer matches at all, so the pipeline yields empty and the `-z` warn branches fire as they did before #0307.

## Expected behavior

`xcconfig_value SU_PUBLIC_ED_KEY <file>` returns the value assigned to exactly `SU_PUBLIC_ED_KEY`, ignoring longer-named keys that share the prefix; a line with no `=` yields the empty string (the pre-#0307 `awk -F'='` behavior), so the `-z` warn branches fire instead of comparing against a bogus value.

## Actual behavior

The helper as it landed in #0307:

```zsh
xcconfig_value() {
    grep -E "^$1" "$2" 2>/dev/null | head -1 | sed -E 's/^[^=]*=[[:space:]]*//; s/[[:space:]]*$//'
}
```

1. **Prefix match** — the pattern is anchored at the start but not terminated at the key name, so a decoy key such as `SU_PUBLIC_ED_KEY_OLD` ordered above the real `SU_PUBLIC_ED_KEY` would silently win via `head -1`. Confirmed against a fixture during the #0307 review.
2. **Malformed line pass-through** — a line containing only a bare key name (no `=`) fails sed's first substitution, so the whole line passes through and the key name comes back as the "value". The practical effect is a `warn` turning into a `cred_fail` for an xcconfig Xcode itself would reject, so it is close to unreachable — but surprising, and the same fix closes it.

## Plan

Anchor the key name to the assignment, e.g. `grep -E "^$1[[:space:]]*="`. That fixes both items at once: a longer-named key no longer matches, and a line with no `=` no longer matches at all (so the pipeline yields empty, restoring the old empty-value behavior). Re-verify with `scripts/preflight.sh --credentials-only` and the fixture set from #0307 (multiple `=`, trailing whitespace, empty value, missing key, missing file, CRLF), plus new fixtures for the decoy-key and bare-key-name cases. `scripts/` is a restricted area per `CLAUDE.md`; this issue is the explicit authorization for this change.
