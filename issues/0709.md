# 0709 — Nothing tells the user or the agent when a command in a Pane exits or is waiting for input

## Description

Child of #0705. When an agent hands the user a command in a Pane, the user has to watch the Pane for the prompt and then tell the agent it finished. In the 2026-11-21 deploy the user typed `y`, the deploy ran, and the agent learned the outcome only when the user said to close the Pane.

## Expected behavior

1. **Exit notification.** `pane split` and `tab new` take `--notify` (MCP `notify: true`): when the command exits, Batty rings the Bell Feed for that Pane with a message naming the command and its exit status ("deploy.sh exited 0"). Works with or without `--wait`.
2. **Waiting-for-input notification (investigate first).** If Batty can reliably tell that the Pane's foreground process is blocked reading the terminal (for example, the foreground process group's state while the shell isn't in the foreground), ring the Bell Feed once when a `--notify` command starts waiting: "deploy.sh is waiting for input". The plan decides whether this is reliable enough to ship. If it isn't, it records why and this item is split into its own issue or dropped.

## Acceptance criteria

1. `--notify` rings exactly one Bell Feed entry per command exit, on the right Pane, with the exit status, and clicking it focuses that Pane.
2. Without `--notify`, behaviour is unchanged.
3. The waiting-for-input decision is recorded in this issue with the evidence behind it.
4. Unit tests cover the exit path; any detection heuristic has tests for a command waiting on a prompt and one that is simply busy.

## Relation

- Umbrella #0705. #0704's `bell list` is how an agent reads these entries; #0710's state query reports the same exit status.
