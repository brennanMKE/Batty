## Description

After the last test finishes, `./build.sh unit` waits another ~12.5–13.4 s in xcodebuild before it reports. `swift test` takes ~2 s for the same step. This tail is now the biggest cost outside test execution. Once #0592's test fixes land, execution takes ~18 s, but the full warm run still lands near 36 s. The target is well under 30 s.

Follow-up to #0592 (`issue/0592`, `## Plan` finding 5 and "Target"). #0587 moved `./build.sh unit` onto xcodebuild through the `BattyKit Unit Tests` scheme. #0588 is related.

## Root cause

xcodebuild's default `-collect-test-diagnostics on-failure` policy runs diagnostics collection after a full, passing `BattyKitTests` run. xcodebuild sits idle waiting on it for ~12 s after `xctest` exits. Nothing in the repo reads those diagnostics: `tools/check-report.py` uses only the xcresult summary and log lines.

## Fix

`build.sh`, `unit)` case: pass `-collect-test-diagnostics never` to `xcodebuild test`, next to `-resultBundlePath`, with a short why comment. `AGENTS.md` "Unit tests" timing updated to ~23 s. Filters, `--full`, `run_check` and the xcresult path are unchanged. `scripts/` untouched.

## Plan

### What the measurements show (2026-11-12, this worktree, M4 10-core, Xcode 27.2, load average ~5)

Each experiment ran `xcodebuild test -workspace Batty.xcworkspace -scheme "BattyKit Unit Tests" -destination platform=macOS -only-testing:BattyKitTests …` warm, with every output line timestamped. "Tail" is the time from the `Test run with 3763 tests …` line to xcodebuild's `Testing started completed` line.

|---|---|---|---|---|

Findings:

1. **The tail is test-diagnostics collection.** It is not the xcresult bundle: xcodebuild writes one into DerivedData even without `-resultBundlePath`, and dropping the flag changed nothing. It is not per-result streaming or parallel testing either. During the tail the test process (`xctest`) has already exited, and a `sample` of xcodebuild shows its main thread idle in `CFRunLoopRun` under `waitForBuildWithBuildLog:` (about 1% CPU). It is waiting on the diagnostics collection that the default policy (`on-failure`) starts. With `-collect-test-diagnostics never` the tail drops from ~12 s to 0.7 s, and the ~1.3 s after `Testing started completed` drops to 0.3 s. Small filtered runs never paid this, so what triggers collection in a full, passing run is still unknown. Candidates are the NSWindow "excessive live window count" warnings and the test-spawned subprocesses. It doesn't matter once the flag is set.
2. **Nothing reads those diagnostics.** `tools/check-report.py` reads only `xcresulttool get test-results summary` (counts and `testFailures`) plus log lines. With the flag, the xcresult summary still reports `totalTestCount 3763, passedTests 3762, failedTests 0, skippedTests 1, result Passed`.
3. **The failure path is unchanged.** A temporary failing suite (`ZZTempFailTests`: one `#expect(1 == 2)`, one passing test, deleted afterwards) under `./build.sh unit ZZTempFailTests` with the flag gave exit 1, `CHECK UNIT: FAILED (1 test, 0 compile errors)`, `==> unit: 2 tests, 1 failed, 0 skipped`, a Haiku summary naming `ZZTempFailTests/deliberatelyFails()`, and the `.failures.txt` digest.
4. **`swift test` is not worth switching to.** With the flag, xcodebuild (22.6–23.1 s) is as fast as `swift test` (23.3 s). Switching would bring back the costs #0587 rejected (filter translation, no xcresult, a second build directory) for no gain.
5. Not tried, because the tail was already gone: `-quiet` (#0592 measured 2.4 s, and it would hide lines check-report parses), the package-resolution flags (pre-test time is already ~3.5–4 s), and `-test-timeouts-enabled`.

### Decision

Keep xcodebuild. Add `-collect-test-diagnostics never` to the `./build.sh unit` invocation. Warm full run: **~37.5 s → ~23 s**, well under the 30 s target. The output contract doesn't change.

### Files

## Measurements (from #0592's plan)

- In every full xcodebuild run, "Testing started completed" lands 12.5–13.4 s after the last test line. One run went from 02:52:03.7 to 02:52:16.3.
- `swift test` has a gap of ~2 s.
- A filtered run of 20 tests takes 3.6 s in total. The tail seems to grow with the number of results.

- For the same work, `swift test` takes ~19.9 s wall and `./build.sh unit` takes ~36 s.
