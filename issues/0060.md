## Description

User has confirmed (2026-05-11) that clicking inside a non-focused pane's terminal body does not move pane focus. The pane I'm clicking in remains visually de-emphasized (per `#0052`'s focus indicator that landed in commit `5d2d36f`), the cursor I'm typing into still belongs to the previously-focused pane, and subsequent commands (`Cmd-D`, `Cmd-T`, `Cmd-Option-Arrow`) target the wrong pane.

This is the **user-visible symptom** of `#0051` ("Split actions ignore which pane is in keyboard focus"), which has been open since 2026-05-11 but not yet worked on. Filing here as a separate report because:

1. `#0052` (focus indicator) just landed and made the bug **more obvious** — the user can now plainly see that the pane they're clicking into stays de-emphasized.
2. `#0053` (chip click-to-focus) just landed for the tab-chip surface only, which may have created the impression that "click-to-focus is done." It is not — only the chip path is wired; the terminal body click path is still missing.
3. The fix scope from this angle is "click anywhere in the pane body should focus the pane," which is a slightly different framing than `#0051`'s "split actions target the wrong pane." Same root cause, slightly different acceptance criteria.

When this lands, `#0051` and this issue can both be closed together — they describe the same fix. Consolidating them into a single resolution commit is fine.

## Steps to reproduce

1. Open a session, hit `Cmd-D` once to create two panes (pane A and pane B). Pane B takes focus (the freshly-split pane). `#0052`'s indicator confirms B is emphasized.
2. Click anywhere inside pane A's terminal body.
3. **Expected:** pane A's frame visibly takes focus (`#0052` indicator moves to A), and typing goes to pane A's shell.
4. **Actual:** pane A's frame stays de-emphasized, the click does nothing visible at the model level, and `Cmd-D` immediately afterwards splits B (the still-focused pane).

The chip-click path *does* work (per `#0053` / `5bff0f0`) — clicking a tab chip in pane A focuses pane A. It's specifically the body / scrollback / terminal-area click that's missing.

## Expected behavior

Clicking inside any pane's `TerminalSurfaceView` should:

1. Cause that surface to take first-responder (already happens — that's how typing works at all).
2. Write `session.tree.focusedPaneID = pane.id` synchronously so `#0052`'s indicator moves and the next command targets the clicked pane.

Both writes should be triggered by the same signal — the surface gaining first-responder. The chip-click path uses the SlidingTabs binding setter; the terminal-body path needs a different hook because the surface doesn't have a tap binding we own.

## Actual behavior

`TerminalSurfaceView` (from `GhosttyTerminal`) handles its own click → first-responder flow and exposes the focused state via `TerminalViewState.isFocused: Bool` (published by the fork's `TerminalSurfaceFocusDelegate` conformance). Nothing in `PaneView` currently observes `tab.terminal.isFocused` and writes back to `tree.focusedPaneID`.

`#0051`'s notes already identified this: *"`TerminalViewState.isFocused` is published by `GhosttyTerminal` (via the `TerminalSurfaceFocusDelegate` conformance landed in the upstream fork). `PaneView` (or `SplitNodeView` wrapping it) can observe `tab.terminal.isFocused` per-tab and, when it flips to `true`, set `tree.focusedPaneID = pane.id`."* The hook just hasn't been written yet.

## Implementation guidance

Two pieces of plumbing already exist; the fix is to connect them.

1. **The signal:** `tab.terminal.isFocused` is `@Published` (or its `@Observable` equivalent) and flips when the surface gains first-responder.
2. **The write path:** `AppStateStore.focusPane(id:)` (added in `#0053`, commit `5bff0f0`) walks sessions and writes `tree.focusedPaneID`. Use it.

Wire it in `PaneView`. The pattern matches the existing `.onChange(of: tab.terminal.bellCount)` modifier:

```swift
TerminalSurfaceView(context: tab.terminal)
    // existing modifiers...
    .onChange(of: tab.terminal.isFocused) { _, isFocused in
        if isFocused {
            if let appStore {
                appStore.focusPane(id: pane.id)
            } else {
                tree.focusedPaneID = pane.id
            }
        }
    }
```

This observes each tab's focus, but only the active tab can actually have first-responder, so the cascade naturally limits itself.

### Re-entrancy

The bug to avoid: a write to `focusedPaneID` causes a re-render that re-reads `tab.terminal.isFocused`, which is still `true`, which fires `.onChange` again. SwiftUI's `.onChange` only fires on *transitions*, not on every render, so this is safe by construction. But verify in practice with a focus-cycle test (rapidly press `Cmd-Option-Left/Right`).

### Cross-session safety

If `appStore.focusPane(id:)` ever gets called with a pane id from a different session than the currently-selected one, it just writes that other session's `focusedPaneID` — which is fine. The pane that fired the focus change is, by definition, in the on-screen session because off-screen surfaces don't have first-responder.

## Acceptance criteria

- Clicking inside any pane's terminal body (not just a chip) sets that pane as the focused pane.
- `#0052`'s indicator visibly moves to the clicked pane immediately.
- `Cmd-D` immediately after the click splits the clicked pane.
- The existing chip-click path (`#0053`) continues to work unchanged.
- The existing geometric `Cmd-Option-Arrow` path (`#0020`) continues to work unchanged.
- No re-entrancy loop: rapid `Cmd-Option-Arrow` cycling doesn't cause render storms.
- A test exercises the path: simulate `tab.terminal.isFocused = true` (or whatever the right entry point is) and assert `tree.focusedPaneID` updates to that pane.

## Out of scope

- Drag-to-focus or scroll-to-focus heuristics — only click / first-responder counts.
- Modifier-click variants (Cmd-click, Option-click) — same path, no special handling.
- Focusing a *session* by clicking inside its window — sidebar selection already handles cross-session focus.

## Root cause

`TerminalSurfaceView` handles its own click → first-responder flow and publishes the resulting focus state via `tab.terminal.isFocused` (driven by the upstream fork's `TerminalSurfaceFocusDelegate` conformance). The SwiftUI view tree had observers for every other surface signal — `bellCount`, `lastDesktopNotificationAt`, `workingDirectory`, `onClose`, plus the inverse direction (`isPaneFocused` → `TerminalSurfaceFocuser.focusWhenReady`) — but no observer for the surface-gained-first-responder edge. The model's `tree.focusedPaneID` therefore stayed pinned to whichever pane had last been set focused programmatically (via `splitFocusedPane`, `removeFocusedPane`, `focusPane(adjacent:)`, or the chip-click setter from `#0053`).

## Fix

Added one `.onChange(of: tab.terminal.isFocused)` to the `ForEach(pane.tabs)` block in `PaneView.swift`, alongside the existing per-surface observers. On the false→true transition it routes the focus write through `AppStateStore.focusPane(id:)` (the helper introduced in `#0053`), falling back to a direct `tree.focusedPaneID = pane.id` write when no app store is in the environment. SwiftUI's `.onChange` only fires on transitions, so there's no re-entrancy risk.
