# 0657 — batty mcp splits stdin messages on U+2028, U+2029 and NEL, breaking JSON strings that contain them

| | |
|---|---|
| **Status** | open |
| **Module** | App / Testing |
| **Platform** | macOS |
| **First seen** | 2026-11-18 |

## Description

The `batty mcp` stdio server (#0647) frames incoming JSON-RPC messages with Foundation's Unicode-aware line splitting, so a message is cut in two wherever it contains a raw LINE SEPARATOR (U+2028), PARAGRAPH SEPARATOR (U+2029) or NEXT LINE (U+0085), not only at `\n`. JSON allows all three unescaped inside strings, and a client is free to send them that way (for example, text pasted into a `notify` message or a Session title). Each half fails to decode, so the server answers with two `-32700 Parse error` replies with `id: null`, and the request itself is never answered; the client waits on its `id` until it times out. MCP's stdio transport delimits messages by `\n` only.

## Current state (verified 2026-11-18)

- `BattyKit/Sources/batty/MCPServer.swift:96` — `MCPServer.serve(input:output:)` reads with `for try await line in input.bytes.lines`. `FileHandle.AsyncBytes.lines` is an `AsyncLineSequence`, which Apple documents as ending a line at LF, CR, CRLF, NEL (U+0085), LS (U+2028) and PS (U+2029). It decodes UTF-8 to find NEL/LS/PS, so the multi-byte sequences `C2 85`, `E2 80 A8` and `E2 80 A9` all end a line.
- `MCPServer.swift:107-113` — `handle(line:output:)` trims whitespace and newlines, decodes the line as `MCPJSONValue`, and on failure sends `parseError` with `id: .null`. Each fragment of a split message lands here.
- `MCPServer.swift:67` — the type's doc comment already states the intended framing: "newline-delimited JSON-RPC 2.0, one message per line".
- `MCPServer.swift:221` — output framing is already correct: each reply is encoded and followed by a single `0x0A`.
- `BattyKit/Tests/BattyKitTests/MCPServerTests.swift` — the suite drives the server over real `Pipe`s through `MCPHarness` (`send(_:)` at line 102 appends `"\n"`; `reply()` at line 106 reads through `PipeLineReader`, which already splits on byte `0x0A` only). No test sends a message containing LS, PS or NEL.

## Steps to reproduce

1. Run `batty-beta mcp` (or start it with the MCP harness in a test).
2. Send `initialize`, then this one line, where `<LS>` is a raw U+2028 (UTF-8 bytes `E2 80 A8`), not the escape ` `:

   ```
   {"jsonrpc":"2.0","id":7,"method":"tools/call","params":{"name":"id","arguments":{"x":"a<LS>b"}}}
   ```

3. Read stdout.

## Expected behavior

The server reads the whole line as one message, because it contains no `0x0A`. It answers once with `id: 7`: a tool result, or a tool error if the arguments are invalid for that tool, the same as it would for `"x":"ab"`.

## Actual behavior

The line is split after `"a` into `{"jsonrpc":…"arguments":{"x":"a` and `b"}}}`. The server sends two `{"jsonrpc":"2.0","id":null,"error":{"code":-32700,"message":"Parse error"}}` replies and never answers `id: 7`.

## Recommended direction (the plan may refine it)

Frame input on the byte `0x0A` only. Read raw bytes from `input.bytes` (or `readabilityHandler`/`availableData`) into a `Data` buffer, cut at each `0x0A`, drop one trailing `0x0D` from the cut line so CRLF clients still work, and decode the remaining bytes as UTF-8 JSON. A final message with no trailing newline at end of file should still be handled, as `lines` does today. Keep the existing empty-line skip. Don't add a general Unicode trim that would remove LS, PS or NEL from inside the message; trimming is harmless only at the ends, where JSON allows only ASCII whitespace anyway.

## Acceptance criteria

- `MCPServer` splits input messages on `0x0A` only. U+2028, U+2029, U+0085 and a lone `\r` inside a line never end a message.
- A line ending in `\r\n` is parsed the same as one ending in `\n`.
- A final line without a trailing `\n` before end of file is still processed.
- New tests in `MCPServerTests` (the existing suite, through `MCPHarness` over the pipe), for example:
  - `rawLineSeparatorInsideAStringIsOneMessage` — after `initialize`, sends a `tools/call` (or `ping` with a `params` string) whose JSON string contains a raw U+2028, and asserts exactly one reply, carrying the request's `id` and no `error.code == -32700`. Include U+2029 and U+0085 in the same test or as parameterized cases.
  - `crlfTerminatedLineIsParsed` — sends a request ending in `\r\n` and gets a normal reply.
- The tests await replies through `PipeLineReader` as the suite already does. No sleeps or timing (AGENTS.md, "Asynchronous tests").
- Existing `MCPServerTests` and `MCPToolCatalogTests` still pass. `./build.sh` and `./build.sh unit` pass.

## Notes

Found by the #0647 reviewer. The problem is input framing only: output already ends each reply with a single `0x0A`. CLI-only change, with no app UI, so no UI tests are affected.
