# 0507 — A Process Status pane following a Tab tombstones permanently when one command inside it exits

| | |
|---|---|
| **Status** | open |
| **Module** | Process Status pane |
| **Platform** | macOS |
| **First seen** | 2026-10-14 |

## Description

`Target.followingTab`'s contract is explicit: "Tombstones only when the Tab itself disappears (the lookup misses), not when a single command within it exits" (`ProcessStatusPaneContent.swift:31-33`). The `.processNotFound` branch of `sample(pid:canReresolve:)` breaks that. It special-cases `.followingName` (re-resolve, else `.waiting`) and then falls through to `runState = .exited` plus `samplingTask?.cancel()` for *everything else* — including `.followingTab`.

That branch is reachable without the Tab going anywhere: `resolveTarget()` reads `tab.terminalNSView?.foregroundPid` and `coreMetricsProvider(pid)` runs after it, so a foreground command that finishes in between yields `ESRCH` against a perfectly live Tab. Once `.exited` is set the pane is dead for good — `startSampling()` opens with `if case .exited = runState { return }` (`:398`), so hide/show does not revive it and no later command in that Tab is ever followed.

Found by an external review of `v1.1.0..ad239f9e` — review id `20261014T193749Z-Batty-883c427`, finding 4 of 5 (medium, correctness, confidence high).

## Steps to reproduce

1. Open a Process Status pane targeting a terminal Tab (Mode B).
2. In that Tab run a short command, e.g. `ls`, and let it finish. Repeat until a sample lands in the window between `foregroundPid` resolution and the metrics read.
3. Run another long-lived command in the same Tab.

## Expected behavior

The pane reports that nothing is running right now and picks up the next foreground process in that Tab. Only the Tab disappearing tombstones it — which `performSample()`'s `.sourceTabGone` branch already handles.

## Actual behavior

The pane shows Exited, the sampling `Task` is cancelled, and it never recovers.

## Notes

- `BattyKit/Sources/BattyKit/Runtime/ProcessStatusPaneContent.swift:534-552`.
- Fix: give `.followingTab` its own arm in `.processNotFound` — leave the last `snapshot` in place (same honesty rule as the other branches), set `runState = .waiting`, and leave the sampling `Task` running so the next tick re-resolves. `.pinned` keeps tombstoning, which is its documented behavior.
- `.waiting` is already the state Mode C uses for "target known, nothing live to sample right now," and the view already renders it, so this needs no new state.
