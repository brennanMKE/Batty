## Description

The user asked (2026-11-22) for "a feature which supports an agent discovering which background images are available and setting them as the user can for a pane or session." Half of that exists: `batty background list --json` (#0700) lists every Background Sets image and My Images image, with an `id` an agent can pass back. The other half doesn't. Nothing reports the background a running Session, Pane or Tab shows now, and nothing sets one. The user does both in the background sheet (Sidebar → Set Session Background…, the Pane menu, the Tab menu).

Two parts, CLI and MCP only, no new UI:

1. **Discovery.** Report each Session's, Pane's and Tab's current background in the topology JSON, so `batty list --json`, `batty session info --json` and their MCP tools (`list`, `session_info`) show it.
2. **Setting.** Add `batty background apply` at Session, Pane and Tab level, with `--none` to clear and `--opacity` / `--terminal-opacity`. It becomes an MCP tool (`background_apply`) automatically, because MCP tools are generated from the capabilities verb catalog (`batty/MCPToolCatalog.swift`).

This takes over item 6 of #0703, which bundled `background apply` with five unrelated verbs. #0703 now points here, and its other five items stay with it. No feature flag: `background list` and #0703 are unflagged, and `FeatureFlags.swift` holds only `sharedProjectImages` and `servers`.

## Expected behavior

### 1. Current background in the topology

Add one optional Codable `background` object to `TopologySessionPayload`, `TopologyPanePayload` and `TopologyTabPayload`. Like `reminder`, it is omitted when nothing applies, and it decodes leniently, so an older CLI or a missing field never fails `list`.

- `own`: this level's own value, or absent when the level follows. It holds:
  - `imagePath`
  - `imageID`: the hosted URL or My Images digest, i.e. the `id` that `background list` prints, or absent when the image isn't from either
  - `imageName`
  - `opacity` and `terminalOpacity` as integer percents, the units `--opacity` takes
- `effectiveSource`: `"tab"`, `"pane"`, `"session"` or `"settings"`, from `effectiveBackground(appWide:)`. An agent can tell an inherited background from the level's own value without walking the tree.
- For a Tab, also `effective`, in the same shape as `own`: the value the terminal shows. Panes and Sessions don't need it, because their `effective` is always their own value or a broader level's.
- A non-terminal Pane and its Tab carry no `background`.
- Text output (`batty list`, `session info`) adds `background=<imageName|none>` to a Session line only when the Session has its own value. Pane and Tab lines aren't printed with that detail today, so they stay as they are.

### 2. `batty background apply [--session ID | --pane ID | --tab ID] (--background-set NAME --background-image TITLE | --background-id ID | --background-digest DIGEST | --background-file PATH | --none) [--opacity 0-100] [--terminal-opacity 0-100] [--json]`

- **Level.** Pass at most one of `--session`, `--pane` or `--tab`. With none, the target is the calling Session: `BATTY_SESSION_ID`, then the focused Session, as other verbs resolve it. A flag with no value isn't supported; an explicit id is required. An unknown id exits 4. A non-terminal Pane, or a Tab in one, exits 4 with a message. The setter would be a silent no-op there.
- **Source.** At most one of these, with the same spellings as `project create`, so an agent's ids from `background list` work in both:
  - `--background-set` + `--background-image` (`.hosted(set:title:)`)
  - `--background-id` (`.hostedID`)
  - `--background-digest` (`.myImage`)
  - `--background-file` (`.file`)
  - `--none`
- **No source.** If only opacity flags are given, they apply to the level's own value. A level that follows and has no image is rejected: "opacity: --opacity needs an image". `--terminal-opacity` alone is valid on a following level. It seeds from the effective value, as `selectCustom()` does. A call with neither a source nor an opacity flag is a validation error.
- **Resolution.** Uses #0700's lookup, download, find-by-digest and import steps, with `store.backgroundImageImporter` (`adoptImage` for a hosted or My Images image, `importImage` for a file). A failed lookup, download or copy exits 4 and changes nothing.
- **Value written.** Matches the sheet:
  - The base is the level's effective value (`selectCustom` semantics). A following level therefore keeps the inherited fit, position and terminal opacity.
  - The image path is set with `pickingImage`-style logic. A first image gets the CLI opacity rule, `cliFirstImageOpacity` (30%). An existing image keeps its opacity.
  - `--opacity` and `--terminal-opacity` are then applied with the factored-out `ProjectWriteBuilder` rules: 0-100 range, `--opacity` needs an image, and no opacity flag with `--none`.
- **Write.** Exactly one call to the level's `setBackgroundOverride`. `--none` writes `nil`, the same as Clear Session/Pane/Tab Background. A Pane write replaces its Tabs' own values, as the Pane sheet does. `projectBackgroundSeed` is never read or written.
- **Output.** Silent on success, or with `--json` the level's new topology `background` object, so the agent sees `own` and `effectiveSource` without another call. The verb doesn't select, focus or activate anything.
- **Annotation:** `edit`, which is idempotent. A repeat call writes an equal value, and every setter skips equal writes.

## Acceptance criteria

1. `batty list --json` and `batty session info --json`, and the MCP `list` and `session_info` tools, report each terminal Session's, Pane's and Tab's `background` with `own` (absent when the level follows), `effectiveSource`, and for a Tab `effective`. An image from Background Sets or My Images carries the `imageID` that `background list` printed. An older-shaped payload without the field still decodes.
2. `batty background apply` exists in `batty` and `batty-beta`, appears in `batty capabilities`, and is the MCP tool `background_apply`, non-destructive and idempotent.
3. With each source (hosted set+title, hosted id, My Images digest, file) and at each level, `background apply` produces the same `backgroundOverride` the sheet would produce, apart from the 30% CLI first-image opacity. A Pane apply clears its Tabs' own values. `--none` returns the level to following.
4. The opacity rules match `project create`. Both call one shared function, not two copies.
5. A failed lookup or fetch, an unknown level id, or a non-terminal Pane exits 4 and changes nothing.
6. A Pane or Tab background applied by the CLI survives a later Project save, because the seed rule from #0702 is untouched.
7. `docs/batty-cli-design.md`, `docs/batty-cli-agent-workflows.md`, `.claude/skills/batty-cli/SKILL.md`, `Concepts.md` (a short line under the background levels, version bumped) and the generated `website/docs/cli/` reference are updated. The changelog notes the verb and the topology field under 1.5.0.
8. `./build.sh` and `./build.sh unit` pass, and the docs tools' `--check` modes pass.
