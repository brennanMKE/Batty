## Description

Batty has no awareness of its own memory use. The #0285 report documents a footprint that grew to 8.4 GB over 42 days — ~38% of all memory in use on the system, pushing the kernel to memory pressure level 2 — without any signal to the user, and RSS-based observation (`ps`) missed it entirely for weeks. Batty should monitor its own footprint and warn the user before the system starts swapping.

This is a mitigation/observability feature: it ships whether or not the underlying graphics-memory growth turns out to be fixable in Batty or upstream in libghostty. It is independent of the other #0285 children — it ships regardless of what the fixes achieve.

## Resolution notes

> 🟢 Resolved 2026-08-01 — Batty now samples its own `phys_footprint` and warns through the Bell Feed when a configurable soft limit is crossed.

Observability, not a fix: this tells the user memory is climbing, it does not slow the climb. That is #0287/#0288/#0293's job. It ships independently of all of them.

## Root cause

Batty had no awareness of its own memory use. The field report's footprint reached 8.4 GB over 42 days — ~38% of all memory in use on a 32 GB machine — with no signal to the user. RSS-based observation missed it entirely for six weeks, because `ps -o rss` excludes compressed and swapped pages: it reported 287 MB against a real `phys_footprint` of 8,546 MB, a 29× under-report.

## Fix

- **`FootprintReader`** — a direct `task_info(TASK_VM_INFO)` read of `phys_footprint`. Never RSS. Returns `nil` on `KERN_SUCCESS` failure or a zeroed `phys_footprint` (the documented `TASK_VM_INFO_REV0_COUNT` case) rather than a plausible small number.
- **`FootprintWarningPolicy`** (pure) maps bytes to a threshold step in `limit/4`-sized bands; **`FootprintWarningState`** (pure) holds the nag-suppression rule; **`FootprintMonitor`** (`@MainActor`) owns a 60-second sampling `Task`. Both provider closures (`limitBytesProvider`, `footprintBytesProvider`) are injectable, which is what makes the logic testable without a timer, the UI, or the live process.
- **Nag suppression** tracks a high-water mark in *bytes*, re-projected through whatever policy is current on every comparison. A warning fires only at a step above the mark; dropping to or below the limit resets it. Fluctuating between two seen steps stays silent, and a pure policy change never fires a warning by itself in either direction.
- **Settings → Advanced → Memory** carries the soft limit (default 4 GB, stepper 1...32).
- **The warning** lands in the Bell Feed carrying the current footprint and the open Terminal Session count, paired with a System notification when Batty is not frontmost.

## Review

Reviewed by claude-opus-5 over two rounds.

Round 1 requested changes on two blocking defects. The first was a **flaky test**: the monitor tests set the limit to 1 byte, collapsing the band size to 1 byte and making the step index equal the raw byte count, so any real footprint growth between back-to-back samples read as an escalation — and Swift Testing's concurrent suites supplied that growth reliably. The reviewer measured **9 failures in 25 runs**; it had passed for the implementer by luck. The second was the feature's own failure mode: `FootprintWarningState` stored a high-water *step index*, meaningful only relative to one policy, so **raising the soft limit in Settings could silently suppress every future warning** (warn at 12 GB against a 4 GB limit → step 9; raise the limit to 10 GB → 12 GB re-reads as step 1 with no reset; the footprint reaching 20 GB → step 5, still not above 9 → never warns again).

Round 2 approved. The reviewer walked the state machine by hand across every transition including raise-limit-while-above and lower-limit-while-above, proved `highWaterBytes` is monotonic between resets (since `step` is monotone non-decreasing), measured the flaky test at 25/25, and **mutation-tested the suite**: suppression removed, reset removed, `evaluate` always returning a step, `sampleOnce` ignoring the provider, and the B2 fix reverted were each killed by named tests — the last by `raisingTheLimitWhileAboveStillWarnsOnFurtherGrowth` and only that test, confirming the regression test is load-bearing for the defect it was written for.

## Gotchas

- **Never measure this app with RSS.** `ps -o rss` under-reported by 29× on the original report and 7× on a later instance; the gap scales with how much has been compressed. Any future memory work must read `phys_footprint`.
- **A high-water mark must be stored in the unit that survives a policy change.** Storing a step index looked equivalent to storing bytes and was not: it silently broke the moment the user changed the setting the feature invites them to change. Re-projecting a physical quantity through the live policy is the pattern to copy.
- **A test that pins a rule must fail when the rule is broken.** Both blocking defects were tests that passed for reasons unrelated to what they claimed to assert. Mutation testing settled it here; it is cheap and worth repeating for any state machine.
- **Swift Testing parallelizes suites by default**, so tests sharing a `UserDefaults` key race. The fix is injectable providers, not `.serialized` — the latter is only right where the shared key is genuinely the thing under test.
- **`formatGB` is locale-insensitive** — `String(format: "%.2f GB", …)` hard-codes `.` as the decimal separator while the surrounding sentence is localized and the app ships 15 locales. One-line fix available: `(Double(bytes) / 1_073_741_824).formatted(.number.precision(.fractionLength(2)))`. Left as a nit.
- **The UI reads GiB but says "GB".** The stepper and the warning text both use `1_073_741_824` so they agree with each other, but Activity Monitor uses decimal GB — Batty's number reads ~7% lower for the same footprint, which may confuse a user cross-checking.
- **`sessionNoun` is an English literal interpolated into a localized string**, so its plural rule is untranslatable. Latent — BattyKit's `String(localized:)` calls are not in the catalog today.
- **Correction (2026-08-01), tracked as follow-up #0295:** the "Activity Monitor uses decimal GB" claim two bullets up is wrong. Verified empirically (#0295): `top` and `footprint` print bytes/2²⁰ as "MB" for a process whose exact `phys_footprint` was known, `ByteCountFormatter.CountStyle.memory` is 1024-based, and Activity Monitor documents the same convention — so Batty's 2³⁰-divided "GB" already matches Activity Monitor's number and label. Do not "fix" toward decimal. The two locale nits (this bullet and the `formatGB` one above) are tracked in #0295.
- **A frontmost crossing is quiet.** `postFootprintWarning` fires only when Batty is not frontmost, so when it is frontmost the only signal is the toolbar bell badge — and step suppression means that step will not fire again.

## Expected behavior

Batty monitors its own memory footprint and warns the user when it crosses a soft limit:

- Batty periodically samples its own `phys_footprint` (e.g. `task_info` with `TASK_VM_INFO` — not RSS, per the measurement trap below). Per-Terminal-Session attribution is a bonus if feasible; a process-level number is the requirement.
- A **configurable soft limit** with a sane default (given ~65 MB of graphics memory per open Terminal Session on the reporting machine, something in the low single-digit GB is a reasonable starting point). Configuration belongs with the app's existing preferences (Settings window).
- Crossing the limit **warns the user** through an existing app affordance — the Bell Feed is the app's notification surface and a natural fit, optionally paired with a System notification when Batty is not frontmost. The implementer picks the exact surface; the requirement is that the warning is visible without the user going looking for it.
- The warning is **actionable**: it states the current footprint and how many Terminal Sessions are open, so the user can decide what to close.
- The warning does **not nag**: once acknowledged, it does not repeat until the situation meaningfully changes (e.g. footprint crosses the next threshold step, or drops below the limit and crosses it again).

**Measurement trap (binding):** `ps -o rss` reported 287 MB while the real `phys_footprint` was 8,546 MB — a **29× under-report**, because RSS excludes compressed and swapped pages (1.9 GB of Batty's footprint was in the compressor). The monitoring feature must read `phys_footprint` via `task_info` with `TASK_VM_INFO`, never RSS.

## Actual behavior

No monitoring, no limit, no warning of any kind.
