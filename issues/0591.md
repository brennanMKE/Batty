## Description

Carved out by the #0590 review (`issue/0590`; see its `## Plan` decision 4 and `## Review`). **Fix this only after #0590 is merged.** Low severity.

A background sheet (Session, Pane or Tab) snapshots the level's values and pending state when it opens. If a withheld image finishes downloading while the sheet is open, it lands on the still-pending level. Cancel then restores the open-time snapshot, which has no image path, so the arrived image is undone at that level. If the sheet was edited first, the edit ends pending, the arrival skips the level, and Cancel puts pending back with no path. Reopening the Project fixes it.

## Plan

Verified on `issue/0591` at 1b6be24 (#0590 merged). Both cases in the Description are real:

- **No edit.** `tabImageArrived` (`AppStateStore+TabImages.swift:173`) and `sharedImageArrived` (`AppStateStore+BackgroundImages.swift:169`) apply the path and end pending. Then Cancel's `cancelRestore` (Pane `PaneRuntime.swift:405`, Tab `TabRuntime.swift:614`, Session `SessionRuntime.swift:277`) writes back the open-time value, which has no path, and the open-time pending state. The arrival has already happened, so nothing applies it again.
- **Edit, then arrival.** The edit ended pending, so the arrival loop's `where pending == identity` filter skips the level. Cancel then puts pending back with no path.

### Approach: an arrival ledger on the runtimes, read by `cancelRestore`

Each runtime records which images arrived, whether or not it was still pending. `cancelRestore` resolves the open-time snapshot against that record and restores once.

I rejected updating the sheet's snapshot on arrival. The snapshot is a view's `@State`, so the store can't reach it without registering live sheets, and the store would then be writing view state from a download callback. The ledger keeps everything in the runtimes and needs no change to the editor or the view.

### Files

- **`Runtime/PaneRuntime.swift`** and **`Runtime/TabRuntime.swift`**
  - Add `@ObservationIgnored var arrivedImages: [ProjectTabImage: String] = [:]` to each. `ProjectTabImage` is `Hashable`. The ledger isn't rendered, so it shouldn't notify.
  - Pane `cancelRestore`: if `pending.pane` has a path in `arrivedImages`, restore `value?.withImagePath(path)` with `pendingImage = nil`. Otherwise keep today's behavior. For each Tab, do the same with `pending.tabs[tab.id]` against the Tab's own `arrivedImages`, then call `tab.restoreBackgroundOverride(resolved, pendingImage: resolvedPending)`.
  - Tab `cancelRestore`: the same resolution, for that Tab only.
  - That makes one write per level, guarded as today. Put the resolution in a small shared helper, such as `func resolvedForCancel(_ value:, pending: ProjectTabImage?) -> (TerminalBackgroundSettings?, ProjectTabImage?)` on each runtime, or as a free function. The implementer chooses.
- **`Runtime/SessionRuntime.swift`**
  - Add `@ObservationIgnored var arrivedProjectImagePath: String?`.
  - `cancelRestore`: if `pending.sessionPending` and a path has arrived, call `restoreBackgroundOverride(value?.withImagePath(path), pending: false, problem: nil)`. That matches what an arrival does through `setBackgroundOverride`. Otherwise keep today's behavior.
- **`Runtime/AppStateStore+TabImages.swift` `tabImageArrived`**
  - Before the pending filters, record `arrivedImages[identity] = path` on every Pane and Tab in the Project's Sessions. Keep the apply logic unchanged.
- **`Runtime/AppStateStore+BackgroundImages.swift` `sharedImageArrived`**
  - Set `arrivedProjectImagePath = path` on every Session with that `projectID`, before the `pendingProjectImage` filter. Keep the apply logic unchanged.

**Why this is safe.** A level is only pending from Project open (`ProjectTreeBuilder`, `AppStateStore.swift:1558`), which builds fresh runtimes with empty ledgers. An arrival before the sheet opened ended that level's wait, so the open-time snapshot can't name an image that arrived before the sheet opened. The ledger only affects Cancel for a level the snapshot says was pending. Writes come from download callbacks and the Cancel button, which are event-origin. None of them is in `body` or `onChange`.

### User checklist

- On a second Mac, open a Shared Project whose Pane or Tab image hasn't downloaded. Open that level's background sheet and wait for the image to appear behind it. Press Cancel. The image should stay.
- Do the same, but change opacity before the image arrives, then press Cancel. The opacity should revert and the image should still appear.
- Repeat both for a Session whose shared image is withheld. The sidebar problem badge should clear once the image arrives, and stay cleared after Cancel.

### Decisions (delegated, recorded here)

1. **The runtimes keep a ledger, rather than the sheet keeping a live snapshot.** No store-to-view wiring is needed, and the editor and view are untouched.
2. **Every runtime in the Project records the arrival, not only pending ones.** That is what covers the edit-then-arrival case.
3. **The ledger is never cleared.** Runtimes are rebuilt when a Project opens, and a level only waits from open. A bounded dictionary of a few entries per runtime is fine.

## Resolution notes

> 🟢 Resolved 2026-11-12 — Pane, Tab and Session `cancelRestore` now resolve the open-time snapshot against a per-runtime record of arrived images, so Cancel keeps an image that arrived while the sheet was open.

## Review

Approved on the first pass. Checks made:

- **Stale records.** A level becomes pending only at Project open (`ProjectTreeBuilder.swift:100,179`, `AppStateStore.swift:1558`), on fresh runtimes with empty records. After that, only `cancelRestore` puts pending back. Update Project and remote edits never set pending on a live runtime. A record can therefore only resolve a wait whose snapshot was taken after that arrival. An arrival before the sheet opened has already ended the wait, so the snapshot isn't pending. A second shared-image arrival during the sheet makes Cancel use the newer path, which is arguably more correct and harmless.
- **Memory.** Each runtime holds at most one entry per distinct image identity in the Project, and they are freed with the runtime.
- **Snapshot value `nil` while pending.** This can't happen: pending is set only when the level has a value at open (and `checked(_:)` always returns settings). Ending pending there is harmless.
- **`cancelKeepsWaitingWhenADifferentImageArrived`.** The test is deterministic. Everything from `open` to `cancel()` is synchronous on the main actor with no suspension point, so the real download can't land in between. Its fake path only goes to the fixture's project store.
- **Sheet-edit tests.** They assert the arrived path, the end of pending and the open-time opacity, which together cover the resolved value. The Pane-sheet test also asserts that the untouched Tab equals its open-time value.
- **One observed write per level is preserved.** The new fields are `@ObservationIgnored`, and every write comes from a download callback or the Cancel button (event-origin), so `docs/swiftui-observation-rules.md` is satisfied.

## Root cause

Confirmed as the Plan describes. Background sheets snapshot the level's value and pending state at open. `cancelRestore` (Pane, Tab, Session) wrote that snapshot back unconditionally. An image that arrived while the sheet was open had already been applied (no edit) or skipped (edit ended pending), so the restore put back the path-less value and the pending state, and nothing reapplied the image.

## Fix

Implemented the Plan's arrival ledger.

- `PaneRuntime.arrivedImages` / `TabRuntime.arrivedImages` (`[ProjectTabImage: String]`) and `SessionRuntime.arrivedProjectImagePath`, all `@ObservationIgnored`, never cleared.
- `tabImageArrived` records the path on every Pane and Tab in the Project's Sessions before the pending filters; `sharedImageArrived` records it on every Session with the Project's id before the pending filter. Apply logic is unchanged.
- Free function `resolvedForCancel(_:pending:arrived:)` in `PaneRuntime.swift`: if the snapshot's pending identity has arrived, returns `(value?.withImagePath(path), nil)`; otherwise the snapshot unchanged. Pane and Tab `cancelRestore` use it, still one write per level.
- Session `cancelRestore`: if the snapshot was pending and a path arrived, restores `value?.withImagePath(path)` with `pending: false, problem: nil`.

No divergence from the Plan. Conservative choice: when the snapshot value is `nil` the resolved value stays `nil` (matching an arrival, which skips a level with no value) but pending still ends.
