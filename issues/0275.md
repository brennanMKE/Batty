# 0275 — isBundleDurable does not detect Gatekeeper app translocation, so Install symlinks into an ephemeral AppTranslocation mount

| | |
|---|---|
| **Status** | open |
| **Module** | Settings |
| **Platform** | macOS |
| **First seen** | 2026-07-24 |

## Description

`isBundleDurable` (added in #0268) refuses to install the `/usr/local/bin/batty` symlink when the running bundle sits under `/DerivedData/` or `/Build/Products/`, because a symlink into a build-products path breaks on the next clean build and surfaces much later as a confusing `command not found`.

**Gatekeeper app translocation produces the same class of ephemeral bundle path and is not covered.** When a user downloads the DMG and runs `Batty.app` directly from `~/Downloads` without dragging it to `/Applications`, macOS runs it from a read-only, randomized mount of the form `/private/var/folders/<…>/AppTranslocation/<UUID>/d/Batty.app`. That path contains neither `/DerivedData/` nor `/Build/Products/`, so it passes the current durability check and Install happily creates a symlink into a location macOS reclaims — the exact failure `isBundleDurable` exists to prevent, reached by the more common route: a real user with a downloaded release, rather than a developer running from Xcode.

Found during the #0268 review by the reviewer subagent (`claude-opus-5`), which declined to gate approval on it since it falls outside #0268's stated scope.

## Steps to reproduce

1. Download the release DMG, open it, and drag `Batty.app` to `~/Downloads` (or run it straight from the mounted DMG's copy after Finder copies it anywhere other than `/Applications`).
2. Launch that quarantined copy — macOS translocates it to an `AppTranslocation` mount.
3. Settings → Advanced → Install the `batty` CLI.

## Expected behavior

Install refuses, the same way it refuses for a DerivedData bundle, with a message a non-developer can act on — tell them to drag Batty to `/Applications` and relaunch, then install.

## Actual behavior

The durability check passes, the auth dialog appears, and a `/usr/local/bin/batty` symlink is created pointing into the translocation mount. The mount disappears (relaunch from a different path, reboot), leaving a dangling symlink and a delayed `command not found`.

*(Actual behavior asserted from the implementation on branch `issue/0268`, not reproduced live — real translocation requires a quarantined download; see Verification expectations.)*

## Current implementation (verified on branch `issue/0268`, 2026-07-24)

`BattyKit/Sources/BattyKit/Settings/CLIInstaller.swift`:

```swift
var isBundleDurable: Bool {
    let path = bundleURL.path(percentEncoded: false)
    return !path.contains("/DerivedData/") && !path.contains("/Build/Products/")
}
```

- `bundleURL` is injectable via `CLIInstaller.init(installPath:bundleURL:fileManager:)` (defaults to `Bundle.main.bundleURL`), which is what makes the predicate unit-testable.
- `install()` throws `CLIInstallerError.bundleNotDurable(path)` when the check fails; its message reads: *"Batty is running from a build folder (\<path\>). Move Batty.app to /Applications, then try installing again."*

Note: `isBundleDurable` does not exist on `main` yet — it lands with the #0268 squash merge. This issue starts after that lands.

## Detection options (implementer's choice)

1. **Substring match** — add `/AppTranslocation/` to the same `contains` chain in `isBundleDurable`. One line, symmetric with #0268's deliberate choice of simple path matching (which the #0268 reviewer judged the right call there). The `/AppTranslocation/` path component has been the documented, stable form since macOS 10.12.
2. **`SecTranslocateIsTranslocatedURL`** — the API Apple provides for exactly this question, and more robust than path matching. However, it is **not in the public Security.framework SDK headers** (verified against the installed SDK, 2026-07-24), so calling it means `dlopen`/`dlsym` plumbing against Security.framework — the pattern Sparkle and LetsMove use (not verified against their current sources). That is real machinery for a predicate the substring already answers.

**Recommendation:** option 1. It matches the existing check's style, needs no framework plumbing, and the failure mode if Apple ever renames the mount path is a missed refusal, not a crash. The ticket does not pre-decide; if the implementer prefers the API, keep the substring as a fallback when the symbol fails to resolve.

## User-facing message

This matters more here than in the DerivedData case. A developer hitting the DerivedData refusal understands immediately; a normal user who downloaded a release and clicked Install does not know what "running from a build folder" means. If the one-line substring fix is taken as-is, the translocated user gets exactly that build-folder wording — reachable but wrong for them. Two additional wrinkles for the translocation copy:

- The advice must include **relaunching**: a translocated instance stays translocated after the user drags the app to `/Applications`; only a fresh launch from the new location clears it.
- Consider whether `bundleNotDurable` should carry a variant (or the message should branch on which pattern matched) so the translocation case can say something like *"Batty is running from a temporary location because it was launched from Downloads. Drag Batty.app to /Applications, relaunch it, then try installing again."* — exact wording is the implementer's call.

Tests live in `BattyKit/Tests/BattyKitTests/` and run under `scripts/build.sh unit`; confirm the new test names appear in the run output.
- `scripts/build.sh` green.
- Reproducing *real* translocation requires downloading a quarantined DMG and running from `~/Downloads` — that end-to-end path (refusal message shown, no auth dialog) needs the user's runtime sign-off and cannot be done headlessly. Mark it in Gotchas, per the pattern in #0249–#0252 and #0268.
