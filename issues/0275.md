## Description

`isBundleDurable` (added in #0268) refuses to install the `/usr/local/bin/batty` symlink when the running bundle sits under `/DerivedData/` or `/Build/Products/`, because a symlink into a build-products path breaks on the next clean build and surfaces much later as a confusing `command not found`.

**Gatekeeper app translocation produces the same class of ephemeral bundle path and is not covered.** When a user downloads the DMG and runs `Batty.app` directly from `~/Downloads` without dragging it to `/Applications`, macOS runs it from a read-only, randomized mount of the form `/private/var/folders/<…>/AppTranslocation/<UUID>/d/Batty.app`. That path contains neither `/DerivedData/` nor `/Build/Products/`, so it passes the current durability check and Install happily creates a symlink into a location macOS reclaims — the exact failure `isBundleDurable` exists to prevent, reached by the more common route: a real user with a downloaded release, rather than a developer running from Xcode.

Found during the #0268 review by the reviewer subagent (`claude-opus-5`), which declined to gate approval on it since it falls outside #0268's stated scope.


## Resolution notes

> 🟢 Resolved 2026-07-25 — `isBundleDurable` now refuses a Gatekeeper-translocated bundle, with refusal copy that tells the user to **relaunch** after moving the app.

The live translocation scenario needs the user's runtime sign-off — it requires a quarantined DMG run from `~/Downloads`.

## Root cause

#0268 added `isBundleDurable` to stop Install creating a `/usr/local/bin/batty` symlink into an ephemeral bundle, but it only recognised `/DerivedData/` and `/Build/Products/` — the *developer's* route to that failure. **Gatekeeper app translocation produces the same class of ephemeral path by the more common route:** downloading the DMG and running `Batty.app` straight from `~/Downloads` makes macOS run it from a randomized read-only mount at `/private/var/folders/…/AppTranslocation/<uuid>/d/Batty.app`. That passed the check, so a normal user could install a symlink into a location macOS reclaims — surfacing much later as `command not found`.

## Fix

`/AppTranslocation/` added to the same `contains` chain, and a distinct `CLIInstallerError.bundleTranslocated(String)` selected by a private `isBundleTranslocated` check.

The separate error exists because **the correct advice differs in one critical way**: a translocated instance stays translocated until relaunched. Reusing `bundleNotDurable`'s "move to /Applications" copy would send the user in a loop — drag, click Install again in the still-translocated instance, hit the same refusal. The copy now reads:

> Batty is running from a temporary location (…) because it was launched without first being moved to /Applications. Drag Batty.app to /Applications, then relaunch Batty before trying to install the CLI — a translocated copy stays temporary until relaunched from its new location.

Substring matching was chosen over `SecTranslocateIsTranslocatedURL`, which is not in the public Security.framework SDK headers and would need `dlopen`/`dlsym`. The failure mode if Apple ever renames the mount path is a missed refusal, not a crash.

## Review

Reviewed by `claude-opus-5`, one round, approved first pass.

The reviewer confirmed the substring matches a real translocated path in both the `/private/var/…` and `/var/…` forms, and that the leading and trailing slashes give the same false-positive immunity #0268's review verified for `~/DerivedData Backup` — only a directory named exactly `AppTranslocation` matches. They confirmed the guard ordering is untouched: there is still exactly one `runPrivileged` call site behind the same three sequential guards, and the new code sits *inside* the existing `guard isBundleDurable else` body, so it selects which error to throw and cannot move the privileged call earlier.

They also reasoned through `uninstall()` and confirmed leaving it alone is correct — translocation makes the *source* ephemeral, while `uninstall()` only removes the destination symlink. The interesting case (a translocated instance with a working `/Applications`-sourced symlink) inspects as `.installedElsewhere`, which the UI renders with the **Install** button — and that path now refuses, so this change additionally stops a translocated instance from clobbering a *working* symlink.

On the flagged `isBundleTranslocated` duplication: accepted, because the branch is only evaluated once `isBundleDurable` has already returned false, so the worst outcome of a future divergence is the wrong refusal *message* — never a missed refusal and never a reached `runPrivileged`. A cosmetic failure mode on a safety-critical guard is the right way round.

## Gotchas

- **A translocated instance stays translocated until relaunched.** Dragging to `/Applications` is not enough on its own; the running process keeps its randomized read-only path. This is why the refusal copy is separate from `bundleNotDurable`'s, and why any future edit to that string must keep the relaunch instruction — a test asserts on it for that reason.
- **The new message is now the longest string that can reach `.failed(String)`** (~290 characters plus a long randomized path). `CLIInstallRow` renders it as `Text(reason).font(.caption)` with no `.fixedSize(horizontal: false, vertical: true)` and no width cap, inside a grouped `Form` with only `minWidth: 460`. Whether it wraps cleanly or widens the Settings window is unverified and belongs on the runtime sign-off list.
- Two wording rough edges, cheap to tighten if the live rendering reads badly: the raw randomized path sits mid-sentence ahead of the instruction, and "a translocated copy" appears in the trailing clause without the term being introduced.
- **Adjacent pre-existing oddity, out of scope:** a translocated instance holding a *valid* `/Applications`-sourced symlink shows the orange `.installedElsewhere` caption "A stale link points to … Installing will replace it." The link is not stale in that case — the running app is the wrong one. Worth revisiting if the CLI install UI is touched again.
- `isBundleTranslocated` recomputes the substring test already inside `isBundleDurable`. Deliberate, to keep the diff narrow; consolidating into a single `nonDurableReason` is the natural cleanup if this area is revisited.

## Steps to reproduce

1. Download the release DMG, open it, and drag `Batty.app` to `~/Downloads` (or run it straight from the mounted DMG's copy after Finder copies it anywhere other than `/Applications`).
2. Launch that quarantined copy — macOS translocates it to an `AppTranslocation` mount.
3. Settings → Advanced → Install the `batty` CLI.

## Expected behavior

Install refuses, the same way it refuses for a DerivedData bundle, with a message a non-developer can act on — tell them to drag Batty to `/Applications` and relaunch, then install.

## Actual behavior

The durability check passes, the auth dialog appears, and a `/usr/local/bin/batty` symlink is created pointing into the translocation mount. The mount disappears (relaunch from a different path, reboot), leaving a dangling symlink and a delayed `command not found`.

*(Actual behavior asserted from the implementation on branch `issue/0268`, not reproduced live — real translocation requires a quarantined download; see Verification expectations.)*

## Current implementation (verified on branch `issue/0268`, 2026-07-24)

`BattyKit/Sources/BattyKit/Settings/CLIInstaller.swift`:

```swift
var isBundleDurable: Bool {
    let path = bundleURL.path(percentEncoded: false)
    return !path.contains("/DerivedData/") && !path.contains("/Build/Products/")
}
```

- `bundleURL` is injectable via `CLIInstaller.init(installPath:bundleURL:fileManager:)` (defaults to `Bundle.main.bundleURL`), which is what makes the predicate unit-testable.
- `install()` throws `CLIInstallerError.bundleNotDurable(path)` when the check fails; its message reads: *"Batty is running from a build folder (\<path\>). Move Batty.app to /Applications, then try installing again."*

Note: `isBundleDurable` does not exist on `main` yet — it lands with the #0268 squash merge. This issue starts after that lands.

## Detection options (implementer's choice)

1. **Substring match** — add `/AppTranslocation/` to the same `contains` chain in `isBundleDurable`. One line, symmetric with #0268's deliberate choice of simple path matching (which the #0268 reviewer judged the right call there). The `/AppTranslocation/` path component has been the documented, stable form since macOS 10.12.
2. **`SecTranslocateIsTranslocatedURL`** — the API Apple provides for exactly this question, and more robust than path matching. However, it is **not in the public Security.framework SDK headers** (verified against the installed SDK, 2026-07-24), so calling it means `dlopen`/`dlsym` plumbing against Security.framework — the pattern Sparkle and LetsMove use (not verified against their current sources). That is real machinery for a predicate the substring already answers.

**Recommendation:** option 1. It matches the existing check's style, needs no framework plumbing, and the failure mode if Apple ever renames the mount path is a missed refusal, not a crash. The ticket does not pre-decide; if the implementer prefers the API, keep the substring as a fallback when the symbol fails to resolve.

## User-facing message

This matters more here than in the DerivedData case. A developer hitting the DerivedData refusal understands immediately; a normal user who downloaded a release and clicked Install does not know what "running from a build folder" means. If the one-line substring fix is taken as-is, the translocated user gets exactly that build-folder wording — reachable but wrong for them. Two additional wrinkles for the translocation copy:

- The advice must include **relaunching**: a translocated instance stays translocated after the user drags the app to `/Applications`; only a fresh launch from the new location clears it.
- Consider whether `bundleNotDurable` should carry a variant (or the message should branch on which pattern matched) so the translocation case can say something like *"Batty is running from a temporary location because it was launched from Downloads. Drag Batty.app to /Applications, relaunch it, then try installing again."* — exact wording is the implementer's call.
