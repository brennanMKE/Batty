## Description

Two related defects in the #0290 footprint-warning strings, plus one correction to the record. The genuinely broken part: `AppStateStore.formatGB(_:)` builds its number with `String(format: "%.2f GB", …)`, hard-coding `.` as the decimal separator inside a sentence that goes through `String(localized:)` — and the app ships `Batty/Localizable.xcstrings` with 15 locales (de, en, es, es-419, fr, it, ja, ko, nl, pl, pt-BR, ru, tr, zh-Hans, zh-Hant). In the same sentence, `sessionNoun` is an English literal (`"Terminal Session"`/`"Terminal Sessions"`) interpolated into the localized string, so its plural rule is untranslatable.

The part that is *not* a defect, contrary to what #0290's review recorded: Batty divides by 2³⁰ and labels the result "GB". Verification (below) establishes that this is exactly what Activity Monitor, `top`, `footprint`, and Apple's own `ByteCountFormatter.CountStyle.memory` do — macOS's memory convention is binary units under decimal-looking labels. #0290's Gotcha claims "Activity Monitor uses decimal GB — Batty's number reads ~7% lower for the same footprint"; that claim is wrong, and left uncorrected it would push a future implementer to "fix" toward decimal division, *creating* the cross-check mismatch it warns about. This issue is the tracked correction.

## Verification of Activity Monitor's units (2026-08-01)

**Measured — command-line tools are binary.** A probe process allocated 2.5 GiB and read its own `phys_footprint` in-process via `task_info(TASK_VM_INFO)`: exactly **2,735,688,272 bytes**. That is 2,608.96 × 2²⁰ or 2,735.7 × 10⁶. Against the same pid:

- `footprint -p <pid>` printed `Footprint: 2609 MB`
- `top -l 1 -pid <pid> -stats mem` printed `2609M`

Both match bytes/2²⁰, not bytes/10⁶ — binary units under an "MB" label.

**Measured — Apple's formatter styles diverge exactly on this axis.** `ByteCountFormatter` on this machine (macOS 26, 2026-08-01):

| Bytes | `.memory` / `.binary` | `.file` / `.decimal` |
|---|---|---|
| 1,000,000,000 | 953.7 MB | 1 GB |
| 1,073,741,824 (2³⁰) | 1 GB | 1.07 GB |
| 8,546,000,000 (#0285's reported footprint) | 7.96 GB | 8.55 GB |

`.memory` — the style Apple named for this exact use — is 1024-based under a "GB" label. The decimal styles are the *file/storage* convention (the Mac OS X 10.6 Finder/Disk Utility change was about storage sizes); conflating that with memory display is precisely the error in #0290's Gotcha.

**Documented — Activity Monitor specifically.** Howard Oakley, "Activity Monitor: meanings and misleadings" (eclecticlight.co, 2022-08-13): "all memory sizes are given in old-style bytes, with 1024 B in 1 KB, and so on, sometimes referred to KiB, MiB, etc."

**Not verified — Activity Monitor's GUI on this machine** (the screen was locked for the whole session; measured tools + `.memory` semantics + the cited article make binary the near-certain answer, but the GUI itself was not observed). One-glance manual check to close the gap: this Mac has `hw.memsize` = 68,719,476,736 bytes = exactly 64 GiB (68.72 decimal GB). Open Activity Monitor → Memory tab → Physical Memory: **"64.00 GB" confirms binary; "68.72 GB" would mean decimal.** (Equivalent per-process check: compare any process's Memory value against `footprint -p <pid>` bytes divided by 2²⁰ and by 10⁶.)

## Current code instances (verified on `main`, 2026-08-01)

- `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:797` — `formatGB(_:)` divides by `1_073_741_824` and formats with `String(format: "%.2f GB", …)`. The division is correct per the verification above; the `String(format:)` is the locale bug. (The function's doc comment already correctly notes `.memory` is 1024-based — the code got it right; the #0290 review record got Activity Monitor wrong.)
- `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:766` — `sessionNoun` English-literal plural interpolated into the `String(localized:)` warning sentence at line 768.
- `BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift:126` — `resolvedFootprintSoftLimitBytes()` multiplies the stepper's GB value by `1_073_741_824`; `BattyKit/Sources/BattyKit/Views/SettingsView.swift:322` labels it "Warn above N GB". Consistent with `formatGB` and with Activity Monitor.

## Expected behavior

- **One documented convention for all user-facing memory values: bytes ÷ 2³⁰, labeled "GB"** — in the warning text, the Settings stepper, and any future memory UI. This matches Activity Monitor's number *and* its label. Relabeling as "GiB" would be pedantically correct but would diverge from the label every macOS surface shows; matching the number a user cross-checks matters most, and here number and label can both match. Record the convention where the next implementer will find it (the `formatGB` doc comment already carries most of it).
- **`formatGB` formats through the locale.** One-line fix: `(Double(bytes) / 1_073_741_824).formatted(.number.precision(.fractionLength(2)))` interpolated into the localized sentence, keeping the fixed two decimals that keep a just-crossed warning visibly above its limit.
- **The Terminal Session count pluralizes through the localization system** (string-catalog plural rules / automatic grammar agreement), not an English ternary. Note the latent scope from #0290: BattyKit's `String(localized:)` calls are not in the catalog today, so this lands fully only when that extraction happens — the fix should at least stop baking the English plural into the interpolation.
- **#0290's record is corrected** so the wrong Activity Monitor claim can't steer future work (done in the same commit as this filing — see Relation).

## Resolution notes

> 🟢 Resolved 2026-08-01 — the footprint warning now formats numbers per the user's locale and pluralises through the string catalog. The GiB convention was verified correct and left alone.

## Root cause

Two defects in the warning strings added by #0290, plus one false alarm.

- `formatGB` used `String(format: "%.2f GB", …)`, hard-coding `.` as the decimal separator inside a sentence that goes through `String(localized:)` in an app shipping 15 locales.
- `sessionNoun` was an English literal chosen by a ternary and interpolated into a localized string, so both the noun and its plural rule were untranslatable.
- The suspected GB-vs-GiB mismatch **did not exist**. Verified empirically: a probe process read exactly 2,735,688,272 bytes via `task_info`, and both `footprint -p` and `top` printed "2609 MB" — bytes ÷ 2²⁰, decisively binary. `ByteCountFormatter.CountStyle.memory` is likewise 1024-based under decimal labels, and Activity Monitor's memory display is binary too. Batty's `1_073_741_824` divisor already matches Activity Monitor's number *and* its label. #0290's Gotcha claiming a ~7% discrepancy was wrong and has been corrected.

## Fix

- `formatGB` now formats via `.formatted(.number.precision(.fractionLength(2)).locale(locale))`, with the locale injectable for tests.
- The ternary is gone; the plural rule lives in `Batty/Localizable.xcstrings`, and the English variation was copied into all 14 other locales marked `needs_review` so each applies its own CLDR plural rule to the same English words (see Gotchas for the limits of that).
- `footprintWarningMessage(footprintText:sessionCount:bundle:locale:)` extracted with production defaults, so tests can inject an explicitly compiled bundle.
- A doc comment on the divisor records why it is binary, so nobody "corrects" it to decimal later.

## Review

Reviewed by claude-opus-5 over two rounds.

Round 1 confirmed the locale fix worked across all 15 locales with **0 mismatches against the old formatter over 50,000 sampled byte values**, then blocked on the plural half. The plural test compared the catalog against a hand-copied literal in the test file and **passed with the feature broken** — mutating the real sentence left it green. Worse, moving the rule into an English-only catalog entry **introduced a regression**: 14 of 15 locales fell back to the base literal and rendered "1 Terminal Sessions" in the singular, where `main`'s ternary had been correct everywhere — and a code comment asserted that exact problem could not happen. Round 1 also corrected the implementer's conclusion that plural rendering was untestable: compiling the catalog with `xcstringstool` and loading it via `Bundle(url:)` makes it directly testable.

Round 2 approved after re-measuring everything: source-side mutation fails all 8 cases, catalog-side singular mutation fails exactly the 4 singular cases while the plural cases stay green (proving the test is precise, not blunt), and `fr`/`de`/`ru` now render "1 Terminal Session" correctly.

## Gotchas

- **`Bundle.main` is the xctest runner under `BattyKitTests`**, so `String(localized:)` silently falls back to source literals and *no* localization behavior is observable by default. Test localization against an explicitly constructed bundle: compile with `xcrun xcstringstool compile`, load with `Bundle(url:)`, pass `bundle:` through. Before this issue, no localization behavior was unit-tested anywhere in this repo.
- **The English-under-foreign-plural-rules state is a bridge, not correctness.** It fixes 11 of 15 locales. **CJK locales (ja, ko, zh-Hans, zh-Hant) still render "1 Terminal Sessions"** — CLDR gives those languages only an `other` category, so the `one` variation is never selected. And **ru renders "21 Terminal Session"** at 21, 31, 101… because CLDR correctly selects `one` there. Both are *correct once the sentence is actually translated*; both look wrong while it is untranslated English. The strings are marked `needs_review` for that reason.
- **"Terminal Session" was deliberately left untranslated.** It is a load-bearing term in `Concepts.md`, distinct from Batty's other "Session" concept, and guessing at it across 14 unverifiable languages was judged a real risk rather than a cosmetic one.
- **Pre-existing imprecision, not introduced here:** the "keeps the warning text visibly above whatever limit it just crossed" comment is not strictly true — 4 GiB + 1 byte still renders `4.00 GB`. Two decimals shrink the ambiguity window from ~500 MB to ~5 MB, which is the real benefit.
- **Nobody has seen these strings rendered in the running app** (the screen was at loginwindow throughout). The user should check the Bell Feed entry and system notification at 1 and at several sessions, the decimal separator on a genuinely non-English system, and the one-glance Activity Monitor cross-check: Memory → Physical Memory should read **64.00 GB** (binary), not 68.72 GB.
