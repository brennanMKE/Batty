## Description

Tier 1 localization target. The largest developer population in the world; Batty's existing CJK IME work already serves this audience for terminal input, so giving them a localized UI completes the experience.

Depends on `#0107`.

## Acceptance criteria

- Every key in `Localizable.xcstrings` has a non-empty `zh-Hans` translation, reviewed by a native speaker.
- Launching Batty with macOS Language & Region set to 简体中文 (zh-Hans) shows the full UI translated.
- Visual sweep confirms no clipping; Chinese characters render at the right size and weight in Settings labels, menu titles, and alert bodies.
- `## Files changed` in the resolution should list the `.xcstrings` diff.

## Notes

- Distinct from Traditional Chinese (`zh-Hant`, tracked as `#0116`). Ship both; some users explicitly prefer one and reject the other.
- Product name "Batty" stays in Latin script.
- Bell feed timestamps should render in the Chinese locale format automatically once the foundation lands.
- Sparkle ships zh-Hans strings.

## Root cause

The `zh-Hans` locale was empty after `#0107` landed — that foundation pass only populated English (with a tiny `de` smoke-test stub for `Quit Batty?` / `Quit` / `Cancel`). `#0108` added Japanese but left `zh-Hans` untouched. Every key in `Localizable.xcstrings` needed a Simplified Chinese translation added before mainland-China users would see any localized UI.

## Fix

Populated `zh-Hans` translations for every key currently in the catalog:

- `Batty` — passes through as the literal Latin-script brand name, matching the catalog's "never translate the product name" convention. No transliteration to 蝙蝠.
- `Quit Batty?` → `要退出 Batty 吗？` (Apple's standard quit-alert phrasing on macOS in Simplified Chinese, e.g. Terminal.app's "要退出"终端"吗？").
- `Quit` → `退出`. `Cancel` → `取消`. Both match the macOS-wide Simplified Chinese terminology used in System Settings and standard `NSAlert` buttons.
- `Paste %lld lines?` (plural) → `要粘贴 %lld 行吗？` for both `one` and `other`. Chinese has no grammatical singular/plural distinction, so both variants carry the same form.
- `There %lld open terminal(s).` (plural) → `有 %lld 个终端已打开。` for both variants. The measure word 个 is the standard general-purpose classifier; 终端 is Apple's established Simplified Chinese rendering for "terminal".
- `%lld unseen bell event(s)` (plural) → `%lld 个未读响铃事件` for both variants. 响铃 (literally "ringing bell") is the natural Simplified Chinese term for the terminal bell; 未读 ("unread/unseen") matches the badge semantics.

Format specifiers (`%lld`) are preserved verbatim. Full-width punctuation (`？`, `。`) is used to match native macOS Simplified Chinese system UI conventions. A space is inserted between Chinese characters and the embedded Latin brand `Batty`, per Apple's house style.

## Files changed

- `Batty/Localizable.xcstrings` — added `zh-Hans` localizations (4 simple keys + 3 plural-aware keys with `one`/`other` variants each).

## Gotchas

- **LLM-authored, not native-speaker reviewed.** Per the acceptance criteria, a native-speaker review pass is still ideal before this ships to mainland-China users. The translations follow Apple's published Simplified Chinese terminology (Terminal.app, System Settings, the macOS Human Interface Guidelines' Simplified Chinese references) and use widely-accepted Apple renderings (粘贴, 终端, 退出, 取消), but phrasing choices ("要…吗？" vs "确定…？", 响铃事件 vs 铃声事件) are judgment calls a native reviewer may want to revisit.
- **Punctuation: full-width vs half-width.** The Japanese pass (#0108) used half-width `?` for the question mark, but Simplified Chinese on macOS native UI strongly favours full-width punctuation (`？`, `。`). I followed Apple's mainland-China convention here. If a future review prefers half-width to match the catalog's English source punctuation more literally, the four affected values are easy to flip.
- **Paste verb: 粘贴 vs 拷贝/粘贴.** macOS uses 粘贴 (zhāntiē) as the standalone "Paste" verb in mainland Simplified Chinese (it appears in the Edit menu as 编辑 → 粘贴). I used 粘贴 — not 拷贝粘贴 ("copy-paste"), which is a colloquial compound, and not Taiwan's 貼上. This matches what Terminal.app's zh-Hans build displays.
- **Plural variants carry the same string** because Chinese has no grammatical number. The catalog still requires both `one` and `other` to be populated, but the rendered output is identical regardless of count.
- **Measure word choice: 个 for terminals, 个 for events.** Both use the neutral general-purpose classifier 个 (gè). More specific classifiers exist (e.g. 台 for machines/devices, 条 for messages/events) but 个 is what Apple uses for similar items in macOS system UI; sticking with 个 keeps the tone consistent with native-feeling mainland Apple software.
- **`knownRegions` in `Batty.xcodeproj/project.pbxproj` still does not list `zh-Hans`.** The `#0107` and `#0108` resolutions noted that `xcstringstool` emits `zh-Hans.lproj/Localizable.strings` and `Localizable.stringsdict` correctly anyway — confirmed locally: building this branch produces both files in the `.app` and `plutil -p` shows the translated values. Registering `zh-Hans` in the Xcode Localization UI is only needed to make the catalog editor render the column.
- **Verified by build, not by runtime.** `xcodebuild -scheme Batty -destination 'platform=macOS' build` passed (with `CODE_SIGN_IDENTITY=-` / `CODE_SIGNING_REQUIRED=NO` / `CODE_SIGNING_ALLOWED=NO`, mirroring the foundation and Japanese subagents' environments). The compiled `zh-Hans.lproj` resources were inspected with `plutil -p` to confirm the catalog round-trip. A full runtime visual sweep under `-AppleLanguages '(zh-Hans)'` — the acceptance criterion for no clipping or wrapping regressions in Settings, the bell feed popover, and alerts — has not been done and is part of what the user needs to confirm before this moves from `resolved` to `closed`.
