## Description

Every Pane in Batty renders exactly one kind of content: Terminal Sessions. The user wants Panes that can host other view kinds — starting with a **Git Status view** and a **Process Status view** — creatable and closable from the `batty` CLI. In the user's words:

> "Once we have the CLI working well for agents we can start adding new views which can support new types of panes. We currently only have terminal panes. The first new view we can add is Git Status. It can monitor the current directory and show status very similar to `git status` but in a more visual way like a Mac app can support which a TUI cannot. The CLI will be able to create a new pane with the Git Status view as well as close it."
>
> "When we get to this issue we can draft visual designs before implementing it."

**This is an umbrella tracking issue. It ships no code itself — all work happens in the children below.**

The load-bearing architectural point, established when this was investigated as a single issue: today the model, the view layer, and the CLI all presume a terminal at every level — a split-tree leaf *is* a `PaneRuntime`, every Tab *is* a Terminal Session, and the pane body unconditionally mounts terminal placeholders whose rendering side effect is spawning a PTY. Introducing a **pane kind** concept is most of the real work; the concrete views are its first clients. The verified source citations for all of this live in #0302, which owns the abstraction design.

**Design-first gate (user-directed):** visual designs for each new view are drafted and approved by the user **before** implementation starts. No view child moves to implementation on an unapproved design; if design review changes scope materially, re-file or amend before coding.

## Prerequisite gate: the CLI must be solid for agents first

The user's framing: "Once we have the CLI working well for agents…". The agent-facing surface that already exists on `main`:

- `batty id` / `batty list --json` — identity and topology (`TopologyPayload`); `TopologyTabPayload` reports `title`, `workingDirectory`, `isActive` (`BattyKit/Sources/BattyXPCCore/TopologyPayload.swift:48-61`).
- `batty pane split [-h|--horizontal | -v|--vertical] [-c <cmd>] [--pane <id>]` — the first mutating XPC verb (#0282), replying with the new pane id so an agent can chain on it.
- `batty pane close [--pane <id>]` — pane-level close with a real result; stale id exits `4` (#0283).
- `batty notify --title <t> [--body <b>] [--sound] [--tab <id>]` — posts into the Bell Feed (#0284).

What a non-terminal pane additionally needs from that surface, and doesn't have today:

- **Kind-aware create.** `PaneSplitRequest` carries only `paneID` / `direction` / `command` (`BattyKit/Sources/BattyXPCCore/PaneSplitPayload.swift:25-35`); `command` presumes a shell. A `--view git-status` style option (plus, probably, a path argument) means either extending that payload with a pane-kind field or adding a new verb — a design decision, since XPC payloads are a versioned wire format between the CLI and the app.
- **Kind-aware close.** `batty pane close` already targets by pane id, so the verb shape generalizes — but its implementation cascades through Tab/Terminal Session teardown (`AppStateStore.closePane`, `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:329`, ending in `TerminalHostStore.releaseTerminalView`), which a non-terminal pane doesn't have. The close path needs a kind-aware branch, not a new verb.
- **Kind-aware `list`.** `TopologyPanePayload`/`TopologyTabPayload` have no kind field; an agent reading the layout must be able to tell a non-terminal pane from a terminal pane.

The gate: don't start view implementation (and arguably not the visual-design phases) until the #0257-umbrella CLI work the user considers "working well for agents" is settled — at minimum the verbs above are user-verified in daily agent use, and any near-term payload changes (e.g. the still-unfiled `tab close` from #0283's notes) have landed so the pane-kind extension doesn't collide with them.

This umbrella can close only when **both** hold:

1. Every child above is resolved.
2. The visual designs for the new views (#0304, #0305) were drafted and **approved by the user before their implementation began** — the design-first gate held, not just the features shipped.

## Scope note

Project guidance to date (recorded in session memory) is that Batty is a terminal multiplexer and general content viewers (markdown preview, image viewer) belong in dedicated apps. Git Status and Process Status sit adjacent to that line: both are developer-workflow tooling tied to a terminal's directory or process, not general file viewers — and the user is requesting them directly, so they're filed as asked. But they **do** expand the Pane model beyond Terminal Sessions, and `PRD.md` (goals §3, Concepts list) and `Concepts.md` (Pane: "hosts the Tab bar and renders the active Tab's Terminal Session") will need updating to a pane-kind vocabulary if this proceeds. That documentation change is a real part of the implementation work, not an afterthought — `Concepts.md` is the canonical vocabulary this tracker and every subagent depend on.
