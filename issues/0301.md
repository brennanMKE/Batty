## Description

Every Pane in Batty renders exactly one kind of content: Terminal Sessions. The user wants a second kind — a **Git Status view** that monitors a directory and presents `git status` visually, the way a Mac app can and a TUI cannot — creatable and closable from the `batty` CLI. In the user's words:

> "Once we have the CLI working well for agents we can start adding new views which can support new types of panes. We currently only have terminal panes. The first new view we can add is Git Status. It can monitor the current directory and show status very similar to `git status` but in a more visual way like a Mac app can support which a TUI cannot. The CLI will be able to create a new pane with the Git Status view as well as close it."
>
> "When we get to this issue we can draft visual designs before implementing it."

This is **not a build-it ticket**. It is explicitly two-phase and design-gated:

- **Phase 1 — visual designs.** Draft mockups/design directions for the Git Status view and settle the design-phase questions below. Deliverable: designs for the user to review. **No implementation happens in phase 1.**
- **Phase 2 — implementation.** Starts only after the user approves the designs. If the design review changes scope materially, re-file or amend before coding.

The load-bearing architectural point: this is the **first Pane whose content is not a Terminal Session**, and today the model, the view layer, and the CLI all presume a terminal at every level (see "What stands in the way"). Introducing a *pane kind* concept is most of the real work; the Git Status view itself is the first client of it.

## Prerequisite gate: the CLI must be solid for agents first

The user's framing: "Once we have the CLI working well for agents…". Concretely, the agent-facing surface that already exists on `main`:

- `batty id` / `batty list --json` — identity and topology (`TopologyPayload`); `TopologyTabPayload` reports `title`, `workingDirectory`, `isActive` (`BattyKit/Sources/BattyXPCCore/TopologyPayload.swift:48-61`).
- `batty pane split [-h|--horizontal | -v|--vertical] [-c <cmd>] [--pane <id>]` — the first mutating XPC verb (#0282), replying with the new pane id so an agent can chain on it.
- `batty pane close [--pane <id>]` — pane-level close with a real result; stale id exits `4` (#0283).
- `batty notify --title <t> [--body <b>] [--sound] [--tab <id>]` — posts into the Bell Feed (#0284).

What a Git Status pane additionally needs from that surface, and doesn't have today:

- **Kind-aware create.** `PaneSplitRequest` carries only `paneID` / `direction` / `command` (`BattyKit/Sources/BattyXPCCore/PaneSplitPayload.swift:25-35`); `command` presumes a shell. A `--view git-status` style option (plus, probably, a path argument) means either extending that payload with a pane-kind field or adding a new verb — a design decision, since XPC payloads are a versioned wire format between the CLI and the app.
- **Kind-aware close.** `batty pane close` already targets by pane id, so the verb shape generalizes — but its implementation cascades through Tab/Terminal Session teardown (`AppStateStore.closePane`, `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:329`, ending in `TerminalHostStore.releaseTerminalView`), which a non-terminal pane doesn't have. The close path needs a kind-aware branch, not a new verb.
- **Kind-aware `list`.** `TopologyPanePayload`/`TopologyTabPayload` have no kind field; an agent reading the layout must be able to tell a Git Status pane from a terminal pane.

The gate: don't start phase 2 (and arguably phase 1) until the #0257-umbrella CLI work the user considers "working well for agents" is settled — at minimum the verbs above are user-verified in daily agent use, and any near-term payload changes (e.g. the still-unfiled `tab close` from #0283's notes) have landed so the pane-kind extension doesn't collide with them.

## What stands in the way (verified in source)

Everything below is why "add a view" is really "introduce a pane kind".

**1. The model presumes a terminal at every level.**

- A split-tree leaf *is* a `PaneRuntime`: `SplitTreeNode` is `case leaf(PaneRuntime)` / `case split(…)` (`BattyKit/Sources/BattyKit/Model/SplitTree.swift:27-30`).
- `PaneRuntime` requires at least one Tab: `precondition(!initial.isEmpty, "PaneRuntime must contain at least one Tab")` (`BattyKit/Sources/BattyKit/Runtime/PaneRuntime.swift:31`).
- `TabRuntime.terminal` is a non-optional `public let terminal: TerminalViewState` (`BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:12`), constructed unconditionally in `init` (`TabRuntime.swift:117`). Every Tab **is** a Terminal Session; there is no way to represent a Tab or Pane without libghostty state today.
- Every pane-creation path funnels through `SplitTree.makePane` (`SplitTree.swift:208-215`), which always builds `PaneRuntime`/`TabRuntime` and inherits the source Tab's terminal cwd.

The design decision phase 1 must produce an answer for: where does *kind* live? Options include a kind on the Pane (a Git Status pane has no Tab bar at all) versus a kind on the Tab (a Git Status tab could sit alongside terminal tabs in one Pane). The user's phrasing — "create a new pane with the Git Status view" — suggests pane-level, but the model consequence differs a lot and the designs should make the choice visible.

**2. The view layer's pane body is unconditionally terminal placeholders.**

`PaneView.body` renders the tab bar plus `ZStack { ForEach(pane.tabs) { TerminalPlaceholderView(…) } }` (`BattyKit/Sources/BattyKit/Views/PaneView.swift:122-129`). There is no branch point where a pane could render anything else. Worse, mounting a `TerminalPlaceholderView` is not passive: its `body` eagerly calls `TerminalHostStore.shared.terminalView(for:windowID:)` to spawn the PTY (`BattyKit/Sources/BattyKit/Views/TerminalPlaceholderView.swift:36-43`). A non-terminal pane must never mount one, or it starts a shell as a rendering side effect.

**3. The terminal-host architecture applies only to terminal kinds — which is a simplification, if the boundary is drawn right.**

Per `docs/view-hierarchy.md` §3, terminal content is not hosted by SwiftUI at all: `TerminalHostStore` keeps one persistent `TerminalHostView` per content window with one `AppTerminalView` subview per live Tab, placed over placeholder-reported frames. A Git Status view is plain SwiftUI — it needs **none** of that (no placement, no host subview, no geometry probe), and SwiftUI's rebuild churn that kills PTYs is harmless to it. The abstraction boundary must become: *terminal* panes get placeholders + host placement; *non-terminal* panes render their SwiftUI body directly. Note the z-order constraint from `view-hierarchy.md` §4 ("AppKit-on-top"): the host layer floats above the SwiftUI tree, but it only occupies frames reported for terminal Tabs, so a non-terminal pane's region has no host subview over it — pointer input should reach the SwiftUI view normally. The `docs/terminal-pane-requirements.md` checklist stays scoped to terminal panes; phase 2 should say explicitly which of its guarantees (if any) a non-terminal pane must still honor.

**4. Persistence: the Codable model needs a kind — but whether anything serializes it today can't be settled from the docs.**

The one Codable layout type is `Pane` carrying only `id` and `isHidden` (`BattyKit/Sources/BattyKit/Model/LayoutModel.swift:15-23`, produced by `PaneRuntime.snapshot()`, `PaneRuntime.swift:39-41`). A pane kind must be added there with a backward-compatible decode (absent field = terminal). However, the documentation contradicts itself about workspace persistence: CLAUDE.md and `docs/view-hierarchy.md` describe `workspace.json` serialization and link a `WorkspaceManager.swift` (`docs/view-hierarchy.md:54`) **that does not exist in the tree**, no code anywhere encodes `Pane`, and `Concepts.md:270`'s version note says Workspace persistence was "never a planned feature" — while per-concept "Persisted:" rows remain (`Concepts.md:37,53,75,94,111`). Can't tell from source which way this is headed; the pane-kind field should be designed as if persistence lands, and the doc inconsistency is worth resolving alongside the `Concepts.md`/`PRD.md` updates this issue already requires.

## Design-phase questions (to answer in phase 1, not decided here)

1. **Which directory does it monitor?** The user said "the current directory" — but a Pane has no cwd of its own; a Terminal Session does (`TabRuntime.workingDirectory`, `TabRuntime.swift:47`). Options to lay out in the designs: the cwd of the sibling terminal Pane it was split from (frozen at creation vs. live-following that pane's `cd`s), an explicitly-set path with a folder picker, or a path supplied by the CLI at creation (`--path`). This is the first thing a design has to answer, including what the view shows when the directory is not a git repository, is a submodule, or is a linked worktree.
2. **What it shows.** Staged / unstaged / untracked groupings, per-file status, branch with ahead/behind, merge/rebase/cherry-pick state, stash count, diff stats. The user's point is that a Mac app can do what a TUI cannot — selection, disclosure triangles, inline diff peeks, click-through to files — so the designs should exploit that rather than reproduce a text table in a nicer font.
3. **Read-only or interactive?** Staging, unstaging, and discarding are the obvious next asks and carry real destructive-action risk (discard especially). The design must settle this explicitly; a read-only first cut is the conservative option and keeps phase 2 small.
4. **How it stays current.** Filesystem watching (FSEvents / `DispatchSource`) vs. polling; debounce strategy for large repos mid-build (thousands of file events); cost of running `git status` on a large working tree; behavior when `.git` itself churns (rebase in progress).
5. **Battery and CPU discipline.** This is a persistent always-on view in an app whose current umbrella (#0285) is about unbounded resource growth. Requirement to carry into the designs: it must not poll aggressively, and it must stop work entirely when its Pane is not visible — the analogue of #0288's occlusion signalling for Terminal Sessions (`setSurfaceVisible` / `OccludedSurfaceTicker`), except here it's Batty's own watcher to suspend, which is strictly easier.

## Scope note

Project guidance to date (recorded in session memory) is that Batty is a terminal multiplexer and general content viewers (markdown preview, image viewer) belong in dedicated apps. Git Status sits adjacent to that line: it is developer-workflow tooling tied to a terminal's directory, not a general file viewer — and the user is requesting it directly, so it's filed as asked. But it **does** expand the Pane model beyond Terminal Sessions, and `PRD.md` (goals §3, Concepts list) and `Concepts.md` (Pane: "hosts the Tab bar and renders the active Tab's Terminal Session") will need updating to a pane-kind vocabulary if it proceeds. That documentation change is a real part of phase 2's work, not an afterthought — `Concepts.md` is the canonical vocabulary this tracker and every subagent depend on.
