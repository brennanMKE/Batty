# 0410 — Dragging a Session over a collapsed Session row in the Sidebar auto-expands that row's Pane list, which adds nothing to a reorder

| | |
|---|---|
| **Status** | open |
| **Module** | Sidebar |
| **Platform** | macOS |
| **First seen** | 2026-09-14 |

## Description

While drag-reordering a Session in the Sidebar, holding the dragged row over another, collapsed Session row expands that Session's Pane list. The user's verdict: "That adds no value to the user. Disable the expansion." A Session-reorder drag has exactly one valid outcome — a new position in the Session list — and nothing about that outcome depends on seeing the hovered Session's Panes. The expansion is a side effect of the AppKit view backing the Sidebar `List`, not something Batty asked for.

This is UI work. Visual sign-off is the user's; mark `resolved`, never `closed`.

## Steps to reproduce

1. Launch Batty with at least two Sessions (Cmd-N twice). Leave every Session's Pane list collapsed (the default — see `SessionRuntime.isPaneListExpanded`).
2. Press and hold on one Session row in the Sidebar and start dragging it.
3. Hover the drag over a different, collapsed Session row and hold still for a moment.

## Expected behavior

While dragging a Session in the Sidebar, hovering over another Session never expands it — not after any hover duration. Reordering still works (the drop indicator appears between rows and the drop lands the Session at the new position), and any other valid drop still works. Click-driven expansion (the chevron) and keyboard-driven expansion are unaffected. Nothing else about Sidebar drag changes.

## Actual behavior

After hovering over a collapsed Session row for a moment, that Session's Pane list expands beneath it, shifting the rows below and revealing `PaneRow`s the reorder has no use for.

## Acceptance

- A Session drag hovering over a collapsed Session row does not expand it, regardless of how long the hover lasts.
- The drop-target indicator still shows, and `.onMove` reorder still lands the Session at the drop position (`WindowRuntime.moveSessions`, `BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift:328`).
- Clicking a Session row's chevron still expands and collapses the Pane list (`PaneSidebarTests.testChevronExpandsAndCollapsesPaneList`, `BattyUITests/PaneSidebarTests.swift:64`, keeps passing). Keyboard expansion (Right/Left arrow on a selected row) is unaffected.
- Hiding a Pane still auto-expands the owning Session's Pane list (`WindowRuntime.hidePane`, `WindowRuntime.swift:774`; `PaneSidebarTests.testHidingPaneAutoExpandsPaneList`, `PaneSidebarTests.swift:142`) — that expansion is deliberate (#0258) and unrelated to drag.
- No other Sidebar drag behavior changes.

## Notes

### Where the Sidebar drag lives

`BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift`:

- Line 20: `List(selection: sidebarSelection)` with `.listStyle(.sidebar)` (line 86).
- Lines 36–39: each Session is a `DisclosureGroup(isExpanded: Binding(get: { session.isPaneListExpanded }, set: { session.isPaneListExpanded = $0 }))` whose label is the `SessionRow` and whose content is the `PaneRow` list.
- Lines 82–84: `.onMove { source, destination in windowRuntime.moveSessions(fromOffsets: source, toOffset: destination) }` — the only drag-and-drop handling in the file.
- The expansion flag is `SessionRuntime.isPaneListExpanded` (`BattyKit/Sources/BattyKit/Runtime/SessionRuntime.swift:26`, `@Observable`, default `false`, not persisted). Its only writers are the `DisclosureGroup` binding setter above and `WindowRuntime.hidePane` (`WindowRuntime.swift:774`).

### Mechanism (high confidence, not yet observed under a debugger)

On macOS a `.sidebar`-styled `List` containing `DisclosureGroup`s is backed by an `NSOutlineView` — the file's own comment at `SessionSidebarView.swift:22–28` says the sidebar List "maps DisclosureGroup onto NSOutlineView expansion", and `PaneSidebarTests.chevron(in:)` (`PaneSidebarTests.swift:24–31`) depends on it by locating the row's native `disclosureTriangle`.

`NSOutlineView` has a built-in behavior of auto-expanding a collapsed item when a drag hovers over it. Apple's header documents it only through the hook that undoes it: `-[NSOutlineView shouldCollapseAutoExpandedItemsForDeposited:]` — "This method returns YES to indicate that auto expanded items should return to their original collapsed state" (AppKit SDK `NSOutlineView.h`, in the `Drag and Drop` section). Before expanding, the outline view consults `NSOutlineViewDelegate.outlineView(_:shouldExpandItem:)` ("If NO is returned, 'item' will not be expanded"). Neither hook is reachable from SwiftUI's public `List` / `DisclosureGroup` / `onMove` API, and SwiftUI installs its own delegate and drag source/destination on the outline view. That is why nothing in Batty's code produces the expansion and nothing in Batty's code can currently veto it.

Because the `DisclosureGroup` binding at lines 36–39 is driven by the outline view's expansion, the drag-hover auto-expand almost certainly also writes `session.isPaneListExpanded = true` through the binding setter. Whether the outline view's post-drop re-collapse (`shouldCollapseAutoExpandedItemsForDeposited:` defaults to `YES`) flows back through the binding is unverified — the implementer should check whether the flag is left `true` after the drop. Either way, the hover-time expansion the user sees is the complaint.

### Candidates checked and ruled out

- No custom `onDrop` / `DropDelegate` / `dropEntered` / `onInsert` in `SessionSidebarView.swift`, `WindowRuntime.swift`, or `SessionRuntime.swift` — the sidebar has only `.onMove`.
- No `Timer` in those files.
- No adopter of `NSSpringLoadingDestination` / `springLoading` anywhere in `BattyKit/Sources` or `Batty/`.
- The only code-driven expansion, `WindowRuntime.hidePane`, fires on hide, not on drag.

### Fix directions (none tried — the implementer must establish which lever actually works)

SwiftUI exposes no modifier for this, so the fix has to reach AppKit. Candidates, roughly least- to most-invasive:

1. **Gate the `DisclosureGroup` binding setter.** Ignore a `true` write while a Sidebar drag session is in flight. The hard part is knowing a drag is in flight: `.onMove` fires only on drop. A local `NSEvent` monitor for `.leftMouseDragged` / `.leftMouseUp` inside the Sidebar, or observing the outline view's `NSTableView` drag-session delegate callbacks, are the obvious detection routes; each has to be checked for whether the auto-expand write actually arrives during an event the monitor can see.
2. **Reach the backing `NSOutlineView` and veto `shouldExpandItem` during a drag.** A zero-size `NSViewRepresentable` placed inside the List (the pattern `WindowIDRegistrar` uses, `BattyKit/Sources/BattyKit/Util/WindowIDRegistrar.swift`) can walk `superview` to the enclosing `NSOutlineView`. Its delegate is SwiftUI's own, so the veto would need a forwarding proxy delegate that answers `outlineView(_:shouldExpandItem:)` with `false` only while `outlineView.draggingSession`-style state says a drag is active. Fragile against SwiftUI internals; the reviewer should weigh that.
3. **Observe `NSOutlineView.itemDidExpandNotification` during a drag and immediately collapse.** Works without touching the delegate but will flicker; probably unacceptable for a polish issue.

### Observation rules apply

Whatever the fix, it either intercepts or suppresses a write to `session.isPaneListExpanded` (an `@Observable` property) that originates from AppKit drag machinery, not from a user click. `docs/swiftui-observation-rules.md` is binding here: the write's origin must be audited (event-origin vs layout/drag-machinery-origin), nothing may synchronously call responder- or constraint-changing AppKit APIs from inside a SwiftUI update, and the fix must not "solve" a mutate-during-update warning by hopping the write into a `Task` (the #0229 class of regression). `WindowIDRegistrar`'s `DispatchQueue.main.async` deferral pattern is the precedent for AppKit side effects from a representable.

### Test coverage today

- **No UI test drags a Session row.** `SidebarTests` (`BattyUITests/SidebarTests.swift`) covers sidebar visibility, Cmd-B collapse/expand, and row selection. `PaneSidebarTests` covers chevron expand/collapse, pane-row click, hide-auto-expands, and the last-visible eye. `DragDropTests` (`BattyUITests/DragDropTests.swift`) covers Pane-swap drags, not Sidebar Session reorder. Session reorder itself (#0011, shipped via `onMove` in #0010) has never had a UI test.
- **Fitting regression coverage:** a `PaneSidebarTests` (or new `SidebarReorderTests`) case that launches with two Sessions, asserts `paneRowCount == 0`, performs `sessionRowA.press(forDuration:thenDragTo: sessionRowB)`-style real drag with a hold over row B (the Mode-B pattern in `DragDropTests.testModeBDragHandleProducesSwap`, `DragDropTests.swift:181`), and asserts `paneRowCount` stays `0` throughout and after the drop while the Session order changed. A companion assertion that `isPaneListExpanded` is still `false` after the drop, via whatever driver intent the implementer adds, would pin the binding-write question above. Unit tests cannot cover this — the behavior lives in `NSOutlineView`.
