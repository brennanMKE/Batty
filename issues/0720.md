## Description

Two `ClipboardConfirmationTests` tests (from #0674, shipped in 1.4.1) failed in the full 1.4.3 release run and passed on a filtered re-run. In both, the clipboard sheet never appeared after a freshly split Pane sent an OSC 52 read:

- `BattyUITests/ClipboardConfirmationTests/testAskDenyIsRememberedForTheSession`: `ClipboardConfirmationTests.swift:72` "XCTAssertTrue failed" (`sheet.waitForExistence(timeout: 10)` after `read1.sh`)
- `BattyUITests/ClipboardConfirmationTests/testAskDialogStaysUpThroughABurst`: `ClipboardConfirmationTests.swift:51` "XCTAssertTrue failed - Ask must show the clipboard dialog"

## Run ids

- Failed: `20261122-161240-36378` (full suite, unfiltered, `release/1.4` at `8dd9af81`).
- Passed on re-run: `20261122-182546-59972` (the two tests above plus #0701's test, `CHECK UI: PASSED (3 tests)`).

The logs of `20261122-161240-36378` were deleted by `scripts/release.sh`'s cleanup (#0721), so the guest's app log for the failure is gone.

## Likely race (hypothesis, not confirmed)

Each test splits a Pane with `batty pane split --command <script>`. The script sends the OSC 52 read (`printf '\033]52;c;?\a'`) as soon as the process starts. The burst test sends three reads 0.2 s apart, and the deny test sends one.

The route that turns the read into the sheet is wired late. `PaneView` sets `tab.terminalDelegate.onClipboardReadConfirmationRequest` inside `.task(id: tab.id)` (`BattyKit/Sources/BattyKit/Views/PaneView.swift`, around line 272), which runs after the new Pane's view appears. Until then, `TerminalDelegateProxy.resolveClipboardConfirmationRoute` (`BattyKit/Sources/BattyKit/Runtime/TerminalDelegateProxy.swift`, around line 273) logs "clipboard confirmation with no route wired — denying" and denies the read silently. If the shell starts and prints before the `.task` runs (more likely under load in a full run), every read is denied and no sheet appears. A single read is lost entirely, and the burst is lost if the wiring takes longer than about 0.4 s.

If this holds, it is also a product bug: a program that reads the clipboard right after its Pane opens is silently denied, even with the Setting on Ask or Always.

## Expected behavior

The tests pass reliably. Either the clipboard route is in place before the Pane's process can emit output (wired where the `TabRuntime` is created, not in a view `.task`), or a read that arrives before wiring is held and routed once the wiring runs. Per `AGENTS.md` "Asynchronous tests", don't fix it by adding waits or a sleep before the printf in the test.

## Plan

### Premise check: the race is confirmed in code (product bug, not just a test bug)

- The surface and PTY start while SwiftUI is still evaluating `body`. `TerminalPlaceholderView.body` calls `TerminalHostStore.shared.terminalView(for:windowID:)` (`BattyKit/Sources/BattyKit/Views/TerminalPlaceholderView.swift:48`). On first request that creates the `AppTerminalView`, sets `view.delegate = tab.terminalDelegate` (`TerminalHostStore.swift:201`) and calls `host.addSubview(view)` (`TerminalHostStore.swift:212`). The host is already in the window, so libghostty starts the surface and the child process right away (doc comment at `TerminalHostStore.swift:174-178`).
- The clipboard route is installed later, in `PaneView`'s `.task(id: tab.id)` (`BattyKit/Sources/BattyKit/Views/PaneView.swift:234`, assignment at `:272`). A `.task` runs as a main-actor Task after the view appears, at least one turn after the `body` that started the PTY.
- Until then `TerminalDelegateProxy.resolveClipboardConfirmationRoute` (`BattyKit/Sources/BattyKit/Runtime/TerminalDelegateProxy.swift:269-279`) finds `onClipboardReadConfirmationRequest == nil`, logs "clipboard confirmation with no route wired — denying" (`:274`) and answers `false`. Nothing records or replays the request.
- `batty pane split --command <script>` runs the script as the Pane's process, and the script's first act is the OSC 52 read. Under a loaded VM the read can reach the delegate before the `.task` runs, so it is denied with no sheet. That matches both failures: one lost read in `testAskDenyIsRememberedForTheSession`, and a 0.4 s burst lost in `testAskDialogStaysUpThroughABurst`.
- Real users hit it too: any program that reads the clipboard as soon as its Pane opens is denied with the Setting on Ask (and also on Allow, since the Setting is checked only inside the route).
- The other delegate signals already handle "fired before the view wired it". Bells are buffered in `TabRuntime` and flushed by `setBellIntake(_:)` (`TabRuntime.swift:540-590`). The pwd is re-read after wiring (`syncWorkingDirectoryFromTerminal()` in the same `.task`). The startup command is armed until the first report (`TerminalDelegateProxy.armStartupCommand`). Only the clipboard route fails closed and drops the request.
- Holding a libghostty request is safe. `TerminalClipboardConfirmationRequest.respond(allow:)` is once-only, its `deinit` denies an unanswered request, and the bridge denies every pending request on surface teardown (`libghostty-spm` `Surface/TerminalSurfaceViewDelegate.swift:85-95`, `InMemory/TerminalCallbackBridge.swift:206-223`). The Ask sheet already holds requests for as long as the user takes.
- Without the guest log of the failing run (#0721 deleted it) the race isn't proven to be the cause of these two failures, but the code permits exactly this failure and nothing else in the path explains a missing sheet. `## Root cause` should say so.

### Approach: hold an unrouted request in the proxy, then route it once the wiring runs

Wiring the route at Tab creation instead was considered and rejected. `TabRuntime` is created at many sites (new Session, split, new Tab, CLI, Project open), several without an `AppStateStore`. `TerminalHostStore` is an app-wide singleton with no store reference. The route also needs `tab.sessionID` and a Window that locates the Tab, and neither is settled at `TabRuntime.init`. A bounded hold in the proxy follows the bell-buffer precedent, keeps the wiring where it is, and closes the race for every creation path.

**Files**

1. `BattyKit/Sources/BattyKit/Runtime/TerminalDelegateProxy.swift`
   - Add `static let maxHeldClipboardRequests = 4`, `private var heldClipboardRequests: [(kind: TerminalClipboardRequestKind, respond: (Bool) -> Void)] = []` and `private var clipboardRoutingClosed = false`. Expose the held count read-only for tests: `var heldClipboardRequestCount: Int { heldClipboardRequests.count }`.
   - `resolveClipboardConfirmationRoute(kind:respond:)`:
     - With a route, forward as today.
     - If `clipboardRoutingClosed`, deny right away.
     - If the hold is full (`count >= maxHeldClipboardRequests`), deny right away and log a warning with the reason (the cap).
     - Otherwise append to the hold and log `notice` "clipboard confirmation held until route wired" with `tabID`.
     - Remove the old "no route wired — denying" path.
   - `onClipboardReadConfirmationRequest` gets a `didSet`. When the new value is non-nil and requests are held, swap the array out first (so a handler that re-enters can't run into a half-drained array), then forward each request in arrival order through the new handler. Setting it to `nil` drains nothing.
   - Add `func denyHeldClipboardRequests()`: set `clipboardRoutingClosed = true`, swap the array out, call each `respond(false)`. It's idempotent.
   - Update the doc comments on `onClipboardReadConfirmationRequest` (lines 66-72) and `resolveClipboardConfirmationRoute` (lines 260-268). The fail-closed guarantee is now: never allows without a route; holds at most N; denies on release or overflow; never hangs, because release, overflow and the upstream deinit backstop each answer the request. Grep every claim made in those comments.
   - The cap bounds memory and how many prompts a program can queue before the view mounts. With N = 4, the 3-read burst is held in full. There is no time deadline: the `.task` runs whenever the placeholder that created the surface appears, and a Tab that never appears is released or deallocated, which answers the request. Say this in the doc comment rather than adding a clock.

2. `BattyKit/Sources/BattyKit/Runtime/AppStateStore+Clipboard.swift`
   - Add `public func wireClipboardConfirmation(for tab: TabRuntime)`, which moves the closure now inlined in `PaneView.swift:272-285` here unchanged (`[weak self, weak tab]`, resolve the Session through `tab.sessionID`, then `routeClipboardConfirmation(to:kind:readPolicy:context:decide:)`). This mirrors `wireBellReporting(for:)` and `wireWorkingDirectoryReporting(for:)`: unit tests exercise the production closure directly (the #0436 rationale in the doc comment at `AppStateStore.swift:2700-2715`).

3. `BattyKit/Sources/BattyKit/Views/PaneView.swift` (`.task(id: tab.id)`, around line 263-285)
   - Replace the inline closure with `appStore?.wireClipboardConfirmation(for: tab)`. When `appStore` is nil (previews and tests only), keep today's behaviour by installing a deny-all route: `tab.terminalDelegate.onClipboardReadConfirmationRequest = { _, decide in decide(false) }`. Without a route those requests would be held until release instead.
   - Trim the existing comment to the *why* (route through the Setting, then the Session; held requests are routed when this runs).
   - Observation rules: draining held requests can write `SessionRuntime.pendingClipboardConfirmation` (observed). That write happens inside the existing `.task` body, a main-actor Task outside any view update (not `body`, `onChange`, `onAppear` or geometry), the same context in which `wireBellReporting` already flushes buffered bells into the observed Bell Feed. No new `Task` hop is added. Don't move this wiring into `onAppear` or `body`.

4. `BattyKit/Sources/BattyKit/Runtime/TerminalHostStore.swift` (`releaseTerminalView(forTabID:)`, line 342)
   - After `let tab = tabRuntimes.removeValue(forKey: id)?.runtime` (`:355`) and before `view.controller = nil` (`:357`), call `tab?.terminalDelegate.denyHeldClipboardRequests()`. A request is answered before its surface is freed, and a request that arrives during teardown is denied. The early-return path (no view registered) needs nothing: without a view there's no surface, so nothing can be held.

No change to `SessionRuntime.requestClipboardReadConfirmation`. Several held requests drained at once behave like a live burst: the first shows the sheet, and later reads while it's up are denied as `.coalesced`, as today.

## Root cause

Test setup. libghostty asks Batty to confirm a clipboard read only when the general pasteboard holds text: with it empty, `TerminalController+Callbacks.swift:184-199` (libghostty-spm) answers `GHOSTTY_CLIPBOARD_READ_UNAVAILABLE` before calling `confirmReadClipboard`, so no sheet can appear. `ClipboardConfirmationTests` never seeded the pasteboard, so they depended on what happened to be there: the host's clipboard, which Tart mirrored into the guest (`tart run` without `--no-clipboard`), or text left by an earlier test that ran `pbcopy`. In a full run that ordering varies, which is why the tests looked flaky; on an idle guest with an empty host clipboard they failed every time.

Evidence: runs `20261122-194034-12106` (fix) and `20261122-195311-139` (baseline `main`) failed, and their `guest-state/app-info.log` has no `clipboard kind=` lines at all: the delegate was never called, and `testDefaultNeverShowsNoClipboardDialog` passed vacuously. Run `20261122-200208-69011` (this branch at `2e61e810`, `AuxiliaryWindowShortcutTests/testSettingsKeyPasteDoesNotReachTheTerminal`, which runs `pbcopy`, then the two Ask tests) passed, `CHECK UI: PASSED (3 tests)`, with `reason=dialog`, `remembered`, `coalesced` x2 and `allowed=true reason=dialog` in the log.

Separately, the early-request race in the plan is real in code: the surface and child process start while `TerminalPlaceholderView.body` is evaluated, but `PaneView` wired the clipboard route later in `.task(id: tab.id)`, and a request arriving in between was denied silently. It is kept fixed below. No VM log so far shows it happening ("held until route wired" appears in none of the runs).

## Fix

- `BattyUITests/ClipboardConfirmationTests`: `seedPasteboard()` puts known text on `NSPasteboard.general` before each split that sends an OSC 52 read, in all three tests, so every read reaches Batty's delegate.
- `tools/vm-lib.zsh` `vm_boot`: `tart run ... --no-clipboard`, so the host clipboard is never copied into a test VM (privacy) and results don't depend on it. Both runners (`run-ui-tests-vm.sh`, `run-sparkle-update-vm.sh`) boot through `vm_boot`; neither uses the host clipboard. `docs/ui-testing-vm.md` notes the flag.
- Product race: `TerminalDelegateProxy` holds an unrouted request (cap `maxHeldClipboardRequests = 4`) and forwards it in arrival order when `onClipboardReadConfirmationRequest` is set (`didSet`). `denyHeldClipboardRequests()` denies the hold and closes it; overflow is denied at once. `AppStateStore.wireClipboardConfirmation(for:)` is the production route closure, moved out of `PaneView` unchanged; `PaneView` calls it, or installs a deny-all route when there's no store. `TerminalHostStore.releaseTerminalView(forTabID:)` denies held requests before freeing the surface.

## Review notes

Resolved (review round 1, 2026-11-22).

- Product fix (`e24c4705`): every libghostty request is answered exactly once on every path. Wired: forwarded straight to the route. Held then wired: `didSet` swaps the hold out and forwards in arrival order; a re-wire finds it empty, so nothing replays. Overflow (cap 4): denied at once. Release: `releaseTerminalView` calls `denyHeldClipboardRequests()` before `view.controller = nil`, and the closed flag denies later arrivals. Proxy deinit: the held closures capture the `TerminalClipboardConfirmationRequest`, whose `deinit` denies an unanswered request (`Surface/TerminalSurfaceViewDelegate.swift:91-95`), and `respond(allow:)` is once-only (`:85-89`), so no leak and no double answer. Nothing resets the route to `nil` anywhere in Sources.
- Observation rules: the drain can write `SessionRuntime.pendingClipboardConfirmation`, but only from `PaneView`'s existing `.task(id: tab.id)`, the same context as before; no new `Task` hop, nothing in `body`/`onChange`/`onAppear`.
- Tests are non-vacuous: each held-request test asserts no decision before wiring, which the old immediate-deny code fails. No sleeps or waits. `releasingTheTerminalViewDeniesHeldRequests` uses `TerminalHostStore.shared` rather than the fresh store the plan suggested; acceptable, it releases what it creates.
