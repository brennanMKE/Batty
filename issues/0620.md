## Description

**HIGH: it blocks review runs. Related to #0601, #0605, #0606 and #0607.** The `LayoutConvergenceProbe` tests on `main` (`b663a656` / `0cef9562`) fail intermittently when the host is busy (load average about 20–30) and pass when run alone. Two parts of the probe's verdicts cause this:
- A settle that needs one more main-queue round than `convergedRoundBound` counts as "did not converge", even when every view is clean at the end.
- The request-volume tests fail if a single tick or switch goes over the ceiling, because they compare the ceiling with `max()`.

Every reviewer runs the full `./build.sh unit`, so one of these flakes can bounce a correct change, or send the reviewer to re-run suites until they pass. That makes a probe failure meaningless as a signal.

Goal: make the probe tests deterministic. A probe failure should mean a real layout loop or a real rise in request volume, never a slow host. Each test must still fail on the code it was written to catch.

## Observed failures (2026-11-13, `.claude/worktrees/main-check`, host load ~20–30)

1. Full `./build.sh unit`: `SessionDetailLayoutConvergenceTests/sessionSwitchUpdateConstraintRequestsStayUnderCeiling(extraSessions:)` failed at the `#expect(switched.converged, ...)` on line 231:
   `rounds=4 rootPasses=8 windowUpdateConstraints=19 posts=658 layoutPosts=7 brokeLoop=false dirty=[]`
   No view was dirty when the settle ended. `rounds=4` is one over `convergedRoundBound` (3) and far under `maxRounds` (12). The 658 posts are under the 770 ceiling for `extraSessions: 12`.
2. Filtered re-run of the suite: it passed once. On the next run, `dividerDragTickRequestsStayUnderCeiling(extraSessions:)` failed at line 282 with `perTick=[25, 35, 25, 25, 25, 25] ceiling=30`. Five ticks were exactly at the calibrated 25 and one spiked to 35.
3. Earlier the same day: `StatusPaneLayoutConvergenceTests/systemMetricsPaneConverges` failed once in a loaded suite run and passed alone.
4. #0606 (resolved on `issue/0606`, not yet on `main`) saw occasional single-tick spikes of 36–160 requests, in at most 3 of 12 ticks, in suite runs. Its review accepted a majority-of-ticks rule (`over.count * 2 < ticks.count`) for the new System Metrics tick test and recorded the spikes as unexplained in its Gotchas.

## Where the verdicts come from (`main`)

`BattyKit/Tests/BattyKitTests/LayoutConvergenceProbe.swift`:
- Lines 156–158: `SettleResult.converged` is `rounds <= LayoutConvergenceProbe.convergedRoundBound && !brokeLoop`.
- Lines 168–170: `maxRounds = 12` is documented as a hang guard. `convergedRoundBound = 3` is documented as "Every converging settle in calibration took one round".
- Lines 234–245: `settle()` runs `window.layoutIfNeeded()` and then one `mainTurn()` (one `DispatchQueue.main.async` hop, lines 226–230) per round. It returns `rounds: round` at the first round where `dirtyViews()` is empty, and `maxRounds + 1` if that round never comes.

  So a settle that ends clean at round 4 and a settle still dirty at round 13 both report `converged == false`. Nothing in the result tells them apart except `rounds` and `dirtyViews`. Under load, deferred main-queue work lands in later turns of the same settle and adds rounds without any loop. Examples are the selection's deferred focus promotion, which the comment at lines 310–316 of `SessionDetailLayoutConvergenceTests.swift` describes, and libghostty's `terminalRunOnMainNextTurn` publishes. The faster turns of an idle host hide this.
- Lines 16–25: an unbounded loop in Batty's own trees trips AppKit's own "more passes than views" cap, which raises `NSGenericException` and ends the test process. The controls use `postBreakerLimit` and `brokeLoop` instead. So the round bound is not the only thing that detects a real loop for Batty's trees.

`BattyKit/Tests/BattyKitTests/SessionDetailLayoutConvergenceTests.swift`:
- Line 188 sets `switchRequestCeiling = [0: 520, 12: 770]`. Line 243 asserts `perSwitch.max() <= ceiling`.
- Line 257 sets `dividerTickRequestCeiling = [0: 30, 12: 42]`. Line 282 asserts `perTick.max() <= ceiling`. The doc comment (lines 248–256) records 57 / 105 per tick before #0607 and 25 / 36 after.
- `converged` is also asserted per settle at lines 160, 167, 171, 224, 231, 267 and 278. The controls at lines 96–151 assert both `converged` and `!converged`.

`BattyKit/Tests/BattyKitTests/StatusPaneLayoutConvergenceTests.swift`:
- `sweep` (lines 220–252) asserts `settled.converged` and `ticked.converged` for every size, scroller style and tick, at lines 242 and 247. `statusPanesConvergeInTheSessionDetailTree` does the same at lines 386 and 393. A single slow settle anywhere in these sweeps fails the test.

## Expected behavior

- A probe test passes on a loaded host whenever the code under test converges and stays within its request budget. The same run under `./build.sh unit` gives the same verdict at load 1 and at load 30.
- `converged` (or whatever replaces it) separates the two cases:
  - **Settled late:** the settle ended with no dirty view, needed more rounds than calibration, and the breaker didn't trip. This is a load artefact. At most it is diagnostic output, not a failure.
  - **Did not converge:** views were still dirty at `maxRounds`, or `brokeLoop` is true. This is a real loop and must fail.

  One possible approach: make "clean at the end and no breaker" the convergence condition, and keep `rounds` in the description. Another is to count only rounds that did layout work, for example `rootPasses` or posts per round, not idle turns. The plan should choose one and justify it against the controls.
- The per-tick and per-switch ceilings use a statistic that a single spike can't move, such as a strict majority under the ceiling (the rule #0606's review accepted) or the median. The plan must show that the chosen statistic still fails the pre-fix code by a wide margin.
- Each probe test keeps its fail-before evidence. Re-check and record in `## Verification`, by a hand-run revert as the original issues did:
  - #0601: `probeDetectsAConstraintFeedbackLoop`, `probeDetectsTheLoopInTheSplitTier` and the System Metrics sweep still fail on the loop they were built against. See #0601's Verification for the revert recipe.
  - #0605: the `...DoesNotChangeFirstResponderDuringLayout` tests and `terminalPlacementWriteMarksNoViewAsNeedingUpdateConstraints`. These don't use `converged` for their verdict, but confirm that a looser `converged` doesn't change them.
  - #0606: the System Metrics tick test, once `issue/0606` is merged. Its old code failed 12 of 12 ticks at 348+ requests.
  - #0607: `dividerDragTickRequestsStayUnderCeiling`. Every tick of the pre-fix code was at 57 / 105, so a majority or median rule against 30 / 42 still fails it.
- No sleeps, no wall-clock assertions, and no "retry until green" (`AGENTS.md`, "Asynchronous tests"). The hang guards stay hang guards.

## Actual behavior

See "Observed failures". A clean settle that took 4 rounds, or one tick at 35 among five at 25, fails the run.

## Steps to reproduce

1. On `main`, put the host under load, for example with a concurrent `./build.sh` in another worktree or a VM UI run. A load average of about 20–30 reproduced it.
2. Run `./build.sh unit SessionDetailLayoutConvergenceTests` several times, or a full `./build.sh unit`.
3. Some runs fail as in "Observed failures". Run the same filter on an idle host and it passes.

## Notes

- **The failure text says it is load, not a loop.** `dirty=[]` together with `brokeLoop=false` and `rounds` well under `maxRounds` describes a settle that finished. A real loop on Batty's trees either crashes the run through AppKit's cap or reports `rounds=13` with dirty views.
- **Don't fix this by raising `convergedRoundBound` or the ceilings alone.** A higher number only moves where a busier host fails. The verdict has to stop depending on how many idle main-queue turns the settle needed.
- The tick and switch spikes (35 here, 36–160 in #0606) are unexplained. If the plan finds their source, for example a deferred focus promotion or a libghostty publish landing inside one tick's settle, removing that cross-tick bleed from the measurement is better than only tolerating it. A settle that also drains already-scheduled deferred work before counting starts is one way to do that.
- `sessionCountMargin` (#0619, on its branch) and any later probe test should use the same rule.

### Related load flake (separate root cause, tracked by #0516)

`ProcessFollowByNameTests` also fails intermittently under the same load and passes alone. It drives real child processes (`ChildProcessFixture`, copies of `/bin/sleep`) and the host's real process table. Seen recently:
- `aSeededFollowOfTheSecondRealProcessShowsThatProcess()` (`ProcessFollowByNameTests.swift:581`)
- `theRealEnumeratorFindsAUniquelyNamedProcessAndItsReplacement()` (`ProcessFollowByNameTests.swift:723`)

Both resolve a running child through `ProcessInspector`'s live process-table walk. That is the path #0516 (open) shows can return a truncated pid list on a busy host. #0565 and #0569 fixed the same symptom in `theRealEnumeratorPrefersTheLongestRunningProcessOfAName`. This flake is not a probe problem, so it is out of scope here. Track it under #0516, or file a new issue with the failure text if #0516's fix doesn't cover these two tests.
