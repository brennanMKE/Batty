## Description

`BattyKit/Sources/BattyKit/` is a flat heap of 46 `.swift` files at the root, plus three existing subdirectories (`ProjectName/`, `Resources/`, `Shortcuts/`). New files keep landing at the root because there's no convention to follow, and the directory listing is now long enough that finding a related file requires Cmd-F instead of scanning. Files that obviously belong together — `SessionDetailView.swift` / `SessionRuntime.swift` / `SessionSidebarView.swift` / `SessionNameCache.swift`, for example — are spread across the same flat listing as unrelated work.

Goal: group source files into folders by concern so the package layout reflects the Concepts in `Concepts.md` and the module conventions in `issues/Issues.md`. New code lands in the right folder by default; existing code is one `git mv` away from where it should live.

## Acceptance criteria

- `BattyKit/Sources/BattyKit/` has fewer than ~8 entries at the root after the move (the umbrella `BattyKit.swift`, the existing `Resources/`, and a small number of new subdirectories).
- Every Swift file is grouped with the others that share its concern. The grouping is documented in a short `docs/source-layout.md` (or a section in an existing doc) so the next contributor knows where to put new files.
- `xcodebuild -scheme Batty -destination 'platform=macOS' build` passes after the move. `xcrun swift test --package-path BattyKit` also passes.
- All commits move files via `git mv` (preserving history) — not delete + re-add. One commit per group is fine; one mega-commit also fine.
- No source code edits in this issue beyond what's strictly required by the move (e.g. nothing should need to change because SPM doesn't care about subdirectory paths for non-resource targets — but if a `#file`-sensitive test or a `Bundle.module` lookup breaks, fix it).

## Out of scope

- Changing what any file does. This is a pure structural refactor.
- Splitting large files into smaller ones. If `PaneView.swift` is 600 lines, it stays 600 lines.
- Renaming files. `SessionDetailView.swift` stays `SessionDetailView.swift`; only its parent directory changes.
- Reorganizing the `Batty/` app target. It's a `PBXFileSystemSynchronizedRootGroup` (per `CLAUDE.md`) and structurally simpler — handle in a separate issue if/when it becomes a problem.
- Touching the `BattyKitTests/` layout — a follow-up issue if tests also become a tangle.

## Notes

- `Package.swift` uses Swift's default `Sources/<TargetName>/` convention with no explicit `path:`. Adding subdirectories under `BattyKit/Sources/BattyKit/` "just works" — SPM treats every Swift file under that root as part of the target regardless of depth. Verified the `resources: [.process("Resources")]` declaration only governs the `Resources/` folder; arbitrary new sibling folders are fine.
- Three folders already exist at the root: `ProjectName/`, `Resources/`, `Shortcuts/`. Leave them alone — they're already organized and renaming `Shortcuts/` to fit a new convention would create unnecessary churn.
- Use `git mv` for every move so blame / log history follows the file. Reviewer can use `git log --follow` to confirm.
- After the move, scan for any `Bundle.module.url(forResource:)` calls that reference paths relative to the source tree. SPM bundles resources at the `Resources/` root, not by source path, so most code should be unaffected — but a `#file`-based path in a test or debug helper could surprise.
- Worth a brief mention in `docs/view-hierarchy.md` (or the new `docs/source-layout.md`) so future Claude sessions and contributors don't fight the convention.

## Root cause

The 45 files at the root of `BattyKit/Sources/BattyKit/` grew there organically because no convention existed. SPM doesn't require subdirectory structure, so new code defaulted to the package root, and each new file made the listing harder to scan — exacerbating the problem for the next contributor.

## Fix

Moved all 45 root-level Swift files into eight PascalCase concern folders using `git mv` (history-preserving). The package root now holds only `BattyKit.swift` plus four directories (`Resources/`, `ProjectName/`, `Shortcuts/` from before, and the eight new concern folders).

Final layout under `BattyKit/Sources/BattyKit/`:

| Folder | Count | Notes |
|---|---|---|
| `Views/` | 14 | SwiftUI views and view-level UI surfaces |
| `Runtime/` | 10 | Long-lived stores, runtimes, registries |
| `Model/` | 5 | Pure value types (Codable/Sendable) |
| `Commands/` | 6 | Menu commands, shortcuts, focus plumbing |
| `Theme/` | 2 | Theme model + preference |
| `Settings/` | 1 | Settings preferences type |
| `Updater/` | 1 | Sparkle updater controller |
| `Util/` | 6 | Cross-cutting helpers |
| (root) | `BattyKit.swift` + `Resources/`, `ProjectName/`, `Shortcuts/` (unchanged) |

The grouping matches the proposed table in the issue exactly — no deviations were needed.

`Package.swift` did not need any change: `resources: [.process("Resources")]` only governs the `Resources/` folder, and SPM picks up Swift files at any depth under the target root.

Documented the convention in `docs/source-layout.md` (linked from `docs/README.md`) so the next contributor knows where new files belong.
