# 0509 — HID thermal reader deduplicates sensor services before reading them, so it can report a failed or cooler reading

| | |
|---|---|
| **Status** | open |
| **Module** | System Metrics pane / Thermal |
| **Platform** | macOS |
| **First seen** | 2026-10-14 |

## Description

`HIDThermalReader.readAll(session:)` builds its cached sensor list with `seen.insert(name).inserted`, keeping only the **first** service for each `Product` name. Every later tick queries only those. This throws away exactly the redundancy `CPUTemperatureAggregation.aggregate` was written to exploit — its own doc comment says "The HID service list repeats each name (three services per name on an M4 Pro), so readings are folded by name before counting," and it deliberately takes the max of the *plausible* readings.

With the dedup in front of it, aggregation never sees the duplicates. If the retained service returns no event, that sensor name silently contributes nothing for the life of the session. If it returns an implausible value (the `isPlausible` guard exists because "one `PMU tdev2` service on an M4 Pro reports -9201.14"), the name is dropped even though a sibling service would have answered. And where duplicates simply differ, the reported CPU temperature is whichever service happened to be enumerated first, not the hottest.

Found by an external review of `ad239f9e..v1.2.0` — review id `20261014T193909Z-Batty-883c427`, finding 1 of 2 (medium, correctness, confidence high).

## Steps to reproduce

Hardware-dependent: needs a Mac where the first-enumerated service for a `PMU tdie*` name is the one that fails or reports an implausible value. Not reproducible on demand; the defect is structural.

## Expected behavior

Every CPU-die service is read each tick and all readings go to `aggregate`, which already folds by name and takes the hottest plausible one.

## Actual behavior

`BattyKit/Sources/BattyKit/Runtime/HIDThermalReader.swift:82-88` discards duplicate services at session-build time.

## Notes

- Fix: drop the `seen` set and keep every service passing `isCPUDieSensor`. The aggregation layer is already duplicate-tolerant, and `sensorCount` is computed from distinct names, so the displayed detail string does not change.
- Cost: roughly 3× the `copyEvent` calls per tick on an M4 Pro. These are IOKit property reads on a cached service list at the pane's sample cadence, not per-frame work.
- `CPUTemperatureAggregationTests` already covers "invalid duplicate followed by a valid one"; the gap was that the reader never let that case reach it.
