# 0630 — Projects… opens straight into the first Project's editor instead of a Projects list to browse, and the window has no ⌘N for New Project

| | |
|---|---|
| **Status** | open |
| **Module** | Projects |
| **Platform** | macOS |
| **First seen** | 2026-11-14 |
| **Priority** | high |
| **Target** | 1.4.0 |

## Description

**Projects ▸ Projects…** should open the Projects window in a browse state: every Project listed, nothing selected, a prominent New Project action, and selecting a Project opens its editor. Today the window never has a browse state. It opens on the first Project's full editor, or on whatever draft the window last held, so it reads as "the editor for one Project", and the user reaches it by way of New Project. User report, verbatim, on Beta 6134dd26 after #0629:

> "I do not have a way to just go into projects to edit them. I have to select New Project and go to another projects. There should be a way to just open Projects and from there I can create a new one."

## Current behavior (verified against 6134dd26)

- **Menu item.** `Projects ▸ Projects…` calls `ProjectEditorWindowController.shared.show(store: store)` with no selection, no draft and `startNewProject: false` (`BattyKit/Sources/BattyKit/Commands/BattyCommands.swift:190-194`). It has no keyboard shortcut.
- **#0629 changed no behavior here.** It moved the item from File to the new Projects menu and renamed it from **Edit Projects…**. The old item made the same `show(store: store)` call (`git show 6134dd26 -- BattyKit/Sources/BattyKit/Commands/BattyCommands.swift`). The only `ProjectEditorViewModel.swift` change in that commit was three localization comments.
- **First open, one or more Projects.** `prepare` builds a `ProjectEditorViewModel` with `initialSelection: nil` (`ProjectEditorWindowController.swift:48-50`). The model's init then loads `store.projects.first` (`Model/ProjectEditorViewModel.swift:183`, `initialSelection.flatMap { store.project(id: $0) } ?? store.projects.first`). The window opens with the first Project selected and its full editor showing in the main area (`Views/ProjectEditorView.swift:140-141`). It does not land on a new-Project draft. There is no state with Projects listed and none selected.
- **First open, zero Projects.** No draft is loaded, so the main area shows `ProjectEditorEmptyState`: "No Projects yet", a sentence of explanation, and a **New Project…** button (`ProjectEditorView.swift:142-143`, `212-242`). This state already meets the requirement.
- **A list exists.** The window is an `HStack` of a 220 pt `ProjectListColumn` and the editor (`ProjectEditorView.swift:136-145`). The column lists every Project from `model.listEntries` (`ProjectEditorView.swift:246-295`, `ProjectEditorViewModel.swift:213-232`), plus an "Untitled" row for an unsaved new draft. A row click calls `requestSelect` (`ProjectEditorView.swift:258-261`). Its context menu has Move Up, Move Down and Delete…. A **New Project…** button sits at the bottom of the column (`ProjectEditorView.swift:283-291`).
- **Reopening an open window does not reset it.** When the window already exists, `prepare` with no selection and no draft returns without navigating (`ProjectEditorWindowController.swift:38-46`). **Projects…** then brings the window forward still showing whatever it last held, such as an Untitled new-Project draft started from Open Project ▸ New Project….
- **Where New Project lives.** It appears in three places, and all three open the window on a new draft with `startNewProject: true`. They are the **Open Project ▸ New Project…** submenu item (`BattyCommands.swift:137-140`), the Open Project picker's New Project action (`Views/SessionDetailView.swift:360-361`), and the editor's own buttons (list column and empty state). The two outside the window need a content window: Open Project ▸ is disabled with no key content window (`BattyCommands.swift:182`).
- **⌘N in the window.** ⌘N is **File ▸ New Session** (`BattyCommands.swift:156-161`, `ShortcutAction.newSession`, user-rebindable). With the Project Editor key, `actionWindow` is nil (`BattyCommands.swift:61-71`), so ⌘N does nothing. The window has no shortcut for New Project.
- **Dirty-draft guard.** Every move away from the current draft (select, new Project, handed-in draft, close, quit) goes through `requestNavigation`. When the draft `isDirty`, it asks "Save changes to this Project?" with Save, Discard Changes and Cancel (`ProjectEditorViewModel.swift:545-555`, `596-640`; `ProjectEditorView.swift:147-159`).

So a user can already reach an existing Project's editor by choosing **Projects ▸ Projects…** and clicking it in the left column. But the window opens on a full editor for an arbitrary Project, or on a stale Untitled draft, never on a list. Nothing tells the user it is a browser. That is how the report reads it.

## Expected behavior

1. **Projects ▸ Projects…** opens the Projects window in a **browse state**:
   - the list shows every Project, with none selected;
   - the main area shows a browse placeholder, such as "Select a Project to edit it", with a **New Project…** button;
   - no Session, Open Project picker or other step is needed first.
2. Selecting a Project in the list opens its editor, as a row click does today.
3. The window offers **New Project** as a button (the list column's button and the placeholder's) and as **⌘N while the Projects window is key**. ⌘N must not create a Session or fall through to New Session while the editor is key. Outside the editor, ⌘N keeps its current binding.
4. With zero Projects, the window shows the empty state with **New Project…**, as today.
5. If the window is already open, **Projects…** brings it forward. It must not throw away a dirty draft without asking. Reopening on a clean draft may return to the browse state; the plan decides and states which.
6. The dirty-draft guard is kept. ⌘N, New Project, row selection, and any move back to the browse state all go through `requestNavigation` and ask first when the draft is dirty.
7. The other entry points keep their behavior: `selecting:` (Edit from the Open Project picker), `newDraft:` (Save Session as Project) and `startNewProject:` (Open Project ▸ New Project…) still land on that Project or draft.

## Notes

- The auto-selection lives in the model's init (`ProjectEditorViewModel.swift:183`). Unit tests that build the model with no `initialSelection` may rely on it. Check `BattyKit/Tests/BattyKitTests/ProjectEditorTests.swift` and `ProjectEditorQuitTests.swift` before changing it. Separating "no selection" (browse) from "load failed" (`unreadableFilePath`) in the empty-state view is part of the work.
- Deleting the selected Project currently selects a neighbour (`ProjectEditorTests.deletingTheSelectedProjectNeedsConfirmationAndSelectsANeighbour`). Decide whether that stays or the window returns to browse.
- UI tests that open the editor through Projects… and expect the first Project already loaded will need updating: `BattyUITests/ProjectsEditorTests.swift`, `ProjectsEditorQuitTests.swift`, `ProjectsOpenTests.swift`, `ProjectsSharingTests.swift` and `ProjectsStartupTests.swift`, all touched by #0629.
- Help text: `BattyKit/Sources/BattyKit/Help/10-projects.md` says "**Projects ▸ Projects…** opens the Project Editor to change, reorder, or delete the Projects you have." Update it to cover the browse state and ⌘N.
- Related: #0629 (Projects menu), #0476 (Save as Project hands in a draft).
