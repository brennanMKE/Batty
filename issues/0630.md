## Description

**Projects ▸ Projects…** should open the Projects window in a browse state: every Project listed, nothing selected, a prominent New Project action, and selecting a Project opens its editor. Today the window never has a browse state. It opens on the first Project's full editor, or on whatever draft the window last held, so it reads as "the editor for one Project", and the user reaches it by way of New Project. User report, verbatim, on Beta 6134dd26 after #0629:

> "I do not have a way to just go into projects to edit them. I have to select New Project and go to another projects. There should be a way to just open Projects and from there I can create a new one."

## Current behavior (verified against 6134dd26)

- **Menu item.** `Projects ▸ Projects…` calls `ProjectEditorWindowController.shared.show(store: store)` with no selection, no draft and `startNewProject: false` (`BattyKit/Sources/BattyKit/Commands/BattyCommands.swift:190-194`). It has no keyboard shortcut.
- **#0629 changed no behavior here.** It moved the item from File to the new Projects menu and renamed it from **Edit Projects…**. The old item made the same `show(store: store)` call (`git show 6134dd26 -- BattyKit/Sources/BattyKit/Commands/BattyCommands.swift`). The only `ProjectEditorViewModel.swift` change in that commit was three localization comments.
- **First open, one or more Projects.** `prepare` builds a `ProjectEditorViewModel` with `initialSelection: nil` (`ProjectEditorWindowController.swift:48-50`). The model's init then loads `store.projects.first` (`Model/ProjectEditorViewModel.swift:183`, `initialSelection.flatMap { store.project(id: $0) } ?? store.projects.first`). The window opens with the first Project selected and its full editor showing in the main area (`Views/ProjectEditorView.swift:140-141`). It does not land on a new-Project draft. There is no state with Projects listed and none selected.
- **First open, zero Projects.** No draft is loaded, so the main area shows `ProjectEditorEmptyState`: "No Projects yet", a sentence of explanation, and a **New Project…** button (`ProjectEditorView.swift:142-143`, `212-242`). This state already meets the requirement.
- **A list exists.** The window is an `HStack` of a 220 pt `ProjectListColumn` and the editor (`ProjectEditorView.swift:136-145`). The column lists every Project from `model.listEntries` (`ProjectEditorView.swift:246-295`, `ProjectEditorViewModel.swift:213-232`), plus an "Untitled" row for an unsaved new draft. A row click calls `requestSelect` (`ProjectEditorView.swift:258-261`). Its context menu has Move Up, Move Down and Delete…. A **New Project…** button sits at the bottom of the column (`ProjectEditorView.swift:283-291`).
- **Reopening an open window does not reset it.** When the window already exists, `prepare` with no selection and no draft returns without navigating (`ProjectEditorWindowController.swift:38-46`). **Projects…** then brings the window forward still showing whatever it last held, such as an Untitled new-Project draft started from Open Project ▸ New Project….
- **Where New Project lives.** It appears in three places, and all three open the window on a new draft with `startNewProject: true`. They are the **Open Project ▸ New Project…** submenu item (`BattyCommands.swift:137-140`), the Open Project picker's New Project action (`Views/SessionDetailView.swift:360-361`), and the editor's own buttons (list column and empty state). The two outside the window need a content window: Open Project ▸ is disabled with no key content window (`BattyCommands.swift:182`).
- **⌘N in the window.** ⌘N is **File ▸ New Session** (`BattyCommands.swift:156-161`, `ShortcutAction.newSession`, user-rebindable). With the Project Editor key, `actionWindow` is nil (`BattyCommands.swift:61-71`), so ⌘N does nothing. The window has no shortcut for New Project.
- **Dirty-draft guard.** Every move away from the current draft (select, new Project, handed-in draft, close, quit) goes through `requestNavigation`. When the draft `isDirty`, it asks "Save changes to this Project?" with Save, Discard Changes and Cancel (`ProjectEditorViewModel.swift:545-555`, `596-640`; `ProjectEditorView.swift:147-159`).

So a user can already reach an existing Project's editor by choosing **Projects ▸ Projects…** and clicking it in the left column. But the window opens on a full editor for an arbitrary Project, or on a stale Untitled draft, never on a list. Nothing tells the user it is a browser. That is how the report reads it.

## Expected behavior

1. **Projects ▸ Projects…** opens the Projects window in a **browse state**:
   - the list shows every Project, with none selected;
   - the main area shows a browse placeholder, such as "Select a Project to edit it", with a **New Project…** button;
   - no Session, Open Project picker or other step is needed first.
2. Selecting a Project in the list opens its editor, as a row click does today.
3. The window offers **New Project** as a button (the list column's button and the placeholder's) and as **⌘N while the Projects window is key**. ⌘N must not create a Session or fall through to New Session while the editor is key. Outside the editor, ⌘N keeps its current binding.
4. With zero Projects, the window shows the empty state with **New Project…**, as today.
5. If the window is already open, **Projects…** brings it forward. It must not throw away a dirty draft without asking. Reopening on a clean draft may return to the browse state; the plan decides and states which.
6. The dirty-draft guard is kept. ⌘N, New Project, row selection, and any move back to the browse state all go through `requestNavigation` and ask first when the draft is dirty.
7. The other entry points keep their behavior: `selecting:` (Edit from the Open Project picker), `newDraft:` (Save Session as Project) and `startNewProject:` (Open Project ▸ New Project…) still land on that Project or draft.

## Plan

### Why the list did not read as a way in

Nothing hides the list. `ProjectListColumn` is always present at 220 pt with a "PROJECTS" caption, sidebar-style rows and a New Project… button (`ProjectEditorView.swift:136-145`, `246-295`). The window still reads as "one Project's editor" because the model's init loads `store.projects.first` (`ProjectEditorViewModel.swift:183`), so a ~900 pt editor fills the window on every fresh open, and a reopen of a live window shows whatever draft it last held, often an Untitled draft from Open Project ▸ New Project…. The column looks like that editor's sidebar, not a browser. The fix is the browse state. The column's layout and width stay as they are.

### Decisions

- **Fresh open** (window closed) with no `selecting:`/`newDraft:`/`startNewProject:` gives the browse state: `draft == nil`, no list selection.
- **Window already open:** Projects… only brings it forward. It keeps the current draft, clean or dirty, so nothing is lost and no guard is needed. `prepare` already returns without navigating when no selection or draft is passed (`ProjectEditorWindowController.swift:38-46`), so this needs no change.
- **Deleting the selected saved Project** keeps selecting a neighbour, as today. The existing test stays unchanged.
- **Discarding an unsaved new draft** (deleting its Untitled row, `discardNewDraft`) returns to the browse state instead of loading `store.projects.last`. Today it lands on an arbitrary Project. The zero-Projects case is unchanged (`draft = nil`).
- **⌘N** is the File ▸ New Session menu item's chord, which the user can rebind (`ShortcutAction.newSession`). It is routed by that one menu action, never by a second `.keyboardShortcut` inside the editor window, so there is exactly one handler. While the editor (or a sheet over it) is key it starts a New Project. Everywhere else it behaves as today.

## Resolution

Projects… now opens a fresh Projects window with nothing selected: the list on the left and a "Select a Project to edit it" placeholder with a **New Project…** button (`project-editor.browse`). Clicking a row loads that Project. If the window is already open, Projects… just brings it forward and keeps the current draft. Deleting an unsaved Untitled draft now goes back to the browse state, not to the last Project.

The File ▸ New Session chord (⌘N by default) now goes through `AppStateStore.newItemRoute()`. While the Project Editor or a sheet over it is key, it starts a New Project (`ProjectEditorWindowController.newProjectFromMenu()`), using the usual unsaved-changes guard. It does nothing while the unsaved-changes or delete question is showing. Elsewhere it behaves as before. Help (`10-projects.md`) is updated to match.

Round 2: File ▸ New Session is now enabled by `AppStateStore.newItemCommandEnabled`, true when there is a content window or the Project Editor window exists. `projectEditorIsOpen` is an observed flag written only by the editor controller when it builds the window (`projectEditorDidOpen()`) and when it closes (`projectEditorDidClose()`). So ⌘N in the Projects window starts a New Project even after the last content window has closed. There is still one handler, the menu item's action, routed by `newItemRoute()`. `newProjectFromMenu()` now sits below `prepare`, which has its doc comment back.

## Review notes

Round 1, 2026-11-14, bounced. `./build.sh`, `./build.sh ui-typecheck` and `./build.sh unit` (4083) all pass on the reviewer's run. The VM run was skipped because the bounce below is a requirement defect the plan's UI filters do not exercise; the next review runs them.

What is right and should stay: the browse state on first open, `placeholder`, no first-Project fallback in the init, Edit…/Save as Project still preselecting, the open window keeping its draft, `requestNewProjectFromShortcut` going through `requestNavigation` and ignoring the chord under a pending question, and the tests (they assert non-default states). No observation-rule violations: `placeholder` is derived, and every write is event-origin.

1. **⌘N beeps while the Projects window is key and no content window is open (blocking).** `BattyCommands.swift`, New Session button: `.disabled(keyWindow == nil)`. `keyWindow` is `store.keyContentWindow`, which is nil exactly when `store.windows` is empty. Projects ▸ Projects… is always enabled, and closing the last content window does not quit Batty (no `applicationShouldTerminateAfterLastWindowClosed`; the content scene is a `WindowGroup`). So "close the window, choose Projects…, press ⌘N" is a reachable path where the item is disabled and ⌘N beeps. The issue's Expected behavior 3 requires ⌘N to start a New Project whenever the Projects window is key. On `main` ⌘N did nothing in the editor in every case, so this is not a pre-existing behavior to keep; it is a gap in the new feature. (With no Batty window key at all, ⌘N beeps on `main` too; that part is pre-existing and fine.)
   - What would satisfy it: ⌘N starts a New Project in the editor with zero content windows, without a second handler firing when a content window does exist. Options: make the enablement depend on something observed that is true while the editor window exists (for example an observed "editor is open" flag the controller writes from `show`/`windowWillClose`, both event-origin), so the item is enabled when `keyWindow == nil` but the editor is open; or handle the chord in the editor window itself (the key window gets `performKeyEquivalent` before the main menu) and keep the menu route for the content-window case. Whichever is chosen, keep exactly one handler per press and add a unit test for the enablement rule (a pure function like `newItemRoute`, with zero windows and the editor open giving enabled). Add a VM UI test that closes the content window, opens Projects…, presses ⌘N and asserts the Untitled row, if the harness can close the last content window without quitting.
   - Remove the matching Gotcha once fixed.

2. **Misplaced doc comment (non-blocking, fix while there).** `ProjectEditorWindowController.swift`: `newProjectFromMenu()` was inserted between `prepare`'s doc comment and `prepare`, so `prepare`'s "Builds the window and model…" paragraph now documents `newProjectFromMenu`, and `prepare` has none. ## Review

Two rounds. Round 1 bounced: ⌘N beeped in the Projects window with no content window, and `prepare` had lost its doc comment. Round 2 approved.

- **⌘N with no content window: fixed.** New Session's enablement is now `newItemCommandEnabled` (content window or editor open). `projectEditorIsOpen` is written only from `prepare`'s window build and `windowWillClose` → `projectEditorDidClose()`, both event-origin and idempotent. The menu action is still the one handler, routed by `newItemRoute()`. With a content window present, enablement and routing are unchanged, and `.newProject` is chosen only while the editor is key, so no Session opens from the Projects window.
- **Doc comment: fixed.** `newProjectFromMenu()` now sits below `prepare`, and `prepare` has its comment back.
- **Disagreement settled: the implementer is right.** Round 1 said closing the last content window doesn't quit Batty. That was wrong. There is no `applicationShouldTerminateAfterLastWindowClosed`, but `removeWindow` calls `terminateIfLastContentWindowGone()` (`AppStateStore.swift`). It schedules termination when no content windows remain, unless `holdQuitForUnsavedEditor()` finds a dirty Project Editor. So the no-content-window state with the editor open exists only when the editor has unsaved edits. The Gotcha and the new UI test (edit first, close the content window, ⌘N, Discard Changes) match the code.
