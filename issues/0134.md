# 0134 — Bell Feed hotkey with keyboard navigation and jump-to-pane

| | |
|---|---|
| **Status** | open |
| **Module** | BellFeed / App |
| **Platform** | macOS |
| **First seen** | 2026-05-16 |

## Description

The Bell Feed today is reachable by clicking the feed badge in the chrome. There's no keyboard path: a user who notices a bell out of the corner of their eye still has to reach for the mouse. Add a global hotkey that opens the feed popover, lets Up / Down move through entries, and lets Return jump straight to the pane that emitted the bell — so the whole "I heard a beep, take me there" loop happens without leaving the home row.

The shape mirrors Open Quickly (#0128): keyboard-only entry, list navigation, Return ends in a focus jump to a terminal. The feed already knows how to jump on click (`click-to-jump` is part of its existing surface — see Concepts.md and the BellFeed module); this issue is the keyboard front door.

## Acceptance criteria

- **Cmd-Shift-B** from anywhere in the app opens the Bell Feed popover and gives keyboard focus to the entry list.
- Pressing **Cmd-Shift-B** again while the feed is open dismisses it (toggle behavior). **Esc** also dismisses.
- **Up / Down** arrow keys move the selection within the entry list. Selection wraps (Down past the last entry goes to the first) or clamps — implementer's call; pick whichever feels closer to the rest of the app's lists.
- **Return** on a selected entry: dismisses the feed, brings the entry's session forward in the sidebar, focuses the entry's tab in its pane, and gives keyboard focus to the terminal. Reuse `TerminalSurfaceFocuser.focusWhenReady` (hardened in #0129) for the final focus step — same path Open Quickly uses.
- Clicking an entry continues to work exactly as it does today (no regression).
- An empty feed shows the feed's existing empty-state UI — opening the feed with no entries should be a no-op visually (no selection, Return does nothing).
- A menu item under whichever menu currently hosts BellFeed actions (or View) mirrors the hotkey for discoverability — same pattern as Cmd-Shift-O in #0128.

## Out of scope

- Filtering / searching the feed. Pure list nav for v1; if the feed grows large enough that filtering matters, file separately.
- Dismissing / clearing entries from the keyboard (e.g. Delete to remove). The hotkey is about jumping, not curating.
- Per-entry actions beyond "jump to pane" (mute that pane, copy the bell timestamp, etc.) — defer.
- A floating-window variant of the feed. The popover anchored at the chrome badge is the existing surface; this issue keeps that anchor.
- System-wide global hotkey (works while Batty is in the background). Cmd-Shift-B is in-app only for v1; system-wide registration is a separate concern with its own UX/permissions implications.

## Notes

- Cmd-Shift-B is the natural mnemonic and follows the Cmd-Shift-O / Cmd-Shift-P pattern from #0128 / #0126. Implementer should grep `BattyShortcuts` / `BattyCommands` to confirm it isn't already bound; if it is, the user's preference is to free it for this and move whatever else lives there.
- The popover is anchored at the chrome badge today. Opening it from a hotkey while the badge is offscreen (full-screen window, hidden toolbar) is the obvious edge case — fall back to a centered anchor in that situation rather than failing silently. Document the fallback in the resolution.
- Each entry already carries a reference to the originating pane (otherwise click-to-jump wouldn't work) — the keyboard activation should reuse the same code path. Don't introduce a parallel jump path.
- Wiring pattern: see how Cmd-Shift-O is wired in `BattyShortcuts.handle(_:)` plus a mirrored menu item (per #0128's resolution). Same shape applies here.
- Visual focus indicator on the selected row should match whatever list-selection style the feed already uses (or the sidebar uses) — don't invent a new highlight just for keyboard mode.
- Related: #0126 (command palette) — once it lands, "Open Bell Feed" should appear there too. That's a #0126 concern, not this issue's.
