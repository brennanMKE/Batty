# 0463 — A new Tab's working directory depends on which entry point created it: the Tab > New Tab menu item spawns at the shell default while Cmd-T, the Command Palette, the tab-strip "+" and Duplicate Tab inherit the source Tab's cwd, and `PaneRuntime.addTab` has no `configuration.workingDirectory` fallback where split and new-Session inheritance do

| **First seen** | 2026-10-11 |

## Description

Six code paths create a Tab. Five pass the source Tab into
`PaneRuntime.addTab(inheritingCWDFrom:)`; one, the menu-bar **Tab > New
Tab** item, calls `addTab()` with no source, so a Tab created by clicking
that menu item starts wherever libghostty puts a surface with no
`working_directory` (the shell's default) instead of in the directory the
active Tab is in. Every other way of making a Tab, and `Concepts.md`'s own
description of the rule ("mirroring the way Cmd-T inherits cwd within a
Pane", `Concepts.md:50`), says a new Tab inherits. `docs/shortcuts.md:73`
("New Tab | `Cmd-T` | Inherits CWD from active tab") and `:102` document the
inheriting form as *the* New Tab action and do not mention the menu
exception.

This is the "adjacent divergence" #0408's Notes recorded and its Gotchas
left unfiled ("Not covered: New Tab from the menu bar ... still takes its
working directory differently; to be filed separately",
`issues/0408.md:212`). #0408 itself added
`AppStateStore.addTab(toPaneID:inheritingCWDFrom:)` for the two in-Pane
mouse affordances and did not touch the menu path.

A second, smaller divergence turned up while auditing: `PaneRuntime.addTab`
reads only the live `terminal.workingDirectory` of the source Tab
(`PaneRuntime.swift:173`), whereas every other cwd-inheritance site in the
app falls back to `terminal.configuration.workingDirectory` when the live
value is still nil (`WindowRuntime.addSession`, `SplitTree.makePane`, see
Notes). So even the inheriting entry points lose the directory when the
source Tab's shell has not yet reported its pwd.

Nothing here was reported by a user; both findings come from code reading
(#0408's audit and this filing). The interactive outcomes in "Actual
behavior" are derived, not observed in a running app.

## Steps to reproduce

Beta only (`./build.sh`), never the user's Prod app.

1. In a Pane whose shell is at a non-home directory (e.g. `cd ~/Developer/Batty`),
   press **Cmd-T**. Run `pwd` in the new Tab.
2. Back in the first Tab, open the **Tab** menu in the menu bar with the
   mouse and click **New Tab**. Run `pwd` in the new Tab.
3. Repeat with Command Palette > New Tab, the tab strip's "+" button, and
   right-click a chip > Duplicate Tab, running `pwd` each time.
4. For the fallback finding: with a fresh Tab whose shell has not yet
   printed a prompt (or a Tab whose foreground program is not a shell with
   integration, so no OSC 7 report has arrived), press Cmd-T immediately and
   run `pwd` in the new Tab once it is up.

## Expected behavior

Not pinned anywhere today beyond `Concepts.md:50` and `docs/shortcuts.md:73`,
both of which describe inheritance as the rule. What a fix must deliver,
whichever answer the user gives to the Open questions:

Acceptance criteria:

1. **One rule for every entry point.** The menu-bar Tab > New Tab item, the
   `BattyShortcuts` NSEvent monitor (`.newTab`), the Command Palette
   (`.newTab`), the tab-strip "+", Duplicate Tab, and the UI-test
   `createTab` intent all produce a Tab with the same working directory
   given the same source Tab. If the chosen rule is "inherit" (what five of
   six paths do today), the menu item passes the focused terminal Pane's
   active Tab as the source like the other paths do, or every path is
   collapsed onto `AppStateStore.addTab(toPaneID:inheritingCWDFrom:)`
   (#0408) so the choice lives in one place. If the chosen rule is "the
   menu is deliberately different", that is written down in
   `docs/shortcuts.md` next to the New Tab row and in `Concepts.md`'s Tab
   section, and this issue says why.
2. **The fallback chain is decided and consistent.** Either
   `PaneRuntime.addTab(inheritingCWDFrom:)` falls back to
   `source.terminal.configuration.workingDirectory` the way
   `WindowRuntime.addSession` (`WindowRuntime.swift:198-199`) and
   `SplitTree.makePane` (`SplitTree.swift:372-373`) do, or the issue records
   why a Tab should not. (#0057's Gotchas, `issues/0057.md:94`, explain why
   the fallback exists: `TerminalViewState.workingDirectory` is
   `internal(set)` to the package and nil until the shell's first pwd
   report; the configured directory is what the shell was actually spawned
   in.)
3. **Unit tests pin it.** Today no BattyKit test asserts that
   `addTab(inheritingCWDFrom:)` propagates a directory at all (the only
   test that calls it, `PaneRuntimeKindGateTests.swift:49`, checks the
   non-terminal gate). Add tests modelled on `SplitTreeCWDTests`
   (`splitInheritsFocusedPaneCWD`, `splitWithoutSourceHasNoCWD`,
   `splitFallsBackToConfigurationWorkingDirectory`) for the Tab path:
   inherit from the source Tab, no source gives nil, and the configuration
   fallback if criterion 2 adopts it. Because the live value is
   `internal(set)`, the tests set `configuration.workingDirectory` on the
   source Tab, exactly as `SplitTreeCWDTests` and
   `AppStateStoreSessionCWDTests` do.
4. **A UI test covers the menu-bar item**, since the menu's `Button`
   closure cannot be unit-tested (`docs/swiftui-observation-rules.md`'s
   Commands-body caution, restated at `AppStateStore.swift:937-942`). In
   the Tart VM: `cd` into a temp directory in the first Tab, click
   **Tab > New Tab** through the menu bar (not `typeKey`, which the
   NSEvent monitor consumes first), then write `$PWD` through the
   `sentinelPath` tmp+mv pattern `PaneFocusTests.swift:205-213` uses and
   assert it equals the temp directory. `SessionCwdRenameTests.swift:26-44`
   shows how to create a directory both the sandboxed runner and the app
   can reach. The existing Cmd-T tests
   (`KeyboardShortcutTests.swift:15-29`, `LifecycleTests.swift:32-44`)
   assert chip counts only and need not change.
5. `./build.sh`, `./build.sh unit` and the VM UI suite pass. No sleeps in
   tests (AGENTS.md).

## Actual behavior

Per code reading, with the first Tab's shell at `~/Developer/Batty`:

- **Cmd-T** (consumed by the NSEvent monitor), **Command Palette > New
  Tab**, the tab-strip **"+"**, and **Duplicate Tab**: the new Tab's `pwd`
  is `~/Developer/Batty`, provided the source Tab's shell has already
  reported its pwd (otherwise see the last bullet).
- **Tab > New Tab clicked in the menu bar**: the new Tab's `pwd` is the
  shell default, not `~/Developer/Batty`. `TabRuntime.init` receives
  `workingDirectory: nil`, never sets `configuration.workingDirectory`
  (`TabRuntime.swift:144-146`), and the package then omits
  `working_directory` from the surface config
  (`TerminalController+Surface.swift:109-117`). #0057's Root cause
  (`issues/0057.md:80`) and `Concepts.md:50` describe that default as
  `$HOME` in practice; the exact directory is libghostty's choice, not
  Batty's, and was not re-verified for this filing.
- **Cmd-T while a non-content window is key** (Settings, Help): the monitor
  stands down (`BattyShortcuts.swift:33`), the SwiftUI key equivalent
  reaches the menu item, and it fires against `defaultTargetWindow()`'s
  most-recently-key content window (`BattyCommands.swift:61`,
  `AppStateStore.swift:920-931`), again without a source Tab. Unverified in
  a running app; follows from the code.
- **Any inheriting path when the source Tab has no live pwd yet** (just
  spawned, or a `command:` Tab running a program that never emits OSC 7):
  `source.terminal.workingDirectory` is nil (`TerminalViewState.swift:25`
  defaults nil; only `terminalDidChangeWorkingDirectory` writes it,
  `TerminalViewState+Delegate.swift:106-111`), `addTab` passes nil, and the
  new Tab spawns at the shell default even though the source Tab was
  itself spawned in a known directory via `configuration.workingDirectory`.

The menu item and the monitor share one binding
(`shortcuts.keyboardShortcut(for: .newTab)` at `BattyCommands.swift:493`;
`ShortcutsStore.shared.binding(for:)` at `BattyShortcuts.swift:39-44`), so
rebinding New Tab moves both. Because the monitor is an
`NSEvent.addLocalMonitorForEvents(matching: .keyDown)` that returns `nil`
when `handle` consumes the event, a Cmd-T pressed while a content window is
key never reaches the menu's key equivalent; the menu closure runs for a
mouse click on the item, or when the monitor declines (first responder is a
`RecorderView`, `BattyShortcuts.swift:24`; key window is not a registered
content window, `:33`; no `keyWindowRuntime()`, `:113`).

### How `PaneRuntime.addTab` resolves the directory

`BattyKit/Sources/BattyKit/Runtime/PaneRuntime.swift:167-181`:

```swift
public func addTab(inheritingCWDFrom source: TabRuntime? = nil) -> TabRuntime {
    guard kind == .terminal else { ... }
    let cwd = source?.terminal.workingDirectory
    let tab = TabRuntime(workingDirectory: cwd)
```

Compare `WindowRuntime.addSession` (`WindowRuntime.swift:198-199`):
`sourceTab?.terminal.workingDirectory ?? sourceTab?.terminal.configuration.workingDirectory`,
and `SplitTree.makePane` (`SplitTree.swift:372-373`, also `:360-361` for the
Git Status branch): the same two-step chain. #0061's Fix
(`issues/0061.md:69`) describes that chain as "same lookup pattern as
`addSession`" and pinned it with
`SplitTreeCWDTests.splitFallsBackToConfigurationWorkingDirectory`. The Tab
path predates both (#0016 added `inheritingCWDFrom`, `issues/0016.md:86`)
and was never given the fallback. `TabRuntime`'s own doc comment
(`TabRuntime.swift:35-55`) sanctions reading the live Combine value on
on-demand paths such as "a new split/tab inheriting cwd", so reading
`terminal.workingDirectory` here is fine; the gap is only the missing
second step.

### History of the menu line

`git log -S` shows the menu's New Tab closure has never passed a source:
`a9cf83f2` (#0017) introduced `store?.selectedSession?.focusedPane.addTab()`,
`7eec59f8` (#0315) changed only the accessor to `focusedTerminalPane?.addTab()`.
#0016, which added `inheritingCWDFrom` and wired PaneView's "+" to it, lists
`BattyCommands.swift` in its Files changed only for `tabMenuTitle(at:)`
(`issues/0016.md:97`). #0062 (`3b3c5341`) gave the NSEvent monitor the
inheriting call and #0126 (`73147e38`) gave the palette the same, so the
menu became the odd one out by omission, not by a recorded decision.
Nothing in #0016, #0017, #0057, #0061, #0062, #0126 or #0315 says the menu
should differ.

### Constraints

- The menu closure and the monitor's `run` are user-event handlers, so
  passing a source Tab or calling `AppStateStore.addTab(toPaneID:)` there
  is an event-origin write and fine under
  `docs/swiftui-observation-rules.md`. Do not move the write into a `Task`.
- `focusedTerminalPane` must stay the accessor on the menu/monitor/palette
  paths (#0315, `SessionRuntime.swift:201-214`); the fix changes what is
  passed, not how the Pane is found.
- The parent's note names `Batty/BattyCommands.swift:489`; the file is
  `BattyKit/Sources/BattyKit/Commands/BattyCommands.swift` (the app target
  has no `BattyCommands.swift`). The menu is `CommandMenu("Tab")`, so the
  item is Tab > New Tab, not File > New Tab.

## Open questions

1. **Should Tab > New Tab inherit like every other path, or is "menu item
   starts fresh at the shell default" a behaviour worth keeping?** The
   filer did not decide. Five paths plus `Concepts.md:50` and
   `docs/shortcuts.md:73` say inherit; nothing records an argument for the
   menu being different. If the user wants a "new Tab at `$HOME`" gesture,
   it would need its own menu item or modifier rather than being the
   accidental behaviour of the one path a user cannot tell apart from
   Cmd-T.
2. **Should `PaneRuntime.addTab` adopt the `configuration.workingDirectory`
   fallback?** Split and new Session do; a Tab created seconds after its
   source Tab appeared currently loses the directory. The filer sees no
   reason for the difference but did not verify how often the live value
   is still nil at the moment a user presses Cmd-T.
3. **Should all six paths route through
   `AppStateStore.addTab(toPaneID:inheritingCWDFrom:)`?** #0408 built it
   for the two mouse paths so Pane focus follows creation; the
   keyboard/menu/palette paths already target the focused Pane, so the
   focus write would be a no-op there (`focusPane(id:)` is idempotent per
   `docs/swiftui-observation-rules.md`). One call site would end the
   "third hand-copied dispatch switch" problem `Concepts.md:83` describes
   for the #0315 kind gate. Implementer's call unless the user has a view.
4. **Target release.** This dates from #0017 and ships in every release so
   far; proposed for `main` (next minor) unless the user wants it in 1.2.x,
   in which case it is fixed on `main` first and cherry-picked to
   `release/1.2` per AGENTS.md.
