# 0613 — WindowRuntime.selectedSessionID is publicly settable despite its heavy didSet, and every Session switch re-themes every terminal even when the Theme is unchanged

| | |
|---|---|
| **Status** | open |
| **Module** | Session / Theme |
| **Platform** | macOS |
| **First seen** | 2026-11-12 |
| **Priority** | medium |

## Description

**HIGH (hardening). Related to #0601 and #0602.** Since #0602, `WindowRuntime.selectedSessionID`'s `didSet` runs the whole selection cascade synchronously: start/stop status-Pane sampling, deny the previous Session's clipboard request, schedule terminal focus, `markActiveTabSeen()` (writes Bell Feed `entries` and unseen counters), and `applySelectionTheme` (libghostty `controller.setTheme` on every terminal Tab of the Session, plus a palette write). That is safe only while every writer is event-origin. The property is `public var`, so any future `$windowRuntime.selectedSessionID` binding or `onChange` writer would silently run the cascade inside a SwiftUI update. And `applySelectionTheme` calls `setTheme` on every Tab on every switch, even when the Session's effective Theme hasn't changed since it was last applied.

## Current state (verified 2026-11-12 on `main` `ce66ca6a`)

- `BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift:77-83`: `public var selectedSessionID: UUID? { didSet { guard oldValue != …; applySelectionVisibility(…); applySelectionEffects(…) } }`.
- `WindowRuntime.swift:1054-1065` (`applySelectionVisibility`), `:1070-1093` (`applySelectionEffects`).
- `Theme/ThemePreference.swift:252-265`: `applySelectionTheme(for:isDark:)` → `applyTerminalTheme` (`:175-187`, `tab.terminal.controller.setTheme(…)` for every terminal Tab) unconditionally.
- Writers outside `WindowRuntime`: `Runtime/AppStateStore.swift:1444-1447` (the `selectedSessionID` shim, `set { windows[0].selectedSessionID = newValue }`), `Testing/UITestDriver.swift:128` (`store.selectedSessionID = session.id`), and 103 direct writes across BattyKit tests (e.g. `WindowRuntimeSessionSelectionVisibilityTests`, `BellFeedVisitTests`, `AppStateStoreFocusTests`).
- The one AppKit-driven writer path: the sidebar `List` selection binding (`Views/SessionSidebarView.swift:284-289`) → `selectSessionFromSidebar` (`WindowRuntime.swift:503-509`). If `NSTableView` ever writes the selection during a reload inside the hosting view's update (row removal, reorder), the cascade runs inside layout. Unverified.

## Rule violated

- `docs/swiftui-observation-rules.md`, "Two-way model ↔ AppKit sync" and the #0602 worked example: the `didSet` funnel is correct only because every writer is event-origin; the API should enforce that.
- swift-guidance `swiftui-observation.md`: mutate observed state through explicit model methods; idempotent hot-path mutators.

## Evidence

- **Proven:** the public setter, the cascade, the unconditional `setTheme`.
- **Inferred:** no bug reproduced; this is hardening plus wasted libghostty work per switch.

## Fix direction

- Make the setter non-public: `public internal(set)` at minimum, or `private(set)` with every writer going through `setSelectedSession(id:)`. Route the `AppStateStore.selectedSessionID` shim and `UITestDriver` through `setSelectedSession(id:)`. With `private(set)`, the 103 test writes must move to `setSelectedSession(id:)` too (`@testable` doesn't open `private` setters); the planner chooses.
- In `applySelectionTheme`, skip `applyTerminalTheme` when the Session's effective Theme name equals the one last applied to it (record it per Session, `@ObservationIgnored`). Keep re-theming on appearance change and global/Session Theme changes, which must invalidate that record.
- Verify with a log or probe that `selectSessionFromSidebar` never fires under `NSHostingView.layout` while Sessions are added, removed or reordered; file separately if it does.

## Tests

- New in `ThemePreferenceTests` (or `WindowRuntimeSessionSelectionVisibilityTests`): `switchingBetweenSessionsWithTheSameThemeDoesNotReapplyTerminalTheme()` (count `setTheme` through a seam; fails before), `switchingToASessionWithADifferentThemeAppliesIt()`, `appearanceChangeReappliesAfterASkippedSwitch()` (non-default fixtures: two Sessions with distinct overrides).
- Compile-level: after the change, `windowRuntime.selectedSessionID = x` from outside the module must not compile; covered by the build.
- Keep passing: every suite that selects Sessions (`WindowRuntimeSessionSelectionVisibilityTests`, `RemoveSessionSelectionTests`, `BellFeedVisitTests`, the #0602 tests).
- UI, at the daily VM run: `BattyUITests/ThemeTests`, `SidebarTests`, `KeyboardShortcutTests` (Cmd-1..9).
