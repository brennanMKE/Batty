## Description

**HIGH (hardening). Related to #0601 and #0602.** Since #0602, `WindowRuntime.selectedSessionID`'s `didSet` runs the whole selection cascade synchronously: start/stop status-Pane sampling, deny the previous Session's clipboard request, schedule terminal focus, `markActiveTabSeen()` (writes Bell Feed `entries` and unseen counters), and `applySelectionTheme` (libghostty `controller.setTheme` on every terminal Tab of the Session, plus a palette write). That is safe only while every writer is event-origin. The property is `public var`, so any future `$windowRuntime.selectedSessionID` binding or `onChange` writer would silently run the cascade inside a SwiftUI update. And `applySelectionTheme` calls `setTheme` on every Tab on every switch, even when the Session's effective Theme hasn't changed since it was last applied.

## Root cause

`WindowRuntime.selectedSessionID` was `public var`, so any app-target binding or `onChange` could run its `didSet` selection cascade inside a SwiftUI update; nothing enforced the event-origin-only rule. Separately, `AppStateStore.applySelectionTheme(for:isDark:)` called `applyTerminalTheme` (libghostty `setTheme` on every terminal Tab) on every switch, even when the Session's effective Theme was unchanged. No user-visible bug was reproduced; this is hardening plus wasted work.

## Fix

Followed the plan. `selectedSessionID` (and the `AppStateStore` shim) are now `public internal(set)`, with the rule documented on the property; `UITestDriver` selects through `setSelectedSession(id:)`. `SessionRuntime` gains `@ObservationIgnored var appliedTerminalThemeName`, written only at the end of `applyTerminalTheme`; `applySelectionTheme` skips the terminal re-theme when the effective Theme name equals it (chrome update stays unconditional). Global, appearance, preview and Session-Theme changes all go through `applyTerminalTheme`, so the record stays truthful. One test-sequence deviation: `WindowRuntime.addSession()` already selects the new Session, so tests select `source` first before selecting `b`.

### Premises checked

- **Confirmed:** `public var selectedSessionID` with the `didSet` cascade (`WindowRuntime.swift:82-89` at `b940f47d`), and `selectionThemeHandler` → `AppStateStore.applySelectionTheme(for:isDark:)` (`ThemePreference.swift:256-265`), which calls `applyTerminalTheme` → `controller.setTheme` on every terminal Tab every time.
- **Confirmed:** no production writer outside BattyKit. Neither `Batty/` nor `BattyTests/` writes it, and no `$…selectedSessionID` binding exists. Writers outside `WindowRuntime.swift` are the `AppStateStore` shim setter (`AppStateStore.swift:1444-1448`) and `UITestDriver.swift:128`.
- **Confirmed:** 103 test writes in 34 files. **17 of them write `nil`**, in `BellNotificationSummaryTests` ×7, `CrossWindowBehaviorTests` ×5, `SaveSessionAsProjectTests`, `WindowRuntimeCreatePaneTests`, `AppStateStoreSessionCWDTests`, `BellFeedStoreTests` and `CloseCancelsAIWorkTests`. `setSelectedSession(id:)` rejects nil and unknown ids by design (#0258), so routing them through it would change what those tests exercise.
- **Theme names identify Theme content:** `BattyThemeCatalog.allThemes` is a static `let`. That makes comparing names a sound way to tell whether a Theme has changed.
- **No cross-Session Tab or Pane moves exist.** New Tabs and Panes get `TabRuntime.startingTheme(sessionThemeOverride:)`, the effective Theme at creation (`TabRuntime.swift:199`, `SplitTree.adopt` `:265-268`). So a Session's Tabs only drift from its last applied Theme through paths that already go through `applyTerminalTheme`.

### Decision: `public internal(set)`, not `private(set)`

`private(set)` would mean adding a nil-clearing test hook and editing 103 call sites in 34 files, which changes what 17 nil-writing tests exercise. `internal(set)` closes the hazard the issue names: no app-target code (`Batty/`, which owns most SwiftUI bindings) can write the property or bind `$windowRuntime.selectedSessionID`. Inside BattyKit, the doc comment states the rule, and `UITestDriver` moves to `setSelectedSession(id:)`.

- `docs/swiftui-observation-rules.md`, "Two-way model ↔ AppKit sync" and the #0602 worked example: the `didSet` funnel is correct only because every writer is event-origin; the API should enforce that.
- swift-guidance `swiftui-observation.md`: mutate observed state through explicit model methods; idempotent hot-path mutators.

## Evidence

- **Proven:** the public setter, the cascade, the unconditional `setTheme`.

## Fix direction

- Make the setter non-public: `public internal(set)` at minimum, or `private(set)` with every writer going through `setSelectedSession(id:)`.
