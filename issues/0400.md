## Description

The pinned `libghostty-spm` (`a2565ccf047c03c74a59dd7c16a8fac7c477852f` per `BattyKit/Package.resolved`, release `1.5.20260903`, `Ghostty.ref` = `c4e16970a…`) ships shell-integration scripts for **bash and zsh only**: `Sources/GhosttyTerminal/Resources/Ghostty/shell-integration/` contains exactly `bash/` (`ghostty.bash`, `bash-preexec.sh`, a license file) and `zsh/` (`.zshenv`, `ghostty-integration`) — verified by listing the checkout at `BattyKit/.build/checkouts/libghostty-spm`. Both are the package's from-scratch MIT rewrite (their headers say so verbatim). Upstream Ghostty at the **same pinned ref** ships five shells — `bash`, `elvish`, `fish`, `nushell`, `zsh` (`src/shell-integration/` in the upstream checkout at `~/Developer/brennanMKE/libghostty-spm/References/ghostty-upstream`, checked out at `c4e16970a…`) — so the fish/elvish/nushell drop is the package's, not upstream's.

Meanwhile Batty lets a user run **any** shell: `SettingsPreference.resolvedShell()` (`BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift:50-54`) returns the free-text Settings override (`SettingsView.swift:37`) or falls back to `$SHELL` / `getpwuid` (`detectedShell()`, `SettingsPreferences.swift:39-48`). The affected population is therefore not "people who typed fish into Settings" — it is **anyone whose macOS login shell is fish, nushell, or elvish**, with zero configuration.

The failure is entirely silent. libghostty still "sets up" integration for these shells — for fish/elvish it only checks that the `shell-integration` directory *exists* before prepending it to `XDG_DATA_DIRS` and exporting `GHOSTTY_SHELL_FEATURES` (`src/termio/shell_integration.zig:76-79`, `setupXdgDataDirs` at `:626`, features export at `:235`; nushell's `setupNushell` goes through the same helper) — but the directory contains no fish/elvish/nushell payload, so the shell autoloads nothing. No warning, no log line a user would ever see.

## This is a regression from the re-pin, not a standing gap

Before [#0389](0389.md)'s re-pin, the package (previous pin `b146b73a…`) shipped **no** shell-integration resources and never set `GHOSTTY_RESOURCES_DIR` (verified via `git ls-tree` in the fork clone: no `Resources/`, no `GhosttyRuntimeResources` type; and nothing in Batty sets the variable — grep of `BattyKit/Sources`, `Batty/`, `scripts/` finds zero hits). libghostty therefore fell back to its sentinel search (`src/os/resourcesdir.zig:64`, `:88` — climb from the executable, look for `Contents/Resources/terminfo/78/xterm-ghostty`, use `Contents/Resources/ghostty`), which found **Batty's own vendored tree** — `Resources/ghostty-runtime/ghostty/shell-integration/`, bundled by `scripts/bundle-ghostty-resources.sh:23-27`, which carries **all five shells** ([#0003](0003.md) vendored them; the layout matching the sentinel search is why #0003 chose it).

The `a2565ccf` package now sets `GHOSTTY_RESOURCES_DIR` itself to its own two-shell bundle (`GhosttyRuntimeResources.swift:23-26`), and in release builds the env var short-circuits the sentinel search (`resourcesdir.zig:52`; the xcframework is built `ReleaseFast`, `Script/build-ghostty.sh:120`). Net: fish/elvish/nushell users **had** working integration and lost it when the re-pin landed, and Batty's five-shell tree still ships in every build as dead weight.

## What degrades, precisely

Traced through source; this is the severity case. Batty consumes exactly two integration-driven signals from the package: `TerminalViewState.workingDirectory` (`:25` in the pinned package — written **only** by the `GHOSTTY_ACTION_PWD` callback, `TerminalCallbackBridge.swift:144-146` → `TerminalViewState+Delegate.swift:108-109`, which libghostty emits from **OSC 7**) and `TerminalViewState.lastCommandDurationNanos` (`:28` — written only by `GHOSTTY_ACTION_COMMAND_FINISHED`, `TerminalCallbackBridge.swift:79-85`, emitted from **OSC 133 D**). With no script sourced, neither ever fires. Downstream:

**Broken outright:**

- **New-Tab cwd inheritance (Cmd-T).** `PaneRuntime.addTab(inheritingCWDFrom:)` reads `source?.terminal.workingDirectory` with **no fallback** (`BattyKit/Sources/BattyKit/Runtime/PaneRuntime.swift:158`). It stays `nil` forever for these shells, so every new Tab spawns at libghostty's default directory rather than the current one — inheritance simply does not exist.
- **The running-command chip never clears.** TUIs set it through their own OSC 2 titles (`TabRuntime.refreshRunningCommandFromTitle`, `TabRuntime.swift:304` — set-only by design), and the **only** clear path is OSC 133 D (`recordCommandFinishedIfNeeded`, `TabRuntime.swift:321`, driven by the observer at `PaneView.swift:675-687`). Once `vim`/`claude`/`ssh` runs in a fish Tab, the chip claims it is running forever.

**Degrades to stale:**

- **New-Session cwd inheritance.** `WindowRuntime.addSession` falls back to `configuration.workingDirectory` (`WindowRuntime.swift:159`, `:172-174`) — the source Tab's *spawn-time* directory, not where the user has since `cd`'d.
- **Tab chip titles and `batty list` paths freeze at the launch directory.** `TabTitleFormatter.chipTitle` (`TabTitleFormatter.swift:6`, cwd reads at `:13-18` and `:33-38`) and the topology payload's `path` (`TopologyPayloadBuilder.swift:57`) both read the OSC 7 mirror (synced only by `syncWorkingDirectoryFromTerminal`, `TabRuntime.swift:257-260`). This is exactly the stuck-chip bug [#0260](0260.md) fixed — resurfacing, but per-shell. Agents reading `batty list` see wrong cwds for these Sessions.

**Largely unaffected:**

- **`batty new` path matching ([#0380](0380.md)).** The requested path seeds `TabRuntime.workingDirectory` at init (`TabRuntime.swift:106-121`), so `NewSessionResolver.findNewSessions` matches without any OSC 7 report; the symlink-race note at `NewSessionResolver.swift:105-110` concerns the OSC 7 *overwrite*, and the resolver normalizes both sides anyway. Listed because the #0392 review flagged it; it survives.
- **Bell Feed** (BEL / OSC 9 / OSC 777 are emitted by the running program, not the shell), **Theme**, and **local** `TERM`/`COLORTERM`/`TERMINFO` (exported by termio for every child regardless of integration, `src/termio/Exec.zig:648-657`).

**Cosmetic:** the scripts' prompt-time OSC 2 titles and DECSCUSR cursor-shape switching. fish sets window titles natively by default, which partially covers the title half; not traced further here.

## The three missing shells are MIT — the license caveat is narrower than #0399's

Batty's vendored tree still carries all five shells, and per the sweep recorded in `Resources/ghostty-runtime/ATTRIBUTION.md` (`:26-33`) and `BattyKit/Sources/BattyKit/Help/09-third-party-licenses.md:342-373`, the GPLv3 taint is confined to the Kitty-derived **bash/zsh trio** (`bash/ghostty.bash`, `zsh/.zshenv`, `zsh/ghostty-integration`). The `fish`, `elvish`, and `nushell` files are Ghostty's own MIT code — no divergent header, re-verified against the vendored copies. Two consequences worth the implementer's attention (still not deciding here):

- **Activating the full vendored tree** is the same package-redirection problem as [#0399](0399.md)'s leading candidate — and the same correction applies: there is no viable "one `setenv` after the package's call" (the package sets the env var with overwrite immediately before `ghostty_init` snapshots it, inside one private method — see #0399's "Correction" section for the full trace). If that route is taken, it drags the GPLv3 bash/zsh files in with it, which is the user's call. The two issues are plausibly **one piece of work**; whichever is implemented first should decide the mechanism for both.
- **Contributing the three MIT files to `Lakr233/libghostty-spm`** has no license obstacle at all — upstream Ghostty is MIT and these files carry no GPL header, so the package could ship them essentially verbatim, closing this issue for every consumer. The user has standing there (merged PR #57). This route fixes this issue without touching #0399's harder problem.

## Expected behavior

A user whose shell is fish, nushell, or elvish gets the same integration a zsh user gets — OSC 7-driven cwd tracking (Tab/Session cwd inheritance, live chip titles, correct `batty list` paths) and OSC 133-driven command-finished behavior — or, at absolute minimum, Batty knows integration is unavailable for the resolved shell and says so (Settings, Help, or a log), instead of silently degrading four features.
