## Description

Grow the `batty` CLI from "open a session at a path" into a coherent, extensible **`batty <noun> <verb> [flags]`** surface. This ticket **defines the concrete v1 argument surface** and implements the foundation + core mutation verbs — all over the existing one-way `batty://` URL scheme (no socket). Design rationale and the full catalog live in `docs/batty-cli-design.md`; this issue pins the exact arguments to build now.

The recent pane work gives the CLI real things to control: `pane split` distributes evenly (#0255) and panes can be hidden/shown (#0256).

**Revision (2026-07-06):** the primary consumer is an agent (Claude Code) running *inside* a pane. It must be able to open a pane vertical/horizontal to **its own** pane — even when that pane lives in a background session or a non-key window — and it needs a way to learn the surrounding topology (its own ids, sibling panes, hidden panes, other sessions). That drives three additions: explicit target ids carried in every `batty://` URL (Foundation §2), client-generated ids so creation verbs can "return" the new id over one-way IPC (Foundation §6), and the **Agent context & session topology** options section below.

## Foundation (Tier 0 — do first)

1. **Grammar:** `batty <noun> <verb> [flags]`. Nouns: **`session`, `pane`, `tab`, `window`** (+ bare app verbs). No `surface`/`workspace`/`worktree` (Batty's tab *is* the terminal). Keep `batty <path>` working as an alias for `batty session new <path>`.
2. **Context env vars + explicit targets in URLs:** inject `BATTY_SESSION_ID`, `BATTY_PANE_ID`, `BATTY_TAB_ID` (≡ surface id) into every surface at spawn (prepend `export …;` to the launch command, per supacode's pattern — see the CLI-context discussion). Every child process in the pane inherits them — this is what associates a Claude Code session with its pane. Every context-sensitive verb resolves its target as: explicit `--session/--pane/--tab` flag → else the `BATTY_*` env → else the app's focused element. **The CLI embeds the resolved ids as query params in every mutation URL** (e.g. `batty://pane/split?direction=vertical&pane=<uuid>`), so the app acts on the *caller's* pane, never on "whatever is focused" — the calling pane may be in a background session or another window. App-side, `BattyURLHandler` resolves ids across **all windows and sessions**; mutating a background target must not steal focus or switch the active session (only the `focus` verbs do that). With one-way IPC an unknown/stale id can only be logged app-side — the CLI can't see the failure (Option B below lets a script at least re-check state afterward).
3. **`batty whoami`** — print the current session/pane/tab **from env alone** (no app round-trip).
4. **Conventions:** global `--json` (reserved for query verbs later), meaningful exit codes, quiet by default. `batty version` / `help` already exist.
5. **IPC decision (pinned, amended):** mutations go over the **`batty://` URL scheme** (fire-and-forget, no daemon). Live reads (`read` screen, `wait`, `send`, `events`) still need a request/response socket and stay deferred (Tier 3). *Topology* queries (`list`, `session info`) turn out **not** to need the socket — see Option B below.
6. **Client-generated ids:** creation verbs (`session new`, `pane split`, `tab new`) have the **CLI mint the new object's UUID**, send it in the URL, and print it to stdout. The IPC stays fire-and-forget, yet the caller immediately knows the id of what it created and can chain commands: `batty pane split -v` → prints `<pane-id>` → later `batty tab new --pane <pane-id> -c 'npm test'` or `batty pane close --pane <pane-id>`. This is the one-way answer to "I opened a pane; now address it."

## Verb surface to build (Tier 1 — all one-way over `batty://`)

Concrete arguments:

```
batty session new [<path>]            # alias: `batty <path>`; defaults to "."; prints new session id
batty session rename <name>           # renames the calling/target session
batty session focus <name|id>
batty session close [--session <id>]

batty pane split [-h|--horizontal | -v|--vertical] [-c|--command <cmd>] [--pane <id>]
                                      # splits the calling/target pane (even 1/n, #0255);
                                      # -c runs a command in the new pane; prints new pane id
batty pane hide [--pane <id>]         # hides the calling/target pane (#0256)
batty pane show <id>                  # restores a hidden pane by id
batty pane focus <up|down|left|right|id>
batty pane zoom [--on|--off|--toggle]
batty pane close [--pane <id>]

batty tab new [-c|--command <cmd>] [--pane <id>]     # new tab in the calling/target pane; prints new tab id
batty tab rename <name>               # renames the calling/target tab
batty tab focus <n|id>
batty tab close [--tab <id>]

batty open                            # activate/foreground Batty
batty notify --title <t> [--body <b>] [--sound]   # posts into the bell feed
batty whoami [--json]                 # prints BATTY_* context (local, no app call)
```

Directional `pane focus` and split placement are computed **relative to the target pane's split tree**, not the screen — so they work identically for a background session.

Each mutation maps to a `batty://…` route the app handles (extending `BattyURLHandler`), targeting the resolved session/pane/tab. Reuse existing app methods where they exist: `AppStateStore.renameSession`, the split path (`SplitTree.splitFocusedPane` — needs a targeted `splitPane(id:)` variant per Foundation §2), `hidePane`/`showPane` (#0256), `focusPane`, `addSession(workingDirectory:)`; add the small ones missing (tab rename, notify-into-feed).

## Agent context & session topology — options

The driving use case: Claude Code runs inside a pane and controls Batty around itself. It must (a) know which session/pane/tab it is in, (b) mutate *relative to itself* even when its session is not active, and (c) see enough topology — sibling panes, hidden panes, other sessions — to act intelligently. (a) and (b) are covered by the env vars + explicit-target URLs above. (c) is a **query**, and Tier 1 has no response channel. Options:

- **A. Env only (`whoami`) — in this ticket regardless.** The pane's shell exports `BATTY_*`; every child process (Claude Code, its subshells, `batty` itself) inherits them. Solves identity and self-relative mutations. Gives zero visibility into siblings or other sessions. Free.
- **B. App-maintained state snapshot — recommended; the missing piece.** Batty writes a JSON topology snapshot to a known path (e.g. `~/Library/Application Support/Batty/state.json`) atomically (write temp + rename), debounced, on every layout/focus mutation. Query verbs just **read the file** — no socket, no daemon:
  - `batty list [sessions|panes|tabs] [--json]` — windows → sessions (id, name, path, active) → tabs → pane tree (split axis, hidden, zoomed, focused).
  - `batty session info [--json]` — the calling/target session's slice.
  - Closes the `pane show <id>` discovery gap (hidden panes appear in the listing).
  - Include each tab's **pty device path** so `batty whoami` can fall back to a `ttyname(stdin)` lookup when env is missing (env scrubbed, `sudo`, nested shells) — the robust pane↔process association.
  - Include Batty's **pid** so the CLI can distinguish "Batty isn't running" from a live snapshot.
  - The layout model is already pure Codable value types (`Session`, `Pane`, `Tab`, `SplitNode`), so the snapshot is nearly free; shape the JSON so a future socket's `list` response reuses it verbatim. This is a derived, disposable runtime artifact — *not* Workspace persistence (#0221).
  - Staleness is one debounce interval (~100 ms) — fine for topology; not fine for screen contents or waiting, which stay socket-tier.
- **C. Reply-file/FIFO RPC over `batty://`** (CLI passes a `--reply <fifo>` path; app writes the response). True request/response without a persistent socket, but fragile lifecycle (timeouts, orphaned FIFOs) and it *is* an ad-hoc RPC protocol — if RPC is warranted, a Unix socket is the cleaner spend. **Declined.**
- **D. Pull the Unix socket forward (Tier 3 now).** Full fidelity (`list`, `read`, `wait`, `events`), but a listener, a protocol, and versioning — exactly the complexity this ticket defers. **Stays deferred**; Option B's schema becomes the socket's `list` payload later.
- **E. Apple Events / scripting interface.** Mac-native request/response, but every calling host process trips the Automation TCC prompt — the very permission friction #0254 flags as the thing to reduce for agents. **Declined.**

**Recommendation: A + B.** Scope decision for the user: land B in this ticket as a "Tier 1.5" after the mutations, or file it as its own child ticket of #0254. Suggested: keep this ticket to Tier 0 + Tier 1 (with the target-id and client-id groundwork, which B depends on) and file B as the immediate follow-up — though note `pane show` stays awkward until B ships.

With A + B the agent loop becomes: `batty whoami --json` (who am I) → `batty list --json` (what's around me) → `batty pane split -v -c '…'` (open a pane next to me, get its id) → `batty notify` (tell the user) — all without a socket, and all correct even when the user is looking at a different session.

## Notes / decisions

- **Flag vs subcommand:** use subcommands (`batty pane split`) over bare option flags (`batty --split`) so each verb is unambiguous and the surface scales. `swift-argument-parser` (already a dependency) models `<noun>` as a `ParsableCommand` with `<verb>` subcommands cleanly.
- **`pane show` needs an id** (a hidden pane has no shell to run `batty` from). Id discovery is a *query* — Option B's `batty list` is the proper fix (hidden panes appear in the listing); until B ships, ids come from `whoami`/client-generated ids/logs. Note this limitation.
- **`-c` on `pane split`** mirrors `tab new -c`: it's the agent primitive "open a pane next to me running X" without needing socket-tier `send`. Same surface-spawn-with-command path as `tab new`.
- **Env is a hint, not truth:** `BATTY_*` reflects spawn time. Ids are stable UUIDs so this is fine today; if panes ever move between sessions, the snapshot's pane→session mapping (Option B) is authoritative and the app should resolve session from the pane id, not trust `BATTY_SESSION_ID`.
- **`notify`** is the on-brand "present agent activity" primitive (routes into the existing bell feed + AI summaries) — keep it simple; richer `status`/`progress` pills are Tier 2 (design doc §D), deferred.
- **Out of scope (deferred):** the two-way socket and everything needing it — `list`, `read` (screen), `send`/`send-key`, `wait`, `events subscribe`, and the sidebar activity pills. Also: git/worktree/GitHub/scripts/plugins (off-mission).
- Keep verbs feeling like native actions with keyboard/menu equivalents where sensible; nothing should require a socket to exist for the app to run.

## Verification expectations

- Unit-test the URL build/parse for each new route and the context-resolution logic (env → flag override) — extend the `SessionURLBuilder`/`BattyURLHandler` test pattern from #0250/#0251.
- Unit-test cross-session target resolution: a mutation aimed at a pane in a **non-active session** mutates that session's tree and does not change the active session or focus.
- Unit-test client-generated id flow: the UUID the CLI mints appears in the URL, and the handler creates the object with that id.
- If Option B lands here: unit-test snapshot encode/decode, the atomic write/read round-trip, and the `list --json` output shape.
- `swift run batty <verb> …` builds/parses standalone; `scripts/build.sh unit` + `scripts/build.sh` green; the embedded binary still lands in the bundle.
- The live end-to-end (a verb actually mutating the running app) needs the user's runtime sign-off, like #0250/#0251.
