## Description

Grow the `batty` CLI from "open a session at a path" into a coherent, extensible **`batty <noun> <verb> [flags]`** surface. This ticket **defines the concrete v1 argument surface** and implements the foundation + core mutation verbs — all over the existing one-way `batty://` URL scheme (no socket). Design rationale and the full catalog live in `docs/batty-cli-design.md`; this issue pins the exact arguments to build now.

The recent pane work gives the CLI real things to control: `pane split` distributes evenly (#0255) and panes can be hidden/shown (#0256).

**Revision (2026-07-06):** the primary consumer is an agent (Claude Code) running *inside* a pane. It must be able to open a pane vertical/horizontal to **its own** pane — even when that pane lives in a background session or a non-key window — and it needs a way to learn the surrounding topology (its own ids, sibling panes, hidden panes, other sessions). That drives three additions: explicit target ids carried in every `batty://` URL (Foundation §2), client-generated ids so creation verbs can "return" the new id over one-way IPC (Foundation §6), and the **Agent context & session topology** options section below.

**Converted to an umbrella (2026-07-26).** The execution is decomposed into the children indexed below, following #0265's structure; this file remains the decision record they reference — the grammar, the verb catalog, the behavior rules, and the transport amendments. Where a child now owns a topic, the text below points at it rather than repeating it. This umbrella carries no code of its own; it stays `open` until every child is terminal, and each child's row is updated when the child resolves.

## Transport amendment (2026-07-26) — agent-facing pane mutations move to XPC

#0257 as filed pinned **all** mutations to the one-way `batty://` scheme, conceding the cost directly in Foundation §2: *"an unknown/stale id can only be logged app-side — the CLI can't see the failure."* Since then the #0265 track built and hardened the XPC request/reply channel (broker launch agent, endpoint handoff, lifecycle hardening, peer code-signing validation, and the #0274 read verbs), with the exit-code vocabulary `0`/`1`/`2`/`3`/`4`/`5` defined in `BattyXPCCore/XPCExitCode.swift` and in use.

**The user has decided: agent-facing pane mutations — `pane split` (#0282) and `pane close` (#0283) — go over XPC, not `batty://`.** Rationale: an agent chaining `pane split --pane <id>` must be able to tell a real split from one that hit a stale id, which one-way IPC cannot do; the sharpest form of the concession above is now avoidable, so it should be avoided. **`batty session new` stays on `batty://`**, because it must launch the app when it isn't running — the URL scheme's one unmatched capability (#0265: "wins outright, and it is not close").

Consequences:

- **Foundation §6's client-generated UUIDs become unnecessary for the XPC verbs** — the reply carries the new pane id, which the CLI prints for chaining. They may still be wanted for `session new`, which stays one-way; that call is not decided here.
- Foundation §5's "mutations go over the `batty://` URL scheme" now reads: mutations *default* to `batty://`; verbs whose caller needs the result go over XPC. The remaining Tier 1 verbs keep their pinned transports until amended per-verb.
- The behavior rules are transport-independent and unchanged: split placement relative to the target pane's split tree, and no focus-stealing for background targets.

## Terminology amendment (2026-07-27) — `surface` is an accepted alias for `tab`; the `focus` verbs get defined semantics

Two decisions from the user's terminology review:

**1. `surface` is an accepted alias for the `tab` noun** — an alias, not a replacement and not a separate addressable thing. This supersedes Foundation §1's original flat rejection of `surface`. Rationale (the reason the alias exists at all): a Tab today owns a Terminal Session, but a Tab may host a **web view** or another view type in future. "Terminal Session" is terminal-specific; `tab`/`surface` stay generic across view types — so `surface` earns alias status where `workspace`/`worktree` stay rejected outright. This is consistent with the as-built facts verified under #0281: the Surface registry (`TerminalHostStore.terminalViews`) is keyed by **tab id**, and `BattyContextEnvironmentKey` has exactly three cases — `BATTY_TAB_ID` *is* the surface id, and no `BATTY_SURFACE_ID` is injected. Batty does have a surface concept (`Concepts.md` defines it; the Surface registry is an architectural rule in `CLAUDE.md`); what it does not have is a surface id distinct from the tab id, which is exactly why the alias costs nothing.

**2. `pane focus` and `tab focus` are now defined, not merely listed** — #0257 as filed named both verbs but never specified their semantics. Pinned:

- **`batty pane focus <id>`** — focuses that pane and **leaves the pane's selected tab unchanged**. Moving focus between panes must not re-select tabs.
- **`batty tab focus <id>`** — **selects that tab if it is not already selected**, and implies focusing its containing pane.

Both verbs are **activating**: the standing rule (Foundation §2) that a mutation aimed at a background session must not switch the active session names the `focus` verbs as its explicit exception, and this is that exception spelled out. Focusing a pane or tab whose session is not the selected session **selects that session** (and makes its containing window key, once multi-window exists — the same bring-forward chain as a Bell Feed click-to-jump). Tests must assert the resulting store state — `selectedSessionID`, the target session's `focusedPaneID`, the target pane's `activeTabID` (unchanged for `pane focus`, updated for `tab focus`) — not merely the absence of a crash.

## Foundation (Tier 0 — do first)

1. **Grammar:** `batty <noun> <verb> [flags]`. Nouns: **`session`, `pane`, `tab`, `window`** (+ bare app verbs). `workspace`/`worktree` stay rejected. *(Amended 2026-07-27: this item originally read "No `surface`/`workspace`/`worktree` (Batty's tab *is* the terminal)." The user has since accepted **`surface` as an alias for `tab`** — not a fifth noun, not a separate addressable thing; see the terminology amendment below.)* Keep `batty <path>` working as an alias for `batty session new <path>`.
2. **Context env vars + explicit targets:** inject `BATTY_SESSION_ID`, `BATTY_PANE_ID`, `BATTY_TAB_ID` (≡ surface id) into every surface at spawn. Every child process in the pane inherits them — this is what associates a Claude Code session with its pane. Every context-sensitive verb resolves its target as: explicit `--session/--pane/--tab` flag → else the `BATTY_*` env → else the app's focused element. **The env injection, `whoami`, and the resolution chain are now owned by [#0281](0281.md)** (including the injection-point wrinkles it verified against source). For verbs staying on `batty://`, the CLI embeds the resolved ids as query params in the mutation URL (e.g. `batty://pane/hide?pane=<uuid>`), so the app acts on the *caller's* target, never on "whatever is focused"; app-side, `BattyURLHandler` resolves ids across **all windows and sessions**. Mutating a background target must not steal focus or switch the active session (only the `focus` verbs do that). With one-way IPC an unknown/stale id can only be logged app-side — the CLI can't see the failure. *(Amended 2026-07-26: that concession is exactly why `pane split`/`pane close` moved to XPC — see the transport amendment above.)*
3. **`batty id`** — print the current session/pane/tab **from env alone** (no app round-trip). **Owned by [#0281](0281.md).** *(Naming decided 2026-07-26 by the user: `id` is the primary command name and `whoami` is a supported alias. This ticket originally specified `whoami` only, and older references below still use that spelling — read them as `batty id`. All new help text, output, and docs say `batty id`.)*
4. **Conventions:** global `--json` (reserved for query verbs later), meaningful exit codes, quiet by default. `batty version` / `help` already exist.
5. **IPC decision (pinned, twice amended):** mutations *default* to the **`batty://` URL scheme** (fire-and-forget, no daemon). *(Amended by #0265: the Tier 3 two-way transport is XPC, not a socket; topology reads landed over it in #0274. Amended 2026-07-26: agent-facing pane mutations — `pane split`, `pane close` — go over XPC too; see the transport amendment above.)* Live reads (`read` screen, `wait`, `send`, `events`) stay deferred at the #0265 umbrella level.
6. **Client-generated ids:** creation verbs staying one-way (`session new`, `tab new`) may have the **CLI mint the new object's UUID**, send it in the URL, and print it to stdout — the one-way answer to "I created something; now address it." *(Amended 2026-07-26: unnecessary for the XPC verbs — `pane split`'s reply carries the real new pane id (#0282). Whether `session new` keeps this mechanism is decided when that verb is scheduled, not here.)*

## Verb surface to build (Tier 1)

Concrete arguments. *(The heading originally read "all one-way over `batty://`"; per the transport amendment, `pane split` → [#0282](0282.md) and `pane close` → [#0283](0283.md) are XPC request/reply verbs, and those children own their grammar — including #0282's default-to-horizontal refinement this table predates. `whoami` → [#0281](0281.md). The rest remain `batty://` as listed.)*

```
batty session new [<path>]            # alias: `batty <path>`; defaults to "."; prints new session id
batty session rename <name>           # renames the calling/target session
batty session focus <name|id>
batty session close [--session <id>]

batty pane split [-h|--horizontal | -v|--vertical] [-c|--command <cmd>] [--pane <id>]
                                      # splits the calling/target pane (even 1/n, #0255);
                                      # -c runs a command in the new pane; prints new pane id
batty pane hide [--pane <id>]         # hides the calling/target pane (#0256)
batty pane show <id>                  # restores a hidden pane by id
batty pane focus <up|down|left|right|id>
                                      # focuses the target pane; the pane's selected tab is
                                      # unchanged (pane focus never re-selects tabs); activates
                                      # the containing session/window (terminology amendment)
batty pane zoom [--on|--off|--toggle]
batty pane close [--pane <id>]

batty tab new [-c|--command <cmd>] [--pane <id>]     # new tab in the calling/target pane; prints new tab id
batty tab rename <name>               # renames the calling/target tab
batty tab focus <n|id>                # selects the tab if not already selected; implies focusing
                                      # its containing pane; activates the containing session/
                                      # window (terminology amendment)
batty tab close [--tab <id>]

batty open                            # activate/foreground Batty
batty notify --title <t> [--body <b>] [--sound]   # posts into the bell feed
batty id [--json]                     # prints BATTY_* context (local, no app call); alias: whoami
```

Directional `pane focus` and split placement are computed **relative to the target pane's split tree**, not the screen — so they work identically for a background session. The `focus` verbs' semantics — pane focus leaves the selected tab alone, tab focus selects-if-needed and implies pane focus, both activate the containing session — are pinned in the 2026-07-27 terminology amendment above.

Each `batty://` mutation maps to a route the app handles (extending `BattyURLHandler`), targeting the resolved session/pane/tab; the XPC verbs dispatch through `AppXPCService` instead (#0282/#0283 own that wiring). Reuse existing app methods where they exist: `AppStateStore.renameSession`, `hidePane`/`showPane` (#0256), `focusPane`, `addSession(workingDirectory:)`; add the small ones missing (tab rename, notify-into-feed). The split path (`SplitTree.splitFocusedPane` — still needs the targeted variant this ticket predicted) is verified and owned by [#0282](0282.md); the close cascade by [#0283](0283.md).

## Agent context & session topology — options

The driving use case: Claude Code runs inside a pane and controls Batty around itself. It must (a) know which session/pane/tab it is in, (b) mutate *relative to itself* even when its session is not active, and (c) see enough topology — sibling panes, hidden panes, other sessions — to act intelligently. (a) and (b) are covered by the env vars + explicit-target URLs above. (c) is a **query**, and Tier 1 has no response channel. Options:

- **A. Env only (`whoami`) — in this ticket regardless.** The pane's shell exports `BATTY_*`; every child process (Claude Code, its subshells, `batty` itself) inherits them. Solves identity and self-relative mutations. Gives zero visibility into siblings or other sessions. Free.
- **B. App-maintained state snapshot — recommended; the missing piece.** Batty writes a JSON topology snapshot to a known path (e.g. `~/Library/Application Support/Batty/state.json`) atomically (write temp + rename), debounced, on every layout/focus mutation. Query verbs just **read the file** — no socket, no daemon:
  - `batty list [sessions|panes|tabs] [--json]` — windows → sessions (id, name, path, active) → tabs → pane tree (split axis, hidden, zoomed, focused).
  - `batty session info [--json]` — the calling/target session's slice.
  - Closes the `pane show <id>` discovery gap (hidden panes appear in the listing).
  - Include each tab's **pty device path** so `batty whoami` can fall back to a `ttyname(stdin)` lookup when env is missing (env scrubbed, `sudo`, nested shells) — the robust pane↔process association.
  - Include Batty's **pid** so the CLI can distinguish "Batty isn't running" from a live snapshot.
  - The layout model is already pure Codable value types (`Session`, `Pane`, `Tab`, `SplitNode`), so the snapshot is nearly free; shape the JSON so a future socket's `list` response reuses it verbatim. This is a derived, disposable runtime artifact — *not* Workspace persistence (#0221).
  - Staleness is one debounce interval (~100 ms) — fine for topology; not fine for screen contents or waiting, which stay socket-tier.
- **C. Reply-file/FIFO RPC over `batty://`** (CLI passes a `--reply <fifo>` path; app writes the response). True request/response without a persistent socket, but fragile lifecycle (timeouts, orphaned FIFOs) and it *is* an ad-hoc RPC protocol — if RPC is warranted, a Unix socket is the cleaner spend. **Declined.**
- **D. Pull the Unix socket forward (Tier 3 now).** Full fidelity (`list`, `read`, `wait`, `events`), but a listener, a protocol, and versioning — exactly the complexity this ticket defers. **Stays deferred**; Option B's schema becomes the socket's `list` payload later.
- **E. Apple Events / scripting interface.** Mac-native request/response, but every calling host process trips the Automation TCC prompt — the very permission friction #0254 flags as the thing to reduce for agents. **Declined.**

**Recommendation: A + B.** Scope decision for the user: land B in this ticket as a "Tier 1.5" after the mutations, or file it as its own child ticket of #0254. Suggested: keep this ticket to Tier 0 + Tier 1 (with the target-id and client-id groundwork, which B depends on) and file B as the immediate follow-up — though note `pane show` stays awkward until B ships.

With A + B the agent loop becomes: `batty id --json` (who am I) → `batty list --json` (what's around me) → `batty pane split -v -c '…'` (open a pane next to me, get its id) → `batty notify` (tell the user) — all without a socket, and all correct even when the user is looking at a different session.

## Option B decided (2026-07-25) — dropped

**[#0274](0274.md) implemented the Tier 3 reads over XPC and dropped Option B's JSON topology snapshot.** `batty list [sessions|panes|tabs] [--json]` and `batty session info [--session <id>] [--json]` are live XPC request/reply verbs with no file-based fallback. The transport amendment is [#0265](0265.md): the Tier 3 two-way channel is XPC (broker agent + `NSXPCConnection`), not the raw Unix socket this ticket penciled in at Foundation §5.

Everything below that assumes Option B ships should be read against this. Specifically:

- **§5's "*Topology* queries turn out **not** to need the socket"** is superseded — they do use the two-way channel, which is now XPC.
- **Option D's "Option B's schema becomes the socket's `list` payload later"** is moot; the payload is defined directly in `BattyKit/Sources/BattyXPCCore/TopologyPayload.swift`.
- **The `pane show` id-discovery gap is closed** by the live `batty list` (hidden panes appear in the listing), not by a snapshot file.
- **The `--reply`/FIFO and socket alternatives (C, D) stay declined**, unchanged.

**The pty device path is gone with it.** This ticket conditioned that field on adopting the snapshot schema, so dropping the schema correctly drops the field — but the *need* it served survives: `whoami`'s `ttyname(stdin)` fallback for when the environment is scrubbed (`sudo`, nested shells, env not inherited). No runtime plumbing exposes a tab's pty device path today. **Decided in [#0281](0281.md): `whoami` v1 is env-only** and fails cleanly where the env is missing; the pty plumbing becomes a new child here if that proves painful.

Also relevant to §2's "Env is a hint, not truth": that note said the snapshot's pane→session mapping would be authoritative if panes ever move between sessions. With no snapshot, the authoritative source is a live `batty list` reply.

**The decision is recorded as reversible** — revisit if the approval-gated degraded mode (no XPC until `SMAppService` approval is granted; no XPC at all in Beta until [#0277](0277.md)) proves painful in practice. Full rationale in [#0274](0274.md)'s Resolution notes.

## Notes / decisions

- **Flag vs subcommand:** use subcommands (`batty pane split`) over bare option flags (`batty --split`) so each verb is unambiguous and the surface scales. `swift-argument-parser` (already a dependency) models `<noun>` as a `ParsableCommand` with `<verb>` subcommands cleanly.
- **`pane show` needs an id** (a hidden pane has no shell to run `batty` from). Id discovery is a *query* — resolved: the live `batty list` shipped in #0274 and hidden panes appear in the listing.
- **`-c` on `pane split`** mirrors `tab new -c`: it's the agent primitive "open a pane next to me running X" without needing socket-tier `send`. Same surface-spawn-with-command path as `tab new`.
- **Env is a hint, not truth:** `BATTY_*` reflects spawn time. Ids are stable UUIDs so this is fine today; if panes ever move between sessions, the authoritative pane→session mapping is a live `batty list` reply (the snapshot is dropped — see "Option B decided" above) and the app should resolve session from the pane id, not trust `BATTY_SESSION_ID`. Copied into #0281, which owns the env work.
- **`notify`** is the on-brand "present agent activity" primitive (routes into the existing bell feed + AI summaries) — keep it simple; richer `status`/`progress` pills are Tier 2 (design doc §D), deferred.
- **Out of scope (deferred):** the two-way socket and everything needing it — `list`, `read` (screen), `send`/`send-key`, `wait`, `events subscribe`, and the sidebar activity pills. Also: git/worktree/GitHub/scripts/plugins (off-mission).
- Keep verbs feeling like native actions with keyboard/menu equivalents where sensible; nothing should require a socket to exist for the app to run.
