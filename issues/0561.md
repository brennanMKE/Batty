## Test or app: the app

**The test's setup and assertions are sound.** The decision code shows that a bell from Pane 2 in this state must add a row:

- `WindowRuntime.locate(tabID:)` (`WindowRuntime.swift:1066`) sets `isFocused` per Pane: `session.id == selectedSessionID && session.tree.focusedPaneID == pane.id && pane.activeTabID == tab.id`. Focus is back on the original Pane, so Pane 2's Tab gets `isFocused == false`.
- `AppStateStore.recordBellTick(forTabID:surfaceID:)` (`AppStateStore.swift:1997`) builds the entry with `seen: location.isFocused && isOwnerKey`, so `seen == false`.
- `routeRealTabBell` (`AppStateStore.swift:2610`) drops an entry only when `BellNotifier.evaluateShouldPost(isBattyActive:entrySeen:)` is false. With `entrySeen == false` it returns true whatever `isBattyActive` is. So the unseen entry goes to `bellFeed.recordOrCollapse`, which adds a row to an empty Feed.

**This is not a #0555 regression.** #0555 only added the drop for `seen == true` while Batty is active. An unseen bell takes the same path as before. The failure means `recordBellTick` was never reached, or was reached with a delta of 0. The new test is simply the first to exercise that path.

**Leading hypothesis (not confirmed by a run): nothing tells `PaneView` that the BEL happened.** The only production call to `recordBellTick` is a SwiftUI callback, `.onChange(of: tab.terminal.bellCount)` in `PaneView.swift:265` (and `recordDesktopNotification` the same way, at `:271`). `tab.terminal` is a `TerminalViewState`, a Combine `ObservableObject` with `@Published var bellCount` (libghostty-spm `TerminalViewState.swift:18`). It is held as a plain `let` on the `@Observable` `TabRuntime`, and `PaneView` has no `@ObservedObject` for it. SwiftUI's Observation tracking does not follow `@Published` writes. `TabRuntime.swift:54-70` documents this same staleness for `terminal.workingDirectory`, fixed with an Observation-tracked mirror in #0260 (and the session title in #0227). So `onChange` only sees a new `bellCount` when something else makes `PaneView` re-evaluate its body. In this test nothing does. The script runs `exec sleep 600` after the BEL, and no focus, title or layout change follows. In normal use a prompt redraw, a title change or a click usually re-renders the view soon after, which would hide the problem or show up as a late row.

`TerminalDelegateProxy.terminalDidRingBell()` (`TerminalDelegateProxy.swift:192`) only forwards to `state.terminalDidRingBell()`, which writes `bellCount` in `publishSoon` on the next main turn. Nothing outside the view calls into `AppStateStore`. The unit tests that cover bells (`BellFeedCleanupTests`, `SessionMuteTests`, `BellFeedSeenDropTests` and others) call `terminalDidRingBell()` and then `recordBellTick` themselves, so none of them covers the view-driven step.

**Alternative app-side cause to rule out:** libghostty never delivered `GHOSTTY_ACTION_RING_BELL` for this surface. The callback bridge (`TerminalCallbackBridge.swift:50`) only runs when `ghostty_app_tick` drains the queue. `OccludedSurfaceTicker.swift` (#0288) explains that a surface Batty marks not visible gets no ticks except from that ticker. Pane 2 was visible, and in the recording it is drawn, so this is less likely. The diagnostic below separates the two causes.

## Recommended fix

1. **Confirm the cause first.** Add an `info` log in `TerminalDelegateProxy.terminalDidRingBell()` and at the start of `AppStateStore.recordBellTick` (tab id, observed `bellCount`), then re-run the filter in the VM. If the proxy logs and `recordBellTick` doesn't, the hypothesis holds. If the proxy doesn't log either, the action never arrived (the alternative cause).
2. **If the hypothesis holds,** move bell and desktop-notification intake out of the view. `TerminalDelegateProxy` already knows `tabID`, so it can call the app store directly (an event-origin call from non-view code, allowed by `docs/swiftui-observation-rules.md`). Delete the two `PaneView` `onChange` observers so no bell is counted twice. Watch the #0436 trap: inside the delegate callback `terminal.bellCount` is still the old value, because `publishSoon` defers the write. So `recordBellTickIfNeeded` must not read `terminal.bellCount` synchronously there. Either count in the proxy and pass the delta, or route on the main turn after the publish lands. Apply the same fix to `recordDesktopNotification` (OSC 9 / OSC 777), which has the same view-only trigger. An Observation-tracked mirror of `bellCount` on `TabRuntime`, like #0260, is the smaller change. But it keeps the record step in a view callback, and it still doesn't fire for a Pane that has no `PaneView` (a Session that isn't selected).
3. **Add a unit test** that sends `terminalDidRingBell()` to an unfocused Tab's `TerminalViewState`, or delegate proxy, and expects one Bell Feed entry without calling `recordBellTick` itself. It must signal completion per AGENTS.md "Asynchronous tests", using `awaitTerminalStatePublish` or a completion seam. With today's code it should fail.
4. **Leave the UI test as it is.** It tests the right thing. Once the fix is in, it is the confirmation: re-run `BattyUITests/BellFeedTests/testBellByteProducesFeedEntry` in the VM (UI confirmation tier).
