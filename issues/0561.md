## Test or app: the app

**The test's setup and assertions are sound.** The decision code shows that a bell from Pane 2 in this state must add a row:

- `WindowRuntime.locate(tabID:)` (`WindowRuntime.swift:1066`) sets `isFocused` per Pane: `session.id == selectedSessionID && session.tree.focusedPaneID == pane.id && pane.activeTabID == tab.id`. Focus is back on the original Pane, so Pane 2's Tab gets `isFocused == false`.
- `AppStateStore.recordBellTick(forTabID:surfaceID:)` (`AppStateStore.swift:1997`) builds the entry with `seen: location.isFocused && isOwnerKey`, so `seen == false`.
- `routeRealTabBell` (`AppStateStore.swift:2610`) drops an entry only when `BellNotifier.evaluateShouldPost(isBattyActive:entrySeen:)` is false. With `entrySeen == false` it returns true whatever `isBattyActive` is. So the unseen entry goes to `bellFeed.recordOrCollapse`, which adds a row to an empty Feed.

**This is not a #0555 regression.** #0555 only added the drop for `seen == true` while Batty is active. An unseen bell takes the same path as before. The failure means `recordBellTick` was never reached, or was reached with a delta of 0. The new test is simply the first to exercise that path.

**Leading hypothesis (not confirmed by a run): nothing tells `PaneView` that the BEL happened.** The only production call to `recordBellTick` is a SwiftUI callback, `.onChange(of: tab.terminal.bellCount)` in `PaneView.swift:265` (and `recordDesktopNotification` the same way, at `:271`). `tab.terminal` is a `TerminalViewState`, a Combine `ObservableObject` with `@Published var bellCount` (libghostty-spm `TerminalViewState.swift:18`). It is held as a plain `let` on the `@Observable` `TabRuntime`, and `PaneView` has no `@ObservedObject` for it. SwiftUI's Observation tracking does not follow `@Published` writes. `TabRuntime.swift:54-70` documents this same staleness for `terminal.workingDirectory`, fixed with an Observation-tracked mirror in #0260 (and the session title in #0227). So `onChange` only sees a new `bellCount` when something else makes `PaneView` re-evaluate its body. In this test nothing does. The script runs `exec sleep 600` after the BEL, and no focus, title or layout change follows. In normal use a prompt redraw, a title change or a click usually re-renders the view soon after, which would hide the problem or show up as a late row.

`TerminalDelegateProxy.terminalDidRingBell()` (`TerminalDelegateProxy.swift:192`) only forwards to `state.terminalDidRingBell()`, which writes `bellCount` in `publishSoon` on the next main turn. Nothing outside the view calls into `AppStateStore`. The unit tests that cover bells (`BellFeedCleanupTests`, `SessionMuteTests`, `BellFeedSeenDropTests` and others) call `terminalDidRingBell()` and then `recordBellTick` themselves, so none of them covers the view-driven step.

**Alternative app-side cause to rule out:** libghostty never delivered `GHOSTTY_ACTION_RING_BELL` for this surface. The callback bridge (`TerminalCallbackBridge.swift:50`) only runs when `ghostty_app_tick` drains the queue. `OccludedSurfaceTicker.swift` (#0288) explains that a surface Batty marks not visible gets no ticks except from that ticker. Pane 2 was visible, and in the recording it is drawn, so this is less likely. The diagnostic below separates the two causes.

An Observation-tracked mirror of `bellCount` on `TabRuntime`, like #0260, is the smaller change. It must signal completion per AGENTS.md "Asynchronous tests", using `awaitTerminalStatePublish` or a completion seam. With today's code it should fail.

## Root cause

`PaneView`'s `.onChange(of: tab.terminal.bellCount)` and `.onChange(of: tab.terminal.lastDesktopNotificationAt)` were the only BEL / OSC 9/777 intake. `tab.terminal` is a Combine `ObservableObject` reached through a plain `let`, so Observation tracks no dependency on it. Those observers compared only when something else re-rendered `PaneView`. In the VM test nothing does after the BEL, so the bell never reached the store. This is the code-level cause from the Plan. The VM run that confirms it is still pending (see Verification).

## Plan

Planned 2026-11-05 against `main` at `197e368b`.

### 1. The cause, from the code: settled. No diagnostic VM run first

**`PaneView`'s two intake observers fire only when something else re-renders `PaneView`, and nothing does after this test's BEL.**

- `.onChange(of:)` compares its value only when the body that declares it is re-evaluated. The two observers (`PaneView.swift:265` and `:272`) are declared in `PaneView.terminalBody`, so they compare only when `PaneView.body` runs.
- `PaneView.body` runs again only when something it reads through Observation changes, or its `@State` or environment changes. `tab.terminal` is a plain `let` holding a Combine `ObservableObject`, so `tab.terminal.bellCount` registers no dependency. No view in BattyKit subscribes to Combine: `grep ObservedObject|StateObject|EnvironmentObject|onReceive` finds only `NotificationCenter` `onReceive`s in `SessionDetailView`, `RootWindowView` and `SettingsView`. So a `bellCount` publish never invalidates any view. The same is true of `lastDesktopNotificationAt` and the chip's `tab.terminal.title`.
- These are the things that do re-render `PaneView`: `pane.tabs`, `pane.activeTabID`, `tree.focusedPaneID`/`visiblePanes`, the Tab mirrors the chip reads (`workingDirectory` #0260, `runningCommandDisplayName`, `aiSuggestedName`, `titleOverride`, `unseenBellCount`, `startupCommandWaiting`, `isDragHovering`), `TabRuntime.bellCount`, the environment (`isSelectedSession`, `themeChrome`, `paneAllottedSize`, `windowIsSeeThrough`) and `@State` (geometry, flash, rename).
- **In the VM test, none of them change after the BEL.** The ring script prints `\a`, touches a file, then runs `exec sleep 600`. Nothing changes the cwd, the title, focus or the layout. The last `PaneView` re-render was the `pane focus` before the gate opened, while `bellCount` was still 0. The BEL's publish lands and nothing compares it again.

**Why real bells did reach the store.** In normal use something on that list changes soon after most bells: the user clicks or selects the Session, a `cd` updates the cwd mirror, the window resizes, or a sibling Tab's state changes. That re-render runs the `onChange` late. The entry's timestamp is still the ring instant (`lastBellAt`, #0397), so the delay never shows in the Feed. The user's decision log (`~/Downloads/batty-bell-decisions-2026-11-05-142840.txt`, from #0555) carries the signature of that delay:
- Tab `87274AF3…` has three BEL records with the same `bellAt=2026-11-05T06:35:14Z`. Tabs `7510A228…`, `5F9C5D4B…` and `E41EEF4F…` each have a pair with the same `bellAt`.
- That is exactly what `recordBellTick`'s `0..<delta` loop writes when several BELs pile up on `terminal.bellCount` before one late re-render. Every bell in the delta is stamped with the last one's `lastBellAt`.
- The log has no record-time field, so it can't show how late they were.

There are two consequences:
- `seen` is decided when the late `onChange` runs, not when the bell rang. A bell rung while the user was elsewhere and picked up by the click that visits the Tab is recorded `seen`. Since #0555, Batty drops it while active. Before #0555, those were among the "seen" rows.
- OSC 9/777 can also lose notifications. `recordDesktopNotificationIfNeeded` keeps only the newest `lastDesktopNotificationAt` that a re-render observes.

**The alternative cause** (libghostty never delivered `RING_BELL`) can't be ruled out from code alone. The Pane is visible, so wakeup-driven `ghostty_app_tick` runs. The plan doesn't spend a VM run on it:
- The structural fix is needed whatever the result. The view-driven path is broken by construction, as above.

### 2. Approach: the delegate callback records the bell. No view observer, no `bellCount` read-back

The data flow after the change:

```
libghostty RING_BELL / DESKTOP_NOTIFICATION (inside ghostty_app_tick, main thread)
  -> TerminalDelegateProxy.terminalDidRingBell()            [at = Date() captured here]
       state.terminalDidRingBell()     (unchanged: TerminalViewState publishes later, for anything else that reads it)
       onRingBell?(at)                 (new, synchronous)
  -> TabRuntime.receiveRingBell(at:)   (installed in TabRuntime.init: bellCount += 1, lastBellAt = at, lastBellMessage = nil)
       bellIntake?(self, .bel(count: 1, at: at))  or buffer it while no intake is wired
  -> AppStateStore.recordBell(forTabID:count:at:)
       locate(tabID:) -> entries -> routeRealTabBell (unchanged: #0555 drop, #0298 collapse, #0297 record, #0523 capture)
```

It never reads `terminal.bellCount`, `terminal.lastBellAt` or `terminal.lastDesktopNotification*`. The proxy passes the ring instant, and the title and body, as arguments. That is the #0436 pattern (`applyReportedWorkingDirectory(_:)` takes the reported path rather than reading it back), so `publishSoon`'s deferral no longer matters.

**Observation rules.**
- The writes (`TabRuntime.bellCount`/`lastBellAt`/`lastBellMessage`, `bellFeed`, unseen counters) run synchronously in a libghostty delegate callback. `docs/swiftui-observation-rules.md` names that ("delegate callbacks from outside the UI (PTY events, libghostty delegates)") as a legitimate owner of observed-state writes.
- The callback runs from `ghostty_app_tick`, which is driven by the wakeup `DispatchQueue.main.async`, the display-link tick or `OccludedSurfaceTicker`'s timer. None of these run inside a SwiftUI update or an `NSHostingView` layout pass.
- The pwd callback already writes observed state from the same place (`AppStateStore.applyReportedWorkingDirectory`, #0227/#0436).
- There is no `Task` hop and no `DispatchQueue.main.async` hop.

### 5. User checklist

In Batty Beta:
1. Split a Pane and click back into the left one.
2. In the right Pane run `sleep 5; printf '\a'`, then click into the left Pane before it rings. A Bell Feed row appears **within a second** of the ring without touching anything, and the right Tab's chip shows the unseen dot.
3. Repeat with `printf '\e]9;hello\a'`. The row shows "hello".
4. Ring in the Tab you are looking at. No row (#0555 unchanged).
5. Run `batty notify` to a background Session. Unchanged.
6. Hide a Pane (eye button), ring from it (`sleep 5; printf '\a'` before hiding). A row appears while it is hidden.

**Expected visible change:** bells that used to be picked up late, often at the click that visited the Tab, and then dropped as "seen", now appear as unseen rows when they ring, with a banner when one applies. The Feed may show somewhat more BEL rows than before.
