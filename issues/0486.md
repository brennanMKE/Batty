| | |
|---|---|

| **First seen** | 2026-10-12 |

## Description

User request (2026-10-12), verbatim:

> It is very hard to select a process because that list is very long. It should start with a text field which allows me to type either the name or PID to filter the list. I also want an option to connect and reconnect to a process by name. When I am working on an app or other CLI tool it would help to show the first process which appears on the list and once that PID disappears it should try to find another one to show.

Two gaps in the Process Status Pane, both in the "Choose Process…" flow:

1. **No filter in the running-process picker.** "Pick a Running Process…" opens a popover listing every same-uid process (several hundred on a working Mac), sorted by name, with no way to narrow it. The design doc promised "a searchable list" (`docs/design/process-status-view.md:393`, §2 "Retargeting"); the shipped view is a plain `List` (`ProcessStatusPaneView.swift:227-245`).
2. **No way to follow a process by name.** The Pane's only two targets are a frozen pid and a Terminal Pane's foreground process (`ProcessStatusPaneContent.Target`, `ProcessStatusPaneContent.swift:28-36`). A pinned pid tombstones the instant it exits (`.exited`, sampling cancelled, `:438-446`) and never looks for a successor (by design for mode A, design §2 "On exit: tombstone, not a guessed successor"). That is the right behavior for "watch *this* pid", but when the user is rebuilding and relaunching an app or CLI tool, the pid changes on every run and the Pane is dead after the first one. The user wants a third target: a process **name**, re-resolved to the first live process with that name whenever the one being shown goes away, repeatedly.

**How the picker and sampling work today (verified on `release/1.2` at `13c168d6`; the Process Status sources are byte-identical on `main` at `4b811662` — `git diff --stat release/1.2 main -- BattyKit/Sources/BattyKit/Views/ProcessStatusPaneView.swift BattyKit/Sources/BattyKit/Runtime/ProcessStatusPaneContent.swift BattyKit/Sources/BattyKit/Runtime/ProcessInspector.swift BattyKit/Tests/BattyKitTests/ProcessStatusPaneContentTests.swift BattyKit/Tests/BattyKitTests/ProcessStatusPaneLifecycleWiringTests.swift` is empty).**

- **The picker.** `chooseProcessMenu` (`BattyKit/Sources/BattyKit/Views/ProcessStatusPaneView.swift:194-220`) is a `Menu("Choose Process…")` with `.menuStyle(.button)`, identifier `process-status.choose-process`. Its "Pick a Running Process…" `Button` (`:208-212`) fetches `ProcessInspector.allSameUserProcesses()` once per click, sorts by `name.localizedCaseInsensitiveCompare` ascending, stores the array in `@State runningProcessesCache`, and sets `isPickingProcess = true`, which presents `runningProcessPicker` as a `.popover` (`:217-219`). The popover is a `List(runningProcessesCache)` of plain-style `Button`s (`:227-245`), each `retarget(to: .pinned(process.id))` and dismisses; root identifier `process-status.running-process-picker`; rows have no identifiers. The fetch-only-on-click rule is load-bearing: `body` re-evaluates once a second because it observes `content.snapshot`, so the list must never be built inside `body` or a `Menu` content closure (`:20-33`, review S4 of #0305, measured 2.6-3.6 ms per rebuild for ~470 processes against a ~0.03 ms/tick budget).
- **The enumeration.** `ProcessInspector.allSameUserProcesses()` (`BattyKit/Sources/BattyKit/Runtime/ProcessInspector.swift:342-349`) walks `allPids()` (`proc_listallpids`, `:353-377`), keeps `bsdInfo(pid:).pbi_uid == getuid()` (`:379-387`), and returns `RunningProcess(id:name:executablePath:)` (`:329-333`) with `name` from `bsdName(_:)` (`proc_bsdinfo.pbi_name`, `:389-393`) and `executablePath` from `identity(pid:)` (`proc_pidpath`, `:126-139`). `pbi_name` is `char[2 * MAXCOMLEN]` = 32 bytes (`sys/proc_info.h:73`, `MAXCOMLEN` 16 in `sys/param.h:95`), so names are at most 31 characters and longer executable names are truncated. `proc_bsdinfo` also carries `pbi_start_tvsec`/`pbi_start_tvusec` (`proc_info.h:80-81`), not surfaced today. `proc_listallpids` order is unspecified; the picker's sort does not define an order among equal names.
- **The sampler.** `ProcessStatusPaneContent` (`BattyKit/Sources/BattyKit/Runtime/ProcessStatusPaneContent.swift`) samples on a 1 s loop: `startSampling()` (`:342-358`) takes one immediate `performSample()` and then runs a `Task` that `await clock.sleep(for: interval)` and samples again while `lifecyclePhase == .active`. `clock` is an injected `SchedulingClock` (`:191`, `init(... clock:)` at `:255-260`, default `SystemClock`), and `coreMetricsProvider` (`:180`, `:259`) is the injected per-pid metrics call. `resolveTarget()` (`:366-377`) maps the target to `.pid`/`.noSelection`/`.sourceTabGone`; `performSample()` (`:379-393`) dispatches; `sample(pid:)` (`:395-509`) handles `.success`, `.processNotFound` (→ `.exited`, `cpuTracker.reset()`, cancels `samplingTask`, keeps the last `snapshot`), `.permissionDenied`, and `.unexpected` (→ `.unavailable`, keeps sampling). `retarget(to:)` (`:302-318`) is the only writer of `target`. `startSampling()` refuses to run once `.exited` (`:343`, `:345`).
- **Where targets come from.** `SplitTree.makePane(... processStatusPid:)` (`BattyKit/Sources/BattyKit/Model/SplitTree.swift:331-356`) builds `.pinned` from the CLI's `--pid` or `.followingTab` from the split source; nothing else constructs a target. `Pane` (`BattyKit/Sources/BattyKit/Model/LayoutModel.swift:15-18`) carries only `id`, `isHidden`, `kind`; targets are runtime-only and nothing persists them across relaunch (workspace persistence was removed in #0172).
- **Tests and seams that exist.** `ProcessStatusPaneContentTests` uses `coreMetricsProvider` closures and `sampleNowForTesting()` (`ProcessStatusPaneContent.swift:245-247`); `ProcessStatusPaneLifecycleWiringTests` drives the periodic loop with `TestClock` (`advance(by:)`, `waitForSleepers(_:)`, `pendingCount`; `BattyKit/Tests/BattyKitTests/TestClock.swift`, documented at `Runtime/SchedulingClock.swift:16-19`). UI coverage of the Pane is `CLIViewPaneTests.testSplitProcessStatus*` (`BattyUITests/CLIViewPaneTests.swift:163-246`) and `ViewGalleryTests.testProcessStatus*` (`:364-411`); **no UI test opens the picker today**. `docs/ui-features.md` has no Process Status section on either branch (`git grep -i "process-status" release/1.2 -- docs/ui-features.md` matches nothing; `main` mentions it once in a feature list at `:797`), and Help mentions the view only in `BattyKit/Sources/BattyKit/Help/05-shortcuts.md:24-25,39-44`.

## Expected behavior

### Part 1 — Filter field in the running-process picker

- The popover opens with a `TextField` above the list, placeholder "Filter by name or PID", identifier `process-status.picker.filter-field`. The list narrows as the user types.
- **Matching rule** (decided here): trim whitespace; an empty query shows every row. If the query is all ASCII digits, a row matches when `String(pid).hasPrefix(query)` **or** its name contains the query; an exact PID match is placed first, the rest keep list order. Otherwise a row matches when its name contains the query, case- and diacritic-insensitively (`range(of:options:[.caseInsensitive, .diacriticInsensitive])`), with no reordering. No fuzzy matching: `FuzzyMatcher` (`BattyKit/Sources/BattyKit/Util/FuzzyMatcher.swift`) is for command names; a process name or pid is typed literally, and substring is what distinguishes `node` from `node_helper`. Implement the rule as a pure function (suggested `ProcessPickerFilter.apply(_ query: String, to: [ProcessInspector.RunningProcess]) -> [ProcessInspector.RunningProcess]`, next to `ProcessInspector.swift`) so it is unit-tested without a view.
- **List order** (decided here, shared with Part 2's "first"): name ascending by `localizedCaseInsensitiveCompare` (as today, `ProcessStatusPaneView.swift:210`), then **start time ascending** (`pbi_start_tvsec`, then `pbi_start_tvusec` — add a `startTime` to `RunningProcess` from the `proc_bsdinfo` the enumerator already reads), then pid ascending. Put this comparator on `RunningProcess` (suggested `static func listOrder(_:_:) -> Bool`) so the picker and the follow-by-name resolver cannot drift apart.
- **Keyboard**: the filter field has focus when the popover opens (`@FocusState` set from the picker's `onAppear`, the same view-local pattern `CommandPaletteView.swift:46,131-137` uses; this is SwiftUI-owned focus state, not an `@Observable` write). Down/Up move a highlighted row (view-local `@State`, reset to none whenever the query changes); Return picks the highlighted row, or the first visible row when none is highlighted; Escape clears the query when it is non-empty and dismisses the popover when it is empty. Clicking a row still picks it. Rows get identifier `process-status.picker.row.<pid>`; the list `process-status.picker.list`; the popover root keeps `process-status.running-process-picker`.
- **Empty result**: when the query matches nothing, the list is replaced by "No processes match “<query>”" with identifier `process-status.picker.empty`.
- The fetch stays once-per-open from the `Button` action (the S4 rule above). Filtering runs over the cached array. Extract the popover content into its own `View` struct (suggested `RunningProcessPickerView`) that owns `query`/highlight `@State`, so the parent's once-a-second `body` re-evaluation does not re-filter; the filter over ≤ ~500 rows is microseconds either way, but the structure should make that obviously true.

### Part 2 — Follow a process by name

- **New target** `ProcessStatusPaneContent.Target.followingName(String)` ("mode C", alongside the design's modes A and B). The stored name is the exact `RunningProcess.name` string (the `bsdName`, ≤ 31 characters). A process matches when its `bsdName` **equals** the stored name, case-sensitively — this is the string the picker showed, so what the user chose is what is followed, and a case-insensitive rule would conflate distinct names on a case-sensitive process table. Candidates are same-uid only, as for everything else in this Pane (design §1.5).
- **Turning it on**: a `Toggle("Follow by name")` in the picker's footer, identifier `process-status.picker.follow-by-name`, off on every open. With it on, choosing a row (click or Return) retargets to `.followingName(row.name)` instead of `.pinned(row.id)`. In addition, while the target is `.pinned` and a snapshot exists, the "Choose Process…" menu gains an item "Follow “<name>” by Name" that retargets to `.followingName` using the name resolved through the same `bsdName(bsdInfo(pid))` path the enumerator uses (hidden when that lookup fails), so a user who already pinned the right process does not have to reopen the picker.
- **Turning it off**: while following a name, the "Choose Process…" menu shows "Stop Following by Name": if a pid is currently resolved it retargets to `.pinned(thatPid)`, otherwise to `nil` (No process selected). Picking any other target (a Terminal Pane, or a row with the toggle off) also ends it. `retarget(to:)` stays the only writer of `target`.
- **Which match is "first"**: the first candidate under `RunningProcess.listOrder` above — so for a single name, the longest-running process with that name, then the lowest pid among processes started in the same microsecond. This is literally "the first process which appears on the list" for that name, and it prefers the long-lived main instance over a short-lived helper that happened to share the name.
- **Resolution and the PID-gone event, using the existing sampler and clock; no new timers.** Add a private `followedPid: pid_t?`. In `resolveTarget()`, `.followingName(name)` returns `.pid(followedPid)` when one is held; otherwise it enumerates once (a new `ProcessInspector.firstSameUserProcess(named:)` that walks `allPids()` + `bsdInfo` only, with no `proc_pidpath` per pid — §1.3 measured the full pid list at ~1 ms), stores and returns the match, or returns a new `Resolution.waitingForName` when there is none. In `sample(pid:)`'s `.processNotFound` branch, when the target is `.followingName`: clear `followedPid`, `cpuTracker.reset()`, set `runState = .waiting`, keep `snapshot`, and **do not cancel `samplingTask`** (unlike `.pinned`, which still tombstones exactly as today). The next tick's `resolveTarget()` re-enumerates; the tick that finds a successor samples it, `pidChanged` is true, so `refreshDisclosuresForNewPid()` runs and the pid-keyed `ProcessCPUDeltaTracker` starts a fresh baseline. This repeats for the Pane's life. Enumeration happens only in the waiting state (once per 1 s tick) and once at each (re)resolve; the steady running state does no enumeration, so §4's per-tick budget is unchanged.
- **Waiting state, not an error**: new `RunState.waiting`. The chip reads "Waiting" (`accessibilityValue` `waiting`, identifier `process-status.state-chip` as today). A banner `process-status.waiting-banner` reads "Waiting for “<name>” — no matching process is running", with " — last seen HH:MM:SS" appended from `snapshot?.capturedAt` when a previous sample exists, in which case the dimmed `lastKnownMetricsRow` is shown under it, as for `.exited`. `hasNoSelection` stays `false` while following a name. `startSampling()`'s two `.exited` guards (`:343`, `:345`) are untouched; `.waiting` must never trip them, so hide/show while waiting resumes the loop (and the enumeration).
- **Mode indicator**: `modeIndicator` (`ProcessStatusPaneView.swift:136-153`) gains `Label("Following “<name>”", systemImage: "arrow.triangle.2.circlepath")`; give the indicator identifier `process-status.mode` with `accessibilityValue` `pinned`, `following-tab`, or `following-name`. Update `noSelectionState`'s hint text (`:371-384`) to mention following by name.
- **Persistence**: the followed name lives on `ProcessStatusPaneContent.target` for the Pane's lifetime — it survives hide/show (`setVisible` only suspends and resumes the loop, `:278-288`) and every waiting/reconnect cycle. It is not persisted across relaunch, because no Pane target is (see Description); no `--process-name` CLI flag or `viewOptions` key is added in this issue. If a CLI flag is wanted later it is its own issue, and `AppStateStore.swift:612`'s `--unique` rule ("`viewOptions` differences never defeat the match") already covers it.
- Logging: `.info` lines at each resolve ("followed name=… resolved pid=…"), each loss ("followed name=… pid=… exited, waiting"), through the file's existing `logger`.

## Actual behavior

The picker lists every same-uid process with no filter; finding one means scrolling a list of several hundred rows. The only targets are a frozen pid and a Terminal Pane; a pinned pid shows "Process exited" after the first rebuild and the Pane has to be re-pointed by hand each time.

## Acceptance criteria

- The picker opens with the filter field focused; typing a name substring or a pid prefix narrows the rows per the matching rule; Up/Down/Return/Escape behave as specified; an unmatched query shows `process-status.picker.empty`.
- A row chosen with "Follow by name" on produces `target == .followingName(name)`, the mode indicator reads following-name, and the Pane shows the first matching process under `listOrder`. When that pid exits, the Pane moves to `.waiting` with the banner and keeps its last sample; when a process with that name appears again, the Pane shows it as `.running` with its new pid, and this works for a second and third replacement without any user action.
- `.pinned` behavior is unchanged: it still tombstones to `.exited` and stops sampling (`pinnedTargetTombstonesOnExitAndStopsSampling`, `tombstoningOnTheImmediateSampleNeverSchedulesThePeriodicTask`, and every other existing test in `ProcessStatusPaneContentTests` and `ProcessStatusPaneLifecycleWiringTests` stay green). `.followingTab` is unchanged.
- Hidden Panes still do zero periodic work while following a name or waiting (`aHiddenProcessStatusPaneDoesNotKeepSampling` green, and a waiting-state variant of it).
- **Unit tests** (`./build.sh unit`), with no sleeps, polling, or timing assertions (`AGENTS.md` "Asynchronous tests"; `docs/async-test-seams.md`):

  - `RunningProcess.listOrder`: name, then start time, then pid, with a fixture of equal names.
  - Follow-by-name through seams: inject a name resolver (suggested `nameResolver: @MainActor (String) -> pid_t?` on `init`, defaulting to the real `firstSameUserProcess(named:)`, the same defaulted-real-value shape as `coreMetricsProvider`) and a `coreMetricsProvider` that returns `.processNotFound` for pid A and `.success` for pid B. ## Notes

- Keep the scope to the Process Status Pane (terminal-multiplexer feature; the user's scope rule applies and this is inside it). No CLI flag, no changes to `.pinned`/`.followingTab` semantics, no change to the "Follow a Terminal Pane…" submenu, no refresh button in the picker (close and reopen re-fetches, as today).
- `docs/swiftui-observation-rules.md` is binding. Everything that writes `ProcessStatusPaneContent` state here is event-origin (a row click, Return in the field, a toggle) or sampling-origin (inside `performSample()`/`sample(pid:)`), the two routine cases. The filter query, highlight, and the follow toggle are view-local `@State`/`@FocusState`, never `@Observable` properties. Do not add `Task`/`DispatchQueue.main.async` hops to "wait for the popover" before focusing the field.
- `.permissionDenied` cannot normally occur for a name-resolved pid (the enumerator keeps same-uid processes only); if it does, handle it as today for a resolved pid and keep `followedPid`. `.unavailable` is likewise unchanged and keeps the pid. PID reuse (the kernel handing a dead followed pid to an unrelated process before the next tick) is the same exposure `.pinned` already has and is out of scope.
- `proc_name()` (used by `identity(pid:)` for `snapshot.name`) and `bsdName` (`pbi_name`) read the same kernel name field, but the spec above deliberately routes the "Follow “<name>” by Name" menu item through `bsdName` so the stored name is exactly what the enumerator will compare against; do not store `snapshot.name` for it without checking they are equal.
