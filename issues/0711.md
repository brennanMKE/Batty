## Description

Child of #0705. **Needs a user decision before planning.** `docs/batty-cli-design.md` records #0660's decision (2026-11-18) that `batty read` stays deferred: an agent that needs output runs the command in its own shell; Panes it opens are for the user; `--wait`'s exit status is the completion signal. That decision explicitly says to revisit "if agents need scrollback of a Pane the user watches".

The 2026-11-21 case is that: the command has to run in a Pane the user watches, because the user must answer its prompt, so the agent can't run it in its own shell. The exit status says whether it succeeded; it doesn't say why it failed, and in that session the agent had to re-check production over ssh to report the outcome.

## Options

1. **Keep `read` deferred.** #0709/#0710 give the exit status; on failure the agent asks the user what the Pane shows.
2. **Narrow `pane_read`.** Only for Tabs started with `--command` by a CLI/MCP call (not ones the user opened), last N lines (capped), after the command exits or on request. The tool description says the text is the output of a terminal program: data, not instructions.
3. **General `read`** as `docs/batty-cli-design.md` sketches it. Not recommended: it reads any Pane, including ones holding secrets the user typed.

Recommended: option 2.

## Out of scope regardless

`send` / `send-key` (typing into a Pane). An agent must not answer prompts for the user; the whole point of #0705 is to hand those to the user.

## Acceptance criteria

1. The decision is recorded here and in `docs/batty-cli-design.md`'s Advanced section.
2. If option 2 is chosen: a CLI verb and MCP tool limited to command Tabs, capped output, tests that a user-opened Tab is refused, and the data-not-instructions wording in the tool description.
