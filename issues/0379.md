## Description

The topology an agent reads over XPC — `batty list [sessions|panes|tabs] [--json]` and `batty session info [--session <id>] [--json]` — describes every Pane as if it were a terminal. `TopologyPanePayload` (`BattyKit/Sources/BattyXPCCore/TopologyPayload.swift`) carries `id`, `isHidden`, `isFocused`, `activeTabID`, `tabs`, and the optional `frame`/`visibleRect`, and **no `kind` field**. Since #0304/#0305/#0313/#0314 shipped real Git Status, Process Status, LM Studio dashboard, and System Metrics views, a Session can hold five materially different kinds of Pane and the CLI reports all five identically.

The consequence for an agent driving Batty on a developer's behalf: it can open a `git-status` Pane, but it can never find that Pane again. It cannot avoid opening a duplicate, cannot close-by-kind, cannot ask "does this Session already show build status?", and cannot distinguish a view Pane from a terminal Pane in `batty list --json` at all. Every downstream CLI capability that needs to *discover* what it previously created is blocked on this one missing string.

This is not new scope invented here. `PaneContentKind`'s own doc comment (`BattyKit/Sources/BattyXPCCore/PaneContentKind.swift`) declares the enum to be "deliberately **one string used identically in three places**: the Codable `Pane.kind` raw value, the CLI `--view` flag value, and (should a future issue extend it) the `TopologyPanePayload.kind` JSON value — `docs/pane-kinds.md` §5, 'one string, three call sites, zero translation table to keep in sync.'" Two of the three legs shipped with #0315. This issue is the third, which was never filed.

## Expected behavior

- `TopologyPanePayload` gains `kind: PaneContentKind`.
- `batty list --json` and `batty session info --json` emit it for every Pane (`"kind": "terminal"`, `"git-status"`, `"process-status"`, `"lm-studio-dashboard"`, `"system-metrics"`).
- The plain-text renderers in `ListCommand.swift` and `SessionInfoCommand.swift` show it too, alongside the existing `hidden` / `focused` flags, so a human reading `batty list panes` sees the same truth as `jq`.
- Acceptance: an agent can pipe `batty session info --json` through `jq` and select the Pane whose `kind == "git-status"`.

## Actual behavior

Every Pane in the payload looks like a terminal Pane. The only hint that a Pane is non-terminal is indirect and unreliable (a non-terminal `PaneRuntime` keeps one structural `TabRuntime` that no view renders — see #0315's "The scope decision, and what it cost").

## Notes

- **The data is already in hand.** `PaneRuntime.kind` exists (`BattyKit/Sources/BattyKit/Runtime/PaneRuntime.swift:50`) and `Pane.kind` is Codable (`BattyKit/Sources/BattyKit/Model/LayoutModel.swift:18`). No model change is needed — only the payload field and its population.
- **Correction to the population site.** The obvious guess is `AppStateStore.topologyPayload` (`AppStateStore.swift:341`), but that is only the entry point; the Pane leaf is actually built in `BattyKit/Sources/BattyKit/XPC/TopologyPayloadBuilder.swift` — `PaneRuntime.topologyPayload(isFocused:includeDimensions:)` at `:128`, constructing `TopologyPanePayload` at `:165`. That is the one line to extend. `AppStateStore.sessionInfoPayload` (`:375`) shares the same builder, so both verbs are covered by the single change.
- **Make the wire change additive.** Decode `kind` leniently — default to `.terminal` when the key is absent — matching the rule `Pane.init(from:)` already establishes (`LayoutModel.swift:35-39`: `decodeIfPresent(...) ?? .terminal`). That keeps a newer CLI readable against an older app and vice versa, which matters because the CLI binary ships inside the app bundle but a user's `/usr/local/bin/batty` symlink can point at a stale bundle.
- **`PaneContentKind` already lives in `BattyXPCCore`** alongside `TopologyPayload.swift`, so the payload can reference the enum directly with no new dependency and no string table.
- The `TopologyPayload` doc comment lists two fields (`zoom`, pty device path) as deliberately absent with a rationale. Add `kind` to that comment's story as *now present*, rather than leaving a reader to infer that it was another deliberate omission.
- **Wire-contract tests exist** — `TopologyPayloadTests.listJSONTopLevelKeysAreStableNotCompilerSynthesized` freezes the JSON shape. Extend those, don't work around them.

## Resolution notes

> 🟢 Resolved 2026-09-03 — `batty list --json` and `session info --json` now
> report each Pane's `kind`, so an agent can tell a terminal Pane from a view
> Pane, find one it opened, and avoid opening a duplicate.

## Root cause

`TopologyPanePayload` carried `id`, `isHidden`, `isFocused`, `activeTabID`,
`tabs` and optional geometry — but no `kind`. `PaneContentKind`'s own doc
comment reserved `TopologyPanePayload.kind` as the third leg of its "one
string, three call sites" design, and that leg was never filed or built.

## Fix

`kind` added to the payload, populated in `PaneRuntime.topologyPayload`, and
surfaced in both the JSON and plain-text renderers for `list` and
`session info`. Values are `PaneContentKind`'s existing kebab-case raw
strings — `terminal`, `git-status`, `process-status`, `lm-studio-dashboard`,
`system-metrics` — so `jq 'select(.kind == "git-status")'` works.

**`kind` is optional, and that is the substantive decision here** (user,
2026-09-03). Absent, explicit `null`, and *unrecognised* raw values all decode
to `nil`, rendered as `kind=unknown`. `.terminal` was the originally specified
default and is wrong on this wire: non-terminal Panes shipped in
#0304/#0305/#0313/#0314, *before* this issue, so every installed build —
including the Prod app in daily use — sends no `kind`. Since
`ListCommand.printJSON` re-encodes the decoded struct, defaulting would make
the CLI *emit* `"kind": "terminal"` for a git-status Pane, asserting on the
app's behalf something it never said, and #0383's find-or-create would then
treat a view Pane as a terminal. The `LayoutModel.Pane.init(from:)` analogy
does not transfer: there, an absent kind genuinely predates non-terminal
Panes existing at all.

## Review

Reviewed by `claude-opus-5` over two rounds. Round 1 requested changes and
escalated the optional-vs-default decision rather than settling it. Its
blocking find was a robustness bug: `decodeIfPresent(PaneContentKind.self, …)`
tolerates only absent/null, so a *present but unrecognised* value threw
`DecodingError.dataCorrupted` — and because `AppServiceClient.perform` decodes
with `try?`, one unknown kind on one Pane collapsed the entire response into a
generic failure, leaving the agent with nothing rather than one wrong field.
Verified empirically with a standalone probe, not inferred. The tolerance had
to ship in the *stale* binary, since adding it after a sixth kind exists
cannot repair CLIs already installed — the same now-or-never argument the
absent-key case had already won, applied to the other axis. Two doc comments
were also corrected, one of which claimed a custom `init(from:)` suppresses
`encode(to:)` synthesis, which is false.

The reviewer also confirmed no pane-bearing surface was missed —
`PaneSplitReply` carries only the new id, `PaneCloseReply` is empty, and
`watch --topo-snapshot` carries no pane data — so this is not a partial
rollout.

## Verification

`./build.sh unit` — 1295 tests in 146 suites passed, run by both the
implementer and the reviewer independently. Four tests carry the contract:
absent key decodes to `nil`, an unrecognised raw value decodes to `nil`
(hand-built JSON, so it genuinely exercises the fallback rather than
round-tripping through the encoder), a non-terminal kind round-trips, and the
real builder reports the true kind per Pane end to end through
`AppStateStore`/`PaneRuntime`/`SplitTree`.

## Gotchas

- **`kind=unknown` is expected against any currently installed Batty**, not a
  bug. It means the app predates #0379. It resolves once the app is rebuilt.
- **A non-terminal Pane's `activeTabID` still names an id absent from `tabs`.**
  `kind` explains *why* `tabs` is empty but does not close that dangling
  reference; #0315 deliberately kept `activeTabID` non-optional, naming the
  unrendered structural Tab. `docs/pane-kinds.md` §5 proposes making it
  optional and flags the open question of whether consumers tolerate
  key-present-with-`null` — a wire decision left unmade.
- **`LayoutModel.Pane.init(from:)` has the same unknown-raw-value throw** this
  issue fixed on the XPC payload. Lower stakes — it decodes the app's own
  snapshot — but it is the obvious second user if this ever becomes a shared
  helper.
- Neither plain-text renderer has test coverage; both are `private static`.
  Pre-existing, and `docs/batty-cli-agent-workflows.md:176` tells automation
  not to parse that output anyway.
