## Description

`SMCThermalReader.read()` walks the CPU-temperature candidate key list (`Tp09`, `Tp0T`, `Tp01`, `Tp05`, `TC0P`) from the top on every call, attempting each key against the SMC until one resolves. Which key a given Mac answers to never changes while the machine is up, so the walk only needs to happen once. The degenerate case is the expensive one: on a Mac where **no** candidate resolves, every 1 Hz tick re-tries all five keys — each attempt being a key-info request plus a read request — for 10 wasted IOKit round trips per second, forever, to learn the same "unavailable" answer. (The connection is also opened and closed per tick, which the same caching pass could fold in.)

Related gap worth recording in the same issue: the candidate list itself is model-specific and has been verified against exactly one machine (an Apple Silicon Mac mini M4, where `Tp09` resolves). The reader's own doc comment carries this caveat from the design doc as known, unresolved future work. A fix here should cache the resolution result (including the negative result), and can widen or reorder the list if better data is available — but list curation is secondary to not re-walking it.

## Expected behavior

The first successful resolution (or the first full-miss) is remembered for the process lifetime; subsequent ticks read the one known-good key directly, or skip the temperature read entirely when the machine is known not to expose one.

## Actual behavior

Every tick walks the full candidate list from scratch; a no-temperature Mac pays 10 IOKit round trips per second indefinitely.

## Resolution notes

> 🟢 Resolved 2026-09-23 — `SMCThermalReader` remembers which temperature key answers (or that none does) for the life of the pane's sampler, so a steady-state tick reads one key instead of walking all five candidates.

Deliberate narrowing: the cache lives for one pane show, not the process lifetime the issue asked for, because #0350 rebuilds the sampler on every show. One walk per show, not per tick.

## Root cause

`read()` walked its five CPU-temperature candidates (`Tp09`, `Tp0T`, `Tp01`, `Tp05`, `TC0P`) from scratch every tick: up to ten IOKit round trips per second.

## Fix

- `SMCTemperatureKeyCache`, owned by the `SystemMetricsSampler` actor: `.unresolved` → `.resolved(key)` or `.unavailable`.
- Probes return `.value` / `.definitivelyAbsent` (`smcResult == 0x84`, SMC's key-not-found, or a wrong data type/size) / `.transientFailure` (transport errors, other result codes, out-of-range decodes). `.unavailable` is cached only when every candidate is definitively absent.
- A walk hit by a transient failure retries next tick, bounded: after three consecutive inconclusive walks the cache settles on `.unavailable` for the show. A resolved key that fails three ticks in a row triggers one re-walk; during that grace period the reading is `(nil, nil)`, so key and value stay consistent.
- Per-tick SMC connection open/close is unchanged. `docs/design/system-metrics-view.md` §4 documents the cache and its rules.

## Gotchas

- A transient failure on a higher-priority candidate followed by a value from a lower one locks the cache onto the lower key for the show.
- A key that alternates between a value and three failures re-walks about every four ticks, indefinitely. By design: every success is a real reading.
