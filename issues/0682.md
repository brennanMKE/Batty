## Description

Child of #0680. The agent page (#0683) must show copy-paste MCP setup for Claude Code, Codex, Cursor and OpenCode, plus the global-instructions prompt, and those snippets must match what `batty agent install` writes byte for byte. Today the entries are inline literals inside `plan`, so there is nothing to render them from.

### Current state (checked against `main` at `3a7c12ec`)

- OpenCode entry (`mcp.<key>`: `type: "local"`, `command: [<cli>, "mcp"]`, `enabled: true`) and Cursor entry (`mcpServers.<key>`: `command`, `args: ["mcp"]`) are built inline at `BattyKit/Sources/BattyCLICore/AgentGuidanceInstaller.swift:253-279`.
- Claude Code is registered through a staged local marketplace: `claude plugin marketplace add <dir>` and `claude plugin install <plugin>@<marketplace>` (lines 239-250). The plugin's `.mcp.json` entry is another inline literal in `stageMarketplace` (lines 382-384), and the SessionStart hook command comes from `sessionStartHookCommand(cliExecutablePath:)` (lines 401-402).
- Codex: `CodexConfigBlock.lines(key:cliCommandName:command:)` (`BattyKit/Sources/BattyCLICore/CodexConfigBlock.swift:23-31`) is already a function, but `internal`, and `block(identity:)` takes a full `AgentGuidanceIdentity`. It writes `env_vars` for `BATTY_SESSION_ID`, `BATTY_TAB_ID`, `BATTY_PANE_ID` (line 16).
- Every entry uses `identity.cliExecutablePath`, the app-bundle path (`AgentGuidanceIdentity.swift:61`). A web snippet must use the bare command name, `batty` (on `PATH` after Settings → Install CLI puts it in `/usr/local/bin`, `BattyKit/Sources/BattyKit/Settings/CLIInstaller.swift:127`).
- The global-instructions prompt is `AgentGlobalInstructionsPrompt.text` (`BattyKit/Sources/BattyCLICore/AgentGlobalInstructionsPrompt.swift:36`).
- `git grep "claude mcp add"` finds nothing: the manual Claude Code form is undocumented.

## Expected behavior

1. **Reusable renderer.** A public `AgentMCPConfigSnippets` (name up to the plan) in `BattyCLICore` returns, for a given server key and CLI command (path or bare name), the OpenCode entry, the Cursor entry, the Claude Code plugin `.mcp.json` entry and the Codex block. `plan` and `stageMarketplace` call it instead of their inline literals, so the installer's output is unchanged byte for byte (existing installer tests keep passing unmodified).
2. **Manual Claude Code form.** The renderer also produces `claude mcp add --scope user batty -- batty mcp` (exact form checked against current Claude Code docs in the plan), documented as the alternative when the user doesn't want the plugin.
3. **Website snippet files.** A generator writes one file per snippet under `website/docs/snippets/`: `claude-code-plugin.txt` (`batty agent install`), `claude-code-mcp-add.txt`, `codex-config.toml`, `cursor-mcp.json`, `opencode.json`, `global-instructions-prompt.txt`. JSON snippets show the whole file shape a user pastes (`{"mcpServers": {...}}`), pretty-printed with the same encoder options the installer uses. Recommended generator: a `--print-config <host>` option on `batty agent install` (also useful to users), driven by `tools/build-agent-snippets.sh`, which writes the files and has `--check`. The plan may choose a small SwiftPM executable target instead if the flag-gated `agent` noun makes the CLI route awkward before #0669.
4. **Drift test.** A BattyKit unit test (`AgentMCPConfigSnippetsSiteTests`) renders every snippet with the bare name `batty` and compares it byte for byte with the committed file under `website/docs/snippets/`, locating the repo root from `#filePath`. It fails with the regenerate command in its message.
5. All new website files are covered by `website/.deploy-hold` (#0681's `docs/` entry).

## Acceptance criteria

1. `./build.sh` and `./build.sh unit` pass; the existing `AgentGuidanceInstaller` tests pass without edits to their expectations.
2. Changing any entry builder (or `AgentGlobalInstructionsPrompt.text`) without regenerating makes `AgentMCPConfigSnippetsSiteTests` and the generator's `--check` fail.
3. Each committed snippet uses `batty`, never an app-bundle path, and the Codex snippet carries `env_vars` for all three `BATTY_*` variables.

## Root cause

Feature work. Each host's MCP entry was an inline literal in `AgentGuidanceInstaller.plan`/`stageMarketplace` (OpenCode, Cursor, plugin `.mcp.json`) and `CodexConfigBlock`, with no shared renderer and no published copy to keep in sync.

New pure `AgentMCPConfigSnippets` (BattyCLICore) builds the OpenCode and `mcpServers` entries, the Codex block (via `CodexConfigBlock.lines`), the `claude mcp add` and `agent install` commands, and fresh-file JSON bytes (`AgentGuidanceInstaller.freshConfigData`, sharing a new `encodeConfig` with `mergeMCPEntry`/`removeMCPEntry`). The installer and `CodexConfigBlock.block` now call it; no behavior change. `siteFiles()` renders six files, written into `website/docs/snippets/` by the new `BattyAgentSnippets` executable target through `tools/build-agent-snippets.sh` (`--check` exits 1 on drift). As planned; `shellQuoted` was made `internal` rather than moved.

Manual Claude Code form `claude mcp add --scope user batty -- batty mcp` checked against `claude mcp add --help` (Claude Code 2.1.329, scratch HOME/CLAUDE_CONFIG_DIR, PATH=/usr/bin:/bin): `Usage: claude mcp add [options] <name> <commandOrUrl> [args...]`, `-s, --scope <scope> (local, user, or project)`, example `claude mcp add my-server -- my-command --some-flag arg1`; stdio is the default transport.

## Plan

Premises checked: line numbers in "Current state" still match (`AgentGuidanceInstaller.swift:289-317` for the OpenCode and Cursor entries, `:459-461` for `.mcp.json`, `:478-480` for the hook command; `CodexConfigBlock.lines` is `internal` at `:23`). `website/docs/` and `website/.deploy-hold` do not exist yet: #0681 is still `open`.

### Decisions

1. **Generator: a small SwiftPM executable target, not `--print-config`.** `agent` is only in the CLI tree when `FeatureFlags.agentIntegration` is on (`BattyCLI.swift:33-35`, off in Prod), and `AgentInstallCommand.run()` refuses to run outside `Batty.app` (`AgentCommand.swift:34-40`). A `--print-config` flag would therefore need a built, bundled Beta CLI to regenerate files, which a doc tool should not. A new target `BattyAgentSnippets`, depending only on `BattyCLICore`, runs with `swift run` and no app. `--print-config` can be added later on top of the same renderer if users ask; it is out of scope here.
2. **Prod name only.** Every committed snippet uses `batty` (`isBeta: false` names: key `batty`, command `batty`). No `batty-beta` files; #0683 tells Beta users to substitute.
3. **Byte-for-byte means "what `agent install` writes into a fresh file".** JSON snippets are the bytes `mergeMCPEntry` writes when the config file does not exist yet (the `JSONEncoder` path, `[.prettyPrinted, .sortedKeys, .withoutEscapingSlashes]` plus a trailing `\n`), not `entryText`'s `JSONSerialization` path, which may format differently. The Codex snippet is what `CodexConfigBlock.merge(existing: nil, ...)` writes, so it **keeps the `# batty:begin` / `# batty:end` markers**. A user who pastes it and later runs `batty agent install` gets `.unchanged` or an in-place replacement, not the "unmarked [mcp_servers.batty] table" conflict.
4. **Manual Claude Code form:** `claude mcp add --scope user batty -- batty mcp`. Options go before the server name and `--` separates the server command (Claude Code MCP docs, `code.claude.com/docs/en/mcp`; the implementer re-checks the form there and records the check in `## Verification`). `--transport stdio` is the default and is omitted. No `env` options: Claude Code starts stdio servers with the parent's environment, so the `BATTY_*` variables arrive without forwarding (unlike Codex). This form gives the MCP server only, not the skill or SessionStart hook; #0683 says so.

4. **New target `BattyKit/Sources/BattyAgentSnippets/main.swift`** and an `.executableTarget(name: "BattyAgentSnippets", dependencies: ["BattyCLICore"], swiftSettings: swiftSettings)` in `BattyKit/Package.swift`. Not added to `products` (root-package executable targets are runnable with `swift run` anyway); do not touch `Batty.xcodeproj`. ### How #0683 consumes the files

#0683's `docs/index.md` generator (stdlib Python, `tools/`) inlines each file between generated-section markers such as `<!-- snippet: codex-config.toml -->` … `<!-- /snippet -->`, inside a fenced block with the matching language (`toml`, `json`, `sh`, `text`). It also links the raw files at `/docs/snippets/<name>` for copying. Its own `--check` compares those sections with the files, so the chain is code → snippet files (this issue's test and `--check`) → `index.md` (#0683's `--check`). The photon MIME map for `.toml` is checked in #0683 or #0685.
