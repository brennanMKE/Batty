# 0587 — `./build.sh unit` takes minutes because it builds far more than the BattyKit tests it runs

## Description

User report: "Unit tests should not take several minutes to run. They should be very fast."

`./build.sh unit` usually takes 3–4 minutes, but the tests run in under 8 seconds. Almost all of the time goes to compiling. Implementers and reviewers run it many times for each issue, so it is the largest share of agent wall time. In the 2026-11-11 session it took about 30 of 108 subagent minutes.

## Steps to reproduce

1. In an issue worktree, change one BattyKit source or test file.
2. Run `./build.sh unit <Suite>`, or plain `./build.sh unit`.
3. Time the run, and compare the log's `SwiftCompile` lines with the "Test run with … passed after …" line.

## Expected behavior

- After a small change, `./build.sh unit <Suite>` finishes in seconds.
- A full `./build.sh unit` finishes in well under a minute.
- The output stays the same: the `CHECK UNIT: PASSED|FAILED|ERROR` line, exit codes 0/1/2, zero tests run counts as an error, the Haiku failure digest, and `-only-testing`-style filters (`<Suite>`, `'<Suite>/<test>()'`).

## Notes

- Related: #0588 (umbrella: split BattyKit into modules with protocol interfaces and per-module test targets, the structural fix behind this one).

### Where the time goes (checked on `main` at 8d30d89)

- **The scheme builds the app and its tests.** `build.sh` (`unit)` case, around line 235) runs `xcodebuild test -workspace Batty.xcworkspace -scheme "Batty (Beta)" -only-testing:BattyKitTests…`. `-only-testing` limits which tests run, not what gets built. `Batty (Beta).xcscheme` has a `buildForTesting = "YES"` entry for the `Batty` app and two testables, `BattyKitTests` and `BattyTests`. The cold run `000202` compiled, grouped by target: `BattyKitTests-product` 344, `ArgumentParser` 94 (+25 `ArgumentParserToolInfo`), `batty` 65, `batty-product` 57, `BattyTests` 43, `Batty` 20.
- **The test target depends on the CLI executable.** In `BattyKit/Package.swift`, `BattyKitTests` depends on `"BattyKit", "batty"` and `ArgumentParser`. That puts the CLI and swift-argument-parser in every unit build, and the log shows the CLI compiled twice (`batty` and `batty-product`).
- **The test target recompiles in full.** In the warm runs `000946` and `001847`, 292 of the 293 compiles were in `BattyKitTests-product`. That is essentially every file in `BattyKit/Tests/BattyKitTests/` (286 files, ~59k lines, one module). The cause isn't known yet. Possibilities: a BattyKit interface change invalidating every importer, the compilation mode, testability settings, or the test module's size. Neither `Configuration/*.xcconfig` sets `SWIFT_COMPILATION_MODE` or `ENABLE_TESTABILITY`, so the defaults apply.
- **Each worktree starts cold.** Each `issue/NNNN` worktree gets its own DerivedData. Five `Batty-*` folders exist now, about 1.2–1.4 GB each, plus `BattyKit-*` from a package-level build. A new worktree's first unit run builds all package dependencies and the app from scratch.

### Directions for the planner (none chosen)

- Run BattyKit tests without the app scheme: a BattyKit-only scheme in the workspace, or `swift test` in `BattyKit/`. `AGENTS.md` says `cd BattyKit && swift test` works. Check whether that's still true and whether the libghostty-spm xcframeworks, `GhosttyTerminal` resources, or `.process("Resources")` / `.copy("Fixtures")` block it. Check too whether the output contract (xcresult, Swift Testing summary parsing in `run_check`) can be kept.
- Drop the `batty` dependency from `BattyKitTests` if the tests only need `BattyCLICore`/`BattyXPCCore`, or move the CLI tests to their own test target.
- Find out why the whole test target recompiles after a small change. Use `-driver-time-compilation` or `-Xfrontend -debug-time-function-bodies`, or compare a test-only edit with a BattyKit-source edit. Consider splitting the test module.
- Warm a new worktree's DerivedData, by seeding it from `main`'s or by using a shared `-derivedDataPath`. Parallel worktrees building into one DerivedData can collide (`AGENTS.md` and `Issues.md` run one implementer at a time, but a reviewer and the orchestrator may overlap).
- Measure before and after: cold, warm with no change, warm after a one-line BattyKit edit, and warm after a one-line test edit. Do this for filtered and full runs.

### Constraints

- `build.sh` at the repo root is not a restricted area. `scripts/` and `Configuration/Build.xcconfig` are (`AGENTS.md` "Restricted areas"), so changing either needs the user's confirmation.
- Update the timing claims in `AGENTS.md` ("Fast (<30 s)") and `CLAUDE.md` to match whatever is measured.
