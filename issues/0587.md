## Description

User report: "Unit tests should not take several minutes to run. They should be very fast."

`./build.sh unit` usually takes 3–4 minutes, but the tests run in under 8 seconds. Almost all of the time goes to compiling. Implementers and reviewers run it many times for each issue, so it is the largest share of agent wall time. In the 2026-11-11 session it took about 30 of 108 subagent minutes.

## Resolution notes

> 🟢 Resolved 2026-11-12 — `./build.sh unit` now runs through a BattyKitTests-only workspace scheme, so it no longer builds the app, `BattyTests` or their dependencies: ~3.6 s warm with no change (was 10.6 s), ~52 s for the full suite (was 64–66 s).

## Review

Round 1: approved first pass. The scheme XML is minimal (empty `BuildAction`, no pre-action, one `BattyKitTests` testable with the same `BuildableReference` as `Batty (Beta)`, plus a plain `LaunchAction`), and `xcodebuild -list -workspace Batty.xcworkspace` lists `BattyKit Unit Tests`. Only the `unit)` case changed; `build`, `run`, `release`, `package`, `ui`/`test` (delegates to `tools/run-ui-tests-vm.sh`, which uses `Batty UI Tests`), `ui-typecheck` (`swiftc -typecheck`) and the passthrough don't use `UNIT_SCHEME`. The `AGENTS.md` timings match the reviewer's run. Minor, not blocking: `docs/batty-cli-install.md:1102` still says `./build.sh unit` is "<30 s", which holds for filtered runs only; the comment at `tools/run-ui-tests-vm.sh:499` explaining why `Batty (Beta)`'s Test action was narrowed still reads correctly as history.

## Root cause

`./build.sh unit` ran `xcodebuild test` with the `Batty (Beta)` scheme. `-only-testing` limits which tests run, not what gets built, so every run planned, built and checked the `Batty` app, `BattyTests` and the CLI, about 7 s on a no-change run and 7–12 s more on warm runs. The multi-minute runs were full `BattyKitTests` recompiles (296 files), which happen when a BattyKit source file is added, removed or renamed, made worse by parallel-agent load. Edits and new internal declarations recompile only a few files (see `## Plan`). That structural cost is #0588's to fix.

## Fix

As planned. A new shared workspace scheme, `Batty.xcworkspace/xcshareddata/xcschemes/BattyKit Unit Tests.xcscheme`, has no build entries, no pre-action and a single `BattyKitTests` testable. `build.sh`'s `unit)` case uses it through `UNIT_SCHEME`. Filter parsing, `-only-testing`, the xcresult path, `run_check`, exit codes and `select_variant Beta` (Active.xcconfig snapshot/restore) are unchanged. No deviation from the plan.

## Plan

### What the measurements show (2026-11-12, this worktree, M4 10-core, Xcode 27.2, load average 13–15 from other agents)

"Kit scheme" is an experimental workspace scheme whose only testable is `BattyKitTests`, with no build entries. It was created for the timing runs, then deleted. | Warm, no change | **10.6 s** | **3.6 s** | 1.7 s |

| Warm, add a new test file | 23 s, 3 compiles | — | — |
| Warm, **add a new BattyKit source file** | **47 s, 308 compiles (296 in `BattyKitTests`)**, 487 % CPU | — | — |
| Full suite, warm, no change | 64–66 s, 3755 tests | 52 s, 3755 tests | — |

Findings:

1. **The issue's premise about recompiles is only partly right.** Cross-module incremental builds work. A body edit or a new internal declaration in BattyKit recompiles 3–6 files, not the whole test target, and so do test-file edits and new test files. The full `BattyKitTests` recompile (296 files) happens when a source file is **added to, removed from, or renamed in** the `BattyKit` module, which is common in feature work. That is the 292/293 case in `## Actual behavior`. Run on a machine loaded by parallel agents (its CPU time is 222 s), it becomes the 3–4 minute runs. Build settings can't fix this. `@testable import` plus one 286-file test module that imports one 227-file library is the structure #0588 replaces.
2. **The app scheme adds about 7 s to every run**, even a no-change run (10.6 s vs 3.6 s), and 7–12 s to warm runs that compile something. Most of that is planning, building and checking the `Batty` app, `BattyTests` and the `batty`/`batty-product` CLI. Cold, the app adds almost nothing, because a cold run is dominated by the packages, BattyKit and the test target.
3. **For full runs, the floor is test execution, not compilation.** The full suite's Swift Testing run takes ~36 s ("Test run with 3755 tests in 363 suites passed after 35.782 seconds"), so a full run can't get "well under a minute" from build changes alone. The issue's "tests run in under 8 seconds" holds only for filtered runs.
4. **A cold run is ~80 s, not minutes.** The global `~/Library/Developer/Xcode/DerivedData/CompilationCache.noindex` already exists, so cold builds are cheaper than the per-folder sizes suggest.

### Decisions

- **(1) Adopt: a BattyKit-only shared workspace scheme for `./build.sh unit`.** This is the measured win (3× on no-change runs, ~8 s on every warm run). It keeps `xcodebuild`, so the `.xcresult`, the `-only-testing` filter syntax, `check-report.py`'s parsing (`ST_RUN` and the xcresult summary are identical, confirmed in the r6 log) and the shared DerivedData with `./build.sh` all stay as they are.
- **`swift test` rejected as the `unit` path.** Its warm times are about the same (1.7 s vs 3.6 s no-change, an equal 19 s after an edit), but it has no `.xcresult`, `Suite/test()` filters would have to be translated into `--filter` regexes, and it keeps a second 1.4 GB `.build/` per worktree, which is cold the first time in every worktree. The claim in `AGENTS.md` that `cd BattyKit && swift test` works was confirmed (11 tests passed), so it stays documented as an alternative.
- **(2) Defer: moving the CLI tests to their own test target.** It's feasible: the 11 files that `@testable import batty` (`ColdLaunchEndpointResolverTests`, `AppConnectDanceTests`, `SessionCommandOpenURLTests`, `CapabilitiesCommandTests`, `FetchPreDispatchStateTests`, `SessionRemindCommandTests`, `ProjectCLITests`, `CapabilitiesInputSchemaTests`, `NewSessionCommandExitMappingTests`, `AgentSkillFlagDriftTests`, `NewSessionCommandTests`) import none of BattyKit. But with (1) in place, `batty` and ArgumentParser cost time only on cold runs (~240 of ~1170 cold compiles), and warm runs don't touch them. A second testable means `build.sh` has to route each `<Suite>` filter to the right target, which puts the filter contract at risk for little gain. Recorded for #0588, where per-module test targets are the plan anyway.
- **(3) Reject: seeding DerivedData by APFS clone.** Cold is ~80 s, and the build database and intermediates are keyed on absolute source paths, so a clone of `main`'s `Batty-*` folder would rebuild almost everything in a worktree at a different path. Only the package checkouts would be reused. Sharing one live DerivedData across concurrent worktrees is unsafe (the reviewer and orchestrator overlap). Not worth a step in the orchestrator workflow.
- **(4) Out of scope here: the full recompile when a file is added.** Splitting `BattyKitTests` into a few test targets by area would not help, because each one still `@testable import`s all of BattyKit and would also recompile fully when a BattyKit file is added. Only splitting the *library* (#0588) fixes it. Recorded on #0588.
- **Not planned: profiling the 36 s full-suite execution.** If it's wanted, it's a separate issue (slow or MainActor-serialized suites). `xcresulttool`'s per-test durations are wall-clock from the start of the run, so they don't single out the slow suites. That would need its own investigation.

## Notes

### Where the time goes (checked on `main` at 8d30d89)

- **The scheme builds the app and its tests.** `build.sh` (`unit)` case, around line 235) runs `xcodebuild test -workspace Batty.xcworkspace -scheme "Batty (Beta)" -only-testing:BattyKitTests…`. `-only-testing` limits which tests run, not what gets built. `Batty (Beta).xcscheme` has a `buildForTesting = "YES"` entry for the `Batty` app and two testables, `BattyKitTests` and `BattyTests`. The cold run `000202` compiled, grouped by target: `BattyKitTests-product` 344, `ArgumentParser` 94 (+25 `ArgumentParserToolInfo`), `batty` 65, `batty-product` 57, `BattyTests` 43, `Batty` 20.
- **The test target depends on the CLI executable.** In `BattyKit/Package.swift`, `BattyKitTests` depends on `"BattyKit", "batty"` and `ArgumentParser`. That puts the CLI and swift-argument-parser in every unit build, and the log shows the CLI compiled twice (`batty` and `batty-product`).
- **The test target recompiles in full.** In the warm runs `000946` and `001847`, 292 of the 293 compiles were in `BattyKitTests-product`. That is essentially every file in `BattyKit/Tests/BattyKitTests/` (286 files, ~59k lines, one module). The cause isn't known yet. Possibilities: a BattyKit interface change invalidating every importer, the compilation mode, testability settings, or the test module's size. Neither `Configuration/*.xcconfig` sets `SWIFT_COMPILATION_MODE` or `ENABLE_TESTABILITY`, so the defaults apply.
- **Each worktree starts cold.** Each `issue/NNNN` worktree gets its own DerivedData. Five `Batty-*` folders exist now, about 1.2–1.4 GB each, plus `BattyKit-*` from a package-level build. A new worktree's first unit run builds all package dependencies and the app from scratch.

- Run BattyKit tests without the app scheme: a BattyKit-only scheme in the workspace, or `swift test` in `BattyKit/`. `AGENTS.md` says `cd BattyKit && swift test` works.
