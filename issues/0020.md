## Description

Keyboard-only navigation through panes. Two related sets of shortcuts:

- **Cmd-Option-arrows** move focus between Panes within the active Session (Concepts → Pane → "Focus movement").
- **Cmd-Ctrl-arrows** resize the Split containing focus by ±5% in the indicated direction.

**Acceptance criteria:**
- Cmd-Option-Left / Right / Up / Down move focus to the spatially-adjacent Pane in that direction.
- Movement is geometric, not tree-order: Cmd-Option-Right moves to the Pane immediately right of the focused one, regardless of how the split tree is shaped.
- If no Pane exists in that direction, the keypress is a no-op.
- Cmd-Ctrl-Left / Right / Up / Down resize the relevant split divider by ±5%.
- Cmd-Ctrl-Up shrinks a vertical split's top child; Cmd-Ctrl-Down expands it (analog for horizontal). Document the convention in code so it's consistent.
- Both sets of shortcuts appear in the menu bar.

## Notes

- The geometric algorithm for Cmd-Option-arrows: from the focused Pane's frame, find the candidate Pane whose frame is on the indicated side and whose center is closest to the source's center.
- Cmd-Ctrl-* may collide with macOS Mission Control / Spaces shortcuts on some user setups. Document the conflict if it arises; we don't change Apple's defaults.

### Deferred — 2026-05-08

Geometric "find pane to my right" requires per-pane on-screen frames, which means each `PaneView` needs to publish its frame upward via `PreferenceKey` or `onGeometryChange`, and `SplitContainerView` (or a coordinator above it) needs to maintain a `[UUID: CGRect]` map. Same pattern needed by SwiftUI to do the spatial lookup `Cmd-Option-Right → "the pane whose frame's left edge is just right of the focused pane's right edge, vertical center closest to the focused pane's vertical center"`.

That's not impossible, but it's a meaningful chunk of SwiftUI plumbing (PreferenceKey, frame publication, coordinator state) and the result is heavily interactive — wrong-direction movements, edge cases at deeply nested splits, etc. all need visual verification.

Cmd-Ctrl-arrows for split resize have the same blocker as #0019: they need the custom split view that owns the ratio (so resizing the focused-pane's enclosing split is well-defined). Deferring both pieces of #0020 until #0019 lands.

In the meantime, the user can click on any pane to focus its terminal (GhosttyTerminal handles per-surface focus natively). Keyboard-only navigation of the split tree is the missing piece, deferred.

### What's left

1. `PaneView` publishes its frame via `.onGeometryChange(for: CGRect.self) { ... }` writing into an env-value or coordinator.
2. `AppStateStore` (or a per-window coordinator) holds the `[paneID: CGRect]` map.
3. New `SessionRuntime.focusPane(adjacentTo:direction:)` method consumes the map.
4. `BattyCommands` adds a "View" or "Pane" submenu with Cmd-Option-arrows wired.
5. After #0019 lands, Cmd-Ctrl-arrows that resize the split containing focus by ±5% are similarly straightforward.

## Phase 2 fix — `1a46393` (focus movement only; resize keys deferred)

Geometric pane focus shipped. New `BattyKit/Sources/BattyKit/PaneFocus.swift` defines `PaneFocusDirection`, `PaneFrameTracker` (plain class, not `@Observable`), `PaneFramePreferenceKey`, and `SessionRuntime.focusPane(adjacent:)`. `SessionRuntime` gains an `@ObservationIgnored let paneFrames = PaneFrameTracker()` so frame publication doesn't trigger view re-renders. `PaneView` publishes its frame in the `"session"` coordinate space via `.preference(...)` in a `.background { GeometryReader { ... } }`. `SessionDetailView` collects via `.coordinateSpace(name:)` + `.onPreferenceChange(...)`. `BattyCommands` Pane menu gains four Cmd-Option-Arrow buttons.

`xcodebuild build` passes; 43 BattyKit tests still passing.

### Why split-resize half is still deferred

Cmd-Ctrl-Arrow split-resize needs to identify the **enclosing split** of the focused pane and bump its ratio by ±5%. With `#0019`'s `id`-bearing `.split` cases this is doable — walk the tree to find the split whose left or right subtree contains `focusedPaneID`, call `tree.updateRatio(forSplitID:to:)` with `currentRatio ± 0.05`. Direction-to-axis: Left/Right resize the nearest enclosing horizontal split; Up/Down resize the nearest vertical split.

Skipping for this commit because (1) the "find the nearest enclosing split with a given axis" walk is non-trivial when splits are nested, and (2) visual verification matters more here than for focus (a wrong resize is more disruptive than a wrong focus jump). Filing as a follow-up.

## Gotchas

- **Visual verification needed.** Create a session with 4 panes. Cmd-Option-Right from top-left → top-right. Cmd-Option-Down → bottom-right. At the leftmost pane, Cmd-Option-Left should be a no-op. Resolved-not-closed.
- **`@ObservationIgnored`** is what prevents the `PaneFrameTracker` from triggering re-renders on every layout pass. Without it, every drag would tank performance.
- **Frames are published in the `"session"` coordinate space**, established at the `SplitContainerView` level. Frames are relative to the session's content area — the right space for "is pane B to the right of pane A?". For window/screen-space frames (e.g. for click-to-jump from system notifications later), a different publishing path is needed.
- **The scoring function favors perpendicular alignment** with a small parallel-axis tiebreaker (`weight = 0.1`). Tunable in `score(from:to:direction:)`.
- **Cmd-Ctrl-Arrow split-resize is deferred.** The keybindings are unbound for now.
- **Click-to-focus is still missing.** Clicking inside a non-focused pane doesn't update `focusedPaneID`. GhosttyTerminal handles per-surface keyboard focus, so typing works, but the model's `focusedPaneID` stays where the keyboard last left it. Worth a follow-up: a `.simultaneousGesture(TapGesture())` on `PaneView` that sets the focused pane.
