# 0361 — The batty CLI launches another instance of the app instead of connecting to the running one

| | |
|---|---|
| **Status** | open |
| **Module** | App |
| **Platform** | macOS |
| **First seen** | 2026-08-22 |

## Description

**User-reported, reproduced by the user, top priority.** Running the `batty` CLI while Batty is already running launches another instance of the app instead of connecting to the one that is running. In the user's words:

> "I do no tkno whow to give you any data because the CLI tool KEEPS LAUNCHING ANOTHER INSTANCE!!! What the fuck?! This is garbage."

This is severe on two counts. First, it is wrong on its own: the CLI's connect dance is designed to launch the app only when no app is running (`docs/xpc/xpc-cli-architecture.md`, "Launching the app on demand"), and here the app *is* running. Second, it **blocks all other diagnosis**: every `batty` command the user runs to inspect state may be talking to a different process than the one they are looking at. #0362 (a Pane-count discrepancy reported in the same session) may be caused or masked by this — the visible Panes and the counts the CLI reports could come from different processes.

## Steps to reproduce

Exact sequence not yet captured. What is known from the user's report:

1. Batty is running (`/Applications/Batty.app`, launched 2026-08-21 20:21).
2. The user runs `batty` commands (which verbs, and which `batty` on `PATH`, not yet confirmed).
3. Another instance of the app launches instead of the command connecting to the running instance. The user reports this happening repeatedly ("KEEPS LAUNCHING").

## Expected behavior

When Batty is already running, every `batty` verb connects to that running instance. The launch-on-demand path fires only when no instance is running, and never produces a second instance alongside a live one.

## Actual behavior

`batty` commands launch additional app instances while the app is already running, repeatedly.

## Investigation

## Notes

### Hypotheses to test

1. **A connection-failure path that launches the app.** The launch mechanism exists and is unconditional on a broker miss: `AppConnectDance.resolveEndpoint` (`BattyKit/Sources/batty/AppConnectDance.swift`) asks the broker for the app's endpoint and, on a miss, calls `AppLauncher.launch` (`BattyKit/Sources/batty/AppLauncher.swift`), which runs `/usr/bin/open -b <bundleID> -g`. If the running app's endpoint registration is missing from the broker the CLI talks to — for any reason — every verb takes the launch path. The broker starting fresh on 2026-08-22 14:27, ~18 hours after the app, is suggestive here: if a broker restart loses the app's registration and the app does not re-register, every subsequent connect dance hits the miss path and launches. To be confirmed by the diagnostic agents, not assumed.
2. **Prod vs Beta bundle-id mismatch** (`co.sstools.Batty` vs `co.sstools.Batty.beta`). `ServiceNames` (`BattyKit/Sources/BattyXPCCore/ServiceNames.swift`) derives both the broker Mach service name (`<bundleID>.broker`) and the launch target from the variant compiled into each binary. A CLI and app built under different variants would rendezvous with different brokers and launch a different bundle id. `CLAUDE.md` documents the `Configuration/Active.xcconfig` trap where the next build silently produces the other product.
3. **XPC peer code-signing rejection** between an ad-hoc-signed dev build and a Developer-ID-signed release build (`BattyKit/Sources/BattyXPCCore/PeerCodeSigningRequirement.swift`, `OwnCodeSigningIdentity.swift`, `OutgoingCodeSigningEnforcement.swift`), where the rejection presents to the CLI as "no app registered" and falls through to a launch.
4. **A stale `/usr/local/bin/batty`** (2026-08-21 14:04) whose wire expectations no longer match the running app or broker.

### Existing context

- #0315 added the typed-pane CLI verbs and documents the XPC wire; #0282 (`pane split`) and #0283 (`pane close`) established the XPC mutation-verb pattern; #0257's transport amendment pinned `batty session new` to `batty://` *specifically because* it must be able to launch the app when it isn't running — launch-on-demand is deliberate design for the not-running case, which makes launching alongside a running instance the defect.
- `docs/batty-cli-install.md`, `docs/batty-cli-design.md`, `docs/xpc/xpc-cli-architecture.md` (see "Launching the app on demand"), and `docs/xpc/` generally.
- Related: #0362 — the Pane-count discrepancy reported in the same session; if the user's CLI commands were creating Panes in a second instance, that discrepancy may have no counting bug behind it at all. The two issues cross-reference each other.

## Investigation findings (2026-08-22)

Every path, line number, and environment fact below was re-verified against the
working tree and the live machine before being written down. Where a claim
handed to this filer did **not** survive verification, it is flagged as a
correction rather than repeated. Nothing here launched the app or ran `batty`.

### Corrections to the existing text above

- **`/usr/local/bin/batty` is a symlink, not a standalone copy.** The
  "Observed data" section's `ls -l` output reads as a 4,822,320-byte regular
  file, but `readlink` and `stat` disagree with that reading:

  ```
  readlink /usr/local/bin/batty
    → /Applications/Batty.app/Contents/Resources/bin/batty
  stat -f "%HT" /usr/local/bin/batty
    → Symbolic Link
  ```

  This is exactly the documented design (`docs/batty-cli-install.md` step 1:
  "a **symlink** (not a copy) to `<Batty.app>/Contents/Resources/bin/batty` —
  installed by `CLIInstaller.install()`"), and `CLIInstaller.swift`
  (`BattyKit/Sources/BattyKit/Settings/CLIInstaller.swift:89-92`) checks
  `FileAttributeType == .typeSymbolicLink` on the install path. The size and
  date `ls -l` printed are the *target's*. **Hypothesis 4 in Notes ("a stale
  `/usr/local/bin/batty`") is therefore ruled out structurally**, not merely
  by hash: the CLI on `PATH` cannot drift from the installed app because it
  *is* the installed app's embedded CLI.
- **The "byte-identical" hash finding is tautological.** `/usr/local/bin/batty`
  and `/Applications/Batty.app/Contents/Resources/bin/batty` both hash to
  `818a69bcca0ebc5002d3ac105f9020b2b20816d26627e37a8b18b0c0bad30e1a` because
  the symlink resolves to the same inode. True, but it proves nothing beyond
  the symlink.
- **The four view kinds did not all merge on 2026-08-22.** Notes above (and
  #0362) say "the four view-kind merges of 2026-08-22 (#0304, #0305, #0313,
  #0314)". Actual commit timestamps on `main`: #0314 `aca515a` 2026-08-21
  23:11:13, #0313 `b6ae529` 2026-08-21 23:35:46, #0305 `9d6c511` 2026-08-22
  00:04:05, #0304 `6b48df2` 2026-08-22 00:34:31. Two landed on the 21st. This
  does not change the conclusion (the installed app predates all four) but the
  date should not be repeated as written.

### Cause 1 — confirmed from code, log evidence not independently re-verified

The exhaust-and-give-up reconnect path is real and reads as described:

- `AppXPCCoordinator.handleBrokerSignal`
  (`BattyKit/Sources/BattyKit/XPC/AppXPCCoordinator.swift:209-218`) clears
  `isRegisteredWithBroker`, then `guard reconnectBudget.consumeAttempt() else`
  logs `"broker … — reconnect budget exhausted this launch, not retrying
  automatically (a future CLI call may still recover it)"` and returns without
  scheduling any retry.
- `BrokerReconnectBudget`
  (`BattyKit/Sources/BattyKit/XPC/BrokerReconnectBudget.swift`) is
  `init(maxAttempts: Int = 5)`; `consumeAttempt()` decrements and returns
  `false` once `remaining` hits 0; `reset()` restores the full budget and its
  doc comment states it is "called on a confirmed registration (the broker
  actually answered `brokerPing`)". So: **5 attempts per launch, refilled only
  by a confirmed registration.** Confirmed.
- `AppConnectDance.resolveEndpoint`
  (`BattyKit/Sources/batty/AppConnectDance.swift:50-60`) treats
  `.endpoint(.none)` — broker reachable, nothing registered — as "no app
  registered", logs `"resolveEndpoint: no app registered, launching …"`, and
  calls `launch(ServiceNames.appBundleIdentifier)`.
- `AppLauncher.launch`
  (`BattyKit/Sources/batty/AppLauncher.swift:17-31`) runs
  `/usr/bin/open -b <bundleIdentifier> -g`. Confirmed.
- **No single-instance guard exists.** `Configuration/Info.plist` has no
  `LSMultipleInstancesProhibited` key (verified by enumerating every `<key>`
  in the file), and `NSRunningApplication` appears nowhere in
  `BattyKit/Sources` or `Batty/`. Nothing prevents `open -b` from producing a
  second live process. Confirmed.

**Not re-verified:** the earlier capture of three instances in 90 seconds
(pids 54285, 54501, 54665). `log show --predicate 'process == "Batty"'
--last 8h` returns **zero** lines on this machine now, so that evidence could
not be reproduced from the unified log at filing time. It is recorded as the
diagnostic agents captured it, not as something this filer confirmed.

### Cause 3 — NEW, and the most direct mechanism found: `batty` on `PATH` resolves to the app's own executable

`/Applications/Batty.app/Contents/MacOS` **is on the user's `PATH`** (entry 20
of 22), which is why the report's `which -a batty` listed a second hit. That
second hit is not a CLI:

```
$ shasum -a 256 /Applications/Batty.app/Contents/MacOS/Batty \
                /Applications/Batty.app/Contents/MacOS/batty
ce0cadd2cbed0e9ad2dfcad5feee39892b1796c155fb4e0b0a121b395bc6461d  …/MacOS/Batty
ce0cadd2cbed0e9ad2dfcad5feee39892b1796c155fb4e0b0a121b395bc6461d  …/MacOS/batty
```

`ls -la Contents/MacOS/` lists exactly one file, `Batty` (29,465,536 bytes).
The volume is case-insensitive, so **`Contents/MacOS/batty` and
`Contents/MacOS/Batty` are the same file — the app's main executable.** The
real CLI is 4,822,320 bytes and lives in `Contents/Resources/bin/`.

**Confirmed:** the `PATH` entry exists, and the name `batty` resolves there to
the app binary. **Hypothesis, not confirmed:** that this is what the user hit.
Today `/usr/local/bin` precedes `/Applications/Batty.app/Contents/MacOS` in
`PATH`, so `batty` resolves to the symlinked CLI. But if that ordering is ever
reversed — a different shell init, a login vs. non-login shell, a `PATH`
rebuild inside a Batty-spawned shell, or `/usr/local/bin/batty` momentarily
absent during a reinstall — then typing `batty` **directly executes the app's
main binary**, which starts a brand-new `NSApplication` process every single
time, with no broker handshake, no `open -b`, and no LaunchServices dedupe.
That mechanism matches "KEEPS LAUNCHING ANOTHER INSTANCE" more exactly than
either cause above, and it would also explain instances that appear and
terminate without servicing anything.

This `PATH` entry does **not** come from the repo: `grep` over
`BattyKit/Sources`, `Batty/`, `scripts/`, and `docs/` finds no code or script
that adds `Contents/MacOS` to `PATH`, and it is absent from `~/.zshrc`,
`~/.zprofile`, `~/.zshenv`, `~/.bash_profile`, `~/.profile`, `/etc/paths`, and
`/etc/paths.d/*`. Its origin is unknown and worth asking the user about.

### What this implies for the fix (scope, not decided design)

Resolving the app by bundle identifier alone is ambiguous on any developer
machine, and resolving the *CLI* by bare name on `PATH` is ambiguous while the
app's `MacOS` directory sits on `PATH`. Options worth weighing, none chosen:

- Resolve the endpoint by the **absolute bundle path** of the app the CLI was
  installed from — the symlink already encodes it, so the CLI can read
  `/proc`-equivalent self-path and walk up to its own `.app`.
- **Verify the resolved app's bundle path and version before launching**, and
  refuse (or warn) on a mismatch.
- Prefer an **already-running** `NSRunningApplication` over any launch.
- Make the CLI **report which app bundle it connected to**, so this is
  diagnosable rather than silent.
- Housekeeping: prune stale LaunchServices registrations
  (`lsregister -kill -r -domain local -domain system -domain user`), and decide
  whether **debug builds should carry a distinct bundle id** so they never
  compete with the installed app.
- Consider whether `Contents/MacOS` belongs on `PATH` at all, and whether a
  case-insensitive collision between the app binary and the CLI name is worth
  designing out (e.g. by not naming them the same word modulo case).

### Ruled out with evidence — do not re-investigate

- **A stale `/usr/local/bin/batty`** (Notes hypothesis 4) — it is a symlink
  into the installed bundle; it cannot be stale relative to the app it points
  at.
- **Prod/Beta bundle-id confusion in the binary the user invoked** (Notes
  hypothesis 2) — the installed CLI resolves to the Prod app's embedded CLI.
  Note this rules out the *binary*, not the *registration*: six bundles still
  claim the beta id, one of them named `Batty.app`.
- **XPC peer code-signing rejection** (Notes hypothesis 3) — all Developer ID,
  same team, same notarization timestamp; logs showed the peer requirement
  succeeding.
- **Broker service unavailability** — `launchctl` showed it running and
  reachable; the broker is alive as pid 54667.
