## Description

**User-reported, reproduced by the user, top priority.** Running the `batty` CLI while Batty is already running launches another instance of the app instead of connecting to the one that is running. In the user's words:

> "I do no tkno whow to give you any data because the CLI tool KEEPS LAUNCHING ANOTHER INSTANCE!!! What the fuck?! This is garbage."

This is severe on two counts. First, it is wrong on its own: the CLI's connect dance is designed to launch the app only when no app is running (`docs/xpc/xpc-cli-architecture.md`, "Launching the app on demand"), and here the app *is* running. Second, it **blocks all other diagnosis**: every `batty` command the user runs to inspect state may be talking to a different process than the one they are looking at. #0362 (a Pane-count discrepancy reported in the same session) may be caused or masked by this — the visible Panes and the counts the CLI reports could come from different processes.

## Resolution notes

> 🟡 Implemented 2026-08-22 across three rounds on `issue/0361-1`, awaiting re-review. Two of the three causes recorded in `## Investigation findings` below are fixed: **Cause 1** (the reconnect budget's permanent give-up) via a self-healing capped backoff retry, and **Cause 2** (bundle-identifier collision — up to ten bundles sharing `co.sstools.Batty`/`.beta`) via resolving the target app by absolute bundle **path** everywhere the CLI decides what to launch or check, including the default `batty`/`batty <path>` verb, which round 1 and round 2 had missed (review round 1's blocking finding, B1). **Cause 3** (`Contents/MacOS` on `PATH` shadowing the real CLI with the app's own main binary, filed as a separate issue) is **not addressed here** — it is an app-side `PATH`-injection question outside this issue's CLI-connect-dance scope, and the fix below does nothing for it. A previously-added `LSMultipleInstancesProhibited` (`Configuration/Info.plist`) was **reverted** after review — see `## Fix` — because its actual scope (per-identifier vs. per-path) is undocumented, and reviewed as likely useless-or-harmful in this specific multi-claimant environment. Not yet set `resolved` — that is the reviewer's call, and end-to-end verification against the live app could not be performed (see `## Gotchas`).

## Root cause

Three independent causes, matching the numbering in `## Investigation findings` below (not "two defects" as an earlier draft of this section said):

1. **Cause 1 — the reconnect budget gave up permanently.** `AppXPCCoordinator.handleBrokerSignal` (`BattyKit/Sources/BattyKit/XPC/AppXPCCoordinator.swift`) clears `isRegisteredWithBroker` on every broker interruption/invalidation and only retries while `BrokerReconnectBudget` (capped at 5, refilled only by a confirmed `brokerPing` round trip) has attempts left. Once exhausted it logged and gave up for the rest of the process's life — no timer, no periodic retry, nothing short of relaunching the app to bring registration back.
2. **Cause 2 — bundle-identifier collision.** `AppConnectDance.resolveEndpoint` treated "broker reachable, no endpoint registered" as grounds to launch via `AppLauncher.launch`, which ran `open -b <bundle-id>` — and `co.sstools.Batty` is claimed by up to ten distinct bundles on a development machine (DerivedData debug builds from every `scripts/build.sh` run, stale unmounted-DMG registrations, the installed app). LaunchServices' resolution among them is not something this CLI controls, so even a correct "don't launch when running" decision (Cause 1's fix) still risked launching, or believing it found, the wrong bundle. **Round 1 fixed this for six of the CLI's seven entry points into `AppConnectDance`; round 3 (review finding B1) found the CLI's default verb — bare `batty` / `batty <path>`, the most-typed invocation — used a wholly separate, unfixed code path (`SessionCommand.swift`'s `openURL`) that still resolved by bundle identifier.** See `## Fix`.
3. **Cause 3 — `Contents/MacOS` on `PATH` shadows the real CLI (not fixed by this issue).** `/Applications/Batty.app/Contents/MacOS` sits on the user's `PATH`, and the volume's case-insensitivity makes `Contents/MacOS/batty` resolve to the same file as `Contents/MacOS/Batty` — the app's 29 MB main executable, not a CLI. If that `PATH` entry ever precedes `/usr/local/bin` (a different shell init, a login vs. non-login shell, `/usr/local/bin/batty` transiently absent during reinstall), typing `batty` launches a brand-new `NSApplication` directly — no broker handshake, no `open`, no LaunchServices dedupe, nothing this issue's fix touches. This matches the user's "KEEPS LAUNCHING ANOTHER INSTANCE" report at least as well as causes 1–2 and is being tracked as a separate issue; nothing in `## Fix` below addresses it.

## Fix

**Causes 1 and 2, entry points 1–6 of 7 (round 1–2).** `AppConnectDance.resolveEndpoint` (`BattyKit/Sources/batty/AppConnectDance.swift`) no longer treats "no endpoint registered" as "safe to launch" unconditionally. It first resolves the target app **by absolute bundle path**, via the new pure type `AppBundleResolution` (`BattyKit/Sources/BattyXPCCore/AppBundleResolution.swift`, unit-tested) and its filesystem/AppKit glue `AppBundleLocator` (`BattyKit/Sources/batty/AppBundleLocator.swift`): the embedded CLI always lives at `<bundle>/Contents/Resources/bin/batty`, and the installed `/usr/local/bin/batty` is a symlink straight into it (confirmed live on the reporting machine: `readlink /usr/local/bin/batty` → `/Applications/Batty.app/Contents/Resources/bin/batty`), so resolving symlinks on the CLI's own `argv[0]` and stripping that suffix identifies the target bundle with **zero LaunchServices involvement** — no ambiguity possible, regardless of how many bundles claim the identifier. Only a standalone CLI copy that is neither the embedded binary nor a symlink to it falls back to the well-known per-variant `/Applications` path, and only after `AppBundleLocator` confirms that path actually exists; if it doesn't, the CLI fails with a message naming the expected path and any other bundles a read-only `mdfind` query finds claiming the identifier (never `lsregister -kill`/`-r` — that stays the user's own, manual call) — a new `AppConnectDance.Failure.appBundleUnresolved` / `XPCExitCode.appBundleUnresolved` (`7`).

Given that resolved bundle, `RunningAppChecker.isRunning(atBundleURL:)` (`BattyKit/Sources/batty/RunningAppChecker.swift`) checks `NSWorkspace.shared.runningApplications` for a process whose own `bundleURL` matches — "is *this exact* bundle running", not "does anything anywhere claim the identifier" — and `AppLauncher.launch(bundleURL:)` (`BattyKit/Sources/batty/AppLauncher.swift`) runs `open <path> -g` (no `-b`), so launching is deterministic. The pure `isAppRunning` → launch-or-wait branch (`NoEndpointRegisteredDecision`) is unchanged from round 1: not running → launch and poll; running-but-unregistered → poll for re-registration and report a distinct `appRunningUnregistered` / exit `6` on timeout, never launching a duplicate.

**Cause 2, entry point 7 of 7 — review round 1 finding B1 (round 3, blocking).** `BattyCLI`'s `defaultSubcommand` (bare `batty` / `batty <path>`, `NewSessionCommand`) never went through `AppConnectDance` at all — it built the `batty://` URL and called `SessionCommand.swift`'s `openURL`, which ran `open -b <bundleIdentifier>` directly, untouched by rounds 1–2. `openURL` now resolves via the same `AppBundleLocator.resolve()` used everywhere else and runs `open -a <bundlePath> <url>` instead of `-b <bundleIdentifier>`. `-a <path>` is strictly stronger than `-b <id>` for the reason `-b` was added in the first place (#0279: keep the shared `batty://` scheme registration from resolving to the wrong Prod/Beta variant) — a path names one exact bundle, so #0279's guarantee holds and the identifier-collision risk is closed. On resolution failure this reports the same `appBundleUnresolved` / exit `7` as every other verb.

**Cause 1 recoverability (round 2).** `AppXPCCoordinator` gained a self-healing backoff retry: a new pure schedule type `BrokerReconnectBackoff` (5s, 10s, 20s, 40s, capped at 60s thereafter) and `SingleSlotRetryScheduler` (`BattyKit/Sources/BattyKit/XPC/SingleSlotRetryScheduler.swift`, unit-tested), a generic "replacing a pending handle always cancels the previous one" primitive guaranteeing repeated give-up events (several broker signals in a row, a repeated repair failure) schedule exactly one pending reconnect attempt, never one per event. Two give-up points now call `scheduleBackoffRetry()` instead of only logging and giving up: `handleBrokerSignal`'s reconnect-budget-exhausted branch, and `attemptRepairIfNeeded`'s "repair already attempted this launch" branch. Deliberately **not** wired into `attemptRepairIfNeeded`'s `SMAppService.state != .enabled` branch — that means the user hasn't opted into the broker agent, and retrying forever against a service they haven't enabled would spin quietly for no reachable outcome; `SettingsView` staying the user-initiated path out of that state (#0270) is undisturbed.

**Diagnosability.** `StatusPayload` gained `bundlePath`/`appVersion`, populated in `AppStateStore.statusPayload()` from the answering process's own `Bundle.main` — ground truth about which on-disk app actually responded, not a CLI-side guess, visible via `batty status`'s new `path=… version=…` fields. This is the concrete answer to "the CLI should be able to say which app it's talking to" — the previous failure mode was silent and undiagnosable by design.

**`LSMultipleInstancesProhibited` — added in round 1, reverted in round 3 after review.** Round 1 added this `Info.plist` key as OS-level defense in depth. Review correctly rejected it: its scope (does it key on `CFBundleIdentifier` alone, or identifier+path?) is undocumented, so nobody can say what it actually does with ten bundles sharing one identifier at ten different paths. If path-scoped, it is inert against Cause 2 (every claimant is a distinct path) — pure risk for zero benefit. If identifier-scoped, it is actively harmful in this environment: it would make LaunchServices refuse to launch a DerivedData Debug build while `/Applications/Batty.app` is running (risking the maintainer's own Xcode Run loop), and could degrade this issue's own launch path too (`open -g <path>` failing outright while any same-identifier build is up, `AppLauncher.launch` returning `false`, and the CLI reporting a bare "app unavailable" instead of launching). It also would not have stopped Cause 3's launch mechanism (a direct exec of the app's own main binary via a shadowed `PATH` entry, not a LaunchServices `open` call at all) — community reports describe exactly that gap. Reverted; not present in this branch's `Configuration/Info.plist`.

## Notes

### Hypotheses to test

1. **A connection-failure path that launches the app.** The launch mechanism exists and is unconditional on a broker miss: `AppConnectDance.resolveEndpoint` (`BattyKit/Sources/batty/AppConnectDance.swift`) asks the broker for the app's endpoint and, on a miss, calls `AppLauncher.launch` (`BattyKit/Sources/batty/AppLauncher.swift`), which runs `/usr/bin/open -b <bundleID> -g`. If the running app's endpoint registration is missing from the broker the CLI talks to — for any reason — every verb takes the launch path. The broker starting fresh on 2026-08-22 14:27, ~18 hours after the app, is suggestive here: if a broker restart loses the app's registration and the app does not re-register, every subsequent connect dance hits the miss path and launches. To be confirmed by the diagnostic agents, not assumed.
2. **Prod vs Beta bundle-id mismatch** (`co.sstools.Batty` vs `co.sstools.Batty.beta`). `ServiceNames` (`BattyKit/Sources/BattyXPCCore/ServiceNames.swift`) derives both the broker Mach service name (`<bundleID>.broker`) and the launch target from the variant compiled into each binary. A CLI and app built under different variants would rendezvous with different brokers and launch a different bundle id. `CLAUDE.md` documents the `Configuration/Active.xcconfig` trap where the next build silently produces the other product.
3. **XPC peer code-signing rejection** between an ad-hoc-signed dev build and a Developer-ID-signed release build (`BattyKit/Sources/BattyXPCCore/PeerCodeSigningRequirement.swift`, `OwnCodeSigningIdentity.swift`, `OutgoingCodeSigningEnforcement.swift`), where the rejection presents to the CLI as "no app registered" and falls through to a launch.
4. **A stale `/usr/local/bin/batty`** (2026-08-21 14:04) whose wire expectations no longer match the running app or broker.

### Corrections to the existing text above

- **`/usr/local/bin/batty` is a symlink, not a standalone copy.** The
  "Observed data" section's `ls -l` output reads as a 4,822,320-byte regular
  file, but `readlink` and `stat` disagree with that reading:

  ```
  readlink /usr/local/bin/batty
    → /Applications/Batty.app/Contents/Resources/bin/batty
  stat -f "%HT" /usr/local/bin/batty
    → Symbolic Link
  ```

  This is exactly the documented design (`docs/batty-cli-install.md` step 1:
  "a **symlink** (not a copy) to `<Batty.app>/Contents/Resources/bin/batty` —
  installed by `CLIInstaller.install()`"), and `CLIInstaller.swift`
  (`BattyKit/Sources/BattyKit/Settings/CLIInstaller.swift:89-92`) checks
  `FileAttributeType == .typeSymbolicLink` on the install path. The size and
  date `ls -l` printed are the *target's*. **Hypothesis 4 in Notes ("a stale
  `/usr/local/bin/batty`") is therefore ruled out structurally**, not merely
  by hash: the CLI on `PATH` cannot drift from the installed app because it
  *is* the installed app's embedded CLI.
- **The "byte-identical" hash finding is tautological.** `/usr/local/bin/batty`
  and `/Applications/Batty.app/Contents/Resources/bin/batty` both hash to
  `818a69bcca0ebc5002d3ac105f9020b2b20816d26627e37a8b18b0c0bad30e1a` because
  the symlink resolves to the same inode. True, but it proves nothing beyond
  the symlink.
- **The four view kinds did not all merge on 2026-08-22.** Notes above (and
  #0362) say "the four view-kind merges of 2026-08-22 (#0304, #0305, #0313,
  #0314)". Actual commit timestamps on `main`: #0314 `aca515a` 2026-08-21
  23:11:13, #0313 `b6ae529` 2026-08-21 23:35:46, #0305 `9d6c511` 2026-08-22
  00:04:05, #0304 `6b48df2` 2026-08-22 00:34:31. Two landed on the 21st. This
  does not change the conclusion (the installed app predates all four) but the
  date should not be repeated as written.

### Cause 1 — confirmed from code, log evidence not independently re-verified

The exhaust-and-give-up reconnect path is real and reads as described:

- `AppXPCCoordinator.handleBrokerSignal`
  (`BattyKit/Sources/BattyKit/XPC/AppXPCCoordinator.swift:209-218`) clears
  `isRegisteredWithBroker`, then `guard reconnectBudget.consumeAttempt() else`
  logs `"broker … — reconnect budget exhausted this launch, not retrying
  automatically (a future CLI call may still recover it)"` and returns without
  scheduling any retry.
- `BrokerReconnectBudget`
  (`BattyKit/Sources/BattyKit/XPC/BrokerReconnectBudget.swift`) is
  `init(maxAttempts: Int = 5)`; `consumeAttempt()` decrements and returns
  `false` once `remaining` hits 0; `reset()` restores the full budget and its
  doc comment states it is "called on a confirmed registration (the broker
  actually answered `brokerPing`)". So: **5 attempts per launch, refilled only
  by a confirmed registration.** Confirmed.
- `AppConnectDance.resolveEndpoint`
  (`BattyKit/Sources/batty/AppConnectDance.swift:50-60`) treats
  `.endpoint(.none)` — broker reachable, nothing registered — as "no app

### Cause 3 — NEW, and the most direct mechanism found: `batty` on `PATH` resolves to the app's own executable

`/Applications/Batty.app/Contents/MacOS` **is on the user's `PATH`** (entry 20
of 22), which is why the report's `which -a batty` listed a second hit. That
second hit is not a CLI:

```
$ shasum -a 256 /Applications/Batty.app/Contents/MacOS/Batty \
                /Applications/Batty.app/Contents/MacOS/batty
ce0cadd2cbed0e9ad2dfcad5feee39892b1796c155fb4e0b0a121b395bc6461d  …/MacOS/Batty
ce0cadd2cbed0e9ad2dfcad5feee39892b1796c155fb4e0b0a121b395bc6461d  …/MacOS/batty
```

`ls -la Contents/MacOS/` lists exactly one file, `Batty` (29,465,536 bytes).
The volume is case-insensitive, so **`Contents/MacOS/batty` and
`Contents/MacOS/Batty` are the same file — the app's main executable.** The
real CLI is 4,822,320 bytes and lives in `Contents/Resources/bin/`.

**Confirmed:** the `PATH` entry exists, and the name `batty` resolves there to
the app binary. **Hypothesis, not confirmed:** that this is what the user hit.
Today `/usr/local/bin` precedes `/Applications/Batty.app/Contents/MacOS` in
`PATH`, so `batty` resolves to the symlinked CLI. But if that ordering is ever
reversed — a different shell init, a login vs. non-login shell, a `PATH`
rebuild inside a Batty-spawned shell, or `/usr/local/bin/batty` momentarily
absent during a reinstall — then typing `batty` **directly executes the app's
main binary**, which starts a brand-new `NSApplication` process every single
time, with no broker handshake, no `open -b`, and no LaunchServices dedupe.
That mechanism matches "KEEPS LAUNCHING ANOTHER INSTANCE" more exactly than
either cause above, and it would also explain instances that appear and
terminate without servicing anything.

This `PATH` entry does **not** come from the repo: `grep` over
`BattyKit/Sources`, `Batty/`, `scripts/`, and `docs/` finds no code or script
that adds `Contents/MacOS` to `PATH`, and it is absent from `~/.zshrc`,
`~/.zprofile`, `~/.zshenv`, `~/.bash_profile`, `~/.profile`, `/etc/paths`, and
`/etc/paths.d/*`. Its origin is unknown and worth asking the user about.

### What this implies for the fix (scope, not decided design)

Resolving the app by bundle identifier alone is ambiguous on any developer
machine, and resolving the *CLI* by bare name on `PATH` is ambiguous while the
app's `MacOS` directory sits on `PATH`. Options worth weighing, none chosen:

- Resolve the endpoint by the **absolute bundle path** of the app the CLI was
  installed from — the symlink already encodes it, so the CLI can read
  `/proc`-equivalent self-path and walk up to its own `.app`.
- **Verify the resolved app's bundle path and version before launching**, and
  refuse (or warn) on a mismatch.
- Prefer an **already-running** `NSRunningApplication` over any launch.
- Make the CLI **report which app bundle it connected to**, so this is
  diagnosable rather than silent.
- Housekeeping: prune stale LaunchServices registrations
  (`lsregister -kill -r -domain local -domain system -domain user`), and decide
  whether **debug builds should carry a distinct bundle id** so they never
  compete with the installed app.
- Consider whether `Contents/MacOS` belongs on `PATH` at all, and whether a
  case-insensitive collision between the app binary and the CLI name is worth
  designing out (e.g. by not naming them the same word modulo case).

### Ruled out with evidence — do not re-investigate

- **A stale `/usr/local/bin/batty`** (Notes hypothesis 4) — it is a symlink
  into the installed bundle; it cannot be stale relative to the app it points
  at.
- **Prod/Beta bundle-id confusion in the binary the user invoked** (Notes
  hypothesis 2) — the installed CLI resolves to the Prod app's embedded CLI.
  Note this rules out the *binary*, not the *registration*: six bundles still
  claim the beta id, one of them named `Batty.app`.
- **XPC peer code-signing rejection** (Notes hypothesis 3) — all Developer ID,
  same team, same notarization timestamp; logs showed the peer requirement
  succeeding.
- **Broker service unavailability** — `launchctl` showed it running and
  reachable; the broker is alive as pid 54667.
