# 0361 — The batty CLI launches another instance of the app instead of connecting to the running one

| | |
|---|---|

## Description

**User-reported, reproduced by the user, top priority.** Running the `batty` CLI while Batty is already running launches another instance of the app instead of connecting to the one that is running. In the user's words:

> "I do no tkno whow to give you any data because the CLI tool KEEPS LAUNCHING ANOTHER INSTANCE!!! What the fuck?! This is garbage."

This is severe on two counts. First, it is wrong on its own: the CLI's connect dance is designed to launch the app only when no app is running (`docs/xpc/xpc-cli-architecture.md`, "Launching the app on demand"), and here the app *is* running. Second, it **blocks all other diagnosis**: every `batty` command the user runs to inspect state may be talking to a different process than the one they are looking at. #0362 (a Pane-count discrepancy reported in the same session) may be caused or masked by this — the visible Panes and the counts the CLI reports could come from different processes.

## Steps to reproduce

Exact sequence not yet captured. What is known from the user's report:

1. Batty is running (`/Applications/Batty.app`, launched 2026-08-21 20:21).
2. The user runs `batty` commands (which verbs, and which `batty` on `PATH`, not yet confirmed).
3. Another instance of the app launches instead of the command connecting to the running instance. The user reports this happening repeatedly ("KEEPS LAUNCHING").

## Expected behavior

When Batty is already running, every `batty` verb connects to that running instance. The launch-on-demand path fires only when no instance is running, and never produces a second instance alongside a live one.

## Actual behavior

`batty` commands launch additional app instances while the app is already running, repeatedly.

## Investigation

Diagnostic subagents were dispatched 2026-08-22 to collect live evidence from the running app and the CLI; their findings will be appended to this issue. Until then, everything in Notes below is a **hypothesis to test, not a finding**.

## Notes

### Hypotheses to test

1. **A connection-failure path that launches the app.** The launch mechanism exists and is unconditional on a broker miss: `AppConnectDance.resolveEndpoint` (`BattyKit/Sources/batty/AppConnectDance.swift`) asks the broker for the app's endpoint and, on a miss, calls `AppLauncher.launch` (`BattyKit/Sources/batty/AppLauncher.swift`), which runs `/usr/bin/open -b <bundleID> -g`. If the running app's endpoint registration is missing from the broker the CLI talks to — for any reason — every verb takes the launch path. The broker starting fresh on 2026-08-22 14:27, ~18 hours after the app, is suggestive here: if a broker restart loses the app's registration and the app does not re-register, every subsequent connect dance hits the miss path and launches. To be confirmed by the diagnostic agents, not assumed.
2. **Prod vs Beta bundle-id mismatch** (`co.sstools.Batty` vs `co.sstools.Batty.beta`). `ServiceNames` (`BattyKit/Sources/BattyXPCCore/ServiceNames.swift`) derives both the broker Mach service name (`<bundleID>.broker`) and the launch target from the variant compiled into each binary. A CLI and app built under different variants would rendezvous with different brokers and launch a different bundle id. `CLAUDE.md` documents the `Configuration/Active.xcconfig` trap where the next build silently produces the other product.
3. **XPC peer code-signing rejection** between an ad-hoc-signed dev build and a Developer-ID-signed release build (`BattyKit/Sources/BattyXPCCore/PeerCodeSigningRequirement.swift`, `OwnCodeSigningIdentity.swift`, `OutgoingCodeSigningEnforcement.swift`), where the rejection presents to the CLI as "no app registered" and falls through to a launch.
4. **A stale `/usr/local/bin/batty`** (2026-08-21 14:04) whose wire expectations no longer match the running app or broker.
