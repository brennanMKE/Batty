# 0612 — WindowLifecycleController.updateNSView defers delegate install, occlusion sync and chrome writes in a main-queue hop on every update

| | |
|---|---|
| **Status** | open |
| **Module** | Window / Theme |
| **Platform** | macOS |
| **First seen** | 2026-11-12 |
| **Priority** | medium |

## Description

**HIGH. Related to #0601 and #0602.** Every `WindowLifecycleController.updateNSView` queues a `DispatchQueue.main.async` block that installs the window delegate, wires `closeWindowCallback`, re-reads occlusion into `TerminalHostStore.setWindowOcclusionVisible` and `WindowRuntime.setWindowVisible`, and — since #0602 — calls `appStore.contentWindowBecameKey(id)` when the window is key, which resolves the effective Theme and writes `themeChrome.palette`. The hop exists to move these writes out of the representable update; the rules forbid that pattern ("restructure which code owns the write"). Its own comment shows the write is reconstructing an event (`didBecomeKey`) that was missed because the delegate was installed late, by this same hop.

`ThemeChrome.palette` is the second half of the problem: it is a cached copy of a derivable fact (the default target window's selected Session's effective Theme), with **six** call paths writing it and no single owner.

## Current state (verified 2026-11-12 on `main` `ce66ca6a`)

- `BattyKit/Sources/BattyKit/Views/RootWindowView.swift:126-170`, `WindowLifecycleController`: `makeNSView` returns a plain `NSView`; `updateNSView` (`:136-166`) is the `DispatchQueue.main.async` block described above; `contentWindowBecameKey` at `:163-165`.
- `RootWindowView.swift:53, :63-64`: the representable sits under `.environment(\.windowIsSeeThrough)`, so it updates whenever `RootWindowView.body` re-runs (#0607, #0608).
- `Theme/ThemeChrome.swift:20`: `public private(set) var palette: ChromePalette`; `:31-33` `update(from:)` assigns unconditionally (`ChromePalette` is `Equatable`, so equal writes don't notify).
- `themeChrome.update` call sites, all in `Theme/ThemePreference.swift`: `applyThemeToAllSurfaces` (`:171`), `applyTheme(_:to:)` (`:194`), `applyActiveSessionTheme` (`:218`, nil), `applyGlobalThemeForCurrentAppearance` (`:243`), `applySelectionTheme` (`:263`, from `selectedSessionID.didSet`), `applyChrome` (`:275`, from `AppStateStore.contentWindowBecameKey`, `Runtime/AppStateStore.swift:1149-1153`, called by `handleWindowDidBecomeKey` `:1137-1140` and by the `updateNSView` hop).
- `Util/WindowIDRegistrar.swift`: already registers synchronously from `viewDidMoveToWindow` (#0437), the pattern to copy.

## Rule violated

- `docs/swiftui-observation-rules.md`, "`Task` and async work": a hop is not a safety device; restructure which code owns the write. A `DispatchQueue.main.async` hop from `updateNSView` is the same move as a `Task` hop.
- Same doc, "Two-way model ↔ AppKit sync": one authority per fact, one writer per direction.
- swift-guidance `swiftui-observation.md` / `concurrency.md`: no deferred observed-state writes from representable updates.

## Evidence

- **Proven:** the hop and its writes; the six palette call paths.
- **Inferred:** `updateNSView` frequency. Nothing loops today only because every write is idempotent (`ChromePalette` `Equatable`, `setWindowVisible`/`setWindowOcclusionVisible` guarded).

## Fix direction (restructure ownership; no hop)

- Replace the representable's hop with an `NSView` subclass (like `RegistrarNSView`) that installs `WindowDelegate` and `closeWindowCallback` synchronously in `viewDidMoveToWindow`. Neither writes observed state nor dirties constraints. Read the initial occlusion and key state there too, or rely on the delegate's `windowDidChangeOcclusionState` / app-wide `didBecomeKey`, since the window orders on screen after its content view attaches (inferred; verify with the multi-window tests). `updateNSView` becomes a no-op.
- Palette: preferably derive it per window from observed inputs (the window's selected Session's `themeOverride`, the global Theme names, the appearance), memoized by theme name, so no write path exists. Minimum: remove `contentWindowBecameKey` from the update path and keep the remaining writers event-origin (`didBecomeKey`, selection `didSet`, KVO appearance, Theme commands).
