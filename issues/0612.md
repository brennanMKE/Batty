## Description

**HIGH. Related to #0601 and #0602.** Every `WindowLifecycleController.updateNSView` queues a `DispatchQueue.main.async` block that installs the window delegate, wires `closeWindowCallback`, re-reads occlusion into `TerminalHostStore.setWindowOcclusionVisible` and `WindowRuntime.setWindowVisible`, and — since #0602 — calls `appStore.contentWindowBecameKey(id)` when the window is key, which resolves the effective Theme and writes `themeChrome.palette`. The hop exists to move these writes out of the representable update; the rules forbid that pattern ("restructure which code owns the write"). Its own comment shows the write is reconstructing an event (`didBecomeKey`) that was missed because the delegate was installed late, by this same hop.

`ThemeChrome.palette` is the second half of the problem: it is a cached copy of a derivable fact (the default target window's selected Session's effective Theme), with **six** call paths writing it and no single owner.

## Root cause

`WindowLifecycleController.updateNSView` queued a `DispatchQueue.main.async` block on every representable update. It installed the window delegate and `closeWindowCallback`, re-read occlusion into `TerminalHostStore` and `WindowRuntime.setWindowVisible`, and called `contentWindowBecameKey`, which wrote `themeChrome.palette`. The hop moved observed-state writes out of the update instead of giving them an owner. `ThemeChrome.palette` was a cached, app-wide copy of a derivable fact with six writers. Confirmed by a fail-before probe on the merged code: tracking `store.themeChrome.palette` and calling `contentWindowBecameKey(second.id)` for a second window with its own Session Theme fired the tracker (`CHECK UNIT: FAILED (1 test)`, "becoming key rewrote the chrome palette").

## Fix

- **Lifecycle.** New `WindowLifecycleNSView` (`RootWindowView.swift`) installs its own retained `WindowDelegate` and the `closeWindowCallback` synchronously in `viewDidMoveToWindow`. It does not read occlusion or key state there. `updateNSView` is empty, and `makeCoordinator` is gone. `WindowDelegate.windowDidChangeOcclusionState` is now the only occlusion writer.
- **Chrome derived per window, never written.** `ThemeChrome` is an immutable, non-observed class with `let palette`. `AppStateStore.chromeThemeName(for:)` resolves, in order: Session preview, the override slot for `appearanceIsDark`, global preview, then the global name for the appearance. `themeChrome(for:)` returns one shared instance per Theme name from `ThemeChromeCache` (`@ObservationIgnored`). `chromePalette(for:)` returns its palette. These are new observed store inputs, each with one event-origin writer: `appearanceIsDark` (`applyGlobalThemeForCurrentAppearance`), `globalDarkThemeName` / `globalLightThemeName` (`setGlobalTheme`), `globalThemePreviewName` (replaces #0616's `globalThemePreviewPending`), and `sessionThemePreviewNames` (replaces `sessionThemePreviewIDs`). All six `themeChrome.update` calls and `applyChrome` were deleted. `applySelectionTheme` keeps only its terminal half, including #0613's `appliedTerminalThemeName` skip.
- **Departures from the plan:**
  1. **No per-window resolver `ThemeChrome`.** The plan kept a `ThemeChrome` on `WindowRuntime` that resolved on each read. With that design, every chrome reader, including every Sidebar row, depended on `selectedSessionID`. `SessionDetailLayoutConvergenceTests/sessionSwitchRequestsDoNotScaleWithSessionCount()` regressed: 16 Sessions cost 216 more requests than 4, against a 212 margin, which undid #0604. Instead, a new `WindowChromeScope` wraps `WindowSeeThroughScope` in `RootWindowView`. It is the only view that calls `themeChrome(for:)`, and it injects the result as `\.themeChrome`. Its content is stored, so a selection change re-runs only the scope, and readers re-render only when the injected instance changes. `WindowSeeThroughScope` takes the applier's palette from `@Environment(\.themeChrome)`. The test fixtures (`SessionDetailTestTree`, `StatusPaneLayoutConvergenceTests`) wrap their trees in `WindowChromeScope` too.
  2. **`contentWindowBecameKey(_:)` kept, not deleted.** It is now a one-line event-origin hook. Its only caller is `handleWindowDidBecomeKey` (the app-wide `NSWindow.didBecomeKeyNotification`), and it only calls `noteContentWindowBecameKey`. **For #0615:** this is the place to write `keyContentWindowID`. It never runs from a view update.
  3. **`setSessionTheme` guards its dictionary removal.** A subscript write to `sessionThemePreviewNames` notifies even when nothing changes, and every window's derivation reads the dictionary.
- `UITestDriver.applyThemeToActiveSession` now goes through `setSessionTheme`, so the override is set and the chrome follows. `.applyTheme` already used `setGlobalTheme` after #0616. `ThemeTests` only checks that the Session rows survive.

## Gotchas

- **Visible change:** each window now shows its own selected Session's chrome. Before, one app-wide palette followed the key window. This needs the user's visual sign-off (Plan, user checklist 1–3).
- **Delegate installed once, on attach.** The old hop re-installed `WindowDelegate` on every update if something else had replaced it. Now nothing re-asserts it. If SwiftUI or AppKit ever reassigns `NSWindow.delegate` after the content attaches, close confirmation, occlusion and full-screen tracking would stop. Not verifiable headlessly; covered by `WindowCloseQuitTests` and `MultiWindowTests` at the daily run.
- **No occlusion read on attach (plan decision 2).** A window attached while already on screen *and* occluded stays "visible" until its next occlusion transition. That costs some background work and has no correctness impact. It also depends on the inference that a `WindowGroup` window is ordered in after its content attaches.
- **Settings with no store.** `SettingsView`'s `themePicker` writes `@AppStorage` directly when `store` is `nil`. That path bypasses `setGlobalTheme`, so `globalDarkThemeName` / `globalLightThemeName` would go stale. It already skipped re-theming surfaces before this change. Not reachable in production: the only `SettingsView()` (`Batty/BattyApp.swift`, `Settings` scene) is given `.environment(\.appStateStore, AppStateStore.shared)`, so `store` is never `nil` there (checked in review).
- **Appearance seed.** `appearanceIsDark` is seeded once in `AppStateStore.init` and after that changes only on an `AppearanceObserver` KVO event (`options: [.new]`, no initial delivery). Before, selection changes re-read `NSApp.effectiveAppearance` for the chrome and so could heal a wrong seed; now nothing does until the next flip. The seed comes from `NSApp` when the store is built, as the old chrome seed did, so this is only a problem if the appearance flips between store construction and observer install in `applicationDidFinishLaunching`.
- An appearance flip invalidates the derivation of a window whose Session has an override, because the override's slot is read for `appearanceIsDark`. Its injected instance stays the same, so its readers don't re-render.

### Decisions (made here, no user input needed)

1. **The palette is derived per window; nothing writes it.** The "single store method" fallback still needs a write when a window is already key at registration, and the only place that knows that is `viewDidMoveToWindow`, which can run inside SwiftUI's update. Derivation removes the write and the hop together. Each content window shows its own selected Session's chrome. Today the one app-wide palette follows the key window, so a non-key window shows the key window's chrome. That is a visible change, and the intended one (`docs/themes.md` already says "the chrome always matches the selected session's effective theme").
2. **No initial occlusion read on attach.** The attach callback can run mid-update, and `setWindowVisible(false)` suspends Pane content, which may write observed content state. Both stores default to visible. A `WindowGroup` window gets its content view before it is ordered on screen (inferred; the VM classes below check it), so ordering in is an occlusion transition that `windowDidChangeOcclusionState` delivers. A window attached already on screen *and* occluded stays "visible" until its next transition. That costs some background work and has no correctness impact. Record this in `## Gotchas`.
3. **No key-state reconstruction on attach.** The palette no longer depends on key state. `registerNSWindow`'s existing `isKeyWindow` backstop (#0439) still records the key order.

### User checklist

1. Open two windows. Give window 2's Session its own Theme. Each window's sidebar and tab chrome should show its own Theme, and clicking between the windows should not repaint either one.
2. Switch the system between Dark and Light. Windows that follow the global Theme should change, and the overridden Session should not.
3. Arrow-key preview in the global and Session Theme Selectors. The chrome previews, and Esc or dismiss restores it.
4. Closing a window with a running process prompts. Closing the last Session closes the window.
5. Minimize and restore a window, or cover it, and confirm terminal and status Panes resume.

## Rule violated

- `docs/swiftui-observation-rules.md`, "`Task` and async work": a hop is not a safety device; restructure which code owns the write. A `DispatchQueue.main.async` hop from `updateNSView` is the same move as a `Task` hop.
- Same doc, "Two-way model ↔ AppKit sync": one authority per fact, one writer per direction.
- swift-guidance `swiftui-observation.md` / `concurrency.md`: no deferred observed-state writes from representable updates.

## Evidence

- **Proven:** the hop and its writes; the six palette call paths.
- **Inferred:** `updateNSView` frequency. Nothing loops today only because every write is idempotent (`ChromePalette` `Equatable`, `setWindowVisible`/`setWindowOcclusionVisible` guarded).

## Fix direction (restructure ownership; no hop)

- Replace the representable's hop with an `NSView` subclass (like `RegistrarNSView`) that installs `WindowDelegate` and `closeWindowCallback` synchronously in `viewDidMoveToWindow`. Neither writes observed state nor dirties constraints. Read the initial occlusion and key state there too, or rely on the delegate's `windowDidChangeOcclusionState` / app-wide `didBecomeKey`, since the window orders on screen after its content view attaches (inferred; verify with the multi-window tests). `updateNSView` becomes a no-op.
- Palette: preferably derive it per window from observed inputs (the window's selected Session's `themeOverride`, the global Theme names, the appearance), memoized by theme name, so no write path exists. Minimum: remove `contentWindowBecameKey` from the update path and keep the remaining writers event-origin (`didBecomeKey`, selection `didSet`, KVO appearance, Theme commands).
