## Description

Muting a Session (Sidebar context menu > Mute Notifications, `SessionRuntime.notificationsMuted`, #0068) suppresses only the macOS banner. Its bells still add unread Bell Feed rows and bump the Tab, Pane and Session unseen counters. `AppStateStore.postNotification` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:2690`) returns early on `notificationsMuted`, but by then `recordBellTick`, `recordDesktopNotification` or `recordCLINotification` has already called `recordOrCollapse` and `propagateUnseenForced`. This is deliberate and documented. `Help/06-notifications.md` says: "The chip dot, sidebar badge, and bell feed still update — mute affects delivery, not capture." `AppStateStoreNotifyTests.mutedSessionSuppressesTheNotifierPostButStillRecordsTheFeedEntry` locks it in.

The goal, from the user (2026-11-05):

> We should make it our goal to declutter the notification list as much as possible so only what is useful remains.

Split out of [#0555](0555.md), "Further decluttering". The question is whether a muted Session's bells count as "ignored" notifications that shouldn't be listed.

## Root cause

Feature change, not a bug. `routeRealTabBell` dropped an entry only when `BellNotifier.evaluateShouldPost` declined the banner (#0555). Mute was checked later, in `postNotification`, after `recordOrCollapse` and `propagateUnseenForced` had run, so a muted Session's bells still added rows and unseen counts. Help, `docs/notifications.md` and tests documented that as intended.

## Fix

`routeRealTabBell`'s drop guard gains `!location.session.notificationsMuted`, so muted bells go through the same `recordDroppedBell` as #0555's seen drop: the #0297 history and #0523 capture (`feedRecorded: false`) still record them, and no row, unseen count or banner is made. `postNotification`'s mute guard stays as a defensive check. Reminders don't use `routeRealTabBell` and are unaffected. No code runs on mute or unmute, so existing rows stay and nothing comes back.

Docs and comments updated per the Plan: `recordBell`/`recordDesktopNotification`/`recordCLINotification`/`postNotification` comments, `BellNotifier.evaluateShouldPost`, `RootWindowView.setUpNotifier`, Help `06-notifications.md`, Help `01-overview.md` (it said Settings has per-session mute; now it says the Sidebar right-click menu has it), `docs/notifications.md` (intro, §1, §3 diagram, §4 table, §7 contract, §10 stale `LayoutModel.swift` row removed, §11, answer key), `docs/bell-feed-capture.md`, `docs/ui-features.md` (mute contract and the nonexistent `menu.sidebar.mute-session.<title>` identifier), `Concepts.md` 0.26 -> 0.27.

Departures from the Plan: merged `main` first (#0561 landed), so the BEL/OSC tests use #0561's `ringBell(in:)` / `requestDesktopNotification(in:)` helpers with no `awaitTerminalStatePublish`. The Plan's Concepts target was 0.27; the merged base was 0.26, so it is 0.27.

### Decisions

1. **A muted Session's bells add no Bell Feed row and bump no unseen counter.** This overrides the filed "Recommended default" below. The user's stated goal is to declutter the list so only what is useful remains. Muting is the user saying, explicitly and per Session, that this Session's bells aren't wanted right now. A row, a chip dot and a Sidebar badge for them are exactly the clutter that goal targets. The filed reason to keep them ("the row and the badge are what's left to show that something happened") is weaker than it looks: mute is runtime-only and resets on relaunch, so it can't swallow bells indefinitely, and the Session is still in the Sidebar one click away. Nothing in `Concepts.md` says mute keeps rows; only Help and the docs promise it, and those get updated here.
   - All three real-tab paths: BEL, OSC 9/777 and `batty notify`. `batty notify` into a muted Session still returns `.posted`, so the CLI exits 0, like #0555's drop.
   - Whether Batty is active or not, and whether the Tab is focused or not. A muted Session's focused-Tab bell in the background would today add a seen row and no banner; it is dropped too.
   - The #0297 decision history still records it (`suppressed:sessionMuted`, or `suppressed:nilNotifier` when no notifier exists, as today), and the #0523 capture log writes an `event` with `feedRecorded: false` and `summarization: notApplicableNotRecorded`. No summarization runs.
2. **Reuse #0555's drop path.** `routeRealTabBell`'s existing guard gains one condition and calls the same `recordDroppedBell`. No second mechanism, no new outcome enum case, no capture schema bump (schema 2 already lets an `event` name an entry with `feedRecorded: false`).
3. **Reminders are exempt.** `fireReminder` (`AppStateStore+Reminders.swift:69`) never goes through `routeRealTabBell`, so it is unaffected by construction. A test locks it in.
4. **Rows that exist when the Session is muted are kept**, with their unseen counts. Mute stays a plain property toggle (`SessionSidebarView.swift:551`): no code runs on mute. Those rows clear the usual ways (visit, Clear All, close). A muted bell is dropped before `recordOrCollapse`, so it never collapses into an existing unread row either (its `repeatCount` doesn't grow).
5. **Unmuting brings nothing back.** Dropped bells were never stored, so there is nothing to restore; again no code runs on unmute. Bells after the unmute behave normally.
6. **The Sidebar shows no sign of a muted Session's bells.** Session and Pane badges and the chip dot all read the unseen counters, which no longer move. What remains, unchanged: `TabRuntime.bellCount`/`lastBellAt` still advance (the delta tracker must, as #0555's tests check), the Pane's own bell flash (`PaneView.triggerBellFlash`, keyed on `TabRuntime.bellCount`, only visible when the Pane is on screen) still plays, and libghostty's in-surface bell sound is still not gated by mute. Those are in-place feedback, not list entries. A Sidebar "muted" glyph is not added; see Open questions.
