## Description

Once a Session has two or more Panes, there is no way to create a new Pane that spans the **full width** (a new full-width row) or the **full height** (a new full-height column) of the Session. Every split command splits the *current* Pane in half, so a new Pane only ever takes half of the focused Pane's area — you can never add a new top-level row or column across the whole Session.

Requested: an **Option-key modifier** that promotes a split to a full-dimension split at the Session's top level. Plain shortcut/button keeps the existing split-the-current-pane behavior; Option + shortcut/button adds a new full-height column or full-width row at the Session level.

## Resolution notes

> 🟢 Resolved 2026-07-09 — holding Option promotes a split to a full-dimension split at the session root: Cmd-Option-D adds a full-height column, Cmd-Shift-Option-D adds a full-width row, and Option-clicking the top-right toolbar split buttons does the same. Plain Cmd-D / Shift-Cmd-D and plain clicks are unchanged.

The actual key chords and Option-click firing live, plus visual confirmation the new pane spans the full session dimension, need the user's sign-off — see Gotchas.

## Root cause

Feature gap, not a bug. Both split entry points (`SplitTree.splitFocusedPane`, and the toolbar buttons that call it) only ever replace the focused leaf with a split, so a new pane is always confined to the focused pane's rectangle. There was no operation to insert a pane at the session root, and no Option-modified command/button to invoke one.

## Fix

- **Model** — new `SplitTree.splitFullDimension(direction:ratio:inheritingFrom:)` wraps the *entire* tree in a new top-level split: `.split(id:, direction:, ratio: 0.5, left: root, right: .leaf(newPane))`. The existing `root` is carried into the `left`/top slot **unchanged** — no leaf is reconstructed, so every `PaneRuntime` (and its `tab.id`) keeps its identity and no Terminal Session/surface is destroyed. The new pane is trailing (right for a column, bottom for a row), matching the existing insertion convention. Shared cwd-inheriting pane creation was refactored into `makePane(inheritingFrom:)`, used by both split methods with byte-identical behavior. Deliberately no chain-rebalance: each full-dimension press gives the new pane 50% of the outer dimension (repeated same-direction presses yield 50/25/25); the divider is user-draggable and this is a predictable edge case (reviewer-accepted).
- **Keyboard** — new `ShortcutAction` cases `splitFullHeightColumn` (Cmd-Option-D) and `splitFullWidthRow` (Cmd-Shift-Option-D), dispatched in `BattyShortcuts.run`. This is the functional path: `BattyShortcuts.handle` is an `NSEvent` local monitor (installed in `Batty/BattyApp.swift`) that resolves the chord and swallows the event before SwiftUI `.keyboardShortcut` sees it; bindings are unique and plain Cmd-D still resolves only to `.splitHorizontal`.
- **Menus / palette / settings** — matching Pane-menu entries in `BattyCommands.swift`, and wiring in `CommandPaletteView.dispatch` (required because the palette lists `ShortcutAction.allCases`; the Settings → Shortcuts pane picks up the two new customizable actions automatically for the same reason).
- **Toolbar** — the top-right split buttons in `SessionDetailView.swift` read `NSEvent.modifierFlags.contains(.option)` at click time and route to the full-dimension op; `.help` tooltips updated. Plain-click behavior is byte-identical.

## Gotchas

- **Manual/UI sign-off pending (user).** Marked `resolved`, not `closed`. Confirm in the running app: Cmd-Option-D adds a full-height column and Cmd-Shift-Option-D a full-width row; Option-click on the two top-right split buttons does the same; the new pane visibly spans the full session dimension; plain Cmd-D / Shift-Cmd-D and plain clicks are unchanged.
- **Repeated same-direction full-dimension splits diminish** (50% of the outer dimension each press → 50/25/25), by design — dividers are draggable to rebalance. If even n+1 sizing is wanted, that's a small follow-up.
- **A plain same-direction split inside a wrapped subtree** chain-rebalances across the new top-level split — existing `splitFocusedPane` behavior, not a regression.
- **Option-click reading `NSEvent.modifierFlags` at a button call site** is new to this codebase (no prior precedent); it built clean and the reviewer judged the AppKit idiom sound, but it's part of what the user's live click-test confirms.

## Current behavior

- `Cmd-D` splits the current Pane **horizontally** — a new Pane appears beside it (left/right split).
- `Shift-Cmd-D` splits the current Pane **vertically** — a new Pane appears above/below it (top/bottom split).
- Both always split *within* the current Pane's bounds. With 2+ Panes there is no way to get a new Pane that spans the Session's full width or full height.
- The split buttons in the **top-right corner of the window** perform the same two splits, with the same limitation.

## Desired behavior

Holding **Option** promotes the split to the Session's top level instead of splitting the focused Pane:

- `Option-Cmd-D` — horizontal split that creates a new **full-height column** spanning the entire Session height (a new top-level column), instead of splitting only the current Pane.
- `Option-Shift-Cmd-D` — vertical split that creates a new **full-width row** spanning the entire Session width (a new top-level row).
- Holding **Option while clicking** the split buttons in the top-right corner of the window applies the same full-dimension behavior.

Plain `Cmd-D` / `Shift-Cmd-D` and un-modified button clicks are unchanged — they keep splitting the current Pane.

## Notes

Likely code areas:

- **Split command handlers / key equivalents** — `BattyKit/Sources/BattyKit/Commands/BattyCommands.swift` wires the menu items via `shortcuts.keyboardShortcut(for: .splitHorizontal)` / `.splitVertical` (around lines 203 and 212); the shortcut definitions live in `BattyKit/Sources/BattyKit/Commands/BattyShortcuts.swift` and `BattyKit/Sources/BattyKit/Shortcuts/ShortcutAction.swift`. The Option variants need new actions (or an option-modified pair of shortcuts) plus menu entries.
- **Split insertion in the model** — `BattyKit/Sources/BattyKit/Model/SplitTree.swift`. `splitFocusedPane(direction:inheritingFrom:)` (around line 123) replaces the focused leaf with a `.split` node — that is the "split within the current pane" behavior. A full-dimension split instead wraps the Session's **root** node in a new `.split` (new column: `.horizontal` with the existing root as one child; new row: `.vertical` likewise), so the new Pane spans the whole Session along the perpendicular axis. Worth deciding the ratio the new top-level row/column gets (even split of the whole dimension vs. something like 1/(n+1)).
- **Top-right toolbar split buttons** — `BattyKit/Sources/BattyKit/Views/SessionDetailView.swift` (around lines 133–148, `toolbar.split-horizontal` / `toolbar.split-vertical`) calls `tree.splitFocusedPane(...)` directly. Option-click needs to detect `NSEvent.modifierFlags` (or equivalent) at click time and route to the top-level insertion instead; the `.help` tooltips should mention the Option variant.
- Sidebar pane-row positions from #0259 derive from `SplitTree` shape, so `column/row` labels should update correctly for free once the tree insertion is right — but the new top-level-wrap path deserves coverage in `SplitTreePanePositionTests` alongside the existing nested-grid cases.
