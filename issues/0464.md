## Description

Two guards in `BattyKit/Sources/BattyKit/Commands/` answer the same
question about a Terminal Session — *is the PTY's foreground process group
a lone interactive shell sitting at its prompt?* — and each answers it with
its own code:

- **#0393's `PlainShellKeyRewrite`** (on `main` at `3b155731`,
  `BattyKit/Sources/BattyKit/Commands/PlainShellKeyRewrite.swift`) downgrades
  Shift/Ctrl-Return to a plain Return. It counts the group with
  `proc_listpgrppids` into an 8-slot buffer (`:55-62`), names the leader with
  `proc_name` (`:48-53`), requires `foregroundGroupMemberCount == 1` (`:35`),
  and its shell list is `zsh, bash, sh, dash, ksh, tcsh, csh` (`:21-23`).
  fish is deliberately excluded (`issues/0393.md:146`: "fish is not in the
  shell list; it handles the sequence itself") and the exclusion is pinned by
  `BattyKit/Tests/BattyKitTests/PlainShellKeyRewriteTests.swift:41`.
- **#0411's `StuckMouseReportGuard`** (branch `issue/0411`, head `6f1c3b46`
  at filing time, **not yet merged and may still change**,
  `BattyKit/Sources/BattyKit/Commands/StuckMouseReportGuard.swift`) withholds
  a left click when DEC mouse reporting was left on at an idle prompt. It
  lists the group with `sysctl(KERN_PROC_PGRP)` (`:34-43`), names the leader
  with its own copy of the `proc_name` wrapper (`:44-49`), requires
  `groupMembers(pid) == [pid]` (`:68`), and its shell list is
  `zsh, bash, fish, sh, dash, ksh, tcsh, csh, nu, elvish` (`:57-59`). fish is
  included, with the comment "a withheld click is harmless there" (`:53-56`).

So today a fish, nu or elvish prompt is "a plain shell" to the click guard
and "not a plain shell" to the key rewrite; the two files carry two
`proc_name` wrappers (a third and fourth already exist in
`Runtime/ProcessInspector.swift:126-138` and
`Runtime/ProcessMetricsReader.swift:211-216`); and the group-size question
is asked of two different kernel interfaces whose return conventions have
already bitten both issues once each (see Notes). The next consumer — #0465
(scroll and motion reports at a stuck prompt) and #0462 (Tab/Escape chords)
both need the same predicate — would be a third copy.

This issue is the consolidation: one helper that returns the foreground
group's pid, the leader's name and the member count (or members), one
mechanism, one reconciled shell policy with the reason for each consumer's
inclusions and exclusions written down, and one set of tests. Target: after
1.2.0, on `main`, once #0411 has landed.

## Steps to reproduce

This is a code-structure issue; the user-visible divergence is:

1. Beta only (`./build.sh`), with a build that includes `issue/0411`. Open
   a Tab and run `fish` (or `nu`), so the foreground group is a lone fish.
2. Type `echo hi` and press **Shift-Enter**. The key rewrite stands down
   (fish is not in its list); whatever fish does with `ESC[27;2;13~` is what
   you see.
3. In the same fish, run `printf '\e[?1000h\e[?1006h'` and left-click the
   Pane. The click guard *does* fire (fish is in its list) and the click is
   withheld.
4. Repeat 2-3 in `zsh`: both guards fire.

Neither #0393 nor #0411 checked fish by hand (`issues/0393.md:144`), so
whether step 2 or step 3 is the *right* behaviour for fish is itself an open
question below.

## Expected behavior

Acceptance criteria:

1. **One helper, two callers.** A single type (name is the implementer's;
   something like `ForegroundProcessGroup` with `pgid`, `leaderName` and
   `memberCount` or `members`) owns every `proc_listpgrppids` / `sysctl` /
   `proc_name` call on this path. `PlainShellKeyRewrite` and
   `StuckMouseReportGuard` call it and contain no libproc or sysctl calls
   themselves. Whether `ProcessInspector.identity(pid:)` and
   `ProcessMetricsReader.readName` also route through it is the
   implementer's call; they have different failure-mode requirements
   (`ProcessInspector.swift:119-125`) and need not change.
2. **One mechanism, with the measured facts in its doc comment.** Either
   `proc_listpgrppids` or `sysctl(KERN_PROC_PGRP)`, chosen per Open question
   1. The comment must state what this filing measured (Notes): the real
   buffer call of `proc_listpgrppids` returns a **pid count**, not bytes; a
   nil-buffer sizing call of either API over-estimates and cannot be used as
   the count; and both agree on a controlled group (3 members, then 1 after
   two are killed). No "the VM is different" wording — the #0411 branch's
   `1bc0472f` message attributes the earlier failure to the VM, and that was
   not the cause.
3. **Shell policy reconciled and explained.** Either one list with named
   per-consumer exclusions, or two lists, but in both cases the code records
   *why* each consumer includes or excludes fish, nu and elvish, and the
   reason is verified by running the shell in a Beta Tab (Shift-Enter at the
   prompt; a click with `printf '\e[?1000h\e[?1006h'` left on), with the
   observation written in `## Work log`. "It handles the sequence itself"
   and "a withheld click is harmless there" are both currently unverified.
4. **Shared tests.** The helper gets its own BattyKit tests: the
   `posix_spawn` group-count test now in
   `PlainShellKeyRewriteTests.swift:64-93` moves to (or is shared with) the
   helper's test file and asserts the member list as well as the count; the
   live-process tests on the branch
   (`StuckMouseReportGuardTests.swift`, `StuckMouseReportGuardLiveProcessTests`)
   fold into the same file. Both consumers' decision tests inject the
   helper's result (a struct or a closure) rather than each defining its own
   `Process` seam. No sleeps, no timing (AGENTS.md "Asynchronous tests").
5. **No behaviour change for the shells both already agree on.**
   `BattyUITests/ShiftEnterTests` (#0393) and
   `BattyUITests/StuckMouseModeClickTests` (#0411) pass unchanged in the
   Tart VM. A fish/nu/elvish behaviour change decided under criterion 3 is
   recorded in the issue, not silently shipped.
6. `./build.sh` and `./build.sh unit` pass.

## Actual behavior

Per code reading (no user report; both consumers work for zsh and bash):

| | `PlainShellKeyRewrite` (`main` `3b155731`) | `StuckMouseReportGuard` (`issue/0411` `6f1c3b46`) |
|---|---|---|
| Group query | `proc_listpgrppids(pgid, &pids, 8 * 4)` → count, capped at 8 (`:58-62`) | `sysctl` `{CTL_KERN, KERN_PROC, KERN_PROC_PGRP, pgid}` sizing call, then a `kinfo_proc` array with 4 slots of slack (`:34-43`) |
| Lone test | `count == 1` (`:35`) | `members == [pid]` (`:68`) |
| Name | `proc_name` (`:48-53`) | `proc_name` (`:44-49`) |
| Shells | zsh bash sh dash ksh tcsh csh (`:21-23`) | zsh bash fish sh dash ksh tcsh csh nu elvish (`:57-59`) |
| Login-shell `-` prefix | not handled | handled in `a43147d4:60`, removed in `6f1c3b46` as dead code (`proc_name` reports `p_comm`, see Notes) |
| Test seam | pass name + count as parameters (`rewrittenModifiers(…)`) | inject `Process { groupMembers, name }` closures |
| Caller | `Batty/BattyApp.swift:84` key monitor | `TerminalClickFocusMonitor.swift:67-71` (branch) click monitor |

Both consumers read the pid from the package's
`AppTerminalView.foregroundPid`
(`BattyKit/.build/checkouts/libghostty-spm/Sources/GhosttyTerminal/Platform/Shared/TerminalView+Process.swift:22-24`
→ `TerminalSurface.foregroundPid`, `Surface/TerminalSurface.swift:413-417`,
which maps Ghostty's 0 to nil). That is `tcgetpgrp` on the pty, i.e. the
pgid, which is why both then ask `proc_name` about the pgid itself.

## Notes

### The `proc_listpgrppids` return value, and what happened on `issue/0411`

`libproc.h:94` declares `int proc_listpgrppids(pid_t pgrpid, void *buffer,
int buffersize)` and documents nothing about the return value. Measured on
this host for this filing (a small C program; a fresh `posix_spawn` group of
three `sleep`s, then two killed and reaped):

| Call | `proc_listpgrppids` | `sysctl(KERN_PROC_PGRP)` |
|---|---|---|
| Real buffer, group of 3 | returns `3` (pids: 3) | `size/stride` = 3 |
| Real buffer, group of 1 | returns `1` | `size/stride` = 1 |
| Sizing call (nil buffer) | returns `986` for a group of 2 | sizing `size/stride` = 7 for a group of 2 |

So: the real-buffer return is a **pid count**, both sizing calls
over-estimate, and the two mechanisms agree. This matches what #0393's
review recorded ("`proc_listpgrppids` returns a pid count, confirmed
empirically on this host", `issues/0393.md`, Review notes for `2cf733d0`)
and what `PlainShellKeyRewrite.swift:55-57` says.

The #0411 branch's first attempt, `a43147d4`
(`StuckMouseReportGuard.swift:29-37` at that commit), called the same API
with a 64-slot buffer and then did
`buffer.prefix(Int(bytes) / MemoryLayout<pid_t>.size)` — dividing the pid
count by 4. For a lone shell that is `1 / 4 == 0`, so `groupMembers`
returned `[]`, `== [pid]` failed, and the guard never matched. Commit
`1bc0472f` replaced it with `sysctl` and attributed the failure to the VM
("proc_listpgrppids returned no members for the shell's group in the VM").
It was the division, not the VM; the same bug had been found and fixed on
`issue/0393` the day before. That is the concrete cost of two copies.

### `proc_name` reports `p_comm`, not `argv[0]`

Verified for this filing: a process started as `exec -a -zsh /bin/sleep 20`
shows `COMM=-zsh` in `ps` but `proc_name` returns `sleep`. So a login
shell's `-zsh` never reaches either guard, and a shell started through a
symlink or renamed binary is identified by its image name. The branch's
`6f1c3b46` already states this (`StuckMouseReportGuard.swift:53-54`) and
dropped the `-` strip; the shared helper's comment should keep that fact.
`sysctl`'s `kinfo_proc.kp_proc.p_comm` is the same field, truncated to
`MAXCOMLEN` (16) — long enough for every shell name in either list, and it
would make the name available from the group query without a second call
(Open question 1).

### The two lone-group tests are not identical

`count == 1` and `members == [pid]` differ when the group's leader has
exited and one non-leader member remains: the count is 1 but the surviving
pid is not the pgid. In that state #0393 then asks `proc_name(pgid)` about a
dead pid, gets nil, and stands down; #0411 fails the `== [pid]` comparison
and stands down. Both fail closed, by different routes. The helper should
pick one and test it.

### Existing process helpers in `Runtime/`

- `ProcessInspector.identity(pid:)` — `proc_pidpath` + `proc_name`, returns
  whatever succeeded (`ProcessInspector.swift:126-138`).
- `ProcessMetricsReader.readName(pid:)` — `proc_name` (`ProcessMetricsReader.swift:211-216`),
  `nonisolated`, part of the system-metrics reader family.
- Other `foregroundPid` readers that need only the pid or name, not group
  membership: `ProcessStatusPaneContent.swift:372`, `AppStateStore.swift:2327`
  (bell decisions, `BellDecisionHistory.swift:97-102`).

None of these lists a process group. The helper could live in `Commands/`
next to its two callers or in `Runtime/` next to these (Open question 2).

### Constraints

- Both guards run inside `NSEvent` local monitors on the main thread
  (`BattyApp.swift:83-86`); the helper is synchronous and must stay cheap.
  #0393 checks key code and modifiers before any process call
  (`PlainShellKeyRewrite.swift:81-83`) so plain typing never pays for it;
  keep that ordering.
- `PlainShellKeyRewrite` is `public` (the app target calls it);
  `StuckMouseReportGuard` is internal. The helper's access level follows
  whichever caller needs it.
- `docs/swiftui-observation-rules.md` is not engaged: neither guard writes
  observed state.

## Open questions

1. **Which mechanism?** `proc_listpgrppids` (libproc, the family
   `ProcessMetricsReader` already uses, undocumented count semantics, needs
   a separate `proc_name` call) or `sysctl(KERN_PROC_PGRP)` (one call
   returns pid, `p_comm` and `p_stat` for every member, so the name and a
   zombie filter come for free; more code). Both agree on this host. The
   filer leans to whichever lets the helper return pid + name + count from
   one call, but did not decide.
2. **Where does it live** — `Commands/` beside its callers, or `Runtime/`
   beside `ProcessInspector` / `ProcessMetricsReader`?
3. **fish, nu, elvish: in or out, per consumer?** #0393 excludes fish on the
   unverified claim that fish binds `CSI 27;2;13~`; #0411 includes fish, nu
   and elvish on the unverified claim that withholding a click costs nothing
   there. Neither has been run. If fish really handles the key, the
   asymmetric answer (out of the key rewrite, in the click guard) is
   correct and the helper exposes one list plus per-consumer exclusions. If
   it does not, one list serves both. Decide after criterion 3's check.
4. **Member cap.** #0393 reads at most 8 pids; #0411 reads all. A shell at
   its prompt has a group of 1, so the cap only matters for the "not lone"
   answer, where any count > 1 suffices. Keep a small cap or read all?
5. **Sequencing.** The obvious order is: merge `issue/0411` as it stands,
   then do this on `main`. The alternative — have #0411 adopt the helper
   before it merges — delays a user-reported bug for a refactor. The filer
   assumes the former; the user may prefer otherwise.
6. **Target release.** After 1.2.0 on `main` (next minor), per the filing
   instruction. Nothing here is user-visible for zsh/bash users.

## Testing notes

- Unit tests run with `./build.sh unit` on the host (fast, no UI). The
  helper's `posix_spawn` test spawns real `sleep` processes in a fresh
  process group and reaps them; it signals readiness structurally
  (`posix_spawn` returns the pid; the group exists immediately) and needs
  no waiting. Keep it free of `Task.sleep` / polling.
- UI tests (`BattyUITests/ShiftEnterTests`, `BattyUITests/StuckMouseModeClickTests`)
  run **only inside the Tart VM** via `tools/run-ui-tests-vm.sh`, never on
  a host Mac (AGENTS.md "UI test automation"). Commit first; the runner
  tests `git archive HEAD`.
- The fish / nu / elvish check in criterion 3 is a by-hand Beta check; the
  VM image has zsh only, so record the observation in `## Work log` rather
  than adding a UI test that needs a shell the VM lacks.
