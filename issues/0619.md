## Review

Approved first pass. The reviewer read `git diff main...HEAD` against `docs/swiftui-observation-rules.md` and the swift-guidance AppKit-interop rules:
- Model → AppKit runs only in `makeNSView`/`updateNSView` (plus the event-origin snap-back), writes no observed state and changes no responder. Every AppKit call is behind a diff.
- Echo guard: `applyingModelChange` swallows the notifications `reloadData`/`reloadItem`/`expandItem`/`collapseItem`/`selectRowIndexes` post. - Pane rows are unselectable (`shouldSelectItem`) and absent from type-select. Drag is limited to this outline's own Session drags (`draggingSource ===`), so multi-window is safe. Reused cells are always reconfigured in `viewFor`, and the cell closures capture the coordinator weakly.
- The Session Theme switch path (style change restyles every cell from `updateNSView`) is covered by `sessionSwitchUpdateConstraintRequestsStayUnderCeiling`, whose Session 2 has its own Theme and which converged under the lowered ceilings.
- Review changed: `BattyUITests/README.md`'s `session-sidebar` row now says it is the `NSOutlineView`, not the List.
- Not verifiable here: the emphasized-row path (`SidebarCellHostingView.emphasized`, which resets two cells' `rootView` when a model-driven switch lands while the outline is first responder in a key window). The probe window can't become key. The same goes for real mouse clicks, drags and context menus on hosting cells. ## Description

**Related to #0604 and #0601.** A Session switch makes about 16 `_postWindowNeedsUpdateConstraints` requests per Sidebar row. About 12 of them come from the `List(selection:)` binding in `SessionSidebarView`: they go away only when the binding's value stops changing. #0604 cut the row bodies' own selection reads, but the binding still scales with the number of Sessions. With the #0604 fix, the Sidebar alone makes 180 requests per switch at 4 Sessions and 372 at 16. This is the per-switch layout work that sits next to AppKit's update-constraints convergence cap, which is what crashed Prod in #0601 with about 19 live Sessions.

Goal: a Session switch's Sidebar cost doesn't grow with the number of Sessions, and the Sidebar keeps:
- arrow-key navigation between Session rows (skipping Pane rows);
- type-select;
- VoiceOver's selected-row semantics (the same class of regression #0579 describes for Background Sets).

When this lands, lower `SessionDetailLayoutConvergenceTests.sessionCountMargin` (212 today) to what's measured plus noise.

## Root cause

Confirmed by measurement (plan's table): every SwiftUI `List` and `Table` variant posts update-constraints requests for every cell when its selection value, any row, or an injected environment value changes, whatever the row content or selection plumbing. The Sidebar's `List(selection:)` therefore cost about 16 requests per Session row on every switch, even though #0604 had already cut the row bodies to the two rows a switch crosses.

## Fix

As planned: the Sidebar's `List` is now `SessionSidebarOutline`, an `NSOutlineView` (`.sourceList`) in an `NSViewRepresentable`, with one `NSHostingView` cell per Session row and Pane row.

- `SessionSidebarCoordinator.apply(outline:style:)` is the model → AppKit direction, run only from `makeNSView`/`updateNSView` (and from a rejected user selection to snap back). It diffs against what the outline shows: `reloadData` only when the Sessions change, `reloadItem(_:reloadChildren:)` only when a Session's Panes change, expand/collapse only where `isPaneListExpanded` differs, cell/row-view restyle only when `SidebarRowStyle` changes, and one `selectRowIndexes` on a switch. It writes no observed state and never changes a responder. `applyingModelChange` swallows the selection and expansion notifications those calls post.
- The data source answers from the coordinator's own snapshot of Sessions and per-Session Panes, never from the live model, so row indices always match the outline's items.
- AppKit → model: `outlineViewSelectionDidChange` calls `selectSessionFromSidebar(id:)` (event-origin); a rejected id snaps the outline back. `outlineViewItemDidExpand/DidCollapse` write `isPaneListExpanded`. `shouldSelectItem` is false for Panes (replaces `.selectionDisabled()`, #0258), `typeSelectStringFor` returns the Session title. Drag reorder via `pasteboardWriterForItem`/`validateDrop` (retargeted to root positions)/`acceptDrop` → `moveSession(from:toRootIndex:)` → `moveSessions(fromOffsets:toOffset:)`.
- `SidebarOutlineRowView` replaces `SidebarRowBackground` (#0135): with a themed/see-through fill it paints the fill, draws the tint on a selected Session row instead of the system block, and reports `interiorBackgroundStyle = .normal`.
- `SessionSidebarRow` is the Session cell's root (no `DisclosureGroup`, no Pane `ForEach`); every accessibility label, value and identifier (`session-row.<title>`, `pane-row.<uuid>`, `pane-eye-toggle.<uuid>`, `pane-background-settings.<uuid>`, `menu.sidebar.remind.<title>`) is unchanged, and the outline carries `session-sidebar`.

Small additions beyond the plan:
- `SidebarCellHostingView` follows the row view's selected-and-emphasized state and renders its content with a white foreground and `backgroundProminence(.increased)`, so the selected row's text reads against the native accent highlight (an `NSHostingView` has no `backgroundStyle` of its own).
- `outline.columnAutoresizingStyle = .firstColumnOnlyAutoresizingStyle` and the column's `.autoresizingMask`, so the one column fills the Sidebar width.
- Stale comments that described the Sidebar as a `List` were updated (`WindowRuntime.selectSessionFromSidebar`/`setSelectedSession`, `SidebarSelectionGuardTests`, `PaneSidebarTests.chevron`).
- `switchRequestCeiling` dropped from `[0: 520, 12: 770]` to `[0: 340, 12: 410]`: the 12-Session maximum fell from about 660 to 350 (more than 100), so per the comment's rule both became the new maxima (287, 350) plus about 17%.

### Decision

Replace the Sidebar's SwiftUI `List` with an `NSOutlineView` inside an `NSViewRepresentable`. Each row is an `NSHostingView` whose SwiftUI content is today's row content, so a switch re-renders only the two cells whose `session.isSelected` flips, and the outline moves its native selection. Arrow keys (skipping Pane rows), type-select, VoiceOver's selected row, the disclosure triangle and its animation, the `.sourceList` selection highlight and the context menu all stay native, as they are under today's `List`, which is itself an `NSOutlineView`.

**Trade-offs to state to the user (not blocking; the three named behaviours are kept):**
- The Sidebar becomes AppKit-backed code that Batty owns (about 300 lines). Structure, expansion and selection are synced by hand, not by SwiftUI's `List`.
- The look is close to today's but not guaranteed identical: row heights come from `rowSizeStyle = .default`, so Pane rows are standard height rather than `listRowInsets`' 2-point insets, and the indentation is the outline's. The sidebar material should still come from `NavigationSplitView`'s sidebar column. User checklist items 1–4 cover this.
- A switch between two Sessions with *different* Session Themes changes `accent` and the see-through tint for every row, so every cell's root is updated. That's O(rows) on those switches only, the same as today. The scaling test's fixture has no Session Themes.

### Files

**1. New `BattyKit/Sources/BattyKit/Views/SessionSidebarOutline.swift`.** All `@MainActor` (the default).

- `struct SessionSidebarOutline: NSViewRepresentable`, `NSView == NSScrollView`. Stored properties:
  - `windowRuntime: WindowRuntime` and `store: AppStateStore`;
  - `style: SidebarRowStyle`, a new `Equatable` struct `{ accent: Color?; sidebarFill: Color?; selectionTint: Color? }`;
  - `actions: SidebarRowActions`, a struct of closures for the parent's `@State` sheet triggers: `onRename(SessionRuntime)`, `onTheme(UUID)`, `onSetColor(UUID)`, `onBackground(UUID)`, `onPaneBackground(UUID)`. It's not `Equatable`; the coordinator just replaces it on every update.
- `makeNSView`: an `SessionSidebarOutlineView` (below) with one `NSTableColumn` as `outlineTableColumn`. Set:
  - `headerView = nil`, `style = .sourceList`, `rowSizeStyle = .default`;

  Wrap it in an `NSScrollView` with `drawsBackground = false`, `hasVerticalScroller = true` and `autohidesScrollers = true`. Then call `context.coordinator.apply(...)` once (below). No `makeFirstResponder` anywhere in this file.
- `updateNSView`: `context.coordinator.update(representable: self, outline:)`. This is the only place SwiftUI drives the outline, and it calls only `coordinator.apply`.
- `final class SessionSidebarOutlineView: NSOutlineView`. Internal, so tests can find it with `probe.allViews()`. No overrides needed. It exists as a named class for tests and for `frameOfOutlineCell` if the indentation needs tuning.
- `final class SessionSidebarCoordinator: NSObject, NSOutlineViewDataSource, NSOutlineViewDelegate`:
  - State: `windowRuntime`, `store`, `style`, `actions`, `sessions: [SessionRuntime]`, `paneIDs: [ObjectIdentifier: [UUID]]` (each Session's pane ids at the last reload), and `applyingModelChange = false`.
  - Items are the model objects themselves: `SessionRuntime` at the root, and `PaneRuntime` children from `session.tree.panesSortedByColumnThenRow`. Both are classes, so NSOutlineView's identity comparison is stable.
  - **`apply(outline:)`**, the model → AppKit direction. It runs with `applyingModelChange = true` for its whole body, reset in a `defer`. It reads observed state, which makes `updateNSView` depend on exactly these reads, and it calls AppKit only where a value differs from what the outline already shows. Order:
    1. *Structure.* If `windowRuntime.sessions` (by `ObjectIdentifier`) differs from `sessions`, call `reloadData()`. Otherwise, for each Session whose `tree.panesSortedByColumnThenRow.map(\.id)` differs from `paneIDs`, call `reloadItem(session, reloadChildren: true)`. Record the new snapshot.
    2. *Expansion.* For each Session, if `session.isPaneListExpanded != outline.isItemExpanded(session)`, call `expandItem(session)` or `collapseItem(session)`.
    3. *Style.* If `style` changed, store it, then update every available row view (`enumerateAvailableRowViews`) and its cell (step 5's `configure`).
    4. *Selection.* If `windowRuntime.selectedSession` has a row and `outline.selectedRow != row`, call `selectRowIndexes([row], byExtendingSelection: false)`.

    A Session switch therefore does one `selectRowIndexes` and nothing else here (the scaling test proves it). The doc comment on `apply` says that, and why the outline is synced in the representable update rather than in an action: it writes no observed state, changes no responder, and the structure calls run only on structural changes, which the convergence tests below settle.
  - **Data source.** `numberOfChildrenOfItem` returns `sessions.count` for `nil` and `session.tree.panesSortedByColumnThenRow.count` for a Session. It returns 0 for a Pane. `child(_:ofItem:)` and `isItemExpandable` (true for `SessionRuntime`, including single-Pane Sessions, matching `testChevronPresentForSinglePaneSession`) follow the same shape.
  - **Cells.** `viewFor(_:item:)` reuses with `makeView(withIdentifier:owner:)` for the identifiers `session-cell` and `pane-cell`. Otherwise it creates the cell and sets `sizingOptions = []` so the cell adds no intrinsic-size constraints (the table sets its frame). Then `configure(_:for:)` sets `rootView`:
    - Sessions get `SessionSidebarRow(session:store:windowRuntime:accent:onRename:...)` (see 2) with `.environment(\.appStateStore, store)`, since a cell is its own SwiftUI root and inherits nothing from the window's tree.
    - Panes get `SidebarPaneCell(pane:session:windowRuntime:accent:onBackgroundSettings:)`.
    - The cell types are `NSHostingView<AnyView>`. They are rebuilt only on reload or a style change, so `AnyView` costs nothing on a switch.
  - **Row views.** `rowViewForItem` returns a `SidebarOutlineRowView` with `fill`/`tint` from `style`.
  - **`shouldSelectItem`** returns `item is SessionRuntime`. This replaces `.selectionDisabled()` and is the #0258 guard at the source. A click on a Pane row never selects it, and arrow keys skip Pane rows (measured).
  - **`typeSelectStringFor`** returns `(item as? SessionRuntime)?.title`, and `nil` for Panes so type-select never lands on them.
  - **`outlineViewSelectionDidChange`** is the AppKit → model direction, the user's click, arrow key or type-select. `guard !applyingModelChange`, then if `outline.item(atRow: selectedRow) as? SessionRuntime`, call `windowRuntime.selectSessionFromSidebar(id: session.id)`. It's an event-origin write, unchanged in meaning. If the setter rejects the id (`selectedSessionID` unchanged), call `apply` again so the outline snaps back. That replaces the List's "re-read the getter" snap-back.
  - **`outlineViewItemDidExpand` / `DidCollapse`** (notifications): `guard !applyingModelChange`, then write `session.isPaneListExpanded = true/false`. This is the user's disclosure-triangle click, which today goes through `DisclosureGroup(isExpanded: $session.isPaneListExpanded)`.
  - **Drag reorder** (replaces `.onMove`):
    - `pasteboardWriterForItem` returns, for a Session only, an `NSPasteboardItem` with `dragType` = `"co.sstools.batty.sidebar-session"` and the Session's index.
    - `validateDrop` accepts only drags whose `draggingSource` is this outline. It retargets any proposal to the root with `setDropItem(nil, dropChildIndex:)`: a drop on a Session or inside its children becomes the index before or after that Session. It returns `.move`.
    - `acceptDrop` calls `moveSession(from:toRootIndex:)`, which calls `windowRuntime.moveSessions(fromOffsets: IndexSet(integer: from), toOffset: to)`. NSOutlineView's root drop index and `onMove`'s `toOffset` both count positions before removal, so it passes straight through. `moveSession` is internal so a unit test can call it without an `NSDraggingInfo`.
- `final class SidebarOutlineRowView: NSTableRowView` with `fill: NSColor?` and `tint: NSColor?`. Setting either calls `needsDisplay = true`. This replaces `SidebarRowBackground` and keeps the #0135 behaviour:
  - `drawBackground(in:)` fills `fill` when it's set, and calls `super` otherwise.
  - `drawSelection(in:)`: with `fill` set, fill `tint` (if any) over the row bounds and suppress the system selection chrome. With no `fill`, call `super` for the native source-list highlight.
  - Colors come from `NSColor(swiftUIColor)`.

### User checklist

1. The Sidebar looks like a sidebar: translucent sidebar material in a plain window, row heights and indentation close to before, Pane rows indented under their Session.
2. Click a Session row: it highlights with the native accent selection and the detail switches. Click a Pane row: its Session is selected and that Pane focused, and the Pane row itself never highlights (#0258).
3. Click a row, then Up/Down. Selection moves Session to Session and skips expanded Pane rows. Type the start of a Session's name and it's selected.
4. Themed and see-through windows: rows paint the sidebar fill, and the selected row shows the subtle tint, not the system's dark gray block (#0135).
5. VoiceOver: on a Session row it announces the title, then "selected" or "unselected" and the rest of the value. Moving with VO keys through the outline reports the selected row.
6. Disclosure triangles expand and collapse with animation. Hiding a Pane expands its Session's list.
7. Drag a Session row to reorder. Right-click a row for the context menu (Rename, Set Color…, Remind, Close, …).
8. With 15 or more Sessions, switching Sessions (Cmd-1…9, clicks) feels as fast as with 4.

## Measurements (from #0604)

Sidebar-only probe, per-switch requests, switches `[1, 2, 3, 0]`, each case run alone:

| Variant | 4 Sessions | 16 Sessions | 16 − 4 |
|---|---|---|---|
| `main` before #0604 | [184, 185, 185, 184] | [400, 401, 401, 400] | 216 |
| #0604 fix (rows read `session.isSelected`), binding unchanged | [180, 181, 181, 180] | [372, 373, 373, 372] | 192 |
| #0604 fix + `Equatable` row conformance, no `.equatable()` | same | same | 192 |
| #0604 fix + binding via `$windowRuntime.<computed property>` instead of `Binding(get:set:)` | same | same | 192 |
| #0604 fix + `.equatable()` on the row | crashes at hosting | | |
| #0604 fix + constant binding | 42 | 90 | 48 |
| rows' selection reads keyed on `false` + constant binding | 0 | 0 | 0 |

With the #0604 fix, a switch evaluates the parent body twice and only the two changed rows' bodies (twice each), at 4 and at 16 Sessions alike. So the binding cost isn't in body evaluation that SwiftUI exposes to the app. It's in what the `List` does with the changed selection value across all its rows. The remaining 48 with a constant binding (about 4 per row) comes from the two changed rows re-rendering. That cost also grows with row count.

## Already ruled out (don't retry)

- **`.equatable()` on `SessionSidebarRow`.** It crashes SwiftUI at hosting with `_DisclosureGroupContainer<...> may not have Body == Never` (`DynamicProperty.swift:380`), because the row's body is a `DisclosureGroup` inside a sidebar `List`.
- **`Equatable` conformance without `.equatable()`.** No change.
- **A keypath binding** (`$windowRuntime.<computed property>`) instead of `Binding(get:set:)`. No change.
- **Dropping `List(selection:)` for tap actions with row-level styling.** That loses `NSTableView` arrow-key navigation, type-select and VoiceOver's selected-row semantics. #0604's plan ruled it out without a user decision. Any approach that changes how selection reaches the `List` needs the user's sign-off on those three behaviours.

## Expected behavior

The Sidebar's per-switch request count is flat in Session count, or close to it: the 16-vs-4 difference is well under today's 192. Arrow keys, type-select, VoiceOver "selected"/"unselected", the #0258 Pane-row guard and the see-through selection tint all behave as they do today.

## Actual behavior

About 12 requests per Sidebar row per switch from the binding, plus about 4 per row from the two changed rows' re-render. That's 192 more at 16 Sessions than at 4.
