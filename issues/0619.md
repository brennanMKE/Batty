## Description

**Related to #0604 and #0601.** A Session switch makes about 16 `_postWindowNeedsUpdateConstraints` requests per Sidebar row. About 12 of them come from the `List(selection:)` binding in `SessionSidebarView`: they go away only when the binding's value stops changing. #0604 cut the row bodies' own selection reads, but the binding still scales with the number of Sessions. With the #0604 fix, the Sidebar alone makes 180 requests per switch at 4 Sessions and 372 at 16. This is the per-switch layout work that sits next to AppKit's update-constraints convergence cap, which is what crashed Prod in #0601 with about 19 live Sessions.

Goal: a Session switch's Sidebar cost doesn't grow with the number of Sessions, and the Sidebar keeps:
- arrow-key navigation between Session rows (skipping Pane rows);
- type-select;
- VoiceOver's selected-row semantics (the same class of regression #0579 describes for Background Sets).

When this lands, lower `SessionDetailLayoutConvergenceTests.sessionCountMargin` (212 today) to what's measured plus noise.

## Current state (verified on `issue/0604` at `2cbe4db1`)

- `BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift`:
  - `body` is `List(selection: sidebarSelection) { ForEach(windowRuntime.sessions) { SessionSidebarRow(...).tag(session.id as UUID?) } }`.
  - `sidebarSelection` is `Binding(get: { windowRuntime.selectedSessionID }, set: { windowRuntime.selectSessionFromSidebar(id: $0) })`. The setter is the #0258 guard: it rejects Pane ids and `nil`, and the List snaps back to the real selection.
  - `SessionSidebarRow` (`private struct`, #0604) reads `session.isSelected` for its `accessibilityValue` and its `SidebarRowBackground`. Pane rows inside it are `.selectionDisabled()`.
- `BattyKit/Sources/BattyKit/Runtime/SessionRuntime.swift`: `isSelected` is observed, `public internal(set)`. It's written only by `WindowRuntime.applyTerminalVisibility`, and only for the two Sessions a switch crosses.
- `BattyKit/Tests/BattyKitTests/SessionDetailLayoutConvergenceTests.swift`:
  - `sessionSwitchRequestsDoNotScaleWithSessionCount` checks that a switch among the same four Sessions with 16 Sessions in the window requests at most `sessionCountMargin` more than with 4.
  - `sessionCountMargin = 212`, which is the measured 192 plus 20. Its comment names the remaining `List(selection:)` cost.

## Measurements (from #0604)

Sidebar-only probe, per-switch requests, switches `[1, 2, 3, 0]`, each case run alone:

| Variant | 4 Sessions | 16 Sessions | 16 − 4 |
|---|---|---|---|
| `main` before #0604 | [184, 185, 185, 184] | [400, 401, 401, 400] | 216 |
| #0604 fix (rows read `session.isSelected`), binding unchanged | [180, 181, 181, 180] | [372, 373, 373, 372] | 192 |
| #0604 fix + `Equatable` row conformance, no `.equatable()` | same | same | 192 |
| #0604 fix + binding via `$windowRuntime.<computed property>` instead of `Binding(get:set:)` | same | same | 192 |
| #0604 fix + `.equatable()` on the row | crashes at hosting | | |
| #0604 fix + constant binding | 42 | 90 | 48 |
| rows' selection reads keyed on `false` + constant binding | 0 | 0 | 0 |

With the #0604 fix, a switch evaluates the parent body twice and only the two changed rows' bodies (twice each), at 4 and at 16 Sessions alike. So the binding cost isn't in body evaluation that SwiftUI exposes to the app. It's in what the `List` does with the changed selection value across all its rows. The remaining 48 with a constant binding (about 4 per row) comes from the two changed rows re-rendering. That cost also grows with row count.

## Already ruled out (don't retry)

- **`.equatable()` on `SessionSidebarRow`.** It crashes SwiftUI at hosting with `_DisclosureGroupContainer<...> may not have Body == Never` (`DynamicProperty.swift:380`), because the row's body is a `DisclosureGroup` inside a sidebar `List`.
- **`Equatable` conformance without `.equatable()`.** No change.
- **A keypath binding** (`$windowRuntime.<computed property>`) instead of `Binding(get:set:)`. No change.
- **Dropping `List(selection:)` for tap actions with row-level styling.** That loses `NSTableView` arrow-key navigation, type-select and VoiceOver's selected-row semantics. #0604's plan ruled it out without a user decision. Any approach that changes how selection reaches the `List` needs the user's sign-off on those three behaviours.

## Expected behavior

The Sidebar's per-switch request count is flat in Session count, or close to it: the 16-vs-4 difference is well under today's 192. Arrow keys, type-select, VoiceOver "selected"/"unselected", the #0258 Pane-row guard and the see-through selection tint all behave as they do today.

## Actual behavior

About 12 requests per Sidebar row per switch from the binding, plus about 4 per row from the two changed rows' re-render. That's 192 more at 16 Sessions than at 4.

## Notes

- Measure with the #0601/#0602 layout probe in a Sidebar-only fixture, like #0604's scratch harness (`SessionDetailFixture` is the shared fixture). Add the scratch harness to the branch, and delete it before the code commit.
- Follow `docs/swiftui-observation-rules.md`. The binding's setter is an event-origin write. Don't move it into a `Task`, and don't write observed state from `body` or a representable update.
- Possible directions, all unmeasured:
  - an `NSTableView`/`NSOutlineView`-backed Sidebar that keeps native keyboard and VoiceOver selection;
  - a `List` whose selection value changes without re-diffing every row;
  - splitting rows so that unchanged rows' cells aren't touched.

  The plan phase should measure before choosing, and bring any change to keyboard or VoiceOver behaviour to the user first.
- Daily UI run classes to watch: `SidebarTests`, `PaneSidebarTests`, `KeyboardShortcutTests`, `BellFeedTests`, `MultiWindowTests`.
- Depends on #0604 landing on `main`. Its `SessionSidebarRow`, `SessionRuntime.isSelected` and `sessionCountMargin` exist only on `issue/0604` as of filing.
