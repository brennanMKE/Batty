## Description

The per-pane rows under each Session heading in the left-column sidebar (added in #0259) must always be sorted **by column, then row** — each column's vertically-stacked panes grouped together top-to-bottom, then the next column — and must keep that order as the split layout changes. The user's original request, verbatim:

> "The list of panes under the session heading in the left column should always be sorted by row then column. New panes could be added at any time but should maintain this sort order."

To be precise about the sort keys: each pane carries a `column/row` position derived from the split tree (#0259, label form `col/row`). The required order is **column-major**: primary key = `column` ascending, secondary key = `row` ascending — which matches the order the label prints (`column/row`).

## Correction (2026-07-09)

The first round shipped **row-major** order (row, then column) based on the original request's wording. The user reviewed it in the running app and clarified they want the opposite — **column-major**. Their example: with a layout where the middle column has two stacked panes `2/1` (top) and `2/2` (below), the shipped row-major order listed `1/1, 2/1, 3/1, 2/2`, splitting the stacked pair `2/1`/`2/2` apart with `3/1` between them. The wanted order is `1/1, 2/1, 2/2, 3/1` — each column's panes grouped together top-to-bottom, then the next column. This branch (`issue/0263-2`) changes the shipped row-major sort to column-major.

## Current behavior

As shipped by the first round (merged from `issue/0263`), the sidebar sorts pane rows **row-major** via `SplitTree.panesSortedByRowThenColumn` — primary key `row`, secondary `column`. For a three-column layout where the middle column is split into two stacked panes, this lists `1/1, 2/1, 3/1, 2/2`: the stacked pair `2/1`/`2/2` is split apart with `3/1` between them.

## Expected behavior

- Pane rows under a Session heading are ordered by `column` ascending, then `row` ascending within each column — column-major. The example above lists `1/1, 2/1, 2/2, 3/1`, keeping each column's vertically-stacked panes together.
- The order holds continuously: panes added by splits (at any time, in any pane), removed panes, and rearranged layouts all re-sort into column-then-row order rather than drifting.

## Resolution notes

> 🟢 Resolved 2026-07-09 — the sidebar pane rows are now sorted column-major (column ascending, then row) via a derived `SplitTree` accessor, so each column's stacked panes stay together top-to-bottom before the next column.

This is the corrected behavior. The first round (also `resolved`, merged from `issue/0263`) shipped row-major; the user reviewed it and clarified they wanted column-major — see `## Correction (2026-07-09)`. Visual confirmation of the sidebar order is the user's sign-off — see Gotchas.

## Root cause

The first round implemented the issue's original wording ("row then column") literally as row-major. In practice that split vertically-stacked panes apart in the list (a middle column's `2/1` and `2/2` were separated by `3/1`), which read as unsorted. The user's actual intent was column-major grouping.

## Fix

Changed the sidebar sort from row-major to column-major:

- `SplitTree.swift` — the pure computed accessor was renamed `panesSortedByRowThenColumn` → `panesSortedByColumnThenRow`, and its comparator changed from `(row, column)` to `(column, row)` ascending (column primary, row secondary). Still derived fresh from `panePositions` each access, no stored state, self-maintaining through splits/closes/rearrangements. `SplitTree` stays a pure value type.
- `SessionSidebarView.swift` — the pane `ForEach` uses the renamed accessor. `PaneRow` label content and `allPanes` are untouched — this is purely a render-order change. Hidden panes (#0256) keep their column-major slot.

## Notes

- **View side** — `BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift`: the sidebar pane `ForEach` feeding `PaneRow`. `PaneRow` already reads `session.tree.panePositions[pane.id]` for its label, so the sort inputs are already at hand.
- **Sort inputs** — `SplitTree.panePositions` / `PanePosition.row` and `.column` in `BattyKit/Sources/BattyKit/Model/SplitTree.swift`. The first round added the accessor `SplitTree.panesSortedByRowThenColumn` sorting by `(row, column)`; the rework flips it to sort by `(column, row)` (and the name should follow).
- The sort should be **derived** — recomputed from `panePositions` whenever the tree changes — not a stored order that needs maintenance. Since `panePositions` is itself derived from tree shape, sorting on it self-maintains through splits, closes, and rearrangements.
- Cross-references: **#0259** introduced these pane rows and the position derivation. **#0260** also edits the same `SessionSidebarView` pane-row path (row *labels* / auto-naming); the sort is orthogonal to the naming, but whoever implements either should be aware of the other.
