## Description

While `tools/run-ui-tests-vm.sh` was running the `BattyUITests` suite in a Tart VM, the user heard tones on the host Mac. Turning the host volume down made them quieter, which places them on the host's audio output, not on another device. Nothing on the host was making sound; the guest was.

**Cause (verified).** `tools/run-ui-tests-vm.sh:355` boots the clone with

```sh
tart run "$CLONE" --no-graphics --dir=run:"$EXPORT":ro >"$RESULTS_DIR/tart-run.log" 2>&1 &
```

and never passes `--no-audio`. Tart 2.32.1's `tart run --help` lists the flag as `--no-audio  Disable audio pass-through to host.`, so by default every sound the guest makes is played on the host's output. `--no-graphics` only drops the window; the guest's audio device still exists and is still routed to the host. (`--suspendable` also removes the audio device, but it changes other devices too; it is not the fix.) No file in this repo mentions `--no-audio` (`grep -rn -- "no-audio"` over `*.md` and `*.sh` matches nothing).

**What in the guest makes sound.** Every audible path in Batty's own code, by grep (`NSSound|NSBeep|AudioServicesPlay|AVAudioPlayer|\.sound = ` over `BattyKit/Sources` and `Batty`), is one of three; the vendored `libghostty-spm` package plays nothing itself (`BattyKit/.build/checkouts/libghostty-spm/Sources` has no `NSSound`/`NSBeep`/`AudioServices`; `GHOSTTY_ACTION_RING_BELL` is only forwarded to `terminalDidRingBell`, `GhosttyTerminal/InMemory/TerminalCallbackBridge.swift:50-53`).

1. **System notifications.** `BellNotifier.post` (`BattyKit/Sources/BattyKit/Runtime/BellNotifier.swift:73-96`) sets `content.sound = .default` (`:85-86`) when `playSound && SettingsPreference.resolvedBellSound()`. Both settings default to on in a fresh guest (`Settings/SettingsPreferences.swift:24-25`, `defaultBellSound`/`defaultSystemNotifications` are `true`), and the delegate's `willPresent` answers `[.banner, .sound]` (`BellNotifier.swift:147`), so the sound plays even while Batty is frontmost. `shouldPost` (`:98-111`) still requires that Batty is not the active app or that the entry is unseen. `playSound` is `true` for bells and OSC notifications and is the CLI's `--sound` flag for `batty notify` (`XPC/AppXPCService.swift:225`, `recordCLINotification(... playSound: request.sound)`; `batty/NotifyCommand.swift:53-54`, default `false`). `postFootprintWarning` (`:120-132`) has the same sound line but fires only when Batty is not active, which no test arranges.
2. **AppKit's beep for a key equivalent nothing handles.** Not a Batty call: when a chord ends unhandled, AppKit itself beeps. `AuxiliaryWindowShortcutTests` (#0480) presses twelve chords while Settings, then Help, is key (`BattyUITests/AuxiliaryWindowShortcutTests.swift:31-44`: Shift-Cmd-X, Cmd-T, Cmd-D, Shift-Cmd-D, Cmd-G, Cmd-J, Cmd-E, Cmd-N, Option-Cmd-Left, Shift-Cmd-], Option-Cmd-1, Ctrl-Cmd-Left) and then Cmd-W (`:156-158`), and Cmd-V then Cmd-W in the paste tests (`:197-198`). By `docs/shortcuts.md:245-263` the menu still sees every one of those chords and the item's action resolves no target and does nothing, with enablement deliberately not gated, so by the code they are consumed silently; a beep needs a chord that no enabled item claims. `ProjectsEditorQuitTests.testCmdWWithASheetOverTheEditorLeavesTheSheetAndTheEditorAlone` (`BattyUITests/ProjectsEditorQuitTests.swift:97-110`) presses Cmd-W over the unsaved-edits sheet; the Close action (`Commands/BattyCommands.swift:598-611`) routes that to `closeProjectEditor(from:)`, which returns without calling `performClose` while a sheet is attached (`Runtime/AppStateStore+Quit.swift:81-86`), so by the code that one is silent too. Treat these as possible, not confirmed: nothing in this issue depends on which chord beeps, because the fix mutes the whole guest.
3. **`NSSound.beep()` in the shortcut recorder** (`BattyKit/Sources/BattyKit/Shortcuts/RecorderView.swift:85`, a rejected key while recording). No UI test reaches it: `grep -rn -i recorder BattyUITests` matches nothing.

**Which tests ask for sound, by grep** (`bell|notify|sound` over `BattyUITests` matches four files: `BellFeedTests.swift`, `CLIBackgroundSessionTests.swift`, `CLIRemoteControlTests.swift`, `Support/BattyCLIHarness.swift`):

The target Session is not selected, so the entry is unseen and `shouldPost` passes; `content.sound = .default`. The test's own comment says the audible effect is not observable on screen (`:196-197`). |

`BattyUITests/Support/BattyCLIHarness.swift` has no notify helper. Its Bell Feed helpers, `openBellFeed` (`:364-376`) and `bellEntryIDs` (`:378-381`), read the popover and make no sound.

**No test depends on sound (verified).** Every bell and notification assertion above checks Bell Feed entries, badge counts or exit codes (`BattyScreen.bellEntryIDs`, `bell-feed-entry.*` identifiers, `badgeCount`, `result.status`); `grep -rn -i sound BattyUITests` finds only the one `--sound` argument and the comment beside it. Muting the guest changes nothing a test observes.

## Steps to reproduce

1. On the host, with the output volume up, run `tools/run-ui-tests-vm.sh BattyUITests/CLIBackgroundSessionTests`.
2. Wait for `testNotifyToABackgroundSessionIsUnseenAndCollapses` to reach its `--sound` notify.
3. Listen. The notification tone plays on the host. Lowering the host volume lowers it.

## Resolution notes

> 🟢 Resolved 2026-10-12. The UI-test runner now boots the guest with `tart run … --no-graphics --no-audio`, so guest sounds no longer play through the host's speakers. `docs/ui-testing-vm.md` explains why.

Owed to the user: listen during a VM run and confirm there are no tones. The fix still has to be cherry-picked onto `release/1.2` (Gotchas).

## Root cause

`tools/run-ui-tests-vm.sh` started the clone with `tart run "$CLONE" --no-graphics --dir=run:…:ro`. Tart routes guest audio to the host output by default (`tart run --help`: "--no-audio  Disable audio pass-through to host."). One test asks for sound on purpose: `CLIBackgroundSessionTests.testNotifyToABackgroundSessionIsUnseenAndCollapses` runs `batty notify --sound`, and `BellNotifier` sets `content.sound = .default`. `BellFeedTests.testBellByteProducesFeedEntry` plays a sound too, but only when Batty is not the active app at that moment.

## Fix

- `tools/run-ui-tests-vm.sh`:
  - adds `--no-audio` to the `tart run` line, with a comment explaining why;
  - its header step 3 and the boot log message now say the guest runs muted.
- `docs/ui-testing-vm.md`:
  - "Clone and boot" names the flag, gives the reason and says what the host hears without it;
  - "Known limits" notes that a runner copy without the flag still plays guest sound.
- `~/Developer/Homelab/cameron/tart-ui-test-vm.md` already had the rule in Homelab commit `95dd721`, so it was confirmed and not edited.
