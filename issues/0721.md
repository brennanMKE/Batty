## Description

`scripts/release.sh` runs `rm -rf "$BUILD_DIR"` (`BUILD_DIR="$REPO_ROOT/build"`) twice: at the start ("==> Cleaning previous build", line 131) and at the end ("==> Cleaning up build artifacts", line 550). The VM runners write their evidence under the same folder: `tools/run-ui-tests-vm.sh` to `build/ui-tests/<run-id>/` and `tools/run-sparkle-update-vm.sh` to `build/sparkle-tests/<run-id>/`. The check logs in `build/checks/` go too.

In the 1.4.3 release (`release/1.4` at `8dd9af81`, 2026-11-22), the release ran in the same `release-1.4` worktree as the Release-tier UI runs. Its cleanup removed `build/ui-tests/` for three VM runs before anyone looked at them, including:

- `20261122-161240-36378`: the full-suite run whose two `ClipboardConfirmationTests` failures are #0720.
- `20261122-175023-17615`: the shard whose result was misreported as "no tests ran" (#0722). Without its log and `.xcresult`, the failing test and the cause are unknown.

Earlier, removing a worktree after its issue merged also lost `build/sparkle-tests/` results.

## Expected behavior

VM runner results survive a release. Options for the plan:

- `release.sh` removes only what it creates (its archive, export and DMG staging subfolders, and the Release `.app` that #0026 is about), not all of `build/`.
- Or the runners write under a results folder that `release.sh` doesn't touch, for example one outside the worktree so it also survives `git worktree remove`.

`docs/ui-testing-vm.md`, the Release tier in `issues/Issues.md` and `scripts/RELEASE.md` say where results live.

## Plan

Approach: `release.sh` removes only the paths it creates under `build/`, through one sourced helper that a selftest exercises on a temp tree. The runners keep writing where they do today (`build/ui-tests/`, `build/sparkle-tests/`), so no docs or tooling that name those paths move. Surviving `git worktree remove` is out of scope (noted in Gotchas).

## Root cause

`scripts/release.sh` ran `rm -rf "$BUILD_DIR"` at the start and end of every run. The VM runners and `build.sh` write their results and logs under the same `build/` folder, so a release deleted them.

## Fix

New sourced helper `scripts/release-cleanup.sh` defines `release_clean_owned_artifacts <build_dir> <path>...`: it validates that every path is strictly under `build_dir` (resolved with `:A`) before deleting any, removes them, then `rmdir`s `build/` only if empty. `release.sh` sources it, declares `RELEASE_OWNED` (archive, Export, exportOptions.plist, app-entitlements.plist; the `ENTITLEMENTS_PLIST` assignment moved up to the variable block) and calls the helper in place of both `rm -rf "$BUILD_DIR"` lines. The #0026 Release `.app` is still removed (it lives only in the archive and Export).

## Verification

- `zsh -n scripts/release.sh`, `zsh -n scripts/release-cleanup.sh`: clean.
- `python3 -I tools/release-cleanup-selftest.py`: `8/8 cases ok` (removes_owned_paths, missing_owned_paths_ok, removes_empty_build_dir, no_build_dir, refuses_build_dir_itself, refuses_outside_path, refuses_empty_args, release_sh_uses_helper).
- `scripts/release.sh --help`: prints usage, exit 0 (helper sourced before arg parsing).
- `release.sh` itself not run; no app code changed, so no `./build.sh`.
- Reviewer re-run (2026-11-22): `zsh -n` on both scripts exit 0; `python3 -I tools/release-cleanup-selftest.py` printed `8/8 cases ok`, exit 0; `scripts/release.sh --help` exit 0.
- Reviewer probes (scratchpad temp trees, sourcing the helper under `set -euo pipefail`): a repo path with spaces and glob characters (`my repo *[x]`) removed exactly the four owned paths and kept `build/ui-tests/`, leaving a sibling `my repo other/` untouched; `build/Export` as a symlink to a directory outside `build/` was refused (nonzero, target intact); `build/` itself a symlink to another directory removed `Export` inside the target and left the link.
