# 0721 — `scripts/release.sh` deletes VM UI-test results under `build/`, so a release run's failures can't be inspected

| | |
|---|---|
| **Status** | open |
| **Module** | Build / Testing |
| **Platform** | macOS |
| **First seen** | 2026-11-22 |
| **Target** | 1.5.0 |

## Description

`scripts/release.sh` runs `rm -rf "$BUILD_DIR"` (`BUILD_DIR="$REPO_ROOT/build"`) twice: at the start ("==> Cleaning previous build", line 131) and at the end ("==> Cleaning up build artifacts", line 550). The VM runners write their evidence under the same folder: `tools/run-ui-tests-vm.sh` to `build/ui-tests/<run-id>/` and `tools/run-sparkle-update-vm.sh` to `build/sparkle-tests/<run-id>/`. The check logs in `build/checks/` go too.

In the 1.4.3 release (`release/1.4` at `8dd9af81`, 2026-11-22), the release ran in the same `release-1.4` worktree as the Release-tier UI runs. Its cleanup removed `build/ui-tests/` for three VM runs before anyone looked at them, including:

- `20261122-161240-36378`: the full-suite run whose two `ClipboardConfirmationTests` failures are #0720.
- `20261122-175023-17615`: the shard whose result was misreported as "no tests ran" (#0722). Without its log and `.xcresult`, the failing test and the cause are unknown.

Earlier, removing a worktree after its issue merged also lost `build/sparkle-tests/` results.

## Expected behavior

VM runner results survive a release. Options for the plan:

- `release.sh` removes only what it creates (its archive, export and DMG staging subfolders, and the Release `.app` that #0026 is about), not all of `build/`.
- Or the runners write under a results folder that `release.sh` doesn't touch, for example one outside the worktree so it also survives `git worktree remove`.

`docs/ui-testing-vm.md`, the Release tier in `issues/Issues.md` and `scripts/RELEASE.md` say where results live.

## Notes

- **`scripts/` is a restricted area** (`AGENTS.md`). A change to `release.sh` needs the user's confirmation first. Changing only the runners' output folder avoids touching it.
- The end-of-run cleanup exists for #0026 (a Release `Batty.app` left in `build/` was indexed by LaunchServices beside the Debug build). Any narrower cleanup must still remove that `.app`.
- Related: #0720, #0722, #0518/#0528 (Release-tier shards).
