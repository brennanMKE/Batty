## Description

Replace the M1 single-pane window shell with a `NavigationSplitView` whose leading column is the session sidebar. Multiple sessions can coexist; selecting a session swaps the detail area. New sessions are created via a "+" toolbar button and start with one Pane / one Tab / one fresh Terminal Session in the user's home directory.

**Acceptance criteria:**
- The window now uses `NavigationSplitView` with a sidebar on the left and detail on the right.
- The sidebar shows a `List` of sessions; each row shows the session title.
- A "+" button in the sidebar's toolbar creates a new session and selects it.
- Exactly one session is selected per Window. Switching sessions instantly swaps the detail area.
- Surfaces in non-selected sessions stay alive (the shell process keeps running).

## Root cause

Feature gap. M2's foundation: hoist app state out of ContentView so multiple sessions can coexist, give each a `TerminalViewState`, and let the user pick which one is showing.

## Fix

Five new public types in `BattyKit/Sources/BattyKit/`:

- `SessionRuntime` — `@Observable` reference type holding `{id, title, terminal: TerminalViewState}`. Reference semantics matter: each session's `TerminalViewState` is the live wrapper around its libghostty surface, and we want it to survive view rebuilds.
- `AppStateStore` — `@Observable` container for the ordered `[SessionRuntime]` and `selectedSessionID`. Initializes with a single default "Session 1". Provides `addSession(title:)`, `removeSession(id:)`, `moveSessions(fromOffsets:toOffset:)`, `selectSession(at:)`. Auto-spawns a replacement when the last session is closed (PRD §6.3 — sessions don't auto-close into nothingness).
- `SessionSidebarView` — `List` with `selection: $store.selectedSessionID`, ForEach over sessions with `.onMove`, "+" toolbar button. Each row binds to `SessionRuntime` and prefers the live terminal title over the session's stored title.
- `SessionDetailView` — `ZStack` of every session's `TerminalSurfaceView`, with non-selected ones at `.opacity(0)` and `.allowsHitTesting(false)`. This is what keeps surfaces alive across session switches: every `TerminalViewState` is rendered into a SwiftUI subtree continuously; the user only sees the selected one. Empty-state `ContentUnavailableView` for the no-selection edge case.
- `RootWindowView` — composes the `NavigationSplitView` with sidebar + detail. Owns the `AppStateStore` via `@State` so each window has its own sessions list per PRD §6.6.

`Batty/ContentView.swift` collapses to a one-liner rendering `RootWindowView()`.

## Gotchas

- **Visual verification needed:** sidebar feel, session-switch responsiveness, surfaces-stay-alive behavior, "+" button click, drag-to-reorder. `xcodebuild build` passes; the rest is the user's spot-check. Resolved-not-closed.
- **All sessions render simultaneously** via the `ZStack`. With many sessions, this could be expensive — every `TerminalSurfaceView` is mounted and presumably driving its display link, even if hidden. v1 acceptable; if resource use balloons, switch to a strategy that swaps the active surface in/out and pauses the inactive ones (probably needs a `TerminalViewState` "paused" flag we don't yet have).
- **Sidebar selection `tag` uses `UUID?`** explicitly, not `UUID`, because `List(selection:)` requires the tag type to match the binding's wrapped type. `selectedSessionID: UUID?` is optional, so `tag(session.id as UUID?)`. SwiftUI's selection error messages on this are notoriously bad.
- **`moveSessions(...)` directly calls `Array.move(fromOffsets:toOffset:)`** — drag-to-reorder works in-memory only. Persistence (#0030) will pick this up once cadence wiring is back online.
- **PRD §6.6 says "Each window has its own session list"**, and `RootWindowView` honors that by owning the store via `@State`. Multiple windows therefore have independent session lists; closing window A's last session doesn't affect window B.
- **Default session has `title = "Session 1"`**, generated from the count. Renaming and duplicate land in #0011.
- **Cmd-Shift-1..9 keyboard selection** lands in #0012 via `store.selectSession(at:)`. The store's API already supports it.
- **Empty-state `ContentUnavailableView`** is defensive; with the auto-spawn-replacement logic in `removeSession`, it should never actually appear. Kept as a safety net.
