## Description

Two related defects in the "Embed CLI" Run Script phase of the app target (`Batty.xcodeproj/project.pbxproj`), both in the same place and fixable in one pass. Both were observed directly during #0270's implementation; that issue fixed only the *new* "Embed Broker" phase and left the pre-existing "Embed CLI" phase alone as out of scope.

**Defect 1 — the embedded CLI silently goes stale.** The phase declares:

```
inputPaths = (
);
outputPaths = (
    "$(TARGET_BUILD_DIR)/$(UNLOCALIZED_RESOURCES_FOLDER_PATH)/bin/batty",
);
```

Note the exact shape: `inputPaths` is **empty** but `outputPaths` is **not** — the phase does declare its output. (An earlier characterization of this defect as "no inputPaths and no outputPaths" is inaccurate on the second half, and the truth is worse: a script phase with *neither* inputs nor outputs runs on every build, which would have accidentally kept the binary fresh. A declared output with **no inputs** means Xcode's incremental build skips the phase whenever `bin/batty` already exists — so after the first build, the phase effectively never reruns, no matter how much the CLI's sources change.)

The developer-facing symptom: change a CLI source file, rebuild, build succeeds — but `Contents/Resources/bin/batty` is still the previously-built binary. Behavior changes don't take effect, and anyone testing the embedded binary is silently validating stale code. This is especially treacherous now that the CLI is gaining real behavior — #0270's `ping`, #0271's `status`, and later children of the XPC track — because a stale embedded binary makes their verification results untrustworthy: a "passing" `batty ping` may be exercising last week's build.

By contrast, the "Embed Broker" phase added by #0270 was given real `inputPaths` from the start (`Configuration/co.sstools.Batty.broker.plist`, `BattyKit/Sources/BattyBroker`, `BattyKit/Sources/BattyXPCCore`) precisely because this staleness was observed on the older phase during that work.

**Defect 2 — phase-ordering coupling through `rm -rf`.** The "Embed CLI" script ends with (quoting the actual `shellScript`):

```bash
rm -rf "${dest}"
mkdir -p "${dest}"
/bin/cp -f "${built}" "${dest}/batty"
```

where `dest` is the entire shared `${TARGET_BUILD_DIR}/${UNLOCALIZED_RESOURCES_FOLDER_PATH}/bin` directory. That `rm -rf` deletes `BattyBroker` on every run. It only works today because "Embed Broker" runs *after* "Embed CLI" in the target's build-phase list and re-creates its own missing declared output every time. A future reorder of the two phases — or a new phase inserted between them that also touches `bin/` — would silently drop the broker from the bundle with no build error. #0270 added explanatory comments to both phases documenting the coupling, but comments are not enforcement.

Both claims above were verified against the current `project.pbxproj` on `main` (phase objects `26B100020000000000000002` "Embed CLI" and `26B100040000000000000004` "Embed Broker").

## Resolution notes

> 🟢 Resolved 2026-07-25 — both Embed phases now set `alwaysOutOfDate = 1`, so an incremental build always re-embeds binaries matching current source, and `Embed CLI` no longer deletes the broker.

The first fix attempt (declaring `inputPaths`) looked verified but did not work; the review caught it. See Gotchas — the mechanism is worth knowing before anyone reaches for `inputPaths` on a script phase again.

## Root cause

Two defects in `Batty.xcodeproj`'s "Embed CLI" Run Script phase.

**Staleness.** The phase declared an `outputPaths` entry but had **empty `inputPaths`**. That combination is worse than declaring neither: Xcode skips the phase whenever the output file already exists, so it effectively never reran on an incremental build. The embedded `Contents/Resources/bin/batty` silently kept shipping a previously-built binary while its source moved on — meaning any verification performed against the embedded CLI could be validating stale code.

**Ordering coupling.** The phase ran `rm -rf` on the whole shared `Contents/Resources/bin` directory, deleting `BattyBroker`. It only worked because "Embed Broker" ran afterward and re-created its own missing declared output. A future phase reorder would have dropped the broker from the bundle with no build error.

## Fix

`alwaysOutOfDate = 1` on **both** "Embed CLI" and "Embed Broker", matching the `Bundle Ghostty Resources` phase that already set it — so all three of the target's script phases are now consistent. The `rm -rf` of the shared directory was narrowed to `rm -f "${dest}/batty"`, so each phase only removes the file it owns.

`inputPaths` was the wrong tool here and was dropped. The phase's work is `xcrun swift build --product batty`, which is itself a complete incremental build system already owning the real dependency graph — sources, `Package.resolved`, and the toolchain. Mirroring that graph into Xcode `inputPaths` duplicated it and, as the review proved, could never be complete.

`docs/batty-cli-install.md` was updated to match, including a correction to a pre-existing claim that Embed CLI was the target's last phase.

## Review

Reviewed by `claude-opus-5`, two rounds.

**Round 1 rejected the fix, and this is the substantive part of the record.** The implementer had reproduced the bug, applied `inputPaths`, and demonstrated the embedded binary picking up a change — apparently sound evidence. The reviewer reproduced it *still broken* and explained why: a directory listed in a script phase's `inputPaths` is stat'd **as a directory**; llbuild compares that directory's own mtime against the phase's outputs and does not walk the tree. On APFS a directory's mtime changes only when its entry list changes — create, delete, rename — **not** when a file inside it is edited in place. The implementer's test had passed only because their editor performed an atomic save, which bumps the parent directory's mtime. The reviewer proved the mechanism with a control: an `os.replace()` write made the phase run, an in-place `open('r+')` write did not.

Round 2 approved after independent verification with the correct methodology: in-place edits to both a `batty` source and a `BattyBroker` source, capturing `st_ino` and `st_mtime_ns` before and after to confirm the inodes were unchanged and the parent directory mtimes byte-identical **to the nanosecond** — precisely the condition that defeated round 1's fix. Both embedded binaries picked up their probes, and both reverted correctly, so the phases demonstrably rerun in both directions.

## Verification

- **The staleness test, run with genuine in-place edits** (`open(path, "r+")`, same inode, parent directory mtime unchanged to the nanosecond): after rebuilding without cleaning, embedded `bin/batty ping --help` showed the probe text and `bin/BattyBroker` contained its own probe string. Both reverted correctly on a second in-place edit — a change the `inputPaths` approach would also have missed. `git status` clean, no probe residue.
- xcodebuild logs `'Embed CLI' will be run during every build` and the same for `'Embed Broker'`.
- `scripts/build.sh unit` — **511 tests in 62 suites passed**, matching the #0270 baseline. This issue adds no tests; it is a build-configuration fix whose verification is necessarily behavioral.
- `scripts/build.sh` — `** BUILD SUCCEEDED **`; `BattyBroker` still `TeamIdentifier=XV8BAAVZ6V`, `flags=0x10000(runtime)`.
- `otool -L | grep -c '@rpath'` → **0** on both embedded binaries.
- `plutil -lint Batty.xcodeproj/project.pbxproj` → OK after every edit, including the round-1 phase-reorder experiment, which was reverted to a byte-identical state.
- **Cost measured, not assumed:** a no-op incremental `scripts/build.sh` is ~7.3s wall, of which the two phases' `swift build` work accounts for ~1.6s (0.86s CLI, 0.71s broker). Not material to the edit-build loop.
- The reviewer independently confirmed the doc's `bash` block is still byte-verbatim against the pbxproj `shellScript`, and that the corrected phase-order claim matches the actual `buildPhases` array.

## Files changed

- `Batty.xcodeproj/project.pbxproj` — `alwaysOutOfDate = 1` on both Embed phases; Embed CLI's `inputPaths` emptied and its `rm -rf` narrowed to `rm -f "${dest}/batty"`.
- `docs/batty-cli-install.md` — rewritten Embed CLI section (verbatim script, the actual fix, why `inputPaths` failed), the "Embed Broker" phase acknowledged, and the stale "last phase" claim corrected.

## Gotchas

- **Directory entries in a script phase's `inputPaths` do not track file *contents*.** llbuild stats the directory itself, and APFS updates a directory's mtime only when its entry list changes. An in-place edit to a file already inside it is invisible. This is a trap for anyone reaching for `inputPaths` on a script phase in this project.
- **Testing that trap requires an in-place write.** Editors, Xcode, `git checkout`, `sed -i`, and vim all save atomically and bump the parent directory's mtime, which masks the bug entirely. Use `open(path, "r+")` and verify both the inode and the parent directory's mtime are unchanged. A test that saves normally will report a broken fix as working — exactly what happened in round 1.
- **`swift build` output is not byte-reproducible across runs**, so md5 equality is the wrong check for a revert. Compare observable behavior instead.
- **`Embed Broker` keeps its `#0270` `inputPaths` while `Embed CLI`'s were dropped** — an asymmetry that could read as load-bearing. It is inert under `alwaysOutOfDate`; removing it is pure pbxproj churn, so fold it into a future pbxproj touch. Do not treat either phase's `inputPaths` as a freshness guarantee.
- **Both Embed phases now run on every build**, including incremental ones. That is deliberate, and the measured cost is ~1.6s.

## Steps to reproduce

1. Build the app (`scripts/build.sh`), producing `Contents/Resources/bin/batty`.
2. Make a visible change to a CLI source file under `BattyKit/Sources/batty/` (or `BattyCLICore`/`BattyXPCCore`, which the `batty` product also links).
3. Rebuild **without** cleaning.
4. Run the embedded `Contents/Resources/bin/batty` from the built bundle.

## Expected behavior

The embedded binary reflects the source change — the "Embed CLI" phase reruns whenever any of the CLI's real source inputs changed, and the two Embed phases don't depend on their relative order for the broker to survive.

## Actual behavior

Xcode skips the "Embed CLI" phase because its declared output exists and it declares no inputs; the bundle keeps shipping the previously-built `batty`. Separately, every run of the phase deletes `bin/BattyBroker`, which only reappears because "Embed Broker" happens to run afterward.

## Notes

**Likely fix** (one pass, both defects, `project.pbxproj` only):

- Give "Embed CLI" `inputPaths` covering its real source inputs, mirroring what "Embed Broker" already declares — the `batty` product's targets are `Sources/batty`, `Sources/BattyCLICore`, and `Sources/BattyXPCCore` per `BattyKit/Package.swift` (the external `swift-argument-parser` dependency is not covered by "Embed Broker"'s precedent either). Keep the existing `outputPaths` entry for `bin/batty`.
- Narrow the `rm -rf` to the file this phase owns — remove/replace `${dest}/batty` rather than wiping the shared `bin/` directory — so the two phases stop depending on their relative order. The ordering comments #0270 added can then be updated or retired.

**Optional, same pass, not required:** the vendored reference `docs/xpc/cli-embedding-and-install.md` shows two refinements that *neither* phase currently has — an `ENABLE_PREVIEWS`/`PREVIEW_FRAMEWORK_PATHS` early-exit so SwiftUI preview builds skip the embed, and a `--scratch-path` under `DERIVED_FILE_DIR` so an Xcode build doesn't fight a terminal `swift build` over the package's `.build` directory. Worth considering while in the file; don't let them grow the scope. (Convention hazard: `#NNNN` references inside `docs/xpc/` are the vendored RemoteControl project's issue numbers, not Batty's.)

**Verification expectations.** The meaningful test is behavioral, not a unit test:

- Change a CLI source file, rebuild *without* cleaning, and confirm the embedded `bin/batty` actually reflects the change — e.g. via `--version` output, a temporary probe, or byte comparison against the freshly built product.
- Confirm `bin/BattyBroker` survives a build after the `rm -rf` is narrowed.
- `scripts/build.sh` and `scripts/build.sh unit` stay green.

**Hazards:** `scripts/` and `Configuration/Build.xcconfig` are restricted areas per `CLAUDE.md` — this fix should touch neither (the plist lives in `Configuration/` but is not being edited). The `project.pbxproj` edit itself carries the hazard #0270 documented: **Xcode rewrites `project.pbxproj` while it has the project open** — close the project in Xcode (or coordinate with the user) before hand-editing. Never relaunch or kill the user's running Batty without asking.

This is a small build-hygiene fix, not an umbrella — keep it scoped to the two Embed phases.
