## Description

`ProcessFollowByNameTests.theRealEnumeratorPrefersTheLongestRunningProcessOfAName()` failed again on 2026-11-09, during a full `./build.sh unit` run (3400 tests in 341 suites) on `issue/0567`. That branch doesn't touch `ProcessInspector` or this suite. Run alone right after, the suite passed (34 tests). #0565 (`d6be2e59`) is on `main`, so its fix didn't remove the flake.

#0565 assumed the cause was two separate live walks being compared. The test now makes **one** walk, but the failure has a new shape. The walk didn't fail and didn't come back empty. It found the **newer** child and missed the older one. So the remaining cause isn't the second walk. The test asserts on global, unsynchronized host state (the live process table and per-pid `proc_pidinfo` reads) during a 3400-test parallel run. Its owned children were unreadable within moments of the walk.

The ordering rule this test was written to prove is now covered by `ProcessInspectorNameSelectionTests` on synthetic records. The live assertion adds flakiness but no coverage.

## Evidence

- Log `.claude/worktrees/issue-0567/build/checks/unit-20261109-001717-78908.log`, only this test's lines read:
  ```
  ✘ Test theRealEnumeratorPrefersTheLongestRunningProcessOfAName() recorded an issue at ProcessFollowByNameTests.swift:785:9: Expectation failed: ProcessInspector.firstSameUserProcess(named: name) == .found(older.processIdentifier)
  ↳ pid 81715: nil; pid 81717: nil
  ↳   ProcessInspector.firstSameUserProcess(named: name) → .found(81717)
  ↳   .found(older.processIdentifier) → .found(81715)
  ✘ Test run with 3400 tests in 341 suites failed after 50.039 seconds with 1 issue.
  ```
  Re-run alone: `unit-20261109-001836-83225.log`, `✔ Test run with 34 tests in 1 suite passed after 0.356 seconds.`
- **The walk itself succeeded.** `firstSameUserProcess(named:)` returned `.found`, not `.unknown` or `.notRunning`. The log's four `allPids:` error lines (00:18:00.27–00:18:00.86, all `errno 12` or the 7424-pid saturation) all come from `ProcessInspectorAllPidsTests`' fake seam. That seam sets `errno = ENOMEM` (`ProcessInspectorAllPidsTests.swift:36,41`) and expects capacities up to 7424 (`:87`). No real walk logged a failure.
- **The walk missed only the older child.** The two children are 81715 (older) and 81717 (newer). `firstProcess(named:in:)` (`ProcessInspector.swift:405-410`) picks the minimum under `listOrder` (`:358-366`): start seconds, then microseconds, then pid. 81715 started first and has the lower pid, so it wins any comparison it's in. It therefore wasn't among `matches` (`:416-428`). Either it wasn't in the pid list, or `bsdInfo(pid:)` returned `nil` for it, or its uid or name didn't match.
- **Afterwards both children were unreadable.** `walkDiagnostic(older, newer)` (`ProcessFollowByNameTests.swift:791-799`) runs only on failure, after the walk. It reads `listedIdentity(pid:)` (`ProcessInspector.swift:453-457`) for each pid and got `nil` for both, including 81717, which the walk had just read. The fixture's SIGKILL runs only in the `defer` after the expectation (`ProcessFollowByNameTests.swift:772`, `ChildProcessFixture.swift:43-48`).
- **The evidence can't say why.** `bsdInfo(pid:)` (`ProcessInspector.swift:539-546`) throws away `errno` and returns `nil` for any short read. So "child already exited" (`ESRCH`) can't be told apart from a transient `proc_pidinfo` failure. The test never checks `older.isRunning` / `newer.isRunning` or `kill(pid, 0)` either.
- **Stale-pid kills were checked and are unlikely.** The only explicit `kill(pid, SIGKILL)` calls in BattyKit tests target the test's own children. One does re-kill an already-reaped pid: `PlainShellKeyRewriteTests.swift:82,85` repeats `kill(follower, SIGKILL)` and `waitpid` in its `defer` after `:89-91` has already reaped `follower`. macOS hands out pids in order, so a freed pid isn't reused until the pid space wraps. That kill is a latent hazard but an unlikely cause here, since these pids were around 81.7k. No source or test sends a group signal (`killpg`, `kill(-pgid)`, `kill(0, …)`).
- The sibling `theRealEnumeratorFindsAUniquelyNamedProcessAndItsReplacement()` (`ProcessFollowByNameTests.swift:724-765`) has the same exposure. It asserts `firstSameUserProcess(named:) == .found(first.processIdentifier)` against a live walk right after the spawn (`:743-746`), then drives a `ProcessStatusPaneContent` through live samples.
- Earlier occurrences: #0516 (2026-10-14) and #0565 (2026-11-05). In both, the walk returned `nil` against a pid the first walk had listed.

## Recommendation

1. **Delete `theRealEnumeratorPrefersTheLongestRunningProcessOfAName()`.** Its ordering rule is proven deterministically by the five `ProcessInspectorNameSelectionTests` (`ProcessInspectorNameSelectionTests.swift:15-41`). The live table can't make "two children, the older one wins" deterministic under a full parallel run. A single snapshot doesn't help, as this failure shows. Real-enumerator coverage stays in the sibling test.
2. **Make the sibling's failures diagnosable instead of silent.** Before each live assertion, `try #require(process.isRunning)` so "the child is gone" fails as its own message. Extend `walkDiagnostic` to report `kill(pid, 0)` / `errno` and the `proc_pidinfo` return value with `errno`. One way is a test-visible `bsdInfoResult(pid:)` that returns the rc and `errno`, with `bsdInfo` built on it (no production behaviour change). If the sibling then flakes, its next failure will say whether the child had exited or the read failed.
3. **Fix the stale re-kill** in `PlainShellKeyRewriteTests.groupMemberCountIsExactForSingleAndMultiMemberGroups()`. The `defer` should kill and reap only pids not already reaped (for example, track `followerReaped`).
4. If the sibling test flakes after this, add it under "Known flaky tests" in `issues/Issues.md` with the log paths, and file a follow-up rather than reopening this one.

## Acceptance criteria

- `ProcessInspectorNameSelectionTests` still passes unchanged (5 tests). Mutating `firstProcess(named:in:)` from `min` to `max` still fails its ordering tests.

- Follows `AGENTS.md` "Asynchronous tests": no sleeps, polling or timing assertions are added.
