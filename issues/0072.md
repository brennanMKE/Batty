## Description

**Severity: critical.** When the user switches away from a tab and later comes back, the tab's contents are gone. A running interactive session (Claude Code, vim, ssh, htop, tail -f) is killed and a fresh shell prompt replaces it. The user reports losing a Claude Code session this way; running `ls` and switching tabs is enough to lose the scrollback.

The logs reveal the mechanism. During normal navigation (`previousTab`, `nextTab`, `focusPaneLeft`, etc.), libghostty repeatedly logs:

```
io_exec: started subcommand path=/usr/bin/login pid=22159
io_exec: started subcommand path=/usr/bin/login pid=22160
io_exec: started subcommand path=/usr/bin/login pid=22161
io_exec: pty fd closed, read thread exiting
surface: surface closed addr=9f67b8000
io_exec: pty fd closed, read thread exiting
surface: surface closed addr=9f66b0000
```

PTYs are being **destroyed and re-created** during navigation that should be purely view-state changes. Three new shells (`pid=34173/34174/34175`) spawn at once during a tab switch — that's an entire pane's worth of tabs being re-mounted.

This violates the architecture rule `CLAUDE.md` explicitly calls out:

> **Surface registry is the single source of truth for live Terminal Sessions.** SwiftUI views only ever store `surfaceID: UUID`, never a `ghostty_surface_t` directly. View rebuilds must not destroy surfaces.

The current `PaneView` / `SessionDetailView` use `TerminalSurfaceView` (a `NSViewRepresentable`) directly inside `ForEach` loops with `.opacity(...)` / `.allowsHitTesting(...)` toggles. That keeps the SwiftUI view tree stable in theory, but in practice SwiftUI is tearing down the underlying NSView and re-creating it whenever the ForEach diff or some other observation invalidates the identity.

## Steps to reproduce

1. Open Batty. Default Session 1 / Pane / Tab.
2. Start a long-lived process: `claude-code` or `vim` or `tail -f /var/log/system.log` or even just leave the prompt open with some scrollback.
3. Cmd-T to create a second tab.
4. Cmd-Shift-[ (previous tab) to switch back to the original tab.
5. **Observed:** the tab shows a fresh shell prompt. The running process is dead. Scrollback is gone.
6. **Expected:** the tab is exactly as it was before — running process unaffected, scrollback intact.

Reproduces with any of: tab switching, pane focus movement, sidebar session selection, sidebar collapse/expand, and probably window minimize.

## Expected behavior

`TerminalSurfaceView`'s underlying NSView and its associated PTY survive arbitrary SwiftUI view-tree churn. The PTY's lifetime is bound to the `TabRuntime` model object, not to whether SwiftUI happens to instantiate or tear down the representable.

When the user returns to a tab:
- Running process is still running.
- Scrollback is intact.
- Cursor position is preserved.

## Implementation guidance

This is non-trivial. Several patterns to consider, in increasing order of complexity:

### A. Stabilize SwiftUI's identity diff (cheapest, may not be enough)

`ForEach(pane.tabs)` relies on `TabRuntime: Identifiable` and uses `tab.id` as the SwiftUI identity. Make absolutely sure:

- `tab.id` is stable across mutations to `pane.tabs` (it is — `let id: UUID`).
- The `ZStack` containing the ForEach is stable (not re-instantiated on parent re-render).
- The `SessionDetailView`'s outer `ZStack { ForEach(store.sessions) { ... } }` doesn't trigger when an irrelevant session property changes.

Add `.id(tab.id)` and `.id(session.id)` modifiers on the representable / SplitContainerView to anchor identity. Use `@StateObject` / `@State` equivalents where appropriate to preserve view-level state across re-renders.

This may fix some cases but probably not all — `NSViewRepresentable.makeNSView` is still called when SwiftUI thinks the view needs to be remade.

### B. Move NSView ownership out of the SwiftUI representable

Hold the `AppTerminalView` (libghostty's NSView) in a coordinator or in the `TabRuntime` itself (lifetime-tied to the model, not the SwiftUI view). The representable's `makeNSView` returns a *wrapper* view that hosts the long-lived NSView as a subview; on tear-down, the wrapper is destroyed but the actual terminal NSView is preserved by a strong reference held in `TabRuntime`.

When the representable is re-instantiated, `makeNSView` re-creates the wrapper, which re-installs the existing NSView. The PTY never closes.

This pattern is well-documented for AppKit ↔ SwiftUI bridges that need stable underlying views. Examples: NSScrollView wrappers, NSCollectionView wrappers in production SwiftUI apps.

### C. Use a single window-level NSView host with manual visibility

Drop `TerminalSurfaceView` from the SwiftUI tree entirely. Have an NSViewController-managed AppKit host that holds every active terminal surface as a subview, manages their frames, and toggles visibility based on `pane.activeTabID` / `tree.focusedPaneID` / `store.selectedSessionID`. SwiftUI renders a "host view" placeholder that the host populates.

This is the heaviest refactor but matches the surface-registry architecture rule most exactly — the registry owns all live surfaces; SwiftUI just renders a positioning placeholder.

### Recommendation

Start with **B**. The wrapper-with-strong-reference pattern is the smallest delta from the current architecture and matches the surface registry rule in `CLAUDE.md`. The `TabRuntime` already owns `terminal: TerminalViewState`; we add a stored `appTerminalView: AppTerminalView?` (weak/strong tradeoff TBD) that survives view rebuilds.

If B doesn't fully stop the respawning (because libghostty's NSView is internally tied to a window/surface controller that resets on parent change), fall back to C.

The reference for "how libghostty wants the NSView to be reused" lives in `../libghostty-spm/Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView.swift` and the `TerminalController` it points at. The fork may need additions to expose a stable surface-reattach API. Track any required fork changes as a separate ticket if discovered.

### Tests

This is hard to unit-test because the failure is a SwiftUI ↔ AppKit lifecycle issue, not pure model code. Best we can do:

- A test that records `TerminalViewState.surface` identity before and after a `pane.tabs.append` mutation, asserting the existing tab's surface is still the same object.
- A UI test in `BattyUITests` that starts a process, switches tabs, comes back, and asserts the process is still running. The challenge is reliably detecting "still running" via UI test — possibly via an OSC-emitted breadcrumb or by reading the displayed prompt text.

The primary verification is manual: start vim, switch away, come back — does vim survive?

## Acceptance criteria

- Running a long-lived process in a tab, switching away (any focus path), and switching back leaves the process and its terminal state intact.
- Bell counts, working-directory tracking, OSC titles, focus state, scrollback — all preserved across navigation.
- The libghostty `io_exec: started subcommand` log fires **only when the user creates a tab** (Cmd-T, Cmd-D, Cmd-N), not when the user navigates between existing tabs.
- The companion `surface: surface closed` log fires **only when the user closes a tab** (Cmd-W, chip ×, shell exit), not on navigation.

## Out of scope

- Persisting terminal state across app launches (`#0055`'s decision — workspace restore is off by default; not affected by this fix).
- Reducing PTY memory or CPU footprint when a tab isn't visible. Suspending the PTY when a tab is hidden is an optimization — not v1.

SwiftUI views only ever store `surfaceID: UUID`, never a `ghostty_surface_t` directly. View rebuilds must not destroy surfaces." — this issue is the surface-registry rule being violated.

- `BattyKit/Sources/BattyKit/TabRuntime.swift` — add a property to hold a strong reference to the libghostty NSView.

- A new wrapper representable (e.g. `StableTerminalSurfaceView`) that hosts the existing NSView from `TabRuntime` rather than calling libghostty to create a new one each time SwiftUI calls `makeNSView`.
- `PaneView.swift` — swap `TerminalSurfaceView(context: tab.terminal)` for the new wrapper.
- Possibly a small addition to `libghostty-spm` (the fork) to expose `AppTerminalView`'s reuse path if it isn't already.

## Root cause

`PaneView` mounted libghostty's `TerminalSurfaceView` directly inside
`ForEach(pane.tabs)`. SwiftUI's diff is free to invalidate and re-mount an
`NSViewRepresentable` whenever a parent re-renders. Each re-mount called
`TerminalViewRepresentable.makeNSView`, which instantiated a fresh
`AppTerminalView` — and libghostty's `AppTerminalView.viewDidMoveToWindow`
created a new surface (PTY + scrollback). The previous `AppTerminalView`
then deallocated; its `TerminalSurfaceCoordinator.deinit` called
`tearDownSurface` → `surface?.free()`, which is what emitted the
`io_exec: pty fd closed` / `surface: surface closed` logs and killed the
running process.

`TerminalViewState.surface` is `weak`, so the *only* strong reference
keeping a live `TerminalSurface` around was the `AppTerminalView` itself.
The instant SwiftUI dropped its reference, the PTY died.

The `.opacity(...)` / `.allowsHitTesting(...)` toggles only affected
visibility — they didn't anchor the underlying NSView's lifetime.

## Fix

Option B from the implementation plan. The `AppTerminalView` is now owned
by `TabRuntime.terminalNSView` and lives as long as the tab does. A new
`StableTerminalSurfaceView` (NSViewRepresentable) returns a disposable
container NSView from `makeNSView`; `updateNSView` re-parents the tab's
existing `AppTerminalView` into the new container, lazily creating it
on first use. SwiftUI can tear down and re-mount the wrapper freely — the
terminal view is retained by `TabRuntime`, removed from the old container
(if any) on dismantle/re-mount, and added back into the fresh one with
Auto Layout pins.

This works without any libghostty changes because
`AppTerminalView.viewDidMoveToWindow` already contains the precise logic
needed: "only create a new surface when one does not already exist". So
attaching an existing terminal view to a brand-new window does *not* spawn
a new PTY — it just resynchronizes metrics and resumes the display link.
Detaching from a window stops the display link but does not free the
surface. Re-parenting between containers in the same window is a no-op
for libghostty's surface lifecycle.

## Files changed

- `BattyKit/Sources/BattyKit/TabRuntime.swift` — adds
  `@ObservationIgnored public internal(set) var terminalNSView: AppTerminalView?`.
  `@ObservationIgnored` so view mounting/unmounting doesn't trigger
  SwiftUI re-renders. Imports `AppKit` and `GhosttyTerminal` for the
  `AppTerminalView` type.
- `BattyKit/Sources/BattyKit/StableTerminalSurfaceView.swift` — new
  wrapper representable. `makeNSView` returns a cheap container;
  `updateNSView` (and `makeNSView`'s initial call) attach the tab's
  long-lived `AppTerminalView`, creating it on first use and re-parenting
  on subsequent mounts. `dismantleNSView` is intentionally a no-op
  (releasing the container is enough; libghostty doesn't free its surface
  on `viewDidMoveToWindow(nil)`).
- `BattyKit/Sources/BattyKit/PaneView.swift` — swaps
  `TerminalSurfaceView(context: tab.terminal)` for
  `StableTerminalSurfaceView(tab: tab)`. All existing modifiers
  (`.opacity`, `.allowsHitTesting`, `.onDrop`, `.task`, every `.onChange`)
  operate on the SwiftUI wrapper and continue to behave identically
  because the wrapper still observes the same `tab.terminal` state.
- `BattyKit/Tests/BattyKitTests/StableTerminalSurfaceTests.swift` — new
  tests cover (1) a tab starts without a terminal NSView, (2) the NSView
  survives container swap (the core property the wrapper relies on), and
  (3) the tab strongly retains the NSView while it's alive.

## Gotchas

- The primary verification is **manual**. The bug is a SwiftUI ↔ AppKit
  lifecycle interaction that's awkward to drive headlessly. To verify:
  open Batty, start a long-lived process in the active tab (`top`, `vim`,
  `claude-code`, `tail -f /var/log/system.log`, or just leave a prompt
  with scrollback), Cmd-T to create a second tab, Cmd-Shift-[ to return.
  The original process must still be running and the scrollback intact.
  Also verify via Console.app: the libghostty `io_exec: started
  subcommand` log should fire only when a tab is created (Cmd-T / Cmd-D /
  Cmd-N), and `surface: surface closed` should fire only when a tab is
  closed (Cmd-W, chip ×, shell exit). Neither should fire on plain
  navigation.
- Option A from the plan (stabilizing SwiftUI identity via `.id()`,
  `@StateObject`, etc.) was rejected because `NSViewRepresentable.makeNSView`
  is still called whenever SwiftUI decides the view needs to be remade,
  no matter how the identity is anchored. Identity stabilization can
  reduce the rate of remounts but can't guarantee zero — and one remount
  is enough to kill a running process.
- Option C (a single window-level NSView host with manual visibility) was
  not needed once libghostty's existing reuse logic was confirmed
  sufficient. If libghostty changes its lifecycle such that
  `viewDidMoveToWindow(nil)` *does* tear down the surface, the wrapper
  would have to keep terminal views in an off-screen "graveyard" subview
  to maintain continuous window attachment. The current implementation
  notes that explicitly.
- `TerminalViewState.surface` is `weak` upstream. The strong reference
  chain that keeps a live PTY alive is exactly:
  `TabRuntime.terminalNSView (strong) → AppTerminalView.core (strong) →
  TerminalSurfaceCoordinator.surface (strong)`. Anything that drops the
  terminal view will free the PTY. Don't add code paths that nil out
  `terminalNSView` unless the tab is being closed.
- `TerminalSurfaceOptions.isEquivalent(to:)` is internal to
  `GhosttyTerminal`. Trying to gate updates to `configuration` on it from
  the wrapper fails to compile. The `TerminalSurfaceCoordinator` already
  guards its own setter via `didSet`, so the wrapper doesn't need to
  re-check.
- The earlier "focus skipped: no AppTerminalView matched the requested
  terminal state" log lines from #0066 should now be much rarer because
  the terminal view persists in the view hierarchy across navigation.
  `TerminalSurfaceFocuser`'s recursive search still walks every subview,
  so wrapping the `AppTerminalView` in an extra container doesn't break
  focus routing.
