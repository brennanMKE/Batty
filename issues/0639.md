## Description

A fired Reminder records a `.reminder` `BellFeedEntry` (`Runtime/AppStateStore+Reminders.swift:313-348`). It shows in the Bell Feed and counts toward `bellFeed.unseenCount`, which turns on `bell.badge`. The user chose **Design D** (`0637/spec.md`, Part 2; `0637/option-D.html`): Reminders get their own toolbar button and popover, and fired Reminders leave the Bell Feed entirely. This issue is the **model and store move** that D needs. The popover is #0640.

This is **step 3 of 4** (sequence table in #0637). It depends on #0637, whose fixed Sidebar glyph this issue rewires, and on #0638, which defines the unread / read / Clear Read concept that fired Reminders now follow.

**Ship constraint:** between this issue and #0640, a fired Reminder is visible in the app only as the Sidebar glyph and the row's accessibility value, plus its System notification. That is acceptable on `main`, but **no release may be cut with #0639 and without #0640**. #0640 is the next issue worked.

## Goal

Fired Reminders live in a list of their own on the store, with the unread / read state from #0638. They record no Bell Feed entry and never light the bell. The System notification looks and behaves exactly as it does today.

## Acceptance criteria

### The fired-Reminder list

- New in-memory, observable store state, for example `firedReminders: [FiredReminder]`, owned by `AppStateStore` (or a small `@Observable` store beside `bellFeed`, following `BellFeedStore`'s aggregate pattern). Each item holds: the Reminder id, Session id, Window id, text (`note`), set time (`createdAt`), due time, fired time, and `read: Bool`. It does not survive a relaunch, like the Feed. Pending Reminders stay on `SessionRuntime.reminder` and are not in this list.
- Stored aggregates, written only when they change: `unreadFiredCount` (or `hasUnreadFired`), and `unreadFiredSessionIDs`, which replaces `bellFeed.dueReminderSessionIDs`.
- A Session has at most one fired item. A new firing on the same Session replaces the older item, so each Session has at most one pending Reminder and one fired Reminder. If the user would rather keep every fired item, see Open question 1.

### Unread / read (the #0638 concept applied)

- A Reminder fires as **unread**, whether or not the Session is selected or muted, as today.
- It becomes **read** on: **Mark All Read** in the list (store API here, button in #0640); selection falling back onto its Session (today's `markSelectedSessionReminderEntriesSeen()`, `Runtime/WindowRuntime.swift:1388-1393`, called from `markActiveTabSeen()` at `:1360`); and a notification Remind Again that is ignored because the Session has a newer pending Reminder (#0633's rule, `AppStateStore+Reminders.swift:81-84`; today that path marks the entry seen through the `defer` at `:76-80`).
- It **leaves the list**, read or unread, on: a visit to its Session (`visitFocusedTab()`, `Runtime/WindowRuntime.swift:1346-1348`; any click, ⌘1–9 or Open Session); **Remind Again** that sets a new Reminder, replacing today's "marks the entry seen and kept" (`AppStateStore+Reminders.swift:67-86`), since the new pending Reminder now shows in Upcoming; **Done** (store API here, buttons in #0640); its Session closing (`Runtime/WindowRuntime.swift:426`); its Window closing (`Runtime/AppStateStore.swift:530`).
- **Clear Read** (store API) removes every read fired Reminder and nothing else. It never touches pending Reminders or the Bell Feed.
- Opening any list marks nothing read.

## Open questions (defaults in place)

1. **More than one fired item per Session?** Default: no. A newer firing on the same Session replaces the older fired item. One pending and one fired per Session keeps the Due list short. The alternative keeps every fired item until visited or cleared.
2. **Does a read fired Reminder keep the Sidebar glyph?** Default: no. Only unread fired Reminders show `alarm.fill`, matching today's `dueReminderSessionIDs` (unseen only). A Session with a read fired Reminder and a pending one shows the `clock`.
3. **Remind Again ignored for a newer pending Reminder: read or untouched?** Default: read, because the user acted on the banner. That keeps today's `defer` behaviour.

## Root cause

Starting state (feature work): a fired Reminder was a `.reminder` `BellFeedEntry`. `fireReminder` recorded it with `bellFeed.record(_:)`, so it showed as a Bell Feed row and counted toward `bellFeed.unseenCount`, which badges the toolbar bell. The Sidebar glyph read `bellFeed.dueReminderSessionIDs`, and the notification's `userInfo` carried the entry id so a tap jumped to the row.

## Fix

Followed the plan.

- New `Runtime/FiredReminderStore.swift`: `FiredReminder` (Reminder id, Session id, Window id, note, `createdAt`, `dueAt`, `firedAt`, `seen`) and an `@Observable` `FiredReminderStore` modelled on `BellFeedStore`. It has stored aggregates (`unseenCount`, `readCount`, `unseenSessionIDs`) written only when they change. Each mutator skips the write when nothing matches. `record(_:)` replaces the Session's older item in one whole-array write.
- `AppStateStore.firedReminders` is passed to every `WindowRuntime` (the default argument keeps bare test constructions compiling). The store API for #0640's buttons: `markAllRemindersRead()`, `clearReadReminders()`, `markFiredReminderDone(id:)`, `openReminderSession(sessionID:)` and `remindFiredReminderAgain(id:minutes:)`.
- `fireReminder` records a `FiredReminder` and posts `postReminder(_:projectID:sessionTitle:)`. It writes nothing to the Bell Feed.
- The banner's Remind Again and the list's Remind Again share one private helper. If the Session has a newer pending Reminder, the helper marks the fired one read and returns (#0633). Otherwise it sets the new Reminder and then removes the fired one. The old `defer`/`markBellSeen` is gone.
- `notificationTapRoute`: a live bell entry id comes first, then `.openReminderSession(sessionID)` for a Reminder payload whose Session is live, then `.openProject` / `.activateOnly`. The `.open` action takes the same route.
- `BellNotifier`: the Reminder `userInfo` no longer carries `entryIdUserInfoKey`. Title, subtitle, body, category and sound are unchanged.
- `WindowRuntime`:
  - `jumpToReminderEntry` became `public jumpToReminderSession(_:)`.
  - `visitFocusedTab` and `removeSession` remove the fired item.
  - `markSelectedSessionFiredReminderSeen()` replaces the per-entry mark.
  - The `kind` guard in `decrementUnseen` is gone.
- `BellFeedStore`: removed `Kind`, `kind`, `reminderSetAt`, `reminderDueAt`, `dueReminderSessionIDs`, `unseenReminderEntries` and `removeReminderEntries`, and the kind filters in `removeEntries(matchingTabIDs:)` and `recordOrCollapse`. The custom `init(from:)` stays. Unknown keys are ignored, so older data with `kind` still decodes, which `aLegacyEntryWithReminderKeysStillDecodes` pins.
- `AppStateStore+BellCapture`: dropped the `entry.kind == .bell` guards and kept the `systemID` checks.
- `BellFeedView`: the Reminder row, `ReminderEntryAccessibility` and the Reminder branch of `pathLabel` are deleted. The Feed has one row type again.
- `SessionSidebarView`: the glyph and the `, reminder due` value read `store.firedReminders.unseenSessionIDs`. The tooltip reads `firedReminders.item(forSessionID:)`, and only inside the alarm leaf.
- No view writes the new state. Every write comes from an event-origin path.
- Docs: `Concepts.md` (version 0.35), `docs/notifications.md` and `Help/06-notifications.md`.

That is fine on `main`, but no release (`X.Y.0` from `main`, or a cherry-pick onto `release/X.Y`) may contain #0639 without #0640. Never cherry-pick #0639 alone onto a release branch. #0640 is planned and implemented next.

**Open questions:** none block. The plan uses the issue's defaults: (1) one fired Reminder per Session, and a newer firing replaces the older; (2) only an **unread** fired Reminder shows `alarm.fill` and `, reminder due`; (3) a Remind Again that is ignored because a newer Reminder is pending marks the fired one read.

**Size:** one implement pass. It is broad (about 9 source files and 15 test files), but it is one model move. Splitting it would leave `Kind.reminder` half-removed, and the test target would not compile in between. Because of the breadth, the orchestrator may want to dispatch the implementer at medium effort.

### Naming (matches #0638's API)

The flag is `seen` in code, and users see Unread and Read, as in `BellFeedEntry`. The store API reuses #0638's names: `unseenCount`, `readCount`, `markAllSeen()`, `removeReadEntries()`. The Session aggregate is `unseenSessionIDs`. It replaces `bellFeed.dueReminderSessionIDs` and is the issue's `unreadFiredSessionIDs`.
