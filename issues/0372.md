## Description

Batty terminals are opaque. There is no way to put a picture behind the text, and no way to let the desktop or another app show through. The user wants both, and wants them to compose:

> "Ultimately with both issues implemented the user should [be] able to tint an image and still see through to other apps or the desktop on a Mac."

So the target is a terminal that is semitransparent *and* backed by an image whose own opacity is adjustable — dial the image down to a tint, dial the terminal background down, and what remains behind both is whatever is on the desktop.

**This umbrella is schedulable work, not a deferred design record.** (Contrast #0341, which is explicitly parked.) It ships no code of its own; the thirteen children below carry it, one of them optional polish, and two of them ([#0551](0551.md), [#0552](0552.md)) later work on managing and syncing images, which the see-through goal above doesn't need. Start with [#0373](0373.md) — everything else is blocked on it.

The load-bearing finding, verified below: **the pinned libghostty already implements all of this natively.** No package bump, no compositing trick, no custom renderer work. What is missing is Batty-side plumbing (two config-builder call sites) and UI (app-wide, per-Pane, per-Session).

## What the pinned libghostty already supports

`BattyKit/Package.swift:31-33` pins `https://github.com/Lakr233/libghostty-spm` at revision `b146b73a8ba3ed2678a22a9de5feecfcbf298d48`. That checkout's `Ghostty.ref` is `35e1a0160c4f6797e1bb1ef8e7a2b8c6b114ab58` — the upstream Ghostty commit the vendored binary was built from.

The `1.3.2` refers to the **binary release** the package downloads: `Package.swift:48` of the pinned checkout fetches `GhosttyKit.xcframework.zip` from release `storage.1.3.2`. Dumping strings from the vendored `GhosttyKit.xcframework/macos-arm64_x86_64/libghostty.a` shows these background config keys present in the binary:

| Key | Notes |
|---|---|
| `background-opacity` | Terminal background alpha. Default-background cells only — see caveats. |
| `background-opacity-cells` | Extends the alpha to cells that paint their own background color. |
| `background-image` | Path to the image. |
| `background-image-fit` | `contain` \| `cover` \| `stretch` \| `none` |
| `background-image-position` | `center`, `top-left`, `bottom-right`, … |
| `background-image-repeat` | |
| `background-image-opacity` | Dims the image independently of the terminal background. |
| `background-blur` | |
| `background-blur-radius` | |
| `background-color` | Already covered by the Theme channel. |

The same dump contains the doc string *"configured `background-opacity` is `0.5` and `background-image-opacity`…"*, confirming the two compose — which is exactly the "tint an image and still see through" result the user asked for.

**The Swift wrapper already exposes part of it.** `Sources/GhosttyTerminal/Configuration/TerminalConfiguration.swift` in the SPM checkout (not in this repo — it is a dependency source) has first-class `Builder.withBackgroundOpacity(Double)` (`:194`) and `withBackgroundBlur(Int)` (`:198`), plus `withCustom(key:value:)` (`:212`), the escape hatch Batty already leans on heavily for `keybind`, `env`, `command`, and `wait-after-command`. `withMinimumContrast` is there too (`:190`), which matters for legibility. The remaining `background-image-*` keys go through `withCustom`.

**Config applies live.** `TerminalController.setTerminalConfiguration(_:)` (SPM checkout, `Controller/TerminalController.swift:225-243`) re-resolves and reapplies without tearing down the surface or the PTY — same in-place story as `setTheme`. It early-returns when the new configuration `==` the old one (`:236`).

**Themes are a separate channel.** `applyThemeToAllSurfaces` / `applyTheme(_:to:)` in `BattyKit/Sources/BattyKit/Theme/ThemePreference.swift` go through `controller.setTheme`, not `setTerminalConfiguration`, so background settings and Theme settings will not clobber each other.

**The Metal layer is already transparency-ready.** `Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView.swift:64-68` (SPM checkout) sets `metal.isOpaque = false` and clear `backgroundColor` on both the `CAMetalLayer` and the view's layer. Nothing in Batty has to change for `background-opacity` to composite over what is behind it.

## The wholesale-replace hazard

**Stated once here so the children can reference it instead of restating it.**

`setTerminalConfiguration` **replaces the entire override set** rather than merging it. Batty builds that set in two independent places:

- `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:172-246` — per-Tab, at init. Builder block opens at `:172`; `setTerminalConfiguration` is called at `:246`.
- `BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift:170-198` — `applyAppearanceToAllSurfaces()`, app-wide on any appearance change. Builder block opens at `:174`; `setTerminalConfiguration` is called at `:196`, inside a loop over every window → session → terminal Pane → Tab.

Background keys added to only one of these will be **silently dropped** the next time the other runs. Change the font size in Settings and every per-Tab background override evaporates. This is the single most likely bug in this feature, and every child issue must handle it.

## Two designs, and how they differ

| | **A. libghostty `background-image`** | **B. `background-opacity` + a SwiftUI layer** |
|---|---|---|
| Composited by | Ghostty's renderer, per surface | CoreAnimation, per window |
| Result | Each Split scales its own copy of the image | One image spans the Window; Splits float over it |
| Batty changes | Two config-builder call sites + UI | Same, plus a new layer in `sessionStack` |
| Risk | Low — never touches the host / z-order architecture | Touches the persistent-host layer guarded by `docs/terminal-pane-requirements.md` |

**A is the recommended path**, and is what [#0373](0373.md), [#0374](0374.md), [#0375](0375.md), and [#0376](0376.md) implement. B is filed as [#0377](0377.md), deferred, because it is the only way to get one continuous image behind all Splits — start it only if the per-Pane result looks wrong to the user.

## Caveats to carry into the children

- **`background-opacity` affects default-background cells only.** A TUI that paints its own colored cells (vim, htop, a shell with a colored prompt background) stays opaque unless `background-opacity-cells` is also set. Expect the image to read mostly around a plain shell prompt. Whether Batty exposes `background-opacity-cells` as a user setting or hard-couples it is a decision [#0375](0375.md) has to make.
- **Legibility needs a deliberate answer.** `minimum-contrast` is already in the config enum (`withMinimumContrast`, `TerminalConfiguration.swift:190`), and `background-image-opacity` dims the image itself. Some combination of the two has to keep text readable over a busy photo; the feature is not done if the default settings can produce unreadable output.
- **`themeChrome.windowBackground` still paints the window padding.** `SessionDetailView.swift:217-220` paints the themed window background behind the terminal host and into the transparent title bar. A per-surface image will look inset against that opaque band unless the region is handled.
- **Supported image formats under the pinned ref: PNG and JPEG only, no animation** (measured in [#0373](0373.md), which also records how unreadable files behave). [#0374](0374.md) and [#0375](0375.md) must restrict their pickers accordingly.

## Notes

**Verification method for the binary claims above.** The key list came from `strings` over the vendored static library:

```
strings -a <DerivedData>/SourcePackages/artifacts/libghostty-spm/libghostty/\
  GhosttyKit.xcframework/macos-arm64_x86_64/libghostty.a | grep -o 'background-[a-z-]*' | sort -u
```

A string in the binary proves the key *exists*, not that it is accepted by the config parser. The stronger proof is `renderedConfig`, which only reflects a config libghostty's own diagnostics accepted (`prepareConfig` fails closed otherwise) — that is [#0373](0373.md)'s verification plan, and the reason #0373 is separable from the UI work.

**Files touched by more than one child**, so work the children strictly one at a time in ascending order, each on its own `issue/NNNN` branch cut from a fresh `main`:

- `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift` — #0373, #0374, #0376
- `BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift` — #0373, #0375
- `BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift` — #0374 (and #0376, if the entry point lands in the Session context menu)
- `BattyKit/Sources/BattyKit/Views/SessionDetailView.swift` — #0377 only
