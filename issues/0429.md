## Description

This is the LM Studio child of umbrella [#0427](0427.md), and it is **blocked by [#0428](0428.md)** (the shared clock, readiness helper, completion-signal conventions and reap gate). It covers 27 sites. `LMStudioDashboardPaneContent` already has injectable intervals (`modelsPollInterval`, `psPollInterval`, `respawnDelay`: `Runtime/LMStudioDashboardPaneContent.swift:59-71`). But every loop reads them through a real `Task.sleep` (`:271`, `:349`, `:728`). The pipe reader applies parsed lines on its own schedule, and no event tells a test that it has done so. So the tests sleep for "long enough", or poll `waitUntil` to a 30s deadline, or dodge the timers with 30s/24h values.

Work: route the three loops and the stale-in-flight comparison through #0428's clock protocol. Add the completion events #0427 lists (parsed-line applied, poll applied, stream-termination handled, and stream-process launched where launch isn't already synchronous with the factory), in the shape #0428's conventions prescribe. Apply #0428's reap gate to `tearDown`. Then rewrite each row below.

### Test-only helper added

`EventCounter` (bottom of `LMStudioDashboardPaneContentTests.swift`) — a lock-guarded, `nonisolated`, `@unchecked Sendable` counter that subscribes to one of the four `AsyncStream<Void>` signals above and lets a test `awaitCount(_:bound:)` a cumulative total, mirroring `TestClock.waitForSleepers`/`TestTeardownReapGate.waitForParkedWaiter`'s "count + threshold waiter" shape. **Gotcha found and fixed during mutation-checking**: the class must be declared `nonisolated` explicitly — this package defaults to `MainActor` isolation, so without it, `awaitCount`'s hang-guard `DispatchWorkItem` (which resumes the continuation from a background `DispatchQueue.global` queue, exactly like `TestClock`'s/`TestTeardownReapGate`'s own timeout branches) crashed the whole test process with a `dispatch_assert_queue` trap (`EXC_BREAKPOINT`/`SIGTRAP`) the instant a bound genuinely expired, instead of failing the test cleanly. Fixed by adding `nonisolated` to the class declaration, with the finding recorded in the type's own doc comment. This is a test-only helper local to this file, not a change to any #0428 shared type.

## Round 2 (review round 1 findings)

Round 1 review (`92c47102`) requested changes: B1 (vacuous `waitForSleepers(1)` on a clock shared by multiple loops), B2 (discarded `advance` return values), B3 (`hidingActually…`'s failure branch released nothing), B4 (six bare `#expect(await …waitForReadyFile(…))` with no release path), missing one-strike and half-`respawnDelay` mutation coverage, production `AsyncStream` cleanup, `EventCounter` waiter cleanup, remaining un-injected clocks, an explicit note on `PaneRuntime.swift:88`, and several stale comments. All addressed on this branch.

**B1 — vacuous `waitForSleepers(1)`.** One `TestClock` is shared by the models loop, the `lms ps` loop, and (once scheduled) the respawn `Task`, so `waitForSleepers(1)` was satisfied by whichever loop's sleeper registered first, not necessarily the one being waited on. Fixed in `staleInFlightIsEvictedOnceThePsPollCrossChecksIt` and `bufferResetsOnRespawnSoPendingDropDoesNotSwallowNewProcessFirstLine`: set the *other* loops' intervals to `.seconds(1000)` (a free virtual value) so they still count toward the total but never fire during the test's own advances, wait for the true total (`waitForSleepers(2)`/`waitForSleepers(3)`), and assert `advance`'s return value equals the expected fired count (`1` in both cases) rather than discarding it. Reproduced the reviewer's exact perturbations against the *pre-fix* code, confirmed the rewritten tests survive them, then reverted:
  - 20000 `Task.yield()`s before `startPsPollTask`'s `clock.sleep` call — `staleInFlightIsEvictedOnceThePsPollCrossChecksIt` still passed (0.323s).
  - 50 `Task.yield()`s before `scheduleRespawn`'s `clock.sleep` call — `bufferResetsOnRespawnSoPendingDropDoesNotSwallowNewProcessFirstLine` still passed (0.197s); also re-ran `modelStreamExitingUnexpectedlyReportsReconnecting` under the same perturbation (unaffected, since it never advances the clock at all) — passed (0.145s).

**B2 — discarded `advance` results.** `connectionStateNeverConflatesNotInstalledWithUnreachable` now advances by `modelsPollInterval` first and asserts `0` fired (the backed-off sleeper must not be due yet), then advances the remainder to `reachabilityPollInterval` and asserts `1` fired — instead of one blind `_ = await clock.advance(by: reachabilityPollInterval)`. Reworded the :152-154-era comment (now above the new advance calls) to state plainly that "the loop's own call is reliably the second of the two counted" is a consequence of this toolchain's cooperative single-actor scheduling of two non-suspending Tasks, not a documented language guarantee — matching the reviewer's "make the claim true, or reword it."

**B3 — `hidingActually…`'s failure branch released nothing.** `setVisible(false)` already nils `modelStreamProcess`/`runtimeStreamProcess` regardless of outcome, and the hide path never schedules a bounded reap (`boundedWait: false`), so `content.tearDown()` had nothing left to terminate in that branch. Added a `killAndReap(_:)` test helper (`SIGKILL` + `Process.waitUntilExit()`, the documented `waitUntilExit()`-on-a-forced-exit exception) and call it directly on `box.model`/`box.runtime` in the failure branch. Verified against the `process.terminate()`-removal mutation: failed cleanly at the 10s bound (previously this crashed the whole test process before the `EventCounter` `nonisolated` fix — see round 1 notes), **and confirmed zero orphaned `sleep 60` processes afterward** (`ps -axo pid,ppid,command | awk '$2==1 && /sleep 60/'` empty), closing the exact leak class #0430's reviewer observed.

**B4 — six bare readiness `#expect`s with no release.** Converted all six (`LMStudioDashboardPaneContentTests.swift`'s `tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM`, `LMStudioDashboardWiringTests.swift`'s `tearDownAllPaneContentSynchronouslyForQuitKillsATermIgnoringSubprocess` and `registryDrainReapsATermIgnoringSubprocessLeftByAClosedPane`) to `guard ... else { Issue.record(...); return }`. Each of the three tests now has a top-level `defer` — registered before the readiness guards, so it covers them too — that releases everything: `tearDownReturnsPromptly…`'s defer calls `gate.open()` then `killAndReap` on both processes (per the reviewer's "open the gate in a defer (§3), so a throwing `#require` can't leave children alive"); the two wiring tests' defers call `killAndReap` on both (one of them consolidates a pre-existing, too-late-registered defer that only covered the code *after* the `#require`s). All three defers are idempotent no-ops on the already-clean success path (opening an open gate, killing an already-dead process).
