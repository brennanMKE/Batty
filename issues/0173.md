#### What was investigated before bailing

- Read `BattyUITests/DragDropTests.swift:30–73` to understand the test.
  The assertion is `tabBars.count == 4` after `applyLayout twoByTwoGrid`
  where `tabBars` matches `identifier BEGINSWITH 'tab-bar.'`.
- Confirmed `tab-bar.<paneID>` is emitted exactly once per pane in
  `BattyKit/Sources/BattyKit/Views/PaneView.swift:101` (on the
  `SlidingTabBar`), so the expected count is `4` for a four-pane grid.
- Compared with `BattyUITests/LayoutTests.swift:24` which uses the same
  `applyLayout twoByTwoGrid` script and asserts on `pane-terminal.`
  count == 4. That test is reported as passing in the suite, which
  suggests the `twoByTwoGrid` driver path itself is fine and the
  failure is specific to how the `tab-bar.` accessibility elements are
  exposed or counted (likely a Mode-A query-shape problem, but cannot
  be confirmed without running).
- Reviewed `BattyKit/Sources/BattyKit/Testing/UITestDriver.swift` and
  the `swapPanes` / `applyLayout` intents. Driver looks correct.

Next subagent should: (1) verify libghostty-spm resolves before
touching the test, (2) run the failing test in isolation, (3) inspect
the captured xcresult to see whether `tabBars.count` is `0`, `1`, or
some other unexpected value — that will tell you whether the
accessibility identifier is unreachable, folded by a parent
`.contain` propagation, or simply not present yet when the wait
expires. The most likely fix is either widening the query (e.g. to
`pane-terminal.` like LayoutTests does, since the test only needs to
count panes), or rewriting the test to avoid the two-launch design
flaw called out in [[0170]]'s gotchas (it cannot capture IDs across
launches anyway, so the second launch is structurally useless).
