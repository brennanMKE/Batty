## Root cause

Two compounding issues:

1. **The reported failure no longer reproduces.** The original
   `XCAssertTrue failed - Expected 4 tab-bar elements after twoByTwoGrid
   layout` was almost certainly the runloop-blocking `Thread.sleep` from
   [[0170]] — the `waitFor` poll loop blocked the main runloop, starving
   XCUITest's XPC bridge of the responses needed to observe the
   `tab-bar.<id>` elements appearing. [[0170]]'s centralized
   `RunLoop.run(until:)`-based `waitFor` fixed that across the suite.
   Three consecutive runs of the unchanged test on today's main passed.

2. **The test design was structurally broken in a way that masked any
   real assertion.** It launched the app twice — once to record
   `idBefore0` and `idBefore2`, then a second time with the swap intent
   to record `idAfter0` and `idAfter2`. Pane UUIDs are minted per launch,
   so the `before`/`after` IDs came from different processes and could
   never be meaningfully compared. The test's only post-swap assertion
   was the tautology `idAfter0.hasPrefix("tab-bar.")`, which always
   passes regardless of whether the swap actually mutated the tree. The
   prior [[0170]] resolution notes called this out as a follow-up.

## Fix

Rewrote `testIntentSwapChangesTabBarOrder` as a single-launch test that
chains `applyLayout twoByTwoGrid` + `swapPanes at: 0 with: 2` in one
script (the existing intent dispatcher only runs at launch, so this is
the only way to compose intents in-process). Replaced the
cross-launch comparison with a structural invariant: after the swap,
exactly four panes exist, all four IDs are distinct, and all begin with
`tab-bar.`. A broken swap that duplicated one pane's contents into
another position would fail the `Set(ids).count == 4` assertion.

Did not modify any app code — the swap behavior itself is correct;
only the test was salvageable.

## Gotchas

- **Several "failing" UI tests in DragDropTests and elsewhere may have
  been fixed transitively by [[0170]].** When dispatching the next
  failing-test issue, run it first and see if it still reproduces. The
  Thread.sleep main-runloop block was a root cause that produced many
  superficially-different failure modes.
- **Intent dispatch is launch-only.** `UITestDriver.runIfNeeded` reads
  `BATTY_UI_TEST_SCRIPT` once during `RootWindowView.task { … }` and
  runs the full script in order. There is no in-process intent bridge
  for a running app, so any test that needs to "do A, observe, then
  do B with knowledge of what A produced" cannot be expressed as
  intents alone — IDs cannot be carried across launches. If a future
  test needs that capability, add a sentinel-file or pasteboard
  channel between the app and the test process; do not add a second
  launch and pretend.
