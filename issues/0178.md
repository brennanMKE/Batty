## Root cause

The original `XCTAssertGreaterThanOrEqual failed: ("0") is less than
("3")` failure at `KeyboardShortcutTests.swift:96` was caused by the
main-runloop-blocking `Thread.sleep` bug fixed in [[0170]]. The test
issues two `Cmd-T` keystrokes to create a third tab chip, then cycles
with `Cmd-Shift-]` / `Cmd-Shift-[`, then counts chips matching
`identifier BEGINSWITH 'tab-chip.'`. The synthesized `typeKey` events
are dispatched asynchronously over XPC; the app side needs the test
process's main runloop to be live in order for accessibility-tree
mutations (the new `tab-chip.<uuid>` identifiers) to be observed.

Pre-[[0170]], the surrounding `Thread.sleep` poll loops on
`@MainActor` test code starved the runloop so the chip-count query
fired before the new chips had been registered with the
accessibility tree — yielding 0 chips and the `0 < 3` failure. The
test itself does no `waitFor` after the cycling keystrokes (it just
queries immediately), which made it especially exposed: it depends
entirely on the runloop staying live between `typeKey` and the
subsequent count.

The app-side Cmd-T / Cmd-Shift-[ / Cmd-Shift-] routing is correct and
the chips do appear within the synchronous `typeKey` window now that
the runloop is pumping properly. Three consecutive runs of the
unchanged test on today's `main` all passed.

## Gotchas

- This test has no `waitFor` between the cycling keystrokes and the
  chip-count query — it relies on the synthesized `typeKey` events
  having fully propagated through the accessibility tree by the time
  the count returns. That's only safe because XCUITest's `typeKey`
  awaits `Wait for co.sstools.Batty.beta to idle` on each call (visible
  in the test log). If a future refactor switches to a non-idling key
  dispatch path, this assertion will start racing the chip-registration
  and need an explicit `waitFor({ count >= 3 }, ...)` wrapper.
- The assertion is structurally weak: it only checks chip count after
  a `]` then `[` cycle, not that the focused chip actually changed.
  A `Cmd-Shift-]` followed by `Cmd-Shift-[` on a healthy build is a
  no-op for focus, so the test would still pass if the cycling
  shortcut were silently broken. If/when this needs to be strengthened
  to actually verify focus changes, the test would need an
  accessibility identifier for the "focused" chip and an assertion
  comparing focused-chip identity before and after each cycle.
