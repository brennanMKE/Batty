# 0382 — The CLI cannot close a Session or hide/show a Pane, so agent-created structure is only partially reversible from the CLI

| | |
|---|---|

| **Platform** | macOS |

## Description

The `batty` CLI can create a Session but cannot close one, and it cannot hide or show a Pane even though the app has done both since #0256. Verified against `BattyKit/Sources/batty/`: `SessionNounCommand`'s subcommand list is `[SessionInfoCommand.self]` and `PaneNounCommand`'s is `[PaneSplitCommand.self, PaneCloseCommand.self]`; `XPCVerb` has no `sessionClose`, `paneHide`, or `paneShow`.

The result is an asymmetry that bites exactly the workflow this CLI exists for. An agent opens a Session for a task, splits three status Panes into it, and when the task is done it can close the Panes one at a time but must leave the Session sitting in the developer's Sidebar for them to dismiss by hand. It can create a Git Status Pane but cannot tuck it away with the eye toggle the way a human can — its only options are "visible" or "destroyed". Agent-created structure should be agent-reversible.

`docs/batty-cli-design.md` §A compounds this by reading as though the CLI verbs already shipped — it cites `pane hide`/`show` with "(#0256 shipped)", which is true of the *app* behavior and false of the CLI. [#0368](0368.md) owns correcting that phrasing; this issue makes it true instead.

## Expected behavior

Over XPC, reusing #0282's mutation-verb pattern and #0283's failure vocabulary:

```
batty session close [--session <id>]
batty pane hide [--pane <id>]
batty pane show <pane-id>
```

- `session close` and `pane hide` resolve their target through the existing chain (explicit flag → `BATTY_*` env → the app's focused element).
- **`pane show` requires an explicit id** and has no env fallback, for the reason #0257 already recorded: a hidden Pane has no shell to run `batty` from. Ids come from `batty list --json`, which includes hidden Panes.
- Reuse the app methods that exist rather than adding parallel paths: `WindowRuntime.hidePane(id:)` / `showPane(id:)` (`WindowRuntime.swift:657` / `:708`, with the `AppStateStore` counterparts at `:821` / `:831`) and the Session-removal path the Sidebar's close control uses (`WindowRuntime.removeSession(id:)` at `:185`, `AppStateStore.removeSession(id:)` at `:684`).
- **Failure vocabulary mirrors `pane close`** — a failure reply (`ok: false`) that the CLI surfaces as exit `4`, with *distinct* stderr messages for each cause so an agent can act on them:
  - unknown or stale id;
  - a Session whose close needs the confirmation dialog XPC has no UI to present;
  - refusal to close the app's last remaining Session.
- `pane show` on a Pane that is already visible, and `pane hide` on one already hidden, should succeed quietly rather than erroring — idempotent verbs are what scripts want.
- Mutating a background target must **not** steal focus or switch the selected Session (#0257 Foundation §2). Only the focus verbs in [#0381](0381.md) do that.

## Scope boundary — deliberately not filed

`tab new`, `tab close`, and the rename verbs (`session rename`, `tab rename`) stay **unfiled on purpose**. #0257's practice is that "a filed ticket reads as scheduled work", and children are filed as each slice is actually scheduled. They remain in #0257's Tier 1 catalog, unscheduled. Do not expand this issue to cover them; if they are wanted, they get their own child. ([#0381](0381.md) adds a `tab` noun for `tab focus` — that noun gaining one subcommand is not an invitation to fill in the rest.)

`pane zoom` likewise stays unfiled, and for a harder reason: `TopologyPayload.swift`'s own doc comment records that **no zoom concept exists anywhere in the runtime model**, so the verb would need the feature built first.

## Notes

- **Confirmation is the interesting case.** Closing a Session with live Terminal Sessions can require the same confirmation a ⌘W close does, and XPC has no UI. #0283 already settled the shape of this for `pane close` — refuse with a failure reply rather than closing without asking, or force-closing behind the user's back. Follow it exactly; do not add a `--force` flag in this issue.
- **Watch-event coverage.** The `watch` verb's app half is on `main` (`XPCVerb.watch`, `AppEventWatcher`, `XPCWatchMessages.swift`), but its event vocabulary predates several shipped mutations and has no `pane_close` event. There is also a verified precedent for coverage holes here: `WindowRuntime.createPane` — the #0331 menu path for typed Panes — **deliberately bypasses** `AppStateStore.splitPane`'s `AppEventWatcher` notification (see its doc comment at `WindowRuntime.swift:450-462`, which matches how the pre-existing GUI split actions behave). So a GUI-created Pane emits nothing today. Whichever of these verbs mutates state should decide, explicitly, whether it emits a watch event, and record the decision. [#0145](0145.md) owns the stream itself and is `in-progress` on its own branch — coordinate rather than duplicating.
- Hidden Panes already appear in `batty list` output flagged as `hidden` (`ListCommand.swift:121`), so id discovery for `pane show` needs no new work.
- Sequence after [#0381](0381.md) if both are worked in the same push — they add sibling subcommands under the same two nouns and will otherwise conflict on the same files.
