## Description

The user runs Batty on a MacBook and on a Mac mini, and today reaches
the mini through Screen Sharing. The want: **run a Session on the Mac
mini and attach to it from the MacBook** — every Pane in that Session
replicated and controllable from the remote Mac, the way `tmux
attach` works, without pushing pixels over a screen-sharing link.

**This is a design-and-stage umbrella for a future major release. It
is not scheduled work and nobody should start it tomorrow.** It ships
no code of its own. Its job is to record the architecture decision,
the hard problems, and a staged decomposition so the work is
*startable* when the user decides to start it — not to signal that it
is queued.

## The load-bearing finding: a remote Pane is not a video stream

The pinned libghostty-spm already supports feeding a surface from
somewhere other than a local PTY. `TerminalSessionBackend` is a public
enum with two cases, `.exec` and `.inMemory(InMemoryTerminalSession)`,
and `TerminalSurfaceOptions.init` takes `backend:` (defaulting to
`.exec`). `InMemoryTerminalSession` is constructed with two closures
and exposes a small byte-level API — see "Verified API surface" below
for exact signatures and paths.

That means a remote Pane does **not** require streaming pixels,
shipping Metal work over the wire, or writing a terminal emulator. It
is an ordinary Batty Pane whose byte source happens to be a network
socket instead of a local PTY:

- remote output arrives and is handed to `receive(_:)`;
- local keystrokes leave through the `write:` handler;
- local resizes leave through the `resize:` handler.

Rendering, IME, selection, scrollback, Themes, the Bell Feed, and the
Split tree are unchanged — they all sit above the byte boundary. This
is what makes the feature tractable at all, and it is why stage 1
below is a small, local, no-network proof.

## Architecture

### Option A — tmux control mode (recommended)

Run `ssh <host> tmux -CC new -A -s <name>`. tmux's control mode emits
a structured, line-oriented protocol (`%output`, `%layout-change`,
`%window-add`, `%begin`/`%end` command replies) instead of drawing a
screen, so Batty parses events rather than scraping a rendered
terminal. Map tmux panes to Batty Panes and the tmux window layout to
the Split tree; route `%output` payloads into `receive(_:)`; send
keystrokes back as tmux input commands.

This is the design iTerm2's tmux integration uses, so the shape is
proven in a Mac terminal app. It inherits, for free, the things that
are expensive to build: server-side persistence across disconnect,
multi-client attach, reconnection, and a wire format that already has
an ecosystem.

Cost: Batty stops being the authority for the things tmux owns
(layout, pane lifecycle, sizing), and inherits tmux's constraints —
see "Hard problems" below.

### Option B — a Batty-native remote protocol (deferred alternative)

Batty on the Mac mini serves; Batty on the MacBook attaches, over SSH
or over Bonjour + TLS. This preserves Batty's own model exactly and
could go past what tmux can express — true per-Pane sizes with no
shared clamp, image protocols, Bell Feed sync, Session color and
Theme fidelity.

The cost is rebuilding tmux: reconnect semantics, a state snapshot
format, scrollback transfer, authentication, and version skew between
two independently-updated copies of the app. **Record it as the
deferred alternative, not the plan.**

### Why A does not foreclose B

Both options need the same first step — a Pane whose bytes come from
somewhere other than a PTY (stage 1, #0342). Everything in stage 1 is
transport-agnostic, so starting with A costs nothing if B is later
chosen.

## Hard problems

These are the parts that are genuinely hard, stated plainly so a
future reader does not rediscover them.

### 1. Size negotiation — inherent, not a defect

tmux clamps a shared session to the smallest attached client. Two
Macs with different displays means one of them is letterboxed. This
is inherent to shared multiplexing; it is not something to engineer
away.

The question the design must answer explicitly is **handoff vs.
simultaneous**:

- **Handoff** — the Mac mini detaches when the MacBook attaches. Only
  one client is ever attached, so the clamp never binds and each Mac
  gets its full display. This matches the user's own phrasing about
  giving control of the terminal to the remote Mac.
- **Simultaneous** — both Macs render the same Session at once, both
  clamped to the smaller geometry.

**Proposed default: handoff.** Recorded as an open question below,
because it is the user's call and it changes the attach/detach UX
(#0346) substantially.

### 2. The Surface registry invariant needs a conceptual amendment

`CLAUDE.md` and `Concepts.md` both state that the Surface registry is
*the single source of truth for live Terminal Sessions*. For a remote
Pane that is no longer true: the **remote** holds the truth, and the
local surface is a replica of it. That is a real amendment to a rule
this project treats as binding, and it has to be written down
deliberately rather than drifted into.

A precision note for whoever does that work: the invariant as written
does not currently point at running code. `SurfaceRegistry`
(`BattyKit/Sources/BattyKit/Runtime/SurfaceRegistry.swift`) exists and
is exactly the `[UUID: ghostty_surface_t]` map both documents
describe, but a grep of `BattyKit/Sources` and `Batty/` finds **no
production caller** — its only references are in
`BattyKit/Tests/BattyKitTests/SurfaceRegistryTests.swift`. The
as-built registry is `TerminalHostStore`, which holds
`terminalViews: [UUID: AppTerminalView]` keyed by *tab id*, with the
surface owned inside the view. The amendment has to describe the
as-built thing, not only the documented one.

### 3. Unsolicited layout changes and the observation rules

With a remote backing a Session, layout changes arrive **from the
network**, unsolicited: `%layout-change`, `%window-add`,
`%unlinked-window-close`, a pane exiting on the far side. Nothing in
Batty's model has that shape today — every Split-tree mutation is
currently the direct consequence of a local command.

`docs/swiftui-observation-rules.md` is binding here and says how to
handle it:

- These are **event-origin** writes — the trigger is a delegate
  callback from outside the UI, the same category as a libghostty PTY
  event. That category is explicitly routine and allowed.
- They must have **an explicit owner**. Never write the Split tree
  from view construction — not from `body`, a view `init`,
  `NSViewRepresentable.updateNSView`, or a preference reduction.
- **Do not defer such a write into a `Task` to dodge a
  mutate-during-update warning.** That is the #0229 trap the doc
  records: it trades a crash for a race, and a `Task { @MainActor }`
  hop is not a safety device. If a write lands in the wrong context,
  restructure *which code owns it*.

`SplitTree` is `@Observable` (`BattyKit/Sources/BattyKit/Model/
SplitTree.swift`), and `@Observable` notifies on every write including
equal-value writes — a naive "apply the whole remote layout on every
`%layout-change`" implementation will invalidate the entire Session's
view tree on every remote keystroke that happens to reflow anything.

### 4. Layout authority moves to the remote

Under option A, tmux owns the split tree. Dragging a Batty divider
stops being a local model edit and becomes a `resize-pane` command
that has to round-trip: send, wait for the remote `%layout-change`,
apply.

**#0338 just shipped and lands directly on this path.** Its fix roots
a stable `.named` coordinate space so the divider `DragGesture`
measures in a space that does not move mid-drag; `onChanged` calls
`SplitDividerMath.ratio(...)` and feeds `onRatioChange`, which calls
`tree.updateRatio(forSplitID:to:)`
(`BattyKit/Sources/BattyKit/Views/SplitContainerView.swift`,
`BattyKit/Sources/BattyKit/Model/SplitTree.swift`, which is also the
sole 0.05–0.95 clamp point). For a remote-backed Session that local
write is no longer authoritative — it is a *prediction*. Two
consequences worth naming now:

- If the local ratio is applied optimistically and the remote's
  `%layout-change` disagrees, the divider snaps back — visually the
  same failure #0338 was filed to fix, from a completely different
  cause. #0338's own root cause (a coordinate space that moved
  because every `onChanged` re-placed the divider) is a warning about
  exactly this class of feedback.
- If the local ratio is *not* applied until the remote replies, the
  drag is only as smooth as the SSH round trip.

Neither is obviously right; #0345 owns choosing.

### 5. Scrollback on attach

tmux's `%output` carries the **live stream only**. Attaching to an
existing session therefore shows an empty Pane until something
prints, which reads as broken. Existing history needs an explicit
`capture-pane -p -S -` (or a bounded `-S -<N>`) replayed into the
surface before live output starts. #0347 owns this, including the
ordering problem: output that arrives while the capture is in flight
must not be interleaved ahead of the history.

### 6. Security

Option A's transport is SSH, and that is a substantial part of why it
is recommended: authentication, host verification, and encryption are
the user's existing SSH configuration, and Batty adds no listening
socket.

Option B does add one. **Batty is unsandboxed**
(`ENABLE_APP_SANDBOX = NO`, `Configuration/Build.xcconfig`) precisely
because it runs arbitrary user processes, so a network listener in
this process has an unusually large blast radius — anything that
reaches it can spawn shells with the user's full privileges. If B is
ever pursued, its authentication and peer-validation design deserves
the same scrutiny #0273/#0278 applied to the XPC broker, at minimum.

## Open questions

1. **Handoff or simultaneous attach?** Proposed default: handoff (see
   Hard problem 1). Blocks #0346's UX and changes whether the size
   clamp is a user-visible concept at all.
2. **Which Batty concepts map to which tmux concepts?** A tmux
   *session* to a Batty **Session** and a tmux *window* to the Split
   tree is the obvious mapping, but Batty also has **Tabs** inside a
   Pane, and tmux windows are the natural home for those. Getting
   this wrong makes #0345 unbuildable.
3. **Does a remote-backed Session look different in the Sidebar?**
   Connection state has to be visible somewhere; #0346 proposes the
   Sidebar row.
4. **Is a `Remote` module added to `issues/Issues.md`?** #0254's
   deliverable step 3 already anticipated this: *"If the SSH/remote
   direction is pursued, propose adding a `Remote` module to
   `issues/Issues.md` (don't invent it ad-hoc before then)."* This
   umbrella and its children deliberately did **not** invent it — they
   use existing module names. That decision is the user's.
5. **Does this change PRD §3?** "Session sharing or remote attach" is
   currently listed as an explicit **v1 non-goal**, and PRD §10 lists
   the adjacent v2 ideas (SSH connection manager, Mosh, the
   "Echolocation" iOS companion). Shipping this means editing both.

## Acceptance criteria

This umbrella can close only when **all** hold:

1. Every child above is terminal (resolved, closed, or wontfix).
2. The user can start a Session on the Mac mini, attach to it from the
   MacBook, drive every Pane in it, detach, and reattach — with the
   Panes' contents and layout intact across the detach.
3. The Surface-registry amendment (Hard problem 2) is written into
   `CLAUDE.md` and `Concepts.md`, describing the as-built registry,
   not only the documented one.
4. `PRD.md` §3's "Session sharing or remote attach" non-goal and §10's
   remote v2 ideas are reconciled with what actually shipped (Open
   question 5).

## Verified API surface

Everything below was read directly from the **pinned** libghostty-spm
checkout — revision `b146b73a8ba3ed2678a22a9de5feecfcbf298d48`, which
matches `Batty.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/
Package.resolved`, at `~/Library/Developer/Xcode/DerivedData/
Batty-dpjvytoxostyangasjrwwxqqbgmw/SourcePackages/checkouts/
libghostty-spm/`. Paths below are relative to that checkout's
`Sources/GhosttyTerminal/`.

- `InMemory/TerminalSessionBackend.swift` —
  `public enum TerminalSessionBackend: Sendable` with `case exec` and
  `case inMemory(InMemoryTerminalSession)`.
- `Surface/TerminalSurfaceOptions.swift` —
  `public struct TerminalSurfaceOptions: Sendable` with
  `public var backend: TerminalSessionBackend`; its `public init`
  signature is `init(backend: TerminalSessionBackend = .exec,
  fontSize: Float? = nil, workingDirectory: String? = nil,
  envVars: [String: String] = [:],
  context: TerminalSurfaceContext = .window)`.
- `InMemory/InMemoryTerminalSession.swift` —
  `public final class InMemoryTerminalSession: @unchecked Sendable`.
  Public members:
  - `init(write: @escaping @Sendable (Data) -> Void,
    resize: @escaping @Sendable (InMemoryTerminalViewport) -> Void)`
  - `func receive(_ data: Data)` and `func receive(_ string: String)`
    — host to terminal.
  - `func sendInput(_ data: Data)` — injects bytes directly into the
    host-side consumer, bypassing `ghostty_surface_key` translation.
  - `func finish(exitCode: UInt32, runtimeMilliseconds: UInt64)`
  - `func readViewportText() -> String?`
- `InMemory/InMemoryTerminalViewport.swift` —
  `public struct InMemoryTerminalViewport: Sendable, Equatable` with
  `columns`/`rows` (`UInt16`) and `widthPixels`/`heightPixels`/
  `cellWidthPixels`/`cellHeightPixels` (`UInt32`).

Three behaviors of that API that constrain the design, read from the
implementation rather than assumed:

- **`receive(_:)` silently drops data when no surface is attached.**
  It guards on `InMemoryTerminalSurfaceAccess.enqueueWrite(_:)`, which
  returns `false` while `surface` is `nil`, and logs a "dropped" line.
  `finish(exitCode:runtimeMilliseconds:)` behaves the same way. Any
  remote client that starts streaming before its Pane's surface exists
  loses those bytes.
- **`readViewportText()` reads the visible rows only** and explicitly
  ignores scrollback (its own doc comment says so). It is not a
  history-transfer mechanism; #0347 exists because of this.
- **Assigning a non-equivalent `configuration` tears the surface down
  and rebuilds it.** `TerminalSurfaceCoordinator.configuration`'s
  `didSet` calls `rebuildIfReady()` unless
  `TerminalSurfaceOptions.isEquivalent(to:)` holds, and
  `rebuildIfReady` starts with `tearDownSurface(...)`. Backend choice
  is therefore effectively a **creation-time** decision: swapping a
  live Pane from `.exec` to `.inMemory` destroys its surface,
  scrollback included.

### How Batty relates to this today

- **Production code does not use the in-memory backend.** Grepping
  `BattyKit/Sources` and `Batty/` for `inMemory`,
  `InMemoryTerminalSession`, and `TerminalSessionBackend` returns
  nothing.
- **Test code already does, and it works.**
  `BattyKit/Tests/BattyKitTests/AtlasOwnershipExperimentTests.swift`
  builds three real, attached surfaces with
  `TerminalSurfaceOptions(backend: .inMemory(
  InMemoryTerminalSession(write: { _ in }, resize: { _ in })))`,
  with no PTY, and observes attachment through
  `TerminalViewState.surface` going non-nil. That harness — written
  for #0287's atlas-ownership experiment, not for this — is direct
  evidence that a `.inMemory`-backed surface attaches and renders
  in-process. #0342 is smaller than it looks because of it.
- **Batty configures `TerminalSurfaceOptions` without naming the
  type.** `TerminalViewState.configuration` is a
  `TerminalSurfaceOptions`; Batty reaches it as
  `tab.terminal.configuration` — assigned to the view in
  `TerminalHostStore.terminalView(for:windowID:)` and mutated in
  `TabRuntime.init` (`self.terminal.configuration.workingDirectory =
  workingDirectory`). Adding a `backend` to that path is a change to
  code that already exists, not a new seam.
- **Surface creation is triggered by window attachment.**
  `AppTerminalView.viewDidMoveToWindow` calls
  `TerminalSurfaceCoordinator.rebuildIfReady()`, and
  `TerminalHostStore.terminalView(for:windowID:)` sets
  `view.configuration` *before* adding the view to the host — which is
  why the configuration, and therefore the backend, must be right
  before the view gets a window.
