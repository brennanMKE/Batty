# 0573 — The System Metrics process list has no filter by process name or PID

| | |
|---|---|
| **Status** | open |
| **Module** | Pane |
| **Platform** | macOS |
| **First seen** | 2026-11-11 |

## Description

The process list in the System Metrics Pane shows every process (often several hundred rows), with no way to narrow it down. Add one filter field above the list. Text typed into it matches a process's name or its PID, so `89` finds PID 1289. One field covers both. The user asked for this filter in "System Status".

User's request, verbatim: "Add a filter field in System Status which can filter by process name or PID. If I put in 89 it would match a PID of 1289, for example. We only need 1 text field for both."

## Which view "System Status" means

No view, Pane kind or string in the app is titled "System Status". `PaneContentKind.displayName` (`BattyKit/Sources/BattyXPCCore/PaneContentKind.swift:64-72`; raw value `system-metrics` at `:41`) lists "Git Status", "Process Status", "LM Studio Dashboard" and "System Metrics". Of the two candidates:

- **System Metrics** (`.systemMetrics`, CLI kind `system-metrics`), `SystemMetricsPaneView` in `BattyKit/Sources/BattyKit/Views/SystemMetricsPaneView.swift`, fed by `SystemMetricsPaneContent` (`BattyKit/Sources/BattyKit/Runtime/SystemMetricsPaneContent.swift`). This view has a "PROCESSES" section (`processSection`, `:335-349`) with Name / PID / CPU / Memory columns and sortable headers (`processListHeader`, `:356-370`). It shows every process in `content.snapshot.processes` (`[ProcessRow]`, `BattyKit/Sources/BattyKit/Runtime/SystemMetricsSnapshot.swift:36-54`) as a flat `List` (`processList`, `:391-402`). **This is the view the request means.** It is the only Pane that shows a list of processes with names and PIDs.
- **Process Status** (`.processStatus`), `ProcessStatusPaneView` in `BattyKit/Sources/BattyKit/Views/ProcessStatusPaneView.swift`. It inspects one process, not a list. Its "Pick a Running Process…" popover (`BattyKit/Sources/BattyKit/Views/RunningProcessPickerView.swift`) **already has** a "Filter by name or PID" field (#0486). Since that filter exists, the request must be about System Metrics.

If the user did mean something else, the planner should ask before planning.

## Expected behavior

1. **One field.** A single search-style text field (magnifying-glass icon, placeholder such as "Filter by name or PID") goes in the PROCESSES section, between the section heading row and `processListHeader`. No second field and no mode toggle.
2. **Matching rule.**
   - Trim surrounding whitespace from the query. An empty or whitespace-only query shows every row.
   - **Name:** the row matches when `ProcessRow.name` contains the query as a substring, ignoring case (and diacritics, like the existing picker filter).
   - **PID:** the row matches when the PID's decimal string (`String(row.pid)`) contains the query as a substring. `89` matches 1289, 89 and 8901. This is a substring match, not a prefix match (see "Differs from the existing picker filter" below).
   - A row matches if **either** rule matches. So `89` also shows a process named `x89y`. Only the PID rule is limited to digits: a non-digit query can never match a PID string, so it filters by name only.
3. **Sort still applies.** The filtered rows keep the column sort the user picked (`sortField` / `sortAscending`, `:28-29`, `sortedRows` `:319-333`). The filter narrows the rows and does not reorder them. Unlike the picker, an exact PID match is not moved to the top. In a sorted table, moving one row would break the sort order the user picked. This is decision 3.
4. **Survives refreshes.** `SystemMetricsPaneContent` replaces `snapshot` wholesale on every 1-second tick while the Pane is visible (`SystemMetricsPaneView.swift:12-16`). The filter must be applied to each new snapshot, so hidden rows don't flash back between ticks. New processes that match show up, and processes that exit disappear. The query text, and the field's keyboard focus, must stay put across ticks.
5. **Clearing.** The field has a clear (x) button while it holds text. Pressing Escape while the field has focus clears it. Escape on an empty field does nothing special. The Pane is not a popover, so unlike `RunningProcessPickerView.escape()` (`:107-113`) there is nothing to dismiss.
6. **Count.** The heading's `"\(count) total"` label (`:342-344`) should say how much the filter hides while it is active, e.g. "12 of 498". It stays "498 total" when the field is empty.
7. **No matches.** When the query matches nothing, the list area shows a short message such as `No processes match “<query>”` in place of an empty table, like `RunningProcessPickerView` (`:38-46`). This is a recommendation. See open question 2.

## Decisions (made while filing)

1. **The filter text is not persisted.** It is view-local `@State` on `SystemMetricsPaneView`, like `sortField` / `sortAscending` are today. When the view is torn down it starts empty again: the Pane is closed, the Pane is hidden (`WindowRuntime.hidePane(id:)` makes `SplitContainerView` stop building the `PaneView`, `docs/pane-view-lifecycle.md` "Hidden Pane" row), or the app relaunches. It is not written to `UserDefaults`, to any Project layout, or to the CLI.
2. **The filter state does not go on `SystemMetricsPaneContent`.** That `@Observable` model (`SystemMetricsPaneContent.swift:40`) owns sampling only. Putting the query there would make every keystroke an observed write on the model that the sampler also writes every second, for no benefit. Keeping the query in view-local `@State`, written only from the field's binding (an event-origin write), is routine under `docs/swiftui-observation-rules.md`. The filtered rows are computed in `body` from `content.snapshot.processes` + the query + the sort, as a pure derivation with no write. Do not add an `onChange(of: content.snapshot)` that stores the filtered rows.
3. **No exact-PID-first reordering** (see Expected behavior 3).
4. **The matching rule is a pure function** outside the view (for example next to `ProcessPickerFilter` in `BattyKit/Sources/BattyKit/Runtime/`, working on `[ProcessRow]`), so it can be unit-tested without a view. This is the same split #0486 used for the picker (`ProcessPickerFilter.swift`, tested in `BattyKit/Tests/BattyKitTests/ProcessPickerFilterTests.swift`).
5. **The filter matches the process name only, not `ProcessRow.path`.** The user asked for name or PID.

## Differs from the existing picker filter

`ProcessPickerFilter.apply` (`BattyKit/Sources/BattyKit/Runtime/ProcessPickerFilter.swift`) matches a PID by **prefix** (`String($0.id).hasPrefix(trimmed)`) and moves an exact PID match to the top. The user's example (`89` → 1289) needs **substring** matching, so the System Metrics filter cannot reuse that rule unchanged. This issue does not change the Process Status picker's behaviour. Its prefix rule is pinned by `ProcessPickerFilterTests` and was decided in #0486. Whether the picker should switch to substring matching too is open question 1.

## Keyboard and focus interactions

- **App key monitor.** `BattyApp.swift:89-91` installs a local `.keyDown` monitor that runs `BattyShortcuts.handle(_:)` (`BattyKit/Sources/BattyKit/Commands/BattyShortcuts.swift:20`) before any view sees the key. Every default `ShortcutAction` binding includes Command (`ShortcutAction.defaultBinding`, `BattyKit/Sources/BattyKit/Shortcuts/ShortcutAction.swift:98` onward: Cmd-, Cmd-Shift-, Cmd-Option- and Cmd-Control-arrow combos). The positional Cmd-1..9 / Cmd-Option-1..9 also include Command. So plain typing, Backspace, Escape and arrow keys reach the field, and Cmd-A/C/V/X/Z are not bound by default. A user-customized binding with no modifier would take that key from this field, as it already does from every other text field in the app. That is out of scope here. `PlainShellKeyRewrite.rewrite` only acts when the first responder is an `AppTerminalView` (`PlainShellKeyRewrite.swift:85`), so it does not touch this field.
- **Click-to-focus.** `PaneView`'s non-terminal shell has `.onTapGesture { appStore?.focusPane(id: pane.id) }` (`BattyKit/Sources/BattyKit/Views/PaneView.swift:432-434`). `TerminalClickFocusMonitor` promotes only `AppTerminalView`s to first responder, and `TerminalSurfaceFocuser` only acts on `tab.terminalNSView`. As far as the code reads, clicking into the field should both focus the Pane and give the field keyboard focus. The planner should confirm that the outer tap gesture does not swallow the first click on the field, and that focusing the Pane does not take first responder away from the field.
- **Refresh vs. focus.** The once-a-second `body` re-evaluation must not rebuild the field with a new identity. That would drop focus and the insertion point mid-typing.
- **Terminal-pane requirements.** `docs/terminal-pane-requirements.md` covers terminal Panes. This view has no terminal surface, so the pointer, file-drop and IME rules there don't apply directly. The only shared surface is the pane shell's tap gesture above.

## Open questions

1. Should the Process Status picker (`ProcessPickerFilter`) also switch from PID-prefix to PID-substring matching, so the two process filters in the app behave the same? Out of scope here unless the user says so.
2. Empty-results message: confirm the wording, and whether it replaces the table or sits inside it.
3. Should Cmd-F (or another shortcut) move focus to the filter field while a System Metrics Pane is focused? No `ShortcutAction` exists for find/filter today, and adding one touches `ShortcutAction`, Settings and the menus. Recommend not doing it in this issue.
4. Does the filter text survive switching to another Session and back, or switching away from and back to the Pane's Tab? This depends on whether SwiftUI keeps `SystemMetricsPaneView`'s `@State` alive across those switches. Whatever happens, `sortField` already behaves the same way, and the filter should match it, not add its own persistence. The planner should check and record what happens.
5. Child processes: the list is flat (`List(sortedRows)`, no parent/child tree), so "keep the children of a matching parent visible" does not apply. Recorded only so it isn't asked again.

## Acceptance criteria (user-verifiable)

1. Open a System Metrics Pane (Pane > Open View > System Metrics, or `batty pane split --view system-metrics`). A single filter field appears above the process table's column headers.
2. Type `89`. Only processes whose PID contains `89` (for example 1289, 8901, 89) or whose name contains `89` stay listed.
3. Type part of a process name in mixed case, e.g. `SAFARI` or `finder`. Matching processes stay listed, ignoring case.
4. With a filter active, wait several seconds. Hidden rows do not flicker back, CPU/Memory values in the visible rows keep updating, and the field keeps its text and focus.
5. With a filter active, click a column header. The filtered rows re-sort and the filter stays applied.
6. The process count label shows how many rows match out of the total while filtering, and returns to "N total" when cleared.
7. Clicking the field's clear button, or pressing Escape in the field, empties it and every process reappears.
8. A query that matches nothing shows a "No processes match …" message, not a blank table.
9. Close the Pane and open a new System Metrics Pane. Its filter field is empty.
10. While typing in the field, no Batty shortcut fires and no keystroke reaches a terminal Pane.

## Notes

- Unit-test target: the pure matching function. Cases: empty and whitespace-only queries return every row; name substring ignoring case; PID substring (`89` matches 1289, 89 and 8901 but not 1298); a digit query that matches either name or PID; a non-digit query never matches by PID; the result keeps the input order. Swift Testing, pure, no sleeps (AGENTS.md "Asynchronous tests").
- UI coverage: give the field an accessibility identifier (e.g. `system-metrics.filter-field`) and the empty state one (e.g. `system-metrics.filter-empty`). Any new UI test runs only in the Tart VM. Per issue, check it compiles with `./build.sh ui-typecheck`.
