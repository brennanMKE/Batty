## Description

In #0412's first full Tart-VM run (run id `20260923-191103-94702`), the app's unified log (`app-warnings.log`) shows `AppXPCCoordinator` failing to reach the broker in every launch, all run long:

- 520 × `broker connection invalidated — discarding it and building a new one`
- 104 × `broker unreachable: Couldn't communicate with a helper application.`
- repeated `broker invalidation — reconnect budget exhausted, scheduling a backoff retry …` (#0361's backoff loop)

That's 624 lines across the run's 73 app launches. The UI suite passed regardless, because no current UI test uses the XPC surface. #0413's planned suite drives Batty through the `batty` CLI (`batty-beta ping`/`list`/`new`/`pane split`/…), and every one of those verbs goes through the broker. **Until this is fixed, #0413 can't run in the VM** beyond asserting the "broker unreachable" exit paths.

## Cause: not established. Two candidates

**1. The broker LaunchAgent was never registered in the fresh guest. This is the most likely cause, and it's by design.** Batty only registers the broker's `SMAppService` agent when the user asks, from Settings. `AppXPCCoordinator.attemptRepairIfNeeded()`'s doc comment (`BattyKit/Sources/BattyKit/XPC/AppXPCCoordinator.swift:269-287`) says a `.notRegistered`/`.requiresApproval` state "means the user has not opted in", and that calling `register()` there "would be an unrequested enrollment — that stays the deliberate, user-initiated action in `SettingsView` (#0270)". The only automatic `register()` call (`:320`) runs when `SMAppService` already reports `.enabled`. A freshly cloned guest has never opted in, so nothing ever registers the agent. Its Mach service doesn't exist, and every connection is invalidated. Signing isn't involved in this candidate at all.

**2. Signing rejects registration, the #0401 failure class. Less likely here than in #0401's case.** #0401 found that an *unsigned* Beta package (`./build.sh package` → `scripts/build-beta.sh`, built with `CODE_SIGNING_ALLOWED=NO`) can't register its broker (`SMAppService` → `-67056`, `errSecCSResourcesNotFound`). `issue/0401` fixes that by ad-hoc signing the whole bundle in `scripts/build-beta.sh`'s package path. **That fix doesn't reach the VM runner.** `tools/run-ui-tests-vm.sh` (on `issue/0412`, `:234-238`) builds with plain `xcodebuild -workspace Batty.xcworkspace -scheme 'Batty UI Tests' … CODE_SIGN_IDENTITY=- CODE_SIGN_STYLE=Manual DEVELOPMENT_TEAM= test`. It never touches `build-beta.sh`.

However, the guest build isn't in #0401's unsigned state. The guest's `xcodebuild.log` shows:

- signing identity "Sign to Run Locally";
- a `CodeSign …/Batty Beta.app` step, which produces an Xcode ad-hoc signature with a resource seal;
- the "Embed Broker" phase re-signing `Contents/Resources/bin/BattyBroker` ("replacing existing signature").

So #0401's specific cause, a bundle with no resource seal, shouldn't apply. Whether `SMAppService` accepts an Xcode ad-hoc-signed, no-team agent is still unverified. `issue/0401`'s `scripts/build-beta.sh` header likewise says #0401 "could not perform a live registration" with an ad-hoc signature.

**The run's logs can't separate these candidates.** The runner's log predicate (`tools/run-ui-tests-vm.sh:249-250`) keeps only `error`/`fault` messages and SwiftUI/AttributeGraph subsystems. The `notice`-level line that would settle it was filtered out: `attemptRepairIfNeeded: SMAppService state is <state>, not .enabled …` (`AppXPCCoordinator.swift:298`).

## Expected behavior

A VM run can bring up a working broker, so `batty-beta ping` answers from inside the guest and #0413's verbs can be exercised against a live app. Whatever it takes (registering the agent in the guest, a signing change, or both) is recorded in `docs/ui-testing-vm.md`. It must not weaken the opt-in rule for real users. If registration turns out to need a user-approval prompt ("Allow in the Background"), the golden image must not accumulate a TCC grant (#0412's rule), and that constraint needs to be written down.

## Notes

- First diagnostic: in a guest, after one launch, capture the `SMAppService` status. You can do that by widening the log predicate to `notice` for the `AppXPCCoordinator` category, or by running `launchctl print gui/$(id -u)/co.sstools.Batty.beta.broker` and `sfltool dumpbtm`. `.notRegistered` confirms candidate 1. A registration error code points at candidate 2.
- If candidate 1 holds, the test harness needs a guest-only way to opt in, for example a UI step through Settings → Register, or a test-mode launch flag. A test-mode flag must never be reachable in a shipped build.
- Hardened Runtime and XPC peer validation: `issue/0401`'s `build-beta.sh` notes that peer validation has an escape hatch for unsigned/ad-hoc builds. Check that it covers the Xcode-ad-hoc guest build too.

## Investigation (round 1, implementer)

Evidence from the existing VM runs under `build/ui-tests/` before any change:

- Every one of the app's connection attempts is invalidated immediately ("Couldn't communicate with a helper application" is the NSXPC error for a Mach service name nobody owns), 5 to 10 per launch with no successful connection in any run. Nothing in the logs suggests a connect-then-reject.
- The app under test runs from `DerivedData/.../Products/Debug/Batty Beta.app`, ad-hoc signed by Xcode ("Sign to Run Locally"). The broker is only ever registered by `BrokerAgentController.register()` (Settings, #0270) or by `attemptRepairIfNeeded()` when `SMAppService` already says `.enabled`. A fresh clone has neither, so launchd has no `co.sstools.Batty.beta.broker` service. That is candidate 1 and it is sufficient by itself.
- Candidate 2's peer-validation half does not apply: `PeerCodeSigningRequirement.requirement(forTeamIdentifier:)` returns `nil` for an ad-hoc binary (no Team ID), so neither the broker nor the app/CLI enforces a requirement in the guest.
- Whether `SMAppService.register()` would accept this ad-hoc Xcode-signed bundle was never tested; the fix below bypasses it (see Gotchas).

## Fix

No production change.

- `tools/vm-guest-broker.sh` (guest only; refuses unless `kern.hv_vmm_present` is 1) bootstraps an equivalent per-user launchd agent (same Label and MachServices key as the bundle's plist, absolute `Program`) for the built app's embedded `BattyBroker` into `gui/<uid>`, and records `codesign`, `launchctl print`, and `batty ping` to `broker-diagnostics.log`.
- Finding: the XCUITest runner (`BattyUITests-Runner.app`) is App Sandboxed (`com.apple.security.app-sandbox`, with a fixed `mach-lookup` allow-list), and a `Process` it spawns inherits that sandbox. Run 20261006-020341-13690's `sandbox-denials.log` records the denial itself: `Sandbox: batty(<pid>) deny(1) mach-lookup co.sstools.Batty.beta.broker`. A `batty` spawned from a test therefore exits 2 even though the broker is up and the app has registered its endpoint with it. So the same script also installs a guest-only launchd agent, `co.sstools.Batty.beta.uitest-cli-relay`, listening inetd-style on `127.0.0.1:47911`. `tools/vm-guest-cli-relay.sh` runs the embedded CLI outside the sandbox for each connection. Protocol: one line of tab-separated arguments in (no shell evaluation, so arguments may contain spaces but not tabs); combined output out, then a final `__EXIT__ <status>` line. The runner's `network.client` entitlement is what lets a test reach it, through `/usr/bin/nc`.
- `tools/run-ui-tests-vm.sh` now runs three separate guest steps (`build-for-testing` with a pinned `-derivedDataPath`, the broker script, `test-without-building`). Each has a guest-side `alarm` bound and a host-side poll-and-kill bound (`wait_bounded`), and results are pulled after the build and broker steps and at the end, also bounded (`pull_results`). Its log predicate now includes `AppXPCCoordinator` and `BrokerAgentController` at info level, and it writes `sandbox-denials.log`.
- `BattyUITests/BrokerReachabilityTests` launches the app and, through the relay, asserts `ping` exits 0, `status --json` reports `state` ok with at least one window and a `bundlePath` equal to the app XCUITest launched, and `list` exits 0.
- `docs/ui-testing-vm.md` is updated for the new flow.

## Gotchas

- This bypasses `SMAppService`, so the VM suite still does not cover Settings registration (#0401); whether `SMAppService.register()` accepts the ad-hoc guest bundle, and whether it would raise an "Allow in the Background" prompt (#0413 open question 3), is still unknown.
- Answers #0413's open question 1 negatively: a binary spawned from the UI-test runner cannot reach the broker (runs 014328-4547 and 020341-13690). CLI-driven tests need the relay.
- The relay listens on loopback with no authentication. It exists only in the disposable guest, where `vm-guest-broker.sh` refuses to run on a host.

## Resolution

The guest never had a `co.sstools.Batty.beta.broker` launchd service: the broker is only
registered from Settings or by repair when `SMAppService` already reports `.enabled`, and a fresh
clone has done neither. The VM runner now bootstraps the embedded broker as a guest-only
per-user agent (`tools/vm-guest-broker.sh`, refuses unless `kern.hv_vmm_present` is 1), after
which the app connects. The CLI spawned by the sandboxed XCUITest runner inherits its sandbox
and is denied `mach-lookup` of the broker, so CLI-driven UI tests go through a guest-only
loopback relay (`tools/vm-guest-cli-relay.sh`, 127.0.0.1:47911) that runs the real embedded CLI
outside the sandbox against the real broker and app. `BrokerReachabilityTests` proves
`ping`/`status`/`list` reach the launched app. No production code, `scripts/` or `Build.xcconfig`
change; the VM suite still does not cover Settings-driven `SMAppService` registration (#0401).
