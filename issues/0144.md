# 0144 — File drop from Finder onto terminal is broken

| | |
|---|---|
| **Status** | open |
| **Module** | DragDrop / Pane |
| **Platform** | macOS |
| **First seen** | 2026-05-19 |

## Description

Dragging one or more files from Finder (or any source producing file URLs) onto a terminal pane no longer inserts their shell-quoted paths at the prompt. The file hover highlight does not appear and the drop is silently rejected.

This is a hard-required v1 feature (PRD §6.12) and a regression from #0022.

## Expected behavior

Dropping a file onto any visible terminal pane inserts its POSIX-quoted path at the cursor — the same behavior confirmed working when #0022 closed on 2026-05-09.

## Actual behavior

The file drag shows a "not allowed" cursor (or no feedback) and nothing is inserted. The `isDragHovering` blue stroke overlay never appears.

## Root cause

`PaneSwapDropTarget` (added for #0127) attaches SwiftUI's `.onDrop(of: [.plainText])` to the `ZStack` containing `TerminalPlaceholderView`s inside `PaneView`. In `sessionStack` (`SessionDetailView`), `TerminalHostInstaller` is the **first** child of the outer `ZStack` and `SplitContainerView` (which contains `PaneView`) is the **second** child. SwiftUI ZStack order maps 1:1 to AppKit subview order, so `PaneView`'s SwiftUI backing NSViews sit **above** `TerminalHostView` in AppKit's z-order.

AppKit's drag-routing algorithm:
1. Calls `hitTest` on the content view, which returns the topmost (highest z-order) view at the cursor — the SwiftUI ZStack backing NSView registered by `PaneSwapDropTarget`'s `.onDrop`.
2. Walks the **ancestor chain** of that view looking for a registered `NSDraggingDestination` that accepts `.fileURL`.
3. The ancestor chain of the SwiftUI ZStack NSView never reaches `TerminalHostView` (they are **siblings**, not ancestor–descendant).
4. No `.fileURL` destination found → drag rejected.

`TerminalHostView` registers for `.fileURL` with `registerForDraggedTypes([.fileURL])` and implements the full `NSDraggingDestination` protocol, but it is never reached because the SwiftUI `.onDrop` view intercepts the drag session first.

This is the same class of z-order / ancestor-chain mismatch documented in issue #0102 (which led to moving file-drop registration from SwiftUI's `.onDrop` into `TerminalHostView` in the first place). #0127's `PaneSwapDropTarget` re-introduced the problem from a different direction.

## Fix

Remove the SwiftUI `.onDrop(of: [.plainText])` call from `PaneSwapDropTarget` entirely — this is what blocks file drops. Pane-swap drop detection must be implemented at the AppKit level to avoid the ancestor-chain problem:

- Add a custom `NSView` subclass implementing `NSDraggingDestination` for `.plainText` (UUID strings only).
- This NSView is added as a subview of `TerminalHostView` (or registered at the same AppKit level), so AppKit's ancestor-chain walk from any terminal subview reaches it.
- In `draggingEntered`/`draggingUpdated`, inspect the pasteboard: if the data is a valid UUID string, accept with `.move`; otherwise return `[]` so the drag falls through to `TerminalHostView`'s file-URL handler.
- Call back into SwiftUI via a `Binding<Bool>` for `isTargeted` (to drive the highlight) and a closure for the swap action.

Until the custom AppKit drop target is implemented, pane-swap-by-drag operates without a highlight (the swap still executes on drop, or is temporarily disabled). File drops must work; pane-swap highlight is secondary.
