## Description

A Shared Project syncs its background's fit, position and opacities, but not its image, so on another Mac the Project opens with no picture until the user chooses the same file again. The image should travel with the Project. Child of [#0372](0372.md). [#0552](0552.md) doesn't depend on this issue; see "What #0551 adds later" in its Plan for what this issue adds there.

> "Since I want to include the image with the Projects feature which can be synced with iCloud we need to also copy the image into the iCloud synced folder."

**Not in 1.3.5 by default.** 1.3.5 is a patch that is close to shipping, and this adds new storage. That is the orchestrator's default, not a user decision, and the user may override it.

## Plan

Written 2026-11-04 against `f76c1252`. Read `docs/swiftui-observation-rules.md` before steps 4 and 5.

**No Apple portal, profile, entitlement or `scripts/` change.** The design uses a plain folder in iCloud Drive as transport. Whether that folder works without a ubiquity entitlement **can't be proven without a real Mac**, so it ships behind a flag, on in Beta, until the user has run U1 to U8 below. Nothing is read from or written to the user's iCloud Drive by any agent, build or test.

**One thing needs the user's OK before step 5:** adding `NSFileProviderDomainUsageDescription` to `Configuration/Info.plist` (see "Evidence"). `AGENTS.md` restricts `Configuration/Build.xcconfig` by name, and `docs/design/projects-sharing.md` calls all of `Configuration/` restricted, so treat it as restricted. It doesn't block steps 1 to 4. If the user declines, leave it out and record that in `## Gotchas`; the access prompt then has no explanation, and may not appear at all (the third-party report under "Evidence").

### The scope rule

From the user: "We only need to sync with iCloud if an image is selected for a Project which is set to be Shared."

- **A copy goes to iCloud in two cases only:** an image is chosen for a Project already set to Shared, or a Project that already has an image becomes Shared.
- **Nothing syncs by being in the library.** An image added through the Background Images window, one used by a Pane or Session, the app-wide default and an image on a local Project are never copied to iCloud or looked up there. Background Images does not list or query the shared folder for them.
- **Retries serve the same selection.** A failed or lost copy of an image a Shared Project's record names is copied again, because the selection still stands. There is no third reason to upload.
- **A local Project's record doesn't exist,** so it has no digest to publish.

### Decisions

| Question | Decision | Why |
|---|---|---|
| Storage | **iCloud Drive folder, as transport only**: `~/Library/Mobile Documents/com~apple~CloudDocs/<Batty or Batty Beta>/Project Backgrounds/<digest>.png`. The suggested shape in this issue is accepted: `imagePath` always names a verified local copy in `ProjectBackgrounds/`. | No portal steps. libghostty never gets a path that isn't materialized, `checked(_:)` keeps its directory rule, opening never touches the network, and older Batty's `reclaim` keeps seeing the local path. The folder sits behind one protocol, so the fallback replaces one type. |
| Shared file name | Fixed, `<digest>.png`, flat. | Finding 5: no user-controlled text in a shared path. A digest validated as 64 lowercase hex is the only input. A file the user renames or moves reads as absent. |
| Display name | The record also carries `imageName`, at most 100 bytes on send. The receiver treats it as untrusted: drops control characters, quote, backslash, `/`, `:` and leading dots, then bounds it; empty becomes `image`. | The Project Editor shows the file's name. This only names the local copy, whose folder is already validated. |
| Is a digest match enough? | **Yes:** SHA-256 of the bytes read equals the record's digest and the file's name, plus the header pixel check, on one read of the bytes. No re-encode, and no extra PNG check. | Finding 6. A sender uploads only what passes `inspect` and `isWithinPixelLimit`, and `inspect` fails on any change after import. A file that passes and still breaks `ghostty_surface_new` must be hand-placed in that user's own folder and named in their own `projects.json`, which is the state #0540 already accepted. Re-encoding would change the digest, so Macs would disagree about the record. |
| Local state | New optional `Project.sharedImage`, in `projects.json`: `.named(digest, name)` or `.removed`. Nil means the Project has never published an image. Pending is derived: `.named` whose digest differs from the digest of `imagePath`. | Finding "A digest named by a record has no `imagePath`". Additive, and written only when set, so a local Project's object stays byte-identical. |
| Pending state | **No new `BackgroundImageState` case.** A pending Project has a nil path (or its earlier image), so `checked(_:)` reports no problem and the Sidebar shows no triangle. The Project Editor shows a caption from `Project.sharedImage`. | Finding 2. Every existing `.missing` warning stays meaning a lost file. |
| Open Sessions | When an image arrives, a Session from that Project whose `backgroundOverride` still equals its `projectBackgroundSeed` gets the new path on both, through `setBackgroundOverride`. A Session the user changed is left alone. | Finding 3: the Project opens without its picture, and the picture appears when it arrives. Seed and override change together, so `SaveSessionAsProject` doesn't read this as the user's edit. |
| Removal | Explicit `imageRemoved: true`. A record's image is one of three: **named**, **removed** or **unspecified** (neither key). Unspecified keeps this Mac's image and pending state. | Older Batty writes unspecified, and a remote "Custom, no image" has to go on keeping this Mac's image (`remoteChangeReplacesOpacityAndKeepsThisMacsImage`). Without an encoding, a None on one Mac would be undone by the next edit on another. |
| Who sets `.removed` | `ProjectStore.upsert` only, for a Shared Project: **None** or **Don't Use This Image** in the Project Editor. | Those are decisions about the Project. See "What each action does". |
| Each variant's folder | **Per variant,** from `SessionNameCache.resolvedDirectoryName()`. | Prod and Beta key-value stores are separate, so one folder's keep-set couldn't see the other's records, and a Beta test must never affect Prod. |
| Upgrade | **No publish without a user action.** `sharedImage` stays nil until the user next chooses an image, saves that Project or re-shares it. A Save with an unchanged image counts, and is last-writer-wins like every other field. | The default this issue proposed, confirmed: `modifiedAt` isn't stamped by the upgrade, and a Mac's hand-chosen image is never replaced by launching. The replaced local copy stays until `reclaim`, and the library has it if a scan promoted it. |
| Older Batty | No code beyond "unspecified keeps everything". A line goes in the release notes of the release that removes the flag. | Checked: `v1.3.4`'s `ProjectSync.swift` has no `background`, and `release/1.3`'s `ProjectSyncBackground` decodes through `TerminalBackgroundSettings`' keyed container, which ignores the new keys and writes only its own. So an older Mac's edit drops the digest and the next edit on a newer Mac publishes it again. 1.3.4's Follow clear stays #0544's decision. Older versions never touch the shared folder. |
| Feature flag | **Yes:** `sharedProjectImages`, on in Beta, off in Prod. Remove it in the release that ships this, after U1 to U8 pass. | It rests on behaviour no agent can verify, and it writes into the user's iCloud Drive. With it off, records don't change, no shared folder is read or written and no new UI shows. |
| Gate | Transport exists only when `!isTestProcess && hasEntitlement && flags.sharedProjectImages`, the same shape as `defaultProjectSyncBackend`. | Finding 9. Routine builds, tests and the VM have no entitlement, so no transport. Only a `./build.sh package --sign` Beta reaches iCloud Drive. |
| Failures | **Never cost the Project.** File work starts after the local commit, and a failure sets `SharedProjectImages.message`. It never throws out of `upsert` or `setShared`. | Finding 8. |
| Merge | `ProjectSyncMerge.apply` stays pure. It gains `honorsSharedImages: Bool = false`, and the coordinator does all file work after the merge. | Requirement. The default keeps existing callers and tests. |
| The window's status | The model keeps `sharedStatus: [digest: SharedImageStatus]` for digests of Shared Projects only. **Not** the field on `BackgroundImageEntry` that #0552 suggested. | The scan and `Equatable` stay untouched, and the scope rule is visible in the type: no other image ever has a status. |

### What each action does

| Action, on a Shared Project unless stated | This Mac's Project | Record | Shared copy |
|---|---|---|---|
| Choose an image | Path to the new local copy, `sharedImage` `.named` | Names the new digest | **New copy uploaded** after the commit. **The old copy stays** until the sweep, unless another record names it |
| Make a Project with an image Shared | `sharedImage` `.named` | Published, naming the digest | **Copy uploaded** after the commit |
| Make a Project with no image Shared | `sharedImage` nil | No image keys | Nothing |
| **None** or **Don't Use This Image** | Path nil, `.removed` | `imageRemoved: true`; other Macs clear theirs | Stays until the sweep |
| Follow Settings | Background nil, `sharedImage` nil | No `background`, as today | Stays until the sweep |
| **Unshare** | Keeps its image and local copy; `sharedImage` nil | Key removed (`withdraw`). Other Macs keep the Project as local with whatever copy they hold, and drop a pending image | **Not deleted now.** Stays until the sweep |
| **Delete the Project** | Gone; local copy left to `reclaim` | Tombstone | **Not deleted now.** Stays until the sweep |
| Remove in Background Images | Path nil, `sharedImage` nil, no stamp, no publish (#0552 rule) | Unchanged. A later Save here publishes unspecified, so other Macs keep their image | Stays. It **comes back here only if another Mac then changes the Project**; the confirmation says so |

**Why nothing is deleted on the spot:** another Mac may be mid-download, a snapshot may be stale, and a user can re-share. Removing the shared copy at once gains little and is the one step that can lose what another Mac needs.

### Cleanup

- **`reclaim` is unchanged in rule.** It also keeps a folder whose digest a Project's `sharedImage` names, including ones in `projects.json` but not this list. `imagePathsInFile()` stays as it is, and a new `sharedImageDigestsInFile()` sits beside it.
- **The sweep** runs after `reclaim` when the Project Editor closes, at most once per launch, off the main actor, and never reads a file's contents. It touches only names matching `<64 hex>.png` in this variant's folder.
- **It runs only if all of these hold:** the folder is available, `snapshotIsAuthoritative`, the backend skipped no undecodable entry (new `snapshotSkippedEntries`, because a newer version's record may name a digest), `mayReferenceUnlistedImages` is false and `imagePathsInFile()` isn't nil.
- **It deletes** a file named by no record in the snapshot and no local `sharedImage`, once that has been true for **30 days** on this Mac's own clock.
- **Dates:** folder dates in iCloud Drive aren't used. A device-local ledger, `shared-image-sweep.json` beside `projects.json`, records when each digest was first seen unnamed, and a digest named again leaves it. 30 days matches `tombstoneLifetime`.
- **Recovery:** a digest named by a record but absent from the folder is uploaded again by any Mac holding it. Deleting too early costs a re-upload, as long as one Mac has a copy.

### Evidence on the entitlement question

**Conclusion: unverified, and only a real Mac can settle it.** No probe was run against `~/Library/Mobile Documents`.

| Source | Says | So |
|---|---|---|

| Third party: [cmdr commit](https://github.com/vdavid/cmdr/commit/01bc0dae) | Calls those APIs on `com~apple~CloudDocs` paths and says they "accept any URL inside an iCloud container" | Encouraging, but its sandbox and entitlement state isn't shown |

| Third party: [a user-filed bug report](https://claudeissues.com/issue/74658-bug-on-mac-desktop-app-is-silently-denied-file-provider-dropbox-onedrive-google) | With no usage string, access was silently denied rather than prompted | Unverified, but it's why the key is worth adding |
| [Forum thread 823369](https://developer.apple.com/forums/thread/823369) | A **sandboxed** app lost `~/Library/Mobile Documents` access mid-session on macOS 26 | Differs from Batty, but a failed read must be a retryable state, never a stored verdict |
| [Forum thread 785030](https://developer.apple.com/forums/thread/785030) | On iOS 18.4+, a file can stay `Downloaded` and never update. One unanswered post | Not a problem here: bytes are checked against the digest, and a mismatch requests a download and stays pending |
| `FoundationErrors.h` | `NSUbiquitousFileNotUploadedDueToQuotaError` (4354), `NSUbiquitousFileUbiquityServerNotAvailable` (4355) | "iCloud is full" is read from `ubiquitousItemUploadingError`, since a plain copy won't report it. Whether it's populated here is U6 |

**Detecting iCloud Drive off (finding 4):** `availability()` returns `.off` if `com~apple~CloudDocs` is missing or its `isUbiquitousItem` value is false or unreadable, `.notAllowed` on `EPERM` or `EACCES`, otherwise `.available`. `ubiquityIdentityToken` and a folder merely existing aren't used. Confirmed by U5, with its fallback below.

**First prompt:** the first access happens only from a user action: saving or sharing a Project with an image, opening a Shared Project with a pending image, or opening the Project Editor on one. A launch or a key-value change never prompts. The injected `UserDefaults` key `SharedProjectImages.folderWasReached` turns on background passes after one success. Shell commands in a Pane may already have made macOS ask, since macOS may attribute them to Batty; nothing relies on that.

### Steps

One commit per step, messages prefixed `#0551`. Run `./build.sh` and `./build.sh unit` after each. New Swift goes in the BattyKit package.

#### Step 1: the flag

- **New `BattyKit/Sources/BattyXPCCore/FeatureFlags.swift`:** `struct FeatureFlags: Sendable, Equatable { var sharedProjectImages: Bool }`, with `resolved(bundleIdentifier:environment:)` through `ServiceNames.Variant`; nil or unknown fails closed and logs. **Deviation from `docs/feature-flags.md`:** no CLI `current`, because the CLI doesn't read this flag; also no UI-test override, because a UI-test build has no entitlement and so already has no transport.
- **`Runtime/AppStateStore.swift`:** `featureFlags:` init parameter (default `.resolved()`), stored as `store.featureFlags`.
- **`docs/feature-flags.md`:** say one flag exists; list the gate sites as they are added (`defaultSharedImageTransport`, `ProjectStore.sharedImagesEnabled`).

#### Step 2: the record and the merge (pure)

- **`Model/Project.swift`:** `public enum ProjectSharedImage: Codable, Sendable, Hashable { case named(digest: String, name: String); case removed }`. `Project.sharedImage`, key `sharedImage`, `encodeIfPresent`, decoded with `try?` so a bad value costs only this field. Validate the digest with `isDigest` on decode.
- **`Model/ProjectSync.swift`:**
  - `ProjectSyncBackground` gains `image: ProjectSyncImage` (`.unspecified`, `.named`, `.removed`). Keys `imageDigest`, `imageName`, `imageRemoved`, in the same object as the settings. Decoded with `try?`: a bad digest or wrong type reads as unspecified; the name goes through the sanitizer. `settings` still always holds a nil path.
  - `syncRecord(home:carriesSharedImage: Bool = false)` maps only from `sharedImage`. With `false`, or nil, the bytes are as today.
  - `Project(syncRecord:home:honorsSharedImages:)`: named becomes `sharedImage`, with a nil path.
  - `replacingDefinition`, when honoring: **named** with the local path's digest equal keeps the path; with a different digest keeps the old path and sets `.named` (pending, and the earlier image still shows); **removed** clears both; **unspecified** keeps both. Not honoring: as today, `sharedImage` untouched.
  - Merge rule 4: a Project that becomes local gets `sharedImage` nil.
- **`Settings/TerminalBackgroundImageImporter.swift`:** `nonisolated static func sanitizedImageName(_:) -> String`, which `fileName(for:)` then shares, and `nonisolated static func storeVerified(bytes: Data, digest: String, name: String, into directory: URL) -> BackgroundImageState`: hash compare, temp file in `directory`, `isWithinPixelLimit` on the temp, then move to `<digest>/<name>.png`; `.rejected` leaves nothing behind.

#### Step 3: the transport and the coordinator

- **New `Settings/SharedImageTransport.swift`:**
  - `protocol SharedImageTransport: Sendable` with async `availability()`, `state(digest:)` (`.absent`, `.notDownloaded`, `.local`), `requestDownload(digest:)`, `read(digest:)`, `write(from: URL, digest:)`, `uploadProblem(digest:)`, `isUploaded(digest:)`, `listDigests()` and `delete(digest:)`.
  - `ICloudDriveImageFolder`: the production type. It takes its root URL and runs each call on its own serial `DispatchQueue` through a continuation, so a blocking read can't hold a cooperative thread or the main actor. `state` uses `lstat` for `SF_DATALESS` and `ubiquitousItemDownloadingStatus`; either saying evicted means `.notDownloaded`. `read` refuses a file over 100 MB and returns `Data`, after `state` says `.local`. `write` stages outside the folder on the same volume and moves it in.
  - It validates every digest with `isDigest` before building a path.
- **New `Model/SharedProjectImages.swift`:** `@MainActor @Observable final class SharedProjectImages`.
  - `init(store:projectBackgrounds:transport:clock:defaults:…)`, with `SchedulingClock` and injected `UserDefaults`. `private(set) var message: String?` and `sharedStatus`, written only on change.
  - `@discardableResult func reconcile(userInitiated: Bool) -> Task<Void, Never>`, for tests to await. **The work list comes only from `store.projects` where `isShared` and `sharedImage` is `.named`,** which is the code form of the scope rule. A pass with no such Project touches no transport call at all.
  - **Path digest matches (upload):** `state`; if `.absent`, `inspect` and pixel check the local copy off the main actor, then `write`. If `.local`, read and compare; a mismatch is replaced (repairs a damaged shared copy). If `.notDownloaded`, nothing, since it can't be read without a download and the name is its digest.
  - **Differs (download):** first, an intact local copy in `ProjectBackgrounds/<digest>/` is used with no transport call. Otherwise `.local`: read, `storeVerified`, then `store.setResolvedSharedImage`. `.notDownloaded`: `requestDownload` once per process, stay waiting; if it throws, record it and read anyway off the main actor. `.absent`: stay waiting.
  - **Triggers:** `store.onSharedImagesChanged` (after an `upsert`, `setShared` or merge commit), a Project open, a Project Editor open, and `NSApplication.didBecomeActiveNotification`. While anything waits, a loop on the injected clock: 30 s doubling to a 15-minute cap, ending when nothing waits. Passes that aren't user-initiated do nothing until `folderWasReached`.
  - **Arrival:** apply to the store, to Sessions (see "Open Sessions"), to an open Project Editor, then post `.battyBackgroundImagesDidChange`. These are writes after an `await`, not from `body` or layout, per the observation rules.
  - **Messages:** iCloud Drive off, not allowed, iCloud full, not uploaded after an hour, wrong file, too large. Wording, for the implementer to keep plain: "Turn on iCloud Drive to send this Project's image to your other Macs. The rest of the Project still syncs." and "Allow Batty to use iCloud Drive in System Settings > Privacy & Security > Files and Folders. The rest of the Project still syncs."
- **New `Model/SharedImageSweep.swift`:** a pure `SharedImageSweep.decide(listed:named:ledger:now:) -> (delete: [String], ledger: [String: Date])`, with the ledger file read and written beside `projects.json`.

#### Step 4: the store and the wiring

- **`Model/ProjectStore.swift`:**
  - `init(..., sharedImagesEnabled: Bool = false)`. With `false`, the record, merge and file are exactly as today.
  - `upsert`, for a Shared Project when enabled, sets `project.sharedImage = ProjectSharedImage.forSave(draft:stored:)` **before** `publish`:

  - New `setResolvedSharedImage(id:digest:path:)`: device state as `recordApproval` is, with no stamp and no publish. It does nothing unless the Project's `sharedImage` still names that digest, since the user may have picked another during the download.
  - `sharedImageDigestsInFile()`, `onSharedImagesChanged`, and pass `honorsSharedImages` and `carriesSharedImage`.
- **`Model/ProjectSync.swift` and `Model/ICloudKeyValueProjectSyncBackend.swift`:** `snapshotSkippedEntries: Bool` on the protocol, set by `snapshot()`. False on `LocalOnlyProjectSyncBackend`, with a test seam.

- **`Runtime/AppStateStore.swift`:** `static func defaultSharedImageTransport(isTestProcess:hasEntitlement:isEnabled:make:)` and `sharedImageTransportFactory`, as for the backend. `projectStore` passes `sharedImagesEnabled`. A lazy `sharedProjectImages: SharedProjectImages?`, nil without a transport. `openProject` calls `reconcile(userInitiated: true)` after the Session exists and **doesn't wait for it**.
- **`Runtime/AppStateStore+Quit.swift`:** `projectEditorDidClose` also starts the sweep.

## Root cause

Feature work. A Shared Project synced its background's fit, position and opacities but never its image: `ProjectSyncBackground` strips the path, and nothing else carried the picture, so each Mac had to choose the file itself. Batty has no ubiquity container, so there was no synced folder to use, and image bytes can't fit the key-value store.

## Fix

Follows the Plan: an iCloud Drive folder as transport only, behind `sharedProjectImages` (on in Beta, off in Prod), with the transport also gated on the entitlement and a non-test process. `SharedProjectImages` builds its work list only from Shared Projects whose `sharedImage` names an image, which is the code form of the scope rule. `imagePath` always names a verified local copy. The record gains `imageDigest`, `imageName` and `imageRemoved`, and `ProjectSyncMerge.apply` stays pure. `NSFileProviderDomainUsageDescription` is in `Configuration/Info.plist`, on the orchestrator's decision. No change to `scripts/`, entitlements, profiles or `Configuration/Build.xcconfig`.

**Departures from the Plan:**

- **`FeatureFlags.resolved` has only `bundleIdentifier:`.** The Plan's `environment:` parameter exists in the recipe for a UI-test override, which the Plan rules out, so it would have been unused.
- **Commits.** Steps 2 to 5 share one code commit, because the store, the coordinator and the UI were written against each other. The branch squashes anyway.
- **Test suites.** The new `ProjectStoreTests` cases are in a new `ProjectStoreSharedImageTests`, because the file's last struct is another suite. The `storeVerified` cases are in `TerminalBackgroundStoreVerifiedTests`, in the same file as the importer tests.

**Plan gaps, and the choice made:**

- **`Project(syncRecord:)` with `.removed`** sets `sharedImage` to `.removed`, so a later Save on this Mac keeps publishing the removal.
- **A record with no `background` (Follow), when honoring,** sets `sharedImage` to nil, matching the action table.
- **`declineSharedImage()` also clears the draft's path.** Otherwise a Project still showing its earlier image would publish that image on Save instead of the removal the table requires.
- **`setShared(true)` on a Project already Shared with a `sharedImage`** keeps that value, so a pending image survives.

- **The Sidebar's triangle:** no code was needed, as the Plan's "Pending state" says.
- **`SharedImageUploadProblem`** has `.iCloudFull` and `.other`; only the first has its own message. `.other` counts toward "not uploaded after an hour".

**Round 2, after review:**

- **A digest can ask for a download again.** `applyArrival` clears it from `requestedDownloads` and `failedDownloads`. Each pass also drops any digest no Project is waiting for, which the review didn't ask for: an image dropped before it arrived had the same bug.
- **The caption and Don't Use This Image are gated.** `ProjectEditorViewModel` takes `sharedImagesAvailable: Bool` (default false), which the window controller sets from `store.sharedProjectImages != nil`. It's a stored value rather than a closure, because the transport can't appear later and the caption is read from `body`.

- **The optional hash re-read improvement wasn't made.** Remembering a verified digest would stop a shared copy damaged later from being repaired until relaunch, and the Plan relies on that repair. So it isn't trivially safe. Each pass still reads and hashes, off the main actor.

## What exists today

The backend's limits are 1,000,000 bytes per value and in total, so image bytes can't go through it.
- **The image is device state by design.** `ProjectSyncBackground` strips the path, and `replacingDefinition` keeps this Mac's own path through a merge.
- **Copies live in `ProjectBackgroundLibrary`**, in `ProjectBackgrounds/` beside `projects.json`, at `<directory>/<64 hex digest>/<name>.png`. `checked(_:)` treats a stored path as untrusted and verifies shape, digest and pixel size. All of that stays for files that arrive from iCloud.

## Storage: the plan settles this

| | **iCloud Drive folder (orchestrator's default)** | **Ubiquity container** |
|---|---|---|
| Location | A Batty folder in `~/Library/Mobile Documents/com~apple~CloudDocs/`, which exists on this Mac | The app's own container, from `url(forUbiquityContainerIdentifier:)` |
| Signing | Assumed none, because the app is unsandboxed. **Unverified; the plan must check it** | iCloud Documents entitlement and new profiles (below) |
| Needs | iCloud Drive turned on | iCloud account |
| Visible to the user | Yes, so it can be moved, renamed or edited | Hidden by default |
| Eviction | Files can be evicted, so a read may block or need a download first | Also evictable, but with the supported download and metadata APIs |
| Status APIs | Whether `ubiquitousItemDownloadingStatus`, `startDownloadingUbiquitousItem` and similar work without an entitlement is unknown | Supported |

What the container would take, from `AGENTS.md` "Developer ID certificate" and `docs/code-signing.md`:

- **Only the user can do the portal steps.** No agent may touch the portal. The user would create the container, assign it to both App IDs and create a new Developer ID profile for each, listing only the certificate with serial `5DAD92F9908AF699`. An agent then commits them to `Configuration/Profiles/` and adds the entitlement to `Batty/Batty.entitlements`, with Manual signing as today. `scripts/verify-profile.sh` asserts only the key-value entitlement and would need extending, and `scripts/` is a restricted area.
- **New profiles are needed.** The committed profiles carry `icloud-services: *`, but their `icloud-container-identifiers` and `ubiquity-container-identifiers` are empty arrays, so they name no container. The line in `docs/code-signing.md` saying "the current ones already allow them" reads wider than that, so the plan shouldn't rely on it.
- **There is a risk to shipped builds to answer first.** `docs/code-signing.md` says changing a capability on an App ID invalidates its profiles, and that the embedded profile is evaluated at every launch. Whether that can affect already installed Batty builds is not known. It has to be answered before anyone changes the App IDs.

## Findings the plan must allow for

Checked against the code on `main`. Items 1 to 4 correct or narrow the first report of this issue.

1. **The path stripping stays.** An absolute path still must not sync. What changes is that the record gains a digest beside the stripped path. `recordCarriesFitPositionAndOpacitiesButNoPath` and `recordWithAStrayImagePathDropsIt` should keep passing. `insertedRemoteProjectKeepsOpacityAndHasNoImage` still holds for a record with no digest, and `aBackgroundAddsLittleToARecord` bounds the growth at 300 bytes.
2. **"The existing no-image state" comes with a warning.** A `.missing` image at open sets `projectBackgroundImageProblem`, which draws an orange triangle on the Sidebar row, and the editor warns too. That is right for a lost file and wrong for one still downloading. `BackgroundImageState` has no pending case, so the plan decides whether to add one.
3. **Opening is one-shot and on the main actor.** `openProject` calls `checked(_:)` synchronously, and `inspect` reads and hashes the whole file there. So a path inside an evictable folder would block the main actor on the network. Nothing re-seeds an open Session when a file later arrives.
4. **`ubiquityIdentityToken` can't detect iCloud Drive under the default.** The backend's own comment says it can stay nil for an app with no ubiquity container, so it can't drive the "iCloud Drive is off" message. A folder that exists isn't proof either. The plan needs another check, and has to say how it was confirmed.
5. **A digest doesn't locate a file.** The file inside the digest folder is named from the user's source, and `TerminalBackgroundControls` shows that name. Either the record also carries the name, which is then untrusted input (path separators, `..`, and the quote and backslash that `fileName(for:)` drops because the path goes into a quoted config value), or the shared layout fixes the name and the other Mac shows something else.
6. **A self-matching digest proves little.** `inspect` compares a file to its own folder's name. In a folder the user can write to, the check that matters is the file against the digest in the record. A corrupt file named for its own digest already passes (#0540 Gotchas), and such a file makes `ghostty_surface_new` return `NULL`. The record is the only thing tying the file to what the importer wrote, and it comes from the user's own account. The plan should say whether that's enough, or whether an arriving file needs more.
7. **`adopt` doesn't check pixel size, and runs on the caller's actor.** `imageState(ofPath:)` does the size check, and an image wider than 16384 px aborts the process. An arriving file has to pass both off the main actor.
8. **The picker's existing error paths don't fit.** `publish` runs before the local commit, and a refusal makes Save fail or leaves the checkbox unset. An image problem probably shouldn't cost the user the rest of the Project.
9. **Routine builds and tests have no backend.** `./build.sh`, unit tests and the VM use `Batty-local.entitlements`, and a test process builds no backend even when signed. The new file code has to follow the same gate, so that no routine build or test reads or writes the user's real iCloud Drive.

**A suggested shape, for the plan to accept or reject:** treat the iCloud folder as transport only. An image's `imagePath` keeps naming a local copy in `ProjectBackgrounds/`, written only after the shared file has been downloaded and verified off the main actor. libghostty then never gets a path that isn't materialized, `checked(_:)` keeps its directory rule, opening never touches the network, and older Batty's `reclaim` keeps seeing the local path.

## Requirements

- **Digest, not path.** The synced record carries the image's digest, never an absolute path.
- **Fetch and verify.** A Mac that lacks the file downloads it, verifies it against the record's digest and then uses it. A digest from the record is validated as 64 lowercase hex before it builds any path.
- **Never fail on absence.** A missing or still-downloading image opens the Project with no picture rather than failing. libghostty is never handed a path that isn't materialized, and no blocking read sits on the main actor.
- **Say when iCloud Drive is off.** The user gets a clear message, and the rest of the Project still syncs. iCloud being full deserves the same thought, since a plain file copy may not report it.
- **Cleanup must not delete what another Mac needs.** See below.
- **Older Batty is handled.** See below.
- **Keep the merge pure.** `ProjectSyncMerge.apply` does no file work. Downloading happens outside it.

### Cleanup

Today `reclaim` runs when the Project Editor closes, keeps what this process and `projects.json` name, and goes by the digest folder's date. It covers only `ProjectBackgrounds/`.

- Removing a local copy is safe for other Macs when the shared copy remains. Removing a shared copy isn't, and this Mac's list can't say what another Mac needs.
- The key-value snapshot does list every shared Project's digest on the account, so it is a candidate keep-set, used only while `snapshotIsAuthoritative`, plus a grace period. Folder dates in iCloud Drive may not behave like local ones, so `refreshDate` and the one-day rule can't simply be reused.
- A digest named by a record but not yet downloaded has no `imagePath`, so `imagePathsInFile()` and the keep-set would miss it.
- A local Project's image is never uploaded. Decide what happens to the shared copy on unshare (`withdraw`) and on delete (`tombstone`).

### Each variant's folder

Decide per-variant folders or one shared digest-named folder. Prod and Beta have separate key-value stores, so a shared folder's keep-set can't see the other variant's records. That favours per-variant folders unless the plan finds a reason otherwise.

### Older Batty

Measured from the sources. `v1.3.4`'s `ProjectSyncRecord` has no `background` at all. `release/1.3` has `ProjectSyncBackground`, whose decoder ignores unknown keys and whose encoder writes only the known ones.

- **A 1.3.4 Mac that edits the Project** publishes a record with no background, which reads as Follow and clears the background, including this Mac's path. #0544 decided on no code change for that, plus a line in the release notes.
- **A Mac without this issue that edits the Project** writes the background back with no digest. On a newer Mac that looks like "Custom, no image", so absent can't safely mean "the image was removed". Today a remote "Custom, no image" keeps this Mac's image (#0540 Gotchas). An explicit removal needs its own encoding if removal should sync at all.
- **The knock-on effect:** once a record stops naming a digest, the local copy becomes reclaimable after a day, and a shared-folder sweep would see no record naming it either.
- **Older versions never touch the shared folder,** and an older version's `reclaim` keeps a local copy `imagePath` names.

The warning about older versions is, so far, only a drafted line in [#0544](0544.md) for the 1.3.5 notes. `website/changelog.html` stops at 1.3.4. The release that ships this issue needs its own line.

### Upgrade

Shared Projects today can have a different image on each Mac, chosen by hand, and none has a digest. Decide whether one gets published without an edit. Publishing stamps `modifiedAt`, and the last writer would replace the other Mac's image. The default that loses nothing is that a digest appears only when the user next chooses an image or saves that Project, but the plan should confirm it.
