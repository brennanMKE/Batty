# 0446 — `LaunchWindowGuard` has no end-to-end test: every UI-suite launch passes `-ApplePersistenceIgnoreState YES`, so the guard never fires in a VM run and removing it would go unnoticed

| | |

| **Status** | open |
| **Module** | Testing / Window |
| **Platform** | macOS |
| **First seen** | 2026-10-09 |

## Description

#0444 fixed the "menu bar but no window" launch with a product guard, `LaunchWindowGuard` (`BattyKit/Sources/BattyKit/Util/LaunchWindowGuard.swift` on `issue/0444`): `BattyAppDelegate.applicationDidFinishLaunching` calls `installAtFirstQuiescence`, which adds a one-shot `beforeWaiting` observer to the main run loop; when it fires, `openContentWindowIfMissing(store:)` checks `AppStateStore.launchNeedsContentWindow` and, if no content window exists, performs the "New Window" menu item. In the same change the UI harness started launching the app with `-ApplePersistenceIgnoreState YES` on every launch (`BattyUITestHarness.stateIsolationArguments`, applied in both `launchBatty()` overloads).

The consequence is that nothing automated proves the guard works end to end, and nothing would fail if it were deleted:

- **The UI suite never exercises it.** The poisoned state the guard exists for needs a launch that outlives AppKit's deferred `NSPersistentUIManager flushAllChanges` (about 15 s after launch, per #0444's root cause), followed by a relaunch that reads the record back. With the isolation flag on every launch, AppKit never reads the record, so the trap never arms. In the full VM run `20261009-144846-86583` on `issue/0444` @ `6b4c1c86` (76 tests, 2 failures, both the #0445 `WindowRegistrationRaceTests` test bug), `guest-state/app-info.log` contains **zero** `LaunchWindowGuard` "launch produced no content window" lines. A regression of the guard (observer never installed, wrong menu title, `launchNeedsContentWindow` returning the wrong answer, the `SwiftUI.PresentedWindowContent` prefix check misfiring) would leave that run green.
- **Unit tests cover only the decision.** `BattyKit/Tests/BattyKitTests/LaunchWindowGuardTests.swift` calls `openContentWindowIfMissing` with a synthetic `NSMenu`, a synthetic `[NSWindow]` list, and a store it registers windows into by hand. It does not exercise `installAtFirstQuiescence` (that the observer is installed, fires once, fires after SwiftUI's own default window would have appeared), nor the real main menu that `BattyCommands` builds, nor the `openWindow(value:)` path the real "New Window" item drives.
- **The only end-to-end evidence is a manual scratch run.** Branch `scratch/0444-noflag` (`99e00846`, one commit on top of `issue/0444`, "SCRATCH (not for merge)") sets `stateIsolationArguments` to `[]`; its run `20261009-144308-84494` (`NonTerminalPaneCloseTests` + `SessionCwdRenameTests` + `SettingsTests`, 5 tests, 0 failures) logged exactly 3 guard firings, on the three `SettingsTests` launches that follow the long-lived cwd launch (pids 5189, 5241, 5294). That is the right shape, but it is a throwaway branch and a hand-run probe, not something the suite repeats.

The obvious test shape — relaunch without the flag after a launch that ran long enough for the flush — is barred by AGENTS.md ("Asynchronous tests (binding)"): no test may make itself pass by waiting out a duration, and the ~15 s flush exposes no completion signal to await. So the test needs a deterministic way to get the persistent-UI record written, plus a harness opt-out of the isolation flag for that one test only.

## Steps to reproduce

Only inside the Tart VM, never on a host Mac (AGENTS.md, #0409).

1. On a checkout of `issue/0444` (or `main` once it lands), delete the `LaunchWindowGuard.installAtFirstQuiescence { … }` call from `BattyAppDelegate.applicationDidFinishLaunching` in `Batty/BattyApp.swift`.
2. `./build.sh unit` — `LaunchWindowGuardTests` still pass (they never touch the install site).
3. `./build.sh ui` — the full suite passes exactly as it did with the guard present; no test notices.

## Expected behavior

A UI test in `BattyUITests` that fails when the guard is removed (step 1 above) and passes with it present, without waiting out AppKit's flush interval. Concretely, the test must make the app reach the state #0444 documented (`hasPersistentStateToRestore=1` on relaunch, no window restored) deterministically, relaunch without `-ApplePersistenceIgnoreState YES`, and assert that a content window appears within the harness's existing `waitForExistence` bound.

## Actual behavior

The suite passes with or without the guard. The guard's only end-to-end verification is the manual scratch run above.

## Notes

Candidate mechanisms for seeding the state without a duration wait, for the implementer to evaluate (not conclusions):

- **App-side signal that the record has been written.** A UI-test-mode-only hook (gated the way `QuitConfirmation.isInUITestMode` and `UITestDriver` already gate on `BATTY_UI_TEST_MODE` / `BATTY_UI_TEST_SCRIPT`) that observes when AppKit's persistent-UI flush has run and writes a sentinel file the test awaits with `waitForFile(at:timeout:)`. The harness already has the sentinel pattern (`sentinelPath(named:)`, `waitForDriverErrors`). The open question is what to observe: #0444's Gotchas record that where AppKit stores the record is unverified (it goes through the `com.apple.appkit.restoration_storage` XPC service, not `~/Library/Saved Application State`), so a filesystem watch may not be available; a log-stream watch or an AppKit notification/hook would need to be found.
- **Injectable flush trigger.** If AppKit exposes a way to force the persistent-UI write early (an `NSPersistentUIManager`/`NSApplication` private or semi-public entry point, or a `UITestIntent` that invokes it), a test-mode intent could trigger it on demand and the test would wait only for the intent's completion sentinel, not for a timer. Anything private needs to be gated to test mode and documented as such.
- **Seed the state directly.** If the record's location and format can be established, the test (or a test-mode intent) could write a poisoned record before the relaunch, which removes the long-lived first launch entirely. Blocked on the same unverified-storage question.
- **Harness opt-out.** Whichever mechanism is chosen, `BattyUITestHarness` needs a way for one test to launch without `stateIsolationArguments` (a parameter on `launchBatty`, or a separate `launchBattyWithoutStateIsolation`), with the default unchanged so the rest of the suite keeps its isolation. The opt-out test must leave the guest clean for later launches, or run last, since a poisoned record is exactly what #0444 showed cascades.

What not to do: a `pause(15)` / `RunLoop.run(until:)` wait for the flush, or a test that asserts on elapsed time. AGENTS.md bars both; #0423 is the record of what that costs.

Run artifacts referenced above are gitignored and currently live under the agent worktrees (`.claude/worktrees/agent-a23f5c9c7f4543e4c/build/ui-tests/20261009-144846-86583/`, `.claude/worktrees/scratch-0444-noflag/build/ui-tests/20261009-144308-84494/`); copy the relevant `guest-state/app-info.log` lines into `issues/0446/` when work starts, since the worktrees are transient.

## Acceptance criterion

A `BattyUITests` test, run in the Tart VM through `tools/run-ui-tests-vm.sh`, that fails when `LaunchWindowGuard.installAtFirstQuiescence` is not called from `BattyAppDelegate` and passes when it is, using no duration-based waits. The full suite still passes with the test added, and `guest-state/app-info.log` for the run shows at least one `LaunchWindowGuard` "launch produced no content window" line attributable to that test.
