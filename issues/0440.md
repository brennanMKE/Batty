## Description

`ProcessGitStatusScannerTests.registryDrainReapsAStubbornProcessWithNoWaitForPendingTeardownCall` is meant to prove that `PendingTeardownReapRegistry.drainSynchronously()` can reap a stubborn child that the scanner scheduled, with no `waitForPendingTeardownSynchronously()` call (#0425's quit-path gap). It doesn't prove that. The scanner is built with the default, always-open `OpenTeardownReapGate`, so the scanner's own `Task.detached` reap runs at the same time as the drain. With a 0.2 s bound, that reap sends its own SIGKILL. When the drain's SIGKILL is removed, the drain's post-kill poll still sees the child exit, because the detached task killed it. The test passes either way. Which reaper wins depends on real-time scheduling, so the result also rests on a concurrent timer, which `AGENTS.md` "Asynchronous tests (binding)" forbids. The #0430 reviewer found this, and #0430's Gotchas records it as an unfixed follow-up.

The fix: inject a closed `TestTeardownReapGate`, so the scanner's detached reap parks before `reapAfterTerminate` and only the registry can kill the child. Then the test fails if the drain's SIGKILL is removed.

## Premise check (read-only, on `main` at `3e8e7236`)

- **The test uses the open gate.** `BattyKit/Tests/BattyKitTests/ProcessGitStatusScannerTests.swift:484` builds `ProcessGitStatusScanner(teardownWaitBound: 0.2, teardownReapRegistry: registry)` and passes no `reapGate:`. The init at `BattyKit/Sources/BattyKit/Runtime/GitStatusPaneContent.swift:268` defaults to `reapGate: TeardownReapGate = OpenTeardownReapGate()`.
- **Two reapers race.** `scheduleTeardownReap` (`GitStatusPaneContent.swift:366-390`) registers with the registry and then starts `Task.detached { await gate.waitUntilOpen(); Self.reapAfterTerminate(process, bound: bound, label: label); ... }`. With an open gate, the scanner's `reapAfterTerminate` (`:344-364`) polls for `bound`, sends `SIGKILL` (`:354`), and polls again. `PendingTeardownReapRegistry.drainSynchronously()` (`BattyKit/Sources/BattyKit/Runtime/PendingTeardownReapRegistry.swift`) runs its own copy of the same loop on the test's thread. With the drain's `kill(..., SIGKILL)` removed, it still polls another `min(bound, 0.5)` = 0.2 s. The detached task's SIGKILL lands inside that window, so `#expect(!process.isRunning)` passes. I didn't run the mutation, because this filing is read-only. The race is visible from the code as written, and it matches the #0430 reviewer's report.
- **The registry's SIGKILL is covered by its own tests.** `PendingTeardownReapRegistryTests.drainSynchronouslyKillsAndReapsARegisteredSigtermIgnoringProcess` registers a stubborn child directly, with no scanner and no competing reaper, and asserts that `drainSynchronously()` kills it. That test should already fail when the drain's SIGKILL is removed. The gap is narrower: the **scanner → registry integration** test can't tell the registry's reap from the scanner's. A test that only reports correctly when a race goes one way is still a gap, since a future change could break the registration path and still pass.
- **The closed-gate pattern already exists.** `terminateAndWaitBrieflyReturnsImmediatelyEvenWhenTheProcessIgnoresSIGTERM` (`ProcessGitStatusScannerTests.swift:385`) injects `TestTeardownReapGate()` with `defer { gate.open() }` registered before the child is spawned. `docs/async-test-seams.md` §3 documents the pattern: await `gate.waitForParkedWaiter()` before asserting, and open the gate in a `defer`.

## Expected behavior

The test fails if `drainSynchronously()` doesn't SIGKILL the child itself, or if `scheduleTeardownReap` stops registering with the injected registry. It passes only because the registry reaped the child.

## Direction

Rewrite `registryDrainReapsAStubbornProcessWithNoWaitForPendingTeardownCall` along these lines:

1. `let gate = TestTeardownReapGate()`, with `defer { gate.open() }` registered **before** `process.run()` (same as the sibling test at `:393-394`).
2. Build the scanner with `reapGate: gate` as well as `teardownReapRegistry: registry`.
3. Keep the existing `guard await ChildProcessReadiness.waitForData(on: readyPipe) else { ...; kill(...SIGKILL); process.waitUntilExit(); return }`.
4. After `scanner.terminateAndWaitBriefly()`, `guard await gate.waitForParkedWaiter() else { ... }`. The failure branch must release everything: SIGKILL and `waitUntilExit()` the child, then `gate.open()`. §4's rule says a bare `#expect` here would carry on as though a waiter had parked. A parked waiter proves the detached task hasn't reached `reapAfterTerminate`, so it can't have killed anything.
5. `#expect(process.isRunning)` as a sanity check, then `registry.drainSynchronously()`, then `#expect(!process.isRunning)` and `#expect(kill(pid, 0) != 0)`. §5 Q3 permits a single check here.
6. Open the gate and `await scanner.awaitPendingTeardownReapsForTesting()`, so the parked detached task finishes. It will find the child already gone. This way no task outlives the test.

Constraints (`AGENTS.md` "Asynchronous tests (binding)", `docs/async-test-seams.md` §3–§4):

- No `Task.sleep`, `Thread.sleep`, polling or elapsed-time checks in the test. `drainSynchronously()` blocks for up to its own bound, but that is production behaviour under test, not a wait in the test.
- Every readiness wait is a `guard`, and each failure branch releases the child and the gate.
- Production isn't changed. `reapGate:` is already an init parameter.

## Resolution notes

## Fix

- **The registry-drain test.** It injects a closed `TestTeardownReapGate`, guards on `waitForParkedWaiter`, drains, and asserts the child is gone with a single `kill(pid, 0)`. It then opens the gate and awaits the pending reaps.
- **Failure branches.** In both gated tests, a failure branch opens the gate and awaits `awaitPendingTeardownReapsForTesting()`, so no task outlives the test.
- **Fixture cleanup.** The stubborn-fixture `defer`s and the three overlapping `sleep 30` tests now use `ChildProcessFixture`. All assertions run before the fixture's `defer`, so the fixture's SIGKILL can't mask a failure to signal.
- **Termination checks.** `terminateIfRunningSignalsEveryOverlappingTrackedProcess` and `aCompletedScans…` now assert `terminationReason == .uncaughtSignal`. If the production code stops signalling, the tests fail instead of passing after `sleep 30` exits on its own.
