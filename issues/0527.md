# 0527 — Batty has no Markdown Viewer Pane for finding and reading Markdown files under a directory

| | |
|---|---|
| **Status** | open |
| **Module** | Pane / Theme |
| **Platform** | macOS |
| **First seen** | 2026-10-19 |

## Description

Add a new non-terminal Pane kind, **Markdown Viewer** (`markdown-viewer`). It is read-only. It roots itself at a directory: the working directory of the Pane it was split from, or an explicit `--path`. It finds every Markdown file under that directory off the main actor and offers a search field that filters the files by relative path. Up/Down/Return/Escape work in the field. The selected file renders as formatted Markdown, with colors taken from the active Theme. A Theme switch repaints the Pane live, the same way the Sidebar and Tab bar do.

User request (2026-10-19, verbatim): "Create a new issue to create a new custom view. This one will be a markdown viewer. It will take current working directory and support a search field to find any matching markdown files under that folder. Then once selected it renders that markdown file. It should work with our themes so the colors look great."

This is new feature work for `main` (the next minor version after 1.3), not a 1.3.x fix. It follows the pattern of the existing view Panes (Git Status #0304, Process Status #0305, LM Studio Dashboard #0313, System Metrics #0314, CLI #0315, menus #0331/#0453). The binding docs below apply to it in full.

**Read before implementing:** `docs/view-hierarchy.md`, `docs/pane-kinds.md` (esp. §2 and §3), `docs/pane-view-lifecycle.md`, `docs/terminal-pane-requirements.md`, `docs/swiftui-observation-rules.md`, `docs/themes.md`, `docs/design/git-status-view.md` §1 (directory resolution and "Change Directory…", which this kind copies), and `docs/async-test-seams.md`.

## Expected behavior

### 1. Pane kind and plumbing

- New case `PaneContentKind.markdownViewer = "markdown-viewer"` in `BattyKit/Sources/BattyXPCCore/PaneContentKind.swift`. Its `displayName` is `"Markdown Viewer"`. One string serves as the Codable `Pane.kind`, the CLI `--view` value and the topology payload `kind` (`docs/pane-kinds.md` §5).
- New `MarkdownViewerPaneContent: PaneContentLifecycle` conformer in `BattyKit/Sources/BattyKit/Runtime/`. It owns the root path, the discovered file list, the selection and the loaded document. It obeys the state machine and the teardown guarantees in `docs/pane-view-lifecycle.md` §3–§5. Hiding the Pane suspends the file watcher (§4 below). Teardown cancels any in-flight discovery or read.
- Adding the enum case breaks every exhaustive `switch` over `PaneContentKind`, and each needs an arm. As of this filing they are: `PaneRuntime.makeContent(for:)`, `SplitTree.makePane` (root resolution, like the `.gitStatus` branch), `SplitTree.inheritedSource(from:in:tabLookup:)` (a split from a Markdown Viewer inherits its root, like `gitStatusDirectory`), the `PaneView` kind switch plus a new `nonTerminalContent` branch, and the Projects switches in `ProjectTreeBuilder`, `SessionProjectCapture`, `ProjectDraft`, `ProjectEditorViewModel` and `ProjectEditorView`. Let the compiler find them, and don't add a `default:`.

### 2. Root directory

Resolution matches Git Status (`docs/design/git-status-view.md` §1). The root is resolved **once at creation** and then **frozen**. It does not follow the source terminal's later `cd`s:

1. An explicit CLI `--path` (resolved to an absolute path client-side).
2. Otherwise, the working directory `SplitTree.inheritedSource` resolves from the source Pane. This is the same directory a terminal split would inherit.
3. Otherwise, `$HOME`.

- **Change Directory…**: a toolbar button and an empty-state button open a directory-only `NSOpenPanel`. Picking a folder cancels the current discovery, clears the selection and rediscovers under the new root. This copies Git Status's retarget.
- **Root unavailable** (missing, not a directory, or unreadable): show an error state with the path, the reason, and Change Directory…. Never crash, and never fall back silently to another directory.
- The current root shows in the Pane's header as an abbreviated path (`~/…`), with the full path in the tooltip.

### 3. File discovery

- Recursive under the root. Matches regular files whose extension is `.md` or `.markdown`, case-insensitive.
- **Skipped**: every hidden entry (any dot-prefixed file or directory, which covers `.git`, `.build`, `.venv`, `.swiftpm`) and these directory names: `node_modules`, `build`, `DerivedData`, `Pods`, `Carthage`, `dist`, `target`, `vendor`. Package contents (`.app`, `.xcodeproj` and similar bundles) are skipped too. Symlinked directories are not followed, which avoids cycles and escaping the root. Put the skip list in one named constant so it can be tested.
- **Cap**: stop after **5,000** matching files, then show a non-blocking notice ("Showing the first 5,000 Markdown files — choose a narrower folder"). Rooting at `$HOME` or `/` must stay responsive.
- **Off the main actor**: discovery runs behind an injectable `nonisolated` protocol (e.g. `MarkdownFileDiscovering`), the same seam shape as `GitStatusScanning`. It returns a value the caller awaits, so the UI never blocks. It honors cancellation between directory entries. While it runs, the Pane shows a progress indicator, and the search field is usable as soon as discovery finishes. Results are relative paths sorted case-insensitively.
- **The list is not live in v1.** It is rebuilt on creation, on Change Directory…, and from a **Refresh** toolbar button. New or deleted files appear after Refresh.

### 4. Search field and selection

- A search field at the top of the Pane filters the discovered files by **relative path**. Reuse `FuzzyMatcher` (`BattyKit/Sources/BattyKit/Util/FuzzyMatcher.swift`). Score a candidate as the higher of its score against the file name and its score against the full relative path, so `readme` ranks `docs/README.md` well. Ties fall back to path order. An empty query lists every file. Put the filter in a pure function (like `OpenQuicklyFilter.apply`) so unit tests can call it.
- Keyboard handling copies `ThemeSelectorView` and `CommandPaletteView` (`.onKeyPress`): **Up/Down** move the highlighted result, clamped and not wrapping. **Return** opens the highlighted result. **Escape** clears a non-empty query, or on an empty query dismisses the results list and returns to the open document, if there is one. Clicking a result opens it.
- Layout must work in a narrow Pane. With no document open, the results list fills the Pane under the search field. With a document open, the document fills the Pane, and typing in or focusing the search field shows the results list as a dropdown under the field. The design pass (Open questions, Q1) settles the exact visual.
- **Focus.** A Markdown Viewer created from the menu, Command Palette or shortcut focuses its search field **from the event that creates it**. That write is event-origin per `docs/swiftui-observation-rules.md`, and #0526 is the recent precedent. It must not come from `onAppear` or geometry callbacks, and never from a `Task` hop. A Pane created by the CLI into a background Session doesn't take focus. The field must not swallow keys meant for a terminal Pane that has focus.
- The highlighted index and selection are model state written only from these events. Nothing writes observed state from `body`, `onChange` driven by layout or focus, or `onGeometryChange`.

### 5. Rendering

- Render with **Textual**'s `StructuredText`. Textual is already a BattyKit dependency (`gonzalezreal/textual` in `BattyKit/Package.swift`), and the Help window uses it today (`HelpSuccessPaneView`). It renders block structure: headings, lists, block quotes, fenced code with syntax highlighting, tables and thematic breaks. It also handles inline styles and text selection (`.textual.textSelection(.enabled)`). **No new package dependency is needed.** See Notes for the alternatives considered.
- `baseURL` is the selected file's directory, so relative links and images resolve against it.
- **Size limit:** a file larger than 2 MB, or one that isn't valid UTF-8, shows a file-error state with the reason, and **Open in Default App** (`NSWorkspace.open`) instead of rendering.
- The file is read off the main actor. Switching files cancels a read that is still in flight, so a slow read can't overwrite a newer selection.
- **Reload on disk change (v1).** Watch the **selected file only**. Use an FSEvents stream on its parent directory with file-level events, reusing the `GitStatusWatching`/`FSEventsGitStatusWatcher` seam shape, so atomic saves (write-temp-and-rename) are caught. Debounce, then reload, keeping the scroll position as best it can. This covers the main use: an agent in the next terminal Pane rewriting `PLAN.md`. If the file is deleted, show "This file was deleted" with the last-rendered content dimmed, or an empty state; the design picks one. The watcher stops when the Pane is hidden or suspended, and the file is re-read once when it's shown again (`docs/pane-view-lifecycle.md` §4).

### 6. Links and images (scope kept modest)

| Link target | v1 behavior |
|---|---|
| Relative or `file:` link to a `.md`/`.markdown` file **inside the root** | Opens in this viewer (selection change). No back/forward history in v1. |
| `http`/`https`/`mailto` | Opens in the default app through `NSWorkspace.open` (Textual uses SwiftUI's `openURL` environment, so override it). |
| Other local file (inside or outside the root), or `.md` outside the root | Opens in the default app through `NSWorkspace.open`. |
| In-document anchor (`#heading`) | No-op in v1. |
| **Local images** under the root (relative or `file:`) | Rendered through a custom `AttachmentLoader` that loads only `file:` URLs inside the root. |
| **Remote images** (`http(s)`) | **Not fetched.** They show as alt text. A file viewer must not make network requests just because a README was opened. Textual's stock `.image(relativeTo:)` loader would fetch remote images through `URLSession`, so don't use it. |

Out of scope for v1: editing, rendering HTML blocks, Mermaid/math, front-matter display (show it as plain text, or strip it; the design decides), search *within* a document, back/forward history, and file drops onto the Pane. `docs/pane-kinds.md` §3 records that `.onDrop` on a non-terminal Pane is a known hazard.

### 7. Theme mapping

Theme colors come from the active `.ghostty` theme through the environment's `ThemeChrome`. The existing view Panes already work this way (`SystemMetricsColors(palette:)`, `BattyTabChip`). `ChromePalette` (`BattyKit/Sources/BattyKit/Theme/ThemeChrome.swift`) has no ANSI colors today, and syntax highlighting needs them. Add a palette derived in the same `ThemeChrome.update(from:)` call, e.g. a `MarkdownPalette` built from `GhosttyThemeDefinition` (`background`, `foreground`, `cursorColor`, `selectionBackground`, `palette[0...15]`). Don't add a second, independent theme pipeline. Every slot is optional: `nil` (no theme selected) means the system adaptive look, the same as `ChromePalette`'s rule.

Proposed role mapping (the design pass may tune it):

| Markdown element | Theme role |
|---|---|
| Pane background | theme `background` (`windowBackground`), so the viewer reads as the same canvas as a terminal |
| Body text, list text | `foreground` (`chromeForeground`) |
| Headings | `foreground`, weighted and sized by level. H1/H2 get a `divider` rule beneath. |
| Links | `accent` |
| Emphasis/strong | `foreground` with italic/bold weight (no color change) |
| Inline code | `foreground` on a code fill (`background` shifted about 8% toward `foreground`, as `tabActiveFill` is derived), monospaced |
| Fenced code block | `Textual` `HighlighterTheme(foregroundColor: foreground, backgroundColor: code fill, tokenProperties: …)`. Tokens: keyword→ANSI 5 (magenta), string→ANSI 2 (green), number/boolean/constant→ANSI 3 (yellow), comment→ANSI 8 (bright black) or `chromeMutedForeground`, function/class-name→ANSI 4 (blue)/ANSI 6 (cyan), inserted→ANSI 2, deleted→ANSI 1 (red) |
| Block quote | `chromeMutedForeground` text, `accent` (or `divider`) left bar |
| Tables | `divider` borders, header row on `chromeBackground` |
| Thematic break | `divider` |
| List markers | `chromeMutedForeground` |
| Search field, results list, header | the existing chrome roles (`chromeBackground`, `chromeForeground`, `chromeMutedForeground`, `sidebarSelectionTint` for the highlighted row, `accent` for match emphasis if any) |

- **Legibility guard**: any ANSI-derived token color whose contrast against the code fill falls below a fixed threshold falls back to `foreground`. `RGBColor.contrast(against:)` already exists and is used by `ChromePalette.preferLegible`. Some themes carry ANSI colors that vanish against their own background.
- **Live update**: the `StructuredText.Style` and `HighlighterTheme` are computed from the environment palette in `body`. Never cache them in `@State` or the content model, so a Theme switch repaints an open document right away.

### 8. Entry points

These match the existing view Panes:

- **Pane menu → Open View** section, and the **Split Horizontally / Split Vertically** submenus in `BattyCommands.swift`, calling `createPane(kind: .markdownViewer, direction:)`. SF Symbol suggestion: `doc.richtext` or `text.document`.
- **`ShortcutAction`**: `splitHorizontalMarkdownViewer` / `splitVerticalMarkdownViewer`, with titles `"Split Horizontally (Markdown Viewer)"` / `"Split Vertically (Markdown Viewer)"`. They appear in the Command Palette (`CommandPaletteView`'s dispatch) and in Settings → Shortcuts. `defaultBinding` is non-optional, so a chord must be chosen. Verify it against `ShortcutAction.allCases`, `ShortcutsStore.reservedShortcuts` and `docs/shortcuts.md`, the way #0331 did (Open questions, Q3).
- **CLI**: `batty pane split --view markdown-viewer [--path <dir>]`, and `--unique`. `--path` is valid today only for `git-status` (`PaneCommand.swift` validation and the capabilities `requires` rule). Widen both to `git-status` and `markdown-viewer`, and carry the path in `viewOptions["path"]` (#0301's "one open-ended field" decision). Unknown `viewOptions` keys stay rejected per kind.
- **Projects**: a Markdown Viewer Pane is captured by Save Session as Project. When the Project opens, the viewer roots at the Project root, or a root-relative folder if the design adds one, the same way `repositoryPath` works for Git Status. **Compatibility note:** `ProjectPane.init(from:)` throws on an unknown `kind`, and 1.3.x's `ProjectStore` drops a Project it can't decode while preserving the file. So a shared (iCloud-synced, #0503) Project containing a Markdown Viewer is dropped from the list on a Mac still running 1.3.x. Decide whether that's acceptable (Q4).
- **Docs**: update `Concepts.md` (the Pane "Purpose" kind list and the #0315 exception's kind list), `docs/pane-kinds.md`, Help `03-panes.md` and `05-shortcuts.md`, `docs/ui-features.md`, and `.claude/skills/batty-cli/SKILL.md`. Every user-facing string uses `String(localized:)` (`docs/localization.md`).

### 9. Empty and error states

Each state has its own accessibility identifier:

| State | Identifier | Content |
|---|---|---|
| Discovering | `markdown-viewer.discovering` | progress indicator |
| No Markdown files under root | `markdown-viewer.no-files` | message + Change Directory… |
| Query matches nothing | `markdown-viewer.no-matches` | "No files match '…'" |
| Root unavailable | `markdown-viewer.root-unavailable` | path, reason, Change Directory… |
| Cap reached | `markdown-viewer.truncated-notice` | non-blocking notice |
| File too large / not UTF-8 / unreadable | `markdown-viewer.file-error` | reason + Open in Default App |
| File deleted while open | `markdown-viewer.file-deleted` | see §5 |

Other identifiers: `markdown-viewer.search-field`, `markdown-viewer.results`, `markdown-viewer.result.<relative-path>`, `markdown-viewer.document`, `markdown-viewer.document-path`, `markdown-viewer.refresh`, `markdown-viewer.change-directory`, `markdown-viewer.root-path`.

### 10. Binding constraints

- **`docs/swiftui-observation-rules.md`**: view construction is pure. Discovery, read and watcher results land on the content model through event-origin writes, never from `body` or layout callbacks. Never "fix" a mutate-during-update warning with a `Task` hop.
- **`docs/terminal-pane-requirements.md`**: run its §6 manual checklist on **terminal** Panes next to a Markdown Viewer after the `PaneView` change. Pointer, keyboard, IME and file drop into the terminal Pane must be unaffected. Pane chrome overlays keep `.allowsHitTesting(false)`.
- **`docs/pane-view-lifecycle.md`**: discovery and the watcher start at Pane creation (`setUp`), never from view code. They suspend on hide and unhide, and are released on close and on app quit.
- **Logging**: a file-scoped `nonisolated private let logger` per file. Paths are logged `.private`.

### 11. Tests

**Unit (`./build.sh unit`, `BattyKit/Tests/BattyKitTests/`).** Follow AGENTS.md "Asynchronous tests" and `docs/async-test-seams.md`: no sleeps, no polling, no timing assertions. Await the discovery handle or task, and drive the watcher through a test double that the test fires explicitly.

- **Discovery** (temp-directory fixtures): finds `.md`/`.MD`/`.markdown` at depth; ignores `.txt`/`.mdx`; skips hidden directories, every named skip directory and bundles; doesn't follow a symlinked directory; stops at the cap with the truncation flag set (inject a small cap); sorted output; relative paths; cancellation stops enumeration (proven by a signal from the discoverer, not by timing); unreadable or missing root gives the root-unavailable result.
- **Filtering**: empty query returns everything in order; subsequence match; file-name hit outranks a scattered path hit; case-insensitive; no-match returns empty.
- **Selection model**: Up/Down clamp at both ends; Return picks the highlighted row; Escape clears the query and then dismisses; highlight resets sensibly when the filtered list shrinks.
- **Theme mapping**: use a fixture `GhosttyThemeDefinition` with deliberately **non-default** colors (see memory note on vacuous "unchanged" fixtures). Each role maps to the expected slot. A `nil` theme yields all-`nil`/system. A low-contrast ANSI token falls back to `foreground`.
- **Link routing**: a pure classifier covering in-root `.md`, out-of-root `.md`, `http(s)`, `mailto`, other local files, anchors, and image URLs (local in-root loads, remote doesn't).
- **Lifecycle**: setUp starts discovery; hide stops the watcher and unhide restarts it and re-reads once; tearDown cancels discovery and the read. Use the recording-double pattern from `PaneContentLifecycleTests`/`GitStatusPaneContentTests`.
- **Plumbing**: `PaneContentKindTests` raw-value round trip; `SplitTreeNonTerminalCWDTests` for root inheritance in both directions (terminal → viewer, viewer → terminal split); CLI parsing accepts `--path` with `--view markdown-viewer` and still rejects it for other non-`git-status` kinds; Project capture and build arms.

**UI (Tart VM only, `./build.sh ui …`; never on the host).**

- `CLIViewPaneTests`: `batty pane split --view markdown-viewer --path <fixture dir>` opens the Pane. Typing filters. Return renders the document (assert `markdown-viewer.document` and a heading's text).
- `PaneMenuViewTests` (or the matching menu test): the Open View item exists and creates the Pane.
- `NonTerminalPaneCloseTests`: closing a Markdown Viewer Pane.
- `ViewGalleryTests`: add `markdown-viewer` to the gallery shots in light and dark, with a fixture document that has headings, a table, a block quote and fenced code in two languages. These screenshots are what the user signs off on visually.

## Open questions for the user

1. **Design-first gate.** The #0301 umbrella required each view Pane's visual design (`docs/design/<view>.md` + `.html` mockup) to be approved before implementation began. Should this issue follow that gate, with a short design doc and mockup covering layout, the list-vs-document arrangement and the theme mapping table first? Or is this request specific enough to waive it? *Recommendation:* a lightweight design pass, approved before code, because "colors look great" is a visual judgment.
2. **Feature flag.** AGENTS.md says unfinished features on `main` stay behind a flag until the release that ships them, and `docs/feature-flags.md` notes there are no flags today. If this lands complete in one squash, it ships in the next minor from `main` with no flag. That's how #0304/#0305/#0313/#0314 landed. If it's split into children, add a `markdownViewer` flag (on in Beta, off in Prod) per `docs/feature-flags.md`. *Recommendation:* no flag, as long as it lands as a single issue.
3. **Default shortcut.** `ShortcutAction.defaultBinding` is non-optional. Which chord? It must be free of every catalog, fixed and macOS-reserved combo. Cmd-M is Minimize. Cmd-Shift-M or a letter checked like #0331's `g`/`j`/`y`/`e` are candidates, to be verified by the implementer.
4. **Projects and older versions.** Is it acceptable that a shared Project containing a Markdown Viewer Pane is dropped from the Project list on a Mac still on 1.3.x? The alternative is to leave Markdown Viewer out of Project capture in v1.
5. **Code font.** Should inline and fenced code use the terminal font from Settings (so code looks like the neighboring terminal) or the system monospaced font? *Recommendation:* the system monospaced font for v1.

## Notes

- **Renderer options considered** (macOS 15.6+):
  1. **Textual (recommended).** Already linked by BattyKit and used by Help. It provides `StructuredText` for block-level Markdown, per-block `StructuredText.Style` protocols (heading, paragraph, block quote, code block, list item, table, table cell, thematic break), `InlineStyle` for code, emphasis, link, strong and strikethrough, and a `HighlighterTheme` with token types for fenced-code highlighting. It also has `imageAttachmentLoader` and `openURL` hooks. All of these are confirmed in the checked-out source under `BattyKit/.build/checkouts/textual/Sources/Textual/`. It adds no dependency.
  2. `AttributedString(markdown:)` / SwiftUI `Text`: parses inline styles only. Block structure (headings, lists, code blocks, tables) comes back as `presentationIntent` attributes that we would have to lay out by hand. That's a lot of work for a worse result.
  3. `WKWebView` + an HTML renderer: a new web-content process per Pane plus a JS or third-party Markdown-to-HTML step. It's heavyweight, and #0266 declined the browser category on exactly these grounds.
  4. A new third-party package (e.g. `swift-markdown-ui`): **needs user approval**, and isn't needed given option 1.
- **Scope history.** Project guidance had treated general content viewers, Markdown preview by name, as out of scope (#0266, #0301's scope note). The user asked for this Pane directly on 2026-10-19, so it's filed as asked. It sits next to Git Status as developer-workflow tooling tied to a terminal's directory.
- `PaneRuntime.makeContent(for:)`'s default for a kind needing call-site context resolves to `$HOME`, as `.gitStatus` does. The real root comes from `SplitTree.makePane`, which must run its `if let contentFactory` check first (see that function's doc comment and the trap #0304 hit).
- **Focus-precedent bugs to avoid:** #0526 (the editor field lost focus on reopen, fixed by focusing from the opening event) and #0229 (a `Task` hop that caused the click regression).
