# 0315 — Add batty CLI verbs to open and close non-terminal view Panes so agents can surface relevant views

| | |
|---|---|
| **Status** | open |
| **Module** | Pane / App |
| **Platform** | macOS |
| **First seen** | 2026-08-07 |

## Description

The `batty` CLI can split and close terminal panes over XPC, but once non-terminal view kinds exist (#0304 Git Status, #0305 Process Status, #0313 LM Studio dashboard, #0314 system metrics/thermals) it has no way to create a pane *of a given kind* or to establish that closing one works. In the user's words:

> "The CLI tool should be able to add and remove panes with the new views for Git Status, Process Status, Thermals and others so that agentic workflows can show the user what is relevant at the time."

The motivating scenario: an **agent** working in a Terminal Session decides that something visual would help the user right now — it opens a Git Status pane before a commit, a thermals pane during a long build, an LM Studio dashboard while dispatching local inference — and closes it when no longer relevant. The pane is a *presentation channel the agent controls*, which is exactly why the create/close verbs must report real results: an agent must be able to distinguish a real mutation from one that hit a stale id.

This is **not new IPC work**. It extends an existing, working mutation-verb pattern — #0282 (`pane split`) and #0283 (`pane close`), both resolved — to typed panes. Most of what is written below is open design questions, deliberately: the verb surface is a public contract for agents and should be settled with the user before implementation. (The #0301 design-first gate applies to the *views'* visual designs, not to this CLI verb — but the verb-shape and naming decisions below are their own one-way doors.)

Module note: the sibling view issues use `Pane / App`; this issue also touches the CLI, which has no module of its own — the CLI/XPC verb issues (#0282, #0283) file it under `App`, so `Pane / App` is the closest existing combination and no new module is invented.

## What already exists (verified against the tree, 2026-08-07)

- **`batty pane split` (#0282) and `batty pane close` (#0283) are resolved, and both go over XPC, not `batty://`** — the user's pinned decision, recorded in #0257's transport amendment (2026-07-26). `pane split` replies with the **real new pane id** (`PaneSplitReply.paneID`, `BattyKit/Sources/BattyXPCCore/PaneSplitPayload.swift`); `pane close` reports a real result, with a stale id exiting `4` (`XPCExitCode.requestFailed`, `BattyKit/Sources/BattyXPCCore/XPCExitCode.swift:25`). The two-way reply is the whole reason those verbs moved to XPC. The verbs are `paneSplit` / `paneClose` in `BattyKit/Sources/BattyXPCCore/XPCVerb.swift:27,37`.
- **`batty session new` stays on `batty://`** because it must be able to launch the app when it isn't running (#0257 transport amendment).
- **Target resolution is shared and settled (#0281):** explicit `--session/--pane/--tab` flag → else `BATTY_SESSION_ID`/`BATTY_PANE_ID`/`BATTY_TAB_ID` env injected at spawn → else the app's focused element. A typed-pane verb must follow the same chain, and the standing behavior rule is binding: mutating a background target must **not** steal focus or switch the active session (only the `focus` verbs do that).
- **`PaneSplitRequest` carries only `paneID` / `direction` / `command`** (`BattyKit/Sources/BattyXPCCore/PaneSplitPayload.swift:25-28`); `command` presumes a shell. There is no kind field anywhere on the wire.
- **The topology read verbs exist over XPC (#0274)** — `batty list` / `batty session info` — but `TopologyPanePayload` / `TopologyTabPayload` (`BattyKit/Sources/BattyXPCCore/TopologyPayload.swift:48,66`) have **no kind field**: an agent reading the layout today cannot tell (a future) non-terminal pane from a terminal pane. The #0301 umbrella already records kind-aware `list` as a required delta.
- **The close cascade is terminal-shaped.** `AppStateStore.closePane(id:)` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:418`) delegates to `WindowRuntime.closePane(id:refuseIfAppsLastPane:)` (`BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift:314`), which tears down bell state and calls `TerminalHostStore.releaseTerminalView(forTabID:)` per tab before removing the pane. A non-terminal pane has none of that state. (#0301 cites this cascade at `AppStateStore.swift:329`; the code has since moved to the lines given here.)

## Scope — open design questions, mostly deliberately undecided

**1. Creating a pane with a view kind — verb shape (open question).** Candidates:

- A new verb, e.g. `batty pane new --view <kind>`.
- Extending `pane split` with a `--view <kind>` flag — since a new pane in a split layout *is* a split, and `pane split` already exists, already resolves targets, and already returns the new pane id, extension may be the cheaper build. Against it: a Git Status pane is not conceptually "splitting a terminal", and #0282's grammar note pinned `pane` as the noun precisely because splitting subdivides a *region* — that argument cuts both ways here.
- Something else (e.g. a `view` noun).

Whatever the shape, it is XPC request/reply carrying the new pane id back, per the transport amendment — an agent chains on the id (`open → later close`). Extending `PaneSplitRequest` versus adding a new payload is part of the same decision; XPC payloads are a versioned wire format between the CLI and the app, so this should not collide with in-flight #0257-umbrella payload changes (e.g. the still-unfiled `tab close`). **Do not pick a shape in this file — settle it with the user before implementation.**

**2. Removing a typed pane — does `pane close` already suffice? (open question).** `batty pane close` targets by pane id, so the *verb shape* generalizes. Whether the *implementation* does depends entirely on where #0302 puts the terminal-host boundary: today's cascade assumes every pane's tabs are Terminal Sessions (see the close-cascade citation above). If #0302/#0303 give non-terminal panes their own teardown path behind a common close entry point, `pane close` may work unchanged; if not, it needs a kind-aware branch. This issue must establish which, not assume either. No new close verb is expected in any case.

**3. View-kind identifiers are a public contract (constraint, and a one-way door).** The CLI-visible names (`git-status`, `process-status`, `thermals`, `lm-studio`, …) become a stable API that agents and scripts hard-code — renaming later breaks callers silently. They should be settled alongside #0302's pane-kind model (where kind lives and what values it takes), not invented per-view as each ships. The Codable/persistence spelling (#0302 question 4), the topology-payload spelling, and the CLI spelling should be decided together, even if they are not the same string.

**4. Discoverability for agents (open question).** An agent cannot hard-code a list it does not know, and the set of kinds grows over time (#0313, #0314 arrived after #0304/#0305). Should there be a read verb — e.g. `batty pane views` — listing the available kinds, so an agent queries capability at runtime instead of failing on an unknown `--view`? This fits the existing read-verb precedent: topology reads landed over XPC in #0274. Related: the kind-aware `list` delta (#0301) is what lets an agent see which typed panes are *already open*, which question 5 depends on.

**5. Duplicate / idempotency behavior (open question).** Agents retry, and two agents can race. If an agent asks for a Git Status pane and one is already open for that repo, what happens — a second pane, success reporting the existing pane's id, or an error? Each is defensible; "focus the existing one" is *not* an option in its plain form, because the no-focus-steal rule binds mutations. The answer probably differs per kind (two Process Status panes watching different pids are sensible; two thermals panes are not) — which suggests the abstraction (#0302) may need to say whether a kind is singleton-per-scope. Decide before implementation; retry-driven pane accumulation is the failure mode.

**6. Error contract (must be specified, not discovered).** XPC can report real failures — that is why this surface exists. The agent-visible outcomes to define, against the existing exit-code vocabulary (`0`/`1`/`2`/`3`/`4`/`5`, `BattyXPCCore/XPCExitCode.swift`):

- Unknown view kind (likely CLI-side `1` if validated client-side against a queried list, or `4` from the app — decide which layer owns validation).
- Stale/unknown target pane id — `4`, matching #0282/#0283.
- Kind not available on this machine — e.g. LM Studio not installed/running/version-drifted; #0313's Gotchas require a degraded state in the *view*, but the *create verb* must still decide whether creating such a pane succeeds (showing the degraded state) or fails.
- Layout cannot accommodate another pane (if any such limit exists or is introduced).

#0283's lesson applies: distinct failures collapsing onto exit `4` are distinguished only by stderr, so the messages are part of the contract too.

## Dependencies

- **Blocked by #0302.** There is no "pane kind" to name until that abstraction exists — today a split-tree leaf *is* a `PaneRuntime` and every Tab *is* a Terminal Session (verified citations in #0302). The kind identifiers (question 3) and the close answer (question 2) both fall out of it.
- **Blocked by #0303.** A CLI-created view pane must obey the lifecycle contract — stop work when hidden, release resources when closed, **observably**. An agent that opens and closes panes repeatedly is exactly the workload that would expose a leak, and #0285 was an unbounded-memory-growth umbrella; this verb multiplies whatever discipline #0303 does or does not enforce.
- **Does not require all four views.** This is implementable against the first view kind that ships and extends as others land — it is gated on #0302 + #0303 plus *one* of #0304/#0305/#0313/#0314, not on all of them collectively.
