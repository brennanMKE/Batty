## Root cause

Starting state, not a defect. #0271 connected the three processes on the happy path. The experiment's accounting was blunt about what that leaves: "Connecting two processes is an afternoon" — the lifecycle work is the actual project, and roughly two thirds of the effort goes on states that only exist because a connection between three processes can fail in more ways than a one-shot URL can.

## Fix

**Distinct interruption/invalidation dispatch** via `BrokerConnectionLifecycle` (a pure enum→action mapping): interruption means the peer died but the connection object is reusable, so registration is re-sent over the *same* connection; invalidation means permanently dead, so the connection is discarded and rebuilt. `BrokerReconnectBudget` bounds automatic reconnects (default 5, reset on a confirmed `brokerPing` reply) so a permanently-gone broker produces a bounded burst rather than a spin loop.

**Orphan reaping and concurrent clients** via `AppXPCConnectionRegistry`, keyed by `ObjectIdentifier`; each connection's own invalidation handler is the only reap signal available, which is exactly what the issue specifies.

**Quit notification** via `PendingRequestRegistry`: `applicationWillTerminate` → `prepareForTermination()` synchronously replies to every in-flight `perform` with an `XPCTerminationSignal.appTerminating` sentinel before invalidating connections, so a mid-request CLI gets exit `5` rather than a raw drop mapped to `3`.

**The `SMAppService` repair path** via `BrokerRepairGuard`, a once-per-launch state machine driven exclusively by a *failed call* — never by `.status`, which can report `.enabled` while launchd has no such service.

**Broker-side hardening**: the broker applies the same interruption/invalidation distinction to its own accepted connections, clearing a stale app endpoint on invalidation only when the invalidating connection is the one that registered it.

**Signal identity (rounds 2–3).** Each broker connection carries a monotonic `UInt64` generation, captured by value into all four handler closures; `handleBrokerSignal` and `handleBrokerCallFailure` drop signals whose generation is not current.

## Review

Reviewed by `claude-opus-5`, **three rounds** — the maximum before the workflow parks a branch. Each round found a real defect, and the third converged.

**Round 1** found two defects sharing one root cause: broker-connection handlers captured only `[weak self]`, so `handleBrokerSignal` could not tell *which* connection fired and unconditionally mutated `isRegisteredWithBroker`, `brokerConnection`, and the budget. (A) `prepareForTermination()` called `invalidate()`, which fires the invalidation handler by contract → `.rebuildConnection` → a fresh `registerAppEndpoint` from a dying process, leaving the broker holding a dead endpoint. (B) `attemptRepairIfNeeded()` overwrote `brokerConnection` without invalidating it, leaving a resumed orphan whose later signals would clobber the new connection's state — and the budget was no backstop, since `reset()` fires on every confirmed ping.

**Round 2** confirmed A closed and all four closures gated, then found the *identity primitive itself* unsafe. `ObjectIdentifier` is unique only among objects **alive at the same time**, while the coordinator compared an id captured from a possibly-deallocated connection against one derived from a connection allocated afterwards. Two sites nil the connection and allocate a replacement with no intervening retain. The reviewer traced the full sequence — broker dies, interruption and invalidation both queue Tasks, the retry's error handler queues a third carrying the old id, the rebuild may place the new connection at the same address — ending in a stale failure being admitted, tearing down a healthy connection and **burning the once-per-launch repair guard**, so a genuine wedge later in that launch could no longer be repaired. Because the MainActor never yields in between, that is the *normal* ordering rather than a rare interleaving; only malloc's choice of address prevented it. The tell was already in the branch: the implementer had hit exactly this address reuse in their own unit test and fixed the test rather than the design.

**Round 3** approved the substitution to a monotonic `UInt64` generation counter, verifying the increment happens exactly once per connection (`grep` confirming a single site), that all four closures capture an immutable `let` copy rather than the mutable property, that no site still compares the old primitive (zero repo-wide hits), and that `.retryOverExistingConnection` correctly reuses the same generation since the connection is unchanged. The residual window is not merely improbable but impossible: generations strictly increase, so a stale signal's generation is strictly less than current, and overflow would trap rather than wrap.

## Gotchas

- **The live fault-injection matrix has never been run.** Everything below is unverified at runtime. In rough priority order:
  1. **Every failure path producing *visible* error output** — the SIGTRAP-class check. The `@Sendable` audit is static, and its failure mode is a silent `EXC_BREAKPOINT` *inside the handler that would have logged it*, so a wrong annotation produces total silence rather than a stack trace. No handler closure on this branch has been observed firing in a real process. **Check this first.**
  2. **Quit the app with a CLI attached → exit `5`, not `3`.** `prepareForTermination` replies to pending requests and then invalidates those same connections microseconds before the process exits; whether the sentinel actually arrives depends on `NSXPCConnection.invalidate()` not discarding an already-enqueued reply. Nothing proves it. This path was rewritten in every round, so it carries the most residual risk.
  3. **`launchctl bootout` → `.status` still lies → repair fires exactly once.** The guard is unit-tested; the wedged-`SMAppService` scenario motivating it is not reproduced.
  4. Broker killed under a running app → next CLI call succeeds after auto re-registration. Also unverified: the *premise* that a broker restart delivers `interruption` rather than `invalidation`.
  5. `kill -9` a connected CLI → the app reaps it.
  6. Two concurrent CLIs; ending one leaves the other undisturbed.
  7. `prepareForTermination()` completing before process exit — reasoned from its all-synchronous body, not observed.
  8. The three-process `log stream` handoff.
- **`NSXPCConnection.current()` returning the same instance `shouldAcceptNewConnection` saw** is assumed, never observed. All broker-side stale-endpoint clearing hinges on it. It **fails safe** — the only symptom is the absence of the `cleared stale app endpoint` line — so grep for that line specifically when running scenario 4.
- **The repair path can under-repair.** The `.enabled` filter reads `SMAppService.status` *after* a failed call, as a "did the user opt in?" check, so item 7's target case (status lies `.enabled` after `bootout`) still repairs. But if status reports `.notRegistered`/`.notFound` while the user *had* enrolled — which happens when the app bundle moves, since `SMAppService` state is keyed to bundle path — the app never self-repairs and the user must re-register from Settings. `.requiresApproval` produces only a log line, with no user-facing nudge.
- **`AppXPCCoordinator` constructs its own `BrokerAgentController`** while `SettingsView` holds a separate `@State` instance, so a repair-path `unregister()`/`register()` will not be reflected in the Settings UI until that view refreshes.
- **`PendingRequestRegistry` relies on an invariant, not a sweep:** every branch through `AppXPCService.perform` must call `resolve`. Today all of them do — including the malformed-request path, which replies before registering — so a `kill -9`'d CLI leaves nothing behind. A future verb that can bail without resolving turns this into a real leak.
- **`ObjectIdentifier` is safe as a registry *key* but not as a *signal identity*.** `AppXPCConnectionRegistry` keeps a strong reference, so a live key implies a live object; the coordinator's superseded connections are not retained at all, which is why they need the generation counter. Do not "unify" these two on the same primitive.
- **An idle connection with no in-flight call still yields exit `3` on app quit**, because there is no exported `CLIClientProtocol` to notify it. Deliberately out of scope per #0265's deferral of streaming and long-lived sessions.

## Scope (each item is an acceptance criterion)

1. **`interruptionHandler` vs `invalidationHandler` handled distinctly** on every connection. They demand *different* responses: interruption = peer died, connection object reusable, re-register; invalidation = permanently dead, rebuild. Conflating them yields either a reconnect loop or a permanently dead connection.
2. **Broker restart under a running app** is detected and the app re-registers its endpoint automatically.
3. **A CLI killed with `kill -9`** leaves an orphaned connection the app must reap via the connection's invalidation handler — there is no other signal.
4. **The app quitting mid-connection** tells attached CLIs before invalidating, so they don't learn only from the connection dropping.
5. **Concurrent clients:** two CLI connections at once work, and ending one must not disturb the other.
6. **No-delivery-confirmation discipline:** one-way calls return `Void` whether or not the peer received them; every "did it work?" answer comes from a subsequent round trip. Audit the #0270/#0271 code for any place that trusts a one-way return.
7. **The `SMAppService` repair path (RemoteControl #0016):** `.status` can report `.enabled` while launchd has no such service (observed directly after `launchctl bootout`), so the app cannot repair its registration by trusting status. Drive re-registration (unregister-then-register) from a **failed call**, guarded to run **once per launch**.
8. **A `@Sendable` audit of every Foundation-supplied handler closure** in the XPC code paths — `remoteObjectProxyWithErrorHandler`, `interruptionHandler`, `invalidationHandler`, and any other Foundation-typed callback. The trap, in full, because there is no compiler help: on Batty's `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` target these closures inherit main-actor isolation (Foundation types them as plain non-`Sendable` closures); Swift emits an isolation assertion at the closure's entry; XPC calls it on its own queue; the process dies with `EXC_BREAKPOINT / SIGTRAP`. **No compiler warning — strict concurrency is fully satisfied.** And the crash lands *inside the handler that would have logged the error*, so the failure produces no output at all. Fix: mark each closure `@Sendable`. The audit must enumerate every such call site and record it (a grep-able list in the resolution notes).
9. **`log stream` verification of the joined subsystem:** app, agent, and CLI all emit under the shared `Logging.subsystem` (wired in by #0269–#0271); confirm a single `log stream` invocation shows a complete handoff across all three processes, and document the invocation in `docs/xpc/` or the resolution notes.

## Out of scope

- Streaming, app-initiated events, long-lived sessions — **explicitly deferred at the umbrella level; no child exists for them by design.** Several lifecycle edges above exist *because* the experiment validated sessions; here they are handled only as far as request/reply connections need.
- New verbs (#0274), signing/notarization (#0273).
