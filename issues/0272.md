## Description

Fourth step of the XPC track under umbrella #0265. The experiment's honest accounting: "Connecting two processes is an afternoon" — the lifecycle work is the actual project. The happy path took about a third of the effort; the rest went on states that only exist because a connection between three processes can fail in more ways than a one-shot URL can. This child makes the channel from #0271 survive the real world.

**Gate:** blocked on #0271. Do not fold this into #0271 "while we're in there" — it is deliberately separate so #0271 can land and prove the hybrid before this cost is paid.

## Scope (each item is an acceptance criterion)

1. **`interruptionHandler` vs `invalidationHandler` handled distinctly** on every connection. They demand *different* responses: interruption = peer died, connection object reusable, re-register; invalidation = permanently dead, rebuild. Conflating them yields either a reconnect loop or a permanently dead connection.
2. **Broker restart under a running app** is detected and the app re-registers its endpoint automatically.
3. **A CLI killed with `kill -9`** leaves an orphaned connection the app must reap via the connection's invalidation handler — there is no other signal.
4. **The app quitting mid-connection** tells attached CLIs before invalidating, so they don't learn only from the connection dropping.
5. **Concurrent clients:** two CLI connections at once work, and ending one must not disturb the other.
6. **No-delivery-confirmation discipline:** one-way calls return `Void` whether or not the peer received them; every "did it work?" answer comes from a subsequent round trip. Audit the #0270/#0271 code for any place that trusts a one-way return.
7. **The `SMAppService` repair path (RemoteControl #0016):** `.status` can report `.enabled` while launchd has no such service (observed directly after `launchctl bootout`), so the app cannot repair its registration by trusting status. Drive re-registration (unregister-then-register) from a **failed call**, guarded to run **once per launch**.
8. **A `@Sendable` audit of every Foundation-supplied handler closure** in the XPC code paths — `remoteObjectProxyWithErrorHandler`, `interruptionHandler`, `invalidationHandler`, and any other Foundation-typed callback. The trap, in full, because there is no compiler help: on Batty's `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` target these closures inherit main-actor isolation (Foundation types them as plain non-`Sendable` closures); Swift emits an isolation assertion at the closure's entry; XPC calls it on its own queue; the process dies with `EXC_BREAKPOINT / SIGTRAP`. **No compiler warning — strict concurrency is fully satisfied.** And the crash lands *inside the handler that would have logged the error*, so the failure produces no output at all. Fix: mark each closure `@Sendable`. The audit must enumerate every such call site and record it (a grep-able list in the resolution notes).
9. **`log stream` verification of the joined subsystem:** app, agent, and CLI all emit under the shared `Logging.subsystem` (wired in by #0269–#0271); confirm a single `log stream` invocation shows a complete handoff across all three processes, and document the invocation in `docs/xpc/` or the resolution notes.

## Out of scope

- Streaming, app-initiated events, long-lived sessions — **explicitly deferred at the umbrella level; no child exists for them by design.** Several lifecycle edges above exist *because* the experiment validated sessions; here they are handled only as far as request/reply connections need.
- New verbs (#0274), signing/notarization (#0273).

## Verification expectations

- Unit tests where the logic is extractable: the once-per-launch repair guard's state machine; interruption-vs-invalidation dispatch (behind a seam if needed). `scripts/build.sh unit` and `scripts/build.sh` green.
- **Fault-injection matrix, run live (this is the point of the child — a passing build proves nothing here):**
  - kill the broker while the app runs → next CLI call succeeds after auto re-registration;
  - `kill -9` a connected CLI → app reaps the connection (observable via log stream / status client count);
  - quit the app with a CLI connected → CLI reports app-terminated (exit `5`) rather than a raw connection drop;
  - `launchctl bootout` the agent, confirm `.status` still lies, then confirm the next failed call triggers the repair path exactly once;
  - two concurrent CLI invocations; end one; the other is undisturbed;
  - every failure path deliberately triggered produces **visible error output** (the SIGTRAP class regression check).
- These live checks need a real machine and the user's coordination (never kill/relaunch the running app without asking — `CLAUDE.md` rule). Name in Gotchas exactly which scenarios were run and which need the user's runtime sign-off.
