# 0363 — Theme Selector opens at the top of the catalog with the first Theme highlighted instead of the active Theme

| | |
|---|---|
| **Status** | open |
| **Module** | Theme |
| **Platform** | macOS |
| **First seen** | 2026-08-22 |

## Description

> "When the themes selector appears it should scroll to the currently active theme and it should be highlighted. Use the same highlight effect used for panes."

The Theme Selector sheet (`Cmd-Shift-T`) always opens scrolled to the top of the catalog with the **first** card in the list wearing the accent outline. The currently active Theme is neither scrolled into view nor marked in any way. With ~500 entries in `BattyThemeCatalog.allThemes` (upstream `GhosttyThemeCatalog` merged with the Batty-original set — `BattyThemeCatalog.swift:16-31`), the active Theme is almost always off-screen, and the outline the user *does* see is pointing at an unrelated Theme.

A precise statement of the defect, because the code is not simply "missing a highlight":

- The selector **does** draw an accent outline, and it **does** own a `ScrollViewReader` that scrolls on selection change. Both mechanisms already exist and work.
- They are driven by `@State private var selectedIndex = 0` (`ThemeSelectorView.swift:18`), a *keyboard-cursor* index that is hard-seeded to `0` and never reconciled with the active Theme. So the existing highlight lands on catalog entry 0, and the existing scroll never fires on presentation because `selectedIndex` does not change.

Both the global selector (`ThemeSelectorView`) and the per-Session selector (`SessionThemeSelectorView`) are affected — they are near-duplicate implementations in the same file and both hard-seed `selectedIndex = 0` (`ThemeSelectorView.swift:18` and `:183`).

The user also asked that the active-Theme highlight reuse **the same highlight effect applied to Panes**. That effect is currently inlined in `PaneView` and is not extracted into anything shareable, so unifying the two is part of the work rather than a one-line application — see "Reusing the Pane highlight" below.

## Steps to reproduce

1. Set a Theme other than the alphabetically-first catalog entry (menu bar → Theme, or Settings → Appearance, or the selector itself).
2. Open the global Theme Selector: `Cmd-Shift-T`, menu bar → Theme → "Open Theme Selector…" (`BattyCommands.swift:124-130`), or the Command Palette entry (`CommandPaletteView.swift:282`). All three post `.battyToggleThemeSelector`, which `SessionDetailView.swift:53-56` turns into `themeSelectorShown.toggle()`, presenting the sheet at `SessionDetailView.swift:81-83`.
3. Observe the sheet: it is scrolled to the very top, and the first card in the "Pinned" section (or "Themes" if nothing is pinned) carries the accent outline.
4. The active Theme is nowhere in view, and nothing on screen identifies it.
5. Repeat for the per-Session selector: right-click a Session in the sidebar → the theming entry, which presents `SessionThemeSelectorView` (`SessionSidebarView.swift:123-129`). Same behavior.

Aggravating detail: arrow-key navigation applies each Theme live as the cursor moves (`ThemeSelectorView.swift:161-166`, `:323-328`). Because the cursor starts at index 0 rather than the active Theme, the very first `Down` keystroke jumps the user to catalog entry 1 — an arbitrary Theme — instead of stepping off the one they are currently using.

## Expected behavior

On presentation, for both `ThemeSelectorView` and `SessionThemeSelectorView`:

1. **Scroll the active Theme into view.** It should be visible without the user searching or scrolling. Anchor is a judgment call; `.center` matches what the existing selection-change scroll already uses (`ThemeSelectorView.swift:97`).
2. **Mark the active Theme as active.** The mark must read as "this is the Theme currently in effect", distinct from the keyboard cursor and from hover.
3. **Seed the keyboard cursor on the active Theme** so `Down` steps to the Theme *after* the active one and `Return` on open is a no-op re-selection rather than a silent switch to catalog entry 0.
4. **No jarring scroll when the active Theme is already visible.** If the target is already on screen (common when a pinned Theme is active — pinned entries render in the first section, `ThemeSelectorView.swift:85-88`), the view should not animate a scroll. `ScrollViewProxy` cannot report visibility, so the pragmatic form is to perform the initial positioning *without* animation (no `withAnimation`), which is a no-op-looking jump when the target is already visible and a silent reposition otherwise. Keep the animated scroll for subsequent arrow-key movement.
5. **Degrade cleanly with no active Theme.** `ThemePreference.activeTheme(isDark:)` returns `nil` when the stored name is empty or missing from the catalog (`ThemePreference.swift:53-59`), and `SessionRuntime.localThemeName` is `nil` for any Session following the global Theme (`docs/themes.md:357-366`). In those cases: no active mark, no scroll, cursor stays at index 0 — the current behavior, which is correct when there genuinely is no active Theme.
6. **Degrade cleanly when the active Theme is filtered out.** Typing in the filter can exclude the active Theme from `allDisplayed`. `onChange(of: query)` already resets `selectedIndex = 0` (`ThemeSelectorView.swift:100`); that stays. The active mark simply does not render when the active Theme is not among the filtered results — it must never be pinned to a stale index.

### Which Theme is "active"

Different for the two selectors, and the implementer must not conflate them:

- `ThemeSelectorView` — the **global** Theme for the current appearance. `ThemePreference.activeTheme()` (`ThemePreference.swift:64-66`) resolves the `NSApp` appearance and reads the dark/light slot; the selector already writes that same key on selection (`ThemeSelectorView.swift:141-144`). Note the appearance-split keys (`ThemePreference.swift:15-16`) — there is no single "the theme name" key any more.
- `SessionThemeSelectorView` — the Session's **effective** Theme: `session.localThemeName` if set, else the global Theme, per the fallback chain in `docs/themes.md:378-381`. Marking only `localThemeName` would leave the mark absent for every Session that follows the global Theme, which is the default state on every launch (`docs/themes.md:359-361`).

## Actual behavior

Cited against current `main`:

- `ThemeSelectorView.swift:18` — `@State private var selectedIndex = 0`. Never seeded from `ThemePreference`; nothing in the file reads `ThemePreference.activeTheme` at all (the only `ThemePreference` reference is the *write* at `:143`).
- `ThemeSelectorView.swift:121` — `ThemeCard(theme:isSelected: globalIndex == selectedIndex, …)`. The only selection input the card gets is the cursor index, so the card at index 0 is outlined on open.
- `ThemeCard.swift:71-76` — the outline: `RoundedRectangle(cornerRadius: 8).stroke(Color.accentColor, lineWidth: 2)` gated on `isSelected`. There is no second visual state for "active" — `ThemeCard` has exactly three inputs beyond the theme itself: `isSelected`, `isPinned`, `onTogglePin` (`ThemeCard.swift:6-9`).
- `ThemeSelectorView.swift:95-99` — the scroll: `.onChange(of: selectedIndex) { … proxy.scrollTo(allDisplayed[newIdx].name, anchor: .center) }`. `onChange` does not fire for the initial value, and `selectedIndex` never leaves `0` on presentation, so no scroll occurs.
- `ThemeSelectorView.swift:75-78` — `.onAppear` does exactly two things: `pinnedIDs = PinnedThemes.load()` and `searchFocused = true`. No positioning, no active-Theme resolution.
- `ThemeSelectorView.swift:183`, `:260-265`, `:284-289`, `:240-243` — the identical situation in `SessionThemeSelectorView`.

So the honest summary: the highlight and the scroll machinery both exist and are correct; what is missing is (a) seeding the cursor from the active Theme, (b) an initial scroll trigger, and (c) a distinct "active" visual separate from the cursor.

## Reusing the Pane highlight

The user asked for "the same highlight effect used for panes". That effect:

- `PaneView.swift:143-149`:
  ```swift
  .overlay {
      RoundedRectangle(cornerRadius: 4)
          .strokeBorder(accentColor, lineWidth: 2)
          .opacity(hasSiblingPanes && isPaneFocused ? 0.6 : 0)
          .animation(.easeInOut(duration: 0.12), value: isPaneFocused)
          .allowsHitTesting(false)
  }
  ```
- `accentColor` is `themeChrome?.accent ?? Color.accentColor` (`PaneView.swift:79-81`), read from `@Environment(\.themeChrome)` (`PaneView.swift:16`), injected once at `RootWindowView.swift:39`.
- Origin: `#0052` ("Active pane is not visually distinguishable from inactive panes"), whose acceptance criteria explicitly call for respecting the active Ghostty Theme's accent color.

**It is not reusable as-is.** The effect is inlined in `PaneView` — a grep of `BattyKit/Sources` for `ViewModifier` finds only `SidebarRowBackground` (`SessionSidebarView.swift:189`) and `TabRunningCommandObserver` (`PaneView.swift:666`); there is no shared focus-outline modifier, no shared corner-radius or line-width constant. `ThemeChrome.focusBorder` (`ThemeChrome.swift:41`) looks like the intended shared hook but is dead — a grep of the whole repo finds no reader.

**Requirement, not a suggestion:** the implementer's first step is to extract the Pane focus outline into a single shared `ViewModifier` (something like an `activeOutline(_:)` taking a plain `Bool`) parameterized on corner radius, and route both `PaneView.swift:143-149` and the Theme Selector's active card through it. Two hand-copied outlines that merely happen to match today would defeat the point of the request. Extraction must not change the Pane's rendered appearance — corner radius 4, line width 2, opacity 0.6, 0.12 s ease-in-out, `.allowsHitTesting(false)` — and the Theme Selector card should pass its own corner radius (the card is clipped at radius 8, `ThemeCard.swift:70`).

Note the near-miss: `ThemeCard`'s existing cursor outline (radius 8, `.stroke`, full-opacity `Color.accentColor`) is *almost* the Pane effect but differs in radius, opacity, `stroke` vs `strokeBorder`, and color source. Do not assume they are the same and collapse them by accident — the cursor and the active mark must remain visually distinguishable (see the next section).

## Gotchas / risks

**Two competing highlights.** After this change a card can be simultaneously the keyboard cursor and the active Theme, and the two can also sit on *different* cards once the user arrows away. The design must keep them distinguishable — e.g. the extracted Pane outline for "active", and a visibly different treatment for the cursor (different color, a filled/heavier ring, or a checkmark badge for "active" as `SessionColorPickerView.swift:162` already does for its "Automatic" entry). Decide this explicitly; do not let "active" and "cursor" render identically, or the user cannot tell which Theme is in effect once they start navigating. Hover has no treatment today (`ThemeCard` has no `onHover`), so nothing to reconcile there — but do not add one in passing.

**Open question for the user — theme-derived accent inside a Theme picker.** The Pane highlight's color comes from the *active* Theme's accent (`PaneView.swift:79-81`). Inside a Theme picker that means every card — including ones previewing wildly different palettes — gets outlined in the current Theme's accent. It may read fine (a consistent "the app's accent marks the current choice") or poorly (an outline that clashes with the swatch it surrounds). **Do not decide this unilaterally.** Raise it; the fallback is the current `Color.accentColor`, which the extracted modifier can accept as an override.

**Observation rules — binding.** `docs/swiftui-observation-rules.md` is binding for this work. The initial `proxy.scrollTo` is a view-driven action and must run from an event-origin hook (`.onAppear` / `.task`), never from `body`, a view `init`, `ViewModifier.body`, or a preference/geometry callback (`swiftui-observation-rules.md:36-41`). Presentation of a sheet is an event-origin flip, so an `.onAppear` write here is in the "routine" bucket of the audit at `swiftui-observation-rules.md:42-50` — but state the reasoning; do not just assert it. And per the same doc, do **not** resolve a mid-update ordering problem by hopping the write into a `Task` (`:167-175`).

**Ordering depends on `pinnedIDs`, which loads in `onAppear`.** `allDisplayed` is `filteredPinned + filteredOthers` (`ThemeSelectorView.swift:38`), and that partition depends on `pinnedIDs`, which starts empty and is only populated at `ThemeSelectorView.swift:76`. So the obvious `SessionColorPickerView` pattern — seeding the cursor in `init` via `_cursor = State(initialValue:)` (`SessionColorPickerView.swift:109-117`), which is the right precedent for the *shape* of the fix — cannot be copied verbatim: an index computed before `pinnedIDs` loads points at the wrong Theme once the Pinned section appears. Either move `PinnedThemes.load()` into `init` (it is a pure `UserDefaults.standard.stringArray` read, `PinnedThemes.swift:8-10`, so this is safe) or compute the index after `pinnedIDs` is assigned. Seeding by *name* and deriving the index from it is more robust than storing a raw index across a reordering.

**Lazy-container scroll targeting.** The cards live in a `LazyVGrid` inside a `LazyVStack` (`ThemeSelectorView.swift:84`, `:116`) with `.id(theme.name)` on each card (`:135`), and ~500 entries. `scrollTo` on a lazy container can silently no-op when called before the container has laid out — an `.onAppear` on the sheet's root fires early enough for this to be a real risk. Verify the scroll actually lands; if it does not, prefer `.task` on the scroll content, or an `.onAppear` on the `ScrollViewReader`'s content, over an arbitrary sleep. Whatever form is chosen, do not animate the initial positioning (see Expected behavior #4).

**Duplication.** `ThemeSelectorView` and `SessionThemeSelectorView` are ~130 near-identical lines each (`ThemeSelectorView.swift:13-172` vs `:177-334`), differing only in how "active" is resolved and what `selectTheme` writes. The fix must land in both. Factoring the shared body out is tempting and probably correct, but it widens the diff considerably — treat it as optional and call it out at review rather than smuggling it in.

**Environment reach into the sheet.** The extracted modifier will want `@Environment(\.themeChrome)`, injected at `RootWindowView.swift:39`. SwiftUI sheets normally inherit the presenting view's environment, but verify it actually arrives inside the sheet rather than assuming — if it does not, the outline silently falls back to `Color.accentColor` and the "same as panes" requirement is quietly unmet.

**Docs are stale here.** `docs/themes.md:33-35` still describes the Theme menu's checkmark as the active-Theme indicator, and `:44-45` still names a single `co.sstools.Batty.themeName` key that `ThemePreference.swift:15-21` has since split into dark/light slots. Neither doc statement describes the Theme Selector's active-Theme presentation, because there isn't one. Update `docs/themes.md` when this lands; the stale key reference is out of scope for this issue.

## Notes

- Precedent for the seeding pattern: `SessionColorPickerView` seeds its keyboard cursor from the Session's current color in `init` and comments on exactly why ("so the ring is visible the instant the sheet opens") — `SessionColorPickerView.swift:94-99`, `:115`. Same class of defect, already solved once in this codebase.
- `#0052` is the origin of the Pane focus outline and is the reference for what that effect is supposed to signal.
- Related selector regressions, for context on this area's history: `#0137` (selector filter and color grid wiring), `#0138` (pinned Themes not surfacing) — see `docs/ui-features.md:191-193`.
- Semantic mismatch worth stating plainly: on a Pane the outline means *focus* ("this Pane receives input"); on a Theme card it would mean *current selection* ("this Theme is in effect"). The effect transfers cleanly at the code level — `isPaneFocused` is a plain computed `Bool` (`PaneView.swift:53-55`), not a `FocusState` binding — so there is no technical obstacle, only the visual-vocabulary question of the same outline carrying two meanings in one app.
