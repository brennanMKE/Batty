## Description

Both tests in `AppearanceBackgroundSettingsTests` failed in today's full VM UI run against `main` (`bc956752`) and again in the re-run of the failures against `main` (`483b8948`). Each fails at `AppearanceBackgroundSettingsTests.swift:21` with a bare `XCTAssertTrue failed`. That line is the `appearance.waitForExistence(timeout: 10)` check in `openAppearanceSettings(in:)`, after the test types ⌘, and looks for `app.toolbars.buttons["Appearance"]`.

The failure snapshot shows Batty with only its content window (`Session 1`). There is no Settings window, so ⌘, did not open Settings. The Appearance tab itself still exists (`SettingsView.swift:20-21`).

Most likely cause (hypothesis): the banner sweep that #0622 added to the shared launch path (`b038b53c`, which landed about 20 minutes before `bc956752`) leaves Notification Center holding keyboard focus. The ⌘, keystroke then goes to Notification Center instead of Batty.

Failing filters:

## Notes

Hypotheses, most likely first:

1. **The #0622 banner sweep leaves Notification Center focused, so ⌘, never reaches Batty.** `GuestBanners.dismissAll()` (`BattyUITests/Support/GuestBanners.swift:28-41`) calls `banner.hover()` (`:35`). It then looks for `center.groups["AXNotificationListItems"].buttons["Close"]` (`:36`). That group doesn't exist in this guest's tree, so the lookup always times out after 2 s and falls back to `banner.swipeRight()` (`:37`). Nothing re-activates Batty afterwards: `launchBatty` calls `GuestBanners.settleAfterLaunch()` (`Support/BattyUITestHarness.swift:31` and `:53`) and returns. `XCUIApplication.typeKey` sends the chord to whatever app has keyboard focus, which the snapshot shows is Notification Center. Before #0622, launches never touched Notification Center. A banner on screen wouldn't block a keystroke, only a click.
   - Fix direction for the plan to decide: click the banner's own `Close` button (`buttons["Close"]` inside the matched banner) instead of the `AXNotificationListItems` lookup. After any sweep, re-activate the app under test (`app.activate()`) and wait until it is frontmost before returning from `launchBatty`.
2. **This class is exposed because it runs first.** Alphabetically it is the first class, so it gets the first launch, which carries the 10 s `notificationsPredicate` wait and the first sweep. The second test sees the banner again, which is consistent with `BellNotifier.ensureAuthorization()` requesting authorization on every launch (the open question recorded in #0622's Gotchas). Any test that launches, has a banner swept, and then types a chord is exposed, not only this class.
3. **Less likely: an app-side change stops ⌘, from opening Settings.** Commits that landed on `main` today and touch this path: `b7a8c1f9` (#0616, Settings' Theme writer), `27c47657` (#0615, key content window tracking for menus) and `9f609e9e` (#0612, window chrome). `AppearanceSettingsView` is still the second tab (`SettingsView.swift:20-21`). ## Plan

### Confirmed cause

Hypothesis 1 holds, with one correction to its mechanism. Evidence from run `20261113-155125-98146`:

- `xcodebuild.log` shows `banner.hover()` performing `Open com.apple.notificationcenterui` → `Activate com.apple.notificationcenterui` before it synthesizes the event. XCUITest activates the owning app of any element it interacts with, so the sweep itself makes Notification Center the active app. The exported hierarchy shows the `Notification Center` Dialog marked **Keyboard Focused**.
- `app.typeKey(",", modifierFlags: .command)` logs `Find the Target Application` and `Synthesize event` with no `Activate co.sstools.Batty.beta` step, so the chord goes to the focused app (Notification Center). Batty's tree at failure has no Settings window.
- The Close lookup `center.groups["AXNotificationListItems"]` never matches: that group is absent, and the banner's own `Button, identifier: 'xmark', label: 'Close'` is a child of the matched banner `Group`. So every sweep falls back to `swipeRight()`, which is unreliable: in the second test four swipes in a row (t=4.4 s to 21.8 s) left the banner in place, each burning the 5 s `!banner.exists` wait.
- Nothing after the sweep hands focus back to Batty.

Not an app regression (hypothesis 3): `AppearanceSettingsView` is still the second tab, and the failure is fully explained by where the keystroke went.

### Approach

All changes are in the UI-test target's support code. No app code changes.

1. `BattyUITests/Support/GuestBanners.swift`
   - `dismissAll` takes the app under test: `dismissAll(returningFocusTo app: XCUIApplication) -> Bool`.
   - Close lookup is scoped to the matched banner: `banner.buttons["Close"].firstMatch` (the `xmark` button), after `banner.hover()` reveals it. Delete the `AXNotificationListItems` lookup and the `swipeRight()` fallback. If Close does not exist, or the banner is still there after the click (bounded by `waitFor`), record `XCTFail` naming the banner's label, then stop sweeping. A wrong selector now fails loudly instead of degrading to a swipe.
   - After any sweep that touched Notification Center (`dismissed == true`), call `app.activate()`. Then assert, with bounded waits as failure guards only, that `app.wait(for: .runningForeground, timeout: 5)` is true and that `center.dialogs["Notification Center"]` no longer exists. If either fails, `XCTFail` with a message saying focus did not return to the app under test. When nothing was dismissed, Notification Center was never activated, so neither step runs.
   - `settleAfterLaunch` takes the app and passes it through: `settleAfterLaunch(app:)`. The first-launch 10 s appearance wait stays as is. It waits for the banner to arrive, returns the moment it appears, and isn't a retry.
   - Update the type's doc comment: hovering or clicking a banner activates Notification Center, so the sweep re-activates the app under test before returning.
2. `BattyUITests/Support/BattyUITestHarness.swift`: both `launchBatty` overloads call `GuestBanners.settleAfterLaunch(app: app)`. The `XCTestCase.dismissBanners()` forwarder becomes `dismissBanners(in app: XCUIApplication)`.
3. Call sites pass their app:
   - `BattyUITests/Support/BattyCLIHarness.swift:379` (`openBellFeed`): `GuestBanners.dismissAll(returningFocusTo: app)`.
   - `ProjectsSymbolTests.swift:41,68,87,107`, `ProjectsSharingTests.swift:144`, `DemoSceneTests.swift:142`: `dismissBanners(in: app)`.
   - `ViewGalleryTests.swift:226-230`: `dismissBanners(in: gallery.app)`. The capture loop (`for _ in 0..<5 { if !dismissBanners() { break } }`) and the separate `gallery.app.activate()` become one call, because `dismissAll` already loops over up to four banners and re-activates the app.
4. `docs/ui-testing-vm.md` "Banners" bullet (around lines 208-214): say that Close is the banner's own `xmark` button, that the sweep re-activates the app under test because interacting with a banner activates Notification Center, and that a sweep that can't close a banner fails the test.

Out of scope: the notifications banner coming back on every launch (`BellNotifier.ensureAuthorization()`, #0622's open question). With working Close and re-activation, each launch's sweep handles it.

## Root cause

`GuestBanners.dismissAll` hovered the banner, which makes XCUITest activate Notification Center, and nothing handed focus back, so the following `typeKey(",", .command)` went to Notification Center and Settings never opened. Its Close lookup (`AXNotificationListItems`) never matched, so every sweep fell back to an unreliable `swipeRight()`.

Round 2 (VM bounce, run `20261113-162135-41935`, 16 of 17 failed): the guest also showed two Login Items "App Background Activity" banners, for "BattyBroker" and "zsh". Background Task Management posts one for each new plist in `~/Library/LaunchAgents`, and `tools/vm-guest-broker.sh` writes the broker agent and the CLI relay agent (`/bin/zsh`) there. The two stack: the top banner is a Group labelled "…, stacked" whose `xmark` button is "Clear All", and the banner under it is a Button with no `xmark` at all. The round-1 sweep looked for "Close" inside the first match (often the hidden Button) and failed the test. In the next run, the notifications banner was hovered while still sliding in, so no `xmark` appeared, and Notification Center's panel stayed open while the pointer rested on the banner.

## Fix

- `tools/vm-guest-broker.sh` writes both agent plists to `~/Library/Application Support/BattyUITests/agents` and bootstraps them from there, so Background Task Management never posts the Login Items banners. (Verified: no Login Items banner in the passing run.)
- `GuestBanners.dismissAll(returningFocusTo:)` hovers the stacked Group if there is one, otherwise the first banner. It first waits for the banner's frame to stop moving, and it hovers a second time if needed. It then clicks the first `xmark` button anywhere in Notification Center (Close or Clear All) and waits for the banner count to drop. A banner it can't close is recorded as an activity with Notification Center's tree attached, not failed.
- After any sweep, it parks the pointer on the app's window and calls `app.activate()`. It fails the test if the app isn't `runningForeground`, or if the Notification Center Dialog is still up once every banner has closed.
- `settleAfterLaunch(app:)` and `dismissBanners(in:)` pass the app through, and all callers are updated. The gallery's extra loop and `activate()` are folded into one call. The `docs/ui-testing-vm.md` Banners bullet is updated.
