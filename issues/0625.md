## Description

Both tests in `AppearanceBackgroundSettingsTests` failed in today's full VM UI run against `main` (`bc956752`) and again in the re-run of the failures against `main` (`483b8948`). Each fails at `AppearanceBackgroundSettingsTests.swift:21` with a bare `XCTAssertTrue failed`. That line is the `appearance.waitForExistence(timeout: 10)` check in `openAppearanceSettings(in:)`, after the test types ⌘, and looks for `app.toolbars.buttons["Appearance"]`.

The failure snapshot shows Batty with only its content window (`Session 1`). There is no Settings window, so ⌘, did not open Settings. The Appearance tab itself still exists (`SettingsView.swift:20-21`).

Most likely cause (hypothesis): the banner sweep that #0622 added to the shared launch path (`b038b53c`, which landed about 20 minutes before `bc956752`) leaves Notification Center holding keyboard focus. The ⌘, keystroke then goes to Notification Center instead of Batty.

Failing filters:

- `BattyUITests/AppearanceBackgroundSettingsTests/testBackgroundControlsAppearInAppearanceSettings`
- `BattyUITests/AppearanceBackgroundSettingsTests/testOpacityFieldsAcceptTypedValuesAndClamp`

## Steps to reproduce

1. `tools/run-ui-tests-vm.sh BattyUITests/AppearanceBackgroundSettingsTests` on `main`.
2. Both tests fail at line 21.

## Expected behavior

⌘, opens Settings, the Appearance toolbar button exists, and both tests pass.

## Actual behavior

## Notes

Hypotheses, most likely first:

1. **The #0622 banner sweep leaves Notification Center focused, so ⌘, never reaches Batty.** `GuestBanners.dismissAll()` (`BattyUITests/Support/GuestBanners.swift:28-41`) calls `banner.hover()` (`:35`). It then looks for `center.groups["AXNotificationListItems"].buttons["Close"]` (`:36`). That group doesn't exist in this guest's tree, so the lookup always times out after 2 s and falls back to `banner.swipeRight()` (`:37`). Nothing re-activates Batty afterwards: `launchBatty` calls `GuestBanners.settleAfterLaunch()` (`Support/BattyUITestHarness.swift:31` and `:53`) and returns. `XCUIApplication.typeKey` sends the chord to whatever app has keyboard focus, which the snapshot shows is Notification Center. Before #0622, launches never touched Notification Center. A banner on screen wouldn't block a keystroke, only a click.
   - Fix direction for the plan to decide: click the banner's own `Close` button (`buttons["Close"]` inside the matched banner) instead of the `AXNotificationListItems` lookup. After any sweep, re-activate the app under test (`app.activate()`) and wait until it is frontmost before returning from `launchBatty`.
2. **This class is exposed because it runs first.** Alphabetically it is the first class, so it gets the first launch, which carries the 10 s `notificationsPredicate` wait and the first sweep. The second test sees the banner again, which is consistent with `BellNotifier.ensureAuthorization()` requesting authorization on every launch (the open question recorded in #0622's Gotchas). Any test that launches, has a banner swept, and then types a chord is exposed, not only this class.
3. **Less likely: an app-side change stops ⌘, from opening Settings.** Commits that landed on `main` today and touch this path: `b7a8c1f9` (#0616, Settings' Theme writer), `27c47657` (#0615, key content window tracking for menus) and `9f609e9e` (#0612, window chrome). `AppearanceSettingsView` is still the second tab (`SettingsView.swift:20-21`). The other ⌘,-then-Appearance classes passed on re-run (see below), which argues against an app regression. To rule it out, run the class with the banner sweep disabled, or with `app.activate()` added after it.

Related (#0622's follow-up): in today's full run against `bc956752`, three other tests failed once and passed on the re-run. All three open Settings with ⌘, at some point:

Its two Help tests open Help from the menu bar instead.
- `BackgroundCatalogSettingsTests/testAddedCatalogsSetsAppearInBackgroundSets` (⌘, then `toolbars.buttons["Appearance"]`, `BackgroundCatalogSettingsTests.swift:26-27`).

They are recorded as known flakes. If hypothesis 1 holds and the failures were the Settings tests, they are the same cause hitting only when a banner is up at that launch, and this fix should cover them. Re-run them after the fix.
