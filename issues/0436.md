# 0436 — `SessionCwdRenameTests` fails in the Tart VM because a `cd` into a project never renames the Session, most likely because Session auto-naming has read the previous working directory since the 2026-09-03 libghostty-spm re-pin

## Description

In the Tart VM, `BattyUITests/SessionCwdRenameTests.testSessionNameTracksCdIntoAndOutOfProjectDir` fails at the assertion `Session should rename to 'BattyCdProbe' after cd into the project dir`. #0416 fixed the earlier fixture-permission failure, and this one surfaced behind it.

**Leading hypothesis, from reading the code and not yet confirmed at runtime.** This is probably not VM-specific. The pinned `libghostty-spm` (`a2565ccf`, re-pinned 2026-09-03 by `b92cd3ce`, #0389/#0397) now writes `TerminalViewState.workingDirectory` one main-queue turn late. Batty's pwd callback reads that property synchronously, immediately after forwarding the update, so it still sees the *previous* directory. Session auto-naming would then run one `cd` behind on every Mac. The test's first `cd` resolves against the old directory, the title stays `Session 1`, and nothing re-runs the resolver within the 10 s poll. This matches every observation #0416's VM rounds recorded.

## What #0416's VM rounds established

From `git show issue/0416:issues/0416.md`, sections `## VM verification — 2026-09-24` and `## Root-cause investigation — 2026-09-24 (round 2)`:

- The shell reaches the fixture directory. A `cd <projectDir> && printf … > <sentinel>` sentinel appeared.
- `$HOST` matched the live `hostname` byte for byte (`Manageds-Virtual-Machine.local`). That rules out libghostty's OSC 7 host-locality check dropping the report.
- `ProjectNameResolver` keys on directory contents, not path spelling, so the `/var` → `/private/var` form doesn't matter.
- The window title (bound to `session.title`) also stayed `'Session 1'`. The model never changed, so this is not a sidebar-rendering miss.
- No crash and no driver-error sentinel. `app-warnings.log` showed only the known #0419 broker loop and the #0420 geometry fault.
- VM run ids: `20260923-234117-89835`, `20260924-000109-6894`, `20260924-000635-11018`.

## Premises checked in code (read-only, 2026-09-24, `main` at `14a0aee5`)

### (b) The pwd → auto-name chain: an ordering bug, settled by reading the code

The chain is libghostty OSC 7 → `GHOSTTY_ACTION_PWD` → `TerminalCallbackBridge` (fork, `Sources/GhosttyTerminal/InMemory/TerminalCallbackBridge.swift:144-154`) → `TerminalDelegateProxy.terminalDidChangeWorkingDirectory` → `onWorkingDirectoryChange` closure → `AppStateStore.handleWorkingDirectoryChange(forTabID:)`.

1. `TerminalDelegateProxy.terminalDidChangeWorkingDirectory(_:)` (`BattyKit/Sources/BattyKit/Runtime/TerminalDelegateProxy.swift:86-89`) calls `state.terminalDidChangeWorkingDirectory(path)` and then **synchronously** `onWorkingDirectoryChange?(path)`.
2. At the pinned revision `a2565ccf`, the fork's `TerminalViewState.terminalDidChangeWorkingDirectory` (`Sources/GhosttyTerminal/State/TerminalViewState+Delegate.swift:106-111`) wraps the write in `publishSoon`. `publishSoon` (`:51-56`) calls `terminalRunOnMainNextTurn` (`Sources/GhosttyTerminal/Platform/Shared/TerminalMainActor.swift:37-45`), which is an unconditional `DispatchQueue.main.async`. At the previous pin `b146b73` the same method was `workingDirectory = path`, a synchronous write. The deferral arrived in fork commit `62874a2` (2026-08-29, "Publish every observable change on the next turn, not only the grid size"). `git merge-base --is-ancestor` confirms it is not in `b146b73`.
3. The closure wired in `PaneView.swift:289-293` ignores its `path` argument (`{ [weak appStore] _ in … }`). It calls `tab.syncWorkingDirectoryFromTerminal()` (`TabRuntime.swift:317-322`) and `handleWorkingDirectoryChange(forTabID:)` (`AppStateStore.swift:1699`). Both read `terminal.workingDirectory` (`AppStateStore.swift:1709`), which still holds the old value at that point.
4. Nothing re-runs the resolver once the deferred write lands. The only callers of `handleWorkingDirectoryChange` are the two `PaneView` sites (`:291` in the callback, `:312` in the one-time `.task` initial resolve).
5. The proxy's own doc comment (`TerminalDelegateProxy.swift:29-30`) says the callback fires "after the new path has been written to `state`". That was true at `b146b73` and is false at `a2565ccf`. #0397 examined exactly this `publishSoon` change and concluded that "production never performs the call-then-read sequence" and that the proxy "never reads back". That holds for bells and desktop notifications, but it missed this pwd path.
6. The unit tests don't cover the ordering. `AISessionNamingTests` and its siblings set `anchorTab.terminal.configuration.workingDirectory` directly and call `handleWorkingDirectoryChange` themselves, so they never go through the proxy.

No other gate on the chain blocks it. There is no debounce and no focus check. There is no active-tab check either: the anchor is `firstLeafPane.tabs[0]`, and the test has one pane and one tab. `titleOverride` is false for a fresh session.

Predicted behavior under this hypothesis: `cd A` leaves the name computed for the previous directory. `cd B` then applies A's name. In the test, the first `cd` resolves the temp home (`Session 1`), so it fails at the first assertion. The second `cd` would have produced `BattyCdProbe`, one step late.

### (a) The "Name sessions from project files" gate: ruled out

- The key is `co.sstools.Batty.autoNameFromFiles` (`SettingsPreferences.swift:16`). `resolvedAutoNameFromFiles()` (`:99-104`) returns `defaultAutoNameFromFiles = true` (`:29`) when the key is absent. The guest's empty defaults domain therefore resolves to **on**.
- `BattyUITestHarness.launchBatty()` (`BattyUITests/Support/BattyUITestHarness.swift:18-24`) sets only `BATTY_UI_TEST_MODE=1` and `BATTY_UI_TEST_TEMP_HOME`. No launch argument or environment variable touches the setting.
- Side finding: nothing in `Batty/` or `BattyKit/Sources` reads `BATTY_UI_TEST_TEMP_HOME` (`git grep` finds only the harness). The launched app does not use it as `$HOME`.
- `ProjectNameRules.bundled` loads from `Bundle.module`, falling back to `.main` (`ProjectNameRules.swift:26-36`), so it does not depend on the environment.

### (c) Shell integration in the guest: consistent, but not proven

- The fork overrides the resources directory. `GhosttyRuntimeResources.configureEnvironment()` (fork `Sources/GhosttyTerminal/Configuration/GhosttyRuntimeResources.swift:23-26`, called from `TerminalController.swift:328`) sets `GHOSTTY_RESOURCES_DIR` to the package's own `Bundle.module` `Ghostty/` directory. The shell integration that runs is therefore the fork's MIT rewrite, not the Kitty-derived copy Batty bundles into `Contents/Resources/ghostty` via `scripts/bundle-ghostty-resources.sh`. This appears to leave Batty's own bundled copy unused for OSC 7, but that is not verified at runtime.
- The fork's `zsh/.zshenv` loads `ghostty-integration` from the first `precmd`. That script emits OSC 7 as `file://${HOST-}<percent-encoded $PWD>` from `_ghostty_precmd`, on every prompt (`ghostty-integration:54-64` at `a2565ccf`). It has no `chpwd` hook and no feature gate. #0416 round 2 cited the Kitty-derived `kitty-shell-cwd://` form from the upstream script, but both forms embed `$HOST`, so its hostname conclusion stands.
- The guest's shell is almost certainly zsh. The sentinel printed a populated `$HOST`, which zsh sets and bash does not. `resolvedShell()` falls back to `$SHELL`, then `getpwuid`, and it is passed as `command`, so libghostty's `detect` sees `zsh`.
- **Not proven:** that the integration actually loaded and emitted OSC 7 in the guest. The sentinel proves only that `cd` ran. If lead (b) is right, OSC 7 *is* arriving and the bug is downstream, so (c) is secondary. It still needs checking if (b) is refuted.

### (d) Whether the test passes on a host run: no evidence for the current code

- The only recorded pass is #0228's, on 2026-05-30 on the host (`issues/0228.md:39`, "1 test passed (20.9 s)"). That was against pin `c69c343`, which wrote synchronously.
- A grep of `issues/` and `docs/` finds no run of this class between the 2026-09-03 re-pin and #0412's first VM run on 2026-09-23. `docs/ui-testing-vm.md:251` records only the fixture failure.
- So "passes on the host" is unestablished for current `main`. If (b) holds, it would fail on the host too. Per `AGENTS.md` it must not be run there to find out.

## Next diagnostics (cheapest first)

1. **Unit test on the host, no VM needed.** In `BattyKitTests`, build a tab through the real `TerminalDelegateProxy` wiring (or the same closure shape `PaneView` installs). Call `proxy.terminalDidChangeWorkingDirectory("<dir with package.json>")`, and inside `onWorkingDirectoryChange` capture `tab.terminal.workingDirectory`. At `a2565ccf` the captured value should be the old one. This confirms or refutes (b) in seconds. It needs a completion signal, not a sleep (`AGENTS.md`, "Asynchronous tests"), for example awaiting the next main-queue turn through a continuation enqueued on `DispatchQueue.main`.
2. **UI-level confirmation in the VM, test-only change.** After `cd <projectDir>`, type a bare `\n` so a second `precmd` emits the same OSC 7. If the Session then renames to `BattyCdProbe`, the one-behind ordering is confirmed end to end.
3. **UI-test driver hook exposing the pane's last reported pwd.** Under `BATTY_UI_TEST_MODE` only, publish two values for the anchor tab: `terminal.workingDirectory`, and the last `path` the proxy received. An accessibility value on the pane or a sentinel file would do. That separates "OSC 7 never arrived" (which is (c)) from "arrived but read stale" (which is (b)) without guest console access.
4. **If (b) is refuted, check (c) directly.** Extend #0416's sentinel with `print -r -- ${+_ghostty_integration_loaded} "$GHOSTTY_RESOURCES_DIR" "${precmd_functions[*]}"`. Alternatively, enable `TerminalDebugLog` with the `.actions` category (routed like `TerminalMetalMetricsLogger.swift:105-113`) under `BATTY_UI_TEST_MODE`, and check the run's app log for `callback action=pwd`.

## Expected behavior

`cd` into a directory containing a project marker renames a single-pane Session to the project name on that same `cd`. `cd` out resets it to `Session N`. `SessionCwdRenameTests` passes in the VM.

## Notes

- A fix direction, if (b) is confirmed. Have the callback act on the `path` it is handed rather than re-reading the deferred property. Or have the runtime layer observe the published `workingDirectory` so the read comes causally after the write, which is #0397's own "downstream of the publish" argument. Any rewiring must respect `docs/swiftui-observation-rules.md`. Do not hop the read into a `Task`, because that is the #0229 anti-pattern. Also fix the stale doc comment at `TerminalDelegateProxy.swift:29-30`, and check `updateTabAutoName`/`syncWorkingDirectoryFromTerminal` (tab chips and the sidebar pane row, #0260), which read the same stale value.
- Run UI tests only through the VM runner (`docs/ui-testing-vm.md`), never on the host (`AGENTS.md`, "UI test automation").
