# 0572 — The batty CLI cannot read or write a Scratch Pad's text

| | |
|---|---|

## Description

Once the Scratch Pad Pane ([#0571](0571.md)) exists, a script or an agent running in a terminal Pane should be able to read its text and replace, append to or clear it, from `batty` / `batty-beta`. Example uses: an agent drops a long command it built into the Scratch Pad for the user to review and edit before running it; the user edits a command in the Scratch Pad and a script reads it back with `batty pane text`. The text stays ephemeral (#0571 decision 2). The CLI never writes it to a file, and nothing about this issue adds persistence.

User request (2026-11-11, verbatim): "this text content will be ephemeral and we should even allow the CLI tool to access it with read/write access, so create a 2nd issue to update CLI tool."

**Depends on #0571.** Work this after #0571 lands on `main`. It needs `PaneContentKind.scratchPad` and the text held in `ScratchPadPaneContent` on `PaneRuntime.content`, reachable from `AppStateStore` with no view on screen (#0571 decision 3). Targets 1.4.0. If #0571 ships unflagged this needs no flag; if #0571 is behind a `scratchPad` flag, these verbs sit behind the same flag, using the CLI-side `current` path in `docs/feature-flags.md` ("CLI (compile time)").

## Existing conventions this follows (checked against the code)

- **Transport.** Acknowledged mutations and live queries go over XPC request/reply: `AppServiceProtocol.perform(_ request: Data, reply:)` (`BattyKit/Sources/BattyXPCCore/XPCProtocols.swift:57`). Each verb has a name constant in `BattyKit/Sources/BattyXPCCore/XPCVerb.swift`, a `…Payload.swift` in `BattyKit/Sources/BattyXPCCore/` (request and reply types, e.g. `SessionRemindPayload.swift`, `PaneHidePayload.swift`), a dispatch arm in `BattyKit/Sources/BattyKit/XPC/AppXPCService.swift`, an `AppStateStore …ForXPC` method returning an outcome enum (e.g. `remindSessionForXPC` in `BattyKit/Sources/BattyKit/Runtime/AppStateStore+Reminders.swift:218`, `hidePaneForXPC` in `AppStateStore.swift:1773`), and a client call in `BattyKit/Sources/batty/AppServiceClient.swift` (e.g. `sessionRemind` at line 209, `paneHide` at 227).
- **Grammar.** `batty <noun> <verb>`. The noun set is `session`, `pane`, `tab`, `window`, plus `project` as a deliberate, user-approved addition (`docs/batty-cli-design.md` §1.1). A Scratch Pad is a Pane, so the verb belongs under `pane`. `pane`'s subcommands today are `split`, `close`, `focus`, `hide`, `show` (`BattyKit/Sources/batty/PaneCommand.swift:15`). Mode flags on one verb follow `batty session remind` (`--in` / `--tomorrow` / `--cancel`, `BattyKit/Sources/batty/SessionRemindCommand.swift`).
- **Targeting.** Explicit flag, then `BATTY_*` environment, then focus (`docs/batty-cli-agent-workflows.md` "Target resolution"; `BattyTargetResolver.resolve(flag:environmentKey:)` in `BattyKit/Sources/BattyCLICore/BattyTargetResolver.swift`). **Catch:** `BATTY_PANE_ID` names the *terminal* Pane the caller runs in (`BattyContextEnvironmentKey.paneID`, `BattyKit/Sources/BattyCLICore/BattyContextEnvironment.swift:17`), which is never a Scratch Pad. The usual pane fallback can't find a Scratch Pad, so this verb needs its own rule (below).
- **Output and exit codes.** Quiet by default, `--json` on query verbs, `send`-style verbs accept stdin (`docs/batty-cli-design.md` §1.4). Grammar errors exit with ArgumentParser's usage code and send nothing. An unknown or wrong target exits `XPCExitCode.requestFailed` (4) (`BattyKit/Sources/BattyXPCCore/XPCExitCode.swift:25`). Broker and app failures map as the other XPC verbs do.
- **Capabilities.** Each verb path opts into an archetype in `BattyKit/Sources/batty/CapabilitiesCommand.swift` (`leafArchetypeByVerbPath`, e.g. `"session remind": "remind"` at line 200), and each command's input schema is checked by `CapabilitiesInputSchemaTests`.
- **Discovery.** `batty list --json` already reports each Pane's `kind` (`TopologyPanePayload.kind`, `BattyKit/Sources/BattyXPCCore/TopologyPayload.swift`), so `select(.kind == "scratch-pad")` finds Scratch Pads once #0571 adds the case. `batty pane split --view scratch-pad --unique` prints an existing visible one's id, or creates one (`PaneCommand.swift:102`).

## Proposed command shape

One verb, `batty pane text`, with mutually exclusive modes, in the style of `session remind`:

```
batty pane text [--pane <id>] [--session <id>] [--json]          # read: print the text to stdout
batty pane text --set <text>    [--pane <id>] [--session <id>]   # replace
batty pane text --append <text> [--pane <id>] [--session <id>]   # append
batty pane text --clear         [--pane <id>] [--session <id>]   # empty it
```

- `--set -` and `--append -` read the text from stdin until EOF, so `pbpaste | batty pane text --set -` and `cat cmd.sh | batty pane text --append -` work. The literal argument `-` always means stdin. To write a lone hyphen, pipe it.
- **Read** prints the text exactly, with no added trailing newline, so `batty pane text > file` round-trips byte for byte. `--json` prints `{"paneID": "...", "sessionID": "...", "text": "..."}` (field names to match the existing payloads' style).
- **Writes** print nothing on success (quiet by default). `--json` on a write prints the same object as a read, after the change.
- `--append` adds the text as given. It does not insert a newline. Open question 4 covers whether it should.
- An open editor shows a CLI write immediately. A CLI write is one undoable change in the editor's undo stack, if the text view allows it cleanly (open question 6).
- The text is UTF-8. Invalid UTF-8 on stdin is a usage error, nothing sent.

### Target resolution for this verb

1. `--pane <id>`: that Pane. Unknown id, or a Pane that is not a Scratch Pad, exits 4 with a message naming the Pane's kind.
2. Otherwise the Session from `--session`, then `BATTY_SESSION_ID`, then the focused Session. In that Session, use its Scratch Pad if there is exactly one.
3. No Scratch Pad in that Session: exit 4 (open question 1).
4. More than one: exit 4 and list their ids (open question 2).

`BATTY_PANE_ID` is deliberately not consulted (see "Catch" above). Hidden Scratch Pads still count: hiding a Pane keeps its text (#0571 acceptance 6).

## Open questions (for the user)

1. **No Scratch Pad open.** Exit 4 with "no Scratch Pad in this Session" (and a hint to run `batty pane split --view scratch-pad`), or have writes create one? *Recommendation:* exit 4 for reads; for writes, exit 4 too, and keep creation explicit through `pane split --view scratch-pad --unique`, which already exists and prints the id. A `--create` flag on writes is a possible later addition.
2. **Several Scratch Pads in one Session.** Exit 4 listing ids, or pick one (most recently focused Scratch Pad, or the focused Pane if it is one)? *Recommendation:* use the focused Pane if it is a Scratch Pad, else exit 4 listing ids. Never guess between several.
3. **Size limit.** XPC payloads are `Data` with no cap in the current payload types. A runaway `cat bigfile | batty pane text --set -` would put megabytes in an `NSTextView`. *Recommendation:* cap the stored text (e.g. 1 MiB UTF-8) in `ScratchPadPaneContent`. A CLI write over the cap exits 4 and changes nothing; it never truncates silently. Should the editor enforce the same cap on paste?
4. **Append and newlines.** Should `--append` add a newline first when the existing text doesn't end in one? *Recommendation:* no; append verbatim. Scripts that want a line add `\n` themselves. Alternatively add `--line` later.
5. **Noun.** `batty pane text` keeps the approved noun set. A sixth noun such as `batty scratch read|write` reads more naturally but needs the same deliberate approval `project` had (`docs/batty-cli-design.md` §1.1). *Recommendation:* `pane text`.
6. **Undo of CLI writes.** Should a CLI `--set` be undoable with Cmd-Z in the editor? It is the user's only way back if a script overwrites their draft. *Recommendation:* yes, one undo step per write, if the implementation can do it without view-driven state writes (`docs/swiftui-observation-rules.md`).
7. **`batty list` / `session info`.** Should the topology payload expose a Scratch Pad's text length (not the text)? *Recommendation:* no for now; `pane text --json` is the way to read it.
8. **Shell injection.** The CLI only moves text in and out of the Scratch Pad; it never sends it to a terminal. Confirm that a "write and run" or "send to terminal" verb stays out of scope (it is #0571 open question 1's territory).

## Acceptance criteria (user-verifiable from a terminal Pane in Batty Beta)

Set up: `P=$(batty-beta pane split --view scratch-pad --unique)`.

1. `printf 'git log --oneline -5' | batty-beta pane text --set -` makes the open Scratch Pad show exactly `git log --oneline -5`.
2. Edit the text in the Scratch Pad by hand. `batty-beta pane text` prints the edited text exactly, with no trailing newline added. `batty-beta pane text --json | jq -r .text` prints the same.
3. `batty-beta pane text --append ' | cat'` adds ` | cat` to the end. `batty-beta pane text --clear` empties it, and `batty-beta pane text` then prints nothing and exits 0.
4. `batty-beta pane text --pane "$P" --set 'echo hi'` targets that Pane explicitly. `--pane` with a terminal Pane's id (e.g. `$BATTY_PANE_ID`) exits 4 and says it is not a Scratch Pad.
5. With no Scratch Pad in the Session, `batty-beta pane text` exits 4 with a message saying so. With two, it exits 4 and lists both ids (or follows whatever open question 2 settles).
6. `batty-beta pane text --set` with no value, or `--set x --clear` together, is a usage error, and the Scratch Pad is unchanged.
7. Close the Scratch Pad, open a new one: `batty-beta pane text` prints nothing. Quit and relaunch Batty Beta: no Scratch Pad text survives, and no file holds it.
8. `batty-beta capabilities --json` lists `pane text` with its options and modes.
9. `batty-beta pane text --help` says the text is not saved.
