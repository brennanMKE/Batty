# 0543 — A corrupt projects.json shows "No Projects yet", and a partly loaded or newer-version file shows no message at all

| | |
|---|---|
| **Status** | open |
| **Module** | Projects |
| **Platform** | macOS |

## Description

When `projects.json` can't be fully loaded, Batty doesn't say so. A corrupt file shows "No Projects yet" with a New Project… button in the picker and the Project Editor, which is false and invites a save. A partly loaded file or a newer-version file shows its Projects with no message, so a Project can be missing with nothing to explain why.

**Low severity: a wording and UX issue, not a blocker for 1.3.5.** The first save copies the original to `projects.json.bak` before replacing it, and the default paths never lose it. Two narrow exceptions are below. Nobody has reported this; the #0542 review raised it.

Related: #0471 (the store and its `.bak` rule), #0542 (adds an accurate message for a file that can't be read at all, not yet on `main` when this was filed). This issue covers the states #0542 leaves alone, which now read differently from its read-failure state.

## What each state tells the user

Measured against the real `ProjectStore` and `ProjectPickerModel` from `issue/0542` at `5be0c9a2`, using temp directories (see "How this was checked"). The Message column is the picker's `emptyState`, plus reading the views.

| State of the file at load | `projects` | Message | After the first save |
|---|---|---|---|
| Read fails (#0542) | empty | "Batty Can't Read Your Saved Projects", with the path. Writes are refused. | Nothing changes |
| Not valid JSON | empty | **`.noProjects`: "No Projects yet"** | Original in `.bak`; the file holds only the new Project |
| Valid, but every Project is dropped | empty | **`.noProjects`** | Not run; same load path as the row below |
| One Project dropped by `LossyProject` | the rest | **None.** The list looks complete. | Original in `.bak`. The next launch loads a healthy file, so the dropped Project is only in `.bak`, with no message then either. |
| Newer `version`, Projects decode | all of them | **None** | Original in `.bak`. The new file isn't version 99 and has lost an unknown top-level key. |
| Newer `version`, every Project dropped, or the `projects` key missing | empty | **`.noProjects`** | Not run |

The last row is the misleading case for a downgrade: a file written by a later Batty says "No Projects yet", not that it needs a newer Batty.

Nothing in `BattyKit/Sources` outside `ProjectStore.swift` reads the dropped count, the newer version, or `backupFileName`. The only record is `logger.error`, so a user can't learn that `.bak` exists.

### Other silent effects, from reading the code only

- **`batty project list`** on a corrupt file prints "No saved Projects." (`Sources/batty/ProjectCommand.swift:97`). `projectFileProblemForXPC` reports only the read-failure state.
- **Sharing stops.** `mergeRemote` skips while the file isn't fully loaded (`ProjectStore.swift:284`) and logs only; `syncError` isn't set, so the picker's caption stays empty.
- **`setShared`, `recordOpen` and `recordApproval`** change memory only in this state and are lost at quit unless a save follows. #0492 records this for `recordOpen`, with no message to the user.

## Limits of the backup

"No data is lost" holds for one cycle in one running app. These two aren't wording problems, but any new message that mentions `.bak` has to be true given them. Both were reproduced:

1. **A second bad load replaces the first backup.** Corrupt file, save, file corrupted again, save: `.bak` went from `FIRST-ORIGINAL` to `SECOND-CORRUPT`. `writeFile` overwrites without checking (`ProjectStore.swift:400`). #0471's Gotchas already notes this. It matters more for a partly loaded file, whose dropped Project lives only in `.bak` after the first save.
2. **Restoring the file by hand while Batty runs loses the restore.** Corrupt file loaded, valid file written over it, `retryLoadIfNeeded()`: `projects` stayed empty, because a decode failure counts as `.loaded` and `reconcileWithFile` returns early (`:378`). The next save left only the new Project in `projects.json` and the old garbage in `.bak`, so the restored Project was in neither. Telling a user to restore from `.bak` is unsafe unless they quit first, or the store re-reads.

Whether to change these here or file them separately is a planning decision.

## Expected behavior

- A corrupt file doesn't say "No Projects yet". It says the saved Projects couldn't be loaded, and what happens to the original on the next save.
- A partly loaded file says that some Projects couldn't be loaded.
- A newer-version file says it came from a newer version of Batty.
- These states stay distinct from #0542's message, because writes aren't refused here and that message's "Your Projects haven't been changed" and "open this window again" wouldn't be accurate: reopening the window doesn't re-read a file that was read successfully, even if it failed to decode.

## Actual behavior

See the table above.

## Steps to reproduce

Use a temp `projects.json` (`BATTY_UI_TEST_PROJECTS_FILE`, as the Projects UI tests do), never a real one.

1. Write `{ not json` to the file and open the Open Project picker. It shows "No Projects yet".
2. Write a valid file with two Projects, one with a relative `rootPath`, and open the picker. It shows one card and no message.
3. Write a valid file with `"version": 99` and open the picker. It shows the cards and no message.

## Notes

### Code locations

On `issue/0542` at `5be0c9a2`; re-check once #0542 lands.

- `Model/ProjectStore.swift`: `:442` keeps the bytes on a dropped Project or newer version, `:445` on a decode failure, and both report `.loaded`. `:159` `unreadableFilePath` covers only `.readFailed`. `LossyProject` is at `:58`.
- `Model/ProjectPicker.swift:239-245`: `emptyState`.
- `Views/ProjectPickerView.swift:287` and `Views/ProjectEditorView.swift:230`: "No Projects yet".

On `main` at `85029bb7`, the same text is at `ProjectPickerView.swift:277` and `ProjectEditorView.swift:217`, and the load results at `ProjectStore.swift:354` and `:357`. `main` has no read-failure message yet.

### Depends on #0542

This builds on the empty-state shape #0542 adds (`ProjectPickerEmptyState.unreadableFile`, `ProjectEditorEmptyState`), so work it after #0542 lands.

### How this was checked

A throwaway Swift Testing probe, run with `swift test --filter LoadStateProbe` in a `git archive issue/0542` copy in a scratch folder, not committed. Each case wrote `projects.json` into its own `FileManager.temporaryDirectory` folder and passed that URL to `ProjectStore(fileURL:)`. No real Application Support folder or `projects.json` was touched. Existing `ProjectStoreTests` already pin the `.bak` contents (`corruptFileLoadsEmptyIsNotOverwrittenUntilSaveThenKeptAsBak`, `oneBadProjectDoesNotDropTheOthersAndOriginalIsBackedUp`, `newerVersionFileIsPreservedAsBakOnFirstSave`), but none pins what the user is told.

### Not verified

- The app wasn't launched, so the views were read and not seen. The steps to reproduce haven't been run in the app.
- The `batty project list`, `mergeRemote`, `setShared` and `recordApproval` effects above were read, not run. No sync backend was used.
- Unknown fields inside a Project on a newer-version save weren't tested, only an unknown top-level key. They're probably lost too, since the file is re-encoded from `Project`.
