## Description

The user chose **Design D**: "I like design D. It is simple and easy to read. We should have a clear concept for Remdiners and Bell Feed notifications. There are unread, read and then the option to clear all read items." Design D adds a **Reminders** toolbar button, just left of the bell, that opens a popover listing **Due** (fired) and **Upcoming** (pending) Reminders. It also offers New Reminder… and per-row actions. Spec: `0637/spec.md`, Part 2, "What D, E and F share" and "Option D". Mockup: `0637/option-D.html`.

This is **step 4 of 4** (sequence table in #0637). It depends on:

- **#0639**: the fired-Reminder list with unread / read state, and its store API (Mark All Read, Clear Read, Done, Remind Again);
- **#0635**: the Quick Reminder bar must not open over another sheet, because Edit and New Reminder… present the bar from this popover;
- **#0636**: tooltips built from the live binding, a pattern this button copies.

The user has accepted one new toolbar button for this, which relaxes the standing "no new toolbar buttons" rule for this button only.

**Override of the spec.** The spec says fired Reminders have "no seen / unseen state … and there is no Clear All". The user replaced that with the shared concept in #0638: fired Reminders are **unread** or **read**, and the list offers **Clear Read**. Where this issue and the spec disagree, this issue wins.

## Goal

A visible home for Reminders. At a glance the user can see what is due and what is coming, act on either, and set a new one. Fired Reminders follow the same unread / read / Clear Read rules as the Bell Feed.

## Acceptance criteria

### Toolbar button

- `RemindersToolbarButton` gets its own view struct, like `BellFeedToolbarButton` (`Views/SessionDetailView.swift:404-432`), so a Reminder change re-renders only this button. It sits in the same `ToolbarItemGroup` (`:203-233`), immediately left of the bell. The order is Split Horizontally, Split Vertically, Reminders, Bell Feed.
- Glyph, rendered hierarchically. The names are in `Resources/SFSymbolNames.txt:401-412`:

  | State | Symbol | Colour |
  |---|---|---|
  | No pending and no unread fired Reminder | `alarm` | toolbar tint |
  | At least one pending, or only read fired ones | `alarm.fill` | toolbar tint |
  | At least one **unread** fired Reminder | `alarm.waves.left.and.right.fill` | accent |

  An unread fired Reminder wins over pending. No count is drawn on the button. A fired Reminder never changes the bell (#0639).
- Tooltip, built from the live binding (#0636's pattern): "Reminders (⌥⌘R)", followed by the state, for example "· 2 upcoming, next at 3:45 PM" or "· 1 due, 2 upcoming".
- Accessibility: identifier `toolbar.reminders`, label "Reminders", and a value of `none`, `2 upcoming`, `1 due, 2 upcoming` or `1 unread due, …`. The label stays "Reminders" whatever the state.

### Popover (360 x 420, the Bell Feed's size)

```
Reminders                              + New Reminder…
------------------------------------------------------
Due  1                        Mark All Read  Clear Read
 ● (alarm) Check the deploy finished…        2 min ago
           api · due 3:31 PM
           [Remind Again in 15 Minutes] [In 1 Hour] [Done]
Upcoming  2
 (clock) Check on ./build.sh unit            in 12 min
         Session 1 · 3:45 PM              (pencil) (x)
 (clock) Review the release notes…            tomorrow
         Batty · tomorrow at 9:00 AM
```

- **Sections.** **Due** comes first: fired Reminders, newest fired first. **Upcoming** follows: every `SessionRuntime.reminder` across `store.windows`, soonest first (`SessionReminder.fireDate(calendar:)`, `Model/SessionReminder.swift:53`). A section with no rows is not shown. Upcoming is a computed list with no new stored state.
- **Due rows.** An accent `alarm` glyph. An **unread dot** (accent) when unread, none when read, the same dot the Bell Feed uses (`Views/BellFeedView.swift:250-255`). Line 1 is the text (`displayText(sessionTitle:)`), up to 3 lines, with the relative time trailing. Line 2 is `<Session> · due <time>` (`ReminderFormat.dueLine`).
- **Upcoming rows.** A `.secondary` `clock` glyph. Line 1 is the text, one line, tail-truncated, with the relative time trailing (`ReminderFormat.relativeLine(due:now:)`, `Model/SessionReminder.swift:205`). Line 2 is `<Session> · <clock phrase>`. They have no unread dot and never count as unread.
- Relative times are drawn inside `TimelineView(.everyMinute)`, so nothing writes observed state per minute.
- **Due section header:** **Mark All Read**, shown while an unread Due row exists, and **Clear Read**, shown while a read Due row exists. They call #0639's store API. Neither touches Upcoming or the Bell Feed.
- **Row actions:**

  | Action | Due row | Upcoming row |
  |---|---|---|
  | Open Session (visits it: selects the Session, keeps its focused Pane and active Tab) | click, Return; the row leaves the list | click, Return |
  | Remind Again in 15 Minutes / 1 Hour | inline buttons on hover or selection, context menu, `R` = 15 min; the row leaves and the new Reminder shows in Upcoming | — |
  | Done | inline button, context menu, Delete; removes the row | — |
  | Edit Reminder… | — | pencil on hover, context menu, `E` |
  | Cancel Reminder | — | x on hover, context menu, Delete |

  - Remind Again is disabled when the Session has a newer pending Reminder (#0633's rule).
  - Edit closes the popover, makes the Session's Window key, then calls `ReminderActions.openBar(for:in:)` (`Views/ReminderMenu.swift:31`) without changing the selected Session. Cancel calls `store.cancelReminder(forSessionID:)` with no confirmation, as the menu does.
- **Header: New Reminder…** closes the popover and opens the Quick Reminder bar for the Window's selected Session (`ReminderActions.openBar(in:)`, `Views/ReminderMenu.swift:37`). The bar opens in edit mode when that Session already has a pending Reminder. Disabled with no selected Session.
- **Empty state:** `ContentUnavailableView` with the `alarm` glyph, "No Reminders", "Set one on a Session to be brought back to it later.", and a "New Reminder for <Session>…" button showing ⇧⌘R.
- **Keyboard:** Up and Down move across Due, then Upcoming, as one selection. Return, Escape, `E`, `R` and Delete work as in the table. Initial selection: the first unread Due row, else the first Due row, else the first Upcoming row. The List's type-select must not swallow `E` and `R`; verify in the VM.
- **Opening the popover marks nothing read.**
- **Popover writes are event-origin only** (clicks and key presses), per `docs/swiftui-observation-rules.md`. The popover is dismissed before the bar's sheet is presented.
- **Toolbar overflow:** not verified by the spec. Check what the bell's popover does today when the toolbar overflows in a narrow Window, and make Reminders match it.

## Root cause

Feature work. After #0639, fired Reminders lived in `FiredReminderStore` with unread / read state and a public store API (Mark All Read, Clear Read, Done, Remind Again, Open Session), but nothing in the UI listed them or the pending Reminders. ## Fix

Implemented the plan as written, with the primary approach on both VM-dependent branches.

- **`Views/RemindersListModel.swift`** (new, pure values): `RemindersRowID`, `RemindersSessionInput`, `RemindersDueRow`, `RemindersUpcomingRow`, `RemindersToolbarGlyph`, `RemindersListModel` and `RemindersPopoverToggle`. It holds every rule the unit tests pin: Due newest first (index tie-break), Upcoming soonest first with an unresolvable date last, `canRemindAgain` (#0633's rule), the glyph, the accessibility value, the initial selection, wrapping arrow movement and the selection after a removal. `current(in:)` reads the store and writes nothing.
- **`ReminderFormat.firedAgo` and `dueAtLine`** for the Due row's trailing time and line 2.
- **`ShortcutAction.toggleReminders`** ("Show Reminders", ⌥⌘R), appended after `remindMe`. `.battyToggleReminders` is posted from `BattyShortcuts.run`, the Window → Show Reminders menu item (after Toggle Bell Feed) and the Command Palette.
- **`ToolbarHelpText.reminders`**: "Reminders (⌥⌘R)", then " · N due[, M upcoming]" or " · M upcoming, next <phrase>".
- **`Views/RemindersToolbarButton.swift`** (new): its own view struct, between the second split button and the bell. Glyph, hierarchical rendering, accent only when ringing, live tooltip, `toolbar.reminders` with label "Reminders" and the model's value, and the popover. Nothing else was added to the toolbar.
- **`SessionDetailView`**: `@State remindersShown` and an `.onReceive(.battyToggleReminders)` guarded by `RemindersPopoverToggle.shouldHandle(isKeyWindow:isShown:)`.
- **`Views/RemindersView.swift`** (new): the 360 × 420 popover. It has a header with New Reminder…, the empty state, and Due / Upcoming `Section`s with `ReadStateHeaderActions` (prefix `reminders`) in the Due header. Rows have hover or selection actions, context menus, accessibility identifiers, values, labels and named actions. Time text sits inside `TimelineView(.everyMinute)` and reads `reminderScheduler.now`. Keys are on the `List`: Up, Down, Return, Escape, Delete, and `E` / `R` through `onKeyPress(characters:)`. `onAppear` sets only the view's own selection, and nothing marks anything read.
- **`ReminderActions.openBarFromList(sessionID:store:)`**: resolves the owning Window and calls `makeKeyAndOrderFront` when it isn't key. It then opens the bar with the attached-sheet gate and never touches the selection.
- **Primary branches shipped, fallbacks not used:**
  - `E` / `R` go through `onKeyPress(characters:)` on the `List`. The fallback, if the VM shows type-select swallowing them, is two hidden zero-size `Button`s with `.keyboardShortcut("e"/"r", modifiers: [])` in the popover.
  - Popover then sheet: `onDismiss()` runs, then the bar write, in the same click or key handler. The fallback, if the bar fails to present or take focus, stores the work in `@State afterDismiss` on `RemindersToolbarButton` and runs it from the popover content's `.onDisappear`. Never a `Task` hop.

**Round 3 (after the VM run on `c30c739f`; reverted in round 4):**
- **The List no longer owns the selection.** `List(selection: $selection)` became `List { … }`. `RemindersView`'s `@State selection` is the only writer, and each row's `listRowBackground` draws the highlight from it (a rounded `Color.primary.opacity(0.1)`; needs the user's eye). Because of the breadth (2 new views, 1 new model, about 8 edited sources, 4 docs, 4 unit-test files and a new UI-test class), dispatch the implementer at **medium** effort rather than low.

### Files and approach

1. **New `Views/RemindersListModel.swift`**: pure values, no view types. Every rule the unit tests pin lives here, as `ReminderBarModel` does for the bar.
   - `nonisolated enum RemindersRowID: Hashable, Sendable { case due(UUID) /* FiredReminder.id */; case upcoming(UUID) /* Session id */ }`
   - `nonisolated struct RemindersSessionInput: Equatable, Sendable { id: UUID; title: String; reminder: SessionReminder? }`
   - `nonisolated struct RemindersDueRow: Equatable, Sendable`: `fired: FiredReminder`, `sessionTitle`, `canRemindAgain: Bool`, `id: RemindersRowID { .due(fired.id) }`, `text` (`fired.displayText(sessionTitle:)`), `isUnread` (`!fired.seen`).
   - `nonisolated struct RemindersUpcomingRow: Equatable, Sendable`: `sessionID`, `sessionTitle`, `reminder: SessionReminder`, `dueAt: Date?`, `id: .upcoming(sessionID)`, `text` (`reminder.displayText(sessionTitle:)`).
   - `nonisolated struct RemindersListModel: Equatable, Sendable`:
     - `init(fired: [FiredReminder], sessions: [RemindersSessionInput], calendar: Calendar)`. `sessions` is every Session of every Window, in Window order, then Sidebar order.
     - **Due:** `firedAt` descending. Ties keep the store's order (sort by `(firedAt, index)` with the enumerated index, because Swift's `sort` is not stable). The title comes from `sessions`, falling back to `String(localized: "(closed)")` as the Bell Feed does. `canRemindAgain` is `session.reminder == nil || session.reminder?.id == fired.id`, which is #0633's rule, the same one `remindAgain` applies.
     - **Upcoming:** every session with a non-nil `reminder`, ordered by `fireDate(calendar:)` ascending. A nil date (an unresolvable wall clock) sorts last, and ties keep input order.
     - `rowIDs: [RemindersRowID]`: Due, then Upcoming. `isEmpty`, `unreadCount`, `readCount` (Due only) and `upcomingCount`.
     - `glyph: RemindersToolbarGlyph` (`enum { case idle, filled, ringing }`, with `systemImage` = `alarm` / `alarm.fill` / `alarm.waves.left.and.right.fill`, and `usesAccent` true only for `.ringing`). The rule: `unreadCount > 0` gives `.ringing`. Otherwise `upcomingCount > 0 || readCount > 0` gives `.filled`. Otherwise `.idle`.
     - `accessibilityValue: String`. Due part: if `unreadCount == 0`, "N due". If every Due row is unread, "N unread due". If only some are, "N due, U unread". Then ", M upcoming" when there are upcoming rows. With nothing at all, "none". So the value contains "unread" exactly when an unread fired Reminder exists.
     - `initialSelection: RemindersRowID?`: the first unread Due row, else the first Due row, else the first Upcoming row.
     - `moved(from: RemindersRowID?, by delta: Int) -> RemindersRowID?`: wraps across `rowIDs` like `BellFeedView.moveSelection` (`Views/BellFeedView.swift:131-137`). A nil or missing `from` with `delta > 0` gives the first row; with `delta < 0`, the last.
     - `static func selection(_ current: RemindersRowID?, after previous: [RemindersRowID], in next: RemindersListModel) -> RemindersRowID?`: keeps `current` if it still exists. Otherwise it takes the row now at `current`'s old index, clamped to the last row, else nil. Repeated Delete then walks down the list.
     - `@MainActor static func current(in store: AppStateStore) -> RemindersListModel` builds the inputs from `store.firedReminders.items`, `store.windows.flatMap(\.sessions)` and `store.reminderScheduler.calendar`. It writes nothing.
   - `nonisolated enum RemindersPopoverToggle { static func shouldHandle(isKeyWindow: Bool, isShown: Bool) -> Bool { isKeyWindow || isShown } }`. A Window acts on `.battyToggleReminders` when it is key or when its own popover is showing, which is the case where the popover window is key (see Premises). A transient popover closes when another Window is clicked, so two Windows never both act.
