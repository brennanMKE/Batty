## Description

Tier 1 localization target. Japan is Apple's #2 market by spend and has a large native-macOS developer community; Batty already invests in CJK Romaji IME for terminal input, so a Japanese UI is the obvious complement.

Depends on `#0107` — populate the `ja` locale in the String Catalog with translations for every user-facing key after the foundation pass lands.

## Acceptance criteria

- Every key in `Localizable.xcstrings` has a non-empty `ja` translation, reviewed by a native speaker.
- Launching Batty with macOS Language & Region set to Japanese (or with `-AppleLanguages '(ja)'` at the scheme level for development) shows the full UI in Japanese with no English fallthrough on menus, Settings, alerts, About, or Sparkle prompts.
- Visual sweep of Settings, the bell feed popover, and the paste / quit / busy-tab alerts confirms no clipping or wrapping regressions — Japanese text is often shorter than English but Settings labels with technical terms can run longer.
- `## Files changed` in the resolution should list the `.xcstrings` diff (one file).

## Notes

- Product name "Batty" stays as-is in Latin script — use `Text(verbatim:)` for that one literal.
- Date / time formatting in the bell feed should already pick up the system locale via `Date.FormatStyle` once `#0107` lands; verify Japanese-style dates render correctly in the popover.
- Keyboard shortcut display strings (e.g. "Cmd-Shift-N") translate the modifier names in some apps; standard macOS practice is to keep the glyphs (⌘⇧N) — verify this matches what Terminal.app does in Japanese.
- Sparkle's update prompts already ship with Japanese — no custom strings needed there.

## Root cause

The `ja` locale was empty after `#0107` landed — that foundation pass only populated English (with a tiny `de` smoke-test stub for `Quit Batty?` / `Quit` / `Cancel`). Every key in `Localizable.xcstrings` needed a Japanese translation added before Japanese users would see any localized UI.

## Fix

Populated `ja` translations for every key currently in the catalog:

- `Batty` — passes through as the literal Latin-script brand name, matching the catalog's "never translate the product name" convention.
- `Quit Batty?` → `Batty を終了しますか?` (Apple's standard quit-alert phrasing, e.g. Terminal.app's "ターミナルを終了しますか?").
- `Quit` → `終了`. `Cancel` → `キャンセル`. Both match the macOS-wide Japanese terminology used in System Settings and standard `NSAlert` buttons.
- `Paste %lld lines?` (plural) → `%lld 行をペーストしますか?` for both `one` and `other`. Japanese has no grammatical singular/plural distinction, so both variants carry the same form.
- `There %lld open terminal(s).` (plural) → `ターミナルが %lld 個開いています。` for both variants. The counter 個 is the neutral general-purpose counter; ターミナル is the established katakana form Apple uses.
- `%lld unseen bell event(s)` (plural) → `未読のベルイベント %lld 件` for both variants. 件 is the standard counter for events / notifications.

Format specifiers (`%lld`) are preserved verbatim.

## Files changed

- `Batty/Localizable.xcstrings` — added `ja` localizations (4 simple keys + 3 plural-aware keys with `one`/`other` variants each).

## Gotchas

- **LLM-authored, not native-speaker reviewed.** Per the acceptance criteria, a native-speaker review pass is still ideal before this ships to Japanese users. The translations follow Apple's published Japanese terminology (Terminal.app, System Settings, the macOS Human Interface Guidelines' Japanese references) and use widely-accepted katakana renderings (ペースト, ターミナル, ベルイベント), but tone choices and counter selection (個 for terminals, 件 for events) are judgment calls a native reviewer may want to revisit.
- **Politeness level: です/ます polite form throughout**, matching macOS system UI conventions. Alert questions end with か? (the half-width `?` form), which matches Apple's localized alerts on macOS 26 in Japanese.
- **Plural variants carry the same string** because Japanese has no grammatical number. The catalog still requires both `one` and `other` to be populated, but the rendered output is identical regardless of count.
- **`knownRegions` in `Batty.xcodeproj/project.pbxproj` still does not list `ja`.** The `#0107` resolution noted that `xcstringstool` emits `ja.lproj/Localizable.strings` and `Localizable.stringsdict` correctly anyway — confirmed locally: building this branch produces both files in the `.app`. Registering `ja` in the Xcode Localization UI is only needed to make the catalog editor render the column.
- **Verified by build, not by runtime.** `xcodebuild -scheme Batty -destination 'platform=macOS' build` passed (with `CODE_SIGN_IDENTITY=-` / `CODE_SIGNING_REQUIRED=NO` / `CODE_SIGNING_ALLOWED=NO`, mirroring the foundation subagent's environment). The compiled `ja.lproj` resources were inspected with `plutil -p` to confirm the catalog round-trip. A full runtime visual sweep under `-AppleLanguages '(ja)'` — the acceptance criterion for no clipping or wrapping regressions in Settings, the bell feed popover, and alerts — has not been done and is part of what the user needs to confirm before this moves from `resolved` to `closed`.
