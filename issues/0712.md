# 0712 — Saving the current Session as a Project leaves that Session without the Project's icon, color, opacity and background images

## Description

User report (2026-11-21), verbatim: "Create an new issue so that when a session is created from the curent session it applies the changes which includes the icon, color, opacity and background images. This should go into a 1.4.3 release as a bug to the 1.4.0 release."

When the user saves the Session they are in as a Project (Save Session as Project… / Save as Project… / Save as New Project…, then Save in the Project Editor), the Project is stored but the Session they saved from stays an ordinary Session. It never becomes backed by the new Project, so whatever the user chose in the editor before clicking Save (the Project's icon, its color, its background image and opacity, and the Pane and Tab backgrounds) does not show on that Session. It shows only on a Session opened from the Project later. The Session also gets no Edit Project… or Update "<name>"… items in its Sidebar menu (#0653), and Open Project focuses nothing and opens a second Session beside it.

This is a bug fix for 1.4.3, filed against 1.4.0: it goes to `main` first through the normal issue workflow, then `git cherry-pick -x` of the squash commit onto `release/1.4` (AGENTS.md, Release branches). Part of the fix is main-only; see "Release split".

## Steps to reproduce

1. Open a plain Session (not from a Project), with two Panes, one with two Tabs.
2. Sidebar row → Save as Project… (or Projects → Save Session as Project…).
3. In the Project Editor, pick a different symbol and color, set a Project background image with image opacity 40% and terminal opacity 80%, and give one Pane and one Tab their own background image.
4. Click Save.
5. Look at the Session in the Sidebar and its Panes and Tabs. Right-click its Sidebar row.
6. Open the Project from the Open Project picker.

## Expected behavior

After Save, the Session the draft was captured from is a Session of the saved Project, exactly as if it had been opened from it, without recreating terminals or touching running processes:

1. Its Sidebar row shows the Project's symbol (legacy or custom SF Symbol) and color (nearest palette entry for a custom hex), and takes the Project name as its pinned title, as `WindowRuntime.addProjectSession` does.
2. It shows the Project's background (image, fit, position, image opacity, terminal opacity), Theme and mute.
3. Each Pane and Tab shows the Project's background for its slot, including a value the user changed in the editor before saving, and the image path switches to the Project's copy (same image) so a later Session cleanup of its own copy can't blank it.
4. Its Sidebar menu shows Edit Project… and Update "<name>"…; Open Project with the default mode focuses it instead of opening another Session; later Project Editor saves reach it through `applyProjectSave`, including the #0702 Pane/Tab background rules.
5. Missing images and images still syncing are marked as at open (`projectBackgroundImageProblem`, `pendingProjectImage`, `pendingImage`, `pendingTabImage`, `requestTabImages`).

## Actual behavior

Only the stored Project changes. The Session keeps its plain Sidebar icon, its previous color and title, and its own backgrounds; edits made in the editor before Save never appear on it. `session.projectID` stays nil, so nothing that keys on it (Sidebar Edit Project, Update, Open Project's focus-existing, `applyProjectSave`) sees the Session.

## Current state (checked against `main` at `99737d19` and `release/1.4` at `76604b24`)

- **The only writer of `projectID`.** `SessionRuntime.projectID` (`Runtime/SessionRuntime.swift:75`, `internal(set)`) is written only in `WindowRuntime.addProjectSession(_:tree:background:)` (`Runtime/WindowRuntime.swift:355-382` on main, `:362` the write; `:355`/`:362` on release/1.4). That function also sets `projectSymbol`, `projectSymbolName`, `themeOverride`, `setBackgroundOverride`, `notificationsMuted`, `setSessionColor`, hidden Panes, focused slot and `isPaneListExpanded`. It builds a new `SessionRuntime`, so it can't be reused as-is on a live Session.
- **UI save path.** `SaveSessionAsProject.begin` (`Views/SaveSessionAsProject.swift:165`) builds a draft with `draft(for:destination:store:)` (`:24`) and opens the Project Editor on it. The draft (`Model/ProjectDraft.swift:11`) carries no reference to the Session it came from. Save is `ProjectEditorViewModel.save()` (`Model/ProjectEditorViewModel.swift:838`), which ends with `projectSaved(previous, stored)` (`:872`), wired to `store.applyProjectSave(previous:saved:)` (`Views/ProjectEditorWindowController.swift:90`, same on release/1.4). `applyProjectSave` only touches Sessions `where session.projectID == saved.id` (`Runtime/AppStateStore.swift:1726` main, `:1675`ff release/1.4), so a new Project reaches no Session.
- **Update is offered only to linked Sessions.** `SaveSessionAsProjectMenuModel.make` (`Model/SaveSessionAsProjectMenu.swift:20`) gives an update target only when `projectID` names a stored Project, and the Sidebar's Edit Project…/Update items depend on it (`Views/SessionSidebarView.swift:571-579`). A linked Session using Save as New Project… keeps its old link; after this fix it should move to the new Project.
- **CLI/MCP path (main only).** `writeProjectForXPC` (`Runtime/AppStateStore+ProjectWriteXPC.swift:24`) handles `batty project create --from-session` / `project_create` and `project edit --from-session`. It captures with `SaveSessionAsProject.draft` (`:34`), stores, and calls `applyProjectSave` only when editing (`:116-119`). The created Project never links the Session; an edit from an unlinked Session updates other Sessions of that Project but not the source.
- **Pane/Tab background seeds (#0702).** `ProjectTreeBuilder.build` stamps each terminal Pane and Tab with `projectBackgroundSeed` (`Model/ProjectTreeBuilder.swift:185`, `:187`), and `applyProjectSlotBackgrounds` (`Runtime/AppStateStore+ProjectSlotBackgrounds.swift:31`) uses those seeds. A captured Session has no seeds, so even after a link, Pane/Tab edits wouldn't reach it. The capture already maps slots to runtime ids: `SessionProjectCapture.paneIDs` / `tabIDs` (`Model/SessionProjectCapture.swift:38-40`), used by `captureLevelBackgrounds` (`Views/SaveSessionAsProject.swift:100`).
- **Image paths.** Save as Project copies each image into the Project background folder (`projectBackgrounds.adopt(path:)`), so the Project's paths differ from the Session's for the same image. `applyProjectSlotBackgrounds`'s `sameBackground` compares by digest; the Session-level `seedProjectBackground` (`AppStateStore.swift:1751`) writes the Project's value unconditionally.

## Approach notes for the planner

- **One owner.** Extract the "make this Session a Session of this Project" part of `addProjectSession` (projectID, symbol, symbol name, title + `titleOverride`, color, Theme, background, mute) into a single method that both `addProjectSession` and the save paths call, e.g. `AppStateStore.linkSession(_:to:capture:)` or a `WindowRuntime` method plus the store's background checks. Don't copy the field list a second time. Layout-only steps (hidden Panes, focused slot, Pane list expanded) stay in `addProjectSession`: the live Session already has its layout.
- **Seeds.** At link, stamp `projectBackgroundSeed` on each Pane/Tab from the capture's `paneIDs`/`tabIDs` and apply the saved slot backgrounds the same way #0702 does, so the editor's pre-Save changes land and later saves follow the #0702 rules. If the user changed the layout's shape in the editor before Save, link the Session but leave Pane/Tab seeds nil (as `applyProjectSlotBackgrounds` does for a shape change).
- **Carrying the source.** The editor needs to know which Session a draft came from: a non-Project field on `ProjectDraft` next to `captureNotes` (e.g. `sourceSessionID: UUID?`), set by `SaveSessionAsProject.draft`, cleared by "Copy from current Session" and by switching to another Project. On Save, link it if that Session still exists; if it was closed, just save. "Copy from current Session" does not link.
- **Observation rules** (`docs/swiftui-observation-rules.md`): the link is an event-origin write from the Save action (`save()` → `projectSaved`) or the XPC handler, never from `body`/`onChange`. Keep writes idempotent (compare before writing, as `applyProjectSave` does).
- **No terminal work.** No Pane, Tab or surface is created or destroyed; startup commands don't run.

## User addition (user, 2026-11-21): agent guidance for --from-session

User, verbatim: "For #0712, note that the agent should be told it can select an icon from Apple's SF Symbols. It can also try to derive a color from the current folder. Maybe it has artifacts which would indicate a primary accent color. It is also nice to set a background image for the session so the agent could pick one an set the opactity to 30% by default."

This is part of the **main-only (1.5.0) CLI/MCP work**: `batty project create --from-session` and MCP `project_create` exist only on `main` (#0700). None of it is cherry-picked to `release/1.4`. With the core fix (acceptance 6), whatever the agent picks (symbol, color, background, opacity) shows on the live Session immediately, because `--from-session` now links the Session it captured.

### What the agent must be told

Four places, each with the same three suggestions, kept short:

- MCP `initialize` instructions: `MCPInstructions.hints` (`BattyKit/Sources/batty/MCPInstructions.swift:18-35`). Today the only Project hint (`:27-28`) covers `background_list` → `project_create` with `layout-json` → `project_open`, and says nothing about `--from-session`, symbols or color. Add a hint (or extend that one) for `project_create` with `from-session`. `applicableHints` (`:37-47`) checks `argument` against `tools[0]`'s input schema, so use `argument: "from-session"` (the kebab-case property name, as the existing hint uses `layout-json`), and the hint drops out if the flag is renamed.
- The flags' `--help` text in `ProjectWriteOptions` (`BattyKit/Sources/batty/ProjectWriteCommand.swift:21-95`). The MCP tool schema is built from these, so `project_create`'s argument descriptions change with them.
- The shipped agent guidance: `.claude/skills/batty-cli/SKILL.md` (copied into the app as `AgentGuidance/skills/batty-cli/SKILL.md` by the build phase at `Batty.xcodeproj/project.pbxproj:363-373`; `:39` is the current "Save a setup for the user" line).
- The CLI reference: `docs/batty-cli-install.md:75` (`project create` row) and the Project example in `docs/batty-cli-agent-workflows.md` (`:413`).

The three suggestions:

1. **Icon: any SF Symbol.** `--symbol-name <name>` (`ProjectWriteCommand.swift:37-38`) sets `customSymbolName`; `--symbol` (`:34-35`) is the curated `ProjectSymbol` list. The two are exclusive (`:114`). **Premise check:** an unknown `--symbol-name` is *not* rejected. `ProjectWriteBuilder.apply` (`Model/ProjectWriteBuilder.swift:48-51`) stores whatever `ProjectAppearance.resolve(symbol:customName:)` (`Model/ProjectAppearance.swift:70-75`) returns: a trimmed non-empty name that isn't a legacy symbol is kept as-is. Only drawing checks it: `ProjectAppearance.swift:58` falls back to the legacy symbol when `ProjectSymbol.exists(name)` (`Model/ProjectSymbol.swift:186-188`, `NSImage(systemSymbolName:)`) is false. So an agent's typo saves silently and the Session shows a folder. The write runs in the app (XPC), where `ProjectSymbol.exists` works: add a warning to the reply's `warnings` (the request still succeeds, as other soft problems do) when the name doesn't exist on this macOS, and tell the agent to use exact SF Symbols names (as shown in Apple's SF Symbols app, e.g. `hammer.fill`).
2. **Color: derive it from the current folder.** Pass it as `--color-hex #RRGGBB` (`ProjectWriteCommand.swift:31-32`, normalized and mapped to the nearest palette entry by `ProjectAppearance.resolve(color:customHex:)`, `ProjectAppearance.swift:79-83`). Tell the agent where a project's accent color usually lives: an Xcode asset catalog `AccentColor.colorset/Contents.json`; web `<meta name="theme-color">`, CSS custom properties (`--primary`, `--accent`, `--brand`), a Tailwind config's `theme.extend.colors`; a logo or brand file (SVG fill, `brand`/`logo` assets); `package.json`/README badge colors. If nothing is clear, leave color out rather than guess.
3. **Background image.** `background_list` (`batty background list`) first, then one of `--background-set`/`--background-image`, `--background-id`, `--background-digest` or `--background-file` (`ProjectWriteCommand.swift:67-80`), optionally `--opacity`/`--terminal-opacity`.

### "30%" means image opacity 0.3, and it is a decision for the user

"Opacity 30%" maps to the Project background's **`imageOpacity` = 0.3** (`--opacity 30`), not `terminalOpacity` (which stays 1.0 / 100, the current default, `ProjectWriteCommand.swift:88`). `--opacity` is already "The Project image's opacity in percent" (`:85`).

Today a Project image picked through the CLI/MCP with no `--opacity` gets `TerminalBackgroundSettings.firstImageOpacity` = 0.15 (`Settings/TerminalBackgroundSettings.swift:83`) via `pickingImage(path:)` (`:117-120`, called from `ProjectWriteBuilder.swift:83`); replacing an existing image keeps its opacity (`:116`). With `--from-session`, the base is the captured Session's background (`Runtime/AppStateStore+ProjectWriteXPC.swift:34-44`), so if the Session already has an image its opacity is kept, not reset.

**Recommended rule:** a new constant (e.g. `TerminalBackgroundSettings.cliFirstImageOpacity = 0.3`), used only in the CLI/MCP Project write path (`ProjectWriteBuilder.background`), when the request picks an image, gives no `--opacity`, and the base had no image (the same case that gets 0.15 today). Explicit `--opacity` always wins. Replacing an existing image keeps its opacity, as now. The UI's first-image default (Settings, Pane/Tab pickers, Project Editor, all through `pickingImage`) stays 0.15. Pane/Tab backgrounds inside a layout document (`Model/ProjectLayoutDocument+Mapping.swift:178`) stay 0.15 unless the user says otherwise: the user asked about "a background image for the session". Update the `--opacity` help ("A first image gets 15.", `ProjectWriteCommand.swift:85`) and the docs row to say 30.

**Readability conflict — the user must decide before the plan is final.** The 0.15 doc comment (`TerminalBackgroundSettings.swift:80-82`) says it is "the highest tested value that keeps both default Themes above 3:1 over an all-black or all-white image", pinned by `TerminalBackgroundConfigTests.firstImageTintKeepsDefaultThemesReadable` (`BattyKit/Tests/BattyKitTests/TerminalBackgroundConfigTests.swift:364`). The filer's estimate with the upstream TokyoNight colors (Dark: bg `#1a1b26`, fg `#c0caf5`; Day: bg `#e1e2e7`, fg `#3760bf`; the planner must confirm against `BattyThemeCatalog`) at 0.3: TokyoNight over white ≈ 3.9:1 (passes), **TokyoNight Day over an all-black image ≈ 2.2:1 (fails 3:1)**. So 0.3 is readable for typical images on the Dark default but not guaranteed on the Light default. Options:

1. **0.3 as asked** for CLI/MCP-set images (recommended default, since the agent is choosing the image and the user asked for 30%), and the guidance tells the agent to prefer a lower `--opacity` for dark images under a light Theme. Add a readability test at 0.3 that documents which combinations stay above 3:1 rather than asserting all four.
2. 0.3 only when it keeps both default Themes above 3:1 for the chosen image (needs the image's mean luminance; more code).
3. Keep 0.15 and have the guidance suggest `--opacity 30` instead.

## Acceptance criteria

1. Saving a Save Session as Project draft in the Project Editor makes the source Session a Session of the saved Project: `projectID`, symbol, symbol name, color, title, Theme, Session/Pane/Tab backgrounds (image, image opacity, terminal opacity) and mute match what `openProject` would give, including values changed in the editor before Save.
2. Save as New Project… from a linked Session moves the link to the new Project.
3. Cancelling or discarding the draft, or Save after the source Session closed, links nothing and doesn't fail.
4. No Pane, Tab or terminal surface is created or destroyed; Pane and Tab ids are unchanged.
5. After the link, Sidebar Edit Project…/Update show, `openProject(id:)` with `.focusExistingOrOpen` returns the Session with `wasCreated == false`, and a later editor save of a Pane or Tab background reaches it.
6. Main only: `project create --from-session` links the captured Session; `project edit --from-session` links it to the edited Project.
7. `addProjectSession` and the link path share one owner; the per-field list is not duplicated.
8. `./build.sh` and `./build.sh unit` pass on `main`, and again on `release/1.4` after the cherry-pick.
9. Main only: the MCP instructions text (with `project_create` in the catalog), the `project create` help, `.claude/skills/batty-cli/SKILL.md` and `docs/batty-cli-install.md` each tell the agent it can pick any SF Symbol with `--symbol-name`, derive `--color-hex` from accent-color artifacts in the current folder, and pick a background (`background list` then a background flag).
10. Main only (subject to the user's opacity decision): `project create --from-session` with a background image and no `--opacity`, from a Session with no image, saves `imageOpacity` 0.3; an explicit `--opacity` wins; the UI's first-image default stays 0.15; layout-document Pane/Tab images stay 0.15.
11. Main only: an unknown `--symbol-name` still saves but returns a warning naming the symbol.
12. Main only: after acceptance 6, the agent's symbol, color, background and opacity show on the captured live Session without reopening it.
