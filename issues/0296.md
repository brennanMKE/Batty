# 0296 — A Beta build leaves `Active.xcconfig` redirected, so `scripts/build.sh` silently builds the Beta product while reporting Prod

## Description

`Configuration/Active.xcconfig` is a persistent, gitignored side-channel (`.gitignore:2`) that decides which product every build actually produces — it `#include`s either `Prod.xcconfig` or `Beta.xcconfig`, pulled in via `#include? "Active.xcconfig"` at the end of `Configuration/App.xcconfig`. `scripts/set-environment.sh <Beta|Prod>` switches it, and nothing restores it afterward. Once it points at Beta, **every subsequent build resolves Beta settings regardless of which scheme is named** — including `scripts/build.sh`, this project's documented pre-commit gate, which prints `Batty (Prod)` while producing `Batty Beta.app`.

The scheme pre-action does not save you: the `Batty (Beta)` scheme's pre-action runs `set-environment.sh Beta`, but as the header comment in `scripts/build-beta.sh` (review round 1, blocking finding 2) documents, a pre-action runs *after* xcodebuild has already resolved build settings for that invocation — whatever `Active.xcconfig` says at the start of a build is what that build uses, and the pre-action write only takes effect for the *next* invocation. `scripts/build-beta.sh` (#0279) exists precisely to snapshot `Active.xcconfig` on entry and restore it on exit via `trap ... EXIT`.

But `scripts/build.sh` honours a `SCHEME` env var (`scripts/build.sh:17`, `SCHEME="${SCHEME:-Batty (Prod)}"`), so `SCHEME="Batty (Beta)" scripts/build.sh` builds Beta *without* going through `build-beta.sh` — and leaves `Active.xcconfig` pointed at Beta indefinitely. Every `scripts/build.sh` "Prod" build after that is a Beta build wearing a Prod label.

## Steps to reproduce

1. `scripts/set-environment.sh Beta` (or equivalently, run `SCHEME="Batty (Beta)" scripts/build.sh` and let the scheme pre-action leave `Active.xcconfig` at Beta).
2. `xcodebuild -project Batty.xcodeproj -scheme "Batty (Prod)" -showBuildSettings | grep -E "PRODUCT_NAME|PRODUCT_BUNDLE_IDENTIFIER"`
3. Observe `PRODUCT_NAME = Batty Beta` and `PRODUCT_BUNDLE_IDENTIFIER = co.sstools.Batty.beta` — from the *Prod* scheme.
4. `scripts/set-environment.sh Prod` restores `PRODUCT_NAME = Batty` / `co.sstools.Batty`.

Reproduced on this checkout 2026-08-03: with `Active.xcconfig` at Beta the Prod scheme resolved `Batty Beta` / `co.sstools.Batty.beta`; after restoring Prod it resolved `Batty` / `co.sstools.Batty`.

## Expected behavior

Building Beta must not be able to silently change what a later Prod build produces. Options — none pre-selected, since `scripts/` and `Configuration/Build.xcconfig` are restricted areas per `CLAUDE.md` and any fix needs explicit go-ahead:

- Have `scripts/build.sh` snapshot and restore `Active.xcconfig` the way `build-beta.sh` already does, or refuse to run when `SCHEME` is overridden.
- Have `scripts/build.sh` assert that the resolved `PRODUCT_NAME` / `PRODUCT_BUNDLE_IDENTIFIER` match the scheme it was asked for, and fail loudly on mismatch. This is the check that would have caught the incident below, and it is cheap.
- Give Beta its own target, so the shared-target product-name caching in `project.pbxproj` (see Notes) stops entirely.
- At minimum, document in `CLAUDE.md` that Beta must be built only via `scripts/build-beta.sh`, and that a dirty `project.pbxproj` after a Beta build is expected residue to discard, never commit.

## Actual behavior

The failure is silent and defeats verification. During the #0285 umbrella work (2026-08-01), agent sessions built Beta via `SCHEME="Batty (Beta)" scripts/build.sh` repeatedly. Every subsequent "`scripts/build.sh` — BUILD SUCCEEDED (Prod scheme)" line in that work was, at minimum, suspect: the app target being built was Beta. Unit-test results were not affected — `BattyKitTests` exercises the Swift package, which does not depend on the app bundle id, and a re-run under restored Prod settings gave an identical 821 tests in 98 suites — but "the Prod app builds" was not actually established at those moments.

One concrete mislabel to record: #0295's review reported inspecting "the freshly built `Debug/Batty.app`" for string-catalog entries (`issues/0295.md:87`); that was almost certainly `Batty Beta.app`. The conclusion still holds — both variants embed the same catalog — but the artifact named was wrong.

## Relation

- Discovered while cleaning up after the #0285 umbrella work, whose Beta builds left `Active.xcconfig` redirected.
- #0279 introduced `scripts/build-beta.sh`, whose header anticipated exactly this hazard ("the very next `-scheme 'Batty (Prod)'` build … would silently build the BETA product while claiming to be Prod") and defended against it — but only for builds routed through that script. This issue is the independent follow-up for the unguarded paths.

## Notes

Diagnostic worth keeping:

```bash
xcodebuild -project Batty.xcodeproj -scheme "Batty (Prod)" -showBuildSettings | grep PRODUCT_NAME
```

Secondary symptom: because Prod and Beta share one target, whichever scheme resolved last caches its product name into the tracked `Batty.xcodeproj/project.pbxproj` (the `Batty.app` product file reference flips to `Batty Beta.app`, plus a file-reference reorder). That shows up as a dirty working tree after any Beta build. It must be discarded, never committed — committing it just makes the next Prod build flip it back.

`Active.xcconfig` is included with `#include?` (optional), so a fresh clone without the file builds with the Prod defaults in `App.xcconfig` — the hazard only exists once `set-environment.sh Beta` (or the Beta scheme pre-action) has run on a checkout.
