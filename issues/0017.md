## Description

Replace the M3 single-pane detail with a recursive SwiftUI view that walks the `SplitNode` tree, rendering `PaneView` at leaves and a horizontal/vertical container at split nodes. This is the visual foundation for splits.

**Acceptance criteria:**
- `SplitContainerView` switches on `SplitNode` cases:
  - `.leaf(Pane)` → `PaneView(pane:)`.
  - `.split(.horizontal, ratio, left, right)` → side-by-side layout with a divider; `ratio` controls the left's width fraction.
  - `.split(.vertical, ratio, left, right)` → stacked layout with a divider; `ratio` controls the top's height fraction.
- Test with a hand-built tree of two leaves under one split — both render, divider is visible.
- Nesting works: a split inside a split inside a leaf renders correctly.
- Resize on the window propagates correctly into nested splits without distortion.

## Notes

- Don't make the divider draggable in this issue — that's #0019.
- Don't introduce keybindings or toolbar buttons here — those are #0018.
- Decide between SwiftUI's `HSplitView`/`VSplitView` and a custom `GeometryReader`-based implementation. `HSplitView` has known limitations with live ratio updates and persistence; a custom implementation is likely necessary by #0019. If we go custom, expose a clean enough API now to avoid a rewrite.

## Root cause

Feature gap. M4 needs sessions to host a recursive tree of panes; until #0017 each session held a single `PaneRuntime` flat. The renderer is the foundation everything else in M4 (#0018–#0021) builds on.

## Fix

Two new types in `BattyKit/Sources/BattyKit/`:

- **`SplitTreeNode`** — `public indirect enum` with `.leaf(PaneRuntime)` and `.split(direction:ratio:left:right:)`. Pure data; the runtime `PaneRuntime` instances live at the leaves. Helper extensions for `firstLeafPaneID` / `firstLeafPane` (default focus selection), `findPane(id:)` (recursive lookup), `allLeafPanes`, and `contains(paneID:)`.
- **`SplitTree`** — `@Observable` reference type holding `root: SplitTreeNode` and `focusedPaneID: UUID`. Default init produces a single-leaf tree with one fresh `PaneRuntime`. `focusedPane` computed property resolves the marker against the tree, falling back to the first leaf if the marker is stale (defensive).

`SessionRuntime` swaps `pane: PaneRuntime` for `tree: SplitTree`. `focusedPane` is exposed as a computed property forwarding to `tree.focusedPane`, so call sites that just want "the active pane" don't need to know about the tree shape.

`SessionDetailView` renders `SplitContainerView(tree: session.tree)` instead of `PaneView` directly. `navigationTitle` reads through `session.focusedPane.activeTab.terminal.title`.

`BattyCommands.focusedPane` updated from `selectedSession?.pane` to `selectedSession?.focusedPane`. The New Tab / Close Tab buttons that referenced `session.pane.addTab()` etc. follow.

`SplitContainerView` is a thin `@Bindable`-wrapper view that delegates to a private `SplitNodeView` doing the actual recursion. `SplitNodeView.body` returns `AnyView` (not `some View`) — a recursive `some View` causes the compiler to complain about the opaque return type being defined in terms of itself.

For now, splits at the SwiftUI layer use `HSplitView` / `VSplitView`, which provide draggable dividers automatically. The `ratio:` associated value on the `.split` case is intentionally not yet wired into the divider position; #0019 will introduce a custom divider with persistent ratios.

`SplitDirection` was promoted from `internal` to `public` because the public `SplitTreeNode.split` case references it. Other LayoutModel.swift types remain `internal` per #0040's deliberate-publicization rule.

## Gotchas

- **AnyView at the recursion point.** A recursive view function returning `some View` doesn't compile because the opaque type is defined in terms of itself. `SplitNodeView.body: AnyView` is the standard workaround. AnyView has a small render-cost penalty (loses some SwiftUI optimizations); acceptable for split tree depth which is bounded by user splits.
- **HSplitView / VSplitView ignore the `ratio:` associated value.** They place the divider at 50% by default and let the user drag. Persisting the post-drag ratio back into `SplitTreeNode` is `#0019`. So for #0017 the ratio is stored but unused at the view layer.
- **Single-leaf trees render the same as M3 PaneView.** The user-visible behavior shouldn't change in this issue. Visual verification of two-leaf and nested-split trees has to wait until #0018 lands a way to actually create splits.
- **`SessionRuntime.focusedPane`** is a computed property that re-reads `tree.focusedPane` each access. Cheap because the tree's focused pane is found by walking the tree once. Will become hot if call sites read it in tight loops; if so, cache.
- **Visual verification needed** for: single-leaf trees still render the same as M3 (no regression); placing the app in front of M2 spot-check (sidebar, sessions, tabs) shouldn't surface any new issues; new behavior surfaces in #0018.
