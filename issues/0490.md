## Description

The Sidebar footer holds one control, the `plus` button that creates a new Session. With Projects (#0469) a Session often starts as a Project, but the only ways to open one are File ▸ Open Project ▸ … and the Command Palette's "Open Project…" rows. The user asked for a second footer button beside the plus that presents the Open Project picker.

The user's words (2026-10-12): "We currently have a plus button in the bottom of the side bar to create a new session. We should add a button to also select a project."

Ships on `main` for 1.3.0, behind the Projects flag. With the flag off the button does not exist.

## Expected behavior

### 1. The button

- A second `Button` in the footer `HStack`, immediately after the plus, before the `Spacer`. Same shape as the plus: `Image(systemName:)` in a `22 × 22` frame, `.buttonStyle(.borderless)`, the footer's default `HStack` spacing. No divider between the two. The footer's padding and background are untouched.
- **SF Symbol: `briefcase`** (outline, to match the stroke weight of `plus`). Why this one:
  - It is not `plus`, and it is not a folder. In Beta every Project-backed row may draw `folder.fill` (#0472) or a catalog symbol (#0482), so a folder in the footer would read as another row marker instead of an action. `folder.badge.plus` is the picker's empty-state illustration and reads as "new folder".
  - It is not in #0482's 36-symbol catalog, and it is not a grid: `square.grid.2x2` would read as Choose Layout…, and `square.grid.3x3.fill` is catalog key `grid`.
  - "Briefcase" is the conventional work/projects metaphor, and at the footer's size (the symbol's body size inside a 22-pt frame) it stays a clear outline with a handle.
  - It has been in SF Symbols since version 1 (macOS 11), well within the macOS 15.6 deployment target; `NSImage(systemSymbolName: "briefcase", accessibilityDescription: nil)` is non-nil on the host (macOS 27). Pin that in a unit test rather than assume it.
  - Runner-up, if the user dislikes it at sign-off: `rectangle.stack`. Do not use a folder variant.
- `.help("Open Project\u{2026}")`. `.accessibilityLabel("Open Project")`. `.accessibilityIdentifier("session-sidebar.open-project-button")`.
- In the same change, give the plus button the identifier `docs/ui-features.md` already documents, `session-sidebar.add-session-button`, so the UI test can prove both buttons exist and are distinct. Do not change the plus button's symbol, help, action or style.
- The File ▸ Open Project submenu keeps its `folder` label. It is a menu image, not the footer, and changing it is out of scope.

### 2. The action: present the picker on this window directly

- Clicking the button presents the Open Project picker sheet on the button's own window. No notification, no `isKeyWindow` gate. The reason is the one #0483 ran into: the key-gated broadcast is right for a global chord that every window hears, and wrong for a control that already knows its window.
- **Mechanism:** hoist the picker's presentation state onto the window runtime, following `pendingCloseRequest`. `WindowRuntime` gains an observed `public var projectPickerShown: Bool = false` (or an equivalent request value; the name is the implementer's). `SessionDetailView.projectPickerBinding` reads `store.featureFlags.projects && windowRuntime.projectPickerShown` and writes `windowRuntime.projectPickerShown = $0`, replacing its private `@State`. The Sidebar button's action is `windowRuntime.projectPickerShown = true` (behind the flag gate in §4). The sheet's `onDismiss` and `runAfterProjectPicker` are unchanged. Every write is event-origin: a button, a sheet dismissal, a menu item (`docs/swiftui-observation-rules.md`).
- Rebase on `main` after #0483 and #0485 have landed (they are lower-numbered and in review), then route their writes to the same property: #0483's `presentProjectPicker()` sets it; #0485's targeted-notification handler toggles it. After this issue there is exactly one presentation variable per window and three writers (File menu via notification, palette via closure, Sidebar button direct). If either issue has not landed when this one starts, say so in the summary and do not reimplement its part.
- **Not a menu.** A footer popup listing Projects plus Choose…/New… was considered and rejected. The picker already lists every Project with a filter, OPEN badges and New Project…; a Sidebar menu would be a third copy of `ProjectFileMenuModel` (after the File menu and the palette), a third gate site, and a third place for the check-mark problem #0484 finding 4 is still deciding. The user's plus button is a one-click action, and this one matches it: one click, the picker, exactly what File ▸ Open Project ▸ Choose Project… gives. The File menu's own list stays where it is.
- **Multi-window (#0242).** Each Sidebar writes its own `WindowRuntime`, so a click in one window never presents the picker in another. The click also makes that window key as a side effect of being a click in it, so the picker always appears over the window the user is looking at; no activation call is needed.
- **Collapsed Sidebar.** The footer is not visible, so neither is the button. The File menu and palette paths are unaffected.

### 3. No Projects yet

The button always presents the picker, and the picker's existing empty state ("No Projects yet" plus New Project…) takes over. Do not open the editor from the button when the store is empty: that would make a footer button's behavior depend on store contents, it would be the only entry point that behaves differently from Choose Project…, and the picker's New Project… already opens the editor on a new draft. The UI test covers this path (§ Acceptance criteria), which `docs/ui-features.md` "Not covered by unit tests" currently lists as untested.

### 4. Flag off

- The button is built only when `store.featureFlags.projects` is true: wrapped in `if`, absent from the view tree, not merely disabled. The Sidebar reads nothing from `store.projectStore`; the picker reads it only after it is presented, as today.
- `SessionDetailView.projectPickerBinding` keeps its `featureFlags.projects &&` guard, so a stray write of the window property can never present the sheet in Prod.
- Append to the gate-site table in `docs/feature-flags.md`: `SessionSidebarView` footer Open Project button (`BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift`) — the button exists, and `WindowRuntime.projectPickerShown` is written from the Sidebar, only when `featureFlags.projects`; no `projectStore` read — #0490. Update the #0475 row's `SessionDetailView` entry to name the window property.

### 5. Keyboard

No shortcut. #0469 forbids new `ShortcutAction` cases while the feature is flagged, and there is nothing to mirror: File ▸ Open Project ▸ Choose Project… has no key equivalent (`BattyCommands.swift:129-131` attaches none; `docs/ui-features.md:747` records the same). The button is reachable through Full Keyboard Access like the plus. The flag-removal issue decides shortcuts for the whole feature.

## Notes

- **Binding docs:** `docs/swiftui-observation-rules.md`. The property is written from a button action, a sheet dismissal, a menu action and (after #0483) a palette `onDismiss`; never from `body`, `onAppear` or a geometry callback. Do not add a `Task` or `DispatchQueue.main.async` hop anywhere in this path. `docs/view-hierarchy.md` applies only in that the Sidebar and the detail view are siblings under `RootWindowView`'s `NavigationSplitView` (`Views/RootWindowView.swift:39-44`); nothing here goes near the terminal host.
- **Why hoist the state instead of a closure from the Sidebar to the detail view.** The two views are siblings created by `RootWindowView`; the only things they share are `store` and `windowRuntime`. A `@State` in `RootWindowView` passed as a `Binding` to both would also work, but `WindowRuntime` already carries per-window presentation requests (`pendingCloseRequest`, `pendingStartupTrusts`) and is reachable from unit tests without a view hierarchy, which the closure route is not.
- **Why no key-window gate.** The gate exists because the toggle notifications are broadcast to every window (#0242). A control inside a window is not a broadcast. Gating it on key status would reproduce #0483's failure whenever the click lands while the window is becoming key.
- Line numbers were grepped on `main` at `dd9f875b` on 2026-10-12 and will drift when #0482, #0483 and #0485 land; all three touch files named here (`SessionSidebarView.swift`, `SessionDetailView.swift`, `ProjectPickerView.swift`, `docs/feature-flags.md`, `docs/ui-features.md`).

## Root cause

Feature request (user, 2026-10-12). The footer had only the + button for a new Session. Opening a Project took the File menu or the Command Palette.

## Fix

- **Hoisted picker state.** `projectPickerShown` moved from `SessionDetailView`'s private `@State` onto `WindowRuntime`, as one observed per-window property.
  - **Three event-origin sites set it:**
    - the window-addressed `.battyToggleProjectPicker` (#0485);
    - the Command Palette's direct present (#0483);
    - the new Sidebar button.
  - **It is cleared by** the picker's `onAction`/`onCancel` and by the sheet binding's setter. The setter skips equal-value writes.
  - The binding keeps its `featureFlags.projects` guard.
  - **Why not reuse the toggle:** reusing #0485's toggle notification was rejected. The Sidebar and the detail view are siblings, so a shared per-window property is the only direct path between them. It also needs no notification or key-window check.
- **`SidebarFooter`** (new, pure):
  - the identifiers;
  - the symbol `briefcase`;
  - help text "Open Project…" and label "Open Project";
  - `showsOpenProjectButton(featureFlags:)`;
  - `presentProjectPicker(in:featureFlags:)`.
- **Buttons.** The new button uses the same 22×22 borderless style as +. The + button gains its documented identifier, `session-sidebar.add-session-button`.
- **Docs.**
  - The footer is no longer called a "header": `docs/ui-features.md` and `Concepts.md` (now v0.10, chained with #0492's 0.9 entry).
  - New gate-site row; the #0475 row now names the window property.
  - Coverage map updated.
