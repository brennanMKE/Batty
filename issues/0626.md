## Description

Each run failed a different set of tests, always with the same message from `openPickerOnFixtures` (`ProcessStatusPickerTests.swift:132`): `the fixture bt-follow-xxxxx never appeared in the picker`. An earlier run failed 6 of the class's tests once, and the next run passed. The class is flaky, not broken by one commit.

- Full run (`bc956752`): `testFilterByNameNarrowsToTheFixtureAndReturnPinsIt`, `testFollowByNameIsOfferedAfterExitAndPicksUpTheRelaunch`, `testFollowByNameReconnectsToEachReplacement`, `testHeaderFollowAndStopButtonsWhileRunning`.

## Notes

What the failure output does and doesn't show:

- **`fixtureLog=Optional("")` proves nothing.** `errorLogPath` is `NSTemporaryDirectory() + "bt-fixture-errors.log"` (`ProcessStatusPickerTests.swift:21`). It is shared by every test in the class and never removed. `tearDownWithError` removes only `fixturePath`, and `BattyUITestHarness.sweepSentinels()` removes only `batty-ui-test-*` entries (`Support/BattyUITestHarness.swift:115-121`). The script writes `rc=$?` only after `sleep` exits, and closing the fixture Pane usually kills it first. So an empty log can't tell "the script ran and `cp` succeeded" from "the script never ran".
- **The dump doesn't record the query or the list size.** The empty state's label is combined (`accessibilityElement(children: .combine)`) and comes out blank in the dump. The unfiltered row count isn't captured either, so an empty list and a list without the fixture look the same.

Hypotheses, most likely first:

1. **The fixture never started, or started much later than the CLI call returned.** `startFixture` runs `/bin/sh <script>` in a new terminal Pane through `batty pane split --pane <terminal> --command …` (`ProcessStatusPickerTests.swift:51-62`, `Support/BattyCLIHarness.swift:321-325`). The script copies `/bin/sleep` to `/tmp/bt-follow-xxxxx` and execs it. The test only knows the CLI printed a Pane id. Candidate causes, none confirmed:
   - The new Pane's terminal surface, and so its shell, isn't started until the Pane is laid out or shown. Several commits on `main` today change when terminals are shown or started: `79925a8d` (#0605, push terminal visibility from actions), `c480b492` (#0603, start a Project's view Panes suspended in an occluded window) and `0cef9562` (#0611, terminal focus). The flake predates today's run, though (the earlier 6-failure run), so these would at most make it worse.
   - The guest takes a long time to assess the first exec of a freshly copied binary in `/tmp`.
   - The split leaves the fixture Pane too small to start in. The VM's content window is 900×504 in the AppearanceBackgroundSettingsTests failure snapshot (#0625), and the window already holds the terminal and the Process Status Pane. The CLI would still report success.
2. **The process walk failed and the picker showed an empty list.** `allSameUserProcesses()` maps a failed walk to `[]` (`ProcessInspector.swift:379`, `(allPids() ?? [])`). The picker then shows "No processes match" with no sign that the walk failed. #0565 made `firstSameUserProcess(named:)` return `.unknown` for this case, but the picker path still swallows it. Six failed walks in a row over about 80 s seem unlikely. `allPids` logs `allPids: probe returned …` / `fill attempt …` at error level, and none appear in the run's `app-warnings.log`.
3. **The listed name differs from the fixture name.** The picker filters on `bsdName` (`pbi_name`, `ProcessInspector.swift:562-566`), case-insensitive substring (`ProcessPickerFilter.swift:13-17`). The name is 15 characters (`bt-follow-` plus 5), which fits. Unlikely, since the same name matches in the passing runs.

Suggested first step for the plan: make the test report what happened before changing anything else.

- Give each test its own log file and write `started $$` before the `cp` and `exec'd` just before running the fixture.
- On failure, dump the filter field's value and the unfiltered row count, and check from the test side whether `/tmp/bt-follow-xxxxx` exists.
- Wait for the fixture's own "started" marker (an event, per AGENTS.md "Asynchronous tests") before opening the picker, instead of reopening the picker six times.

Related: #0516 (`allPids()` truncation, open; its remaining work moved to #0565, resolved) and #0565 (failed walk is `.unknown`). Neither covers this test. Truncation doesn't explain one process missing from six separate walks, and the saturation retry is in place (`ProcessInspector.swift`, `allPidsMaxAttempts`). #0486 (open) is the feature these tests cover.

Verification tier: UI confirmation, with `BattyUITests/ProcessStatusPickerTests` run at least twice. A single green run proves little for a flake that fails a different subset each time.

## Root cause

**Confirmed (implement round 2): the picker's first presentation read the list's previous value.** `ProcessStatusPaneView` kept the fetched list (`runningProcessesCache`) and the presentation flag (`isPickingProcess`) as two `@State` values, written together in `pickRunningProcess()`'s `Button` action, with the list read only inside the `.popover(isPresented:)` content closure. On the first presentation in the view's lifetime, that content was built from the list's previous value (`[]`), so the picker opened on "No processes match" with no rows. `RunningProcessPickerPresentationTests.separateCacheAndIsPresentedShowsAnEmptyListOnFirstOpen` reproduces it on the host with the production anchor (`Menu`, `.menuStyle(.button)`): the action writes 3 items, the content is handed 0; a second open is handed 6. Before the fix, asserting `[3, 6]` on that shape failed with `[0, 6]` (unit run `unit-20261113-165722-90928`). Not test-only: a user's first "Pick a Running Process…" after a Process Status Pane appears opened empty.

**The empty second open in VM run `20261113-163814-65378` is not reproduced and not explained.** On the host, a second open is correct whether it happens after the first popover's dismissal has landed or during its close animation (0, 1, 5, 50 or 500 main-queue turns after `show = false`; throwaway experiment, not committed). After the fix it no longer occurs in the VM: `testFilterByPidListsItFirstAndEscapeClearsThenDismisses` dismisses the picker and opens it a second time, typing the pid and expecting its row, and passed in both VM runs below. Under `.popover(item:)` the content is a function of the presented item only, so any reuse of a stale content host or `@State` reset can no longer show a list other than the one the opening action fetched; which of these happened in that run remains unknown.

**Earlier diagnosis (implement round 1).** The plan's leading cause (slow first exec, C1) is refuted.** VM run `20261113-163814-65378` (commit `44101499`, base fixture warmed once, per-test fixtures hard-linked) failed `testFilterByPidListsItFirstAndEscapeClearsThenDismisses` with this dump:

- Fixture log: `started`, `linked`, `exec` all in the same second (`1794616913`). The hard link and exec were instant.
- `ps`: `5514 5509 S+ 00:29 /tmp/bt-follow-f8c4b`: the fixture had been running for 29 s, under the right name, as a child of the script's `sh`, through both picker opens.
- Picker: `filter=bt-follow-f8c4b`, `unfiltered=0` (no row at all after Escape cleared the query). `fixtureExists=true`.

Every test in the run, passing or not, still needed the reopen. The first open never listed the fixture, even though the exec marker had already been logged. So the time is not spent in `cp` or `exec`. The picker shows an empty or stale process list. The old 6-reopen loop hid this, and that hiding is what made the failure look like a slow exec.

**Hypothesis (not confirmed):** `ProcessStatusPaneView.pickRunningProcess()` writes `runningProcessesCache` and `isPickingProcess = true` in the same action. The `.popover(isPresented:)` content (`runningProcessPicker`, which reads `runningProcessesCache` into `RunningProcessPickerView.processes`) is attached to a `Menu`, and it can be built from the previous value of the cache: empty on the first open, and the previous open's fetch on later opens. That fits "first open never finds it, a later open usually does" and `unfiltered=0`. An AX exposure problem with the `List` rows has not been ruled out. This is an app bug (Module Pane), not a test problem. Under the plan's rules it needs its own issue, so this implement phase **bailed** before the second VM run.

## Fix

Followed `## Plan (revised)`.

- `RunningProcessPickerView.swift`: new `RunningProcessPickerRequest: Identifiable` (a fresh `UUID` per open, plus the fetched `processes`).
- `ProcessStatusPaneView.swift`: `runningProcessesCache` and `isPickingProcess` replaced by one `@State pickerRequest: RunningProcessPickerRequest?`. `pickRunningProcess()` (still only called from `Button` actions: the header menu item and the empty-state button) sets it to a request carrying the sorted `ProcessInspector.allSameUserProcesses()`. The popover is `.popover(item: $pickerRequest) { runningProcessPicker($0.processes) }`; `onPick`/`onDismiss` set it to `nil`. The S4 doc comment moved to `pickerRequest`, and the stale "built once per open" comment was corrected. No `Task` hop, no `onAppear` fetch.
- `RunningProcessPickerPresentationTests` (new): two probes with the production anchor, hosted in an ordered-front window. The popover content is a child view handed the list as a `let` (as `RunningProcessPickerView` is) and records what it was given. Waiting is the turn-bounded main-queue hop of `PaneViewRenderTests.pump`. Its hang guard is 50,000 turns rather than 200, because a popover's `onDisappear` lands only when the close animation completes (about 4,200–4,700 turns on the host); the condition is still checked after every turn. Each window is closed only after its popover's dismissal has landed.
- `ProcessStatusPickerTests`: removed `prepareBase` and the base/hard-link path (per-test `cp /bin/sleep` again; per-test log, `exec`-marker wait and failure dump kept). `openPickerOnFixtures` opens once, with no reopen. `openPicker` waits for `choose.isHittable` before clicking, and `launchWithProcessStatusPane` calls `app.activate()` after the window appears.

Divergence from the plan: the probes record from a child view's `let` rather than reading `cache.count` inside the content's `onAppear`. A `@State` read in a closure that runs later returns the current value, so the first attempt recorded 3 for both shapes and did not reproduce the bug.

## Plan

### What the evidence shows (2026-11-13, plan phase)

Read from the re-run `20261113-155125-98146` (vm-main worktree) and the full run `20261113-145108-64936` (`build/ui-tests/`):

- **The first picker open never finds a freshly copied fixture, in any test, passing or failing.** Opens per test (count of `Type 'bt-follow-…'` steps): re-run 2,3,2,6,5,6,6,3; full run 2,3,6,3,2,6,6,6. So the first exec of a new `/tmp/bt-follow-xxxxx` takes from about 15 s to more than 80 s after `pane split --command` returns.
- **A relaunch of the same, already-copied file is fast.** In `testExitedBannerFollowButtonThenRelaunch` (re-run, passed) the second `startFixture` reuses the copy (`[ -x … ] ||` skips `cp`), and follow-by-name picks the new pid within about 2.5 s. The follow-by-name relaunch rounds never fail. Only the fresh copy is slow.
- **The fixture Pane is up and its command started.** Frames from the failing test's screen recording (`testFilterByPid…`, xcresult attachment "Screen Recording … 04.00.56 PM") show the fixture Pane as the middle split with `Last login: … on ttys002` and no prompt: `login` ran and handed off to the command, which prints nothing. The Pane is not zero-sized, unstarted, or waiting on a startup-command banner. `--command` sets the surface's command (`TabRuntime.commandOverride` → `applyShellAndAppearancePreferences`), not the typed `StartupCommandDelivery` path, so the 10 s readiness deadline doesn't apply.
- The picker itself works: it lists rows once the fixture runs, and `testNoMatchShowsTheEmptyState` passes. `app-warnings.log` has no `allPids` errors. `sandbox-denials.log` has no Batty, `sh`, `cp` or `bt-follow` entries.

**Leading cause (not confirmed):** the first `exec` of a newly written binary in the guest is held up for tens of seconds, probably by an exec-time assessment (amfid / syspolicyd / XProtect) of a file with a new inode. While it waits, the process is still named `sh`, so the picker has no `bt-follow-…` row. Still unknown: whether the time goes to `cp` or to the `exec`, and which daemon causes it. Hypotheses 2 (failed walk) and 3 (name mismatch) from the Notes are unlikely but not ruled out. The diagnostics below settle all three in one VM run.

### Approach

Diagnostics and the fix for the leading cause go in together, so the confirmation run either passes or names the cause. All changes are test-side apart from fix C3. No sleeps, and no longer timeouts. The waits in the helper get shorter, not longer.

**1. Per-test, timestamped fixture log (diagnostic).** In `ProcessStatusPickerTests.swift`:
- Replace the shared `errorLogPath` with a per-test `fixtureLogPath` under the runner's temp dir, named `batty-ui-test-fixture-<uuid8>.log` so `sweepSentinels()` removes it. Create it empty in `setUpWithError`.
- The script appends one line per step with `$$` and `$(/bin/date +%s)`: `started`, `copied` (or `reused`) with `cp`'s rc, `warmed` with the warm-run rc (below), and `exec` just before the real exec. Each line is written after its step completes. `stderr` of every step also goes to the log.

**2. Fix for the leading cause (C1): pay the first exec once per class, and give each test a unique name through a hard link.**
- Add a class-level base fixture `/tmp/bt-base-<uuid5>` (a `static` name chosen once per class run) that is copied from `/bin/sleep` and **warmed** with one throwaway run (`<base> 0`, which exits at once), so its first-exec assessment is over before any test needs it.
- Each test's fixture `/tmp/bt-follow-xxxxx` becomes `ln <base> <fixturePath>`: a new name (a process's `p_comm`/`pbi_name` comes from the last path component it was exec'd through) with the same, already-assessed vnode. Fall back to `cp` only if `ln` fails, and log which path the script took.
- `startFixture` then waits for the **event** that the script reached its `exec` line, using `BattyUITestHarness.waitForFile`-style checks on the log's `exec` line (a written marker, not elapsed time), with a hang-guard bound. A fixture that never reaches `exec` now fails at that point with the log in the message, so a slow prepare is no longer reported as a picker problem.
- Preparing the base: the first `startFixture` in a class run splits once with a prepare script (`cp`, warm run, write `ready`), waits for `ready` under a hang-guard, then closes that Pane. Later tests see that the base exists through the same marker file and skip this step. If the diagnostics show the single warm run is itself longer than the guard, the follow-up (recorded in `## Gotchas`, not done here) is to have `tools/run-ui-tests-vm.sh` stage and warm the base in the guest before `xcodebuild` starts.
- `openPickerOnFixtures` no longer reopens six times. One open after the `exec` marker, waiting for the rows with the existing 5 s bound, then at most one reopen. That covers an exec that lands between the walk and the typing, a race that a hard-linked, pre-assessed binary makes narrow. The 83 s failure mode is removed rather than hidden.

**3. Failure dump (diagnostic, all candidate causes).** When the fixture row isn't found, before `XCTFail` (see note), collect:
- the filter field's `value` (`process-status.picker.filter-field`) and, after clearing the query with one Escape, the unfiltered row count `rows(app).count` (0 means a failed walk, C3);
- the per-test fixture log, and whether `fixturePath` exists (`FileManager.fileExists`, readable by the runner even where it can't write);
- a process snapshot: one `pane split --command` running a dump script that writes `ps -axo pid,ppid,stat,etime,comm` plus `/usr/bin/log show --last 3m --style compact --predicate 'process IN {"amfid","syspolicyd","XprotectService","kernel"} AND (eventMessage CONTAINS "bt-" OR eventMessage CONTAINS "sleep")'` to a `batty-ui-test-diag-<uuid8>.txt` file, then a `done` marker. The test waits for the marker under a hang-guard and attaches the file as an `XCTAttachment` (`.keepAlways`), with its first 40 lines in the failure message. The `ps` rows for the fixture Pane's tree show a stuck `sh` (exec held, C1), a stuck `cp` (copy held), no `sh` at all (C2), or a running `bt-follow-…` the picker didn't list (C3/C4).
- Note: `continueAfterFailure = false` stops the test at the first `XCTFail`, so the dump runs before it, and the dump's own waits use `waitFor` results and never assert.

**4. Fixes for the other candidates, applied only if the dump points at them** (the implementer does C1 now; C2–C4 are written into `## Gotchas` as the next step when the run shows them):
- **C2, the script never starts** (`ps` shows `login`/`bash` but no `sh` child, and the log has no `started`): wait for the fixture Pane's terminal body `pane-terminal.<id>` to exist before the exec-marker wait, and open a follow-up app issue on the surface/command start path (Module Pane / Terminal) instead of patching the test around it.

Unit test in BattyKitTests: `ProcessInspectorTests.allSameUserProcessesIsNilWhenTheWalkFails`, through the existing `allPids` seam if there is one (otherwise add an injectable pid source; it must not change production behaviour).

## Plan (revised)

Written 2026-11-13 after VM run `20261113-163814-65378`. This replaces `## Plan` above as the plan for the next implement phase. Module becomes **Pane** (the cause is in the app); the test-side diagnostics stay.

### Confirmed cause: the popover's first presentation reads `runningProcessesCache` before the opening action's write

`ProcessStatusPaneView` keeps the fetched list and the presentation flag as two separate `@State` values (`BattyKit/Sources/BattyKit/Views/ProcessStatusPaneView.swift:36-37`). `pickRunningProcess()` writes both in one `Button` action (`:259-263`). The `.popover(isPresented: $isPickingProcess)` content closure (`:234-236`) is the only place `runningProcessesCache` is read (`:271-272`), so `body` has no dependency on it. When the popover is presented for the first time in the view's lifetime, SwiftUI builds its content from the value the closure captured before the action ran, so `RunningProcessPickerView.processes` is `[]` and the picker shows "No processes match". Once that popover host exists, later opens read the current value.

Confirmed on the host with a throwaway hosting experiment (BattyKit, `NSHostingView` in an ordered-front `NSWindow`, never committed). One action set `cache = [3 items]` and `show = true`, the popover content recorded `cache.count` in `body` and `onAppear`, then the popover was dismissed by state and opened again with 6 items:

| anchor | first open saw | second open saw |
|---|---|---|
| `Button` + `.popover(isPresented:)` | **0** | 6 |
| `Menu(.button)` + `.popover(isPresented:)` (production shape) | **0** | 6 |
| `Menu(.button)` + `.popover(item:)`, list carried in the item | 3 | 6 |

This matches the VM evidence. The exec marker was logged before the first open, yet every test needed a reopen, and the dump showed `unfiltered=0` (an empty list, not a list missing the fixture). It also explains the original 83 s failures: the old 6-open loop paid one guaranteed-empty first open per test.
