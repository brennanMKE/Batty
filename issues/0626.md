## Description

`ProcessStatusPickerTests` failed in today's full VM UI run against `main` (`bc956752`) and again in the re-run against `main` (`483b8948`). Each run failed a different set of tests, always with the same message from `openPickerOnFixtures` (`ProcessStatusPickerTests.swift:132`): `the fixture bt-follow-xxxxx never appeared in the picker`. An earlier run failed 6 of the class's tests once, and the next run passed. The class is flaky, not broken by one commit.

- Full run (`bc956752`): `testFilterByNameNarrowsToTheFixtureAndReturnPinsIt`, `testFollowByNameIsOfferedAfterExitAndPicksUpTheRelaunch`, `testFollowByNameReconnectsToEachReplacement`, `testHeaderFollowAndStopButtonsWhileRunning`.
- Re-run (`483b8948`, run id `20261113-155125-98146`): `testFilterByPidListsItFirstAndEscapeClearsThenDismisses`, `testFollowByNameIsOfferedAfterExitAndPicksUpTheRelaunch`, `testFollowByNameReconnectsToEachReplacement`. The other six tests in the class passed in that run.

Each failure lasts about 83 s. The helper opens the picker, types the fixture's name and waits up to 5 s for a row, six times. Each open fetches a fresh process list (`ProcessStatusPaneView.pickRunningProcess()`, `ProcessStatusPaneView.swift:259-263`). So the fixture stayed out of the list for more than a minute after `batty pane split --command` returned. That is not a startup delay of a few seconds.

Failing filters, for confirmation runs: `BattyUITests/ProcessStatusPickerTests` (the whole class, since a different subset fails each time).

## Notes

What the failure output does and doesn't show:

- **`fixtureLog=Optional("")` proves nothing.** `errorLogPath` is `NSTemporaryDirectory() + "bt-fixture-errors.log"` (`ProcessStatusPickerTests.swift:21`). It is shared by every test in the class and never removed. `tearDownWithError` removes only `fixturePath`, and `BattyUITestHarness.sweepSentinels()` removes only `batty-ui-test-*` entries (`Support/BattyUITestHarness.swift:115-121`). The script writes `rc=$?` only after `sleep` exits, and closing the fixture Pane usually kills it first. So an empty log can't tell "the script ran and `cp` succeeded" from "the script never ran".
- **The dump doesn't record the query or the list size.** The empty state's label is combined (`accessibilityElement(children: .combine)`) and comes out blank in the dump. The unfiltered row count isn't captured either, so an empty list and a list without the fixture look the same.

Hypotheses, most likely first:

1. **The fixture never started, or started much later than the CLI call returned.** `startFixture` runs `/bin/sh <script>` in a new terminal Pane through `batty pane split --pane <terminal> --command …` (`ProcessStatusPickerTests.swift:51-62`, `Support/BattyCLIHarness.swift:321-325`). The script copies `/bin/sleep` to `/tmp/bt-follow-xxxxx` and execs it. The test only knows the CLI printed a Pane id. Candidate causes, none confirmed:
   - The new Pane's terminal surface, and so its shell, isn't started until the Pane is laid out or shown. Several commits on `main` today change when terminals are shown or started: `79925a8d` (#0605, push terminal visibility from actions), `c480b492` (#0603, start a Project's view Panes suspended in an occluded window) and `0cef9562` (#0611, terminal focus). The flake predates today's run, though (the earlier 6-failure run), so these would at most make it worse.
   - The guest takes a long time to assess the first exec of a freshly copied binary in `/tmp`.
   - The split leaves the fixture Pane too small to start in. The VM's content window is 900×504 in the AppearanceBackgroundSettingsTests failure snapshot (#0625), and the window already holds the terminal and the Process Status Pane. The CLI would still report success.
2. **The process walk failed and the picker showed an empty list.** `allSameUserProcesses()` maps a failed walk to `[]` (`ProcessInspector.swift:379`, `(allPids() ?? [])`). The picker then shows "No processes match" with no sign that the walk failed. #0565 made `firstSameUserProcess(named:)` return `.unknown` for this case, but the picker path still swallows it. Six failed walks in a row over about 80 s seem unlikely. `allPids` logs `allPids: probe returned …` / `fill attempt …` at error level, and none appear in the run's `app-warnings.log`.
3. **The listed name differs from the fixture name.** The picker filters on `bsdName` (`pbi_name`, `ProcessInspector.swift:562-566`), case-insensitive substring (`ProcessPickerFilter.swift:13-17`). The name is 15 characters (`bt-follow-` plus 5), which fits. Unlikely, since the same name matches in the passing runs.

Suggested first step for the plan: make the test report what happened before changing anything else.

- Give each test its own log file and write `started $$` before the `cp` and `exec'd` just before running the fixture.
- On failure, dump the filter field's value and the unfiltered row count, and check from the test side whether `/tmp/bt-follow-xxxxx` exists.
- Wait for the fixture's own "started" marker (an event, per AGENTS.md "Asynchronous tests") before opening the picker, instead of reopening the picker six times.

Related: #0516 (`allPids()` truncation, open; its remaining work moved to #0565, resolved) and #0565 (failed walk is `.unknown`). Neither covers this test. Truncation doesn't explain one process missing from six separate walks, and the saturation retry is in place (`ProcessInspector.swift`, `allPidsMaxAttempts`). #0486 (open) is the feature these tests cover.

Verification tier: UI confirmation, with `BattyUITests/ProcessStatusPickerTests` run at least twice. A single green run proves little for a flake that fails a different subset each time.
