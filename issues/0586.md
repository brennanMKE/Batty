## Description

Give a Session its own Theme (Sidebar "Set Session Theme…"). Then open a new Tab in it with Cmd-T, the tab-strip "+", or "Duplicate Tab". The new Tab's terminal draws in the app-wide Theme, not the Session's. It switches to the Session's Theme only when something re-applies the Session Theme: selecting another Session and back, or adding or removing a Pane in that Session.

Found while planning [#0584](0584.md). That issue turns the per-Session override into a Dark/Light pair and lets a Project set it, so most Project Sessions will carry their own Theme and this will show up much more often.

## Plan

Premises re-checked on `issue/0586` at 8fca195 (after #0584 and #0589). All hold: `TabRuntime.init` still seeds `TerminalViewState(theme: Self.activeTheme())`, the global Theme. `PaneRuntime.addTab` threads only background overrides. The split paths (`splitFocusedPane`, `splitFullDimension`, `splitPane(kind:)`) build the new Pane's Tab in the static `SplitTree.makePane` with the global Theme, then call `adopt(_:)`. #0584 landed as `SessionRuntime.themeOverride: ThemePair?` plus `ThemePreference.effectiveTheme(override:isDark:)`. `themeOverride` has three writers: `WindowRuntime.addProjectSession`, `SessionThemeSelectorView`, and the Sidebar's Clear Session Theme. `duplicateSession(id:)` copies neither the Theme nor the background.

Approach: mirror the Session's Theme override down the tree the way #0376 mirrors the background, and resolve the starting Theme when the Tab is built. The mirror is passive. It only seeds new Tabs and never re-themes existing ones, because the callers that write `themeOverride` already call `applyTheme`/`applyActiveSessionTheme`, and the Theme selector's preview depends on that split. All writes happen in model or event-handler code, none in view code.

### Files

- `BattyKit/Sources/BattyKit/Runtime/SessionRuntime.swift`: add a `didSet` on `themeOverride` that calls `tree.setSessionThemeOverride(themeOverride)`. That covers all three writers and Duplicate.
- `BattyKit/Sources/BattyKit/Model/SplitTree.swift`: add an `@ObservationIgnored private(set) var sessionThemeOverride: ThemePair?` and `setSessionThemeOverride(_:)`, which stores it and pushes it to every Pane. In `adopt(_:)`, push the mirror to the new Pane, then (terminal Pane only) call `setTheme` on its Tabs' controllers with the effective Theme. This is the one place that fixes split-created Tabs. It runs before any surface exists, the same guarantee `adopt` already relies on.
- `BattyKit/Sources/BattyKit/Runtime/PaneRuntime.swift`: add an `@ObservationIgnored` `sessionThemeOverride` mirror (no view reads it) and `setSessionThemeOverride(_:)`, which only stores it. `addTab` passes it to `TabRuntime.init`.
- `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift`: add an init parameter `sessionThemeOverride: ThemePair? = nil`. Replace `activeTheme()` with a starting-Theme helper: `ThemePreference.effectiveTheme(override:isDark: NSApp?.effectiveAppearance.isDark ?? true)?.toTerminalTheme() ?? .default`. Factor the resolution into one helper and use it from `adopt` too, so there is a single path.
- `BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift`, `duplicateSession(id:)`: set `copy.themeOverride = source.themeOverride` before the copy is selected. Selecting it re-applies the Theme to the copy's first Tab.
- `BattyKit/Sources/BattyKit/Views/SessionDetailView.swift`: **remove** the `.onChange(of: windowRuntime.selectedSession?.tree.allPanes.count)` re-theme. Only splits add Panes to a live tree (all three paths go through `adopt`). Closing a Pane needs no re-theme, hiding doesn't change `allPanes`, and no path moves a Pane between Sessions. With `adopt` theming new Tabs, the handler is redundant, and it was a view callback writing into terminal controllers and `ThemeChrome`. Removing a write can't break the observation rules. The `onAppear` and `selectedSessionID` re-themes stay: they cover Project open, whose tree is built before the Session exists, and changes made while a Session wasn't selected.
- Docs: in `docs/themes.md`, rewrite "New-tab initialization" so that new Tabs and Split Tabs start with the Session's effective Theme through the mirror, and change the stale `localThemeName` mentions in the sections nearby to `themeOverride`. In `Concepts.md`, add "Duplicate copies it" to Session's Theme override line.

### Decisions (delegated to me)

- **Duplicate Session copies the source's Theme override.** #0589 treats the Theme as Session state that a Project captures, and a copy that silently changes colors reads as a bug. The background is still not copied (Concepts.md says so explicitly). This issue doesn't change that, and I'm not filing it.
- **Project-open Tabs** (`ProjectTreeBuilder`) still start with the global Theme and get re-themed when the new Session is selected (`addProjectSession` always selects it). No change.
- **Appearance flip:** `applyGlobalThemeForCurrentAppearance` walks every Tab in the tree, so a Tab created after the fix follows the pair's slot. A test covers this.

- **Removed `allPanes.count` `onChange`:** every Pane insertion goes through `adopt` (`splitFocusedPane`, `splitFullDimension`, `splitPane`, including the `tabs:` move path and `ProjectTreeBuilder`). `ThemeChrome` depends only on the selected Session's effective Theme, which a split, close or unhide doesn't change. - `adopt` now also re-themes Tabs moved into a new split through `splitPane(tabs:)`. Those may already have surfaces, but `setTheme` on a live controller is what `applyTerminalTheme` already does, and the result is the correct Session Theme.

## Root cause

`TabRuntime.init` seeded its `TerminalViewState` with `ThemePreference.activeTheme()`, the global Theme, and had no Session context. `PaneRuntime.addTab` threaded only background overrides, and split-created Panes built their first Tab in the static `SplitTree.makePane`. The Session Theme reached surfaces only through `applyActiveSessionTheme`, which ran on Session selection and (for splits) on `SessionDetailView`'s `allPanes.count` `onChange`. Adding a Tab doesn't change the Pane count, so nothing re-themed it.

## Fix

Implemented as planned. `SessionRuntime.themeOverride` `didSet` mirrors the override to `SplitTree.sessionThemeOverride` (`@ObservationIgnored`), which pushes it to each Pane's `@ObservationIgnored` `sessionThemeOverride`. `PaneRuntime.addTab` passes it to the new `TabRuntime.init(sessionThemeOverride:)`, which resolves its starting Theme through the new `TabRuntime.startingTheme(sessionThemeOverride:)` (`ThemePreference.effectiveTheme(override:isDark:)` for `NSApp`'s appearance). `SplitTree.adopt` gives a new Pane the mirror and, for a terminal Pane, calls `setTheme` on its Tabs with the same helper, which fixes all three split paths before any surface exists. The mirror is passive: it never re-themes existing Tabs. `WindowRuntime.duplicateSession` copies `themeOverride` (delegated decision, see Plan). Removed `SessionDetailView`'s `allPanes.count` `onChange` re-theme, since `adopt` now covers splits. Updated `docs/themes.md` ("New-tab initialization", stale `localThemeName` mentions) and `Concepts.md`.

No deviations. One conservative note: `startingTheme` resolves the global fallback from `UserDefaults.standard` (production), the same source the old `activeTheme()` used; the tests therefore use override Themes chosen to differ from the `.standard` globals.

## Steps to reproduce

1. Select a Session. In the Sidebar, choose "Set Session Theme…" and pick a Theme that looks clearly different from the app-wide one.
2. Press Cmd-T (or click "+" in the tab strip, or right-click a Tab and choose "Duplicate Tab").
3. Look at the new Tab's terminal colors.
4. Select another Session, then select this one again.

## Expected behavior

The new Tab draws in the Session's effective Theme from its first frame, the same as every other Tab in the Session.

## Actual behavior

At step 3 the new Tab uses the app-wide Theme for the current appearance. At step 4 it changes to the Session's Theme.

## Notes

### Where it happens (checked on `main` at 699e7f0)

- `TabRuntime.init` (`BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift`) builds its `TerminalViewState(theme: Self.activeTheme())`. `activeTheme()` calls `ThemePreference.activeTheme()`, which is the global Theme. The Tab has no Session context at that point.
- `PaneRuntime.addTab(inheritingCWDFrom:)` (`Runtime/PaneRuntime.swift`) passes the Pane's and Session's **background** overrides into the new `TabRuntime` but no Theme. Every new-Tab path goes through it: `AppStateStore.addTab(toPaneID:inheritingCWDFrom:)` (tab-strip "+" and "Duplicate Tab" via `PaneView.addTabFocusingPane`), `BattyShortcuts` and `BattyCommands` (Cmd-T), `CommandPaletteView`, and `UITestDriver`.
- The Session Theme only reaches surfaces through `AppStateStore.applyTheme(_:to:)`, which `applyActiveSessionTheme(for:)` calls. In `SessionDetailView` that runs from `.onAppear`, `.onChange(of: selectedSessionID)` and `.onChange(of: selectedSession?.tree.allPanes.count)`. Adding a Tab doesn't change the Pane count, so nothing re-themes the new Tab.

### Split-created Panes (premise check)

The report asked about splits too. A split's new Pane also builds its first `TabRuntime` with the global Theme (`SplitTree` around line 428, through `PaneRuntime`). It gets fixed right away, though: the `allPanes.count` `onChange` re-applies the Session Theme, so in the selected Session a split shows the right Theme within one update. A split into a Session that isn't selected (for example `batty pane split` from the CLI) keeps the global Theme until that Session is selected, and selecting a Session always re-themes it, so you can't see the difference. The fix should still give split-created Tabs the right Theme when they are built. Then the `allPanes.count` re-theme can be reconsidered. It is a view callback that writes into terminal controllers (see `docs/swiftui-observation-rules.md`).

### Fix direction

- **Land this after #0584 and use its resolver.** #0584's plan (on unmerged branch `issue/0584`) replaces `SessionRuntime.localThemeName` with `themeOverride: ThemePair?` and adds `ThemePreference.effectiveTheme(override:isDark:defaults:)` as the single resolver. A fix written against `localThemeName` would be thrown away.
- Probable shape: a new Tab takes its starting `TerminalTheme` from its Session's effective Theme, not the global one. `PaneRuntime` already threads `sessionBackgroundOverride` to new Tabs (#0376), and the Theme override could follow the same path: Session → Pane → `TabRuntime.init`. The alternative is for `addTab` (and the split path) to call `controller.setTheme` right after creating the Tab. That runs inside the user-event handler, so it is not a view-update write. Either way, keep it out of view code.
- Appearance changes: `applyGlobalThemeForCurrentAppearance` → `applyThemeToAllSurfaces` skips overridden Sessions entirely. Under #0584's pair model, check that a Tab created after this fix still follows the Session pair's slot when the appearance flips.

### Related

- `WindowRuntime.duplicateSession(id:)` doesn't copy the source Session's Theme override, so a duplicated Session follows the app-wide Theme. That may be intended. Decide while working this, and file it separately if it's a bug.
- #0139 (per-Session Theme), #0147/#0149 (fallback chain), #0363 ("in effect" card), #0376 (Session background override threaded to new Tabs).
