# 0586 — A new Tab in a Session with its own Theme starts with the app-wide Theme until the Session is selected again

| | |
|---|---|
| **Status** | open |
| **Module** | Theme / Tabs / Session |
| **Platform** | macOS |
| **First seen** | 2026-11-11 |

## Description

Give a Session its own Theme (Sidebar "Set Session Theme…"). Then open a new Tab in it with Cmd-T, the tab-strip "+", or "Duplicate Tab". The new Tab's terminal draws in the app-wide Theme, not the Session's. It switches to the Session's Theme only when something re-applies the Session Theme: selecting another Session and back, or adding or removing a Pane in that Session.

Found while planning [#0584](0584.md). That issue turns the per-Session override into a Dark/Light pair and lets a Project set it, so most Project Sessions will carry their own Theme and this will show up much more often.

## Steps to reproduce

1. Select a Session. In the Sidebar, choose "Set Session Theme…" and pick a Theme that looks clearly different from the app-wide one.
2. Press Cmd-T (or click "+" in the tab strip, or right-click a Tab and choose "Duplicate Tab").
3. Look at the new Tab's terminal colors.
4. Select another Session, then select this one again.

## Expected behavior

The new Tab draws in the Session's effective Theme from its first frame, the same as every other Tab in the Session.

## Actual behavior

At step 3 the new Tab uses the app-wide Theme for the current appearance. At step 4 it changes to the Session's Theme.

## Notes

### Where it happens (checked on `main` at 699e7f0)

- `TabRuntime.init` (`BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift`) builds its `TerminalViewState(theme: Self.activeTheme())`. `activeTheme()` calls `ThemePreference.activeTheme()`, which is the global Theme. The Tab has no Session context at that point.
- `PaneRuntime.addTab(inheritingCWDFrom:)` (`Runtime/PaneRuntime.swift`) passes the Pane's and Session's **background** overrides into the new `TabRuntime` but no Theme. Every new-Tab path goes through it: `AppStateStore.addTab(toPaneID:inheritingCWDFrom:)` (tab-strip "+" and "Duplicate Tab" via `PaneView.addTabFocusingPane`), `BattyShortcuts` and `BattyCommands` (Cmd-T), `CommandPaletteView`, and `UITestDriver`.
- The Session Theme only reaches surfaces through `AppStateStore.applyTheme(_:to:)`, which `applyActiveSessionTheme(for:)` calls. In `SessionDetailView` that runs from `.onAppear`, `.onChange(of: selectedSessionID)` and `.onChange(of: selectedSession?.tree.allPanes.count)`. Adding a Tab doesn't change the Pane count, so nothing re-themes the new Tab.

### Split-created Panes (premise check)

The report asked about splits too. A split's new Pane also builds its first `TabRuntime` with the global Theme (`SplitTree` around line 428, through `PaneRuntime`). It gets fixed right away, though: the `allPanes.count` `onChange` re-applies the Session Theme, so in the selected Session a split shows the right Theme within one update. A split into a Session that isn't selected (for example `batty pane split` from the CLI) keeps the global Theme until that Session is selected, and selecting a Session always re-themes it, so you can't see the difference. The fix should still give split-created Tabs the right Theme when they are built. Then the `allPanes.count` re-theme can be reconsidered. It is a view callback that writes into terminal controllers (see `docs/swiftui-observation-rules.md`).

### Fix direction

- **Land this after #0584 and use its resolver.** #0584's plan (on unmerged branch `issue/0584`) replaces `SessionRuntime.localThemeName` with `themeOverride: ThemePair?` and adds `ThemePreference.effectiveTheme(override:isDark:defaults:)` as the single resolver. A fix written against `localThemeName` would be thrown away.
- Probable shape: a new Tab takes its starting `TerminalTheme` from its Session's effective Theme, not the global one. `PaneRuntime` already threads `sessionBackgroundOverride` to new Tabs (#0376), and the Theme override could follow the same path: Session → Pane → `TabRuntime.init`. The alternative is for `addTab` (and the split path) to call `controller.setTheme` right after creating the Tab. That runs inside the user-event handler, so it is not a view-update write. Either way, keep it out of view code.
- Appearance changes: `applyGlobalThemeForCurrentAppearance` → `applyThemeToAllSurfaces` skips overridden Sessions entirely. Under #0584's pair model, check that a Tab created after this fix still follows the Session pair's slot when the appearance flips.

### Related

- `WindowRuntime.duplicateSession(id:)` doesn't copy the source Session's Theme override, so a duplicated Session follows the app-wide Theme. That may be intended. Decide while working this, and file it separately if it's a bug.
