# 0396 — Closing a Session from the Sidebar bypasses the close-confirmation gate and emits no `session_destroyed` watch event, one instance of a layer-wide split between GUI and CLI mutation paths

| | |
|---|---|
| **Status** | open |
| **Module** | App / Session / Sidebar |
| **Platform** | macOS |
| **First seen** | 2026-09-03 |

## Description

`WindowRuntime.removeSession(id:)` (`BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift:191`) is the odd path out on two counts: it neither gates on `needsConfirmClose` before destroying every Terminal Session in the Session, nor emits the `session_destroyed` watch event — while its siblings do the first and its `AppStateStore` counterpart does the second. The Sidebar's "Close" control (`SessionSidebarView.swift:278-280`, the session context menu) calls it directly, so a human closing a Session from the Sidebar gets neither protection. Surveying the rest of `WindowRuntime` (below) shows this is not a one-off: watch-event emission lives almost entirely at the `AppStateStore` layer, and every GUI dispatch path that calls `WindowRuntime` (or `SplitTree`) directly sails past it — plus two cascades that skip the event even when the mutation *originated* from the CLI.

**1. No confirmation gate.** The other destroy paths sweep `needsConfirmClose` first and refuse or prompt:

- `WindowRuntime.requestCloseTab` — gate at `WindowRuntime.swift:358`, routes to a `PendingCloseRequest` dialog.
- `WindowRuntime.closePane` — gate at `WindowRuntime.swift:514`, returns `.needsConfirmation`.
- `WindowRuntime.requestCloseOtherTabs` — gate at `WindowRuntime.swift:409`.
- Window close / quit — `QuitConfirmation.windowNeedsConfirmClose` at `QuitConfirmation.swift:64`.

`removeSession` (`WindowRuntime.swift:191-219`) has no such sweep — it clears bell state, releases every Tab's terminal view, tears down non-terminal content, and removes the Session. Today this is **latent**: `TerminalViewState+Polyfill.swift:27` hard-codes `var needsConfirmClose: Bool { false }` (the polyfill's own comment at `:23` says it guards "against a future fork that declares `needsConfirmClose`"), so nothing prompts anywhere. The moment the libghostty fork exposes the real value, the asymmetry goes live: ⌘W on a Tab in that Session prompts, Sidebar "Close" on the whole Session silently kills every running process in it. Note also that the GUI's confirmation vocabulary has no shape for this — `PendingCloseRequest.Kind` (`Commands/PendingCloseRequest.swift:13-18`) has only `singleTab` and `otherTabs` cases, so gating this path means extending that vocabulary, not just calling it.

**2. No watch event.** The sole `session_destroyed` emitter on `main` is `AppStateStore.removeSession` (`AppStateStore.swift:782-783`; verified — `grep -rn "session_destroyed" BattyKit/Sources` finds exactly one `AppEventWatcher.send`, plus the enum case at `XPCWatchMessages.swift:87`). The Sidebar never reaches it: `windowRuntime.removeSession(id:)` contains no `AppEventWatcher.send`. Today `AppStateStore.removeSession`'s only callers are `UITestDriver.swift:62` and its own file — so on `main` the event effectively never fires in production at all. An agent using `batty watch` sees nothing when a human closes a Session from the Sidebar. (The `AppStateStore` emitter also fires *before* and *regardless of* the `windowOwning` lookup at `:786` — an unknown id emits `session_destroyed` for a Session that was never destroyed. Same method, opposite defect.)

The Sidebar path additionally skips a third counterpart-only behavior: `AppStateStore.removeSession` cancels any in-flight AI name-suggestion task first (`AppStateStore.swift:779`, impl at `:1519-1523`); the `WindowRuntime` path leaves that task running. Whether a late suggestion for a dead Session id has any observable effect was not traced here — noted for the implementer, not asserted as a bug.

## Expected behavior

One decision, made explicitly and applied consistently:

- Once `needsConfirmClose` is real, closing a Session from the Sidebar is never *more* destructive than ⌘W on one of its Tabs — either it prompts by the same rule, or a recorded decision says why session-level close is exempt.
- A `batty watch` subscriber's view of Session lifetime does not depend on which hand destroyed the Session (CLI verb, Sidebar click, or cascade from an emptied tree) — or, if it deliberately does, `batty watch`'s contract states exactly which origins emit, and #0145 builds against that statement.

This issue deliberately does **not** reopen what #0283 settled and #0382 followed: the XPC verbs stay *stricter* than the GUI (an unattended caller may not bypass a guard a human would see; no `--force`). The open question is only whether the GUI path should *acquire* the guard and the event, not whether the CLI should lose them.

## Survey — the pattern across `WindowRuntime` (verified on `main`, 2026-09-03)

Emitters on `main`, complete list: `AppStateStore.splitPane` → `pane_split` (`AppStateStore.swift:490-491`); `AppStateStore.addSession` → `session_created` (`:772-773`); `AppStateStore.removeSession` → `session_destroyed` (`:782-783`); `AppStateStore.focusSessionForXPC` → `session_focused` (`:981-982`); `AppStateStore.focusPaneForXPC` → `pane_focused` (`:1036-1037`); `AppStateStore.focusTabForXPC` → `active_tab_changed` + `tab_focused` (`:1071-1083`); and exactly one in `WindowRuntime`: `jumpToTab` → `active_tab_changed` (`WindowRuntime.swift:751-759`).

What skips them:

- **`session_created`** — every GUI new-session path calls `WindowRuntime.addSession` (`WindowRuntime.swift:159`) directly, bypassing the emitter: the Sidebar "+" (`SessionSidebarView.swift:94`), `BattyShortcuts.swift:116`, the menu items at `BattyCommands.swift:62` and `:92`, and the Command Palette (`CommandPaletteView.swift:210`). The only production caller of the emitting `AppStateStore.addSession` is the URL handler (`BattyURLHandler.swift:28`).
- **`session_destroyed`** — the Sidebar (`SessionSidebarView.swift:279`), plus two **cascades**: `WindowRuntime.closeTab` removes the Session when a pane's last Tab closes and the tree empties (`WindowRuntime.swift:308-311`), and `WindowRuntime.closePane` does the same (`:536-539`) — both call `WindowRuntime.removeSession`, never the emitter. The cascade case matters because `AppStateStore.closePane` (`AppStateStore.swift:576-582`) — the CLI `batty pane close` path — delegates to `WindowRuntime.closePane`: a **CLI-initiated** pane close that empties a Session destroys that Session with no `session_destroyed`. The skip is therefore not confined to GUI-origin mutations.
- **`pane_split`** — `WindowRuntime.createPane` (`WindowRuntime.swift:484`) documents a deliberate bypass of `AppStateStore.splitPane`'s emission (doc comment at `:459-468`), and the GUI terminal splits it cites as precedent call `SplitTree` directly with no event: `SessionDetailView.swift:135-151`, `CommandPaletteView.swift:226-238`, `BattyShortcuts.swift:135-147`.
- **`active_tab_changed`** — emitted by `jumpToTab` (Open Quickly, `OpenQuicklyView.swift:149`; notification jump via `AppStateStore.jumpToTab:948-951`) and by `focusTabForXPC`, but not by: `jumpToBellEntry` (`WindowRuntime.swift:763-777`, writes `activeTabID` at `:776`, immediately adjacent to the emitting `jumpToTab`), the GUI tab-chip selection binding (`PaneView.swift:553-563`), or `PaneRuntime`'s select/next/previous tab moves (`PaneRuntime.swift:232`, `:240`, `:248`).
- **`tab_created`** — in the vocabulary (`XPCWatchMessages.swift:89`, and `allNames` derives from `allCases`, so `batty watch` accepts it as a filter) with **zero emitters anywhere** on `main`. A subscriber can filter on an event that cannot fire.
- **Not skips, but absences**: no `pane_close`, pane-hidden, or pane-shown vocabulary exists at any layer (`hidePane`/`showPane` at `WindowRuntime.swift:663`/`:714`, `AppStateStore.swift:915`/`:925` are silent on both layers) — #0382's notes already flag the coverage decision for the verbs it adds.

## Deliberate or accidental?

The evidence supports **accidental placement, later rationalized once** — not a designed "GUI actions are the human's own, so they emit nothing" rule:

- Against a deliberate GUI-silence rule: `WindowRuntime.jumpToTab` emits from a GUI path (`WindowRuntime.swift:751-759`, comment "#0145: notify the active XPC watchers"); `WatchEventPayload.fromCli` (`XPCWatchMessages.swift:21`, default `false` at `:32`) exists precisely "for disambiguating app vs CLI activity", which only makes sense if app-origin emissions were envisioned; and #0381's own doc comment states the principle outright — a `batty watch` subscriber "must not silently miss a change" (`AppStateStore.swift:1047-1053`). The CLI-origin cascade hole (pane close emptying a Session) violates even the hypothetical rule.
- For deliberateness, exactly one datum: `createPane`'s doc comment (`WindowRuntime.swift:459-468`) — but it justifies the bypass by *matching the existing GUI splits' behavior*, i.e. it cites the status quo as precedent rather than stating a principle.

Reading: #0145's initial emitters were attached to the XPC-facing `AppStateStore` entry points as verbs shipped (#0282, #0381), GUI dispatch happens to call `WindowRuntime`/`SplitTree` directly, and nothing ever decided the layering. `createPane` then locked one instance in with a comment.

## Candidate directions (deliberately not decided here)

Like [#0332](0332.md) and [#0395](0395.md), this asks for the property, not a mechanism. Candidates, with their known trade-offs:

- **Route the Sidebar's Close through `AppStateStore.removeSession`** — the event (and the name-suggestion cancellation) come for free. But *not* the gate: `AppStateStore.removeSession` has no confirmation sweep either — on `issue/0382` the gate lives in the new `closeSessionForXPC` wrapper, not in `removeSession`. A GUI gate would still need a `requestRemoveSession`-style path (mirroring `requestCloseTab` vs `closeTab`) plus a new `PendingCloseRequest.Kind` case. Also inherits the counterpart's emit-before-validate defect noted above.
- **Add the gate and the emission to `WindowRuntime.removeSession` directly** — every caller (Sidebar, both cascades, `AppStateStore`) gets both at once, and `jumpToTab` is precedent for emitting from this layer. Trade-offs: the cascades arrive having already passed their own gates, so the sweep is redundant there (harmless, but worth a comment); and the XPC path would double-emit unless `AppStateStore.swift:782-783` moves down in the same change.
- **Declare the split deliberate and document it** — GUI-origin mutations emit nothing; `batty watch`'s contract states precisely which origins emit (today: some XPC verbs, the URL handler's session create, Open Quickly / notification tab jumps — minus the cascades), and #0145 builds to that contract. Cheapest, but the CLI-origin cascade hole and the dead `tab_created` filter are inconsistent with any contract worth writing down, so at minimum those still need fixing or explicit documenting.
- **Hand the event half to #0145** — it owns the watch stream and is `in-progress` on its own branch (`issue/0145`). The evidence supports this for the *coverage* question specifically: the emission holes span five event types across two layers, which is a stream-design decision, not a `removeSession` patch. The confirmation-gate half is independent of #0145 and can proceed on its own either way. Coordinate rather than duplicate; #0382's notes already say the same for its verbs.

## Notes

- All `file:line` citations are against `main` at filing time. The findings were surfaced during #0382's review with line numbers from that branch (`AppStateStore.removeSession` sits at `:844-853` there); everything was re-verified against `main` and the numbers here reflect it.
- **Branch context**: `issue/0382` (unmerged; commits `eb35671`, `13a1a85`) adds `closeSessionForXPC`, which gates on `needsConfirmClose` and routes through the emitting `AppStateStore.removeSession` — the CLI verb gets both properties; the Sidebar path is untouched. Its doc comment describes the reused `removeSession(id:)` as "the Sidebar's own 'Close' control, which already emits the `session_destroyed` watch event … regardless of caller" — false of the Sidebar's actual call target (`WindowRuntime.removeSession`), while the same file's `SessionCloseOutcome.needsConfirmation` comment correctly says the Sidebar "applies no such gate today". Two same-named methods on adjacent layers got conflated within a single reviewed diff — a live demonstration of why this split is a trap, and something for whichever fix lands to correct in passing if #0382 merges as-is.
- The original report framed the event half as GUI-only ("an agent … silently misses a human closing one from the Sidebar"). The survey found it wider: the `closePane`/`closeTab` cascades skip the event for CLI-origin mutations too, and the create side (`session_created`) has the same GUI-wide skip as the destroy side. Nothing in the report turned out narrower than described; the two prompt line numbers that had drifted are corrected above.
- `removeSession` already carries a scar from the same shape of problem: its `tearDownNonTerminalContent` call exists because #0314's review found this exact path skipping a teardown step the "single choke point" story claimed was universal (comment at `WindowRuntime.swift:203-208`). The method has a track record of being the path everyone forgets.
