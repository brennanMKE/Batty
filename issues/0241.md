# 0241 — Theme does not adapt to Dark/Light mode; store a separate theme per appearance

| | |
|---|---|
| **Status** | open |
| **Module** | Theme / Settings |
| **Platform** | macOS |
| **First seen** | 2026-06-15 |

## Description

The active Theme does not adapt when the user switches the system (or app) appearance between Dark and Light. A theme chosen while in Dark mode stays applied when macOS flips to Light, so a dark-on-black palette is left running against a light desktop (and vice versa), which reads poorly. We should keep a separate theme preference for each appearance — a Dark theme and a Light theme — pick reasonable defaults for both, and when the user changes the theme, store it against the appearance that is currently active. On an appearance change the matching theme is re-applied automatically.

Ghostty already supports this via its text config (`theme = light:<name>,dark:<name>`); Batty should offer the equivalent through its existing Theme UI rather than a config file.

## Steps to reproduce

1. Launch Batty in Dark mode and pick a dark theme from the Theme selector.
2. Switch macOS to Light appearance (System Settings → Appearance, or the auto Dark/Light schedule at sunset/sunrise).
3. Observe the terminal palette.

## Expected behavior

- Two independent theme preferences are persisted: one used while the appearance is Dark, one while it is Light.
- Reasonable built-in defaults are seeded for both modes so a fresh install looks correct in either appearance without the user configuring anything.
- Changing the theme writes to the slot for the **currently active** appearance only — choosing a theme in Light mode does not disturb the Dark choice.
- When the appearance changes (manual toggle or the auto schedule), the theme for the new appearance is applied live to all surfaces that follow the global theme, and the View → Theme chrome updates to match.

## Actual behavior

A single global theme is stored and applied regardless of appearance. The selected theme persists across a Dark↔Light switch, leaving a mismatched palette until the user manually reopens the Theme selector and picks something else.

## Notes

Current design (for whoever picks this up):

- `ThemePreference` (`BattyKit/Sources/BattyKit/Theme/ThemePreference.swift`) stores one global theme name under a single `UserDefaults` key, `co.sstools.Batty.themeName` (`ThemePreference.defaultsKey`). There is no appearance dimension.
- `ThemeSelectorView.selectTheme` (`BattyKit/Sources/BattyKit/Views/ThemeSelectorView.swift:139`) writes that one key and calls `store.applyThemeToAllSurfaces`.
- `AppStateStore.applyActiveSessionTheme` resolves the fallback chain `session.localThemeName → global key → none`. The per-session `localThemeName` override mechanism should be preserved; this change is about the *global* slot becoming two slots (Dark / Light).
- A grep for `effectiveAppearance` / `NSAppearance` / `colorScheme` across `Batty` and `BattyKit/Sources` returns nothing — there is currently no appearance observation anywhere, so the work includes observing appearance changes (e.g. `NSApp.effectiveAppearance` / KVO on `effectiveAppearance`, or a SwiftUI `@Environment(\.colorScheme)` bridge) and re-running theme application when it flips.

Design sketch:

- Replace the single global key with two keys (e.g. `…themeName.dark` and `…themeName.light`), or one composite preference. Keep `defaultsKey` resolution backward-compatible — migrate an existing single value into the slot matching the appearance at first launch after upgrade so current users don't lose their choice.
- Add appearance observation that, on change, resolves the global theme for the new appearance and calls the existing `applyThemeToAllSurfaces` path.
- The Theme selector and the View → Theme menu should make it clear which appearance's slot is being edited (it follows the current appearance), per `docs/swiftui-observation-rules.md` for any observed-state writes triggered by appearance flips.

This is a feature/enhancement rather than a regression; scope is terminal theming only (per project scope).
