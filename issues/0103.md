# 0103 — Crash: `PaneRuntime.activeTab` force-indexes empty `tabs` when closing the last tab in a pane

| | |
|---|---|
| **Status** | open |
| **Module** | PaneRuntime / TabRuntime |
| **Platform** | macOS |
| **First seen** | 2026-05-13 |

## Description

Closing a pane crashed with `Thread 1: Fatal error: Index out of range` on:

```
BattyKit/Sources/BattyKit/PaneRuntime.swift:27
    tabs.first { $0.id == activeTabID } ?? tabs[0]
```

`activeTab` is a non-optional computed property that falls back to `tabs[0]` when `activeTabID` no longer matches any tab. But `PaneRuntime.removeTab(id:)` deliberately allows `tabs` to become empty (the comment on line 39–41 says so: *"Allows the pane to become empty — callers must handle the empty case (typically by removing the pane)"*). During the close-pane cascade there's a window between "last tab removed" and "pane removed" where `tabs` is `[]` and `activeTab` is reachable.

Likely re-entry paths into `activeTab` during that window:

- SwiftUI re-evaluating `PaneView` after `tabs` mutation but before `SplitTree` prunes the empty pane. `PaneView.swift:60` (`pane.addTab(inheritingCWDFrom: pane.activeTab)`) and `PaneView.swift:143–144` (the new drag-hover overlay from #0102 — `pane.activeTab.isDragHovering`) both read `pane.activeTab` during view body recomputation.
- Other call sites that read `.activeTab` synchronously: `SessionDetailView.swift:153`, `BattyShortcuts.swift:88`, `PasteConfirmation.swift:105`, `SplitTree.swift:83`, `AppStateStore.swift:47`.

The #0102 fix added two new `pane.activeTab.isDragHovering` reads on every `PaneView` body recomputation, which is the most plausible trigger that surfaced this latent bug now. But the root issue — `activeTab` claims to be non-optional while the model permits an empty `tabs` — has been there since `removeTab` was written.

## Steps to reproduce

The exact gesture wasn't captured, but the crash fired while closing a pane. Reliable repro path is likely:

1. Open a session with one or more panes.
2. In a pane with exactly one tab, close that tab (via chip close button, ⌘W, or "Close Tab" context menu).
3. The pane-close cascade removes the last tab; SwiftUI re-renders before the pane itself is removed; one of the `pane.activeTab` readers hits an empty `tabs` and the `tabs[0]` fallback traps.

## Root cause

The type signature lies. `PaneRuntime.activeTab: TabRuntime` promises a non-optional, but the underlying `tabs` array is allowed to be empty. The `?? tabs[0]` fallback was written assuming `tabs` is never empty, but `removeTab` explicitly weakens that invariant for the close-pane handoff. The first reader that touches `activeTab` between "last tab removed" and "empty pane pruned" crashes.

## Fix

Two reasonable shapes:

1. **Make `activeTab` optional.** Change to `var activeTab: TabRuntime? { tabs.first { $0.id == activeTabID } ?? tabs.first }`. Update every call site to handle `nil` — most are SwiftUI bodies that can short-circuit with `if let activeTab` or `pane.activeTab?.isDragHovering ?? false`. This is the honest model: an empty pane has no active tab.

2. **Tighten the model so `tabs` is never empty.** Re-enforce the `precondition(!initial.isEmpty, …)` from `init` as an invariant — make `removeTab` of the last tab a no-op (or rename to make the contract explicit, e.g. `removeTabIfNotLast`), and require the close-pane path to remove the *pane* (which removes its tabs along with it), never to drain a pane to zero. This avoids changing every caller but pushes the responsibility onto the close-pane cascade.

Option 1 is smaller and more honest; option 2 matches the original precondition in `init`. Subagent should pick based on which keeps the `AppStateStore` close-tab/close-pane cascade simplest. Either way, also audit the cascade to ensure the SwiftUI observer doesn't re-read `activeTab` for an about-to-be-pruned pane (pane removal should happen in the same observation batch as the last-tab removal, or `PaneView` should be gated by a `tabs.isEmpty` check upstream).

## Acceptance criteria

- Closing the last tab in a pane removes the pane without crashing, regardless of how the close was triggered (chip close, ⌘W, context menu, app-store close).
- Closing a tab in a pane that has siblings continues to work as before — active selection moves to the previous tab.
- No `pane.activeTab` call site assumes `tabs` is non-empty; if option 1 is taken, every reader handles `nil` explicitly.
- Add a unit test: a `PaneRuntime` with one tab, remove that tab, then read `activeTab` — must not crash. (Test will fail today.)

## Notes
