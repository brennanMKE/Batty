## Description

`batty new` without `--no-wait` is the path agents use to get back the new Session's id and Pane id (`docs/batty-cli-agent-workflows.md`, which also warns about agents racing it on the same path). It takes a pre-dispatch snapshot, dispatches through `openURL`, then polls for the new Session. `NewSessionCommand.pollForNewSession` is fully covered by `NewSessionCommandTests`, because both `resolveEndpoint` and `fetchTopology` are injected closures. The two call sites that *feed* it are not covered. Both call `BrokerAppEndpointClient.fetchEndpoint` directly, so any test that reaches them tries a real XPC connection to the broker's Mach service:

1. **`NewSessionCommand.fetchPreDispatchState(resolveAppBundle:isAppRunning:)`** (`BattyKit/Sources/batty/NewSessionCommand.swift`). It calls `BrokerAppEndpointClient.fetchEndpoint(timeout: snapshotTimeout)`, then maps the result:
   - `.unreachable` → `.degraded`
   - `.endpoint(.some)` → `AppServiceClient.list(…)`, then `.ready(endpoint:snapshot:)`, or `.degraded` if `list` fails
   - `.endpoint(.none)` → bundle resolve plus `NoEndpointRegisteredDecision`, then `.notRunningYet` or `.degraded`

   `resolveAppBundle` and `isAppRunning` are already injectable. The broker fetch is not. The `AppServiceClient.list` call in the `.ready` arm is not either.
2. **The `.notRunningYet` arm's `resolveEndpoint:` closure in `run()`** (the cold-launch wait). It is written inline in `run()` and calls `BrokerAppEndpointClient.fetchEndpoint(timeout: Self.pollRequestTimeout)` on every attempt until it gets an endpoint, which it caches in `cachedEndpoint`. It also sets the captured `lastFetchWasBrokerUnreachable` flag. On a `.timedOut(endpointEverSeen: false, …)` outcome, that flag decides between exit `2` (`XPCExitCode.brokerUnreachable`) and exit `3` (`XPCExitCode.appUnavailable`) (#0380 round 3 review, N8). Neither the caching nor the exit-code choice is tested.

This is the same untestability that #0365 fixed for `AppConnectDance.resolveEndpoint`. Both `NewSessionCommandTests`' type-level doc comment and `pollForNewSession`'s doc comment name these two call sites as the gap that is still open.

## Expected behavior

Both call sites go through a `fetchEndpoint: (TimeInterval) -> BrokerAppEndpointClient.Result` seam that defaults to `{ BrokerAppEndpointClient.fetchEndpoint(timeout: $0) }`. That is the exact signature and default #0365 gave `AppConnectDance.resolveEndpoint`. `fetchPreDispatchState` also needs a `list`/`fetchTopology` seam for its `.ready` arm. The cold-launch closure moves out of `run()` into a testable unit (for example, a static helper or a small type) that owns `cachedEndpoint` and `lastFetchWasBrokerUnreachable`, so the exit-`2`-vs-`3` choice can be checked without calling `run()`. Tests pin:

1. **`fetchPreDispatchState` mapping.**
   - `.unreachable` → `.degraded`. The bundle resolve and running check are not consulted.
   - `.endpoint(.some)` with a successful list → `.ready` carrying that snapshot.
   - `.endpoint(.some)` with a failed list → `.degraded`.
   - `.endpoint(.none)` with the app not running → `.notRunningYet`.
   - `.endpoint(.none)` with the app running → `.degraded`.
   - `.endpoint(.none)` with the bundle resolve failing → `.degraded`.
   - The fetch is called exactly once, with `snapshotTimeout`.
2. **Cold-launch `resolveEndpoint`.**
   - `.endpoint(.none)` and `.unreachable` both return `nil`.
   - The first `.endpoint(.some)` is returned and cached, so later calls make **no** further fetches.
   - The fetch is called with `pollRequestTimeout`.
   - The flag tracks the *last* fetch: `.unreachable` followed by `.endpoint(.none)` clears it.
3. **Exit mapping on `!endpointEverSeen` timeout.** A persistently `.unreachable` broker → exit `2`. A persistent `.endpoint(.none)` → exit `3`.

Fixtures must make each assertion non-vacuous. For example, the "no further fetch after caching" test needs a fetch stub that would return something *different*, or record the call, if it were called again.

## Notes

- `run()` also calls `openURL(url)` with defaults, and that spawns a real `/usr/bin/open` (#0414). This issue does not need `run()` to be unit-testable end to end. Extracting the two call sites and the exit mapping is enough, so it does not depend on #0414. A later full-`run()` test would need both seams.
- When this lands, update the doc comments that describe the gap: `NewSessionCommandTests`' type-level comment and `pollForNewSession`'s doc comment. Grep for every claim a rewritten comment makes.
- The comment above `fetchPreDispatchState()` in `run()` explains why it is deliberately non-launching: it uses `BrokerAppEndpointClient`/`RunningAppChecker` directly rather than `AppConnectDance`, so `open` stays the only launch path. Adding the seam must not route either call site through `AppConnectDance.resolveEndpoint`, which can launch.

## Resolution notes

> 🟢 Resolved 2026-09-23 — both of `NewSessionCommand`'s broker fetches are now seamed, and the `batty new` pre-dispatch, cold-launch wait, and exit-2-vs-3 decision are unit-tested without a real broker.

## Root cause

`fetchPreDispatchState` and `run()`'s inline `.notRunningYet` `resolveEndpoint:` closure called `BrokerAppEndpointClient.fetchEndpoint` directly, the `.ready` arm called `AppServiceClient.list` directly, and the closure owned the `cachedEndpoint` / `lastFetchWasBrokerUnreachable` state that decides exit 2 vs 3.

## Fix

- `fetchPreDispatchState` gained `fetchEndpoint` and `fetchTopology` seams (defaults are the real calls; `run()` passes none).
- The inline closure became `ColdLaunchEndpointResolver` (a nested `final class`, so `resolve` can be passed as the closure), owning the cache and the last-fetch flag; `init(timeout:)` defaults to `NewSessionCommand.pollRequestTimeout`, which `run()` relies on.
- The exit decision is pure `notFoundExitCode(lastFetchWasBrokerUnreachable:)`: exit 2 when the poll's last broker fetch was unreachable, exit 3 otherwise. Both call sites stay non-launching and outside `AppConnectDance`.
