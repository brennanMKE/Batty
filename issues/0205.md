
The runner gets translocated to `~/.Trash/...` and immediately killed. This
is a system-level signing/quarantine issue, not a code bug. The ad-hoc
codesigning produced by `CODE_SIGN_IDENTITY=-` plus `com.apple.provenance`
xattrs on the build products tripped Gatekeeper. Result: every
`xcodebuild test` invocation returns "Early unexpected exit, operation never
finished bootstrapping — Test crashed with signal kill before establishing
connection." with zero test cases run.

What was investigated:

- The four tests in `TabRenameTests.swift` (`#0202` `#0203` `#0204` `#0205`)
  appear to share a single root cause — all four assert on
  `tab-chip.<title>` accessibility identifiers, and per the issue tracker
  all four fail on `[[0170]]`-stabilized runs. The two-intent test
  (`testResetActiveTabTitleClearsOverride`) and the home-dir test
  (`testRenameWinsOverHomeDirTilde`) both end up with `titleOverride = nil`
  at query time, identical to the passing `testEmptyRenameIsNoOp`.
- Reading `BattyKit/Sources/BattyKit/Views/PaneView.swift:90` shows the
  identifier is computed inline:
  `.accessibilityIdentifier("tab-chip.\(chipTitle(for: tab))")`. The chip
  closure is then wrapped by `SlidingTabBar`'s outer
  `.contentShape(Rectangle()).onTapGesture(...).accessibilityAddTraits(.isButton)`.
  Likely culprit: SwiftUI consolidates the chip's inner accessibility
  element when the outer button-trait wrapper is applied, and the inner
  `.accessibilityIdentifier` is dropped from the merged element. This is a
  known shape-of-bug with SwiftUI accessibility on macOS.
- `TabTitleFormatter.chipTitle` returns "Tab" (fallback) or "~" (home cwd)
  at minimum — never empty — so the identifier is never bare `tab-chip.`.
- Driver intents in `UITestDriver.swift` run synchronously inside `.task`,
  so `renameActiveTab("Temporary")` followed by `resetActiveTabTitle` both
  fire before any assertion runs.

Proposed fix to try (NOT verified):

Add `.accessibilityElement(children: .combine)` between `.frame(...)` and
`.accessibilityIdentifier(...)` on the chip in `PaneView.swift:89-90` so
the chip becomes a single combined accessibility element with a stable
identifier, surviving SlidingTabBar's outer button-trait wrapping. Caveat:
this collapses the inner `onClose` button's accessibility into the chip,
which may break a future test of the close button — but no current test
queries it.

Bailing rather than committing the unverified fix because the user's
memory note (`feedback_run_tests_before_resolving.md`) requires
`xcodebuild ... test` to pass before resolving any test-writing issue,
and the runner-kill prevents that here. Next subagent on a machine where
the UI test runner runs cleanly should apply the proposed fix and verify
the four `TabRenameTests` pass together.
