## Description

A Session opened from a Project keeps its appearance (backgrounds and Theme) in two places: the Project definition, and a separate set of runtime overrides on the Session, its Panes and its Tabs. Open copies the Project into the runtime overrides and records seeds. From then on, each copy is edited on its own. Update Project reconciles them with seed and diff rules. Every background sheet reads only its own level, so what a sheet shows, what the terminal shows and what the Project stores can all differ.

The user, on Batty Beta built from 6ea4abc, reported the bug that shows it:

> "there is a consistency issue. I just opened a project after I selected the background image for a terminal tab. but later I tapped the gear button to adjust opacity and it showed the pane was not customized. I had to change it to custom but then it cleared the image before I selected another one again. this all needs to be made consistent."

Their screenshot (no longer available) shows the Sidebar with Session "Batty" and a Pane row "1/1 — Claude". The row has the gear (Pane Background…) and the eye button. The eye is the Pane's show/hide toggle, not see-through.

The user then set the scope, in their words:

> "We need Projects to apply the state for a session and all panes and tabs. There should not be 2 separate states being managed."

For a Session opened from a Project, the Project is the single source of truth for that Session's appearance at every level. Edits made in the running Session save straight to the Project, and the runtime renders from it. See User decisions.

## User decisions (2026-11-12)

The first two decisions recorded here at filing ("edits save straight to the Project", "appearance only") were **superseded the same day** by the user's clarification. In their words: "Projects are meant to be a saved snapshot of a session that the user wants to restore repeatedly. So anything they can do in a session can be persisted in a Project so it can be restored when opening a Project." Asked whether a change in a running Project Session should change the Project right away or only on save, the user chose **only when I save**.

- **A Project is a snapshot.** The running Session is the one live state. Changes in it (backgrounds, opacity, Theme, see-through, Splits, Tabs, names, directories, commands) don't touch the Project until **Update Project** (or **Save as Project**).
- **Complete capture and restore.** Update Project / Save as Project capture *everything* a Session can hold: layout, Tabs, Tab names, working directories, startup commands, and appearance at every level a Session supports — Session, Pane and Tab backgrounds (image, fit, position, image and terminal opacity), the Theme pair, and see-through. Opening the Project restores all of it exactly. Anything a Session can do that a Project can't store is a gap to close here.
- **No reconciliation rules.** Because opening restores the snapshot exactly and Update captures the whole current state, Update writes what the Session shows; the per-field seed rules (`projectBackgroundSeed`, `projectThemeSeed`, the per-Tab seeds) exist only to paper over the two-state model and should go. *(Orchestrator's reading; the planner confirms nothing else depends on them.)*
- **Project Editor edits the snapshot only.** Editing a Project in the editor doesn't change an open Session of it; reopening applies it. *(Orchestrator's decision; the user delegated decisions. It follows from "snapshot".)*
- **Pane level in the Project.** The runtime has Session, Pane and Tab background levels, so the Project stores all three (add a Pane background to the Project's Pane), rather than fanning a Pane value out to Tabs. *(Orchestrator's decision, answering open question 1.)*
- **Sessions not opened from a Project** are unchanged.
- **Background sheet behaviour** (orchestrator's decision): keep #0585's rule that a Pane gear write applies to every Tab in the Pane. Every background sheet opens showing the effective value the visible terminal shows, and names its source: this Tab, Pane, Session, Project or Settings. Custom seeds from that value, never from a value with no image. Changing only the opacity keeps the image.
- Expected behavior below was written for the superseded write-through model; where it says edits write to the Project or update open Sessions live, these decisions win.

## Resolution notes

> 🟢 Resolved 2026-11-12 — A Project is now a full snapshot of its Session (every background level, Theme, split sizes, hidden Panes, active Tabs, focus, mute, Pane-list expansion, per-Tab startup commands) captured only by Update / Save as Project and restored exactly on open, and every background sheet shows and seeds from the effective value with its source, so the Pane gear over a Tab's image shows Custom and an opacity-only change keeps the image.

## Review

Round 1, approved first pass (claude-opus-5-5, medium). Re-ran the build, the UI type-check, the filtered suites and the full unit tier (below). Checked:

- **Motivating bug.** `PaneRuntime.isCustomized` counts Tabs' own values; the gear reads `showsCustomBackground`; the editor's `update` transforms the shown (active Tab's effective) value, so an opacity-only edit carries the image to the Pane level (`editingOpacityOnATabSourcedPaneKeepsTheImage`).
- **Split sizes.** Capture multiplies each binary ratio down a same-direction chain and records pre-order; restore walks the same pre-order (`chains` reserved on entry to `expand`) and sets `f_i / sum(f_i...)` on the split found by its two sides' first leaves, which is unique in the right-nested chains `splitPane` builds. The column-major 2x2 permutation `[rows-left, cols, cols]` matches the row-major preset's pre-order. Bad stored sizes can't fail an open: `validFractions()` rejects a shape mismatch, NaN and values outside (0, 1); restore needs only positive values (it renormalizes), and `updateRatio` clamps to 0.05-0.95.
- **Pending flags.** `pendingProjectImage` is set in `openProject` after `addProjectSession`, whose own `setBackgroundOverride` would otherwise clear it. The Pane's is set after the non-clearing `restoreBackgroundOverride`; Tabs' at construction, and the Session mirror push doesn't clear them. Every user write clears its level; arrivals apply only to a pending level.
- **Startup commands.** Only the stored command moves with its Tab; arming still reads `project.startupCommands` and checks `startupCommandsHash` and the run toggle, so the trust prompt isn't bypassed, and a reordered set re-prompts.
- **Name on Update.** Project Session titles are pinned (`titleOverride`), so only an explicit Sidebar rename differs from the Project name; Update proposes it in the Editor draft, whose `validate()` refuses a case-insensitive clash. Under the snapshot decision this is captured state, not a silent rename. Accepted.
- **Identity-less Tab images dropped on Update.** Only a hand-written or pre-#0585 Project with a missing image file; the file is already gone on this Mac. Accepted.
- **Observation rules.** Source, note and gear state are computed reads in `body`; no new writes from view updates.
- **Carved out (to file).** The `## Gotchas` pending-image edge is wider than stated, and is a regression from main's seeds; see "Follow-up to file" below. Narrow (needs an image withheld at open, a sheet Cancel, then an explicit Update), so not blocking.

### Follow-up to file

**Cancel in a background sheet ends a withheld image's pending state, so Update Project drops the image.** `BackgroundOverrideEditor.cancel()` restores through the clearing setters: for a Pane whose Tabs have own values, Cancel (even with no edit) calls `PaneRuntime.setBackgroundOverride`, which clears every Tab's `pendingTabImage` and the Pane's `pendingImage` before `restoreReplacedOverrides` puts the values back; for a Tab or Session sheet, an edit then Cancel clears `pendingTabImage` / `pendingProjectImage`. Then (a) an image still downloading no longer reaches that level, and (b) Update Project writes that level without its image identity, and for the Session sets `draft.sharedImage = nil`, so a Shared Project publishes the image's removal to every Mac. Removing an image in the Background Images window restores a Pane's Tabs the same way. Fix: Cancel must restore the pending state it started with (snapshot it with `originalOverride` / `replacedOverrides` and restore through non-clearing setters), with tests for each level.

## Root cause

Confirmed in code, as the plan's premises say. Every background sheet read only its own level: `BackgroundOverrideEditor.isFollowing` was `target.backgroundOverride == nil`, `current` was own ?? inherited, and `PaneRuntime.inheritedBackground` skipped the Tabs. So a Pane whose only value was a Tab's showed Follow, seeded Custom from the Session or Settings value (no image), and `update` did nothing while following. The Sidebar gear read only `pane.backgroundOverride`. Behind that, a Project Session kept appearance twice: the Project, and runtime overrides plus seeds (`projectBackgroundSeed`, `projectThemeSeed`, per-Tab seeds) that Update Project reconciled field by field. Update also carried startup commands by slot and Tab index, dropped split sizes, saved hidden Panes as visible, and fanned a Pane value out to its Tabs because the Project had no Pane level.

## Fix

Implemented the plan's seven checkpoints in order, under the User decisions (Project = snapshot, saved only by Update Project / Save as Project).

1. **Sheets.** `BackgroundOverrideHolder` gains `effectiveBackground(appWide:) -> EffectiveBackground` (value + `BackgroundSource`), `isCustomized` and `narrowerLevelsNote`; `inheritedBackground` is gone. The editor follows `!isCustomized`, shows and seeds from the effective value, and `update` transforms the shown value. A Pane is customized while it or any Tab has a value, and shows the active Tab's effective value. The sheet shows a source caption (`<prefix>.source`) and a note (`<prefix>.note`). The gear uses `pane.showsCustomBackground`. Editor: `.projectTab(followsPane:projectHasBackground:)` and "Follows Settings" when the Project has no background.
2. **Model.** `ProjectPane` gains `background`, `image`, `isHidden`, `activeTab`; `ProjectLayout` gains `focusedSlot`, `splitFractions` and `validFractions()`; `Project` (and `ProjectSyncRecord`) gain `notificationsMuted`, `paneListExpanded`. Each is written only when set, so old records encode byte-identically. `backgroundEntries` / `mappingBackgroundEntries` re-base the Tab-image helpers so Pane images use the Tab identity, sync, merge, resolve and sweep machinery. `mappingTabs` / `mappingTabBackgrounds` copy the layout instead of rebuilding it, so focus and sizes survive.
3. **Capture.** `SessionProjectCapture` records hidden state, active Tab, focus, `paneIDs`, each Tab's `projectStartupCommand`, and split fractions (each flattened chain member's share, rounded to 4 decimals with the last entry renormalized). `updateDraft` takes the layout whole. `SaveSessionAsProject` has one capture path: Session background (kept as stored only while the open withheld its image), each Pane's and Tab's own value with identities kept from the stored Project by digest, Theme always, mute, expansion, and on Update the Session title and color.
4. **Restore.** `ProjectTreeBuilder` sets each Tab's command, the active Tab, the Pane background via the non-clearing `PaneRuntime.restoreBackgroundOverride`, and applies valid fractions to the right-nested chains `splitPane` builds (ratio `f_i / sum(f_i...)`, split found by its two sides' first leaves). `addProjectSession` sets mute, hides Panes through `hidePane`, restores focus, then sets the Pane-list expansion last.
5. **Seeds removed.** Replaced by `SessionRuntime.pendingProjectImage`, `PaneRuntime.pendingImage` and the existing `TabRuntime.pendingTabImage`, each cleared by any write to that level. Arrivals apply only to a level still pending.
6. **Editor Pane level.** `ProjectPaneBackgroundTarget`, `setPaneBackground` (replaces the Pane's Tab values), `paneBackgroundSummary`, a Background row in `PaneInspector` (`project-editor.pane.background.*`, sheet prefix `project-pane-background-sheet`); Tab summaries and sheets say Follows Pane / Project / Settings.
7. **Docs.** `Concepts.md` 0.30, `docs/design/projects-sharing.md`, the Projects help page, and the doc comments that said "seeds" or "in memory only".

Deviations and choices (conservative, user asleep):

- **Column-major 2x2 grid sizes.** A grid built by `PaneLayout.apply` has per-column row splits, which a row-major grid can't express. Capture stores the left column's row split for the rows and the column split for both rows. A grid opened from a Project is row-major, so it round-trips exactly.
- **UI test `testPaneGearReplacesATabsOwnBackground`** drags the terminal-opacity slider instead of toggling `opacity-cells`: that toggle is disabled at 100% terminal opacity, the default, so the plan's step would be a no-op.
- **A Tab image with no identity** (a hand-written or pre-#0585 Project) that is missing at open is dropped on Update, because with no identity there is nothing to keep. The plan's tests for that case were the seed tests it removes.
- `PaneRuntime.pendingImage` was added in checkpoint 3 rather than 5, because capture already reads it.
- Update takes the Session title as the name when it differs from the Project name. The Editor's existing uniqueness check runs before Save.

## Plan

Written 2026-11-12 against `issue/0589` at 09c6206. **`## User decisions` is binding and supersedes `## Expected behavior` wherever that section says edits write through to the Project, the runtime renders from the Project, the Editor updates open Sessions live, a remote merge re-renders open Sessions, or Update Project stops capturing appearance.** Under the decisions the running Session is the one live state, the Project is a full snapshot taken only by Update Project / Save as Project, and opening restores it. The "Background sheets (every level)" part of Expected behavior still stands, except that runtime sheets name Tab, Pane, Session or Settings (a Project's values are restored into those levels, so "Project" appears only in the Project Editor).

### Decisions taken (user delegated)

1. **Runtime sheets name Tab / Pane / Session / Settings; the Editor's sheets name Tab / Pane / Project / Settings.** Restored values live in runtime levels, so a runtime "Project" source would be a seed in disguise.
2. **Pane sheet mode.** The Pane is *customized* when it has its own value **or any Tab in it has one**. Customized shows Custom selected, the gear filled with accessibility value `custom`, controls enabled, and the values of the **active Tab's effective background**. Any edit writes the edited effective value to the Pane level, which replaces every Tab's own value (#0585 rule kept). Done with no edit writes nothing. A caption warns when Tabs in the Pane have their own values. Follow clears the Pane and its Tabs; Cancel restores both.
3. **Editor Pane level replaces Tabs the same way**, so the Editor and the runtime agree; Cancel restores.
4. **Startup command follows its Tab**, not its index. A reordered set changes the approval hash, so the next open re-prompts. That is the existing trust contract.
5. **Invalid stored layout extras are ignored at open, never fatal**: `splitFractions` whose shape doesn't match the topology means equal sizes; an out-of-range `focusedSlot` or `activeTab` means the first; hiding never hides the last visible Pane (`WindowRuntime.hidePane`'s rule). So the Editor's layout editing needs no new code for them, and a hand-edited file can't break an open.
6. **Theme**: Set Session Theme keeps writing both slots. Update captures `themeOverride` as is, unknown names included.
7. **Several Sessions of one Project** are independent snapshots of it, so no shared state.
8. **Project deleted while its Session is open**: unchanged. Update becomes Save as new (`SaveSessionAsProject.draft`).
9. **Shared Projects**: every new field is definition and syncs, except Pane `background.imagePath`, which is device state like a Tab's. Pane images use the Tab identity type and machinery (`ProjectTabImage`).
10. **Pending images replace seeds.** A level that opened without its Project image (missing, rejected, or not yet downloaded) records that as device state, and any user write to that level clears it. While pending, Update keeps the Project's stored image for that level and an arriving image is applied. This is the narrow job the seeds did, without comparing values.

No blocking questions.

### User checklist

1. **Motivating bug.** Open a Project whose Tab has an image (or set one from the Tab chip). In the Sidebar, the Pane's gear is filled. Click it: Custom is selected, the Tab's image and opacities show, and the caption says it's the Tab's. Drag image opacity: the image stays and the opacity changes. Cancel puts it back.
2. **Other sheets.** The Tab chip Background… and Set Session Background… sheets name their source. The Session sheet says when Panes or Tabs have their own background.
3. **Full snapshot.** In a Project Session:
   - change every level's background, the Theme, the split sizes, the active Tabs and the focused Pane;
   - hide a Pane, mute the Session, collapse or expand the Pane list;
   - rename a Tab, close and reorder Tabs.
   
   Then Update Project → Save, close the Session and reopen the Project. Everything is back, each startup command is on its own Tab, and a reordered command set asks for trust again.
4. **No live writes.** Change a background in the Session without Update; reopen in a new Session (Open Project with the Session closed): the old snapshot shows. Edit the Project in the Editor while its Session is open: the open Session doesn't change.
5. **Editor.** A terminal Pane's inspector has a Background row; editing it replaces that Pane's Tab values, and Cancel restores them. A Tab card says Follows Pane / Project / Settings correctly.
6. **Shared Project, two Macs.** A Pane image chosen on one Mac reaches the other on open, like a Tab image.

## Steps to reproduce (the motivating bug)

1. In the Project Editor, open a Project with one Terminal Pane. On a Tab card, set Background → Custom, pick an image, then Save & Open. (Or, in any Session, right-click a Tab chip → Background… → Custom → pick an image.)
2. The Tab shows the image. In the Sidebar, the Pane row's gear is the outline `gearshape`, with accessibility value `following`.
3. Click the gear. The sheet opens with **Follow Session** or **Follow App Default** selected. The controls are disabled and show the Session's or app-wide value, without the Tab's image and with a different opacity.
4. Click **Custom for This Pane**. The Tab's image disappears and the controls show no image. The user has to pick the image again.
5. The Project still stores the Tab's image. The running Session no longer shows it. Update Project would now write the Pane value onto every Tab.

## Expected behavior

**Single source of truth (Project Sessions)**

- When a Session opened from a Project renders a background or a Theme, it reads it from that Project's definition.
- These edits write to the Project (`ProjectStore`) and then re-render:
  - the Sidebar Pane gear
  - the Tab chip **Background…** / **Clear Background**
  - **Set Session Background…** / **Clear Session Background**
  - **Set Session Theme…** / **Clear Session Theme**
- Editing the Project in the Project Editor updates open Sessions of that Project live. A merge from another Mac does the same; see Open questions.
- No seed or diff reconciliation is left for appearance fields. Update Project no longer captures them: they're already in the Project.
- Layout edits in the Session (Splits, new or closed Tabs, Tab names, directories, commands) stay runtime changes until Update Project, as today.

**Background sheets (every level)**

- **The Pane gear's sheet shows what the terminal shows.** It opens on the active Tab's effective background (image, fit, position, image opacity, terminal opacity) and names where it comes from: this Tab, Pane, Session, Project or Settings.
- **Custom seeds from that effective value**, never from a value with no image. Changing only the opacity keeps the current image.
- **Saving writes the Pane level**: every Tab in the Pane, per #0585, and it carries the image the user saw.
- **Cancel** restores everything.
- **The other sheets work the same way**: the Tab chip **Background…** sheet, **Set Session Background…**, and the Project Editor's Project row and Tab card. Each shows the effective value and its source the same way, and seeds Custom from it. None says "not customized" or "Follow …" while another level is what's visible.
- **The gear's own state** (outline or filled, accessibility `following` or `custom`) must not say the Pane is uncustomized while a Tab in it has its own value.

## Notes

### What becomes redundant for Project Sessions

- `SessionRuntime.projectBackgroundSeed`, `SessionRuntime.projectThemeSeed` and `TabRuntime.projectBackgroundSeed`, and every "unchanged since open" comparison against them: Update Project, Tab image arrival, image removal and the quit in-use set.
- Update Project's appearance capture: `captureBackground`, `captureTabBackgrounds` and the Theme diff in `SaveSessionAsProject.draft(for:destination:...)`. Update Project then captures layout only. Save as **new** Project from a plain Session still needs the capture.
- The copy into runtime overrides at open (`addProjectSession`'s `setBackgroundOverride` / `themeOverride`, and `ProjectTreeBuilder`'s `backgroundOverride:` seed). The runtime renders from the Project instead.
- Pane replace rule: a Pane gear write in a Project Session becomes a write of that value to every Tab of the Pane **in the Project**, because the Project has no Pane level. That matches today's Save capture (`tab.own ?? pane.own`) and #0585's "most recent action wins". Cancel restores the Project's prior Tab values. Whether a Pane-level field is added to `ProjectPane` instead is an open question.
- The Sidebar "Follow Session" wording inside a Project Session: the Project's background is what the user means.

### Other inconsistencies on these paths

1. **Clicking the already-selected Follow card wipes Tab values.** #0585 made this deliberate (`PaneRuntime.swift:184-185`). With Follow shown as selected, a click that looks like a no-op erases every Tab's image.
2. **The Session sheet ignores narrower levels.** `SessionRuntime.inheritedBackground` returns `appWide` (`SessionRuntime.swift:259-261`), and Set Session Background… keeps Pane and Tab values. A Session edit can change nothing on screen, and the sheet doesn't say why.
3. **"Project" never appears as a runtime source.** The Project's background becomes the Session override (`WindowRuntime.swift:271-274`), so a Tab following it says "Follow Session" (`BackgroundOverrideSettingsView.swift:46-60`).
4. **"Follow Project" while the Project follows Settings.** The Tab card summary (`ProjectEditorViewModel.swift:311-316`) and the `.projectTab` scope (`BackgroundOverrideSettingsView.swift:62-69`) always say Project. `ProjectTabBackgroundTarget.inheritedBackground` falls back to `appWide` (`ProjectEditorViewModel.swift:1143-1145`).
5. **The Tab chip sheet already gets the level right.** `TabRuntime.inheritedBackground` (`TabRuntime.swift:583-585`) includes Pane and Session. It still needs the source shown the same way as the other sheets.
6. **Pane sheet with Tabs that differ.** It shows the **active** Tab (`PaneRuntime.activeTab`, around `PaneRuntime.swift:170`). It should say when other Tabs have their own values that Save will replace.

### Open questions for the planner

1. **Pane level in the Project.** Should the Project gain a `ProjectPane.background`, so the gear maps 1:1, or does a gear write fan out into each `ProjectTab.background`? Fan-out keeps #0585's model but loses "this Pane follows"; a new field changes the definition, the sync record and the merge.
2. **Shared Projects.** A live edit saves to the Project, stamps `modifiedAt` and publishes, so every slider drag would publish. Should the sheet write live to the runtime and save once on Done, or debounce? A merge from another Mac should re-render this Mac's open Sessions of that Project; `mergeRemote` has no such hook today. Last-writer-wins can overwrite an edit in progress in an open sheet.
3. **Several open Sessions of one Project** (`ProjectOpenMode.openNew`, `AppStateStore.swift:1472-1478`) share one appearance state. An edit in one changes the others live. Confirm that's intended.
4. **Mapping runtime Tabs to Project Tabs.** Layout edits are runtime-only until Update Project, so a Session can have Tabs the Project doesn't (Cmd-T, Duplicate, Split) or lack Tabs it has. #0585 maps by slot and index through `SessionProjectCapture.tabIDs`. Where does a Tab-chip edit on an unsaved Tab go: runtime-only until Update Project, or disallowed? And what happens to a Project Tab value whose runtime Tab was closed or moved?
5. **Device state stays per-Mac.** Image paths, pending identities and `projectBackgroundImageProblem` stay runtime and device state (#0501, #0585). Only the definition fields move.
6. **Theme.** `Project.theme` is a `ThemePair`; Set Session Theme… writes `.both(name)` (`ThemeSelectorView.swift:494`). In a Project Session, should it write the slot for the current appearance, or both slots, as today?
7. **Project deleted or made unreadable while its Session is open.** Today `SaveSessionAsProject.draft` falls back to a new Project. What does the Session render from then? Presumably it falls back to plain runtime overrides seeded from the last value.
8. **Concepts.md** §Session, §Pane and §Tab describe Session, Pane and Tab overrides as "in-memory only, apart from a Project seeding it". These need rewording for Project Sessions.

### Constraints

- `docs/swiftui-observation-rules.md` is binding. Effective values and sources must be computed for display, never written from `body` or `onChange`. Every write comes from a button, menu or control binding. A Project save that re-renders open Sessions must not run inside a view update.
- `BackgroundOverrideHolder` (`BackgroundOverrideSettingsView.swift:7-19`) is the seam. Each holder needs an "effective value and source", and for a Project Session a target that writes the Project.
- **UI tests:** `PaneBackgroundSettingsTests/testPaneGearReplacesATabsOwnBackground` and the #0585 Tab chip and editor tests guard the area.
- **Unit tests:** coverage lives in `TabBackgroundOverrideTests`, `PaneBackgroundOverrideTests`, `SessionBackgroundOverrideTests`, `ProjectBackgroundEditorTests`, `SaveSessionAsProjectTests` and `TabImageResolutionTests`. The seed-rule tests in `SaveSessionAsProjectTests` change meaning for Project Sessions.
