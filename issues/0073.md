# 0073 — Auto-set tab title to display name when a known TUI command runs

| | |
|---|---|
| **Status** | open |
| **Module** | Tabs / TerminalSurface |
| **Platform** | macOS |
| **First seen** | 2026-05-11 |

## Description

When the user runs a known TUI app in a tab (e.g. `claude`, `vim`, `aider`), Batty should set the tab title to the app's display name (e.g. `Claude Code`, `Vim`, `Aider`) so the chip row tells you which tab is running which agent at a glance. When the command exits, the title reverts to whatever the chip's normal resolution chain produces (cwd basename, user override, etc.).

The mapping lives in code as a hardcoded `[String: String]` (or `[String: TUIAppDescriptor]`) keyed by the command binary's basename.

## Expected behavior

- A new `TUIAppRegistry` (static / immutable) maps command name → display name.
- A new `TabRuntime` field (e.g. `runningCommandDisplayName: String?`) holds the active display name when a registered command is running. Nil when at a bare prompt or running an unregistered command.
- `TabTitleFormatter.chipTitle(for:fallback:)` consults the new field early in the resolution chain:

  1. `titleOverride` (user-set Rename) — still wins absolutely.
  2. **`runningCommandDisplayName`** (new) — beats live OSC titles, beats cwd basename.
  3. Live OSC title (stripped + prettified) — current step 2.
  4. cwd basename — current step 3.
  5. Fallback (Tab N / Tab).

- When the registered command exits, `runningCommandDisplayName` clears and the chip falls back to the cwd-basename or whatever the normal chain returns.

## Implementation guidance

### Detection signal

This is the hard part. Two options:

#### Option A: shell-integration OSC 133

Ghostty ships shell-integration scripts (we already inject them — see `io_exec: shell integration automatically injected shell=.zsh` in the logs). OSC 133 fires `D` markers around commands. The fork's `TerminalSurfaceCommandFinishedDelegate` already handles **command-finished**. A companion **command-started** signal would tell us when `claude` (or any command) begins running, and pass the argv[0]. Then we look up the command in `TUIAppRegistry` and set the display name.

The fork (`brennanMKE/libghostty-spm`) needs a new delegate protocol (`TerminalSurfaceCommandStartedDelegate`?) wired through the action callback bridge. Inspect `../libghostty-spm/Sources/GhosttyTerminal/InMemory/TerminalCallbackBridge.swift` — if libghostty has an OSC 133 `A` / `C` markup callback exposed, the addition is small (mirror of `command_finished`). If not, this needs upstream work in libghostty itself.

#### Option B: foreground process polling

Periodically (every ~500ms while a tab is visible) check the foreground process group via `tcgetpgrp(ptyFd)` and read its argv[0] via `ps -p <pid>` or the equivalent libc call. Compare to the registry. Set the display name when the foreground process matches; clear when it returns to the shell PID.

This doesn't require a fork change. It's also useful for `#0054` (Cmd-W with busy confirmation), since "is something running" is the same signal at a higher level. The two issues could share infrastructure.

Downsides: 500ms latency, polling overhead, requires exposing the PTY fd from libghostty (probably a fork addition anyway).

#### Recommendation

Option B as v1 if libghostty exposes the PTY fd or the foreground pid; Option A as v1 if a small libghostty addition for OSC 133 `A` markup is available. The user has already shown willingness to extend the fork (see `#0044` history). Investigate which is the smaller delta.

A v0.1 stub: implement the registry and the title-formatter step now, gated on a `TabRuntime.runningCommandDisplayName` that **nothing writes yet**. Tests can validate the registry and the formatter behavior end-to-end. The detection signal lands in a follow-up.

### Data model

New file `BattyKit/Sources/BattyKit/TUIAppRegistry.swift`:

```swift
public enum TUIAppRegistry {
    /// Command basename → display name. Lowercased keys; lookups lowercase
    /// the input. Aliases (`pdx` for `plandex`) point at the same display
    /// name as the canonical command.
    public static let displayNames: [String: String] = [
        "claude":       "Claude Code",
        "codex":        "Codex",
        "opencode":     "OpenCode",
        "gemini":       "Gemini CLI",
        "crush":        "Crush",
        "amp":          "Amp",
        "droid":        "Droid",
        "cursor-agent": "Cursor CLI",
        "aider":        "Aider",
        "goose":        "Goose",
        "plandex":      "Plandex",
        "pdx":          "Plandex",
        "cn":           "Continue CLI",
        "qwen":         "Qwen Code",
        "cline":        "Cline CLI",
        "roo":          "Roo Code CLI",
        "kilo":         "Kilo Code CLI",
        "sweagent":     "SWE-agent",
        "gptme":        "gptme",
        "pi":           "Pi",
        "forge":        "Forge",
        "copilot":      "GitHub Copilot CLI",
        "q":            "Amazon Q Developer",
    ]

    public static func displayName(for command: String) -> String? {
        let key = (command as NSString).lastPathComponent.lowercased()
        return displayNames[key]
    }
}
```

`displayName(for:)` is forgiving: if the caller passes a full path (`/usr/local/bin/claude`), it strips to basename.

### TabTitleFormatter

Update `BattyKit/Sources/BattyKit/TabTitleFormatter.swift`:

```swift
public static func chipTitle(for tab: TabRuntime, fallback: String = "Tab") -> String {
    if let override = tab.titleOverride, !override.isEmpty { return override }
    if let running = tab.runningCommandDisplayName, !running.isEmpty { return running }
    if let stripped = stripShellPromptPrefix(tab.terminal.title), !stripped.isEmpty {
        return prettifyPath(stripped)
    }
    if let cwd = tab.terminal.workingDirectory, !cwd.isEmpty {
        return prettifyPath(cwd)
    }
    return fallback
}
```

v1 ships the catalog as code. A v2 setting could let the user add their own command → display-name mappings via Settings. Out of scope.

## Acceptance criteria

- `TUIAppRegistry.displayName(for: "claude")` returns `"Claude Code"`.
- `TUIAppRegistry.displayName(for: "/opt/homebrew/bin/claude")` returns `"Claude Code"` (basename handling).
- `TUIAppRegistry.displayName(for: "/usr/bin/ls")` returns `nil`.
- `TabTitleFormatter.chipTitle` returns the display name when `runningCommandDisplayName` is set, preserving the existing precedence rules.
- When the detection signal eventually lands and the user runs `claude` in a tab, the chip flips to `Claude Code`. When `claude` exits, the chip reverts to its prior label.
- Aliases share display names: `pdx` and `plandex` both show `Plandex`.

## Out of scope

- The detection signal itself (option A or B) — file as a separate follow-up issue once we pick the path. v1 lands the registry + formatter + field with no writer.
- User-configurable additions to the registry (settings UI).
- Per-tab display-name preference overrides.
- Animations / transitions when the title flips.

#### libghostty investigation (why the writer is deferred)

I read the libghostty-spm sources and the underlying `ghostty.h` (in `BattyKit/.build/artifacts/libghostty-spm/libghostty/GhosttyKit.xcframework/macos-arm64_x86_64/Headers/ghostty.h`) to scope the writer. Findings:

- **No command-started action callback exists.** The C API exposes `GHOSTTY_ACTION_COMMAND_FINISHED` (with `exit_code` + `duration`) but no companion "command started" action and no argv payload on either side. `GHOSTTY_ACTION_PROMPT_TITLE` is a different signal (a hint telling the apprt to prompt the user for a title); it is not OSC 133 `A`/`C`.
- **OSC 133 `A`/`C` markers are not surfaced through the bridge.** `TerminalCallbackBridge.handleAction` covers `set_title`, `cell_size`, `ring_bell`, `render`, `config_change`, `progress_report`, `command_finished`, `desktop_notification`, `open_url`, `mouse_over_link`, `pwd` — nothing for prompt-start or command-start. Even if libghostty internally consumes the OSC 133 prompt markers (it must, to drive `command_finished`), it does not re-emit them to the apprt with the typed command line.
- **PTY fd / foreground pid are not exposed.** `ghostty_surface_*` functions in `ghostty.h` cover input, sizing, focus, occlusion, clipboard, splits, IME, keybindings, and read-selection — but there is no accessor returning the PTY file descriptor or the child pid. Without one, Option B (foreground-pid polling via `tcgetpgrp`) can't be implemented without fork work either.

Both detection paths therefore require additions to `brennanMKE/libghostty-spm` (and possibly upstream libghostty), which the dispatch brief said to bail out of mid-stride. Deferred to a follow-up that decides between:

- **Option A (preferred if cheap upstream):** add a `GHOSTTY_ACTION_COMMAND_STARTED` action that fires on OSC 133 `C` with the typed command line, surface it as `TerminalSurfaceCommandStartedDelegate` in libghostty-spm, conform `TerminalViewState` to it, and wire `TabRuntime.runningCommandDisplayName` from the new state.
- **Option B (fallback):** add `ghostty_surface_pty_fd(ghostty_surface_t)` or `ghostty_surface_command_pid(ghostty_surface_t)` so Batty can poll the foreground pid at ~1Hz while the tab is visible. Coordinated with `#0054` (Cmd-W busy confirmation).

#### What ships now is still useful

- The registry is callable: `TUIAppRegistry.displayName(for: "claude")` returns `"Claude Code"`. When the writer lands it has nothing to learn about the catalog.
- The formatter precedence is locked and tested. Any future writer just sets/clears the field and the chip rerenders.
- A v0.1 manual smoke path: a developer can drop `tab.runningCommandDisplayName = "Claude Code"` in a debugger to confirm the chip flips. The visible behavior wired end-to-end will land with the detection signal.

### 2026-05-12 — Second-pass investigation; writer is blocked upstream of libghostty-spm

A fresh subagent re-examined the C ABI to determine whether Option A or Option B could be implemented entirely inside `brennanMKE/libghostty-spm` (the Swift wrapper). It cannot. The blocker is one level deeper than the previous bail note implied: not the SPM wrapper, but the underlying libghostty binary.

#### What `libghostty-spm` actually contains

`Package.swift` declares `libghostty` as a remote `.binaryTarget` pointing at a prebuilt `GhosttyKit.xcframework.zip` published on the upstream Lakr233 releases page. The Swift wrapper layer (`GhosttyTerminal`, `GhosttyKit` glue) calls into that binary through the C ABI exposed in `Headers/ghostty.h`. Neither the Zig sources for libghostty nor a build pipeline that compiles them lives in this fork — only the shim around the prebuilt framework.

That means changes to the C ABI (new action enum values, new struct fields, new `ghostty_surface_*` functions) cannot be made by editing only `libghostty-spm`. They require rebuilding libghostty from upstream Zig source and republishing the xcframework.

#### Both detection paths require ABI changes

I reread the full `ghostty_action_tag_e` enum (lines 875-940 of `ghostty.h`) and every `ghostty_surface_*` C function (lines 1088-1160):

- **Option A (OSC 133 command-start signal)** would require a new `GHOSTTY_ACTION_COMMAND_STARTED` enum value plus a `ghostty_action_command_started_s` struct carrying the typed command line. Neither exists today; the closest neighbor `GHOSTTY_ACTION_COMMAND_FINISHED` only carries `exit_code: int16_t` and `duration: uint64_t`. `GHOSTTY_ACTION_PROMPT_TITLE` is unrelated — it's a hint to the apprt to *prompt the user* for a title. No callback fires on OSC 133 A or OSC 133 C with the command line.

- **Option B (foreground-pid polling)** would require a new `ghostty_surface_pty_fd` or `ghostty_surface_command_pid` accessor on `ghostty_surface_t`. None of the existing surface functions return the PTY fd, the child pid, or the foreground pgid. `ghostty_surface_process_exited` returns `bool` only.

There is one interesting wrinkle: the C config has two backends, `GHOSTTY_SURFACE_IO_BACKEND_EXEC` and `GHOSTTY_SURFACE_IO_BACKEND_HOST_MANAGED`. The host-managed mode hands the PTY off to the SPM caller via `receive_buffer` / `receive_resize` callbacks — but it requires the *host* (the SPM consumer, in our case Batty) to spawn the child process and own the PTY end-to-end. Batty currently uses `EXEC` mode (libghostty spawns the shell), and switching to host-managed for the sole purpose of getting at the PTY fd would mean rewriting how Batty creates surfaces, manages process lifecycle, and handles shell exits — far larger than the issue's scope and well into "rewrite the integration" territory.

#### Bail

This issue's writer is blocked on upstream libghostty. The plan-of-record options are:

1. Open a PR / issue against `ghostty-org/ghostty` proposing a `command_started` action with the typed command line on the C ABI (mirror of `command_finished`). Wait for it to land in upstream, ship in the next published xcframework, then resume here.
2. Same shape but for `ghostty_surface_pty_fd` / `ghostty_surface_command_pid`. Less aligned with libghostty's existing design ("apprt sees events, not raw PTY state") but simpler to implement upstream.
3. Switch Batty to `GHOSTTY_SURFACE_IO_BACKEND_HOST_MANAGED` and run the child process ourselves. Out of scope for this issue; a much larger architectural change that #0073 alone doesn't justify.

Status stays `open`. Step 1 (registry + field + formatter) is shipped and useful; the writer needs an upstream libghostty change before it can be wired.
