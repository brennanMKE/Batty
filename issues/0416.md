## Description

`SessionCwdRenameTests.setUpWithError()` (`BattyUITests/SessionCwdRenameTests.swift:26-40`) creates two fixture directories at hard-coded paths, `/tmp/batty-uitest-proj-<id>` and `/tmp/batty-uitest-plain-<id>`, and writes a `package.json` into the first. In #0412's first full Tart-VM run (run id `20260923-191103-94702`), the first `createDirectory` threw and the test failed before it launched Batty:

```
SessionCwdRenameTests.swift:0: error: -[BattyUITests.SessionCwdRenameTests testSessionNameTracksCdIntoAndOutOfProjectDir] :
failed: caught error: "Error Domain=NSCocoaErrorDomain Code=513 "You don't have permission to save the file
"batty-uitest-proj-051B746…" in the folder "tmp"." … NSPOSIXErrorDomain Code=1 "Operation not permitted"
```

No prompt appeared. The guest denied the write outright. This is a test-fixture problem, not a Batty defect. The session-rename behavior the test covers (#0227) was never exercised.

### Likely mechanism (confirmed)

In the guest, the UI-test runner is signed with the App Sandbox entitlement. The guest's `xcodebuild.log` packages `BattyUITests.xctest.xcent` with `"com.apple.security.app-sandbox" = 1` and signs `BattyUITests-Runner.app` / `BattyUITests.xctest` with `--entitlements …/BattyUITests.xctest.xcent`. Confirmed directly in three VM runs' pulled `xcodebuild.log` (`build/ui-tests/20260923-234117-89835/xcodebuild.log:8674-8704` and identical blocks in the other two): the full entitlements dump shows `"com.apple.security.app-sandbox" = 1` plus `"com.apple.security.temporary-exception.files.absolute-path.read-only" = ( "/" )` — the runner can *read* anywhere under `/` but has no matching write exception, so it can't create entries directly in `/tmp` (or anywhere else outside its own container) even though it can read them.

On the host the test passed because the old runner, `scripts/run-ui-tests.sh:111`, re-signed the runner with `codesign --force --deep --sign - "$RUNNER"` and no `--entitlements`. That re-sign drops the sandbox entitlement. The VM runner (`tools/run-ui-tests-vm.sh` on `issue/0412`) doesn't re-sign, because #0412 open question 5 found the Gatekeeper re-sign unnecessary in the guest. So in the guest the runner keeps its sandbox.

## Expected behavior

The test creates its fixtures somewhere both the runner and the unsandboxed app can reach, and it passes in the VM. `NSTemporaryDirectory()` / `FileManager.default.temporaryDirectory` is the obvious candidate. The rest of the suite already uses it this way: `BattyUITestHarness.sentinelPath(named:)` puts sentinel files there for the app's shell to write and the runner to poll, and `launchBatty()` passes it to the app as `BATTY_UI_TEST_TEMP_HOME` (`BattyUITests/Support/BattyUITestHarness.swift:21`, `:38`, `:115-119`).

## Scope (round 2, current)

**#0416 resolves as the fixture-permission fix only.** That fix — fixture directories moved from a hard-coded `/tmp` path to `NSTemporaryDirectory()` — is confirmed working across three separate VM runs (`20260923-234117-89835`, `20260924-000109-6894`, `20260924-000635-11018`): `setUpWithError()` no longer throws `NSCocoaErrorDomain Code=513`, and the shell the app spawns is independently confirmed to reach the fixture directory (see the `## Root-cause investigation` section's hostname-sentinel diagnostic).

The `testSessionNameTracksCdIntoAndOutOfProjectDir` rename assertion that still fails after that fix is a **separate** problem — the auto-rename pipeline itself not completing in this guest, for a cause round 2's investigation narrowed but did not pin down. That failure is tracked as its own issue, **#0436**, and is out of scope here. The `## VM verification` and `## Root-cause investigation` sections below predate this scope decision and read as though the whole test needs to pass before this issue resolves ("should not move to `resolved`", "candidate for a new issue", Expected behavior's "and it passes in the VM") — that guidance is superseded by this note and by `## Relation`, kept for the historical record of how the investigation actually went, not as current instruction.

## Notes

- The current code chose `/tmp` on purpose. Its comment (`SessionCwdRenameTests.swift:30-31`) says: "Live under /tmp (not NSTemporaryDirectory) so the unsandboxed app process resolves the same absolute paths the terminal cd's into." Whoever changes it must check that concern still holds for the new location:
  - A sandboxed runner's temporary directory sits under its container, and on the host it's under `/var/folders/…`. Either way it's a symlinked `/var` → `/private/var` path.
  - The shell's OSC 7 pwd will likely report the resolved `/private/…` form.
  - The test asserts on the Session title. That comes from `ProjectNameResolver` reading `package.json` at the cwd, so a path-string mismatch shouldn't matter. Verify it in the guest anyway.
- Run the fix in the VM only (`./build.sh ui BattyUITests/SessionCwdRenameTests`), never on the host (`AGENTS.md`, "UI test automation").
- #0412's doc gives this as its example of the guest being "not identical" to the host in filesystem permissions (`docs/ui-testing-vm.md`, "Findings for follow-up", on `issue/0412`). Any other UI test that writes outside the runner's own temp directory would hit the same denial. A grep of `BattyUITests/` for `"/tmp` found only this file and the doc comment on `sweepSentinels()`, which actually uses `NSTemporaryDirectory()`.

## Root-cause investigation — 2026-09-24 (round 2)

Two more VM runs, each with a code-only diagnostic added to `SessionCwdRenameTests.swift` (no product code touched), to find why the rename never happens once the fixture is reachable.

**Path spelling / project marker — ruled out by code reading, no VM run needed.** `ProjectNameResolver.resolve(at:)` (`BattyKit/Sources/BattyKit/ProjectName/ProjectNameResolver.swift`) and the bundled `node` rule (`BattyKit/Sources/BattyKit/Resources/project-name-rules.json`) key entirely on directory *contents* (`FileManager.contentsOfDirectory`, then a JSON `name` field read from `package.json`) — nothing compares path strings, so the `/var` → `/private/var` symlink form the shell reports doesn't matter, exactly as this issue's own `## Notes` predicted.

**Rename trigger, hypothesis 1 — OSC 7 hostname validation — ruled out as the specific mechanism.** Batty pins upstream `github.com/Lakr233/libghostty-spm` at `a2565ccf` (`BattyKit/Package.resolved`), not a fork. Reading a local checkout of that same repository, `brennanMKE/libghostty-spm` at `d617253` (`References/ghostty-upstream/src/termio/stream_handler.zig`, `reportPwd`) showed libghostty validates the OSC 7 URI's host against a live `gethostname()` call (`internal_os.hostname.isLocal`, `src/os/hostname.zig`) and **drops the pwd update entirely** on a mismatch — no error, no delegate call. The zsh shell-integration script embeds `$HOST` (`Sources/GhosttyTerminal/Resources/Ghostty/shell-integration/zsh/ghostty-integration`, identical text in both the `brennanMKE` checkout and the pinned revision's own `SourcePackages/checkouts` copy — diffed byte for byte), which zsh caches once at shell startup; a fresh VM clone settling its hostname (DHCP/Bonjour) after the shell already started would make `$HOST` stale forever for that shell, silently breaking every OSC 7 report. Plausible enough to test directly: added a diagnostic (`BattyUITests/SessionCwdRenameTests.swift`) that types `cd <projectDir> && printf 'HOST=%s LIVEHOST=%s\n' "$HOST" "$(hostname)" > <sentinel>` instead of a bare `cd`, and waits on the sentinel before checking the rename.

- **Host checks before VM run `20260924-000109-6894`:** `tart list` — only stopped golden images; host Batty ASN `0x0-0x58058-"Batty"`. `./build.sh` and `./build.sh unit` both green (1715 tests) before running.
- **Result:** sentinel appeared (shell reached the directory), reporting `HOST=Manageds-Virtual-Machine.local LIVEHOST=Manageds-Virtual-Machine.local` — an **exact match**. This proves two things and no more: the shell reached the fixture directory (independent re-confirmation of this issue's actual fix), and *if* an OSC 7 report was sent, its embedded `$HOST` would not have been rejected by libghostty's locality check. It does **not** prove the ghostty zsh integration actually loaded in this guest shell (the `.zshenv`/`ZDOTDIR` injection `ghostty-integration` depends on), or that any OSC 7 sequence was emitted at all — "OSC 7 never emitted because the integration didn't load in the guest shell" remains an open candidate, not ruled out by this result.
- **Host checks after:** `tart list` clean, ASN unchanged.

**Rename trigger, hypothesis 2 — model vs. rendering — narrowed by a second diagnostic.** Since the shell-level signal was clean, the remaining gap is somewhere between libghostty's pwd delegate and the sidebar row XCUITest polls. Added a second diagnostic: on failure only, read `app.windows.firstMatch.title` — bound to `session.title` via `SessionDetailView.navigationTitle`, a SwiftUI binding entirely independent of the sidebar row's accessibility identifier — to tell apart "the model's `session.title` never changed" from "it changed but the sidebar didn't re-render."

- **Host checks before VM run `20260924-000635-11018`:** `tart list` — only stopped golden images; host Batty ASN `0x0-0x58058-"Batty"`. `./build.sh` and `./build.sh unit` both green (1715 tests) before running.
- **Result:** failure message: `shell reported: HOST=Manageds-Virtual-Machine.local LIVEHOST=Manageds-Virtual-Machine.local; window title: 'Session 1'`. **The window title never changed either** — confirming the failure is a model-level miss, not a sidebar-rendering-only one. `crashes/` empty, no new driver-error sentinel, `app-warnings.log` (41 lines) shows only the already-known broker-unreachable loop (#0419) and the SwiftUI geometry-cycling Fault (#0420).
- **Host checks after:** `tart list` clean, ASN unchanged (`0x0-0x58058-"Batty"`) across both rounds — Batty never restarted.

**Conclusion: root cause not found; stopping per instruction rather than guessing further in code this session doesn't own.** What's confirmed: the shell reaches the fixture directory (this issue's actual fix, re-confirmed twice), and its reported `$HOST` matches a live `hostname` call byte-for-byte. What's *not* confirmed: whether the ghostty shell integration ever loaded in this guest shell, or whether any OSC 7 report was sent at all. So the candidates for why `session.title` never updates are, in order of how directly this round's evidence bears on them:

1. **OSC 7 never emitted** — the zsh integration (`.zshenv`/`ZDOTDIR` injection) didn't load in the guest shell, so no pwd report was ever sent. Nothing this round distinguishes this from candidate 2; the host-matching sentinel says nothing about whether a report was sent, only what its host *would* have been.
2. **OSC 7 sent and (conditional on 1 not being true) passed libghostty's locality check**, but something between the delegate callback and `session.title` swallowed it: libghostty's C/Zig `reportPwd` → the `GHOSTTY_ACTION_PWD` callback bridge (`TerminalCallbackBridge.swift`, in the upstream `libghostty-spm` package pinned at `a2565ccf` — not a fork) → `TerminalDelegateProxy.terminalDidChangeWorkingDirectory` → `AppStateStore.handleWorkingDirectoryChange(forTabID:)`. That function's actual early-return guards are `!session.titleOverride`, `session.tree.allPanes.count == 1`, a nil/empty `cwd` (read from `anchorTab.terminal.workingDirectory ?? anchorTab.terminal.configuration.workingDirectory`), and `resolved != session.title` (`AppStateStore.swift:1699-1744`) — a cache hit and `nameFromFiles` are not early returns in this function; they're branches inside the `resolveAutoTitle` helper it calls.

None of these was directly instrumented this round, and none is reachable from a UI test without either a new production-code seam or guest console access to libghostty's own debug log — neither of which this round added. This could be a genuine, environment-specific defect in how the upstream `libghostty-spm` package behaves headless/in a VM (no real display, `DisplayManager` warnings appear in every run's `app-warnings.log`), or a latent bug in `AppStateStore`'s gating logic that a real Mac happens never to trip. Both remain speculation past this round's evidence. Per the coordinator's explicit instruction, stopping here rather than fixing code without the VM budget left to verify a fix — the rename failure is tracked as its own issue, **#0436** (see `## Scope` above and `## Relation` below), which should start by distinguishing candidate 1 from candidate 2 (a guest-side trace/log check for whether `ghostty-integration` actually sourced, or a temporary production-code trace on the delegate callback, are the two paths worth trying first).

Kept two of the diagnostics as permanent test aids (both cheap, both informative): the `cd`-succeeded-plus-`$HOST`/`hostname` sentinel, and the on-failure window-title read. Removed a third (an on-failure enumeration of sidebar-cell `.identifier`s) — it returned only `[""]` (the identifier isn't set on the direct cell element XCUITest enumerated) and added no signal; fixing it properly needs its own verification pass this round didn't have budget for.

## Fix

- **Fixtures.** `projectDir` and `plainDir` are now built under `NSTemporaryDirectory()`, and `tearDownWithError` removes them. The UI-test runner is sandboxed: its `.xcent` has `app-sandbox = 1` plus a read-only exception for `/`, so reads work everywhere but writes to `/tmp` are denied (NSCocoaErrorDomain 513).
- **Two diagnostics, kept permanently.**
  - The typed command is now `cd <dir> && printf 'HOST=… LIVEHOST=…' > <sentinel>`. The sentinel is a sibling of the project dir, so `ProjectNameResolver` never sees it. The test waits for the sentinel file as an event.
  - On failure, the test reads the window title. This separates a model-level miss from a rendering-only miss.
