## Description

Child of #0646; depends on #0648. Two pieces: `batty serve <dir>`, a built-in static file server that reloads on file change and shows in a Server Pane, and a **web preview Pane** kind (WKWebView) so a served page or a dev site can be viewed inside Batty, not only in an external browser.

The use case is previewing locally the web pages made for Claude Artifacts and similar static sites, without reaching for `python3 -m http.server` and a separate browser window.

Feature request from the user (Brennan), 2026-11-17.

### Current state (checked against `main` at `3b5735c3`)

- No Pane kind renders web content. `PaneContentKind` has `terminal`, `git-status`, `process-status`, `lm-studio-dashboard`, `system-metrics`. Nothing under `BattyKit/Sources` or `Batty/` imports WebKit.
- Viewer Panes are in scope: the user asked for a Markdown Viewer Pane on 2026-10-19 (#0527, open) and a Scratch Pad (#0571, open).
- `docs/batty-cli-design.md`'s "Deliberately skip" list names "in-app browser automation". A preview Pane is a viewer the user looks at; it offers no CLI verbs to click, type into or script the page, so it does not cross that line.

## Root cause

Feature work. Starting state: #0648's Server Pane existed with an `inApp` backend kind reserved but no in-process server, nothing in Batty imported `Network` or `WebKit`, and there was no Pane kind that could show a web page. `ServerPaneContent` assumed every listener was another process (scan, probe, metrics, signals), which would have found Batty's own pid for an in-app server.

## Fix

Followed the plan's five steps, one commit each.

- **Step 1** `PaneContentKind.webPreview` (`web-preview`), excluded from `paneSplitKinds`/`projectSlotKinds`, refused by `pane split`, captured as an empty terminal slot with a note. `WebPreviewURLPolicy`. Design docs (`docs/design/web-preview-pane.md`/`.html`, `server-pane-view.md` §6), Concepts, PRD, feature-flags, docs index.
- **Step 2** `Runtime/StaticServer/`: `HTTPRequestHead`, `StaticFilePathResolver` (percent-decode once, `..`/NUL 403, dot segments 404, `realpath` prefix check, regular files only, `/__batty/` reserved), MIME table, `ByteRange`, `ReloadScriptInjector`, directory listing, pure `StaticHTTPResponder` (method, Host check, Range, injection rule, HEAD, no-store/nosniff), `StaticFileServer` on `NWListener` with `requiredLocalEndpoint = 127.0.0.1` and `acceptLocalOnly`, `FSEventsDirectoryWatcher` on its own queue, `StaticReloadBroadcaster` and a 150 ms `StaticReloadDebouncer` on the injected clock. `NWListener` binds loopback-only as hoped, so the BSD-socket fallback was not needed.
- **Step 3** `InProcessServerBackend` protocol and `InAppStaticServerBackend`; `ServerPaneContent` skips scan/probe/metrics/stats/signals for it, stops it synchronously in `tearDown`, Stop/Restart stop and rebind the same port (`lastError` on a busy port); "Serving" chip and in-app facts grid; `ServerServeRequest`, `XPCVerb.serverServe`, `AppStateStore.serveStaticForXPC` (bind first, then re-resolve the calling Pane), `ServedSiteOpenTarget` setting and picker, `batty server serve`.
- **Step 4** `WebPreviewEngine`/`WKWebViewPreviewEngine` (non-persistent store, `BattyPreview/1`, inspectable, policy-driven navigation and UI delegates, KVO state), `WebPreviewPaneContent` (engine made on first show, unmount and media suspend while hidden, reload on show only after a change, synchronous teardown, broadcaster subscription by port), `WebPreviewPaneView` (toolbar, error state, `NSViewRepresentable` host that only reassigns `onMouseDown`), `WebPreviewRequest`/`Reply`, `XPCVerb.serverPreview`, `openWebPreviewForXPC`, Open in Batty on every Server Pane backend, `serve --open`, `batty server preview`.
- **Step 5** `BattyUITests/CLIWebPreviewTests` (seven tests) and the CLI, agent-workflow, install, skill, agent-snippet and pane-kinds docs.

Deviations from the plan:

- `WebPreviewURLPolicy` lives in `BattyXPCCore`, not `BattyKit/Runtime`, so the `batty` CLI target (which links only `BattyCLICore`/`BattyXPCCore`) can validate `--url` client-side with the same rules.
- `StaticResolution.listing` carries the relative path as well as the directory (the listing title needs it).
- The debouncer takes the broadcaster and the broadcaster's `onBroadcast` hook calls `server.broadcastReload()`, instead of the debouncer holding the server.
- `batty server start` on a port held by an in-app server fails with `already serving <root> on port P; stop it first` (not in the plan; without it `start` would have replaced the in-app backend).
- `serverReply` reports an in-app server's state from `isServing` (`listening`/`stopped`), so `serve --json` says `listening` before the first 1 s tick.
- `serve --open` on a reused Server Pane also opens or reuses the preview.

Loopback targets still load in the preview.
- Doc comments of `ServerTerminalSink` and `makeTerminalBackend` moved back to their declarations.
- `StaticFileServerTests` stop every server in a `defer`. `MCPToolCatalogTests.serverVerbsBecomeToolsOnlyWithServerPaneOn` lists `server_serve` and `server_preview`.
- Tests: `InAppStaticServerRealSocketTests` (`stopThenResumeRebindsTheSameFixedPortAndServes`, `serverPaneRestartOfARunningServerServesAgain`: real `StaticFileServer` on a fixed free port, restart, `GET /` returns 200), which both fail with `port N is in use` when the await is removed; `resumeServingBindsOnlyAfterTheStoppedListenerIsReleased` (fake held on a gate) and the fake's call log (`start, stop, wait, start`); four `newWindow…` policy tests in `WebPreviewURLPolicyTests`.

The Pane would show Batty's CPU and memory, and `performStop` would ask the backend for a `ServerStopDecision` and signal processes. The `pane split` schema is a static `capabilitiesInputSchema` with no `FeatureFlags` parameter, and `--url` would be an always-present `@Option`. The preview view mounts its `WKWebView` only while its content is active, so an inactive web view is never in the window to take clicks.

Clicking into a `WKWebView` doesn't reach `nonTerminalShell`'s `.onTapGesture` (AppKit takes the click), so the preview needs its own click-to-focus (Step 4).

### Decisions (the issue's open questions, decided per the user's "complete every #0646 child" instruction)

1. **Grammar: `batty server serve [<dir>]` and `batty server preview`, under #0648's `server` noun.** There is no new top-level verb. The `server` noun is already flag-gated as a whole (`BattyCLI.subcommands(for:)`), and `stop`/`restart` already resolve a Server Pane by `--port`. `<dir>` defaults to the current directory and is made absolute client-side, as `--path` is.
   - `serve` options: `--port N`, `--open`, `--no-inject`, `--split right|down`, `--pane`, `--json`.
   - `preview` takes `--url U` or `--port N` (exactly one), plus `--split`, `--pane` and `--json`.
2. **Server implementation: Network.framework, in-process, no new dependency.**
   - `NWListener` with `NWParameters.tcp`, `requiredLocalEndpoint = .hostPort(host: .ipv4(.loopback), port: N or .any)` and `acceptLocalOnly = true`, on a private serial queue.
   - A small HTTP/1.1 handler for `GET` and `HEAD`, one request per connection, `Connection: close`.
   - Fallback, only if a test shows `NWListener` won't bind loopback-only: a BSD `socket`/`bind(INADDR_LOOPBACK)` listener with a `DispatchSourceRead` accept loop handing each fd to the same handler. Record that in `## Fix`.
   - `Package.swift` is unchanged (WebKit and Network are system frameworks).
3. **Binding: `127.0.0.1` only, not configurable.** Without `--port`, the kernel picks a free port (port 0), so a scan for a free port can never race. With `--port N`, that exact port is used, and a busy port is an error (`port N is in use`), never a silent fallback. The URL shown and opened is `http://127.0.0.1:<port>/`, not `localhost`, so browsers don't try `::1` first.
4. **Security.**
   - Path resolution: percent-decode once. Refuse `NUL` and any `..` segment (403). Drop `.` and empty segments. Refuse any segment starting with `.` (404, so `.git/` and `.env` are never served and never confirmed to exist).
   - Symlinks: `realpath(3)` the candidate and require it to be the root's `realpath` or under it plus `/` (403 otherwise). Not `URL.resolvingSymlinksInPath()`, which maps `/private/var` to `/var` and would break the prefix check under temp directories.
   - Only regular files are served.
   - The reserved prefix `/__batty/` never maps to a file.
   - **Host-header check against DNS rebinding:** `Host` must be `127.0.0.1:<port>`, `localhost:<port>` or `[::1]:<port>`, else 403. Without it, a page on another site that rebinds its name to 127.0.0.1 could read the served folder.
   - Every response sends `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`, and no CORS headers.
   - Requests other than `GET`/`HEAD` get 405 with `Allow`. A head over 16 KiB gets 431. Malformed requests get 400.
5. **Directory index and listing.** A directory request without a trailing slash gets a 301 to the slash form. A directory with `index.html` serves it. A directory without one gets a minimal HTML listing: names only, dotfiles hidden, sorted, links percent-encoded, names HTML-escaped. Reason: the main use case is a folder of Artifact pages with no index, the listener is loopback-only, and the user chose the root.
6. **MIME types: a fixed table, not `UTType`, so results are the same on every macOS.** It covers html/htm, css, js/mjs, json, map, svg, png, jpg/jpeg, gif, webp, avif, ico, txt, md (as `text/plain`), xml, csv, pdf, wasm (`application/wasm`, needed for streaming compile), woff/woff2/ttf/otf, mp4/webm/mp3/wav. Text types get `; charset=utf-8`; anything else is `application/octet-stream`. A single `Range: bytes=` range is honoured (206, or 416 when unsatisfiable), so `<video>` and `<audio>` seek. Multi-range requests get the full 200.
7. **Reload on change.**
   - **Watching:** an FSEvents stream on the root (`FileEvents | NoDefer | WatchRoot`, 50 ms latency) delivers on the server's queue. Paths with a dot-component under the root are ignored. Relevant events hop to the main actor into a 150 ms trailing-edge debouncer on the injected `SchedulingClock`.
   - **Browsers:** the server injects a one-line `<script>` that opens an `EventSource` on `/__batty/reload` and calls `location.reload()` on a message. It goes before the last `</body>` (case-insensitive), or at the end when there is none, and only into `text/html` responses. The SSE endpoint keeps each connection open and writes `data: reload\n\n` to every client on a change.
   - **Batty preview Panes:** reload in-process, with no injection. The preview's `WKWebViewConfiguration.applicationNameForUserAgent` is `BattyPreview/1`, and the server never injects for a `User-Agent` containing `BattyPreview/`. The preview subscribes to the server's main-actor change broadcaster, found by port through the store. A preview therefore always shows the bytes as they will ship, and never reloads twice.
   - `--no-inject` serves every file byte-for-byte. Browsers then reload by hand; Batty previews still reload.
   - The watcher lives as long as the server is serving, not as long as the Pane is visible. A hidden Server Pane keeps serving, and browsers still reload. FSEvents is event-driven, not periodic, so this is not the "periodic work while suspended" `docs/pane-view-lifecycle.md` §4 forbids. Record that in the design doc.
8. **Lifetime, reuse and restart.**
   - One in-app server per (Session, root `realpath`). Re-running `serve` on the same root reuses its Server Pane: it is shown if hidden, the server is resumed on the same port if stopped, and the preview is opened or reused with `--open`.
   - `serve` on the same root with a different explicit `--port` fails with `already serving <root> on port P; stop it first`.
   - `stopsOnTearDown = true`: closing the Server Pane cancels the listener, every connection and the watcher, synchronously in `tearDown()`. Quitting Batty frees the socket with the process.
   - Stop keeps the Pane, showing "Stopped". **Restart is offered after all** (the issue said it isn't needed): it rebinds the same port. That costs one method on the backend, and it saves `batty server restart --port N` from a special "cannot restart" error for this backend. A busy port on restart leaves the Pane Stopped and returns `port N is in use`.
9. **Web preview Pane kind: `web-preview` (`PaneContentKind.webPreview`, display name "Web Preview"), a separate Pane from the Server Pane** (issue Q7). Reasons: it can show any dev server, including terminal-backed #0648 servers, and the Server Pane's facts stay visible next to the page.
   - It is created by `batty server preview`, by `serve --open`, and by the Server Pane's new **Open in Batty** button, which every backend gets while the state is listening and the URL is allowed.
   - It is excluded from `paneSplitKinds` and `projectSlotKinds`, for the flag reason in the premises and because it needs a URL. Save as Project captures it as an empty terminal slot with a note, like `.server`. There is no menu or Command Palette entry.
   - Placement: from the CLI, next to the calling Pane per `--split`, else the Server Pane placement setting. From the button or `--open`, below that Server Pane (`.vertical`). The calling Pane keeps focus either way.
   - One preview per (Session, URL origin). Re-running for the same origin navigates the existing Pane to the new URL and shows it if hidden.
10. **Preview scope (issue Q5, Q6).**
    - **Top-level navigation:** only `http`/`https` to `localhost`, `127.0.0.1` or `[::1]` (exact hosts; `127.0.0.1.evil.com` and `localhost.evil.com` are refused), plus `about:blank`.
    - **User-clicked links elsewhere:** a top-level link the user clicks to any other `http(s)` host opens in the default browser. A script-driven top-level navigation elsewhere is cancelled and logged. `file:` is refused everywhere.
    - **Subresources and subframes:** allowed from any `http(s)`/`data:`/`blob:` source, so Artifact pages that load their scripts from CDNs work.
    - **Other behaviour:** `target=_blank` and `window.open` follow the same rules (a loopback URL loads in the same view). A response the view can't show (a download) is cancelled.
    - **Data:** a non-persistent `WKWebsiteDataStore` per Pane, so nothing reaches disk and nothing is shared across Panes.
    - `isInspectable = true`, so Web Inspector is available from the context menu. That is a developer viewer, not automation.
    - The preview has no CLI verbs to click, type into or script the page, so it stays outside `docs/batty-cli-design.md`'s "Deliberately skip: in-app browser automation".
11. **Feature flag: reuse `serverPane`, with no new flag.** Both pieces ship in 1.5.0 under the #0646 umbrella. Everything new is reached only through the already-gated `server` noun or a Server Pane. With the flag off, both new XPC verbs reply `server panes are not available in this build`.
12. **Settings and `--open`.** Settings › General › Server Panes gets a second picker, "Open served sites in: Batty / Default Browser" (`co.sstools.Batty.servedSiteOpenTarget`, default Batty, shown only with the flag on). `serve --open` follows it. The default is Batty because an agent's `--open` should not pull the user out to another app. The Server Pane's own buttons are explicit (Open in Browser, Open in Batty) and ignore the setting.
13. **Server Pane display for the in-app backend.** The chip reads "Serving" (green) or "Stopped". The facts grid shows Root (path, middle-truncated, selectable), Requests (count, read from a lock-guarded counter on the 1 s tick while visible), Live reload ("N browsers" or "Off" with `--no-inject`) and Last change (relative time). There is no PID, CPU, memory, stats or HTTP probe.

## Expected behavior

### `batty serve <dir>`

```sh
batty serve ./site
```

- Starts an in-app static file server rooted at `<dir>` (resolved to an absolute path by the CLI, as `--path` is today) on a free port, bound to **127.0.0.1 only**, and shows it in a Server Pane (#0648) with the URL, state, request count if cheap, Open in Browser and Stop. Restart is not needed (there is no command to rerun); Stop shuts the listener.
- Serves `index.html` for a directory request and sensible MIME types. No directory listing beyond what is needed to find files (see Open questions). Never serves outside `<dir>`: path traversal (`..`, encoded variants, symlinks pointing outside) is refused.
- **Reload on file change:** when a file under `<dir>` changes, open preview Panes and connected browser tabs reload. Watching follows the existing FSEvents patterns (Git Status already debounces filesystem events), off the main actor.
- `--port N` picks a port; `--open` also opens the web preview Pane (or the browser, per Settings); placement follows #0648's Settings and `--split`. Re-running `batty serve` on the same directory reuses its server and Pane.
- The server lives as long as its Pane: closing the Server Pane stops it; quitting Batty stops it.

### Web preview Pane

- A new non-terminal Pane kind (name to be chosen, for example `web-preview`) hosting a `WKWebView` that shows one URL.
- Opened from the Server Pane (an "Open in Batty" button next to Open in Browser) and from the CLI (for example `batty pane split --view web-preview --url http://127.0.0.1:8083/`).
- Minimal chrome: the URL, Back, Forward, Reload, Open in Browser. No tabs, bookmarks or history beyond Back/Forward.
- Reloads when the static server signals a change.
- Loads `http://localhost`/`127.0.0.1` URLs by default. Whether to allow any URL is an open question.

### Rules

- Must respect `docs/pane-kinds.md`, `docs/view-hierarchy.md`, `docs/terminal-pane-requirements.md` and `docs/swiftui-observation-rules.md`. The WKWebView is an AppKit view inside the Pane body, so the z-order and event-routing constraints in `docs/terminal-pane-requirements.md` apply directly: neighboring terminal Panes must keep pointer input, keyboard, file drop, text drop and IME, and focus must move in and out of the web view cleanly. Run that doc's manual checklist. Setup, teardown and show/hide follow `docs/pane-view-lifecycle.md`: a hidden preview Pane releases or suspends its web content.
- The visual design is drafted under `docs/design/` and approved by the user before implementation (#0301's design-first gate).
- `Concepts.md` gains the web preview Pane; `batty capabilities --json` lists the new verb and options; the `batty-cli` skill gets a recipe (#0647).
- Behind a feature flag (`FeatureFlags`, Beta on / Prod off) until the release that ships it.

## Acceptance criteria

- `batty serve ./site` serves the folder on 127.0.0.1 at a free port and shows a Server Pane; the URL loads `index.html`.
- A request for `/../` or a symlink out of the root returns 403/404, never the file. The listener is not reachable on the Mac's LAN address.
- Editing a file under the root reloads an open preview Pane.
- The web preview Pane shows the served page, its Back/Forward/Reload/Open in Browser work, and the `docs/terminal-pane-requirements.md` checklist passes with it next to terminal Panes.
- Closing the Server Pane or quitting Batty frees the port.
- Unit tests cover path resolution and traversal refusal, MIME mapping, the change-to-reload signal (awaited, no sleeps) and port selection. A UI test covers opening and closing a preview Pane, checked with `./build.sh ui-typecheck`.

## Open questions

1. **Grammar.** `batty serve` is a new top-level verb (`docs/batty-cli-design.md` §4). Keep it, or make it `batty server serve <dir>` under #0648's noun?
2. **Server implementation.** `Network.framework` (`NWListener`) with a small HTTP/1.1 handler, or a vendored package? Adding a dependency to `BattyKit/Package.swift` needs the user's approval.
3. **Reload mechanism.** Inject a small script into served HTML that listens on Server-Sent Events or a WebSocket, or reload only the in-Batty preview Pane (no injection, browsers reload by hand)? Injection changes the served bytes, which matters when previewing pages exactly as they will ship.
4. **Security.** Bind to `127.0.0.1` only (proposed, and not configurable?). Serve dotfiles (`.git/`, `.env`)? Proposed: refuse dotfiles by default. Directory listings: off, or on for directories without `index.html`?
5. **Web preview scope.** localhost-only, or any URL? Any URL makes it a general browser Pane, which the "simple, Mac-first" bar argues against. Non-persistent `WKWebsiteDataStore` per Pane, or shared?
6. **Claude Artifacts fidelity.** Artifact pages load scripts from a fixed set of CDNs. Previewing them needs network access from the preview Pane to those hosts even if navigation stays on localhost. Allow subresources from any host while restricting top-level navigation?
7. **Kind name** for the preview Pane, and whether the Server Pane and preview Pane can be one Pane with a toggle instead of two.

## Notes
