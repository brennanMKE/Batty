## Description

After `#0072` (wrapper preserves the `AppTerminalView` across SwiftUI rebuilds) and `#0074` (the wrapper's attach logic is idempotent and eager), the NSView is now reliably *in the container* — but the user reports the pane is **still blank** after navigation. The screenshot shows three "Batty" tabs in the chip row with completely black/empty terminal areas below. No prompt, no scrollback, no output.

Logs show the smoking gun:

```
re-attaching orphaned AppTerminalView to container
focus skipped: no AppTerminalView matched the requested terminal state
io_exec: started subcommand path=/usr/bin/login pid=95053
...
re-attaching orphaned AppTerminalView to container
focus skipped: no AppTerminalView matched the requested terminal state
```

Every new tab or split fires the re-attach (which is now expected per `#0074`'s logic — initial attach also looks "orphaned"), but the AppTerminalView still produces no visible output. The PTY is alive (libghostty spawns the shell). The NSView is in the hierarchy. **The renderer isn't painting.**

## Hypothesis

`AppTerminalView.viewDidMoveToWindow` in `../libghostty-spm/Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView.swift` handles three cases:

- `window == nil`: stop display link.
- `window != nil && surface == nil`: `rebuildIfReady` (create surface, start PTY).
- `window != nil && surface != nil`: `synchronizeMetrics` only.

When our wrapper re-parents an existing AppTerminalView to a new container that's already in a window:
1. `removeFromSuperview` → `viewDidMoveToWindow(nil)` → display link stopped.
2. `addSubview` to new container → `viewDidMoveToWindow(newWindow)` → `synchronizeMetrics`.

But **`synchronizeMetrics` does NOT restart the display link.** The renderer needs an active display link to paint. After our reparent, the link is stopped and never resumed. The PTY keeps running, output keeps being processed by libghostty internally, but the metal layer never draws.

That matches every observation: PTY alive, NSView present, screen blank.

## Steps to reproduce

Per the user's repro (consistent with the logs):

1. Launch Batty.
2. `cd ~/Developer/brennanMKE/Batty`, type `claude`. A Claude Code session is running.
3. `Cmd-T` (new tab) — view tree mutates, the original tab's wrapper re-mounts, AppTerminalView is reparented.
4. Switch back to the original tab.
5. **Observed:** the tab is blank. The Claude Code session is technically still alive (the PTY survived per `#0072`) but you can't see any of its output.

## Expected behavior

When the wrapper re-parents an AppTerminalView, the display link / renderer state is restored so the metal layer paints again. The user sees the existing PTY's output as if no remount happened.

## Implementation guidance

Two paths. Investigate which is the smaller delta:

### Path 1: Force a display-link restart on re-attach

Most surgical. After `addSubview` and constraint activation in `StableTerminalSurfaceView.attachIfNeeded`, prod libghostty to restart its renderer. Look in the fork for:

- A public method on `AppTerminalView` (or its coordinator / surface) that restarts the display link or kicks the renderer. Names to grep: `displayLink`, `startDisplayLink`, `setNeedsDisplay`, `needsDisplay`, `render`, `synchronize`.
- If none exists, the fork needs a small addition: a public `restartRenderer()` (or equivalent) that re-creates / resumes the CVDisplayLink and forces a frame.
- A possibly-good shortcut: `view.window?.makeFirstResponder(view); view.needsDisplay = true` — try this first, it may be enough for AppKit's coalescing to kick the renderer back to life.

Document what you find in the resolution Gotchas.

### Path 2: Switch to Option C — surface registry + single AppKit host

The architecture rule in `CLAUDE.md` actually asks for this:

> Surface registry is the single source of truth for live Terminal Sessions. SwiftUI views only ever store `surfaceID: UUID`, never a `ghostty_surface_t` directly. View rebuilds must not destroy surfaces.

The cleanest version: one NSViewController-managed host view per window. The host holds every active AppTerminalView as a subview and never removes them — it just positions and toggles visibility based on `pane.activeTabID`, `tree.focusedPaneID`, `store.selectedSessionID`. SwiftUI renders a `HostAnchorView` (a small NSViewRepresentable) per pane that tells the host where to position the relevant terminal NSView for that pane via frame geometry.

This is heavier work but matches the architecture rule and eliminates the reparent step entirely — the display link never stops because the NSView never leaves its container.

### Recommendation

Try **Path 1 first** — much smaller delta. If a simple `needsDisplay = true` (or fork-side `restartDisplayLink()`) brings the renderer back, ship that. If libghostty's renderer can't be coerced into restarting without recreating the surface (which would lose the PTY), fall back to Path 2.

Either way, the existing `StableTerminalSurfaceView`'s "PTY survives view tear-down" guarantee from `#0072` must be preserved.

## Acceptance criteria

- After navigating away from a tab and back (any focus path), the tab's terminal contents are **visibly rendered** — running process output, scrollback, prompt.
- The "re-attaching orphaned AppTerminalView to container" log can still fire; it's no longer a problem because the renderer resumes correctly.
- "focus skipped: no AppTerminalView matched the requested terminal state" continues to be acceptable as a brief cold-launch race (per `#0066`); it should not produce blank panes during normal navigation.
- Specifically: a `claude` session running in tab 1, `Cmd-T` to spawn tab 2, `Cmd-Shift-[` back to tab 1 → the Claude Code TUI is visible and interactive.

## Out of scope

- Persisting the rendered state across app restarts (workspace restore is off by default per `#0055`).
- Optimizing the display link for non-visible tabs (we could pause it for hidden tabs; later optimization).

### What the libghostty code actually does on re-attach

`../libghostty-spm/Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView+Lifecycle.swift`,
`viewDidMoveToWindow()` (libghostty branch `batty-delegates`, commit
`ef88eed`):

```swift
if window != nil {
    if surface == nil {
        core.rebuildIfReady()
    } else {
        core.synchronizeMetrics()
    }
    updateMetalLayerMetrics()
    updateColorScheme()
    core.startDisplayLink()      // <-- ALWAYS called on re-attach
    core.requestImmediateTick()  // <-- ALWAYS called on re-attach
    ...
} else {
    core.stopDisplayLink()
    core.setFocus(false)
}
```

So the claim in this issue's "Hypothesis" that `synchronizeMetrics` is the
only thing that runs on re-attach with an existing surface is **wrong**.
`startDisplayLink()` + `requestImmediateTick()` always run. In theory the
renderer resumes. The Path 1 premise ("inject a missing display-link
restart") therefore does not match the code as it ships.

### What the renderer actually is

It is **render-on-demand**, not a continuous display link. See
`TerminalSurfaceCoordinator.scheduleTickIfNeeded` — it does a one-shot
`DispatchQueue.main.async` tick, then sets `tickScheduled = false`. The only
thing that drives subsequent renders is `bridge.onRenderRequest` (called
from `GHOSTTY_ACTION_RENDER` in `TerminalCallbackBridge.handleAction`),
which libghostty fires whenever the surface has new content. Plus the
metric-sync paths in `setFrameSize` / `layout` / `viewDidChangeBackingProperties`
which all call `requestImmediateTick`.

So if the bug is truly "renderer stopped, everything else fine", the
question is: why don't subsequent `onRenderRequest` callbacks restart the
tick? Possible answers I could not eliminate without runtime instrumentation:

1. `bridge.rawSurface` got nilled or `onRenderRequest` got disconnected.
   The `bridge` ivar on the coordinator is set in `init`, and `rawSurface`
   is cleared by `tearDownSurface`. If nothing tears down, both stay set.
2. `shouldRenderFrame` returns false because `isAttached()` returns false.
   `isAttached` is `{ [weak self] in self?.window != nil }`. After the
   reparent re-completes, `window` should be non-nil.
3. The `controller.onWakeup` closure was nilled. It is set in
   `rebuildIfReady` to call `requestImmediateTick`. It is **also** cleared
   in `tearDownSurface(removingBridgeFrom:)`. If a stale code path runs
   `tearDownSurface`, the wakeup is lost — but ghostty's `onRenderRequest`
   path still works via `bridge`, so this would only matter for the
   controller-driven wakeups.

None of these are reliable to diagnose without runtime breakpoints.

### What was considered for the wrapper-side kick

`AppTerminalView` exposes only `delegate`, `controller`, `configuration`,
`setSurfaceVisible(_:)`, and (via extension) `fitToSize()` as the public
mutators. Of these:

- `controller =` re-set triggers `rebuildIfReady`, which `tearDownSurface`s.
  **Kills the PTY.** Not viable.
- `configuration =` re-set triggers `rebuildIfReady` when not equivalent.
  Same problem.
- `setSurfaceVisible(true)` is guarded by `isDisplayVisible != visible`, and
  the default is already `true`, so a single call is a no-op. Toggling
  `false` → `true` would call `stopDisplayLink()` on the false leg, then
  `requestImmediateTick` on the true leg. That's exactly what we want, but
  the intermediate `setOcclusion(false)` may have side effects (ghostty
  signals occlusion to the process, e.g. for SIGWINCH semantics).
- `fitToSize()` is `synchronizeMetrics() + requestImmediateTick()`. Cheap.
  But this is **already what `viewDidMoveToWindow` does** on the new-window
  attach. If that path isn't fixing things, calling `fitToSize()` from the
  wrapper after re-attach is redundant.
- `view.needsDisplay = true`, `view.layer?.setNeedsDisplay()` don't drive
  Metal layer redraws — Metal is explicit-draw, not delegate-based.

I considered but did not ship any of these because none of them
*meaningfully* differs from what `viewDidMoveToWindow` already does, and
the user has been burned twice by "this should work" landings.

## Root cause

The `#0072` and `#0074` wrappers both violated rule 1 of
`nsviewrepresentable-state-persistence.md`:

> Never call `removeFromSuperview()`, replace `subviews`, or assign a
> new `documentView` in `updateNSView`. Mutate properties in place.

`StableTerminalSurfaceView.attachIfNeeded` re-parented the
`AppTerminalView` between containers on every mount cycle. Even when
the re-parent landed cleanly, libghostty's `viewDidMoveToWindow(nil)`
→ `viewDidMoveToWindow(newWindow)` pair tore down and restarted
auxiliary state (display link, key-window observers, screen-change
observers) the renderer relied on. In practice the renderer's
on-demand tick chain — driven by `bridge.onRenderRequest` from
libghostty's render-callback path — did not always resume after the
detach/reattach pair, leaving the metal layer un-painted. PTY was
alive; NSView was in the hierarchy; nothing drew. Three subagents in a
row tried to plug specific holes in that chain (re-parent contract,
idempotent attach, then a hypothesized display-link-restart) and each
exposed the next layer of fragility.

The fix is architectural, not surgical: never reparent.

## Fix

Single persistent AppKit host per window. The `AppTerminalView` for
each tab now lives in one `TerminalHostView` owned by
`TerminalHostStore` and added once as a subview of the window's
`contentView`. SwiftUI no longer touches the terminal NSView — it
renders transparent `TerminalPlaceholderView`s that report their
window-coordinate frame via `TerminalPlacementPreferenceKey`, and
`SessionDetailView` forwards the merged placement map to the host
store. The host updates `frame` and `isHidden` per terminal; it never
reparents. `viewDidMoveToWindow` fires exactly twice in a terminal's
lifetime: once on first appearance (host adds it on first
`terminalView(for:)` call), once on close
(`pane.removeTab(id:)` calls `TerminalHostStore.releaseTerminalView`).

This matches the architecture rule in `CLAUDE.md`:

> Surface registry is the single source of truth for live Terminal
> Sessions. SwiftUI views only ever store `surfaceID: UUID`, never a
> `ghostty_surface_t` directly. View rebuilds must not destroy
> surfaces.

`TabRuntime.terminalNSView` remains as a back-reference for tests and
tab-scoped consumers, but the host store is the authority. The
`#0072` PTY-survival contract is preserved end-to-end: closing a tab
is the only thing that releases an `AppTerminalView`.

## Gotchas

- The behavioural fix (terminal renders across navigation) cannot be
  unit-tested. It lives in AppKit's Metal pipeline and SwiftUI's
  `NSViewRepresentable` lifecycle. Visual verification under the
  repro from `#0072` (start a TUI such as `claude`, `Cmd-T`,
  `Cmd-Shift-[`) is the only way to confirm the renderer is painting
  after navigation. **I did not run this verification** — no
  interactive desktop available from this session. The unit tests
  cover only the model contracts (`TerminalHostStore` idempotency and
  release, `PaneRuntime` model behaviour). Build passes
  (`xcodebuild -scheme Batty -destination 'platform=macOS' build`),
  `swift test --package-path BattyKit` reports 180/180.
- Coordinate space assumption: SwiftUI's `frame(in: .global)` returns
  coordinates in the root SwiftUI hosting view's space, and the host
  is added as a subview of the window's `contentView` (which is the
  `NSHostingView` for the SwiftUI `Window` scene). `TerminalHostView`
  is `isFlipped = true` so its subview frames use SwiftUI's top-left
  origin. If this assumption is wrong (e.g. the contentView is some
  intermediate AppKit view that wraps the hosting view at a non-zero
  origin), terminals will be offset and the manual verification will
  catch it; the fix is a single `host.convert(_:from:)` call when
  applying placements.
- Z-order: the host is added `positioned: .above, relativeTo: nil` so
  it overlays the SwiftUI tree. The host itself is transparent, and
  `TerminalHostView.hitTest(_:)` falls through to the SwiftUI tree
  for points not inside a visible terminal subview. The chip row
  remains visible because terminals are only positioned where the
  placeholder is (below the chip row).
- The host releases terminal views in two places:
  `PaneRuntime.removeTab` / `closeOtherTabs` (model-driven tab close),
  and `AppStateStore.removeSession` (session removal cascade). Don't
  add a third path; if a tab needs to go, route through one of those.
  Releasing here is what kills the PTY — same contract as `#0072`.
- `TerminalHostStore.shared` is a singleton, justified by Batty being
  single-window-by-default. If multi-window lands, this becomes one
  store per window keyed by window identifier. The tests use a
  freshly-constructed `TerminalHostStore()` (not `.shared`) so they
  do not pollute global state.
- libghostty's `AppTerminalView.viewDidMoveToWindow(nil)` does NOT
  free the surface — it only stops the display link and clears focus.
  When `releaseTerminalView` calls `removeFromSuperview`, the
  `viewDidMoveToWindow(nil)` runs but the surface stays alive until
  the `AppTerminalView` deallocates (which it does immediately,
  because the host's dictionary entry and `TabRuntime.terminalNSView`
  are both released). At that point the
  `TerminalSurfaceCoordinator.deinit` calls `tearDownSurface` →
  `surface?.free()`. This is the PTY shutdown path.
- The previous wrappers (`#0072` and `#0074`) hooked
  `dismantleNSView` as an explicit no-op; this version doesn't need
  that hook at all because the placeholder isn't an
  `NSViewRepresentable` — it's just a SwiftUI `GeometryReader`
  emitting a preference key. The release path runs from the model
  side (`pane.removeTab`), never from SwiftUI's lifecycle.
- `closeTab` in `AppStateStore` no longer duplicates the
  `releaseTerminalView` call — the cascade goes
  `closeTab → pane.removeTab → TerminalHostStore.releaseTerminalView`.

## Phase 2 — host attached via NSViewRepresentable (commit c6ba431)

Phase 1 worked architecturally — single host, no reparenting, terminals
added once and frame-positioned — but the **attach point** was wrong.
`TerminalHostStore.attachHost(to:)` added the `TerminalHostView` as a
subview of `window.contentView`. On modern macOS the contentView is an
`NSHostingController.view`, and AppKit logs this exact warning when a
foreign `NSView` is added under it:

```
Adding 'TerminalHostView' as a subview of NSHostingController.view is
not supported and may result in a broken view hierarchy. Add your view
above NSHostingController.view in a common superview or insert it into
your SwiftUI content in a NSViewRepresentable instead.
```

The result was a hierarchy that AppKit refused to paint reliably —
panes still came up blank — even though Phase 1's lifecycle invariants
all held.

### Fix

Apply Pattern 3 from `nsviewrepresentable-state-persistence.md`
literally. The host stays owned by `TerminalHostStore.shared`, but it
reaches the view hierarchy through `TerminalHostInstaller`, an
`NSViewRepresentable` whose `makeNSView` returns the singleton's
existing `hostView`:

```swift
struct TerminalHostInstaller: NSViewRepresentable {
    func makeNSView(context: Context) -> TerminalHostView {
        TerminalHostStore.shared.hostView
    }
    func updateNSView(_ nsView: TerminalHostView, context: Context) { }
    static func dismantleNSView(_ nsView: TerminalHostView, coordinator: ()) { }
}
```

Even when SwiftUI tears down and rebuilds the representable, the host
and every `AppTerminalView` subview survive in the store. The empty
`dismantleNSView` is load-bearing: without it, SwiftUI would release
the host on view-hierarchy churn and destroy every live PTY.

`TerminalHostStore` loses `attachHost(to:)` and `attachedWindow`.
There is no contentView attachment anywhere now — the store just owns
the host and vends it.

### Coordinate space

Phase 1 used `proxy.frame(in: .global)` and added the host directly to
`contentView`, so global coordinates more-or-less matched
contentView-local. Phase 2 puts the host inside the SwiftUI tree as a
sibling of session chrome, so the host's local coordinates are no
longer the same as `.global`.

Fix: declare a named coordinate space on the ZStack that contains the
host installer, and report placeholder frames in that named space:

- `SessionDetailView` calls `.coordinateSpace(name: TerminalHostInstaller.coordinateSpaceName)`
  on the ZStack.
- `TerminalPlaceholderView` reports `proxy.frame(in: .named(TerminalHostInstaller.coordinateSpaceName))`.

The named space and the host installer share the same parent and the
same origin, so the values feed straight into
`subview.frame = placement.frame` on the host with no further
conversion.

### Strict invariants preserved

All Phase 1 invariants still hold:

- The store owns the host. `makeNSView` retrieves it; never constructs.
- Terminals are added to the host once. Never reparented.
- `updateNSView` is a no-op (the real update path is
  `updatePlacements` driven by preference-key changes).
- `dismantleNSView` is a no-op (the host must not be released).
- No `removeFromSuperview` calls outside `releaseTerminalView` on tab
  close.
