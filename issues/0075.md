# 0075 — Re-attached terminal NSView renders blank: display link / renderer state lost across reparent

| | |
|---|---|
| **Status** | open |
| **Module** | TerminalSurface / Pane / GhosttyKit |
| **Platform** | macOS |
| **First seen** | 2026-05-11 |

## Description

After `#0072` (wrapper preserves the `AppTerminalView` across SwiftUI rebuilds) and `#0074` (the wrapper's attach logic is idempotent and eager), the NSView is now reliably *in the container* — but the user reports the pane is **still blank** after navigation. The screenshot shows three "Batty" tabs in the chip row with completely black/empty terminal areas below. No prompt, no scrollback, no output.

Logs show the smoking gun:

```
re-attaching orphaned AppTerminalView to container
focus skipped: no AppTerminalView matched the requested terminal state
io_exec: started subcommand path=/usr/bin/login pid=95053
...
re-attaching orphaned AppTerminalView to container
focus skipped: no AppTerminalView matched the requested terminal state
```

Every new tab or split fires the re-attach (which is now expected per `#0074`'s logic — initial attach also looks "orphaned"), but the AppTerminalView still produces no visible output. The PTY is alive (libghostty spawns the shell). The NSView is in the hierarchy. **The renderer isn't painting.**

## Hypothesis

`AppTerminalView.viewDidMoveToWindow` in `../libghostty-spm/Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView.swift` handles three cases:

- `window == nil`: stop display link.
- `window != nil && surface == nil`: `rebuildIfReady` (create surface, start PTY).
- `window != nil && surface != nil`: `synchronizeMetrics` only.

When our wrapper re-parents an existing AppTerminalView to a new container that's already in a window:
1. `removeFromSuperview` → `viewDidMoveToWindow(nil)` → display link stopped.
2. `addSubview` to new container → `viewDidMoveToWindow(newWindow)` → `synchronizeMetrics`.

But **`synchronizeMetrics` does NOT restart the display link.** The renderer needs an active display link to paint. After our reparent, the link is stopped and never resumed. The PTY keeps running, output keeps being processed by libghostty internally, but the metal layer never draws.

That matches every observation: PTY alive, NSView present, screen blank.

## Steps to reproduce

Per the user's repro (consistent with the logs):

1. Launch Batty.
2. `cd ~/Developer/brennanMKE/Batty`, type `claude`. A Claude Code session is running.
3. `Cmd-T` (new tab) — view tree mutates, the original tab's wrapper re-mounts, AppTerminalView is reparented.
4. Switch back to the original tab.
5. **Observed:** the tab is blank. The Claude Code session is technically still alive (the PTY survived per `#0072`) but you can't see any of its output.

## Expected behavior

When the wrapper re-parents an AppTerminalView, the display link / renderer state is restored so the metal layer paints again. The user sees the existing PTY's output as if no remount happened.

## Implementation guidance

Two paths. Investigate which is the smaller delta:

### Path 1: Force a display-link restart on re-attach

Most surgical. After `addSubview` and constraint activation in `StableTerminalSurfaceView.attachIfNeeded`, prod libghostty to restart its renderer. Look in the fork for:

- A public method on `AppTerminalView` (or its coordinator / surface) that restarts the display link or kicks the renderer. Names to grep: `displayLink`, `startDisplayLink`, `setNeedsDisplay`, `needsDisplay`, `render`, `synchronize`.
- If none exists, the fork needs a small addition: a public `restartRenderer()` (or equivalent) that re-creates / resumes the CVDisplayLink and forces a frame.
- A possibly-good shortcut: `view.window?.makeFirstResponder(view); view.needsDisplay = true` — try this first, it may be enough for AppKit's coalescing to kick the renderer back to life.

Document what you find in the resolution Gotchas.

### Path 2: Switch to Option C — surface registry + single AppKit host

The architecture rule in `CLAUDE.md` actually asks for this:

> Surface registry is the single source of truth for live Terminal Sessions. SwiftUI views only ever store `surfaceID: UUID`, never a `ghostty_surface_t` directly. View rebuilds must not destroy surfaces.

The cleanest version: one NSViewController-managed host view per window. The host holds every active AppTerminalView as a subview and never removes them — it just positions and toggles visibility based on `pane.activeTabID`, `tree.focusedPaneID`, `store.selectedSessionID`. SwiftUI renders a `HostAnchorView` (a small NSViewRepresentable) per pane that tells the host where to position the relevant terminal NSView for that pane via frame geometry.

This is heavier work but matches the architecture rule and eliminates the reparent step entirely — the display link never stops because the NSView never leaves its container.

### Recommendation

Try **Path 1 first** — much smaller delta. If a simple `needsDisplay = true` (or fork-side `restartDisplayLink()`) brings the renderer back, ship that. If libghostty's renderer can't be coerced into restarting without recreating the surface (which would lose the PTY), fall back to Path 2.

Either way, the existing `StableTerminalSurfaceView`'s "PTY survives view tear-down" guarantee from `#0072` must be preserved.

## Acceptance criteria

- After navigating away from a tab and back (any focus path), the tab's terminal contents are **visibly rendered** — running process output, scrollback, prompt.
- The "re-attaching orphaned AppTerminalView to container" log can still fire; it's no longer a problem because the renderer resumes correctly.
- "focus skipped: no AppTerminalView matched the requested terminal state" continues to be acceptable as a brief cold-launch race (per `#0066`); it should not produce blank panes during normal navigation.
- Specifically: a `claude` session running in tab 1, `Cmd-T` to spawn tab 2, `Cmd-Shift-[` back to tab 1 → the Claude Code TUI is visible and interactive.

## Out of scope

- Persisting the rendered state across app restarts (workspace restore is off by default per `#0055`).
- Optimizing the display link for non-visible tabs (we could pause it for hidden tabs; later optimization).

## Notes

- This is the third issue in the `#0072` → `#0074` → `#0075` chain trying to nail down PTY + NSView preservation. Each layer fixed a real bug but exposed the next. With this one, all three should converge.
- The fork may need an addition. Document the required public API surface; if it's tiny (one method to restart the renderer), it's worth landing inline.
