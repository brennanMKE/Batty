## Description

In a long-running Prod Batty 1.3.0, one terminal is drawn on top of the content no matter which Session is selected. User report, 2026-10-25, verbatim:

> There is currently a glitch in this instance of Batty. It appears there is a terminal window appearing over others no matter which session I am using.

It is not a separate window. `CGWindowListCopyWindowInfo` shows exactly one on-screen Batty window: window 105003, layer 0, bounds 74,70 1838x934, title "Batty". The overlay is inside the main window.

**A live debug-level log confirmed the cause, and it has been traced in code (see "Live reproduction" and "Traced cause" below).** When Cmd-W closes the last tab of a terminal Pane, the Pane leaves the split tree. About 12 ms after `releaseTerminalView` frees that tab, `TerminalHostStore` creates a *new* terminal view for the same, just-released tab id, and the new view spawns a fresh PTY and login shell. No model references that tab any more, so nothing ever hides or releases the new view. It sits in the persistent `TerminalHostView` (`docs/view-hierarchy.md` §3), unhidden at its last frame and without Pane chrome, and draws over every Session. The new view comes from `TerminalPlaceholderView.body`, which calls the store's get-or-create `terminalView(for:windowID:)` on every evaluation, and the store keeps no record that the tab was released. The `TabRuntime ... still referenced 0.5s after release` notice (the #0520 leak signal) fires right after each recreation.

Two orphans were on screen in pid 194, from a closed Backbeat Session and from a closed MilkDropMetalKit Session. The user exited both shells, and both views now show "Process exited. Press any key to close the terminal." The MilkDropMetalKit shell (58325) was exited at 00:12:45. Only quitting Batty clears them today. Exiting the shell and pressing the close key at the "Process exited" screen does nothing (see "The close key does not remove an orphan"). `batty list` does not show them, and the CLI has no verb to close a tab.

## Root cause

`TerminalPlaceholderView.body` calls `TerminalHostStore.shared.terminalView(for:windowID:)` on every evaluation, and the store's get-or-create kept no record of released tabs. When a Pane's last tab is closed, SwiftUI can evaluate that Pane's placeholder once more while it still holds the dead `TabRuntime`. That evaluation built a new `AppTerminalView` (new PTY and shell) for the released id, and the placeholder's last `onGeometryChange` unhid it via `setPlacement`. No model tab referenced the id, so nothing hid or released it, and `AppStateStore.closeTab(id:)` silently ignored its "press any key to close" request because no window owned the tab.

## Fix

- `TerminalHostStore` keeps `releasedTabIDs: Set<UUID>`, inserted at the top of `releaseTerminalView(forTabID:)` (before the no-view early return). `terminalView(for:windowID:)` now returns `AppTerminalView?`: after the existing-view branch, a released id logs a `.notice` (`refused terminal view for released tab …`) and returns `nil` without creating anything. `setPlacement` and `updatePlacements` skip released ids, so no dead `placements` entry is left. Tab ids are fresh `UUID()`s and never reused, so the set is never pruned.
- `AppStateStore.closeTab(id:)`: when no window owns the tab but the shared store still has a view for it, log `.warning` and call `releaseTerminalView(forTabID:)`, so an orphan that slips through can be closed from inside it.
- Comments and docs: the placeholder comment no longer claims idempotence; `TerminalHostInstaller.updateNSView` and `TerminalSurfaceFocuser` no longer name the nonexistent `TerminalPlacementPreferenceKey` / `updatePlacements` as the production path; `docs/swiftui-observation-rules.md` (sanctioned exceptions) and `docs/view-hierarchy.md` §3/§4 describe `setPlacement` as the production path and the store's released-id refusal.
- No observed state is written, and there are no `Task` hops. The set is a plain property on the non-`@Observable` store, written only from close paths.

### Approach

The store owns the rule "a released tab never gets a view again". That keeps the sanctioned `body` exception within its documented first-mount-only bound without moving creation out of `body`. Moving creation to an event-owned path is a larger change to the terminal-host architecture, and this fix doesn't need it. Nothing writes observed state. The record of released ids is a plain stored property on the non-`@Observable` `TerminalHostStore`, written only from the close paths (event-origin), never from `body`. No `Task` hops.

### Traced cause (read-only trace of `main`, unchanged since `v1.3.0`)

None of `Views/TerminalPlaceholderView.swift`, `Views/PaneView.swift`, `Runtime/TerminalHostStore.swift` or `Util/TerminalHostInstaller.swift` (all under `BattyKit/Sources/BattyKit/`) has changed between `v1.3.0` and `main`. The trace below applies to the running 1.3.0 build and to `main`.

1. **`body` creates terminals.** `TerminalPlaceholderView.body` (`Views/TerminalPlaceholderView.swift:43`) runs `let _ = TerminalHostStore.shared.terminalView(for: tab, windowID: windowID)` on *every* body evaluation, with no condition. The comment above it calls this "Idempotent — the store returns the existing view on every call after the first". That only holds while the view is still registered. This body is the only production caller of `terminalView(for:windowID:)`.
2. **The store's get-or-create has no memory of releases.** `TerminalHostStore.terminalView(for:windowID:)` (`Runtime/TerminalHostStore.swift:163`) looks only at `terminalViews[tab.id]`. `releaseTerminalView(forTabID:)` (line 280) removes that entry along with `placements`, `tabRuntimes` and `tabWindowMap`, and records nothing else. So a later call takes the creation branch:
   - It makes a new `AppTerminalView` and wires `delegate`, `controller` and `configuration` from the dead `TabRuntime`.
   - It runs `host.addSubview(view)`, re-registers the view in `terminalViews`, `tabWindowMap` and `tabRuntimes`, and sets `tab.terminalNSView`.
   - It logs `created terminal view for tab …`. libghostty sees the view join a window and spawns a new PTY (`io_exec: started subcommand`).

   Nothing refuses an id that was just released. The new view also holds `tab.terminal.controller`, which is why the `TabRuntime` and its ghostty app outlive the 0.5 s probe (the #0520 notice).
3. **The re-creation sequence.** When the emptied Pane leaves the split tree, SwiftUI evaluates that Pane's `TerminalPlaceholderView.body` once more while it still holds the dead `TabRuntime`. That evaluation re-creates the view (00:08:38.748). The placeholder's `onGeometryChange` then calls `setPlacement(Placement(frame:, isVisible: true), forTabID:)`. That is the `occlusionApply[setPlacement] tab=284EFD2D isHidden=false … effective=true` line at 00:08:38.756, and it unhides the view at the placeholder's last frame. Then the placeholder unmounts.

   Which update triggered that last evaluation (the Pane's removal, or an observation flip on the dying `TabRuntime`/Pane) is inferred from the code and the log timing, not observed directly.
4. **Nothing hides it afterwards.** No production path hides views whose tab has left the model:
   - The only production callers of `setPlacement` are the placeholder itself (`TerminalPlaceholderView.swift:50, 56`) and the hide-Pane path in `WindowRuntime` (around line 918). The hide-Pane path walks only the tabs of the Pane being hidden.
   - `updatePlacements(_:forWindowID:)` would hide tracked views that are missing from its map, but it has **no production caller**. Only `StableTerminalSurfaceTests` calls it. The comment in `TerminalHostInstaller.updateNSView` (`Util/TerminalHostInstaller.swift:36–39`) says geometry is "pushed into the host via `TerminalHostStore.updatePlacements(_:forWindowID:)`, which is driven by `TerminalPlacementPreferenceKey` changes". That comment is stale, because no `TerminalPlacementPreferenceKey` type exists in the sources. The "sanctioned exceptions" paragraph in `docs/swiftui-observation-rules.md` names the same function as the placement path.
   - `releaseTerminalView` already ran from the close path, and no model tab has the id, so nothing calls it again.

   The view stays in `terminalViews`, unhidden at its last frame, above every Session, for the life of the process. Its `AppTerminalView` keeps receiving clicks (`click-focus: tab=<dead id>`).
5. **This breaks a binding rule.** `docs/swiftui-observation-rules.md` says "View construction is pure", and it allows `TerminalPlaceholderView.body`'s lazy `terminalView(for:)` only as a "one-time `addSubview` into the persistent host on first mount … bounded by design — first-mount-only". Re-creating the view for a released tab breaks that bound. `PaneView.swift:90–94` already warns that this call "lazily spawns a PTY as a rendering side effect" (`docs/pane-kinds.md` §2). Until now it was guarded only against non-terminal Pane kinds reaching the placeholder, not against a terminal tab that has been released.

### The close key does not remove an orphan

At 00:12:45.915 the user ran `exit` in the MilkDropMetalKit orphan, and shell 58325 / login 58323 are gone. libghostty logged `io_exec: pty fd closed`, and Batty logged `PaneView onClose tab=284EFD2D… processAlive=false`. The user then pressed keys at the "Process exited. Press any key to close the terminal." screen. `onClose tab=284EFD2D processAlive=false` was logged again at 00:12:46.722 and 00:12:48.377, and the view stayed on screen. The Backbeat orphan shows the same pattern: `onClose tab=33CEB33B` at 00:05:43.155, 00:06:13.741, 00:06:15.565 and 00:06:15.788, with the view still there.

So libghostty's close request does reach Batty, but nothing acts on it. In the code:

- The handler is installed in `PaneView`'s `.task(id: tab.id)` (`Views/PaneView.swift:287–294`). It calls `appStore.closeTab(id: tab.id)` and falls back to `pane?.removeTab(id:)` only when `appStore` is nil.
- `AppStateStore.closeTab(id:)` (`Runtime/AppStateStore.swift:1430`) looks for the tab in each window with `window.locate(tabID:)`. If no window has it, the method returns silently and logs nothing.
- The orphan's tab was already removed from the model, so nothing is found, and `releaseTerminalView` is never called for the registered view.

The orphan cannot be closed from inside it, from the CLI, or from the UI.

**Still open:** which close sequences cause the extra body evaluation. It happened for MilkDropMetalKit and Backbeat, but not for Homelab (see below).

**Fix directions for the planner (options, not decisions):**

- The store refuses to create a view for a released tab, for example with a tombstone set of released ids in `TerminalHostStore`, or a closed flag on `TabRuntime` that `releaseTerminalView` sets and `terminalView(for:windowID:)` checks.
- And/or move creation out of `body` into an event-owned path (the tab-creation event, or an `onAppear` that checks the tab is still live), so evaluating `body` can never spawn a PTY.
- Separately, decide whether the stale `updatePlacements` comment and the swiftui-observation-rules paragraph should be corrected, or whether a per-window sweep that hides views for tabs absent from the model is wanted as defence in depth.
- Make the close path release orphans too: when `onClose` (or `AppStateStore.closeTab(id:)`) finds no model tab for an id that `TerminalHostStore` still has a view for, call `releaseTerminalView(forTabID:)`, so an orphan that slipped through can at least be closed from inside.
- Unit test: after `releaseTerminalView(forTabID:)`, a call to `terminalView(for:windowID:)` for the same `TabRuntime` creates no view (`hasTerminalView(forTabID:)` stays false, the host's subview count is unchanged) and attaches no controller, so no PTY spawns.

**What differs is unknown.** Removing a Pane does not always trigger it. In the same recording, the user closed tabs 03D5CB3E, 7A49C4AD and EC85B6F6 in Session Homelab. Pane 1906D3DE was removed at 00:09:16.036, then a Pane whose tab 8566EFB1 had no registered view was closed. None of this logged `created terminal view`. It is not known what differs between Homelab and MilkDropMetalKit (layout, the type of sibling Pane, selection or focus state at close time). The planner should compare them.
