# 0535 — A terminal stays drawn over the selected Session in a long-running Prod Batty no matter which Session is selected

| | |
|---|---|

| **Module** | TerminalSurface / GhosttyKit / Session / Tabs |
| **Platform** | macOS |

## Description

In a long-running Prod Batty 1.3.0, one terminal is drawn on top of the content no matter which Session is selected. User report, 2026-10-25, verbatim:

> There is currently a glitch in this instance of Batty. It appears there is a terminal window appearing over others no matter which session I am using.

It is not a separate window. `CGWindowListCopyWindowInfo` shows exactly one on-screen Batty window: window 105003, layer 0, bounds 74,70 1838x934, title "Batty". The overlay is inside the main window.

**A live debug-level log confirmed the cause (see "Live reproduction" below).** When Cmd-W closes the last tab of a terminal Pane, the Pane leaves the split tree. About 12 ms after `releaseTerminalView` frees that tab, `TerminalHostStore` creates a *new* terminal view for the same, just-released tab id, and the new view spawns a fresh PTY and login shell. No model references that tab any more, so nothing ever hides or releases the new view. It sits in the persistent `TerminalHostView` (`docs/view-hierarchy.md` §3), unhidden at its last frame and without Pane chrome, and draws over every Session. The `TabRuntime ... still referenced 0.5s after release` notice (the #0520 leak signal) fires right after each recreation.

Two orphans are on screen in pid 194 now. The first, from a closed Backbeat Session, shows "Process exited. Press any key to close the terminal." The second, from MilkDropMetalKit, runs a live shell (pid 58325). Only quitting Batty clears them today. `batty list` does not show them, and the CLI has no verb to close a tab.

## Steps to reproduce

Not yet reproduced on demand. This is what produced the second orphan (see "Live reproduction"). Try it in **Batty Beta**, not as a host UI test:

1. Open a Session with at least two terminal Panes and a Git Status Pane in a split.
2. Press Cmd-W on the tabs of one terminal Pane until that Pane is empty and leaves the tree.
3. Watch a debug-level `log stream` for `created terminal view for tab <just-released id>`, followed by libghostty `io_exec: started subcommand`.

The same steps did not always trigger it in the same recording. See "What differs is unknown" below.

## Expected behavior

Only the selected Session's active Tab terminals are visible. Terminals belonging to unselected Sessions, inactive Tabs, or closed Tabs are hidden (`isHidden = true`) or removed from the host, and nothing draws over the selected Session.

## Actual behavior

A terminal view for a closed tab stays visible over the content area, with no Pane chrome, whichever Session is selected. Clicks still reach it under the dead tab id. Its shell keeps running until the user exits it, and after that the view stays on screen showing "Process exited".

**What this settles.**

- `releaseTerminalView(forTabID:)` works as designed. It frees the surface and PTY and calls `removeFromSuperview()`. The orphan is a **second** view, created *after* the release.
- Here is the likely mechanism, inferred from the log and not yet traced in code. Removing the emptied Pane from the split tree causes a re-render. During it, something still holding the closing tab, most likely that Pane's `TerminalPlaceholderView` (or `TerminalHostInstaller`) on its way out, calls the store's get-or-create path, `TerminalHostStore.terminalView(for:windowID:)`. That path re-creates the view and puts it back in `terminalViews` and `tabWindowMap` under the released id. It also re-applies a visible placement (`setPlacement … isHidden=false`). From then on no model tab has that id, so no close path calls `releaseTerminalView` for it, and no later placement map ever includes it. Note: `updatePlacements` hides any tracked view of that window that is missing from its map, so either it never ran for that window after the recreation, or something re-showed the view. The log does not settle which. Either way the view stays unhidden at its last frame over every Session.
- `docs/view-hierarchy.md` §4 rule "Always go through the store" is not enough on its own: the store's get-or-create path accepts a tab id it has just released. Either the store needs to refuse a released id, or the view path needs to stop asking for one.
- The link to #0520 is now direct for these two tabs. The view rendering the released tab is what keeps its `TabRuntime` alive past the 0.5 s probe. Whether every #0520 notice is a recreation, or only some, is not known. Only one `created terminal view` line appears in this whole recording, against the seven notices in the earlier 3-hour log (five in the 22:01 burst).

**What differs is unknown.** Removing a Pane does not always trigger it. In the same recording, the user closed tabs 03D5CB3E, 7A49C4AD and EC85B6F6 in Session Homelab. Pane 1906D3DE was removed at 00:09:16.036, then a Pane whose tab 8566EFB1 had no registered view was closed. None of this logged `created terminal view`. It is not known what differs between Homelab and MilkDropMetalKit (layout, the type of sibling Pane, selection or focus state at close time). The planner should compare them.

**User hypothesis (2026-10-25): "closing a git status view may be causing it."** Recorded as stated. Here is what the evidence shows so far:

- For it: the MilkDropMetalKit Session had a Git Status Pane next to its terminal Panes. Git Status `setVisible` and watcher churn happens around Session switches.
- Against it: the recreation happened when the *terminal* Pane was removed (00:08:38.748), before the Git Status Pane closed (00:08:40.280).

It is not ruled out as a factor in the layout, for example as the sibling type.
