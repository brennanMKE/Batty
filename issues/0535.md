# 0535 — A terminal stays drawn over the selected Session in a long-running Prod Batty no matter which Session is selected

## Description

In a long-running Prod Batty 1.3.0, one terminal is drawn on top of the content no matter which Session is selected. User report, 2026-10-25, verbatim:

> There is currently a glitch in this instance of Batty. It appears there is a terminal window appearing over others no matter which session I am using.

It is not a separate window. `CGWindowListCopyWindowInfo` shows exactly one on-screen Batty window: window 105003, layer 0, bounds 74,70 1838x934, title "Batty". So the overlay is inside the main window. The likely cause is an `AppTerminalView` in the window's persistent `TerminalHostView` that is still unhidden and placed above whichever Session is selected (see `docs/view-hierarchy.md` §3 and §5). This is unconfirmed. Nobody has inspected the view tree, and the app must not be restarted to inspect it.

The same process logged seven `TabRuntime ... still referenced 0.5s after release` notices in three hours, across unrelated tab closes. That is the leak signal tracked in #0520. This report may be the first user-visible symptom of that leak, but the link is not proven.

## Steps to reproduce

Unknown. Seen once, in a Prod instance that had been running for about 10 days. No reproduction is known yet.

## Expected behavior

Only the selected Session's active Tab terminals are visible. Terminals belonging to unselected Sessions, inactive Tabs, or closed Tabs are hidden (`isHidden = true`) or removed from the host, and nothing draws over the selected Session.

## Actual behavior

One terminal stays visible over the content area when the user switches Sessions.

### Where to look (hypotheses, not findings)

- `TerminalHostStore.releaseTerminalView(forTabID:)` (`BattyKit/Sources/BattyKit/Runtime/TerminalHostStore.swift`, around line 280) calls `view.removeFromSuperview()` on every release. So a *released* tab's view should not stay in the host, even when its `TabRuntime` leaks. A leaked `TabRuntime` keeps the ghostty app and glyph atlas alive, not the NSView in the hierarchy. If the overlay is a closed tab's terminal, then something kept or re-added that view, or a close path never reached `releaseTerminalView`.
- `updatePlacements(_:forWindowID:)` (same file, around line 383) only touches views in `terminalViews` whose `tabWindowMap[id] == windowID`. A view still attached to the host but missing from `terminalViews`, or mapped to the wrong window, would never be hidden again. It would keep its last frame and `isHidden == false` through every Session switch. That matches the "over every Session" symptom.
- Per `docs/view-hierarchy.md` §2, unselected Sessions stay mounted at `.opacity(0)`, and their placeholders keep reporting frames with `isVisible == false`. A placeholder that stops emitting, or emits a stale `isVisible == true`, would leave its terminal unhidden over the selected Session.
- Whatever holds the leaked `TabRuntime` references (#0520), such as a SwiftUI placeholder, `PaneView`, or a rename sheet, may also be what keeps a placement or view alive. That is worth checking together with #0520.
