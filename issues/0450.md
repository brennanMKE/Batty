# 0450 — A Pane created with `batty pane split --command <cmd>` whose command finishes quickly shows Ghostty's red "failed to launch the requested command" banner even when the command ran successfully

| | |
|---|---|
| **Status** | open |
| **Module** | Pane / GhosttyKit / App / Testing |
| **Platform** | macOS |
| **First seen** | 2026-10-09 |

## Description

When an agent (or a human) runs `batty pane split --command <cmd>` and `<cmd>` exits within
a few tens of milliseconds, the new terminal Pane does not show the command's output on a
quiet, open Pane as `docs/batty-cli-agent-workflows.md` and `docs/batty-cli-install.md`
describe. It shows libghostty's abnormal-exit banner in red:

```
Ghostty failed to launch the requested command:

/usr/bin/login -flp admin /bin/bash --noprofile --norc -c exec -l /bin/sh /Users/admin/Library/Containers/Tests.xctrunner/Data/tmp/batty-ui-test-cli-ED2A66BA/agent.sh

Runtime: 93 ms

Press any key to close the window.
```

The command did not fail. In the run that produced that frame the script ran to completion
and every assertion about its side effects passed. The banner is misleading for exactly the
case agents use `--command` for most — a short command whose output should stay on screen —
and "Press any key to close the window" invites the reader to dismiss output the docs
promise will remain visible.

## Steps to reproduce

1. Launch Batty Beta.
2. From any shell: `batty pane split --command '/bin/sh -c "echo hello"'` (anything that
   exits in well under 250 ms; `--command 'true'` also does it).
3. Look at the new Pane.

## Expected behavior

The Pane stays open showing the command's output (here `hello`), with no failure banner —
the behavior both docs describe:

- `docs/batty-cli-agent-workflows.md:122-125`: "`--command` replaces the configured shell for
  that Pane and keeps the Pane open after the command exits so its output remains visible."
- `docs/batty-cli-install.md:1228-1232`: "`-c` panes also set libghostty's
  `wait-after-command = true` for that one pane, so the pane survives its command exiting
  instead of closing immediately — output stays readable until the pane is closed
  deliberately."

If a successful quick exit is instead meant to show *some* end-of-process marker, it must not
be worded as a launch failure, and the behavior must be documented deliberately.

## Actual behavior

The Pane shows the red "Ghostty failed to launch the requested command: … Runtime: N ms …
Press any key to close the window." banner. Whatever the command printed is above it (if it
printed anything), but the headline says the command failed.

## Notes

### How Batty passes `--command` to libghostty

- `batty pane split -c/--command` carries the string over XPC (`PaneSplitPayload.command`)
  into `TabRuntime(workingDirectory:command:)` (`BattyKit/Sources/BattyKit/Model/SplitTree.swift:374`).
- `TabRuntime.applyShellAndAppearancePreferences`
  (`BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:253-275`) renders it into the
  per-surface Ghostty config as `command = <cmd>` and, for `-c` panes only,
  `wait-after-command = true` (#0282 round 3). The comment block there records that
  `wait-after-command` was verified to round-trip with zero config diagnostics
  (`SplitTreeTargetedSplitTests.swift:144-181`) and quotes libghostty's semantic for it:
  "the terminal window will stay open until any keypress is received".
- Batty does **not** set `abnormal-command-exit-runtime` anywhere (no match in
  `BattyKit/Sources` or `Batty/`), so the pinned libghostty's default applies.
- The `/usr/bin/login -flp <user> /bin/bash --noprofile --norc -c exec -l /bin/sh <script>`
  line in the banner is libghostty's own macOS launch wrapper around the `command =` value;
  neither `exec -l` nor `login -flp` appears in Batty's sources.

### What the pinned libghostty says about the heuristic

The Zig core is not vendored — `BattyKit/.build/checkouts/libghostty-spm` (Lakr233/libghostty-spm
at `a2565ccf047c03c74a59dd7c16a8fac7c477852f`) ships `GhosttyKit.xcframework` as a binary
target built from upstream Ghostty `c4e16970a803b170e352432424f44192cb59f3ac` (`Ghostty.ref`).
Ghostty embeds its config documentation in the binary, so `strings` on
`BattyKit/.build/artifacts/libghostty-spm/libghostty/GhosttyKit.xcframework/macos-arm64_x86_64/libghostty.a`
yields the pinned build's own text for the two relevant keys:

> `abnormal-command-exit-runtime`: The number of milliseconds of runtime below which we
> consider a process exit to be abnormal. This is used to show an error message when the
> process exits too quickly. **On Linux, this must be paired with a non-zero exit code. On
> macOS, we allow any exit code because of the way shell processes are launched via the
> login command.**

> `wait-after-command`: If true, keep the terminal open after the command exits. Normally,
> the terminal window closes when the running command (such as a shell) exits. With this
> true, the terminal window will stay open until any keypress is received. This is primarily
> useful for scripts or debugging.

So per libghostty's own documentation the banner on macOS is driven by runtime alone, and the
command's exit status is irrelevant to whether it appears. The same binary also contains
the alternative end-of-process message `Process exited. Press any key to close the terminal.`
(the `wait-after-command` path); what the recordings show is the abnormal-exit banner, not
that one, so on a quick exit the abnormal check is what fires even with
`wait-after-command = true` set.

The default threshold in the pinned build is not confirmed from the binary (the docs string
does not include the value). The Ghostty 1.3.1 installed on the host
(`/Applications/Ghostty.app/Contents/MacOS/ghostty +show-config --default`) reports
`abnormal-command-exit-runtime = 250` and `wait-after-command = false`; both observed
runtimes (93 ms, 32 ms) are well under 250 ms. Whether the comparison is `<` or `<=` and the
exact message layout live in upstream `src/Surface.zig` (`childExited`), which an
implementer should read at commit `c4e16970a803` rather than assume.

### Exit status of the scripts

Not recorded anywhere in the run: the banner prints no exit code, the `surface:` log line
carries none, and the tests capture only the inner `batty` invocations' stdout/stderr, not
the script's own status. Structurally, `agent.sh` has no `set -e` so its status is that of
its last line (`touch`), and `touch-sentinel.sh` is only `touch`; both sentinels were
created, so the scripts' own status was almost certainly 0 — but whether the
`login`/`bash`/`sh -l` wrapper preserves it is unverified, and per the documentation quoted
above it would not change the outcome on macOS anyway.

### Open questions for the implementer (do not assume answers)

- Is setting `abnormal-command-exit-runtime` to `0` (or another value) on `-c` panes enough
  to suppress the banner, and does the quick-exit path then fall through to the
  `wait-after-command` "Process exited." message? Confirm against the pinned `Surface.zig`,
  and run the key through the same `ghostty_config_new`/`load_file`/`finalize` diagnostics
  check `SplitTreeTargetedSplitTests` uses — `TabRuntime.swift` warns that one unrecognised
  token has been observed to take the whole per-surface config down. The key *is* present in
  the pinned binary's string table.
- Even on the non-banner path, libghostty's documented semantic is "stay open until any
  keypress is received", whereas `docs/batty-cli-install.md` promises "until the pane is
  closed deliberately". Check what Batty does with the resulting close-surface request for a
  `-c` Pane and reconcile the docs with the behavior, whichever way it goes.
- Whether the "Process exited." marker (if that is where this lands) is acceptable for the
  agent use case, or whether the Pane should look like a finished command with no trailer at
  all. Either is fine as long as it is deliberate and documented.

### Acceptance

A successful short-lived `--command` leaves the Pane open showing its output without the
"Ghostty failed to launch the requested command" banner (or a documented, deliberate
alternative), covered by a Tart-VM UI test — the three existing `--command` tests already
produce the condition, so an assertion that the banner text is absent from (and the
command's output is present in) the new Pane after the sentinel lands is a natural fit.
