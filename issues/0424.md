## Description

#0354 added two tests for the `SIGKILL` escalation in `LMStudioDashboardPaneContent.reapAfterTerminate(_:bound:label:)` (`BattyKit/Sources/BattyKit/Runtime/LMStudioDashboardPaneContent.swift:722-740`):

- `LMStudioDashboardPaneContentTests.tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM` (`BattyKit/Tests/BattyKitTests/LMStudioDashboardPaneContentTests.swift:348-400`)
- `LMStudioDashboardWiringTests.tearDownAllPaneContentSynchronouslyForQuitKillsATermIgnoringSubprocess` (`BattyKit/Tests/BattyKitTests/LMStudioDashboardWiringTests.swift:213-262`)

Both spawn `/bin/sh -c "trap '' TERM; exec sleep 60"` (`LMStudioDashboardPaneContentTests.swift:286-291`, `LMStudioDashboardWiringTests.swift:225-230`) to stand in for an `lms` child that ignores `SIGTERM`. That child ignores `SIGTERM` only after `sh` has parsed and run `trap '' TERM`. A `SIGTERM` that arrives earlier kills it on the default disposition. If that happens, the `SIGKILL` branch never runs, and the test passes whether or not the escalation works.

### The race is real in general

The #0422 (Git Status) reviewer checked this with a standalone repro. It calls `Process.run()` and then `terminate()` with no delay in between, using the same shell command. The child died on `SIGTERM` 20 out of 20 times. Replacing the `SIGKILL` with a no-op left the Git Status tests green.

### The LM Studio tests don't currently hit it (verified 2026-09-23)

Unlike the repro, neither LM Studio test tears down right after `run()`. Both sleep 200 ms after setup first:

- `LMStudioDashboardPaneContentTests.swift:371`, before `content.tearDown()` at `:379`
- `LMStudioDashboardWiringTests.swift:248`, before `window.tearDownAllPaneContentSynchronouslyForQuit()` at `:255`

In practice that is long enough for `sh` to install the trap.

Mutation check, run in a clean worktree whose `LMStudioDashboardPaneContent.swift` and both test files are identical to `main`:

1. Baseline: `cd BattyKit && swift test --filter LMStudioDashboard` ran 23 tests in 2 suites, and all passed.
2. Mutation: replaced `kill(process.processIdentifier, SIGKILL)` at `LMStudioDashboardPaneContent.swift:732` with a no-op. Both tests failed:
   - `tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM` failed at `:398` and `:399` (`model.isRunning == false`, `runtime.isRunning == false`).
   - `tearDownAllPaneContentSynchronouslyForQuitKillsATermIgnoringSubprocess` failed at `LMStudioDashboardWiringTests.swift:259` and `:260`.
   - The four orphaned `sleep 60` children were then killed by hand.
3. Reverted. `git status` was clean.

So today the LM Studio tests **do** exercise the `SIGKILL` path. What's left is a latent weakness, not a vacuous test.

### What's still fragile

The trap being installed in time depends on a fixed wall-clock sleep, not on a signal from the child.

- **Heavy host load (see #0423) could stretch `sh` startup past 200 ms.** The quit-path wiring test would then pass vacuously: nothing between its `#expect(model.isRunning)` (`:252`) and the teardown shows that the trap is in place.
- **The PaneContent test is partly protected.** Its `#expect(model.isRunning)` immediately after `tearDown()` (`:391`) would *probably* catch a `SIGTERM` death. But `Process.isRunning` flips asynchronously, so that check isn't reliable either.
- **Copying the pattern without the sleep brings the race back.** #0422 shows this is exactly how the pattern gets reused.

## Expected behavior

Each `SIGTERM`-ignoring fixture proves that the trap is installed before the test sends `SIGTERM`. The tests then exercise the escalation deterministically, whatever the host load.

Proposed fix: a readiness handshake. Change the command to `trap '' TERM; echo ready; exec sleep 60`, attach a stdout `Pipe`, and block (with a timeout) until `ready` is read before tearing down. That can replace the 200 ms sleep, or come in addition to it where the test also needs the models poll. Put the helper in one place for both LM Studio tests and the #0422 Git Status tests, so they can't drift apart.

Caveat: a stdout `Pipe` won't work unchanged for the LM Studio fixtures. `spawnModelStream` (`LMStudioDashboardPaneContent.swift:381-425`) and `spawnRuntimeStream` replace both `standardOutput` and `standardError` on the process the injected factory returns, and they install their own `readabilityHandler`s. So the handshake needs a channel the content doesn't own. For example, the fixture writes `ready` to a temp file (`trap '' TERM; echo ready > "$READY"; exec sleep 60`), and the test polls that file with a timeout before tearing down. The #0422 Git Status fixtures can use whatever channel suits their own spawning code. After the fix, mutation-verify again: with the `SIGKILL` no-op'd, both tests must fail, and they must also fail with the 200 ms sleep removed.

## Resolution notes

> 🟢 Resolved 2026-09-23 — the LM Studio SIGTERM-ignoring teardown tests wait for a ready file the child writes after installing its trap, instead of a fixed 200 ms sleep, and every `sleep 60` test fixture now `exec`s so no `sleep` grandchild outlives its shell.

## Fix

- New shared `LMStudioSIGTERMIgnoringFixture` (`trap '' TERM; echo ready > <file>; exec sleep 60`, bounded `waitForReadyFile`, per-test temp dir). A temp file is used because the content owns the child's stdout/stderr. Used by `tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM`, `tearDownAllPaneContentSynchronouslyForQuitKillsATermIgnoringSubprocess`, and #0425's `registryDrainReapsATermIgnoringSubprocessLeftByAClosedPane`.
- All eight `sh -c "…; sleep 60"` fixtures in the LM Studio test files end in `exec sleep 60`, so SIGTERM reaches `sleep` directly instead of orphaning it for up to 60 s.
- Test-only; no production code changed. The Git Status tests keep their own stdout handshake (#0422), since their spawn path differs.
