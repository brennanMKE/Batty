# 0523 — Batty keeps no record of each Bell event's raw input and the text it showed the user, so the Bell Feed can't be tuned on real data

| | |
|---|---|
| **Status** | open |
| **Module** | BellFeed / Settings |
| **Platform** | macOS |
| **First seen** | 2026-10-18 |

## Description

Feature request. The user wants to improve the Bell Feed and needs a week of real-world data first. For every Bell event, that data is the **raw input** (what the terminal or CLI sent, plus its context) next to the **translated output** (the AI prompt and reply, and the text actually shown in the Bell Feed row and the System notification). Today nothing records that pair. Add an opt-in, local-only capture log that writes one JSON Lines record per Bell event to a file under Application Support. The user turns it on in 1.3.2 Prod, runs it for a week, and then we process the file.

**Release target: 1.3.2.** This is new work on `main`, cherry-picked to `release/1.3` with `git cherry-pick -x`. The user approved this as an exception to the AGENTS.md "Release branches" rule that keeps feature work off release branches. Record the release-branch commit in the Work log. It ships **without a feature flag**, because the user will run the Prod build. "Off by default" plus the toggle is what keeps it inert.

#0524 (rating Bell Feed entries) depends on this issue and writes to the same file.

## Current state (verified on main `7ed271e7`)

**Feed model.** `BellFeedEntry` (`BattyKit/Sources/BattyKit/Runtime/BellFeedStore.swift`) has `id`, `timestamp`, the window, session, pane, tab and surface ids, `message: String?` (raw OSC 9/777 body, or the CLI `notify` text formatted as `"title\nbody"` by `AppStateStore.formatNotifyMessage`; `nil` for a bare BEL), `summary: String?` (AI summary, filled in later), `seen`, `repeatCount` and `firstOccurrenceAt`. `BellFeedStore` is in-memory, capped at 200 entries, and never persisted.

**The three record paths** in `AppStateStore.swift` are `recordBellTick` (BEL, around line 1843), `recordDesktopNotification` (OSC 9/777, around line 1892) and `recordCLINotification` (CLI `notify`, around line 1962). Each builds a `BellFeedEntry` and then:
- calls `bellFeed.record(entry)` when the entry is seen at creation (the focused Tab), otherwise `bellFeed.recordOrCollapse(entry)`;
- on `.recorded`, calls `postNotification(for:at:trigger:)` and `scheduleSummarization(for:tabTitle:sessionTitle:)`;
- on `.collapsed(existing)`, calls only `recordCollapsedNotificationDecision`. That bumps `repeatCount` and refreshes `timestamp` on the **existing** entry, posts nothing, and starts no new summary. Note: the decision record built there carries the *incoming* entry's id (the one that was not stored), not the surviving entry's id. The capture record for a collapsed occurrence must join on the surviving entry's id, taken from `.collapsed(BellFeedEntry)`.

**Summarization.** `scheduleSummarization` (`AppStateStore.swift:2647`) returns early when `notificationSummarizer` is nil (no Foundation Models, i.e. before macOS 26) or when the "Summarize with AI" toggle is off (`SettingsPreference.resolvedSummarizeNotificationsWithAI`). Otherwise it starts a `Task` that calls `NotificationSummarizing.summarize(message:tabTitle:sessionTitle:)`, runs the result through `NotificationSummary.sanitize`, and calls `bellFeed.updateSummary(_:forEntryID:)`. Empty Tab and Session titles are passed as `nil`. The Tab title passed in is `location.tab.terminal.title`, **not** the override-aware label used in the notification title.

**Summarizer.** `FoundationModelsNotificationSummarizer` (`BattyKit/Sources/BattyKit/ProjectName/NotificationSummarizer.swift`) builds a `LanguageModelSession(instructions: Self.instructions)` and sends `Self.prompt(message:tabTitle:sessionTitle:)`. The prompt is lines of `Message: ...`, `Tab: ...`, `Session: ...` followed by "Summarize this notification in a short phrase." The summarizer already sanitizes internally and maps `NONE` to `nil`. So **the protocol never exposes the exact prompt or the raw model reply**, and a `nil` result can't be told apart from "model unavailable", "error", "cancelled" or "model said NONE". Capturing those needs a protocol change; see Expected behavior 3.

**What the user actually sees.**
- Bell Feed row (`BellFeedRow` in `Views/BellFeedView.swift`): path label `"<Session> › Pane N › <Tab label>"` from `pathLabel(for:)`, a `×N` badge when `repeatCount > 1`, a relative timestamp, and the body text `entry.summary ?? entry.message`. The body line is omitted when both are nil or empty. A bare BEL row with no summary shows no body text.
- System notification (`BellNotifier.post` in `Runtime/BellNotifier.swift`): title `"Batty — <Session> › Pane N › <Tab label>"`, body `entry.message` when non-empty, else `"Bell"`. **The AI summary never reaches the System notification.** It is posted once, before the summary exists, and is never re-posted.

**Post or suppress decision.** `BellDecisionHistory.swift` already models this. It has `BellTriggerKind` (`bel`, `oscNotification`, `cliNotification`) and a `BellDecisionRecord` with outcome `.submitted` or `.suppressed(reason)`. The reasons are `nilNotifier`, `sessionMuted`, `systemNotificationsDisabled`, `frontmostAndSeen` and `collapsedIntoUnread`. The record also holds the gate facts (`battyActive`, `entrySeenAtCreation`, `sessionMuted`, ...) and `foregroundPid` / `ttyName`. `AppStateStore.makeBellDecisionRecord` builds it. The history is an in-memory 1000-record ring buffer, exported only by hand through `BellDecisionExportRow` (Settings → Advanced → Diagnostics, `Views/SettingsView.swift`). Its `sessionTitle`, `tabLabel` and `message` are truncated to `BellDecisionFormat.maxFieldLength` (500). The capture must not inherit that truncation for `message`.

**Process and directory.** `TabRuntime.terminalNSView?.foregroundPid` (libghostty `tcgetpgrp`) works in practice; the #0298 export shows real pids. The vendored doc comment in `libghostty-spm/.../TerminalView+Process.swift` says it can be nil on some Ghostty builds, so treat it as optional. `ProcessInspector.identity(pid:)` (`Runtime/ProcessInspector.swift`) turns a pid into `name` and `executablePath`. The working directory is `TabRuntime.workingDirectory` (the observation-tracked mirror; read it, not `terminal.workingDirectory`).

**Screen text, the open part.** libghostty-spm already implements a per-row viewport read: `InMemoryTerminalSession.readViewportText()` (`BattyKit/.build/checkouts/libghostty-spm/Sources/GhosttyTerminal/InMemory/InMemoryTerminalSession.swift`, around line 113). It does one `ghostty_surface_read_text` per viewport row with `GHOSTTY_POINT_VIEWPORT` / `GHOSTTY_POINT_COORD_EXACT`, then calls `ghostty_surface_free_text`. Batty's Panes use `AppTerminalView`, which does **not** offer that method. Its `surface: TerminalSurface?` accessor is internal to the package, so BattyKit can't reach the surface from the view. BattyKit does `@_exported import GhosttyKit`, so the C functions themselves are callable if BattyKit can get a `ghostty_surface_t` for the Tab. `SurfaceRegistry` (`Runtime/SurfaceRegistry.swift`) stores `ghostty_surface_t` handles, but nothing in production registers into it today. libghostty-spm is the upstream package pinned by revision in `BattyKit/Package.swift`, not a fork. Possible routes for the implementer:
- a public route already in the pinned package that this survey missed;
- an upstream change exposing `readViewportText()` on `TerminalView`, followed by a revision bump;
- another way to get the Tab's `ghostty_surface_t`.

If none works for 1.3.2, ship without it. Write `screen: null` with a `screenUnavailableReason`, and leave a follow-up issue. **This is not a blocker for the rest of the issue.**

## Expected behavior

1. **Setting.** A "Capture Bell Feed data" toggle, off by default, in every build (Prod included), with a new `SettingsPreference` key in the existing `co.sstools.Batty.*` style. Recommended placement: Settings → Advanced → Diagnostics, next to the bell-decision export. Its help text says, in plain words, that:
   - the file stores notification text, Tab and Session titles, working directories and the last lines of the terminal screen;
   - terminal output can contain secrets such as tokens, passwords and keys;
   - the file stays on this Mac and is never sent anywhere.

   Two buttons sit next to it, "Reveal Capture File in Finder" and "Clear Capture". Reveal is disabled when no file exists. Clear deletes the current and rotated files and needs a confirmation built into the view; no `confirm()`-style dialog. Both work whether the toggle is on or off.
2. **One event record per Bell event**, written for every occurrence, including seen-at-creation and collapsed ones, through all three record paths. Footprint-warning entries (`BellFeedEntry.systemID`) are out of scope. Fields:
   - `schema` (integer, `1`), `type: "event"`, `recordID` (fresh UUID), `entryID` (the surviving `BellFeedEntry.id`, the join key), `capturedAt` (ISO 8601 UTC) and `appVersion` / build;
   - **Raw input:**
     - `trigger` (`BellTriggerKind` raw value);
     - `message` (the raw text, untruncated up to a generous cap such as 16 KB, with a `messageTruncated` flag);
     - `tabTitle` (`terminal.title`) and `tabLabel` (the override-aware label the UI shows);
     - `sessionTitle`;
     - `foregroundProcess` (`{pid, name, executablePath}` or null);
     - `workingDirectory`;
     - `screen` (the last ~20 non-trailing-blank lines of the originating Terminal Session's visible viewport, or null), plus `screenUnavailableReason` when null;
   - **Feed and notification outcome:**
     - `seenAtCreation`;
     - `collapse` (`{collapsed: Bool, repeatCount, firstOccurrenceAt}`);
     - `notification` (`{outcome: "submitted" | "suppressed", reason}`, reusing the `BellDecisionRecord` outcome and `SuppressionReason` raw values from the same decision record the store already builds; don't recompute the gates);
     - `notificationTitle` and `notificationBody` (the exact strings `BellNotifier.post` would use, or null when suppressed);
     - `feedRowPath` and `feedRowText` (the row's path label and body text at record time, i.e. `message` before any summary);
   - **Summary status at record time:** `summarization: "scheduled" | "skippedNoSummarizer" | "skippedDisabled" | "notApplicableCollapsed"`.
3. **Summary data, joined by `entryID`.** When summarization runs, the capture gets:
   - the exact `instructions` and `prompt` strings sent to the model;
   - the raw model reply, before any sanitizing;
   - a result status: `ok`, `none` (the model said NONE), `rejectedBySanitize`, `modelUnavailable`, `error` (with the error description), `cancelled` or `timedOut`;
   - `elapsedSeconds`;
   - the `sanitizedSummary`;
   - the `feedRowText` after the update (the text the row now shows).

   This needs `NotificationSummarizing` to return more than `String?`. For example, it can return a result value carrying the prompt, the raw reply and the status, or take an observer. Production behavior must stay the same: the same sanitize rules, the same `updateSummary` write, and nothing new on the main thread. Every existing test double conforming to the protocol gets updated.
4. **No record loss, no main-thread blocking.** The summary arrives asynchronously, possibly never (for example, the app quits first). The implementer chooses the shape:
   - an immediate `event` record plus a later `summary` record keyed by `entryID`; or
   - one record written when the summary completes or a timeout expires.

   Either way:
   - an event is never lost because its summary is pending or never comes;
   - a summary is never written without its event;
   - a `summary` record whose `entryID` matches no `event` record is impossible by construction;
   - records from concurrent bells never interleave mid-line.

   All encoding and file I/O runs off the main actor, through a serial writer (an actor or a serial queue). The main-actor bell path only snapshots values and enqueues. The screen read, if implemented, is the one synchronous piece; keep it bounded to the viewport rows. Capture off means no snapshot work at all: no screen read, no `ProcessInspector` call, no file touched.
5. **File location and size.** The file is `bell-feed-capture.jsonl` under `~/Library/Application Support/<variant dir>/`. Resolve the variant directory with `SessionNameCache.resolvedDirectoryName(bundleIdentifier:)`, the way `ProjectStore.canonicalFileURL` does, so the result is `Batty` for Prod and `Batty Beta` for Beta. Create the directory if missing. Cap the file at about 1000 records or a size cap (suggested 10 MB), whichever comes first. When it fills, rotate the current file to `bell-feed-capture.1.jsonl`, replacing any older one, so about two generations survive a busy week. The format is UTF-8 JSON Lines with one object per line, `\n`-terminated, and keys sorted so diffs are stable. A write failure is logged with the file-scoped `Logger` and never surfaces as UI or crashes.
6. **Local only.** No network, no upload, no telemetry, no CLI or XPC exposure. The file is only ever written by Batty and read by the user.
7. **Docs.** Create `docs/bell-feed-capture.md` describing:
   - every record type and field, with types and nullability;
   - the `schema` versioning rule (bump on any breaking change);
   - the join rules (`entryID` across `event`, `summary` and #0524's `rating` records);
   - the rotation behavior;
   - a short example `jq` query (for example, raw message vs. final row text).

   Add it to `docs/README.md` and add a line to the `Bell Feed` section of `Concepts.md`.

## Acceptance criteria

- [ ] With the toggle off (the default), a BEL, an OSC 9 and a CLI `notify` produce no file and no capture work.
- [ ] With it on, each of the three triggers appends exactly one `event` record with every field above, and a collapsed repeat appends its own `event` record carrying the surviving `entryID` and the updated `repeatCount`.
- [ ] `notification.outcome` / `reason` match the `BellDecisionRecord` the store records for the same occurrence, including `collapsedIntoUnread`.
- [ ] `notificationBody` is the raw message or `"Bell"`, and `feedRowText` at record time is `message`, matching what `BellNotifier.post` and `BellFeedRow` actually render.
- [ ] When summarization runs, the capture contains the exact prompt and instructions, the raw reply, the status, the sanitized summary and the post-update row text, joinable to the event by `entryID`. Skipped summaries are recorded with the right reason.
- [ ] Screen text is captured for a live Pane, or the issue records why it couldn't be and a follow-up issue is filed.
- [ ] The file lands in the variant-correct Application Support directory and rotates at the cap.
- [ ] Reveal and Clear work.
- [ ] `docs/bell-feed-capture.md` exists and matches the code.
- [ ] Release archive check passes (`./build.sh release archive ...`), because this ships in a release.

## Tests

Unit tests in `BattyKit/Tests/BattyKitTests/` (`./build.sh unit`):
- **Encoding:** every record type round-trips through `JSONDecoder`, carries `schema: 1`, and encodes as one line.
- **Store integration**, using the existing `AppStateStore` bell test setups (see `AppStateStoreBellCollapseTests`, `AppStateStoreBellDecisionHistoryTests`, `BellNotificationSummaryTests`):
  - each trigger produces the expected event record;
  - collapse joins on the surviving id;
  - toggle off writes nothing;
  - a stub summarizer's prompt, raw reply and status reach the capture;
  - every skip reason is recorded.
- **Writer:**
  - appends in order under concurrent enqueues with no interleaved lines;
  - rotates at the record cap and at the size cap;
  - Clear removes both generations;
  - a write into an unwritable directory logs and does not throw to the caller.

  Use a temporary directory injected into the writer, never the real Application Support path.
- **Async rules (binding, AGENTS.md "Asynchronous tests").** No sleeps, polling or timing assertions. Await the writer's own completion signal (for example, an awaitable `flush()` or the returned `Task`) and the existing `summarizationTaskForTesting(entryID:)` handle. Bound every await with the shared `ResumeOnce` guard (`docs/async-test-seams.md`).
- **UserDefaults isolation:** tests that flip the toggle use a per-test suite, per `docs/isolate-userdefaults-in-tests.md`, never `UserDefaults.standard`.

## Notes

- `BellDecisionHistory` stays as it is: in-memory, always on, manual export. The capture reuses its outcome and reason vocabulary, not its storage or its 500-character truncation.
- Prefer one snapshot point per occurrence, right after the decision record is built, so `notification`, `collapse` and the feed fields come from the same moment.
- Don't put capture code on the terminal input path or in any SwiftUI `body`. The bell callbacks already run on the main actor outside view updates.
- Open question, for the implementer to decide and record: whether a capture record should also note `battyActive` and the key-window facts. They are cheap and already in `BellDecisionRecord`, so including them is recommended.
