## Description

First step of the XPC track under umbrella #0265: the shared contract the CLI, the broker agent, and the app will all link — the equivalents of the experiment's `XPCProtocols.swift`, `Messages.swift`, and `ServiceNames.swift`. Pure types plus unit tests; no broker, no listener, no registration, no new verbs. Fully unit-testable with no XPC involved.

**Gate:** this child starts only when the XPC track is green-lit — per RemoteControl `FINDINGS.md`, "add the XPC layer when the first command genuinely needs a reply. Do not build the broker speculatively." The candidate first verb is `batty status` (#0271). See the umbrella's child index for the gating order.

## Resolution notes

> 🟢 Resolved 2026-07-24 — the shared XPC contract lands in a new dependency-free `BattyXPCCore` target: `@objc` protocols carrying JSON-in-`Data`, derived `ServiceNames`, and the exit-code vocabulary.

The most valuable output was not planned: this package's `.defaultIsolation(MainActor.self)` makes every XPC-facing declaration implicitly main-actor-isolated, which the RemoteControl reference could not have predicted. See Gotchas — it binds #0270–#0274.

## Root cause

Starting state, not a defect. The XPC track needed a shared contract the CLI, the broker agent, and the app could all link before any of them could be built.

## Fix

New target **`BattyXPCCore`** (Foundation only, no product dependencies), chosen over extending `BattyCLICore` because that target is scoped to the `batty://` URL-scheme contract and the broker would otherwise link a URL builder it will never call. `BattyKit` depends on and re-exports it, mirroring the existing `BattyCLICoreReexport.swift` pattern; the `batty` executable is deliberately **not** yet wired to it, since no CLI verb uses it until #0271.

Contents: `@objc` protocols whose structured payloads cross as JSON-encoded `Data` (the approach RemoteControl validated, not the never-exercised Swift-native `XPCListener`/`XPCSession` API); reply blocks declared `@escaping @Sendable` on every protocol the project controls; `ServiceNames` deriving the launchd `Label` and plist filename from a single constant; and the exit-code vocabulary as `Int32` constants (2 broker unreachable, 3 app unavailable, 4 request failed, 5 app terminated the session — 0 and 1 already come from `ArgumentParser.ExitCode`).

`CLIClientProtocol` and `startSession`/`endSession` were deliberately omitted: #0265 defers streaming and long-lived sessions with no child filed by design, and declaring the surface would presuppose unscheduled work. Adding a third `@objc` protocol later is purely additive against `NSXPCInterface`.

## Review

Reviewed by `claude-opus-5`, two rounds.

Round 1 upheld every design call and requested one change: the `nonisolated` discipline — the branch's headline invariant — had no regression guard, because every `@Test` body is itself MainActor-isolated and would keep compiling and passing if the annotations were stripped. ## Gotchas

- **`.defaultIsolation(MainActor.self)` makes XPC-facing declarations implicitly main-actor-isolated, and there is no equivalent in the RemoteControl reference.** `BridgeKit` has no such setting, so nothing in `docs/xpc/` predicts this. Without annotation you get `call to main actor-isolated ... in a synchronous nonisolated context` and `main-actor-isolated conformance ... cannot be used in nonisolated context`. **Every XPC protocol requirement must be `nonisolated func`, and every `Codable` payload must be `nonisolated` at the type level** — annotating only the `init` does *not* fix the isolated-conformance error (verified both ways). This is the same crash class as the `@Sendable` reply-block trap, one layer up, and it binds #0270–#0274.
- **A `@MainActor` class cannot conform to these protocols at all** — `conformance ... crosses into main actor-isolated code and can cause data races [#ConformanceIsolation]`. #0271's app-side exported object must therefore be a `nonisolated final class` that hops inward (`Task { @MainActor … }` / `MainActor.assumeIsolated`), not a `@MainActor` class. Architecturally correct — XPC delivers on its own queues — but it is a design constraint, not a stylistic choice.
- **The `otool -L` check on this branch is vacuous.** `batty` is not yet linked to `BattyXPCCore`, so zero `@rpath` entries is the unchanged baseline and proves nothing about the new target. `BattyXPCCore`'s cleanliness is verifiable structurally from `Package.swift` instead. **#0271 is the child that first links it and must re-run the check for real** rather than inheriting a false sense that this branch cleared it.
- **Three protocol requirements remain unguarded** — `BrokerProtocol.registerAppEndpoint`, `BrokerProtocol.appEndpoint`, and `AppServiceProtocol.ping` still compile with `nonisolated` removed. Closing them is ~3 lines inside the existing `callOffActor` helpers; #0270/#0271 add the real call sites for exactly those three, which is the natural place for the coverage to arrive. Separately, `@Sendable` on reply blocks is **not** compile-guardable at all — `@Sendable` closures are a subtype of non-`Sendable` ones, so no call-site formulation catches its removal.
- **`ServiceNames.broker` is invariant across Prod and Beta.** The literal `co.sstools.Batty.broker` does not vary with `PRODUCT_BUNDLE_IDENTIFIER` (`co.sstools.Batty` vs `co.sstools.Batty.beta`), so both variants would ship a LaunchAgent with the same `Label`. #0265 trap 3 warns that multiple copies on disk confuse launchd, with recovery costing `sfltool resetbtm` and a reboot. **#0270 owns the plist and must decide this deliberately** — suffix per variant, or do not install the agent from Beta at all.
- The reference doc's fifth constant, `agentBundleProgram`, is absent — correct for this scope, but #0270 should add it to `ServiceNames` rather than inlining a path literal.

## Scope

1. **`@objc` protocols whose structured payloads cross as JSON-encoded `Data`.** This is the *validated* approach (RemoteControl #0002), not the Swift-native `XPCListener`/`XPCSession` API (never exercised in the experiment). It "keeps `NSSecureCoding` class allowlisting entirely out of the picture" and "cost nothing and saved a category of problem — worth repeating in Batty." The payloads themselves are ordinary `Codable, Sendable` structs — testable without XPC, printable when something breaks — just carried inside `Data`.
2. **Reply blocks declared `@escaping @Sendable` from day one.** This is the corollary that saved the experiment everywhere the compiler could help: declaring reply blocks in the project's own `@objc` protocols `@Sendable` makes the compiler enforce it at every call site the project controls, leaving only the Foundation-supplied handlers exposed (those are #0271/#0272's problem; the full trap is copied there).
3. **A `ServiceNames` single source of truth.** The launchd `Label` and plist filename must be *derived* from one constant. **Four strings must be identical** — plist filename, plist `Label`, `MachServices` key, and the name the code connects to — and any mismatch makes launchd *silently* decline to reserve the name, surfacing much later as an unexplained "connection invalid." Per the experiment: "the four-strings-must-match problem is the plan's most expensive gotcha and deriving them halves the places it can go wrong."
4. **The exit-code vocabulary**, defined as shared constants: `2` broker unreachable, `3` app unavailable, `4` request failed, `5` app terminated the session. "It is what makes the CLI scriptable, and it costs nothing to define up front." (`0` success and `1` CLI-side input failure already exist in the shipped CLI.)
5. **Logging:** any file here that logs joins the shared `Logging.subsystem` (`BattyKit/Sources/BattyKit/Logging.swift` pattern per `CLAUDE.md`) — the experiment found a shared subsystem across app, agent, and CLI "was the only practical way to watch a handoff. Wire it in from the first commit, not when something breaks."

## The placement constraint (the expensive trap — do not skip)

**These types must land in `BattyCLICore` or a sibling target with the same dependency-free discipline — never in full `BattyKit`.** This is the #0252 link-dependency hazard, copied here in full because a child that omits it will rediscover it:

> The CLI target depending on the full `BattyKit` *library* transitively links Sparkle (plus libghostty, SlidingTabs, Textual) via `@rpath`; the embedded binary at `Contents/Resources/bin/batty` cannot reach `Contents/Frameworks/` and crashes at launch with `Library not loaded: @rpath/Sparkle.framework/...` — while appearing to work under `swift run`. The shipped fix was the dependency-free `BattyCLICore` target (Foundation only, no product dependencies); the `batty` executable links only that.

The broker agent will have the same constraint (it is a bare executable outside `Contents/Frameworks/` reach). If a new sibling target is created instead of extending `BattyCLICore`, it must carry the same "Foundation only, no product dependencies" comment discipline `Package.swift` already documents for `BattyCLICore`.

Distinct second hazard, also relevant when wiring tests: **the build-graph hazard (#0249)** — never wire an executable *product* from the package as an Xcode package-product dependency of the app target; it pulls the executable into the `Batty (Prod)` scheme's build graph and breaks `BattyKitTests`' `Bundle.module` resolution (`unable to find bundle named BattyKit_BattyKit`). `swift test` does not reproduce it; only `scripts/build.sh unit` catches it. This child adds no executable, but any `Package.swift` edit must be checked against both hazards.

## Out of scope

- The broker executable target, plist, embedding, signing, registration (#0270).
- App-side listener, endpoint handoff, any live connection, any new CLI verb (#0271).
- Lifecycle handlers and the `@Sendable` audit of Foundation-supplied closures (#0272) — this child only sets the `@Sendable` discipline on the protocols it declares.
