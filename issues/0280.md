# 0280 — Scripted builds follow whichever variant `Active.xcconfig` last selected, so `run-ui-tests.sh` silently tests a Prod host and `build.sh` silently builds Beta while reporting Prod

| | |
|---|---|
| **Status** | open |
| **Module** | Build |
| **Platform** | macOS |
| **First seen** | 2026-07-26 |

## Description

Both `scripts/run-ui-tests.sh` and `scripts/build.sh` inherit the `Active.xcconfig` one-invocation lag that #0279 fixed only for `scripts/build-beta.sh`: the scheme name passed to `xcodebuild` does not decide which variant gets built — whatever `Configuration/Active.xcconfig` says **on entry** does. The direction is symmetric, and both scripts have now been caught by it:

- `scripts/run-ui-tests.sh` pins `SCHEME="Batty (Beta)"` (line 39) — a load-bearing choice, since `UITestDriver.swift` (line 14) documents that UI tests run against the Beta build with no `#if DEBUG` gate. Run the script while `Active.xcconfig` points at Prod and it builds a **Prod-configured** host while believing it built Beta, then silently skips its own host-app re-signing step because the `Batty Beta.app` path it guards on doesn't exist.
- `scripts/build.sh` — the documented pre-commit gate — defaults to the Prod scheme. Run it while `Active.xcconfig` points at Beta and it builds the **Beta product while reporting Prod** (measured; see the `build.sh` consequences section below).

This is a pre-existing build-tooling defect that the #0279 work surfaced; it is **not** a child of the #0265 umbrella. The `scripts/build.sh` half was originally filed separately as [#0296](0296.md) (2026-08-03) and folded in here with user approval — its evidence is merged below.

## The mechanism (verified during #0279's review)

`scripts/set-environment.sh` writes `Configuration/Active.xcconfig`, which `Configuration/App.xcconfig` pulls in via `#include? "Active.xcconfig"` (line 21 on `main`). The Xcode scheme's pre-action runs `set-environment.sh` — but pre-actions execute **after** `xcodebuild` has already resolved build settings for that invocation, so the pre-action's write only takes effect for the *next* invocation. #0279's reviewer captured this empirically in a `-scheme 'Batty (Prod)'` build log: `PRODUCT_NAME="Batty Beta"` exported at log line 1169, and `set-environment.sh: Active.xcconfig → Prod.xcconfig` only at line 1692 (recorded in #0279's Review section, blocking finding 2). The direction is symmetric: a `-scheme 'Batty (Beta)'` invocation with `Active.xcconfig` on Prod builds the Prod configuration.

`Active.xcconfig` drifts as a matter of routine — at filing time it sits at `#include "Beta.xcconfig"` on `main`, left there by the #0279 work. Any Xcode-GUI build of the Prod scheme, or `scripts/build.sh` (the pre-commit gate), flips it back to Prod, arming this defect for the next `run-ui-tests.sh` run.

## Consequences for `run-ui-tests.sh` specifically

With `Active.xcconfig` on Prod (post-#0279 configuration, where Beta's product is `Batty Beta.app`):

1. **Wrong variant built and tested.** `build-for-testing` resolves Prod settings: product `Batty.app`, bundle identifier `co.sstools.Batty`, Sparkle's real `SUFeedURL`. The UI suite then exercises a host that shares the running daily-driver Prod app's bundle identifier — and therefore its `UserDefaults`, broker Mach service name, and launchd label — exactly the interference #0277/#0279 exist to prevent.
2. **The host-app re-sign is silently skipped.** `HOST_APP="$PRODUCTS_DIR/Batty Beta.app"` (line 65) is guarded by `if [[ -d "$HOST_APP" ]]` (line 77). When the build produced `Batty.app` instead, the guard skips the `codesign` with no message. Re-signing the runner + host app is what this script exists to do, per `CLAUDE.md`'s explanation of the Gatekeeper translocation problem — the runner re-sign (unconditional) still happens, but the host-app half of the documented repair never runs, and nothing says so.

## Consequences for `scripts/build.sh` specifically (merged from #0296)

The opposite direction, with `Active.xcconfig` on Beta:

1. **The pre-commit gate verifies the wrong artifact.** `scripts/build.sh` prints `Batty (Prod)` while producing `Batty Beta.app`. Measured 2026-08-03 on this checkout: with `Active.xcconfig` left on Beta, `xcodebuild -project Batty.xcodeproj -scheme "Batty (Prod)" -showBuildSettings` reported `PRODUCT_NAME = Batty Beta` and `PRODUCT_BUNDLE_IDENTIFIER = co.sstools.Batty.beta` — from the *Prod* scheme. After `scripts/set-environment.sh Prod`, the same invocation resolved `Batty` / `co.sstools.Batty`. Every "`scripts/build.sh` — BUILD SUCCEEDED (Prod scheme)" line produced in that state establishes only that the Beta app builds; unit-test results are unaffected (`BattyKitTests` exercises the Swift package, which doesn't depend on the app bundle id), but "the Prod app builds" was not actually checked.
2. **`scripts/build.sh` honours a `SCHEME` env override with no `Active.xcconfig` guard.** `scripts/build.sh:17` reads `SCHEME="${SCHEME:-Batty (Prod)}"`, so `SCHEME="Batty (Beta)" scripts/build.sh` builds Beta *without* going through `build-beta.sh` — the Beta scheme's pre-action then leaves `Active.xcconfig` switched indefinitely, and every subsequent `scripts/build.sh` "Prod" build is a Beta build wearing a Prod label. This is exactly how the state arose during the #0285 umbrella work: agent sessions built Beta via the `SCHEME` override repeatedly, and **the condition recurred twice in one day (2026-08-03)** during cleanup.
3. **Secondary symptom: dirty `project.pbxproj`.** Prod and Beta share one target, so whichever scheme resolved last caches its product name into the tracked `Batty.xcodeproj/project.pbxproj` (the `Batty.app` product file reference flips to `Batty Beta.app`, plus a file-reference reorder). It must be discarded, never committed — committing it just makes the next Prod build flip it back.

One concrete mislabel to record: #0295's review reported inspecting "the freshly built `Debug/Batty.app`" for string-catalog entries (`issues/0295.md:87`); that was almost certainly `Batty Beta.app`. The conclusion still holds — both variants embed the same catalog — but the artifact named was wrong.

Diagnostic worth keeping:

```bash
xcodebuild -project Batty.xcodeproj -scheme "Batty (Prod)" -showBuildSettings | grep PRODUCT_NAME
```

**Interim rule now documented in `CLAUDE.md`** (commit `798677a`): build Beta only via `scripts/build-beta.sh`, never `SCHEME="Batty (Beta)" scripts/build.sh`; a dirty `project.pbxproj` after a Beta build is expected residue to discard. That is an operational mitigation, not a fix — this issue remains the ticket for making the scripts themselves safe.

## The `HOST_APP` line has been dead code since the script was born

Verified with `git show 51acf65:scripts/run-ui-tests.sh`: the line `HOST_APP="$PRODUCTS_DIR/Batty Beta.app"` and its `if [[ -d … ]]` guard are present verbatim in commit `51acf65` (2026-05-20), the commit that created the script. Before #0279 renamed the Beta product, **both** variants produced `Batty.app`, so `Batty Beta.app` never existed in the products directory and the host-app re-sign branch has never once executed. Two implications:

- The UI suite has run green for months without the host-app re-sign ever firing (the host is built unsigned via `CODE_SIGNING_ALLOWED=NO`; only the mis-signed Apple-template runner triggers the Gatekeeper translocation). Whether the host-app re-sign is actually *required* is therefore unproven in both directions.
- #0279 makes the branch fire for the first time. Its first real execution — `codesign --force --deep --sign -` on a `Batty Beta.app` host — is unproven. #0279's Gotchas records this explicitly: treat the first run as unproven.

## Steps to reproduce

For `run-ui-tests.sh` — not executed for this filing (a run locks the machine ~10 min); reasoned from the mechanism #0279's review verified empirically in the opposite direction:

1. `scripts/set-environment.sh Prod` (or build the Prod scheme once in Xcode).
2. `scripts/run-ui-tests.sh BattyUITests/TabRenameTests` (any subset).
3. Inspect the `build-for-testing` log: settings resolve to Prod (`PRODUCT_NAME = Batty`, `co.sstools.Batty`) despite `-scheme "Batty (Beta)"`.
4. Observe the products directory contains `Batty.app`, not `Batty Beta.app`, and the host-app `codesign` at line 78 is skipped without any output.

For `build.sh` — reproduced on this checkout 2026-08-03 (cheap; no build needed):

1. `scripts/set-environment.sh Beta` (or equivalently, run `SCHEME="Batty (Beta)" scripts/build.sh` and let the scheme pre-action leave `Active.xcconfig` at Beta).
2. `xcodebuild -project Batty.xcodeproj -scheme "Batty (Prod)" -showBuildSettings | grep -E "PRODUCT_NAME|PRODUCT_BUNDLE_IDENTIFIER"`
3. Observe `PRODUCT_NAME = Batty Beta` and `PRODUCT_BUNDLE_IDENTIFIER = co.sstools.Batty.beta` — from the *Prod* scheme.
4. `scripts/set-environment.sh Prod` restores `PRODUCT_NAME = Batty` / `co.sstools.Batty`.

## Expected behavior

A scripted build produces the variant its scheme names, regardless of what `Active.xcconfig` said beforehand — or fails loudly if it cannot:

- `scripts/run-ui-tests.sh` builds and tests a genuinely Beta-configured host (`Batty Beta.app`, `co.sstools.Batty.beta`, empty Sparkle feed). The host-app re-sign either runs or the script says why it didn't.
- `scripts/build.sh` verifies a genuinely Prod-configured product (or the variant of whatever scheme it was asked for), so the pre-commit gate actually checks the artifact it claims to.

## Actual behavior

The variant is decided by leftover `Active.xcconfig` state, silently, in both directions. On Prod, `run-ui-tests.sh` builds and tests a Prod-configured `Batty.app` while claiming Beta, and the host-app re-sign is silently skipped by the `-d` guard. On Beta, `build.sh` builds `Batty Beta.app` while printing `Batty (Prod)` — the pre-commit gate verifies the wrong artifact and says nothing.

## Notes

### Fix angles — two, and they are not the same

#0279's fix for `build-beta.sh` is the obvious template: snapshot `Configuration/Active.xcconfig` on entry (including the file-absent case — `#include?` tolerates absence), restore it in a `trap … EXIT` that preserves the triggering exit status. But that template solves *leaving the neighbor's state intact*; `run-ui-tests.sh` has the opposite problem — it must **guarantee the right value is in place before `xcodebuild` resolves settings**, not merely put back what it found.

- **Set-then-verify (recommended core).** Call `scripts/set-environment.sh Beta` at the top of the script, before the first `xcodebuild`. Then, after `build-for-testing`, assert the expectation instead of guarding on it: if `"$PRODUCTS_DIR/Batty Beta.app"` does not exist, fail loudly — the current silent `if [[ -d … ]]` becomes a hard check. This turns both failure modes (wrong variant, skipped re-sign) into immediate errors.
- **Snapshot/restore (recommended addition, from the `build-beta.sh` template).** On its own it does not fix this script — but combined with set-then-verify it stops `run-ui-tests.sh` from becoming the *next* script that leaves `Active.xcconfig` pointed at Beta and breaks the following Prod build, which is precisely the failure #0279's review round 1 caught in `build-beta.sh`.

Recommended: both — set Beta on entry, restore the entry snapshot on exit, assert `Batty Beta.app` exists after the build.

**One fix addresses both scripts.** The same two ingredients cover `scripts/build.sh`: snapshot/restore `Active.xcconfig` the way `scripts/build-beta.sh` already does, and/or assert that the resolved `PRODUCT_NAME` / `PRODUCT_BUNDLE_IDENTIFIER` match the requested scheme and fail loudly on mismatch (the cheap check that would have caught the 2026-08-03 incident). No option is pre-selected here — `scripts/` is a restricted area per `CLAUDE.md` and any fix needs the user's explicit go-ahead. Other angles recorded in #0296 before the fold: refuse to run when `SCHEME` is overridden, or give Beta its own target so the shared-target product-name caching in `project.pbxproj` stops entirely.

### The broader option — worth raising, not deciding here

The root disease is that scripted builds depend on mutable repo state (`Active.xcconfig`) that the scheme name doesn't control. A broader fix makes the variant explicit at the `xcodebuild` invocation itself — e.g. passing the variant's settings directly or via `-xcconfig` — so `Active.xcconfig`'s state stops mattering for *any* scripted build (`build.sh`, `build-beta.sh`, `run-ui-tests.sh` alike). That would retire the whole class of lag bugs, at the cost of a second source of truth that can drift from the xcconfig files, and it touches more of the restricted `scripts/` area. Raise with the user; the narrow per-script guard is sufficient for this ticket.

### Restricted area — implementation needs explicit go-ahead

`scripts/` is a restricted area per `CLAUDE.md` ("Authored deliberately; small mistakes break notarization"). #0279's `build-beta.sh` was authorized because the user explicitly requested that script; **no such authorization exists for modifying `run-ui-tests.sh`**. Do not implement this issue without the user's explicit confirmation first.

### Signing hazard — keep every build unsigned

The user's Developer ID certificate was revoked once by repeated *signed* local builds against this project's `CODE_SIGN_STYLE = Automatic` (recorded in issues/0265.md; see also `build-beta.sh`'s header). `run-ui-tests.sh` already passes `CODE_SIGN_IDENTITY="-" CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=NO` on both invocations — any fix must preserve that, and any verification of this issue must avoid unnecessary signed builds entirely.

### Verification expectations

- **The decisive check:** with `Active.xcconfig` deliberately set to Prod, run the fixed script — it must either produce and re-sign a genuinely Beta-configured host (`Batty Beta.app`, `CFBundleIdentifier = co.sstools.Batty.beta`, empty `SUFeedURL`, verified by inspecting the built bundle, not by reading the script) or fail loudly. Silent production of a Prod `Batty.app` with the re-sign skipped is the bug.
- **Neighbor check:** after the script exits (success, failure, and Ctrl-C), `Active.xcconfig` matches its entry state — the same four-path trap verification #0279's reviewer ran for `build-beta.sh`.
- A cheap partial pass (single test class) can prove the build/re-sign path without the full suite. A full-suite run takes ~10 minutes and locks the machine — run it on the Mac mini per `CLAUDE.md`, and note the environmental UI-test failure modes recorded in project memory before blaming the diff.
- Real end-to-end confirmation (full suite green against the renamed `Batty Beta.app` host, first-ever execution of the host-app re-sign) needs the user to schedule it; the implementer should state plainly what was and wasn't run.
