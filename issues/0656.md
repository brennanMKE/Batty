## Description

The File menu's way into Projects leads to a picker, not to the place where Projects are managed. To edit a Project from the File menu, the user goes to File ▸ Open Project ▸ **Choose Project…**, which presents the keyboard-driven Open Project picker. The picker's only edit path is Cmd-E on a card. The Project Editor, where Projects are listed, edited, reordered and deleted, is reached from a different menu: the top-level **Projects ▸ Projects…** item. So opening and editing Projects is split across two menus, and the File menu item that sounds like "manage Projects" only opens one.

User's words: "I feel like the File menu items is not right. When I want to edit a project I have to instead use Choose Project. Maybe that should just be Projects."

## Root cause

Feature work. File ▸ Open Project ended in Choose Project… (the keyboard picker), and the Project Editor lived only under the top-level Projects ▸ Projects…, so the two menus overlapped and the editor was hard to find.

## Fix

Followed the plan. `ProjectFileMenuModel.Item.chooseProject` became `.projects`; its menu item opens the Project Editor, selecting the default target Window's Session's Project via the new pure `ProjectFileMenuModel.editorSelection(projectID:projects:editorIsOpen:)` (nil when the editor is already open or the Project is gone). The top-level Projects menu keeps only the Save/Update items. `.disabled(keyWindow == nil)` moved from the submenu to the per-Project items, so Projects… and New Project… work with no content window. The now-unused picker toggle path (`.battyToggleProjectPicker`, `ProjectPickerToggle`, the `onReceive`, `toggleProjectPicker(in:)`) and its unit tests are deleted. Help and docs updated. No divergence from the plan.

## Recommended direction (the plan may refine it)

1. In File ▸ Open Project, replace **Choose Project…** with **Projects…**, which opens the Project Editor. When the key content window's current Session was opened from a Project (`projectID` non-nil and that Project still exists), the editor opens with that Project selected (`show(store:selecting:)`). Otherwise it opens with nothing selected, like Projects ▸ Projects… today. From Settings, Help or the Project Editor, use the default target window's selected Session.
2. Keep the per-Project items and **New Project…** in the submenu, in the same order (Projects, divider, Projects…, New Project…).
3. The keyboard picker loses its menu-bar entry. That is acceptable because the Sidebar footer button and the Command Palette still present it, and Open Quickly and the per-Project items open Projects by name. The plan should confirm this and say whether "Open Project…" in the Command Palette stays as the picker's keyboard path. Don't add a new shortcut unless the plan argues for one.
4. Remove the duplicate: either drop **Projects…** from the top-level Projects menu, leaving only the Save/Update items, or keep it with the same selection behavior. Two items with the same title in two menus doing slightly different things is the confusion this issue is about. Recommendation: keep one **Projects…**, in File ▸ Open Project, and leave the Projects menu for saving the current Session. The plan decides and records why.
5. Rename `ProjectFileMenuModel.Item.chooseProject` to match (e.g. `.projects`) and update its unit tests.

## Plan

Written 2026-11-18 against `issue/0656` at `3dd5f253`. Every premise under "Current state" checks out in the code: the items and order in `ProjectFileMenuModel.make`, the `.chooseProject` action in `BattyCommands.projectMenuItem` (`:126-138`), the top-level `CommandMenu("Projects")` (`:196-204`), `ProjectEditorWindowController.show(store:selecting:newDraft:startNewProject:)` (`:122`), `SessionRuntime.projectID` (`:75`), and the existing-Project check in `SaveSessionAsProject.editProject` (`:182-192`). Two things the issue did not mention:

- **Choose Project… is the only poster of `.battyToggleProjectPicker`.** The Command Palette (#0483) and the Sidebar footer present through `AppStateStore.presentProjectPicker(in:)`. Removing the item leaves the notification, `ProjectPickerToggle`, the `onReceive` in `SessionDetailView.swift:62-66` and `AppStateStore.toggleProjectPicker(in:)` with no caller. This plan deletes them.
- **The Open Project submenu is `.disabled(keyWindow == nil)`** (`BattyCommands.swift:193`). With no content window left, the whole submenu is disabled. Today the top-level Projects ▸ Projects… still opens the editor in that state, and `ProjectsEditorTests.testCommandNInProjectsWindowWithNoContentWindowStartsNewProject` relies on it (it reopens the editor after closing the last content window). Removing the top-level item must not lose that.

### Decisions

1. **One Projects… item, in File ▸ Open Project. The top-level Projects menu keeps only the Save/Update items.** The confusion the user reported comes from having two menus. Keeping two items with the same title invites the same confusion. The Projects menu becomes "save this Session as a Project", and the File submenu becomes "open or manage Projects". It keeps its name, because "Save Session as Project…" still needs a home and moving it would be a separate change.
2. **Selection rule for Projects…:** take the Session from `store.defaultTargetWindow()?.selectedSession`, not `actionWindow`, which is nil while Settings, Help or the editor is key. The editor opens with that Session's Project selected when `projectID` is non-nil and the Project is still in `projectStore.projects`. Otherwise it opens with nothing selected (browse state). **When the editor is already open**, Projects… only brings it forward and passes no selection. Reason: a selection request on a dirty editor raises the unsaved-changes prompt, and a "show me the Projects window" item should never interrupt an edit in progress. The Sidebar's Edit Project… is the explicit "edit this one" path and still navigates. This also keeps `testReopeningProjectsKeepsTheCurrentDraft` true.
3. **Enablement:** drop `.disabled(keyWindow == nil)` from the `Menu`. Put it on each per-Project Toggle instead, since those need a content window to open into. Projects… and New Project… are always enabled, because the editor works with no content window. This preserves the no-content-window path that the top-level item used to provide. No new chord, and no new `ShortcutAction`.
4. **The keyboard picker keeps two entry points: the Sidebar footer button and the Command Palette's "Open Project…".** The palette row is its keyboard path, and it stays. Open Quickly and the per-Project items still open Projects by name. Cmd-E edit in the picker is unchanged. No new shortcut: the picker is one of four ways to open a Project, and none of them is lost.
5. **Rename** `ProjectFileMenuModel.Item.chooseProject` to `.projects` (id `"projects"`).
6. **Delete the dead toggle path** (notification, `ProjectPickerToggle`, `onReceive`, `toggleProjectPicker(in:)`, and their unit tests), so no code or docs describe a route that nothing takes.

No open questions block the work.
