## Description

Under heavy host load, a full `./build.sh unit` run fails most of `ProjectXPCTests` together, each with `no XPC reply for projectOpen` (`BattyKit/Tests/BattyKitTests/ProjectXPCTests.swift:76`). `GitStatusPaneContentTests` failed in the same runs. Both suites pass when run alone. Issue branches that never touch Projects or git status fail the per-commit unit tier because of this.

## Resolution notes

> 🟢 Resolved 2026-11-18 — the XPC, git-status and test-clock waits now fail only after two quiet intervals with a drained main queue, and name the step they reached, so a backlogged main queue under load no longer looks like a lost reply.

## Review

Two rounds. Round 1 bounced for a misplaced `ScanGate` doc comment, `XPCRequestTrace.describe` naming `openProjectForXPC` for every verb, and a trailing blank line. Round 2 fixed exactly those three; approved.

## Root cause

Confirmed test-side, no production defect. `ProjectXPCTests.perform`, `GitStatusPaneContentTests`' `ScanGate.waitForScanStarted` / `ScanHandledSignal.wait` and `TestClock.waitForSleepers` each raced their event against a one-shot `asyncAfter(TestBounds.hangGuard)`. Every step they wait on is a main-queue job, so a main queue that is a minute deep under load looks the same as a lost event. Evidence (plan's temporary hog: `hangGuard` = 3 s plus a test posting 16 x 0.5 s busy-spin blocks to `DispatchQueue.main`, reverted before commit):

- Before the fix: `./build.sh unit ProjectXPCTests` -> `CHECK UNIT: FAILED (16 tests, 0 compile errors)`, failures "no XPC reply" and `clock.waitForSleepers(1)` expiring.
- After the fix, same hog and bound: `CHECK UNIT: PASSED (29 tests)`.

## Fix

New `MainQueueProgressGuard` (test support): expires only after two consecutive `bound` intervals with no progress **and** a drained main-queue sentinel; a backlogged interval re-arms. `ProjectXPCTests.perform` now calls `service.perform` directly inside its own continuation (drops the extra `responseTask` hops) and guards it with an `XPCRequestTrace` (`sent` / `appTaskStarted` / `replied`), so a missing reply names the step reached. GitStatus waits use a `ScanTrace` (entered / returned / handled) as progress and in failure messages; `TestClock.waitForSleepers` uses the sleeper count. Interval is still `TestBounds.hangGuard`.

Round 2 (after review): `ScanTrace` now sits above `ScanGate`'s doc comment, so each type keeps its own doc. `XPCRequestTrace.describe(verb:)` names `openProjectForXPC` only for `projectOpen`; other verbs that fetched the store say "started and fetched the store, but never replied", and a `.sent`-only trace says "no store fetch recorded (the app's Task never started, or this verb never fetches the store)", which covers unknown verbs. `aLostReplyNamesTheStepItReached` checks all three wordings. Dropped the trailing blank line in `ProjectXPCTests.swift`. Round 2 runs: `./build.sh` -> `CHECK BUILD: PASSED`; `./build.sh unit ProjectXPCTests` -> `CHECK UNIT: PASSED (28 tests)`; `./build.sh unit GitStatusPaneContentTests` -> `CHECK UNIT: PASSED (20 tests)`; full `./build.sh unit` -> `CHECK UNIT: PASSED (4827 tests)`, exit 0 (1-min load 25.09 before, 34.24 after).

## Likely cause (read-only investigation, `main` at `81824a0d`)

There is no real XPC and no lost wakeup. The 60 s hang guard measures total wall time, and under load most of that time is the test queueing behind every other test that runs on the main actor.

- `perform(_:verb:payload:)` (`ProjectXPCTests.swift:66`–`78`) calls `AppXPCService.perform` directly, in-process. No `NSXPCConnection` is involved. It wraps the reply in a `@MainActor` `responseTask` and races it with `awaitBounded` (`AwaitBounded.swift:7`–`21`), whose guard is `DispatchQueue.global(qos: .utility).asyncAfter(.now() + TestBounds.hangGuard)`, which is 60 s of wall time from the start of the wait.
- Reply path for `projectOpen` (`BattyKit/Sources/BattyKit/XPC/AppXPCService.swift:532`–`575`):
  - `perform` registers the reply in `PendingRequestRegistry` (lock-based, `PendingRequestRegistry.swift:26`–`64`).
  - It starts a `Task { @MainActor }`, which calls `store.openProjectForXPC` (`AppStateStore+ProjectXPC.swift:37`).
  - `openProjectForXPC` calls `requestOpenProject` → `finishOpen` → `openProject` (`AppStateStore+ProjectStartup.swift:43`), and the completion runs synchronously on the `.skip`/`.runWithoutPrompt` paths.
  - The completion calls `pendingRequests.resolve` → reply → continuation, and `responseTask` resumes on the main actor.
  - That is two or three main-actor enqueues with no blocking work. `activateWindow` returns early because the tests have no `NSWindow` (`AppStateStore.swift:2329`–`2336`). The trust-sheet timeout uses the injected `TestClock`, not real time.
- `registry.resolve` removes the entry and calls the reply under the lock discipline, so a reply cannot be dropped. Sixteen tests failing together also points to a shared stall, not a per-test race.
- `ProjectXPCTests` is a non-serialized `@MainActor` suite (`:90`–`91`), and so are most of the roughly 4,800 BattyKitTests. Swift Testing runs them in parallel, but every main-actor job runs one at a time on the main thread. With about 1/30 of a core, plus synchronous main-actor blockers (`waitUntilExit()` and `killAndReap` in `@MainActor` suites, #0677), the two or three hops can take more than 60 s.
- **`GitStatusPaneContentTests` has the same cause.** Its fake scanner's `waitForScanStarted(bound:)` (`GitStatusPaneContentTests.swift:117`–`133`) and the scan-result signal wait at `:247`–`:262` use the same kind of wall-clock `asyncAfter(+hangGuard)` guard, and the event they wait for is produced by `@MainActor` `GitStatusPaneContent` work that queues the same way. The tests use `TestClock` for scheduling, so this is not a real-time dependency of the code under test.
- This is the same mechanism #0675 found for `SharedProjectImagesTests`, where the starved pass made zero transport calls. #0675 fixed that suite's guard to measure lack of progress instead of total time (`FakeSharedImageTransport.waitForHeldRead` re-arms while `_calls.count` grows). `docs/async-test-seams.md` §4 says not to raise `hangGuard` again.

## Expected behavior

- `ProjectXPCTests` and `GitStatusPaneContentTests` pass in full `./build.sh unit` runs on a heavily loaded host. Their guards expire only on a real lost reply or a hung scan, not because the main actor was busy.
- A guard failure says how far the request got. For `projectOpen`, that means one of: the `perform` Task never started, `openProjectForXPC` was entered but the completion never ran, or the reply was resolved but `responseTask` never resumed. For git status, that means whether the scan started.
- No sleeps, polling, elapsed-time assertions, or a larger `hangGuard` (`AGENTS.md`, #0443).

## Plan

Written 2026-11-18 against `main` at `50f32725`. Test-only: no production defect found.

### Cause, checked in code

- `ProjectXPCTests.perform` (`:66`–`78`) is `@MainActor` and wraps `service.perform` in a `Task { @MainActor }` (`responseTask`), then races it with `awaitBounded` (`AwaitBounded.swift:7`–`21`), whose guard is a one-shot `asyncAfter(+60 s)` armed when the wait starts. The reply needs three main-queue jobs: `responseTask` starts, the app's `Task { @MainActor }` in `AppXPCService.perform` (`AppXPCService.swift:533`) runs `storeProvider()` then `openProjectForXPC` (completion synchronous on the non-trust paths), and `responseTask` resumes after the reply. Nothing blocks and nothing uses real time (`TestClock`); the reply is resolved through the lock-guarded `PendingRequestRegistry`, which cannot drop it. So the only thing that can push a reply past 60 s is the queue in front of each main-queue job.
- `GitStatusPaneContentTests`: `requestScan` (`GitStatusPaneContent.swift:812`–`826`) starts a main-actor `scanTask`, the fake scanner runs off main, and `handleScanResult` runs back on main and fires `onScanResultHandledForTesting`. `ScanGate.waitForScanStarted` (`:117`–`133`) and `ScanHandledSignal.wait` (`:247`–`262`) use the same one-shot 60 s `asyncAfter` guard.
- `TestClock.waitForSleepers` (`TestClock.swift:190`–`209`) has the same one-shot guard. Both suites use it (ProjectXPC trust-sheet tests, GitStatus debounce test), and a sleeper registers only after main-actor hops.
- No production defect: `AppXPCService.perform`'s `projectOpen` path and `openProjectForXPC` are correct; the issue's reading holds.

### Approach and reasons

- **(b), a no-progress guard, is the fix.** A one-shot wall-clock guard cannot tell "the main queue is 60 s deep" from "the reply was lost". The new guard fails only when (1) the test-visible step count has not advanced for a full interval **and** (2) a sentinel block posted to `DispatchQueue.main` at the start of that interval has already run, i.e. the main queue drained past everything queued before it. It needs two such quiet intervals in a row before failing. That covers the race where a step is stamped just before its successor hop is enqueued: the second interval's sentinel is posted at least one interval after the last stamp, so the pending hop is definitely ahead of it. The interval stays `TestBounds.hangGuard` (60 s); no constant grows. A genuine lost reply on an idle main queue fails in about 120 s instead of 60 s.
- **(a), `nonisolated` suites, is rejected for both suites.** The code under test (`AppStateStore`, `GitStatusPaneContent`, `Fixture`, the `NSWindow` activation tests) is main-actor, so `nonisolated` bodies would add `MainActor.run` hops rather than remove them, and the app's own `Task { @MainActor }` hop stays either way. The starvation comes from the rest of the main-actor suites, not these suites' isolation. Instead, `perform` drops `responseTask`: it calls `service.perform` directly inside its own continuation and resumes from the reply closure, removing two of the three main-queue hops per request. (`AppXPCService` is not `Sendable`, so it cannot move into an off-main `Task`; calling it synchronously from the main-actor helper is the simplest correct form.)
- **No suite `.timeLimit`.** A run-level limit would bring back the wall-clock failure under load. If the main queue never drains, every main-actor test is hung anyway and the run is visibly stuck; say so in `## Gotchas`.
