## Description

A non-terminal view kind that shows, live, what a local LM Studio server is doing: which models are loaded and with what runtime config, whether inference is running, request throughput, and recent prediction activity. Like #0304 and #0305 it is **design-gated per the #0301 umbrella**: visual designs are drafted and approved by the user before implementation starts; no move to implementation on an unapproved design.

The user's motivation, in their words:

> "I am currently integrating local AI into my Claude Code workflow so it is dispatching work to OpenCode which uses a local model run inside LM Studio. It will be helpful to have a live view into what is happening."

The value is observability into an *agentic* pipeline the user cannot otherwise see: Claude Code dispatches work to OpenCode, OpenCode runs a local model inside LM Studio, and today that middle-and-bottom of the stack is a black box. A Batty Pane watching the LM Studio server turns it into a live dashboard sitting next to the terminals driving it.

Everything below marked "from the reference" comes from `0313/lmstudio-realtime-api.md` (see Attachments), which was verified live on 2026-08-07 against the user's Mac mini LM Studio server. Read it in full before designing — this issue summarises only what constrains the design.

## What the interfaces actually support (from the reference)

These facts bound the design; a mockup that ignores them cannot be built.

- **Exactly one push feed exists**: the diagnostics log stream (`lms log stream --json --stats` emitting NDJSON, or the SDK's `unstable_streamLogs` over WebSocket). Everything else is polling. There is **no general-purpose `/events` SSE endpoint** — `GET /api/v1/events`, `/api/v0/events`, and `/` all return 404.
- **`--stats` is mandatory for throughput data.** tok/s and time-to-first-token exist *only* in the log stream's `llm.prediction.output` stats block — the OpenAI-compat response returns `"stats": {}`.
- **The feed is per-prediction, not per-token.** `llm.prediction.input` fires when a prediction starts; `llm.prediction.output` fires when it ends, carrying the whole completion at once. **A live token-by-token ticker is impossible for traffic other clients originate** (OpenCode's requests included) — only requests the dashboard itself sends can stream per-token via SSE. No design may propose a live token stream for observed traffic; it cannot be built.
- **In-flight state is derived**: an `input` event with no matching `output` yet. Pairing is by `modelIdentifier` in arrival order and is **heuristic** — events carry no request ID, and a `parallel: 2` instance can have two predictions outstanding at once.
- **`lms ps` is the only source of GENERATING vs IDLE**, plus `DEVICE` and `TTL`; neither REST endpoint exposes them. The reference warns to check whether the installed CLI build supports `--json` before writing a column-position parser.
- **No load/unload push events.** Model load/unload transitions must be synthesised by diffing `/api/v1/models` polls (~1 Hz is fine; loaded-vs-not is a non-empty `loaded_instances` array, or `/api/v0/models`'s explicit `state` field).
- **The SDK streaming method is alpha.** `unstable_streamLogs` is marked in-source "Do not use this method in production yet" and carries an `unstable_` prefix — an API-stability risk to record in the design (the CLI subprocess is the alternative transport for the same feed).

## The prompt feed is a full transcript — treat it as a privacy surface

Not a footnote: `llm.prediction.input` carries the **entire rendered prompt after the Jinja chat template** — system prompt, tool definitions, conversation history, everything. One OpenCode turn produced a ~28 KB event at 28,411 prompt tokens (from the reference). The feed contains every prompt anyone sends that server, from any client.

Two consequences for the design:

1. **A prompt/completion inspector panel is a privacy surface inside Batty.** Whether to show prompt text at all, and if so with what retention and redaction, is an open design question that needs the user's answer — not a default-on panel.
2. **Volume is a real constraint.** Tens of KB per event, unbounded over a long session. Retention policy (ring buffer size, discard-on-hide per #0303) must be part of the design, not an afterthought — this project has an entire umbrella (#0285) about unbounded growth.

## Local vs remote LM Studio — an architectural fork needing the user's answer

Predictions execute on the Mac mini. The reference says to run the collector there, and records as **untested** whether a MacBook Air's local `lms log stream` sees mini-originated predictions (LM Link mirrors models, not necessarily diagnostics). For a desktop app Pane this is a genuine fork:

- **Local-only**: the Pane observes the LM Studio instance on the same machine Batty runs on. Simple, but a Batty on the MacBook Air may see nothing useful while the mini does the work.
- **Remote-capable**: the Pane connects to a remote LM Studio (the mini) over the network. The WebSocket/REST interfaces allow it in principle, but the reference warns that `ai.sstools.co` is an **open public endpoint** that must not be reused unauthenticated for a feed rebroadcasting prompt text — remote access requires an authenticated path that does not exist today.

Flag this as an open question for the user before design work commits either way. Note also that the reference's §6 sketches a collector + SSE + browser architecture; **a Batty Pane is a different target** — it can consume the SDK or the CLI subprocess directly in-process, so §6's panel table is the useful part and its network topology is not necessarily applicable.

## Candidate panels (design-phase material, not decisions)

Grounded in what the data supports (reference §6):

- Loaded models with size, quantization, architecture, and per-instance context config (`/api/v1/models` polling).
- Busy/idle light with TTL countdown and device (`lms ps`).
- Live request list: in-flight (unmatched `input` events) plus recent completions with durations.
- tok/s over time and TTFT distribution (`stats.tokensPerSecond`, `stats.timeToFirstTokenSec`).
- Context-window pressure: `stats.promptTokensCount` ÷ `loaded_context_length`.
- Stop-reason breakdown (`stats.stopReason`: `eosFound`, length, …).
- Engine errors and warnings (`-s runtime` / `-s server` log sources).
- Connection health (SDK `system.whenDisconnected()`, or subprocess liveness).
- Prompt/completion inspector — **only if the privacy question above is answered in its favor**.

Explicitly **not supported by any interface** (say so in the designs so nothing is promised): live token-by-token display of other clients' traffic; GPU/memory utilization (needs `powermetrics`/`ioreg` separately — see #0314); per-request client identity or attribution (events carry no client or request ID).

## Gotchas

This Pane depends on external software the project does not control: LM Studio's CLI output format (`lms ps` columns, NDJSON banner lines), an SDK method marked alpha, and an undocumented WebSocket wire protocol the reference says not to hand-roll. The design must define behavior for **LM Studio not installed, not running, and version-drifted** — a degraded/empty state, not a crash or a spinner. The reference pins the CLI commit it was verified against (`6041ae0`); re-verify against the installed version when implementation eventually starts.
