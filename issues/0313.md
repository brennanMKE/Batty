## Description

A non-terminal view kind that shows, live, what a local LM Studio server is doing: which models are loaded and with what runtime config, whether inference is running, request throughput, and recent prediction activity. Like #0304 and #0305 it is **design-gated per the #0301 umbrella**: visual designs are drafted and approved by the user before implementation starts; no move to implementation on an unapproved design.

The user's motivation, in their words:

> "I am currently integrating local AI into my Claude Code workflow so it is dispatching work to OpenCode which uses a local model run inside LM Studio. It will be helpful to have a live view into what is happening."

The value is observability into an *agentic* pipeline the user cannot otherwise see: Claude Code dispatches work to OpenCode, OpenCode runs a local model inside LM Studio, and today that middle-and-bottom of the stack is a black box. A Batty Pane watching the LM Studio server turns it into a live dashboard sitting next to the terminals driving it.

Everything below marked "from the reference" comes from `0313/lmstudio-realtime-api.md` (see Attachments), which was verified live on 2026-08-07 against the user's Mac mini LM Studio server. Read it in full before designing — this issue summarises only what constrains the design.

## Phase 1 status (2026-08-08) — spike verified live, designs delivered, awaiting user approval

**Phase 1 is complete and landed on `main`. Phase 2 has not started and must not start until the user answers the two questions below.** Status stays `in-progress`, not `resolved` — same posture as #0304, #0305 and #0314.

Deliverables: `docs/design/lmstudio-dashboard-view.md` and `docs/design/lmstudio-dashboard-view.html` (five states: idle with models loaded, prediction in flight, completed with stats, no server reachable, and the Prompt Inspector opt-in variant).

### Two questions that need the user's answer — the design recommends but does not decide

1. **Should the dashboard show prompt or completion text at all?** `llm.prediction.input` carries the entire rendered prompt — system prompt, tool definitions, full conversation history — for every request *anyone* sends that server. The design's recommendation: **off by default**, with an explicit opt-in "Prompt Inspector" capped at 5 entries, never sourced from the `server` log stream. States 1–4 are deliberately useful with prompt text entirely absent.
2. **Local-only or remote-capable?** Predictions run on the Mac mini; Batty may run elsewhere. The design's recommendation: **local-only for phase 1**. Remote would need an authenticated path that does not exist, and the reference warns `ai.sstools.co` is an open public endpoint that must not be reused unauthenticated for a feed that rebroadcasts prompt text.

### The spike — run against a live server, with corrections to the reference

Verified against `http://localhost:1234` on the same mini the reference used, CLI commit `6041ae0`. **Every load-bearing claim was independently re-verified by the reviewer**, and one was settled by a third experiment.

**A privacy finding the reference does not report, and the most consequential result here:** the **`server`-source log stream leaks full request *and completion* bodies in free-text lines at the default `info` level** — confirmed verbatim by the reviewer, including an `info` line carrying a whole completion. This is the same exposure class as `input`/`output`, differently shaped, and it narrowed the design's Engine Errors panel to `runtime`-source only. Anything that tails LM Studio's server log is reading prompts.

**Pairing is worse than "heuristic" — it is observably inconsistent.** Three independent concurrent-prediction trials across implementer and reviewer:

| Trial | `input` order | `output` order | Arrival-order pairing |
|---|---|---|---|
| 1 | PERLINE, ODD (identical ms) | ODD, PERLINE | wrong |
| 2 | PERLINE, ODD | ODD, PERLINE | wrong |
| 3 | ODD, PERLINE | ODD, PERLINE | correct |

Two of three wrong on the same server, model and prompts. The mechanism is visible in the data: input arrival order is nondeterministic under near-simultaneity while outputs arrive in completion order, so **there is no stable bias a UI could compensate for**. That is precisely why the design surfaces the caveat in its own UI copy rather than attempting to fix the pairing.

Worth recording how that conclusion was reached: told by review that outputs had arrived reversed, the implementer checked its *own* capture, found them **not** reversed, and declined to assert a reversal it had not observed — attributing the reversal to the reviewer's run and keeping both as data points. The third trial confirmed the resulting "run-to-run inconsistent" framing was more accurate than either single run.

**Corrections to the reference document:**

- `/api/v0/events` and `/` return **200 with `{"error":"Unexpected endpoint..."}`**, not 404. Only `/api/v1/events` truly 404s. The conclusion — no push feed — is unaffected.
- `stats` appears in output events **without** `--stats` on this build, contradicting the reference's "mandatory."
- The reference's "~28 KB at 28,411 tokens" ratio does not match the measured ratio. Order of magnitude confirmed (an 18 KB prompt produced an 18,241-byte event); the exact figure is carried forward marked unverified.

**New findings:** `lms ps --json` costs ~130–157 ms per call against `/api/v1/models`'s ~11 ms — unlike the sibling views' near-free polls, which shapes the cadence design. `lms log stream -s` accepts exactly one source per invocation, so prediction events and error logs need separate subprocesses.

**Confirmed from the reference:** no request ID anywhere; `output` arrives whole rather than per-token, so **a live token ticker is impossible for observed traffic**; the OpenAI-compat `stats` is `{}`; both WebSocket endpoints upgrade.

**Could not verify:** `unstable_streamLogs` itself (no TS/Node harness) — the alpha-API risk is recorded and designed around by choosing the CLI subprocess transport; whether a MacBook Air sees mini-originated predictions, since the spike ran *on* the mini and adds no evidence either way; `-s runtime`'s own content-safety.

### Other design decisions

**Retention** reuses `BellFeedStore`'s `cap = 200`. **History is discarded entirely on hide** — a named departure from #0305/#0314, justified because a prediction log cannot be cheaply resampled the way a live metric can. The degraded state is defined: two consecutive failed polls declare the server unreachable, both log-stream subprocesses terminate, the `lms ps` poll stops, and `/api/v1/models` backs off to a 5 s reachability probe (itself cancelled on hide, so "zero periodic work while suspended" holds).

## What the interfaces actually support (from the reference)

These facts bound the design; a mockup that ignores them cannot be built.

- **Exactly one push feed exists**: the diagnostics log stream (`lms log stream --json --stats` emitting NDJSON, or the SDK's `unstable_streamLogs` over WebSocket). Everything else is polling. There is **no general-purpose `/events` SSE endpoint** — `GET /api/v1/events`, `/api/v0/events`, and `/` all return 404.
- **`--stats` is mandatory for throughput data.** tok/s and time-to-first-token exist *only* in the log stream's `llm.prediction.output` stats block — the OpenAI-compat response returns `"stats": {}`.
- **The feed is per-prediction, not per-token.** `llm.prediction.input` fires when a prediction starts; `llm.prediction.output` fires when it ends, carrying the whole completion at once. **A live token-by-token ticker is impossible for traffic other clients originate** (OpenCode's requests included) — only requests the dashboard itself sends can stream per-token via SSE. No design may propose a live token stream for observed traffic; it cannot be built.
- **In-flight state is derived**: an `input` event with no matching `output` yet. Pairing is by `modelIdentifier` in arrival order and is **heuristic** — events carry no request ID, and a `parallel: 2` instance can have two predictions outstanding at once.
- **`lms ps` is the only source of GENERATING vs IDLE**, plus `DEVICE` and `TTL`; neither REST endpoint exposes them. The reference warns to check whether the installed CLI build supports `--json` before writing a column-position parser.
- **No load/unload push events.** Model load/unload transitions must be synthesised by diffing `/api/v1/models` polls (~1 Hz is fine; loaded-vs-not is a non-empty `loaded_instances` array, or `/api/v0/models`'s explicit `state` field).
- **The SDK streaming method is alpha.** `unstable_streamLogs` is marked in-source "Do not use this method in production yet" and carries an `unstable_` prefix — an API-stability risk to record in the design (the CLI subprocess is the alternative transport for the same feed).

## The prompt feed is a full transcript — treat it as a privacy surface

Not a footnote: `llm.prediction.input` carries the **entire rendered prompt after the Jinja chat template** — system prompt, tool definitions, conversation history, everything. One OpenCode turn produced a ~28 KB event at 28,411 prompt tokens (from the reference). The feed contains every prompt anyone sends that server, from any client.

Two consequences for the design:

1. **A prompt/completion inspector panel is a privacy surface inside Batty.** Whether to show prompt text at all, and if so with what retention and redaction, is an open design question that needs the user's answer — not a default-on panel.
2. **Volume is a real constraint.** Tens of KB per event, unbounded over a long session. Retention policy (ring buffer size, discard-on-hide per #0303) must be part of the design, not an afterthought — this project has an entire umbrella (#0285) about unbounded growth.

## Local vs remote LM Studio — an architectural fork needing the user's answer

Predictions execute on the Mac mini. The reference says to run the collector there, and records as **untested** whether a MacBook Air's local `lms log stream` sees mini-originated predictions (LM Link mirrors models, not necessarily diagnostics). For a desktop app Pane this is a genuine fork:

- **Local-only**: the Pane observes the LM Studio instance on the same machine Batty runs on. Simple, but a Batty on the MacBook Air may see nothing useful while the mini does the work.
- **Remote-capable**: the Pane connects to a remote LM Studio (the mini) over the network. The WebSocket/REST interfaces allow it in principle, but the reference warns that `ai.sstools.co` is an **open public endpoint** that must not be reused unauthenticated for a feed rebroadcasting prompt text — remote access requires an authenticated path that does not exist today.

Flag this as an open question for the user before design work commits either way. Note also that the reference's §6 sketches a collector + SSE + browser architecture; **a Batty Pane is a different target** — it can consume the SDK or the CLI subprocess directly in-process, so §6's panel table is the useful part and its network topology is not necessarily applicable.

## Candidate panels (design-phase material, not decisions)

Grounded in what the data supports (reference §6):

- Loaded models with size, quantization, architecture, and per-instance context config (`/api/v1/models` polling).
- Busy/idle light with TTL countdown and device (`lms ps`).
- Live request list: in-flight (unmatched `input` events) plus recent completions with durations.
- tok/s over time and TTFT distribution (`stats.tokensPerSecond`, `stats.timeToFirstTokenSec`).
- Context-window pressure: `stats.promptTokensCount` ÷ `loaded_context_length`.
- Stop-reason breakdown (`stats.stopReason`: `eosFound`, length, …).
- Engine errors and warnings (`-s runtime` / `-s server` log sources).
- Connection health (SDK `system.whenDisconnected()`, or subprocess liveness).
- Prompt/completion inspector — **only if the privacy question above is answered in its favor**.

Explicitly **not supported by any interface** (say so in the designs so nothing is promised): live token-by-token display of other clients' traffic; GPU/memory utilization (needs `powermetrics`/`ioreg` separately — see #0314); per-request client identity or attribution (events carry no client or request ID).

## Gotchas

This Pane depends on external software the project does not control: LM Studio's CLI output format (`lms ps` columns, NDJSON banner lines), an SDK method marked alpha, and an undocumented WebSocket wire protocol the reference says not to hand-roll. The design must define behavior for **LM Studio not installed, not running, and version-drifted** — a degraded/empty state, not a crash or a spinner. The reference pins the CLI commit it was verified against (`6041ae0`); re-verify against the installed version when implementation eventually starts.

## Gotchas

- **CLI version drift, found and handled, not just anticipated.** The
  reference and phase-1 design doc were verified against CLI commit
  `6041ae0`; this machine's installed build reports `71bd99c`. Re-checked
  every load-bearing claim against the drifted build: `/api/v1/models`'s
  `loaded_instances[].config` now includes an extra
  `reasoning_budget_message` key absent from the reference (tolerated —
  every config field this dashboard reads is decoded individually, and the
  extra key is simply ignored); `lms ps --json`'s field names, lowercase
  `status`, and `null` `deviceIdentifier`/`ttlMs` all still match; the
  `--stats`-optional behavior the phase-1 spike found on `6041ae0` was not
  independently re-tested against `71bd99c` in this round (the code passes
  `--stats` defensively regardless, and decodes an absent `stats` block as
  `nil` either way, so this is a belt-and-suspenders case, not a load-bearing
  gap).
- **`PaneRuntime.init` constructs the `LMStudioDashboardPaneContent` but
  deliberately never calls `setUp()` on it.** `PaneRuntime.init` is
  exercised directly by pre-existing, unrelated model-layer tests
  (`AppStateStorePaneSplitTests`, `PaneContentKindTests`,
  `RequestCloseTabTests`) that construct `.lmStudioDashboard`-kind panes to
  assert on `kind`/focus/close behavior and never render them — if
  construction alone started a real subprocess and HTTP poll, every one of
  those tests (and any future one that does the same) would spawn one, and
  on a machine with LM Studio actually installed and running — this one —
  it would be a *real* subprocess, not a harmless no-op. `setUp()` is
  instead called from `LMStudioDashboardView`'s `.task`, guarded by
  `lifecyclePhase == .notSetUp`, the first time the pane is genuinely
  rendered. `hidePane`/`showPane` calling `setVisible` on a pane that was
  never rendered (so never `setUp`) is a legal, logged `.rejected` no-op
  per the state machine, not a crash — `LMStudioDashboardWiringTests`
  covers this directly. This is a narrowing of the design doc's own §7
  table, which describes `setUp` as running unconditionally "at Pane
  creation" — recorded here as a deliberate, reasoned deviation, not an
  oversight.
- **Throughput is a text summary, not the sparkline the design describes.**
  Given the "get it done" pragmatics, the mini-chart (design §3.5) was
  built as an average-tok/s line plus a stop-reason tally rather than an
  actual sparkline widget — same underlying data (computed client-side from
  the retained ring), lighter visual investment. Worth a follow-up pass if
  the user wants the visual sparkline specifically.
- **`showPane`'s asymmetry, flagged by the design as an open wiring
  question, was resolved by making it explicit** (mirroring `hidePane`
  rather than relying on a remount) — safe because `setVisible` is
  idempotent by contract regardless of how many times or from where it's
  called.
- **Not verified, and owed by this change** (same obligation every prior

## Review round 1 (2026-08-21) — REQUEST CHANGES, addressed

Reviewer confirmed the build/test results, and rated privacy posture, drift
tolerance, degraded-state handling, observation-rule compliance, and
terminal-path isolation as genuinely good (audited all 17 `logger.` call
sites for a prompt-leak path; found none). Findings were concentrated in
subprocess lifecycle:

- **B1 — stderr `readabilityHandler` never cleared at EOF, a permanent
  full-core busy-spin.** Reproduced live: 2,203,223 invocations in 2
  seconds after the child exited, never stopping, on every exit path
  (hide, teardown, unreachable-backoff, respawn). Fixed: stderr's handler
  now nils itself out on an empty read exactly like stdout's already did,
  and `terminateModelStream`/`terminateRuntimeStream` clear both handlers
  explicitly, not just stdout's.
- **B3 — subprocess teardown was asserted only via `lifecyclePhase ==
  .tornDown`, exactly the assertion `issues/0313.md`'s own binding
  contract excludes** ("log evidence, a counter, a footprint delta — not
  an assertion"). Reviewer proved it by commenting out both
  `process.terminate()` calls: all 1092 tests still passed, leaving 12
  orphan processes. Fixed: two new tests
  (`tearDownActuallyTerminatesBothSubprocesses`,
  `hidingActuallyTerminatesBothSubprocesses`) capture the actual `Process`
  objects the injected factories hand out and assert `isRunning == false`
  after `tearDown()`/`setVisible(false)`. Re-ran the reviewer's exact
  mutation (commented out both `terminate()` calls) to confirm the new
  tests catch it — they failed with `(model.isRunning → true) == false`
  and the equivalent for `runtime` — then restored the source and killed
  the two orphaned `sleep 60` processes the mutation run left behind.
- **S1 — `Dictionary(uniqueKeysWithValues:)` traps on a duplicate `lms ps`
  identifier**, external drifting input that could crash the app against
  this issue's own "version-drift never crashes" commitment. Fixed:
  `uniquingKeysWith: { _, latest in latest }`.
- **S2 — `expecting…StreamExit` could stick `true` permanently**, set by
  the caller *before* calling `terminate…`, which early-returns when the
  process is already `nil`. On "LM Studio not running, then started," the
  stuck flag would misread the next genuine stream death as expected: no
  respawn, no `.reconnecting`, pill stuck reading "Connected" with the live
  feed silently dead. Fixed: the flag is now set inside
  `terminateModelStream`/`terminateRuntimeStream`, after the `guard let
  process` — only when there's an actual process to signal.
- **S3 — `LMStudioCLI.runPs` never drained `errorPipe`**, so more than
  64 KB of stderr (a stack trace from a drifted build) would block the
  child and wedge `waitUntilExit()`, permanently stalling `psPollTask`.
  Fixed: `lms ps --json`'s stderr routes straight to
  `FileHandle.nullDevice` — this call has no use for it, so there's
  nothing to drain.
- **B2 (three close paths never calling `tearDown()`) is out of scope for
  this branch** — shared across all four kind-switch-touching issues,
  #0314 is fixing it centrally and this branch inherits it on rebase.
- **The `.task`-driven `setUp()` deviation was judged sound in mechanism
  (race-free) but is being resolved centrally by #0314** via an injectable
  `contentFactory` on `PaneRuntime.init`. Deferred, not built here, per
  the coordinator's explicit instruction — this branch keeps its `.task`
  guard until it rebases onto the merged #0314 change.

test. Closing that gap would mean adding new test-injection API to
`AppStateStore` itself — shared infrastructure `#0314` owns and already
explicitly decided (at review, non-blocking) was acceptable to leave
UI-test-only. Building that unilaterally as a single kind's implementer
felt like the wrong layer for the decision, so this round instead adds
the strongest verification available at this kind's own layer: proof that
the shared `tearDownAllPaneContent()` helper those two paths call
actually kills this kind's real subprocesses (above). Left as a
follow-up if the coordinator wants the fuller seam built.
