## Description

Closing the last Tab in a Pane removes the Pane from the Split tree, and the parent Split is replaced by its remaining child (`Concepts.md` → Pane → "Closing", → Split → "Collapsed"). This is the inverse of #0018's split operation.

**Acceptance criteria:**
- Closing the last Tab in a Pane (via Cmd-W, chip close button, or programmatically) removes the Pane.
- The parent `.split(...)` node is replaced in its grandparent's slot by the surviving sibling subtree.
- If the closing Pane is the only Pane in the Session, the Session keeps an empty Pane with a "+ New tab" placeholder — we do **not** auto-close Sessions.
- Focus moves to the surviving sibling (or its first leaf, recursively). Typing immediately goes to the newly-focused surface.
- Surfaces are torn down via `SurfaceRegistry.destroy(surfaceID)` — no PTY leaks.

## Notes

- This issue is the natural pair to #0018 (split). Resolve them together if helpful, but they remain separate so each is independently committable.
- Consider adding a sanity assert that the tree is well-formed after every collapse (no `.split` with one child, no orphaned panes) — useful during development; remove or downgrade to debug-only later.

## Root cause

Feature gap. M4 splits introduced multi-pane sessions; without a way to remove panes, the tree only grows.

## Fix

Three layered changes:

- **`SplitTreeNode.removingPane(_:from:)`** — recursive walker returning the new subtree with the named pane removed. Returns `nil` if the entire subtree consisted of the removed pane, signaling its parent split to collapse. The split-case dispatch uses both child results to decide: surviving sibling takes the parent's slot when one child is `nil`; the split reconstructs with both new children otherwise.
- **`SplitTree.removeFocusedPane()`** — guards on `allPanes.count > 1` so the session never hits zero leaves; calls the walker; reassigns `root` and resets `focusedPaneID` to the first leaf of the new tree.
- **`SessionRuntime.closeFocusedTab()`** — single entry point used by Cmd-W. Three cases:
  1. `focusedPane.tabs.count > 1` → `pane.closeActiveTab()` (M3 path).
  2. Tabs == 1 but `tree.allPanes.count > 1` → `tree.removeFocusedPane()` (this issue).
  3. Tabs == 1 and only pane in session → no-op (`Concepts.md` calls for "empty pane placeholder", deferred polish).

`BattyCommands` Close Tab now calls `closeFocusedTab()` and its disabled predicate (`canCloseFocusedTab`) is true when **either** tabs > 1 **or** panes > 1. So Cmd-W works in both multi-tab and multi-pane single-tab scenarios.

## Gotchas

- **Visual verification:** create two panes via Cmd-D, switch focus to the new pane (click on it; geometric Cmd-Option-arrows is #0020 deferred), Cmd-W → that pane should disappear and the original takes the full space. Repeat with vertical split via Cmd-Shift-D. `xcodebuild build` passes; resolved-not-closed.
- **Empty-pane-placeholder for the only-pane single-tab case** is deferred. Today Cmd-W in that situation no-ops (because the system Cmd-W "Close Window" likely takes precedence anyway since our button is disabled). Once `closeFocusedTab` decides "you tried to close the only tab in the only pane", a future polish could either close the session (but Concepts.md says no — sessions don't auto-close) or render an "empty pane with + New tab" placeholder. Leaving for a follow-up.
- **The chip-X close button on the only tab in a multi-pane session is still hidden.** That's a UX gesture worth adding (clicking the X on the only tab of a split-off pane to collapse the pane is iTerm2-style natural), but it requires PaneView knowing whether it's in a multi-pane session. Either an environment value or a callback prop. Filed as a polish follow-up.
- **`focusedPaneID` after collapse** is reset to `newRoot.firstLeafPaneID`. That's defensive; arguably the user would prefer the *sibling* (geometric neighbor) to take focus, since they were "in" the closed pane and the sibling is the natural next target. v1 simplicity wins; revisit when there's geometric pane-frame data (#0020).
- **Tree well-formedness invariant:** every `.split` always has two non-nil children. The collapse logic preserves this — when one child becomes empty, the parent split is replaced by the surviving child; we never end up with a `.split(left: nil, right: x)`. Worth defending with a debug-only assertion if invariants are violated; out of scope for v1.
