## Description

`LMStudioDashboardPaneContent` correctly caps its three display rings — completions at `completionCap` (`BellFeedStore.cap` = 200), the inspector at 5, engine errors at `engineErrorCap` = 50 — but two other growth points are unbounded:

- **`inFlight`** is bounded only by a 5-minute staleness sweep (`startedAt < cutoff`). Nothing limits how many entries can accumulate *within* the window, and each entry can carry prompt text: the `-s model` stream's lines include the full prompt, held in `pendingPrompts` until matched. A burst of requests against a busy server holds arbitrarily much prompt text for up to 5 minutes.
- **`modelStreamBuffer` / `runtimeStreamBuffer`** grow until a newline arrives. A malformed or adversarial stream that never emits `\n` (or one enormous NDJSON line — again, `-s model` lines carry full prompt text) grows the `Data` without limit.

Secondary, same code path: `consumeLines(from:)` extracts each line with `buffer.removeSubrange(..<range.upperBound)`, which is O(remaining bytes) per line — quadratic over a large buffer arriving in many small chunks. A cap plus an offset-based consume (drain once per `append`) fixes both.

This is exactly the unbounded-growth class the #0285 umbrella spent several issues retro-fixing out of the terminal path; new view kinds should not reintroduce it.

## Expected behavior

`inFlight` has a hard entry cap (oldest dropped, count-based, alongside the existing staleness sweep); the two stream buffers have a hard byte cap with a defined overflow behavior (drop the line, log once); line consumption is not quadratic.

## Actual behavior

`inFlight` and both line buffers can grow without bound between newlines / within the staleness window.

## Resolution notes

> 🟢 Resolved 2026-09-23 — the LM Studio dashboard's in-flight list is capped at 50 entries and each NDJSON stream line at 256 KB; an oversized or never-terminated line is dropped (logged once) and the stream resynchronizes at the next newline.

## Root cause

`inFlight` had only a 5-minute time-based sweep, no count cap, and each entry can carry a full prompt via `pendingPrompts`. The stream buffers were raw `Data` that only shrank on `\n`, so a line without a newline grew them without bound. `consumeLines` also removed bytes once per line, which is quadratic for a chunk with many lines.

## Fix

- `inFlightCap = 50`: the oldest entries (by insertion) are evicted with their `pendingPrompts` text after every insert. Hard ceiling ≈ 50 × 256 KB ≈ 12.5 MB, far less at design §1.5's measured event sizes.
- `streamLineByteCap = 256 KB`, about 14× the largest event measured live (18,257 bytes; the reference's ~28 KB is unverified).
- `NDJSONLineBuffer`: one forward scan and one `removeSubrange` per append; an over-cap line's bytes are discarded until its newline, then parsing resumes. It signals once when a drop begins and once when it ends (with the total), so logging is per line, not per pipe read.
- Both stream buffers are reset when their subprocess respawns, so a leftover drop state can't swallow the new process's first line.
