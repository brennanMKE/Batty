## Description

Evaluate embedding a Chromium-based web view in Batty using the user's own **CEFWebView** package (`/Users/brennan/Developer/brennanMKE/CEFWebView`, work in progress, MIT), motivated primarily by **agentic workflows driven through the `batty` CLI**. The user's framing: "explore embedding a web view in Batty using a project I put together recently ... It would likely be useful with the CLI tool for agentic workflows."

This is an **exploration/decision ticket** in the #0254 mold, not a commitment to build. The deliverable is a decision record; no Batty app code changes under this ticket. The governing constraint from #0254 applies verbatim: **Batty stays simple and stays a first-class Mac app** — Batty exists precisely because cmux/supacode/herdr were *too much*. The bar is high, and this ticket's job is to make the case honestly on both sides.

Prior art in this tracker: #0254's cmux survey records a **"scriptable in-app browser (DOM automation)"** as a cmux feature — the direct precedent for this idea, and part of the feature set the user walked away from. Apply that lens; do not assume adoption.

## The scope objection, head-on

The project has an established principle that Batty is a terminal multiplexer and does not accumulate general content viewers — markdown preview, image viewers, and similar have been declined on exactly those grounds. A browser is the largest possible instance of that category, in bundle weight, process count, and maintenance surface.

**The only justification that clears the bar is agent automation the terminal genuinely cannot provide** — not "it would be handy to have a browser." If the exploration cannot name a concrete agent capability that requires an *embedded* view, the recommendation is decline, and this ticket succeeds by saying so.

## The central question: CEF vs WKWebView

This is the crux and should be the first section of the decision record.

- **WKWebView** is system-provided: zero bundle weight, no extra entitlements, no helper-process signing, no framework to track against Chromium releases. Its automation surface is thin — `evaluateJavaScript(_:)` / `callAsyncJavaScript`, snapshot APIs — but it is free.
- **CEF**'s justification has to be capability WKWebView cannot deliver — realistically the **Chromium DevTools Protocol** (full DOM inspection, expression evaluation, input synthesis, network interception, reliable screenshots). CEFWebView's `IMPLEMENTATION_GUIDE.md` lists "Remote DevTools protocol" as a CEF advantage in its comparison table, but note: **no DevTools/CDP wiring exists in the package's sources today** — it appears only in the guide's "Next Steps" TODO list, alongside the JavaScript bridge (`evaluateJavaScript`). Neither is implemented (verified by searching `Sources/`; the current public surface is navigation only — see maturity below).

Frame the evaluation as: *what specific agent capability requires CDP?* If the honest answer is "screenshot a page and read the DOM," WKWebView may well suffice at a fraction of the cost — and that is a legitimate outcome of this exploration. Do not pre-judge it in either direction.

## Cost inventory (verified against the CEFWebView repo, 2026-07-24)

- **Bundle weight.** The CEF framework binaries are git-ignored (`Frameworks/`, populated by `build_cpp.sh` from a `CEF/cef_binary_*` distribution) and absent from the checkout, so the on-disk size is **not measured**. `build.sh`'s release notes name CEF version **146.0.10**; the guide puts each helper executable at 20–30 MB and baseline memory at ~100–200 MB for Chromium plus its processes. Batty ships as a notarized DMG — the framework would dominate the download size and must be measured before any go decision.
- **Multi-process architecture.** CEF requires separate helper executables. The package builds two (`CEFHelper`, `CEFHelperRenderer`); the demo app's `WebView/Scripts/embed_cef_helpers.sh` embeds **three helper `.app` bundles** under `Contents/Frameworks/` (`WebView Helper.app`, `WebView Helper (GPU).app`, `WebView Helper (Renderer).app`) alongside `Chromium Embedded Framework.framework`, and **signs each one individually** with entitlements (`codesign --options runtime`). For Batty that is a real change to `scripts/release.sh` (a restricted area): per-helper signing, plus a post-embed symlink repair step (`fix_cef_framework.sh` — Xcode's Embed Frameworks phase expands the framework's symlinks into copies).
- **Entitlements and notarization — the prominent flag.** `JIT.md` documents three required entitlements: `com.apple.security.cs.allow-jit`, `com.apple.security.cs.allow-unsigned-executable-memory`, and `com.apple.security.get-task-allow`, and instructs applying them to **both Debug and Release**. The repo does exactly that: the demo app's `Configuration/Build.xcconfig` sets `CODE_SIGN_ENTITLEMENTS` unconditionally for all configurations, and `embed_cef_helpers.sh` bakes all three (including `get-task-allow`) into every helper, signed with `--timestamp=none`. **`get-task-allow` is a debug-only entitlement — Apple's notary service rejects submissions that carry it** (and `--timestamp=none` signatures are likewise non-notarizable). CEFWebView's documented configuration is therefore a *development* configuration, not a shippable one; a shipping Batty would have to drop `get-task-allow`, use timestamped Developer ID signing, and verify CEF's helper IPC still works without it — unproven in this repo. The two JIT entitlements would remain and genuinely weaken Batty's Hardened Runtime posture (arbitrary W+X memory in a notarized app); Batty is already unsandboxed (`ENABLE_APP_SANDBOX = NO`, deployment target 15.6, confirmed in `Configuration/Build.xcconfig`) with Hardened Runtime kept on precisely for notarization, so this is a real posture trade-off to state plainly.
- **Maintenance.** CEF must be tracked against Chromium's release cadence, including security updates — an embedded browser that lags Chromium is a liability. Batty currently has exactly one heavy native dependency (libghostty via the `brennanMKE/libghostty-spm` fork); this would be a second, larger, faster-moving one.
- **Maturity.** The README says, in full: "A work in progress." What works: the Swift package builds a `CEFWebView` `NSViewRepresentable` + `@Observable CEFWebViewState` over an ObjC++ `CEFWrapper` bridging the CEF **C++** API (`CefRefPtr` ref-counting, not the C API); Swift 6, macOS 15+, `defaultIsolation(MainActor.self)` — conventions that happen to match Batty's. What does not: the public API is navigation-only (load URL, back/forward/reload, title/URL/progress/loading state) — no JS evaluation, no CDP, no screenshots; the guide's Known Issues list "Renderer Process Not Spawning" as *Under Investigation* (blank pages), and `CEFWebViewState` carries a `rendererHelperFailed` flag to surface that failure in the demo UI; code signing is "Needs Testing" and notarization is an open TODO. The agent-facing capability that motivates this ticket is precisely the part not yet built.

## Model and architecture questions (to frame, not answer here)

- **Where does a web view live in the model?** Per `Concepts.md`, a Tab *is* a Terminal Session — "Each Tab owns exactly one Terminal Session," one-to-one, born and torn down together. Would a web view be a new kind of Tab, a new kind of Pane, or something else entirely? The layout model is pure `Codable`/`Sendable` value types (`Session`, `Pane`, `Tab`, `SplitNode`) with no view or libghostty types embedded — adding a non-terminal variant is a **Workspace persistence format change**, not a UI tweak.
- **View hierarchy.** `docs/view-hierarchy.md` describes the persistent AppKit terminal host and the surface-registry rule: SwiftUI stores only `surfaceID: UUID`, and view rebuilds must never destroy surfaces. A CEF `NSView` (with live helper subprocesses behind it) needs an equivalent persistence story. Does the existing host generalize to non-terminal views, or is a parallel registry required?
- **Terminal pane requirements.** `docs/terminal-pane-requirements.md` constrains what can be added to the pane area (pointer input, keyboard, drops, IME, AppKit z-order). A second heavyweight native view in the split tree must be checked against it — the #0143 regressions are the cautionary example.

## The CLI / agentic angle (the actual motivation)

Sketches for discussion in the #0257 `batty <noun> <verb>` grammar — **not** a pinned surface:

```
batty web open <url>       # open a URL in an embedded web view
batty web eval <js>        # evaluate JS, return the result
batty web read             # DOM / text contents
batty web screenshot       # capture the rendered page
```

**The critical sequencing fact:** every useful browser-automation verb is a **read** — DOM contents, evaluation results, screenshots. #0257 Foundation §5 pins Tier 0/1 as one-way fire-and-forget `batty://` URLs with **no response channel**, deferring all live reads to Tier 3. A scriptable browser is therefore **blocked on the two-way transport being evaluated in #0265** (XPC vs Unix socket). This work cannot start before #0265 concludes; only `web open` would even function over the one-way channel.

**The honest alternative an agent already has today:** Playwright, Puppeteer, or `curl` running in a normal Batty pane, driving a real browser out-of-process — full CDP, zero Batty changes, zero bundle weight. The decision record must ask what an *embedded* view adds over that. The likely answer — "the user can see and interact with what the agent is doing, in the same window" — is real, but it has to be weighed against the entire cost inventory above.
