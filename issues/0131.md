## Description

The current Cmd-1…9 / Cmd-Option-1…9 assignment feels backwards for most workflows:

| Shortcut | Current | Preferred default |
|---|---|---|
| Cmd-1…9 | Jump to tab N in focused pane | Jump to session N |
| Cmd-Opt-1…9 | Jump to session N | Jump to tab N in focused pane |

Sessions are the primary navigation unit (sidebar, one per project/context). Tabs are secondary within a pane. The lighter shortcut (Cmd-1…9, no Option) should go to the more-used target.

Add a binary preference in Settings → General (or a dedicated Shortcuts area) — **"Cmd-1…9 switches: Sessions / Tabs"** — that swaps the two sets of bindings. Default: Sessions.

## Acceptance criteria

- Default behavior: Cmd-1…9 jumps to session N (currently Cmd-Opt-1…9 behavior); Cmd-Opt-1…9 jumps to tab N in the focused pane (currently Cmd-1…9 behavior).
- A `UserDefaults`-backed preference controls which target Cmd-1…9 addresses. The other set (Cmd-Opt-1…9) automatically takes the opposite target — no need to expose it separately.
- The preference is surfaced in Settings as a picker or toggle with clear labels ("Sessions" / "Tabs").
- Both sets of shortcuts update live when the preference changes — no restart required.
- The menu items in the Session and Tab menus reflect the active bindings (show the correct modifier in the label or via `.keyboardShortcut`).

## Root cause

The two `ForEach` blocks in `BattyCommands.swift` had their modifier sets hardcoded — `.command` for tabs and `[.command, .option]` for sessions — with no preference to swap them.

## Fix

- Added `CmdNumberTarget` enum (`sessions` / `tabs`) and `cmdNumberTargetKey` to `SettingsPreferences.swift`. Default is `sessions`.
- Added a "Keyboard" section to `GeneralSettingsView` in `SettingsView.swift` with a segmented `Picker` bound to the preference via `@AppStorage`.
- Added `@AppStorage(SettingsPreference.cmdNumberTargetKey)` to `BattyCommands` and a `cmdNumberSwitchesSessions` computed property. Both `ForEach` blocks now pick their `EventModifierFlags` from that property, so the menu bar shortcuts update live when the preference changes.

## Files changed

- `BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift` — added `cmdNumberTargetKey`, `defaultCmdNumberTarget`, `CmdNumberTarget` enum, and registered the default
- `BattyKit/Sources/BattyKit/Views/SettingsView.swift` — added `@AppStorage` binding and "Keyboard" section to `GeneralSettingsView`
- `BattyKit/Sources/BattyKit/Commands/BattyCommands.swift` — added `@AppStorage` binding, `cmdNumberSwitchesSessions` computed property, and dynamic modifier sets in both `ForEach` blocks

## Gotchas

- `@AppStorage` in `Commands` structs updates live because SwiftUI re-evaluates `body` on storage changes, so the menu bar items pick up the new `.keyboardShortcut` without a restart.
- UI sign-off (verifying the Settings picker and menu shortcuts in a running app) not done headlessly.

## Notes

- The two ForEach blocks are in `BattyKit/Sources/BattyKit/Commands/BattyCommands.swift`: session switching at line 45–53 (Cmd-Opt-1…9) and tab switching at lines 191–199 (Cmd-1…9). Swapping them is the mechanical change; the preference gate wraps the modifier set.
- A `UserDefaults` key like `"cmdNumberTarget"` with values `"sessions"` / `"tabs"` (or a `Bool`) is sufficient. A small `@AppStorage`-backed enum in a new `CmdNumberPreference.swift` would keep it clean.
- The preference should live alongside the other general preferences (font, cursor, etc.) in the Settings window, not buried in the Shortcuts recorder — it's a mode switch, not a keybinding.
- These shortcuts are currently hardcoded in `BattyCommands.swift`, not in `ShortcutAction`, so no changes to `ShortcutsStore` are needed unless the decision is made to make them fully remappable (out of scope here).

## Re-opened

**Reported by user 2026-05-18:** the Settings → General → Keyboard picker is visible and the segmented control flips between "Sessions" and "Tabs," but the actual shortcut behavior does not change. Cmd-1…9 keeps doing whatever it was doing on launch regardless of the picker state.

The original `## Gotchas` section claimed `@AppStorage` in a `Commands` struct would cause SwiftUI to re-evaluate `body` and pick up the new `.keyboardShortcut` modifier on the menu bar items live. That assumption appears to be wrong in practice — `Commands` is a SwiftUI scene-modifier protocol, not a `View`, and the menu/key-equivalent registration with AppKit's `NSMenu` happens once at scene-construction time. Recomputing `body` on a `Commands` may not actually re-register the global key equivalents with AppKit's menu system.

**Fix direction:**

- Verify the actual symptom first — run in Xcode, set the picker, then `defaults read com.batty.app cmdNumberTarget` (or whatever the key is) to confirm `@AppStorage` is at least writing. If it is, the bug is in how `Commands` reacts; if it isn't, the picker binding is broken.
- If `Commands.body` re-evaluation does not flow through to the menu bar's `NSMenu` key equivalents, the cleanest workaround is to read the preference at command-dispatch time rather than baking it into the `.keyboardShortcut` modifier — i.e., keep both Cmd-N and Cmd-Opt-N bound, and have each command's action check the preference and decide whether to operate on the session at index N or the tab at index N. That way the binding registration doesn't need to update; only the action body does.
- Alternatively (heavier), drive the menu re-registration explicitly when the preference changes — observe `UserDefaults.didChangeNotification` and call into `NSApp.mainMenu` to update the affected items' key equivalents. Avoid if option 1 works.
- Whichever approach, the resolution must satisfy the original acceptance criterion **"Both sets of shortcuts update live when the preference changes — no restart required."** No restart-to-apply workarounds.

## Re-resolution

The v1 `## Gotchas` claim that `@AppStorage` in a `Commands` struct would cause SwiftUI to re-evaluate `body` and re-register `NSMenu` key equivalents was at most half-right — even if `body` does recompute, the menu-bar registration was never the load-bearing path. Per `docs/shortcuts.md` (Section 3), Batty installs an `NSEvent.addLocalMonitorForEvents(matching: .keyDown)` in `BattyAppDelegate.applicationDidFinishLaunching` whose handler — `BattyShortcuts.handle(_:)` — runs *before* menu-bar key-equivalent dispatch. Its positional-binding `switch` on `(mods, chars)` hardcoded `[.command]` → "select tab N" and `[.command, .option]` → "select session N" and consumed the event, so the SwiftUI menu items were never reached regardless of which modifier set they were registered with. The v1 fix flipped the `.keyboardShortcut(...)` modifiers on the menu items but left the NSEvent monitor unchanged, which is exactly the symptom the user reported: the picker flips, the menu labels likely update, but Cmd-1…9 keeps doing whatever the monitor was hardcoded for.

Fixed `BattyShortcuts.handle(_:)` to read `co.sstools.Batty.cmdNumberTarget` from `UserDefaults` at dispatch time (via a new `currentCmdNumberTarget()` helper) and pick the session-N vs tab-N code path accordingly. Both `Cmd-N` and `Cmd-Opt-N` stay permanently bound — only the action body branches on the preference — so no re-registration is required and the swap takes effect on the very next keystroke after the picker is flipped. The dynamic `.keyboardShortcut(...)` modifiers in `BattyCommands.swift` from the v1 fix are kept as-is so the menu-bar labels also reflect the user's choice; the only change in this round is the `Commands/BattyShortcuts.swift` file and a documentation refresh in `docs/shortcuts.md`.

### Files changed

- `BattyKit/Sources/BattyKit/Commands/BattyShortcuts.swift` — positional `Cmd-1…9` / `Cmd-Opt-1…9` switch branches now read the preference at dispatch time and pick session-N vs tab-N accordingly; added `currentCmdNumberTarget()` helper that reads `SettingsPreference.cmdNumberTargetKey` from `UserDefaults`.
- `docs/shortcuts.md` — updated the "Fixed combos" table to reflect that Cmd-1…9 now defaults to sessions (with the Settings preference swap noted) and added a short paragraph explaining the dispatch-time read.

### Gotchas

- The shortcut path actually fires from `BattyShortcuts.handle(_:)`, not from `BattyCommands` `.keyboardShortcut(...)` modifiers. Anyone editing positional Cmd-1…9 / Cmd-Opt-1…9 behavior should change `BattyShortcuts.handle(_:)` first — the menu items in `BattyCommands.swift` are for menu-bar label / discoverability and would otherwise look out of sync.
- No unit test was added for the dispatch logic: `BattyShortcuts.handle(_:)` takes an `NSEvent` and pokes a live `AppStateStore` through `WorkspaceManager.shared.store`, which is heavy to mock. The dispatch-time preference read is a one-liner against `UserDefaults.standard`, already exercised by the existing acceptance behavior.
- Not verified headlessly: the actual live behavior swap (flipping the picker and confirming the next Cmd-1 selects a session vs. a tab) and the menu-bar label correctness (whether the menus show Cmd-1 / Cmd-Opt-1 next to the correct items after a flip). Both want interactive sign-off before this moves to `closed`.
