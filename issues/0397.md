## Description

**Verdict up front, because it decides this issue's priority: the crash is test-only. Desktop notifications and the Bell Feed keep working at runtime under the new pin** — with high confidence from source reading (the residual caveat is in Notes). This is not a release blocker for #0389; it is a hard gate on `./build.sh unit`, which is this project's pre-commit and review-verification command, so #0389 cannot land until it is fixed.

#0389's branch (`issue/0389`, commit `f852244`, unmerged) re-pins `Lakr233/libghostty-spm` in `BattyKit/Package.swift:32` from revision `b146b73` (tag `1.3.2`) to `a2565cc` (tag `1.5.20260903`). `./build.sh` succeeds, but `./build.sh unit` then dies with `Fatal error: Unexpectedly found nil while unwrapping an Optional value` at `store.bellFeed.entries.first!` — `BattyKit/Tests/BattyKitTests/BellNotificationSummaryTests.swift:200` or `:285` depending on the run. The dying xctest host then drags ~1271 tests into the failure report; that count is an artifact of the dead host, not real failures. The implementer's controlled comparison (session observation, not reproducible from source): new pin, 4/4 runs crash (3 dirty builds + 1 clean); old pin restored on the same branch, clean build, 1291 tests in 146 suites pass with no crash.

**Mechanism — found in the fork's Swift wrapper, not in the vendored Ghostty core.** Between the two pinned revisions, libghostty-spm commit `62874a2` ("Publish every observable change on the next turn, not only the grid size", 2026-08-29, extending `30b93c0`) rewrote `Sources/GhosttyTerminal/State/TerminalViewState+Delegate.swift` so that every `@Published` mutation routes through a `publishSoon` helper (`TerminalViewState+Delegate.swift:51` at `a2565cc`) that defers the write via `terminalRunOnMainNextTurn` (`Sources/GhosttyTerminal/Platform/Shared/TerminalMainActor.swift:37-45`) — an unconditional `DispatchQueue.main.async`, **never inline, even when already on the main thread**. The fork did this to stop "Publishing changes from within view updates is not allowed" when callbacks land inside a SwiftUI layout pass (the file's own doc comment, `:25-50`). Concretely:

- Old pin (`b146b73`): `terminalDidRequestDesktopNotification` sets `lastDesktopNotificationAt` synchronously (`TerminalViewState+Delegate.swift:44-48`); `terminalDidRingBell` bumps `bellCount` synchronously (`:39-42`).
- New pin (`a2565cc`): the same callbacks capture `Date()` and defer the writes one main-queue turn (`TerminalViewState+Delegate.swift:88-94` for the bell, `:97-104` for the notification).

The crashing sequence in the tests is synchronous call-then-read:

```swift
tab.terminal.terminalDidRequestDesktopNotification(title: "CI", body: "passed")
store.recordDesktopNotification(forTabID: tab.id)
let entryID = store.bellFeed.entries.first!.id   // traps under the new pin
```

`recordDesktopNotification` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:1368`) guards on `location.tab.recordDesktopNotificationIfNeeded()` (`:1373`), which reads `terminal.lastDesktopNotificationAt` (`BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:278`). Under the new pin that property (`@Published public internal(set)`, `Sources/GhosttyTerminal/State/TerminalViewState.swift:23`) is still `nil` at read time — the write is sitting in the main queue — so the guard returns without recording an entry, and the force-unwrap on the next line traps.

**Both crash sites share this one root cause.** `:200` (`summarizationRunsWhenToggleOn`) and `:285` (`summaryUpdatesCorrectEntry`) are the only two force-unwraps in the file; which one fires first depends on Swift Testing's execution order, which is why the reported line alternates between runs. The crash is deterministic because the trap happens synchronously, before any suspension point could let the deferred publish land.

## Why this is test-only, not user-facing

Production never performs the call-then-read sequence. The **only** production trigger for `recordDesktopNotification` is the view observing the published property itself: `.onChange(of: tab.terminal.lastDesktopNotificationAt)` at `BattyKit/Sources/BattyKit/Views/PaneView.swift:250-256` — and bells identically via `.onChange(of: tab.terminal.bellCount)` at `:243-249`. The read is causally *downstream* of the publish: `onChange` cannot fire until the deferred write has landed, at which point `recordDesktopNotificationIfNeeded` reads a non-nil value. The one-turn deferral therefore delays the Bell Feed entry, the posted macOS notification, and the #0246 summarization kickoff by one main-queue turn (imperceptible) but cannot skip them. The only other caller of the delegate methods in Batty is `TerminalDelegateProxy` (`BattyKit/Sources/BattyKit/Runtime/TerminalDelegateProxy.swift:61-63`), a pure forwarder from libghostty's surface callbacks into the same `TerminalViewState` — it never reads back. The CLI `notify` path (#0284, `recordCLINotification`) does not touch `TerminalViewState` at all.

Note also which half of the dependency moved: the vendored Ghostty core ref advance (`Ghostty.ref` `35e1a01` → `c4e16970a`, the 993-commit jump #0390 documents) is **not** the mechanism — no C-API or callback-timing change from Ghostty itself is involved. The break lives entirely in the fork's Swift wrapper commit `62874a2`, which happens to ride along with the same tag. The test was relying on a synchronous-publish ordering that was never a documented contract, and the wrapper withdrew it.

## The blast radius is wider than the two crash sites

The call-a-delegate-method-then-read-synchronously pattern is the standard fixture idiom across BattyKitTests. `grep -rl 'terminalDidRingBell\|terminalDidRequestDesktopNotification\|terminalDidChangeTitle\|terminalDidChangeWorkingDirectory\|terminalDidFinishCommand' BattyKit/Tests/BattyKitTests/` matches **12 files**: `AppStateStoreBellCollapseTests`, `AppStateStoreBellDecisionHistoryTests`, `AppStateStoreClosePaneTests`, `BellFeedCleanupTests`, `BellFeedStoreTests`, `BellNotificationSummaryTests`, `CrossWindowBehaviorTests`, `MarkActiveTabSeenTests`, `SessionMuteTests`, `TabAutoNamingTests`, `TabRuntimeBellTests`, `TabRuntimeRunningCommandTests`. Under the new pin every synchronous call-then-read in those files reads stale state; whether each individual test crashes, fails, or silently passes depends only on how it asserts. Within `BellNotificationSummaryTests` alone:

- `:200` and `:285` trap (force-unwrap).
- `:165`, `:185`, `:233`, `:255` go **vacuous** — `#expect(store.bellFeed.entries.first?.summary == nil)` passes with zero entries, so the "skipped/dropped summarization" tests stop testing anything.
- `:320` (`bellTickSummarizationAlsoRuns`) genuinely fails: the deferred `bellCount` publish lands during the test's yield loop, but nothing calls `recordBellTick` a second time (production relies on `onChange` for that), so no entry ever records.

This matters for the fix: **deleting the two force-unwraps would convert a loud, honest crash into silent loss of coverage across a dozen files.** The real defect is that the fixtures encode an ordering contract the dependency no longer offers.

## Expected behavior

`./build.sh unit` passes under the `1.5.20260903` pin with the bell/notification suites still exercising what they exercise today — no vacuous passes, no force-unwrap traps — so #0389 can proceed to review. No production behavior change is required by this issue; if the implementer finds evidence contradicting the test-only verdict above (see Notes for the one unverified caveat), that discovery upgrades this to a release blocker and should be recorded here prominently before anything else.

## Candidate directions (deliberately not decided here)

Like [#0332](0332.md) and [#0395](0395.md), this asks for the property, not a mechanism. Candidates, with trade-offs:

- **Drain the deferral in tests**: a shared test helper that, after invoking a delegate callback, awaits one main-queue hop (e.g. `await withCheckedContinuation { c in DispatchQueue.main.async { c.resume() } }`) before the read/record step. Smallest conceptual change and keeps the real callback path under test; touches fixture code in up to 12 files, and encodes the wrapper's "one turn" implementation detail — if the fork ever defers by two turns, the suites break again the same way.
- **Stop calling the delegate methods from fixtures** — set the observable state directly and treat the delegate methods as the fork's own concern. Blocked as stated: the properties are `public internal(set)` inside `GhosttyTerminal` (`TerminalViewState.swift:18-23`), so BattyKit tests cannot write them without fork cooperation (a testing seam upstream) or a Batty-side wrapper layer over `TerminalViewState`. The wrapper layer is the bigger, more durable version of this: Batty's runtime would own the state Batty's tests need to fabricate.
- **Drive `recordBellTick`/`recordDesktopNotification` from a Combine subscription in the runtime layer instead of `PaneView`'s `.onChange`** — then tests and production share one trigger path, and a test that publishes (even deferred) gets the record for free once it yields. There is direct precedent: `TerminalDelegateProxy.onWorkingDirectoryChange` exists because the `.onChange`-over-`@Published` path "fired only opportunistically" for working-directory updates (`TerminalDelegateProxy.swift:29-36`, #0227). Trade-offs: this is a change to bell/notification production wiring to fix a test problem, it must respect `docs/swiftui-observation-rules.md` (the #0229 lesson about write ownership), and it widens #0389's diff or becomes a prerequisite issue.
- **Patch the fork to publish inline when safe** (e.g. only defer when actually inside a view update, or expose a synchronous test hook). Rejected-by-default: the pin targets an upstream release tag, #0390 already established that fork divergence ships as PR material, and the fork's own doc comment (`TerminalViewState+Delegate.swift:25-50`) argues one blanket rule over per-callback judgement — upstream is unlikely to take it back.

Whichever direction wins, it should also un-vacuate the four assertions listed above (assert an entry *exists* before asserting on its summary), so the coverage this file was built for in #0246 survives.

## Notes

- **The one unverified caveat on the test-only verdict**: the conclusion rests on reading every production consumer of `lastDesktopNotificationAt`/`bellCount` on `main`, not on exercising OSC 9 in a running Beta build against the new pin. #0389's branch did run a fork-built Beta for its footprint measurement (`0d12764`), but nothing in its notes says bells or desktop notifications were exercised. A 30-second manual check (`printf '\e]9;hello\a'` in a Beta pane under the new pin, watch the Bell Feed) during #0389's or this issue's verification would close it completely.
- **Prior flake history: could not be established.** Reports exist from earlier subagent sessions that `BellNotificationSummaryTests` / `NotificationSummaryTests` intermittently aborted on the *old* pin, which would recast the new pin as making a latent race deterministic. The repo holds no evidence either way: no comments in the test file, no issue mentions (`grep -rl NotificationSummary issues/` hits only `0246.md` and `0395.md`), no commits touching the file since it landed (`12d4b55`, its only commit). Mechanically, the old pin's synchronous writes cannot produce *this* trap; if old-pin aborts were real they had a different cause. One candidate worth a look but **unconfirmed speculation**: several suites in this file `set`/`removeObject` the same `SettingsPreference.summarizeNotificationsWithAIKey` in `UserDefaults.standard` (e.g. `:79`, `:173`, `:193`, `:220`), and Swift Testing runs tests concurrently — a cross-test race there could produce intermittent assertion failures, though not a nil-unwrap crash.
- **#0395's classification stands.** It lists `BellNotificationSummaryTests.swift:332,:347` under "Not implicated — `Date()` as plain data, fully deterministic"; those lines are `BellFeedStoreUpdateSummaryTests` fixture timestamps and remain harmless. This issue is a different mechanism entirely: deterministic publish-ordering, not load-dependent wall clock. Zero overlap in fix territory.
- **#0246's Foundation Models path is incidental.** The crash happens before any summarizer runs, and the suites use the `RecordingSummarizer` double throughout — the on-device model is never invoked in unit tests. #0246 merely authored the only two force-unwraps in the tree that read the Bell Feed synchronously after a delegate call.
- The line numbers `:200`/`:285` and the 4/4-vs-0 comparison come from the implementer session on `issue/0389`; the filer verified the crash sites are the file's only `first!` reads and traced the mechanism from source, but did not run `./build.sh unit` against the new pin (doing so requires checking out the unmerged branch). All `file:line` citations are against `main` (Batty) and the two pinned revisions of `~/Developer/brennanMKE/libghostty-spm` as noted.
- The old pin's `Ghostty.ref` is `35e1a0160c4f6797e1bb1ef8e7a2b8c6b114ab58` (per the fork repo and #0390), superseding the `332b2ae`-era shorthand used in the session report.
