## Description

`CURRENT_PROJECT_VERSION` (the integer build number Sparkle compares against) is currently set by hand in `Configuration/App.xcconfig`. Forgetting to bump it before a release ships a DMG whose `CFBundleVersion` matches the previous release's — exactly what happened with `1.0.1`, which carried the same `build = 1` as `1.0.0` and therefore couldn't be offered as an auto-update through Sparkle (Sparkle ranks items by `sparkle:version`, not by `sparkle:shortVersionString`).

Rather than relying on a manual bump every release, derive the build number automatically from today's date in `YYYYMMDD` form when `scripts/release.sh` runs. The value is monotonically increasing, human-readable, never collides with the prior release, and is independent of the marketing version.

## Acceptance criteria

- `scripts/release.sh` computes `BUILD_NUMBER="$(date -u +%Y%m%d)"` at the start of the build phase and passes `CURRENT_PROJECT_VERSION=$BUILD_NUMBER` to `xcodebuild archive`. The override beats the static value in `App.xcconfig` for release archives.
- `Configuration/App.xcconfig` keeps a static `CURRENT_PROJECT_VERSION` value (any small integer is fine — used only by Xcode-driven Debug builds, which Sparkle never sees).
- The release script prints the computed build number at the end of its run alongside the DMG path, so the operator can paste it into `website/appcast.xml` as `sparkle:version`.
- `scripts/RELEASE.md` documents the convention: "MARKETING_VERSION is the marketing version (e.g. 1.0.2); CURRENT_PROJECT_VERSION is auto-derived from today's date as YYYYMMDD by release.sh — do not bump it by hand."
- `xcodebuild -scheme Batty -destination 'platform=macOS' build` (Debug, no override) still passes with the static value from `App.xcconfig`.
- A dry run of `scripts/release.sh` proves the build number lands in `Batty.app/Contents/Info.plist` correctly. (Not part of the commit; a manual smoke step the user does when cutting 1.0.2.)

## Out of scope

- Generating a separate committed `Configuration/Version.xcconfig` for tag-time reproducibility. The shipped artifact is the immutable record; tag reproducibility isn't a requirement here.
- Same-day re-release collision handling. If two releases ever go out on the same UTC day, both report the same `YYYYMMDD` and Sparkle won't offer the second to users on the first. Handle when it actually happens — likely via `date -u +%Y%m%d%H%M` for that one-off, or a per-day counter.
- Adding a `preflight.sh` gate that warns when the build number would collide with the prior tagged release. Useful, but tracked separately.
- Updating the 1.0.0 / 1.0.1 historical state. 1.0.1 is already tagged; the auto-derived scheme starts with 1.0.2.

## Notes

- Apple's `CFBundleVersion` docs say "should consist of three non-negative period-separated integers" but in practice a single integer is universally accepted; many shipping apps use a single integer. Sparkle's documentation assumes single-integer build numbers.
- `YYYYMMDD` (e.g. `20260514`) fits comfortably in 32-bit signed int (max ~2.1B; `YYYYMMDD` max is ~2.5M years out). No overflow concerns.
- Override applies only to the release archive command in `scripts/release.sh`. Debug builds invoked from Xcode use the static xcconfig value — fine because Sparkle is never consulted from a Debug build.
- This pairs naturally with the 1.0.2 release: the user has other improvements to bundle before cutting it, and this convention can land first.

## Root cause

`CURRENT_PROJECT_VERSION` lived as a static value in `Configuration/App.xcconfig` and required a manual edit before each release. When 1.0.1 was cut, the marketing version was bumped (`MARKETING_VERSION = 1.0.0 → 1.0.1`) but the build number was not. Both 1.0.0 and 1.0.1 shipped with `CFBundleVersion = 1`. Sparkle ranks appcast items by `sparkle:version` (an integer build number, mapped from `CFBundleVersion`), not by `sparkle:shortVersionString`, so it treated the 1.0.1 item as "same build" and never offered the update to 1.0.0 users.

## Fix

`scripts/release.sh` now computes `BUILD_NUMBER="$(date -u +%Y%m%d)"` at the start of the build phase and passes it to `xcodebuild archive` via a command-line override (`CURRENT_PROJECT_VERSION=$BUILD_NUMBER`). Xcode's command-line settings beat xcconfig values, so the release archive gets today's date as its build number regardless of what `App.xcconfig` says. Debug builds invoked from Xcode keep reading the static xcconfig value — fine because Sparkle is never consulted from a Debug build.

The script prints the computed build number alongside the final DMG path so the operator can paste it into `website/appcast.xml` as `sparkle:version` without having to read it back from the bundle.

`scripts/RELEASE.md` step 1 was rewritten to make the convention explicit: bump `MARKETING_VERSION` by hand, but **do not** bump `CURRENT_PROJECT_VERSION` — it's auto-derived. Step 6 was updated to point at the script's printed output as the canonical source of `sparkle:version`.

## Files changed

- `scripts/release.sh` — computes `BUILD_NUMBER` from `date -u +%Y%m%d`, passes it as `CURRENT_PROJECT_VERSION` on the `xcodebuild archive` command line, prints the build number with the final DMG path.
- `scripts/RELEASE.md` — step 1 documents that `CURRENT_PROJECT_VERSION` is auto-derived and not to be touched by hand; step 6 points at the script's output for `sparkle:version`.

## Gotchas

- **Same-day re-releases collide.** Two builds on the same UTC day both report the same `YYYYMMDD` and Sparkle won't offer the second to users on the first. Mitigation when it happens: switch to `date -u +%Y%m%d%H%M` for that one-off release, or append a per-day counter. Not worth handling preemptively.
- **`CFBundleVersion` format.** Apple's docs say "three non-negative period-separated integers," but a single integer is universally accepted in practice and Sparkle's documentation assumes it. `YYYYMMDD` is a single integer ~20M, well inside 32-bit signed.
- **Static value in `App.xcconfig` is unchanged** (`CURRENT_PROJECT_VERSION = 1`). It's a Debug-build placeholder now; any value would do. Left as-is so the file diff stays minimal.
- **Verified by build, not by full release pipeline.** A Debug `xcodebuild build` passed using the static xcconfig value (confirming Debug still works). A full `scripts/release.sh` run hasn't been done from this commit yet; that will happen when the 1.0.2 release is cut, at which point the operator should confirm `Info.plist`'s `CFBundleVersion` matches today's `YYYYMMDD`.
- **`scripts/tag-release.sh` and `scripts/preflight.sh` are unchanged.** They only inspect `MARKETING_VERSION`, which is still hand-bumped. There's a stale comment in `tag-release.sh:3` and a stale `Build.xcconfig` reference in `RELEASE.md:136` (both for `MARKETING_VERSION`); those are pre-existing documentation drift unrelated to this fix and should be cleaned up separately.
