# 0124 — Auto-derive CURRENT_PROJECT_VERSION from today's date in scripts/release.sh

| | |
|---|---|
| **Status** | open |
| **Module** | Build |
| **Platform** | macOS |
| **First seen** | 2026-05-14 |

## Description

`CURRENT_PROJECT_VERSION` (the integer build number Sparkle compares against) is currently set by hand in `Configuration/App.xcconfig`. Forgetting to bump it before a release ships a DMG whose `CFBundleVersion` matches the previous release's — exactly what happened with `1.0.1`, which carried the same `build = 1` as `1.0.0` and therefore couldn't be offered as an auto-update through Sparkle (Sparkle ranks items by `sparkle:version`, not by `sparkle:shortVersionString`).

Rather than relying on a manual bump every release, derive the build number automatically from today's date in `YYYYMMDD` form when `scripts/release.sh` runs. The value is monotonically increasing, human-readable, never collides with the prior release, and is independent of the marketing version.

## Acceptance criteria

- `scripts/release.sh` computes `BUILD_NUMBER="$(date -u +%Y%m%d)"` at the start of the build phase and passes `CURRENT_PROJECT_VERSION=$BUILD_NUMBER` to `xcodebuild archive`. The override beats the static value in `App.xcconfig` for release archives.
- `Configuration/App.xcconfig` keeps a static `CURRENT_PROJECT_VERSION` value (any small integer is fine — used only by Xcode-driven Debug builds, which Sparkle never sees).
- The release script prints the computed build number at the end of its run alongside the DMG path, so the operator can paste it into `website/appcast.xml` as `sparkle:version`.
- `scripts/RELEASE.md` documents the convention: "MARKETING_VERSION is the marketing version (e.g. 1.0.2); CURRENT_PROJECT_VERSION is auto-derived from today's date as YYYYMMDD by release.sh — do not bump it by hand."
- `xcodebuild -scheme Batty -destination 'platform=macOS' build` (Debug, no override) still passes with the static value from `App.xcconfig`.
- A dry run of `scripts/release.sh` proves the build number lands in `Batty.app/Contents/Info.plist` correctly. (Not part of the commit; a manual smoke step the user does when cutting 1.0.2.)

## Out of scope

- Generating a separate committed `Configuration/Version.xcconfig` for tag-time reproducibility. The shipped artifact is the immutable record; tag reproducibility isn't a requirement here.
- Same-day re-release collision handling. If two releases ever go out on the same UTC day, both report the same `YYYYMMDD` and Sparkle won't offer the second to users on the first. Handle when it actually happens — likely via `date -u +%Y%m%d%H%M` for that one-off, or a per-day counter.
- Adding a `preflight.sh` gate that warns when the build number would collide with the prior tagged release. Useful, but tracked separately.
- Updating the 1.0.0 / 1.0.1 historical state. 1.0.1 is already tagged; the auto-derived scheme starts with 1.0.2.

## Notes

- Apple's `CFBundleVersion` docs say "should consist of three non-negative period-separated integers" but in practice a single integer is universally accepted; many shipping apps use a single integer. Sparkle's documentation assumes single-integer build numbers.
- `YYYYMMDD` (e.g. `20260514`) fits comfortably in 32-bit signed int (max ~2.1B; `YYYYMMDD` max is ~2.5M years out). No overflow concerns.
- Override applies only to the release archive command in `scripts/release.sh`. Debug builds invoked from Xcode use the static xcconfig value — fine because Sparkle is never consulted from a Debug build.
- This pairs naturally with the 1.0.2 release: the user has other improvements to bundle before cutting it, and this convention can land first.
