## Description

When the user types `exit` at the shell prompt (or hits Ctrl-D on an empty prompt, or the shell otherwise terminates cleanly), libghostty's surface fires its close callback but Batty keeps the surface and its containing tab/pane on screen. The user is left looking at a dead terminal with the shell's `[Process completed]`-style banner and has to manually `Cmd-W` or click the chip × to close it.

Convention across other terminal apps:

- **Terminal.app** — has a "When the shell exits" preference: *Close the window*, *Close if the shell exited cleanly*, or *Don't close the window*. Default is "Close if the shell exited cleanly."
- **iTerm2** — same set of options, with the same default.
- **Ghostty** — closes the surface immediately when the shell exits.
- **Alacritty / kitty** — close immediately.

The user wants Batty to do the obvious thing: when the shell exits, close the tab (and cascade into pane/session cleanup the way `Cmd-W` already does).

## Steps to reproduce

1. Open Batty. In any tab, type `exit` and hit Enter.
2. **Observed:** the shell exits, the terminal shows `Saving session…/[Process completed]`-style output, the tab and pane stay on screen indefinitely.
3. **Expected:** the tab closes immediately. If it was the only tab in the pane, the pane closes. If it was the only pane in the session, the session closes (matching the existing `AppStateStore.closeTab(id:)` cascade).

## Expected behavior

When a tab's terminal surface fires its close signal:

1. Close the tab via the existing `AppStateStore.closeTab(id:)` path so the cascade (last-tab → remove pane → last-pane → remove session → empty-store → restore default session) runs as it does for any other close.
2. No confirmation dialog. The user explicitly exited the shell; that's their confirmation.
3. If the user was viewing the tab when it closed, focus jumps to whatever `pane.removeTab` selects next (already correct behavior).

Match Terminal.app's safer default: **close on clean exit; close on any exit** is fine for v1 (Ghostty's default). If we ever want a "Don't close" preference, add it under Settings later — defer until asked.

The `processAlive: Bool` parameter that `TerminalSurfaceCloseDelegate` passes through is interesting but not load-bearing for v1: a true value would mean libghostty is closing the surface while a process is still running (e.g., a future "force close busy tab" path from `#0054`). For v1 we close regardless of `processAlive` — the user-visible behavior is identical.

## Actual behavior

`TerminalSurfaceCloseDelegate.terminalDidClose(processAlive:)` fires and is wired through to `TerminalViewState.onClose: ((Bool) -> Void)?` (callback property on the state). Nothing in Batty sets that callback. The surface stays alive in the view tree showing whatever output the shell printed before it exited.

## Notes

### Detection signal (already available)

The fork (`brennanMKE/libghostty-spm` on branch `batty-delegates`) already exposes the signal we need:

```swift
// in TerminalSurfaceViewDelegate.swift
public protocol TerminalSurfaceCloseDelegate: TerminalSurfaceViewDelegate {
    func terminalDidClose(processAlive: Bool)
}

// in TerminalViewState.swift
public var onClose: ((Bool) -> Void)?

// in TerminalViewState+Delegate.swift
public func terminalDidClose(processAlive: Bool) {
    onClose?(processAlive)
}
```

So this is **not blocked on a fork change** — unlike `#0054`, which would need a separate fork delegate for "process running right now." We just need to set `onClose` on each `TerminalViewState`.

### Wiring options

1. **At `TabRuntime` init** — pass an `onClose` callback into `TabRuntime` that captures the `tabID` and routes to `AppStateStore.closeTab(id:)`. Cleanest, but `TabRuntime` doesn't currently know about `AppStateStore`. Would need a back-reference or a closure.
2. **In `PaneView.onAppear`** (or `.task`) — set `tab.terminal.onClose = { _ in appStore?.closeTab(id: tab.id) }`. The view has `appStore` in scope already. The downside is per-view wiring; if a tab's surface is created off-view we'd miss it.
3. **In `AppStateStore` (or a new lifecycle helper)** — observe new tabs being added and set their `onClose` centrally. Most decoupled, but requires a hook on tab creation.

Path 2 (`PaneView`'s lifecycle) is the smallest change and matches how `onChange(of: tab.terminal.bellCount)` already routes events to `AppStateStore`. v1 should ship that. Re-evaluate if we ever spawn a `TabRuntime` outside `PaneView`'s observation (currently we don't — every tab goes through a pane).

### Cascade behavior

`AppStateStore.closeTab(id:)` already handles every cascade case:

- Tab is one of many in its pane → just remove the tab.
- Tab is the last in its pane → remove the pane via `tree.removePane(id:)`.
- Pane was the last in the session → `tree.removePane` returns `true` → `removeSession(id:)`.
- `removeSession` re-creates a default session when sessions become empty.

So routing the auto-close through `closeTab(id:)` gets all of this for free. Don't reinvent.

### Edge cases

- **Last tab of last session.** `removeSession` would re-create a default `Session 1`, so the user types `exit` in their only tab and ends up with a fresh shell prompt in a freshly-created tab. That's *almost* right but feels slightly surprising. Alternative: quit the app when the last surface closes via shell exit. v1 should keep the re-create behavior (matches "Cmd-W on the last tab" today; users who want quit-on-exit can `exit` and then `Cmd-Q`). Track separately if it ever bites.
- **Rapid sequential exits.** If a user runs `exec exit` or scripts multiple shell exits, the closes might pile up. `closeTab(id:)` is idempotent against an unknown id (no-op), so duplicate fires are safe.
- **Surface destroyed before `onClose` fires.** If a tab's `TerminalViewState` is torn down (e.g., user manually closes the tab) before the shell exit signal lands, the callback never fires — also fine.
- **Shell crashes vs. clean exit.** `processAlive: Bool` distinguishes these in theory; in practice libghostty fires close on either. v1 doesn't differentiate; both close the tab.

### Settings escape hatch (v2)

If a user later complains that they want to see the exit output before the tab disappears, add a Settings toggle: "When the shell exits: *Close the tab* / *Keep the tab open*." Default to close. Don't build the toggle in v1 — single behavior is simpler and matches the user's request.

### Related issues

- `#0054` (Cmd-W with busy confirmation) — orthogonal. `#0054` is for the *user-initiated* close path; this one is for the *shell-initiated* close path. They share the same `closeTab(id:)` cascade.
- `#0044` / `#0045` (fork delegate plumbing) — already landed. `TerminalSurfaceCloseDelegate` + `onClose` are part of that plumbing.

## Acceptance criteria

- Typing `exit` (or Ctrl-D on an empty prompt) in any tab closes that tab immediately.
- If the closed tab was the only one in its pane, the pane closes.
- If the closed pane was the only one in its session, the session closes (and the store regenerates a default session as it does today via `removeSession`'s recovery).
- No confirmation dialog; the user already confirmed by exiting.
- Closing a tab via `exit` produces no race or crash if the user is rapidly cycling focus through panes at the moment of exit.
- A unit test exercises the `onClose` → `closeTab(id:)` wiring at the model level (no view tree needed): inject a fake terminal that fires its `onClose` callback, assert the tab is gone.

## Suggested implementation sketch

In `PaneView.body`, alongside the existing `.onChange(of: tab.terminal.bellCount) { ... }` modifiers, set up the close callback once per tab. The cleanest spot is a `.task(id: tab.id)` modifier on each `TerminalSurfaceView`:

```swift
TerminalSurfaceView(context: tab.terminal)
    .task(id: tab.id) {
        tab.terminal.onClose = { _ in
            if let appStore {
                appStore.closeTab(id: tab.id)
            } else {
                pane.removeTab(id: tab.id)
            }
        }
    }
```

The `.task(id:)` form re-establishes the callback whenever the tab id changes (so tab swaps don't lose the wiring). The `[weak appStore]` capture isn't strictly necessary since `appStore` is an environment value and survives the closure's lifetime, but adding it doesn't hurt.

Alternative: set `onClose` inside `TabRuntime.init` if we pass an `onClose` closure as a parameter — keeps the wiring closer to the model. Either path is fine; pick the one that lands the smallest diff.

## Out of scope

- A "Don't close on shell exit" Settings toggle (defer to v2).
- Distinguishing clean exit from crash via `processAlive` and showing different UI (e.g., a "Restart shell" button in the dead surface). Possible future feature; not v1.
- Auto-quitting the app when the last tab closes via shell exit. Track separately if it becomes a request.
- Handling the case where `exit` is run in a TUI subshell inside `vim`'s `:term` — that's a nested-shell concern outside Batty's surface model.

## Root cause

`TerminalSurfaceCloseDelegate.terminalDidClose(processAlive:)` was already being forwarded by the libghostty fork into `TerminalViewState.onClose: ((Bool) -> Void)?`, but nothing in Batty assigned that callback. With no observer, the surface stayed in the view tree after the shell exited and the user was left looking at a dead terminal until they manually closed the tab.

## Fix

Set `tab.terminal.onClose` for every tab from `PaneView`'s `ForEach(pane.tabs)` block via a `.task(id: tab.id)` modifier on the `TerminalSurfaceView`. The closure routes to `AppStateStore.closeTab(id:)`, which already handles the full cascade — last tab removes the pane, last pane removes the session, empty store recreates a default session via `removeSession`'s recovery path. `processAlive` is ignored for v1; both clean and force exits close the tab.

## Files changed

- `BattyKit/Sources/BattyKit/PaneView.swift` — add `.task(id: tab.id)` alongside the existing `.onChange` modifiers on each `TerminalSurfaceView` to install the `onClose` callback.
- `BattyKit/Tests/BattyKitTests/ShellExitAutoCloseTests.swift` — new test suite that installs the same callback the view does, fires it directly, and asserts the cascade ran (non-last tab removed; last tab of last session triggers default-session recovery; idempotent under repeat fires; `processAlive` flag is ignored).

## Gotchas

- The closure captures `tab.id` (a `UUID`) and `appStore`/`pane` weakly. `appStore` is an environment value with app-lifetime ownership, so the weak capture is conservative rather than necessary, but it keeps the closure safe against any future restructuring that decouples the tab's terminal state from the view tree.
- The fix is wired in `PaneView` rather than `TabRuntime.init` because every live `TerminalViewState` is currently owned by a tab that goes through a pane. If a future code path spawns a `TabRuntime` outside of a pane's observation (which would be unusual — the surface registry expects pane-driven lifecycle), the wiring would need to move to a more central spot.
- The visual confirmation — typing `exit` in a tab and watching it disappear — needs the user. The model-level test covers the cascade; the SwiftUI `.task` modifier itself isn't exercised by unit tests.
