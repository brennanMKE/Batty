# 0074 — Tab is present but its terminal NSView is missing (empty pane below the chip)

## Description

User reported that, after a series of splits and tab closes, one tab had its chip present in the tab bar but **the terminal area below the chip was empty** — no NSView, no scrollback, no prompt. The logs show four consecutive `focus skipped: no AppTerminalView matched the requested terminal state` messages at the moment of the report:

```
focus skipped: no AppTerminalView matched the requested terminal state
focus skipped: no AppTerminalView matched the requested terminal state
focus skipped: no AppTerminalView matched the requested terminal state
focus skipped: no AppTerminalView matched the requested terminal state
```

The focuser (from `#0066`) walks `NSApp.windows` looking for the `AppTerminalView` whose libghostty delegate is `tab.terminal`. When all four lookups miss, **there is no NSView in the window's view hierarchy** corresponding to that tab. The tab's `TabRuntime` exists (the chip rendered), but either:

1. `tab.terminalNSView` is nil (the wrapper never created one).
2. `tab.terminalNSView` exists but is not a subview of any container (the wrapper's `updateNSView` didn't re-parent it).
3. `tab.terminalNSView` exists as a subview of an orphaned container that's no longer in the window.

This is a follow-up to `#0072` (the wrapper fix). `#0072` made the PTY survive SwiftUI rebuilds; this issue says the wrapper is incomplete — under some sequence of mutations (the user reproduced via `splitHorizontal` then multiple `closeTab` calls), the NSView ends up orphaned.

## Steps to reproduce (best guess from logs)

Based on the user's log sequence:

1. Launch Batty.
2. `cd ~/Developer/brennanMKE/Batty`. Session auto-renames to "Batty" (per `#0058`).
3. Type `claude` (so the tab is running a TUI).

## Expected behavior

The wrapper from `#0072` (`StableTerminalSurfaceView`) must guarantee that whenever a tab is mounted (i.e. `pane.tabs.contains(tab)` and the pane is visible), the tab's `terminalNSView` is non-nil and is a subview of the wrapper's container. Specifically:

- First mount: `updateNSView` creates the AppTerminalView lazily and attaches it.
- Re-mount after SwiftUI tear-down: `updateNSView` re-parents the existing `terminalNSView` into the new container.
- After pane/tab structural changes (split, close-sibling, etc.): every still-living tab's NSView is hosted by *some* container that's in the window hierarchy.

The "empty terminal area" symptom should never appear.

## Investigation hypotheses

In rough order of likelihood:

### 1. `makeNSView` returns before `updateNSView` runs in a stale state

SwiftUI's lifecycle for NSViewRepresentable:
- `makeNSView` is called once per representable instance to create the NSView.
- `updateNSView` is called subsequently when SwiftUI's diff thinks the wrapper needs to update.

If `updateNSView` doesn't run after `makeNSView` (because SwiftUI thinks nothing changed), the container is empty. The wrapper's current shape may put the AppTerminalView creation inside `updateNSView` — fine when an update fires, but not if SwiftUI skips it on first mount.

**Fix:** move the AppTerminalView creation into `makeNSView` (create the container AND attach the NSView in one step). `updateNSView` only re-parents on demand if the NSView's superview is somehow nil.

### 2. The AppTerminalView's superview pointer doesn't survive coordinator hand-off

If SwiftUI re-creates the wrapper's `Coordinator` between renders, the wrapper may try to look up the previously-attached AppTerminalView via the wrong code path. Confirm the `terminalNSView` lookup is always via `tab.terminalNSView` (the TabRuntime-held strong ref), not via a coordinator-local cache.

### 3. Container view's superview is detached

When SwiftUI tears down the wrapper, the container goes away. The AppTerminalView was its subview, so its `.superview` becomes nil. On re-mount, a new container is created; if `updateNSView` doesn't re-call `addSubview(tab.terminalNSView)`, the NSView floats orphaned.

**Fix:** `updateNSView` should always check `terminalNSView.superview != container` (or `terminalNSView.superview == nil`) and re-parent.

### 4. Race during split: new pane's wrapper mounts before the parent pane's wrapper unmounts

A `Cmd-D` split creates a new `PaneRuntime` and adds it to the tree. Both the old pane and the new pane render. If the old pane's wrapper's container is the previous superview of the AppTerminalView, and the new container's `addSubview` arrives before the old one releases, the AppKit superview pointer might end up pointing at a stale container.

**Fix:** `removeFromSuperview` on the existing AppTerminalView before `addSubview` to a new container. Idempotent and safe.

### 5. The wrapper is being asked to host a NSView that belongs to a different TabRuntime

If `pane.tabs` reorders or a tab is swapped between panes, the wrapper might mount with a `tab` reference whose `terminalNSView` is still rendered in a different wrapper. Two wrappers can't share one NSView — the second `addSubview` would silently move the view, leaving the first wrapper's container empty.

**Fix:** in `updateNSView`, always `removeFromSuperview` and re-attach. Whichever wrapper updates last "wins" the NSView.

## Implementation guidance

The likely fix is a small refinement to `StableTerminalSurfaceView`:

```swift
func makeNSView(context: Context) -> NSView {
    let container = NSView()
    container.translatesAutoresizingMaskIntoConstraints = false
    attachIfNeeded(to: container)
    return container
}

func updateNSView(_ container: NSView, context: Context) {
    attachIfNeeded(to: container)
}

private func attachIfNeeded(to container: NSView) {
    // Lazily create the NSView if this is the first mount.
    if tab.terminalNSView == nil {
        tab.terminalNSView = makeAppTerminalView(for: tab.terminal)
    }
    guard let view = tab.terminalNSView else { return }

    // If the view is parented to a different container (or floating
    // orphaned), move it to the current one.
    if view.superview !== container {
        view.removeFromSuperview()
        view.translatesAutoresizingMaskIntoConstraints = false
        container.addSubview(view)
        NSLayoutConstraint.activate([
            view.leadingAnchor.constraint(equalTo: container.leadingAnchor),
            view.trailingAnchor.constraint(equalTo: container.trailingAnchor),
            view.topAnchor.constraint(equalTo: container.topAnchor),
            view.bottomAnchor.constraint(equalTo: container.bottomAnchor),
        ])
    }
}
```

Key invariants:

- `tab.terminalNSView` is created in `makeNSView` (first mount) AND re-checked in `updateNSView` (every subsequent call). Always non-nil after either path runs.
- `addSubview` is preceded by `removeFromSuperview` so the AppKit superview pointer is single-owner.
- Auto-layout pinning ensures the AppTerminalView fills the container regardless of resize.

Also add a debug `os.log` in the wrapper's `updateNSView` when `tab.terminalNSView?.superview === nil`, so future "empty pane" repros leave a breadcrumb in Console.

## Tests

This is hard to unit-test because the failure is a SwiftUI ↔ AppKit lifecycle issue. Best we can do:

- Test that after `pane.removeTab(...)` (on a non-active tab), the active tab's `terminalNSView` is unchanged and has the same identity.
- Test that toggling `pane.activeTabID` between two tabs doesn't nil-out either tab's `terminalNSView`.
- A UI test in `BattyUITests` that performs the repro sequence (split, close × 3) and asserts the focused tab has a non-empty terminal frame. Detection via `XCUIElement.value` reading the visible terminal text, or via a sentinel chip-label.

## Acceptance criteria

- After any sequence of splits, closes, and focus changes, every active tab in the visible pane shows its terminal NSView.
- The "empty terminal area below the chip" symptom never reproduces.
- `TerminalSurfaceFocuser` log "no AppTerminalView matched the requested terminal state" stops appearing after split/close sequences (it should only appear for a brief moment during the cold-launch race that `#0066` documented).
- Existing `#0072` invariants hold: PTY survives navigation; tab contents persist across switching.

## Notes

- This is directly downstream of `#0072`. The wrapper landed and fixed the most common case (tab switching), but a less-common path (split + close cascade) is still corrupting the NSView ↔ container relationship.
- The `focus skipped` log is the *symptom*, not the cause. The cause is the NSView not being a subview of any container in the window. The fix is in the wrapper's mount logic, not in the focuser.
- Coordinate with `#0072`'s commit `7a01ff1` (StableTerminalSurfaceView). The diff is small — mostly tightening `updateNSView`'s re-parent guarantees.
