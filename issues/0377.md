## Description

**This is an alternative to [#0373](0373.md)'s approach, not a follow-on to it, and it is deferred — filed `open` so the design is not lost, but it should only be started if the per-Pane result from #0373–#0376 looks wrong to the user.** Do not schedule it speculatively.

The difference is what the image is attached to. libghostty's `background-image` is composited by Ghostty's renderer **per surface**, so every Split scales and draws its own copy — four Panes means four copies of the picture, each squeezed into its own rectangle. That may be exactly what the user wants, or it may look like a tiled mess. If it is the latter, the only way to get **one continuous image spanning the whole Window** with the Splits floating over it is to composite it in Batty instead:

- Set `background-opacity` on the surfaces (the [#0373](0373.md) plumbing, which this design still needs) so the terminals are semitransparent.
- Draw the image **once**, as a SwiftUI layer *behind* the persistent terminal host.

## Why it is viable

Two facts, both verified against the current tree:

- **The Metal layer is already transparency-ready.** `Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView.swift:64-68` in the pinned SPM checkout sets `metal.isOpaque = false` and a clear `backgroundColor` on both the `CAMetalLayer` and the view's layer in `commonInit()`. Nothing in Batty has to change for a semitransparent surface to composite over what is behind it.
- **The themed background already renders behind the host, in the right place.** `BattyKit/Sources/BattyKit/Views/SessionDetailView.swift` builds `sessionStack` as a `ZStack` (`:183-224`): `TerminalHostInstaller(windowID:)` is installed at `:195`, and `:217-220` applies `.background(themeChrome?.windowBackground ?? Color.clear, ignoresSafeAreaEdges: .all)` behind the whole stack, extending into the transparent title bar (`WindowChromeApplier`). That existing background modifier is exactly where a window-wide image layer would go.

*(Citation correction: an earlier research note put the themed background at line 216. It is at `:217-220`, with the `themeChrome?.windowBackground` expression on `:218`. The host at `:195` is correct.)*

## The ordering trap

`SplitContainerView` and its Pane placeholders come **after** the terminal host in that `ZStack` (`SessionDetailView.swift:197-206`, inside a `ForEach` over `windowRuntime.sessions`), so they render *above* the terminals. That ordering is deliberate — the comment at `:191-194` explains that terminals render behind chips and sidebar overlays, and that AppKit hit-testing on `TerminalHostView` routes clicks inside a visible terminal frame to that terminal while clicks outside fall through to SwiftUI.

The consequence: **a per-Pane image cannot be drawn in the Pane views.** Anything drawn there lands on top of the terminal, not behind it. The image layer must go *below* the host, which is why this design is window-spanning by construction rather than by choice.

## Review risk this issue carries and the others do not

This touches the persistent-host layer and the ZStack ordering guarded by `docs/view-hierarchy.md` and `docs/terminal-pane-requirements.md`. Both are binding per `CLAUDE.md`, and #0143 is the documented precedent for what goes wrong when a new layer is added to the pane body without reading them: file drops broken, clicks broken.

Whoever implements this **must** read both docs first and run the manual checklist in `docs/terminal-pane-requirements.md` before marking the work complete — pointer input, keyboard, file drop, text drop, and IME all have to survive. An image layer that inserts an interactive or hit-testable view between the host and the window is the exact failure mode those docs exist to prevent; the layer must be non-interactive (`.allowsHitTesting(false)`) and must not change the host's position in the ZStack.

## Notes

- **This design still needs `background-opacity`** from [#0373](0373.md) — without semitransparent surfaces there is nothing to see through. It does **not** need `background-image`, `background-image-fit`, `background-image-position`, or `background-image-opacity`, since SwiftUI does the fitting and the dimming.
- **Fit, position, and image opacity move into SwiftUI**, which means they are Batty's problem rather than libghostty's: `.resizable().aspectRatio(contentMode:)` and `.opacity(_:)` cover the common cases and are easier to get right than mapping onto libghostty's enum values.
- **`themeChrome.windowBackground` composition.** The image layer and the themed window background occupy the same slot. Decide whether the image replaces it, layers over it, or layers under it — and note that the themed color extends into the transparent title bar, so an image that replaces it will change the title-bar appearance too.
- **Seeing through to the desktop** — the user's stated end goal for this batch (see [#0372](0372.md)) — is a *third* thing again, requiring the `NSWindow` itself to be non-opaque. Neither this design nor [#0373](0373.md)'s gets there on its own. If this issue is ever scheduled, settle that question here, because this is the design where the whole compositing stack is already in scope.
- **Verification.** Largely visual and therefore not unit-testable. If scheduled, budget for the `docs/terminal-pane-requirements.md` manual checklist and expect to mark `resolved`, not `closed`.
