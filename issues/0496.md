# 0496 — ⌘W with a sheet over Settings or Help sends `performClose` to the sheet instead of the window it hangs from

| | |
|---|---|

| **Platform** | macOS |

| **Target release** | 1.3.0 on `main`; candidate for `git cherry-pick -x` onto `release/1.2` (see Notes) |

## Description

#0480 made the Tab menu's Close item call `performClose` on the key window while an auxiliary window (Settings, Help, or any titled window that is not a registered content window) is key, so ⌘W closes that window instead of a hidden Tab. The classifier that decides "auxiliary" walks up from a sheet or child window to the window it hangs from, but the close is then sent to the **raw key window**. With a sheet over Settings or Help, the key window is the sheet: `performClose` goes to a window with no close button, and neither the sheet nor Settings closes. #0481 fixed the same shape for the Project Editor (`closeProjectEditor(from:)`, which walks `sheetParent` and acts on the editor, doing nothing while a sheet is attached) and recorded this remaining case in its Gotchas as a follow-up candidate.

Not behind the Projects flag: the auxiliary branch exists in both variants.

## Current code (verified 2026-10-13 on `main` at `673c6530` and `issue/0480-1.2` at `27d12b0b`)

- **The Close item** (`BattyKit/Sources/BattyKit/Commands/BattyCommands.swift:610-631`): `let key = NSApp.keyWindow` (`:613`); `if store.closeProjectEditor(from: key) { return }` (`:614-616`); then `if store.auxiliaryWindowIsKey { key?.performClose(nil) } else { actionWindow?.requestCloseFocusedTab() }` (`:617-621`); `.disabled(!store.closeItemIsEnabled)` (`:631`).
- **The classifier** `AppStateStore.isAuxiliaryWindow(_:isContentWindow:)` (`Runtime/AppStateStore.swift:1025-1030`): `while let up = current.sheetParent ?? current.parent { current = up }` (`:1027`), then "not a content window, titled, not a non-activating panel". Its doc comment (`:1014-1024`) says "a sheet or child window over a content window is not auxiliary and a dialog over Settings is". `auxiliaryWindowIsKey` (`:1042-1044`) reads it through the injectable `keyWindowProvider` (`:1039`). So for a sheet over Settings, `auxiliaryWindowIsKey` is true and `key` is the sheet.
- **The editor precedent** `closeProjectEditor(from:close:)` (`Runtime/AppStateStore+Quit.swift:77-86`): resolves the editor through `projectEditorWindow(from:)` (`AppStateStore.swift:1004-1008`, a `sheetParent` walk), and closes only when `editor === window, editor.attachedSheet == nil` (`:84`); otherwise returns true having done nothing. `close` is injected for tests. Unit test `ProjectEditorQuitTests.aSheetOverTheEditorResolvesToTheEditorAndIsLeftAlone` (`BattyKit/Tests/BattyKitTests/ProjectEditorQuitTests.swift:364`); UI test `ProjectsEditorQuitTests.testCmdWWithASheetOverTheEditorLeavesTheSheetAndTheEditorAlone` (`BattyUITests/ProjectsEditorQuitTests.swift:97`).
- **Classifier tests with real never-shown windows**: `AuxiliaryWindowGateTests.aSheetIsJudgedByTheWindowItHangsFrom` (`:60`) and `aChildWindowIsJudgedByTheWindowItHangsFrom` (`:84`).
- **No Batty-authored sheet hangs from Settings or Help today.** `SettingsView.swift` and `Views/Help/*.swift` contain no `.sheet(`, `.confirmationDialog(`, `.alert(`, `.popover(` or `beginSheetModal`. The bell-decision export (`SettingsView.swift:383-397`) uses app-modal `NSSavePanel.runModal()` and `NSAlert.runModal()`, which are not sheets. So there is no end-to-end reproduction on `main` right now; the exposure is latent and will become real with the first SwiftUI `.alert`/`.confirmationDialog` in Settings or Help (macOS attaches those to the window), with a popover (a child window, which the classifier also resolves upward), or with a third-party auxiliary window such as Sparkle's update window, which the classifier's comment names.
- **`issue/0480-1.2`** (the backport branch, not yet on `release/1.2`: `git log release/1.2 --grep='#0480'` is empty) has the same code at `BattyCommands.swift:510-511`: `if store.auxiliaryWindowIsKey { NSApp.keyWindow?.performClose(nil) }`, with no `closeProjectEditor` call (no Projects there).

## Expected behavior

- ⌘W while a sheet or child window hangs from an auxiliary window **does nothing**: no `performClose` to the sheet, no beep. ⌘W while the auxiliary window itself is key closes it, as today. This is `closeProjectEditor`'s rule applied to every auxiliary window.
- **Mechanism**: one `static func topLevelWindow(from:)` on `AppStateStore` holding the `sheetParent ?? parent` walk, used by `isAuxiliaryWindow` and by a new `closeAuxiliaryWindow(from:close:) -> Bool` shaped like `closeProjectEditor(from:close:)`: resolve the top-level window; if it is not auxiliary, return false; close it only when `window === topLevel` and `topLevel.attachedSheet == nil`; return true. The Close item becomes `closeProjectEditor(from: key) || closeAuxiliaryWindow(from: key)` before falling to `requestCloseFocusedTab()`. `.disabled(...)` is untouched (enablement is never gated: #0480's "gate at action time only").
- `release/1.2` gets the same rule without the editor call.
