## Description

#0361 changed two things the CLI docs state as fact: it replaced
identifier-based launching (`open -b <bundle-id>`) with path-based launching
(`open -a <resolved-bundle-path>` / `open -g <path>`), and it added two exit
codes beyond the documented `2`–`5` range. `docs/batty-cli-install.md` and
`docs/xpc/xpc-cli-architecture.md` still describe the old behavior.

This matters more than usual for these two files. `docs/batty-cli-install.md`
opens by declaring itself "a from-the-source record of how the `batty`
command-line tool actually works in this repo today … every path, target name,
and code excerpt below was read directly from the source" and explicitly tells
readers to use it, not the older `docs/cli-tool-install.md`, as the source of
truth for current behavior. A doc that claims that standing has to be held to it.

## Expected behavior

Both docs describe the shipped behavior: launching targets a resolved absolute
bundle path, and the exit-code vocabulary runs `2` through `7`.

## Actual behavior

Stale statements at these verified locations:

**`open -b <bundle-id>` / identifier-based launching:**

- `docs/batty-cli-install.md:98` — step 5 of the `new` walkthrough: "`openURL(url)`
  (`SessionCommand.swift`) spawns `/usr/bin/open -b <bundleIdentifier> <url-string>`",
  followed by ~15 lines rationalizing the `-b` flag as #0279's fix. #0361 round 3
  changed this to `open -a <bundleURL.path> <url-string>` after resolving the
  bundle via `AppBundleLocator.resolve()`; the `-b` rationale is now history, not
  current behavior, and should read that way.
- `docs/batty-cli-install.md:1189` — the File inventory row for
  `SessionCommand.swift`: "`openURL(_:bundleIdentifier:)` (spawns
  `/usr/bin/open -b <bundleIdentifier>`, defaulting to
  `ServiceNames.appBundleIdentifier` — `#0279`)". The signature itself changed:
  it is now `openURL(_:resolveAppBundle:)`.
- `docs/xpc/xpc-cli-architecture.md:363` — "the CLI can start the app
  (`NSWorkspace`, or `open -b <bundle-id>`)". This is the prescriptive
  architecture doc, so the guidance itself is what is now wrong: identifier-based
  launching is the thing #0361 removed, because up to ten bundles on a developer
  machine claim `co.sstools.Batty`.

**Exit codes:**

- `docs/batty-cli-install.md:1060` — "XPC-backed commands use exit codes `2`
  through `5` for transport and app-side failures."
- `docs/xpc/xpc-cli-architecture.md:353-358` — the `| Code | Meaning |` table
  stops at `5`.

#0361 adds, in `BattyKit/Sources/BattyXPCCore/XPCExitCode.swift`:

| Code | Symbol | Meaning |
|---|---|---|
| 6 | `appRunningUnregistered` | app is running at the resolved bundle path but never re-registered with the broker inside the poll bound; the CLI reports this instead of launching a duplicate |
| 7 | `appBundleUnresolved` | could not determine deterministically which on-disk bundle to target; reported instead of falling back to ambiguous LaunchServices identifier lookup |

## Notes

### Also worth checking while in these files

- `docs/xpc/xpc-cli-architecture.md:363-366`'s surrounding paragraph says "Bound
  the wait and exit 3 when it expires." Post-#0361 that is only true when nothing
  was running; the app-running case expires to `6`. See **#0369**, which proposes
  shortening that bound for the `6` case — if both land, the doc should describe
  whatever bound wins rather than being updated twice.
- Line 1060's claim sits inside a bullet titled "Only `new` lacks an app-side
  failure code". #0361 gave `new` a real resolution failure (`7`) before `open` is
  ever spawned, so that bullet's framing needs a second look, not just a range
  bump.

### Scope decision: `docs/themes.md` is filed separately

A prior filer flagged `docs/themes.md:44-45` (a pre-split
`co.sstools.Batty.themeName` key) as possible scope for this issue. **Filed as
its own issue, #0370, not folded in here.** Reasons: different module (`Docs /
Theme` vs the CLI/XPC surface), no shared cause with #0361, and the theme drift
is broader than the two lines cited — `docs/themes.md` repeats the stale key at
`:129` and `:497`, cites a wrong file path at `:130`, and has a separate stale
claim at `:33-35`. Bundling it would have made this issue's verification harder
to review, not easier.

### Relation

- **#0361** — the change that made these statements stale. It landed on `main` as
  `5b87627` while this issue was being filed, and every doc line cited above was
  re-verified as still stale on `main` after that merge. Note the branch went
  through three rounds and reverted part of round 1 (`LSMultipleInstancesProhibited`),
  so write the doc against what actually landed, not against the issue's narrative.
- **#0370** — the `docs/themes.md` drift split out of this issue.
