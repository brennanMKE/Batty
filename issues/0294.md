# 0294 — A terminal layer allocates drawables at 2× the content area on a 1× display

| | |
|---|---|
| **Status** | open |
| **Module** | TerminalSurface |
| **Platform** | macOS |
| **First seen** | 2026-07-31 |

## Description

The live-process instrumentation of #0285 found a drawable geometry class of **3290×1924 px — exactly 2× the 1645×962 pt terminal content area — on a host whose only display has backing scale 1.0** (single 1920×1080 non-Retina display). Three such drawables exist (the standard 3-per-layer swap chain), totalling **72.6 MB — 5% of the entire 1472 MB footprint** — for one layer rendering at 4× the pixels it can possibly display.

Suspected cause: a mis-set `contentsScale` or `drawableSize` on one layer. From outside the process this could not be distinguished from a window snapshot or a system effect layer, so **the first task is in-process confirmation**: log `NSView.layer.contentsScale` and `CAMetalLayer.drawableSize` per surface and find which surface (if any) owns the 2× geometry.

## Relation

- Child of umbrella #0285 (found by the live instrumentation, `issues/0285/investigation-live.md` §H1 anomaly).
- Related code note in #0293: `AppTerminalView` orphans the `CAMetalLayer` it creates in `commonInit` and `updateMetalLayerMetrics` keeps writing `drawableSize` to it (`AppTerminalView+Lifecycle.swift:188-192`) — a stale scale factor written through that path is a plausible mechanism.

## Expected behavior

Every terminal layer's drawable size matches its view size × the actual display backing scale. On a 1× display, a 1645×962 pt pane gets 1645×962 px drawables.

## Actual behavior

One layer holds three 3290×1924 px drawables (24.2 MB each) for a 1645×962 pt content area on a 1× display.

## Notes

- The measurement is region-geometry arithmetic from `vmmap` (`issues/0285/investigation-live.md`, H1 geometry table): region size 24.2 M closes to 3290×1924×4 B. It held identically across both samples 20 minutes apart, surviving a pane resize.
- Cross-reference: `updateMetalLayerMetrics` writes `drawableSize` (`AppTerminalView+Lifecycle.swift:188-192` in libghostty-spm) — including to the orphaned `CAMetalLayer` noted in #0293. Ghostty's own `IOSurfaceLayer` sizing is a separate path; part of the confirmation step is establishing which layer class owns the 2× geometry.
- If the in-process log shows all Batty surfaces at 1× and the 2× layer is a window snapshot or system effect layer, resolve this as not-a-Batty-bug with the evidence attached.
- **The in-process confirmation can run against the Beta build**: scheme `Batty (Beta)`, bundle id `co.sstools.Batty.beta` (`Configuration/Beta.xcconfig:4`), built with `SCHEME="Batty (Beta)" scripts/build.sh`. Its distinct bundle id gives it separate UserDefaults and workspace persistence, so the `contentsScale` / `drawableSize` logging build can be launched, driven, and killed freely without disturbing the release instance. (Confirm first that the anomaly reproduces on a fresh Beta instance at all — it may be specific to the long-lived release process.)

### 2026-08-01 investigation — instrumentation landed, anomaly still unreproduced

**Status stays `open` deliberately.** Two rounds of work landed diagnostic
instrumentation on `main`, but the 3290×1924 geometry was never observed
in-process. What follows is what the next session needs.

**Leading hypothesis (found in review, not by measurement).** At the pinned
`b146b73`, every scale-factor path in `GhosttyTerminal` terminates in a
hardcoded `?? 2.0` — `AppTerminalView.swift:63` and `:74-77`, and
`TerminalSurfaceCoordinator.swift:43`. `synchronizeMetrics`
(`TerminalSurfaceCoordinator.swift:153-180`) multiplies view size by that scale
before `setContentScale`/`setSize`, so a code path taking the fallback on a 1×
display sizes the ghostty surface to `bounds × 2` — **1645×962 → 3290×1924
exactly**, matching the observed class.

**Correction to that hypothesis, from the second review.** The "detached view"
half is narrower than first stated. `updatePlacements`
(`TerminalHostStore.swift:311-328`) sets `isHidden = true` without
`removeFromSuperview`, so background-tab views keep a non-nil `window` and never
reach the fallback; and `releaseTerminalView` (`:239-249`) nils `controller` —
freeing the surface — *before* `removeFromSuperview()`, so a detached view has
no surface left to size. The genuinely reachable fallback is `commonInit`'s
`metal.contentsScale = NSScreen.main?.backingScaleFactor ?? 2.0`
(`AppTerminalView.swift:63`), which runs when `window` is nil **by
construction**. `NSScreen.main` is nil at loginwindow and with displays asleep.

**What the fresh-instance run does and does not establish.** On a freshly
launched Beta with a single restored pane (`bounds=672x416`,
`windowBackingScale=1.0`, `activeLayer=IOSurfaceLayer`,
`activeContentsScale=1.0`), an orphaned `CAMetalLayer` was present via
reflection but not active, at 672×416 / scale 1.0, and a simultaneous
`tools/memsample.sh` census found exactly 3 IOSurfaces all at 672×416 — the
`IOSurfaces = layers × 3` invariant holding with `layers = 1`, flat over 3+ idle
minutes. **This establishes** that in that configuration the orphaned layer
holds no IOSurface-backed drawables. **It does not establish** zero cost in
general: `nextDrawable()` was never observed, only inferred from absent
attributable surfaces plus code reading, and the configuration is far smaller
than where the anomaly appeared (1 layer vs 31, 672×416 vs 1645×962, minutes vs
7 days, no hidden tabs, no resize or display change). Correct scope: *zero cost
in the steady state of a fresh single-pane instance.*

The 3290×1924 class participates in the same 3-per-layer and paired-glyph-atlas
signature as every legitimate terminal layer, which argues against "window
snapshot" or "system effect layer."

**Instrumentation now on `main`** — `TerminalMetalMetricsLogger`, inert unless
`BATTY_LOG_METAL_LAYER_METRICS` is set. Two signals: the periodic 10 s dump
(the only line carrying Terminal Session identity), and a forward of
libghostty's public `TerminalDebugLog` `.metrics` category, which fires
process-globally from inside `synchronizeMetrics` regardless of store
membership — so a transient `scale=2.0` cannot slip past it. Only `.metrics` is
enabled; `.standard`/`.all` carry `.input`/`.output` and would route keystrokes
and shell output into the unified log. **Re-grep `TerminalDebugLog.log(.metrics`
on every libghostty bump** before trusting `privacy: .public` — all 14 call
sites were audited as geometry-only at this revision, but semantic drift
upstream is the one silent hazard.

- **Repro protocol** (requires a GUI session on the 1× display):
  1. Build Beta with `scripts/build-beta.sh` — **not** `SCHEME="Batty (Beta)"
     scripts/build.sh`, which leaves `Configuration/Active.xcconfig` redirected
     so the next Prod build silently builds Beta (#0280; the rule is in
     `CLAUDE.md`). Then launch the binary directly so the env var is inherited
     (`open` alone will not pass it):
     `BATTY_LOG_METAL_LAYER_METRICS=1 "<BUILT_PRODUCTS_DIR>/Batty Beta.app/Contents/MacOS/Batty Beta"`
  2. In a second terminal: `log stream --style compact --predicate 'subsystem == "co.sstools.Batty.beta" AND category == "TerminalMetalMetricsLogger"'`
  3. **The decisive line is `sync view=… scale=… pixels=…`**, emitted at the
     instant a pixel size is computed, before `setContentScale`/`setSize` — it
     captures a transient scale that polling current state would miss.
     `metalMetrics tab=… pane=… session=…` is the 10 s snapshot and the only
     line with Terminal Session identity.
  4. **The 2× signature:** any `sync` line reading `scale=2.00` with `pixels`
     exactly twice `view` — e.g. `sync view=1645.00x962.00 scale=2.00
     pixels=3290x1924` (healthy is `scale=1.00 pixels=1645x962`). Corroborating:
     `surface contentScale x=2.00 y=2.00`, `surface setSize 3290x1924`. In the
     periodic dump: `activeContentsScale=2.0`, or `activeLayerBounds` /
     `activeDrawableSize` at twice `bounds`, or `orphanedContentsScale=2.00`.
  5. Provoke both fallback conditions — `window` and `NSScreen.main` nil: create
     sessions and split panes while the app is inactive and the screen is locked
     or displays are asleep; lock, wait, wake, then switch tabs and resize.
     Leave it ≥ 20 min to match the original sample spacing.
  6. Cross-check with `tools/memsample.sh` against the Beta pid: look for the
     24.2 MB (3290×1924×4 B) region class, then correlate the `metalMetrics
     tab=…` line whose geometry matches to name the owning Terminal Session.
  7. If no `scale=2.00` line ever appears while the 24.2 MB class *is* present
     in the census, the geometry is not Batty's — resolve as not-a-Batty-bug
     with both logs attached.

- **Still unknown:** whether any Batty terminal layer ever actually holds the
  3290×1924 geometry — the anomaly has not been reproduced in-process, and the
  `?? 2.0` fallbacks identified as the plausible mechanism have not been
  observed firing; this issue stays `open` pending a GUI session that runs the
  repro protocol above.

- **Technique worth reusing:** `open -n -a` forwards the calling shell's
  environment to the launched app (`man 1 open`), where a direct binary exec can
  stall on a `TCCAccessRequest()` prompt with the screen locked. `-n` is
  load-bearing — without it `open` activates an existing instance and applies no
  environment — and `open --env VAR=value` is the explicit, more reliable form.

### 2026-08-07 investigation — round 3: citations re-verified, upstream PR #44 ruled irrelevant, anomaly still not reproduced

**Citations re-verified against the pinned revision.** Checked out
`beta-build/DerivedData/SourcePackages/checkouts/libghostty-spm` (confirmed
`git rev-parse HEAD` = `b146b73a8ba3ed2678a22a9de5feecfcbf298d48`, matching
`Package.resolved`). `AppTerminalView.swift:63` (`metal.contentsScale =
NSScreen.main?.backingScaleFactor ?? 2.0`), `:74-77` (`core.scaleFactor`
closure, same fallback chain plus `window?.backingScaleFactor`), and
`TerminalSurfaceCoordinator.swift:43` (`var scaleFactor: () -> Double = {
2.0 }`) all match exactly what the leading hypothesis cites — no drift this
time. Note for future rounds: `./build/SourcePackages/checkouts/libghostty-spm`
and `./BattyKit/.build/checkouts/libghostty-spm` in this repo are **stale**
(pinned at `c69c343`, a May-27 commit, not the current `b146b73a` July-27
pin) — only the `beta-build/` checkout was current at the time of this
check. Always run `git -C <checkout> rev-parse HEAD` before trusting a
vendored source tree's line numbers.

**Upstream PR #44 ("host-managed resize coherence") does not touch this
code path.** Fetched `https://github.com/Lakr233/libghostty-spm` `main`
read-only (`git fetch ... main`, inspected via `git show`/`git diff`, no
changes to the local clone's branches or remotes). `git diff b146b73a
FETCH_HEAD -- Sources/GhosttyTerminal/Surface/TerminalSurfaceCoordinator.swift`
and the same for `AppTerminalView.swift` show PR #44's four commits
(`f32ba80`, `ff1d4a2`, `959e5f1`, `18a2018`) add: (1) a guard in
`rebuildIfReady` that keeps a hidden pane's surface instead of tearing it
down when the view reports zero size, (2) an opt-in leading+trailing
coalescing throttle around `synchronizeMetrics` (renamed internally to
`performMetricsSync`), off by default, and (3) removal of one
host-resize-dispatch call (`configuration.inMemorySession?.updateViewport`)
that ran at the wrong point in the resize sequence. **None of this touches
`scaleFactor()`, `commonInit`'s `metal.contentsScale` line, or the `let
scale = scaleFactor()` / `pixelWidth`/`pixelHeight` computation inside
`performMetricsSync`** — diffed byte-for-byte identical between `b146b73a`
and upstream `FETCH_HEAD` (`31884f5`, includes the already-adopted #0292/#0319
PR #45 on top). **Conclusion: adopting the PR #44 resize-coherence work
(tracked separately as part of #0319's scope) would neither fix nor worsen
this anomaly — it is orthogonal.** The right frame stays "fix in Batty (or
libghostty-spm) if reproduced," not "wait for the dependency bump."

**Repro attempts, this round.** Built Beta via `scripts/build-beta.sh`
(clean run, no #0317 recurrence this time; `Configuration/Active.xcconfig`
verified back on `Prod.xcconfig` after). Launched with
`open -n --env BATTY_LOG_METAL_LAYER_METRICS=1 "beta-build/Products/Batty
Beta.app"` and streamed `/usr/bin/log stream --style compact --predicate
'subsystem == "co.sstools.Batty.beta" AND category ==
"TerminalMetalMetricsLogger"'` throughout (note: `log` is a zsh shell
builtin in this environment — `/usr/bin/log` must be called explicitly or
the stream silently fails with "too many arguments"). Confirmed via
`system_profiler SPDisplaysDataType` the host is single-display 1920×1080,
backing scale 1.0 — matching the original anomaly's host. Drove the app via
`osascript`/System Events (the #0311 technique) and `cliclick`:

- Created 4 additional Sessions, 4 additional Tabs, and both a vertical and
  horizontal Pane split, growing the process from 1 to 11 live terminal
  views (11 layers × 3 = 33 IOSurfaces, confirmed by `tools/memsample.sh`).
- Resized the window repeatedly via `osascript ... set size of window 1`
  across widths 334–1200+ pt (a real AppKit layout/resize pass each time —
  confirmed by the sync-line count jumping from 80 to 102 across one burst).
  A `cliclick` divider-drag attempt did not register as a resize (window
  frame unchanged); the AppleScript resize did and is the one that counts.
- Deactivated Batty Beta (`Finder` frontmost) and issued menu commands
  against the backgrounded process — these executed with a delay once the
  app regained focus, not while genuinely backgrounded, so this did **not**
  exercise `NSApp.isActive == false` at the moment of view construction.
- Ran `tools/memsample.sh sample --target beta` twice, ~2.5 minutes apart,
  after all the above churn: both samples show **byte-identical** geometry
  census (11 layers, 33 IOSurfaces, same 7 geometry classes, all matching
  pane point-bounds exactly at scale 1.0) — `tools/memsample.sh diff` reports
  "(no geometry-class changes)". No 3290×1924 class, no 24.2 MB region, no
  region at any 2× multiple of a pane's bounds.
- Across the whole session (828 log lines, 100+ `sync` lines spanning the
  session/tab/split/resize churn above), **every single `scale=` value was
  `1.00`** (`grep -o 'scale=[0-9.]*' | sort -u` → `scale=1.00` and nothing
  else). `orphanedContentsScale` and `activeContentsScale` were `1.00` in
  every periodic dump line, with zero exceptions.

**New finding: the "displays asleep" repro vector does not work in this
environment, confirmed directly and independent of Batty.** Before spending
more cycles on Batty-level repro, tested the claim "`NSScreen.main` is nil
... with displays asleep" directly with a standalone `swift screencheck.swift`
one-liner (`print(NSScreen.screens.count, NSScreen.main, ...)`), no Batty
involved. Baseline: `NSScreen.screens.count=1`, `NSScreen.main` non-nil,
`backingScaleFactor=1.0`. Ran `pmset displaysleepnow` and sampled the same
probe 5× over the next ~2.5 s: **`NSScreen.main` stayed non-nil at scale 1.0
in every sample.** `pmset -g log` explains why: this session is being driven
over Screen Sharing (`ScreensharingAgent` posting `UserIsActive` /
`com.apple.iohideventsystem.queue.tickle.nxevent` assertions, plus `powerd`'s
"Prevent sleep while display is on" assertion) — an active remote-desktop
session keeps WindowServer's notion of "display on" alive regardless of the
physical backlight, so `displaysleepnow` never actually removes the screen
from `NSScreen.screens` here. **This falsifies, for this specific
environment, the half of the repro protocol that says displays-asleep is a
usable trigger.** Future rounds run over Screen Sharing should not spend
time on `pmset displaysleepnow` — it is a no-op for `NSScreen.main` under an
active remote session on this machine.

**Not attempted: actual screen lock / loginwindow.** This is the other half
of the fallback condition and remains completely untested across all three
rounds. Deliberately did not attempt it this round: `sysadminctl
-screenLock status` reports a 300 s deferred-lock delay (irrelevant to a
*deliberate* Lock Screen action, which engages the password prompt
immediately), no auto-login user is configured, and there is no stored
password available to this session to recover if GUI automation lost access
to the desktop afterward. Locking the screen without a guaranteed way back
in risks stranding the session — the task's explicit constraint against
locking without due consideration was treated as binding. This is the one
remaining genuinely untested state; a future round with either (a) explicit
user go-ahead plus a recovery plan (e.g., the user unlocking in person, or
running the test on a machine/session where the operator holds the
credentials), or (b) a way to engineer a truly screenless WindowServer
session (e.g., disconnecting a real external display, not available on this
remote session) is what it would take to close this off.

**Honest bottom line for round 3: outcome (c), neither confirmed nor
refuted.** The 24.2 MB / 3290×1924 class did not appear in this Beta
instance's census (11 layers, several minutes of varied churn), and no
`scale=2.00` line ever fired — but per round 1/2's own caveat this doesn't
positively rule out the anomaly on a long-lived, much larger instance (the
original report was 31 layers over 7 days). No fix was applied; none of the
`?? 2.0` fallback sites were changed. The `window == nil` fallback path
(reachable "by construction" during every `commonInit`, independent of
screen state) also never produced `scale=2.00` despite dozens of new-view
constructions in this round — that alone is mildly against the leading
hypothesis being the *dominant* mechanism, since `commonInit`'s fallback
only matters when `NSScreen.main` is *also* nil at that instant, and on
this healthy, screen-attached host it never was. The loginwindow condition
remains the one lever nobody has pulled yet.
