# 0294 — A terminal layer allocates drawables at 2× the content area on a 1× display

| | |
|---|---|
| **Status** | open |
| **Module** | TerminalSurface |
| **Platform** | macOS |
| **First seen** | 2026-07-31 |

## Description

The live-process instrumentation of #0285 found a drawable geometry class of **3290×1924 px — exactly 2× the 1645×962 pt terminal content area — on a host whose only display has backing scale 1.0** (single 1920×1080 non-Retina display). Three such drawables exist (the standard 3-per-layer swap chain), totalling **72.6 MB — 5% of the entire 1472 MB footprint** — for one layer rendering at 4× the pixels it can possibly display.

Suspected cause: a mis-set `contentsScale` or `drawableSize` on one layer. From outside the process this could not be distinguished from a window snapshot or a system effect layer, so **the first task is in-process confirmation**: log `NSView.layer.contentsScale` and `CAMetalLayer.drawableSize` per surface and find which surface (if any) owns the 2× geometry.

## Relation

- Child of umbrella #0285 (found by the live instrumentation, `issues/0285/investigation-live.md` §H1 anomaly).
- Related code note in #0293: `AppTerminalView` orphans the `CAMetalLayer` it creates in `commonInit` and `updateMetalLayerMetrics` keeps writing `drawableSize` to it (`AppTerminalView+Lifecycle.swift:188-192`) — a stale scale factor written through that path is a plausible mechanism.

## Expected behavior

Every terminal layer's drawable size matches its view size × the actual display backing scale. On a 1× display, a 1645×962 pt pane gets 1645×962 px drawables.

## Actual behavior

One layer holds three 3290×1924 px drawables (24.2 MB each) for a 1645×962 pt content area on a 1× display.

## Notes

- The measurement is region-geometry arithmetic from `vmmap` (`issues/0285/investigation-live.md`, H1 geometry table): region size 24.2 M closes to 3290×1924×4 B. It held identically across both samples 20 minutes apart, surviving a pane resize.
- Cross-reference: `updateMetalLayerMetrics` writes `drawableSize` (`AppTerminalView+Lifecycle.swift:188-192` in libghostty-spm) — including to the orphaned `CAMetalLayer` noted in #0293. Ghostty's own `IOSurfaceLayer` sizing is a separate path; part of the confirmation step is establishing which layer class owns the 2× geometry.
- If the in-process log shows all Batty surfaces at 1× and the 2× layer is a window snapshot or system effect layer, resolve this as not-a-Batty-bug with the evidence attached.
- **The in-process confirmation can run against the Beta build**: scheme `Batty (Beta)`, bundle id `co.sstools.Batty.beta` (`Configuration/Beta.xcconfig:4`), built with `SCHEME="Batty (Beta)" scripts/build.sh`. Its distinct bundle id gives it separate UserDefaults and workspace persistence, so the `contentsScale` / `drawableSize` logging build can be launched, driven, and killed freely without disturbing the release instance. (Confirm first that the anomaly reproduces on a fresh Beta instance at all — it may be specific to the long-lived release process.)
