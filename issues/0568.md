# 0568 — The Tomorrow Reminder time resets to 9:00 AM instead of remembering the last one chosen

| | |
|---|---|
| **Status** | open |
| **Module** | Session / Settings |
| **Platform** | macOS |
| **First seen** | 2026-11-09 |

## Description

The one-click "Tomorrow at 9:00 AM" Reminder and the Reminder sheet's Tomorrow time picker always start at 9:00 AM. Suppose a user sets Tomorrow at 8:30 in the sheet. The next time, they have to pick 8:30 again, and the one-click menu item still reads 9:00 AM. #0514 shipped this on purpose ("not remembered, no Settings row", orchestrator decision 2) and logged it as a Gotcha: "The Tomorrow menu label always reads 9:00 AM, since a time edited in the sheet is not remembered." This issue remembers the last Tomorrow time the user chose, with no Settings row. Targets 1.4.0. Parent: [#0514](0514.md).

## Verified facts (main `254cfb2a`)

- **The default is a constant.** `ReminderSpec.defaultTomorrowHour = 9` and `defaultTomorrowMinute = 0` set it, and `ReminderSpec.defaultTomorrow` (`BattyKit/Sources/BattyKit/Model/SessionReminder.swift:59-64`) is built from them.
- **Labels.** `ReminderActions.tomorrowTitle` is a static computed property with no store (`Views/ReminderMenu.swift:14-24`, through `defaultTomorrowTimeText`). The Command Palette builds its own title: "Remind Me Tomorrow at …" (`Views/CommandPaletteView.swift:233`).
- **One-click actions** pass `.defaultTomorrow`. These are in `ReminderMenu.swift` (the Tomorrow button) and in `CommandPaletteView.swift:235`.
- **`ReminderMenu` is built in two places.** One is the Session menu (`Commands/BattyCommands.swift:226`). The other is the Sidebar row's context menu (`Views/SessionSidebarView.swift:553`). Both already have the `store` in hand.
- **Sheet default.** `ReminderDraft`'s `tomorrowHour` / `tomorrowMinute` default to the constants (`Views/ReminderSheet.swift:19-20`), and so does the fallback in `init(editing:)` (`:32-33`). Editing an existing Tomorrow Reminder reopens on its own time, and that must not change. The sheet commits through `store.editReminder(spec, note:forSessionID:)` (`ReminderSheet.swift:228-230`), which falls back to `setReminder`.
- **Preferences pattern.** Keys live in `SettingsPreference` (`Settings/SettingsPreferences.swift`, as `co.sstools.Batty.*` constants). Reads go through `resolved…(defaults:)` helpers against `AppStateStore.preferences` (`Runtime/AppStateStore.swift:95`), which tests inject per `docs/isolate-userdefaults-in-tests.md`.
- **Observation.** A label computed straight from `UserDefaults` is not observed. A SwiftUI `Commands` menu or Sidebar context menu that reads it may keep showing the old time after the user picks a new one.

## Recommended approach

- **Add the preference.**
  - Add `SettingsPreference.reminderTomorrowTimeKey` (for example `co.sstools.Batty.reminderTomorrowTime`) holding minutes since midnight, and a `resolvedReminderTomorrowTime(defaults:) -> (hour, minute)` that falls back to 9:00 when the value is missing or out of range.
  - Expose the value on `AppStateStore` as an observed property (for example `lastTomorrowReminderTime`), seeded from `preferences` at init and written to `preferences` with each change. Then the menu and palette labels update without reading `UserDefaults` in `body`. The write happens only from event-origin code (`docs/swiftui-observation-rules.md`).
- **When to remember.**
  - The time is remembered when a Tomorrow Reminder is **set or updated from the sheet** with `choice == .tomorrow`.
  - The one-click Tomorrow item reuses the remembered time, so it writes nothing new.
  - Presets and custom durations do not touch it.
  - If [#0567](0567.md) lands first, the plan decides whether `batty session remind --tomorrow --at` also writes it. The recommendation is no: a script's choice shouldn't change the GUI default.
- **Use it everywhere.**
  - The one-click menu item, its label and the palette entry use `.tomorrow(hour:minute:)` from the remembered time.
  - A new sheet's (`ReminderDraft()` / `init(editing: nil, ...)`) Tomorrow picker defaults to it.
  - Pass the time into `ReminderDraft` rather than reading global state, so the draft stays a pure, testable value.
- **No Settings row.** Update `Concepts.md` (Reminder → Setting, "Tomorrow at 9:00 AM") and `docs/ui-features.md` to say the time is remembered.

## Acceptance criteria

1. On a fresh install, the menu, the palette and the sheet show Tomorrow at 9:00 AM.
2. After the user sets a Reminder for Tomorrow at 8:30 AM from the sheet:
   - the Session menu, the Sidebar context menu and the Command Palette all read "Tomorrow at 8:30 AM"
   - a one-click Tomorrow Reminder resolves to 8:30 the next day
   - a new sheet's Tomorrow picker starts at 8:30
3. Editing an existing Tomorrow Reminder still opens on that Reminder's own time.
4. The remembered time survives a relaunch.
5. A missing or invalid stored value falls back to 9:00 AM.

## Test ideas

Use isolated `UserDefaults`, and use non-default fixtures so the "unchanged" assertions aren't vacuous.

- `tomorrowTimeDefaultsToNineWhenUnset`
- `tomorrowTimeFallsBackToNineForInvalidStoredValue`: -1, 1440, and a string.
- `settingATomorrowReminderFromTheSheetRemembersItsTime`: 8:30, then check the store property and the preference.
- `presetAndCustomDurationRemindersDoNotChangeTheRememberedTime`: seed 7:15 first.
- `oneClickTomorrowUsesTheRememberedTime`: seed 7:15, then check that the components resolve to 07:15 on the next day (pinned calendar).
- `newDraftDefaultsTomorrowPickerToRememberedTime`
- `editingDraftKeepsTheReminderOwnTime`: remembered 7:15, Reminder at 10:00, so the draft shows 10:00.
- `tomorrowMenuTitleUsesRememberedTime`: pinned locale and calendar.
