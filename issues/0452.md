# 0452 — The System Metrics view Pane's status badges wrap into tall pill blobs and its five stat tiles break labels mid-word and truncate values at narrow Pane widths

| | |
|---|---|
| **Status** | open |
| **Module** | Pane |
| **Platform** | macOS |
| **First seen** | 2026-10-09 |

## Description

At roughly 330 points wide, the System Metrics view Pane (`BattyKit/Sources/BattyKit/Views/SystemMetricsPaneView.swift`) renders its header and stat row as a broken layout: the green "Thermal: Nominal" badge and the white "Memory pressure: Normal" badge wrap onto three and two lines inside a `Capsule()`, so each becomes a tall pill blob with a corner radius of half its own height, and the five stat tiles are forced into a single row so narrow that their uppercase labels hyphenless-break mid-word ("MEMO / RY / USED", "COMP / RESSE / D") and their values break or truncate ("21. / 0%", "6.5 / 7 / GB", "0....", "Not a..."). The user reviewed the capture from Tart VM run `20261009-215934-61877` (Light appearance) and flagged it for this release: "this looks terrible. The green blob around Thermal has rounded corners which are so extreme. Same for the white blob next to it. This is the design we need to fix."

This is a design/UX issue, high priority (user-flagged for the release). Final visual sign-off is the user's: the resolution sets `resolved`, never `closed`.

## Steps to reproduce

1. In the Tart VM (or any Batty Beta window) open a terminal Pane and run `batty-beta pane split --view system-metrics` (the `CLIViewPaneTests` path), or use the equivalent Pane menu action.
2. Drag the Split divider so the view Pane is about 330 points wide, or narrower. `SplitTree.updateRatio` (`BattyKit/Sources/BattyKit/Model/SplitTree.swift:524`) clamps the ratio to 0.05–0.95 and nothing clamps a Pane to a point-based minimum, so the view can be given far less than 330 points.
3. Wait for the first sample (`system-metrics-refresh-button` appears, `system-metrics-waiting` disappears).

## Expected behavior

Acceptance criteria:

1. **Status indicators are compact and single-line.** Thermal state and memory pressure are shown as a colored dot or small SF Symbol plus text, or as a tag with a modest fixed corner radius (the design mockup's own values are 7px and 6px — see Notes), with `lineLimit(1)` and `fixedSize(horizontal: false, vertical: true)` or equivalent so a badge never wraps mid-phrase and its shape never degenerates into a tall pill. The word before the colon and the state after it are never separated onto different lines. When the row cannot fit both badges plus the refresh affordance, the badges wrap as whole units (the mockup's `flex-wrap: wrap`), or the "Refreshing every 1s" caption is dropped first — never the badge text.
2. **Stat tiles reflow with the available width.** The five tiles (CPU aggregate, Memory used, Compressed, CPU temperature, Fan) are laid out in an adaptive grid (`GridItem(.adaptive(minimum:))`, `ViewThatFits`, or a custom `Layout`) or collapse to a compact label/value list, chosen by available width, so that labels never break mid-word and values are never truncated or wrapped at any width down to roughly 300 points. Below that the view degrades gracefully (secondary `sub` text hides before anything truncates; `—` placeholders stay intact) but still never produces a mid-word break or a clipped value.
3. **Tiles share one height and one baseline** within a row, with values aligned, at every column count.
4. **"Refreshing every 1s"** either fits on one line or is hidden; it never wraps and never pushes the badges into wrapping.
5. **Per-core utilization** never renders a labeled empty area: on the no-baseline tick (see Notes, this is a first-tick state, not a sampling bug) it shows `coreCount` empty track bars, or a short placeholder, rather than nothing under the "PER-CORE UTILIZATION" heading.
6. **Memory legend** labels and byte values never wrap mid-word ("Compresse / d 0.0 MB"); the four legend items wrap as whole units or stack.
7. **Visual language matches the other view Panes**: badge and tile styling is consistent with `ProcessStatusPaneView` and `LMStudioDashboardView` (tinted translucent fills with colored text, 6-point corner radii, Dynamic Type text styles), ideally through one shared badge/tile helper the four views can use, rather than solid-fill white-on-green pills and opaque `controlBackgroundColor` cards used nowhere else.
8. **Both appearances, three widths**: layout verified at narrow (~300 pt), medium (~500 pt), and wide (full-window) Pane widths, in Light and Dark.

Verification:

- Screenshots from the #0451 view-gallery test (`BattyUITests/ViewGalleryTests`, narrow and large Pane captures, Light and Dark if reachable) produced in the Tart VM through `tools/run-ui-tests-vm.sh` under AGENTS.md's standing authorization. #0451 is in flight on `.claude/worktrees/issue-0451`; this issue depends on its captures for the visual check and must not modify that test.
- Unit coverage where the layout decision is pure: if the implementer introduces a width-to-column-count (or width-to-layout-mode) function, test it the way `PaneViewTruncateTests` tests `PaneView.truncate` (`BattyKit/Tests/BattyKitTests/PaneViewTruncateTests.swift`). `PaneViewRenderTests` (`BattyKit/Tests/BattyKitTests/PaneViewRenderTests.swift`) shows how to host a real view in an un-ordered `NSHostingView` for a synchronous layout pass if a geometry assertion is wanted; it also records that `accessibilityChildren()` is empty for such a host, so content-level assertions are not available in-process.
- `./build.sh` and `./build.sh unit` pass.

`docs/swiftui-observation-rules.md` is binding for this view code: view construction stays pure, and width-driven reflow must not write `@State` from `GeometryReader`/`onGeometryChange` (a geometry-origin flip runs inside AppKit's layout pass). Prefer `ViewThatFits`, adaptive `GridItem`s, or a custom `Layout`, which decide the layout without writing observed state.

## Notes

Causes, each verified against the screenshot and the code (`BattyKit/Sources/BattyKit/Views/SystemMetricsPaneView.swift` unless stated):

1. **Badges.** `thermalChip` (`:96-103`) is a `Label` with `.background(Capsule().fill(thermalStateColor))` at `:102`; `pressureChip` (`:125-136`) is a `Text` with `Capsule().strokeBorder` over `Capsule().fill(Color(nsColor: .controlBackgroundColor))` at `:132-134`. Neither has `lineLimit`, `fixedSize`, or a minimum width, so the `HStack(spacing: 10)` at `:78` lets the text wrap and the capsule follows the wrapped height. The label strings carry the colon inline ("Thermal: Nominal", `:107`; "Memory pressure: \(pressureLabel)", `:126`), which is why the colon lands on its own line. The design mockup these views were ported from specifies rectangles, not pills: `docs/design/system-metrics-view.html:188-192` gives `.thermal-chip` `border-radius: 7px` and `:199-202` gives `.pressure-chip` `border-radius: 6px`, with the `.status-row` at `:184-187` set to `flex-wrap: wrap`. The Swift port substituted `Capsule()` for both.
2. **Tile grid.** `metricsGrid` (`:158-181`) is `LazyVGrid(columns: Array(repeating: GridItem(.flexible(), spacing: 8), count: 5), spacing: 8)` at `:159`: five flexible columns at every width. At 330 points, after the `.padding(.horizontal, 14)` at `:55` and four 8-point gutters, each tile is about 54 points wide, and after `.padding(9)` at `:196` the text gets about 36 points. `metricTile` (`:183-200`) sets no `lineLimit` or `minimumScaleFactor` on the uppercase label (`:185-187`) or the 15-point value (`:188-190`), so they wrap character by character, while the `sub` line has `.lineLimit(1)` at `:194` and truncates instead ("Not a...", "6 cor..."). Tiles are `.frame(maxWidth: .infinity)` only (`:197`), so each background is its own intrinsic height and the row's cards do not match. The mockup has the same fixed `grid-template-columns: repeat(5, 1fr)` (`docs/design/system-metrics-view.html:227-232`) with no narrow-width rule, so the adaptive behavior has to be designed here, not recovered from the mockup.
3. **Refresh caption.** `Text("Refreshing every 1s")` at `:82-84` has no `lineLimit` or `fixedSize` and sits after `Spacer(minLength: 8)` at `:81`, so it is the first thing squeezed.
4. **Per-core area.** `coreBarsSection` (`:204-216`) iterates `content.snapshot.cpu.perCorePercent ?? []` at `:210` inside a 34-point-high `HStack`. `perCorePercent` is deliberately `nil` on the no-baseline tick: the first sample after creation and after every hide-then-show (`BattyKit/Sources/BattyKit/Runtime/SystemMetricsSampler.swift:81-91`, documented at `BattyKit/Sources/BattyKit/Runtime/SystemMetricsSnapshot.swift:7-20`). The heading still renders, so that tick shows a labeled blank. This is expected first-tick state, not a sampler bug; the design gap is the missing placeholder. `coreCount` is populated from the raw tick read on that same tick (`SystemMetricsSampler.swift:91`), so empty track bars can be drawn.
5. **Legend.** `memorySection`'s `HStack(spacing: 14)` at `:250-257` holds four `memoryLegendItem`s (`:261-266`) whose `Text("\(label) \(bytes)")` at `:264` has no `lineLimit`, so each item wraps inside its share of the row.
6. **Visual language.** No shared badge or tile component exists in `BattyKit/Sources/BattyKit/Views/` (the only `Card`/`Badge`/`Tile` type is `ThemeCard`). The sibling views converge on one style the metrics view does not use: `ProcessStatusPaneView.swift:160-167` `chip(_:color:)` is `.caption2.weight(.semibold)`, `padding(6, 2)`, `color.opacity(0.15)` fill with the text in `color`, and its banners at `:300`, `:312`, `:334` are `RoundedRectangle(cornerRadius: 6)` with tinted fills; `LMStudioDashboardView.swift:150-156` `statusPill` uses the same tinted-capsule recipe on a single short word, and its rows at `:146` and `:336` use `.quaternary` fills with 6- and 4-point radii. `SystemMetricsPaneView` instead uses a solid `.green` fill with `.white` text (`:98-102`), opaque `controlBackgroundColor` cards with a 7-point radius and a stroke (`:198-199`), and hard-coded point sizes (9, 9.5, 10.5, 11, 11.5, 12, 13, 15 at `:186`, `:189`, `:192`, `:207`, `:256`, `:281`, `:284`, `:311`, `:315`, `:330`, `:371`, `:376`, `:386`) where the siblings use `.caption`/`.caption2`/`.callout`. The sibling capsules survive because their text is one short word with no spaces; the recipe itself is not narrow-safe either, so a shared helper should carry the `lineLimit(1)`/`fixedSize` guard for all four views.

Secondary, same view: the process list's fixed trailing columns (`:326-328` header, `:378-384` rows: 60 + 56 + 76 points plus 8-point gaps) leave the name column about 60 points at 330 points wide; it is middle-truncated (`:372-373`) rather than broken, so it is not part of the user's report, but an adaptive pass should check it at the same widths.

Narrowest Pane: there is no point-based minimum. `SplitTree.updateRatio` clamps to 0.05–0.95 (`SplitTree.swift:524`, reused by keyboard resize at `:560-576`), and `PaneView` clamps itself to the allotted size (`SplitContainerView.swift:10-33`, #0261) and clips overflow. The "good down to ~300 pt, graceful below" criterion above is therefore a design target, not a code-enforced floor; the implementer may propose a `minWidth` for view Panes but it is not required by this issue.
