# 0702 — Saving a Project doesn't update the Pane and Tab backgrounds of its open Sessions

## Description

User report (2026-11-20), verbatim: "When I edit a project and set the opacity and background image I want it to change the project which is already opened. Maybe more than 1 is opened for the same project. Make it work for both. This should be a fix for a 1.4.2 release."

#0653 (shipped in 1.4.1) made a Project Editor save apply live to every open Session of that Project, but only for the **Project-level** background. A Project can also carry its own background on a Pane slot or on a Tab (the Project Editor's per-Pane and per-Tab Background rows, and Save Session as Project / Update Project, which copy the Session's Pane and Tab overrides into the Project). When the user edits any of those, or edits the Project background while a Pane or Tab of the Project has its own, the open Session keeps showing the old image and opacities until the Project is opened again. With two Sessions open from one Project, both stay stale.

This is a bug fix: it goes to `main` first through the normal issue workflow, then `git cherry-pick -x` of the squash commit onto `release/1.4` for 1.4.2 (AGENTS.md, Release branches).

## Current state (checked against `main` at `c727bdcd` and `release/1.4` at `eca8ef61`)

- **How a save reaches open Sessions.** `AppStateStore.applyProjectSave(previous:saved:isDark:)` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:1705` on main, `:1672` on release/1.4). It loops `for window in windows` and `for session in window.sessions where session.projectID == saved.id`, so it already reaches **every** open Session of the Project in **every** Window. It is not a first-match lookup; that part works (pinned by `ProjectLiveApplyTests.savingABackgroundAppliesItToEveryOpenSessionOfThatProjectAndNoOther`, which opens the Project in two Windows).
- **Callers.** The Project Editor (`Views/ProjectEditorWindowController.swift:90`, from `ProjectEditorViewModel.save()` at `Model/ProjectEditorViewModel.swift:872`), which also serves the Sidebar's Edit Project… item (#0653). On `main` only, `batty project edit` over XPC (`Runtime/AppStateStore+ProjectWriteXPC.swift:117`, #0700, target 1.5.0; not on release/1.4).
- **What it applies.** Name, color, symbol, Theme, and `Project.background` through `seedProjectBackground` (`AppStateStore.swift:1731` main / `:1699` release), which calls `session.setBackgroundOverride`. `TerminalBackgroundSettings` carries the image path, fit, position, `imageOpacity` and `terminalOpacity`, so both opacities travel with it. The doc comment (`AppStateStore.swift:1694-1700`) states the gap: "Layout, Pane and Tab backgrounds, Tab directories and commands, and mute wait for the next open." #0653 Plan item 6 put per-Pane and per-Tab backgrounds out of scope; `ProjectLiveApplyTests.layoutAndPaneBackgroundsWaitForTheNextOpen` pins that.
- **How backgrounds cascade at runtime.** Session → Pane → Tab: a Tab shows `tab.backgroundOverride ?? pane.backgroundOverride ?? session` (`Runtime/TabRuntime.swift:336` `setBackgroundOverrides`, `Runtime/PaneRuntime.swift:210-211, 400-404`). A Session-level change pushes down through `SplitTree.setSessionBackgroundOverride` → `PaneRuntime.setSessionBackgroundOverride` (`PaneRuntime.swift:237`), and Tabs or Panes with their own override keep it. So Tabs that follow the Session already update; Tabs and Panes holding their own value do not.
- **Root cause.** When a Project opens, `ProjectTreeBuilder.build` (`Model/ProjectTreeBuilder.swift:93` for Tabs, `:177` for Panes) writes each Project Tab's and Pane's background into that runtime Tab's or Pane's **own** `backgroundOverride`, the same field a user's Sidebar/Pane/Tab background edit writes. After open, the runtime keeps no link from a Pane or Tab back to its Project slot and no record of which value came from the Project. So `applyProjectSave` has nothing to update them by, and (1) per-Pane/per-Tab edits in the editor never reach open Sessions, and (2) a Project-level edit is hidden in every Pane/Tab that was opened with its own Project value, because the own override wins the cascade.
- **How many Sessions one Project can have.** Several. `openProject(id:mode:)` defaults to `.focusExistingOrOpen` (selects the first existing one), but `.openNew` always opens another, in any Window (`AppStateStore.swift:1673-1679`).
- **Branch differences.** The background path is identical on both branches: `applyProjectSave`'s body, `seedProjectBackground`, `SessionRuntime`, `SplitTree` and `ProjectTreeBuilder` are unchanged between them. `PaneRuntime.swift` and `TabRuntime.swift` differ only in unrelated main-only work (`addTab(workingDirectory:command:select:)` from #0667, command-finished observers from #0668); `ProjectEditorViewModel.swift` differs from #0700's validation extraction. Only `main` has the CLI caller. Keep the fix inside the background code so the cherry-pick applies cleanly; if it touches `addTab` or the `TabRuntime` init, expect a conflict on release/1.4.

## Expected behavior

Saving a Project (Project Editor, Edit Project…, and on main `batty project edit`) updates the background image, fit, position, image opacity and terminal opacity in **every** Session open from that Project, in every Window, selected or not:

1. **Project background** applies to the Session as today (`seedProjectBackground`), including the #0653 changed-fields rule.
2. **Per-Pane and per-Tab Project backgrounds** that changed in the save apply to the matching Pane or Tab of each open Session, **if that Pane or Tab still holds the value the Project gave it** (or the value of the previous save). Setting one to nil in the Project returns that Pane/Tab to following the Pane/Session.
3. A Pane or Tab whose background the user changed in the running Session (Pane or Tab background sheet) keeps the user's value.
4. Panes and Tabs the user added after open, or that no longer map to a Project slot (closed, moved), follow the cascade only, which already updates them.
5. Missing images and images still syncing are marked as at open (`checkBackground` / `projectBackgrounds.checked`, `pendingTabImage`, `requestTabImages`).

**Telling inherited from overridden.** The model does not record it today. Recommendation: at open, `ProjectTreeBuilder` stamps each runtime terminal Pane with its Project slot index and each Tab with (slot, tab index), plus the checked `TerminalBackgroundSettings?` it seeded (`@ObservationIgnored`, e.g. `projectSeed`). On save, for each Pane/Tab with a stamp: if its current `backgroundOverride == projectSeed`, it is inherited, so write the new Project value (through the restore-style setters, not `PaneRuntime.setBackgroundOverride`, which clears every Tab's own value) and update `projectSeed`; otherwise it is a user override, so leave it. Update Project should refresh the stamps so the Session's current values become the new seeds. The planner may choose a different provenance scheme, but must not compare against the stored previous Project alone: `checkBackground` can rewrite the path, so the seed has to be the checked value that was actually applied.

Writes happen from the save action (event origin), per `docs/swiftui-observation-rules.md`; no `Task` hops.

### User checklist

1. Open one Project twice (Open in New Session, or once in each of two Windows), with a Tab that has its own background in the Project. Edit that Tab's image and both opacities in the Project Editor and Save. Both Sessions change at once.
2. Do the same with a Pane background.
3. In one Session, change that Tab's background from the Tab chip menu, then edit it again in the Project. That Session keeps yours and the other one updates.
4. Clear the Tab's background in the Project. The Tab shows the Pane's or Project's background.
5. Change only the Project background. Every following Tab in both Sessions updates, and Tabs with their own background keep theirs.
6. Remove a Tab in the editor and change another Tab's background in the same save. Nothing per-Tab changes until you open the Project again (expected).

### Open questions (not blocking; defaults chosen above)

- **Shape-changing saves.** Default: a save that adds, removes or re-kinds a Pane, or adds or removes a Tab, applies no per-level backgrounds and clears the open Sessions' seeds. Without stable slot ids there's no safe way to tell which Tab was removed. Stable ids on `ProjectPane`/`ProjectTab` would make add and remove precise, but they change the stored format; that's a 1.5 feature, not a 1.4.2 fix.
- **Moved Tabs.** Default: a Tab dragged to another Pane keeps its seed and still follows its Project slot, as its startup command does. The issue's rule 4 says moved Tabs should follow only the cascade. Doing that means changing the Tab move code, which is next to the #0667/#0668 code, so it isn't done.

### Gotchas for the implementer

- Compare the level's current value against the seed, never against `previous`'s stored value: `checked` can strip a missing path (issue, "Telling inherited from overridden").
- Never call `PaneRuntime.setBackgroundOverride` here: it clears the Tabs' own values and `pendingImage`.
- Update Project with a runtime layout whose shape matches the Project but whose Tabs were moved between Panes can map a moved Tab to its old slot. The digest rule makes this harmless for the usual case (same image). Note it in `## Gotchas` if the tests show otherwise.

## Fix

Followed the Plan. Each Terminal Pane and its stored Tabs are stamped at open (`ProjectTreeBuilder`) with a `ProjectBackgroundSeed` (slot, Tab index, the checked value applied). `applyProjectSave` now calls the new `applyProjectSlotBackgrounds` for every open Session of the Project: a level whose own value still equals its seed takes the saved value through the restore setters (Tabs' own values and pending images survive a Pane write); a level whose value matches the saved one (equal, or same image digest at another path, the Update Project case) adopts it as its seed; anything else is the user's and is left alone. A save that changes the layout's shape clears the seeds and applies nothing per level. A level left waiting on an image triggers `requestTabImages`, and `tabImageArrived` moves the seed forward with the arrived path. No deviations.

A Pane or Tab whose background you changed in the Session keeps yours. (#0702)"
