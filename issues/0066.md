## Description

When Batty launches, the default session's terminal pane is visible but does not hold keyboard focus / first responder. Keystrokes go nowhere (or to the window's chrome) until the user clicks inside the terminal pane. This is unusual for a terminal app — Terminal.app, iTerm2, Ghostty, and Alacritty all auto-focus the terminal on launch.

Hypothesis: `TerminalSurfaceView` (NSViewRepresentable wrapping libghostty's `AppTerminalView`) doesn't auto-take first responder when the window first appears. SwiftUI's NSViewRepresentable bridge doesn't propagate focus state to AppKit by default — you have to explicitly call `becomeFirstResponder` on the underlying NSView, or use `.focused` / `@FocusState` bindings that the bridge respects.

## Steps to reproduce

1. Launch Batty (cold start, no existing window).
2. Without clicking anywhere, try to type. Nothing reaches the shell.
3. Click anywhere inside the terminal pane area.
4. Type — now the keystrokes land in the shell as expected.

## Expected behavior

On launch, the active tab's terminal surface holds first responder. The user can immediately type without clicking. This should also apply to:

- A new session opened via `Cmd-N` — focus lands in the new session's terminal.
- A new tab opened via `Cmd-T` — focus lands in the new tab's terminal.
- A new pane created by split (`Cmd-D`) — focus lands in the new pane's terminal (the model already sets `tree.focusedPaneID` to the new pane).
- Window restore after `Cmd-H` / `Cmd-M` — focus returns to whatever was previously focused.

## Notes

- Likely fix path: in `PaneView` (or the wrapper around `TerminalSurfaceView`), call `tab.terminal.surface?.becomeFirstResponder()` after `.onAppear`. Or more idiomatic: bridge SwiftUI `@FocusState` to AppKit first responder via the NSView's `becomeFirstResponder` / `resignFirstResponder` overrides.
- This is independent of `#0051` / `#0060` (click-to-focus on a non-focused pane). Those issues are about *moving* focus between panes by clicking. This one is about *initial* focus on launch.
- The bug likely became more visible after `#0063`'s recent `WindowGroup → Window` change because the auto-window-creation that was previously firing on `Cmd-N` accidentally gave the surface focus on creation. Now that `Cmd-N` properly hits our action and creates an in-window session, focus stays where it was — which is "nowhere" on initial launch.
- macOS first-responder propagation through SwiftUI's NSViewRepresentable is famously finicky; sample code at `Documentation/AppKit/Cocoa First Responder` may have useful patterns.

## Acceptance criteria

- Cold launch: typing immediately lands in the shell, no click needed.
- After `Cmd-N`: typing lands in the new session's shell.
- After `Cmd-T`: typing lands in the new tab's shell.
- After `Cmd-D` / `Cmd-Shift-D`: typing lands in the new pane's shell.
- After clicking the sidebar to switch sessions: typing lands in the selected session's focused pane's shell.

## Out of scope

- Auto-focus behavior when restoring from `Cmd-Tab` or window minimize. macOS's default first-responder restoration should handle this.
- Pane-level focus rotation logic (`#0051` / `#0060`) — covered separately.
- Focus indication styling (`#0052` — done).

## Root cause

SwiftUI's `NSViewRepresentable` bridge does not auto-promote the wrapped `AppTerminalView` to first responder when its hosting window becomes key. libghostty's `AppTerminalView` declares `acceptsFirstResponder = true`, but AppKit's automatic first-responder selection at window key-time picks whichever responder happens to be earliest in the chain, and SwiftUI's hosting layer interposes its own (non-key-handling) responders. The result: on cold launch and after every Cmd-N / Cmd-T / Cmd-D, the surface NSView is in the hierarchy but no one ever calls `makeFirstResponder` on it, so keystrokes fall on the window chrome until the user clicks the pane.

## Fix

Added a `TerminalSurfaceFocuser` helper that walks `NSApp.windows` recursively for the `AppTerminalView` whose libghostty `delegate` is a given `TerminalViewState`, then calls `window.makeFirstResponder(view)` on the match. Identity is delegate-pointer-based (`view.delegate === terminal`) because `AppTerminalView.surface` is package-internal and not callable from BattyKit.

The helper has a `focusWhenReady(terminal:)` variant that retries once after a 50ms delay, covering the cold-launch race where the NSView is not yet attached when the SwiftUI hook fires.

Triggers wired:

- `PaneView` — `.onAppear` on each `TerminalSurfaceView` (initial mount); `.onChange(of: pane.activeTabID)` (Cmd-T / tab switching); `.onChange(of: isPaneFocused)` (Cmd-D / new pane becomes focused; Cmd-Option-arrows).
- `SessionDetailView` — `.onAppear` (initial window), `.onChange(of: store.selectedSessionID)` (sidebar selection / Cmd-N).

Each trigger guards on `tab.id == pane.activeTabID && isPaneFocused` so background tabs and non-focused panes do not yank focus.

## Files changed

- `BattyKit/Sources/BattyKit/TerminalSurfaceFocuser.swift` — new helper that locates the `AppTerminalView` for a `TerminalViewState` and routes first-responder.
- `BattyKit/Sources/BattyKit/PaneView.swift` — added `.onAppear` and `.onChange` hooks on `TerminalSurfaceView` to request focus when the active tab in the focused pane becomes visible.
- `BattyKit/Sources/BattyKit/SessionDetailView.swift` — added `.onAppear` and `.onChange(of: selectedSessionID)` to route focus into the newly-selected session's focused pane's active tab.

## Gotchas

- `AppTerminalView.surface` is internal (not `public`) in libghostty-spm, so the focuser identifies the matching view via `view.delegate === terminal` — the `delegate` is set to the `TerminalViewState` instance during `configureView`. If a future libghostty release drops the delegate-as-state arrangement, this lookup would need to change.
- The 50ms retry covers the cold-launch race, but it's a delay, not a callback. A more robust path would be to plumb a "view did move to window" callback from libghostty back into Batty; that requires an upstream change to expose a hook on `AppTerminalView`. The retry path keeps Batty as a plain consumer of the SPM.
- Manual verification still required — the user has not yet verified that cold-launch / Cmd-N / Cmd-T / Cmd-D all land focus correctly on their machine. Build + tests pass; visual confirmation outstanding.
