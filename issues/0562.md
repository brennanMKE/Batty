## Description

The #0514 review (Session Reminders, squash-merged as `2bfa3acb`) approved the work but listed four non-blocking findings, N1 to N4. This issue tracks them. ## Findings

### N1. No test covers the `kind == .bell` guard that hides ratings on Reminder rows

`BattyKit/Sources/BattyKit/Runtime/AppStateStore+BellCapture.swift:113`:

```swift
guard entry.kind == .bell, entry.sessionID != BellFeedEntry.systemID, isBellCaptureEnabled else { return .hidden }
```

`entry.kind == .bell` is what makes `bellRatingAvailability(for:)` return `.hidden` for a `.reminder` entry. Without it, a Reminder row would show the Good/Bad Summary rating menu when Bell Feed capture is on, disabled as `.notCaptured` because Reminder entries are never marked captured. The reviewer removed the guard and the full unit suite (3275 tests) still passed.

`BattyKit/Tests/BattyKitTests/BellFeedRatingTests.swift` tests the other two conditions: `captureOffHidesRatingsAndWritesNothing` covers capture off, and `systemEntryIsNeverRatable` covers the system entry. No test there or anywhere in `BattyKit/Tests` calls `bellRatingAvailability` on a `.reminder` entry.

**Fix:** add a test next to `systemEntryIsNeverRatable`, for example `reminderEntryIsNeverRatable`. It should turn capture on, record a `BellFeedEntry` with `kind: .reminder` and a real Session id, and expect `bellRatingAvailability(for:) == .hidden`. Marking the entry captured (`bellFeed.markCaptured`) as well makes the test fail in both cases if the guard is removed: `.available` when captured, `.notCaptured` when not. Confirm that it fails with the guard removed.

Side note, not part of N1: `ratableEntry(id:)` (same file, line 157) checks capture, the captured set and the system id, but not `kind`. So `rateBellEntry` and `suggestBellText` rely on Reminder entries never being marked captured. The plan can decide whether that needs its own guard or test.

### N2. `ManualSchedulingClock`'s comment gives `SystemClock` as the reason for the lock

`BattyKit/Sources/BattyKit/Testing/ManualSchedulingClock.swift:10-13` says:

> Lock-guarded rather than actor-isolated for the same reason as `SystemClock`: `SchedulingClock` is `nonisolated`, …

`SystemClock` (`BattyKit/Sources/BattyKit/Runtime/SchedulingClock.swift:70`) has no lock. The protocol doc in the same file says so (line 28: "`SystemClock` has no mutable state; `TestClock` is lock-guarded"). The type the comment means is `TestClock` (`BattyKit/Tests/BattyKitTests/TestClock.swift:11`, "Lock-guarded and `nonisolated`/`Sendable` rather than actor-isolated"). `TestClock` is in the test target, so the comment should name it as `TestClock` (`BattyKitTests/TestClock.swift`), the way the protocol doc does.

**Fix:** change "`SystemClock`" to "`TestClock`" in that sentence.

### N3. Concepts.md's version history capitalizes "A Shared Project's image"

`Concepts.md:316` reads "Previously 0.23 — 2026-11-04: A Shared Project's image travels through iCloud Drive, behind a flag (#0551)." Before #0514 the line read "Previously 0.23 — 2026-11-04: a Shared Project's image …", with a lowercase "a" (`git show 2bfa3acb^:Concepts.md`, line 301). The other entries put a lowercase word after the colon.

**Fix:** change "A Shared" back to "a Shared". Don't bump the document version for this.

### N4. docs/notifications.md says no "kind" field exists

`docs/notifications.md:90-93`, the `batty notify` (#0284) paragraph, says a CLI entry "rides the same `BellFeedEntry` shape as a BEL/OSC-9 entry, unmodified — no new "kind" field distinguishes it". Since #0514, `BellFeedEntry` has a `kind: Kind` field (`.bell` / `.reminder`, `BellFeedStore.swift:59-64`). The next paragraph in the same doc describes `kind == .reminder`.

What the sentence means still holds. `AppStateStore.recordCLINotification` builds its `BellFeedEntry` without a `kind:` argument (`AppStateStore.swift:2130`), so the entry gets the default `.bell` and looks like any BEL/OSC-9 row. Only the wording is out of date.

**Fix:** reword it to say that a CLI row is `kind == .bell`, the same as a BEL/OSC-9 entry, and that nothing marks it as coming from the CLI apart from its message text.
