## Description

**HIGH. Related to #0612.** Three related ownership problems in Theme application:

1. **Echo re-apply.** Four places write the global Theme `UserDefaults` key and apply it: the Theme Selector, the Command Palette's "Theme: X" commands, the View → Theme menu in `BattyCommands`, and the Settings picker. Settings' picker also has `.onChange(of: selection.wrappedValue)` on its `@AppStorage`, which fires when **any** of the other three writes the key and calls `applyThemeToAllSurfaces` again: `controller.setTheme` on every Tab of every following Session in every window, plus a palette write. It stops after one step, but it doubles the work and runs inside the Settings window's update transaction, treating a downstream flip as a Settings choice.
2. **Preview without restore.** Arrowing in the global `ThemeSelectorView` previews with `applyThemeToAllSurfaces`, and in `SessionThemeSelectorView` with `applyTheme(_:to:)`. Both only write libghostty and the palette. `cancelSelection` in both just dismisses, and neither presenter has an `onDismiss`. Esc/Cancel leaves every surface on the previewed Theme while the stored preference or `themeOverride` still names the old one; the next appearance change, Session switch or new Tab silently jumps back. The doc comment at `ThemeSelectorView.swift:306` says "Cancelling restores whichever theme was active before the picker opened" — false.
3. **View-init migration reach.** `ThemeSelectorView.init` calls `ThemePreference.activeTheme()` and `SessionThemeSelectorView.init` calls `effectiveTheme`, both of which run `migrateAndSeedIfNeeded`, a `UserDefaults` write that `@AppStorage` observers watch. It can't fire today because `AppStateStore.init` runs it first, but view init is supposed to be structurally pure, and the comment that justifies it cites stale lines.

## Root cause

Confirmed as described. Four production writers (plus the UI-test driver) each wrote the global Theme key to `UserDefaults.standard` and applied it themselves, and Settings' `themePicker` `onChange` re-applied on every key flip, whoever wrote it. Arrow-key previews applied Themes with no record that a preview was pending and no `onDismiss` on either presenter, so Esc left surfaces on the previewed Theme. Both selector inits resolved through `activeTheme()`/`effectiveTheme`, which run `migrateAndSeedIfNeeded` (a defaults write), and read `.standard` rather than the store's `preferences`.

## Fix

Implemented the plan as written:
- `AppStateStore.setGlobalTheme(named:[isDark:])` is the only writer of the global Theme keys (into `preferences`); it applies only when the slot is the current appearance's and the name resolves. The Theme Selector, Command Palette, View → Theme menu, Settings picker (`Binding` setter) and `UITestDriver.applyTheme` all call it. Settings' theme `onChange` and `appliesNow` are gone, as are the font-size / cursor-style / cursor-blink / system-notifications `onChange`s (moved into `Binding` setters). `@Environment(\.colorScheme)` was removed from `AppearanceSettingsView` (no other use).
- Preview is store-owned transient state (`@ObservationIgnored globalThemePreviewPending`, `sessionThemePreviewIDs`): `previewGlobalTheme` / `previewSessionTheme` set it, `setGlobalTheme` / `setSessionTheme` clear it, and the presenters' `onDismiss` calls `endGlobalThemePreview()` / `endSessionThemePreviews(in: windowRuntime)` to re-apply the committed Theme. `cancelSelection` still only sets `isPresented = false`.
- `ThemePreference.storedTheme` / `storedEffectiveTheme` are pure, non-migrating reads; the selector inits use them with `store.preferences`. The stale comment block and the false "Cancelling restores…" doc comment were replaced.
- `ThemeCard` exposes `accessibilityValue("active")` for the UI test.
- No new `themeChrome.update` call site (#0612 boundary).

Small deviations: `UITestDriver`'s `.applyTheme` guard became `!= nil` (the bound `theme` was otherwise unused, a compiler warning).

## Plan

Written 2026-11-13 against `issue/0616` at `79925a8d`. Premises re-verified: every line the issue cites is current (SettingsView `:136/:146/:149` side-effect `onChange`s, `:176-199` `themePicker` with its `onChange` at `:192-197`, `:367`; ThemeSelectorView `:99-111`, `:270-296`, `:306`, `:341`, `:493-516`; CommandPaletteView `:198-200`; BattyCommands `:31-32`, `:729-736`; AppStateStore `:1366`). The three view writers write `UserDefaults.standard`, while the store reads `preferences`. They are the same suite in production (`AppStateStore.shared` takes the default `.standard`), but tests can't observe the view writes. The store-owned write below uses `preferences`, which fixes that too.

**Scope boundary with #0612.** #0612 owns `ThemeChrome.palette` and its writers. This plan adds **no new `themeChrome.update` call site**: preview, commit and restore all route through the existing `applyThemeToAllSurfaces`, `applyTheme(_:to:)` and `applyActiveSessionTheme(for:)`, so #0612's list of six call paths stays accurate. Don't touch `applyChrome`, `applySelectionTheme`, `contentWindowBecameKey` or `WindowLifecycleController`.

### Approach

One store-owned write path for each fact:

- **Global Theme.** `AppStateStore.setGlobalTheme` is the only code that writes `ThemePreference.dark/lightDefaultsKey`. It persists the name and applies it when that slot is the current appearance's.
- **Session Theme.** `AppStateStore.setSessionTheme` is the only code that writes `themeOverride` from the selector.
- **Preview.** Preview is transient, store-owned state: a flag the commit clears and the sheet's `onDismiss` consumes. A Cancel/Esc dismissal re-applies the committed Theme. A dismissal after a commit does nothing.
- **Views.** Views stop deciding anything. Settings binds through a `Binding` setter that calls the store, and its `onChange` echo is deleted. The selectors read the committed Theme through a pure, non-migrating read of `store.preferences`.
