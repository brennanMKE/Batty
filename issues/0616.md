# 0616 — Global and Session Theme application has no single owner: Settings re-applies other writers' choices, and Theme Selector Cancel never restores the previewed surfaces

| | |
|---|---|

## Description

**HIGH. Related to #0612.** Three related ownership problems in Theme application:

1. **Echo re-apply.** Four places write the global Theme `UserDefaults` key and apply it: the Theme Selector, the Command Palette's "Theme: X" commands, the View → Theme menu in `BattyCommands`, and the Settings picker. Settings' picker also has `.onChange(of: selection.wrappedValue)` on its `@AppStorage`, which fires when **any** of the other three writes the key and calls `applyThemeToAllSurfaces` again: `controller.setTheme` on every Tab of every following Session in every window, plus a palette write. It stops after one step, but it doubles the work and runs inside the Settings window's update transaction, treating a downstream flip as a Settings choice.
2. **Preview without restore.** Arrowing in the global `ThemeSelectorView` previews with `applyThemeToAllSurfaces`, and in `SessionThemeSelectorView` with `applyTheme(_:to:)`. Both only write libghostty and the palette. `cancelSelection` in both just dismisses, and neither presenter has an `onDismiss`. Esc/Cancel leaves every surface on the previewed Theme while the stored preference or `themeOverride` still names the old one; the next appearance change, Session switch or new Tab silently jumps back. The doc comment at `ThemeSelectorView.swift:306` says "Cancelling restores whichever theme was active before the picker opened" — false.
3. **View-init migration reach.** `ThemeSelectorView.init` calls `ThemePreference.activeTheme()` and `SessionThemeSelectorView.init` calls `effectiveTheme`, both of which run `migrateAndSeedIfNeeded`, a `UserDefaults` write that `@AppStorage` observers watch. It can't fire today because `AppStateStore.init` runs it first, but view init is supposed to be structurally pure, and the comment that justifies it cites stale lines.

## Rule violated

- `docs/swiftui-observation-rules.md`, "Two-way model ↔ AppKit sync": one authority per fact; never reconstruct intent from downstream observable flips.
- Same doc, "What counts as SwiftUI-driven update code": view `init`s must not write observed state (reachable path, even if guarded today).
- Same doc, "`Task` and async work": work that must follow a sheet's dismissal goes in `onDismiss` (#0475).

## Evidence

- **Proven:** the echo path; that no restore path exists; the stale comment.
- **Inferred:** whether the Settings scene's graph stays alive after its window closes (which would put the echo on every Theme commit after Settings was first opened). The visible cancel bug: no UI test covers cancel (`BattyUITests/ThemeTests.swift`).

## Fix direction

- One owner: `AppStateStore.setGlobalTheme(named:isDark:)` writes the key and applies. Theme Selector, Command Palette, the View → Theme menu and Settings all call it. Settings' picker uses `Binding(get:set: { store.setGlobalTheme(…) })`; delete its `onChange`. Move the font/cursor/notification side effects into their controls' setters the same way.
- Preview as owned transient state: record the committed Theme when the sheet is presented (in the presenting action), and in the sheet's `onDismiss` re-apply it unless a commit happened. Or a store-owned `previewTheme` that `onDismiss` clears. Fix the false doc comment.
- Give the selector views a pure read (e.g. `ThemePreference.storedTheme(isDark:)` with no migration), or pass the active Theme name in from the presenting action. Delete the stale comment.
