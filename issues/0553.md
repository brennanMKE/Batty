# 0553 — A lingering projects.json.bak blocks every background image Remove indefinitely, and the user can't tell why or clear it from the app

| | |
|---|---|
| **Status** | open |
| **Module** | Projects / Settings |
| **Platform** | macOS |
| **First seen** | 2026-11-04 |

## Description

Once `projects.json.bak` exists, every Remove in the Background Images window is refused, on every launch, until the user finds and deletes that file by hand. The refusal says Batty "can't read all of your saved Projects", which doesn't name the file and is untrue when `projects.json` itself is healthy. Batty offers no other way out.

**It fails safe: no data is lost.** Removing nothing is the intended rule, because a leaked image is cheaper than a lost one, and a backup may be the user's only copy of Projects that were dropped.

**Not for 1.3.5.** The Remove path exists only through #0552, which is on `issue/0552` and not yet on `main`. This can't be worked until #0552 lands. The #0552 review raised it. Related: #0543, covered under "How this relates to #0543".

## What holds it in place

Read from `issue/0552` at `eb6f1c8e`.

- **Only one writer.** `ProjectStore.writeFile` (`Model/ProjectStore.swift:437-441`) writes the backup, on the first save after a load that dropped Projects, hit a newer version or couldn't decode. A later such save overwrites it.
- **Nothing deletes it.** The store's only `removeItem` (`:525`) is for its temp file. A search of the sources, Help and `website/` finds no restore or cleanup UI and no mention of the file for users.
- **The check only looks for the file.** `mayReferenceUnlistedImages` (`ProjectStore.swift:172-176`) is true whenever the file exists, whatever it holds and whichever image is being removed, so it stays true across launches.
- **Remove is refused.** `removalRefusal` (`Runtime/AppStateStore+BackgroundImages.swift:65`) returns the text above, and `BackgroundImagesView` shows it with only a dismiss button. `BackgroundImagesModelTests.refusesWhileABackupExists` pins the refusal.
- **Reclaim stops too.** `ProjectBackgroundLibrary.reclaim` (`Settings/ProjectBackgroundLibrary.swift:73`), called at quit, returns without removing anything and writes only a `logger.notice`, so unreferenced Project background images accumulate.

## Expected behavior

- The user can tell that a backup is why Remove is refused, and has a way out from inside Batty.
- That way out doesn't silently discard the backup, which may be the only copy of dropped Projects.
- Remove and `reclaim` work again once the user has taken it.

The planner decides what the way out is.

## Actual behavior

Every Remove is refused with text that doesn't mention the backup, for as long as the file exists. The only way out is deleting a file in Application Support that Batty never tells the user about.

## Steps to reproduce

Needs #0552. Use a temp `projects.json` (`BATTY_UI_TEST_PROJECTS_FILE`, as the Projects UI tests do), never a real one.

1. Start with a valid `projects.json` and write any `projects.json.bak` beside it.
2. Open the Background Images window and choose Remove on any image, whether or not anything uses it.
3. The refusal appears and nothing is removed. Quit and reopen: it's refused again.

To create the backup the way a user would, write `{ not json` to `projects.json`, open Batty and save a Project.

## How this relates to #0543

They cover two sides of the same backup, and neither fixes the other.

- **#0543 is about the load:** what the user is told while `projects.json` is corrupt, partly loaded or from a newer version, up to the first save.
- **This issue is about what follows that save:** `projects.json` is healthy again, so the #0543 states no longer apply and its messages won't appear, yet the backup is still blocking. #0543's table records this for a dropped Project: "The next launch loads a healthy file, so the dropped Project is only in `.bak`, with no message then either."
- **They meet at the same refusal.** Before the first save, `unreadableOriginal != nil` makes `mayReferenceUnlistedImages` true with no backup on disk. There the refusal's wording is accurate, and the way out is #0543's concern, not this issue's.

Two of #0543's findings limit any way out here, and are recorded there as reproduced:

1. A second bad load replaces the first backup, so a backup isn't guaranteed to hold what the user first lost.
2. Restoring by hand while Batty runs loses the restore, so any wording or action that suggests restoring has to account for it.

**Recommendation: plan both together.** Both need one account of what the backup is and what the user can do with it, and #0543 says a user can't learn that `.bak` exists. Separate plans risk two messages that disagree about it. The planner decides whether they land on one branch or two, and whether #0543's two limits get fixed here, there or separately. #0543 is unblocked, as #0542 has landed, but planning them together means waiting for #0552 here.

## Notes

### Shipped code has the reclaim half

`mayReferenceUnlistedImages` and the `reclaim` guard are already on `main` and `release/1.3` (`ProjectBackgroundLibrary.swift:80` on both). So a 1.3.x install with a backup already skips reclaim silently. That only leaks images and has no user-visible refusal, so it doesn't change the "not for 1.3.5" call, but it means an install can already hold a backup when Remove first ships.

### Not verified

- Read from the code and its tests, not run: the app wasn't launched, and the steps to reproduce haven't been followed in it.
- How often real installs hold a backup is unknown. Nobody has reported this.
