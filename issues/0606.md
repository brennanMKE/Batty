## Description

**HIGH. Related to #0601.** `SystemMetricsPaneView` puts an AppKit-backed `List` (an `NSTableView` in its own `NSScrollView`, with a hosting view per row) inside SwiftUI's outer `ScrollView`, inside the detail column's `NSHostingView`. Every 1 s sample replaces `snapshot`, `body` re-sorts every process row, and the table reloads. In #0601's `StatusPaneLayoutConvergenceTests` sweep, System Metrics' worst settle made **951** `_postWindowNeedsUpdateConstraints` requests, against 10 for Git Status and 0 for Process Status and LM Studio. It converged, but it is by far the largest layout requester among the status views, in the window whose convergence cap the #0601 Prod crash hit.

## Resolution notes

> 🟢 Resolved 2026-11-13 — System Metrics' process list is a pid-keyed `LazyVStack` of `Equatable` rows in the Pane's single `ScrollView`, sorted once per tick in `SystemMetricsPaneContent`, removing the nested `List` that made hundreds of window update-constraints requests every 1 s tick.

## Review

Approved first pass. Checked: one scroller (no `List`, no inner `ScrollView`, no pinned header); sort lives in the model, applied once in `performTick()` after the generation guard, and `setProcessSort(_:)` is header-button (event-origin) only and guards equal values; `ForEach` keyed by `ProcessRow.id` (pid); `SystemMetricsProcessRowView` stores only `row` and `colors`, both with synthesized `Equatable` covering every displayed input (name, pid, path for the menu's disabled state, CPU, memory, palette); context menu, `system-metrics-*` accessibility identifiers and theming kept; comments and docs match the code; Root cause does not claim the #0601 crash. The tick test's majority-of-ticks assertion is accepted: the old code fails 12 of 12 ticks at 348+ requests, the fix gives 0 on most ticks, so `over.count * 2 < ticks.count` separates them with wide margin, the `sortedProcesses.count` expectation keeps it non-vacuous, and every tick must still converge. The residual single-tick spikes (36-160, at most 3 of 12) are unexplained and recorded in Gotchas; they are an order of magnitude below the removed per-tick cost and not a blocker. No code changed in review.

## Root cause

The process list was a SwiftUI `List` (an `NSTableView` in its own `NSScrollView`, a hosting view per row) nested inside the Pane's outer `ScrollView`, and `body` re-sorted every row on each evaluation. Every 1 s sample replaced `snapshot`, the table reloaded, and the window received hundreds of `_postWindowNeedsUpdateConstraints` requests **per tick** (348–376 at 480×600 in the new test before the fix), scaling with the visible table height rather than the row count. Replacing only the `List` takes typical ticks to 0, which confirms the issue's inferred cause.

This removes the largest steady per-tick layout requester among the status views in the detail column's hosting tree, in the window whose convergence cap the #0601 Prod crash hit. It is **not proven** to be that crash's cause: #0601's probe never reproduced the crash.

## Fix

As planned:

- `ProcessRowSort` (in `SystemMetricsSnapshot.swift`): field + direction, `sorted(_:)` with one comparator whose ties break by pid ascending in both directions (so equal-key and denied rows keep their order between ticks), and `toggled(for:)` (the header button's logic).
- `SystemMetricsPaneContent` owns `processSort` and `sortedProcesses`. `performTick()` sorts once per tick after the generation guard; `setProcessSort(_:)` (called only from the header buttons) guards equal values and re-sorts the current snapshot without sampling. The #0614 properties were not touched.
- `SystemMetricsPaneView`: the `List`, `SortField`, the two `@State` sort properties and `sortedRows` are gone. The list is a `LazyVStack(spacing: 0)` of `SystemMetricsProcessRowView(...).equatable()` keyed by `ProcessRow.id` (pid), with the same background, corner radius and border, no height frame, no pinned header.
- New `SystemMetricsProcessRowView` (`View, Equatable`, stores only `row` and `colors`): the old row body, a 1 pt bottom separator overlay, `.contentShape(Rectangle())`, and the old context menu (Copy PID, Reveal Executable in Finder disabled without a path). Column widths moved here and the header reads them.

**Divergence from the plan: the tick test's assertion.** The plan asserted every tick ≤ 24. With the fix, filtered runs gave 0 on all 12 ticks, but suite runs showed an occasional single tick of 36–160 (e.g. `1100 rows 720x900 overlay tick 3=160`, `470 rows 720x900 legacy tick 2=75`), at most 3 of 12 per case, including with the suite temporarily `.serialized`. The test therefore requires **fewer than half** the ticks over the ceiling (`over.count * 2 < ticks.count`) and lists every tick's count in its failure message; each tick must still converge. The old code fails it with 12 of 12 ticks over. The test's doc comment states this.

### Design

One scroller (the existing outer `ScrollView`), a `LazyVStack` of rows keyed by pid, sorting moved into the model, and an `Equatable` row view so a tick only re-renders rows whose values changed.

1. **`BattyKit/Sources/BattyKit/Runtime/SystemMetricsSnapshot.swift`**: add a pure value type next to `ProcessRow`:
   ```swift
   public nonisolated struct ProcessRowSort: Equatable, Sendable {
       public enum Field: String, CaseIterable, Sendable { case name = "Name", pid = "PID", cpu = "CPU", memory = "Memory" }
       public var field: Field
       public var ascending: Bool
   ```

## Rule violated

- `docs/swiftui-observation-rules.md`, "AppKit interop hazards": layout participants in the hosting tree must converge cheaply; a participant that re-dirties the window every pass is what hits AppKit's cap (#0601).
- swift-guidance `ui.md`/`performance.md`: one scroll owner; don't nest an AppKit-backed `List` in a `ScrollView`; keep `body` work cheap.

## Evidence

- **Proven (measured):** the 951 figure. **Correction to the audit:** it is the worst single settle across the whole sweep (3 widths × 8 heights × 2 scroller styles, plus 3 sampler ticks at each), not a per-tick figure, and the fixture's `TickingMetricsSampler` has 40 processes, not the ~470 of a real system. A real process list is ~10× larger, so the production figure is likely higher.
- **Inferred:** that the nested `List` is the cause. The four status views differ mainly in this `List`, the `LazyVGrid`s and two drawing-only `GeometryReader`s. The planner should confirm by measuring with the `List` replaced before choosing the fix.

## Fix direction

Give scrolling one owner (layout ownership, no timing change):

- Replace the `List` with a `LazyVStack` of `processRow`s, keeping separators and `contextMenu`, inside the existing outer `ScrollView`. That drops the nested `NSScrollView`/`NSTableView` and the per-row hosting views. Or make the `List` the only scroller and put the dashboard sections in its header.
- Optionally have `SystemMetricsPaneContent` publish rows already sorted for the current sort key, so `body` stops sorting every tick.
- Keep #0601's lesson: no hand-built `NSScrollView` host (round 1 of #0601 crashed in the VM).
