# 0606 — System Metrics nests a List inside its ScrollView and refills it every second, making the most layout requests of any status view

## Description

**HIGH. Related to #0601.** `SystemMetricsPaneView` puts an AppKit-backed `List` (an `NSTableView` in its own `NSScrollView`, with a hosting view per row) inside SwiftUI's outer `ScrollView`, inside the detail column's `NSHostingView`. Every 1 s sample replaces `snapshot`, `body` re-sorts every process row, and the table reloads. In #0601's `StatusPaneLayoutConvergenceTests` sweep, System Metrics' worst settle made **951** `_postWindowNeedsUpdateConstraints` requests, against 10 for Git Status and 0 for Process Status and LM Studio. It converged, but it is by far the largest layout requester among the status views, in the window whose convergence cap the #0601 Prod crash hit.

## Rule violated

- `docs/swiftui-observation-rules.md`, "AppKit interop hazards": layout participants in the hosting tree must converge cheaply; a participant that re-dirties the window every pass is what hits AppKit's cap (#0601).
- swift-guidance `ui.md`/`performance.md`: one scroll owner; don't nest an AppKit-backed `List` in a `ScrollView`; keep `body` work cheap.

## Evidence

- **Proven (measured):** the 951 figure. **Correction to the audit:** it is the worst single settle across the whole sweep (3 widths × 8 heights × 2 scroller styles, plus 3 sampler ticks at each), not a per-tick figure, and the fixture's `TickingMetricsSampler` has 40 processes, not the ~470 of a real system. A real process list is ~10× larger, so the production figure is likely higher.
- **Inferred:** that the nested `List` is the cause. The four status views differ mainly in this `List`, the `LazyVGrid`s and two drawing-only `GeometryReader`s. The planner should confirm by measuring with the `List` replaced before choosing the fix.

## Fix direction

Give scrolling one owner (layout ownership, no timing change):

- Replace the `List` with a `LazyVStack` of `processRow`s, keeping separators and `contextMenu`, inside the existing outer `ScrollView`. That drops the nested `NSScrollView`/`NSTableView` and the per-row hosting views. Or make the `List` the only scroller and put the dashboard sections in its header.
- Optionally have `SystemMetricsPaneContent` publish rows already sorted for the current sort key, so `body` stops sorting every tick.
- Keep #0601's lesson: no hand-built `NSScrollView` host (round 1 of #0601 crashed in the VM).
