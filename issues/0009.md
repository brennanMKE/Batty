## Description

End of M1. Wire up the minimum end-to-end app: launch Batty, see a working shell prompt rendered by libghostty inside a single Pane in a single Session in a single Window. No sidebar UI yet (M2), no tabs (M3), no splits (M4) — just a real Terminal Session you can type into.

**Acceptance criteria:**
- `ContentView` (or its successor) renders a single `TerminalSurfaceView` filling the window.
- Cmd-N opens a new window with its own surface.
- Typing reaches the shell; the shell's output renders correctly.
- Cmd-Q quits cleanly (surface destroyed via `dismantleNSView`).
- Window can be resized without blurring or clipping rendering (sanity-check that #0007 sizing is correct).
- This is the canonical "Hello, surface" milestone (PRD §9 M1).

## Revised approach — 2026-05-08

Now that `BattyKit` depends on `GhosttyTerminal`, M1's "hello, surface" is largely a few lines of SwiftUI:

```swift
import SwiftUI
import BattyKit  // re-exports GhosttyTerminal

struct ContentView: View {
    @State private var context = TerminalViewState()

    var body: some View {
        TerminalSurfaceView(context: context)
            .frame(minWidth: 600, minHeight: 400)
    }
}
```

The `TerminalViewState` is `@Observable` and exposes `title`, `surfaceSize`, `isFocused`, `renderedConfig`, etc. — all the runtime state we'd otherwise have to plumb manually.

**Revised acceptance criteria:**
- `Batty/ContentView.swift` imports `BattyKit` and renders `TerminalSurfaceView(context: TerminalViewState())` in place of the Xcode template stub.
- App launches, a working shell prompt appears, typing reaches the shell, output renders.
- Cmd-N opens a new window with its own `TerminalViewState` and surface.
- Cmd-Q quits cleanly.
- Window resizes don't blur or clip text (`GhosttyTerminal` handles `drawableSize` internally per the `TerminalSurfaceCoordinator`).

**Out of scope (still):** session/pane/tab hierarchy (M2+), drag-drop (`#0022`), bell capture (`#0024`).

**Note on PTY backend:** The default `TerminalViewState()` will start a real shell (PTY) on macOS via libghostty's exec backend. If sandbox or other constraints intervene, `InMemoryTerminalSession` from `GhosttyTerminal` is the host-managed fallback (we can ignore it for v1 since App Sandbox is off — confirmed by the recent sandbox commit).

## Root cause

Not a bug — feature gap. The template `ContentView` rendered a SwiftUI placeholder. M1 needs a real terminal surface visible end-to-end.

## Fix

Rewrote `Batty/ContentView.swift` to:

- `import BattyKit` (which re-exports `GhosttyTerminal`).
- Hold a `@State TerminalViewState` instance.
- Render `TerminalSurfaceView(context: terminal)` with `minWidth: 600, minHeight: 400`.
- Bind the window's `navigationTitle` to `terminal.title`, falling back to `"Batty"` when libghostty hasn't yet emitted a title.

Cmd-N (new window) works via the default SwiftUI `WindowGroup` behavior — each new window instantiates its own `ContentView` and therefore its own `TerminalViewState` and its own libghostty surface. Cmd-Q quits via the standard Mac app menu.

## Files changed

- `Batty/ContentView.swift` — replaced 13 lines of placeholder UI with the GhosttyTerminal-backed surface (+ window title binding).

## Gotchas

- **Visual verification is the user's.** `xcodebuild build` passes; "fonts look right", "typing reaches the shell", "output renders correctly", and "resize doesn't blur or clip" are eye-test items that need a human at the keyboard. Issue is `resolved`, not `closed` — flip to `closed` after spot-checking.
- **No terminfo bundled (#0003 still open).** `$TERM` will fall back to `xterm-256color`. Most things work; some advanced Ghostty terminfo features (kitty keyboard, extended SGR) won't until terminfo lands. Not a #0009 problem.
- **No shell-integration scripts bundled (#0003).** `terminalDidChangeWorkingDirectory` (used in #0016) won't fire until shell-integration is wired up; for now `TerminalViewState` will only update title via OSC 0/1/2. Acceptable for M1.
- **Single-window-per-`@State` semantics.** Each window has its own `terminal` `@State`; closing a window destroys its surface. This matches PRD §6.6 ("Multiple windows are independent — each has its own session list and detail state"). Future M2 work (sidebar/sessions) will hoist state above `ContentView`.
- **#0008 (IME smoke test) and #0007 (drag-drop NSView shim decision) are unblocked by this issue landing.** Both can be exercised against the running app.
- **`#Preview { ContentView() }` may fail** if SwiftUI previews can't initialize libghostty. Untested. If previews are needed for other views, fall back to `InMemoryTerminalSession` for the preview path or guard the preview with `#if DEBUG`. PRD §11 already flags "Metal in SwiftUI previews" as a known limitation.
