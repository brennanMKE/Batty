## Description

Write `docs/shortcuts.md` to document Batty's keyboard-shortcut system end-to-end. The shortcut routing is non-obvious because it bypasses SwiftUI Commands for the load-bearing path (per `#0062`), uses the Issues-app's recorder pattern (per `#0070`), and has reserved/fixed combos that aren't user-customizable.

Depends on `#0076` (which creates the `docs/` folder).

## What `docs/shortcuts.md` must cover

### 1. User-facing summary

- Where shortcuts are configured: **Settings → Shortcuts** (per `#0070`).
- How to record a new binding: click the recorder, press the combo, Esc to cancel.
- Reserved combos that can't be assigned: `Cmd-Q`, `Cmd-H`, `Cmd-M`, `Cmd-Tab`, `Cmd-,`.
- Fixed (non-customizable) combos: `Cmd-1..9` (tab selection), `Cmd-Option-1..9` (session selection), `Cmd-C` / `Cmd-V` (clipboard).
- Default bindings table — copy from `ShortcutAction.defaultBinding`.

### 2. The full catalog of customizable actions

Pull from `ShortcutAction.allCases`. For each: display name, default binding, what it does, related issues.

### 3. The routing architecture (the load-bearing section)

- **`BattyShortcuts.handle(_:)`** is installed as an `NSEvent.addLocalMonitorForEvents(.keyDown)` in `BattyAppDelegate.applicationDidFinishLaunching`. This monitor runs *before* the menu bar's key-equivalent dispatch and before AppKit's `performClose:` / `performKeyEquivalent:` fallback.
- Reading from `ShortcutsStore.shared`, it translates the NSEvent into a `ShortcutBinding(key:modifiers:)` candidate and matches against every `ShortcutAction.allCases`. On match, dispatches to `WorkspaceManager.shared.store` and returns true to consume the event.
- Why this exists: SwiftUI's `Commands` system can't beat NSWindow's `performClose:` on `Cmd-W` and can't beat libghostty's `AppTerminalView.performKeyEquivalent` on terminal-focused panes (per `#0062`'s investigation). The NSEvent monitor sits above both.
- Special case: when a `RecorderView` (Settings → Shortcuts) has first responder, the monitor returns `false` so the keystroke reaches the recorder. Otherwise the user would never be able to bind a shortcut without firing the existing action.
- libghostty's defaults are nuked via `keybind = clear` in `TabRuntime.applyShellAndAppearancePreferences`, with `cmd+c=copy_to_clipboard` re-added.

### 4. Persistence

- `ShortcutsStore` is `@MainActor @Observable`, singleton (`.shared`).
- JSON-encoded blob in `UserDefaults` under key `co.sstools.Batty.keyboardShortcuts`.
- Unknown action IDs decoded from older blobs are silently dropped (forward-compat).
- Missing actions in the loaded blob fall back to `defaultBinding`.
- Reset paths: `resetToDefault(_:)`, `resetAllToDefaults()`.

### 5. The recorder (Settings UI)

- `ShortcutsSettingsView` → `ShortcutRow` (one per action) → `KeyboardShortcutRecorder` (NSViewRepresentable) → `RecorderView` (NSView subclass).
- The recorder's `performKeyEquivalent` override is important — it captures menu-shortcut-style keystrokes that would otherwise be handled by the menu bar.
- The recorder rejects plain character keys without a non-shift modifier (so you can't bind `t` and shadow text input).
- Bare special keys (arrows, return, etc.) are accepted without modifiers since they're not text input.

### 6. Reserved combos

- Defined in `ShortcutsStore.reservedShortcuts`: `Cmd-Q`, `Cmd-H`, `Cmd-M`, `Cmd-Tab`, `Cmd-,`.
- The Settings UI warns when a reserved combo is chosen but still saves it (user can decide). This matches the Issues app's behavior, where v1 trades warning-but-allow for predictable UI.

## Root cause

Not a bug — a documentation gap. The shortcut routing introduced by
`#0062` (NSEvent local monitor as the load-bearing dispatch path) and
the customization system introduced by `#0070` (recorder UI,
`ShortcutsStore`, `UserDefaults` persistence, reserved combos) had no
single entry-point document. A user wondering "where do I change
Cmd-W?" or a contributor asking "why doesn't libghostty's keybind take
effect?" had to read source code in nine files plus three issue
threads.

## Gotchas

- The Settings → Shortcuts pane saves reserved combos rather than
  refusing them outright; documented this as a deliberate v1 trade-off
  (per `#0070`). In practice, the system-reserved combos (`Cmd-Q`,
  `Cmd-H`, `Cmd-M`, `Cmd-Tab`) never reach the NSEvent monitor anyway
  because the OS intercepts them first, and `Cmd-,` is consumed by
  SwiftUI's `Settings` scene. The warning row is the user feedback;
  Reset is the escape hatch.
- The shortcut router has two layered fall-throughs that aren't
  obvious from a single file: the NSEvent monitor checks the
  `ShortcutsStore` catalog first, then the fixed `Cmd-1..9` /
  `Cmd-Option-1..9` switch, then returns `false` to let AppKit
  dispatch normally. Documented as a numbered list inside Section 3.
- The `keybind = clear` directive in `TabRuntime` means user-set
  libghostty keybindings via `.ghostty` configs do not take effect.
  Called this out explicitly in the Quick-answer-key — it's the kind
  of thing a libghostty user will trip over and assume is a bug.
- The pre-existing uncommitted edit to `issues/0076.md` (the
  resolution markdown for `#0076` that hasn't been committed yet) was
  left untouched. Only `issues/0077.md`, `docs/shortcuts.md`, and
  `docs/README.md` are part of this issue's two commits.
