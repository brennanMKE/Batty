## Description

Survey three popular libghostty-adjacent terminal/agent tools — **herdr**, **supacode**, **cmux** — and decide, feature by feature, what (if anything) Batty should adopt. This is an **exploration/decision issue**, not a commitment to build. The governing constraints are unchanged: **Batty stays simple and stays a first-class Mac app.** Each feature that survives exploration becomes its own child ticket; this issue is the map and the decision record.

Context: the user previously used **cmux**, then built Batty because cmux had persistent bugs, a feature set far larger than wanted, and (in the user's view) poor UX — and because cmux/supacode/herdr all lean cross-platform and/or "agent command center," whereas the user wants a Mac-first, simple tool. So the bar for adopting anything here is high: it must earn its complexity and feel native.

Companion prior art: `docs/supacode-feature-review.md` already inventoried supacode and recommended a small on-brand subset (Cmd-F search, open-in-editor, jump-to-unread; declined agents/worktrees/GitHub/scripts/zmx/telemetry). This issue extends that lens to herdr and cmux and to the specific remote/agent/cloud ideas below. PRD §10 already lists an "SSH connection manager," Mosh, and an iOS companion ("Echolocation") as v2 ideas — this overlaps and may feed back into the PRD.

## The three apps (as surveyed 2026-07-03)

- **herdr** (herdr.dev, `github.com/ogulcancelik/herdr`) — a **TUI binary, "not an app"** ("one terminal for the whole herd"). Runs inside existing terminals. Real panes/tabs, **server-side persistent sessions that survive laptop close**, **remote SSH attach** (responsive TUI usable from phones/tablets), agent state at-a-glance (blocked/working/done), a **CLI + Unix-socket API** to create/split panes, run commands, and inspect output, plugin ecosystem. macOS/Linux stable, Windows beta. No Electron, **no account, no telemetry**. Open source.
- **supacode** (supacode.sh) — "the command center for coding agents": agents in **git worktrees**, **GitHub PR/CI** integration, a rich **CLI + `supacode://` deeplinks** (tab/surface/split control), **zmx** session persistence, **SSH remote surfaces (beta)**, per-repo scripts. macOS 26. Heavy; mostly off-mission for Batty (see the review doc).
- **cmux** (cmux.com, `github.com/manaflow-ai/cmux`, GPL) — the one the user left. Native macOS (Swift/AppKit/libghostty), "built for multitasking, organization, and programmability." Vertical tabs w/ git branch + ports + notification rings, split panes, **scriptable in-app browser** (DOM automation), session persistence, multi-agent orchestration, **SSH workspaces + remote tmux attach**, **iOS real-time sync**, **CLI + Unix-socket API** (pane management, screen reading, screenshots, browser automation), "Skills." Cross-platform "coming soon"; optional paid "Founders Edition" (iOS app, Cloud VMs).

**Pattern:** remote/SSH persistence and a CLI/socket control surface are table stakes across all three; agents-as-first-class and cloud/cross-platform are where they diverge from Batty's intent. Batty's edge is being *unapologetically Mac-first and small*.

## Candidate features to consider (user-requested)

### 1. Manage & access remote SSH sessions
All three support this in some form (herdr's server-side persistent sessions are the most ambitious; supacode/cmux run `ssh host` in a surface, cmux also attaches remote tmux). Batty today: local only; PRD §10 lists an "SSH connection manager" as a v2 idea.
- **Simple version (on-brand):** a "New Session from saved host" that just spawns `ssh user@host` in a normal surface (supacode/cmux's approach). Reuses everything Batty already has; the surface is just a shell that happens to be remote. Saved hosts + a small connect UI.
- **Ambitious version (off-brand risk):** server-side persistence so remote agents survive disconnect (herdr's model, or wrapping remote `tmux`/`zmx`). This is a real complexity jump (a daemon/persistence protocol) and edges toward the "detach/attach" the PRD explicitly deferred.
- **Decision to make:** simple saved-host SSH is likely worth adopting; server-side persistence probably not (yet).

### 2. Paste a screenshot while SSH'd and pass the image automatically
**Novel — none of the three advertise this.** Batty already inserts shell-quoted *local* paths on Finder drop (PRD §6.12), which is the user's primary way to share screenshots with Claude Code locally. Over SSH that breaks: a local path means nothing on the remote. The idea: when a surface is a remote SSH session, dropping/pasting an image **transfers the image to the remote** (e.g. `scp`/`sftp` into a temp dir, or pipe over the existing SSH channel) and inserts the **remote** path instead.
- **Why it fits Batty:** it's a direct, Mac-native extension of the drag-drop feature the user already relies on, and it solves a concrete workflow pain (sharing screenshots with a remote agent). Genuinely differentiated.
- **Hard parts:** knowing a surface is remote and to which host (parse the running `ssh` invocation, or only enable it for saved-host sessions from #1 where the connection is known); choosing a transfer channel (separate `scp` connection vs. multiplexed control socket); temp-file lifecycle/cleanup on the remote. Best done *after* #1 (saved-host SSH), which gives the connection metadata for free.

### 3. Manage agents + CLI to open/close panes

> **CLI action catalog + foundation:** see `docs/batty-cli-design.md` — surveys the herdr/supacode/cmux CLI & socket APIs and proposes the `batty <noun> <verb>` grammar, context env vars, the one-way-URL-vs-two-way-socket decision, and a tiered action catalog (structure, focus, activity pills for agents, introspection, advanced automation).

herdr and cmux both expose a **CLI + Unix-socket API** to create/split/close panes and run commands; supacode's `batty`-analog (`supacode`) does the same via deeplinks. Batty just started down this road: the **`batty` CLI** (#0249) with `batty <path>` (#0250/#0251) and the proposed context env vars + rename verbs (discussed but not yet ticketed). Extending it to open/close/split panes and target the calling pane (via `$BATTY_*` env, see the CLI-context discussion) is the natural continuation.
- **Simple, on-brand:** a *curated* set of `batty` verbs — `batty split [-h|-v]`, `batty new-tab`, `batty close`, `batty rename-session/tab` — reusing the `batty://` URL scheme and the context env vars a surface would export. No socket, no agent-orchestration framework.
- **Off-brand risk:** "manage agents" as first-class objects (presence badges, liveness sweeps, agent state UI) is supacode/herdr territory and requires patching Ghostty (supacode's OSC 3008) — declined in the review doc. Keep to *CLI control of panes/tabs*, not an agent dashboard.

## Bigger idea: optional open-source cloud backend + accounts

The user floated a self-hostable, open-source cloud backend (run on a local Linux or Mac server), an account system, **Passkeys** for auth (or **Keychain** if the whole thing stays Mac-only), enabling remote access/sync.

This is the item in **most tension with "keep Batty simple."** A cloud backend + accounts + auth is a second product with its own maintenance, security surface, and ongoing cost — the opposite of the "no account, no telemetry, local-first" stance herdr advertises and Batty's PRD implies (§7 Privacy: "No telemetry"). Framing for the decision:
- **What problem does it actually solve** that plain SSH (#1) doesn't? If the goal is "reach my Mac mini's terminals from elsewhere," SSH (possibly + a persistence layer) may be enough without accounts/cloud.
- **If pursued, keep it optional and local-first:** self-hosted only, no mandatory account, Keychain-backed for the all-Mac case, Passkeys only if a browser/cross-device client is in scope. Anything that makes the base app require a backend violates "first-class Mac app that just opens to a shell."
- **Recommendation (tentative):** treat this as a *separate, later* exploration gated on whether #1/#2/#3 leave a real unmet need. Don't let it expand Batty's core.

## The concrete Mac pain point worth solving

The user's actual friction: reaching the Mac mini today via Screen Sharing (heavy) or SSH, and hitting **macOS permission prompts that require a password** — TCC / privileged-operation dialogs that block **agents** (an agent can't type a GUI password). This is arguably the **most on-brand opportunity** because it's a *Mac-specific* problem a Mac-first app is uniquely placed to help with, and it's what makes remote agent work painful today.
- Explore what Batty could legitimately do here **without becoming a security foot-gun**: surface/route these prompts, pre-grant the permissions Batty's own terminals need, document the TCC entitlements a headless-agent workflow requires, or integrate with `Remote Login`/`Remote Management` setup. Be careful: auto-dismissing or scripting past macOS auth prompts is exactly the kind of thing to *not* do casually (security + notarization implications). The value is in reducing legitimate friction, not defeating the security model.
- This deserves its own focused exploration once the scope is understood; it may be the single most valuable thread here.

## Notes

Keep the bar high. The reason Batty exists is that cmux/supacode/herdr were *too much*. Adopt the small, native, differentiated pieces (saved-host SSH, screenshot-over-SSH, curated CLI pane control, and — most interestingly — easing macOS permission friction for remote/agent use); be skeptical of the account/cloud/agent-dashboard directions that would turn Batty into the thing it was built to avoid.
