## Description

Batty pins libghostty-spm to revision `c69c34354e511af7a3e6d7e5e2a4fa2fed4b90ff` (= tag **1.2.2**) in `BattyKit/Package.swift:31-34`. Latest upstream is **1.3.2** (`b146b73`, published 2026-07-27), vendoring ghostty commit `35e1a0160c4f6797e1bb1ef8e7a2b8c6b114ab58`. The stale pin blocks the headline fix of the #0285 umbrella: 1.3.2 adds `TerminalSurfaceOptions.envVars` (per-surface env vars, wired to `ghostty_surface_config_s.env_vars` in `TerminalController+Surface.swift:34-35` @ 1.3.2), which is exactly what #0287 needs to collapse Batty's one-`ghostty_app_t`-per-Tab design into a shared controller.

The bump also picks up ~2 months of vendored ghostty (8 autopublish rounds). That window is not empty: ghostty upstream acknowledged leaks in the 1.2.3 era — a PageList leak and a styles leak triggered by TUIs emitting many styles, with Claude Code CLI named as a trigger (ghostty-org/ghostty#10289) — with fixes landing for 1.3. Batty is pinned *behind* those. Whether they touch the graphics half of the footprint is unverified; the source investigation found no renderer or Metal changes in the wrapper's Swift layer across 1.2.2 → 1.3.2, so the memory-relevant delta is entirely in the vendored xcframework.

Wrapper API additions across the range (`git log 1.2.2..1.3.2`): per-surface `envVars` (#32), prompt navigation (#30), host-managed output queueing (#29), foreground PID / tty (#27), scrollbar action (#37), arm64e slices, and **namespaced xcframework headers** (`Headers/libghostty/`) — the last is a possible import-path break worth checking during the bump.

Files to update:

- `BattyKit/Package.swift:31-34` — the pinned revision.
- `BattyKit/Package.resolved` — resolved pin.
- `Batty.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved` — the app workspace's resolved pin.

Acceptance: builds clean (`scripts/build.sh`), `scripts/build.sh unit` passes, the app runs, no behavior regressions.

## Resolution notes

> 🟢 Resolved 2026-08-01 — libghostty-spm bumped 1.2.2 → 1.3.2; review caught that the bump silently enabled copy-on-select, which was fixed before landing.

The bump itself was mechanical. The value of this issue turned out to be the regression it nearly shipped: upstream's "selection copy leak" fix also flipped a runtime clipboard semantic, and only a runtime test caught it.

## Root cause

Batty pinned libghostty-spm at tag 1.2.2 (`c69c34354e511af7a3e6d7e5e2a4fa2fed4b90ff`), twelve releases behind 1.3.2 (`b146b73a8ba3ed2678a22a9de5feecfcbf298d48`). The stale pin lacked `TerminalSurfaceOptions.envVars`, which #0287 requires, and trailed ~2 months of vendored ghostty development including 1.3-era leak fixes.

A second, unanticipated root cause surfaced during review. Upstream commit `6505146` — filed as "Fix AppKit selection copy leak" and characterized in this issue's original Notes as a kilobytes-only C-string leak — also flips `runtimeConfig.supports_selection_clipboard` from `false` to `true`. Combined with ghostty's `copy-on-select = true` default (which Batty never overrode) and upstream's `writeClipboard` discarding the clipboard kind and writing `NSPasteboard.general` unconditionally, mouse-selecting text in a pane silently overwrote the user's system clipboard. Under 1.2.2 the `false` flag made this inert.

## Fix

- Bumped the pin to `b146b73a8ba3ed2678a22a9de5feecfcbf298d48` (tag 1.3.2) in `BattyKit/Package.swift` and both `Package.resolved` files, keeping the exact-`revision:` pinning style.
- Added `copy-on-select = false` to `TabRuntime`'s configuration builder, restoring the pre-bump behavior. Placed outside the `if let command` branch so it applies to every Tab, not only `-c` panes.
- Refreshed two `wait-after-command` verification comments and one docs citation that named the old pinned revision.

No new 1.3.2 wrapper APIs were adopted — `envVars` adoption is deliberately left to #0287 so this bump could land as an isolated, revertible change.

## Review

Reviewed by claude-opus-5 over two rounds.

Round 1 requested changes: the bump was mechanically correct, but the one behavior area it changed — selection/copy — had never been exercised. The Beta smoke test proved a shell spawned and rendered, which says nothing about the clipboard path. Round 1 also flagged a stale revision citation in `docs/batty-cli-install.md` and comment style that appended a verification round per bump.

Round 2 approved. The reviewer independently confirmed at source level that `supports_selection_clipboard = true` and that `writeClipboard` discards the clipboard kind; proved the new directive round-trips clean rather than assuming it (the vendored binary carries `invalid value` diagnostics, and `prepareConfig` fails closed on any diagnostic — a malformed value would have silently discarded every other directive Batty emits); confirmed `copy-on-select` appears exactly once in the repo with no conflict; re-ran the unit suite; and confirmed the change does not box in #0287, since the directive is a static global sitting beside `font-size` and `cursor-style`, all of which #0287 relocates wholesale.

## Gotchas

- **A "leak fix" in a dependency changelog can carry a behavior flip.** Upstream #23 read as a kilobytes-scale C-string leak; it also changed a runtime clipboard semantic. Reading the diff rather than the title is what caught it. The original Notes line in this issue propagated the wrong framing and has been corrected.
- **`prepareConfig` fails closed on the entire config.** Any single malformed directive causes every other setting — cursor style, font size, keybinds, `BATTY_*` env vars — to be silently discarded and the default config used instead. Adding a config directive therefore needs diagnostic verification, not just "it built".
- **`xcodebuild -resolvePackageDependencies` does not write back to the shared workspace `Package.resolved`.** It resolves into DerivedData only, so that file was hand-edited — matching the precedent set by commit `244104a`. Its `originHash` has never tracked the libghostty pin and was correctly left alone; a full build+test afterwards left the tree clean, confirming xcodebuild accepted it.
- **Building the Beta scheme rewrites `project.pbxproj` and both `.xcscheme` files** with a cached product name, because both schemes share one target BlueprintIdentifier. This churn is incidental and was discarded before each commit; expect it when building Beta locally.
- **No regression test pins `copy-on-select`.** `command`, `wait-after-command`, and `env` each have a `renderedConfig.contains(...)` assertion; this directive does not, so a future edit could silently drop it and reintroduce clipboard clobbering. (`keybind` directives are unasserted too, so this matches existing convention rather than breaking it.) Worth adding a cheap guard.
- **One comment clause is inferred, not measured.** "matching the 1.2.2 behavior Batty was built against" rests on the flag flip rather than a measurement of 1.2.2 — ghostty's embedded docs are ambiguous enough to permit a reading where 1.2.2 also clobbered. The fix is correct either way.
- **Middle-click paste is unaffected and remains enabled.** ghostty documents middle-click primary-paste as active even when `copy-on-select = false`, and the wrapper's `readClipboard` also ignores clipboard kind. This is not a regression from this bump — it behaved the same at 1.2.2 — so it was deliberately left alone. Changing it would need `middle-click-action = ignore` and its own issue.

## Notes

- The namespaced-headers change (`Headers/libghostty/` in the xcframework) may require import-path adjustments — flag and fix as part of the bump.

- 1.3.2 does **not** add per-surface `command` or `wait_after_command` — that gap is tracked separately as #0292 and does not block this bump.
- `Fix AppKit selection copy leak (#23)` is not just a small kilobytes-only C-string leak fix in `readSelection` — it also flips `TerminalController+Config.swift`'s `runtimeConfig.supports_selection_clipboard` from `false` to `true`. Combined with ghostty's own `copy-on-select = true` default (which Batty never overrides) and `writeClipboard` ignoring clipboard kind and writing straight to `NSPasteboard.general`, this bump makes mouse-selecting text in a pane write to the system clipboard with no Cmd-C — a real behavior change, not just a leak fix. See review round 2 for the verified regression and fix (`copy-on-select = false` added to `TabRuntime`'s configuration builder).
