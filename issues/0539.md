# 0539 — A semitransparent Pane composites over the window's background color, so the desktop never shows through, because the window and the background behind the terminal host are opaque

| | |
|---|---|
| **Status** | open |
| **Module** | Window / Theme / TerminalSurface |
| **Platform** | macOS |
| **First seen** | 2026-11-03 |

## Description

Lowering `background-opacity` makes the terminal surface transparent, but what shows through is Batty's own window color, never the desktop or another app. That misses the goal [#0372](0372.md) exists for:

> "Ultimately with both issues implemented the user should [be] able to tint an image and still see through to other apps or the desktop on a Mac."

No child of #0372 owns this. [#0373](0373.md) plumbed the config keys, and [#0374](0374.md)'s plan defers this work to a follow-up, which is this issue. **#0372 isn't finished, and the feature flag can't come off, until this lands.**

## Steps to reproduce

Today this needs a `background-opacity` below 1, which has no UI until [#0374](0374.md) lands.

1. In Batty Beta, give a Pane a terminal opacity of about 0.5.
2. Put a brightly colored window or desktop picture behind the Batty window.

## Expected behavior

The desktop or the window behind Batty is visible through the Pane's default-background cells.

## Actual behavior

From the code, not yet observed in a running app: the Pane blends with the Theme's window color, or with the system window background when no Theme is active. Nothing behind the Batty window is visible.

## What sits behind a terminal, confirmed in code

Line numbers are against `d2ecebbc`.

| Layer | Where | State |
|---|---|---|
| The surface | `AppTerminalView.swift:75-79` in the `libghostty-spm` checkout | Clear: `metal.isOpaque = false`, with a clear background on the `CAMetalLayer` and the view's layer |
| Terminal host | `TerminalHostView.swift:51` | Clear layer |
| Pane placeholder | `TerminalPlaceholderView.swift:46` | `Color.clear` |
| Themed band | `SessionDetailView.swift:305-308` | `themeChrome?.windowBackground ?? Color.clear`, behind the whole `sessionStack` and into the title bar |
| Window color | `WindowChromeApplier` in `RootWindowView.swift:319-327` | `window.backgroundColor` is an opaque Theme color, or `nil` with no Theme |
| Window opacity | Nothing in `Batty/` or `BattyKit/Sources` sets `isOpaque` on a window | AppKit's default, which is opaque for a window like this |

So at least three things have to change: `window.isOpaque`, `window.backgroundColor`, and the themed band. `WindowChromeApplier` is the only writer of `window.backgroundColor` and it re-applies on every SwiftUI update, so it has to learn about this state or it will restore the opaque color.

## The rest of the chrome

These surfaces sit beside the terminal rectangle, not behind it, so they don't stop a Pane showing the desktop. They do stay opaque around it, which is a design decision for this issue rather than a compositing blocker:

- Terminal tab bar: `chromeBackground ?? Color.clear` (`PaneView.swift:249`). Opaque only with a Theme.
- Non-terminal Pane shell: `chromeBackground ?? .windowBackgroundColor` (`PaneView.swift:434`). Opaque with or without a Theme.
- Sidebar list and footer: `chromeBackground` when themed (`SessionSidebarView.swift:143-144`, `:173`). Without a Theme it uses `.automatic` list content and `.bar`, whose look over a non-opaque window hasn't been seen.
- Split dividers: `dividerColor` (`SplitContainerView.swift:206`).

## Questions for the plan

- **Who owns the window-level state?** It's a fact about the window, while opacity is set per Pane today ([#0374](0374.md)), then per Session and app-wide ([#0376](0376.md), [#0375](0375.md)). It needs one owner and a declared writer under `docs/swiftui-observation-rules.md`, and it must react to Panes closing and to the app-wide default changing.
- **What derives it?** Every Pane in the window, or only those in the selected Session? Unselected Sessions keep their surfaces, hidden.
- **Which Panes are affected?** A Pane at opacity 1 should still paint itself opaque, but any region no surface covers changes once the band goes clear. That includes a window with no Session selected, where `ContentUnavailableView` sits over the band.
- **`themeChrome` is app-wide**, with a per-window view of it only through the environment. `WindowChromeApplier` reads the same palette in every window, so a per-window transparent state can't live in the palette.
- **Should see-through be always on, or follow a setting?** Going non-opaque whenever any surface is below 1 ties a window-wide change to one Pane's slider. The plan should say what the user sees at each end of that slider.
- **`background-blur`** is in the pinned binary per [#0372](0372.md), and is a window-level look too. Batty doesn't emit it today. Decide whether it belongs here or stays out.

## Unverified

None of this has been measured. Check each one in the real app before relying on it.

- **Click-through.** From memory, fully transparent pixels of a non-opaque macOS window can pass clicks to the app underneath. If so, `background-opacity = 0` would break the first requirement in `docs/terminal-pane-requirements.md`, and text selection and scrolling with it. `TerminalHostView.hitTest` doesn't help: it only routes within the window, and a window-server pass-through would never reach it.
- **A minimal-alpha background.** From memory, upstream Ghostty's own macOS app uses a near-zero-alpha white window background rather than `.clear`. Worth measuring against click-through and appearance. That app's source isn't in this repo's checkout, so this wasn't checked.
- **Hidden backing layers.** `RootWindowView` uses `NavigationSplitView` inside a SwiftUI `WindowGroup`. Whether either paints an opaque layer behind the detail column once the band and window are clear is unknown. There may be a layer the grep can't find.
- **Window shadow and title bar.** How the shadow, the title bar and the toolbar look over a non-opaque window, with and without a Theme.

## Verification

The see-through result can't be proven by unit test: it's a property of how the window server composites the window. Any derivation of the window-level state can be unit tested on its own, and the plan should name those tests. Beyond that it needs a run in the real app, plus UI tests where they can pin behavior such as clicks still reaching a surface.

Run the `docs/terminal-pane-requirements.md` §6 checklist with a Pane at 0, at about 0.5, and at 1. Mark `resolved`, not `closed`, and say in `## Gotchas` what wasn't seen.
