## Description

Lowering `background-opacity` makes the terminal surface transparent, but what shows through is Batty's own window color, never the desktop or another app. That misses the goal [#0372](0372.md) exists for:

> "Ultimately with both issues implemented the user should [be] able to tint an image and still see through to other apps or the desktop on a Mac."

No child of #0372 owns this. [#0373](0373.md) plumbed the config keys, and [#0374](0374.md)'s plan defers this work to a follow-up, which is this issue. **#0372 isn't finished, and the feature flag can't come off, until this lands.**

The user's requirement: "In Apple's Terminal app users can make it the terminal semitransparent so you can see other apps or the desktop through the terminal pane." And: "In Settings under appearance there should be a slider for opacity and a text field where I can change the number as well. That will control opacity for all panes. Then you could allow a local override." The user tried the slider in Beta and saw no see-through.

## Resolution notes

## Root cause

Feature work, starting state: `background-opacity` made the surface transparent, but the window stayed opaque with an opaque or default `backgroundColor`, and the detail column's band painted the Theme color behind the host. So a Pane composited over Batty's own color, never the desktop. This is from the code and the plan's measurements. The real result wasn't seen.

## Fix

`AppStateStore.isWindowSeeThrough(_:)` computes the window state from the flag, native full screen and every terminal Pane in every Session, using `PaneRuntime.effectiveTerminalOpacity(appWide:)`. Its new inputs have one writer each: `setAppWideTerminalOpacity`, called from `applyAppWideBackgroundToAllSurfaces`, and `WindowRuntime.setNativeFullScreen`, called from three `WindowDelegate` callbacks. Those callbacks look the runtime up without creating one, so a callback arriving after a window closes can't add an empty window to `store.windows`.

`RootWindowView.body` reads it once and passes it to `WindowChromeApplier` and `\.windowIsSeeThrough`. `WindowSeeThrough.apply` is the only writer of `isOpaque` and `backgroundColor`, and stays in the applier's existing `DispatchQueue.main.async`. With opacity 100 or the flag off, it makes today's writes, and the `isOpaque` branch fires only after a flip.

While see-through, the band is clear unless no Session is selected. The themed title bar gets the zero-height top band. Tab bars, dividers and the Sidebar stay solid. With no Theme, the painted Sidebar rows remove the system selection, so `WindowSeeThrough.sidebarSelectionTint` draws the selected row with a 12% primary overlay, the same strength as a Theme's tint. It returns `nil` with no Theme when not see-through, so that path is unchanged. The misleading sheet caption is gone, and both the sheet and Settings now say what happens below 100%.

Deviations from the plan:

- **`appWideTerminalOpacity` has an idempotent setter.** `private(set)` can't be written from the extension in `SettingsPreferences.swift`, so that code calls an internal `setAppWideTerminalOpacity`. The guard moved there.
- **`RootWindowView` resolves `windowRuntime` in `init`,** as `SessionDetailView` and `SessionSidebarView` do, and doesn't call `windowRuntime(for:)` from `body`.
- **`ignoresMouseEvents = false` isn't undone on the way back to opaque.** The plan doesn't ask for it. The value only has to be set explicitly while non-opaque, and it matches the getter's default.
- **`opaqueApplyWithNoTheme...` compares against an untouched `NSWindow`** as planned, and `seeThroughThenOpaqueRestoresTheWindow` does the same for the no-Theme case.

Also done: the `docs/view-hierarchy.md` §1-2 correction and a see-through note, the `docs/feature-flags.md` gate site, `Concepts.md` 0.18, and the handoff note in #0376. Open question defaults are followed: Terminal Opacity keeps accepting 0, the Sidebar is solid while see-through, blur is out of scope ([#0541](0541.md)), and this stays on `main` behind the flag.

### Decisions

**Window state: computed, with no stored flag and no writer of its own.** `AppStateStore.isWindowSeeThrough(_ window: WindowRuntime) -> Bool`:

```swift
guard featureFlags.terminalBackgrounds, !window.isNativeFullScreen else { return false }
return window.sessions.contains { session in
    session.tree.allPanes.contains {
        $0.kind == .terminal && $0.effectiveTerminalOpacity(appWide: appWideTerminalOpacity) < 1
    }
}
```

A stored flag would need a trigger on every Pane close, split, Session close and override write, and would go stale. A computed read tracks those by itself, and Panes closing and windows opening later are correct without extra code. It is per window because it reads a `WindowRuntime`, so nothing goes in `themeChrome`.

| Input | Owner | Writer, and its origin |
|---|---|---|
| `pane.backgroundOverride` | `PaneRuntime` | Existing `setBackgroundOverride`, audited in #0374 and #0375 |
| `appWideTerminalOpacity` (new) | `AppStateStore`, `public private(set)` | `applyAppWideBackgroundToAllSurfaces`, idempotent. Every `AppWideBackgroundEditor` path already ends there. Seeded in `init` from `backgroundGate.storedSettings()`, which returns `.off` with the flag off before touching `UserDefaults`, and doesn't hash the image |
| `isNativeFullScreen` (new) | `WindowRuntime`, `private(set)` | `setNativeFullScreen(_:)`, idempotent, called from `WindowDelegate` callbacks: `windowWillEnterFullScreen`, `windowDidExitFullScreen`, `windowDidFailToEnterFullScreen`. Outside the view update, same shape as the occlusion callback |

`AppWideBackgroundGate` stays non-observable. The new property is what views read.

**Which Panes count: every terminal Pane in every Session of the window, hidden ones too.** Selecting only the current Session would flip the window on every Session switch, the most frequent action in the app, to save a cost nobody would see. A Pane at 100 in a see-through window paints itself solid, and all chrome paints itself, so an all-opaque Session looks the same either way.

**Always on when below 100, with no separate switch.** That is the requirement: the slider is the control. At each end of a Pane's slider: at 100 with every other Pane at 100, the window is opaque as it is today. Below 100 that Pane shows the desktop and the other Panes keep their own value.

**At 100 or flag off, the same writes as today.** The opaque branch of `apply` is today's code, plus `if !window.isOpaque { window.isOpaque = true; window.invalidateShadow() }`, which never fires unless a flip happened. The band expression returns today's value. Prod never reaches a non-opaque write, because the flag guard comes first.

**See-through branch of `apply`:** set `backgroundColor` to `WindowSeeThrough.windowColor` (black at 0.004), `ignoresMouseEvents = false`, then `if window.isOpaque { window.isOpaque = false; window.invalidateShadow() }`. `titlebarAppearsTransparent` stays driven by the palette in both branches. It stays in `updateNSView`'s existing `DispatchQueue.main.async`, because the flip changes `NSThemeFrame`'s subviews and must not run inside the layout pass. That hop carries an AppKit side effect, not a model write, so it isn't the pattern `AGENTS.md` forbids.

**Full screen: opaque, as upstream does.** The surface composites over the Theme color, which is the look before this issue. No restored or initial sync is needed: restoration is disabled, and a window entering full screen gets the delegate callback.

**Click-through at 0: two guards, no floor on the field for now.** From memory, a non-opaque window passes clicks through pixels of alpha 0 unless `ignoresMouseEvents` has been set to false explicitly, and the getter reading false (measured) doesn't tell the two states apart. So the see-through branch sets it explicitly, and the window color keeps alpha at 1/255 under every surface. Neither is proven. A non-opaque window's region never reaches `TerminalHostView.hitTest` if the window server passes the click on. See Open question 1 for the fallback.

**Chrome: solid, as in Terminal.app, with only the terminal rectangle clear.** One helper, `WindowSeeThrough.chromeBacking(isSeeThrough:windowBackground:)`, returns `.clear` when off, otherwise the Theme's window color or `Color(nsColor: .windowBackgroundColor)`.

| Surface | With no Theme | With a Theme |
|---|---|---|
| Title bar | System bar stays solid (measured) | Zero-height top band in `windowBackground` (measured) |
| Sidebar list and footer | Takes the themed code path with `.windowBackgroundColor`, because glass over the desktop isn't predictable | Unchanged |
| Terminal tab bar | `chromeBacking` under the existing `.background` | `chromeBacking` under `chromeBackground` |
| Split dividers | `chromeBacking` under `dividerColor`, so they look as they do today | Same |
| No Session selected | Full band in `.windowBackgroundColor` behind `ContentUnavailableView` | Full band in `windowBackground`, today's |
| Non-terminal Panes | Unchanged: already opaque (`PaneView.swift:434`) | Unchanged |

All of these are `.background`s below or beside the surface. The host keeps its `ZStack` position, nothing goes above the pane body, and nothing registers a drag type, so `docs/terminal-pane-requirements.md` §4-5 aren't touched.

**The caption.** Remove `PaneBackgroundSettingsView.swift:115`. In both the sheet and `TerminalBackgroundSettingsSection`, add: "Below 100%, the desktop and other windows show through, except in full screen."

**Image and terminal opacity together.** Computed from `shaders.metal:435-441`, for an opaque image pixel with image opacity `I` at or below 1 and terminal opacity `T`: desktop share is `1-T`, image `T*I`, Theme color `T*(1-I)`.

| `T` | `I` | What the user sees |
|---|---|---|
| 1 | any | No desktop, as today |
| 0.5 | 1 | Half desktop, half image, no Theme color |
| 0.5 | 0.15 (first-image default) | Half desktop, 42% Theme color, under 8% image: the image is barely there |
| 0.3 | 1 | The "tint" the umbrella asks for: 70% desktop, 30% image |
| 0 | any | No image at all: text over the desktop |

So the tint comes from raising image opacity to 100 and lowering terminal opacity. Text stays solid at every `T`, and cells a program painted stay solid unless the `background-opacity-cells` toggle is on. No default changes here. Terminal opacity defaults to 100, so the defaults stay readable. A light-on-dark Theme at 0 over a bright desktop isn't readable, which is the same trade Terminal.app offers, and `minimum-contrast` can't help (#0375).

**Blur: out, filed as [#0541](0541.md).** It isn't a small addition: the binary's call is stubbed. It takes either the private `CGSSetWindowBackgroundBlurRadius` called from Batty, or a behind-window `NSVisualEffectView` below the host, which touches the layer `docs/view-hierarchy.md` guards. Orchestrator: have it filed, linked from #0372 and this issue, as behind the same flag but not blocking its removal unless the user says so.

**Live, multi-window, no teardown.** Opacity changes go through `setTerminalConfiguration` as they do now. This issue adds only window and background writes, and no `AppTerminalView` is touched. Each `RootWindowView` reads its own runtime. A later window computes the value on its first `body`.

**Observation audit.** `RootWindowView.body` computes the value once, passes it to `WindowChromeApplier`, and sets `\.windowIsSeeThrough` in the environment beside `\.themeChrome`, so children read one `Bool`, not every Pane. Its new dependencies change only on a split, close, override or opacity change. The cycle: model write → `body` → `updateNSView` → async `isOpaque` and `backgroundColor`. Nothing there flips an observed value, so it dead-ends. The field's commit can run inside a responder change (#0375's audit); `appWideTerminalOpacity` is one more observable write on that path, which calls no responder or constraint API.

## Steps to reproduce

1. In Batty Beta, set Terminal Opacity to about 50 in Settings → Appearance, or on a Pane through its gear.
2. Put a brightly colored window or desktop picture behind the Batty window.

## Expected behavior

The desktop or the window behind Batty is visible through the Pane's default-background cells.

## Actual behavior

The user tried the slider in Beta and saw no see-through. From the code: the Pane blends with the Theme's window color, or with the system window background when no Theme is active. Nothing behind the Batty window is visible.

## What sits behind a terminal, confirmed in code

Line numbers are against `d2ecebbc`.

| Layer | Where | State |
|---|---|---|
| The surface | `AppTerminalView.swift:75-79` in the `libghostty-spm` checkout | Clear: `metal.isOpaque = false`, with a clear background on the `CAMetalLayer` and the view's layer |
| Terminal host | `TerminalHostView.swift:51` | Clear layer |
| Pane placeholder | `TerminalPlaceholderView.swift:46` | `Color.clear` |
| Themed band | `SessionDetailView.swift:305-308` | `themeChrome?.windowBackground ?? Color.clear`, behind the whole `sessionStack` and into the title bar |
| Window color | `WindowChromeApplier` in `RootWindowView.swift:319-327` | `window.backgroundColor` is an opaque Theme color, or `nil` with no Theme |
| Window opacity | Nothing in `Batty/` or `BattyKit/Sources` sets `isOpaque` on a window | AppKit's default, which is opaque for a window like this |

So at least three things have to change: `window.isOpaque`, `window.backgroundColor`, and the themed band. `WindowChromeApplier` is the only writer of `window.backgroundColor` and it re-applies on every SwiftUI update, so it has to learn about this state or it will restore the opaque color.

## The rest of the chrome

These surfaces sit beside the terminal rectangle, not behind it, so they don't stop a Pane showing the desktop. They do stay opaque around it, which is a design decision for this issue rather than a compositing blocker:

- Terminal tab bar: `chromeBackground ?? Color.clear` (`PaneView.swift:249`). Opaque only with a Theme.
- Non-terminal Pane shell: `chromeBackground ?? .windowBackgroundColor` (`PaneView.swift:434`). Opaque with or without a Theme.
- Sidebar list and footer: `chromeBackground` when themed (`SessionSidebarView.swift:143-144`, `:173`). Without a Theme it uses `.automatic` list content and `.bar`, whose look over a non-opaque window hasn't been seen.
- Split dividers: `dividerColor` (`SplitContainerView.swift:206`).

## Questions for the plan

- **Who owns the window-level state?** It's a fact about the window, while opacity is set per Pane today ([#0374](0374.md)), then per Session and app-wide ([#0376](0376.md), [#0375](0375.md)). It needs one owner and a declared writer under `docs/swiftui-observation-rules.md`, and it must react to Panes closing and to the app-wide default changing.
- **What derives it?** Every Pane in the window, or only those in the selected Session? Unselected Sessions keep their surfaces, hidden.
- **Which Panes are affected?** A Pane at opacity 1 should still paint itself opaque, but any region no surface covers changes once the band goes clear. That includes a window with no Session selected, where `ContentUnavailableView` sits over the band.
- **`themeChrome` is app-wide**, with a per-window view of it only through the environment. `WindowChromeApplier` reads the same palette in every window, so a per-window transparent state can't live in the palette.
- **Should see-through be always on, or follow a setting?** Going non-opaque whenever any surface is below 1 ties a window-wide change to one Pane's slider. The plan should say what the user sees at each end of that slider.
- **`background-blur`** is in the pinned binary per [#0372](0372.md), and is a window-level look too. Batty doesn't emit it today. Decide whether it belongs here or stays out.

## Unverified

None of this has been measured. Check each one in the real app before relying on it.

- **Click-through.** From memory, fully transparent pixels of a non-opaque macOS window can pass clicks to the app underneath. If so, `background-opacity = 0` would break the first requirement in `docs/terminal-pane-requirements.md`, and text selection and scrolling with it. `TerminalHostView.hitTest` doesn't help: it only routes within the window, and a window-server pass-through would never reach it.
- **A minimal-alpha background.** From memory, upstream Ghostty's own macOS app uses a near-zero-alpha white window background rather than `.clear`. Worth measuring against click-through and appearance. That app's source isn't in this repo's checkout, so this wasn't checked.
- **Hidden backing layers.** `RootWindowView` uses `NavigationSplitView` inside a SwiftUI `WindowGroup`. Whether either paints an opaque layer behind the detail column once the band and window are clear is unknown. There may be a layer the grep can't find.
- **Window shadow and title bar.** How the shadow, the title bar and the toolbar look over a non-opaque window, with and without a Theme.

## Verification

The see-through result can't be proven by unit test: it's a property of how the window server composites the window. Any derivation of the window-level state can be unit tested on its own, and the plan should name those tests. Beyond that it needs a run in the real app, plus UI tests where they can pin behavior such as clicks still reaching a surface.

Run the `docs/terminal-pane-requirements.md` §6 checklist with a Pane at 0, at about 0.5, and at 1. Mark `resolved`, not `closed`, and say in `## Gotchas` what wasn't seen.
