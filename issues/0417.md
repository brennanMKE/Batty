## Description

In #0412's first full Tart-VM run (run id `20260923-191103-94702`), every test in `BattyUITests/PaneSidebarTests.swift` failed with a real `XCTAssertTrue` failure. None of the failures were a crash or a setup error:

| Test | Failing line | Message |
|---|---|---|
| `testChevronExpandsAndCollapsesPaneList` | `:81` | `Expanding must reveal one row per pane` |
| `testChevronPresentForSinglePaneSession` | `:106` | `Expanding a single-pane session must show its one pane row` |
| `testClickingPaneRowDoesNotBlankSession` | `:127` | (no message) |
| `testHidingPaneAutoExpandsPaneList` | `:159` | `Hiding a pane must auto-expand the sidebar pane list` |
| `testEyeDisabledForLastVisiblePane` | `:179` | (no message) |

**All five fail at the same kind of assertion:** `waitFor({ paneRowCount(in: app) == N }, timeout: 5)`. It counts elements whose identifier begins with `pane-row.`. Those identifiers come from `SessionSidebarView.swift:54` (`.accessibilityIdentifier("pane-row.\(pane.id.uuidString)")` on each `PaneRow` inside the Session's `DisclosureGroup`). Every assertion before that point passed:

- the window appeared;
- in the two tests that check it, the pane-row count was `0` before expansion;
- the disclosure chevron (`app.disclosureTriangles.firstMatch`) or the title-row hide eye (`pane-eye-button.*`) existed and was clicked.

So in the guest, one of two things happens. Either the list never expands, or it expands and the rows never become visible to XCUITest under the `pane-row.` identifier. In `testHidingPaneAutoExpandsPaneList` the list is expanded by the model (`WindowRuntime.hidePane` sets it, not a chevron click), and it fails the same way. That points at the second explanation, rows not surfacing, rather than at the click.

The same run's other Sidebar tests passed: `SidebarTests` 3/3, `MultiWindowTests` 3/3. So the Sidebar itself is present and usable to automation in the guest.

## Root cause

A real Sidebar regression, not a guest/environment artifact and not a "missing wait" — confirmed with a VM run (`20260924-002137-27332`) that added a temporary `app.debugDescription` dump right after expanding the pane list in two of the five tests (one via chevron click, one via `WindowRuntime.hidePane`'s model-driven expansion). The dump proved both halves of the mechanism actually work in the guest:

- The `DisclosureGroup` genuinely expands — the outline gained a second `OutlineRow` for the pane, and its `DisclosureTriangle` reported `value: 1`.
- The `PaneRow` content genuinely renders — its `Text(paneLabel)` ("1/1 — ~") and eye-toggle `Button` ("Show"/disabled) both appear as distinct AX elements in that new row, each showing the *correct, per-row* content (label/value differ correctly row to row).

But both of those elements carried `identifier: 'session-row.Session 1'` — the *session* row's identifier — instead of the pane row's own `pane-row.<uuid>` / `pane-eye-toggle.<uuid>`. `PaneSidebarTests.paneRowCount(in:)` filters on `identifier BEGINSWITH 'pane-row.'`, which this identifier never satisfies, so it read `0` after every expansion regardless of pane count or which action triggered the expansion — matching all five observed failures, including the model-driven one in `testHidingPaneAutoExpandsPaneList`.

**Superseded — first hypothesis and "current understanding" below (round 1 review, `10eea690`, correctly rejected this).** ~~`SessionSidebarView.swift` applied `.accessibilityIdentifier("session-row.\(session.title)")` to the *whole* `DisclosureGroup { content } label: { … }` expression, not just to the label — a structural ancestor of both the label and the disclosed pane-row content. Moving that identifier down to wrap only `SessionRow(...)` inside the `label:` closure (so it is a *sibling* of the pane-row `ForEach`, not an ancestor) was committed and re-run (VM run 2, `20260924-003142-45814`): all five tests still failed at the identical lines, with no change in behavior. This disproves simple structural-ancestry scoping as the mechanism.~~ This reasoning was wrong on its own terms: the ancestry move (still in place; it is harmless and correct scoping regardless) put `SessionRow`'s own `session-row.<title>` identifier where it belongs, but **`PaneRow` itself was never marked as an accessibility container**, so the fix could not have worked — after the move, `PaneRow`'s *own* `pane-row.<uuid>` identifier (not the session's) would still spread to its children, making `paneRowCount` count 2 elements per pane (one for the label `StaticText`, one for the eye `Button`) instead of 1 — which fails the same "== 2" / "== 1" assertions at the same lines for an entirely different reason than concluded at the time. Run 2 is not evidence against the ancestry move; it never actually exercised a correct fix.

**Real mechanism, cited already elsewhere in this codebase.** Without `.accessibilityElement(children: .contain)`, SwiftUI on macOS folds a compound container view into a single accessibility leaf, and whichever `accessibilityIdentifier` is applied to that outer, folded container wins for every descendant element — overriding any identifier a child tried to set closer in the view tree. This is already documented and fixed once in this exact codebase: `PaneView.swift:219-225` marks the tab bar `.accessibilityElement(children: .contain)` specifically so each tab chip keeps its own `tab-chip.<title>` identifier instead of the whole bar collapsing to one shared identifier. The *same* run-1 `app.debugDescription` dump that found this issue's symptom shows the *same* mechanism firing one level deeper, outside the sidebar `List` entirely: the tab chip's own Close button carries `identifier: 'tab-chip.Tab'` (the chip's identifier) instead of its own — `BattyTabChip` itself isn't marked `.contain` internally, so its Close button inherits the chip's outer identifier. `PaneRow` had the identical gap: `.accessibilityIdentifier("pane-row.\(pane.id.uuidString)")` was applied to `PaneRow` without `.accessibilityElement(children: .contain)` first, so it spread to both `PaneRow`'s label `Text` and its eye-toggle `Button`, silently overriding the `Button`'s own `pane-eye-toggle.<uuid>` — which was therefore unreachable in the AX tree before this fix, independent of anything to do with `SessionRow`, `DisclosureGroup`, or `NSOutlineView` bridging specifically. The earlier "current understanding" paragraph in this section (now superseded) was chasing a List/NSOutlineView-specific theory because the tab-bar precedent wasn't checked against the run-1 dump at the time.

**Automation-only impact.** VoiceOver never exposes `accessibilityIdentifier` to begin with — it reads accessibility label/value/traits, not identifiers, so this defect never affected VoiceOver users. The impact is entirely on automation clients (XCUITest, and any other tool that queries by `accessibilityIdentifier`), which is exactly `PaneSidebarTests`' own predicament.

## Fix

`BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift`: added `.accessibilityElement(children: .contain)` to `PaneRow` immediately before its `.accessibilityIdentifier("pane-row.\(pane.id.uuidString)")` — the same shape as the tab bar's existing `.contain` + `.accessibilityIdentifier("tab-bar.\(pane.id.uuidString)")` at `PaneView.swift:219-226`. This makes `PaneRow`'s own container carry `pane-row.<uuid>` while its children (the label `Text`, the eye toggle `Button`) keep their own identity — `pane-eye-toggle.<uuid>` is no longer overridden. `SessionRow` was *not* given `.contain`: it has no child with its own identifier to protect (no `Button`, nothing else already identified), so the fold-to-a-leaf behavior is harmless there and adding `.contain` would be an unnecessary, non-minimal change to a row that #0418 (a concurrently active sidebar issue) may also be touching. The `.accessibilityIdentifier("session-row.\(session.title)")` placement on `SessionRow` inside the `label:` closure (from the earlier, still-valid part of the round-1 fix) is kept — it's correct scoping independent of the `.contain` question.

`BattyUITests/PaneSidebarTests.swift`: restored `paneRowCount(in:)` / `firstPaneRow(in:)` / `firstEyeToggle(in:)` to their original `identifier BEGINSWITH`-based queries (`pane-row.` / `pane-eye-toggle.`) — content-based matching is no longer needed now that the identifiers themselves work, and `MATCHES` is no longer used, closing off the SIGABRT hazard in this file entirely (the general hazard stays documented in `docs/ui-testing-vm.md`'s "Known limits" since a future predicate could still hit it). Added a short comment on `paneRowCount` pointing at `SessionSidebarView`'s `.contain` fix and `PaneView.swift:219-225` so a future reader doesn't have to rediscover the mechanism.

## Resolution notes

> 🟢 Resolved 2026-09-24 — all five `PaneSidebarTests` pass in the Tart VM, and `TabRenameTests` still passes too. Pane rows and their eye toggles now expose their own accessibility identifiers.

## Root cause

`PaneRow` in `SessionSidebarView.swift` had no `.accessibilityElement(children: .contain)`. SwiftUI on macOS folds a container like that into a single leaf element, and the outer identifier spreads to every child. This is the same mechanism already documented at `PaneView.swift:219-225` for the tab bar. As a result, the pane rows' text and eye buttons carried an ancestor's identifier, `identifier BEGINSWITH 'pane-row.'` never matched, and `pane-eye-toggle.*` was unreachable. The impact is on automation only: VoiceOver never exposes `accessibilityIdentifier`.

## Fix

- `.accessibilityElement(children: .contain)` on `PaneRow`, placed before its `pane-row.<uuid>` identifier. `SessionRow` was left alone because it has no child with its own identifier.
- `PaneSidebarTests` queries are back to their original identifier-based form. Only a comment was added.
- `docs/ui-testing-vm.md` gains a gotcha: a `MATCHES` predicate evaluated over `.any` or mixed-type descendants can SIGABRT the guest app. That happened in run `20260924-005144-71495` during an intermediate content-matching attempt, which was later dropped.
