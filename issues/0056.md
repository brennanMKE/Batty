## Description

This is a **verification** ticket, not a fresh bug. Once `#0051`, `#0052`, and `#0053` land — click-to-focus on the terminal surface, visual indication of the focused pane, click-to-focus on a tab chip — we need to confirm end-to-end that the **split button** (toolbar split-horizontal / split-vertical icons) and the `Cmd-D` / `Cmd-Shift-D` keybindings target whichever pane the user perceives as focused.

Today, the splits dispatch to `store?.selectedSession?.tree.splitFocusedPane(...)` which operates on `tree.focusedPaneID`. The model side is already correct. The verification gap is the *view → model* side: after the user clicks into a pane (whether on the terminal body or on a chip), does `tree.focusedPaneID` reflect that click before the next split action runs?

Don't start this ticket until `#0051`, `#0052`, and `#0053` are all in `resolved` or `closed`.

## Steps to reproduce (the test scenario)

After `#0051`, `#0052`, and `#0053` have landed:

1. Open a session. Hit `Cmd-D` to create two panes (A on left, B on right). `tree.focusedPaneID = B`. The visual cue from `#0052` shows B emphasized.
2. Click anywhere in pane A's terminal body. The `#0052` emphasis should flip to A. The `#0051` write should set `tree.focusedPaneID = A`.
3. Click the toolbar split-horizontal button (or hit `Cmd-D`). **Expected:** A splits, producing A + A' to the right of A. B stays untouched. **Failure mode to catch:** B splits because the click-to-focus write didn't land before the menu/keybinding fired.
4. Repeat the dance using a tab-chip click instead of a terminal-body click (the `#0053` path).
5. Repeat with `Cmd-Shift-D` (split vertically).

Then exercise the keyboard-only path:

6. With two panes side-by-side and B focused, hit `Cmd-Option-Left` to move focus to A. The `#0020`-style geometric movement already writes to `focusedPaneID`. Hit `Cmd-D`. Expected: A splits.

## Expected behavior

The split action always targets the pane the user perceives as focused, regardless of *how* they focused it:

- Click in terminal body (`#0051`)
- Click on tab chip (`#0053`)
- Geometric arrow movement (`#0020`)
- Newly-split pane takes focus (`#0018`)

`#0052`'s visual emphasis is the user-facing source of truth: the pane that's emphasized *is* the one the next split targets. If the test ever shows the emphasis and the split target disagreeing, that's a bug worth re-opening regardless of which side is wrong.

## Actual behavior (to be verified)

Unknown until `#0051` and `#0053` land. The hypothesis is that they will make it work; this ticket is to **confirm** rather than **fix**.

If the verification reveals a bug, file (or re-open) the appropriate dependency issue with a precise repro. Don't fix the bug under this ticket — keep this one focused on the test pass/fail signal.

## Notes

- Verification effort is small: 5–10 minutes of clicking + Cmd-D, ideally with a quick UI-test pass that scripts the click → split → assert-which-pane-grew chain. A dedicated UI test in `BattyUITests` that exercises this would be the artifact this ticket produces.
- Re-entrancy is the most likely failure path: if the click-to-focus write is scheduled async (e.g. via `.task` or `DispatchQueue.main.async`), `Cmd-D` fired in the same runloop cycle could see the *old* `focusedPaneID`. Synchronous write from the click handler is the safer design.
- Related: `#0018` (split focuses new pane), `#0020` (geometric focus movement), `#0051` (terminal-surface click-to-focus — dependency), `#0052` (focus visual indication — dependency for "user perceives"), `#0053` (chip click-to-focus — dependency).

## Acceptance criteria

- Block: `#0051`, `#0052`, `#0053` are all `resolved` or `closed`.
- Manual verification: each of the six scenarios above (terminal-body click + split, chip click + split, geometric movement + split; horizontal and vertical) splits the correct pane every time.
- A UI test in `BattyUITests` covers at least scenarios (3) and (6) — click-to-focus + split, and arrow-focus + split — to prevent regression.
- If verification fails, this ticket gets `## Notes` describing exactly which scenario broke, and the failing scenario is filed as a new bug or re-opened under the matching dependency issue. This verification ticket itself is not the place to land the fix.

## Out of scope

- Splitting on a non-focused pane via right-click context menu — separate feature, not currently part of the toolbar/keybinding flow.
- "Split into N panes" or other advanced split shapes — Concepts.md scope is one-divider-at-a-time recursive splits.
- Persistence of the split layout — separate axis, covered by the Persistence module.

## Verification result

All dependencies are resolved (`#0051`, `#0052`, `#0053`). At the model level the contract holds: a `focusedPaneID` write followed by `splitFocusedPane` targets the written pane. Added `FocusThenSplitTests` exercises the explicit-focus path.

## Files changed

- `BattyKit/Tests/BattyKitTests/FocusThenSplitTests.swift` (new) — model-level test asserting that writing `tree.focusedPaneID` then splitting targets the written pane.

## Gotchas

- **The XCUITest scenarios from the AC (3) and (6) are not implemented.** Adding a meaningful UI test would require accessibility identifiers on `PaneView` and per-pane click hit areas that the test harness can query. That's separate scope — file a dedicated UI-test instrumentation issue if regression risk justifies it. The model-level test caught the relevant invariant; the view-side wiring from `#0051` (`.onChange(of: tab.terminal.isFocused) { ... }`) calls `AppStateStore.focusPane(id:)` synchronously, so re-entrancy isn't a concern.
- **The geometric-focus path (`session.focusPane(adjacent: .left)`) couldn't be unit-tested cleanly** because it depends on `paneFrames` being populated by SwiftUI rendering. The dedicated test (`directFocusedPaneIDWriteThenSplitTargetsThatPane`) writes `focusedPaneID` directly, which is what `#0020`'s geometric movement does internally. Manual verification of the keyboard path remains the user's check.
- **Visual emphasis (`#0052`) is the user-facing source of truth.** If you ever see the emphasis disagree with which pane the next `Cmd-D` splits, that's a regression worth investigating immediately — file under `#0051` or `#0052` as appropriate.
