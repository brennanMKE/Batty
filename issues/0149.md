## Description

The theme system was over-corrected during the #0147 fix. The correct design is a two-tier fallback chain (`localThemeName` → global UserDefaults → system default), but the current code treats `localThemeName = nil` as "no theme / system default" instead of "inherit global." As a result, switching sessions after applying a global theme drops the chrome back to the system default, and terminals and chrome are inconsistent. See `docs/themes.md` section 9 for the authoritative design.

## Steps to reproduce

1. Launch the app (UserDefaults has a previously-chosen global theme, e.g. "Red Alert").
2. Observe Session 1: chrome is system dark, terminal background is also default — the global theme is not applied at all.
3. Open the global theme selector (Cmd-Shift-T) and pick "Red Alert".
4. All 3 sessions show red terminals and red chrome.
5. Switch to Session 2.
6. Chrome drops to system dark. Terminal stays red. Chrome and terminal are inconsistent.
7. Switch back to Session 1 — chrome is also system dark now, not red.

## Expected behavior

- On launch, if a global theme was previously chosen, all sessions (with `localThemeName = nil`) start with that theme applied (chrome + terminal background).
- Applying a global theme updates all sessions whose `localThemeName` is `nil`. Sessions with a local override keep their local theme.
- Switching sessions updates the chrome to reflect the selected session's effective theme (local override if set, global fallback otherwise). The chrome never drops to system default unless neither local nor global theme is set.

## Actual behavior

- `AppStateStore.init()` initializes `themeChrome` with a nil palette instead of seeding from the global UserDefaults key. The chrome starts system default even when a global theme is stored.
- `TabRuntime.init()` uses `TerminalViewState(theme: .default)` — new terminals ignore the global theme entirely.
- `applyActiveSessionTheme()` has no global fallback. Sessions with `localThemeName = nil` always reset chrome to system default, regardless of the stored global theme.
- `applyThemeToAllSurfaces()` (incorrectly, from a recent change) sets `session.localThemeName = theme.name` on every session — this means sessions no longer follow the global theme on subsequent changes.

## Notes

**Correct design** (see `docs/themes.md` section 9):

```
session.localThemeName  →  ThemePreference (UserDefaults)  →  system default
```

- `nil` = follow global. Changing global theme propagates immediately.
- non-nil = override. Changing global theme leaves this session alone.

**Required code changes:**

1. **`AppStateStore.init()`** — restore `ThemeChrome(palette: ChromePalette(theme: ThemePreference.activeTheme()))` so the chrome starts correct on launch.

2. **`TabRuntime.init()` + `TabRuntime.activeTheme()`** — restore `TerminalViewState(theme: Self.activeTheme())` and the private `activeTheme()` static method that reads the global UserDefaults key. This bakes the global theme into libghostty before surface creation — the only reliable init-time path.

3. **`applyActiveSessionTheme()`** — restore the global fallback, but scoped to the selected session only (not all sessions):
   ```swift
   public func applyActiveSessionTheme() {
       guard let session = selectedSession else { return }
       let themeName = session.localThemeName
           ?? UserDefaults.standard.string(forKey: ThemePreference.defaultsKey)
       if let name = themeName, !name.isEmpty,
          let theme = GhosttyThemeCatalog.theme(named: name) {
           applyTheme(theme, to: session)
       } else {
           themeChrome.update(from: nil)
       }
   }
   ```

4. **`applyThemeToAllSurfaces()`** — remove the `session.localThemeName = theme.name` line added in the recent regression fix. The global picker must NOT write `localThemeName`. It should only apply to sessions whose `localThemeName` is `nil`:
   ```swift
   for session in sessions where session.localThemeName == nil {
       // apply terminal theme
   }
   // Update chrome only if the selected session follows global
   if selectedSession?.localThemeName == nil {
       themeChrome.update(from: theme)
   }
   ```

**Root cause of the regression:** #0147 correctly identified that the original `applyActiveSessionTheme()` was calling `applyThemeToAllSurfaces()` (applying to all sessions when it should apply to only the selected one). But the fix went too far — it removed the global fallback entirely, changed `nil` to mean "no theme," and broke the fundamental two-tier design. The correct fix for #0147 was to scope `applyActiveSessionTheme()` to the selected session while keeping the global fallback.

## Root cause

Over-correction in the #0147 fix: the global fallback was removed from `applyActiveSessionTheme()`, `AppStateStore.init()` was changed to start with a nil palette, `TabRuntime.init()` was changed to use `.default`, and `applyThemeToAllSurfaces()` was incorrectly changed to write `localThemeName` on all sessions. Together these broke the `nil → global` fallback contract.

## Fix

Restored all four code locations to implement the correct two-tier fallback chain: `session.localThemeName` → global `UserDefaults` key → system default.

- `AppStateStore.init()` seeds `themeChrome` from `ThemePreference.activeTheme()`
- `TabRuntime.init()` uses `Self.activeTheme()` (restored private helper)
- `applyThemeToAllSurfaces()` only applies to `localThemeName == nil` sessions; never writes `localThemeName`
- `applyActiveSessionTheme()` resolves `session.localThemeName ?? UserDefaults global`; falls back to chrome reset only when neither is set

## Files changed

- `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift` — seed themeChrome from global theme
- `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift` — restore `Self.activeTheme()` and `activeTheme()` helper
- `BattyKit/Sources/BattyKit/Theme/ThemePreference.swift` — fix `applyThemeToAllSurfaces` and `applyActiveSessionTheme`
