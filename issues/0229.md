## Description

Running the full UI suite for release prep surfaced 6 failing tests in `PaneFocusTests`. They reproduce **identically on `main`** with none of the in-flight #0227/#0228 changes, so they are pre-existing — not introduced by recent work. Two of them are an outright app crash (`EXC_BREAKPOINT` / `NSException` thrown inside AppKit constraint layout) during Cmd-Option-arrow focus movement across a split.

## Failing tests

- `testClickInBottomPaneAfterVerticalSplitFocusesIt` — XCTAssertTrue failed (click didn't move focus)
- `testClickInLeftPaneAfterHorizontalSplitFocusesIt`
- `testClickInRightPaneAfterHorizontalSplitFocusesIt`
- `testClickInTopPaneAfterVerticalSplitFocusesIt`
- `testCmdOptionArrowsMoveFocusAcrossHorizontalSplit` — `Application co.sstools.Batty.beta is not running` (app crashed; ~104 s timeout)
- `testCmdOptionArrowsMoveFocusAcrossVerticalSplit` — `crashed in <external symbol>` (~107 s)

`testCmdDFocusesNewPane` and `testCmdShiftDFocusesNewPane` pass.

## Crash signature

From `~/Library/Logs/DiagnosticReports/Batty-2026-05-30-2*.ips`:

- `EXC_BREAKPOINT (SIGTRAP)` via `+[NSApplication _crashOnException:]`
- Faulting stack is entirely AppKit: `_NSViewLayout` → `NSPerformVisuallyAtomicChange` → `-[NSView _layoutSubtreeWithOldSize:]` → `-[NSWindow _layoutViewTree]` → display-cycle layout. No Batty/BattyKit frames in the top frames — an Objective-C exception raised during the constraint-based layout pass.

## Long Description

Two distinct symptoms, possibly related:

1. **Click-to-focus after split (4 tests):** clicking a pane after a horizontal/vertical split does not move focus to it. These may be sensitive to the test machine not being frontmost/focused — focus/click UI tests are the most environment-dependent in the suite.
2. **Cmd-Option-arrow focus navigation across splits (2 tests):** the app crashes with an AppKit-layout `NSException`. This looks like a genuine crash, not just a focus assertion miss.

### Investigation 2026-06-03 (bailed — could not verify on this machine)

**Blocked by environment, not by analysis.** The whole point of this issue
is to reproduce the crash and confirm a fix via
`scripts/run-ui-tests.sh BattyUITests/PaneFocusTests`. On this MacBook the

```

    Not authorized for performing UI testing actions.
```

All 8 tests fail at `BattyUITestHarness.swift:22` with this AX
authorization error (the runner is missing the Accessibility/Automation
TCC grant; the system prompt was canceled). This is exactly the
MacBook-vs-Mac-mini split the issue already flags. Because the harness
can't drive the UI, the crash and the chipTitle loop are both
**unreproducible on this machine**, so no code change could be verified to
the project's standard ("compilation alone is NOT verification"). Rather
than commit a speculative fix, work stopped here. `scripts/build.sh`
passes; no code was changed.

**Static analysis narrowed the loop to a SwiftUI body / AppKit layout
feedback cycle, ranked by likelihood:**

1. **First-responder churn during focus move (top suspect for the crash).**
   `PaneView` reacts to `isPaneFocused` via
   `.onChange(of: isPaneFocused) { … TerminalSurfaceFocuser.focusWhenReady(tab:) }`,
   which calls `window.makeFirstResponder(view)` and also schedules a
   retry `Task` (16ms→800ms ladder). Promoting first responder inside a
   SwiftUI update can re-enter AppKit layout (`_NSViewLayout`), matching
   the crash stack. The terminal's `isFocused` flip then routes back
   through `.onChange(of: tab.terminal.isFocused) → appStore.focusPane(id:)`,
   which sets `tree.focusedPaneID`. `@Observable` fires `withMutation`
   even on equal-value writes, so re-asserting the same `focusedPaneID`
   re-invalidates every `PaneView`. The retry `Task` keeps re-issuing
   `makeFirstResponder` across runloop turns, which can keep the cycle hot
   during the focus move — consistent with the repeating chipTitle log.
   Suggested fix to try on the mini: (a) make `AppStateStore.focusPane(id:)`
   a no-op when `focusedPaneID` is already `id` (avoid the redundant
   `@Observable` mutation); (b) gate `focusWhenReady`'s retry so it
   doesn't fire when the view is already first responder; (c) consider
   hopping `focusWhenReady`'s initial `makeFirstResponder` to the next
   runloop turn (`Task { @MainActor in … }`) so it never runs inside the
   SwiftUI layout pass.

2. **Geometry → frame mutation re-entrancy.** `TerminalPlaceholderView.body`
   has a side effect (`let _ = TerminalHostStore.shared.terminalView(for:)`,
   which does `addSubview` on first eval) and an `.onGeometryChange` that
   synchronously sets `view.frame` via `setPlacement`. Setting an
   `AppTerminalView.frame` (frame-based view inside a SwiftUI Auto-Layout
   container) during the layout pass can re-dirty layout. `isPaneFocused`
   is a `let` on the placeholder, so each focus move recreates the
   placeholder and re-runs this. Worth instrumenting
   `TerminalHostStore.setPlacement` / `updatePlacements` for repeated
   frame writes during a focus move.

3. **`chipMaxWidth`/`charBudget` from `paneWidth`.** `paneWidth` is
   `@State` from `.onGeometryChange`; it feeds `.frame(width: chipMaxWidth)`
   on each chip. Lower likelihood (chip width derives from pane width, not
   vice-versa) but a rounding oscillation can't be ruled out from static
   reading alone.
