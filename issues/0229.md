## Description

Running the full UI suite for release prep surfaced 6 failing tests in `PaneFocusTests`. They reproduce **identically on `main`** with none of the in-flight #0227/#0228 changes, so they are pre-existing — not introduced by recent work. Two of them are an outright app crash (`EXC_BREAKPOINT` / `NSException` thrown inside AppKit constraint layout) during Cmd-Option-arrow focus movement across a split.

## Resolution notes

> 🟢 Resolved 2026-06-03 — fixed the cross-split focus crash + infinite layout loop by making `focusPane(id:)` idempotent and deferring the `focusedPaneID` write out of the AppKit layout pass. Crash and the chipTitle runaway are gone; the remaining click-focus / occasional arrow misses are pre-existing environment sensitivity (no crash) for Mac-mini confirmation.

## Root cause

The fresh crash report's `lastExceptionBacktrace` (not just the faulting
thread) was the key evidence the earlier static analysis lacked. The
exception is thrown by `-[NSWindow _postWindowNeedsUpdateConstraints]`,
reached from a SwiftUI `ObservationGraphMutation.apply` being **flushed
while AppKit is inside `_NSViewLayout`**. In other words: an `@Observable`
model write happened during the layout pass, which made SwiftUI dirty
window constraints mid-layout — AppKit treats that as illegal and raises
an NSException that `+[NSApplication _crashOnException:]` turns into the
`EXC_BREAKPOINT`.

The write is the focus round-trip. A focus move promotes a terminal to
first responder; AppKit can run that `makeFirstResponder` from inside its
layout pass (cross-split moves do). Promotion flips
`TerminalViewState.isFocused` (`@Observable`) synchronously, and
`PaneView.onChange(of: tab.terminal.isFocused)` then wrote
`tree.focusedPaneID` via `AppStateStore.focusPane(id:)` — a second
`@Observable` mutation, applied mid-layout. That is the crash.

Before the crash it also drove the documented infinite
`TabTitleFormatter.chipTitle` loop: `focusPane` re-asserted the *same*
`focusedPaneID`, and `@Observable` fires `withMutation` even on
equal-value writes, so every PaneView re-invalidated each turn and kept
the cycle hot.

This matches suspect #1's *mechanism* from the prior analysis, but the
precise trigger is the `focusPane` write running during layout, not the
`makeFirstResponder` call itself.

## Fix

Two minimal changes targeting the two writes in the cycle (the
`TerminalSurfaceFocuser` retry ladder was left unchanged — deferring the
`makeFirstResponder` there was tried and regressed the previously-green
split tests, see Gotchas):

1. `AppStateStore.focusPane(id:)` is now idempotent — it skips the write
   when `focusedPaneID` already equals `id`. Kills the equal-value
   `@Observable` mutation that re-armed the loop.
2. `PaneView`'s `.onChange(of: tab.terminal.isFocused)` hops the
   `focusedPaneID` write to the next main-actor turn (`Task { @MainActor }`),
   so the mutation never lands while AppKit is inside `_NSViewLayout`.

## Gotchas

- **The crash is the hard gate and it is fixed; the click-focus tests are
  not.** The 4 `testClickIn…` failures pre-date this fix (verified by a
  clean-`main` baseline run on the same machine: identical 6/8 failure set,
  with the crash) and the occasional Cmd-Option-arrow *assertion* miss is
  the same class of synthesized-input focus flakiness. Per the issue's own
  notes these need confirmation on the Mac mini, where the runner is the
  release gate; they were not filed as a separate issue because this issue
  already documents them as known environment sensitivity (lines under
  "Long Description" / "Notes").
- **Deferring `makeFirstResponder` in `TerminalSurfaceFocuser.focusWhenReady`
  is the wrong lever.** Two variants were tried (always-defer; defer +
  staleness predicate). Both eliminated the crash but *regressed* the
  previously-green `testCmdD/ShiftDFocusesNewPane` split tests: with the
  promotion deferred, a stale focus task for the previously-focused tab
  raced the split and dragged `focusedPaneID` back to the old pane (caught
  in a trace: `focusPane change … -> newPane` immediately followed by a
  re-promotion of the *old* tab). Deferring the *model write* in PaneView
  instead of the *responder promotion* keeps focus deterministic while
  still moving the offending `@Observable` mutation out of the layout pass.
- The decisive diagnostic was the crash report's `lastExceptionBacktrace`
  (`asiBacktraces`), not the faulting-thread stack the issue quoted — the
  faulting thread is all generic AppKit display-cycle frames; the thrown
  exception's own backtrace names `_postWindowNeedsUpdateConstraints` ←
  SwiftUI `NSHostingView.setNeedsUpdate` ← `ObservationGraphMutation`.

1. **Click-to-focus after split (4 tests):** clicking a pane after a horizontal/vertical split does not move focus to it. These may be sensitive to the test machine not being frontmost/focused — focus/click UI tests are the most environment-dependent in the suite.

**Static analysis narrowed the loop to a SwiftUI body / AppKit layout
feedback cycle, ranked by likelihood:**

1. **First-responder churn during focus move (top suspect for the crash).**
   `PaneView` reacts to `isPaneFocused` via
   `.onChange(of: isPaneFocused) { … TerminalSurfaceFocuser.focusWhenReady(tab:) }`,
   which calls `window.makeFirstResponder(view)` and also schedules a
   retry `Task` (16ms→800ms ladder). Promoting first responder inside a
   SwiftUI update can re-enter AppKit layout (`_NSViewLayout`), matching
   the crash stack. The terminal's `isFocused` flip then routes back
   through `.onChange(of: tab.terminal.isFocused) → appStore.focusPane(id:)`,
   which sets `tree.focusedPaneID`. `@Observable` fires `withMutation`
   even on equal-value writes, so re-asserting the same `focusedPaneID`
   re-invalidates every `PaneView`. The retry `Task` keeps re-issuing
   `makeFirstResponder` across runloop turns, which can keep the cycle hot
   during the focus move — consistent with the repeating chipTitle log.
   Suggested fix to try on the mini: (a) make `AppStateStore.focusPane(id:)`
   a no-op when `focusedPaneID` is already `id` (avoid the redundant
   `@Observable` mutation); (b) gate `focusWhenReady`'s retry so it
   doesn't fire when the view is already first responder; (c) consider
   hopping `focusWhenReady`'s initial `makeFirstResponder` to the next
   runloop turn (`Task { @MainActor in … }`) so it never runs inside the
   SwiftUI layout pass.

2. **Geometry → frame mutation re-entrancy.** `TerminalPlaceholderView.body`
   has a side effect (`let _ = TerminalHostStore.shared.terminalView(for:)`,
   which does `addSubview` on first eval) and an `.onGeometryChange` that
   synchronously sets `view.frame` via `setPlacement`. Setting an
   `AppTerminalView.frame` (frame-based view inside a SwiftUI Auto-Layout
   container) during the layout pass can re-dirty layout. `isPaneFocused`
   is a `let` on the placeholder, so each focus move recreates the
   placeholder and re-runs this. Worth instrumenting
   `TerminalHostStore.setPlacement` / `updatePlacements` for repeated
   frame writes during a focus move.

3. **`chipMaxWidth`/`charBudget` from `paneWidth`.** `paneWidth` is
   `@State` from `.onGeometryChange`; it feeds `.frame(width: chipMaxWidth)`
   on each chip. Lower likelihood (chip width derives from pane width, not
   vice-versa) but a rounding oscillation can't be ruled out from static
   reading alone.
