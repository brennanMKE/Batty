## Description

The user wants the Projects commands in their own top-level **Projects** menu, and the **Background Images…** item gone from the File menu. User request, verbatim:

> "Change the File menu. Make a top level Projects item and put the Save to Project and Edit Projects there. But just change Edit Projects to Projects since it brings up the window. Remove the Background Images item. It does not do anything when that window is opened. It is a selector UI."

Today the File menu is built in `BattyKit/Sources/BattyKit/Commands/BattyCommands.swift`, in `CommandGroup(replacing: .newItem)` (line 147). In order, it has: New Window, New Session, Open Quickly…, Open Project ▸ (submenu), the Save Session items (`saveSessionMenuItems`, lines 87–109), **Edit Projects…** (lines 181–186, opens `ProjectEditorWindowController.shared.show(store:)`), and **Background Images…** (lines 188–192, opens `BackgroundImagesWindowController.shared.show(store:)`).

"Save to Project" in the request means the Save Session items. Their titles depend on the selected Session:
- From a Session opened from a Project: **Update "Name"…** and **Save Session as New Project…**.
- Otherwise: **Save Session as Project…**.

All of them are disabled when `SaveSessionAsProjectMenuModel.isEnabled` is false. None of the moved items has a keyboard shortcut, and none is behind a feature flag. The Projects flag was removed in #0504 (resolved). `FeatureFlags` (`BattyKit/Sources/BattyXPCCore/FeatureFlags.swift`) now carries only `sharedProjectImages`. The Project Editor window is already titled "Projects" (`ProjectEditorWindowController.swift:79`), so the new item name matches the window.

## Requirements

1. **A top-level Projects menu.** Add a `CommandMenu("Projects")`. Move the Save Session items into it with their titles, enablement and Update/New split unchanged. Move **Edit Projects…** into it, renamed **Projects…**, with the same action and SF Symbol. Keep any shortcuts, though the moved items have none today.
   - **Placement.** The requested place is right after File. SwiftUI `CommandMenu`s are inserted between View and Window in declaration order; the existing Session, Theme, Pane and Tab menus are placed that way. A custom menu probably can't sit directly after File. That is also the macOS convention: app-specific menus go between View and Window, like Xcode's Product menu or Safari's History and Bookmarks. Put Projects first among the custom menus, before Session, which is next to File in spirit. The plan checks the actual menu-bar order and records the reason.
   - **Open Project.** The request doesn't mention the **Open Project ▸** submenu (lines 170–178, with Choose Project… and New Project…). It stays in File unless the user says otherwise; the plan may ask. Don't move it silently.
2. **Remove Background Images… from the File menu.** In the user's view, the window is a selector, and opened standalone it does nothing useful. Every other entry point that opens it in standalone (`.manage`) mode:
   - Command Palette `extra:backgroundImages` "Background Images…" (`CommandPaletteView.swift:122–135`, with the `openBackgroundImages` test seam at line 60).
   - Settings ▸ Appearance ▸ Background ▸ **Manage Images…** (`SettingsView.swift:314–317`, `appearance-background.manage-images`). This also opens the standalone window, not the picker.
   - The window lists itself in the Window menu while open. That isn't an opener.
   - No CLI command opens it (checked `BattyKit/Sources/batty`, `BattyCLICore`).

   The picker paths stay: the **Choose…** sheets in `TerminalBackgroundControls.swift:65–76` (`BackgroundImagesView(mode: .pick(...))`), used by Settings, the Pane and Session background sheets, and the Project Editor's background row.

   **Before removing the other entry points, the plan must resolve one conflict.** The standalone window is more than a selector. In `BackgroundImagesView.swift`, `.manage` mode is the only place that offers **Remove…** (the context menu at line 160 and `RemoveSelectionButton` at line 242 are both `if !isPicking`), along with its removal confirmation and in-use listing. Remove all standalone entry points and users can no longer delete images from the library. The default is still to remove the palette entry. The plan then picks one option, or asks the user:
   - (a) keep Settings' **Manage Images…** as the one standalone path, or
   - (b) add Remove to `.pick` mode and remove every standalone entry point (and possibly `BackgroundImagesWindowController`).
3. **UI tests.** Update every test that opens Background Images or the Projects items from the File menu:
   - `BattyUITests/BackgroundImagesWindowTests.swift`:
     - `openFromFileMenu` (line 32) is used by `testFileMenuOpensTheWindowAndWindowMenuListsIt`, `testAnImageShowsItsThumbnailNameAndSize`, `testRemovingAnUnusedImageRemovesItsCell`, `testRemovingAProjectsImageListsTheProjectAndClearsItsPath`, `testArrowKeySelectsACellOnTheFirstOpen`, `testClickingACellAfterScrollingKeepsTheGridStill`, `testArrowKeySelectionAfterScrollingKeepsTheGridStill` and `testClickingACellCutOffAtTheBottomKeepsTheGridStill`.
     - `testCommandPaletteOpensTheWindow` and `testSettingsManageImagesOpensTheWindow` (depending on the decision in requirement 2).
     - `testProjectChooseCopiesThePickIntoProjectBackgrounds` clicks File ▸ Edit Projects (line 392).
     - The Remove tests need whichever path keeps Remove reachable.
   - `BattyUITests/BackgroundSetsTests.swift`: File ▸ Background Images at lines 75, 224 and 355. These are in `testBackgroundSetsShowsTheSetsWithoutFetchingAFullSizeImage`, `testClickingAnotherImageWhileOneDownloadsAppliesTheNewOne`, and the #0624 scroll tests from line 307 (`testSelectingASetImageAfterScrollingKeepsTheGridStill` and the later grid-still tests that open the window through the code at line 355). Move them to the picker path, or to the kept manage path.
   - `BattyUITests/ProjectsOpenTests.swift:355–357` asserts File has Edit Projects and Save Session as. Change it to the Projects menu, and assert File no longer has them.
   - `BattyUITests/Support/ProjectsHarness.swift:358–362` `openEditorFromFileMenu`, which clicks File ▸ Edit Projects. It is used across `ProjectsEditorTests`, `ProjectsEditorQuitTests`, `ProjectsSharingTests`, `ProjectsStartupTests` and `ProjectsSymbolTests` (22 references). Point it at Projects ▸ Projects…, and consider renaming the helper.
   - Unit test `BattyKit/Tests/BattyKitTests/CommandPaletteViewActionTests.swift:46` `backgroundImagesCommandOpensTheWindow`. Remove or update it with the palette entry.
   - Check the new UI tests compile with `./build.sh ui-typecheck`. The tests run in the VM per the verification tiers.
4. **Docs, Help, website.** Update every place that names these menu locations:
   - Help: `BattyKit/Sources/BattyKit/Help/10-projects.md` lines 8–10 (File ▸ Save Session as Project…, Update, Save Session as New Project…, File ▸ Edit Projects…). `BattyKit/Sources/BattyKit/Help/11-backgrounds.md:35` (File → Background Images…, Manage Images…).
   - `docs/ui-features.md`: lines 910, 1011, 1236, 1293 and 1325 (File ▸ Edit Projects…, the File-menu order "between Open Project and Edit Projects", the test table).
   - `website/backgrounds.html:268` "Choose File → Background Images…".
   - `README.md` has no mentions. Leave `website/changelog.html` history as is, but add a 1.4.0 entry if the changelog for the release is being written.
   - Check the localization catalog for the old strings: "Edit Projects…" goes and "Projects…" is new.

## Notes

- The user's premise is partly false. The standalone window does do things: it lists every image with its uses and size, offers Add from File… and Remove…, and shows Background Sets. Requirement 2's conflict comes from that. Raise it with the user if the plan can't settle it from the request.
- The `.newItem` CommandGroup also builds `projectMenuItem(.newProject)` (line 137–140), which opens the Project Editor with `startNewProject: true`. That item stays in the Open Project submenu.
- Restricted areas are untouched: no `Configuration/Build.xcconfig` or `scripts/` changes.
