## Description

When Sparkle installs an update and asks Batty to quit, Batty answers with its modal "Quit Batty? There are N open terminal(s)." alert (`QuitConfirmation.shouldQuitOrPrompt`, run from `applicationShouldTerminate`). Sparkle waits until someone answers. With the headless #0714 driver nobody can, so the update never installs. A real user who has just clicked **Install and Relaunch** in Sparkle's dialog is asked a second time whether to quit.

The VM run had "Keep terminals running when Batty quits" on (#0696), so the alert's warning was also wrong: those terminals would have been kept. On `main` and in shipped 1.4.x that option doesn't exist, terminals do close on an update, and the alert's text is accurate. The plan has to decide what a Sparkle-initiated quit should do in each case (see Expected behavior).

**Shipped versions show the alert too, by reading the code.** `release/1.4` has the same path: `applicationShouldTerminate` → `AppStateStore.handleTerminateRequest` → `QuitConfirmation.shouldQuitOrPrompt` → `NSAlert.runModal()`, gated only by `SettingsPreference.resolvedConfirmQuit`, whose default is `defaultConfirmQuit = true`. Prod's `UpdaterController` builds `SPUStandardUpdaterController(… updaterDelegate: nil …)`, so nothing tells the quit path that Sparkle asked for it. So a 1.4.x user with any terminal open who clicks Install and Relaunch should get "Quit Batty?". This was not reproduced on a Prod build: the evidence below is a Beta built from `issue/0696` + `main` + `issue/0715`. In Prod it is a redundant second confirmation, not data loss or a hang, because a person is there to click Quit. If they click Cancel, Sparkle's installer gets `applicationTerminated: false` and the update stays staged.

### Premises checked

- The path is as the issue says. `BattyApp.applicationShouldTerminate` → `AppStateStore.handleTerminateRequest` (`AppStateStore+Quit.swift`) → the default `confirm` → `QuitConfirmation.shouldQuitOrPrompt` → `NSAlert.runModal()`. That is gated by `SettingsPreference.resolvedConfirmQuit` (default `true`) and `openTerminalTabCount > 0`. Both backends pass `updaterDelegate: nil` / `delegate: nil` today.
- **Which callback runs before Sparkle's quit, for install-and-relaunch.** `SPUCoreBasedUpdateDriver` reacts to the user's `.install` by calling `-[SPUInstallerDriver installWithToolAndRelaunch:YES …]` (l.317). That runs `shouldPostponeRelaunchForUpdate` (if implemented), then `installerWillFinishInstallationAndRelaunch:`. In `SPUCoreBasedUpdateDriver` (l.322–338) that calls **`updater(_:willInstallUpdate:)`**, then posts `SUUpdaterWillRestartNotification` and calls **`updaterWillRelaunchApplication(_:)`**. Only after that does it send `SPUResumeInstallationToStage2` to the installer (`SPUInstallerDriver.m` l.600–611), which is what sends the app its quit Apple Event. So both callbacks run in the app, on the main thread, **before** `applicationShouldTerminate`. This is the same for the standard driver and the #0714 headless driver, because both go through `SPUCoreBasedUpdateDriver`.
- **Install-on-quit** (the headless `onquit` mode, or a staged update with the standard driver): the user starts the quit. Sparkle's installer waits for the app to terminate, and the app-side `installerWillFinishInstallationAndRelaunch:` runs (if at all) after termination (`SPUInstallerDriver.m` l.352–366). So an install-on-quit is an **ordinary quit** and may ask, as the issue says.
- **The standard controller forwards the delegate.** `SPUStandardUpdaterController(startingUpdater:updaterDelegate:userDriverDelegate:)` builds its `SPUUpdater` with that delegate. It holds the delegate weakly (IBOutlet), as `SPUUpdater` does, so `UpdaterController` must keep a strong reference.
- **Does shipped 1.4.x show the alert?** Yes, by reading the code (not reproduced on a Prod build, and no VM Prod run is planned). `release/1.4`'s `applicationShouldTerminate` / `handleTerminateRequest` / `QuitConfirmation` match `main`, and its `UpdaterController` passes `updaterDelegate: nil`. `SPUStandardUserDriver.showInstallingUpdate(applicationTerminated: false, …)` (l.864–882) just closes its status window and keeps the retry handler. So a 1.4.x user with `confirmQuit` on and at least one terminal open gets "Quit Batty?" after clicking Install and Relaunch. Quit installs. Cancel leaves the update staged, and it installs on the next quit (which asks again). A redundant prompt, not a hang or data loss.
- `windowNeedsConfirmClose` is a separate path (window close) and is not touched.

### Decisions

1. **Signal: a one-shot "preconfirmed quit" flag**, set by `SPUUpdaterDelegate.updater(_:willInstallUpdate:)` on both backends. That callback fires for every immediate install, relaunching or not. `updaterWillRelaunchApplication` would miss a non-relaunching immediate install. Identifying the Quit Apple Event's sender was rejected: Sparkle's installer is a separate process (Autoupdate/the progress agent) whose identity and bundle path vary, and the same event comes from logout, Dock and `osascript`.
2. **The flag is consumed by the next terminate request**, whatever its outcome, and also cleared by `updater(_:didAbortWithError:)` (a failed install). So:
   - a cancelled quit (only possible through the Project Editor's Cancel, since the alert is skipped) leaves no flag behind, and a later Cmd-Q asks;
   - if Sparkle's standard driver retries the terminate after a cancel (the user re-opens the update and clicks again), `installWithToolAndRelaunch` runs again, but Sparkle doesn't re-notify `willInstallUpdate` (`_notifiedDelegateInstallationWillFinish`). So that retry **asks** "Quit Batty?". That's acceptable: a person is there, and the headless driver never retries. Record it in `## Gotchas`.
   - Residual: if the installer dies after `willInstallUpdate` and before it sends the quit, the flag survives until the next quit, which then skips the alert once. Record it in `## Gotchas`. Not worth a clock.
3. **Terminals not kept (1.4.x, `main` today, or #0696's option off): no second alert.** This is the issue's recommended default. The user just chose Install and Relaunch in Sparkle's dialog, the headless driver can't answer a modal, and a warning belongs in the update flow if anywhere, not in `applicationShouldTerminate`. This removes the only on-screen notice that N terminals will close during an update. That is a user-visible change, so the changelog says it (see Files). The user can override this (Open question 1).
4. **Terminals kept (#0696):** the Sparkle quit never prompts. That follows from 3. Nothing here depends on #0696's setting.
5. **A dirty Project Editor still asks** Save / Discard / Cancel on a Sparkle quit. The flag only skips the "Quit Batty?" confirm step, never the editor question (unsaved edits are real data, per the issue).
6. **Ordinary quits are unchanged**, because the flag is only set by `willInstallUpdate`.
7. **Prod impact and `release/1.4`:** 1.4.x shows a redundant confirmation, not a failure. **Recommendation: don't cherry-pick to `release/1.4`.** 1.4.x has no headless hook, the alert's text is accurate there (terminals do close), a person can always answer it, and the change touches `UpdaterController`, which differs on `release/1.4` (no #0714 files), so it wouldn't apply cleanly. It ships in 1.5.0. The user decides (Open question 2).
8. **File › Restart (#0696):** a note for #0696, no code here. #0696 is not merged (`issue/0696`). Text for #0696's next round (the implementer appends it to `issues/0696.md` on `main` as a `## Notes` bullet, an ad-hoc edit): "`HostRestart.request()` should call `PreconfirmedQuit.shared.mark(.restart)` (add the `.restart` reason) right before `NSApp.terminate(nil)`, so Restart skips the 'Quit Batty?' alert the same way a Sparkle install does (#0718). Restart exists only with 'Keep terminals running' on, so the alert's 'terminals will close' warning is wrong there. The editor question still applies."

## Fix

- #0717's `SparkleAutoConfirmUpdaterDelegate` is now `UpdaterDelegate` (`Updater/UpdaterDelegate.swift`), used by both backends. `updater(_:willInstallUpdate:)` marks `.sparkleInstall`; `updater(_:didAbortWithError:)` clears it; the background-check refusal applies only with `refusesBackgroundChecks: true` (headless). - `AppStateStore.handleTerminateRequest` takes `preconfirmedQuit: PreconfirmedQuit = .shared`. A marked quit skips `confirm` (the "Quit Batty?" alert) but still asks a dirty Project Editor's Save / Discard / Cancel.

Sparkle's terminate request arrives as a Quit Apple Event (`_handleAEQuit`), the same as `osascript … to quit`, a logout, or Dock › Quit. The app gets no other sign that Sparkle sent it.

The #0715 harness works around this by writing `co.sstools.Batty.confirmQuit -bool NO` in the guest (`tools/vm-guest-sparkle.sh`, `setup` step, commit `4245d52d`). The next runs got past the quit: `20261122-010332-5463` and `20261122-010537-9057` reached the -67065 failure that #0716 fixes.

## Expected behavior (the plan decides)

1. **A quit that Sparkle starts for Install and Relaunch does not show the "Quit Batty?" alert.** The user already chose to install and relaunch, and the headless driver can't answer an alert. Options for the plan:
   - an `SPUUpdaterDelegate` on both backends (`updaterWillRelaunchApplication(_:)`, or `updater(_:willInstallUpdateOnQuit:immediateInstallationBlock:)`) that sets a one-shot "update quit" flag the terminate path reads;
   - a flag set by the user driver at `showReady(toInstallAndRelaunch:)` once it replies `.install`;
   - identifying the sender of the Quit Apple Event. That is less robust; say why if it is chosen.

   The flag must be cleared if the quit is cancelled or the install fails, so a later Cmd-Q still asks.
2. **When terminals are not kept** (1.4.x, `main`, or #0696's option off), decide whether the update still warns that N terminals will close. Recommended default: no second alert. The user has just clicked Install and Relaunch, and Sparkle's own dialog is the confirmation. If the plan keeps a warning, it belongs before the install (in the update flow, Prod/Beta standard driver only), never as a modal inside `applicationShouldTerminate` that the headless driver can't answer. Record the decision and the reason in the plan.
3. **When terminals are kept** (#0696's option on), the Sparkle quit never prompts. Its warning would be wrong.
4. **File › Restart** (#0696, `HostRestart.request()` → `NSApp.terminate(nil)`, only shown with the opt-in on) goes through the same `applicationShouldTerminate` and so shows the same alert today. Decide whether Restart skips it too; recommended: yes, since Restart only exists when terminals are kept. That part depends on #0696's code, which is only on `issue/0696`. If #0696 hasn't merged when this is planned, scope it as a note for #0696 rather than code here.
5. A dirty Project Editor still asks its Save / Discard / Cancel question on any quit, including a Sparkle one. Unsaved edits are real data. Whether that may hold a headless install is #0714's existing Gotcha and is out of scope here.
6. Ordinary quits (Cmd-Q, Dock › Quit, `osascript` quit, logout) behave exactly as today.

## Acceptance criteria

- A Sparkle-initiated install-and-relaunch quits without the "Quit Batty?" alert, with `confirmQuit` at its default (`true`), in the standard and headless backends.
- After a cancelled or failed install, Cmd-Q with open terminals still shows the alert (the flag doesn't leak).
- The decision for the terminals-not-kept case (Expected behavior 2) is recorded in the plan and implemented. If it changes what 1.4.x users see, note it in the changelog entry.
- Unit tests, without showing an `NSAlert` or starting an `SPUUpdater`: the terminate decision with the update flag set and unset, with `confirmQuit` true and false, and the flag being cleared on cancel. `handleTerminateRequest`'s injected `confirm` closure is the existing seam.
- **#0715 runner:** the `confirmQuit -bool NO` line and its comment are removed from `tools/vm-guest-sparkle.sh`. A runner run gets past `trigger` with the default setting, so A exits and B relaunches (the run may still FAIL later on #0716's -67065). Record the run id. If #0715 hasn't merged when this lands, note the dependency in #0715 instead, and remove the line once both are on `main`.
- Progressive disclosure: no new UI, Settings row or prompt.
