# 0718 — The "Quit Batty?" confirmation blocks Sparkle's Install and Relaunch

| | |
|---|---|
| **Status** | open |
| **Module** | App / Build |
| **Platform** | macOS |
| **First seen** | 2026-11-22 |
| **Target** | 1.5.0 |

## Description

When Sparkle installs an update and asks Batty to quit, Batty answers with its modal "Quit Batty? There are N open terminal(s)." alert (`QuitConfirmation.shouldQuitOrPrompt`, run from `applicationShouldTerminate`). Sparkle waits until someone answers. With the headless #0714 driver nobody can, so the update never installs. A real user who has just clicked **Install and Relaunch** in Sparkle's dialog is asked a second time whether to quit.

The VM run had "Keep terminals running when Batty quits" on (#0696), so the alert's warning was also wrong: those terminals would have been kept. On `main` and in shipped 1.4.x that option doesn't exist, terminals do close on an update, and the alert's text is accurate. The plan has to decide what a Sparkle-initiated quit should do in each case (see Expected behavior).

**Shipped versions show the alert too, by reading the code.** `release/1.4` has the same path: `applicationShouldTerminate` → `AppStateStore.handleTerminateRequest` → `QuitConfirmation.shouldQuitOrPrompt` → `NSAlert.runModal()`, gated only by `SettingsPreference.resolvedConfirmQuit`, whose default is `defaultConfirmQuit = true`. Prod's `UpdaterController` builds `SPUStandardUpdaterController(… updaterDelegate: nil …)`, so nothing tells the quit path that Sparkle asked for it. So a 1.4.x user with any terminal open who clicks Install and Relaunch should get "Quit Batty?". This was not reproduced on a Prod build: the evidence below is a Beta built from `issue/0696` + `main` + `issue/0715`. In Prod it is a redundant second confirmation, not data loss or a hang, because a person is there to click Quit. If they click Cancel, Sparkle's installer gets `applicationTerminated: false` and the update stays staged.

## Expected behavior (the plan decides)

1. **A quit that Sparkle starts for Install and Relaunch does not show the "Quit Batty?" alert.** The user already chose to install and relaunch, and the headless driver can't answer an alert. Options for the plan:
   - an `SPUUpdaterDelegate` on both backends (`updaterWillRelaunchApplication(_:)`, or `updater(_:willInstallUpdateOnQuit:immediateInstallationBlock:)`) that sets a one-shot "update quit" flag the terminate path reads;
   - a flag set by the user driver at `showReady(toInstallAndRelaunch:)` once it replies `.install`;
   - identifying the sender of the Quit Apple Event. That is less robust; say why if it is chosen.

   The flag must be cleared if the quit is cancelled or the install fails, so a later Cmd-Q still asks.
2. **When terminals are not kept** (1.4.x, `main`, or #0696's option off), decide whether the update still warns that N terminals will close. Recommended default: no second alert. The user has just clicked Install and Relaunch, and Sparkle's own dialog is the confirmation. If the plan keeps a warning, it belongs before the install (in the update flow, Prod/Beta standard driver only), never as a modal inside `applicationShouldTerminate` that the headless driver can't answer. Record the decision and the reason in the plan.
3. **When terminals are kept** (#0696's option on), the Sparkle quit never prompts. Its warning would be wrong.
4. **File › Restart** (#0696, `HostRestart.request()` → `NSApp.terminate(nil)`, only shown with the opt-in on) goes through the same `applicationShouldTerminate` and so shows the same alert today. Decide whether Restart skips it too; recommended: yes, since Restart only exists when terminals are kept. That part depends on #0696's code, which is only on `issue/0696`. If #0696 hasn't merged when this is planned, scope it as a note for #0696 rather than code here.
5. A dirty Project Editor still asks its Save / Discard / Cancel question on any quit, including a Sparkle one. Unsaved edits are real data. Whether that may hold a headless install is #0714's existing Gotcha and is out of scope here.
6. Ordinary quits (Cmd-Q, Dock › Quit, `osascript` quit, logout) behave exactly as today.

## Acceptance criteria

- A Sparkle-initiated install-and-relaunch quits without the "Quit Batty?" alert, with `confirmQuit` at its default (`true`), in the standard and headless backends.
- After a cancelled or failed install, Cmd-Q with open terminals still shows the alert (the flag doesn't leak).
- The decision for the terminals-not-kept case (Expected behavior 2) is recorded in the plan and implemented. If it changes what 1.4.x users see, note it in the changelog entry.
- Unit tests, without showing an `NSAlert` or starting an `SPUUpdater`: the terminate decision with the update flag set and unset, with `confirmQuit` true and false, and the flag being cleared on cancel. `handleTerminateRequest`'s injected `confirm` closure is the existing seam.
- **#0715 runner:** the `confirmQuit -bool NO` line and its comment are removed from `tools/vm-guest-sparkle.sh`. A runner run gets past `trigger` with the default setting, so A exits and B relaunches (the run may still FAIL later on #0716's -67065). Record the run id. If #0715 hasn't merged when this lands, note the dependency in #0715 instead, and remove the line once both are on `main`.
- Progressive disclosure: no new UI, Settings row or prompt.

## Things to verify

- In Sparkle 2.9.1's headers, which delegate callbacks run before the installer's terminate request in both the relaunch and the install-on-quit paths. Also which ones the standard controller forwards when it's built with a delegate (`SPUStandardUpdaterController(startingUpdater:updaterDelegate:userDriverDelegate:)`).
- In onquit mode, the user (or the harness's `osascript … quit`) starts the quit, not Sparkle. That quit is an ordinary quit and may legitimately ask. Check what the #0715 runner's onquit `trigger` step does once the guest no longer turns `confirmQuit` off. It may need to answer or bypass the alert, as a harness step and not an app change.
- Whether the shipped 1.4.x standard driver really shows the alert. Check by reading `SPUStandardUserDriver`'s behaviour after `applicationTerminated: false`, or by a manual check on a Prod-signed build in the VM, not on the host. State which in the plan.
- `windowNeedsConfirmClose` (window close) is a separate path and is not affected.
- Grep every factual claim in new comments (for example, which Sparkle callback fires first).
