# 0715 — No automated test shows whether a Sparkle update keeps every Session and its running processes

## Description

The user's goal for #0696: **a Sparkle update must relaunch the app and restore every Session with its running processes.** Nothing tests that end to end today, and it is known to fail (#0696 Findings, "Restart quit without relaunching: sudden termination", Fix 2). Testing it by hand needs two signed builds, a feed, a signing key and an install, and the result is easy to misread.

Add a VM runner, **`tools/run-sparkle-update-vm.sh`**, that builds an older Beta package (A) and a newer one (B) on the host, serves a test appcast inside a disposable Tart VM, installs A, sets up Sessions with running processes through the `batty-beta` CLI, has Sparkle update to B, and checks that every Session, Pane and Tab came back attached to the same live processes.

**Expected first result: `CHECK SPARKLE: FAILED` at the stale-host rejection.** That baseline is the point of this issue. #0716 is the fix, and this runner passing is #0716's done criterion.

## Background

- **Why it fails today** (#0696 Findings, Fix 2). After Sparkle replaces the bundle, the new app's outgoing XPC check (`XPCHostChannelOpener` → `OutgoingCodeSigningEnforcement.apply` → `setCodeSigningRequirement`) rejects the old, still-running BattyHost with -67065 `errSecCSNoSuchCode`. macOS validates a running process against the file at its path, and that file has changed. The app logs `terminal helper connection: unavailable` and `restore: helper unavailable; 0 restored tabs start fresh`, falls back to in-process PTYs, and the old host's terminals are lost.
- **Signing matters for the reproduction.** `OutgoingCodeSigningEnforcement` skips the requirement when the app has no team identifier (ad-hoc or unsigned build). An unsigned `./build.sh package` therefore would *not* reproduce the failure; it would pass for the wrong reason. The packages must carry a team signature.
- **Beta has no feed.** `Configuration/Beta.xcconfig` blanks `SU_FEED_URL` and `SU_PUBLIC_ED_KEY`, and `UpdaterController` doesn't start Sparkle without a feed URL. `Configuration/Info.plist` takes both from those build settings.
- **Build numbers.** `scripts/build-beta.sh` stamps `CFBundleVersion` with the UTC minute (`release_build_number`, #0713). Sparkle compares `CFBundleVersion`, so B must be strictly greater than A. Two packages built in the same minute would tie.
- **`appcast-item.sh`** signs with `sign_update --account Batty` (the Keychain key) and hardcodes the enclosure URL to `batty.sstools.co`.
- **The VM.** `tools/run-ui-tests-vm.sh` and `docs/ui-testing-vm.md` show how a run takes a `tart-lease` slot, requests memory through the memory-signal protocol, clones `tart-golden require --xcode 27.0` into `batty-uitest-<run-id>`, boots headless and muted with a read-only share, collects results and deletes the clone on every exit path. Guest builds there are ad-hoc (the guest has no certificates), which is why this runner builds on the host instead. `tools/vm-guest-broker.sh` bootstraps the broker so `batty` verbs work in a fresh guest (#0419).

## What the runner does

**On the host:**
1. Resolve the commit to test (see "Which commit" below) and export it, as the UI runner does, so uncommitted edits are never tested.
2. Build two Beta packages from that commit, A and then B, with:
   - `BATTY_BETA_FEED_URL` (new, opt-in): the test feed URL inside the VM, for example `http://127.0.0.1:<port>/appcast.xml`.
   - `BATTY_BETA_ED_PUBLIC_KEY` (new, opt-in): the public half of a throwaway Ed25519 key generated per run.
   - A strictly greater build number for B than A. The plan picks how: a third opt-in variable (for example `BATTY_BETA_BUILD_NUMBER`) or waiting for the next minute. An override is preferred; waiting is fragile.
   - **B's BattyHost binary must differ from A's** (different cdhash), or the stale-host check may pass by accident because the bytes on disk didn't change. The field failure was between different builds. The plan makes sure of this (for example, stamp the build number into the host binary, or an `LC_UUID`-affecting constant), and the runner asserts the two cdhashes differ before booting the VM.
   - With both variables unset, `build-beta.sh` and every Beta package behave exactly as today (blank feed, no key, no Sparkle).
3. Generate the throwaway key pair into the run's results folder. **The private key comes from a file and never touches the Keychain**: signing uses `sign_update --ed-key-file <file>`. Sparkle's `generate_keys` stores what it generates in the Keychain, so the key is generated another way (for example CryptoKit's `Curve25519.Signing.PrivateKey` in a small script, or `openssl genpkey -algorithm ed25519`), written in the format `--ed-key-file` reads; the plan checks that format against the Sparkle version in `BattyKit/Package.resolved`. No `--account`, no Keychain item. The key file stays in the gitignored results folder or a temp dir that the runner removes.
4. Archive B (DMG or zip, the plan picks what Sparkle installs most simply) and generate `appcast.xml` through `scripts/appcast-item.sh` with a new key-file option, plus an enclosure URL option so the item points at the VM's local server instead of `batty.sstools.co`. Without the new options the script behaves exactly as today.
5. Lease, memory, clone and boot exactly as `tools/run-ui-tests-vm.sh` does (shared helpers if the plan factors them out, without changing the UI runner's behavior).

**In the guest:**
6. Serve the feed and B's archive locally: `python3 -m http.server` bound to loopback inside the VM (photon if the golden has it). If Sparkle or App Transport Security refuses plain HTTP to loopback, the plan picks the alternative (HTTPS with a certificate trusted only in the guest, or an ATS exception only in test packages) and records it.
7. Install A into `/Applications`. Disable Gatekeeper (`spctl --master-disable` or equivalent) **inside the disposable VM only**, documented as such. A notarized run is a separate, manual step that needs the user's approval each time (AGENTS.md).
8. Opt in to "Keep terminals running" without the Settings UI: write `co.sstools.Batty.keepTerminalsRunningWhenBattyQuits` and register the BattyHost agent the way the Settings toggle does. The plan finds a guest-only way (a `defaults write` plus `launchctl bootstrap`, as `tools/vm-guest-broker.sh` does for the broker, or a guest-only script). The shipped app keeps its opt-in rule (AGENTS.md "progressive disclosure").
9. Launch A with the #0714 hook set, then set up through `batty-beta` (the plan confirms each verb on the commit under test):
   - several Sessions, one opened from a Project (`batty-beta project open`), with a Session background and a Pane with lowered terminal opacity;
   - a Tab running a counter loop that appends an increasing number to a file once a second;
   - splits, and more than one Tab in a Pane.
10. Record a baseline: Session, Pane, Tab and Terminal Session ids; each shell's pid; the BattyHost pid and the path and cdhash of its executable; the Project link; the last lines of scrollback per Tab; the counter's last value.
11. Trigger the update through the #0714 hook (install and relaunch). Wait on events with an upper bound, not fixed sleeps: the old app's pid exiting, the new app's pid appearing, `restore:` log lines.
12. Verify:
    - the running app's `CFBundleVersion` is B's;
    - BattyHost runs B's binary (its executable's cdhash matches B's, and it answers the new app);
    - every Session, Pane and Tab is restored in place, the Project link included (Project symbol, Save as Project shows Update), and the backgrounds and opacity are as before;
    - the same shell pids are alive and are still children of BattyHost;
    - the counter file has no gap and keeps growing after the update;
    - the `restore:` log lines show attach for every Terminal Session and no fallback (no `-67065`, no `helper unavailable`, no in-process PTYs);
    - no orphan or zombie processes: no shells outside BattyHost's children, no `Z` rows, no second BattyHost.
13. Repeat for **install on quit**: from a fresh A install, stage B through the hook's on-quit mode, quit A (Cmd-Q path through `batty-beta` or `osascript` *inside the guest only*), wait for the install to finish, reopen the app, and run the same checks.

**Output:**
- Logs, the baseline and after-update snapshots, `log show` extracts for `restore:`, `sparkle-auto:`, BattyHost and Sparkle, and crash reports, in the gitignored `build/sparkle-tests/<run-id>/`.
- A final line on every exit path: `CHECK SPARKLE: PASSED|FAILED|ERROR [(detail)]`, exit code 0, 1 or 2 with the same meaning as `./build.sh` (FAILED is a check that ran and failed; ERROR is a run that couldn't get that far). The FAILED detail names the first failing check, for example `CHECK SPARKLE: FAILED (helper unavailable after update: -67065)`.
- The VM clone is deleted afterwards, on every exit path, as in the UI runner.

1. #0696 doesn't ship until a Sparkle update keeps every Session. 1.4.3 won't carry it.

## Decisions for the plan

- **Signing.** Developer ID signing is allowed only through `./build.sh package --sign`, and never with `--notarize` unless the user approves. An unsigned package skips the XPC requirement and can't reproduce the failure (see Background). Recommended: `./build.sh package --sign` (Manual signing, committed profile, never contacts Apple). If the plan wants a different team signature, it must not use Automatic Developer ID signing or any portal action (AGENTS.md "Developer ID certificate").
- How the packages reach the guest (the read-only share, as the UI runner exports its tar files).
- How the throwaway key is generated without the Keychain, and where it lives during the run.
- Whether the runner shares code with `tools/run-ui-tests-vm.sh` or copies the lease/memory/clone steps. Sharing must not change the UI runner's behavior.

## What to verify

- The runner never builds or runs anything Batty on the host except `./build.sh package` and Sparkle's command-line tools. No UI scripting on the host (AGENTS.md); any `osascript` runs only inside the guest.
- Only one VM at a time: the runner waits for a slot like the UI runner and never runs alongside it.
- The FAILED baseline is a real reproduction: the results show the old host's pid still running after the update, the new app's `-67065`, and the Tabs starting fresh. A PASS on the first run means the reproduction is wrong (for example an unsigned build or identical host binaries), not that the bug is gone.
- The Beta packages with the test feed are never copied anywhere but the VM and the results folder. Nothing goes to `website/` or `dist/`.
