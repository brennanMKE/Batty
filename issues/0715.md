## Description

The user's goal for #0696: **a Sparkle update must relaunch the app and restore every Session with its running processes.** Nothing tests that end to end today, and it is known to fail (#0696 Findings, "Restart quit without relaunching: sudden termination", Fix 2). Testing it by hand needs two signed builds, a feed, a signing key and an install, and the result is easy to misread.

Add a VM runner, **`tools/run-sparkle-update-vm.sh`**, that builds an older Beta package (A) and a newer one (B) on the host, serves a test appcast inside a disposable Tart VM, installs A, sets up Sessions with running processes through the `batty-beta` CLI, has Sparkle update to B, and checks that every Session, Pane and Tab came back attached to the same live processes.

**Expected first result: `CHECK SPARKLE: FAILED` at the stale-host rejection.** That baseline is the point of this issue. #0716 is the fix, and this runner passing is #0716's done criterion.

## Root cause

Feature work. The starting state: nothing tested a Sparkle update end to end. Beta packages had no feed or key, `appcast-item.sh` could sign only with the Keychain key and only for `batty.sstools.co`, and the UI runner's Tart lifecycle was inline in `tools/run-ui-tests-vm.sh`. The failure the runner must reproduce, the new app rejecting the still-running old BattyHost with -67065, came from #0696's Findings. Run `20261122-010537-9057` confirmed it in both modes (see Verification, "VM runs").

## Fix

Followed the plan. User approvals recorded (2026-11-21): the `build-beta.sh` opt-in variables, the `appcast-item.sh` test options, and the runner's standing authorization. The authorization is in AGENTS.md "UI test automation". Orchestrator decisions: two signed builds per run are accepted, an HTTP feed refusal stops the run as an ERROR with no HTTPS fallback, and a stale broker gets one restart with a warning.

- `scripts/build-beta.sh`: `BATTY_BETA_BUILD_NUMBER` (digits only, else exit 2). `BATTY_BETA_FEED_URL` and `BATTY_BETA_ED_PUBLIC_KEY` must be set together (else exit 2); they are appended as `SU_FEED_URL`/`SU_PUBLIC_ED_KEY` on both build paths, refused with `--notarize` (exit 2), and checked in the built Info.plist by the new `check_feed`. When they're unset, the arrays are empty, so the xcodebuild argv is unchanged.
- `scripts/appcast-item.sh`: `--ed-key-file`, `--enclosure-url` (drops `releaseNotesLink`, prints a test-item note) and `--sign-update`. With no options its behaviour is unchanged.
- `tools/vm-lib.zsh`: the UI runner's lifecycle blocks, moved with their comments and renamed `vm_*`. `run-ui-tests-vm.sh` now calls them. Its messages, id prefix, exit codes and cleanup order are unchanged.
- The guest turns off `co.sstools.Batty.confirmQuit` and serves an empty appcast until the trigger (see Findings 1 and 2). It screenshots and `sample`s an app that won't quit.
- New: `tools/run-sparkle-update-vm.sh`, `tools/vm-guest-sparkle.sh`, `tools/sparkle-test-key.swift`, `tools/sparkle-update-check.py`, and two self-tests.

Deviations from the plan:
- Lifecycle steps that used to `fail` inline (`vm_wait_for_free_slot`, `vm_boot`) now set `VM_LIB_ERROR` and return non-zero; the UI runner `fail`s with that same message. One small change: a `kern.hv_vmm_present` read that itself fails used to be a `set -e` abort (`ERROR (aborted, exit N)`). It is now the named "hv_vmm_present" ERROR.
- The Project background option on `issue/0696` is `--background-file <png>`, not `--background-image`. The latter takes a Background Sets title.
- `shell-pids` and `orphans` check that the current BattyHost is an ancestor, not the direct parent. Batty may wrap a `-c` command in a login shell.
- `counter-final.txt` is also written into `after/`, where the checker reads it. The checker takes `--crashes` and `--out`.
- Before the `baseline` and `after` snapshots, the guest waits (up to 60 s) until `terminal-layout.json` has as many Tabs as `list --json`. The app writes the layout on a timer, so an early copy can be stale.
- Topology is compared on ids, `direction` and nesting only, across the whole `terminal-layout.json`. It uses that file, not `list --json`, because that file's schema is known.

### Findings from the runs (app-level, filed as #0717, #0718 and #0719)

1. **The headless updater checks at launch** (filed as #0717). With `BATTY_BETA_SPARKLE_AUTO` set, Sparkle's own scheduled first check ran right after `armed` and installed B before any trigger. This is contrary to #0714's "checks only when told to". The harness works around it: the feed holds no item until `trigger` swaps the real appcast in.
2. **The "Quit Batty?" confirmation blocks a Sparkle install-and-relaunch** (filed as #0718). It does so even with "keep terminals running" on. Sparkle's terminate request sits behind a modal alert that says N terminals are open, although they would be kept. The guest turns `co.sstools.Batty.confirmQuit` off. With the standard driver a user would see this alert after clicking Install.
3. **The broker needs a restart after an update** (filed as #0719). `batty ping` failed after the new app launched in both modes, until `launchctl kickstart -k` of the broker (plan open question 3). This affects users' CLI after an update.

### Premises checked

- **`build-beta.sh` builds the tree it lives in** (`REPO` is the script's own parent folder). So each package is built by running `./build.sh package --sign` inside its own exported tree. That is the sanctioned Developer ID site (AGENTS.md), and it never uses the live working copy. The tree needs `../SlidingTabs` next to it, because `BattyKit/Package.swift` uses `.package(path: "../../SlidingTabs")`. The profiles it needs are committed (`Configuration/Profiles/`). `Active.xcconfig` is written and restored by the script.
- **BattyHost** (only on `issue/0696`) is built by the "Embed Host" phase (`swift build --product BattyHost`, Beta only). With `CODE_SIGNING_ALLOWED=YES` and an identity, it is signed with the build's own identity (`--timestamp=none` outside Archive). A `--sign` package therefore carries a team-signed host. An unsigned host would skip `OutgoingCodeSigningEnforcement` and pass for the wrong reason, so the runner checks the team.
- **A and B get different host cdhashes because they are built in different folders.** A Debug `swift build` binary records absolute object-file paths and their mtimes in its debug map (`N_OSO` stabs), so two clean trees at different paths give different bytes and so different cdhashes. Nothing on `main` needs to change for this. The runner **asserts** that the cdhashes differ before it boots a VM (ERROR if they don't). Fallback if that assertion ever fires: a commit on `issue/0696` adds `-Xlinker -sectcreate -Xlinker __TEXT -Xlinker __batty_build -Xlinker <file holding $CURRENT_PROJECT_VERSION>` to "Embed Host". It isn't planned now because it can only land on `issue/0696`.
- **Feed and key.** `Configuration/Info.plist` takes `SUFeedURL` and `SUPublicEDKey` from `$(SU_FEED_URL)` and `$(SU_PUBLIC_ED_KEY)`, and `Beta.xcconfig` blanks both. Settings passed on the xcodebuild command line override the xcconfig, so `build-beta.sh` only has to append them. `SUEnableAutomaticChecks` is `true`, so there is no permission prompt.
- **`sign_update` 2.9.1** has `-f/--ed-key-file <file>` (checked with `--help`). `generate_keys` always uses the Keychain, so it is not used.
- **`appcast-item.sh`** mounts a DMG to read the versions, signs with `--account Batty`, and hardcodes the `batty.sstools.co` enclosure URL and release-notes link. A **DMG** for B keeps all of that logic. Sparkle installs from a DMG.
- **The opt-in.** On `issue/0696`, `SettingsPreference.ptyHostEnabled` is `flags.ptyHost && defaults.bool(forKey: "co.sstools.Batty.keepTerminalsRunningWhenBattyQuits")`. The app only connects at launch. The agent is registered (`SMAppService`) only from the Settings toggle (`HostSettingsModel.setEnabled`). The guest shortcut is therefore `defaults write` plus a `launchctl bootstrap` of a plist equivalent to the embedded `Contents/Library/LaunchAgents/co.sstools.Batty.beta.host.plist` (same Label and MachServices key, ProcessType Interactive, AbandonProcessGroup, and an absolute `Program` in place of `BundleProgram`). This is the same approach `tools/vm-guest-broker.sh` takes for the broker. The shipped app is unchanged.
- **The CLI** (`issue/0696`): `new <dir> --json`, `project create` (`--name --root --symbol --background-image --opacity --terminal-opacity --json`), `project open <name> --json`, `pane split [--vertical] --pane <id> -c <cmd> --json`, `tab new --pane <id> -c <cmd> --json`, `list --json` and `ping`. **Gaps:** no verb reads scrollback, no verb sets a per-Pane opacity, and the topology JSON has no Project link or backgrounds. The runner reads the Project link, backgrounds and terminal opacity from `~/Library/Application Support/Batty Beta/terminal-layout.json` (`HostLayoutFile`), which carries them since the #0696 round "Restore keeps the Project link". It takes screenshots in place of scrollback. The per-Pane opacity override stays covered by `HostLayoutProjectRestoreTests/opacityOnlyOverridesSurviveARestore` and the user checklist.
- **Restore logs** (`HostRestore.swift`): `restore: helper unavailable; N restored tabs start fresh` is `.notice`, and `restore: tabs=N attach=N exited=N fresh=N` is **`.info`**. Info lines aren't kept in the log store by default, so the guest captures a live `log stream --level info`, not `log show`. BattyHost logs under `process == "BattyHost"`.
- **The #0714 contract** (committed in `issue/0714`'s plan, `bbcbdd40`) is used verbatim. Variable `BATTY_BETA_SPARKLE_AUTO=relaunch|onquit`, set only with `open --env` on a not-running app. At launch the app logs `sparkle-auto: armed mode=…`. The check starts when the distributed notification `co.sstools.Batty.beta.sparkle-auto.check` is posted with the plan's JXA one-liner. The lines are `installing and relaunching`, `staged for install on quit`, `error: …`, `start failed: …`, `check ignored: session in progress` and `ignored: …`, in category `SparkleAutoConfirm`, subsystem `co.sstools.Batty.beta`. No Project Editor is ever opened, so a dirty one can't block the quit. **If the #0714 implementation renames anything, this plan and the runner must change to match.** The runner keeps every name in one block of constants.

### Decisions

1. **What is tested.** `--ref <commit-ish>` (default `HEAD` of the runner's checkout) is resolved with `git rev-parse --verify "<ref>^{commit}"`. A repeatable `--merge <ref>` builds a **throwaway merge commit** with no branch and no working-tree change: `git merge-tree --write-tree <acc> <ref>`, then `git commit-tree <tree> -p <acc> -p <ref> -m "sparkle-vm throwaway merge"`, folded left over every `--merge`. A conflict is `ERROR (merge conflict: <ref>)`. The resulting sha and its parents go into `run.txt`. This tests `issue/0696` with #0714 and #0715 before either is merged, with no stacked branch:
   - **#0715 acceptance run** (implementer and reviewer): `tools/run-sparkle-update-vm.sh --ref issue/0696 --merge issue/0714 --merge issue/0715`. If #0714 has already landed on `main`, use `--merge main` instead of `--merge issue/0714`.
   - **After #0714 and #0715 land:** the orchestrator merges `main` into `issue/0696`, as for #0713, and runs `tools/run-sparkle-update-vm.sh --ref issue/0696` from the `main` checkout. This is #0716's loop. After #0696 merges, use `--ref main` or the default.
   - **Host tooling** (the runner, `appcast-item.sh`, the key tool, the checker and the guest scripts) always comes from the runner's own checkout. **The app** comes from the ref's tree, built with that tree's own `./build.sh package --sign`.
   - **Fast preflight on the ref's tree, before any build.** ERROR unless `scripts/build-beta.sh` mentions `BATTY_BETA_FEED_URL` ("ref predates #0715"), the tree contains `BATTY_BETA_SPARKLE_AUTO` (`git grep -q` on the commit: "ref lacks the #0714 hook"), and the tree contains `BattyKit/Sources/BattyHost` ("ref has no BattyHost (#0696)").
2. **Host build.**
   - Work trees are persistent and gitignored: `build/sparkle-tests/work/A/{Batty,SlidingTabs}` and `.../B/...`. Each run wipes every source file but keeps `Batty/beta-build/` (its DerivedData), so a repeat run against the same commit rebuilds incrementally. `--clean` wipes them completely. A and B are always at different paths, which is the cdhash difference.
   - Both trees are extracted on the host with `git archive <sha> | tar -x`. The virtio-fs symlink limit applies only to the share. SlidingTabs is `git archive HEAD` of `../SlidingTabs`, as the UI runner does.
   - Build numbers: `A = release_build_number` (sourced from `scripts/build-number.sh`) and `B = A + 1`.
   - Feed URL: `http://127.0.0.1:47912/appcast.xml`. Port 47912 is next to the UI relay's 47911.
   - Each build runs as `env BATTY_BETA_FEED_URL=… BATTY_BETA_ED_PUBLIC_KEY=… BATTY_BETA_BUILD_NUMBER=… ./build.sh package --sign`. ## Background

- **Why it fails today** (#0696 Findings, Fix 2). After Sparkle replaces the bundle, the new app's outgoing XPC check (`XPCHostChannelOpener` → `OutgoingCodeSigningEnforcement.apply` → `setCodeSigningRequirement`) rejects the old, still-running BattyHost with -67065 `errSecCSNoSuchCode`. macOS validates a running process against the file at its path, and that file has changed. The app logs `terminal helper connection: unavailable` and `restore: helper unavailable; 0 restored tabs start fresh`, falls back to in-process PTYs, and the old host's terminals are lost.
- **Signing matters for the reproduction.** `OutgoingCodeSigningEnforcement` skips the requirement when the app has no team identifier (ad-hoc or unsigned build). An unsigned `./build.sh package` therefore would *not* reproduce the failure; it would pass for the wrong reason. The packages must carry a team signature.
- **Beta has no feed.** `Configuration/Beta.xcconfig` blanks `SU_FEED_URL` and `SU_PUBLIC_ED_KEY`, and `UpdaterController` doesn't start Sparkle without a feed URL. `Configuration/Info.plist` takes both from those build settings.
- **Build numbers.** `scripts/build-beta.sh` stamps `CFBundleVersion` with the UTC minute (`release_build_number`, #0713). Sparkle compares `CFBundleVersion`, so B must be strictly greater than A. Two packages built in the same minute would tie.
- **`appcast-item.sh`** signs with `sign_update --account Batty` (the Keychain key) and hardcodes the enclosure URL to `batty.sstools.co`.
- **The VM.** `tools/run-ui-tests-vm.sh` and `docs/ui-testing-vm.md` show how a run takes a `tart-lease` slot, requests memory through the memory-signal protocol, clones `tart-golden require --xcode 27.0` into `batty-uitest-<run-id>`, boots headless and muted with a read-only share, collects results and deletes the clone on every exit path. Guest builds there are ad-hoc (the guest has no certificates), which is why this runner builds on the host instead. `tools/vm-guest-broker.sh` bootstraps the broker so `batty` verbs work in a fresh guest (#0419).

## What the runner does

**On the host:**
1. Resolve the commit to test (see "Which commit" below) and export it, as the UI runner does, so uncommitted edits are never tested.
2. Build two Beta packages from that commit, A and then B, with:
   - `BATTY_BETA_FEED_URL` (new, opt-in): the test feed URL inside the VM, for example `http://127.0.0.1:<port>/appcast.xml`.
   - `BATTY_BETA_ED_PUBLIC_KEY` (new, opt-in): the public half of a throwaway Ed25519 key generated per run.
   - A strictly greater build number for B than A. The plan picks how: a third opt-in variable (for example `BATTY_BETA_BUILD_NUMBER`) or waiting for the next minute. An override is preferred; waiting is fragile.
   - **B's BattyHost binary must differ from A's** (different cdhash), or the stale-host check may pass by accident because the bytes on disk didn't change. The field failure was between different builds. The plan makes sure of this (for example, stamp the build number into the host binary, or an `LC_UUID`-affecting constant), and the runner asserts the two cdhashes differ before booting the VM.
   - With both variables unset, `build-beta.sh` and every Beta package behave exactly as today (blank feed, no key, no Sparkle).
3. Generate the throwaway key pair into the run's results folder. **The private key comes from a file and never touches the Keychain**: signing uses `sign_update --ed-key-file <file>`. Sparkle's `generate_keys` stores what it generates in the Keychain, so the key is generated another way (for example CryptoKit's `Curve25519.Signing.PrivateKey` in a small script, or `openssl genpkey -algorithm ed25519`), written in the format `--ed-key-file` reads; the plan checks that format against the Sparkle version in `BattyKit/Package.resolved`. No `--account`, no Keychain item. The key file stays in the gitignored results folder or a temp dir that the runner removes.
4. Archive B (DMG or zip, the plan picks what Sparkle installs most simply) and generate `appcast.xml` through `scripts/appcast-item.sh` with a new key-file option, plus an enclosure URL option so the item points at the VM's local server instead of `batty.sstools.co`. Without the new options the script behaves exactly as today.
5. Lease, memory, clone and boot exactly as `tools/run-ui-tests-vm.sh` does (shared helpers if the plan factors them out, without changing the UI runner's behavior).

**In the guest:**
6. Serve the feed and B's archive locally: `python3 -m http.server` bound to loopback inside the VM (photon if the golden has it). If Sparkle or App Transport Security refuses plain HTTP to loopback, the plan picks the alternative (HTTPS with a certificate trusted only in the guest, or an ATS exception only in test packages) and records it.
7. Install A into `/Applications`. Disable Gatekeeper (`spctl --master-disable` or equivalent) **inside the disposable VM only**, documented as such. A notarized run is a separate, manual step that needs the user's approval each time (AGENTS.md).
8. Opt in to "Keep terminals running" without the Settings UI: write `co.sstools.Batty.keepTerminalsRunningWhenBattyQuits` and register the BattyHost agent the way the Settings toggle does. The plan finds a guest-only way (a `defaults write` plus `launchctl bootstrap`, as `tools/vm-guest-broker.sh` does for the broker, or a guest-only script). The shipped app keeps its opt-in rule (AGENTS.md "progressive disclosure").
9. Launch A with the #0714 hook set, then set up through `batty-beta` (the plan confirms each verb on the commit under test):
   - several Sessions, one opened from a Project (`batty-beta project open`), with a Session background and a Pane with lowered terminal opacity;
   - a Tab running a counter loop that appends an increasing number to a file once a second;
   - splits, and more than one Tab in a Pane.
10. Record a baseline: Session, Pane, Tab and Terminal Session ids; each shell's pid; the BattyHost pid and the path and cdhash of its executable; the Project link; the last lines of scrollback per Tab; the counter's last value.
11. Trigger the update through the #0714 hook (install and relaunch). Wait on events with an upper bound, not fixed sleeps: the old app's pid exiting, the new app's pid appearing, `restore:` log lines.
12. Verify:
    - the running app's `CFBundleVersion` is B's;
    - BattyHost runs B's binary (its executable's cdhash matches B's, and it answers the new app);
    - every Session, Pane and Tab is restored in place, the Project link included (Project symbol, Save as Project shows Update), and the backgrounds and opacity are as before;
    - the same shell pids are alive and are still children of BattyHost;
    - the counter file has no gap and keeps growing after the update;
    - the `restore:` log lines show attach for every Terminal Session and no fallback (no `-67065`, no `helper unavailable`, no in-process PTYs);
    - no orphan or zombie processes: no shells outside BattyHost's children, no `Z` rows, no second BattyHost.
13. Repeat for **install on quit**: from a fresh A install, stage B through the hook's on-quit mode, quit A (Cmd-Q path through `batty-beta` or `osascript` *inside the guest only*), wait for the install to finish, reopen the app, and run the same checks.

**Output:**
- Logs, the baseline and after-update snapshots, `log show` extracts for `restore:`, `sparkle-auto:`, BattyHost and Sparkle, and crash reports, in the gitignored `build/sparkle-tests/<run-id>/`.
- A final line on every exit path: `CHECK SPARKLE: PASSED|FAILED|ERROR [(detail)]`, exit code 0, 1 or 2 with the same meaning as `./build.sh` (FAILED is a check that ran and failed; ERROR is a run that couldn't get that far). The FAILED detail names the first failing check, for example `CHECK SPARKLE: FAILED (helper unavailable after update: -67065)`.
- The VM clone is deleted afterwards, on every exit path, as in the UI runner.

## Decisions for the plan

- **Signing.** Developer ID signing is allowed only through `./build.sh package --sign`, and never with `--notarize` unless the user approves. An unsigned package skips the XPC requirement and can't reproduce the failure (see Background). Recommended: `./build.sh package --sign` (Manual signing, committed profile, never contacts Apple). If the plan wants a different team signature, it must not use Automatic Developer ID signing or any portal action (AGENTS.md "Developer ID certificate").
- How the packages reach the guest (the read-only share, as the UI runner exports its tar files).
- How the throwaway key is generated without the Keychain, and where it lives during the run.
- Whether the runner shares code with `tools/run-ui-tests-vm.sh` or copies the lease/memory/clone steps. Sharing must not change the UI runner's behavior.

## What to verify

- The runner never builds or runs anything Batty on the host except `./build.sh package` and Sparkle's command-line tools. No UI scripting on the host (AGENTS.md); any `osascript` runs only inside the guest.
- Only one VM at a time: the runner waits for a slot like the UI runner and never runs alongside it.
- The FAILED baseline is a real reproduction: the results show the old host's pid still running after the update, the new app's `-67065`, and the Tabs starting fresh. A PASS on the first run means the reproduction is wrong (for example an unsigned build or identical host binaries), not that the bug is gone.
- The Beta packages with the test feed are never copied anywhere but the VM and the results folder. Nothing goes to `website/` or `dist/`.
