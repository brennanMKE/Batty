## Description

Wire Sparkle for auto-updates so users on direct downloads can stay current without manual reinstalls (PRD §11, Architecture dependencies).

**Acceptance criteria:**
- Sparkle SPM dependency added.
- `SUFeedURL` configured in Info.plist pointing at a `appcast.xml` we host.
- "Check for Updates…" menu item under the Batty menu.
- A signed appcast item served from our release flow can prompt users to update; the update applies on relaunch.
- EdDSA signing keys generated and the public key embedded in Info.plist; private key stored outside the repo.

## Notes

- Sparkle requires a hosted endpoint for the appcast. Decide on a hosting story (GitHub Pages? S3?) — note the chosen approach in the resolved Notes.
- Auto-update prompts should respect "Do not show again until next version" — Sparkle handles this by default.

## Root cause

Sparkle requires three pieces: the SPM dependency in the project, a `SUFeedURL` pointing at a hosted appcast, and an EdDSA public key embedded in Info.plist. The first is code; the latter two need hosting and a one-time key-generation step that's the user's call.

## Fix

Ship the code half + scaffolding so flipping the user-side switches activates Sparkle without further code changes.

- **`BattyKit/Package.swift`** adds `sparkle-project/Sparkle@2.6.0` as a remote SPM dependency. Linked into the BattyKit target so the Batty app gets it transitively.
- **`UpdaterController` (new, BattyKit)** wraps `SPUStandardUpdaterController`. Has an `isConfigured` property that checks for `SUFeedURL` in `Info.plist` (non-empty string) — early-returns from `checkForUpdates()` and logs when not configured, so the menu item is a clean no-op until the user wires the feed URL.
- **`BattyCommands`** replaces the `.appInfo` CommandGroup with `About Batty` + a Divider + "Check for Updates…" that calls `UpdaterController.shared.checkForUpdates()`. The menu item is `.disabled` when `isConfigured` is false.
- **`scripts/SPARKLE.md`** is the user-side checklist: pick an appcast hosting URL (GitHub Pages / S3 / self-hosted), generate the EdDSA key pair via Sparkle's `generate_keys` tool, add `SUFeedURL` and `SUPublicEDKey` to the Batty Info.plist. Plus per-release: `sign_update` to compute the EdDSA signature for each DMG, then append an `<item>` to `appcast.xml`.

## Gotchas

- **The menu item is disabled until `SUFeedURL` is populated in the running app's `Info.plist`.** With `GENERATE_INFOPLIST_FILE = YES` (the current Batty target config), arbitrary plist keys need either a custom `Info.plist` file (set `INFOPLIST_FILE = Batty/Info.plist` and turn off `GENERATE_INFOPLIST_FILE`) or `INFOPLIST_KEY_*` build settings if your Xcode version honors them for non-canonical keys. `scripts/SPARKLE.md` documents both options.
- **EdDSA private key never enters the repo.** `generate_keys` stores it in the macOS keychain under `https://sparkle-project.org`. Loss of the key means the user can no longer sign updates that existing clients will accept — keep a backup outside the keychain (e.g., an encrypted note) if the developer machine is replaceable.
- **The appcast URL is on you to host.** The doc nudges toward GitHub Pages because it's free and fits the project's existing GitHub presence, but S3 / self-hosted works just as well. The DMG download URL referenced from `<enclosure>` doesn't have to be the same host.
- **No `INFOPLIST_KEY_SUEnableAutomaticChecks` shipped here.** Sparkle defaults are conservative (manual checks until the user opts in); set it once Info.plist is wired up.
- **`SPUStandardUpdaterController(startingUpdater: true, ...)` is constructed at `UpdaterController.shared` access time.** That happens at the first menu interaction (or earlier if anything else references the singleton). With no `SUFeedURL`, Sparkle initializes but never polls.
- **Per-release `sign_update` invocation** lives in `scripts/SPARKLE.md` rather than being baked into `scripts/release.sh`. Keeping it manual avoids surprising the user with a Sparkle signature attempt when Sparkle isn't even configured yet. Once Sparkle is live, fold the call into the release pipeline.
