## Description

The unit tests that #0429 and #0430 migrated to event-based waits now fail in bulk when the host is loaded. `LMStudioDashboardPaneContentTests` and `GitStatusPaneContentTests` are the affected suites. **Every failure is a hang-guard bound expiring. None is a logic assertion.** In each failing run, many tests in the same suite time out within a millisecond of each other. The same code passes on an immediate rerun.

The hang-guard defaults across the test target are inconsistent: 5, 10, 15 and 30 s. The two failing suites use 10 s and 15 s. Their tests and their production code are both `@MainActor`, and Swift Testing starts roughly 1,760 tests at once. So an event that has to pass through a MainActor job can queue behind hundreds of other tests' MainActor work. #0428 measured that backlog above 30 s under load, and for that reason set its own defaults to 30 s and made its suites `nonisolated`. These two suites can't go `nonisolated`, because the code they test is MainActor.

AGENTS.md "Asynchronous tests" says the bound is "a failure guard, never the mechanism the test relies on". Raising it therefore costs a passing test nothing. It only changes how long a real regression takes to fail. The work is to use one shared, generous hang-guard constant for every helper, and then to prove under deliberate CPU load that saturation is the only cause. A lost wakeup would produce the same symptom, and a bigger bound would hide it.

## Mechanism: still to confirm

The #0428 diagnosis was MainActor saturation. It is the leading hypothesis, but two details suggest the delay may be elsewhere, and the fix should confirm which it is:

1. **Cooperative thread pool starvation.** `EventCounter` is `nonisolated`. Its `consumeTask` is a plain `Task` created in a nonisolated `init`, so it runs on the global cooperative pool. `ScanHandledSignal.wait` is a `nonisolated` async call and hops there too. That pool is only as wide as the core count (12 on this host). Tests that block a pool thread synchronously, for example with `Process.waitUntilExit()`, a synchronous `drainSynchronously` reap or a contended `NSLock`, can starve it. Meanwhile every timeout runs on a Dispatch utility queue outside the pool, so the timeouts fire on schedule while the events can't be delivered. The same-millisecond clusters match that picture.
2. **MainActor saturation.** The emitting side, `emit…()` in `LMStudioDashboardPaneContent` and `handleScanResult` in `GitStatusPaneContent`, runs on MainActor. The events queue behind the other tests' MainActor jobs, as #0428 measured.

A cheap way to tell a slow event from a lost one: when an `EventCounter` or `ScanHandledSignal` wait expires, keep the wait registered and log how long after expiry the event actually arrived. Record that on the issue. It is a diagnostic, not a pass path. A late arrival means the event was delayed. No arrival at all means a real signal bug.

## Proposed direction

1. **One shared hang-guard constant.** Add it to the test target, for example `enum TestBounds { static let hangGuard: TimeInterval = 60 }`, and make it the default for every hang-guard helper in the table above, including the inline 5 s guard in `CrossWindowBehaviorTests`. Remove the explicit `bound: 30` overrides in `LMStudioDashboardPaneContentTests`, because the new default covers them. Leave the negative-test `0.2` bounds and the production reap bound as they are. Passing tests are not slowed, because the bound only matters on failure.
2. **Rule out a lost wakeup deterministically.** Run the full package under deliberate CPU load: start several `yes > /dev/null` processes, at least one per core, and kill them all afterwards, including on Ctrl-C. Use the new bound and repeat. Zero hang-guard expiries confirms the cause is saturation. **Any expiry that remains is a signal bug to investigate, not a reason to raise the bound again.** Use the late-arrival diagnostic above to tell which it is.
3. **Weigh limiting parallelism for these suites.** Two cautions:
   - `.serialized` only serializes tests *within* one suite. It doesn't stop the other ~1,700 tests from filling MainActor or the cooperative pool. `BellNotificationSummaryTests.swift:130` and `AppXPCServicePaneSplitUniqueTests.swift:17-35` already record this limitation.
   - Serializing a 15- or 23-test suite that spends real time in subprocesses lengthens the run.
   Adopt `.serialized` only if the loaded runs show that contention within the suite matters. Otherwise record why it was rejected.
4. **Document the constant** in `docs/async-test-seams.md` §4, "The hang-guard bound". Say what it is, why it is generous, which bounds are deliberately excluded, and that raising it again is not a fix for a remaining expiry. Update the per-helper defaults quoted in §1–§3 so they cite the constant instead of literal values.

## Done when

- Every hang-guard helper in the test target defaults to the single shared constant, and no helper has its own literal default.
- The package runs `swift test --parallel` at least 10 times back to back under the CPU load described above (report N) with zero hang-guard expiries. `./build.sh unit` then passes under the same load. Commands and counts are recorded in `## Verification`.
- If any expiry happened during that work, it was root-caused as a signal bug and fixed, not absorbed by the bound.
- `docs/async-test-seams.md` documents the constant.

### `.serialized` — rejected

Per "Proposed direction" step 3, considered adding `.serialized` to `LMStudioDashboardPaneContentTests`/`GitStatusPaneContentTests`. ### Late-arrival diagnostic (temporary, reverted)

Per the issue's suggested diagnostic, before landing the 60s default I temporarily instrumented `EventCounter.awaitCount`, `ScanHandledSignal.wait`, and `awaitScanHandled` (which normally clears `onScanResultHandledForTesting` immediately on failure — that clear was itself hiding late arrivals, so the diagnostic kept the callback wired past a failed wait instead) to log how long after the hang-guard's expiry the real event actually arrived. I temporarily set `TestBounds.hangGuard = 5` to force expiries deterministically, started 8 `yes > /dev/null` background burners, and ran `swift test --parallel` 6 times.

Every run failed (expected, given the artificially short 5s bound), and every logged expiry that could be observed was a **late arrival, never a loss**:

| Run | EventCounter late-arrivals (of ~9-13 expiries) | ScanHandledSignal late-arrivals (of 12 expiries) | Observed lateness |
|---|---|---|---|
| diag 1 | 13/13 | not yet instrumented | 4.7–5.1s late (9.7–10.1s total) |
| diag 2 | 13/13 | not yet instrumented | 2.2s late (7.2s total) |
| diag 3 | 13/13 | not yet instrumented | 4.7–5.1s late (9.7–10.1s total) |
| diag 4 | 13/13 | 3/12 | 6.1s late (11.1s total) |
| diag 5 | 13/13 | 0/12 | n/a for ScanHandledSignal this run |
| diag 6 | 13/13 | 12/12 | 14.2s late (19.2s total) |

The `EventCounter` diagnostic logged a late arrival for every single expiry it caught, across all 6 runs — direct, positive evidence that those particular waits were delayed, not lost.

The `ScanHandledSignal` diagnostic (git status) is **inconclusive**, not confirming, for the runs where most expiries went unobserved (diag 4: 9 of 12 unobserved; diag 5: 12 of 12 unobserved). `GitStatusPaneContent.requestScan()`'s `scanTask` captures `[weak self]` (`GitStatusPaneContent.swift:816-819`: `scanTask = Task { [weak self] in let result = await self?.scanner.scan(atPath: path); self?.handleScanResult(result, generation: requestGeneration) }`), and `GitStatusPaneContentTests`' tests `guard await awaitScanHandled(...) else { return }` with no further strong reference to `content`. Once the test function returns, `content` can be deallocated before the scan task resumes — at which point `self?.handleScanResult(...)` is a no-op, so the callback the diagnostic depends on never runs *regardless of whether the underlying event would have arrived*. An unobserved case therefore proves nothing either way: it is not evidence the event was lost, and it is not evidence it was merely late. Only diag 6 (12 of 12 observed) gives positive evidence for `ScanHandledSignal`, and there every one was a late arrival (14.2s late, ~19.2s total).

The no-lost-wakeup conclusion for this issue does **not** rest on the unobserved `ScanHandledSignal` cases. It rests on `## Verification` below: 12/12 `swift test --parallel` runs at the real `TestBounds.hangGuard = 60` produced zero hang-guard expiries in either suite. If a wakeup were actually being lost rather than delayed, a 60s bound — twelve times the original 5s diagnostic bound, and roughly 4x the worst delay this diagnostic measured (~14-19s) — would not have made every expiry disappear; it would still show up, just less often. The diagnostic's job was only to characterize *why* the original tight bounds failed (saturation-driven delay, confirmed for `EventCounter`); it is not itself the proof that no wakeup is ever lost.

All diagnostic instrumentation was reverted with precise edits back to the exact code in the "Helpers changed" commit — confirmed via `git diff` showing only the intended bound-routing changes remaining, no diagnostic residue. See `## Verification` below for the final proof at the real `TestBounds.hangGuard = 60`.
