## Description

User request (2026-10-12), verbatim:

> The Git Status view should also show worktrees.

The Git Status Pane knows it is *inside* a linked worktree (the header's "Worktree" badge) but never shows the set of worktrees the repository has. A user who keeps several `git worktree`s of one repository — the way this project's own issue workflow does, one worktree per `issue/NNNN` branch — has no view of them from Batty: which exist, where they are on disk, which branch each has checked out, which one the Pane is looking at, and which are locked or stale. The ask is a **Worktrees** section in the Git Status Pane, read-only like everything else in that view (`docs/design/git-status-view.md` §3).

**How the Git Status Pane works today (verified on `main` at `fdf5ab68`, 2026-10-12):**

- **Existing identifiers.** `git-status.snapshot`, `git-status.not-a-repo`, `git-status.scan-failed`, `git-status.operation-banner`, `git-status.diff-peek`, `git-status.file.<path>` (`GitStatusPaneView.swift:65,90,121,312,351,434`). `docs/ui-features.md` has **no Git Status section** — it mentions `git-status.snapshot` only inside the Projects sections (`:672`, `:861`). - **UI-test fixtures.** `BattyCLI.makeGitRepository(in:)` (`BattyUITests/Support/BattyCLIHarness.swift:289-303`) hand-writes a `.git` directory "without running `git` (the sandboxed runner may not be able to)". Real repositories are built by `ViewGalleryTests` instead, by running a shell script *inside a terminal Pane* via `pane split --command` (`runScript`, `:148-152`) and waiting for a sentinel file (`BattyUITestHarness.waitForFile`); `worktreeFixtureScript` (`:532-575`) already builds a main repo plus one linked worktree with `git worktree add`, and `testGitStatusWorktreeWithStash` (`:325-346`) opens the Pane on the linked worktree and asserts the "Worktree" badge by label.

**What `git worktree list --porcelain -z` emits (captured on git 2.54.0, Apple Git-157, 2026-10-12, from a temp repo with a main checkout and four linked worktrees):** one record per worktree, each attribute its own NUL-terminated token, records separated by an extra NUL (so `\0\0` ends a record). Attribute lines: `worktree <absolute path>`, `HEAD <40-hex sha>`, then exactly one of `branch refs/heads/<name>` or `detached`, or `bare` (in which case there is no `HEAD`/`branch`/`detached` at all), then optionally `locked` or `locked <reason>`, and optionally `prunable <reason>` (observed: `prunable gitdir file points to non-existent location` after `rm -rf` of a linked worktree's directory). The main worktree is printed first; from inside a linked worktree the output is identical, and the command works from any subdirectory. A path containing a space is printed raw (unquoted) under `-z`. A bare repository prints itself as `worktree <path>` + `bare` and then its linked worktrees. The call took ~20 ms wall-clock in that repo.

## Expected behavior

### Data: one more `git` call inside the existing scan, no new trigger

- `ProcessGitStatusScanner.performScan(atPath:)` runs a third command after the status call, on the same background queue and in the same `run(_:)` tracking (so `terminateIfRunning`/`terminateAndWaitBriefly` cover it with no further change): `git -C <path> worktree list --porcelain -z`. Its stdout, decoded as UTF-8, goes into a new `GitStatusRawScan.worktreeListOutput: String?` (defaulted to `nil` in the memberwise `init`, so the three existing construction sites compile unchanged). A non-zero exit or undecodable output logs once at `.error` with the stderr and leaves the field `nil`; **it never fails the scan** — the file groups must keep working on a `git` too old for `-z`/`locked`/`prunable` on `worktree list`.
- `-z` is chosen for the same reason the status parser uses it (`GitStatusPorcelainParser`'s doc comment, `GitStatusModel.swift:186-202`): without it, git C-quotes unusual paths and the parser would have to unescape.
- **Refresh policy (decided):** the list is re-read on every scan the Pane already performs — activation, show-after-hide, Change Directory…, the refresh button, and each debounced FSEvents burst. No new timer, watcher, or per-tick process: the only new process is one extra `git` per *scan*, and a scan already spawns two. Re-reading per scan rather than once at setup is what makes "I ran `git worktree add` in the terminal next to this Pane" show up: from the **main** worktree, that command writes `.git/worktrees/<name>/` under the watched `directoryPath`, so FSEvents fires and the next scan picks the new entry up; `git worktree lock` writes `.git/worktrees/<name>/locked`, same path. **Known limit, accepted:** a Pane watching a *linked* worktree does not see the common dir (`activate()` watches only `directoryPath`, `GitStatusPaneContent.swift:761`), and a Pane in the main worktree does not see a linked worktree's directory being deleted elsewhere (that is what makes it `prunable`); in both cases the refresh button, or any later change under the watched tree, catches up. A second FSEvents stream on `<common dir>/worktrees` is **not** part of this issue; if it is wanted, file it separately.

### Model: a pure parser and an entry type

- New `GitWorktreeEntry` in `GitStatusModel.swift` — `Sendable, Equatable, Hashable, Identifiable` (`id` is `path`) — with `path: String` (absolute, as git printed it), `headSHA: String?`, `branch: String?` (the `refs/heads/` prefix stripped), `isDetached: Bool`, `isBare: Bool`, `isLocked: Bool`, `lockReason: String?`, `isPrunable: Bool`, `pruneReason: String?`, and `isCurrent: Bool` (set during composition, below, never by the parser).
- New `GitWorktreeListParser.parse(_ output: String) -> [GitWorktreeEntry]`, next to `GitStatusPorcelainParser`: split on NUL, start a new record at each empty token (the `\0\0` record terminator) and at the first `worktree ` token, ignore any attribute line it does not recognise (forward compatibility), tolerate a missing trailing terminator, return `[]` for empty input. It is pure — no I/O, no `Process` — so it is tested from string fixtures exactly as the status parser is.
- `GitStatusSnapshot` gains `worktrees: [GitWorktreeEntry]` (defaulted to `[]` in the `init`, which keeps its single external construction site in `GitStatusPaneContent.swift:844-861` and any test fixtures compiling).

### Composition: current marker and order

- In `handleScanResult` (`GitStatusPaneContent.swift:835-861`), parse `raw.worktreeListOutput` (or `[]` when `nil`), then mark `isCurrent` on the entry whose `path` equals `raw.repositoryToplevel` after both are normalised with `URL(fileURLWithPath:).standardizedFileURL.resolvingSymlinksInPath().path` — git prints both from its own resolved view of the filesystem, but `/tmp` versus `/private/tmp` is exactly the kind of difference that would otherwise leave nothing marked. Exactly one entry is current whenever the Pane is inside a worktree (from the main checkout, from a linked worktree, and from any subdirectory of either, since `--show-toplevel` is the worktree root in all three cases). A bare entry is never current (a bare directory is never a toplevel).
- **Order (decided):** the main worktree first (git always prints it first; keep that), then the linked worktrees sorted by `path` with `localizedStandardCompare` so the list is stable across git versions and filesystems rather than inheriting `.git/worktrees` directory order. The current entry keeps its place and is marked, not moved.

### View: a Worktrees section

- A fifth `DisclosureGroup`, titled `Worktrees (N)`, rendered **after** the four file groups and the "working tree clean" line (it is repository-level information, not a working-tree change group, so the existing groups' order and the clean-line condition are untouched). Plain `DisclosureGroup` with no `isExpanded` binding, so it starts collapsed like the others; the user's expand/collapse is SwiftUI-owned view state (`docs/swiftui-observation-rules.md` — nothing here writes `@Observable` state from view code).
- **Visibility (decided: hide, not collapse):** the group renders only when `worktrees.count >= 2`. With a single plain checkout the list would contain exactly the Pane's own directory, marked current — no information — and hiding matches `fileGroup`'s existing "empty renders nothing" rule, which is also what keeps `CLIViewPaneTests`' single-repository fixtures and `ViewGalleryTests`' captures of the populated-repository and merge-conflict fixtures unchanged. (`testGitStatusWorktreeWithStash`'s capture *will* gain the section; that is the intended design-review capture.)
- **Row** (`accessibilityIdentifier` `git-status.worktree.<last path component>`), one line, middle-truncated, in the same `.callout` treatment as `pathLabel`:
  - a leading glyph: `checkmark.circle.fill` tinted `.accentColor` for the current worktree, `circle` in `.secondary` otherwise — the current marker;
  - the path abbreviated with `~` via `(path as NSString).abbreviatingWithTildeInPath` (precedent: `ProjectEditorViewModel.swift:229`), basename `.medium`, directory `.secondary`, as `pathLabel` does for files (`GitStatusPaneView.swift:359-381`);
  - then the branch name in `.secondary`, or `detached @ <first 7 of headSHA>` (the header's own wording at `:261`), or nothing for a bare entry;
  - trailing badges built with the existing `badge(_:systemImage:)` (`:283-289`): `Bare` (`archivebox`), `Locked` (`lock`, with `.help(lockReason)` when git gave one), `Prunable` (`trash`, `.help(pruneReason)`). The row's `accessibilityValue` is the space-separated subset of `current`, `bare`, `locked`, `prunable`, `detached` that applies (empty otherwise), and its `accessibilityLabel` is "`<~path>`, `<branch | detached @ sha | bare>`" so a UI test can assert the row without parsing the pixels. **Identifier length:** XCUITest rejects identifier queries longer than 128 characters (`BattyUITestHarness.swift:139-141`), which is why the identifier carries the last path component and not the absolute path; two worktrees with the same basename share an identifier, and the tests disambiguate by label.
- **Context menu** on a row, non-mutating: **Copy Path** (the absolute `path`, not the `~` form, onto `NSPasteboard.general` as the file rows do at `:461-464`) and **Reveal in Finder** (`NSWorkspace.shared.activateFileViewerSelecting`, same as `:458-460`); Reveal is disabled for a prunable entry whose directory no longer exists. **No add, remove, prune, lock, unlock, or move** — design §3 "read-only" stands, and a destructive worktree action needs its own confirmation UX.
- **Open a terminal here — deferred, not in this issue.** "New Tab / Split here, in this worktree's directory" is the natural next ask, but no GUI path today creates a terminal Pane or Tab with an explicit directory: `WindowRuntime.createPane(kind:direction:contentFactory:)` (`WindowRuntime.swift:614-626`) takes no path, `PaneRuntime.addTab(inheritingCWDFrom:)` (`PaneRuntime.swift:167-181`) inherits from a `TabRuntime` only, and `SplitTree.makePane`'s `path:` parameter feeds only the `.gitStatus` branch (`SplitTree.swift:389-396`) while a terminal split reads the source Tab's cwd (`:404-410`). A split from the Git Status Pane itself therefore starts at the shell default today — that is the bug #0487 is about (splits from non-terminal Panes not inheriting a working directory), and the plumbing it adds is what a "terminal here" action would ride on. File that action as a follow-up once #0487 lands, linked from this issue's Resolution notes; until then Copy Path + `cd` is the path.

### Bare repositories

- A Git Status Pane pointed **at** a bare repository keeps today's behaviour: `.notARepository` (`scanOfABareRepositoryReturnsNotARepository` stays green). The worktree list is only read once `--is-inside-work-tree` is `true`, so no new process runs for that case.
- A Pane inside a linked worktree **of** a bare repository (the `git clone --bare` + `git worktree add` layout) lists the bare entry first with the `Bare` badge, no branch, never current, and its own entry marked current.

### Linked worktrees

- The section works from inside a linked worktree and marks that worktree current (verified above that `git worktree list` prints the full set from a linked worktree, and `--show-toplevel` resolves to the linked worktree's root). The header's existing "Worktree" badge is unchanged.

### Logging

`.info` per scan with the entry count and the current path through the file's existing `logger`; `.error` once per failed `worktree list` call with the stderr.

## Actual behavior

The Pane shows the file groups and a "Worktree" badge when it happens to be inside one, and nothing about the repository's other worktrees — not their paths, branches, which is current, or which are locked or prunable. The only way to see them from Batty is `git worktree list` in a terminal Pane.

## Root cause

This was a missing feature. The scan never read `git worktree list`.

## Fix

- `ProcessGitStatusScanner.performScan` runs `git worktree list --porcelain -z` as a third command inside the existing tracked `run(_:)`. A failure is logged and never fails the scan.
- `GitWorktreeListParser` is a pure parser that produces `GitWorktreeEntry` values. `GitStatusSnapshot.worktrees` holds them.
- `handleScanResult` marks the current entry by comparing paths after resolving symlinks. The main worktree comes first, and the linked worktrees follow, sorted by path.
- `GitStatusPaneView` adds the section only when there are at least two worktrees. Each row gets the identifier `git-status.worktree.<basename>`. Its accessibility label is "<~path>, <branch | detached @ sha | bare>", followed by any of `current`, `locked` and `prunable` that apply.
- The list refreshes on every scan the Pane already runs. No new timer or watcher was added.
