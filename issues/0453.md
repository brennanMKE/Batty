## Description

Testing Batty Beta by hand on 2026-10-09, the user reported finding "zero UI to open any of the new views at all" in the menus — and pointed out this was discussed before. Both halves are accurate. The four non-terminal view Pane kinds (Git Status, Process Status, LM Studio Dashboard, System Metrics) *are* reachable from the GUI, but every GUI path requires already knowing where they are hidden:

- **The Pane menu** (`BattyKit/Sources/BattyKit/Commands/BattyCommands.swift:221-331`) lists "Split Horizontally ▸" (`:286`) and "Split Vertically ▸" (`:329`) as submenus whose first item is **Terminal** (`:250-256`, `:293-299`), then — below a divider — Git Status (`:259`, `:302`), Process Status (`:266`, `:309`), LM Studio Dashboard (`:273`, `:316`), System Metrics (`:280`, `:323`), each calling `keyWindow?.createPane(kind:direction:)`. Nothing at the Pane menu's top level says "view", "Git Status", or anything other than "Split …". A person scanning the menu bar for the new feature sees the same four split verbs Batty has always had; the view names are only visible after hovering a submenu arrow on a row whose label describes a terminal split.
- **No other menu names a view.** The full menu surface is `BattyCommands.swift:66` (File group), `:89` (View ▸ Toggle Sidebar — the only item Batty adds to the system View menu), `:101` (Session), `:135` (Theme), `:168` (About), `:179` (Edit), `:201` (Window), `:217` (Help), `:221` (Pane), `:430` (Tab). There is no "Views" menu, no "Open View" section, and no sidebar or Session-menu entry.
- **The window toolbar** (`BattyKit/Sources/BattyKit/Views/SessionDetailView.swift:176-203`) has two split buttons that call `tree.splitFocusedPane` / `tree.splitFullDimension` (Option held) and nothing else — terminal only. **This is intentional and stays that way; see Constraints below.**
- **The Command Palette** (`BattyKit/Sources/BattyKit/Views/CommandPaletteView.swift:244-259`) dispatches all eight `splitHorizontal<Kind>`/`splitVertical<Kind>` actions and lists them automatically from `ShortcutAction.allCases`, but under the names "Split Horizontally (Git Status)" etc. — found only if you search for the view by name or already know to look under "Split".
- **Keyboard shortcuts.** The task premise that these actions have no default chords is **false** and this issue should not repeat it: `ShortcutAction.defaultBinding` (`BattyKit/Sources/BattyKit/Shortcuts/ShortcutAction.swift:121-136`) ships `Cmd-G`/`Cmd-Shift-G` (Git Status), `Cmd-J`/`Cmd-Shift-J` (Process Status), `Cmd-Y`/`Cmd-Shift-Y` (LM Studio Dashboard), `Cmd-E`/`Cmd-Shift-E` (System Metrics), dispatched by the NSEvent monitor in `BattyKit/Sources/BattyKit/Commands/BattyShortcuts.swift:154-169` and shown as badges on the submenu rows. They are documented in `docs/shortcuts.md:107-114` and the in-app Help catalog `BattyKit/Sources/BattyKit/Help/05-shortcuts.md:22-29`, whose only prose about the menu location is at `:39-41`: "In the Pane menu, 'Split Horizontally' and 'Split Vertically' are submenus: Terminal first…". The chords exist; nothing in the visible UI advertises them next to a view's name.
- **The CLI** (`batty pane split --view <kind>`, #0315) is the path every demo and test uses (`BattyUITests/CLIViewPaneTests.swift:96-207`, `docs/beta-demo-script.md` §3), which is exactly why the gap went unnoticed by automation: no UI test opens a view through the menu bar.

Net effect: the one part of the release a first-time user is most likely to go looking for is the one part the menu bar never names. The feature is shipped and working; its *entry point* is not.

## The prior discussion (so this gap is recorded accurately)

- **#0301** (umbrella, `open`) — "Expand Batty beyond terminal-only Panes with new view kinds". Its Children table (`issues/0301.md:54`) lists #0331 as "menu affordance for creating typed panes — the GUI counterpart of #0315".
- **#0331** (`resolved` 2026-08-22, branch `issue/0331-1`, landed in `145d94c0`; never user-`closed`) — "No menu affordance creates a typed Pane, so the new view kinds are reachable only through the CLI". Filed 2026-08-09 from the user's question, quoted there: *"Is there an issue to support using the menu to split out a new pane and select one of the new view types?"* The filing laid out four shapes without choosing (`issues/0331.md:38-51`): (1) a separate **"New Pane ▸" submenu listing kinds**, distinct from the Split items; (2) kind as a submenu under each existing split item; (3) a single "Split with View…" picker overlay; (4) something else. During implementation the user chose shape (2) **as an Option-hover reveal** on Split Horizontally/Vertically — plain click unchanged, Option swaps in the kind list — and asked for one letter per kind as shortcuts. The Option-alternate could not ship: `NSMenuItem.isAlternate` forces `Cmd-Option-D`/`Cmd-Shift-Option-D`, already bound to Split Full-Height Column/Full-Width Row in the same menu. The user had pre-approved an "always-visible submenus" fallback for that case, and that is what shipped (`BattyCommands.swift:222-246` comment; `issues/0331.md` Resolution notes and Gotchas). #0331's own Gotchas flag that this "doesn't fully clear" the user's bar and that the submenu's readability "is unverified — … the user is in the best position to react to the actual menu once it's running." That reaction is this issue.
- **#0315** (`resolved`) — the CLI verbs; its directive "omitting the kind means Terminal, so no existing caller changes behavior" is why Terminal stays the first submenu item and why the plain `Cmd-D`/`Cmd-Shift-D` chords still split a terminal.
- **#0304 / #0313 / #0314** (`resolved`) — the Git Status, LM Studio Dashboard, and System Metrics views themselves. None of them, nor `docs/design/*.md`, specifies a menu placement; #0331 records that "the CLI is the only creation surface either issue actually commits to building".
- **#0383** (`resolved`) — `--unique` find-or-create for the CLI. Explicitly leaves the menu, palette, and shortcuts free to create duplicate view Panes (`issues/0383.md:39`); nothing here changes that.
- **#0257** (umbrella, `open`) — CLI verb surface; `issues/0257.md:153`: "Keep verbs feeling like native actions with keyboard/menu equivalents where sensible."

So: the user asked in August for a menu path to the views; what shipped hides them two levels down behind a label that reads as the old terminal action, with the #0331 fallback explicitly flagged as provisional pending the user seeing it. The user has now seen it.

## Steps to reproduce

1. Launch Batty Beta with one Session open.
2. Read every menu-bar title and every top-level item in File, Edit, View, Session, Theme, Pane, Tab, Window, Help looking for "Git Status", "System Metrics", "Process Status", "LM Studio", or "View".
3. Note that the Pane menu's top-level items read Split Horizontally ▸, Split Vertically ▸, Split Full-Height Column, Split Full-Width Row, Layouts…, and the tab/pane-management items — nothing names a view.
4. Only by hovering "Split Horizontally ▸" does a list with Git Status / Process Status / LM Studio Dashboard / System Metrics appear.

## Expected behavior

The four views are discoverable from the menu bar without knowing to open a split submenu, with the UI kept as lightweight as possible:

1. **A top-level, clearly named entry point in the menu bar.** Preferred: a section in the Pane menu (e.g. a divider then four items, or a "Open View ▸" / "Views ▸" submenu at the Pane menu's top level) listing **Git Status**, **Process Status**, **System Metrics**, **LM Studio Dashboard** by their `PaneContentKind.displayName` with the SF Symbols already used for them (`arrow.triangle.branch`, `list.bullet.rectangle`, `gauge`, `cpu` — `BattyCommands.swift:261-283`). Each opens that view beside the focused Pane via `WindowRuntime.createPane(kind:direction:)` (`BattyKit/Sources/BattyKit/WindowRuntime.swift:588-600`), whose default direction is already `.horizontal`. Placing the entries in the system View menu (next to Toggle Sidebar, `BattyCommands.swift:89`) is an acceptable alternative if the implementer and user prefer it; either way the names must be visible at the top level of some menu. The Split Horizontally ▸ / Split Vertically ▸ submenus stay as the direction-choosing path, so #0331's shape is extended, not reverted.
2. **Default keyboard shortcuts are shown next to the view's name.** The chords already exist (`Cmd-G`, `Cmd-J`, `Cmd-Y`, `Cmd-E`, `ShortcutAction.swift:121-136`). The new top-level items should carry the horizontal variant's `keyboardShortcut` so the badge appears where a person reading for "Git Status" will see it. Because SwiftUI menus render a chord badge on every item bound to it, the implementer must check that the same chord appearing on both the new item and the submenu row renders acceptably (and whether the NSEvent monitor plus a duplicated `.keyboardShortcut` causes a double dispatch); if it does not, drop the badge from the submenu rows rather than the new items. No new `ShortcutAction` cases are required; if any are added, `ShortcutDocsSyncTests` (#0329) requires `docs/shortcuts.md` and `Help/05-shortcuts.md` to change in the same commit.
3. **Enabled state matches existing behavior:** items disabled when `keyWindow?.selectedSession == nil`, exactly as the split items are (`BattyCommands.swift:288`, `:331`).
4. **Documentation follows:** `Help/05-shortcuts.md:39-41` and `docs/shortcuts.md` §9 describe the new location; `docs/beta-demo-script.md` (currently uncommitted edits in the working tree — coordinate, don't clobber) can mention the menu path alongside the CLI.
5. **Tests:** a `BattyUITests` test that opens each of the four views through the new menu path (Tart VM only, per AGENTS.md — `app.menuBars.firstMatch.menuBarItems["Pane"]` as in `BattyUITests/MultiWindowTests.swift:67-68`) and asserts the Pane appears, plus unit tests for any new command routing (extend `BattyKit/Tests/BattyKitTests/WindowRuntimeCreatePaneTests.swift` if a new dispatch arm is introduced).

## Constraints (user decisions, 2026-10-09)

- **The window toolbar must not change.** No dropdown chevron, no long-press menu, no fourth button: the toolbar keeps its current three action buttons (Split Horizontally, Split Vertically, Bell Feed — `SessionDetailView.swift:176-215`) exactly as they are. The user wants the UI as lightweight as possible. Views are reachable from the **menu bar, Command Palette, keyboard shortcuts, and CLI only.**
- Omitted kind still means Terminal everywhere (#0315 directive); `Cmd-D`/`Cmd-Shift-D` and the toolbar buttons keep creating terminal Panes.
- The menu may create duplicate view Panes deliberately (#0383's scope note); do not add singleton gating here.

## Actual behavior

No menu title or top-level item names a view. The views are reachable only via Pane ▸ Split Horizontally ▸ / Split Vertically ▸ (second level, under a label that reads as the terminal split), the Command Palette (by typing a view's name), the `Cmd-G/J/Y/E` chords (undiscoverable without Help or Settings ▸ Shortcuts), or the CLI.

## Notes

- Priority: **high — blocks the release.** The view Panes are the release's headline feature and the user-facing entry point is missing.
- Touching `BattyCommands.swift` alone keeps this out of the terminal-host path. If the implementer ends up touching `SessionDetailView.swift` or any pane body for any reason (they should not need to, given the toolbar constraint), `docs/terminal-pane-requirements.md` and `docs/swiftui-observation-rules.md` are binding.
- `keyWindow` in `BattyCommands` is `store.keyWindowOrFirstRegistered()` (`BattyCommands.swift:61`); the new items should use the same accessor so the enabled state and target window agree with the split items.
- Relation: child of #0301 (add to its Children table when claimed; this filing touches only this file); follows up #0331 (whose provisional fallback this revisits); sibling of #0315 (CLI) — same `PaneContentKind` vocabulary, same `createPane` machinery.

## Resolution notes

- `BattyCommands.swift`: the Pane menu now opens with an "Open View" section (Section header, no extra nesting) listing Git Status, Process Status, System Metrics, LM Studio Dashboard with their existing SF Symbols, each calling `keyWindow?.createPane(kind:direction: .horizontal)` and `.disabled(keyWindow?.selectedSession == nil)`, followed by a Divider and the unchanged Split items.
- Badges: the new items carry the horizontal chords (Cmd-G/J/E/Y). The horizontal rows inside the Split Horizontally submenu no longer carry `.keyboardShortcut`, so each chord is shown on one item only. The Terminal row and all vertical rows keep theirs. In a content window `BattyShortcuts` takes the chord before the menu does, so it never runs twice; when another window such as Settings has focus (`BattyShortcuts.swift:34` gate), the menu shortcut is what runs it. The Split submenus list the views in the same order as Open View.
- No new `ShortcutAction` cases and no new dispatch arm, so no new unit test (existing `WindowRuntimeCreatePaneTests` cover `createPane`; `ShortcutDocsSyncTests` unaffected).
- Toolbar untouched.
- Docs: `docs/shortcuts.md` section 9 and `Help/05-shortcuts.md` describe the Open View section.
- UI test: `BattyUITests/PaneMenuViewTests.swift` opens each view via Pane menu and asserts the content identifiers `git-status.snapshot`, `process-status-view`, `system-metrics-pane`, `lmstudio-dashboard`.
- `docs/beta-demo-script.md` (uncommitted in main checkout, not touched): lines 137-138 say "View -> New Pane (#0331)", which does not exist; it should read "Pane -> Open View" (or Pane -> Split Horizontally -> <kind>).
