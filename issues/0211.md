## Description

The per-session notification count badge shown next to sessions in the sidebar sometimes renders as a plain white circle with no visible number inside. The number is presumably being drawn in a color that has insufficient contrast against the badge's fill on certain themes.

## Expected behavior

The count inside the badge should always be legible — the badge fill and text colors should be chosen so there is enough contrast for the number to be read on every theme.

## Actual behavior

On some themes the badge appears as a solid white circle with no readable number — the text is either the same color as the fill (or close enough that it disappears) or otherwise invisible.

## Notes

- Likely the badge text color is hard-coded (e.g. white-on-accent) while the fill color is theme-derived, so when the theme's accent happens to be light the text disappears into the fill.
- Consider deriving the text color from the badge fill via a luminance check (pick black or white based on the fill's perceived brightness), or pinning the fill to a theme-independent color that always contrasts with white text.

## Root cause

`SessionRow` in `SessionSidebarView.swift` drew the unseen-bell count with `.foregroundStyle(.white)` over a `Capsule().fill(accent ?? Color.accentColor)`. The accent comes from `ThemeChrome` and is derived from each theme's chosen highlight slot (cursor → ANSI 4 → ANSI 6). On themes whose chosen accent happens to be near-white (light themes with a pale cursor), white text on a white fill collapses to the "plain white circle" symptom described in the report.

## Fix

Took the luminance approach (option (a) from the issue notes). Reused the existing `RGBColor.contrast` / `ChromePalette.preferLegible` helpers in `ThemeChrome.swift` — the project already implements WCAG 2.x relative luminance and contrast ratio for chrome-palette decisions, so there was no need to add a new helper.

`ChromePalette` now computes an `accentForeground` at theme-load time by picking whichever of pure white or pure black has the higher WCAG contrast against the selected accent. `ThemeChrome` exposes it alongside `accent`, and `SessionRow` uses it for the badge text, falling back to `.white` when no theme is active so unthemed chrome behavior is unchanged.

## Verification

- `scripts/build.sh` — succeeded after the change (initial compile failed on `RGBColor.white`/`.black` shorthand; fixed by constructing explicit `RGBColor(red:green:blue:)` values).
- No unit tests were run or added — the existing `ThemeChromeTests` already cover the underlying `relativeLuminance` / `contrast` / `preferLegible` primitives this fix composes.
- Visual verification across themes is the user's per the CLAUDE.md UI-work rule; the build only proves the code compiles and renders without crashing.

## Files changed

- `BattyKit/Sources/BattyKit/Theme/ThemeChrome.swift` — added `accentForeground` to `ChromePalette` (storage, `.default`, theme-driven init, memberwise init) and exposed it on `ThemeChrome`. The accent foreground is computed by `preferLegible` against pure black and pure white.
- `BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift` — threaded `accentForeground` from `themeChrome` into `SessionRow` and used it for the unseen-bell badge text, with `.white` as the unthemed fallback.

## Gotchas

- `RGBColor` is the internal value-type used for palette math; it does not have `.white`/`.black` shorthand constructors — the call site has to spell out `RGBColor(red: 1, green: 1, blue: 1)` and the black equivalent. Easy to trip on if you assume parity with `Color`/`NSColor`.
- The fix only touches the sidebar count badge. Other call sites that paint hard-coded text on the theme accent (notably `BattyTabChip` and `PaneView` overlays) were not audited — if similar legibility complaints surface for those, they should be filed separately and can adopt the same `themeChrome?.accentForeground` pattern.
