# 0211 — Sidebar notification count badge is unreadable on some themes

## Description

The per-session notification count badge shown next to sessions in the sidebar sometimes renders as a plain white circle with no visible number inside. The number is presumably being drawn in a color that has insufficient contrast against the badge's fill on certain themes.

## Expected behavior

The count inside the badge should always be legible — the badge fill and text colors should be chosen so there is enough contrast for the number to be read on every theme.

## Actual behavior

On some themes the badge appears as a solid white circle with no readable number — the text is either the same color as the fill (or close enough that it disappears) or otherwise invisible.

## Notes

- Likely the badge text color is hard-coded (e.g. white-on-accent) while the fill color is theme-derived, so when the theme's accent happens to be light the text disappears into the fill.
- Consider deriving the text color from the badge fill via a luminance check (pick black or white based on the fill's perceived brightness), or pinning the fill to a theme-independent color that always contrasts with white text.

## Root cause

`SessionRow` in `SessionSidebarView.swift` drew the unseen-bell count with `.foregroundStyle(.white)` over a `Capsule().fill(accent ?? Color.accentColor)`. Because both the fill and the text color were chosen independently of the row's actual text style, any theme whose accent landed near pure white collapsed the badge into a plain white capsule with the number invisible inside.

## Fix

Redesigned the badge as an outlined chip rather than a filled one. The `Capsule()` is now drawn with `.stroke(accent ?? Color.accentColor, lineWidth: 1)` and a clear interior, and the count `Text` no longer carries a `.foregroundStyle` modifier at all — it inherits the row's environment text color, which is the same color the session title is already rendering in. The accent stroke keeps the chrome theming, but the number reads against the row background just like the session title beside it.

## Verification

- `scripts/build.sh` — succeeded.
- No unit tests changed; the previous luminance-based fix's general-purpose helpers (`RGBColor.contrast`, `ChromePalette.preferLegible`) stay because they're still used elsewhere in `ChromePalette` (e.g. the active-tab stroke). Nothing in the test suite referenced the removed property.
- Visual confirmation across themes is the user's per the CLAUDE.md UI-work rule; compilation only proves the new view renders and lays out.

## Files changed

- `BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift` — badge `Capsule` now uses `.stroke(...)` instead of `.fill(...)`; dropped the explicit `.foregroundStyle` on the count `Text`; removed the now-unused `accentForeground` parameter from `SessionRow` and its caller.
- `BattyKit/Sources/BattyKit/Theme/ThemeChrome.swift` — removed `accentForeground` entirely (storage on `ChromePalette`, `.default` slot, theme-driven init, memberwise init, public surface on `ThemeChrome`). The badge was the only consumer.

## Gotchas

- An earlier attempt (code commit `1e947d0`, resolution commit `d3f3c4f`) shipped a filled-capsule design with a luminance-chosen `accentForeground`. The user redirected to the stroked-outline design recorded above and that earlier approach has been replaced wholesale — the supporting `accentForeground` property was removed at the same time.
- Other call sites that paint over the theme accent — `BattyTabChip` (a 6×6 unseen-dot circle, no text overlay) and `PaneView` (`.strokeBorder` only, no fill-with-text) — don't share this anti-pattern and were not touched.

## Notes (post-fix)

- The redesign deliberately stops the badge from competing with the session title typographically: it keeps the chroma cue (theme-tinted outline) but lets the row's text style dominate the chip's interior.
