# 0227 — Session name stays stuck on the initial working directory; cd does not reset/update it

| | |
|---|---|
| **Status** | in-progress |
| **Module** | Session / TerminalSurface |
| **Platform** | macOS |
| **First seen** | 2026-05-30 |

## Description

Single-pane session auto-naming (#0213) does not reliably react to `cd`. Repro: open a session in a named project folder (it takes the folder's name), create a new session, then `cd` that session to a different folder — the session keeps the original name instead of resetting to `Session N` / the new folder's name. #0213 was supposed to deliver this; the regression is that the live signal never reaches the model.

## Long Description

Root cause is **not** in #0213's model logic. `AppStateStore.handleWorkingDirectoryChange` + `resolveAutoTitle` are correct — a unit test reproducing the exact sequence against the store passes. The defect is in how the cwd change reaches that code:

- The live cwd value is `TerminalViewState.workingDirectory`, declared `@Published` on a Combine `ObservableObject`. `TerminalViewState` is **upstream** (libghostty-spm / `GhosttyTerminal`), and uses `ObservableObject`/`@Published` deliberately to support iOS 15 / Mac Catalyst 15, where the `@Observable` macro (iOS 17 / macOS 14+) isn't available. Batty can't change that.
- `PaneView` consumed it via `.onChange(of: tab.terminal.workingDirectory)`. But `PaneView` only observes the `@Observable` model (`@Bindable pane`/`tree`); it holds no `@ObservedObject` on `tab.terminal`, and the `@Observable` macro does not track nested Combine `@Published` properties. So the `.onChange` re-evaluated only when `PaneView`'s body re-rendered for some *other* observable reason.
- A plain `cd` is a pure terminal/Combine event with no accompanying observable-model change, so nothing re-rendered the pane and the rename never fired — the name stayed on the initial directory. Session creation/switching caused enough incidental churn that the *first* name landed, which is why the bug reads as "new session keeps the old name."

## Steps to reproduce

1. In session A, `cd` into a recognized project folder (e.g. `~/Developer/Batty`). Sidebar shows "Batty".
2. Create a new session (it inherits the cwd and is also named "Batty").
3. In the new session, `cd ~` (or any non-project folder).
4. The new session's sidebar name stays "Batty".

## Expected behavior

On step 3/4 the name drops "Batty" — resetting to `Session N` (no project / no cached name) or updating to the new folder's project/cached name, per #0213's rules. Only the primary (anchor) pane of a single-pane session drives this; user-renamed sessions (`titleOverride`) are never touched.

## Actual behavior

The auto-derived name persists until some unrelated UI change forces a pane re-render.

## Relation

- Carved out of investigation into [[0213]] (live-update model logic — correct) and [[0214]] (create-time unify — separate, still open).

## Root cause

`PaneView.onChange(of: tab.terminal.workingDirectory)` depended on SwiftUI re-rendering to notice a Combine `@Published` change that neither the view nor the `@Observable` layer subscribes to. The cwd→rename trigger therefore fired only opportunistically.

## Fix

Drive auto-naming from libghostty's authoritative pwd callback instead of a SwiftUI render dependency:

- `TerminalDelegateProxy` (Batty's `TerminalSurfacePwdDelegate`) gains an `onWorkingDirectoryChange` closure, fired in `terminalDidChangeWorkingDirectory(_:)` right after the new path is written to `state`.
- `PaneView` wires that closure in the existing `.task(id: tab.id)` block (the same choke point that wires `onClose`) to call `AppStateStore.handleWorkingDirectoryChange(forTabID:)`, and does one initial resolve there to cover the case where the surface reported its cwd before the wiring ran. The unreliable `.onChange(of: tab.terminal.workingDirectory)` is removed.

Per the view-hierarchy doc, non-selected sessions keep their `PaneView` mounted, so `.task` wires every session's anchor tab, foreground or background.

## Gotchas

- The model test passing is necessary but not sufficient — it proves the store logic, not the wiring. This bug lived entirely in the wiring, so treat a green `swift test` as "didn't regress the model," not "fixed." UI-level verification is the real gate.
- `TerminalViewState` is upstream and intentionally Combine-based; do not attempt to convert it to `@Observable` — that would break the package's iOS 15 support. Bridging the signal (as done here) is the correct shape.
