# 0557 — A Claude Code BEL and its "waiting for your input" notification from the same Tab would show as two Bell Feed rows, because collapse requires identical messages

| | |
|---|---|
| **Status** | open |
| **Module** | BellFeed |
| **Platform** | macOS |
| **First seen** | 2026-11-05 |

## Description

If a Tab rings a bare BEL and then posts an OSC 9/777 notification for the same moment, for example Claude Code ringing and then reporting "Claude is waiting for your input", the Bell Feed shows two rows for one event. `BellFeedStore.recordOrCollapse` (`BattyKit/Sources/BattyKit/Runtime/BellFeedStore.swift:262`) collapses a repeat only when `candidate.message == entry.message`. A BEL has `message == nil`, and an OSC entry carries text, so the two never match.

The goal, from the user (2026-11-05):

> We should make it our goal to declutter the notification list as much as possible so only what is useful remains.

Split out of [#0555](0555.md), "Further decluttering".

## What the data shows

The pair is plausible, but **the user's exported log has no instance of it.** `~/Downloads/batty-bell-decisions-2026-11-05-142840.txt` holds 188 records from 2026-10-25 to 2026-11-05: 17 BEL and 171 OSC.

- None of the 17 BELs has an OSC from the same Tab within 10 s.
- Only 2 BELs share a Tab with any OSC at all. The gaps are 101 s ("◑ Next steps") and 1188 s ("◑ Hack the Planet fan site").
- The other BELs come from shell Tabs ("Terminal", path titles) with no OSC traffic.

Claude Code's own notifications arrive as OSC 9 alone.

## Recommended default

**Don't change collapse yet.** Leave this issue open as a watch item. Re-examine it with the #0523 capture log (`docs/bell-feed-capture.md`) once it holds a week or more of data with capture on, and look for a BEL and an OSC from the same `tabID` within a few seconds. If pairs show up, the rule to plan:

- A bare BEL (`message == nil`) arriving within **5 s** of an unread OSC row from the same Tab folds into that row. It bumps `repeatCount`, the BEL adds no row, and no second banner is posted.
- An OSC arriving within 5 s of an unread BEL row from the same Tab replaces that row's `message` with its text. The row's `id` is kept, so a pending notification tap still resolves.
- The #0297 record for the folded bell gets `suppressed:collapsedIntoUnread`, as #0298 repeats do today.

5 s is a guess, and the capture data should set it. #0298 picked its 30-minute window the same way.

## Notes

- #0298's rule deliberately treats `nil == nil` as a match for BEL floods and never matches across `nil` and text. Any change here must keep both BEL-flood collapse and the "same Tab only, never global" rule.
- If [#0556](0556.md) (prune on visit) lands first, a pair whose first row was already pruned by a visit can't fold. That's fine, because the user saw it.
