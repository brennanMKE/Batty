## Description

`./build.sh ui` runs XCUITest directly on the host Mac. XCUITest's `testmanagerd` sets up Accessibility for running GUI apps and can bootstrap `XCTAutomationSupport` into apps other than the one under test. On 2026-09-12 a UI test run from another project did that to the user's Prod Batty and crashed it, killing 38 live Terminal Sessions (#0409). A Batty UI test run on the host is the same hazard pointed at the user's own terminals: the host this repo lives on (`brennan-mac-mini-m4`, "cameron") is where the user runs Batty.

`AGENTS.md` already says, in its binding "UI test automation" section, that UI tests only run inside a disposable Tart VM. It points at `docs/ui-testing-vm.md` (#0412) and "the VM runner it describes". **Neither exists yet.** This issue creates them: a Batty golden image, a VM runner, a build phase that refuses to build `BattyUITests` on a host, `./build.sh ui` routed to the VM, and Batty's own doc. Two sibling projects on this host (Changeover, Curator) already run their UI tests this way, so the pattern is proven. Batty has a few extra problems the siblings didn't (see Notes), and they have to be checked in the guest, not assumed.

## Current state (verified 2026-09-23)

- `build.sh:14` documents `./build.sh ui [target ...]` as "UI tests (delegates to scripts/run-ui-tests.sh)". At `build.sh:79-84` the `ui|test)` case runs `exec "$REPO/scripts/run-ui-tests.sh" "$@"`.
- `scripts/run-ui-tests.sh` runs everything on the host. It snapshots `Configuration/Active.xcconfig` and selects Beta via `scripts/set-environment.sh Beta`. Then it runs `xcodebuild -scheme "Batty (Beta)" -destination platform=macOS CODE_SIGN_IDENTITY=- CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=NO build-for-testing`. Next it re-signs `BattyUITests-Runner.app` and `Batty Beta.app` ad hoc with `codesign --force --deep --sign -` (its header says this is a workaround for Gatekeeper translocating the Apple-template runner to the Trash). Finally it runs `test-without-building`, turning each positional argument into `-only-testing:<spec>`. It has no host check.
- Both shared schemes, `Batty (Beta).xcscheme` and `Batty (Prod).xcscheme`, list `BattyUITests` in their Test action alongside `BattyKitTests` and `BattyTests`, all `skipped = "NO"`. A plain `xcodebuild -scheme "Batty (Beta)" test` on the host therefore runs the UI suite. Curator avoids this with a separate UI-test scheme.
- The `BattyUITests` target (`Batty.xcodeproj/project.pbxproj`, the `PBXNativeTarget "BattyUITests"` block) has only the Sources, Frameworks and Resources build phases. There is no script phase and no host guard.
- The suite is 21 Swift files under `BattyUITests/` with 73 `func test` methods. AGENTS.md says "60+ tests, ~10 min".
- Stale instructions that still tell agents to run UI tests on the host:
  - `issues/Issues.md`, "Build / verify command for this project": "on the Mac mini … `scripts/run-ui-tests.sh`". It also names the `Batty (Prod)` scheme, which is stale.
  - `BattyUITests/README.md` "Running locally": `xcodebuild -scheme Batty -destination 'platform=macOS' test`.
  - `issues/0409.md` Plan, Step 4, which puts the UI-level regression guard "Mac mini only".

## Precedent on this host (read, not re-verified here)

**Shared host setup.** This lives in `~/Developer/Homelab/cameron/tart-ui-test-vm.md`.

- Tart 2.x is installed, and VM storage is under `~/.tart`.
- The current golden, `changeover-uitest-golden` (built from `ghcr.io/cirruslabs/macos-tahoe-xcode:27`, per the host doc's latest golden record), has:
  - macOS 26.6.2 (25G83) with admin auto-login.
  - Xcode 27.0 (27A266a) at `/Applications/Xcode_27.app`.
  - 6 CPUs and 12288 MB of memory.
  - Automation Mode without authentication and developer mode enabled.
  - Screen lock off and every `pmset` sleep at 0.
  - SSH that refuses every user: the `admin` nested group (GID 80) is removed from `com.apple.access_ssh`.
  - Access through `tart exec` only.
- The doc's ground rules:
  - Nothing on the host changes beyond Tart and `~/.tart`.
  - A live working copy or `$HOME` is never shared into the guest read-write.
  - Only one VM runs at a time.
- `tart list` on 2026-09-23 showed these local VMs: `changeover-uitest-golden`, `curator-uitest-golden`, `quartermaster-uitest-golden`, `switchyard-uitest-golden`, and one running `quartermaster-uitest-20260923-180418-56351` clone. Other projects are using the same two-guest budget right now.

**Curator's pattern.** This comes from `~/Developer/brennanMKE/Curator/docs/ui-testing-vm.md` and `~/Developer/brennanMKE/Curator/scripts/run-ui-tests-vm.sh`, and matches Changeover's `~/Developer/brennanMKE/Changeover/run-ui-tests-vm.sh`.

1. **Own golden.** The project has its own golden, cloned from Changeover's: `tart clone changeover-uitest-golden curator-uitest-golden`. It is never run directly and never touches another project's golden. It is re-cloned when Changeover's is rebuilt.
2. **Preflight.** The script checks, in order:
   - Tart and the golden are present.
   - **No other VM is running** (`tart list` has no `running` row). Otherwise it refuses.
   - At least 20 GiB of disk is free.
   - There is enough memory. If the host is short, it requests memory through the memory-signal protocol (`~/Developer/Homelab/cameron/lm-studio-memory.md`: the `dev.homelab.memory-observer` LaunchAgent unloads LM Studio models and answers `ready` or `failed`). The request is released in the EXIT trap.
3. **Stale-clone sweep.** The sweep matches only the script's own run-id shape, `<prefix>-<YYYYMMDD>-<HHMMSS>-<pid>`, and re-checks the golden's name inside the loop. This is a hard lesson: on 2026-09-13 Changeover's first sweep matched any `changeover-uitest-` name and deleted the golden itself (the "Incident, 2026-09-13" note in the host doc).
4. **Clean export.** `git archive HEAD | tar -x` goes into a fresh temp directory, never the live working copy, so **uncommitted edits are not tested**.
5. **Clone and boot.** Each run makes a fresh clone, `<prefix>-<run-id>`, and boots it headless: `tart run … --no-graphics --dir=run:"$EXPORT":ro`, with the export shared **read-only**. The script then waits on `tart exec <clone> true` with a boot timeout.
6. **Build and test in the guest.** The script copies the source to `~/src` in the guest and runs `xcodebuild … test CODE_SIGN_IDENTITY=- CODE_SIGN_STYLE=Manual DEVELOPMENT_TEAM=`. The guest has no certificates, so the build is signed ad hoc.
7. **Results back.** `tart exec <clone> tar -C ~/results -cf - . | tar -x -C build/ui-tests/<run-id>/` streams the results back, not the read-only share. Curator also brings back an `app-warnings.log` (the app's errors, faults and SwiftUI/AttributeGraph messages) and any crash reports from the guest.
8. **Cleanup.** An EXIT trap stops and deletes the clone and removes the export.
9. **Host guard.** The UI-test target's first build phase fails unless `sysctl -n kern.hv_vmm_present` is `1`, which is true only inside a VM. Curator verified on cameron (value `0`): `error: CuratorUITests only build inside a VM. Run scripts/run-ui-tests-vm.sh.` / `** TEST BUILD FAILED **`, before any test code compiles.
10. **Results recorded.** Changeover's first full run took about 90 s clone-to-delete. Curator's took about 90 s including 32 s of tests. Both recorded host-safety checks after every run: no new crash reports on cameron, the same `lsappinfo` ASNs for the host's GUI apps (Batty included), and only goldens left in `tart list`.

## Open questions to verify in the guest (not answered here)

1. **SwiftPM resolution in the guest.** `BattyKit/Package.swift` depends on `https://github.com/Lakr233/libghostty-spm` (pinned revision `a2565cc…`, which provides `GhosttyKit`, `GhosttyTerminal` and `GhosttyTheme`), plus Sparkle, `gonzalezreal/textual` and `apple/swift-argument-parser`, all from GitHub. Does resolution (and any binary-artifact download libghostty-spm needs) work over Tart's NAT, and how long does it add to each run? Each clone starts with no package cache.
2. **The local-path dependency outside the repo.** `BattyKit/Package.swift` has `.package(path: "../../SlidingTabs")`, which resolves to `~/Developer/brennanMKE/SlidingTabs`, a separate git repo (origin `git@github.com:brennanMKE/SlidingTabs.git`). A `git archive HEAD` of Batty does not include it, so the guest build fails without it. The runner has to export it too, at the right relative path. It should probably be a `git archive HEAD` of SlidingTabs as well, and whether to use its HEAD or a pinned commit needs deciding. Neither Changeover nor Curator had this problem.
3. **Beta variant selection in the export.** `Configuration/Active.xcconfig` is gitignored (`.gitignore:2`), so it is missing from a `git archive`. `Configuration/App.xcconfig:42` includes it optionally (`#include? "Active.xcconfig"`), and the defaults above that line are Prod's (`PRODUCT_BUNDLE_IDENTIFIER = co.sstools.Batty`, `APP_PRODUCT_NAME = Batty`). The `Batty (Beta)` scheme's pre-action takes effect only on the *next* `xcodebuild` invocation (#0280). How should the guest build be forced to Beta: running `scripts/set-environment.sh Beta` in the guest before `xcodebuild`, writing `Active.xcconfig` into the export, or something else? Confirm with `-showBuildSettings | grep PRODUCT_NAME` in the guest (expect `Batty Beta`).
4. **Ad hoc signing of everything in the bundle.** The app is built with `CODE_SIGN_IDENTITY=-`. The "Embed CLI" and "Embed Broker" Run Script phases copy `batty` and `BattyBroker` into `Contents/Resources/bin/` and sign them explicitly only when `CODE_SIGNING_ALLOWED=YES` and `EXPANDED_CODE_SIGN_IDENTITY` is set. Otherwise they print `note: code signing disabled or no identity; embedded … left unsigned`. What signature do the embedded CLI and broker end up with in the guest, and does the app launch?
   - #0401 established that the *unsigned* package's broker cannot register (`SMAppService` → `errSecCSResourcesNotFound`). Whether a bundle signed ad hoc with a resource seal fares differently is unknown. That decides which XPC verbs #0413 can cover in the VM.
5. **Is `run-ui-tests.sh`'s re-sign step still needed?** It was added because Gatekeeper translocated the runner on the host. Curator's guest run needed no re-sign with `CODE_SIGN_IDENTITY=- CODE_SIGN_STYLE=Manual DEVELOPMENT_TEAM=`. Try Batty without it first, and keep it only if the guest shows the same failure.
6. **Prompts specific to Batty.** Batty spawns shells, registers a broker LaunchAgent, and posts notifications. Does any of these raise a prompt in a fresh guest ("Allow in the Background", Notifications, Files and Folders for the shell's cwd) that blocks tests? The guest has no TCC grants and must not accumulate any.
7. **Suite time and memory.** The host suite takes about 10 min. With 6 CPUs and 12 GB, how long does it take in the guest, and does the memory-signal request size (Curator uses guest memory + 4096 MB) hold up for a libghostty build?

## Resolution notes

> 🟢 Resolved 2026-09-23 — `BattyUITests` now runs only inside a disposable Tart VM clone. `./build.sh ui` routes there, a build phase refuses to build the UI-test target on a host, and the first full suite run is recorded in `docs/ui-testing-vm.md`.

## Fix

- **Golden.** `batty-uitest-golden` is cloned from `changeover-uitest-golden`, with nothing Batty-specific installed. The golden record is in the doc.
- **Runner: `tools/run-ui-tests-vm.sh`.**
  - It lives in `tools/`, not in restricted `scripts/`.
  - **Export.** It exports `git archive HEAD` of Batty, plus SlidingTabs at its sibling path, and forces Beta in the guest.
  - **Before it clones.** It waits for a free VM slot and requests memory through the host's memory signal. Before waiting, it sweeps only stale `batty-uitest-<YYYYMMDD>-<HHMMSS>-<pid>` clones whose pid is dead.
  - **Running the suite.** It builds and tests in the guest, passes positional targets through as `-only-testing:`, and pulls results into `build/ui-tests/<run-id>/`. It prints a summary and exits with the test status.
  - **Cleanup.** Cleanup is best-effort, idempotent and signal-safe:
    - errexit is off inside it;
    - kills are bounded;
    - a second signal during cleanup is ignored;
    - it always releases memory, deletes the clone and removes the export.
- **Host guard.** A "Refuse to build on a host Mac" build phase is the first phase of `BattyUITests`. It fails unless `kern.hv_vmm_present=1`.
- **Schemes.** `BattyUITests` has moved out of `Batty (Beta)` and `Batty (Prod)` into a new `Batty UI Tests` scheme, so host `test` / `./build.sh unit` never reach it.
- **Routing and docs.**
  - `./build.sh ui|test` now delegates to the VM runner.
  - `scripts/run-ui-tests.sh` is untouched, but nothing routes to it any more. The guest needed no re-sign step.
  - Doc updates: `docs/ui-testing-vm.md` is new; `docs/README.md` gets an index entry; `tools/README.md`, `BattyUITests/README.md` and `issues/Issues.md` are updated.

- **The broker never connects in the guest** (an ad hoc-signed `SMAppService` bundle). Filed as #0419. This limits which XPC verbs #0413 can cover in the VM.
- **SwiftUI "Geometry action is cycling" fault:** 93 per run. Filed as #0420.
- **Pass status can be green without an `.xcresult`.** A run that passes but fails to pull its results still exits 0, with only a log line.
- **SlidingTabs is exported at its current `HEAD`**, not a pinned commit.
