## Description

Write `docs/themes.md` to document Batty's theme system: where themes come from, how they're loaded, how the user selects one, and how the change propagates to live terminal surfaces.

Depends on `#0076` (which creates the `docs/` folder).

## What `docs/themes.md` must cover

### 1. User-facing summary

- Where themes are selected: **menu bar → Theme**, listing each available theme. The active theme is marked with a check icon.
- Theme selection is persistent (stored in `UserDefaults`).
- Themes apply to **all open terminal surfaces immediately** — no need to reopen tabs.
- New tabs inherit the active theme on creation.

### 2. Theme catalog source

- Themes ship with the **Ghostty theme catalog** (`GhosttyThemeCatalog.allThemes`) which comes from the libghostty SPM dependency. The catalog enumerates `GhosttyThemeDefinition` instances by name.
- A `GhosttyThemeDefinition.toTerminalTheme()` accessor converts to a `TerminalTheme` value type that the surface controller accepts.
- Catalog is read-only at runtime. Adding a theme means adding to the catalog upstream in the libghostty fork (or shipping ad-hoc themes as a future feature — out of scope today).

### 3. User selection and persistence

- `ThemePreference.defaultsKey` (UserDefaults string key) stores the selected theme's display name.
- `BattyCommands` exposes the Theme menu using `@AppStorage(ThemePreference.defaultsKey)` so the menu re-renders when the value changes.
- Selection writes to `activeThemeName` (the `@AppStorage` value) AND calls `store.applyThemeToAllSurfaces(theme)` to push the change live.

### 4. How a new tab picks up the theme

- `TabRuntime.activeTheme()` (private static) reads `UserDefaults.standard.string(forKey: ThemePreference.defaultsKey)`, looks up the matching `GhosttyThemeDefinition` from the catalog, and returns its `TerminalTheme` (or `.default` if missing).
- `TabRuntime.init` passes this theme into `TerminalViewState(theme:)` so the new surface starts in the right theme.
- This runs on every tab creation — no warm cache.

### 5. Live theme application

- `AppStateStore.applyThemeToAllSurfaces(_:)` iterates all sessions → panes → tabs and calls `tab.terminal.controller.setTheme(_:)` (or equivalent libghostty API).
- libghostty repaints the surface with the new colors. Scrollback and running TUIs re-render with the new palette.
- No PTY restart, no NSView teardown — the surface controller handles theme swaps in-place.

### 6. Theme structure

- `TerminalTheme` (from `GhosttyTerminal`) is a value struct containing foreground / background / palette colors (16 ANSI + 240+ extended).
- `GhosttyThemeDefinition.toTerminalTheme()` parses the Ghostty `.toml` (or equivalent) into the typed `TerminalTheme`.
- Naming: theme display names come directly from the Ghostty catalog (e.g. `"Solarized Dark"`, `"Gruvbox"`).

### 7. Settings → Appearance overlap

- Settings → Appearance shows per-app appearance preferences (font size, cursor style, blink). These are NOT theme-related.
- Cursor style settings (`SettingsPreference.resolvedCursorStyle()`) live separately from the theme. They apply to every surface regardless of theme.
- Font size is similarly orthogonal — a single user-wide font size, not theme-tied.

### 8. Where to look in the code

| File | Role |
|---|---|
| `BattyKit/Sources/BattyKit/Theme.swift` | Re-exports / convenience surface for theme types |
| `BattyKit/Sources/BattyKit/ThemePreference.swift` | UserDefaults key + helpers |
| `BattyKit/Sources/BattyKit/TabRuntime.swift` | `activeTheme()` reading the preference |
| `BattyKit/Sources/BattyKit/BattyCommands.swift` | The Theme menu builder + selection action |
| `BattyKit/Sources/BattyKit/AppStateStore.swift` | `applyThemeToAllSurfaces(_:)` propagation |
| `BattyKit/Sources/BattyKit/SettingsView.swift` | Appearance pane (font / cursor — adjacent, not theme) |
| `../libghostty-spm/Sources/GhosttyTheme/...` | Upstream catalog source |

### 9. Adding a new theme (developer workflow)

- v1: themes are baked into libghostty-spm. To add one, update the fork's theme catalog and bump `BattyKit/Package.swift` / `Package.resolved`.
- Out of scope today: user-supplied `.toml` themes loaded from `~/Library/Application Support/Batty/themes/`. Track separately if requested.

## Root cause

Not a bug — a documentation gap. The theme system spans Batty
(`ThemePreference`, `TabRuntime.activeTheme()`,
`AppStateStore.applyThemeToAllSurfaces`, `BattyCommands` Theme menu,
`SettingsView` Appearance pane) and the libghostty-spm fork
(`GhosttyThemeCatalog`, `GhosttyThemeDefinition`, the
`toTerminalTheme()` accessor). A new contributor had no single entry
point describing where the catalog lives, how selection is persisted,
how new tabs pick up the theme, or how live application avoids
tearing down surfaces.

## Fix

- Wrote `docs/themes.md` covering all nine sections from the spec:
  user-facing summary, catalog source (with a file table for the
  `brennanMKE/libghostty-spm` `GhosttyTheme` target), user selection
  and persistence (the single `co.sstools.Batty.themeName` `UserDefaults`
  key), how new tabs pick up the theme via `TabRuntime.activeTheme()`,
  live theme application via `applyThemeToAllSurfaces(_:)`, theme
  structure (`GhosttyThemeDefinition` vs `TerminalConfiguration` vs
  `TerminalTheme`), Settings → Appearance overlap (font/cursor are

## Gotchas

- `BattyKit/Sources/BattyKit/Theme.swift` contains an alternative
  `Theme` / `ThemeParser` / `ThemeStore` set of types that parse
  Ghostty's `.ghostty` config format from disk. **It is not on the
  active selection path** — the runtime flow goes through
  `GhosttyThemeCatalog`, not `ThemeStore`. The parser is still
  exercised by `BattyKitTests/ThemeTests.swift` against a hand-rolled
  fixture; the doc calls it out as a placeholder for the future
  user-themes-on-disk feature.
- `TabRuntime.activeTheme()` reads `UserDefaults` directly at every
  tab construction — there is no warm cache and no `@Observable`
  theme object. Documented explicitly so future readers don't assume
  state lives somewhere it doesn't.
- `applyThemeToAllSurfaces(_:)` does **not** clear the `UserDefaults`
  key when catalog lookup fails. If the user upgrades and the named
  theme is gone, existing surfaces keep their last applied colors and
  new tabs fall back to `TerminalTheme.default`. The doc surfaces this
  reconciliation gap in section 4 and the Quick answer key.
- `TerminalTheme` already has separate light/dark slots, but
  `GhosttyThemeDefinition.toTerminalTheme()` packs the same
  `TerminalConfiguration` into both. macOS appearance-aware theme
  pairs are explicitly listed as out of scope.
- The 0078 spec referenced the fork branch as `batty-delegates`; the
  current pin in `BattyKit/Package.swift` is a `revision:` SHA on that
  fork, which the doc references by SHA-via-`Package.swift` rather
  than by branch name (so it stays accurate if the branch is renamed
  or rebased).
- Visual sign-off (menu order, picker layout) is a UI concern — left
  as `resolved` per CLAUDE.md's "for UI work, mark `resolved` not
  `closed`" rule, though this is a doc PR so the user transition to
  `closed` is mostly a content-review checkpoint.
