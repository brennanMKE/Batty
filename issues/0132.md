## Description

Newly created Terminal Sessions and newly split panes are not receiving keyboard focus. After creating a new session, the user cannot type a command into it until they click into the pane. After splitting a pane, clicking on a sibling pane to focus it also does not consistently work.

These two symptoms likely share a single root cause in how first-responder status is assigned to `TerminalSurfaceView` when the surface is first inserted into the window's view hierarchy, and how click-to-focus is wired on existing panes when the split layout changes.

## Steps to reproduce

1. Launch Batty.
2. Create a new session (sidebar "+" or `Cmd-N`).
3. Without clicking anywhere, try to type a shell command.
4. From the focused pane, create a horizontal or vertical split.
5. Click on the new sibling pane (or back on the original) to try to focus it and type.

## Expected behavior

- A new session's initial pane should be first responder immediately on appear — typing should go straight to the shell.
- After a split, the newly created pane should take focus automatically, and clicking any visible pane should make it first responder so keystrokes go to that pane's surface.

## Actual behavior

- New session appears but keystrokes are dropped (or routed elsewhere) until the user clicks inside the pane.
- After splitting, click-to-focus on sibling panes is unreliable — focus stays on whichever pane held it before the split, or click events do not promote the clicked pane to first responder.

## Notes

- Both symptoms are likely the same bug — file as one issue and split later only if the root causes turn out to be unrelated.
- Likely areas to investigate:
  - `TerminalSurfaceView` (NSViewRepresentable) — `makeNSView` / `updateNSView` and whether `window?.makeFirstResponder(_:)` is called when a new surface is added.
  - Pane creation paths for new sessions vs. splits — whether both call into the same focus-promotion helper.
  - Click / mouseDown handling on the pane's NSView — `acceptsFirstResponder`, `becomeFirstResponder`, and whether `mouseDown(with:)` requests first responder before forwarding to libghostty.
  - See `docs/view-hierarchy.md` for the surface-registry / persistent AppKit host rules that govern how surfaces are reparented; focus assignment must respect that lifecycle.

## Root cause

Two related first-responder gaps with one shape: AppKit does not auto-promote a clicked or freshly-mounted `AppTerminalView` to its window's first responder, and the upstream libghostty-spm `AppTerminalView.mouseDown(with:)` only forwards the mouse position and button press to its `TerminalSurface` — it never calls `window.makeFirstResponder(self)`.

- **Click-to-focus on sibling panes:** clicking on a sibling pane's terminal sends `sendMousePos` and `sendMouseButton` to that surface but leaves the window's first responder pointed at the previously focused pane, so keystrokes continue flowing there. The `windowDidBecomeKey` observer in libghostty-spm only takes effect when `firstResponder === self`, so nothing inside the surface ever bridges the gap.
- **New session no focus on appear:** `SessionDetailView.onChange(of: store.selectedSessionID)` and the new pane's `TerminalPlaceholderView.onAppear` both call `TerminalSurfaceFocuser.focusWhenReady`, but the helper ran one attempt synchronously and then retried once after 50ms. A brand-new session's `AppTerminalView` walks three independent runloop turns before keystrokes can land — placeholder mount creates the view as `isHidden = true`; the placeholder reports its frame via the `PreferenceKey` flow; `TerminalHostStore.updatePlacements` then unhides it. The single 50ms retry could race past the unhide pass, and even when the focus call landed in time, AppKit silently refuses to deliver key events to a hidden view, so a successful `makeFirstResponder` on a still-hidden view became a no-op.

## Fix

- Add `TerminalClickFocusMonitor`, a `@MainActor` singleton-style enum that installs a single `NSEvent.addLocalMonitorForEvents(matching: [.leftMouseDown])` at app launch. On every left mouse-down it hit-tests the window root, walks up to the nearest `AppTerminalView` ancestor, and calls `window.makeFirstResponder(terminal)` if it is not already first responder. The event is returned unmodified, so the libghostty mouse-down path still runs. Started from `BattyAppDelegate.applicationDidFinishLaunching` alongside the existing key-event monitor.
- Expand `TerminalSurfaceFocuser.focusWhenReady` to retry on a 16/50/150/400 ms back-off and to treat a hidden match as "not ready" so the promotion is deferred until `TerminalHostStore.updatePlacements` has unhidden the view. `focus(terminal:)` now reports success/failure so the back-off loop terminates as soon as a visible view is promoted, and a `[weak terminal]` capture ensures a closed/replaced surface does not keep the retry task alive.

The model-side focus follow-up (`tree.focusedPaneID`, the focus-border overlay, the `markActiveTabSeen` bell cascade) is unchanged — it is driven by `PaneView.onChange(of: tab.terminal.isFocused)`, which fires from libghostty's focus delegate the moment `becomeFirstResponder` runs.

## Files changed

- `BattyKit/Sources/BattyKit/Commands/TerminalClickFocusMonitor.swift` — new file. The local `NSEvent` mouse-down monitor that walks the hit-tested view and promotes any `AppTerminalView` ancestor to first responder.
- `BattyKit/Sources/BattyKit/Commands/TerminalSurfaceFocuser.swift` — `focus(terminal:)` returns a `Bool`, skips hidden matches; `focusWhenReady(terminal:)` retries on a staggered schedule with a `[weak terminal]` capture; the rationale for both is documented inline.
- `Batty/BattyApp.swift` — `BattyAppDelegate.applicationDidFinishLaunching` calls `TerminalClickFocusMonitor.start()` next to the existing key-event monitor.

## Gotchas

- `AppTerminalView` is declared `public final class` in libghostty-spm, so the only way to interpose on `mouseDown` from the Batty side is at the event-monitor level — subclassing is closed off. Anyone tempted to "just" override the mouse path will need to revisit `libghostty-spm` itself.
- `NSWindow.makeFirstResponder` on an `isHidden` `NSView` succeeds at the responder-chain level but key events are not dispatched to a hidden view. Without the new "skip hidden matches" guard, the focuser could report success while the user kept typing into the void — exactly the original symptom in a different costume. Treat `isHidden` as a hard signal to wait for the next placement pass.
- The click monitor uses `.leftMouseDown` only. Right-clicks and middle-clicks are left alone so a context-menu invocation on a sibling pane does not steal focus from whatever the user was typing into — revisit only if a future bug reports right-click focus surprises.
- This is a UI-timing fix; it was verified by the `xcodebuild -scheme Batty -destination 'platform=macOS' build` pass and the full `BattyKit` test suite (220 tests). The interactive behaviors — new-session keystrokes landing immediately, click-to-focus on sibling panes promoting correctly — could not be exercised headlessly and need a Mac-app sanity check before closing.

## Re-opened

**Reported by user 2026-05-18:** the original symptom is still present in practice. Creating a new session or a new tab creates the pane with a terminal, but typing does nothing until the user clicks into the terminal with the mouse.

This is exactly the bug the original fix (`86a4f89` — `TerminalClickFocusMonitor` + `TerminalSurfaceFocuser.focusWhenReady` back-off) was supposed to resolve. Click-to-focus on existing sibling panes may now work (the new mouse-down monitor handles that), but the new-session and new-tab auto-focus path is still broken.

**Why the v1 fix didn't take (hypothesis):**

The v1 `## Fix` notes that `SessionDetailView.onChange(of: store.selectedSessionID)` and `TerminalPlaceholderView.onAppear` call `focusWhenReady(terminal:)`, and that the focuser now retries on a 16/50/150/400 ms back-off while skipping hidden views. The hypothesis at the time was that this would outlast the `TerminalHostStore.updatePlacements` unhide pass.

Likely failure modes to check, in order of likelihood:

1. **Wrong terminal handed to `focusWhenReady`.** When a new tab is added to an existing pane, the focus call may be running against the *previously-active* tab's terminal (which then becomes hidden), not the newly-created one. The Focuser correctly skips hidden views — and then never finds the new visible terminal because it was never asked about it.
2. **Focus call fires before the new tab is the active tab.** If `focusWhenReady` runs in the same runloop tick as the tab being marked active, the placement pass hasn't materialized the new view yet and the back-off chain finishes before the view ever becomes visible. The 16/50/150/400ms ladder might still not be enough if `updatePlacements` is throttled or coalesced behind other state updates.
3. **The new-session path doesn't actually call `focusWhenReady` for the right reason.** `SessionDetailView.onChange(of: store.selectedSessionID)` fires when the selection changes — but creating a new session and selecting it may be racy with the view tree mounting the pane. The placeholder's `onAppear` is the other hook; check whether it actually runs for a freshly-created session.
4. **The `TerminalClickFocusMonitor` may be inadvertently competing** — promoting a sibling on first-mouse activate that should have gone to the new pane.

**How to reproduce:**

1. Launch Batty.
2. Create a new session (sidebar `+`, or `Cmd-N`) — without touching the mouse, try to type.
3. Repeat with a new tab in the current pane (`Cmd-T` or the `+` button on the tab bar).

**Acceptance criterion for the fix:** in both reproduction steps above, typing immediately reaches the new terminal's shell with no mouse click required. Click-to-focus on sibling panes (the other half of the original issue) must keep working — don't regress that while fixing the new-session/new-tab path.

## Re-resolution

The actual root cause was none of the four hypothesized timing failures. `TerminalSurfaceFocuser.focus(terminal:)` walked the window view tree looking for the `AppTerminalView` whose `delegate === terminal` (a `TerminalViewState`). That comparison silently stopped matching when `#0125` introduced `TerminalDelegateProxy` as the installed delegate — the delegate is now the proxy, not the state, so `===` is always `false`. The v1 back-off ladder (16/50/150/400 ms) was running every time but finding no view to promote and exhausting itself with no effect. Click-to-focus kept working because `TerminalClickFocusMonitor` uses an `NSView` hit-test and never consulted the delegate. The Focuser had been broken for every tab in the app since `#0125` shipped; v1 of `#0132` did not exercise the focuser in a way that exposed it because the assumption was that the back-off ladder was the missing piece.

Replaces the delegate-keyed view-tree walk with a direct tab-keyed lookup. `TerminalSurfaceFocuser.focus(tab:)` reads `tab.terminalNSView` (the back-reference that `TerminalHostStore.terminalView(for:)` sets when it creates the view) and promotes it directly — no view-tree traversal, no delegate identity step that can fall out of sync if the delegate type changes again. `focusWhenReady` now takes a `TabRuntime` and grows the back-off tail to 16/50/150/400/800 ms so the geometry-settling backstop in `TerminalPlaceholderView` has time to land on slow cold launches. Click-to-focus on existing sibling panes is unchanged — that path lives in `TerminalClickFocusMonitor` and was never affected by the delegate-identity break.

### Files changed

- `BattyKit/Sources/BattyKit/Commands/TerminalSurfaceFocuser.swift` — `focus(terminal:)` and `focusWhenReady(terminal:)` replaced with `focus(tab:)` and `focusWhenReady(tab:)` that look up the `AppTerminalView` via `TabRuntime.terminalNSView` instead of walking the view tree by delegate identity. Back-off ladder extended to 800 ms. Comments document the `#0125` delegate-proxy regression so the lookup does not slide back.
- `BattyKit/Sources/BattyKit/Views/SessionDetailView.swift` — call site updated to pass the active `TabRuntime` instead of `activeTab.terminal`.
- `BattyKit/Sources/BattyKit/Views/PaneView.swift` — three call sites (`.onAppear`, `.onChange(of: pane.activeTabID)`, `.onChange(of: isPaneFocused)`) updated to pass `tab` instead of `tab.terminal`.

### Tests added

- `BattyKit/Tests/BattyKitTests/TerminalSurfaceFocuserTests.swift` — three smoke tests covering the early-return predicates of `focus(tab:)`: no `terminalNSView`, no `window`, `isHidden`. They guard against regressing the lookup back to delegate-identity matching. The "view exists, is attached to a window, is visible, gets promoted" path requires an attached `NSWindow` and a real layout pass; that's exercised interactively, not in unit tests.

### Gotchas

- The visible behavior — `Cmd-N` puts a new session into focus and keystrokes land in the new shell; `Cmd-T` puts a new tab into focus and keystrokes land in the new shell; clicking a sibling pane still promotes it to first responder — could not be verified headlessly. `xcodebuild ... build` passes and the full BattyKit test suite (254 tests) is green; the interactive sanity check has to happen in a running app.
- The new lookup depends on `TabRuntime.terminalNSView` being set before `focus(tab:)` runs. That assignment happens inside `TerminalHostStore.terminalView(for:)`, which is called from `TerminalPlaceholderView.body`. For the brand-new-tab and brand-new-session paths, the focuser's first call will run before the placeholder mounts (returns `false`), and the back-off ladder catches it once `terminalView(for:)` has been called and the placement pass has run. The 16/50/150/400/800 ms tail is intentional and load-bearing — don't trim it without re-verifying cold launch.
- If a future change replaces `TerminalDelegateProxy` with another wrapper, or introduces an analogous indirection on any other identity-keyed lookup in the focus path, the existing tests still pass (they only cover the early-return predicates). The defense against another silent regression is the inline comment in `TerminalSurfaceFocuser` plus this resolution note — both point at the `delegate === terminal` failure mode that `#0125` introduced.
