## Description

Phase 4 of the #0234 multi-window umbrella: replace the singular `Window(mainWindowTitle, id: "main")` scene in `Batty/BattyApp.swift` with `WindowGroup(for: WindowID.self)` and add the user-facing New Window action, per `docs/multi-window-design.md` §4 and §7.

Scope:

- Scene: data-driven `WindowGroup` whose presented value is the stable `WindowID`; `defaultValue:` keeps cold start at exactly one window; `ContentView(windowID:)` resolves its `WindowRuntime` via `AppStateStore.windowRuntime(for:)`. Help and Settings scenes unchanged.
- `ShortcutAction.newWindow` appended (rawValue namespace is append-only) with default binding Shift-Cmd-N — verified free: Cmd-N is `.newSession` (`ShortcutAction.swift:59`), bell feed is Shift-Cmd-B (`ShortcutAction.swift:87`). Automatically rebindable in Settings → Keyboard.
- Menu: "New Window" above "New Session" in the existing `CommandGroup(replacing: .newItem)` in `Commands/BattyCommands.swift`, using `@Environment(\.openWindow)`. The NSEvent-monitor path (`BattyShortcuts`) dispatches through a single captured open-window hook on `AppStateStore` (`@ObservationIgnored`, same wiring style as `onAllSessionsClosed`).
- `BattyShortcuts.mainWindowIsKey()` replaced by the registry-based content-window check (the `"main"`-identifier heuristic breaks under `WindowGroup`); shortcut dispatch targets the key window's `WindowRuntime`.
- A new window contains one fresh session (`Session 1` in that window's numbering) with its shell in `$HOME` — no cross-window cwd inheritance.

## Acceptance criteria

- Shift-Cmd-N (and File → New Window) opens a second window with its own sidebar, selection, and working terminal; Cmd-N still creates a session in the key window; the chord is rebindable in Settings.
- All existing shortcuts dispatch against the key window only; Settings/Help windows still bypass main-window shortcuts.
- `scripts/build.sh unit` passes; UI suite updated for the new action and passes; new UI test covers New Window.

## Root cause

Not a bug — Phase 4 of the #0234 umbrella, and the phase that first makes multi-window exist. Starting state: `Batty/BattyApp.swift` used a singular `Window(id: "main")` scene, so no second window could be opened by any means.

## Fix

Scene swapped to `WindowGroup(for: WindowID.self)` with a `defaultValue:` closure (cold start = one window); `ContentView(windowID:)` → `RootWindowView(windowID:)` resolves its per-window `WindowRuntime` via `AppStateStore.windowRuntime(for:)`, which is now lookup-first-then-lazily-create (the single convergence point for launch, New Window, and future restoration). `WindowRuntime.init` seeds `Session 1` (shell in `$HOME`) when its session list is empty, so each new window gets its own session with no cross-window cwd inheritance. `ShortcutAction.newWindow` appended (append-only rawValue) with default Shift-Cmd-N, automatically rebindable in Settings. "New Window" menu item added above "New Session" via `@Environment(\.openWindow)`; the NSEvent-monitor path (`BattyShortcuts`) opens windows through a captured `AppStateStore.openWindowAction` hook (set in `OpenWindowHookInstaller.onAppear`). The `"main"`-identifier key-window heuristic was replaced by an `NSWindow↔WindowID` registry (`nsWindowMap`, populated by `WindowIDRegistrar` via a deferred `DispatchQueue.main.async` in `updateNSView`); shortcut dispatch now targets `keyWindowRuntime()`. Settings/Help scenes omit the registrar, so they correctly fall through to macOS without consuming main-window shortcuts.

## Review

Reviewed by claude-opus-4-8, one round, approved first pass. The orchestrator raised the mutate-during-view-init question (lazy `windowRuntime(for:)` creation from view `init`); the reviewer resolved it in the implementation's favor with a rigorous observation-rules analysis: `windows` is `@ObservationIgnored`, the call is idempotent and MainActor-serialized, and the constructed runtime reads only `let` properties — no "modifying state during view update" hazard. The reviewer independently re-ran the unit gate and judged the written UI test well-formed. Four non-blocking notes captured in Gotchas.

This is a UI-automation/accessibility infrastructure issue on the Mac mini, likely needing an Accessibility/Automation permission grant for the test runner. #0240 (the dedicated full-UI-suite phase) must clear this before it can run the suite.

## Gotchas

- **Menu-item / command-palette clicks still target `windows[0]`, not the key window.** `BattyCommands` (New Session, Session/Pane/Tab menus) and `CommandPaletteView` call `store.…` which forwards to `windows[0]`. The keyboard path is correct (the NSEvent monitor routes through `keyWindowRuntime()`), so the acceptance criteria hold, but menu/palette dispatch to the focused window is unfinished. This overlaps #0239's `keyWindowRuntime` work — flagged in #0239's Notes so it isn't lost.
- **`unregisterNSWindow` is defined but never called** — window-close teardown (and the matching `releaseHost` from #0236) is #0239 scope. A stale map entry is harmless: a deallocated window is never `NSApp.keyWindow`.
- **`themeChrome` is shared across windows** — pre-existing single-chrome design; per-window theming isn't in the design doc.
- **Sidebar visibility is still global** (`SidebarPreference.hiddenKey`) — per-scene `@SceneStorage` migration is explicitly #0238 scope.
- **Environment hygiene for UI tests:** a booted iOS simulator silently breaks the macOS test control session (`test runner hung before establishing connection`). If `scripts/build.sh unit` ever "hangs," check `xcrun simctl list devices booted` before suspecting code — it is almost certainly environmental.
