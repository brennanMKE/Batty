# 0681 — The website's deploy docs are stale and contradict `scripts/deploy-website.sh`, and nothing can hold unreleased pages off the server

## Description

Child of #0680, first in order. Before the agent pages land on `main`, the website needs one documented deploy process and a way to keep files that are on `main` off the live server until the release that ships them. Today there are two conflicting deploy processes and no hold mechanism, so a 1.4.x deploy from `main` would publish the 1.5.0 agent pages early.

### Current state (checked against `main` at `3a7c12ec`)

- `website/README.md` "Deployment" (lines 33-44) still suggests GitHub Pages, Netlify or S3. The process actually in use, `rsync -avz website/ photon:/var/www/vhosts/batty.sstools.co/` with a dry run first and **never `--delete`**, appears only under "Background images" (lines 82-89).
- `scripts/RELEASE.md` step 7 (lines 177-187) says to deploy with `scripts/deploy-website.sh`, which rsyncs to `$BATTY_EC2_HOST:$BATTY_EC2_PATH` **with `--delete`** (`scripts/deploy-website.sh:14, 101-106`). That contradicts the README's rule: `--delete` would remove older DMGs and catalog images that exist only on the server.
- "Per-release workflow" step 4 (`website/README.md:62`) says only "Push to the hosting destination."
- No exclude list exists. `deploy-website.sh` excludes only `.DS_Store`, `*.swp` and `*.bak`; the README's rsync excludes nothing (it also copies `website/README.md` and `website/downloads/README.md` to the server).

## Expected behavior

1. `website/README.md` "Deployment" describes the one real process: preflight checks, a dry run, the real rsync to `photon:/var/www/vhosts/batty.sstools.co/`, never `--delete`, the user's go-ahead each time, and the post-deploy `curl -sI` checks. The stale GitHub Pages/Netlify/S3 text goes. The "Background images" section links to it instead of repeating the rsync commands.
2. A committed hold list, `website/.deploy-hold` (rsync `--exclude-from` format, one path per line, with a header comment), names files that are on `main` but must not be deployed yet. Both rsync commands pass `--exclude-from=website/.deploy-hold` and also exclude `README.md` files and `.deploy-hold` itself. Initially it lists the paths #0680's children will add: `docs/` (every agent-facing page, snippet, CLI reference, skill zip and marketplace lives under it, #0680 Decisions 2026-11-19), `llms.txt` and `llms-full.txt`. Each child that adds a held file confirms it is listed.
3. A small check, `tools/check-website-hold.py` (stdlib Python, run with `python3 -I`, with a self-test like `tools/check-backgrounds-selftest.py`), exits non-zero when any deployable page (`website/*.html`, `sitemap.xml`, `robots.txt`) links to a held path. It joins the README's pre-deploy checks.
4. `scripts/RELEASE.md` step 7 and `scripts/deploy-website.sh` agree with the README: no `--delete`, the hold list applied. **`scripts/` is a restricted area (`AGENTS.md`): the plan must stop and get the user's confirmation before changing either file.** If the user declines, the README says which process wins and the issue records the decision.
5. "Per-release workflow" in `website/README.md` gets an explicit deploy step that points at the Deployment section. Later children (#0682-#0688) add their generator `--check` and regeneration steps there.

## Acceptance criteria

1. `git grep -n -e "--delete" website scripts/RELEASE.md scripts/deploy-website.sh` finds no rsync that uses it (or, if the user declined the `scripts/` change, the README states the decision and #0681's Work log records it).
2. A dry run with the documented command lists no path from `website/.deploy-hold` and no `README.md`.
3. `python3 -I tools/check-website-hold.py` exits 0 on `main`, and its self-test shows it exits non-zero for a page that links `docs/index.html` while `docs/index.html` is held.
4. The README's Deployment, Background images and Per-release workflow sections name one process.
