# 0401 — An unsigned Beta package cannot register its XPC broker (`SMAppService` rejects it with `errSecCSResourcesNotFound`), so `batty-beta` is unusable on a fresh install — and there is no distributable Beta artifact for a second Mac

| | |
|---|---|
| **Status** | open |
| **Module** | Build / Settings / Docs |
| **Platform** | macOS |
| **First seen** | 2026-09-08 |

## Description

The default `./build.sh package` output — the build every Beta user installs first — ships a broker LaunchAgent that macOS refuses to register, so the entire XPC surface (`batty-beta ping`, `status`, `list`, `notify`, the #0361 connect dance) is dead on arrival. The reported symptoms, from the user's screenshot of Batty Beta's Settings:

> The operation couldn't be completed. Codesigning failure loading plist: co.sstools.Batty.beta.broker.plist code: -67056

shown in red under the Broker Agent row, and in a terminal:

```
$ batty-beta ping
batty: broker unreachable
```

(exit 2, `XPCExitCode.brokerUnreachable`, `BattyKit/Sources/BattyXPCCore/XPCExitCode.swift:18`). The Command-Line Tool row in the same Settings window shows `batty-beta` installed with a green check — the symlink half of the install (`CLIInstaller`, `SettingsView.swift:298`) is signing-independent and works. Only broker registration fails.

**This answers a question the repo explicitly recorded as open.** `scripts/build-beta.sh`'s header, "THE SIGNING QUESTION" (`scripts/build-beta.sh:18-46`), documents that the default build is unsigned — `CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO` (`:20-24`, set at `:237`) with only the ad-hoc arm64 signature `swift build` applies to the embedded CLI and broker — and says at `:32-40` that whether launchd/`SMAppService` will accept that ad-hoc signature "is an OPEN QUESTION". #0279's Verification section likewise lists "whether an ad-hoc signature satisfies launchd for the Beta agent" as the open question that "decides whether `--sign` is ever needed". This report is the answer: **it will not.** The unsigned package's broker cannot register, so `--sign` is needed — exactly once per install (see below).

### Mechanism

- `./build.sh package` delegates to `scripts/build-beta.sh` (`build.sh:87-90`). Unless `--sign` is passed, the build runs with `CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO` (`scripts/build-beta.sh:237`), and the "Embed CLI" / "Embed Broker" Run Script phases skip their explicit `codesign` step when `CODE_SIGNING_ALLOWED` ≠ `YES` (both phases in `Batty.xcodeproj/project.pbxproj` print `note: code signing disabled or no identity; embedded broker left unsigned`). What remains on the embedded binaries is only the ad-hoc signature `swift build` applies so arm64 code can run at all; the app bundle itself carries no Developer signature.
- The Settings "Register" button (`SettingsView.swift:443-445`) calls `BrokerAgentController.register()` (`BattyKit/Sources/BattyKit/Settings/BrokerAgentController.swift:94-104`), which calls `SMAppService.register()` on `SMAppService.agent(plistName: "co.sstools.Batty.beta.broker.plist")`. The thrown error's `localizedDescription` is stored in `lastErrorDescription` (`:100`) and rendered in red in the row (`SettingsView.swift:436-439`) — that is exactly the screenshot's text, produced by `SMAppService` itself.
- **`-67056` is `errSecCSResourcesNotFound`** — verified against the SDK, not guessed: `<Security/CSCommon.h>` in `MacOSX.sdk` declares `errSecCSResourcesNotFound = -67056, /* code has no resources but signature indicates they must be present */` (`CSCommon.h:80`, between `errSecCSResourcesNotSealed = -67057` and `errSecCSResourcesInvalid = -67055`). It is a Security-framework static-code-validation error: the code object being evaluated carries a signature whose CodeDirectory implies a sealed resource envelope, but no valid `_CodeSignature/CodeResources` seal covers the bundle. That is precisely the state the unsigned package is in — ad-hoc signatures present on the Mach-Os inside an app bundle that has no resource seal — so `SMAppService`'s code-signing validation of the agent fails while "loading" the plist's `BundleProgram`, before launchd ever gets a registration. #0270 recorded the general rule ("launchd refuses to start an improperly signed agent — surfacing as an opaque registration failure"); this is that failure with its exact error code attached.
- Which specific code object Security was validating when it returned `-67056` (the `.app` bundle wrapping the `BundleProgram`, or the broker Mach-O evaluated in bundle context) is **not pinpointed** — `SMAppService`'s message names only the plist. The conclusion doesn't depend on it: the unsigned default cannot produce a registerable agent, and one `--sign` build demonstrably can (Notes).

### 1. The immediate fix is known and low-risk — but deliberately not the default

One `--sign` build fixes it: `./build.sh package --sign` signs the bundle and both embedded binaries with the project's Automatic signing identity. The constraint that makes this a considered act rather than a default is the certificate-revocation history: `scripts/build-beta.sh:239-241` prints, on every `--sign` run, "This should be rare — once per Beta install, not per code change. Repeated signed local builds are what revoked the cert before (see issues/0265.md)", and the header (`:26-30`) states the project's Developer ID certificate "was revoked once already by repeated *signed* local builds against `CODE_SIGN_STYLE = Automatic`". [#0265](0265.md)'s own record of that incident sits in its "Effort data" section: the single most expensive line in the RemoteControl experiment's whole session ($27.43) was "a **code-signing incident unrelated to the experiment** — repeated *signed* local builds against an Automatic-signing project. Avoidable entirely with `CODE_SIGNING_ALLOWED=NO` on repeated local builds." That history is why the script's recommended cadence (`:43-46`) is `--sign` **once per Beta install**, then unsigned builds for every further code change — a signed build belongs to an install, not to iteration.

### 2. The distributable-artifact gap

There is no way to produce a Beta `.dmg`. `scripts/release.sh` builds, Developer ID-signs, notarizes, staples, and verifies a DMG — but it is hard-coded Prod-only (`SCHEME="Batty (Prod)"`, `scripts/release.sh:18`; output `dist/Batty-<sha>.dmg`), and its notarization step (`xcrun notarytool submit`, `:467`) submits to Apple, which `CLAUDE.md` forbids running autonomously. So a user wanting to test Beta on a second Mac today copies `beta-build/Products/Batty Beta.app` by hand and clears quarantine with `xattr -dr com.apple.quarantine`. Options, deliberately not decided here (the decision belongs to implementation, with trade-offs written down, per the #0332 pattern):

- **Extend `release.sh` (or add a sibling `release-beta.sh`) to produce a Beta DMG.** Reuses the proven pipeline shape; `scripts/` is a restricted area (`CLAUDE.md`), so it needs explicit user sign-off either way. Sub-question: with or without the notarize step.
- **A signed-but-not-notarized DMG plus documented `xattr` instructions.** No Apple submission, no notary throughput consumed, no per-run approval. Cost: Gatekeeper on the second Mac still treats the app as unidentified (a non-notarized signature does not pass quarantine), so the `xattr -dr` step remains — it just becomes a documented, packaged flow instead of folklore. Note also that `--sign` uses the *Automatic* identity, which resolved to **Apple Development** (not Developer ID) on the sanctioned rebuild (Notes) — fine for local installs, but a distribution-shaped artifact may want the Developer ID identity `release.sh` uses.
- **Notarize Beta too.** Gives second-Mac installs the same first-launch experience as Prod. Costs: needs its own explicit approval each time (the standing shared-state rule), and consumes notary throughput on throwaway test builds.

### 3. Are the defaults right?

`./build.sh package` defaulting to unsigned optimizes for iteration speed and certificate safety — correctly, for the routine case. The cost is that the **first** build a user installs is the one configuration that cannot work, and the only warning is a conditional stdout hint at build time (`scripts/build-beta.sh:278-282`: "Whether that's enough for launchd to start the bundled LaunchAgent is not yet known… only re-run with `--sign` if the broker never registers") — text that (a) is now known to be wrong in its uncertainty, and (b) scrolls away long before the user hits the Settings error. Considerations, again laid out rather than decided:

- **Update the messaging to state the known answer.** Cheapest, certain: the script's header (`:32-40`), its unsigned-build epilogue (`:278-282`), and the `--help` text all still say "not yet known"/"try this build first". They should say: the unsigned build's broker *will not register*; `--sign` once per install is required for a working `batty-beta`.
- **Fail loudly / warn unconditionally on unsigned builds** — e.g. print a prominent "this build's broker cannot register; run `--sign` once for a fresh install" instead of the conditional hint. Keeps the safe default, removes the trap.
- **Detect a fresh install and default to `--sign` for it** (e.g. when `/Applications/Batty Beta.app` is absent). Automates the recommended cadence, but couples the build machine's state to a guess about the install target, adds a code path to a deliberately simple script, and — worst case — re-signs more often than the cadence intends, which is the exact hazard the default exists to prevent. The revocation history argues for keeping signing an explicit human act.

### 4. Diagnosability: exit 2 conflates four different problems

`batty-beta ping` says only "broker unreachable" (exit 2) for at least four states with different fixes: (a) agent never registered, (b) registration attempted but **rejected** (this issue's `-67056`), (c) registration parked in `requiresApproval` awaiting Login Items approval, (d) agent registered and healthy per launchd but not answering (wedged). What the code can actually tell apart today, checked before proposing anything:

- `BrokerPingClient` collapses every failure into `Outcome(reachable: false)`: interruption, invalidation, proxy error, and the wait timeout all finish the same value (`BattyKit/Sources/batty/BrokerPingClient.swift:28-29`, `:32-34`, `:43`). `BrokerAppEndpointClient` does the same into `.unreachable` (`BrokerAppEndpointClient.swift:30-46`, `:53`) — its one extra distinction (`endpoint(nil)` vs `.unreachable`, `:12-15`) is about the *app*, not the broker. `AppConnectDance.Failure.brokerUnreachable`'s own doc comment already acknowledges the conflation: "agent not registered, or `SMAppService`'s `requiresApproval` state" (`AppConnectDance.swift:16-18`).
- Distinguishable **in principle** without new IPC: an immediate connection invalidation (nobody owns the Mach service name — launchd has no registration: states a/b/c) versus a timeout on a resumed connection (name owned, no reply: state d). The handlers are already separate closures; they just finish identical values. Splitting them would let exit 2's message say "broker not registered — open Batty Beta's Settings → Broker Agent" versus "broker registered but not answering", which is the fix-relevant fork.
- **Not** distinguishable from the CLI: a/b/c from each other. `SMAppService.agent(plistName:)` resolves against the *calling* bundle (#0270's binding constraint), and the CLI is a bare Mach-O — it cannot query registration state or the app's `lastErrorDescription`. Distinguishing "rejected with `-67056`" from "never registered" is knowledge only the app has; the CLI can at most point at Settings, where the real error already renders. The exit-code vocabulary has precedent for splitting failure modes when the fix differs (`XPCExitCode.swift`: 3, 6, and 7 all exist for exactly that reason — #0361), but a new code is only worth it if scripts need the distinction; a better stderr message may be enough.

## Steps to reproduce

1. `./build.sh package` (no `--sign`) and install: `cp -R "beta-build/Products/Batty Beta.app" /Applications/`.
2. Launch Batty Beta, open Settings, use the Command-Line Tool row to install `batty-beta` (succeeds, green check).
3. In the Broker Agent row, click Register.
4. `batty-beta ping` in any terminal.

## Expected behavior

- A fresh Beta install ends with a working `batty-beta` — either because the documented/scripted install path produces a registerable broker, or because the failure states plainly what to do (one `--sign` build) at the moment the user hits it.
- `scripts/build-beta.sh`'s header, epilogue, and `--help` no longer describe the ad-hoc-signature question as open — they state the answer this report established.
- There is a decided, documented story for getting a Beta build onto a second Mac (one of §2's options, or an explicit "copy + `xattr`" doc), so the artifact gap is a choice rather than an accident.
- The user-facing failure is diagnosable: at minimum, "broker unreachable" points somewhere actionable; ideally the not-registered vs not-answering fork (§4) is distinguished where the code can honestly tell.

## Actual behavior

Registration fails with `Codesigning failure loading plist: co.sstools.Batty.beta.broker.plist code: -67056`; every XPC verb exits 2 with `batty: broker unreachable`; the only guidance anywhere is build-time stdout that still calls the outcome unknown; and no Beta artifact suitable for another Mac exists.

## Notes

- **The on-disk failing state no longer exists.** By investigation time (2026-09-08), both `beta-build/Products/Batty Beta.app` and `/Applications/Batty Beta.app` had been replaced by the one sanctioned `--sign` rebuild: `codesign -dvv` shows `Authority=Apple Development: Brennan Stehling`, `TeamIdentifier=XV8BAAVZ6V`, signed 2026-09-08 17:14, with a full `_CodeSignature/CodeResources` seal on the bundle and a real (non-ad-hoc) signature on `Contents/Resources/bin/BattyBroker`. The unsigned failure above is therefore reconstructed from the screenshot text plus the script's defaults, not re-observed against the current install. Whether the signed copy's broker actually registers and answers `batty-beta ping` is the user's runtime verification to report.
- **The `--sign` identity is Apple Development, not Developer ID** (previous bullet's `codesign` output). For a local install that's fine; it matters only for §2's distribution options, where `release.sh` deliberately uses the Developer ID identity (`scripts/release.sh:28`).
- **No user-facing doc covers this failure.** The in-app Help pages (`BattyKit/Sources/BattyKit/Help/01-overview.md` … `09-third-party-licenses.md`) never mention the broker; `docs/beta-teardown.md` covers removal only (its unregister-before-delete ordering, from #0270) and says nothing about a broker that won't register in the first place. The Settings row's own caption (`SettingsView.swift:433`) correctly says registration state isn't health, but nothing anywhere says what `-67056` means or that `--sign` is the fix.
- The error text renders via `BrokerAgentController.lastErrorDescription` → `SettingsView.swift:436-439`; it is `SMAppService`'s own `localizedDescription`, not Batty copy — so "fixing the message" for §4 means adding Batty-side interpretation next to it, not editing it.
- `-67056` arithmetic check: `0xFFFEFA10` as `OSStatus`. Neighbors in `CSCommon.h` (`errSecCSResourcesNotSealed = -67057`, `errSecCSResourcesInvalid = -67055`) are the same resource-seal family, consistent with the unsigned-bundle reading.
- #0270's Gotchas warned that `--timestamp=none` and the ad-hoc `bin/batty` signature would surface later at notarization (#0273 fixed the Prod path); this issue is the same underlying gap surfacing on the Beta *install* path instead.
