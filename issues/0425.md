## Description

#0354 moved the LM Studio dashboard's "wait, then `SIGKILL`" reap off the main actor. `tearDown()` now sends `SIGTERM` and then:

- hands the bounded wait and escalation to a `Task.detached(priority: .utility)` (`scheduleTeardownReap`, `BattyKit/Sources/BattyKit/Runtime/LMStudioDashboardPaneContent.swift:695-702`);
- records each `(process, label)` in the content's own `pendingTeardownReaps` (`:142`).

A detached task may never run once the app starts exiting. So the quit path doesn't rely on it:

1. `BattyAppDelegate.applicationWillTerminate` (`Batty/BattyApp.swift:113-138`) calls `window.tearDownAllPaneContentSynchronouslyForQuit()` for every entry in `AppStateStore.shared.windows`.
2. That method (`BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift:760-767`) walks `sessions` → `tree.allPanes` and calls `waitForDeferredTeardown()` on any content that conforms to `DeferredTeardownWaiting` (`LMStudioDashboardPaneContent.swift:775-797`).

That walk can only reach content that is **still in the model** at quit time. Every other path that tears down a dashboard removes the content from the model right away. After that, its pending reap is held only by the detached task, and the quit path has no reference to it:

- **Closing a pane** (`closePane`, `WindowRuntime.swift:628-660`), **its last tab** (`closeTab`, `:378-400`), or **its session** (`removeSession`, `:233-270`) calls `tearDownNonTerminalContent(in:)`, then removes the pane from the tree or the session from `sessions`.
- **Closing a window** runs `RootWindowView`'s `windowWillClose` teardown. It calls the plain `runtime.tearDownAllPaneContent()` (`BattyKit/Sources/BattyKit/Views/RootWindowView.swift:221`), not the synchronous variant, and then `store.removeWindow(id:)` (`:233`). `removeWindow` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:181-189`) drops the `WindowRuntime` from `windows`.

### When this orphans a child

A child that ignores `SIGTERM` leaks when the app exits during its reap window. That window is up to `teardownWaitBound` (0.5 s) plus up to 0.5 s after the `SIGKILL`, so about 1 s per stream. Two cases:

1. **Closing a dashboard pane, tab, session or window and then quitting within about 1 s.** Unlikely.
2. **Closing the last content window.** This is more likely than the original report assumed. `removeWindow` calls `terminateIfLastContentWindowGone()` (`AppStateStore.swift:260-281`), which schedules `terminateHandler()` (`NSApp.terminate(nil)`) on the **next main run-loop turn** via `DispatchQueue.main.async`.
   - By then the window is already gone from `windows`, so `applicationWillTerminate` walks nothing, and the detached reap has had at most one run-loop turn.
   - The same applies to closing the last session of the only window: `onAllSessionsClosed` closes the window and goes down the same path.
   - So when you close the only window while it holds an LM Studio dashboard, whether a `SIGTERM`-ignoring `lms` child gets reaped comes down to the detached task's bounded poll racing process exit.

Overall likelihood is still low, because `lms log stream` normally dies on `SIGTERM`. The escalation exists for the case where it doesn't, and in that case the child is orphaned onto launchd. That is the outcome #0354's quit-path review round was meant to prevent.

## Expected behavior

The app never exits while a subprocess reap from any teardown path is still pending. Quitting, including the implicit quit when the last window closes, synchronously drains every outstanding reap, bounded exactly as `reapAfterTerminate` bounds it today, whatever model object once owned the process.

Proposed fix: a process-wide registry of pending reaps.

- `scheduleTeardownReap` registers the `(process, label, bound)` there, not only in the content's own array, and the detached task deregisters it when it finishes.
- `applicationWillTerminate` drains the registry synchronously, after the per-window walk or instead of it.
- Everything in the registry is lock-protected and `nonisolated`, like `AppXPCCoordinator`'s termination state, so the detached tasks can deregister off the main actor.
- The registry makes `DeferredTeardownWaiting` and the per-content `pendingTeardownReaps` array redundant for the quit path. Consider folding them in.
- #0422's Git Status fix defers its own subprocess wait off the main actor, so it should register in the same place. Then there is one drain point for every deferred reap, not one protocol conformer per kind.

Test: close a window (or a pane) holding a dashboard whose fixture children ignore `SIGTERM`. Before the detached reap completes, drain the registry the way the quit path does. Both children must be dead when it returns.
- Mutation-verify that skipping the drain makes the test fail.
- Use a readiness-handshake fixture (see #0424) so the `SIGTERM`-ignoring child is really ignoring it.

## Resolution notes

> 🟢 Resolved 2026-09-23 — quitting now drains every pending subprocess reap in the process, including ones left by a pane, session or window closed just before quit (and the close-the-last-window quit), not just content still in the window model.

## Root cause

The quit-path wait from #0354/#0422 walked only `AppStateStore.windows`. Closing a pane, tab or session tears content down and removes it from the tree; closing a window also calls `removeWindow`, and closing the last content window terminates the app on the next turn. In all of these, the detached reap is unreachable by the time `applicationWillTerminate` runs.

## Fix

- New `PendingTeardownReapRegistry` (`nonisolated final class`, `NSLock`-guarded, `.shared` plus an injectable instance for tests). It is not an actor because the drain must block `applicationWillTerminate` synchronously.
- `LMStudioDashboardPaneContent` and `ProcessGitStatusScanner` register when scheduling a detached reap and deregister when it completes. `applicationWillTerminate` calls `drainSynchronously()` after the existing per-window walk. The drain snapshots under the lock and reaps outside it; its total is the sum of per-entry worst cases (~1.0 s per SIGTERM-ignoring LM Studio stream, ~0.6 s per `git`), near zero for cooperative children.
- The per-window walk is kept. The drain routinely re-polls entries the walk already handled; re-reaping an exited process returns immediately.
