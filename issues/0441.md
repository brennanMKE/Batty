## Description

After a full-package `swift test --parallel` run of `BattyKit`, `sleep 60` children spawned by test fixtures sometimes stay alive with `ppid` 1. That means the test process exited while they were still running, and launchd adopted them. This was seen once during #0429's work: two processes, and a repeat run straight afterwards was clean (#0429's Notes, "Orphaned-process check"). They weren't from the LM Studio tests, which #0429 hardened and checked clean over many filtered and full runs. A leaked child ignores `SIGTERM` in several fixtures, so it runs for its full 60 s and is still alive after the run reports a result.

Work: audit **every** child-spawning test for a path where the child can outlive the test. Route them all through one shared kill-and-reap helper, and make sure every `sh -c` fixture `exec`s its long-running command, so no grandchild survives when `sh` is killed.

## Premise check (read-only, on `main` at `3e8e7236`)

`grep -rn '/bin/sh\|/bin/sleep\|exec sleep\|posix_spawn' BattyKit/Tests` lists every child-spawning test. Each one is covered below.

**`sleep 60` spawners.** Only these can produce the observed orphans:

| Site | Fixture | Leak path found |
|---|---|---|
| `PendingTeardownReapRegistryTests.swift:104` `drainSynchronouslyReapsEveryRegisteredEntryIndependently` | 2 × `trap '' TERM; echo ready; exec sleep 60` | **Yes.** The `for` loop at `:107-110` runs `try process.run()` on each fixture before the `defer` at `:111` is registered. If the second `run()` throws, the first child is never killed. It ignores `SIGTERM`, so it lives 60 s and outlives the test process. The readiness wait at `:109` is also a bare `#expect`, which `docs/async-test-seams.md` §4 forbids. |
| `PendingTeardownReapRegistryTests.swift:79` `drainSynchronouslyKillsAndReapsARegisteredSigtermIgnoringProcess` | stubborn, `exec sleep 60` | The readiness wait at `:83` is a bare `#expect`, and the `defer` at `:85` is registered after it. Today nothing between them can throw, so this isn't a live leak. It is the same shape #0430 converted to `guard` in `ProcessGitStatusScannerTests`, though. |
| `PendingTeardownReapRegistryTests.swift:43` `registerThenDeregisterLeavesNothingPending` | `/bin/sleep 60` directly | None. The `defer` comes straight after `run()`. |
| `ProcessGitStatusScannerTests.swift:385`, `:450`, `:484` | stubborn `makeStubbornProcess()` (`:375-383`), `exec sleep 60` | Readiness is already a `guard` whose failure branch kills and reaps the child (#0430). Each `defer` does `kill(pid, SIGKILL)` without `waitUntilExit()`. That can't leave a *live* child, but it isn't the same helper the other files use. |
| `LMStudioSIGTERMIgnoringFixture.swift:45-46`, `LMStudioDashboardPaneContentTests.swift`, `LMStudioDashboardWiringTests.swift` | `exec sleep 60`, with and without the TERM trap | #0429 audited and hardened these. Two identical file-private `killAndReap(_:)` helpers exist (`LMStudioDashboardPaneContentTests.swift:1257`, `LMStudioDashboardWiringTests.swift:424`). They're the natural seed for the shared helper. |

**Other spawners.** None of these is `sleep 60`, so none could have produced the observed orphans. They're in scope for the same helper, since each has the same class of leak:

| Site | Fixture | Leak path found |
|---|---|---|
| `ProcessGitStatusScannerTests.swift:330`, `:509`, `:534` | 2 × `/bin/sleep 30` | **Yes.** `try processA.run()` then `try processB.run()` (`:334-335`, `:513-514`, `:538-539`) come before the `defer`. If B's `run()` throws, A is left running for 30 s. |
| `ChildProcessReadinessTests.swift:25` | `exec sleep 30` | `defer { process.terminate() }` sends SIGTERM and doesn't reap. The child has no trap, so it dies. Low risk. |
| `ChildProcessReadinessTests.swift:11`, `:45` | short `echo` children | None. |
| `ProcessInspectorTests.swift:46`, `:121`, `:318`; `ProcessStatusPaneContentTests.swift:286`, `:549`, `:570`, `:681` | `/bin/sleep` for 0.05–2 s, `posix_spawn` | Can't outlive the run by more than 2 s. `:318` already SIGKILLs and `waitpid`s in a `defer`. |

The orchestrator's candidate list included `ChildProcessReadinessTests`, but its fixtures are `sleep 30` and `echo`, not `sleep 60`. It can't be the source of the observed orphans. It's still in the audit's scope.

**`exec` check.** Every `sh -c` fixture with a long-running command already ends in `exec sleep …`, so none of today's fixtures leaves a grandchild behind. `LMStudioSIGTERMIgnoringFixture.swift:28-35` documents why. The shared helper should keep this guaranteed for new fixtures. One option is a fixture builder that always generates the `exec` form, so a test can't write `sh -c '...; sleep 60'` by hand.

**Mechanisms the audit must also rule in or out.** I found no live leak path for these by reading the code, but they fit an intermittent orphan under parallel load:

1. **A detached reap still pending when the test process exits.** `ProcessGitStatusScanner.scheduleTeardownReap` (`BattyKit/Sources/BattyKit/Runtime/GitStatusPaneContent.swift:366`) and the LM Studio equivalent send `SIGTERM` and then SIGKILL on a `Task.detached`. A test whose last step is `terminateAndWaitBriefly()`/`tearDown()` on a TERM-ignoring child, with no `await …awaitPendingTeardownReapsForTesting()` and no `defer` SIGKILL, depends on that task finishing before the process exits. At the very end of a run it may not.
2. **The test process crashing or being killed mid-test.** In #0429 round 1, a `dispatch_assert_queue` trap in a `@MainActor` timeout closure orphaned children exactly this way. Any crash leaks every child alive at that moment. Check whether the run that produced the orphans also reported a crash or an unexpected exit.
3. **How `swift test --parallel` spreads suites across processes.** Establish whether it runs suites in more than one worker process, and whether a worker can exit while a test's `defer` hasn't run yet.

## Expected behavior

No test child outlives the test that spawned it, on any exit path: success, a failed `#expect`, a thrown `#require` or `try`, an early `return` from a failed readiness `guard`, or a detached reap still pending.

## Direction

- Add one shared test helper, e.g. `ChildProcessFixture` next to `ChildProcessReadiness.swift`. It owns spawn → track → `SIGKILL` → `waitUntilExit()`, and registers its cleanup **before** `run()`, so a throwing `run()` of a later child can't skip an earlier child's cleanup. Replace both file-private `killAndReap` helpers and every ad-hoc `if process.isRunning { kill(pid, SIGKILL) }` `defer` with it.
- Build fixtures only in the `exec` form (see above).
- Convert the remaining bare readiness `#expect`s (`PendingTeardownReapRegistryTests.swift:83`, `:109`) to `guard` with a releasing failure branch, per `docs/async-test-seams.md` §4.
- A test that leaves a detached reap scheduled on a TERM-ignoring child either awaits `awaitPendingTeardownReapsForTesting()` or SIGKILLs and reaps in a `defer`.
- `AGENTS.md` "Asynchronous tests (binding)" applies: no sleeps or polling added to make the cleanup "settle". `waitUntilExit()` after `SIGKILL` is the documented exception, as #0429 established.

## Done when / how to verify

This can't run in CI or the Tart VM: the VM runs UI tests, and orphans on the guest say nothing about the host. Verify on the host, and record the commands and results in the resolution:

1. Before each batch, record any pre-existing matches, so an unrelated `sleep 60` in a user shell isn't miscounted:
   `ps -axo pid,ppid,command | awk '$2==1 && /sleep 60/'`
2. Run `cd BattyKit && swift test --parallel` for the full package **10 times**. The seen rate was 1 in about 2 full runs, which is too little data to size N. 10 runs at least tries to reproduce it before the fix. After each run, run the same `ps … | awk` check. It must show nothing new. Also check `sleep 30` the same way.
3. Mutation, to prove the helper covers the throwing path: temporarily make the second fixture's `run()` throw in `drainSynchronouslyReapsEveryRegisteredEntryIndependently`, for example by pointing its `executableURL` at a nonexistent path. Confirm the first child is reaped (none left by the check above). Revert.
4. `./build.sh unit` passes.

If the orphan can't be reproduced before the fix, say so in the resolution. Don't claim the fix is what resolved it. Record which leak paths above were closed, and that 10 runs came back clean.

## Work notes (implementer)

The orphan itself could not be reproduced before the fix (10 baseline-equivalent
runs after the fix all came back clean — see below); this closes the leak
paths the filer's audit found by inspection, it doesn't prove those paths were
*the* cause of the one observed occurrence in #0429.

**New shared helper** — `BattyKit/Tests/BattyKitTests/ChildProcessFixture.swift`
(`@MainActor final class ChildProcessFixture`). `run(_:)` appends the process
to an internal array *before* calling `Process.run()` on it, so a later
process's throwing `run()` can never skip an earlier process's cleanup.
`killAndReapAll()` (called from one `defer` registered before any `run()`)
SIGKILLs and `waitUntilExit()`s everything tracked, in order; harmless on a
process that never started. `static killAndReap(_:)` is the same
SIGKILL+`waitUntilExit()` primitive on its own, for callers that don't need
the tracking array.

**Leak paths closed:**

- `PendingTeardownReapRegistryTests.swift` `drainSynchronouslyReapsEveryRegisteredEntryIndependently`
  (was `:104-121`) — the live leak. Rewritten to route both fixtures through
  one `ChildProcessFixture`, tracked before each `run()`. Also converted the
  bare readiness `#expect` to a `guard`/`Issue.record`/`return`, per
  `docs/async-test-seams.md` §4.
- `PendingTeardownReapRegistryTests.swift` `drainSynchronouslyKillsAndReapsARegisteredSigtermIgnoringProcess`
  (was `:79-102`) — not a live leak today (nothing throws between `run()` and
  the old `defer`), but converted the same way for consistency and because
  the bare readiness `#expect` at the old `:83` was itself a §4 violation.
- `PendingTeardownReapRegistryTests.swift` `registerThenDeregisterLeavesNothingPending`
  (was `:43-58`) — not a leak; moved onto `ChildProcessFixture` too, so no
  ad-hoc `defer { if process.isRunning { kill(...) } }` remains in this file.
- `ProcessGitStatusScannerTests.swift` `:330`, `:509`, `:534` (three tests:
  `terminateAndWaitBrieflyTerminatesEveryOverlappingTrackedProcess`,
  `terminateIfRunningSignalsEveryOverlappingTrackedProcess`,
  `aCompletedScansCleanupDoesNotClobberAnotherStillRunningScan`) — each ran
  `try processA.run(); try processB.run()` before either `defer`. Minimal fix
  per the orchestrator's brief (this file is shared with #0440, worked next):
  each process's own `defer` is now registered immediately after its own
  `run()`, so a throwing `processB.run()` can't skip `processA`'s cleanup.
  Did not introduce `ChildProcessFixture` here, to keep the diff small for
  #0440.
- LM Studio `killAndReap` dedup: `LMStudioDashboardPaneContentTests.swift`
  and `LMStudioDashboardWiringTests.swift` each had an identical file-private
  `killAndReap(_ process: Process?)`. Both now forward to
  `ChildProcessFixture.killAndReap(_:)`; call sites (`killAndReap(box.model)`,
  etc.) are unchanged, so this is a pure dedup with no behavior change to the
  LM Studio suites (per the orchestrator's explicit constraint).

**Deferred (not fixed here):**

- **No exec-form fixture builder.** The issue's Direction suggests a fixture
  builder that always generates the `exec sleep …` form, so a future test
  can't write `sh -c '...; sleep 60'` by hand and leave a grandchild behind.
  Not built — today's fixtures all already use `exec` (confirmed by the
  filer's audit), so nothing currently regresses without it, but nothing
  guards a *future* fixture either.
- **`ProcessGitStatusScannerTests.swift`'s stubborn-fixture `defer`s use an
  ad-hoc kill without a reap**, and its plain `sleep 30` `defer`s terminate
  without reaping. Specifically: the three stubborn-fixture `defer { if
  process.isRunning { kill(pid, SIGKILL) } }` blocks (in
  `terminateAndWaitBrieflyReturnsImmediatelyEvenWhenTheProcessIgnoresSIGTERM`,
  `waitForPendingTeardownSynchronouslyBlocksUntilAStubbornProcessIsReaped`,
  `registryDrainReapsAStubbornProcessWithNoWaitForPendingTeardownCall`) send
  `SIGKILL` but never call `waitUntilExit()`; the six `sleep 30` `defer { if
  process{A,B}.isRunning { process{A,B}.terminate() } }` blocks (across
  `terminateAndWaitBrieflyTerminatesEveryOverlappingTrackedProcess`,
  `terminateIfRunningSignalsEveryOverlappingTrackedProcess`,
  `aCompletedScansCleanupDoesNotClobberAnotherStillRunningScan`) send only
  `SIGTERM`, no `SIGKILL` escalation, and don't reap either. Neither pattern
  is a live leak by itself (each still signals the process before the test
  process exits), but neither matches `ChildProcessFixture`'s
  guarantee-a-reap contract. Left as-is per the orchestrator's brief to keep
  this file's diff minimal — both go to #0440, which works this file next.
- **`ChildProcessReadinessTests.swift:32`'s `defer { process.terminate() }`
  only sends `SIGTERM`** (on a plain `exec sleep 30` with no `SIGTERM` trap,
  so the child does die on it) — no `SIGKILL` escalation and no
  `waitUntilExit()` reap. The original audit called this "low risk" since
  the fixture has no trap; not moved onto `ChildProcessFixture` here.

**Causes investigated:**

1. *A detached reap still pending when the test process exits.* Checked every
   `scheduleTeardownReap`/`reapAfterTerminate` call site in the test suites
   (`ProcessGitStatusScannerTests.swift`, `LMStudioDashboardPaneContentTests.swift`,
   `LMStudioDashboardWiringTests.swift`): every test that leaves a detached
   reap in flight either awaits `awaitPendingTeardownReapsForTesting()`, or
   reaps synchronously and SIGKILLs in a `defer` —
   `ProcessGitStatusScannerTests.swift`'s
   `waitForPendingTeardownSynchronouslyBlocksUntilAStubbornProcessIsReaped`
   (`:448`) and `registryDrainReapsAStubbornProcessWithNoWaitForPendingTeardownCall`
   (`:482`) don't await the testing hook, but each calls a synchronous reap
   (`scanner.waitForPendingTeardownSynchronously()`, `registry.drainSynchronously()`)
   before returning, backstopped by the same `defer` SIGKILL as every other
   test here. No test found that ends without one of these three. Ruled out
   as a currently-live path, though it remains a structural risk if a future
   test adds a new deferred-reap call site without the same discipline.
2. *The test process crashing mid-test.* All 10 full `swift test --parallel`
   runs (see below) were grepped for `Fatal error`/`Illegal instruction`/
   `Segmentation fault`/`crashed`/`Thread 1: Fatal` — none found. Two of the
   10 runs had test failures, but they were all `Issue recorded` (assertion
   failures), all confined to `LMStudioDashboardPaneContentTests` (an
   apparent pre-existing flake under heavy parallel host load — e.g.
   `notInstalledWhenCLIMissingButModelsPollStillWorksOverHTTP`, `LMStudioDashboardPaneContentTests.swift:73`),
   never a crash, and never accompanied by an orphan. No crash was observed
   in this investigation, so this cause could not be confirmed or excluded
   further — it stays a plausible mechanism for the original one-time
   observation.
3. *How `swift test --parallel` spreads suites across processes.* Watched
   the process tree during a `swift test --parallel` run
   (`ps -axo pid,ppid,command`), polled once a second: it briefly showed a
   `swiftpm-xctest-helper` child process (bundle path plus a
   `TemporaryFile...` argument) that ran empty — no test output, no fixture
   children under it in any sample — and exited; this looks like a
   bundle/test-list discovery pass, not test execution. It was gone by the
   next sample, replaced by exactly one `swiftpm-testing-helper` child
   process (`--test-bundle-path ... --parallel --filter ... --testing-library
   swift-testing`) that ran the whole `BattyKitTests.xctest` bundle; no
   additional worker processes appeared for the rest of the run. For a Swift
   Testing target (as opposed to classic XCTest), `--parallel` parallelizes
   across Swift concurrency tasks *inside that one `swiftpm-testing-helper`
   process*, not by forking one OS process per suite/class the way XCTest's
   own parallel mode does. This means: (a) there are two child processes in
   sequence, but only the second ever spawns fixture children, so it is the
   only one whose exit could reparent still-alive fixture children to
   launchd — consistent with the "test process exited while [children] were
   still running" framing in the Description — and (b) mechanism 3 as
   originally framed ("a worker can exit while a test's `defer` hasn't run
   yet") does not apply in the multi-process sense for this package's Swift
   Testing suites; the more precise risk is *that single*
   `swiftpm-testing-helper` process exiting (by crash, mechanism 2) or the
   run ending with a reap still detached (mechanism 1) while a `Process` it
   spawned is still alive.

## Resolution notes

> 🟢 Resolved 2026-09-24 — the leak paths found in the audit are closed. Child-process test fixtures now go through `ChildProcessFixture`, which tracks each process *before* `run()`. If a later `run()` throws, it can no longer skip an earlier child's SIGKILL and reap. The original orphan did not reproduce in 10 loaded runs, before or after this change, so it is not claimed as reproduced-then-fixed.

## Fix

- **New `ChildProcessFixture`** (test target, `@MainActor`). Its `killAndReap` sends SIGKILL and then calls `waitUntilExit`, and skips processes that have already exited. `killAndReapAll()` runs in a `defer` that is registered before any `run()`.
- **`PendingTeardownReapRegistryTests`** now uses the fixture. Its readiness `#expect`s are now guards.
- **`ProcessGitStatusScannerTests`** gets a minimal defer-ordering fix at three sites.
- **The LM Studio `killAndReap` helpers** now forward to the fixture, with unchanged behaviour.
