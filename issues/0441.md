# 0441 — A full-package `swift test --parallel` run intermittently leaves `sleep 60` test children alive and reparented to launchd

| | |
|---|---|
| **Status** | open |

| **Platform** | macOS |

## Description

After a full-package `swift test --parallel` run of `BattyKit`, `sleep 60` children spawned by test fixtures sometimes stay alive with `ppid` 1. That means the test process exited while they were still running, and launchd adopted them. This was seen once during #0429's work: two processes, and a repeat run straight afterwards was clean (#0429's Notes, "Orphaned-process check"). They weren't from the LM Studio tests, which #0429 hardened and checked clean over many filtered and full runs. A leaked child ignores `SIGTERM` in several fixtures, so it runs for its full 60 s and is still alive after the run reports a result.

Work: audit **every** child-spawning test for a path where the child can outlive the test. Route them all through one shared kill-and-reap helper, and make sure every `sh -c` fixture `exec`s its long-running command, so no grandchild survives when `sh` is killed.

## Premise check (read-only, on `main` at `3e8e7236`)

`grep -rn '/bin/sh\|/bin/sleep\|exec sleep\|posix_spawn' BattyKit/Tests` lists every child-spawning test. Each one is covered below.

**`sleep 60` spawners.** Only these can produce the observed orphans:

| Site | Fixture | Leak path found |
|---|---|---|
| `PendingTeardownReapRegistryTests.swift:104` `drainSynchronouslyReapsEveryRegisteredEntryIndependently` | 2 × `trap '' TERM; echo ready; exec sleep 60` | **Yes.** The `for` loop at `:107-110` runs `try process.run()` on each fixture before the `defer` at `:111` is registered. If the second `run()` throws, the first child is never killed. It ignores `SIGTERM`, so it lives 60 s and outlives the test process. The readiness wait at `:109` is also a bare `#expect`, which `docs/async-test-seams.md` §4 forbids. |
| `PendingTeardownReapRegistryTests.swift:79` `drainSynchronouslyKillsAndReapsARegisteredSigtermIgnoringProcess` | stubborn, `exec sleep 60` | The readiness wait at `:83` is a bare `#expect`, and the `defer` at `:85` is registered after it. Today nothing between them can throw, so this isn't a live leak. It is the same shape #0430 converted to `guard` in `ProcessGitStatusScannerTests`, though. |
| `PendingTeardownReapRegistryTests.swift:43` `registerThenDeregisterLeavesNothingPending` | `/bin/sleep 60` directly | None. The `defer` comes straight after `run()`. |
| `ProcessGitStatusScannerTests.swift:385`, `:450`, `:484` | stubborn `makeStubbornProcess()` (`:375-383`), `exec sleep 60` | Readiness is already a `guard` whose failure branch kills and reaps the child (#0430). Each `defer` does `kill(pid, SIGKILL)` without `waitUntilExit()`. That can't leave a *live* child, but it isn't the same helper the other files use. |
| `LMStudioSIGTERMIgnoringFixture.swift:45-46`, `LMStudioDashboardPaneContentTests.swift`, `LMStudioDashboardWiringTests.swift` | `exec sleep 60`, with and without the TERM trap | #0429 audited and hardened these. Two identical file-private `killAndReap(_:)` helpers exist (`LMStudioDashboardPaneContentTests.swift:1257`, `LMStudioDashboardWiringTests.swift:424`). They're the natural seed for the shared helper. |

**Other spawners.** None of these is `sleep 60`, so none could have produced the observed orphans. They're in scope for the same helper, since each has the same class of leak:

| Site | Fixture | Leak path found |
|---|---|---|
| `ProcessGitStatusScannerTests.swift:330`, `:509`, `:534` | 2 × `/bin/sleep 30` | **Yes.** `try processA.run()` then `try processB.run()` (`:334-335`, `:513-514`, `:538-539`) come before the `defer`. If B's `run()` throws, A is left running for 30 s. |
| `ChildProcessReadinessTests.swift:25` | `exec sleep 30` | `defer { process.terminate() }` sends SIGTERM and doesn't reap. The child has no trap, so it dies. Low risk. |
| `ChildProcessReadinessTests.swift:11`, `:45` | short `echo` children | None. |
| `ProcessInspectorTests.swift:46`, `:121`, `:318`; `ProcessStatusPaneContentTests.swift:286`, `:549`, `:570`, `:681` | `/bin/sleep` for 0.05–2 s, `posix_spawn` | Can't outlive the run by more than 2 s. `:318` already SIGKILLs and `waitpid`s in a `defer`. |

The orchestrator's candidate list included `ChildProcessReadinessTests`, but its fixtures are `sleep 30` and `echo`, not `sleep 60`. It can't be the source of the observed orphans. It's still in the audit's scope.

**`exec` check.** Every `sh -c` fixture with a long-running command already ends in `exec sleep …`, so none of today's fixtures leaves a grandchild behind. `LMStudioSIGTERMIgnoringFixture.swift:28-35` documents why. The shared helper should keep this guaranteed for new fixtures. One option is a fixture builder that always generates the `exec` form, so a test can't write `sh -c '...; sleep 60'` by hand.

**Mechanisms the audit must also rule in or out.** I found no live leak path for these by reading the code, but they fit an intermittent orphan under parallel load:

1. **A detached reap still pending when the test process exits.** `ProcessGitStatusScanner.scheduleTeardownReap` (`BattyKit/Sources/BattyKit/Runtime/GitStatusPaneContent.swift:366`) and the LM Studio equivalent send `SIGTERM` and then SIGKILL on a `Task.detached`. A test whose last step is `terminateAndWaitBriefly()`/`tearDown()` on a TERM-ignoring child, with no `await …awaitPendingTeardownReapsForTesting()` and no `defer` SIGKILL, depends on that task finishing before the process exits. At the very end of a run it may not.
2. **The test process crashing or being killed mid-test.** In #0429 round 1, a `dispatch_assert_queue` trap in a `@MainActor` timeout closure orphaned children exactly this way. Any crash leaks every child alive at that moment. Check whether the run that produced the orphans also reported a crash or an unexpected exit.
3. **How `swift test --parallel` spreads suites across processes.** Establish whether it runs suites in more than one worker process, and whether a worker can exit while a test's `defer` hasn't run yet.

## Expected behavior

No test child outlives the test that spawned it, on any exit path: success, a failed `#expect`, a thrown `#require` or `try`, an early `return` from a failed readiness `guard`, or a detached reap still pending.

## Direction

- Add one shared test helper, e.g. `ChildProcessFixture` next to `ChildProcessReadiness.swift`. It owns spawn → track → `SIGKILL` → `waitUntilExit()`, and registers its cleanup **before** `run()`, so a throwing `run()` of a later child can't skip an earlier child's cleanup. Replace both file-private `killAndReap` helpers and every ad-hoc `if process.isRunning { kill(pid, SIGKILL) }` `defer` with it.
- Build fixtures only in the `exec` form (see above).
- Convert the remaining bare readiness `#expect`s (`PendingTeardownReapRegistryTests.swift:83`, `:109`) to `guard` with a releasing failure branch, per `docs/async-test-seams.md` §4.
- A test that leaves a detached reap scheduled on a TERM-ignoring child either awaits `awaitPendingTeardownReapsForTesting()` or SIGKILLs and reaps in a `defer`.
- `AGENTS.md` "Asynchronous tests (binding)" applies: no sleeps or polling added to make the cleanup "settle". `waitUntilExit()` after `SIGKILL` is the documented exception, as #0429 established.

## Done when / how to verify

This can't run in CI or the Tart VM: the VM runs UI tests, and orphans on the guest say nothing about the host. Verify on the host, and record the commands and results in the resolution:

1. Before each batch, record any pre-existing matches, so an unrelated `sleep 60` in a user shell isn't miscounted:
   `ps -axo pid,ppid,command | awk '$2==1 && /sleep 60/'`
2. Run `cd BattyKit && swift test --parallel` for the full package **10 times**. The seen rate was 1 in about 2 full runs, which is too little data to size N. 10 runs at least tries to reproduce it before the fix. After each run, run the same `ps … | awk` check. It must show nothing new. Also check `sleep 30` the same way.
3. Mutation, to prove the helper covers the throwing path: temporarily make the second fixture's `run()` throw in `drainSynchronouslyReapsEveryRegisteredEntryIndependently`, for example by pointing its `executableURL` at a nonexistent path. Confirm the first child is reaped (none left by the check above). Revert.
4. `./build.sh unit` passes.

If the orphan can't be reproduced before the fix, say so in the resolution. Don't claim the fix is what resolved it. Record which leak paths above were closed, and that 10 runs came back clean.
