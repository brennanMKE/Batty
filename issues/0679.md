# 0679 — Experiment: the Session Sidebar can switch between a wide names list and a narrow symbols-only rail

| | |
|---|---|
| **Status** | open |
| **Module** | Sidebar / Window / App |
| **Platform** | macOS |
| **First seen** | 2026-11-19 |
| **Target** | 1.5.0 |

## Description

**This is an experiment.** It is a time-boxed prototype that answers whether a narrow, symbols-only Session Sidebar rail is feasible. It is not the finished feature. It follows the first step of the recommendation in the design proposal "A symbols-only Sidebar" (published at https://claude.ai/artifact/8vcw9MnGZqtMAtsVrRQibA, drawn from source at `c1f7be6e`). That step is the half-day column prototype. The user liked the proposals but knows they carry risk. They want to try the rail themselves from a Beta DMG before deciding go or no-go.

The question the experiment must answer: **will `NavigationSplitView` hold a ~56 pt sidebar column (or ~84 pt, wide enough to contain the traffic lights) and switch back to ~220 pt on demand?** Today `RootWindowView.swift` sets `.navigationSplitViewColumnWidth(min: 180, ideal: 220, max: 320)`, so nothing narrower than 180 pt is possible. NavigationSplitView on macOS is known to cache a column's width and ignore later changes to `navigationSplitViewColumnWidth`, and it may enforce its own minimum. If neither width holds, the fallbacks are reaching into the underlying `NSSplitViewItem` (fragile) or owning an `NSSplitViewController` (a large change that touches the terminal-host rules in `docs/view-hierarchy.md`). The experiment records which of these is needed.

The whole feature sits behind a new feature flag: on in Batty Beta, off in Prod (`BattyKit/Sources/BattyXPCCore/FeatureFlags.swift`, `docs/feature-flags.md`). With the flag off it is invisible and inert. There is no menu item, Command Palette entry, Settings → Shortcuts row or key binding, and the column width and the drag behavior are exactly as they are today.

## Scope

1. **Style command and hotkey (page option B).** Add a new rebindable `ShortcutAction`, appended to the end since raw values are persistence keys. It toggles the key window's Sidebar between wide (names) and narrow (symbols-only rail). The default is **⌥⌘B** as the page proposes. As of filing, the catalog binds only ⌘B (`toggleSidebar`) and ⇧⌘B (Bell Feed) on `b`, so ⌥⌘B is free. Re-check this when planning. Add the action to the View menu (`BattyCommands.swift`), the key monitor (`BattyShortcuts.swift`), the Command Palette (`CommandPaletteView.swift`) and Settings → Shortcuts. The menu title says what will happen ("Show Symbols Only" / "Show Session Names"). **⌘B stays plain show/hide** and brings the Sidebar back in whichever style was last showing. Using the style command while the Sidebar is hidden shows it in the requested style. The style is per-window state kept beside `sidebarHidden` in `RootWindowView.swift`.
2. **Drag to snap (page option C).** Dragging the Sidebar divider below a threshold of about 120 pt snaps to the rail on release. Dragging the rail's edge out past the threshold restores names. **The hard part is `docs/swiftui-observation-rules.md`, which is binding.** Deciding the style from a measured width in `onGeometryChange` or a layout callback is a geometry-origin write to observed state, and that is forbidden. The plan must find an **event-origin** path, such as an `NSSplitViewDelegate` hook, a mouse-up / drag-end event on the divider, or the outline deriving its own presentation from its own bounds without writing observed state. If none is workable, the plan must record why. Do not hop a write into a `Task` to dodge the rule (the #0229 lesson). No `makeFirstResponder` or `addSubview` from SwiftUI callbacks.
3. **The rail itself.** It shows each Session's colored symbol, or the colored `circle.fill` dot for a plain Session, and nothing else: no name and no chevron/disclosure (Pane rows are not shown in rail mode). It has a selection highlight (the rounded tint plus a hairline ring, since the bold name is gone) and a `.help` tooltip with the Session title. The existing badges move onto the symbol's corners: the unseen-bell count as a filled corner badge ("9+" above nine), and one bottom-corner glyph for the Reminder or Project-image warning, in priority order due alarm, then image warning, then pending clock. The footer's New Session and Open Project… buttons stack vertically. VoiceOver labels and values stay as they are (`rowAccessibilityValue` already carries everything). Drag-to-reorder, arrow keys and type-select keep working. Each Session's expanded state survives a trip through the rail. ⌘1…⌘9 are unchanged. The outline work lives in `SessionSidebarOutline.swift`: a flush style instead of source-list insets, zero children reported in rail mode, a centered cell. `SessionSidebarView.swift` handles the footer.

Widths to try: 56 pt first, then 84 pt with the traffic lights inside the rail if 56 misbehaves. For each, look at where macOS puts the traffic lights and the toolbar sidebar button, and whether ⌘B restores the correct width.

## Out of scope

- Previous / Next Session hotkeys (separate later issue).
- Grouping Settings → Shortcuts into sections (separate later issue).
- Hover-to-peek (page option D) and the title-bar strip (option E).
- ⌘-held number hints and the rail-mode "Panes" context submenu. These are later steps of the recommendation and can be filed if the experiment is a go.
- Remembering the style across relaunch, or a Settings default for it.

## Acceptance

- In a Batty Beta build, ⌥⌘B (and the View menu / Command Palette entries) toggles wide ↔ rail in the key window, and ⌘B still shows and hides the Sidebar in the last style.
- Dragging the divider below ~120 pt snaps to the rail, and dragging it back out restores names, with no observation-rule violations ("Modifying state during view update" or "AttributeGraph cycle" in the console).
- The rail matches item 3 above.
- With the flag off (Prod), behavior is identical to today.
- `./build.sh` and `./build.sh unit` pass. New UI tests for the toggle and the rail width compile under `./build.sh ui-typecheck`. Existing `BattyUITests/SidebarTests.swift` expectations, which read the session-sidebar frame width and the chevron position, stay green with the flag's default state, or are given a rail case.
- A **findings write-up** in this issue (a `## Findings` section): what worked, what didn't, which widths were chosen and why, whether NavigationSplitView held the narrow column or needed the `NSSplitViewItem` / owned-split-view fallback, how the traffic lights and toolbar button behaved, terminal reflow on switch, and a recommendation to go or not go. The user uses this to decide.
- A Beta build is produced for the user to install (`./build.sh package --sign`; notarize only with the user's go-ahead). The user will try it from a Beta DMG.
