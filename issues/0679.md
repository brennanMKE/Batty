The style itself does come back as decision 1 asks; only the width lags until the next ⌥⌘B or drag.

Round 3 bounced (hidden ⌥⌘B resized terminals three times). Round 2 approved the original build. Round 1 bounced: Beta opened the names column at 58 pt, and the flag-hidden ⌥⌘B action still showed up in Prod's shortcut collisions. Round 2 approved:

**This is an experiment.** It is a time-boxed prototype that answers whether a narrow, symbols-only Session Sidebar rail is feasible. It is not the finished feature. It follows the first step of the recommendation in the design proposal "A symbols-only Sidebar" (published at https://claude.ai/artifact/8vcw9MnGZqtMAtsVrRQibA, drawn from source at `c1f7be6e`). That step is the half-day column prototype. The user liked the proposals but knows they carry risk. They want to try the rail themselves from a Beta DMG before deciding go or no-go.

The question the experiment must answer: **will `NavigationSplitView` hold a ~56 pt sidebar column (or ~84 pt, wide enough to contain the traffic lights) and switch back to ~220 pt on demand?** Today `RootWindowView.swift` sets `.navigationSplitViewColumnWidth(min: 180, ideal: 220, max: 320)`, so nothing narrower than 180 pt is possible. NavigationSplitView on macOS is known to cache a column's width and ignore later changes to `navigationSplitViewColumnWidth`, and it may enforce its own minimum. If neither width holds, the fallbacks are reaching into the underlying `NSSplitViewItem` (fragile) or owning an `NSSplitViewController` (a large change that touches the terminal-host rules in `docs/view-hierarchy.md`). The experiment records which of these is needed.

The whole feature sits behind a new feature flag: on in Batty Beta, off in Prod (`BattyKit/Sources/BattyXPCCore/FeatureFlags.swift`, `docs/feature-flags.md`). With the flag off it is invisible and inert. There is no menu item, Command Palette entry, Settings → Shortcuts row or key binding, and the column width and the drag behavior are exactly as they are today.

## Root cause

Feature work (experiment). Starting state: `RootWindowView` pinned the Sidebar column to `navigationSplitViewColumnWidth(min: 180, ideal: 220, max: 320)`, the outline (`SessionSidebarOutline`) had one names presentation, and nothing could switch the column below 180 pt.

## Fix

Followed the plan, behind the new `compactSidebar` flag (on in Beta, off in Prod):

- `FeatureFlags.compactSidebar` plus the `BATTY_UI_TEST_FORCE_COMPACT_SIDEBAR_OFF` force-off override; the override now forces each flag off independently.
- `SidebarStyle` / `SidebarRailMetrics` / `SessionRailBadge` (pure, `Model/SidebarStyle.swift`); `WindowRuntime.sidebarStyle` (not persisted).
- `SidebarSplitBridge` (`Views/SidebarSplitBridge.swift`), mounted as a background of the detail column only with the flag on. It finds the `NSSplitView` (and its `NSSplitViewController`) above it, observes `.battyToggleSidebarStyle` with a plain selector observer, and owns a `.leftMouseDown` local monitor that runs `NSSplitView.mouseDown(with:)` synchronously for a press that hit-tests to the split view itself, then commits the snap with `finishDividerDrag`. It is the only writer of `sidebarStyle`; both writes are event-origin and synchronous, with no `Task` hop and nothing written during the drag.
- Column range: `SidebarRailMetrics.columnRange` (flag off: 180/220/320, unchanged; flag on: railWidth/220/320). Resting width set through `setPosition(_:ofDividerAt: 0)`.
- Outline rail mode: `.plain` style, indentation 0, `.custom` row size at 40 pt (names metrics saved and restored), `rail-cell` cells (`SessionSidebarView.railCell` / `SessionRailRow`), zero children and not expandable, and the expansion-sync loop skipped so `isPaneListExpanded` survives. `SidebarOutlineRowView.isRail` draws a rounded tint with a 1 pt ring. `outlineTableColumn = nil` was **not** needed: the rail cell starts at x < 4 and is centred (pinned by `railStyleUsesRailCellsAndFlushOutline`).
- Footer: buttons extracted to `footerButtons`; stacked `VStack` in the rail, today's `HStack` in names.
- `ShortcutAction.toggleSidebarStyle` (appended, ⌥⌘B) with `isAvailable(_:)`, filtered in `BattyShortcuts.handle`, `CommandPaletteView.allCommands` (dynamic title), `ShortcutsSettingsView(flags:)`; the View menu item exists only with the flag on and its title says what will happen.

Deviations from the plan:

- **Footer compressibility (new).** The first headless run showed the style command landing at 84 pt, not 56. The `NSSplitViewItem` already had `minimumThickness == 56`, and a second `setPosition(56)` after the next settle held. What clamped it was the names-mode footer's fixed buttons and padding (~84 pt minimum), still in place when `setPosition` runs, before SwiftUI restacks the footer. With the flag on, the footer now gets `CompressibleSidebarFooter` (`frame(minWidth: 0, maxWidth: .infinity, alignment: .leading).clipped()`). - `railRowsKeepTheirAccessibilityIdentifierAndValue` is `.disabled` with its reason: a headless `NSHostingView` cell exposes no SwiftUI accessibility children. ### Decisions (with reasons)

1. **Rail width: 56 pt by default, 84 pt via a Beta-only tuning default.** 56 pt is the issue's first ask and wins the most terminal columns; with the Sidebar hidden macOS already draws the traffic lights over the detail title bar, so it is a known-good layout. 84 pt is the narrowest rail that contains the lights (x ≈ 19 to 79 pt). Rather than building twice, `SidebarRailMetrics.railWidth(defaults:)` reads `co.sstools.Batty.sidebarRailWidth` and accepts only 56 or 84, anything else is 56. The user tries the wider one with `defaults write co.sstools.Batty.beta co.sstools.Batty.sidebarRailWidth -int 84` and a relaunch. It is read once per window, only when the flag is on (so Prod reads nothing), and is deleted with the experiment.
2. **Column width: a constant range from the documented modifier, and the resting width set through the NSSplitView at event time.** Changing `navigationSplitViewColumnWidth` values on a style switch is unreliable: NavigationSplitView caches widths and clamps instead of moving, and going rail → names with `min: 180` would land on 180 and lose the user's previous width (`docs/ui-features.md` requires toggling twice to restore the prior width). And option C needs the rail edge to be draggable outward, which a fixed 56 pt range forbids. So with the flag on the modifier is the constant `min: railWidth, ideal: 220, max: 320`. With the flag off it stays `min: 180, ideal: 220, max: 320`. The column's resting width is set by `NSSplitView.setPosition(_:ofDividerAt: 0)` from one AppKit-side owner, `SidebarSplitBridge`, inside the event that asked for the change. ⌘B needs nothing new: NSSplitViewItem restores its pre-collapse width on reveal, which is the last style's width. If the experiment shows SwiftUI re-applies `ideal` on reveal (the rail comes back at 220), the fallback to try is a style-dependent `ideal` (railWidth in rail mode) with min/max kept constant, and record that in Findings. If `setPosition` on SwiftUI's split view does not hold at all, stop and record that the owned-`NSSplitViewController` fallback would be needed (no-go for this experiment).
3. **Drag snap hook: intercept the divider's mouse-down in an NSEvent local monitor and run NSSplitView's own tracking synchronously, then commit on return.** Rejected: `splitViewDidResizeSubviews` / `NSSplitView.didResizeSubviewsNotification` and `onGeometryChange` (layout-origin, forbidden for observed writes); `splitView(_:constrainSplitPosition:ofSubviewAt:)` (needs the split view's delegate, which is SwiftUI's `NSSplitViewController`); a `.leftMouseUp` monitor (NSSplitView drags in a nested tracking loop, and local monitors never see events pulled by `nextEvent(matching:)`); a deferred default-mode `RunLoop.perform` (a `Task`-style hop, the #0229 lesson). Chosen: the bridge's `.leftMouseDown` monitor checks the event is in its window, `clickCount == 1`, the column is not collapsed, and `window.contentView?.hitTest(event.locationInWindow) === splitView` (only the divider area hit-tests to the NSSplitView itself; every Pane, terminal and the outline hit-test to their own views, so no pane-body event is touched). It then calls `splitView.mouseDown(with: event)` itself, which returns after the user lets go, reads the column's width, decides with the pure `SidebarRailMetrics.resolveDragEnd(width:railWidth:)`, writes `WindowRuntime.sidebarStyle` and sets the snapped position, and returns nil (the event is consumed because it was already delivered). Why this obeys `docs/swiftui-observation-rules.md`: the write happens in an NSEvent monitor (listed as event-origin in the core invariant), synchronously, in the code that embodies the intent (the "AppKit-initiated" direction of "Two-way model ↔ AppKit sync", like `TerminalClickFocusMonitor`), with no SwiftUI callback calling AppKit and no hop. During the drag nothing writes observed state: names just truncate live, and the snap happens on release. If direct forwarding misbehaves (no tracking, or a stuck cursor), ship option B only and record C as not feasible without owning the split view.
4. **One writer for the style.** `WindowRuntime.sidebarStyle` (model, per window, in process, not persisted: restoration is disabled and remembering the style across relaunch is out of scope) is written only by `SidebarSplitBridge` (command and drag end). The outline, the footer and the menu title only read it. The command reaches the bridge as `.battyToggleSidebarStyle`, posted like `.battyToggleSidebar`. The bridge observes it with a plain `NotificationCenter` observer (not SwiftUI `onReceive`), so the AppKit calls run in the menu or key-monitor event, never in a SwiftUI update. This deviates from the issue's "kept beside `sidebarHidden` in RootWindowView": the AppKit drag hook and the outline coordinator both hold `windowRuntime`, not the view's `@State`/`@SceneStorage`, and `@SceneStorage` would add nothing with restoration disabled.
5. **Style command while hidden:** the bridge sets `splitViewItem.isCollapsed = false` (the item from `splitView.delegate as? NSSplitViewController`), then `setPosition`. The toolbar sidebar button flips the same property and NavigationSplitView already syncs `columnVisibility` → `sidebarHidden` from it (`RootWindowView.onChange(of: columnVisibility)`). If the binding does not follow, record it in Findings. The fallback is to post `.battyToggleSidebar` instead and accept the old width on reveal.
6. **Rail rendering: the same `NSOutlineView`, re-configured.** It is not a separate view. Selection, arrow keys, type-select, drag-reorder and VoiceOver's selected row stay native, and only one AX element (`session-sidebar`) exists.

### User checklist

1. In Batty Beta, press ⌥⌘B. You get a 56 pt rail of colored symbols with no names or chevrons, and the selected Session shows a tint and a ring. Hover over a row and its name appears as a tooltip.
2. Check the rail's badges, starting with the unseen-bell count ("9+" above nine). Then check the bottom corner of the symbol: the alarm when a Reminder is due, the warning when a Project image has a problem, and the clock when a Reminder is pending.
3. In the rail:
   - ⌘1…⌘9, the arrow keys and type-select still work.
   - Drag a row to reorder it.
   - Right-click a row: the full Session menu opens.
   - The footer's + and briefcase are stacked and both work.
4. Press ⌥⌘B again. Names come back at the earlier width, and the expanded Sessions are still expanded.
5. Press ⌘B in each style. The Sidebar comes back in the same style and width. Hide it, press ⌥⌘B: it stays hidden and the View menu title flips; the next ⌘B shows the new style.
6. Drag the divider below about 120 pt and let go: it snaps to the rail. Drag between 120 and 180 pt: it snaps to 180. Drag the rail edge out past 120 pt: names return.
7. Check where the traffic lights and the toolbar sidebar button sit at 56 pt. Then relaunch with `defaults write co.sstools.Batty.beta co.sstools.Batty.sidebarRailWidth -int 84` and compare.
8. Run the pane checklist in `docs/terminal-pane-requirements.md` next to the divider: clicks, file drop, text drop and selection in the terminal next to the Sidebar.
9. Check that the View menu, the Command Palette and Settings → Shortcuts show the new entry. Prod (flag off) shows none of them.
