## Description

During the 1.4.1 release run of the whole VM UI suite on `release/1.4` at `eca8ef61` (run `20261119-214126-8580`), one test failed:

- `BattyUITests/BackgroundImagesWindowTests/testReturnPicksTheSelectedImageAndClosesThePicker`, at `BattyUITests/BackgroundImagesWindowTests.swift:556`: `XCTAssertTrue failed - the arrow key selected nothing` (21.958 s).

A re-run of the whole `BackgroundImagesWindowTests` class in a fresh VM passed 19/19, so this is a flake, not a regression. `BackgroundImagesWindowTests.swift` and `BackgroundImagesView.swift` are the same on `main` (`c45074c5`) as on `eca8ef61`. The fix is test-only or a robustness fix in the picker, for 1.5.0.

The run's results folder (`build/ui-tests/20261119-214126-8580/` in the `release-1.4` worktree) has since been removed. It was read before that. The timeline in `xcodebuild.log` shows the picker opened (t=11.45 s), the My Images segment was clicked (t=13.28–13.89 s), and the `Harbor-return` cell existed at t=14.94 s. Then `waitForPicture` passed and the right arrow was sent. After that the 5 s wait for `isSelected` timed out, which is the 21.958 s total.

## What the test does

`testReturnPicksTheSelectedImageAndClosesThePicker` (`BattyUITests/BackgroundImagesWindowTests.swift:550-561`):

1. `openPaneChooser` (`:489-499`) opens the Pane's gear sheet, clicks Choose (`pane-background-sheet.choose-image`), waits for the picker, clicks the **My Images** segment (`showMyImages`, `:106-111`), and waits until the `Harbor-return` thumbnail is drawn (`waitForPicture`, `:66-76`).
2. Sends one `.rightArrow` (`:555`). It expects `background-images.cell.Harbor-return` to report `isSelected` within 5 s (`:556`).
3. Sends `.return` and expects the picker to close and the Pane to have an image.

The test library is the per-test scratch folder, and `BackgroundImageLibrary.scan()` sorts newest first (`BattyKit/Sources/BattyKit/Settings/BackgroundImageLibrary.swift:55`). So the fresh fixture is the first cell, and `move(_:columns:)` with no selection picks index 0 (`BattyKit/Sources/BattyKit/Views/BackgroundImagesView.swift:292-298`). If the key reached the grid, `Harbor-return` would be selected. The failure means the key **did not reach the grid's `onKeyPress`**.

## Hypothesis: grid focus is a race when the picker opens on Background Sets

All line numbers are in `BattyKit/Sources/BattyKit/Views/BackgroundImagesView.swift`.

- The Pane in this test has no image, so `opening(forCurrent:)` resolves to the **Background Sets** tab. In `onAppear` (`:92-100`) `tab` is `.backgroundSets`, so `gridFocused = true` is not written. `.defaultFocus($gridFocused, true, priority: .userInitiated)` (`:89`) applies only when the sheet is first presented, and at that point no `.focused($gridFocused)` view exists (`:188` is in the My Images branch only).
- `.task { await model.refresh() }` (`:82`) fills `entries` while the tab is still Background Sets. `onChange(of: model.entries.isEmpty)` (`:101-103`) fires then, but `tab != .myImages`, so it writes nothing. It will not fire again, because `entries` stays non-empty.
- The only focus write left is the segment's binding setter (`tabBinding`, `:204-213`). It sets `tab = .myImages` and `gridFocused = true` **in the same transaction** that first inserts the `case .myImages` branch (`:62-70`). The grid there is built inside a `GeometryReader` (`content`, `:142-148`), so the `.focusable()/.focused($gridFocused)` view (`:186-188`) only exists after a layout pass gives the reader a size. A focus write to a binding whose focusable view doesn't exist yet may be honoured once it appears or may be dropped, depending on timing. A loaded VM makes the gap wider. The comment at `:184-185` records that this grid already had a focus-not-taken bug once.
- If the write is dropped, focus stays on the clicked segmented control (or nowhere), and `.rightArrow` goes to the segmented control or beeps. `selection` never changes and the cell never reports `.isSelected` (`:427`). Nothing retries, because no event writes `gridFocused` again until the user clicks a cell.

`testArrowKeySelectsACellOnTheFirstOpen` (`:263-274`), `requestRemoval` (`:244-258`, used by the Delete and Remove tests) and `testArrowKeySelectionAfterScrollingKeepsTheGridStill` (`:338-363`) take the same "click My Images, then arrow key" path. They have the same exposure even though they didn't fail in this run.

A less likely cause: the key arrived before the segment click's focus change had been applied. XCUITest's "wait for idle" after the click (t=13.89 s) makes that unlikely, and `waitForPicture` adds several hundred ms of screenshots before the key.

## Expected behavior

The test is deterministic. Prefer fixing the picker, so a real user's first arrow key after switching to My Images also works:

- **Picker (preferred):** make grid focus deterministic when My Images is shown. Write `gridFocused = true` from an event that runs once the focusable grid exists, not only in the same transaction that creates it. Options: an `onAppear` on the grid view itself (event-origin, from its insertion), or `.defaultFocus` scoped to the My Images branch. Follow `docs/swiftui-observation-rules.md`: no write from `body` or geometry callbacks, no `Task` hop to "fix" ordering, and no `makeFirstResponder` from a SwiftUI callback.
- **Test:** before sending the arrow key, wait on an observable signal that the grid has keyboard focus, for example `hasKeyboardFocus` on an element the grid exposes (give the focusable grid an accessibility identifier such as `background-images.grid`), polled with `waitFor`/`XCTNSPredicateExpectation`. Never use a sleep. Do the same in the other tests above that send an arrow key after `showMyImages`. Optionally make the `:556` message say whether the grid had focus, so a future failure tells the two causes apart.
