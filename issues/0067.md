# 0067 — Closing the focused session selects Session 1 instead of the previous sibling

## Description

When the user has several sessions open (Session 1, Session 2, Session 3 in that order) and closes the **focused** session via `Cmd-W` (cascading through the last-tab → last-pane → `removeSession` path), `AppStateStore.removeSession` selects `sessions.first?.id` as the new active session. So closing Session 3 jumps focus back to Session 1 even though Session 2 was the immediate prior neighbor.

User expectation matches every multi-tab/multi-document macOS app convention: closing the rightmost item shifts focus to the item just to its left. For Batty: closing Session 3 should select Session 2; closing Session 2 should select Session 1; closing Session 1 (the leftmost) selects whatever's next to its right (now the new leftmost).

## Steps to reproduce

1. Launch Batty. Default session "Session 1" is selected.
2. Press `Cmd-N` twice to create Sessions 2 and 3. Session 3 is selected.
3. Press `Cmd-W` to close Session 3.
4. **Observed:** Session 1 is now selected.
5. **Expected:** Session 2 is selected (the session immediately preceding Session 3 in the sidebar order).

## Expected behavior

`AppStateStore.removeSession`'s focus-fallback logic should pick the session immediately preceding (or following, for the leftmost case) the closed session, not always `sessions.first`.

Pseudocode:

```swift
public func removeSession(id: UUID) {
    guard let index = sessions.firstIndex(where: { $0.id == id }) else { return }
    sessions.remove(at: index)
    if selectedSessionID == id {
        // Prefer the session that was just to the left of the closed one.
        // For index 0, the new leftmost (sessions[0]) becomes selected.
        // For non-zero index, sessions[index - 1] (now occupying the previous
        // slot's left neighbor) is selected.
        let newIndex = max(0, index - 1)
        selectedSessionID = sessions.indices.contains(newIndex) ? sessions[newIndex].id : nil
    }
    if sessions.isEmpty {
        NotificationCenter.default.post(name: .battyAllSessionsClosed, object: nil)
    }
}
```

## Actual behavior

Current code:

```swift
if selectedSessionID == id {
    selectedSessionID = sessions.first?.id
}
```

Always falls back to the first session in the list, regardless of where the closed session was. With three sessions and closing the rightmost, the user lands on the leftmost instead of the middle.

## Notes

- This is one of two long-standing UX gaps in the session-close flow that the user surfaced testing the new Cmd-W routing (`#0062` / NSEvent monitor). The companion fix (quit-on-empty instead of auto-recreate) landed alongside this filing — that one was an immediate must-have; this one is a small refinement that the user explicitly asked to track for later.
- Doesn't change `closeTab(id:)` semantics — only `removeSession`'s focus-fallback choice.
- Behavior on closing the leftmost (index 0) session: with the proposed change, `max(0, 0 - 1) == 0`, so we'd pick `sessions[0]` which is the new leftmost (the old second). That matches Safari/iTerm2 behavior — when you close the first tab, the second tab takes over the first slot.

## Acceptance criteria

- With sessions [1, 2, 3] and 3 selected, `Cmd-W` (closing 3) leaves 2 selected.
- With sessions [1, 2, 3] and 2 selected, `Cmd-W` (closing 2) leaves 1 selected.
- With sessions [1, 2, 3] and 1 selected, `Cmd-W` (closing 1) leaves 2 selected (the new leftmost).
- A unit test in `CloseTabCascadeTests` or similar exercises the three cases.

## Out of scope

- Closing non-focused sessions (e.g. via sidebar right-click → Close). Different code path; same convention should apply but track when wired.
- Quit-on-empty behavior (already fixed alongside this filing).

## Root cause

`AppStateStore.removeSession(id:)` always reassigned `selectedSessionID` to `sessions.first?.id` when the removed session was the focused one. That ignored the captured `index` of the removed session and dropped focus to the leftmost item regardless of where the user had been working.

## Fix

After removing the session, compute `newIndex = max(0, index - 1)` and select the session now occupying that slot (if any). Because the removal shifts later sessions left by one, this lands focus on the previous left neighbor when closing the middle/rightmost item, and on the new leftmost (the old second session) when closing the leftmost — matching Safari/iTerm2 tab-close behavior.

## Files changed

- `BattyKit/Sources/BattyKit/AppStateStore.swift` — replace the unconditional `sessions.first?.id` fallback with the previous-sibling index calculation.
- `BattyKit/Tests/BattyKitTests/RemoveSessionSelectionTests.swift` — new Swift Testing suite covering all three acceptance cases (rightmost, middle, leftmost close).
