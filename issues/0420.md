# 0420 — SwiftUI logs a "Geometry action is cycling between duplicate values" Fault on nearly every Batty launch

| | |
|---|---|
| **Status** | open |
| **Module** | App |
| **Platform** | macOS |
| **First seen** | 2026-09-23 |

## Description

SwiftUI logs this Fault-level message on almost every Batty launch:

```
F  Batty Beta[4558:428b] [com.apple.SwiftUI:Invalid Configuration] Geometry action is cycling between duplicate values.
```

In #0412's first full Tart-VM run (run id `20260923-191103-94702`), the app's unified log (`app-warnings.log`) recorded it **93 times**. It came from **72 of the run's 73 distinct Batty Beta processes**, one or two per process. So it's systematic, not something a particular test triggers.

SwiftUI emits this message when an `onGeometryChange` action keeps firing because the action's own effects feed back into the geometry it measures. The value moves between identical values instead of settling. Under `docs/swiftui-observation-rules.md` (binding), `onGeometryChange` is in the "requires an audit" set. A geometry-origin flip that writes observed state runs inside layout. A write that re-invalidates the measured geometry is exactly the loop this Fault reports.

It's unknown whether this is new. Nothing in the routine loop would show it: it appears only in the app's own unified log, not in `xcodebuild` test output or `./build.sh unit`. It's also not yet confirmed on the host, only in the guest.

## Candidates

`grep -rn onGeometryChange BattyKit/Sources` on `main` finds five call sites:

| # | Site | Measures | Action writes | Why it could cycle |
|---|---|---|---|---|
| 1 | `Views/TerminalPlaceholderView.swift:45` | `frame(in: .named("terminal-host"))` (`CGRect`) | `@State lastFrame`, plus `TerminalHostStore.shared.setPlacement(…)` | `setPlacement` repositions the persistent AppKit terminal subview. If moving that host view (or its hosting container) shifts the placeholder's frame in the named space, even by rounding, the action fires again. **Strongest candidate:** it runs once per terminal Tab, and every launch has one. |
| 2 | `Views/PaneView.swift:159` | `frame(in: .named("session"))` (`CGRect`) | `@State frameInSession`, which feeds `.preference(PaneFramePreferenceKey…)` at `:158` | `SessionDetailView.swift:246` reduces that preference into `session.paneFrames.frames` (observed model state) in `onPreferenceChange`. A frame → preference → model write → re-layout loop is possible if anything reads `paneFrames` during layout. |
| 3 | `Views/PaneView.swift:162` | `size` (`CGSize`) | `@State paneWidth`, `paneHeight` | If any view whose layout depends on `paneWidth`/`paneHeight` (for example, adaptive toolbar content) changes the Pane's own size, it loops. |
| 4 | `Views/SplitContainerView.swift:194` | container length along the split axis (`CGFloat`) | `@State containerLength` | Same pattern. Only live in split Sessions, which a plain launch doesn't have, so it's a weaker fit for "once per launch". |
| 5 | `Views/SessionDetailView.swift:139` | `safeAreaInsets.top` (`CGFloat`) | `@State splitDetailToolbarSafeInsetTop`, pushed down as `.environment(\.splitDetailToolbarSafeInsetTop, …)` at `:142` | Runs once per window, which fits the "once per launch" count. **A grep of `BattyKit/Sources` finds no reader of `\.splitDetailToolbarSafeInsetTop`** other than this setter and its `EnvironmentValues` declaration (`Commands/FocusedValues.swift:40`). If that's right, the write only invalidates the detail subtree and feeds nothing, which makes this site both a suspect and cheap to remove. |

These are hypotheses from reading the code. None has been shown to be the source.

## Expected behavior

A Batty launch logs no `Geometry action is cycling` Fault. The offending `onGeometryChange` action is restructured per `docs/swiftui-observation-rules.md`, so ownership of the write changes and the geometry settles. Hopping the write into a `Task` is forbidden by the same doc; see the #0229 note in `AGENTS.md`.

## Notes

- Bisect before changing anything. For each candidate in turn, temporarily comment it out or make it idempotent, then count the Fault per launch.
- On the host, a build-only check plus launching `Batty Beta` yourself is fine. Don't relaunch or kill a Batty the user has running, and never run UI tests on the host (`AGENTS.md`). The count can also come from a VM run, since `app-warnings.log` already captures `com.apple.SwiftUI` messages.
- Useful probe: `log stream --predicate 'process == "Batty Beta" AND eventMessage CONTAINS "Geometry action is cycling"'` while launching.
- Candidate 1 is on the terminal-host path. Read `docs/view-hierarchy.md` and `docs/terminal-pane-requirements.md` before touching it. The placement mechanism is non-negotiable architecture.
- Candidate 5: before deleting it as dead, grep again for any reader, including key-path strings.
