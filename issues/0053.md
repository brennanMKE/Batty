# 0053 — Clicking a tab chip in a non-focused pane should focus that pane

| | |
|---|---|
| **Status** | open |
| **Module** | Tabs / Pane |
| **Platform** | macOS |
| **First seen** | 2026-05-11 |

## Description

`#0051` covers click-to-focus for the *terminal surface* (clicking on the body of a non-focused pane should set `tree.focusedPaneID` to that pane). This issue covers the symmetric case of clicking a **tab chip** inside a non-focused pane's tab bar. Today, clicking a chip updates the **pane-local** `activeTabID` (via SlidingTabs' tap handler), but does not update `tree.focusedPaneID`. So a user who clicks a chip in a non-focused pane sees the tab selection change *but the pane is still not focused* — typing then either goes to the previously-focused pane, or worse, lands ambiguously somewhere.

The user's mental model is that clicking *anywhere* visible inside a pane — tab bar, terminal body, scrollback, even the drag-drop highlight — focuses that pane. The chip is part of the pane; clicking it should focus the pane.

`#0051`'s "Out of scope" section explicitly punted the chip case to a follow-up, citing "SlidingTabs's tap-to-select already handles it." That was incorrect — SlidingTabs only sets `activeID` inside its `items` binding; it has no knowledge of session-level pane focus.

## Steps to reproduce

1. Open a session with two panes (`Cmd-D`). Pane B is focused (newly-split panes take focus).
2. Add a couple of tabs to pane A (the non-focused pane) — `Cmd-T` while focus is in A.
3. Re-focus pane B (`Cmd-Option-Right` or wait until #0051 lands and click in B's terminal).
4. Click any chip in pane A's tab bar. **Expected:** that chip becomes A's active tab, *and* pane A becomes the focused pane. **Actual:** A's active tab changes, but `tree.focusedPaneID` is still B; subsequent `Cmd-D` splits B, not A.

## Expected behavior

Clicking a tab chip in pane X — regardless of whether X is currently focused — should:

1. Set `pane.activeTabID = clickedTabID` on X (already happens via SlidingTabs).
2. Set `session.tree.focusedPaneID = X.id`.

In that order, ideally in one user-perceived action. Both writes are tiny model updates; no animation choreography needed.

## Actual behavior

`SlidingTabBar` accepts an `activeID: Binding<UUID?>` and writes to that binding when a chip is tapped. `PaneView` passes `activeIDBinding` (lines 173–180 of `PaneView.swift`) which mutates `pane.activeTabID`. That binding has no awareness of `tree.focusedPaneID`, so the pane-focus marker stays put.

## Notes

- Two implementation paths:
  - **In `activeIDBinding`'s setter:** when the binding's `set` fires, also call something like `appStore?.focusPane(id: pane.id)` (a new helper on `AppStateStore`, paired with the one #0051 needs). One-line change in `PaneView`. Clean because the same write path that updates the active tab also updates pane focus.
  - **In a separate `.simultaneousGesture` on the chip:** less clean — duplicates the tap detection, and we have less control over hit-testing inside SlidingTabs.
- Prefer the binding setter path. It also covers `selectTab(at:)` if we eventually route programmatic tab selection through the same setter.
- The `.contextMenu { tabContextMenu(for: tab) }` modifier on each chip means right-clicking a chip in a non-focused pane currently raises that pane's context menu without focusing the pane. Arguably the menu should also focus the pane on open; v1 can punt unless it shows up in practice.
- `AppStateStore.focusPane(id: UUID)` — proposed helper. Walks `sessions` to find the owning session, then writes `session.tree.focusedPaneID = id` (and possibly `selectedSessionID = session.id` if the click was in a non-selected session — but cross-session tab clicks shouldn't be possible since only the selected session is on-screen).
- Related: `#0051` (click in terminal body), `#0052` (visual indication that focus moved). All three together close the loop — the user can click anywhere in a pane, they can see the focus move, and subsequent commands target the clicked pane.

## Acceptance criteria

- Clicking any tab chip in any pane (focused or not) sets that pane as the focused pane.
- The active-tab marker inside the clicked pane updates correctly (existing behavior, must not regress).
- `Cmd-D` immediately after the click splits the clicked pane, not the previously-focused one.
- No re-entrancy: writing `focusedPaneID` from the chip-click path doesn't trigger a re-render that re-fires the click handler.
- Right-clicking a chip (for the context menu) does NOT cause unexpected focus changes — context menu remains a passive read-only interaction unless we explicitly decide otherwise.

## Out of scope

- Click-to-focus on the terminal surface body (tracked in `#0051`).
- Visual feedback that focus changed (tracked in `#0052`).
- Focusing a *session* in the sidebar — already works via `List` selection.
