# 0337 — Closing a Pane moves focus to the first Pane instead of the most recently focused surviving Pane

| | |
|---|---|
| **Status** | resolved |
| **Module** | Split / Pane |
| **Platform** | macOS |
| **First seen** | 2026-08-19 |
| **Closed** | 2026-09-05 |
| **Branch** | issue/0337 |

## Description

When the focused Pane is closed, focus lands on the Split tree's **leftmost
leaf** — in practice the Session's original "main" Pane — rather than on the
Pane the user was in before. Working with two or three temporary Panes and
closing them one at a time therefore requires manually re-focusing after
every close, and each close drops the user into the one Pane they did not
want to touch.

The behavior is not a race or a view-layer artifact: it is a single line of
model code choosing a positional fallback, and there is **no per-Pane focus
history anywhere in the app** for it to choose from instead.

## Steps to reproduce

1. Launch Batty. A Session opens with one Pane (call it **Main**), which is
   the tree's only leaf and therefore its first leaf.
2. Split three times from Main (`Cmd-D` / `Cmd-Shift-D`), producing Panes
   **A**, **B**, **C**. Each split focuses the new Pane
   (`SplitTree.splitFocusedPane` / `splitPane`, `SplitTree.swift:174`, `:204`,
   `:283`).
3. Click into **A**, then **B**, then **C** — focus history, if it existed,
   would now read C → B → A → Main.
4. With **C** focused, close it: `Cmd-W` on its last Tab, or
   `batty pane close` targeting it.
5. Observe which Pane is focused. Repeat for **B**, then **A**.

## Expected behavior

- Closing the focused Pane moves focus to the **most recently focused
  surviving Pane** in that Session — closing C focuses B, then closing B
  focuses A, then closing A focuses Main. Three temporary Panes can be used
  and dismissed in order with no manual re-focus.
- When no focus history is available for the Session (fresh Session,
  restored state, a Pane that was never focused), fall back in this order:
  the closed Pane's **adjacent sibling subtree** (the subtree that absorbed
  its space), then that subtree's nearest leaf. Only when nothing else
  resolves does the current leftmost-leaf behavior remain acceptable.
- Closing a Pane that was **not** focused must still leave focus exactly
  where it was — that already holds today and must not regress
  (`AppStateStoreClosePaneTests.closingAPaneLeavesAnAlreadyVisibleSiblings
  HiddenStateAlone`).
- Focus must never land on a hidden Pane (#0256's invariant), and the
  fallback chain must skip hidden Panes rather than un-hide one when a
  visible candidate exists.

## Actual behavior

Focus is reassigned to the tree's leftmost leaf. The choice is made in one
place, reached by every close path:

- `BattyKit/Sources/BattyKit/Model/SplitTree.swift:305-307` —
  `removePane(id:)`:

  ```swift
  if !newRoot.contains(paneID: focusedPaneID) {
      focusedPaneID = newRoot.firstLeafPaneID
  }
  ```

- `BattyKit/Sources/BattyKit/Model/SplitTree.swift:288-294` —
  `removeFocusedPane()` does the same unconditionally:
  `focusedPaneID = newRoot.firstLeafPaneID`. (No production caller found:
  its only caller is `SessionRuntime.closeFocusedTab()`,
  `BattyKit/Sources/BattyKit/Runtime/SessionRuntime.swift:71-78`, which
  itself has no production call site — the shipping ⌘W path is
  `WindowRuntime.closeFocusedTab()`. Any fix should still cover it or delete
  it, so the two do not drift.)

- `firstLeafPaneID` is defined at
  `BattyKit/Sources/BattyKit/Model/SplitTree.swift:33-40` and recurses into
  the **left** child at every split — i.e. leftmost/topmost leaf, which for
  a Session split outward from its original Pane is that original Pane. That
  is exactly the "always the main Pane" the report describes.

The one secondary reassignment is also positional:

- `BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift:410-412` — when the
  leaf `removePane` picked turns out to be hidden, focus moves to
  `session.tree.visiblePanes.first`, again a positional first, not a
  recency-based choice.

### Do the close paths diverge?

Both entry points converge on the same `SplitTree.removePane` line, so the
bug is shared — but they are not the same routine, and a fix must touch
both:

| Entry point | Route | Hidden-Pane fixup (#0256) |
|---|---|---|
| ⌘W / menu "Close Tab"/"Close Pane" / Command Palette / Tab chip ✕, `.terminal` Pane whose last Tab closes | `WindowRuntime.closeFocusedTab()` → `closeTab(id:)` → `session.tree.removePane(id:)` (`WindowRuntime.swift:219`) | **No** — the tab-cascade path has no post-remove focus fixup at all |
| ⌘W on a **non-terminal** Pane (#0334) | `closeFocusedNonTerminalPane` → `WindowRuntime.closePane(id:refuseIfAppsLastPane:)` (`WindowRuntime.swift:309`, `:375`) | Yes (`WindowRuntime.swift:396-416`) |
| CLI `batty pane close` over XPC (#0283) | `PaneCommand.swift:166` → `AppServiceClient.paneClose` → `AppXPCService.swift:154` → `AppStateStore.closePane(id:)` (`AppStateStore.swift:477-480`) → `WindowRuntime.closePane` | Yes (same block) |

So: one shared positional choice in the Model layer, plus a Runtime-layer
fixup that exists on the `closePane` branch and not on the `closeTab`
cascade branch.

## Root cause analysis

**No most-recently-used / focus-history state exists for Panes anywhere in
the app.** A repo-wide search for `mru`, `mostRecent`, `recentlyFocused`,
`focusHistory`, `focusStack`, `lastFocused`, `previouslyFocused` across
`BattyKit/` and `Batty/` returns nothing. The complete focus state for a
Session is the single scalar `SplitTree.focusedPaneID`
(`SplitTree.swift:99`); when the Pane it names disappears, there is no
record of what was focused before it, so the only thing `removePane` can do
is pick a Pane by position — and it picks the first leaf.

This was a knowingly deferred v1 simplification. #0021 (closed) wrote it
down at the time:

> **`focusedPaneID` after collapse** is reset to `newRoot.firstLeafPaneID`.
> That's defensive; arguably the user would prefer the *sibling* (geometric
> neighbor) to take focus, since they were "in" the closed pane and the
> sibling is the natural next target. v1 simplicity wins; revisit when
> there's geometric pane-frame data (#0020).

Both of that note's preconditions have since landed: geometric Pane frames
exist (`PaneFrameTracker` / `SessionRuntime.paneFrames`,
`BattyKit/Sources/BattyKit/Commands/PaneFocus.swift:13-17`, fed from
`SessionDetailView.swift:201`), and structural position data exists
(`SplitTree.panePositions()`, `SplitTree.swift:673-734`). This issue is the
revisit — with the added finding that geometric adjacency alone would *not*
satisfy the report: the user wants recency order, which needs state that
does not exist yet.

The Session-level equivalent of this bug was already fixed. #0067 ("Closing
the focused session selects Session 1 instead of the previous sibling")
replaced a `sessions.first` fallback with index adjacency, and that fix is
still in place at `WindowRuntime.swift:130-133`:

```swift
if selectedSessionID == id {
    let newIndex = max(0, index - 1)
    selectedSessionID = sessions.indices.contains(newIndex) ? sessions[newIndex].id : nil
}
```

Panes never received the analogous treatment.

## Proposed fix sketch

1. **Add a per-Session (Window-scoped by containment) Pane focus stack.**
   Recency is per Session because `focusedPaneID` is per Session; a Window
   holds many. The natural home is `SessionRuntime` beside `paneFrames`
   (`SessionRuntime.swift:26`) — an `@ObservationIgnored` ordered `[UUID]`,
   most-recent-first. Marking it `@ObservationIgnored` matters: the stack is
   bookkeeping no view should re-render on, and `paneFrames` sets the
   precedent.
2. **Push on focus change, in one place.** `WindowRuntime.focusPane(id:)`
   (`WindowRuntime.swift:429-445`) already guards the equal-value write and
   is the single choke point for deliberate focus moves. Any other direct
   `session.tree.focusedPaneID = …` write must be routed through it or push
   explicitly — the direct writes at `WindowRuntime.swift:412`, `:477`,
   `:532`, `:562`, `SplitTree.swift:174`, `:204`, `:283`, `:293`, `:306`,
   and `SessionRuntime.focusPane(adjacent:)`
   (`PaneFocus.swift`, `tree.focusedPaneID = best`) are the full inventory
   to audit. Leaving any of them un-pushed silently degrades the stack to
   stale entries.
3. **Prune on close.** Remove the closed Pane's id from the stack *and*
   drop any id no longer present in the tree, so a closed Pane can never be
   re-selected and the stack cannot grow without bound. Prune before
   selecting the successor.
4. **Select the successor by recency, with a positional fallback chain.**
   Replace the bare `focusedPaneID = newRoot.firstLeafPaneID` decision with:
   first surviving, visible entry in the recency stack → the sibling subtree
   that absorbed the closed Pane's space → that subtree's nearest leaf →
   `firstLeafPaneID` as the last resort. `SplitTreeNode.removingPane` already
   knows which subtree was promoted, so the sibling is derivable without new
   geometry.
5. **Cover both close routes.** The recency lookup has to run for the
   `closeTab` cascade (`WindowRuntime.swift:219`) as well as
   `closePane` (`WindowRuntime.swift:392`). Putting the successor choice
   inside `SplitTree.removePane` covers both by construction, but
   `SplitTree` is Model-layer and must not reach into Runtime types — pass
   the recency list in, or return the removed subtree's replacement so the
   Runtime layer decides. Either shape is fine; a fix that patches only
   `WindowRuntime.closePane` leaves the ⌘W path (the one in the report)
   unfixed.
6. **Keep #0256's hidden-Pane invariant.** Whatever the recency stack
   returns must be filtered for `isHidden` before it is written, so the
   existing `WindowRuntime.swift:396-416` guarantee still holds, and it
   should hold for the `closeTab` cascade too rather than only for
   `closePane`.

## Acceptance criteria

- Splitting three Panes from a main Pane, focusing them in order, then
  closing the focused Pane three times in a row walks focus back through
  A → B → Main (or equivalent for the chosen ordering) with no manual
  re-focus at any step.
- The main Pane is focused after a close only when it genuinely is the most
  recent surviving Pane in the focus history.
- Closing a **non-focused** Pane leaves focus untouched.
- Focus never lands on a hidden Pane after a close; a hidden most-recent
  entry is skipped in favor of the next visible one.
- The behavior is identical whether the Pane is closed via ⌘W (last Tab of a
  `.terminal` Pane), ⌘W on a non-terminal Pane, or `batty pane close`.
- A closed Pane's id is never re-selected later — the stack is pruned, not
  merely popped.
- New unit tests in `BattyKit/Tests/BattyKitTests/` cover, at minimum:
  - the three-sequential-closes walk-back described above, asserting
    `session.tree.focusedPaneID` after each close;
  - the main Pane is *not* focused after the first close when a more recent
    survivor exists;
  - closing a non-focused Pane does not move focus;
  - the fallback when no history exists picks the sibling subtree, not the
    leftmost leaf, and never a hidden Pane;
  - both `AppStateStore.closePane(id:)` (the XPC route) and the
    `WindowRuntime.closeTab` last-Tab cascade produce the same successor.
    `AppStateStoreClosePaneTests.swift` is the right home for the first and
    `CloseTabCascadeTests.swift` for the second.
- `scripts/build.sh unit` passes with the new tests observed running.

## Gotchas

- **`docs/swiftui-observation-rules.md` is binding here** — this is a
  focus-flow change, which the doc governs explicitly.
- **Every focus write must stay event-origin.** Pushing onto the recency
  stack belongs with the code that *causes* the focus change (a click, a
  keyboard command, a close action), never in `body`, a view `init`, an
  `NSViewRepresentable` update, or a preference reduction. Do not derive
  recency from a geometry/layout `onChange` — `SessionDetailView` already
  feeds `paneFrames` from a preference-change handler, and layering focus
  intent onto that flow makes it layout-origin.
- **Do not fix a mutate-during-update violation with a `Task` hop.** If the
  new write path trips "Modifying state during view update", restructure
  which code owns the write. The #0229 click-to-focus regression is exactly
  this mistake, and it is the case study at the end of the observation-rules
  doc.
- **`@Observable` notifies on equal-value writes.** `focusPane(id:)`
  (`WindowRuntime.swift:438`) already guards with an inequality check for
  this reason; any new setter must do the same, or every close ripples a
  no-op invalidation through every `PaneView`.
- **The Surface registry is the source of truth for live Terminal
  Sessions.** Closing a Pane already releases each Tab's terminal view
  (`TerminalHostStore.shared.releaseTerminalView(forTabID:)`,
  `WindowRuntime.swift:391`) before the tree mutation. Recency bookkeeping
  must not reorder relative to that teardown, must never hold a strong
  reference to a `PaneRuntime`/surface (store `UUID`s only, per the
  architectural rule in `CLAUDE.md`), and must not cause a surviving Pane's
  surface to be released or a closed Pane's id to be handed back to the
  focuser.
- **The stack must not resurrect ids across Sessions.** `focusPane(id:)`
  deliberately does not change the selected Session; a per-Session stack
  keeps that property for free, whereas a Window-wide stack would need an
  explicit guard.
- **`AppStateStore.closePane` refuses the app's last Pane**
  (`.refusedLastPane`, `AppStateStore.swift:477-480`). A refused close must
  leave the recency stack untouched — prune only on an actual `.closed`
  outcome, or a refusal will silently corrupt the ordering.
- **#0381's three XPC focus writers must feed the same recency stack.**
  `AppStateStore.focusPaneForXPC(id:)`, `.focusTabForXPC(id:)`, and
  `.focusSessionForXPC(id:)` write `focusedPaneID`/`activeTabID` directly
  today (there is no recency stack for them to push onto yet). Once this
  issue introduces per-Pane focus history, wire all three into it —
  otherwise closing a Pane right after `batty pane focus`/`batty tab focus`
  falls back to the wrong Pane instead of the one an agent just brought to
  the human's attention.
- **(Implementer, review round 1) Keyboard-follow after ⌘W is unverified.**
  Unit tests confirm `SplitTree.focusedPaneID`/the recency-chosen Pane is
  correct after every close path, and the model→AppKit focus-follow
  direction was traced and found intact — but no unit test can show that
  after ⌘W closes a Pane, *keyboard input* actually lands in the
  recency-chosen Pane rather than only the highlight moving there
  (`docs/swiftui-observation-rules.md`'s checklist item 5: "Focus and click
  behavior cannot be signed off by compilation or unit tests"). That needs
  a manual pass or a UI test.

- **`./build.sh ui BattyUITests/PaneFocusTests` should be run before this is
  closed.** `docs/swiftui-observation-rules.md` checklist item 5 states focus and
  click behavior cannot be signed off by compilation or unit tests, and this
  change adds a `didSet` to the property every focus write goes through — the
  #0229 blast radius. That class is 8 existing tests, needs no new ones, and is
  the direct regression guard for split-focus, click-to-focus, and
  Cmd-Option-arrow. It was not run here (UI tests lock the machine).
- **Keyboard-follow after Cmd-W is unverified.** No unit test can show that after
  closing a Pane the *keyboard* lands in the recency-chosen Pane rather than only
  the highlight moving. `BattyUITests/PaneFocusTests.swift` has no close coverage
  at all; adding one is worth a follow-up rather than widening this issue.
- **`resolveHiddenFocusFallback`'s doc comment and log line are now inaccurate.**
  Both assert that reaching the guard with a hidden focused Pane implies
  `visiblePanes` is empty. Review found a production path where that is false:
  `WindowRuntime.jumpToTab` (`:745`, reached from `OpenQuicklyView.swift:149`)
  writes `focusedPaneID` with no `isHidden` check and no un-hide, so Open Quickly
  onto a hidden Pane followed by closing a different Pane reaches the guard with
  visible Panes present. The behavior is correct and arguably better — the Pane
  the user navigated to gets un-hidden rather than silently abandoned — but the
  `logger.notice` saying "left with no visible panes" will lie to a future
  debugger. The underlying `jumpToTab` hole is pre-existing.

## Design decision (implementation, branch `issue/0337`)

**Structure chosen:** the recency stack lives directly on `SplitTree`
(`@ObservationIgnored private var focusHistory: [UUID]`, most-recent-first),
not on `SessionRuntime` as the fix sketch proposed. `SplitTree` is already
1:1 with a `SessionRuntime` (`SessionRuntime.tree`), so "per-Session" falls
out for free either way; putting it on `SplitTree` let `focusedPaneID`
itself gain a `didSet` that pushes on every write, which becomes the single
choke point the fix sketch's item 2 asked for — no per-call-site audit of
`WindowRuntime.swift`/`PaneLayout.swift`/`PaneFocus.swift`/`PaneView.swift`
was needed or performed; every direct `tree.focusedPaneID = …` write in the
codebase is automatically covered, including ones outside this issue's own
diff (`PaneLayout.swift`'s layout-apply writes, `PaneFocus.swift`'s
Cmd-Option-arrow movement). **Alternative rejected:** a `SessionRuntime`-side
stack with an explicit `recordFocus(_:)` method every writer must
remember to call — rejected because it reintroduces exactly the
audit-every-call-site risk the fix sketch flagged as its own biggest hazard.

**The five decisions:**
1. **Remembered Pane is the one being closed:** its id is pruned from the
   stack before a successor is chosen (`SplitTree.removePane`), so it can
   never be its own successor.
2. **Remembered Pane is hidden:** filtered out at *every* step of the
   fallback chain — the history lookup, the sibling-subtree lookup, and the
   final positional fallback — via `isHidden`/`firstVisibleLeafPaneID`. Only
   the absolute last resort (`firstLeafPaneID`) can still land on a hidden
   pane, when literally no visible pane survives. Because the Model chain
   already guarantees a *visible* successor whenever any visible Pane
   survives in the session, `WindowRuntime.resolveHiddenFocusFallback(in:)`
   (generalized from the pre-existing `closePane`-only fixup to also cover
   the `closeTab` cascade) only has one real branch left: un-hide the
   focused Pane itself when it's the only one left (review round 1 found an
   earlier "move to `visiblePanes.first`" branch here was dead code and it
   was removed). Un-hiding is Runtime-layer work (`TerminalHostStore`
   placements, content lifecycle) a Model-layer type must not perform.
3. **A whole subtree is removed at once:** unaffected — `SplitTree
   .removePane(id:)` is the one routine both `closeTab`'s cascade and
   `closePane` funnel through, so a cascade that also empties the session
   hits `removePane`'s own `guard let newRoot = SplitTreeNode
   .removingPane(...) else { focusHistory.removeAll(); return true }`
   branch and never consults a stack for a session about to disappear.
4. **Per-Session vs. per-Window:** per-Session (via `SplitTree`), matching
   `focusedPaneID`'s own scope, for the same reason the fix sketch gave —
   `focusPane(id:)` deliberately never changes the selected Session, and a
   per-Session stack keeps that property for free.
5. **Eviction:** on every `removePane(id:)` call, the stack is filtered to
   drop the closed id and any id no longer present in the tree — bounded by
   the tree's own pane count, never independently unbounded.

**Correction (review round 1):** an earlier version of this note claimed
the history-lookup step's hidden-Pane filter could only be proven by
bypassing `AppStateStore.closePane`/`WindowRuntime.closePane` and calling
`SplitTree.removePane` directly, because `resolveHiddenFocusFallback(in:)`
"silently corrects the wrong Model-layer answer." That is true only when
the fixture makes the Runtime-layer backstop's own answer
(`visiblePanes.first`) coincide with the correct recency answer — it does
not in general. **The filter is observable through the production
`closePane` path** whenever the recency answer and `visiblePanes.first`
differ: `AppStateStoreClosePaneTests
.closingFallsBackToTheMostRecentVisibleHistoryEntryNotTheFirstVisiblePane`
builds a tree where the most-recently-focused *visible* survivor is not
the same Pane the backstop would fall back to, and goes red when the
filter is dropped (confirmed by mutation). The Model-layer-only test
(`SplitTreeFocusHistoryTests
.theHistoryLookupItselfSkipsAHiddenEntryRankedAheadOfAVisibleOne`) is kept
as well, purely as the minimal isolation case with no Runtime layer in the
call path at all. Full mutation-testing results are in the implementer's
report.
