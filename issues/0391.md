## Description

**This blocks the entire release pipeline. `scripts/release.sh` cannot produce an artifact at all until it is resolved.** Every optimized (`-O`) build of `BattyKit` crashes the Swift compiler, so archive → sign → notarize → DMG never gets past the first step. The issue is small in code terms and total in effect: no Release build of Batty can be cut, universal or otherwise.

Debug builds are unaffected — `./build.sh`, `./build.sh unit`, and every Beta build compile and run normally. That is why this went unnoticed: no Release build had been cut since the offending type landed with #0361, and the crash only exists under optimization.

The crash is in `swift-frontend` itself, not in any project diagnostic. Verbatim from the build output:

```

  SIL Debug Info Generator } on SIL for BattyKit)
While running pass #1502939 SILFunctionTransform "EarlyPerfInliner"
  on SILFunction "@$s8BattyKit24SingleSlotRetrySchedulerCfD".
 for 'deinit' (at BattyKit/Sources/BattyKit/XPC/SingleSlotRetryScheduler.swift:16:20)
```

Crashing frame, from the stack dump — note the repeated frame, a recursion in the layout-constraint compatibility check:

```
4  swift-frontend  isCallerAndCalleeLayoutConstraintsCompatible(swift::FullApplySite) + 236
5  swift-frontend  isCallerAndCalleeLayoutConstraintsCompatible(swift::FullApplySite) + 236
```

## Steps to reproduce

1. Be on `main` with no workaround applied (the stash below not popped).
2. Run a Prod Release archive:

   ```bash
   ./build.sh release archive -archivePath dist/Batty.xcarchive -configuration Release
   ```

3. `swift-frontend` crashes while optimizing the `BattyKit` module.

## Expected behavior

A Release archive builds, producing `dist/Batty.xcarchive`, so `scripts/release.sh` can carry on to signing, notarization, and DMG creation.

## Actual behavior

`swift-frontend` crashes in the SIL optimizer. No archive is produced, and the release pipeline stops at its first step.

## Notes

### The type involved

`BattyKit/Sources/BattyKit/XPC/SingleSlotRetryScheduler.swift` defines
`public final class SingleSlotRetryScheduler<Handle>` — a small, ordinary,
dependency-free class holding exactly two stored properties:

- `private var pending: Handle?` — the at-most-one deferred handle
- `private let cancel: (Handle) -> Void` — the closure used to cancel one

Its API is `init(cancel:)`, a computed `hasPending: Bool`, `replace(with:)`
(cancels whatever was pending, then stores the new handle), and `clear()`
(cancels the pending handle and nils the slot). It is generic over the handle
type specifically so the "replacing cancels the old one" invariant is testable
without `Dispatch` — `SingleSlotRetrySchedulerTests` exercises it with `Int`
stand-ins. The single production instantiation is in
`BattyKit/Sources/BattyKit/XPC/AppXPCCoordinator.swift:65`:

```swift
private let backoffRetryScheduler = SingleSlotRetryScheduler<DispatchWorkItem> { $0.cancel() }
```

backing `AppXPCCoordinator`'s self-healing backoff retry from #0361.

**There is no explicit `deinit` anywhere in the source.** The mangled name
`$s8BattyKit24SingleSlotRetrySchedulerCfD` demangles to the *deinit* of the
class, and the compiler is crashing on the **implicit** one it synthesizes.
The cited location `:16:20` is the class declaration line itself —
`public final class SingleSlotRetryScheduler<Handle> {`, column 20 being the
`S` of the type name — which is where a synthesized member gets attributed.

### Facts, each established by an actual build — not inferred

- **Not architecture-specific.** The crash first appeared compiling the
  `x86_64` slice. A rebuild forced with `ARCHS=arm64 ONLY_ACTIVE_ARCH=NO`
  crashed identically on arm64.
- **Debug is fine.** Only `-O` triggers it; every Beta/Debug build in this
  project builds and runs.
- **The workaround is one behaviour-neutral line.** Adding an explicit empty
  `deinit {}` to the class produced `ARCHIVE SUCCEEDED`.

Toolchain at the time of the crash: `Apple Swift version 6.3.3
(swiftlang-6.3.3.1.3 clang-2100.1.1.101)`, Xcode 26.6 (17F113), with
`-swift-version 6` (`SWIFT_VERSION = 6.0` in `Configuration/Build.xcconfig`,
`swiftLanguageModes: [.v6]` in `BattyKit/Package.swift`), `-O`,
`-enable-default-cmo` (SwiftPM's default for a release library build), and
`-default-isolation MainActor` (`.defaultIsolation(MainActor.self)` in
`Package.swift`'s shared `swiftSettings`).

### The workaround is stashed, not committed — restore it, don't rediscover it

It is sitting in the stash, taken off branch `issue/0390`:

```bash
git stash list       # "On issue/0390: 0391 compiler-crash workaround"
git stash show -p 'stash@{0}'
```

The whole diff is an explicit empty `deinit {}` plus a comment explaining why it
exists. Whoever picks this up should restore or re-apply that rather than
re-deriving it.

**The workaround must stay behaviour-neutral.** The empty body is deliberate.
Making the `deinit` call `clear()` would cancel the pending handle on
deallocation — a real semantic change, and one that belongs to **#0367**, not
here. Keep the body empty; keep the comment that says why.

### This is an upstream compiler bug, not a defect in this project's code

`SingleSlotRetryScheduler` is ordinary Swift: a final class, two stored
properties, no unusual generics constraints, no `@_` attributes. A synthesized
`deinit` should not crash the optimizer, and the recursion visible in
`isCallerAndCalleeLayoutConstraintsCompatible` points at a compiler-side
problem in the performance inliner's eligibility check.

**Recommendation for the user to decide, not a task:** this is worth reporting
to Apple (Feedback Assistant) and/or swift.org with a reduced test case. The
stack trace, the exact toolchain, the `-O` / `-enable-default-cmo` /
`-default-isolation MainActor` flag set, and the both-architectures result above
are already most of a bug report; a standalone reduction of the class would
finish it.

### Verification for whoever fixes it

A full Release archive must succeed:

```bash
./build.sh release archive -archivePath dist/Batty.xcarchive -configuration Release
```

Two things about that command:

- `./build.sh` now **defaults to the Beta scheme**; `release` is the only path
  that selects the Prod scheme. Plain `./build.sh archive` builds Beta and
  proves nothing here. (Note `CLAUDE.md` still refers to `scripts/build.sh`,
  which no longer exists — `./build.sh` at the repo root is the entry point,
  as `issues/Issues.md` describes.)
- **A universal archive is the real gate.** The arm64-only build was used only
  to isolate the crash and show it was not architecture-specific. A public
  release must build both slices, so verification must not pass `ARCHS=arm64`
  or `ONLY_ACTIVE_ARCH=YES`.

The current release artifacts are **not** evidence that the universal Release
path works. `dist/Batty.xcarchive` and `dist/Batty-prerelease.dmg` (built at
`cc059e0`) were both produced arm64-only *with the workaround applied* —
`lipo -archs` on the app inside each reports `arm64` alone.

### Relation

- **#0367** — same type (`SingleSlotRetryScheduler`), **distinct problem; do not
  merge the two.** #0367 is a runtime-semantics issue: nothing tells the
  scheduler that a scheduled handle has *fired*, so the slot is never cleared on
  execution and `hasPending` reads a stale `true` until the next `replace(with:)`
  or `clear()`. Its fix adds a "mark fired" path (or a self-clearing wrapped
  handle) and grows the test suite. This issue (#0391) is a **build/toolchain**
  problem whose entire fix is a behaviour-neutral empty `deinit {}` to dodge a
  compiler crash. Fixing #0367 does not fix this, and the tempting shortcut —
  "just make the `deinit` call `clear()`, it fixes both" — is wrong: it silently
  imports #0367's semantic change into a release unblock, and it is not what
  #0367 asks for either.
- **#0361** — introduced `SingleSlotRetryScheduler` and its only production
  caller. That is when the crash became latent; it stayed invisible until a
  Release build was next attempted.



## Resolution notes

> 🟢 Resolved 2026-09-02 — an explicit empty `deinit {}` on
> `SingleSlotRetryScheduler` sidesteps the swift-frontend 6.3.3 crash, and a
> universal Release archive builds again.

## Root cause

Not a defect in this project's code. `swift-frontend` 6.3.3 crashes in the SIL
`EarlyPerfInliner` while compiling `BattyKit` at `-O`, on the **implicit**
deinit of `public final class SingleSlotRetryScheduler<Handle>`. Debug builds
never reach that optimizer path, so the crash was invisible to every gate the
project ran — no Release build had been cut since the class landed with #0361.

## Fix

An explicit `deinit {}`, deliberately empty. Writing any explicit deinit
sidesteps the inliner path that crashes on the synthesized one. The comment
records three things: that the defect is in `swift-frontend` rather than in
this class, the exit criterion (delete it once the toolchain moves past 6.3.3
and confirm the Release archive still succeeds), and that the body must stay
empty — calling `clear()` would cancel the pending handle on deallocation,
which is a real behavior change belonging to #0367.

## Review

Reviewed by `claude-opus-5`, one round, request-changes then satisfied. It
verified the fix independently rather than trusting the report: re-ran the unit
suite, and checked the archive from the artifact — `Info.plist` showing
`Architectures {x86_64, arm64}` and a `CreationDate` postdating the fix commit,
plus its own `lipo -archs`. It also confirmed isolation is unchanged (an
explicit `deinit` stays nonisolated by default under
`.defaultIsolation(MainActor.self)`, so no dealloc-time actor hop) and that
#0367's territory is untouched. Its two blocking items were comment-only — a
missing exit criterion and no plain statement that the bug is upstream — both
added verbatim. The orchestrator verified the final text against what review
specified rather than spending a second full review round on a comment edit.

- `./build.sh release archive -archivePath dist/Batty.xcarchive -configuration Release`

## Gotchas

- **The crash does not reduce to a standalone test case.** Four minimal repros —
  a generic class with a closure-typed stored property, a non-generic variant, a
  generic one without the closure, and the real `DispatchWorkItem` call pattern —
  all compiled cleanly at `-O -swift-version 6 -default-isolation MainActor
  -enable-default-cmo`. This is an inference from four negative attempts, not
  proof, but it is well supported: the crash is in `EarlyPerfInliner`'s
  eligibility check on pass **#1502939**, a counter only a large module reaches,
  and the production instantiation lives in a different file
  (`AppXPCCoordinator.swift:65`), reachable only through whole-module plus
  `-enable-default-cmo`. **Anyone filing this upstream needs a reduction that
  carries the caller and the module, not just the type** — a two-file repro will
  not reproduce it.
- **One other generic class exists in the codebase** and is currently unaffected:
  `public nonisolated final class XPCOnce<Value: Sendable>`
  (`BattyKit/Sources/BattyXPCCore/XPCOnce.swift`), same shape, no explicit
  deinit. It compiled at `-O` in the successful archive, so it is empirically
  fine today — but it is the first place to look if this resurfaces on a
  different symbol.
- **The only detector is the Release archive itself.** That is why this went
  unnoticed for months: unit and UI tests both build Debug. `CLAUDE.md`'s Test
  strategy now documents the Release build as a gate.
- No test pins the empty-deinit invariant. About ten lines — a counting `cancel`
  closure, a nested scope, assert the counter stays 0 after dealloc — would make
  the comment's `MUST` enforced rather than asserted. It belongs with **#0367**,
  the next issue to touch this file and the one tempted to change the deinit.
