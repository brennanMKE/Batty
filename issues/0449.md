## Description

The first full Tart-VM run on `main` after #0413 landed — run
`build/ui-tests/20261009-160500-38943/`, whose `git archive HEAD` snapshot was `5da86e01`
(the runner does not record the SHA; the run id's 16:05:00 start falls between the #0413
commit at 16:04:45 and the #0448 commit at 16:08:52) — finished 105 tests with exactly one
failure:

```
BattyUITests/WindowRestorationTests.swift:166: error: -[BattyUITests.WindowRestorationTests testToggleSidebarAffectsOnlyKeyWindow] :
Failed to get matching snapshot: No matches found for first query match sequence:
`Descendants matching type Outline` -> `Elements matching predicate '"session-sidebar" IN identifiers'`,
given input Window, identifier: 'SwiftUI.PresentedWindowContent<BattyKit.WindowID, SwiftUI.ModifiedContent<Batty_Beta.ContentView, SwiftUI._BackgroundModifier<Batty_Beta.OpenWindowHookInstaller>>>-1-AppWindow-2'
```

The same test passed in every prior full run on record — `20261006-033829-79840`,
`20261006-035152-84796`, `20261009-144846-86583`, `20261009-150820-16116` (on #0445 =
`4b326408`, 76/76), and `20261009-154936-33306` (the #0413 branch itself) — each in ~6.5 s.
The failing run took 8.08 s.

This is not an `XCTAssertTrue failed` on the `waitFor` result. It is XCUITest recording a
failure *inside* the predicate: a property read on an `XCUIElement` whose query no longer
resolves. Because `setUpWithError` sets `continueAfterFailure = false`, that recorded failure
aborts the test before the `waitFor` can return.

### What line 166 asserts, and which window the failed query targeted

Line 166 is the first post-Cmd-B check (`WindowRestorationTests.swift:165-169`):

```swift
XCTAssertTrue(
    waitFor({ !newWinSidebar.exists || newWinSidebar.frame.width < expandedWidth / 2 },
            timeout: 5),
    "Key window's sidebar must collapse after Cmd-B"
)
```

`newWinSidebar` is `BattyUITestHarness.sidebar(in: newWindow)` (`BattyUITestHarness.swift:163-170`),
and `newWindow` is `window(withIdentifier: newWindowIdentifier, in: app)` — the window opened
by Shift-Cmd-N. The failure message's `given input Window, identifier: '…-AppWindow-2'`
names that **new** window (the original launch window is `…-AppWindow-1`; both appear in the
hierarchy attachment below). So the query that failed is the new, key window's sidebar
Outline — the one Cmd-B is *supposed* to collapse. The #0445 window lookup resolved
correctly; the `Outline` descendant under it did not.

### The trace shows the two property reads straddling the collapse

`xcodebuild.log` lines 3790–3817 for the failing run, after `Type 'b' key with modifiers '⌘'`
at t=5.02 s:

```
t = 5.16s Checking existence of `"session-sidebar" Outline`     ← newWinSidebar.exists  → true
t = 5.18s Find the "session-sidebar" Outline                    ← newWinSidebar.frame   → still wide
t = 5.26s Checking existence of `"session-sidebar" Outline`     ← exists → true
t = 5.28s Find the "session-sidebar" Outline                    ← frame  → still wide
t = 5.36s Checking existence of `"session-sidebar" Outline`     ← exists → true
t = 5.37s Find the "session-sidebar" Outline                    ← frame  → NO MATCH
t = 6.39s     Find the "session-sidebar" Outline (retry 1)
t = 7.42s     Find the "session-sidebar" Outline (retry 2)
t = 7.43s     Collecting debug information to assist test failure triage
…:166: error: … Failed to get matching snapshot …
```

Each `waitFor` iteration performs two independent AX round-trips: `exists` takes a snapshot
and finds the Outline; `frame` then re-resolves the same query against a *fresh* snapshot
(XCUIElement queries re-resolve on every property access — the class doc comment at
`WindowRestorationTests.swift:64-66` already says so). In the third iteration the Outline was
present for `exists` (t=5.36) and gone 10 ms later for `frame` (t=5.37). `XCUIElement.frame`
on a query with no match does not return `.zero`; it records "Failed to get matching
snapshot" as a test failure and, after XCUITest's own two retries, the test aborts.

Compare the most recent passing run (`20261009-154936-33306`, same test, after Cmd-B at
t=5.05 s):

```
t = 5.19s Checking existence / 5.20s Find     (iteration 1: exists → true, frame → wide)
t = 5.27s Checking existence / 5.28s Find     (iteration 2)
t = 5.36s Checking existence / 5.38s Find     (iteration 3)
t = 5.46s Checking existence of `"session-sidebar" Outline`     ← exists → false; `||` short-circuits; step 1 passes
t = 5.47s Checking existence of `"session-sidebar" Outline`     ← origSidebar.exists → true
t = 5.48s Find the "session-sidebar" Outline                    ← origSidebar.frame > half → step 2 passes
t = 5.49s Terminate
```

The passing runs pass because the collapse happened to land in the ~80 ms gap *between*
iterations, so the next `exists` read saw it gone and the `||` never reached `frame`. The
failing run's collapse landed in the ~10 ms gap *inside* an iteration, between `exists` and
`frame`. Same product behaviour, different interleaving. The predicate has a
time-of-check/time-of-use window on every iteration; the collapse is ~0.3–0.4 s after
Cmd-B, so roughly one in several runs will lose the race.

### The product did what the test wants

The "App UI hierarchy" attachment XCUITest captured at failure time (exported from
`UITests.xcresult` for this test, 138 KB, two copies) shows:

- `Window (Main)` … `-1-AppWindow-2` (the new, key window): `Group → SplitGroup →
  Group → tab-bar…, pane-eye-button…, pane-terminal…` — **no `session-sidebar` Outline
  anywhere under it**, and the toolbar button reads `label: 'Show Sidebar'`.
- `Window` … `-1-AppWindow-1` (the original window): `SplitGroup → … → Outline,
  {{69.0, 151.0}, {222.0, 490.0}}, identifier: 'session-sidebar', label: 'Sidebar'` with its
  `OutlineRow` still present — expanded, untouched.

That is exactly the expected end state: Cmd-B collapsed only the key window's Sidebar and
left the original window's alone. The test failed on the way to observing it.

## Steps to reproduce

1. Commit on `main` (the runner snapshots `git archive HEAD`).
2. `tools/run-ui-tests-vm.sh BattyUITests/WindowRestorationTests` (or the full suite).
3. Repeat. The failure is interleaving-dependent; 1 of 6 recorded full runs hit it.

## Expected behavior

`testToggleSidebarAffectsOnlyKeyWindow` passes deterministically whenever the product
collapses only the key window's Sidebar on Cmd-B — regardless of *when* within the test's
polling loop the AX tree drops the Outline.

## Actual behavior

Once in six recorded full VM runs the test aborts at line 166 with "Failed to get matching
snapshot" for the new window's `session-sidebar` Outline, even though the failure-time
hierarchy shows the Sidebar did collapse in that window and remained expanded in the other.

## Notes

### Candidate causes (recorded as open, not conclusions)

1. **Test-side TOCTOU in the line-166 predicate (strongest, per the traces above).**
   `!newWinSidebar.exists || newWinSidebar.frame.width < expandedWidth / 2` is two AX
   queries; the second can fail if the element vanishes after the first. The passing runs
   only pass because the `||` short-circuited on an `exists == false` read that happened
   to land between iterations. Note the test's own comment (`:157-164`) chose `!exists`
   over `!isHittable` specifically to be occlusion-independent, and the "or it shrinks"
   half was added to cover a `NavigationSplitView` that keeps the column in the tree at
   reduced width. Both halves are reasonable; it is their *sequencing inside one
   iteration* that is racy.

   Deterministic fixes that need no sleep (no `Task.sleep`, no `pause`, no timing
   assertions — AGENTS.md "Asynchronous tests" is binding):
   - Read one snapshot per iteration. For example, `waitFor` over
     `newWindow.outlines["session-sidebar"].allElementsBoundByIndex` (or the
     `collectionViews` / `.any` fallback `sidebar(in:)` would have picked), and treat
     `isEmpty` as collapsed and `first!.frame.width < half` as shrunk — a single query
     resolution feeds both branches.
   - Or wait on `!newWinSidebar.exists` alone first (the branch every passing run actually
     took), then evaluate `frame` only if the element still exists after that wait.
   - Or wait on an observable the collapse *produces* rather than on the disappearance:
     the new window's toolbar button flips from `label: 'Hide Sidebar'` to
     `label: 'Show Sidebar'` (visible in the hierarchy attachment); a single
     `waitForExistence` on that button in `newWindow` has no two-read window.

   Whatever shape is chosen, `origSidebar`'s check at line 173
   (`origSidebar.exists && origSidebar.frame.width > expandedWidth / 2`) has the mirror
   image of the same two-read structure and should be made single-read too, even though it
   never fails today (the original window's Sidebar never changes, so there is nothing to
   race against).

2. **Regression from #0413 (`5da86e01`).** That commit added
   `.accessibilityValue(session.id == windowRuntime.selectedSessionID ? "selected" : "unselected")`
   on the `session-row` (`SessionSidebarView.swift:90`), `.accessibilityValue(pane.isHidden ?
   "hidden" : "visible")` on `pane-eye-toggle` (`:374`), and
   `.accessibilityValue(isActive ? "active" : "inactive")` on `tab-chip` (`PaneView.swift:216`).
   None of these touch the `session-sidebar` identifier on the `List` itself, the
   `NavigationSplitView` column, or the Cmd-B handler, and the same test passed on the #0413
   branch run (`20261009-154936-33306`) with these edits already present. Weak candidate —
   listed because it is the only product change between the last pass and the failure, and
   a rerun on the same SHA is the cheapest way to rule it out.

3. **Regression from #0445 (`4b326408`, `window(withIdentifier:in:)`).** The helper only
   wrapped the predicate lookup the test already used (`git show 4b326408 --
   BattyUITests/WindowRestorationTests.swift` is a pure extraction). The failure message
   names the correct window (`AppWindow-2`), so the lookup resolved; and the test passed in
   two full runs on and after that commit. Weakest candidate.

4. **#0437-style key-window race (Cmd-B dropped or routed to the wrong window).** Ruled
   out for this run by the hierarchy attachment: the new window lost its Outline and the
   original kept its 222 pt one, so Cmd-B reached the right window. The class doc comment's
   #0437 caveat (`:72-84`) still applies to future runs but is not what happened here.

### Why no guest-side cause is suspected

`crashes/` is empty, the app pid (15561) stayed alive through the triage snapshots, and both
windows and their content were fully enumerable at failure time. Nothing in the trace
suggests the AX tree was slow to build; the Outline was present on every `exists` read.
