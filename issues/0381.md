# 0381 — No CLI verb focuses a Session, Pane, or Tab, so an agent cannot bring what it opened to the human's attention

| | |
|---|---|

## Description

`batty session focus`, `batty pane focus`, and `batty tab focus` are listed in #0257's Tier 1 verb surface and have had fully pinned semantics since its 2026-07-27 terminology amendment — and none of the three is built. Verified against `BattyKit/Sources/batty/`: `SessionNounCommand`'s subcommand list is `[SessionInfoCommand.self]`, `PaneNounCommand`'s is `[PaneSplitCommand.self, PaneCloseCommand.self]`, there is no `tab` noun at all, and `XPCVerb` has no focus verb of any kind.

This is *the* "show the human what I did" verb, and its absence is the largest hole in Batty as an agent control surface. An agent can create a Session, split a `git-status` Pane into it, and open a System Metrics dashboard — and if the developer is looking at a different Session, none of it is visible. The only tool the agent has is `batty notify`, which posts to the Bell Feed and hopes the human clicks. **`notify` tells; `focus` shows.** The pair is what makes "the agent drives the human's window to display project status" actually work.

## Expected behavior

Implement over XPC, reusing #0282's mutation-verb pattern (request payload, reply, `ok: false` → exit `4` for an unknown or stale id):

```
batty session focus <id>
batty pane focus <id>
batty tab focus <id>
```

Semantics are **already pinned** by #0257's 2026-07-27 terminology amendment; implement exactly those, do not re-litigate:

- **`pane focus <id>`** focuses that Pane and **leaves the Pane's selected Tab unchanged** — moving focus between Panes must never re-select Tabs.
- **`tab focus <id>`** selects that Tab if it is not already selected, and **implies focusing its containing Pane**.
- **All three verbs are activating.** The standing rule (#0257 Foundation §2) that a mutation aimed at a background Session must not switch the active Session names the focus verbs as its one explicit exception, and this is that exception. Focusing a Pane or Tab whose Session is not the selected Session **selects that Session**, and makes its containing Window key once multi-window exists — the same bring-forward chain a Bell Feed click-to-jump uses.

**Directional `pane focus <up|down|left|right>` is deferred.** #0257's table lists it, but id-based targeting is what an agent needs, and directional focus drags in split-tree geometry work with no agent-facing payoff. Say so in the help text so the omission reads as deliberate.

Target resolution follows the existing chain (explicit id → `BATTY_*` env → the app's focused element) via `BattyTargetResolver`, though an explicit id is the normal agent case since the ids come straight from `pane split`, `batty new` (once #0380 lands), or `batty list --json`.

## Verification expectations

#0257's amendment pins the test shape too: **assert the resulting store state**, not merely the absence of a crash — `selectedSessionID`, the target Session's `focusedPaneID`, and the target Pane's `activeTabID` (unchanged for `pane focus`, updated for `tab focus`). Cover the cross-Session case explicitly: focusing a Pane in a non-selected Session must change `selectedSessionID`, which is the opposite of what every other mutation verb must do.

## Notes

- **`docs/swiftui-observation-rules.md` is binding here and this is the riskiest part of the work.** Focus and selection flow is exactly the area it governs. The mutation must originate in the XPC-dispatched `Task { @MainActor }` inside `AppXPCService` — an event-origin write, which is routine — and must never be routed through a view callback or hopped into a `Task` to dodge a mutate-during-update warning (the #0229 regression is the documented cost of that shortcut).
- **`tab focus` needs a `tab` noun that does not exist yet.** Adding `TabNounCommand` with a single `focus` subcommand is in scope; the rest of the `tab` verbs are deliberately not (see #0257's "a filed ticket reads as scheduled work" rule, and [#0382](0382.md), which restates the boundary).
- Reuse the app methods that exist (`AppStateStore.focusPane`, the Session-selection path the sidebar uses, the Bell Feed's click-to-jump chain) rather than adding parallel ones.
- **Watch-event coverage.** The `watch` verb's app side is on `main` (`XPCVerb.watch`, `AppEventWatcher`, `XPCWatchMessages.swift`) but its event vocabulary predates these verbs and has no `session_focus` event. Emitting one from the focus path is cheap while this code is open; coordinate with [#0145](0145.md), which owns the watch stream and is `in-progress` on its own branch.
- Sequence this **before** [#0337](0337.md) (focus-after-close history) — the two touch the same focus flow and should not collide on separate branches. Also consider landing [#0332](0332.md) first, since these verbs add new `focusedPane` consumers and #0332 makes the kind-gate structural.
