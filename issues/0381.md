## Description

`batty session focus`, `batty pane focus`, and `batty tab focus` are listed in #0257's Tier 1 verb surface and have had fully pinned semantics since its 2026-07-27 terminology amendment — and none of the three is built. Verified against `BattyKit/Sources/batty/`: `SessionNounCommand`'s subcommand list is `[SessionInfoCommand.self]`, `PaneNounCommand`'s is `[PaneSplitCommand.self, PaneCloseCommand.self]`, there is no `tab` noun at all, and `XPCVerb` has no focus verb of any kind.

This is *the* "show the human what I did" verb, and its absence is the largest hole in Batty as an agent control surface. An agent can create a Session, split a `git-status` Pane into it, and open a System Metrics dashboard — and if the developer is looking at a different Session, none of it is visible. The only tool the agent has is `batty notify`, which posts to the Bell Feed and hopes the human clicks. **`notify` tells; `focus` shows.** The pair is what makes "the agent drives the human's window to display project status" actually work.

## Expected behavior

Implement over XPC, reusing #0282's mutation-verb pattern (request payload, reply, `ok: false` → exit `4` for an unknown or stale id):

```
batty session focus <id>
batty pane focus <id>
batty tab focus <id>
```

Semantics are **already pinned** by #0257's 2026-07-27 terminology amendment; implement exactly those, do not re-litigate:

- **`pane focus <id>`** focuses that Pane and **leaves the Pane's selected Tab unchanged** — moving focus between Panes must never re-select Tabs.
- **`tab focus <id>`** selects that Tab if it is not already selected, and **implies focusing its containing Pane**.
- **All three verbs are activating.** The standing rule (#0257 Foundation §2) that a mutation aimed at a background Session must not switch the active Session names the focus verbs as its one explicit exception, and this is that exception. Focusing a Pane or Tab whose Session is not the selected Session **selects that Session**, and makes its containing Window key once multi-window exists — the same bring-forward chain a Bell Feed click-to-jump uses.

**Directional `pane focus <up|down|left|right>` is deferred.** #0257's table lists it, but id-based targeting is what an agent needs, and directional focus drags in split-tree geometry work with no agent-facing payoff. Say so in the help text so the omission reads as deliberate.

Target resolution follows the existing chain (explicit id → `BATTY_*` env → the app's focused element) via `BattyTargetResolver`, though an explicit id is the normal agent case since the ids come straight from `pane split`, `batty new` (once #0380 lands), or `batty list --json`.

## Verification expectations

#0257's amendment pins the test shape too: **assert the resulting store state**, not merely the absence of a crash — `selectedSessionID`, the target Session's `focusedPaneID`, and the target Pane's `activeTabID` (unchanged for `pane focus`, updated for `tab focus`). Cover the cross-Session case explicitly: focusing a Pane in a non-selected Session must change `selectedSessionID`, which is the opposite of what every other mutation verb must do.

## Notes

- **`docs/swiftui-observation-rules.md` is binding here and this is the riskiest part of the work.** Focus and selection flow is exactly the area it governs. The mutation must originate in the XPC-dispatched `Task { @MainActor }` inside `AppXPCService` — an event-origin write, which is routine — and must never be routed through a view callback or hopped into a `Task` to dodge a mutate-during-update warning (the #0229 regression is the documented cost of that shortcut).
- **`tab focus` needs a `tab` noun that does not exist yet.** Adding `TabNounCommand` with a single `focus` subcommand is in scope; the rest of the `tab` verbs are deliberately not (see #0257's "a filed ticket reads as scheduled work" rule, and [#0382](0382.md), which restates the boundary).
- Reuse the app methods that exist (`AppStateStore.focusPane`, the Session-selection path the sidebar uses, the Bell Feed's click-to-jump chain) rather than adding parallel ones.
- **Watch-event coverage.** The `watch` verb's app side is on `main` (`XPCVerb.watch`, `AppEventWatcher`, `XPCWatchMessages.swift`) but its event vocabulary predates these verbs and has no `session_focus` event. Emitting one from the focus path is cheap while this code is open; coordinate with [#0145](0145.md), which owns the watch stream and is `in-progress` on its own branch.
- Sequence this **before** [#0337](0337.md) (focus-after-close history) — the two touch the same focus flow and should not collide on separate branches. Also consider landing [#0332](0332.md) first, since these verbs add new `focusedPane` consumers and #0332 makes the kind-gate structural.

## Review round 1 — fixes and decisions

The reviewer approved the core design (XPC `Task { @MainActor }` hop,
focus-write reuse, equal-value `@Observable` guards, `tab focus` implying
pane focus, the #0337 claim, and both extrapolated semantics — optional
positional `<id>` with env fallback, and `session focus` = select Session +
activate Window with no Pane/Tab writes) and found four blocking gaps, all
fixed in round 2:

- **B1** — `focusPaneForXPC(id:)`/`focusTabForXPC(id:)` could land focus on
  a hidden Pane, violating #0256's invariant. Both now un-hide the target
  before the focus write, matching `WindowRuntime.jumpToBellEntry`'s
  "un-hide before navigating" order. Covered by
  `focusPaneForXPCUnhidesTheTargetIfItWasHidden` and
  `focusTabForXPCUnhidesTheContainingPaneIfItWasHidden`.
- **B2** — `activateWindow` called only `makeKeyAndOrderFront`, which does
  not bring Batty forward when it isn't the active app — the XPC focus
  verbs are always the out-of-app case (an agent running `batty` from a
  shell while the human is elsewhere), unlike the in-app
  `jumpToBellEntry` path this method's original comment cited as
  precedent. Fixed by adding `NSApp.activate(ignoringOtherApps: true)`
  (the same call `BellNotifier`'s notification-tap path already makes) and
  deminiaturizing first so focusing into a minimized window isn't a
  silent no-op.
- **B3** — two semantics were unpinned and reviewer-mutation-proved:
  (a) `focusPaneForXPCLeavesThePanesActiveTabUnchanged` asserted against
  the pane's *default first* tab, so a mutation that re-selected the first
  tab on every focus passed; rewritten to assert against a non-first tab,
  plus a new cross-session variant
  (`focusPaneForXPCInABackgroundSessionLeavesItsActiveTabUnchanged`).
  (b) `session focus`'s "no Pane/Tab side effects" had zero coverage; added
  `focusSessionForXPCLeavesTheTargetSessionsPaneAndTabFocusUnchanged`.
  Each new/rewritten test was verified to fail under the reviewer's stated
  mutation and pass after reverting it.
- **B4** — `docs/batty-cli-install.md` and `docs/batty-cli-agent-workflows.md`
  were stale (no focus verbs, wrong top-level command count, wrong
  noun-children sentence — also fixed the pre-existing #0384
  `capabilities` staleness in the same pass). Added the three focus rows,
  corrected "eight" → "ten" registered top-level commands, and added a
  "`notify` tells, `focus` shows" workflow section with the deferral notes
  for directional `pane focus`, `session focus <name>`, and `tab focus <n>`.

Non-blocking items also addressed:

- **N1** — `WatchEventType` is now `CaseIterable`; `allNames` derives from
  `allCases.map(\.rawValue)` instead of a hand-listed literal that could
  silently drift (the reviewer's mutation deleting two events from the
  literal passed the whole suite). Added an exact-equality test
  (`watchEventTypeAllNamesIsExactlyTheEightExpectedEvents`).
- **N2** — decided to emit both: `focusTabForXPC` now emits
  `active_tab_changed` (mirroring `WindowRuntime.jumpToTab`) whenever the
  focus write actually changes the pane's active tab, in addition to
  `tab_focused`. A `batty watch` subscriber tracking the active tab via
  `active_tab_changed` alone must not miss a change driven by `tab focus`.
- **N3** — all three focus events now pass `fromCli: true` — they are
  emitted only from the `*ForXPC` methods, so they are always CLI-driven.
- **N4** — documented (here, and in `docs/batty-cli-agent-workflows.md`)
  that `session_focused`/`pane_focused`/`tab_focused` mean "a `batty
  {session,pane,tab} focus` call ran," not "the focused element changed":
  emission lives only in the `*ForXPC` methods (clicks/chips/shortcuts
  emit nothing), and a no-op focus (already-focused target) still emits.
  Defensible — matches `pane_split`'s precedent — but #0145 needs this
  documented rather than inferred when it designs richer watch semantics.
- **N5** — `session focus <name>` and `tab focus <n>` are not implemented;
  only UUIDs parse for either (a name/index yields exit `1`). Documented
  with an "id-based targeting only" line in both commands' `--help`
  discussion (matching the existing directional-`pane-focus` deferral
  note) and in `docs/batty-cli-install.md`'s command table.
- **N7** — added a note to [#0337](0337.md)'s Gotchas: once it introduces
  per-Pane focus history, these three XPC focus writers must be wired
  into it.

**Corrected test count**: round 1 was reported as "1346, up from a 1342
baseline." The 1342 figure corresponds to nothing measured. Actual:
`main` is 1313 tests / 148 suites; round 1's branch was 1346 / 150 (+33 =
12 store-state + 21 wire tests); round 2 adds 5 more (4 B1/B3 coverage

## Gotchas

- **Window-forward behavior, cross-Space behavior, and minimized-window
  deminiaturization are unverified against a live app.** `activateWindow`'s
  `NSApp.activate(ignoringOtherApps:)` and `deminiaturize(nil)` calls are
  the correct AppKit calls per the `BellNotifier` precedent, and the
  store-state assertions (`selectedSessionID`, `focusedPaneID`,
  `activeTabID`) are covered by unit tests, but nothing in `BattyKitTests`
  can exercise actual window-server behavior — whether the window truly
  comes forward when Batty is backgrounded, whether it does so across a
  macOS Space switch, or whether a minimized window visibly restores.
  Needs manual verification with a running app.
- **No end-to-end round trip verified.** The `batty session/pane/tab
  focus` CLI commands were built and compile, and their wire-format tests
  (`FocusPayloadTests`) pass, but no CLI-to-running-app round trip was run
  in this session per the hard constraint against launching/restarting the
  app.
- **No UI-level focus-ring coverage.** There is no UI test confirming a
  focused Pane/Tab visibly shows a focus ring or that the sidebar reflects
  the newly selected Session after an XPC focus call.
- **`tab focus <id>` accepts a non-terminal Pane's phantom tab id and
  degenerates to `pane focus`.** A non-terminal Pane (e.g. `.lmStudioDashboard`)
  reports `tabs: []` in `list --json` while its `activeTabID` still names a
  phantom tab (#0315's Gotcha). Verified: calling `focusTabForXPC(id:)` with
  that phantom id un-hides and focuses the owning Pane, selects its Session,
  and emits `tab_focused`, but never writes `activeTabID` (the phantom is
  always already active, so the `oldTabID != tabID` guard never fires) — it
  is a strictly longer spelling of `pane focus <that pane's id>`, which is
  already fully public via `list --json` with no gate. #0332 separately
  closes the *fallback* half of this (`focusedTabIDFallback()` gains a
  `kind == .terminal` guard), after which only the explicit-id path above
  survives. This is documented behavior, not an unverified claim — it was
  confirmed with a unit test.
