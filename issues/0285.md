## Description

A single Batty process reached an **8.4 GB physical footprint** (peak 8.5 GB) after 42 days of uptime with 111 open Terminal Sessions — the largest process on a 32 GB machine, pushing the kernel to memory pressure level 2. **84% of the footprint is graphics memory**: IOSurface 5.3 GB across 755 regions and IOAccelerator 1.4 GB across 2,651 regions. That works out to ~6.8 IOSurfaces and ~64.5 MB of graphics memory per open Terminal Session.

The most diagnostically useful observation: the footprint grew **+277 MB in ~11 minutes** of ordinary scrolling with **no Panes or Tabs opened or closed**, and never gave any of it back. Growth without surface lifecycle events points at the redraw path allocating rather than reusing — reproducible in minutes, not days.

**This is now an umbrella tracking issue. It ships no code itself — all work happens in the children below.** The source-trace investigation (attached) settled where the memory is owned:

- **Teardown is NOT leaking.** The original hypothesis #1 (surfaces retained after Pane close) is refuted by the source: the close chain reaches `ghostty_surface_free` / `ghostty_app_free`, the retain graph is clean, and no reopen/undo stack exists. The remaining wart is that the free is deferred to ARC rather than deterministic (#0289).
- **The dominant Batty-side cause is one `ghostty_app_t` per Tab.** Ghostty's shared glyph-atlas cache (`font.SharedGridSet`) is owned per app, so N Tabs means N private atlas sets and zero sharing — the best explanation for the 2,651 IOAccelerator regions and the content-driven scrolling growth (#0287, unblocked by the dependency bump in #0286).
- **Occlusion is never signalled** — the wrapper's `setSurfaceVisible(_:)` has zero callers, so background and hidden Tabs render on every PTY wakeup (#0288).
- **Some of the footprint is unreclaimable without an upstream change**: the C API has no way to release a surface's GPU resources short of destroying the surface and its PTY, so hidden sessions keep ~48 MB of swap chain regardless of what Batty does (#0293).

## Acceptance criteria

This umbrella can close only when **both** hold:

1. Every child above is resolved.
2. A measured before/after on **`phys_footprint`** demonstrates the improvement — same workload shape as the original report (multiple Terminal Sessions, scrolling output, hidden Tabs), sampled with the #0291 harness or the `footprint`/`vmmap` tooling.

**Measurement trap (binding for all children):** `ps -o rss` reported 287 MB while the real `phys_footprint` was 8,546 MB — a **29× under-report**, because RSS excludes compressed and swapped pages (1.9 GB of Batty's footprint was in the compressor). All memory work on this app must read `phys_footprint` (via the `footprint` tool, `vmmap`, `top`'s MEM column, or `task_vm_info.phys_footprint` in-process), **never RSS**.

## Steps to reproduce

Condensed from the attached report (§ Suggested reproduction):

1. **Fastest:** with Panes already open, generate continuous scrolling output (`yes | head -1000000` or `find / 2>/dev/null`) in 2–3 Terminal Sessions and sample `footprint -p <pid>` every minute for 10 minutes. A steady climb with no Pane open/close confirms redraw-path allocation.
2. **Teardown check:** open ~20 Panes, record `footprint`, close all 20, record again. A footprint that does not return to baseline means Terminal Session teardown leaks. Repeat open/close 10× — a staircase confirms it.
3. **Resize check:** open 20 Panes, resize the window repeatedly, watch the IOSurface region count in `footprint`.
4. **Long-run:** 50+ Panes for 24 h with light activity, sample hourly.

Note: `pgrep Batty` returns nothing on the reporting machine; get the pid by matching the full binary path (`ps -Ao pid=,comm= | awk '/Batty\.app\/Contents\/MacOS\/Batty$/{print $1; exit}'`).

## Actual behavior

Batty has no awareness of its own memory use. The footprint grew to 8.4 GB over 42 days — ~38% of all memory in use on the system after unrelated apps were trimmed — without any signal to the user. RSS-based observation (`ps`) missed it entirely for weeks.

## Notes

### Investigation hypotheses (condensed from the report, ordered by expected payoff)

*Kept for the record; the source trace (attached) has since confirmed, refuted, or reassigned each — see the Description summary and the children.*

1. **IOSurface retention per Terminal Session (~5.3 GB).** 755 surfaces for 111 open terminals. Check: are surfaces released on Tab close or only at quit (are some of the 755 from long-closed Panes)? Reallocated on resize/font change without freeing the predecessor? Is there a drawable pool, or does each redraw allocate? Do occluded/background Panes keep full-size drawables? (With 111 Panes, only a handful are ever visible.) *Outcome: teardown clean (#0289 caveat); occlusion omission confirmed (#0288); reclaim needs upstream (#0293).*
2. **IOAccelerator region count (~1.4 GB across 2,651 regions, avg 0.53 MB).** Reads like per-Pane texture/buffer allocations. Check whether glyph atlases are shared across surfaces or duplicated per surface — 111 copies of a shared atlas would explain the magnitude. *Outcome: confirmed as the headline, caused Batty-side by app-per-Tab (#0287).*
3. **"Owned physical footprint (unmapped) (graphics)" — 409 MB across 4,028 regions.** GPU memory released CPU-side but still charged to the process; likely a symptom of #1/#2.
4. **~728 orphaned thread stack regions** (1,390 stack regions vs 662 live threads, ~6 threads per Terminal Session). Only 53 MB, but points at a thread-lifecycle issue. *Outcome: all threads are Ghostty's, multiplied by app-per-Tab; live measurement still open (#0291, experiment set).*
5. **Address-space fragmentation** — 13.4 GB writable / 87% unallocated, 625 GB VSZ, ~23,000 regions; page-table overhead rather than a direct footprint problem.

### Code locations for the investigation

- `BattyKit/Sources/BattyKit/Runtime/TerminalHostStore.swift` — process-wide registry of per-window `TerminalHostView` hosts and per-Tab `AppTerminalView`s; `releaseTerminalView(forTabID:)` is the teardown gate. Hidden (`isHidden = true`) views for background Tabs are the place to check occlusion behavior.
- `BattyKit/Sources/BattyKit/Runtime/SurfaceRegistry.swift` — the Surface registry (`register`/`unregister` of `ghostty_surface_t`); confirms whether unregister actually reaches libghostty teardown.
- `AppTerminalView` / the Metal layer live in the **`GhosttyTerminal` / `GhosttyKit` products of the external `libghostty-spm` package** (github.com/Lakr233/libghostty-spm; local clone at `~/Developer/brennanMKE/libghostty-spm`). Per-surface IOSurface/atlas behavior is most likely upstream — the investigation should establish the Batty/upstream boundary precisely so follow-ups get filed in the right tracker.
