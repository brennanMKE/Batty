| **Platform** | macOS |

## Description

A single Batty process reached an **8.4 GB physical footprint** (peak 8.5 GB) after 42 days of uptime with 111 open Terminal Sessions — the largest process on a 32 GB machine, pushing the kernel to memory pressure level 2. **84% of the footprint is graphics memory**: IOSurface 5.3 GB across 755 regions and IOAccelerator 1.4 GB across 2,651 regions. That works out to ~6.8 IOSurfaces and ~64.5 MB of graphics memory per open Terminal Session.

The most diagnostically useful observation: the footprint grew **+277 MB in ~11 minutes** of ordinary scrolling with **no Panes or Tabs opened or closed**, and never gave any of it back. Growth without surface lifecycle events points at the redraw path allocating surfaces rather than reusing them — reproducible in minutes, not days.

This issue has two parts:

1. **Investigate** where the graphics memory goes (details in Notes and the attached report). The outcome may spawn follow-up issues — including upstream libghostty issues — which will be filed separately when the investigation lands; they are deliberately not pre-filed here.
2. **Deliver user-facing memory monitoring with a soft-limit warning** (Expected behavior below). We may not be able to reduce the per-Terminal-Session cost — the render surfaces live inside libghostty — but we can at least measure it and warn the user before the system starts swapping. This part ships regardless of what the investigation concludes.

**Measurement trap:** `ps -o rss` reported 287 MB while the real `phys_footprint` was 8,546 MB — a **29× under-report**, because RSS excludes compressed and swapped pages (1.9 GB of Batty's footprint was in the compressor). All memory work on this app — including the monitoring feature itself — must read `phys_footprint` (via the `footprint` tool, `vmmap`, `top`'s MEM column, or `task_vm_info.phys_footprint` in-process), never RSS.

## Steps to reproduce

Condensed from the attached report (§ Suggested reproduction):

1. **Fastest:** with Panes already open, generate continuous scrolling output (`yes | head -1000000` or `find / 2>/dev/null`) in 2–3 Terminal Sessions and sample `footprint -p <pid>` every minute for 10 minutes. A steady climb with no Pane open/close confirms redraw-path allocation.
2. **Teardown check:** open ~20 Panes, record `footprint`, close all 20, record again. A footprint that does not return to baseline means Terminal Session teardown leaks. Repeat open/close 10× — a staircase confirms it.
3. **Resize check:** open 20 Panes, resize the window repeatedly, watch the IOSurface region count in `footprint`.
4. **Long-run:** 50+ Panes for 24 h with light activity, sample hourly.

Note: `pgrep Batty` returns nothing on the reporting machine; get the pid by matching the full binary path (`ps -Ao pid=,comm= | awk '/Batty\.app\/Contents\/MacOS\/Batty$/{print $1; exit}'`).

## Expected behavior

Batty monitors its own memory footprint and warns the user when it crosses a soft limit:

- Batty periodically samples its own `phys_footprint` (e.g. `task_info` with `TASK_VM_INFO` — not RSS, per the measurement trap above). Per-Terminal-Session attribution is a bonus if feasible; a process-level number is the requirement.
- A **configurable soft limit** with a sane default (given ~65 MB of graphics memory per open Terminal Session on the reporting machine, something in the low single-digit GB is a reasonable starting point). Configuration belongs with the app's existing preferences (Settings window).
- Crossing the limit **warns the user** through an existing app affordance — the Bell Feed is the app's notification surface and a natural fit, optionally paired with a System notification when Batty is not frontmost. The implementer picks the exact surface; the requirement is that the warning is visible without the user going looking for it.
- The warning is **actionable**: it states the current footprint and how many Terminal Sessions are open, so the user can decide what to close.
- The warning does **not nag**: once acknowledged, it does not repeat until the situation meaningfully changes (e.g. footprint crosses the next threshold step, or drops below the limit and crosses it again).

This is a mitigation/observability feature: it ships whether or not the underlying graphics-memory growth turns out to be fixable in Batty or upstream in libghostty.

## Actual behavior

Batty has no awareness of its own memory use. The footprint grew to 8.4 GB over 42 days — ~38% of all memory in use on the system after unrelated apps were trimmed — without any signal to the user. RSS-based observation (`ps`) missed it entirely for weeks.

## Notes

### Investigation hypotheses (condensed from the report, ordered by expected payoff)

1. **IOSurface retention per Terminal Session (~5.3 GB).** 755 surfaces for 111 open terminals. Check: are surfaces released on Tab close or only at quit (are some of the 755 from long-closed Panes)? Reallocated on resize/font change without freeing the predecessor? Is there a drawable pool, or does each redraw allocate? Do occluded/background Panes keep full-size drawables? (With 111 Panes, only a handful are ever visible.)
2. **IOAccelerator region count (~1.4 GB across 2,651 regions, avg 0.53 MB).** Reads like per-Pane texture/buffer allocations. Check whether glyph atlases are shared across surfaces or duplicated per surface — 111 copies of a shared atlas would explain the magnitude.
3. **"Owned physical footprint (unmapped) (graphics)" — 409 MB across 4,028 regions.** GPU memory released CPU-side but still charged to the process; likely a symptom of #1/#2.
4. **~728 orphaned thread stack regions** (1,390 stack regions vs 662 live threads, ~6 threads per Terminal Session). Only 53 MB, but points at a thread-lifecycle issue.
5. **Address-space fragmentation** — 13.4 GB writable / 87% unallocated, 625 GB VSZ, ~23,000 regions; page-table overhead rather than a direct footprint problem.

The report's suggested fixes (release on close, drawable pooling, occlusion eviction, shared atlases, surface caps, stack reclamation) are candidate follow-ups, not commitments — where the allocation sits upstream, the follow-up is a libghostty issue rather than a Batty change.

### Code locations for the investigation

- `BattyKit/Sources/BattyKit/Runtime/TerminalHostStore.swift` — process-wide registry of per-window `TerminalHostView` hosts and per-Tab `AppTerminalView`s; `releaseTerminalView(forTabID:)` is the teardown gate. Hidden (`isHidden = true`) views for background Tabs are the place to check occlusion behavior.
- `BattyKit/Sources/BattyKit/Runtime/SurfaceRegistry.swift` — the Surface registry (`register`/`unregister` of `ghostty_surface_t`); confirms whether unregister actually reaches libghostty teardown.
- `AppTerminalView` / the Metal layer live in the **`GhosttyTerminal` / `GhosttyKit` products of the external `libghostty-spm` package** (github.com/Lakr233/libghostty-spm; local clone at `~/Developer/brennanMKE/libghostty-spm`). Per-surface IOSurface/atlas behavior is most likely upstream — the investigation should establish the Batty/upstream boundary precisely so follow-ups get filed in the right tracker.

### Code locations for the monitoring feature

- `BattyKit/Sources/BattyKit/Views/SettingsView.swift` + `BattyKit/Sources/BattyKit/Settings/` — soft-limit preference.
- `BattyKit/Sources/BattyKit/Runtime/BellFeedStore.swift`, `BellNotifier.swift`, `Views/BellFeedView.swift` — the existing notification surface, if the Bell Feed is chosen for the warning.
- Terminal Session count for the warning text is derivable from `TerminalHostStore` (live `AppTerminalView` count) or the Surface registry.
