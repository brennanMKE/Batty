## Description

A single Batty process reached an **8.4 GB physical footprint** (peak 8.5 GB) after 42 days of uptime with 111 open Terminal Sessions — the largest process on a 32 GB machine, pushing the kernel to memory pressure level 2. **84% of the footprint is graphics memory**: IOSurface 5.3 GB across 755 regions and IOAccelerator 1.4 GB across 2,651 regions. That works out to ~6.8 IOSurfaces and ~64.5 MB of graphics memory per open Terminal Session.

The most diagnostically useful observation in the original report: the footprint grew **+277 MB in ~11 minutes** of ordinary scrolling with **no Panes or Tabs opened or closed**, and never gave any of it back. (The live instrumentation later failed to reproduce this on an idle instance — but its sessions were idle throughout, so the scrolling repro remains untested, not refuted.)

**Reframe from the live instrumentation (`0285/investigation-live.md`): this is an unbounded per-session cost, not a leak over time.** Across two instances with a 6× uptime difference, footprint tracked session count, not uptime: 56.6 MB per Terminal Session at 7 days / 26 sessions vs 77.0 MB per session at 42 days / 111 sessions. The measured instance was flat over 20 minutes of idle sampling (non-monotonic, 1472 → 1475 MB) and had already returned ~660 MB from its 2.1 GB peak. The problem is that every Terminal Session — visible or not — permanently holds ~35–42 MB of graphics memory.

**This is now an umbrella tracking issue. It ships no code itself — all work happens in the children below.** The source-trace investigation and the live instrumentation (both attached) settled where the memory is owned:

- **Teardown is NOT leaking** per the source trace: the close chain reaches `ghostty_surface_free` / `ghostty_app_free`, the retain graph is clean, and no reopen/undo stack exists. The remaining wart is that the free is deferred to ARC rather than deterministic — and no Tab close was ever observed live, so the open/close census is still the top untested question (#0289).
- **Layers are retained for non-visible Terminal Sessions, and occlusion is never signalled** — measured: 31 live `CAMetalLayer`s for 26 sessions, 22 of them at a geometry only 2 panes can occupy on screen; the wrapper's `setSurfaceVisible(_:)` has zero callers. The costs that scale with layer count (~700 MB of the 1090 MB graphics footprint) make this the biggest Batty-side lever (#0288).
- **One `ghostty_app_t` per Tab defeats Ghostty's shared glyph-atlas cache** per the source trace (#0287, unblocked by the dependency bump in #0286) — but the live region arithmetic points at per-*surface* atlas ownership instead (93 atlases for 31 layers = 3 per layer, not 1 per app), and total atlas is 119 MB (11% of graphics), so that child is now gated on a one-command ownership experiment before any refactor.
- **Some of the footprint is unreclaimable without an upstream change**: the C API has no way to release a surface's GPU resources short of destroying the surface and its PTY (#0293, now including a cheaper `maximumDrawableCount` ask confirmed by the measured 3:1 drawable ratio).
- **One layer renders at 2× the content area on a 1× display** — 72.6 MB, 5% of the measured footprint, found only by the live census (#0294).

## Acceptance criteria

This umbrella can close only when **both** hold:

1. Every child above is resolved.
2. A measured before/after on **`phys_footprint`** demonstrates the improvement — same workload shape as the original report (multiple Terminal Sessions, scrolling output, hidden Tabs), sampled with the #0291 harness or the `footprint`/`vmmap` tooling.

**Measured baseline to beat** (live instrumentation, 2026-07-31 — pid 9870, 7 d 8 h uptime): 26 Terminal Sessions, 31 layers, **1472 MB footprint, 74% graphics** (IOSurface 377 MB / IOAccelerator 465 MB / unmapped-graphics 248 MB), **~56.6 MB per Terminal Session**. Cross-instance finding: footprint tracks **session count**, not uptime — 56.6 MB/session here vs 77.0 MB/session on the 42-day instance, across a 6× uptime difference. The per-session number is the one future work has to move.

**Measurement trap (binding for all children):** `ps -o rss` reported 287 MB while the real `phys_footprint` was 8,546 MB — a **29× under-report**, because RSS excludes compressed and swapped pages (1.9 GB of Batty's footprint was in the compressor). All memory work on this app must read `phys_footprint` (via the `footprint` tool, `vmmap`, `top`'s MEM column, or `task_vm_info.phys_footprint` in-process), **never RSS**.

## Steps to reproduce

Condensed from the attached report (§ Suggested reproduction):

1. **Fastest:** with Panes already open, generate continuous scrolling output (`yes | head -1000000` or `find / 2>/dev/null`) in 2–3 Terminal Sessions and sample `footprint -p <pid>` every minute for 10 minutes. A steady climb with no Pane open/close confirms redraw-path allocation.
2. **Teardown check:** open ~20 Panes, record `footprint`, close all 20, record again. A footprint that does not return to baseline means Terminal Session teardown leaks. Repeat open/close 10× — a staircase confirms it.
3. **Resize check:** open 20 Panes, resize the window repeatedly, watch the IOSurface region count in `footprint`.
4. **Long-run:** 50+ Panes for 24 h with light activity, sample hourly.

Note: `pgrep Batty` returns nothing on the reporting machine; get the pid by matching the full binary path (`ps -Ao pid=,comm= | awk '/Batty\.app\/Contents\/MacOS\/Batty$/{print $1; exit}'`).

## Actual behavior

Batty has no awareness of its own memory use. The footprint grew to 8.4 GB over 42 days — ~38% of all memory in use on the system after unrelated apps were trimmed — without any signal to the user. RSS-based observation (`ps`) missed it entirely for weeks.

## Notes

### Investigation hypotheses (condensed from the report, ordered by expected payoff)

*Kept for the record; the source trace and the live instrumentation (both attached) have since confirmed, refuted, or reassigned each — see the Description summary and the children. **Do not re-investigate the refuted ones.***

1. **IOSurface retention per Terminal Session (~5.3 GB).** 755 surfaces for 111 open terminals. Check: are surfaces released on Tab close or only at quit (are some of the 755 from long-closed Panes)? Reallocated on resize/font change without freeing the predecessor? Is there a drawable pool, or does each redraw allocate? Do occluded/background Panes keep full-size drawables? (With 111 Panes, only a handful are ever visible.) *Outcome: partly confirmed, mechanism corrected — exactly 3 drawables per layer (`CAMetalLayer` default triple buffering), not accumulation; **the resize sub-hypothesis is refuted by measurement** (a mid-sampling pane resize was a clean 1:1 swap: six 820×962 drawables freed, six 934×962 allocated, net surface count unchanged at 93). Occlusion/retained-layer sub-hypothesis confirmed and now evidence-backed (#0288); teardown clean per source but Tab close never observed live (#0289); reclaim needs upstream (#0293).*
2. **IOAccelerator region count (~1.4 GB across 2,651 regions, avg 0.53 MB).** Reads like per-Pane texture/buffer allocations. Check whether glyph atlases are shared across surfaces or duplicated per surface — 111 copies of a shared atlas would explain the magnitude. *Outcome: duplication confirmed by measurement (93 × 1040 K grayscale + 94 × 272 K color atlases, none shared), but the ownership reading is contested — source trace says per-App (Batty-fixable via #0287), live region arithmetic says per-surface (3 per layer, upstream). #0287 is gated on the settling experiment. Total atlas is 119 MB / 11% of graphics on the measured instance — smaller than this hypothesis implied.*
3. **"Owned physical footprint (unmapped) (graphics)" — 409 MB across 4,028 regions.** GPU memory released CPU-side but still charged to the process; likely a symptom of #1/#2. *Outcome: inconclusive but bounded and stable — byte-identical across all 11 live samples, which is inconsistent with an independent leak.*
4. **~728 orphaned thread stack regions** (1,390 stack regions vs 662 live threads, ~6 threads per Terminal Session). *Outcome: **REFUTED — counting artifact, nothing to fix.** `footprint`'s `stack` category counts each thread's guard page as a separate region: on the live instance, 125 live threads → 125 `Stack` + 125 `STACK GUARD` + 6 misc = exactly the 256 regions reported, 1:1 stacks to threads, zero orphans. Ratio 2.05 there vs 2.10 in the original report — same artifact. The reported "1,390 regions vs 662 threads" resolves to 662 stacks + 662 guards + 66 misc.*
5. **Address-space fragmentation** — 13.4 GB writable / 87% unallocated, 625 GB VSZ, ~23,000 regions. *Outcome: **REFUTED.** The unallocated figure is normal pthread stack reservation (live instance: 125 threads × 16 MB virtual against 2.8 MB dirty), and the "625 GB VSZ" is the same reservation accounting inflated further. Not fragmentation, not a footprint concern.*

### Live-instrumentation caveats (2026-07-31)

- **Idle growth was not reproduced**: 20 minutes of sampling moved the footprint 1472 → 1475 MB, non-monotonic, dipping below baseline in 5 of 11 samples, and the process had already returned ~660 MB from its 2.1 GB peak. But the user's sessions were idle throughout, so this does **not** refute the original scrolling repro ("+277 MB in 11 minutes") — that scenario remains untested, exactly that.
- The strongest live claims (3 drawables per layer, atlases not shared, resize frees cleanly) rest on region-count arithmetic that held exactly across two samples — tight, but inferences from outside the process.
