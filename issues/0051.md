# 0051 — Split actions ignore which pane is in keyboard focus

| | |
|---|---|
| **Status** | open |
| **Module** | Split / Pane |
| **Platform** | macOS |
| **First seen** | 2026-05-11 |

## Description

When a session already has multiple panes, clicking inside a pane's terminal and typing puts keyboard focus on that pane's `TerminalSurfaceView`, but the session's `tree.focusedPaneID` may still point at a different pane (the one that took focus via `splitFocusedPane`, geometric `focusPane(adjacent:)`, or whichever pane held the marker last). Hitting **Split Horizontally** / **Split Vertically** (toolbar buttons or `Cmd-D` / `Cmd-Shift-D`) splits **that** pane, not the one the user was just typing in.

User-visible failure mode: "I was typing in pane B; I hit Cmd-D expecting B to split; instead pane A grew a new sibling because the model's focused pane was still A."

## Steps to reproduce

1. Open a session, hit `Cmd-D` once to create two panes (pane A on the left, B on the right). `tree.focusedPaneID = B`.
2. Click inside pane A's terminal. Type something — keystrokes go to A's shell. The model is unaware that "focus" has moved.
3. Hit `Cmd-D`. **Expected:** A splits, becoming A + A'. **Actual:** B splits (because `tree.focusedPaneID` is still B from step 1).

## Expected behavior

Click-to-focus should be a complete operation: clicking inside a pane (or `TerminalSurfaceView` gaining first-responder focus by any means) updates `tree.focusedPaneID` to that pane so subsequent split / tab / focus-movement operations target the visually-focused pane.

The split toolbar buttons and `Cmd-D` / `Cmd-Shift-D` keybindings remain unchanged — they always operate on `tree.focusedPaneID`. The bug is that the marker isn't being updated when the user clicks inside a pane.

## Actual behavior

`tree.focusedPaneID` only updates on:
- `splitFocusedPane(...)` — sets the new pane as focused.
- `removeFocusedPane()` — clamps to the first leaf.
- `focusPane(adjacent:)` — geometric `Cmd-Option-Arrow` movement.

Nothing in the SwiftUI tree currently observes "this pane's TerminalSurfaceView became key" and writes back to `tree.focusedPaneID`.

`#0020`'s resolution notes called this out explicitly: *"Click-to-focus on a pane is still missing. The user can switch focus geometrically via keyboard, or by pressing Cmd-D / Cmd-Shift-D (which lands focus on the new pane), but clicking inside a non-focused pane doesn't currently update focusedPaneID."*

This issue moves the click-to-focus follow-up from a Gotcha bullet to a tracked ticket because the user has now hit it in normal use.

## Acceptance criteria

- After clicking inside any pane's terminal, `tree.focusedPaneID` reflects that pane.
- After typing into any pane (so its `TerminalSurfaceView` gains first-responder), `tree.focusedPaneID` reflects that pane.
- `Cmd-D` / `Cmd-Shift-D` (and the toolbar split buttons) split whichever pane the user was just typing in, with no perceptible delay between focus-change and split-action.
- Existing focus paths (`splitFocusedPane` setting the new pane, `removeFocusedPane`, geometric `focusPane(adjacent:)`) continue to work.
- No re-entrancy or render loops: writing `focusedPaneID` from a focus observer must not trigger a re-render that re-fires the observer.

## Notes

- `TerminalViewState.isFocused` is published by `GhosttyTerminal` (via the `TerminalSurfaceFocusDelegate` conformance landed in the upstream fork). `PaneView` (or `SplitNodeView` wrapping it) can observe `tab.terminal.isFocused` per-tab and, when it flips to `true`, set `tree.focusedPaneID = pane.id`.
- Alternative implementation: a `.simultaneousGesture(TapGesture())` on the `TerminalSurfaceView` overlay. Less reliable than the focus delegate (a click that lands on the OSC selection or scrollback wouldn't fire a tap; a `Cmd-Tab` away/back wouldn't either).
- Prefer the `isFocused` observation — it captures both click-to-focus and other paths that put the terminal first-responder.
- The model already has `SessionRuntime.tree.focusedPaneID`; this is a one-way write from the view layer driven by AppKit/SwiftUI focus state.
- Consider whether to track focus at the **pane** level only (current model) or also at the **tab** level inside a pane. For v1 the pane-level marker plus each pane's own `activeTabID` is sufficient — clicking a tab's chip already updates `activeTabID` via SlidingTabs.
- See related: `#0018` (split actions — focuses new pane on split), `#0020` (geometric focus movement — `Cmd-Option-Arrow`), `#0045` / `#0050` (chip-content vs chip-layout work that doesn't overlap here).

## Suggested implementation sketch

In `PaneView`:

```swift
.onChange(of: pane.activeTab.terminal.isFocused) { _, isFocused in
    if isFocused {
        // Find the SessionRuntime that owns this pane via the env
        // store and set its tree.focusedPaneID = pane.id.
    }
}
```

`appStore` is already available via `@Environment(\.appStateStore)` in `PaneView`. The session-walk is the only complexity: given a `pane.id`, find which session contains it and update that session's tree. A new helper on `AppStateStore` (e.g. `func focusPane(id: UUID)`) keeps the walk centralized.

## Out of scope

- Click-to-focus on a non-active **tab** chip (already handled by SlidingTabs's tap-to-select).
- Per-tab focus inside a pane (each pane's `activeTabID` is the right marker).
- Animating the focus change. The marker update is invisible by itself; the next action (`Cmd-D`, etc.) reveals whether it worked.
