## Description

An agent can list and open Projects through `batty` and `batty mcp`, but it can't make one. Today only the Project Editor and Save Session as Project create a Project. So an agent that has just set up a repo can't save "this layout, with this Background Set image at this opacity" for the user. The user asked (2026-11-19) for the MCP to let an agent create new Projects and say how the layout is set up, which image from the Background Sets to use, and the opacity. Target 1.5.0 (user decision), the release that ships the MCP server (#0647).

Add three verbs: `batty background list`, `batty project create` and `batty project edit`. All three come only through the CLI and MCP, with no new UI. MCP tools are generated from `batty capabilities`, so each verb becomes an MCP tool once it has a `CapabilitiesDescribable` schema and an annotations row.

## Root cause

Feature work. The starting state: only the Project Editor and Save Session as Project could write a Project, the CLI's `project` noun had only `list` and `open`, the editor's validation lived inside `ProjectEditorViewModel`, and nothing listed Background Sets over XPC.

## Fix

Followed the plan's five steps, one commit each.

1. `ProjectValidator` holds the editor's rules unchanged; `ProjectEditorViewModel.validate()`, `commandProblem` and `unavailableThemeNames()` forward to it. `ProjectEditorField.cliPath` names fields for CLI errors.
2. BattyXPCCore: strict `ProjectLayoutDocument` (unknown keys, wrong types and bad shapes fail with a JSON path), `ProjectVocabulary`, `ProjectWriteRequest`/`Reply`, `BackgroundList*` payloads, and the `backgroundList`, `projectCreate` and `projectEdit` verbs.
3. App side: `ProjectLayoutDocument+Mapping` (pure, path-named errors), `ProjectWriteBuilder` (scalar fields, opacity rules, startup-command assignment), `HostedBackgroundsModel.catalogsForCLI()` (never marks Browse opened) and `hostedImage(set:title:)`/`hostedImage(id:)`, `AppStateStore.backgroundListForXPC`, `createProjectForXPC`/`editProjectForXPC`, and the three `AppXPCService` cases. Images take the picker's route: `hosted.select` then `importer.adoptImage(path:from: pickSources)`, My Images by digest through `adoptImage`, a file through `importImage`; Pane and Tab levels get `tabImageIdentity.identity(forPath:keeping: nil)`. Edit calls `applyProjectSave(previous: stored, saved:)`.
4. CLI: `ProjectCreateCommand`/`ProjectEditCommand` sharing `ProjectWriteOptions` (`@OptionGroup`), `BackgroundNounCommand`/`BackgroundListCommand`, `AppServiceClient.backgroundList`/`projectWrite`, schemas with conflicts, the `edit` archetype, MCP array options repeated per element, and the MCP instructions hint.
5. Docs, skill, Concepts 0.38, and the regenerated CLI reference.

Deviations from the plan:

- The plan's handler signatures returned `Result<_, String>`, which doesn't compile (`String` isn't an `Error`). They return a small `CLIOutcome<Reply>` enum (`.success`/`.failure(String)`) instead, in `ProjectWriteBuilder.swift`.
- `ProjectWriteBuilder.apply` takes `imagePath: String??` (nil = keep, `.some(nil)` = clear, a path = newly picked) rather than `background: TerminalBackgroundSettings??`, because the builder owns the opacity rules.
- The layout document's structure is checked (`ProjectLayoutDocument.check()`) before any image is fetched, so a bad `kind` never downloads anything; scalar-field errors (bad hex, `--opacity` with no image) are found after image resolution, but still save nothing.
- `ProjectLayoutDocumentError` gained `missingKey` and `panesWithoutPreset` cases alongside the plan's list.
- `ProjectWriteXPCTests` and `BackgroundListXPCTests` call the `AppStateStore` methods directly rather than through `AppXPCService.perform`; the service cases only decode, call and encode, like `projectList`.
- `ProjectLayoutMappingTests`, `ProjectWriteBuilderTests` and `BackgroundListXPCTests` live in `ProjectWriteXPCTests.swift`; `ProjectVocabularyTests` lives in `ProjectLayoutDocumentTests.swift`.
- Added `resolveProjectAppEndpoint()` (the former private `resolveAppEndpoint()` in `ProjectCommand.swift`, now shared by the new commands).
- Layout `kind` values are `PaneContentKind` raw values (`git-status`, not the issue example's `gitStatus`); the docs and `--help` say so.

## Current state (checked against `main` at `eb989310`)

- **The current design rules this out on purpose.** `docs/batty-cli-design.md:39-44` says `project` has only `list` and `open`: "There are no `project add`, `remove` or `edit` verbs; Projects are edited in the Project Editor." The doc comment on `ProjectNounCommand` (`BattyKit/Sources/batty/ProjectCommand.swift:8-10`) says the same. This issue changes that decision at the user's request, so both texts must be updated (see Docs). The CLI never reads `projects.json`. The app owns `ProjectStore` and answers over XPC (`XPCVerb.projectList`/`projectOpen`, `BattyKit/Sources/BattyXPCCore/XPCVerb.swift:156, 163`; dispatched in `BattyKit/Sources/BattyKit/XPC/AppXPCService.swift:500, 517`; handlers in `BattyKit/Sources/BattyKit/Runtime/AppStateStore+ProjectXPC.swift:20, 37`). The new verbs follow the same split.
- **Project fields**, all in `BattyKit/Sources/BattyKit/Model/Project.swift`: `name` 462, `rootPath` 465, `color: SessionColor` 469, `customColorHex` 473, `symbol: ProjectSymbol` 476, `customSymbolName` 480, `layout: ProjectLayout` 481, `runStartupCommandsOnOpen` 482, `approvedCommandsHash` 483, `isShared` 487, `background: TerminalBackgroundSettings?` 495, `sharedImage` 498, `theme: ThemePair?` 502.
- **Layout model.** `ProjectLayout` (`Project.swift:295-305`) has `root: ProjectLayoutNode`, an optional `preset: PaneLayout`, `focusedSlot` and `splitFractions`. `ProjectLayoutNode` (`:153-155`) is `.pane(ProjectPane)` or `.split(direction:children:)`, encoded as `{"type":"pane"|"split",...}`. `ProjectPane` (`:64-82`) has `kind: PaneContentKind`, `tabs`, `repositoryPath` (Git Status), `background`, `image`, `isHidden` and `activeTab`. `ProjectTab` (`:12-23`) has `title`, `workingDirectory`, `startupCommand`, `background` and `image`. - **Opacity has two settings, not one.** `TerminalBackgroundSettings` (`BattyKit/Sources/BattyKit/Settings/TerminalBackgroundSettings.swift:39-48`) has `imagePath`, `fit`, `position`, `imageOpacity`, `terminalOpacity` and `opacityAffectsCells`. `imageOpacity` has no upper clamp, because values above 1 mean something to libghostty (`:63-65`). `terminalOpacity` is clamped to 0...1. A first image gets `firstImageOpacity = 0.15` (`:83`), the highest value that keeps both default Themes readable.
- **Hosted images have a stable id.** It is the full-size URL: `HostedBackgroundImage.id` is `full` (`BattyKit/Sources/BattyKit/Settings/BackgroundCatalog.swift:6-11`), and `HostedImageKey` is keyed on it (`BattyKit/Sources/BattyKit/Model/HostedBackgroundsModel.swift:10-14`). Titles are unique only within a set.
- **Hosted picks are not copied into the Project folder (premise correction).** `HostedBackgroundsModel.select(_:)` (`:378-432`) returns the path of the downloaded-cache copy, fetching it first if needed. `ProjectBackgroundLibrary.adopt(path:)` (`BattyKit/Sources/BattyKit/Settings/ProjectBackgroundLibrary.swift:69-72`) leaves a cached copy where it is ("the cache owns it"). Only local files (My Images, a file the user chose) are digest-copied into the Project background folder (`TerminalBackgroundImageImporter.adopt`). ## Expected behavior

### 1. `batty background list [--set NAME] [--json]` (read-only)

- Lists every Background Set from every catalog the app knows, built-in and user-added. For each image it gives `set`, `title`, `id` (the full-size URL, which is stable), `thumbnailURL`, `fullURL`, `catalogURL` and `downloaded` (true when a cached copy exists).
- `--set` filters by set name, case-insensitively and exactly. An unknown set exits 4 and lists the set names.
- **My Images** (`BackgroundImagesModel`) appear as a separate group, `set: "My Images"`. Each carries a `digest` id and its name, never a filesystem path.
- The answer comes from the app over XPC, because the app owns the catalog cache. When the catalog is offline the verb prints the cached contents and a warning (`HostedCatalogProblem.offlineShowingCache`). With no cache it exits 4.
- Annotation: the `list` archetype.

### 2. `batty project create`

```
batty project create --name N --path DIR
    [--color C | --color-hex #RRGGBB] [--symbol S | --symbol-name SF_NAME]
    [--theme NAME | --theme-dark NAME --theme-light NAME]
    [--preset PRESET | --layout FILE|- | --from-session [ID]]
    [--background-set SET --background-image TITLE | --background-id URL | --background-file PATH | --no-background]
    [--opacity 0-100] [--terminal-opacity 0-100]
    [--startup-command CMD ...]
    [--json]
```

- Defaults: color `blue` and symbol `folder` (the `Project` init defaults, `Project.swift:512-513`), no Theme (Settings Theme), preset `singlePane` with one Tab in the root, no background.
- `--path` must be an absolute path to an existing directory. Relative paths are resolved against the caller's cwd in the CLI before sending, so the app never sees a relative root.
- `--opacity` sets the Project background's `imageOpacity` as a percentage. It defaults to 15 (`firstImageOpacity`) when an image is given, and is rejected without one. `--terminal-opacity` sets `terminalOpacity` and defaults to 100. The CLI caps `--opacity` at 100 even though the model allows more (recommend; open question below).
- `--background-set/--background-image` resolves to one hosted image by set name and title (case-insensitive, exact). `--background-id` takes the full URL from `background list`. Both fetch the image through `HostedBackgroundsModel.select`, the same path the picker uses, and save its cached path. The verb fails with exit 4, saving nothing, if the fetch fails. `--background-file` digest-copies a local file into the Project background folder through `ProjectBackgroundLibrary.adopt`, as the editor's Choose File does.
- `--startup-command` may be repeated. Each command goes to the next terminal Tab in slot order, and there must not be more commands than Tabs. For anything more involved, use `--layout`.
- **`--layout FILE|-`** reads a small, documented JSON layout document, not the raw `projects.json` encoding, so that agents get a stable contract:

  ```json
  {
    "preset": "mainLeftTwoRight",
    "panes": [
      { "kind": "terminal",
        "tabs": [ { "title": "server", "cwd": "web", "command": "npm run dev" },
                  { "cwd": "." } ],
        "background": { "id": "https://batty.sstools.co/backgrounds/deep-space/03-....png", "opacity": 20 } },
      { "kind": "gitStatus", "repository": "." },
      { "kind": "processStatus" }
    ],
    "focusedPane": 0
  }
  ```

  `preset` is a `PaneLayout` raw value, and `panes` fills its slots in order. The other option is `"root"`: a nested `{ "split": "horizontal"|"vertical", "children": [...] }` tree whose leaves are pane objects. `kind` is a `PaneContentKind` raw value. A `cwd` is relative to the Project root. A per-Pane or per-Tab `background` takes `id` (hosted URL), `digest` (My Images) or `file`, plus `opacity`. The verb rejects unknown keys, rather than ignoring them, so a typo never saves silently. `batty project create --help` documents the schema, and `batty capabilities --json` carries it in `description`.
- `--from-session [ID]` captures a live Session through `SessionProjectCapture.capture`, the caller's own Session when no ID is given. It is the CLI equivalent of Save Session as Project. When combined with other flags, those override the captured fields.
- **Validation** uses the same rules as the Project Editor. Move them out of `ProjectEditorViewModel.validate()` into a pure `ProjectValidator` that the editor and the XPC handler both call, so the two can't drift. Errors exit 4 and name the field. Warnings, such as a Tab folder that doesn't exist yet or an unknown Theme, are printed to stderr and do not stop the save.
- **Safety:**
  - Create never overwrites. A name collision, ignoring case, is an error that names the existing Project.
  - The write goes through `ProjectStore.upsert` (atomic write, Shared Projects publish unchanged).
  - New Projects are local (`isShared = false`).
  - **Startup commands are never pre-approved.** `approvedCommandsHash` stays nil, so the first `project open` shows the approval sheet, as #0477 requires. Neither verb gets a flag to approve them.
- Output: `Created Project "N"`, or with `--json` `{ "id", "name", "rootPath", "paneCount", "tabCount", "warnings": [...] }`.
- Annotation: the `new` archetype (`readOnlyHint: false, destructiveHint: false, idempotentHint: false`).

### 3. `batty project edit <name|id> [same options]`

- Changes only the fields that are given. A field that is not given keeps its stored value, including Pane/Tab backgrounds and split fractions.
- `--name` renames the Project, failing on a collision. `--path` changes the root. `--layout`, `--preset` and `--from-session` replace the whole layout. `--no-background` clears the Project background. `--opacity` alone changes the opacity of the existing image.
- After the save, it calls `applyProjectSave(previous:saved:)`. Open Sessions then pick up name, color, symbol, Theme and Project background at once. A layout change waits for the next open, as it does for an editor save, and the reply says so (`"appliesOnNextOpen": ["layout"]`).
- A layout edit that changes startup commands invalidates the approval through the existing hash comparison. No new path is needed.
- An unknown name or id exits 4 with the close matches, like `project open` (`AppStateStore+ProjectXPC.swift:74`).
- Annotation: a new `edit` archetype with `readOnlyHint: false, destructiveHint: false, idempotentHint: true`. Editing replaces fields, so it is not "destructive" in the MCP sense, but it is not read-only.

### 4. No delete verb (recommended)

This issue adds no `project delete`. Deleting a Project can't be undone, can withdraw a Shared Project from other Macs, and is not something an agent needs in order to set the user up. **Open question for the user:** add `project delete <name> --yes` with the `close` archetype (`destructiveHint: true`) in a later issue?

### Unchanged

- Shared Projects sync is unchanged. CLI writes go through the same `upsert`/`publish` as editor saves.
- An open Project Editor window sees the change through `ProjectStore` observation. A CLI edit made while that Project's draft is dirty in the editor is the same case as two Batty copies editing one file. It needs no new handling, but the handling should be checked.
- No menu, Sidebar, Command Palette or Settings changes.

## Acceptance criteria

- `batty background list --json` lists the built-in sets with `id` equal to each image's full URL, plus My Images by digest.
- `batty project create --name Demo --path ~/x --background-set "Deep Space" --background-image "<title>" --opacity 20` creates a Project. In the Project Editor it shows that image at 20% image opacity, and opening it shows the image.

- A Project created with startup commands still shows the approval sheet on its first open.
- `batty capabilities --json` lists all three verbs with schemas and the annotations above, and `batty mcp` exposes them as tools. The annotation coverage test passes.

- **Correction to the issue's "hosted picks are not copied" claim.** It is half wrong. `ProjectBackgroundLibrary.adopt(path:)` leaves only a **Downloaded-cache** path in place (`isCached` checks `Library/Downloaded`). A Background Sets pick lands in `Library/Hosted`, and the editor's picker copies it into the Project background folder before it reaches the draft: `BackgroundOverrideSettingsView.startAdopt(ofLibraryPath:)` (`Views/BackgroundOverrideSettingsView.swift:374`) calls `library.importer.adoptImage(path:from: images.pickSources)`, where `pickSources` = [My Images folder, Hosted folder]. So the CLI route for a hosted image is: `await hosted.select(image).value` gives the Hosted path (nil means the fetch failed). Then `await store.projectBackgrounds.importer.adoptImage(path:from: store.backgroundImages.pickSources)` digest-copies it into the Project folder (nil means the copy failed). My Images (by digest) uses the same `adoptImage` on the entry's path. A local `--background-file` uses `await store.projectBackgrounds.importer.importImage(from:)`, the re-encoding import that `ProjectBackgroundFixture.copy` uses. A Pane or Tab level also gets `store.tabImageIdentity.identity(forPath: copy, keeping: nil)`. That gives `.hosted(url:name:)` for a hosted copy, because the digest folder name survives the copy and `derive` finds the Hosted record. Anything else gets `.custom`. The Project level stores no `image`. `ProjectStore.upsert` computes `sharedImage` for a Shared Project.
- **Privacy rule.** The built-in catalog is never fetched before the user's first Browse (`HostedBackgroundsModel.refresh` returns early when `!hasBrowsed`, and `canCheckNow` says the same; Help and the privacy page promise it). The CLI keeps that promise. `background list` never marks the catalogs browsed. Before a first Browse, the built-in catalog shows only a cached copy, or nothing plus a warning. `--background-id` accepts only a URL found in a loaded catalog, so the CLI never downloads an arbitrary URL.
- The editor's opacity controls run 0...1 (`TerminalBackgroundControls.opacityRow`, `in: 0...1`). New Projects get `runStartupCommandsOnOpen = true` (`ProjectDraft` init default), while `Project`'s init defaults to false.
- **Not flagged.** `project` and MCP ship unflagged, and these verbs are complete when they merge, so no feature flag is needed (`docs/feature-flags.md` rule: only unfinished features are flagged).

### Decisions on the open questions (recorded defaults; the user can override)

1. **`--opacity N`** is the Project background's `imageOpacity`, as a whole percent from 0 to 100. A value outside that range is a usage error (exit 64, from ArgumentParser `validate()`), not a silent clamp. It cannot go above 100 because the Project Editor's own control stops at 100%. The model allows more only for libghostty's opacity-boost case, and the CLI must not save a value the editor can't show or edit back. `--opacity` defaults to 15 (`firstImageOpacity`) for a first image. When an image is replaced, the old opacity is kept (`pickingImage` semantics). `--opacity` with no image given and none stored exits 4 ("--opacity needs an image").
2. **`--terminal-opacity N`** is `terminalOpacity`, 0 to 100, default 100. It is allowed without an image (a see-through Project background with no image).
3. **No delete verb.** Deferred: a later issue may add `project delete --yes` (`close` archetype).
4. **The layout schema is a small DTO, not the `projects.json` encoding.** That encoding is verbose (`{"type":"pane","pane":{...}}`), decodes leniently (a bad field silently drops), and carries device paths. The DTO is `ProjectLayoutDocument` in BattyXPCCore (below). It decodes strictly, and the app maps it onto `ProjectLayout`.
5. **Name collision on create**, ignoring case, exits 4 with `a Project named "X" already exists`, and nothing is written. On `edit`, `--name` colliding with another Project is the same error.
6. **`edit` touches only the fields given.** It starts from the stored `Project` (keeping `id`, `approvedCommandsHash`, `lastOpenedAt`, `isShared`, `sharedImage`, `splitFractions`, Pane/Tab backgrounds, mute and the Pane list) and changes only what flags name. `--preset`, `--layout`/`--layout-json` and `--from-session` replace the whole `layout`.
7. **`--from-session`** reuses `SaveSessionAsProject.draft(for:destination:store:)`. Create uses `.newProject`, edit uses `.update(project.id)`, and edit takes only the draft's `layout` from it.
8. **Shared Projects unchanged.** Writes go through `ProjectStore.upsert` (publish, `sharedImage`). Create sets `isShared = false`, and edit never changes `isShared`.
9. **MCP has no stdin** (`MCPToolRunner` sets `standardInput = nullDevice`), and it runs in the server's cwd. So besides `--layout FILE|-`, add **`--layout-json TEXT`** (inline document). That is the form agents use through MCP.
10. **`--from-session`** is a flag. The Session is `--session <id>`, else `BATTY_SESSION_ID`, else the focused Session (the same fallback the `session` verbs use). The app returns an "unknown session id" failure (exit 4) when none matches.
11. **Extra flags beyond the issue's synopsis**, kept small: `--background-digest D` (a My Images image, mirroring the layout document's `digest`), `--no-theme` (clears the Theme on edit), and `--session` (above).
12. **`background list` exit codes:** exit 0 whenever at least one image is listed, with any catalog problems printed to stderr as warnings (and in `--json` under `warnings`). It exits 4 when nothing at all can be listed and some catalog has a problem or was never fetched (the message names the cause and says to open Background Sets once). An unknown `--set` exits 4 and lists the set names.
