# 0421 — `scripts/run-ui-tests.sh` and `scripts/RELEASE.md` still send the release UI-test gate to the host runner, which can no longer build the UI tests once #0412 removes them from the Beta scheme

|---|---|

## Description

**`scripts/` is a restricted area (`AGENTS.md`, "Restricted areas").** The fix below needs the user's explicit sign-off before anyone edits `scripts/run-ui-tests.sh` or `scripts/RELEASE.md`. An implementer must not proceed on this issue's say-so alone.

The release checklist still names the old host UI-test runner as the gate. `scripts/RELEASE.md` step 2 ("Sanity-check the build and run tests", `:83-99`) lists:

```bash
./build.sh
./build.sh unit
scripts/run-ui-tests.sh   # full UI test suite — ~10 min, locks the machine
```

It then says "**UI tests are the gate for releases** … do not ship over a failing UI test", and "Run the preflight on the Mac mini". Once #0412 lands, that command no longer runs any UI tests:

- `issue/0412` removes `BattyUITests` from the Test actions of `Batty (Beta).xcscheme` and `Batty (Prod).xcscheme`. It moves the target to its own `Batty UI Tests` scheme, and only `tools/run-ui-tests-vm.sh` invokes that scheme.
- `scripts/run-ui-tests.sh` hard-codes `SCHEME="Batty (Beta)"` (`:39`). Its `build-for-testing` step (`:80-86`) therefore no longer builds `BattyUITests-Runner.app`. The script exits at `:102-104` with `==> Runner not found at: …/BattyUITests-Runner.app` (reported by the orchestrator; it follows from the code). If a stale runner from before #0412 is still in DerivedData, the script instead re-signs it and runs `test-without-building` against a scheme with no UI-test Testable. Either way no UI test runs, and the checklist's gate is empty.
- #0412's own doc is slightly wrong about this. `docs/ui-testing-vm.md` "Guards" item 3 (on `issue/0412`) says the host guard "blocks it structurally — the moment it tries `build-for-testing` against `BattyUITests`, the same guard phase fires". With `BattyUITests` out of the Beta scheme, the script never builds that target, so the guard never fires. The script fails earlier, for a different reason. Correct that sentence when this lands.

Before #0412 lands, the script still works on the host, and running it is the #0409 hazard. #0412 exists to retire that path: `AGENTS.md` on `issue/0412` forbids running `scripts/run-ui-tests.sh` on the host.

## Expected behavior

After the user signs off:

1. **`scripts/run-ui-tests.sh`** is either **retired** (deleted, with its Gatekeeper re-sign rationale kept in `docs/ui-testing-vm.md` history), or reduced to a thin shim that **delegates to `./build.sh ui "$@"`** and so to the VM runner. It must never invoke `xcodebuild` on the host. #0412 open question 5 found the re-sign unnecessary in the guest, so nothing guest-side depends on keeping it.
2. **`scripts/RELEASE.md` step 2** names `./build.sh ui` (VM) as the UI-test gate. It drops "locks the machine" and "Run the preflight on the Mac mini", since the VM needs neither. It points at `docs/ui-testing-vm.md` for the one-VM-at-a-time preflight and its "wait for a free slot" behavior.
3. Other references are updated to match:
   - `AGENTS.md:93` (on `issue/0412`) lists `scripts/run-ui-tests.sh` among the scripts that snapshot and restore `Active.xcconfig`.
   - `AGENTS.md:121` names it in the host "never run" list.
   - `docs/ui-testing-vm.md` Guards item 3 (above).
   - `website/changelog.html:127` mentions the script historically. It is probably fine to leave as history.

## Notes

- Sequence after #0412 merges. Until then, `main` still routes `./build.sh ui` through `scripts/run-ui-tests.sh` (`build.sh:79-84` on `main`).
- If the shim option is chosen, keep it from silently succeeding when the VM runner refuses to start because another VM is running. It should propagate the runner's exit status.
