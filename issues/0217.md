# 0217 — App silently quits when all shell processes exit, bypassing quit confirmation

| | |
|---|---|
| **Status** | open |
| **Module** | App / Tabs |
| **Platform** | macOS |
| **First seen** | 2026-05-27 |

## Description

When every shell process exits on its own — without any explicit user action — Batty silently terminates without showing a quit confirmation dialog. The user returns to find the app gone and all session context lost. The "confirm quit when terminals are open" preference is ineffective against this path because the confirmation check runs after all sessions have already been removed.

## Steps to reproduce

1. Open Batty with at least one active session.
2. Leave the app in the background while all running shell processes exit naturally (e.g., a script finishes, `exit` is called, or a long-running CLI tool such as Claude Code completes and returns to the shell, which then also exits).
3. Return to the app.

**Result:** Batty is no longer running. No dialog was shown.

## Expected behavior

Batty prompts before quitting, or does not quit at all. The "confirm quit when terminals are open" setting is respected regardless of how the close originates.

## Actual behavior

The app silently terminates. No dialog. No indication to the user that anything happened.

## Root cause (fully traced)

The bug lives at the intersection of three components:

**1. `PaneView` wires shell exit → `closeTab` (`PaneView.swift:145-153`)**

```swift
.task(id: tab.id) {
    tab.terminal.onClose = { [weak appStore, weak pane] _ in
        if let appStore {
            appStore.closeTab(id: tab.id)
        } else {
            pane?.removeTab(id: tab.id)
        }
    }
}
```

When libghostty reports that a terminal's child process exited, `onClose` fires and calls `appStore.closeTab`. This is the same path used for a user clicking the tab's close button — there is no distinction between "user closed this" and "shell exited on its own."

**2. `AppStateStore.closeTab` cascades all the way to app termination (`AppStateStore.swift:228-242`, `66-82`)**

`closeTab` → removes the tab from its pane → if pane is now empty, removes the pane from the tree → if the tree is now empty, calls `removeSession` → if `sessions` is now empty, posts `.battyAllSessionsClosed`. At this point, all session state is already gone.

**3. The quit-confirmation guard is bypassed (`QuitConfirmation.swift:23-26`)**

```swift
let openTabs = store.sessions.reduce(0) { acc, session in
    acc + session.tree.allPanes.reduce(0) { $0 + $1.tabs.count }
}
guard openTabs > 0 else { return true }
```

`applicationShouldTerminate` receives `NSApp.terminate(nil)` posted by the `battyAllSessionsClosed` observer. By then, every tab has already been removed from the store, so `openTabs == 0` and the guard returns `true` immediately — no dialog. The confirmation is structurally impossible to show at this point.

**The confirmation was never intended to guard this path.** It was written to protect against a user explicitly pressing Cmd-Q with live terminals open. The shell-exit path bypasses it entirely.

## Notes

### Observed instance

On 2026-05-27, Batty (PID 7680, started 18:36) had no crash log and no core dump. The prior process left `workspace.json` dated May 21 (unread on launch — workspace restore is not yet implemented). The bell feed entry `"Claude Code: Claude is waiting for your input"` in workspace.json identifies Claude Code as the process that was running; when it exited and the shell followed, the cascade ran silently.

### Fix options

Three approaches, from least to most invasive:

**A. Do not auto-close on shell exit (recommended baseline).** When `onClose` fires because the shell exited (not because the user closed the tab), leave the pane open showing a "Process exited" placeholder (similar to how Terminal.app and iTerm2 behave by default). The user explicitly closes the tab/pane/session. This makes the close cascade a user-only action, not a process-exit action. Requires distinguishing user-close from process-exit at the `onClose` callsite — libghostty's `terminalDidClose(processAlive:)` delegate provides the `processAlive` flag, but that only indicates whether the process is still alive at close time, not the close reason. May need a new signal or heuristic.

**B. Guard the last-session removal.** Before `removeSession` empties `sessions`, check whether any live tabs remain and, if so, show the quit confirmation at that point rather than delegating to `applicationShouldTerminate`. The confirmation fires while the state is still present, making the dialog meaningful. This keeps auto-close on shell exit but inserts a "you're about to lose everything, quit?" step.

**C. Reset to empty session instead of quitting.** When `removeSession` would leave `sessions` empty via the shell-exit path (not a user quit), post a different notification (e.g., `.battyAllTerminalsClosed`) and respond by creating a fresh default session rather than terminating. The app stays open and ready. The downside: the user may not notice their previous session context is gone.

**D. Add a "close tab when process exits" preference** (default: on for compatibility) to gate whether `onClose` calls `closeTab` or leaves the tab open. Most terminal emulators offer this. Makes Option A opt-in rather than forced.

Workspace restore (`#Persistence`) would reduce the impact of any of these by allowing the last session layout to be recovered on next launch, but it does not prevent the silent-quit problem.
