# 0169 — UI test suite: modal confirmation flows (paste, quit, close-with-process)

| | |
|---|---|
| **Status** | resolved |
| **Module** | Tests / Settings / App / Tabs |
| **Platform** | macOS |
| **First seen** | 2026-05-20 |

## Description

Three confirmation modals — multi-line paste ([[0035]], [[0105]]), close-with-process-running ([[0036]], [[0054]]), and quit ([[0036]]) — protect users from accidentally running dangerous input or losing work. Each has had at least one regression and all three are easy to break by accident because they intersect with the existing UI-test bypass (`BATTY_UI_TEST_MODE`) that suppresses them. The bypass is required for the suite to run at all, so testing the modals requires a *second* harness mode that allows them but auto-dismisses with a chosen outcome.

## Regressions this suite would have caught

- [[0035]] — Multi-line paste confirmation initial wiring. Tests that the sheet appears for multi-line content and not for single-line content.
- [[0036]] — Close-confirmation when processes are running + About panel. Tests that closing a pane with a long-running shell prompts confirm.
- [[0054]] — `Cmd-W` should close the active tab, with confirmation if a process is running. Tests that the confirmation gates the close.
- [[0105]] — Multi-line paste prompt is on by default. Covered in [[0166]] for the default-value side; here we cover the *behavior* once the prompt is enabled.

## Test cases

### Multi-line paste — would catch [[0035]] / [[0105]]

- **Single-line paste does not prompt.** Driver: copy a single-line string to the pasteboard (`setPasteboardString` intent). Paste into the focused terminal via `Cmd-V`. Assert no `multi-line-paste-sheet` exists; assert the text reached the terminal (sentinel check).
- **Multi-line paste shows the sheet.** Copy `"line1\nline2\n"`. Paste. Assert `multi-line-paste-sheet` exists.
- **Confirming the sheet sends the paste.** Dismiss with the Paste button. Sentinel: verify both lines reached the shell.
- **Cancelling the sheet sends nothing.** Dismiss with Cancel. Sentinel stays empty.

### Close-with-process — would catch [[0036]] / [[0054]]

- **Closing a tab running `sleep 1000` shows confirmation.** Driver: focus tab, send `sleep 1000`, wait, type `Cmd-W`. Assert `close-confirmation.sheet` exists.
- **Confirm closes the tab.** Click Close in the sheet. Assert the tab chip is gone.
- **Cancel keeps the tab.** Click Cancel. Assert the tab still exists.
- **Closing a tab at a clean prompt does NOT prompt.** Fresh tab, no running process, `Cmd-W`. Assert no sheet; tab closed.

### Quit confirmation — would catch [[0036]] regressions

- **Quit with no running processes proceeds silently.** Driver: clean state. Send `Cmd-Q` (with the bypass disabled). Assert app terminates.
- **Quit with a running process shows confirmation.** Start a `sleep 1000` in a pane. Send `Cmd-Q`. Assert `quit-confirmation.sheet` exists.
- (This test must NOT use the existing `BATTY_UI_TEST_MODE` bypass — see below.)

## Harness extension required

The existing `BATTY_UI_TEST_MODE=1` short-circuits all three modals so `xcodebuild test`'s terminate doesn't hang. That bypass is incompatible with these tests. Options:

- **Per-modal env vars.** New `BATTY_UI_TEST_ALLOW_PASTE_PROMPT=1` / `..._ALLOW_CLOSE_PROMPT=1` / `..._ALLOW_QUIT_PROMPT=1`. The test sets the one it wants, leaves the others off.
- **Test-mode "intercept and auto-dismiss".** Single env var `BATTY_UI_TEST_AUTO_DISMISS=<outcome>` that lets the modal *appear* (so the test can assert presence) but auto-dismisses after a short delay with the chosen outcome. Simpler than juggling per-modal flags.

Recommend the per-modal-allow approach — gives the most explicit test control and the simplest production-code impact (each modal already gates on a bool from `QuitConfirmation.isInUITestMode`-style check; just split the check).

## Accessibility identifiers needed

- `multi-line-paste-sheet`, `.paste-button`, `.cancel-button`.
- `close-confirmation.sheet`, `.close-button`, `.cancel-button`.
- `quit-confirmation.sheet`, `.quit-button`, `.cancel-button`.

## Driver intents needed (from [[0158]])

- `setPasteboardString(text:)`.
- `sendShellInput(text:)` — already in [[0164]]'s vocabulary.
- The Cmd-V / Cmd-W / Cmd-Q can be driven via `XCUIApplication.typeKey(...)`.

## Out of scope

- The system pasteboard's behavior across processes (system surface, not Batty's).
- The "Don't ask again" toggle if/when added (tracked separately).
- About panel content (separate concern; trivial).

## Acceptance criteria

- All test cases pass under `xcodebuild -scheme 'Batty (Beta)' -destination 'platform=macOS' test`.
- The per-modal harness extension is implemented and documented.
- The quit test runs reliably without hanging the test runner (the per-modal flag is the mitigation).

## Notes

- Depends on [[0158]] for the foundation and on a small `QuitConfirmation`-area change for the per-modal env-var split.
- This suite must run *after* the test that confirms `BATTY_UI_TEST_MODE` is still respected — otherwise a regression that silently disables the bypass would only show up here, by hanging.
