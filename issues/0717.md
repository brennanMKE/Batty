# 0717 — The Beta Sparkle auto-confirm hook installs an update at launch before it is triggered

| | |
|---|---|
| **Status** | open |
| **Module** | Build / Testing |
| **Platform** | macOS |
| **First seen** | 2026-11-22 |
| **Target** | 1.5.0 |

## Description

With `BATTY_BETA_SPARKLE_AUTO` set (#0714), Batty Beta checks the feed, downloads and installs an update about one second after launch, before the trigger notification is posted. #0714's contract says the headless updater is **armed** at launch and checks **only** when the distributed notification `co.sstools.Batty.beta.sparkle-auto.check` arrives, so a test can set up Sessions and record a baseline first (#0714 "Deviation from the issue: the check is triggered, not run at launch").

The check that ran was Sparkle's own scheduled or automatic one, not the hook's: no `sparkle-auto: check requested` line appears before `update found`. The headless user driver then installs whatever that check finds, because `updateFoundChoice` replies `.install` regardless of who started the check.

#0715's runner works around this by serving an appcast with no `<item>` until its `trigger` step copies the real appcast into place. That workaround hides the bug. A harness that serves the real feed from the start installs B before any Session exists, and the test then measures nothing.

Only the hook is affected: Prod ignores `BATTY_BETA_SPARKLE_AUTO`, and a Beta without the variable builds the standard updater exactly as before (#0714 Review).

## Evidence

Run `20261122-005540-91680` (#0715 runner, relaunch mode, packages reused from `20261122-005046-82299`, A=202611220850, B=202611220851). This run was made before the empty-feed workaround, so the guest served the real appcast from the start. Results are in the `issue-0715` worktree under `build/sparkle-tests/20261122-005540-91680/relaunch/guest/logs/`.

`sparkle-auto.log`, with no `check requested` line and no trigger posted (the run stopped earlier, at `populate: exit 3`):

```
08:56:18.587 sparkle-auto: update found version=1.5.0 build=202611220851 stage=notDownloaded
08:56:18.596 sparkle-auto: downloading
08:56:18.731 sparkle-auto: extracting
08:56:19.362 sparkle-auto: ready to install
08:56:19.362 sparkle-auto: installing and relaunching
08:56:19.370 sparkle-auto: installing applicationTerminated=false
```

`feed-server.log`: the 08:56:12 request is the guest's own readiness probe (`curl`). The app fetched at 08:56:18, 1.2 s after `armed`:

```
"GET /appcast.xml HTTP/1.1" 200 -    [08:56:12]
"GET /appcast.xml HTTP/1.1" 200 -    [08:56:18]
"GET /B.dmg HTTP/1.1" 200 -          [08:56:18]
```

The guest's `defaults.txt` from the same run (collected after the failure) has `SUHasLaunchedBefore = 1` and `SULastCheckTime = "2026-11-22 08:56:19 +0000"`, written by that check. The guest had never launched Batty Beta before this run.

For comparison, run `20261122-010002-102` (empty feed until the trigger) logs `check requested` at 09:00:57.837, then `update found` at 09:00:57.849. That is the ordering the contract requires.

The workaround in the #0715 runner is in `tools/vm-guest-sparkle.sh` (on `issue/0715`):
- the `setup` step: the comment "The headless updater also runs Sparkle's own launch-time check, so the feed holds no item until `trigger` swaps the real appcast in", then `sed '/<item>/,/<\/item>/d'` writing the empty `feed/appcast.xml`;
- the `trigger` step: `cp "$S/appcast-real.xml" "$S/feed/appcast.xml"` before posting the notification.

## Likely cause (for the plan to confirm)

- `Configuration/Info.plist` sets `SUEnableAutomaticChecks = true`. The hook's `UpdaterController.init` (`.headless` branch) calls `SPUUpdater.start()`, which begins Sparkle's update cycle. A fresh guest has no `SULastCheckTime`, so the first scheduled check is due at once.
- `SparkleAutoConfirmUserDriver` treats a scheduled check like a requested one, and `SparkleAutoConfirm.updateFoundChoice` returns `.install`.
- #0714's plan assumed "No scheduled-check wait" and verified only through unit tests that never start an `SPUUpdater` (#0714 Gotchas: "The hook has not run live yet").

Possible fixes, for the plan to choose: turn automatic checks off for the headless updater only (`automaticallyChecksForUpdates = false` before `start()`, or the `SPUUpdaterDelegate` scheduling hooks); or have the driver dismiss any update found by a check the hook didn't request. The fix must not change the `.standard` path, Prod, or a Beta without the variable.

## Expected behavior

With the hook set, the app logs `sparkle-auto: armed mode=…` and then makes no feed request until the trigger arrives. After `check requested`, it behaves as #0714 specifies. Nothing else about the contract (variable, values, notification name, log lines) changes.

## Acceptance criteria

- With `BATTY_BETA_SPARKLE_AUTO` set and a feed that offers a newer build from the start, no request for the appcast is made and no `update found` line is logged before the trigger is posted, for at least as long as the runner's populate and baseline steps take.
- After the trigger, `check requested` comes before `update found`, in both `relaunch` and `onquit` modes.
- The `.standard` path is unchanged: Prod, and a Beta without the variable, still build `SPUStandardUpdaterController(startingUpdater: hasFeedURL, …)` with automatic checks as today.
- Unit tests pin whatever decides this (for example, that the headless backend turns automatic checks off, or that a hook-unrequested update is dismissed), without starting an `SPUUpdater` or using the network, and with no sleeps.
- **The #0715 runner workaround is removed:** `tools/vm-guest-sparkle.sh` serves the real appcast from `setup` on, and `trigger` only posts the notification. The runner then still gets past `trigger` with the same result as before. How this relates to #0715:
  - If #0715 has already merged when this lands, remove the workaround in this issue's branch.
  - If #0715 has not merged, note in #0715 that the workaround stays until this issue lands, and remove it here afterwards.
  - Either way, record a runner run id that shows `armed` → (no feed request) → `check requested` → `update found` with the real feed served from the start.

## Things to verify

- That the extra check is Sparkle's scheduled check and not something else (for example a second `start()` or the relaunched B). Sparkle logs (`org.sparkle-project` subsystem) around `armed` should show which.
- Whether `SULastCheckTime` or `SUEnableAutomaticChecks` in the guest's defaults (`defaults.txt` in the run folder) changes the timing. The fix must not rely on a clean defaults domain.
- That the relaunched B, which starts without the variable and runs the standard driver, still shows no UI in the VM (its feed holds nothing newer).
- Grep every comment the fix adds or changes in `UpdaterController.swift`, `SparkleAutoConfirm.swift` and the #0714 contract text for claims that are no longer true (for example "checks when the … distributed notification arrives").
