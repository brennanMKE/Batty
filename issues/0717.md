## Description

With `BATTY_BETA_SPARKLE_AUTO` set (#0714), Batty Beta checks the feed, downloads and installs an update about one second after launch, before the trigger notification is posted. #0714's contract says the headless updater is **armed** at launch and checks **only** when the distributed notification `co.sstools.Batty.beta.sparkle-auto.check` arrives, so a test can set up Sessions and record a baseline first (#0714 "Deviation from the issue: the check is triggered, not run at launch").

The check that ran was Sparkle's own scheduled or automatic one, not the hook's: no `sparkle-auto: check requested` line appears before `update found`. The headless user driver then installs whatever that check finds, because `updateFoundChoice` replies `.install` regardless of who started the check.

#0715's runner works around this by serving an appcast with no `<item>` until its `trigger` step copies the real appcast into place. That workaround hides the bug. A harness that serves the real feed from the start installs B before any Session exists, and the test then measures nothing.

Only the hook is affected: Prod ignores `BATTY_BETA_SPARKLE_AUTO`, and a Beta without the variable builds the standard updater exactly as before (#0714 Review).

### Cause, confirmed in the code

- `UpdaterController.init`, `.headless` branch: `SPUUpdater(… delegate: nil)` then `try updater.start()`.
- `SPUUpdater.m` `startUpdater:` (l.146–190) dispatches `startUpdateCycle` to the next main-queue turn. `startUpdateCycle` (l.398–466) doesn't prompt, because `SUEnableAutomaticChecks` is in `Info.plist` (`[_host boolNumberForKey:SUEnableAutomaticChecksKey] != nil`). It calls `scheduleNextUpdateCheckFiringImmediately:NO usingCurrentDate:YES` (l.503–600). With `automaticallyChecksForUpdates == YES` and no `SULastCheckTime`, `lastCheckDate` is `distantPast`, so the check is overdue and `_checkForUpdatesInBackground` runs at once with `SPUUpdateCheckUpdatesInBackground`. This is Sparkle's scheduled check, not a second `start()` and not the relaunched B, which matches `SULastCheckTime` being written by that check and the 1.2 s gap after `armed`.
- That check uses `SPUScheduledUpdateDriver`, which still calls the user driver's `showUpdateFound`, and `SparkleAutoConfirm.updateFoundChoice` replies `.install`.
- With an old `SULastCheckTime`, the same thing happens one `SUScheduledCheckInterval` later, so a fix can't rely on clean defaults.

### Fix chosen: the headless updater gets a delegate that refuses every check the hook didn't start

`SPUUpdaterDelegate.updater(_:mayPerformUpdateCheck:error:)` (Swift: `func updater(_ updater: SPUUpdater, mayPerform updateCheck: SPUUpdateCheck) throws`) runs in `checkForUpdatesWithDriver:` (l.844–855) before the driver fetches the feed. Throwing aborts that check through `abortUpdateDriver(error, YES)`. For a scheduled driver, `showErrorToUser` is `_showedUpdate` (`NO`), so the user driver gets no call at all (`SPUScheduledUpdateDriver.m` l.104–107, `SPUUIBasedUpdateDriver.m` l.452–494). No feed request, no `sparkle-auto:` driver line, and the next scheduled attempt is an interval away and refused the same way.

The hook's own check is `updater.checkForUpdates()`, which is `SPUUpdateCheckUpdates`. So the rule is: **allow `.updates`, refuse `.updatesInBackground` and `.updateInformation`.**

Rejected alternatives:
- `updater.automaticallyChecksForUpdates = false` before `start()`. The header and `SPUUpdaterSettings` say the setter **persists to the host bundle's user defaults** (`co.sstools.Batty.beta`). It would turn automatic checks off for the relaunched B and for every later launch of that Beta, including a developer's own Beta. That's a change outside the hook.
- `-SUEnableAutomaticChecks NO` in the argument domain. `open --env` can't pass arguments, and rewriting `NSArgumentDomain` from inside the app is a process-wide hack.
- Driver replies `.dismiss` to an unrequested update. The feed and the download request would still be made, which fails the first acceptance criterion, and the scheduled driver's dismissal is a "skip until later" with its own side effects.

The `.standard` path is untouched: `SPUStandardUpdaterController(startingUpdater: hasFeedURL, updaterDelegate: nil, userDriverDelegate: nil)` stays byte-for-byte. The headless `start()`-failure fallback also stays `updaterDelegate: nil`. (#0718 later gives the standard path a delegate. See "Interaction with #0718" below.)

A small race remains and is accepted: while Sparkle's scheduler probes install status (`scheduleNextUpdateCheck…` sets `sessionInProgress` for one async probe right after start), a trigger posted in that window logs `check ignored: session in progress`. The runner posts the trigger minutes after `armed`, after populate and baseline. Record this in `## Gotchas`.

## Resolution notes

> 🟢 Resolved 2026-11-22 — The headless updater's delegate refuses Sparkle's scheduled checks, so the hook checks only on its trigger, and the runner serves the real feed from setup.

## Root cause

The headless `SPUUpdater` was built with `delegate: nil` and started. `Info.plist` sets `SUEnableAutomaticChecks`, so `startUpdateCycle` scheduled Sparkle's own check, due at once on a fresh guest (no `SULastCheckTime`) and one `SUScheduledCheckInterval` later otherwise. That `SPUScheduledUpdateDriver` check still reached `SparkleAutoConfirmUserDriver.showUpdateFound`, which replies `.install` whoever started the check.

## Fix

- `SparkleAutoConfirm.allowsUpdateCheck(_:)`: only `.updates` (the hook's own `updater.checkForUpdates()`) is allowed. `.updatesInBackground` and `.updateInformation` are refused.
- New `SparkleAutoConfirmUpdaterDelegate` (`SPUUpdaterDelegate`): `updater(_:mayPerform:) throws` calls `decide(_:)`, which logs `sparkle-auto: background check refused` and throws an `NSError` in the private domain `co.sstools.Batty.SparkleAutoConfirm`, code 1 (not `SUNoUpdateError`). Sparkle aborts the check before fetching the feed and, for a scheduled driver, tells the user driver nothing.
- `UpdaterController`: the `.headless` backend passes the delegate to `SPUUpdater` and keeps it strongly in `Running.headless` (Sparkle holds it weakly). The `.standard` path and the `start()`-failure fallback are unchanged (`updaterDelegate: nil`). Doc comment updated: checks run only on the notification; the delegate refuses scheduled checks.
- Tests call `decide(_:)` directly rather than constructing an `SPUUpdater`, so nothing touches the host bundle under `swift test` (the plan's fallback path).
- `tools/vm-guest-sparkle.sh`: the #0715 workaround is gone. `setup` copies the real appcast straight to `feed/appcast.xml`; `appcast-real.xml` is dropped and the onquit `want=` reads `feed/appcast.xml`. `launch` records its stream offset in `launch-offset.txt`; `trigger` fails with `GUEST-ERROR: sparkle-auto: update found before the trigger` if the stream since launch holds `update found`, and then only posts the notification. `feed-requests.txt` gets the `GET /appcast.xml` count at launch and at trigger (informational).
- `docs/ui-testing-vm.md`: the empty-feed sentence is replaced by the refusal and the new trigger guard.

## Decisions

- The new log line `sparkle-auto: background check refused` is accepted as an addition to #0714's contract (orchestrator decision). No existing name, value or line changes.
- The refusal is a delegate gate, not `automaticallyChecksForUpdates = false`, because that setter persists to the Beta's defaults.

## Review

Round 1: code approved first pass; VM verification by the orchestrator (run `20261122-021932-45348`) confirmed the log order in both modes, so resolved.

- **Refusal, checked in Sparkle 2.9.1 source.** `SPUUpdater.m` `checkForUpdatesWithDriver:` calls `updater:mayPerformUpdateCheck:error:` before the configuration check and before the driver runs, and aborts through `abortUpdateDriver(error, YES)`, so no feed request is made. The scheduled driver aborts with `showErrorToUser:_showedUpdate` (`NO` before an update is shown), and `SPUUIBasedUpdateDriver` then calls no user-driver method; the automatic and probing drivers never reach the user driver on abort. The compiled `SparkleAutoConfirmUpdaterDelegate.o` carries the `updater:mayPerformUpdateCheck:error:` ObjC thunk, so the Swift method really binds to the optional requirement.
- **Hook's own check allowed.** `-checkForUpdates` is the only `SPUUpdateCheckUpdates` call site (`SPUUpdater.m` l.735); scheduled is `.updatesInBackground` (l.640), `checkForUpdateInformation` is `.updateInformation` (l.774).
- **Unchanged paths.** `.standard` and the `start()`-failure fallback are byte-identical (`updaterDelegate: nil`). Prod and unhooked Betas never construct the delegate.
- **Delegate lifetime.** `SPUUpdater` holds `__weak _delegate` (l.72); `Running.headless` keeps it strongly.
- **Guest script.** `appcast-real.xml`, the `sed` item strip and the trigger-time copy are all gone; no other reference remains in the repo outside resolved issue history. The trigger guard reads `launch-offset.txt` (a missing file hits `err "no launch offset"`; checked in zsh), and the script has no `pipefail`, so `grep -q` exiting early can't mask a match.
- **Tests** assert the throw, the exact log line, the silent allow and the error domain; no sleeps, no `SPUUpdater`.
- **Comments and docs** grepped: the class doc, `allowsUpdateCheck` doc, the `decide` doc, the code-1 comment and the `docs/ui-testing-vm.md` sentence all match the code and Sparkle source.

Non-blocking notes (no change required):
- If the stream log ever shrank below the launch offset, `tail -c +N` would print nothing and the trigger guard would pass silently. Nothing rotates or truncates `stream.log` (one launchd agent, written once in `setup`, fresh clone per mode), and the existing `wait_log` uses the same offset pattern, so this is only a hardening option: `(( $(stream_size) >= launch_off )) || err "stream truncated since launch"`.
- A refused scheduled check still runs `updateLastUpdateCheckDate`, so `SULastCheckTime` is written in the hooked Beta's defaults, as any check would. It only defers that Beta's next scheduled check by one interval.
- The tests call `decide(_:)`, not the protocol method; the selector binding is confirmed by the compiled thunk, not by a test. A `responds(to:)` check on `updater:mayPerformUpdateCheck:error:` would pin it.

## Likely cause (for the plan to confirm)

- `Configuration/Info.plist` sets `SUEnableAutomaticChecks = true`. The hook's `UpdaterController.init` (`.headless` branch) calls `SPUUpdater.start()`, which begins Sparkle's update cycle. A fresh guest has no `SULastCheckTime`, so the first scheduled check is due at once.
- `SparkleAutoConfirmUserDriver` treats a scheduled check like a requested one, and `SparkleAutoConfirm.updateFoundChoice` returns `.install`.
- #0714's plan assumed "No scheduled-check wait" and verified only through unit tests that never start an `SPUUpdater` (#0714 Gotchas: "The hook has not run live yet").

Possible fixes, for the plan to choose: turn automatic checks off for the headless updater only (`automaticallyChecksForUpdates = false` before `start()`, or the `SPUUpdaterDelegate` scheduling hooks); or have the driver dismiss any update found by a check the hook didn't request. The fix must not change the `.standard` path, Prod, or a Beta without the variable.

## Expected behavior

With the hook set, the app logs `sparkle-auto: armed mode=…` and then makes no feed request until the trigger arrives. After `check requested`, it behaves as #0714 specifies. Nothing else about the contract (variable, values, notification name, log lines) changes.
