## Description

Settings → AI Agents gets guided setup next to the CLI tool install: the developer chooses to install the CLI and/or MCP. The **Rescope** section below overrides the "First offer" bullet, acceptance criterion 2, open question 1 and the plan's Step 3 on `issue/0666`; Steps 1-2 there (record, policy, coordinator, silent refresh) stay. `docs/design/agent-setup-offer.md` (on `issue/0666` only) is superseded and should not land. Re-plan Step 3 on the branch before implementing; when the branch's copy of this file conflicts with `main` at merge, keep `main`'s Description, Rescope, Expected behavior and Acceptance criteria.


Child of #0660. The `batty` MCP server, the skill, and the plugin hook reach an agent only after the user discovers `batty agent install` or Settings → Advanced → AI Agents. And once installed, they stay at the version that installed them: the plugin is staged with `identity.version`, the skill is copied, and nothing re-runs the installer when Batty updates. "Automatic" should mean: one clear prompt the first time, then Batty keeps what the user accepted up to date by itself.

### Current state

- The installer runs only on request: `AgentInstallCommand` (`BattyKit/Sources/batty/AgentCommand.swift`) or the Settings rows (`AgentIntegrationModel.beginInstall`/`confirmInstall`, `BattyKit/Sources/BattyKit/Settings/AgentIntegrationModel.swift:58-76`; shown by `AdvancedSettingsView` only with `agentIntegration`, `BattyKit/Sources/BattyKit/Views/SettingsView.swift:497`).
- The plugin manifest and marketplace carry `identity.version` (`AgentGuidanceInstaller.stageMarketplace`, `BattyKit/Sources/BattyCLICore/AgentGuidanceInstaller.swift:358-386`); copied skills are stamped (`copySkill(… stamp:)`, `:397`). Nothing compares them with the running app's version.
- MCP entries point at the CLI inside the app bundle (`identity.cliExecutablePath`), so moving or renaming the app breaks them silently.

## Rescope (2026-11-19)

- **No offer.** Nothing at launch: no sheet, banner, Bell Feed row or prompt. `AgentSetupPolicy`'s `.offer` decision and `WindowRuntime.pendingAgentSetupOffer` are removed (or never built); a missing record means "never set up" and nothing happens.
- **Guided setup in Settings → Advanced.** The Command-Line Tool and AI Agents sections become one guided flow (layout per the plan; a short design note in the plan is enough): (1) **Command-line tool** — install/uninstall the `batty` (or `batty-beta`) symlink, as `CLIInstallRow` does today; (2) **MCP server and agent guidance** — a checkbox per detected host (Claude Code, Codex, Cursor, OpenCode), each saying what it writes (MCP entry, skill, plugin/hook), then Install… with the existing confirmation of the plan's action list. The developer can choose CLI only, MCP only, or both. Short guidance text explains each and links to Help (#0671).
- **Record and refresh.** Install… records `accepted` with the hosts chosen (`recordManualInstall`), and the CLI install is recorded too if the refresh needs it (e.g. a moved app re-points the symlink). The silent post-update refresh stays as built in Steps 1-2: only for what the user installed, logged, problem lines shown as a caption in Settings, never a modal.
- A fresh install shows nothing new until the developer opens Settings → Advanced and installs something.

## Expected behavior (as filed 2026-11-18; the "First offer" bullet is superseded by the Rescope above)

- **First offer.** On a launch where an agent host is detected (same detection as `plan`) and Batty has never asked, Batty offers setup once: what it will install for which hosts (the plan's summary) with **Set Up** and **Not Now**. Not Now is remembered; Settings → AI Agents stays the way back. Nothing is written without Set Up.
- **Refresh after update.** On launch, if the user accepted setup earlier and the installed guidance's version differs from the app's (or the recorded CLI path no longer exists), Batty re-applies only the actions for hosts it set up before, without asking, and logs the report. A `manual` or `failed` outcome shows a non-blocking note in Settings → AI Agents, never a modal.
- **State.** One small record of what was accepted and at which version (for example in `UserDefaults` under a `co.sstools.Batty…` key, injected so tests isolate it per `docs/isolate-userdefaults-in-tests.md`).
- The installer's file and subprocess work runs off the main actor (as `confirmInstall` already does with `Task.detached`).
- UI tests never write to the real home: the UI-test driver suppresses the offer.

## Acceptance criteria

1. Unit tests with an injected installer and defaults: offer shown once when a host is detected and never asked; not shown after Not Now or after Set Up; refresh runs with no prompt when the recorded version differs, and only for previously accepted hosts; no refresh when versions match.
2. ~~The offer's visual design is drafted and approved by the user before implementation.~~ Superseded (no offer). Instead: unit tests show a missing record yields no action at launch; Settings installs exactly the hosts the developer checked (CLI only, MCP only, both).
4. A fresh install shows nothing new: no sheet, prompt or banner at launch (UI test: plain launch, no `agent-setup-offer` element).
3. `./build.sh ui-typecheck` passes for any new UI test; the offer is suppressed under `BATTY_UI_TEST_SCRIPT`.

## Decisions (user, 2026-11-18)

- "Automatic" means: ask once, then on each app update silently refresh what the user accepted.
- `agent install` does not touch global instruction files (#0664); the offer can show #0664's copyable prompt instead.
