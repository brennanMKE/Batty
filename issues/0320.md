## Description

A full recompile of the current `main` tree emits **seven compiler warnings across five files** — and none of them show up in normal use, because `scripts/build.sh` on an unchanged tree recompiles nothing and reports a clean build. All seven were re-verified on 2026-08-07 by touching the five sources and rebuilding (`BUILD SUCCEEDED`, warnings emitted):

```
Batty/BattyApp.swift:16:44 — left side of nil coalescing operator '??' has non-optional type 'WindowID', so the right side is never used
BattyKit/Sources/BattyKit/Runtime/TerminalHostStore.swift:329:18 — weak variable 'viewProbe' was never mutated; consider changing to 'let' constant
BattyKit/Sources/BattyKit/Runtime/TerminalHostStore.swift:330:18 — weak variable 'tabProbe' was never mutated; consider changing to 'let' constant
BattyKit/Sources/BattyKit/Theme/AppearanceObserver.swift:23:24 — call to main actor-isolated instance method 'applyGlobalThemeForCurrentAppearance()' in a synchronous nonisolated context
BattyKit/Sources/BattyKit/Views/SplitContainerView.swift:147:13 — capture of non-Sendable type 'Left.Type' in an isolated closure
BattyKit/Sources/BattyKit/Views/SplitContainerView.swift:147:13 — capture of non-Sendable type 'Right.Type' in an isolated closure
BattyKit/Sources/BattyKit/Views/TerminalPlaceholderView.swift:47:65 — main actor-isolated static property 'coordinateSpaceName' can not be referenced from a Sendable closure
```

Every cited path and line matches the current tree. These are not one problem; they group into three kinds, below, and each needs its own assessment — this issue is a cleanup umbrella, not a single defect.

## The warnings, grouped by kind

### 1. Dead code that already misled a review — `BattyApp.swift:16`

`WindowGroup(for: WindowID.self)` supplied with a `defaultValue:` closure yields a **non-optional** binding, so in

```swift
ContentView(windowID: windowID ?? AppStateStore.shared.initialWindowID)
```

the `??` never evaluates and `AppStateStore.shared.initialWindowID` is unreachable *at this call site*. The property is not dead overall — it is genuinely read at `BattyApp.swift:24`, the `defaultValue:` closure itself.

**Verified history** (`git log -L 14,20:Batty/BattyApp.swift`): the `??` and the `defaultValue:` closure were introduced **together** in #0237 (commit `7a92f22`, `windowID ?? WindowID()` alongside `defaultValue: { WindowID() }`), so the right-hand side has been dead since the day it was written — it is not a vestige from before `defaultValue:` existed. #0251 (commit `43b6e1f`) later rewrote both sides to `initialWindowID` without noticing the `:16` side could never run.

**This warning falsified part of #0316's analysis.** #0316's production-reachable inventory (item 1) counts `initialWindowID` as "read from two SwiftUI scene-body positions in `Batty/BattyApp.swift`: the `WindowGroup` content closure (`:16` ...) and the `defaultValue:` closure (`:24`)" and reasoned about a scene-body re-evaluation trapping through it. The `:16` read cannot execute — the binding is non-optional, so only the `:24` read is real. #0316's fix remains correct (the `:24` use is real, and `initialWindowID` must not trap on an empty `windows` array), but the safety argument was partly built on an unreachable branch. Removing the dead `?? ...` at `:16` eliminates the source of that confusion.

### 2. Swift 6 concurrency warnings — may hide real defects

Three warnings (four diagnostics) where the compiler is flagging isolation, under `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` / Swift 6.0:

- **`AppearanceObserver.swift:23`** — `store.applyGlobalThemeForCurrentAppearance()` (main-actor-isolated) called from the synchronous, nonisolated KVO callback closure in `NSApp.observe(\.effectiveAppearance)`. The most suspicious of the set: it is a theme-application call on a path where `docs/swiftui-observation-rules.md` is binding, and the file's own doc comment asserts the write is "safe under the `docs/swiftui-observation-rules.md` rules" — an argument about *observation* rules that does not answer the *isolation* question the compiler is raising.
- **`SplitContainerView.swift:147` (×2)** — the `.onGeometryChange(for:of:)` `of:` closure captures the generic `Left.Type` / `Right.Type` metatypes into an isolated closure.
- **`TerminalPlaceholderView.swift:47`** — `TerminalHostInstaller.coordinateSpaceName` (main-actor-isolated static) referenced from `.onGeometryChange`'s `Sendable` `of:` closure.

Each needs individual assessment: is the isolation annotation wrong, is the call site wrong, or is the code fine and the expression of it wrong? **These must not be silenced reflexively** with `@MainActor`, `nonisolated(unsafe)`, `@unchecked Sendable`, or assumeIsolated wrappers — the question is whether the isolation is actually correct, not how to make the diagnostic disappear. If assessment shows a real defect (particularly the `AppearanceObserver` one), that likely warrants its own issue rather than a drive-by fix inside this umbrella.

### 3. `weak var` → `let` — `TerminalHostStore.swift:329-330`

`viewProbe` / `tabProbe` in `verifyReferenceHygiene(view:tab:tabID:)` are `weak var` but never mutated. These are the deliberate deallocation probes added by #0289 (confirmed: `verifyReferenceHygiene` appears in #0289's Fix and Files-changed sections). The fix is mechanical (`weak let`), but must not defeat the probes' purpose — they exist precisely to observe deallocation via the weak reference going nil, and the surrounding doc comment explains why `weak` is load-bearing. Verify the probe log paths still fire after the change.

## Why these were invisible — the systemic gap

`scripts/build.sh` on an unchanged tree reports zero warnings because nothing recompiles; warnings only surface after touching the sources or on a clean build. So the pre-commit gate documented in CLAUDE.md ("Always confirm the headless `scripts/build.sh` invocation passes before committing") **cannot catch a newly introduced warning in a file the change did not touch, and can miss one even in a file it did** — a warning emitted once scrolls by, and every subsequent incremental build is silent about it.

Questions to raise with the user, deliberately not decided here:

- Should the build treat warnings as errors (`SWIFT_TREAT_WARNINGS_AS_ERRORS`), so a warning can never land silently?
- Should a periodic clean-build (or touch-all-and-rebuild) warning sweep be part of the workflow — e.g. release preflight?
- Should `scripts/build.sh` grow a mode that forces a warning sweep?

Any of these touches `Configuration/Build.xcconfig` and/or `scripts/`, both **restricted areas per CLAUDE.md** — they require the user's explicit go-ahead and must not be changed as a side effect of resolving this issue.

## Steps to reproduce

1. On a clean `main` checkout, run `scripts/build.sh` twice; the second run reports success with no warnings (nothing recompiles).
2. `touch` the five files listed above (or do a clean build) and run `scripts/build.sh` again.
3. Seven warnings are emitted alongside `BUILD SUCCEEDED`.

## Expected behavior

A full recompile of `main` emits zero warnings, and the workflow has an answer for how a newly introduced warning gets noticed before it lands.

## Actual behavior

Seven warnings across five files, some long-standing (the `BattyApp.swift:16` dead branch dates to #0237), none visible to the incremental pre-commit gate.

## Root cause

Reproduced all seven warnings exactly as cited by touching the five files and running `scripts/build.sh` before any change. They break into three independent causes:

1. **`BattyApp.swift:16`** — dead code, as the filer's history established: `WindowGroup(for:)` with `defaultValue:` yields a non-optional binding, so `windowID ?? AppStateStore.shared.initialWindowID` can never evaluate its right side.
2. **`TerminalHostStore.swift:329-330`** — mechanical: `viewProbe`/`tabProbe` are read-only within `verifyReferenceHygiene`, never reassigned, so `weak var` triggers the "never mutated" diagnostic. `weak let` is semantically identical for this use — Swift zeroes a weak reference on deallocation regardless of `var`/`let`; `let` only forbids *reassigning* the reference itself, which this function never did.
3. **Concurrency (three warnings, one real gap, two API-signature mismatches, none a functional defect):**
   - **`AppearanceObserver.swift:23`** — `NSObjectProtocol.observe(_:options:changeHandler:)` (Foundation/AppKit) is not concurrency-audited: its `changeHandler` parameter has a plain, unannotated closure type, so the compiler infers the closure literal as running in a nonisolated context regardless of the file's `MainActor`-by-default module setting. The call to the main-actor `applyGlobalThemeForCurrentAppearance()` from inside it is therefore flagged. This is **not** a functional bug: KVO delivers notifications synchronously on whatever thread mutates the observed property, and `NSApplication.effectiveAppearance` is AppKit UI state that only ever changes on the main thread (AppKit is main-thread-affine). The gap is in the API's Swift 6 annotations, not in this call site's actual behavior — confirmed by writing a test that triggers a real KVO change and observes the callback's effect land correctly (see Verification).
   - **`SplitContainerView.swift:147` (×2)** — `onGeometryChange(for:of:action:)`'s `of:` transform is declared `@escaping @Sendable (GeometryProxy) -> T` (confirmed against the SwiftUICore swiftinterface) — SwiftUI documents this closure as a pure, possibly-off-main-actor computation. The closure read `direction` via implicit `self.direction`, which captures all of `self` — including this view's generic `Left`/`Right` type parameters, whose metatypes are not `Sendable`. This *is* a real (if inert) sloppiness: the closure only needed one `Sendable` enum value and was capturing the whole generic view for it.
   - **`TerminalPlaceholderView.swift:47`** — same `@Sendable of:` closure, reading `TerminalHostInstaller.coordinateSpaceName`, a main-actor-isolated static property purely because nothing overrode the module's default isolation — the property is an immutable `String` literal with no actual dependency on the main actor.

## Fix

1. `Batty/BattyApp.swift:16` — removed the dead `?? AppStateStore.shared.initialWindowID`; `ContentView(windowID: windowID)` uses the non-optional binding directly. `initialWindowID` still reads at `:24` (`defaultValue:`), unchanged.
2. `BattyKit/Sources/BattyKit/Runtime/TerminalHostStore.swift:329-330` — `weak var` → `weak let` for `viewProbe`/`tabProbe`. The probes still nil out on deallocation exactly as before; only reassignment (never used) is now disallowed.
3. `BattyKit/Sources/BattyKit/Theme/AppearanceObserver.swift` — wrapped the call in `MainActor.assumeIsolated { self.store.applyGlobalThemeForCurrentAppearance() }`, with a doc comment explaining why the assumption holds (KVO + main-thread-affine AppKit state) and why this is not a reflexive silence: `assumeIsolated` asserts the main-actor invariant with a **runtime trap** if it's ever wrong, rather than a compile-time-only annotation (`@MainActor`) or an unchecked escape hatch (`nonisolated(unsafe)`). Added `AppearanceObserverTests.swift` — the first test for this type — driving a real `NSApp.effectiveAppearance` KVO change and asserting the resulting `themeChrome.palette` matches the new appearance's theme, which only holds if the callback reached the main actor and ran to completion.
4. `BattyKit/Sources/BattyKit/Views/SplitContainerView.swift:147` — changed the `of:` closure to `{ [direction] in direction == .horizontal ? $0.size.width : $0.size.height }`, explicitly capturing the `Sendable` `SplitDirection` value instead of implicitly capturing `self`. No behavior change — `direction` is a `let` property, so the captured value equals what `self.direction` would have read.
5. `BattyKit/Sources/BattyKit/Views/TerminalPlaceholderView.swift:72` — marked `TerminalHostInstaller.coordinateSpaceName` `nonisolated`. It is a compile-time `String` constant with no main-actor dependency; the compiler still verifies this is safe (it is — the declaration touches nothing else).
