## Description

[#0373](0373.md) plumbs the background config keys through to libghostty and stores them as `SettingsPreference` keys, but nothing in the Settings window writes them — the app-wide defaults are unreachable from the UI. This issue adds the Appearance controls that set them.

This is the **app-wide default** level of the three-level scope chain described in [#0374](0374.md): Pane override → Session override → app-wide default. A user who never sets a Pane or Session override sees these settings everywhere.

**New requirement from the user, 2026-11-03:** "In Settings under appearance there should be a slider for opacity and a text field where I can change the number as well. That will control opacity for all panes."

## Resolution notes

> 🟢 Resolved 2026-11-03 — Settings → Appearance has a Background section, behind the flag that is on in Beta and off in Prod, with an image picker, fit, position, and a slider plus a whole-percent field for each opacity, applying live to every Pane without its own override; the desktop does not show through until #0539, and the look and real key-window changes need the user's check.

Three rounds. Round 1 bounced because the requested text field was missing, every slider event re-hashed the image, and two modifiers sat on multi-view containers. Round 2 bounced for a `Section` identifier that could replace its rows' identifiers, and for a typed value that didn't apply when the window stopped being key. Round 3 approved with no code change. Round 3's conclusions, reached independently:

- **Both round 2 notes are met.** `appearance-background.section` appears nowhere in the sources or tests, and `windowDidResignKey` goes through `applyDraft`, the same function as Return.
- **Observer lifecycle is right.** It is added on `controlTextDidBeginEditing`, which precedes the first `controlTextDidChange`, so every draft has one. It is removed on end, on the deferred disable (aborted editing sends no end notification, measured in round 2), and in `deinit`. `removeObserver(self, name:, object: nil)` removes only this coordinator's registration, so a Tab between fields can't touch the other field's. `removeObserver` is thread-safe, so the nonisolated `deinit` is fine, and it compiles under `.defaultIsolation(MainActor.self)` in Swift 6 mode with no warning in changed files. A re-render doesn't touch the observer, because `render` and `setEnabled` don't call it, and SwiftUI keeps a field and its coordinator together. If the field goes away without an end notification, `editedField` is weak and the handler returns.
- **The handler's origin is safe.** It writes observed state from an AppKit key-window change, so I traced who changes the key window. Every `makeKeyAndOrderFront`, `performClose` and `close` in `BattyKit/Sources` and `Batty` is event-origin: menu and key handling, XPC, feed clicks (`activateWindow`'s comment lists its callers, and `jumpToBellEntry`'s comment agrees). The window machinery isn't inside a layout pass there. The sheet's own dismissal, which does run from a SwiftUI update, can't reach the handler: Done and Cancel end editing first, which removes the observer. The one remaining path is in `## Gotchas`: a file importer opened with a draft. The writes on the path call no responder or constraint API (audit in `## Fix`), and `editor.string` and `selectAll` only change the field editor's text and selection, in a window whose first responder doesn't change.
- **Cancel is safe.** `editor.cancel()` sets `originalOverride` unconditionally, after `commitTypedOpacity`, so a draft committed on resign is undone. Settings has no Cancel.
- **Switching apps mid-typing applies the half-typed value.** That's acceptable: it is visible, one action corrects it, and the text is selected so the next keystroke replaces it. Recorded in `## Gotchas`.
- **`observedWindow` is a read-only seam.** Production writes it and never reads it, and removal doesn't use it, so it changes no behaviour.
- **The tests aren't vacuous.** The notification is posted, but `type` drives a real field editor, so the observer comes from a real `controlTextDidBeginEditing`, and `theWindowIsObservedOnlyWhileEditing` shows it. Without the observer, `draftCommitsOnceWhenTheWindowResignsKeyAndEditingContinues` and the redisplay cases would fail. `anotherWindowResigningKeyCommitsNothing` holds a live draft, so it pins the `object:` filter. `aResignAfterFocusLossCommitsNothing` would pass on `hasDraft` alone, but the observed-window test covers removal. The deferred disable's block still has no unit test, and the reasoning above stands in for one.
- **What isn't proven:** that a real close or click sends the notification with the editor attached. I didn't measure it, because that needs a window on the user's screen taking key. It is on the User checklist.

No carved-out scope needs its own issue. #0538 and #0539 already exist.

## Root cause

Feature work. #0373 stored the app-wide keys and #0374 added the Pane sheet, but nothing in Settings wrote the keys. Also, `TabRuntime` and `applyAppearanceToAllSurfaces` read those keys with no flag check, so on a Prod build of `main` a hand-written path reached libghostty. That is confirmed by reading the code, not by running Prod.

## Fix

- **Storage:** a path to a Batty-owned copy in `~/Library/Application Support/<variant>/TerminalBackgrounds/<SHA-256 of the copy>/<name>.png`. No bookmark, because Batty is unsandboxed and libghostty never sees the user's file.
- **Gate:** `AppWideBackgroundGate` is now the only route from the persisted keys to a builder. A path reaches libghostty only if it has the exact shape above and the file's hash matches its folder. With the flag off, it returns `.off` before reading `UserDefaults` or the disk, so a flag-off build emits no background lines.
- **Live apply:** `applyAppWideBackgroundToAllSurfaces` uses each Tab's own builder and skips Panes with an override. It does not use `applyAppearanceToAllSurfaces`, so #0538 doesn't spread to every slider step. #0538 is not fixed here.
- **Settings:** a Background section in Appearance, using `TerminalBackgroundControls`, shared with the Pane sheet. Restore Defaults removes every key.
- **`background-opacity-cells`:** an opt-in toggle, off by default. `minimum-contrast` is deliberately not exposed, because it doesn't sample the image (source, per the plan).
- **First-image tint:** 0.15 instead of 0.35.
- **#0374's defects:** Done is disabled during an import, Pane copies live in a pid folder so a second running copy keeps its images, and the sliders have accessibility labels.
- **Non-numeric opacity:** a stored non-number now falls back to the default instead of `0`.

## Gotchas

- **Not covered by the gate, deliberately:** someone who places a file in the directory under a folder named for its own SHA-256 is outside this guard, and such a file could abort the app. So is a file swapped between the check and the surface's read. Both need deliberate action in Application Support and can't arise from a stale setting or a hand-edited key.
- **Damage after the check isn't caught until the next inspection.** The memo holds `.usable` for the session, so a file damaged after its check reaches every new Tab until the next launch, or until Settings re-inspects it. That's kept: it is rare and a launch recovers.
- **A Pane can lose a seeded image.** The plan says an old image stays until the next launch's first pick. If the user seeds a Pane, presses None or Restore Defaults, then makes the launch's first pick, `retaining` is `nil` and the seeded file is deleted. A missing path is benign (#0373), so that Pane's later Tabs just have no image.
- **An import outlives its view.** If Settings closes or switches tabs during an import, the import still applies, but a Settings view reopened before it finishes shows the old value until it next appears.
- **Clicking empty space or a slider doesn't end editing.** AppKit doesn't move focus for those. A typed value applies on Return, Tab, a click into another field, or when the field's window stops being key: clicking a terminal or closing Settings applies it. So does switching to another app, which also makes the window resign key. The Pane sheet's buttons commit it too. A slider move replaces a draft, as the later intent.
- **Real key-window changes haven't been seen.** The tests post `didResignKeyNotification`, because a window never shown can't become key. That closing the window and clicking another window send it while the field editor is still attached is assumed, not measured. The User checklist covers both.
- **Switching apps mid-typing applies what's there.** Type 3 on the way to 37, then switch away, and 3% applies to every following Pane until corrected. The text is selected, so typing 37 on return replaces it. The same goes for anything that takes key from the window, such as Spotlight.
- **Choose… with a draft commits it, possibly inside a view update.** Clicking Choose… doesn't end editing, so the open panel taking key is what applies the draft. If SwiftUI presents the panel inside a view update, the `@State` write in Settings could raise "Modifying state during view update". The key write and config push still happen and nothing on that path calls a responder or constraint API, so the cost is a console warning. Not observed.

### Decisions

**Storage: a path to a Batty-owned copy.** Neither the user's path nor a bookmark. Batty is unsandboxed, so a bookmark adds nothing, and libghostty never sees the user's file, so moving or deleting the original changes nothing.

**Where the copy lives.** `~/Library/Application Support/<SessionNameCache.resolvedDirectoryName()>/TerminalBackgrounds/`, per variant, because Caches can be purged and this is a setting. Pane imports stay in Caches. A Pane that seeded from the app-wide value points into Application Support, which is fine.

**The importer's cleanup changes as follows.**

- Two importer instances with different rules, chosen by an init parameter `cleanup`. Both still run it once, on the actor's first import.
- **App-wide, `.allButRetained`:** remove every folder in the directory except the one holding `retaining`, which is the path in `UserDefaults` at that moment. Nothing runs at launch, so nothing is touched until the user picks an image. An old image stays on disk until the next launch's first pick, so a Pane that seeded from it this launch keeps working.
- **Pane, `.deadProcessFolders`:** the directory becomes `<Caches>/<bundle id>/TerminalBackgrounds/<pid>/`. The first import removes sibling folders whose name is not the pid of a live process (`kill(pid, 0)`, injected as `isProcessAlive` for tests), which also removes #0374's old digest folders. **This fixes #0374's second-copy defect:** another running copy's folder has a live pid. A reused pid only delays cleaning a folder.

**Startup safety: every persisted path goes through one gate, and the file must prove it is the importer's output.**

- **The copy's folder is the SHA-256 of the copy's own bytes:** `<directory>/<64 hex>/<name>.png`. Today it's the digest of the *source*. That makes the path self-certifying, with no second key to keep in step.
- **`AppWideBackgroundGate`** is the only route from the persisted keys to a builder. It is `.usable` only if the path is exactly `<directory>/<64 lowercase hex>/<name>.png` by component comparison, with no standardizing, so `..` fails, and the file's SHA-256 equals the folder name.
- This covers every case without trying to out-guess libghostty's decoder:

  | Persisted state | Gate | Tab | Settings shows |
  |---|---|---|---|
  | No key | `.none` | No image | "None" |
  | Copy intact | `.usable` | Image | Its name |
  | Copy deleted or purged | `.missing` | Shell, no image | "Image not found. Choose it again." |
  | Bit flip, truncation, any file swapped in, including one over 16384 px | `.rejected` | Shell, no image | "The saved image can't be used. Choose it again." |
  | Hand-edited path to anywhere else | `.rejected` | Shell, no image | Same |
  | Hand-edited array, number or junk string in any key | Falls back | Shell, defaults | Defaults |

- The Tab keeps its terminal opacity and every other override. `background-image*` lines are simply absent. The gate logs `.error` with the path `.private`. The key stays until the user acts, and picking again repairs it. **The worst outcome is a Tab with no picture.**
- **Not covered, deliberately:** someone who places a file in that directory under a folder named for its own SHA-256 is outside this guard, and could abort the app. So is a file replaced between the check and the surface's read. Both need deliberate action in Application Support and can't arise from a stale setting, a hand-edited key or disk damage to a checked file. `## Gotchas` must say this.

**File I/O and the builders.** The `TerminalConfiguration` closures do none. The gate memoizes one `(path, state)`, so reading is `UserDefaults` plus a comparison. It reads and hashes the file only when the path differs from the memo: once per launch at the first Tab, once per pick, and when Settings appears (`refreshImageState`). That hash runs synchronously on the main actor, **14 ms measured for a 43.8 MB file**. I chose that over an asynchronous check because the first Tab needs the answer before its surface spawns, and a late push would show the image popping in and need a second write path. **Pane overrides aren't checked:** they aren't persisted and come from the importer in this process, or from the gate's own output.

**Flag off: Prod reads nothing.** `AppWideBackgroundGate.live` is built from `FeatureFlags.resolved()`. Disabled, `settings()` returns `.off` before touching `UserDefaults`, so both builders emit what they emit today. The Settings section is absent, and its state lives in a subview that isn't constructed. Same flag, `terminalBackgrounds`.

**Live push: a new path, and no `applyAppearanceToAllSurfaces`.** `AppStateStore.applyAppWideBackgroundToAllSurfaces()` walks windows → Sessions → terminal Panes, **skips any Pane with `backgroundOverride != nil`**, and re-renders each Tab through its own builder with the new value. So per-Tab lines survive, overrides keep theirs, and `setTerminalConfiguration`'s equality guard skips Tabs with no change. The Theme is a separate channel in both directions, and tests pin that. A Tab degraded by #0538 regains its lines as a side effect, as with #0374's fan-out; that isn't the fix, and #0538 stays open.

**Observation audit.** Every write starts from a control binding, a button or the importer's result. **No `onChange` and no `@AppStorage` in the section.** It writes through an editor, as the Pane sheet does. Its `@State` holds a copy of the stored value, refreshed from `onAppear` and after each edit; that local state feeds no AppKit call. `setTerminalConfiguration` touches neither the responder nor layout (#0374's audit), so nothing writes back. The gate isn't `@Observable`, so its memo write during a read invalidates nothing.

**`background-opacity-cells`: a separate toggle, off by default.** Coupling it to the slider would fix "does nothing in vim", but it also fades explicit cell backgrounds. At low opacity that breaks text whose foreground relies on its own background, such as a tmux status bar with `fg=black,bg=green` on a dark Theme. Selected and inverse cells stay opaque either way (source, `generic.zig:3066-3070`). So: `opacityAffectsCells: Bool = false` on `TerminalBackgroundSettings`, and a toggle, "Include programs that paint their own background". Emitted only when the toggle is on **and** terminal opacity is below 1, so off still emits nothing. It appears in the Pane sheet too, through the shared controls, because overrides are all-or-nothing.

## Storage: path or security-scoped bookmark

**Decide and record which, explicitly.** Batty is unsandboxed (`ENABLE_APP_SANDBOX = NO`, see `CLAUDE.md`), so a plain absolute path is very likely sufficient and a security-scoped bookmark is unnecessary ceremony. That is the recommendation — but state it in the resolution notes rather than leaving it implied, because "we stored a path" and "we stored a bookmark" are indistinguishable from the outside until the first user moves the file.

libghostty is handed a path string in the config either way, so a bookmark would have to be resolved to a path before emission.

## Handle a missing or unreadable image deliberately

**The sharpest failure mode in this feature.** If the stored path no longer resolves — the file was moved, deleted, or lives on an unmounted volume — the config containing `background-image = /gone.png` may fail libghostty's diagnostics. `prepareConfig` fails closed, which means the *entire* override set is dropped: font size, cursor style, every `keybind`, every `env`. The user moves one image file and their Cmd-key bindings stop working.

So: **before emitting `background-image`, check the path resolves and is readable. If it does not, emit no `background-image` line at all** and let everything else through. Log it (`Logger`, per `CLAUDE.md` — not `print`). Consider surfacing it in the Settings UI as a "image not found" state next to the picker rather than failing silently, since a background that quietly stops appearing is a confusing bug report.

[#0373](0373.md) is tasked with establishing whether a bad path actually does fail the config under the pinned ref. Read its answer; the guard is worth having either way, but the severity depends on it.

**Answered in [#0373](0373.md), and it changes this guard:** a missing path is benign (no diagnostic, no image, other overrides survive). The case that needs guarding is a file that claims to be PNG/JPEG but doesn't decode: `ghostty_surface_new` returns `NULL`, leaving a Pane with no shell on every new Tab. Also from #0373's plan: images over the Metal texture limit are not measured and may fail every frame, so test them here, and upstream keeps one image copy in VRAM per terminal, so memory scales with Tab count.

## Notes

- **`background-opacity` affects default-background cells only.** A TUI painting its own colored cells (vim, htop) stays opaque unless `background-opacity-cells` is also set. Decide whether this UI exposes `background-opacity-cells` as its own control, couples it to the opacity slider, or leaves it alone — and say which. Users will otherwise report "the opacity slider does nothing" from inside vim.
- **Legibility.** `minimum-contrast` is available via `Builder.withMinimumContrast` (`TerminalConfiguration.swift:190` in the SPM checkout). It is the mechanism for keeping text readable over a busy photo. Expose it, apply it implicitly when an image is set, or explicitly decide not to — but the default settings must not be able to produce unreadable output.
- **The themed window background still paints behind everything.** `SessionDetailView.swift:217-220` paints `themeChrome?.windowBackground` behind the terminal host and into the transparent title bar. Semitransparent surfaces composite over *that*, not over the desktop, and the window padding around the surfaces will stay opaque, making an image look inset. See [#0374](0374.md)'s note — whichever issue lands first should resolve or explicitly ticket this.
- **Verification.** The preference writes and the resulting `renderedConfig` are unit-testable via the technique [#0373](0373.md) establishes, including the missing-file guard (point the preference at a nonexistent path, assert no `background-image` line *and* that the other overrides survive). The Settings UI itself and the rendered result are not; mark `resolved`, not `closed`, and note in `## Gotchas` what could not be verified.

## From #0374

- **Use `TerminalBackgroundImageImporter`.** The picker must store the path it returns, never the user's file. Measured against the pinned `libghostty.a`: a PNG or JPEG wider than 16384 px aborts the whole process, on a live surface too, and a bit-flipped or truncated file passes ImageIO but makes `ghostty_surface_new` return `NULL`. This replaces the "not measured" note on oversize images.
- **Cleanup caveat.** The importer deletes its directory on its first import of each launch, because Pane overrides aren't persisted. A persisted app-wide path would be deleted too, so this issue must change that behavior or store the copy elsewhere.
