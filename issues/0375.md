## Description

[#0373](0373.md) plumbs the background config keys through to libghostty and stores them as `SettingsPreference` keys, but nothing in the Settings window writes them — the app-wide defaults are unreachable from the UI. This issue adds the Appearance controls that set them.

This is the **app-wide default** level of the three-level scope chain described in [#0374](0374.md): Pane override → Session override → app-wide default. A user who never sets a Pane or Session override sees these settings everywhere.

## What to build

Controls in Settings → Appearance, alongside the existing font-size and cursor controls that `SettingsPreference.applyAppearanceToAllSurfaces()` already serves:

- **Image picker** — `NSOpenPanel`, restricted to the formats [#0373](0373.md) confirmed load under the pinned libghostty. Do not guess the format list; a picker that accepts a file libghostty then silently ignores is worse than no picker.
- **Fit** — `contain` / `cover` / `stretch` / `none` (`background-image-fit`).
- **Position** — `background-image-position` (`center`, `top-left`, `bottom-right`, …). Enumerate the accepted values from the pinned binary rather than inventing a list.
- **Image opacity** — `background-image-opacity`, so the image can be dialled down to a tint.
- **Terminal background opacity** — `background-opacity`.
- **A "None" / clear affordance** that restores the default-off state: no image, opacity back to fully opaque, and — critically — makes [#0373](0373.md)'s builders emit nothing at all, not `background-opacity = 1`.

**Live-apply through `applyAppearanceToAllSurfaces()`** (`BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift:170-198`). It already exists, already rebuilds the configuration, and already walks every window → session → terminal Pane → Tab (`:190-198`), skipping non-terminal Panes. Once [#0373](0373.md) has taught its builder to emit the background keys, this UI just has to write the preferences and call it.

## Storage: path or security-scoped bookmark

**Decide and record which, explicitly.** Batty is unsandboxed (`ENABLE_APP_SANDBOX = NO`, see `CLAUDE.md`), so a plain absolute path is very likely sufficient and a security-scoped bookmark is unnecessary ceremony. That is the recommendation — but state it in the resolution notes rather than leaving it implied, because "we stored a path" and "we stored a bookmark" are indistinguishable from the outside until the first user moves the file.

libghostty is handed a path string in the config either way, so a bookmark would have to be resolved to a path before emission.

## Handle a missing or unreadable image deliberately

**The sharpest failure mode in this feature.** If the stored path no longer resolves — the file was moved, deleted, or lives on an unmounted volume — the config containing `background-image = /gone.png` may fail libghostty's diagnostics. `prepareConfig` fails closed, which means the *entire* override set is dropped: font size, cursor style, every `keybind`, every `env`. The user moves one image file and their Cmd-key bindings stop working.

So: **before emitting `background-image`, check the path resolves and is readable. If it does not, emit no `background-image` line at all** and let everything else through. Log it (`Logger`, per `CLAUDE.md` — not `print`). Consider surfacing it in the Settings UI as a "image not found" state next to the picker rather than failing silently, since a background that quietly stops appearing is a confusing bug report.

[#0373](0373.md) is tasked with establishing whether a bad path actually does fail the config under the pinned ref. Read its answer; the guard is worth having either way, but the severity depends on it.

## Notes

- **`background-opacity` affects default-background cells only.** A TUI painting its own colored cells (vim, htop) stays opaque unless `background-opacity-cells` is also set. Decide whether this UI exposes `background-opacity-cells` as its own control, couples it to the opacity slider, or leaves it alone — and say which. Users will otherwise report "the opacity slider does nothing" from inside vim.
- **Legibility.** `minimum-contrast` is available via `Builder.withMinimumContrast` (`TerminalConfiguration.swift:190` in the SPM checkout). It is the mechanism for keeping text readable over a busy photo. Expose it, apply it implicitly when an image is set, or explicitly decide not to — but the default settings must not be able to produce unreadable output.
- **The themed window background still paints behind everything.** `SessionDetailView.swift:217-220` paints `themeChrome?.windowBackground` behind the terminal host and into the transparent title bar. Semitransparent surfaces composite over *that*, not over the desktop, and the window padding around the surfaces will stay opaque, making an image look inset. See [#0374](0374.md)'s note — whichever issue lands first should resolve or explicitly ticket this.
- **Verification.** The preference writes and the resulting `renderedConfig` are unit-testable via the technique [#0373](0373.md) establishes, including the missing-file guard (point the preference at a nonexistent path, assert no `background-image` line *and* that the other overrides survive). The Settings UI itself and the rendered result are not; mark `resolved`, not `closed`, and note in `## Gotchas` what could not be verified.
