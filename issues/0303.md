## Description

Before any non-terminal view kind ships (#0304 Git Status, #0305 Process Status), it needs a **lifecycle contract**: proper setup and teardown, plus a show/hide state change, so that hidden views stop costing compute and closed views release memory. The user's stated goal is reducing computer and memory costs — this issue defines the system that enforces it, so each concrete view doesn't invent (or skip) its own discipline.

The requirement: **any new view kind must declare how it stops work when hidden and how it releases resources when closed — and both must be observable** (log evidence, a counter, a footprint delta — something a test or an investigation can check), not asserted.

## Resolution notes

> 🟢 Resolved 2026-08-08 — `docs/pane-view-lifecycle.md` defines the contract, `PaneContentLifecycle` in BattyKit makes it a real protocol with a state machine, and 25 new tests make it executable rather than aspirational.

The contract ships ahead of any conformer, as intended: no non-terminal view kind exists yet, so nothing is wired into `PaneView` or the terminal render path and no manual pane checklist is owed. #0304 lands the pane-kind field and the first conformer together and pays that cost once.

## Root cause

Starting state, not a defect. #0288 and #0289 established terminal-side occlusion and deterministic teardown the expensive way, under the #0285 resource-growth umbrella — after a footprint reached 8.4 GB. Non-terminal view kinds had no equivalent discipline to adopt, so each would have invented or skipped its own.

## Fix

Three pieces:

- **`docs/pane-view-lifecycle.md`** — the contract. A four-phase state machine (`notSetUp → active/suspended → tornDown`), the three visibility facts that drive it (non-selected Session, inactive Tab, hidden Pane) cited to where they are computed today, what a suspended view is allowed to cost (zero), what teardown must guarantee, and an explicit section on what the tests do and do not prove.
- **`BattyKit/Sources/BattyKit/Runtime/PaneContentLifecycle.swift`** — `PaneLifecyclePhase`, `PaneLifecycleEvent`, `PaneLifecycleTransitionResult`, a pure value-type `PaneLifecycleStateMachine`, the `PaneContentLifecycle` protocol (`setUp(visible:)` / `setVisible(_:)` / `tearDown()` / `lifecyclePhase`), and `PaneLifecycleController`.
- **`BattyKit/Tests/BattyKitTests/PaneContentLifecycleTests.swift`** — transition coverage plus a `RecordingPaneContent` double with a `WatcherLedger` that proves release deterministically: a plain counter read on the next statement after `tearDown()` returns, with no `await`, no `Task`, no run-loop spin.

Conformer ownership is settled as **model-owned, hung off `PaneRuntime`** (parallel to `TabRuntime.terminal`), because `WindowRuntime.closePane` needs direct reachability and a view-owned conformer would reproduce the SwiftUI-churn bug class `docs/view-hierarchy.md` §3 exists to prevent.

## Gotchas

- **`TerminalHostStore.updatePlacements(_:forWindowID:)` is dead code.** Its only callers are `BattyKitTests`, and `TerminalHostInstaller`'s comment claiming a `TerminalPlacementPreferenceKey` drives it refers to a key #0141 deleted. Anything reasoning about how a hidden pane's terminal gets turned off must look at `WindowRuntime.hidePane`'s explicit per-tab `setPlacement` loop instead. This mis-citation cost a full review round here and was #0256's round-1 blocker before that.
- **`hidePane` and `showPane` are not symmetric.** `hidePane` flips `isHidden` *and* drives `setPlacement(isVisible: false)` per tab. `showPane` only flips `isHidden` and returns — the un-hide is delivered by the remounted placeholder's `onGeometryChange`. Wiring a conformer's `setVisible(true)` into `showPane` is therefore new behavior for that function, not a mirror of something already there.
- **SwiftUI unmount is not a delivery mechanism.** `onDisappear` and `deinit` are both ruled out by the contract's synchronicity rule; a conformer that relied on them would sit `.active` with its watcher running after `hidePane`, reproducing #0288 one layer up.
- **The non-selected-Session visibility fact has no model-level function to hook into yet.** The hidden-Pane and inactive-Tab facts do. Whichever child needs it will have to add one.

## Why design this in from the start

Terminal Sessions already went through this the hard way, under the #0285 resource-growth umbrella. Two resolved children are the precedents this lifecycle should generalise:

- **#0288 — occlusion signalling.** Non-visible Terminal Sessions used to keep rendering on every PTY wakeup; #0288 wired visibility so they stop, with a Batty-side ticker keeping bells, titles, and child-exit events flowing. That is exactly the show/hide half of this lifecycle. Notably, #0288's investigation found the libghostty C API offered **no way to release a surface's GPU resources short of destroying the surface and its PTY** (tracked upstream as #0293) — terminal views were boxed in by an external API. A non-terminal view is plain SwiftUI plus Batty-owned watchers/timers: it has **complete freedom** to suspend and release, which is precisely the argument for demanding a real lifecycle from day one instead of accepting "it's hidden, it's probably fine".
- **#0289 — deterministic teardown.** `releaseTerminalView(forTabID:)` logged "released" while the actual free waited on ARC; #0289 made surface teardown synchronous at close time. The lesson to carry into this contract verbatim: **a log line claiming teardown is not evidence teardown happened.** The lifecycle's "released on close" claim must be verifiable against the process (footprint sample, deallocation hook, live-object count), not against the log.

#0285 as a whole is the cautionary context: resource discipline retrofitted after a footprint reaches 8.4 GB costs an umbrella's worth of issues. New view kinds start with the discipline built in.

## Expected behavior

A lifecycle definition (protocol or equivalent, plus the state transitions) that every non-terminal view kind adopts, covering:

1. **Setup** — when the view's backing work (watchers, pollers, subprocesses) starts; a view that is created hidden must not start work it would immediately suspend.
2. **Show/hide** — driven by the same visibility facts that drive terminal occlusion (Pane in a non-selected Session, inactive Tab, hidden Pane): hidden views suspend watchers/timers and do zero periodic work; showing resumes and refreshes.
3. **Teardown** — synchronous and deterministic on close, releasing watchers, caches, and subprocesses; not ARC-timed.
4. **Observability** — a way to verify (not just log) that a hidden view is idle and a closed view released its resources.

This issue can deliver the contract together with #0302's abstraction proposal; it ships ahead of both concrete views so #0304 and #0305 implement against it.
