# 0346 — Remote-backed Sessions in the Sidebar: connection state, attach, detach, reconnect

| | |
|---|---|
| **Status** | open |
| **Module** | Sidebar / Session |
| **Platform** | macOS |
| **First seen** | 2026-08-21 |

## Description

Make a remote-backed Session a first-class thing the user can see and
operate: a Session row in the Sidebar that shows where it is running
and whether it is connected, with explicit attach and detach, and
sane handling when the connection drops and comes back.

Up to [#0345](0345.md) the remote plumbing exists but has no home in
the UI. This issue gives it one. It is the difference between "the
protocol works" and "the user can use this."

The architecture, the size-clamp problem, and the handoff question
live in [#0341](0341.md) and are not restated here.

**Not scheduled work.** Inherits #0341's status: staged for a future
major release, not queued.

### Blocked on a decision, not just on code

This issue cannot be designed until #0341's **Open question 1 —
handoff versus simultaneous attach** — is answered by the user,
because the two produce different UX:

- **Handoff (proposed default).** The Mac mini detaches when the
  MacBook attaches. One client at a time, so the tmux size clamp
  never binds and each Mac renders at its own full geometry. The UI is
  about *taking* and *releasing* control, and it matches the user's
  own framing of giving control of the terminal to the remote Mac.
- **Simultaneous.** Both Macs stay attached and both render, clamped
  to the smaller client's geometry. The UI then has to *explain the
  letterboxing*, because it is inherent to shared multiplexing and
  cannot be engineered away — and an unexplained clamped Session
  reads as a bug.

## Expected behavior

1. **Creating a remote-backed Session.** The user names a host and a
   tmux session and gets a Session in the Sidebar. Existing remote
   sessions on that host are discoverable rather than typed from
   memory.
2. **Connection state is visible in the Sidebar row** — connected,
   connecting, reconnecting, disconnected, failed — without the user
   having to click into the Session. A Session whose remote is gone
   must never look identical to a healthy one.
3. **Attach and detach are explicit user actions**, reachable from the
   Sidebar row's context menu alongside the existing Rename /
   Duplicate / Set Color / Close items.
4. **Detach is not close.** Detaching leaves the remote tmux session
   running; closing the Batty Session likewise defaults to leaving it
   running. Killing the remote session, if offered at all, is a
   separate, clearly-labeled, confirmed action.
5. **Reconnect after a drop.** A dropped connection retries with
   backoff, and on success the Session comes back with its Panes and
   layout intact rather than as a fresh empty Session. Retrying
   forever in silence is not acceptable; the user can see it is
   retrying and can stop it.
6. **Failures are diagnosable.** Host unreachable, authentication
   failed, tmux missing on the remote, tmux session gone — each
   produces a distinguishable message, not a generic failure.
7. **Local Sessions are untouched.** A user who never uses this
   feature sees no change: no new required setup, no new Sidebar
   chrome on local Sessions, no slower launch.

## Acceptance criteria

1. A remote-backed Session appears in the Sidebar with a visible
   indication that it is remote and which host it is on, and remains
   visually distinguishable from a local Session at a glance.
2. Connection state is rendered in the Sidebar row and updates live
   through at least: connecting, connected, dropped, reconnecting,
   reconnected.
3. Attach and detach work from the Sidebar row's context menu, and
   detach demonstrably leaves the remote tmux session alive
   (`tmux ls` on the remote).
4. Pulling the network mid-session shows the disconnected state within
   a bounded, stated time, and restoring it reconnects with the Panes
   and layout intact — verified end to end, not simulated.
5. The **handoff-versus-simultaneous decision is recorded in the
   issue** with the user's answer, and the shipped behavior matches
   it. If simultaneous is chosen, the size clamp is explained in the
   UI where the user will encounter it.
6. `scripts/build.sh unit` passes with new `BattyKitTests` covering
   the connection state machine as a pure state machine: every
   transition, the backoff schedule, retry cancellation, and the
   distinct failure classifications. No network in the unit suite.
7. New UI is covered by `BattyUITests` and the suite is run on the Mac
   mini via `scripts/run-ui-tests.sh` (not raw `xcodebuild test`).
   Per `CLAUDE.md`, new UI features get new UI tests.
8. Every write to observed state driven by a connection event has a
   named owner outside view construction, and no `Task` hop was used
   to dodge a mutate-during-update warning.
   `docs/swiftui-observation-rules.md` is binding; connection-state
   changes are event-origin flips and are routine *when owned
   properly*.

## Notes

- Credentials stay in the user's existing SSH configuration. Do not
  introduce a Batty-managed credential store here; #0343 makes the
  same point for the same reason.
- Session color and title: a remote-backed Session still gets a
  `SessionColor` and a title. Whether the title follows the tmux
  session name, and whether the name cache
  (`session-name-cache.json`, keyed by working directory) applies at
  all to a remote Session, both need answers — the cache's key is a
  *local* path.
- Batty persists nothing today (`Concepts.md`: Sessions, Panes, Tabs,
  and Terminal Sessions are all in-memory only). A remote-backed
  Session is the first thing in Batty with state genuinely worth
  restoring across a relaunch, since the remote survives. Do not
  build persistence here — but note that this issue is where the
  argument for it starts, and #0172 removed the previous
  `workspace.json` machinery.
- Discovery of existing sessions on a host is `tmux ls` over the same
  channel #0343 built; it does not need a second transport.
