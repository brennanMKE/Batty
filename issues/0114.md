## Description

Tier 2 localization target. South Korea has a strong tech ecosystem and a meaningful macOS developer population. Batty's existing CJK IME work serves Korean Hangul input on the terminal side; localizing the UI completes the experience.

Depends on `#0107`.

## Acceptance criteria

- Every key in `Localizable.xcstrings` has a non-empty `ko` translation, reviewed by a native speaker.
- Launching with macOS Language & Region set to 한국어 shows the full UI translated.
- Visual sweep confirms Hangul renders cleanly in Settings labels, menu items, and alerts.
- `## Files changed` should list the `.xcstrings` diff.

## Notes

- Hangul tends to be slightly more compact than English horizontally — clipping risk is lower than in German or French, but verify anyway.
- Product name "Batty" stays in Latin script.
- Bell feed timestamps render in Korean format via the system locale automatically.
- Sparkle ships Korean strings.

## Root cause

`Localizable.xcstrings` had no `ko` translations after the localization
foundation (`#0107`) landed. Users running macOS with Language & Region
set to 한국어 would fall back to English for every catalog-driven string
in the app shell (quit-confirmation alert, paste-confirmation sheet,
sidebar bell-count tooltip).

## Fix

Populated every key in `Batty/Localizable.xcstrings` with Korean (`ko`)
translations. Strings follow Apple's Korean macOS UI register:
noun-phrase buttons (종료 / 취소) rather than verbal forms, and the
"-(으)ㄹ까요?" interrogative for confirmation alerts. Plural variations
carry identical `one` and `other` values because Korean has no
grammatical plural; counter words (줄 for lines, 개 for terminals, 건
for events) take the role plural inflection plays in English. The
`Batty` brand stays in Latin script.

## Files changed

- `Batty/Localizable.xcstrings` — added `ko` entries for all 7 keys
  (Batty, Paste %lld lines?, There %lld open terminal(s).,
  %lld unseen bell event(s), Quit Batty?, Quit, Cancel).

## Gotchas

- Translations are LLM-authored, not native-speaker reviewed; a Korean
  pass before release is still advisable per the issue's acceptance
  criteria.
- **Korean lacks grammatical plural**, so `one` and `other` variants are
  intentionally identical. The number itself plus a native counter word
  (수 분류사 / counter) carries the quantity. Chosen counters: **줄**
  for visible terminal lines (the standard counter for rows/lines of
  text — `1줄`, `100줄`), **개** as the generic counter for terminal
  instances (more natural here than 대 / 건 — `터미널 1개`, `터미널
  10개`), and **건** for bell *events/incidents* (the conventional
  counter for notification-like occurrences — `이벤트 1건`, `이벤트
  10건`). Korean does not insert a space between numeral and counter
  in modern Apple UI usage, so `%lld줄` / `%lld개` / `%lld건` are
  written without an intervening space.
- Used the polite-question ending **"-(으)ㄹ까요?"** for both
  confirmation prompts (`종료할까요?`, `붙여넣을까요?`) rather than
  the more formal `-시겠습니까?` — Apple's macOS Korean confirmation
  dialogs (e.g. Terminal.app's quit prompt, Finder's empty-trash
  prompt) use the lighter `-까요?` form, and matching it keeps Batty
  consistent with system idiom.
- Apple Korean macOS uses **noun-phrase buttons** rather than verbal
  forms: `종료` not `종료하다` or `종료합니다`; `취소` not `취소하다`.
  The catalog follows that convention.
- "Batty" stays in Latin script — *not* transliterated to 배티. Apple
  consistently keeps Latin product names un-transliterated in Korean UI
  (Safari, Mail, Xcode are all written in Latin in 한국어 menus), so
  the brand survives every alert as-is.
- Hangul rendering: South Korean default macOS font (Apple SD
  Gothic Neo) covers all catalog characters; no font-availability
  concerns. Hangul is more compact than English horizontally — alert
  buttons and tooltips should not need layout tweaks.
- Catalog-only change; no Swift source touched. `project.pbxproj`
  `knownRegions` does not need to enumerate `ko` — Xcode 15+ String
  Catalogs are self-describing and read locale columns directly.
