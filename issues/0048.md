# 0048 — Tab chip titles don't truncate, so the "+" button and inactive tabs are pushed out of narrow panes

| | |
|---|---|
| **Status** | open |
| **Module** | Tabs |
| **Platform** | macOS |
| **First seen** | 2026-05-11 |

## Description

Tab chips render at their natural text width — long titles like `brennan@macbook-air-m4-brennan-2:~` (the default shell title) consume the full chip width with no truncation. When a pane is narrower than the sum of its tabs at full width, the chips overflow and the trailing affordances (the "+" button, the rightmost tab chip) get pushed off the visible row.

In the attached screenshot the bottom-right pane is split to roughly half the window width. Its two tabs at their natural widths exceed that available width; the active (rightmost) chip is truncated against the window edge, and that pane's "+" button isn't visible at all. The user has no way to add a tab to that pane without resizing the split.

## Steps to reproduce

1. Open a window with two side-by-side panes (horizontal split).
2. In the smaller pane, add a second tab (`Cmd-T`).
3. Observe: the chip widths consume the full pane width; the "+" button is no longer visible; the active chip is clipped at the right edge.

## Expected behavior

Tab chip widths adapt to the available row width so every tab plus the "+" affordance remain visible. Options (any/all may be acceptable):

- Truncate chip titles with an ellipsis when the chip can't render at full width.
- Establish a minimum per-chip width (e.g. ~80pt of title space) below which the bar scrolls horizontally with an indicator.
- Always reserve space for the "+" button at the trailing edge so it never disappears.

## Actual behavior

- Each chip renders at the title's natural width.
- The "+" button is hidden when chips collectively exceed the pane width.
- The trailing chip is clipped by the pane's right edge.

## Notes

- This is the root cause of which `#0047` (tab bar leaking into adjacent pane) is the visual symptom. Fixing one without the other leaves the user worse off: clipping without truncation hides accessible tabs; truncation without clipping still risks leaking content.
- The shell default title (`user@host:cwd`) is long but typical — Batty shouldn't assume short titles. The cwd-basename fallback from `#0016` produces shorter titles when shell-integration is active, but the OSC 0/1/2 path commonly sets the long form.
- Implementation hint: `SlidingTabBar` is the third-party SwiftUI component from the `SlidingTabs` package. Truncation policy probably lives inside that package; check whether it exposes a sizing/truncation knob before reaching for a fork.
- Related: `#0046` (close-the-last-tab cascade). With both fixes in, narrow panes become tractable to manage.
