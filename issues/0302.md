# 0302 — Every layer of the Pane path presumes a Terminal Session; explore a pane-kind abstraction that supports any view type without regressing terminals

## Description

Batty cannot represent a Pane whose content is not a Terminal Session — the assumption is baked in at every layer of the model and view path. Before any concrete non-terminal view (#0304 Git Status, #0305 Process Status) can exist, a **pane kind** abstraction has to be designed. The deliverable of this issue is an **exploration and a written proposal**, not a finished refactor: where *kind* lives, how the view layer branches on it, how the terminal-host boundary is drawn, and how the Codable model carries it — with explicit evidence that terminal panes lose nothing.

**"Prevent regressions" is the operative constraint.** `docs/view-hierarchy.md`, `docs/terminal-pane-requirements.md`, and `docs/swiftui-observation-rules.md` are binding for any change on this path, and the manual pane checklist (pointer input, keyboard, file drop, text drop, IME) must still pass on terminal panes after any spike or restructuring. #0143 is the recorded example of what breaks when that checklist is skipped — file drops and clicks both regressed.

## What stands in the way (verified in source)

Everything below is why "add a view" is really "introduce a pane kind".

**1. The model presumes a terminal at every level.**

- A split-tree leaf *is* a `PaneRuntime`: `SplitTreeNode` is `case leaf(PaneRuntime)` / `case split(…)` (`BattyKit/Sources/BattyKit/Model/SplitTree.swift:27-30`).
- `PaneRuntime` requires at least one Tab: `precondition(!initial.isEmpty, "PaneRuntime must contain at least one Tab")` (`BattyKit/Sources/BattyKit/Runtime/PaneRuntime.swift:31`).
- `TabRuntime.terminal` is a non-optional `public let terminal: TerminalViewState` (`BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:12`), constructed unconditionally in `init` (`TabRuntime.swift:117`). Every Tab **is** a Terminal Session; there is no way to represent a Tab or Pane without libghostty state today.
- Every pane-creation path funnels through `SplitTree.makePane` (`SplitTree.swift:208-215`), which always builds `PaneRuntime`/`TabRuntime` and inherits the source Tab's terminal cwd.

The central design decision this issue must produce an answer for: **where does *kind* live?** Options include a kind on the Pane (a non-terminal pane has no Tab bar at all) versus a kind on the Tab (a Git Status tab could sit alongside terminal tabs in one Pane). The user's phrasing — "create a new pane with the Git Status view" — suggests pane-level, but the model consequence differs a lot and the proposal should make the choice and its consequences visible.

**2. The view layer's pane body is unconditionally terminal placeholders.**

`PaneView.body` renders the tab bar plus `ZStack { ForEach(pane.tabs) { TerminalPlaceholderView(…) } }` (`BattyKit/Sources/BattyKit/Views/PaneView.swift:122-129`). There is no branch point where a pane could render anything else. Worse, mounting a `TerminalPlaceholderView` is not passive: its `body` eagerly calls `TerminalHostStore.shared.terminalView(for:windowID:)` to spawn the PTY (`BattyKit/Sources/BattyKit/Views/TerminalPlaceholderView.swift:36-43`). **A non-terminal pane must never mount one, or it starts a shell as a rendering side effect.**

**3. The terminal-host architecture applies only to terminal kinds — which is a simplification, if the boundary is drawn right.**

Per `docs/view-hierarchy.md` §3, terminal content is not hosted by SwiftUI at all: `TerminalHostStore` keeps one persistent `TerminalHostView` per content window with one `AppTerminalView` subview per live Tab, placed over placeholder-reported frames. A non-terminal view is plain SwiftUI — it needs **none** of that (no placement, no host subview, no geometry probe), and SwiftUI's rebuild churn that kills PTYs is harmless to it. The abstraction boundary must become: *terminal* panes get placeholders + host placement; *non-terminal* panes render their SwiftUI body directly. Note the z-order constraint from `view-hierarchy.md` §4 ("AppKit-on-top"): the host layer floats above the SwiftUI tree, but it only occupies frames reported for terminal Tabs, so a non-terminal pane's region has no host subview over it — pointer input should reach the SwiftUI view normally. The `docs/terminal-pane-requirements.md` checklist stays scoped to terminal panes; the proposal should say explicitly which of its guarantees (if any) a non-terminal pane must still honor.

**4. Persistence: the Codable model needs a kind — but whether anything serializes it today can't be settled from the docs.**

The one Codable layout type is `Pane` carrying only `id` and `isHidden` (`BattyKit/Sources/BattyKit/Model/LayoutModel.swift:15-23`, produced by `PaneRuntime.snapshot()`, `PaneRuntime.swift:39-41`). A pane kind must be added there with a backward-compatible decode (absent field = terminal). However, the documentation contradicts itself about workspace persistence: CLAUDE.md and `docs/view-hierarchy.md` describe `workspace.json` serialization and link a `WorkspaceManager.swift` (`docs/view-hierarchy.md:54`) **that does not exist in the tree**, no code anywhere encodes `Pane`, and `Concepts.md:270`'s version note says Workspace persistence was "never a planned feature" — while per-concept "Persisted:" rows remain (`Concepts.md:37,53,75,94,111`). Can't tell from source which way this is headed; the pane-kind field should be designed as if persistence lands, and the doc inconsistency is worth resolving alongside the `Concepts.md`/`PRD.md` vocabulary updates the umbrella already requires.

## Expected behavior

A written proposal (design doc or amendments to this issue and the umbrella) that settles:

1. Where kind lives (Pane vs Tab) and the model changes it implies (`SplitTreeNode`, `PaneRuntime`, `TabRuntime`, `SplitTree.makePane`).
2. How `PaneView` branches so a non-terminal pane never mounts a `TerminalPlaceholderView`.
3. The terminal-host boundary: `TerminalHostStore` host/placement machinery applies to terminal kinds only, and which `docs/terminal-pane-requirements.md` guarantees (if any) extend to non-terminal panes.
4. The pane-kind field in the Codable `Pane` value type with a backward-compatible decode, designed as if workspace persistence lands.
5. How the proposal composes with the umbrella's kind-aware CLI deltas (create / close / `list` payloads) without colliding with in-flight #0257-umbrella payload changes.
6. Evidence that terminal panes regress nothing: any spike that touches the terminal/pane path re-runs the manual checklist (pointer input, keyboard, file drop, text drop, IME) on terminal panes.
