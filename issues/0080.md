## Description

Port the Issues app's Help window pattern to Batty. The Issues app ships a self-contained Help window that renders bundled markdown files via a two-pane `NavigationSplitView`, completely independent of the main window's state. Reuse the pattern.

This issue is the **bootstrap** — add the markdown-rendering dependency, port the views and the catalog model, wire the Help menu, and seed with one placeholder section. Content for each Help section lands in follow-up issues (`#0081`–`#0088`).

## Reference implementation

`../Issues` ships these files:

- `Issues/Views/HelpView.swift` — root `NavigationSplitView`, sidebar + detail, with a `[String: Result<String, Error>]` cache keyed by section id.
- `Issues/Views/HelpSidebarView.swift` — `List(HelpCatalog.sections, selection:)`.
- `Issues/Views/HelpSuccessPaneView.swift` — renders markdown via `Textual`'s `StructuredText`.
- `Issues/Views/HelpErrorPaneView.swift` — shows load failures.
- `Issues/Views/HelpLoadError.swift` — typed error.
- `Issues/Models/HelpSection.swift` — `Identifiable` struct with `id`, `title`, `resourceName`.
- `Issues/Models/HelpCatalog.swift` — static `[HelpSection]` driving the sidebar order.
- `Issues/Help/*.md` — bundled section content (`01-overview.md`, `02-tabs.md`, etc., numbered prefix for stable ordering).

Dependency: `https://github.com/gonzalezreal/textual.git` (provides `StructuredText` markdown view). Already used in Issues for markdown rendering.

## What this issue ships

### 1. Add the Textual package

Add `gonzalezreal/textual` to `Batty.xcodeproj`'s package dependencies. Pin a stable version matching what Issues uses (check `../Issues/Issues.xcodeproj/project.pbxproj` for the resolved version). Link the `Textual` library to the `Batty` target.

Note: BattyKit doesn't need the dependency; the Help views live in the app target alongside `BattyApp.swift`. Adding to BattyKit pulls SwiftUI into BattyKit's public API surface which we want to avoid.

### 2. Port the model

Create `Batty/Help/HelpSection.swift`:

```swift
struct HelpSection: Identifiable, Hashable {
    let id: String
    let title: String
    let resourceName: String  // matches the .md filename without extension
}
```

Create `Batty/Help/HelpCatalog.swift` with the initial section list:

```swift
enum HelpCatalog {
    static let sections: [HelpSection] = [
        .init(id: "01-overview",      title: "Overview",            resourceName: "01-overview"),
        .init(id: "02-sessions",      title: "Sessions",            resourceName: "02-sessions"),
        .init(id: "03-panes",         title: "Panes and Splits",    resourceName: "03-panes"),
        .init(id: "04-tabs",          title: "Tabs",                resourceName: "04-tabs"),
        .init(id: "05-shortcuts",     title: "Keyboard Shortcuts",  resourceName: "05-shortcuts"),
        .init(id: "06-notifications", title: "Notifications",       resourceName: "06-notifications"),
        .init(id: "07-themes",        title: "Themes",              resourceName: "07-themes"),
        .init(id: "08-drag-and-drop", title: "Drag and Drop",       resourceName: "08-drag-and-drop"),
    ]
}
```

The follow-up issues each ship one of these markdown files. v1 of this bootstrap issue can ship the catalog with stubs, OR can ship only `01-overview.md` and let later issues add to the catalog incrementally — pick whichever makes the build green from the first commit. Recommend shipping all eight resources as **placeholder stubs** ("Documentation coming soon — see `#NNNN`") so the sidebar reflects the planned outline and follow-up issues only need to update content.

### 3. Port the views

Direct ports of:
- `HelpView.swift` → `Batty/Help/HelpView.swift`.
- `HelpSidebarView.swift` → `Batty/Help/HelpSidebarView.swift`.
- `HelpSuccessPaneView.swift` → `Batty/Help/HelpSuccessPaneView.swift`.
- `HelpErrorPaneView.swift` → `Batty/Help/HelpErrorPaneView.swift`.
- `HelpLoadError.swift` → `Batty/Help/HelpLoadError.swift`.

Adjustments for Batty:

- Drop references to `Color.appBackground` / `Color.appText` (Batty doesn't have these). Use `Color(NSColor.windowBackgroundColor)` / `.primary`, or just inherit defaults.
- Drop `#if DEBUG` preview blocks if they reference missing types — they're decorative.
- The `HelpView` body's `Bundle.main.url(forResource:withExtension:subdirectory: "Help")` lookup should match Batty's bundled directory name. Confirm the `.md` files land in `Batty.app/Contents/Resources/Help/` after build.

### 4. Bundle the markdown files

In Xcode, add the `Batty/Help/*.md` files to the `Batty` target with **Folder Reference** (not Group). That preserves the `Help/` subdirectory inside the bundle so `Bundle.main.url(subdirectory: "Help")` resolves.

Alternative: add as a Group but ensure the Build Phase → Copy Bundle Resources lists each `.md`. Folder Reference is simpler.

### 5. Open Help via the menu

Add a `Window("Help", id: "help") { HelpView() }` scene in `BattyApp.swift`. Wire the standard `Cmd-?` (Help menu) to open it. Drop the system-default Help menu items (some are auto-generated by macOS) via `CommandGroup(replacing: .help)`:

```swift
CommandGroup(replacing: .help) {
    Button("Batty Help") {
        openHelpWindow()
    }
    .keyboardShortcut("?", modifiers: .command)
}
```

`openHelpWindow()` uses `EnvironmentValues.openWindow` or `NSWorkspace.shared.open(url:)` for the `batty://help` registered scheme. Pick whichever lands smallest — SwiftUI's `Window` scene with a stable `id` plus `@Environment(\.openWindow)` is the cleanest:

```swift
@Environment(\.openWindow) private var openWindow

Button("Batty Help") {
    openWindow(id: "help")
}
```

Note: `BattyCommands` already does `.commandsRemoved()` on the main `Window` scene (per `#0062`). The Help window scene needs its own definition in `BattyApp.body` and gets the standard Window menu items by default — that's fine for the Help window.

### 6. Seed `01-overview.md`

A short overview (~200 words) summarizing what Batty is, the main concepts (Window → Session → Pane → Tab), and pointers to the other sections. Tone matches the doc in `docs/view-hierarchy.md` (`#0076`) but user-facing rather than developer-facing.

The other sections (`02-sessions.md` through `08-drag-and-drop.md`) ship as placeholder stubs:

```markdown

Documentation coming soon — see issue #0082.
```

Replace each stub as the corresponding follow-up issue lands.

## Acceptance criteria

- Selecting **Help → Batty Help** (or pressing `Cmd-?`) opens a Help window with a sidebar listing all eight sections.
- Selecting "Overview" renders the seeded markdown via `StructuredText`.
- Selecting any other section shows the placeholder stub.
- The Help window is independent of the main window — closing Help doesn't affect terminals; closing the main window doesn't close Help.
- The Help window's sidebar selection persists for the lifetime of that window instance.

## Root cause

Feature gap: Batty had no in-app Help. The Issues app already shipped a
self-contained, dependency-light Help window pattern (markdown sections in
a NavigationSplitView rendered via Textual's `StructuredText`) that was a
direct fit for Batty's needs.

## Fix

Ported the Issues Help system verbatim and adapted it to Batty's
conventions:

- Added the **Textual** Swift Package dependency to the `Batty` app
  target only (not BattyKit, since the dependency pulls in SwiftUI and
  BattyKit should keep its public API surface free of view types).
  Pinned to branch `main`, matching the Issues app's pin; the
  resolved revision is `5b06b811c0f5313b6b84bbef98c635a630638c38`.
- Created `Batty/Help/` with the model (`HelpSection`, `HelpCatalog`),
  the views (`HelpView`, `HelpSidebarView`, `HelpSuccessPaneView`,
  `HelpErrorPaneView`), and a typed `HelpLoadError`. Dropped
  `Color.appBackground` / `Color.appText` references and `#if DEBUG`
  preview blocks during the port; otherwise the views are byte-for-byte
  equivalents.
- Seeded `01-overview.md` with a ~300-word user-facing overview
  introducing Window / Session / Pane / Tab / Split / Theme / Bell Feed
  / Workspace and pointing at the seven other sections. The seven
  follow-up files (`02-sessions.md` through `08-drag-and-drop.md`) ship
  as placeholder stubs referencing `#0082`–`#0088`.
- Added a second `Window("Batty Help", id: "help")` scene in
  `BattyApp.swift`. The Help scene is independent of the main scene,
  so closing it doesn't affect terminals and closing terminals doesn't
  affect Help.
- Added `CommandGroup(replacing: .help)` to `BattyCommands`. A small
  private SwiftUI view (`BattyHelpMenuButton`) hosts the
  `@Environment(\.openWindow)` lookup because `Commands` builders
  aren't `View` and can't read environment values directly. The button

## Gotchas

- **Folder Reference vs Group, in a synchronized root group world.**
  The issue spec asked for a Folder Reference so that `Help/` is
  preserved as a subdirectory in the built bundle. In practice, the
  `Batty/` target uses a `PBXFileSystemSynchronizedRootGroup`, which
  flattens nested resources: the eight `.md` files land directly in
  `Batty.app/Contents/Resources/` with no `Help/` subdirectory. The
  Issues app's bundle has the same flat layout for the same reason.
  Rather than fight the synchronized-group default by introducing
  exception sets, the port follows the upstream pattern and uses
  `HelpView`'s existing two-step lookup: first
  `Bundle.main.url(forResource:withExtension:subdirectory: "Help")`,
  then `Bundle.main.url(forResource:withExtension:)` as a fallback.
  The fallback hits at runtime today; if a future Xcode change starts
  preserving the subdirectory, the first lookup will take over with
  no code change.
- **`.commandsRemoved()` on the main scene doesn't suppress the Help
  menu**, because `.commandsRemoved()` only removes the system-default
  commands that would otherwise auto-apply to that Scene's window —
  not commands installed via the `.commands { … }` modifier. The Help
  menu is installed via `BattyCommands`'s
  `CommandGroup(replacing: .help)`, so it shows up correctly.
- **`CommandGroup` builders are not `View` builders.** Reading
  `@Environment(\.openWindow)` inside a `CommandGroup` closure compiles
  but the lookup silently returns a no-op `OpenWindowAction`. Hosting
  the button in its own `View` (here `BattyHelpMenuButton`) makes the
  environment lookup work as expected, same trick the Issues app uses.
- **UI sign-off.** Visual verification (sidebar styling, padding,
  markdown rendering details, dark-mode appearance) is the user's call
  — left at `resolved`, not `closed`.
