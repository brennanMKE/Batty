## Description

> **Rescoped 2026-11-19 (user decision below).** This issue first said "add PhotonHTTP as an SPM dependency in `BattyKit/Package.swift`". It now says: Batty adds **no** package dependency; `batty server serve <dir>` runs the PhotonHTTP command-line tool when the user has installed it separately, in a terminal Pane, tracked in the Servers list like `server start`. The SPM, tools-version 6.4 bump and tag-pinning items are dropped.

Child of #0689 (decision E, as amended 2026-11-19).

### Facts from PhotonHTTP llms.txt (2026-11-19)

Source: `https://photon-http.sstools.co/llms.txt` (summary bullets and "Start here" / "Run a site"), and the two pages it links for running: `docs/getting-started.md` ("Install", "Serve a folder") and `docs/running-on-a-mac.md` ("Serve a folder", "Command line", "Control commands", "Binding to all interfaces and the firewall prompt", "Shutdown, restart and reload"). These replace the facts read from the repo at `2d01f282` earlier today (executable then still `SwiftWebServer`, no install path).

- **Executable: `photon`.** Requires macOS 15+ and a Swift 6.4 toolchain (Xcode or swift.org); not built or tested on Linux.
- **Install** (builds from source, no Homebrew formula or binary release named): `curl -fsSL https://photon-http.sstools.co/install.sh | bash`. It clones the repo, builds a release binary and installs `photon` to `/usr/local/bin`, using sudo only for the final copy and only when that folder isn't writable; it never edits shell files. Options after `bash -s --`: `--prefix DIR` installs to `DIR/bin` (e.g. `~/.local` needs no sudo), `--version REF` picks a git tag or branch (default `main`). From a checkout: `scripts/install.sh`. Check with `photon --help`. Uninstall: delete the binary; it has no other files.
- **Serve a folder:** `photon serve [DIR] [--port PORT] [--host HOST]`. Defaults: current directory, port `8080`, host `127.0.0.1` (only this Mac can connect; `0.0.0.0` shares on the network). `--port 0` picks a free port and the `listening` line shows which. `/` and every directory serve their `index.html`; a directory without the trailing slash redirects. `serve` never reads `http-config.json`, so a stray config can't change it; it is always plain static serving (no TLS, compression, logs or vhosts — those need `photon --config FILE`).
- **Readiness:** stdout prints `listening HOST:PORT` (e.g. `listening 127.0.0.1:8080`) once bound; "Scripts can wait for the first line." stderr gets `photon: serving /abs/root`, warnings, `signal 15, shutting down`, `stopped`, and errors.
- **Exit status:** `0` after a graceful stop, `1` on a configuration or startup error (missing root, port in use) with a message, `2` on a usage error.
- **Stopping:** SIGINT and SIGTERM start a graceful shutdown: listeners stop accepting, in-flight requests finish for up to `drainTimeout` seconds (default `10`), the rest are cancelled, exit `0`. A second signal during the drain is harmless.
- **Status:** there is **no HTTP status or health endpoint**. `photon status [--config FILE] [--json]`, `reload` and `restart` find a server through its status file (`statusFile`, default `run/status.json` next to the config, JSON, mode 0600, holds `pid`, `listening`, `state` …) and signal its pid; there is no control socket. The status file "is written only when the server runs with a config file" — so a `photon serve` server has none, and `photon status`/`restart` don't apply to it. Prometheus metrics (`accessLog.metrics`) also need a config.
- **Reload:** hot reload watches `http-config.json` (config-only); there is **no reload-on-change of served files** and no injected reload script.
- **Firewall:** loopback (`127.0.0.1`, `::1`) never triggers the macOS firewall prompt; a non-loopback bind by a newly built (unsigned) `photon` does. "A server reached only through a local reverse proxy or a tunnel (Tailscale, Cloudflare Tunnel) can stay on loopback."
- **TLS / HTTP/2 / HTTP/3:** config-file only (PKCS#12 identity loaded in memory); not relevant to `serve`, which is HTTP/1.1 cleartext on loopback. Tailnet HTTPS comes from `tailscale serve` (#0694).

## Expected behavior

Updated 2026-11-19 from the PhotonHTTP llms.txt facts above.

- **No dependency.** `BattyKit/Package.swift` is unchanged; nothing from PhotonHTTP is linked into the app.
- **Detection** (read-only, off the main actor, only when `serve` runs or Settings is shown): an executable named `photon` on the login-shell `PATH`, then the installer's locations: `/usr/local/bin/photon` (default) and `~/.local/bin/photon` (the documented `--prefix ~/.local`). No Homebrew path is documented; the plan may also check `/opt/homebrew/bin/photon` cheaply but must not claim a formula exists. Only `photon` is accepted (the old `SwiftWebServer` executable has no `serve` subcommand).
- **`batty server serve [<dir>] [--port N] [--open]`** (dir defaults to the caller's cwd, matching `photon serve`) runs, in a new terminal Pane as `server start` does (#0692):

  ```
  <photon path> serve <absolute dir> --host 127.0.0.1 --port <N>
  ```

  `--host 127.0.0.1` is passed explicitly (it is also the default) so a future default change can't widen the bind. **Port:** `--port N` when given; otherwise Batty picks a free loopback port itself and passes it, rather than `--port 0`, because the `listening` line goes to the terminal Pane's PTY, which Batty does not parse, and the server registry tracks a known port (`ListeningPortScanner`). Batty does not use photon's default 8080, so two serves don't collide.
- **Readiness:** the server registers in the Servers list (#0691) as a managed `start`-style entry for that port, and shows as listening once `ListeningPortScanner` finds the listener (equivalent to photon's `listening 127.0.0.1:N` line, which the user sees in the Pane). If photon exits `1` (port in use, missing root) the Pane shows its stderr message and the entry shows not listening, as for `server start`. `--wait` (as on `start`) may return once listening.
- **Status in the list:** name, port, state from the process and the port scan — the same as `server start`. PhotonHTTP has no status endpoint, and its status file exists only with a config file, which `serve` ignores; Batty writes no config and serves no `/_batty/status`. The Process Status Pane (#0692) watches the `photon` process.
- **Stop / restart:** `server stop` uses `server start`'s terminal-job ownership rules (#0658); SIGINT or SIGTERM makes photon drain for up to 10 s and exit `0`, so the stop escalation must allow that drain before SIGKILL (the plan checks the current escalation delays). `server restart` stops and reruns the same command line; `photon restart` does not apply (no status file under `serve`).
- **Not installed:** `serve` fails before creating a Pane, with a message like: "`batty server serve` needs PhotonHTTP's `photon` command, which isn't installed. Install it (macOS 15+, Swift 6.4 toolchain) with `curl -fsSL https://photon-http.sstools.co/install.sh | bash`, then check with `photon --help`. See https://photon-http.sstools.co/docs/getting-started.md". Batty never runs the installer. Settings (Advanced, near the CLI install) and Docs mention PhotonHTTP as an optional, separately installed tool with the same command and link; no prompt or banner.
- **Remove the in-app server** (orchestrator default, open question below): delete `Runtime/StaticServer/`, `InAppStaticServerBackend`, the in-app parts of `AppStateStore+StaticServer.swift` and their tests.
- Starts only on request; nothing listens at launch.

## Acceptance criteria

1. Unit tests with an injected executable locator and command runner (no sleeps): detection finds `photon` on `PATH` and in the fallback locations (`/usr/local/bin`, `~/.local/bin`), and reports absent otherwise; `serve` builds the exact argv `[<photon>, "serve", <abs dir>, "--host", "127.0.0.1", "--port", "<N>"]` with `--port N` and with a Batty-picked port; `serve` without the tool fails with the install-guidance message and creates no Pane; the server registers on the `listening` line / listener and leaves the list on exit.
2. `BattyKit/Package.swift` and `Package.resolved` gain no PhotonHTTP entry; `git grep -n NWListener BattyKit/Sources` finds no static-server use (if the open question is decided as remove).
3. UI test (typecheck only per issue): with a stub `photon` executable on `PATH`, `server serve <dir>` opens a terminal Pane and a `toolbar.servers` row.
4. A fresh install shows nothing new and opens no listening socket until `server serve` runs; without PhotonHTTP installed nothing about it appears except the optional mention in Settings and Docs.
5. `./build.sh`, `./build.sh unit`, `./build.sh ui-typecheck` pass.
6. The website Docs page (`website/docs/index.md`, #0683) already describes `batty server serve` running `photon`. The "photon not installed" message and install guidance match the Docs page text, and the implementer re-runs `python3 -I tools/build-docs-page.py --check`, updating `website/docs/index.md` if the shipped behaviour differs.

## Open questions

1. **Remove the in-app `NWListener` server (#0649) or keep it as a fallback when PhotonHTTP isn't installed?** Orchestrator default (the user may override): **remove** it, to keep the app small; `serve` then needs PhotonHTTP. Keeping it would also keep its reload-on-change behavior, which the PhotonHTTP CLI does not provide (confirmed by the llms.txt docs: `photon` hot-reloads only its config file, and `serve` reads none).

## Decisions (user, 2026-11-19)

- **License:** PhotonHTTP (`github.com/brennanMKE/PhotonHTTP`) now has an MIT license (GitHub reports spdx `MIT`, pushed 2026-11-19). Kept as context; Batty no longer bundles it.
- **Rename:** the user is renaming the package from `SwiftWebServer` to `PhotonHTTP`. The package rename landed (`a333f2bf`); the executable product was still `SwiftWebServer` as of `2d01f282`; the published docs (llms.txt, 2026-11-19) name it `photon`.
- "We may not need to install PhotonHTTP directly in Batty. Instead we can simply offer to use it if the user installs it separately as a CLI tool."
