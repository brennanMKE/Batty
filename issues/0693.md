## Decision (2026-11-20)

User, verbatim: "we do not need PhotonHTTP as an external CLI tool. It can be used when available and we could offer to install it."

- **PhotonHTTP is not a dependency** of Batty or of `batty server serve`. Nothing is linked and nothing requires it.
- **The built-in static server stays** (`Runtime/StaticServer/`, `InAppStaticServerBackend`). It is the default and the fallback for `server serve` whenever `photon` is not found. This answers open question 1: keep, don't remove.
- **When a `photon` executable is found, `server serve` uses it.**
- **Settings offers to install it, on click only.** Settings shows whether `photon` is installed and offers an "Install PhotonHTTP…" action that explains what it runs; the install runs only when the user clicks, in a visible terminal Pane. Never automatically, never a popup.
- **`server serve --engine builtin|photon`** gives an explicit choice (recommended, included below).

This supersedes the 2026-11-19 scope below in which `serve` required PhotonHTTP, failed when it was missing, and removed the in-app server.

### Facts from PhotonHTTP llms.txt (2026-11-19)

Source: `https://photon-http.sstools.co/llms.txt` (summary bullets and "Start here" / "Run a site"), and the two pages it links for running: `docs/getting-started.md` ("Install", "Serve a folder") and `docs/running-on-a-mac.md` ("Serve a folder", "Command line", "Control commands", "Binding to all interfaces and the firewall prompt", "Shutdown, restart and reload"). These replace the facts read from the repo at `2d01f282` earlier today (executable then still `SwiftWebServer`, no install path).

- **Executable: `photon`.** Requires macOS 15+ and a Swift 6.4 toolchain (Xcode or swift.org); not built or tested on Linux.
- **Install** (builds from source, no Homebrew formula or binary release named): `curl -fsSL https://photon-http.sstools.co/install.sh | bash`. It clones the repo, builds a release binary and installs `photon` to `/usr/local/bin`, using sudo only for the final copy and only when that folder isn't writable; it never edits shell files. Options after `bash -s --`: `--prefix DIR` installs to `DIR/bin` (e.g. `~/.local` needs no sudo), `--version REF` picks a git tag or branch (default `main`). From a checkout: `scripts/install.sh`. Check with `photon --help`. Uninstall: delete the binary; it has no other files.
- **Serve a folder:** `photon serve [DIR] [--port PORT] [--host HOST]`. Defaults: current directory, port `8080`, host `127.0.0.1` (only this Mac can connect; `0.0.0.0` shares on the network). `--port 0` picks a free port and the `listening` line shows which. `/` and every directory serve their `index.html`; a directory without the trailing slash redirects. `serve` never reads `http-config.json`, so a stray config can't change it; it is always plain static serving (no TLS, compression, logs or vhosts — those need `photon --config FILE`).
- **Readiness:** stdout prints `listening HOST:PORT` (e.g. `listening 127.0.0.1:8080`) once bound; "Scripts can wait for the first line." stderr gets `photon: serving /abs/root`, warnings, `signal 15, shutting down`, `stopped`, and errors.
- **Exit status:** `0` after a graceful stop, `1` on a configuration or startup error (missing root, port in use) with a message, `2` on a usage error.
- **Stopping:** SIGINT and SIGTERM start a graceful shutdown: listeners stop accepting, in-flight requests finish for up to `drainTimeout` seconds (default `10`), the rest are cancelled, exit `0`. A second signal during the drain is harmless.
- **Status:** there is **no HTTP status or health endpoint**. `photon status [--config FILE] [--json]`, `reload` and `restart` find a server through its status file (`statusFile`, default `run/status.json` next to the config, JSON, mode 0600, holds `pid`, `listening`, `state` …) and signal its pid; there is no control socket. The status file "is written only when the server runs with a config file" — so a `photon serve` server has none, and `photon status`/`restart` don't apply to it. Prometheus metrics (`accessLog.metrics`) also need a config.
- **Reload:** hot reload watches `http-config.json` (config-only); there is **no reload-on-change of served files** and no injected reload script.
- **Firewall:** loopback (`127.0.0.1`, `::1`) never triggers the macOS firewall prompt; a non-loopback bind by a newly built (unsigned) `photon` does. "A server reached only through a local reverse proxy or a tunnel (Tailscale, Cloudflare Tunnel) can stay on loopback."
- **TLS / HTTP/2 / HTTP/3:** config-file only (PKCS#12 identity loaded in memory); not relevant to `serve`, which is HTTP/1.1 cleartext on loopback. Tailnet HTTPS comes from `tailscale serve` (#0694).

## Plan

Written 2026-11-20 against `main` at `1b2da996` (worktree `issue/0693`). Follows the 2026-11-20 Decision: PhotonHTTP is optional, the built-in server stays the default and fallback.

### Decisions this plan takes (defaults; the user may override)

- **D1. Install prefix (open question 3): the documented default command**, exactly `curl -fsSL https://photon-http.sstools.co/install.sh | bash`. It installs `photon` to `/usr/local/bin`, which is on every login shell's `PATH` through `path_helper`, so `photon --help` works right after. If `/usr/local/bin` isn't writable the script asks for an administrator password with `sudo` for the final copy only. That prompt appears in the visible terminal Pane the button opens, and the button focuses that Pane so the user can type it. No `--prefix ~/.local`: it only works when `~/.local/bin` is on the user's `PATH`, which Batty can't promise. Detection checks `~/.local/bin` anyway, for users who install that way by hand.
- **D2. Discovery uses the caller's `PATH` and fixed candidates, never a login shell.** `batty server serve` runs in the user's shell, so the CLI sends its own `PATH` in the request (`searchPath`), and the app searches that `PATH`, then `/usr/local/bin/photon`, `~/.local/bin/photon` and `/opt/homebrew/bin/photon`, in that order. The Homebrew path is a cheap extra check; the docs must not say a formula exists. Settings has no caller, so it searches the app's own `PATH` and the same candidates. Spawning `$SHELL -l -c 'command -v photon'` was rejected: it runs the user's rc files (side effects, slow, can hang on prompts) just to show a Settings row. Only an executable regular file named `photon` is accepted. Detection is a few `stat` calls and runs off the main actor (detached task), only when `serve` runs or the Settings row appears or is refreshed.
- **D3. Readiness needs no new prober.** A photon serve is a `TerminalTabServerBackend` entry, so `ServerEntry`'s existing tick (`PortListenerScanning` + `HTTPProbing`, both already injected) marks it listening. Batty doesn't parse photon's `listening` line.
- **D4. Stop bounds for photon.** The current `StopBounds()` default is SIGINT, wait 5 s, SIGTERM, wait 3 s, SIGKILL (`ProcessGroupStopper.swift`). PhotonHTTP drains for up to 10 s after the first signal, and a second signal doesn't shorten the drain. So a photon entry gets `StopBounds.photonServe = StopBounds(interrupt: .seconds(11), terminate: .seconds(2))`. The command-finished event still ends the wait early (`exitEvent`). The CLI's `serverStopTimeout` (15 s, `ServerCommand.swift`) goes to 20 s, because the stop/restart XPC reply awaits `awaitPendingWork()` (`AppXPCService.swift`).
- **D5. Settings placement: General ▸ Servers.** That section is shown only with the `servers` flag (`GeneralSettingsView(showsServers:)`), so the row follows the flag for free and stays out of Prod until 1.5.0.
- **D6. Wire shape.** A new `ServeEngine` enum (`builtin`, `photon`) in `BattyXPCCore`. A photon serve's wire `kind` is a new `ServerKind.photon` case, so `server list` text lines name it with no change to the column layout (`id, name, port, kind, state, url[, tailnet]`): built-in rows still say `static`, photon rows say `photon`. JSON replies also carry `engine`. The CLI and app ship together, so the new enum case is safe.
- **D7. `--open` with photon** opens the browser once, when the entry's listener first appears (event-driven, through `onListenerChange`), not at reply time when nothing listens yet. No waiting in the XPC handler.
- **D8. Process Status Pane.** A photon serve opens one on its first listener, the same as `server start` (`wantsProcessStatus = true`), as the issue says. A built-in serve stays as today (no Pane).

## Expected behavior

Rewritten 2026-11-20 for the decision above. PhotonHTTP facts are from the llms.txt section.

- **No dependency.** `BattyKit/Package.swift` and `Package.resolved` are unchanged; nothing from PhotonHTTP is linked into the app.
- **Built-in server kept.** `Runtime/StaticServer/`, `InAppStaticServerBackend` and `AppStateStore+StaticServer.swift` stay, with their tests and their reload-on-change behaviour.
- **Detection** (read-only, off the main actor, only when `serve` runs or the Settings section is shown): an executable named `photon` on the login-shell `PATH`, then the installer's locations: `/usr/local/bin/photon` (default) and `~/.local/bin/photon` (the documented `--prefix ~/.local`). No Homebrew path is documented; the plan may also check `/opt/homebrew/bin/photon` cheaply but must not claim a formula exists. Only `photon` is accepted (the old `SwiftWebServer` executable has no `serve` subcommand).
- **Engine choice for `batty server serve [<dir>] [--port N] [--open] [--engine builtin|photon]`** (dir defaults to the caller's cwd):
  - no `--engine`: `photon` when detected, otherwise the built-in server. Nothing is printed or shown about PhotonHTTP when it is absent; the built-in server just runs, as today.
  - `--engine builtin`: always the built-in server (for example to keep reload-on-change, which `photon serve` doesn't do).
  - `--engine photon`: `photon` only; if it isn't found, fail before creating a Pane with: "`photon` (PhotonHTTP) isn't installed. Install it from Settings, or run `curl -fsSL https://photon-http.sstools.co/install.sh | bash` (macOS 15+, Swift 6.4 toolchain), then check with `photon --help`. See https://photon-http.sstools.co/docs/getting-started.md". No silent fallback when the user named the engine.
  - `server list` and the Servers list show which engine a serve uses.
- **Photon engine run** — in a new terminal Pane as `server start` does (#0692):

  ```
  <photon path> serve <absolute dir> --host 127.0.0.1 --port <N>
  ```

  `--host 127.0.0.1` is passed explicitly (it is also the default) so a future default change can't widen the bind. **Port:** `--port N` when given; otherwise Batty picks a free loopback port itself and passes it, rather than `--port 0`, because the `listening` line goes to the Pane's PTY, which Batty does not parse, and the server registry tracks a known port (`ListeningPortScanner`). Batty does not use photon's default 8080, so two serves don't collide.
- **Photon readiness:** the server registers in the Servers list (#0691) as a managed `start`-style entry for that port and shows as listening once `ListeningPortScanner` finds the listener (the user sees photon's `listening 127.0.0.1:N` line in the Pane). If photon exits `1` (port in use, missing root) the Pane shows its stderr message and the entry shows not listening, as for `server start`. `--wait` may return once listening.
- **Photon status:** name, port, state from the process and the port scan, the same as `server start`. PhotonHTTP has no status endpoint, and its status file exists only with a config file, which `serve` ignores; Batty writes no config. The Process Status Pane (#0692) watches the `photon` process.
- **Photon stop / restart:** `server stop` uses `server start`'s terminal-job ownership rules (#0658); SIGINT or SIGTERM makes photon drain for up to 10 s and exit `0`, so the stop escalation must allow that drain before SIGKILL (the plan checks the current escalation delays). `server restart` stops and reruns the same command line and engine; `photon restart` does not apply (no status file under `serve`).
- **Built-in engine:** unchanged behaviour of today's `serve`.
- **Settings — PhotonHTTP row** (in the Servers section, or next to the CLI/agent setup in Advanced; the plan picks one and follows the `servers` flag while it exists): shows "Installed at <path>" or "Not installed", with one sentence that PhotonHTTP is an optional static server `batty server serve` uses when present, and a link to https://photon-http.sstools.co/docs/getting-started.md. When not installed, an **"Install PhotonHTTP…"** button. The row's text, visible before the click, explains what will run: the command `curl -fsSL https://photon-http.sstools.co/install.sh | bash`, that it downloads and builds PhotonHTTP from source and needs macOS 15+ and a Swift 6.4 toolchain (Xcode or swift.org), and that it installs `photon` to `/usr/local/bin` and may ask for an administrator password for that copy. Clicking it opens a new terminal Pane in the current Session running that command, so the user sees all output and any sudo prompt; Batty never runs the installer itself or in the background, and never on launch. When the Pane's command exits, the row re-detects (on Settings appear, or a Refresh control). No sheet, alert, banner or prompt anywhere else.
- **Docs and Help** describe the engine choice, `--engine`, and the Settings install action.
- Starts only on request; nothing listens at launch.
