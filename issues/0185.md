## Root cause

The test snapshots the `tab-chip.*` count, dispatches `Cmd-T`, polls
until the chip count is exactly `chipsBefore + 1`, then dispatches
`Cmd-W` and polls until the count returns to `chipsBefore`. Both
`XCTAssertTrue` calls (`LifecycleTests.swift:39` and `:42`) are the
post-keystroke `waitFor` polls.

Pre-[[0170]], each test file's duplicated `waitFor` helper used
`Thread.sleep(forTimeInterval: 0.1)` from a `@MainActor` test method,
starving the test process's main runloop and preventing XCUITest's XPC
bridge from delivering the post-keystroke accessibility-tree snapshots
inside the 5s budget. The predicate kept reading the stale chip count
and the assertion failed before the second keystroke was meaningfully
verified.

The app-side Cmd-T and Cmd-W routing is correct; the new chip appears
and is removed well inside 5s now that the centralized `waitFor`
(commit `eb00412`) pumps the runloop via `RunLoop.run(until:)` between
predicate evaluations.

## Fix

(commit `eb00412`'s `waitFor` overhaul). This matches the resolution
pattern for sibling issues [[0174]], [[0175]], [[0178]], [[0179]], and

## Gotchas

- The test uses strict equality (`== chipsBefore + 1` and `== chipsBefore`)
  rather than the looser `> chipsBefore` pattern in
  `KeyboardShortcutTests.testCmdTCreatesNewTab`. This is tighter and
  would catch a regression where Cmd-T creates two chips or Cmd-W is a
  no-op — both of which would silently pass the `testCmdTCreatesNewTab`
  / `testCmdWClosesTabNotWindow` pair.
- Both assertions depend on XCUITest's `typeKey` awaiting
  `Wait for co.sstools.Batty.beta to idle` (visible in the test log)
  before returning, plus the `waitFor` runloop pump, to surface the
  updated accessibility-tree state. If a future refactor switches to a
  non-idling key dispatch path, the 5s `waitFor` budget should remain
  generous enough — but the dependency is real.
