## Root cause

Real app bug, not a test bug. `BattyShortcuts.handle` is installed
as a global `NSEvent` local monitor in `BattyAppDelegate` and ran
for every Cmd-key event regardless of which window was key. With the
Settings panel focused, Cmd-W still matched the `closeTab` binding
and fired `store.closeFocusedTab()` against the background main
window's focused tab. Closing the last tab in the only session
posted `battyAllSessionsClosed`, which the delegate handled by
calling `NSApp.terminate(nil)` — so the entire app quit when the
user pressed Cmd-W expecting to dismiss Settings.

The XCUITest failure message — "Application co.sstools.Batty.beta is
not running" — is a downstream symptom of the process exit, not the
real diagnostic.

## Fix

Resolved by code commit `c452302`. Added a `mainWindowIsKey()` gate
at the top of `BattyShortcuts.handle`. When the key window isn't the
Batty main window (SwiftUI `Window(_, id: "main")`), the monitor
returns false and macOS routes the event through normal NSWindow
handling — so Cmd-W reaches the Settings panel's `performClose:` and
closes only that window.

`mainWindowIsKey()` uses two signals: SwiftUI sets the underlying
NSWindow's `identifier` to contain the scene id, so an identifier
containing "main" matches; falls back to the documented main-window
title ("Batty") if the identifier check fails.

Verified locally with `scripts/run-ui-tests.sh` — the full 60-test
UI suite passes (was 16 failing on entry to this session).

## Gotchas

This is the kind of bug a UI test suite is supposed to catch — and
it would have, in #0166's original spec, except for the chain of
masking issues ([[0170]] runloop block, [[0205]]-era runner kill).
Worth keeping in mind: global `NSEvent` monitors are convenient but
need explicit window scoping for any action that targets a specific
window's content.
