## Description

Observed 2026-11-18 during a website deploy. After regenerating the Background Sets page with `python3 -I tools/build-backgrounds-page.py` and deploying with the documented `rsync -avz website/ photon:/var/www/vhosts/batty.sstools.co/` (`website/README.md`, "Background images"), Apache served `https://batty.sstools.co/backgrounds.html` as **403 Forbidden**. The file had been written `-rw-------`, and `rsync -a` preserves permissions, so the server copy was unreadable by the web server user. It was fixed by hand (`chmod 644` locally and on the server); the live page returns 200 now. Every future regenerate + deploy will repeat the 403.

### Current state (checked against `main`)

- `tools/build-backgrounds-page.py:185-189` writes the page atomically: `tempfile.mkstemp(dir=page_path.parent, prefix=".backgrounds-", suffix=".tmp")`, writes the bytes through `os.fdopen(fd, "wb")`, then `os.replace(tmp, page_path)`. Nothing sets the mode.
- `tempfile.mkstemp` always creates the file with mode `0600`, regardless of the umask. Confirmed on this host: a `mkstemp` file is `0o600` while `umask` is `022`. `os.replace` keeps the temp file's mode, so `website/backgrounds.html` ends up `0600` after every write. (The working-tree copy is `-rw-r--r--` today only because it was chmod'ed by hand.)
- The `--check` path (`:168-180`) and the "already up to date" path (`:182-184`) don't write, so only a run that actually changes the page triggers this.
- Git records only the executable bit, so the `0600` mode never shows in `git status` or a diff; it is visible only on the working-tree file and, after deploy, on the server.
- **No other tool under `tools/` has the same pattern.** `grep -n "mkstemp\|os.replace" tools/` finds only `build-backgrounds-page.py`. `tools/check-backgrounds.py` (the catalog check run before deploy) only reads the catalog and images; it has no write path. The selftests (`tools/build-backgrounds-page-selftest.py`, `tools/check-backgrounds-selftest.py`) write into their own temp fixtures, not into `website/`.
- `website/README.md:90` lists the post-deploy `curl -sI` checks: `backgrounds/catalog.json` returns 200 with the right headers, plus one full-size and one thumbnail image. It does not check `backgrounds.html`, so a 403 on the page itself goes unnoticed by the documented checks.

## Expected behavior

A regenerated `website/backgrounds.html` is world-readable like any other file in `website/`: mode `0644`, or `0666` masked by the current umask (what a plain `open(..., "w")` would produce), while keeping the atomic temp-file-plus-`os.replace` write. Deploying it with the documented rsync serves it with 200.

## Resolution notes

> 🟢 Resolved 2026-11-18 — the generator now sets the temp file to 0644 before the atomic replace, so a regenerated `backgrounds.html` deploys world-readable instead of returning 403.

## Root cause

`tools/build-backgrounds-page.py` writes the page atomically through `tempfile.mkstemp`, which always creates the file with mode `0600`, and `os.replace` keeps that mode. Every run that changed the page left `website/backgrounds.html` at `0600`; `rsync -a` preserved it on the server, so Apache returned 403. Confirmed: the new mode selftest case fails against `main`'s generator with `0o100600`.

## Fix

Added `PAGE_MODE = 0o644` (with a one-line why comment) and `os.fchmod(fd, PAGE_MODE)` right after `mkstemp`, inside the existing `try`, before the bytes are written. `mkstemp` in `website/`, `os.replace`, and unlink-on-failure are unchanged, so the write stays atomic. Fixed `0644`, not umask-derived, as the plan decided. `--check` and the up-to-date path still write nothing. `website/README.md`'s post-deploy checks now require `backgrounds.html` to return 200, with the `stat -f %Lp` hint for a 403. Skipped the optional `tools/README.md` sentence. No deviations otherwise.

## Plan

The selftest (`tools/build-backgrounds-page-selftest.py`, 28/28 passing) has no case about file mode or leftover temp files. `website/README.md`'s post-deploy `curl -sI` paragraph (end of "Background images") checks the catalog and two images, not the page. `tools/README.md` ("build-backgrounds-page.py") documents the selftest command. Neither `tools/` nor `website/` is a restricted area.

### Files

- **`tools/build-backgrounds-page.py`** — in the write block, right after `mkstemp` and inside the existing `try`, call `os.fchmod(fd, 0o644)` before writing the bytes. Keep `mkstemp(dir=page_path.parent, prefix=".backgrounds-", suffix=".tmp")`, `os.replace`, and the unlink-on-failure path unchanged, so the write stays atomic. Use a fixed `0o644` rather than `0o666 & ~umask`: the page is a deploy artifact, and under a restrictive umask (`077`) the umask variant would reproduce the 403. A fixed mode is also simpler: reading the umask in Python means `os.umask(0)` followed by restoring it. Name the mode in a module constant (e.g. `PAGE_MODE = 0o644`) with a one-line comment saying why: `mkstemp` always creates `0600`, `rsync -a` preserves it, and the server then returns 403. No other behaviour changes; `--check` and the "already up to date" path still write nothing.
- **`tools/build-backgrounds-page-selftest.py`** — add the cases below. Add `import os` (and `stat` if used).
- **`website/README.md`** — in the post-deploy paragraph ("After deploying, check with `curl -sI` …"), also require `https://batty.sstools.co/backgrounds.html` to return 200. Add a short clause that a 403 there usually means the file was deployed without world read (`stat -f %Lp website/backgrounds.html` should print `644`).

### Tests (all in `tools/build-backgrounds-page-selftest.py`)

- **`@case("written page is mode 0644 even when the old page was 0600")`** — build `Fx(d)`, `os.chmod(fx.page, 0o600)` first so the case can't pass vacuously on a fixture that `write_text` already created `0644`, then `fx.run()` (expect exit 0 and `"OK: wrote"`), then assert `stat.S_IMODE(os.stat(fx.page).st_mode) == 0o644`. It also covers the acceptance criterion's `mode & 0o044 == 0o044`. It must fail against the current code (the result is `0o600`). The implementer confirms that by running the selftest before the source fix, or by pointing the selftest at `git show main:tools/build-backgrounds-page.py` saved to a scratch path (the selftest takes the generator path as `argv[1]`), and records the FAIL line in `## Verification`.
- **`@case("a write leaves no temp file behind")`** — after a successful write, `list(fx.page.parent.glob(".backgrounds-*.tmp")) == []`. This pins the atomic write path the fix touches, and the leftover-dotfile concern in Notes.
- Optional, if cheap: **`@case("--check and an up-to-date run do not change the page's mode")`** — after a write, `chmod 0o600`, run with `--check`, then run again with no arguments (up to date), and assert the mode is still `0o600` both times. This shows that only the real write path sets the mode. Skip it if it complicates the fixture.

Existing guards: the 28 current selftest cases (regenerate, prose untouched, `--check`, example catalog) must all still pass.
