# 0652 — build-backgrounds-page.py writes website/backgrounds.html with mode 0600, so the deployed page returns 403 Forbidden

| | |
|---|---|

| **Platform** | macOS |

| **Target** | 1.5.0 |

## Description

Observed 2026-11-18 during a website deploy. After regenerating the Background Sets page with `python3 -I tools/build-backgrounds-page.py` and deploying with the documented `rsync -avz website/ photon:/var/www/vhosts/batty.sstools.co/` (`website/README.md`, "Background images"), Apache served `https://batty.sstools.co/backgrounds.html` as **403 Forbidden**. The file had been written `-rw-------`, and `rsync -a` preserves permissions, so the server copy was unreadable by the web server user. It was fixed by hand (`chmod 644` locally and on the server); the live page returns 200 now. Every future regenerate + deploy will repeat the 403.

### Current state (checked against `main`)

- `tools/build-backgrounds-page.py:185-189` writes the page atomically: `tempfile.mkstemp(dir=page_path.parent, prefix=".backgrounds-", suffix=".tmp")`, writes the bytes through `os.fdopen(fd, "wb")`, then `os.replace(tmp, page_path)`. Nothing sets the mode.
- `tempfile.mkstemp` always creates the file with mode `0600`, regardless of the umask. Confirmed on this host: a `mkstemp` file is `0o600` while `umask` is `022`. `os.replace` keeps the temp file's mode, so `website/backgrounds.html` ends up `0600` after every write. (The working-tree copy is `-rw-r--r--` today only because it was chmod'ed by hand.)
- The `--check` path (`:168-180`) and the "already up to date" path (`:182-184`) don't write, so only a run that actually changes the page triggers this.
- Git records only the executable bit, so the `0600` mode never shows in `git status` or a diff; it is visible only on the working-tree file and, after deploy, on the server.
- **No other tool under `tools/` has the same pattern.** `grep -n "mkstemp\|os.replace" tools/` finds only `build-backgrounds-page.py`. `tools/check-backgrounds.py` (the catalog check run before deploy) only reads the catalog and images; it has no write path. The selftests (`tools/build-backgrounds-page-selftest.py`, `tools/check-backgrounds-selftest.py`) write into their own temp fixtures, not into `website/`.
- `website/README.md:90` lists the post-deploy `curl -sI` checks: `backgrounds/catalog.json` returns 200 with the right headers, plus one full-size and one thumbnail image. It does not check `backgrounds.html`, so a 403 on the page itself goes unnoticed by the documented checks.

## Expected behavior

A regenerated `website/backgrounds.html` is world-readable like any other file in `website/`: mode `0644`, or `0666` masked by the current umask (what a plain `open(..., "w")` would produce), while keeping the atomic temp-file-plus-`os.replace` write. Deploying it with the documented rsync serves it with 200.

## Acceptance criteria

- After `python3 -I tools/build-backgrounds-page.py` writes a changed page, `stat -f %Lp website/backgrounds.html` reports `644` under the default `022` umask (not `600`).
- The write stays atomic: the temp file is still created in `website/` and moved into place with `os.replace`, and still removed on failure.
- `tools/build-backgrounds-page-selftest.py` gains a case asserting the written page's mode is group- and world-readable (for example, `mode & 0o044 == 0o044`), and it fails against the current code.
- `website/README.md`'s post-deploy checks also require `curl -sI https://batty.sstools.co/backgrounds.html` to return 200.

## Notes

- The temp file name starts with `.backgrounds-`; if a run is killed between `mkstemp` and `os.replace`, the leftover is a dotfile in `website/` that rsync would deploy. Not part of this report, but worth keeping in mind if the write path is touched.
- `website/README.md` is not under the restricted `scripts/` folder; `tools/` isn't restricted either.
