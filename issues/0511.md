# 0511 — `capabilities --json` advertises an inputSchema that is invalid under its own declared JSON Schema dialect

| | |
|---|---|
| **Status** | open |
| **Module** | CLI / Capabilities |
| **Platform** | macOS |
| **First seen** | 2026-10-14 |

## Description

Every property object inside a verb's `inputSchema.properties` carries `"required": <bool>`. In JSON Schema, a `properties` value **is itself a schema**, and `required` is a reserved keyword whose value must be an array of property names. A boolean there is a metaschema violation, so a standards-compliant validator can reject the very schema `CapabilitiesPayload.jsonSchemaDialect` tells it to validate against (`https://json-schema.org/draft/2020-12/schema`). The whole point of #0402 was handing an agent a schema it can use mechanically; an invalid schema does not do that.

Found by an external review of `v1.1.0..ad239f9e` — review id `20261014T193749Z-Batty-883c427`, finding 1 of 5 (medium, correctness, confidence high).

## Steps to reproduce

1. `batty capabilities --json`
2. Pull any verb's `inputSchema` out and validate it against `https://json-schema.org/draft/2020-12/schema`.

## Expected behavior

The emitted `inputSchema` validates against the dialect it declares. Required-ness is expressed only by the object-level `required` array, which is where the standard puts it.

## Actual behavior

Each property subschema carries `"required": true|false`. `CapabilitiesPropertyPayload` (`BattyKit/Sources/BattyXPCCore/CapabilitiesInputSchemaPayload.swift:57`) declares `public let required: Bool` and `CodingKeys` maps it to the literal `required` key (`:84`).

## Notes

- The non-standard `cliKind` and `enumValueNames` keys are *not* the same problem: unknown keywords are explicitly ignored by the spec. Only `required` collides with a reserved keyword, and only it has the wrong type.
- Fix: keep the information (it is genuinely useful to an agent and is asserted by `CapabilitiesInputSchemaTests`) but emit it under a non-reserved key, `cliRequired`, matching the `cliKind` precedent already in this payload. Nothing outside the Swift sources pins the old key name — `grep -rn cliKind` over `*.md`/`*.json` only hits `issues/0402.md`'s prose, and no test asserts the literal encoded key set.

### A second, adjacent defect found while fixing this

The object-level `required` array is **not** consistent with the per-property flags. `ProjectOpenCommand`'s positional `name` is declared `required: true` (`BattyKit/Sources/batty/ProjectCommand.swift:218`, asserted at `CapabilitiesInputSchemaTests.swift:222`) but its schema passes no `required:` array at all (`ProjectCommand.swift:217`), so the standard array an agent would actually read is empty. `notifyTitleIsTheOnlyRequiredParameterAcrossAllVerbs` (`CapabilitiesInputSchemaTests.swift:456`) encodes that gap as intended behavior in its comment. `batty project open` with no name exits 64, so `name` is mandatory in fact. Fixed here alongside the key rename, with the test and its comment updated. The one-line source change is its own commit so the behavior change can be dropped on its own; the two assertions that cover it live in the key-rename commit's test file and were not worth splitting out, so reverting the source line fails them.
