# 0362 — A Session reports 3 Panes while only 2 terminal Panes are visible

| | |
|---|---|
| **Status** | open |
| **Module** | Pane / Session |
| **Platform** | macOS |
| **First seen** | 2026-08-22 |

## Description

**User-reported, reproduced by the user, top priority.** The Session-level Pane count disagrees with what is on screen: the Session says 3 Panes exist while only 2 terminal Panes are visible in the Split area. In the user's words:

> "There is a bug where I am currently seeing 2 panes for terminals yet under the session it shows there are 3."

A count that disagrees with the visible layout means either a phantom Pane is being counted, a real Pane is not being rendered, or the count and the view are coming from different processes entirely (see #0361, reported in the same session — the `batty` CLI launching additional app instances may be causing or masking this).

## Steps to reproduce

Exact sequence not yet captured. What is known from the user's report:

1. The user has a Session whose Split area shows 2 terminal Panes.
2. Under that Session (the sidebar's per-Session Pane listing and/or a CLI count — which surface exactly is not yet confirmed), 3 Panes are reported.

How the third Pane came to exist — a split that was closed, a hide via the eye toggle, a CLI-created Pane, a non-terminal view kind — is not yet known.

## Expected behavior

The number of Panes a Session reports matches the Panes the user can see, and any deliberate exception (e.g. a hidden Pane listed in the sidebar so it can be re-shown) is visually distinguishable as such, not a bare higher count.

## Actual behavior

The Session reports 3 Panes; only 2 terminal Panes are visible.

## Investigation

Diagnostic subagents were dispatched 2026-08-22 to collect live evidence from the running app; their findings will be appended to this issue. Until then, everything in Notes below is a **hypothesis to test, not a finding**.

## Notes

### Hypotheses to test

1. **A non-terminal or phantom-tab Pane counted as a terminal Pane.** #0315's "The scope decision, and what it cost" section documents that a non-terminal `PaneRuntime` keeps one structural `TabRuntime` that no view ever renders, and that review had to kind-gate **ten separate consumers** that counted or listed it — the quit-confirmation count, `batty status`'s `tabCount`, `batty list --tabs`, Open Quickly, the sidebar row (which rendered `"2/1 — Tab"`), the drag preview, and theme/settings reconfiguration. **A missed gate in a count is exactly this bug's shape**, and the four view kinds merged onto `main` on 2026-08-22 (#0304 Git Status, #0305 Process Status, #0313 LM Studio dashboard, #0314 system metrics/thermals, under umbrella #0301) each added consumers of Pane/Tab structure.
2. **A hidden Pane.** `SplitTree.visiblePanes` (`BattyKit/Sources/BattyKit/Model/SplitTree.swift:136`) excludes `isHidden` Panes, but the sidebar's per-Session Pane listing iterates `panesSortedByColumnThenRow` (`SessionSidebarView.swift:40`), which is built on `allPanes` and deliberately includes hidden Panes so the eye toggle can re-show them. A Pane hidden via the eye button — or stuck `isHidden` through some path that should have closed it — would produce exactly "2 visible, 3 listed". The question is whether a third Pane legitimately exists in a hidden state the user didn't recognize, or is orphaned.
3. **A display site using the full pane list where it means visible Panes** — the `visiblePanes` vs `allPanes` distinction applied at the wrong site.
4. **A close path that removes the view but leaves the node in the Split tree**, so the tree (and every count derived from it) retains a Pane that no longer renders.
5. **Two app instances (#0361).** If the user created Panes via the CLI while #0361 was occurring, the visible Panes and the reported count may come from *different processes* — no counting bug at all. This must be ruled out first, since it invalidates any single-process analysis of the other hypotheses.

### Existing context

- #0315 — the kind-gating precedent and the phantom structural `TabRuntime` (read "The scope decision, and what it cost").
- #0304, #0305, #0313, #0314 — the four view-kind merges of 2026-08-22, umbrella #0301.
- #0361 — the CLI multi-instance issue reported in the same session; cross-referenced both ways.

## Investigation findings (2026-08-22)

Every path and line number below was re-verified against the working tree
before being written down. Nothing here launched the app or ran `batty`.

### The hidden-Pane hypothesis is contradicted by user testing

The mechanism in Notes hypothesis 2 is real and every citation checks out:

- `SplitTree.allPanes` (`BattyKit/Sources/BattyKit/Model/SplitTree.swift:132-134`)
  returns `root.allLeafPanes`; `SplitTree.visiblePanes` (`:137-139`) returns
  `root.visibleLeafPanes`, documented as "All panes in the tree whose
  `isHidden` is `false`". *(Minor correction: Notes above cites `:136` for
  `visiblePanes`; line 136 is the doc comment, the declaration is 137.)*
- `SplitTree.panesSortedByColumnThenRow` (`:826-836`) sorts **`allPanes`**,
  unfiltered.
- The sidebar's per-Session Pane listing is a `ForEach` over exactly that
  (`BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift:40`).
- `batty list`'s `panes=` field comes from `session.allPanes.count`
  (`BattyKit/Sources/batty/ListCommand.swift:112-113`).
- A successful hide/show logs **nothing**: `WindowRuntime.hidePane`
  (`BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift:657-705`) emits a
  single `logger.notice` only on the last-visible-pane refusal path, and
  `WindowRuntime.showPane` (`:708-724`) has no logging at all. That explains
  the empty log trail. *(Correction: the citation handed to this filer said
  `WindowRuntime.swift:610-677`; the actual ranges are 657-705 and 708-724.
  Line 610 is inside `tearDownAllPaneContent`.)*

**But the user has now reported:** *"I toggled the button to change visibility
multiple times. I could not get 3 panes to appear."* If the third Pane were
merely `isHidden`, toggling should reveal it — and the eye control is enabled
in exactly that case (`SessionSidebarView.swift:321-323`:
`pane.isHidden || session.tree.visiblePanes.count > 1`). A hidden Pane's row
also renders in `.secondary` foreground with an `eye.slash` icon, so it is
visually marked as hidden rather than presenting as a bare extra row.

**The hidden-Pane hypothesis is therefore downgraded from "most probable" to
"unconfirmed and contradicted by user testing."**

### New leading hypothesis: the third Pane is a non-terminal Pane, and this is not a bug

The user's exact words are *"I am currently seeing 2 panes **for terminals**
yet under the session it shows there are 3."* That phrasing fits a Session
containing two terminal Panes and one non-terminal Pane.

Supporting evidence, all verified against the **installed** build's source
(`main` at `7658c37`, the last commit before the app binary's Aug 21 14:04
mtime):

- `PaneContentKind` already had all five cases in that build — `.terminal`,
  `.gitStatus`, `.processStatus`, `.lmStudioDashboard`, `.systemMetrics` —
  because #0315 landed 2026-08-09, long before it.
- In that build none of the four views were implemented yet. The enum's own
  doc comment: *"`.terminal` is the only kind that renders real content today.
  Every other case renders as a deliberately provisional placeholder
  (`PaneView`'s non-terminal arm)."* `PaneView` at that commit renders
  `PaneContentPlaceholderView(kind: pane.kind)` for the non-terminal arm,
  showing only `Text(kind.displayName)`.
- The sidebar row for such a Pane reads `"<position> — <kind display name>"`
  (`SessionSidebarView.swift:315-319`, `PaneRow.label(position:firstTab:kind:)`)
  — e.g. `"2/1 — Git Status"`, deliberately *not* `"2/1 — Tab"`.
- In that build the only way to create one is the CLI (`batty pane split
  --view …`, #0315); the menu/palette affordances are #0331, which landed
  2026-08-22 14:46 — after the installed build.

So: two terminal Panes plus one placeholder Pane renders as three Panes on
screen and reports three in the sidebar, and toggling visibility would never
make a *third terminal* appear. **This would mean #0362 is expected behavior,
not a defect** — though possibly a discoverability problem, since the user did
not recognize the third Pane as a Pane.

**Not confirmed.** Testing it requires only looking at the third sidebar row's
label in the user's running app: a kind display name confirms this reading, a
`"2/1 — <tab title>"` label refutes it. Ask the user, or capture a screenshot
of the expanded Session in the sidebar.

### Other hypotheses to record, unranked and untested

- A Pane exists in the Split tree but renders at **zero or near-zero size** (a
  splitter ratio collapsed toward 0, or a layout bug), so it is counted and
  "visible" yet invisible on screen.
- A Pane whose **content fails to render** while the node persists.
- The **show path is broken for this particular Pane** — `showPane` clears
  `isHidden` but something else keeps it out of the rendered tree.
- A Pane belonging to a **different Session** being counted into this one.
- A Pane created in one of the **duplicate instances** from #0361 and somehow
  reflected in this instance's count.

### Ruled out

- **The #0315 phantom-`TabRuntime` theory** (Notes hypothesis 1). Its ten
  kind-gated consumers were all *tab* count/list sites; a phantom tab cannot
  inflate a *pane* count. Verified independently: grepping every
  `allPanes.count` / `visiblePanes.count` site in `BattyKit/Sources` and
  `Batty/`, **no pane-counting site branches on `kind`**. The only
  `kind`-gated `allPanes` traversals are content/theme/quick-open sites —
  `SettingsPreferences.swift:194`, `ThemePreference.swift:166`,
  `OpenQuicklyView.swift:51`, `ProcessStatusPaneView.swift:174` — none of
  which feeds the sidebar listing or `batty list`.
- **A stale node after close** (Notes hypothesis 4). `WindowRuntime.closePane`
  (`:505` onward) and `SplitTree.removePane` (`:377-386`) handle tree repair
  and focus correctly — `removePane` reassigns `focusedPaneID` to
  `newRoot.firstLeafPaneID` when the focused pane left the tree. Existing
  coverage in `BattyKit/Tests/BattyKitTests/AppStateStoreClosePaneTests.swift`
  and `PaneHideTests.swift`.

### Blocked on #0361

`batty list panes --json` would answer this immediately, but it routes through
`AppConnectDance.resolveEndpoint`'s launch-fallback path and may spawn another

### Test gap worth closing

`BattyKit/Tests/BattyKitTests/PaneHideTests.swift` never asserts
`allPanes.count` anywhere — `grep -n "allPanes.count"` over that file returns
nothing. The nearest test, `visiblePanesExcludesHiddenPanes` (`:303-316`),
builds a **two**-Pane tree and asserts `visiblePanes.count == 2` → `== 1` after
hiding → `== 2` after unhiding, without ever pairing those with
`allPanes.count == 2`. *(Correction: the framing handed to this filer described
this as "asserts `visiblePanes.count == 2` after hiding one of three" at
`:308-315`; the tree has two Panes, not three, and line 308 is the assertion
*before* the hide. The underlying gap is real and broader than described —
`allPanes.count` is unasserted in the entire file.)* Pairing the two counts in
one assertion is the shape that would pin this bug.

## Diagnosis parked, test gap closed (2026-08-22)

**Status stays `open`.** No behavior changed and the reported defect is
neither reproduced nor refuted — do not read the merged branch as a fix.

The decisive test named in the Investigation findings above (what the third
sidebar row's label reads in the running app) could not be run: the user's
app state has changed since the report, and the two ways to force the
question were both closed off. Relaunching the app to reproduce is barred by
a standing project rule, and `batty list panes --json` routes through the
launch-fallback path that may spawn a second instance — #0361 is fixed on
`main`, but the *running* binary predates that fix, so the CLI answer would
have been exactly as untrustworthy as before.

What landed instead is the one deliverable this issue names that does not
need live evidence: the test gap. `BattyKit/Tests/BattyKitTests/PaneHideTests.swift`
now pairs `allPanes.count` with `visiblePanes.count` in the same assertions
(the shape that would pin this bug), asserts `removePane` leaves no stale
node in the tree, and pins that a non-terminal Pane is counted in
`allPanes` — which is the leading, still-unrefuted reading of the user's
"3 vs 2" report.

**What these tests do and don't settle.** They pin `SplitTree`'s primitives
as kind-blind. They say nothing about the display sites that read them, and
those remain the open question: `SessionSidebarView.swift:40`'s
`panesSortedByColumnThenRow` listing and `ListCommand.swift:112-113`'s
`panes=` field.

**Lead worth following when this recurs**, surfaced by review: `batty list`'s
`panes=` does not come from `SplitTree.allPanes` at all. It comes from
`TopologySessionPayload.allPanes`
(`BattyKit/Sources/BattyXPCCore/TopologyPayload.swift:124-158`), an
*independent* recursive traversal over a separately-built payload tree. It
can diverge from `SplitTree.allPanes` without any of the tests added here
noticing, which makes it a more likely home for a genuine count discrepancy
than the tree primitives.

**To settle this issue**, capture either: the expanded Session in the sidebar
showing all three Pane rows and their labels (a kind display name such as
`2/1 - Git Status` confirms the non-terminal reading; `2/1 - <tab title>`
refutes it), or `batty list --json` from a build that postdates #0361's fix,
alongside a screenshot of the same Window.
