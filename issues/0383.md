# 0383 — Repeated `pane split --view` calls silently create duplicate view Panes, so agents have no idempotent find-or-create

| | |
|---|---|
| **Status** | open |
| **Module** | Pane / App |
| **Platform** | macOS |
| **First seen** | 2026-08-27 |

## Description

`batty pane split --view system-metrics` run twice produces two System Metrics Panes. Run a helper script three times and the developer's Session fills with stacked copies of the same dashboard. Nothing warns, nothing dedupes, and — until [#0379](0379.md) lands — nothing in `batty list --json` even lets the caller notice it happened.

That is a poor fit for how agents actually work. An agent re-runs its setup step on every task, after a restart, and after any failure it retries. What it needs is not "create a Pane" but **"make sure a Git Status Pane is showing, and tell me its id"** — find-or-create. Today the only way to approximate that is to close everything first, which destroys Panes the developer may have been reading.

## Expected behavior

Add `--unique` to `batty pane split --view <kind>`:

- If the target Session already contains a **visible** Pane of that kind, print *that* Pane's id and exit 0. Nothing is created; the command is idempotent.
- Otherwise, split as it does today and print the new Pane's id.
- Without the flag, behavior is **unchanged** — duplicates remain possible on purpose.
- `--unique` is only meaningful with `--view <kind>`; reject it for a terminal split (there is no sensible "the terminal Pane" to find) the same way `--pid` and `--path` are already rejected against the wrong kinds in `PaneCommand.swift`.

Either way the caller gets a Pane id on stdout and can chain, which is the property that makes the flag worth having.

## Pinned scope rules

- **Match rule: same Session, same kind, not hidden.** A hidden Pane does not satisfy `--unique` — the caller asked for something the human can see, and `pane show` (see [#0382](0382.md)) is the verb for un-hiding. Scope is the *target Session*, not the Window and not the app.
- **`viewOptions` differences do not defeat uniqueness.** A `git-status` Pane pointed at a different `--path`, or a `process-status` Pane pinned to a different `--pid`, still counts as "a Pane of that kind" and is returned as-is; the flag does not re-point it. Asking for the same kind on different options in one Session is rare enough to require closing the existing Pane first. **Say this in the `--unique` help text** so the behavior is discoverable at the point of use rather than only in this issue.
- When more than one visible Pane of the kind exists (created before `--unique`, or without it), return one deterministically — the first in the Session's existing Pane ordering — rather than erroring.

## This does not decide singleton enforcement

`docs/pane-kinds.md` §5 designs a per-kind `isSingletonPerSession` flag, and `PaneContentKind.swift` carries a long, deliberate comment recording that it was **not** built: [#0315](0315.md)'s "Orchestrator decisions for this implementation round (2026-08-09)" pins duplicate behavior as "always create a new pane, no singleton enforcement yet", because the enforcement policy — what scope counts as "the same", what happens on conflict — is the user's **open question 5**, not a technical call an implementer can make.

**This issue implements only the ergonomic half and leaves that question open.** `--unique` is opt-in, per-call, and CLI-only. `PaneContentKind.isSingletonPerSession` stays unbuilt. The Pane menu, the command palette, and the keyboard shortcuts can still create duplicate view Panes deliberately, and must continue to. An implementer who finds themselves adding a per-kind singleton property, or blocking a duplicate anywhere in the UI, has left this issue's scope — stop and hand the question back.

## Notes

- **Blocked by [#0379](0379.md).** The "find" half needs the Pane's `kind`, and it should read the same source the topology payload reads (`PaneRuntime.kind`) rather than growing a second way to ask what kind a Pane is. Building `--unique` against a private app-side lookup while `batty list --json` still cannot answer the same question would leave the agent unable to verify what the flag did.
- The resolution itself happens **app-side**, in the `paneSplit` handler, not by having the CLI issue a `list` first and decide — a client-side check would race the app and would not be atomic with the split.
- The reply shape needs no new payload: `PaneSplitReply` already carries a Pane id. Consider whether the caller should be able to tell "found" from "created"; if a field is added, keep it additive and default-decodable like the rest of the wire types.
- Verify the ordinary path is untouched: an existing test asserting that omitting `--view` keeps every split a terminal split (#0315's directive) must still pass, and a `--view` split without `--unique` must still produce a second Pane.
