# 0394 — Typing in the Theme Selector filter leaves the view scrolled past the matching Themes

| | |
|---|---|
| **Status** | open |
| **Module** | Theme |
| **Platform** | macOS |
| **First seen** | 2026-09-02 |

## Description

> "When I type in text in the theme selector and it is scrolled down and there are only a few items at the very top I cannot see them. This is bad UX and it needs to be fixed. Either this is a SwiftUI problem or we are using it wrong."

It is the second one. Filtering the Theme Selector narrows ~500 Themes down to a handful that now all sit at the top of the list, but the scroll offset is left exactly where it was. The user is looking at the empty space below the results and sees nothing.

The filter change resets the *keyboard cursor* and nothing else:

```swift
.onChange(of: query) { _, _ in cursorIndex = 0 }   // ThemeSelectorView.swift:185
```

Neither of the two `scrollTo` calls added by `#0363` covers this:

- `ThemeSelectorView.swift:180-184` — `.onChange(of: cursorIndex)` scrolls only when `cursorIndex` **changes**. The line above assigns `0`, which is frequently the value it already held, and SwiftUI's `onChange` does not fire on an equal-value assignment. So the scroll silently does not happen.
- `ThemeSelectorView.swift:190-193` — `scrollToActiveIfNeeded(proxy:)` runs once from the `.onAppear` at `:166-179` and targets only the *active* Theme, guarded by `allDisplayed.contains(where:)`. It never re-runs on a filter change, and it would decline anyway whenever the filter excludes the active Theme — which is the whole point of typing a filter.

**`SessionThemeSelectorView` has the identical defect.** It is a near-duplicate of the global selector in the same file (`#0363` measured them at ~130 near-identical lines each and deliberately left them unfactored), and carries the same three lines: `.onChange(of: query) { _, _ in cursorIndex = 0 }` at `:389`, the cursor scroll at `:384-388`, and `scrollToActiveIfNeeded` at `:394-397`. **A fix that lands in only one selector is half a fix.**

## Steps to reproduce

1. Open the Theme Selector (`Cmd-Shift-T`).
2. Scroll well down the ~500-entry catalog with the mouse or trackpad — far enough that the top of the list is off-screen.
3. Type a filter string that matches only a few Themes.
4. The view stays where it was. The matching Themes are up at the top, out of sight; the visible area is blank.

The per-Session selector reproduces the same way: right-click a Session in the sidebar → the theming entry (`SessionSidebarView.swift`), then steps 2–4.

### Why it sometimes appears to work — read this before "fixing" the cursor path

The behavior is intermittent, and the intermittency is the diagnostic:

- On the **first** keystroke after opening, `cursorIndex` is usually the active Theme's seeded index (a non-zero number, per `#0363`). Assigning `0` is a real change, `onChange(of: cursorIndex)` fires, and the view *does* scroll. This is the case that makes the bug look absent.
- On **every subsequent keystroke**, `cursorIndex` is already `0`. The assignment is a no-op, `onChange` does not fire, and nothing scrolls. Manually scrolling the list does not move `cursorIndex`, so scrolling down and then typing another character lands squarely in this case — exactly the sequence the user reported.
- If the active Theme happens to be pinned and first in the display order, `cursorIndex` starts at `0` and *no* keystroke ever scrolls.

An implementer who assumes the existing `onChange(of: cursorIndex)` path already handles filter changes will conclude there is nothing to fix and will fix nothing.

## Expected behavior

When the filter changes and there are matching Themes, the matching Themes are visible without the user scrolling manually — from any prior scroll position, on any keystroke, in **both** selectors.

## Actual behavior

The scroll offset is untouched by filtering. With the list scrolled down and a filter that matches only entries near the top, the user sees empty space.

## Notes

### `pinnedIDs` decides what "the top" is

`allDisplayed` is `filteredPinned + filteredOthers` (`ThemeSelectorView.swift:110`, `:323`), so the first element of the filtered list depends on which Themes are pinned — a match in the Pinned section outranks an earlier catalog entry that isn't pinned. Any scroll-to-top must target **the first element of the current filtered list** (`allDisplayed.first?.name`), resolved fresh at the moment of the scroll. Do not scroll to a remembered index, a remembered Theme name, or the top of the catalog order.

Also note the anchor: the existing cursor scroll uses `anchor: .center` (`:182`, `:386`). Centering the *first* result is not the same as showing the top of the list — it can leave the `"Pinned"` / `"Themes"` section header (`:156-163`) scrolled off above it. Whatever anchor the fix picks should be chosen deliberately for the "show me the top of the results" case, not inherited from the arrow-key case.

### Animated or not — decide, don't inherit

`#0363` made the initial positioning **unanimated** on purpose (a jarring twitch when the target is already visible, `ThemeSelectorView.swift:166-179`) while keeping the animated scroll for arrow-key movement (`:182`). A filter-change scroll is a third case with its own argument on both sides — an unanimated jump reads as instant, but an animated swoop from offset 400 to the top on every keystroke would be worse than the bug. Pick one and say why; do not let the choice fall out of which code path the fix happens to reuse.

### The observation rules are binding here

`docs/swiftui-observation-rules.md` governs this file — `#0363`'s implementation and its review both turned on it, and its `## Gotchas` records the reasoning.

- Any new `scrollTo` must fire from an **event-origin** hook. A filter keystroke is an event-origin flip of `query`, which puts an `onChange(of: query)` action in the doc's "routine" bucket (`swiftui-observation-rules.md:42-50`) — but state the reasoning rather than asserting it.
- No state writes from `body`, view `init`, `ViewModifier.body`, or preference/geometry callbacks.
- **Do not hop the scroll into a `Task` to dodge an ordering problem** (`swiftui-observation-rules.md:167-175`). If the scroll fires before `allDisplayed` reflects the new query, restructure which code owns the write; a `Task` hop trades an ordering bug for a race, which is the `#0229` regression.

### The lazy-container hazard

The cards live in a `LazyVGrid` (`:206`) inside a `LazyVStack` (`:155`) with ~500 entries and `.id(theme.name)` per card (`:226`). `#0363` recorded that `scrollTo` on a lazy container can silently no-op if called before the container has laid out, and solved its own initial-scroll case by attaching the `.onAppear` to the `ScrollViewReader`'s **content** rather than the sheet root (`:166-179`). The same trap applies to a filter-change scroll: the target row may not have been realized yet at the moment the query changes. Verify the scroll actually lands rather than assuming it does — and per the previous point, an arbitrary sleep or `Task` hop is not the answer.

### An existing accidental half-path, for completeness

When a filter matches nothing, `body` swaps `scrollContent` for `ContentUnavailableView` (`:134-143`). Deleting back to a matching query re-inserts `scrollContent`, which re-fires the `.onAppear` at `:166` and so re-runs `scrollToActiveIfNeeded`. That is the only route by which a query change currently repositions anything other than through the cursor, it only triggers via a round trip through the empty state, and it scrolls to the *active* Theme rather than to the results. It is not a foundation to build on — just don't be surprised by it while testing.

## Open questions (for the user — do not decide these unilaterally)

1. **When the filter is cleared** (query emptied), where should the view go? Restore the scroll position from before the filter, jump to the active Theme (matching what presentation does), or stay at the top of the now-unfiltered list? All three are defensible; the user has not chosen.
2. **Should the scroll also fire when the filter widens** — a character deleted, so the result set grows — or only when it narrows? Firing on every query change is simpler and self-consistent; firing only on narrowing preserves the user's position while they backspace.

## Acceptance criteria

- From any prior scroll position, typing a filter that matches only Themes near the top of the list brings them into view without manual scrolling — on the first keystroke and on every keystroke after it.
- The scroll target is the first entry of the current filtered list, correct whether or not it comes from the Pinned section.
- `ThemeSelectorView` and `SessionThemeSelectorView` behave identically.
- No regression to `#0363`'s behavior: the sheet still opens scrolled to the active Theme (unanimated), the active Theme still wears the `ActiveOutline`, and arrow keys still animate-scroll the cursor.

## Testing

`#0363` extracted the order/index math into two internal free functions — `themeDisplayOrder(pinnedIDs:)` (`ThemeSelectorView.swift:21-25`) and `themeCursorIndex(activeThemeName:pinnedIDs:)` (`:32-36`) — precisely so they could be unit-tested without a SwiftUI host; `BattyKit/Tests/BattyKitTests/ThemeSelectorViewTests.swift` covers them today. **Whatever new logic this fix needs (target resolution, "should we scroll" predicate) should be extracted the same way and unit-tested there.** `./build.sh unit` is the gate.

The scroll itself cannot be unit-tested and needs a human eye:

- Verify by hand in a **Beta** build — `./build.sh` defaults to Beta, `./build.sh run` launches `Batty Beta.app`. `./build.sh release` is Prod and is for releases only.
- **Never test against the user's Prod app at `/Applications/Batty.app`**, and never restart it.
- No UI-test coverage exists for either Theme Selector (`#0363` confirmed a grep of `BattyUITests` and `BattyTests` finds no reference to them), so nothing here is guarded by the UI suite.

## Relation

Builds directly on **`#0363`**, which introduced everything this issue touches: the `cursorIndex` seeding in `init`, the unanimated initial `scrollTo` from the `ScrollViewReader`'s content, and the animated `onChange(of: cursorIndex)` scroll. `#0363` explicitly scoped the filter case to only "the active mark must not render when the active Theme is filtered out" (its Expected behavior #6) and kept `onChange(of: query) { cursorIndex = 0 }` unchanged — the scroll consequence of filtering was never in its scope. This issue is that gap.
