## Description

Tabs have no right-click context menu. `Tab.titleOverride` exists in the persistence model and `PaneView.chipTitle(for:)` already honors it, but there's no UX surface to actually set or clear it. Add a context menu on each tab chip that exposes rename and the other actions that naturally fit at this level.

## Acceptance criteria

- Right-clicking a tab chip opens a context menu. The menu items operate on the right-clicked tab, not the active tab.
- The menu contains, at minimum:
  - **Rename…** — opens a sheet (or inline editor) seeded with the current `titleOverride` or live `terminal.title`, then writes the result into `titleOverride`. Cancel preserves the current value.
  - **Reset Title** — clears `titleOverride` so the chip falls back through `terminal.title` → cwd basename → `"Tab N"` per the `#0016` resolution.
  - **Duplicate Tab** — adds a new tab in the same pane, inheriting the source tab's `workingDirectory` via the existing `PaneRuntime.addTab(inheritingCWDFrom:)` path.
  - **Close Tab** — same as the chip "x" / Cmd-W: routes through `AppStateStore.closeTab(id:)` so the cascade in `#0046` applies.
  - **Close Other Tabs** — closes every tab in the pane except the right-clicked one.
- The selected tab in the context menu is the one the user actually right-clicked, even if a different tab is currently active.
- Menu items respect their own enabled/disabled state — e.g. **Close Other Tabs** is disabled when the pane has only one tab.

## Notes

- `Concepts.md` → Tab notes that the chip title resolves as: focused-surface process name → cwd basename → user-set override. The user-set override piece is exactly what rename writes.
- Implementation hint: `DefaultTabChip` from the `SlidingTabs` package may or may not expose a `.contextMenu { ... }` slot. If it doesn't, attach `.contextMenu` to the tab chip's view wrapper inside `PaneView`'s `SlidingTabBar` content closure.
- Rename UX: a one-shot sheet matches the existing `RenameSessionSheet` pattern from `SessionSidebarView`. Inline rename (TextField swap on the chip) is nicer but riskier — focus management inside a third-party tab bar gets fiddly.
- Out of scope for v1: **Move Tab To New Pane** / **Move Tab To Another Session** drag-out flows. Useful but a separate issue (`#0014` notes mention this as a follow-up).
- Out of scope: **Pin Tab** (no pinning model in the persistence schema). Could ship later if it becomes useful.

## Steps to reproduce (lack of)

1. Open a tab.
2. Right-click on the tab chip.
3. Observe: no menu appears.

## Expected vs. actual

- Expected: context menu with Rename, Reset Title, Duplicate Tab, Close Tab, Close Other Tabs.
- Actual: nothing happens.

## Root cause

`Tab.titleOverride` was wired through the persistence model and the chip title resolution back in `#0016`, but no UX entry point ever shipped. Right-click on a SwiftUI view does nothing by default — you have to attach `.contextMenu` explicitly, and the project's `PaneView` hadn't.

## Fix

`PaneView` attaches a `.contextMenu` to each `DefaultTabChip` via the `SlidingTabBar` content closure. Each item operates on the right-clicked tab (not the active tab), since the closure captures the `tab` argument from the chip builder.

Menu shipped:

- **Rename…** opens `RenameTabSheet` (new, mirrors the existing `RenameSessionSheet` pattern). Seeds the draft with `titleOverride` or the live `terminal.title`. On commit, writes the trimmed string to `titleOverride`; an empty string clears it. Cancel preserves.
- **Reset Title** clears `titleOverride`. Disabled when there's nothing to clear.
- **Duplicate Tab** calls `pane.addTab(inheritingCWDFrom: tab)` so the new tab spawns in the source tab's cwd — same path as the "+" button.
- **Close Tab** routes through `appStore.closeTab(id:)` so the `#0046` cascade applies (closes pane / session when appropriate). Falls back to `pane.removeTab` when no store is injected (preview/test).
- **Close Other Tabs** uses a new `PaneRuntime.closeOtherTabs(keeping:)` primitive that wipes everything except the target and makes it active. Disabled when the pane has fewer than 2 tabs.

## Files changed

- `BattyKit/Sources/BattyKit/PaneRuntime.swift` — added `closeOtherTabs(keeping:)`.
- `BattyKit/Sources/BattyKit/PaneView.swift` — `@State` for `renamingTab`/`renameDraft`; `.contextMenu` wired on each chip via a `tabContextMenu(for:)` view builder; `.sheet(item: $renamingTab)` presents `RenameTabSheet`.

## Gotchas

- **The context menu attaches to the chip's wrapper, not the title text.** Right-clicking the chip's "x" button or its hover area both open the menu — SwiftUI's `.contextMenu` doesn't fire when the user right-clicks an interactive subview that has its own gesture, but in practice the chip text region is the main target and it works.
- **Rename sheet uses `.sheet(item:)`** with `renamingTab: TabRuntime?` as the optional. `TabRuntime` is `Identifiable`, so SwiftUI keys the sheet to the tab id and a fresh sheet appears for each rename. If two consecutive renames target the same tab the existing sheet stays up; that's expected.
- **`closeOtherTabs` doesn't go through the cascade** because by definition the kept tab keeps the pane alive — nothing can cascade to empty. If someone passes an id that isn't in the pane, it's a no-op (handled by the `tabs.first(where:)` guard).
- **Tab title is truncated to 24 chars** at display time per `#0048`. The user can rename to a longer string but only the truncated form shows on the chip. The rename field itself has no character cap — the override persists in full into `Tab.titleOverride`.
- **No keyboard shortcut for Rename** in the chip context menu. The Session sidebar's Rename uses a context menu too without a shortcut. If a global Cmd-R for "Rename Active Tab" becomes useful, add it to `BattyCommands` later — out of scope here.
- **Out-of-scope items called out in the filed issue (Move Tab To New Pane, Pin Tab) are not added.** They need separate model changes (drag-out flow / pinned-tab state) that aren't free.
