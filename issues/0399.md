## Description

[#0392](0392.md) was filed to get `COLORTERM=truecolor` and a resolvable `TERM` onto a remote host reached with `ssh` from a Batty Tab. Its branch (`issue/0392`, commit `c9e9218`) does the config half correctly — `builder.withCustom("shell-integration-features", …)` with the SSH halves enabled, emitted from both `TerminalConfiguration` builders (`TabRuntime.swift` and `SettingsPreferences.swift`) so neither wipes the other. **That declaration is inert.** The pinned `libghostty-spm`'s shell-integration scripts contain no `ssh()` function at all, so no value of `shell-integration-features` produces any SSH behavior. #0392 is being rescoped to the declaration and the documentation; per `issues/Issues.md`'s no-dangling-follow-ups rule, this issue owns the actual outcome: `ssh <host> 'echo $COLORTERM'` printing `truecolor` from a Batty Tab.

Verified against the pinned checkout (`BattyKit/.build/checkouts/libghostty-spm`, revision `a2565ccf047c03c74a59dd7c16a8fac7c477852f` per `BattyKit/Package.resolved`, `Ghostty.ref` = `c4e16970a803b170e352432424f44192cb59f3ac`, release `1.5.20260903` — the re-pin landed by [#0389](0389.md)):

- `Sources/GhosttyTerminal/Resources/Ghostty/shell-integration/` contains **bash and zsh only**, and both scripts are a from-scratch MIT rewrite — each header reads "Written from scratch for libghostty-spm. Not derived from Ghostty's or Kitty's … integration (both GPLv3)" (`bash/ghostty.bash:1-9`, `zsh/ghostty-integration:1-7`).
- Neither script defines `ssh()`. The only occurrence of the string `ssh` in either is the zsh header's own disclaimer, verbatim (`zsh/ghostty-integration:22-23`): *"Anything else in the list is ignored; sudo, ssh-\* and path need a ghostty binary or change the user's environment, and this integration does neither."* The bash script does not mention `ssh` at all.

So the rewrite deliberately scopes out exactly the features #0392 turned on. (Drift note: #0392's issue file cites `Ghostty.ref = 35e1a0160…` — that predates the #0389 re-pin; the pinned upstream ref today is `c4e16970a…`.)

## The vendored tree was live until the re-pin unplugged it

Batty already bundles a *working* upstream-style implementation. `Resources/ghostty-runtime/ghostty/shell-integration/` (vendored by [#0003](0003.md), copied into `Batty.app/Contents/Resources/` by `scripts/bundle-ghostty-resources.sh:23-27`) carries the full Kitty-derived scripts:

- `bash/ghostty.bash:119` — `function ssh()`; `:126` — `ssh_opts+=(-o "SetEnv COLORTERM=truecolor")`; `:151` — `infocmp -0 -x xterm-ghostty`; `:159` — the remote `tic` install over a `ControlMaster` connection. `zsh/ghostty-integration:318` has the zsh twin.
- The sibling terminfo entry `Contents/Resources/terminfo/78/xterm-ghostty` (the #0003 sentinel, asserted by `scripts/preflight.sh`).

And that layout is not a coincidence — it is exactly what libghostty's resource discovery wants. `src/os/resourcesdir.zig` (verified at the pinned upstream ref, readable at `~/Developer/brennanMKE/libghostty-spm/References/ghostty-upstream`, checked out at `c4e16970a…`) climbs from the executable looking for `Contents/Resources/` containing the sentinel `terminfo/78/xterm-ghostty` (`:64`, `:88`) and, on a hit, uses `<…>/Contents/Resources/ghostty` as the resources dir — i.e. Batty's vendored tree.

**Before the #0389 re-pin, that fallback was the active path.** The previous pin (`b146b73a…`) shipped no `Resources/` at all and had no `GhosttyRuntimeResources` type (verified via `git ls-tree` in the fork clone), and nothing in Batty sets `GHOSTTY_RESOURCES_DIR` (grep of `BattyKit/Sources`, `Batty/`, `scripts/` — zero hits), so the sentinel search found Batty's five-shell tree. The `a2565ccf` package instead sets the env var itself — `GhosttyRuntimeResources.configureEnvironment()` (`Sources/GhosttyTerminal/Configuration/GhosttyRuntimeResources.swift:23-26`) does `setenv("GHOSTTY_RESOURCES_DIR", <package bundle path>, 1)` — and in release builds the env var is checked *first* (`resourcesdir.zig:52`; the xcframework is built `ReleaseFast`, `Script/build-ghostty.sh:120`), so the sentinel search never runs and Batty's vendored tree is now dead weight. That redirection is also what [#0400](0400.md) traces for the missing fish/elvish/nushell scripts — the two issues are plausibly one piece of work.

## Correction: the "one setenv after the package's call" premise does not survive source

The #0392 review proposed activating the vendored tree with a single `setenv("GHOSTTY_RESOURCES_DIR", …, 1)` "sequenced after the package's own call." **There is no such sequencing point.** The package's call chain is `TerminalController.init` → `initializeRuntimeIfNeeded()` (`Sources/GhosttyTerminal/Controller/TerminalController.swift:162`, `:325-330`), a private, once-guarded method whose body is `configureEnvironment()` immediately followed by `ghostty_init(0, nil)` — and libghostty snapshots the resources dir *during* `ghostty_init` (`src/global.zig:221`). So:

- Set the env var **before** the package runs → clobbered by the package's `setenv(…, 1)` (overwrite flag).
- Set it **after** → too late; the snapshot was taken between the two adjacent lines Batty cannot get between.

Activating the vendored tree therefore requires touching the package or its built product, not Batty's process environment. That materially changes the trade-off analysis below.

## Candidate directions (deliberately not decided here)

Like [#0332](0332.md) and [#0395](0395.md), this asks for the outcome, not a mechanism. Candidates, with what is known about each:

- **Activate Batty's vendored tree via the fork.** The user's fork (`~/Developer/brennanMKE/libghostty-spm`, `origin` = `brennanMKE/libghostty-spm`) is already how Batty consumes the package, and a one-line change there — honor a pre-set `GHOSTTY_RESOURCES_DIR` (i.e. `setenv(…, 0)`), or an explicit host-supplied resources URL — would let Batty point libghostty at `Contents/Resources/ghostty`. Caveats, all three real: (1) it is an ordering/behavior dependency on package internals that must survive every future pin bump; (2) the vendored `bash`/`zsh` scripts are **GPLv3** (Kitty-derived — `BattyKit/Sources/BattyKit/Help/09-third-party-licenses.md:342-373`, `Resources/ghostty-runtime/ATTRIBUTION.md`), so activating them in a proprietary notarized app is the **user's decision**, not an implementation detail; (3) Batty ships no `ghostty` binary (`Contents/Resources/bin/` holds `batty` and `BattyBroker`), so the wrapper's cache check (`bash/ghostty.bash:146`, `"$GHOSTTY_BIN_DIR/ghostty" +ssh-cache …`) always misses and every `ssh` pays one extra `ControlMaster` round-trip.
- **Ask upstream (Lakr233/libghostty-spm) to grow MIT ssh support.** The user has standing — merged PR #57 (fork clone commit `5407839`). Notably, upstream Ghostty at the **very ref the package pins** has a native, non-Kitty `+ssh` implementation (`src/cli/ssh.zig`, landed 2026-05-04, commit `484d6ec66`) whose logic could inform an MIT script — the "needs a ghostty binary" objection in the rewrite's header is about invoking `+ssh-cache`, and a script can degrade gracefully without it (the vendored wrapper already does).
- **Wait for the package to close the gap on its own.** Weakest option: the rewrite's header *states* it will not do this, and the same rewrite/pin has now produced multiple capability losses — the SSH features here, the fish/elvish/nushell scripts entirely ([#0400](0400.md)), the disclaimed `sudo`/`path` features, plus the unrelated pin regressions [#0390](0390.md) and [#0397](0397.md). No ETA exists.
- **Document the manual workaround only.** `SendEnv COLORTERM` in `~/.ssh/config` plus a one-time `infocmp -x xterm-ghostty | ssh <host> tic -x - -o ~/.terminfo`. Already written: `docs/ssh-colors-and-terminfo.md:151-165` on `issue/0392` (lands on `main` with that issue's squash). Cheapest, and leaves the Expected behavior below unmet by the product.

## Dead end, corrected: the native `+ssh` action is present, exported, and still unreachable

Recorded so nobody chases it. The static library **does** contain the native Zig `+ssh` action — `strings` on `BattyKit/.build/artifacts/libghostty-spm/libghostty/GhosttyKit.xcframework/macos-arm64_x86_64/libghostty.a` shows its working parts (`ControlMaster=yes`, `SendEnv=COLORTERM`, `mkdir -p ~/.terminfo 2>/dev/null && tic -x -`) and its full help text. And, correcting the claim this issue was drafted from, `ghostty.h` **does** export a CLI entrypoint: `GHOSTTY_API void ghostty_cli_try_action(void)` (`Headers/libghostty/ghostty.h:1148`). It is still unreachable from Batty as pinned, for a different reason: the action is detected from the argv handed to `ghostty_init` (`src/main_c.zig:110`, `:139-148`; `src/global.zig:131-137`), the package hardcodes `ghostty_init(0, nil)` (`TerminalController.swift:329`), and when an action *is* present `ghostty_cli_try_action` never returns — it runs the action and calls `exit`. Reaching it means shipping something that behaves as a `ghostty` CLI binary and re-plumbing the package's init. Out of proportion for this feature; noted in case a bundled `ghostty`-shim ever becomes worthwhile (it would also fix the `+ssh-cache` miss above).

## The remote-write caveat

`ssh-terminfo`, if ever activated, pipes Batty's terminfo into `tic` **on a machine the user may not own**, creating `~/.terminfo` there (vendored `bash/ghostty.bash:151-172`; the same behavior is baked into the library's native action per the strings above). The install is conservative — per-user, no `sudo`, short-circuits if the entry already resolves — but it is still an unrequested write to a remote home directory. #0392 (under revision at filing time) is dropping `ssh-terminfo` from its declared value for exactly this reason and shipping `ssh-env` only. Whatever this issue enables must treat remote terminfo installation as an explicit user decision — default-off, or clearly disclosed in Settings and Help.

## Expected behavior

From a Tab in Batty Beta, with whatever mechanism this issue lands and any opt-ins it defines enabled:

- `ssh <host> 'echo $COLORTERM'` prints `truecolor` (host `sshd` permitting via `AcceptEnv`).
- `$TERM` on the remote host resolves — either `xterm-ghostty` after an explicitly-consented terminfo install, or a safe widely-known fallback (`xterm-256color`) when not.
- No writes to a remote machine happen without an explicit user decision.
- The behavior and its limits are documented (the #0392 docs deliverable is the natural home).

Like #0392, final verification needs a real remote host and is not achievable from a build alone.
