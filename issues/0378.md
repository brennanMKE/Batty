## Description

Non-terminal Panes (`git-status`, `process-status`, `lm-studio-dashboard`, and `system-metrics`) have shared header chrome with a visibility eye control, but no visible way to close the Pane. A terminal Pane exposes an X on each Tab chip, and closing its last Tab removes the Pane and collapses its parent Split. Non-terminal Panes do not render a Tab bar, so they lost the equivalent mouse-reachable close path when the new Pane kinds were added.

Add an X control to the top-left corner of the shared non-terminal Pane header, opposite the existing visibility eye control on the right. Activating it should close that Pane through the existing Pane lifecycle so its non-terminal resources are torn down and its parent Split collapses in the same way it does when a terminal Pane loses its last Tab.

## Steps to reproduce

1. Create any non-terminal Pane in a Session.
2. Inspect the Pane's header chrome.
3. Try to close the Pane using the mouse.

## Expected behavior

Every non-terminal Pane has a clearly visible X in the top-left of its header, opposite the visibility eye. Activating the X closes the Pane and gives its Split space to the surviving sibling subtree.

## Actual behavior

The non-terminal Pane header shows the visibility eye and, when siblings exist, the Pane drag handle, but no close control.

## Acceptance criteria

- The shared header for every non-terminal `PaneContentKind` displays a borderless X control in its top-left corner, with the visibility eye remaining at the opposite right edge.
- The control has an appropriate help label, accessibility label, and stable accessibility identifier.
- Activating the control uses the existing Pane-close path; it tears down the Pane's content lifecycle, removes the Pane from the Session's Split tree, and collapses the parent Split without leaving an orphaned Pane or background work.
- Existing close refusal or confirmation outcomes are represented to the user rather than silently discarding the action.
- Terminal Pane chrome, Tab close behavior, Terminal Session focus, keyboard input, pointer input, file drop, text drop, and IME behavior remain unchanged.
- Unit tests cover the close action's model/lifecycle outcome, and a UI test verifies the control is visible and closes a non-terminal Pane.
- `scripts/build.sh unit` and the targeted UI test pass.

## Notes

The shared non-terminal header is currently assembled in `PaneView.nonTerminalShell`. `AppStateStore.closePane(id:)` and `WindowRuntime.closePane(id:refuseIfAppsLastPane:)` already provide Pane removal, Split collapse, terminal cleanup, non-terminal content teardown, and explicit refusal outcomes for the app's final Pane. The implementation should reuse that lifecycle rather than removing a Split node directly from view code.

Because this change touches Pane chrome and event routing near terminal content, implementation and review must follow `docs/view-hierarchy.md`, `docs/terminal-pane-requirements.md`, and `docs/swiftui-observation-rules.md` and verify that terminal input behavior is unaffected.

## Gotchas

- **The UI test ships unrun.** `BattyUITests/NonTerminalPaneCloseTests.swift` calls `BattyUITestHarness.launchBatty(script:)`, whose last statement is `app.launch()`; `issues/0386.md` (still `open`, and it names #0378 as blocked on it) measures that exact launch path at zero windows, so the test fails at line 24 before it ever reaches the close button — identically on unmodified `main`. This is a deliberate deviation from the acceptance criterion "a UI test verifies the control is visible and closes a non-terminal Pane": the test file is written, reviewed, and left in the tree unrun rather than deleted or weakened. It becomes live the moment #0386 lands. Until then, coverage for this issue is unit tests (`NonTerminalPaneTeardownPathsTests.swift`, `RemoveSessionWatchEventTests.swift`) plus the user's own manual check of the button in a running Beta build.
- **Correction to commit `53521d8`'s message.** That message says `.needsConfirmation` "remain[s] reachable, so the alert stays" — imprecise. `TerminalViewState+Polyfill.swift` hard-codes `needsConfirmClose` to `false`, and `TabRuntime.needsConfirmClose` is `needsConfirmCloseOverride ?? terminal.needsConfirmClose`, where the override is `#0398`'s *test-only* seam that no production code ever sets. `.needsConfirmation` is unit-testable (pinned by `closeNonTerminalPaneReturnsNeedsConfirmationWhenTheStructuralTabIsFlaggedBusy`) but not reachable in a running app today. `PaneView.paneCloseButton`'s own code comment already states this correctly; the commit message conflated "unit-testable" with "reachable in production."
- **With `.refusedLastPane` structurally unreachable from the button and `.needsConfirmation` unreachable in production, only `.unknownPane` is live** — and only via a race: a second click landing after the pane's first close already removed it from the tree but before SwiftUI tears the button's view down. Keeping all three switch arms is still correct (exhaustiveness, and `.needsConfirmation` going live the day the polyfill is replaced), but the user should not expect to actually see `paneCloseFailureMessage`'s alert under normal use.
