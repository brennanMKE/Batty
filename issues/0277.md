# 0277 — Give Beta its own suffixed broker identity so both variants ship working XPC

|---|---|

| **Platform** | macOS |

## Description

Beta builds are currently excluded from XPC entirely, and the user has decided that is not the end state: **Beta should get its own suffixed broker identity**, so both variants ship a working broker, register independently, and can never drive each other. This supersedes the Prod-only decision recorded in #0270's Gotchas and removes the stopgap guard #0271 added on top of it.

Current state, verified against source:

- `ServiceNames.broker` is the invariant literal `co.sstools.Batty.broker` (`BattyKit/Sources/BattyXPCCore/ServiceNames.swift`), and `ServiceNames.appBundleIdentifier` is the invariant literal `co.sstools.Batty` — while `PRODUCT_BUNDLE_IDENTIFIER` is `co.sstools.Batty` for Prod (`Configuration/App.xcconfig`) and `co.sstools.Batty.beta` for Beta (`Configuration/Beta.xcconfig`).
- #0270 shipped the broker **Prod-only**: the "Embed Broker" Run Script phase in `Batty.xcodeproj/project.pbxproj` checks `PRODUCT_BUNDLE_IDENTIFIER` and, when it is not `co.sstools.Batty`, removes any previously embedded `bin/BattyBroker`, `rm -rf`s the `LaunchAgents` directory, and exits — a Beta bundle carries no LaunchAgent at all.
- #0271 added a **fail-closed guard** in `AppXPCCoordinator.start()` (`BattyKit/Sources/BattyKit/XPC/AppXPCCoordinator.swift`) that returns early with a logged notice when `Bundle.main.bundleIdentifier != ServiceNames.appBundleIdentifier`. Without it, launching Beta would call `registerAppEndpoint` on Prod's broker and silently **replace Prod's stored endpoint** — after which `batty status` drives Beta while Prod's registration stays dead until relaunch. The guard's own comment records that it "forecloses nothing about the eventual variant-suffixing decision #0270 left open"; this ticket is that decision.
- Meanwhile Beta still embeds `bin/batty` unconditionally (the "Embed CLI" phase has no variant check), and both variants' `CLIInstaller` (`BattyKit/Sources/BattyKit/Settings/CLIInstaller.swift`) defaults to the same `installPath: "/usr/local/bin/batty"` symlink — so today a Beta-installed CLI silently flips the PATH command to a variant whose XPC verbs can only fail closed.

Target state: the Mach service name, launchd `Label`, plist filename, and app bundle identifier are all derived per variant from a single source — Prod keeps `co.sstools.Batty.broker` unchanged (no migration for existing installs); Beta gets `co.sstools.Batty.beta.broker`. Each variant's broker, app, and CLI agree on that variant's names and never touch the other's.

## The core difficulty: the plist gets no build-setting expansion

A LaunchAgent plist copied into the bundle by a build phase does **not** get `$(VAR)` build-setting substitution the way `INFOPLIST_FILE` does. This is verified, not assumed: the Embed Broker phase copies `Configuration/co.sstools.Batty.broker.plist` with a plain `/bin/cp -f`, and both the plist's own header comment and `BrokerAgentPlistTests.swift`'s doc comment record the constraint explicitly ("a build-phase-copied plist gets no `$(VAR)` substitution"). So `$(PRODUCT_BUNDLE_IDENTIFIER)` inside the plist would ship as a literal dollar-string, and launchd would silently decline to reserve the name.

Realistic approaches (implementer decides; recommendation below):

1. **Generate the plist in the Embed phase from a template** *(recommended)*. The phase is already a `/bin/zsh` script with `PRODUCT_BUNDLE_IDENTIFIER` in its environment; replace the `cp` with a substitution (e.g. `sed` on a placeholder, or `PlistBuddy` edits on a copied template) producing `${PRODUCT_BUNDLE_IDENTIFIER}.broker.plist` with matching `Label` and `MachServices` key. Single source of truth — every string in the shipped plist traces to `PRODUCT_BUNDLE_IDENTIFIER`, the same value the app's `CFBundleIdentifier` expands from. Cost: the shipped plist no longer exists verbatim in the repo, so `BrokerAgentPlistTests` must change shape — test the template (placeholder present, structure intact) and reproduce the substitution in Swift, asserting the result against each variant's `ServiceNames` derivation.
2. **Two static per-variant plists**, with the phase copying the right one. Keeps the file-on-disk test pattern byte-for-byte (each plist asserted against its variant's `ServiceNames` values), but duplicates the hand-typed XML the four-string rule warns about; the tests then police the drift they created the possibility of.
3. **`INFOPLIST_PREPROCESS`-style machinery** — that setting applies to the target's `INFOPLIST_FILE`; no mechanism was found for applying it to an arbitrary build-phase-copied plist (not verified exhaustively). Not recommended; do not burn time here unless options 1–2 both fail.

## The bare-Mach-O asymmetry

#0270 recorded (and `ServiceNames.swift`'s comments repeat) that computing the Mach name from `Bundle.main.bundleIdentifier` at **runtime** does not work for the broker or the CLI: both are bare Mach-Os at `Contents/Resources/bin/` with no adjacent `Info.plist` for `Bundle.main` to resolve. Only the app can read its own bundle id. So the variant has to reach those two processes another way:

- **Build-time baking** *(the straightforward path)*: the Embed phases already run `xcrun swift build` per product; pass a variant define (e.g. `-Xswiftc -D` conditional on `PRODUCT_BUNDLE_IDENTIFIER`) so the compiled binary selects its variant's names. Keep the derivation functions themselves unconditional in `ServiceNames` — both variants' names computable and testable from any build — with only the *selection* of "current" conditional. Caveats to verify during implementation, not assume: both variants share `BattyKit/.build`, so alternating Prod/Beta builds may thrash the SwiftPM cache (flag changes should invalidate it — behavior not verified); and a generated-source alternative would dirty the working tree from a build phase, which is worse.
- **Runtime enclosing-bundle resolution** *(alternative, needs a spike)*: both binaries physically live inside the `.app`; a process can resolve its own executable path (`_NSGetExecutablePath` + symlink resolution — `CommandLine.arguments[0]` is the symlink when invoked from PATH), walk up to the enclosing `.app`, and read that bundle's identifier via `Bundle(url:)` — which is not `Bundle.main` and is not ruled out by #0270's constraint. One binary then serves whichever bundle it ships in, with no conditional compilation. **Not verified in this repo**; if chosen, it must fail closed when the binary is not inside a bundle (a copied-out `batty` must error, never silently target Prod).

Either way, the app side keeps reading `Bundle.main.bundleIdentifier` (works today; `CFBundleIdentifier` is expanded from `PRODUCT_BUNDLE_IDENTIFIER`), and `BrokerAgentController`'s `SMAppService.agent(plistName:)` call takes the variant-derived plist name.

## Scope

1. **Variant-parameterized `ServiceNames`** (`BattyXPCCore`): Mach service name, launchd `Label`, plist filename, and `appBundleIdentifier` all derived per variant from the app bundle identifier — `"\(bundleID).broker"` yields `co.sstools.Batty.broker` (Prod, unchanged — existing Prod installs need no migration) and `co.sstools.Batty.beta.broker` (Beta). This preserves #0269's **four-strings-must-match** rule *per variant*: plist filename, plist `Label`, `MachServices` key, and the connect-time name. A mismatch makes launchd *silently* decline to reserve the name, surfacing much later as an unexplained "connection invalid".
2. **`ServiceNames.appBundleIdentifier` becomes variant-aware.** It is not only documentation: step 3 of the CLI connect dance launches the app by this identifier, so a Beta CLI with a Prod-baked identifier would launch the wrong app. Same for the fail-closed comparison sites.
3. **Plist generation or per-variant plists** per "The core difficulty" above, including updating the Embed Broker phase's `outputPaths` (currently hardcoded to the Prod plist filename; the phase is `alwaysOutOfDate = 1`, so the practical impact is on correctness of intent, not incremental builds — verify) and cleaning stale other-variant plists from `Contents/Library/LaunchAgents/` on incremental builds.
4. **Re-enable Beta embedding**: the Prod-only check in the Embed Broker phase goes away or becomes variant-aware (embed always; name by variant). The skip branch's `rm -f`/`rm -rf` cleanup logic is obsolete once both variants embed.
5. **Remove #0271's fail-closed guard in `AppXPCCoordinator.start()`.** It exists only because the identity is invariant; once names are variant-derived, Beta talking to Beta's broker is the *feature*, and leaving the guard in place would silently disable exactly what this ticket enables. Replace the equality check with the variant-aware derivation (the app derives its names from `Bundle.main.bundleIdentifier` and can no longer collide with the other variant by construction).
6. **The CLI resolves the same variant's names as the app that embedded it**, and the PATH collision is handled — see the next section.
7. **Settings**: the Broker Agent section (gated on `isEmbedded` in `SettingsView`) will now appear in Beta too — intended, since Beta now has a working agent. `BrokerAgentController` takes the variant-derived plist name.
8. **User-visible consequence, state it in the UI-facing docs or release notes**: with both variants registered, System Settings → General → Login Items & Extensions shows **two entries**, and launchd carries two services. That is correct behavior under this decision, not a bug — but a user running both will see it.

## The single-`batty`-on-PATH problem

This is the hardest sub-problem and gets explicit treatment, not a hand-wave.

`/usr/local/bin/batty` is a symlink into exactly one app bundle (`CLIInstaller`, verified). The embedded binary's baked (or bundle-resolved) names follow the bundle it ships in. Consequences:

- **One `batty` on PATH serves exactly one variant.** A Prod-installed `batty` drives Prod — deterministically, even while a Beta app is running and frontmost. It cannot reach Beta, and that is *correct*: no clobbering, no ambiguity, exit 2/3 semantics stay honest per variant. Do not try to make one symlink serve both variants by guessing from what is running — that reintroduces the cross-variant hazard this ticket exists to kill.
- **The real defect to fix**: both variants' Settings expose "Install CLI" targeting the *same* `/usr/local/bin/batty` path today, so installing from Beta silently flips which variant the PATH command drives (last writer wins). Recommended resolution: **Beta installs under a different name — `/usr/local/bin/batty-beta`** — by parameterizing `CLIInstaller`'s `installPath` per variant. Prod keeps `batty`; Beta is reachable by `batty-beta` (or by full bundle path without installing). #0268's four-state install inspection then inspects each variant's own path and never reports the other variant's symlink as its own.
- Alternatives considered: Beta's installer refusing to install (leaves Beta CLI reachable only by full bundle path — cheaper, but makes Beta XPC testing clumsy for exactly the people who run Beta); a runtime `--bundle-id`/environment override on a single binary (adds a footgun that reintroduces cross-variant driving; reject unless a concrete need appears).

## Verification expectations

Follow the #0270/#0272 pattern:

- **Unit tests for the derivation**: for each variant, the four strings are mutually consistent; across variants, every derived name *differs*; Prod's derived values are byte-identical to today's literals (the no-migration guarantee).
- **Plist assertions extending the `BrokerAgentPlistTests` pattern**: each shipped (or generated-from-template) plist asserted against its variant's `ServiceNames` values — `Label`, `MachServices` key, `BundleProgram`, `RunAtLoad` absent. If the template approach is chosen, the tests reproduce the substitution and assert both variants' outputs; the drift tests must still fail loudly on a corrupted or missing file (#0270 round 2 proved the `#filePath` seam fails safe — keep that property).
- `scripts/build.sh unit` and `scripts/build.sh` green; `otool -L | grep -c '@rpath'` → 0 on both embedded binaries in both variants' bundles.

**The decisive checks are runtime and need the user's sign-off** — they cannot be claimed from a green build:

- Both variants' agents register on one machine without colliding; both labels visible under `launchctl` independently.
- `batty ping` / `batty status` from each variant's CLI reach *that* variant's broker and app, with correct exit codes.
- Neither variant's launch or registration clobbers the other's — Prod's `batty status` still drives Prod while Beta is running, and vice versa.
- The `batty-beta` (or chosen) install path resolves the right variant.

**Trap warning, from #0270 (expect this during development):** `SMAppService` state outlives builds and is keyed to the bundle. Testing two variants' agents on one machine is *exactly* the situation that wedges launchd with multiple app copies on disk, and recovery can cost `sfltool resetbtm` and a reboot. `.status` can report `.enabled` while launchd has no such service — confirm with round trips (`batty ping`), never `.status`. Coordinate runtime testing with the user; never relaunch or kill a running Batty without asking.

Also note `Batty.xcodeproj/project.pbxproj` must not be hand-edited while Xcode has the project open (#0270's trap: Xcode rewrites it mid-edit), and `Configuration/Build.xcconfig` / `scripts/` remain restricted areas requiring explicit user confirmation.

## Out of scope

- Notarization of the (now two) embedded agents and the `--timestamp=none` gap — **#0273**, unchanged; this ticket does not block it, and Beta builds are not notarized anyway.
- Tier 3 read verbs — **#0274**, not blocked by this.
- Any change to `batty://` URL-scheme verbs (the scheme is registered per app; variant behavior there is whatever it is today).
- Lifecycle semantics — #0272's machinery (generations, reconnect budget, repair path) is untouched apart from name derivation flowing through it.
