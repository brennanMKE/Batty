## Description

**HIGH. Related to #0601 and #0604.** A divider drag calls `SplitTree.updateRatio` at pointer rate, and `updateRatio` reassigns `root`. `SplitTreeNode` embeds each split's `ratio` and is not `Equatable`, so every write notifies (and does so even when the clamp leaves the value unchanged). Everything that reads `root` directly or through `allPanes`, `visiblePanes`, `panePositions` or `panesSortedByColumnThenRow` re-renders per drag tick: the window root (through `isWindowSeeThrough`, #0608), the whole sidebar body (which iterates every Session), every sidebar Pane row, every `PaneView` of the Session, the main-menu `Commands` body, and Process Status panes. Only the one `DraggableSplitView` needs the ratio.

### Premises checked

- Confirmed: `SplitTreeNode` (`Model/SplitTree.swift:27-30`) is a non-`Equatable` indirect enum carrying `ratio: Double`. `SplitTree.root` is a plain `@Observable` stored property (`:128`). `updateRatio` (now `:722-725`, not `:709-712`) clamps and reassigns `root` unconditionally through the functional `SplitTreeNode.updatingRatio`. Under the toolchain rule in `docs/swiftui-observation-rules.md`, a non-`Equatable` value notifies on every write, so every drag tick and every clamped no-op notifies every reader of `root`.
- Every ratio writer goes through `updateRatio`: the divider drag (`Views/SplitContainerView.swift:84-86`), keyboard resize (`resizeFocusedSplit`, `:761-776`, reached from `BattyShortcuts`, `BattyCommands` and `CommandPaletteView`), and Project open (`ProjectTreeBuilder.swift:186`). Equalization (`rebalancingChain`/`rebalancedChain`, `:944-1041`) writes ratios only during a split (`splitFocusedPane`, `splitPane`), which also changes structure, so `root` legitimately changes there.
- Ratio readers outside the view: `SessionProjectCapture.swift:159-161` (Save Session as Project), `XPC/TopologyPayloadBuilder.swift:92-104` (CLI topology), and `SplitTreeNode.ratio(forSplitID:)` (keyboard resize, tests). All are pull-time snapshots. No source code uses `withObservationTracking` on the tree.
- Only `SplitNodeView` → `DraggableSplitView` needs the ratio in a view.

### Approach: a per-split observable ratio box (not a ratio dictionary)

The issue offers two options. Use the **per-split `@Observable` box**:
- The ratio stays next to its split, so there is one source of truth. There are no orphaned or missing dictionary entries to reconcile after close, swap or rebalance.
- The enum's arity is unchanged. Every existing `case .split(_, _, _, let l, let r)` match still compiles. The compiler flags every site that uses `ratio` as a `Double` (a `SplitRatio` can't be multiplied), so the implementer can't miss one.
- Tracking is per split: one drag tick invalidates only the `DraggableSplitView` that reads that box. A `[UUID: Double]` dictionary would invalidate every split view in the Session on each tick. In-place dictionary writes also notify even when equal (`ObservationEqualWriteSemanticsTests.inPlaceMutationsNotifyEvenWhenNothingChanges`).

Making `SplitTreeNode` `Equatable` is *not* part of the fix (each tick is a different value, as the issue says). Leave it non-`Equatable`.

## Fix

- `SplitTreeNode.split` now carries `ratio: SplitRatio`, a small `@Observable` main-actor box, instead of a `Double` (`Model/SplitTree.swift`). `updateRatio` clamps, looks up the box (`ratioBox(forSplitID:)`) and writes `box.value` only when it differs; it never assigns `root`. `updatingRatio(in:forID:to:)` is deleted. New splits (`splitFullDimension`, `inserting`) make a new box; `rebalancedChain` updates the existing box in place and keeps it in the rebuilt node, so the mounted divider view sees the new share.

## Rule violated

- `docs/swiftui-observation-rules.md`, "Observation semantics and dependency granularity": tracking is per property read; computed helpers broaden dependencies; a non-`Equatable` struct notifies on every write.
- swift-guidance `swiftui-observation.md`: a frequently written observed property should be narrow and `Equatable`; readers depend only on the facts they show.

## Evidence

- **Proven:** the read sites, the non-`Equatable` type and the unconditional write.
- **Inferred:** the per-tick cost. Gesture-origin writes are legal, so this is a cost problem, not a correctness one. Measure with `LayoutConvergenceProbe` while driving `updateRatio` in a loop.

## Fix direction

- Move ratios out of the structural tree: a separately observed `ratios: [UUID: Double]` on `SplitTree` read only by `SplitNodeView`/`DraggableSplitView`, or a small per-split `@Observable` ratio box. `root` then changes only on structural edits (split, close, swap, layout apply, equalize).
- Make `updateRatio` a no-op when the clamped value equals the current one.
- Making `SplitTreeNode` `Equatable` alone does not help: each drag tick is a different value.
- Keyboard resize (`SplitTree.ResizeDirection`) and equalization write ratios too and must go through the same storage.
