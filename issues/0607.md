# 0607 — SplitTree.root holds split ratios in a non-Equatable tree, so every divider-drag tick re-renders every reader of the tree's structure

| | |
|---|---|

## Description

**HIGH. Related to #0601 and #0604.** A divider drag calls `SplitTree.updateRatio` at pointer rate, and `updateRatio` reassigns `root`. `SplitTreeNode` embeds each split's `ratio` and is not `Equatable`, so every write notifies (and does so even when the clamp leaves the value unchanged). Everything that reads `root` directly or through `allPanes`, `visiblePanes`, `panePositions` or `panesSortedByColumnThenRow` re-renders per drag tick: the window root (through `isWindowSeeThrough`, #0608), the whole sidebar body (which iterates every Session), every sidebar Pane row, every `PaneView` of the Session, the main-menu `Commands` body, and Process Status panes. Only the one `DraggableSplitView` needs the ratio.

## Rule violated

- `docs/swiftui-observation-rules.md`, "Observation semantics and dependency granularity": tracking is per property read; computed helpers broaden dependencies; a non-`Equatable` struct notifies on every write.
- swift-guidance `swiftui-observation.md`: a frequently written observed property should be narrow and `Equatable`; readers depend only on the facts they show.

## Evidence

- **Proven:** the read sites, the non-`Equatable` type and the unconditional write.
- **Inferred:** the per-tick cost. Gesture-origin writes are legal, so this is a cost problem, not a correctness one. Measure with `LayoutConvergenceProbe` while driving `updateRatio` in a loop.

## Fix direction

- Move ratios out of the structural tree: a separately observed `ratios: [UUID: Double]` on `SplitTree` read only by `SplitNodeView`/`DraggableSplitView`, or a small per-split `@Observable` ratio box. `root` then changes only on structural edits (split, close, swap, layout apply, equalize).
- Make `updateRatio` a no-op when the clamped value equals the current one.
- Making `SplitTreeNode` `Equatable` alone does not help: each drag tick is a different value.
- Keyboard resize (`SplitTree.ResizeDirection`) and equalization write ratios too and must go through the same storage.

## Tests

- New in `SplitTreeResizeTests` (or a new `SplitTreeRatioObservationTests`): `ratioChangeDoesNotNotifyRootReaders()` — `withObservationTracking { _ = tree.allPanes }` must not fire on `updateRatio`; fails before, passes after. `clampedEqualRatioWriteDoesNotNotify()` with a non-default starting ratio pinned at the clamp. `structuralEditStillNotifiesRootReaders()` as the control.
