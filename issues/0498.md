## Description

**Reopened 2026-10-13 (round 2):** the follow-by-name actions must be visible controls inside the Process Status Pane, not items that exist only inside the "Choose Process…" pull-down and the picker's checkbox. See "Reopened (user, 2026-10-13)" and "Expected behavior — round 2: visible controls" below. Round 1 (the four behaviour refinements) is done and stays as recorded in the Resolution sections.

#0486 (on `release/1.2` as `814a3182`) added `Target.followingName`: the Process Status Pane shows the first live process with a name and re-resolves it whenever that process exits. Its two review rounds and its Gotchas left four refinements as follow-up candidates. None is a regression; each is a rough edge in the shipped feature:

1. **"Follow “<name>” by Name" is offered only while the pinned process is running.** The common case the user described is the opposite: a pinned app or CLI tool has just exited (`.exited`), the user is about to relaunch it, and the menu item is gone.
2. **About 1 s of Waiting flash and about 2 s of latency** on a fast relaunch: the tick that notices the loss only clears the pid; the next tick re-resolves.
3. **PID reuse.** The followed pid is a bare `pid_t`; if the kernel hands a dead followed pid to an unrelated process before the next tick, the Pane keeps sampling it.
4. **Following from a clicked row follows the `listOrder` first match, not the clicked process.** With several same-named processes, choosing the second row with "Follow by name" on shows the first one. The same happens with "Follow “<name>” by Name" from a pinned pid.

`main` gets the feature with #0494; the source issue is `git show release/1.2:issues/0486.md`.

## Expected behavior

1. **Store the listed name on `Snapshot`.** Add `listedName: String?` (the `bsdName`, read through `listedName(pid:)` where `identity` is read, on `pidChanged` is enough since `pbi_name` is stable for a pid). The menu item is offered for `.pinned` whenever `snapshot?.listedName` is non-nil and `runState` is `.running` **or** `.exited`; it retargets to `.followingName(listedName)` (seeded with the pid under item 4 when still alive; unseeded after `.exited`, so the next match is the successor). `retarget` already sets `runState = .running` (`:327`) before `startSampling()`, so the `.exited` guards there are not tripped; the test proves it.
2. **Re-resolve immediately on loss.** In the `.processNotFound` branch for `.followingName`, call `nameResolver(name)` at once; if it returns a live pid other than the lost one, sample it in the same tick (one bounded re-entry, never a loop), so a successor that already exists when the loss is noticed shows with no Waiting flash. Otherwise `.waiting` as today. At most one extra enumeration per loss; the steady running state still enumerates nothing.
3. **Guard against PID reuse.** Record the followed process as (pid, `startSeconds`, `startMicroseconds`, name), not a bare pid: `firstSameUserProcess(named:)` returns the `RunningProcess` (or a sibling that does). On every tick with a held pid, one `bsdInfo(pid:)` read confirms the start time and `bsdName` still match before `coreMetrics` runs; a mismatch is treated as a loss (item 2 then re-resolves). Document the per-tick cost against `docs/design/process-status-view.md` §4 (one `proc_pidinfo(PROC_PIDTBSDINFO)` call, on the order of microseconds). `.pinned` stays unguarded, as #0486 decided.
4. **The clicked row comes first.** Add a seed to the follow entry point (for example `retarget(to: .followingName(name), seedPid: pid)` or `followName(_:startingWith:)`) that sets the followed record to the chosen pid when it is alive and its `bsdName` equals the name; later re-resolutions use `listOrder` as today. `Target` is unchanged (public enum). Both the picker row and the "Follow “<name>” by Name" item pass their pid. `retarget(to:)` stays the only writer of `target`.

## Resolution notes

> 🟢 Resolved 2026-10-13. Follow-by-name in the Process Status Pane:
> - It is offered after the pinned process has exited.

## Root cause

These are #0486's four review follow-ups:
- The menu item required `.running` and a live `listedName(pid:)`.
- Loss only cleared the pid, so the next tick re-resolved.
- The followed pid was a bare `pid_t`.
- `retarget` dropped the clicked pid.

## Fix

- `Snapshot.listedName` stores the `bsdName`. The menu item shows for `.pinned` when the process is `.running` or `.exited`.
- On loss, `nameResolver` is called once. A live successor is sampled in the same tick through the real `coreMetricsProvider`, with one bounded re-entry.
- The followed process is held as pid, start time and name. On each tick, one `bsdInfo` read confirms it. A mismatch counts as a loss. `Resolution.successorPid` with `canReresolve: false` stops a second enumeration on reuse.
- A seed pid on the follow entry point makes the clicked row, or the pinned pid, come first. `Target` is unchanged.
- Docs: `docs/ui-features.md`, `docs/design/process-status-view.md` Mode C and `Help/03-panes.md`.
