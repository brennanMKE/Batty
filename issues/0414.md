## Description

`openURL(_:resolveAppBundle:)` in `BattyKit/Sources/batty/SessionCommand.swift` is how the CLI hands a `batty://` URL to the app. It is the only dispatch path for `batty new`, which is also the CLI's default subcommand: `NewSessionCommand.run()` calls it on both the `--no-wait` path and the wait path. The bundle-resolution step is injectable (`resolveAppBundle:`, #0361 round 3), and `SessionCommandOpenURLTests` (#0365) covers its failure branch. Once resolution succeeds, though, the function builds and runs a real `Process` inline, with no seam:

- `executableURL` is `/usr/bin/open`
- `arguments` is `["-a", bundleURL.path(percentEncoded: false), url.absoluteString]`
- if `process.run()` throws, it prints `batty: failed to open URL: …` and throws `ExitCode.failure`
- if `terminationStatus != 0`, it prints `batty: open exited with status N` and throws `ExitCode.failure`
- otherwise it returns normally

Any unit test that reaches this code launches or activates a real app bundle. So no test can pin any of the behavior above. `SessionCommandOpenURLTests`' own doc comment says so and stops at the failure branch. The argv is the part that matters most. The whole point of #0361 round 3 (B1) was to target the resolved bundle by **path** (`-a <bundlePath>`) instead of `-b <bundleIdentifier>`, which LaunchServices can resolve to any stale or other-variant bundle. Nothing stops a later edit from quietly reverting that.

## Expected behavior

`openURL` takes a process-runner injection seam whose default keeps today's behavior. It should follow the closure-default style that `AppConnectDance.resolveEndpoint` already uses for `launch: (URL) -> Bool = { AppLauncher.launch(bundleURL: $0) }`, and for `fetchEndpoint`/`sleep` (#0365). One possible shape is a closure taking the executable URL and argv, returning the termination status and throwing on spawn failure. Unit tests in `SessionCommandOpenURLTests` then pin:

1. **Argv.** On a successful resolve, the runner is invoked exactly once with `/usr/bin/open` and `["-a", <resolved bundle path>, <url.absoluteString>]`. There is no `-b` and no bundle identifier. The bundle path should contain a space (e.g. `…/Batty Beta.app`) so the test also proves the path is passed unencoded.
2. **Zero exit.** Termination status `0` returns without throwing.
3. **Non-zero exit.** A non-zero status throws `ExitCode.failure`.
4. **Spawn failure.** A runner that throws maps to `ExitCode.failure`.
5. **Failure branch unchanged.** The existing resolution-failure test also asserts that the runner is **never** called. Today that is only implied by the fact that the test doesn't launch anything.

## Notes

- `AppLauncher.launch(bundleURL:)` (`BattyKit/Sources/batty/AppLauncher.swift`) has the same inline `Process` shape (`open -g <path>`) and has no seam of its own either. Its injectability comes from its caller's `launch:` parameter. The seam added here could be shared with it, but this issue does not require that.
- `NewSessionCommand.run()` calls `openURL(url)` with defaults. Any future end-to-end unit test of `run()` needs this seam threaded through as well. That is one reason this issue and #0415 are separate but related.
- Keep comments to the *why* (AGENTS.md). The existing #0361 history on `openURL`'s doc comment stays as it is.

## Relation

- Follow-up of #0365, which added the `fetchEndpoint`/`sleep` seams to `AppConnectDance.resolveEndpoint` and `SessionCommandOpenURLTests`' failure-branch test, and stopped at this `Process` boundary.
- Sibling of #0415, the same untestability shape in `NewSessionCommand`'s direct `BrokerAppEndpointClient.fetchEndpoint` calls. The two can ship independently.
- Part of the CLI-reliability release. #0413's VM-only end-to-end suite covers the live side (a real `open` against a real bundle). This issue covers the unit-level contract.

## Resolution notes

> 🟢 Resolved 2026-09-23 — `SessionCommand.openURL` takes a `runProcess` seam, and tests now pin its exact argv (`-a <bundle path> <url>`, never `-b`) and exit-code mapping without spawning anything.

## Root cause

`openURL` built and ran a `Process` for `/usr/bin/open` inline, so only its bundle-resolution-failure branch (#0365's `SessionCommandOpenURLTests`) was testable.

## Fix

- `openURL` gained `runProcess: (URL, [String]) throws -> Int32`, defaulting to the same `run()` / `waitUntilExit()` / `terminationStatus` sequence the inline code used. Both production callers (`NewSessionCommand.swift`) pass no seams.
- Behavior unchanged: status 0 returns; non-zero status or a spawn throw logs as before and throws `ExitCode.failure`.
