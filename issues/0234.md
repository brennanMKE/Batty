# 0234 — Support multiple windows with a Shift-Cmd-N New Window shortcut

| | |
|---|---|

## Description

Batty currently supports a single window. Add multi-window support — especially valuable on multiple displays — with a New Window command on Shift-Cmd-N, customizable in Settings like other shortcuts (Cmd-N stays New Session). This change cuts across the riskiest parts of the app (terminal host, focus flow, persistence), so this is an **umbrella ticket**: the first deliverable is a design/audit phase, and implementation lands as separately-tracked child tickets carved out of it. No code ships directly on this ticket.

## Long Description

### Current state (audited 2026-06-11)

- **Scene:** `Batty/BattyApp.swift` uses a singular `Window(mainWindowTitle, id: "main")` scene, not `WindowGroup` (deliberate, per #0063). No second window can exist.
- **State:** `AppStateStore.shared` is a singleton with a single `selectedSessionID`, app-wide sidebar visibility, and the global `sessions: [SessionRuntime]` list. There is no per-window state container.
- **Terminal host:** `TerminalHostStore.shared` manages one persistent AppKit `hostView` installed in the one window. An `NSView` can live in only one window, so multi-window requires the host architecture to become window-aware (one host view per window, store managing all of them). This is the single highest-risk area — see Risks.
- **Shortcuts:** `ShortcutAction` (`BattyKit/Sources/BattyKit/Shortcuts/ShortcutAction.swift`) is the customizable-shortcut registry; adding a `.newWindow` case with a Shift-Cmd-N `defaultBinding` makes it automatically rebindable in Settings. **Shift-Cmd-N is verified free**: `toggleBellFeed` is now Shift-Cmd-B (the #0063 Gotchas note claiming Shift-Cmd-N is taken is stale), and the only `n` binding is Cmd-N → `.newSession`.
- **Persistence:** the Workspace schema (#0029) already models `windows: [WindowState]` — each `WindowState` has `windowFrame`, `isZoomed`, `sidebarCollapsed`, `selectedSessionID`, and its own `sessions` array — but `WorkspaceManager` reads only `windows[0]` on load and writes exactly one `WindowState` on save (#0030 noted per-window persistence as a follow-up).
- **Lifecycle:** `BattyAppDelegate.onAllSessionsClosed` terminates the app when the last *session* closes; with multiple windows the termination condition needs rethinking (last window vs last session).
- **Docs:** `Concepts.md` already promises multi-window ("supported for users with multiple displays… Each Window is independent — its own Sidebar list of Sessions, its own selected Session"), and PRD §6.2/§6.5 describes it, but it was never implemented and the docs' Cmd-N reference predates #0063.

### Key design decisions for the planning phase

1. **Session ownership: partitioned vs shared.** The persistence schema nests `sessions` *under* `WindowState`, and Concepts.md says each window has "its own Sidebar list of Sessions" — both point to **partitioned** (a session lives in exactly one window), which also matches how terminal multiplexers behave. The alternative (one global list, every window shows all sessions, per-window selection only) contradicts the schema. Decide explicitly; everything downstream depends on it.
2. **Terminal host topology.** One `TerminalHostView` per window, with `TerminalHostStore` managing the set. Moving a session between windows (if in scope at all — candidate for a later child) means reparenting `AppTerminalView`s across hosts without violating the view-hierarchy rules. Surfaces must survive window open/close/move; closing a window with live sessions must either be blocked, confirm, or migrate sessions — decide which.
3. **Scene type.** `WindowGroup` with per-window state (an identity the window scene binds to) vs programmatic `Window` scenes. Restoration of N windows with frames on the right displays must work with whichever is chosen.
4. **What stays global:** the surface registry, `SessionNameCache`, theme, `ShortcutsStore`, and the bell feed store. Bell-feed click-to-jump must route to (and key) the window owning the target session.

### Phases (carve into child tickets when work begins; re-audit between phases)

1. **Design + docs:** per-window state model, session ownership decision, terminal-host multi-window design; update `docs/view-hierarchy.md` and `Concepts.md` *before* code. Output: a design doc the later children reference.
2. **Per-window state container, single-window behavior unchanged:** introduce the window-state layer (selection, sidebar) around `AppStateStore` with exactly one window — a pure refactor gated on zero behavior change, full unit + UI test pass.
3. **Window-aware terminal host:** host view per window; rules in `docs/view-hierarchy.md` extended for multi-host.
4. **New Window action:** `.newWindow` in `ShortcutAction` (default Shift-Cmd-N), menu item, scene changes; new windows open empty with one fresh session.
5. **Persistence:** save all windows, restore all windows with frames/zoom/sidebar/selection; migration keeps existing single-window workspaces loading unchanged.
6. **Cross-window behaviors:** bell-feed routing, app termination semantics, (optional, separate) moving sessions between windows.
7. **Regression pass:** full UI test suite on the Mac mini plus the manual checklist in `docs/terminal-pane-requirements.md` (pointer input, keyboard, IME, file/text drop) in *both* windows.

### Risks / regression vectors (why this umbrella exists)

- **Surface destruction:** the surface registry rule — view rebuilds must never destroy surfaces — now has window open/close/restore as new rebuild triggers. A closing window must not tear down surfaces that should migrate or persist.
- **Observation rules (#0227/#0229/#0230 class):** window key/main changes and host installation run inside AppKit layout/responder machinery. Per `docs/swiftui-observation-rules.md` (binding), focus/selection writes triggered by window-origin flips must be restructured, never Task-hopped. Every phase touching focus or selection re-reads that doc first.
- **Terminal-pane behaviors:** `docs/terminal-pane-requirements.md` checklist must pass per-window; #0143 documents what breaks when this is skipped.
- **Persistence migration:** schema already allows multiple windows, but round-tripping must not lose sessions for existing users; `windows[0]`-only reading is load-bearing today.
- **UI tests:** `BattyUITests` (60 tests) assume one window; expect updates and run the full suite (Mac mini) before each phase resolves.

## Steps to reproduce

1. Open Batty on a Mac with two displays.
2. Try to open a second window (File menu, Shift-Cmd-N, dock menu).

## Expected behavior

Shift-Cmd-N (customizable in Settings → Keyboard) opens a new window with its own sidebar of sessions and its own selection; windows restore to their displays on relaunch; Cmd-N keeps creating a new session in the focused window. All existing single-window behavior — terminal input, focus, drops, IME, bell feed, persistence — is unchanged.

## Actual behavior

The app is a single `Window` scene; no second window can be opened by any means.
