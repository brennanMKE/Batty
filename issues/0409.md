## Description

**Severity: high — data loss.** The user's Prod Batty 1.1.0 (build 20260821, `co.sstools.Batty`, `/Applications/Batty.app`, running since 2026-08-21 20:21) crashed at 2026-09-12 17:06:06 PDT, killing all live Terminal Sessions. Nothing in Batty's own test flow touched Prod. The trigger was an XCUITest run in a *different* project: a Claude subagent working in `Changeover` ran `xcodebuild -project Changeover.xcodeproj -scheme Changeover -destination 'platform=macOS' test`, whose scheme includes `ChangeoverUITests`. XCUITest's automation session enumerated running apps via Accessibility, singled out Batty, asked `testmanagerd` to bootstrap the `XCTAutomationSupport` backend into the Batty process, and Batty segfaulted inside that framework's session initializer about four seconds later.

User directive on filing: **"XCTAutomationSupport should never terminate the Batty app. We only test with the beta!"**

### Crash report facts (verified against the attached `.ips`)

- `EXC_BAD_ACCESS` / `SIGSEGV`, `KERN_INVALID_ADDRESS at 0x0000000000000020`; `termination.byProc` = `exc handler`. A near-null dereference (offset `0x20` from a null base — `x0` was `0x0` in the faulting thread's register state).
- Faulting thread **index 154**, queue `com.apple.root.user-initiated-qos` (a libdispatch global-queue worker). Its entire stack: `__66-[XCTAutomationSession initWithAccessibilityFramework:dataSource:]_block_invoke + 200` (`XCTAutomationSupport`) → `_dispatch_call_block_and_release` → `_dispatch_client_callout` → `_dispatch_root_queue_drain` → `_dispatch_worker_thread2` → `_pthread_wqthread` → `start_wqthread`. **No Batty, libghostty, AppKit, or SwiftUI frames anywhere on the faulting thread.**
- The main thread was idle in `-[NSApplication run]` / `__CFRunLoopRun` / `mach_msg2_trap` at capture time.
- `XCTAutomationSupport` was loaded from `/System/Library/PrivateFrameworks/XCTAutomationSupport.framework/Versions/A/XCTAutomationSupport` (version 26.6, build 24901). **Batty.app does not link or bundle XCTest**: `otool -L /Applications/Batty.app/Contents/MacOS/Batty | grep -i xct` matches nothing and `find Batty.app -iname '*XCT*'` finds nothing. It was injected by the system.
- The process had **201 threads** at crash time. The breakdown is exactly 38 each of libghostty's per-surface threads (`renderer`, `io`, `io-reader`, `io-gather`, `cf_release` = 190) plus the main thread, `com.apple.NSEventThread`, `com.apple.SwiftUI.AsyncRenderer`, `CVDisplayLink`, six unnamed threads, and the one dispatch worker that crashed. That is consistent with **38 live Terminal Sessions** at the time. Recorded as an observation only — nothing in the report ties the thread count or the surface count to the fault.
- macOS 26.6.2 (25G83), `Mac16,11`, arm64; only one Batty crash report exists on this machine (`~/Library/Logs/DiagnosticReports/Batty-2026-09-12-170611.ips`, copied verbatim as the attachment below).

## Steps to reproduce

Repro sketch — not yet attempted; the implementer should confirm whether this reproduces at all before hunting for a mitigation:

1. Launch Batty Beta (`./build.sh package` or run from Xcode) and open several Sessions with several Panes and Tabs each, so there are tens of live Terminal Sessions (the crashed Prod instance had ~38). Leave Batty as the frontmost app.
2. From a separate, unrelated Xcode project that has a macOS UI test target (any trivial `XCUIApplication().launch()` test — `~/Developer/brennanMKE/Changeover` with its `ChangeoverUITests` target is the known trigger), run `xcodebuild -project <X>.xcodeproj -scheme <X> -destination 'platform=macOS' test`.
3. Watch `log stream --predicate 'process == "testmanagerd"'` for "Setting up AX for pid <Batty PID>" and "requested endpoint for process with pid <Batty PID>", and watch whether Batty Beta crashes within a few seconds of the endpoint request.
4. Vary: Batty not frontmost; Batty with a single Terminal Session; Batty with the Sidebar hidden / a non-terminal-kind Pane focused — to find what, if anything, in Batty's state makes the session init fault.

## Expected behavior

An external XCUITest / accessibility automation session from another app or project must never crash Batty — least of all Prod with live Terminal Sessions. Whatever an automation client asks of Batty's accessibility tree, the worst outcome should be a slow or incomplete answer, not process termination.

## Actual behavior

Within four seconds of `testmanagerd` bootstrapping `XCTAutomationSupport` into the Prod Batty process on behalf of an unrelated project's UI test runner, Batty segfaulted on a dispatch worker thread inside `-[XCTAutomationSession initWithAccessibilityFramework:dataSource:]_block_invoke`, and all 38 live Terminal Sessions (and their shell processes) were lost.

## Notes

### Open questions for the implementer (not conclusions)

1. **Is this an Apple bug that Batty merely provokes, or something in Batty's accessibility exposure?** The faulting frame is entirely inside Apple's private framework with a null base pointer. Candidates worth ruling in or out, in the Batty accessibility tree that `XCTAutomationSession` walks on init:
   - The terminal host: `TerminalHostView` (`BattyKit/Sources/BattyKit/Views/TerminalHostView.swift`) is a persistent `NSView` added directly to the window's `contentView`, outside the SwiftUI hierarchy, holding one `AppTerminalView` per Tab (libghostty-spm's `Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView.swift`, an `open class AppTerminalView: NSView`). Non-active terminal views are kept in the host but `isHidden`. With ~38 of these, does the AX tree expose 38 opaque `NSView`s with no role, and does `XCTAutomationSession` cope with that?
   - Element count / tree shape: SwiftUI `NavigationSplitView` + Sidebar `List` + Split tree + per-Pane Tab bars, over a persistent AppKit overlay. Does init do a full-tree snapshot?
   - Elements deallocated mid-query: Tabs closing, Panes collapsing, or Sessions switching while the off-main-thread session init is walking the tree. Nothing in the log shows the user doing anything in the 4 s window, but the crashed Prod had 38 shells running that could have been changing titles.
   - Off-main-thread accessibility access: the crash is on a `user-initiated-qos` dispatch worker, not the main thread. If XCTAutomationSupport's data source reads NSAccessibility off-main, any Batty-side accessibility value that is computed from main-actor state is a candidate.
2. **Does it reproduce at all** with the repro sketch above, and does it depend on the number of live Terminal Sessions, on Batty being frontmost, or on which Pane kind is focused?
3. **If it is purely an Apple bug**, what mitigation is available? Ideas to evaluate, none verified: making the terminal host / `AppTerminalView` subtree an explicit accessibility element with a role (so a UI-test client gets a well-formed leaf instead of a raw view), `accessibilityChildren`-pruning the hidden terminal views, or documenting "don't run any XCUITest target while Prod Batty has live work" as a known hazard if nothing on the app side helps.
4. **Should Batty's own UI test suite be re-examined?** It launches its own host app via `XCUIApplication().launch()` in `BattyUITests/Support/BattyUITestHarness.swift` (lines 19–22 and 36–40), and per `CLAUDE.md` runs only against the Beta build — but the same `kAXClientTypeXCUITest` machinery is what attached to Prod here. Whether a Batty UI-test run can also reach a *Prod* instance that happens to be running is worth checking as part of this issue (the user's directive is that it must not).

### Accessibility customizations that exist in Batty today (verified by grep at filing, `main` tip `7c67796`)

There are **no** `NSAccessibility*` protocol overrides, no `isAccessibilityElement`, `accessibilityRole`, `accessibilityChildren`, or `accessibilityRepresentation` anywhere in `Batty/` or `BattyKit/Sources/`. Everything is SwiftUI modifiers:

- `BattyKit/Sources/BattyKit/Views/PaneView.swift:215` — `.accessibilityIdentifier("tab-chip.<title>")` on each `BattyTabChip`; `:225–226` — `.accessibilityElement(children: .contain)` + `.accessibilityIdentifier("tab-bar.<paneID>")` on the Tab bar (the comment there explains that without `.contain`, SwiftUI on macOS folds the bar into a single leaf and the identifier propagates to every child Button).
- `BattyKit/Sources/BattyKit/Views/TerminalPlaceholderView.swift:61–63` — `.accessibilityElement()`, `.accessibilityLabel(isPaneFocused ? "focused" : "unfocused")`, `.accessibilityIdentifier("pane-terminal.<paneID>")` on the transparent `Color.clear` placeholder that reports geometry for the AppKit terminal host. This is the only accessibility element that stands in for a Terminal Session; the real `AppTerminalView` under it carries none.
- `BattyKit/Sources/BattyKit/Views/OpenQuicklyView.swift:118` — `.accessibilityElement(children: .combine)` on a result row.
- Identifier / label / value modifiers only (no element-shape changes) in `BellFeedView.swift`, `CommandPaletteView.swift`, `GitStatusPaneView.swift`, `LMStudioDashboardView.swift`, `ProcessStatusPaneView.swift`, `SessionColorPickerView.swift`, `SessionDetailView.swift`, `SessionSidebarView.swift`, `SystemMetricsPaneView.swift` (all under `BattyKit/Sources/BattyKit/Views/`).
- `docs/ui-features.md` (the "Accessibility identifiers" subsections, e.g. lines 67–74) documents these identifiers as the contract Batty's own UI tests assert against.
- libghostty-spm's AppKit `AppTerminalView` has no accessibility code either; the only accessibility references in that package are in its Example apps and the UIKit path. Checked against the revision resolved for the Beta build (`a2565ccf047c03c74a59dd7c16a8fac7c477852f` in `BattyKit/Package.resolved`); Prod 1.1.0 may have been built against a different revision — not verified.
