## Description

**Severity: high — data loss.** The user's Prod Batty 1.1.0 (build 20260821, `co.sstools.Batty`, `/Applications/Batty.app`, running since 2026-08-21 20:21) crashed at 2026-09-12 17:06:06 PDT, killing all live Terminal Sessions. Nothing in Batty's own test flow touched Prod. The trigger was an XCUITest run in a *different* project: a Claude subagent working in `Changeover` ran `xcodebuild -project Changeover.xcodeproj -scheme Changeover -destination 'platform=macOS' test`, whose scheme includes `ChangeoverUITests`. XCUITest's automation session enumerated running apps via Accessibility, singled out Batty, asked `testmanagerd` to bootstrap the `XCTAutomationSupport` backend into the Batty process, and Batty segfaulted inside that framework's session initializer about four seconds later.

User directive on filing: **"XCTAutomationSupport should never terminate the Batty app. We only test with the beta!"**

### Crash report facts (verified against the attached `.ips`)

- `EXC_BAD_ACCESS` / `SIGSEGV`, `KERN_INVALID_ADDRESS at 0x0000000000000020`; `termination.byProc` = `exc handler`. A near-null dereference (offset `0x20` from a null base — `x0` was `0x0` in the faulting thread's register state).
- Faulting thread **index 154**, queue `com.apple.root.user-initiated-qos` (a libdispatch global-queue worker). Its entire stack: `__66-[XCTAutomationSession initWithAccessibilityFramework:dataSource:]_block_invoke + 200` (`XCTAutomationSupport`) → `_dispatch_call_block_and_release` → `_dispatch_client_callout` → `_dispatch_root_queue_drain` → `_dispatch_worker_thread2` → `_pthread_wqthread` → `start_wqthread`. **No Batty, libghostty, AppKit, or SwiftUI frames anywhere on the faulting thread.**
- The main thread was idle in `-[NSApplication run]` / `__CFRunLoopRun` / `mach_msg2_trap` at capture time.
- `XCTAutomationSupport` was loaded from `/System/Library/PrivateFrameworks/XCTAutomationSupport.framework/Versions/A/XCTAutomationSupport` (version 26.6, build 24901). **Batty.app does not link or bundle XCTest**: `otool -L /Applications/Batty.app/Contents/MacOS/Batty | grep -i xct` matches nothing and `find Batty.app -iname '*XCT*'` finds nothing. It was injected by the system.
- The process had **201 threads** at crash time. The breakdown is exactly 38 each of libghostty's per-surface threads (`renderer`, `io`, `io-reader`, `io-gather`, `cf_release` = 190) plus the main thread, `com.apple.NSEventThread`, `com.apple.SwiftUI.AsyncRenderer`, `CVDisplayLink`, six unnamed threads, and the one dispatch worker that crashed. That is consistent with **38 live Terminal Sessions** at the time. Recorded as an observation only — nothing in the report ties the thread count or the surface count to the fault.
- macOS 26.6.2 (25G83), `Mac16,11`, arm64; only one Batty crash report exists on this machine (`~/Library/Logs/DiagnosticReports/Batty-2026-09-12-170611.ips`, copied verbatim as the attachment below).

## Expected behavior

An external XCUITest / accessibility automation session from another app or project must never crash Batty — least of all Prod with live Terminal Sessions. Whatever an automation client asks of Batty's accessibility tree, the worst outcome should be a slow or incomplete answer, not process termination.

## Actual behavior

Within four seconds of `testmanagerd` bootstrapping `XCTAutomationSupport` into the Prod Batty process on behalf of an unrelated project's UI test runner, Batty segfaulted on a dispatch worker thread inside `-[XCTAutomationSession initWithAccessibilityFramework:dataSource:]_block_invoke`, and all 38 live Terminal Sessions (and their shell processes) were lost.

## Notes

### Open questions for the implementer (not conclusions)

1. **Is this an Apple bug that Batty merely provokes, or something in Batty's accessibility exposure?** The faulting frame is entirely inside Apple's private framework with a null base pointer. Candidates worth ruling in or out, in the Batty accessibility tree that `XCTAutomationSession` walks on init:
   - The terminal host: `TerminalHostView` (`BattyKit/Sources/BattyKit/Views/TerminalHostView.swift`) is a persistent `NSView` added directly to the window's `contentView`, outside the SwiftUI hierarchy, holding one `AppTerminalView` per Tab (libghostty-spm's `Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView.swift`, an `open class AppTerminalView: NSView`). Non-active terminal views are kept in the host but `isHidden`. With ~38 of these, does the AX tree expose 38 opaque `NSView`s with no role, and does `XCTAutomationSession` cope with that?
   - Element count / tree shape: SwiftUI `NavigationSplitView` + Sidebar `List` + Split tree + per-Pane Tab bars, over a persistent AppKit overlay. Does init do a full-tree snapshot?
   - Elements deallocated mid-query: Tabs closing, Panes collapsing, or Sessions switching while the off-main-thread session init is walking the tree. Nothing in the log shows the user doing anything in the 4 s window, but the crashed Prod had 38 shells running that could have been changing titles.
   - Off-main-thread accessibility access: the crash is on a `user-initiated-qos` dispatch worker, not the main thread. If XCTAutomationSupport's data source reads NSAccessibility off-main, any Batty-side accessibility value that is computed from main-actor state is a candidate.
2. **Does it reproduce at all** with the repro sketch above, and does it depend on the number of live Terminal Sessions, on Batty being frontmost, or on which Pane kind is focused?
3. **If it is purely an Apple bug**, what mitigation is available? Ideas to evaluate, none verified: making the terminal host / `AppTerminalView` subtree an explicit accessibility element with a role (so a UI-test client gets a well-formed leaf instead of a raw view), `accessibilityChildren`-pruning the hidden terminal views, or documenting "don't run any XCUITest target while Prod Batty has live work" as a known hazard if nothing on the app side helps.
4. **Should Batty's own UI test suite be re-examined?** It launches its own host app via `XCUIApplication().launch()` in `BattyUITests/Support/BattyUITestHarness.swift` (lines 19–22 and 36–40), and per `CLAUDE.md` runs only against the Beta build — but the same `kAXClientTypeXCUITest` machinery is what attached to Prod here. Whether a Batty UI-test run can also reach a *Prod* instance that happens to be running is worth checking as part of this issue (the user's directive is that it must not).

### Accessibility customizations that exist in Batty today (verified by grep at filing, `main` tip `7c67796`)

There are **no** `NSAccessibility*` protocol overrides, no `isAccessibilityElement`, `accessibilityRole`, `accessibilityChildren`, or `accessibilityRepresentation` anywhere in `Batty/` or `BattyKit/Sources/`. Everything is SwiftUI modifiers:

- `BattyKit/Sources/BattyKit/Views/PaneView.swift:215` — `.accessibilityIdentifier("tab-chip.<title>")` on each `BattyTabChip`; `:225–226` — `.accessibilityElement(children: .contain)` + `.accessibilityIdentifier("tab-bar.<paneID>")` on the Tab bar (the comment there explains that without `.contain`, SwiftUI on macOS folds the bar into a single leaf and the identifier propagates to every child Button).
- `BattyKit/Sources/BattyKit/Views/TerminalPlaceholderView.swift:61–63` — `.accessibilityElement()`, `.accessibilityLabel(isPaneFocused ? "focused" : "unfocused")`, `.accessibilityIdentifier("pane-terminal.<paneID>")` on the transparent `Color.clear` placeholder that reports geometry for the AppKit terminal host. This is the only accessibility element that stands in for a Terminal Session; the real `AppTerminalView` under it carries none.
- `BattyKit/Sources/BattyKit/Views/OpenQuicklyView.swift:118` — `.accessibilityElement(children: .combine)` on a result row.
- Identifier / label / value modifiers only (no element-shape changes) in `BellFeedView.swift`, `CommandPaletteView.swift`, `GitStatusPaneView.swift`, `LMStudioDashboardView.swift`, `ProcessStatusPaneView.swift`, `SessionColorPickerView.swift`, `SessionDetailView.swift`, `SessionSidebarView.swift`, `SystemMetricsPaneView.swift` (all under `BattyKit/Sources/BattyKit/Views/`).
- `docs/ui-features.md` (the "Accessibility identifiers" subsections, e.g. lines 67–74) documents these identifiers as the contract Batty's own UI tests assert against.
- libghostty-spm's AppKit `AppTerminalView` has no accessibility code either; the only accessibility references in that package are in its Example apps and the UIKit path. Checked against the revision resolved for the Beta build (`a2565ccf047c03c74a59dd7c16a8fac7c477852f` in `BattyKit/Package.resolved`); Prod 1.1.0 may have been built against a different revision — not verified.

## Plan

Ordered. Nothing here is implemented yet; status stays `open`. Steps 1–2 are diagnosis and gate step 3 — do not ship a mitigation for a crash that has not been reproduced once, because there is no way to tell whether it worked.

### Step 1 — Reproduce deterministically

**Goal:** a repeatable harness that either crashes Batty Beta on demand or shows the crash does not reproduce under any of the varied conditions. Never point any of this at Prod: an XCUITest session is not contained to the app under test — this issue is the proof that it can kill other running apps — so run the harness only on a Mac with nothing to lose (the Mac mini per `CLAUDE.md`'s UI-test rule), with Prod Batty quit, with no other live terminal work open, and only with the user's explicit go-ahead for each run.

1. **Build a throwaway XCUITest project outside the Batty repo** (e.g. `/tmp/AXProbe` — a new macOS app from the Xcode template with its UI test target; nothing to commit). Its one test is the template's `XCUIApplication().launch()`. The Changeover target (`~/Developer/brennanMKE/Changeover/ChangeoverUITests`) is the known trigger and can serve as a control, but a fresh project proves the trigger is generic, not Changeover-specific.
2. **Populate Batty Beta with ~38 Terminal Sessions** to match the crashed instance. Two routes, both already in the repo:
   - Scripted launch: `BattyUITests/Support/BattyUITestHarness.swift`'s `launchBatty(script:)` feeds `BATTY_UI_TEST_SCRIPT` to `UITestDriver` (`BattyKit/Sources/BattyKit/Testing/UITestDriver.swift`), whose intents include `createSession`, `createTab`, `splitHorizontal`, `splitVertical`, and `applyLayout` (e.g. `twoByTwoGrid`, as `BattyUITests/DragDropTests.swift` uses). But that launches Batty *from* an XCUITest session, which conflates the trigger with the setup — use it only for the regression guard in step 4.
   - Preferred for the repro: launch `Batty Beta.app` normally and drive it from the CLI — `batty-beta new <path>` creates a Session, and the `split` / `tab` subcommands add Panes and Tabs (`docs/batty-cli-agent-workflows.md`; the Beta CLI installs as `/usr/local/bin/batty-beta`, `docs/batty-cli-install.md`). Confirm the count with `batty-beta list --json` and `ps -M <pid> | wc -l` (expect ~5 threads per surface).
3. **Make Batty Beta frontmost**, then run `xcodebuild -project AXProbe.xcodeproj -scheme AXProbe -destination 'platform=macOS' test` from a shell that is *not* inside Batty. Keep `log stream --predicate 'process == "testmanagerd" OR subsystem == "com.apple.dt.xctest"' --style compact` running in a second terminal outside Batty.
4. **Read the log for the two lines that mattered here:** "Setting up AX for pid <BetaPID>" and "requested endpoint for process with pid <BetaPID>, preferredBackendPath …/XCTAutomationSupport.framework". If the endpoint request never targets Batty, the run was not a valid trial — the crash needs the bootstrap, not just AX enumeration.
5. **Isolate the variables, one per run, ~3 runs each** (the 17:10–17:11 sessions did not crash the relaunched Prod, so a single negative means nothing):
   - *Frontmost:* Batty frontmost vs. Finder frontmost. Prediction from the log: Batty only gets the endpoint request when frontmost.
   - *Surface count:* 1 vs. ~10 vs. ~38 Terminal Sessions.
   - *Tree shape:* Sidebar shown vs. hidden (Cmd-B); focused Pane `.terminal`-kind vs. a `git-status` Pane; all Terminal Sessions in one Session vs. spread across many Sessions (only the selected Session's Panes are on screen; the rest are `isHidden` in `TerminalHostView`).
   - *Activity:* idle shells vs. shells producing output (e.g. `yes | head -c 100M` in several Tabs) during the run.
6. **Record every run** (variables, endpoint requested y/n, crash y/n, `.ips` path) in this issue's Notes.

**Verification:** a table of runs with at least one reproduced crash, or a documented set of negatives across all variables. **Uncertain:** whether it reproduces at all — the crash may need a specific timing between AX enumeration and Batty's state changing, in which case step 2's idle-vs-active variable is the lever.

### Step 2 — Diagnose

**Goal:** name the mechanism, or establish that it is opaque Apple code with no Batty-side input.

- **Capture on every crash:** the `.ips` (already symbolicated for system frames; Batty frames, if any appear, symbolicate against the Beta dSYM in DerivedData), the `log stream` output from step 1 with a ±10 s window around `captureTime`, and — before the run — an Accessibility Inspector snapshot of Batty's tree (Xcode → Open Developer Tool → Accessibility Inspector, target Batty Beta, expand the window) noting the element count and what the `TerminalHostView` / `AppTerminalView` subtree reports (role, children, whether hidden terminal views are listed).
- **Hypotheses to rule in or out, in order of cost:**
  1. *Apple bug with no Batty input.* If a trivial AppKit app with no custom accessibility, made frontmost, also dies under the same probe, stop here and go to step 3's Radar item. Cheapest test; do it first.
  2. *libghostty surface views expose nothing or a huge tree.* `AppTerminalView` (libghostty-spm, `Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView.swift`) has no accessibility code; `TerminalHostView` (`BattyKit/Sources/BattyKit/Views/TerminalHostView.swift`) has none either. Check in Accessibility Inspector whether the ~38 hidden `AppTerminalView`s appear as roleless children of the window and whether the surface-count variable in step 1 correlates.
  3. *Elements freed mid-query.* Correlates with the idle-vs-active variable. SwiftUI rebuilds `PaneView` Tab chips on title changes (`PaneView.swift:215`), so shells changing titles during the walk is the concrete candidate.
  4. *Accessibility values computed off the main thread.* The faulting thread is a dispatch worker. `TerminalPlaceholderView.swift:61–63` computes `accessibilityLabel` from `isPaneFocused`, main-actor state; whether XCTAutomationSupport's data source reads it off-main is unknown. A `Thread.isMainThread` assertion in a temporary `accessibilityLabel` override on `TerminalHostView` during repro runs would answer it — throwaway instrumentation, not committed.
- **Verification:** a written finding in this issue's Notes naming which hypothesis survived, with the run table and inspector snapshot as evidence. **Uncertain:** hypotheses 3–4 may be indistinguishable from the outside if the fault is inside Apple's bootstrap before any Batty accessibility method is called (the faulting block is the *session initializer*, which may not have touched Batty's tree yet).

### Step 3 — Batty mitigations, ranked by confidence and risk

Only after step 2. Nothing here may write observed state from `body`/`onChange`, and nothing may call `addSubview`/`makeFirstResponder` from SwiftUI callbacks (`docs/swiftui-observation-rules.md`, "AppKit interop hazards in Batty").

### Step 4 — Regression guard

**Goal:** pin whatever step 3 lands so a later accessibility change cannot silently reopen it, without adding a machine-locking UI test to the routine loop.

- **Unit-level (runs in `./build.sh unit`, every commit):** if rank 1 lands, a `BattyKitTests` test that instantiates `TerminalHostView`, adds two terminal views (one hidden), and asserts the host's `accessibilityChildren()` / each view's `accessibilityRole()` and `isAccessibilityElement()` — pure AppKit attribute reads, no window needed. Lives in `BattyKit/Tests/BattyKitTests/`.
- **UI-level (`./build.sh ui`, Mac mini only, release preflight):** one new class in `BattyUITests/`, e.g. `AccessibilityTreeTests`, launched via `BattyUITestHarness.launchBatty(script:)` with `applyLayout: twoByTwoGrid` plus several `createTab` intents, that walks `app.windows.firstMatch.descendants(matching: .any)` and asserts the walk completes and the app is still `.runningForeground`. This exercises the same `kAXClientTypeXCUITest` path from inside Batty's own session. It cannot reproduce the *external-frontmost-app* bootstrap (the app under test is bootstrapped differently from a bystander), so it is a smoke check, not a repro.
- **Scripted external probe (manual, documented, not in CI):** keep the step 1 probe project's recipe in this issue's Notes (or `docs/`) as the pre-release check to run on the Mac mini alongside `./build.sh ui`: Beta with ~38 surfaces, frontmost, external XCUITest run, assert Batty survives. This is the only check that covers the actual trigger.

**Verification:** the new unit test is named in the run output of `./build.sh unit`; the UI class runs green once on the Mac mini. **Uncertain:** whether the UI-level smoke check adds signal beyond the unit test — if step 2 shows the tree is never consulted before the fault, drop it and keep only the manual probe.

### Step 5 — Process guard

**Goal:** no agent on this machine starts an XCUITest run without the user approving that specific run, regardless of project.
