# 0299 — `tools/memsample.sh` undercounts Beta-owned IOSurfaces because vmmap truncates `SurfaceID:` on long rows, turning passing invariants into false FAILs

| | |
|---|---|
| **Status** | open |
| **Module** | Build |
| **Platform** | macOS |
| **First seen** | 2026-08-04 |

## Description

`compute_target_owner_stats` in `tools/memsample.sh` selects IOSurface detail rows with `/SurfaceID:/` (`tools/memsample.sh:227`). But `vmmap` truncates that detail column when the line runs long, eliding the *front* of the field: the row prints `...aceID: 0x109 …` instead of `SurfaceID: 0x109 …`, and the awk pattern silently drops it. The dropped rows are excluded from `SURFACE_ROWS` entirely, so every derived stat is wrong at once: `batty_iosurfaces`, `batty_windowserver_shared`, `OWNER_GEO_TABLE`, and `OWNER_HISTOGRAM`.

The truncation is not random — it hits exactly the rows that matter most on the Beta target. The line only runs long enough to truncate when the owner label is long — `'Batty Beta.debug.dylib'` (22 chars) versus release's `'Batty'` (5) — **and** the row also carries the `, shared with WindowServer[607]` suffix. So the undercount lands entirely on Beta-owned, WindowServer-shared rows: the numerator of invariant 1, and disproportionately the shared count of invariant 2.

**Verified live 2026-08-04** against both running instances (filer, read-only `vmmap` passes):

- Beta (Debug build, owner `'Batty Beta.debug.dylib'`): `grep -c 'SurfaceID:'` matched **61** rows; **6** additional rows were truncated to `...aceID:` — all 6 owned by `'Batty Beta.debug.dylib'`, all 6 `shared with WindowServer`. The never-truncated geometry+owner tail on `^IOSurface` rows matched **67** = 61 + 6.
- Release (`/Applications/Batty.app`, owner `'Batty'`): 103 `SurfaceID:` rows, **0** truncated, tail pattern also 103 — fully consistent.

Example truncated row (live, Beta pid):

```
IOSurface   130a28000-130b38000  [ 1088K ...] rw-/rw- SM=SHM PURGE=N  ...aceID: 0x109  1265x216 (BGRA) 1088K  'Batty Beta.debug.dylib', shared with WindowServer[607]
```

**Measured consequence (2026-08-03, live Beta instance):** the harness reported 60 IOSurfaces / 20 layers / 16 WindowServer-shared; corrected values are **66 / 22 / 22**. With the correct numbers all three invariants pass exactly — 66/3 = 22.00 layers; ws-shared = 22 = `layers`, the bottom of the `[22, 44]` range; 1040 K atlas count = 66 = IOSurface count. As reported, **two of the three invariants falsely FAIL** (60 is a multiple of 3, so invariant 1 happened to pass that day with a wrong layer count of 20; 16 shared fell below the `[20, 40]` range; 66 atlases ≠ 60 surfaces). On the 2026-08-04 live check the miscount (61) isn't even a multiple of 3, so invariant 1 FAILs outright too.

This makes the harness a **false-signal generator**, exactly the class #0291's own review round 1 blocked on once already (the strict-equality invariant 2). Worse, `tools/README.md` explicitly instructs the reader to treat a FAIL as "a finding to report, never as a bug in the harness to paper over" — correct advice sitting on top of a harness bug that manufactures FAILs.

## Why this gates #0285's experiments

The undercount affects **only the Beta target** — which is precisely the build #0291's Notes designate for all four driven experiments (a)–(d) of the #0285 umbrella (separate bundle id, separate UserDefaults, safe to open/close Tabs in). Every before/after comparison run on Beta would be wrong, and wrong by a *varying* amount, because how many rows truncate depends on how many happen to carry the WindowServer-shared suffix at that instant (invariant 2's own documentation records that count oscillating ±1–2 on a ~1 s timescale at idle). A delta between two Beta samples can therefore be pure truncation noise.

Note the asymmetry with #0291's Gotchas: the anticipated Beta failure mode ("wrong owner label guess") was designed to self-diagnose loudly through the owner histogram. This one does not — the truncated rows vanish before the histogram is built, so the histogram shows a plausible-looking `'Batty Beta.debug.dylib'` count that is merely too small.

**What is *not* affected:** the all-owners geometry-class census (`CENSUS`, `tools/memsample.sh:313`) already matches on the geometry+owner tail, not on `SurfaceID:`, so census counts and class-level diffs are correct; `ATLAS_1040K` reads `footprint` IOAccelerator lines; all `footprint -f bytes` metrics are untouched. The bug is confined to the four `SURFACE_ROWS`-derived values — which are exactly the ones the invariants judge.

## Steps to reproduce

1. Run the Beta build (Debug, so the owner label is `'Batty Beta.debug.dylib'`) with enough Tabs that some surfaces are WindowServer-shared.
2. `PID=$(ps -Ao pid=,comm= | awk '/Batty Beta\.app\/Contents\/MacOS\/Batty Beta$/{print $1; exit}')`
3. Compare: `vmmap $PID | grep -c 'SurfaceID:'` versus `vmmap $PID | grep -E '^IOSurface ' | grep -cE "[0-9]+x[0-9]+ \([A-Z0-9]+\) [0-9.]+[KMG]  '[^']*'"`.
4. Observe the first is smaller; `vmmap $PID | grep -E '\.\.\.[A-Za-z]*aceID:'` shows the dropped rows, all long-owner and WindowServer-shared.
5. `tools/memsample.sh invariants --target beta` reports FAILs that disappear once the corrected counts are used.

## Expected behavior

`tools/memsample.sh` counts every IOSurface row owned by the target binary regardless of how `vmmap` formats the line, on both release and Beta targets. The three invariants judge real counts; a FAIL means the process deviated, not that the parser did.

## Actual behavior

On the Beta target the harness drops every row whose `SurfaceID:` label was truncated — 6 of 66 on the 2026-08-03 measurement, 6 of 67 on the 2026-08-04 verification, always the WindowServer-shared ones — and reports false invariant FAILs against the exact build designated for the #0285 experiments.

## Notes

**Proposed fix:** stop keying on the truncatable `SurfaceID:` label and match the never-truncated geometry+owner tail at end-of-line instead — e.g. select rows with

```bash
grep -E "^IOSurface " | grep -E "[0-9]+x[0-9]+ \([A-Z0-9]+\) [0-9.]+[KMG]  '[^']*'"
```

`vmmap`'s truncation elides the *front* of the detail column and keeps the tail, so the geometry, size, quoted owner label, and any `, shared with WindowServer[…]` suffix survive on every row (verified on all 6 live truncated rows). The same awk body can then keep extracting owner (first quoted string), ws flag, and geometry per row; only the row-selection predicate changes. The `^IOSurface ` anchor replaces the specificity the `SurfaceID:` label used to provide. The existing `CENSUS` line already trusts this tail pattern, and the live cross-check (67 tail matches = 61 intact + 6 truncated; 103 = 103 + 0 on release) confirms it is neither over- nor under-inclusive on current output.

`tools/` is deliberately *not* part of the restricted `scripts/` area (#0291 placed the harness there for that reason), so the fix needs no special authorization — but per #0291's review history, the reviewer should run the fixed tool against a live Beta process, not just read the diff: every one of #0291's three review rounds found a wrong-measurement defect only by executing the tool.

Regression check worth adding to the fix's verification: on both targets, assert `batty_iosurfaces` equals the count from the tail-pattern one-liner in Steps 3 above, and that the truncated-row grep in Step 4 no longer changes any reported number.
