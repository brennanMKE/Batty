## Description

**Correction (review round 1, #0299):** the framing below, as originally filed, is wrong about *where* this bug bites. `vmmap`'s elision is **tty-width driven** — it shortens the detail column to fit the *controlling terminal's* width, but does **not** elide at all when its own stdout is a pipe or file (measured: `>file`, `| grep`, `$(...)` capture, and a forced `$COLUMNS` all produced zero elisions; `-wide` also disables it outright at any width). `tools/memsample.sh`'s `sample_pid` reads `vmmap` through `vm_out="$(vmmap "$pid" 2>&1)"` — a command-substitution capture — so **the shipped harness's own automated invariant/sample runs were never actually susceptible to this defect**, and no #0285 Beta experiment run through `tools/memsample.sh` was ever corrupted by it. The defect is real, but it is scoped to a person **hand-running the equivalent `vmmap | grep 'SurfaceID:'` one-liner interactively in a narrow-enough terminal** (this file's own `tools/README.md` and `issues/0285/investigation-live.md` both document such one-liners for exactly that kind of ad hoc check) — not to anything `tools/memsample.sh` itself produced. See the corrected "Measured consequence," "Why this gates #0285's experiments," and "Steps to reproduce" sections below.

`compute_target_owner_stats` in `tools/memsample.sh` selected IOSurface detail rows with `/SurfaceID:/` (`tools/memsample.sh:227`, pre-fix). `vmmap` can truncate that detail column when the line runs long **and it is writing to an interactive terminal**, eliding the *front* of the field: the row prints `...aceID: 0x109 …` instead of `SurfaceID: 0x109 …`, and the awk pattern silently drops it. Were this to happen inside a code path that consumes `vmmap`'s output directly on a tty, every stat derived from the dropped rows would be wrong at once: `batty_iosurfaces`, `batty_windowserver_shared`, `OWNER_GEO_TABLE`, and `OWNER_HISTOGRAM`. `tools/memsample.sh` does not do this (see the correction above) — but a hand-run one-liner in a narrow terminal does.

The elision is not random when it does occur interactively — it hits exactly the rows that matter most on the Beta target. The line only runs long enough to truncate when the owner label is long — `'Batty Beta.debug.dylib'` (22 chars) versus release's `'Batty'` (5) — **and** the row also carries the `, shared with WindowServer[607]` suffix. So the undercount lands entirely on Beta-owned, WindowServer-shared rows: the numerator of invariant 1, and disproportionately the shared count of invariant 2.

**Verified live 2026-08-04**, hand-running `vmmap` directly against both running instances in an interactive terminal (filer, read-only `vmmap` passes — not via `tools/memsample.sh`, whose own capture is immune per the correction above):

- Beta (Debug build, owner `'Batty Beta.debug.dylib'`): `grep -c 'SurfaceID:'` matched **61** rows; **6** additional rows were truncated to `...aceID:` — all 6 owned by `'Batty Beta.debug.dylib'`, all 6 `shared with WindowServer`. The geometry+owner tail on `^IOSurface` rows, which survives further into narrow widths than `SurfaceID:` does, matched **67** = 61 + 6 at this terminal's width.
- Release (`/Applications/Batty.app`, owner `'Batty'`): 103 `SurfaceID:` rows, **0** truncated, tail pattern also 103 — fully consistent.

Example truncated row (live, Beta pid):

```
IOSurface   130a28000-130b38000  [ 1088K ...] rw-/rw- SM=SHM PURGE=N  ...aceID: 0x109  1265x216 (BGRA) 1088K  'Batty Beta.debug.dylib', shared with WindowServer[607]
```

**Measured consequence (2026-08-03, live Beta instance):** hand-running the invariant-check one-liners interactively (**not** `tools/memsample.sh invariants`, whose `$(...)`-captured `vmmap` call is immune — see the correction above) produced 60 IOSurfaces / 20 layers / 16 WindowServer-shared; corrected values are **66 / 22 / 22**. With the correct numbers all three invariants pass exactly — 66/3 = 22.00 layers; ws-shared = 22 = `layers`, the bottom of the `[22, 44]` range; 1040 K atlas count = 66 = IOSurface count. As hand-run, **two of the three invariants falsely FAIL** (60 is a multiple of 3, so invariant 1 happened to pass that day with a wrong layer count of 20; 16 shared fell below the `[20, 40]` range; 66 atlases ≠ 60 surfaces). On the 2026-08-04 live check the miscount (61) isn't even a multiple of 3, so invariant 1 FAILs outright too.

This makes hand-running these one-liners interactively a **false-signal generator**, exactly the class #0291's own review round 1 blocked on once already (the strict-equality invariant 2) — but it does **not** make the shipped `tools/memsample.sh` tool one, since its own automated invocation was never susceptible. `tools/README.md` explicitly instructs the reader to treat a FAIL as "a finding to report, never as a bug in the harness to paper over"; that advice still holds for FAILs from `tools/memsample.sh` itself, but a reader hand-running the equivalent one-liner interactively in a narrow terminal needs to rule out elision first — which the fix below (the tail predicate, and `-wide` on the harness's own call) makes easier and, for the shipped tool, unnecessary.

## Why this gates #0285's experiments

**This does not gate #0285's experiments through `tools/memsample.sh` itself** — the tool's `$(...)`-captured `vmmap` call was never susceptible, so every Beta sample/invariant/diff taken with the actual tool was trustworthy on this axis, past and future. What it does gate is any *manual* cross-check a reader does by hand-running the documented one-liners (this README, `issues/0285/investigation-live.md`) directly in an interactive terminal narrower than ~185–200 columns: the undercount there is scoped to **only the Beta target** — the build #0291's Notes designate for all four driven experiments (a)–(d) of the #0285 umbrella (separate bundle id, separate UserDefaults, safe to open/close Tabs in). A manual before/after comparison done that way could be wrong by a *varying* amount, because how many rows elide depends on how many happen to carry the WindowServer-shared suffix at that instant (invariant 2's own documentation records that count oscillating ±1–2 on a ~1 s timescale at idle) as well as on the terminal's exact width. A delta computed from two such hand-run samples could be pure elision noise.

Note the asymmetry with #0291's Gotchas: the anticipated Beta failure mode ("wrong owner label guess") was designed to self-diagnose loudly through the owner histogram. This one does not — the elided rows vanish before the histogram is built, so the histogram shows a plausible-looking `'Batty Beta.debug.dylib'` count that is merely too small. (Again: only reachable by hand-running the one-liner interactively, not through `tools/memsample.sh`.)

**What is *not* affected:** the all-owners geometry-class census (`CENSUS`, `tools/memsample.sh:313`) already matches on the geometry+owner tail, not on `SurfaceID:`, so census counts and class-level diffs are correct; `ATLAS_1040K` reads `footprint` IOAccelerator lines; all `footprint -f bytes` metrics are untouched. The bug is confined to the four `SURFACE_ROWS`-derived values — which are exactly the ones the invariants judge.

## Steps to reproduce

**Correction:** step 5 as originally filed was wrong — `tools/memsample.sh invariants --target beta` does not reproduce this (its `vmmap` call is captured via `$(...)`, which is immune). Reproducing the elision requires an actual interactive terminal narrower than ~185–200 columns; running the one-liners below through this agent's non-interactive shell, a pipe, or a file redirect will not reproduce it either (review round 1 confirmed zero elisions across all of those).

1. Run the Beta build (Debug, so the owner label is `'Batty Beta.debug.dylib'`) with enough Tabs that some surfaces are WindowServer-shared.
2. `PID=$(ps -Ao pid=,comm= | awk '/Batty Beta\.app\/Contents\/MacOS\/Batty Beta$/{print $1; exit}')`
3. In an interactive Terminal window narrower than ~185–200 columns, compare: `vmmap $PID | grep -c 'SurfaceID:'` versus `vmmap $PID | grep -E '^IOSurface ' | grep -cE "[0-9]+x[0-9]+ \([A-Z0-9]+\) [0-9.]+[KMG]  '[^']*'"`.
4. Observe the first is smaller (and, below ~182 columns on this owner label, the tail pattern degrades too — measured via a pty width sweep in review round 2: the tail held 38/38 down to 183 columns where `SurfaceID:` was already 25/38); `vmmap $PID | grep -E '\.\.\.[A-Za-z]*aceID:'` shows the dropped rows, all long-owner and WindowServer-shared.
5. `tools/memsample.sh invariants --target beta` does **not** reproduce this — its `vmmap` call is captured via `$(...)`, which review round 1 confirmed is immune. Reproduction is scoped to hand-running the step-3 one-liner directly in a narrow interactive terminal.

## Expected behavior

Any code path or documented one-liner that counts IOSurface rows owned by the target binary should do so regardless of how `vmmap` formats the line, on both release and Beta targets and at any terminal width. `tools/memsample.sh` already met this via its `$(...)` capture being immune to elision by accident; the fix (tail predicate + `-wide`) makes it hold by construction, and also protects anyone hand-running the equivalent one-liner interactively.

## Actual behavior

`vmmap`, run interactively in a narrow-enough terminal, elides every row whose `SurfaceID:` label was truncated — 6 of 66 on the 2026-08-03 measurement, 6 of 67 on the 2026-08-04 verification, always the WindowServer-shared ones. A `SurfaceID:`-anchored count of that interactive output would report false invariant FAILs. `tools/memsample.sh` itself was never exposed to this because it captures `vmmap` via command substitution, which vmmap does not elide against — no #0285 Beta experiment run through the actual tool was ever affected.

## Notes

**Proposed fix:** stop keying on the truncatable `SurfaceID:` label and match the geometry+owner tail at end-of-line instead — e.g. select rows with

```bash
grep -E "^IOSurface " | grep -E "[0-9]+x[0-9]+ \([A-Z0-9]+\) [0-9.]+[KMG]  '[^']*'"
```

`vmmap`'s elision strips the *front* of the detail column and keeps the tail, so the geometry, size, quoted owner label, and any `, shared with WindowServer[…]` suffix survive further into narrower widths than `SurfaceID:` does (verified on all 6 live truncated rows) — **but review round 1 measured the tail is not immune either**, and it does *not* elide "when stdout is redirected" as a blanket rule (round 2 disproved that: `>file`, `| grep`, and `$(...)` all read 38/38 with zero elisions under a real 120-column pty) — elision is purely a function of the *controlling terminal's* width. Against a live Beta process (pty width swept via `TIOCSWINSZ`, review round 2), the geometry tail held 38/38 down to 183 columns and first degraded at ~182, with both predicates collapsing to 0-1 below ~150; these thresholds are also owner-label-length dependent (release's 5-char `'Batty'` held its tail past where Beta's 22-char label degraded, only giving way around ~176). The fix's real robustness comes from two things together: (1) `sample_pid` should pass `vmmap -wide`, which disables elision outright at any width, and (2) `tools/memsample.sh`'s existing `$(...)` capture pattern, which is immune regardless of the controlling terminal's width. The tail predicate alone is a strict improvement over `SurfaceID:` at every width tested, but should not be described as immune. The same awk body can then keep extracting owner (first quoted string), ws flag, and geometry per row; only the row-selection predicate changes. The `^IOSurface ` anchor replaces the specificity the `SurfaceID:` label used to provide. The existing `CENSUS` line already trusts this tail pattern, and the live cross-check (67 tail matches = 61 intact + 6 truncated; 103 = 103 + 0 on release) confirms it is neither over- nor under-inclusive on current (piped, non-elided) output.

`tools/` is deliberately *not* part of the restricted `scripts/` area (#0291 placed the harness there for that reason), so the fix needs no special authorization — but per #0291's review history, the reviewer should run the fixed tool against a live Beta process, not just read the diff: every one of #0291's three review rounds found a wrong-measurement defect only by executing the tool.

Regression check worth adding to the fix's verification: on both targets, assert `batty_iosurfaces` equals the count from the tail-pattern one-liner in Steps 3 above, and that the truncated-row grep in Step 4 no longer changes any reported number.

## Resolution notes

> 🟢 Resolved 2026-08-04 — row selection no longer keys on a label `vmmap` elides, and `-wide` makes the harness immune by construction. **The harness itself was never affected** — that part of the original report was wrong.

## Root cause

`compute_target_owner_stats` selected IOSurface detail rows with `/SurfaceID:/`. `vmmap` elides the front of that column to fit the **controlling terminal's width**, printing `...aceID:`, which drops the row from the match.

**But the scope in the original report was wrong.** `sample_pid` captures via `vm_out="$(vmmap "$pid" 2>&1)"` — command substitution — and `vmmap` does not elide at all when its own stdout is a pipe or file. Verified under a real 120-column pty: `> file`, `| grep`, and `$(...)` all returned 38 of 38 rows. So no #0285 Beta sample taken through `tools/memsample.sh` was ever corrupted. The 60/20/16-vs-66/22/22 discrepancy that prompted this issue came from **hand-run interactive one-liners**, not from the tool.

## Fix

- Row extraction moved to `extract_surface_rows()`, selecting on the geometry+owner tail rather than the `SurfaceID:` label — a strict improvement at every width measured.
- `sample_pid` now calls `vmmap -wide`, making immunity structural rather than an accident of `$(...)` capture.
- `tools/memsample.sh selftest` added: a fixture of captured real `vmmap` lines including the truncated form, asserting exact counts.
- The false framing was corrected in `tools/memsample.sh`, `tools/README.md`, and this issue's own Description.

## Review

Reviewed by claude-opus-5 over two rounds, and **each round found the previous round's correction was itself wrong.**

Round 1 established the mechanism the original report had guessed at: elision is tty-width driven and absent when stdout is a pipe — which meant the harness was never susceptible and this issue's framing was wrong. Round 2 then found the *correction* wrong in two places: a claim that `vmmap` elides "even when stdout is redirected" (measured false under a 120-column pty, and self-contradicting), and a `~170` column threshold that was off by ~13 in the unsafe direction — the tail actually holds 38/38 down to 183 and degrades at 182, so a reader at 175 columns would have taken a 34% undercount as exact.

The reviewer built a pty harness (`TIOCSWINSZ`) to vary the controlling terminal's width independently of stdout. That is what made both errors visible; neither was reachable by reasoning.

## Gotchas

- **The harness path was never affected**, and that is the part of the original report that was wrong. `vmmap` elides only when writing to a narrow controlling terminal; `sample_pid` captures through a pipe. Numbers produced by `tools/memsample.sh` have always been trustworthy on this axis — #0285's experiments were never blocked by a harness defect.
- **Hand-running `vmmap` is the thing to be careful with.** Pass `-wide`, or redirect to a file. The one-liners in `tools/README.md` and `issues/0285/investigation-live.md` undercount in an interactive terminal narrower than ~185–200 columns.
- **The geometry+owner tail is a strict improvement, not immunity.** Against the live Beta it held 38/38 down to 183 columns, degraded at 182, and collapsed to 1 below 150. **Those thresholds are specific to that process's owner-label length and surface geometry** — on release (`'Batty'`, 5 chars) the tail held to ~176. Do not treat them as constants.
- **Two rounds of correction were each wrong before this landed.** If a claim here matters to a decision, measure it rather than trusting the prose — a pty harness varying terminal width independently of stdout is what settled it.
