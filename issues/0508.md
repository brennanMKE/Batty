# 0508 — `batty status` cannot decode a reply from an older running app, which is the exact case it exists to diagnose

| | |
|---|---|
| **Status** | open |
| **Module** | CLI / XPC |
| **Platform** | macOS |
| **First seen** | 2026-10-14 |

## Description

`StatusPayload` gained two non-optional fields, `bundlePath` and `appVersion` (#0361). Its `Decodable` conformance is synthesized, so a missing key is a hard decode failure. The app is the encoder and the CLI is the decoder, and the two are *not* guaranteed to be the same build — that mismatch is the entire premise of #0361, whose doc comment says the failure mode was "nothing told the user which of several bundles sharing `co.sstools.Batty` ... they were actually talking to."

So: a new `batty` talking to a 1.1-era app still running gets five fields, fails to decode, and reports a generic error instead of reporting the stale app's identity. There is no protocol-version field anywhere in `XPCRequest`/`XPCResponse` to negotiate with.

Found by an external review of `v1.1.0..ad239f9e` — review id `20261014T193749Z-Batty-883c427`, finding 5 of 5 (medium, correctness, confidence high).

## Steps to reproduce

1. Keep a pre-#0361 build of Batty.app running.
2. Run a current `batty status --json` against it.

## Expected behavior

The two added fields degrade to an explicit unknown value and the rest of the status prints, so the user can see they are talking to an old app.

## Actual behavior

Decoding `StatusPayload` throws; `status` reports a failure state with no app identity in it.

## Notes

- `BattyKit/Sources/BattyXPCCore/StatusPayload.swift:29-32`. Existing tests (`XPCContractTests.swift:230-257`, `StatusJSONPayloadTests`) only round-trip payloads that already have both fields, so the gap is untested.
- Fix: hand-write `init(from:)` and decode the two new keys with `decodeIfPresent`, falling back to `"unknown"` — the same sentinel `appVersion`'s own doc comment already names for the case where neither `CFBundleShortVersionString` nor `CFBundleVersion` resolves. The five original fields stay required: an app that cannot supply those is not a Batty this CLI can talk to at all.
- Encoding is unchanged, so a new app answering an old CLI is unaffected (the old CLI ignores unknown keys).
