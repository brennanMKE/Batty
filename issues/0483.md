## Description

In Batty Beta (Projects flag on), choosing the Command Palette row **"Open Project…"** (`id: "extra:openProjectPicker"`) closes the palette and then nothing happens: the Open Project picker sheet never appears. Clicking the row and pressing Return on it behave the same. The other ways to reach the same picker work. File ▸ Open Project ▸ Choose Project… presents it, and the palette's own **"Open Project: <name>"** rows open their Project. Only the palette-to-picker path is broken.

#0478's VM UI tests found it. `ProjectsOpenTests.testCommandPaletteOpenProjectRowPresentsThePicker` (click) and `ProjectsOpenTests.testCommandPaletteOpenProjectRowPresentsThePickerWithReturn` (Return) failed in every VM run that included them. That includes the full-suite run `build/ui-tests/20261012-162742-80765/` (149 tests, 8 skipped, exactly these 2 failed), and the earlier runs `20261012-155148-63732`, `20261012-160517-68223` and `20261012-161430-72461`. Each time, `project-picker.root` did not appear within 10 s after the row was chosen. The failure-time UI hierarchy shows neither the palette nor the picker. The palette's dismissal therefore completes, and the picker is never presented.

This is a regression in #0475's shipped behavior. #0475's resolution listed "palette "Open Project…" presenting the picker" under **Not verified here**, deferred to #0478.

## Steps to reproduce

1. Launch Batty Beta with at least one Project in `projects.json`.
2. Open the Command Palette (⇧⌘P) and type "Open Project".
3. Click the **Open Project…** row, or select it and press Return.

## Expected behavior

The palette closes, and the Open Project picker sheet ("Open a Project", `project-picker.root`) presents on the same window, with its filter field focused. This is the same result File ▸ Open Project ▸ Choose Project… gives.

## Actual behavior

The palette closes and no sheet appears. No error or log shows it.

## Notes

### Code path (verified on `main` at `6f4acab8`)

- The palette row is `BattyKit/Sources/BattyKit/Views/CommandPaletteView.swift:113-122`. Its action is `runAfterDismiss { NotificationCenter.default.post(name: .battyToggleProjectPicker, object: nil) }`.
- `CommandPaletteView.runAfterDismiss` (`:193-199`) hands the closure to the host's `afterDismiss` seam when one is set, and runs it at once otherwise. A row choice sets `isPresented = false` and then calls `cmd.action()` (`:272-273`).
- `SessionDetailView` (`Views/SessionDetailView.swift:79-85`) presents the palette with `.sheet(isPresented: $commandPaletteShown, onDismiss: runAfterCommandPalette)` and passes `afterDismiss: { afterCommandPalette = $0 }`. `runAfterCommandPalette` (`:310-314`) runs the stored closure from the sheet's `onDismiss`. This is the #0475 / #0473 rule recorded in `docs/swiftui-observation-rules.md:179-186`: work that follows a sheet's dismissal waits for `onDismiss`.
- So the toggle notification is posted **synchronously inside the palette sheet's `onDismiss`**. Its handler is `SessionDetailView.swift:56-59`: `.onReceive(... .battyToggleProjectPicker) { guard store.featureFlags.projects, isKeyWindow else { return }; projectPickerShown.toggle() }`.
- `isKeyWindow` (`:299-301`) is `store.keyWindowRuntime()?.id == windowRuntime.id`. `AppStateStore.keyWindowRuntime()` (`Runtime/AppStateStore.swift:882-886`) maps `NSApplication.shared.keyWindow` through `nsWindowMap`, so it returns nil whenever the key window is not a registered content window.
- The picker sheet is `.sheet(isPresented: projectPickerBinding, onDismiss: runAfterProjectPicker)` (`:92`). The notification name is declared at `Views/ProjectPickerView.swift:8`.
- The File menu's working path is `Commands/BattyCommands.swift:128-130` (`postToContentWindow(.battyToggleProjectPicker)`, defined at `:660-663`). It posts from a menu action while the content window is key and no sheet is in flight.
- The "Open Project: <name>" rows (`CommandPaletteView.swift:150-165`) also run in `onDismiss`, but they call `ProjectOpenPresenter.open` directly. They go through neither a notification nor the key-window check, and they work.

### Suspected cause (unverified)

Nobody has confirmed this with logging or a debugger. There are two candidates, and either one fits the evidence:

1. **The key-window guard rejects the post.** While the palette sheet's window is closing, `NSApp.keyWindow` may still be the sheet's window, or nil, rather than the content window. In that case `isKeyWindow` is false and the handler returns without flipping `projectPickerShown`. That is the #0242 fan-out guard misfiring for a post that, unlike the menu's, is not made while the content window is key.
2. **SwiftUI drops a sheet presented from another sheet's `onDismiss`.** If the guard passes, `projectPickerShown` flips to true inside the palette's dismissal transaction, and SwiftUI may ignore or immediately reset a second `.sheet` presentation requested from that transaction.

The first step of the fix is to find out which one it is, for example with a `logger.debug` in the `onReceive` handler that records whether the guard passed. Record the answer in the resolution.

### Fix constraints

- **Binding:** `docs/swiftui-observation-rules.md`. Do **not** wrap the post or the toggle in `Task { @MainActor in … }`, `DispatchQueue.main.async` or `asyncAfter` to "let the dismissal finish". That is the band-aid the rules forbid (the #0229 click regression). Restructure **which code owns the presentation write**. For example, the palette's chosen action could be handed to `SessionDetailView` as a value (as `afterProjectPicker` already is for the picker's own actions, `SessionDetailView.swift:316-327`), so that `runAfterCommandPalette` sets `projectPickerShown = true` directly for *this* window. That would not route a broadcast notification back through a key-window guard. It would also remove candidate 1 by construction. If candidate 2 turns out to be the cause, the chosen structure must be one SwiftUI honors without a time hop, and the resolution must say which SwiftUI behavior it relies on.
- The flag gate stays: with `featureFlags.projects == false` the row does not exist, and the picker sheet is not installed (#0475 §4).
- The #0242 guarantee must hold. Choosing the row in one window must not present the picker in any other window.
- No new `ShortcutAction` case (#0469).

### Tests

- The existing unit test `ProjectPickerTests.thePickerEntryPostsTheToggle` (`BattyKit/Tests/BattyKitTests/ProjectPickerTests.swift:325-337`) builds `CommandPaletteView` with no `afterDismiss`, so the action runs at once and the post succeeds. It covers neither the `onDismiss` path nor the key-window guard, which is why it passed while the feature was broken. Replace or extend it so a unit test covers the new ownership of the presentation write. That means the value the palette hands its host, and the host deciding to present the picker, without waiting on time (`AGENTS.md` "Asynchronous tests").
- The two `ProjectsOpenTests` UI tests above are the acceptance test. #0478 lands them wrapped in `XCTExpectFailure` that references this issue. **This fix must remove that `XCTExpectFailure` marking.** Both tests must then pass in the Tart VM (`tools/run-ui-tests-vm.sh BattyUITests/ProjectsOpenTests`), and the full `ProjectsOpenTests` class must stay green.
- `./build.sh unit` passes.

## Resolution notes

> 🟢 Resolved 2026-10-12. The Command Palette's "Open Project…" row now opens the Open Project picker on the palette's own window, whether chosen by click or by Return.

Owed to the user, as manual checks in Batty Beta:
- With two windows open, choose the palette row in window A. The picker should appear only in A.
- The picker's filter field is focused when it appears.

## Root cause

The cause was candidate 1, the key-window guard. The palette row posted `.battyToggleProjectPicker` synchronously, inside the palette sheet's `onDismiss`. The `SessionDetailView` handler is gated on `isKeyWindow`, which maps `NSApp.keyWindow` through `nsWindowMap`. At that moment the key window was not the registered content window, so every receiver dropped the toggle.

This was confirmed by elimination in VM runs `20261012-234631-47144` and `20261012-235109-52372`. The fix still presents the picker from the palette's `onDismiss`, exactly as before, and only bypasses the guard. So candidate 2, that SwiftUI drops a sheet presented from another sheet's `onDismiss`, is ruled out.

## Fix

- `CommandPaletteView` takes a `presentProjectPicker: (@MainActor () -> Void)?` closure. The "Open Project…" row runs `runAfterDismiss { presentProjectPicker?() }`, with no NotificationCenter post. A nil closure does nothing.
- `SessionDetailView` passes a closure that checks `featureFlags.projects` and then sets its own `projectPickerShown = true`.
  - The write is event-origin and made in `onDismiss`, with no hop.
  - It is scoped to the window that hosts the palette (#0242), and needs no key-window check.
- The `.battyToggleProjectPicker` handler keeps its `isKeyWindow` guard. It now serves only the File menu.
- The strict `XCTExpectFailure` wrappers from #0478 are removed from both palette UI tests.
