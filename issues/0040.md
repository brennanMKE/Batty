# 0040 — Migrate code from Batty app target into BattyKit

| | |
|---|---|
| **Status** | open |
| **Module** | App / Build / Docs |
| **Platform** | macOS |
| **First seen** | 2026-05-08 |

## Description

Move as much code as possible out of the `Batty` app target and into the `BattyKit` Swift Package. The app target should be lightweight: `@main BattyApp`, top-level `Scene`/`WindowGroup` wiring, app-level menus, and any glue that genuinely has to live in the bundle. Everything else — models, persistence, theme parsing, layout views, surface registry, terminal surface NSView wrapper, bell-feed store — belongs in `BattyKit/Sources/BattyKit/`.

This unlocks two things:

1. **Direct access to dependencies.** `BattyKit` already declares `libghostty-spm` (re-exported as `GhosttyKit`) and `SlidingTabs` as deps. Code in the app target has to round-trip through `BattyKit`'s re-exports; code inside `BattyKit` has them natively.
2. **Unit-testability without the app harness.** `BattyKitTests` can `import BattyKit` cleanly without the test-bundle bootstrap crash that `BattyTests` hits when it tries to `import BattyKit` (see `#0001` Gotchas — there's something about libghostty static initializers that doesn't survive the xctest plugin loader running inside the app target's test host).

**Acceptance criteria:**

- All Swift files currently in `Batty/` *except* `BattyApp.swift`, `ContentView.swift` (or its successor), and any genuinely app-target-only glue have been moved to `BattyKit/Sources/BattyKit/`.
- `BattyApp.swift` imports `BattyKit` and uses the moved types.
- `xcodebuild -scheme Batty -destination 'platform=macOS' build` passes.
- `xcodebuild -scheme Batty -destination 'platform=macOS' test` runs the existing tests — preferably moved into `BattyKit/Tests/BattyKitTests/` so they exercise the package directly.
- The app launches and shows the same UI as before the migration (no behavior change).

## Notes

### What's currently in `Batty/` and where it goes

As of resolving this issue's filing time:

| File | Current location | Target location | Notes |
|---|---|---|---|
| `BattyApp.swift` | `Batty/` | **stay in `Batty/`** | App entry point; must be in the app target |
| `ContentView.swift` | `Batty/` | stay in `Batty/` (or its successor view) | Top-level `Scene` content; will reference `BattyKit` types |
| `LayoutModel.swift` | `Batty/` | `BattyKit/Sources/BattyKit/` | Pure value types, no dependencies on app shell |
| `Workspace.swift` | `Batty/` | `BattyKit/Sources/BattyKit/` | Pure value types |
| `WorkspaceStore.swift` | `Batty/` | `BattyKit/Sources/BattyKit/` | File IO, depends on Foundation only |
| `Theme.swift` | `Batty/` | `BattyKit/Sources/BattyKit/` | Parser + discovery, Foundation only |
| `GhosttySmoke.swift` | `Batty/` | likely **delete** during migration | Compile-time linkage stub; once `BattyKit` itself uses `ghostty_*` symbols, this becomes redundant |
| `SlidingTabsSmoke.swift` | `Batty/` | likely **delete** during migration | Same rationale |

### What's currently in `BattyTests/` and where it goes

The test files mirror the source moves. Migrate them to `BattyKit/Tests/BattyKitTests/` so they exercise the package directly via `@testable import BattyKit` rather than the app target. This also sidesteps the BattyTests-target test-bootstrap crash on `import BattyKit` (see #0001 Gotchas).

| File | Current location | Target location |
|---|---|---|
| `LayoutModelTests.swift` | `BattyTests/` | `BattyKit/Tests/BattyKitTests/` |
| `WorkspaceTests.swift` | `BattyTests/` | `BattyKit/Tests/BattyKitTests/` |
| `WorkspaceStoreTests.swift` | `BattyTests/` | `BattyKit/Tests/BattyKitTests/` |
| `ThemeTests.swift` | `BattyTests/` | `BattyKit/Tests/BattyKitTests/` |
| `BattyTests.swift` (Xcode template stub) | `BattyTests/` | leave as-is or delete; minimal value |

The `@testable import Batty` becomes `@testable import BattyKit`. Other than the import statement, test bodies should not need changes.

### Access control

When moving types out of the app target, types that need to be visible to `Batty` callers must be marked `public`. Today `LayoutModel.swift`, `Workspace.swift`, `WorkspaceStore.swift`, `Theme.swift` use the implicit `internal` access level; they'll need explicit `public` on types and on every member that the app target uses (initializers, properties, methods). For types that are purely internal to `BattyKit`, leave them `internal` — fewer public-API commitments to defend later.

### Out of scope

- Setting up a `BattyKitTests` target / scheme inside the Xcode project so it shows up in the test navigator. SPM tests run via `swift test` from `BattyKit/` and via `xcodebuild test` against the `Batty` scheme transitively. If schema-level test integration is needed, file a follow-up.
- Restructuring `BattyKit` into multiple targets (e.g. splitting models from views into separate libraries). Premature; v1 keeps `BattyKit` as a single library target.

### Ground rules for code added after this migration

Going forward, **default to `BattyKit/Sources/BattyKit/`** for any new Swift file that doesn't strictly require the app target. Reserve `Batty/` for `@main`, top-level scenes, app-lifecycle delegate methods, and resource-bundle-dependent glue. CLAUDE.md should be updated to reflect this rule once the migration lands.
