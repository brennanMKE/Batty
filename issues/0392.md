# 0392 — Batty never sets `shell-integration-features`, so `COLORTERM` and `xterm-ghostty` terminfo never reach a remote host over SSH

## Description

The request, in the user's words, was:

> "support using COLORTERM by setting the colors from the current theme so that apps like nvim use those colors even in a remote SSH session."

**That is not achievable as stated, and the attached research note says so on its first page.** Quoting it:

> `COLORTERM` does not carry your theme. It is a single word — `truecolor` or `24bit` — and it answers exactly one question: *may I send 24-bit colour?* It says nothing about which colours, and there is no environment variable that does.

There is no mechanism, in any terminal, by which a Theme's colours are shipped to a remote host as data. Two separate mechanisms exist, and **they pull in opposite directions**:

- **`COLORTERM=truecolor` propagation** tells a remote app it *may* emit 24-bit RGB. When it does, Batty draws exactly those RGB values and **the active Theme is ignored** — the app's own colourscheme wins.
- **The Theme reaching a remote app** happens only when the app emits **ANSI colour indices 0–15**. Batty resolves each index through the active Theme's palette at render time, so changing the Theme changes every running remote app instantly, with nothing to sync and no reconnect.

So the note's own conclusion for nvim is to turn `termguicolors` **off**, not on — giving up truecolor is precisely what makes the Theme apply. An implementer who does not internalise this will build the wrong feature: enabling `COLORTERM` propagation *reduces* the Theme's reach, it does not extend it.

A third route exists and is worth capturing: **OSC 10/11 queries**, by which an app asks the terminal for its live background/foreground colour (neovim supports this). It is the only way an app learns actual colour *values* rather than indices. This issue does not build anything for it; it is named so the docs deliverable can mention it.

**What Batty can actually do**, and the real gap: Batty never emits the `shell-integration-features` config key at all, so both of libghostty's SSH integration halves are off, and neither `COLORTERM` nor a resolvable `TERM` survives the hop.

## The verified gap

**Batty emits no `shell-integration-features` key anywhere.** Verified 2026-09-02 by grepping `BattyKit/Sources` and `Batty/` for `shell-integration`, `shellIntegration`, `COLORTERM`, `ssh-env`, and `ssh-terminfo`. Every hit is unrelated:

- `BattyKit/Sources/BattyKit/Util/TUIAppRegistry.swift:58` — a doc comment mentioning "the shell-integration path that motivates this".
- `BattyKit/Sources/BattyKit/Help/09-third-party-licenses.md` — the bundled-file attribution table.
- `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:298` and `BattyKit/Sources/BattyKit/Commands/ExitDispatcher.swift:12` — comments naming `ssh` as an example TUI.

There is **no** occurrence of `COLORTERM` in Batty's own sources.

Consequently Batty inherits libghostty's shipped default, which per the note is:

```
shell-integration-features = cursor,no-sudo,title,no-ssh-env,no-ssh-terminfo,path
```

Both SSH halves are off, which is why `COLORTERM` does not arrive and `TERM=xterm-ghostty` does not resolve remotely.

| Feature | Effect |
|---|---|
| `ssh-terminfo` | Installs the `xterm-ghostty` terminfo entry on the remote host on first connect so `TERM=xterm-ghostty` resolves there. Successful installs are cached (`ghostty +ssh-cache`, `--clear` to reset) — **see the caveat below; Batty has no `ghostty` binary to cache with.** |
| `ssh-env` | Propagates terminal environment including `COLORTERM`, and falls back to a widely-known `TERM` where the entry cannot be installed. |

### The plumbing exists and is bundled — this is genuinely a config-only change

Three things were checked, because "the config key exists" would not by itself be enough:

1. **The key reaches the spawned process in the pinned libghostty.** `BattyKit/.build/checkouts/libghostty-spm/Patches/ghostty/0002-host-managed-io-modern.patch` shows `.shell_integration_features = config.@"shell-integration-features"` being passed into `termio.Exec.init`. Ghostty pin: `Ghostty.ref` = `35e1a0160c4f6797e1bb1ef8e7a2b8c6b114ab58`.
2. **Batty uses the `.exec` backend, not `.host_managed`.** That same patch introduces a `.host_managed` alternative that would bypass `termio.Exec` entirely — and with it `shell_integration_features`, `command`, `env`, and `term`. Grepping `BattyKit/Sources` and `Batty/` for `hostManaged` / `host_managed` / `HostManaged` returns **nothing**, so Batty is on the `.exec` path where the key is honoured. (Corroborating: `TabRuntime` already relies on `command` and `env`, which are `.exec`-only, and `TabRuntime.swift:249-255`'s comment describes bridging "libghostty's authoritative pwd signal" — an OSC 7 emission from the shell-integration scripts, so shell integration is demonstrably live.)
3. **The shell-integration scripts that implement the feature are bundled in the app.** `Resources/ghostty-runtime/ghostty/shell-integration/` carries the `ssh` wrapper function for bash (`bash/ghostty.bash:117-185`), zsh (`zsh/ghostty-integration:317+`), fish (`fish/vendor_conf.d/ghostty-shell-integration.fish:124+`), elvish and nushell, each gated on `$GHOSTTY_SHELL_FEATURES` containing `ssh-`. `scripts/bundle-ghostty-resources.sh` rsyncs that tree into `Batty.app/Contents/Resources/ghostty/shell-integration/`.

So no new plumbing is required — one `withCustom("shell-integration-features", …)` line in the right places is the whole code change. What follows is why "the right places" is more than one place, and what does *not* work cleanly.

## What to establish and decide

### 1. Enable `ssh-env` and `ssh-terminfo` — default-on, or a Setting?

They have very different risk profiles and should probably be decided separately.

**`ssh-env` is self-contained and cheap.** Read the bundled wrapper (`Resources/ghostty-runtime/ghostty/shell-integration/bash/ghostty.bash:126-127`): it adds exactly two ssh options and nothing else.

```bash
ssh_opts+=(-o "SetEnv COLORTERM=truecolor")
ssh_opts+=(-o "SendEnv TERM_PROGRAM TERM_PROGRAM_VERSION")
```

No remote side effect, no subprocess, no cache. It also pins `TERM=xterm-256color` for the remote session (`ssh_term` defaults to that at `:121` and is only upgraded to `xterm-ghostty` by the `ssh-terminfo` branch at `:147` / `:165`) — which is *safer* than shipping an unresolvable `TERM=xterm-ghostty`, and is exactly what the user's nvim case needs. Note the remote host must still list `COLORTERM` in `sshd`'s `AcceptEnv`; the note records that the Pis already do (`AcceptEnv LANG LC_* COLORTERM NO_COLOR`). A host that does not simply ignores it — no error.

**`ssh-terminfo` runs code on someone else's machine.** It pipes `infocmp -0 -x xterm-ghostty` into a remote `tic` over a `ControlMaster` connection (`ghostty.bash:151-172`; the cache check is `:146`, the cache write `:169`). The remote snippet is conservative — it exits 0 early if `infocmp xterm-ghostty` already resolves, and installs into `~/.terminfo`, not `/usr/share/terminfo`, so it does **not** need `sudo` as the note's manual one-liner does. Still, it is a write to a remote home directory that the user did not explicitly ask for on that connection, and it adds a connection round-trip. That argues for opt-in, or at minimum for disclosure in the Settings UI and Help. **Lay out the trade-off in the resolution; do not decide it unilaterally.**

**A concrete caveat specific to Batty, not present in the note (which was written about Ghostty proper).** The `ssh-terminfo` branch's cache check is:

```bash
if "$GHOSTTY_BIN_DIR/ghostty" +ssh-cache --host="$ssh_target" >/dev/null 2>&1; then
```

**Batty ships no `ghostty` executable.** `Batty.app/Contents/Resources/bin/` contains exactly `batty` and `BattyBroker` (verified against the built Debug app), and nothing in `BattyKit/Sources` or `Batty/` sets `GHOSTTY_BIN_DIR`. So that test always fails and control falls to the `elif command -v infocmp` branch — the install path — on **every** `ssh` invocation, and the "Cache successful installation" call afterwards is `… || true`, so it silently no-ops. Net effect: `ssh-terminfo` still *works*, but the cache never populates and every connection pays one extra `ControlMaster` round trip (fast, because the remote snippet short-circuits once the entry exists, but not free). The note's advice to "check `ghostty +ssh-cache` after the first connection" **does not apply to Batty** — there is no such command here. Decide whether that per-connection cost is acceptable, or whether Batty needs its own cache equivalent, before enabling `ssh-terminfo` by default.

### 2. Where the value is set — the replace-not-merge hazard

`setTerminalConfiguration` **replaces** the entire override set rather than merging it, and Batty builds that set in two independent places:

- `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:172-246` — the per-Tab builder at Tab init, ending at `terminal.controller.setTerminalConfiguration(configuration)` (`:246`). This is where `builder.withCustom("env", "BATTY_TAB_ID=…")` and friends live (`:225-231` — the line numbers handed to this filer were verified and are correct).
- `BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift:170-199` — `applyAppearanceToAllSurfaces()`, applied app-wide on any appearance change, calling `setTerminalConfiguration` at `:196`.

A key emitted from only one of those is silently dropped the next time the other runs. This is the same hazard documented in [#0373](0373.md) and [#0372](0372.md). **Set it in both, or explain in the resolution why not.** Both builders already duplicate the six-line `keybind` block verbatim; factoring the shared emission into one helper that both call sites invoke would fix the class of bug rather than one instance, and [#0373](0373.md) proposes the same refactor — coordinate rather than doing it twice.

**But note a wrinkle the background-image work does not have.** `shell-integration-features` is consumed at **process spawn** (`termio.Exec.init`, per the patch above), not at render time. Reapplying it to a live surface cannot change an already-running shell — the shell already read `$GHOSTTY_SHELL_FEATURES` at startup. So emitting it from `applyAppearanceToAllSurfaces()` is purely defensive, to stop the value being wiped for surfaces created later; the user-visible behaviour only changes for **newly created Tabs**. Say that in the Help text, or the first bug report will be "I turned it on and my open SSH session didn't change".

For completeness: the Theme path is a *third* apply site (`ThemePreference.applyThemeToAllSurfaces` / `applyTheme(_:to:)`, `BattyKit/Sources/BattyKit/Theme/ThemePreference.swift:151-193`) but it calls `controller.setTheme(_:)`, not `setTerminalConfiguration`. In the pinned SPM package those are separate slots merged by `resolveEffectiveConfig` (`GhosttyTerminal/Controller/TerminalController.swift:203-219, 224-227`), so the Theme is not part of this hazard. Do not "fix" it there.

### 3. Is Batty's terminfo installable remotely at all?

**Yes — checked, and it is in better shape than the third question assumed.**

- `Batty.app/Contents/Resources/terminfo/78/xterm-ghostty` is present in the built app (the #0003 sentinel; `scripts/bundle-ghostty-resources.sh:26`, asserted again by `scripts/preflight.sh:417-422`).
- `TERMINFO=<bundle>/Contents/Resources/terminfo infocmp -0 -x xterm-ghostty` succeeds and emits `xterm-ghostty|ghostty|Ghostty,…` — so the local `infocmp` step the `ssh-terminfo` wrapper depends on will work.
- The entry declares `Tc` (and `colors#256`), the direct-truecolor capability. Worth knowing: some apps detect truecolor from `Tc` rather than `COLORTERM`, so a remote host that *does* get the entry installed gains truecolor detection even without `COLORTERM`.

**What is not yet confirmed is what `TERM` Batty actually sets in a local surface.** Batty never emits the `term` config key (no hits for `"term"` as a config key in `BattyKit/Sources`), so it inherits libghostty's default, which is `xterm-ghostty`. That is a *strong inference*, not an observation — and #0003's own investigation notes explicitly warned that before the resources were vendored, `$TERM` "will fall back to whatever libghostty defaults to (likely `xterm-256color`)". **The implementer must confirm this empirically** — open a Tab in Batty Beta and run `echo $TERM` — because the whole of `ssh-terminfo` is meaningless if the local `TERM` is not `xterm-ghostty`. Record the observed value in the resolution.

### 4. Documentation is a deliverable, not a footnote

The note's most useful finding for a Batty user is the palette route, and **no code change makes it discoverable**. It belongs in two places:

- **`docs/`** — a new engineer-facing page (or a section in `docs/themes.md`) covering: what `COLORTERM` does and does not carry; the indices-0–15 route and why it is what makes a Theme follow you over SSH; the `termguicolors = false` consequence for nvim, with the note's measured colourscheme table; OSC 10/11 as the query route; and the Batty-specific caveats above (no `ghostty` binary, spawn-time-only, `~/.terminfo` not `sudo`). Register it in `docs/README.md`'s "Available" list — every other guide there is listed with a one-paragraph summary; match that shape.
- **In-app Help** — `BattyKit/Sources/BattyKit/Help/` (`01-overview.md` … `09-third-party-licenses.md`). `07-themes.md` is the natural home for the "your Theme follows you over SSH if the app emits indices 0–15" paragraph; if the SSH settings get a UI, they need their own Help coverage too. Note that Help pages are user-facing and localized — check how the existing pages handle that before adding a tenth file rather than extending `07-themes.md`.

## Expected behavior

- A remote host reached with `ssh` from a Batty Tab receives `COLORTERM=truecolor`.
- `TERM` resolves on the remote host rather than producing "unknown terminal type".
- A remote app that emits ANSI indices 0–15 renders in Batty's active Theme, and switching the Theme recolours it live.
- The relationship between the two — that truecolor and Theme-following are mutually exclusive — is documented where a user will find it.

## Actual behavior

`COLORTERM` is unset on the remote host. `TERM=xterm-ghostty` is sent but unresolvable there unless the user installed the entry by hand. Nothing anywhere tells the user that emitting indices 0–15 is what makes the Theme apply.

## Acceptance

Run from a Tab in **Batty Beta**:

```bash
ssh <host> 'echo $COLORTERM'                         # -> truecolor
ssh <host> 'infocmp $TERM >/dev/null && echo terminfo-ok'
ssh <host> 'echo $TERM'                              # record the value
echo $TERM                                           # local, in a Batty Tab — record it
```

Plus, manually: with a remote app emitting indices 0–15 (the note's `termguicolors = false` nvim config is the reference case), switch Batty's Theme and confirm the remote app's colours change **with no reconnect**.

**This cannot be verified purely locally** — it needs a real remote host. The note names Debian 13 Raspberry Pis (`yoyo`, `buzz`); `buzz` is recorded there as *not* having the `xterm-ghostty` entry yet, which makes it the better `ssh-terminfo` test target and `yoyo` the better control. If no remote host is reachable from the implementing environment, that is a bail per Issues.md's verification rule, not a "verified by build".

**Beta only.** `./build.sh` defaults to the `Batty (Beta)` scheme; Prod is `./build.sh release` and is for release builds only. Never touch the user's Prod app at `/Applications/Batty.app`, and never launch or relaunch a Batty the user is running.

## Notes

### Corrections to source material, made while filing

The note was written about **Ghostty proper (1.3.1), not Batty**, and three of its statements do not carry over unchanged:

1. **`ghostty +ssh-cache` does not exist under Batty.** Batty embeds libghostty as a static library and ships no `ghostty` CLI. The cache check inside the bundled `ssh` wrapper therefore always fails; see §1 above for the consequence.
2. **`ssh-terminfo` does not need `sudo` here.** The note's manual one-liner (`infocmp -x xterm-ghostty | ssh yoyo sudo tic -x -o /usr/share/terminfo -`) is a system-wide install; the bundled wrapper installs into `~/.terminfo` instead. The two are not equivalent, and the automatic one is the less invasive of the pair.
3. **The config-file route does not apply.** The note edits `~/Library/Application Support/com.mitchellh.ghostty/config`. Batty does not read Ghostty's config file — every setting reaches libghostty through `TerminalConfiguration` builders in Swift. There is no user-editable config file to change, which is exactly why this is a code issue.

The note's advice to keep the manual `infocmp | tic` provisioning step regardless (because it covers hosts reached from other terminals) stands and is unaffected by anything here.

### A stale citation in `CLAUDE.md`, noticed while verifying

`CLAUDE.md` documents the build entry point as `scripts/build.sh` (and `scripts/build-beta.sh`) with Prod as the default. **`scripts/build.sh` does not exist.** The real entry point is `./build.sh` at the repo root, and its own header states it "defaults to the `Batty (Beta)` scheme", delegating to `scripts/build-beta.sh` only for `./build.sh package`. Not this issue's job to fix, but the acceptance commands above use the real script, and anyone following `CLAUDE.md` verbatim will get a "no such file" error.
