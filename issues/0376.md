## Description

A Session can already carry its own Theme — `SessionRuntime.localThemeName` (`BattyKit/Sources/BattyKit/Runtime/SessionRuntime.swift:21`), set from the per-Session Theme Selector in the sidebar's context menu. There is no equivalent for the terminal background, so once [#0373](0373.md) and [#0375](0375.md) land, every Session is stuck with the app-wide image and opacity.

This issue adds the same shape for backgrounds, so one Session can be decorated differently from the rest — the middle level of the three-level scope chain described in [#0374](0374.md): Pane override → **Session override** → app-wide default.

## Root cause

### Design

**Resolution.** Pane beats Session beats app-wide. Each tier is a complete `TerminalBackgroundSettings?`: `nil` follows, non-nil is whole, and a non-nil value with `imagePath == nil` means "no image" and hides a broader image.

**Storage follows the `sessionID` shape,** which already runs `SessionRuntime` → `SplitTree` → `PaneRuntime` → `TabRuntime` for the same reason: `TabRuntime` and `addTab` have no reference to their Session.

| Holder | Field | Observed? | Written by |
|---|---|---|---|
| `SessionRuntime` | `public private(set) var backgroundOverride` | yes, the source of truth | `setBackgroundOverride` only |
| `SplitTree` | `private(set) var sessionBackgroundOverride` | `@ObservationIgnored` | `SessionRuntime.setBackgroundOverride` |
| `PaneRuntime` | `private(set) var sessionBackgroundOverride` | yes, `isWindowSeeThrough` reads it | `SplitTree` |
| `TabRuntime` | `paneBackgroundOverride`, `sessionBackgroundOverride` | `@ObservationIgnored` | `PaneRuntime` |

`SplitTree.sessionBackgroundOverride` exists only so a new Pane can be told. Every level below `SessionRuntime` has one writer, and no path writes upward, so there is no echo.

**No `SessionRuntime.init` parameter.** A Session starts with no override, and #0540 uses the setter (see "Seam for #0540").

### Image safety

- **A Session override uses `store.backgroundImageImporter`,** so its copy goes in `<Caches>/<bundle id>/TerminalBackgrounds/<pid>/` under `.deadProcessFolders`. That rule fits: the override is in-memory, so the copy has to last as long as the process, and a second running copy keeps its own images.
- **It is not inspected,** for the reason #0375 gave Pane overrides: the value comes from this process's importer or from the gate's own output, and isn't read from disk. Seeding uses `gate.settings()`, which has already dropped an image that failed inspection.

## Mirror the `localThemeName` pattern exactly

The Theme case is the template, and the resolution semantics should match it property for property:

- **Storage.** `SessionRuntime.localThemeName: String? = nil` (`SessionRuntime.swift:21`). Add the background override in the same place, with the same `nil`-means-follow convention.
- **Resolution.** `ThemePreference.effectiveTheme(localThemeName:isDark:)` (`BattyKit/Sources/BattyKit/Theme/ThemePreference.swift:76-87`) resolves local → global: use the local value if set and valid, else fall through. Its doc comment (`:68-75`) makes the key distinction explicit — "in effect" is not the same question as "has a local override", because a Session following the global value still *has* an effective value and must be displayable.
- **"Follows global" semantics.** When the app-wide value changes, `applyThemeToAllSurfaces` updates only the Sessions that have no override: `windows.flatMap { $0.sessions }.filter { $0.localThemeName == nil }` (`ThemePreference.swift:158`). A Session with no background override must likewise pick up *later* app-wide background changes automatically; a Session with one must not be reset by them.
- **Application.** `applyTheme(_:to:)` (`ThemePreference.swift:179-191`) fans out over `session.tree.allPanes where pane.kind == .terminal` → `pane.tabs`; `applyActiveSessionTheme(for:)` (`:205-224`) is the caller that resolves local → global first. Note the `.kind == .terminal` filter — a non-terminal Pane's `tabs` holds one structural placeholder `TabRuntime` whose controller was never attached to a rendered surface (#0315 review round 1, finding 3). The background equivalent fans out the same way — but through `setTerminalConfiguration`, not `setTheme`, since backgrounds are a config-override channel and Themes are their own channel (see [#0372](0372.md)).
- **Entry point.** The per-Session Theme Selector is presented as a `.sheet(item:)` from the sidebar's Session context menu (`BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift:123-129`, presenting `SessionThemeSelectorView`), sitting next to a `SessionColorPickerView` sheet at `:130-136`. The background override belongs in the same neighborhood. If [#0374](0374.md) has already built a background sheet for Panes, reuse it with a Session-scoped binding rather than authoring a second one.

## Survive the wholesale-replace hazard

Documented in full in [#0372](0372.md). `setTerminalConfiguration` **replaces** the entire override set rather than merging it, and Batty builds that set in two independent places — `TabRuntime.swift:172-246` (per-Tab, at init) and `SettingsPreferences.swift:170-198` (`applyAppearanceToAllSurfaces()`, app-wide).

Concretely for this issue: a Session with a background override must not be reset by the next app-wide `applyAppearanceToAllSurfaces()`, which today builds one configuration from app-wide preferences and pushes it to every Tab in every window. The Theme channel already solves the analogous problem by filtering to unoverridden Sessions (`ThemePreference.swift:158`); the config channel needs the equivalent, either by filtering or by resolving the chain per Session inside the loop.

**And a Session override must reach Tabs created later.** Like the Pane case in [#0374](0374.md), `TabRuntime`'s builder runs at Tab-init and must read the resolved value, or the next `Cmd-T` in that Session opens with the app-wide background instead of the Session's. Cover it with a test: set a Session override, create a new Tab, assert its `renderedConfig` carries the Session's background lines.

## Notes

Decide whether the override is all-or-nothing (a Session either has a full background config or follows entirely) or per-field, and record which. All-or-nothing is simpler and matches `localThemeName`; per-field is more flexible and much easier to get subtly wrong.
