## Description

`scripts/release.sh` destroys the dSYM of every release it builds. The archive lands in `build/` (`ARCHIVE_PATH="$BUILD_DIR/$APP_NAME.xcarchive"`, `release.sh:22`, with `BUILD_DIR="$REPO_ROOT/build"`, `:20`), so the debug symbols end up at `build/Batty.xcarchive/dSYMs/Batty.app.dSYM` — and the cleanup step at the end of a successful release runs `rm -rf "$BUILD_DIR"` (`release.sh:366`), deleting the archive and the dSYM with it. The string `dSYM` never appears anywhere in `release.sh`; nothing copies it out before the delete. `dist/` receives only `Batty-$GIT_SHA.dmg` (`:313`, via `WORK_DMG` at `:312`), and both `build/` and `dist/` are gitignored (`.gitignore:3`, `:8`), so once the script finishes, the symbols are gone from every machine, permanently.

The cost is not hypothetical — it has already been paid. **#0311** is a real field crash of release 1.1.0 (20260805) that is currently blocked on exactly this: six unsymbolicated Batty frames (`+51236`, `+46664`, `+304636`, `+305944`, `+1062472`, `+1063128`, load address `0x1023d4000`, binary UUID `d164cb47-89b6-37fc-90b6-23c6bcd5c6bd`). With the dSYM, those resolve to file:line in one `atos` invocation and the trapping statement is named. Without it, #0311 rests on source reading and a register hint that may be incidental. Both machines were searched: `mdfind "com_apple_xcode_dsym_uuids == d164cb47-…"` returns nothing, and `dist/` on the MacBook holds only DMGs and release notes.

The shipped binary is not a substitute. DWARF debug info is emitted into the `.o` files at compile time and collected by `dsymutil` into the `.dSYM` bundle during archiving — it is never present in the shipped executable. A binary yields function-level symbols at best, and only when unstripped; no `dwarf-with-dsym` build ever gives file:line from the binary alone. No debug/strip overrides are set in `Configuration/*.xcconfig`, so Xcode's archive defaults apply: the installed product is stripped (correctly — see Notes) and the dSYM is the sole carrier of symbols.

**The deletion is deliberate and its reason is legitimate.** The comment block at `release.sh:361-365` documents it as the fix for **#0026**: leaving a Release `Batty.app` in `build/` makes LaunchServices index it alongside the Debug build in DerivedData, both claiming bundle id `co.sstools.Batty`, so tapping a notification can route to either and two Batty dock icons appear. Any fix here must preserve that protection. The remedy was aimed at the `.app`; the dSYM was collateral.

## Steps to reproduce

1. Run `scripts/release.sh` to completion (do not do this autonomously — see Notes; the mechanism is fully established by reading the script).
2. Observe `dist/` contains `Batty-<sha>.dmg` and nothing else; `build/` no longer exists.
3. Receive a crash report from the field for that build. Run `mdfind "com_apple_xcode_dsym_uuids == <binary UUID>"` — no result on any machine. The report's Batty frames cannot be resolved to file:line.

## Expected behavior

Every release preserves its dSYM as a durable artifact, **zip-archived** (the user's explicit instruction — zipping keeps Spotlight from indexing it and causing side effects; see Notes for the tradeoff this accepts):

- Before the `rm -rf "$BUILD_DIR"` at `release.sh:366`, copy/zip `build/Batty.xcarchive/dSYMs/Batty.app.dSYM` into `dist/` — e.g. `dist/Batty-$GIT_SHA-dSYM.zip`, matching the DMG's git-sha keying.
- **The dSYM must be unambiguously matchable to a crash report.** Crash reports identify the binary by UUID, not by sha, so record the binary UUID (from `dwarfdump --uuid`) in the release notes or a sidecar text file next to the zip. This is an explicit acceptance criterion: a dSYM that cannot be confidently paired with a crash is nearly worthless.
- The #0026 protection stays intact: `build/` is still fully removed; no `.app` survives outside the DMG.

Verification the implementer must perform (without running a full notarized release — see Notes):

- `dwarfdump --uuid` on the unzipped dSYM prints the same UUID as `dwarfdump --uuid` on the built `Batty.app/Contents/MacOS/Batty`.
- `atos -o <dSYM>/Contents/Resources/DWARF/Batty -arch arm64 -l <load addr> <addr>` resolves a known address to a plausible symbol.

## Actual behavior

The dSYM exists transiently inside `build/Batty.xcarchive/dSYMs/` during the release, is never copied anywhere, and is deleted by `rm -rf "$BUILD_DIR"` at the end of every successful run. Release 1.1.0 (20260805) shipped this way; its crash in #0311 cannot be symbolicated.

## Notes

**Tradeoff accepted by zipping — recorded, not buried.** Spotlight indexing of dSYMs is a feature, not a side effect: `mdfind "com_apple_xcode_dsym_uuids == <uuid>"` is precisely how Xcode and `atos` auto-locate a dSYM by UUID, and it is the exact query run while investigating #0311. Zipping defeats that lookup, making symbolication a manual unzip-first step. Note also that the #0026 hazard was LaunchServices registering a second *executable* `.app` — a dSYM is not executable and would not hit that path, so the #0026 rationale does not itself argue for zipping; zipping remains defensible for size and for keeping `dist/` tidy. The user has explicitly chosen the zip; the cost is accepted. There is a middle option the implementer should raise rather than silently pick: keep the zip in `dist/` for distribution/archival **and** leave an unzipped copy in a developer-local, non-distributed location so `mdfind` still works.

**Restricted area.** `scripts/` is restricted per `CLAUDE.md`, but the user has authorized modifying `release.sh` for this specific purpose. The standing rule still applies: **do not run `scripts/release.sh` autonomously** — notarization submits the binary to Apple. The fix therefore needs a verification strategy that does not require a full notarized release: exercise the archive + dSYM-copy stage only (e.g. run through the `xcodebuild archive` step and the new copy/zip logic, then stop), or add a dry-run path that skips notarization. Either way, the `dwarfdump`/`atos` checks above must actually run against a real archived dSYM.

**Do not touch strip settings.** `Configuration/Build.xcconfig` is a restricted area, and stripping the shipped binary is correct anyway — the dSYM is the right place for symbols. This issue is about retention, not about changing what ships.

**Beta builds.** Consider whether `scripts/build-beta.sh` should retain dSYMs too — Beta is what gets exercised during development, so its crashes are at least as likely. Flagged for the implementer to assess; not required for this issue if it expands scope unreasonably.

**Retention.** dSYM zips are large-ish; one per release will accumulate in `dist/`. A retention policy may eventually be wanted. Flagged only — do not solve here.

**Verified vs. proposed.** Verified directly in the current tree, 2026-08-07: `release.sh:20/:22` (archive path under `build/`), `:312-313` (only the DMG reaches `dist/`), `:361-366` (#0026 cleanup comment and `rm -rf "$BUILD_DIR"`), zero occurrences of `dSYM` in `release.sh`, `.gitignore:3/:8` (`build/`, `dist/`), no strip/debug overrides in `Configuration/*.xcconfig`, and the empty `mdfind` result for the 1.1.0 binary UUID. Proposed (implementation decisions, not yet verified): the `Batty-$GIT_SHA-dSYM.zip` naming, the sidecar-UUID mechanism, the Beta extension, and the dry-run verification path.

## Root cause

`scripts/release.sh` archived into `$BUILD_DIR/Batty.xcarchive` (`:22`), which puts the dSYM at `build/Batty.xcarchive/dSYMs/Batty.app.dSYM` — a location whose sole reader is the export step a few lines later. Nothing downstream ever read the dSYM again, and the `rm -rf "$BUILD_DIR"` at the end of a successful run (the deliberate #0026 fix for LaunchServices double-registering a Release `Batty.app`) took it out along with the `.app`. The dSYM was collateral damage of a cleanup step aimed at a different file.

## Fix

Two additions to `scripts/release.sh`, both gated to never weaken the #0026 protection (`build/` is still fully removed every time):

1. **Fail-fast existence/UUID check**, right after `xcodebuild archive` and before the slow export/notarize path (`DSYM_PATH="$ARCHIVE_PATH/dSYMs/$APP_NAME.app.dSYM"`; `dwarfdump --uuid` on it). Scoped specifically to `Batty.app.dSYM` — that is the one whose absence must be fatal. If it's missing or `dwarfdump` can't read it, the script exits 1 immediately — no notarization submission for a release that couldn't be symbolicated anyway. Failing before the ~10-minute notarize round trip, not after, was a deliberate placement choice.
2. **Preservation step**, moved (after review round 1) to run right after the version-consistency gate — before the DMG/notarize/staple steps, not after them:
   - `dist/Batty-$GIT_SHA-$BUILD_NUMBER-dSYM.zip` — **the whole `dSYMs/` directory**, zipped (`ditto -c -k --sequesterRsrc --keepParent "$ARCHIVE_PATH/dSYMs" "$DSYM_ZIP"`), not just `Batty.app.dSYM`. A real archive carries six dSYMs: `Batty.app.dSYM`, `Sparkle.framework.dSYM`, `Installer.xpc.dSYM`, `Downloader.xpc.dSYM`, `Autoupdate.dSYM`, `Updater.app.dSYM`. Sparkle runs in-process, so a Sparkle crash lands in a *Batty* crash report as unsymbolicated frames in the Sparkle image; the XPC services and Updater crash as their own processes. Batty ships auto-update, so all of these are live surface, and the marginal cost is small next to the app dSYM's own size (measured below). See Gotchas for why `--sequesterRsrc` specifically is required.
   - `dist/Batty-$GIT_SHA-$BUILD_NUMBER-dSYM.txt` — sidecar text file recording git sha, build number, marketing version, the zip's basename, `dwarfdump --uuid` output for **all six** dSYMs (every architecture's UUID, each on its own line, with a path relative to the zip's own internal layout — see below), and a copy-pasteable `unzip` + `atos` recipe for the main app dSYM plus a note on how to symbolicate the other five. This is the piece that makes the archive matchable to a crash report — a crash report names the binary by UUID, `dist/` is keyed by git sha, and this file is the join.
   - The recorded `dwarfdump --uuid` output uses **relative paths** (`cd "$ARCHIVE_PATH" && dwarfdump --uuid dSYMs/*.dSYM`), not the absolute `$BUILD_DIR/...` paths `dwarfdump` would otherwise print. `$ARCHIVE_PATH` lives under `$BUILD_DIR`, which the cleanup step deletes — a sidecar recording paths that can't exist by the time anyone reads it would be actively misleading. The relative form (`dSYMs/Batty.app.dSYM/...`) also matches the zip's own internal layout exactly.
   - A **best-effort** copy of the *entire* `.xcarchive` (not just the dSYMs) into `~/Library/Developer/Xcode/Archives/<date>/Batty <build>-<sha>.xcarchive` — the same directory tree Xcode's own Organizer uses for archives it creates. This is the "middle option" flagged in the issue's Notes rather than picked silently: it keeps `mdfind "com_apple_xcode_dsym_uuids == <uuid>"` working on the machine that produced the release (the exact query that came up empty during #0311's investigation), without touching the zip-in-`dist/` choice for the distributed/durable copy. **Reviewer-confirmed safe against #0026**: macOS does not descend into `.xcarchive` packages for LaunchServices registration or Spotlight content indexing — the reviewer built two identical `.app` bundles under the Archives date directory, one loose and one inside an `.xcarchive`; the loose one was registered and indexed within seconds (including the `NOTIFICATION#:` activity type #0026 was about), the one inside the `.xcarchive` was neither, and `mdfind` still found the archived dSYMs by UUID within seconds. `rm -rf "$LOCAL_ARCHIVE_DEST"` runs immediately before the `ditto` copy (added after review round 1) so a same-day re-release at the same sha replaces the previous attempt deterministically instead of `ditto` merging into it. Failure to write it (permissions, disk space, whatever) prints a warning and does not fail the release — this is a nice-to-have local convenience, not the acceptance criterion.
3. The final "Done." summary block now also prints the dSYM zip path and points at the UUID sidecar file.

**Why moved before notarization (review round 1):** the block originally ran after `notarytool submit --wait`, `stapler staple`, and DMG creation. All of those run under `set -euo pipefail`; if any failed, the script aborted *before* `rm -rf "$BUILD_DIR"`, leaving a Release `Batty.app` in `build/` — the exact #0026 condition — and skipping appcast emission. The preservation block's own writes (~40 MB zip, ~125 MB archive copy for this project's binary sizes) have their own failure mode (ENOSPC), and running them after a ~10-minute notarization round trip meant a disk-space failure there wasted that round trip *and* still stranded `build/`. Moved to right after the version-consistency gate (where `ACTUAL_SHORT` already exists), with `GIT_SHA` hoisted up to the same point (previously computed later, in the DMG section) — this ensures the dSYM is safely in `dist/` before the expensive, more failure-prone remote steps run at all, and doesn't change when `rm -rf "$BUILD_DIR"` itself runs (still last, after the DMG is stapled and verified).

**Naming decision:** `Batty-$GIT_SHA-$BUILD_NUMBER-dSYM.{zip,txt}`, extending the existing `Batty-$GIT_SHA.dmg` convention with the build number. Justification: #0311's crash report identified the build by `CFBundleVersion` (`20260805`), not by git sha, so an operator holding a crash report and searching `dist/` benefits from the build number being in the filename, not just inside the sidecar.

**Beta builds (raised, not implemented):** assessed and intentionally out of scope. `Batty.xcodeproj/project.pbxproj` sets `DEBUG_INFORMATION_FORMAT = dwarf` for Debug and `dwarf-with-dsym` only for Release; `scripts/build-beta.sh` builds `CONFIGURATION=Debug`, so it never produces a dSYM bundle to begin with — there is nothing for a Beta-side version of this fix to preserve today. If Beta ever switches to `dwarf-with-dsym`, this should be revisited.

## Review

Opus review, round 1: **request-changes**. Core approach (fail-fast check, zip + sidecar, `.xcarchive` middle option) approved; two independent findings confirmed the design was sound (the `.xcarchive`/#0026 non-interaction, and that every variable including `ACTUAL_SHORT` is assigned before use under `set -euo pipefail`). Two required changes: (1) preserve the whole `dSYMs/` directory, not just `Batty.app.dSYM` (Sparkle/XPC/Updater dSYMs were missing); (2) move the whole preservation block to before notarization/DMG/staple, since a failure in those (or in the block's own ~165 MB of writes) after round 1's placement could abort the script before `rm -rf "$BUILD_DIR"`, stranding the #0026 condition. Also corrected: the `--sequesterRsrc` note understated the failure mode (no UUID lines printed at all without it, not "correct UUIDs alongside a spurious error"); the sidecar recorded soon-to-be-deleted `$BUILD_DIR` paths; the local archive copy could merge with a stale same-day leftover instead of replacing it. All addressed in round 2; see Fix and Verification below. Round 2 not yet re-reviewed as of this writing.

## Gotchas

- `ditto -c -k --keepParent` **without** `--sequesterRsrc` pollutes the zip with AppleDouble `._*` files wherever the source carries extended attributes (every `xcodebuild`-produced file here has `com.apple.provenance` set) — including inside `Contents/Resources/DWARF/`. On the unzipped result this doesn't just add noise: `dwarfdump --uuid` on the affected directory prints **only** the "not a valid object file" error and **no UUID lines at all** (reviewer-confirmed; round-1 verification here originally understated this as "correct UUIDs printed alongside a spurious error," which was wrong). Always use `--sequesterRsrc` when zipping a dSYM (or any Xcode-produced bundle) with `ditto`.
- The local `~/Library/Developer/Xcode/Archives/<date>/` copy is intentionally best-effort/non-fatal — a release must not fail because the operator's `$HOME` is unusual or out of space. It also means that path is **not** an acceptance criterion; the `dist/` zip + sidecar `.txt` is the durable, required artifact. It is also **~125 MB per release** (the full `.xcarchive`, dSYMs included), accumulates indefinitely under `~/Library/Developer/Xcode/Archives/` with no pruning, and sits entirely outside both the repo and `.gitignore`'s reach (it's real Xcode Organizer state, not a build artifact this project owns) — same "flagged, not solved here" category as the `dist/` retention note below, just a second location with the same shape of problem. Whoever eventually designs a retention policy for the `dist/` zips should look at this location too.
- Did not modify `scripts/build-beta.sh` — Beta builds Debug configuration, which uses `DEBUG_INFORMATION_FORMAT = dwarf` (no dSYM emitted at all), so there is currently nothing for a Beta-side fix to preserve. Flagged in `## Fix` for revisiting if that ever changes.
- Retention of accumulating dSYM zips in `dist/` (and now the `.xcarchive` copies under `~/Library/Developer/Xcode/Archives/`, see above) is unaddressed, per the issue's own Notes that it's flagged only, not to be solved in this issue.
