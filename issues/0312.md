# 0312 — release.sh deletes the dSYM with build/, so no shipped release can be symbolicated from a field crash report

| | |
|---|---|
| **Status** | open |
| **Module** | Build |
| **Platform** | macOS |
| **First seen** | 2026-08-07 |

## Description

`scripts/release.sh` destroys the dSYM of every release it builds. The archive lands in `build/` (`ARCHIVE_PATH="$BUILD_DIR/$APP_NAME.xcarchive"`, `release.sh:22`, with `BUILD_DIR="$REPO_ROOT/build"`, `:20`), so the debug symbols end up at `build/Batty.xcarchive/dSYMs/Batty.app.dSYM` — and the cleanup step at the end of a successful release runs `rm -rf "$BUILD_DIR"` (`release.sh:366`), deleting the archive and the dSYM with it. The string `dSYM` never appears anywhere in `release.sh`; nothing copies it out before the delete. `dist/` receives only `Batty-$GIT_SHA.dmg` (`:313`, via `WORK_DMG` at `:312`), and both `build/` and `dist/` are gitignored (`.gitignore:3`, `:8`), so once the script finishes, the symbols are gone from every machine, permanently.

The cost is not hypothetical — it has already been paid. **#0311** is a real field crash of release 1.1.0 (20260805) that is currently blocked on exactly this: six unsymbolicated Batty frames (`+51236`, `+46664`, `+304636`, `+305944`, `+1062472`, `+1063128`, load address `0x1023d4000`, binary UUID `d164cb47-89b6-37fc-90b6-23c6bcd5c6bd`). With the dSYM, those resolve to file:line in one `atos` invocation and the trapping statement is named. Without it, #0311 rests on source reading and a register hint that may be incidental. Both machines were searched: `mdfind "com_apple_xcode_dsym_uuids == d164cb47-…"` returns nothing, and `dist/` on the MacBook holds only DMGs and release notes.

The shipped binary is not a substitute. DWARF debug info is emitted into the `.o` files at compile time and collected by `dsymutil` into the `.dSYM` bundle during archiving — it is never present in the shipped executable. A binary yields function-level symbols at best, and only when unstripped; no `dwarf-with-dsym` build ever gives file:line from the binary alone. No debug/strip overrides are set in `Configuration/*.xcconfig`, so Xcode's archive defaults apply: the installed product is stripped (correctly — see Notes) and the dSYM is the sole carrier of symbols.

**The deletion is deliberate and its reason is legitimate.** The comment block at `release.sh:361-365` documents it as the fix for **#0026**: leaving a Release `Batty.app` in `build/` makes LaunchServices index it alongside the Debug build in DerivedData, both claiming bundle id `co.sstools.Batty`, so tapping a notification can route to either and two Batty dock icons appear. Any fix here must preserve that protection. The remedy was aimed at the `.app`; the dSYM was collateral.

## Steps to reproduce

1. Run `scripts/release.sh` to completion (do not do this autonomously — see Notes; the mechanism is fully established by reading the script).
2. Observe `dist/` contains `Batty-<sha>.dmg` and nothing else; `build/` no longer exists.
3. Receive a crash report from the field for that build. Run `mdfind "com_apple_xcode_dsym_uuids == <binary UUID>"` — no result on any machine. The report's Batty frames cannot be resolved to file:line.

## Expected behavior

Every release preserves its dSYM as a durable artifact, **zip-archived** (the user's explicit instruction — zipping keeps Spotlight from indexing it and causing side effects; see Notes for the tradeoff this accepts):

- Before the `rm -rf "$BUILD_DIR"` at `release.sh:366`, copy/zip `build/Batty.xcarchive/dSYMs/Batty.app.dSYM` into `dist/` — e.g. `dist/Batty-$GIT_SHA-dSYM.zip`, matching the DMG's git-sha keying.
- **The dSYM must be unambiguously matchable to a crash report.** Crash reports identify the binary by UUID, not by sha, so record the binary UUID (from `dwarfdump --uuid`) in the release notes or a sidecar text file next to the zip. This is an explicit acceptance criterion: a dSYM that cannot be confidently paired with a crash is nearly worthless.
- The #0026 protection stays intact: `build/` is still fully removed; no `.app` survives outside the DMG.

Verification the implementer must perform (without running a full notarized release — see Notes):

- `dwarfdump --uuid` on the unzipped dSYM prints the same UUID as `dwarfdump --uuid` on the built `Batty.app/Contents/MacOS/Batty`.
- `atos -o <dSYM>/Contents/Resources/DWARF/Batty -arch arm64 -l <load addr> <addr>` resolves a known address to a plausible symbol.

## Actual behavior

The dSYM exists transiently inside `build/Batty.xcarchive/dSYMs/` during the release, is never copied anywhere, and is deleted by `rm -rf "$BUILD_DIR"` at the end of every successful run. Release 1.1.0 (20260805) shipped this way; its crash in #0311 cannot be symbolicated.

## Notes

**Tradeoff accepted by zipping — recorded, not buried.** Spotlight indexing of dSYMs is a feature, not a side effect: `mdfind "com_apple_xcode_dsym_uuids == <uuid>"` is precisely how Xcode and `atos` auto-locate a dSYM by UUID, and it is the exact query run while investigating #0311. Zipping defeats that lookup, making symbolication a manual unzip-first step. Note also that the #0026 hazard was LaunchServices registering a second *executable* `.app` — a dSYM is not executable and would not hit that path, so the #0026 rationale does not itself argue for zipping; zipping remains defensible for size and for keeping `dist/` tidy. The user has explicitly chosen the zip; the cost is accepted. There is a middle option the implementer should raise rather than silently pick: keep the zip in `dist/` for distribution/archival **and** leave an unzipped copy in a developer-local, non-distributed location so `mdfind` still works.

**Restricted area.** `scripts/` is restricted per `CLAUDE.md`, but the user has authorized modifying `release.sh` for this specific purpose. The standing rule still applies: **do not run `scripts/release.sh` autonomously** — notarization submits the binary to Apple. The fix therefore needs a verification strategy that does not require a full notarized release: exercise the archive + dSYM-copy stage only (e.g. run through the `xcodebuild archive` step and the new copy/zip logic, then stop), or add a dry-run path that skips notarization. Either way, the `dwarfdump`/`atos` checks above must actually run against a real archived dSYM.

**Do not touch strip settings.** `Configuration/Build.xcconfig` is a restricted area, and stripping the shipped binary is correct anyway — the dSYM is the right place for symbols. This issue is about retention, not about changing what ships.

**Beta builds.** Consider whether `scripts/build-beta.sh` should retain dSYMs too — Beta is what gets exercised during development, so its crashes are at least as likely. Flagged for the implementer to assess; not required for this issue if it expands scope unreasonably.

**Retention.** dSYM zips are large-ish; one per release will accumulate in `dist/`. A retention policy may eventually be wanted. Flagged only — do not solve here.

**Verified vs. proposed.** Verified directly in the current tree, 2026-08-07: `release.sh:20/:22` (archive path under `build/`), `:312-313` (only the DMG reaches `dist/`), `:361-366` (#0026 cleanup comment and `rm -rf "$BUILD_DIR"`), zero occurrences of `dSYM` in `release.sh`, `.gitignore:3/:8` (`build/`, `dist/`), no strip/debug overrides in `Configuration/*.xcconfig`, and the empty `mdfind` result for the 1.1.0 binary UUID. Proposed (implementation decisions, not yet verified): the `Batty-$GIT_SHA-dSYM.zip` naming, the sidecar-UUID mechanism, the Beta extension, and the dry-run verification path.
