## Description

When a request names no Window, Session, Pane or Tab, Batty picks the target Window through three different fallbacks, and none of them is the Window the user last worked in. XPC verbs, menu commands and the command palette use `keyWindowRuntime() ?? windows.first`. When no content Window is key, that gives the **oldest** surviving Window. `batty <path>` uses `anyContentWindowRuntime()`. On `main` that gives an arbitrary registered Window, in `Dictionary` order. On `issue/0437` it gives the **newest** registered Window.

The common CLI case hits this. A user works in Window B, switches to another app (a terminal elsewhere, an editor, a script runner), and runs `batty pane split` or `batty notify`. Batty is not active, so `NSApp.keyWindow` is nil and `keyWindowRuntime()` returns nil. The verb then lands in Window A, which the user may not have touched in hours. A `batty <path>` run in the same situation can land in yet another Window. This works against the release goal that the CLI reliably controls the app (#0413): the same no-target command can act on different Windows depending on which code path serves it.

There should be one documented policy, "the most recently key content Window", served by one helper that every no-target fallback uses.

## Premises checked in code (read-only)

Checked on `main` at `6fdb3343` and on `issue/0437` at `fbd13f71` (`git show issue/0437:<path>`). #0437 changes only `anyContentWindowRuntime()` and `WindowIDRegistrar` among the code below. Every other line cited is identical on both.

1. **The key-Window lookup is nil whenever Batty is not active.** `keyWindowRuntime()` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:758-762`) looks up `NSApplication.shared.keyWindow` in `nsWindowMap`. When the app deactivates, AppKit resigns key on its Window, so `keyWindow` is nil and this returns nil. The same is true when a non-content Window (Settings, an alert, a panel) is key, because only content Windows are in `nsWindowMap`. The implementer should confirm the app-inactive case with a log line. The code has no other path to a Window, so the fallback always decides.
2. **The fallback is "oldest", by construction.** `windows` is append-only: `windowRuntime(for:)` only appends (`AppStateStore.swift:151-176`, append at `:174`), and `removeWindow(id:)` only removes (`:181-184`). `windows.first` is therefore the oldest surviving Window. It is not filtered through `nsWindowMap`, so in principle it can also be a runtime whose `NSWindow` has not registered yet.
3. **`batty <path>` uses a different fallback.** `addSession` (`AppStateStore.swift:905`) resolves `anyContentWindowRuntime() ?? windows.first`. On `main`, `anyContentWindowRuntime()` (`:810-815`) returns `nsWindowMap.values.first`, which is undefined order. On `issue/0437` it returns `windows.last { registeredIDs.contains($0.id) }`, the newest registered Window. #0437's doc comment gives the reason: "the one a CLI invocation with no explicit target is most likely meant to reach." The other fallbacks were not changed to match. `batty <path>` goes through `/usr/bin/open` with a `batty://` URL (`BattyKit/Sources/batty/SessionCommand.swift:51-73`), which activates Batty. So a key Window often exists by the time `BattyURLHandler.handle` runs (`BattyKit/Sources/BattyKit/Runtime/BattyURLHandler.swift:28`), but that depends on activation ordering and is not guaranteed. XPC verbs never activate the app.
4. **Nothing records which content Window was last key.** `git grep` finds no `didBecomeKeyNotification` or `windowDidBecomeKey` in the sources. `WindowDelegate` (`BattyKit/Sources/BattyKit/Views/RootWindowView.swift:156-256`) implements only `windowShouldClose`, `windowWillClose` and `windowDidChangeOcclusionState`.

## Call sites that resolve a no-target Window

### XPC (CLI) verbs, through the `focused*IDFallback` helpers

The helpers are `sessionInfoPayload(sessionID: nil)` (`AppStateStore.swift:384`), `focusedSessionIDFallback()` (`:403-408`, lookup at `:404`), `focusedPaneIDFallback()` (`:419-424`, lookup at `:420`) and `focusedTabIDFallback()` (`:441-453`, lookup at `:443`, which also calls `focusedPaneIDFallback()` at `:442`). Each one does `keyWindowRuntime() ?? windows.first`.

In `BattyKit/Sources/BattyKit/XPC/AppXPCService.swift`, eight verbs use them:

|---|---|---|
| `paneSplit` | `:121` | `focusedPaneIDFallback()` |
| `paneClose` | `:173` | `focusedPaneIDFallback()` |
| `notify` | `:206` | `focusedTabIDFallback()` |
| `sessionFocus` | `:233` | `focusedSessionIDFallback()` |
| `paneFocus` | `:260` | `focusedPaneIDFallback()` |

A ninth verb, `sessionInfo` (`:94`), uses `sessionInfoPayload(sessionID: nil)`, so `batty session info` with no id reports the oldest Window's Session. `paneShow` requires an explicit id (`:377`). `list` and `status` do not target anything. The `watch` verb's topology snapshot (`:435`) takes `snapshot.windows.first?.sessions.first` as its event's `sessionID`. That is the same "first Window" choice, but it labels an event rather than acting on something, so it is lower priority. It should still follow the policy if cheap.

These verbs are also covered by payload doc comments that name the fallback: `BattyKit/Sources/BattyXPCCore/{PaneSplit,PaneClose,PaneFocus,PaneHide,SessionClose,SessionFocus,TabFocus,Notify}Payload.swift` and `TopologyPayload.swift:265`. Those comments need rewording if the policy changes. `UITestDriver.swift:137` also uses `focusedPaneIDFallback()`, but it is test-only.

### Menu commands, the command palette, and app-global actions, through `keyWindowOrFirstRegistered()`

`keyWindowOrFirstRegistered()` (`AppStateStore.swift:778-780`) is `keyWindowRuntime() ?? windows.first`. Despite its name, it does not filter through registration.

- `BattyCommands.keyWindow` (`BattyKit/Sources/BattyKit/Commands/BattyCommands.swift:50`) feeds every menu action and `.disabled` check: New Session (`:62`, `:92`), session selection by index (`:112`), splits and typed-pane splits (`:238-320`), `:323`, `:332`, Focus Pane (`:353-377`), Resize Split (`:387-411`), New Tab (`:438`), Close Tab (`:446-458`), Previous/Next Tab (`:471`, `:479`), tab by index (`:490`), and the helpers at `:508-524`. The fallback matters when Batty is active but the key Window is not a content Window. For example, with Settings key, File > New Session adds a Session to the oldest Window, not the one the user just left.
- `CommandPaletteView` (`BattyKit/Sources/BattyKit/Views/CommandPaletteView.swift:72` Duplicate Session, `:204` `dispatch(_:)`).
- `focusedTerminalTab` (`AppStateStore.swift:799-801`), which `ExitDispatcher` (`BattyKit/Sources/BattyKit/Commands/ExitDispatcher.swift:27-34`) and `PasteConfirmation` (`BattyKit/Sources/BattyKit/Views/PasteConfirmation.swift:80`, `:105`) use.
- `markActiveTabSeen()` (`AppStateStore.swift:1356-1358`).
- The action shims `moveSessions`, `selectSession`, `closeFocusedTab`, `requestCloseFocusedTab`, `confirmPendingClose` and `cancelPendingClose` (`AppStateStore.swift:956`, `:966`, `:989`, `:1009`, `:1029`, `:1038`).

### `batty <path>`, through `anyContentWindowRuntime()`

- `addSession` (`AppStateStore.swift:905`), called from `BattyURLHandler.swift:28`. On `main` it picks in `Dictionary` order. On `issue/0437` it picks the newest registered Window.

### Related, not a fallback target

- `recordBellTick` (`AppStateStore.swift:1370`), `recordDesktopNotification` (`:1419`) and `recordCLINotification` (`:1489`) treat `keyWindowRuntime() == nil` as single-window mode for bell seen-ness. When Batty is inactive with several Windows open, a bell in any Window's focused Tab counts as seen. This is a policy question about seen-ness, not about targeting. Consider it while changing the helper, but it does not have to move with it.
- `BattyShortcuts.handle` (`:34`, `:48`, `:113`) and the notification receivers (`RootWindowView.swift:62`, `SessionDetailView.swift:273`) must keep requiring a *currently* key content Window. A keystroke can only come from the key Window, and those paths correctly do nothing without one. They must not adopt the new fallback.

## Steps to reproduce

1. Launch Batty. In Window A, note the Session name. Press Shift-Cmd-N to open Window B and click into it.
2. Switch to another app, such as Terminal.app, so Batty is not active.
3. From that app, run `batty-beta notify "hello"` (or `batty-beta pane split`, or `batty-beta session info`) with no `--tab`, `--pane` or `--session`, and with `BATTY_*_ID` unset.
4. Separately, with Batty still in the background, run `batty-beta <some-dir>`.

## Expected behavior

Every no-target request resolves the same Window: the content Window that was most recently key. In step 3 that is Window B. If that Window has closed, the request goes to the next most recently key Window still open. If no content Window has ever been key, it goes to the newest registered Window, and only then to `windows.first` (the headless unit-test case). `batty <path>` in step 4 targets the same Window.

## Actual behavior

This is predicted from the code and has not been reproduced by hand. Step 3 posts the notification to, splits, or reports on Window A's selected Session. Step 4 lands in the newest registered Window on `issue/0437`, and in an arbitrary one on `main`.

*(Round-trip notes from implementation, kept separate from the Resolution sections `issues/Issues.md` reserves for the orchestrator after review approval.)*

### Root cause (confirmed)

Re-read `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift` at the top of this branch (built on `issue/0437`'s synchronous `RegistrarNSView` registration) and confirmed every premise in the issue's "Premises checked in code" section unchanged:

1. `keyWindowRuntime()` (`:759-763` pre-fix) is nil whenever `NSApplication.shared.keyWindow` is nil or not a registered content window. Confirmed empirically in a unit test (see "NSApp.keyWindow in unit tests" below): `NSApplication.shared.keyWindow` is `nil` in this test host, and calling `makeKeyAndOrderFront(nil)` on a fresh `NSWindow` does not change that (`w.isKeyWindow` stays `false`) — the app-inactive case the issue asked to confirm with a log line is real, and additionally, this test host can't fake "key" at all headlessly.
2. `windows.first` (`keyWindowOrFirstRegistered()`, and the four `focused*IDFallback`/`sessionInfoPayload` fallbacks) was the oldest surviving Window, by construction (`windows` is append-only).
3. `anyContentWindowRuntime()` (pre-fix, from #0437) resolved the newest *registered* Window when no Window was key — a different tier-3 answer from the other fallbacks' oldest-Window default, and neither honored "most recently key."
4. `git grep -e didBecomeKeyNotification -e windowDidBecomeKey` found nothing in production sources before this change — confirmed nothing recorded key history.

### Fix

1. **`AppStateStore.recentlyKeyWindowIDs: [WindowID]`** (`@ObservationIgnored`, oldest-first/most-recent-last) plus **`noteContentWindowBecameKey(_ id:)`** (public, pure — moves `id` to the end, no duplicate) as the single write path.
2. **`NSWindow.didBecomeKeyNotification` observer**, installed app-wide (`object: nil`, `queue: .main`) in `init`, removed in a new `deinit`. Its handler, `handleWindowDidBecomeKey(_:)`, looks the `NSWindow` up in `nsWindowMap` and calls `noteContentWindowBecameKey` only for content windows — Settings/Help/panels are filtered out because they were never registered.
   - `deinit` needed a `nonisolated(unsafe)` on the observation token (`keyWindowObservation: NSObjectProtocol?`): a nonisolated `deinit` can't read a main-actor-isolated stored property whose type is the existential `any NSObjectProtocol` (the compiler won't infer it `Sendable`) — confirmed by a real compile error before adding the annotation. Safe because the property is only ever mutated on the main thread and only read in `deinit`, after every other reference (including a notification callback's `weak self`) is already gone.
   - The observer closure bridges into this main-actor-isolated instance with `MainActor.assumeIsolated`, following the exact pattern already in `AppearanceObserver`'s KVO callback and `AppXPCCoordinator.scheduleBackoffRetry`'s `DispatchWorkItem` — both documented as safe because `queue: .main`/`DispatchQueue.main.asyncAfter` already guarantee the main thread, even though the closure type itself isn't actor-annotated.
3. **Backstop in `registerNSWindow(_:for:)`**: if the just-registered `NSWindow.isKeyWindow` is already `true`, it's noted as most-recently-key immediately, covering the case the issue's Notes flagged — a window becoming key before `RegistrarNSView.viewDidMoveToWindow` runs.
4. **`pruneRecentlyKeyWindowID(_:)`** (private), called from both `unregisterNSWindow` (resolving the `WindowID` via `nsWindowMap` before removing that entry) and `removeWindow(id:)` (belt-and-braces, since `WindowDelegate.windowWillClose` calls both and a test might call either alone).
5. **One resolver, one implementation.** `defaultTargetWindow()` is the full 4-tier policy (key → most-recently-key registered → newest registered → `windows.first`), and `addSession`, `keyWindowOrFirstRegistered()`, `sessionInfoPayload(sessionID: nil)`, `focusedSessionIDFallback()`, `focusedPaneIDFallback()`, and `focusedTabIDFallback()` all call it directly. **Round 1 review correction**: an earlier version of this fix kept `anyContentWindowRuntime()` as a separate method (delegating to a private `registeredTargetWindow()` covering tiers 1–3 only) on the claim that `addSession`'s `anyContentWindowRuntime() ?? windows.first` relied on `anyContentWindowRuntime()` returning `nil` rather than `windows.first` when nothing was registered. That claim was false — `anyContentWindowRuntime() ?? windows.first` and `defaultTargetWindow()` give the identical result in every case, since `addSession`'s own `?? windows.first` already covers exactly the case the split was supposedly protecting, and `addSession` was `anyContentWindowRuntime()`'s only production caller. `anyContentWindowRuntime()` was removed entirely; `addSession` now calls `defaultTargetWindow()` directly. The two tests that pinned the nil-specifically contract (`BattyURLHandlerRoutingTests.anyContentWindowRuntimeIsNilWithoutRegisteredNSWindow`/`...ReturnsRegisteredWindowRuntime`) and the two #0437 tier-3 regression guards (`MultiWindowStoreTests.anyContentWindowRuntimePrefersMostRecentlyCreatedRegisteredWindow`/`...SkipsUnregisteredNewerWindow`) were repointed at `defaultTargetWindow()`, renamed, and re-verified to still guard the same behavior (newest-registered tie-breaking, skip-unregistered-newer) — just via the one remaining method.
6. **`keyWindowOrFirstRegistered()` kept its name** rather than being renamed (the issue's Notes said "consider renaming... since 'first' will no longer be accurate"). Kept because `BattyCommands`, `CommandPaletteView`, and several `AppStateStore` action shims (`moveSessions`, `selectSession`, `closeFocusedTab`, `requestCloseFocusedTab`, `confirmPendingClose`, `cancelPendingClose`, `focusedTerminalTab`) already call it by this name and its own unit test (`CrossWindowBehaviorTests.keyWindowFallbackResolvesToNilWhenNoWindowsRemain`) names it in a doc comment as "the actual production method `BattyCommands.keyWindow` delegates to" — renaming would have meant updating all of those for no behavioral gain, since it now simply forwards to `defaultTargetWindow()`. Its doc comment was rewritten to say plainly that "first" is no longer accurate.
7. **The `watch` verb's topology snapshot** (`AppXPCService.swift`, `subscriptionRequest.sendTopoSnapshot`) now looks up `store.defaultTargetWindow()?.id` and finds the matching entry in the already-built `TopologyPayload.windows` array, falling back to `.first` only if that lookup somehow misses (unreachable — the snapshot is built from the same `windows` array `defaultTargetWindow()` reads). Per the issue's "should still follow the policy if cheap" — this is O(n) over a handful of windows, not a second full topology walk.
8. **Grep-verified the `BattyXPCCore` payload doc comments** the issue's premise #4 called out (`PaneSplit/PaneClose/PaneFocus/PaneHide/SessionClose/SessionFocus/TabFocus/NotifyPayload.swift`, `TopologyPayload.swift:265`). None of them actually describe the *window*-selection policy — they describe the CLI's `--flag → env var → focused-element` resolution chain and just name `AppStateStore.focused*Fallback()`/`sessionInfoPayload(sessionID:)` by reference, without claiming "oldest" or any other window-tier detail. `git grep -n "oldest\|windows\[0\]\|windows.first\|first registered\|arbitrary\|Dictionary order" BattyKit/Sources/BattyXPCCore/*.swift` found nothing — so no edit was needed there. The one doc comment that *did* make a now-stale claim was `AppStateStore.sessionInfoPayload`'s own (not a `BattyXPCCore` payload file): "today that means the key window's selected session, or the first window's selected/first session when no window is key" — rewritten to name `defaultTargetWindow()`'s policy.

## Resolution notes

> 🟢 Resolved 2026-09-24 — every lookup with no explicit target now resolves to the same Window, the one the user last worked in. That covers the 9 CLI/XPC verbs, `batty <path>` (`addSession`), menu commands, the command palette, `session info` and the `watch` label. ## Fix

- **Key-window history.** `AppStateStore` keeps `@ObservationIgnored` `recentlyKeyWindowIDs`, updated by `noteContentWindowBecameKey` from an app-wide `NSWindow.didBecomeKeyNotification` observer that listens on the main queue and holds `[weak self]`.
  - The observer only acts on Windows present in `nsWindowMap`, so Settings, Help and panels are ignored.
  - `registerNSWindow` also records a Window that is already key when it registers.
  - IDs are pruned on unregister and on `removeWindow`.
  - The observer is removed in a new `nonisolated` `deinit`. The token is `nonisolated(unsafe)` because it is written once in `init` and read only in `deinit`.
- **One resolver.** `anyContentWindowRuntime()` is removed and `addSession` calls `defaultTargetWindow()`. `keyWindowOrFirstRegistered()`, the `focused*IDFallback` helpers and `sessionInfoPayload(nil)` delegate to it.
- **Current-key-Window-only paths are unchanged.** `BattyShortcuts` and the per-Window receivers still require a current key Window.
- **`RootWindowView`.** `init` now requires a store, and its toggle receiver reads the injected store.
