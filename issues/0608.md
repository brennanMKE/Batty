## Description

**HIGH. Related to #0601 and #0604.** `RootWindowView.content` calls `store.isWindowSeeThrough(windowRuntime)` in its body. That helper walks every Session's `tree.allPanes`, each terminal Pane's Tabs and their background overrides. In the usual all-opaque window, `contains` never short-circuits, so the window root depends on every tree, Pane, Tab and background override in the window. Any split, close, Tab add/close/reorder, background edit, or divider-drag tick (#0607) in any Session re-runs the root body — the `NavigationSplitView`, the `.environment(\.windowIsSeeThrough)` subtree, `WindowChromeApplier` and `WindowLifecycleController` (whose `updateNSView`s each queue a main-queue block, #0612) — even though the Bool almost never flips. The cost grows with the number of Sessions.

Separately, `WindowSeeThrough.apply` rewrites `titlebarAppearsTransparent`, `backgroundColor` and `ignoresMouseEvents` on every call, changed or not, and it runs after every `WindowChromeApplier` update.

## Plan

Written 2026-11-13 against `issue/0608` at `79925a8d`. I checked the premises in the code. `RootWindowView.swift:53` calls `store.isWindowSeeThrough(windowRuntime)` in `content(_:)`. `AppStateStore.swift:122-129` scans every Session, Pane and Tab. `PaneRuntime.swift:201-204` reads each Tab's override, the Pane's override and `sessionBackgroundOverride`. `WindowSeeThrough.apply` guards only `isOpaque`. `WindowChromeApplier.updateNSView` hops through `DispatchQueue.main.async`. All of these are as the issue describes.

### Decision: move the read into a narrow scope view, not a stored fact

The issue offers two options. I chose the wrapper view, for three reasons:

1. **A stored fact needs too many writers.** A stored `WindowRuntime.isSeeThrough` changes when any of these change: `WindowRuntime.setNativeFullScreen`, Session add, remove or move between windows, every `SplitTree` structural change (split, close, Pane move), Tab add, close or move between Panes, the override setters, and `setAppWideTerminalOpacity`. The override setters are `SessionRuntime.swift:257,267`, `PaneRuntime.swift:214,224,231`, `TabRuntime.swift:299-324` and `SplitTree.swift:237`, and they include the async image-resolution arrivals. None of the Pane or Tab writers knows its window, so each store path would need a recompute call. Missing one leaves the window stuck opaque or stuck see-through, a visible bug that unit tests don't catch.
2. **Deriving it through `withObservationTracking`** would need a deferred main-queue hop to write the result, plus a test seam. That is the hop-a-write shape that `AGENTS.md` warns against.
3. **The wrapper is correct by construction.** The helper stays computed, so its existing tests, including `sessionOverrideInvalidatesAnObservedSeeThroughRead`, keep passing unchanged. Only a small view re-evaluates on a structural change. It hands the `NavigationSplitView` subtree an *equal* `Bool`, so no environment reader is invalidated. The `NavigationSplitView` is built by the parent and stored as a value, so it is not rebuilt.

The scan still runs, inside the scope's body, but it is cheap and no longer re-runs `RootWindowView.body`, `WindowIDRegistrar` or `WindowLifecycleController`. The issue's withObservationTracking test idea (`splittingAnOpaqueSessionDoesNotNotifySeeThroughReaders`) assumed the stored fact. It is replaced by the hosting tests below.

### User checklist

- Set a Pane's (or a Tab's) terminal opacity below 100%: the desktop shows through that terminal and the chrome stays solid. Set it back to 100%, and the window becomes opaque again with no gray flash.
- In an opaque window with several Sessions, split, close, add Tabs and drag dividers: no visible change and nothing stalls.
- Switch Themes with and without a see-through Pane. The title bar color and transparency follow the Theme.
- Enter native full screen with a see-through Pane: the window is opaque. Exit, and it is see-through again.
- With two windows, only the window with a translucent Pane is see-through.

## Rule violated

- `docs/swiftui-observation-rules.md`, "Observation semantics and dependency granularity": computed helpers called from `body` broaden dependencies; pass narrow values.
- swift-guidance `swiftui-observation.md`: a parent body should depend only on the facts it shows; AppKit property writes from update paths should be change-guarded.

## Evidence

- **Proven:** the dependency set and the unguarded writes.
- **Inferred:** the magnitude. Measure with `LayoutConvergenceProbe`.

## Fix direction

- Either store `isSeeThrough: Bool` on `WindowRuntime`, recomputed by the existing writers (Tab/Pane/Session `setBackgroundOverride`, `setAppWideTerminalOpacity`, Pane and Tab create/close, `setNativeFullScreen`) and written only on change. It is `Equatable`, so `RootWindowView` invalidates only on a flip. All writers are event-origin. Or move the read into a small wrapper view that applies only `.environment(\.windowIsSeeThrough)` and `WindowChromeApplier`, so `RootWindowView.body` does not depend on it. The planner chooses; the first removes the scan entirely.
- Guard each property write in `WindowSeeThrough.apply` (`if window.titlebarAppearsTransparent != x`, compare `backgroundColor` before assigning, same for `ignoresMouseEvents`).
