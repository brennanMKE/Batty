# 0608 — RootWindowView.body depends on every Pane in every Session through isWindowSeeThrough, and WindowSeeThrough.apply rewrites unchanged window properties

## Description

**HIGH. Related to #0601 and #0604.** `RootWindowView.content` calls `store.isWindowSeeThrough(windowRuntime)` in its body. That helper walks every Session's `tree.allPanes`, each terminal Pane's Tabs and their background overrides. In the usual all-opaque window, `contains` never short-circuits, so the window root depends on every tree, Pane, Tab and background override in the window. Any split, close, Tab add/close/reorder, background edit, or divider-drag tick (#0607) in any Session re-runs the root body — the `NavigationSplitView`, the `.environment(\.windowIsSeeThrough)` subtree, `WindowChromeApplier` and `WindowLifecycleController` (whose `updateNSView`s each queue a main-queue block, #0612) — even though the Bool almost never flips. The cost grows with the number of Sessions.

Separately, `WindowSeeThrough.apply` rewrites `titlebarAppearsTransparent`, `backgroundColor` and `ignoresMouseEvents` on every call, changed or not, and it runs after every `WindowChromeApplier` update.

## Current state (verified 2026-11-12 on `main` `ce66ca6a`)

- `BattyKit/Sources/BattyKit/Views/RootWindowView.swift:53`: `let isSeeThrough = store.isWindowSeeThrough(windowRuntime)` in `content(_:)`, called from `body`; used at `:63` (`.environment(\.windowIsSeeThrough, …)`) and `:64` (`WindowChromeApplier(palette:isSeeThrough:)`).
- `Runtime/AppStateStore.swift:122-129`: `isWindowSeeThrough` reads `window.isNativeFullScreen`, `window.sessions`, each `session.tree.allPanes`, `pane.kind`, and `effectiveTerminalOpacity(appWide: appWideTerminalOpacity)`.
- `Runtime/PaneRuntime.swift:189-192`: `effectiveTerminalOpacity` reads `tabs`, each Tab's `backgroundOverride`, the Pane's `backgroundOverride` and `sessionBackgroundOverride`.
- `Views/WindowSeeThrough.swift:52-74`, `apply(palette:isSeeThrough:to:)`: unguarded writes at `:54-56` (see-through branch: `titlebarAppearsTransparent`, `backgroundColor`, `ignoresMouseEvents`) and `:64-68` (opaque branch: `titlebarAppearsTransparent`, `backgroundColor`). Only `isOpaque` is guarded.
- `Views/RootWindowView.swift:309-324`, `WindowChromeApplier.updateNSView`: `DispatchQueue.main.async { WindowSeeThrough.apply(…) }`. The doc sanctions this deferred applier because it writes only AppKit window properties; the issue is the volume and the redundant writes, not the hop.

## Rule violated

- `docs/swiftui-observation-rules.md`, "Observation semantics and dependency granularity": computed helpers called from `body` broaden dependencies; pass narrow values.
- swift-guidance `swiftui-observation.md`: a parent body should depend only on the facts it shows; AppKit property writes from update paths should be change-guarded.

## Evidence

- **Proven:** the dependency set and the unguarded writes.
- **Inferred:** the magnitude. Measure with `LayoutConvergenceProbe`.

## Fix direction

- Either store `isSeeThrough: Bool` on `WindowRuntime`, recomputed by the existing writers (Tab/Pane/Session `setBackgroundOverride`, `setAppWideTerminalOpacity`, Pane and Tab create/close, `setNativeFullScreen`) and written only on change. It is `Equatable`, so `RootWindowView` invalidates only on a flip. All writers are event-origin. Or move the read into a small wrapper view that applies only `.environment(\.windowIsSeeThrough)` and `WindowChromeApplier`, so `RootWindowView.body` does not depend on it. The planner chooses; the first removes the scan entirely.
- Guard each property write in `WindowSeeThrough.apply` (`if window.titlebarAppearsTransparent != x`, compare `backgroundColor` before assigning, same for `ignoresMouseEvents`).
