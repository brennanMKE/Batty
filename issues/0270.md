## Description

Second step of the XPC track under umbrella #0265: the broker launch agent that owns the Mach service name. This exists because of two facts the experiment confirmed the hard way: **a plain app cannot publish a named Mach service** (only launchd hands out receive rights), and an **`NSXPCListenerEndpoint` is a live Mach right, not data** — it cannot be written to a file or printed, only sent over an existing XPC connection. So a small broker agent, started on demand by launchd, holds the name; the app registers its endpoint with it (#0271).

**Gate:** blocked on #0269 (shared types) and on the XPC track being green-lit. Do not start speculatively.

## Resolution notes

> 🟢 Resolved 2026-07-25 — the broker launch agent ships, embedded and Developer-ID signed, with `batty ping` as the health check and a registration-state UI that never claims health.

The broker is **Prod-only** by deliberate decision; the cross-variant consequence is recorded in Gotchas and needs the user's sign-off. Live `batty ping` against a launchd-started broker still needs runtime verification.

## Root cause

Starting state, not a defect. Two facts forced this design: a plain app cannot publish a named Mach service (only launchd hands out receive rights), and an `NSXPCListenerEndpoint` is a live Mach right rather than data — it cannot be written to a file or printed, only sent over an existing XPC connection. A small launchd-started broker must therefore own the name.

## Fix

**Broker target** (`BattyBroker`) linking only the dependency-free `BattyXPCCore`, embedded at `Contents/Resources/bin/BattyBroker`, with the agent plist at `Contents/Library/LaunchAgents/co.sstools.Batty.broker.plist` (`MachServices`, bundle-relative `BundleProgram`, no `RunAtLoad`).

**Embedding** uses a single "Embed Broker" Run Script phase mirroring the existing "Embed CLI" phase, rather than the two Copy Files phases the issue's scope literally suggested. The reviewer judged this deviation not merely acceptable but *better*: a Copy Files phase would not have signed the Mach-O, and launchd — unlike Finder or `PATH` — refuses to start an improperly signed agent. The phase codesigns explicitly with `--options runtime`, guarded on `CODE_SIGNING_ALLOWED` so iteration builds still work.

**Prod/Beta:** the broker ships Prod-only. The embed phase checks `PRODUCT_BUNDLE_IDENTIFIER` and skips binary and plist together when it is not `co.sstools.Batty`, so a Beta bundle carries no LaunchAgent at all. The alternative — computing the Mach name from `Bundle.main.bundleIdentifier` at runtime — does not work for a bare Mach-O like the broker or CLI, which have no adjacent `Info.plist` for `Bundle.main` to resolve.

**`batty ping`** reaches the broker via `bootstrap_look_up` and exits `0` on success or `2` (`XPCExitCode.brokerUnreachable`) when the name is unowned. The Settings UI shows registration *state* only and explicitly never claims health, because `SMAppService.status` can report `.enabled` while launchd has no such service.

The CLI gained subcommands (`new` as `defaultSubcommand`, plus `ping`). `open` was deliberately **not** used, leaving #0257's pinned `batty open` (activate/foreground) unclaimed. Bare `batty` and `batty <path>` are unchanged.

## Review

Reviewed by `claude-opus-5`, two rounds.

Round 1 confirmed every headline claim independently — including proving the Prod/Beta skip produces no half-embed in either direction by running the extracted phase script against a pre-populated fake bundle — then required three changes: the `Broker` class had no compile-time guard on its `nonisolated` discipline (stripping it still built), Beta shipped a Settings control that could only fail, and nothing asserted the shipped plist against `ServiceNames`.

Round 2 approved after re-verifying each guard rather than trusting the report. The reviewer went a step further than asked and proved the `exportedObject as any BrokerProtocol` cast is load-bearing rather than decorative: with `nonisolated` stripped **and** the cast removed, the product builds clean — so without the cast the regression would ship silently. They also tested a case the implementer had not: with the plist moved away, all four drift tests fail loudly rather than silently passing, so the `#filePath` seam fails safe.

Worth recording: the implementer's first attempt at verifying the `registerAppEndpoint`/`appEndpoint` guards produced a false "still builds" because the test target had not actually recompiled. Forcing a rebuild confirmed both predicted `[#ActorIsolatedCall]` errors. Guard verification requires a genuine rebuild.

## Gotchas

- **Cross-variant hazard — needs a product decision.** `ServiceNames.broker` is invariant, and Beta still embeds `bin/batty` unconditionally (only the broker and plist are Prod-gated). So a Beta-built `batty ping` resolves and reports against **Prod's** broker whenever Prod's agent is registered on the same Mac — a Beta CLI can report "reachable" for, and once #0271 lands actually drive, the Prod app instead of failing closed. Nothing detects or warns about this at runtime. The practical consequence: every XPC-dependent verb (`batty ping` now, `batty status` in #0271, the reads in #0274) is **permanently Prod-only in practice**, not merely for agent registration.
- **`--timestamp=none` will block notarization.** Copied verbatim from the vendored reference, which never notarized. Batty does ship notarized, and the notary service rejects a Developer ID-signed nested binary with no secure timestamp. `bin/batty`'s adhoc signature is the same underlying gap in another form. Both belong to **#0273** and are named here so that issue does not rediscover them mid-release.
- **`AppServiceProtocol.ping` remains the one unguarded protocol requirement.** `registerAppEndpoint` and `appEndpoint` gained guards this round; `ping` is correctly left to #0271, which adds its first real call site.
- **Verifying an isolation guard requires forcing a genuine rebuild.** A stale test target reports "still builds" and reads as a missing guard when the guard is in fact present.
- **The two Embed phases share `Contents/Resources/bin/` and the coupling is enforced only by phase order.** "Embed CLI" does `rm -rf` on the whole directory, deleting `BattyBroker`, and only works because "Embed Broker" runs afterward and re-creates its missing declared output. A future phase reorder would drop the broker silently with no build error. Comments were added to both phases; see [#0276](0276.md) for the related stale-`inputPaths` defect on the older phase.

## Scope

1. **Broker executable target** in the Xcode app project. Per the port plan, **the app target owns the agent embedding — none of it can live in the package**, because `SMAppService.agent(plistName:)` resolves relative to the *calling* bundle. The broker links the dependency-free shared-types target from #0269 (it sits outside `Contents/Frameworks/` reach, so the #0252 `@rpath` constraint applies to it exactly as to the CLI).
2. **The agent plist** at `Contents/Library/LaunchAgents/<label>.plist` with a `MachServices` key and a bundle-relative `BundleProgram`, **no `RunAtLoad`** (launchd starts it on demand). Plist filename, plist `Label`, `MachServices` key, and the connect-time name are all derived from the single `ServiceNames` constant (#0269) — any mismatch makes launchd *silently* decline to reserve the name.
3. **Two Copy Files phases** (broker binary + plist into the bundle) — see the packaging traps below.
4. **`SMAppService.agent(plistName:)` registration** from the app, plus a minimal status UI so the user can see registration state, including the **`requiresApproval` path**: `SMAppService.register()` can land in `requiresApproval`, requiring the user to enable the app under System Settings → General → Login Items & Extensions — **and until then every CLI command over XPC fails.** On the experiment's dev machine it went straight to `.enabled` with no prompt — explicitly not something to rely on, and it means the approval path cannot be reliably tested. Surface the state honestly rather than assuming approval.
5. **`batty ping`** — the health check that reaches the broker **with the app never launched** (launchd starts the agent on demand). `FINDINGS.md` calls it "the most valuable diagnostic in this repo": if it passes, launchd owns the name; if it fails, nothing app-side is worth looking at. Build it in this child, not later. Exit codes: `0` success, `2` broker unreachable (vocabulary from #0269).
6. **Logging:** the broker joins the shared `Logging.subsystem` from its first commit (see #0269 scope item 5).

## Traps that apply here (copied — the expensive part)

All from the experiment's issue history, not speculation:

- **`dstSubfolderSpec = 1` ("Wrapper") in a Copy Files phase is the `.app` root, not `Contents/`.** Getting it wrong fails signing with "unsealed contents present in the bundle root," which names neither the file nor the phase.
- **Xcode does not sign Mach-O files a script phase drops into the bundle**, and launchd refuses to start an improperly signed agent — surfacing as an opaque registration failure. The agent must be signed with the same team identity as the app. If any part of the embedding is script-driven, sign the dropped Mach-O explicitly.
- **A binary in `Contents/Resources/bin/` is sealed as a *resource*, not nested code**, so `codesign --deep --strict` never mentions it — it looks unsigned when it is not. This already concerns Batty: `bin/batty` lives exactly there. Do not "verify" agent signing with `--deep --strict` alone.
- **`SMAppService` state outlives builds and is keyed to the bundle**, so multiple copies of the app on disk confuse launchd; recovering a wedged dev state can mean `sfltool resetbtm` and a reboot. Expect this during development.
- **`.status` can report `.enabled` while launchd has no such service** (observed directly after `launchctl bootout`). Registration confirmation must come from a round trip (`batty ping`), never from `.status`. The full failed-call-driven repair path is #0272's scope; this child must simply never *trust* `.status` for its UI claim of health.
- **Xcode rewrites `project.pbxproj` while it has the project open** — mid-edit in the experiment it deleted the build configurations of a newly hand-added target and left a dangling build file, surfacing as `error: SWIFT_VERSION '' is unsupported`. Close the project in Xcode (or coordinate with the user) before hand-editing, and note the running-app rule: never relaunch/kill the user's running Batty without asking.
- **Repeated signed local builds are the experiment's single most expensive line item** ($27.43 — a certificate-revocation incident from repeated *signed* builds against an Automatic-signing project). Use `CODE_SIGNING_ALLOWED=NO` on repeated local iteration builds where signing isn't the thing under test.

Note: `Configuration/Build.xcconfig` and `scripts/` are restricted areas per `CLAUDE.md` — if this child needs to touch either, get explicit user confirmation first.
