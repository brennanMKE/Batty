## Description

Second step of the XPC track under umbrella #0265: the broker launch agent that owns the Mach service name. This exists because of two facts the experiment confirmed the hard way: **a plain app cannot publish a named Mach service** (only launchd hands out receive rights), and an **`NSXPCListenerEndpoint` is a live Mach right, not data** — it cannot be written to a file or printed, only sent over an existing XPC connection. So a small broker agent, started on demand by launchd, holds the name; the app registers its endpoint with it (#0271).

**Gate:** blocked on #0269 (shared types) and on the XPC track being green-lit. Do not start speculatively.

## Scope

1. **Broker executable target** in the Xcode app project. Per the port plan, **the app target owns the agent embedding — none of it can live in the package**, because `SMAppService.agent(plistName:)` resolves relative to the *calling* bundle. The broker links the dependency-free shared-types target from #0269 (it sits outside `Contents/Frameworks/` reach, so the #0252 `@rpath` constraint applies to it exactly as to the CLI).
2. **The agent plist** at `Contents/Library/LaunchAgents/<label>.plist` with a `MachServices` key and a bundle-relative `BundleProgram`, **no `RunAtLoad`** (launchd starts it on demand). Plist filename, plist `Label`, `MachServices` key, and the connect-time name are all derived from the single `ServiceNames` constant (#0269) — any mismatch makes launchd *silently* decline to reserve the name.
3. **Two Copy Files phases** (broker binary + plist into the bundle) — see the packaging traps below.
4. **`SMAppService.agent(plistName:)` registration** from the app, plus a minimal status UI so the user can see registration state, including the **`requiresApproval` path**: `SMAppService.register()` can land in `requiresApproval`, requiring the user to enable the app under System Settings → General → Login Items & Extensions — **and until then every CLI command over XPC fails.** On the experiment's dev machine it went straight to `.enabled` with no prompt — explicitly not something to rely on, and it means the approval path cannot be reliably tested. Surface the state honestly rather than assuming approval.
5. **`batty ping`** — the health check that reaches the broker **with the app never launched** (launchd starts the agent on demand). `FINDINGS.md` calls it "the most valuable diagnostic in this repo": if it passes, launchd owns the name; if it fails, nothing app-side is worth looking at. Build it in this child, not later. Exit codes: `0` success, `2` broker unreachable (vocabulary from #0269).
6. **Logging:** the broker joins the shared `Logging.subsystem` from its first commit (see #0269 scope item 5).

## Traps that apply here (copied — the expensive part)

All from the experiment's issue history, not speculation:

- **`dstSubfolderSpec = 1` ("Wrapper") in a Copy Files phase is the `.app` root, not `Contents/`.** Getting it wrong fails signing with "unsealed contents present in the bundle root," which names neither the file nor the phase.
- **Xcode does not sign Mach-O files a script phase drops into the bundle**, and launchd refuses to start an improperly signed agent — surfacing as an opaque registration failure. The agent must be signed with the same team identity as the app. If any part of the embedding is script-driven, sign the dropped Mach-O explicitly.
- **A binary in `Contents/Resources/bin/` is sealed as a *resource*, not nested code**, so `codesign --deep --strict` never mentions it — it looks unsigned when it is not. This already concerns Batty: `bin/batty` lives exactly there. Do not "verify" agent signing with `--deep --strict` alone.
- **`SMAppService` state outlives builds and is keyed to the bundle**, so multiple copies of the app on disk confuse launchd; recovering a wedged dev state can mean `sfltool resetbtm` and a reboot. Expect this during development.
- **`.status` can report `.enabled` while launchd has no such service** (observed directly after `launchctl bootout`). Registration confirmation must come from a round trip (`batty ping`), never from `.status`. The full failed-call-driven repair path is #0272's scope; this child must simply never *trust* `.status` for its UI claim of health.
- **Xcode rewrites `project.pbxproj` while it has the project open** — mid-edit in the experiment it deleted the build configurations of a newly hand-added target and left a dangling build file, surfacing as `error: SWIFT_VERSION '' is unsupported`. Close the project in Xcode (or coordinate with the user) before hand-editing, and note the running-app rule: never relaunch/kill the user's running Batty without asking.
- **Repeated signed local builds are the experiment's single most expensive line item** ($27.43 — a certificate-revocation incident from repeated *signed* builds against an Automatic-signing project). Use `CODE_SIGNING_ALLOWED=NO` on repeated local iteration builds where signing isn't the thing under test.

Note: `Configuration/Build.xcconfig` and `scripts/` are restricted areas per `CLAUDE.md` — if this child needs to touch either, get explicit user confirmation first.

## Out of scope

- App-side anonymous listener, endpoint registration, the CLI connect dance, `batty status` (#0271).
- The failed-call-driven `SMAppService` repair path and all lifecycle hardening (#0272).
- Notarization-grade signing verification and peer validation (#0273) — this child gets the agent running under local development signing, which is all the experiment validated.

## Verification expectations

- Unit tests where logic is extractable (plist-name/`ServiceNames` derivation is already covered by #0269; anything new here, e.g. registration-state mapping for the UI, gets tests). `scripts/build.sh unit` and `scripts/build.sh` green.
- **The live checks are inherently runtime and need a real machine:** `batty ping` succeeds with the app never launched (agent started on demand); the agent appears under `launchctl` for the derived label; the agent binary in the built bundle carries a valid signature (checked directly, not via `--deep --strict`).
- **What genuinely cannot be verified:** the `requiresApproval` Login Items flow (not reliably reproducible even in the experiment) and behavior under a notarized build (deferred to #0273). Say so plainly in Gotchas and name what needs the user's runtime sign-off.
