# 0548 — The title bar above the terminal doesn't drag the window while Terminal Opacity is below 100, though it does above the Sidebar and at 100

## Description

The user's report on Batty Beta, built from `main` at `c3ee2772`:

> "There is a problem in the beta. I cannot seem to drag the window with the title bar over the terminal pane. I can drag from over the sidebar on the left. This is with opacity set to 80% but once I change it to 100% I can drag the window from the title bar. This is a bad regression that needed to be fixed."

**Blocks 1.3.5.** The regression came with see-through windows in [#0539](0539.md): `f98b6109` on `main`, picked to `release/1.3` as `03c6aa43`, which is in `b95e088c`. No tag contains that pick, so shipped 1.3.4 doesn't have it. [#0544](0544.md) removed the feature flag on both branches (`6d977630` on `release/1.3`), so 1.3.5 would ship this to Prod. Fix on `main` first, then `git cherry-pick -x` to `release/1.3`.

**The cause isn't known.** Nothing here has been reproduced by an agent or measured; everything under "Hypotheses" is a candidate.

## Steps to reproduce

1. In Batty Beta, set Terminal Opacity to 80 in Settings → Appearance.
2. Press in an empty part of the title bar above a terminal and drag.
3. Do the same in the title bar above the Sidebar.
4. Set Terminal Opacity back to 100 and repeat step 2.

## Expected behavior

The window follows the pointer in all three drags.

## Actual behavior

Step 2 doesn't move the window. Steps 3 and 4 do.

## What differs between 100 and below 100

From reading the code at `2c3014ff`. `AppStateStore.isWindowSeeThrough` flips, and only these things follow from it:

| Change while see-through | Where | Applies |
|---|---|---|
| `window.isOpaque = false`, then `invalidateShadow()` | `WindowSeeThrough.apply`, `WindowSeeThrough.swift:57-60` | Always |
| `window.backgroundColor` = black at 0.004 | `:55` | Always |
| `window.ignoresMouseEvents = false`, set explicitly | `:56` | Always |
| Backdrop band goes from the Theme color to clear | `backdropFill`, `SessionDetailView.swift:308-315` | **Only with a Theme.** With no Theme it is already `.clear` at 100 |
| Zero-height top band added, painting into the title bar | `SessionDetailView.swift:318-331`, `.allowsHitTesting(false)` | Exists either way once see-through. It paints only with a Theme |
| Sidebar list and footer get a solid fill | `sidebarFill`, `SessionSidebarView.swift` | Always; with a Theme the fill was already there |
| Tab bar and dividers get a solid backing | `chromeBacking` | Always |

Not changed by the flip: the terminal host's position in the `ZStack` (`SessionDetailView.swift:286`), `TerminalHostView.hitTest` (returns `nil` when no terminal is at the point, `TerminalHostView.swift:102-105`), the toolbar (`.toolbar { toolbarItems }`, `:183`), and `titlebarAppearsTransparent` (Theme-driven in both branches). Batty doesn't set `isMovable`, `isMovableByWindowBackground` or `mouseDownCanMoveWindow` anywhere, so title bar dragging is entirely AppKit's default behaviour, and #0539 changed the conditions AppKit decides under.

## Hypotheses

**All unproven. Each needs a measurement before a fix is chosen.** The Plan should start by telling them apart, not by picking one.

1. **AppKit's title bar routing changes when the window goes non-opaque.** Clue, measured in #0539's plan: while opaque, `NSThemeFrame` holds a full-window `NSVisualEffectView`, and AppKit removes it when `isOpaque` goes false. Something that view provided in the hit path, such as answering `mouseDownCanMoveWindow`, may go with it. It fits "works at 100". What's missing is why the Sidebar side would still work. Its new solid fill might be the answer, or the Sidebar's own hosting view may answer differently.
2. **The window server passes the press on, or treats the region differently, because it is nearly transparent.** The window color is 1/255 alpha, and #0539 recorded click-through as **never measured**: its offscreen check reported a miss everywhere, so it said nothing. #0539's probe measured the title bar over the detail column at alpha 1, offscreen and with no real desktop, and that counts against this one, at least with no Theme. The Sidebar has solid paint under its part of the title bar and the detail column doesn't, which fits. If the press goes to the app behind, that app would activate or take the click.
3. **`ignoresMouseEvents = false`, set explicitly, changes how the window takes events.** From memory, the explicit value makes a non-opaque window take events it would otherwise pass on. That should help, not harm, but it is new on this path and trivially removable in a probe.
4. **The clear band removed whatever made the region draggable.** This can hold **only with a Theme**, because with no Theme the band is `.clear` at 100 too and dragging works there. A SwiftUI color view may answer `mouseDownCanMoveWindow` differently from nothing at all (from memory, `NSView`'s default depends on whether the view is opaque; check it).
5. **The terminal host or a clear SwiftUI layer sits under the title bar and takes the press.** Weakest on reading: its frame and `hitTest` don't change with opacity, so it would have to fail at 100 as well. What could still change is a view's answer to `mouseDownCanMoveWindow` once the window or backdrop isn't opaque, which merges into 1 or 4. The host's real frame relative to the toolbar safe area wasn't measured.

**Theme dependence is unknown.** The report doesn't say whether a Theme was active.

### Cheap ways to tell them apart

- **Ask the user two things:** was a Theme active, and does the app behind react to the press (activate, take the click)? A reaction points at 2, and no reaction points at routing inside AppKit (1, 3, 4, 5).
- **No Session selected, while see-through.** `backdropFill` paints solid there. If the title bar drags, paint or the band matters (2 or 4).
- **In-process hit test, no synthetic input.** In a throwaway process, or a temporary log in a Beta build, walk `window.contentView?.superview?.hitTest(point)` at a title bar point over the detail column and over the Sidebar, then the view's `mouseDownCanMoveWindow` and its superviews', opaque versus non-opaque, with and without a Theme. A difference there settles 1, 4 and 5 without touching the window server. This doesn't need a shown window, unlike #0539's click-through check.
- **Remove one change at a time** in a probe: `ignoresMouseEvents`, the band, the alpha of the window color (1/255 versus something visibly higher).
- **Log `sendEvent`** in the VM to see whether a mouse-down reaches the window at all.

Never script input on the host (`AGENTS.md`, "UI test automation"). Anything synthetic goes in the VM.

## Test plan

**A VM UI test should be able to do this.** `BattyUITestHarness.launchBatty()` gives a real app in the real window server, `XCUIElement.frame` reads the window's frame, and `SplitDividerDragTests.swift:46-72` already has the coordinate helper and `press(forDuration:thenDragTo:)` from arbitrary window points. `TerminalSeeThroughTests.swift` already has `withSettings` and `setTerminalOpacity`. No existing test drags a window, so this hasn't been tried in the VM.

Add to `BattyUITests/TerminalSeeThroughTests.swift`:

- **`testTitleBarOverTheTerminalDragsTheWindowBelowFullOpacity`**: the fix's test. Set Terminal Opacity to 80, close Settings, read `app.windows.firstMatch.frame`, press an empty title bar point over the detail column, drag down and right about 60 points, and wait for the frame's origin to move by that amount while its size stays the same. Restore Defaults at the end.
- **`testTitleBarOverTheTerminalDragsTheWindowAtFullOpacity`**: control. The same drag at 100. It passes before and after the fix, so a failure of the first test can't be blamed on the gesture or on the VM.
- **`testTitleBarOverTheSidebarDragsTheWindowBelowFullOpacity`**: control, from the report.

Details for the plan to settle:

- **Choose the point from real frames.** Take the first Pane's frame for `x` and the window's top edge for `y`. Stay clear of the toolbar's buttons, which sit at the trailing end of the same strip, and check that no toolbar button's frame contains the point, otherwise the test would drag from a button.
- **Run the first test before the fix.** It must fail on unfixed code in the VM, with both controls passing. If it passes there, the VM doesn't reproduce the bug: #0539 noted the guest is headless with a paravirtualized GPU, so a pass is evidence, not proof for a real display. Say so in `## Gotchas`, and the user's Mac becomes the only proof.
- **Tier: treat this as UI confirmation.** Although this wasn't filed from a daily run, the behaviour lives in the window server and unit tests can't reach it. The implementer and the reviewer each run `tools/run-ui-tests-vm.sh` with the three filters above, and `TerminalSeeThroughTests` as a whole, since its two click tests have never been reported run for this path. Commit first, because the runner tests `git archive HEAD`.

Unit tests can still pin whatever the fix changes in `WindowSeeThrough.apply` or the fills, in `WindowSeeThroughTests`, with a non-default fixture.

## Other pointer behaviour to retest at opacity below 100

`docs/terminal-pane-requirements.md` §6 covers the inside of a terminal only: click, text selection, scroll, file and text drop, keyboard, IME. **It has no item for the window's chrome**, so #0539's checklist step 5 couldn't have caught this. The fix should add a chrome item to §6.

Retest at 80 and at 0, with and without a Theme, and at 100 as the control. Everything here is unverified at below 100, and any of it may share this cause:

| Behaviour | Why it might be affected | How |
|---|---|---|
| Double-click the title bar over the terminal to zoom | Same hit path as the drag | UI test if practical: it follows the system's title bar double-click setting, so the test must read or set that for the guest. Otherwise the user's checklist |
| Traffic lights | They sit on the Sidebar side with the Sidebar shown, which works per the report. **Collapse the Sidebar**, so they sit over the detail column | User's checklist, or a UI test using the window's standard buttons |
| Title bar drag with the Sidebar collapsed | The whole title bar is then over the detail column | User's checklist, or a variant of the first test |
| Toolbar buttons (Split Horizontally and the rest) | Same strip as the failing drag | UI test: clicking one should do its action |
| Terminal tab bar: click a tab, drag a chip | Directly below the title bar, and it got a new `chromeBacking` | Existing `TabChipRenderingTests` run at 100 only. User's checklist below 100 |
| Split divider drag | Got the same `chromeBacking`, and it is translucent over a clear band | Existing `SplitDividerDragTests` run at 100 only. User's checklist below 100 |
| Window resize from the edges and corners next to a terminal | The same region where a press might not count as the window's | User's checklist |
| Window drag in a window where only one Pane has a local override below 100 | The same flip by a different route | User's checklist |

**User checklist for the fix:** on the user's Mac, at Terminal Opacity 80 and at 0, with and without a Theme, with the Sidebar shown and collapsed: the title bar drags the window, double-click zooms, and the rest of the table behaves as it does at 100.
