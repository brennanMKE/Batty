# 0364 — Batty puts its own app bundle's `Contents/MacOS` on the `PATH` of every shell it spawns, so typing `batty` can exec the app's main binary and launch a new instance

## Description

Every shell Batty spawns inherits `/Applications/Batty.app/Contents/MacOS` on its
`PATH`. On this Mac's case-insensitive APFS volume, `Contents/MacOS/batty` **is**
`Contents/MacOS/Batty` — the app's own 29 MB main executable. So inside any Batty
Pane, the name `batty` is one `PATH` reordering away from resolving to the app
binary instead of the CLI, and executing it starts a brand-new `NSApplication`
process: no LaunchServices, no dedupe, no broker handshake, no CLI code path at
all. This is the most direct known mechanism behind the user's "the CLI KEEPS
LAUNCHING ANOTHER INSTANCE" report in **#0361**, and #0361's fix does not cover
it — see "Why #0361's fix does not reach this" below.

Today the collision is latent, not active: `/usr/local/bin` precedes the app's
`MacOS` directory in `PATH`, so `batty` resolves to the real CLI. It becomes
active the moment that ordering changes or `/usr/local/bin/batty` is absent —
and it is absent by default, because the symlink is only created when the user
opts in from Settings → Advanced (`docs/batty-cli-install.md`,
`BattyKit/Sources/BattyKit/Settings/CLIInstaller.swift`). A fresh install where
the user never visited Settings → Advanced has **no** `/usr/local/bin/batty`,
which means `batty` in a Batty Pane resolves to the app binary on the first try.

## Decision (2026-08-27) — remedy is a PATH env seam plus an `argv[0]` guard; no executable rename

The user has decided the remedy. Implement **both** layers below; do **not**
rename the app's main executable.

1. **PATH env seam.** Stop letting the app bundle's `Contents/MacOS` be the
   directory that answers `batty` in a shell Batty spawns. Batty already injects
   into the spawned environment through libghostty's `env` config directive —
   `TabRuntime.applyShellAndAppearancePreferences` sets `BATTY_TAB_ID` /
   `BATTY_PANE_ID` / `BATTY_SESSION_ID` via `builder.withCustom("env", …)`
   (`BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:225-231`, re-verified
   against `main` on 2026-08-27) — so a `PATH` override has an existing seam.
   Prefer pointing the injected `PATH` at `Contents/Resources/bin`, where the
   real CLI actually lives, ahead of `Contents/MacOS`. **Design risk to settle
   first:** confirm libghostty's `env` directive can *override* an inherited
   `PATH` rather than only add new variables. If it cannot, ship layer 2 alone
   and record that finding here.

   *Settled, 2026-08-27 (implementer); citation corrected, review round 1
   (2026-09-10):* it can override. The original citation here (`ghostty
   +show-config --default --docs` against the real Ghostty 1.3.1 app,
   reasoning from "the closest runnable reference to the pinned
   libghostty-spm b146b73/tag 1.3.2") was a docs-inference stand-in, not
   first-hand source evidence, and also misstated the actual pin — the
   repo's real pin is `a2565ccf047c03c74a59dd7c16a8fac7c477852f` / tag
   `1.5.20260903` (`TabRuntime.swift`'s own neighboring comment states this
   correctly; see `BattyKit/Sources/BattyKit/Runtime/TabRuntimeCLIPathSeam.swift`'s
   doc comment for the corrected citation). Review round 1 verified the
   claim against the actual pinned source instead:
   `src/termio/Exec.zig:819-827` at Ghostty commit `c4e16970` (the commit
   that pin resolves to) shows the `cfg.env_override` loop — `try env.put(entry.key_ptr.*, entry.value_ptr.*)`
   for every configured `env` key — applied *after* `GHOSTTY_BIN_DIR` and its
   `PATH` append (line 692), and `env.put` on the same key unconditionally
   replaces the prior value in that map. Independently re-confirmed here by
   fetching that exact file at that exact commit
   (`https://raw.githubusercontent.com/ghostty-org/ghostty/c4e16970/src/termio/Exec.zig`)
   and reading lines 819-826 directly — the override block does end at line
   826, one line short of the cited range, immaterial to the claim. This is
   now first-hand source evidence, not a docs inference, and layer 1 is
   confirmed live rather than merely documented.
2. **`argv[0]` guard.** Make the app's main binary refuse to act as the CLI when
   it is invoked under the wrong name: at startup, before `NSApplication`
   starts, if `argv[0]`'s basename is case-insensitively equal to `batty`, print
   a one-line pointer to the real CLI (`…/Contents/Resources/bin/batty`, or the
   `/usr/local/bin/batty` symlink installed from Settings → Advanced) on stderr
   and exit. This is the backstop for shells that re-export `PATH` and for any
   invocation that reaches the binary by a path the env seam never touched.

**Rejected: renaming the app's main executable.** It would fix the root cause —
Beta is already immune precisely because its executable is named `Batty Beta` —
but `EXECUTABLE_NAME` / `PRODUCT_NAME` live in `Configuration/`, which
`CLAUDE.md` marks **restricted**, and the name is baked into code signing, the
DMG, and Sparkle's update expectations. The user considered the rename and
judged it too costly for the benefit. **Do not re-propose it.** If a future
reader concludes the rename is the obviously correct fix, this paragraph is the
answer: it was considered and declined on purpose.

Also still rejected, carried over from #0361: `LSMultipleInstancesProhibited` —
already evaluated and deliberately reverted there, and it cannot stop a
non-LaunchServices exec like this one anyway.

**Blast radius of the chosen remedy: contained in `BattyKit`.** Both layers are
Swift changes inside the package (the `TabRuntime` env seam and a startup guard
in the app's entry path); neither touches `Configuration/`, code signing,
notarization, the DMG, Sparkle, or `scripts/`. There is no signing or
release-pipeline impact and no user sign-off needed beyond the usual
`scripts/build.sh unit` + `scripts/build.sh` gate.

## Steps to reproduce

Verified structurally rather than by execution — nothing below launched the app
or ran `batty`, per this session's constraint.

1. In a shell spawned by Batty, run `echo $PATH | tr ':' '\n'`.
   `/Applications/Batty.app/Contents/MacOS` appears in the list.
2. Run `shasum -a 256 /Applications/Batty.app/Contents/MacOS/Batty
   /Applications/Batty.app/Contents/MacOS/batty` — identical digests, because
   both names address the same inode.
3. Remove (or never install) `/usr/local/bin/batty`, or reorder `PATH` so the
   app's `MacOS` directory comes first.
4. Type `batty`. The resolved binary is the app's main executable.

## Expected behavior

Inside a Batty Pane, `batty` either resolves to the `batty` CLI or is not found.
It must never resolve to something that launches an app instance.

## Actual behavior

`batty` can resolve to `/Applications/Batty.app/Contents/MacOS/Batty`, the app's
main executable. Executing it starts another instance of Batty.

## Evidence (verified first-hand, 2026-08-22)

**The case collision is real.** `ls -la /Applications/Batty.app/Contents/MacOS/`
lists exactly one file:

```
-rwxr-xr-x@ 1 brennan  admin  29465536 Aug 21 14:04 Batty
```

and both spellings hash the same:

```
$ shasum -a 256 /Applications/Batty.app/Contents/MacOS/{Batty,batty}
ce0cadd2cbed0e9ad2dfcad5feee39892b1796c155fb4e0b0a121b395bc6461d  …/MacOS/Batty
ce0cadd2cbed0e9ad2dfcad5feee39892b1796c155fb4e0b0a121b395bc6461d  …/MacOS/batty
```

The real CLI is a different, much smaller binary at
`/Applications/Batty.app/Contents/Resources/bin/batty` (4,822,320 bytes).

**The `PATH` entry is present only in Batty-spawned shells.** In a shell whose
process ancestry is `Batty (pid 41541) → /usr/bin/login → zsh`, the app's `MacOS`
directory is the second-to-last `PATH` entry, after `/usr/local/bin`:

```
 9  /usr/local/bin
…
20  /Applications/Batty.app/Contents/MacOS
```

A clean login shell (`env -i /bin/zsh -lc 'echo $PATH'`) has 13 entries and does
**not** include it.

*Correction to the report that prompted this issue:* it described the entry as
"position 20 of 22". In this filer's shell it is position 20 of 21. The absolute
index depends on what else the harness adds; the load-bearing facts are that it
is present, and that it sits **after** `/usr/local/bin`.

**Origin: libghostty, confirmed from the live environment.** The same
Batty-spawned shell carries libghostty's own environment stamps, including:

```
GHOSTTY_BIN_DIR=/Applications/Batty.app/Contents/MacOS
GHOSTTY_RESOURCES_DIR=/Applications/Batty.app/Contents/Resources/ghostty
TERM_PROGRAM=ghostty
```

`GHOSTTY_BIN_DIR` is the host app's own executable directory, and its value is
exactly the `PATH` entry in question. The libghostty binary
(`GhosttyKit.xcframework/macos-arm64_x86_64/libghostty.a`) contains the literal
symbol `GHOSTTY_BIN_DIR` and references `__NSGetExecutablePath`, which is how it
derives that directory at runtime. libghostty is consumed as a **prebuilt
xcframework** (`libghostty-spm`, pinned revision `b146b73` in
`BattyKit/Package.swift` at filing time) — there is no vendored Zig source in
this repo, so the appending logic itself could not be read. Recorded
accordingly: **the origin is libghostty with high confidence from environment
and binary evidence, but the `PATH`-append line was not read in source.**

*Correction, review round 1 (2026-09-10):* `BattyKit/Package.swift`'s pin has
since moved to `a2565ccf047c03c74a59dd7c16a8fac7c477852f` (tag
`1.5.20260903`) — `b146b73` is stale, not current. The append line the
paragraph above couldn't read *has* since been read in source and confirmed:
`src/termio/Exec.zig:686-709` (Ghostty commit `c4e16970`, the commit that pin
resolves to) shows `GHOSTTY_BIN_DIR` computed and appended onto `PATH` there;
see the Decision section's corrected citation for the `env_override` half of
the picture.

**It does not come from this repo or from the user's shell config.** `grep` over
`BattyKit/`, `Batty/`, and `scripts/` finds no code that adds `Contents/MacOS` to
`PATH` (the only `Contents/MacOS` hits under those three directories are in
`docs/`). The entry is also absent from a clean login shell, which rules out `~/.zshrc`, `~/.zprofile`,
`~/.zshenv`, `/etc/paths`, and `/etc/paths.d/*`.

*Correction, 2026-08-27:* re-verified against `main`. The scoped claim above
holds — nothing in `BattyKit/`, `Batty/`, or `scripts/` adds `Contents/MacOS` to
`PATH`, and the `TabRuntime` `env` seam cited in the Decision section is exactly
where such an override would go. The parenthetical was too strong, though: the
tree carries two more `Contents/MacOS` matches outside those directories, at
`tools/memsample.sh:59-60`, where they are `ps` process-name patterns for the
Prod and Beta executables — not a `PATH` mutation.

**Beta is not affected.** `/Applications/Batty Beta.app/Contents/MacOS/` contains
`Batty Beta`, not `Batty` — no case-insensitive collision with `batty`. The
defect is Prod-only, which is a useful hint for the "rename the executable"
remedy below.

**Not executed, so not proven by running it:** that exec'ing
`Contents/MacOS/Batty` under the name `batty` produces a live second instance.
That follows structurally — it is the app's `@main` binary — but this session was
instructed not to launch the app, so it is recorded as inference, not observation.

## Why #0361's fix does not reach this

#0361 fixed the CLI's own resolution and launch logic: `AppConnectDance`
resolves one specific bundle **path** instead of a bundle identifier, refuses to
launch when a process at that path is already running (new exit code `6`), and
`SessionCommand.openURL` targets the resolved path with `open -a`. All of that
lives in the `batty` executable target. **The path described here never runs any
of it** — the kernel execs the app binary directly.

#0361 also evaluated and **deliberately reverted** an
`LSMultipleInstancesProhibited` key in `Configuration/Info.plist`, partly because
it cannot stop a non-LaunchServices exec like this one. A first-hand report of
the key failing against a launchd-spawned duplicate is cited on Apple Developer
Forums thread 738837; that citation is recorded as #0361 received it and was
**not** re-fetched here (no network access was used for this filing). Either way,
do not re-propose that key as the fix for this issue.

#0361's own Resolution notes already name this as out of scope and say it is
"filed as a separate issue" — this is that issue.

## Notes

### Possible remedies — options, not decisions

None of these is chosen; they are recorded so the implementer starts from a real
menu rather than the first idea.

- **Rename the app's main executable** so it cannot collide case-insensitively
  with `batty` (Beta already avoids the collision by being named `Batty Beta`).
  Cleanest at the root, but `EXECUTABLE_NAME`/`PRODUCT_NAME` live in
  `Configuration/`, which `CLAUDE.md` marks **restricted**, and the name is baked
  into code signing, the DMG, and Sparkle's update expectations. Needs explicit
  user sign-off before anyone touches it.
- **Do not put `Contents/MacOS` on the spawned shell's `PATH` at all**, or append
  it only *after* the standard entries. Batty already injects into the spawned
  environment through libghostty's `env` config directive —
  `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:225-231` sets
  `BATTY_TAB_ID` / `BATTY_PANE_ID` / `BATTY_SESSION_ID` via
  `builder.withCustom("env", …)` — so a `PATH` override has an existing seam. Note
  the entry is *already* after `/usr/local/bin` today, so "append later" alone
  does not close the no-CLI-installed case.
- **Ship the CLI under a name that cannot collide** with any executable inside
  the bundle.
- **Have the app binary detect argv[0]-style invocation** (`argv[0]` basename
  case-insensitively equal to `batty`, or a non-LaunchServices launch) and refuse
  with a message pointing at the real CLI, instead of starting an
  `NSApplication`.
- **Point `GHOSTTY_BIN_DIR` / the injected `PATH` at
  `Contents/Resources/bin`** instead of `Contents/MacOS`, so the directory that
  lands on `PATH` is the one that actually holds the CLI. This is the option
  that most directly turns the bug into the intended behavior — worth checking
  whether libghostty exposes it as configuration before assuming it does not.

## Gotchas

**Nothing in this issue's implementation or review ever launched Prod, spawned
a real libghostty surface, or exec'd the compiled app binary under any name.**
Both layers are verified by mutation-tested pure-function unit tests, by real
libghostty config round-trips (`renderedConfig` / `lastConfigurationIssue`
against the bundled `libghostty.a`), and by a standalone probe app bundle
measuring `argv[0]` / `CFBundleExecutable` semantics outside Batty. Three
things remain for the user to confirm on a real Prod install:

1. **A normal launch still works.** Dock, Spotlight, double-click, and
   `open -a` on the Prod build must open a window as before. This is the one
   that would make the app unlaunchable if the guard's exemption were wrong.
   Evidence says it is right — `CFBundleExecutable` is `Batty`, LaunchServices
   execs `Contents/MacOS/Batty` built from that same plist value, so the
   invoked basename matches exactly — but it has not been observed.
2. **The `PATH` seam reaches a real spawned shell.** In a Prod Pane,
   `echo $PATH | tr ':' '\n'` should show **no**
   `/Applications/Batty.app/Contents/MacOS`, and should include
   `/Applications/Batty.app/Contents/Resources/bin` **appended after** the
   existing entries, not first. (In a login shell `/etc/zprofile`'s
   `path_helper` reorders `PATH`; the bundled directory survives that
   reordering, `Contents/MacOS` stays gone.)
3. **The guard actually refuses.** Reach the Prod app binary under the name
   `batty` — e.g. a symlink named `batty` pointing at `Contents/MacOS/Batty`,
   or a `PATH` entry exposing that directory — and confirm it prints the
   refusal message to stderr and exits non-zero rather than opening a second
   window.

**The `argv[0]` guard is completely inert in Beta.** Beta's executable is
`Batty Beta`, whose basename never matches `batty` case-insensitively, so
`ArgvZeroGuard.isSpuriousCLIInvocation` returns `false` for every Beta
invocation and neither branch ever fires. Testing against Beta exercises none
of layer 2; only a Prod install does. (Layer 1, the `PATH` seam, *is* active in
Beta and can be checked there via step 2 above, substituting `Batty Beta.app`.)

**Accepted residual:** a bare, correctly-cased `Batty` typed at a shell is
exempt by design — the exemption is static-name equality, not path equality.
Reaching the app binary that way requires a hand-made `Batty` symlink or a
`PATH` entry containing the bundle's `MacOS` directory, which layer 1 strips
from every Batty-spawned Pane and which is absent from a clean login shell.
`CLIInstaller` never creates a capitalized command name. This was weighed
against the alternative (round 1's shape, which refused bare `Batty` but let
the far more reachable lowercase `Contents/MacOS/batty` through) and chosen
deliberately.

**The one input that would brick the app** is
`Bundle.main.infoDictionary?["CFBundleExecutable"]` returning `nil`, which
fails closed to refusal. It is unreachable for a launchable `.app` —
LaunchServices cannot locate the binary to exec without that key — but note
that "fail closed" here means "unlaunchable", not "safe".
