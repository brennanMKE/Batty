# 0252 — Embedded `batty` CLI crashes at launch: transitively links Sparkle via @rpath from the full BattyKit import

| | |
|---|---|

| **Module** | Build / App |
| **Platform** | macOS |
| **First seen** | 2026-06-30 |
| **Closed** | 2026-06-30 |

## Description

The `batty` CLI shipped by #0249 is embedded in the app bundle but **crashes on launch** when run from there (`/usr/local/bin/batty` → symlink → `Contents/Resources/bin/batty`). Because the `batty` target depended on the whole `BattyKit` library, it transitively linked `Sparkle.framework` via `@rpath`, and from `Resources/bin/` there is no rpath reaching `Contents/Frameworks/`, so dyld fails with `Library not loaded: @rpath/Sparkle.framework/...`. The CLI installs but does nothing.

## Long Description

#0249's verification only exercised the CLI via `cd BattyKit && swift run batty` (from the SwiftPM build dir, where Sparkle *does* resolve) and checked the embedded copy with `file` (architecture only) — it never *ran* the embedded binary, so the runtime crash was missed. The tool's real job is tiny (`SessionURLBuilder.buildURL()` + `open`), and `SessionURLBuilder` imports nothing but `Foundation`; none of Sparkle / libghostty / SlidingTabs / Textual is needed. Depending on all of `BattyKit` was what dragged them in and inflated the binary to 26 MB.

## Steps to reproduce

1. `scripts/build.sh` to build the app.
2. Run the embedded CLI directly: `"$APP/Contents/Resources/bin/batty" --version`.
3. Observe a dyld crash (`Library not loaded: @rpath/Sparkle.framework/Versions/B/Sparkle`) instead of a version string.

## Expected behavior

The embedded `batty` runs standalone from inside the bundle (and from the `/usr/local/bin/batty` symlink), and `batty --version` reports the host app's version.

## Actual behavior

The embedded `batty` aborts at launch with an unresolved `@rpath/Sparkle.framework` load, before any command runs. `--version` also reported a hardcoded `0.1.0` unrelated to the app.

## Resolution notes

> 🟢 Resolved 2026-06-30 — Decoupled the CLI from `BattyKit`: `SessionURLBuilder` moved to a new dependency-free `BattyCLICore` target that the CLI links exclusively, so `batty` no longer links Sparkle (26 MB → 2.4 MB, zero `@rpath` deps). Also made `batty --version` read the host app's `Info.plist` so it matches the installed app.

## Root cause

The `batty` `executableTarget` declared `dependencies: ["BattyKit"]`. `BattyKit` links `Sparkle` (and libghostty/SlidingTabs/Textual), so the CLI inherited a dynamic `@rpath/Sparkle.framework` load command. The embed phase copies the binary to `Contents/Resources/bin/`, which is two directories below `Contents/Frameworks/`; the CLI's baked-in rpaths (`@loader_path`, `/usr/lib/swift`, the Xcode toolchain) can't reach the bundled framework, so dyld can't resolve Sparkle at launch. It only appeared to work from the SwiftPM build directory, whose rpath happens to include the built Sparkle.

## Fix

Split a dependency-free core out of `BattyKit` and point the CLI at it only:

- New `.target(name: "BattyCLICore")` in `BattyKit/Package.swift`, with no product dependencies (Foundation only).
- Moved `SessionURLBuilder.swift` into `BattyCLICore` (content unchanged).
- `BattyKit` now depends on `BattyCLICore` and re-exports it (`@_exported import BattyCLICore`), so existing `import BattyKit` / `@testable import BattyKit` consumers (the app, `BattyURLHandler`, tests) keep seeing the same public API with no call-site changes.
- `batty` now depends on `BattyCLICore` instead of `BattyKit`, so it links no GUI frameworks. Binary drops from 26 MB to 2.4 MB with zero `@rpath` dependencies.
- `batty --version` now calls `resolveAppVersion()`, which reads `CFBundleShortVersionString` from the app's `Info.plist` (two directories up from the symlink-resolved executable), so the CLI version tracks the installed app instead of a hardcoded string. Falls back to `"unknown"` when run outside a bundle.

## Gotchas

- **Binary size is the canary.** A healthy `batty` is ~2.4 MB with no `@rpath` lines in `otool -L`. If it ever balloons back toward 26 MB or shows a framework `@rpath`, the CLI got re-coupled to `BattyKit` (directly or transitively) and will crash again from the bundle. The embed target (`Contents/Resources/bin/`) is two levels below `Contents/Frameworks/`, so any dynamic framework dependency is unreachable at runtime.
- **This narrows #0249's "CLI imports BattyKit" design.** Keeping CLI code in the package is still satisfied — `BattyCLICore` *is* in the package — but the CLI must depend only on the dependency-free core, never the full GUI library.
- **`--version` outside a bundle returns `unknown`.** Running `batty` straight from the SwiftPM build dir has no host app `Info.plist`, so the fallback fires. That's expected; only the embedded/installed CLI reports a real version.
- **Universal/Release arch still unverified** (carried over from #0249) — only the single-arch Debug embed was exercised. Confirm `lipo -info` on the embedded binary when cutting a release.
