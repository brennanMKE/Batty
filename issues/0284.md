# 0284 — Add `batty notify` to post an agent notification into the Bell Feed

| | |
|---|---|
| **Status** | open |
| **Module** | App / BellFeed |
| **Platform** | macOS |
| **First seen** | 2026-07-27 |

## Description

Fourth child of the #0257 umbrella: the `batty notify` verb from its Tier 1 surface —

```
batty notify --title <t> [--body <b>] [--sound]   # posts into the bell feed
```

— letting a CLI caller post an entry into Batty's **Bell Feed**. #0257's Notes pin the intent: *"`notify` is the on-brand 'present agent activity' primitive (routes into the existing bell feed + AI summaries) — keep it simple; richer `status`/`progress` pills are Tier 2 (design doc §D), deferred."*

**Not implemented today** (verified 2026-07-27): the shipped CLI on `main` (`BattyKit/Sources/batty/BattyCLI.swift`) has subcommands `new`, `ping`, `status`, `list`, `session`; the in-flight #0281 branch adds `id` (`IDCommand.swift`). Nothing under `BattyKit/Sources/batty/` mentions notify.

**Why now:** #0257 sketches the agent loop as `batty id --json` → `batty list --json` → `batty pane split -v -c '…'` → `batty notify`. With #0281–#0283 building the first three steps, `notify` is the missing last one — how a long-running agent tells the user "done" or "I need input" without the user watching that pane.

Unlike #0282/#0283, several design decisions here are genuinely open. This ticket poses them explicitly; the implementer (with the user where flagged) decides and records the choices in the resolution.

## Design questions to decide (posed, not pre-decided)

### 1. Transport — `batty://` or XPC?

#0257's Tier 1 table lists `notify` under the one-way `batty://` verbs, but its 2026-07-26 transport amendment moved the agent-facing pane mutations (#0282, #0283) to XPC so a stale target yields a real exit code instead of silent success.

- **For `batty://`:** `notify` in its simplest form carries no target id that can go stale and returns no value an agent needs to chain on; fire-and-forget is semantically plausible for a notification. It also works with no broker registered — relevant because XPC has an approval-gated degraded mode (no XPC until `SMAppService` approval; none at all in Beta until #0277 per #0274's resolution notes).
- **For XPC:** `notify` is the *terminal* step of the agent loop, and "agent believes the user was told, but nothing happened" is the least recoverable silent failure in the whole chain — exactly the failure class the transport amendment exists to eliminate. If pane attribution is adopted (question 3), a stale `--pane` id becomes possible and the stale-target argument applies directly. And `batty://`'s one unmatched capability — launching the app — is worthless here: posting into the feed of an app that isn't running is meaningless, so `notify` gains nothing from staying one-way.

**Filer's recommendation: XPC**, reusing #0282's mutation-verb pattern (verb string in `BattyXPCCore/XPCVerb.swift` — currently `status`/`list`/`sessionInfo`, verified; dispatch in `AppXPCService.perform(_:reply:)`; CLI via the generalized `AppServiceClient.perform<Payload>` dance from #0274; exit codes per `XPCExitCode.swift`, with "app not reachable" surfacing as a nonzero exit the agent can see). The decision is the implementer's/user's to confirm and record.

### 2. Provenance in the feed

Every Bell Feed entry today represents a real terminal event from a Terminal Session, and the UI assumes that. Verified model facts:

- `BellFeedEntry` (`BattyKit/Sources/BattyKit/Runtime/BellFeedStore.swift`) requires **five non-optional UUIDs** — `windowID`, `sessionID`, `paneID`, `tabID`, `surfaceID` — plus optional `message`, optional AI `summary`, and `seen`. There is **no source/kind field**; nothing in the model distinguishes BEL from OSC 9, let alone a CLI origin.
- `BellFeedView.pathLabel(for:)` resolves the path label `Session › Pane N › Tab` against the **live** model and renders `"(closed)"` when the ids don't resolve — so a CLI entry stuffed with placeholder UUIDs would render as `(closed)`.
- `AppStateStore.jumpToBellEntry(_:)` marks the entry seen and no-ops when `windowID` is not a live window — a placeholder-id entry would be an inert row.
- Cleanup is keyed on `tabID` (`BellFeedStore.removeEntries(matchingTabIDs:)` via `cleanUpBellState`, per `docs/notifications.md` §6): an entry attributed to a real tab is purged when that tab closes; an entry with no real tab is never purged (cap-evicted only — probably fine, but note it).

So the implementer must decide: does the model grow an entry kind (or optional ids) so CLI notifications are first-class and visually distinguishable, or does `notify` attribute itself to a real tab and ride the existing shape unchanged? Should a CLI-originated entry be visually distinguishable from a bell at all? Whatever is chosen, the `(closed)` rendering and dead click-to-jump for unresolvable ids must not be the accidental outcome.

### 3. Does it need a target at all?

Should `--pane` / `--session` be accepted so an agent can attribute the notification to a pane other than its own — and does #0281's resolution chain (explicit flag → `BATTY_*` env → focused element) apply when no flag is given? Note the interaction with question 2: attribution to the calling pane gives the feed row a truthful path label and a working click-to-jump "for free," which may itself be the argument for resolving a target even though the verb doesn't strictly need one. Also decide the out-of-pane case: `batty notify` invoked from a plain Terminal.app shell has no `BATTY_*` env and no focused-element claim to make — does it post untargeted, or fail?

### 4. `--sound` and system notifications

Verified against `docs/notifications.md` and `AppStateStore` source — the existing pipeline a `notify` entry would ride:

- `postNotification(for:at:)` early-returns when `session.notificationsMuted` (per-session mute suppresses only the macOS banner; the feed row and unseen counters still happen). If `notify` attributes to a session, decide whether mute applies to it — the consistent answer is probably yes, but say so.
- `BellNotifier.post` is further gated by Settings → Notifications → "Show system notifications", and suppresses the banner when the app is active and the entry is already seen.
- Sound today is app-wide: the "Play sound" setting makes `BellNotifier` attach `.default` sound to the `UNNotificationContent`. There is **no per-event sound control** — so pin what `--sound` means: request sound on this one notification subject to the app-wide toggle, or override the toggle? (Silently overriding a user setting from a CLI flag is the answer to argue against.)
- Decide whether `batty notify` can raise a macOS system notification at all, or only a feed entry. If it posts through `postNotification`/`BellNotifier`, it needs the `sessionTitle`/`paneIndex`/`tabLabel` context that only a resolved target provides (see question 3).
- Per #0257's Notes, the entry should flow through AI summarization like any other: `AppStateStore.scheduleSummarization(for:tabTitle:sessionTitle:)` runs at both existing record sites, gated on the summarizer being present and the Settings toggle (verified).

### 5. Flood guard

`BellFeedStore` is capped at 200 entries, newest-first eviction (verified). A looping agent calling `notify` in a tight loop would evict every real bell and could spam Notification Center. Worth deciding whether any guard is wanted (e.g. coalescing identical repeats), but do not over-engineer — a sentence in the resolution recording the decision is enough.

## As-built starting points (verified against source 2026-07-27)

- **Feed write path:** `BellFeedStore` is `@Observable @MainActor`; `record(_:)` inserts at index 0 and enforces the cap. `AppStateStore.recordBellTick(forTabID:surfaceID:)` and `recordDesktopNotification(forTabID:surfaceID:)` are the two existing recording sites — both `locate(tabID:)` a live tab, compute seen-ness from focus + key window, `propagateUnseenForced` when unseen, then `postNotification` and `scheduleSummarization`. A CLI notify needs its own recording entry point on `AppStateStore`; #0257 already anticipated "add the small ones missing (tab rename, notify-into-feed)."
- **Overlap to weigh:** an agent running *inside* a pane can already produce a titled feed entry + banner today by emitting OSC 9 / OSC 777 escapes (`docs/notifications.md` §2 — captured via `TerminalSurfaceDesktopNotificationDelegate` into the same pipeline). `batty notify`'s value over that: it works when stdout is redirected or the caller is not the pane's foreground process, it has an explicit flag surface, and (if XPC) it reports success. The implementer should consider whether the app-side handler can converge with the OSC 9 path rather than building a parallel one.
- **CLI surface:** `notify` is a bare app-level verb (no noun), like `open` in #0257's table — it hangs off `BattyCLI.subcommands` directly rather than a noun command. Follow the existing subcommand pattern.
- **If XPC:** wiring points as in #0282 — `XPCVerb.swift`, `AppXPCService.perform(_:reply:)` (hops to `@MainActor` for store access), `AppServiceClient.perform<Payload>`. Exit codes per `BattyXPCCore/XPCExitCode.swift` (`0` success … `4` request failed), the vocabulary #0282/#0283 use.

## Binding constraints (copied — do not merely cross-reference)

- If it goes over XPC: **payloads are `Codable, Sendable` structs carried as JSON-encoded `Data`** inside the `@objc` protocols, `nonisolated` at type level; protocol requirements are `nonisolated func`; reply blocks `@escaping @Sendable`. Guard new payload types with off-actor round-trip helpers as `XPCContractTests` does, and assert raw decoded JSON keys (the #0274 `_0` lesson), not just round-trips.
- **Every Foundation-supplied handler closure gets `@Sendable`** — there is no compiler warning, and the failure is a silent `SIGTRAP` inside the very handler that would have logged the error.
- **`os.Logger` interpolation of a dynamic `String` defaults to `.private`** — add `privacy: .public` explicitly.
- **Verify isolation guards under a forced rebuild** (`rm -rf .build`); stale targets produced false "still builds" results twice on the XPC track.
- **Code-signing protocol:** never run `scripts/build.sh` for iteration (its `unit` path cannot disable signing); use `cd BattyKit && swift test` and `xcodebuild … CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO`. The user's Developer ID certificate was revoked once by repeated signed local builds.
- **Writing to the feed touches `@Observable` state** — `docs/swiftui-observation-rules.md` is binding. The write must land on `@MainActor` via an event-origin path (an XPC/URL handler hop is the routine case); it must never be made from view-driven code, and never "fixed" by hopping into a `Task` from inside a view update.
- **User-facing strings** (any new feed-row labels, notification content) follow `docs/localization.md`; the existing feed code uses `String(localized:)` throughout.

## Verification expectations

Follow the #0271/#0274 pattern:

- **Unit tests for the pure parts:** argument parsing (`--title` required; `--body` and `--sound` optional; whatever target flags are adopted, with UUID validation → exit 1 client-side); payload round-trip **plus raw-JSON key assertions** if XPC; feed-entry construction (correct fields, seen-ness, cap behavior, and — per the question-2 decision — kind/attribution shape).
- **Store assertions:** a notify aimed at (or attributed to) a background session records the entry and bumps unseen counters without changing `selectedSessionID`, the active session's focused pane, or any other session; per-session mute suppresses only the banner path, per the question-4 decision.
- `cd BattyKit && swift test` and `xcodebuild … CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO` green; `otool -L` on `batty` still shows zero `@rpath` dependencies (if the CLI target is touched).
- **Needs the user's runtime sign-off** (do not disturb the running app; coordinate): `batty notify --title …` from inside a pane actually produces a visible Bell Feed row (and banner, per the decisions above) in the live app — that cannot be verified headlessly and is stated honestly as the gap.

## Out of scope

- Richer `status`/`progress` activity pills — explicitly Tier 2 (#0257 Notes, design doc §D), deferred.
- The remaining #0257 verbs (`session new/rename/focus/close`, `pane hide/show/focus/zoom`, tab verbs, `open`).
- Persisting the Bell Feed or changing its cap/eviction semantics beyond what question 5 decides.
