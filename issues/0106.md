# 0106 — Option / Ctrl / Cmd shortcuts do not move the cursor like Terminal.app

| | |
|---|---|

## Description

Standard macOS Terminal-style cursor navigation does not work at the shell prompt. Pressing **Option-Left** inserts letters into the line instead of jumping the cursor one word to the left. The expectation is that Option, Ctrl, and Cmd modifier combinations behave the way Terminal.app and iTerm2 do — so word-jumping, line-start / line-end, and the other standard readline-style edits work out of the box.

## Steps to reproduce

1. Open a Batty terminal session running the default shell (zsh).
2. Type a long command on the prompt without pressing Enter, e.g. `echo one two three four`.
3. Press **Option-Left** to try to jump the cursor one word back.

## Expected behavior

Option-Left moves the cursor one word to the left (and Option-Right one word to the right). More broadly, the standard macOS-Terminal modifier conventions should all hold:

| Shortcut | Effect |
|---|---|
| Option-Left / Option-Right | Move by word |
| Option-Delete | Delete previous word |
| Cmd-Left / Cmd-Right | Move to start / end of line |
| Cmd-Delete | Delete to start of line |
| Ctrl-A / Ctrl-E | Move to start / end of line (readline native) |
| Ctrl-W / Ctrl-U / Ctrl-K | Delete previous word / line / to end of line |

Ctrl-* shortcuts already work because the shell handles them; Option-* and Cmd-* are the ones that need terminal-side translation into the right escape sequences.

## Actual behavior

Option-Left (and other Option-modified arrow / delete combinations) types literal characters into the prompt instead of producing the word-motion escape sequence the shell expects. The terminal is currently treating Option as "Option-as-Meta produces an altered character" rather than "Option-arrow / Option-delete is a navigation key combo."

## Root cause

Cmd (`super` in Ghostty's modifier vocabulary) has no default Ghostty binding for arrow keys or backspace, so Cmd-Left / Cmd-Right / Cmd-Backspace fall through with no useful terminal output. The previous attempt at this issue addressed Cmd by adding three `super+…` keybinds that emit `\x01` / `\x05` / `\x15`; those work, confirmed by the user.

The Option side was different. The first attempt set `macos-option-as-alt = true` on the assumption libghostty would then translate Option-arrow / Option-Backspace into the Meta-prefixed escape sequences readline wants. In this xcframework that flag did not produce the visible behavior — Option-arrow kept composing letters into the prompt at a fresh shell. Whether the cause is that the flag is only consulted at surface creation (not when re-applied via `setTerminalConfiguration`), an xcframework regression, or AppKit composing the chord before libghostty's keybind matcher sees the event, the observable result was the same: Option-as-Alt didn't kick in.

## Fix

Replaced `macos-option-as-alt` with explicit `alt+…` keybinds that emit the raw escape sequences shells expect:

- `alt+left=text:\x1bb` — ESC followed by `b`, which readline reads as Meta-b (`backward-word`).
- `alt+right=text:\x1bf` — ESC followed by `f`, Meta-f (`forward-word`).
- `alt+backspace=text:\x1b\x7f` — ESC + DEL, Meta-Backspace (`backward-kill-word`).

These are the exact byte sequences Terminal.app and iTerm2 send for the same chords, so they work uniformly in zsh, bash, vim insert mode, fzf, and any other reader that respects readline's Meta-prefixed primitives. They route through the same libghostty keybind-matcher path that already works for the `super+…` chords, so they bypass any option-as-alt translation entirely.

The same configuration is applied symmetrically in the tab-creation path and the live-settings refresh path, so changing a setting like font size doesn't silently strip the bindings.

## Files changed

- `BattyKit/Sources/BattyKit/TabRuntime.swift` — removed the `macos-option-as-alt` line and added three explicit `alt+…` keybinds to the `TerminalConfiguration` builder used when each tab is created.
- `BattyKit/Sources/BattyKit/SettingsPreferences.swift` — same change in the builder inside `AppStateStore.applyAppearanceToAllSurfaces()`, so re-applying appearance preferences keeps the bindings in place.
