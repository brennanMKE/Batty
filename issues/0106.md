# 0106 — Option / Ctrl / Cmd shortcuts do not move the cursor like Terminal.app

| | |

## Description

Standard macOS Terminal-style cursor navigation does not work at the shell prompt. Pressing **Option-Left** inserts letters into the line instead of jumping the cursor one word to the left. The expectation is that Option, Ctrl, and Cmd modifier combinations behave the way Terminal.app and iTerm2 do — so word-jumping, line-start / line-end, and the other standard readline-style edits work out of the box.

## Steps to reproduce

1. Open a Batty terminal session running the default shell (zsh).
2. Type a long command on the prompt without pressing Enter, e.g. `echo one two three four`.
3. Press **Option-Left** to try to jump the cursor one word back.

## Expected behavior

Option-Left moves the cursor one word to the left (and Option-Right one word to the right). More broadly, the standard macOS-Terminal modifier conventions should all hold:

| Shortcut | Effect |
|---|---|
| Option-Left / Option-Right | Move by word |
| Option-Delete | Delete previous word |
| Cmd-Left / Cmd-Right | Move to start / end of line |
| Cmd-Delete | Delete to start of line |
| Ctrl-A / Ctrl-E | Move to start / end of line (readline native) |
| Ctrl-W / Ctrl-U / Ctrl-K | Delete previous word / line / to end of line |

Ctrl-* shortcuts already work because the shell handles them; Option-* and Cmd-* are the ones that need terminal-side translation into the right escape sequences.

## Actual behavior

Option-Left (and other Option-modified arrow / delete combinations) types literal characters into the prompt instead of producing the word-motion escape sequence the shell expects. The terminal is currently treating Option as "Option-as-Meta produces an altered character" rather than "Option-arrow / Option-delete is a navigation key combo."

## Root cause

libghostty defaults `macos-option-as-alt` to `false`, which makes Option act as the macOS character-composing modifier — so Option-Left enters the option-composed glyph for the left-arrow key rather than emitting the Meta-prefixed escape sequence shells need for word motion. Cmd (`super` in Ghostty's modifier vocabulary) has no default Ghostty binding for arrow keys or backspace, so Cmd-Left / Cmd-Right / Cmd-Backspace fall through with no useful terminal output. Together this meant the Terminal.app-style cursor-motion shortcuts simply didn't reach the shell.

## Fix

Enabled `macos-option-as-alt = true` so Option behaves as Alt/Meta, which transparently fixes Option-Left/Right (Meta-b / Meta-f, already bound by readline to word motion) and Option-Backspace (Meta-Backspace, bound to backward-kill-word) without any extra keybinds. Added three `super+…` keybinds that emit `\x01`, `\x05`, and `\x15` so Cmd-Left / Cmd-Right / Cmd-Backspace map to Ctrl-A (beginning-of-line), Ctrl-E (end-of-line), and Ctrl-U (unix-line-discard). The control-character primitives were chosen over terminfo-style sequences (`esc:OH` / `esc:OF`) because they work uniformly in emacs and vi-insert readline modes, in vim's command mode, and in any other line editor that respects the readline control set — they don't depend on terminfo key entries being present and matching. The same configuration is applied symmetrically in the tab-creation path and the live-settings refresh path, so changing a setting like font size doesn't silently strip the new bindings.

## Files changed

- `BattyKit/Sources/BattyKit/TabRuntime.swift` — added `macos-option-as-alt` plus three `super+…` keybinds to the `TerminalConfiguration` builder used when each tab is created.
- `BattyKit/Sources/BattyKit/SettingsPreferences.swift` — added the same four lines to the builder inside `AppStateStore.applyAppearanceToAllSurfaces()`, so re-applying appearance preferences keeps the bindings in place.
