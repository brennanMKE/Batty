## Description

Add a new "Session Naming" section to Settings with two toggles controlling the automatic naming of sessions: one for file-based derivation (the `ProjectNameResolver` rules that read project marker files like `Package.swift`, `package.json`, `Cargo.toml`), and one for Foundation Models naming (the on-device AI fallback from #0231/#0232 that uses path/contents signals to pick a name). Both default to on, preserving current behavior.

## Long Description

Settings infrastructure today: `SettingsView` (`BattyKit/Sources/BattyKit/Views/SettingsView.swift`) is a tabbed view (General / Appearance / Notifications / Keyboard) whose tabs are `Form`s of `Section`s with `Toggle`s, each backed by a `UserDefaults` key declared in `SettingsPreference` (`BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift`) following the pattern: a `co.sstools.Batty.<name>` key constant, a `default<Name>` constant, and a `resolved<Name>()` accessor that treats a missing key as the default.

New section and keys:

- **Section "Session Naming"** — placement: a new `Section` in the General tab (or a new tab if General is getting crowded; implementer's judgment, but a section was requested).
- **Toggle 1 — file-based derivation** (e.g. "Name sessions from project files"): key `co.sstools.Batty.autoNameFromFiles`, default `true`. When off, `resolveAutoTitle` skips the `ProjectNameResolver` step. Cached user-assigned names (`SessionNameCache`) still apply — those are explicit user choices, not automatic naming — and `titleOverride` pinning is unaffected.
- **Toggle 2 — Foundation Models naming** (e.g. "Use Apple Intelligence to suggest names"): key `co.sstools.Batty.autoNameWithAI`, default `true`. When off, `AppStateStore` never schedules an AI suggestion (and cancels any in-flight one on toggle-off, or simply lets the staleness checks drop it). On macOS < 26 the toggle should be shown disabled with a caption like "Requires macOS 26" (or hidden — implementer's judgment; disabled-with-caption is more discoverable). The runtime gate (`FoundationModelsNameSuggester.makeIfAvailable()` + per-call availability check) stays — the toggle is an additional user-intent gate, not a replacement.

Semantics:

- The two toggles are independent. Rules off + AI on means the AI fallback still runs whenever the deterministic chain lands on the default "Session N". Rules on + AI off is #0231-era behavior minus the AI step. Both off means sessions only get cached user names or "Session N".
- The toggles gate *automatic* naming only. Manual rename, `SessionNameCache` recall of a user's earlier rename, and the "Session N" default are not affected.
- Toggle changes take effect on the next cwd change; no need to retroactively rename existing sessions when a toggle flips (matches how other settings like cursor style apply forward).

Consumption points:

- `AppStateStore.resolveAutoTitle(forCWD:sessionIndex:cache:resolver:)` — skip the resolver step when file-based naming is off. Keep the function pure: pass the flag in as a parameter (resolved by the caller) rather than reading `UserDefaults` inside, so existing unit-test patterns keep working.
- `AppStateStore.handleWorkingDirectoryChange(forTabID:)` / `scheduleNameSuggestion` — skip scheduling when AI naming is off.
- Follow `docs/swiftui-observation-rules.md` for any new observed state; the toggles themselves are plain `@AppStorage`-style bindings like the existing settings.

Testing: unit tests in `BattyKitTests` for the resolution behavior under each of the four toggle combinations (file-derivation skipped when off, AI never scheduled when off, cache hits and user renames unaffected). UI-level verification of the new section is manual (mark `resolved`, not `closed`, and note it in Gotchas per CLAUDE.md).

## Steps to reproduce

1. Open Batty → Settings.
2. Look for controls governing automatic session naming.

## Expected behavior

A "Session Naming" section offers two toggles: naming from project files, and Apple Intelligence name suggestions. Turning either off stops that mechanism; turning both off leaves only user renames and the "Session N" default. The AI toggle communicates its macOS 26 requirement on older systems.

## Actual behavior

No settings exist for session naming; both the file-based derivation and the Foundation Models fallback are always on with no way to opt out.

## Resolution notes

> Added a "Session Naming" section to the General settings tab with two independent toggles (project-file derivation and Apple Intelligence suggestions, both default on) gating only the automatic naming paths.

## Root cause

Feature gap: both automatic-naming mechanisms — `ProjectNameResolver` file derivation and the Foundation Models fallback from #0231/#0232 — were unconditionally on, with no user-facing opt-out.

## Fix

- `SettingsPreference` gains `autoNameFromFilesKey` / `autoNameWithAIKey` (`co.sstools.Batty.autoNameFromFiles` / `co.sstools.Batty.autoNameWithAI`), `defaultAutoNameFromFiles` / `defaultAutoNameWithAI` (both `true`), and `resolvedAutoNameFromFiles()` / `resolvedAutoNameWithAI()` accessors treating a missing key as the default — the exact pattern of `resolvedConfirmQuit()`.
- `AppStateStore.resolveAutoTitle` gains a `nameFromFiles: Bool = true` parameter that skips the `ProjectNameResolver` step when `false`. The function stays pure — no `UserDefaults` reads; `handleWorkingDirectoryChange` resolves the flag and passes it in. Cache hits stay live with the toggle off: they record explicit user renames, not automatic naming. The defaulted parameter keeps existing direct-call tests source-compatible.
- `handleWorkingDirectoryChange` gates the whole AI step on `resolvedAutoNameWithAI()`: when off, it neither schedules a suggestion nor applies a memoized one (a memoized AI name is still automatic naming), and it cancels any in-flight request. **In-flight handling on toggle-off:** the chosen behavior is the issue's "simplest correct" option — the next cwd report cancels the in-flight task, and the existing staleness checks in `applySuggestedName` stand; no extra toggle re-check was added to the apply path, so a result that lands between toggle-off and the next cwd report may still apply once. Toggle changes otherwise take effect on the next cwd change; no retroactive renaming.
- `SettingsView` General tab gains a "Session Naming" `Section` with the two toggles bound via `@AppStorage`, placed between Quit and Keyboard. On macOS < 26 (`#available(macOS 26, *)` check) the AI toggle is disabled with a "Requires macOS 26" caption; on macOS 26+ the caption notes that naming applies on directory change and manual renames win. The runtime gate (`FoundationModelsNameSuggester.makeIfAvailable()` + per-call availability) is unchanged — the toggle is an additional user-intent gate.
- Manual rename, `SessionNameCache` recall, `titleOverride` pinning, and the "Session N" default are untouched. `clearSessionName`'s direct resolver use is an explicit user action, not automatic naming, and was deliberately left ungated.

## Gotchas

- **The Settings UI needs the user's visual sign-off** (section layout/placement in the General tab, toggle labels, and the disabled-with-caption rendering on macOS < 26 — this machine runs macOS 26, so the `aiNamingSupported == false` branch was verified only by code inspection). Marked `resolved`, not `closed`, per CLAUDE.md.
- Tests mutate `UserDefaults.standard`, which is process-shared, and Swift Testing interleaves `@MainActor` tests at suspension points. The `withPreferences` helper keeps keys non-default only inside a synchronous body (set → act → remove with no `await`), so parallel tests can never observe the flipped keys; awaits on suggestion tasks happen after restore, which is safe because nothing re-reads the toggles past the synchronous decision point in `handleWorkingDirectoryChange`.
- The memo gate matters: without it, toggling AI off would still apply previously memoized AI names on revisited paths — the memo is part of the AI mechanism, not user intent.
- The new keys were deliberately not added to `SettingsPreference.registerDefaults()` — the resolved accessors already treat a missing key as `true` (same precedent as `confirmQuitKey`), and registering would change nothing observable.
