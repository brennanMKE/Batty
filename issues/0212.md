## Description

Repoint the `libghostty-spm` Swift package dependency in `BattyKit/Package.swift` from the local fork (`https://github.com/brennanMKE/libghostty-spm` at revision `2694c40bd1b8f110ad4e6714e0ab7b04ee1f858f`) to the upstream `Lakr233/libghostty-spm` at tag `1.1.9` (commit `6ebd4bd2867f4bb8084e438dfa9a6531ad1f2ca7`). The fork's reason for existing — local changes ahead of upstream — has been merged upstream, so the fork is no longer needed and we can track upstream main directly.

This also unblocks the build, which has been broken since the fork pin (#0210) referenced a Lakr233 binary asset that was pruned (HTTP 404 at `storage.1.0.1779090382/GhosttyKit.xcframework.zip`). The upstream `1.1.9` binary at `storage.1.1.9/GhosttyKit.xcframework.zip` is live.

Resolves [[0210]]. Unblocks [[0173]], [[0174]], [[0175]], [[0178]], [[0179]], [[0180]], [[0185]], [[0186]] (all eight failing-UI-test issues whose subagents could not build).

### 2026-05-25 — partial: pin change works, second blocker discovered

The Package.swift change to `Lakr233/libghostty-spm@6ebd4bd` (tag `1.1.9`) was attempted but reverted from the working copy pending a decision on a second, separable blocker.

**What works:** SPM resolves the new pin cleanly. The 404-asset problem from [[0210]] is gone.

**What blocks the build now:** Xcode's embed-frameworks validation rejects the macOS slice of the new xcframework:

```
error: Framework .../libghostty.framework contains Info.plist,
expected Versions/Current/Resources/Info.plist since the platform
does not use shallow bundles
```

The downloaded `macos-arm64_x86_64/libghostty.framework` is packaged as a shallow bundle (iOS-style — `Info.plist`, `Headers/`, `Modules/`, and the binary all at the framework root, no `Versions/A/` directory). macOS frameworks require the versioned layout. The framework's own `Info.plist` declares `CFBundleSupportedPlatforms = ["MacOSX"]`, so the slice intends to be a macOS framework — this is an upstream packaging bug, not a platform mismatch.

This is not a 1.1.9 regression: `storage.1.1.5` has the same shallow layout. The older `storage.1.0.*` assets that previously worked (e.g. `storage.1.0.1779090382` from [[0210]]) are themselves 404 and can no longer be inspected, so we can't confirm whether older releases had the correct versioned layout or whether the project relied on some local fixup that's since been lost.

### Possible resolutions

Pick one:

1. **Add a project build-script phase** that converts the shallow macOS slice to versioned layout before Xcode's embed step runs. Real engineering fix; ~30 lines of zsh; mutates the SPM artifact in `DerivedData` (idempotent re-run-safe). Entirely in-tree; no upstream dependency.
2. **Fix upstream packaging** in `Lakr233/libghostty-spm`: re-cut `storage.1.1.9` with the versioned macOS framework layout. Best long-term answer; out-of-our-repo work; the in-tree change would just be the Package.swift pin once a new asset is up.
3. **Skip embed validation** via `SkipEmbeddedFrameworksValidation=YES`. Quick to test, but doesn't survive code-signing/notarization, so not a real fix for shipping — only useful for diagnosis.

### Why partial work wasn't committed

The Package.swift pin change is correct in isolation, but committing it without resolution of the second blocker would leave `main` in a state where every build fails at the embed-framework step. The original `brennanMKE/libghostty-spm@2694c40` pin also fails (at the 404-asset step), so neither pin currently builds — but reverting keeps the failure mode the same as the rest of recent history (`fee517f` onward) rather than introducing a new one.

A direct, unilateral mutation of the SPM artifact in `DerivedData` to verify path 1 was attempted and correctly denied by the harness — the artifact is package-manager territory and any modification belongs in a checked-in build script, not a one-off hand-edit. Path 1 needs explicit go-ahead before implementation.

## Root cause

Two stacked upstream issues:

1. The previous pin (`brennanMKE/libghostty-spm@2694c40`) referenced a Lakr233 binary asset (`storage.1.0.1779090382/GhosttyKit.xcframework.zip`) that has since been removed from Lakr233's releases page. SPM 404s on graph resolution. (This is what [[0210]] tracked.)
2. The newer Lakr233 releases (verified for `storage.1.1.5` and `storage.1.1.9`) ship the macOS slice of `libghostty.framework` as a shallow bundle — `Info.plist`, binary, `Headers/`, `Modules/` all at the framework root, no `Versions/A/` tree. macOS embed-frameworks validation rejects this layout: `Framework /.../libghostty.framework contains Info.plist, expected Versions/Current/Resources/Info.plist since the platform does not use shallow bundles`. The framework's own `Info.plist` declares `CFBundleSupportedPlatforms = ["MacOSX"]`, so the slice intends to be macOS — this is an upstream packaging bug.

## Fix

- Re-pinned `BattyKit/Package.swift` to `https://github.com/Lakr233/libghostty-spm` at revision `6ebd4bd2867f4bb8084e438dfa9a6531ad1f2ca7` (tag `1.1.9`, current `main`). This addresses the 404 and lets us track upstream directly now that the fork's local changes have been merged.
- Added `scripts/fix-libghostty-framework.sh`: idempotent zsh script that reshapes the macOS slice in the SPM artifact cache from shallow to versioned layout (`Versions/A/{Headers,Modules,Resources,binary}` with root-level symlinks). Handles partial-conversion state by tearing down and reshaping fresh.
- Added `scripts/build.sh`: wrapper that runs `xcodebuild -resolvePackageDependencies`, then the fixup, then `xcodebuild build`. This is now the canonical build command for the project.

The fixup script cannot run as an Xcode build phase: `ProcessXCFramework` executes well before any of the target's `PBXShellScript` phases, so by the time a build-phase script runs, the embedded `libghostty.framework` is already shallow. Wrapping the build is the only place a fixup can sit and reliably precede `ProcessXCFramework`.

## Verification

- Purged `DerivedData/Batty-*` to force a fresh SPM extract.
- `scripts/build.sh` — `** BUILD SUCCEEDED **`. Observed:

## Gotchas

- **The fixup cannot live in an Xcode build phase.** `ProcessXCFramework` runs before any `PBXShellScript` phase on the consuming target, so any build-phase script attempting to fix the source xcframework runs too late. (An earlier attempt added a `PBXShellScriptBuildPhase` to the Batty target and confirmed via log line numbers that the script fired at log line ~5525 while `ProcessXCFramework` had already run at line ~2108.) The wrapper script approach is necessary.
- **SPM repopulates the source xcframework opportunistically.** During a single build, after the fixup script mutated the source, the original shallow root files reappeared alongside the new `Versions/A/` tree — Xcode appears to refresh the artifact mid-build from the `SourcePackages/artifacts/extract/` cache. This is why the fix has to run between `-resolvePackageDependencies` and `build`, with no other steps in between, rather than as a build phase.
- **`scripts/build.sh` is now the canonical build command.** Raw `xcodebuild -scheme "Batty (Prod)" -destination 'platform=macOS' build` will fail at the embed-frameworks step. `Issues.md` and `CLAUDE.md` updated to reflect this in the same change set.
- **The actual project scheme name is `Batty (Prod)`, not `Batty`.** Pre-existing doc drift; updated alongside the wrapper-script reference.
- **`release.sh` is unaffected by this fix.** It calls `xcodebuild archive` directly, which produces a different artifact path — but it also won't work until similarly wrapped or until upstream packaging is fixed. Out of scope for #0212; file a follow-up if/when distribution becomes relevant again.
