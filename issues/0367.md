## Description

**Cosmetic today; a trap the moment `hasPending` is used as a guard.**
`SingleSlotRetryScheduler` (`BattyKit/Sources/BattyKit/XPC/SingleSlotRetryScheduler.swift`)
stores a pending handle and offers `replace(with:)`, `clear()`, and `hasPending`.
Nothing ever tells it a handle has **run**. There is no `didFire()` / `take()` /
completion hook, and `AppXPCCoordinator`'s `retryAfterBackoff` does not clear the
slot when it executes.

Two consequences follow:

- `hasPending` returns `true` forever after the first retry is scheduled, even
  once that retry has fired and finished. It reports "a handle is stored", not
  "an action is pending".
- A later `replace(with:)` or `clear()` calls `cancel()` on a `DispatchWorkItem`
  that already executed. That is a documented no-op on `DispatchWorkItem`, so
  nothing breaks — it is simply dead work built on a false premise.

Neither costs anything at present, because `AppXPCCoordinator` never branches on
`hasPending` — the only production reads are `replace(with:)` and `clear()`. The
type's own doc comment invites exactly that branch though ("`true` while a handle
is pending"), and the first caller who trusts it gets the wrong answer.

## Expected behavior

`hasPending` is `true` only while an action is genuinely still going to happen —
the slot is cleared when the handle fires, not just when it is cancelled or
replaced.

## Actual behavior

`hasPending` is `true` from the first `replace(with:)` until the next `clear()`,
regardless of whether the scheduled action already ran.

## Notes

### Shape of the fix

The type is deliberately generic over its handle (`SingleSlotRetryScheduler<Handle>`,
`DispatchWorkItem` in production) with no `Dispatch` dependency, specifically so
the "replacing cancels the old one" invariant is unit-testable against a plain
value stand-in. Keep that. Options that preserve it:

- Add a `markFired()` / `clearWithoutCancelling()` that nils the slot without
  calling `cancel`, and have `retryAfterBackoff` call it first thing.
- Or have `replace(with:)` hand back a wrapped handle whose execution clears the
  slot, so the caller cannot forget.

Either way the existing `SingleSlotRetrySchedulerTests` should grow a case
asserting `hasPending == false` after a fire, alongside the existing
replace/cancel coverage.

## Resolution notes

> 🟢 Resolved 2026-09-23 — `SingleSlotRetryScheduler.markFired()` clears the slot when the scheduled handle runs, so `hasPending` means "an action is still going to happen", and a later `clear()`/`replace(with:)` no longer cancels an already-fired handle.

## Root cause

As filed: nothing told the scheduler its handle had run, so `hasPending` stayed `true` after the first retry fired.

## Fix

- `SingleSlotRetryScheduler.markFired()` sets `pending` to nil without calling `cancel`. No identity check: a handle superseded by `replace(with:)` is always cancelled before it can run, because both happen on the main serial queue (since #0366).
- `AppXPCCoordinator.retryAfterBackoff()` calls `backoffRetryScheduler.markFired()` first, before its `listenerEndpoint` guard.
- `hasPending`'s doc now matches. The #0391 `deinit {}` workaround is unchanged; its comment no longer forward-references this issue.
