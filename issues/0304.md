## Description

The first concrete non-terminal view: a **Git Status view** that monitors a directory and presents `git status` visually, the way a Mac app can and a TUI cannot — creatable and closable from the `batty` CLI. In the user's words (from the #0301 umbrella):

> "The first new view we can add is Git Status. It can monitor the current directory and show status very similar to `git status` but in a more visual way like a Mac app can support which a TUI cannot. The CLI will be able to create a new pane with the Git Status view as well as close it."
>
> "When we get to this issue we can draft visual designs before implementing it."

This is **not a build-it ticket**. It is explicitly two-phase and design-gated per the umbrella:

- **Phase 1 — visual designs.** Draft mockups/design directions for the Git Status view and settle the design-phase questions below. Deliverable: designs for the user to review. **No implementation happens in phase 1.**
- **Phase 2 — implementation.** Starts only after the user approves the designs. If the design review changes scope materially, re-file or amend before coding.

Deliverables:

- `docs/design/git-status-view.html` — a self-contained mockup covering five states: clean repo; mixed staged/unstaged/untracked with badges and an open diff peek; mid-rebase with a conflict; not-a-git-repository; and large-repo stale-while-refreshing.

The four decisions, for the user to accept or redirect:

1. **Directory** — resolved once at pane creation (CLI `--path`, else the previously-focused Pane's active-Tab working directory, else `$HOME`), then **frozen**. Not live-following. A "Change Directory…" picker is the explicit way to retarget.
2. **What it shows** — header with repo/branch/ahead-behind/stash and submodule/worktree badges; a state banner for rebase/merge/cherry-pick; four disclosable groups (conflicted/staged/unstaged/untracked, the first conditional); click-to-select inline diff peek; a non-mutating context menu.
3. **Read-only** for the first ship. Staging, unstaging and discard are named as deferred, not stubbed.
4. **Currency** — FSEvents with two-layer debounce, running `git --no-optional-locks status --porcelain=v2 --branch --show-stash` off the main thread, wired to `PaneContentLifecycle` so a hidden pane does zero periodic work.

Review: `claude-opus-5`, three rounds. Every round found a factual error in text describing this codebase, and two of those arrived in text written to correct the previous round's error:

- **Round 1** — the doc justified freezing the directory by claiming `SplitTreeNode` is flat and cannot track siblings pairwise. - **Round 3** — verified the corrected attribution to `inserting`'s nesting, traced both concrete nesting shapes, and independently verified the newly-added `removingPane` claim (`SplitTree.swift:357-375`) rather than accepting it. Approved.

## Design-phase questions (to answer in phase 1, not decided here)

1. **Which directory does it monitor?** The user said "the current directory" — but a Pane has no cwd of its own; a Terminal Session does (`TabRuntime.workingDirectory`, `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:47`). Options to lay out in the designs: the cwd of the sibling terminal Pane it was split from (frozen at creation vs. live-following that pane's `cd`s), an explicitly-set path with a folder picker, or a path supplied by the CLI at creation (`--path`). This is the first thing a design has to answer, including what the view shows when the directory is not a git repository, is a submodule, or is a linked worktree.
2. **What it shows.** Staged / unstaged / untracked groupings, per-file status, branch with ahead/behind, merge/rebase/cherry-pick state, stash count, diff stats. The user's point is that a Mac app can do what a TUI cannot — selection, disclosure triangles, inline diff peeks, click-through to files — so the designs should exploit that rather than reproduce a text table in a nicer font.
3. **Read-only or interactive?** Staging, unstaging, and discarding are the obvious next asks and carry real destructive-action risk (discard especially). The design must settle this explicitly; a read-only first cut is the conservative option and keeps phase 2 small.
4. **How it stays current.** Filesystem watching (FSEvents / `DispatchSource`) vs. polling; debounce strategy for large repos mid-build (thousands of file events); cost of running `git status` on a huge working tree; behavior when `.git` itself churns (rebase in progress). Whatever the answer, the watcher suspends when the Pane is hidden and tears down when it closes, per the #0303 lifecycle.

## Root cause

Not a bug — this is the phase-2 build-out of a design-gated feature. #0315 shipped the kind-switch plumbing with a deliberately provisional placeholder for every non-terminal kind; this issue replaces that placeholder for `.gitStatus` specifically with the real, approved view.

## Fix

**Directory resolution (§1).** `batty pane split --view git-status [--path <dir>]` now threads an optional `--path` end to end: `PaneCommand` resolves it to an absolute path, rejects it client-side unless `--view git-status` was also given (review round 1, D3 — the original check only rejected the *terminal* case, so it was silently accepted-and-ignored for every other non-terminal kind), and packs it into `PaneSplitRequest.viewOptions["path"]` — a generic, per-kind string-keyed option bag (review round 1's shared-wire-shape decision, replacing the bespoke `path: String?` field this issue shipped first) that `AppXPCService` unpacks and hands to `AppStateStore.splitPane`/`SplitTree.splitPane`/`makePane` as a plain `path: String?` internally. When `--path` is omitted, `makePane` falls back to the target pane's own active Tab's working directory (the same cwd a terminal split would inherit); `PaneRuntime.init` falls back to `$HOME` as the last resort. The directory is frozen at construction — the only way it changes afterward is the view's own "Change Directory…" picker (`GitStatusPaneContent.changeDirectory(to:)`, backed by an `NSOpenPanel`).

**`contentFactory` composability with #0313 (round 3 rebase).** `SplitTree.makePane`/`splitPane` and `AppStateStore.splitPane` all gained a `contentFactory` parameter from #0313, defaulting to `PaneRuntime.makeContent` in that issue's own code. Merged naively, this issue's `.gitStatus`-specific path-resolution branch inside `makePane` would have *ignored* an explicit test-supplied `contentFactory` and constructed a real `GitStatusPaneContent` anyway — the compiler doesn't catch that, since both "no override" and "an override matching the default" are indistinguishable once the default is baked in as a concrete function value. Fixed by changing all three `contentFactory` parameters' defaults from a concrete `PaneRuntime.makeContent` to `nil`, forwarded unchanged at every layer; only `SplitTree.makePane` — the one place with both `path` and `source` in scope — resolves `nil` into either the real default (`PaneRuntime.makeContent(for:)`, for every kind but `.gitStatus`) or the path-aware `.gitStatus` override. An explicit `contentFactory` now always wins, unconditionally, regardless of which layer supplied it.

**Repository-toplevel resolution (round 3, R1 — blocking).** `git status --porcelain=v2` always reports paths relative to the repository's working-tree root, never `directoryPath` (which can be a subdirectory of the repo — the common case, since `SplitTree.makePane` inherits the source pane's cwd). `--show-toplevel` is now part of the same combo `rev-parse` call (placed *before* `--show-superproject-working-tree`, whose line is absent — not blank — outside a submodule and would otherwise shift `--show-toplevel`'s position). `GitStatusRawScan`/`GitStatusSnapshot` carry the resolved `repositoryToplevel`; `GitStatusPaneContent.repositoryToplevelOrDirectoryPath` and the view's `absoluteFileURL(for:)` use it instead of `directoryPath` for `diff(atPath:)` and the three file-URL-building context-menu actions. `repoName` is derived from the toplevel's last path component, not `directoryPath`'s.

**The conformer.** `GitStatusPaneContent` (`BattyKit/Sources/BattyKit/Runtime/GitStatusPaneContent.swift`) is model-owned — reachable via `PaneRuntime.content: (any PaneContentLifecycle)?` (main's shared, kind-generic property post-#0314; cast at the read site, `PaneView.nonTerminalContent`), constructed once at `PaneRuntime.init` via the injectable `contentFactory` and never rebuilt by SwiftUI churn. It conforms to `PaneContentLifecycle` via `PaneLifecycleController` exactly per `docs/pane-view-lifecycle.md` §6: `setUp(visible:)` goes straight to `.suspended` without ever creating a watcher when the initial visibility is `false`; `setVisible(true)` (re)acquires a watcher and forces exactly one refresh; `setVisible(false)` releases the watcher/debounce timer to true zero and sends a non-waiting `terminate()` to any in-flight scan; `tearDown()` does the same plus a bounded (~300ms poll, not `waitUntilExit()`) wait for the subprocess to actually exit, and is idempotent.

Two injectable seams keep the conformer testable without a real filesystem/subprocess and match the production shape 1:1: `GitStatusWatching` (production: `FSEventsGitStatusWatcher`, a real recursive `FSEventStream` on the resolved path, 400ms software-debounced on top of the OS's own coalescing) and `GitStatusScanning` (production: `ProcessGitStatusScanner`, spawning the user's real `git` via `/usr/bin/env` off the main thread). The scan command is `git --no-optional-locks -C <path> status --porcelain=v2 --branch --show-stash -z`, plus one combined `git rev-parse --path-format=absolute --is-inside-work-tree --git-dir --git-common-dir --show-superproject-working-tree` call for the not-a-repo/submodule/worktree facts, plus plain `FileManager` existence checks against `rebase-merge`/`rebase-apply`/`MERGE_HEAD`/`CHERRY_PICK_HEAD` for the state banner. An in-flight-scan flag coalesces a debounce tick that lands mid-scan into "run once more after this one finishes," bounding concurrent `git` subprocesses to one per pane. A monotonic `generation` counter, bumped on every `activate`/`suspend`/`changeDirectory`, lets a scan result that arrives after the pane has since been hidden (or retargeted) recognize it's stale and discard itself rather than updating UI nobody wants updated.

**Parsing (§2, §4) — rewritten in round 1 for `-z` (B1).** `GitStatusPorcelainParser` (`BattyKit/Sources/BattyKit/Model/GitStatusModel.swift`) is a pure, no-I/O parser for `-z`-terminated `--porcelain=v2` output — branch/oid/detached, ahead/behind/upstream, stash count, and the four record types (`1` ordinary, `2` rename/copy — now two separate NUL-terminated tokens, path then origPath, not one token with an embedded tab — `u` unmerged, `?` untracked). The pre-round-1 version ran without `-z` and took every path field literally; without `-z`, porcelain v2 C-quotes any path with a control character or (under the default `core.quotePath=true`) any byte ≥ 0x80, so a file named `café.txt` rendered as the literal escaped text `"caf\303\251.txt"` — which then broke `git diff -- <path>` (matched nothing, so the diff peek said "No diff available." for every such file) and Reveal in Finder/Copy Path/Open in Default Editor (all resolved to a path that didn't exist). `-z` disables that quoting entirely and is git's own documented recommendation for machine consumption. Field layout re-verified against real `git status --porcelain=v2 -z` output (git 2.50.1, via `od -c`) for a real non-ASCII filename, a path with a space, and a path with a literal `"`. Separately, `ProcessGitStatusScanner`'s decode of `git status`'s stdout now surfaces a `.scanFailed` state instead of silently collapsing an undecodable byte sequence to `""` and reporting a clean working tree for a repository that isn't (the pre-round-1 code did `String(data:encoding:.utf8) ?? ""`).

**The view (§2, §3).** `GitStatusPaneView` (`BattyKit/Sources/BattyKit/Views/GitStatusPaneView.swift`) renders the header (repo name, branch or detached-HEAD short SHA, ahead/behind arrows, stash badge, submodule/worktree badges, a manual refresh button, "Change Directory…"), the state banner for rebase/merge/cherry-pick, four `DisclosureGroup`s (conflicted — conditional, sorted first — /staged/unstaged/untracked) with two-letter status badges colored by the same red/green/orange/gray semantic vocabulary the design calls out, a click-to-select inline diff peek (`git diff`/`git diff --cached` via the same scanner seam), and a non-mutating context menu (Reveal in Finder, Copy Path, Open in Default Editor). Entirely read-only, per §3 — no action here calls a git mutation. `PaneView.gitStatusBody` wires it in, sharing the `nonTerminalHeader` (drag handle + eye button) that `#0334` already established for every non-terminal kind.

**Lifecycle wiring at the shared choke points (`docs/pane-view-lifecycle.md` §5) — now generic, via #0314.** `WindowRuntime.hidePane`/`showPane` call `pane.content?.setVisible(false/true)`; `tearDownNonTerminalContent(in:)` — one helper, called from `closePane`, `removeSession`, `closeTab`'s pane-removal branch, `RootWindowView.windowWillClose`, and `BattyAppDelegate.applicationWillTerminate` — calls `pane.content?.tearDown()`. All five call sites are kind-agnostic; `GitStatusPaneContent` gets exactly the same treatment `SystemMetricsPaneContent` does, with no `.gitStatus`-specific code in `WindowRuntime` at all. `SplitTree.makePane` is the one place that *is* kind-specific: for `.gitStatus` it overrides the default `contentFactory` with one that resolves the directory (CLI `--path`, else the source pane's cwd, else `$HOME`) before constructing `GitStatusPaneContent`.

## Review

**Round 1 — `claude-opus-5` — REQUEST CHANGES**, confirmed build/1092/121, mutation-tested the parser and lifecycle code, and independently verified the read-only guarantee, FSEvents lifecycle, debounce, and every defined non-repo/hostile-path state before finding two blocking defects:

- **B1 — the parser never decoded git's C-quoted paths.** Without `-z`, porcelain v2 C-quotes any non-ASCII (`core.quotePath=true`, the default) or control-character path, and the pre-round-1 parser took that quoted, escaped text literally. Fixed by adding `-z` to the status command and rewriting `GitStatusPorcelainParser` around NUL-terminated tokens (a rename/copy record's `origPath` is now a separate token, not a tab-joined suffix). Also fixed: `ProcessGitStatusScanner` no longer silently decodes an undecodable byte sequence to `""` (which would have reported a clean tree for a dirty repo) — it's now a distinct `.scanFailed` state.
- **B2 — `isWorktree` compared two differently-shaped paths.** `--git-dir` and `--git-common-dir` are only directly comparable when both are resolved the same way; without `--path-format=absolute`, a plain checkout's `--git-dir` from a subdirectory (the common case, since a new pane inherits its source's cwd) came back relative while `--git-common-dir` didn't, producing a false "Worktree" badge. The approved design (`docs/design/git-status-view.md` §1) specified the comparison this way; the design was the origin of the bug, corrected here. Fixed by adding `--path-format=absolute`.

Both fixes were mutation-tested by reverting each in turn and confirming the corresponding test fails, then restoring — `scanOfAPlainSubdirectoryIsNotMisidentifiedAsAWorktree` catches B2's regression exactly; `scanHandlesARealNonASCIIFilenameEndToEnd` catches B1's.

## Gotchas

- **The one-time `rev-parse`/marker-file shape checks are re-run on every scan, not cached after the first success.** The design (§4) frames these as "single, cheap, additional `git rev-parse` calls run once at setup," implying a cache. This implementation re-derives `is-inside-work-tree`/`git-dir`/`git-common-dir`/`show-toplevel`/`show-superproject-working-tree` and the four marker-file existence checks on every refresh instead, to avoid a second cached-state model living alongside the scan result. Functionally correct (a repo doesn't stop being a submodule/worktree/change its toplevel between refreshes), and cheap (rev-parse and `FileManager.fileExists` are not `git status`), but a real, if small, deviation from the design's stated optimization.
- **The session-selection half of "effective visibility" is not wired.** `docs/pane-view-lifecycle.md` §2 names two facts that matter for a non-terminal pane's visibility: the hidden-Pane fact (wired) and the non-selected-Session fact (no model-level call site exists yet to source it from). `PaneRuntime.init` approximates initial visibility from `isHidden` alone. A `.gitStatus` pane in a background (non-selected) Session keeps its watcher/debounce running rather than suspending — bounded (one FSEventStream + occasional single `git` subprocess), not the full "zero periodic work" ideal. Flagged, not fixed.
- **`ProcessGitStatusScanner.activeProcess` isn't scan-scoped (D1, filed as a follow-up).** A `changeDirectory → suspend → activate` sequence in quick succession can have an older scan's `defer { setCurrentProcess(nil) }` clear a newer scan's `activeProcess` out from under it, making a subsequent `terminateAndWaitBriefly()` a silent no-op for that newer process. Bounded: no orphaned process, the cost is a missed `SIGTERM` on the pathological interleaving.
- **`setUp(visible: false)` leaves `state == .loading` rather than running the shape checks (D5, filed as a follow-up).** A hidden-at-creation `.gitStatus` pane shows a spinner until the first `setVisible(true)` completes a full scan, rather than showing the repo name/not-a-repo state immediately.
- **The manual terminal-pane checklist (`docs/terminal-pane-requirements.md` §6) is owed, not run.** This is the same gap #0315 and #0334 each recorded and left open.
- **No visual verification against the mockup.** Built to the design document's prose and the mockup's HTML/CSS structure, cross-checked textually, but this implementer cannot run the app or take a screenshot.
- **Diff peek has no syntax highlighting beyond +/- line coloring**, per the design's own explicit non-goal. Capped at 2000 lines (D2).
- **The "Refreshing…" indicator shows immediately whenever a scan is in flight**, rather than only after a ~1s threshold as the design suggests for the large-repo case.
- **C1/C2 — resolved via the #0314 rebase, confirmed twice, not just assumed.** `tearDown()` runs on all five pane-removal paths via `WindowRuntime.tearDownNonTerminalContent(in:)`/`tearDownAllPaneContent()`; `contentFactory` injection means a test can construct a `.gitStatus` pane without starting a real watcher. Re-confirmed via instrumentation after every subsequent rebase (see `## Verification`).
- **`RootWindowView.windowWillClose`/`applicationWillTerminate` calling `tearDownAllPaneContent()` is code-correct but test-uncovered** (noted by #0314's own reviewer). `NonTerminalPaneTeardownPathsTests` calls `tearDownAllPaneContent()` directly — a cheap, real seam — but nothing exercises the actual `NSWindowDelegate`/`NSApplicationDelegate` callbacks that call it. Shared #0314 infrastructure, not `.gitStatus`-specific.
- **`diff(atPath:)`'s pathspec handling.** `--literal-pathspecs` (added this round) fixes the `*`/`?` globbing case for the diff peek specifically. Not audited elsewhere.
