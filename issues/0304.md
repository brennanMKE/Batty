## Description

The first concrete non-terminal view: a **Git Status view** that monitors a directory and presents `git status` visually, the way a Mac app can and a TUI cannot — creatable and closable from the `batty` CLI. In the user's words (from the #0301 umbrella):

> "The first new view we can add is Git Status. It can monitor the current directory and show status very similar to `git status` but in a more visual way like a Mac app can support which a TUI cannot. The CLI will be able to create a new pane with the Git Status view as well as close it."
>
> "When we get to this issue we can draft visual designs before implementing it."

This is **not a build-it ticket**. It is explicitly two-phase and design-gated per the umbrella:

- **Phase 1 — visual designs.** Draft mockups/design directions for the Git Status view and settle the design-phase questions below. Deliverable: designs for the user to review. **No implementation happens in phase 1.**
- **Phase 2 — implementation.** Starts only after the user approves the designs. If the design review changes scope materially, re-file or amend before coding.

## Phase 1 status (2026-08-08) — designs delivered, awaiting user approval

**Phase 1 is complete and landed on `main`. Phase 2 has not started and must not start until the user approves.** The issue stays `in-progress`, not `resolved`: #0301's acceptance criteria require the design-first gate to have actually held, and the user's approval is that gate.

Deliverables:

- `docs/design/git-status-view.md` — the design document, answering all four design-phase questions with decisions rather than options.
- `docs/design/git-status-view.html` — a self-contained mockup covering five states: clean repo; mixed staged/unstaged/untracked with badges and an open diff peek; mid-rebase with a conflict; not-a-git-repository; and large-repo stale-while-refreshing.

The four decisions, for the user to accept or redirect:

1. **Directory** — resolved once at pane creation (CLI `--path`, else the previously-focused Pane's active-Tab working directory, else `$HOME`), then **frozen**. Not live-following. A "Change Directory…" picker is the explicit way to retarget.
2. **What it shows** — header with repo/branch/ahead-behind/stash and submodule/worktree badges; a state banner for rebase/merge/cherry-pick; four disclosable groups (conflicted/staged/unstaged/untracked, the first conditional); click-to-select inline diff peek; a non-mutating context menu.
3. **Read-only** for the first ship. Staging, unstaging and discard are named as deferred, not stubbed.
4. **Currency** — FSEvents with two-layer debounce, running `git --no-optional-locks status --porcelain=v2 --branch --show-stash` off the main thread, wired to `PaneContentLifecycle` so a hidden pane does zero periodic work.

Review: `claude-opus-5`, three rounds. Every round found a factual error in text describing this codebase, and two of those arrived in text written to correct the previous round's error:

- **Round 1** — the doc justified freezing the directory by claiming `SplitTreeNode` is flat and cannot track siblings pairwise. It is an `indirect enum` binary tree and `SplitTree.inserting` produces exactly that pairwise relationship. The decision was right; the premise was not, and the user would have been approving on it. Round 1 also caught that the specified command omitted `--no-optional-locks`, so refreshes would have contended for `.git/index.lock` with git running in the user's own terminal pane, and that "terminates the subprocess synchronously" overstated `Process.terminate()`.
- **Round 2** — the replacement reasoning blamed `rebalancingChain` for restructuring the tree. That function preserves shape exactly; its own doc comment says it "rebalances every ratio in that chain". Round 2 also explicitly *cleared* the bounded-timeout teardown against `docs/pane-view-lifecycle.md` §5 rather than letting it slide, reasoning that §5 forbids deferral to a Batty-controlled later moment and a bounded wait on the calling thread is not that.
- **Round 3** — verified the corrected attribution to `inserting`'s nesting, traced both concrete nesting shapes, and independently verified the newly-added `removingPane` claim (`SplitTree.swift:357-375`) rather than accepting it. Approved.

What phase 2 will owe, recorded so the cost is visible before approval: `docs/pane-kinds.md` §6 obligates whichever issue lands the kind field, the `PaneView` kind-switch and the non-terminal render path to re-run `docs/terminal-pane-requirements.md` §6's manual checklist on **terminal** panes, and again in a **mixed-kind** session. #0304 phase 2 is that issue.

## Design-phase questions (to answer in phase 1, not decided here)

1. **Which directory does it monitor?** The user said "the current directory" — but a Pane has no cwd of its own; a Terminal Session does (`TabRuntime.workingDirectory`, `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:47`). Options to lay out in the designs: the cwd of the sibling terminal Pane it was split from (frozen at creation vs. live-following that pane's `cd`s), an explicitly-set path with a folder picker, or a path supplied by the CLI at creation (`--path`). This is the first thing a design has to answer, including what the view shows when the directory is not a git repository, is a submodule, or is a linked worktree.
2. **What it shows.** Staged / unstaged / untracked groupings, per-file status, branch with ahead/behind, merge/rebase/cherry-pick state, stash count, diff stats. The user's point is that a Mac app can do what a TUI cannot — selection, disclosure triangles, inline diff peeks, click-through to files — so the designs should exploit that rather than reproduce a text table in a nicer font.
3. **Read-only or interactive?** Staging, unstaging, and discarding are the obvious next asks and carry real destructive-action risk (discard especially). The design must settle this explicitly; a read-only first cut is the conservative option and keeps phase 2 small.
4. **How it stays current.** Filesystem watching (FSEvents / `DispatchSource`) vs. polling; debounce strategy for large repos mid-build (thousands of file events); cost of running `git status` on a huge working tree; behavior when `.git` itself churns (rebase in progress). Whatever the answer, the watcher suspends when the Pane is hidden and tears down when it closes, per the #0303 lifecycle.
