## Description

The first concrete non-terminal view: a **Git Status view** that monitors a directory and presents `git status` visually, the way a Mac app can and a TUI cannot — creatable and closable from the `batty` CLI. In the user's words (from the #0301 umbrella):

> "The first new view we can add is Git Status. It can monitor the current directory and show status very similar to `git status` but in a more visual way like a Mac app can support which a TUI cannot. The CLI will be able to create a new pane with the Git Status view as well as close it."
>
> "When we get to this issue we can draft visual designs before implementing it."

This is **not a build-it ticket**. It is explicitly two-phase and design-gated per the umbrella:

- **Phase 1 — visual designs.** Draft mockups/design directions for the Git Status view and settle the design-phase questions below. Deliverable: designs for the user to review. **No implementation happens in phase 1.**
- **Phase 2 — implementation.** Starts only after the user approves the designs. If the design review changes scope materially, re-file or amend before coding.

## Design-phase questions (to answer in phase 1, not decided here)

1. **Which directory does it monitor?** The user said "the current directory" — but a Pane has no cwd of its own; a Terminal Session does (`TabRuntime.workingDirectory`, `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:47`). Options to lay out in the designs: the cwd of the sibling terminal Pane it was split from (frozen at creation vs. live-following that pane's `cd`s), an explicitly-set path with a folder picker, or a path supplied by the CLI at creation (`--path`). This is the first thing a design has to answer, including what the view shows when the directory is not a git repository, is a submodule, or is a linked worktree.
2. **What it shows.** Staged / unstaged / untracked groupings, per-file status, branch with ahead/behind, merge/rebase/cherry-pick state, stash count, diff stats. The user's point is that a Mac app can do what a TUI cannot — selection, disclosure triangles, inline diff peeks, click-through to files — so the designs should exploit that rather than reproduce a text table in a nicer font.
3. **Read-only or interactive?** Staging, unstaging, and discarding are the obvious next asks and carry real destructive-action risk (discard especially). The design must settle this explicitly; a read-only first cut is the conservative option and keeps phase 2 small.
4. **How it stays current.** Filesystem watching (FSEvents / `DispatchSource`) vs. polling; debounce strategy for large repos mid-build (thousands of file events); cost of running `git status` on a huge working tree; behavior when `.git` itself churns (rebase in progress). Whatever the answer, the watcher suspends when the Pane is hidden and tears down when it closes, per the #0303 lifecycle.
