## Description

When a user renames a session (e.g. `Session 2` → `Batty`), it's almost always because the session's first pane is working in a directory that has a meaningful name (`~/Developer/Batty`). The user has no way to tell Batty "every time I start a session in this directory, call it `Batty`" — they re-rename every time. Over weeks of use this is a real friction.

Proposed feature: maintain a key/value cache mapping **working directory path → most recently used session name**. When a new session is created (per `#0057`, its first pane starts in the focused pane's CWD), look up the CWD in the cache; if a name exists, apply it automatically as the session title. When the user renames a session, write back to the cache keyed on the first pane's current CWD.

Cap the cache at ~100 entries with LRU eviction so it doesn't grow unbounded. Store as a small JSON file in Application Support next to `workspace.json`.

## Behavior summary

| Event | Effect on cache |
|---|---|
| User renames a session via the sidebar context menu / inline rename | Write `(firstPaneCWD, newName)` to cache. Updates LRU recency. |
| User creates a new session whose first pane lands in a known CWD | Apply cache's name as the session title. Updates LRU recency. |
| User creates a new session in an unknown CWD | Default name (`Session N`) as today. No cache write. |
| Cache exceeds 100 entries | Evict the least-recently-used entry. |
| Cache file missing / corrupt | Treat as empty; recreate on next write. Quiet recovery. |

## Steps to reproduce (motivating workflow)

1. Open Batty. Default session "Session 1" opens in `~`.
2. `cd ~/Developer/Batty`. Rename the session (sidebar context menu) to `Batty`.
3. Quit. Relaunch.
4. **Today:** new "Session 1" opens at `~`. Even if you cd to `~/Developer/Batty` you have to rename again.
5. **With `#0057`:** new "Session 1" opens at the focused pane's CWD. Still named `Session 1`.
6. **With this feature on top of `#0057`:** new session's first pane is in `~/Developer/Batty`; the cache lookup hits "Batty"; the session opens already named `Batty`.

The matching scenario without quit/relaunch: create a second session from a focused pane already in `~/Developer/Batty`. The second session is auto-named `Batty` immediately.

## Expected behavior

### Cache schema

```json
{
  "version": 1,
  "entries": [
    {
      "path": "/Users/brennan/Developer/Batty",
      "name": "Batty",
      "lastUsedAt": "2026-05-11T18:02:13Z"
    },
    {
      "path": "/Users/brennan/Developer/brennanMKE/libghostty-spm",
      "name": "ghostty fork",
      "lastUsedAt": "2026-05-10T22:31:04Z"
    }
  ]
}
```

- `path` — absolute path string. Stored as-is from `TerminalViewState.workingDirectory`. Do not resolve symlinks; do not collapse `$HOME` to `~`. The user's intuition matches the literal shell-reported path.
- `name` — the session title the user picked. Trimmed of whitespace; non-empty.
- `lastUsedAt` — ISO-8601 timestamp; powers LRU eviction.
- `version` — schema version so we can evolve the format later without crashing old caches.

### Lookup rules

- Exact-path match only for v1. No prefix or "starts with" matching. Different intuitions in `~/Developer/Batty` vs `~/Developer/Batty/BattyKit` should not collide.
- Match consumes the entry's `lastUsedAt` slot — bump it to "now" so frequently-used names stay alive against the 100-cap eviction.
- A miss leaves the session at its default name (`Session N`). Don't apply heuristic fallbacks like basename — those are tracked separately if we want them.

### Write rules

- Write on rename. Source the path from `session.tree.firstLeafPane.tabs[0].terminal.workingDirectory` at the moment of the rename (the *first* pane's *first* tab's CWD). The rationale is that "the session is for working on X" is anchored by where it started; downstream cd's don't change the identity of the session.
- Don't write on default-named sessions (`Session N`). If the user never renames, no signal.
- Don't write when the path is empty / unknown (shell hasn't published OSC 7 yet, etc.). Just skip — the user can rename later when the path is settled.

### Cap and eviction

- Hard cap: 100 entries. When inserting the 101st, drop the entry with the oldest `lastUsedAt`.
- A `Settings` toggle to clear the cache is fine to add now: "Clear remembered session names" button under a future "Sessions" pane in Settings. v1 can ship without the UI; the cache file is deletable manually.

### Storage location

- `~/Library/Application Support/Batty/session-name-cache.json`. Sibling to `workspace.json`.
- Atomic write (write to temp, rename) so a crash mid-save doesn't truncate the file. The existing `WorkspaceStore` already implements this pattern — reuse the helper or factor it out.

## Implementation sketch

- New `SessionNameCache` (in `BattyKit/Sources/BattyKit/SessionNameCache.swift`) — `@Observable final class` exposing `lookup(path: String) -> String?` and `record(path: String, name: String)`. Owns the cache file.
- `AppStateStore` holds one instance. `addSession` consults it after `#0057`'s CWD inheritance lands; rename paths call `record` after writing the title.
- Persistence: 250ms debounce on writes (rename burst protection). Save on `applicationWillTerminate` via the existing `WorkspaceManager` hook.
- Unit tests: round-trip JSON; LRU eviction at 101 entries; lookup hit / miss / empty cache; rename on a default-named session writes, rename clearing the name back to empty does not write a blank entry.
- Concepts.md → Session needs a one-paragraph mention of the cache, so the convention is documented.

## Notes

- **Dependency on `#0057`.** Without CWD inheritance, the new session's CWD is the shell's startup default (`$HOME`), which would hit a single cache slot ("Home") and apply whatever name the user once gave a home-directory session. Order: ship `#0057` first; this feature on top.
- **Caching the *first* pane's *first* tab's CWD is deliberate.** It matches user intuition ("this session is for the Batty project"). Caching the focused pane's CWD at rename time would mean a session renamed while temporarily in a subdirectory would map the subdirectory to the name, which gets messy fast. First-pane-first-tab is the stable anchor.
- **No path normalization in v1.** If the user's shell reports `/Users/brennan/Developer/Batty` and a different shell ever reports `/Users/brennan/./Developer/Batty`, those won't match. In practice macOS shells emit canonical paths via OSC 7. Revisit if it becomes a real issue.
- **Rename hooks.** Existing rename entry points: sidebar context menu rename (`AppStateStore.renameSession`), any future inline-rename UI, and the bell-feed-jump path doesn't rename. The single `renameSession` call site is the right hook.
- **The cache is separate from `workspace.json`.** Workspace persistence is the layout snapshot (and per `#0055` may stop being read on launch); the name cache is user-preference data that should survive `#0055`'s disable. Separate file, separate lifetime.
- **Related:** `#0043` (session names sticking through OSC title changes — fixed by ignoring shell-set titles for the sidebar). This feature is layered on top: once we ignore shell-set titles, user-set titles are stable, and the cache makes them auto-applied on the next matching CWD.
- **Out-of-scope variants worth noting** (so we don't accidentally widen v1):
  - Per-repo `.battyrc` files defining a session name — heavier; do only if asked.
  - Git-root-based naming (`git rev-parse --show-toplevel` → basename) — useful but inferred, not user-picked. The cache is about remembering user choices.
  - Project-detection heuristics (`package.json`'s `name`, etc.) — same as above; explicit user input wins.

## Acceptance criteria

- Renaming a session whose first pane is in `~/Developer/Batty` writes `(/Users/<me>/Developer/Batty, "Batty")` to the cache.
- Creating a new session whose first pane lands in `~/Developer/Batty` (per `#0057`) auto-applies the title `Batty` before the user sees the new session.
- A miss (unknown CWD) leaves the session at `Session N` default.
- The cache file at `~/Library/Application Support/Batty/session-name-cache.json` survives quit/relaunch.
- Caps at 100 entries; LRU evicts the oldest.
- Corrupt or missing cache file is recovered to empty silently.
- Unit tests cover round-trip, eviction, hit/miss/empty, and the rename-on-default-name behavior.

## Out of scope

- A UI for browsing or editing cache entries.
- Sharing the cache across machines (iCloud sync, Dropbox-style).
- Wildcard / prefix matching, regex matching.
- Per-session "remembered name" override (user-disable for a specific session).

## Root cause

Feature gap. After `#0057` landed CWD inheritance, renaming the auto-named "Session N" to something meaningful in the same project directory had to happen on every new session — Batty had no memory of past user-chosen names tied to a working directory.

## Fix

Added a `SessionNameCache` (`@Observable` class, main-actor) that owns `~/Library/Application Support/Batty/session-name-cache.json` and exposes `lookup(path:)` / `record(path:name:)` / `save()`. `AppStateStore` now holds a `nameCache` (injectable for tests):

- `addSession` consults the cache using the inherited CWD before defaulting to `"Session N"`. An explicit `title` argument still wins; only the default path goes through the cache.
- `renameSession` writes back to the cache after applying the new title, skipping default `Session N` titles via a `^Session \d+$` regex match and skipping empty CWDs. The path is sourced from `session.tree.root.firstLeafPane.tabs[0].terminal.workingDirectory` with a fallback to `configuration.workingDirectory`.
- Writes are debounced 250ms to absorb rapid renames; `WorkspaceManager.applicationWillTerminate` flushes via `nameCache.save()`. Atomic write uses temp file + `FileManager.replaceItemAt`. Cap is enforced at 100 entries with LRU eviction by `lastUsedAt`. Corrupt or missing files recover to empty silently and the next write replaces them.

Schema: `{ "version": 1, "entries": [{ "path", "name", "lastUsedAt" }] }`.

## Files changed

- `BattyKit/Sources/BattyKit/SessionNameCache.swift` — new file. The cache type plus `SessionNameCacheEntry` / `SessionNameCacheFile` Codable schema and JSON encoder/decoder.
- `BattyKit/Sources/BattyKit/AppStateStore.swift` — adds `nameCache: SessionNameCache`, wires `addSession`'s cache lookup before default title, and the rename-time write with default-name skip.
- `BattyKit/Sources/BattyKit/WorkspaceManager.swift` — flushes `store.nameCache.save()` on `applicationWillTerminate` alongside the existing workspace save.
- `BattyKit/Tests/BattyKitTests/SessionNameCacheTests.swift` — new file. 17 tests covering round-trip, LRU eviction (at and past 100), hit/miss/empty lookup, corrupt-file recovery, rename-on-default-name, default-title detection, explicit-title override behavior.
- `Concepts.md` — adds a "Name cache" bullet under the Session entry describing the cache, location, write/lookup rules, and cap.

## Gotchas

- The lookup happens *before* the default `"Session \(sessions.count + 1)"` is composed, but only when the caller didn't pass an explicit `title`. Explicit titles always win — that's needed so `duplicateSession`'s `"<title> Copy"` and other internal callers don't accidentally pick up a cached name.
- Path matching is exact — no `~` collapse, no symlink resolution. macOS shells emit canonical paths via OSC 7, so this works in practice; revisit if it becomes a real issue.
- `nameCache.lookup` bumps `lastUsedAt` on a hit, so simply *reading* from the cache during `addSession` keeps frequently-used entries alive against the 100-cap. Tests that want to verify behavior without affecting recency should `snapshot()` rather than `lookup()`.
- The write path is debounced 250ms, but tests pass `debounce: .zero` to keep them deterministic. Production code relies on `applicationWillTerminate` to flush pending writes via the explicit `save()` call.

## Phase 2 fix — `e658e6b` — apply cached name on anchor tab CWD change

User reported 2026-05-11 that Phase 1 only worked at session creation. `cd`-ing into a known directory after the session existed didn't rename anything. The cache was being consulted only in `addSession`, with no observation of running CWD changes.

### What changed

- `AppStateStore.handleWorkingDirectoryChange(forTabID:)` — new method. Finds the session that owns the changed tab, returns early if the tab isn't the session's anchor (first leaf pane's first tab — same anchor used by `renameSession`'s write rule), reads the new CWD (live `terminal.workingDirectory` with a `configuration.workingDirectory` fallback to mirror the existing pattern), and if the cache has a hit, sets `session.title = cachedName`. Returns early when the title is already the cached value to avoid no-op `@Observable` writes triggering downstream renders.
- `PaneView` adds `.onChange(of: tab.terminal.workingDirectory)` alongside the existing bell-tick and desktop-notification observers, routed to `appStore?.handleWorkingDirectoryChange(forTabID: tab.id)`.
- `BattyKit/Tests/BattyKitTests/AppStateStoreCWDChangeTests.swift` — 6 new tests covering: anchor-tab cd with cache hit renames the session, anchor-tab cd with no hit leaves the title alone, non-anchor-tab cd is ignored (matches the write rule's anchor), idempotent re-fire is a no-op, empty/nil CWD is a no-op, and a "rename then cd-back" scenario where the user renamed the session, manually retitled to "Misc," and `cd`-ing back into the anchored directory restores the cached name.

### Why the anchor-only rule

Both the write side (`renameSession`) and the read side (this Phase 2) key on the **first leaf pane's first tab's CWD**. Matching anchors keeps the cache predictable: the entry the user is writing when they rename, and the entry that triggers an auto-apply, refer to the same thing. The alternative — auto-applying on *any* tab's CWD change — would have the session title flicker when the user `cd`s in a non-anchor tab to an unrelated directory that happens to be in the cache.

### Verification

- `xcodebuild -scheme Batty -destination 'platform=macOS' build` ✅
- `swift test --package-path BattyKit` — 128 tests in 18 suites ✅ (6 new in `AppStateStoreCWDChangeTests`)
- Visual: in the default session, `cd ~/Developer/Batty` (after having previously renamed a session to "Batty" in that directory). The session should rename to "Batty" without quit/relaunch. **Pending user confirmation.** Resolved-not-closed.

### Gotchas (Phase 2)

- **Auto-apply does not auto-revert.** If the user `cd`s away from a cached directory, the title stays at whatever was last applied (cached or user-set). v1 keeps it simple; if reversion is desired later it'd need a separate "is this title cache-derived or user-set" flag on the session.
- **No throttling.** A loop running `cd a; cd b; cd a; cd b` would fire `handleWorkingDirectoryChange` on every `cd`. The lookup is O(n) over cache entries (n ≤ 100) plus a session walk, both cheap. If this becomes a hotspot it'd need a debounce, but in practice OSC 7 emissions are rate-limited by terminal output.
- **No SwiftUI test for the `.onChange` wiring.** The handler is tested in isolation; the wiring relies on PaneView's existing pattern (bell/notification observers use the same shape and have worked in production). If the wiring ever regresses, the first user signal will be "I cd into Batty and the session doesn't rename" — which is what just happened, so we'll catch it again.
