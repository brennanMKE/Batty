## Description

#0315 established the invariant that tab-mutating actions must not act on a non-terminal pane — such a pane holds one structural, never-rendered `TabRuntime` that no view displays (`PaneRuntime.kind`'s scope note). It took three review rounds to enforce, because the invariant lives in call-site discipline: three separately hand-copied dispatch switches over `ShortcutAction` (`BattyCommands`, `BattyShortcuts`, and `CommandPaletteView.dispatch` — the last missed twice) each needed the same guard. The final fix centralized it — `SessionRuntime.focusedTerminalPane` returns the focused pane only when `kind == .terminal`, and the shared choke points `WindowRuntime.closeFocusedTab()` / `.requestCloseFocusedTab()` and `ExitDispatcher.focusedTerminalTab` gate internally.

But `SessionRuntime.focusedPane` is still public, still non-optional, and still the natural thing to reach for. Nothing in the model, the compiler, or the test suite stops the next consumer from doing exactly what the last three did. Three ungated focused-pane consumers already exist (verified below); a fourth will be written eventually, and if three review rounds caught three, it is not safe to assume review catches the fourth.

**The real ask of this issue is not "gate these three."** It is: what would make the invariant *structural* rather than *remembered*? Candidate shapes, deliberately not decided here:

- Make the ungated accessor unavailable or unattractive — e.g. rename `focusedPane` to something that reads as a deliberate act (`focusedPaneAnyKind`), or narrow its access so kind-agnostic uses (focus tracking, tree layout) keep working while tab-reaching uses (`focusedPane.activeTab`, `focusedPane.addTab`) go through `focusedTerminalPane`.
- Remove or gate the ungated public sibling `SessionRuntime.closeFocusedTab()` (zero callers today — see below).
- A test that enumerates `focusedPane` consumers (grep-shaped or otherwise) and fails when a new one appears outside an allowlist.
- Align `PasteDispatcher` with `ExitDispatcher` so the "mirrors exactly" comment becomes true again, and assert the mirror with a shared helper or a test rather than a comment.
- Something else entirely.

Pick during implementation, with the trade-offs written down.

## The three ungated consumers (each verified against source, 2026-08-09)

**1. `PasteDispatcher` no longer mirrors `ExitDispatcher`, and the comment claiming it does is false.** `ExitDispatcher`'s doc comment (`BattyKit/Sources/BattyKit/Commands/ExitDispatcher.swift:21-23`) says its resolution "mirrors `PasteDispatcher`'s target resolution exactly so both writes agree on what 'focused Terminal Session' means." #0315 rewrote `ExitDispatcher.focusedTerminalTab` (`:41`) to route through `focusedTerminalPane` — and edited that very comment — but `PasteDispatcher.focusedTerminalTab` (`BattyKit/Sources/BattyKit/Views/PasteConfirmation.swift:104-110`) still resolves through plain `focusedPane.activeTab`. The two no longer agree.

   Behavioral consequence (traced through the branch source): with a non-terminal pane focused, `handlePasteRequest` (`PasteConfirmation.swift:74-97`) resolves a **non-nil** placeholder tab (a non-terminal pane still holds one structural `TabRuntime`), so the `forwardStandardPaste()` fallback at `:76` is skipped. If paste strictness triggers, it posts `.battyRequestPaste` and `SessionDetailView` (`BattyKit/Sources/BattyKit/Views/SessionDetailView.swift:57`) presents the confirmation sheet; confirming — or pasting a short text directly — calls `tab.terminal.send(text)`, which no-ops because the placeholder tab never acquires a surface (`TerminalViewState.send` guards on nil `surface` and returns `false`; libghostty-spm checkout, `Sources/GhosttyTerminal/State/TerminalViewState.swift:41-47`). Net: Cmd-V with a non-terminal pane focused silently does nothing, possibly after showing a paste-confirmation sheet for a paste that cannot land, instead of falling back to the standard responder-chain paste. Not a tab mutation — but a real divergence hiding behind a comment that asserts the opposite.

**2. `SessionRuntime.closeFocusedTab()` is an ungated public sibling of the gated `WindowRuntime.closeFocusedTab()`, with zero callers.** On the branch it sits at `BattyKit/Sources/BattyKit/Runtime/SessionRuntime.swift:71-78` (on `main`, `:54`), directly below the `focusedTerminalPane` accessor whose doc comment declares the very invariant it ignores: it reads plain `focusedPane` and closes tabs / removes panes with no kind check. Verified zero call sites: every `closeFocusedTab` reference in code (product and tests) resolves to `AppStateStore.closeFocusedTab()` or `WindowRuntime.closeFocusedTab()` — receivers are `store.`, `window.`, or `store.windows[0].`; nothing calls it on a `SessionRuntime`. This is pre-existing on `main`, not introduced by #0315 — #0046's own Gotchas (`issues/0046.md:79`) already flagged it as "unused by product code… consider removing in a cleanup pass if no one adopts it". Nobody adopted it; #0315 made it dangerous instead of merely dead.

**3. `UITestDriver.createTab` adds a tab through plain `focusedPane`, ungated.** `BattyKit/Sources/BattyKit/Testing/UITestDriver.swift:78-83` (branch; `main:78` identical): resolves `store.selectedSession?.focusedPane` and calls `pane.addTab(inheritingCWDFrom:)`. `UITestDriver` is compiled into **every** build including release — deliberately no `#if DEBUG`, because UI tests run against the Beta build (its own doc comment, `:13-14`) and Prod/Beta share one target — but is runtime-gated on the `BATTY_UI_TEST_SCRIPT` env var, so production launches never enter it. The #0315 reviewer judged this acceptable because no driver intent creates a non-terminal pane (verified: no kind-typed intent exists in the file) — but that half of the justification expires the moment a driver intent can, or a UI-test script runs alongside the #0315 CLI verbs that do. Note the driver's `closeActiveTab` (`:86`) is already safe — it routes through `store.closeFocusedTab()` into the gated `WindowRuntime` choke point. Adjacent observation, same class but benign today: `renameActiveTab` / `resetActiveTabTitle` (`:90-104`) write `titleOverride` on whatever `focusedPane.activeTab` yields, including a placeholder tab — cosmetic, no structural mutation.

## What #0315 already covers (out of scope here)

#0315 added tests for the three paths it gated — `RequestCloseTabTests.closeFocusedTabDoesNotRemoveANonTerminalPanesStructuralTab` (`BattyKit/Tests/BattyKitTests/RequestCloseTabTests.swift:49`), `CommandPaletteViewActionTests`, and `ExitDispatcherTests` (which exercises the production `focusedTerminalTab` resolution directly). Those paths are done. This issue is about the paths it did *not* gate, and about making the next ungated consumer impossible — or at least loud — rather than a fourth review finding.

## Mechanism chosen (implementation, #0332)

Before touching any consumer, every `file:line` citation above was re-verified against `main` (the branch-context premise was indeed stale — #0315 has merged; see the Root-cause-equivalent note in the implementer's report). All three instances still held true, at slightly moved line numbers, plus the `closeFocusedTab()` line number moved (`SessionRuntime.swift:100-107` on current `main`, not `:71-78`).

**Chosen: rename `SessionRuntime.focusedPane` → `focusedPaneAnyKind`, and remove the dead `SessionRuntime.closeFocusedTab()` outright.**

- `focusedPaneAnyKind` is a compiler-enforced rename, not a test or a comment: the plain name `focusedPane` no longer exists on `SessionRuntime`, so every existing call site (production and test, ~30 across the tree) had to be individually re-typed to either `focusedPaneAnyKind` (kind-agnostic reads: focus tracking, tree-split "which pane to inherit cwd from," bell-seen bookkeeping) or `focusedTerminalPane`/the new `AppStateStore.focusedTerminalTab` (tab-reaching uses). A future engineer who types `session.focusedPane` gets `error: value of type 'SessionRuntime' has no member 'focusedPane'` at compile time, not silent access to the ungated accessor — they are forced to choose consciously between the "any kind" and "terminal only" spellings, and the "any kind" spelling reads as an opt-out rather than the path of least resistance.
- `SessionRuntime.closeFocusedTab()` (ungated public sibling of the gated `WindowRuntime.closeFocusedTab()`) had zero callers, re-verified on this branch by grepping every `closeFocusedTab` reference in product and test code — every receiver resolves to `AppStateStore.closeFocusedTab()` or `WindowRuntime.closeFocusedTab()`. Removing it (rather than gating it) means there is no dangerous method left to accidentally call — the strongest of the "gate or remove" options the issue offered, and free because nothing used it.
- **`AppStateStore.focusedTerminalTab`** is a new canonical, single-implementation resolver both `ExitDispatcher.focusedTerminalTab(in:)` and `PasteDispatcher`'s private helper now delegate to, instead of each hand-copying `store.keyWindowOrFirstRegistered()?.selectedSession?.focusedTerminalPane?.activeTab`. This is what makes `ExitDispatcher`'s doc comment ("mirrors `PasteDispatcher`'s target resolution exactly") true by construction rather than by two authors remembering to keep two copies in sync — which is exactly how they drifted the first time.

**Alternatives considered and rejected:**

- *Narrow `focusedPane`'s access level* (e.g. `internal` instead of `public`) — rejected because `SessionRuntime` and its consumers already span module-internal call sites that legitimately need the kind-agnostic pane (tree layout, bell bookkeeping in `WindowRuntime`), so narrowing access wouldn't separate "safe" from "unsafe" callers — it would just move the dangerous default from "public and ungated" to "internal and still ungated," with no compiler signal distinguishing a tab-reaching use from a kind-agnostic one. The rename does what narrowing access was trying to do, more precisely.
- *A test enumerating `focusedPane` consumers with an allowlist* — rejected as the primary mechanism per the issue's own stated preference ("prefer a mechanism the compiler enforces... a test over a comment"): a grep-shaped test only fires in CI/pre-commit, after the ungated code is already written and possibly shipped in a local build; a compile error fires the moment the code is typed, in every environment including Xcode's live diagnostics. It's also strictly weaker than the rename here (the rename makes the exact defect this test would allowlist-check for impossible to *write*, not just impossible to *land*). Not added as a supplementary layer either, to avoid a second enforcement mechanism nobody maintains once the rename makes it redundant — a stale, always-passing allowlist test is worse than no test (explicitly flagged as a risk in the assignment).
- *Leave `focusedPane` named as-is and just fix the three consumers* — this is exactly the "gate these three" framing the issue said not to settle for; it would leave a fourth ungated consumer exactly as easy to write as the first three were.

## Mechanism, round 2 — the rename alone was disproven; the gate moved to the mutation

Round 1's reviewer compiled a probe against `SplitTree.focusedPane` (`BattyKit/Sources/BattyKit/Model/SplitTree.swift:127-129`) — the 16-call-site production idiom the `SessionRuntime.focusedPane` rename never touched, since it lives on a different type:

```swift
let pane = session.tree.focusedPane
pane.addTab(inheritingCWDFrom: pane.activeTab)   // the exact #0315 defect
pane.closeActiveTab()
```

This compiled cleanly and reproduced the exact #0315 defect. The rename made *one* spelling read as an opt-out; it did nothing about the spelling every real Tab-scoped dispatch path already had four lines of context reaching for (`BattyCommands.swift:239,282,324,333`, `BattyShortcuts.swift:135,139,143,147`, `CommandPaletteView.swift:226,230,234,238`, `SessionDetailView.swift:135,137,149,151`).

**Fix: push the kind gate down to the mutation itself, not the lookup.** `PaneRuntime.addTab(inheritingCWDFrom:)` and `PaneRuntime.closeActiveTab()` (`BattyKit/Sources/BattyKit/Runtime/PaneRuntime.swift`) now guard on `kind == .terminal` internally — a non-terminal pane's placeholder Tab is untouched, and the call logs (`logger.error`, not `assertionFailure`: this guards a call-site bug in shared UI dispatch code, and a crash there is worse than a no-op — see `docs/swiftui-observation-rules.md`'s AppKit-interop cautions about the same call paths) and returns/no-ops rather than corrupting the pane. This holds **regardless of which accessor got the caller to the pane** — `focusedPaneAnyKind`, `SplitTree.focusedPane` directly, `WindowRuntime.locate(tabID:)`, a future accessor not yet written. Verified against the reviewer's own probe: `PaneRuntimeKindGateTests.theRound1ReviewersExactProbeIsANoOpOnANonTerminalPane` runs it verbatim and asserts the tab count is unchanged; reverting the gate turns that test red (confirmed by hand during implementation).

The rename (`focusedPane` → `focusedPaneAnyKind`) on `SessionRuntime` is **kept as a second, non-load-bearing layer** — it still gives a future engineer typing `session.focusedPane` a compile error and a conscious choice, which is valuable for the accessors it actually reaches. It is not renamed further (`SplitTree.focusedPane` was left alone, per the reviewer's "optional" framing) because the mutation-point gate makes the accessor spelling irrelevant to correctness; a second rename would be defense-in-depth with no defect it closes that the mutation gate doesn't already close.

**A fourth ungated consumer was found and closed in this round**, independent of any accessor: `AppStateStore.focusedTabIDFallback()` (the XPC `notify` verb's no-`--tab` resolution) reached a non-terminal pane's `activeTabID` through `session.tree.allPanes`, never through `focusedPane`/`focusedPaneAnyKind`/`focusedTerminalPane` at all — the rename, by construction, could not have seen it. It is now gated (`pane.kind == .terminal`, else `nil`) at the same read site, with a test (`focusedTabIDFallbackIsNilWhenTheFocusedPaneIsNotTerminal`) confirmed to fail under reversion.

**Residual gap, not closed by this round (`issue/0381`, not yet merged):** `AppStateStore.focusTabForXPC(id:)` resolves via `WindowRuntime.locate(tabID:)` (no kind gate) and writes `location.pane.activeTabID = tabID`. For a non-terminal pane this write is a same-value no-op today (the pane's `tabs` array holds only the placeholder `locate` found the id through), so it does not corrupt the model — but the verb still reports `.focused` for a phantom tab id an agent could read off `batty list`'s `TopologyPanePayload.activeTabID` (#0315's still-open residual gap). Neither of this round's two mechanisms — the `PaneRuntime` mutation gate (wrong shape: `activeTabID` assignment isn't `addTab`/`closeActiveTab`) nor a `focusedPane` rename (wrong axis: `locate(tabID:)` never goes through a focused-pane accessor) — closes this. Left for `#0381`'s own implementer, flagged in that issue's context via this round's report; `WindowRuntime.locate(tabID:)` gaining a kind-aware variant, or `focusTabForXPC` checking `location.pane.kind` before reporting success, are the two shapes that would.

## Gotchas

- **Cmd-V / paste responder chain is untested end-to-end.** `PasteConfirmationNonTerminalPaneTests` and the `forwardStandardPaste` seam test (N2) exercise `PasteDispatcher.handlePasteRequest` directly against a model-only `AppStateStore` — neither drives an actual Cmd-V keystroke through a live `NSApp`/responder chain with a real focused `AppTerminalView`. Whether the injected `forwardStandardPaste` closure genuinely stands in for `NSApp.sendAction(#selector(NSText.paste(_:)), to: nil, from: nil)` reaching the right responder in a running app is unverified; needs a live app (ideally a UI test) to close out.
- **`UITestDriverTests` covers `dispatch(_:store:)` directly, not the end-to-end env-var path.** `UITestDriver.runIfNeeded(store:)` reads `BATTY_UI_TEST_SCRIPT`, JSON-decodes it, and dispatches — none of that decode/env-var plumbing is exercised by the new tests, which call `dispatch` directly (the same shortcut `ExitDispatcherTests` takes). A real UI test driving a `.createTab` intent against a `--view git-status` pane, end to end through the env var, was not run (this implementer cannot run UI tests per this round's constraints) and is still owed.
- **B4's stale-retry scenario is reasoned, not reproduced.** The revert restores the pre-#0332 unconditional `TerminalSurfaceFocuser.focusWhenReady` call in `SessionDetailView.focusSelectedSessionTerminal()`. The bug the *round-1* gate risked reintroducing — a live 800 ms retry ladder from a previously-focused tab firing after focus moved to a non-terminal pane, dragging the model back through the `isFocused` echo (#0229/#0230's class) — requires a live app with real timing (session switch mid-retry-ladder, focus landing on a non-terminal pane) to actually trigger or rule out. Not reproducible in `BattyKitTests`' synchronous, no-AppKit-window environment.
- **B2's `batty notify` scenario is unit-tested at the model layer only.** `focusedTabIDFallbackIsNilWhenTheFocusedPaneIsNotTerminal` proves `AppStateStore.focusedTabIDFallback()` returns `nil` for a non-terminal focused pane, and by extension that `AppXPCService`'s notify handler takes its existing "no tab to target" failure branch — but no test drives an actual `batty notify` CLI invocation over a real XPC connection against a running app with a Git Status pane focused. That full round-trip (`batty pane split --view git-status` → focus it → `batty notify --title x` with no `--tab`) needs a live app to confirm the failure reply is what an agent actually sees.

## Gotchas

Recorded at review approval; none block the fix, all are follow-on work.

- **`PaneRuntime.removeTab(id:)` is the one ungated one-line route** to a
  zero-tab non-terminal Pane — the exact outcome `closeActiveTab()`'s guard
  prevents, via the method `closeActiveTab` delegates to. It cannot simply be
  gated: `WindowRuntime.closeTab(id:)` calls it on any Pane kind and then
  dissolves the emptied Pane, which is correct behavior. Anyone adding a
  tab-close path must route through `WindowRuntime.closeFocusedTab()` or
  `requestCloseTab(id:)`, never `removeTab` directly.
- **`addTab`'s `return activeTab ?? tabs[0]` fallback can only ever trap.**
  `activeTab` is nil iff `tabs` is empty, so `tabs[0]` is reachable only when it
  is guaranteed to be out of range — it reads like a considered fallback and is
  not one. Unreachable in production today. Worth a `precondition` with a real
  message, or a comment stating it is provably unreachable.
- **B3 has no test coverage.** Reverting both rerouted call sites
  (`WindowRuntime.addSession`'s cwd inheritance and `markActiveTabSeen`) leaves
  the whole suite green. The "a non-terminal placeholder tab never carries a
  working directory" premise holds today only because `SplitTree.makePane`
  passes no `tabs:` argument; `PaneRuntime(tabs: [TabRuntime(workingDirectory:
  "/tmp")], kind: .gitStatus)` does carry one. The day any non-terminal Pane
  wants its own directory — plausible for `.gitStatus`, whose conformer already
  resolves a `directoryPath` — the two spellings diverge silently. Suggested
  pin: split a terminal Pane at a known cwd into a `.gitStatus` Pane, focus it,
  call `window.addSession()`, assert the new Session's first Tab inherits no
  cwd. That also pins the quiet product decision this refactor made — Cmd-N with
  a non-terminal Pane focused is now hard-guaranteed not to inherit its cwd.
- **`docs/pane-kinds.md:844`** says "there is no plain `focusedPane` left to
  reach for by accident." Read strictly the parenthetical scopes that to
  `SessionRuntime`, but believing it globally is precisely the round-1 error, and
  it now sits in the canonical pane-kinds doc. `SplitTree.focusedPane` is
  deliberately unchanged; the gate that makes that safe lives on `PaneRuntime`'s
  mutations.
- **`UITestDriver`'s `.createTab` kind guard is now dead weight** — removing it
  alone leaves the suite green, because the `PaneRuntime` gate catches the same
  behavior. Harmless, in-style, and it produces a better log line than the deep
  gate, so it stays; nobody should read it as load-bearing.

Not verifiable without a live app: the Cmd-V responder chain end to end; the
`BATTY_UI_TEST_SCRIPT` env-var decode path; the stale-retry-ladder scenario
behind the B4 revert (needs real 800 ms timing with a Session switch mid-ladder);
and a real `batty notify` round trip over XPC with a Git Status Pane focused.
