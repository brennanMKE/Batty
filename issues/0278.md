# 0278 — Outgoing XPC connections never validate the peer's code signature, so app and CLI trust whatever owns the broker's Mach service name

| | |
|---|---|
| **Status** | open |
| **Module** | App / Build |
| **Platform** | macOS |
| **First seen** | 2026-07-25 |

## Description

#0273 wires peer code-signing validation into the **listener** side only: the broker's `NSXPCListener(machServiceName:)` (`BattyKit/Sources/BattyBroker/main.swift`) and the app's anonymous listener (`AppXPCCoordinator.start()`) both call `setConnectionCodeSigningRequirement(_:)`, so *incoming* connections must come from a binary signed with the same team identity. The **outgoing** side has no counterpart: no `NSXPCConnection` in the codebase calls `NSXPCConnection.setCodeSigningRequirement(_:)`. Verified on branch `issue/0273` — `git grep setCodeSigningRequirement` matches only the two listener sites and their comments/tests; the connection-side API appears nowhere.

The consequence: a process that managed to own the `ServiceNames.broker` Mach service name could impersonate the broker to both the app and the CLI. The app would hand its listener endpoint (`registerAppEndpoint`) to an impostor; the CLI would accept an attacker-supplied endpoint from step 2 of the connect dance and connect `batty status` to whatever it points at.

This was found during #0273's review and is scoped out by #0273's own wording ("the broker and app only accept connections *from* binaries signed with the same team identity") — a genuine follow-up, not an omission in that child.

**Threat model, stated plainly so nobody treats this as an emergency:** owning a launchd Mach service name in the user's GUI domain requires registering a launchd job that claims it — i.e. the ability to install a LaunchAgent, which is already substantial local access. An attacker with that much foothold has easier targets than Batty's status verb. This is **defense-in-depth** — completing the symmetric half of a validation story #0273 started — not a live exploit or a critical hole. It is worth fixing; it is not urgent.

## The outgoing connection sites that need the requirement

All four construction sites, verified on `issue/0273`:

1. **App → broker** — `BattyKit/Sources/BattyKit/XPC/AppXPCCoordinator.swift`, `connectToBroker(endpoint:)` (line 114): `NSXPCConnection(machServiceName: ServiceNames.broker)`. This is the connection over which the app hands out its anonymous-listener endpoint.
2. **CLI → broker (ping)** — `BattyKit/Sources/batty/BrokerPingClient.swift`, `ping(timeout:)` (line 23): `NSXPCConnection(machServiceName: ServiceNames.broker)`.
3. **CLI → broker (endpoint fetch)** — `BattyKit/Sources/batty/BrokerAppEndpointClient.swift`, `fetchEndpoint(timeout:)` (line 24): `NSXPCConnection(machServiceName: ServiceNames.broker)`.
4. **CLI → app (post-handoff)** — `BattyKit/Sources/batty/AppServiceClient.swift`, `status(endpoint:timeout:)` (line 32): `NSXPCConnection(listenerEndpoint: endpoint)`. Validating here closes the "attacker-supplied endpoint" half even if the broker connection was already validated — the endpoint is data the broker handed back, not something launchd vouches for.

(`AppXPCConnectionRegistryTests` also constructs an `NSXPCConnection`, but against a local anonymous listener in a unit test — out of scope.)

## Expected behavior

Each outgoing connection applies the same requirement the listeners already do, via the existing `BattyXPCCore` helpers — no new machinery:

- `OwnCodeSigningIdentity.currentTeamIdentifier()` reads the running binary's own Team Identifier from its signature.
- `PeerCodeSigningRequirement.requirement(forTeamIdentifier:)` builds the requirement string (`anchor apple generic and certificate leaf[subject.OU] = "<team>"`), returning `nil` for a nil/empty team.
- When the helper returns a requirement, call `connection.setCodeSigningRequirement(_:)` before `resume()`. When it returns `nil`, set nothing — same pattern as the two listener sites, ideally factored so the four call sites don't repeat the if/else + logging by hand.

**Binding design constraint, carried over from #0273:** a `nil` team identifier — an ad-hoc or unsigned local build (`CODE_SIGNING_ALLOWED=NO` iteration) — must **skip enforcement entirely**, exactly as the listener sites do. `PeerCodeSigningRequirement`'s doc comment calls this "the documented, deliberate development escape hatch, not an oversight." Do not harden it into a fail-closed check; that breaks every local dev connection.

## Notes

- **The two directions are independently enforceable, and that asymmetry deserves a moment's thought rather than a reflexive "make it symmetric."** The CLI validating the broker is meaningful (it's what stops the impostor-broker scenario). But the CLI *itself* may be ad-hoc signed in a dev build (`swift build` output before `scripts/release.sh` re-signs it), in which case its own `currentTeamIdentifier()` is `nil` and it enforces nothing — while the properly signed app and broker still validate each other and still reject the ad-hoc CLI on the listener side. That per-process self-derivation is the design working as intended, not a bug; the implementer should confirm the dev matrix (signed app + ad-hoc CLI, and vice versa) degrades the way the escape hatch intends rather than wedging. Raised here; the resolution should record the reasoning, whichever way it lands.
- **`NSXPCConnection.setCodeSigningRequirement(_:)`** is the connection-side sibling of the listener API #0273 used (macOS 13+; Batty targets 15.6+). Not yet exercised in this codebase — the exact call-site ergonomics (it can throw/reject an invalid requirement string, per the listener API's behavior) should be confirmed against the SDK during implementation, not assumed from this ticket.
- **Interaction with #0277 (Beta suffixed broker identity):** per-variant service names change *which Mach service* each side connects to, and both variants sign with the same team, so a team-identity requirement should hold across variants as-is. But whoever implements #0277 and this issue second should re-check that assumption — mention only; the two shouldn't be coupled.
- Requirement-string failures on outgoing connections surface as connection invalidation, which every one of the four sites already maps to an "unreachable" outcome — so a rejected impostor should degrade into the existing exit-code vocabulary (`2`/`3`) without new error paths. Worth confirming, not assuming.

## Verification expectations

Following #0273's pattern:

- **Unit tests:** requirement construction is already covered by `BattyKitTests/PeerCodeSigningRequirementTests` (nil/empty → nil, team → string, distinct teams → distinct strings) — nothing new to test there. If the fix factors the "derive identity → maybe set requirement on a connection" step into a shared helper, any pure part of that helper (e.g. the decision of whether to enforce) is unit-testable; the `setCodeSigningRequirement` call itself is not, without a live peer. Say plainly in the resolution what was and wasn't unit-testable. `scripts/build.sh unit` stays green.
- **The decisive check is runtime and needs a real signed build**, in *both* directions: the genuine signed broker is accepted by the signed app and CLI, and a differently-signed (or ad-hoc) stand-in occupying the service name is refused by both. This shares the **same blocked verification as #0273**: this machine has only an `Apple Development` certificate and no `Developer ID Application` certificate, and neither notarization nor a live foreign-team impostor test can run without the user's involvement. Mark honestly in the resolution which runtime checks were performed, by whom, and which remain outstanding — same discipline #0273's Verification expectations demand.
