# 0537 — The release build number is the UTC date, so two releases on the same UTC day get the same build number

| | |
|---|---|
| **Status** | open |
| **Module** | Build |
| **Platform** | macOS |
| **First seen** | 2026-10-27 |

## Description

`scripts/release.sh` sets the release build number (`CFBundleVersion`, which Sparkle compares as `sparkle:version`) to the UTC date in `YYYYMMDD` form. Any two releases built on the same UTC date get the same build number, and Sparkle does not offer the second one to users of the first. The UTC date also differs from the Pacific date the user sees: anything released after 17:00 PDT gets the next day's number.

This has now blocked a release. 1.3.3 was tagged at 2026-10-26 20:11 PDT, which was 2026-10-27 in UTC, so its build number is `20261027`. The 1.3.4 release, built on 2026-10-27 PDT from `release/1.3`, also got `20261027`. Sparkle would not have offered 1.3.4 to 1.3.3 users, so that DMG was not published.

User request, 2026-10-27, verbatim:

> Can we add the hour and minute to the build number so we can do more than 1 release per day?

**Decision (user, 2026-10-27):**

- The build number becomes UTC `YYYYMMDDHHMM`, for example `202610272315`. It is still one integer. Every 12-digit value is greater than every earlier 8-digit build, so Sparkle's ordering stays monotonic across the format change.
- The preflight's same-day check becomes a failure when the new build number is not strictly greater than the newest `sparkle:version` in `website/appcast.xml`. Its message must be accurate (today it points at an override that does not exist).
- `scripts/RELEASE.md` is updated to match.
- `scripts/` is a restricted area. The user explicitly asked for this change.
- Target: the 1.3.4 release. Fix on `main` through the normal issue workflow, then `git cherry-pick -x` onto `release/1.3`. `git diff main release/1.3 -- scripts/` is empty as of filing, so the cherry-pick applies cleanly.

## Steps to reproduce

1. Release a version with `scripts/release.sh` (for example 1.3.3, archived 2026-10-27 UTC).
2. Bump `MARKETING_VERSION` and run `scripts/release.sh` again on the same UTC date.
3. Compare the new DMG's `CFBundleVersion` with the newest `sparkle:version` in `website/appcast.xml`.

## Expected

Each release gets a build number strictly greater than every earlier release, however many releases happen in one day. The preflight refuses to proceed when that would not hold.

## Actual

Both releases get the same `YYYYMMDD` build number. Sparkle treats the second as "no update available". `scripts/preflight.sh` only warns about it.

## Notes

Facts checked against the code on `main` at filing:

- `scripts/release.sh:117` — `BUILD_NUMBER="$(date -u +%Y%m%d)"`. There is no environment or flag override.
- `scripts/release.sh:151` — passes it to `xcodebuild` as `CURRENT_PROJECT_VERSION="$BUILD_NUMBER"`. `Configuration/Info.plist:20` reads `$(CURRENT_PROJECT_VERSION)` into `CFBundleVersion`. `Configuration/App.xcconfig:50` keeps a static `1` for Debug builds only.
- `scripts/release.sh:330-332` — checks that the archived `CFBundleVersion` equals `$BUILD_NUMBER`. This check does not depend on the format.
- `scripts/release.sh:385-386` (dSYM zip and UUID file names), `:413` and `:543` (printed summary), `:433` (local `.xcarchive` name) — use `$BUILD_NUMBER` in file names and output. A 12-digit value works in all of them. `:432` names the archive folder from `date -u +%Y-%m-%d`, separately.
- `scripts/preflight.sh:543-564` — the build-number collision gate. `:549` computes `TODAY_BUILD="$(date -u +%Y%m%d)"` and `:552-553` takes the highest `sparkle:version` in the appcast. When they are equal, `:558-559` only calls `warn`, with a message telling the user to "override release.sh BUILD_NUMBER", which `release.sh` has no way to do. With the new format, the preflight should compute the candidate the same way `release.sh` does and `fail` unless it is strictly greater. The preflight and `release.sh` run at different times, so the candidate is only an estimate. `release.sh` could also check its actual `$BUILD_NUMBER` against the appcast before archiving. The plan should decide that.
- `scripts/preflight.sh:646` and `:675` — compare the DMG's `CFBundleVersion` with the appcast's `sparkle:version`. These do not depend on the format.
- `scripts/appcast-item.sh:119` — writes `sparkle:version` from the DMG's own `CFBundleVersion`, so it picks up the new format with no change. The comment at `:10` mentions the old value `20260521` as history only.
- `scripts/RELEASE.md:73-80` — documents "today's UTC date in `YYYYMMDD` form (e.g. `20260514`)". Needs updating. `scripts/SPARKLE.md:78` mentions `20260521` as history only.
- `website/appcast.xml:40` — 1.3.3 has `sparkle:version="20261027"`. Older items have `20261019` and `20261018`.
- `git for-each-ref refs/tags/v1.3.3` — tagger date `2026-10-26 20:11:47 -0700`. `a2b61d6e` ("Bump version to 1.3.4", on `release/1.3` only) was committed at `2026-10-27 15:01:38 -0700`, which is still 2026-10-27 in UTC.
- No unit test, `tools/` script, `build.sh` path or app code parses the release build number. Other `%Y%m%d` uses (`scripts/screenshot-batty.sh:57`, `tools/run-ui-tests-vm.sh:152`, `.claude/skills/batty-cli/install.sh:149`) are unrelated timestamps.
- A 12-digit value fits zsh's 64-bit integer comparison (`-lt`/`-eq` in preflight) and is a valid `CFBundleVersion` for a Developer ID app outside the App Store.
