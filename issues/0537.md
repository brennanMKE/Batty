## Description

`scripts/release.sh` sets the release build number (`CFBundleVersion`, which Sparkle compares as `sparkle:version`) to the UTC date in `YYYYMMDD` form. Any two releases built on the same UTC date get the same build number, and Sparkle does not offer the second one to users of the first. The UTC date also differs from the Pacific date the user sees: anything released after 17:00 PDT gets the next day's number.

This has now blocked a release. 1.3.3 was tagged at 2026-10-26 20:11 PDT, which was 2026-10-27 in UTC, so its build number is `20261027`. The 1.3.4 release, built on 2026-10-27 PDT from `release/1.3`, also got `20261027`. Sparkle would not have offered 1.3.4 to 1.3.3 users, so that DMG was not published.

User request, 2026-10-27, verbatim:

> Can we add the hour and minute to the build number so we can do more than 1 release per day?

**Decision (user, 2026-10-27):**

- The build number becomes UTC `YYYYMMDDHHMM`, for example `202610272315`. It is still one integer. Every 12-digit value is greater than every earlier 8-digit build, so Sparkle's ordering stays monotonic across the format change.
- The preflight's same-day check becomes a failure when the new build number is not strictly greater than the newest `sparkle:version` in `website/appcast.xml`. Its message must be accurate (today it points at an override that does not exist).
- `scripts/RELEASE.md` is updated to match.
- `scripts/` is a restricted area. The user explicitly asked for this change.
- Target: the 1.3.4 release. Fix on `main` through the normal issue workflow, then `git cherry-pick -x` onto `release/1.3`. `git diff main release/1.3 -- scripts/` is empty as of filing, so the cherry-pick applies cleanly.

## Steps to reproduce

1. Release a version with `scripts/release.sh` (for example 1.3.3, archived 2026-10-27 UTC).
2. Bump `MARKETING_VERSION` and run `scripts/release.sh` again on the same UTC date.
3. Compare the new DMG's `CFBundleVersion` with the newest `sparkle:version` in `website/appcast.xml`.

## Expected

Each release gets a build number strictly greater than every earlier release, however many releases happen in one day. The preflight refuses to proceed when that would not hold.

## Actual

Both releases get the same `YYYYMMDD` build number. Sparkle treats the second as "no update available". `scripts/preflight.sh` only warns about it.

The preflight and `release.sh` run at different times, so the candidate is only an estimate. `release.sh` could also check its actual `$BUILD_NUMBER` against the appcast before archiving. - No unit test, `tools/` script, `build.sh` path or app code parses the release build number. Other `%Y%m%d` uses (`scripts/screenshot-batty.sh:57`, `tools/run-ui-tests-vm.sh:152`, `.claude/skills/batty-cli/install.sh:149`) are unrelated timestamps.
- A 12-digit value fits zsh's 64-bit integer comparison (`-lt`/`-eq` in preflight) and is a valid `CFBundleVersion` for a Developer ID app outside the App Store.

## Plan

Premises checked against the worktree (branch `issue/0537`, same as `main` at `240abd5a`): every line reference in Notes holds. `release.sh:117` computes `BUILD_NUMBER`, `:151` passes it to `xcodebuild`, `:330-332` checks it. `preflight.sh:543-564` is the gate, with the wrong "override release.sh BUILD_NUMBER" hint at `:559`. `preflight.sh --credentials-only` exits at `:416`, before the version gates, so the gate below never runs inside `release.sh`'s own credential check. One more fact matters here. **`release/1.3`'s `website/appcast.xml` lags `main`'s.** `git diff main release/1.3 -- website/appcast.xml` deletes 62 lines. The newest `sparkle:version` on `release/1.3` is `20261014`, and on `main` it is `20261027` (1.3.3). The appcast items are committed on `main`, so a check that reads only the checked-out appcast would pass against stale data in a release worktree.

### Decisions

1. **Build number:** UTC `date -u +%Y%m%d%H%M`, computed once in `release.sh`. This was decided by the user.
2. **`release.sh` also checks its real number before archiving, and aborts if it is not greater.** Preflight runs minutes or hours earlier and can only estimate. `release.sh` is the only place that knows the actual value. The check is cheap and needs no network.
3. **Which appcast is read:** both scripts take the **maximum** `sparkle:version` across two sources. The first is the checked-out `website/appcast.xml`. The second is local `main`'s copy, `git -C "$REPO_ROOT" show main:website/appcast.xml`, read only when `git rev-parse --verify -q main` succeeds. A missing `main` ref is skipped silently. In a `release/X.Y` worktree this catches items that landed only on `main`, as 1.3.3's did. On `main` both sources are the same file. This is safe because `main` is where the appcast is edited and deployed from, so its copy is the newest record of what was shipped. Taking the max can only make the check stricter. Reading the live feed (`https://batty.sstools.co/appcast.xml`) was considered and rejected: it adds network and failure modes for little gain, and the user deploys from `main`.
   XML comments are stripped before matching (`perl -0777 -pe 's/<!--.*?-->//gs'`, as `appcast_newest_attr` already does), so placeholder text in the authoring comment can never count.

### Files

- **`scripts/build-number.sh` (new, sourced library, not executable on its own).** It has the minimal `#!/usr/bin/env zsh` header and a one-paragraph comment explaining why the number is `YYYYMMDDHHMM`: two releases on one UTC day collided at `YYYYMMDD` (#0537), and every 12-digit value is greater than every 8-digit one, so the change keeps Sparkle's ordering monotonic. It defines three functions:
  - `release_build_number` prints `$(date -u +%Y%m%d%H%M)`.
  - `newest_appcast_build <repo_root>` prints the highest `sparkle:version` across the two sources in decision 3, or nothing if neither has one.
  - `build_number_is_newer <candidate> <newest>` returns 0 when `<newest>` is empty or `candidate > newest` (zsh `(( ))` arithmetic, 64-bit), and 1 otherwise. It is pure, so the dry check can call it directly.

  Both scripts source this file, so preflight computes its estimate exactly the way `release.sh` computes the real number.
- **`scripts/release.sh`.**
  - Source `"$SCRIPT_DIR/build-number.sh"` near the top.
  - Move the build-number computation **before** `==> Cleaning previous build`, so a refusal leaves `build/` untouched. Replace `:117` with `BUILD_NUMBER="$(release_build_number)"`.
  - Add the gate right after it: `NEWEST_BUILD="$(newest_appcast_build "$REPO_ROOT")"`, and if `! build_number_is_newer "$BUILD_NUMBER" "$NEWEST_BUILD"`, print an error and `exit 1`. The error names both numbers. It says Sparkle would not offer this build to users of the newest release, says the number is the UTC time `YYYYMMDDHHMM` at archive time and that the appcast numbers come from `website/appcast.xml` and `main`'s copy, and tells the user to check the system clock and the appcast's newest item. When the two numbers are equal it says to re-run in the next minute. It must not mention any override, because none exists.
  - Change nothing else. File names, the `:330` equality check and the summary all work with 12 digits.
  - Update the header comment only if it describes the build number. It does not today.
- **`scripts/preflight.sh`.**
  - Source `"$SCRIPT_DIR/build-number.sh"` if the script has `SCRIPT_DIR`. Otherwise derive the path the same way it derives `REPO_ROOT`.
  - Replace the gate at `:543-564`. The new comment says `release.sh` uses UTC `YYYYMMDDHHMM` at archive time, so this is an estimate and `release.sh` repeats the check with the real number.
  - Logic: `CANDIDATE="$(release_build_number)"` and `NEWEST="$(newest_appcast_build "$REPO_ROOT")"`.
    - No newest found: `pass "appcast has no prior sparkle:version (first release)"`.
    - `build_number_is_newer` succeeds: `pass "build number now ($CANDIDATE) > newest in appcast ($NEWEST)"`.
    - Otherwise: `fail` with an accurate message. For example: "build number release.sh would use now ($CANDIDATE, UTC YYYYMMDDHHMM) is not greater than the newest sparkle:version in the appcast ($NEWEST); Sparkle would not offer it. Check the system clock and the appcast's newest item."
  - Keep the "appcast.xml not found" `warn` for the case where neither source exists. Leave `APPCAST=` at `:550` in place, because later gates (`:646`, `:675`) use it.
- **`scripts/RELEASE.md` `:73-80`.** Change "today's UTC date in `YYYYMMDD` form (e.g. `20260514`)" to "the UTC date and time in `YYYYMMDDHHMM` form (e.g. `202610272315`)". Add one sentence: `release.sh` and the preflight refuse a build number that is not strictly greater than the newest `sparkle:version` in `website/appcast.xml` or in `main`'s copy of it, so releases may happen any number of times a day, at most once a minute. Leave the historical `20260521`/`20260522` mentions (RELEASE.md `:157-158`, `appcast-item.sh:10`, `SPARKLE.md:78`) as they are.
- **`scripts/appcast-item.sh`:** no change. It reads `CFBundleVersion` from the DMG.

## Root cause

`scripts/release.sh` set `BUILD_NUMBER="$(date -u +%Y%m%d)"`, so any two releases archived on the same UTC date got the same `CFBundleVersion`/`sparkle:version`, and Sparkle offered nothing. `scripts/preflight.sh`'s gate only `warn`ed on equality and suggested an override that `release.sh` never had. It also read only the checked-out appcast, which on `release/1.3` lags `main`'s.

## Fix

As planned. New sourced library `scripts/build-number.sh` with `release_build_number` (UTC `date -u +%Y%m%d%H%M`), `newest_appcast_build <repo_root>` (max `sparkle:version` across the checked-out `website/appcast.xml` and `git show main:website/appcast.xml`, XML comments stripped), and `build_number_is_newer <candidate> <newest>`. `release.sh` sources it, computes the number before `==> Cleaning previous build`, and exits 1 with an accurate message (no override mentioned; "re-run in the next minute" when equal) if it is not strictly greater. `preflight.sh` sources it and its gate now `fail`s instead of `warn`ing, keeping `APPCAST=` for later gates. `RELEASE.md` documents the new format and the refusal.

One addition beyond the plan text: `newest_appcast_build` ends its pipeline with `|| true`, because `release.sh` runs under `set -euo pipefail` and a `grep` with no match (first release, or no appcast) would otherwise abort the script inside the command substitution.

## Review

Approved first pass. Checked: `BUILD_NUMBER` is computed once and the same value flows to `CURRENT_PROJECT_VERSION`, the archived `CFBundleVersion` equality check, the dSYM/archive names and both printed lines. The gate runs before `rm -rf build/` and before any archive, sign or notarize step; only the pre-existing read-only credential checks (`notarytool history`) come earlier. The comparison is zsh `(( ))` 64-bit integer arithmetic on digit-only values, so 12 vs 8 digits compares numerically. With no local `main` ref the second source is skipped and the checked-out appcast is still read.

Judgment on `|| true` in `newest_appcast_build`: it is needed (grep with no match, or `sort` getting SIGPIPE from `head -1`, would otherwise abort `release.sh` under `pipefail`). Its cost is that an appcast where no `sparkle:version="digits"` parses at all, in both sources, reads as "first release" and passes. Accepted: `appcast-item.sh` always writes the quoted attribute form, the current appcast parses correctly (`20261027`), and a partially malformed appcast (one bad item) would not be caught by an empty-result error either. Not carved-out scope.
