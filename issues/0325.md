# 0325 — Cmd-Ctrl-arrows Split resize is documented in present tense but has no implementation

| | |
|---|---|
| **Status** | open |
| **Module** | Split / Docs |
| **Platform** | macOS |
| **First seen** | 2026-08-08 |

## Description

`Concepts.md` is the canonical vocabulary every session and subagent is told to treat as authoritative, and it describes a keyboard shortcut in present tense — with no "planned" marker — that has no implementation anywhere in the codebase:

- `Concepts.md:72` — "Keyboard: Cmd-Ctrl-arrows resize the Split containing focus by ±5%."
- `Concepts.md:128` — "**Resized by:** dragging the divider, or Cmd-Ctrl-arrows. Updates to `ratio` are persisted."

Evidence that the shortcut is unimplemented (all verified against the working tree on `main`, 2026-08-08):

- `BattyKit/Sources/BattyKit/Shortcuts/ShortcutAction.swift` — the full catalog of user-configurable shortcuts declares `splitHorizontal`, `splitVertical`, `splitFullHeightColumn`, `splitFullWidthRow`, and `focusPane{Left,Right,Up,Down}`, but no resize action of any kind.
- `SplitTree.updateRatio(forSplitID:to:)` (`BattyKit/Sources/BattyKit/Model/SplitTree.swift:296`) has exactly one production call site: the divider drag gesture at `BattyKit/Sources/BattyKit/Views/SplitContainerView.swift:83`. (One test call site exists in `SplitTreeEqualizationTests.swift:132`.)
- `BattyKit/Sources/BattyKit/Commands/BattyCommands.swift` has Focus Pane Left/Right/Above/Below menu items but nothing resize-related.
- Broad greps for a resize implementation come up empty: no `resizeSplit` / `adjustRatio` / ±5% ratio-step code anywhere in `Batty/` or `BattyKit/Sources/`; the only Control-modifier handling outside generic shortcut-recorder infrastructure (`ShortcutBinding.swift`, `RecorderView.swift`, `BattyShortcuts.swift` modifier translation) is nonexistent; no raw `keyDown`/`performKeyEquivalent` path handles Cmd-Ctrl-arrows.

This is not a doc-only drift, though. Unlike #0324 (where the code had moved on and the doc was stale), here the weight of evidence says the feature was **intended**:

- `PRD.md:90` — user journey step 13: "Resize splits with Cmd-Ctrl-arrows | I can give one pane more screen real estate without the mouse".
- `PRD.md:162` — "**Keyboard resize:** Cmd-Ctrl-arrows resize the split containing focus by ±5%."
- `PRD.md:341` — the M4 — Splits milestone's definition of done includes "Drag-to-resize dividers, focus movement, and resize keybindings all work."
- `PRD.md:48` — design principle 7: "**Keyboard-first.** Every action that matters has a keybinding."
- `issues/Issues.md` module table — the `Split` module's own description reads "Split tree, dividers, drag-resize, **keyboard resize**, focus movement."

So the M4 milestone claims resize keybindings as part of done, yet the keybinding does not exist. Either the milestone shipped incomplete or the keybinding was dropped along the way without the docs being updated.

## Expected behavior

One of two resolutions — **this is the user's call; this issue deliberately does not pick one:**

1. **Implement the shortcut** — add a resize action (four directions) to `ShortcutAction`, wire it to `SplitTree.updateRatio` with a ±5% step on the Split containing focus, per the documented behavior. The PRD's user journey, spec section, M4 definition of done, and keyboard-first principle all treat this as a promised feature, which argues for this option.
2. **Correct the docs** — if the feature is deliberately abandoned, update `Concepts.md:72` and `:128`, `PRD.md:90`, `:162`, and `:341`, and the `Split` module row in `issues/Issues.md` to stop describing it (or mark it explicitly as planned/dropped).

Do not assume the doc is wrong just because the code is missing — `Concepts.md` and `PRD.md` are design documents as much as descriptions, and here they agree with each other against the code.

## Actual behavior

Pressing Cmd-Ctrl-arrow keys in a session with splits does nothing to the split ratio. The only way to resize a Split is dragging the divider. Meanwhile the canonical vocabulary, the PRD spec, and a milestone marked as shipped all state the keyboard path exists.

- If option 1 is chosen, note the default Cmd-Option-arrows are already taken by `focusPane*`, so Cmd-Ctrl-arrows are free as documented; check for conflicts with macOS system shortcuts (Ctrl-Cmd-arrows have no default system binding, but Mission Control owns Ctrl-arrows).
