## Description

`Concepts.md` is the canonical vocabulary every session and subagent is told to treat as authoritative, and it describes a keyboard shortcut in present tense — with no "planned" marker — that has no implementation anywhere in the codebase:

- `Concepts.md:72` — "Keyboard: Cmd-Ctrl-arrows resize the Split containing focus by ±5%."
- `Concepts.md:128` — "**Resized by:** dragging the divider, or Cmd-Ctrl-arrows. Updates to `ratio` are persisted."

Evidence that the shortcut is unimplemented (all verified against the working tree on `main`, 2026-08-08):

- `BattyKit/Sources/BattyKit/Shortcuts/ShortcutAction.swift` — the full catalog of user-configurable shortcuts declares `splitHorizontal`, `splitVertical`, `splitFullHeightColumn`, `splitFullWidthRow`, and `focusPane{Left,Right,Up,Down}`, but no resize action of any kind.
- `SplitTree.updateRatio(forSplitID:to:)` (`BattyKit/Sources/BattyKit/Model/SplitTree.swift:296`) has exactly one production call site: the divider drag gesture at `BattyKit/Sources/BattyKit/Views/SplitContainerView.swift:83`. (One test call site exists in `SplitTreeEqualizationTests.swift:132`.)
- `BattyKit/Sources/BattyKit/Commands/BattyCommands.swift` has Focus Pane Left/Right/Above/Below menu items but nothing resize-related.
- Broad greps for a resize implementation come up empty: no `resizeSplit` / `adjustRatio` / ±5% ratio-step code anywhere in `Batty/` or `BattyKit/Sources/`; the only Control-modifier handling outside generic shortcut-recorder infrastructure (`ShortcutBinding.swift`, `RecorderView.swift`, `BattyShortcuts.swift` modifier translation) is nonexistent; no raw `keyDown`/`performKeyEquivalent` path handles Cmd-Ctrl-arrows.

This is not a doc-only drift, though. Unlike #0324 (where the code had moved on and the doc was stale), here the weight of evidence says the feature was **intended**:

- `PRD.md:90` — user journey step 13: "Resize splits with Cmd-Ctrl-arrows | I can give one pane more screen real estate without the mouse".
- `PRD.md:162` — "**Keyboard resize:** Cmd-Ctrl-arrows resize the split containing focus by ±5%."
- `PRD.md:341` — the M4 — Splits milestone's definition of done includes "Drag-to-resize dividers, focus movement, and resize keybindings all work."
- `PRD.md:48` — design principle 7: "**Keyboard-first.** Every action that matters has a keybinding."
- `issues/Issues.md` module table — the `Split` module's own description reads "Split tree, dividers, drag-resize, **keyboard resize**, focus movement."

So the M4 milestone claims resize keybindings as part of done, yet the keybinding does not exist. Either the milestone shipped incomplete or the keybinding was dropped along the way without the docs being updated.

## Resolution notes

> 🟢 Resolved 2026-08-08 — ⌘⌃ + arrows now move the divider of the nearest matching-axis Split by ±5%. The docs were right; the code was missing.

Resolution 1 of the two the issue left open. Five documented sources agreed against the code — `PRD.md`'s user journey, spec, M4 definition of done and keyboard-first principle, plus `Concepts.md` and `issues/Issues.md`'s `Split` module row — so implementing was the reading, not a coin flip.

## Root cause

M4 was marked done with "resize keybindings all work" in its definition of done, but the keybinding was never written. `SplitTree.updateRatio(forSplitID:to:)` existed and had exactly one production caller: the divider-drag gesture. `ShortcutAction` had no resize case at all.

Review turned up the likely origin: **upstream Ghostty ships `super+ctrl+left=resize_split:left,10` as a stock macOS default binding.** The chord and the ±-step language in `PRD.md` almost certainly came from there — the docs described Ghostty's behavior, and Batty never implemented its own.

## Fix

Four directional actions following #0309's established end-to-end shape:

- **`ShortcutAction.swift`** — `resizeSplitLeft/Right/Up/Down`, defaulting to ⌘⌃ + arrows. Being in the catalog means they appear automatically in the Command Palette and Settings ▸ Shortcuts, and are rebindable.
- **`SplitTree.swift`** — `ResizeDirection`, `resizeStep`, `resizeFocusedSplit(_:)`, plus `SplitTreeNode.nearestAncestorSplitID(containing:matchingAxis:)` and `ratio(forSplitID:)`.
- **`BattyShortcuts.swift`** (live NSEvent monitor), **`CommandPaletteView.swift`** (palette), **`BattyCommands.swift`** (Pane-menu items with key equivalents from `shortcuts.keyboardShortcut(for:)`, not hardcoded).

Three design calls, all of which review confirmed match upstream Ghostty exactly:

1. **Which Split** — walks from the focused pane to the *nearest ancestor whose direction matches the arrow's axis*, skipping perpendicular parents; silent no-op if none matches. Equivalent to Ghostty's reverse path stride.
2. **Which direction** — each arrow moves the divider in its own geographic direction, focus-independent. Menu items are named **"Move Split Divider …"** rather than "Resize Split …", per upstream, because focus-independent semantics make "Resize Split Left" read as "make my pane wider" only half the time.
3. **Clamping** — reuses `updateRatio`'s existing `max(0.05, min(0.95, …))` verbatim rather than inventing a second policy; the same call the divider drag makes.

## Review

Reviewer: `claude-opus-5`, two rounds.

Round 1 went to upstream Ghostty's source rather than reasoning from first principles, and found `resizing(node:by:in:with:)` doing the identical deepest-matching-ancestor walk with the identical direction mapping — which settled both the design and the chord's provenance. It independently verified the chord is free, including that `BattyShortcuts.makeCandidate` already translates `.control` into `EventModifiers` (not a given), that macOS Mission Control is bare `⌃`+arrow and Sequoia tiling is `fn`+`⌃`+arrow, and that upstream ships the exact chord.

Its one required finding was a real hole: **`.down` was completely untested.** It was called exactly once, inside `singleUnsplitPaneResizeIsANoOp`, where no split exists — so the call returned at the `guard` before reaching the sign or the axis mapping. Flipping `.down`'s sign or mis-mapping its axis left all 980 tests green, the same defect class the implementer's own `.left` mutation test was built to rule out.

Round 2 **reproduced both mutations itself** rather than accepting the implementer's report, confirming 3 failures for the sign flip and 4 for the axis mis-map, and verified the discriminating assertions fail in *opposite directions* under a `.horizontal` mis-map rather than passing coincidentally.

## Gotchas

- **The `rawValue`s stay `resizeSplitLeft` etc. even though the display names say "Move Split Divider".** That is deliberate — the raw values are the persistence keys for user-customised bindings, and renaming them would silently drop anyone's rebind.
- **A resize can silently do nothing.** ⌘⌃← in a session whose splits are all vertical has no matching-axis ancestor and no-ops. The Pane-menu items are gated on `canFocusAdjacentPane` (more than one pane), which is coarser than "a matching-axis ancestor exists" — so the menu item can look enabled and do nothing. Upstream Ghostty guards the identical action on `surfaceTree.isSplit`, the same coarseness, and the keyboard path bypasses `.disabled` entirely anyway.
- **The ±5% step is applied to the split's ratio, not to pixels**, so the visual movement depends on the container's size. This matches the divider-drag path, which writes the same `ratio`.
- **`docs/shortcuts.md` does not list these actions** — its table was already missing nine existing ones before this change, and lists wrong defaults for `toggleSidebar` and `toggleBellFeed`. Filed separately rather than fixed here.

2. **Correct the docs** — if the feature is deliberately abandoned, update `Concepts.md:72` and `:128`, `PRD.md:90`, `:162`, and `:341`, and the `Split` module row in `issues/Issues.md` to stop describing it (or mark it explicitly as planned/dropped).

Do not assume the doc is wrong just because the code is missing — `Concepts.md` and `PRD.md` are design documents as much as descriptions, and here they agree with each other against the code.

## Actual behavior

Pressing Cmd-Ctrl-arrow keys in a session with splits does nothing to the split ratio. The only way to resize a Split is dragging the divider. Meanwhile the canonical vocabulary, the PRD spec, and a milestone marked as shipped all state the keyboard path exists.
