## Description

Child of #0660. An agent can open a terminal *Pane* that runs a command (`pane split -c`), but not a *Tab*. A Tab is often the better fit: a long build or test run in a new Tab of the agent's own Pane keeps the layout as it is. Add `batty tab new [--pane <id>] [-c <command>] [--cwd <dir>] [--background] [--json]`, which is also an MCP tool (`tab_new`) because the catalog is built from `capabilities`.

### Current state

- `tab` has one verb, `focus` (`BattyKit/Sources/batty/TabCommand.swift:17`). `docs/batty-cli-design.md` §2 A lists `batty tab new [-c <cmd>]` as proposed, and `docs/batty-cli-agent-workflows.md:546-548` lists "creating a Tab" as not available.
- The app can add a Tab: `AppStateStore.addTab(toPaneID:inheritingCWDFrom:)` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:1967`) and `PaneRuntime.addTab` (`BattyKit/Sources/BattyKit/Runtime/PaneRuntime.swift:290`), which builds a `TabRuntime` with no command parameter.
- `TabRuntime` already supports a per-Tab command: `pane split -c` passes it through and `applyShellAndAppearancePreferences` sets `command`, `wait-after-command = true` and `abnormal-command-exit-runtime = 0` for it (`BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:429-458`).
- `pane split` prints only the new Pane's id and has no `--json` (`BattyKit/Sources/batty/PaneCommand.swift:183-193`).

## Expected behavior

- New XPC verb `tabNew` with `TabNewRequest { paneID?, command?, workingDirectory?, background? }` and `TabNewReply { sessionID, paneID, tabID }`.
- Target: `--pane`, else `BATTY_PANE_ID`, else the focused Pane (`BattyTargetResolver`). A non-terminal target Pane is a failure (exit 4) with a clear message.
- Working directory: `--cwd` (resolved to an absolute path by the CLI), else the calling Tab's cwd when the target is the caller's Pane, else the Pane's active Tab's cwd (same inheritance as Cmd-T; see #0463 for the existing inconsistency, not fixed here).
- `-c`: same semantics as `pane split -c` (runs in place of the shell; the Tab stays open after the command exits until closed).
- By default the new Tab becomes the Pane's active Tab, without moving keyboard focus away from the caller's Pane. `--background` adds it without selecting it.
- Plain output: the new Tab's id. `--json`: the reply.
- Emits a watch event like the other mutations (existing names: `pane_split`, `tab_focused`, `session_created`; the planner picks a `tab_created`-style name).

## Acceptance criteria

1. Unit tests on `AppStateStore`: adds a Tab to the target Pane with the command and cwd; refuses a non-terminal Pane; unknown Pane id fails; `background` leaves the active Tab unchanged; the caller's Pane keeps focus.
2. `CapabilitiesInputSchemaTests` drift oracle covers `tab new`; `MCPToolCatalogTests` lists `tab_new`.
3. A UI test (type-checked with `./build.sh ui-typecheck`, run in the next daily VM run) creates a Tab with `-c` and checks the chip appears.
4. Behind `agentIntegration` until #0669, per `AGENTS.md` ("Unfinished features on `main` stay behind a feature flag").

## Root cause

Feature work. `tab` had only `focus`; `PaneRuntime.addTab` took no command and always selected the new Tab, and the only store entry point (`AppStateStore.addTab(toPaneID:inheritingCWDFrom:)`) also focuses the Pane, so no XPC path could add a Tab without moving focus.

## Fix

As planned. New `tabNew` XPC verb (`TabNewRequest`/`TabNewReply` in `BattyXPCCore/TabNewPayload.swift`); `PaneRuntime.addTab` gains `workingDirectory`, `command` and `select` (defaults keep Cmd-T unchanged); `AppStateStore.newTabForXPC` + pure `tabNewSource` (no focus, selection or window writes; emits `tab_created` and, when selected, `active_tab_changed`, both `fromCli: true`); `AppXPCService` case reads `storeProvider()`; `TabNewCommand` with `--pane`, `-c/--command`, `--cwd` (pure `resolveWorkingDirectory`, also expands `~`), `--background`, `--json`; `"tab new": "new"` archetype; `docs/batty-cli-install.md` entries. No feature flag (plan decision 1, overrides AC 4; needs the user's nod).

Small deviations: `resolveTargetPaneID` in `PaneCommand.swift` changed from file-private to internal so `TabNewCommand` reuses it; `CapabilitiesCommandTests.verbRosterListsEveryShippedVerb` roster gains `"tab new"`; `emptyCommandIsTreatedAsNoCommand` asserts the absence of `wait-after-command = true` (the rendered config always carries a default `command =` line, so the planned "no `command =` line" check could not hold).

## Gotchas

- The new UI test passed in a filtered VM run at review (`CLIRemoteControlTests`, 18 tests).
- Surfaces are created lazily, but this does not delay `-c` in practice (corrected at review). `TerminalPlaceholderView` (`Views/TerminalPlaceholderView.swift:48`) creates the terminal view, and with it the PTY, the first time its placeholder renders. `SessionDetailView.sessionStack` keeps every Session of a window mounted (`ForEach(windowRuntime.sessions)` with opacity 0 for unselected ones), and `PaneView`'s `ZStack` has a placeholder for every Tab (`ForEach(pane.tabs)`), not only the active one. So a new Tab, with or without `--background` and in a selected or unselected Session, starts its `-c` command on the next SwiftUI update. The exception is a hidden Pane: `SplitContainerView` renders a hidden leaf as a zero-size placeholder with no `PaneView`, so a Tab added to a hidden Pane starts only when the Pane is shown. #0668 (`--wait`) should refuse a hidden Pane or document this.

## Resolution notes

> 🟢 Resolved 2026-11-18 — `batty tab new [--pane] [-c] [--cwd] [--background] [--json]` (and the `tab_new` MCP tool) adds a terminal Tab without moving focus, Session selection or the key window.

## Review

Approved first pass. Checked: `newTabForXPC` writes only `activeTabID` (skipped with `--background`), which goes through `PaneRuntime.activeTabID`'s `moveShown`/`activeTabDidChange` choke point, and never `focusPane`, `setSelectedSession` or `activateWindow`. `tab_created` and `active_tab_changed` are sent with `fromCli: true`. The target is resolved as `--pane` → `BATTY_PANE_ID` → `focusedPaneIDFallback`, through the shared `resolveTargetPaneID`. `-c ""` is treated as no command, and the command threads through `TabRuntime.init(command:)` as `pane split -c` does. The capabilities schema, archetype and MCP catalog tests are in place. The XPC write runs from the verb's `Task { @MainActor }` (event-origin), and nothing writes from a view callback. Views still store only Tab ids, and the eager view creation stays in the placeholder. The implementer's gotcha said that `--background -c` does not run until the Tab is selected. That is wrong: every Session and every Tab placeholder stays mounted, so the PTY starts on the next update. Only a hidden Pane defers the start. I corrected the gotcha rather than bouncing, because the issue's purpose (an agent runs a command in a new Tab) works as shipped.

## Plan

Planned 2026-11-18 against `main` at `b9911b66`. Premises checked in code: `tab` has only `focus` (`TabCommand.swift:13-18`, whose doc comment says `tab new` stays unbuilt until scheduled); `PaneRuntime.addTab(inheritingCWDFrom:)` (`PaneRuntime.swift:290`) takes no command and always selects the new Tab; `AppStateStore.addTab(toPaneID:inheritingCWDFrom:)` (`AppStateStore.swift:1967`) also calls `window.focusPane`, so the XPC path must not reuse it; `TabRuntime.init(... command:)` already applies `command`, `wait-after-command = true` and `abnormal-command-exit-runtime = 0` (`TabRuntime.swift:176-205, 429-458`); `pane split -c` reaches it through `SplitTree.makePane` (`SplitTree.swift:499-501`). `WatchEventType.tabCreated = "tab_created"` already exists (`XPCWatchMessages.swift:89`) and nothing emits it. MCP tools come from `capabilities` (`MCPToolCatalog.toolName` maps `tab new` to `tab_new`; `--json` is appended automatically when the verb has a `json` property).

### Decisions (recorded reasons)

1. **No feature flag.** This overrides acceptance criterion 4. `tab new` is a general CLI verb like `pane split -c`: complete on merge, reads and writes no files, and useful to any script, not only to the agent integration. `AGENTS.md`'s flag rule covers *unfinished* features; this one is finished when it lands, and 1.4.x patches ship from `release/1.4`, so nothing on `main` reaches Prod before 1.5.0 anyway. Gating one verb inside an ungated noun would also need two `tab` noun types switched in `BattyCLI.subcommands(for:)`, extra test cases, and then #0669 to undo them. Consequence: #0669 has no gate site from #0667. The orchestrator should tell the user; if they want the flag, it is a small follow-up (gate `TabNewCommand` in `TabNounCommand` via `subcommands(for:)`).
2. **Reply shape** `TabNewReply { sessionID: UUID, paneID: UUID, tabID: UUID }`, all non-optional. #0668 extends it with optional fields (`exitCode: Int?`, `durationMs: Int?`) so older readers keep decoding. `--json` prints it with `[.prettyPrinted, .sortedKeys, .withoutEscapingSlashes]`, as `ServerCommand.sendServer` does. Plain output: the Tab id alone.
3. **Request shape** `TabNewRequest { paneID: UUID?, sourceTabID: UUID?, command: String?, workingDirectory: String?, background: Bool? }`. `sourceTabID` is `BATTY_TAB_ID` from the CLI's environment (no flag). The app uses it as the cwd source only when that Tab is in the target Pane, else the Pane's active Tab. #0668 adds `wait`/`timeout` fields here.
4. **Focus.** Never calls `window.focusPane`, `setSelectedSession` or `activateWindow`; the focused Pane, the selected Session and the key window are unchanged. Without `--background` the new Tab becomes the Pane's active Tab (`activeTabID` write). When the target is the focused Pane of the selected Session (the usual "my own Pane" case), the existing `SplitTree.activeTabDidChange` → focus-intent path moves typing to the new Tab inside that Pane, exactly as Cmd-T does. Keyboard focus never leaves the caller's Pane. `--background` leaves `activeTabID` alone.
5. **Hidden Pane:** allowed, not un-hidden (no visibility side effects); `moveShown` keeps the new Tab hidden. **Non-terminal Pane:** refused with `"pane is not a terminal pane"` (exit 4). **`-c ""`** is treated as no command, like `pane split`.
6. **`--cwd`:** resolved by the CLI to an absolute, standardized path (`URL(fileURLWithPath:).standardizedFileURL.path`) and rejected client-side (exit 1, `batty: --cwd is not a directory: <path>`) when it isn't an existing directory, because libghostty would otherwise silently start the shell in its default directory.
7. **Watch events:** emit the existing `tab_created` (`sessionID`, `targetPaneID`, `tabID`, `fromCli: true`). When the active Tab flips (no `--background`), also emit `active_tab_changed` with `fromCli: true`, mirroring `focusTabForXPC` (#0145: subscribers tracking the active Tab must not miss a CLI-driven change).
8. **`--title`:** not added (open question 2; no rename verb exists).
