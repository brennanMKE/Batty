## Description

Umbrella for splitting BattyKit into smaller Swift modules, each with a stable protocol interface, so that unit tests can use mocks of other modules and a change to one file no longer recompiles every test. Target: **before a 2.0 release**. This is planning only: the user said not to start the work now.

User's words: "We should break down the code base into smaller modules so we don't have such a monolith and all unit tests are not impacted by changes to a single file. We probably should define interfaces for each module and try to make it stable. This is done with protocols in Swift. Once we have protocols we can create mocks of protocols so unit tests can be faster because they don't have to hook into the real implementation. This is a bigger effort, possibly before a 2.0 release."

#0587 is the near-term fix for slow `./build.sh unit` runs (scheme, CLI dependency, DerivedData). This issue is the structural fix behind it.

## Current state (checked on `main`, 2026-11-12)

- **One library module.** `BattyKit/Package.swift` declares five source targets: `BattyKit` (227 Swift files), `BattyXPCCore` (35), `batty` (23, the CLI executable), `BattyCLICore` (4) and `BattyBroker` (4). That is 293 source files in all, and almost everything the app does is in `BattyKit`. The app target (`Batty/`) is only a few files on top of it.
- **One test module.** `BattyKitTests` has 286 Swift files and about 59,400 lines. 262 of them use `@testable import BattyKit`. Because `@testable` exposes `internal` symbols, a change to any internal declaration in `BattyKit` changes the interface that every test file imports, so the whole test target recompiles. #0587 measured warm runs that recompiled 292 of 293 test-target files after a small change.
- **The test target depends on the CLI.** `BattyKitTests` depends on `"BattyKit", "batty"` and `ArgumentParser` (see #0587).
- **What triggers the full test-target recompile (#0587).** Body edits and new internal declarations in BattyKit recompile only 3–6 files; the full `BattyKitTests` recompile happens when a BattyKit source file is added, removed or renamed. Splitting `BattyKitTests` alone wouldn't help (each part still `@testable import`s all of BattyKit), and moving the 11 CLI test files (`@testable import batty`) into their own target was deferred to this split.
- **Precedent for small modules.** `BattyCLICore` and `BattyXPCCore` are already split out as dependency-free targets (Foundation only), so the `batty` CLI and the `BattyBroker` agent don't pull in Sparkle or libghostty. The comments in `Package.swift` explain why. Any new module split should follow the same rule: depend only on what it needs.
- **Precedent for protocols and fakes.** `BattyKit` already defines protocol seams, among them `KeyValueStoring`, `SchedulingClock`, `BellNotifying`, `NotificationSummarizing`, `GitStatusScanning`, `GitStatusWatching`, `SystemMetricsSampling`, `ProjectSyncBackend`, `PaneContentLifecycle`, `TeardownReapGate`, `SessionNameSuggesting`, `BackgroundCatalogFetching` and `SharedImageTransport`. Tests already use fakes for them: `FakeKeyValueStore`, `FakeBackgroundCatalogFetcher`, `FakeSharedImageTransport`, `FakeSystemMetricsSampler`, `FakeSMCProbe`, `FakeListAllPIDs`, `SpyBellNotifier`, `SpyReminderNotifier`, `StubSummarizer`. Some test doubles ship in the library itself (`BattyKit/Sources/BattyKit/Testing/`: `FixtureBackgroundCatalogFetcher`, `ManualSchedulingClock`, `UITestDriver`). These are the pattern to extend.

## Candidate seams (a sketch, not a decision)

The source folders under `BattyKit/Sources/BattyKit/` suggest where modules could split. File counts are for 2026-11-12.

| Folder | Files | What's there | Notes |
|---|---|---|---|
| `Theme/` | 8 | Theme catalog, pinned themes, theme preference, chrome | 2 files import libghostty (`GhosttyTheme`). Small and fairly self-contained, so a good first candidate. |
| `Settings/` | 17 | Preferences, background image library and catalog fetching, hosted image store, CLI installer, broker agent controller | Mixed. The background catalog and image code could be its own `Backgrounds` module; already behind `BackgroundCatalogFetching` and `SharedImageTransport`. |
| `Model/` | 32 | `LayoutModel` / `SplitTree` / `PaneLayout` value types, `Project` and `ProjectStore`, project sync, project editor view model, Git status model | The layout value types (`Pane`, `SplitDirection`) are pure, Codable and Sendable by rule, so they fit a dependency-free core module. Projects (store, sync, picker, editor model) could be a `Projects` module. |
| `Runtime/` | 58 | `AppStateStore` and its extensions, Window/Session/Tab/Pane runtimes, `SurfaceRegistry`, `TerminalHostStore`, bell feed, reminders, status-view Pane contents (Git status, process status, system metrics, LM Studio), metric readers | The largest and most entangled folder. Status-view Pane contents and the metric readers look separable behind `PaneContentLifecycle` and `SystemMetricsSampling`. The terminal and surface code is the hardest part (see Constraints). |
| `Views/` | 57 | SwiftUI and AppKit views, window controllers | Likely stays near the top of the graph, depending on the others through their protocols. |
| `Commands/` | 12 | Menu commands, shortcuts, focus helpers, terminal click and key handling | 4 files import libghostty. |
| `XPC/` | 13 | App-side XPC service, broker connection, topology payloads | Builds on `BattyXPCCore`, which is already its own module. |
| `Shortcuts/`, `ProjectName/`, `Util/`, `Updater/` | 7, 4, 12, 1 | Shortcut handling, project name suggestion, utilities, Sparkle wrapper | `Util/` holds `Logging.swift` (`Logging.subsystem`), which every module needs, so it belongs in the lowest layer. `Updater/` isolates Sparkle. |

## Constraints

- **Swift 6 with MainActor default isolation.** Every target uses `.defaultIsolation(MainActor.self)` and `StrictConcurrency` (the `swiftSettings` in `Package.swift`). Protocols that cross module boundaries need deliberate isolation (`nonisolated`, `Sendable`, or `@MainActor`). Mocks must match it.
- **Surface registry rule.** The Surface registry is the single source of truth for live Terminal Sessions. Views store only `surfaceID: UUID`, never `ghostty_surface_t`, and view rebuilds must not destroy surfaces (`AGENTS.md`, "Architectural rules"). A module split must keep one registry, owned by one module, and must not leak libghostty types through protocols.
- **Terminal-host architecture.** `docs/view-hierarchy.md` sets non-negotiable rules for how the model maps onto the SwiftUI tree and the persistent AppKit terminal host. `docs/terminal-pane-requirements.md` and `docs/swiftui-observation-rules.md` are binding too. Moving the terminal path between modules must preserve all of them. It should be the last split, not the first.
- **libghostty dependency.** `BattyKit` depends on `GhosttyKit`, `GhosttyTerminal` and `GhosttyTheme` from `libghostty-spm` (pinned to a revision). 16 source files import them, in `Commands/`, `Runtime/`, `Theme/`, `Util/` and `Views/`. Modules that don't touch the terminal should not depend on libghostty at all. That way their tests don't link the xcframeworks.
- **Other dependencies.** Sparkle, SlidingTabs and Textual are linked into `BattyKit` today. Each should be linked only by the module that uses it.
- **The `batty` CLI and `BattyBroker`.** They must keep linking only `BattyCLICore` and `BattyXPCCore`. If they link a module that brings in Sparkle or libghostty, they crash at launch outside the app bundle.
- **Resources.** `BattyKit` carries `.process("Resources")` and `.copy("Help")`, and `BattyKitTests` carries `.copy("Fixtures")`. Each new module needs its own resources, or a shared resource module, with `Bundle.module` lookups updated.
- **Restricted areas.** `Configuration/Build.xcconfig` and `scripts/` need the user's confirmation before they change (`AGENTS.md`, "Restricted areas"). `build.sh` and the scheme will need updates so `./build.sh unit` runs every new test target and keeps its output contract (see #0587).
- **Public API surface.** Today almost everything in `BattyKit` is `internal` and reached through `@testable`. Splitting means choosing what each module makes `public` (or `package`), which is the "stable interface" the user asked for.

## Acceptance criteria (umbrella level)

- `BattyKit` is split into several modules along seams like those above, each with a protocol interface that other modules depend on instead of on concrete types.
- Each module has its own test target. Those tests mostly use mocks of other modules' protocols, not the real implementations, and use `@testable` only for their own module.
- Changing the implementation (not the interface) of one module doesn't recompile other modules' tests. This is checked by timing a one-line implementation edit and counting `SwiftCompile` lines per target, as #0587 does.
- Unit-tier timings are measured before and after: cold, warm with no change, warm after a one-line implementation edit in one module, and warm after a one-line test edit. The results are recorded here.
- The app, the `batty` CLI and `BattyBroker` still build and behave the same. The Release build (`./build.sh release archive …`) passes at `-O` for both architectures. Debug builds don't cover `-O` optimizer paths (#0391).
- `AGENTS.md`, `CLAUDE.md` and `docs/` describe the module layout and the rule for adding new code to it.
