# 0477 — The batty CLI cannot list or open Projects, so an agent or script cannot start a Project's Session

| | |
|---|---|
| **Status** | open |
| **Module** | Projects / App |
| **Platform** | macOS |
| **First seen** | 2026-10-12 |

## Description

Artboard 4 (`issues/0469/EntryPoints.dc.html`) shows two CLI verbs:

```
% batty-beta project list
NAME             ROOT                                PANES
Batty            ~/Developer/brennanMKE/Batty        3
Homelab          ~/Developer/Homelab                 2  open
% batty-beta project open Batty
Opened Session "Batty"
```

This issue adds a `project` noun with `list` and `open` verbs. The app handles them through XPC, because the app owns `ProjectStore` and the CLI never reads `projects.json` itself. With the flag off, the noun does not exist in the binary, so it is absent from `--help` and from `batty capabilities`, and the app rejects the XPC verbs as unknown.

## Expected behavior

**1. CLI surface** (`BattyKit/Sources/batty/`):

- A `ProjectNounCommand` (`commandName: "project"`) with:
  - `ProjectListCommand` (`list`, `--json`). Columns: name, root (with `~` abbreviation), pane count, and an `open` marker when a Session from the Project is open. Ordered as in the store.
  - `ProjectOpenCommand` (`open <name>`, `--new` to always open another copy, `--json`). Name matching is case-insensitive exact (#0471's `project(named:)`). On success it prints `Opened Session "<name>"` or `Focused Session "<name>"` (or JSON with `sessionID`, the focused `paneID`, and `created: Bool`, mirroring `batty new`'s session id / pane id output in `NewSessionCommand.swift`). An unknown name exits non-zero with a clear message that lists the close matches.
- Follow the existing noun pattern: `SessionNounCommand`, `PaneNounCommand` and `TabNounCommand` are wired in `BattyCLI.configuration.subcommands` (`Sources/batty/BattyCLI.swift:14`).
- **Flag gate.** The CLI is a bare Mach-O whose variant is compile-time (`ServiceNames.current`, set by `-DBATTY_VARIANT_BETA` in the "Embed CLI" build phase). Include `ProjectNounCommand` in the subcommand list only when `FeatureFlags.current.projects` (#0470) is true. `BattyCLI.configuration` is a `static let` today, so make the list a function of an injectable flags value, for example `BattyCLI.subcommands(for: FeatureFlags)`. `BattyKitTests` builds without `-DBATTY_VARIANT_BETA` (`swift test`), so `current` is always off there. The tests must exercise both values through the parameter.
- **`batty capabilities`** already derives its verb list by walking `BattyCLI.configuration.subcommands` (`Sources/batty/CapabilitiesCommand.swift:99-101`), so a gated-out noun is absent for free. With the flag on, the two new verb paths must be opted into `leafArchetypeByVerbPath` deliberately. Its coverage test, `CapabilitiesInputSchemaTests.leafArchetypeByVerbPathCoversExactlyTheShippedVerbPaths` (named in `CapabilitiesCommand.swift:141-146`), fails otherwise. Decide the annotations: `project list` is read-only, and `project open` is not destructive but is activating, like `focus`. The same test file covers each verb's input schema.

**2. XPC** (`BattyXPCCore/XPCVerb.swift`, `BattyKit/XPC/AppXPCService.swift`):

- New verbs `projectList` and `projectOpen`, with Codable payloads in `BattyXPCCore`.
- `AppXPCService` handles them only when `store.featureFlags.projects` is true. Otherwise the request falls through to the existing `default:` arm, which replies `unknown verb: <verb>` (`AppXPCService.swift:394-396`). A Beta CLI pointed at a Prod app (or the other way round) therefore degrades to a clear error.
- `projectOpen` calls #0472's `openProject(id:mode:)`. **Trust prompt (#0473).** If the Project's commands need confirmation, the app shows the sheet. The XPC reply must not block indefinitely on an unattended sheet. Choose one of two behaviors. Either reply once the Session exists, so the sheet's choice only affects whether commands run, or reply after the choice with a reasonable bound and an exit status that says the user hasn't answered yet. Pick one, document it in the CLI help text and `docs/batty-cli-agent-workflows.md`, and test it. In both designs the CLI must never pass a "skip the prompt" flag. There is no `--yes`, because commands must not run without the user's consent.
- Emit the same `session_created` / `session_focused` watch events the GUI path emits (`AppStateStore.addSession`, `focusSessionForXPC`), with `fromCli: true` where the existing verbs set it.

**3. Docs.** `docs/batty-cli-design.md:38` fixes the noun set as "`session`, `pane`, `tab`, `window`". Amend it: `project` is a deliberate fifth noun, approved with the Projects design on 2026-10-12 (#0469), and Beta-only until 1.3.0. Update `docs/batty-cli-install.md` and `docs/batty-cli-agent-workflows.md` if they enumerate nouns. Update the repo's `batty-cli` agent skill (`.claude/skills/batty-cli/SKILL.md`) with the two verbs, marked Beta-only (`batty-beta`).

**4. Gate-site list.** Append the CLI subcommand list, the `AppXPCService` handler, and the skill/doc notes to #0470's list.

## Acceptance criteria

- Unit tests for the CLI tree:
  - `BattyCLI.subcommands(for: FeatureFlags(projects: true))` contains the `project` noun with `list` and `open`;
  - with `projects: false` it does not;
  - `CapabilitiesCommand.verbs()` (or its flag-parameterized equivalent) reports `project list` and `project open` only when the flag is on;
  - the archetype coverage test passes for both.
- Argument parsing tests: `project open Batty`, `project open "My Project" --new --json`, a missing name → usage error.
- `AppXPCService` unit tests:
  - with `FeatureFlags(projects: false)`, `projectList`/`projectOpen` reply `ok: false, error: "unknown verb: …"`, and `ProjectStore` is never constructed;
  - with the flag on and seeded Projects, `projectList` returns them with correct open markers;
  - `projectOpen` on a name creates or focuses, with `created` set correctly;
  - an unknown name fails.
- No sleeps, deadline polls, or elapsed-time assertions. XPC tests await the reply continuation (`docs/async-test-seams.md`, `AGENTS.md` "Asynchronous tests").
- Manual check in Batty Beta: `batty-beta project list` and `batty-beta project open <name>` behave as on artboard 4. The Prod `batty` binary has no `project` subcommand (`batty --help`, `batty capabilities`). Record the results.
- `./build.sh unit` passes with the new tests in the output.

## Notes

- `docs/xpc/xpc-cli-architecture.md` describes the CLI → broker → app path and the connect dance (`AppConnectDance.swift`). `project open` launches the app on demand like `batty new` does. Confirm that the flag-on app is the one that answers. The variant is matched by `ServiceNames`, so a Beta CLI reaches the Beta app.
- Don't add `project add/remove/edit` verbs. They are not in the approved design, and editing belongs in the Project Editor (#0474). If the user wants them later, file them separately.
