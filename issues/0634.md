# 0634 — Choosing Keep in the Quick Reminder bar after its Reminder fired drops the edited text and closes the bar

| | |
|---|---|
| **Status** | resolved |
| **Module** | Session / Sidebar |
| **Platform** | macOS |
| **First seen** | 2026-11-15 |
| **Priority** | high |
| **Target** | 1.4.0 |

## Description

If a Reminder fires while its Quick Reminder bar is open in edit mode, choosing **Keep <time>** throws away the text the user just typed. The bar closes as if the edit was saved, but nothing was saved: the store finds no pending Reminder and returns nil, and the bar never checks. The user wants this fixed before the 1.4.0 release.

The same Session-keyed commit has a second effect: if the Session's Reminder was *replaced* while the bar was open (for example by `batty session remind` from a script), Keep writes the edited text onto the newer Reminder, and **Remove Reminder** cancels the newer Reminder. Neither is the Reminder the bar was opened on.

Follow-up to #0631 (Quick Reminder bar, squash `cafbae32`).

## Steps to reproduce

1. Set a Reminder on Session "api" with the text "check the deploy", in 5 minutes.
2. About a minute before it is due, press ⇧⌘R. The bar opens in edit mode with **Keep <time>** highlighted.
3. Change the text to "check the deploy and the logs". Leave the bar open until the Reminder fires (the banner and the Bell Feed entry appear, with the old text).
4. Press Return, which chooses **Keep <time>**.

## Expected behavior

A commit from the bar acts on the Reminder the bar was opened on, identified by its id, and the user's edited text is never silently discarded:

- **Keep, the bar's Reminder still pending:** unchanged from today. Only the text changes; the id, creation time, due instant and system-request identifier stay.
- **Keep, the bar's Reminder is no longer pending** (it fired, was cancelled, or was replaced): the store changes nothing and reports that the Reminder is gone, rather than a bare nil. The bar stays open with the edited text intact and turns into a new-Reminder bar: the Keep and Remove rows go, the time rows stay with **In 15 Minutes** highlighted, and a line says the Reminder already fired (or was changed). The user then picks a time, and the Reminder is set with the edited text, or presses Escape. A replacement Reminder's text is never rewritten.
- **Remove, the bar's Reminder is no longer pending:** nothing is cancelled. A newer Reminder on the Session stays. The bar closes, since the user asked for no Reminder.

## Actual behavior

The bar closes, and "check the deploy and the logs" is gone. The fired entry and banner carry the old text, and no Reminder is pending. If the Reminder had been replaced instead, the replacement silently takes the edited text (Keep) or is cancelled (Remove).

## Root cause (verified against `cafbae32`)

- `ReminderBarView.init` (`BattyKit/Sources/BattyKit/Views/ReminderBarView.swift:29-34`) seeds `ReminderBarModel` once from `session.reminder`. `ReminderBarModel.init(editing:...)` (`BattyKit/Sources/BattyKit/Views/ReminderBarModel.swift:79-83`) builds the `.keep(due)` and `.remove` rows and keeps no Reminder id.
- The Reminder fires while the bar is open: `fireReminder` sets `session.reminder = nil` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore+Reminders.swift:294-296`). The bar's model does not change, so it still offers Keep.
- `ReminderBarModel.commit(row:now:calendar:)` returns `.keep(note:)` for the Keep row (`ReminderBarModel.swift:133-134`). `ReminderBarCommit.keep` carries only the note (`:35`).
- `ReminderBarView.activate(_:)` (`ReminderBarView.swift:167-177`) passes the commit to `ReminderActions.commit` (`BattyKit/Sources/BattyKit/Views/ReminderMenu.swift:43-45`) and then calls `onClose()` whatever the result.
- `commitReminderBar(.keep)` (`AppStateStore+Reminders.swift:36-37`) calls `updateReminderNote(_:forSessionID:)` (`:48-58`), which looks up the Session's *current* `session.reminder`. With none, it logs and returns nil (`:49-51`), which `activate` ignores. With a replacement pending, it rewrites the replacement's note. `.remove` (`:38-40`) calls `cancelReminder(forSessionID:)`, which cancels whatever is pending.

So the premise is confirmed, and it is wider than reported: the bar identifies its Reminder by Session, not by id.

## Notes

- The bar's model stays seeded once in `init` and is mutated only from key and click handlers (`docs/swiftui-observation-rules.md`). Handling "gone" at commit time, from the store's result, keeps it that way, with no `onChange` on `session.reminder`. A live update of the bar when the Reminder fires (an `onChange` whose flip is the scheduler's fire, an event-origin write) is a possible extra, not a requirement here.
- The fired Bell Feed entry and banner keep the text the Reminder had when it fired. This issue does not ask to rewrite them with the edited text.
- Commits of the time rows (`.set`) are not affected. They replace the pending Reminder by design and carry the bar's text.

## Plan

Written 2026-11-15 against `b10634f5`. Every line reference in "Root cause" above was re-checked and holds: `ReminderBarView.swift:29-34` and `:166-177`, `ReminderBarModel.swift:79-83`, `:35` and `:133-134`, `ReminderMenu.swift:43-45`, and `AppStateStore+Reminders.swift:36-40`, `:48-58` and `:294-296`. Two more facts the plan depends on: `updateReminderNote` has no caller outside `commitReminderBar` and two tests (`AppStateStoreReminderTests.swift:393`, `:434`), and the CLI and XPC paths don't use it. The store already records which Reminders fired in `remindersFiredThisLaunch` (`AppStateStore.swift:47`, `@ObservationIgnored`), so it can tell "fired" from "changed" without new state.

### Approach

The bar remembers the id of the Reminder it was opened on. Keep and Remove carry that id. The store acts only when the Session's pending Reminder still has that id, and otherwise returns a "gone" outcome. On a gone Keep, the view tells its own model, from the click or key handler that ran the commit. That turns the bar into a new-Reminder bar with the text kept. No `onChange` on `session.reminder` is added. The model is still seeded once in `init` and mutated only from event handlers (`docs/swiftui-observation-rules.md`), and the store write still happens synchronously in the same handler, with no `Task` hop.

## Fix

The `## Root cause` above was confirmed by the red runs below. The fix follows the plan exactly.

- `ReminderBarModel` now records `editingReminderID`. `ReminderBarCommit.keep` and `.remove` carry that id. `markReminderGone(fired:)` turns an edit-mode bar into a new-Reminder bar: the Keep and Remove rows go, `.after(15)` is highlighted, the text and picked date are kept, and `notice` is set to `.fired` or `.changed`. `isEditing` is now `private(set) var`.
- `commitReminderBar` returns a new `ReminderBarOutcome` (`saved`, `removed`, `reminderGone(fired:)`, `rejected`, plus a convenience `reminder`). Keep goes through `updateReminderNote(_:reminderID:forSessionID:)`, which writes nothing unless the Session's pending Reminder has that id. Remove goes through the new `cancelReminder(id:forSessionID:)`, which cancels only that id. "Fired" vs "changed" is read from `remindersFiredThisLaunch`. The unguarded `cancelReminder(forSessionID:)` is unchanged.
- `ReminderActions.commit` returns the outcome. `ReminderBarView.activate` calls `model.markReminderGone` from the same key or click handler when a Keep comes back `.reminderGone`, and stays open. Every other outcome closes the bar as before, including a gone Remove. There is no `onChange`, no `Task` hop, and no focus write (focus is already `.text` in list mode). A secondary notice line (`reminder-bar.notice`) under the header shows the plan's wording.

No deviations from the plan. `ReminderBarOutcome` and `ReminderBarNotice` live in `ReminderBarModel.swift`, next to `ReminderBarCommit`, which the plan allowed. In the store tests, the shared setup is factored into three private helpers (`editBar(for:text:)`, `commitBar(_:row:on:)` and `keepRow(_:)`).
