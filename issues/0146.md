# 0146 — Separate Bundle ID for development vs release builds via xcconfig schemes

| | |
|---|---|
| **Status** | open |
| **Module** | Build / Config |
| **Platform** | macOS |
| **First seen** | 2026-05-19 |

## Description

Running the app from Xcode during development uses the same Bundle ID (`co.sstools.Batty`) as the production release. This means the dev build and the App Store / notarized DMG build share the same container, UserDefaults, Sparkle state, and dock presence. A separate Bundle ID for the development build (e.g. `co.sstools.Batty.beta`) would allow both to coexist cleanly on the same machine and prevent dev data from contaminating production state.

## Expected behavior

- **Xcode / development builds** use Bundle ID `co.sstools.Batty.beta`, product name `Batty Beta`, a visually distinct app icon, and a separate Sparkle feed URL (or none).
- **Release builds** (built via `scripts/release.sh` or the Prod scheme) use Bundle ID `co.sstools.Batty`, product name `Batty`, and the production Sparkle feed.
- Switching between the two requires no manual edits to any source file or xcconfig. The build scheme drives everything.

## Approach

Follow the pattern documented in `../BetaProd/README.md`:

1. **Add `Active.xcconfig`** to `Configuration/`. This file contains a single `#include` that points at either `Beta.xcconfig` or `Prod.xcconfig`. It is generated (or overwritten) by a pre-build script; add it to `.gitignore` so it never appears as a dirty working-tree change.

2. **Add `Beta.xcconfig` and `Prod.xcconfig`** to `Configuration/`. Each overrides the keys that differ between environments:

   | Key | Beta value | Prod value |
   |---|---|---|
   | `PRODUCT_BUNDLE_IDENTIFIER` | `co.sstools.Batty.beta` | `co.sstools.Batty` |
   | `PRODUCT_NAME` | `Batty Beta` | `Batty` |
   | `ASSETCATALOG_COMPILER_APPICON_NAME` | `AppIconBeta` | `AppIcon` |
   | `SU_FEED_URL` | *(omit or point at a beta feed)* | `$(HTTPS)/batty.sstools.co/appcast.xml` |

3. **Add `#include? "Active.xcconfig"` to `Configuration/Build.xcconfig`** (optional include so cold builds without `Active.xcconfig` still compile).

   > **Restricted area:** `Configuration/Build.xcconfig` is listed in `CLAUDE.md` as a restricted file — changes require explicit user confirmation before implementation.

4. **Create `scripts/set-environment.sh`** — takes a single argument (`Beta` or `Prod`), writes `Active.xcconfig` with the appropriate `#include`, and optionally copies the matching app icon set into `Batty/Assets.xcassets/AppIcon.appiconset/`.

5. **Create (or update) two build schemes:**
   - `Batty (Beta)` — pre-action runs `set-environment.sh Beta`
   - `Batty (Prod)` — pre-action runs `set-environment.sh Prod`

   Both pre-actions must be configured to "Provide build settings from" the Batty target so `$PROJECT_DIR` is defined.

6. **Add a `AppIconBeta` icon set** to `Batty/Assets.xcassets/` — visually distinct from `AppIcon` (e.g. a tinted or badged variant) so it is immediately obvious which build is running.

   > **Restricted area:** `Batty/Assets.xcassets/AppIcon.appiconset/` is listed in `CLAUDE.md` as restricted — icon asset changes require explicit user confirmation.

7. **Update `issues/Issues.md` build/verify commands** to reference both schemes if the default scheme changes.

## Implementation order

1. Confirm with user which keys belong in Beta vs Prod (Bundle ID, name, icon, Sparkle feed).
2. Implement `scripts/set-environment.sh` and the xcconfig files — no Xcode project changes yet.
3. Add schemes + pre-actions to `Batty.xcodeproj` (or instruct user to add them manually since the project file is complex to edit by hand).
4. Verify by running `./scripts/set-environment.sh Beta`, building, and confirming the Beta bundle ID appears in `codesign -dv`.

## Notes

- `Configuration/App.xcconfig` currently holds `PRODUCT_BUNDLE_IDENTIFIER`, `PRODUCT_NAME`, `MARKETING_VERSION`, Sparkle keys, and other per-app settings. The Beta/Prod split will override only the keys that differ; everything else stays in `App.xcconfig`.
- `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` should stay in `App.xcconfig` (same version for both environments) unless a separate Beta versioning scheme is desired.
- The `../BetaProd/README.md` guide and the `xcode-betaprod` Claude Code skill (if installed) can assist with the full setup.
- Do not run `scripts/release.sh` to verify — notarization is a shared-state action requiring explicit user sign-off.
