## Description

Every read of `needsConfirmClose` in the app resolves to a literal `false` through a statically-dispatched extension property with no override, injection, or substitution point anywhere in the chain. The consequence is stronger than "untested": the close-confirmation branches are **unexecutable**. Nobody — not a unit test, not a UI test, not the user running a Beta with `sleep 30` in a tab — can make one of them run. Every confirmation path in the app is dead code that will go live all at once the day the real predicate ships, having never been exercised. Three issues have now independently documented deferring on exactly this (#0283, #0382, #0396) — three deferrals are a pattern, not a coincidence.

The polyfill: `BattyKit/Sources/BattyKit/Util/TerminalViewState+Polyfill.swift:27` defines `needsConfirmClose` as a Batty-side **extension** computed property on `TerminalViewState`, returning literal `false`. Its doc comment explains the history — #0054's confirmation plumbing was authored against a fork-side change (intended commit `8915065`) exposing `ghostty_surface_needs_confirm_quit` / `ghostty_surface_process_exited` as Swift properties; that fork commit was never pushed, so the polyfill stubs both predicates pending upstream.

**Four independent reasons no override is possible today** (each verified against source, 2026-09-06):

1. `TerminalViewState` is a `public final class` in the external package (`libghostty-spm` checkout at the pinned ref, `Sources/GhosttyTerminal/State/TerminalViewState.swift:13`) — not subclassable.
2. The property lives in an `extension`, and extension members on classes are **statically dispatched** — even a non-final class could not override it at these call sites.
3. `TabRuntime` is a `public final class` (`BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:9`) and `terminal` is a `public let` (`:12`) constructed inside `init` (`self.terminal = state` at `:118`) — no injection parameter, no setter, no factory hook.
4. No protocol abstraction exists: every call site reads the concrete `$0.terminal.needsConfirmClose`.

**The call sites, complete list on `main`** (six today; a seventh is in flight):

- `WindowRuntime.requestCloseTab` — gate at `BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift:364`, routes to a `PendingCloseRequest` dialog.
- `WindowRuntime.requestCloseOtherTabs` — busy sweep at `WindowRuntime.swift:415`.
- `WindowRuntime.closePane` — gate at `WindowRuntime.swift:520`, returns `PaneCloseOutcome.needsConfirmation` (#0283).
- `AppStateStore.closeSessionForXPC` — sweep at `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:664`, returns `SessionCloseOutcome.needsConfirmation` (#0382).
- `QuitConfirmation.windowNeedsConfirmClose` — `BattyKit/Sources/BattyKit/Views/QuitConfirmation.swift:64`, gates window close and quit.
- `RootWindowView.windowShouldClose` — busy-count at `BattyKit/Sources/BattyKit/Views/RootWindowView.swift:175`, feeds the "Close Window?" alert text.
- *(Branch, unmerged)* `WindowRuntime.requestRemoveSession`'s prompt sweep — `issue/0396` at `WindowRuntime.swift:256`; on that branch the other sites sit at `:411`, `:462`, `:569`. Once #0396 lands, seven sites total.

**What "unexecutable" means for each affected issue** — each documented the deferral independently, in its own words:

- **#0283** — `PaneCloseOutcome.needsConfirmation`: "Currently unreachable: `TerminalViewState+Polyfill.swift` hardwires `needsConfirmClose` to `false`" (`issues/0283.md:36`), and its Gotchas repeat it: "will start firing when the libghostty fork gap closes — untested at that point" (`issues/0283.md:80`).
- **#0382** — `SessionCloseOutcome.needsConfirmation`: doc comment says outright "**Unreachable today, same as `PaneCloseOutcome.needsConfirmation` one tier down** (#0283 never got a test for it either)" (`AppStateStore.swift:611`).
- **#0396** (in review on `issue/0396`) — its new `RemoveSessionWatchEventTests` documents the same limitation for `requestRemoveSession`'s prompt branch (branch file `BattyKit/Tests/BattyKitTests/RemoveSessionWatchEventTests.swift:21`, `:194` — "Every real TabRuntime reports needsConfirmClose == false today").
- Plus the pre-existing #0054 paths — `requestCloseTab`, `requestCloseOtherTabs`, `QuitConfirmation` — whose gap `RequestCloseTabTests.swift:10-11` documents.

**Why it matters beyond tidiness:** these are the guards that stop Batty destroying a Session or Pane with live processes in it. #0283 settled that an unattended caller must not bypass a guard a human would have seen; that decision is only as good as the guard, and the guard has never run. When the real predicate arrives, five distinct dialog/refusal flows (single tab, other tabs, pane, session, window/quit) activate simultaneously with zero prior executions between them.

## What the pinned upstream actually exposes (verified against the checkout, 2026-09-06)

This is the load-bearing fact for choosing a direction, and it **changed with #0389's re-pin** — the polyfill's doc comment (written against fork HEAD `ef88eed`) is now stale:

- The pin is `a2565cc` (`BattyKit/Package.swift:32`, release `1.5.20260903`), whose binary target downloads the xcframework built from Ghostty ref `c4e16970a` (checkout `Package.swift:53`, release tag `upstream.c4e16970a803`).
- **The C API at that pin exports the predicates.** `ghostty.h` in the shipped xcframework declares `ghostty_app_needs_confirm_quit(ghostty_app_t)` (`:1180`), `ghostty_surface_needs_confirm_quit(ghostty_surface_t)` (`:1193`), and `ghostty_surface_process_exited(ghostty_surface_t)` (`:1194`) — the very symbols #0054 was authored against.
- **The Swift layer exposes none of it.** `grep -rn "needsConfirmClose\|needs_confirm\|process_exited" Sources/` over the checkout returns zero hits. And no handle escapes for Batty to call the C functions itself: `TerminalSurface.rawValue` (the `ghostty_surface_t`) is internal (`Sources/GhosttyTerminal/Surface/TerminalSurface.swift:25`), `TerminalController.app` (the `ghostty_app_t`) is internal (`Sources/GhosttyTerminal/Controller/TerminalController.swift:51`). `TerminalViewState.surface` is publicly *readable* (`TerminalViewState.swift:34`) but yields only the wrapper, not the pointer.
- Batty's own `SurfaceRegistry` (`BattyKit/Sources/BattyKit/Runtime/SurfaceRegistry.swift`) stores raw `ghostty_surface_t` handles — but it has **zero callers** anywhere in the tree; nothing registers into it. It is not a route.

So the gap is no longer a C-API gap: it is a ~10-line Swift-wrapper gap in `GhosttyTerminal`, exactly the missing half of #0054's original two-sided change. That reframes the "wait for upstream" option below. Note also the two problems are orthogonal: even a real upstream `needsConfirmClose` would presumably be computed from the live surface and not settable, so unit tests (model-only, no live surfaces — `BattyKitTests` never attach one) would *still* be unable to force it `true` without a Batty-side seam. Production signal and test seam need separate answers, even if one change delivers both.

## Expected behavior

- At least one confirmation branch (ideally each outcome shape: `PendingCloseRequest` dialog, `PaneCloseOutcome.needsConfirmation`, `SessionCloseOutcome.needsConfirmation`, quit/window-close gate) is executable by a `BattyKitTests` unit test that forces a tab to report busy and observes the prompt/refusal, so the day the real predicate ships these paths go live already exercised.
- The mechanism is decided with trade-offs written down (candidates below), not defaulted into by a fourth deferral.
- Whatever lands corrects the stale polyfill doc comment (the C symbols now exist at the pin) and the misleading `RequestCloseTabTests.swift:10-11` comment (see Notes).

## Candidate directions (deliberately not decided here)

Like [#0332](0332.md) and [#0396](0396.md), this issue asks for the property, not a mechanism. Candidates, with known trade-offs — note the first three address the *test seam*, the last two the *production signal*, and a full fix likely pairs one of each:

- **Test-only predicate seam on `WindowRuntime`.** The #0396 reviewer sketched `@ObservationIgnored var needsConfirmClosePredicate: (TabRuntime) -> Bool = { $0.terminal.needsConfirmClose }`, routed through `WindowRuntime`'s sweeps and overridable under `@testable import`. Cheapest; zero production behavior change. But it covers only the `WindowRuntime` sites (four of seven once #0396 lands), leaving `AppStateStore.closeSessionForXPC`, `QuitConfirmation.windowNeedsConfirmClose` (a `static` method — no instance to hang a closure on without changing its shape), and `RootWindowView:175` unexecutable. Partial coverage may be acceptable if the covered branches are deemed representative; say so explicitly if so.
- **Batty-owned indirection on `TabRuntime`** — a stored or overridable `needsConfirmClose` on `TabRuntime` that defaults to the polyfill's value, with all seven sites reading `$0.needsConfirmClose` instead of `$0.terminal.needsConfirmClose`. Retires the caveat for every site at once and creates the single choke point where the real signal plugs in later. Trade-offs: touches a hot `@Observable` type (a stored property is observation-tracked — audit against `docs/swiftui-observation-rules.md`; today's reads run in sweeps and AppKit delegate callbacks, not `body`, so this looks safe but must be checked); and it moves the polyfill's semantics into Batty's model layer, which the eventual real-signal change must then unwind.
- **Protocol abstraction** over the slice of `TerminalViewState` that `TabRuntime` needs. The most conventional seam, but the heaviest: `TabRuntime.terminal` is reached for far more than this one `Bool` (title, cwd, bells, send/paste), so the protocol either balloons or splits `terminal` into two handles. Likely over-engineering for one predicate; listed for completeness.
- **Wait for upstream to ship the real property, test then.** This is what has effectively happened three times already. What would make the fourth time different: at the current pin the C symbols already exist (above), so "waiting" now means waiting only for a small Swift exposure — and, per the orthogonality note, even that day the branches remain *untestable from unit tests* without a seam, because forcing a genuinely busy surface requires a live process no `BattyKitTests` test spawns. Waiting alone can never satisfy the Expected behavior here; at most it retires the polyfill.
- **Ask upstream for the wrapper (and possibly the seam).** PR `Lakr233/libghostty-spm` to expose `needsConfirmClose` / `processExited` on `TerminalViewState` (or `TerminalSurface`) reading the now-shipped C symbols. The user has standing: merged work already in the fork's history (the #56/#57 follow-ups — checkout commits `8d9780a`…`9df3f3b` are the user's, and `f4d9fbd` cites the PRs), and #0390/#0389 just demonstrated the fork absorbing exactly this kind of two-sided change (the clipboard port landed upstream before the release was cut). Shipping the property upstream makes the polyfill's designed removal cue fire — "duplicate-member error… that's the cue to delete the polyfill" (`TerminalViewState+Polyfill.swift:23-26`) — and fixes the production signal for all seven sites. It does not by itself deliver unit-testability (orthogonality note above) unless the upstream property is made injectable, which is a bigger ask.

## Decision (implementation, 2026-09-08)

Chose **Batty-owned indirection on `TabRuntime`** (candidate 2), not the `WindowRuntime`-level closure seam the #0396 reviewer sketched (candidate 1).

`TabRuntime.needsConfirmClose` is a new computed property — `needsConfirmCloseOverride ?? terminal.needsConfirmClose`, where `needsConfirmCloseOverride: Bool?` is an `@ObservationIgnored`, `internal` (test-only, reached via `@testable import`) stored property defaulting to `nil`. Every one of the seven call sites (four in `WindowRuntime` — `requestRemoveSession`, `requestCloseTab`, `requestCloseOtherTabs`, `closePane`; one in `AppStateStore.closeSessionForXPC`; one in `QuitConfirmation.windowNeedsConfirmClose`; one in `RootWindowView`'s `WindowDelegate`) now reads `tab.needsConfirmClose` instead of `tab.terminal.needsConfirmClose`. Production behavior is unchanged: no production code ever sets the override, so every real `TabRuntime` still resolves through the (polyfilled, hard-coded `false`) `terminal.needsConfirmClose`.

**Rejected candidate 1** (`WindowRuntime`-level closure) because it explicitly covers only 4 of 7 sites by its own description — `AppStateStore.closeSessionForXPC`, `QuitConfirmation.windowNeedsConfirmClose` (`static`, no instance to hang a closure on without changing its shape), and the `RootWindowView` site would stay unexecutable, which is exactly the "partial coverage" the candidate list flagged as needing an explicit justification I couldn't give — three of seven branches staying dead code was not an acceptable trade for the marginally smaller diff.

**Rejected candidate 3** (protocol abstraction) as over-engineering for one `Bool`, per the candidate list's own note: `TabRuntime.terminal` is reached for far more than `needsConfirmClose` (title, cwd, bells, send/paste), so a protocol slice either balloons or splits `terminal` into two handles for no benefit here.

**Rejected candidates 4 and 5** (wait for upstream / ask upstream for the wrapper) on the orthogonality point the issue itself raises: even the day upstream ships a real, non-polyfilled `needsConfirmClose`, `BattyKitTests` still can't force a live surface's process into a "needs confirmation" state without spawning a real PTY — so neither retires the test-seam problem this issue is actually about. Whether an upstream PR should *also* happen is a separate, `production-signal` question — see the recommendation below — but it doesn't substitute for the seam.

**Observation-safety check** (per `docs/swiftui-observation-rules.md`): `needsConfirmCloseOverride` is `@ObservationIgnored`, so it participates in no Observation tracking. `needsConfirmClose` itself is a plain computed property with no macro-synthesized storage; its only read is `terminal` (a `let`, not `@Observable`-tracked as a value) and the ignored override. Every one of the seven call sites runs in a sweep, XPC dispatch handler, or `NSWindowDelegate` callback — none in `body`/`onChange`/`onGeometryChange` — so this introduces no new mutate-during-update surface.

**Seventh site correction**: `RootWindowView`'s `WindowDelegate.windowShouldClose` computed its `busyCount` inline, which would call `NSAlert.runModal()` (a blocking modal) if exercised end-to-end in a unit test with the override set true. Extracted the count into `WindowDelegate.busyTabCount(in:)` — mirroring the existing `QuitConfirmation.openTerminalTabCount` precedent, pulled out of `shouldQuitOrPrompt` for the identical reason — so the count is testable without ever calling `runModal()`.

**Coverage**: all seven sites are now unit-tested driving the confirmation/refusal branch via the override — `RequestCloseTabTests` (`requestCloseTab`, `requestCloseOtherTabs`), `AppStateStoreClosePaneTests` (`closePane` → `.needsConfirmation`), `RemoveSessionWatchEventTests` (`requestRemoveSession`), `AppStateStoreCloseSessionForXPCTests` and `AppXPCServiceCloseHideShowTests` (`closeSessionForXPC` → `.needsConfirmation`, at both the model and XPC-dispatch layers), `CrossWindowBehaviorTests` (`QuitConfirmation.windowNeedsConfirmClose`), and the new `WindowDelegateBusyTabCountTests` (`RootWindowView`'s extracted `busyTabCount`). None is blocked.

**`#if DEBUG` was considered and declined** for `needsConfirmCloseOverride`, for three reasons: `BattyKit/Sources/BattyKit/Testing/UITestDriver.swift:14` is a repo precedent for shipping a test affordance ungated rather than compile-conditioned; gating the override would make `needsConfirmClose`'s *shape* (does the fallback exist at all) configuration-dependent, which is a worse property for a safety guard than an unconditional `nil` default that provably collapses to the prior expression in every build; and a packaged Beta doesn't define `DEBUG`, so a `#if DEBUG` gate would create a Beta/unit-test divergence in exactly the code path this issue exists to make uniform across environments. Safety instead comes from `internal` visibility (a shipped `@testable` reach is uncompilable, not merely conventionally avoided) plus the `nil`-default/no-initializer/`init`-never-assigns argument above — verified independently by review round 1.

**Recommendation for the day the polyfill can go**: yes, an upstream wrapper change should follow (candidate 5) — the C symbols already ship, so exposing `needsConfirmClose`/`processExited` on `TerminalViewState` is the ~10-line gap the issue's investigation identified, not a Ghostty-side wait. That is orthogonal to this issue's seam and is not implemented here per the instruction not to touch `libghostty-spm`.

### The deletion cue this file predicted does not exist

`TerminalViewState+Polyfill.swift`'s doc comment claims that building
against a fork which declares these natively "will result in a
duplicate-member error — that's the cue to delete the polyfill". **That
claim is false**, demonstrated empirically: Swift gives a same-module
extension member priority over the imported type's own declaration,
silently and with no diagnostic. Resolving `needsConfirmClose` from a
*separate* module does report "ambiguous use", but the polyfill and its
one production call site (`TabRuntime.swift:294`) are both inside
`BattyKit`, so the re-pin will compile clean with the polyfill still
shadowing the real property.

So the re-pin must delete the polyfill deliberately. Checklist for that
work, whenever the fork change lands in a tagged release:

1. Bump `revision:` in `BattyKit/Package.swift`.
2. Delete `BattyKit/Sources/BattyKit/Util/TerminalViewState+Polyfill.swift`
   — no compiler error will prompt this.
3. Correct the stale comment at `RequestCloseTabTests.swift:10-19`.
4. The existing tests use `TabRuntime.needsConfirmCloseOverride` and are
   unaffected, but the *production* path goes live for the first time.
   Unit tests still cannot spawn a live process, so add a manual check
   with a real busy tab at that point.

Pushing the fork branch and opening its PR is the user's call; neither
has been done.
