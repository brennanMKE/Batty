# 0297 — Bell-triggered notification decisions leave no log trail, so there is no data to identify which sources generate unwanted notifications

| | |
|---|---|
| **Status** | open |
| **Module** | BellFeed |
| **Platform** | macOS |
| **First seen** | 2026-08-03 |

## Description

The user is getting many system notifications that are not meaningful and wants to filter them out — but there is no data to design the filter from. Nothing in the bell path emits a log record when a bell fires or when a notification-posting decision is made, so there is no way to pattern-match "which Session / Tab / process is generating the noise."

**This issue is instrumentation only: emit one log line per bell-triggered notification decision, with enough fields to support pattern analysis.** The filtering rules themselves are out of scope. Per this tracker's no-dangling-follow-ups rule, the filtering follow-up is deliberately *not* filed now — it gets filed when this instrumentation has produced findings to design against, and this issue's resolution notes should link it then.

The decision points to instrument (all verified against source):

- **BEL**: libghostty `RING_BELL` → `TerminalViewState.bellCount` → `PaneView.onChange` (`BattyKit/Sources/BattyKit/Views/PaneView.swift:132`) → `AppStateStore.recordBellTick(forTabID:)` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:615`), via `TabRuntime.recordBellTickIfNeeded()` delta-dedupe.
- **OSC 9 / OSC 777**: `TerminalViewState.lastDesktopNotificationAt` → `AppStateStore.recordDesktopNotification(forTabID:)` (`AppStateStore.swift:653`), which carries a message.
- **CLI `batty notify`** (#0284): `AppStateStore.recordCLINotification(tabID:title:body:playSound:)` — a third, non-escape-sequence source.
- All three converge on `postNotification(for:at:)` (`AppStateStore.swift:1155`) → `BellNotifier.post(for:...)` (`BattyKit/Sources/BattyKit/Runtime/BellNotifier.swift:65`).
- **System-generated entries are a separate class**: #0290's footprint warning shares the Bell Feed using the `BellFeedEntry.systemID` sentinel (`BellFeedStore.swift:34`) and posts via `BellNotifier.postFootprintWarning`, not `post(for:)`. The log must distinguish real bells from system entries or the analysis will conflate them.

Crucially, **recording a Bell Feed entry and posting a system notification are different decisions**, and the unwanted-notification complaint is about the latter. Suppression already happens at several points, and each is a fact worth logging: `postNotification` returns early on a nil notifier or `session.notificationsMuted`; `BellNotifier.post` returns early when `SettingsPreference.resolvedSystemNotifications()` is off or when `shouldPost` declines (app frontmost and entry already seen — `BellNotifier.swift:90`). A useful record therefore logs *the decision and its reason*, not just "a bell happened."

## Expected behavior

Every bell-triggered notification decision leaves exactly one log line through the project's standard file-scoped `Logger` (per `CLAUDE.md`: `nonisolated private let logger = Logger(subsystem: Logging.subsystem, category: "<Filename>")`; never `print`/`NSLog`), at a level that persists for later analysis — `.notice`, not `.debug`, since `.debug` is not persisted by default (#0294's `TerminalMetalMetricsLogger` chose `.notice` for exactly this reason).

The record should be greppable enough that the user can run something like:

```bash
log show --predicate 'subsystem == "co.sstools.Batty"' --last 1d
```

and eyeball a table for patterns.

**Fields, by availability at the log site (verified, not aspirational):**

Directly available today at `recordBellTick` / `recordDesktopNotification` / `recordCLINotification` / `postNotification`:

- Trigger kind — BEL vs OSC 9/777 vs CLI notify vs system entry (distinguished by call site).
- Window / Session / Pane / Tab / surface identity — all on the `BellFeedEntry` being constructed.
- Tab title at the time — `postNotification` already computes `tabLabel` (override → terminal title → "Tab N"); `location.session.title` likewise.
- Whether Batty was frontmost (`NSApplication.shared.isActive`) and whether the entry was seen-at-creation (`effectivelySeen`).
- The posting outcome: posted vs suppressed, and which gate suppressed it (session muted, notifications setting off, frontmost-and-seen, nil notifier).
- Message presence/content for OSC 9/777 and CLI entries.

Obtainable with modest extra plumbing:

- Foreground process: the 1.3.2 libghostty-spm bump (#0286) exposes `foregroundPid` (`tcgetpgrp` on the pty) and `ttyName` as public `TerminalView` properties (`TerminalView+Process.swift` in the package); `TabRuntime` holds `terminalNSView: AppTerminalView?`, so both are reachable at the log site. The process *name* needs a libproc lookup (`proc_name`/`proc_pidpath`) from the PID — feasible since the app is unsandboxed, but it is extra code; logging PID + tty alone already lets patterns be joined against `ps` output. Note both are nil until the surface has a process, and the PID is the foreground process *group* at the moment of logging, which for a bell delivered late (see timing note below) may no longer be the process that rang it.

Not reliably available: the full command line of what rang the bell — libghostty does not surface it; treat the OSC message / running-command display name / tab title as proxies.

## Notes

**Privacy (the main risk of this feature).** Tab titles, OSC 9 message bodies, and anything command-derived can contain sensitive text, and the unified log persists on disk. The implementation must use deliberate `privacy:` annotations rather than defaulting everything to `.public`: identifiers (UUIDs, PIDs, tty names), counts, trigger kind, and decision/outcome should be `.public` so they are pattern-matchable; titles, messages, and process/command names should be `.private` by default. That trade-off is real — private fields show as `<private>` in `log show`, which blunts the analysis — so the implementer should consider `.private(mask: .hash)` for titles/process names: stable hashes support "the same source keeps ringing" clustering without storing the text. Getting this wrong in the `.public` direction is worse than a weaker analysis.

**Always-on vs opt-in — recommendation: always-on.** The case for an env-var gate is #0294's `BATTY_LOG_METAL_LAYER_METRICS` precedent and log-volume discipline. But #0294 logs periodic per-surface metric dumps; this logs one line per bell-decision — a human-visible, feed-capped event (the Bell Feed itself caps at 200 entries). Even a pathologically noisy day is thousands of lines, which is negligible for the unified log. More importantly, the complaint is retrospective: the user notices "I've been getting junk notifications" *after* the fact, and an opt-in gate guarantees the data is missing at exactly that moment and forces a reproduce-under-flag cycle. One `.notice` line per decision, always on, with disciplined privacy annotations, is the right trade. If review disagrees, the fallback is on-by-default with an env var to *disable*.

**Suggested log site.** A single choke point beats scattering: `postNotification(for:at:)` sees every real-tab path (all three triggers) plus the suppression facts, and `BellNotifier.post`'s internal gates would need to report their verdict back or log their own line — simplest is one line at `postNotification` for the record/attempt and one at `BellNotifier.post`/`postFootprintWarning` for the final posted/suppressed outcome, both `.notice`, category per filename per the logging convention. Implementer's call, as long as one bell = one analyzable decision record and system entries are labeled.

**Bells that never reach a view.** The BEL path routes through `PaneView.onChange`, i.e. view-driven observation. The chosen log site should sit in the runtime layer (`AppStateStore`/`BellNotifier`), not the view, so the record survives any future rerouting of that observation — and so unit tests can assert on it without UI.
