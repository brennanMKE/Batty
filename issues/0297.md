## Description

The user is getting many system notifications that are not meaningful and wants to filter them out — but there is no data to design the filter from. Nothing in the bell path emits a log record when a bell fires or when a notification-posting decision is made, so there is no way to pattern-match "which Session / Tab / process is generating the noise."

**This issue is instrumentation only: emit one log line per bell-triggered notification decision, with enough fields to support pattern analysis.** The filtering rules themselves are out of scope. Per this tracker's no-dangling-follow-ups rule, the filtering follow-up is deliberately *not* filed now — it gets filed when this instrumentation has produced findings to design against, and this issue's resolution notes should link it then.

The decision points to instrument (all verified against source):

- **BEL**: libghostty `RING_BELL` → `TerminalViewState.bellCount` → `PaneView.onChange` (`BattyKit/Sources/BattyKit/Views/PaneView.swift:132`) → `AppStateStore.recordBellTick(forTabID:)` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:615`), via `TabRuntime.recordBellTickIfNeeded()` delta-dedupe.
- **OSC 9 / OSC 777**: `TerminalViewState.lastDesktopNotificationAt` → `AppStateStore.recordDesktopNotification(forTabID:)` (`AppStateStore.swift:653`), which carries a message.
- **CLI `batty notify`** (#0284): `AppStateStore.recordCLINotification(tabID:title:body:playSound:)` — a third, non-escape-sequence source.
- All three converge on `postNotification(for:at:)` (`AppStateStore.swift:1155`) → `BellNotifier.post(for:...)` (`BattyKit/Sources/BattyKit/Runtime/BellNotifier.swift:65`).
- **System-generated entries are a separate class**: #0290's footprint warning shares the Bell Feed using the `BellFeedEntry.systemID` sentinel (`BellFeedStore.swift:34`) and posts via `BellNotifier.postFootprintWarning`, not `post(for:)`. The log must distinguish real bells from system entries or the analysis will conflate them.

Crucially, **recording a Bell Feed entry and posting a system notification are different decisions**, and the unwanted-notification complaint is about the latter. Suppression already happens at several points, and each is a fact worth logging: `postNotification` returns early on a nil notifier or `session.notificationsMuted`; `BellNotifier.post` returns early when `SettingsPreference.resolvedSystemNotifications()` is off or when `shouldPost` declines (app frontmost and entry already seen — `BellNotifier.swift:90`). A useful record therefore logs *the decision and its reason*, not just "a bell happened."

## Expected behavior

**Superseded twice, landing on a manual-export design (user directive, mid-implementation) — this replaces both the always-on-`Logger` text and the Settings-toggle-gated verbatim-`Logger` text that preceded it.** Nothing is written to the unified log, to disk, or anywhere else the user didn't explicitly direct it. Instead:

- **`AppStateStore.bellDecisionHistory`** (`BellDecisionHistory`, `BattyKit/Sources/BattyKit/Runtime/BellDecisionHistory.swift`) is an in-memory ring buffer holding the most recent **1000** bell-triggered notification decisions, oldest-first eviction once full. Every real-tab bell path (BEL, OSC 9/777, CLI `notify`) still converges on `AppStateStore.postNotification(for:at:trigger:playSound:)`, which is the single capture point — one bell = one `BellDecisionRecord` appended.
- **Collection is unconditional** — no Settings toggle, in both Prod and Beta. The privacy question that motivated a toggle in the two earlier designs (writing user content to a persistent, system-wide log) doesn't exist for a buffer that never leaves process memory; a toggle defaulting off would only guarantee the buffer is empty exactly when the user, noticing noise after the fact, reaches for it.
- **Settings → Advanced → Diagnostics** (`BellDecisionExportRow` in `SettingsView.swift`) is the only way this data leaves the process: **Copy** to the pasteboard, **Save to File…** via a standard `NSSavePanel` (never a fixed path), and **Clear**. A live count ("N of 1000 collected") reflects the buffer as bells arrive while Settings is open.
- **Export text** (`BellDecisionFormat.exportText`/`.format`) is one line per decision, newest-first, stable field order — greppable and sortable in a text editor, with a one-line `#`-comment header (export time, record count, a note that `bellAt` is UTC) so a saved file is self-describing out of context. `sessionTitle`, `tabLabel`, and `message` are written **verbatim** (quoted, with `\`/`"`/newlines escaped) rather than hashed: the user reviews this themselves, deliberately, after choosing to export it, so a digest with no stable join key (Session/Pane/Tab UUIDs aren't persisted between launches; a live `batty list` join only shows a tab's *current* title) would defeat the point. A stable FNV-1a digest is kept alongside each of those three fields as a secondary clustering aid. All three are also bounded to 500 characters **at capture time** (`BellDecisionFormat.truncateForRetention`, called from `AppStateStore.makeBellDecisionRecord`), not just at format time — round-1 review flagged storing more per field as unbounded dead weight (×1000 records, held for the process lifetime, with nothing bounding an OSC 9/777 or CLI `notify` body upstream); truncating the raw text at the export's own display limit is lossless since escaping only ever expands a character.

**Fields, by availability at the capture site (verified, not aspirational):**

Directly available today at `recordBellTick` / `recordDesktopNotification` / `recordCLINotification` / `postNotification`:

- Trigger kind — BEL vs OSC 9/777 vs CLI notify vs system entry (distinguished by call site; system entries never reach `postNotification` at all — see Relation).
- Window / Session / Pane / Tab / surface identity — all on the `BellFeedEntry` being constructed.
- The bell's own timestamp (`BellFeedEntry.timestamp` / `location.tab.lastBellAt`) — distinct from capture time, so #0288's occluded-Tab poll skew (below) is visible in the data rather than merely documented here.
- Tab title at the time — `postNotification` already computes `tabLabel` (override → terminal title → "Tab N"); `location.session.title` likewise.
- Whether Batty was frontmost (`NSApplication.shared.isActive`) and whether the entry was seen-at-creation (`effectivelySeen`).
- The outcome: submitted vs suppressed, and which gate suppressed it (session muted, notifications setting off, frontmost-and-seen, nil notifier).
- Message presence/content for OSC 9/777 and CLI entries.

Obtainable with modest extra plumbing:

- Foreground process: the 1.3.2 libghostty-spm bump (#0286) exposes `foregroundPid` (`tcgetpgrp` on the pty) and `ttyName` as public `TerminalView` properties (`TerminalView+Process.swift` in the package); `TabRuntime` holds `terminalNSView: AppTerminalView?`, so both are reachable at the capture site. The process *name* needs a libproc lookup (`proc_name`/`proc_pidpath`) from the PID — feasible since the app is unsandboxed, but it is extra code; capturing PID + tty alone already lets patterns be joined against `ps` output. Note both are nil until the surface has a process, and the PID is the foreground process *group* at the moment of capture, which for a bell delivered late (see the #0288 timing note) may no longer be the process that rang it. Still deferred — not implemented.

Not reliably available: the full command line of what rang the bell — libghostty does not surface it; treat the OSC message / running-command display name / tab title as proxies.

## Resolution notes

> 🟢 Resolved 2026-08-03 — every bell-triggered notification decision is captured to an in-memory ring of the most recent 1000, exportable from Settings via Copy or Save to File.

Instrumentation only. The filtering follow-up is #0298, and this export is the intended way to design its rule against real traffic rather than guesswork.

## Root cause

The user was getting many notifications that were not meaningful and wanted to filter them, but there was no record of what generated them. `BellFeedStore` kept entries; nothing recorded the *decision* — which trigger fired, which suppression gate it passed, and whether a system notification was actually posted.

## Fix

- **`BellDecisionHistory`** — a `@MainActor @Observable` ring buffer of the most recent 1000 `BellDecisionRecord`s, oldest-first eviction, with `clear()`.
- **`BellDecisionFormat`** — a pure formatter (`format`, `exportText`, `quotedField`, `stableDigest`, `truncateForRetention`). One line per decision, stable field order, newest-first.
- **`AppStateStore.postNotification`** — the single choke point all three trigger paths funnel through — records unconditionally, **above** every suppression guard, so suppressed decisions are captured too. That was the point: the user's complaint is about notifications that *survived* the gates, so the log must show which gate each one passed.
- **Settings → Advanced → Diagnostics** — live "N of 1000 collected", Copy, Save to File… (`NSSavePanel`), Clear.

Captured per decision: trigger kind (BEL / OSC 9 / CLI), session / pane / tab / window ids, `bellAt`, verbatim session title, tab label and message body (500-char bound), stable digests alongside for clustering, foreground PID and tty, `battyActive`, `seenAtCreation`, and each gate's outcome.

## Review

Reviewed by claude-opus-5 over three rounds, across **two design redirects from the user**.

The original design was an always-on OSLog record. Round 1 blocked: the implementation hashed titles and message bodies, and the reviewer traced that the identification path does not close — session/pane/tab UUIDs are not persisted anywhere, `tabLabel` at bell time differs from the current title precisely when it is informative, and for OSC/CLI notifications **the message body *is* the source identity** with no join at all. A recurring digest would tell the user they had one noisy source and nothing about what it was.

The user then redirected to the current shape: no OSLog, an in-memory ring, manual export. That removed the privacy problem wholesale — nothing persists anywhere the user did not deliberately put it — and made the enable toggle's rationale disappear, so collection became unconditional.

Round 2 blocked on two items. `Save to File…` used `try?`, so a failed write closed the panel and the user believed it had saved — on the deliverable path, never once run. And the buffer stored the three text fields **untruncated**, truncating only at format time, retaining unbounded text ×1000 records for the process lifetime — in a project whose active umbrella is unbounded memory growth.

Round 3 approved, having re-measured both mutations and verified grapheme-safe truncation empirically with a 501-cluster ZWJ emoji string.

## Gotchas

- **Nothing persists until you act.** The decision history is an in-memory ring buffer only — never written to the unified log, to disk, or to any file on its own. It leaves the process solely through Settings → Advanced → Diagnostics: **Save to File…** (a standard `NSSavePanel`, never a fixed path; cancelling writes nothing) or **Copy**. A failed save surfaces an alert and logs under category `SettingsView` instead of failing silently.
- **Copy is a real exposure.** The pasteboard is readable by every running app, and with Handoff enabled the text can sync to your other devices. The export contains session titles, tab labels, and OSC 9/777 and `batty notify` message bodies **verbatim**, not hashed — deliberate, because a digest has no stable join key across launches, but it means the text carries whatever your terminal put there. Prefer Save to File… over Copy for anything sensitive.
- **Session-lifetime retention.** Collection is unconditional — there is no on/off toggle — and the buffer holds the most recent 1000 decisions. **Clear** or quitting Batty are the only ways to drop what has been collected.
- **500-character field bound.** `sessionTitle`, `tabLabel` and `message` are each truncated to 500 characters *at capture time*. Caveat when reading an export: a field that was cut renders a `…` marker only if its first 500 characters contained a `\`, `"`, or newline. A cut plain-text field shows 500 characters with **no** marker, so a field ending at exactly 500 characters may or may not have been longer. Content shown is always correct; only the truncation *signal* can be absent. The code's "provably lossless" doc comment refers to content, not to the marker.
- **`outcome=submitted` means submitted, not seen.** It records that Batty handed the notification to `UNUserNotificationCenter`. Focus modes, Notification Summary and per-app settings can still hold or drop it downstream. Read it as "Batty tried."
- **`bellAt` can lag the real bell by up to 500 ms (#0288).** Bells in occluded Tabs are delivered by `OccludedSurfaceTicker`'s 500 ms poll rather than a live callback. `bellAt` is exported specifically so that skew is visible rather than hidden; do not treat sub-second ordering as exact. `bellAt` is UTC; the suggested save filename's timestamp is local.
- **Still needs your eye.** No one has rendered this UI. Verify by hand: the Diagnostics section appears in Settings → Advanced; the "N of 1000 decisions collected" count updates live as bells arrive while Settings is open; Copy / Save to File… / Clear behave sensibly on an empty buffer; the caption is not clipped at the default Settings window size; and a real saved file opens as one greppable line per decision.

## Notes

**Privacy (the main risk of this feature).** Tab titles, OSC 9 message bodies, and anything command-derived can contain sensitive text, and the unified log persists on disk. The implementation must use deliberate `privacy:` annotations rather than defaulting everything to `.public`: identifiers (UUIDs, PIDs, tty names), counts, trigger kind, and decision/outcome should be `.public` so they are pattern-matchable; titles, messages, and process/command names should be `.private` by default. That trade-off is real — private fields show as `<private>` in `log show`, which blunts the analysis — so the implementer should consider `.private(mask: .hash)` for titles/process names: stable hashes support "the same source keeps ringing" clustering without storing the text. Getting this wrong in the `.public` direction is worse than a weaker analysis.

**Superseded by round-1 review, after the enablement change above.** This paragraph was written against an always-on, every-Prod-install log; the toggle (default off in Prod, opt-in even in Beta, which is a locally-run non-distributed build per #0279) changed the exposed population to one person, on their own machine, about their own terminal, who deliberately turned it on. Under that premise, hashing failed the feature's own goal: Session/Pane/Tab UUIDs are not persisted between launches (no workspace persistence for the layout tree), `tabLabel` at bell time can differ from a live `batty list` join, and `message` — the actual source identity for OSC 9/CLI entries ("Claude Code is waiting for your input", a build-failure body) — has no join at all. A digest recurring N times says "one noisy source," never what it is, which reintroduces the reproduce-under-flag cycle this section's "always-on" argument was written to avoid — through the privacy dimension instead of the enablement one. The shipped behavior: `sessionTitle`, `tabLabel`, and `message` are logged **verbatim** (quoted, escaped, length-bounded), with a stable FNV-1a digest kept alongside each as a secondary clustering aid. See `BellDecisionFormat.format`'s doc comment (`BattyKit/Sources/BattyKit/Runtime/BellDecisionHistory.swift` — this file was later renamed and the design itself superseded again; see Expected Behavior) for the reasoning that carried forward, and the Settings caption (`BellDecisionExportRow` in `SettingsView.swift`, successor to the `BellDecisionLoggingRow` this paragraph originally referred to) for the user-facing warning this requires. The per-field `privacy:` prescription in the Expected Behavior section was also not followed as literally written — the line is composed as one pre-escaped string in a pure, testable function rather than through `Logger`'s own per-argument `privacy:` interpolation, for reasons unrelated to this reversal (OSLog's redaction isn't introspectable from a unit test); see the same doc comment.

**Always-on vs opt-in — recommendation: always-on.** The case for an env-var gate is #0294's `BATTY_LOG_METAL_LAYER_METRICS` precedent and log-volume discipline. But #0294 logs periodic per-surface metric dumps; this logs one line per bell-decision — a human-visible, feed-capped event (the Bell Feed itself caps at 200 entries). Even a pathologically noisy day is thousands of lines, which is negligible for the unified log. More importantly, the complaint is retrospective: the user notices "I've been getting junk notifications" *after* the fact, and an opt-in gate guarantees the data is missing at exactly that moment and forces a reproduce-under-flag cycle. One `.notice` line per decision, always on, with disciplined privacy annotations, is the right trade. If review disagrees, the fallback is on-by-default with an env var to *disable*.

**Suggested log site.** A single choke point beats scattering: `postNotification(for:at:)` sees every real-tab path (all three triggers) plus the suppression facts, and `BellNotifier.post`'s internal gates would need to report their verdict back or log their own line — simplest is one line at `postNotification` for the record/attempt and one at `BellNotifier.post`/`postFootprintWarning` for the final posted/suppressed outcome, both `.notice`, category per filename per the logging convention. Implementer's call, as long as one bell = one analyzable decision record and system entries are labeled.

**Bells that never reach a view.** The BEL path routes through `PaneView.onChange`, i.e. view-driven observation. The chosen log site should sit in the runtime layer (`AppStateStore`/`BellNotifier`), not the view, so the record survives any future rerouting of that observation — and so unit tests can assert on it without UI.
