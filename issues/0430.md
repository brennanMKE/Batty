## Description

This is the Git Status / scanner child of umbrella [#0427](0427.md), and it is **blocked by [#0428](0428.md)** (the shared clock, readiness helper, completion-signal conventions and reap gate). It covers 29 sites. `GitStatusPaneContent` debounces through a real `Task.sleep(nanoseconds: debounceNanoseconds)` (`Runtime/GitStatusPaneContent.swift:761`). It exposes `handledScanResultCount` (`:669`) and `awaitPendingTeardownReapsForTesting()` (`:397`), but no scan-completion event. So the tests poll `waitUntil` to a 15s deadline, use a real scan delay to hide mid-scan, and rely on 20–30ms windows to show that nothing deferred or periodic happened.

Work: route the debounce and all deferred/periodic work through #0428's clock protocol, so the fake's pending-work count becomes the "nothing scheduled" proof. Add a scan-handled event in the shape #0428's conventions prescribe. Gate the fake scanner with a continuation. Then rewrite each row below.

### Round 2 (review response, commit `07306c33`)

Fixed all five findings from round 1 (Opus review):

- **B1 (`drainMainActorQueue` was a forbidden Task-hop-count poll).** Deleted
  it entirely. The three "nothing happened" tests
  (`createdHiddenNeverAcquiresAWatcherOrScans`, `redundantShowDoesNotDoubleAcquireOrDoubleRefresh`,
  `setVisibleAfterTearDownIsRejectedAndDoesNothing`) now assert synchronously,
  right after the call under test, using two new production test-only
  accessors on `GitStatusPaneContent`: `hasNoScheduledOrAcquiredWorkForTesting`
  (`watcher`/`debounceTask`/`scanTask` all nil — meaningful only when nothing
  has ever run, or everything was already torn down, since a completed
  `Task` reference is never nilled back on success) and `generationForTesting`
  (the activation counter, for the redundant-show case where `scanTask` is
  already non-nil from a legitimate prior scan). All three tests also inject
  `TestClock` and assert `clock.pendingCount == 0`.
  - **Scope decision:** a bare, untracked `Task { self.activate() }` —
    assigned to none of `watcher`/`debounceTask`/`scanTask` — cannot be
    observed without waiting on real time, which `AGENTS.md` forbids — that
    gap is accepted, not closed, and is documented on
    `hasNoScheduledOrAcquiredWorkForTesting`'s own doc comment. **Correction
    (round 3 review, B6):** the original wording here and on five other
    comments claimed `clock.pendingCount == 0` extends this same catch to
    "any clock-routed deferred work." That's false: `TestClock` only
    registers a sleeper once a `Task`'s body actually reaches `await
    clock.sleep(for:)`; a `Task` that hasn't been scheduled to run yet —
    tracked or not — has registered nothing, so `pendingCount == 0` cannot
    tell "correctly did nothing" apart from "scheduled something that
    hasn't started." Merely routing through the clock, on its own, proves
    nothing synchronously. The "deferred activate" mutation these tests are
    required to catch (`## Done when`) is re-expressed as one that *is*
    observable with no wait for a different reason: `setUp`'s hidden branch
    scheduling `debounceTask = Task { await clock.sleep(for: .seconds(1));
    self?.activate() }` instead of doing nothing is caught because the
    `Task` *object itself* is assigned to the tracked `debounceTask`
    property synchronously, at the point of assignment — not because
    anything registered on the clock. See the mutation table below.
- **B2 (hang-guard lived in production, no cancellation).** Deleted
  `awaitScanResultHandledForTesting` and its `scanHandledWaiters` dictionary
  from `GitStatusPaneContent.swift` entirely. Production now exposes only
  the bare event: `onScanResultHandledForTesting: ((Int) -> Void)?`, fired
  once per `handleScanResult` call, `nil` by default, never read or set by
  production code. The bounded wait moved into `BattyKitTests` as
  `ScanHandledSignal` (`nonisolated final class ... : @unchecked Sendable`),
  using the shared `ResumeOnce` + a cancellable `DispatchWorkItem`, matching
  `ChildProcessReadiness`'s own shape.
  - **A real bug surfaced while fixing this, unrelated to the review
    finding itself:** the first version of `ScanHandledSignal` had a
    lost-wakeup race. `Package.swift` sets `.defaultIsolation(MainActor.self)`
    for this whole package, so a bare `nonisolated func`/method actually
    runs on the global *concurrent* executor, not "wherever" — calling
    `await signal.wait(bound:)` from `@MainActor` code is a genuine executor
    hop, not a synchronous call. If the real scan completed (on MainActor,
    via `handleScanResult`) and called `signal.signal()` *before* `wait()`'s
    own hop had landed and registered its continuation, the signal found no
    waiter, did nothing, and `wait()` then only ever resolved via its 15s
    timeout — this was caught empirically as a *mutation-triggered* false
    failure (adding an unrelated, harmless extra `Task` inside `activate()`
    changed MainActor scheduling enough to flip the race's usual outcome).
    Fixed by adding an `isSignaled` flag, checked both before creating the
    continuation and *again inside* its registration closure — the same
    "check again inside the closure" idiom `TestTeardownReapGate.waitUntilOpen()`
    already uses for the identical concurrent-`open()` race. Also separately
    confirmed (via a temporary, since-deleted test) that `ScanGate`'s own
    `waitForScanStarted` — already `nonisolated` since round 1 — has no such
    bug: it already checked `hasStarted` inside its continuation closure.
  - The runtime crash this design avoids was also reproduced directly (a
    throwaway scratch test, since deleted): resuming a `CheckedContinuation`
    created inside a bare `@MainActor`-isolated function, from the
    background `DispatchQueue` a hang-guard timeout fires on, traps with
    `EXC_BREAKPOINT`/`SIGTRAP` in `dispatch_assert_queue_fail` — because the
    timeout closure, written lexically inside `@MainActor` code, is itself
    inferred `@MainActor`-isolated, and that closure runs on a raw GCD
    thread with no Swift Task/executor hop to reconcile the mismatch. Kept
    entirely on a `nonisolated` type, as `ScanHandledSignal` now is, this
    cannot happen — matching why `TestClock`/`TestTeardownReapGate`/
    `ChildProcessReadiness`/`ScanGate` are all explicitly `nonisolated` too.
- **B3 (failure branches released nothing).**
  - `rapidWatcherEventsCoalesceIntoOneScanAfterTheDebounceWindow`'s
    `waitForSleepers(1)` failure branch now calls `content.tearDown()`.
  - `hidingDuringAnInFlightScanDiscardsItsResult`'s `waitForScanStarted()`
    failure branch now calls `gate.release()` then `content.tearDown()`.
  - `ProcessGitStatusScannerTests`'s three bare

  `#expect(await clock.advance(by: ...) == 1)` and, after the scan-handled
  wait, `#expect(clock.pendingCount == 0)`.

  - `handledScanResultCount`'s doc comment no longer cites the deleted

  - `hidingAnActivePaneStopsTheWatcherAndSuspendsToZeroPeriodicWork`'s

  - `docs/async-test-seams.md` §4's table: moved "Git Status scan-handled"

## Gotchas

- **Accepted scope limit (orchestrator decision).** An *untracked* `Task { await clock.sleep(...); activate() }` that has not started yet cannot be detected without waiting: `TestClock` registers a sleeper only once the Task body reaches `sleep(for:)`. Only work assigned to `watcher`, `debounceTask` or `scanTask` is caught. The issue's "deferred activate" mutation is re-expressed through the tracked seam.
- **Default isolation.** This package defaults to MainActor isolation, so a bare `nonisolated` async function really does hop executors. A signal can fire before `wait()` registers, so check an `isSignaled` flag both before registering and inside the registration closure.
- **Follow-up, not fixed here.** `registryDrainReapsAStubbornProcessWithNoWaitForPendingTeardownCall` doesn't isolate the registry's own SIGKILL, because the scanner's detached reap kills the process concurrently. Injecting a closed `TestTeardownReapGate` would isolate it.
