## Description

Publish the three hosted Background Sets on batty.sstools.co: the 15 full-size PNGs, a thumbnail for each made from it, and a `catalog.json` that lists them with `sha256` and `bytes`. Add a check script that fails when the catalog and the files disagree, and run it before every deploy. Child of [#0574](0574.md), which defines the catalog format this checks. Targets 1.4.0.

What is on `main` now (37704a2b):

- `website/backgrounds/catalog.json`: 3 sets (`future-cities`, `cool-vehicles`, `beautiful-landscapes`) of 5 images each. It has no `sha256` and no `bytes`, and none of the 30 files it names exist yet.
- `docs/background-image-prompts.md`: the prompts, the file names, the output size (3840 × 2400 PNG, or the largest 16:10 size the generator supports, recorded) and the thumbnail rule: 480 × 300, made with `sips`, never generated.

**Blocked on the images.** The user is generating them with Codex. Until they are in `website/backgrounds/<set>/`, only the check script and its self-test can land.

## Work

1. **Images.** Put each PNG at the path its prompt names. If a generator size other than 3840 × 2400 was used, record it in the prompts doc and set `width`/`height` in the catalog to match.
2. **Thumbnails.** Make each one from its full-size image, as the prompts doc says, for example `sips -z 300 480 01-skyline-fog.png --out 01-skyline-fog-thumb.png`. A thumbnail must be PNG and must keep the full-size image's aspect ratio. `sips -z` forces the size, so a non-16:10 source would be distorted, and the check catches that.
3. **Catalog.** Fill in `sha256` and `bytes` for every `full` and `thumbnail`, using the script's write mode (below), and set `updated`.
4. **Check script**, `tools/check-backgrounds.py`. It goes in `tools/`, not `scripts/`, which is a restricted area. Run as `python3 -I tools/check-backgrounds.py [--write] website/backgrounds/catalog.json`. It exits 0 when everything passes and 1 with one line per problem otherwise. It uses the standard library only, and reads PNG dimensions from the `IHDR` chunk, with no `sips` dependency, so it also runs on Linux. It checks:
   - the JSON parses, `schemaVersion` is 1, and every required field from #0574 is present with the right type;
   - set ids are unique, and image ids are unique across the whole catalog and match `^[a-z0-9][a-z0-9-]{0,63}$`;
   - every `url` is relative, and resolves to a file inside `website/backgrounds/`, with no `..` escape and no absolute or `http:` URL in the built-in catalog;
   - every file exists, starts with the PNG signature, and its `IHDR` width and height equal the catalog's;
   - `sha256` and `bytes` are present and match the file;
   - each thumbnail's aspect ratio equals its full-size image's (within 1%), and its longest side is at most 1024;
   - each full-size image is no wider or taller than 4096 (`TerminalBackgroundImageImporter.maxPixelSize`; larger works but is downscaled in Batty, so it's a waste), and at most the full-size byte limit #0577 sets;
   - no PNG under `website/backgrounds/` is missing from the catalog (an orphan file is an error, since `rsync` would publish it).

   `--write` fills in or corrects `sha256` and `bytes` only, keeps key order and the existing formatting style, then runs the checks. Add `tools/check-backgrounds-selftest.py`, in the style of `tools/worklog-selftest.py`, with fixtures under a temporary folder for: a good catalog, a missing file, a wrong dimension, a wrong hash, a duplicate id, a `..` URL and an orphan PNG.
5. **Documentation.** Under a "Background images" section in `website/README.md`, describe how to add an image (generate, `sips`, `--write`, check, deploy). Add a line pointing at it in `docs/background-image-prompts.md`.
6. **Privacy page.** `website/privacy.html` says, under "Network requests", that Batty makes "exactly one kind of outbound network request", the Sparkle appcast fetch. That stops being true in 1.4.0. Add the background catalog requests: what is fetched (the built-in catalog, thumbnails, and full-size images only on request), from where (batty.sstools.co, and any catalog URL the user adds), how often (per the answer to #0574 open question 2), and how to stop it. Also say that no identifying data is sent beyond what any HTTPS request carries. Ship this with or before the 1.4.0 release.

## Deploy (shared state: the user's go-ahead each time)

Deploying the website changes a live, shared system, so it needs the user's explicit go-ahead every time (AGENTS.md "Authoring rules"). An agent does not deploy on its own.

- Run `python3 -I tools/check-backgrounds.py website/backgrounds/catalog.json` first. Don't deploy if it fails.
- Two deploy routes exist and they disagree. `scripts/deploy-website.sh` (documented in `scripts/RELEASE.md` step 7) runs `rsync --delete` to `$BATTY_EC2_HOST:$BATTY_EC2_PATH`. The route used in practice is `rsync -avz` **without `--delete`** to `photon:/var/www/vhosts/batty.sstools.co/`, after a `-n` dry run, because `--delete` would wipe the older DMGs on the server: local `website/downloads/` holds only the current one, since DMGs are gitignored. The user picks the route.
- After deploying, check with `curl -sI` that `https://batty.sstools.co/backgrounds/catalog.json` returns 200, with `Content-Type: application/json` and an `ETag` or `Last-Modified` header (#0577's refresh depends on one), and that one full-size and one thumbnail URL return 200 with the expected `Content-Length`.
- Wiring the check into `scripts/deploy-website.sh` would edit a restricted file. Ask the user before doing it.

## Open questions

1. **Commit the PNGs to git?** 15 full-size PNGs are likely 150 to 300 MB (#0574 open question 1), and every replaced image adds its full size to history. DMGs are kept out with `.gitignore` (`*.dmg`), and so are the demo videos (`website/demo/*.mp4`). Options: commit them (simple, and `rsync` sees them), add them to `.gitignore` and keep the source of truth somewhere else, or use Git LFS. Thumbnails and `catalog.json` are small and should be committed either way.
2. **Should the server set cache headers** for `backgrounds/` (for example, a long `max-age` on PNGs, and `no-cache` with validators on `catalog.json`)? That is Apache config on the host, outside the repo.

## Acceptance criteria

1. `python3 -I tools/check-backgrounds.py website/backgrounds/catalog.json` exits 0 on `main` once the images are in, and the self-test passes.
2. Deleting a thumbnail, editing one byte of a full-size image, or changing one `width` each makes the check exit 1 and name the problem.
3. Opening `https://batty.sstools.co/backgrounds/catalog.json` in a browser after the deploy shows the catalog, and each `full` and `thumbnail` URL in it opens the right picture.
4. Each thumbnail looks like a small, undistorted version of its full-size image.
5. `https://batty.sstools.co/privacy.html` describes the background catalog requests.
