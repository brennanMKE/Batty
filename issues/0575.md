### Files

**1. `tools/check-backgrounds.py` (new), Python 3, standard library only, executable, `#!/usr/bin/env python3`.**

Usage: `python3 -I tools/check-backgrounds.py [--write] website/backgrounds/catalog.json`. The catalog's folder is the **root**. Every URL resolves inside it. Output is one line per problem, `<json path>: <problem>`, for example `sets[0].images[2].full: missing file future-cities/03-sky-gardens-dawn.png`, then a summary line: `N problems (M of K files missing)` or `OK: S sets, I images, K files`. Exit 0 when there are no problems, 1 when there are any (an unreadable or unparseable catalog included), 2 for a usage error (argparse's default).

Structure it so the self-test can import it with `importlib.util.spec_from_file_location`, the way `tools/worklog-selftest.py` loads `worklog.py`. No work at import time. `main(argv)` returns the exit code, behind `if __name__ == "__main__": sys.exit(main(sys.argv[1:]))`. Top-level functions:

- `image_info(data: bytes) -> (kind, width, height) | None`. `kind` is `"png"` or `"jpeg"`.
  - PNG: the 8-byte signature `\x89PNG\r\n\x1a\n`, then the first chunk must be `IHDR` (length 13). Width and height are big-endian `uint32`s.
  - JPEG: starts with `FF D8 FF`. Walk the markers from offset 2: skip `FF` fill bytes, skip standalone markers (`D0`–`D7`, `01`), read each segment's 2-byte length, and stop at the first SOF marker (`C0`–`CF` except `C4`, `C8`, `CC`). Height is at segment offset +3 and width at +5, both big-endian `uint16`. Hitting `SOS` (`DA`) or the end of the data first means no SOF was found. Return `None`. Bounds-check every read, so truncated or garbage input returns `None` and never raises.
- `check(catalog_path) -> list[str]`: every problem, in catalog order, then orphans.
- `write(catalog_path) -> list[str]`: the `--write` text rewrite (below), then `check`.
- Limits as module constants, so the self-test can lower them: `FULL_MAX_PIXELS = 4096` (`TerminalBackgroundImageImporter.maxPixelSize`, in `BattyKit/Sources/BattyKit/Settings/TerminalBackgroundImageImporter.swift:28`), `FULL_MAX_BYTES = 50 * 1024 * 1024` and `THUMB_MAX_BYTES = 2 * 1024 * 1024` (#0577's limits table), `THUMB_MAX_PIXELS = 1024`, `ASPECT_TOLERANCE = 0.01`. Say in a comment where each one comes from. These describe hosted files, so they aren't shared with the Swift code.

Checks, in this order:

1. **Parse.** The file reads as UTF-8 and `json.loads` succeeds. If not, report `catalog: <error>` and stop, since nothing else can run.
2. **Schema (#0574 "Catalog format").** Report the first bad path in each object, and keep going through siblings.
   - Top level: `schemaVersion` is an `int`, not a `bool`, and equals 1. `name` is a string of 1–100 characters after `strip()`. `updated`, when present, matches `^\d{4}-\d{2}-\d{2}$`. `homepage`, when present, starts with `https://`. `sets` is a list of 1–50.
   - Set: `id` matches `^[a-z0-9][a-z0-9-]{0,63}$`. `title` has 1–100 characters. `description`, when present, is a string of at most 300 characters. `images` is a list of 1–100.
   - Image: `id` uses the same pattern. `title` has 1–100 characters. `credit`, when present, has at most 200. `full` and `thumbnail` are objects.
   - File: `url` is a string. `width` and `height` are positive `int`s, not `bool`s. `sha256`, when present, matches `^[0-9a-f]{64}$`. `bytes`, when present, is a non-negative `int`, not a `bool`.
   - Unknown fields are ignored, as #0574 requires.
3. **Unique ids.** Set ids are unique. Image ids are unique across the **whole catalog**. Report each duplicate with both paths. Also report a `url` used by more than one file entry, which would also break `--write`.
4. **URL.** The `url` is relative: it has no scheme (`urllib.parse.urlsplit(url).scheme == ""`), no netloc, no query or fragment, no leading `/`, no `\`, no empty segment, and no `.` or `..` segment. It ends in `.png`, `.jpg` or `.jpeg`, lowercase. As a second guard, `(root / url).resolve()` must be relative to `root.resolve()`. Any URL that fails is reported and not opened.
5. **File.** It exists and is a regular file. If it's missing, report `missing file <url>` and skip the remaining checks for that entry. Otherwise `image_info` must recognize it, and its kind must match the extension (`.png` means PNG, `.jpg`/`.jpeg` means JPEG). For example: `future-cities/01-skyline-fog.png is JPEG data, not PNG`. Its width and height must equal the catalog's: `width 3840 in catalog, 3000 in file`.
6. **Hash and size.** `sha256` and `bytes` are present, and they equal `hashlib.sha256(data).hexdigest()` and `len(data)`. A missing value reports `sha256 missing (run with --write)`.
7. **Limits.** Full: width and height are at most `FULL_MAX_PIXELS`, and the file is at most `FULL_MAX_BYTES`. Thumbnail: the longest side is at most `THUMB_MAX_PIXELS`, the file is at most `THUMB_MAX_BYTES`, and `abs(tw/th - fw/fh) / (fw/fh) <= ASPECT_TOLERANCE`, using the catalog's dimensions. Skip the aspect check when either entry failed step 2. The thumbnail may be a different format from its full-size image.
8. **Orphans.** Walk `root` recursively. Every regular file that isn't `catalog.json`, isn't hidden (no path component starting with `.`) and isn't named by a valid catalog `url` is reported: `orphan file <relative path> (not in catalog; rsync would publish it)`. This covers every file type, not just images, because `rsync` publishes them all. Hidden files such as `.DS_Store` are skipped.

`--write` fills in or corrects `sha256` and `bytes` **only**, and keeps the file's existing text everywhere else:
- It parses the JSON first. If parsing or the schema fails, it writes nothing and reports the problems.
- For each file entry whose file exists, whose kind matches its extension, and whose URL passed step 4, it computes `sha256` and `bytes`.
- **Text edit, not `json.dumps`,** so the hand-formatted one-object-per-line layout survives. A file object has no nested braces. Find its span by searching the raw text for the JSON-encoded `"url": <json.dumps(url)>` (allowing any whitespace around the colon). Step 3 makes each match unique. Expand to the enclosing `{` and `}`, then `json.loads` that span and check that it matches the parsed entry. If it doesn't match, write nothing, report the entry, and exit 1. Re-render the span on one line, in the same `{ "k": v, ... }` style the catalog uses: the existing keys in their existing order, with values updated in place, then `sha256` and `bytes` appended if they weren't there before.
- It writes the file only if the text changed, through a temporary file in the same folder and `os.replace`. It never touches `updated`; the README tells the user to set it by hand.
- Then it runs `check` and exits with its result. Missing files are reported but don't stop `--write` from filling in the files that exist.

**2. `tools/check-backgrounds-selftest.py` (new),** in the style of `tools/worklog-selftest.py` and `tools/check-report-selftest.py`. It has a module docstring with the usage line, loads `check-backgrounds.py` with `importlib`, and prints `ok   <name>` or `FAIL <name>: got …; want …` for each case. It ends with `N/M passed` and exits 0 only when every case passes. No `sips`, no network and no git, so it runs on Linux.

Fixtures, built in a `tempfile.TemporaryDirectory()` per case:
- `make_png(w, h)`: a real minimal PNG built with `struct` and `zlib`, with signature, `IHDR` (8-bit gray), one `IDAT` of zero rows, and `IEND`, each with the right CRC (`zlib.crc32`). Keep fixtures small (full 160×100, thumbnail 48×30), so they stay cheap.
- `make_png_header(w, h)`: a signature plus `IHDR` only, so a file can *declare* 5000×3125 without the cost of a real image. The checker reads only the header, so this is enough for limit cases.
- `make_jpeg(w, h)`: `FF D8`, an `APP0` segment, a `C0` SOF segment carrying `h` and `w`, then `FF D9`.
- `build_root(...)`: writes a two-set, two-images-per-set catalog in the same one-line-per-file text style as the real catalog, plus its files. A keyword lets each case override one detail. The good catalog's hashes are computed from the fixture bytes.
- The real catalog is never used as a fixture. One extra case only parses it: `real catalog parses and passes the schema`, which loads `website/backgrounds/catalog.json` relative to the repo and asserts no step-2 or step-3 problems. Missing files are allowed there.

## Work

1. **Images.** Put each PNG at the path its prompt names. If a generator size other than 3840 × 2400 was used, record it in the prompts doc and set `width`/`height` in the catalog to match.
2. **Thumbnails.** Make each one from its full-size image, as the prompts doc says, for example `sips -z 300 480 01-skyline-fog.png --out 01-skyline-fog-thumb.png`. A thumbnail must be PNG and must keep the full-size image's aspect ratio. `sips -z` forces the size, so a non-16:10 source would be distorted, and the check catches that.
3. **Catalog.** Fill in `sha256` and `bytes` for every `full` and `thumbnail`, using the script's write mode (below), and set `updated`.
4. **Check script**, `tools/check-backgrounds.py`. It goes in `tools/`, not `scripts/`, which is a restricted area. Run as `python3 -I tools/check-backgrounds.py [--write] website/backgrounds/catalog.json`. It exits 0 when everything passes and 1 with one line per problem otherwise. It uses the standard library only, and reads PNG dimensions from the `IHDR` chunk, with no `sips` dependency, so it also runs on Linux. It checks:
   - the JSON parses, `schemaVersion` is 1, and every required field from #0574 is present with the right type;
   - set ids are unique, and image ids are unique across the whole catalog and match `^[a-z0-9][a-z0-9-]{0,63}$`;
   - every `url` is relative, and resolves to a file inside `website/backgrounds/`, with no `..` escape and no absolute or `http:` URL in the built-in catalog;
   - every file exists, starts with the PNG signature, and its `IHDR` width and height equal the catalog's;
   - `sha256` and `bytes` are present and match the file;
   - each thumbnail's aspect ratio equals its full-size image's (within 1%), and its longest side is at most 1024;
   - each full-size image is no wider or taller than 4096 (`TerminalBackgroundImageImporter.maxPixelSize`; larger works but is downscaled in Batty, so it's a waste), and at most the full-size byte limit #0577 sets;
   - no PNG under `website/backgrounds/` is missing from the catalog (an orphan file is an error, since `rsync` would publish it).

   `--write` fills in or corrects `sha256` and `bytes` only, keeps key order and the existing formatting style, then runs the checks. Add `tools/check-backgrounds-selftest.py`, in the style of `tools/worklog-selftest.py`, with fixtures under a temporary folder for: a good catalog, a missing file, a wrong dimension, a wrong hash, a duplicate id, a `..` URL and an orphan PNG.
5. **Documentation.** Under a "Background images" section in `website/README.md`, describe how to add an image (generate, `sips`, `--write`, check, deploy). Add a line pointing at it in `docs/background-image-prompts.md`.
6. **Privacy page.** `website/privacy.html` says, under "Network requests", that Batty makes "exactly one kind of outbound network request", the Sparkle appcast fetch. That stops being true in 1.4.0. Add the background catalog requests: what is fetched (the built-in catalog, thumbnails, and full-size images only on request), from where (batty.sstools.co, and any catalog URL the user adds), how often (per the answer to #0574 open question 2), and how to stop it. Also say that no identifying data is sent beyond what any HTTPS request carries. Ship this with or before the 1.4.0 release.

## Deploy (shared state: the user's go-ahead each time)

Deploying the website changes a live, shared system, so it needs the user's explicit go-ahead every time (AGENTS.md "Authoring rules"). An agent does not deploy on its own.

- Run `python3 -I tools/check-backgrounds.py website/backgrounds/catalog.json` first. Don't deploy if it fails.
- Two deploy routes exist and they disagree. `scripts/deploy-website.sh` (documented in `scripts/RELEASE.md` step 7) runs `rsync --delete` to `$BATTY_EC2_HOST:$BATTY_EC2_PATH`. The route used in practice is `rsync -avz` **without `--delete`** to `photon:/var/www/vhosts/batty.sstools.co/`, after a `-n` dry run, because `--delete` would wipe the older DMGs on the server: local `website/downloads/` holds only the current one, since DMGs are gitignored. The user picks the route.
- After deploying, check with `curl -sI` that `https://batty.sstools.co/backgrounds/catalog.json` returns 200, with `Content-Type: application/json` and an `ETag` or `Last-Modified` header (#0577's refresh depends on one), and that one full-size and one thumbnail URL return 200 with the expected `Content-Length`.
- Wiring the check into `scripts/deploy-website.sh` would edit a restricted file. Ask the user before doing it.

## Open questions

1. **Commit the PNGs to git?** 15 full-size PNGs are likely 150 to 300 MB (#0574 open question 1), and every replaced image adds its full size to history. DMGs are kept out with `.gitignore` (`*.dmg`), and so are the demo videos (`website/demo/*.mp4`). Options: commit them (simple, and `rsync` sees them), add them to `.gitignore` and keep the source of truth somewhere else, or use Git LFS. Thumbnails and `catalog.json` are small and should be committed either way.
2. **Should the server set cache headers** for `backgrounds/` (for example, a long `max-age` on PNGs, and `no-cache` with validators on `catalog.json`)? That is Apache config on the host, outside the repo.

## Acceptance criteria

1. `python3 -I tools/check-backgrounds.py website/backgrounds/catalog.json` exits 0 on `main` once the images are in, and the self-test passes.
2. Deleting a thumbnail, editing one byte of a full-size image, or changing one `width` each makes the check exit 1 and name the problem.
3. Opening `https://batty.sstools.co/backgrounds/catalog.json` in a browser after the deploy shows the catalog, and each `full` and `thumbnail` URL in it opens the right picture.
4. Each thumbnail looks like a small, undistorted version of its full-size image.
5. `https://batty.sstools.co/privacy.html` describes the background catalog requests.
