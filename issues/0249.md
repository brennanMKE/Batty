## Description

Batty should ship a command-line tool, simply called `batty`, and the Batty app should be able to install it to `/usr/local/bin/batty` from within the app. Writing to `/usr/local/bin` requires elevated privileges, which is awkward to do from a Mac app — the mechanism is not obvious.

The reference project **supacode** (`../supacode`) already solves this: it installs `/usr/local/bin/supacode` from its Mac app. The approach has been researched and documented at `docs/cli-tool-install.md`, which this issue should be implemented against.

## Relation

- Follow-on defect: [#0252](0252.md) — the embedded CLI crashed at launch (transitively linked Sparkle via `@rpath`); verification here never ran the embedded copy.

## Resolution notes

> 🟢 Resolved 2026-06-23 — `batty` CLI is defined as a `BattyKit` package `executableTarget`, embedded into the app bundle, and installable to `/usr/local/bin/batty` from Settings via an NSAppleScript privileged symlink.

The Settings UI (Advanced tab → Install/Uninstall row) and the actual privileged auth dialog can't be verified headlessly — those need the user's visual sign-off, which is why this is `resolved`, not `closed`. The CLI's command surface is intentionally minimal (`version`/`help`); defining real subcommands (starting with `batty <path>` to create a session) is tracked in #0250.

## Root cause

Greenfield feature, not a bug. Starting state: no CLI target, no installer, no Settings hook. The interesting constraint was *how a Mac app installs a tool to the privileged `/usr/local/bin`*, and *how to keep the CLI's code in the Swift package* per the project's code-management goal.

## Fix

- **`BattyKit/Package.swift`** gains an `.executable(name: "batty")` product and an `.executableTarget(name: "batty", dependencies: ["BattyKit"])`, reusing the shared `swiftSettings`. The CLI `import`s BattyKit, so the model layer stays in the package and `swift run batty` works with no Xcode.
- **Embedding** copies the built binary to `Contents/Resources/bin/batty`. The originally-planned approach — making the app target depend on the package *executable product* via an Xcode `XCSwiftPackageProductDependency` — was implemented first and **broke the `scripts/build.sh unit` gate** (see Gotchas). The shipped approach instead builds the CLI *from the package* inside the "Embed CLI" Run Script phase (`xcrun swift build --product batty`) and copies the result, keeping the executable out of the app scheme's build graph. The phase declares its output path so the app signing pass re-signs the embedded binary.
- **`CLIInstaller.swift`** (in BattyKit) ports supacode's mechanism: a symlink at `/usr/local/bin/batty` into the bundle, created via `NSAppleScript` `do shell script "mkdir -p … && rm -f … && ln -s …" with administrator privileges`; `uninstall()` is a privileged `rm -f`; `isInstalled()` compares the symlink target to the current bundle path; `-128` maps to a silent `.cancelled`.
- **`SettingsView.swift`** adds an Advanced tab with an Install/Uninstall row driven by an `@Observable` `CLIInstallModel`; `onAppear` checks installed state; cancel is a no-op.

## Gotchas

- **Do NOT make the app target depend on the `batty` executable *product* via an Xcode `XCSwiftPackageProductDependency`.** Doing so pulls the executable into the `Batty (Prod)` scheme's build graph and breaks the xcodebuild test runner's resolution of BattyKit's `Bundle.module` resource bundle — every `BattyKitTests` test then crashes on launch with `resource_bundle_accessor.swift: Fatal error: unable to find bundle named BattyKit_BattyKit`. Pure `swift test` does NOT show this, so it's easy to miss; the canonical gate `scripts/build.sh unit` does. Build the CLI from the package in the Run Script phase instead.
- **Universal/Release arch path is unverified.** The embed script passes all `${ARCHS}` as `--arch` flags to a single `swift build` (SwiftPM emits one universal binary); only the single-arch Debug build was exercised. Check `lipo -info` on the embedded binary when first cutting a release.
- **The `.installing`/`.uninstalling` ProgressView never actually renders** because `NSAppleScript` blocks the main thread synchronously through the auth dialog. Matches supacode; cosmetic only.
- **Symlink, not copy** — moving/renaming `Batty.app` makes `isInstalled()` read false (the symlink targets the old bundle path); re-install self-heals.

## What needs to happen

1. **Define the `batty` command-line executable as an `executableTarget` in the `BattyKit` Swift package** (`BattyKit/Package.swift`), with a matching `.executable` product named `batty`. Sources under `BattyKit/Sources/batty/`. The CLI `import`s `BattyKit` so it shares the model layer — keeping as much code as possible in the package is the governing goal here. `cd BattyKit && swift run batty --help` should work with no Xcode involved.
2. **Embed the built binary in the app bundle** at `Contents/Resources/bin/batty`. Xcode does not auto-embed a package *executable* product, so the Batty app target must (a) depend on the `batty` executable product and (b) run a copy build phase that places `BUILT_PRODUCTS_DIR/batty` into `Contents/Resources/bin/batty` (output path declared so the app signing pass re-signs it).
3. **Install from the app** by creating a symlink at `/usr/local/bin/batty` pointing back into the bundle, escalating privileges via `NSAppleScript` `do shell script "... with administrator privileges"` (triggers the standard macOS auth dialog branded with the app's icon). No SMJobBless / XPC privileged helper needed. Put `CLIInstaller.swift` in BattyKit too (it only uses `Bundle.main` / `FileManager` / `NSAppleScript`).
4. **Surface install / uninstall in Settings**, with an "installed" state check (symlink resolves to the *current* bundle path).
5. **Uninstall** removes `/usr/local/bin/batty` (privileged `rm -f`).

The initial scope of what the `batty` CLI actually *does* is out of scope for this issue beyond a minimal working entry point — the focus here is the install plumbing. A follow-up issue can define the CLI's command surface.

## Reference

- **`docs/cli-tool-install.md`** — full engineering guide. It documents supacode's mechanism (exact code excerpts with `../supacode` file/line refs) and the Batty plan, which **deliberately diverges from supacode**: supacode uses a standalone Xcode/Tuist command-line-tool target, whereas Batty defines the CLI as a `BattyKit` package `executableTarget` (§4.1) so the CLI shares package code. The install/escalation code is ported verbatim.

Key adaptation notes from the doc:
- **CLI lives in the Swift package**, not a standalone Xcode target — top goal is to keep as much code as possible in BattyKit. The app target only embeds + installs the built binary.
- **Batty is unsandboxed** (`ENABLE_APP_SANDBOX = NO`), so unlike supacode it does **not** need the `com.apple.security.automation.apple-events` entitlement — `do shell script ... with administrator privileges` works without it, and Hardened Runtime can stay on.

## Notes

Gotchas captured in the doc: the install is a **symlink, not a copy**, so moving/renaming the app makes it read as "not installed" (re-install self-heals); user-cancel of the auth dialog returns error `-128`; `NSAppleScript` must run on the main thread; shell-escaping and `mkdir -p /usr/local/bin` matter. Worth weighing symlink-vs-copy and `/usr/local/bin`-vs-`~/.local/bin` (the latter needs no privilege escalation) — both discussed in the doc.

The `scripts/` directory is a restricted area (release pipeline); the doc suggests an inline Run Script build phase rather than adding a script there.

Watch the one less-trodden spot: Xcode auto-links *library* package products but does **not** auto-embed a package *executable* product into the bundle — the app target needs an explicit dependency on the `batty` executable product plus the copy phase. Confirm a clean app build actually produces `${BUILT_PRODUCTS_DIR}/batty` before relying on it. The BattyKit workspace sole-owner rule still applies (don't re-add a bare `XCLocalSwiftPackageReference`).

(Resolution update: the executable-product-dependency embedding above turned out to break the unit-test gate; the shipped fix builds the CLI from the package in the Run Script phase instead — see `## Gotchas`.)
