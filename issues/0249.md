# 0249 — Add a `batty` CLI tool that the app can install to /usr/local/bin

| | |
|---|---|
| **Status** | open |
| **Module** | App / Build / Settings |

## Description

Batty should ship a command-line tool, simply called `batty`, and the Batty app should be able to install it to `/usr/local/bin/batty` from within the app. Writing to `/usr/local/bin` requires elevated privileges, which is awkward to do from a Mac app — the mechanism is not obvious.

The reference project **supacode** (`../supacode`) already solves this: it installs `/usr/local/bin/supacode` from its Mac app. The approach has been researched and documented at `docs/cli-tool-install.md`, which this issue should be implemented against.

## What needs to happen

1. **Build a `batty` command-line executable** as a separate Xcode target (or build phase) that produces a normal CLI binary named `batty`.
2. **Embed the binary in the app bundle** at `Contents/Resources/bin/batty` via a post-build copy step.
3. **Install from the app** by creating a symlink at `/usr/local/bin/batty` pointing back into the bundle, escalating privileges via `NSAppleScript` `do shell script "... with administrator privileges"` (triggers the standard macOS auth dialog branded with the app's icon). No SMJobBless / XPC privileged helper needed.
4. **Surface install / uninstall in Settings**, with an "installed" state check (symlink resolves to the *current* bundle path).
5. **Uninstall** removes `/usr/local/bin/batty` (privileged `rm -f`).

The initial scope of what the `batty` CLI actually *does* is out of scope for this issue beyond a minimal working entry point — the focus here is the install plumbing. A follow-up issue can define the CLI's command surface.

## Reference

- **`docs/cli-tool-install.md`** — full engineering guide derived from supacode: exact mechanism, code excerpts with `../supacode` file/line refs, a near-verbatim `CLIInstaller.swift` port renamed to `batty`, the Xcode target + Run Script setup, and gotchas.

Key adaptation note from the doc: **Batty is unsandboxed** (`ENABLE_APP_SANDBOX = NO`), so unlike supacode it does **not** need the `com.apple.security.automation.apple-events` entitlement — `do shell script ... with administrator privileges` works without it, and Hardened Runtime can stay on.

## Notes

Gotchas captured in the doc: the install is a **symlink, not a copy**, so moving/renaming the app makes it read as "not installed" (re-install self-heals); user-cancel of the auth dialog returns error `-128`; `NSAppleScript` must run on the main thread; shell-escaping and `mkdir -p /usr/local/bin` matter. Worth weighing symlink-vs-copy and `/usr/local/bin`-vs-`~/.local/bin` (the latter needs no privilege escalation) — both discussed in the doc.

The `scripts/` directory is a restricted area (release pipeline); the doc suggests an inline Run Script build phase rather than adding a script there.
