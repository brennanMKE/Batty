# 0438 — `MultiWindowTests.testNewWindowHasIndependentSidebar` clicks the original Window instead of the new one, because `app.windows` is z-ordered, and passes without checking which Window got the Session

| | |
|---|---|
| **Status** | open |
| **Module** | Testing / Window |
| **Platform** | macOS |
| **First seen** | 2026-09-24 |

## Description

`BattyUITests/MultiWindowTests.swift:50-51` tries to make the new Window key with `app.windows.element(boundBy: 1).click()` before pressing Cmd-N. XCUITest orders `app.windows` by z-order (frontmost first), not by creation order. Right after Shift-Cmd-N the new Window is frontmost, so it is index 0, and `boundBy: 1` resolves to the **original** Window. The test still passes because its assertion (`:54-56`) counts `session-row.*` elements across *all* Windows. Any new Session anywhere satisfies it, so it cannot tell whether Cmd-N reached the new Window. It proves nothing about the per-window behavior its doc comment (`:32-33`) claims to cover.

## Evidence (#0412's VM run `20260923-191103-94702`, test passed in 8.006 s)

In the `xcodebuild.log` of that run, which is in #0412's worktree (`.claude/worktrees/agent-aec34d365e1bf8010/build/ui-tests/20260923-191103-94702/xcodebuild.log`, lines 10724-10782), the click step reads:

- `t = 4.57s Click Window (Element at index 1)`
- `t = 4.72s Check for interrupting elements affecting "…-AppWindow-1" Window`. **Index 1 resolved to `AppWindow-1`, the original Window.**
- `t = 4.73s Found 1 interrupting element: Window at {{91.0, 173.0}, {900.0, 504.0}}`, which is then named `"…-AppWindow-2"`. That is the new, frontmost Window covering the click target.
- `t = 5.44s Did not handle the interruption, but will attempt to continue…`, then `Synthesize event`. The click was sent at a point in `AppWindow-1` that `AppWindow-2` covers. Which Window actually took it, and so which one was key for the Cmd-N at `t = 5.98s`, can't be determined from the log. The test's assertion can't determine it either.

Every other `AppWindow` reference in the log names only `AppWindow-1` or `AppWindow-2`. None of them contradicts this reading. (`grep -n AppWindow` finds 37 hits.)

## Premises checked (read-only, `main` at `3e5b9b8b`)

- The test body matches the description above. It launches, presses Shift-Cmd-N, waits for `app.windows.count >= 2`, waits for 2 or more session rows, clicks `element(boundBy: 1)`, presses Cmd-N, and asserts the *global* row count grew. The helper `sessionRowCount(in:)` (`:80-85`) queries `app.descendants(matching: .any)` with no per-window scope.
- The `#0238.md:62` Gotcha says "`app.windows` … is **creation-ordered** (`boundBy:0` = original, `boundBy:1` = the new/frontmost window)". The log above contradicts it. So does #0418's round-1 review (commit `c9bb6ac5` on `issue/0418`: "VM logs show app.windows is z-ordered, not creation-ordered"). The same false claim appears in `BattyUITests/WindowRestorationTests.swift:33` and `:54`, which #0418 is rewriting. #0418's round-2 notes cite this test as the "established pattern" for making a new Window key. The pattern doesn't work.
- Sibling with the same premise: `SettingsTests.swift:74` takes `app.windows.element(boundBy: 1)` as the Settings window after Cmd-,. Under z-ordering that is the main Window, and `frame.width > 200` passes for it too. So this is probably another vacuous pass. It is out of scope here, but should be fixed the same way or filed separately.

## Expected behavior

The test identifies the new Window positively, makes sure it is key, presses Cmd-N, and asserts that the new Window's Sidebar gained a Session row while the original Window's row count is unchanged.

## Notes

- **Fix direction (the one #0418 round 2 is adopting).** Before Shift-Cmd-N, capture the identifiers of the existing Windows (`app.windows.allElementsBoundByIndex.map(\.identifier)`). After it, take the new Window to be the one whose identifier wasn't in that set (currently `…-AppWindow-2`), and address both Windows as `app.windows[identifier]`. Never use `boundBy:` indices. Scope each count to its Window: `window.descendants(matching: .any).matching(identifier BEGINSWITH 'session-row.')`. Assert new Window +1, original +0.
- Don't use a click to make the new Window key. The click is occluded and XCUITest's interruption handling makes it unreliable in the VM's headless display. Instead, wait on a positive signal that the new Window is frontmost or key, for example that it is index 0 of `app.windows`, confirmed by identifier. If that wait keeps failing, the cause may be #0437 (a new Window becomes key before `WindowIDRegistrar` registers it), not a test problem.
- Consider a shared `BattyUITestHarness` helper, such as `newWindow(after:in:)` returning `XCUIElement`, so `MultiWindowTests`, `WindowRestorationTests` and `SettingsTests` stop re-deriving window identity.
- Correct the `#0238.md:62` Gotcha (or add a dated correction note pointing here) so the creation-order claim stops being cited.
- UI tests run only through the Tart VM runner (`docs/ui-testing-vm.md`), never on the host (`AGENTS.md`, "UI test automation").
