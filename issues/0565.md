## Description

`ProcessFollowByNameTests.theRealEnumeratorPrefersTheLongestRunningProcessOfAName()` failed again during a full `./build.sh unit` run (3313 tests) on `issue/0561`. That branch doesn't touch `ProcessInspector` or this suite. The suite passed alone (30 tests), and a full re-run passed. The failure is the same one #0516 recorded on 2026-10-14. The #0516 fix (`86c022fc`, retry `allPids()` on a saturated buffer) has been on `main` since then, so buffer saturation was not the only cause, or not the cause at all.

The test calls the real enumerator twice, back to back, against the live host process table. It expects both walks to see the same two `sleep` children. Under a full parallel unit run the host process table churns heavily (the failing pid, 99870, sits just under macOS's pid ceiling of 99998, so pids were about to wrap). The second walk found neither child, even though the first walk had just listed both.

It does not break the letter of `AGENTS.md` "Asynchronous tests": it has no sleeps, no polling and no timing assertions. It does depend on global, unsynchronized host state that parallel tests mutate, which is the same source of unreliability that rule exists to remove. `firstSameUserProcess(named:)`'s ordering can be proved with no real processes. One real-process smoke test can stay, but it must not compare two snapshots.

The failure may also point at a real production gap. `allPids()` returns `[]`, without logging, when either `proc_listallpids` call returns `<= 0`. Callers can't tell a failed syscall from "no processes", so a Mode C pane would briefly report Waiting for a running process, as #0516 described.

### Mode C trace: what "unknown" must do

`nameResolver` runs in three places (`ProcessStatusPaneContent.swift`):

1. **`resolveTarget()` with nothing followed** (`:442`, through `resolveByName` `:446-455`). This covers setUp, retarget, and every tick while the pane shows Waiting. Today a failed walk returns `nil`, which becomes `.waitingForName`, which writes `runState = .waiting`. Right after `retarget`/`setUp` (`runState = .running`, `snapshot = nil`) that is the false Waiting banner #0516 described. **New behaviour: leave `runState`, `snapshot`, `hasNoSelection` and `followed` exactly as they are and keep the sampling task running, so the next tick enumerates again.** While the pane shows Waiting it keeps showing Waiting. Right after a retarget it shows the `.running` layout with "—" tiles (`metricsRow` with a nil `snapshot`, `ProcessStatusPaneView.swift:375-381`) for at most one sampling interval, not a Waiting banner.
2. **`reresolve` after the followed pid's identity changed** (`:432-436`). The pid was recycled or exec'd into another name. That comes from a per-pid `identityReader` read, not from the walk, so the followed process is known to be gone. With `.unknown` there is no successor: drop `followed` (`reresolve` already does) and return `.waitingForName`, so the pane shows Waiting. That is true: the process it followed is gone. The next tick re-enumerates.
3. **`reresolve` after `coreMetricsProvider` returns `.processNotFound`** (`:539-548`). ESRCH on the followed pid itself, so again a fact, not a walk result. The existing `if canReresolve, case .pid(let successor) = reresolve(...) else { runState = .waiting }` already sends anything that isn't a pid to `.waiting`. No change is needed there beyond the new case being non-`.pid`.

While a followed process is alive, the walk isn't consulted at all. `resolveTarget` returns `.pid(followed.pid)` after one `identityReader` read. So a failed walk can never flip a pane that is showing a running process. Only the "looking for a process" states consult the walk, and (1) is the only one where the walk alone decides the state. That case is now a no-op tick.

## Root cause

The witness test compared two independent live walks of the host process table (`allSameUserProcesses()`, then `firstSameUserProcess(named:)`), so any difference between the walks failed it, whatever the cause. Underneath, `allPids(listAllPIDs:)` turned a failed `proc_listallpids` probe or fill into a silent `[]`, which every caller read as "no such process". Mode C could therefore report Waiting for a running process after one failed walk. Whether the 2026-11-05 failure was a whole-walk failure or two per-pid misses isn't established (see Gotchas).

## Fix

- `ProcessInspector.allPids(listAllPIDs:)` returns `[pid_t]?`. A probe or fill that returns `<= 0` (a `0` probe included) logs the failing call, attempt, return value and `errno`, then returns `nil`, never a partial list. The saturation retry is unchanged.
- New `ProcessInspector.NameLookup` (`found` / `notRunning` / `unknown`). `firstSameUserProcess(named:)` returns it, `.unknown` on a failed walk, and selects through the new pure `firstProcess(named:in:)`.
- `children(ofPid:)` returns `nil` on a failed walk, and `loadChildProcesses()` shows `.unavailable` for it. `allSameUserProcesses()` maps a failed walk to `[]` (out of scope, per the Plan).
- Mode C: `resolveByName` maps `.unknown` to a new `Resolution.lookupFailed`. `performSample()` writes no observed state for it, so the tick is a no-op and sampling continues. After a pid-reuse identity change, `.lookupFailed` becomes `.waitingForName`, because the followed process is known to be gone. The `.processNotFound` path already sends any non-`.pid` result to `.waiting`.
- Tests: new `ProcessInspectorNameSelectionTests` (5). `ProcessInspectorAllPidsTests` swaps the zero-probe test for a failed-probe test and adds two failed-fill tests. `ProcessFollowByNameTests` gains four failed-walk tests, and its real-process smoke tests now make one walk per assertion, each checked against a pid the test owns and carrying a failure-only per-pid diagnostic `Comment`.
- `issues/Issues.md`: the Known-flaky bullet for this test is removed, and the lead bullet stays.

The existing `allPids(listAllPIDs:)` seam plus an injected per-pid `bsdInfo` reader would also work. The pure split is smaller and needs no fake `proc_bsdinfo`.

If the smoke test in step 2 ever fails again, the new log line will show whether the walk failed or the children really vanished.
