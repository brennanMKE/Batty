## Description

The user, on the background work under [#0372](0372.md):

> "We also need to set the image and opacity value in saved projects. Don't forget that."

A Project records how to start a Session, but it has no background. No child of #0372 covers this: #0374 ruled it out for its own scope ("Not persisted... Save as Project don't carry it"), and #0376 is an in-memory override only.

## Resolution notes

> 🟢 Resolved 2026-11-03 — A saved Project can store a terminal background image and opacity, edited in the Project Editor and seeded into every Session opened from it, with Project copies reclaimed only when `projects.json` can be trusted in full, behind the flag that is on in Beta and off in Prod; the rendered look and two-Mac sync need the user's check.

## Review

Two rounds. Round 1 bounced because `reclaim` could delete every Project's image after a failed read of `projects.json`, and because its one-day age didn't protect a reused digest folder (`## Review notes`). The failed read in `ProjectStore.load` was filed separately as [#0542](0542.md).

Round 2 approved with no code change. Every round 1 note is met. What this round checked:

- **`load` and `decodeFile`:** identical behaviour. The read-failure branch is untouched and still returns `([], nil)`, so #0542 can change it without touching `decodeFile`. Messages and return values match for decode failure, a missing file, dropped elements and a newer version. The newer-version line now logs after the element loop rather than before it, which doesn't matter.
- **`imagePathsInFile`:** `nil` for an absent, unreadable or undecodable file, a dropped element, or a newer version. `reclaim` returns before building a keep-set on `nil`. The keep-set is memory, the file and `inUse` together.
- **`refreshDate`:** on all three reuse paths, and a failure is logged, not thrown. The deviation on `adopt`'s first return is correct: Save as Project from a Project-seeded Session reaches it, and the other importers' cleanups don't read dates.
- **The two-copies gap:** accepted. See `## Gotchas`. It costs a look, not data, and can't crash.
- **The `"not json"` argument has no solo mutation; this doesn't matter.** The store loads a good file first, so `unreadableOriginal` is `nil` and no `.bak` exists, and only `imagePathsInFile` can make `reclaim` return `nil`. With that file, only its decode failure can do it. Removing the re-read made this argument fail (round 2's first mutation row), so it isn't vacuous.
- **Test hygiene:** no sleeps, `reclaim`'s task is awaited, temp directories only, and nothing added writes `UserDefaults.standard`.

Non-blocking: every `reclaim` re-decodes the file, so a Project with a bad value logs its decode error again at each editor close. `imagePathsInFile`'s doc comment reads awkwardly ("Nil unless the whole file can be trusted: it is absent...") but is correct.

## Root cause

Feature work. `Project` and `ProjectDraft` had no background field, the Project Editor had no control for one, and `ProjectTreeBuilder` builds Tabs with no override, so a Session opened from a Project always followed the app-wide value.

## Fix

Follows the plan. A Project stores `background: TerminalBackgroundSettings?`, tolerantly decoded and written only when set. Opening checks the image and seeds the Session override before the Session joins the window. The image path is device state and doesn't sync (premise 1); the other fields do. Copies live in `ProjectBackgrounds/` beside `projects.json` and are reclaimed when the Project Editor closes. Reclaim re-reads `projects.json` first and removes nothing unless the whole file can be trusted; it keeps whatever the store's list, the file or an open Session or Pane names. Reusing a copy refreshes its folder's date. Save Session as Project copies the Session's image; Update replaces the stored background only if the Session changed it from the seed.

Divergences from the plan:

- **`AppStateStore.projectBackgrounds` is a `var` set after `init`, not an init parameter.** `ProjectBackgroundLibrary` is internal and `AppStateStore.init` is public, which doesn't compile. `projectSyncBackendFactory` is the same kind of seam.
- **`ProjectBackgroundLibrary.init` takes no `importer:`.** It builds its own `.unreferenced` importer; nothing needed another.
- **The setter also skips adopt when the path equals the draft's current path.** Following the plan literally, every slider tick on a newly picked image would hash the file.
- **`ProjectBackgroundRow` has `.id(model.selectedID)`.** `prepare` can swap the draft while the sheet is up (Save as Project from the content window). This ends the sheet, so its Cancel can't write one Project's value onto another.
- **`AppStateStore.projectBackgroundReclaim` is added,** so tests can await the close's reclaim and prove the flag-off close started none.
- **`copyFromCurrentSessionLeavesTheBackgroundAlone` is in `SaveSessionAsProjectTests.swift`.** `ProjectEditorLayoutTests.swift` doesn't exist; the Copy from Current Session tests are in that file.
- **Added tests:** `updateKeepsABackgroundAddedAfterTheOpen`, `aPathThatCannotBeCopiedStoresNoImageAndSaysSo`, `summaryNamesTheImage`.

Round 2, beyond the review notes:

- **`adopt` also refreshes the date on its first return,** when the path is already in the Project folder. The notes name the "destination already usable" return, and this is the same reuse: Save as Project from a Project-seeded Session comes through here. `adoptOfAPathAlreadyThereRefreshesItsFoldersDate` covers it.
- **Added tests:** `reclaimSkipsWhenTheFileBecameUntrustworthy` (undecodable, drops an element, newer version, each after a good load) and `reclaimKeepsAnImageOnlyTheListNames`. The notes require those behaviours but name no test for them.
- **`reclaimSkipsWhileABackupExists` also saves a file.** With an absent file now skipping too, it would have passed without its backup check.

## Gotchas

- **Another running copy's open Sessions aren't known to reclaim.** `inUse` is this process's. If such a Session's Project no longer names an image and its folder is over a day old, another copy's close can remove the file. An unsaved draft is covered by the date refresh; a live Session isn't. On that copy:
  - **Existing surfaces keep showing the image.** Re-rendering the same path doesn't read the file, because `changeConfig` only calls `prepBackgroundImage` when the path changed (`renderer/generic.zig`, at the pinned ref). This is from reading the source, not measured.
  - **A new Tab or Split in that Session has no image and a working shell.** The open fails, and the renderer logs it and carries on. #0373 measured this for `ghostty_surface_new`.
  - **Removal can't produce a half-read file,** so it can't reach the undecodable-image `NULL` surface. Removal only unlinks, and a file already open reads whole.
  - **Save as Project there** stores no image and says so, because `adopt` returns `nil` for a missing path.
  - **What's lost:** Batty's copy of an image that Project no longer uses. Choosing the original again restores it.
- **A `projects.json.bak` stops reclaim for good.** `ProjectStore` writes that file and nothing removes it, so `mayReferenceUnlistedImages` stays true and copies leak until the user deletes the backup. This is the plan's choice, a leak over a lost image.
- **An absent `projects.json` now means no reclaim,** so copies from drafts never saved stay until a first save. Deleting the last Project leaves a file with an empty list, so that case still reclaims.
- **Not seen:** the rendered look, the row's fit at the editor's minimum height, and two-Mac sync behaviour. The app wasn't launched. Run the plan's user checklist.
- **The four new UI tests have only been type-checked.** The daily run exercises them first.
- **A hand-placed corrupt file named for its own digest still passes the check.** Nothing outside libghostty's decoder can detect it, as for #0375.
- **With no image, a Tab's config has only the terminal opacity lines,** because `SettingsPreferences` writes fit, position and image opacity only alongside an image. They stay stored on the Project.
- **A remote "Custom, no image" doesn't remove this Mac's image,** because the path is device state. A remote Follow clears the whole background, including the path.
- **`Help/10-projects.md` is deliberately unchanged;** the flag's removal adds the section (noted in `docs/feature-flags.md`).
- **The Background note can go while it's still true.** `ProjectEditorViewModel.setBackgroundOverride` clears `captureNotes[.background]` on any write, including a sheet Cancel that changes nothing. "A Pane's own background isn't saved" therefore disappears once the user touches the sheet. The note has already shown on the row and no data is lost, so review doesn't require a change.
- **Check by hand:** the plan's user checklist. Also, with a Project's sheet up and its draft edited, use Save as Project from the content window: confirm the unsaved-changes question appears once the sheet is closed. That wasn't run.

## Review notes

Round 1, bounced 2026-11-03. Everything below concerns `ProjectBackgroundLibrary.reclaim` deleting images it shouldn't. The rest of the review found no blocking problem.

**Must fix**

1. **Reclaim can delete every Project's image after a failed read of `projects.json`.** `ProjectStore.load` returns `([], nil)` when the file exists but `Data(contentsOf:)` throws (permissions, an I/O error, a restore in progress). `unreadableOriginal` is then `nil` and there's no `.bak`, so `mayReferenceUnlistedImages` is `false`. The next Project Editor close builds its keep-set from an empty list and removes every digest folder older than a day. The issue and plan both say nothing runs if the file isn't fully loaded. The same thing happens when the file is absent, for example moved away and later restored.

   Fix: in `reclaim`, re-read the file. Add a `ProjectStore` method that returns the image paths the file names now, or `nil` when the file is absent, can't be read or can't be decoded, drops any element, or has a newer version. `reclaim` returns `nil` on `nil`. Its keep-set becomes memory, the file and `inUse` together. Decoding a small JSON file at close is cheap, and the close is already a main-actor event.

2. **The one-day age doesn't do what its comment says.** `reclaim`'s comment says the age covers another running copy of this variant, whose save this store's list doesn't show. It fails in two ways:
   - A running copy keeps its list for weeks, because the list is only read at launch, so the protection ends after a day. Item 1's re-read fixes this for saved Projects.
   - `adopt` and `importImage` reuse an existing digest folder without changing its date. A copy saved today into an old folder can be deleted straight away by another copy's close, or an unsaved draft in that copy can lose its image.

   Two running copies of Batty Beta are realistic here: an installed Beta and a development build share one Application Support folder, and nothing in the app prevents it. Within one process the race isn't reachable in practice, because `removeUnreferenced` runs as one actor turn right after the close.

   Fix: set the digest folder's modification date to now on both reuse paths, `TerminalBackgroundImageImporter.adopt` (destination already usable) and `importImage` (copy already intact). It's about two lines. A failure to set the date is logged and doesn't fail the import. Reword `reclaim`'s comment to match what then holds.

## Plan

Written 2026-11-03 against `2c61c5a1`. Nothing was run. Everything here comes from reading the code. Search by symbol: line numbers in earlier issues have moved.

### Premises checked

Confirmed: the `Actual behavior` list; `LossyProject` drops a Project whose decoder throws; `ProjectSyncRecord`'s synthesized `Codable` throws on a wrong type, and `snapshot()` then skips the record; `TerminalBackgroundSettings` has neither `Codable` nor `Hashable`; `applyProjectSymbol` is the only field pushed to open Sessions; `batty project` has only `list` and `open`; the store's limits; `.allButRetained` removes every entry of its own directory.

**Wrong or incomplete:**

1. **"The path syncs" loses images, so it doesn't.** `ProjectSyncMerge` replaces a Project whole, keeping only what `replacingDefinition` carries over. With a synced path, renaming a Project on Mac A publishes A's path, and Mac B's own image is gone from B's Project, then reclaimed from B's disk. A pick on B does the same to A. The path can't work on the other Mac anyway: `inspect` compares components, so another home gives `.rejected` and the same home gives `.missing` unless the same image was imported there. **The path is device state.** The stated outcome holds exactly: on another Mac the Project keeps its opacity and has no image. Bytes can't reach the store, because no path or image is in the record.
2. **"`SessionProjectCapture` reads `session.backgroundOverride`" (seam item 3) doesn't fit.** Its doc comment promises it "writes nothing", capture has to copy a file, and Copy from Current Session shares it and must not touch the background. `SaveSessionAsProject.draft` reads the override instead.
3. **"Capture must re-import" needs no decode.** `importImage` is async and `draft` and `begin` are synchronous. A copy's folder is named for its bytes, so a byte copy into the Project folder is still valid. This is a new synchronous `adopt`.
4. **The sheet's Custom button would store a path that fails later.** `BackgroundOverrideEditor.selectCustom` seeds from the inherited value, which here is the app-wide value with its path in `TerminalBackgrounds/`. Saved as is, it is `.rejected` at open and can be deleted by the app-wide cleanup. The Project's setter adopts such a path.
5. **`inspect` doesn't check size.** It checks shape and digest. A hand-placed oversized PNG in a folder named for its own digest passes, and that aborts the process. #0375 accepted this for app-wide; the Project path adds a header check, which reads no pixels. A hand-placed *corrupt* file named for its digest still can't be detected, so that stays a Gotcha.
6. **An importer's `Cleanup` case can't do this job alone.** `cleanUpIfNeeded` runs inside the first import, on the actor, with no access to the main-actor `ProjectStore`. The new case is a no-op there, and a separate method takes the keep-set.
7. **"Save must not lose an import" is solved by a sheet.** The controls are six rows and the editor's minimum height is 620. `BackgroundOverrideSettingsView` already has the mode cards, Cancel, the import, and Done disabled during import, and a modal sheet makes Save unreachable meanwhile.

### Files

Paths under `BattyKit/Sources/BattyKit/`.

**`Settings/TerminalBackgroundSettings.swift`**
- `extension TerminalBackgroundSettings: Hashable, Codable`. Keys `imagePath` (only when set), `fit`, `position`, `imageOpacity`, `terminalOpacity`, `opacityAffectsCells`.
- `init(from:)`: `try decoder.container(...)` may throw on a non-object. Each field is then `try?`: a non-string path is `nil`, an unknown `fit` or `position` falls back to the `init` default, and a non-number opacity falls back to 1. It ends by calling the normalizing `init`, so range clamps and path rules apply.

**`Model/Project.swift`**

**`Model/ProjectSync.swift`**

## Persistence

**The image needs a Project-owned directory.** Neither existing one is safe (`TerminalBackgroundImageImporter`):

- **App-wide, `<App Support>/<variant>/TerminalBackgrounds/`, `.allButRetained`:** the first pick of each launch removes every entry except the folder holding the current app-wide path. It would delete a Project's copy, and a subfolder of this directory would go with it. The new directory must be outside it.
- **Pane, `<Caches>/<bundle id>/TerminalBackgrounds/<pid>/`, `.deadProcessFolders`:** removed after the process dies, and Caches can be purged.

So a path can't simply be copied into a Project. A Pane override can point into either directory, so capturing one must re-import the image.

**A Project directory needs its own cleanup rule:**

- Never remove a copy any Project references.
- Don't clean while the file on disk isn't fully loaded (`ProjectStore.unreadableOriginal`). Dropped Projects and `projects.json.bak` may reference copies that the in-memory list doesn't show.
- Decide what happens to a copy imported for an unsaved draft, and to one left behind by a deleted Project or a remote merge.
- An open Session may still point at a copy the Project has replaced. A missing path is benign (#0373), but the plan should say when removal happens.

**Startup safety must cover this path.** Measured in #0374: a corrupt image makes `ghostty_surface_new` return `NULL`, and an image over 16384 px wide aborts the process, killing every Terminal Session. `projects.json` can be hand-edited, restored or synced, so a stored path is untrusted.

- `AppWideBackgroundGate` doesn't cover it. It reads only the `UserDefaults` keys, and it memoizes one path.
- #0375 leaves Pane overrides uninspected because "they aren't persisted". That reason doesn't hold for a value read from `projects.json`.
- `TerminalBackgroundImageImporter.inspect(path:directory:)` can be reused with the new directory. Call it when the Project opens, before `ProjectTreeBuilder` creates any Tab, so the first surface already has the checked value. #0375 measured 14 ms on the main actor for a 43.8 MB file.
- On `.missing` or `.rejected`, drop only the image and keep the opacity. Never fail the open: the builder already falls back for a bad Tab folder rather than failing. The Project Editor should name the problem, as Settings does in #0375.
- Test a stored path to an arbitrary file outside the directory.

## File format

- **Keep `projects.json` at version 1.** `docs/design/projects-sharing.md` records earlier additions as additive at version 1. Raising `ProjectsFile.currentVersion` would make an older Batty treat the file as newer than it knows.
- **Older files must decode.** The new key has to be optional.
- **A local Project with no background stays byte-identical**, as `isShared` does: write the key only when set, in the hand-written `Project.encode`.
- **Decoding must be tolerant.** `LossyProject` drops a whole Project when its decoder throws, and the loader then backs up the original. Decode the new field with `try?`, as `customColor` and `symbolName` do, so a bad value or an unknown future `fit` can't cost the user a Project. Route values through `TerminalBackgroundSettings.init` so its path and opacity normalization applies.
- **`TerminalBackgroundSettings` isn't `Codable` or `Hashable` today,** and neither are its two enums, while `Project` is both. The plan decides between conforming it and adding a dedicated stored type. Either must include `opacityAffectsCells` from #0375.
- **An older Batty loses the field on save, and that has precedent.** The doc comments on `customColorHex` and `customSymbolName` already accept it: "Older Batty versions ignore and, on their next save, drop it." Prod and Beta keep separate `projects.json` files, so this only arises across versions of one variant.

**The field can be dropped silently in hand-written copies,** so each needs a test with a non-default value: `Project.CodingKeys`, `encode` and `init(from:)`, `Project.init`, `ProjectDraft.init(project:)`, `ProjectDraft.makeProject()`, `syncRecord(home:)` and `init(syncRecord:home:)`.

## Sharing

There is no Project export. Sharing is iCloud key-value sync, whose `ProjectSyncRecord` is an explicit list of definition fields (`docs/design/projects-sharing.md`). **The image can't travel with it:** the backend caps the whole store at 1 MB (`maxTotalBytes`), and a copy can reach tens of MB. The path is machine-local too.

- Fit, position and opacities are portable. The plan decides whether they are definition, and whether the path is device state that `replacingDefinition` keeps.
- If the path syncs, the other Mac would get `.missing`, or `.rejected` if its home directory differs, and `PortablePath` handles only the root today. A later pick there would also publish its path back over the first Mac's.
- **Merging replaces a Project whole,** with last writer winning. Anything not in the record is lost on the next merge unless it is carried over as device state. An older Mac that saves a shared Project also publishes it without these fields, as already happens for custom colors.
- `ICloudKeyValueProjectSyncBackend.snapshot` skips a record it can't decode, so a bad synced value must not make `ProjectSyncRecord` throw. Synthesized `Codable` would throw on a wrong type here.
- Update the table in `docs/design/projects-sharing.md`.

## From #0376

#0376 touches no `Project`, `projects.json` or importer code. This issue needs only these:

1. **Seeding:** call `session.setBackgroundOverride(checked)` in `WindowRuntime.addProjectSession`, before `sessions.append(session)`, after running `inspect`. `ProjectTreeBuilder` has built the Tabs, but they have no surface until first render, so the first surface gets the value.

3. **Capture:** `SessionProjectCapture` reads `session.backgroundOverride`. Its path can name the pid folder or the app-wide folder, so capture must re-import.
4. **Clearing:** today, clearing a Project-seeded Session falls to the app-wide value. To fall to the Project's value instead, store the seed, return it from `SessionRuntime.inheritedBackground`, and have `setBackgroundOverride` fan out `backgroundOverride ?? seed`. `applyAppearanceToAllSurfaces` reads `session.backgroundOverride` directly, so it must use the same resolved value. `TabRuntime`'s builder and its stored fields don't change.
