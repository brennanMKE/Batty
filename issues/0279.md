## Description

The user runs `/Applications/Batty.app` (Prod) continuously as their daily driver — the current session is days old — and wants to test Beta builds going forward **without interfering with it**. Verbatim ask: full separation for testing the Beta build, plus **a script that produces an app they can copy into `/Applications`** to run as the Beta, without a name conflict with `Batty.app`.

#0277 separated the broker Mach service name, launchd `Label`, plist filename, CLI install path (`batty` vs `batty-beta`), and app bundle identifier. `UserDefaults` was always separate (keyed by bundle id), and Sparkle is disabled for Beta (`SU_FEED_URL` empty in `Configuration/Beta.xcconfig` — verified). **This issue covers what #0277 did not separate, plus the packaging.** Three concrete leaks are verified against source below; the implementation must additionally run a systematic sweep (categories listed) — the three named leaks are what one pass found, not a proven-complete list.

## Verified leak 1 — `SessionNameCache` is one shared file, mutated by both variants

`BattyKit/Sources/BattyKit/Model/SessionNameCache.swift` line 51: `public static let defaultDirectoryName = "Batty"` — a hardcoded literal, not derived from the bundle identifier. `canonicalFileURL` (line 86) appends it to `~/Library/Application Support/`, resolving to `~/Library/Application Support/Batty/session-name-cache.json` for **both** variants.

Confirmed live: that file was modified today (2026-07-26 15:32) by the running Prod app. A Beta build reads and writes the same file, so:

- Each process loads the file **once at init** and holds the entries in memory; the other variant's later writes are never re-read, then clobbered.
- Writes are debounced (250 ms, `pendingSaveTask`) whole-file replacements — two apps interleave last-writer-wins, silently losing each other's auto-generated session names (#0260's Apple Intelligence naming).

Fix direction: derive the directory (or filename) per variant. **Prod's path must stay byte-identical** — the running app's cache must survive this change with no migration, mirroring #0277's no-migration guarantee for Prod's broker names.

Same directory, noted but **out of scope**: an orphaned `workspace.json` dated 2026-05-22. No code in the repo references it (verified by grep); #0221 (open) records the Workspace persistence layer as unimplemented. Don't touch it — but whatever per-variant directory convention this issue establishes is the convention #0221's future restore work will inherit, so record the decision clearly.

## Verified leak 2 — Beta's broker and CLI log under Prod's subsystem

All four `Logging.swift` copies resolve `Bundle.main.bundleIdentifier ?? "co.sstools.Batty"`:

- `BattyKit/Sources/BattyKit/Util/Logging.swift` line 6 (app side — **fine**: Beta's app resolves `co.sstools.Batty.beta` at runtime)
- `BattyKit/Sources/BattyXPCCore/Logging.swift` line 13
- `BattyKit/Sources/batty/Logging.swift` line 15
- `BattyKit/Sources/BattyBroker/Logging.swift` line 13

The broker and CLI are **bare Mach-Os with no bundle** (`Contents/Resources/bin/`, no adjacent `Info.plist` — the #0270/#0277 asymmetry), so `Bundle.main.bundleIdentifier` is `nil` in both and they take the literal Prod fallback **regardless of variant**. Consequence: `log stream --level info --predicate 'subsystem == "co.sstools.Batty"'` — the exact invocation #0272 documents as the only practical way to watch a three-process handoff — mixes Prod's app/broker/CLI with Beta's broker/CLI, indistinguishably.

**The fix is now cheap.** `ServiceNames.current` already knows the variant at compile time — `#if BATTY_VARIANT_BETA` at `BattyKit/Sources/BattyXPCCore/ServiceNames.swift` line 128, baked via `-Xswiftc -DBATTY_VARIANT_BETA` in both Embed phases (#0277) — so the fallback can key off the variant instead of the literal. The four copies are a deliberate dependency-free-target discipline (#0270; #0271 and #0278 Gotchas both record the duplication and the anticipated-but-unscoped consolidation into `BattyXPCCore`); this issue fixes the **fallback** in whichever copies a variant-less process actually uses — it does not take on the consolidation refactor, though landing the fix via `BattyXPCCore` (which broker and CLI both link) is fair game if it falls out naturally.

## Verified leak 3 — both variants register the `batty://` scheme, and the CLI opens it untargeted

Both variants build with the same `Configuration/Info.plist` (`INFOPLIST_FILE` set only in `App.xcconfig`; `Beta.xcconfig` does not override it — verified), so a Beta copy in `/Applications` registers a **second** LaunchServices handler for the `batty` scheme (Info.plist lines 40–46).

`openURL` in `BattyKit/Sources/batty/SessionCommand.swift` (lines 52–67) dispatches `batty://` URLs via `/usr/bin/open <url>` with **no `-b` bundle id** — LaunchServices picks whichever handler it prefers. So with Beta installed, the Tier 0/1 mutation verbs (`batty <path>`, `batty new`) — the primary shipping CLI path — can open a session in the **wrong variant**. The XPC path already does this right: `AppLauncher.launch` (`BattyKit/Sources/batty/AppLauncher.swift`) uses `open -b <ServiceNames.appBundleIdentifier> -g`, which #0277 made variant-correct.

In-repo prior art that this ambiguity is real: `scripts/release.sh` line 313's #0026 comment — a leftover `Batty.app` in `build/` makes LaunchServices route URLs/notifications "to either" copy.

Fix direction: pass `-b` with the variant's baked bundle identifier in `openURL` (the CLI already links `BattyXPCCore` and has `ServiceNames.current`). Separately decide whether Beta should register the `batty` scheme at all — targeted `open -b` fixes the CLI, but a `batty://` link clicked anywhere else (browser, docs) still routes to an arbitrary handler while both apps register the scheme. A per-variant scheme is one option; state the decision and its trade-off rather than leaving it implicit.

## Minor verified sharing (test-only, sweep-list severity)

`UITestDriver.writeError` (`BattyKit/Sources/BattyKit/Testing/UITestDriver.swift` lines 18, 204–206) writes sentinels with the fixed prefix `batty-ui-test-driver-error-` into `NSTemporaryDirectory()` — the per-user `$TMPDIR`, shared across unsandboxed apps. Only matters while UI tests run; include in the sweep verdicts, fix only if cheap.

## The sweep — required, not optional

**Do not stop at the leaks above.** Before implementation is considered complete, sweep the whole codebase for any state keyed by a literal rather than the bundle identifier (or a variant derivation). Candidate categories to check explicitly, with the one-pass findings so far:

| Category | One-pass finding (verify, don't trust) |
|---|---|
| Hardcoded `"Batty"` path/directory literals | Leak 1; sweep for others |
| Application Support / Caches / temp-file locations | Leak 1; `cachesDirectory` — zero hits; `$TMPDIR` sentinel above |
| Notification names | `Notification.Name("co.sstools.Batty.*")` literals in 7 view/runtime files — **in-process `NotificationCenter` only**; zero `DistributedNotificationCenter` uses in the repo, so no cross-process leak; the Prod-literal prefix under Beta is a cosmetic misnomer, not a defect |

## Packaging — a Beta app that can sit in `/Applications`

`Configuration/App.xcconfig` sets `PRODUCT_NAME = Batty` for both variants (`Beta.xcconfig` overrides only `PRODUCT_BUNDLE_IDENTIFIER` and the two Sparkle keys — verified), so a Beta build also produces `Batty.app` and **cannot** be copied next to the Prod app.

1. **Distinct Beta product name** — e.g. `PRODUCT_NAME = Batty Beta` in `Configuration/Beta.xcconfig`, yielding `Batty Beta.app`. Restricted-area check, verified: `CLAUDE.md` restricts `Configuration/Build.xcconfig` specifically; `Beta.xcconfig` and `App.xcconfig` are not on that list. State in the resolution which files were actually touched.
2. **Audit the rename's knock-on effects.** Verified so far:
   - Both Embed phases write via `$(UNLOCALIZED_RESOURCES_FOLDER_PATH)` / `$(CONTENTS_FOLDER_PATH)` (project.pbxproj), which derive from `WRAPPER_NAME = $(PRODUCT_NAME).app` — they follow the rename automatically. Confirm on a built bundle rather than by reading.
   - Both broker plists' `BundleProgram` is the bundle-relative `Contents/Resources/bin/BattyBroker` — independent of the `.app` name (verified in both `Configuration/*.broker.plist`).
   - `scripts/preflight.sh` lines 118–128 `find … -name "Batty.app"` picks the **most recently modified** `Batty.app` in DerivedData — today that can silently select a *Beta* product (same name!); after the rename it silently ignores Beta. Decide which behavior a Prod-preflight should have and document it; don't leave it accidental.
   - `CLIInstaller.swift` hardcodes "Batty.app" in user-facing refusal copy (lines 180, 182; comment at 63 — the #0268/#0275 durability messages). Under Beta these name the wrong app; derive from the running bundle.
   - Not verified — audit: `CFBundleName`/menu-bar/Login Items display strings, anything in `Configuration/Info.plist` or the UI tests that assumes the literal name `Batty`/`Batty.app`.
3. **The build script** — produces a Beta `.app` the user copies into `/Applications`. Requirements:
   - **Must not disturb the running Prod app** and must not require quitting it: build-only, no `launchctl`/`SMAppService` mutations, no app launches.
   - Lives in `scripts/`, which is a restricted area per `CLAUDE.md`. **The user's explicit request for this script is the confirmation that rule requires** — recorded here as the authorization; the implementer still shouldn't touch other scripts beyond the audited preflight change above without asking.
   - Follow house style: zsh, `set -euo pipefail`, repo-root resolution, commented header with usage — read `scripts/build.sh`, `preflight.sh`, `verify-dmg.sh` first. `build.sh` already honors a `SCHEME` env var (`Batty (Beta)` scheme exists in `xcshareddata/xcschemes/` — verified); reuse rather than duplicate where sensible.
   - Build into a dedicated output location and leave no stray bundle copies behind — `release.sh`'s #0026 comment documents that leftover product copies confuse LaunchServices routing (doubly relevant once leak 3 exists).

## The signing question — answer with evidence, not on paper

The tension this ticket must confront, not gloss:

- The user's Developer ID certificate was **revoked once already** by repeated *signed* local builds against this project's `CODE_SIGN_STYLE = Automatic` (`Configuration/Build.xcconfig` line 16; #0265 records the $27.43 incident). The user has explicitly demanded it not happen again.
- But #0270 records that **launchd refuses to start an improperly signed agent**, and that the agent must be signed with the same team identity as the app (experiment finding, under development signing). A Beta whose broker can't register has no working XPC — defeating a large part of what makes the Beta testable.
- So the script cannot simply hardcode `CODE_SIGNING_ALLOWED=NO` and declare victory, *and* it must not institutionalize repeated signed builds.

**Open question the implementation must answer empirically: does an ad-hoc signature suffice for `SMAppService` registration and launchd starting the bundled LaunchAgent, or is a real team identity required?** (Unsigned iteration builds already leave the broker with only `swift build`'s automatic ad-hoc arm64 signature — the Embed phases' `CODE_SIGNING_ALLOWED=NO` branch, verified in project.pbxproj.)

- If **ad-hoc suffices**: the script builds unsigned/ad-hoc always; the revocation hazard is avoided entirely.
- If **a team identity is required**: the ticket must specify how signed builds stay rare and deliberate — sign once, copy to `/Applications`, iterate unsigned for everything else; the signed path is an explicit opt-in flag, never the default; document the expected cadence (a signed build per Beta *install*, not per code change).

The experiment is cheap but **requires an `SMAppService` registration on the user's machine**, which #0270 warns can wedge launchd (recovery: `sfltool resetbtm` + reboot) — two app copies on disk is *exactly* the wedging scenario. **Coordinate the registration test with the user; never run it autonomously**, and never while the timing is bad for their running Prod session.

Also expected (confirm, don't assume): a locally built, non-notarized Beta gets no quarantine attribute, so Gatekeeper does not block it from `/Applications`. Beta never notarizes (#0273 is the Prod release pipeline; untouched).

## Verification expectations

Follow the #0277 pattern — unit tests for everything derivable, then honesty about what needs runtime:

- **Unit tests**: per-variant session-name-cache location (both variants differ; Prod byte-identical to today's path — the no-migration guarantee); logging-subsystem resolution per variant (the derivation function, both variants, plus the baked fallback); `CLIInstaller` copy naming the running variant's app. `cd BattyKit && swift test` and the unsigned workspace gate (`xcodebuild test … CODE_SIGNING_ALLOWED=NO`) stay green; `scripts/build.sh` and `scripts/build.sh unit` green.
- **Both bundles built (unsigned) and inspected**: Beta product is `Batty Beta.app`; Embed outputs landed at the renamed paths; `otool -L | grep -c '@rpath'` → 0 on all four embedded binaries; no path either bundle writes at runtime collides with the other's (enumerate them).
- **The decisive checks are runtime and need the user** — state this plainly; a green build proves none of it:
  - Both apps running simultaneously; each keeps its own session names; Prod's `session-name-cache.json` untouched by Beta activity.
  - `log stream` cleanly separates the variants — Beta's app *and* broker *and* CLI all under `co.sstools.Batty.beta`; nothing of Beta's under the Prod predicate.
  - `batty` and `batty-beta` each reach their own app, including `batty <path>` landing in the right variant with both installed (leak 3).
  - Both agents registered without collision (two Login Items entries — expected, per #0277).
- All runtime checks scheduled around the user's running Prod session (memory directive: never relaunch/kill the running app without asking).

## Teardown — documented and repeatable, required

#0270 records that leftover `SMAppService` state keyed to a bundle is exactly what wedges launchd. So this ticket ships a documented teardown (in `docs/`, wherever fits the existing structure) covering, in order: quit Beta; unregister its LaunchAgent (Settings, or the documented `SMAppService` path) **before** deleting the bundle; remove `/Applications/Batty Beta.app`; remove `/usr/local/bin/batty-beta`; remove Beta's Application Support directory; `defaults delete co.sstools.Batty.beta` if desired. Note explicitly why unregister-before-delete matters.
