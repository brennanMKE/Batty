## Description

UI regression tests covering pane focus interactions — click-to-focus on the pane body, click-to-focus on the chip, geometric arrow-key movement, and the visual focus indicator. The proximate motivator: a user-reported regression where `Cmd-Shift-D` (vertical split) left the bottom pane un-clickable for focus (`#0090`).

Depends on `#0091` (UI test harness bootstrap).

## What this issue ships

A `PaneFocusTests` (or similar) UI test class with the following test cases. Each uses the harness from `#0091` and accessibility identifiers on the relevant views.

### Horizontal split

1. `cmdD_makesNewPaneFocused` — after `Cmd-D`, the focus indicator is on the new (right) pane.
2. `clickInLeftPaneBody_focusesLeftPane` — after `Cmd-D`, click in the left pane's terminal area. The indicator moves to the left pane.
3. `clickInRightPaneBody_focusesRightPane` — symmetric.
4. `clickInLeftChipFocusesLeftPane` — chip-click variant (#0053).
5. `cmdOptionLeft_focusesLeftPane` — arrow-key variant.
6. `cmdOptionRight_focusesRightPane` — arrow-key variant.

### Vertical split (the regression motivator)

7. `cmdShiftD_makesNewPaneFocused` — bottom pane focused after vertical split.
8. `clickInTopPaneBody_focusesTopPane` — direct repro of `#0090`. Click in the top pane's terminal area; the indicator moves up.
9. `clickInBottomPaneBody_focusesBottomPane` — the inverse case.
10. `cmdOptionUp_focusesUpperPane` — arrow-key variant.
11. `cmdOptionDown_focusesLowerPane` — arrow-key variant.

### Recursive split

12. `splitThenSplit_eachPaneClickable` — `Cmd-D` then `Cmd-Shift-D` on the right pane. Click each of the three resulting panes; the indicator goes to the clicked one.

### Verifying the indicator

The focus indicator (per `#0052`) is a 2pt accent-color border on the focused pane. UI tests can verify it indirectly by:

- Pressing `Cmd-D` after a click — the pane that splits is the one the test intended to focus. If the wrong pane splits, the click-to-focus didn't take.
- Reading a sentinel: type `printf 'focus-marker' && echo done > /tmp/batty-ui-test-<uuid>-focus` in the supposedly-focused pane's prompt; the test asserts the sentinel file appears.

The sentinel approach is more reliable than trying to inspect SwiftUI accent-color borders through XCUI.

## Acceptance criteria

- The 12 test cases above all pass on the current build (after `#0090` is fixed).
- The vertical-split tests would fail on a build that regresses `#0090`.
- The harness helpers (`splitHorizontal()`, `splitVertical()`, `clickInPaneBody(at:)`, etc.) live in `BattyUITests/Support/` and are reused by other UI test classes.
- Tests run in CI cleanly — no stuck-app failures, no flaky timing.

## Out of scope

- Visual diffing of the focus indicator color/thickness (the sentinel approach is enough).
- Cross-session focus (sidebar selection changes — covered in `#0094`).

## Notes

- `#0090` (the vertical-split focus bug) must be fixed before these tests pass. If running the tests against the current build before `#0090` lands, expect `clickInTopPaneBody_focusesTopPane` (and possibly `clickInBottomPaneBody_focusesBottomPane`) to fail.
- Click coordinates relative to a SwiftUI view: use `XCUIElement.coordinate(withNormalizedOffset:)` so tests don't break when window size changes.
