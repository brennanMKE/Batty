## Description

Port back into Batty the two `CLIInstaller` improvements the RemoteControl experiment made over Batty's own implementation (named explicitly in RemoteControl's `FINDINGS.md` line 176 and its #0027 reconciliation). These are **independent of the XPC decision** — they improve the existing installer regardless of whether XPC ever ships.

1. **`isBundleDurable`** — refuse to install a symlink whose target is a bundle under `/DerivedData/` or `/Build/Products/`. Batty has no equivalent today: launching from Xcode and clicking Install in Settings → Advanced silently creates a `/usr/local/bin/batty` symlink that breaks on the next clean build, surfacing much later as `command not found`.
2. **A four-state install inspection** — `notInstalled` / `installedHere` / `installedElsewhere(String)` / `blockedByFile` — replacing the current `isInstalled() -> Bool`. Lets the UI say *where* a stale link points and refuse to clobber a real file at the destination.

## Resolution notes

> 🟢 Resolved 2026-07-24 — `isInstalled() -> Bool` is replaced by a four-state inspection, and `install()` can no longer destroy a real file at the destination.

Follow-up filed: **[#0275](0275.md)** — `isBundleDurable` does not yet detect Gatekeeper app translocation, which produces an equally ephemeral bundle path by the more common route (a downloaded release run from `~/Downloads`).

## Root cause

Two defects in the shipped installer, both stemming from install state being a single boolean.

`isInstalled()` returned true only when the destination was a symlink resolving exactly to the current bundle's CLI path. Every other condition — a stale link from a moved or renamed app, a dangling link into a deleted build, or a plain file someone else put there — collapsed into "not installed". `install()` then ran `mkdir -p … && rm -f <dst> && ln -s <src> <dst>` under `NSAppleScript` with administrator privileges, so the `rm -f` clobbered whatever sat at `/usr/local/bin/batty`, including a real user file, behind an auth dialog that gave no hint that was about to happen.

Separately, nothing checked whether the *source* bundle was durable. Launching from Xcode and clicking Install created a symlink into `…/DerivedData/…/Batty.app`, which the next clean build invalidated — surfacing days later as `command not found` with no connection to the action that caused it.

## Fix

`inspectInstallState()` returns one of four states — `.notInstalled`, `.installedHere`, `.installedElsewhere(String)`, `.blockedByFile` — built on `attributesOfItem(atPath:)`, which does not follow symlinks. That distinction is what separates a symlink from a real file and what catches a dangling link that `fileExists` misreports as absent.

`install()` now runs three sequential guards — bundled binary exists → `isBundleDurable` → not `.blockedByFile` — all before `runPrivileged` is reachable; `uninstall()` carries the same `blockedByFile` guard. `isBundleDurable` rejects a `bundleURL` under `/DerivedData/` or `/Build/Products/`.

Stale-link self-heal is deliberately preserved: `.installedElsewhere` is not in the refusal set, so re-running Install still overwrites. Only a non-symlink refuses.

`CLIInstaller.init` gained injectable `installPath`, `bundleURL`, and `fileManager` (defaulted to production values), which is what makes the state machine testable without touching `/usr/local/bin` or raising an auth dialog. `NSAppleScript` stays synchronous on the main thread — the known cosmetic gap where `.installing` spinners never render is documented and was left alone.

## Review

Reviewed by `claude-opus-5`, one round, approved first pass.

The reviewer verified the data-loss path from source rather than from the summary: `install()` has exactly one `runPrivileged` call site behind three guards with no early return or alternate branch, and the residual states were each checked individually — a directory stats as `.typeDirectory` and refuses, a dangling symlink correctly proceeds, and the only fall-through from a real file would require `lstat` to throw on a readable parent directory. Localization was checked directly against `Batty/Localizable.xcstrings` (18 hand-curated `manual` keys; BattyKit's Settings surface is already entirely outside it, so the new captions match existing practice — not a gap in this diff). The reviewer also confirmed the substring matching in `isBundleDurable` is sound because the trailing slashes mean a path like `~/DerivedData Backup/Batty.app` is correctly accepted.

TOCTOU between the in-process inspection and the later privileged shell run was raised and judged not worth blocking: exploiting it requires write access to `/usr/local/bin` during the seconds the auth dialog is up, and the pre-existing code had no check at all, so this is a strict improvement rather than a new exposure.

## Gotchas

- **A regression in the guards would hang `scripts/build.sh unit` on an auth dialog rather than failing cleanly.** The two throw-path tests call the real `install()`/`uninstall()` and depend on the guards short-circuiting before `runPrivileged`. Injecting the privileged runner as a closure seam would make that deterministic; not done here.
- **`uninstall()` now removes an `.installedElsewhere` symlink** where the old code no-op'd. Not reachable from the UI — that state shows the Install button, never Uninstall — and correct for the self-heal intent.
- `SettingsView.swift` hardcodes `/usr/local/bin/batty` in the `.blockedByFile` caption, duplicating the path now carried by `CLIInstallerError.blockedByFile`. One source of truth would be better if that copy is touched again.
- The static `inspect(installPath:expecting:fileManager:)` is indirection no test calls — the injectable `init` is the seam the tests actually use. Could be inlined.
- **Gatekeeper app translocation is not covered** — see [#0275](0275.md). A translocated bundle at `/private/var/folders/…/AppTranslocation/<uuid>/d/Batty.app` passes `isBundleDurable` today, and that is the path a normal user takes (download the DMG, run from Downloads). The existing refusal copy also would not fit that case: it says "build folder", and the correct advice includes *relaunching* after dragging to `/Applications`, since a translocated instance stays translocated.

## Current state (verified against source via `docs/batty-cli-install.md`, 2026-07-24)

- `BattyKit/Sources/BattyKit/Settings/CLIInstaller.swift` — install path hardcoded to `/usr/local/bin/batty`; symlink (not copy); privileged via in-process `NSAppleScript` `do shell script … with administrator privileges`.
- `isInstalled()` returns true only when `FileManager.destinationOfSymbolicLink(atPath:)` exactly equals the current bundle's `bundledCLIPath`. A stale symlink (app moved/renamed, or a DerivedData path from a deleted build) and a plain file at the destination are both indistinguishable from "not installed".
- **`install()` runs `mkdir -p … && rm -f <dst> && ln -s <src> <dst>`** — the `rm -f` clobbers *whatever* is at the destination, including a real file the user put there. The `blockedByFile` state must be detected *before* the privileged command runs, and the UI must refuse rather than overwrite.
- UI: `CLIInstallRow` driven by `@Observable CLIInstallModel` in `BattyKit/Sources/BattyKit/Views/SettingsView.swift` (states today: `.checking`, `.installed`, `.notInstalled`, `.installing`, `.uninstalling`, `.failed(String)`).

Reference implementation: RemoteControl's installer (vendored under `docs/xpc/cli-embedding-and-install.md` once #0267 lands; until then the sibling checkout at `/Users/brennan/Developer/brennanMKE/RemoteControl`, read-only).

## Traps that apply here

- **`NSAppleScript` must run on the main thread** — the existing code comment says so and callers are `@MainActor`. Keep that invariant; do not move the privileged call onto a background task to "fix" the known cosmetic gap that `.installing`/`.uninstalling` spinners never render (the auth dialog blocks the main thread synchronously — documented, acceptable).
- **Keep the inspection logic testable.** The experiment's process lesson: moving the installer state machine into the package is what made it testable, "which is where the actual bugs were." The four-state inspection should be unit-testable (inject paths / a file-manager seam) without touching `/usr/local/bin` or showing an auth dialog.
- **Stale-link self-heal must survive.** Today, re-running Install overwrites a stale symlink (`rm -f` before `ln -s`) — that behavior is correct for the `installedElsewhere` state and must be preserved; only `blockedByFile` (a non-symlink at the destination) refuses.
- The durability check gates the *source* (the bundle the symlink would point into), not the destination. A user running a properly installed `/Applications/Batty.app` must be unaffected.
