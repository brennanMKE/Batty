## Description

Second child of the #0257 umbrella and the **first mutating XPC verb**. Per the transport amendment recorded in #0257: agent-facing pane mutations go over XPC request/reply, not the one-way `batty://` scheme, because an agent chaining `pane split --pane <id>` must be able to tell a real split from one that hit a stale id — which one-way IPC cannot report. The reply carries the **new pane id**, printed to stdout, so an agent can chain on it (`batty pane split -v` → `<pane-id>` → later `batty pane close --pane <pane-id>`). Client-generated UUIDs (#0257 Foundation §6) are unnecessary for this verb — the reply channel returns the real id.

## Resolution notes

> 🟢 Resolved 2026-07-27 — `batty pane split` lands as the first *mutating* XPC verb: it splits a named or resolved pane, defaults to horizontal, replies with the new pane id, and a `-c` pane now stays open after its command exits.

A stale pane id exits `4` rather than silently succeeding — the reason this verb went to XPC rather than `batty://`. Whether a split visibly happens on screen needs the user's runtime sign-off.

## Root cause

Starting state, not a defect. #0281 gave an agent the ability to identify itself and #0274 let it read the layout, but nothing let it *act*. `pane split` is the first verb that changes the app's structure, so it also had to establish the mutation-over-XPC pattern #0283 and #0284 reuse.

## Fix

**`batty pane split [-h|--horizontal | -v|--vertical] [-c|--command <cmd>] [--pane <id>]`**, defaulting to **horizontal**, over XPC request/reply. The target resolves through #0281's shared chain (explicit `--pane` → `BATTY_PANE_ID` → focused pane), and the reply carries the new pane id to stdout so an agent can chain on it.

New `XPCVerb.paneSplit` with `PaneSplitRequest`/`PaneSplitReply` in `BattyXPCCore`; `SplitTree.splitPane(id:direction:ratio:command:)` as a targeted variant reusing the existing `inserting`/`rebalancingChain` machinery and returning `nil` for an unknown id; `AppStateStore.splitPane` searching every window and session without touching `selectedSessionID`; dispatch in `AppXPCService`; CLI through the generalized `AppServiceClient.perform<Payload>` rather than a fork; and a new `PaneNounCommand` following `SessionNounCommand`'s pattern.

**Focus policy** (a judgment call the issue delegated): tree focus moves to the new pane **only when the split target was already that tree's focused pane**, mirroring `splitFocusedPane`'s existing behavior. A named-but-unfocused target — a sibling, or any pane in a background session — leaves the tree's focus alone. Symmetric for foreground and background, layered on the separate guarantee that `selectedSessionID` and the key window are never touched.

**`-c` plumbing:** `TabRuntime.commandOverride`, set at construction and surviving `attachContext`'s re-apply, emits `command = <override>` **instead of** the shell preference rather than alongside it — deliberately, because `command`'s repeat-key semantics in libghostty are unverified, unlike `env`, which #0281 confirmed accumulates.

**`-c` panes stay open after the command exits** (user decision, 2026-07-27). `wait-after-command = true` is emitted in the same branch as the override, so it is structurally scoped to `-c` panes. Before this, `pane split -c 'npm test'` ran the tests and the pane vanished with its output — fine for `htop`, wrong for the short-lived command an agent is most likely to run.

## Review

Reviewed by `claude-opus-5`, three rounds — the third deliberately narrow.

**Round 1 found the blocking gap**: the targeted-split tests never asserted targeting. `splitsTheNamedPaneEvenWhenAnotherPaneIsFocused` carried a comment saying the new pane must land adjacent to paneA, but asserted only non-nil, a pane count, `contains`, and not-entirely-hidden — **every one of which passes identically if the split had wrongly landed on paneB**. The sibling rebalancing test could not distinguish either, since splitting A or B in a same-direction chain both rebalance to thirds. So the single most important property of the new method had no coverage. Fixed with `tree.panePositions[id]?.label` assertions.

Round 1 also traced the exit-4 path end to end and confirmed it distinct from 2/3/5; verified by reading — not trusting — that `SplitTree.splitPane` writes exactly `root` and conditionally `focusedPaneID` and nothing else; confirmed observation-rules compliance (event-origin XPC work hopped to `@MainActor`, not a #0229-shape `Task` hop); and confirmed each payload type is `nonisolated` with its **own** off-actor guard and raw-JSON key assertions.

**It also found the `-c` lifetime footgun** by tracing `PaneView.swift:158` → `closeTab(id:)` rather than from any failing test, which produced the user decision above.

**Round 3 cleared the scoping**, which was the real risk of the wait directive: `applyShellAndAppearancePreferences` has exactly two call sites, `commandOverride` is a `private let` assigned once so `attachContext`'s re-apply replays the same value and cannot manufacture one, and every `TabRuntime` construction passes `command:` only from `SplitTree.makePane`. The directive is structurally unreachable without `-c`, so Cmd-D and existing tabs are unaffected. The reviewer also confirmed the negative test is not vacuous by checking that a sibling test asserts a *positive* substring on the same `renderedConfig`.

## Gotchas

- **An agent cannot dismiss a waiting `-c` pane.** `wait-after-command` waits for *any keypress*, which needs input delivered to that surface. So agent-driven `-c` panes accumulate until a human closes one or **#0283's `pane close`** lands — which makes #0283 the natural next step rather than an optional sibling.
- **`-c` bypasses the configured shell entirely.** The override replaces the shell's `command =` line rather than appending, so shell-integration behavior — notably OSC 7 cwd reporting, which drives Batty's auto-naming and `handleWorkingDirectoryChange` — may not fire for that pane.
- **`commandOverride` is not in the Codable layout model**, so a restored workspace brings a `-c` pane back as a plain shell pane with no wait directive. Pre-existing consequence of persistence not being implemented (#0221); worth knowing when it lands.
- **In the selected session, the focus write reaches the first responder.** An agent-initiated split therefore moves the user's keyboard focus into the new pane — correct for user-initiated Cmd-D, more debatable when an agent did it unprompted. Flagged for the runtime sign-off rather than changed.
- **The `TopologySplitDirection` → `SplitDirection` mapping falls back to `.horizontal`** on an unknown raw value, so a future divergence between the two enums would silently degrade vertical splits. A test now pins both directions.
- Minor, deferred: the explanatory comment block in `TabRuntime` names a round number and a test class, which `CLAUDE.md` warns is the rot-prone kind of comment. Trim if that file is touched again.

## Grammar

```
batty pane split [-h|--horizontal | -v|--vertical] [-c|--command <cmd>] [--pane <id>]
```

- **Defaults to horizontal when no direction is given.** This is a refinement the user asked for that #0257 does not currently specify — #0257's verb table lists the flags but no default; this issue pins it. `-h` and `-v` are mutually exclusive.
- `--pane <id>` targets an explicit pane; otherwise the target resolves via #0281's chain (explicit flag → `BATTY_PANE_ID` env → focused pane).
- `-c|--command <cmd>` runs a command in the new pane — the agent primitive "open a pane next to me running X" (#0257 Notes).
- **The noun is `pane`, deliberately** *(terminology sweep, 2026-07-27)*: splitting subdivides a **region** of the session's split tree — it never splits a terminal. The target pane's tabs are untouched; the new pane arrives beside it with one fresh tab/Terminal Session. Even with `surface` now an accepted alias for `tab` (#0257's terminology amendment), `surface split` would be a category error — the thing being split is the region, not the terminal.
- Exit codes per the `BattyXPCCore/XPCExitCode.swift` vocabulary (verified): `0` success, `1` CLI input error, `2` broker unreachable, `3` app unavailable, `4` request failed, `5` app terminated. An unknown or stale target pane id is a **`4`**, with a message on stderr — the entire reason this verb is on XPC.

## Behavior rules (from #0257, binding)

- **Split placement is computed relative to the target pane's split tree, not the screen** — identical behavior when the target lives in a background session or a non-key window.
- **Mutating a background target must not steal focus or switch the active session.** Only the `focus` verbs do that.
- The new pane joins the even 1/n distribution from #0255 (verified: `splitFocusedPane`'s chain-rebalance re-equalizes the contiguous same-direction chain).

## As-built starting points (verified against source 2026-07-26)

- **#0257 predicted the need for a targeted split variant, and that is still true.** `SplitTree.splitFocusedPane(direction:ratio:inheritingFrom:)` (`BattyKit/Sources/BattyKit/Model/SplitTree.swift`, ~line 131) is the only split entry point and operates on `focusedPaneID`. No `splitPane(id:)` exists. However, the underlying `SplitTreeNode.inserting(newPane:adjacentTo:direction:ratio:into:)` already takes an arbitrary target pane id (`splitFocusedPane` passes `adjacentTo: focusedPaneID`), so a targeted variant is a thin wrapper over existing machinery, including the #0255 rebalance pass.
- **Focus hazard in the existing path:** `splitFocusedPane` unconditionally sets `focusedPaneID = newPane.id`. For a background-session target, moving that *session's own* tree focus to the new pane may or may not be wanted — but it must never propagate to the app's `selectedSessionID`, key window, or first responder. Decide and test the intended tree-focus behavior explicitly; `docs/swiftui-observation-rules.md` is binding for any focus/selection write (XPC-driven writes hop to `@MainActor` and are event-origin, which is the routine case — keep it that way).
- **`-c` needs new plumbing.** `TabRuntime.init` takes only `workingDirectory`; the only command configuration today is the global shell preference (`builder.withCustom("command", shell)` in `TabRuntime.applyShellAndAppearancePreferences`). There is no per-tab/per-pane "run this command" path. Note the new pane already inherits the source pane's cwd via `SplitTree.makePane(inheritingFrom:)` (verified).
- **XPC wiring points** (all verified): add the verb to `BattyXPCCore/XPCVerb.swift`; dispatch in `AppXPCService.perform(_:reply:)` (`BattyKit/Sources/BattyKit/XPC/AppXPCService.swift`), which hops to `@MainActor` for store access; CLI side goes through the generalized `AppServiceClient.perform<Payload>` dance (`BattyKit/Sources/batty/AppServiceClient.swift`) that #0274 extracted — a mutation verb should reuse it, not fork it.
- **Cold-start note:** the connect dance launches the app by bundle id when no endpoint is registered. A split whose target ids came from a previous app instance will then correctly fail with exit `4` — stale ids are *supposed* to be visible now; do not paper over this.
- New CLI surface: a `pane` noun does not exist yet (verified — subcommands today are `new`, `ping`, `status`, `list`, `session`); this issue introduces `PaneNounCommand` with `split` as its first verb, following `SessionNounCommand`'s pattern.

## Binding constraints (copied — do not merely cross-reference)

- **Payloads are `Codable, Sendable` structs carried as JSON-encoded `Data`** inside the `@objc` protocols, `nonisolated` at type level; protocol requirements are `nonisolated func`; reply blocks `@escaping @Sendable`. Guard new payload types (split request + split reply) with off-actor round-trip helpers as `XPCContractTests` does. Beware unlabeled associated values — #0274 shipped-then-caught compiler-synthesized `_0` JSON keys; assert raw decoded JSON keys, not just round-trips.
- **Every Foundation-supplied handler closure gets `@Sendable`** — there is no compiler warning, and the failure is a silent `SIGTRAP` inside the very handler that would have logged the error.
- **`os.Logger` interpolation of a dynamic `String` defaults to `.private`** — add `privacy: .public` explicitly.
- **Verify isolation guards under a forced rebuild** (`rm -rf .build`); stale targets produced false "still builds" results twice on the XPC track.
- **Code-signing protocol:** never run `scripts/build.sh` for iteration (its `unit` path can't disable signing); use `cd BattyKit && swift test` and `xcodebuild … CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO`. The user's Developer ID certificate was revoked once by repeated signed local builds.
- **Mutations aimed at a background session must not steal focus or change the active session** — assert against the store (`selectedSessionID`, focused pane, active tab), not merely absence of a crash. #0274 proved its reads this way; the same assertions apply doubly to the first mutation.

## Verification expectations

Follow the #0271/#0274 pattern:

- **Unit tests for the pure parts:** argument parsing (default-horizontal with no flag; `-h`/`-v` mutual exclusion; `-c` capture; `--pane` UUID validation → exit 1 client-side); request/reply payload round-trips **plus** raw-JSON key assertions; the targeted split variant on a constructed tree (splits the *named* pane, not the focused one; 1/n rebalance holds; unknown id fails).
- **Cross-session store assertions:** a split aimed at a pane in a non-active session mutates that session's tree and leaves `selectedSessionID`, the active session's focused pane, and every other session untouched.
- **Failure result:** an unknown/stale pane id produces the failure reply → CLI exit `4`, and the app logs it publicly.
- `cd BattyKit && swift test` and `xcodebuild … CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO` green; `otool -L` on `batty` still shows zero `@rpath` dependencies.
