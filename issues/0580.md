## Description

The user replaced #0574's `schemaVersion` 1 catalog format with a much simpler one, and the app side (#0576, branch `issue/0576`) is adopting it now. Everything on the website side still writes, checks and documents the old format: `website/backgrounds/catalog.json`, `tools/check-backgrounds.py` (with `--write` filling `sha256` and `bytes`), `tools/build-backgrounds-page.py`, both self-tests, the "Make your own set" section of `website/backgrounds.html`, `website/examples/background-catalog.json`, `website/README.md`, `docs/background-image-prompts.md` and `tools/README.md`. Convert all of them to the new format. Child of [#0574](0574.md). **It must land before the website is deployed**, so batty.sstools.co never serves a catalog that 1.4.0 can't read.

User decision (2026-11-11, verbatim):

> "I don't think we need to include all those details. I think we can keep it super simple. It will have sets which have a name property. Each set will have images which include the name for the thumbnail and full size. Each image can have a title as well. We don't need to include the dimensions, hash or bytes. Simplify."

## The new format

```json
{
  "sets": [
    { "name": "Future Cities",
      "images": [
        { "title": "Skyline in the Fog", "thumbnail": "future-cities/01-skyline-fog-thumb.png", "full": "future-cities/01-skyline-fog.png" }
      ] }
  ]
}
```

- `sets` is required. Each set's `name` is required.
- Each image's `thumbnail` and `full` are required strings: a path relative to the catalog's URL, or an absolute `https` URL.
- `title` is optional. Without it, the title is the file name of `full` without its extension (`01-skyline-fog`). This must match #0576's parser exactly; check its fallback before writing the builder's.
- Unknown fields are ignored.
- There is no `schemaVersion`, no catalog `name`, `updated` or `homepage`, no set or image `id`, no `description` or `credit`, and no `width`, `height`, `sha256` or `bytes`.
- On the app side (#0576): an image's identity is its resolved `full` URL, nothing checks a hash, and dimension limits come from the file's header.

## Decisions (recommended by the filer; the planner confirms or overrides)

1. **No dimension report.** The checker already reads each file's header for the type, the pixel limits and the thumbnail/full aspect-ratio check (kept, 1% tolerance, now from headers). Printing every size adds nothing a reader acts on. The `OK:` summary line keeps its set, image and file counts.
2. **Absolute `https` URLs are accepted by the shape check and skipped by the file checks.** The format allows them, and the example catalog and other people's catalogs may use them. Skipped files are counted in the summary line (for example `OK: 3 sets, 24 images, 48 files, 0 remote`). An absolute URL that isn't `https` is a problem. The built-in catalog has no absolute URLs. `website/README.md` says so, because a remote file there wouldn't be deployed with the site.
3. **Section anchors come from a slug of the set's `name`**: lowercase, every run of other characters becomes one `-`, trimmed, so `Future Cities` stays `#set-future-cities`, as today. A duplicate set name is a checker problem, so slugs from distinct names don't collide in practice. If two do anyway, the builder appends `-2`, `-3`.
4. **Captions show the title only.** Reading sizes from the files would make the builder depend on images that aren't in git, and `--check` would then fail in any clean checkout. The `bg-meta` span (`3840 × 2400 · 7.9 MB`) goes. Remove the now-unused `.bg-meta`, `.bg-credit` and `.bg-set-description` rules in `website/css/style.css` (lines 255 and 283 to 284) too.
5. **`<img>` gets a fixed `width="480" height="300"`**, the built-in thumbnail size (`docs/background-image-prompts.md`, "Thumbnails"). The page doesn't shift as thumbnails load: the attributes reserve the box, and `website/css/style.css` (`.bg-image img`, line 268) already sets `aspect-ratio: 16 / 10; object-fit: cover`. The checker's aspect check catches a thumbnail that isn't 16:10 of its full image. Nothing on the page reads real dimensions.

### What #0576's parser does (the contract this follows)

Read from the 0576 worktree. If it has changed by implement time, re-read it and follow it; #0576 wins.

- Top level: `sets` must be an array, at most 50. Nothing else is read. An empty `sets` parses.
- Set: an object; `name` a string, trimmed, 1–100 characters; `images` an array, at most 100, at most 1,000 across the catalog. An empty `images` parses. **Set names need not be unique** (`BackgroundSet.id` is the index; the source says "Names needn't be unique").
- Image: an object; `full` then `thumbnail`, each a non-blank string that resolves with `URL(string:relativeTo: catalogURL)` to `https` with a host. A duplicate resolved `full` is rejected at `…images[i].full`. A duplicate `thumbnail` is allowed.
- `title`: absent, `null` or blank after trimming means the fallback; a non-string is rejected; over 100 characters after trimming is rejected; otherwise the trimmed text.
- **Title fallback:** `HostedBackgroundImage.fileStem(of: full)` = `full.deletingPathExtension().lastPathComponent` of the **resolved** URL, so it is percent-decoded and loses only the last extension (`01-skyline-fog.png` → `01-skyline-fog`, `a.b.png` → `a.b`).
