# 0466 — `--include-dimensions` never prints the `visible=` field its help promises, and the `frame` it does print is stale for Panes in a background Session and comes from whichever Tab's view is iterated last, not the active Tab

| | |
|---|---|
| **Status** | open |
| **Module** | App / Pane |
| **Platform** | macOS |
| **First seen** | 2026-10-11 |

## Description

`batty list --include-dimensions` and `batty session info --include-dimensions`
(#0144, landed as `e6416c5d`) promise two per-Pane rectangles and deliver
one, and the one they deliver is only trustworthy for the visible, active
Tab of a Pane in the selected Session. Four defects, all in
`BattyKit/Sources/BattyKit/XPC/TopologyPayloadBuilder.swift` and the CLI
printers that consume it; every claim below was re-grepped on `main` at
`d97e6b18` for this filing.

1. **`visibleRect` is hard-coded `nil`, so `visible=` never appears.**
   `PaneRuntime.topologyPayload(isFocused:includeDimensions:)` returns
   `visibleRect: nil` unconditionally
   (`TopologyPayloadBuilder.swift:174`). Nothing else in `BattyKit/Sources`
   assigns the field: `grep -rn visibleRect BattyKit/Sources` finds only
   the payload declaration (`BattyXPCCore/TopologyPayload.swift:99-100`,
   doc comment "Optional visible rectangle (frame minus window chrome).
   Only populated when `--include-dimensions` is set"), its
   init/decoder, the two printers, and the two help strings. The help
   text promises it in four places: the `@Flag` help on
   `ListCommand.swift:30` and `SessionInfoCommand.swift:63` ("Include
   `frame` and `visibleRect` dimensions in pane objects"), and the
   `capabilities --json` property descriptions on `ListCommand.swift:150`
   and `SessionInfoCommand.swift:157`. The plain-text printers are ready
   for it — `ListCommand.paneLine` appends
   `visible=x,y,wxh` when `pane.visibleRect` is non-nil
   (`ListCommand.swift:127-128`) and `SessionInfoCommand.printPlainText`
   does the same (`SessionInfoCommand.swift:134-135`) — but the branch is
   dead. `issues/0144.md:46-51` shows what the field was meant to carry.

2. **Panes in a background (non-selected) Session report their last
   laid-out frame.** The builder reads `tab.terminalNSView!.frame`
   (`TopologyPayloadBuilder.swift:134-142`). Non-selected Sessions stay
   mounted at `.opacity(0)` and the host hides their terminals with
   `isHidden = true` (`docs/view-hierarchy.md:127-130`);
   `PaneView.swift:252` passes `isVisible: tab.id == pane.activeTabID &&
   isSessionSelected` to the placeholder. When `isVisible` is false,
   `TerminalHostStore.setPlacement` and `updatePlacements` only set
   `view.isHidden = true` and never write `view.frame`
   (`TerminalHostStore.swift:390-399`, `:424-433`), so the view keeps
   the frame it had the last time its Session was selected. The builder
   gates on the model's `PaneRuntime.isHidden`
   (`TopologyPayloadBuilder.swift:132`), which is false for a visible
   Pane of a background Session, so that stale frame is reported with no
   marker that it is stale. (`TopologySessionPayload.isActive` tells the
   reader which Session is selected, but nothing says the frame is not
   current.)

3. **The loop overwrites `frame` once per Tab, so the last Tab with a
   `terminalNSView` wins.** `for tab in tabs where tab.terminalNSView !=
   nil` (`TopologyPayloadBuilder.swift:134`) assigns `frame` on every
   iteration without a `break` and without consulting `activeTabID`.
   Every Tab in a terminal Pane has a placeholder and therefore a view
   (`PaneView.swift:249-255` iterates `pane.tabs`), and an inactive Tab's
   view is hidden but keeps its last frame (same mechanism as item 2).
   Tabs of one Pane normally share geometry, so this usually agrees with
   the active Tab, but a Tab that was last active before the Pane was
   resized (or that was never active and still has `frame: .zero`, in
   which case the `bounds`/`subviews` fallbacks at `:143-158` run) can
   disagree, and the payload offers no way to tell which Tab's rectangle
   was used. The intent per `issues/0144.md:95` was "the active
   session/tab window's `frame`".

4. **#0447 fixed only the hidden-Pane case, and no BattyKit unit test
   pins that branch.** `d97e6b18` added `&& !isHidden` to the
   `includeDimensions` guard (`TopologyPayloadBuilder.swift:132`, `git
   blame`), because `WindowRuntime.hidePane` pushes a
   `Placement(frame: .zero, isVisible: false)` (`WindowRuntime.swift:883-889`)
   that `setPlacement` ignores for the frame (item 2), leaving the hidden
   view with a stale frame too. The only coverage is the UI test
   `CLIReadVerbTests.testIncludeDimensionsReportsFramesOfVisiblePanes`
   (`BattyUITests/CLIReadVerbTests.swift:108-160`), which runs only in the
   Tart VM. `BattyKit/Tests/BattyKitTests/AppStateStoreTopologyPayloadTests.swift`
   has no test that passes `includeDimensions: true` (grep for
   `includeDimensions`, `frame`, `visibleRect` in that file: none), even
   though `TerminalSurfaceFocuserTests.swift:27-29` already shows the
   seam — `tab.terminalNSView = AppTerminalView(frame: .zero)` is
   settable from `@testable import BattyKit` — so a unit test can set a
   view frame, flip `pane.isHidden`, call
   `topologyPayload(isFocused:includeDimensions:)` and assert `frame ==
   nil`.

Nothing user-reported depends on this; #0144's stated consumer is an
agent deciding whether a Pane is "still large enough to split further"
(`issues/0144.md:15`), and `issues/0451.md:26` plans to use
`--include-dimensions` to confirm a Pane's achieved size in a UI test.
Both read `frame` and would be misled by items 2 and 3 on a background
Session. Target: after 1.2.0, on `main`.

## Steps to reproduce

Beta build (`./build.sh`), with the Beta CLI (`batty-beta`) on `PATH`.

1. `batty-beta list panes --include-dimensions`. Observe `frame=` on each
   terminal Pane and no `visible=` anywhere. `batty-beta list --help`
   says the flag includes "`frame` and `visibleRect`".
2. Create a second Session (`batty-beta new`), split it so its Pane is
   much smaller than the first Session's Pane, then `batty-beta session
   focus <first-session-id>` so the second Session is in the background.
   Resize the window substantially. `batty-beta list panes
   --include-dimensions`: the background Session's Panes report the
   frame they had before the resize.
3. In the selected Session, open two Tabs in one Pane (Cmd-T), switch to
   Tab 1, split the Pane so it shrinks, then run `batty-beta list panes
   --include-dimensions`. The reported frame is Tab 2's last-laid-out
   frame if Tab 2 is iterated last and its view has a non-zero frame,
   not necessarily the active Tab's.

Step 3's outcome depends on Tab order and on whether Tab 2 was ever
active; the code reading in item 3 is the authority, not the manual
repro.

## Expected behavior

Acceptance criteria (the Open questions decide the shape; these hold
whichever way they go):

1. **The help text and the output agree.** Either `visibleRect` is
   populated whenever `frame` is, or the field and the `visible=` branch
   are removed from the payload, both printers, both `@Flag` help strings
   and both `capabilities --json` descriptions. No flag promises a field
   that never appears.
2. **If kept, `visibleRect` has a written definition** in
   `TopologyPayload.swift`'s doc comment that matches what the builder
   computes (Open question 1), and a BattyKit unit test asserts it for a
   known view frame.
3. **A frame is reported only when it describes something on screen
   now,** or the payload says it does not. Concretely: a visible Pane of
   the selected Session reports its active Tab's current frame; a Pane in
   a non-selected Session either reports no frame or the payload carries
   an explicit marker (Open question 2); a hidden Pane reports no frame
   (keeps #0447's behaviour); a non-terminal Pane reports no frame
   (`testIncludeDimensionsReportsFramesOfVisiblePanes` line 140 already
   asserts this).
4. **The frame comes from the active Tab.** The builder selects
   `tabs.first { $0.id == activeTabID }` (or equivalent) rather than
   iterating all Tabs; the inactive-Tab fallback, if any, is deliberate
   and documented in the builder.
5. **BattyKit unit tests pin every branch** of the frame decision:
   hidden Pane → nil; non-terminal Pane → nil; background Session →
   whatever criterion 3 decides; active Tab chosen over an inactive Tab
   with a different frame; `visibleRect` per criterion 2. These run under
   `./build.sh unit` using the `terminalNSView` seam, with no sleeps.
6. **The existing UI test still passes in the VM**, extended with a
   background-Session case if criterion 3 chooses "no frame" or a marker
   (the test already creates `left`/`right`/`below`/`hidden`/`view`
   Panes; add a second Session via `BattyCLI.newSession`, focus the
   first, and assert the second Session's Panes per the decision).
7. `./build.sh`, `./build.sh unit` and the VM UI suite pass. Docs that
   describe the flag say what the fields mean if the implementer touches
   them. On `main` today neither `.claude/skills/batty-cli/SKILL.md` nor
   `docs/batty-cli-install.md` mentions `--include-dimensions` (grep:
   none), so the help strings and `capabilities --json` are the only
   documentation.

## Actual behavior

- `visible=` is never printed; `"visibleRect"` is never present in
  `--json` output (`TopologyPayloadBuilder.swift:174`).
- A Pane in a background Session reports the frame its view had when the
  Session was last selected (`TerminalHostStore.swift:397-398`, `:431-432`
  leave `view.frame` alone when hiding).
- The reported frame is whichever Tab's view is iterated last and has a
  non-zero frame (`TopologyPayloadBuilder.swift:134-160`), not
  `activeTabID`'s.
- Only the hidden-Pane branch is guarded (`:132`) and only a VM-only UI
  test exercises it; `./build.sh unit` covers none of the frame logic.

## Notes

### Where the numbers come from

`TerminalHostStore.Placement.frame` is "host-local" (`TerminalHostStore.swift:66-69`,
`:552-560`): the placeholder measures itself in the
`TerminalHostInstaller.coordinateSpaceName` space
(`TerminalPlaceholderView.swift:45-48`) and the host writes that straight
into `view.frame` (`TerminalPlaceholderView.swift:20-21`). So `frame` in
the payload is in the terminal host's coordinates (AppKit, origin
bottom-left of the host), not screen or window coordinates. The payload
doc comment (`TopologyPayload.swift:97`) does not say so; whatever this
issue decides about `visibleRect`, criterion 2 should record the
coordinate space for `frame` too.

### A cheap signal the builder already has

`AppKit`'s `view.isHidden` is true for exactly the views whose frame is
stale under items 2, 3 and 4: `TerminalHostStore` hides a view whenever
its placement is not visible (`:397-398`, `:431-432`), and
`isVisible` is `tab.id == pane.activeTabID && isSessionSelected`
(`PaneView.swift:252`). Gating on `!view.isHidden` instead of (or as well
as) `!pane.isHidden` would cover all three stale cases in one check and
would also pick the active Tab automatically, because only the active
Tab's view is unhidden. The implementer should weigh it against an
explicit `activeTabID` lookup plus a Session-selected flag passed down
from `SessionRuntime.topologyPayload(isActive:)`
(`TopologyPayloadBuilder.swift:53`), which is more legible and does not
depend on AppKit state. `TerminalSurfaceFocuserTests.swift:34-39`
already sets `view.isHidden = true` on a bare `AppTerminalView` in a
unit test, so either approach is unit-testable.

### Original intent

`issues/0144.md` (status still `open`, metadata in a non-standard
format) is the spec. `:46-51` sketches `visibleRect` as a sub-rectangle
of `frame`; `:95` says to read "the active session/tab window's `frame`
and available `visibleRect` in its owning terminal surface"; `:96`
asks for "a fresh snapshot (not cached)". The builder reads live view
state, so items 2 and 3 are not caching bugs; they are reading live
state from views the host deliberately leaves un-updated while hidden.

### Constraints

- `docs/swiftui-observation-rules.md`: the builder runs on an XPC
  request, not in a view update; reading `view.frame` / `view.isHidden`
  is fine. It must not write any observed state.
- `TopologyPanePayload` decoding must stay tolerant of absent fields
  (`TopologyPayload.swift:143`, `decodeIfPresent`) so an older CLI keeps
  working against a newer app and vice versa. Removing `visibleRect`
  from the encoder is wire-compatible; renaming or changing its meaning
  needs the same care #0379 took for `kind` (`:146-149`).
- Scope rule from #0447: the UI suite does not fix product defects; this
  issue is where the product change goes.

## Open questions

1. **Keep `visibleRect` or drop it?** The payload comment says "frame
   minus window chrome", but every Pane's `frame` is already inside the
   content area, so that definition yields `frame` itself. A meaningful
   alternative is the part of the Pane's frame not covered by the Pane's
   own chrome (tab bar, toolbar), or the intersection with the window's
   visible content rect after the Sidebar. If no consumer needs it (#0144
   names none for `visibleRect` specifically; its `jq` example at
   `issues/0144.md:73-75` reads `visibleRect.width`), dropping the field
   is less code than defining it. User decision.
2. **Background Session: omit the frame, or mark it?** Omitting is
   consistent with the hidden-Pane rule (#0447) and with
   `BattyScreen.mismatch`'s "each visible Pane of the selected Session
   has its anchor on screen" (`BattyUITests/Support/BattyCLIHarness.swift:388-392`).
   Marking (for example reporting the frame plus relying on
   `TopologySessionPayload.isActive == false`) preserves information an
   agent planning a split in a background Session might want, at the
   cost of the frame being from an unknown time. The filer leans to
   omitting; user decision.
3. **Fallbacks for a Tab whose view has a zero frame.** The
   `bounds`/`subviews` fallbacks (`TopologyPayloadBuilder.swift:143-158`,
   from `e6416c5d`) exist for "layout hasn't run". With an
   active-Tab-only lookup, is a zero-frame active Tab (first layout
   pending) reported as nil, or are the fallbacks kept? Nil is simpler
   and honest; implementer's call unless the user cares.
4. **Should `pane show` / `pane focus` on a background Session make the
   frame fresh?** Out of scope here unless the user wants it; noting
   because an agent that reads a nil frame for a background Pane has no
   verb to "lay it out" without switching Sessions.

## Testing notes

- Unit tests: `./build.sh unit` on the host. Build the fixture the way
  `AppStateStoreTopologyPayloadTests.topologyPayloadReportsHiddenPane`
  does (`AppStateStore()`, `splitFocusedPane`, `hidePane`), then assign
  `tab.terminalNSView = AppTerminalView(frame: NSRect(...))` as
  `TerminalSurfaceFocuserTests` does, set `view.isHidden` where the
  design uses it, and call `pane.topologyPayload(isFocused:
  includeDimensions: true)` or `store.topologyPayload(includeDimensions:
  true)`. Assert the `Rectangle` values exactly. Use a non-zero frame on
  the inactive Tab that differs from the active Tab's so the active-Tab
  assertion cannot pass vacuously. No `Task.sleep`, no polling.
- UI tests: only inside the Tart VM via `tools/run-ui-tests-vm.sh
  BattyUITests/CLIReadVerbTests`, never on a host Mac (AGENTS.md "UI test
  automation", #0409). Commit first; the runner tests `git archive HEAD`.
  `BattyCLIHarness.swift:41`, `:137` already parse `frame` from JSON;
  extend `CLITopology.Pane` with `visibleRect` only if Open question 1
  keeps it.
- The filer ran no build and no test for this filing; the line
  references are from reading `main` at `d97e6b18`.
