## Description

#0413 added `BattyUITests/CLIRemoteControlTests.swift`, `BattyUITests/CLIViewPaneTests.swift` and `BattyUITests/Support/BattyCLIHarness.swift` (branch `issue/0413`, 29/29 passing in VM run 5 on `449c3f98`). Its own "Not covered" section and the review of that branch list behaviors that `docs/batty-cli-install.md`, `.claude/skills/batty-cli/SKILL.md` and the CLI sources under `BattyKit/Sources/batty/` document as guaranteed but that no test exercises, plus assertions that would still pass if the flag under test were silently dropped. Each gap below was re-checked against the sources on 2026-10-09; the file and line references are what the check found.

**This issue depends on #0413 merging to `main` first.** Everything here extends that suite; nothing here is a prerequisite for it.

### A. Behaviors with no test

1. **`pane focus` / `tab focus` aimed at a non-selected Session.** `AppStateStore.focusPaneForXPC` and `focusTabForXPC` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift`) call `window.setSelectedSession(id:)` on the target's owning Session before focusing, so the verbs are documented (SKILL.md §5, `TabFocusCommand` doc comment) as switching the selected Session. `testPaneFocusMovesTheFocusedPane`, `testFocusMovesBetweenTerminalAndViewPane` and `testTabFocusMovesTheActiveTabChip` all target Panes and Tabs inside the already-selected Session, so the Session switch is never observed. Only `session focus` is tested against a background Session.
2. **`notify` aimed at a background Session.** `AppStateStore.recordCLINotification` computes `effectivelySeen = location.isFocused && isOwnerKey` and takes the `recordOrCollapse` + `propagateUnseenForced` path when the target Tab is not focused. `testNotifyPostsBellFeedEntries` only notifies the selected Session's focused Tab, so the unseen path, the Sidebar's unseen badge and the collapse behavior are untested through the CLI.
3. **Coverage reporting.** #0413's Scope says "The suite writes out (as test output, and recorded in the resolution) a per-verb table". The resolution table exists in `issues/0413.md`, but a grep of both test classes for `print(`, `XCTAttachment` or "coverage" finds nothing that emits it as test output. Either emit it (an `XCTAttachment` from a suite-level teardown, or a static table attached by the first test) or declare in this issue's resolution that the markdown table is the deliverable.
4. **`--include-dimensions`.** Both `ListCommand` and `SessionInfoCommand` accept it and the plain-text printers add `frame=`/`visible=` fields; the JSON `TopologyPanePayload` carries `frame` and `visibleRect` (`BattyKit/Sources/BattyXPCCore/TopologyPayload.swift:98-100`). No test passes the flag. A test should assert the reported `frame` of a visible Pane is non-empty and consistent with the on-screen anchor frame, and that a hidden Pane reports no frame (or whatever the payload documents).
5. **`list sessions` / `list tabs`.** `ListCommand.Scope` has three cases; `testStatusSessionInfoAndListAgreeWithTheScreen` only runs `list panes` (plus `list --json`). `sessions` is the default scope and `tabs` is the only plain-text view that prints Tab ids, so both are user-facing and untested.
6. **`session info` without `--session`.** Documented as "flag → `BATTY_SESSION_ID` → focused Session" (`docs/batty-cli-install.md` command table; `SessionInfoCommand`). The relay carries no `BATTY_*` environment, so running `session info --json` with no flag from the test process exercises the app's focused-Session fallback directly. `testStatusSessionInfoAndListAgreeWithTheScreen` always passes `--session`.
7. **`notify --sound`, and the entry's title/body and Tab attribution.** `testNotifyPostsBellFeedEntries` only counts `bell-feed-entry.*` identifiers. `formatNotifyMessage` builds `"\(title)\n\(body)"` and `BellFeedRow` renders `entry.summary ?? entry.message` (`BellFeedView.swift:162`) and the `pathLabel` (`Session › Pane N › Tab`), but neither `Text` has an identifier, so the test cannot assert which Tab the entry is attributed to or that the body made it through. `--sound` only reaches `BellNotifier.post(... playSound:)`, which sets `content.sound` on a `UNMutableNotificationContent` gated by `SettingsPreference.resolvedBellSound()`; it has no on-screen effect. Either add identifiers/values to the row's message and path labels (production change, a11y only) or declare attribution and `--sound` out of scope with that reason.
8. **Focused-element fallback for `pane split` without `--pane` and `notify` without `--tab`.** `AppXPCService.perform` resolves `request.paneID ?? AppStateStore.shared.focusedPaneIDFallback()` for `paneSplit` and `request.tabID ?? focusedTabIDFallback()` for `notify` (`BattyKit/Sources/BattyKit/XPC/AppXPCService.swift:121, 206`). Every CLI call in the suite names an explicit id (the harness doc comment says so), so the fallback — the path a human typing `batty-beta pane split` in a non-Batty terminal actually hits — is never exercised.
9. **SKILL.md §4 `--unique` rules.** `AppStateStore.findUniquePane` matches `session.tree.visiblePanes` only, and `AppXPCService` returns the match before any focus write, so (a) a hidden Pane of the kind is not a match and a new one is created, and (b) a match never moves focus. `testUniqueReusesTheSameGitStatusPane` neither hides the Pane between calls nor reads `focusedPaneID` after the match.
10. **SKILL.md §5: `focus` brings the window forward.** `AppStateStore.activateWindow` deminiaturizes, calls `makeKeyAndOrderFront` and `NSApp.activate(ignoringOtherApps:)` for all three focus verbs. No test checks it. A VM-feasible check: miniaturize the window (Cmd-M) or activate another app, run `pane focus <id>`, and assert the Batty window is key/frontmost again (and not miniaturized).

### B. Assertions that pass without proving what they are named for (from the #0413 review)

1. **`testSplitGitStatusRendersTheFixtureRepository`** asserts only `git-status.snapshot` exists. `BattyCLI.makeGitRepository` writes `untracked-file.txt`, and `GitStatusPaneView.swift:266` gives each file row `git-status.file.<path>`. Assert `git-status.file.untracked-file.txt` exists: that is the only assertion that proves the Pane scanned `--path` rather than the source Pane's cwd.
2. **`testSplitGitStatusWithNonRepositoryPathShowsNotARepository`** cannot prove `--path` because the source Pane's cwd (the temp home) is not a repository either, as its own comment admits. Give the source Pane a repository cwd (for example `new <repo>` then split that Pane with `--path <plain-dir>`) so the not-a-repo state can only come from `--path`.
3. **`testSplitProcessStatusAcceptsPid`** passes if `--pid` is dropped on the wire: the pid reaches `AppXPCService.swift:151` (`request.viewOptions?["pid"]`) and the Process Status content, but `TopologyPanePayload` has no pid field (its fields are `id`, `isHidden`, `isFocused`, `activeTabID`, `tabs`, `kind`, `frame`, `visibleRect`), so `list --json` cannot confirm the pin and the view exposes nothing to read it from. Verifying it needs either a payload field or an accessibility value on the Process Status header naming the pinned pid; pick one and assert it, or declare the pin unverifiable with that reason.
4. **`testIDReportsThePaneItRunsIn`** asserts `id` outside a Pane exits `!= 0`. `IDCommand.run()` throws `ExitCode.failure` on `BattyIdentityContext.resolve()` failure, which is exit `1`. Assert `== 1`.
5. **`testBadTargetsExitWithDocumentedCodesAndChangeNothing`** has no malformed-UUID case for `notify --tab not-a-uuid` or `session info --session not-a-uuid`. Both resolvers throw `ExitCode.failure` on `.malformedFlag` (`NotifyCommand.resolveTargetTabID`, `SessionInfoCommand.swift`'s file-private `resolveTargetSessionID`), so both belong in the `malformed` list.
6. **`BrokerReachabilityTests`** carries its own `relay(_:)`, `CLIResult` and `appUnderTest()` that duplicate `BattyCLI.run`, the harness `CLIResult` and `BattyCLI.appBundleURL(from:)`. Rewrite it on the shared harness so a relay protocol change (the `__EXIT__` marker, the port) has one place to update.
7. **Process Status run-state chip and banners still have no identifiers.** `ProcessStatusPaneView.swift` has exactly three (`process-status-view`, `process-status.choose-process`, `process-status.running-process-picker`); the `stateChip`, `exitedBanner`, `permissionDeniedBanner`, `unavailableBanner` and `noSelectionState` views called out in #0413's Notes are still unidentified. Add them (a11y-only production change; the state as an accessibility value, not the localized text) so a `--view process-status` test can assert the pinned process's run state, which also closes B.3.

## Expected behavior

Each item in A and B is either covered by a test in `CLIRemoteControlTests` / `CLIViewPaneTests` (or a sibling class on the same harness) that passes in the Tart VM, or is listed in this issue's resolution as out of scope with the specific reason (for example "`--sound` has no on-screen effect; verifying it needs a `UNUserNotificationCenter` seam"). No item is left silently uncovered. Where an item needs an accessibility identifier or value in production code, that change is a11y-only and is listed in the resolution's Files changed.

## Actual behavior

The behaviors in A have no test; the assertions in B pass whether or not the flag or exit code they are named for is honored.

## Notes

- Run through `tools/run-ui-tests-vm.sh BattyUITests/CLIRemoteControlTests BattyUITests/CLIViewPaneTests BattyUITests/BrokerReachabilityTests` only; never on the host (#0409, #0412).
- Every CLI call still goes through the #0419 relay, so A.6 and A.8 test the app's focused-element fallback, not the `BATTY_*` environment fallback; the environment path is already covered by `testAgentInsideAPaneOpensGitStatusUniquelyTwice` and `testIDReportsThePaneItRunsIn`.
- For A.1 and A.10, `activateWindow` is a no-op when no `NSWindow` is registered; in the VM a window always is, so an assertion that the window is key after the verb is meaningful there.
- Any product defect these tests surface (for example a focus verb that does not switch the Session, or a dropped `--pid`) is filed as its own issue and linked here, per #0413's rule; fixing it is not in this issue's scope.
