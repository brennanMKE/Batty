## Description

Two small introspection gaps that together force agents into guesswork.

**`batty status` emits one prose line and has no `--json`.** Verified in `BattyKit/Sources/batty/StatusCommand.swift`: the command prints

```
batty: pid 4821 uptime 132.4s windows 1 sessions 3 tabs 7 path=/Applications/Batty.app version=1.4.0
```

and there is no `--json` flag anywhere in the file. Every other read verb has one — `batty list --json`, `batty session info --json`, `batty id --json`. A script that wants the pid, the Session count, or (since #0361) the answering bundle's path and version has to regex a human-readable sentence whose wording is not a contract. The data is already a Codable wire type: `StatusPayload` (`BattyKit/Sources/BattyXPCCore/StatusPayload.swift`) carries `pid`, `uptimeSeconds`, `windowCount`, `sessionCount`, `tabCount`, `bundlePath`, `appVersion`. Encoding it is nearly free.

**There is no `batty capabilities` verb.** `docs/batty-cli-design.md` lists it three times — §E's "cheap introspection worth having early", the verb catalog's `batty capabilities [--json]` — list supported verbs **[2-way or static]**", and item 10 of its priority list, "self-describing CLI so agents can discover verbs". None of it is built. An agent facing an installed `batty` has no way to ask what this build can do, and the CLI binary a user's `/usr/local/bin/batty` symlink resolves to may well be older than the running app.

## Expected behavior

- **`batty status --json`** prints the encoded `StatusPayload` and nothing else on stdout. The existing prose line stays the default, unchanged — it is what a human types.
- **`batty capabilities [--json]`** prints the verb roster and the exit-code vocabulary. Plain text for humans, JSON for scripts.

## Pinned decisions

- **`capabilities` is static, with no XPC round-trip.** The CLI and the app ship together in one bundle, so the CLI knows its own verb list at compile time; asking the app would add a failure mode (broker unreachable) to a command whose entire job is to work before you know whether anything else does. It must succeed with exit 0 even when Batty is not running.
- **Compile the data in, do not hand-maintain a second list.** The exit codes already exist as one source of truth in `BattyXPCCore/XPCExitCode.swift`; derive from it. Derive the verb roster from the ArgumentParser command tree where practical, so a verb added later cannot silently go unreported.
- Report verbs that are actually wired in this build. `XPCVerb.watch` exists app-side but has **no CLI command** ([#0145](0145.md) owns finishing it) — `capabilities` must not advertise a `watch` verb the CLI cannot run. When #0145 lands, its verb appears here automatically if the roster is derived rather than hand-written.

## Notes

- `--json` on `status` must not print the prose line as well; mixed output breaks `jq`. `docs/batty-cli-agent-workflows.md` already tells agents to use `--json` forms and treat the plain-text forms as for people — this makes `status` honor that rule.
- Encode with the same conventions the other `--json` verbs use so an agent sees one house style across the CLI.
- Keep the JSON shape additive and forward-compatible for the same reason the topology payloads are: an installed CLI can be older or newer than the app that answers it.
- `capabilities` is a natural place to state which exit code means what, and that is the part agents get wrong most often — [#0368](0368.md) is separately fixing `docs/batty-cli-agent-workflows.md`'s exit-code table, which is verified stale (it stops at `5`, omitting `6` app-running-but-unregistered and `7` app-bundle-unresolved). Deriving both the doc and this verb from `XPCExitCode.swift` is what stops them drifting again.
- Both halves are mechanical and independently testable; they are filed together because they are the same "let scripts introspect instead of guessing" gap, and separately from the mutation verbs because neither changes app state.

## Resolution notes

> 🟢 Resolved 2026-09-02 — `batty status --json` emits machine-readable state
> on every path including failures, and a new `batty capabilities` verb lets an
> agent discover the verb roster and exit-code vocabulary without a round trip.

## Fix

**`status --json`** encodes the existing `StatusPayload` on success and, on
every failure branch, emits `{"state":…, "exitCode":…, "message":…}` on stdout
before throwing the same exit code as before. JSON goes to stdout, prose to
stderr, on every path — a `jq` pipe is safe.

**`capabilities [--json]`** derives its roster by walking
`BattyCLI.configuration.subcommands`, so a verb added later is reported
automatically, and derives exit codes numerically from `XPCExitCode` plus
`ArgumentParser.ExitCode` rather than duplicating them. It makes no XPC call,
so it answers when the app is not running — which is the case an agent most
needs it for.

## Review

Reviewed by `claude-opus-5`, approved first pass. It verified the roster by
running the real binary rather than trusting the walk, and confirmed the
omission of `watch` is real (the XPC verb exists; no CLI command does), that
`session`/`pane` are correctly absent because neither declares a
`defaultSubcommand`, and that `capabilities --bogus` exits 64 exactly as it
advertises. It also confirmed the nine codes match #0368's corrected table
line for line.

Its strongest finding was structural and better than claimed: `state` and
`exitCode` cannot disagree, because `fail(state:exitCode:message:)` uses one
variable for both the JSON body and the thrown `ExitCode`, and **both switches
are exhaustive with no `default:`** — so a new failure case is a compile error,
not a silent prose-only exit.

The anticipated conflict with #0368 did not exist: `git merge-tree` produced a
clean tree, and both sets of doc edits survive intact.

## Gotchas

- **The `Package.swift` line settles #0365's blocker but not its ask.** Adding
  `"batty"` to `BattyKitTests`'s dependencies makes `@testable import batty`
  work — the reviewer confirmed `AppConnectDance`, `AppBundleLocator`,
  `RunningAppChecker`, `StatusCommand` and `SessionInfoCommand` are all now
  reachable. That **invalidates #0365's framing**: it proposes three structural
  options (move to a library target, extract one, add a test target), and a
  fourth cheaper one existed. But **none of #0365's four seam assertions are
  written**, so it stays open with reduced scope, and its "Why no test uses
  them" section is now factually stale. The shipping link graph is unchanged —
  `batty` still depends only on `BattyCLICore`, `BattyXPCCore` and
  `ArgumentParser`, so #0365's no-Sparkle/no-libghostty discipline holds.
- **`collectVerbs`' name fallback diverges from ArgumentParser's.** It uses
  `String(describing: type)` where ArgumentParser kebab-cases. Latent — every
  current command sets `commandName` explicitly — but a future verb without one
  would be advertised under a name that does not work. A test asserting every
  walked command declares an explicit `commandName` would close it.
- **The `state`-string pairing test is tautological.** It declares its own
  `(state, code)` table and checks the payload echoes it, never reading
  `StatusCommand`'s call sites. The *numbers* are safe by construction; only the
  string label is unguarded. All seven are currently correct.
- **`capabilities` reports verbs but not flags** — an agent still cannot
  discover that `list` accepts `--json`. In scope as filed; the obvious next
  increment if agent self-description is the goal.
- **`docs/batty-cli-agent-workflows.md` does not mention either addition**,
  despite being the agent-facing doc that carries the exit-code table and tells
  agents to prefer `--json`. Worth a pointer to `capabilities` as the discovery
  entry point.
