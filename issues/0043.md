# 0043 — Sidebar session row keeps overwriting the user-set name with the live terminal title

| | |
|---|---|
| **Status** | open |
| **Module** | Sidebar / Session |
| **Platform** | macOS |
| **First seen** | 2026-05-08 |

## Description

In the sidebar, every session row's label collapses to the live terminal title (e.g. `brennan@host`, the default zsh prompt-set title). The user-set session name (`Session 1`, or whatever was set via Rename) flashes briefly and is then replaced. This makes sessions indistinguishable from each other in the sidebar — defeating the whole point of named workspaces.

User reproduced 2026-05-08: "the session name in the left sidebar changes to USER@HOST all the time. It does not show the session name because it gets replaced. Create an issue to leave the session name."

The same logic is in the **Session menu** (`BattyCommands.sessionMenuTitle`) and probably has the same problem.

## Steps to reproduce

1. Launch Batty.
2. Note the sidebar shows "Session 1" briefly.
3. Wait for the shell prompt to render — the row label changes to `<user>@<host>` (or whatever the shell sets via OSC 0/1/2).
4. Right-click → Rename → "Frontend" → Enter. Row briefly shows "Frontend", then reverts to `<user>@<host>`.

## Expected behavior

The sidebar row shows the **user-set session title** (`session.title`), independent of what the terminal sets via OSC. Renaming a session sticks. Default-named sessions show "Session 1", "Session 2", etc.

## Actual behavior

`SessionRow.displayTitle` and `BattyCommands.sessionMenuTitle` both prefer the live terminal title over the user-set title:

```swift
// in SessionSidebarView.swift
private var displayTitle: String {
    let live = session.terminal.title
    return live.isEmpty ? session.title : live
}
```

The intent (per `#0016`) was that the **per-tab chip** prefers the live title — that's the right call inside a pane where the chip identifies "what's running in this tab". But the **session-level identity** in the sidebar is workspace-level metadata; it should be sticky.

## Acceptance criteria

- `SessionSidebarView`'s `SessionRow.displayTitle` returns `session.title` directly (no live-title fallback). When a session is freshly created with the default name, "Session N" shows; when renamed via the context menu, the new name sticks regardless of what the terminal title becomes.
- `BattyCommands.sessionMenuTitle(at:)` returns `session.title` similarly. The "Session" menu in the menu bar shows user-set names so Cmd-Option-1..9 entries are recognizable.
- `SessionDetailView.navigationTitle` keeps showing the live terminal title — that's the **window** title, conventionally "what's currently happening", and matches Mac terminal app norms (Terminal.app and iTerm2 both put the live title in the window chrome).
- Manual verification: rename a session to "Frontend"; sidebar shows "Frontend" and stays "Frontend" after the shell sets its title; Session menu also shows "Frontend"; window title shows the live `<user>@<host>` or whatever OSC says.

## Notes

- The fix is small — a few lines in two files (`SessionSidebarView.swift` and `BattyCommands.swift`). PRD §6.6 (Tab) and Concepts → Tab still prescribe the focused-surface-process → cwd → user-override resolution **for tabs**. That's correct and should not be touched. This issue is **only** about session-level labels in the sidebar/menu.
- Once `#0014` (M3, tabs in panes) lands, the session-row label could optionally include "Session 1 — 3 tabs" or similar; out of scope here. Just stop the overwrite.
