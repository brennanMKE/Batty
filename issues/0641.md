# 0641 — Menu-routed shortcuts act on the Window behind an attached sheet

| | |
|---|---|
| **Status** | resolved |
| **Module** | App / Window |
| **Platform** | macOS |
| **First seen** | 2026-11-15 |
| **Priority** | medium |
| **Target** | 1.4.0 |

## Description

While a sheet or sheet-style dialog is attached to a Window, the main menu's Session, Pane and Tab items still act on that Window, behind the sheet. Their key equivalents reach the menu because `BattyShortcuts.handle` declines every chord while the sheet is key, so ⌘N adds a Session, ⌘T adds a Tab, ⌘W closes the focused Tab, ⌘1…9 switch Sessions, the split, focus and divider chords rearrange the Session, ⇧⌘X types `exit` into the Terminal, and **Pane ▸ Background Images…** stacks a second sheet. All of this happens behind a sheet that the user believes holds focus.

#0635 found this and fixed only the Reminder entry points (Remind Me… and Edit Reminder…). The rest was left out of scope ("Same defect elsewhere" in `0635.md` `## Plan`, and its Review notes).

**Two of these actions destroy state, not just rearrange it** (see "Data loss" below): ⌘W can close an idle Tab, ending its Terminal Session, and ⇧⌘X sends `exit\n` into the focused Terminal. Both happen behind the sheet with no confirmation. This issue is filed untargeted, as the orchestrator asked, because the full fix changes about 40 actions just before 1.4.0. The orchestrator or the user should decide whether that destructive subset is split out for 1.4.0.

## Steps to reproduce

1. With one Session that has two Tabs, both at an idle shell prompt, right-click the Session in the Sidebar and choose **Rename**. The Rename Session sheet is up and key.
2. Press ⌘W.
3. Cancel the rename.

## Expected behavior

While any sheet or dialog is attached to a content Window, no menu item that targets a Window acts on that Window. Its chord is consumed or beeps, and the sheet keeps focus. Once the sheet is gone, every item works again with no stale disabled state. This is what #0635 did for ⇧⌘R.

## Actual behavior

The focused Tab behind the sheet closes during step 2. The same path runs every item listed below.

## Root cause (verified at `da1a534f`)

- **The chord reaches the main menu.** `BattyShortcuts.handle` returns false at `guard appStore.keyWindowIsContentWindow()` (`BattyKit/Sources/BattyKit/Commands/BattyShortcuts.swift:34`). A SwiftUI sheet's window is not in `nsWindowMap` (`Runtime/AppStateStore.swift:1143-1146`), so while the sheet is key the event falls through to the main menu's key equivalents.
- **The menu's target is the Window behind the sheet.** Every action closure in `BattyCommands` reads `actionWindow`, which is `store.menuTargetWindow()` (`Commands/BattyCommands.swift:71`). `menuTargetWindow(projectEditorIsKey:projectPickerIsKey:auxiliaryWindowIsKey:)` (`Runtime/AppStateStore.swift:1349-1358`) returns nil only for the Project Editor, the Open Project picker or an auxiliary window. `isAuxiliaryWindow` walks a sheet up to its parent, so "a sheet or child window over a content window is not auxiliary" (`:1309-1323`). Then `defaultTargetWindow()` (`:1240-1251`) falls back to `recentlyKeyWindowIDs`, which is the Window behind the sheet.
- **Nothing on that path checks for an attached sheet.** #0635 added `AppStateStore.windowHasAttachedSheet(_:)` (`:2483-2485`), but its only caller is the Reminder path (`ReminderActions.openBar(for:in:windowHasAttachedSheet:)`, through `ReminderMenuItems.open()` and `BattyShortcuts.run`'s `.remindMe`).
- **The other two `menuTargetWindow` callers inherit the hole.** `newItemRoute(...)` (`:1383-1395`, File ▸ New Session, `BattyCommands.swift:157`) and `focusedTerminalTab(projectEditorIsKey:auxiliaryWindowIsKey:)` (`:1437-1441`) both resolve through it. The second is the target of `PasteDispatcher.handlePasteRequest` (Edit ▸ Paste, `BattyCommands.swift:301-305`) and `ExitDispatcher.sendExit` (Tab ▸ Exit Shell, `:661-663`).

The menu-bar path itself (a SwiftUI `Commands` item stays enabled and runs while a sheet is key) was confirmed in the VM by #0635: `testSessionMenuRemindMeWhileAnotherSheetIsUpDoesNothing` reached the enabled item over the Rename Session sheet (run `20261115-222158-30675`). The other items below were checked by reading the code, not run.

## Data loss

- **⌘W (Close Tab).** `WindowRuntime.requestCloseFocusedTab()` (`Runtime/WindowRuntime.swift:683-690`) calls `requestCloseTab(id:)` (`:661-672`), which closes the Tab at once when `needsConfirmClose` is false, that is, an idle shell. The Terminal Session ends and its scrollback is gone. A focused non-terminal Pane closes immediately through `closeNonTerminalPane`. Repeated ⌘W presses can cascade: the last Tab closes its Pane and the Session, and the last Session runs `onAllSessionsClosed` (`:443-446`). When a process is running, the close-confirmation dialog is raised behind the sheet, so it stacks instead. The `closeAuxiliaryWindow(from:)` early return (`Runtime/AppStateStore+Quit.swift:111-115`) does not catch this, because a sheet over a content window is not auxiliary.
- **⇧⌘X (Exit Shell).** `ExitDispatcher.sendExit` sends `exit\n` unconditionally into whatever the focused Terminal is running (`Commands/ExitDispatcher.swift:5-29`). At a shell prompt it ends the shell and the Tab. In an editor, REPL or ssh session, the text is typed into that program.
- **⌘V (Paste)**, over a sheet with no text field focused, sends the clipboard into the Terminal behind it. With the paste strictness setting off, a multi-line clipboard runs as commands.

If the user wants a 1.4.0 fix, these three items are the subset to split out. Everything else in the table rearranges or adds state and is recoverable.

## Proposed fix: one gate in `menuTargetWindow()`

Add the attached-sheet check to `menuTargetWindow()` itself, as #0635's Plan suggested, rather than one check per item:

- Give `menuTargetWindow` a fourth injectable input, for example `targetHasAttachedSheet: Bool? = nil`, defaulting to `windowHasAttachedSheet(candidate.id)` for the Window that `defaultTargetWindow()` resolves. It returns nil when that is true. Keep it a pure rule with the AppKit state injected, as `isAuxiliaryWindow(_:isContentWindow:)` and the other three flags are, so it can be unit-tested without an `NSWindow`.
- `newItemRoute`, `focusedTerminalTab(...)` and every `actionWindow` closure then decline over a sheet with no per-item code. Enablement stays on `keyWindow` / `keyContentWindow`, because `attachedSheet` is not observed state and a `.disabled(...)` driven by it could stay stuck after the sheet closes (the trap described in `BattyCommands.swift:62-70`, and #0635's "items stay enabled" decision).
- Edit ▸ Paste then falls through to `forwardStandardPaste()` over a sheet (`PasteDispatcher.handlePasteRequest`, the `focusedTerminalTab == nil` branch), which is the right behaviour for a text field in the sheet.

Callers that must **not** be gated, which the planner has to route around the new rule:

- **`PasteDispatcher.confirm(_:in:)`**, called from the paste confirmation sheet's own Paste button (`SessionDetailView.swift:80-83`) while that sheet is still attached. It resolves through `store.focusedTerminalTab`, so a gate inside `focusedTerminalTab` would silently drop every confirmed paste. It needs an ungated resolution (for example `defaultTargetWindow()`'s focused terminal Tab), or the gate must sit in `menuTargetWindow` callers other than this one.
- **The Command Palette and Open Quickly** run their actions from `onDismiss` / `afterDismiss` hooks (`SessionDetailView.swift:88`, `runAfterCommandPalette` at `:314-318`, and `runAfterOpenQuickly` at `:320`), when AppKit may still report the sheet as attached. #0635 kept the palette ungated for the same reason. Check whether any palette action resolves through `menuTargetWindow()`.
- XPC and CLI paths use `defaultTargetWindow()` and stay unchanged.

The per-item alternative (a `windowHasAttachedSheet` check in each of about 40 closures) is not recommended. It repeats what `menuTargetWindow` already centralises for the Project Editor, the picker and auxiliary windows, and a new menu item would have to remember it.
