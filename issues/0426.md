## Description

`SettingsPreference`'s `resolved…()` readers always read `UserDefaults.standard`, and the BattyKit tests that exercise those readers set and remove keys on `UserDefaults.standard` too. The unit-test host is bare `xctest` (see `AppearanceObserverTests.swift:22-27`), so every `./build.sh unit` run on the machine uses the same defaults domain, backed by one `cfprefsd`. With parallel agents now routinely running `./build.sh unit` from separate worktrees at once (`git worktree list` shows several), one run can set or remove a key while another run is inside its own `withPreferences` window, or while a test that never pins the key is reading it. That is the most likely cause of #0423's two AI-naming failures that nobody could reproduce.

The in-process guards don't help across processes. `@MainActor`, `@Suite(.serialized)`, and the "keep keys non-default only inside a synchronous body" rule in the `withPreferences` helpers all order work inside one xctest process. None of them can stop another process's write. #0423's branch pins `autoNameWithAIKey` around every AI-path `handleWorkingDirectoryChange` call. That shrinks the window from "the whole test body" to "one synchronous call", but it doesn't close it. The other run's `withPreferences` `defer` can still `removeObject` or write `false` between this run's `set` and its read.

The fix is to give tests a private preferences source instead of a shared global one.

`ShortcutsStoreTests` (`UserDefaults(suiteName:)`, `:11-13`) and `ThemePreferenceTests` (`isolatedDefaults`, `:13-15`) already use per-test suites. That's the pattern to extend.

A save/restore writer is worse than a set/remove one across processes. If two runs overlap, run B can "restore" the non-default value that run A saved mid-test, which leaves a stale key behind for every later run.

## Expected behavior

- A unit test that exercises a settings-gated path controls the value that path reads, and no other process can change it mid-test. Concretely, the naming path (`handleWorkingDirectoryChange`, `updateTabAutoName`) reads its toggles from a preferences source the test supplies, such as a `UserDefaults(suiteName:)` unique to that test, removed on teardown.
- Production behavior doesn't change: the app still reads `UserDefaults.standard`, and every key and default stays the same.
- Apply the same injection at minimum to the naming readers (`resolvedAutoNameFromFiles`, `resolvedAutoNameWithAI`) and to `resolvedSummarizeNotificationsWithAI`, since `BellNotificationSummaryTests` holds its key across `await`s. Also cover the other rows above, or say in the issue why a row is left alone.
- Once a test's source is isolated, remove the `withPreferences`-on-`.standard` helpers and the comments that justify `.standard` (for example `AppearanceObserverTests.swift:22-27`, and the `withPreferences` doc comment that #0423 adds). Don't leave them to describe a mechanism that no longer exists.

## Design constraints

- **No silent default that changes behavior (#0359 lesson).** #0359 was a defaulted dependency (`tabLookup = { _ in nil }`) that production paths silently inherited. Avoid that shape here. If the source is a parameter on `AppStateStore` (or an `@ObservationIgnored` property, as `nameSuggester` is at `AppStateStore.swift:55`), then either `.standard` really is the only production value, set in exactly one place, or the parameter has no default and every construction site (`AppStateStore.shared` at `:12`, plus the ~54 test files that call `AppStateStore(`) passes one explicitly. Pick one and say which. A test must not be able to fall back to `.standard` just by forgetting to pass an argument. If it can, the flake comes back without anyone noticing.
- Keep `SettingsPreference`'s key names and `default…` constants as they are. The Settings window (`@AppStorage` in `Views/SettingsView.swift`) must keep reading the same keys.
- A plain `UserDefaults` instance is enough. A protocol is only worth it if a reader needs something `UserDefaults` can't provide. Say why if you add one.
- Keep the fixture rule from `feedback_nondefault_test_fixtures`: a test that asserts "setting off → no AI call" must set the key to `false` on its own suite, not rely on an absent key.

## Resolution notes

> 🟢 Resolved 2026-09-23 — BattyKit unit tests no longer read or write `UserDefaults.standard`. Settings-gated code reads an injected `UserDefaults`, and tests use a disposable suite per test that lives under the temp directory. Nothing lands in `~/Library/Preferences`.

## Fix

Follows `docs/isolate-userdefaults-in-tests.md`, which this branch commits and which is binding. The one deviation, the suite-name shape, is the user's decision.

- **Injection.** `AppStateStore.init(…, preferences: UserDefaults = .standard)`, following the doc's defaulted-parameter shape. Every settings-gated path in the store reads `preferences`; the full list is in the `AppStateStore.preferences` doc comment:
  - auto-naming
  - summarization
  - the bell-decision system-notifications gate
  - appearance: cursor, blink and font size
  - the footprint soft limit
  - theme resolution
  - paste strictness
  - quit and close confirmation
- **Readers.** `SettingsPreference`'s readers gained `defaults:` overloads. Six zero-arg `.standard` wrappers that no longer had callers were deleted. `FootprintMonitor(defaults:)` and `windowNeedsConfirmClose(window:defaults:)` take the injected defaults.
- **`TestDefaults`** (`BattyKit/Tests/BattyKitTests/Support/`):
  - The suite name is an absolute path, `NSTemporaryDirectory()/batty-tests/<run-uuid>/tests.<fn>.<UUID>`.
  - A reverse-DNS name was tried first, as in the doc's original example. `cfprefsd` re-created its plist in `~/Library/Preferences` after teardown, 20 times out of 20.
  - `tearDown()` removes the domain and its plist.
- **Tests.** 13 test files migrated. Their `withPreferences`-style set/restore on `.standard` is gone.

## Step 1 inventory: production `.standard` reads left in place

None of these is reached from a unit test that writes the key, so none can race.

- `TabRuntime.applyShellAndAppearancePreferences` (shell, cursor, blink, font size). It is a `private static` called from `init` and `attachContext`, before any store exists. Injecting it would widen `TabRuntime` → `PaneRuntime` → `SessionRuntime` → `SplitTree` construction. A code comment gives the justification.
- `BellNotifier` (`resolvedSystemNotifications()`, `resolvedBellSound()`). Tests use `SpyBellNotifier`.
- `SettingsPreference.registerDefaults()`. It has no caller anywhere, and was already dead code before this issue.
- `PinnedThemes.load()` / `save()`, `BattyShortcuts.currentCmdNumberTarget()`, `ThemeSelectorView.selectTheme`, the command palette's `theme:` action, `RootWindowView.applyLegacySidebarMigrationIfNeeded`, and `UITestDriver`'s `.applyTheme` case. No unit test reaches any of them.
  - The command-palette theme action writes `.standard` directly, while other paths read `store.preferences`. That's harmless in production, where the two are the same object, but it's a latent inconsistency.
- `FootprintMonitorIntegrationTests.defaultLimitBytesProviderReadsTheRealPreference` reads `.standard` on purpose, because it pins the production default. It is read-only.

**`@AppStorage` usages:** out of scope per the doc, and listed for the record.
- `BattyCommands.swift:22-24`
- `SettingsView.swift`: shell override, paste strictness, confirm quit, cmd-number target, auto-name and AI toggles, font, cursor, themes, bell sound, notifications, summarize, footprint limit
- `RootWindowView.swift:24`
