## Resolution notes

> 🟢 Resolved 2026-11-12 — A background sheet's Cancel and the Background Images Pane removal path now restore pending image state through non-clearing setters, so a withheld image still arrives and Update Project keeps its identity.

## Description

Follow-up carved out by the #0589 review (`issue/0589`, not yet merged; see its `## Review` "Follow-up to file" and `## Gotchas`). **Fix this only after #0589 is merged.** The code it cites exists only on that branch until then. Line numbers below are from `issue/0589` at 87810e4.

#0589 replaced the Project seeds with explicit pending state: `SessionRuntime.pendingProjectImage`, `PaneRuntime.pendingImage` and `TabRuntime.pendingTabImage`. A level is pending when the open left its image out (missing, rejected, or still downloading). Pending state does two jobs. An image that arrives later reaches only a level that is still pending. Update Project keeps the stored image identity of a level that is still pending. Any write to a level clears its pending state, which is correct for a user edit.

A background sheet's Cancel isn't a user edit, but it restores through the same clearing setters. So Cancel ends the pending state it was supposed to leave alone:

- **Pane sheet, Cancel with no edit**, when the Pane's Tabs have their own values. `BackgroundOverrideEditor.cancel()` (`BattyKit/Sources/BattyKit/Views/BackgroundOverrideSettingsView.swift:168-173`) calls `target.setBackgroundOverride(originalOverride…)`. `PaneRuntime.setBackgroundOverride` (`Runtime/PaneRuntime.swift:189-196`) passes its guard whenever any Tab has its own value. It sets `pendingImage = nil` and pushes to the Tabs with `clearingOwn: true`, which clears every Tab's `pendingTabImage` (`Runtime/TabRuntime.swift:289-299`). `restoreReplacedOverrides` (`PaneRuntime.swift:385-389`) then puts the Tabs' values back through `TabRuntime.setBackgroundOverride` (`TabRuntime.swift:303-310`), which also clears `pendingTabImage`. The values come back but the pending state doesn't.
- **Tab sheet, edit then Cancel.** The restore write differs from the edited value, so `TabRuntime.setBackgroundOverride` clears `pendingTabImage`.
- **Session sheet, edit then Cancel.** `SessionRuntime.setBackgroundOverride` (`Runtime/SessionRuntime.swift:252-258`) sets `pendingProjectImage = false`.
- **Removing an image in the Background Images window.** For a Pane whose own value names the removed image, `AppStateStore+BackgroundImages.swift:151-156` keeps the Tabs' values with `replacedOverrides()`, writes the Pane through `setBackgroundOverride` and restores the Tabs with `restoreReplacedOverrides`. That clears every Tab's `pendingTabImage` the same way, though the Tabs themselves weren't edited.

## Effect

1. An image still downloading never reaches that level. The arrival path skips levels that are no longer pending (`AppStateStore+TabImages.swift:180-187`, `AppStateStore+BackgroundImages.swift:172`).
2. A later Update Project saves that level without its image identity. For a Pane or Tab, `SaveSessionAsProject.captureLevelBackgrounds`' `entry` (`Views/SaveSessionAsProject.swift:123-136`) uses the pending identity only when `pending` is non-nil. Otherwise a level with no path is stored with no image. For the Session, `captureBackground` (`:78-95`) returns early only while `pendingProjectImage` is set. Otherwise it stores the path-less value and sets `draft.sharedImage = nil` (`:94`). **For a Shared Project, that sends the image's removal to every Mac.**

## Regression

This is a regression against `main`. Before #0589, Update Project read the seeds (`projectBackgroundSeed` and the per-Tab seeds), and a sheet Cancel didn't touch them. #0589's `## Gotchas` noted only the Pane-Cancel/Tab case. The reviewer found the wider scope above.

## Steps to reproduce

Narrow, which is why it didn't block #0589:

1. Open a Project whose Session, Pane or Tab image is withheld at open: missing, rejected, or still downloading on a second Mac for a Shared Project.
2. Open that level's background sheet and press Cancel. For the Pane, the Pane's Tabs must have their own values, and no edit is needed. For a Tab or Session, edit first, then Cancel.
3. Run Update Project, or wait for the download to finish.

## Expected behavior

Cancel and the Background Images removal path leave a level's pending state as it was when the sheet opened, or before the removal. A pending image still arrives, and Update Project still keeps the stored identity.

## Suggested fix

The reviewer's suggestion: Cancel restores the pending state it started with. Snapshot it next to `originalOverride` / `replacedOverrides` when the sheet opens, and restore through non-clearing setters. `PaneRuntime.restoreBackgroundOverride` (`PaneRuntime.swift:200-204`) is the existing model for that, and the Tab and Session levels need equivalents. Apply the same treatment to the Background Images Pane path, so a removal no longer clears its Tabs' pending state.

Tests, one per level, in the style of `ProjectBackgroundOpenTests` / `SaveSessionAsProjectTests`. For each, open with a withheld image, run the editor's Cancel (for Pane: no edit, with Tab values; for Tab and Session: after an edit), then assert that (a) the level is still pending, (b) a later arrival applies, and (c) Update keeps the image identity. For the Session, also assert that `sharedImage` isn't cleared. Add a test for the Background Images removal path that checks a Tab's pending state survives.

## Root cause

Confirmed by reading the code and by the new tests failing paths: a background sheet's Cancel restored through the clearing setters (`PaneRuntime.setBackgroundOverride` with `clearingOwn: true`, `TabRuntime.setBackgroundOverride`, `SessionRuntime.setBackgroundOverride`), which end `pendingImage` / `pendingTabImage` / `pendingProjectImage` (and the Session's `projectBackgroundImageProblem`). The Background Images removal path used the same Pane write plus `restoreReplacedOverrides`, clearing every Tab's pending state.

## Fix

As planned. `BackgroundOverrideHolder` gains `pendingSnapshot()` and `cancelRestore(_:replaced:pending:)` (defaults: `.empty`, and today's `setBackgroundOverride` + `restoreReplacedOverrides`, so the Project Editor holders are unchanged). The sheet snapshots pending state into a third `@State` via `State(initialValue:)` and passes it to `BackgroundOverrideEditor.pending` (default `.empty`); `cancel()` makes one `cancelRestore` call. New non-clearing restores: `TabRuntime.restoreBackgroundOverride(_:pendingImage:)`, `SessionRuntime.restoreBackgroundOverride(_:pending:problem:)`; the Pane reuses its existing `restoreBackgroundOverride`, puts `pendingImage` back, then restores each live Tab's value and pending image. The removal path now calls `pane.restoreBackgroundOverride(…withImagePath(nil))` directly.

Divergences (conservative): `PaneRuntime.cancelRestore` returns early for a non-terminal Pane, matching its setters. `updateKeepsTabIdentitiesAfterAPaneSheetCancel` lives in `TabImageResolutionTests` (it needs that suite's hosted-image helpers), name kept. The Session tests live in `SaveSessionAsProjectBackgroundTests` (the struct in `SaveSessionAsProjectTests.swift` that has `openedSession`). Existing callers that build `BackgroundOverrideEditor` without `pending` get `.empty`, which for a Pane equals the old behavior (pending cleared).

## Review

Approved first pass (round 1). Checked:
- `TabRuntime.restoreBackgroundOverride` writes and renders the value before restoring `pendingTabImage`; render doesn't read pending state, so the order is safe.
- Pane Cancel sets a Tab missing from the open-time `replaced` snapshot to nil. That matches the old path (`setBackgroundOverride` with `clearingOwn: true` then `restoreReplacedOverrides` did the same to every Tab not in the snapshot), so it is no regression for a Tab added while the sheet was open. Its pending state is nil too, which is right: only Project open sets pending.
- The only runtime construction of `BackgroundOverrideEditor` (the sheet) passes `pending`; callers relying on the `.empty` default are tests and the Project Editor holders, which have no pending state.
- Removal path: `PaneRuntime.restoreBackgroundOverride` still pushes the path-less value to the Tabs (which render), and Tabs whose own value names the image are cleared just above it, so the removed image still leaves the Pane and its Tabs.
- The sheet's snapshot is `State(initialValue:)` in `init`, a read of the target, not an observed write during view update. Cancel's writes are button-event origin.
- Cancel with no edit is a true no-op at every level: each write is guarded on inequality, and the Session's `pendingProjectImage` is `@ObservationIgnored`.
- Not covered (pre-existing, plan decision 4): an image arriving while a sheet is open is reverted by Cancel's stale snapshot; this was already true of `replacedOverrides` before this change.

## Plan

Verified on `issue/0590` at 1770d42 (#0589 merged): every file:line cited above still matches, so the line numbers hold on `main` too. Two premises needed adding. A Session write also clears `projectBackgroundImageProblem` (`SessionRuntime.swift:256`), which Cancel should put back as well. A Tab or Session Cancel with no edit is already a no-op, because their setters return early on an equal value, so only the Pane needs the no-edit fix.

### Files

- **`Views/BackgroundOverrideSettingsView.swift`**
  - Add a value type `BackgroundPendingSnapshot` with `sessionPending: Bool`, `sessionProblem: BackgroundImageState?`, `pane: ProjectTabImage?` and `tabs: [UUID: ProjectTabImage]`, plus an `.empty` value.
  - Add two requirements to `BackgroundOverrideHolder`:
    - `func pendingSnapshot() -> BackgroundPendingSnapshot`, which defaults to `.empty`.
    - `func cancelRestore(_ value: TerminalBackgroundSettings?, replaced: [UUID: TerminalBackgroundSettings], pending: BackgroundPendingSnapshot)`. Its default is today's behavior: `setBackgroundOverride(value)`, then `restoreReplacedOverrides(replaced)` when that isn't empty. The Project Editor holders have no pending state and keep this default.
  - The sheet takes `pendingSnapshot()` into a third `@State`, next to `originalOverride` and `replacedOverrides`, using `State(initialValue:)` in `init`. That's a read, not a write, so it's allowed under the observation rules. The sheet passes it to `BackgroundOverrideEditor` as a new `pending` field.
  - `cancel()` maps the values through `restorable` as it does now, then makes one call: `target.cancelRestore(…, replaced:, pending:)`. Cancel is a button event, so these writes are event-origin.
- **`Runtime/TabRuntime.swift`**
  - Add `func restoreBackgroundOverride(_ value: TerminalBackgroundSettings?, pendingImage: ProjectTabImage?)`. It's `setBackgroundOverride` without the clear: write the value only when it differs and render only when the winning value changes. After that, write `pendingTabImage` only when it differs.
  - `cancelRestore` calls it with `pending.tabs[id]`, and `pendingSnapshot()` returns the Tab's own `pendingTabImage` under its id.
- **`Runtime/PaneRuntime.swift`**
  - `pendingSnapshot()` returns `pane: pendingImage` and every Tab's `pendingTabImage`.
  - `cancelRestore` does three things in order:
    1. Calls `restoreBackgroundOverride(value)`, which already exists and clears nothing.
    2. Puts `pendingImage` back, writing only when it differs.
    3. For each live Tab, calls `tab.restoreBackgroundOverride(replaced[tab.id], pendingImage: pending.tabs[tab.id])`.
  - In step 3, a Tab missing from `replaced` gets `nil`. That's correct because every Tab without its own value at open had `nil`, and a Pane write since then cleared any own value. Tabs closed in the meantime are skipped. With no edit, every write is guarded out, so the whole Cancel does nothing.
  - Extend the doc comment on `restoreBackgroundOverride` so it covers Cancel and image removal as well as Project open.
- **`Runtime/SessionRuntime.swift`**
  - `pendingSnapshot()` returns `sessionPending` and `sessionProblem`.
  - Add `func restoreBackgroundOverride(_ value:, pending: Bool, problem: BackgroundImageState?)`. When the value differs, it writes `backgroundOverride` and `tree.setSessionBackgroundOverride(value)`. It then sets `pendingProjectImage = pending` (that property is `@ObservationIgnored`) and writes `projectBackgroundImageProblem` only when it differs.
  - `cancelRestore` calls this new method.
- **`Runtime/AppStateStore+BackgroundImages.swift:151-156`**
  - Replace the `replacedOverrides` / `setBackgroundOverride` / `restoreReplacedOverrides` sequence with `pane.restoreBackgroundOverride(pane.backgroundOverride?.withImagePath(nil))`. That call keeps the Tabs' own values and their pending state without a round-trip.
  - The Pane's own `pendingImage` doesn't matter here. A Pane whose value names the path isn't pending, because a pending Pane has no path.

### User checklist

- Open a Shared Project on a second Mac before its Tab or Pane image has downloaded. Open the Pane gear's sheet and press Cancel. The image should still appear once it downloads.
- On a Project whose Session image is missing, edit the Session background, then press Cancel. Update Project should keep the image, and the sidebar problem badge should still show.

### Decisions (delegated, recorded here)

1. **One holder call for Cancel, not new clearing flags.** `cancelRestore` keeps pending-state knowledge in the runtimes. The editor only carries an opaque snapshot, and the Project Editor holders are unchanged through the default.
2. **The Session's `projectBackgroundImageProblem` is restored with its pending flag.** Both describe the same withheld image, so Cancel shouldn't hide the sidebar badge.
3. **The removal path uses `PaneRuntime.restoreBackgroundOverride` directly** instead of snapshotting and restoring, because removal is not a Pane edit.
4. **Out of scope: an image that arrives while the sheet is open and edited.** The edit ends pending, so the arrival skips that level, and Cancel then puts pending back with no path. Update still keeps the identity, which is the regression being fixed, and reopening resolves it. Applying a late arrival on Cancel would need the store in the editor. If it matters, file it separately.
5. **Out of scope: removing in Background Images the very image a level is pending on.** That is a separate question about whether a pending wait should end.
