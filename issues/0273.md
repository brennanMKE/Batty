## Description

Fifth step of the XPC track under umbrella #0265. This child exists to close the **two questions the experiment left unanswered** (recorded in #0265 "Predicted vs. found" items 2 and 4):

1. **Does agent registration survive Hardened Runtime + notarization + stapling end to end?** The experiment ran local development signing only — its `docs/build-and-release.md` states "No notarization" explicitly. What *was* verified: launchd refuses to start an improperly signed agent, and the agent must be signed with the same team identity as the app. Whether a notarized, stapled, quarantined build still registers and serves the CLI is unknown.
2. **Peer code-signing requirement enforcement.** `setPeerCodeSigningRequirement` (or an equivalent peer-validation mechanism — the exact API is **not verified**; it was never exercised and appears nowhere in the experiment's findings or docs) so the broker and app only accept connections from binaries signed with the same team identity. Currently any local process could connect to the Mach service.

Also in scope: whatever `scripts/release.sh` and `scripts/verify-dmg.sh` changes the agent needs (e.g. verifying the agent's signature in the DMG gate), and closing the pre-existing verification gap recorded in `docs/batty-cli-install.md` §6: the mechanism that takes `bin/batty` from "ad-hoc signed by swift build" to notarization-grade signing is *presumed* to be Xcode's automatic re-sign during archive/export but is **not independently verified** — this child's notarized-build inspection should confirm it for both `bin/batty` and the agent.

**Gate:** blocked on #0270 (the agent must exist); should follow #0272 so the channel being notarized is the hardened one.

## Resolution notes

> 🟢 Resolved 2026-07-25 — the notarization blockers are fixed, peer code-signing validation is enforced on both listeners, and the release scripts now inspect the embedded binaries directly. Two latent release-pipeline defects were found and fixed along the way.

**The issue's two headline questions remain open and can only be closed by the user** — see Gotchas. Both need a notarization run and a signed install, and this machine has no Developer ID Application certificate.

## Root cause

Three distinct problems, two of them latent and unnoticed.

**The stated one:** #0270 signed the broker with `--timestamp=none`, copied verbatim from a reference project that never notarized. Apple's notary service rejects a Developer ID-signed nested binary with no secure timestamp, so this would have failed the first submission.

**`bin/batty` was never re-signed at all.** `docs/batty-cli-install.md` §6 recorded a *presumption* that Xcode's archive/export pass re-signs it. Building with real signing disproved it: `flags=0x2(adhoc)`, `TeamIdentifier=not set`, in every configuration. A binary under `Contents/Resources/bin/` is sealed as a **resource**, not nested code, so `codesign --deep --strict` never inspects it — an ad-hoc signature there passes packaging checks silently while still failing notarization.

**The release pipeline was already broken.** Both Embed phases looped over `${ARCHS}` unquoted, and zsh does not word-split an unquoted parameter expansion. Release's default multi-arch `ARCHS="arm64 x86_64"` therefore collapsed into a single invalid `--arch "arm64 x86_64"` flag and `swift build` failed outright. This was never observed because the loop arrived with #0249 on 2026-06-23 while the newest tag, `v1.0.5`, is dated 2026-06-17 — **no release has ever run with it present**. Nothing shipped broken; the next archive would simply have been the first failure.

## Fix

**Timestamps** are now fetched only when `ACTION == install` — Xcode's own axis for this, and the value the Run Script phase actually sees during an archive (confirmed by instrumenting the phase; `-showBuildSettings` reports `ACTION=archive` and is misleading). Every other action keeps `--timestamp=none`, so ordinary iteration never blocks on reaching Apple's timestamp authority.

**`bin/batty` is signed explicitly** by the Embed CLI phase, with the same policy the broker already had.

**`${=ARCHS}`** forces zsh word-splitting in both Embed phases; Release builds now produce genuine universal binaries.

**Peer code-signing validation.** The API this issue guessed at (`setPeerCodeSigningRequirement`) does not exist. The real ones — verified in the macOS 26.5 SDK's `NSXPCConnection.h`, both `API_AVAILABLE(macos(13.0))`, comfortably under the 15.6 target — are `NSXPCListener.setConnectionCodeSigningRequirement(_:)` and `NSXPCConnection.setCodeSigningRequirement(_:)`. New `PeerCodeSigningRequirement` (requirement-string construction) and `OwnCodeSigningIdentity` (team identifier via `SecCodeCopySelf` / `SecCodeCopySigningInformation`) live in dependency-free `BattyXPCCore` and are wired into the broker's Mach-service listener and the app's anonymous listener before `.resume()`. A `nil` team identifier — an ad-hoc or unsigned local build — skips enforcement rather than locking out development.

**`scripts/release.sh` and `scripts/verify-dmg.sh`** now inspect `Contents/Resources/bin/{BattyBroker,batty}` directly: not ad-hoc, team matches the app's, `Authority` matches the app's exactly, hardened runtime, secure timestamp present, zero `@rpath`. `release.sh` also re-signs both loose binaries after export and then re-seals the app bundle, before the gate and before notarization.

## Review

Reviewed by `claude-opus-5`, two rounds.

**Round 1 caught that the new verification gate would abort every release run.** The `Authority=` extraction piped `codesign` into `awk` with an early `exit`, closing the pipe mid-write; `codesign` died on SIGPIPE, the pipeline returned 141, and `set -o pipefail` plus `set -e` killed the script. The reviewer ran it against `/Applications/Batty.app` ten times and it aborted 10/10, with no error message and no DMG. They also established that the gate *detected* the archive/export signing gap but nothing *fixed* it, so the first real release would stop at the gate with no remediation — "shipping a pipeline whose expected outcome is abort" was the objection.

**Round 2 approved after independent re-verification of the riskiest addition.** Rather than trusting the post-export re-sign block, the reviewer rebuilt the scenario on a scratch `.app` and confirmed: re-signing the two loose binaries genuinely breaks the bundle seal (so the re-seal is necessary, not defensive padding); the entitlements round-trip is byte-faithful and `--xml` is *required*, since the plain form emits a human-readable dump that would be garbage as input; `--options runtime` reproduces export's flag state exactly, as measured against the real `/Applications/Batty.app`; and the ordering is correct and idempotent. They then re-audited every pipeline in both scripts for siblings of the SIGPIPE defect, stress-testing the early-exiting consumers 20–30 times each, and found none.

The implementer's own verification was notably thorough: they reproduced the SIGPIPE abort before fixing it, and confirmed the archive-time signing premise by instrumenting the Embed phases and running a real `xcodebuild archive` (which needs no Developer ID certificate), finding both binaries stamped `Authority=Apple Development: …` inside the archive.

## Gotchas

- **The two questions this issue exists to answer are still open.** Neither can be closed without the user:
  1. **Does agent registration survive notarization and stapling?** Requires a real `scripts/release.sh` run and a quarantined install from the resulting DMG, then confirming the agent registers and `batty ping` / `batty status` succeed.
  2. **Is a foreign-team client actually refused?** Requires a throwaway, differently-signed test client and a live connection attempt against both the broker and the app, while confirming the real CLI still connects. Static `SecStaticCodeCheckValidity` evidence is not the same thing.
- **This machine cannot cut a release.** `security find-identity` shows only `Apple Development: Brennan Stehling`; there is **no Developer ID Application certificate**, so `-exportArchive` with a Developer ID identity cannot be attempted here at all.
- **Whether `-exportArchive` re-signs loose resource binaries remains unverified**, for that same reason. The post-export re-sign in `release.sh` makes the pipeline correct either way — re-signing already-correct content is a no-op — but the underlying behavior is an open question, not a settled one.
- **A binary sealed as a resource is invisible to `codesign --deep --strict`.** `Contents/Resources/bin/*` never appears in its output, so passing that gate proves nothing about the CLI or the broker. Always inspect those two with `codesign -dv` per file. This is what hid the ad-hoc `bin/batty` for a month.
- **`release.sh`'s app-level Authority gate is now tautological** — the re-sign immediately above it sets the Authority to `$SIGN_IDENTITY`, so its error text ("`-exportArchive` did not sign with the Developer ID identity requested above") can no longer fire. Harmless, but misleading if it ever appears.
- **The entitlements extraction carries `|| true`**, so a future `codesign -d` output-format change would silently strip entitlements via the `else` branch. A warning on that path would make the failure visible.
- **Only the listener side validates peers.** Outgoing connections — app→broker, CLI→broker, and CLI→app after the handoff — set no requirement, so a process owning the Mach name could impersonate the broker to both. Filed as [#0278](0278.md). Realistically defense-in-depth rather than a live exploit, since owning a launchd Mach name in the user's GUI domain already requires the ability to install a LaunchAgent.
- Minor: `docs/batty-cli-install.md` §6's first bullet has nested bold that renders oddly, and the Embed CLI comment's phrasing about the Profile action slightly undercuts its own "never block on Apple's TSA for non-release builds" rationale.

## Restricted-area and process constraints (binding)

- **`scripts/` is a restricted area per `CLAUDE.md`** — modifying `release.sh` / `verify-dmg.sh` requires explicit user confirmation before the edit, not just at review.
- **`scripts/release.sh` must never be run autonomously.** Notarization submits the binary to Apple (a shared-system action). Every notarization run in this child needs the user's explicit go-ahead, each time.
- **`Configuration/Build.xcconfig` is also restricted** if entitlement/signing settings need touching.
- **The certificate-revocation hazard:** the experiment's single most expensive line item ($27.43) was repeated *signed* local builds against an Automatic-signing project triggering certificate revocation. Iterate with `CODE_SIGNING_ALLOWED=NO` wherever signing is not the thing under test, and keep actual signed builds to the minimum the verification needs.

## Traps that apply here (copied)

- **A binary sealed as a *resource* is invisible to `codesign --deep --strict`** — `Contents/Resources/bin/batty` never appears in its output, so "the verify gate passed" does not mean the CLI (or anything script-dropped) is properly signed. Inspect the specific binaries directly (`codesign -dv` per file).
- **launchd refuses an improperly signed agent with an opaque registration failure** — if the notarized build's agent won't register, suspect the signature before the code.
- **"Unsealed contents present in the bundle root"** names neither the file nor the phase — if signing fails after packaging changes, re-check the Copy Files destinations from #0270 first.
- `verify-dmg.sh` already checks signing, notarization, stapling, and Gatekeeper acceptance under quarantine — extend it rather than duplicating it.

## Verification expectations

Genuinely cannot be automated end to end — say so plainly in the resolution. The credible verification is:

- A full `scripts/release.sh` run (user-authorized, user-witnessed) producing `dist/Batty-<sha>.dmg`; `scripts/verify-dmg.sh` passes.
- On a quarantined install from that DMG: the agent registers, `batty ping` and `batty status` succeed — the end-to-end answer to open question 1. Needs the user's runtime sign-off; mark `resolved` only per the review gate and record in Gotchas exactly which steps the user performed.
- Peer validation demonstrated both ways: the real CLI connects; an unsigned/other-team test client is refused. (The negative case needs a throwaway client binary; keep it out of the app bundle and out of the repo, or under the issue's attachments folder.)
- `codesign -dv` inspection of the notarized bundle shows Developer ID + hardened runtime + secure timestamp on the app, the agent, **and** `bin/batty` (closing the `docs/batty-cli-install.md` §6 caveat).
- `scripts/build.sh unit` stays green throughout (no code-path regressions from entitlement/signing changes).
