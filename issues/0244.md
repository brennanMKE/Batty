# 0244 — Applying a layout does nothing in the key window (picker acts on windows[0])

| | |
|---|---|
| **Status** | open |
| **Module** | Split / Window |
| **Platform** | macOS |
| **First seen** | 2026-06-17 |

## Description

Multi-window regression: choosing a layout in the layout picker has no visible effect. The layout is applied to the first window's selected session (`windows[0]`), not the key window's — so when the key window is a second window (the common case, and the picker now opens only in the key window per #0242), nothing the user sees changes.

A sweep for the same `windows[0]`-shim pattern in view code found two more instances of the same root cause, fixed together here:
- **Open Quickly** lists/jumps among `windows[0]`'s sessions only.
- **Paste confirmation** sends the confirmed paste to `windows[0]`'s focused terminal, not the key window's.

(The theme picker (#0243) and the per-window picker presentation (#0242) are confirmed working by the user.)

## Steps to reproduce

1. Open two windows (Shift-Cmd-N); the second window is key.
2. Open the layout picker in the key window and choose a layout.

## Expected behavior

The layout applies to the key window's selected session and its panes re-arrange.

## Actual behavior

Nothing happens in the key window. (The layout is silently applied to the first window's session instead.)

## Notes

- Root cause: view code resolves the target through the `AppStateStore` → `windows[0]` forwarding shim instead of the window that owns the picker. Confirmed sites:
  - `LayoutPickerView.activate()` (`LayoutPickerView.swift:97`) — `store.selectedSession?.tree`.
  - `OpenQuicklyView.allResults` / `activate` (`OpenQuicklyView.swift:50`, `:136`) — `store.sessions`, `store.jumpToTab`.
  - `PasteDispatcher.focusedTerminalTab` (`PasteConfirmation.swift:105`) — `store.selectedSession?.focusedPane.activeTab`; feeds both `handlePasteRequest` and `confirm`.
- `CommandPaletteView` is already correct — it resolves `store.keyWindowRuntime() ?? store.windows[0]` (`CommandPaletteView.swift:67,193`). That is the template; `LayoutPickerView`/`OpenQuicklyView` are presented inside `SessionDetailView`, which already holds the owning `windowRuntime`, so they should take that directly.
- Same regression class as #0240 (Phase 7), #0242, #0243.
- Logs were not retrievable while diagnosing: `log show` returns nothing for any subsystem (including system subsystems) in the working environment, and OSLog `info`/`debug` are not persisted by default. Diagnosis was by code audit.
