## Description

Multi-window regression: choosing a layout in the layout picker has no visible effect. The layout is applied to the first window's selected session (`windows[0]`), not the key window's — so when the key window is a second window (the common case, and the picker now opens only in the key window per #0242), nothing the user sees changes.

A sweep for the same `windows[0]`-shim pattern in view code found two more instances of the same root cause, fixed together here:
- **Open Quickly** lists/jumps among `windows[0]`'s sessions only.
- **Paste confirmation** sends the confirmed paste to `windows[0]`'s focused terminal, not the key window's.

(The theme picker (#0243) and the per-window picker presentation (#0242) are confirmed working by the user.)

## Steps to reproduce

1. Open two windows (Shift-Cmd-N); the second window is key.
2. Open the layout picker in the key window and choose a layout.

## Expected behavior

The layout applies to the key window's selected session and its panes re-arrange.

## Actual behavior

Nothing happens in the key window. (The layout is silently applied to the first window's session instead.)

## Notes

- Root cause: view code resolves the target through the `AppStateStore` → `windows[0]` forwarding shim instead of the window that owns the picker. Confirmed sites:
  - `LayoutPickerView.activate()` (`LayoutPickerView.swift:97`) — `store.selectedSession?.tree`.
  - `OpenQuicklyView.allResults` / `activate` (`OpenQuicklyView.swift:50`, `:136`) — `store.sessions`, `store.jumpToTab`.
  - `PasteDispatcher.focusedTerminalTab` (`PasteConfirmation.swift:105`) — `store.selectedSession?.focusedPane.activeTab`; feeds both `handlePasteRequest` and `confirm`.
- `CommandPaletteView` is already correct — it resolves `store.keyWindowRuntime() ?? store.windows[0]` (`CommandPaletteView.swift:67,193`). That is the template; `LayoutPickerView`/`OpenQuicklyView` are presented inside `SessionDetailView`, which already holds the owning `windowRuntime`, so they should take that directly.
- Same regression class as #0240 (Phase 7), #0242, #0243.
- Logs were not retrievable while diagnosing: `log show` returns nothing for any subsystem (including system subsystems) in the working environment, and OSLog `info`/`debug` are not persisted by default. Diagnosis was by code audit.

## Root cause

`AppStateStore.sessions` / `.selectedSession` / `.jumpToTab` are forwarding shims onto `windows[0]` (`AppStateStore.swift:200,209,288`), left from the #0235 multi-window refactor. Three view-level actions still resolved their target through those shims rather than the window that owns the action, so they operated on the first window regardless of which window was key:

- `LayoutPickerView.activate()` applied the layout to `store.selectedSession?.tree` (windows[0]).
- `OpenQuicklyView` built results from `store.sessions` and jumped via `store.jumpToTab` (windows[0]).
- `PasteDispatcher.focusedTerminalTab` resolved the focused tab from `store.selectedSession` (windows[0]); it feeds both `handlePasteRequest` and `confirm`.

Because the pickers now open only in the key window (#0242), the key window is commonly the second window, whose state the shims never touch — so the layout change/paste/jump silently hit the unseen first window.

## Fix

Route each action to the window that owns it, matching the already-correct `CommandPaletteView` pattern (`store.keyWindowRuntime() ?? store.windows[0]`):

- `LayoutPickerView` and `OpenQuicklyView` now take the owning `WindowRuntime` (already held by `SessionDetailView`, which presents them) instead of `AppStateStore`, and operate on `windowRuntime.selectedSession` / `.sessions` / `.jumpToTab`.
- `PasteDispatcher.focusedTerminalTab` resolves `keyWindowRuntime() ?? windows[0]`, fixing both paste paths in one place.

## Verification

`scripts/build.sh unit` — build succeeded; **337 unit tests in 40 suites passed**. The three fixes are SwiftUI view / static-helper level: the picker logic is in private view methods and the paste path depends on `NSApplication.shared.keyWindow` (which can't be set in a unit-test context), so they are not cleanly unit-testable — behavioral confirmation is the visual check below. No regressions in the existing suite.

## Files changed

- `BattyKit/Sources/BattyKit/Views/LayoutPickerView.swift` — takes `windowRuntime`; applies the layout to `windowRuntime.selectedSession?.tree`.
- `BattyKit/Sources/BattyKit/Views/OpenQuicklyView.swift` — takes `windowRuntime`; builds results from `windowRuntime.sessions` and jumps via `windowRuntime.jumpToTab`.
- `BattyKit/Sources/BattyKit/Views/SessionDetailView.swift` — passes `windowRuntime` to both pickers.
- `BattyKit/Sources/BattyKit/Views/PasteConfirmation.swift` — `focusedTerminalTab` resolves the key window.

## Gotchas

- Not covered by an automated test (view-private logic + `NSApp.keyWindow` dependence). Visual sign-off is the user's: with two windows, in the key window — (a) apply a layout and confirm its panes rearrange; (b) Open Quickly lists that window's tabs and jumps within it; (c) a confirmed paste lands in that window's focused terminal. Marked `resolved`, not `closed`.
- This was the third `windows[0]`-shim regression (after #0242 presentation and #0243 theme). A `grep -nE "store\.(selectedSession|sessions|selectedSessionID|jumpToTab|addSession|closeTab)" BattyKit/Sources/BattyKit/Views` sweep is now clean of action paths; any *new* view that needs the active window should take `windowRuntime` (or resolve `keyWindowRuntime()`), never the `AppStateStore` shim. Consider making the shim accessors `@available(*, deprecated)` within view code, or removing them once all callers are migrated, to prevent a fourth recurrence.
