`TabAutoNamingTests.swift:168` has a test with the same name, `staleCwdResultIsDropped`. The report names the `AISessionNamingTests` one. Confirm that from the next failure's output.

## What each test depends on in real time

### `cpuPercentReflectsSubstantialRealCoreUsage`: two measurement windows that don't line up, plus a live 1 s sampler

The test compares production's `cpuPercent` with an expectation it computes itself from the same kernel ticks. The two are measured over **different wall-clock windows**:

- **Expected:** ticks and `Date()` bracketed by `beforeMetrics`/`beforeTime` (`:417-418`) and `afterTime`/`afterMetrics` (`:442-443`), around a 1.2 s busy loop on a detached task (`:433-440`).
- **Production:** `ProcessCPUDeltaTracker.percentages(for:at:)` (`Runtime/ProcessCPUDeltaTracker.swift:61-82`) divides the ticks since the tracker's **previous baseline** by the wall time since that baseline. `content.sampleNowForTesting()` (`:444`) is the final sample.

Two things make the production window depend on scheduling:

1. **`setUp(visible: true)` (`:415`) starts the real periodic sampler.** `startSampling()` (`Runtime/ProcessStatusPaneContent.swift:268-283`) takes one sample, then loops `Task.sleep(for: samplingInterval)` → `performSample()` on the main actor. The default interval is `.seconds(1)` (`:195`). Every `performSample()` goes through `cpuPercent(for:)` and moves the tracker's baseline forward. The test `await`s the detached burn, which frees the main actor, so the sampler can tick during the 1.2 s burn, and again afterwards if the test's resumption is delayed. The final `sampleNowForTesting()` then measures only from the *last periodic tick*.
   - If that tick lands late in the burn, or after it, while the test waits for the main actor, the production window is mostly idle time. `cpuPercent` then comes out far below the full-window expectation, which is exactly the `> expectedPercent / 5` failure.
   - On an idle machine the tick lands around 1.0 s into the burn, and the remaining ~0.2 s is still busy, so the test passes.
2. **The main-actor hop after `.value`** (`:440` → `:442`). Under host load, and with other main-actor tests in the same process, resuming the test can take a long time. That lengthens the production window with idle time the expected window partly shares, but not in the same proportion.

Also, `getpid()` is the whole test process. CPU burned by *other* tests running in parallel lands in both windows, but unevenly.

A fix probably constructs the content with a very long `samplingInterval`, or otherwise keeps the periodic sampler out of the measurement, so the only baselines are the ones the test controls. It should also bracket the expectation with the same sample points production uses. #0395 already had to rework this test (see its round 2 B4 note); keep its non-circularity requirement.

### The two `AISessionNamingTests`: no timers, but async scheduling and process-global settings

Neither test sleeps or has a timeout. On the code path they exercise, their only non-deterministic inputs are:

- **An unstructured `Task`**, created by `AppStateStore.scheduleNameSuggestion(for:cwd:)` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:1756-1777`) and awaited through `nameSuggestionTasks[...]?.task.value`. When it runs relative to the test's own main-actor code depends on the scheduler. `staleCwdResultIsDropped` expects the in-flight task to exist (`#expect(inflight != nil)`) and the stale result to be rejected by `applySuggestedName`'s `currentCWD == cwd` guard (`:1786-1805`). `persistenceRoundTripReResolves…` expects the suggestion to *have applied* after `awaitSuggestion` (`#expect(session.title == "Meeting Notes")`).
- **`UserDefaults.standard`**, which is process-global. Whether the AI step runs at all depends on `SettingsPreference.resolvedAutoNameWithAI()` and `resolvedAutoNameFromFiles()` (`BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift:99-111`), read synchronously in `handleWorkingDirectoryChange` (`AppStateStore.swift:1699-1742`). Like most of `AISessionNamingTests`, but unlike its settings-toggle tests and every AI test in `TabAutoNamingTests`, these two tests don't wrap that call in `withPreferences(...)`. They rely on the keys being *absent*, which means default `true`. `AISessionNamingTests`' own `withPreferences` doc comment (`:304-305`) says keys may be non-default only inside a synchronous body "so parallel main-actor tests can't observe them across a suspension point".
  - Every writer of these two keys found by grep is in the main-actor `AISessionNamingTests` and `TabAutoNamingTests` and uses that synchronous pattern. So a cross-test leak isn't proven.
  - A stale persisted value left by an interrupted earlier run would fail every run, not intermittently.

Reading the code didn't find a mechanism that explains a one-off failure. **Step one is to capture the actual failure output.** Loop the suite under synthetic load (#0395 used 30 CPU hogs), for example:

```
for i in $(seq 20); do ./build.sh unit || break; done
```

Then record which `#expect` failed.

## Expected behavior

All three tests pass deterministically under host CPU contention. Each test's pass/fail depends only on inputs it controls, not on when the scheduler runs a sampler tick or a detached/unstructured task.

## Resolution notes

> 🟢 Resolved 2026-09-23 — the Process Status CPU test's measurement window is now deterministic; the AI-naming tests pin the AI-naming setting they depend on. The naming failures were **not reproduced**, so that part is a defensive fix, not a confirmed root cause.

Follow-up for the remaining cross-process exposure: [#0426](0426.md).

## Root cause

- `cpuPercentReflectsSubstantialRealCoreUsage` (argued from the code, not reproduced live): the test used the default 1 s sampling interval, so a periodic tick during or just after the 1.2 s CPU burn moved `ProcessCPUDeltaTracker`'s baseline, and the final sample measured a short, mostly idle slice.
- AI-naming tests: 81 pre-fix runs under modest synthetic load (alone, with `TabAutoNamingTests`, and the full suite) never reproduced the failures. Within one process nothing can race: every read and write is main-actor and `withPreferences` writes synchronously. The likely mechanism is cross-process: `UserDefaults.standard` for bare `xctest` goes through cfprefsd, so a concurrent unit run in another worktree (routine in this session's parallel workflow) can flip `autoNameWithAIKey` while another run relies on its unset default.

## Fix

- The CPU test constructs content with `samplingInterval: .seconds(3600)`, so only `setUp`'s immediate sample and the test's explicit sample bound the window; tears the content down in a `defer`.
- Every AI-scheduling test in `AISessionNamingTests` and `MultiWindowCWDNamingTests` pins `autoNameWithAIKey: true` in a synchronous `withPreferences` scope (tests with a nil suggester are independent of the toggle). This narrows but cannot close the cross-process window; #0426 proposes per-test preference sources.
