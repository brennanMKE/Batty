## Description

Relaunch after quitting with several Windows open is covered only by hand.

**Premise correction (verified on `main`).** The #0240 follow-up note asked for a test of "#0238 frame and relaunch restoration with N windows". That behavior no longer exists. `Batty/BattyApp.swift` puts `.restorationBehavior(.disabled)` on the content `WindowGroup` (line 49) and on the Help `Window` (line 68), by user decision of 2026-10-09 (#0444). The comment there records what that gives up: #0238's window-count, display and `@SceneStorage` restoration. It also says that "whether the first window's frame is still remembered by AppKit's own autosave is unverified". `issues/0238.md` Gotchas carries the matching "Superseded by #0444" note. So the behavior to pin down today is:

> Quit with N content Windows open → relaunch opens exactly **one** content Window, with a fresh Session, and no stale restored Window appears next to the one `AppStateStore.init` seeds.

That last clause is why `BattyApp.swift` keeps restoration off. The first Window's frame on relaunch is an open question that the test can record.

Nothing in `BattyUITests` exercises this.

- **Every launch passes `-ApplePersistenceIgnoreState YES`.** `BattyUITestHarness.stateIsolationArguments` (`BattyUITests/Support/BattyUITestHarness.swift:19`) is added in both `launchBatty()` overloads (lines 28 and 46). With it, AppKit never reads saved state.
- **Tests end with `app.terminate()`, not a clean quit.** That is about 213 call sites. macOS commits window state only on a clean quit (`issues/0238.md` Gotchas; `WindowRestorationTests.swift` header).
- **`WindowRestorationTests` covers only per-window sidebar state and new-window sessions within one launch.** Its header says frame-level restoration "is verified manually".

A clean quit is reachable from XCUITest: `ProjectsEditorQuitTests` already sends Cmd-Q and awaits `app.wait(for: .notRunning, timeout:)` (lines 55–58). `QuitConfirmation.isInUITestMode` bypasses the quit alert under `BATTY_UI_TEST_MODE`.

## Expected behavior

A `BattyUITests` test that:

1. launches;
2. opens a second, and ideally a third, content Window (Shift-Cmd-N), telling Windows apart by `identifier` and not `boundBy:` (see #0438);
3. quits with Cmd-Q and awaits `.notRunning`;
4. relaunches **without** `-ApplePersistenceIgnoreState YES`;
5. asserts exactly one content Window with one Session (the Settings and Help Windows don't count), and asserts the CLI `batty list --json` window count matches if that is cheap.

It may also record the first Window's frame before quit and after relaunch, as evidence for the open "AppKit autosave" question. It should not fail on the frame until the user decides what the frame behavior should be.

## Actual behavior

No automated test quits with several Windows and relaunches. A regression that re-enabled restoration, or that let a stale `WindowID` window appear next to the seeded one (#0444's failure class), would pass the suite.

## Notes

- **Harness opt-out.** The test needs a way to launch without `stateIsolationArguments` for its relaunch only (a parameter on `launchBatty`, or a separate helper). #0446 needs the same opt-out for `LaunchWindowGuard`, so build it once and share it.
- **Guest hygiene.** The relaunch reads real saved state, so the test must leave the guest clean for later launches, or run last. #0444 showed that a poisoned record cascades into every later test.
- **No duration waits.** Await `.notRunning` and window existence; do not wait out AppKit's ~15 s persistent-UI flush (#0444, #0446; AGENTS.md "Asynchronous tests"). The clean quit is what commits the state, so no flush wait should be needed. Confirm that in the VM.
- **Window identity.** Use `BattyUITestHarness.window(withIdentifier:in:)` / identifiers captured before each new Window opens, as `WindowRestorationTests` does. `app.windows` is z-ordered and `boundBy:` indices move on reorder (#0438).

## Acceptance criterion

A new `BattyUITests` test, run in the Tart VM through `tools/run-ui-tests-vm.sh`, quits cleanly with at least two content Windows and asserts that the relaunch shows exactly one content Window with a fresh Session. It fails if `.restorationBehavior(.disabled)` is removed from the content scene (checked once by hand on a scratch branch and recorded in the Work log). The full suite still passes after it.
