# 0624 — Selecting an image in the Background Images window makes the view jump

| | |
|---|---|
| **Status** | open |
| **Module** | Settings / Theme |
| **Platform** | macOS |
| **First seen** | 2026-11-13 |
| **Priority** | high |

## Description

User report, verbatim: "When I select an image in the Background Images view it jumps. Fix that. There's no reason for it to jump."

Clicking an image to select it should only move the highlight outline. Instead the view jumps. Selection is a highlight only in the manage window: nothing in it should change the scroll position or the layout. User-reported against the 1.4.0 release candidate.

The report doesn't say which tab (My Images or Background Sets) or how far the view jumps (back to the top, or to some other row). The plan phase should reproduce both tabs and record which one jumps. The code paths differ (see Context), so the fix may differ too.

## Steps to reproduce

1. Open File → Background Images… (also in Settings and the Command Palette).
2. On My Images, have enough images that the grid scrolls. Scroll part way down.
3. Click an image that is not already highlighted.
4. Repeat on the Background Sets tab.

## Expected behavior

The clicked cell gets the accent outline. The scroll position and every cell's position stay where they were.

## Actual behavior

The view jumps when the image is selected.

## Context

Files:

- `BattyKit/Sources/BattyKit/Views/BackgroundImagesWindowController.swift`: builds the window. Its content is an `NSHostingController` around `BackgroundImagesView(model: store.backgroundImages, mode: .manage)`, with `sizingOptions = []`. `windowDidBecomeKey` calls `model.refreshUses()` and starts `hosted.windowBecameKey()`.
- `BattyKit/Sources/BattyKit/Views/BackgroundImagesView.swift`: the My Images tab and the window shell.
- `BattyKit/Sources/BattyKit/Views/BackgroundSetsView.swift`: the Background Sets tab.
- `BattyKit/Sources/BattyKit/Views/ActiveOutline.swift`: the highlight.
- `BattyKit/Sources/BattyKit/Model/BackgroundImagesModel.swift`: `entries`, `uses`, `refreshUses()`.

Selection state:

- My Images: `@State private var selectedDigest: String?` in `BackgroundImagesView`. `click(_:)` sets `selectedDigest = entry.digest` and then `gridFocused = true` (`@FocusState`), and calls `pick` only in `.pick` mode. Each `BackgroundImageCell` gets `isHighlighted: entry.digest == selectedDigest || entry.digest == currentDigest`.
- Background Sets: `@State private var selected: HostedImageKey?` in `BackgroundSetsView`. `click(_:key:)` in manage mode (`onPick == nil`) does `if selected != key { selected = key }` and nothing else.
- The highlight is `.activeOutline(isHighlighted, cornerRadius: 6)`, an `.overlay` of a `strokeBorder` with an opacity change and `.allowsHitTesting(false)`. An overlay doesn't change the cell's size, so the outline alone shouldn't cause a layout change.

Grid and scroll containers:

- My Images: `content` puts a `GeometryReader` around `grid(columns:)`. The column count comes from the width. `grid` is a `ScrollView` holding a `LazyVGrid` of `GridItem(.flexible(), alignment: .top)`, with `ForEach(model.entries)`. The `ScrollView` itself has `.focusable()`, `.focusEffectDisabled()` and `.focused($gridFocused)`, plus the `.onKeyPress` arrow, return and delete handlers. There is no `ScrollViewReader`, `scrollTo` or `scrollPosition` in either file (grep confirms).
- Background Sets: a `ScrollView` holding a non-lazy `VStack`. Each catalog section has a `LazyVGrid(.adaptive)` per set. That `ScrollView` is not focusable, and `BackgroundSetsView` has no focus state.
- Cell heights vary within a row. `BackgroundImageCell` has a fixed 110 pt picture, then a name line, then a size line. After those come a uses line (`lineLimit(2)`, so one or two lines) and an optional shared-status line (shown only when `sharedStatus != nil`).

## Hypotheses (unverified, confirm before fixing)

1. **Focus moves the scroll position (My Images; most likely for that tab).** `click` sets `gridFocused = true` on a `.focusable()` `ScrollView`. When a scroll view gains focus, or focus is set again, SwiftUI on macOS may scroll to show the focus target. The focus target is the whole scroll view's content, so it may scroll to the content's top or origin. This would also explain why the jump happens on a plain selection and never on the arrow keys, if that turns out to be true. To check: comment out `gridFocused = true` in `click` and see whether the jump goes away. Also check whether the jump happens only on the first click (focus gained) or on every click.
2. **A `LazyVGrid` re-layout with rows of different heights.** Changing selection re-runs the parent `body`, and with it the whole `ForEach`. A lazy grid with unequal cell heights can re-estimate the rows it isn't showing and move the content offset. This affects both tabs (Background Sets also re-runs its `ScrollView` content when `selected` changes). To check: give every cell a fixed height and see whether the jump goes away.
3. **The first click also makes the window key.** If the window was not key, the click runs `windowDidBecomeKey`, which calls `model.refreshUses()`. That writes `uses` only when they differ, and starts a catalog check. A changed uses line (one line to two) or a catalog merge would change cell heights or Background Sets content at the moment of the click. To check: see whether the jump happens only when the click activates the window.
4. **The `GeometryReader` wrapper.** `grid(columns:)` is built inside the `GeometryReader` closure. If the column count, or the identity of the `ScrollView` under the reader, changes on a re-render, the `ScrollView` is rebuilt and its offset is reset. Not expected on a plain selection, but rule it out.

## Notes

- `docs/swiftui-observation-rules.md` is binding here. The fix changes focus and selection flow, and code that writes `@State` and `@FocusState` from view events. Selection writes must stay event-origin writes. Don't move a write into a `Task` to dodge an update-time write, and don't add `makeFirstResponder` from a SwiftUI callback.
- `docs/terminal-pane-requirements.md` does not apply. This window hosts no Pane.
- Keep the arrow-key and Delete behavior the `.onKeyPress` handlers give, and keep the grid focusing on open and on the switch back to My Images. Those came from earlier work on this view (the comment on `.focusable()` records that a zero-size focus holder never took focus).
- Existing UI coverage: `BattyUITests/BackgroundImagesWindowTests.swift` and `BattyUITests/BackgroundSetsTests.swift`. A UI test for this bug would scroll, click a cell, and assert that a visible cell's frame did not move.
