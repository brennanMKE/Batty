## Description

User report, verbatim: "When I select an image in the Background Images view it jumps. Fix that. There's no reason for it to jump."

Clicking an image to select it should only move the highlight outline. Instead the view jumps. Selection is a highlight only in the manage window: nothing in it should change the scroll position or the layout. User-reported against the 1.4.0 release candidate.

The report doesn't say which tab (My Images or Background Sets) or how far the view jumps (back to the top, or to some other row). The plan phase should reproduce both tabs and record which one jumps. The code paths differ (see Context), so the fix may differ too.

## Steps to reproduce

1. Open File → Background Images… (also in Settings and the Command Palette).
2. On My Images, have enough images that the grid scrolls. Scroll part way down.
3. Click an image that is not already highlighted.
4. Repeat on the Background Sets tab.

## Expected behavior

The clicked cell gets the accent outline. The scroll position and every cell's position stay where they were.

## Actual behavior

The view jumps when the image is selected.

## Hypotheses (unverified, confirm before fixing)

1. **Focus moves the scroll position (My Images; most likely for that tab).** `click` sets `gridFocused = true` on a `.focusable()` `ScrollView`. When a scroll view gains focus, or focus is set again, SwiftUI on macOS may scroll to show the focus target. The focus target is the whole scroll view's content, so it may scroll to the content's top or origin. This would also explain why the jump happens on a plain selection and never on the arrow keys, if that turns out to be true. To check: comment out `gridFocused = true` in `click` and see whether the jump goes away. Also check whether the jump happens only on the first click (focus gained) or on every click.
2. **A `LazyVGrid` re-layout with rows of different heights.** Changing selection re-runs the parent `body`, and with it the whole `ForEach`. A lazy grid with unequal cell heights can re-estimate the rows it isn't showing and move the content offset. This affects both tabs (Background Sets also re-runs its `ScrollView` content when `selected` changes). To check: give every cell a fixed height and see whether the jump goes away.
3. **The first click also makes the window key.** If the window was not key, the click runs `windowDidBecomeKey`, which calls `model.refreshUses()`. That writes `uses` only when they differ, and starts a catalog check. A changed uses line (one line to two) or a catalog merge would change cell heights or Background Sets content at the moment of the click. To check: see whether the jump happens only when the click activates the window.
4. **The `GeometryReader` wrapper.** `grid(columns:)` is built inside the `GeometryReader` closure. If the column count, or the identity of the `ScrollView` under the reader, changes on a re-render, the `ScrollView` is rebuilt and its offset is reset. Not expected on a plain selection, but rule it out.

### Cause: narrowed, not yet confirmed

Every state write the view makes on a click leaves the scroll position and cell frames alone when it is made programmatically. So the jump needs the real mouse event. The one thing a real click does that these writes don't is the click-to-focus interaction of the `.focusable()` modifier that sits directly on the scrolling `ScrollView` (`grid(columns:)`). That is hypothesis 1, but through the click itself rather than through the `gridFocused` write. On top of it, `click(_:)` re-asserts `gridFocused = true` on every click. That write is redundant: the grid is focused on open (`defaultFocus` and `onAppear`), when entries first appear, and on the switch back to My Images, and nothing else in the My Images tab takes click focus. So My Images has two focus writers for one fact, which the binding rules forbid ("one authority per fact"), and the jump comes from their interaction with a real click.

Hypothesis 3 (the click makes the window key, so `refreshUses()` changes a uses line) can only explain a jump on the click that activates the window. The step 1 tests click while the window is already key, so they tell the two apart.

Background Sets has no focusable view and no focus state. Its click makes one `@State` write, which the experiment shows doesn't move anything. If it jumps too, the shared cause is the real click inside the `ScrollView`, and the decision table below covers that case.

## Plan (round 3)

Planned and worked 2026-11-13 after the user reported that Beta 6975f1ba "still jumps sometimes". Every earlier reproduction clicked while the window was already key. Lead: the click that selects often also makes the window key, and `windowDidBecomeKey` runs `model.refreshUses()` and `hosted.windowBecameKey()`, which may check the catalog and rewrite `hosted.catalogs`. `BackgroundSetsView.body` read `hosted.catalogs` whole, so every grid above the viewport was re-evaluated.

### Findings from reading the code

- Every model write is already guarded: `refreshUses` (`if found != uses`), `update(_:_:)` (`if list != catalogs`), `reconcileAvailability`, `setFetch`, `insertAvailable`. There are no in-place or equal writes when nothing changed.
- A due check still makes three real changes to `catalogs` (`isChecking` on, `lastChecked` from `loadChecks`, `isChecking` off), even when the server answers 304. Each one invalidated `BackgroundSetsView.body`: `sections` was built from `catalogs`, and `controls` (read in the same `body`) read `isCheckingAny`. A check is due on any key event at least 5 minutes after the last one, so it runs exactly when the user comes back to the window.
- The parent also read per-cell state: `selected == key` for every cell, and `hosted.fetches[key]` in each cell's `.accessibilityActions`. `uses` came down from `BackgroundImagesView.body`. My Images had the same pattern: `selectedDigest`, `model.uses[...]` and `sharedStatus` were read in the grid's `ForEach`.

### Step 1: reproduce (no production change except a UI-test seam)

- `UITestDriver.backgroundCatalogCheckInterval` / `BATTY_UI_TEST_BACKGROUND_CATALOG_CHECK_INTERVAL`: seconds between checks, honored only with the fixture folder. It feeds a new `HostedBackgroundsDependencies.checkInterval` (default `refreshInterval`). With `0`, every key event makes a check due.

### Step 2: fix (structural)

- `HostedBackgroundsModel.contents: [HostedCatalogContent]` (url, catalog, problem) is written through `setCatalogs` only when it changes. A check that finds the same catalog leaves it untouched. `BackgroundCatalogFilter.sections` and `BackgroundSetsView.body` read it instead of `catalogs`.
- `BackgroundSetsControls` is its own view and is the only reader of `isCheckingAny`.
- `GridSelection<ID>` (`@Observable`, `select` writes only on change) holds the highlight in both tabs. Only the cells read `selection.id` in their `body`, plus My Images' new `RemoveSelectionButton`. Clicks, arrow keys and `add` write it as event-origin writes.

- No Task hops, no scroll save or restore, no focus changes.

## Gotchas

**Diagnostics for the user's next jump.** The 1 pt shift is fixed, but it isn't the several-row jump the user sees. `BackgroundImagesScrollMonitor` (owned by the window controller while the window is open) watches every `NSClipView` bounds change in the Background Images window. When the origin moves by more than 4 pt and no live scroll or recent scroll-wheel event explains it, it logs a `.notice`. The entry has the old and new origin, the document height, the tab, the current event type, and the last 12 events from `BackgroundImagesDiagnostics`: window became key, selection change, catalog check, catalog contents write, uses refresh (changed or unchanged), download state, thumbnail load (runs coalesced with a count), and Refresh. The ring is plain storage, never observed, written only from the existing action and model paths. A window live resize is skipped.

After a jump, the user runs this on the MacBook:

```
log show --last 10m --predicate 'subsystem == "co.sstools.Batty.beta" AND category == "BackgroundImagesScrollMonitor"' --info
```

The monitor watches every clip view in its window, not one found once from the hosting view, because switching tabs replaces the scroll view. A programmatic or keyboard scroll (Page Down, arrow keys moving off-screen) is also logged; the current event type tells those apart.

**The user's large jump is not yet reproduced.** The VM showed only a 1 pt shift after a catalog check, and that shift is fixed. Whether the several-row jump the user sees has the same cause is unknown; the scroll monitor above exists to find out from the next occurrence on the user's Mac.

Review notes on the monitor: it observes `NSView.boundsDidChangeNotification` app-wide (object nil) while the window is open, filtered by window, which is cheap; the first bounds change of a new clip view only seeds its origin and is never logged; a non-live resize (zoom button) or a keyboard scroll is logged as unexpected and the current event type tells them apart. `BackgroundSetsScrollStabilityTests` settles layout with a fixed 20-turn main-queue pump (no wall-clock wait) and passes both before and after the fix, so it is not a regression guard; the regression guards are the three `accuracy: 0` UI tests.

### What a selection does (manage mode, the window from the File menu)

1. `.onTapGesture { click(image, key: key) }` (`BackgroundSetsView.swift:166`). `onPick` is nil in manage mode (`BackgroundImagesView.swift:72`, `pickHandler` returns nil for `.manage`), so `click` only does `if selected != key { selected = key }` (`BackgroundSetsView.swift:180-182`). No image is applied, no `hosted` or `model` write, no `refreshUses`, no focus write. `BackgroundSetsView` has no focus state and its `ScrollView` is not focusable.
2. `selected` is `@State` of `BackgroundSetsView` (`:15`) and is read in that view's `body`, inside the `ForEach` closure of every set's grid: `isHighlighted: selected == key` (`:163`). So the write invalidates the **whole** `BackgroundSetsView.body`: `sections` is recomputed (`:22`), and the single `ScrollView` → non-lazy `VStack` (`:27-28`) → `ForEach(sections)` → `ForEach(sets)` (`:97`) → one `LazyVGrid` per set (`:151-156`) all get new content. Every set's `LazyVGrid` is handed a fresh `ForEach`, including the three sets wholly above the viewport.
3. Identity is stable: `Section.id` is the catalog URL (`BackgroundCatalogFilter.swift:11`), `BackgroundSet.id` is its catalog position, `HostedBackgroundImage.id` is its full URL (`BackgroundCatalog.swift:6-24`). No `.id()` modifier. So no subtree is rebuilt and no `@State` is reset; the selection changes no structure. Only two cells' `isHighlighted` differ, and `.activeOutline` is an overlay (no size change).
4. The window is already key (opened from the File menu, then scrolled), so `windowDidBecomeKey` (`BackgroundImagesWindowController.swift:57-62`) does not run on the click. No `GeometryReader` or `onGeometryChange` in this tab; columns are `.adaptive` inside the grid.

So the only thing a click changes beyond the two outlines is a re-evaluation of every off-screen `LazyVGrid` above the viewport.

### What differs between the user and the VM

- **Thumbnails do not matter.** The shipped thumbnails are all 480 x 300 (checked: 32 of 32 in `website/backgrounds/*/*-thumb.png`), the size the fixture writes. And a cell's picture box is `Color.clear.aspectRatio(16/10, .fit)` with the picture in an `.overlay` (`BackgroundSetsView.swift:208-211`), so a thumbnail's size, or its loading late, never changes a cell's height.
- **The status line does.** A cell's height varies by one caption line: `status` (`:245-267`) shows "In use", "Available offline" or a red failure (`lineLimit(2)`) only when the image has been downloaded (`hosted.available`, filled by `reconcileAvailability` from `HostedImageStore.localPath`, `HostedBackgroundsModel.swift:490-498`) or failed; otherwise nothing. The VM fixture never downloads anything, so in the VM every cell in every set is the same height. A user of 1.4 who has used Background Sets has downloaded some images, so some rows above the viewport are a line taller than others (and than the visible Deep Space rows).
- Smaller differences: the user's real window size, and catalogs the user added (`hosted.catalogs.count > 1` adds a catalog heading, `:86-89`).

### Candidates, ranked

1. **Off-screen lazy grids re-estimate rows of unequal height (most likely).** A `LazyVGrid` does not build rows outside the visible region; it estimates their height. When its content is replaced (step 2 above), it re-estimates the rows it isn't showing. The first plan's host experiment saw exactly this: the document height drifted by up to 100 pt on any re-render of a lazy grid with unequal rows. At the bottom of Background Sets, every unbuilt row is **above** the viewport, in three wholly off-screen grids, so any re-estimate there changes the document height above the visible rows. The `NSScrollView` keeps its clip origin, so the visible content shifts by the difference: the reported jump, with Deep Space's heading coming down into view. With uniform rows (the VM) the estimate equals the measured height, which explains why the VM didn't reproduce it. This cannot be shown fully from source because the estimation is inside SwiftUI; the tests below confirm it.
2. **A catalog check or availability change re-renders the same body.** `hosted.catalogs` (read in `body`, `:22`, `:86`) is rewritten when a check starts or ends (`isChecking`), and `available` when downloads are reconciled. Either re-evaluates the same grids with the same effect as candidate 1. On the user's steps this happens on open (`windowBecameKey`, `browseAppeared`), not on the click, unless a check is still running when the user clicks (network latency the VM fixture doesn't have). Same mechanism, different writer.
3. **The click activates the window.** Ruled out for the reported steps (the window is key), kept only as a row in the decision table.

### Step 2: the selection stops re-rendering the grids (`BackgroundSetsView.swift`)

The selection is a fact about two cells, so only those two cells may depend on it.

- Add `@Observable final class GridSelection<ID: Hashable> { private(set) var id: ID?; func select(_ id: ID?) { if self.id != id { self.id = id } } }` in its own file in `BattyKit/Sources/BattyKit/Views/` (no observed state beyond `id`).
- `BackgroundSetsView` holds `@State private var selection = GridSelection<HostedImageKey>()` instead of `selected`, and `body` never reads `selection.id`. `HostedBackgroundCell` takes `selection: GridSelection<HostedImageKey>` instead of `isHighlighted` and computes `selection.id == key` in its own `body` for `.activeOutline`. A click then invalidates only the cell losing and the cell gaining the outline. `BackgroundSetsView.body`, the `ForEach`es and the `LazyVGrid`s are not re-evaluated, so no off-screen row is re-estimated.
- `click` writes `selection.select(key)` / `selection.select(next)`: event-origin, as now, keeping the "only on change" guard inside `select`. Pick mode keeps the `pickOrCancel` logic unchanged.
- Apply the same holder to My Images (`BackgroundImagesView.swift:25`, `:157`): `selectedDigest` is read in the grid's `ForEach` for `isHighlighted`, so a click there re-evaluates its `LazyVGrid` the same way, and its cells also vary in height (uses line of one or two lines, optional shared line). `selectedEntry`, `move`, `add`, `requestRemovalOfSelection` and the Remove button's `.disabled` read or write the holder; the Remove button reading `selection.id` re-renders only `bottomBar`'s subtree if it is factored into its own small view taking the holder, so do that. Leave `gridFocused` writes as they are (not implicated).
- No `Task` hop, no `ScrollViewReader`, `scrollTo`, `scrollPosition` or offset save/restore, no `makeFirstResponder`.

### Step 3: only if the Refresh test fails

Separate the catalog check's progress from the catalogs the grids read: `controls` reads `hosted.isCheckingAny` (fine, it's outside the scroll view), but `isChecking` lives inside `HostedCatalogState`, so a check rewrites `catalogs` and re-renders every grid. Move the in-flight flag out of `HostedCatalogState` into its own observed property on `HostedBackgroundsModel` (for example `checking: Set<URL>`), read by `controls` and by the catalog progress row only, so `catalogs` changes only when a catalog's content or problem changes. Keep `update(_:_:)`'s compare-before-write. This is a model change with its own unit tests (`HostedBackgroundsModelTests`: a check that returns the same catalog leaves `catalogs` untouched, by `withObservationTracking`).
