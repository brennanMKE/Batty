# 0395 — BattyKit unit tests lean on wall-clock deadlines and real sleeps, so a loaded machine fails reviews of branches that never touched the code under test

| | |
|---|---|
| **Status** | open |
| **Module** | Build / Pane |
| **Platform** | macOS |
| **First seen** | 2026-09-02 |

## Description

Two BattyKit suites have now produced intermittent failures while reviewing branches that do not touch the code they test: `ProcessStatusPaneContentTests` failed during the review of `issue/0380`, and `GitStatusPaneContentTests` failed 3 tests during the review of `issue/0383`. Both passed on immediate re-run; neither branch modifies the pane-content code under test. The shared mechanism is wall-clock timing — the suites poll toward fixed real-time deadlines and sleep for fixed real durations, so their pass/fail line is drawn by how loaded the machine happens to be, not by the diff under review.

The cost is not the re-run — it is attribution. `./build.sh unit` is this project's pre-commit gate and the reviewer's re-verification command; every future review that sees red in these suites must spend a round distinguishing "this branch broke something" from "the machine was busy," and that tax is paid on every branch, by every reviewer, indefinitely. Worse, it trains reviewers that red is usually noise — and a reviewer who has learned that red is usually noise is a reviewer who will eventually wave a real regression through. Two separate reviews in one session each had to run the suite multiple times and reason about attribution before they could trust their own verdict.

## The margin is already gone

Both suites poll with a file-local `waitUntil` whose default deadline is **15 seconds of wall clock per call**:

- `GitStatusPaneContentTests` — helper at `BattyKit/Tests/BattyKitTests/GitStatusPaneContentTests.swift:115` (`timeoutNanoseconds: 15_000_000_000`, 2 ms poll interval at `:120`), used at **15 call sites** (`:144` through `:387`). Measured wall-clock for this one suite: **0.16 s** run in isolation, **~8 s** inside a full `swift test`, and **20.9 s** under `./build.sh unit` (the xcodebuild harness). Under the harness that actually gates commits, the suite's *total* already exceeds its own per-wait deadline — it stays green only because the 15 s budget is per-wait rather than per-suite. That is one load spike of margin.
- `ProcessStatusPaneContentTests` — same shape (`waitUntil(timeout: .seconds(15))` at `BattyKit/Tests/BattyKitTests/ProcessStatusPaneContentTests.swift:24`, 50 ms poll at `:28`), plus a hard `Task.sleep(for: .seconds(1.5))` at `:107` and a CPU burn to a 1.2 s `Date()` deadline at `:248-250`. **21.9 s** in the same `./build.sh unit` run.

(The duration numbers are measurements from the review sessions above, on one machine — they are load-dependent by the nature of this issue, but the shape is what matters: isolation to full-suite-under-xcodebuild is a two-orders-of-magnitude spread, and the gap between suite duration and per-wait deadline has already closed.)

The files themselves already know. `ProcessStatusPaneContentTests.swift:17-23` justifies the generous budget: the suite "runs alongside ~1100 other tests, several of which spawn real subprocesses and block synchronously (`Process.waitUntilExit()`), which can starve the cooperative thread pool and delay a `Task`'s resumption well past its nominal `Task.sleep` duration." And `:240-246` records a prior in-file casualty: an inline CPU-burn loop made the *unrelated* `samplingStopsWhileSuspendedAndResumesWhenShown` "flake under `./build.sh unit`'s xcodebuild harness even though it had been stable for three consecutive full-suite `swift test` runs beforehand." The pattern has already bitten within its own file once; now it bites across branches.

## A mis-attribution worth correcting

During one of the review rounds the `GitStatusPaneContentTests` failures were initially blamed on `git` subprocess cost. That is wrong: `GitStatusPaneContentTests` spawns **no** subprocess at all — it uses `RecordingWatcher` (`GitStatusPaneContentTests.swift:25`) and `RecordingScanner` (`:63`) doubles throughout, exactly as its header comment (`:7-23`) says; the only `Process` mentions in the file are comments naming the production conformers. The suite that spawns real `git` is `ProcessGitStatusScannerTests` (fixture helper `runGit` at `BattyKit/Tests/BattyKitTests/ProcessGitStatusScannerTests.swift:23-32`), and the suite that calls `process.waitUntilExit()` on spawned children is `ProcessStatusPaneContentTests` (`:140`, `:330`, `:360`). The shared failure mechanism is the wall-clock polling deadline under load, not subprocess cost in the failing suite.

## Survey: wall-clock dependence across BattyKitTests

The problem is broader than the two suites that happened to flake, though it is concentrated in the pane-content suites landed by #0304 / #0305 / #0313. Full sweep of `BattyKit/Tests/BattyKitTests/` for `waitUntil`, `Task.sleep`, `waitUntilExit`, `RunLoop` spins, and `Date()` arithmetic:

**Polling toward a wall-clock deadline** (the flaking pattern):

- `GitStatusPaneContentTests.swift:115` — 15 s `waitUntil`, 15 call sites (`:144,:157,:178,:183,:191,:199,:214,:227,:254,:269,:316,:349,:367,:381,:387`).
- `ProcessStatusPaneContentTests.swift:24` — 15 s `waitUntil`, call sites at `:93` and `:115`.

**Fixed real sleeps as synchronization** (pass depends on async work finishing inside an arbitrary real duration):

- `LMStudioDashboardPaneContentTests.swift` — eleven fixed `Task.sleep` waits of 80–400 ms (`:64,:85,:103,:127,:151,:175,:245,:251,:290,:329,:332`).
- `LMStudioDashboardWiringTests.swift:184` — 200 ms sleep, after spawning two real `/bin/sh -c "sleep 60"` stream processes (`:170-181`).
- `CrossWindowBehaviorTests.swift:361,:380` — 200 ms sleeps to let a `DispatchQueue.main.async`-deferred terminate check run.
- `GitStatusPaneContentTests.swift:133,:170,:202,:242` (20 ms) and `:282` (150 ms) — short fixed sleeps between steps.

**Fixed real sleeps as negative assertions** ("nothing happened for N seconds") — the least compressible kind, since they pay their full duration on every green run and a too-short window silently weakens the assertion:

- `ProcessStatusPaneLifecycleWiringTests.swift:82` — `Task.sleep(for: .seconds(1.2))` to assert a hidden pane does *not* keep sampling.
- `ProcessStatusPaneContentTests.swift:107` — `Task.sleep(for: .seconds(1.5))` to assert no capture while hidden.

**Real subprocesses + `waitUntilExit()`** (deliberate real-kernel methodology per `ProcessStatusPaneContentTests.swift:7-13`; these are load *generators* for the polling suites as much as potential victims):

- `ProcessInspectorTests.swift:50,:126` — `/bin/sleep` children.
- `ProcessStatusPaneContentTests.swift:140,:330,:360` — `/bin/sleep` children.
- `ProcessGitStatusScannerTests.swift:31` — real `git` fixture commands.
- `FootprintMonitorIntegrationTests.swift:173` — `xcrun xcstringstool compile` per test via `compileCatalogBundle` (`:158-178`).
- `AtlasOwnershipExperimentTests.swift:58` — `vmmap` of the test process; plus a `RunLoop.main.run(until: Date().addingTimeInterval(0.3))` spin at `:100`.

**Not implicated** — `Date()` as plain data, fully deterministic: `ProcessCPUDeltaTrackerTests.swift:29,:47,:55,:64` (timestamps injected through the tracker's `at:` parameter; arithmetic is on the injected values), `BellNotificationSummaryTests.swift:332,:347`, `TabRuntimeBellTests.swift:73`, `PaneHideTests.swift:193`, `BellFeedStoreTests.swift:15`, `LMStudioDashboardPaneContentTests.swift:31,:186`. These need no change.

## Expected behavior

A red `./build.sh unit` on an issue branch means the branch broke something. A genuine hang or regression in the pane-content lifecycle fails fast and reproducibly; a loaded machine does not fail the suite at all. Reviewers stop having to run the suite twice to know what a failure means.

## Candidate directions (deliberately not decided here)

Like [#0332](0332.md), this issue asks for the property, not a specific mechanism — pick during implementation, with the trade-offs written down. Candidates, none mutually exclusive:

- **Virtualize time**: make the polling deadline (and the content types' own cadences) run against an injected clock or scheduler instead of `ContinuousClock.now` / real `Task.sleep`, so tests advance time deterministically. Strongest fix for the negative-assertion sleeps; largest change, since it needs seams in `ProcessStatusPaneContent` / `GitStatusPaneContent` rather than only in the tests.
- **Replace polling with a deterministic await** on the value the test actually cares about — a continuation or stream the content type completes when state changes, so the test suspends until the event rather than sampling wall clock. Removes the deadline concept entirely for positive assertions; does nothing for "nothing happened" assertions.
- **Shrink the per-wait budget** so a genuine hang fails in ~1 s instead of 15 s. Cheap, but only re-tunes the load-sensitivity trade-off rather than removing it — the 15 s budget exists precisely because smaller budgets flaked (`ProcessStatusPaneContentTests.swift:17-23`).
- **Serialize the timing-sensitive suites** (`.serialized`, or otherwise exclude them from concurrent execution) so subprocess-spawning neighbors cannot starve their tasks mid-wait. Directly attacks the documented starvation mechanism; lengthens total suite wall-clock.
- **Split slow / timing-sensitive tests into a separate target** that is not part of the routine `./build.sh unit` gate, keeping the pre-commit gate fast and deterministic. Trade-off: a target outside the gate must still be run *somewhere* on a defined cadence, or it rots — if this direction is chosen, the issue resolving it must pin where and when that target runs.
- **Restructure negative assertions to assert on cause, not absence of effect over real time** — e.g. assert the sampling task is cancelled / the timer is invalidated when hidden, rather than sleeping 1.2–1.5 s and asserting the snapshot did not move. Converts the two slowest waits in the suite into instant checks.

## Notes

- The reviewer workflow (`issues/Issues.md`, "Reviewer subagent") tells reviewers to re-run verification "if in doubt" — these suites currently *guarantee* doubt, which converts the instruction into a standing tax.
- `GitStatusPaneContentTests` is currently green under `./build.sh unit` only because its 15 s budget applies per `waitUntil` call; any change that made a single wait span most of the suite (e.g. a first-wait stall while xcodebuild warms up) crosses the line. Treat the 20.9 s suite / 15 s deadline ratio as the alarm, not the failure count so far.
- The `~1100 other tests` figure quoted above is from the source comment (`ProcessStatusPaneContentTests.swift:18`), not a fresh count.
- The per-suite duration measurements (0.16 s / ~8 s / 20.9 s / 21.9 s) and the specific failure counts (1 suite on `issue/0380`, 3 tests on `issue/0383`, both green on re-run) are observations from the review sessions that prompted this filing; they are not reproducible from source and will vary with machine and load. Everything cited with a `file:line` above was re-verified against the working tree at filing time.
