## Description

Two BattyKit suites have now produced intermittent failures while reviewing branches that do not touch the code they test: `ProcessStatusPaneContentTests` failed during the review of `issue/0380`, and `GitStatusPaneContentTests` failed 3 tests during the review of `issue/0383`. Both passed on immediate re-run; neither branch modifies the pane-content code under test. The shared mechanism is wall-clock timing — the suites poll toward fixed real-time deadlines and sleep for fixed real durations, so their pass/fail line is drawn by how loaded the machine happens to be, not by the diff under review.

The cost is not the re-run — it is attribution. `./build.sh unit` is this project's pre-commit gate and the reviewer's re-verification command; every future review that sees red in these suites must spend a round distinguishing "this branch broke something" from "the machine was busy," and that tax is paid on every branch, by every reviewer, indefinitely. Worse, it trains reviewers that red is usually noise — and a reviewer who has learned that red is usually noise is a reviewer who will eventually wave a real regression through. Two separate reviews in one session each had to run the suite multiple times and reason about attribution before they could trust their own verdict.

## The margin is already gone

Both suites poll with a file-local `waitUntil` whose default deadline is **15 seconds of wall clock per call**:

- `GitStatusPaneContentTests` — helper at `BattyKit/Tests/BattyKitTests/GitStatusPaneContentTests.swift:115` (`timeoutNanoseconds: 15_000_000_000`, 2 ms poll interval at `:120`), used at **15 call sites** (`:144` through `:387`). Measured wall-clock for this one suite: **0.16 s** run in isolation, **~8 s** inside a full `swift test`, and **20.9 s** under `./build.sh unit` (the xcodebuild harness). Under the harness that actually gates commits, the suite's *total* already exceeds its own per-wait deadline — it stays green only because the 15 s budget is per-wait rather than per-suite. That is one load spike of margin.
- `ProcessStatusPaneContentTests` — same shape (`waitUntil(timeout: .seconds(15))` at `BattyKit/Tests/BattyKitTests/ProcessStatusPaneContentTests.swift:24`, 50 ms poll at `:28`), plus a hard `Task.sleep(for: .seconds(1.5))` at `:107` and a CPU burn to a 1.2 s `Date()` deadline at `:248-250`. **21.9 s** in the same `./build.sh unit` run.

(The duration numbers are measurements from the review sessions above, on one machine — they are load-dependent by the nature of this issue, but the shape is what matters: isolation to full-suite-under-xcodebuild is a two-orders-of-magnitude spread, and the gap between suite duration and per-wait deadline has already closed.)

The files themselves already know. `ProcessStatusPaneContentTests.swift:17-23` justifies the generous budget: the suite "runs alongside ~1100 other tests, several of which spawn real subprocesses and block synchronously (`Process.waitUntilExit()`), which can starve the cooperative thread pool and delay a `Task`'s resumption well past its nominal `Task.sleep` duration." And `:240-246` records a prior in-file casualty: an inline CPU-burn loop made the *unrelated* `samplingStopsWhileSuspendedAndResumesWhenShown` "flake under `./build.sh unit`'s xcodebuild harness even though it had been stable for three consecutive full-suite `swift test` runs beforehand." The pattern has already bitten within its own file once; now it bites across branches.

## A mis-attribution worth correcting

During one of the review rounds the `GitStatusPaneContentTests` failures were initially blamed on `git` subprocess cost. That is wrong: `GitStatusPaneContentTests` spawns **no** subprocess at all — it uses `RecordingWatcher` (`GitStatusPaneContentTests.swift:25`) and `RecordingScanner` (`:63`) doubles throughout, exactly as its header comment (`:7-23`) says; the only `Process` mentions in the file are comments naming the production conformers. The suite that spawns real `git` is `ProcessGitStatusScannerTests` (fixture helper `runGit` at `BattyKit/Tests/BattyKitTests/ProcessGitStatusScannerTests.swift:23-32`), and the suite that calls `process.waitUntilExit()` on spawned children is `ProcessStatusPaneContentTests` (`:140`, `:330`, `:360`). The shared failure mechanism is the wall-clock polling deadline under load, not subprocess cost in the failing suite.

## Expected behavior

A red `./build.sh unit` on an issue branch means the branch broke something. A genuine hang or regression in the pane-content lifecycle fails fast and reproducibly; a loaded machine does not fail the suite at all. Reviewers stop having to run the suite twice to know what a failure means.

## Candidate directions (deliberately not decided here)

Like [#0332](0332.md), this issue asks for the property, not a specific mechanism — pick during implementation, with the trade-offs written down. Candidates, none mutually exclusive:

- **Virtualize time**: make the polling deadline (and the content types' own cadences) run against an injected clock or scheduler instead of `ContinuousClock.now` / real `Task.sleep`, so tests advance time deterministically. Strongest fix for the negative-assertion sleeps; largest change, since it needs seams in `ProcessStatusPaneContent` / `GitStatusPaneContent` rather than only in the tests.
- **Replace polling with a deterministic await** on the value the test actually cares about — a continuation or stream the content type completes when state changes, so the test suspends until the event rather than sampling wall clock. Removes the deadline concept entirely for positive assertions; does nothing for "nothing happened" assertions.
- **Shrink the per-wait budget** so a genuine hang fails in ~1 s instead of 15 s. Cheap, but only re-tunes the load-sensitivity trade-off rather than removing it — the 15 s budget exists precisely because smaller budgets flaked (`ProcessStatusPaneContentTests.swift:17-23`).
- **Serialize the timing-sensitive suites** (`.serialized`, or otherwise exclude them from concurrent execution) so subprocess-spawning neighbors cannot starve their tasks mid-wait. Directly attacks the documented starvation mechanism; lengthens total suite wall-clock.
- **Split slow / timing-sensitive tests into a separate target** that is not part of the routine `./build.sh unit` gate, keeping the pre-commit gate fast and deterministic. Trade-off: a target outside the gate must still be run *somewhere* on a defined cadence, or it rots — if this direction is chosen, the issue resolving it must pin where and when that target runs.
- **Restructure negative assertions to assert on cause, not absence of effect over real time** — e.g. assert the sampling task is cancelled / the timer is invalidated when hidden, rather than sleeping 1.2–1.5 s and asserting the snapshot did not move. Converts the two slowest waits in the suite into instant checks.

## Chosen direction

**This is a reduction in flakiness, not a resolution.** Round 1 of this fix reduced the failure rate under load substantially (verified again in round 2: 0 failures across 3 loaded runs at load average ~100-125 with the round-2 fixes, vs. baseline's 5-13 failures at comparable load — see the loaded-run table below; reproduced independently a third time in round 3's review) but round 1's review correctly demonstrated that `samplingStopsWhileSuspendedAndResumesWhenShown`'s positive `waitUntil` can still fail under sufficiently extreme MainActor starvation, at any cadence and any deadline this round tried (round 3, N4: this paragraph previously misattributed that finding to round 2's review). No fixed real-time deadline is provably sufficient against unbounded contention; this issue narrows how often that ceiling is hit, it does not remove the ceiling.

Implemented as a blend of **"replace polling with a deterministic await"**, a narrow seam-only slice of **"virtualize time"**, **"restructure negative assertions to assert on cause"** where that didn't lose coverage, and — added in round 2, based on direct measurement rather than the round-1 assumption that it wouldn't help — **"serialize the timing-sensitive suites."** Applied only to the two suites that actually flaked in review (`GitStatusPaneContentTests`, `ProcessStatusPaneContentTests`) and the one negative-assertion sleep the survey named in a third file (`ProcessStatusPaneLifecycleWiringTests.swift:82`).

- **`ProcessStatusPaneContent` gained an injectable `samplingInterval` (default `.seconds(1)`, matching production)** — the same pattern `GitStatusPaneContent.debounceNanoseconds` already used. `samplingStopsWhileSuspendedAndResumesWhenShown` and the wiring suite's `aHiddenProcessStatusPaneDoesNotKeepSampling` inject a 20ms cadence, cutting the *typical-case* real wait from ~2.5s/~1s to sub-100ms — round 2 pinned the production default itself with a dedicated instant test (`defaultSamplingIntervalMatchesProductionDesign`), since no other test exercises it any more.
- **`GitStatusPaneContent` gained a `handledScanResultCount` testability counter** (`@ObservationIgnored`), incremented before the generation/phase guard in `handleScanResult`. `hidingDuringAnInFlightScanDiscardsItsResult`'s 150ms fixed sleep became a poll on this counter — a real deterministic await on the actual completion event.
- **All three of the originally-deleted "nothing async happens" sleeps in `GitStatusPaneContentTests` are now restored** (`createdHiddenNeverAcquiresAWatcherOrScans`, `redundantShowDoesNotDoubleAcquireOrDoubleRefresh`, `setVisibleAfterTearDownIsRejectedAndDoesNothing` — round 3, B2). Round 1 deleted all three, and round 2 kept them deleted, on the strength of mutations (M1/M2/M3) that only exercised the *synchronous* form of each regression (`activate()` called directly); round 3's review supplied the *deferred* form (`Task { activate() }` from the same branch) and showed both prior rounds were blind to it (M1-async/M2-async/M3-async: green on rounds 1 and 2, red once the sleeps are restored). `redundantShowDoesNotDoubleAcquireOrDoubleRefresh` keeps its instant `isRefreshing` check for the synchronous case *and* the restored wait for the deferred case — neither alone was sufficient.
- **`hidingAnActivePaneStopsTheWatcherAndSuspendsToZeroPeriodicWork` keeps its restored sleep from round 2** (B1) — deleting it made the assertion `x == x`, unfalsifiable against the exact "periodic work survives suspend" regression this test exists to catch (M5 below). Falsifiability here is cadence-dependent (round 3, N3): a leaked poller firing slower than this wait's window would still escape, the same limit any fixed-window wait has.
- **The two negative-assertion sleeps named in the original survey were shrunk, not eliminated**: `samplingStopsWhileSuspendedAndResumesWhenShown`'s hidden-period wait (1.5s → 200ms) and the wiring suite's equivalent (1.2s → 200ms). Round 1 claimed this real wait was protecting against a dropped `.cancel()` call; round 2's mutation testing (M6 below) disproved that specifically — the periodic loop's own phase guard already masks that exact bug regardless of this wait or of `isSamplingTaskAlive`. What the wait actually catches (M7 below) is the more literal regression `docs/pane-view-lifecycle.md` §4 names: hiding not stopping periodic sampling *at all* (phase guard and cancellation both gone). The two tests that only checked the released-reference half of that claim (`hidingActuallyCancelsTheSamplingTaskNotJustTheObservablePhase`, `tearDownActuallyCancelsTheSamplingTask`) are renamed (round 3, N2 — `hidingReleasesTheSamplingTaskReferenceNotJustTheObservablePhase`, `tearDownReleasesTheSamplingTaskReference`) to stop claiming cancellation they don't verify.
- **Both suites are now marked `@Suite(.serialized)`** (round 2, B3) — round 1 rejected this on the theory that #0383's finding ("`.serialized` doesn't protect shared state across suites") ruled it out; that finding is real but answers a different question, confirmed on inspection (round 3): neither suite touches any `static`/`shared`/`UserDefaults`/`NotificationCenter` state, and both suites' test doubles are file-local, so #0383/#0397 genuinely don't apply here regardless. Measured directly: unserialized, both suites failed the majority of their timing-sensitive tests under ~30-process contention (13 failures / 18 issues in each of multiple runs, confirmed independently by both round 2 and round 3's review); serialized, 0 failures across at least 6 runs total (3 from this round, 3 from round 3's own ablation) at equal or higher load. **Cost, not fixed (round 3)**: `.serialized` adds ~1.7-2.0s (~12-14%) to the unloaded gate (13.9s → 15.4-15.9s per round 3's measurement), and both suites are now exactly `./build.sh unit`'s critical path — every future test added to either suite adds its full duration to the gate, not just to its own suite.
- **`waitUntil`'s poll interval was widened 2ms → 10ms** (round 2, N4). Both `waitUntil` implementations record a loud `Issue` on timeout (round 2, B2's follow-up) instead of silently returning, so a starved wait fails at the wait, not on a downstream expectation that misattributes it as a behavioral regression. **The 15s → 30s deadline widening from round 2 is reverted back to 15s** (round 3, N1): 30s was compensating for misattribution, which loud timeout reporting now fixes directly regardless of deadline size, and for starvation `.serialized` now measurably removes — with both of those addressed, a smaller ceiling costs nothing on a passing run and halves how long a genuine hang takes to report (225s worst case across this suite's 15 call sites, down from 450s).
- **`cpuPercentReflectsSubstantialRealCoreUsage` was rewritten**, not left as a fixed floor (round 2, B4): its old `cpuPercent > 10` assertion is a claim about how much of a *shared* core this process got, which a sufficiently loaded machine can legitimately drive below any fixed floor without the code under test being wrong (observed 9.55%/8.56% under contention in round 2's review, and 9.96% independently in round 3's). It now independently re-derives the expected percentage from the same raw kernel ticks and checks production's answer against *that*, within a 5x band. **Round 3, B1 found that re-derivation circular against one specific bug**: it uses the same `MachTimebase.nanosecondsPerTick` constant production does, so an error *in that constant* cancels out of the comparison — proven by forcing it to `1.0` (a real ~42x error on arm64, this issue's original defect relocated one level up), which left this rewritten test green while `main`'s original floor-based test (correctly) went red. Fixed with a genuinely non-circular pin: `ProcessInspectorTests.machTimebaseNanosecondsPerTickAgreesWithAnIndependentClock` brackets a real interval with both `mach_absolute_time()` and `ContinuousClock` — two independently-implemented clocks measuring the same wall-clock interval, sharing no computation with `nanosecondsPerTick`, and immune to CPU contention (both advance at a fixed hardware rate regardless of scheduling, unlike CPU-time ticks) — and asserts they agree within a 2x band. Confirmed red under the same `nanosecondsPerTick = 1.0` mutation.
- **Out of scope this round**: the fixed-sleep suites named in the wider survey (`LMStudioDashboardPaneContentTests`, `LMStudioDashboardWiringTests`, `CrossWindowBehaviorTests`) were not touched — they weren't implicated in either actual review-time flake, and converting them with the same mutation-tested rigor would have exceeded this round's scope. Recommend a follow-up issue if they start flaking in practice.

## Gotchas

- **The periodic loop's use of the injected `samplingInterval` is unpinned.**
  `defaultSamplingIntervalMatchesProductionDesign` pins the stored default only.
  With the seam un-wired, M7 goes green and both suites stay fully green — so
  the falsifiability of both shrunk 200 ms negative assertions rests on an
  unpinned seam. Not a live defect (M7 is red today, verified), and hardcoding
  over the seam is not a plausible accidental bug, but it is a coverage
  dependency this branch introduces, of the same shape as the circularity round
  3 closed. Closeable in ~6 lines: inject 20 ms, activate, wait 200 ms, expect
  `capturedAt` advanced.
- **M5's table row overstates its breadth.** It reads "poller gated on nothing",
  but a poller routed through the type's own `requestScan()` is green, since
  that method has its own phase guard. It is red only when the poller bypasses
  `requestScan`.
- **`ContinuousClock` and `mach_absolute_time()` agreed to 7 decimals**, implying
  a shared hardware counter. Independence from *Batty's constant* — the property
  the new test needs — holds regardless, but a machine suspend mid-bracket could
  diverge them. Negligible in practice.
- **`.serialized` costs ~12-14% of the gate** (13.9 s to 15.9 s unloaded), and
  both suites are now exactly the run's critical path — `ProcessStatusPaneContentTests`'s
  own duration equals the whole run. Every future test added to either suite adds
  its full duration to `./build.sh unit`.
- **Flakiness is reduced, not eliminated.** `samplingStopsWhileSuspendedAndResumesWhenShown`
  can still fail under sufficiently extreme MainActor starvation regardless of
  cadence or deadline.
