## Description

A user with a Project open wants to right-click its Session row in the Sidebar, choose **Edit Project…**, change the Project's background, opacity, color or symbol in the Project Editor, and see the open Session change when they save. Today the row's context menu has no way to reach the Project Editor, and saving in the editor changes only the stored Project. The one exception is the symbol, which already updates live. The user's request (2026-11-18): "When a project is opened allow the right-click to show a menu item to edit that project in the list of sessions in the left sidebar. It should allow for making changes like the background, opacity, color and icon which would then update the opened project."

### Current state (checked against `main`)

- **Sidebar row context menu.** `SessionRowMenu` (`BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift:515-583`) is attached to the whole row (`.contextMenu` at `:363`). Its items, in order: Rename, Reset Name | Set Color…, Reset Color (only when overridden) | Set Session Theme…, Clear Session Theme, Set Session Background…, Clear Session Background | Mute/Unmute Notifications, the Reminder items | for a Project-backed Session **Update "<Project>"…** and **Save as New Project…** (otherwise **Save as Project…**) | Close. The Project-backed case is detected through `SaveSessionAsProject.menuModel(store:session:)` (`Views/SaveSessionAsProject.swift:15-18`), which looks up `session.projectID` in the `ProjectStore`. There is no item that opens the Project Editor.
- **How a Project-backed Session shows in the Sidebar.** `SessionRuntime.projectID`, `projectSymbol` and `projectSymbolName` (`Runtime/SessionRuntime.swift:75-88`) are set when the Project opens, in `WindowRuntime.addProjectSession` (`Runtime/WindowRuntime.swift:355-375`). The row draws the Project's symbol tinted with the Session color instead of the solid circle (`SessionRowIconView`, `SessionSidebarView.swift`; `SessionRowIcon.systemName`).
- **Where the Project Editor opens today.** It is one app-wide window, `ProjectEditorWindowController.shared` (`Views/ProjectEditorWindowController.swift`, window title "Projects"). `show(store:selecting:newDraft:startNewProject:)` (`:122`) already selects a given Project by id. Callers: Projects → Projects… (`Commands/BattyCommands.swift:202`), File → New Project… (`:142`), File → New Session when it routes to New Project (`:163`), the Open Project picker's Edit Project / Cmd-E (`Views/SessionDetailView.swift:339`, via `ProjectPickerView.swift:349`), and Save as Project / Update Project (`Views/SaveSessionAsProject.swift:170`). An "Edit Project…" Sidebar item would be one more caller of `show(store:selecting: session.projectID)`.
- **The editor's fields that the request names.** In `Views/ProjectEditorView.swift`: the header fields (name, root, color, symbol through `ProjectSymbolPicker`) in `ProjectHeaderFields` (`:491`); the Theme row (`ProjectThemeRow`, `:389`, opens `ProjectThemeSheet`); the Background row (`ProjectBackgroundRow`, `:416`, opens `BackgroundOverrideSettingsView` with scope `.project`), which holds the image, fit, position, image opacity and terminal opacity (`TerminalBackgroundSettings`, `Settings/TerminalBackgroundSettings.swift:40-48`). Each Pane and each Tab card also has its own background row (`:955`, `:1099`).
- **What saving does to an open Session today.** On save, the editor calls `model.projectSaved`, which the controller wires to `AppStateStore.applyProjectSymbol(of:)` (`ProjectEditorWindowController.swift:90`). That method (`Runtime/AppStateStore.swift:1661-1668`) updates `projectSymbol` / `projectSymbolName` on every open Session with that `projectID`, and its doc comment says "Title and color stay as pinned at open." Nothing else is pushed: color, Theme, background and opacity, name, Layout and the Pane/Tab backgrounds take effect only on the next open. **Save & Open** doesn't help: it opens with `ProjectOpenMode.focusExistingOrOpen` (`ProjectEditorWindowController.swift:56-59`), which only selects the Session that is already open.
- **This is documented as intended today.** `Concepts.md`, Project → Storage: "The running Session is the one live state: changes in it reach the Project only through Update Project, and editing a Project in the Project Editor doesn't change a Session already open from it." This issue changes that rule for the fields below, so `Concepts.md` must change with it.
- **Color has two forms.** A Project stores a palette `color: SessionColor` and an optional `customColorHex` (`Model/Project.swift:469`, and `ProjectAppearance.resolve(color:customHex:)` at `:528`). A Session has only the palette index (`addProjectSession` passes `project.color.rawValue` to `setSessionColor`). `customColorHex` is not read anywhere under `Runtime/`, so a custom hex color never reaches a Session, at open or otherwise.
- **The runtime counterparts.** The Project's background becomes the Session's background override at open (`session.setBackgroundOverride(background)` in `addProjectSession`; `projectBackgroundImageProblem` covers an image that failed its check). The Project Theme becomes `session.themeOverride`. The color goes through `WindowRuntime.setSessionColor(id:to:)`. Sidebar row items already write each of these at runtime (Set Color…, Set Session Theme…, Set Session Background…).

## Expected behavior

1. A Project-backed Session's Sidebar row context menu has an **Edit Project…** item (U+2026 ellipsis), grouped with the Update / Save as New Project items. It appears only when `session.projectID` names a Project still in the `ProjectStore`. A Session whose Project was deleted, and a plain Session, don't show it.
2. Choosing it opens the existing Project Editor window with that Project selected (`ProjectEditorWindowController.shared.show(store:selecting:)`), brought forward like the other entry points. If the editor has unsaved changes to another Project, the editor's existing unsaved-changes prompt runs; nothing is lost silently.
3. Saving the Project updates every open Session backed by it, in every Window, live, for at least the fields the user named: **background** (image, fit, position), **opacity** (image and terminal opacity), **color**, and **symbol** (which already works). The Session's Sidebar row icon tint, its terminals' background and opacity, and its Session color change without reopening the Project.
4. Cancel, or closing the editor without saving, changes nothing in the open Session.

### Decisions for the plan phase

These aren't settled by the request. The plan should choose one for each and record why:

- **Runtime overrides.** If the user changed the Session's color, background or Theme from the Sidebar after opening, does a Project save overwrite them? A suggested rule: a save writes only the fields whose stored value changed in this save, so an untouched field leaves the runtime value alone.
- **Theme and name.** The request doesn't name them. Decide whether the Project Theme also applies live (it maps cleanly to `themeOverride`), and whether a renamed Project renames its open Session (the title is pinned at open and the user may have renamed the Session).
- **Custom hex color.** A Session can't show `customColorHex` today. Either apply the nearest palette color, or make it explicit (in the editor or the issue's Gotchas) that a custom color reaches the Session only once Sessions support it.
- **Pane and Tab backgrounds, Layout.** Probably out of scope: the Layout can't be re-applied to a live tree. Pane/Tab background edits map to slots that may no longer exist. Say so explicitly.

## Acceptance criteria

- [ ] The context menu of a Project-backed Session row shows **Edit Project…**. A plain Session's row doesn't, and neither does a row whose Project was deleted.
- [ ] **Edit Project…** opens the Project Editor with that Project selected. This works from any Window and with the editor already open on another Project, and it respects the unsaved-changes prompt.
- [ ] After a save, an open Session backed by the Project shows the new background, opacities, color and symbol without being reopened, in every Window that has one.
- [ ] Cancel leaves the open Session unchanged.
- [ ] The behavior chosen for runtime overrides, Theme, name and custom color is implemented and covered by unit tests (BattyKit, e.g. alongside `ProjectSymbolTests`, which already tests `applyProjectSymbol`).
- [ ] `Concepts.md` (Project → Storage, and the `applyProjectSymbol` doc comment) is updated to describe the new live-apply rule.
- [ ] A UI test covers right-click → Edit Project… → change color → Save → the row's icon tint changes. It is compiled with `./build.sh ui-typecheck` and run in the VM per the verification tiers. `BattyUITests/ProjectsEditorTests.swift` is the nearby suite.

### Premises checked

All premises in the Description hold, with three corrections:

- "Cancel" no longer exists (#0654). The no-change paths are **Revert** (`ProjectEditorViewModel.revert()`, writes nothing) and closing with **Discard Changes**. Neither calls `projectSaved`. An unchanged Save returns early in `save()` before `projectSaved` (`ProjectEditorViewModel.swift:942-945`), so it applies nothing either.
- `Project.color` is already the palette entry nearest `customColorHex` (`Project.init` runs `ProjectAppearance.resolve`, which calls `nearestPalette(toHex:)`). `addProjectSession` passes `project.color.rawValue`, so a custom hex already reaches an opened Session as its nearest palette color. It doesn't reach it as the exact hex.
- `show(store:selecting:)` on an open editor goes through `model.requestNavigation(.select(id))`. That call raises the Save / Discard / Cancel prompt when the draft is dirty and does nothing when the id is already selected. Requirement 2 needs no new code in the controller.

### Decisions

1. **Runtime overrides: a save applies only the fields it changed.** The store compares the stored Project before the save with the one after it. A field that the save left alone doesn't touch the open Session, so a color, Theme or background the user set from the Sidebar survives a save that only renamed the Project or changed its symbol. A field the save did change overwrites the Session's value, including a Sidebar override. The user just chose that value for this Project, and it is the value they see in the editor. The same rule covers every open Session of the Project, in every Window (two Sessions opened with `.openNew` both follow).
2. **Theme applies live.** It maps one-to-one to `session.themeOverride`, the editor shows it beside Background, and it is appearance just like color and background. When the Theme changed: set `session.themeOverride = saved.theme` (nil clears it, and the Session follows the global Theme), then re-theme that Session's terminals with `applyActiveSessionTheme(for:)`. Do this for every matching Session, selected or not, as `applyGlobalThemeForCurrentAppearance` does. An unselected Session's chrome follows from the observed `themeOverride`.
3. **The name applies live, under the same changed-fields rule.** When `name` changed: `session.title = saved.name` and `titleOverride = true`, the same writes `addProjectSession` makes. Write them directly rather than through `renameSession`, so `SessionNameCache` stays untouched, as at open. Otherwise the row would keep the old name beside an `Update "<new name>"…` item. A Session the user renamed in the Sidebar keeps its name until a save actually renames the Project.
4. **Custom hex color: apply the nearest palette color**, which is `saved.color`, the same value used at open. Color counts as changed when `color` or `customColorHex` differs. The Session's color goes through `WindowRuntime.setSessionColor(id:to:)`, which sets `colorOverride`, as at open. Exact-hex Session colors are out of scope (Sessions only hold a palette index). `## Gotchas` must say that a custom color shows on the open Session as its nearest palette color.
5. **Symbol** keeps today's behavior: always written (idempotent writes; no runtime override exists).
6. **Out of scope, applied at the next open only:** Layout, Pane sizes, hidden Panes, focus, per-Pane and per-Tab backgrounds, Tab directories and startup commands, `notificationsMuted`, `paneListExpanded` and root. The Layout can't be re-applied to a live tree. Pane and Tab slots may no longer line up with the Session. Mute is a per-Session toggle the request didn't name. `Concepts.md` says so.
7. **Only Project Editor saves apply live.** iCloud sync merges, the CLI, and Update Project through the editor are covered as follows. Update Project *is* an editor save, and its captured fields equal the Session's own values, so applying them changes nothing (setSessionColor, setBackgroundOverride and themeOverride are all idempotent for equal values). Sync merges and CLI edits keep today's behavior (next open).
8. **No feature flag.** The whole feature lands in this one issue.

## Root cause

The Sidebar's Project items (`SessionRowMenu`) offered Update and Save as New Project but nothing that opened the Project Editor, and the editor's save seam (`projectSaved`) passed only the saved Project to `AppStateStore.applyProjectSymbol(of:)`, which copied the symbol and nothing else onto open Sessions.

## Fix

- `ProjectEditorViewModel.projectSaved` now passes `(previous, saved)`; `save()` captures the stored Project before the upsert.
- `AppStateStore.applyProjectSave(previous:saved:)` (with an `isDark:` overload for tests) replaces `applyProjectSymbol`. For every Session of the Project in every Window it always writes the symbol, and only when the save changed that field: name (title + `titleOverride`), color (`setSessionColor`, nearest palette entry), background (via new private `seedProjectBackground`, same checks as `openProject`), Theme (`themeOverride` + `applyActiveSessionTheme(for:isDark:)`). Runs synchronously from the Save action (event origin), no Task hop.
- `SaveSessionAsProject.editProject(session:store:open:)` opens the editor on the backing Project; the Sidebar row shows "Edit Project…" (`menu.sidebar.editProject`) first among the Project items.
- Harness-only row value gains `, tint <SessionColor>` before `, icon …`; UI harness `rowTint` / `waitForRowTint`.
- Concepts.md (0.37) and docs/ui-features.md updated.

## Gotchas

- A custom (non-palette) Project color shows on the open Session as its nearest palette color; Sessions hold only a palette index.
- Deviation: `openProject` was left on its original background code (it passes the background into `addProjectSession` before the Session is appended); only the live apply uses `seedProjectBackground`. Routing open through the helper would set the background after `addProjectSession`, a behavior change the plan didn't intend. The two paths duplicate ~5 lines.
- `rowValueCarriesTheTintOnlyWhenIconsAreExposed` became `rowValueCarriesTheTintOnlyWhenGiven` (the `exposesRowIcon` env flag is a static let and can't be injected); it tests `rowAccessibilityValue` directly.
- The new UI test and `ProjectsSymbolTests` passed in a filtered VM run during review (run `20261118-151520-54087`). Visual live re-theme, background image and opacity on screen are the user's sign-off.
- When a Theme save clears the Project Theme and no global Theme is set, `applyActiveSessionTheme` finds no effective Theme and leaves the terminals on the old one (same as Clear Session Theme today).
- Update Project through the editor copies the Session's image into the Project folder, so its save re-applies the background with the adopted path: the same image, a new path on the Session's override.
