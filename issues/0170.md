## Description

Every UI test in the [[0158]]–[[0169]] series — and the pre-existing tests from [[0091]]–[[0095]] — calls `Thread.sleep(forTimeInterval:)` on the main thread. The test methods are `@MainActor`, so the sleep blocks the main runloop. XCUITest uses XPC to communicate with the target app and *requires the main runloop to be spinning* in the test process to dispatch responses; `Thread.sleep` starves it. The runtime warning fires:

> This method should not be called on the main thread as it may lead to UI unresponsiveness.

Beyond the warning, this is a correctness problem: every `XCUIElement.exists` / `.value` / query enumeration inside a `waitFor` poll loop has to wait for the runloop to unblock between sleeps, which makes assertions race-prone, intermittently slow, and occasionally just wrong (the predicate evaluates against stale element state). Tests like `testIntentSwapChangesTabBarOrder` (the trigger for this issue) appear to "not pass" partially because of this — though that test has a separate design problem too (see [[0172]] when filed).

Two patterns:

1. **Duplicated `waitFor` helpers (13 files).** Each test file privately defines the same 6-line helper:

   ```swift
   private func waitFor(_ predicate: @escaping () -> Bool, timeout: TimeInterval) -> Bool {
       let deadline = Date().addingTimeInterval(timeout)
       while Date() < deadline {
           if predicate() { return true }
           Thread.sleep(forTimeInterval: 0.1)
       }
       return predicate()
   }
   ```

   One fix should have been one helper; instead it's 13 copies of the same bug.

2. **Standalone "let it settle" pauses (in `WorkspacePersistenceTests`, `BellFeedTests`, `TerminalPersistenceTests`).** Flat delays — e.g. `Thread.sleep(forTimeInterval: 1.5)` — used as "wait long enough for the workspace save to flush" or "wait for the bell to propagate." Strictly worse than the polling version: they always pay the worst-case latency, have no early-success path, no timeout failure message, and contribute disproportionately to test suite runtime.

## Why this happens (best read)

The author needed a general "wait for arbitrary predicate" helper. `XCUIElement.waitForExistence(timeout:)` — which *is* used correctly elsewhere in the suite (17+ call sites) — only handles "this element exists"; it can't express `tabBars.count == 4` or `focusedIndex == 3`. So they wrote `waitFor`. The simplest implementation is a busy-loop with `Thread.sleep`, and that's what landed.

What's missing from the author's toolkit: `XCTNSPredicateExpectation`. It's been in XCTest since macOS 10.11 but it's less googleable than `XCTWaiter` and easy to miss. The combination is exactly the right tool — it evaluates the predicate at intervals *while spinning the runloop in between*, so XPC callbacks land and the predicate sees fresh element state.

## Why not `async`/`await` + `Task.sleep`?

`Task.sleep` is non-blocking — it suspends the task and yields the thread back to the runloop — so async tests with `try await Task.sleep` would technically eliminate the warning. But:

- Every XCUIElement method called between sleeps is still synchronous and runloop-driven. Async/await alone doesn't change which calls spin the runloop.
- XCTest's expectation system is what was built for "wait for predicate while letting the runloop run." `XCTNSPredicateExpectation` integrates with the test report (you get a useful timeout failure message naming the predicate), works in sync or async tests, and is the canonical idiom anyone maintaining the suite expects to see.
- An async refactor of every test method would be a much larger change for the same outcome.

`XCTWaiter` + `XCTNSPredicateExpectation` is the right tool. Async tests are fine, but the *wait mechanism* should be expectation-based regardless.

## Fix

### A. Centralize one corrected `waitFor` in `BattyUITestHarness`

```swift
extension BattyUITestHarness {
    @discardableResult
    nonisolated static func waitFor(
        _ predicate: @escaping () -> Bool,
        timeout: TimeInterval = 5,
        description: String = "predicate"
    ) -> Bool {
        let exp = XCTNSPredicateExpectation(
            predicate: NSPredicate(block: { _, _ in predicate() }),
            object: nil
        )
        exp.expectationDescription = description
        return XCTWaiter().wait(for: [exp], timeout: timeout) == .completed
    }
}
```

`XCTWaiter` spins the calling thread's runloop while waiting. From a `@MainActor` test method, that's the main runloop — exactly what XCUITest needs.

### B. Delete the 13 duplicate `waitFor` helpers

Each test file's private `waitFor` becomes a call to `BattyUITestHarness.waitFor(...)`. Call sites need no other change (signature is compatible).

### C. Fix the harness's own poll loops

`waitForDriverErrors` and `waitForFile` both use `Thread.sleep`. Rewrite each on top of the new `waitFor`:

```swift
static func waitForDriverErrors(timeout: TimeInterval = 3) -> String? {
    var found: String? = nil
    _ = waitFor({
        let fm = FileManager.default
        let tmp = NSTemporaryDirectory()
        if let entries = try? fm.contentsOfDirectory(atPath: tmp) {
            for entry in entries where entry.hasPrefix("batty-ui-test-driver-error-") {
                let path = (tmp as NSString).appendingPathComponent(entry)
                found = (try? String(contentsOfFile: path)) ?? "unknown driver error"
                return true
            }
        }
        return false
    }, timeout: timeout, description: "driver error sentinel")
    return found
}
```

### D. Address standalone settle-pauses (separate, smaller pass)

The flat `Thread.sleep(forTimeInterval: 1.5)` calls in `WorkspacePersistenceTests` and the 0.5s/1.0s in `BellFeedTests` / `TerminalPersistenceTests` need case-by-case attention:

- Replace with a predicate-based `waitFor` against an observable signal where one exists (e.g. workspace.json mtime change, a new bell-feed entry appearing).
- Keep as flat delays only where there is genuinely no observable signal — and in those cases, the delay is wrong on principle (slow test, no failure diagnostics) but is the lesser evil until the app exposes a signal.

This part can land in the same commit if straightforward, or be deferred to a follow-up issue if the audit reveals real complexity. Recommend doing it in the same pass — the audit is small.

## Root cause

13 test files each defined a private `waitFor(predicate, timeout)` helper that loop-polled with `Thread.sleep(forTimeInterval: 0.1)`. Test methods are `@MainActor`, so the sleep blocked the main runloop. XCUITest's XPC bridge needs the main runloop spinning to deliver responses from the app process; blocking it starved that delivery and triggered the "this method should not be called on the main thread" warning. Eight standalone `Thread.sleep` calls (in `WorkspacePersistenceTests`, `BellFeedTests`, `TerminalPersistenceTests`, `ModalConfirmationTests`) had the same problem and were worse on principle — flat delays with no early-success path.

## Fix

Centralized two helpers in `BattyUITestHarness`:

- `waitFor(_:timeout:description:)` polls a predicate every ~50ms via `RunLoop.current.run(until:)`. The runloop stays live for XPC delivery; predicate evaluation cadence matches the prior `Thread.sleep(0.1)` cadence.
- `pause(_:)` runs the runloop for a fixed duration using the same `RunLoop.run(until:)` primitive — replacement for the standalone settle-pauses.

Both exposed via an `extension XCTestCase` so the 100+ call sites in test methods are unchanged (`waitFor({ ... }, timeout: 5)` still works, just resolves to the central impl).

`XCTNSPredicateExpectation` + `XCTWaiter` was the first attempt — it eliminates the warning but its block-predicate path polls at ~1Hz with no public control, which is too slow for fine-grained state transitions (focus index, chip count). Documented in the file-scoped comment so future me doesn't try it again.

`BattyUITestHarness.waitForDriverErrors` and `waitForFile` were rewritten on top of the new `waitFor` so the harness itself doesn't contain any `Thread.sleep`.

## Gotchas

- **`XCTNSPredicateExpectation` polls at ~1Hz** — the natural-looking "XCTest way to wait for a predicate" is too slow for UI-state polling. Don't reach for it for this use case. `RunLoop.run(until:)` with a tight predicate loop is what you want.
- **`RunLoop.run(mode:before:)` vs `RunLoop.run(until:)`** — the first returns when an input source is processed *or* the date is reached, leading to tight CPU loops when events arrive faster than the poll cadence. The second runs the loop for the full duration regardless. Use `run(until:)` for poll-loop waits.
- **Pre-existing test failures are not fixed by this change.** `testCmdTCreatesNewTab`, `testCmdDFocusesNewPane`, `testIntentSwapChangesTabBarOrder`, and many others fail in the same way on the pre-change baseline (verified via `git stash`). Those failures are app-side or test-design bugs and will need separate investigation. The trigger test (`testIntentSwapChangesTabBarOrder`) in particular has a documented design flaw (two app launches in one method) that should be filed as its own issue.
- **The runtime warning is gone** — verified by absence of "main thread" warnings in the test output after the change.
- **The standalone settle-pauses are still flat delays.** `pause(1.5)` in `WorkspacePersistenceTests` still pays the full 1.5s. Replacing those with predicate-based waits (e.g. workspace.json mtime change) is a follow-up — out of scope here. Workspace persistence is being removed entirely in [[0172]], so those settle-pauses will likely disappear with the suite.
- **Build with `'Batty (Beta)'`, not `Batty`.** The CLAUDE.md scheme name is stale.
