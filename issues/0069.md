# 0069 — Bell notifications don't clear when the user navigates to the bell's pane

| | |
|---|---|
| **Status** | open |
| **Module** | BellFeed / Sidebar |
| **Platform** | macOS |
| **First seen** | 2026-05-11 |

## Description

When a bell rings in a non-focused pane/tab/session, Batty correctly increments `unseenBellCount` on the tab, pane, and session and posts a desktop notification. But when the user **navigates to that pane** (via sidebar click, `Cmd-Option-N`, `Cmd-Option-Arrow`, chip click, or terminal-body click), the unseen count and the badge stay. The user has to either click the matching entry in the Bell Feed popover or use "Mark All Bells Seen" from the menu to clear it.

Convention from every other notification-aware app: visiting the place the notification points to **is** the acknowledgement. macOS Mail clears the unread badge when you view the message; iMessage clears the unread count when the conversation opens; Slack clears the channel badge when you switch to it. Batty should do the same — focusing a tab clears its unseen bells, which decrements the pane and session counters.

## Steps to reproduce

1. Two sessions open. Session 1 selected. Session 2 has a tab that's about to ring a bell.
2. In Session 2's tab, run `printf '\\a'` (or any command that triggers a bell). Sidebar shows a badge on Session 2.
3. Click Session 2 in the sidebar. The pane's terminal becomes visible and first-responder.
4. **Observed:** the badge on Session 2 in the sidebar still shows the unseen count. The bell-feed entry for that ring still appears as unseen.
5. **Expected:** the unseen count on the active tab drops to 0, and the session/pane counts decrement accordingly. The bell-feed entry is marked seen.

Same with any focus-changing path:
- `Cmd-Option-2` to jump to Session 2 from a hotkey.
- Pane-focus via `Cmd-Option-Arrow` to a pane that had unseen bells.
- Click inside a non-focused pane's terminal body (`#0060`) where bells had rung.

## Expected behavior

When a `tab` becomes the "actively viewed" tab — defined as:

```
session.id == store.selectedSessionID
&& session.tree.focusedPaneID == pane.id
&& pane.activeTabID == tab.id
```

— any unseen bell-feed entries pointing at that tab are marked seen, and `tab.unseenBellCount` drops to 0 with the cascaded decrement on `pane.unseenBellCount` and `session.unseenBellCount`.

This should fire on every focus-changing path that lands on a previously-unseen tab:
- Sidebar selection change (`selectedSessionID`).
- Pane focus change (`tree.focusedPaneID`).
- Tab switch within a pane (`pane.activeTabID`).
- Bell-feed click (already works — `jumpToBellEntry` exists, but it specifically marks the single matched entry seen; we want the broader sweep).

## Implementation guidance

### Where to gate the sweep

Add a helper on `AppStateStore` that, given the "actively viewed" tab, walks `bellFeed.entries` and marks any matching `tabID` as seen. The decrement cascade through `markBellSeen(id:)` already exists (`decrementUnseen(for:)`).

```swift
public func markActiveTabSeen() {
    guard let session = selectedSession else { return }
    let pane = session.focusedPane
    let tabID = pane.activeTabID
    let entriesToClear = bellFeed.entries.filter { $0.tabID == tabID && !$0.seen }
    for entry in entriesToClear {
        markBellSeen(id: entry.id)
    }
}
```

Also explicitly zero `tab.unseenBellCount` to handle the case where bell-feed entries were pruned (the feed cap is finite) but the unseen count on the tab is still non-zero. That's a belt-and-suspenders write.

### When to call it

Three hooks:

1. **`selectedSessionID` change** — observe in `RootWindowView` / `SessionDetailView` via `.onChange(of:)` and call `store.markActiveTabSeen()`.
2. **`tree.focusedPaneID` change** — observe in `SessionDetailView` (it has `session.tree` in scope) and call `store.markActiveTabSeen()`.
3. **`pane.activeTabID` change** — observe in `PaneView` and call `store.markActiveTabSeen()`.

Each one is a small `.onChange` modifier. They overlap slightly (sidebar selection + pane focus often change together) but `markActiveTabSeen` is idempotent — running it twice on the same tab is a no-op after the first call.

### Initial state

On launch, the actively viewed tab is the default Session 1's first pane's first tab. With a fresh store, no bells have been recorded — so calling `markActiveTabSeen` from `.task` is a no-op. Safe.

### The `seen` flag and `unseenBellCount` are slightly redundant

`BellFeedEntry.seen: Bool` is the per-entry flag. `tab/pane/session.unseenBellCount: Int` is the aggregate. `markBellSeen(id:)` flips the entry's `seen` and decrements the aggregates. Both paths converge correctly via `decrementUnseen(for:)`.

A subtle case: the bell feed has a finite cap (drops oldest beyond N entries). If a bell rings, increments the unseen counts, then is dropped from the feed, the aggregates still hold the count. `markActiveTabSeen` only walks the current feed entries, so the aggregates wouldn't fully clear. Add the explicit `tab.unseenBellCount = 0` write after the loop to handle that.

## Acceptance criteria

- After a bell rings in a non-focused tab, switching to that tab (via sidebar click, hotkey, pane-arrow movement, or pane-body click) zeroes the tab's unseen bell count.
- The pane and session aggregates decrement accordingly.
- The sidebar's session badge disappears (or decrements when only one tab in a multi-tab session had bells).
- The bell-feed entries for that tab become `seen` (the popover stops highlighting them as unseen).
- Running multiple back-to-back focus changes (rapid `Cmd-Option-Arrow`) doesn't cause negative counts or duplicate-mark-seen issues.
- A unit test exercises the gate: record a bell tick on a non-active tab, switch active tab to it, assert `unseenBellCount == 0`.

## Out of scope

- A "Don't auto-clear on focus" preference. Add only if a user asks. Most users want this behavior on by default.
- Per-pane vs per-tab acknowledge semantics — v1 acknowledges everything for the actively viewed tab, not the whole pane or session.
- Bell-feed entry decay or auto-removal — separate concern.

## Notes

- `AppStateStore.jumpToBellEntry(_:)` already routes selection + focus + tab to a bell's location and marks the entry seen. Make sure the new helper doesn't double-clear when jumping from the bell feed.
- The unseen-bell dot on tab chips (`BattyTabChip.hasUnseen`) reads `tab.unseenBellCount > 0`. Once that drops to 0, the dot disappears. No view change needed.
- The bell flash overlay (`PaneView.triggerBellFlash`) is purely visual and unaffected by this fix.
