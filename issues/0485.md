## Description

In Batty Beta (Projects flag on), with Settings or Help as the key window, choosing a Project by name from **File ▸ Open Project** opens it, but in a window the user can't see. The submenu item is enabled, the click is accepted, and nothing visible happens. Behind Settings, the most recently key content window has gained a Project-backed Session, its startup commands may have been typed into shells the user isn't looking at, or (when the command set is new) the startup-command trust sheet is now pending on that hidden window and shows up the next time the user returns to it.

This is a mouse action, not a chord leak. The Open Project items have no key equivalents (`docs/ui-features.md:731`, and nothing in `BattyCommands.projectMenuItem` attaches a `.keyboardShortcut`), so #0480's "menu chords reach through Settings" fix does not cover it, and #0480 deliberately left the Projects open path alone (see "Relation to #0480" below). The user asked for a named Project in plain words; the question this issue decides is what the app should do with that request when no content window is in front.

**Mechanism (verified on `main` at `9981f902`).**

- The item is a `Toggle` whose `set` calls `ProjectOpenPresenter.open(id:mode: .focusExistingOrOpen, in: store)` (`BattyKit/Sources/BattyKit/Commands/BattyCommands.swift:121-124`). The submenu is enabled while `keyWindow != nil` (`:173`), and `keyWindow` is `store.keyWindowOrFirstRegistered()` (`:61`), which is `defaultTargetWindow()`, so it stays enabled with Settings key.
- `ProjectOpenPresenter.open` (`Views/ProjectOpenPresenter.swift:18-29`) calls `store.requestOpenProject(id:mode:completion:)` with no `fromCli`.
- `requestOpenProject` (`Runtime/AppStateStore+ProjectStartup.swift:43-93`) decides through `ProjectStartupTrust.decide`:
  - `.skip` / `.runWithoutPrompt` → `finishOpen` (`:137-163`) → `openProject` (`Runtime/AppStateStore.swift:1226-1265`). If the Project is already open in some window, that branch selects the Session **and calls `activateWindow(window)`** (`:1240-1248`), so the content window comes forward: this case is already visible. Otherwise the target is `defaultTargetWindow()` (`:1249`), the Session is added there (`:1258`), and the window is activated **only for the CLI** (`:1261`, `if fromCli { activateWindow(target) }`). With `.runWithoutPrompt`, `armStartupCommands` then types the commands into that hidden Session's shells.
  - `.prompt` → the trust request is appended to `defaultTargetWindow()`'s `pendingStartupTrusts` (`AppStateStore+ProjectStartup.swift:72-87`), and again the window is activated **only for the CLI** (`:88-90`). So from Settings, the sheet is queued on a window the user can't see.
- `defaultTargetWindow()` (`AppStateStore.swift:951-962`) returns the key content window if there is one, else the most recently key registered content window (#0439). With Settings or Help key, `keyWindowRuntime()` (`:885-888`) is nil, so step 2 picks the window behind Settings.
- `activateWindow` (`AppStateStore.swift:1710-1718`) deminiaturizes, `makeKeyAndOrderFront`, and `NSApp.activate`. Its doc comment already records that every caller is event-origin, which a menu action is.

**The other two submenu items are not the same bug.**

- **Choose Project…** calls `postToContentWindow(.battyToggleProjectPicker)` (`BattyCommands.swift:128-130`, `:660-663`). On `main` the only guard there is `projectEditorIsKey`, so the notification is posted, but every receiver requires its own window to be key (`Views/SessionDetailView.swift:56-59`, via `isKeyWindow` at `:299-301`), so with Settings key the item is enabled and does nothing. On branch `issue/0480`, `postToContentWindow` (`BattyCommands.swift:664-667` there) drops the post earlier, with the same visible result. This is the "enabled but inert" state described under Notes, not a hidden open.
- **New Project…** calls `ProjectEditorWindowController.shared.show(store:startNewProject: true)` (`BattyCommands.swift:131-134`), which opens the Project Editor window. That window becomes key and is visible, so the action itself is fine. What needs checking is the editor's **Save & Open** afterwards: `ProjectEditorViewModel.saveAndOpen` (`Model/ProjectEditorViewModel.swift:684-693`) closes the editor first, "so the trust sheet presents over a content window", and then calls the `openProject` closure, which is `ProjectOpenPresenter.open` (`Views/ProjectEditorWindowController.swift:61-64`). If the editor was opened from Settings, AppKit may hand key status back to Settings when the editor closes, and the open would then land in the hidden window the same way. **Reproduce this** (open Settings, File ▸ Open Project ▸ New Project…, fill in a Project, Save & Open) and record whether it does.

**Two paths already bring the window forward, and must keep working.** The CLI `batty project open` goes through `openProjectForXPC` (`Runtime/AppStateStore+ProjectXPC.swift:38-73`), which calls `requestOpenProject(fromCli: true)` and so activates the target in both the create and the trust-sheet case. The Project Editor's Save & Open goes through the closure above. Both resolve through `defaultTargetWindow()`, and that is intentional (`AppStateStore.swift:1002-1003` on `main`: "XPC and CLI paths keep using `defaultTargetWindow()`"; #0480's reference design says the same). `defaultTargetWindow()` itself must not change.

## Steps to reproduce

1. Launch Batty Beta with at least one Project in `projects.json` that is not open, and one content window with a Session.
2. Press ⌘, to open Settings. Click a non-text control such as the Appearance pane button, so no text field is first responder.
3. From the menu bar, choose File ▸ Open Project ▸ <that Project's name>.
4. Observe that nothing visible happens. Close Settings.
5. Repeat with Help (Help ▸ Batty Help) as the key window.
6. Repeat step 3 with a Project whose startup commands have not been approved (new or changed command set).

## Expected behavior

A decision, recorded in the resolution, between the two options below, applied the same way for Settings, Help, and any other auxiliary window (#0480's classifier: Project Editor, About, standalone `NSOpenPanel`s).

**Recommended: bring the target content window forward and open there.** Reasons:

1. The user named the Project with the mouse, from an enabled item. There is no accidental-chord risk, which was the whole case for blocking in #0480. Silently ignoring a deliberate, enabled menu choice is the worst of the three outcomes (do it visibly, do it hidden, do nothing), and the item cannot be disabled instead: menu enablement must not read the key-window state, because nothing observed changes when focus returns to a content window and the item could stay disabled (#0480 "Gate at action time only, never in menu enablement"; `BattyCommands.swift:63-70` on `main` records the same rule for `actionWindow`).
2. The code already does this in three places for the same reason: the focus-existing branch of `openProject` activates unconditionally (`AppStateStore.swift:1244`), and the CLI activates in both the create case (`:1261`) and the trust-sheet case (`AppStateStore+ProjectStartup.swift:88-90`), with the comment "the CLI caller is waiting on this sheet, which is invisible if Batty is behind another app or minimized". A GUI caller behind Settings is in the same position. Bringing the window forward makes the from-Settings case consistent with "check an already-open Project in this submenu", which today brings its window forward.
3. The trust sheet must be seen when it is asked. A sheet pending on a hidden window means the user clicked, saw nothing, and later finds a dialog asking to run commands they don't remember requesting.
4. #0480's own per-command guidance for "from anywhere" commands was: keep them, but bring the target window forward so the result is visible.

**The alternative: block.** Return early from the menu action while `auxiliaryWindowIsKey` (branch `issue/0480`), as the Session-changing chords now do. This is simpler and symmetric with #0480, but it leaves an enabled item that does nothing, for a request that was unambiguous. If this is chosen, say why the asymmetry with the CLI (which activates) is acceptable, and this issue then depends on #0480 landing first for the classifier.

Either way:

- The Project Editor's Save & Open and `batty project open` keep working exactly as now (same target resolution, same activation), and `defaultTargetWindow()` is unchanged. Only the GUI menu entry's behavior while an auxiliary window is key changes.
- The Command Palette's "Open Project: <name>" rows (`Views/CommandPaletteView.swift:160`) and the picker's choice (`SessionDetailView.swift:316-327`) only run with a content window key, since both are sheets on it, and need no change.
- Choose Project… and New Project… follow the same decision where it applies: if "bring forward" is chosen, Choose Project… should bring the target content window forward and present the picker on it, rather than stay inert; if "block" is chosen, it stays inert as on `issue/0480`. New Project… keeps opening the editor; the Save & Open follow-through is covered by the reproduction in the Description.

## Actual behavior

With Settings or Help key, File ▸ Open Project ▸ <name> adds the Session to the content window behind Settings and leaves Settings in front. With a new command set, the trust sheet is queued on that hidden window and appears when the user next makes it key. Choose Project… does nothing. Both traced by reading the code on `main`; **reproduce in the VM before changing anything**, including the Save & Open follow-through from New Project….

## Resolution notes

> 🟢 Resolved 2026-10-13. When Settings, Help or the Project Editor is the key window, these all now bring the target content window forward and act on it:
> - **File ▸ Open Project ▸ <name>:** opens the Project in the target window. If startup commands need approval, the trust sheet appears there.
> - **Choose Project…:** presents the picker on that window.
>
> The CLI and `defaultTargetWindow()` are unchanged.

Owed to the user, as manual checks in Batty Beta:
- From Settings and from Help, choose File ▸ Open Project ▸ <name>, both with and without an unapproved startup command.
- Open Settings, then File ▸ Open Project ▸ New Project…. Fill in a Project and choose Save & Open, then note where the Session lands.
- From Settings, choose Choose Project…. The picker should appear on the content window.

## Root cause

GUI opens resolved their target through `defaultTargetWindow()`. While an auxiliary window was key, that returned the most recently key content window. `openProject` and `requestOpenProject` activated that window only for CLI opens, so a GUI open from Settings or Help built the Session, or queued the trust sheet, in a window hidden behind it.

Choose Project… was enabled but did nothing from Settings. It posted through `postToContentWindow`, and its receiver is gated on `isKeyWindow`.

## Fix

Decision: bring the window forward rather than block. The click is deliberate, and #0480 forbids gating menu enablement on key-window state.

- **`openProject` and `requestOpenProject`.** The create path in `openProject` and the `.prompt` path in `requestOpenProject` now run `if fromCli || auxiliaryWindowIsKey { activateWindow(target) }`. Both run synchronously in the event-origin menu action. The CLI still activates exactly once. The already-open focus branch already activated, so it is unchanged.
- **Choose Project…** When an auxiliary window is key, it activates `defaultTargetWindow()`. It then posts `.battyToggleProjectPicker` with that window's `WindowID` in `userInfo`.
  - `ProjectPickerToggle.shouldHandle(userInfo:windowID:isKeyWindow:)` makes the named window handle the toggle whether or not it is key.
  - An unnamed toggle is handled by the key window only, as before.
  - This item has no key equivalent. The draft's `currentEvent` keyDown check was removed, because it guarded a chord that does not exist.
- **Save & Open from the editor** is covered by the same check, because the editor counts as an auxiliary window.
- **Flag off:** every new line sits after the existing `featureFlags.projects` guards. A row for it was added to the gate-site table in `docs/feature-flags.md`.

Opus reviewed this in two rounds.
- **Round 1 requested changes:**

- **Round 2 approved, pending the VM run.** Its doc nits were fixed in `0fb65f4e`.
