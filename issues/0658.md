## Description

Follow-up to #0648 (Server Pane), recorded there by the round-2 reviewer as non-blocking (`issues/0648.md`, Gotchas, "Shell re-lookup after the cached shell exits").

In start mode, `TerminalTabServerBackend` finds the Tab's shell once and caches it as `shellStamp` (pid plus start time). When the cached shell is no longer in the process table, it does not refuse. It clears the cache and runs the lookup again:

- `BattyKit/Sources/BattyKit/Runtime/ServerBackend.swift:160-168`, `shell(in:table:)`: if the cached stamp doesn't match a live record, `shellStamp = nil` (line 164), then `ServerJobResolver.locateTabShell(tabID:spawnedAfter:snapshot:table:)` is called again with the same `spawnBaseline` (line 165), and whatever it returns is cached (line 166).
- `BattyKit/Sources/BattyKit/Runtime/ServerJobOwnership.swift:159-182`, `locateTabShell`: for `/bin/zsh`, whose environment the kernel hides, the shell is "the only same-user shell whose Batty child started after `baseline`" (lines 179-181). The baseline is taken once, when the Server Pane's Tab was created, so any Batty Tab created later also passes `baseline.precedes`.
- `stopDecision` (`ServerBackend.swift:151-158`) is reached from `ServerPaneContent.performStop` (`ServerPaneContent.swift:453-455`) and from `refreshStopRefusal` on every tick (`ServerPaneContent.swift:289-291`).
- The guard against this is `backend.isAvailable` (`ServerBackend.swift:106`, `lookup(tabID) != nil`), checked only at the top of `performTick` (`ServerPaneContent.swift:242`). Between the shell exiting and the surface/Tab being removed (or between ticks), the Tab still counts as available.

### Scenario

1. `batty server start` creates Tab A for a Server Pane; baseline B is taken; zsh S1 is found and cached.
2. The user later opens Tab C anywhere in Batty (new Tab, split, Project open). Its zsh S2 starts after B. C runs its own server, a job group whose listener holds the Server Pane's port (for example, the user moved the dev server to C, or the Pane's server died and C's took the port).
3. S1 exits (user types `exit`, shell crashes). Tab A has not been removed yet, so `isAvailable` is still true.
4. Stop (button, `batty server stop|restart`, or a tick's `refreshStopRefusal`) calls `shell(in:)`. S1's stamp no longer matches, so the lookup runs again. With S1 gone, S2 is the only shell after B and is returned and cached as "this Tab's shell".
5. `planGroupStop` finds C's listener descending from S2 in its own group and plans the stop. Batty sends SIGINT/SIGTERM/SIGKILL to C's job.

The window is short (Ghostty closes the surface when its shell exits), but it is not zero, and the cache then holds the wrong shell for the rest of the Pane's life if Tab A survives.

## Why it matters

The rule #0648 was bounced and reworked over is that Stop must never signal a job Batty did not start for this Pane. Here Stop signals a job in another Tab that the Pane never started. It's the user's process, and it can hold unsaved state.

## Expected behaviour

Once a shell has been identified for a Pane, never identify another one.

- The first successful `locateTabShell` result is the Pane's shell for the life of that backend. Keep the stamp; never set it back to nil.
- If the cached shell (pid plus start time) is no longer live, or is a zombie, `stopDecision` returns `.refused` with a reason, for example "the shell of this Server Pane's terminal has exited". It does not call `locateTabShell` again.
- Restart refuses the same way, through the existing `stopRefusal` path: Stop and Restart are hidden and "Stop unavailable: <reason>" is shown. `batty server stop|restart` fail with `stop refused: <reason>`.
- Before any shell has been found, lookup behaves as today. A failed lookup (nil) may be retried on a later Stop or tick, because nothing has been cached yet.
- `server start` on that port again creates a new Tab, a new baseline and a new backend, so the user can recover. That path doesn't change.

## Acceptance criteria

- [ ] `TerminalTabServerBackend.shell(in:table:)` never re-runs `locateTabShell` after a shell has been cached; a missing or zombie cached shell yields `.refused(reason)`.
- [ ] New test `ServerPaneContentTests.stopRefusesAfterTheTabShellExitsEvenWhenANewerShellHoldsThePort`. Build `FakeProcessTable` so the Tab shell is found by start time, with the environment hidden and a `spawnBaseline` before it. Tick so the shell is cached. Then remove the shell, and add a newer same-user Batty `login` child and shell started after the baseline, with a job group whose listener the scanner reports on the port. Then: `performStop()` returns false, `stopRefusal` is non-nil, and `FakeProcessSignaller.sent` is empty.
- [ ] New test `ServerPaneContentTests.zombieTabShellRefusesStopWithoutRelookup`. Same setup, but the cached shell stays in the table as a zombie. Stop refuses and nothing is signalled.
- [ ] New test `ServerPaneContentTests.stopRetriesTheLookupWhileNoShellHasBeenFound`. While no shell has been found, a later tick that can find one caches it and Stop proceeds as before. This keeps the pre-cache path working.
- [ ] Existing `ServerJobOwnershipTests` and `ServerPaneContentTests` (including `stopRefusesWhenTheTabShellIsNotFound` and `pidReusedDuringEscalationIsNotSignalled`) still pass.
- [ ] `./build.sh` and `./build.sh unit` pass. No VM run (logic change only, covered by unit tests).
- [ ] Update `issues/0648.md` Gotchas cross-reference, if the reviewer's note is kept, to point at this issue, and update any Server Pane design doc that describes the re-lookup.
