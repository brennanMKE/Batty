## Description

[#0404](0404.md) shipped `.claude/skills/batty-cli/install.sh` and `BattyKit/Tests/BattyKitTests/AgentSkillInstallScriptTests.swift`, which pins the script's discipline by **grepping its text from Swift** — exact-line pins, position checks (`preClearIndex < guardIndex < backupMoveIndex < swapIndex`), and one negative pin. Rounds 3–5 of that issue's review established, empirically, that this approach has a ceiling: a text pin can see that a line is *present*, but not whether it is *reachable* or which *branch* it sits in. The reviewer's mutations G (reversed then/else so backup+swap run only when staging failed), H (early `return 0` at the top of `install_into`), and I (every global install block wrapped in `if false`) all survive every text pin with all pinned lines in page order.

Exactly one test executes the script: `partialDestinationFailureExitsNonZero` (`AgentSkillInstallScriptTests.swift:221`) runs `install.sh` as a subprocess against a scratch temp directory used as `$HOME`, and asserts four things — baseline exit 0, the Claude Code copy's `SKILL.md` exists after the baseline, the second (forced-failure) run exits non-zero, and its output contains `"destinations failed"`. Nothing else about what a run *leaves on disk* is ever asserted. Every other guarantee the installer earned across four review rounds is verified only as text, or was verified only by hand during review and would regress silently.

### The mutation record, re-verified at filing (2026-09-10, against `main` tip `8df8e8d`)

- **H and I are caught — but only as a side effect.** The behavioral test's baseline does an install and then reads `fakeHome/.claude/skills/batty-cli/SKILL.md`, so an installer that installs nothing fails at the `fileExists` pin (#0404 round-5 item 1 made that failure attributable). Nothing asserts *why* the file should be there; the catch is incidental to reading one file once.
- **G is also caught now — #0404's Gotchas entry saying it isn't is stale.** The Gotchas claim "the reversed-branch case is not [caught]"; that was reasoned from "text pins can't see branches" but, as far as the record shows, never re-run against the behavioral test that round 4 added afterward. Verified at filing: applying G (`elif true` swap, all pinned lines in page order — every text pin confirmed still green) makes a fresh install take the failure branch, so the baseline installs nothing and exits 1 ("4 of 4 destinations failed" on this machine). Both `#expect(baseline.status == 0)` and the `fileExists` pin go red. Any reading of "backup+swap run only when staging failed" makes a clean baseline install nothing, so the same incidental mechanism that catches H and I catches G.
- **The class is still open.** Constructed and verified at filing — call it mutation J: insert one line, `backup="$parent/batty-cli-stale.$$"`, immediately after the pinned assignment `backup="$backup_root/$(basename "$dest").$(date +%Y%m%d%H%M%S).$$"` (`install.sh:149`). Every text pin passes: the pinned `backup_root=` and `backup=` lines are untouched, the negative sibling pin (`backup="$dest.backup.`) doesn't match, both gated `mv` lines are intact, all position checks hold. The behavioral test passes exactly as written: baseline exits 0 and installs everything; the second run's backup `mv` fails inside the read-only skills directory, returns 1, prints the summary, exits 1. But the routine path the test never exercises — a *writable* stale refresh, which is precisely what `SKILL.md`'s own refresh snippet tells every installed agent to run — exits 0 and leaves **two** `SKILL.md` files under `.claude/skills/` (`batty-cli/` and `batty-cli-stale.<pid>/`): the #0404 round-3 B1 harm (a stale duplicate skill competing in the host's scan root, the [#0383](0383.md) skew self-inflicted), resurrected undetected.

The structural lesson: incidental catching is not coverage. G, H, and I all die because the baseline happens to read one file; J survives because nothing asserts the shape of the tree a run leaves behind. A cheap partial mitigation for the most realistic *text*-level hole already shipped — the negative pin `#expect(!script.contains("rm -rf \"$dest\"\n"))` (`AgentSkillInstallScriptTests.swift:96`) kills a gratuitous "clean the destination first" refactor, which was the plausible-refactor version of the historical #0403 round-1 defect (mutation F) — but the structural answer to the reachability class is behavioral coverage, and #0404's Gotchas explicitly owes it: "Extending that behavioural harness is owed as a follow-up."

## Expected behavior

This is an **extension of the harness `partialDestinationFailureExitsNonZero` already established**, not the introduction of one. That test set the shape: run `install.sh` via `Process` against a scratch temp directory as `$HOME`; clear `XDG_CONFIG_HOME` and `CODEX_HOME` from the child environment (without which a developer with `XDG_CONFIG_HOME` set would have the unit suite write into their real `~/.config/opencode/skills`); pre-create `fakeHome/.claude` so host detection never depends on `$PATH`; restore permissions and remove the temp tree via `defer` on every path; drain output through a `readabilityHandler` into the lock-protected buffer. `ProcessGitStatusScannerTests` is the in-repo precedent for real shell execution in unit tests. The properties owed, each currently verified only by hand across review rounds or pinned only as text:

1. **Assert the installed tree, not just an exit code.** After a clean run, every expected destination holds exactly one `SKILL.md`, and no `SKILL.md` exists anywhere under a `*/skills/` path in the scratch `$HOME` other than the destinations themselves. That is the actual invariant behind the backup-placement fix (`backup_root="$(dirname "$parent")/batty-cli-skill-backups"`, `install.sh:146`), currently pinned only as that string's text — this assertion is what kills mutation J, and it gives the G/H/I class an attributable failure instead of an incidental one.
2. **The non-destructive contract, behaviorally:** (a) a pre-existing install with distinct content survives a forced staging failure byte-intact — the current test *forces* that failure but never re-reads the stale copy afterward to confirm it survived; (b) a symlink destination is backed up *as a link* rather than dereferenced (`install.sh:143`'s `readlink` report and the backup `mv` are both text-pinned only); (c) the `diff -rq` no-op path (`install.sh:122`) writes nothing at all — mtime-stable, zero backups, zero staging.
3. **`--dry-run` writes nothing** (filesystem unchanged before/after — #0404's round-1 verification did this by hand with a `find | md5` comparison; nothing automated it), and **`--project DIR`** populates the three project-scoped paths. Both are pinned today only as `case`-arm text (`AgentSkillInstallScriptTests.swift:145-147`) and `try_install` call-site text (`:173-175`).
4. **Keep the reversed-branch class caught for a stated reason.** Whether via property 1's tree assertion or an explicit baseline assertion, the test file should be able to say which check owns mutations G/H/I — today the answer is "the baseline happens to read one file," which the next refactor of the test could remove without knowing what it was load-bearing for.

1. Copy `.claude/skills/batty-cli/` somewhere disposable; in its `install.sh`, add `backup="$parent/batty-cli-stale.$$"` on a new line directly after the existing `backup="$backup_root/..."` assignment.
2. Confirm every assertion in `AgentSkillInstallScriptTests` still holds against the mutated text, and that the `partialDestinationFailureExitsNonZero` procedure (baseline; append to the installed `SKILL.md`; `chmod 555` the skills dir; re-run) still yields exit 0 / file present / exit 1 / "destinations failed".
3. Restore the skills dir to `755`, run the installer once more (the routine stale refresh): exit 0, and `find "$FAKEHOME/.claude/skills" -name SKILL.md` prints two paths.

## Actual behavior

`./build.sh unit` is green under mutation J, and would stay green under any regression that misplaces backups, dereferences symlinks, rewrites byte-identical destinations, ignores `--dry-run`, or drops `--project`'s fan-out — so long as the baseline still installs the Claude Code copy and partial failures still exit non-zero.

## Candidate approaches (deliberately not decided here)

1. **Sibling `@Test` funcs sharing a factored harness.** Extract `runInstaller`/`LockedOutputBuffer`/scratch-HOME setup from `partialDestinationFailureExitsNonZero` into a shared helper, then add focused behavioral tests per property (tree shape, staging-failure survival, symlink backup, no-op stability, dry-run, `--project`). Most legible failure attribution; several subprocess spawns per run (the script is sub-second against a scratch HOME, and the unit suite's <30 s budget has room, but measure).
2. **One end-to-end scenario walk** — install → byte-identical re-run → stale refresh → symlink replace → dry-run → `--project`, asserting the full tree after each step. Fewest spawns; a failure early in the walk obscures everything after it.
3. **Assert the tree inside the existing test only** (add the exactly-one-`SKILL.md`-per-scan-root sweep to the baseline and post-failure states of `partialDestinationFailureExitsNonZero`). Cheapest; closes J and gives G/H/I an attributable owner; leaves symlink/no-op/dry-run/`--project` text-pinned — an explicit interim at best.

Whatever lands: the text pins stay — they are cheap, catch stale-text regressions the behavioral layer can't attribute, and the F negative pin has no behavioral equivalent that is any stronger. The behavioral layer is an addition, not a replacement. Tests must keep the established hygiene: never a real `$HOME`, permissions restored before `defer` removal, and the "N of M destinations failed" count asserted as the substring, not a hardcoded count (it varies with which host directories the machine detects).
