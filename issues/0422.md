# 0422 — Closing a Git Status pane can block the main actor for up to 0.3 s while `terminateAndWaitBriefly` polls with `Thread.sleep`

## Description

This is the Git Status version of #0354 (LM Studio dashboard). Verified on `main`:

- `GitStatusPaneContent` is main-actor, the package default (`BattyKit/Sources/BattyKit/Runtime/GitStatusPaneContent.swift:449`). Its `tearDown()` (`:538-543`) calls `suspend(waitForInFlightScan: true)`.
- `suspend` (`:559-575`) calls `scanner.terminateAndWaitBriefly()` synchronously when `waitForInFlightScan` is true.
- `ProcessGitStatusScanner` is `nonisolated` (`:180`). Its `terminateAndWaitBriefly()` (`:237-250`) runs on the caller's thread, which here is the main thread. It sends `SIGTERM` to every in-flight `git` subprocess, then polls:

  ```swift
  let deadline = Date().addingTimeInterval(0.3)
  while processes.contains(where: { $0.isRunning }), Date() < deadline {
      Thread.sleep(forTimeInterval: 0.01)
  }
  ```

  The wait is bounded at 0.3 s. That's one deadline shared by all processes, not one per process.

So closing a Git Status pane while a scan is in flight can stall the main actor for up to 0.3 s. A large repository is the likely case, since `git status --porcelain=v2` can take a while there. Typing, rendering and every other Pane in the window freeze for that time.

`tearDown()` isn't only reached from closing a pane. `WindowRuntime.tearDownNonTerminalContent(in:)` (`Runtime/WindowRuntime.swift:719-723`) calls it serially for each Pane. So does `tearDownAllPaneContent()` (`:736-740`), which runs on window close and on app quit. A window with several Git Status panes that are all scanning can therefore stack up to 0.3 s per pane.

The other two suspend paths don't wait, because they pass `waitForInFlightScan: false` and call `terminateIfRunning()`:

- visibility change (`setVisible` → `.suspended`, `:531`, which #0349 now also drives on Session deselection);
- `changeDirectory(to:)` ("Change Directory…" retargeting, `:726`).

Only teardown blocks.

As with #0354, the bounded synchronous wait was deliberate. The protocol doc comment (`:87-93`) cites `docs/pane-view-lifecycle.md` §5's "bounded, deliberately, not unbounded" reasoning for the synchronous-teardown obligation. The cost is visible jank on a user-initiated close.

## Expected behavior

Pane close, and window close, don't block the main actor waiting for `git` to exit. For example: terminate synchronously, then hand the "wait briefly, and escalate if it's still running" tail to a background task that owns the `Process` references. The lifecycle contract's guarantee that teardown verifiably reaps its subprocesses must not be weakened (#0303, `docs/pane-view-lifecycle.md` §5).

## Notes

- Solve this together with #0354. The two cases are the same shape: `LMStudioDashboardPaneContent.waitBounded(for:label:)` spins `Thread.sleep(forTimeInterval: 0.02)` at `LMStudioDashboardPaneContent.swift:678-681`. A shared "terminate, then reap off-main" helper would fix both, and any later subprocess-backed Pane kind.
- Unlike LM Studio's wait, this one doesn't escalate to `SIGKILL` after the deadline. It logs a warning and abandons the wait (`:247-249`), which can leave a `git` process running past teardown. Decide whether the off-main tail should add that escalation.
- Existing tests: `GitStatusPaneContentTests` uses a fake scanner that only counts `terminateAndWaitBriefly()` calls. `ProcessGitStatusScannerTests` exercises the real method (`terminateAndWaitBrieflyIsASafeNoOpWhenNothingHasEverRun`, `:290`; `terminateAndWaitBrieflyTerminatesEveryOverlappingTrackedProcess`, `:329`), but nothing asserts that teardown *doesn't block the caller*. A fix should add that assertion, using a slow in-flight process, and should still check that the process is reaped.
