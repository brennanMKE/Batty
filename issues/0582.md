## Description

When you click a Background Sets image in a **Choose…** sheet, its cell adds a row under the title with a small spinner and a **Cancel** button while the full-size image downloads. The user doesn't want that row. Show the spinner centered over the downloading thumbnail instead, and drop the Cancel button. Clicking that thumbnail again cancels the download. Clicking a different thumbnail cancels the one in flight and starts the new one. Follow-up to [#0576](0576.md).

User report (2026-11-11, verbatim):

> "When I select a background image it shows a busy indicator and cancel button. I don't like that. Just put the busy indicator over the center of the thumbnail. And clicking the thumbnail while it is loading can cancel it. And if the user taps a different background that also cancels it."

## Steps to reproduce

1. Open **Settings → Appearance → Background** and click **Choose…**. A Session's, Pane's or Project's **Choose…** works too.
2. Switch to **Background Sets**.
3. Click an image that isn't downloaded yet.

## Expected behavior

- No status row with a spinner and **Cancel** under the cell while it downloads.
- A spinner centered over the downloading thumbnail. The thumbnail stays visible under it, perhaps dimmed.
- Clicking the downloading thumbnail again cancels the download. The spinner goes, nothing is applied, and the sheet stays open with the current background unchanged.
- Clicking a different thumbnail while one downloads cancels that download and starts the new one. Only the new image is applied when it finishes. This already works today (see Notes); keep it.
- The other status lines stay as they are: "In use", "Available offline" and a failure's reason.

Its key matches `pendingPick`, so it joins the running fetch and doesn't cancel it (`select`, line 181, returns the running task). Today a second click does nothing you can see.

## Notes

**Premise check: downloads happen only in Choose… sheets.** The report says "select", and the Background Images window (**File → Background Images…**) also shows Background Sets. There, `onPick` is nil (`BackgroundSetsView.swift:12-13`, and `pickHandler` in `BackgroundImagesView.swift:199-200` returns nil outside `.pick` mode). A click only highlights the cell and fetches nothing. So the busy row appears only in a **Choose…** sheet (`TerminalBackgroundControls.swift:65-77` presents `BackgroundImagesView` in `.pick` mode). Clicking a thumbnail to cancel only matters there. In the window, a click goes on only selecting.

**Cancellation is already supported.**
- `HostedBackgroundsModel.cancelFetch(_:)` (lines 234-239) cancels the key's running `Task`. If the fetch is still queued for one of the two slots (`maxConcurrentFetches`, line 56), it also takes it out of `fetchWaiters`.
- The cancel reaches the network: `URLSessionBackgroundCatalogFetcher` wraps the data task in `withTaskCancellationHandler` (lines 61-69) and cancels it.
- `runSelect` (lines 218-231) treats `.fetch(.cancelled)` as a quiet cancel, clearing the cell's state with no failure message.
- `HostedImageStore.fetch` downloads into a per-fetch temporary folder that a `defer` removes (`HostedImageStore.swift:113-115`), so a cancelled download leaves no partial file.
- Unit tests cover all this: `cancelledSelectClearsTheStateAndKeepsNothing`, `cancellingAQueuedFetchLeavesTheQueueAndClearsItsCell` and `repickingAnImageRightAfterItsFetchWasCancelledFetchesItAgain` in `BattyKit/Tests/BattyKitTests/HostedBackgroundsModelTests.swift`.

**A pick that supersedes another is already handled.** Picking a different image calls `releasePendingPick()` (line 259). That cancels the earlier pick's fetch when the pick started it (`ownsFetch`), and bumps `pickGeneration`, so the earlier pick's `onPicked` never runs. If the pick joined a fetch something else started, that fetch keeps running, but its result still isn't applied. Tests: `aLaterHostedPickWinsOverAnEarlierOneThatFinishesAfterIt`, `aCachedHostedPickSupersedesAnEarlierDownload`, `aPickOfADifferentImageStillCancelsTheFetchItStarted` and `aPickJoiningAnotherFetchOfTheSameImageNeverCancelsIt`. A **My Images** pick, **Add from File…**, the sheet's **Cancel** and dismissing the sheet call `supersedePicks()` (`BackgroundImagesView.swift:87, 218, 291, 300`). So the third expected behavior needs no model change, only a check that it still holds.

**What's new is the same-image click.**
- Today a second `pick` of the downloading key joins the fetch. Now a click on a cell whose key is `.fetching` should cancel it: something like `cancelFetch(key)` plus `supersedePicks()`, so the pending pick never delivers. A click on a cell that isn't fetching picks as before.
- The view can tell from `hosted.fetches[key]`, which it already reads.
- Decide what happens to the `selected` highlight on a cancelling click.
- Keep the joined-fetch rule: cancelling a fetch this sheet didn't start, such as one in another open sheet, would stop it for both. `releasePendingPick`'s `ownsFetch` guard already encodes that. A click that cancels probably goes through a model method that respects it, not a raw `cancelFetch`.
- Make sure a third click (pick, cancel, pick) starts a fresh fetch. `select`'s cancelled-task path (lines 180-187) already waits for the cancelled task to unwind.

**View rules.** The new click path writes observed state (`fetches`) from a tap, an event origin, so it's routine under `docs/swiftui-observation-rules.md`. The spinner overlay must not take the cell's tap (`.onTapGesture`, `BackgroundSetsView.swift:110`). Give it `.allowsHitTesting(false)` or put it inside the same tappable shape.

**Accessibility identifiers.** No UI test uses `background-sets.cell.<stem>.progress` or `.cancel` (grepped `BattyUITests` and `BattyKit/Tests` on 2026-11-11). Keep `.progress` on the new overlay spinner so a test can find it, and drop `.cancel`. A UI test for click-to-cancel would need the fixture fetcher to hold a download.

## Review

Approved first pass (round 1, Opus). Checked against the plan and `docs/swiftui-observation-rules.md`:

- `pickOrCancel` decides in the model from `pendingPick` and `isFetching` (false once the task is cancelled), so a click during a cancelled fetch's unwind window starts a fresh pick, which `select` serialises behind the cancelled task. The joined-fetch rule holds: a pick that joined another fetch is only superseded.
- `pickCancelPickFetchesAFreshCopyAndAppliesIt` releasing the hold before the second request is correct, not a stall: the re-pick's task awaits the cancelled one, which in `FakeBackgroundCatalogFetcher` resumes only on release and then throws `.cancelled`; the fresh fetch then runs unheld. The test is deterministic and awaits every task (no waiting).
- View writes (`selected`, model state) come only from the tap or the accessibility action, an event origin; `body` only reads `fetches`. The overlay has `.allowsHitTesting(false)`, so the cell's `.onTapGesture` gets the second click.
- Accessibility: the overlay's `.accessibilityElement()` "Downloading" child inside the `.contain` cell, and the conditional "Cancel Download" action, are sound. The action also shows on a cell spinning for another sheet's fetch, where it would join rather than cancel; that's the rare two-sheet case, and the VoiceOver check stays with the user.
- Non-blocking nit: `testClickingADownloadingImageAgainCancelsIt` uses `Thread.sleep(forTimeInterval: 1)` where the harness's `pause(_:)` is the house helper (it keeps the runloop live; #0170 removed the `Thread.sleep` copies). The binding no-wait rule in `AGENTS.md` covers unit tests, and `docs/ui-testing-vm.md` accepts a fixed UI-test pause when there's no signal. The pause also checks little, because the cancelled fixture request has already thrown by the time the spinner goes. Swap it for `pause(1)` the next time this file is touched; it isn't worth its own issue.

## Root cause

Starting state (feature change, not a bug): `HostedBackgroundCell.status` rendered a `.fetching` row (small spinner plus a **Cancel** button calling `cancelFetch`) under the title, and the thumbnail showed a spinner only while the thumbnail itself loaded. A second click on the downloading cell called `pick` again, which joins the running fetch, so a click could never cancel.

## Fix

- `HostedBackgroundsModel.pickOrCancel(_:onPicked:)` (beside `pick`): if the sheet's `pendingPick` is this image and its fetch task is live (`isFetching`), call `supersedePicks()` and return nil; otherwise delegate to `pick`. `pick`/`select`/`cancelFetch`/`releasePendingPick` are unchanged. A pick that joined someone else's fetch is only dropped (the fetch keeps running), per the existing joined-fetch rule.
- `BackgroundSetsView.click`: in pick mode it calls `pickOrCancel`; a cancelling click clears the highlight (orchestrator-confirmed), otherwise highlights the key. Writes `selected` only on change. Manage mode is unchanged.
- `HostedBackgroundCell`: the `.fetching` status row is gone (`EmptyView`); a second overlay on the thumbnail dims it (`black 0.25`) and centers a `.regular` `ProgressView`, `.allowsHitTesting(false)`, labelled "Downloading", id `background-sets.cell.<stem>.progress`. The `.cancel` id is gone.
- VoiceOver: a "Cancel Download" accessibility action on the cell while it downloads in pick mode, routed through `click`.
- Fixture fetcher: waits while `<rest>.hold` exists (throws `.cancelled` if cancelled); UI fixture gets `hold`/`release`.
- Help: the Background Sets bullet says a second click stops the download and another click switches.

No deviation from the plan, except the unit test `pickCancelPickFetchesAFreshCopyAndAppliesIt` does not wait for the second request before releasing: the re-pick serialises behind the cancelled fetch, which in the unit fetcher only unwinds on release.

### Files and approach

1. **`BattyKit/Sources/BattyKit/Model/HostedBackgroundsModel.swift`** — add one method beside `pick`, and leave `pick`, `select`, `cancelFetch` and `releasePendingPick` as they are (the existing "same key joins" tests depend on `pick`'s behavior):

   ```swift
   /// A click on a cell in a Choose… sheet. A click on the image this sheet's
   /// pending pick is still downloading cancels that pick instead (a fetch it
   /// joined keeps running for whoever started it). Returns nil when it cancelled.
   @discardableResult
   func pickOrCancel(_ image: HostedBackgroundImage, onPicked: @escaping @MainActor (String) -> Void) -> Task<Void, Never>?
   ```

   Body: `let key = HostedImageKey(image)`; if `pendingPick?.key == key && isFetching(key)` → `supersedePicks()` and return nil; else `return pick(image, onPicked: onPicked)`. Notes:
   - The decision lives in the model, not the view, because only the model knows `pendingPick` and whether the task is already cancelled. The view must not decide from `fetches[key] == .fetching`: right after a cancel, `fetches[key]` stays `.fetching` until `runSelect` unwinds, and a click in that window must start a fresh pick (pick → cancel → pick), which `isFetching` (false for a cancelled task) gets right and `select`'s cancelled-task path already serialises.
   - `isFetching` is true while the fetch is still queued for a slot too (the task exists and isn't cancelled), and `cancelFetch` already removes the waiter, so a queued pick cancels the same way.
   - A pick that joined a fetch it didn't start (`ownsFetch == false`) is only superseded: its `onPicked` never runs, but the other fetch continues and the cell's spinner stays until that finishes. That is the existing joined-fetch rule; see Open questions.
   - A click on a cell that's spinning for a fetch this sheet's pending pick isn't on (started by another sheet, or by an earlier pick of another sheet) is an ordinary pick that joins it, as today.
   - Writes: `pickGeneration`, `pendingPick` (both `@ObservationIgnored`) and, via `cancelFetch`, the task cancel; `fetches` is written later by `runSelect` after an `await`. All originate from a tap — event-origin, routine under `docs/swiftui-observation-rules.md`. No `Task` hop is introduced.

2. **`BattyKit/Sources/BattyKit/Views/BackgroundSetsView.swift`**

In pick mode call `hosted.pickOrCancel(image) { onPick($0) }`; if it returns nil (cancelled) set `selected = nil`, else `selected = key`. Rationale: in a Choose… sheet the highlight shows what is being picked; after a cancel nothing is (see Open questions). Write only on change (`if selected != new { selected = new }`) per the doc's note that `@State`/`@Observable` notify on equal writes — cheap to honour.

### Open questions (none blocking)

- **Highlight after a cancelling click.** The plan clears `selected` (nothing is being picked). Alternative: keep the highlight. Default to clearing unless the user prefers otherwise.
- **Cancelling a pick that joined someone else's download** (two Choose… sheets open at once, which is rare) drops this sheet's pick but leaves the spinner until the other sheet's download finishes, by the existing joined-fetch rule.
