## Description

Nothing in Batty ever emits a `background-image` or `background-opacity` config key, so terminals are unconditionally opaque with no image behind them. The pinned libghostty supports both natively (see [#0372](0372.md) for the verified key table and the pin hashes) — this issue is the plumbing that makes them reachable, and nothing else.

**No UI.** This is deliberately the first child and deliberately headless: it is the only piece of the background feature with real risk, and it is the only piece that can be proven correct by unit test alone. [#0374](0374.md), [#0375](0375.md), and [#0376](0376.md) all sit on top of it and are pure UI once this lands.

### Measured: unreadable images (the "Also confirm" answers)

| File given to `background-image` | `ghostty_surface_new` |
|---|---|
| Valid PNG, valid JPEG | Surface created |
| PNG with no extension | Surface created |
| **Missing path** | Surface created, no image |
| GIF, BMP, TIFF, HEIC, random bytes | Surface created, no image |
| GIF renamed `.png` | Surface created, no image |
| **Corrupt PNG, corrupt JPEG, truncated PNG, 0-byte `.png`** | **`NULL`: no surface** |

- **Formats: PNG and JPEG only.** `Config.zig` says so at the pinned ref and `prepBackgroundImage` (`renderer/generic.zig:1935-2019`) decodes only those. GIF, BMP, WebP and others log a warning and show nothing. The type comes from the file's magic bytes, then the extension, so a picker's extension filter is not a guarantee. **No animation:** GIF is refused, and the loader decodes one image, so an APNG can show at most a still (APNG itself not tested).
- **A missing path is benign**, contrary to this issue's fear: no diagnostic, other overrides survive, no image.
- **The sharp failure is a different one: a file that claims to be PNG/JPEG but doesn't decode.** `try wuffs.png.decode` propagates out of the renderer's init (`generic.zig:800`), `ghostty_surface_new` returns `NULL`, and `TerminalSurfaceCoordinator.swift:200-203` only logs it to a debug log. The result is a Pane with no terminal and no shell, for **every new Tab** while the preference points at that file. On a live surface the same `try` fails inside `changeConfig` and is logged by the renderer thread; that path is source reading, not measured.
- **Oversized images are unverified.** `uploadBackgroundImage` is a `try` in `drawFrame` (`generic.zig:1738`), so an image over the Metal texture limit may fail every frame. Not measured; #0375 should test it.
- Upstream documents one image copy in VRAM **per terminal**, so memory scales with Tab count. Relevant to `FootprintMonitor` and to #0375's help text.

### Files and approach

**`BattyKit/Sources/BattyKit/Settings/TerminalBackgroundSettings.swift` (new).**

- `enum BackgroundImageFit: String, CaseIterable, Sendable` — `contain`, `cover`, `stretch`, `none`.
- `enum BackgroundImagePosition: String, CaseIterable, Sendable` — the nine documented values, with `center` as the middle (not `center-center`).
- `struct TerminalBackgroundSettings: Equatable, Sendable` with `imagePath: String?`, `fit`, `position`, `imageOpacity: Double`, `terminalOpacity: Double`, and a `static let off`. #0374 and #0376 reuse this value type for their overrides.
- Normalization lives in one `init`, because every invalid value below would otherwise fail the whole config or inject one:
  - `imagePath`: trim nothing; expand a leading `~` with `NSString.expandingTildeInPath`; then **`nil` unless it is absolute and contains no control characters**. A newline in a path would inject a config line, and a relative path resolves against the temp directory holding the generated config, so it is never what the user meant and can raise the `NotDir` diagnostic above.
  - `terminalOpacity`: non-finite falls back to `1`; clamp to `0...1`.
  - `imageOpacity`: non-finite falls back to `1`; floor at `0`, **no upper clamp**, because upstream gives values over `1` a meaning when `background-opacity < 1` and that is #0375's call.
- No file I/O here. See "Open questions" for why the decode guard stays in #0375.

**`SettingsPreferences.swift`.**

- Keys `backgroundImagePathKey`, `backgroundImageFitKey`, `backgroundImagePositionKey`, `backgroundImageOpacityKey`, `backgroundOpacityKey`, using the existing `co.sstools.Batty.` prefix, plus defaults. Add them to `registerDefaults()`.
- `public static func resolvedBackground() -> TerminalBackgroundSettings` and `static func resolvedBackground(defaults: UserDefaults)`, matching the existing paired shape. One aggregate accessor rather than five, because every caller needs the set. An unknown stored fit or position falls back to the default rather than reaching libghostty.
- Add an internal `extension TerminalConfiguration.Builder` with `mutating func withSharedPreferences(fontSize:cursor:blink:background:)`. It emits **everything both builders must agree on**: font size, cursor style and blink, `shell-integration-features`, `env PATH=…`, the six `keybind` lines, then the background lines. Moving the existing #0392 and #0364 comments here keeps one copy of each.
- Background emission, inside that helper:
  - `imagePath != nil` → `background-image = "<path>"` **always quoted** (`LineIterator` trims unquoted whitespace, and quoting is harmless for every other path), then `background-image-fit`, `background-image-position`, `background-image-opacity`, all through `withCustom`.
  - `imagePath == nil` → none of those four, even if fit, position or opacity are stored.
  - `terminalOpacity < 1` → `withBackgroundOpacity`. `1` emits nothing.
  - `background-image-opacity` is formatted with `Double.description`, which is locale-independent. **Never `.formatted()` or a localized format**; the `0,35` row above is what that produces in a comma-decimal locale.
- `applyAppearanceToAllSurfaces` reads `resolvedBackground(defaults: preferences)` and calls the helper. Correct its comment, which currently names this issue as owning the omitted `copy-on-select`, `keybind = clear` and `cmd+c` lines; see open question 1.

**`Runtime/TabRuntime.swift`.**

- `applyShellAndAppearancePreferences` calls the helper **last**, after `keybind = clear` and `cmd+c=copy_to_clipboard`. `clear` must precede the six bindings, and this ordering is why the helper can't run first. Everything per-Tab stays here: `copy-on-select`, `command`, `wait-after-command`, `abnormal-command-exit-runtime`, `env BATTY_*`, `keybind = clear`, `cmd+c`.
- Add a stored `@ObservationIgnored private let preferences: UserDefaults` and an `init` parameter `preferences: UserDefaults = .standard`, used **only for the background read** at both call sites (`init` and `attachContext`). This is the test seam: tests may not write `.standard`, and `attachContext` re-renders, so a one-shot parameter would not cover it. Update the doc comment on `applyShellAndAppearancePreferences`, which explains why the other readers stay on `.standard`. `PaneRuntime`, `SessionRuntime` and `SplitTree` do not change; production keeps `.standard`.

**`issues/0375.md`, `issues/0372.md`.** Implementer adds one line to #0375 pointing at this issue's findings (its planned guard names the missing-file case, and the case that needs guarding is the undecodable file), and updates #0372's "unconfirmed" format caveat and pin citation.

## Root cause

Feature work. Neither config builder emitted a `background-image*` or `background-opacity` key, so terminals were always opaque with no image. The two builders also duplicated their shared lines by hand, which is the drift the replace hazard punishes, because `setTerminalConfiguration` replaces the whole override set.

## Fix

- Added `TerminalBackgroundSettings`, with `BackgroundImageFit` and `BackgroundImagePosition`. Its `init` does all normalization: a path must be absolute after tilde expansion and free of control characters, `terminalOpacity` is clamped to `0...1`, `imageOpacity` is floored at `0` with no upper clamp, and non-finite opacities become `1`.
- Added five `SettingsPreference` keys and `resolvedBackground()`, which produces the off state for absent keys, because `registerDefaults()` still has no caller. An unknown stored fit or position falls back to the default.
- Added `TerminalConfiguration.Builder.withSharedPreferences(fontSize:cursor:blink:background:)`, now the only source of the font, cursor, `shell-integration-features`, `env PATH`, six `keybind` and background lines. Both builders call it. `TabRuntime` calls it last so `keybind = clear` still precedes the six bindings.
- Added `TabRuntime.init(preferences:)`, used only for the background read, at both `init` and `attachContext`. `PaneRuntime`, `SessionRuntime` and `SplitTree` are unchanged, so production stays on `.standard`.
- Off emits nothing: no image lines without a path, and no `background-opacity` at `1`.

**Behavior for `copy-on-select` and keybinds is unchanged.** The appearance builder still drops `copy-on-select = false`, `keybind = clear` and `cmd+c`, as it did before. That is tracked by [#0538](0538.md). The comment there now states the gap and points to #0538 rather than attributing it to this issue. Within `TabRuntime`'s rendered config, the font and cursor lines now come after the per-Tab lines; no test or known key depends on that order.

**Deviations from the plan.** Test additions only, no code deviations: `opacitiesClampOnlyWhereLibghosttyRequiresIt` isn't in the plan's list, `pathWithSpacesIsEmittedQuoted` also covers a path containing `"` and `#`, which libghostty accepts, and the review added `perTabKeybindClearPrecedesEveryOtherKeybind`.

- A non-numeric stored opacity renders as `0`, because `defaults.double` returns `0.0` for a stored string or array. Today only a hand-run `defaults write` can do that, and `defaults delete` undoes it. #0375's UI must write real doubles, and a text field or import path would need to validate.

## What to build

**A new `SettingsPreference` key group** for background settings — image path, fit, position, image opacity, and terminal background opacity — registered in `SettingsPreference.registerDefaults()` (`BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift:203-214`) alongside the existing `fontSizeKey` / `cursorStyleKey` / `cursorBlinkKey` entries, with `resolved…()` accessors matching the shape of `resolvedFontSize()` (`:56`) and `resolvedCursorStyle()` (`:61`).

**Emission from both config builders**, sourced from that key group:

- `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:172-246` — the per-Tab builder, at Tab init.
- `BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift:170-198` — `applyAppearanceToAllSurfaces()`, app-wide on any appearance change.

**Both, not one.** `setTerminalConfiguration` replaces the entire override set rather than merging it, so a key emitted from only one builder is silently dropped the next time the other runs — the wholesale-replace hazard documented in [#0372](0372.md). Changing the font size in Settings must not wipe the background. Consider factoring the shared emission into one helper both call sites invoke, rather than duplicating the logic; the two builders already duplicate the `keybind` block, and that duplication is exactly how this class of bug gets in.

**Use the typed builder method where one exists:** `Builder.withBackgroundOpacity(Double)` (`TerminalConfiguration.swift:194` in the SPM checkout) for opacity. The `background-image*` keys have no typed method and go through `withCustom(key:value:)` (`:212`), the same escape hatch already used for `keybind`, `env`, `command`, and `wait-after-command`.

**Defaults must be off.** No image; `background-opacity` effectively `1`. A user who never opens any background UI must see zero change in rendering.

**Emit nothing at all when disabled** — do not emit `background-opacity = 1` as a no-op. This mirrors how `wait-after-command` is scoped in the existing code (`TabRuntime.swift:213`, emitted only for `-c` panes) and keeps the `renderedConfig` negative assertions below clean and meaningful.

## Verification

**Mandatory, and the reason this issue is separable from the UI.** Unit tests in `BattyKit/Tests/BattyKitTests/` asserting that `tab.terminal.renderedConfig`:

- **contains** the emitted lines when the preferences are configured, and
- **omits** them when they are not.

`renderedConfig` only reflects a config that libghostty's own diagnostics accepted — `prepareConfig` fails closed otherwise. So a green `contains("background-image = …")` assertion is genuine proof that the pinned binary accepted the key, not proof of string formatting.

Model the tests and their doc comments on the existing `wait-after-command` pair in `BattyKit/Tests/BattyKitTests/SplitTreeTargetedSplitTests.swift`: the doc comment at `:146-162` records the method and the control experiment, `commandOverridePaneWaitsAfterTheCommandExits` (`:163`) is the positive assertion, and `nilCommandPaneDoesNotWaitAfterItsShellExits` (`:175`) is the negative. `BattyContextInjectionTests.swift` uses the same `renderedConfig` technique for the `env` keys, including an idempotence check at `:60-62`.

**Add the negative control the existing doc comment describes**: confirm a deliberately misspelled key (e.g. `background-imag`) is rejected — `diagnostics=1 "unknown field"` — so the harness is proven capable of failing. Without it, a passing test proves nothing about acceptance.

**Also add a test for the replace hazard**: configure a background, then run `applyAppearanceToAllSurfaces()`, and assert the background lines are still in `renderedConfig`. That is the regression this issue is most likely to ship.

Gate: `scripts/build.sh unit`.

## Also confirm and record

**Which image formats actually load** under the pinned ref, and whether animated formats are supported at all. [#0374](0374.md) and [#0375](0375.md) both put a file picker in front of the user and must restrict it to formats that work; guessing produces a picker that accepts files which then silently fail. Record the answer in this issue's resolution notes so the UI children can cite it.

Note that a `renderedConfig` assertion proves libghostty *accepted the config key*, not that it *decoded the image file*. Confirming formats may need a manual check with real files, or an inspection of the upstream Ghostty source at `Ghostty.ref` `35e1a0160c4f6797e1bb1ef8e7a2b8c6b114ab58`. If the answer can't be established cheaply, say so plainly rather than asserting a format list.

**How an unreadable image path behaves.** If pointing `background-image` at a nonexistent path makes libghostty's diagnostics fail the whole config, then a single stale path silently drops *every other override with it* — font size, keybinds, env. That is the sharpest failure mode in this feature. Establish the behavior here; [#0375](0375.md) owns the guard.
