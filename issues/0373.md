# 0373 — Plumb libghostty's `background-image` and `background-opacity` config keys through `TerminalConfiguration`

| | |
|---|---|
| **Status** | open |
| **Module** | GhosttyKit / Theme |
| **Platform** | macOS |
| **First seen** | 2026-08-22 |

## Description

Nothing in Batty ever emits a `background-image` or `background-opacity` config key, so terminals are unconditionally opaque with no image behind them. The pinned libghostty supports both natively (see [#0372](0372.md) for the verified key table and the pin hashes) — this issue is the plumbing that makes them reachable, and nothing else.

**No UI.** This is deliberately the first child and deliberately headless: it is the only piece of the background feature with real risk, and it is the only piece that can be proven correct by unit test alone. [#0374](0374.md), [#0375](0375.md), and [#0376](0376.md) all sit on top of it and are pure UI once this lands.

## What to build

**A new `SettingsPreference` key group** for background settings — image path, fit, position, image opacity, and terminal background opacity — registered in `SettingsPreference.registerDefaults()` (`BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift:203-214`) alongside the existing `fontSizeKey` / `cursorStyleKey` / `cursorBlinkKey` entries, with `resolved…()` accessors matching the shape of `resolvedFontSize()` (`:56`) and `resolvedCursorStyle()` (`:61`).

**Emission from both config builders**, sourced from that key group:

- `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:172-246` — the per-Tab builder, at Tab init.
- `BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift:170-198` — `applyAppearanceToAllSurfaces()`, app-wide on any appearance change.

**Both, not one.** `setTerminalConfiguration` replaces the entire override set rather than merging it, so a key emitted from only one builder is silently dropped the next time the other runs — the wholesale-replace hazard documented in [#0372](0372.md). Changing the font size in Settings must not wipe the background. Consider factoring the shared emission into one helper both call sites invoke, rather than duplicating the logic; the two builders already duplicate the `keybind` block, and that duplication is exactly how this class of bug gets in.

**Use the typed builder method where one exists:** `Builder.withBackgroundOpacity(Double)` (`TerminalConfiguration.swift:194` in the SPM checkout) for opacity. The `background-image*` keys have no typed method and go through `withCustom(key:value:)` (`:212`), the same escape hatch already used for `keybind`, `env`, `command`, and `wait-after-command`.

**Defaults must be off.** No image; `background-opacity` effectively `1`. A user who never opens any background UI must see zero change in rendering.

**Emit nothing at all when disabled** — do not emit `background-opacity = 1` as a no-op. This mirrors how `wait-after-command` is scoped in the existing code (`TabRuntime.swift:213`, emitted only for `-c` panes) and keeps the `renderedConfig` negative assertions below clean and meaningful.

## Verification

**Mandatory, and the reason this issue is separable from the UI.** Unit tests in `BattyKit/Tests/BattyKitTests/` asserting that `tab.terminal.renderedConfig`:

- **contains** the emitted lines when the preferences are configured, and
- **omits** them when they are not.

`renderedConfig` only reflects a config that libghostty's own diagnostics accepted — `prepareConfig` fails closed otherwise. So a green `contains("background-image = …")` assertion is genuine proof that the pinned binary accepted the key, not proof of string formatting.

Model the tests and their doc comments on the existing `wait-after-command` pair in `BattyKit/Tests/BattyKitTests/SplitTreeTargetedSplitTests.swift`: the doc comment at `:146-162` records the method and the control experiment, `commandOverridePaneWaitsAfterTheCommandExits` (`:163`) is the positive assertion, and `nilCommandPaneDoesNotWaitAfterItsShellExits` (`:175`) is the negative. `BattyContextInjectionTests.swift` uses the same `renderedConfig` technique for the `env` keys, including an idempotence check at `:60-62`.

**Add the negative control the existing doc comment describes**: confirm a deliberately misspelled key (e.g. `background-imag`) is rejected — `diagnostics=1 "unknown field"` — so the harness is proven capable of failing. Without it, a passing test proves nothing about acceptance.

**Also add a test for the replace hazard**: configure a background, then run `applyAppearanceToAllSurfaces()`, and assert the background lines are still in `renderedConfig`. That is the regression this issue is most likely to ship.

Gate: `scripts/build.sh unit`.

## Also confirm and record

**Which image formats actually load** under the pinned ref, and whether animated formats are supported at all. [#0374](0374.md) and [#0375](0375.md) both put a file picker in front of the user and must restrict it to formats that work; guessing produces a picker that accepts files which then silently fail. Record the answer in this issue's resolution notes so the UI children can cite it.

Note that a `renderedConfig` assertion proves libghostty *accepted the config key*, not that it *decoded the image file*. Confirming formats may need a manual check with real files, or an inspection of the upstream Ghostty source at `Ghostty.ref` `35e1a0160c4f6797e1bb1ef8e7a2b8c6b114ab58`. If the answer can't be established cheaply, say so plainly rather than asserting a format list.

**How an unreadable image path behaves.** If pointing `background-image` at a nonexistent path makes libghostty's diagnostics fail the whole config, then a single stale path silently drops *every other override with it* — font size, keybinds, env. That is the sharpest failure mode in this feature. Establish the behavior here; [#0375](0375.md) owns the guard.
