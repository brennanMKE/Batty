## Description

After the #0127 re-resolution (dedicated drag handle, `PaneSwapDropTarget` on terminal body), the drop zone highlight is unreliable. Dragging a pane handle over another pane often does not highlight that pane at all; the highlight only appears when the cursor is near the edge of the target pane, not anywhere inside it.

## Expected behavior

Dragging the grip handle over any part of another pane highlights the entire pane immediately and consistently, regardless of where over the target the cursor is.

## Actual behavior

The drop zone highlight fires only near edges (the narrow strip of SwiftUI chrome where the AppKit NSView doesn't cover), or not at all.

## Root cause

`PaneSwapDropTarget` applies `.onDrop` to SwiftUI content (the ZStack of `TerminalPlaceholderView`s). The AppKit terminal NSView, positioned by `TerminalHostStore` directly into the window's AppKit layer, sits **above** the SwiftUI content in AppKit's z-order. The macOS drag system routes drags to the topmost AppKit view under the cursor; the terminal NSView claims the drag first, so SwiftUI's `.onDrop` hit-test is never reached except near pane edges where the NSView doesn't extend.

Additionally, any persistent SwiftUI `.onDrop` overlay — even one behind `.allowsHitTesting(false)` — registers its backing NSView as an AppKit `NSDraggingDestination` for all drag sessions regardless of declared UTTypes, blocking Finder file drops from ever reaching the terminal NSView.

## What has been tried and why it failed

### Attempt 1 — `Color.clear` SwiftUI overlay (commits `4967d31`, `996e378`)

Moved `.onDrop` onto a `Color.clear.contentShape(Rectangle())` overlay so the drop target is above the NSView in SwiftUI's rendering order.

**Broke:** Pane clicks — `Color.clear` with `contentShape` absorbs all pointer events.

### Attempt 2 — Add `.allowsHitTesting(false)` to the overlay (commit `bf84304`)

Added `.allowsHitTesting(false)` to prevent the clear overlay from absorbing clicks while hoping AppKit's drag routing would still reach the SwiftUI-registered `NSDraggingDestination`.

**Broke:** File drops (#0022) — SwiftUI's `.onDrop` registers its backing NSView as an AppKit `NSDraggingDestination` for all drag sessions, regardless of the declared UTTypes. With the overlay above the terminal NSView in z-order, ALL drags (including file drops) are claimed by the overlay's destination registration before reaching the terminal NSView that handles them.

Both attempts reverted in `0da775f`. The app is back to pre-#0143 state: file drops and clicks work; pane-swap highlight is unreliable.

## Fix

Drag-start overlay strategy: no overlay exists in the normal (no-drag) state, so Finder file drops reach `TerminalHostView` unimpeded. The moment the user starts dragging a pane's grip handle, a `PaneSwapDropZone` overlay appears over every other pane. These overlays use `.onDrop(of: [.plainText])` and show the highlight border. Because file drops during a pane-swap drag are an edge case the user is unlikely to need, blocking other drag types for the duration is acceptable.

Three components:

1. **`PaneSwapDragState`** — file-private `@Observable` singleton. Tracks `isDragging` and `sourcePaneID`. `startDrag(from:)` installs a global `NSEvent` left-mouse-up monitor (cleans up on drag end) and a 30-second fallback `Timer` (cleans up if Escape or other cancel path skips the monitor).

2. **`paneDragHandle` `.onDrag`** — calls `PaneSwapDragState.shared.startDrag(from: pane.id)` before returning the `NSItemProvider`, so the state is set the instant the DnD session begins.

3. **`PaneSwapDropZone`** — `Color.clear.contentShape(Rectangle()).onDrop(...)` overlay that only exists when `isDragging && sourcePaneID != pane.id`. Calls `tree.swapPanes` on drop with a spring animation and calls `endDrag()` via `defer`. Shows `strokeBorder` highlight while `isTargeted`. Replaces the old no-op `PaneSwapDropTarget` `ViewModifier`.

## Files changed

- `BattyKit/Sources/BattyKit/Views/PaneView.swift` — added `PaneSwapDragState` singleton; updated `paneDragHandle` to call `startDrag`; added conditional `.overlay` on the terminal ZStack; replaced `PaneSwapDropTarget` (no-op ViewModifier) with `PaneSwapDropZone` (live View); removed unused `@State private var isPaneSwapTarget`.

## Gotchas

Interactive verification needed — cannot be confirmed headlessly:

- **(a) Drop zones appear on target panes when dragging the grip handle.** The `PaneSwapDropZone` overlay only exists while `PaneSwapDragState.shared.isDragging` is true and the pane is not the source; verify it materializes on all non-source panes as soon as the drag begins.
- **(b) File drops from Finder still work after a pane-swap drag completes.** The overlay is removed by `endDrag()` which fires on mouse-up; verify that a subsequent Finder file drop inserts the path into the terminal as expected.
- **(c) The 30-second fallback clears overlays if the drag is cancelled (e.g. Escape).** The global NSEvent mouse-up monitor may not fire for keyboard-cancelled drags; the fallback `Timer` is the safety net — verify overlays eventually disappear after an Escape-cancelled drag.
