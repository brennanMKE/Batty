## Description

Follow-up to #0587 (`issue/0587`; see its `## Gotchas` "Slowest tests" and `## Review`). After #0587 a full warm `./build.sh unit` takes ~52 s, of which ~35–37 s is Swift Testing execution (3755 tests). Build changes can't take it lower. User goal: unit tests that are "very fast".

The suite is effectively serialized. `cd BattyKit && swift test --no-parallel` takes 37.5 s with per-test durations summing to 36.9 s, about the same as the ~33 s parallel wall time. The likely cause is MainActor default isolation (#0528's event-stream run saw nearly every test start in the first second and end at 20–23 s, queued on the main actor). `.serialized` traits appear in 4 test files, and shared state may also play a part. None of this has been confirmed.

Three suites account for ~20 s:

- `ProcessGitStatusScannerTests`: 11.45 s. Spawns real `git` subprocesses.
- `AtlasOwnershipExperimentTests`: 5.83 s, all from one test, `secondSurfaceOnSameControllerAtlasDelta()`. It's an experiment, and it runs in the routine gate.
- `ProjectStoreReadFailureTests`: 2.68 s.

## Expected

A full `./build.sh unit` runs well under 30 s, with the slow tests either made faster or moved to an opt-in slow tier. Scope for the planner:

- Speed up the slow suites (shared git fixtures, fewer subprocesses), or move them behind the slow tier. `build.sh` already reserves a `--full` flag for #0528's fast/full split (`build.sh:237`). Check #0528's state and build on it rather than adding a second mechanism.
- Decide where `AtlasOwnershipExperimentTests` belongs. An experiment probably shouldn't be in the routine gate.
- Find out why the suite serializes: MainActor default isolation, `.serialized` traits, shared global state. Decide whether non-UI suites can safely run `nonisolated` or in parallel.
- Measure the serial and parallel wall time before and after. Per-test durations from xcresult and parallel `swift test` are wall-clock from the start of the run, so use `swift test --no-parallel` (or the event stream) to rank tests.

## Resolution notes

> 🟢 Resolved 2026-11-12 — warm `./build.sh unit` drops from ~52 s to ~35 s (execution ~18 s) by taking the real-git fixtures off the main actor, skipping needless ACL cleanup, and moving the Atlas experiment to a new `--full` slow tier.

## Root cause

Confirmed in planning: every test is `@MainActor` (package default isolation), so Swift Testing queues them all on the main thread. Three suites dominated: `ProcessGitStatusScannerTests` ran 5+ synchronous `git` processes per test (`waitUntilExit()`) on the main actor; `ProjectStoreReadFailureTests` spawned `/bin/chmod -N` in every fixture's `cleanup()` although only `denyRead()` tests add an ACL; `AtlasOwnershipExperimentTests` (~5.9 s of vmmap and run-loop spins) ran in the routine gate.

## Fix

As planned:

- Real-git tests in `ProcessGitStatusScannerTests` and their static fixture helpers are `nonisolated`; the process-lifecycle tests (from `makeSleepProcess` on) stay `@MainActor`. The two no-op `terminate*` tests at the top of that range were included as the plan's line range said; they only touch the already-`nonisolated` scanner.
- `ReadFailureFixture` records `aclApplied` in `denyRead()`; `cleanup()` runs `chmod -N` only then.
- New slow tier: `SlowTests.enabled` (`BATTY_FULL_TESTS == "1"`), applied to `AtlasOwnershipExperimentTests.secondSurfaceOnSameControllerAtlasDelta()`. `./build.sh unit --full` exports `TEST_RUNNER_BATTY_FULL_TESTS=1` and the banner shows `full, `.
- `tools/check-report.py` `classify()`: on rc 0 with every test skipped, `ERROR "no tests ran (N skipped; slow tests need --full)"`, exit 2. Used `skipped >= total` rather than `==` (same effect, defensive).
- Docs: `AGENTS.md` (commands, tiers and timings, a nonisolated-for-blocking-processes bullet), `issues/Issues.md` Release row, `docs/batty-cli-install.md`, the `tools/run-ui-tests-vm.sh` comment, and a `## Relation` line in `issues/0528.md`.

Sub-30 s is not reached (see Plan "Target"); the follow-up about xcodebuild's ~13–16 s post-run tail is for the orchestrator to file.

## Review

Approved first pass (round 1). Checked: the `nonisolated` real-git tests and helpers touch no shared mutable state (no static vars, no `@unchecked Sendable` / `nonisolated(unsafe)`), use UUID-named temp dirs, and call only `nonisolated` helpers and the already-`nonisolated` scanner; the process-lifecycle tests stay `@MainActor`. `aclApplied` is set before the `chmod +a` call, so a throwing `denyRead()` still gets cleaned up. The `skipped >= total` guard can't fire on a filtered run that runs at least one test. `--full` reaches the runner via `TEST_RUNNER_BATTY_FULL_TESTS` (confirmed: 0 skipped) and `swift test` inherits `BATTY_FULL_TESTS` directly. The trait is the only skip mechanism and is documented in `AGENTS.md`; the Issues.md Release row names `--full`.

Minor, not blocking: `classify()` applies the all-skipped guard to `--stage ui` as well, so a VM run filtered to only on-request UI tests (e.g. `DemoSceneTests` without `BATTY_UI_DEMO=1`) now ends `CHECK UI: ERROR (… slow tests need --full)` — the exit 2 is consistent with "zero tests run", but the `--full` hint is unit-specific and misleading there. Needs a follow-up (scope the hint to `stage == "unit"`).

Findings (premises checked):

1. **Serialization is MainActor default isolation, confirmed.** Every test struct is `@MainActor` (explicitly or by `.defaultIsolation(MainActor.self)` in `Package.swift`), so Swift Testing starts them all and they queue on the main thread. `.serialized` (4 files) only orders tests within their own suite and is not a factor. A 6 s `sample` of the run with the three slow suites skipped shows the main thread busy in ordinary app-model tests (`MultiWindowStoreTests`, `ProjectEditorWindowTests`, `ProjectOpenTests`, …) doing file I/O (atomic writes, `rename`, `fsync`, temp dirs) and AppKit. There is no fourth hotspot. Those tests exercise `@MainActor` app types; marking them `nonisolated` would only add hops back to the main actor, so the long tail (~15–17 s) is not touched here.
2. **`ProcessGitStatusScannerTests` blocks the main actor on its *fixtures*, not on the scanner.** `ProcessGitStatusScanner` is already `nonisolated` and runs git in `Task.detached`; the cost is `runGit`/`makeRepoWithOneCommit` running 5+ synchronous `git` processes per test with `waitUntilExit()` on the main actor. Marking the real-git tests and their static fixture helpers `nonisolated` lets them run on the global executor in parallel with each other and with the main-actor queue. It compiled with no other change and passed. The process-lifecycle tests in the same struct (`terminateAndWaitBriefly…`, `waitForPendingTeardown…`, `registryDrain…`, `terminateIfRunningSignals…`, `aCompletedScansCleanup…`) call main-actor helpers (`killAndReap`, `killAndReapAll`) and stay `@MainActor`.
3. **`ProjectStoreReadFailureTests` spends ~2.5 s spawning `/bin/chmod -N` in every fixture's `cleanup()`,** even though only the tests that call `denyRead()` ever add an ACL.
4. **`AtlasOwnershipExperimentTests` is a finished experiment kept as a regression check.** #0287 is `resolved`; the doc comment says the test should fail if libghostty ever starts sharing atlases per App. It runs `/usr/bin/vmmap` four times and spins the main run loop 3 × 0.3 s (#0435, open). It can't be made cheap or moved off the main actor (real `NSWindow` + surfaces). Decision: **keep it, move it to the opt-in full tier.** Don't delete it.
5. **xcodebuild adds ~12–13 s after the test run ends.** In every full xcodebuild run, "Testing started completed" lands 12.5–13.4 s after the last test line (02:52:03.7 → 02:52:16.3 in one run). With `swift test` the gap is ~2 s. A 20-test filtered run costs 3.6 s total, so the gap grows with the number of results (xcodebuild used ~10 s more CPU than `swift test` for the same tests). `-quiet` saved only 2.4 s. This is outside the test code; see "Target" below.

### Slow tier: build #0528's unit half here

#0528 is `open`, unworked, and reserves `--full` (`build.sh:239`). Its §1 asks for exactly this mechanism, and its open question 1 leans toward an environment-gated trait because skipped tests stay visible in both runners. Decision: implement **only the unit half of #0528 §1** here. The VM `--build-only`/`--full` work stays in #0528.

- Mechanism: an environment-gated trait, `.enabled(if: SlowTests.enabled, "slow: run with ./build.sh unit --full")`. `SlowTests.enabled` reads `BATTY_FULL_TESTS == "1"` from `ProcessInfo.processInfo.environment`. Skipped tests show as skipped in both runners and are never silently dropped.
- `./build.sh unit --full [filters…]` exports `TEST_RUNNER_BATTY_FULL_TESTS=1` before `xcodebuild test`. xcodebuild strips the prefix and passes `BATTY_FULL_TESTS=1` to the test runner. `cd BattyKit && BATTY_FULL_TESTS=1 swift test` is the package equivalent.
- The only slow test today is `AtlasOwnershipExperimentTests.secondSurfaceOnSameControllerAtlasDelta()`. The criterion (write it in AGENTS.md): a test is slow if it takes over ~1 s on its own (`swift test --no-parallel --filter`), *and* it can't be made fast or taken off the main actor, *and* it guards an external assumption rather than Batty logic.
- **Routine count is unchanged:** `CHECK UNIT: PASSED (3763 tests)`, with `==> unit: 3763 tests, 0 failed, 1 skipped`. (`check-report.py` reads `totalTestCount` from the xcresult, which includes skipped tests.) The full tier reports `3763 tests, 0 failed, 0 skipped`, apart from the existing `getuid() != 0` trait in `SessionNameToolTests`, which never skips for a normal user.
- **Guard against an all-skipped filtered run.** `./build.sh unit AtlasOwnershipExperimentTests` without `--full` would otherwise print `PASSED (1 test)` having run nothing. In `tools/check-report.py` `classify()`, when `rc == 0`, `total > 0` and `skipped == total`, return `ERROR`, `"no tests ran (N skipped; slow tests need --full)"`, exit 2. That matches "zero tests run is exit 2".
