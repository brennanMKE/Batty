# 0556 — Bell Feed rows stay in the list after the user visits the Pane they came from, so read notifications pile up under the bell

| | |
|---|---|
| **Status** | open |
| **Module** | BellFeed / Split / Tabs |
| **Platform** | macOS |
| **First seen** | 2026-11-05 |

## Description

A Bell Feed row stays in the list after the user goes to the Pane it came from. Today the visit only marks the row seen, so read notifications pile up until the 200-entry cap evicts them. The user decided on 2026-11-05: "Prune rows once we go to a pane with a notification." A visit to the Pane a row belongs to should now remove that row from the Bell Feed. The #0297 decision history and the #0523 capture log keep their records.

The goal, from the user (2026-11-05):

> We should make it our goal to declutter the notification list as much as possible so only what is useful remains.

Split out of [#0555](0555.md), "Further decluttering". That issue replaces its own earlier default, that read rows stay, with this decision.

## What marks rows seen today

Checked against main `c51a7e1b`. `WindowRuntime.markActiveTabSeen()` (`BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift:1029`) takes the selected Session's `focusedTerminalPane`, reads its `activeTabID`, marks every unseen entry with that `tabID` seen, and decrements the counters. The callers:

| Caller | Fires on |
|---|---|
| `SessionDetailView` `.onAppear` (`Views/SessionDetailView.swift:188`) | The detail view appearing, for example when a Window opens |
| `SessionDetailView` `.onChange(of: windowRuntime.selectedSessionID)` (`:194`) | Any change of the selected Session |
| `SessionDetailView` `.onChange(of: selectedSession?.tree.focusedPaneID)` (`:212`) | Any change of the focused Pane |
| `PaneView` `.onChange(of: pane.activeTabID)` → `AppStateStore.markActiveTabSeen()` (`Views/PaneView.swift:352`, `AppStateStore.swift:1980`) | Any change of a Pane's active Tab. It acts on the key Window, or on `windows.first` |
| `AppStateStore.markBellSeen(id:)` | A Feed row click or a notification tap, before `jumpToBellEntry` |
| `AppStateStore.markAllBellsSeen()` | Window > Mark All Bells Seen |

Three things are worth knowing:

- **Neither the Window becoming key nor the app becoming active is a trigger.** No `didBecomeKey` or `didBecomeActive` path calls `markActiveTabSeen`.
- **Seen is per Tab, not per Pane.** Only the active Tab's rows are marked. A row for an inactive Tab in the visited Pane stays unread.
- **The `onChange` triggers fire whatever flipped the value.** That includes layout-origin flips: the selection falling back after a Session closes (`removeSession`), the focus falling back after a Pane closes (`closePane`), the active Tab falling back after a Tab closes (`PaneRuntime.removeTab`), a new split taking focus, and `onAppear` on Window open. Each one marks the newly active Tab's rows seen today.

## Expected behavior

- When the user **really visits** a Tab, every Bell Feed row with that `tabID` is removed. The Tab and Pane counters, and the Session's unseen counter, are decremented for the rows that were still unread, as `cleanUpBellState(forTabIDs:)` already does (`WindowRuntime.swift:1121`). Reuse that, or `BellFeedStore.removeEntries(matchingTabIDs:)` plus `decrementUnseen`.
- A **real visit** is one of these user actions:
  - clicking the Sidebar row, or Cmd-1..9
  - clicking a Pane, or Cmd-Option-arrows
  - clicking a Tab chip, or Cmd-Option-1..9 and next/previous Tab
  - a Bell Feed row click or a notification tap (click-to-jump)
  - the CLI focus verbs (`session focus`, `pane focus`, `tab focus`), because `activateWindow` brings the Window and the app to the front
- These are **not** visits: a selection or focus fallback after a close, a new split or new Tab taking focus, the detail view's `onAppear`, the Window becoming key, and the app becoming active. Today they mark rows seen. Keep that, but don't prune on them.
- **Mark All Bells Seen** keeps marking rows seen and doesn't remove them.
- `BellDecisionHistory` and the capture log are not touched. Neither is ever pruned from the Feed. A rating (#0524) for a removed row is dropped with it. `pruneRatingState` already runs on `removeEntries`.

## Implementation constraint (binding)

Read `docs/swiftui-observation-rules.md` first. The current seen-marking lives in `onChange` handlers, which can't tell a gesture from a layout fallback. Don't add the prune there, and don't filter by origin inside `onChange`. Put the prune in the event-origin code that performs the visit: the store and Window methods the gestures, the keyboard commands, `jumpToBellEntry` and the XPC focus verbs call. Expose one entry point, for example `WindowRuntime.visit(tabID:)`. Never hop the write into a `Task` (the #0229 lesson). The plan has to list every gesture path that writes `selectedSessionID`, `focusedPaneID` or `activeTabID`, and say which of them call the visit.

## Open questions, with recommended defaults

1. **Pane or Tab granularity?** The user said "a pane". Focus and seen-ness are per Tab (`Concepts.md`, Focus), and a row for an inactive Tab hasn't been looked at. **Recommended:** prune the rows for the Tab that becomes active in the visited Pane, not every Tab in it. Rows for that Pane's other Tabs go when those Tabs are visited.
2. **Fallback focus after a close.** **Recommended:** mark seen, as today, but don't prune.
3. **Footprint warning rows (#0290)** have no Tab (`BellFeedEntry.systemID`). **Recommended:** never pruned by a visit. They leave by cap, as now.
4. **Session Reminder rows ([#0514](0514.md), open).** #0514 specifies that a Reminder entry is marked seen when the user selects its Session, by any path that runs `markActiveTabSeen()`. Its jump is Session-level, and its `paneID`/`tabID` are only placeholders taken at fire time. **Recommended:** a real visit to the Reminder's Session removes its Reminder row, the same way a Tab visit removes bell rows. Tell #0514's implementer, since #0514 is worked next. If #0514 lands first, this issue extends it. If this lands first, #0514 builds on the visit entry point.
5. **Rows the user opened in the Feed without jumping**, for example by keyboard selection. **Recommended:** not a visit. Only click-to-jump counts.
