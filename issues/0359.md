# 0359 — ProcessStatusPaneContent's tabLookup defaults to a nil lookup, so followingTab targets tombstone outside the splitPane construction path

| | |
|---|---|
| **Status** | open |
| **Module** | Pane |
| **Platform** | macOS |
| **First seen** | 2026-08-21 |

## Description

`ProcessStatusPaneContent.init(target:tabLookup:)` defaults `tabLookup` to `{ _ in nil }`, and `SplitTree`'s pane-construction helper repeats the same default. Only `SplitTree.splitPane` supplies a real closure (resolving a tab id through the live tree). Any `.processStatus` `PaneRuntime` built through another path inherits the nil lookup — and a nil lookup makes *every* `.followingTab` target resolve to `.sourceTabGone`, tombstoning the pane instantly.

The trap is not limited to construction-time targets: the lookup is consulted whenever a `.followingTab` target is (re)resolved, so a pane created with no target (or a `.pid` target) through a nil-lookup path will also tombstone the moment the user picks a terminal pane from the view's own "Follow a Terminal Pane…" menu. The UI offers a choice the content object silently cannot honor.

A defaulted dependency that is required for a whole feature to function is the wrong shape: either the lookup should be a required init parameter (no default), or the nil default should be impossible to reach from any production construction path — enforced, not hoped.

## Expected behavior

Every constructed `.processStatus` content object can resolve `.followingTab` targets, regardless of which code path built it; "Follow a Terminal Pane…" works on any process-status pane. If a construction path genuinely cannot supply a lookup, that path cannot compile (no silent default).

## Actual behavior

Only `splitPane`-built panes get a working lookup; any other construction yields a content object where every `.followingTab` target — including one chosen later by the user — immediately reports `.sourceTabGone`.
