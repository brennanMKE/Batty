## Description

**CRITICAL (inferred). Related to #0601 and #0604.** On a Tab switch or a Session switch, the outgoing Tab's `TerminalPlaceholderView` sees `isVisible` go false in `.onChange(of: isVisible)` and calls `TerminalHostStore.setPlacement`, which sets `isHidden = true` on its `AppTerminalView`. That view is usually the window's first responder. AppKit documents that hiding the first responder makes its next valid key view the first responder (or the window). So a first-responder change, `resignFirstResponder` → `core.setFocus(false)` and possibly `becomeFirstResponder` on another visible terminal, runs synchronously inside the `NSHostingView.layout` pass that flushed the `onChange`. That is the #0229 crash class: a responder-changing AppKit side effect from a SwiftUI-driven callback.

`docs/swiftui-observation-rules.md` sanctions the placement path's frame and `isHidden` writes for their **constraint** effect (they dirty no constraints since #0601). It doesn't cover this **responder** side effect, and the code that decides visibility is reconstructing a model fact (which Tab or Session is showing) from an observed flip instead of the action that changed it pushing it.

## Root cause

Confirmed. `TerminalPlaceholderView`'s `.onChange(of: isVisible)` called `TerminalHostStore.setPlacement`, which set `isHidden = true` on the outgoing Tab's `AppTerminalView` from inside the `NSHostingView` layout pass that delivered the `onChange`. When that view was the window's first responder, AppKit moved the first responder right there. The new probe tests observed it on unfixed sources, for both a Tab switch and a Session switch: `makeFirstResponder(SwiftUI.KeyViewProxy) previousIsTerminal=true inLayout=true`. AppKit picked the next valid key view, a SwiftUI proxy, mid-layout, and the terminal was no longer first responder. The visibility decision was also reconstructed from an observed flip (`tab.id == pane.activeTabID && isSessionSelected`) rather than pushed by the action that changed it.

## Fix

Implemented per the plan. Ownership after the fix:

- The actions own *whether* a Tab's terminal is shown, through `TerminalHostStore.setTabShown(_:forTabID:)`, called synchronously in the event that changed the model:
  - `PaneRuntime.activeTabID`'s `didSet` → `moveShown(from:to:)`;
  - `WindowRuntime.selectedSessionID`'s `didSet` and `init` → `applyTerminalVisibility(deselecting:selecting:)`;
  - `hidePane` (`setTabShown(false)` plus `forgetFrame`) and `showPane` (`setTabShown(true)` for the active Tab, selected Session only);
  - `SplitTree.adopt` (`isInSelectedSession && !isHidden`).
- Hiding resigns the view as first responder to the window first (`resignFirstResponderIfHosting`, `makeFirstResponder(nil)`).
- The placeholder only reports *where* it is, through `reportFrame(_:forTabID:)` from `onGeometryChange`. That call moves a shown Tab's view and reveals it on its first frame, and never hides.
- Deleted: `onChange(of: isVisible)`, the `isVisible` parameter, `@State lastFrame`, the `isSelectedSession` environment value and key, and its `SessionDetailView` write. That write was one of #0604's per-Session fan-out reads. `setPlacement` and the `placements` map are gone too, replaced by `shownTabIDs` and `frames`.
- `updatePlacements` is now an internal test reconcile with no production caller.

Divergences and details beyond the plan:

- `reportFrame` re-applies `setSurfaceVisible` and `syncOccludedTicker()` on **every** report when the view exists, not only when it changed `isHidden`. A surface defaults to display-visible (`TerminalSurfaceCoordinator.isDisplayVisible = true`). Only the old per-report `setPlacement` call told a background Tab's freshly created view that it was not visible and put it in the occluded tick set (#0288). Keeping that cadence avoids a rendering and bell-ticking regression for background Tabs.
- `setTabShown` runs the surface-visibility pass only when the view's `isHidden` actually changed. A view that stays hidden gets the pass from its placeholder's `reportFrame`. This keeps `TerminalHostStoreOcclusionTests`' recorded `setSurfaceVisible` sequences unchanged.
- The two halves are factored into private `recordShown` / `recordFrame` helpers, so `updatePlacements` makes exactly one surface-visibility pass per view, as before.
- Added test accessors `isTabShown(_:)` and `reportedFrame(forTabID:)`. `placement(forTabID:)` composes them.

Then only `hidingTheFirstResponderTerminalResignsToTheWindow` changes, and both probe tests still pass (verified in that run). Left as planned; flagged for review.

## Review

Approved first pass. One review change: the `shownTabIDs` doc comment in `TerminalHostStore.swift` named only `setTabShown` and `releaseTerminalView` as writers; it now also names the test reconcile `updatePlacements`, which writes through the shared `recordShown` helper.

Findings:

- **Every visibility push is event-origin.** All `PaneRuntime.activeTabID` writers were re-grepped: `addTab`, `removeTab`, `closeOtherTabs`, the three `select*Tab` methods, `jumpToTab`, `jumpToBellEntry`, `focusTabForXPC`, `ProjectTreeBuilder` (before the tree is in a window) and `PaneView.activeIDBinding`, which the tab bar writes from a tap. All `selectedSessionID` writers are actions, plus `init`, which calls `applyTerminalVisibility` itself. `pane.isHidden` is written only by `hidePane` and `showPane`. `isInSelectedSession` is written only by `applyTerminalVisibility`. `reportFrame` has one caller, the placeholder's `onGeometryChange`. Nothing that calls `setTabShown` or `moveShown` is reachable from `body`, `onChange`, `onGeometryChange` or a representable update.
- **`reportFrame` cannot hide and cannot change the first responder.** `recordFrame` only writes `frame` and `isHidden = false`, and only for a shown Tab. Unhiding is responder-neutral. The per-report `setSurfaceVisible` and `syncOccludedTicker()` are the same cadence the old `setPlacement` had on every geometry report. The deviation keeps #0288 occlusion for background Tabs' freshly created views and adds no cost over `main`.
- **Keep the explicit `makeFirstResponder(nil)`.** It is a resignation, not a second writer of focus. It writes no model state; Batty does not hook `focusBridge.onFocusChange`. `TerminalSurfaceFocuser` stays the only code that promotes a terminal, and `TerminalClickFocusMonitor` stays the only click-side writer. Without the explicit resign, AppKit picks the next valid key view, which can be another visible terminal: in a split, or the incoming Session's terminal. That terminal's `becomeFirstResponder` runs `core.setFocus(true)`, which shows a focused cursor and, for an app that turned on focus reporting (DEC 1004: vim, tmux), writes a focus-in sequence to the wrong PTY. Resigning to the window is deterministic and has no such side effect. The cost is about 90 extra update requests per switch in the 12-Session case (616 max, under the 770 ceiling), measured once. That is acceptable, and #0604 is the place to reduce per-switch work.
- **No creation path is missing a push.**
  - New Session, Project open (`addProjectSession`) and duplicate Session all select the new Session, so `selectedSessionID`'s `didSet` pushes. Project open's splits go through `adopt` while `isInSelectedSession` is false, and `hidePane` runs before selection.
  - XPC or UI splits into a background Session go through `adopt`. XPC or UI new Tabs go through `addTab`, then `moveShown`, which inherits the outgoing Tab's state.
  - Closing a Tab: `removeTab` and `closeOtherTabs` call `moveShown` before release, so the closing view is resigned and hidden first.
  - Closing a Session: its Tabs are released before `selectedSessionID` changes, and `applyTerminalVisibility` skips the removed Session.
  - A new window: `init` pushes for its first Session.
  - Restore: there is no workspace restore since #0172.
  - Sessions never move between windows: `moveSessions` only reorders within a window.
- **`isSelectedSession` is gone.** There are no remaining readers or writers anywhere in the repo.
- **Tests:** fail-before evidence is recorded for both the probe tests and the key store tests. There are no sleeps; the probe tests settle through `LayoutConvergenceProbe`. Each "hidden" assertion starts from a revealed view, and the controls (background Session, already-hidden Pane) assert a visible counterpart, so they are not vacuous.
- **Not blocking, pre-existing:** `adopt` runs before `SplitTreeNode.inserting`, so if an insert fails, an orphaned new Pane's active Tab stays in `shownTabIDs`. It was already orphaned before this change (its Tab is never released either); this adds one UUID to that existing orphan.

### Premises checked

- **Confirmed.** `TerminalPlaceholderView.swift:47-62`: `onGeometryChange` and `.onChange(of: isVisible)` both call `TerminalHostStore.setPlacement`. `setPlacement` (`TerminalHostStore.swift:445-464`) writes `view.isHidden = true` when `!placement.isVisible`. `PaneView.swift:273` computes `isVisible: tab.id == pane.activeTabID && isSessionSelected`. So on a Tab or Session switch the outgoing view is hidden from inside the SwiftUI update.
- **Confirmed, with a correction.** Hiding the first responder changes it, and AppKit does it through the window's overridable `makeFirstResponder(_:)`. A scratch AppKit program (window not key, two accepting subviews, the first one first responder) showed `isHidden = true` calling `window.makeFirstResponder(nil)`. The view got `resignFirstResponder`, and the window became first responder, not the sibling. A key window with a recalculated key-view loop may pick `nextValidKeyView` instead, as the issue says. Either way the responder change runs where the `isHidden` write runs. A `makeFirstResponder` override can observe it, so the probe test below can see it.
- **Confirmed.** Unhiding never changes the first responder. AppKit reassigns it only when the first responder, or one of its ancestors, is hidden. A reveal from layout is responder-neutral, and since #0601 it is constraint-free (`terminalPlacementWriteMarksNoViewAsNeedingUpdateConstraints`). **Hiding** from layout is the hazard. This plan keeps reveal-on-first-frame in the placeholder path and moves every hide into the actions.
- **Every writer of the three visibility inputs is event-origin.** The implementer re-greps to confirm.
  - `PaneRuntime.activeTabID` is written by `addTab`, `removeTab`, `closeOtherTabs`, `selectTab(at:)`, `selectNextTab`, `selectPreviousTab` (`PaneRuntime.swift:274-362`), `WindowRuntime.jumpToTab`/`jumpToBellEntry` (`:1216`, `:1251`), `AppStateStore.focusTabForXPC` (`:2012`), `ProjectTreeBuilder` (`:175`, before the tree is in a window) and `PaneView.activeIDBinding` (`:723`). `SlidingTabBar` writes that binding only from `.onTapGesture` (`SlidingTabs/Sources/SlidingTabs/SlidingTabBar.swift:214`).

### Design

**Ownership after the fix:**
- The actions own *whether* a Tab's terminal is shown. They push it to the store synchronously, in the event that changed the model.
- The placeholder reports *where* it is: frames only, through `onGeometryChange`.
- The store shows a view when the Tab is shown **and** a frame is known. It never takes visibility from the placeholder.

`onChange(of: isVisible)` and the `isVisible` parameter are deleted.

The fact pushed: a terminal Tab is shown ⇔ its Session is the window's selected Session ∧ `!pane.isHidden` ∧ `pane.activeTabID == tab.id`. Window occlusion stays separate, as today (`setSurfaceVisible` = `!view.isHidden && windowVisible`).

#### `BattyKit/Sources/BattyKit/Runtime/TerminalHostStore.swift`

Replace `placements: [UUID: Placement]` with two non-observed records:
- `shownTabIDs: Set<UUID>`: what the actions last pushed. Absent means not shown.
- `frames: [UUID: CGRect]`: the last frame each placeholder reported. Absent means no frame yet.

New API, replacing `setPlacement(_:forTabID:)`, which is deleted:

- `func reportFrame(_ frame: CGRect, forTabID id: UUID)`. **Only the placeholder calls it.**
  - Ignore released ids.
  - Store the frame.
  - If the view exists and the Tab is in `shownTabIDs`: write `view.frame` when it differs, and unhide the view if it is hidden (the first-mount and show-Pane reveal).
  - If the Tab is not shown, record the frame only. Don't move a hidden view; that is today's behaviour, and it avoids resizing background PTYs on every window resize.
  - **It never sets `isHidden = true`.** Call `setSurfaceVisible` and `syncOccludedTicker()` only when this call changed `isHidden`.
- `func setTabShown(_ shown: Bool, forTabID id: UUID)`. **Only actions call it.** Idempotent: return early when membership doesn't change.
  - Ignore released ids.
  - `true`: insert. If the view exists and a frame is known, apply the frame and unhide.
  - `false`: remove. If the view exists and is visible, call `resignFirstResponderIfHosting(view)`, then `view.isHidden = true`.
  - Then `setSurfaceVisible(effective)` and `syncOccludedTicker()`.
- `func isTabShown(_ id: UUID) -> Bool`, for the transfer in `PaneRuntime` and for tests.
- `func moveShown(from oldID: UUID, to newID: UUID)` is the Tab-switch primitive. It computes `let wasShown = shownTabIDs.contains(oldID)`, calls `setTabShown(false, forTabID: oldID)`, then `setTabShown(wasShown, forTabID: newID)`. A Tab switch never changes whether its Pane is on screen, so the incoming Tab inherits the outgoing Tab's state. `PaneRuntime` therefore needs no Session or window knowledge.
- `func forgetFrame(forTabID id: UUID)`, used by `hidePane`. The placeholder unmounts, so on `showPane` the reveal waits for the remounted placeholder's first frame and never flashes at a stale frame.
- `private func resignFirstResponderIfHosting(_ view: AppTerminalView)`: if `view.window?.firstResponder` is `view` or a descendant of it, call `window.makeFirstResponder(nil)`. This makes the window the destination instead of whatever `nextValidKeyView` AppKit would choose, which could be another visible terminal (the transient wrong-surface focus in the issue's Mechanism). It is a resignation, never a promotion. The deferred, generation-guarded `TerminalSurfaceFocuser` stays the only promoter of the incoming terminal. It runs only from `setTabShown(false)`, which only actions call, so it never runs inside layout. The comment must say so.
- `terminalView(for:windowID:)` is unchanged: a new view is created hidden. Nothing in `body` reveals it. The first `reportFrame` does, if the Tab is shown.
- `releaseTerminalView(forTabID:)`: remove the id from `shownTabIDs` and `frames` **before** the `guard let view` early return. Entries for Tabs whose view was never created must not leak (the #0285 / #0315 class `hidePane`'s comment describes).
- `updatePlacements(_:forWindowID:)` has no production caller. Keep it as an `internal` test reconcile, reimplemented as, per id, `setTabShown(placement.isVisible)` then `reportFrame(placement.frame)`, and hide this window's views that are absent from the map with `setTabShown(false)`. Keep the `Placement` struct as its input type. Keep `placement(forTabID:)` as a test accessor that composes `frames[id]` and `shownTabIDs`, returning nil when neither is recorded.
- Rewrite the doc comments that name `setPlacement`: the type comment, `effectiveSurfaceVisible`, `syncOccludedTicker`, and the `terminalView(for:)` `translatesAutoresizingMaskIntoConstraints` comment, which now says "`reportFrame` writes this view's frame and may unhide it from SwiftUI's layout pass".

### User checklist

## Rule violated

- `docs/swiftui-observation-rules.md`, "AppKit interop hazards", rule 1: never synchronously call responder-changing AppKit APIs from SwiftUI-driven callbacks. Hiding the first responder is one.
- Same doc, "Two-way model ↔ AppKit sync": route intent from its source; don't reconstruct it from downstream observable flips.
- swift-guidance `swiftui-observation.md`: no AppKit side effects with responder or layout consequences from `onChange` during an update.

## Mechanism

Tab switch: chip click → `activeTabID` write → SwiftUI update inside `NSHostingView.layout` → outgoing placeholder's `onChange(of: isVisible)` → `isHidden = true` on the first-responder terminal → AppKit moves first responder to `nextValidKeyView` → `resignFirstResponder`/`becomeFirstResponder` run mid-layout. Session switch is the same through `\.isSelectedSession`. A transient wrong-surface focus is also possible until `TerminalSurfaceFocuser`'s deferred promotion focuses the incoming Tab.

## Evidence

- **Proven from code:** the call path and that it runs from `onChange` / `onGeometryChange`.
- **Inferred:** the responder change, from AppKit's documented `isHidden` behavior. Not reproduced; whether AppKit raises depends on what the new responder does.

## Fix direction (restructure write ownership; no `Task`/main-queue hop)

Make Tab and Session visibility an action-owned push, the way #0602 did for selection effects:

- One choke point for `PaneRuntime.activeTabID` writes (a `didSet` or one method every writer calls) and the existing `WindowRuntime.applySelectionVisibility` call a new `TerminalHostStore.setTabVisible(_:forTabID:)` synchronously, during event dispatch. It hides the outgoing view and shows the incoming one there, so any responder change AppKit makes happens outside layout.
- The placeholder then reports frames only, through `onGeometryChange`; delete `onChange(of: isVisible)`. First-mount reveal must still work: `TerminalSurfaceFocuser`'s retry ladder (`Commands/TerminalSurfaceFocuser.swift:68-76`) relies on placement unhiding a freshly mounted view.
- Update the sanctioned-exception paragraph in `docs/swiftui-observation-rules.md` and `docs/view-hierarchy.md`: placement from layout is frame-only; visibility is pushed by the actions.
- Do not defer the `isHidden` write into a `Task` or `DispatchQueue.main.async` (#0229).
