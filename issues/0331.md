## Description

Once the non-terminal view kinds exist (#0304 Git Status, #0305 Process Status, #0313 LM Studio dashboard, #0314 system metrics), a person using the app has no way to create one. #0315 gives *agents* `batty pane split --view git-status` over XPC; nothing gives the *user* a menu item, shortcut, or palette command that does the same thing. In the user's words:

> "Is there an issue to support using the menu to split out a new pane and select one of the new view types?"

There was not — this is that issue. The gap is confirmed in the design record itself: `docs/design/git-status-view.md` states plainly that "the CLI is the only creation surface either issue actually commits to building (`#0301`: 'creatable and closable from the `batty` CLI'; nothing in `#0304`/`#0301` asks for a toolbar/menu 'New Git Status Pane' action)" (`docs/design/git-status-view.md:123-126` on `main`). None of the four design docs in `docs/design/` says anything about menu placement or GUI creation — their "menu" mentions are all context menus *inside* the views. So as things stand, typed panes would ship agent-only by design, and this issue exists to close that asymmetry deliberately rather than by omission.

## What exists today — `main` vs the in-flight `issue/0315` branch (verified 2026-08-09)

**On `main`, there is no pane-kind concept in Swift source at all.** `git grep PaneContentKind main` matches only docs (`docs/pane-kinds.md`, the four `docs/design/*.md`) and issue files — no `.swift` file. The menu surface this issue would extend:

- The **Pane menu** (`BattyKit/Sources/BattyKit/Commands/BattyCommands.swift:210` on `main`) opens with four split items — Split Horizontally (`:211-218`), Split Vertically (`:220-227`), Split Full-Height Column (`:229-236`), Split Full-Width Row (`:238-245`) — each calling `tree.splitFocusedPane(direction:inheritingFrom:)` or `tree.splitFullDimension(direction:inheritingFrom:)`, which are terminal-only (they inherit the source pane's cwd and spawn a shell; no kind parameter exists on `main`). Then a "Layouts…" item (`:247-253`).
- The corresponding **`ShortcutAction` cases** (`BattyKit/Sources/BattyKit/Shortcuts/ShortcutAction.swift` on `main`): `splitHorizontal` (Cmd-D), `splitVertical` (Cmd-Shift-D), `splitFullHeightColumn` (Cmd-Opt-D), `splitFullWidthRow` (Cmd-Shift-Opt-D), per `defaultBinding`. The catalog holds 25 cases; its header comment pins `rawValue` as a `UserDefaults` persistence key, append-only.
- The **Command Palette** builds its list from the catalog: `for action in ShortcutAction.allCases where action != .commandPalette` (`BattyKit/Sources/BattyKit/Views/CommandPaletteView.swift:55` on `main`). Any case added to `ShortcutAction` appears in the palette (and in Settings ▸ Shortcuts) with no palette-side listing work — though `CommandPaletteView.dispatch(_:)` (`CommandPaletteView.swift:195`) switches exhaustively over the enum, so each new case also needs one dispatch arm, compiler-enforced.
- **Picker precedent** exists for the "one item opens a chooser" shape: the layout picker (`ShortcutAction.layoutPicker`, Cmd-Shift-L) and theme selector (`ShortcutAction.themeSelector`, Cmd-Shift-T) are both single menu items that post a notification (`.battyToggleLayoutPicker` at `BattyCommands.swift:248`, `.battyToggleThemeSelector` at `:126`) toggling a palette-style overlay. Note the layout picker's menu item is disabled unless the session has exactly one pane (`BattyCommands.swift:253`, `tree.allPanes.count != 1`).

**On branch `issue/0315` (in flight — review round 1 requested changes; not merged, plus uncommitted work-in-progress in `BattyCommands.swift` / `BattyShortcuts.swift` / `WindowRuntime.swift` at the time of filing):**

- `PaneContentKind` (`BattyKit/Sources/BattyXPCCore/PaneContentKind.swift`, new file on the branch) — `String`-backed, `CaseIterable`, with `terminal`, `git-status`, `process-status`, `lm-studio-dashboard`, `system-metrics` and a `displayName` per kind ("Terminal", "Git Status", …). One string used identically as Codable raw value and CLI flag value, per `docs/pane-kinds.md` §5.
- `PaneRuntime.kind` / `Pane.kind`, a kind-switch in `PaneView.body`, and `batty pane split --view <kind>` where omitting `--view` means Terminal and an unknown kind exits `1` listing the valid set.
- Non-terminal kinds render a deliberately provisional placeholder — no real view ships on that branch; the four view designs remain unapproved under #0301's gate.
- The branch's Tab menu work (in flight) disables Cmd-T/Cmd-W/etc. for non-terminal panes.

Nothing about kind selection touches the Pane menu's split items on either `main` or the branch: after #0315 lands, the GUI's split actions still produce only terminal panes, and only the CLI can produce anything else.

## The central design question (posed here, deliberately not answered)

Splitting now has **two dimensions: a direction and a kind.** The menu has four direction-shaped split actions; with five kinds that is up to twenty combinations, and the menu cannot simply be the cross product. Plausible shapes, none picked here — this wants settling with the user, the same way #0315 holds its verb shape open:

1. **A separate "New Pane ▸" submenu listing kinds**, distinct from the existing Split items, which stay terminal-only. Simple, but leaves the direction question dangling (see below) and adds a second creation vocabulary next to "Split".
2. **Kind as a submenu under each existing split item** ("Split Horizontally ▸ Terminal / Git Status / …"). Complete, but turns four one-click items into four submenus and taxes the overwhelmingly common case (terminal).
3. **A single "Split with View…" item opening a picker.** There is direct precedent: the layout picker and theme selector are both single `Cmd-Shift`-chorded items posting a toggle notification that opens a palette-style overlay picker. A kind picker would be the third instance of that pattern.
4. Something else (e.g. a per-pane toolbar "+" affordance rather than a menubar item).

Sub-questions that follow from the shape, also left open:

- **Does each kind get its own `ShortcutAction` case** (so "Split with Git Status" is individually rebindable, appears in the Command Palette via the `allCases` loop, and shows in Settings ▸ Shortcuts), or does only a single picker action enter the catalog? Per-kind cases are the discoverability-maximizing route but grow the catalog by four-plus cases now and one per future kind forever; the catalog's `rawValue`s are append-only persistence keys, so kind-per-case names become permanent.
- **What happens to the direction when a kind is chosen?** A typed pane still has to land somewhere in the split tree. Does it inherit a fixed default direction, use the last-used split direction, always split one particular way, or does the picker ask for both kind and direction? (The CLI sidesteps this: `pane split` already carries an explicit `-h`/`-v` flag.)
- **Should the menu reflect singleton-ness?** `docs/pane-kinds.md` §5 gives `PaneContentKind` a per-kind singleton-per-scope flag concept whose enforcement it assigns to the create path. A menu can do something the CLI error contract cannot: disable (or checkmark) a kind that is already open. Whether it should is part of the shape decision.

## Consistency with the CLI (#0315's directive binds here too)

#0315's user directive (2026-08-09) is that omitting the kind means Terminal, so no existing caller changes behavior. The menu equivalent of that rule: **the four existing split items keep producing terminal panes, unchanged** — no added prompt, no changed chord, no behavioral difference for the common case. Whatever affordance this issue adds is additive next to them, exactly as `--view` is additive next to bare `pane split`.

Vocabulary should also match: the branch's `PaneContentKind.displayName` values ("Git Status", "Process Status", "LM Studio Dashboard", "System Metrics") are the natural menu labels, keeping the GUI names, the CLI's kebab-case identifiers, and the model's raw values as one set of names per `docs/pane-kinds.md` §5's one-string decision rather than inventing a fourth spelling.

## Discoverability and the #0329 test gate

Adding `ShortcutAction` cases makes the new commands appear in the Command Palette and Settings ▸ Shortcuts automatically — a real argument for that route. But #0329 (resolved) landed `ShortcutDocsSyncTests`, which pins every documented chord — the in-app Help catalog (`BattyKit/Sources/BattyKit/Help/05-shortcuts.md`) and `docs/shortcuts.md` — to `ShortcutAction.defaultBinding`, including completeness checks. **Any new catalog case must update `docs/shortcuts.md` and the Help catalog in the same change or the pre-commit gate fails.** That is working as intended, but it is scope this issue carries if the per-kind-action route is chosen.

## Does #0301's design-first gate apply?

Judged: **no, with one sequencing caveat.** The gate (per #0301) covers "visual designs for each new view" — what a Git Status pane *looks like* — and #0315 already records that it does not extend to the CLI verb, only to the views. A menu affordance is the same category as the CLI verb: a creation surface, not a view design. Its own design questions (the shapes above) are interaction/menu-structure decisions of the kind this tracker settles in the issue itself with the user, not drafted-visual-design work.

The caveat: unlike the CLI (an agent-facing surface), a menu is user-discoverable. If this ships before any real view does, the menu would advertise "Git Status" and produce the provisional placeholder the `issue/0315` branch renders for non-terminal kinds. Whether that is acceptable (it makes the plumbing demoable) or whether this issue should sequence after the first approved view (#0304 is the likely first) is a scheduling decision to make with the user, not a reason to import the visual-design gate wholesale.

## Resolution notes

> 🟡 In progress — implementer round 1 complete, awaiting review. All four kinds are reachable from the Pane menu, the Command Palette, and the keyboard; no CLI/model changes were needed since `PaneContentKind`/`SplitTree.splitPane(id:direction:kind:...)` already existed (#0315).

The design-question survey above (posed 2026-08-09) is answered by two rounds of direction from the user during this implementation, superseding the "settle it yourself" latitude the issue originally left open:

- **Shape:** not the plain "New Pane ▸" submenu (option 1) or the picker-overlay (option 3) — the user asked for **option 2's kind-under-each-split-item shape**, specifically as an Option-hover reveal on **Split Horizontally**/**Split Vertically** only (leaving Split Full-Height Column/Split Full-Width Row untouched).
- **Direction question:** answered directly by the shape — a kind chosen under "Split Horizontally" splits horizontally, under "Split Vertically" splits vertically. No separate direction picker.
- **Singleton/checkmark question:** left unaddressed, matching #0315's own deferral — `PaneContentKind.isSingletonPerSession` still doesn't exist.
- **Keyboard shortcuts:** the user reversed the issue's own default-inclination ("no dedicated shortcut is a fine outcome") after the first pass — explicitly asked for one letter per kind, paired plain-Cmd/Cmd-Shift like `splitHorizontal`/`splitVertical` already are. Eight new `ShortcutAction` cases were added as a result (see Fix).

**The literal Option-hover request could not ship as asked.** `NSMenuItem.isAlternate` requires the alternate item to share its primary's key equivalent plus exactly one more modifier. For `Cmd-D`/`Cmd-Shift-D` that forces `Cmd-Option-D`/`Cmd-Shift-Option-D` — already the live bindings for **Split Full-Height Column**/**Split Full-Width Row**, in the same Pane menu. Shipping the Option-alternate as specified would have put two menu rows visibly claiming the same chord the moment Option was held — precisely the collision the user's own instructions said to avoid. Per the user's own pre-approved fallback ("if Option-alternates plus submenus turn out not to compose cleanly in AppKit... fall back to always-visible submenus"), this ships as **always-visible submenus**: clicking "Split Horizontally"/"Split Vertically" now opens a submenu (Terminal first, then the four kinds) rather than splitting a terminal pane immediately. The `Cmd-D`/`Cmd-Shift-D` keyboard chords are unaffected — `BattyShortcuts`' NSEvent monitor dispatches them directly, independent of the menu's structure — only a *mouse click* on the row costs one extra click versus before.

## Fix

- **`WindowRuntime.createPane(kind:direction:contentFactory:)`** (new, `WindowRuntime.swift`) — the single production entry point every surface below calls. Splits the focused Pane in the selected Session along `direction` (default `.horizontal`), routing through `SplitTree.splitPane(id:direction:kind:...)` directly — the same call `AppStateStore.splitPane(id:...)` forwards to for the XPC/CLI path (#0303: a menu-created typed pane obeys the same create machinery as a CLI-created one). Deliberately bypasses `AppStateStore.splitPane`'s cross-window search and `AppEventWatcher` notification, matching how the existing GUI split actions already behave (no watch event today, typed or not). `contentFactory` forwards to `SplitTree.splitPane`'s own injection seam so tests can suppress a kind's real conformer.
- **Eight new `ShortcutAction` cases** (`ShortcutAction.swift`): `splitHorizontalGitStatus`/`splitVerticalGitStatus`, `splitHorizontalProcessStatus`/`splitVerticalProcessStatus`, `splitHorizontalLMStudioDashboard`/`splitVerticalLMStudioDashboard`, `splitHorizontalSystemMetrics`/`splitVerticalSystemMetrics`. Defaults: `Cmd-G`/`Cmd-Shift-G`, `Cmd-J`/`Cmd-Shift-J`, `Cmd-Y`/`Cmd-Shift-Y`, `Cmd-E`/`Cmd-Shift-E` — checked by hand against every existing catalog entry, the fixed/clipboard combos, and the macOS-reserved list before picking. No terminal-vs-non-terminal gate needed on any of them (unlike #0315's Tab-scoped commands): splitting works the same regardless of what kind the focused Pane already is.
- **All three dispatch paths updated in the same change**, per #0315's own lesson about this exact trap: `BattyCommands.swift`'s Pane menu (submenus, see below), `BattyShortcuts.swift`'s NSEvent-monitor `run(_:appStore:)` switch, and `CommandPaletteView.dispatch(_:)`. Every switch is exhaustive with no `default:` case, so the compiler — not just review — now enforces that a ninth kind or a renamed case cannot silently go missing from one of the three.
- **Menu (`BattyCommands.swift`, Pane menu):** "Split Horizontally" and "Split Vertically" became `Menu` submenus. Each lists **Terminal** first — the exact same call the item used to make directly — then Git Status, Process Status, LM Studio Dashboard, System Metrics, each carrying its own keyboard-shortcut hint. "Split Full-Height Column"/"Split Full-Width Row" are unchanged.
- **Command Palette (`CommandPaletteView.swift`):** no new ad-hoc entries needed — the existing `for action in ShortcutAction.allCases` loop in `allCommands` picks up all eight new actions automatically, each with its keyboard-shortcut hint, once `dispatch(_:)` handles them.
- **No CLI, wire, or model changes.** `PaneContentKind`, `PaneRuntime.kind`, and `SplitTree.splitPane(id:direction:kind:...)` all already existed from #0315/#0304/#0305/#0313/#0314; this issue is pure menu/shortcut/palette wiring on top of them.
- **No new parameter-entry UI.** `.gitStatus` with no explicit path resolves to the split source's cwd (`SplitTree.makePane`'s existing resolution order); `.processStatus` with no explicit pid falls into its existing "follow the split-source pane's active Tab" mode. Both already worked this way for the CLI's bare `--view git-status`/`--view process-status`; this issue changes nothing about that resolution, only how the split gets triggered.

## Gotchas

- **The Option-hover design as literally requested cannot ship** — see Resolution notes. If the user still wants a modifier-triggered reveal rather than an always-visible submenu, it would need a different chord pairing than `Cmd-D`/`Cmd-Shift-D` (or accepting the visible collision), not a retry of the same AppKit mechanism.
- **Clicking "Split Horizontally"/"Split Vertically" now costs one extra click** for the plain-terminal case (open submenu, then click Terminal) versus the single click before. The keyboard chord is unchanged. Flagging this explicitly since "zero new visual noise for someone who just wants a terminal split" was the user's own bar and this doesn't fully clear it for mouse users.
- **`G`/`J`/`Y`/`E` are a first pass**, chosen collision-free but otherwise fairly arbitrary (only `G` for Git Status has a real mnemonic). The user said explicitly these can be revisited after trying them — see `docs/shortcuts.md` §9 for the full rationale.
- **`docs/ui-features.md` was not updated.** Its eleven documented feature areas (drag-and-drop, rename, theme, layout picker, bell feed, tab chips, settings, sidebar, fuzzy finders, modals) are each backed by a dedicated UI-test suite (`[0159]`–`[0169]`); this issue doesn't add a new UI-test suite or fall inside an existing one, so there was no existing section to extend. `docs/shortcuts.md` and the Help catalog carry the actual documentation for what changed instead.
- **Not launched/visually verified** — see Verification.
