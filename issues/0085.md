### Customizing shortcuts

- Open **Settings → Shortcuts** (`Cmd-,`).
- Click a recorder, press the new combo. Press `Esc` to cancel.
- Each row has a Reset button; the pane bottom has Reset All.
- Warnings appear when two actions share the same combo, or when the combo matches a macOS-reserved one (`Cmd-Q`, `Cmd-H`, `Cmd-M`, `Cmd-Tab`, `Cmd-,`). Reserved combos still save with the warning visible.
- Customizations persist across launches.

### Fixed (non-customizable) shortcuts

`Cmd-1` through `Cmd-9` (tab selection) and `Cmd-Option-1` through `Cmd-Option-9` (session selection) are positional and intentionally not customizable. `Cmd-C` / `Cmd-V` follow the system clipboard convention.

### Why some shortcuts work everywhere

Batty's shortcuts fire **regardless of which view has keyboard focus** — the terminal, the sidebar, the tab strip, or a popover. They go through an app-level event monitor rather than the menu bar's standard handling. This means you can press `Cmd-N` from inside a terminal session and it creates a new session, not sending Cmd-N to the shell.

### When Help can't override

A handful of macOS system shortcuts can't be overridden by any app, including Batty: Mission Control, Spotlight, screenshot capture, and screen-recording trigger combinations. These behave normally regardless of Batty's settings.

## Root cause

`Batty/Help/05-shortcuts.md` shipped as a one-line stub ("Documentation coming soon — see issue #0085.") after the Help-window bootstrap in `#0080`. Users opening Help and clicking Keyboard Shortcuts saw nothing useful.

## Fix

Replaced the stub with the full user-facing reference per this issue's spec. The four default-binding tables (Sessions / Panes / Tabs / Other) are sourced from `ShortcutAction.defaultBinding` in `BattyKit/Sources/BattyKit/Shortcuts/ShortcutAction.swift`; the reserved-combo list is sourced from `ShortcutsStore.reservedShortcuts`. Both match the spec exactly. Display names follow the source ("Show Previous Tab", "Focus Pane Above/Below") so the Help text matches the labels users see in Settings → Shortcuts. The "why shortcuts work everywhere" section translates the NSEvent local-monitor architecture into plain user terms without naming internal types. Cross-links use filenames so the page renders correctly inside the Help window and on GitHub.

## Gotchas

- The spec table used "Focus Pane Up / Down" but `ShortcutAction.displayName` says "Focus Pane Above / Below". Help follows the source so users see the same label in Help and in Settings.
- Similarly, the spec said "Previous Tab / Next Tab"; the source says "Show Previous Tab / Show Next Tab". Help follows the source.
- `Cmd-,`, `Cmd-?`, `Cmd-Q`, `Cmd-C`, `Cmd-V` are not in `ShortcutAction.allCases` — they're handled by SwiftUI's Settings scene, the Help menu, the system, and libghostty/`PasteDispatcher` respectively. The Help page lists them under "Other" because users still need to see them, even though they aren't in the Shortcuts pane.
