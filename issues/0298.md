## Description

When a source emits the same notification repeatedly while the previous one is still unread, every repeat becomes a fresh Bell Feed entry and a fresh system notification. The user's motivating examples are agent/TUI messages that repeat verbatim — "Claude Code is waiting for your input", "build failed". In the user's words:

> When there is a redundant new notification for a previous and still unread notification we can collapse it to the latest one. The example of "Claude Code is waiting for your input" is a great one to collapse. Same for "build failed" and others like it.

So: when a new notification is redundant with an earlier one that is still unread, collapse them into the latest rather than accumulating duplicates.

This is the **filtering follow-up that #0297 deliberately deferred**. #0297 is instrumentation only — it collects the most recent 1000 bell/notification decision records in memory and exposes Copy / Save to File / Clear in Settings → Advanced → Diagnostics. **That export is the intended way to validate any collapse rule against real traffic before committing to it.** Design the rule from the exported data, not from intuition.

**What happens today (verified against source):**

- `BellFeedStore.record(_:)` (`BattyKit/Sources/BattyKit/Runtime/BellFeedStore.swift:76`) unconditionally inserts every entry at index 0 — no dedupe, no coalescing, cap 200.
- Every repeat calls `postNotification(for:at:)` (`AppStateStore.swift:1155`) → `BellNotifier.post(for:...)` (`BellNotifier.swift:65`). `shouldPost` (`BellNotifier.swift:90`) returns `true` whenever Batty is not frontmost, so a backgrounded user gets a **banner per repeat** — this is very likely the actual irritation, more than the duplicate feed rows. Each request uses `entry.id.uuidString` as its `UNNotificationRequest` identifier, so Notification Center never replaces an earlier banner. (Reusing the collapsed entry's identifier on re-post is a cheap mechanism worth considering: UNUserNotificationCenter replaces a delivered notification when a new request reuses its identifier.)
- `BellFeedRow` (`Views/BellFeedView.swift:134`) shows no repeat count; the unseen badge (`BellFeedStore.unseenCount`) counts entries, so N repeats inflate the badge by N.

## The open design question: what counts as "redundant"

The user has not specified the matching rule, and the choice materially changes behavior. Options, with trade-offs:

1. **Exact message text within the same Terminal Session** (in practice: same `tabID`, since a Tab owns exactly one Terminal Session — see scope note below). Safest and most predictable; collapses "Claude Code is waiting for your input" repeating in one pane. Misses near-identical variants (a message carrying a changing counter, timestamp, or path).
2. **Same source regardless of text** (any new entry from a tab that already has an unread entry). Catches variants, but would collapse a genuine "build failed" arriving after a "waiting for input" from the same pane — different information, wrongly merged. Probably too aggressive.
3. **Normalised text** (trim, case-fold, strip trailing digits/paths) within a session — a middle ground; more powerful and more surprising.

**Orchestrator's recommendation (not a settled decision — user to confirm):** start with option 1, exact message text scoped to the Terminal Session, precisely because it is the variant #0297's export can confirm or refute against real data; treat looser matching as a later refinement once real patterns are visible.

> **Decision (2026-08-04, user):** the redundancy rule is **deliberately left unspecified for now** — the user was asked to choose among the options above and chose to decide after seeing real traffic from #0297's Settings → Advanced → Diagnostics export (merged to `main` as commit `9efac11`). The absence of a matching rule here is a recorded decision, not an omission. **Implementation is blocked on that data**: collect a representative sample via the export, evaluate the candidate rules against it, then bring the choice back to the user. Status stays `open`; the option analysis above is kept as the menu to choose from.
>
> **Superseded 2026-08-07 (user, having seen the export analysis below).** Three decisions, now settled:
>
> 1. **Matching rule: option 1 — exact message text, scoped to the same Tab, unread entries only.** Key on the message **text/digest**, never on `tabLabel` — finding 4 shows Claude Code animates a spinner glyph in the Tab title, so the same 12 identical messages carried three different `tabLabelDigest` values and label matching would have collapsed nothing. Scope to `tabID`, not text-globally — finding 3 shows digest `a9416c86e44502db` appeared in two unrelated Sessions ("Pi Trouble" ttys002 and "Batty" ttys000) and a text-only rule would have wrongly merged them.
> 2. **Time bound: 30 minutes.** Beyond that, post a fresh entry instead of collapsing. Rationale: finding 5's real case is a 3h48m gap in Tab `1D133C49` where an unbounded rule folds a 04:38 event into a 00:50 row, so the feed row's timestamp silently jumps four hours and the earlier event leaves no trace. The user accepted one extra banner across ~6 hours of traffic to avoid that.
> 3. **Bare BEL bells (`message: nil`) DO collapse** — all unread message-less bells from one Tab become one row with the latest timestamp. This is now an explicit decision, not a side effect of `nil == nil`. The user's reasoning: a bare bell carries no information beyond "it rang again", and the flooding case (`for i in {1..20}; do printf '\a'; done` producing 20 rows) is what this issue exists to fix. The sample contains exactly one bare-BEL record, so this path was effectively untested by data and got its own dedicated unit test coverage (`BellFeedCollapseTests.twoBareBellsSameTab_collapse`, `.bareBellsFromDifferentTabs_doNotCollapse`, `.twentyRapidBareBellsCollapseToOneEntryWithRepeatCount20`) instead of being validated against traffic.
>
> "Collapse it to the latest one" means: the existing entry's `timestamp` refreshes to the repeat's, it moves to the top of the newest-first feed, and a new `repeatCount` field (starts at 1, incremented on each collapse) is shown in the row as `×N` — preserving the "it rang N times" information an unbounded merge would otherwise destroy. `seen`, `id`, and `summary` are left untouched by a collapse.

A wrinkle with option 1: **BEL entries carry `message: nil`** (`AppStateStore.recordBellTick`, `AppStateStore.swift:629` constructs entries with `message: nil`). Under exact-text matching, every BEL from the same tab is "identical", so all unread BEL rings from one tab collapse into one row. That is arguably exactly right (a bell carries no information beyond "it rang again"), but it should be a stated decision, not an accident. OSC 9/777 entries carry `location.tab.lastBellMessage`; CLI `batty notify` entries carry `title\nbody` via `formatNotifyMessage`.

## Behavior to specify (verified anchors, decisions left open)

**"Still unread" has a precise existing definition.** `BellFeedEntry.seen` (`BellFeedStore.swift:23`) is the authoritative flag. It is set at creation when the source tab is focused in the key window (`effectivelySeen` in `recordBellTick` / `recordDesktopNotification` / `recordCLINotification`, `AppStateStore.swift:627/661/723`), and cleared to seen by exactly three paths:

- `AppStateStore.markBellSeen(id:)` (`AppStateStore.swift:849`) — feed-row click or system-notification tap.
- `AppStateStore.markAllBellsSeen()` (`AppStateStore.swift:856`) — the feed's Clear All button.
- `WindowRuntime.markActiveTabSeen()` (`WindowRuntime.swift:476`) — activating a tab in the key window marks all of that tab's unseen entries seen.

That last path naturally bounds any unread-based collapse: the moment the user visits the tab, its entries become seen and the next notification starts a fresh entry. "Unread" as the collapse criterion therefore already means "the user has not visited the source or acknowledged the entry", which matches the user's intuition.

**What "collapse" means concretely — each of these needs a decision:**

- Does the existing entry move to the top with a refreshed timestamp (feed is strictly newest-first; `BellFeedStore.init` sorts by timestamp descending), or stay in place with its original time? Moving to top with refreshed timestamp seems to match "collapse it to the latest one".
- Is a repeat count shown ("×3")? `BellFeedRow` has no such affordance today; adding one means a count field on `BellFeedEntry` (which is `Codable` — watch persistence/serialization compatibility if that ever matters) or a computed grouping in the view.
- Does the unseen badge count 1 or N for a collapsed group? Today `unseenCount` counts entries, so collapsing to one entry means the badge shows 1. Probably correct — the badge should measure "things needing attention", not "times the shell nagged".
- Does the **system notification** re-post on each repeat, get suppressed after the first unread one, or replace the delivered banner in place (identifier reuse, above)? Suppress-or-replace is likely the user's real want; a decision either way should be recorded.
- What happens to `summary` (the async AI summary, `BellFeedStore.updateSummary`) and `scheduleSummarization` on a collapsed repeat — skip re-summarizing an identical message?
- Interaction with `TabRuntime.recordBellTickIfNeeded()` delta-dedupe and `unseenBellCount` propagation (`propagateUnseenForced` / `decrementUnseen`): if repeats collapse into one entry but `unseenBellCount` still increments per repeat, the tab/pane/session dot counters drift from the feed. `markActiveTabSeen` already handles residual counter drift (`WindowRuntime.swift:487-491`), but the design should keep counters and entries consistent by construction.

**Scope.** The Bell Feed is global but every entry carries `windowID` / `sessionID` / `paneID` / `tabID` / `surfaceID`. The natural collapse scope is the Terminal Session, which in entry terms is `tabID` (one Tab owns exactly one Terminal Session; `surfaceID` is unreliable — the BEL and OSC record paths default it to a throwaway `UUID()`, flagged vestigial in #0281). Collapsing across tabs ("build failed" in two different panes) would merge genuinely distinct events — don't.

**System entries (#0290) must be excluded.** The footprint warning shares the feed via the `BellFeedEntry.systemID` sentinel (`BellFeedStore.swift:34`) and has its own step-based suppression in `FootprintMonitor` plus its own posting rule (`BellNotifier.postFootprintWarning` fires only when Batty isn't frontmost). Note that under a tabID-scoped rule, all system entries share `tabID == systemID` — a same-source rule would wrongly fold distinct footprint steps together, and even exact-text matching could interact with the step logic. The collapse rule should skip `systemID` entries outright.

**Timing (#0288).** Occluded Tabs deliver bells via the 500 ms `OccludedSurfaceTicker` poll, and `recordBellTick` loops `for _ in 0..<delta` — several repeats can arrive in one batched call rather than evenly spaced. A time-window-based collapse rule would therefore behave differently for background Tabs than foreground ones. The purely unread-based rule the user described is immune to this; if a time bound is added (collapse only within N seconds), the batching skew needs to be accounted for.

**Time bound — open question.** The user described a purely unread-based rule ("previous and still unread"), with no time component. A time bound adds complexity and the #0288 skew problem; the recommendation is to start without one and let #0297's data show whether stale-unread collapses (a repeat hours later folding into a morning entry) are actually confusing in practice.

The log does not record mark-seen events directly — see the instrumentation gap below.
3. **`tabID` scoping is confirmed against real data, and global text matching is refuted.** Digest `a9416c86e44502db` appears in two *different* Sessions — "Pi Trouble" (ttys002, pid 96078) and "Batty" (ttys000, pid 90781). Under a no-time-bound rule the second folds into an entry from before midnight. This is exactly the scenario "Time bound — open question" asked about, and the data confirms it is reachable rather than hypothetical. Still a judgment call: it is one banner saved versus a feed row whose timestamp jumps forward by four hours.
6. **The Description's assumption about which gate fires is wrong for this traffic.** `battyActive=true` on **all 13** records, yet 10 were submitted. 7. **The `nil`-message BEL sub-rule is untested.** Exactly one BEL record (`19D86E95`, `messageDigest=nil`) — enough to confirm the wrinkle at line 38 is reachable, nowhere near enough to validate collapsing all message-less bells from a Tab into one row.

**Instrumentation gaps this export revealed (candidates for a #0297 follow-up, not decided here):**

- **No mark-seen events.** The log records `seenAtCreation` per decision but never records when an entry is later marked seen (`markBellSeen` / `markAllBellsSeen` / `markActiveTabSeen`). Finding 2's reconstruction has to infer those transitions, so the collapse simulation is an estimate, not a replay. Recording seen-transitions would make the rule verifiable offline against a real trace.
- **Export order is not `bellAt` order.** Records are newest-first *except* `EEFB81DF` (04:38:33Z), which sits between the 05:50:11Z and 05:45:30Z rows — the history is ordered by append time and the two disagree. Any offline analysis must sort by `bellAt` explicitly rather than trusting file order. Worth a look at whether append-vs-`bellAt` skew is itself a bug.

**Sample-size caveat.** 13 records out of a 1000 capacity, ~6 hours, one dominant digest, two real sources. Sufficient to refute the time-window variant (finding 1), confirm `tabID` scoping (3) and `messageDigest` keying (4), and correct the frontmost assumption (6). Not sufficient to tune option 3's normalisation, to validate the BEL sub-rule (7), or to judge how often stale-unread collapses (5) would annoy in daily use. A longer capture across more varied sources would strengthen 5 and 7.

**Where this leaves the recommendation.** The data supports the original recommendation — option 1, exact message text scoped to `tabID`, unread-based, no time bound — and adds evidence against the time-bound alternative. The two calls still genuinely open for the user: whether a stale unread entry (finding 5) should still absorb a repeat hours later, and whether message-less BELs collapse the same way (finding 7).

## Root cause

`BellFeedStore.record(_:)` unconditionally inserted every entry at index 0 — no dedupe, no coalescing. Every entry, including an exact repeat of a still-unread one, became its own feed row and its own call into `postNotification` → `BellNotifier.post`, so a flooding source (a bare-BEL loop, or an agent repeating "waiting for your input") produced one banner per repeat with no way for the feed or Notification Center to show "this happened N times" instead of N rows.

## Fix

- **`BellFeedEntry.repeatCount: Int`** (default 1) — how many raw occurrences an entry represents. Manual `Codable` (`init(from:)`) defaults a missing key to 1 so decoding an older-shaped payload doesn't throw (`BellFeedStore.swift`).
- **`BellFeedEntry.firstOccurrenceAt: Date`** (defaults to `timestamp` at construction) — the collapse-window anchor, set once and never touched by a collapse. `timestamp` keeps refreshing to the latest occurrence (so the row still shows "when did this most recently happen"), but the 30-minute bound is measured from this fixed point. **Added in review round 2** after the reviewer traced a bug in the first cut, which anchored against the entry's own `timestamp` — see below.
- **`BellFeedStore.recordOrCollapse(_:collapseWindow:)`** — the matching rule itself: same `tabID`, `candidate.message == entry.message` (relies on `nil == nil` for bare BEL — no special-casing needed), candidate still `!seen`, and `abs(new.timestamp - candidate.firstOccurrenceAt) <= collapseWindow` (`BellFeedStore.collapseWindow = 30 * 60`, inclusive at the boundary). `entry.tabID == BellFeedEntry.systemID` (the #0290 footprint warning) skips the whole function and always records — a same-`tabID` rule would otherwise fold distinct footprint steps together. On a match: the existing entry is removed from its current index, `repeatCount` incremented, `timestamp` set to the repeat's own (`firstOccurrenceAt` untouched), and reinserted at index 0 (moves to the top, newest-first).
  - **Round-2 fix: the anchor must be fixed, not sliding.** The first cut measured the bound against `candidate.timestamp`, which is refreshed on every collapse — so a chain of individually-compliant gaps could walk the row's displayed time arbitrarily far from the event that actually opened it, exactly the "timestamp silently jumps forward" failure the bound exists to prevent. Reviewer's repro from the real export: Tab `8E75F975`'s four-event chain `05:58:46 → 06:20:00 → 06:23:32 → 06:44:38` has every consecutive gap under 30 minutes (21m14s, 3m32s, 21m6s) but spans **45m52s** end to end — a sliding anchor collapses all four into one row, silently placing the feed's displayed time 45+ minutes past the event that opened it. Anchoring to `firstOccurrenceAt` (fixed at 05:58:46) instead means the fourth event, 45m52s past that anchor, correctly opens a new row instead of extending the chain — see the Verification section's replay for the corrected count.
- **`AppStateStore.recordBellTick` / `recordDesktopNotification` / `recordCLINotification`** — each now calls `bellFeed.recordOrCollapse(entry)` instead of `bellFeed.record(entry)` whenever the new occurrence is not itself effectively seen (a seen-at-creation bell, i.e. the tab is currently focused, always gets its own entry — any earlier unread entry for that tab would already have been cleared by `markActiveTabSeen`, so there is nothing sound to collapse into). On `.recorded`, behavior is unchanged (`postNotification` + `scheduleSummarization`). On `.collapsed`, neither runs — instead `recordCollapsedNotificationDecision` logs the #0297 decision with a forced `outcome=suppressed:collapsedIntoUnread` and never calls `notifier.post`, which is the actual mechanism that stops the repeat banner.
- **`BellDecisionRecord.SuppressionReason.collapsedIntoUnread`** — new case, so a collapsed repeat still appears in the #0297 export instead of silently disappearing from the log. `AppStateStore.makeBellDecisionRecord` grew a `forcedOutcome` parameter so the collapsed path can report this without going through (or misrepresenting the result of) the notifier gates it never reached.
- **`WindowRuntime.decrementUnseen(for:)`** — now decrements the tab/pane/session sidebar counters by `entry.repeatCount`, not a flat 1. A collapsed entry represents `repeatCount` raw occurrences, each of which called `propagateUnseenForced` once when it arrived; clearing the single row that absorbed all of them (via `markBellSeen`, a feed-row click or notification tap) must release all of them or the numeric sidebar badges (`SessionSidebarView`) stay permanently inflated. `markActiveTabSeen`'s own residual-reset (`WindowRuntime.swift:487-491`) already covered the tab-visit path; this makes every mark-seen path consistent by construction instead of relying on that one safety net.
- **`BellFeedRow`** (`BellFeedView.swift`) — shows `×N` next to the path label when `repeatCount > 1`.

## Gotchas

- **The append-vs-`bellAt` ordering skew (flagged in the export analysis above) is real, not benign, and not fixed here.** Record `EEFB81DF` (Tab `1D133C49`, `bellAt=2026-08-05T04:38:33Z`) sits between the 05:50:11Z and 05:45:30Z rows in the export — roughly a 67–72 minute append-order skew, two orders of magnitude past the sub-second/500ms skew #0288 already documents for the occluded-poll path. Investigated the plausible mechanism: OSC 9/777 capture is `.onChange(of: tab.terminal.lastDesktopNotificationAt)`-driven (`PaneView.swift:138`), which only fires on a SwiftUI update pass for that view. I ruled out "the view isn't mounted while its Session isn't selected" — `SessionDetailView.swift` renders `ForEach(windowRuntime.sessions)` and keeps every Session's `SplitContainerView` mounted simultaneously in one `ZStack`, toggling only `opacity`/`allowsHitTesting` on selection, so a background Session's `PaneView` (and its `onChange` modifiers) stay live in the tree regardless of which Session is selected. I also ruled out async/Task reordering — the `onChange` closure calls `AppStateStore.recordDesktopNotification` synchronously. That leaves the mechanism underdetermined from static reading alone: something delays the SwiftUI update pass for a non-selected Session's Tab well past what `OccludedSurfaceTicker`'s 500ms libghostty-queue drain would suggest, and settling it needs either a live repro or the mark-seen/finer-timestamp instrumentation this issue's export already flags as missing. **Recommend filing this as its own follow-up issue** rather than folding a speculative fix into this one, per this issue's instruction not to expand scope on the instrumentation gaps.
- **The mark-seen instrumentation gap (also flagged above) means the replayed banner count is a reconstruction, not a verified replay** — same caveat finding 2 already carried. A future #0297 follow-up that logs `markBellSeen`/`markAllBellsSeen`/`markActiveTabSeen` events would let this rule be validated against a true trace instead of an inferred one.
- **Notification banners are not updated in place on a collapse.** The design suppresses the *repeat's* system notification entirely rather than replacing the already-delivered banner's text with a "×2" count — simpler, and sufficient for the stated goal (stop the banner-per-repeat flood), but a user staring at a stale single-occurrence banner while the feed row now says "×5" is a real, if minor, gap. Not addressed here; worth a line in a future issue if it turns out to matter in practice.
- **`BellFeedStore.record`'s 200-entry cap eviction leaks unseen state — pre-existing, but this issue amplifies the magnitude.** `record` (`:141-147`) evicts past `cap` with `removeLast` and never decrements `unseenCount`/the tab-pane-session counters for the evicted entry. That leak existed before #0298 (an evicted unread entry always leaked exactly 1), but a collapsed entry can now carry `repeatCount` up to however many raw occurrences it absorbed, so an evicted collapsed row leaks up to `repeatCount`, not 1. Net effect is likely favorable regardless — collapsing means fewer rows reach the cap in the first place, so cap pressure (and therefore how often this leak fires at all) goes down even though any single leak that does happen is now bigger. Not fixed here; it's a `record`-level bug orthogonal to the collapse rule, not something this issue introduced.
- **The sidebar's numeric badges and the feed row's `×N` count the same thing differently, and that divergence is deliberate and unresolved.** `SessionSidebarView.swift:211`/`:291` show raw occurrence counts (`unseenBellCount`, unaffected by collapsing — a 20-bell flood still shows sidebar **20**), while the Bell Feed shows one row at `×20`. That's internally consistent with each element's own tooltip wording ("N unseen bell event(s)" vs. "repeated N times"), but the Description's original framing (this issue, above: "the badge should measure things needing attention, not times the shell nagged") argued for the *opposite* on the sidebar count specifically. This issue did not change `unseenBellCount`'s semantics — only how many `decrementUnseen` releases per mark-seen (see Fix) — so the sidebar still counts occurrences, not distinct still-open notifications. Left as-is; flagging so a future reader doesn't assume the two numbers are supposed to match.
- Could not verify the `×N` badge or the collapsed-row-moves-to-top behavior by eye in the running app — this was implemented and unit-tested only, per the "never restart/relaunch the user's running Batty" constraint.
