## Description

**This is the single remaining blocker on ~510 MB of Batty's memory footprint, and it comes first — everything else is set aside until it lands.**

Batty's memory problem (#0285) is already fixed upstream. Ghostty commit **`c4e16970a803b170e352432424f44192cb59f3ac`** — *"renderer: release GPU resources for hidden surfaces (macOS)"*, 2026-08-25 — does exactly what #0293 asked for and #0389 set out to build by hand. The fork's pinned `Ghostty.ref` is `35e1a0160c4f6797e1bb1ef8e7a2b8c6b114ab58` (2026-07-09), **47 days and 993 commits behind it**, which is why `Renderer.setVisible` at the pin only starts and stops the CVDisplayLink and never touches the swap chain — precisely what #0388 measured (21 IOSurfaces = 7 layers × 3, unmoved by occlusion).

#0389 bumped the ref on the user's fork and **the xcframework builds**: branch `issue-0389-ref-bump` in `~/Developer/brennanMKE/libghostty-spm`, four of ten patches needed context-only `-v2` variants for Zig 0.16 API moves, selected via upstream API markers in `Script/apply-patches.sh`. `Script/verify-xcframework.sh` passes.

**But the fork's own Swift no longer compiles**, because upstream rewrote the clipboard protocol somewhere in those 993 commits. `Sources/GhosttyTerminal/Controller/TerminalController+Callbacks.swift` is written against the old C shape and fails to build against the new header. That break — not anything to do with occlusion, rendering, or memory — is the sole thing standing between Batty and the fix.

**Two decisions the user has already made, recorded here so nobody relitigates them:**

1. **This work comes first.** The rest of the issue queue waits until this lands.
2. **If the pin moves, this port ships as part of the PR to `Lakr233/libghostty-spm`.** It is not an optional extra; a wrapper that cannot compile against the ref it pins is not a submittable change.

## The API delta — verified against both trees

Read from `/tmp/ghostty-read` (a read-only Ghostty clone) with `git show <ref>:include/ghostty.h`. Old = `35e1a01`, new = `c4e16970a`.

### The surface entry point: one function became two, and the first changed shape

Old (`include/ghostty.h:1155`) — a bare NUL-terminated C string plus a trailing `confirmed` flag:

```c
GHOSTTY_API void ghostty_surface_complete_clipboard_request(ghostty_surface_t,
                                                               const char*,
                                                               void*,
                                                               bool);
```

New (`include/ghostty.h:1222`, `:1226`) — a struct payload, and a separate deny leg:

```c
GHOSTTY_API void ghostty_surface_complete_clipboard_request(
    ghostty_surface_t,
    const ghostty_clipboard_complete_s*,
    void*);
GHOSTTY_API void ghostty_surface_deny_clipboard_request(ghostty_surface_t,
                                                           void*);
```

`src/apprt/embedded.zig:2263-2272` documents the new function: *"Deny a clipboard read request started via the read callback, e.g. because the user rejected a confirmation prompt. Request types whose protocol expects an answer have their denial reply written to the pty. The request pointer is invalidated."*

### New structs

```c
// The payload for completing a clipboard read request.
typedef struct {
  const ghostty_clipboard_content_s *contents;
  size_t contents_len;
  const char *const *available;
  size_t available_len;
  bool confirmed;
  bool remember;
} ghostty_clipboard_complete_s;

// The payload of a clipboard read confirmation request: the would-be
// completion contents plus the information shown in the permission prompt.
typedef struct {
  const ghostty_clipboard_content_s *contents;
  size_t contents_len;
  const char *const *available;
  size_t available_len;
  const char *name;
  bool can_remember;
} ghostty_clipboard_confirm_s;
```

### Changed struct — this one is a silent correctness hazard

`ghostty_clipboard_content_s` gained a length and lost its NUL-termination guarantee. The header now says: *"One representation of clipboard contents. The data is binary-safe with an explicit length; it is not necessarily null-terminated."*

```c
// old                          // new
typedef struct {                typedef struct {
  const char *mime;               const char *mime;
  const char *data;               const char *data;
} …;                              size_t len;
                                } …;
```

This affects the **write** path too, which the earlier round's notes did not mention. `TerminalCallbacks.writeClipboard` does `String(cString: data)` (`TerminalController+Callbacks.swift:69`) — reading past the end of a non-terminated buffer. The write callback's *signature* is unchanged, so this will compile clean and be wrong at runtime.

### Changed enums

```c
ghostty_clipboard_e        + GHOSTTY_CLIPBOARD_PRIMARY
ghostty_clipboard_request_e + GHOSTTY_CLIPBOARD_REQUEST_KITTY_READ
                            + GHOSTTY_CLIPBOARD_REQUEST_KITTY_WRITE
                            + GHOSTTY_CLIPBOARD_REQUEST_LIST
```

New enum:

```c
// apprt.ClipboardReadResult
typedef enum {
  GHOSTTY_CLIPBOARD_READ_STARTED,
  GHOSTTY_CLIPBOARD_READ_UNAVAILABLE,
  GHOSTTY_CLIPBOARD_READ_UNSUPPORTED,
} ghostty_clipboard_read_result_e;
```

### Changed runtime callbacks

```c
// OLD (:1001-1008)
typedef bool (*ghostty_runtime_read_clipboard_cb)(void*,
                                                  ghostty_clipboard_e,
                                                  void*);
typedef void (*ghostty_runtime_confirm_read_clipboard_cb)(
    void*,
    const char*,
    void*,
    ghostty_clipboard_request_e);

// NEW (:1063-1074)
typedef ghostty_clipboard_read_result_e (*ghostty_runtime_read_clipboard_cb)(
    void*,
    ghostty_clipboard_e,
    void*,
    const char* const*,   // requested mime types
    size_t,
    bool);                // also list all available mime types
typedef void (*ghostty_runtime_confirm_read_clipboard_cb)(
    void*,
    const ghostty_clipboard_confirm_s*,
    void*,
    ghostty_clipboard_request_e);
```

`ghostty_runtime_write_clipboard_cb` and `ghostty_runtime_config_s`'s field list are **unchanged**.

### Correction: "async" is not the new part

The prior characterisation of this change as *"a synchronous, single-string clipboard read replaced by an async, multi-mime-type design with explicit permission confirmation"* is **half right, and the wrong half is load-bearing** — an implementer who believes the read path becomes async for the first time will redesign machinery that already exists.

The old callback was **already deferred**. `src/apprt/embedded.zig:57-59` at `35e1a01`: *"Returns true if the clipboard request was started and complete_clipboard_request may be called with the given state pointer."* Same opaque state pointer, same deferred completion. And confirmation already existed — `confirm_read_clipboard_cb` plus the trailing `confirmed` bool on the completion.

What is **actually** new:

- **Multi-mime, binary-safe payloads.** A single `const char*` became an array of `{mime, data, len}` plus a list of available types, and the read callback is now *told which representations the caller wants*. `embedded.zig:62-68`: *"The MIME types are exactly the representations the caller wants served; the embedder should read only those. Text-like types are always requested as the canonical `text/plain`."*
- **A tri-state result and a mandatory answer.** `bool` → `STARTED`/`UNAVAILABLE`/`UNSUPPORTED`, and *"in which case complete_clipboard_request or deny_clipboard_request must eventually be called with the given state pointer"*. Exactly one of the two legs must run. The old API had no deny leg at all.
- **A persistent-permission concept.** `remember` on completion, `can_remember` on the confirm payload, and `name` — a human-readable identifier for the permission prompt. **This is the genuinely new product surface**, and it is what makes this issue more than a signature update.
- **Kitty clipboard protocol (OSC 5522) request types**, which is what motivated the rewrite upstream.

## What the wrapper supports today

The failing file is `Sources/GhosttyTerminal/Controller/TerminalController+Callbacks.swift` in the fork (branch `issue-0389-ref-bump`). Its current shape:

- **`writeClipboard`** (`:59-78`) — takes `clipboard: ghostty_clipboard_e` and `contents: UnsafePointer<ghostty_clipboard_content_s>?`, reads only `contents?.pointee` (the **first** element, ignoring `contentsLen`), and does `String(cString: data)`.
- **`readClipboard`** (`:80-111`) — takes `(userdata, clipboard: ghostty_clipboard_e, opaquePtr: UnsafeMutableRawPointer?) -> Bool`. Reads `NSPasteboard.general.string(forType: .string)` (or `UIPasteboard.general.string`), logs `clipboard paste read empty` or `clipboard paste read bytes=… lines=…`, and calls `ghostty_surface_complete_clipboard_request(surface, cString, opaquePtr, false)` (`:107`).
- **`confirmReadClipboard`** (`:113-135`) — takes `string: UnsafePointer<CChar>?` and `request: ghostty_clipboard_request_e` (`:115`, `:117`), logs `clipboard paste confirm request=… bytes=… lines=…`, and calls the same completion with `true` (`:132`).

*(Correction to the dispatching notes: `clipboard:`/`contents:` at `:61-62` are the **write** callback's parameters, not the read callback's. The read callback never sees a `ghostty_clipboard_content_s`.)*

So the wrapper **does** already model a confirmation concept — the `false`/`true` trailing argument, and a distinct confirm callback — but it is a single synchronous-looking call into one completion function, with **no deny path and no notion of remembering a decision**. What survives the port:

| Survives | Must be rewritten |
|---|---|
| The bridge/userdata plumbing (`Unmanaged<TerminalCallbackBridge>`, `bridge.rawSurface`) | Both callback signatures and their C shims |
| The `NSPasteboard`/`UIPasteboard` reads themselves | Wrapping the read in a `ghostty_clipboard_complete_s` (contents array + lifetime) |
| The `TerminalDebugLog` breadcrumbs (worth keeping — they were the diagnostic for large-paste bugs) | The `false`/`true` confirmed flag → struct field, plus the new `remember` flag |
| `TerminalController+Config.swift`'s field assignments as a *pattern* | Mime-type negotiation: honour the requested list, optionally report `available` |
| | A deny path — there is nothing to port; `ghostty_surface_deny_clipboard_request` has no predecessor |
| | `writeClipboard` must iterate `contentsLen` and honour `content.len` instead of `String(cString:)` |

## Scope: which of the nine clipboard files the port actually touches

Clipboard-related code appears in nine wrapper files. Grepped and classified — **only three are in scope**, which is what makes this a day rather than a week:

**In scope (touch the C API):**

- `Controller/TerminalController+Callbacks.swift` — the whole of it. Both `TerminalCallbacks` statics and the three free-function C shims (`terminalControllerWriteClipboardCallback` `:157`, `…ReadClipboardCallback` `:173`, `…ConfirmReadClipboardCallback` `:185`). This is where essentially all the work is.
- `Controller/TerminalController+Config.swift` (`:104`, `:108-110`) — assigns the three callbacks into `ghostty_runtime_config_s`. Mechanically unchanged if the shims match the new typedefs, but it will fail to typecheck until they do, so it is on the compile path.
- `Surface/TerminalSurface.swift` — **if** a deny entry point is exposed to embedders. `setOcclusion(_:)` at `:201-205` is the model for a thin 1:1 passthrough. Today the file only mentions clipboard in a doc comment (`:119`).

**Not in scope (never see the C clipboard API):**

- `InMemory/TerminalCallbackBridge.swift` — one doc comment at `:19`. Would only change if a permission UX needs a delegate hook, which is a design choice, not a compile requirement.
- `Platform/AppKit/AppTerminalView.swift` (`:154-163`), `AppTerminalView+Input.swift` (`:109-119`), `AppTerminalView+PublicInput.swift` (`:21`), `Platform/UIKit/UITerminalView+PublicInput.swift` (`:12`), `Platform/UIKit/TerminalInputAccessoryView.swift` (`:195`) — these go through named binding actions (`"copy_to_clipboard"`, `"paste_from_clipboard"`) and direct `NSPasteboard`/`UIPasteboard` access. **String-named binding actions are unaffected by the C struct rewrite.**

### The multi-platform scoping decision

The wrapper builds for **macOS, iOS, and Mac Catalyst**, and `Patches/ghostty/README.md` states patches apply to all three equally. The existing `readClipboard`/`writeClipboard` are already `#if canImport(UIKit)` / `#elseif canImport(AppKit)` forked internally.

A clipboard-permission UX has to either work on all three or be **explicitly scoped to macOS with the others stubbed** — e.g. iOS/Catalyst always-allow, or always-deny for OSC 52 reads. **This is a scoping decision for the user, not a default to fall into silently.** Note that iOS has its own system-level pasteboard permission prompt, so "always allow" there is not the same risk posture it is on macOS.

## UX decision (user, 2026-09-01) — prompt once per Session, remember, macOS only

**Decided. Implement this; do not re-open it.**

**Policy: prompt once per Session, then remember the answer for that Session.**
The first time a program in a Session asks to read the clipboard, Batty shows
a confirmation naming the requesting program (`ghostty_clipboard_confirm_s`
carries `name`). The user's answer is remembered for the rest of that Session
and applied to subsequent requests from it without prompting.

This maps directly onto the new API rather than fighting it: the upstream
`remember` / `can_remember` fields exist for exactly this shape. Pass
`remember` back on the completion when the user's choice is to be retained,
and honour `can_remember` — when upstream says a request cannot be remembered,
prompt for it regardless of any stored answer.

**Scope of "remember" is the Session**, matching how the user reasons about
this app: one Session is one working context. It is deliberately *not*
per-Pane (too chatty — a Session's Panes are one context) and *not* app-wide
(too coarse — a decision made for one project should not silently authorise
another). The stored answer lives with the `SessionRuntime` and dies with it;
it is **not persisted across launches**, so a new launch re-prompts. Nothing
in this issue writes to `UserDefaults`.

**Platform: macOS only.** The iOS and Catalyst paths get a deliberate stub
that always denies (never a silent allow, which would be strictly less safe
than today). Record the stub as a known limitation in the fork's code, and
say plainly in any upstream PR that the permission UX is macOS-only so a
maintainer is not surprised — the wrapper is multi-platform and
`Patches/ghostty/README.md` notes patches apply to all three equally.

### Why the API grew a deny leg

A terminal program asking to *read* the clipboard is an exfiltration vector
(OSC 52 and similar): the clipboard routinely holds passwords, tokens, and
private URLs, and before this change any program that could write escape
sequences could ask for them. Upstream's answer is to require the embedder to
answer every read request explicitly — complete or deny — rather than
defaulting to allow. Batty should not undo that by choosing always-allow.

### Implementation constraints that follow

- **Exactly one of complete/deny must fire for every request.** A prompt
  dismissed by a Pane closing, a Session closing, or a Window tearing down
  must still resolve to a **deny**, or the requesting program waits forever.
  This is the sharpest correctness hazard in the port — cover it with a test.
- Follow the codebase's established confirmation pattern rather than inventing
  one: `WindowRuntime.swift:46`/`:416`/`:422-437` plus
  `SessionDetailView.swift:84-95`'s `.confirmationDialog`, with
  `QuitConfirmation.swift` as the policy half.
- The prompt must name the requesting program from `ghostty_clipboard_confirm_s.name`;
  an unnamed "something wants your clipboard" prompt trains users to click
  through it.
