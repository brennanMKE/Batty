# 0437 — A newly opened Window can drop Cmd-B and misroute other key-window shortcuts until `WindowIDRegistrar` registers it, because registration is deferred and never retried

| | |
|---|---|
| **Status** | open |
| **Module** | Window / App / Testing |
| **Platform** | macOS |
| **First seen** | 2026-09-24 |

## Description

A Window opened with Shift-Cmd-N can be `NSApp.keyWindow` before it is in `AppStateStore.nsWindowMap`. For that interval, every "key window" lookup in the app misses it. Cmd-B toggles no Window. Menu-routed commands fall back to `windows.first`, the *original* Window. CLI verbs with no explicit target do the same. The gap is at least one main-queue turn wide. If `nsView.window` is still nil when the deferred block runs, the gap lasts until SwiftUI next calls `updateNSView` on the registrar, which may be much later. Nothing retries it.

A reviewer found this by reading the code during #0418. Nobody has reproduced it by hand. #0418's VM run 1 (`20260924-011144-7893`) matches the symptom: Cmd-B was typed about 10 ms after the new Window's Sidebar became accessible, and the new Window's Sidebar never collapsed. That run also had the #0438 window-ordering confusion, so it is suggestive, not conclusive.

## Premises checked in code (read-only, `main` at `0ec4ea9a`)

1. **Registration is deferred and has no retry.** `WindowIDRegistrar.updateNSView` (`BattyKit/Sources/BattyKit/Util/WindowIDRegistrar.swift:29-35`) does `DispatchQueue.main.async { guard let window = nsView.window else { return }; AppStateStore.shared.registerNSWindow(window, for: id) }`. `makeNSView` returns a plain `NSView` with no `viewDidMoveToWindow` override. The registrar is the only production caller of `registerNSWindow` (`git grep registerNSWindow` finds only it plus tests). It is installed once per Window at `RootWindowView.swift:41` (`.background(WindowIDRegistrar(windowID: windowID))`). Its only input, `windowID`, is constant, so SwiftUI has no reason of its own to call `updateNSView` again.
2. **The gate is false until registration.** `keyWindowIsContentWindow()` and `keyWindowRuntime()` (`AppStateStore.swift:750-762`) both look up `NSApplication.shared.keyWindow` in `nsWindowMap`. An unregistered key Window gives `false` and `nil`.
3. **Cmd-B falls through, then toggles nothing.** `BattyShortcuts.handle` returns `false` at `BattyShortcuts.swift:34` (`guard appStore.keyWindowIsContentWindow() else { return false }`), so the local monitor does not consume the event. The event then goes on to normal key-equivalent handling. The View menu's "Toggle Sidebar" item (`BattyCommands.swift:78-87`, bound to `shortcuts.keyboardShortcut(for: .toggleSidebar)`, not disabled) posts `.battyToggleSidebar`. Every `RootWindowView` receives it, and each one checks `AppStateStore.shared.keyWindowRuntime()?.id == windowID` (`RootWindowView.swift:59-66`, check at `:62`). That is `nil` for all of them, so no Window toggles. If the menu path doesn't fire (a responder consumed the key equivalent first), the shortcut is dropped earlier. The result is the same.

### Everything that resolves the key Window through `keyWindowRuntime()`, and so shares the gap

**Keyboard shortcuts through `BattyShortcuts.handle`.** Every `ShortcutAction` except `.newWindow` is gated by `keyWindowIsContentWindow()` (`:34`). The actions that run then resolve `guard let window = appStore.keyWindowRuntime()` (`:113`). That covers `newSession`, `closeTab`, `newTab`, `splitHorizontal`, `splitVertical`, `splitFullHeightColumn`, `splitFullWidthRow`, the eight typed-pane splits (`splitHorizontal/VerticalGitStatus`, `…ProcessStatus`, `…LMStudioDashboard`, `…SystemMetrics`), `focusPaneLeft/Right/Up/Down`, `previousTab`, `nextTab`, `resizeSplitLeft/Right/Up/Down`, and `exitShell`, plus every action posted as a notification (below). The positional Cmd-1..9 and Cmd-Option-1..9 bindings resolve through `keyWindowRuntime()` at `:48`. `.newWindow` (`:109-111`) runs before that lookup, but it is still behind the `:34` gate. So Shift-Cmd-N pressed from an unregistered key Window also falls through to the menu's New Window item.

**Notification-toggled overlays whose receivers gate on `keyWindowRuntime()?.id`.** With no match, no Window acts. These are `.battyToggleSidebar` (`RootWindowView.swift:62`), and `.battyToggleBellFeed`, `.battyToggleCommandPalette`, `.battyToggleOpenQuickly`, `.battyToggleLayoutPicker`, `.battyToggleThemeSelector` and `.battyRequestPaste`. The last six all go through `SessionDetailView.isKeyWindow` (`SessionDetailView.swift:37-58`, `:272-274`). They are posted from `BattyShortcuts.run` (`:182-193`), from `BattyCommands` menu items, and from `CommandPaletteView.swift:272`.

**Menu commands through `BattyCommands.keyWindow`, which is `keyWindowOrFirstRegistered()`, which is `keyWindowRuntime() ?? windows.first`** (`BattyCommands.swift:50`, `AppStateStore.swift:778-780`). These don't drop the action; they send it to the original Window. That covers New Session (`:62`, `:92`), Cmd-1..9 session selection (`:112`), the split and typed-pane split items (`:238-320`), Focus Pane (`:353-377`), Resize Split (`:387-411`), New Tab (`:438`), Close Tab (`:446-458`), Previous/Next Tab (`:471`, `:479`), and tab selection by index (`:490`). Because `BattyShortcuts` falls through during the gap, Cmd-N, Cmd-T and Cmd-W can land in this path. For example, Cmd-N pressed in the brand-new Window would add a Session to the original Window. The same fallback feeds `focusedTerminalTab` (`AppStateStore.swift:799-801`, which `ExitDispatcher` and `PasteDispatcher` use), `markActiveTabSeen()` (`:1357`), and the `AppStateStore` shims `moveSessions`/`selectSession`/`closeFocusedTab`/`requestCloseFocusedTab`/`confirmPendingClose`/`cancelPendingClose` (`:956-1038`).

**CLI (XPC) verbs with no explicit target.** Several verbs resolve their default target through `focusedSessionIDFallback()`, `focusedPaneIDFallback()` or `focusedTabIDFallback()` (`AppStateStore.swift:403-450`), each of which is `keyWindowRuntime() ?? windows.first`. They are `paneSplit` (`AppXPCService.swift:121`), `paneClose` (`:173`), `notify` (`:206`), `sessionFocus` (`:233`), `paneFocus` (`:260`), `tabFocus` (`:287`), `sessionClose` (`:314`) and `paneHide` (`:347`). `sessionInfo`'s no-id fallback (`AppStateStore.swift:384`) works the same way. During the gap, a CLI call without `--session`/`--pane`/`--tab` targets the original Window instead of the one the user just opened and is looking at. `addSession` (the `batty <path>` URL path, `BattyURLHandler.swift:28`) uses `anyContentWindowRuntime()` (`AppStateStore.swift:810-815`). That falls back to `nsWindowMap.values.first`, which is an arbitrary registered Window because `Dictionary` has no order. This matters for the CLI-reliability goal. It is a narrow window, but an agent script that opens a Window and immediately runs a verb hits it deterministically.

**Seen-ness heuristics.** `recordBellTick` (`:1370`), `recordDesktopNotification` (`:1419`) and `recordCLINotification` (`:1489`) treat `keyWindowRuntime() == nil` as single-window mode. During the gap, a bell in a non-key Window's focused tab can be marked seen. This is minor, but it shares the root cause.

**Existing tests don't cover the timing.** `MultiWindowStoreTests.registerNSWindowMapsWindowToID` and `CrossWindowBehaviorTests` call `registerNSWindow` directly. Nothing exercises `WindowIDRegistrar` or the ordering between "Window becomes key" and "Window is registered".

## Steps to reproduce

1. Launch Batty with one Window.
2. Press Shift-Cmd-N, and press Cmd-B right away, without clicking.

## Expected behavior

The new Window is registered by the time it can receive key events. Cmd-B collapses the new Window's Sidebar and leaves the original's alone. Cmd-N adds a Session to the new Window. A no-target CLI verb resolves the Window the user sees as key.

## Actual behavior

This is predicted from the code and has not yet been reproduced by hand. During the gap, Cmd-B toggles no Window. Menu-routed Cmd-N, Cmd-T and Cmd-W and no-target CLI verbs act on the original Window.

## Notes

- **Suggested direction.** Register synchronously when the view joins its Window. One option is a small `NSView` subclass in `WindowIDRegistrar` that registers from `viewDidMoveToWindow` (and re-registers if the Window changes). This is AppKit calling into AppKit, not a SwiftUI update pass, so `docs/swiftui-observation-rules.md`'s rule against AppKit side effects from `updateNSView` doesn't apply. `nsWindowMap` is `@ObservationIgnored` (`AppStateStore.swift:69`), so the write notifies no observer. Alternatively, or as a backstop, register on `NSWindow.didBecomeKeyNotification` for that Window, so "is key" can never come before "is registered". Either way, keep `registerNSWindow` idempotent (it already is) and read `docs/view-hierarchy.md` and `docs/swiftui-observation-rules.md` first. Don't "fix" this by adding another `DispatchQueue.main.async` or `Task` hop, which is the #0229 anti-pattern.
- **Regression tests.**
  - UI test, in the Tart VM only (`docs/ui-testing-vm.md`): press Shift-Cmd-N, wait only until the new Window exists (identify it by the identifier not present before, per #0438), press Cmd-B without clicking, then assert that the *new* Window's Sidebar collapsed and the original's did not. Add a Cmd-N variant that asserts the Session lands in the new Window.
  - Unit test, if feasible: host `WindowIDRegistrar`'s view in a real `NSWindow` in `BattyKitTests`. Assert that the Window is in the map (`registeredContentWindowCount` or a test seam) as soon as the view is added to the Window's content view, synchronously and without draining the main queue. Per `AGENTS.md` "Asynchronous tests", don't wait or sleep to make it pass.
- The `nsWindowMap.values.first` fallback in `anyContentWindowRuntime()` is order-undefined when two or more Windows are registered. Once registration can no longer lag, consider whether it should prefer the most recently key or most recently created Window.
- Run UI tests only through the VM runner, never on the host (`AGENTS.md`, "UI test automation").
