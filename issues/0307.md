# 0307 — preflight.sh Sparkle key cross-check drops the trailing base64 pad from SU_PUBLIC_ED_KEY, so every valid key reports a false mismatch

| | |
|---|---|
| **Status** | open |
| **Module** | Build |
| **Platform** | macOS |
| **First seen** | 2026-08-04 |

## Description

The Sparkle EdDSA cross-check in `scripts/preflight.sh` (added by #0306) compares the private key's public half in the login keychain against `SU_PUBLIC_ED_KEY` in `Configuration/App.xcconfig` — but the `awk -F'='` extraction at lines 309-310 splits on *every* `=`, silently dropping the key's trailing base64 pad. The comparison can therefore never succeed for any valid key: the check reports `cred_fail` ("does NOT match … updates signed here would be unverifiable") even when the keys are byte-identical, blocking or misleading a release preflight with a false negative.

## Plan

Replace the `awk -F'='` extraction with one that splits on the first `=` only and strips surrounding whitespace, e.g.:

```bash
SU_KEY=$(grep -E '^SU_PUBLIC_ED_KEY' "$APP_XCCONFIG" 2>/dev/null \
    | head -1 | sed -E 's/^[^=]*=[[:space:]]*//; s/[[:space:]]*$//')
```

(guidance, not a contract). Also sweep `scripts/preflight.sh` and the sibling release scripts for any other `awk -F'='` value extraction that would truncate base64 or `=`-containing values — note findings, but keep this issue scoped to the Sparkle key check. `scripts/` is a restricted area per `CLAUDE.md`; this issue is the explicit authorization to fix this check.

## Steps to reproduce

1. Have a valid Sparkle EdDSA private key in the login keychain under account `Batty`, with its matching public key in `Configuration/App.xcconfig` as `SU_PUBLIC_ED_KEY` (the actual state of this machine, verified 2026-08-04).
2. Run the preflight credentials check (`scripts/preflight.sh`, credentials section).
3. Observe the Sparkle cross-check fail.

## Expected behavior

When the keychain key's public half matches `SU_PUBLIC_ED_KEY`, the check takes the `cred_pass` branch at line 320-321 ("Sparkle private key present and matches SU_PUBLIC_ED_KEY").

## Actual behavior

The check always falls through to the `cred_fail` at line 323:

```
[✗] Sparkle private key's public half (17V/QFAmgnEvb+YhA0+c/oA8TghcNVLOY5qYIa6aMZA=) does NOT match SU_PUBLIC_ED_KEY in App.xcconfig (17V/QFAmgnEvb+YhA0+c/oA8TghcNVLOY5qYIa6aMZA) — updates signed here would be unverifiable by installed clients
```

The two values are byte-identical except for the missing trailing `=` on the second — the tell that the xcconfig side was truncated during extraction, not actually different.

## Notes

Mechanism, verified 2026-08-04 against `scripts/preflight.sh` lines 309-310:

```bash
SU_KEY=$(grep -E '^SU_PUBLIC_ED_KEY' "$APP_XCCONFIG" 2>/dev/null \
    | head -1 | awk -F'=' '{sub(/^[ \t]+/, "", $2); print $2}')
```

`awk -F'='` splits the xcconfig line

```
SU_PUBLIC_ED_KEY = 17V/QFAmgnEvb+YhA0+c/oA8TghcNVLOY5qYIa6aMZA=
```

on every `=`, so `$1` is the field name, `$2` is the key value *without* its trailing pad, and `$3` is the empty string after the pad. Printing `$2` drops the final `=`, and the comparison at line 322 (`[[ "$SPARKLE_PUB" == "$SU_KEY" ]]`) can never be true.

- **Not key-specific, not machine-specific.** An Ed25519 public key is 32 bytes, which base64-encodes to exactly 44 characters ending in exactly one `=` pad — always. This check has never passed and cannot pass for any valid key.
- The other branches still behave correctly: `-z "$SU_KEY"` (empty xcconfig value, line 318-319) and `-z "$SPARKLE_PUB"` (missing keychain key, line 316-317). Only the match branch is unreachable.
- The keys on this machine actually do match — this is purely a parsing bug in the preflight gate.
- The suggested `sed` extraction also strips trailing whitespace, which the awk version did not — a stray trailing space in the xcconfig would have caused the same phantom mismatch.
- Related: #0306 (the issue that introduced this cross-check; documents the Sparkle key living in the login keychain under account `Batty`), `scripts/RELEASE-CREDENTIALS.md:114` (references the same cross-check).
