## Description

Pressing **Remind Again in 15 Minutes** or **Remind Again in 1 Hour** on a Reminder banner always sets a new Reminder on that Session, even when the user has already set a newer Reminder there. A Session holds one Reminder, so the newer Reminder (its text and its time) is silently replaced by a copy of the old one. Nothing tells the user: Remind Again leaves Batty in the background by design. The user wants this fixed before the 1.4.0 release.

Follow-up to #0631 (Quick Reminder bar, squash `cafbae32`), which added the Remind Again actions.

## Steps to reproduce

1. Set a Reminder on Session "api" with the text "check the deploy", in 5 minutes.
2. Let it fire. The banner "check the deploy" appears with Open Session and both Remind Again actions; leave it in Notification Center.
3. Press ⇧⌘R on "api" and set a new Reminder "review PR 412", in 1 hour.
4. In Notification Center, press **Remind Again in 15 Minutes** on the earlier "check the deploy" banner.

## Expected behavior

A Remind Again action acts on the Reminder its banner was for, identified by the banner's Reminder id (`payload.reminderID`), not by the Session alone:

- **The Session has no pending Reminder:** unchanged from today. A new Reminder with the banner's text is set `minutes` from now, and the fired Bell Feed entry is marked seen.
- **The Session has a pending Reminder whose id is not the banner's `reminderID`** (any pending Reminder at that point is newer, because the banner's own Reminder was cleared when it fired, `fireReminder`, `AppStateStore+Reminders.swift:294-296`): the action is ignored. The pending Reminder keeps its id, text, due time and scheduled system request, no Reminder is created, and nothing is scheduled or removed. The fired entry is still marked seen, because the user acted on that banner. The store logs the skip at `notice`.
- **The payload has no `reminderID`** and a Reminder is pending: treat it like the case above and ignore it. In-app posts always carry the id (`BellNotifier.reminderUserInfo`, `BellNotifier.swift:253-266`), so this only guards a malformed payload.

## Actual behavior

The pending "review PR 412" Reminder is replaced by a new "check the deploy" Reminder due in 15 minutes. Its system request is removed and a new one is scheduled. Nothing on screen tells the user.

## Root cause (verified against `cafbae32`)

- `BellNotifierDelegate.userNotificationCenter(_:didReceive:withCompletionHandler:)` (`BattyKit/Sources/BattyKit/Runtime/BellNotifier.swift:295-316`) builds a `NotificationTapPayload` from the banner's userInfo, which carries the entry id, the Reminder id, the Session id and the text. For Remind Again it skips `NSApp.activate` (`:307`) and calls the store's `onTap`.
- `AppStateStore.handleNotificationTap` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore+Reminders.swift:199-203`) sends `.remindAgain` to `remindAgain(minutes:payload:)` before any routing.
- `remindAgain` (`AppStateStore+Reminders.swift:63-72`) checks only that the Session still exists (`:64`), then calls `setReminder(.after(minutes:), note: payload.note, forSessionID:)` (`:68`). It never reads `payload.reminderID` or `session.reminder`.
- `setReminder` (`:78-99`) replaces whatever is pending, "one per Session" by design: it overwrites `session.reminder` (`:92`), the scheduler entry (`:93`), and removes the previous system request (`:94-96`).

So the premise is confirmed: the action is keyed by Session, and the newer Reminder is lost.

## Notes

- The planner may prefer a visible response over a silent skip, for example activating Batty and opening the Quick Reminder bar in edit mode on the newer Reminder. This issue only requires that the newer Reminder is never replaced without the user seeing it. The silent skip above is the minimum, and it matches Remind Again's existing promise of staying in the background.
- Pressing Remind Again twice on the same banner lands in the same branch: the first press sets a Reminder with a new id, so a second press is ignored rather than resetting the timer.
- Remind Again on an older banner when a *later* Reminder has already fired (so nothing is pending) still sets a Reminder with the older banner's text. That does not replace anything, and is out of scope.
- The scheduled (after-quit) request uses the open-only category (`ReminderNotification.scheduledCategory`, `ScheduledReminderNotification.swift:107-133`), so it has no Remind Again action and is not affected.

## Resolution notes

> 🟢 Resolved 2026-11-15 — Remind Again now ignores a banner when the Session holds a different pending Reminder, so a newer Reminder is never replaced; the fired entry is still marked seen.

## Root cause

Confirmed as described: `remindAgain(minutes:payload:)` in `AppStateStore+Reminders.swift` checked only that the Session existed, then called `setReminder`, which replaces whatever Reminder is pending. It never compared `payload.reminderID` with `session.reminder`.

## Fix

As planned (silent skip). `remindAgain` binds the Session, and if it has a pending Reminder whose id differs from `payload.reminderID` (nil never matches), it logs at `notice` and returns without calling `setReminder`. Marking the fired entry seen moved into a `defer` after the Session guard, so both branches mark it seen and the gone-Session path still marks nothing. No deviation from the plan.

## Plan

Planned 2026-11-15 against `issue/0633` at `b10634f5`. Every premise in the Description was checked against the code and holds: `remindAgain` (`AppStateStore+Reminders.swift:63-72`) reads only `payload.sessionID` and calls `setReminder` (`:78`), which replaces `session.reminder` and removes the previous system request. `fireReminder` clears `session.reminder` only when the ids match (`:294-296`). `BellNotifier.reminderUserInfo` (`BellNotifier.swift:253-266`) always writes the Reminder id. `SessionReminder` is `Equatable` (`Model/SessionReminder.swift:7`), so `session.reminder == newer` compiles.

**Decision:** skip silently and log, the minimum in the Description. Remind Again keeps its promise of not activating Batty (`BellNotifierDelegate` passes `activates = false` for `.remindAgain`).
