## Root cause

The reported failure no longer reproduces. The original `XCTAssertTrue
failed` at `DragDropTests.swift:89` was caused by the main-runloop-
blocking `Thread.sleep` bug fixed in [[0170]]. The test launches the
app twice (the original-launch tab-bar capture, then a second launch
that issues `applyLayout twoByTwoGrid` + `swapPanes at: 1 with: 1`)
and polls `waitFor({ tabBars2.count == 4 }, timeout: 10)` after the
second launch. The pre-[[0170]] `waitFor` blocked the main runloop on
`@MainActor`, starving XCUITest's XPC bridge so the four `tab-bar.<id>`
accessibility elements were not observed before the timeout expired.

The same-pane swap behavior itself is correct — the `tree.swapPanes`
guard short-circuits when `id == id`, leaving the four-pane grid
intact — and is now observable since [[0170]] replaced the duplicated
`Thread.sleep` poll helpers with the centralized
`RunLoop.run(until:)`-based `waitFor`. Three consecutive runs of the
unchanged test on today's `main` all passed.

## Fix

No code change. The fix landed transitively with [[0170]]
(commit `eb00412`'s `waitFor` overhaul). This issue follows the same
pattern as the just-resolved [[0174]] — surface-level failure
explained by the runloop block, confirmed cleared after the
stabilization pass.

## Gotchas

- This test launches the app twice (cold launch to capture initial
  `tabBars`, then a second launch with the swap script). Because pane
  UUIDs are minted fresh per launch, the `idsBefore` captured from the
  first launch can't be meaningfully compared against the second
  launch's tab-bar identifiers — the only assertion that survives the
  cross-launch boundary is the structural `tabBars2.count == 4`
  check. That's the same design-flaw class called out in [[0173]]'s
  rewrite of `testIntentSwapChangesTabBarOrder`; if the assertion ever
  needs to be strengthened (e.g. "the swap really was a no-op, IDs
  unchanged"), the test would need to be rewritten as a single-launch
  flow chaining both intents — see [[0173]] for the template.
- The same-pane-swap path in `tree.swapPanes(id:with:)` has a
  same-id guard that logs a notice and returns early. If that guard
  is ever removed, this test would silently keep passing (the pane
  count would still be 4 after a self-swap that's actually a no-op
  destructive operation, depending on implementation). A stronger
  assertion would require the rewrite called out above.
