# 0635 — Remind Me… opens the Quick Reminder bar even while another sheet is up on the Window

| | |
|---|---|
| **Status** | resolved |
| **Module** | Session / App |
| **Platform** | macOS |
| **First seen** | 2026-11-15 |
| **Priority** | high |
| **Target** | 1.4.0 |

## Description

Pressing ⇧⌘R (`ShortcutAction.remindMe`) while a sheet is already up on a Window, such as Rename Session, the Theme Selector or the paste confirmation, still asks that Window to present the Quick Reminder bar. The result is a second sheet on top of the first, reported as stacking. Every other sheet toggle in the same view ignores its chord while a sheet is key. The user wants this fixed before the 1.4.0 release.

The defect predates #0631, but only partly. The old Reminder sheet had the same ungated path through the Session menu's **Remind Me ▸ Custom…** and **Edit Reminder…** items, which can be clicked in the menu bar while a sheet is up. Those items had no key equivalent before #0631 (`git show cafbae32^:BattyKit/Sources/BattyKit/Views/ReminderMenu.swift` has no `keyboardShortcut`, and `ShortcutAction` had no `remindMe`). #0631 added ⇧⌘R, and the chord makes the defect much easier to hit.

## Steps to reproduce

1. Right-click a Session in the Sidebar and choose **Rename**. The Rename Session sheet is up and key.
2. Press ⇧⌘R. (Or choose **Session ▸ Remind Me…** in the menu bar.)

## Expected behavior

While any sheet or dialog is attached to a Window, nothing opens the Quick Reminder bar on that Window:

- ⇧⌘R does nothing. The attached sheet keeps focus and the key is consumed or beeps, like the other declined chords.
- **Session ▸ Remind Me…** and **Edit Reminder…** are disabled, or choosing them does nothing. **Cancel Reminder** may stay enabled, since it opens no sheet.
- `WindowRuntime.reminderBarSessionID` is not written, so the bar does not appear after the other sheet closes either.
- When the attached sheet is the Quick Reminder bar itself, ⇧⌘R stays a no-op (today's `openBar` same-Session guard).
- The Command Palette's Remind Me… row is unchanged. It closes the palette first and opens the bar from the palette's `afterDismiss` hook, when no sheet is attached.

## Actual behavior

`reminderBarSessionID` is set and SwiftUI is asked to present the bar while the other sheet is still attached. The user reports a stacked second sheet. (Whether AppKit stacks it or queues it until the first sheet ends can't be checked headlessly. Both are wrong.)

## Root cause (verified against `cafbae32`)

- **The chord reaches the menu, not `BattyShortcuts`.** While a sheet is key, `BattyShortcuts.handle` returns false at `appStore.keyWindowIsContentWindow()` (`BattyKit/Sources/BattyKit/Commands/BattyShortcuts.swift:34`; `AppStateStore.swift:1143-1146`), because the sheet window is not in `nsWindowMap`. The event goes to the main menu, where ⇧⌘R is the key equivalent of the Session menu's **Remind Me…** / **Edit Reminder…** (`ReminderMenuItems`, `BattyKit/Sources/BattyKit/Views/ReminderMenu.swift:78-92`, mounted at `Commands/BattyCommands.swift:236-239`).
- **The menu's target resolves to the Window behind the sheet.** `ReminderMenuItems`'s `target` reads `actionWindow`, which is `store.menuTargetWindow()` (`BattyCommands.swift:71`). That is nil only while the Project Editor, the Open Project picker or an *auxiliary* window is key (`AppStateStore.swift:1349-1358`). `isAuxiliaryWindow` walks a sheet up to its parent, and "a sheet or child window over a content window is not auxiliary" (`AppStateStore.swift:1309-1323`). So `menuTargetWindow()` returns the content window, and `defaultTargetWindow()` falls back to the most recently key content window (`:1240-1251`).
- **Nothing checks for an attached sheet.** `ReminderActions.openBar(for:in:)` (`ReminderMenu.swift:31-34`) returns early only when the bar is already up for the same Session, then writes `window.reminderBarSessionID`. `SessionDetailView` presents the bar from that id (`reminderBarBinding`, `SessionDetailView.swift:127-133`, `:326-334`). Its other sheets keep their own state, mostly view-local `@State` (`commandPaletteShown`, `themeSelectorShown`, `layoutPickerShown`, `pendingPaste`, `backgroundPickPaneID`; `projectPickerShown` and `pendingStartupTrusts` live on `WindowRuntime`), and none of it is consulted.
- **The other sheet toggles are already gated.** Their notification handlers start with `guard isKeyWindow` (`SessionDetailView.swift:42-74`), and `isKeyWindow` is `store.keyWindowRuntime()?.id == windowRuntime.id` (`:315-317`). That is false while a sheet window is key, so the Command Palette, Theme Selector and Layout Picker chords do nothing over a sheet. The ⇧⌘R path bypasses that pattern: `BattyShortcuts.run`'s `.remindMe` case calls `ReminderActions.openBar(in:)` directly (`BattyShortcuts.swift:204-205`), and the menu item calls `openBar(for:in:)`.

Sheets it can stack on, all attached to the content window:

- `SessionDetailView`: paste confirmation, Command Palette, Open Quickly, Layout Picker, Open Project picker, pane background image picker, Theme Selector, startup-command trust sheet; plus the close-confirmation and clipboard-read `confirmationDialog`s.
- `SessionSidebarView` (`:135-171`): Rename Session, Session theme, Session color, pane background settings, Session background.
- `PaneView` (`:136`, `:154`): Rename Tab, Tab background.

The Open Project picker is the one exception: `menuTargetWindow()` already returns nil while it is key (`projectPickerIsKey`).

## Notes

- The other menu items that open a sheet on the content window may have the same hole when clicked in the menu bar over a sheet (for example the pane background items). Only the Reminder path is in scope here. The planner should check whether a shared "Window has an attached sheet" gate for `menuTargetWindow()` callers that present sheets is cheap.
- UI tests run only in the Tart VM (`docs/ui-testing-vm.md`).

## Root cause

As the Description states, confirmed against the code: while another sheet is key, `BattyShortcuts.handle` declines (the sheet window is not a content window), so ⇧⌘R reaches the main menu's **Remind Me…** / **Edit Reminder…** item. Its target resolves to the content window behind the sheet (`menuTargetWindow()` does not treat a sheet as auxiliary), and `ReminderActions.openBar(for:in:)` wrote `reminderBarSessionID` without checking for an attached sheet.

## Fix

As planned. `AppStateStore.windowHasAttachedSheet(_:)` reports `nsWindow(for:)?.attachedSheet != nil` (false for an unregistered window). The pure rule `ReminderActions.openBar(for:in:windowHasAttachedSheet:)` declines when it is true. `ReminderMenuItems.open()` (Session menu and Sidebar context menu) and `BattyShortcuts.run`'s `.remindMe` case route through it. The items stay enabled and consume the chord, since `attachedSheet` is not observed state. The palette row and Sidebar clicks are unchanged. `RenameSessionSheet`'s field gained `rename-session.field` for the UI tests. No deviations.

### Premises checked

Every code claim in the Description holds at `b10634f5`:

- `BattyShortcuts.handle` is the app's local key monitor (`Batty/BattyApp.swift:90`). It returns false at `guard appStore.keyWindowIsContentWindow()` (`BattyShortcuts.swift:33`), and a SwiftUI sheet's window is not in `nsWindowMap` (`AppStateStore.swift:1143-1146`). So while a sheet is key, ⇧⌘R (the `.remindMe` default, `ShortcutAction.swift:183-184`) falls through to the main menu. There it is the key equivalent of **Remind Me…** / **Edit Reminder…** (`ReminderMenuItems`, `ReminderMenu.swift:77-92`).
- The Session menu's `target` closure (`BattyCommands.swift:236-239`) reads `actionWindow` = `store.menuTargetWindow()` (`:71`). That is nil only for the Project Editor, the Open Project picker or an auxiliary window (`AppStateStore.swift:1349-1358`). A sheet over a content window is not auxiliary (`:1309-1323`), and `defaultTargetWindow()` (`:1240-1251`) falls back to `recentlyKeyWindowIDs`, which is the window behind the sheet.
- `ReminderActions.openBar(for:in:)` (`ReminderMenu.swift:31-34`) guards only on the same Session, then writes `reminderBarSessionID`. `SessionDetailView` presents the bar from it (`reminderBarBinding`, `:326-334`; `.sheet(item:)` at `:127-133`).
- The other toggles are gated by `guard isKeyWindow` (`SessionDetailView.swift:41-74`, `isKeyWindow` at `:315-317`).

**One correction to Expected behavior.** **Remind Me…** / **Edit Reminder…** will *not* be disabled while a sheet is up. Choosing them, or pressing ⇧⌘R, does nothing. The reason: `NSWindow.attachedSheet` is not observed state. A `.disabled(...)` driven by it would not re-run the `Commands` body when the sheet closes, so the item could stay disabled. That is the trap `BattyCommands`' `actionWindow` doc comment (`:62-70`) describes. The item still handles the chord and consumes it, so nothing beeps and the sheet keeps focus. **Cancel Reminder** stays ungated, since it opens no sheet.

### Approach

Gate the *menu* entry point, not `openBar(for:in:)` itself. The Command Palette's row must stay unchanged. It calls `openBar(for:in:)` from the palette sheet's `onDismiss` (`SessionDetailView.swift:88`, `runAfterCommandPalette`). At that moment AppKit may still report the palette as `attachedSheet`, so a gate inside `openBar(for:in:)` could break `testPaletteRemindMeSwapsIntoTheBar`. The Sidebar row's click and `onEdit` (`SessionSidebarView.swift:364`, `:372`) also stay ungated: a document-modal sheet blocks mouse events to its parent window, so those can't fire over a sheet.

     /// Opens the bar from a menu item or chord, unless a sheet is attached

     static func openBar(for session: SessionRuntime, in window: WindowRuntime, windowHasAttachedSheet: Bool) {

### Same defect elsewhere (out of scope; suggest a follow-up issue)

`menuTargetWindow()` ignores attached sheets for every Session, Pane and Tab menu item. While a sheet is key, a menu-routed chord acts on the window behind it. Examples:
- ⌘N adds a Session.
- ⌘T adds a Tab.
- ⌘W calls `requestCloseFocusedTab()`, which can stack the close-confirmation dialog.
- ⌘1…9 switches Sessions.
- The split and focus items act on the window behind.
- **Pane ▸ Background Images…** (`BattyCommands.swift:597-605`) posts a window-addressed notification that its handler accepts "key or not" (`SessionDetailView.swift:66-71`), so it can stack a second sheet the same way.

A single gate in `menuTargetWindow()` (nil while `windowHasAttachedSheet`) would fix all of these. But it changes about 40 actions, including the paste-target path (`AppStateStore.swift:1437-1440`), just before 1.4.0. So it isn't the "same single gate" this issue needs. The orchestrator should file it separately.
