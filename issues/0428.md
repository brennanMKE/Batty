## Description

This is the foundation child of umbrella [#0427](0427.md), and it blocks the other BattyKit children ([#0429](0429.md)–[#0433](0433.md)). #0427 lists about 84 unit-test sites that wait on sleeps, deadline polls, or elapsed time, which `AGENTS.md` "Asynchronous tests (binding)" forbids. Most of the replacements need the same few pieces, and BattyKit has none of them yet. `grep -rnE "protocol .*(Clock|Scheduler)"` over `BattyKit/Sources` finds nothing. The only readiness helpers are two copies of an unbounded blocking `waitForReady(_ pipe:)` and a `Thread.sleep`-polled `waitForReadyFile`. If each area child builds its own, the result is three clocks, three readiness helpers, and three different ways to prove "returns without blocking". This issue builds each piece once. It proves each one on a single real site and answers the three "verify" questions #0427 left open. It does not migrate anything else.

## Scope

### 1. One injected clock/scheduler protocol

A single protocol that the LM Studio, Git Status and Process Status content types can all take. It must cover every use #0427 found:

- **Sleep until a deadline / for a duration.** LM Studio's models poll, `lms ps` poll and respawn delay (`Runtime/LMStudioDashboardPaneContent.swift:271`, `:349`, `:728`). Git Status' debounce (`Runtime/GitStatusPaneContent.swift:761`). Process Status' sampler (`Runtime/ProcessStatusPaneContent.swift:335-337`).
- **`now`.** LM Studio's stale-in-flight window compares against it, and so do the timestamps `ProcessStatusPaneContent` feeds `ProcessCPUDeltaTracker`.
- **Pending work that can be inspected.** The fake must be able to say "nothing is scheduled". This is how Git Status and Process Status prove "zero periodic work while suspended" and "no deferred activate" without a fixed window.

Deliverables:

- The protocol and a **production implementation** in `BattyKit/Sources`, backed by the real clock.
- A **test fake** that only moves when the test advances it. It needs `advance(by:)` (or advance-to-next), a readable `now`, and a pending-work count or drain. The test must be able to await "the work woken by this advance has run", so an advance never needs a follow-up sleep.
- The production default is set **explicitly at each production construction site**. It must not be a parameter default that silently applies in the app (the #0359 lesson, repeated in #0427 "Production seams needed").

**Proving use:** route `ProcessStatusPaneContent`'s sampler loop through the protocol. Then rewrite `ProcessStatusPaneLifecycleWiringTests.swift:114` (`aHiddenProcessStatusPaneDoesNotKeepSampling`, which today sleeps 200ms at a 20ms cadence through the `samplingInterval` seam, `:16-40`) to pass the fake through the `contentFactory` override, advance many intervals while hidden, and assert no sample. [#0431](0431.md) builds on this for the rest of Process Status.

### 2. Shared child-process readiness helper (test support)

One helper in `BattyKit/Tests/BattyKitTests/` that awaits a child process's "ready" signal as an event. It has two variants:

- **Pipe variant.** Use when the test owns the child's stdout. It uses a `FileHandle.readabilityHandler` plus a checked continuation. This replaces the two copies of `waitForReady(_ pipe:)` (`PendingTeardownReapRegistryTests.swift:44-46`, `ProcessGitStatusScannerTests.swift:389-391`). Both copies block on `availableData` with **no upper bound**, so a child that never writes hangs the whole suite.
- **FIFO variant.** Use when the content's own factory owns stdout, as in `LMStudioSIGTERMIgnoringFixture`. `mkfifo` a path, the child writes `ready` into it, and the test reads it through the same readability-handler plus continuation path. This replaces `LMStudioSIGTERMIgnoringFixture.waitForReadyFile` (`:49-53`, a `Thread.sleep(0.01)` poll to a 5s deadline).

Both variants take an upper bound. The bound is a **hang guard only**: on expiry the test fails with a clear message. It is never how the helper succeeds. The handler must be cleared and the continuation resumed exactly once on every path: data, EOF, and bound expiry.

**Proving uses:**

- Pipe variant: `PendingTeardownReapRegistryTests` (the `waitForReady` helper at `:44-46` and its calls at `:90`, `:119`). The helper copy is deleted.
- FIFO variant: `LMStudioSIGTERMIgnoringFixture.waitForReadyFile` (`:49-53`). Its call sites (`LMStudioDashboardPaneContentTests.swift:375-376`, `LMStudioDashboardWiringTests.swift:256-257`, `:341-342`) change only mechanically, to call the new helper. The rest of those tests stays with [#0429](0429.md).

### 3. Completion-signal conventions

Pick and write down which shape a production seam uses in which situation, so the children don't argue it out five times:

- **Returned or exposed `Task`.** Use for a one-shot unit of async work the production code starts, e.g. the summarization `Task` in `AppStateStore.scheduleSummarization` (`AppStateStore.swift:2084`).
- **Callback / continuation.** Use where production already has a callback, e.g. `terminateHandler` or `Process.terminationHandler`.
- **`AsyncStream` of events.** Use for repeated events a test awaits a count of: LM Studio line-applied, poll-applied and stream-termination-handled; Git Status scan-handled; stream-process-launched.

For each shape, the conventions must cover four things. Who creates the stream or continuation. Whether it is test-only (`…ForTesting`) or always on, and why always-on is acceptable when it is. How a test bounds the await as a hang guard. How it avoids changing production behaviour.

Put the conventions where the children will read them: a short addition to `AGENTS.md` "Asynchronous tests (binding)" pointing at a `docs/` guide (list it in `docs/README.md`). This issue edits only those docs lines. It must not touch the user's other uncommitted `docs/` work.

**Proving use (callback shape):** `CrossWindowBehaviorTests.swift:446` (`removeWindowOnLastWindowEventuallyTerminates`), which sleeps 200ms for the `DispatchQueue.main.async`-deferred terminate (`Runtime/AppStateStore.swift:271`). `terminateHandler` is already a callback, so resume a continuation (or use `confirmation`) from it and await that. The rest of that file stays with [#0433](0433.md).

### 4. Reap gate for proving "returns without blocking" structurally

A test-controlled gate for the deferred reap work. Today that work is the per-process `Task.detached` in `LMStudioDashboardPaneContent` (`:759-760`) and `ProcessGitStatusScanner.scheduleTeardownReap` (`Runtime/GitStatusPaneContent.swift:296-314`). The test holds the gate closed. Then the teardown call returning while the gate is still closed and the child is still running is the proof that it didn't wait on the reap. After that the test opens the gate and awaits `awaitPendingTeardownReapsForTesting()`. In production the gate is always open. Setting it must be explicit at the production construction site, the same rule as §1.

**Proving use:** `ProcessGitStatusScannerTests.swift:409-415` (`terminateAndWaitBrieflyReturnsImmediatelyEvenWhenTheProcessIgnoresSIGTERM`, today `elapsed < .milliseconds(50)`), including its `waitForReady` call at `:402`, which moves to the §2 pipe helper. The remaining scanner rows, the kill poll at `:425-431` included, stay with [#0430](0430.md). [#0429](0429.md) applies the same gate to LM Studio's `tearDown`.

### 5. Resolve #0427's three "verify" questions

Write each answer into this issue's resolution, with the evidence (XNU source, Foundation source, or an experiment). The owning child applies it.

1. **`posix_spawn` and argv readability.** Does XNU's `posix_spawn` return only after the new image's argv/env is set up, so that `KERN_PROCARGS2` can read it immediately? This decides whether `ProcessInspectorTests.swift:330`'s `usleep(50_000)` can just be deleted, or whether the child has to signal readiness. Owner: [#0431](0431.md).
2. **`CLOCK_UPTIME_RAW`.** Is `clock_gettime_nsec_np(CLOCK_UPTIME_RAW)` exactly `mach_absolute_time()` converted to nanoseconds on both arm64 and x86_64? If so, `machTimebaseNanosecondsPerTickAgreesWithAnIndependentClock` (`ProcessInspectorTests.swift:215-240`) can compare back-to-back reads with no interval. Owner: [#0431](0431.md).
3. **When `Process.isRunning` flips after a reap.** Once `awaitPendingTeardownReapsForTesting()` or `PendingTeardownReapRegistry.drainSynchronously()` returns, has the child already been `waitpid`-ed, so that `isRunning == false` and `kill(pid, 0) != 0` both hold at once? Or does Foundation reap asynchronously, so a single `kill(pid, 0)` check could still see a zombie and the test must await `terminationHandler` first? This decides the `kill(pid, 0)` polls at `ProcessGitStatusScannerTests.swift:425-431` (owner [#0430](0430.md)) and `PendingTeardownReapRegistryTests.swift:105-111` (owner [#0432](0432.md)).

(#0427's fourth "Verify", whether a stream `Process` has already launched when `makeModelStreamProcess` returns, `LMStudioDashboardPaneContentTests.swift:316`, stays with [#0429](0429.md). It is specific to that factory.)

## Out of scope

Every other #0427 inventory row. Migrate only the proving uses named above. The children rebase onto this and do the rest.

## Done when

- Each of the four pieces exists and its proving use has been migrated. Each piece also has direct unit tests (e.g. the fake clock's advance and pending-work semantics, and the readiness helper's hang-guard expiry path).
- The three verify answers are recorded here with evidence.
- `grep -rnE 'Task\.sleep|Thread\.sleep|usleep|asyncAfter|RunLoop\.main\.run\(until|ContinuousClock\.now|waitUntil|Date\(\) *<'` over the proving-use sites and the new helpers returns nothing but hang-guard bounds.
- `./build.sh unit` passes.
- Every mutation the replaced waits were documented to catch still fails the rewritten test. In particular, the leaked-sampler mutation `ProcessStatusPaneLifecycleWiringTests.swift:114` guards: re-introducing a sampler that keeps running while hidden must fail the rewrite. So must a `terminateAndWaitBriefly()` that waits on the reap before returning.
