## Description

Child of #0660. MCP hosts put the server's `initialize` `instructions` into the agent's context, so this is the one place every MCP-capable host (Claude Code, Codex, Cursor, OpenCode) tells the agent about Batty without any instruction file. Today the text is fixed and hedged. It should state what the server's own environment says: in Batty with these ids, or not in a Batty Pane.

### Current state

- `MCPServer.instructions` is a static string: "You may be running inside Batty, a macOS terminal multiplexer. These tools mirror the batty command-line verbs … Omitted Session/Pane/Tab targets resolve to your own Pane through the BATTY_* environment variables. Call capabilities for the full vocabulary." (`BattyKit/Sources/batty/MCPServer.swift:72-77`), sent unchanged by `initializeResult` (`MCPServer.swift:147-156`).
- The server runs with the agent's environment, and each tool's child process inherits it (`BattyKit/Sources/batty/MCPToolRunner.swift:16-18`), so the server can read `BATTY_*` at start-up and knows whether targets will default to a Pane.
- The instructions name no tool for any view: nothing maps "git status" to `pane_split` with `view: git-status`, or "dev server" to `server_start`.

## Plan

Planned 2026-11-18 against `main` at `3b2e6c4f` (#0661 merged).

Premises checked: `MCPServer.instructions` is the static string at `MCPServer.swift:72-77`, sent by `initializeResult` (`:147-156`); `MCPCommand.run` builds the server with no environment input; `AgentContextNote` (`BattyCLICore`) already owns the three-way `resolve(environment:)` and the in-Batty header. One premise is out of date: `pane split -c/--command` already exists (`PaneCommand.swift:58`, property `command`), so "a command in a new Pane → `pane_split` with `command`" goes in now; only `tab_new` waits for #0667 (no `tab new` verb today, `TabCommand` has only `focus`). Targets with no id fall back to `BATTY_*`, then the focused Pane/Tab/Session (help text on every `--pane`/`--tab`/`--session`), which confirms the outside-Batty wording.

### Decisions

1. **Builder lives in the `batty` target, not `BattyCLICore`.** It needs `MCPToolCatalog` (in `batty`) to filter the tool map. The id lines and the three-way resolution come from `AgentContextNote`, so the in-Batty identity text has one source.
2. **The tool map is a static table filtered against the live catalog, not prose.** Each entry names a tool, optionally an argument and value, and a short "when" phrase. At render time an entry is dropped unless the catalog has that tool and (if given) that argument and enum value. So with `serverPane` off the `server_*` lines vanish instead of naming tools that don't exist, and a renamed verb drops out of the text rather than lying to the agent. A test (below) makes a dropped entry fail in the flag-on catalog, so the rename is caught in CI, not silently hidden.
3. **Not generating the "when" phrases from capabilities descriptions.** Verb abstracts say what a verb does, not when an agent should reach for it ("dev server", "git status"); the mapping is editorial. Filtering plus the drift test is enough.
4. **Outside Batty** (`.notInBatty`): "You are not running in a Batty Pane (no BATTY_* environment). These tools act on Batty's focused Session, Tab or Pane unless you pass ids; use them only when the user asks for Batty." No ids. The tool map still follows, since a user who asks for Batty from another terminal still benefits.
5. **Incomplete `BATTY_*`** (`.incomplete(description)`): the outside-Batty text plus one line "BATTY_* is incomplete (<description>); pass ids explicitly." Per-key fallback in the CLI means partial context resolves some targets, so "acts on this Pane" would be wrong and plain "not in Batty" would hide the cause.
6. **Codex env filtering (open question 1):** no special case here; #0665 owns it, as the issue recommends.
7. **Rule lines are not reused verbatim.** `AgentContextNote.ruleLines` are CLI-phrased (`batty pane split --view …`); inside MCP the agent should call tools. The map carries the same advice in tool form, including close-what-you-open (`pane_close`/`session_close`).
8. **Drift check without parsing prose:** the builder exposes the filtered hints, and tests check each hint against the catalog; a second test checks that every backticked lower-case identifier in the rendered text is a catalog tool or a catalog property name.

## Expected behavior

- `MCPServer` takes its instructions as an init parameter. `MCPCommand.run` builds them from the process environment with #0661's builder.
- In a Batty Pane: "You are running in a terminal Pane of Batty … Session S, Tab T, Pane P. Tools with no target act on this Pane." plus the shared rules and a short tool map: status views → `pane_split` with `view`; dev servers → `server_start`/`server_attach`; static sites → `server_serve` with `open`; a page → `server_preview`; a command in a new Pane or Tab → `pane_split` with `command` / `tab_new` (#0667, #0668); attention → `notify`; later → `session_remind`.
- Outside Batty: says the agent is not in a Batty Pane, that tools act on Batty's focused Pane unless given ids, and to use them only when the user asks for Batty.
- Kept short (MCP hosts may truncate instructions; aim under ~1,500 characters).

## Root cause

`MCPServer.instructions` was a static string ("You may be running inside Batty"), built with no environment, so an MCP agent never learned its Session, Tab or Pane, nor which tool fits which task.

## Fix

- `AgentContextNote.identityLines(context:)` extracted; `header` builds from it (output unchanged).
- New `MCPInstructions` (`batty` target): resolves `BATTY_*` via `AgentContextNote.resolve` into in-Batty (identity lines + "act on this Pane"), not-in-Batty, or incomplete text; appends a static tool-per-task hint table filtered against the live `MCPToolCatalog` (tool, argument and enum value must exist).
- `MCPServer` takes `instructions:` as an init parameter; `MCPCommand.run` builds them from the process environment and the same catalog it serves.
- Docs bullet in `docs/batty-cli-agent-workflows.md`.
