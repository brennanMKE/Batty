## Root cause

The original `XCTAssertTrue failed - Expected new tab chip after Cmd-T`
assertion at `KeyboardShortcutTests.swift:24` was caused by the
main-runloop-blocking `Thread.sleep` bug fixed in [[0170]]. The test
snapshots the `tab-chip.*` count, dispatches a `Cmd-T` keystroke, then
polls (via the shared `waitFor`) until the chip count exceeds the
snapshot. The synthesized `typeKey` is delivered asynchronously over
XPC, and the new chip only appears in the accessibility tree after the
app side processes the shortcut and the tab-bar view rebuilds.

Pre-[[0170]], the duplicated per-file `waitFor` polled with
`Thread.sleep(forTimeInterval: 0.1)` on a `@MainActor` test method —
starving the test process's main runloop and preventing XCUITest's XPC
bridge from delivering the updated accessibility-tree snapshot inside
the 5s timeout. The predicate kept seeing the stale (`chipsBefore`)
count and the assertion failed.

The app-side Cmd-T routing is correct; the new chip does appear well
inside 5s now that the centralized `waitFor` (commit `eb00412`)
pumps the runloop via `RunLoop.run(until:)` between predicate
evaluations.

## Gotchas

- The test asserts strictly `> chipsBefore`, not `== chipsBefore + 1`.
  If a future change accidentally creates more than one chip per
  Cmd-T (e.g. tab restoration racing with the new-tab action), this
  assertion still passes silently. Tightening to `== chipsBefore + 1`
  would catch that class of regression.
- The test relies on XCUITest's `typeKey` awaiting `Wait for
  co.sstools.Batty.beta to idle` (visible in the test log) before
  returning, plus the `waitFor` runloop pump, to surface the new
  accessibility node. If a future refactor switches to a non-idling
  key dispatch path, the 5s `waitFor` budget should remain generous
  enough — but worth knowing the dependency exists.
