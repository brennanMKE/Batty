# 0250 — `batty <path>` creates a session in the running app; rename the CLI entry source off main.swift

| | |
|---|---|
| **Status** | open |
| **Module** | App / Session |
| **First seen** | 2026-06-23 |

## Description

Now that the `batty` CLI exists and installs (#0249), it needs to actually do something. Two changes, in order:

1. **Fix the entry-point source naming.** The CLI source is currently `BattyKit/Sources/batty/main.swift` using top-level code. As the tool grows it should use a proper `@main` entry point (e.g. with `swift-argument-parser`), but **`@main` conflicts with a file named `main.swift`** — SwiftPM treats `main.swift` as the implicit top-level entry, which collides with the `@main` attribute. Rename the source (e.g. `Batty CLI.swift` / `BattyCLI.swift`) and introduce a `@main` entry point.

2. **`batty <path>` tells the running Batty app to create a new Session at that path.** The primary action. Running `batty <path>` — including the common `batty .` for the current directory — should have the Batty Mac app **create a new Session whose first Pane's shell starts in that directory**. `batty .` resolves to the shell's current working directory.

## Expected behavior

- `batty .` → Batty creates a new Session rooted at the current directory.
- `batty ~/Developer/Foo` / `batty ./sub/dir` / relative and absolute paths → new Session rooted at the resolved, absolute path.
- The path is resolved relative to the CLI's own working directory (it runs in the user's shell), then passed to the app as an absolute path.
- Sensible behavior when Batty isn't running, when the path doesn't exist, and when the path isn't a directory (see Open questions).

## Notes — design considerations (not prescriptive)

**IPC: CLI → running app.** There is currently no IPC channel between a separate process and the running Batty app. `HyperlinkOpener` is the only outward path and it's the wrong direction. Candidate mechanisms to evaluate:
- A custom **URL scheme** (`batty://session?path=…`) registered via `CFBundleURLTypes`, opened from the CLI with `NSWorkspace`/`open`, handled in the app via `onOpenURL` / `application(_:open:)`. Simplest; also auto-launches the app if not running and activates it. Path must be percent-encoded.
- A **local socket / `CFMessagePort` / XPC** channel (supacode uses a local socket — see `docs/cli-tool-install.md` §5 "CLI ↔ app communication"). More flexible (could return status, list sessions later) but more machinery, and needs its own launch-if-not-running story.

A URL scheme is likely the lightest first step for a one-way "create a session here" action; pick deliberately and note the choice. Whatever the mechanism, it is **orthogonal to the install plumbing** that #0249 delivered.

**Session creation at a path.** `AppStateStore.addSession(title:)` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:233`) does not currently accept a starting directory — new Sessions inherit CWD from the previously-focused Pane or fall back to `$HOME` (see `Concepts.md` "CWD inheritance"). This work needs a way to create a Session whose first Pane/Tab/Terminal Session spawns in an explicit directory. Reuse the existing `TerminalConfiguration.workingDirectory` path that Cmd-T / CWD inheritance already use, rather than inventing a parallel mechanism. The session-name cache (exact-path match) should then auto-apply any remembered name for that directory, which is a nice side effect.

**App activation / windowing.** Batty is single-window-by-default (PRD). `batty .` should bring the app to the front and create the Session in the key window (or a window if none is open). Decide whether it launches Batty when not running (a URL scheme gets this for free).

## Open questions

- If Batty is **not running**, should `batty .` launch it and then create the session, or print an error? (Launch-and-create is the friendlier behavior.)
- Non-directory / nonexistent path: error out on the CLI side (before involving the app), or let the app decide? Prefer validating on the CLI side and exiting non-zero with a clear message.
- Should `batty` with no args still print usage (current behavior), with `batty <path>` being the path form? A bare path that isn't a known subcommand should be treated as the session-create path.

## Relation

Follow-up to #0249 (CLI tool + install plumbing). #0249 deliberately shipped a minimal `version`/`help`-only command surface and called out defining real subcommands as separate work — this is that work.
