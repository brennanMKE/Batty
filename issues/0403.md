## Description

The user's proposal, second half (the first half is [#0402](0402.md)'s machine-readable tool definitions): define an agent skill for driving Batty, keep it as a subfolder of this repo, have `batty capabilities` tell people how to install it, and stamp the Batty version into the skill so an app update can prompt a skill refresh.

The gap it closes: `docs/batty-cli-agent-workflows.md` is good and current — target resolution order, the four `batty new` failure modes, `--unique` idempotency and its focus asymmetry, `notify`-vs-`focus`, the exit-code table with `batty new`'s exit-4 exception — but it only reaches an agent that happens to be working *inside this repo*, where CLAUDE.md points at it. Batty's actual audience is the opposite: an agent running in some unrelated project's Pane, holding `BATTY_*` env vars and a `batty` on `PATH`, with zero knowledge that the doc exists. #0402's JSON gives that agent the *signatures*; it cannot give it the *sequencing* — the knowledge that is procedural rather than schematic:

- Capture the id `pane split` prints and chain with `--pane`; never chain by focus (`docs/batty-cli-agent-workflows.md`, "Target resolution" and the split recipes).
- `--unique` is what makes a setup script re-runnable — and a `--unique` match, unlike a create, never moves focus (ibid., "Idempotent setup").
- `notify` tells, `focus` shows — and the focus verbs are the CLI's one sanctioned focus-stealing exception (ibid., #0257's amendment).
- `pane show` requires an explicit id because a hidden Pane has no shell a `batty` call could run from; get ids from `list --json`, which flags `"hidden": true` (ibid., "Cleaning up").
- `batty new`'s exit `4` means "poll timed out", not "rejected" — re-running creates a duplicate Session (ibid., "Failure handling").
- Never parse the plain-text `list` forms; `--json` only (ibid.).

There is no `.claude/skills/` directory in this repo today (verified 2026-09-09), and nothing anywhere distributes this knowledge with the app.

## Claude Code skill conventions (established against the official docs, 2026-09-09)

- A skill is a directory containing `SKILL.md` with YAML frontmatter (`name`, `description` — the description drives model-invocation matching; no frontmatter field is strictly required). Supporting files sit alongside and are referenced as relative markdown links. Guidance: keep `SKILL.md` under ~500 lines, push detail into supporting files.
- Locations: personal `~/.claude/skills/<name>/`, project `.claude/skills/<name>/`, or bundled in a plugin (`<plugin>/skills/<name>/`) distributed via a plugin marketplace.
- **Project skills auto-load only for that repository.** A skill committed to *this* repo's `.claude/skills/` reaches agents working on Batty itself — useful, but not the audience. Reaching an agent in an arbitrary project means installing into `~/.claude/skills/` (a copy step) or distributing as a plugin. "Installing the skill", per the user's proposal, is exactly that copy — which is what makes the version-coupling question below real: an installed copy is a snapshot that nothing refreshes.
- **No versioning or stale-skill mechanism exists in Claude Code** — no documented frontmatter `version` field with semantics, no update prompt, no auto-refresh. Whatever "prompt to update" means here, this project has to build it out of convention: text inside the skill, output from the CLI, or both.

## Expected behavior

1. A canonical Batty agent skill exists in this repo (the repo is the authoring source of truth), teaching an agent the sequencing knowledge above plus how to bootstrap: check `batty ping`/`batty status`, read `batty capabilities --json` first, and trust the live capabilities output over the skill's own text wherever they disagree.
2. A user can install it for all their projects with one obvious action, and the install path is discoverable from the CLI (see the placement question below).
3. The installed skill knows which Batty surface it was written against, and a mismatch with the installed Batty is *detected* — by the agent at session start, cheaply — rather than silently teaching flags an older app ignores or omitting verbs a newer app has.
4. `docs/batty-cli-agent-workflows.md` and the skill do not become two independently-maintained copies of the same prose; whichever relationship is chosen (supersede, package, generate) is recorded and enforced or at least drift-flagged.

## The sync mechanism — skill and app ship from the same tagged release

The user's design (2026-09-09): the skill carries the Batty version it was authored against, a mismatch against the installed app prompts the agent to update the skill, and the update comes **from the very same tagged GitHub release as the app** — "each release could add new CLI versions and options," so skill and CLI evolve together per release. The plumbing that makes this near-free already exists (each verified 2026-09-09):

- `scripts/tag-release.sh` reads `MARKETING_VERSION` from `Configuration/App.xcconfig` and tags `v<VERSION>` — its own header comment says why: "so the tag always matches what shipped" (`scripts/tag-release.sh:2-3`, extraction at `:41`; `MARKETING_VERSION = 1.1.0` at `Configuration/App.xcconfig:25`).
- The skill living in this repo means the same commit that adds a flag can update the skill, and the same tag publishes both. **Version equality between skill and app is then true by construction, not by discipline** — there is no separate skill release that can lag.
- `capabilities --json` already emits `cliVersion` (#0384), so the app-side comparison input exists today.

What this buys: the refresh source is a stable, predictable URL derived from nothing but the version — the agent (or the human it prompts) fetches the skill as it stood at tag `v<version>`, with no registry, no update server, and no "latest" ambiguity. And it makes the skill a **release artifact**: once the tag is the publication channel, a release that changes the CLI surface without touching the skill becomes a visible omission at tag time rather than silent drift — worth a preflight check in the release pipeline eventually (`scripts/` is a restricted area; that hook is decided with the user at implementation, not assumed here).

Still open, to be settled at implementation — stated plainly rather than hand-waved:

- **Older skill, newer app:** warn or hard-fail? Warn-and-defer-to-live-`capabilities` is the plausible default (the direction is mostly benign — see the failure modes below), but the threshold could reasonably harden across major versions.
- **App older than skill** (the user updated the skill but not the app): the skill now teaches flags the app silently ignores — the #0383 trap from the other side. Should the skill pin a **minimum app version** alongside its authored-against version, so this direction warns loudly rather than symmetrically?
- **When the check runs:** on skill load, on the first `batty` call of a session, or both? Load-time is earliest but runs even in sessions that never touch Batty; first-call keeps the cost where the risk is.

## The version-coupling failure modes (the subtle part — work these, don't restate the idea)

There are **three** artifacts that can skew, not two: the installed skill, the installed `batty` CLI binary, and the running app. The CLI and app normally travel together — the installed CLI is a symlink into the app bundle, and `resolveAppVersion()` reads `CFBundleShortVersionString` from two directories up (`BattyKit/Sources/batty/SessionCommand.swift:18-35`) — but the skew is not hypothetical: the Beta currently installed on this machine is CLI 1.1.0, which predates #0384, so `batty capabilities` there doesn't exist and falls through to the default `new` subcommand (observed live, 2026-09-09). And a bare SwiftPM-built binary reports `cliVersion: "unknown"` (observed live).

- **Skill older than app** — mostly benign: the agent misses new verbs/flags but everything it does still works. Self-healing *if* the skill's first instruction is "read `capabilities --json`; it outranks me" — the agent discovers the additions the skill doesn't mention (once #0402 makes flags discoverable at all).
- **Skill newer than app** — actively harmful, and it is exactly the #0383 shape: a skill that teaches `--unique` against an app predating the flag produces silent duplicate Panes, because the older app ignores the unknown request key (`issues/0383.md:52`). The skill telling the agent about a feature is precisely what turns "app lacks flag" from harmless into a trap. This direction is the one the coupling must catch.
- **Skill newer than the CLI binary** — worse than the above, because even the probe can misfire: on a pre-#0384 CLI, `batty capabilities` isn't a parse error, it's a `new` invocation with a bad path (exit 1). The skill's bootstrap text has to handle "the discovery verb itself is missing" without doing damage.

**Where the check belongs — candidates:**

- *In the skill*: the skill records the Batty version it was authored against; its bootstrap step tells the agent to read `batty capabilities --json`, compare versions, and on mismatch warn the human and prefer live output. Works with zero app changes and for every consumer, but only as well as agents follow instructions.
- *In `capabilities` output*: the app ships its own current skill (see placement below) and the payload names that skill's version, so an agent — or the skill's own bootstrap — can compare installed-copy vs shipped-copy directly. The app can never know what's in `~/.claude/skills/`; it can only state what it ships. Additive JSON only, per #0384's forward-compatibility rule.
- *Both*, which is likely where this lands: the skill carries the key and the habit of checking; the JSON carries the truth to check against.

**What "prompt to update" means when the consumer is an agent:** Claude Code will never prompt — there is no such mechanism (above). Concretely it can only mean: the agent's bootstrap comparison fails, and the skill instructs it to (a) tell the human in one line, (b) prefer live `capabilities` output for the rest of the session, and optionally (c) refresh `~/.claude/skills/` from the matching tagged release on GitHub — or from the app bundle's shipped copy, if bundling is chosen — if the human says yes. The tagged-release mechanism above makes a refresh source exist regardless of the placement decision below; bundling adds an offline local copy on top.

**Two distinct questions, one mechanism each (user decision, 2026-09-09 — this section as originally filed conflated them):**

1. *"Is my skill stale?"* — a **version comparison** answers this completely. The skill records the Batty version it was authored against; the agent compares it to the installed Batty's version; a mismatch means refresh. Staleness detection does not need to know *what* changed to know that *something might have* — and with the tagged-release sync above, "the versions match" genuinely means "authored against this exact surface."
2. *"What can this build actually do?"* — that is [#0402](0402.md)'s schema, and it is the authority **at call time regardless of skill freshness**. The skill's standing instruction — live `capabilities` output outranks the skill's own prose — holds even when the versions match.

These are complementary, not competing; the original filing answered (2) with (1)'s tool. A capability hash, floated in the filing as the "truthful key," would be **strictly worse for (1)**: it changes on every flag tweak and description edit, prompting refreshes for changes the skill's prose never covers (by design — the skill deliberately does not duplicate parameter rosters; see Notes), whereas the release version changes exactly when a new surface ships and names exactly which skill to fetch. The hash idea belongs, if anywhere, to #0402's capability-negotiation territory, not to staleness detection.

Operational caveats on the version key, kept from the filing's verification: `cliVersion` is `"unknown"` from a bare SwiftPM-built binary (observed live), and it describes the CLI binary rather than the answering app (`issues/0383.md:52`) — normally the same thing, since the installed CLI is a symlink into the app bundle (`SessionCommand.swift:18-35`), but when it matters that the *app* answered, the app's own version is `status --json`'s `appVersion` (#0361/#0384). The skill's bootstrap text should treat `"unknown"` as "cannot verify — warn and rely on live `capabilities` output," not as a match or a mismatch.

## Placement and install-instruction candidates (deliberately not decided here)

**Where the skill lives / installs from:**

- *Repo subfolder only* (`.claude/skills/batty/` here) — the user's suggestion, and right as the authoring source; also gives agents working on Batty itself the skill for free. Batty users don't have this repo checked out, so "install" means fetching from GitHub — which the tagged-release mechanism above turns from a weakness into the design: tag `v<version>` is the stable refresh origin, no clone required.
- *Shipped in the app bundle* (like the CLI itself, `Contents/Resources/`) — the app version and skill version then travel atomically, `Settings → Advanced` gains "Install agent skill" next to the existing "Install command line tool" (the established precedent for exactly this shape of install), and a stale `~/.claude/skills/` copy has a local source to refresh from. Repo stays the source; the build copies it in.
- *Plugin marketplace* — the formal distribution channel for third-party skills; heaviest, and adds an external moving part; probably later, not first.

**Where the install instruction appears (the user suggested `capabilities` print it):**

- The discovery argument is real: `capabilities` is the one verb an agent is told to run first, so a pointer there reaches the right reader at the right moment.
- The caution is also real: `capabilities`' plain output is parsed by nobody by contract, but #0384 pinned the output discipline for this CLI — JSON on stdout uncontaminated, prose separated — precisely because mixed output breaks `jq` pipelines (`issues/0384.md`, Notes). Any instruction line must never appear on the `--json` path's stdout; a structured field there (e.g. a skill source path) is fine.
- Candidates: a trailing line in the *plain-text* `capabilities` output only; a dedicated `batty skill` verb (`install`/`status`/`path`) mirroring how the CLI itself is installed; `--help` discussion text; Settings → Advanced UI only. Note new verbs auto-appear in the roster (`CapabilitiesCommand.verbs()` walks the tree — keep that property).

**What happens to `docs/batty-cli-agent-workflows.md`:**

- *Skill packages the doc* — SKILL.md is a thin bootstrap (identity, capability check, pointers) and the workflow prose ships as the skill's supporting file(s), sourced from the doc at build/copy time. Doc remains canonical; no second copy is hand-maintained.
- *Skill supersedes the doc* — the doc shrinks to a pointer at the skill. Honest, but in-repo readers lose the current single-page reference, and issue files cite the doc's sections by name.
- *Both maintained by hand* — the default failure mode, and a named drift hazard: the doc already drifted from shipped reality once (#0368 — the exit-code table was stale until derived from `XPCExitCode`). Two copies of sequencing prose drift faster. If this option is chosen anyway, it needs a drift check, not good intentions.

## Notes

- The skill's content should *not* duplicate what #0402 makes machine-readable: parameter rosters, enum values, and conflicts belong in the JSON the agent fetches live; the skill teaches sequencing, failure handling, and the bootstrap/version habit. That division is what keeps the skill small (the <500-line guidance) and slow-changing — the JSON churns with every flag; the sequencing knowledge has been stable across #0380–#0383.
- The skill is useful even before #0402 lands, and its staleness detection is truthful today: `cliVersion` is already in `capabilities --json`, which is all a version comparison needs. #0402 should still land first, for the actual reason: the schema is the call-time authority the skill's advice defers to — capability *negotiation* ("what can this build do") needs parameters in the payload, and today two builds with different flag rosters emit byte-identical capabilities JSON. Landing the authority before the document that points at it keeps the skill's "live output outranks me" instruction meaningful from day one.
- Prod installs `batty`, Beta installs `batty-beta` (`docs/batty-cli-agent-workflows.md`, Prerequisites) — the skill has to name both or resolve which is present, and a machine with both installed is a real case (this one, per the skew observation above).
- Scope guard: this is agent-facing documentation and distribution for the existing terminal-multiplexer CLI — no new pane content, no non-terminal viewers.

## Implementation decisions (2026-09-09, on `issue/0403`)

Recorded per the issue's own "deliberately not decided here" markers, resolved during implementation:

- **Skill location:** `.claude/skills/batty-cli/SKILL.md`, **repo subfolder only** — not bundled into `Batty.app`, not a plugin marketplace entry. Bundling would need real Settings → Advanced UI work (a second "Install agent skill" control alongside the CLI installer) and, eventually, an `Embed CLI`-style build-phase copy step; a plugin marketplace is heavier still. Both are legitimate follow-ups but out of scope for a documentation/distribution issue with a hard no-Swift-UI-work constraint on this pass. "Install" therefore means fetching the tagged directory from GitHub (see the skill's own "Refreshing this skill" section) rather than a local-bundle copy.
- **Doc-duplication:** the skill is a **condensed subset** of `docs/batty-cli-agent-workflows.md`'s sequencing sections, not a superset (bundling the doc verbatim) and not a replacement (superseding it). The doc stays canonical — issue files (`#0380`–`#0383`) already cite its section names, and it carries detail (the full `batty new`/URL trace, exact stderr wording) the skill deliberately omits to stay under the 500-line guidance. Each file now points at the other (`docs/batty-cli-agent-workflows.md`'s new top-of-file pointer; the skill's closing "Relationship" section). There is no mechanical drift check across two prose files — that would need a generator, which is a bigger change than this issue scoped — so the mitigation is: the doc is the tiebreaker on disagreement, and a same-repo edit changing sequencing behavior should update both files in the same diff. A release-time hook that could *flag* (not fully prevent) drift is described in the Notes bullet below; it was not built (`scripts/` is restricted).
- **Version-check design, all three open questions:**
  1. *Warn vs. hard-fail:* **always warn, never hard-fail**, in every direction (skill-older, skill-newer, unknown). The schema-authority rule (`inputSchema` always outranks this skill's prose) makes every direction recoverable — refusing to work over a version string mismatch would be more conservative than the actual risk (a silently duplicated Pane, recoverable via `list --json`) warrants.
  2. *Minimum app version pin:* **yes** — the skill states `Minimum compatible app version: 1.1.0` alongside its authored-against version. It doesn't escalate to a hard fail; it escalates the *dangerous* direction (installed app older than the skill) from a one-line warning to an instruction to verify every recommended parameter against that verb's live `inputSchema.properties` before using it, rather than trusting a recipe verbatim. Today both values are identical (`1.1.0`) since this is the skill's first version; a future skill update that adds a recipe depending on a not-yet-universal flag would bump the minimum independently of the authored-against version.
  3. *When the check runs:* **once per session, at the same moment as the bootstrap `capabilities --json`/`status --json` calls** the skill already mandates before any other verb — not separately at "skill load" (loading a markdown file is inert; nothing executes) and not before every subsequent `batty` call (unnecessary repeated cost for a value that doesn't change mid-session).
  - **`"unknown"` handling:** treated as a third state, not a mismatch — "cannot verify," with the same "trust live `inputSchema` for the rest of the session" instruction as a real mismatch, but no direction-specific warning since there's nothing to compare against. Verified live against the actual bare-SwiftPM-built binary in this worktree (see `## Verification` below): `batty capabilities` prints `batty unknown capabilities` and the fallback (non-git-clone) install text, exactly as designed.
  - **Three artifacts, not two (round-1 review B3):** the skill, the `batty`/`batty-beta` binary, and the app instance that actually answers XPC requests can all skew independently — normally the CLI binary and the answering app are the same version (the installed CLI is a symlink into the app bundle), but a stale running instance, or a machine with both Prod and Beta installed, can leave them apart. `capabilities --json`'s `inputSchema` describes only the CLI binary's own compiled-in surface — it is not proof the *answering app* honors a given flag, which is exactly the case the harm model (`--unique` against an older app) describes. The bootstrap now also runs `status --json` and compares its `appVersion` alongside `cliVersion`, and §1's version table states plainly that a flag appearing in `inputSchema` is not proof the app honors it.
- **Install-instruction placement:** a trailing block in **plain-text `capabilities` output only** (`CapabilitiesCommand.plainTextSummary`), not a new verb and not `--help`. Reasoning: `capabilities` is already the verb an agent/human is told to run first, so a pointer there reaches the right reader without adding CLI surface (a new `batty skill` verb would need its own schema entry, tests, and drift-gate); the plain-text/`--json` branches in `run()` are structurally separate code paths (`JSONEncoder` vs. this string), so the pointer text cannot reach `--json`'s stdout by construction — verified live: `capabilities --json`'s top-level keys are exactly `cliVersion`/`exitCodes`/`jsonSchemaDialect`/`verbs` (unchanged from #0402) and its stderr is 0 bytes.
- **`scripts/` hook (described, not built — restricted area):** a release-preflight check, most naturally a step `scripts/release.sh` or `scripts/tag-release.sh` runs before tagging, that fails the release when the CLI's command surface changed since the last tag (e.g., a diff of `batty capabilities --json`'s `verbs[]` between `HEAD` and the previous `vX.Y.Z` tag, or simpler, a git diff over `BattyKit/Sources/batty/*Command.swift` since that tag) but neither `.claude/skills/batty-cli/SKILL.md` nor `docs/batty-cli-agent-workflows.md` changed in the same range. This would make "a release that changes the CLI surface without touching the skill" (Notes, #0402's Relation) a visible preflight failure instead of silent drift, closing the loop the sync-mechanism section calls out as "worth a preflight check ... eventually." Not implemented here per the hard constraint on modifying `scripts/` without the user's go-ahead.

## Round-1 review (2026-09-09) — findings and fixes

Reviewer verified every schema-fidelity claim (flags/enums/exit codes against a real branch build), all three mutation results, exact-array-equality test style, and the two already-resolved open questions. Four blocking findings, all fixed on this branch:

- **B1 — the refresh recipe could destroy the user's skill with nothing to replace it.** `v1.1.0` is already tagged (predates #0403 by weeks — see `## Gotchas`) and can never be re-tagged onto this commit, so the original `rm -rf` before `cp -R` recipe would delete `~/.claude/skills/batty-cli` and then fail to restore it the first time this branch ships as a `1.1.0` build. Fixed in **both** `SKILL.md`'s "Refreshing this skill" snippet and `CapabilitiesCommand.skillInstallLines`: the fetch is staged to a `.new` suffix, the existing install is removed only after `[ -d ... ]` confirms the staged copy actually contains the skill, and the swap is `mv`, never a bare overwrite. `$tmp` is cleaned unconditionally. See `## Gotchas` for the `MARKETING_VERSION` implication.
- **B2 — the flagship `notify` recipe passed a Pane id to `--tab`, which resolves to `.unknownTab` and exits `4`.** The bug was inherited verbatim from `docs/batty-cli-agent-workflows.md`'s own "notify tells, focus shows" example — sharpest evidence yet that "the doc wins on disagreement" propagates errors as faithfully as truth (see N1 below). Fixed in **both** files: the example now omits `--tab` (falls back to `BATTY_TAB_ID`, then the focused Tab — what a script holding only a Pane id actually wants), and the surrounding prose in both files states that `--tab` takes a Tab id, not a Pane id.
- **B3 — the bootstrap collapsed three skewable artifacts to two and never consulted the answering app's own version.** `inputSchema` describes the CLI *binary's* compiled-in surface, not proof the app that answers XPC requests honors a given flag — the exact shape of the `--unique` harm model. `SKILL.md`'s §1 now also runs `batty status --json`, captures `appVersion`, compares both versions against the pin, and states explicitly that a flag in `inputSchema` is not proof the app honors it (the CLI-binary check and the answering-app check can now disagree, and the table says what to do when they do).
- **B4 — the mandatory `## Verification` section was missing** (referenced but never written). Added below.

Non-blocking items addressed: **N1** — a new drift test, `AgentSkillFlagDriftTests.everyFlagTheSkillShowsExistsOnItsVerbInCapabilities`, extracts every `batty <verb> --flag` invocation from `SKILL.md` and asserts it against `capabilities --json`'s live schema (mutation-tested: renaming `--unique` to a fabricated `--idempotent` in the skill's text turned the test red; reverted). **N2** — the refresh snippet in `SKILL.md` itself now guards `"unknown"` the same way the CLI's printed version does. **N4** — every recipe now resolves `BATTY=$(command -v batty || command -v batty-beta)` once in the bootstrap and invokes `"$BATTY"` thereafter, instead of a hardcoded `batty` that would be command-not-found on a Beta-only machine. **N5** — §6 now states `pane hide`'s exit-`4` refusal when the target is its Session's only visible Pane, and that generic "refresh topology" advice doesn't fix that specific cause. **N9** — "the four conflicts" now correctly scopes itself to `pane split`'s four, naming `new`'s fifth (`--json`/`--no-wait`) separately.

Deferred (reviewer's "as you see fit" bucket) with reasoning: **N3** is done (one sentence noting the minimum-version pin is vacuous while both values are `1.1.0`). **N6** (absolute GitHub URLs for `docs/…`/`#NNNN` cross-references) was not done — the skill's own repository-URL constant already gives an agent enough to resolve `github.com/brennanMKE/Batty/blob/v<version>/docs/...` by hand if it ever needs to, and rewriting every internal cross-reference as an absolute URL throughout the skill risked introducing exactly the kind of hand-maintained, untested duplication this issue is trying to avoid elsewhere. **N7** (no test ties the repository URL together across its three occurrences) and **N8** (the known-version branch of `plainTextSummaryAppendsTheSkillBlockExactlyOnceAfterExitCodes` is never exercised end-to-end because SwiftPM test binaries always report `"unknown"`) are real, narrow gaps, left for a follow-up rather than this pass — see `## Gotchas`.

## Gotchas

- **`v1.1.0` is already tagged (commit `1c6bd29`, 2026-08-21, pushed to public origin) and predates `capabilities`, #0402's schema, and this skill entirely** — `git ls-tree -r v1.1.0 -- .claude` is empty. `MARKETING_VERSION` is still `1.1.0` on this branch, so version equality does not yet mean "authored against this surface"; it will once a release bumps `MARKETING_VERSION` and re-tags. Shipping this branch as an actual release requires bumping `MARKETING_VERSION` first — printing an install command that resolves to `v1.1.0` before that bump would clone a tag missing the skill (caught by B1's non-destructive fix, but still worth avoiding by sequencing the version bump before release).
- The project-scoped copy at `.claude/skills/batty-cli/` auto-loads for any agent working on Batty itself (this repo), in addition to being the thing an external install copies — the same file serves both audiences without extra plumbing.
- Only a live install can confirm three things this implementation pass could not test: that Claude Code actually picks up a skill installed via a plain `cp -R` into `~/.claude/skills/`; that the `description` frontmatter triggers on an organic prompt like "split a pane in Batty" rather than only on an explicit `batty` mention; and that an agent given this skill actually performs the mandatory bootstrap call before its first mutating verb. That last one is the design's single point of failure — the whole version-coupling mechanism depends on an agent following a written instruction — and it's untestable from a worktree with no live Claude Code session to observe.
- **N7/N8 (deferred, not built):** the GitHub repository URL is a literal in three places (`CapabilitiesCommand.skillRepositoryURL`, and duplicated as prose in `SKILL.md`'s own refresh snippet) with nothing asserting they agree if one is ever edited without the other. And `plainTextSummaryAppendsTheSkillBlockExactlyOnceAfterExitCodes` calls `CapabilitiesCommand.buildPayload()`, which reports `cliVersion == "unknown"` in every CI/test environment (no app bundle), so the ordering test's own "known version" formatting is only exercised by the separately-parameterized `skillInstallLinesForAKnownVersionCloneTheMatchingTag` test, never end-to-end through `plainTextSummary` itself.

## Round-2 review (2026-09-09) — findings and fixes

Two blocking findings, both fixed on this branch, plus the exact-array test each affects:

- **R2-B1 — `status --json` does not put `appVersion` at the top level.** `SKILL.md`'s bootstrap comment and prose said "capture .appVersion", but `StatusJSONPayload`'s top-level keys are `state`/`exitCode`/`status` (`message` on failure only) — `appVersion` is nested under `status`.
