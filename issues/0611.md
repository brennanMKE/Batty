## Description

**HIGH (inferred). Related to #0601, #0602 and #0604.** Model-initiated terminal focus still has view-side writers keyed on observed flips: each terminal `TerminalPlaceholderView` in `PaneView` calls `TerminalSurfaceFocuser.focusWhenReady(tab:)` from `.onAppear`, `.onChange(of: pane.activeTabID)` and `.onChange(of: isPaneFocused)`. None of them checks that the Pane's Session is selected, and every Session stays mounted (#0604). `focusWhenReady` bumps one process-wide `generation`, which cancels every in-flight promotion. So a focus move or a new Pane in a **non-selected** Session — for example a CLI/XPC `split` aimed at a background Session's focused Pane (allowed by #0257, which moves that tree's focus to the new Pane) — cancels the selected Session's retry ladder. If that happens in the 16–800 ms after a Session switch, while the selected terminal is still hidden waiting for placement, the new ladder targets a hidden view, `focus(tab:)` keeps returning false, and the selected terminal never becomes first responder until the user clicks.

Since #0602, `WindowRuntime.selectedSessionID`'s `didSet` also issues focus (`applySelectionEffects` → `focusTerminal`). So the model-initiated direction now has two writers on different triggers: the selection action and these view handlers.

## Resolution notes

> 🟢 Resolved 2026-11-13 — model-initiated terminal focus now has one writer, `WindowRuntime.requestTerminalFocus`, gated on the window's selected Session and keyed per window; `PaneView`'s three inferred focus handlers are gone.

## Root cause

Model-initiated terminal focus was written from three `PaneView` callbacks (`.onAppear`, `.onChange(of: pane.activeTabID)`, `.onChange(of: isPaneFocused)`) in every mounted Session, keyed on observed flips and never checking that the Pane's Session was selected, while `WindowRuntime.applySelectionEffects` was a second writer. Every `focusWhenReady` bumped one process-wide generation, so a focus move in a background Session (e.g. an XPC `splitPane` aimed at its focused Pane) cancelled the selected Session's retry ladder. The lost-focus outcome is inferred from the code (timing-dependent); not reproduced.

## Fix

Followed the plan. One writer, `WindowRuntime.requestTerminalFocus(_:inSession:)`, which issues only when the Session is the window's selected Session, reached from:
- `SplitTree.focusedPaneID`'s `didSet` and `PaneRuntime.activeTabID`'s `didSet` (via the new `weak var tree` back reference and `SplitTree.activeTabDidChange(in:)`), through `SplitTree.focusIntentHandler`, which only `applyTerminalVisibility` sets (selected tree) and clears (deselected tree), next to `isInSelectedSession`;
- `focusSelectedTerminal()`, called by `applySelectionEffects` and by `AppStateStore.registerNSWindow` on a window's first registration (launch / New Window first mount).

`TerminalSurfaceFocuser` keeps its ladder but keys the generation per `WindowID` (`generations`, `generation(for:)`, `forgetWindow(_:)`, the last called from `tearDownForWindowClose()`). `focusTerminal` is now assigned in `init` with the window's id. The three `PaneView` handlers are deleted. Stale comments fixed (`TerminalSurfaceFocuser`, `selectedSessionID` doc, `addTab(toPaneID:)`, `PaneView` x2, `WindowIDRegistrar`/`RegistrarNSView`, the #0332 B4 note moved to `focusSelectedTerminal`), and the Model-initiated bullet in `docs/swiftui-observation-rules.md` names the single writer. No new `Task`/main-queue hop.

Divergence: `SessionDetailLayoutConvergenceTests.terminalPlacementWriteMarksNoViewAsNeedingUpdateConstraints` now resigns first responder (`makeFirstResponder(nil)` + settle) before measuring (see Gotchas).

### Design decision: model choke points, not one call per action

More than 30 sites write `SplitTree.focusedPaneID` or `PaneRuntime.activeTabID` with the meaning "show and focus this":
- menu commands (`BattyCommands`);
- shortcuts (`BattyShortcuts`);
- `SessionDetailView`'s split buttons;
- `PaneView`'s chip binding and "+";
- `PaneFocus`, `PaneLayout`, `UITestDriver` and XPC;
- `WindowRuntime`/`AppStateStore` actions.

Many of them call `tree.splitFocusedPane` or `pane.addTab` directly. Adding a focus call at each site would leave a lost-focus bug at every site that gets missed. So the plan follows the pattern #0602 (`selectedSessionID`'s `didSet`) and #0605 (`PaneRuntime.activeTabID`'s `didSet` → `moveShown`) already use: the model's own setter is the single funnel. It runs synchronously inside whichever action wrote it, so intent still comes from the action, not from an observed flip in a view. The setter forwards to **one** `WindowRuntime` method, and that method decides whether the request goes through.

Single writer of the model-initiated direction after the fix: `WindowRuntime.requestTerminalFocus(_:inSession:)` → `focusTerminal` seam → `TerminalSurfaceFocuser.focusWhenReady(tab:in:)`. It has four callers:
1. `SplitTree.focusedPaneID`'s `didSet`;
2. `PaneRuntime.activeTabID`'s `didSet` (via the tree);
3. `selectedSessionID`'s `didSet` (`applySelectionEffects`);
4. first registration of a content window.
