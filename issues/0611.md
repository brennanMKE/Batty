# 0611 — PaneView infers terminal focus from onAppear and onChange in every mounted Session, and those calls can cancel the selected Session's focus promotion

## Description

**HIGH (inferred). Related to #0601, #0602 and #0604.** Model-initiated terminal focus still has view-side writers keyed on observed flips: each terminal `TerminalPlaceholderView` in `PaneView` calls `TerminalSurfaceFocuser.focusWhenReady(tab:)` from `.onAppear`, `.onChange(of: pane.activeTabID)` and `.onChange(of: isPaneFocused)`. None of them checks that the Pane's Session is selected, and every Session stays mounted (#0604). `focusWhenReady` bumps one process-wide `generation`, which cancels every in-flight promotion. So a focus move or a new Pane in a **non-selected** Session — for example a CLI/XPC `split` aimed at a background Session's focused Pane (allowed by #0257, which moves that tree's focus to the new Pane) — cancels the selected Session's retry ladder. If that happens in the 16–800 ms after a Session switch, while the selected terminal is still hidden waiting for placement, the new ladder targets a hidden view, `focus(tab:)` keeps returning false, and the selected terminal never becomes first responder until the user clicks.

Since #0602, `WindowRuntime.selectedSessionID`'s `didSet` also issues focus (`applySelectionEffects` → `focusTerminal`). So the model-initiated direction now has two writers on different triggers: the selection action and these view handlers.

## Current state (verified 2026-11-12 on `main` `ce66ca6a`)

- `BattyKit/Sources/BattyKit/Views/PaneView.swift:339-350`: `.onAppear { guard tab.id == pane.activeTabID, isPaneFocused …; focusWhenReady(tab:) }`, `.onChange(of: pane.activeTabID)`, `.onChange(of: isPaneFocused)` — each guards only on the Tab being active and the Pane focused **within its own tree**. `isSessionSelected` (`:16`) is not consulted.
- `Commands/TerminalSurfaceFocuser.swift:57`: `private static var generation = 0`; `:78-100` `focusWhenReady` increments it and runs a 6-step ladder (0, 16, 50, 150, 400, 800 ms), abandoning when `requested != Self.generation`; `focus(tab:)` (`:40-48`) returns false when the view is hidden.
- `Runtime/WindowRuntime.swift:159`: `@ObservationIgnored var focusTerminal: (TabRuntime) -> Void = { TerminalSurfaceFocuser.focusWhenReady(tab: $0) }`; called from `applySelectionEffects` (`:1070-1093`, at `:1089`).
- `Runtime/AppStateStore.swift:783-819`: `splitPane(id:…)` targets background Sessions without touching `selectedSessionID`.
- Stale comment: `TerminalSurfaceFocuser.swift:59-66` says "All call sites are SwiftUI-driven callbacks (`onChange` / `onAppear`)"; `WindowRuntime.applySelectionEffects` is now an event-origin call site. `WindowRuntime.swift:66-72` relies on "`PaneView`'s terminal `onAppear` focuses the mounted Session's focused Tab" for the init case.

## Rule violated

- `docs/swiftui-observation-rules.md`, "Two-way model ↔ AppKit sync": each direction gets exactly one declared writer; an observed property is evidence that something changed, not evidence of intent — route intent from its source.
- swift-guidance `swiftui-observation.md`: don't reconstruct intent in `onChange`; drive side effects from the action.

## Evidence

- **Proven:** the three handlers lack a selected-Session check; the generation is global; #0602 added a second writer.
- **Inferred:** the lost-focus outcome; needs the timing above. Not reproduced.

## Fix direction (restructure write ownership; no new `Task` hop)

- Route focus intent from the actions, as #0602 did for selection: the writers of `activeTabID` and `focusedPaneID` that mean "focus this" (`addTab`, `selectNext`/`selectPrevious`, `focusPane`, `jumpToTab`, tab-bar selection, splits) call one `WindowRuntime` method (e.g. `focusIntent(tab:)`) that runs `focusTerminal` only when the Tab's Session is selected in its window (and the window is the one being acted on).
- Delete the three `PaneView` handlers. Cover first mount (new window, new Session, new Tab) with an event-origin call from the code that creates it.
- Consider keying `generation` per window so another window's intent can't cancel this one's.
- Update the stale comments named above.
