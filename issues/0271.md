## Description

Third step of the XPC track under umbrella #0265: connect the three processes and land the first verb that returns real data and a real exit code — the proof that the hybrid works. This is the capability the URL scheme cannot provide at any price: today a `batty /valid/dir` reaching a running-but-broken Batty still exits 0 (`docs/batty-cli-install.md` §"Known limitations"), because success only means LaunchServices accepted the URL.

**Gate:** blocked on #0270 (broker agent). This child is the payoff the whole track was green-lit for; if the track was gated on "the first command genuinely needs a reply," this is that command.

## Resolution notes

> 🟢 Resolved 2026-07-25 — the three processes connect end to end and `batty status` returns real app state with a real exit code. The URL scheme's "exits 0 even when the app is broken" limitation is closed for XPC-tier verbs.

Live end-to-end behavior against a *running* app is **not** verified — see Verification. A fail-closed guard now blocks Beta from overwriting Prod's broker registration; the underlying variant-naming decision is still open for the user.

## Root cause

Starting state, not a defect. `batty <path>` over the URL scheme exits 0 whenever LaunchServices accepts the URL, even if the app is running but broken — recorded as a known limitation in `docs/batty-cli-install.md`. Closing it requires a reply channel, which is what this child builds.

## Fix

**App side** (`BattyKit/Sources/BattyKit/XPC/`): `AppXPCService`, a `nonisolated final class` exporting `AppServiceProtocol`, dispatching on `XPCRequest.verb` and hopping to `@MainActor` to read `AppStateStore.shared.statusPayload()`. `AppXPCListenerDelegate` mirrors the broker's pattern including the load-bearing `as any AppServiceProtocol` cast at the assignment. `AppXPCCoordinator` creates the anonymous listener at launch and registers its endpoint with the broker — flipping `isRegisteredWithBroker` only inside a subsequent `brokerPing` reply, never off `registerAppEndpoint` returning, since one-way calls give no delivery confirmation.

**CLI side**: the five-step connect dance — broker connect, endpoint fetch, launch by bundle id if nil, bounded poll, then a direct `NSXPCConnection(listenerEndpoint:)` with the broker out of the path. `batty status` reports pid, uptime, and window/session/tab counts, with exit codes 0/2/3/4 from #0269's vocabulary.

**Shared** (`BattyXPCCore`): `StatusPayload`, `XPCVerb.status`, `ServiceNames.appBundleIdentifier`, plus two extractions made for testability — `BoundedPoll` (generic bounded retry with an injectable `sleep`) and `XPCOnce<Value>` (a resume-once wrapper, now shared rather than duplicated).

**Cross-variant guard:** `AppXPCCoordinator.start()` returns early with a logged notice when `Bundle.main.bundleIdentifier != ServiceNames.appBundleIdentifier`, positioned before the listener is created and therefore before any registration call.

## Review

Reviewed by `claude-opus-5`, two rounds.

Round 1 judged the core engineering sound and requested two changes. The audit work behind that judgement is worth recording: the reviewer enumerated **all 12** Foundation-supplied handler closures in the diff rather than spot-checking, confirming each carries `@Sendable`; proved `XPCOnce` safe against double-resume (flag under `NSLock`, single `signal()`), neither-fires (bounded by timeout), and main-thread deadlock (`NSXPCConnection` delivers replies on its own private queue); traced reply-exactly-once through every path in `perform`, including app-mid-quit, where the client's 3s timeout yields a clean exit 3 rather than a hang; and checked the `AppStateStore` changes against `docs/swiftui-observation-rules.md`, finding `statusPayload()` reads only a `let` and an `@ObservationIgnored` property and so touches zero observed state.

The two required changes were the CLI connect path having **no logging at all** — leaving the half of the handoff that decides between exit 2, 3, and 4 invisible to `log stream`, precisely during the failure paths this child exists to make debuggable — and a **fail-closed guard**, because this child turns the cross-variant hazard from a read into a write.

Round 2 approved. The reviewer captured the unified log themselves rather than trusting the report, re-verified two isolation guards under forced recompilation, and scrutinized the one round-2 change with real regression potential (the `resolveEndpoint` short-circuit on failed launch), concluding it is safe: `open -b <id> -g` returns 0 for an already-running or already-launching app, so the nil-then-endpoint race the dance depends on is entered with a zero exit and the poll still running; a nonzero exit means LaunchServices refused, which cannot subsequently produce a registration.

## Gotchas

- **The cross-variant hazard is now a write, and the guard is a stopgap.** #0270 recorded the read-only version (a Beta CLI reporting "reachable" for Prod). This child made the app *register*, so without the guard, launching Beta would call `registerAppEndpoint` on Prod's broker and **replace Prod's stored endpoint** — after which `batty status` drives Beta and Prod's registration stays dead until Prod is relaunched, silently. The guard converts that into an explicit logged no-op. **The real decision — whether Beta gets a suffixed broker identity or keeps being excluded — remains open for the user** and is unchanged by this fix.
- **The dance's worst case is ~24.8 s, not ~5 s.** Each of 20 poll attempts can itself block up to 1.0 s on `XPCOnce.wait` against a *wedged* broker (connectable but non-replying), plus 19 × 250 ms of sleep. Still bounded and still not a hang, but the original comment understated it and the numbers are load-bearing in a file whose purpose is boundedness.
- **`XPCOnce.wait(timeout:)` blocks the calling thread and must never be called from the main actor.** It lives in shared `BattyXPCCore`, which the GUI app links, so a future app-side caller could freeze the UI. Documented in the file.
- **Exit code 4 is nearly unreachable for `status` specifically**, because the app always handles that verb; it becomes live with #0274's verbs. That is correct behavior, not a gap.
- **Mid-poll broker-unreachable is deliberately folded into "keep retrying"** rather than failing fast — a scope call handed to #0272's lifecycle hardening.
- **The wired-together dance is not unit-tested** — only `BoundedPoll` is, since the poll step calls `BrokerAppEndpointClient.fetchEndpoint` directly rather than through an injected seam. Steps 1–5 in combination are covered only by the live checks above.
- **`Logging` now exists in three near-identical copies** (`BattyKit/Util/`, `BattyBroker/`, `batty/`). All three consumers link `BattyXPCCore`, so it could collapse to one declaration there with identical per-process behavior. The duplication follows #0270's precedent and is defensible; worth folding into a future cleanup.

## Scope

1. **App-side anonymous listener** (`NSXPCListener.anonymous()`) and registering its endpoint with the broker at app launch.
2. **The CLI's five-step connect dance**, exactly as validated:
   1. connect to the broker's Mach service (launchd starts the agent on demand),
   2. ask the broker for the app's endpoint,
   3. if `nil`, launch the app by bundle identifier,
   4. **poll** the broker until the app registers (registration races launch),
   5. open `NSXPCConnection(listenerEndpoint:)` directly — the broker is out of the path from here.

   **The bounded poll loop (~30 lines) is load-bearing:** without the bound, a broken app hangs the CLI forever; without the retry, a nil endpoint immediately after launch reads as failure when it is normal. Performance reference point: measured cold start with the app not running was **0.284 s total, one 250 ms poll** (RemoteControl #0010).
3. **`batty status`** — returns real app state (the experiment returned pid, uptime, window count, client count, broker registration state out of the live process; round trip measured at 0.3 ms). Batty's equivalent should report at least pid, uptime, and window/session counts. Exit codes per the #0269 vocabulary: `0` success, `2` broker unreachable, `3` app unavailable, `4` request failed.
4. **Logging:** app-side listener code and the CLI connect path join the shared `Logging.subsystem` from the first commit — `log stream` on the shared subsystem is the only practical way to watch a handoff.

## Traps that apply here (copied — the expensive part)

- **The `@Sendable` SIGTRAP crash (RemoteControl #0016) — a near-certainty for Batty, and the single highest-value thing to carry over.** Batty builds with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` (`Configuration/Build.xcconfig`). On such a target, closures passed to `remoteObjectProxyWithErrorHandler`, `interruptionHandler`, and `invalidationHandler` inherit main-actor isolation, because Foundation types those parameters as plain non-`Sendable` closures. Swift emits an isolation assertion at the closure's entry; XPC calls it on its own queue; the process dies with `EXC_BREAKPOINT / SIGTRAP`. **There is no compiler warning — strict concurrency is fully satisfied.** The fix is marking each closure `@Sendable`. The worst part: the crash happens *inside the handler that would have logged the error*, so failures produce no output at all. Every Foundation-supplied handler closure written in this child gets `@Sendable`; the exhaustive audit is #0272, but do not knowingly ship one without it here.
- **Reply blocks in project-owned protocols are already `@escaping @Sendable`** (#0269) — keep that discipline for any protocol added here.
- **One-way calls give no delivery confirmation.** `registerAppEndpoint` returns `Void` whether or not the broker received it. The app must confirm registration with a subsequent round trip, never by the call returning.
- **An `NSXPCListenerEndpoint` is a live Mach right, not data** — it can only travel over an existing XPC connection. Do not attempt to persist or print it.
- **Deliberately trigger the failure paths during verification.** The experiment's two most expensive defects (the SIGTRAP above, and a memory blow-up in a read loop) were invisible to a passing build and a successful happy-path test.

## Out of scope

- Lifecycle hardening — broker restarts, `kill -9` reaping, app-quit notification, concurrent clients, the `SMAppService` repair path (#0272). This child may keep minimal handlers, but the distinct interruption/invalidation responses are #0272's acceptance criteria.
- Read verbs beyond `status` (`list`, topology) and the Option B decision (#0274).
- Streaming, events, long-lived sessions — **explicitly deferred at the umbrella level; no child exists for them by design.**
- Changes to existing `batty://` verbs — Tier 0/1 mutations stay on the URL scheme, unchanged.
