## Description

Today Batty's keyboard shortcuts are hardcoded in `BattyShortcuts.handle(_:)` (the NSEvent monitor) and in `BattyCommands` (the menu bar). Users can't change them — if their muscle memory says `Cmd-T` should be "New Session" instead of "New Tab", they're stuck.

Add a **Shortcuts** pane to the Settings window where each customizable hotkey is a row with the action name, a click-to-record recorder showing the current binding, and a per-row Reset button. A "Reset All to Defaults" button sits at the bottom. Persist via `UserDefaults` so customizations survive restart.

## Reference implementation

The companion **Issues** app at `../Issues` has a mature, working implementation we should mirror. The relevant files:

- `../Issues/Issues/Views/Settings/ShortcutsSettingsView.swift` — the pane root.
- `../Issues/Issues/Views/Settings/ShortcutRow.swift` — one row per action with collision/reserved warnings.
- `../Issues/Issues/Views/Settings/KeyboardShortcutRecorder.swift` — `NSViewRepresentable` wrapper.
- `../Issues/Issues/Views/Settings/RecorderView.swift` — `NSView` subclass that captures `keyDown` while focused; rejects bare characters; handles `performKeyEquivalent` so menu shortcuts don't preempt while recording.
- `../Issues/Issues/State/ShortcutBinding.swift` — Codable `{ key, modifiers }` with a `displayString` (e.g. `⌘⇧→`) and `keyboardShortcut: KeyboardShortcut` accessor.
- `../Issues/Issues/State/ShortcutAction.swift` — the catalog enum.
- `../Issues/Issues/State/ShortcutsStore.swift` — `@Observable @MainActor` store, JSON-encoded blob in `UserDefaults` key `keyboardShortcuts`. Knows collisions and a small set of reserved combos (Cmd-Q, Cmd-H, Cmd-M, Cmd-Tab).

We can copy the pattern almost verbatim. Differences:

- Batty's logger subsystem is `Logging.subsystem` (already standard in this repo). Match.
- Batty doesn't have an `appBackground` color in previews — use whatever exists or skip the colored backgrounds.
- The Issues app has its own `AppCommandsController.shared.shortcuts` to host the store; Batty already has `WorkspaceManager.shared.store` for the AppStateStore. The shortcuts store should be its own singleton or attached to `WorkspaceManager` (separate concerns from session state — recommend its own singleton or attached to a small helper).

- `BattyKit/Sources/BattyKit/Shortcuts/ShortcutsSettingsView.swift` — copy; same color/preview adjustments as above.

Suggest putting them in a `Shortcuts/` subfolder under `BattyKit/Sources/BattyKit/` for organizational clarity. The package uses `PBXFileSystemSynchronizedRootGroup` so the subfolder is fine. For BattyKit (a Swift Package) the directory structure within `Sources/BattyKit/` doesn't matter to the build — just make sure new files are inside that directory.

### Wire-up changes

1. **`BattyShortcuts.swift`** — rewrite the `handle(_:)` to dispatch based on store bindings instead of hardcoded patterns. Pseudocode:

```swift
public static func handle(_ event: NSEvent) -> Bool {
    let store = ShortcutsStore.shared
    let mods = SwiftUI.EventModifiers(rawValue: ...)  // translate NSEvent flags
    let key = ...  // translate event to a key string matching ShortcutBinding.key
    let candidate = ShortcutBinding(key: key, modifiers: mods.rawValue)

    for action in ShortcutAction.allCases {
        if store.binding(for: action) == candidate {
            run(action)
            return true
        }
    }
    return false
}

private static func run(_ action: ShortcutAction) {
    let store = WorkspaceManager.shared.store
    switch action {
    case .newSession: store.addSession()
    case .closeTab: store.closeFocusedTab()
    case .newTab: store.selectedSession?.focusedPane.addTab(inheritingCWDFrom: ...)
    // ... etc.
    }
}
```

The match check should be exact (key + modifiers). EventModifier translation needs to match what `RecorderView` writes (lowercased key, modifiers bitfield).

2. **`BattyCommands.swift`** — the menu items still need `.keyboardShortcut(...)` modifiers for *display* in the menu bar (so users see the current binding next to each menu item). Read from the store:

```swift
Button("New Session") { store.addSession() }
    .keyboardShortcut(ShortcutsStore.shared.keyboardShortcut(for: .newSession))
```

Note: menu's `.keyboardShortcut` is shown in the menu but the actual key handling goes through `BattyShortcuts.handle`. The menu shortcut is partly decorative + click target. Be aware of the focus issue from `#0062` — the menu shortcut may not fire when terminal has focus, but the NSEvent monitor catches all cases.

3. **`SettingsView.swift`** — add a new `TabItem` for Shortcuts:

```swift
ShortcutsSettingsView()
    .tabItem { Label("Shortcuts", systemImage: "keyboard") }
```

### Reserved shortcuts

Batty's reserved set should match Issues' plus our own:
- `Cmd-Q`, `Cmd-H`, `Cmd-M`, `Cmd-Tab` (macOS-reserved).
- `Cmd-,` (Settings) — also reserved.

Don't include Cmd-1..9 in the reserved list — they aren't reserved by macOS; we just chose not to make them customizable.

### Persistence and migration

First-time launch: no `keyboardShortcuts` key in UserDefaults. The store falls back to defaults via `loadFromDefaults`. No migration needed.

If a user has set custom bindings and we later add a new `ShortcutAction` case, `loadFromDefaults` fills missing cases with `defaultBinding`. Unknown keys are ignored (forward-compat).

### Tests

Port the Issues app's `ShortcutsStoreTests` if it exists. At minimum:

- Round-trip a binding through UserDefaults: set, recreate the store with the same UserDefaults instance, assert it loaded.
- `collisions(_:excluding:)` returns the expected actions when two are bound to the same combo.
- `isReserved(_:)` returns true for Cmd-Q.
- `resetToDefault(_:)` flips a customized binding back to its default.
- `resetAllToDefaults()` clears all.

Use a temp `UserDefaults(suiteName:)` per test to avoid polluting the user's real defaults.

## Acceptance criteria

- Settings has a new "Shortcuts" tab listing each of the 13 customizable actions.
- Each row shows the action name, current binding (or "Click to record"), a recorder, and a Reset button.
- Clicking the recorder focuses it with an accent ring; the next non-modifier `keyDown` writes a new binding.
- Esc cancels recording without clearing the binding.
- Reset returns one row to its default; "Reset All" returns all rows.
- Collisions (two actions bound to the same combo) show a warning row.
- Reserved combos (Cmd-Q, Cmd-H, Cmd-M, Cmd-Tab, Cmd-,) show a warning row and are saved anyway (user can pick a non-reserved combo, matching Issues' behavior).
- After saving a new binding, the corresponding action fires when the user presses the new combo from terminal focus (via `BattyShortcuts.handle`).
- The menu bar shows the current binding next to each action's label.
- Bindings persist across restart via `UserDefaults`.

## Out of scope

- Allowing user customization of `Cmd-1..9` and `Cmd-Option-1..9` (positional tab/session selection).
- Adding new actions beyond the v1 catalog.
- Multi-keystroke chords (e.g. `Cmd-K Cmd-T`). v1 is single-combo only.
- Import/export of shortcut sets.
- Live preview in the recorder while the user holds modifiers (the Issues app doesn't do this either — it commits on key-down).

## Notes

- The Issues app's `RecorderView.performKeyEquivalent` override is important — without it, menu shortcuts would intercept the recording attempt (`#0062` symptom from the other angle). Port it verbatim.
- `BattyShortcuts.handle` is the load-bearing key dispatcher per the `#0062` fix — keep that monitor in place, just have it read from the store.

## Root cause

Keyboard shortcuts were hardcoded in two places — the NSEvent monitor (`BattyShortcuts.handle`) and the menu bar (`BattyCommands`). There was no Settings affordance for users to customize them.

## Fix

Ported the Issues app's `ShortcutsStore` pattern under `BattyKit/Sources/BattyKit/Shortcuts/`. Introduced a 13-case `ShortcutAction` catalog and a JSON-backed `ShortcutsStore` singleton persisted in `UserDefaults` under `co.sstools.Batty.keyboardShortcuts`. `BattyShortcuts.handle` now translates each `NSEvent` into a candidate `ShortcutBinding` (mirroring `RecorderView.makeBinding`) and matches against the store; menu items in `BattyCommands` use `.keyboardShortcut(ShortcutsStore.shared.keyboardShortcut(for:))` so the menu shows the live binding. A new Shortcuts pane in `SettingsView` lets users click-to-record per-action, with per-row Reset and a Reset All button.

`Cmd-1..9`, `Cmd-Option-1..9`, `Cmd-C`, and `Cmd-V` remain hardcoded by design — positional/pasteboard standards. Reserved combos (`Cmd-Q`/`H`/`M`/`Tab`/`,`) are still saved when chosen but surface an inline warning; the user can pick another combo or hit Reset.

## Gotchas

- Menu `.keyboardShortcut(...)` is partly decorative; the NSEvent monitor in `BattyShortcuts.handle` is the load-bearing dispatcher (matches the `#0062` design). The menu shortcut still updates live whenever the store changes because SwiftUI re-evaluates the Commands body.
- Reserved combos are saved anyway so the warning row appears (matches Issues' behavior); the user can pick something else or hit Reset.
- `Cmd-1..9`, `Cmd-Option-1..9`, `Cmd-C`, and `Cmd-V` are intentionally NOT customizable in v1.
- The recorder rejects bare character keys (`t` with no modifier) so user customization can't shadow text input. Special keys (arrows, return, etc.) are accepted bare.
- Manual verification not done here. Recommended: Settings → Shortcuts, change Close Tab to a new combo (e.g. `Cmd-K`), confirm the new combo closes the tab, confirm the old `Cmd-W` no longer does. Reset and confirm `Cmd-W` works again. Also confirm the menu bar's Tab → Close Tab label updates to show the new combo.
