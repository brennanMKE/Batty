## Description

Five BattyKit unit tests pass alone but fail in a full `./build.sh unit` run when the host is loaded, so issue branches that never touch their code fail the per-commit unit tier. Three are in `SharedProjectImagesTests`, one in `LMStudioDashboardPaneContentTests`, and one in `ProcessFollowByNameTests`. Each depends on wall-clock time or on the shared main actor in a way `AGENTS.md` "Asynchronous tests" rules out. This is the same family as #0672 (`MCPServerTests`), but different code; #0672 stays separate.

Failing tests (2026-11-18):

- `SharedProjectImagesTests/aPickDuringADownloadWins()`
- `SharedProjectImagesTests/aSlowReadDoesNotHoldTheMainActor()`
- `SharedProjectImagesTests/openingAPendingProjectDoesNotWaitForTheTransport()`
- `LMStudioDashboardPaneContentTests/tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM()`
- `ProcessFollowByNameTests/theRealEnumeratorFindsAUniquelyNamedProcessAndItsReplacement()`

## Steps to reproduce

1. Load the host: on 2026-11-18, a deliberate 8× `yes > /dev/null` load in the #0672 worktree, or ordinary load from other worktree builds plus a Tart VM.
2. Run the whole suite with `./build.sh unit`.
3. Seen:
   - `.claude/worktrees/issue-0672/build/checks/unit-20261118-203755-70712.log.failures.txt`: all three `SharedProjectImagesTests` with `no read reached the gate` (`SharedProjectImagesTests.swift:21`), and the LM Studio test at `LMStudioDashboardPaneContentTests.swift:866`, `:874`–`:877`.
   - The #0664 review re-run (`issues/0664.md` Work log, 2026-11-18): `CHECK UNIT: FAILED (1 test)` on `theRealEnumerator…`. Its digest was not kept, so the failing line is unknown.
4. Each suite passes alone.

## Expected behavior

- All five tests pass in full `./build.sh unit` runs under a bounded synthetic load. They pass in each of at least 3 consecutive full runs with an 8× `yes` load running on the host (`for i in $(seq 8); do yes > /dev/null & done`, killed afterwards), and also in the routine run with no load.
- No test relies on a child process outliving an amount of wall-clock time. A test fixture's child lives until the test kills it.
- A readiness or hang guard (`TestBounds.hangGuard`, 60 s) can only expire on a real lost signal. It does not expire because the awaited work is queued behind the rest of the suite on the main actor. Raising `hangGuard` is not the fix (`docs/async-test-seams.md`: "any expiry that survives at `TestBounds.hangGuard` is a signal bug to root-cause").
- No test blocks the main actor on a real child process or a system-wide process walk (`AGENTS.md`: such tests must be `nonisolated`, as in `ProcessGitStatusScannerTests`).
- When a guard does expire, the failure says which await it was.

## Actual behavior

Under load, the three `SharedProjectImagesTests` time out after 60 s waiting for a held read that never arrives. In the LM Studio test, both `SIGTERM`-ignoring children have already exited by line 866. The real-enumerator test fails once at an unknown line.

## Notes

Likely causes, from the code at `main` (`dd227f21`). Confirm each one in the plan.

**LM Studio (`tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM`): the child's lifetime is a 60 s wall-clock timer.**
- `BattyKit/Tests/BattyKitTests/LMStudioSIGTERMIgnoringFixture.swift:46` runs `trap '' TERM; echo ready > …; exec sleep 60`, so each child exits on its own 60 s after spawning.
- The test is `@MainActor` (`LMStudioDashboardPaneContentTests.swift:16`). Between `content.setUp` and line 866 it awaits two FIFO readiness events and `gate.waitForParkedWaiter(2)`, and each await hops back onto the contended main actor.
- If that stretch takes more than 60 s, `sleep 60` expires and the children exit before `#expect(model.isRunning)` (`:866`).
- The rest follows from that. Each reap finds an exited child and never sleeps on the grace clock, so `graceClock.waitForSleepers(2)` (`:874`) waits out its own 60 s guard and returns false, and `advance(by:) == 2` fails (`:877`).
- Fix direction: tie the child's lifetime to the test, not to time. For example, block on a pipe or FIFO the test holds open, or use an effectively unbounded sleep that the existing `defer { killAndReap }` (`:827`–`:831`) ends. Check `LMStudioSIGTERMIgnoringFixture`'s other callers for the same assumption.

**`SharedProjectImagesTests` (all three): a 60 s wall-clock guard around work that queues on the main actor and the cooperative pool.**
- `requireHeldRead()` (`SharedProjectImagesTests.swift:18`–`25`) calls `FakeSharedImageTransport.waitForHeldRead`. That method's guard starts a `DispatchQueue.global().asyncAfter(+60 s)` the moment the test begins waiting (`Support/FakeSharedImageTransport.swift:73`–`93`).
- The read it waits for comes from `SharedProjectImages.runPass` (`BattyKit/Sources/BattyKit/Model/SharedProjectImages.swift:153`). The class is `@MainActor`, and before it reaches `transport.read` the pass:
  - awaits the previous pass (`:100`);
  - makes a `Task.detached` hop per digest for `existingCopy` (`:171`), which is file I/O plus hashing on the shared cooperative pool;
  - awaits `transport.availability()` (`:190`);
  - goes through `download` → `transport.state` (`:303`) → `readAndStore` (`:337`).
- Every one of those steps resumes on the main actor, which the whole parallel suite shares.
- One log had all three tests expiring together, which points to a window where the main actor (or pool) was starved for over a minute, not to a lost wakeup in the fake. The plan should still confirm that `read(digest:)` (`:118`–`131`) resumes registered waiters correctly. Its `defer { _readWaiters = [:] }` clears waiters while it holds the lock, so check whether a waiter that registers after the clear but before `_heldReads` is appended can miss the signal.
- What starves the main actor is the next cause below, and others like it. A test that blocks the main thread synchronously holds up every `@MainActor` test that is waiting.

**`ProcessFollowByNameTests/theRealEnumerator…`: real processes and a system-wide process walk, run synchronously on the main actor.**
- The suite is `@MainActor` (`ProcessFollowByNameTests.swift:11`), and the test (`:723`) is synchronous `throws`.
- On the main thread it:
  - copies `/bin/sleep`;
  - spawns real children;
  - walks every pid on the host several times (`ProcessInspector.firstSameUserProcess(named:)` → `allPids()`, `BattyKit/Sources/BattyKit/Runtime/ProcessInspector.swift:416`, `:495`);
  - blocks in `ChildProcessFixture.killAndReap` → `Process.waitUntilExit()` (`ChildProcessFixture.swift:57`–`61`, a `@MainActor` class).
- This is the pattern `AGENTS.md` forbids ("A test that blocks on a child process … must not do it on the main actor"). Under load it is slow itself and it stalls every other main-actor test, which makes it a candidate cause of the `SharedProjectImagesTests` and #0672 expiries.
- `ProcessStatusPaneContent(target:tabLookup:)` here also uses its default real clock for the sampling task it starts in `setUp(visible:)` (`ProcessStatusPaneContent.swift:410`–`425`). The synchronous body can't interleave with that task, but the test should inject a `TestClock` anyway.
- The failing assertion is unknown. Candidates:
  - a walk that misses the just-spawned child, if the host's process table churns past `allPidsMaxAttempts` (`ProcessInspector.swift:472`);
  - `runState` not being `.waiting` or `.running` when expected.
- The plan should make the test `nonisolated`, with its fixtures off the main actor, and make it print `walkDiagnostic` on every failing expectation. Then the next failure names its cause.

**Audit.** Check `ChildProcessFixture`'s other users and the other `@MainActor` suites that call `killAndReap` or `waitUntilExit`, because each one adds to main-actor starvation under load. Fix them here, or list them in the plan with a follow-up issue.

**Related:** #0672 (`MCPServerTests` time limits under load), #0443 (why `TestBounds.hangGuard` is 60 s and must not be raised again), #0423, #0427, #0428 (async-test seam rules), #0516 (`allPids` truncation).

## Plan

### Causes, checked against the code (2026-11-18, plan phase)

1. **LM Studio teardown test: confirmed.** The child's lifetime is a 60 s timer. `LMStudioSIGTERMIgnoringFixture.swift:46` ends with `exec sleep 60`. The test (`LMStudioDashboardPaneContentTests.swift:786`, in a `@MainActor` suite, `:16`) awaits two FIFO readiness events and then `gate.waitForParkedWaiter(2)` before `#expect(model.isRunning)` at `:866`. When those main-actor hops take more than 60 s under load, both children have already exited. Each reap then finds a dead child and never sleeps on the grace clock, so `graceClock.waitForSleepers(2)` (`:874`) expires and `advance(by:) == 2` (`:877`) fails. Every other `exec sleep 60` fixture in the LM Studio and teardown suites makes the same assumption (list under Files).
2. **`SharedProjectImagesTests` (3 tests): no lost wakeup in the fake. The guard expires because the pass is starved.**
   - `waitForHeldRead` (`Support/FakeSharedImageTransport.swift:73`–`93`) checks `_heldReads` and registers in `_readWaiters` under one lock acquisition.
   - `read(digest:)` (`:124`–`130`) appends to `_heldReads` and drains `_readWaiters` (the `defer { _readWaiters = [:] }` runs before the lock is released) under the same lock. So a waiter that registers before the append is in the drained set and is resumed. A waiter that arrives after it sees `_heldReads` non-empty and returns `true` at once. No interleaving falls between the two.
   - The timeout removes its own entry under the lock, and `ResumeOnce` (`ResumeOnce.swift:38`) makes a race between the timeout and the resume harmless. `setOnResumed` is set before the waiter registers.
   - The 60 s therefore measures the pass itself. From `reconcile` (`SharedProjectImages.swift:96`) to `transport.read` (`:337`), the pass makes about five main-actor resumptions: the Task start, the `existingCopy` `Task.detached` hop (`:171`), `availability()` (`:190`), `state` (`:303`), then `readAndStore` → `read`. Each one queues behind every other main-actor test in the parallel run. The LM Studio failure in the same log needed a stall of at least 60 s too, so the main actor was saturated or blocked for over a minute in that window.
   - No production change: `SharedProjectImages` is `@MainActor` by design, its hops are its production behaviour, and nothing here shows a production starvation bug. The test-side fix is (a) take synchronous process work off the main actor (cause 3 and the audit), and (b) make the guard measure lack of progress, not total time, and say how far the pass got.
3. **`ProcessFollowByNameTests` real-process tests: confirmed pattern, failing line unknown.**
   - `theRealEnumeratorFindsAUniquelyNamedProcessAndItsReplacement` (`ProcessFollowByNameTests.swift:723`) and `aSeededFollowOfTheSecondRealProcessShowsThatProcess` (`:581`) are synchronous tests in a `@MainActor` suite (`:11`).
   - On the main actor they copy a binary, spawn `sleep 300` children (`:592`, `:736`), and block in `ChildProcessFixture.killAndReap` → `waitUntilExit` (`ChildProcessFixture.swift:57`–`61`; the class is `@MainActor`, `:30`).
   - `ProcessStatusPaneContent(target:tabLookup:)` defaults to `SystemClock()` (`ProcessStatusPaneContent.swift:306`).
   - Most of the `#expect`s carry no diagnostic (`content.runState`, `.waiting` checks), which is why the #0664 failure can't be placed.
   - `ProcessInspector` is `@MainActor` through the package default isolation (`Package.swift:7`). The production follow-by-name walk runs on the main actor, and that stays as is.
4. **Other synchronous main-actor process work: audit.** The two that run external tools for real time are:
   - `FootprintWarningMessageLocalizationTests` (`FootprintMonitorIntegrationTests.swift:142`, default `@MainActor`): eight `xcrun xcstringstool compile` runs, each blocking in `waitUntilExit` (`:173`).
   - `AgentSkillInstallScriptTests` (`AgentSkillInstallScriptTests.swift:36`, default `@MainActor`): runs `bash install.sh` twice and blocks in `waitUntilExit` (`:267`).
