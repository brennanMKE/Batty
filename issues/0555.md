## Description

When Batty is active and a bell, OSC 9/777 notification or `batty notify` arrives from the Tab the user is looking at, Batty posts no banner, because the user already saw it. It still adds a row to the Bell Feed, marked seen. In the user's exported decision log those rows are 92 of 188 bells, almost half of the list under the bell. This issue stops adding them. The #0297 decision history and the #0523 capture log keep recording every one of them.

The user's requirement, verbatim (2026-11-05):

> We should not add discarded or ignored notifications to the list showing under the bell.

The goal this issue serves, also from the user (2026-11-05):

> We should make it our goal to declutter the notification list as much as possible so only what is useful remains.

This issue's scope is only the rows that are discarded at creation. The other decluttering work is filed separately; see "Further decluttering" in Notes.

## Expected behavior

- If **Batty is active** (`NSApplication.shared.isActive`) **and** the entry is **seen at creation**, no `BellFeedEntry` is added. Seen at creation means the source Tab is the active Tab of the focused Pane of the selected Session, in the key Window when more than one Window is registered. This applies to every trigger: BEL, OSC 9/777 and CLI `notify`.
- That bell is still recorded in `BellDecisionHistory` (#0297), with `outcome=suppressed:frontmostAndSeen` as today. When capture is on, it is still written to the capture log (#0523), and the record says no row was added.
- Every other bell is recorded exactly as today. That includes a bell from the focused Tab while Batty is in the background: the banner is posted and the row stays.

## Actual behavior

`AppStateStore.recordBellTick` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:1993`), `recordDesktopNotification` (`:2036`) and `recordCLINotification` (`:2100`) each compute `effectivelySeen = location.isFocused && isOwnerKey`. Then each one runs:

```swift
let outcome: BellFeedStore.RecordOutcome = effectivelySeen
    ? .recorded(bellFeed.record(entry))
    : bellFeed.recordOrCollapse(entry)
```

A seen entry is always inserted. `handleBellOutcome` (`:2632`) then calls `postNotification`. That records the #0297 decision. `BellNotifier.post` declines to post through `evaluateShouldPost(isBattyActive:entrySeen:)` (`BellNotifier.swift:116`), which returns `false` only when Batty is active and the entry is seen. `BellFeedView` renders `store.bellFeed.entries` unfiltered (`Views/BellFeedView.swift:50`).

- All 92 discarded rows are OSC: 85 Claude Code "Claude is waiting for your input" and 7 "Claude needs your permission". None are BEL or CLI.
- The 7 `collapsedIntoUnread` records added no row. `BellFeedStore.recordOrCollapse` (`BellFeedStore.swift:262`) removes the matching unread entry, increments its `repeatCount`, refreshes its `timestamp` and reinserts it at index 0, then returns `.collapsed`. They are already handled, so this issue leaves them alone.

After this change the same traffic leaves 89 rows instead of 181.

## What depends on a seen-at-creation entry existing

Each item below was checked against main `c51a7e1b`.

- **The ordering of record and decide.** Today `bellFeed.record` runs before `postNotification` reads `NSApplication.shared.isActive` (`makeBellDecisionRecord`, `:2740`, and again in `BellNotifier.shouldPost`, `:107`). To drop the row, the decision has to come first. Build the entry, read `isActive` once, decide whether to keep the row, then record the #0297 decision with that same `battyActive` value. If `isActive` were read twice, the row and the decision record could disagree.
- **Unit tests need an `isActive` seam.** Nothing in `AppStateStore` lets a test choose whether Batty is active. `NSApplication.shared.isActive` is read directly. Add an injected provider that defaults to `NSApplication.shared.isActive` and that tests can set. Don't let the test outcome depend on whether the test host happens to be frontmost.
- **Define the rule by facts, not by `Outcome`.** `BellDecisionRecord.outcome` reports `nilNotifier`, `sessionMuted` and `systemNotificationsDisabled` before `frontmostAndSeen` (`BellDecisionHistory.swift:117-133`). A focused, active bell with notifications turned off is reported `systemNotificationsDisabled`, but the user was still looking at it. The drop rule is `battyActive && entrySeenAtCreation`, the same two inputs `evaluateShouldPost` takes. It does not depend on the outcome enum.
- **Tab, Pane and Session unread state** is unaffected. `propagateUnseenForced(at:)` already runs only for `!effectivelySeen`, and a seen entry is never counted by `unseenCount(...)`. `TabRuntime.recordBellTickIfNeeded()` and `recordDesktopNotificationIfNeeded()` must still run. They advance the libghostty delta trackers (`lastObservedBellCount`, `lastObservedNotificationAt`) and `bellCount`/`lastBellAt`/`lastBellMessage`. Skipping them would make the next bell count twice. `PaneView`'s bell flash (`onChange(of: pane.tabs.map(\.bellCount)...)`, `PaneView.swift:349`) keys off `bellCount`, so it still fires for a focused bell. That is the intended visual feedback.
- **Collapse.** A seen-at-creation entry never goes through `recordOrCollapse`. It can't absorb a repeat or be a match candidate (`!candidate.seen`). Dropping it changes nothing about #0298.
- **AI summarization.** `handleBellOutcome`'s `.recorded` case calls `scheduleSummarization` (`:2643`). For a dropped entry that would be a Foundation Models call whose `updateSummary` finds nothing to update, so skip it. The capture event needs a new `BellCaptureSummarization` case for this, for example `notApplicableNotRecorded` (`BellFeedCapture.swift:66`), next to `notApplicableCollapsed`.
- **The #0523 capture record.** `captureBellEvent` (`AppStateStore+BellCapture.swift:17`) must still write the `event` record. Two parts of it assume a row exists:
  - `feedRowPath` and `feedRowText` describe a row the user never sees. Add a field such as `feedRecorded: false`, bump `BellCaptureSchema.version`, and document the field in `docs/bell-feed-capture.md`. Keep the two row fields filled in as "what it would have shown", or set them to null, and say which in the doc. The recommended default is to keep them filled, so the data stays comparable.
  - `bellFeed.markCaptured(entry.id)` puts the id into `capturedEntryIDs`, which is pruned only on cap overflow or `removeEntries`. Don't call it for a dropped entry, or the id stays there for the rest of the launch. The rating UI (#0524) can't reach a dropped entry anyway: `ratableEntry` (`:150`) needs it in `bellFeed.entries`.
- **The #0297 decision history** keeps recording everything, unchanged. `BellDecisionRecord.entryID` will name an entry that was never in the feed. Say so in that field's doc comment.
- **CLI `notify` (#0284).** It goes through the same `effectivelySeen` and `handleBellOutcome` path, so the rule applies to it too. The recommended default: an agent's `batty notify` to the Tab the user is looking at, while Batty is active, adds no row, the same as an OSC 9 from that Tab. The CLI still reports `.posted` (exit 0), because the notification was handled.
- **Click-to-jump and notification-tap lookups.** `BellFeedView` (`:29`, `:67`) resolves its keyboard selection against `store.bellFeed.entries`. The notifier's tap handler in `RootWindowView.setUpNotifier()` (`RootWindowView.swift:110-121`) looks the tapped id up the same way and no-ops when it's missing. A dropped entry never gets a banner, because the drop condition is exactly `evaluateShouldPost == false`, so no tap can name it. That coupling must hold: if `evaluateShouldPost` ever gains an input, the drop rule changes with it. Put a comment at both sites.
- **The footprint warning (#0290)** records with `seen: false` and never goes through these paths. It is unaffected.
- **Session Reminders (#0514, open)** are specified to be recorded unseen and through `record(_:)`, never through this rule. They are unaffected, but #0514's implementer should know this rule exists.

## Open questions, with recommended defaults

1. **Does "ignored" include muted Sessions?** Recommended: not in this issue. A muted Session's bell from a non-focused Tab is not seen, and today it gets an unread row and bumps the counters. That behavior is tested (`AppStateStoreNotifyTests.mutedSessionSuppressesTheNotifierPostButStillRecordsTheFeedEntry`) and promised in Help ("mute affects delivery, not capture"). Changing it is its own decision: [#0558](0558.md). A muted Session's bell from the focused Tab while Batty is active *is* dropped here, because the user was looking at it.
2. **Do rows that become read later stay?** The user decided (2026-11-05): no. Visiting the Pane a row belongs to removes the row. That is its own issue, [#0556](0556.md), and this issue doesn't implement it.
3. **Does CLI `notify` follow the rule?** Recommended: yes. See above.
4. **The focused Tab while Batty is in the background.** Recommended: keep the row. The banner was posted and the user wasn't looking.
5. **Window-level focus without app focus**, for example a second Batty Window being key while another app is frontmost. The rule needs both conditions, so the row is kept.

## Root cause

Every real-Tab bell path (`recordBellTick`, `recordDesktopNotification`, `recordCLINotification`) always called `bellFeed.record` for a seen-at-creation entry, even when `BellNotifier` would then decline the banner because Batty was active and the user was looking at the Tab. Those rows were noise by construction.

## Fix

Followed the Plan. The three record methods now call one private router, `AppStateStore.routeRealTabBell`. It reads `isBattyActiveProvider()` once per bell, and when `!BellNotifier.evaluateShouldPost(isBattyActive:entrySeen:)` it calls `recordDroppedBell`, which writes the #0297 decision record and, with capture on, an `event` record with `feedRecorded: false` and `summarization: notApplicableNotRecorded`. No `bellFeed` write, no unseen propagation, no notifier post, no summarization. `makeBellDecisionRecord` takes `battyActive` instead of reading `NSApplication`. Capture schema bumped to 2; `markCaptured` runs only for recorded entries. Docs updated as listed.

Small choices the Plan left open:
- `BellFeedTests.testBellByteProducesFeedEntry` creates its scratch directory locally in the test instead of adding class-level `setUp`/`tearDown` state; nothing else in the class needs it.
- The bulk `isBattyActiveProvider = { false }` insertion went after every `let store = AppStateStore(...)` in the 12 affected unit files (the 13th, `TabRuntimeBellTests`, builds no store), including stores that don't record a bell. Harmless and simpler than picking them one by one.
- `BellFeedSeenDropTests` is a `final class` (for `TestDefaults` teardown in `deinit`, the pattern the capture tests use), not a `struct`.

### Files and approach

1. **`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift`**
   - Add `isBattyActiveProvider` next to `notifier`. Give it a short doc comment: it is read once per bell by the bell router, its production default is the live read, and tests set it.
   - Add one private router that all three record methods call after building their `BellFeedEntry`. They keep their own location lookup, their `TabRuntime` delta calls (`recordBellTickIfNeeded` / `recordDesktopNotificationIfNeeded`, which must still run first) and their entry construction. Shape:
     ```swift
     private func routeRealTabBell(_ entry: BellFeedEntry, in window: WindowRuntime, at location: WindowRuntime.BellLocation, trigger: BellTriggerKind, playSound: Bool = true) {
         let battyActive = isBattyActiveProvider()
         guard BellNotifier.evaluateShouldPost(isBattyActive: battyActive, entrySeen: entry.seen) else {
             recordDroppedBell(entry, at: location, trigger: trigger, battyActive: battyActive)
             return
         }
         let outcome: BellFeedStore.RecordOutcome = entry.seen ? .recorded(bellFeed.record(entry)) : bellFeed.recordOrCollapse(entry)
         if !entry.seen { window.propagateUnseenForced(at: location) }
         handleBellOutcome(outcome, incoming: entry, at: location, trigger: trigger, playSound: playSound, battyActive: battyActive)
     }
     ```
     Move the existing #0298 comment ("a seen-at-creation bell … skipped entirely") onto the `record` branch. Add one comment on the guard. It should say that a seen entry is dropped exactly when the notifier would decline the banner, so no notification tap can name a dropped entry (`RootWindowView.setUpNotifier`'s lookup).
