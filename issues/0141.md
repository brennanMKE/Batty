# 0141 — Replace GeometryReader with onGeometryChange

| | |
|---|---|
| **Status** | resolved |

## Description

`GeometryReader` disrupts SwiftUI's layout system: it expands to fill all available space, breaks natural alignment, and forces size constraints on its children. macOS 15+ provides `onGeometryChange(for:of:transform:)` as a non-disruptive replacement for reading geometry as a side effect. All four current usages in BattyKit should be migrated.

## Sites to migrate

### 1. `SessionDetailView.swift:89` — Easy

Reads `safeAreaInsets.top` in a `.background {}` block and stores it in `@State`.

```swift
// Current (acceptable but outdated)
.background {
    GeometryReader { geo in
        Color.clear
            .onAppear { splitDetailToolbarSafeInsetTop = geo.safeAreaInsets.top }
            .onChange(of: geo.safeAreaInsets) { _, inset in
                splitDetailToolbarSafeInsetTop = inset.top
            }
    }
}
```

```swift
// Target
.onGeometryChange(for: CGFloat.self, of: { $0.safeAreaInsets.top }) {
    splitDetailToolbarSafeInsetTop = $0
}
```

### 2. `PaneView.swift:193` — Medium

Also nested in `.background {}`. Reads `geo.frame(in: .named("session"))` for a preference key AND reads `geo.size.width/height` for local pane dimensions. Two separate `onGeometryChange` calls replace both reads.

### 3. `TerminalPlaceholderView.swift:29` — Medium

Top-level `GeometryReader` (most disruptive form). Reads `proxy.frame(in: .named(coordinateSpaceName))` to report terminal placement to `TerminalHostStore`. `onGeometryChange` can extract the frame from the same named coordinate space.

```swift
// Target
Color.clear
    .onGeometryChange(for: CGRect.self, of: { $0.frame(in: .named(TerminalHostInstaller.coordinateSpaceName)) }) { frame in
        let placement = TerminalHostStore.Placement(frame: frame, isVisible: isVisible)
        TerminalHostStore.shared.updatePlacement(for: tab, placement: placement)
    }
```

### 4. `SplitContainerView.swift:66` — Hard / Possibly keep

Top-level `GeometryReader` that **drives layout** — it measures available space and uses it to compute child pane sizes within the same render pass. `onGeometryChange` is a side-effect hook and cannot drive layout the same way. Options:

- Replace with a custom `Layout` conformance (the correct modern approach for layout-driving code).
- Keep `GeometryReader` here if the complexity of a custom `Layout` is not justified.

This site needs a design decision before implementation.

## Root cause

`GeometryReader` was used in three view files as a side-effect probe rather than a layout driver, producing the layout-expansion and alignment-disruption problems inherent to that pattern. Site 4 (`SplitContainerView`) was using it as a layout driver and required a different fix (see #0145).

## Fix

- **Site 1** (`SessionDetailView`): Replaced `.background { GeometryReader { ... } }` with `.onGeometryChange(for: CGFloat.self, of: { $0.safeAreaInsets.top })`. Removed the `.onAppear`/`.onChange` pair.
- **Site 2** (`PaneView`): Added `@State private var frameInSession: CGRect` as a bridge. Background now uses `Color.clear.preference(..., value: [pane.id: frameInSession]).onGeometryChange(for: CGRect.self)` to update the preference key and a second `onGeometryChange(for: CGSize.self)` to update `paneWidth`/`paneHeight`. No `GeometryReader`.
- **Site 3** (`TerminalPlaceholderView`): Dropped the outer `GeometryReader` and the `TerminalPlacementPreferenceKey` path entirely. Single `onGeometryChange` updates `lastFrame` and calls `setPlacement` directly. `onChange(of: isVisible)` handles visibility-only changes using the stored `lastFrame`. Removed the corresponding `onPreferenceChange` block and `TerminalPlacementPreferenceKey` struct.

## Files changed

- `BattyKit/Sources/BattyKit/Views/SessionDetailView.swift`
- `BattyKit/Sources/BattyKit/Views/PaneView.swift`
- `BattyKit/Sources/BattyKit/Views/TerminalPlaceholderView.swift`

## Gotchas

- Site 2's `@State frameInSession` means the preference key lags one render cycle behind geometry changes. This matches the latency of the old `GeometryReader` approach (also 2-pass), so there is no regression.
- Site 3: dropping the preference key means `TerminalHostStore.updatePlacements` is no longer called from the SwiftUI tree. All updates go through `setPlacement` (single-tab merge), which was already the "backstop" path. Cold-launch behavior should be equivalent or better since `onGeometryChange` never misses the second layout pass.
- Manual UI sign-off not done headlessly.

## Expected behavior

All geometry reads are non-disruptive side effects (`onGeometryChange`) or, where layout must be driven, use a proper `Layout` conformance. No top-level `GeometryReader` remains in the view tree.

## Actual behavior

Four `GeometryReader` usages exist. Two are nested safely in `.background` blocks (sites 1–2); two are top-level and disrupt alignment/sizing (sites 3–4).

## Notes

- `onGeometryChange(for:of:transform:)` requires macOS 15+. Batty targets macOS 15.6, so no back-deployment needed.
- Sites 1 and 2 are straightforward mechanical rewrites.
- Site 3 requires care: the coordinate-space frame must still be read from the correct `.named()` scope.
- Site 4 is the design question — evaluate a custom `Layout` before migrating.
- Migrate sites 1–3 first and ship; tackle site 4 separately as its own sub-task.
