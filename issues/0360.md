# 0360 — ProcessGitStatusScanner's activeProcess slot is shared across overlapping scans, silently disarming terminateAndWaitBriefly

| | |
|---|---|
| **Status** | open |
| **Module** | Pane |
| **Platform** | macOS |
| **First seen** | 2026-08-21 |

## Description

`ProcessGitStatusScanner` tracks the subprocess it may need to kill in a single `activeProcess` slot: `run()` does `setCurrentProcess(process)` on entry and `defer { setCurrentProcess(nil) }` on exit, and `terminateAndWaitBriefly()` reads whatever the slot currently holds. `scan()` hops to `DispatchQueue.global(qos: .utility)`, so two scans can be in `run()` concurrently — e.g. the sequence `changeDirectory → suspend → activate` starts a second `scan()` while the first block is still running. The interleaving that goes wrong: scan B sets the slot to its process, then scan A finishes and its `defer` nulls the slot — so when `terminateAndWaitBriefly()` fires (teardown/suspend), the slot is empty and B's `git status` receives no SIGTERM.

**The blast radius is bounded — do not over-scope the fix.** Every `run()` invocation reaches `waitUntilExit()` on its own process regardless of the slot's state, so no child is ever orphaned or left unreaped; the process runs to natural completion and is fully cleaned up. The cost of the race is precisely one missed early-termination signal — a `git status` in a huge repo runs a few seconds longer than it needed to after its pane was torn down. It is a correctness wart in the cancellation path, not a leak.

The fix shape: make the slot scan-scoped rather than instance-scoped — e.g. `setCurrentProcess(nil)` only if the slot still holds *this* scan's process (compare-and-clear), or track a generation/set of live processes so `terminateAndWaitBriefly` can signal all of them.

## Expected behavior

`terminateAndWaitBriefly()` signals every scan subprocess still running at the time of the call, regardless of how scans interleaved.

## Actual behavior

An older scan's exit can null out a newer scan's slot entry, making `terminateAndWaitBriefly()` a silent no-op for the newer process; that process still exits and is reaped normally, just without the early SIGTERM.
