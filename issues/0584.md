## Description

A Project has no Theme field. Every Session opened from a Project starts out following the app-wide Theme. The only way to give it a different Theme is the Sidebar's **Set Session Theme…**, which is in memory only: it is gone when the Session closes, and Save as Project / Update Project don't capture it. The user:

> "With Projects, can I also set a theme for that session? I think it does not support that. I think we should."

Requested behavior: a Project can store an optional Theme. A Session opened from that Project renders its Terminal Sessions with that Theme instead of the app-wide one. With no Theme set, the Session follows the app-wide Theme as it does today. This is the Theme counterpart of [#0540](0540.md), which did the same for the terminal background, and it should be built the same way.

## Root cause

Feature work. `Project`, `ProjectSyncRecord`, `ProjectDraft` and the Project Editor had no Theme. The only Session-level Theme was `SessionRuntime.localThemeName`, a single in-memory name that Save as Project / Update Project never read. The resolvers also disagreed: `applyActiveSessionTheme(for:)` reset the chrome on an unknown local name instead of falling back, and `applyThemeToAllSurfaces` skipped any Session with a non-nil name, even an unresolvable one.

## Fix

Followed the plan. The orchestrator settled the open questions: chrome keeps following the selected Session's Theme, Set Session Theme writes both slots, and the new-Tab gap is out of scope (filed separately).

- New `ThemePair` (dark/light, trimmed, `normalized` → nil when empty, tolerant per-slot decode: wrong type, >128 UTF-8 bytes or control characters read as nil).
- `SessionRuntime.localThemeName` → `themeOverride: ThemePair?`, plus `projectThemeSeed`.
- One resolver: `ThemePreference.effectiveTheme(override:isDark:)` and `overrideTheme(_:isDark:)`. `applyThemeToAllSurfaces`, `applyActiveSessionTheme(for:)` and `applyGlobalThemeForCurrentAppearance` gained internal `isDark:` overloads. A Session follows global when `overrideTheme` is nil. The appearance pass re-applies each overriding Session's own slot, then sets the chrome from the selected Session's effective Theme. `applyTheme(_:to:)` is split into a chrome-free `applyTerminalTheme(_:to:)` and the chrome-updating wrapper.
- `Project.theme` and `ProjectSyncRecord.theme`, written with `encodeIfPresent` and decoded tolerantly. Merge carries it as definition.
- `addProjectSession` seeds `themeOverride` and `projectThemeSeed`. `SaveSessionAsProject.draft` takes the Session's Theme on new, and on Update only when `themeOverride != projectThemeSeed`. Inlined in `draft(...)` rather than a separate `captureTheme` helper, since it is two lines.
- `ProjectDraft.theme`. `ProjectEditorViewModel`: `.theme` field, `themeSummary`, `unavailableThemeNames()`, `setTheme(_:)` (guards equal values), and a non-blocking warning for unknown names.
- `ProjectThemeRow` above Background (not gated on `showsBackground`), plus a new `ProjectThemeSheet` with a Dark | Light segmented switch, Follow Settings, a filter, and pinned/all `ThemeCard` grids. It edits local `@State` and Done calls `setTheme`. It has no keyboard cursor and no live preview.
- Deviation: the editor Theme tests are a new `ProjectEditorThemeTests` suite inside `ProjectEditorTests.swift`, and the Save tests are a new `SaveSessionAsProjectThemeTests` suite inside `SaveSessionAsProjectTests.swift`. Both sit next to their existing suites rather than being added to them.
- Docs: Concepts.md (Theme scope, Project contains/definition, Session affordances and Theme override), PRD §6.8 and §10, docs/themes.md §9 and out of scope, docs/design/projects-sharing.md, Help 10-projects ("## Theme" and the Shared sentence) and 07-themes ("Session and Project themes").
- Round 2 (review bounce): `testDarkThemeIsWrittenToTheProject` now clicks `project-theme-sheet.filter` and types `TokyoNight` before waiting for `project-theme-sheet.card.TokyoNight`, then waits for the card to be hittable before clicking it, as `ThemeTests.testFilterScrollsMatchIntoView` does. The cards are in a name-sorted `LazyVGrid`, so without the filter the card is never created. `testThemeRowOpensTheSheetShowingFollow` touches only the Follow and Cancel buttons, which are outside the grid, so it needed no change. No production change.

## Plan

Planned 2026-11-11 against `main` at `874363d`. Binding inputs are the user decisions below: an optional Dark Theme and an optional Light Theme, set independently. An unknown name is kept, falls back, and is shown as unavailable. No flag. Projects only.

### Premises checked

- `Project`, `ProjectSyncRecord`, `ProjectDraft` and `ProjectEditorView` have no Theme. `addProjectSession` seeds no Theme. `SaveSessionAsProject` and `SessionProjectCapture` don't read `localThemeName`. All confirmed.
- **The resolvers disagree today.** `ThemePreference.effectiveTheme(localThemeName:isDark:)` falls back to the global Theme when the local name isn't in the catalog. `applyActiveSessionTheme(for:)` doesn't: it does `localThemeName ?? global`, and an unknown local name makes it reset the chrome to nil and leave the surfaces alone. `applyThemeToAllSurfaces` skips every Session with `localThemeName != nil`, so a Session holding an unknown name also misses global changes. The "keep the unknown name" decision needs one resolver used everywhere (below).
- Every caller of `applyThemeToAllSurfaces` passes the Theme for the current appearance (Settings' `appliesNow` slot, `ThemeSelectorView.selectTheme`, the palette, `BattyCommands`, `UITestDriver`, and the appearance observer). So deciding "does this Session follow global" by the current appearance is sound.
- `tab.terminal.theme` (`TerminalViewState.theme`, from `controller.theme`) can be read, so tests can check what a surface got.
- **Existing gap, not in scope:** `TabRuntime.init` bakes in the *global* Theme. Splits are re-themed through `SessionDetailView`'s `onChange(of: allPanes.count)`, but a new Tab (Cmd-T) in a Session with a Session Theme isn't re-themed until the Session is selected again. That is true of #0139 today. A Project Theme makes it more visible. See open question 1.

### Approach: the Session override becomes a pair

The Project stores a pair. The runtime Session override becomes the same pair, resolved by the current appearance. That replaces having a Project pair *and* a single `localThemeName` with two chains to reconcile.

- New value type **`ThemePair`** (BattyKit `Theme/ThemePair.swift`, `Codable, Sendable, Hashable`): `dark: String?`, `light: String?`.
  - `init(dark:light:)` trims each slot and turns an empty one into nil.
  - `static func both(_ name:)`.
  - `func name(isDark:) -> String?` and `var isEmpty`.
  - A failable `normalized` returns nil when both slots are nil, so "no Theme" has exactly one representation (`nil`).
  - Codable keys `dark` / `light`, each written with `encodeIfPresent`. Decoding is tolerant per slot: a wrong type, an empty string, a name over 128 UTF-8 bytes or a name with control characters reads as nil for that slot. The bad slot is logged and the other slot is kept.
  - No catalog check in the model. An unknown name is data and round-trips verbatim.
- **`SessionRuntime`**: replace `localThemeName: String?` with `themeOverride: ThemePair?`, still not persisted. Add `@ObservationIgnored public internal(set) var projectThemeSeed: ThemePair?`, the counterpart of `projectBackgroundSeed`.
  - **Set Session Theme…** (`SessionThemeSelectorView.selectTheme`) writes `.both(theme.name)`. That keeps today's meaning, "this Session uses this Theme in every appearance". It replaces a Project's pair for the rest of the Session's life.
  - **Clear Session Theme** writes nil and is shown when `themeOverride != nil`.
  - Arrow-key preview still calls `applyTheme(_:to:)` only and writes nothing.
- **One resolver** in `ThemePreference`. `effectiveTheme(override: ThemePair?, isDark:, defaults:)` returns the override's slot for `isDark` if the catalog has it, else the global Theme. Next to it, `overrideTheme(_ override: ThemePair?, isDark:) -> GhosttyThemeDefinition?` returns only a *resolvable* override slot. The old `effectiveTheme(localThemeName:…)` overloads go, and their tests move to the new signature.
- **`AppStateStore` application** (`ThemePreference.swift` extension):
  - `applyActiveSessionTheme(for:)` resolves through `effectiveTheme(override:isDark:defaults: preferences)`, so an unknown or unset slot falls back to global instead of resetting the chrome.
  - `applyThemeToAllSurfaces(_:)` gains an internal `isDark:` overload. The public one passes `NSApp` appearance. A Session counts as "following global" when `overrideTheme(session.themeOverride, isDark:) == nil`. The chrome condition uses the same test on `selectedSession`.
  - `applyGlobalThemeForCurrentAppearance()` gets an internal `isDark:` overload. After the global pass it re-applies every overriding Session's own slot for the new appearance. Without that, a Session with Dark = X switched to Light, picks up the global Light, and stays there when Dark returns, because it is filtered out as overridden. Then it sets the chrome from the selected Session's effective Theme. To re-theme surfaces without touching the chrome, split `applyTheme(_:to:)` into a chrome-free `applyTerminalTheme(_:to:)` and the existing wrapper that also updates the chrome. Event-origin only (AppKit KVO). Nothing new runs from view code.
  - `SessionThemeSelectorView.init` marks the effective card with the new resolver.
  - **Chrome:** unchanged. The chrome follows the selected Session's effective Theme, as it has since #0135. See open question 2.
- **`Project.theme: ThemePair?`**:
  - New `theme` CodingKey. Encoded with `encodeIfPresent` after `sharedImage`, so a Project with no Theme is byte-identical to today.
  - Decoded tolerantly like `background`. A wrong type reads as nil and is logged, and never fails the Project.
  - Stored through `.normalized`.
  - Added to `init` (default nil) and the doc comment ("definition; older Batty ignores and drops it on save").
- **`ProjectSyncRecord.theme: ThemePair?`**:
  - New optional key, decoded with `try?`, so a bad value can't make `snapshot()` skip the record.
  - `Project.syncRecord(home:…)` writes `theme`. `Project(syncRecord:)` reads it.
  - `replacingDefinition` takes it from the record (it is definition, last-writer-wins). A record without the key, such as one from an older Batty, means no Theme. That matches how `customColor`/`symbolName` behave.
  - `ProjectStore.upsert` already stamps `modifiedAt` on every save, so a Theme change publishes and stamps with no store change. Confirm in a test.
  - `docs/design/projects-sharing.md`: add `theme` to the Definition row of the table.
- **Open** (`WindowRuntime.addProjectSession`): set `session.themeOverride = project.theme` and `session.projectThemeSeed = project.theme` before `selectedSessionID = session.id`. The selection's `onChange` then calls `applyActiveSessionTheme(for:)` with the override already in place. No new application call, and no write from view code. An unknown name is seeded as is, so it falls back at render time and survives a later Save.
  - Re-focusing an open Project doesn't reseed.
  - Saving a Project doesn't touch its open Session, as with the background.
- **Save as Project / Update Project** (`SaveSessionAsProject.draft`):
  - Add `captureTheme(of:into:replacingStored:)`. A new Project always takes `session.themeOverride`. Update takes it only when `session.themeOverride != session.projectThemeSeed`, which is #0540's seed rule.
  - Consequence to document: Clear Session Theme followed by Update clears the Project's Theme, the same as the background.
  - `SessionProjectCapture.updateDraft(of:)` already starts from `ProjectDraft(project:)`, so the stored Theme carries over once `ProjectDraft` copies it.
  - **Copy from current Session** leaves the draft's Theme alone, as it leaves the background (#0540 decisions table).
- **`ProjectDraft`**: add `var theme: ThemePair?`, copied in `init(project:)` and added to the memberwise init (default nil). `makeProject()` passes `theme?.normalized`. The dirty check comes through `Equatable` for free.
- **`ProjectEditorViewModel`**:
  - Add `ProjectEditorField.theme`.
  - `func setTheme(_ pair: ThemePair?)` is a button action from the sheet's Done. It guards on equal values, because `@Observable` notifies on equal writes.
  - `var themeSummary: String`, with these forms:
    - "Follows Settings"
    - "Dark: X · Light: Follows Settings"
    - "Dark and Light: X" when both slots are equal
    - an unknown name rendered "X (not available)"
  - `func unavailableThemeNames() -> [String]`, from the catalog.
  - `validate()` adds a **warning** (never an error) on `.theme` when a slot names a Theme this Mac lacks: "“X” isn't available in this version of Batty. Sessions opened from this Project use the Settings Theme instead until it is. Saving keeps it." Save stays enabled.
- **`ProjectEditorView`**:
  - Add a `ProjectThemeRow` in `ProjectEditorMain`, directly above `ProjectBackgroundRow`, in the same style: a caption "Theme", a summary, `Spacer`, **Edit…**, and `FieldMessages` for the `.theme` warning. Same padding as `ProjectBackgroundRow`, and the same `.id(model.selectedID)` so a swapped draft ends the sheet.
  - Unlike Background it isn't gated on `showsBackground`. It needs no image library.
  - **`ProjectThemeSheet`** (new file `Views/ProjectThemeSheet.swift`):
    - Layout: a segmented **Dark | Light** slot switch, a **Follow Settings** choice for the selected slot, the filter field, and a `ThemeCard` grid reusing `ThemeCard` and `PinnedThemes`, with sections like `SessionThemeSelectorView`. `isActive` marks the slot's chosen name.
    - When the selected slot holds an unknown name, a caption says it's unavailable. Choosing Follow Settings or a card replaces it. Leaving the slot alone keeps it.
    - The sheet edits a local `@State` pair, seeded in `init` from `model.draft?.theme`. **Done** calls `model.setTheme(_:)`. **Cancel** writes nothing.
    - No live preview to surfaces: the editor isn't bound to a Session.
    - The initial slot is the current appearance, read once in `init`, not in `body`.
    - Scroll-to-active reuses the existing `onAppear` proxy pattern.
    - No writes from `body`, `onChange` or `onAppear` beyond the existing scroll and cursor patterns (`docs/swiftui-observation-rules.md`).
  - Identifiers:
    - Row: `project-editor.theme.summary`, `project-editor.theme.edit`, `project-editor.theme.warning`.
    - Sheet: `project-theme-sheet.root`, `.slot` (segmented), `.follow` (value "selected" when the slot is nil, as the background sheet's follow button reports), `.card.<name>`, `.unavailable`, `.done`, `.cancel`.
- Out of scope, per the user decisions and #0585: per-Tab or per-Pane Theme, persisting a plain Session's Theme, a flag, and the new-Tab gap above. Theme stays a Project-level field. #0585 adds `ProjectTab.background` and touches neither `ThemePair` nor the Theme row. Its Tab cards live in `PaneInspector`, not the top section.

### Open questions (none blocking)

1. **New Tab in a themed Session** gets the global Theme until the Session is reselected. This predates this issue (#0139) and also affects Set Session Theme. Recommendation: file it as its own issue rather than widen this one. The fix belongs in the Tab-creation path (`PaneRuntime.addTab`), not in a view `onChange`.
2. **Chrome.** The plan keeps today's behavior: the Sidebar and window chrome follow the selected Session's effective Theme, Project-seeded or not. If the user wants the chrome to stay on the app-wide Theme, that is a separate change to `applyTheme(_:to:)` for every Session Theme.

## Steps to reproduce

1. Open the Project Editor for any Project.
2. Look for a Theme control. There is none, and `Project` has no Theme field.
3. Open the Project, right-click its Session in the Sidebar and choose **Set Session Theme…**. Pick a Theme other than the app-wide one.
4. Choose **Update Project** (or Save as Project), save, close the Session, and open the Project again.

## Expected behavior

- The Project Editor has a Theme control (likely next to the background control) with a "Follow Settings" choice (no Theme stored) and a picker that reuses the Theme Selector's cards.
- Opening the Project seeds the new Session's `localThemeName` from the Project's Theme. Terminal Sessions in every Terminal Pane of that Session render with it, and switching to that Session applies it through the existing path (`applyActiveSessionTheme(for:)`).
- Changing the app-wide Theme in Settings leaves a Project-themed Session alone, the same as any Session with a Session Theme. A Project with no Theme follows the app-wide Theme, including the Dark/Light switch (#0241).
- **Set Session Theme…** and **Clear Session Theme** still work on a Project-opened Session for the rest of its life. Clearing makes it follow the app-wide Theme.
- Save as Project and Update Project capture the Session's Theme. Follow #0540's seed rule: Update Project writes the Theme only if the user changed it after opening, so a Session that never touched its Theme can't overwrite the Project's (compare `projectBackgroundSeed`).
- Shared Projects: the Theme is part of the **definition**, not device state. It is a catalog name with no path, so it syncs in `ProjectSyncRecord`, changing it stamps `modifiedAt`, and conflicts resolve last-writer-wins like the other definition fields.
- Older Batty versions ignore the new key, and on their next save they drop it, as they do for `background`, `customColor` and `symbolName`. A local Project that has no Theme encodes byte-identically to today.

## Actual behavior

- `Project` (`BattyKit/Sources/BattyKit/Model/Project.swift`) and `ProjectSyncRecord` (`Model/ProjectSync.swift`) have no Theme field. `ProjectEditorView` has no Theme control (its only `themeChrome` uses are `nil` arguments for preview rendering).
- `WindowRuntime.addProjectSession(_:tree:background:)` seeds title, color, symbol and background, but not a Theme. The new Session's `localThemeName` is `nil`, so it follows the app-wide Theme.
- `SessionRuntime.localThemeName` exists (#0139): set by the Sidebar's **Set Session Theme…**, cleared by **Clear Session Theme**, and "Not persisted — resets to nil on every launch". `SaveSessionAsProject` and `SessionProjectCapture` don't read it, so a Session Theme is lost when the Session is saved as a Project.

## Notes

### Premise corrections

The report assumed "Theme is app-wide today". That holds for anything persisted, but not for a running Session. A per-Session override has existed since #0139, with its fallback chain from #0147/#0149 and the "in effect" card from #0363. Concepts.md §Theme ("Per-Session or per-Pane Theme overrides are out of scope") and PRD §6.8 / §10 ("Per-surface theme override is out of scope for v1") are already stale about that. So this issue extends an existing in-memory Session Theme into a persisted Project field. The new parts are UI, model and sync, not rendering.

Related: [#0585](0585.md) adds a per-Tab background to Projects. Theme stays Project-level only, here.

Related: [#0586](0586.md): a new Tab in a Session with its own Theme starts with the app-wide Theme. Fix it after this lands, using this issue's resolver.

### Where the code is

- Resolution and application: `BattyKit/Sources/BattyKit/Theme/ThemePreference.swift`. See `effectiveTheme(localThemeName:isDark:)`, `applyThemeToAllSurfaces` (skips Sessions where `localThemeName != nil`), `applyTheme(_:to:)` (Terminal Panes only, and also updates `themeChrome`) and `applyActiveSessionTheme(for:)`.
- Catalog: `BattyThemeCatalog.theme(named:)` (`Theme/BattyThemeCatalog.swift`) resolves a name against the compiled-in catalog only: about 485 upstream themes plus the Batty-original ones. `ThemeStore.discoverAll` in `Theme/Theme.swift` can read `~/.config/ghostty/themes/` and the bundle's `Themes/` folder, but nothing calls it, so no Theme comes from a file today.
- Precedent to copy: #0540 (`Project.background`, `projectBackgroundSeed`, `SaveSessionAsProject.captureBackground`, the `.background` `ProjectEditorField`), #0376 (Session background override) and #0374 (Pane background).
- Project seeding: `WindowRuntime.addProjectSession`, where the Theme would be seeded next to `setBackgroundOverride`.

### Shared vs local (#0501)

The definition / device-state split puts the Theme in the definition, because it identifies a catalog entry and names no file on this Mac. That is unlike the background, where the image path is device state and the rest is definition. The Theme needs no transport like #0551's: it is just a catalog name. It must still survive a Mac running a Batty that lacks that name (see open questions).

### Docs and scope change

This turns down PRD §10's deferral for a Project's Session. When this is worked:

- Concepts.md §Theme: replace the "Scope (v1)" bullet with: app-wide default; a per-Session override (in memory, #0139); and a Project Theme that seeds that override at open.
- Concepts.md §Project: add the Theme to "Contains" and to the definition list in "Shared or local".
- PRD §6.8 and §10: update both.
- `docs/themes.md`: line 526 lists per-session overrides as out of scope, which is already wrong. #0370 tracks other stale parts of that file.

### Open questions for the planner / user

1. **One Theme or a Dark/Light pair?** The app-wide Theme stores one per appearance (#0241). `localThemeName` is a single name that doesn't change with the appearance. Should a Project store one name (matching the Session Theme) or a pair?
2. **Chrome.** `applyTheme(_:to:)` already pushes the Session Theme into the app-wide `themeChrome` when that Session is selected (#0135). So the window chrome and Sidebar follow the selected Session's Theme, and chrome is one object for all Windows. Is that right for a Project Theme, or should the chrome stay on the app-wide Theme?
3. **Unknown Theme name.** If a Shared Project names a Theme this Mac's Batty doesn't have (an older build without a new Batty-original Theme, or a future user-file Theme if `ThemeStore` is ever wired up), the fallback today is the app-wide Theme. Should the Theme name be kept on the Project and the problem shown (the way `projectBackgroundImageProblem` is shown in the Sidebar row), so a Save from that Mac doesn't drop it?
4. **Persisting the Session Theme outside Projects.** Should **Set Session Theme…** on a Session not opened from a Project persist too? There's nowhere to put it since #0172 removed workspace persistence, so this issue leaves that out.
5. **Per-Pane Theme.** #0374 added a per-Pane background but there is no per-Pane Theme. If a Session is ever given one, Save as Project should note it isn't saved, like the "A Pane's own background isn't saved" note. Out of scope here.
6. **Feature flag.** Shared Project images shipped behind `FeatureFlags.sharedProjectImages`. Does this need a flag, or does it ship directly because it reuses an existing rendering path?

## User decisions (2026-11-11)

- **Theme shape:** a Project stores an optional Dark Theme and an optional Light Theme, independently. Either, both or neither may be set; an unset slot follows the app-wide Theme for that appearance.
- **Unknown Theme name on this Mac:** keep the stored name and fall back to the app-wide Theme; the Project Editor shows it as unavailable, and a save never drops it.
- **Feature flag:** none.
- **Scope:** Projects only. Plain Sessions keep the in-memory Session Theme override; no new Session persistence.
