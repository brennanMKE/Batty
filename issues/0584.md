# 0584 — A saved Project can't store a Theme, so a Session opened from it always follows the app-wide Theme and its Session Theme is lost on Save as Project

| | |
|---|---|
| **Status** | open |
| **Module** | Projects / Theme |
| **Platform** | macOS |
| **First seen** | 2026-11-11 |

## Description

A Project has no Theme field. Every Session opened from a Project starts out following the app-wide Theme. The only way to give it a different Theme is the Sidebar's **Set Session Theme…**, which is in memory only: it is gone when the Session closes, and Save as Project / Update Project don't capture it. The user:

> "With Projects, can I also set a theme for that session? I think it does not support that. I think we should."

Requested behavior: a Project can store an optional Theme. A Session opened from that Project renders its Terminal Sessions with that Theme instead of the app-wide one. With no Theme set, the Session follows the app-wide Theme as it does today. This is the Theme counterpart of [#0540](0540.md), which did the same for the terminal background, and it should be built the same way.

## Steps to reproduce

1. Open the Project Editor for any Project.
2. Look for a Theme control. There is none, and `Project` has no Theme field.
3. Open the Project, right-click its Session in the Sidebar and choose **Set Session Theme…**. Pick a Theme other than the app-wide one.
4. Choose **Update Project** (or Save as Project), save, close the Session, and open the Project again.

## Expected behavior

- The Project Editor has a Theme control (likely next to the background control) with a "Follow Settings" choice (no Theme stored) and a picker that reuses the Theme Selector's cards.
- Opening the Project seeds the new Session's `localThemeName` from the Project's Theme. Terminal Sessions in every Terminal Pane of that Session render with it, and switching to that Session applies it through the existing path (`applyActiveSessionTheme(for:)`).
- Changing the app-wide Theme in Settings leaves a Project-themed Session alone, the same as any Session with a Session Theme. A Project with no Theme follows the app-wide Theme, including the Dark/Light switch (#0241).
- **Set Session Theme…** and **Clear Session Theme** still work on a Project-opened Session for the rest of its life. Clearing makes it follow the app-wide Theme.
- Save as Project and Update Project capture the Session's Theme. Follow #0540's seed rule: Update Project writes the Theme only if the user changed it after opening, so a Session that never touched its Theme can't overwrite the Project's (compare `projectBackgroundSeed`).
- Shared Projects: the Theme is part of the **definition**, not device state. It is a catalog name with no path, so it syncs in `ProjectSyncRecord`, changing it stamps `modifiedAt`, and conflicts resolve last-writer-wins like the other definition fields.
- Older Batty versions ignore the new key, and on their next save they drop it, as they do for `background`, `customColor` and `symbolName`. A local Project that has no Theme encodes byte-identically to today.

## Actual behavior

- `Project` (`BattyKit/Sources/BattyKit/Model/Project.swift`) and `ProjectSyncRecord` (`Model/ProjectSync.swift`) have no Theme field. `ProjectEditorView` has no Theme control (its only `themeChrome` uses are `nil` arguments for preview rendering).
- `WindowRuntime.addProjectSession(_:tree:background:)` seeds title, color, symbol and background, but not a Theme. The new Session's `localThemeName` is `nil`, so it follows the app-wide Theme.
- `SessionRuntime.localThemeName` exists (#0139): set by the Sidebar's **Set Session Theme…**, cleared by **Clear Session Theme**, and "Not persisted — resets to nil on every launch". `SaveSessionAsProject` and `SessionProjectCapture` don't read it, so a Session Theme is lost when the Session is saved as a Project.

## Notes

### Premise corrections

The report assumed "Theme is app-wide today". That holds for anything persisted, but not for a running Session. A per-Session override has existed since #0139, with its fallback chain from #0147/#0149 and the "in effect" card from #0363. Concepts.md §Theme ("Per-Session or per-Pane Theme overrides are out of scope") and PRD §6.8 / §10 ("Per-surface theme override is out of scope for v1") are already stale about that. So this issue extends an existing in-memory Session Theme into a persisted Project field. The new parts are UI, model and sync, not rendering.

Related: [#0585](0585.md) adds a per-Tab background to Projects. Theme stays Project-level only, here.

### Where the code is

- Resolution and application: `BattyKit/Sources/BattyKit/Theme/ThemePreference.swift`. See `effectiveTheme(localThemeName:isDark:)`, `applyThemeToAllSurfaces` (skips Sessions where `localThemeName != nil`), `applyTheme(_:to:)` (Terminal Panes only, and also updates `themeChrome`) and `applyActiveSessionTheme(for:)`.
- Catalog: `BattyThemeCatalog.theme(named:)` (`Theme/BattyThemeCatalog.swift`) resolves a name against the compiled-in catalog only: about 485 upstream themes plus the Batty-original ones. `ThemeStore.discoverAll` in `Theme/Theme.swift` can read `~/.config/ghostty/themes/` and the bundle's `Themes/` folder, but nothing calls it, so no Theme comes from a file today.
- Precedent to copy: #0540 (`Project.background`, `projectBackgroundSeed`, `SaveSessionAsProject.captureBackground`, the `.background` `ProjectEditorField`), #0376 (Session background override) and #0374 (Pane background).
- Project seeding: `WindowRuntime.addProjectSession`, where the Theme would be seeded next to `setBackgroundOverride`.

### Shared vs local (#0501)

The definition / device-state split puts the Theme in the definition, because it identifies a catalog entry and names no file on this Mac. That is unlike the background, where the image path is device state and the rest is definition. The Theme needs no transport like #0551's: it is just a catalog name. It must still survive a Mac running a Batty that lacks that name (see open questions).

### Docs and scope change

This turns down PRD §10's deferral for a Project's Session. When this is worked:

- Concepts.md §Theme: replace the "Scope (v1)" bullet with: app-wide default; a per-Session override (in memory, #0139); and a Project Theme that seeds that override at open.
- Concepts.md §Project: add the Theme to "Contains" and to the definition list in "Shared or local".
- PRD §6.8 and §10: update both.
- `docs/themes.md`: line 526 lists per-session overrides as out of scope, which is already wrong. #0370 tracks other stale parts of that file.

### Open questions for the planner / user

1. **One Theme or a Dark/Light pair?** The app-wide Theme stores one per appearance (#0241). `localThemeName` is a single name that doesn't change with the appearance. Should a Project store one name (matching the Session Theme) or a pair?
2. **Chrome.** `applyTheme(_:to:)` already pushes the Session Theme into the app-wide `themeChrome` when that Session is selected (#0135). So the window chrome and Sidebar follow the selected Session's Theme, and chrome is one object for all Windows. Is that right for a Project Theme, or should the chrome stay on the app-wide Theme?
3. **Unknown Theme name.** If a Shared Project names a Theme this Mac's Batty doesn't have (an older build without a new Batty-original Theme, or a future user-file Theme if `ThemeStore` is ever wired up), the fallback today is the app-wide Theme. Should the Theme name be kept on the Project and the problem shown (the way `projectBackgroundImageProblem` is shown in the Sidebar row), so a Save from that Mac doesn't drop it?
4. **Persisting the Session Theme outside Projects.** Should **Set Session Theme…** on a Session not opened from a Project persist too? There's nowhere to put it since #0172 removed workspace persistence, so this issue leaves that out.
5. **Per-Pane Theme.** #0374 added a per-Pane background but there is no per-Pane Theme. If a Session is ever given one, Save as Project should note it isn't saved, like the "A Pane's own background isn't saved" note. Out of scope here.
6. **Feature flag.** Shared Project images shipped behind `FeatureFlags.sharedProjectImages`. Does this need a flag, or does it ship directly because it reuses an existing rendering path?

## User decisions (2026-11-11)

- **Theme shape:** a Project stores an optional Dark Theme and an optional Light Theme, independently. Either, both or neither may be set; an unset slot follows the app-wide Theme for that appearance.
- **Unknown Theme name on this Mac:** keep the stored name and fall back to the app-wide Theme; the Project Editor shows it as unavailable, and a save never drops it.
- **Feature flag:** none.
- **Scope:** Projects only. Plain Sessions keep the in-memory Session Theme override; no new Session persistence.
