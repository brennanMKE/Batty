# 0703 — The CLI and MCP can't rename, restyle or close Sessions and Tabs, manage Reminders, or set a live background

| | |
|---|---|
| **Status** | open |
| **Module** | Session / Tabs / Docs |
| **Platform** | macOS |
| **First seen** | 2026-11-20 |
| **Target** | 1.5.0 |

## Description

An agent driving Batty through `batty` or `batty mcp` can create, focus and close Sessions and Panes and open Tabs, but it can't do several things the Sidebar, Tab bar and Reminders popover already do: rename a Session or Tab, set a Session's color or Theme, close a single Tab, see or cancel Reminders across Sessions, or put a background image on a running Session, Pane or Tab. The user decided (2026-11-20) to round out the CLI/MCP command set for 1.5.0, the release that ships the MCP server (#0647) and `project create/edit` / `background list` (#0700).

Add these verbs, CLI and MCP only, with no new UI (AGENTS.md, progressive disclosure). Every verb goes over XPC to the app and calls the **same store mutators the UI calls**, so observation and idempotence rules are already met. MCP tools come from `batty capabilities`, so each verb needs a `CapabilitiesDescribable` schema and an annotations row.

1. `batty session rename`
2. `batty session set` (color and Theme)
3. `batty tab rename`
4. `batty tab close`
5. `batty reminder list` and `batty reminder cancel`
6. `batty background apply`

## Current state (checked against `main` at `1b2da996`)

### Sessions

- **Fields a Session has** (`BattyKit/Sources/BattyKit/Runtime/SessionRuntime.swift`): `title` + `titleOverride` (`:10, :18`), `themeOverride: ThemePair?` (`:28`), `backgroundOverride` (`:35`, private set, written through `setBackgroundOverride` `:276`), `colorIndex: Int` into `SessionColor.allCases` + `colorOverride` (`:61, :71`), `projectSymbol`/`projectSymbolName` (`:79, :88`, `internal(set)`, copied from a Project), `reminder` (`:84`).
- **Premise correction: a Session has no custom hex color and no symbol of its own.** Color is a palette index only; the hex color (`customColorHex`) and the symbol belong to a Project and are only copied to a Session that was opened from one. The Sidebar's context menu (`Views/SessionSidebarView.swift:530-560`) offers Rename, Reset Name, Set Color… / Reset Color, Set Session Theme… / Clear Session Theme, and Set/Clear Session Background. There is no Session symbol picker and no hex color. So `session set --color-hex` and `--symbol` from the original request **have nothing to write** without adding new Session model fields and new Sidebar drawing, which the Sidebar-row rule (AGENTS.md, "never grow the Session row") argues against. Recommendation: leave them out. An agent that wants a hex color or symbol makes a Project (`batty project create --color-hex/--symbol`). See Open questions.
- **Mutators the UI uses:**
  - Rename: `AppStateStore.renameSession(id:to:)` (`Runtime/AppStateStore.swift:1847`) → `WindowRuntime.renameSession` (`Runtime/WindowRuntime.swift:488`): trims, ignores empty, sets `titleOverride`, records the name cache, and cancels in-flight AI naming. Reset Name: `clearSessionName(id:)` (`AppStateStore.swift:1857`).
  - Color: `WindowRuntime.setSessionColor(id:to:)` (`WindowRuntime.swift:288`, idempotent, rejects out-of-range) and `resetSessionColor(id:)` (`:304`). Names are `ProjectVocabulary.colorNames` (`BattyXPCCore/ProjectLayoutDocument.swift:293`), the `SessionColor` order.
  - Theme: `ThemePreference.setSessionTheme(_:for:)` (`Theme/ThemePreference.swift:276`) is the single writer from the Theme Selector: sets `.both(name)`, clears any preview, applies. Clear Session Theme sets `themeOverride = nil` then `applyActiveSessionTheme(for:)` when that Session is selected (`SessionSidebarView.swift:546-551`). `ThemePair(dark:light:)` (`Theme/ThemePair.swift:17`) allows per-appearance slots; only a Project restore writes them separately today (`WindowRuntime.swift:365`).

### Tabs

- Tab rename is a direct write of `TabRuntime.titleOverride: String?` (`Runtime/TabRuntime.swift:11`) from `Views/PaneView.swift:142-144` (empty → nil) and the Reset item (`:592`). There is no store mutator; add one (`AppStateStore.renameTab(id:to:)`, idempotent: skip an equal write) and have `PaneView` keep its own path or move to it (planner's call, no behavior change).
- Tab close: `AppStateStore.closeTab(id:)` (`AppStateStore.swift:1888`) → `WindowRuntime.closeTab(id:)` (`WindowRuntime.swift:590`): removes the Tab, collapses an emptied Pane, and **removes the Session when its tree empties**. `requestCloseTab(id:)` (`:663`) raises the confirmation sheet when `tab.needsConfirmClose`.
- **Premise correction on `--force`.** The existing XPC close verbs refuse rather than force: `pane close` (#0283) and `session close` (#0382) return `.needsConfirmation` (exit 4) when any Tab `needsConfirmClose`, and their docs state "no `--force` flag exists to bypass this" (`batty/SessionInfoCommand.swift:255-262, 276-280`; `AppStateStore.swift:1036-1068`). They also refuse closing the app's last Pane/Session (`.refusedLastPane`, `AppStateStore.swift:974-991`). Recommendation: `tab close` follows the same pinned shape, no `--force` (Open questions if the user wants one). Note that `needsConfirmClose` is hard-coded `false` by `Util/TerminalViewState+Polyfill.swift:41`, so the refusal can't fire against a live surface today; it is unit-testable through `TabRuntime.needsConfirmCloseOverride` (`TabRuntime.swift:177`).

### Reminders

- One pending Reminder per Session (`Model/SessionReminder.swift`, `id: UUID`). Fired Reminders live in `FiredReminderStore` (`Runtime/FiredReminderStore.swift`) and show in the Reminders popover as "due" rows, pending ones as "upcoming" (`Views/RemindersListModel.swift:5-11`).
- `batty session remind` (`batty/SessionRemindCommand.swift`, #0567) sets, replaces or cancels one Session's Reminder. `batty list` and `session info` already print `reminder=<dueAt>` per Session (`batty/ListCommand.swift:115`), and the topology JSON carries `TopologyReminderPayload` with `id`, `dueAt`, `note`, `kind`, `createdAt` (`BattyXPCCore/TopologyPayload.swift:225`). Fired Reminders are not exposed over XPC at all.
- Mutators: `cancelReminder(id:forSessionID:)` (`Runtime/AppStateStore+Reminders.swift:147`, returns whether it cancelled), `cancelReminder(forSessionID:)` (`:139`), `markFiredReminderDone(id:)` (`:386`).

### Backgrounds

- Runtime levels: `SessionRuntime.setBackgroundOverride` (`SessionRuntime.swift:276`), `PaneRuntime.setBackgroundOverride` (`Runtime/PaneRuntime.swift:221`, clears every Tab's own value, which is what the Pane sheet does), `TabRuntime.setBackgroundOverride` (`TabRuntime.swift:352`). All three conform to `BackgroundOverrideHolder` (`Views/BackgroundOverrideSettingsView.swift:7`), the protocol the background sheet writes through. The sheet adopts a picked library image with `importer.adoptImage(path:from:)` (`BackgroundOverrideSettingsView.swift:380`).
- #0700's resolution path: `AppStateStore.resolveProjectImages` (`Runtime/AppStateStore+ProjectWriteXPC.swift:134-180`) turns `.hosted(set:title:)`, `.hostedID` and a file into a path via `HostedBackgroundsModel.catalogsForCLI()`, `hostedImage(set:title:)`/`hostedImage(id:)`, `hosted.select(image)`, `importer.adoptImage` or `importer.importImage`. `ProjectWriteBuilder` owns the opacity rules (`--opacity` defaults to `TerminalBackgroundSettings.firstImageOpacity` = 15 with an image, rejected without one; `--terminal-opacity` defaults to 100). Reuse both, don't copy them.
- **#0702 seeds.** A Pane or Tab opened from a Project carries `projectBackgroundSeed` (`Runtime/AppStateStore+ProjectSlotBackgrounds.swift:7`). A Project save writes a level only while its own value still equals its seed. A CLI apply that writes a different value through the normal setter therefore already counts as the user's change, and the next Project save leaves it alone, the same as a sheet edit. `background apply` must **not** touch `projectBackgroundSeed`. The Session level has no seed: a later Project save that changes the Project background still replaces it (#0653's changed-fields rule), exactly as after a Sidebar edit.

### Capabilities and MCP

- Annotations are per archetype, keyed by verb path (`batty/CapabilitiesCommand.swift:170-240`). `close` is `destructiveHint: true`; `edit` (#0700) is non-destructive and idempotent. `CapabilitiesInputSchemaTests.leafArchetypeByVerbPathCoversExactlyTheShippedVerbPaths` fails for any verb without a row.

## Expected behavior

All verbs resolve their target the way existing verbs do (`--session`/`--tab`/`--pane` flag, then `BATTY_SESSION_ID`/`BATTY_TAB_ID`/`BATTY_PANE_ID`, then the focused one), exit 4 on an unknown id, print nothing (or the id) on success, and take `--json`. None selects or activates a window, except where noted.

### 1. `batty session rename [--session ID] (NAME | --reset)`

- `NAME` → `AppStateStore.renameSession(id:to:)`. An empty or whitespace-only name is a validation error (exit 64-style `ValidationError`), not a silent no-op.
- `--reset` → `clearSessionName(id:)`, the Sidebar's Reset Name.
- Annotation: `edit`.

### 2. `batty session set [--session ID] [--color NAME | --reset-color] [--theme NAME | --dark-theme NAME --light-theme NAME | --no-theme]`

- At least one option is required.
- `--color` takes a `ProjectVocabulary.colorNames` name → `setSessionColor(id:to:)`; `--reset-color` → `resetSessionColor(id:)`.
- `--theme NAME` → `setSessionTheme(_:for:)` with the resolved `GhosttyThemeDefinition` (both slots, same as the Theme Selector). `--dark-theme`/`--light-theme` set one or both slots of `themeOverride` (a missing slot keeps the current value, matching `ThemePair`'s "unset slot follows the global preference"), then apply the effective Theme to the Session (`applyTheme(_:to:)` for the current appearance) the way `setSessionTheme` does. `--no-theme` mirrors Clear Session Theme, including the selected-Session re-apply.
- Theme names resolve case-insensitively against the Theme catalog; an unknown name exits 4 and names it (unlike the Project path, where an unknown Theme is a warning, because a live Session can't apply a missing Theme).
- No `--color-hex` or `--symbol` (see Current state; Open questions).
- Writes go through the named mutators only; no direct `SessionRuntime` field writes from the XPC handler beyond what those mutators do.
- Annotation: `edit`.

### 3. `batty tab rename [--tab ID] (NAME | --reset)`

- Sets or clears `TabRuntime.titleOverride` through a new idempotent store mutator, with the same trimming as `PaneView` (empty → reset). Exit 4 for an unknown Tab.
- Annotation: `edit`.

### 4. `batty tab close [--tab ID]`

- Closes one Tab through `AppStateStore.closeTab(id:)`, so an emptied Pane collapses and an emptied Session is removed, as with ⌘W.
- Refused with exit 4, closing nothing, when: the Tab id is unknown; the Tab `needsConfirmClose` (no `--force`, matching `pane close`/`session close`); or the Tab is the app's last Tab across every window (the `.refusedLastPane` guard one tier down).
- The outcome is an enum like `PaneCloseOutcome` (`closed`, `unknownTab`, `needsConfirmation`, `refusedLastTab`).
- Annotation: `close` (destructive).

### 5. Reminders: `batty reminder list` and `batty reminder cancel ID`

Recommended shape: a new `reminder` noun rather than `session remind --list`, because listing spans every Session and Window while `session remind` acts on one target Session. `session remind --cancel` stays unchanged.

- `batty reminder list [--session ID] [--json]` lists pending Reminders (`state: "pending"`, from each Session's `reminder`) and fired Reminders not yet removed (`state: "due"`, from `FiredReminderStore`, with `read`). Each row: `id`, `sessionID`, `sessionName`, `state`, `dueAt` (ISO 8601 UTC, as in `TopologyReminderPayload`), `note`, `kind`. Order matches the Reminders popover (`RemindersListModel`). `--session` filters. Annotation: `list`.
- `batty reminder cancel ID` cancels a pending Reminder by its id through `cancelReminder(id:forSessionID:)` (the app finds the Session). A due (fired) Reminder id is removed like the popover's Done (`markFiredReminderDone(id:)`). An unknown id exits 4. Annotation: a new `cancel` archetype, `destructiveHint: true`, `idempotentHint: false`.
- Update `docs/batty-cli-design.md`'s noun list for the new `reminder` noun.

### 6. `batty background apply [--session ID | --tab ID | --pane ID] (--background-set NAME --background-image TITLE | --background-id URL | --background-file PATH | --none) [--opacity 0-100] [--terminal-opacity 0-100]`

- Exactly one level flag (default: the calling Tab's Session, i.e. `--session` resolved from `BATTY_SESSION_ID`/focus); exactly one source. `--background-id` is added beside the requested options for parity with `project create` (#0700) and `background list`'s ids.
- Image resolution reuses #0700's `resolveProjectImages` path (hosted: `catalogsForCLI` → `hostedImage` → `hosted.select`; My Images by digest; a file through `importer.importImage`), factored so it no longer assumes a Project. A failed fetch exits 4 and changes nothing.
- Opacity rules come from `ProjectWriteBuilder` (`--opacity` defaults to 15 with an image and is rejected without one or with `--none`; `--terminal-opacity` defaults to 100). If the level already has an image and only opacity flags are given, apply them to its current value (no source required in that case; planner to confirm the conflicts encoding).
- Writes go through the level's `setBackgroundOverride` (the `BackgroundOverrideHolder` path the sheet uses). `--none` writes `nil` (follow the next level up), matching Clear Session/Pane/Tab Background. A Pane write clears its Tabs' own values, as the Pane sheet does.
- Does not touch `projectBackgroundSeed`; a CLI apply counts as a user change and survives later Project saves at Pane and Tab level (#0702).
- Annotation: `edit` (idempotent: the setters skip equal writes).

### Shared

- Six new XPC verbs in `BattyXPCCore/XPCVerb.swift` with request/reply payloads, dispatched in `AppXPCService`, handled in new `AppStateStore+*XPC.swift` files following `AppStateStore+ProjectWriteXPC.swift`.
- Each verb has a `CapabilitiesDescribable` schema with `conflicts`/`requires` encoding the option groups, and an annotations row.
- MCP instructions (`batty/MCPInstructions.swift`) mention rename/set/background apply only if the existing hint list covers comparable verbs; no new prose otherwise.
- No new UI, menus or Settings rows.

## Acceptance criteria

1. Each of the six verbs exists in `batty` and `batty-beta`, appears in `batty capabilities`, and is an MCP tool with the annotation above (`tab close`, `reminder cancel` destructive).
2. `session rename`, `session set`, `tab rename` produce the same model state as the Sidebar/Tab-bar actions, verified against the store, with no new direct field writes outside store mutators.
3. `tab close` refuses (exit 4, nothing closed) for an unknown Tab, a Tab needing confirmation, and the app's last Tab; otherwise closes exactly that Tab and collapses empties as ⌘W does.
4. `reminder list` shows pending and due Reminders across all windows; `reminder cancel` cancels a pending one by id and removes a due one; unknown ids exit 4.
5. `background apply` resolves images exactly as `project create` does, writes through the level's setter, honors the opacity rules, and a following Project save leaves a CLI-applied Pane/Tab background in place.
6. `docs/batty-cli-design.md`, `docs/batty-cli-agent-workflows.md`, `.claude/skills/batty-cli/SKILL.md`, `Concepts.md` (Reminder and the CLI mentions; bump its version) and the generated `website/docs/cli/` reference are updated; the changelog notes the verbs under 1.5.0.
7. `./build.sh` and `./build.sh unit` pass; the docs tools' `--check` modes pass.

## Open questions (recommended defaults in bold)

1. Session hex color and symbol: **leave out** (no model field; Projects cover it), or add `SessionRuntime` fields drawn by the Sidebar row?
2. `tab close --force`: **no**, matching `pane close`/`session close`; or add `--force` to all three together in a later issue.
3. Reminders shape: **new `reminder` noun with `list` and `cancel`**, or `session remind --list`.
4. `background apply` default level when no flag is given: **the calling Session**, or require an explicit level.
