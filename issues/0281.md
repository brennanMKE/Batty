## Description

First child of the #0257 umbrella and the prerequisite for every agent-facing verb: an agent (Claude Code) running *inside* a pane must know which session/pane/tab it is in before it can split, close, or inspect anything relative to itself. Three deliverables:

1. **Env injection at spawn:** inject `BATTY_SESSION_ID`, `BATTY_PANE_ID`, `BATTY_TAB_ID` into every surface at spawn, so every child process in the pane (the shell, Claude Code, `batty` itself) inherits them. #0257 Foundation §2 describes prepending `export …;` to the launch command (supacode's pattern).
2. **`batty id [--json]`** — prints that context **from env alone**, no app round-trip (#0257 Foundation §3). Works even when the app is unreachable. **`id` is the primary command name; `whoami` is registered as an alias.** *(Decided 2026-07-26 by the user; #0257 originally specified `whoami` only.)* Rationale: the question an agent is actually asking is "which pane am I in?", and `id` is the shorter, more guessable name for that — the CLI's whole purpose here is to be reached for by an agent that has not read the docs. `whoami` is kept as an alias because it is the Unix idiom a human will try first, it costs nothing, and #0257 and `docs/batty-cli-design.md` already use that spelling throughout. **All new help text, output, and documentation should say `batty id`;** treat `whoami` as an undocumented-but-supported alias. `swift-argument-parser` supports this via `CommandConfiguration(commandName:aliases:)` — verify that spelling against the pinned version, and if aliases are unavailable, declare a second `ParsableCommand` delegating to the same implementation rather than duplicating logic. **This issue's implementer also updates the `whoami` references in `docs/batty-cli-design.md` and `docs/batty-cli-install.md`** when the command ships; they are left alone until then rather than renaming an unbuilt command across the docs.
3. **The shared target-resolution chain** — explicit flag → `BATTY_*` env → focused element — implemented once as a unit-testable helper that #0282 (`pane split`), #0283 (`pane close`), and the already-shipped `batty session info` all consume.

## Resolution notes

> 🟢 Resolved 2026-07-27 — every surface now spawns carrying `BATTY_SESSION_ID`, `BATTY_PANE_ID`, and `BATTY_TAB_ID`; `batty id` (alias `whoami`) reports them from env alone; and one shared resolution chain backs both it and `batty session info`.

An agent inside a pane can now identify itself. That the vars actually reach a **live** spawned shell needs the user's runtime sign-off — headless verification tops out at proving libghostty accepts the configuration.

## Root cause

Starting state, not a defect. #0274 shipped the read verbs, so an agent could see the layout — but nothing told it *which* pane it was in, and every context-sensitive verb had to be given an explicit id. #0257 Foundation §2/§3 specified the fix; this issue builds it.

## Fix

**Env injection uses libghostty's `env =` config directive, not the shell prepend #0257 anticipated.** The implementer queried the bundled binary rather than reading docs and found `env = KEY=VALUE` (available since libghostty 1.2.0, settable repeatedly). It is strictly better than prepending `export …;` to the launch command: the `command` block is only set when a custom shell is configured, so the prepend would have silently skipped the default-shell case, and it carries no shell-quoting hazard.

**The ids aren't knowable where the configuration is currently built**, so injection is deferred. `TerminalController.init` creates `ghostty_app_t` synchronously inside `TabRuntime.init`, but the real surface — `ghostty_surface_new`, the process exec — only happens on first SwiftUI render via `TerminalHostStore.terminalView(for:windowID:)`. `TabRuntime` now carries nil-at-construction `paneID`/`sessionID` plus `attachContext(paneID:sessionID:)`, which re-applies the full configuration once both are known. Four call sites cover every creation path: `SessionRuntime.init` (via `tree.attachToSession`), `PaneRuntime.addTab`, `SplitTree.splitFocusedPane`, and `SplitTree.splitFullDimension`.

**`batty id`** (with `whoami` registered via `CommandConfiguration(aliases:)`, verified present in the pinned swift-argument-parser 1.8.2) prints the context from env alone — no XPC, no broker, works when the app is unreachable.

**The shared chain** — explicit flag → `BATTY_*` env → focused element — lives in `BattyCLICore` as `BattyContextEnvironment` / `BattyIdentityContext` / `BattyTargetResolver`, all `nonisolated` at type level. `Foundation` only, so the `batty` executable still links no product dependencies (#0252's `@rpath` hazard, #0249's build-graph hazard). `session info`'s `resolveSessionID()` now delegates to it, closing the seam #0274 deliberately left.

**Malformed-value policy:** a malformed *flag* always errors — the user typed it this time. A malformed *env* value is treated as absent and falls through, because env is a hint reflecting spawn time, not truth. `batty id` itself requires all three vars present and well-formed, since a partial identity would mislead.

## Review

Reviewed by `claude-opus-5`, two rounds — the first deliberately heavyweight, the second deliberately narrow.

**Round 1 found no correctness defects**, and the verification behind that is worth recording because it went past what was claimed. Rather than accepting "the test would have failed if the directive were rejected," the reviewer built a standalone harness against the *pinned* libghostty and ran a control: a bogus key yields `diagnostics=1 "unknown field"`, `env` yields `0`, and a malformed `env` value yields `"env: value required"` — proving it is genuinely the env field and not an accidental match. They confirmed `prepareConfig` fails closed on diagnostics, which is what makes the implementer's `renderedConfig.contains(…)` assertions real proof of acceptance rather than of string formatting.

Two load-bearing assumptions nobody had checked were also verified: `ConfigurationBuilder.withCustom` **appends**, so all three `env` lines survive rather than last-write-wins; and `applyShellAndAppearancePreferences` builds a *fresh* `TerminalConfiguration`, so the attach-time re-apply cannot accumulate duplicates.

The four attach sites were re-derived exhaustively rather than trusted — `tabs.append` appears exactly once in the codebase, so there is no move-tab-between-panes path to miss — and pre-spawn ordering was traced independently, including confirming that the second `setTerminalConfiguration` does not clobber an inherited working directory.

Round 1's three findings were all minor: a doc parenthetical that contradicted `Concepts.md`, a missing `--json` shape test the issue had asked for, and an inaccurate doc comment.

**Round 2 approved.** The reviewer confirmed the JSON test is genuinely shape-sensitive by running a negative control (renaming `tabID` → `surfaceID` makes the assertion false), and built the CLI to confirm `--help` really does render `id, whoami`.

## Gotchas

- **Workspace persistence will become a fifth attach site.** The four call sites are complete *today* only because no `SplitTree` is ever built from saved state — there is no restore path. When persistence lands (#0221), a restored pane whose `attachContext` is missed will spawn without the env vars, silently, and only on that path.
- **`env =` requires `KEY=VALUE`** and libghostty rejects a bare key with `"env: value required"`. Distinct keys accumulate; the same key overwrites. `withCustom` appends, and the configuration is rebuilt rather than mutated on re-apply — both are relied upon.
- **`BATTY_TAB_ID` is the surface id.** The Surface registry (`TerminalHostStore.terminalViews`) is keyed by tab id, and `BattyContextEnvironmentKey` has exactly three cases — no `BATTY_SURFACE_ID` is injected. `surface` is an accepted **alias** for the `tab` noun, kept rather than rejected because a Tab may host a web view or other non-terminal view later while "Terminal Session" stays terminal-specific.
- **`BellFeedEntry.surfaceID` is vestigial** — `recordBellTick(forTabID:surfaceID: UUID = UUID())` defaults it to a fresh random UUID, and every real caller takes that default, so the stored value is inert and nothing reads it. Unrelated to this issue; worth cleaning up whenever the feed model is next touched.
- **`whoami` cannot be undocumented.** ArgumentParser lists aliases automatically, so `batty --help` renders `id, whoami`. The issue's "undocumented-but-supported" wording is unachievable; all prose and output say `batty id` instead.
- **`batty id` is env-only by design.** #0274's Option B drop took the pty-device-path field with it, so there is no `ttyname(stdin)` fallback for a scrubbed environment (`sudo`, some nested shells). It fails cleanly rather than guessing. If that proves painful, the pty plumbing is a new child of #0257.
- **`docs/batty-cli-design.md` §1.1 still reads "No `surface`, no `workspace`, no `worktree`."** Compatible with the alias decision — an alias is not a member of the noun set — but read alone it implies a flat rejection. Folded into the terminology sweep.

## As-built starting points (verified against source 2026-07-26)

- **The CLI today** (`BattyKit/Sources/batty/BattyCLI.swift`) has subcommands `new` (default; bare `batty` / `batty <path>`), `ping`, `status`, `list`, and `session` (with only `info`). No `whoami`, no `pane` noun, and `BATTY_*` appears nowhere in app code — only in comments anticipating this issue.
- **#0274 left the seam for exactly this work.** `SessionInfoCommand.resolveSessionID()` (`BattyKit/Sources/batty/SessionInfoCommand.swift`) implements `--session` flag → `nil` fallthrough, with a marked comment: *"the eventual resolution order is `--session` flag → `BATTY_SESSION_ID` env var → focused session … its env-var read slots in as a middle branch in `resolveSessionID()` below, between the flag check and the `nil` fallthrough."* And `AppStateStore.sessionInfoPayload(sessionID: UUID? = nil)` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift`, ~line 211) already accepts `nil` as "no explicit target," so retrofitting the env branch touches nothing app-side. Retrofit `session info` onto the shared helper as part of this issue so there is one chain, not two.
- **The spawn-time configuration point** is `TabRuntime.applyShellAndAppearancePreferences(to:)` (`BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift`), which builds the `TerminalConfiguration` and sets `builder.withCustom("command", shell)` — but **only when the custom-shell preference is non-empty**. The default case sets no `command` at all, so the "prepend `export …;`" approach must also synthesize a command line for the default-shell case (or find an env-passing mechanism in the libghostty configuration — not verified whether one exists).
- **An ordering wrinkle the implementer must resolve:** that configuration is applied inside `TabRuntime.init`, but a `TabRuntime` is constructed *before* it is placed into a `PaneRuntime` (`SplitTree.makePane` builds `PaneRuntime(tabs: [TabRuntime(...)])`) and before the pane joins a session — so `BATTY_PANE_ID`/`BATTY_SESSION_ID` are not knowable at the point the config is currently set. The ids are all stable UUIDs, so the fix is plumbing (pass ids down, or set/update the config later, before the surface actually spawns), not a model change. Not deciding the mechanism here; flagging that the obvious injection point does not currently have the data.

## Decisions carried from #0257 / #0274

- **`whoami` is env-only in v1.** #0274 dropped the topology snapshot and with it the pty-device-path field that would have powered a `ttyname(stdin)` fallback for scrubbed environments (`sudo`, nested shells). No runtime plumbing exposes a tab's pty device path today; #0257's amendment says the implementer must either add that plumbing or accept env-only. **This issue accepts env-only** — `whoami` fails cleanly (exit 1, message on stderr) when the env is absent. If the scrubbed-env case proves painful, the pty plumbing is a new child under #0257, not scope creep here.
- **Env is a hint, not truth** (#0257 Notes): `BATTY_*` reflects spawn time. Ids are stable UUIDs so this holds today; if panes ever move between sessions, the authoritative pane→session mapping is a live `batty list` reply, and the app should resolve session from the pane id rather than trust `BATTY_SESSION_ID`.
- **Helper placement:** the chain needs only Foundation (env access + UUID parsing), so it belongs in a target the CLI links without pulling in the app — `BattyCLICore` or `BattyXPCCore`, never full `BattyKit` (the #0252 link-dependency hazard and the #0249 build-graph hazard both apply to anything the `batty` executable links).

## Binding constraints (copied — do not merely cross-reference)

- **Payloads are `Codable, Sendable` structs carried as JSON-encoded `Data`** inside the `@objc` protocols, `nonisolated` at type level; protocol requirements are `nonisolated func`; reply blocks `@escaping @Sendable`. Guard any new payload type with off-actor round-trip helpers as `XPCContractTests` does. (`whoami` itself does no XPC; this binds any payload work done while retrofitting `session info`.)
- **Every Foundation-supplied handler closure gets `@Sendable`** — there is no compiler warning, and the failure is a silent `SIGTRAP` inside the very handler that would have logged the error.
- **`os.Logger` interpolation of a dynamic `String` defaults to `.private`** — add `privacy: .public` explicitly (#0274 nearly shipped eight blinded log lines this way).
- **Verify isolation guards under a forced rebuild** (`rm -rf .build`); stale targets produced false "still builds" results twice on the XPC track.
- **Code-signing protocol:** never run `scripts/build.sh` for iteration (its `unit` path can't disable signing); use `cd BattyKit && swift test` and `xcodebuild … CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO`. The user's Developer ID certificate was revoked once by repeated signed local builds.
- **Anything aimed at a background session must not steal focus or change the active session** — assert against the store (`selectedSessionID`, focused pane, active tab), not merely absence of a crash.

## Verification expectations

Follow the #0271/#0274 pattern:

- **Unit tests for the pure parts:** the resolution chain's precedence (explicit flag beats env; env beats the `nil`/focused fallthrough; each id — session, pane, tab — resolved independently), malformed-UUID handling for both flag and env values (decide and test whether a malformed env value errors or falls through — document the choice), and `whoami` output shape for both plain and `--json` forms, including the missing-env failure.
- **Retrofit test:** `session info` with `BATTY_SESSION_ID` set and no `--session` flag targets the env session; with both set, the flag wins.
- `cd BattyKit && swift test` and `xcodebuild … CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO` green; `otool -L` on `batty` still shows zero `@rpath` dependencies.
- **Needs the user's runtime sign-off** (do not disturb the running app; coordinate): in a freshly spawned pane, `echo $BATTY_PANE_ID` prints a UUID matching `batty list` output; `batty whoami` agrees; a pane created by a split carries its *own* ids, not the parent's; ids survive into a nested shell and into a running agent's environment.
