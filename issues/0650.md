## Description

The Background Images picker always opens on the My Images tab. For a user who picks hosted images from Background Sets, My Images is empty (hosted images never join My Images, per `Concepts.md`), so every open lands on "No background images yet." and they must switch tabs by hand. When the current background is already a Background Sets image, the Background Sets tab does not highlight it or scroll to it either, so there is no way to see what is chosen without hunting through every set.

User report, 2026-11-17: "Make background image selection better. When I bring it up it starts on the empty tab instead of the list of sets, which would be better. Also, if I have already selected an image from those sets it should show that tab and also have the image selected and scrolled into view. The fact that it does not do this is weak UX." The user was choosing Pane backgrounds in the Project Editor, picking images such as "Sky Gardens at Dawn" from the Future Cities set.

### Current state (checked against `main` at `5ca5c9ca`)

- **The tab is fixed at My Images.** `BackgroundImagesView` declares `@State private var tab: Tab = .myImages` (`BattyKit/Sources/BattyKit/Views/BackgroundImagesView.swift:22`). Nothing sets the initial tab from `current` or from what the user last used. Focus also goes to the My Images grid on appear (`:75-79`).
- **"The empty tab" is My Images with no library images.** `content` shows "No background images yet." with an Add from File… button when `model.entries` is empty (`BackgroundImagesView.swift:103-118`). `model.entries` is the My Images library scan (`Model/BackgroundImagesModel.swift:64-70`). Hosted images live in the hosted image store (`BackgroundImages/Hosted/`) and "never join My Images" (`Concepts.md:186`), so a user who only uses Background Sets always sees this empty state.
- **Only My Images knows the current image.** `BackgroundImagesView` gets `current: String?` (`:18`), works out `currentDigest` from the path's digest folder (`:33-35`), and passes `isCurrent: entry.digest == currentDigest` to each My Images cell (`:140`, highlighted at `:333`). `BackgroundSetsView` is built with only `model` and `onPick` (`:61`; `BackgroundSetsView.swift:14-16`). Its `GridSelection<HostedImageKey>` starts empty (`BackgroundSetsView.swift:18`), and a cell is outlined only when `selection.id == key` (`:230`), which happens only after a click in this sheet (`:143-146`).
- **Nothing scrolls to any image.** Neither view uses `ScrollViewReader`, `scrollTo` or `scrollPosition`. In My Images the current cell is outlined but may be off screen. `BackgroundImagesScrollMonitor.swift` is a diagnostics ring for scroll jumps, not scroll positioning.
- **The current image can be matched to a set image.** A picked hosted image is copied into the target's folder under its digest folder (`TerminalBackgroundImageImporter.adoptImage`, `Settings/TerminalBackgroundImageImporter.swift:240-244`; `digest(ofPath:)` at `:104-108`), so `current`'s digest equals the hosted copy's digest. Each `HostedBackgroundCell` already works out its own digest from `hosted.store.localPath(for:)` (`BackgroundSetsView.swift:240-243`), and `HostedImageRecord` maps `url` to `digest` (`Settings/HostedImageStore.swift:10-14`). A Project Tab's image identity is `.hosted(url:name:)` for a Background Sets image (`Model/ProjectTabImage.swift:11-13`, `derive` at `:82-93`; `Settings/TabImageIdentity.swift`). So both a digest match and a URL match are possible.

### Every place the picker opens (all open on My Images today)

`BackgroundImagesView` is built in two places, and both pass `current`:

1. `TerminalBackgroundControls` Choose… sheet (`Views/TerminalBackgroundControls.swift:51`, sheet at `:65-75`, `current: current.imagePath`). This is used by:
   - Settings → Appearance → Background, the app-wide default (`Views/SettingsView.swift:292`);
   - `BackgroundOverrideSettingsView` (`Views/BackgroundOverrideSettingsView.swift:294`), which is the gear sheet for a Pane (`Views/PaneView.swift:156`), a Tab (`Views/SessionSidebarView.swift:162`) and a Session (`SessionSidebarView.swift:172`), and the Project Editor's Project background (`Views/ProjectEditorView.swift:456`), Pane background (`ProjectEditorView.swift:957`) and Tab background (`ProjectEditorView.swift:1102`).
2. Pane → Background Images… (`Commands/BattyCommands.swift:612-622`), received in `Views/SessionDetailView.swift:72-77`, which shows `PaneBackgroundImagePickerSheet` (`Views/PaneBackgroundImagePicker.swift:38-50`, `current:` the Pane's effective image path).

## Steps to reproduce

1. With no images in My Images, open the Project Editor for a Project and click a terminal Pane's background edit button, then Choose….
2. The picker opens on My Images, showing "No background images yet."
3. Switch to Background Sets and pick an image (for example "Sky Gardens at Dawn" in Future Cities). The sheet closes and the Pane's image is set.
4. Click Choose… again.

## Expected behavior

- **Default tab is Background Sets** when the current image is not a My Images image (including when there is no image).
- **Current image is a Background Sets image:** the picker opens on Background Sets with that image's cell selected (outlined, the same highlight a click gives) and scrolled into view, so its set is visible without scrolling by hand.
- **Current image is a My Images image** (the natural generalization): the picker opens on My Images with that cell selected and scrolled into view.
- This applies to every entry point listed above, since they all share `BackgroundImagesView`.
- Arrow keys and Return start from the selected current image, as My Images already does via `currentDigest` (`BackgroundImagesView.swift:239-246`).
- No new writes in `body`, and the scroll must not cause the visible-row jumps `GridSelection` and the scroll monitor were added to prevent (`GridSelection.swift:5-7`). See `docs/swiftui-observation-rules.md`.

## Actual behavior

At step 4 the picker opens on the empty My Images tab again. After switching to Background Sets, no cell is outlined and the list is scrolled to the top, so the user has to find "Sky Gardens at Dawn" by hand. In My Images, the current image is outlined but not scrolled to.

## Notes

### Open questions

1. **Matching rule.** Should the current path be matched to a set image by digest (the hosted copy's digest folder equals the adopted copy's), by the `HostedImageRecord` URL for that digest, or by both? Hosted downloads are re-encoded per Mac, so the digest is valid only on this Mac. In the Project Editor, a Tab whose identity is `.hosted(url:)` could be matched by URL directly.
2. **Image no longer in any catalog** (dropped by the catalog, or its catalog was removed): open on Background Sets with nothing selected, or on My Images? Suggest Background Sets with nothing selected.
3. **Catalog still loading or offline:** the sets arrive after the sheet appears. Should the selection and scroll happen once the image's set has loaded, at most once per open, and never again after the user scrolls or types in the filter?
4. **Active filter text:** if the filter hides the current image, should it be cleared on open? The query is `@State` (`BackgroundSetsView.swift:19`), so it starts empty on each open today.
5. **Downloaded image cache** (`BackgroundImages/Downloaded/`): a synced Project Tab's image downloaded there is a hosted image with a URL but no hosted-store copy. Is it treated as a Background Sets image for this purpose? It probably should be, matched by URL.
6. **No current image:** should the default be Background Sets always, or should the last tab the user used be remembered? The report asks for Background Sets; remembering the last tab is not requested.
7. **Follow-the-parent sheets:** in a gear sheet that follows (`editor.isFollowing`), the controls are disabled. Should `current` be the effective (inherited) image, as Pane → Background Images… already uses, so the inherited image is shown as current?

### Related

- #0629 made Background Images only a picker. #0595 and #0596 cover Background Sets. #0585 covers Tab image identity and the downloaded image cache. `BackgroundSetsTests.swift:24` and `BackgroundCatalogSettingsTests.swift:98,122` click the Background Sets segment first, and `BackgroundSetsTests.swift:392` clicks My Images. Changing the default tab will change what these UI tests assume.

## Plan

Planned 2026-11-17 against `issue/0650` at `8087fc07`. The premises in Current state hold. Two details matter for the design. `current` is always an adopted copy in the target's own folder, so its identity has to be worked out from the digest folder. And `BackgroundImagesModel` lives as long as the store (`AppStateStore.backgroundImages` is lazy), so `entries` and `hosted.contents` may already be filled when the sheet opens, or may arrive later after an `await`.

### Decisions on the open questions

1. **Matching rule: URL identity first, then digest.** The current path goes through `ProjectTabImage.derive(path:hostedRecords:cacheEntries:)`. That is the same rule every Tab writer uses: a hosted record whose digest is the path's digest gives `.hosted(url:)`, then a Downloaded cache entry with a URL, otherwise `.custom(digest:)`. A `.hosted(url)` result is matched to a set cell by `HostedImageKey(url:) == HostedImageKey(image)`, which is `image.full`. A `.custom(digest)` result is matched to a My Images cell by digest, as `currentDigest` already does.
2. **Image no longer in any catalog:** the sheet opens on Background Sets, the selection seeds to the key, no cell shows it and nothing scrolls. That is harmless: the first click on any cell replaces the selection.
3. **Catalog still loading or offline:** the selection is seeded when the view is built, so a cell shows the outline the moment it exists. The scroll runs once per appearance of the tab, when the current image first shows in `hosted.contents`. `contents` is written only after an `await` in `loadCachedStates`/`refresh`, so the flip is event-origin. The scroll is skipped if the filter has text by then. A user who scrolled by hand before the catalog arrived still gets one scroll when it arrives. Detecting a hand scroll would take a geometry-origin write, which the rules forbid.
4. **Filter:** `query` already starts empty on every open, so nothing needs clearing.
5. **Downloaded cache:** counts as a Background Sets image, matched by URL, because `derive` already reads the cache entries.
6. **No current image:** opens on Background Sets. The last tab is not remembered.
7. **Following sheets:** no change. Each entry point keeps passing the `current` it passes today, so the change stays inside the picker. Pane → Background Images… already passes the effective image.
8. **A custom image opens on My Images without waiting for the scan.** `scan()` promotes every non-hosted digest from the app-wide, Project and default folders into My Images, so a `.custom` current image is in My Images once the scan finishes. The tab is chosen at open time from the two small record files and is never flipped later. If the image turns out not to be in My Images (a rare Shared Project copy from another Mac), My Images opens with nothing outlined, as it does today.
9. **My Images does not seed `GridSelection`.** The current image keeps the outline it has today (`isCurrent`), arrow keys already start from `currentDigest`, and Remove… stays disabled until the user selects a cell. That way Delete on open can't offer to remove the image in use. This change adds only the scroll.
10. **Background Sets has no arrow-key navigation today.** Adding it is out of scope. Return or arrow keys on that tab do nothing, as now.
11. **Side effect the user asked for:** opening on Background Sets runs `browseAppeared()` on every open, which marks the catalogs browsed and checks the built-in catalog (throttled to `refreshInterval`). Before this change that happened only once the user clicked the tab.

## Root cause

`BackgroundImagesView` hard-coded `@State private var tab: Tab = .myImages`, and nothing looked at `current` to decide the opening tab. `BackgroundSetsView` always started with an empty `GridSelection` and had no scroll target, so a Background Sets image in use was never outlined or brought into view.

## Fix

- New pure `BackgroundPickerOpening` (`Model/BackgroundPickerOpening.swift`) decides the tab and target from `current` through `ProjectTabImage.derive`: a hosted record or Downloaded entry with a URL opens Background Sets on that `HostedImageKey`, any other digest opens My Images on that digest, and no image opens Background Sets. `BackgroundImagesModel.opening(forCurrent:)` feeds it the two record files.
- `BackgroundImagesView`: `opening`/`tab` start nil and are set in the sheet's `onAppear` (event-origin). Until then the body shows `Color.clear`, so neither tab (nor `browseAppeared`) is built first. My Images scrolls to the current digest once.
- `BackgroundSetsView` takes `current:`, seeds `GridSelection(id: current)` at init, tags cells with `.id(key)`, and scrolls once (only with an empty filter) when the current image is listed.
- Scroll trigger: one `scrollToCurrent(proxy)` guarded by an unobserved `PickerScrollOnce`, called from (a) `onGeometryChange` on the scroll view, once its height is non-zero, and (b) `onChange` of "current image is listed", for a catalog or scan that arrives later. In My Images (round 2) the geometry trigger sits on the grid's own `ScrollView` inside `grid(columns:proxy:)`, not on `content`, so it fires when the grid first gets a size, whether at open or after the first scan. It records the size in the unobserved `PickerScrollOnce.viewportSized`, and `scrollToCurrent` returns without spending the guard until the grid is sized and the current image is listed. The plan's `onChange(initial: true)` and its fallback (`onAppear` on the ScrollView, and on its content) were both tried, and both left the clip origin at 0 in `currentImageInTheLastSetIsScrolledIntoViewOnAppear`. The geometry callback writes no observed state and `scrollTo` changes no constraints or responders.
- Cells expose `.isSelected` when highlighted, for UI tests. `GridSelection` gains `init(id:)`. The scroll monitor no longer hard-codes `tab = "My Images"`.

## Review notes

Round 1, 2026-11-17 — bounced. The reviewer's run matched the draft: `./build.sh` CHECK BUILD: PASSED; `./build.sh ui-typecheck` CHECK UI-TYPECHECK: PASSED; `./build.sh unit BackgroundPickerOpeningTests` PASSED (8 tests), `BackgroundSetsScrollStabilityTests` PASSED (5 tests), `BackgroundImagesModelTests` PASSED (19 tests); full `./build.sh unit` CHECK UNIT: PASSED (4217 tests, 1 skipped; log `build/checks/unit-20261117-234718-42394.log`).

What holds and needs no change:
- **Observation rules.** The `onGeometryChange(for: Bool.self)` trigger complies with `docs/swiftui-observation-rules.md`. It writes only the unobserved `PickerScrollOnce` flag, which is the doc's own "geometry … goes from `onGeometryChange` straight into unobserved storage" pattern. `BackgroundImagesDiagnostics` is documented plain storage ("never observed"). `ScrollViewProxy.scrollTo` is not one of the doc's forbidden AppKit calls (`makeFirstResponder`, `addSubview`, window operations, frame writes on Auto Layout views). The doc does not mention `scrollTo` at all, so it neither allows nor forbids it explicitly. No `Task` hop was added.
- The opening tab is decided in the sheet's `onAppear` (event-origin), not in `body`. `body` only reads `tab`/`opening`, and the `nil` case builds `Color.clear`, so no tab runs `browseAppeared` before the decision.
- The Background Sets path (seeded `GridSelection`, `.id(key)`, warm and late-catalog scrolls) is unit-tested and correct. The UI test updates match the new default.

What must change:

1. **My Images: no scroll on the first open of a launch (cold path).** `BackgroundImagesView.swift` puts the `onGeometryChange` on `content`. On the first open of a launch, `model.entries` is empty (the model is lazy, and the view's own comment says "the grid doesn't exist until the scan's `await` writes `entries`"). So `content` is the empty/progress `VStack`. Its height turns non-zero at once, `scrollToCurrent` returns early because `currentEntryShown` is false, and the Bool never flips again. When the scan's `entries` arrive, only `.onChange(of: currentEntryShown)` fires, and it calls `scrollTo` in the same transaction that first builds the `GeometryReader` and grid `ScrollView`. That is the shape the implementer found lands nowhere (`onChange(initial: true)` and `onAppear` on a scroll view with no size yet), and it consumes the once-guard, so nothing retries. The new UI test covers only the warm reopen, so this path has no coverage at all.
   *Fix:* move the `onGeometryChange(for: Bool.self, of: { $0.size.height > 0 })` trigger onto the grid's `ScrollView` inside `grid(columns:)`, or onto the `GeometryReader` branch of `content`. Then it fires when the grid first gets a size, whether that is at open (warm) or after the scan (cold). Keep the `onChange(of: currentEntryShown)` trigger for an entry that joins a grid that already exists. The `ScrollViewReader` stays outside the `GeometryReader`.
   *Test:* add a hosted unit test, for example `BackgroundImagesViewScrollTests` or in `BackgroundImagesModelTests`'s neighbourhood, reusing `BackgroundSetsScrollStabilityTests`'s hosting harness and turn-bounded `pump` (no sleeps). Seed enough library images to scroll, and host `BackgroundImagesView` with `current` set to the path of the last grid cell's image. Cover both (a) warm: `await model.refresh()` before hosting, and (b) cold: host first, then `await model.refresh()` and pump. Expect the clip origin > 0 in both, and == 0 with `current: nil` on My Images (switch the tab through the binding, or seed a custom current that is the first cell). If the cold case can't be made to land without a `Task`/`asyncAfter` hop, say so in `## Gotchas` rather than hopping.
2. **Misplaced comment in `BackgroundSetsView.swift`.** "`contents` is written only after an `await` in the model, so this flip is an event, never layout." sits above `.onGeometryChange`, but it explains the `.onChange(of: currentIsListed)` two lines below. Move it onto that `onChange`.

Possible follow-up (not blocking, the orchestrator decides): `docs/swiftui-observation-rules.md` has no line on programmatic scrolling. A short note would settle the question this review had to reason out: "`ScrollViewProxy.scrollTo` from `onGeometryChange` is allowed when it is guarded by unobserved state, because it moves the clip origin and changes no constraints or responders. From `onAppear`/`onChange(initial:)` on a scroll view that has no size yet, it lands nowhere."
