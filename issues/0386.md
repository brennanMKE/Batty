# 0386 — Batty presents no window when its executable is launched directly, only when launched through LaunchServices

| | |
|---|---|
| **Status** | open |
| **Module** | App / Window |
| **Platform** | macOS |
| **First seen** | 2026-08-28 |

## Description

The app does not present a window when its executable is spawned by path. Launching `Batty Beta.app/Contents/MacOS/Batty Beta` directly yields a running process with a complete menu bar and **zero windows**; launching the same build with `open -n` yields one window. This is a defect in the app's launch path, not in the test harness — but because `XCUIApplication.launch()` spawns the executable by path, the consequence is that **every test in `BattyUITests` fails at its launch wait** (`XCTAssertTrue failed - Main window did not appear within 10s`, `BattyUITests/BattyUITests.swift:22`), a 100% failure rate across the whole suite.

That blocks the full UI suite and therefore release preflight, and has done so — undiagnosed and repeatedly misattributed — since **2026-06-15**.

Measured directly against the built `Batty Beta.app`, counting windows via System Events 6 seconds after launch:

| Launch method | `BATTY_UI_TEST_MODE` | Windows |
|---|---|---|
| `open -n "$APP"` | unset | 1 |
| `open -n "$APP"` | `1` | 1 |
| direct exec of `$APP/Contents/MacOS/Batty Beta` | `1` | 0 |
| direct exec of `$APP/Contents/MacOS/Batty Beta` | unset | 0 |

## Steps to reproduce

No XCTest required; takes six seconds:

```bash
APP="<DerivedData>/Build/Products/Debug/Batty Beta.app"
"$APP/Contents/MacOS/Batty Beta" &   # 0 windows
open -n "$APP"                       # 1 window
```

Or run any UI test: `scripts/run-ui-tests.sh BattyUITests/SidebarTests`.

## Expected behavior

A content window is presented on launch regardless of the launch mechanism. `XCUIApplication.launch()` sees a window, and `BattyUITests` runs to completion.

## Actual behavior

Under direct exec the process launches, finishes initialization, and presents nothing. Every UI test then fails on its first `waitForExistence`.

## Forensics

From a failing run's `.xcresult` and the unified log:

- The process launches and `BattyAppDelegate.applicationDidFinishLaunching` (`Batty/BattyApp.swift:66`) runs **to completion** — the last statement is `xpcCoordinator.start()` (`Batty/BattyApp.swift:82`), and its `AppXPCCoordinator: anonymous listener resumed` line (`BattyKit/Sources/BattyKit/XPC/AppXPCCoordinator.swift:109`) is emitted.
- The full `.commands` menu bar is built and visible in the accessibility snapshot.
- XCTest's idle detector marks the app idle.
- **Zero** SkyLight/AppKit `context … for window` lines are ever emitted for that pid. A normally-launched Batty emits them.
- No crash, no fault, no exception.

So: the app comes up healthy and simply never gets a window.

## Suspected cause (to be confirmed, not assumed)

`Batty/BattyApp.swift:15` declares the content scene as:

```swift
WindowGroup(for: WindowID.self) { $windowID in
    ContentView(windowID: windowID)
        .background(OpenWindowHookInstaller())
} defaultValue: {
    AppStateStore.shared.initialWindowID
}
```

A data-driven, restorable `WindowGroup` negotiates "present a fresh window vs. restore a previous one" through launch/session state that a direct `exec` may not establish. Before **#0237** (commit `7a92f22`, merged 2026-06-15) the scene was a plain `Window(mainWindowTitle, id: "main")`, which always self-presents.

Corroboration: `issues/0240.md` records the identical total-suite signature (`Main window did not appear within 10s`, 66/66 tests) appearing on **2026-06-15 — the same day #0237 landed** — and attributes it to an LLDB/toolchain fault. The same misattribution recurs in `issues/0338.md` on 2026-08-20.

The implementer must confirm the mechanism experimentally (e.g. instrument scene creation, compare `NSApplication` launch state / `NSApplicationLaunchIsDefaultLaunchKey` / restoration negotiation between the two launch paths) before changing the scene. Do not treat the above as established.

## Do not regress what #0237 bought

`issues/0237.md` is Phase 4 of the #0234 multi-window umbrella and is the change that made multi-window exist at all. Whatever fixes this must preserve:

- **`WindowID`-keyed windows.** The presented value is the stable `WindowID`; `ContentView(windowID:)` → `RootWindowView(windowID:)` resolves its per-window `WindowRuntime` via `AppStateStore.windowRuntime(for:)` (lookup-first-then-lazily-create — the single convergence point for launch, New Window, and future restoration).
- **Exactly one window on cold start.** The `defaultValue:` closure returns `AppStateStore.shared.initialWindowID` specifically so SwiftUI's first content window reuses the already-seeded runtime instead of creating a phantom second one — the phantom-window bug of **#0251**, where `batty <path>` sessions landed in an invisible `windows[0]`.
- **`openWindow(value: WindowID())`** as the New Window path — File → New Window and Shift-Cmd-N (`ShortcutAction.newWindow`, rebindable in Settings), plus the `AppStateStore.openWindowAction` hook wired by `OpenWindowHookInstaller` for the `BattyShortcuts` NSEvent-monitor path.
- **`.handlesExternalEvents(matching: Set())`** on the scene, which suppresses the extra empty window SwiftUI would otherwise open for `batty://` URL events (#0251's second root cause).
- **The `NSWindow ↔ WindowID` registry** (`nsWindowMap`, `keyWindowRuntime()`) that replaced the `"main"`-identifier key-window heuristic, and app termination via `terminateIfLastContentWindowGone`.
- Settings and Help scenes staying out of main-window shortcut dispatch.

A fix that presents a window by reverting to a singular `Window` scene is not acceptable.

## Acceptance criteria

- A content window is presented on launch **regardless of launch mechanism** — `open -n`, direct exec of the executable, and `XCUIApplication.launch()` all produce exactly one window on cold start.
- The six-second direct-exec reproduction above shows a window.
- `BattyUITests` runs green again under `scripts/run-ui-tests.sh`.
- Everything listed under "Do not regress what #0237 bought" still holds, verified by `MultiWindowTests` and `WindowRestorationTests` passing.
- `scripts/build.sh unit` passes.

## Ruled out — do not re-investigate

- **Not an LLDB/toolchain fault.** The `IDELaunchParametersSnapshot: no debugger version` / `DebuggerLLDB.DebuggerVersionStore.StoreError` line is benign. Verified healthy: a single Xcode 26.6 (17F113), `xcode-select` on `/Applications/Xcode.app/Contents/Developer`, `LLDB.framework` present, `lldb-2100.0.17.203` runs. `sudo xcodebuild -runFirstLaunch` was run and changed nothing. **Two prior issues (#0240, #0338) blamed this and were wrong.**
- **Not the Prod/Beta config mixup (#0280).** Reproduced with `Active.xcconfig` on Beta and `-showBuildSettings` confirming `PRODUCT_NAME = Batty Beta` / `PRODUCT_BUNDLE_IDENTIFIER = co.sstools.Batty.beta`.
- **Not the harness environment variables.** `BATTY_UI_TEST_MODE=1` makes no difference either way (see the table). Its only reader is `QuitConfirmation` (`BattyKit/Sources/BattyKit/Views/QuitConfirmation.swift:13`), which does not touch window creation. (The harness also sets `BATTY_UI_TEST_TEMP_HOME` — no reader in app sources — and `BATTY_UI_TEST_SCRIPT`, read by `UITestDriver`; neither is set on the plain `launchBatty()` path's failure.)
- **Not window-restoration state on disk.** No `~/Library/Saved Application State` entry exists for the Beta app. (This does not rule out the *in-process* restoration negotiation described under Suspected cause.)
- **Not duplicate LaunchServices registrations.** Five registered copies of `co.sstools.Batty.beta` do exist, but the failing run's log shows `LSApplicationCheckIn` resolving the correct current build path.
- **Not #0378's diff**, which does not touch the launch path.

Reproduced on `main` and on issue branches, under both `scripts/run-ui-tests.sh` and Xcode's own test runner.

## Notes

**Adjacent defect — already being addressed in the working tree, do not fold it into this fix.** As committed on `main`, `scripts/build.sh` defaults to `SCHEME="${SCHEME:-Batty (Prod)}"` and passes that scheme through for every action including `test`, while its usage header advertises `scripts/build.sh test  # run UI tests`. Since `scripts/run-ui-tests.sh` pins `SCHEME="Batty (Beta)"` and the UI suite's host is `Batty Beta.app` / `co.sstools.Batty.beta`, `scripts/build.sh test` runs the UI suite against the **Prod** host app and bundle id — adjacent to #0280's failure mode.

At the time of filing, uncommitted working-tree edits by a concurrent session already fix this: `build.sh` gains a `ui` action (with `test` as an alias) that delegates to `run-ui-tests.sh`, and `run-ui-tests.sh` gains an `Active.xcconfig` snapshot/restore trap around a `set-environment.sh Beta` call. If those land, this note is historical and needs no separate issue; if they are discarded, file it separately.
