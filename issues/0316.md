## Description

#0311 fixed exactly one `windows[0]` trap site — `BattyCommands.keyWindow` — after a confirmed, reproduced crash (`EXC_BREAKPOINT` from `Array.subscript` on an empty `windows`). It deliberately left every other such site unfixed, and its own Fix B made the dangerous state *longer-lived*: before it, `NSApp.terminate` ran synchronously from inside the window-close notification and the process was effectively already dying when `windows` emptied; now the app intentionally survives at least one extra main-runloop turn with `windows == []` and `nsWindowMap == [:]` (the `DispatchQueue.main.async` deferral documented in `terminateIfLastContentWindowGone()`'s doc comment, `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:160-195`). Every remaining `windows[0]` site is reachable during that turn, and each one traps identically to the #0311 crash.

This is the full inventory of code sites (not comments) matching `grep -rn 'windows\[0\]' BattyKit/Sources Batty`, re-derived and verified against the current tree on 2026-08-07. Note that #0311's Gotchas list has already drifted: its `AppStateStore.swift` line numbers for the action shims are off by +6 (e.g. `moveSessions` cited at `:597`, now `:603`), and its claim that those seven shims are "the real action shims real menu items and shortcuts call" is no longer accurate — see the classification below.

### Production-reachable (verified callers in shipping code paths)

1. **`AppStateStore.initialWindowID`** — `AppStateStore.swift:110-112`, reads `windows[0].id` with **no fallback at all**. Read from two SwiftUI **scene-body** positions in `Batty/BattyApp.swift`: the `WindowGroup` content closure (`:16`, `windowID ?? AppStateStore.shared.initialWindowID`) and the `defaultValue:` closure (`:24`). This is the worst class: a scene-body re-evaluation during the empty-`windows` turn would trap the entire `WindowGroup`, not just a menu command.
2. **`AppStateStore.addSession(title:workingDirectory:)`** — `AppStateStore.swift:573`, `anyContentWindowRuntime() ?? windows[0]`. Production path: an OS-delivered `batty://` URL → `BattyAppDelegate.application(_:open:)` (`Batty/BattyApp.swift:85-92`) → `BattyURLHandler.handle(_:store:)` (`BattyKit/Sources/BattyKit/Runtime/BattyURLHandler.swift:28`) → this method. A `batty <path>` invocation landing during the deferred-terminate turn traps. `anyContentWindowRuntime()` returns nil in exactly this state (`nsWindowMap` is empty).
3. **`AppStateStore.markActiveTabSeen()`** — `AppStateStore.swift:719`, `(keyWindowRuntime() ?? windows[0])`. Production caller: `PaneView.swift:205`, `.onChange(of: pane.activeTabID)`. An `onChange` firing during last-window teardown is timing-dependent but not excluded.
4. **`CommandPaletteView.swift:67` and `:193`** — `store.keyWindowRuntime() ?? store.windows[0]`. Production view code; evaluated when the palette body/actions run.
5. **`PasteConfirmation.swift:107`** — `(store.keyWindowRuntime() ?? store.windows[0]).selectedSession?...`. Production view code on the paste-confirmation path.

A caller sweep on 2026-08-07 found **no production call sites** — `BattyCommands`, `BattyShortcuts`, and the views now call the per-window `WindowRuntime` methods directly — so these are currently exercised only from tests and `UITestDriver` (env-var-gated, compiled into the product):

## Steps to reproduce

No single reproduction covers all sites; the enabling state is the one #0311 verified 2/2: close the sole window ~1.5-2 s after launch, which drives `removeWindow` → `terminateIfLastContentWindowGone` → the deferred terminate, leaving `windows == []` for at least one runloop turn. Any of the sites above evaluated in that turn traps. The concrete candidate repro for site 2: deliver a `batty://session?path=...` URL timed into that turn.

## Expected behavior

No code path can trap on `windows[0]` while `windows` is empty. `AppStateStore.keyWindowOrFirstRegistered()` (added by #0311, `AppStateStore.swift:479`) already exists as the total version of the `keyWindowRuntime() ?? windows[0]` pattern — most sites are a one-line change to use it (or `windows.first`) and become optional. Per #0311's precedent, each production-reachable site's fix carries a unit test proving the empty-`windows` case (the pattern in `CrossWindowBehaviorTests.swift`, including the `terminateHandler` override gotcha #0311 documented).

## Actual behavior

Twenty `windows[0]` subscript sites across `AppStateStore.swift`, `CommandPaletteView.swift`, and `PasteConfirmation.swift` trap on an empty `windows` array, and the empty-`windows` state now has a deliberate, non-zero lifetime on every last-window close.

## Notes

- **Scope honestly.** Changing a function's return to optional propagates to its callers — #0311's Fix A touched ~30 use sites for one property. `initialWindowID` is the hard case: its callers are scene bodies that need *some* `WindowID`; options include returning a stable fallback ID, caching the seed ID separately from the `windows` array, or making the scene tolerate absence — a design decision for the implementer, not settled here.
- The test-only shims could alternatively be moved behind a test-support seam or asserted with a clear diagnostic rather than made total; what's not acceptable is leaving them as silent trap sites reachable from production code.
- Re-grep before implementing: `grep -rn 'windows\[0\]' BattyKit/Sources Batty`. This inventory was verified 2026-08-07 and will drift like #0311's did.
- #0311's Gotchas note that `#0234` (multi-window, in-progress) adds writers of `windows`/`nsWindowMap`; coordinate.

## Root cause

Same defect class as #0311, repeated at every other site the fix left
deliberately unclosed: `AppStateStore.windows` can legitimately be empty for
one main-run-loop turn after the last content window closes (`terminateIfLastContentWindowGone()`'s
`DispatchQueue.main.async` deferral), and every unguarded `windows[0]`
subscript reachable during that turn traps `EXC_BREAKPOINT` identically to
the confirmed #0311 crash.

**Re-verification of the inventory (2026-08-07, before any fix applied):**
re-ran `grep -rn 'windows\[0\]' BattyKit/Sources Batty` against the tree at
the start of this issue's work. The issue's inventory was accurate — same 20
code sites (5 production-reachable items, one of which,
`CommandPaletteView`, spans two lines; 6 caller-less action shims; 5
test-only shims spanning 8 lines; 20 lines total), same classification, no
line-number drift beyond what the issue already accounted for. No
discrepancy found.

## Fix

**Production-reachable sites (5 items / 6 code lines) — all made total:**

- **`AppStateStore.initialWindowID`** (`AppStateStore.swift`) — the worst
  site, read from `BattyApp`'s `WindowGroup` scene body. A scene body must
  stay pure (no writes, no `Task` hop — `docs/swiftui-observation-rules.md`),
  so the fix could not "compute a fallback on demand." Instead, a new
  `@ObservationIgnored private let seedWindowID: WindowID` is captured once
  in `init`, independent of the mutable `windows` array. `initialWindowID`
  becomes `windows.first?.id ?? seedWindowID` — a pure read of two
  already-set values, no different in shape from the property it replaces.
  Reusing the *original* seed id (not a fresh `WindowID()`) preserves
  identical behavior whenever a window exists and, in the empty-window turn,
  resolves to the same id `windowRuntime(for:)` already knows how to
  lazily recreate a runtime for — matching that method's existing contract
  rather than inventing a new fallback shape.
- **`AppStateStore.addSession(title:workingDirectory:)`** — changed return
  type from `SessionRuntime` to `SessionRuntime?`. Returns `nil` (with an
  error-level log line) only when neither `anyContentWindowRuntime()` nor
  `windows.first` resolves — i.e. only in the deliberate post-last-window
  turn, when the process is already committed to quitting. Chosen over
  silently reviving a phantom `WindowRuntime` (via `windowRuntime(for:
  seedWindowID)`) because that alternative was evaluated and rejected: it
  would leave an orphaned model-layer window with no NSWindow, and because
  `terminateIfLastContentWindowGone`'s deferred re-check treats *any*
  non-empty-sessions window as "don't terminate," it could leave the process
  running headless with no visible window — a worse outcome than a clean
  quit. `BattyURLHandler.handle(_:store:)`, the one production caller
  (an OS-delivered `batty://` URL), now guards the `nil` case and logs
  instead of force-using the result.
- **`AppStateStore.markActiveTabSeen()`** — `keyWindowOrFirstRegistered()?.markActiveTabSeen()`.
  Production caller: `PaneView`'s `onChange(of: pane.activeTabID)`. No tab
  exists to mark seen once `windows` is empty, so a silent no-op is the
  *correct* behavior here, not a degraded one.
- **`CommandPaletteView.swift`, two sites** (`allCommands`'s "Duplicate
  Session" action; `dispatch(_:)`) — both now call
  `store.keyWindowOrFirstRegistered()` and guard/no-op on `nil` rather than
  indexing `store.windows[0]`. `dispatch(_:)`'s guard is placed once at the
  top rather than per-`switch`-case: in practice this palette can only be
  showing over a live content window, so the empty-`windows` state is not
  expected to be reachable through it at all — the guard exists because the
  alternative is a trap, not because per-action behavior needed to be
  preserved in a state that shouldn't occur. Both `allCommands` and
  `dispatch(_:)` were loosened from `private` to internal (module-visible)
  access specifically so a test could call the production methods directly,
  mirroring #0311's own precedent of extracting `keyWindowOrFirstRegistered()`
  for exactly this reason.
- **`PasteConfirmation.swift`'s `focusedTerminalTab(in:)`** — now
  `store.keyWindowOrFirstRegistered()?.selectedSession?.focusedPane.activeTab`.
  Already returned `TabRuntime?`, so `nil` on an empty `windows` composes
  with the existing "nothing focused" fallback path
  (`PasteDispatcher.handlePasteRequest` forwards to the standard system
  paste) with no further change needed there.

**Caller-less public-API shims (6 items) — made total anyway.** `moveSessions(fromOffsets:toOffset:)`,
`selectSession(at:)`, `closeFocusedTab()`, `requestCloseFocusedTab()`,
`confirmPendingClose()`, `cancelPendingClose()` all had no production caller
as of this issue's re-verified sweep (`BattyCommands`/`BattyShortcuts`/views
call the per-window `WindowRuntime` methods directly; only `closeFocusedTab()`
has any caller at all — `UITestDriver.swift`, env-var-gated but compiled
into the product). **Reasoning for fixing them despite no current caller:**
the fix is cheap — each becomes `guard let window = keyWindowOrFirstRegistered() else { <log>; return }`,
no signature change, no propagation to any caller since they already return
`Void` — and leaving a public, trap-capable `windows[0]` sitting next to its
now-fixed sibling (`markActiveTabSeen`, identical shape, IS
production-reachable) would be an inconsistency inviting exactly the
regression #0316 exists to close out: a future caller reintroducing the
#0311 trap class through "the API that happened to still have the bug."
The counter-consideration (making an API total when no caller needs it yet
can mask a design question a real caller should have forced) does not apply
here — these are pure no-op-on-empty degradations with no optionality to
propagate, not a case where returning `nil`/optional would ripple outward.

**Documented test-only shims (5 items / 8 lines) — left alone.**
`onAllSessionsClosed` get/set, `sessions`, `selectedSessionID` get/set,
`selectedSession`, `pendingCloseRequest` get/set. Re-verified via
grep across `BattyKit/Sources` and `Batty` that every non-test caller of
these five accessors is zero — the only callers found anywhere are
`BattyKit/Tests/BattyKitTests/*` and `UITestDriver.swift`, both already
covered by the issue's own classification. No evidence surfaced that
they are production-reachable, so per the issue's instruction they were
left as-is.

## Gotchas

- **`git checkout -- <file>` discards ALL uncommitted work on that file, not
  just the mutation you just made.** Mid-mutation-testing, this session ran
  `git checkout -- BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift`
  intending to undo a single reverted line and instead wiped every one of
  this issue's fixes to that file (init seeding, `addSession`, all six
  action shims, `markActiveTabSeen`) back to the pre-#0316, unfixed state —
  since none of it was committed yet. Caught immediately via `git diff --stat`
  showing zero changes, and all fixes were manually re-applied from the
  in-context record of what had been written. **For any future mutation
  testing against uncommitted work: snapshot the good file to a scratch
  path first (`cp file /path/to/backup`) and restore from that copy, never
  `git checkout --`/`git stash` against a file with other uncommitted
  changes still needed.**
- **#0234 (multi-window, in-progress) coordination** — same caution #0311
  already recorded, reconfirmed here: nothing in this fix assumes "at most
  one content window." Every fallback used is `windows.first` /
  `keyWindowOrFirstRegistered()`, never a fixed index. The new
  `seedWindowID` is captured once in `init` and never re-derived from
  `windows`, so it stays valid regardless of how many windows the registry
  later grows to hold. `addSession`'s `nil`-on-empty behavior and
  `terminateIfLastContentWindowGone`'s staleness-guard shape (re-reading
  live `self.windows`/`self.nsWindowMap` at execution time, not a captured
  decision) are unchanged by this issue and must be preserved by any
  #0234 change that adds new writers of `windows`/`nsWindowMap`.
- **`addSession`'s alternative design (lazily reviving `seedWindowID` via
  `windowRuntime(for:)` instead of returning `nil`) was considered and
  rejected** — see `## Fix` above for why: it risks a headless zombie
  process rather than a clean quit, because `terminateIfLastContentWindowGone`'s
  guard treats any non-empty-`sessions` window as "don't terminate." Anyone
  revisiting this site should re-derive this tradeoff rather than assume
  reviving a window is obviously safer than dropping the request.
- **Not independently verified**: whether a `batty://` URL delivered in the
  exact empty-`windows` turn (the concrete repro #0316 itself suggested) was
  reproduced end-to-end as a live scenario — this issue's verification is
  unit-test-level (calling `addSession`/`BattyURLHandler.handle` with
  `windows` emptied via `removeWindow`), the same level #0311's own
  verification used for its non-crash-reproduction sites. Only #0311's
  *original* crash site (`BattyCommands.keyWindow`) was verified via a live
  Beta reproduction; #0316 did not additionally attempt live Beta
  reproductions for these sites, since #0311 already established the
  mechanism (empty `windows` during the deferred-terminate turn) and this
  issue's job was closing the remaining sites within that established
  mechanism, not re-proving the mechanism itself.

- **`CommandPaletteView`'s single top-of-function guard also suppresses seven
  window-independent actions** — `.toggleSidebar`, `.toggleBellFeed`,
  `.commandPalette`, `.openQuickly`, `.layoutPicker`, `.themeSelector`, and
  `.newWindow` (which calls `AppStateStore.shared.openWindowAction?()`). No
  regression today: those sites trapped before this change, and the palette
  cannot be showing with zero windows. But `.newWindow` is precisely the
  action you would want to work when no window exists, so **#0234 should
  revisit this** if it adds a window-less palette entry point.

- **`closeFocusedTab` was made total because `UITestDriver` calls it, while
  `store.selectedSession` / `store.sessions` — which `UITestDriver` calls 15
  times — were left as raw `windows[0]`.** Defensible (this issue scoped
  test-only shims out), but the two decisions rest on different grounds. The
  exposure is UI-test-run-only.
