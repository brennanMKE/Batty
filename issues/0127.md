## Description

Swap two panes' positions in the split tree by dragging one over the other. Pick up a pane from its title strip (or a dedicated drag handle), drag it over another pane in the same window, drop — the two panes exchange positions and the layout animates into place. Mirrors tmux's `prefix-{` / `prefix-}` swap, but with direct manipulation instead of a keybinding.

The implementation can borrow from the existing tab-reorder behavior in SlidingTabs, which already handles a similar pattern — chip drag, drop-target highlight, animated reposition. Translating that to panes-in-a-split-tree is the work.

## Acceptance criteria

- A pane's title strip (or another deliberate handle — not the terminal body) initiates a drag when long-pressed or dragged with enough threshold to distinguish from a normal click.
- During the drag, the dragged pane's chrome follows the cursor as a translucent preview.
- Every other pane in the same window highlights as a drop target when the cursor enters its bounds.
- Dropping over a target pane swaps the two panes in the underlying `SplitNode` tree. The split structure (which splits are horizontal / vertical, the ratios) is preserved — only the leaf contents (terminal sessions) trade places.
- The post-drop transition animates smoothly — both panes' frames interpolate to their new positions, not a hard cut. Reuse SwiftUI's `.animation(.spring, value: …)` against the layout model so the renderer's existing layout pass handles the tweening.
- The dragged pane's keyboard focus follows the swap (the originally-dragged pane stays focused, now in its new position).
- Drop on the originally-dragged pane (no-op location) cancels cleanly with a snap-back animation; no state change.
- Drop outside any pane cancels cleanly.

## Out of scope

- Dragging a pane *into a split position* (e.g. drop on the right half of a target pane to convert it into a new split with the dragged pane on the right). That's "rearrange the tree by drag," a strictly larger feature. Pure swap is a clean v1; the split-creation variant can land as a follow-up.
- Dragging a pane out of the window to detach it. Multi-window support is gated on `#0027`; until that lands, drag-to-detach has nowhere to go.
- Dragging a tab between panes. That's a different shape and tracked separately if needed.
- Cross-session pane drag. Pane swap stays within the current session for v1.

## Notes

- The existing tab-chip drag in SlidingTabs is the prior art — read it first. The pane drag will sit one level up in the view hierarchy (`PaneView` rather than tab chip) but the gesture, the translucent preview, and the drop-target highlight should feel consistent.
- The split-tree mutation is a swap on two `SplitNode.leaf(...)` cases (or wherever leaf panes live) — find the two paths to the swapped leaves, exchange them. Make sure focus state, bell counters, and any per-pane runtime state (`PaneRuntime`) travel with the pane, not with the tree position.
- Animation: SwiftUI's implicit layout animation on a `.spring(response: 0.32, dampingFraction: 0.78)` (roughly tmux-fast, not iOS-bouncy) tends to feel right for terminal-app UI. Worth a quick A/B with the existing split-divider drag for consistency.
- Cursor: standard "grabbing hand" during the drag, "no" cursor over invalid drop zones (everywhere except inside the window's other panes).
- File-drop UX (`#0022`) lives on the terminal *body*; pane-drag UX should live on the title strip / handle, so the two don't conflict. Verify by reproducing: drag a file from Finder onto a pane vs. drag the pane handle of one pane onto another.

## Root cause

There was no direct-manipulation affordance for swapping two panes — the SplitTree had `splitFocusedPane`, `removePane`, and `updateRatio`, but no operation that exchanged two leaves in place. There was also no per-pane drag handle distinct from the SlidingTabBar chip area or the terminal body, so any pane drag-source would have collided with the existing tab-reorder gesture or the file-drop receiver on the terminal.

## Fix

Three layered additions:

1. **`SplitTree.swapPanes(_:_:)`** — finds the two leaves matching the supplied pane ids and rebuilds the tree with the `PaneRuntime` references at those two positions exchanged. The split structure (split-node ids, directions, ratios) is preserved verbatim by walking the existing tree and only substituting at matched leaves. Because `PaneRuntime` is a reference type carrying its own tabs and per-pane runtime state, focus tracking (which is by pane id) follows the pane to its new tree position automatically.
2. **`PaneDragController`** — a per-`SessionRuntime` `@Observable` that tracks `draggedPaneID`, `cursorLocation`, and the resolved `dropTargetPaneID`. The hit test runs against the existing `PaneFrameTracker.frames` map (already populated by `SessionDetailView.onPreferenceChange(PaneFramePreferenceKey.self)`), so no new layout plumbing was needed. Exposes `begin` / `update` / `end` / `cancel` for the gesture caller.
3. **`PaneView` drag handle + drop-target overlay** — adds a small `rectangle.grid.1x2` grip icon at the leading edge of the tab-bar row, gated on `hasSiblingPanes` so a single-pane session has no handle. The grip carries a `DragGesture(minimumDistance: 4, coordinateSpace: .named("session"))` that pushes updates into the controller. While the controller is active the dragged pane fades to 0.35 opacity, the candidate drop target draws an accent-color highlight overlay, and `SplitContainerView` overlays a translucent preview rectangle that tracks the cursor. The swap call is wrapped in `withAnimation(.spring(response: 0.32, dampingFraction: 0.78))`, and the recursive `SplitNodeView` tags leaves with `.id(pane.id)` and splits with `.id(splitID)` so SwiftUI treats moved panes as the same view at a new position rather than a teardown/recreate.

Drop-on-self and drop-outside-any-pane both leave `dropTargetPaneID == nil`, so `end()` returns `nil` and the gesture cleanly resets state with no model mutation; the translucent preview disappears, the dragged pane returns to full opacity.

Crucially the swap is purely a model mutation — no `AppTerminalView` is reparented or recreated. The `TerminalHostStore` keeps each tab's NSView keyed by `tab.id`; when the placeholders re-emit frames after the swap, the host moves the existing subviews to the new frames.

## Gotchas

- Visual sign-off is the user's. The headless test suite covers the swap math and the controller's state machine, but the actual SwiftUI interactions are not verified here: (a) the spring animation timing / "feels right" call, (b) translucent-preview rendering and tracking, (c) `NSCursor.openHand` cursor change on the handle, (d) drop-target highlight visibility, (e) keyboard focus actually following the swap on the live `AppTerminalView`. Verify in the Mac app.
- The grip handle uses `Image(systemName: "rectangle.grid.1x2")` and only appears when the session has more than one pane. The hover cursor uses `NSCursor.openHand` (push/pop) — there's no separate "closed hand" mid-drag because SwiftUI's `DragGesture` doesn't fire an event the moment the gesture activates; the open-hand cue is good enough at the v1 bar.
- The host pane-NSView placement updates (`TerminalHostStore.updatePlacements`) are not themselves animated — they're set imperatively per preference-change. Smoothness during the post-drop transition relies on SwiftUI's layout system delivering intermediate frame values as the spring interpolates, which it does because the placeholder's `Color.clear` view inside `GeometryReader` re-emits the preference on every layout pass. If a future refactor short-circuits that re-emission, the terminal would jump-cut while the chrome animates; the placement update path would then need a parallel animation hook.
- The DragGesture has no explicit cancel hook — if SwiftUI tears the gesture mid-drag (e.g. a window crash), `onEnded` won't fire and `PaneDragController` state would be stale until the next `begin`. `PaneDragController.cancel()` exists for future use but isn't currently wired to any cancellation path. Acceptable for v1.
- The `.id(pane.id)` on each leaf preserves PaneView state (paneWidth, paneSize, renamingTab, etc.) across the swap so a half-edited rename sheet doesn't disappear if the user happens to swap a pane mid-rename. Without it, SwiftUI would use positional identity and tear down both PaneView state bags on every swap.
