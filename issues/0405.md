## Description

`WindowRuntime.jumpToTab` is the only navigation path in `WindowRuntime`/`AppStateStore` that writes `focusedPaneID` without checking `isHidden` and un-hiding first. Every one of its three siblings — `jumpToBellEntry`, `focusPaneForXPC`, `focusTabForXPC` — enforces the invariant established by #0256 ("focus must never land on a hidden pane") before writing focus. `jumpToTab` does not, so navigating to a Tab that belongs to a hidden Pane leaves `focusedPaneID` pointing at a Pane that renders as a zero-size `Color.clear` placeholder.

## Steps to reproduce

1. Hide a Pane (the eye button in its tab bar, or `batty pane hide`).
2. Press ⌘P (Open Quickly).
3. Pick a Tab belonging to the hidden Pane. `OpenQuicklyView.swift:51` sources results from `session.tree.allPanes.filter { $0.kind == .terminal }` — hidden Panes are included in the list.

## Expected behavior

Same as every other navigation entry point: the Session switches, the target Pane is un-hidden (`showPane`), and only then does focus move to it — matching `jumpToBellEntry`'s documented sequence ("Un-hide the pane before navigating to it").

## Actual behavior

`WindowRuntime.jumpToTab` (`WindowRuntime.swift:829-856`) writes `selectedSessionID` (:838), `session.tree.focusedPaneID` (:839), and `pane.activeTabID` (:840) with no `isHidden` check and no call to `showPane`. The Session switches, but the Pane stays hidden and renders as `Color.clear.frame(width: 0, height: 0)` (`SplitContainerView.swift:63`). The user sees nothing happen.

## Notes

**Invariant and siblings (all verified against current code):**

- #0256 established "a Pane's `isHidden` flag and `focusedPaneID` must never point the same way" as a binding invariant.
- `WindowRuntime.hidePane` (`WindowRuntime.swift:757-799`) deliberately moves focus off the target *before* setting `isHidden = true`, per its own comment at `:765`: "Move focus before hiding so `focusedPaneID` never references a hidden pane."
- `WindowRuntime.jumpToBellEntry` (`WindowRuntime.swift:857-871`) un-hides before navigating: comment at `:862-864` ("Un-hide the pane before navigating to it — a bell from a hidden pane's surface must be reachable via the feed (#0256)"), guard at `:865-867`.
- `AppStateStore.focusPaneForXPC` (`AppStateStore.swift:1237-1256`) carries the same guard at `:1248-1250`, with a comment explicitly citing "#0256's invariant."
- `AppStateStore.focusTabForXPC` (`AppStateStore.swift:1272-`) carries the matching guard at `:1279-1281`.
- `jumpToTab` itself has no such guard anywhere in `WindowRuntime.swift:829-856`.

**Prior sighting, never filed as its own defect:** #0337's Gotchas section (line ~317) already names this exact hole — "`WindowRuntime.jumpToTab` ... writes `focusedPaneID` with no `isHidden` check and no un-hide" — but only in the context of a stale log message in `resolveHiddenFocusFallback` lying about an invariant that `jumpToTab` had already broken. #0337 explicitly calls the underlying `jumpToTab` hole "pre-existing" and out of scope for that issue. This ticket is that follow-up, now filed against the focus-correctness consequence directly (Open Quickly landing focus on an invisible Pane), not just the inaccurate log line.

**Related work that established/relies on the same guard shape:** #0256 (introduced the invariant and `hidePane`/`showPane`), #0381 (added `tab focus` / `focusTabForXPC`, which honors the guard), #0382 (added `pane hide`/`pane show` CLI verbs, i.e. `hidePane`/`showPane` themselves).

**Unverified — needs a running app:** whether *keyboard* input follows into the invisible Pane after this bug fires, or whether keystrokes go nowhere. Both outcomes are wrong, and the fix (un-hiding before focusing, matching every sibling) does not depend on knowing which — but no unit test can observe actual key routing, so this is left unverified rather than asserted either way.
