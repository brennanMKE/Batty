**Migrated sites** (`ProcessStatusPaneContentTests.swift`):

- `waitUntil` helper (`Task.sleep(50ms)` deadline poll) — deleted; both
  callers below were rewritten to use the injected clock.
- `samplingStopsWhileSuspendedAndResumesWhenShown` — now injects `TestClock`
  (kept the non-default `.milliseconds(20)` sampling interval). Uses the
  `docs/async-test-seams.md` §1 "once per tick" idiom: `waitForSleepers(1)`
  to confirm the periodic task is parked, `advance(by:)` to fire one tick,
  `waitForSleepers(1)` again to confirm the loop re-registered (proving the
  tick's `performSample()` already ran) before asserting `capturedAt`
  advanced. The "nothing sampled while hidden" window is now
  `advance(by: .milliseconds(20 * 50))` (50 virtual sampling intervals)
  instead of a real `Task.sleep(200ms)` — a leaked loop would still be
  parked on `clock.sleep(for:)` and this advance would fire it, so it can't
  be missed the way a fixed wall-clock window could. **Review round 1, B3:
  the `waitForSleepers` guard failure branches returned without releasing
  anything, and the test never tore `content` down at all — round 2 adds
  `defer { content.tearDown() }` right after construction, so both an early
  guard-failure return and the test's own normal end (which leaves sampling
  resumed) cancel the parked `Task` instead of leaking it on `clock`
  forever** (`TestClock` never lets time pass on its own, so nothing else
  would ever wake or cancel a leaked sampler).
- `cpuPercentReflectsSubstantialRealCoreUsage` — rewritten to remove all
  wall-clock dependence. **Round 1 of this rewrite called
  `content.cpuPercent(for:)` directly with hand-built `ProcessSample`s,

  `sample(pid:)`'s `.success` branch, and `cpuTicksUser` dropped when that
  branch builds its `ProcessSample`), because neither mutation sits on the
  path a direct `cpuPercent(for:)` call exercises.** Round 2 goes through
  the real path instead: constructs with a recording `coreMetricsProvider`
  that still calls the real `ProcessInspector.coreMetrics` but records each
  result, calls `setUp(visible: true)` to take the baseline (through
  `sample(pid:)`), burns a fixed amount of CPU (now 1,000,000 iterations of
  cheap `sqrt` arithmetic on a deterministic input, not `Double.random` —
  cheaper per round 1's N-finding too), `advance(by: .seconds(1))`, then
  `sampleNowForTesting()` (through `sample(pid:)` again) — and asserts
  `snapshot?.cpuPercent` against the tick delta the *recording provider*

**Migrated sites** (`ProcessInspectorTests.swift`):

- `machTimebaseNanosecondsPerTickAgreesWithAnIndependentClock` — no longer
  brackets a real `Task.sleep(200ms)` with `mach_absolute_time()` and
  `ContinuousClock.now`. Per `docs/async-test-seams.md` §5 Q2,
  `clock_gettime_nsec_np(CLOCK_UPTIME_RAW)` is documented
  (`clock_gettime(3)`) to already be `mach_absolute_time()` converted to
  nanoseconds, so this now takes one `mach_absolute_time()` reading and one
  `CLOCK_UPTIME_RAW` reading back-to-back (absolute values since boot) and
  compares `MachTimebase.nanosecondsPerTick`'s conversion against the
  kernel's own — no interval, no wait. **Round 1's tolerance band
  (`0.5 < ratio < 2.0`) was found too loose in review (B1): a reviewer
  multiplied `nanosecondsPerTick` by 2, 1.5, and 1.9 and all three still
  passed. Round 2 tightens this to `abs(ratio - 1) < 1e-3`** — back-to-back
  reads of these two absolute since-boot clocks agree to within about 166ns
  out of well over 1e11 in practice, so 1e-3 relative still comfortably
  passes a correct constant while catching all three of the reviewer's
  mutations. Also corrected the comment's "nanoseconds apart at most" claim
  — a preempted thread can be descheduled between the two reads for
  milliseconds under load; what actually keeps the ratio tight is that even
  a millisecond gap is negligible against a since-boot value that's
  ordinarily minutes to hours, not that the gap itself is nanosecond-scale.
- `commandLineHandlesARealProcessWithAZeroLengthArgvZeroWithoutLeakingItsEnvironment`

## Resolution notes

> 🟢 Resolved 2026-09-24 — Process Status unit tests no longer wait on real time. Periodic sampling runs on an injected `TestClock`. The CPU-percent test goes through the real `sample(pid:)` path with a virtual interval. The timebase test compares two absolute clock reads within a 1e-3 band. The `posix_spawn` `usleep` is gone.

## Fix

- **Production.** `ProcessStatusPaneContent.cpuPercent(for:)` now passes `at: clock.now` to the delta tracker. `SystemClock.now` is `Date()`, so production behaviour is unchanged, and `SplitTree` relies on that default (per `docs/async-test-seams.md` §1).
- **`samplingStopsWhileSuspendedAndResumesWhenShown`.** Uses `TestClock`, advancing one tick at a time and guarding each wait. A `defer { tearDown() }` releases the parked sampler on every path.
- **`cpuPercentReflectsSubstantialRealCoreUsage`.** Passes a recording `coreMetricsProvider`, then runs `setUp`, a 1M-iteration burn, `advance(1s)` and `sampleNowForTesting()`. It asserts `snapshot.cpuPercent` against the tick delta the provider recorded, and `deltaTicks > 0` is a `#require`.
- **`machTimebaseNanosecondsPerTickAgreesWithAnIndependentClock`.** Compares one `mach_absolute_time()` read with one `CLOCK_UPTIME_RAW` read, requiring `abs(ratio - 1) < 1e-3`.

## Gotchas

- **`samplingInterval: .seconds(60)` in the CPU test guards a real ordering race.** With a 1 s interval, the periodic tick would race `sampleNowForTesting()`, and a second sample with zero elapsed time returns nil. The comment beside it describes the failure slightly wrong.
- **Optional hardening, not done.**
  - Assert `advance(by: 1s) == 0`.
  - Require exactly 2 recorded metrics rather than `>= 2`. As written, the test would silently absorb a regression where `setUp` samples twice at t=0.
- **Arch limit.** On x86_64 the timebase is 1/1, so the timebase test can't detect an inverted conversion there.
