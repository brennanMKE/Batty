# 0344 — A single remote Pane: wire the tmux control-mode stream into an `.inMemory`-backed Pane

| | |
|---|---|
| **Status** | open |
| **Module** | GhosttyKit / TerminalSurface / Pane |
| **Platform** | macOS |
| **First seen** | 2026-08-21 |

## Description

Join the two halves: take the tmux control-mode stream from
[#0343](0343.md) and drive an `.inMemory`-backed Pane from
[#0342](0342.md) with it. **One Pane. No splits, no layout mirroring,
no Sidebar work.** This is the first point at which the user sees a
real shell running on the Mac mini rendered inside Batty on the
MacBook.

The wiring is small by design, because #0342 and #0343 did the work:

- `%output` for the tracked tmux pane goes to
  `InMemoryTerminalSession.receive(_:)`.
- The session's `write:` handler turns local keystrokes into a tmux
  `send-keys` (or equivalent input command) on the control channel.
- The session's `resize:` handler turns local geometry changes into a
  tmux `resize-pane`, or into a client-size negotiation, depending on
  the handoff decision recorded as #0341's Open question 1.

The architecture, the size-clamp problem, and the Surface-registry
amendment live in [#0341](0341.md) and are not restated here.

**Not scheduled work.** Inherits #0341's status: staged for a future
major release, not queued.

## Expected behavior

1. The user points Batty at a host and a tmux session name and gets a
   Pane showing that tmux pane's live output.
2. Typing in the Pane reaches the remote shell. Interactive programs
   work — `vim`, `top`, `less`, a full-screen TUI — because the
   remote is a real terminal and Batty is only moving bytes.
3. Resizing the Pane changes the remote pane's geometry, and
   full-screen programs on the remote reflow correctly.
4. Closing the Pane detaches from tmux; **the remote session keeps
   running** and can be reattached. Killing it is not the default
   close behavior — persistence is the entire reason for tmux.
5. A dropped connection (`ssh` dies, the network goes away, the
   remote reboots) leaves the Pane in a visibly non-live state rather
   than a silently frozen one that looks live. Reconnection itself is
   #0346's job; not lying to the user is this issue's job.
6. The Pane is otherwise an ordinary Batty Pane: Theme applies,
   selection and copy work, the Bell Feed sees bells that arrive in
   the byte stream, IME works.

## Acceptance criteria

1. A remote shell on the Mac mini renders in a Batty Pane on the
   MacBook and is fully interactive, verified with at least one
   full-screen program (`vim` or `top`) and one that emits sustained
   output.
2. Local geometry changes reach the remote — verified by `tput
   cols`/`tput lines` on the remote agreeing with the Pane, after a
   real Split-divider drag and after a Window resize.
3. Closing the Pane leaves the tmux session alive on the remote
   (`tmux ls` confirms) and reattaching shows the same shell with its
   state intact.
4. `scripts/build.sh unit` passes, with new `BattyKitTests` covering
   the mapping layer: `%output` for the tracked pane routed to
   `receive(_:)` and output for *other* panes not routed to it;
   keystrokes translated to the correct outbound command;
   `InMemoryTerminalViewport` translated to the correct
   `resize-pane`. Drive these from the #0343 parser against recorded
   transcripts, not against a live remote — the unit suite must stay
   fast and must not need a network.
5. **The pre-attach byte window is closed.** `receive(_:)` drops data
   when the session has no surface yet (see #0342's acceptance
   criterion 5 and #0341's verified-API notes). A remote stream can
   start before the Pane's surface exists, so this issue must prove
   the first bytes of a session are not lost — a test that feeds
   output before attachment and asserts it renders after.
6. **Latency is characterized, not just "it works".** Measure and
   record round-trip keystroke-to-render over the local network. If
   it is bad enough to be unpleasant, say so and say why, rather than
   leaving #0345 and #0346 to discover it.
7. `docs/terminal-pane-requirements.md` §6's manual checklist is run
   on the remote Pane — pointer input, keyboard, IME, file drop, text
   drop — with results recorded, including which of them are
   *semantically* different for a remote Pane. File drop in
   particular is a known open question (see Notes).
8. Every write this issue makes to observed state from a network
   event has a named owner and is not deferred into a `Task` to dodge
   a mutate-during-update warning. See #0341's Hard problem 3;
   `docs/swiftui-observation-rules.md` is binding.

## Notes

- **File drop is genuinely unresolved for a remote Pane.** Batty
  inserts shell-quoted **local** paths on Finder drop (PRD §6.12); on
  a remote shell a local path is meaningless. #0254's candidate
  feature 2 is the same problem for plain SSH sessions and proposes
  transferring the file and inserting the *remote* path. This issue
  should not solve that — it should record what the current behavior
  is (almost certainly "inserts a useless local path") and whether it
  should be disabled rather than left wrong.
- Which tmux pane a Batty Pane tracks needs an explicit identity, not
  an index — tmux pane ids (`%0`, `%1`) are stable, positions are
  not. #0345 depends on this being right.
- Bell handling: a BEL in the remote stream arrives as ordinary bytes
  in `%output` and should reach the Bell Feed through the normal
  surface path. Confirm rather than assume — tmux may intercept it.
- Keep the "one Pane" boundary honest. Any temptation to handle a
  second tmux pane belongs in #0345.
