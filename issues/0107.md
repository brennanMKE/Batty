## Description

Batty currently ships with zero localization. Every user-facing string — menu titles, Settings panel labels, alert dialogs (paste confirmation, busy-tab close, quit confirmation), About panel credits, and the Sparkle update sheet — is a hardcoded English literal in Swift / SwiftUI source. macOS users running their system in any non-English locale see English UI throughout.

This issue is the foundation pass: extract every user-facing literal into a String Catalog, wire SwiftUI's auto-localization, populate the English entries, and prove the round-trip works. **No non-English translations are part of this issue** — those are filed separately as `#0108`–`#0121`, each depending on this one.

## Acceptance criteria

- A `Localizable.xcstrings` catalog (Xcode 15+ String Catalog format) is checked in under `Batty/` (or `BattyKit/Sources/BattyKit/Resources/`, whichever is more natural for the build).
- Every user-facing literal in `Batty/` and `BattyKit/Sources/BattyKit/` has been converted to a `LocalizedStringKey` (SwiftUI `Text`, button labels, alert titles) or `String(localized: …)` (non-View code, menu titles built from raw strings, log-adjacent UI text).
- English entries are populated in the catalog for every extracted key.
- A locale-switch smoke test confirms the catalog drives the UI: temporarily set a development-only override locale (e.g. via `Bundle.main` swap or scheme-level `-AppleLanguages` argument) and verify that adding a stub second locale changes the rendered text.
- The build still passes `xcodebuild -scheme Batty -destination 'platform=macOS' build` with no new warnings about missing or unused keys.
- A short translator handoff note is added to `docs/` describing the export workflow (`xcodebuild -exportLocalizations`) so each subsequent language issue can be picked up by anyone with a translator on call.

## Scope checklist

The audit pass should at minimum cover:

- App / Window
  - Main menu titles (File, Edit, View, Sessions, Tabs, Window, Help, Batty)
  - Menu item titles + key-equivalent annotations
  - About panel: app name, version line template, credits paragraph
  - Window titles (per-session derived title is user data — leave it; chrome around it is not)
- Sidebar / Sessions
  - "New Session", session-rename placeholder, duplicate / close labels
  - Empty-state copy if any
- Tabs / Panes
  - Busy-tab close confirmation ("A process is still running…")
  - Split direction labels (if surfaced in UI)
- Bell feed
  - Popover header, empty-state copy, per-row time formatting (use `Date.FormatStyle` locale-aware)
  - System notification title / body templates
- Settings
  - All pane titles (General, Appearance, Notifications, Paste, Updates)
  - Every field label and explanatory subtitle
  - Picker option display names (cursor style, paste strictness, theme, font, etc.)
- Alerts / sheets
  - Paste confirmation ("Paste N lines?") — note the pluralization, use String Catalog plural variants
  - Quit confirmation ("You have N terminals open…") — plural
  - Drag-drop error states if any
- Sparkle
  - Sparkle's standard update prompts are already localized by the framework for ~20 locales; we just need to confirm our `Info.plist` allows Sparkle to pick the runtime locale. No custom strings to extract.

## Out of scope

- Actual translations into any non-English language — filed as separate dependent issues.
- Right-to-left layout audit — flag it under a separate issue if any RTL language is later prioritized (Arabic, Hebrew). None of the current planned languages need RTL.
- Localizing terminal output — that's user data from arbitrary shells; not ours to translate.
- Help-book / user-guide localization — those documents live under `docs/` and are addressed separately when/if a guide ships.

## Notes

- Prefer the Xcode 15+ **String Catalog (`.xcstrings`)** over legacy `.strings`. It handles plurals (`%lld lines`) natively, scans source automatically, and Xcode regenerates on build.
- SwiftUI's `Text("Hello")` is auto-localized via `LocalizedStringKey`. Forced English bypass is `Text(verbatim: "Hello")` — useful for things like the literal product name "Batty" that should never translate.
- For string formatting with values, use `String(localized: "Paste \(n) lines", defaultValue: "Paste \(n) lines")` so the catalog can capture the parameterized form.
- Keys should be the English text itself (the SwiftUI convention) — not symbolic keys like `paste.confirmation.title`. This keeps the source readable and translator-friendly.
- Investigate adding a lint / build-phase script that scans diff hunks for new `Text("…")` calls and warns if they're not picked up by the catalog. Optional follow-up; don't gate this issue on it.

## Root cause

There was no localization infrastructure at all — no String Catalog, no `Localizable.strings`, no convention for marking call sites as translatable. Every user-facing literal was an English string that bypassed any lookup. Non-View code was the worst offender (NSAlert in `QuitConfirmation`, the `runningLabel` helper in `AppStateStore`, `PendingCloseRequest.title`, `BellNotifier`'s notification content, `PasteStrictness.displayName`, `ShortcutAction.displayName`, the `RecorderView` placeholder, `HelpLoadError.errorDescription`); SwiftUI views were already auto-localizable via `LocalizedStringKey` but had no catalog to resolve against.

## Fix

- Added a single `Batty/Localizable.xcstrings` catalog at the app target. `Bundle.main` is the resolution bundle for both the app and BattyKit, so one catalog drives every call site.
- Converted non-View literals to `String(localized:)` — including the alert texts in `QuitConfirmation`, the close-confirmation message templates in `AppStateStore`, the title getter on `PendingCloseRequest`, `BellNotifier`'s notification title/body, the "©" / multi-line credits in `AboutPanel`, the `(closed)` and tab-label fallbacks in `BellFeedView`, `TabTitleFormatter`'s default `"Tab"` fallback, every case of `PasteStrictness.displayName` and `ShortcutAction.displayName`, the recorder placeholder strings in `RecorderView`, the warning strings in `ShortcutRow`, the dynamic `sessionMenuTitle` / `tabMenuTitle` helpers in `BattyCommands`, the `Help` catalog section titles, and `HelpLoadError`.
- Kept SwiftUI auto-extraction for `Text("…")`, `Button("…")`, `Label("…", systemImage:)`, `Toggle("…", isOn:)`, `Picker("…", selection:)`, `Section("…")`, `TextField("…", text:)`, `Stepper("…", value:)`, and `.help("…")` call sites. Xcode 26's `xcstringstool` auto-merges discovered keys into the catalog on build.
- Treated the product name "Batty" as never-translate: `BattyApp` uses a `let mainWindowTitle: String = "Batty"` variable so the `Window(_:id:)` overload takes the verbatim-`String` path; `SessionSidebarView`'s `.navigationTitle("Batty")` is wrapped in `Text(verbatim:)`; the unseen-bell badge count uses `Text(verbatim: "\(count)")`. "Batty Help" remains a `LocalizedStringKey` so translators can localize the word "Help" while keeping the brand intact when split correctly.
- Declared plural variants for `Paste %lld lines?`, `%lld unseen bell event(s)`, and `There %lld open terminal(s).` in the catalog using the catalog's native `variations.plural` format.
- Stubbed a `de` translation for `Quit Batty?`, `Quit`, and `Cancel` as the acceptance-criteria smoke test. Building the app emits `Resources/de.lproj/Localizable.strings` with the German values; running the app with `-AppleLanguages '(de)'` shows the quit alert in German, proving the catalog drives the UI.
- Added `docs/localization.md` describing the `xcodebuild -exportLocalizations` / `-importLocalizations` round-trip and the call-site conventions (`Text(verbatim:)`, `String(localized:)`, plural format specifiers, `extractionState: manual` for the brand). Linked from `docs/README.md`.

## Gotchas

- **Plural specifier must reference the value.** The catalog rejects a plural variation that doesn't reference the count, so `"%@ unseen bell event(s)"` had to become `"%lld unseen bell event(s)"` (Int → `%lld`). SwiftUI's `LocalizedStringKey` interpolation of an `Int` maps to `%lld`, so the source `\(session.unseenBellCount)` continues to work without change.
- **The Window title initializer is overloaded.** `Window("Batty", id:)` resolves to the `LocalizedStringKey` overload because the argument is a string literal. To force the verbatim-`String` overload (so the product name never translates), pass a `String` variable: `Window(mainWindowTitle, id:)`. `Text(verbatim:)` doesn't compile here — `Window` takes the title directly, not a `Text`.
- **`Text(_:String)` is already verbatim.** Passing a non-literal `String` to `Text(_:)` picks the `StringProtocol` overload, not the `LocalizedStringKey` overload, so it does not re-translate strings that came back from `String(localized:)`. `Text(verbatim:)` is only required to suppress lookup of a string *literal*. The change was applied conservatively to a few call sites for clarity, but is not load-bearing.
- **`String(localized:)` is not a compile-time constant**, so it can't appear as a default-argument value. `TabTitleFormatter.chipTitle(fallback: "Tab")` had to be reshaped into `fallback: String? = nil` with the localized default resolved inside the function body.
- **The catalog is auto-managed by Xcode on build.** Pre-seeded entries should set `"extractionState" : "manual"` so they survive a future "clean unused keys" pass; the keys auto-discovered from `Text("…")` / `String(localized: "…")` will appear with the default extraction state and Xcode keeps them in sync with source.
- **macOS 26's `xcstringstool` correctly emits `de.lproj/Localizable.strings` from the catalog even though `de` isn't listed in `project.pbxproj`'s `knownRegions`.** Per-language subagents working `#0108`–`#0121` will likely need to register their locale via Xcode's Localization UI (which updates `knownRegions`) to make the catalog column appear in the catalog editor; the smoke test confirms the runtime path works regardless.
- **`-AppleLanguages` round-trips at the system layer.** Running `Batty.app` with `-AppleLanguages '(de)'` is enough to verify the catalog drives the UI; you don't need to switch the macOS system language to test.
- **The signing certificate "Mac Development" was not found** on this machine, so the build was verified with `CODE_SIGN_IDENTITY=- CODE_SIGNING_REQUIRED=NO CODE_SIGNING_ALLOWED=NO`. This is a per-machine signing-credential gap, not a build regression introduced by this change; the canonical `xcodebuild -scheme Batty -destination 'platform=macOS' build` invocation in `CLAUDE.md` will succeed for any developer with the team's Mac Development certificate provisioned.
