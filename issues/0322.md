# 0322 — Test targets carry four compiler warnings invisible to the incremental gate, two masking real test defects

| | |
|---|---|
| **Status** | open |
| **Module** | Build |
| **Platform** | macOS |
| **First seen** | 2026-08-08 |

## Description

#0320 cleared all compiler warnings from the app and kit sources — a forced full recompile of every `.swift` under `BattyKit/Sources` and `Batty` now produces zero warnings. But the sweep did not cover the test targets: forcing a recompile of `BattyKitTests` produces 4 unique warnings (~35 log lines repeated across compile invocations). The pre-commit gate (`scripts/build.sh unit`) does not surface them on incremental builds — the test files are unchanged, so they never recompile and never re-emit. This is the same structural problem #0320 was filed about: warnings that exist but are invisible in normal use, so they never generate pressure to fix.

All four warnings were verified against source before filing — each cited line does what the warning says:

1. `BattyKit/Tests/BattyKitTests/BellFeedCollapseTests.swift:110:15` — result of call to `markSeen(id:)` is unused. `BellFeedStore.markSeen(id:)` returns `BellFeedEntry?` and is not `@discardableResult`; the test at line 110 calls it for its side effect (marking the entry seen) and drops the return.
2. `BattyKit/Tests/BattyKitTests/CrossWindowBehaviorTests.swift:173:51` — comparing non-optional `UUID` to `nil` always returns true. `SplitTree.focusedPaneID` is declared `public var focusedPaneID: UUID` (non-optional), so `#expect(w1.sessions[0].tree.focusedPaneID != nil)` is a tautology that can never fail.
3. `BattyKit/Tests/BattyKitTests/MultiWindowCWDNamingTests.swift:205:13` — `suggestedPaths` never mutated; use `let`. Verified worse than the warning says: the variable is vestigial. The local `FixedSuggester` class records paths into its own `paths` property; nothing ever appends to `suggestedPaths`, and its only use is line 232's `_ = suggestedPaths  // Suppress unused warning` — a suppression line serving a dead variable.
4. `BattyKit/Tests/BattyKitTests/SidebarRestorationTests.swift:76:13` — mutation of captured var `received` in concurrently-executing code. The `NotificationCenter.addObserver(forName:object:queue:)` handler (a Sendable closure) sets `received = true` at line 76, and the test body reads it at line 82 after `await Task.yield()`.

Two of the four are likely real test defects, not just noise:

- **Warning 2 is a tautological assertion.** Whatever `#expect(... != nil)` was meant to verify — presumably that `jumpToBellEntry` focuses a pane in the target session — is currently unverified; the expectation cannot fail under any behavior. Note also that the line inspects `w1.sessions[0]` (the originally focused session) while the jump targeted `targetSession`, so the intent needs re-deriving, not just a mechanical rewrite.
- **Warning 4 is a data race.** A captured `var` mutated from a Sendable closure and read from the test body has no synchronization; the compiler is pointing at exactly the pattern that makes a test flaky or silently wrong.

Both should be **fixed properly, not silenced**:

- For warning 2: make the assertion actually check something — e.g. assert that the target session's `focusedPaneID` equals the pane the bell entry belongs to (and decide whether `focusedPaneID` being non-optional means the check should compare against a concrete pane ID rather than nil).
- For warning 4: make the capture concurrency-safe — use Swift Testing's `confirmation`, an actor/`Mutex`-isolated box, or `NotificationCenter`'s async notification sequence instead of a bare captured `var`.

Warnings 1 and 3 are ordinary cleanliness: `_ = store.markSeen(id: first.id)` (or `@discardableResult` on the API if dropping the result is generally fine), and deleting `suggestedPaths` together with its suppression line.

## Steps to reproduce

1. `scripts/build.sh unit` on an incremental build — zero warnings reported (test sources unchanged, nothing recompiles).
2. Force a full recompile of the test targets (e.g. `touch` the test files, clean the module's build products, or clean-build the test bundle).
3. The 4 warnings above appear, repeated across compile invocations (~35 log lines).

## Expected behavior

Test targets compile with zero warnings, matching the standard #0320 established for app and kit sources, and the two tautological/racy tests actually verify what they claim to.

## Actual behavior

Four warnings in `BattyKitTests`, invisible on incremental builds; one assertion cannot fail, and one test relies on an unsynchronized captured `var`.

## Notes

The invisibility mechanism is the interesting part: `scripts/build.sh unit` only recompiles changed files, so warnings in untouched test files are structurally silent — the same gap #0320 identified for the main targets. Consider whether the eventual fix should also address detection (e.g. a periodic clean-build check), though that may belong in its own follow-up if scoped.
