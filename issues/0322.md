## Description

#0320 cleared all compiler warnings from the app and kit sources — a forced full recompile of every `.swift` under `BattyKit/Sources` and `Batty` now produces zero warnings. But the sweep did not cover the test targets: forcing a recompile of `BattyKitTests` produces 4 unique warnings (~35 log lines repeated across compile invocations). The pre-commit gate (`scripts/build.sh unit`) does not surface them on incremental builds — the test files are unchanged, so they never recompile and never re-emit. This is the same structural problem #0320 was filed about: warnings that exist but are invisible in normal use, so they never generate pressure to fix.

All four warnings were verified against source before filing — each cited line does what the warning says:

1. `BattyKit/Tests/BattyKitTests/BellFeedCollapseTests.swift:110:15` — result of call to `markSeen(id:)` is unused. `BellFeedStore.markSeen(id:)` returns `BellFeedEntry?` and is not `@discardableResult`; the test at line 110 calls it for its side effect (marking the entry seen) and drops the return.
2. `BattyKit/Tests/BattyKitTests/CrossWindowBehaviorTests.swift:173:51` — comparing non-optional `UUID` to `nil` always returns true. `SplitTree.focusedPaneID` is declared `public var focusedPaneID: UUID` (non-optional), so `#expect(w1.sessions[0].tree.focusedPaneID != nil)` is a tautology that can never fail.
3. `BattyKit/Tests/BattyKitTests/MultiWindowCWDNamingTests.swift:205:13` — `suggestedPaths` never mutated; use `let`. Verified worse than the warning says: the variable is vestigial. The local `FixedSuggester` class records paths into its own `paths` property; nothing ever appends to `suggestedPaths`, and its only use is line 232's `_ = suggestedPaths  // Suppress unused warning` — a suppression line serving a dead variable.
4. `BattyKit/Tests/BattyKitTests/SidebarRestorationTests.swift:76:13` — mutation of captured var `received` in concurrently-executing code. The `NotificationCenter.addObserver(forName:object:queue:)` handler (a Sendable closure) sets `received = true` at line 76, and the test body reads it at line 82 after `await Task.yield()`.

Two of the four are likely real test defects, not just noise:

- **Warning 2 is a tautological assertion.** Whatever `#expect(... != nil)` was meant to verify — presumably that `jumpToBellEntry` focuses a pane in the target session — is currently unverified; the expectation cannot fail under any behavior. Note also that the line inspects `w1.sessions[0]` (the originally focused session) while the jump targeted `targetSession`, so the intent needs re-deriving, not just a mechanical rewrite.
- **Warning 4 is a data race.** A captured `var` mutated from a Sendable closure and read from the test body has no synchronization; the compiler is pointing at exactly the pattern that makes a test flaky or silently wrong.

Both should be **fixed properly, not silenced**:

- For warning 2: make the assertion actually check something — e.g. assert that the target session's `focusedPaneID` equals the pane the bell entry belongs to (and decide whether `focusedPaneID` being non-optional means the check should compare against a concrete pane ID rather than nil).
- For warning 4: make the capture concurrency-safe — use Swift Testing's `confirmation`, an actor/`Mutex`-isolated box, or `NotificationCenter`'s async notification sequence instead of a bare captured `var`.

Warnings 1 and 3 are ordinary cleanliness: `_ = store.markSeen(id: first.id)` (or `@discardableResult` on the API if dropping the result is generally fine), and deleting `suggestedPaths` together with its suppression line.

## Resolution notes

> 🟢 Resolved 2026-08-08 — all four warnings cleared, and the two that masked real defects now verify something. A forced full test-target recompile emits zero source warnings.

The tautological assertion took two rounds to actually fix: the first attempt corrected which session it inspected but was still true by construction. It now fails under mutation.

## Root cause

#0320 cleared compiler warnings from the app and kit targets but its sweep did not cover test targets, and `scripts/build.sh unit` only surfaces warnings for files it recompiles — so on the incremental builds everyone actually runs, these four were invisible. Same structural blind spot #0320 was filed about, one target over.

Two of the four were not cosmetic:

- `CrossWindowBehaviorTests.swift` asserted `w1.sessions[0].tree.focusedPaneID != nil` against a **non-optional** `UUID`. The comparison could never fail, so whatever it meant to check went unverified. It was also inspecting the originally-focused session while the jump under test targeted a different one.
- `SidebarRestorationTests.swift` mutated a captured `var` inside a `Sendable` `NotificationCenter` handler that enqueues onto the main queue, then read it from the test body behind a hopeful `await Task.yield()`. A genuine data race.

## Fix

- **`BellFeedCollapseTests.swift`** — `_ = store.markSeen(id:)` at the one side-effect-only call site, rather than adding `@discardableResult`. The return value is real control flow at `WindowRuntime.swift:482` and `AppStateStore.swift:1079` (both guard/if-let) and is asserted in `BellFeedStoreTests.swift:51`; making it discardable would have quietly weakened those.
- **`CrossWindowBehaviorTests.swift`** — the test now splits the target session so focus sits on a *different* pane before the bell rings, asserts that precondition explicitly, and then asserts `targetSession.tree.focusedPaneID == pane.id` after the jump. Pre- and post-state genuinely differ, so the assertion exercises the write in `WindowRuntime.jumpToBellEntry`.
- **`MultiWindowCWDNamingTests.swift`** — `suggestedPaths` deleted outright along with its `_ = suggestedPaths` suppression line; nothing read it.
- **`SidebarRestorationTests.swift`** — rewritten around Swift Testing's `confirmation(_:)`, which is purpose-built for "did this async callback fire" and is internally synchronized, so no shared mutable capture exists to race on.

## Review

Reviewer: `claude-opus-5`, two rounds.

Round 1 reproduced the warning sweep independently (forced full test-target recompile, confirming `BattyKitTests` genuinely rebuilt across 108 `SwiftCompile` lines) and approved three of the four fixes with specific evidence for each. It then found that the tautology fix **was still a tautology**: `SplitTree.init(root:)` sets `focusedPaneID` to the first leaf pane at construction, and nothing writes it between session creation and the jump — so deleting the production line under test would have left the new assertion passing. A compile-time tautology had been traded for a construction-time one.

Round 2 verified the strengthened assertion from source and then **ran the mutation test itself**: commenting out `WindowRuntime.swift:470` produced exactly two failures, one of them the strengthened assertion. It also confirmed the extra pane changed nothing else the test covers, and corrected one of its own round-1 claims — `PaneHideTests.swift:208` is pre-existing real coverage of that same write, so "no coverage anywhere" had been too strong.

## Gotchas

- **`scripts/build.sh unit` does not show you warnings in files it doesn't recompile.** These four survived #0320 and sat unnoticed. To actually check, force a full recompile: `find BattyKit/Tests -name '*.swift' -exec touch {} +` then run the gate. Nothing in the repo does this automatically, so the blind spot remains open.
- **An assertion can be a tautology by construction, not just by type.** `#expect(targetSession.tree.focusedPaneID == pane.id)` looks like a real check and passes for the right-looking reason, but `SplitTree.init` had already made it true. The only reliable test of a test is to break the production line it covers and confirm it fails.
- **`FixedSuggester.paths` in `MultiWindowCWDNamingTests.swift` is still write-only dead state** — appended to, never read. Not a warning, so deliberately left; noted here so the next reader knows it was seen rather than missed.

3. The 4 warnings above appear, repeated across compile invocations (~35 log lines).

## Expected behavior

Test targets compile with zero warnings, matching the standard #0320 established for app and kit sources, and the two tautological/racy tests actually verify what they claim to.

## Actual behavior

Four warnings in `BattyKitTests`, invisible on incremental builds; one assertion cannot fail, and one test relies on an unsynchronized captured `var`.

## Notes

The invisibility mechanism is the interesting part: `scripts/build.sh unit` only recompiles changed files, so warnings in untouched test files are structurally silent — the same gap #0320 identified for the main targets. Consider whether the eventual fix should also address detection (e.g. a periodic clean-build check), though that may belong in its own follow-up if scoped.
