## Description

The user's report (2026-10-13), verbatim:

> When I opened the project I created it did not run the commands for the terinmals that I had set.

A Project created through Save Session as Project starts with `runStartupCommandsOnOpen` off. New Project… starts with it on. When the user then adds startup commands in the Project Editor, the only control for the flag is the footer toggle, which stays off, and opening the Project silently runs nothing: no trust prompt, no hint, no indicator. The commands are stored and visible in the editor, so the Project looks configured.

Ships on `main` for 1.3.0, behind the Projects flag. With the flag off nothing here is reachable.

## Steps to reproduce

1. With a Session open, use Sidebar ▸ Save Session as Project (or the File menu or palette entry).
2. In the editor, type a startup command into a Tab (for example `claude`). Leave the footer toggle as it is. Save.
3. Close the Session and open the Project from the picker.

## Expected behavior

The trust sheet (#0473) prompts for the unapproved commands, and after approval they are typed into their Tabs.

## Actual behavior

Nothing runs. The user's Beta `~/Library/Application Support/Batty Beta/projects.json` holds one Project, "Batty", with `startupCommand` `claude` on one Tab and `lri` on another, `"runStartupCommandsOnOpen": false`, and no `approvedCommandsHash`.

## Current code (verified on `main` at `c2349a5e`, 2026-10-13)

- `SessionProjectCapture.newDraft(name:existingNames:)` (`BattyKit/Sources/BattyKit/Model/SessionProjectCapture.swift:241-252`) builds the captured draft with `runStartupCommandsOnOpen: false` (`:247`), under the comment "The run toggle is off: a captured Project has no commands." (`:239-240`). Called from `BattyKit/Sources/BattyKit/Views/SaveSessionAsProject.swift:52`.
- `ProjectDraft.init(id:name:rootPath:color:symbol:layout:runStartupCommandsOnOpen:)` (`Model/ProjectDraft.swift:50-57`) defaults the flag to `true`, so New Project… starts on.
- `SessionProjectCapture.updateDraft(of:)` (`SessionProjectCapture.swift:259-277`, "Update from Session", called from `SaveSessionAsProject.swift:48`) starts from `ProjectDraft(project:)` and so keeps the stored Project's flag.
- `ProjectStartupTrust.decide` (`Model/ProjectStartupTrust.swift:35-40`) returns `.skip` when the flag is off or there are no commands; otherwise `.prompt` or `.runWithoutPrompt` by `approvedCommandsHash`.
- The flag's only control is the footer `Toggle` "Run startup commands when the Project opens", `project-editor.run-commands`, in `ProjectEditorFooter` (`Views/ProjectEditorView.swift:891-904`), bound through `ProjectEditorViewModel.setRunStartupCommandsOnOpen` (`Model/ProjectEditorViewModel.swift:525`). Nothing in the editor or at open time says that stored commands will not run.
- Existing tests pin the current default: `SessionProjectCaptureTests.swift:318` and `SaveSessionAsProjectTests.swift:173`, `:229`, `:247` assert `!draft.runStartupCommandsOnOpen`; they change with D1.

## Decisions

- **D1. A captured draft defaults `runStartupCommandsOnOpen` to `true`**, the same as New Project…. `newDraft` drops the `runStartupCommandsOnOpen: false` argument and the stale comment. This is safe: `decide` returns `.skip` while there are no commands, and once the user adds some the trust sheet (#0473) prompts before anything runs, because a new Project has no `approvedCommandsHash`.
- **D2. "Update from Session" keeps the stored Project's toggle.** `updateDraft(of:)` already does this; it is unchanged.
- **D3. The editor shows a hint when commands exist but the toggle is off.** When the draft has at least one non-empty startup command and `runStartupCommandsOnOpen` is `false`, a caption appears beside the footer toggle: "Startup commands won't run when this Project opens." Accessibility identifier `project-editor.commands-off-hint`. It disappears as soon as the toggle is on or the last command is cleared. Wording is open to the user's sign-off.
- **D4. No migration of stored Projects.** A Project saved before this issue keeps its stored flag; the user turns the toggle on in the editor, and the D3 hint shows them why. Said again under Notes.

## Notes

- **No migration.** The user's existing "Batty" Project, and any other Project saved with the toggle off, is not rewritten. Turning the toggle on in the editor is the fix for stored Projects, and the D3 hint makes the off state visible.
- **Why the default was off.** The comment at `SessionProjectCapture.swift:239-240` reasoned that a captured Project has no commands, so the toggle did not matter. It stopped being true the moment the user typed a command into the captured draft, and the toggle never followed.
- **Why not prompt at open time instead.** `decide` returning `.skip` for a flag-off Project is the documented contract of #0473 (the toggle is the user's way to keep a Project's commands without running them). The bug is the default plus the silence in the editor, not the skip.
- Line numbers were grepped on `main` at `c2349a5e` on 2026-10-13.
