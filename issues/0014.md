## Description

Each Pane (a leaf of the split tree) renders a SlidingTabs bar above its content area. Adding a tab creates a fresh Terminal Session; closing a tab tears its surface down; non-active tabs keep running in the background. This is the M3 milestone — even though splits aren't here yet, every Pane (currently the only one) gets a tab strip.

**Acceptance criteria:**
- `PaneView` shows `SlidingTabBar` at the top with a chip per Tab.
- Clicking a chip selects that Tab; the Pane's rendered surface swaps to the active Tab's surface.
- The "+" affordance on `SlidingTabBar` adds a new Tab with a fresh Terminal Session (cwd inherited from the focused tab's cwd).
- Closing a tab via its chip's close button calls `SurfaceRegistry.destroy(surfaceID)` and removes the Tab.
- `onReorderCommit` from SlidingTabs persists the new order in the Pane model.
- Visual: chip uses `DefaultTabChip` (or a custom chip later). Default chip's `hasUnseen` dot remains `false` for now — bell wiring is #0028.

## Notes

- Closing the last Tab in a Pane is **out of scope** here — that interacts with split collapse and is owned by #0021.
- Title resolution (focused-surface process → cwd → user override) is #0016.
- Keybindings for tab navigation are #0015.

## Root cause

Feature gap. M3 introduces tabs at the pane level — until now each Session held a single `TerminalViewState` directly. The runtime model needed to grow a Pane → [Tab] hierarchy paralleling `Concepts.md` → Pane / Tab.

## Fix

Three new public types in `BattyKit/Sources/BattyKit/`:

- **`TabRuntime`** — `@Observable {id, titleOverride, terminal: TerminalViewState}`. Each tab owns exactly one `TerminalViewState`, which is the live wrapper around its libghostty surface.
- **`PaneRuntime`** — `@Observable {id, tabs: [TabRuntime], activeTabID}`. Init is non-empty by precondition; `addTab()` appends and selects; `removeTab(id:)` is a no-op when only one tab remains (last-tab semantics belong to #0021); `activeTab` computed property returns the currently-rendered tab.
- **`PaneView`** — wraps the SlidingTabs package's `SlidingTabBar` above a `ZStack` of the pane's `TerminalSurfaceView`s. Inactive tabs are at `.opacity(0)` and `.allowsHitTesting(false)` so their surfaces stay alive but invisible — same approach as `SessionDetailView`'s session ZStack from #0010. Uses `DefaultTabChip`; `hasUnseen=false` (bell wiring is #0028); `onClose=nil` when `tabs.count == 1` so the close button hides.

`SessionRuntime` swapped its `terminal: TerminalViewState` for `pane: PaneRuntime`. New sessions still spawn one pane, one tab, one fresh terminal — M2 behavior is preserved at the user-visible level.

`SessionDetailView` renders `PaneView(pane: session.pane)` instead of `TerminalSurfaceView(context: session.terminal)` directly. The window's `navigationTitle` resolves through `session.pane.activeTab.terminal.title`.

The chip title resolves: `titleOverride` (future user-set) → live terminal title → `"Tab"` fallback. The chip prefers the live OSC title because at the **tab level** the live title is the right identity (per `Concepts.md` → Tab); this is distinct from the **session level**, where #0043 made the user-set name sticky.

## Gotchas

- **Visual verification needed.** Confirm: SlidingTabs bar appears at the top of the pane, "+" adds a fresh tab with a fresh shell, clicking chips switches the visible terminal, drag-to-reorder works, close button on a chip removes the tab, close button hides when only one tab. `xcodebuild build` passes; resolved-not-closed.
- **Resource cost grows quadratically with sessions × tabs.** Every TerminalSurfaceView in every PaneView in every SessionDetailView is mounted at all times via the nested ZStacks. A user with 5 sessions × 5 tabs = 25 live surfaces, all driving display links. Acceptable for v1; if we hit a wall, the optimization is to swap visible surfaces in/out of the SwiftUI tree rather than holding all of them. Holding `TerminalViewState` instances alive is what keeps shells alive, so the runtime objects can stay in memory regardless.
- **`activeTabID` is non-optional UUID** but SlidingTabs's `activeID:` API takes `Binding<T.ID?>`. `PaneView` exposes a custom `Binding<UUID?>` wrapper that maps non-optional to optional and ignores `nil` writes. This means SlidingTabs cannot deselect everything by writing nil — that's by design; a pane always has an active tab.
- **No keybindings yet.** Cmd-T / Cmd-W / Cmd-1..9 / Cmd-Shift-[ ] are #0015. The "+" button and chip clicks are the only affordances right now.
- **Title resolution at the tab level prefers live title.** This is *correct* per `Concepts.md` → Tab and is the inverse of the session-level rule fixed in #0043. The two levels have different semantics: session = sticky workspace identity; tab = "what's running here right now". A `titleOverride` field is in place for the future user-set rename UX from #0016.
- **cwd inheritance is not implemented.** Per the issue Notes, new tabs should ideally spawn in the focused tab's cwd. That requires `TerminalSurfacePwdDelegate` wiring, which is part of #0016. For now, `addTab()` creates a `TerminalViewState()` with default cwd (the user's `$HOME` via libghostty's exec backend). Documented as a follow-up to #0016.
