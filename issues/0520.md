# 0520 — The `TabRuntime ... still referenced 0.5s after release` notice fires on nearly every app launch in the UI suite, across unrelated close paths, which is the documented leak signal

| | |
|---|---|
| **Status** | open |
| **Module** | GhosttyKit / Tabs / Window |
| **Platform** | macOS |
| **First seen** | 2026-10-16 |

## Description

`TerminalHostStore.releaseTerminalView(forTabID:)` calls `verifyReferenceHygiene` (`BattyKit/Sources/BattyKit/Runtime/TerminalHostStore.swift:293`, 328–341). That holds a `weak` probe on the closed tab's `TabRuntime`, checks it 0.5 s later on the main queue, and logs at `.notice` if it is still alive:

> TabRuntime for tab <UUID> still referenced 0.5s after release — expected to clear shortly on its own (a rename sheet or SwiftUI placeholder can hold it briefly); repeated notices across unrelated tab closes would mean something is leaking a TabRuntime reference and keeping its ghostty app + glyph atlas alive

The doc comment (lines 314–315) and `docs/view-hierarchy.md` §6 both say that one notice on one close is expected. They also say that "repeated notices across *multiple, unrelated* tab closes is the real signal to chase". `TabRuntime` owns the `TerminalController`: the per-Tab `ghostty_app_t` and its glyph atlas (#0285). The surface and PTY are freed synchronously before the probe runs (#0289), so a held `TabRuntime` keeps the ghostty app and atlas alive, not the shell.

The #0240 multi-window VM runs show that signal. Counts are from `guest-state/app-info.log` (artifacts under the `Batty-0240` worktree's `build/ui-tests/`):

| Run | Notices | App processes with a notice | Notices per process |
|---|---|---|---|
| `20261016-181007-64163` (unfiltered, cut off at 40 min, see #0518) | 10 | 8 | 7 processes x 1, pid 22725 x 3 |
| `20261016-185336-94049` (`MultiWindowCLITests` … `WindowRestorationTests`) | 23 | 23 | 1 each |

In total there were 33 notices. Each UI test is its own app launch, and they come from unrelated suites and close paths:

- the multi-window window close in `MultiWindowCLITests` (pid 5300, 01:55:40; `testClosingOneWindowLeavesTheOtherIntact` closes a window through its close button, on `issue/0240`);
- `LifecycleTests` / `ModalConfirmationTests` (pid 15352);
- the Projects suites (pids 17292–18555, and pid 22725 three times during `ProjectsStartupTests`);
- every one of the `ViewGalleryTests` launches (pids 7115–8683, one per launch, each about 5 s after that process's first log line).

The run-1 window is truncated (#0519), so the true run-1 count is higher.

Two caveats:

- **This is not proof of a leak.** The probe takes one sample at 0.5 s. Nothing logs whether the `TabRuntime` is freed later, and `app.terminate()` kills each process seconds afterwards. A holder that clears at 0.6 s and one that never clears look the same.
- **The specific close path behind each notice was not confirmed from the logs.** The `released terminal view` / `created terminal view` debug lines that would pair each notice with its close are not stored on the guest (#0519).

## Steps to reproduce

Only inside the Tart VM, never on a host Mac (AGENTS.md, #0409).

1. `tools/run-ui-tests-vm.sh BattyUITests/ViewGalleryTests` (or `BattyUITests/MultiWindowTests`).
2. `grep -c "TabRuntime for tab .* still referenced" build/ui-tests/<run-id>/guest-state/app-info.log`.

To see it locally, without UI automation: in a Beta build, close a Tab and then close a second Window. Stream `log stream --level info --predicate 'subsystem == "co.sstools.Batty.beta" AND category == "TerminalHostStore"'`.

## Expected behavior

A closed Tab's `TabRuntime`, and with it the ghostty app and glyph atlas, deallocates soon after `releaseTerminalView(forTabID:)`. If the 0.5 s notice fires at all, a later check finds the reference gone.

## Actual behavior

The notice fires on nearly every launch that closes a Tab or Window, across unrelated close paths. Nothing shows whether the reference is ever released.

## Notes

Investigation directions (not conclusions):

- **Second, later sample.** Add a follow-up check in `verifyReferenceHygiene`, e.g. 5 s after the first, that logs at `.notice` or `.error` when it is still alive and at `.debug` when it has cleared. That separates "slow to drain" from "held". It stays diagnostic-only and does not gate teardown. A UI test that keeps the app alive past the second sample, and awaits a completion signal rather than sleeping (AGENTS.md, "Asynchronous tests"), could then assert on it.
- **Trace the holder.** Use Instruments Allocations or Leaks, or the Xcode memory graph debugger, after closing a Tab in a Beta build. Find what retains `TabRuntime`. Candidates from the doc comment: `TerminalPlaceholderView`, `PaneView`, a rename sheet. Others to rule out: a SwiftUI `@State` / `@Environment` capture, a closure in `TabRuntime`'s own observers, `WindowRuntime` / `PaneRuntime` arrays, Command Palette or Open Quickly models, the Bell Feed, and the CLI/XPC session snapshot.
- **One-shot pattern.** Most processes log exactly once, even when the test closes more than one Tab, so the first close per process may be the special case. For example, a lazily created object could capture the first `TabRuntime` it sees. Check that before assuming a per-close leak.
- **Unit-level reproduction.** If the holder lives in BattyKit model or runtime code, a `BattyKitTests` test can assert that the `TabRuntime` deallocates after `closeTab` / window close, using a `weak` reference plus an `autoreleasepool` (as `StableTerminalSurfaceTests` already does). No timing is involved.

## Acceptance criterion

The holder is identified and either fixed, or documented as bounded with evidence (the later sample shows it clearing). After the change, a VM run of `ViewGalleryTests` + `MultiWindowTests` shows no `TabRuntime` still alive at the later check. `docs/view-hierarchy.md` §6 is updated to describe whatever the probe now logs.
