# 0713 — Beta packages report version 1.4.0 (1) because main was never moved to 1.5.0 and Beta packaging never stamps a build number

## Description

User report (2026-11-21), verbatim: "I think I am running the latest .dmg but this is what I see as the version. That looks totally wrong. Version 1.4.0 (1)" and then "No, this build should not show this version number. The 1 should at least be the normal time stamp."

Every Batty Beta built by `./build.sh package` (unsigned, `--sign`, `--sign --notarize`, `--sign --notarize --no-submit`) shows `CFBundleVersion` `1`, because `scripts/build-beta.sh` never overrides `CURRENT_PROJECT_VERSION` the way `scripts/release.sh` does. And a Beta built from `main` shows `MARKETING_VERSION` `1.4.0`, because `main` was not moved to the next minor after `release/1.4` was cut, while 1.4.1 and 1.4.2 shipped from `release/1.4`. The result, `1.4.0 (1)` in the About panel, looks like an old release and doesn't identify the build.

The user directed the outcome on 2026-11-21 (quoted above): Beta packages carry the normal timestamp build number, and Betas from `main` don't claim to be 1.4.0.

## Steps to reproduce

1. On `main`, `./build.sh package --sign --notarize --no-submit` (or any `./build.sh package` variant).
2. Install the DMG/app and open Batty Beta → About Batty Beta.

Already reproduced with today's `~/Gibson/Batty/Batty-Beta-0696-pty-host-7ad7a5d5-unnotarized.dmg` (built from `issue/0696`): the mounted `Batty Beta.app/Contents/Info.plist` has `CFBundleShortVersionString` `1.4.0`, `CFBundleVersion` `1`, `CFBundleIdentifier` `co.sstools.Batty.beta`.

## Expected behavior

- About shows `1.5.0 (<YYYYMMDDHHMM>)` for a Beta from `main`, e.g. `1.5.0 (202611212315)`, the same build-number form as Prod (`1.4.2 (202611210007)`).
- A Beta packaged from `release/1.4` shows `1.4.2 (<timestamp>)`.

## Actual behavior

`1.4.0 (1)` for every Beta from `main`; `<X.Y.Z> (1)` for every Beta from any branch.

## Current state (checked on `main` at `452c4ab9`)

- **Versions.** `Configuration/App.xcconfig:49-50`: `MARKETING_VERSION = 1.4.0`, `CURRENT_PROJECT_VERSION = 1` on `main` and on `issue/0696`. On `release/1.4`, `1.4.2` / `1` (bumps `eca8ef61` 1.4.1, `76604b24` 1.4.2, only on that branch). `Configuration/Info.plist:17-20` reads both through `$(MARKETING_VERSION)` / `$(CURRENT_PROJECT_VERSION)`.
- **Release stamping.** `scripts/build-number.sh` defines `release_build_number()` = `date -u +%Y%m%d%H%M`. `scripts/release.sh:30` sources it, `:165` passes `CURRENT_PROJECT_VERSION="$BUILD_NUMBER"` to `xcodebuild archive`, and `:330-346` reads `CFBundleVersion` back from the exported app with PlistBuddy and fails if it doesn't match.
- **Beta packaging doesn't stamp.** `build.sh:220-223` execs `scripts/build-beta.sh`. Its two `xcodebuild` calls pass no `CURRENT_PROJECT_VERSION`:

- **preflight.** `scripts/preflight.sh:529-532` requires `CURRENT_PROJECT_VERSION` to live only in `App.xcconfig` (no `project.pbxproj` override). A command-line build-setting override, as `release.sh` uses, satisfies that.
- **Who reads the values.** `Views/AboutPanel.swift:11-12` (the user's screenshot), bell-capture diagnostics `Runtime/AppStateStore+BellCapture.swift:60-61`, `Runtime/AppStateStore.swift:720-721`, `batty --version` (`batty/SessionCommand.swift:30`), agent-guidance identity (`BattyCLICore/AgentGuidanceIdentity.swift:56`, marketing version only).

### Corrections to the orchestrator's premises

- **Sparkle doesn't order Betas.** The Beta variant has no update feed: `Configuration/Beta.xcconfig` sets `SU_FEED_URL =` and `SU_PUBLIC_ED_KEY =` empty. So `(1)` is an identification problem (About, crash reports, bell diagnostics), not an update-ordering one. Sparkle compares `CFBundleVersion` only for Prod.
- **`./build.sh package` without `--sign` also goes through `build-beta.sh`** (unsigned Debug `xcodebuild build`). It is a Beta package too and should get the stamp, so the fix covers all four `package` variants, not only `--sign`.
- **`scripts/RELEASE.md:80-82` is now wrong** in one sentence: "The static value left in `App.xcconfig` is only used by Xcode-driven Debug builds, which Sparkle never sees." Beta packages use it today. After the fix it becomes true for `./build.sh`, `./build.sh unit`, Xcode and the VM runner; reword it to say so.
- **No doc has the "bump `main` after cutting `release/X.Y`" step.** AGENTS.md "Release branches" (`AGENTS.md:244-253`) says to create `release/X.Y` from the tag and to bump `release/X.Y` for patches, but nothing about `main`. `scripts/RELEASE.md` has no release-branch section at all (step 1 "Choose the version", `:63-92`; step 8 "Tag the release", `:195`ff). `docs/code-signing.md` says nothing about versions. History confirms the gap: `main`'s last bump is `0cd7d2fb Bump version to 1.4.0`.

## Approach notes for the planner

1. **Stamp every Beta package** in `scripts/build-beta.sh`:
   - `source "$REPO/scripts/build-number.sh"` (`REPO` is set at `scripts/build-beta.sh:106`) and compute `BUILD_NUMBER=$(release_build_number)` once near the top.
   - Add `CURRENT_PROJECT_VERSION="$BUILD_NUMBER"` to both the `xcodebuild archive` call (`:339`) and the `xcodebuild build` call (`:528`).
   - After each, read `CFBundleVersion` from the produced app (`$APP_PATH/Contents/Info.plist` after export; `$BUILT_APP/Contents/Info.plist` after build) with PlistBuddy and fail with an error if it isn't `$BUILD_NUMBER`, as `release.sh:337-346` does. Do the check before signing-dependent steps (DMG, notarization) so a mismatch costs nothing.
   - Print it in the final summary, e.g. `==> Built: … (1.5.0 (202611212315))`.
   - Don't apply the appcast collision gate (`newest_appcast_build` / `build_number_is_newer`): Betas have no feed.
   - **No change to signing, export options, entitlements, profiles or notarization logic.** Only the build-number argument, the read-back check and the summary line.
   - Watch the incremental-build cost: a command-line build setting that changes every minute applies to every target in the workspace (BattyKit package targets too). Check a second `./build.sh package` run's time against today's; if the override forces a full rebuild of BattyKit, say so in the resolution (release.sh already pays this cost for archives). Don't switch to editing Info.plist after the build: that breaks the signature on `--sign` builds.
2. **Plain `./build.sh` dev builds, `./build.sh unit`, Xcode and the VM runner keep `CURRENT_PROJECT_VERSION = 1`.** They aren't installed for use; a stable value keeps incremental builds warm. Say so in `scripts/RELEASE.md` and the `build-beta.sh` header.
3. **Move `main` to 1.5.0.** `Configuration/App.xcconfig:49` → `MARKETING_VERSION = 1.5.0` on `main` only, never cherry-picked. `CURRENT_PROJECT_VERSION` stays `1`. Grep tests for a hard-coded `1.4.0` that reads the real bundle (none found: `AgentGuidanceInstallerTests.swift:45` writes its own `1.5.0` fixture).
4. **Docs.**
   - AGENTS.md "Release branches", "Cutting a release" bullet: add "then bump `MARKETING_VERSION` on `main` to `X.(Y+1).0` and commit it as `Bump version to X.(Y+1).0`, so Betas from `main` don't share the shipped version."
   - `scripts/RELEASE.md`: add the same as a step after tagging (or a short "Release branches" note pointing to AGENTS.md), and fix the `:80-82` sentence per the corrections above, mentioning that Beta packages get a timestamp build number too.
   - `build.sh` help text for `package` (`build.sh:27-30`) and the `build-beta.sh` header: one line saying the package's `CFBundleVersion` is the UTC timestamp.
