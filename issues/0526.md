# 0526 — Reopening the Bell Feed's Suggest Better Text editor after saving with Return sometimes leaves the text field without keyboard focus

| | |
|---|---|
| **Status** | open |
| **Module** | BellFeed / Testing |
| **Platform** | macOS |
| **First seen** | 2026-10-18 |

## Description

Regression in #0524 (Bell Feed entry ratings). Open Suggest Better Text from a Bell Feed entry's context menu, type, and press Return to save. Then open Suggest Better Text again on the same entry. Sometimes the text field does not get keyboard focus. The caret is not in the field, and typing goes nowhere until the user clicks the field. The first open focuses the field correctly. Only the reopen after a save fails, and only some of the time.

Data capture is not affected. The saved suggestion is written correctly. The bug is in focus only.

Release target: 1.3.2. #0524 was cherry-picked to `release/1.3` as a user-approved exception, like #0523. The fix for this issue follows the same path: fix on `main` through the normal issue workflow, then `git cherry-pick -x` onto `release/1.3` with the user's approval.

## Steps to reproduce

1. Turn on the Bell Feed capture log, so the rating items appear in the entry context menu.
2. Make a Bell fire so the Bell Feed has an entry. Open the Bell Feed popover.
3. Right-click the entry and choose **Suggest Better Text…**. The field has keyboard focus.
4. Type some text and press Return. The editor saves and closes, and the Bell Feed list comes back.
5. Right-click the same entry and choose **Suggest Better Text…** again.

The automated reproduction is the UI test `BattyUITests/BellFeedRatingTests.swift` `testEditorTakesFocusOnOpenReturnSavesAndEscapeCancels`.

## Expected behavior

Every time the editor opens, including a reopen right after a save, the suggestion `TextField` (`bell-feed.suggest.field`) holds keyboard focus. The user can type at once.

## Actual behavior

On the reopen, the field sometimes does not get keyboard focus. The UI test fails at line 140, `waitForEditorFocus(reopened, in: app)`, with `XCTAssertTrue failed - the suggestion field must hold keyboard focus when the editor opens`. That helper waits up to 5 s for `hasKeyboardFocus == true` on the field. The first-open assertion in the same test (line 130) passes.

## Notes

Code: `BattyKit/Sources/BattyKit/Views/BellFeedView.swift`. These structural facts were checked against the code at the time of filing:

- `BellFeedView.body` swaps between the editor and the list on `@State suggestion: SuggestionTarget?`. When `suggestion` is non-nil and its entry exists, the body shows `BellSuggestionEditor(...)` with `.id(id)`, where `id` is the entry id. Otherwise it shows a `List(selection: $selectedEntryID)` (`bell-feed.list`). The editor and the list are never on screen together.
- The `List` has its own `.onKeyPress` handlers for `.return` (jump to the selected entry), `.escape` (dismiss the popover), `.upArrow` and `.downArrow`.
- The context-menu **Suggest Better Text…** button sets `suggestion = store.bellRatingSnapshot(forEntryID:)...`. Saving runs `store.suggestBellText(...)` and then `suggestion = nil`. Cancel sets `suggestion = nil`.
- `BellSuggestionEditor` (around line 232) has `@FocusState private var fieldFocused: Bool`. The `TextField` has `.focused($fieldFocused)`. The only focus request is `.onAppear { fieldFocused = true }` on the editor's outer `VStack`.
- The `TextField` handles Return in two places: `.onSubmit { if canSave { onSave(draft) } }` and `.onKeyPress(keys: [.return])`, which calls `onSave(draft)` and returns `.handled` when there are no modifiers.
- The reopen uses the same `.id(id)` value as the first open, because it is the same entry. The editor left the hierarchy in between, so SwiftUI builds a new editor and a new `@FocusState`.

Suspected cause, not yet confirmed: after a save, the `List` comes back as a new AppKit table view inside the popover and may take first responder. On the reopen, the context menu closes, the list is torn down, and the editor's `onAppear` focus write all happen close together. The `fieldFocused = true` write can land before the new field is in a window that can take first responder, or lose to the outgoing list or the popover's own responder handling. When it loses, nothing asks for focus again. The first open may pass only because the responder state happens to be different before any save has happened. The implementer must confirm the real sequence before choosing a fix.

### Constraints for the fix

- **Follow `docs/swiftui-observation-rules.md` (binding).** Do not "fix" this by moving the focus write into a `Task`, `DispatchQueue.main.async`, `asyncAfter`, or any delayed retry. That trades a lost write for a race (see #0229). Do not call `makeFirstResponder` or other responder-changing AppKit APIs from SwiftUI callbacks (`body`, `onAppear`, `onChange`, representable updates). Restructure which code owns the focus request. For example, the focus could come from the event that opens the editor rather than from layout-driven `onAppear`, or the focus state could live where the swap happens.
- The reopen must be **deterministic**: the field has focus on every open, not usually.
- Keep the existing behaviour. Return saves and closes the editor, leaving the Bell Feed open. Escape in the editor cancels without dismissing the Bell Feed. The list's Return, Escape and arrow-key handling still work after the editor closes.
- **Do not weaken the test.** Keep the `hasKeyboardFocus` assertion and its 5 s bound in `waitForEditorFocus`, and keep the reopen step. Do not add pauses to make it pass.
- Follow `docs/terminal-pane-requirements.md` if the change touches focus beyond the Bell Feed popover.
