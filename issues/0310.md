## Description

Batty owns zero themes. The entire catalog is upstream Ghostty's dump — 485 entries vendored in the `brennanMKE/libghostty-spm` fork (branch `batty-delegates`) as `Sources/GhosttyTheme/Themes/Themes_<Letter>.swift` buckets plus `Themes/ThemeCatalog_Generated.swift` (see `docs/themes.md` §2). The catalog is read-only at runtime; there is no API to register a theme on the fly, so any Batty-original theme has to land in the fork and reach the app via a package-revision bump in `BattyKit/Package.swift` (`docs/themes.md` §10) — hence the `Build` module tag.

This issue adds a curated set of Batty-original pop-culture terminal themes on top of that catalog, starting with four dark/light theme pairs drawn from *Hackers* (1995). The palettes are already designed and previewed (see Attachments); the remaining work is the delivery architecture in the fork, honest verification of the palettes against real terminal output, and the catalog/package plumbing.

**Per-appearance support already exists and shapes the deliverable.** Batty selects between two catalog themes — one per macOS appearance — via `ThemePreference.darkDefaultsKey` / `lightDefaultsKey` (`co.sstools.Batty.themeName.dark` / `.light`, with migration off the legacy single key) in `BattyKit/Sources/BattyKit/Theme/ThemePreference.swift`, defaulting to `TokyoNight` (dark) and `TokyoNight Day` (light). `BattyKit/Sources/BattyKit/Theme/AppearanceObserver.swift` observes `NSApp.effectiveAppearance` and re-applies the global theme on change. The mechanism is two catalog themes, one per appearance — not the `TerminalTheme(light:dark:)` pair, which `toTerminalTheme()` still collapses to the same config. A dark-only theme therefore drops Light-mode users back to `TokyoNight Day`, which is why every Batty-original theme must ship a light companion (see acceptance criteria).

**The main architectural decision to settle before writing any palettes:** `docs/themes.md` §10 describes hand-adding a `GhosttyThemeDefinition` to the matching `Themes_<Letter>.swift` bucket — but `Script/generate-themes.sh` in the fork downloads the whole theme set from `mbadolato/iTerm2-Color-Schemes` and **regenerates those bucket files and `ThemeCatalog_Generated.swift` wholesale**. A hand-added theme is silently destroyed the next time the generator runs. Batty-original themes must live in a **separate, non-generated bucket** (e.g. `Themes_Batty.swift`) that the generator never writes, with its entries appended to `allThemes` by a mechanism that survives regeneration. Settle this first.

## Expected behavior

The four Hackers-set theme pairs (eight catalog entries — each dark theme plus its `<Name> Day` light companion) appear in the Theme menu and Settings picker like any catalog theme, and every theme in the set meets all of these acceptance criteria:

- **Owns an unclaimed hue pairing.** No existing catalog theme may already occupy the same identity. The neon space is crowded — `Cyberpunk`, `Cyberpunk Scarlet Protocol`, `Cyberdyne`, `Synthwave` (plus `Synthwave Alpha` and `Synthwave Everything`), `Neon`, `Warm Neon`, `Cobalt Neon`, `Laser`, `Retro Legends`, `Hacktober`, `Matrix`, `Blue Matrix`, `Spacegray Eighties`, `C64`, `Borland`, `IRIX Console`, `IRIX Terminal` — so each new theme must stake out a bg/accent pairing none of those hold.
- **Foreground-on-background contrast clears WCAG 4.5:1.**
- **All 16 ANSI slots stay semantically usable** — red reads as error, yellow as warning, green as success — verified against real output (`git status`, a failing build log, `ls --color`), not just against swatches. An "aesthetic" theme that makes a compiler error invisible is a failure.
- **Slot 2 (green) must not read as Matrix green on any theme**, or the set loses its identity.
- **Every theme ships a light companion named `<Name> Day`**, following the `TokyoNight` / `TokyoNight Day` precedent, so a user can set the pair in both appearance slots and appearance switching stays inside the set instead of falling back to `TokyoNight Day`.
- **Light companions follow the light-palette conversion convention** (`TokyoNight Day`'s palette shows it) — this is the part implementers get wrong: slot 0 is a near-background light tint, not black; slot 15 is the ink (the foreground), not white; slots 9–14 **repeat** 1–6 rather than brightening, because a "brighter" variant on a light background is less legible and bold text would vanish; and neon accents must darken substantially to hold 4.5:1 on paper — the acid yellow `f0e800` becomes ochre `8a6a00`, and Acid Burn can't simply invert at all (lime ink on white is unreadable), so its companion changes the relationship: acid-tinted stock, plum ink, lime demoted to an accent.
- Themes survive a rerun of `Script/generate-themes.sh` in the fork (the non-generated-bucket requirement above).

The reference images the palettes were drawn from live in the user's `~/Downloads` (`Hackers.jpg` — the UK quad poster, `Hackers2.jpg` — the blue teaser poster, `Hackers3.jpg` — a cast photo). Do **not** copy them into the repo; they are third-party promotional images. They matter here because the quad poster (violet/magenta/acid-yellow) and the teaser poster (steel-blue monochrome) are genuinely different color worlds — which is why Hackers and Hackers Blue are two themes rather than one compromise.

### Candidates for follow-up themes (verified absent from all 485 catalog entries)

Every name below was checked against the full catalog and is absent. These are candidates, not committed scope — each listed with the hue pairing that would make it distinct:

- **Tron / Encom** — true black with `6fc3df` cyan and an `ffae00` amber antagonist accent. Cyan+amber on black is unclaimed.
- **Max Headroom** — the strongest of the untaken ones: harsh chroma-key electric blue ground, blown-out yellow and magenta video-feedback accents. Nothing in the catalog is built on a saturated blue *background*.
- **WarGames / WOPR** — strict two-tone cyan-white vector on black with a single red DEFCON accent. Risk: collapses into the existing monochrome themes unless kept genuinely two-tone.
- **Weird Science** — 80s mall pastel: hot pink, cyan, lilac. Would be the rare bright/pastel entry in a set that is otherwise all dark.
- **Swordfish** — weakest of the suggestions; the film's memorable element is the 3D file-system UI rather than a palette. Amber-on-slate is the honest reading.
- Also worth noting: **Blade Runner** (sodium amber vs rain teal), **Nostromo / MU-TH-UR** (amber phosphor monochrome), **Sneakers**, **Ghost in the Shell**. **Jurassic Park / SGI** overlaps the existing `IRIX Console` / `IRIX Terminal`, and **Fallout Pip-Boy** collides with `Matrix` green — both are exactly why the "own an unclaimed hue pairing" criterion exists.

Each later candidate needs a light companion too. **Weird Science is the one whose light variant is the primary form** — 80s mall pastel works better on paper than on black, making it the set's natural light-first entry.

### Naming

Film titles are trademarks. Upstream Ghostty already ships `Cyberdyne` (a Terminator reference), so precedent exists — but prefer in-world names over film titles where one is available and evocative (`The Gibson`, `Acid Burn`, `WOPR`, `Encom`, `MU/TH/UR`). A consideration, not a blocker.

### Stale doc

`docs/themes.md` is stale on appearance handling: §5 claims "Batty does not currently honour macOS appearance changes for theme swapping" and §10 lists appearance-paired themes as a future enhancement — both made false by the per-appearance keys in `ThemePreference.swift` and `AppearanceObserver.swift`. The doc needs a refresh; recorded here for a later decision, not filed as its own issue and not fixed in this one.

### Out of scope

These remain separate concerns and are explicitly not part of this issue: user-supplied themes loaded from disk, and a theme-editing UI in Batty. This issue is only about authoring Batty-original palettes (with their light companions) and getting them into the catalog durably.
