## Description

Shard B of the 1.4.3 Release-tier UI suite, run `20261122-175023-17615` (`release/1.4` at `8dd9af81`), ended with xcodebuild's own summary "Executed 106 tests, with 1 test skipped and 1 failure (0 unexpected)". The runner then printed:

```
==> RESULT: TEST FAILED (exit 65)
==> ui: 0 tests
CHECK UI: ERROR (no tests ran)
```

So a real test failure was reported as "could not run" (exit 2), and the failing test was never named. The identical re-run `20261122-182847-61367` passed: "Executed 106 tests, with 1 test skipped and 0 failures (0 unexpected)", `CHECK UI: PASSED`. The skipped test is `SessionReminderTests/testSuggestionIsSelectedSoTypingReplacesIt`.

Shard B classes: ProjectsSymbolTests ProjectsSyncEntitlementTests RemindersPopoverTests SessionBackgroundSettingsTests SessionCwdRenameTests SessionReminderTests SettingsTests SheetMenuGateTests ShiftEnterTests SidebarTests SplitDividerDragTests StuckMouseModeClickTests TabChipRenderingTests TabRenameTests TerminalPersistenceTests TerminalSeeThroughTests ThemeTests ViewGalleryTests WindowCloseQuitTests WindowRegistrationRaceTests WindowRestorationTests.

The run's logs were deleted by `scripts/release.sh` (#0721), so which test failed is unknown.

## Root cause

Two defects, both confirmed from the code; which one fired in `20261122-175023-17615` is unconfirmed (logs deleted, #0721).

1. `XC_EXECUTED` in `tools/check-report.py` (`Executed (\d+) tests?, with (\d+) failures?`) never matched a summary line with a skipped clause ("with 1 test skipped and 1 failure"), so the log fallback had no count and no skipped count.
2. `tools/run-ui-tests-vm.sh` pulled the whole results folder in one 90 s/120 s-bounded `tar`, only logged a failure, and then fell back to `xcodebuild-build.log` (no test lines) whenever `xcodebuild.log` was missing, even after the test step had run. That yields `0 tests` / `no tests ran` regardless of the parser.

## Fix

Followed the plan.
- `check-report.py`: tolerant `XC_EXECUTED` plus `parse_executed(line) -> (executed, skipped, failed, unexpected)`; the log fallback now fills `skipped`. New repeatable `--missing NAME` (a nonexistent `--log` also counts). With anything missing, an `ERROR` outcome other than `interrupted` becomes `ERROR (results not retrieved from guest: …)`; `PASSED`/`FAILED` stand. Prints `==> not retrieved from the guest: …` and leads the digest with it instead of the "No tests ran" hint. `classify` keeps its old logic in `_classify` and wraps it.
- `vm-lib.zsh`: `vm_run_guest_step` takes an optional third argument, a host file to tee the step's output into.
- `run-ui-tests-vm.sh`: the test step tees to `xcodebuild-stream.log`; `pull_results [all|logs|bundle]` reports the cause (`host bound … hit`, `tart exec exit N`, `tar -x exit N (partial archive)`), sets `PULL_FAILED`, preserves `step_rc`; default bound 300/330 s, bundle 600/660 s; final pull is logs then bundle, each retried once. Summary log selection never reads `xcodebuild-build.log` after the test step ran; it falls back to `xcodebuild-stream.log` or passes `--missing`. Comment and header corrected.
- Small addition not spelled out in the plan: the `bundle` pass exits 0 without archiving when the guest has no `UITests.xcresult` (build failure), so it isn't reported as a pull failure.

Round 2 (review notes 1–4):
- `run-ui-tests-vm.sh`: the final passes are `pull_results logs || pull_results logs || LOGS_PULL_FAILED=1` and the same for `bundle` with `BUNDLE_PULL_FAILED`, so a pass that fails twice no longer trips errexit and is recorded. `PULL_FAILED` removed. Log selection: if the logs pass failed (or `xcodebuild.log` is absent) a non-empty `xcodebuild-stream.log` is read, otherwise `--missing xcodebuild.log`; on a build failure a failed logs pass adds `--missing xcodebuild-build.log`. If the bundle pass failed, `--missing UITests.xcresult` whatever is on disk.
- `check-report.py`: an `--xcresult` whose name is in `--missing` is not read (a partial bundle could give wrong counts).
- `docs/ui-testing-vm.md`: worst-case final pull ≈ 33 min, and the twice-failed-pass behavior. `vm-lib.zsh`: comment says a tee file merges stderr into stdout.

## Review notes

Round 1, 2026-11-22 — **bounced**. The parser, selftest, tee and docs are right; the final pull is not.

1. **Blocking: a pull that fails twice aborts the runner.** `tools/run-ui-tests-vm.sh` lines 545–546 (`pull_results logs || pull_results logs`, `pull_results bundle || pull_results bundle`) run under `set -euo pipefail` (re-enabled at line 489). When the retry also returns 1, errexit fires (checked: `zsh -c 'set -euo pipefail; f(){ return 1 }; f || f; echo after'` exits 1 without printing). The run then ends `CHECK UI: ERROR (aborted, exit 1)` via `cleanup`/`finish_check_line`, never reaching the `RESULT:` line, the `--missing` logic or check-report. So exactly the case this issue is about (a large bundle timing out twice) loses a `FAILED` verdict whose `xcodebuild.log` did come back, and never prints `results not retrieved from guest`. The selftest can't see it because it never runs the runner. Fix: don't let a pull failure propagate, e.g. `pull_results logs || pull_results logs || true` (same for bundle), or run the pulls inside `set +e`.
2. **Blocking (same lines): a failed pass must count as missing even when it left a partial file.** `PULL_FAILED` is set but never read. When the logs pass fails after its retry, a truncated `xcodebuild.log` (from `tar -x` of a partial archive) is still read as if complete; with rc 0 and no summary line that is `ERROR (no tests ran)`, the message this issue removes. When the bundle pass fails, a partial `UITests.xcresult` dir keeps `UITests.xcresult` out of `--missing`. Track the outcome of each final pass (e.g. `LOGS_PULL_FAILED`, `BUNDLE_PULL_FAILED`, or drop `PULL_FAILED` for them): if the logs pass failed, prefer a non-empty `xcodebuild-stream.log` over `xcodebuild.log` and otherwise pass `--missing xcodebuild.log`; if the bundle pass failed, pass `--missing UITests.xcresult` whatever is on disk. Remove `PULL_FAILED` if nothing reads it.

## Cause (from reading the code)

**The failure was an ordinary assertion failure, not an expected one.** No test in `BattyUITests/` uses `XCTExpectFailure`. In XCTest's summary, "(0 unexpected)" counts thrown errors, so "1 failure (0 unexpected)" is one failed assertion. That's why xcodebuild exited 65.

**`tools/check-report.py` can't parse that summary line.** It reads counts from the `.xcresult` (`read_xcresult`) when it can, and falls back to the log. The log pattern is `XC_EXECUTED = re.compile(r"Executed (\d+) tests?, with (\d+) failures?")` (line 54). It doesn't match when a test was skipped, because xcodebuild then writes "with 1 test skipped and 1 failure". Checked: the pattern returns no match for "Executed 106 tests, with 1 test skipped and 1 failure (0 unexpected)". With no count, `classify` sees `total == 0` on a non-zero exit and returns `ERROR, "no tests ran"`. It also didn't find the failure through `XC_CASE_FAILED` (`Test Case '…' failed`), or it would have reported `FAILED`.

**Most likely, the results never came back from the guest.** The passing re-run, with the same skipped test, got its counts from the `.xcresult`, so in 175023 the `.xcresult` was probably missing or unreadable. `pull_results` in `tools/run-ui-tests-vm.sh` copies the guest's results folder back best-effort, under a 90 s guest / 120 s host bound, and only logs "Failed to pull some results back from the guest" on failure. If `xcodebuild.log` didn't come back either, the runner falls back to `summary_log="$RESULTS_DIR/xcodebuild-build.log"` (around line 521), which holds the build-for-testing output and no test lines at all. That gives `total == 0` and "no tests ran" whatever the parser does. The "Executed 106 tests" line the orchestrator saw was the guest's test output streamed to the terminal, not the host's copy of `xcodebuild.log`. #0701 records another run (`20261119-222504-63894`) that reported `CHECK UI: ERROR` only because the pull failed. Unconfirmed, because the logs are gone.

## Expected behavior

- `check-report.py` parses every form of xcodebuild's `Executed N tests, with …` line, including "with K tests skipped and M failures", and takes the executed, skipped and failed counts from it.
- A non-zero exit with a parsed failure count is `CHECK UI: FAILED`, never "no tests ran", and the digest names the failing test from the `Test Case '…' failed` lines.
- When the `.xcresult` or `xcodebuild.log` didn't come back, the runner says so next to the `CHECK UI:` line instead of silently reading `xcodebuild-build.log`, and the pull bound is sized for a 30-minute run's result bundle (or the pull is retried).
- `tools/check-report-selftest.py` covers the skipped-and-failed summary line and the missing-`.xcresult` case.
