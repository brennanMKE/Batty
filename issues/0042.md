## Description

`#0012` wired Cmd-Shift-1..9 to select the Nth session, matching the original PRD. macOS reserves four of those nine combinations for screenshots:

- **Cmd-Shift-3** — full-screen screenshot
- **Cmd-Shift-4** — selection screenshot
- **Cmd-Shift-5** — screenshot/recording menu
- **Cmd-Shift-6** — Touch Bar screenshot

So the user can never reach sessions 3, 4, 5, or 6 via the documented shortcut without disabling the system hotkeys. Verified by the user in their spot-check.

The replacement modifier set must:

1. Avoid every reserved macOS hotkey across all 9 numeric keys.
2. Not collide with `Cmd-1..9` which the PRD reserves for **per-pane tab selection** (#0015).
3. Not collide with `Cmd-Shift-[ / ]` which is reserved for tab cycling.
4. Be reachable on standard Apple keyboards without contorted finger positions.
5. Stay available for terminal apps generally (Cmd-Option-Number is what iTerm2 uses for window/tab switching, so it's familiar to the user base).

**Recommendation: Cmd-Option-1..9 for session selection, Cmd-Option-N for new session.** Cmd-Option-Number is unreserved on macOS, fits prior art, and leaves Cmd-N (new window) and Cmd-T (new tab — future #0015) untouched.

## Acceptance criteria

- `BattyCommands.swift` uses `[.command, .option]` instead of `[.command, .shift]` for the nine session-selection buttons.
- The "New Session" entry's shortcut moves from Cmd-Shift-Option-N to **Cmd-Option-N** (one fewer modifier; consistent with the family).
- `xcodebuild -scheme Batty -destination 'platform=macOS' build` passes.
- Verify in the running app: Cmd-Option-1, Cmd-Option-2, …, Cmd-Option-9 reach every session without macOS intercepting. Cmd-Option-N adds a session.
- PRD.md, Concepts.md, and issues/Issues.md are updated everywhere they currently say "Cmd-Shift-1..9 selects the Nth Session" → "Cmd-Option-1..9 selects the Nth Session". The grep:
  ```bash
  grep -rn "Cmd-Shift-[1-9]" PRD.md Concepts.md issues/
  ```
  should return zero hits after the fix.

## Notes

- This issue is a regression flagged by the user during M2 spot-check; not a bug we shipped knowingly. The original PRD chose Cmd-Shift-1..9 without auditing for system collisions.
- The Bell Feed (#0026) keeps Cmd-Shift-N — the letter N is distinct from Cmd-Option-N (different modifier set). No conflict.
- Cmd-Option-Number doesn't collide with any standard Mac app I know of. macOS Finder uses Cmd-Option-N for "New Smart Folder", but that's Finder-only — within Batty's menu definition our binding wins.
- If the user later prefers a different family (e.g. Cmd-Ctrl-1..9), this is a one-line change in `BattyCommands.swift`.

## Out of scope

- Changing Cmd-1..9 (tab selection — #0015), Cmd-D / Cmd-Shift-D (split — #0018), or any other shortcut. Only the session-selection family is affected by this issue.
- Auditing every other keybinding in the project for system collisions. If more conflicts surface, file follow-ups.

## Root cause

`#0012` chose Cmd-Shift-1..9 verbatim from the original PRD without auditing for system collisions. macOS Big Sur and later reserve Cmd-Shift-3 / -4 / -5 / -6 for screenshot capture; the user couldn't reach sessions 3-6 via the keyboard.

## Fix

`BattyKit/Sources/BattyKit/BattyCommands.swift`: switched the modifier on all nine session-selection buttons and the "New Session" button from `[.command, .shift]` (and `[.command, .shift, .option]` for New) to `[.command, .option]`. This matches iTerm2's tab/window-selection family.

Docs swept: every `Cmd-Shift-1..9` reference for session selection in `PRD.md`, `Concepts.md`, and `issues/Issues.md` was rewritten to `Cmd-Option-1..9`. The `Concepts.md` Session entry now also notes *why* we picked Cmd-Option, so future work doesn't try to revert.

`grep -rn "Cmd-Shift-[1-9]" PRD.md Concepts.md issues/` returns zero hits after the fix.

## Gotchas

- **`Cmd-Option-N` may collide with macOS Finder's "New Smart Folder"**. Inside Batty, our menu definition wins — there is no actual conflict at runtime. If a user is in Finder, that's outside our scope.
- **Visual verification** is the user's: Cmd-Option-1..9 reach every session, Cmd-Option-N adds a new session, screenshot keys (Cmd-Shift-3, -4, -5) still capture screenshots without interference. `xcodebuild build` passes; runtime confirmation is resolved-not-closed.
- **#0012 was already resolved** when this issue surfaced. Rather than re-open it, this issue layers a fix; the keybinding history is now Cmd-Shift-1..9 (#0012) → Cmd-Option-1..9 (#0042).
