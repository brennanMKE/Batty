# 0342 — Prove the `.inMemory` terminal backend end to end with a local in-process byte source

| | |
|---|---|
| **Status** | open |
| **Module** | GhosttyKit / TerminalSurface |
| **Platform** | macOS |
| **First seen** | 2026-08-21 |

## Description

Stand up one Batty Pane whose Terminal Session runs on
`TerminalSessionBackend.inMemory` instead of `.exec`, fed by a
**local, in-process** byte source — no network, no SSH, no tmux — and
demonstrate that all three directions of the byte boundary work:
output renders, keystrokes leave, and resizes leave.

This is the de-risking step for the [#0341](0341.md) umbrella and is
deliberately much smaller than every other child. Nothing about it is
remote. Its entire purpose is to answer "does a Pane driven by bytes
we supply behave like a normal Pane?" before any networking exists to
confuse the answer. If the answer is no, the umbrella's central
premise — that a remote Pane is an ordinary Pane with a different byte
source — is wrong, and that is much better to learn here than in
#0344.

**Not scheduled work.** Inherits #0341's status: this is staged for a
future major release, not queued.

### What already exists, and why this is smaller than it looks

`BattyKit/Tests/BattyKitTests/AtlasOwnershipExperimentTests.swift`
already constructs real, attached surfaces with

```swift
TerminalSurfaceOptions(
    backend: .inMemory(InMemoryTerminalSession(write: { _ in },
                                               resize: { _ in }))
)
```

with no PTY, and observes attachment succeeding. That harness was
written for #0287's atlas-ownership experiment and its handlers are
deliberately empty, so it proves surface *creation* on the in-memory
backend and nothing else. This issue starts from that known-good
construction and makes the handlers real.

Production code does not use the backend at all — grepping
`BattyKit/Sources` and `Batty/` for `inMemory`,
`InMemoryTerminalSession`, or `TerminalSessionBackend` returns
nothing. The seam it must reach is `tab.terminal.configuration` (a
`TerminalSurfaceOptions`), assigned to the view in
`TerminalHostStore.terminalView(for:windowID:)` and already mutated in
`TabRuntime.init`.

The exact public signatures of `InMemoryTerminalSession`,
`TerminalSurfaceOptions`, and `InMemoryTerminalViewport`, verified
against the pinned checkout, are listed in #0341's "Verified API
surface" section. Do not re-derive them from memory; that section also
records three behaviors that constrain this work.

## Expected behavior

A Pane can be created with an in-memory backend and a caller-supplied
byte source, and then behaves like any other Pane:

1. **Output renders.** Bytes handed to
   `InMemoryTerminalSession.receive(_:)` appear in the Pane, with
   escape sequences, colors, and the active Theme applied exactly as
   for a `.exec` Pane. A vt100 test pattern or `ls --color` capture
   replayed through `receive(_:)` looks identical to the real thing.
2. **Keystrokes egress.** Typing in the focused Pane invokes the
   `write:` handler with the corresponding bytes, including modifier
   chords and control characters. Nothing is swallowed and nothing is
   duplicated.
3. **Resizes egress.** Resizing the Pane — by dragging a Split
   divider, by resizing the Window, or by hiding the Sidebar — invokes
   the `resize:` handler with an `InMemoryTerminalViewport` carrying
   the new `columns`/`rows`, and the reported grid matches what a
   `.exec` Pane of the same geometry would report.
4. **Process exit.** `finish(exitCode:runtimeMilliseconds:)` produces
   the same Pane-level end-of-session behavior a real shell exit does.
5. **Nothing else regresses.** The Pane still does IME, selection,
   copy/paste, file drop, and Bell Feed events, because none of those
   live below the byte boundary.

The byte source itself is a stand-in — an echo loop, a canned
transcript replayed on a timer, a local `Process` pumped by hand —
chosen for testability, not for shipping. It is explicitly not a
feature; the choice of `.exec` vs `.inMemory` must not become a
user-visible option in this issue.

## Acceptance criteria

1. A Pane in a running Batty renders content that arrived through
   `receive(_:)` and never touched a PTY, with correct escape-sequence
   handling and the active Theme applied.
2. Keystrokes typed into that Pane are observed arriving at the
   `write:` handler, byte-for-byte, including at least one control
   character and one modifier chord.
3. Resizing that Pane is observed arriving at the `resize:` handler
   with correct `columns`/`rows`, driven by a real Split-divider drag
   rather than a programmatic size change.
4. `scripts/build.sh unit` passes, including new `BattyKitTests`
   coverage for the byte plumbing: output-in, input-out, resize-out,
   and the pre-attach drop described below.
5. The **pre-attach drop is handled, not merely observed.**
   `receive(_:)` guards on
   `InMemoryTerminalSurfaceAccess.enqueueWrite(_:)`, which returns
   `false` while the session has no surface — bytes arriving before
   the surface exists are dropped and logged, not buffered.
   `finish(exitCode:runtimeMilliseconds:)` has the same guard. This
   issue must either buffer on Batty's side until attachment or
   establish and document the ordering that makes the gap
   unreachable. #0344 and #0347 both depend on the answer, and a
   remote stream is far more likely to hit this window than a local
   one.
6. The backend choice is made **at Tab creation**, not flipped on a
   live Pane. `TerminalSurfaceCoordinator.configuration`'s `didSet`
   calls `rebuildIfReady()` whenever the new options are not
   `isEquivalent(to:)` the old, and `rebuildIfReady` begins by tearing
   the surface down — so flipping a live Pane's backend destroys its
   surface and its scrollback. Whatever plumbing this issue adds must
   make that hard to do by accident.
7. `docs/terminal-pane-requirements.md` §6's manual checklist is run
   against the in-memory Pane — pointer input, keyboard, IME, file
   drop, text drop — and the result recorded. The bytes changing
   source does not exempt the Pane from those guarantees; #0143 is the
   recorded example of what skipping this costs.

## Notes

- No UI affordance ships here. If a way to create such a Pane is
  needed for manual verification, keep it behind a debug/test-only
  path rather than a menu item.
- `readViewportText()` reads the visible rows only and explicitly
  ignores scrollback. It is useful for asserting rendered output in
  tests; it is not a history mechanism (see #0347).
- The umbrella's Hard problem 2 notes that `SurfaceRegistry` has no
  production callers and `TerminalHostStore` is the as-built registry.
  This issue does not need to resolve that, but whoever works it will
  be the first to see it up close.
