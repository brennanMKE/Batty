# 0516 — `allPids()` can silently return a truncated process list, so follow-by-name loses a running process

| | |
|---|---|
| **Status** | open |
| **Module** | Process Status pane |
| **Platform** | macOS |
| **First seen** | 2026-10-14 |

## Description

`ProcessInspector.allPids()` sizes its buffer from one `proc_listallpids(nil, 0)` probe plus 64 slots of headroom, then fills it with a second call. If the host starts more than 64 processes between the two calls, the fill saturates the buffer and `proc_listallpids` returns exactly the capacity — there is no error, no `errno`, and nothing distinguishes "this is the whole list" from "this is as much as fit." The tail of the pid list is dropped.

Every caller inherits it: `firstSameUserProcess(named:)` (Mode C's per-tick resolution), `allSameUserProcesses()` (the "Choose Process…" picker), and `children(ofPid:)` (the child-processes disclosure). A truncated list makes a running process look like it does not exist.

Found while verifying the #0507–#0513 branch, not reported by either external review.

## Steps to reproduce

Needs a busy machine — the process table has to grow by more than 64 between two adjacent syscalls. It reproduced once in roughly ten consecutive `./build.sh unit` runs on this Mac with back-to-back `xcodebuild` invocations churning compiler and test-runner processes.

## Expected behavior

`allPids()` returns every pid, or nothing. Two adjacent calls never disagree about a process that was alive across both.

## Actual behavior

`ProcessFollowByNameTests.theRealEnumeratorPrefersTheLongestRunningProcessOfAName()` is the witness. It spawns two copies of a uniquely named `sleep`, held alive for 300 s by `ChildProcessFixture`, then calls two enumerators back to back:

```
Expectation failed: ProcessInspector.firstSameUserProcess(named: name) == listed.first?.id
ProcessInspector.firstSameUserProcess(named: name) → nil
listed.first?.id → 2505
```

`allSameUserProcesses()` saw pid 2505. `firstSameUserProcess(named:)`, microseconds later and against the same live child, did not. Both go through `allPids()`; one of them got a truncated list. (`Test-Batty (Beta)-2026.10.14_17-52-06--0700.xcresult`, `ProcessFollowByNameTests.swift:675`.)

This reads as a flaky test. It is not — the test is correct and the code under it is wrong.

## Notes

- `BattyKit/Sources/BattyKit/Runtime/ProcessInspector.swift:441-466`. The existing comment there is about a different, already-fixed bug (`proc_listallpids` returns a pid count, not a byte count); the saturation case is untreated.
- Fix: treat `actualCount == capacity` as "possibly truncated" and retry with a doubled buffer, bounded, logging if it never settles. A fixed headroom cannot be made large enough — it is a race, not a sizing error.
- User impact is a Mode C pane reporting Waiting for a process that is running, and a "Choose Process…" picker missing entries, both transient and both on exactly the busy machine where a process monitor is most wanted.
- **2026-11-05, reconciled with #0565.** The saturation retry this issue asked for landed in `86c022fc` (2026-10-14), with `ProcessInspectorAllPidsTests` covering it. That commit didn't go through the review pipeline, so this file never got resolution sections and is still `open`. The witness test failed again on 2026-11-05 with that fix in place (#0565). So the claim above that "the test is correct and the code under it is wrong" was only half right. The test compared two separate live walks, and that comparison can fail for reasons truncation doesn't explain (both children missing at once). The remaining work belongs to #0565:
  - the "or nothing" half of Expected behavior: a failed walk becomes an explicit, logged failed result instead of a silent `[]`, so Mode C treats it as unknown and keeps its state;
  - the witness test is rewritten to make one walk against the pids it owns, with the ordering proved by pure tests.

  Nothing else in this issue is left once #0565 lands. Status stays `open`, and closing it is the user's call.
