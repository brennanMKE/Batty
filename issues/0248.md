## Description

The multi-window refactor left a block of per-window forwarding shims in `AppStateStore` (lines ~192–289) that hard-code `windows[0]` — `sessions`, `selectedSessionID`, `addSession`, `removeSession`, `renameSession`, `closeTab`, `selectSession`, and ~20 more. Any caller still using these shims silently operates on the *first* window regardless of which window is key, which is a regression source: layout/Open Quickly/paste (#0244) and quit/bell (#0239) were already fixed piecemeal, and session auto-naming (#0231/#0232) is currently broken in every window but the first for the same reason. This issue is a systematic audit: enumerate every `windows[0]` site and every consumer of the shims, and route each to the key window (or document why `windows[0]` is genuinely correct).

## Resolution notes

> 🟢 Resolved 2026-06-17 — Audited all 43 `windows[0]` sites: migrated 22 behavioral action/handler shims to resolve the owning or key window, fixed the auto-naming regression, and left the view-read shims at `windows[0]` deliberately (with comments) to preserve the SwiftUI observation contract.

## Root cause

The multi-window refactor (#0234 children) turned `AppStateStore` from a single-window singleton into a `windows: [WindowRuntime]` owner, but kept a block of forwarding shims pointing at `windows[0]` for backward compatibility. Any caller that wasn't individually migrated then operated on the first window regardless of which was key. #0239 and #0244 fixed symptoms one at a time; `handleWorkingDirectoryChange` (auto-naming) and `applyAppearanceToAllSurfaces` (settings) were the next two unmigrated consumers — naming was dead outside the first window, and appearance changes only reached the first window's surfaces.

## Fix

Audited every `windows[0]` occurrence in `BattyKit/Sources/` and `Batty/` and classified each as a view-read path, an action/event path, or genuinely first-window-correct.

- **Auto-naming handlers** now iterate across all windows by tab/session ownership: `handleWorkingDirectoryChange` loops every window's sessions to find the anchor tab; `applySuggestedName` resolves the session via `windows.lazy.flatMap(\.sessions)`. Single-pane / `titleOverride` / default-title gating preserved exactly.
- **Mutating/ID-keyed shims** (`removeSession`, `renameSession`, `clearSessionName`, `duplicateSession`, `jumpToTab`, `closeTab`, `requestCloseTab`, `focusPane`, `requestCloseOtherTabs`) resolve the owning window via new helpers (`windowOwning(sessionID:)`, `WindowRuntime.locate(tabID:)`) that return optionals and no-op when not found.
- **Key-window-scoped actions** (`addSession`, `moveSessions`, `selectSession`, `closeFocusedTab`, `requestCloseFocusedTab`, `confirmPendingClose`, `cancelPendingClose`, `markActiveTabSeen`) use `keyWindowRuntime() ?? windows[0]` (the fallback keeps unit-test/single-window behavior identical).
- **`applyAppearanceToAllSurfaces`** (settings font/cursor/keybinds) now iterates `windows.flatMap { $0.sessions }`, mirroring the already-fixed `applyThemeToAllSurfaces` — found by review, was the one consumer both the round-1 sweep missed.
- **View-read shims** (`sessions`, `selectedSessionID`, `selectedSession`, `pendingCloseRequest`) were left at `windows[0]` on purpose, with comments: `keyWindowRuntime()` reads `NSApp.keyWindow`, which is not `@Observable`, so a view depending on it would not re-invalidate on key-window change. View code resolves its window from the SwiftUI environment instead; these shims are now only read from tests / `UITestDriver` (single-window-safe).
- `onAllSessionsClosed` left at `windows[0]` (app-quit hook, per #0239 design); the two `ThemePreference` `themeChrome` decisions that read the first window's selected-session keep `windows[0]` with a one-line justification (chrome is a single app-wide object).

## Gotchas

- The read shims (`sessions`, `selectedSessionID`, `selectedSession`) must stay `windows[0]`, not `keyWindowRuntime()`: the latter reads `NSApp.keyWindow` (not `@Observable`), so a view depending on it would render stale. New view code must resolve its window from the `windowID` environment, never these shims. Action/event code is where key-window resolution belongs.
- `keyWindowRuntime()` returns nil in unit-test context (no NSApp key window), so the cross-window auto-naming fix is written to iterate windows by tab ownership rather than depend on `keyWindowRuntime()` — that's what makes it unit-testable.

## Long Description

### Root pattern

The correct resolution already exists: `keyWindowRuntime()` returns the `WindowRuntime` for `NSApp.keyWindow`, and the established idiom at migrated call sites is `store.keyWindowRuntime() ?? store.windows[0]` (the fallback covers unit-test/preview contexts where no window is key). The regression is that the `AppStateStore` forwarding shims were left pointing at `windows[0]` as a backward-compat convenience, so un-migrated callers grab the first window by accident rather than by intent.

This has already produced regressions fixed one at a time:

- **#0239** — quit confirmation and bell-feed routing widened beyond `windows[0]`.
- **#0244** — layout picker, Open Quickly, and paste were acting on `windows[0]` instead of the key window.
- **This issue's trigger** — `handleWorkingDirectoryChange(forTabID:)` iterates the `sessions` shim (→ `windows[0].sessions`), so CWD-driven auto-naming (project-file derivation *and* the Foundation Models fallback) never fires for sessions in any window other than the first. This is the concrete bug that surfaced the broader problem; fixing it is part of this audit, not a separate ticket.

The piecemeal approach is the problem — each fix addresses one symptom while the shims keep handing out `windows[0]` to the next un-audited caller. A single sweep is needed.

### Scope

1. **Enumerate every `windows[0]` occurrence** in `BattyKit/Sources/` and `Batty/` (currently ~43, many in comments). For each, classify:
   - **Genuinely correct** — e.g. internal forwarding that is about to be removed, or a context where the first window is definitionally right. Document why.
   - **Should be the key window** — migrate to `keyWindowRuntime() ?? windows[0]`, or to an explicit window passed by the caller.
2. **Audit every consumer of the forwarding shims** (`sessions`, `selectedSessionID`, `selectedSession`, `pendingCloseRequest`, `addSession`, `removeSession`, `renameSession`, `clearSessionName`, `duplicateSession`, `moveSessions`, `selectSession`, `closeTab`, `closeFocusedTab`, `requestCloseTab`, `requestCloseFocusedTab`, `requestCloseOtherTabs`, `confirmPendingClose`, `cancelPendingClose`, `focusPane`, `jumpToTab`, `onAllSessionsClosed`). A shim caller that runs in response to user action in a window is almost always wrong to target `windows[0]`.
3. **Fix `handleWorkingDirectoryChange`** (and check `applySuggestedName`, which resolves the session via `sessions.first(...)` — confirm it finds sessions across all windows, not just `windows[0]`): the cwd-change handler must locate the anchor tab across every window's sessions, and apply naming to whichever window owns that tab.
4. **Prefer eliminating the ambiguity at the source.** Rather than leave shims that quietly mean "first window," consider removing them (forcing callers to name a window) or redefining them to resolve against the key window — whichever keeps the call sites honest. Removing them turns every remaining bug of this class into a compile error instead of a silent runtime regression. Weigh against unit-test ergonomics (tests rely on the `windows[0]` fallback when no window is key) — the `keyWindowRuntime() ?? windows[0]` shape preserves that.

### Constraints

- Follow `docs/multi-window-design.md` (the `WindowRuntime` model and key-window resolution) and `docs/swiftui-observation-rules.md` (several of these paths run from focus/selection/observed-state writes — window-key changes happen inside AppKit machinery, so route writes through event-origin code, never Task-hop).
- This is a behavior-preserving correctness sweep for single-window use (where `keyWindowRuntime() ?? windows[0]` and `windows[0]` coincide) and a bug fix for multi-window use. Single-window behavior must not change.
- Don't expand scope into new multi-window features — just make existing operations target the correct window.

## Steps to reproduce

1. Open a second window (Shift-Cmd-N).
2. In that window, `cd` a single-pane session into a project folder (or rename/close tabs / apply session operations).
3. Observe that auto-naming doesn't fire (and check whether other session/tab operations affect the first window instead of the active one).

## Expected behavior

Session, tab, pane, selection, and auto-naming operations act on the window the user is interacting with. `windows[0]` is used only where the first window is definitionally correct, and that is documented at each such site.

## Actual behavior

The `AppStateStore` forwarding shims hard-code `windows[0]`, so any un-migrated caller operates on the first window regardless of which is key. Auto-naming is dead outside the first window; other operations are suspect until audited.
