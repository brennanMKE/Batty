## Description

The user's request, verbatim: "We need the skill to be installable for any agent whether it is Claude, Codex, OpenCode or another type. How do we do that?"

[#0403](0403.md) shipped `.claude/skills/batty-cli/SKILL.md` — 265 lines of sequencing knowledge, `name`/`description` YAML frontmatter (`SKILL.md:1-4`), a version pin (`:8`), and a non-destructive self-refresh recipe (`:88-109`). Every distribution surface it built is Claude-shaped:

- The repo location is `.claude/skills/batty-cli`, a constant at `BattyKit/Sources/batty/CapabilitiesCommand.swift:245`.
- The plain-text `capabilities` output announces it as a "Claude Code skill" (`CapabilitiesCommand.swift:280`) and its install recipe stages into `~/.claude/skills/batty-cli` and nowhere else (`CapabilitiesCommand.swift:297-305`).
- The skill's own refresh snippet targets `~/.claude/skills` literally (`SKILL.md:98-106`).
- The drift gate reads exactly one path: `AgentSkillFlagDriftTests.skillMarkdown()` resolves `.claude/skills/batty-cli/SKILL.md` from `#filePath` (`BattyKit/Tests/BattyKitTests/AgentSkillFlagDriftTests.swift:19-28`).

But the skill's *content* is portable Markdown teaching a host-agnostic CLI — nothing in its 265 lines is Claude-specific. What varies per host is only: where an installed copy lives, what frontmatter the host reads, whether a project-scoped copy auto-loads, and how the host decides the skill is relevant. This issue is about making one authored skill reach all four hosts **without hand-maintaining four copies of the same prose** — which this repo's own history says would be the failure mode (see the AGENTS.md evidence below).

Two conclusions fall out:

1. **For the three skill-reading hosts, the content problem is already solved** — the same directory-with-`SKILL.md`, same two frontmatter fields, works byte-identically in all three (proved below by `quest`). Only the *placement* differs. Both `quest` and `batty-cli` use exactly `name` + `description` and nothing else — the lowest common denominator all three hosts accept. The first host-specific frontmatter key anyone adds is the first forced divergence; don't add one until a host requires it.
2. **Codex is the genuinely hard case**, and `AGENTS.md` does not solve it. `AGENTS.md` is emerging as a cross-tool convention (OpenCode reads it too), but it serves a different purpose: repo-wide, always-loaded guidance for agents working *in this repo*. The skill's audience is the opposite — an agent in some unrelated project's Pane (`issues/0403.md`, Description). This repo's `AGENTS.md` never leaves this repo, so it cannot carry the skill to that audience; at best a user's *global* instruction file (if Codex supports one) can carry a condensed pointer ("run `batty capabilities --json` first; sequencing notes at <tagged URL>"). `AGENTS.md` is the right vendor-neutral anchor for *in-repo* guidance, and the wrong vehicle for a task-triggered, globally-installed skill — the two are complementary, not substitutes.

## The repo's own multi-host precedents — the evidence to design from

**The `quest` skill is a working three-host install of one canonical skill, with zero copies.** `git ls-files -s .cursor` shows `.cursor/skills/quest` tracked as a symlink (mode `120000`) whose blob content is the absolute path `/Users/brennan/Developer/Skills/QuestSkill/quest`. On this machine, `~/.claude/skills/quest` and `~/.config/opencode/skills/quest` are symlinks to the *same* canonical folder. The mechanism is that skill repo's `install.sh`: "'Installing' links that folder into each tool's skills directory (symlink, so edits are live)" — it detects Claude Code (`~/.claude/skills`) and OpenCode (`~/.config/opencode/skills`) globally, covers Cursor per-project via `--project DIR/.cursor/skills`, backs up any non-symlink it replaces, and links. So quest's answer to duplication is: **one canonical folder, N symlinks, no generator, no divergence possible** — and it demonstrates that one `SKILL.md` (frontmatter: `name`, `description` — the same two fields as `batty-cli`) satisfies all three hosts unmodified, with host-specific extras (an OpenCode plugin under `plugin/`, a slash-command stub under `command/`) riding along in the same folder harmlessly.

Its one structural flaw is also instructive: the tracked `.cursor/skills/quest` symlink stores a machine-specific absolute path — on any other clone of Batty it dangles. Symlinks work for live-checkout development; they are the wrong shape for Batty's actual audience, which installs from a tagged GitHub fetch (`issues/0403.md`, "Implementation decisions") and has no canonical checkout to point at.

**`AGENTS.md` is the cautionary precedent: a hand-copied near-duplicate of `CLAUDE.md`, already badly drifted.** 180 lines vs 192; `diff` shows 58 changed lines. The header parallel is exact (`CLAUDE.md:5` "binding guidance for Claude sessions" / `AGENTS.md:5` "binding guidance for Codex sessions"), but:

- `AGENTS.md:73` still says "`./build.sh` is a thin wrapper... Direct `xcodebuild` calls work too; the wrapper is a convenience. The actual scheme is `Batty (Prod)`" — flatly contradicting `CLAUDE.md`'s current binding rule ("**Never invoke `xcodebuild` directly for a build you intend to trust**") *and* contradicting `AGENTS.md`'s own line 77 four lines later ("defaults to the `Batty (Beta)` scheme"). The file is internally inconsistent because it was partially updated.
- `AGENTS.md` is missing `CLAUDE.md`'s release-build section entirely (the #0391 `-O`-only compiler-crash lesson).
- A mechanical Claude→Codex substitution produced fabricated model ids: `AGENTS.md:169` tells Codex to pin its filer to "`Codex-fable-5`" (also `Codex-sonnet-5`, `Codex-opus-4-8`) — ids that do not exist.

That is the four-copy future in miniature, on a file pair only *two* copies wide with an identical purpose. And #0403 already recorded the same lesson intra-Claude: the skill inherited `docs/batty-cli-agent-workflows.md`'s `--tab`-takes-a-Pane-id bug *verbatim* (`issues/0403.md`, round-1 B2 — "'the doc wins on disagreement' propagates errors as faithfully as truth"). Duplicated prose drifts; duplicated *and* mechanically-transformed prose drifts wrong.

**`.opencode/quest.json` is the counter-example that not everything multi-host is a skill:** it is a JSON state file (an active quest instance) consumed by an OpenCode *plugin* (`.opencode/package.json` pins `@opencode-ai/plugin` 1.18.18; only `quest.json` is tracked, the rest gitignored). Different job, different shape — no bearing on skill placement except as proof OpenCode is live on this machine.

## Expected behavior

1. **Exactly one authored copy of the skill exists in this repo.** Whatever lands, no host's variant is hand-maintained prose — the AGENTS.md drift above is the named anti-goal. If the chosen shape ever puts two real copies of skill bytes in the repo, byte-divergence between them must itself be test-red.
2. **An agent (or its human) on Claude Code, Cursor, or OpenCode can install the skill with one discoverable action**, and the action is discoverable the same way today's is — from `capabilities`' plain-text output and/or the docs. Codex gets the best available documented channel (likely an instruction-file pointer at the tagged skill URL), with the limitation stated honestly rather than papered over.
3. **Every shipped copy stays under the drift gate.** `AgentSkillFlagDriftTests.everyFlagTheSkillShowsExistsOnItsVerbInCapabilities` (`AgentSkillFlagDriftTests.swift:187`) must cover each real `SKILL.md` the repo ships, not just the `.claude/` one — see "Keeping the drift gate" below.
4. **The refresh path refreshes what is actually installed.** A copy in OpenCode's skills dir must not follow instructions that refresh only `~/.claude/skills` and leave itself stale (`SKILL.md:98-106` does exactly that today, for any non-Claude install).
5. **The #0384 pins hold**: `capabilities --json` stdout stays pure JSON; any grown install text is plain-text-path only; JSON additions (e.g. a structured list of install destinations) are additive.
6. **The #0403 version coupling holds per installed copy**: authored-against version, minimum-app-version pin, refresh-from-tag `v<cliVersion>`, warn-never-hard-fail.

## Candidate approaches (deliberately not decided here)

Like [#0332](0332.md) and [#0402](0402.md), this files the property, not the mechanism. What each costs:

1. **One canonical folder + symlinks (the quest model).** Repo keeps `.claude/skills/batty-cli/` as the real files; `.cursor/skills/batty-cli` (and an OpenCode project location, if one exists) become **relative** symlinks into it — relative, not absolute, so they survive clones, fixing quest's one flaw. Externally, an install script symlinks or copies per host. Pro: zero duplication by construction; the drift gate's single path keeps covering everything, since every link resolves to the same file. Con: git-tracked symlinks are unusual on macOS toolchains and each host's willingness to follow them needs live verification (quest proves Claude Code and Cursor-in-this-repo tolerate them on this machine; a fresh clone and each host's sandboxing behavior are unverified); and the *external* install can't be a symlink at all for the tag-fetch audience — a `git clone` of `v<version>` yields files to copy, not a checkout to point at.
2. **One canonical copy in-repo + install-time fan-out (extend #0403's recipe into a loop).** The repo layout doesn't change; the install/refresh recipe detects hosts the way QuestSkill's `install.sh` does (`~/.claude` → `~/.claude/skills`, OpenCode config dir → its skills dir, `--project`-style opt-in for `.cursor/skills`) and copies the same staged bytes into each, with #0403's stage-verify-swap discipline (`CapabilitiesCommand.swift:297-305`) applied per destination. Pro: no generator, no new repo copies, drift gate untouched; content portability is already proved by quest, so the copies are byte-identical at install time. Con: N installed copies age independently — refresh must enumerate and refresh *all* detected copies or the skew multiplies (#0383's harm model, times N); the recipe grows well past what a plain-text trailer comfortably prints (see below); and every recipe change now touches the two hand-synced snippet copies plus their pinning tests (`AgentSkillFlagDriftTests.swift:170`, `CapabilitiesCommandTests.skillInstallLinesForAKnownVersionCloneTheMatchingTag`).
3. **Vendor-neutral canonical home (e.g. `skills/batty-cli/`) with per-host stubs/symlinks including `.claude/`.** Philosophically cleanest — no host owns the source of truth. Con, and it is expensive: the current path is load-bearing in shipped artifacts — the constant at `CapabilitiesCommand.swift:245`, the drift test's hardcoded resolution (`AgentSkillFlagDriftTests.swift:19-28`), the refresh snippets in both `SKILL.md` and the CLI, and the exact-array tests that pin them — and #0403's tag mechanism means every already-tagged release permanently prints the old path. A move is a compatibility event, not a rename.
4. **Generated per-host copies from one source.** Strictly more machinery than the evidence demands: quest demonstrates the three skill-reading hosts need *identical* bytes, so there is nothing for a generator to vary until some host's frontmatter forces divergence. Park this until that day; a generator whose transform is the identity function is just a copy with extra failure modes.
5. **Ship only the Claude copy and document manual install elsewhere (status quo plus a docs page).** Cheapest; honest; strictly worse discoverability for exactly the audience #0403 was filed to reach. Acceptable only as an explicit interim.

**What the existing evidence favors:** quest establishes that the content needs no per-host variation, which eliminates 4 and reduces the whole problem to placement + refresh. The workable composite is 2 for external installs (copies are the only shape a tag-fetch supports) with 1's *relative*-symlink trick optionally covering in-repo project scope for Cursor/OpenCode agents working on Batty itself. Decide during implementation, with the trade-offs written down.

## Keeping the drift gate across N copies

The gate is the property that stops any shipped copy going stale against the CLI surface: `everyFlagTheSkillShowsExistsOnItsVerbInCapabilities` parses `SKILL.md` and asserts every `batty <verb> --flag` it shows against the live `capabilities --json` schema (`AgentSkillFlagDriftTests.swift:187`; companion snippet/recipe pins at `:170` and `:214`). Today it reads one hardcoded path (`:19-28`).

- Under approaches 1/2/3 the repo still holds **one** real `SKILL.md`, so the gate needs no widening — symlinked stubs resolve to the gated file for free.
- If any approach ever puts a second real copy in the repo, the cheap and sufficient extension is: parameterize `skillMarkdown()` over an enumerated list of shipped copies (or a glob over the known host dirs), run the same assertions per copy, **and add a byte-equality assertion across copies** so divergence itself — not just flag drift — turns `./build.sh unit` red. That last assertion is what the CLAUDE.md/AGENTS.md pair never had.
- Installed copies under `$HOME` are outside any unit test's reach by design — their freshness is the version-check's job (#0403's bootstrap), not the gate's. The gate guarantees what *ships*; the bootstrap guards what's *installed*.

## Install and refresh across hosts

`capabilities`' plain-text trailer currently prints one Claude-shaped recipe (`CapabilitiesCommand.swift:277-309`) — the one that took two review rounds to make non-destructive (#0403 B1, R2-B2: stage to `.new`, verify `SKILL.md` exists in the stage, swap, never leave the user with nothing). Options for going multi-host, none decided here:

- **Detect the host and print its recipe.** The CLI cannot reliably know which agent is reading its output — env sniffing (`CLAUDECODE`, Cursor/OpenCode equivalents) is fragile and wrong for the human-in-a-plain-terminal case. Weak.
- **Print all recipes.** The single recipe is already ~17 lines; four host variants of a stage-verify-swap script in a plain-text trailer is unreadable. Weak.
- **Print one recipe parameterized by destination** (the script already computes everything but the target dir) **plus a short host→destination table.** Moderate cost, keeps the trailer one screen.
- **Point at one canonical installer** — a documented page or a checked-in install script fetched from the same tag (`v<cliVersion>`), which does host detection properly the way QuestSkill's `install.sh` already demonstrates (detect → back up → place → report per target). Most capable; note `scripts/` is a restricted area, so where such a script lives (repo `scripts/`, the skill folder itself, or docs) is decided with the user.

Whatever is chosen: the stdout-purity pin stands — `capabilities --json` stays pure JSON (#0384; verified byte-for-byte in #0403's verification), so all of this is plain-text-path or additive-JSON only. And the refresh half must refresh **every detected installed copy**, not the Claude one — that correction applies to the skill's own snippet (`SKILL.md:88-109`) and the CLI's printed copy identically, and both are pinned by exact-text tests that will need the same edit.

## Version coupling per host

#0403's mechanism — authored-against version in the skill body (`SKILL.md:8`), minimum-compatible-app pin, refresh from tagged release `v<cliVersion>`, compare against `cliVersion`/`.status.appVersion` at bootstrap, warn-never-hard-fail — is **content, not host convention**. It survives unchanged on any host that receives the `SKILL.md` body intact: nothing in it references Claude, and the tag URL derives from the CLI's own reported version. Two places it does *not* survive:

1. **The refresh snippet's destination** (`SKILL.md:98-106`): a copy living in `~/.config/opencode/skills/batty-cli` that follows its own instructions refreshes `~/.claude/skills/batty-cli` and leaves itself stale — the #0383 skew, self-inflicted. The snippet must become destination-aware (refresh in place, or refresh all detected hosts).
2. **Hosts that can't carry the skill at all** (Codex today): a pointer in an instruction file carries no bootstrap procedure an agent will reliably execute, so the version handshake degrades to "the pointer says run `capabilities --json` first." State that ceiling honestly in whatever the Codex channel turns out to be.

### What was built

- **`.claude/skills/batty-cli/install.sh`** (new, executable, lives in the skill folder per constraint #2 — not `scripts/`). Detects and copies (never symlinks — the tag-fetch audience has no canonical checkout to link back to) into: `~/.claude/skills/batty-cli` (Claude Code), `~/.config/opencode/skills/batty-cli` (OpenCode, XDG-aware), `~/.cursor/skills/batty-cli` (Cursor, if `~/.cursor` exists or `cursor` is on PATH), `~/.codex/skills/batty-cli` and `~/.agents/skills/batty-cli` (Codex, both conventions), plus `--project DIR` opt-in for `DIR/.claude/skills`, `DIR/.cursor/skills`, `DIR/.agents/skills`. Every destination is staged to a `.new` sibling, verified to contain `SKILL.md`, then swapped (`mv`) — #0403's stage-verify-swap discipline, applied per destination instead of to one hardcoded path. If an existing destination is already byte-identical to what would be staged, nothing is touched at all (a `diff -rq` short-circuit added in round 3 — see below). Otherwise any pre-existing install — symlink or not — is preserved by moving it to a backup path *outside* the scanned skills root (round 3 fixed this: see B1/B2 below). A destination that already resolves (via `pwd -P`) to the script's own directory is skipped, so running `install.sh --project .` from inside this repo can't remove-then-recreate the file it's currently executing from. Supports `--dry-run` (prints what would happen, touches nothing) and reports per-target (installed / backed-up-and-installed / up-to-date-skipped / canonical-skipped / stage-incomplete).
- **`CapabilitiesCommand.skillInstallLines`** rewritten: instead of inlining the whole stage-verify-swap recipe against one hardcoded `~/.claude/skills` path, it now clones the tagged release and hands off to that clone's own `install.sh` (`"$tmp/.claude/skills/batty-cli/install.sh"`). This is *shorter* than the old recipe (13 printed lines vs. ~20), because the per-destination discipline moved into the script instead of being reprinted inline. Two failure points are still checked before the hand-off: the `git clone` can fail (network / bad tag), and a tag can predate the installer entirely (any tag before #0404) — both leave existing installs untouched, matching what `install.sh` itself guarantees for the destinations it manages. The "Claude Code skill" wording at the old line 280 is now "Portable skill teaching agents to drive this CLI — installs for Claude Code, Cursor, OpenCode, and Codex."
- **`SKILL.md`'s "Refreshing this skill" section** rewritten to match: it now clones and hands off to `install.sh` instead of inlining `~/.claude/skills`-only shell, so a copy living in, say, OpenCode's directory refreshes every detected host (including itself) rather than only Claude's — closing the exact #0383-shaped self-inflicted skew the issue named at `SKILL.md:98-106`.
- **`docs/batty-cli-agent-workflows.md`**'s pointer at the skill no longer says "Claude Code skill"; it now names `install.sh` and states plainly that living under `.claude/` is the skill's original authoring location, not a scope restriction.
- **`capabilities` plain-text trailer**: chose **"point at one canonical installer"** (the issue's own higher-capability option) over "one recipe parameterized by destination plus a host→destination table." Where a claim mattered enough to hinge a design decision on (the `.agents/skills` cross-tool convention, specifically), it was cross-checked against a second independent source (Cursor's own docs corroborate Codex's from the other direction: Cursor lists `~/.codex/skills`/`.codex/skills` as paths *it* reads for compatibility, which is only sensible if Codex itself already had *some* directory-based skill convention by the time Cursor wrote that).
- **`git merge-tree --write-tree main issue/0404`**: run from the worktree against the two refs; reported a clean merge tree with no conflict markers. Not re-verified after every subsequent edit in this session — re-run before any merge decision.
- **The release-time preflight hook** described in #0403's Notes (failing a release when the CLI surface changes without a matching skill/doc update) remains undescribed-but-not-built, unchanged from #0403 — still out of scope here since `scripts/` is restricted and this issue didn't touch it either.

- **That the `batty-cli-skill-backups` directory is invisible to every host is reasoned, not observed.** It is placed one level above each scan root, so a `<skills-root>/*/SKILL.md` scan cannot reach it, and three edit+refresh cycles across all eight destinations left exactly one `SKILL.md` per scan root. But no host was actually asked to scan a tree containing one — in particular, Cursor's documented *recursive* project scan for `.cursor/skills` / `.agents/skills` was never exercised against a repo holding `$PROJECT_DIR/.claude/batty-cli-skill-backups/`.
- **`--project DIR` writes `DIR/.claude/`, `DIR/.cursor/`, and `DIR/.agents/` into a user's repo**, and on a second run adds a `batty-cli-skill-backups/` directory beside each. Whether that is acceptable clutter in a tracked `.claude/` directory is a judgement no test makes for the user.
- **The text-based test pins cannot see control flow.** `AgentSkillInstallScriptTests` greps `install.sh` from Swift, so "textually present" does not mean "reachable". Three mutations constructed during review survive every text pin — reversing the then/else so backup+swap run only when staging *failed*, an early `return 0` at the top of `install_into`, and wrapping every global block in `if false` — but all three are caught incidentally by `partialDestinationFailureExitsNonZero`, which executes the script for real and reads a file the baseline install must have produced. The gap is narrower than that but still real: [#0406](0406.md) demonstrates a one-line mutation (misrouting `backup=` back into the scanned skills root) that passes every text pin *and* the behavioural test, while resurrecting the #0383 harm on the routine refresh path. Extending the behavioural harness is owed there.
