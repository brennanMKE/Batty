## Description

A field crash of the release build: **Batty 1.1.0 (20260805)**, `/Applications/Batty.app`, `co.sstools.Batty`, pid 51733, crashed **~3.9 seconds after launch** (launch 2026-08-06 23:38:51.3428, crash 23:38:55.2859) on **Thread 0, the main thread**, with `Exception Type: EXC_BREAKPOINT (SIGTRAP)`, `esr: 0xf2000001 (Breakpoint) brk 1`.

**This is a Swift runtime trap, not a memory-protection fault** — a `fatalError`, failed `precondition`/`assert`, force-unwrap of nil, out-of-bounds index, or similar deliberate `brk` instruction in Batty's own code path. That makes it far more tractable than a wild pointer: some specific statement decided to trap.

The stack (read bottom-up) shows the shape of the failure: the user closed a window, Batty's close observer synchronously called `NSApplication.terminate:`, AppKit's terminate path spun the runloop mid-teardown, SwiftUI flushed a pending transaction and re-evaluated the menu-bar `Commands` body against half-torn-down state, and something in that body trapped.

Hardware/OS: **`Mac16,12`, macOS `26.4.1 (25E253)`** — note this is a *different machine* from the Mac mini used for development (`Mac16,11`, macOS 26.5.1); possibly the MacBook Air. The ~4-second process lifetime is itself a clue: state restoration or an immediate window-close is in play.

## Mechanism

Three tiers of certainty here. Keep them separate.

**What the crash report establishes:** a Batty notification observer on the window-close path (frames 29–32) synchronously invoked `-[NSApplication terminate:]` (frame 28); AppKit's persistent-state teardown spun the runloop (frame 25); SwiftUI flushed a transaction and re-evaluated a `Commands` body (frames 5–14); the trap fired inside Batty code called from `CommandGroup.init(after:addition:)` (frames 0–2).

**What was verified in the current source tree** (matches the stack shape, though the crashed binary is 20260805 and cannot be symbolicated — see Notes):

- `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:161` — `NSApp.terminate(nil)` inside `private func terminateIfLastContentWindowGone()`, reached from `public func removeWindow(id:)` (`:138`), whose doc comment says "Called from the window-close teardown path". That is exactly frames 29–32.
- The re-evaluated commands body is `BattyKit/Sources/BattyKit/Commands/BattyCommands.swift`. It has exactly two `CommandGroup(after:)` sites: `:65` (`.sidebar`) and `:176` (`.windowArrangement`). Frame 1 is `CommandGroup.init(after:addition:)`, so one of these two closures is the frame-2 caller; frame 0 is code inside it.

**Hypothesis (leading, unproven):** the `Commands` body is being evaluated against half-torn-down app state — mid-`terminate`, after the last window's teardown has started — and some value it reads is in a state that never occurs during normal evaluation, tripping a trap (force-unwrap, precondition, or index). Which exact statement traps is unknown without the dSYM.

**Register hint — a lead to check first, explicitly unconfirmed:** the crashed thread state has `x25 = "type metadata for KeyboardShortcut"` and `x28 = _swiftEmptyArrayStorage`. The `CommandGroup(after: .sidebar)` site at `BattyCommands.swift:65-75` applies `.keyboardShortcut(shortcuts.keyboardShortcut(for: .toggleSidebar))`. However, that path was traced in the current source and looks nil-safe at every step: `ShortcutsStore.keyboardShortcut(for:)` (`ShortcutsStore.swift:65`) → `binding(for:)` (`:61`) uses `bindings[action] ?? action.defaultBinding`, and `ShortcutBinding.keyboardShortcut` (`ShortcutBinding.swift:71-78`) uses `key.first ?? " "`. So the register contents may be incidental — `KeyboardShortcut` metadata is plausibly live in registers during any commands-body evaluation. Do not present this as the cause; check it first, then move on.

## Expected behavior

Closing the last content window quits the app cleanly. Terminate is initiated from a stable point in the runloop, not synchronously from inside an `NSWindow` close-notification observer, so SwiftUI never re-evaluates the `Commands` body against mid-teardown state.

## Actual behavior

`NSApp.terminate(nil)` runs synchronously inside the window-close observer; AppKit's terminate path re-enters the runloop; SwiftUI re-evaluates `BattyCommands` mid-teardown and traps (`EXC_BREAKPOINT`), crashing instead of quitting.

## Notes

**Relation to the project's re-entrancy rules.** `docs/swiftui-observation-rules.md` forbids SwiftUI callbacks from synchronously calling responder-changing AppKit APIs because `NSHostingView` runs SwiftUI updates inside AppKit's layout pass. This crash is the mirror image: an **AppKit notification observer synchronously calling `terminate:`, which re-enters SwiftUI**. Note the standing warning (CLAUDE.md, the #0229 regression) against "fixing" such violations by hopping the call into a `Task` — a fix that merely defers `terminate` to the next runloop turn needs justification that it changes *ownership* of the call, not just its timing.

**Investigation blocker — no dSYM for the crashed binary.** Searched: `mdfind com_apple_xcode_dsym_uuids == d164cb47-89b6-37fc-90b6-23c6bcd5c6bd` returns nothing, `~/Library/Developer/Xcode/Archives` does not exist, and `dist/` is empty. The four Batty frames cannot be symbolicated to file:line, so the exact trapping statement is unknown. For later resolution if the dSYM surfaces:

- Binary UUID: `d164cb47-89b6-37fc-90b6-23c6bcd5c6bd` (Batty 1.1.0, build 20260805)
- Batty frame offsets: `+51236` (trap, frame 0), `+46664` (frame 2, commands body), `+304636` / `+305944` (frames 30/29, terminate path), `+1062472` / `+1063128` (frames 31/32, close observer)

This is a process gap: release builds should retain their dSYMs — without them every field crash report is this much harder. That likely warrants its own issue (not filed here).

**Not a memory crash.** At crash: `TOTAL 2.7G` virtual, but `MALLOC 97.4M` and writable regions 198.8M. This is unrelated to the #0285 graphics-memory umbrella; do not conflate them.

**Concurrent activity, recorded as observation only:** Thread 7 was deep in `AG::LayoutDescriptor` / `swift_conformsToProtocol` on `com.apple.root.utility-qos` — AttributeGraph building type layouts off the main thread. Probably benign/coincidental. Sparkle 2.9.1 was loaded and, given the app was ~4 seconds old, an update check was plausibly in flight; Sparkle is not implicated by the stack.

### 2026-08-07 — the trap is almost certainly `store.windows[0]` on an empty array

Found by source reading; **no dSYM and no reproduction**, so this is a
strong hypothesis, not a confirmed root cause.

**The candidate** — `BattyKit/Sources/BattyKit/Commands/BattyCommands.swift:38`:

```swift
private var keyWindow: WindowRuntime { store.keyWindowRuntime() ?? store.windows[0] }
```

`Array` subscript out of range traps via `brk 1` — exactly the observed
`EXC_BREAKPOINT` / `Trace/BPT trap: 5`, and unlike a force-unwrap it leaves
no `asi` / `lastExceptionBacktrace` field, which matches the attached `.ips`
(both absent). It is the **only unguarded trap-capable construct in the
file** — a scan for `!`, `try!`, `as!`, literal subscripts, `precondition`,
`fatalError` and `assert` found nothing else.

**Why it is reachable at exactly this moment** — every step verified in the
current tree, and both files are unchanged from the release commit
`240e7e4` except one unrelated line:

1. `AppStateStore.removeWindow(id:)` (`AppStateStore.swift:139`) runs
   `windows.removeAll { $0.id == windowID }` — **`windows` is now empty**.
2. `:145` immediately calls `terminateIfLastContentWindowGone()`, which
   reaches `NSApp.terminate(nil)` (`:161`) **synchronously, still inside the
   `NSWindow` close notification**.
3. AppKit's `_waitForPendingChangesToFinish` spins the runloop (frame 25).
4. SwiftUI flushes a transaction and re-evaluates the `Commands` body
   (frames 5-13).
5. `keyWindow` evaluates. `keyWindowRuntime()` (`:370-374`) returns nil —
   it requires both `NSApplication.shared.keyWindow` and an
   `nsWindowMap` entry, and the window is mid-close.
6. The `?? store.windows[0]` fallback indexes an **empty** array. Trap.

The comment on `:36-37` states the fallback exists "so previews/tests
without a key window still compile without force-unwrapping." The author
avoided a force-unwrap and reached for an array subscript, which traps
identically — and the teardown window where `windows` is empty was not
anticipated.

**What is NOT established.** Frame 1 is `CommandGroup.init(after:addition:)`
and there are two such groups — `:65` (`.sidebar`) and `:176`
(`.windowArrangement`) — and *neither references `keyWindow` directly*. In an
optimized build the `@CommandsBuilder` closures are inlined into one
function, so frame 0's offset cannot be attributed to a specific closure
without a dSYM. So the mechanism and the state are established; the precise
frame attribution is not.

**This does not block a fix.** `store.windows[0]` is a latent crash on an
empty array regardless of which closure evaluates it, and calling
`terminate:` synchronously from inside a close notification is a
re-entrancy defect regardless of what traps. Both are worth fixing on their
own merits. Two distinct changes:

- **Make `keyWindow` total.** It must not trap when no windows remain. This
  needs `keyWindow` to become optional (or the commands to tolerate its
  absence), which touches every menu item that reads it — the larger part of
  the work.
- **Stop re-entering SwiftUI from the close observer.** Note the CLAUDE.md
  caution from #0229: do not "fix" this by hopping the `terminate` call into
  a `Task`, which trades a crash for a race. The question to answer is which
  code should *own* the terminate decision, not merely when it runs.

**Confirmation still wanted, cheaply:** the unified log from the crashing
Mac around 23:38:45-23:38:56 would settle it. `removeWindow` logs
`remaining windows=0` (`:140`) and `terminateIfLastContentWindowGone` logs
`no content windows remain; terminating` (`:160`). If both appear
immediately before the crash timestamp, steps 1-2 are confirmed observation
rather than inference.

## Root cause

Two independent defects, both load-bearing for the observed crash shape:

**A. `BattyCommands.keyWindow` was not total.** `BattyCommands.swift:38` read
`store.keyWindowRuntime() ?? store.windows[0]`. The `??` fallback was written
to avoid a force-unwrap, but `Array` subscript traps identically to a
force-unwrap on an invalid index — it only looks safer. `windows` can
legitimately be empty while this `Commands` body is evaluated, because of
defect B.

**B. `terminateIfLastContentWindowGone()` called `NSApp.terminate(nil)`
synchronously from inside `WindowDelegate.windowWillClose(_:)`** — a genuine
`NSWindowDelegate` callback that AppKit invokes from deep inside its own
window-closing call stack (`-[NSWindow _finishClosingWindow]` →
`postNotificationName:` → the delegate). `NSApp.terminate(nil)`'s own
implementation spins the run loop (`-[NSPersistentUIManager
_waitForPendingChangesToFinish]`) **before that call stack unwinds**, and the
spin can flush a pending SwiftUI transaction that re-evaluates the menu-bar
`Commands` body — including `BattyCommands.keyWindow` — while
`AppStateStore.windows` is empty, already emptied by `removeWindow(id:)`.

**Correction, from review:** the original framing above had A and B's
relationship backwards. `AppStateStore.windows` is declared
`@ObservationIgnored` (`AppStateStore.swift:103`), so emptying it does
**not**, by itself, invalidate or re-trigger the `Commands` body — SwiftUI's
Observation tracking never sees that write. The re-evaluation that trapped
was driven by *some other* pending transaction (an ordinary, unrelated
observed-state change) that AppKit's terminate-time run-loop spin happened
to flush; defect B's synchronous `terminate:` call is what created the
opportunity for *that* flush to happen mid-teardown, but it is not what made
`windows` itself observable-empty. Given that, **defect A alone is necessary
and sufficient to fix this specific crash** — a `Commands` body evaluated at
any point while `windows` is empty, for any reason, no longer traps once
`keyWindow` is total. Defect B is a separate, independently-motivated
re-entrancy-hygiene fix — `NSApp.terminate` should not be called synchronously
from inside AppKit's own window-close notification callback, full stop — but
it does **not** close the window in which `windows` can be read empty by a
re-evaluated `Commands` body. If anything it *lengthens* that window: instead
of terminating near-immediately from inside the synchronous call, the app now
deliberately stays alive with `windows == []` for at least one additional
main-run-loop turn (see `## Fix` and `## Gotchas` for what remains reachable

## Fix

**A — made `keyWindow` total.** `BattyCommands.swift:50`: `store
.keyWindowOrFirstRegistered()`, changing the property's type from
`WindowRuntime` to `WindowRuntime?`. Every one of the ~30 use sites in the
file was audited and updated: action closures use optional chaining
(`keyWindow?.addSession()`), `.disabled(...)` modifiers that read through
`keyWindow` now read `nil` as "disabled" via optional chaining, and the two
action buttons that had no existing `.disabled` guard ("New Session" in both
the File menu and the Session menu) gained `.disabled(keyWindow == nil)` so
a phantom keyWindow can't silently no-op instead of visibly graying out —
per the task's standing guidance that a menu item silently acting on a
phantom window is worse than one that's disabled. No use site was left
force-unwrapped or subscripted. Review round 1: the fallback expression
itself (`keyWindowRuntime() ?? windows.first`) was extracted into
`AppStateStore.keyWindowOrFirstRegistered()` so it has a real regression
test — see Verification.

**B — deferred the terminate *actuation*, not the *decision*.**
`AppStateStore.terminateIfLastContentWindowGone()` still makes its decision
synchronously and unconditionally (`nsWindowMap.isEmpty` and `windows
.allSatisfy { $0.sessions.isEmpty }`, unchanged), and `windows.removeAll`/
`nsWindowMap.removeValue` — the writes that produced that decision — are
untouched, still fully synchronous, in the same place they were. Only the
call to actually quit is wrapped in `DispatchQueue.main.async`, so it runs on
a later run-loop turn, outside any nested AppKit call stack, and re-verifies
both guards immediately before calling `terminateHandler()` (default:
`NSApp.terminate(nil)`; overridable — see Verification). If a window somehow
appears before that turn runs, the stale decision aborts instead of
terminating on outdated state. A `terminationScheduled` flag prevents
`unregisterNSWindow` and `removeWindow` — which both call this method
synchronously from the same `windowWillClose` — from queuing two deferred
checks.

**Why this is not the `Task`-hop CLAUDE.md and #0229 forbid.** #0229 deferred
a *write* (`focusedPaneID`) that a second writer (an AppKit focus echo) was
racing over the same fact; the deferred write just changed who won, and the
regression was that it lost a race the synchronous version used to win.

**Correction, from review:** the original text here claimed "`windows` and
`nsWindowMap` have exactly one writer each" — that's false, and the review
caught it precisely because one of this issue's own new tests disproves it.
Writers of `windows`: `init`, `windowRuntime(for:)`, `removeWindow(id:)`.
Writers of `nsWindowMap`: `registerNSWindow`, `unregisterNSWindow`.
`windowRuntime(for:)` is reachable in the deferred gap — a New Window action
between the decision and the deferred check running is exactly what
`deferredTerminateAbortsIfANewWindowAppearsBeforeItRuns` simulates. So
soundness here does **not** come from writer exclusivity. It comes from the
deferred block **re-reading live `self.windows`/`self.nsWindowMap` at
execution time** rather than trusting the state captured when the decision
was made: if the world moved on before the next turn — a new window
registered — the stale decision aborts instead of terminating on outdated
state. That re-read-on-execution shape, not "only one writer exists," is
what makes this sound, and it is the same staleness-guard shape
`docs/swiftui-observation-rules.md` prescribes for model-initiated AppKit
follow-ups ("the follow-up into AppKit runs on a fresh main-actor turn ...
and carries a staleness guard ... so a superseded follow-up can never fire
late"). Any future writer of `windows`/`nsWindowMap` (#0234 will add some)
must preserve this: the deferred block must keep reading live store state,
never a snapshot taken at decision time.

## Gotchas

- **Any future test that empties `windows` on a store must consider
  `terminateHandler`.** `removeWindow`/`unregisterNSWindow` reaching zero
  windows now defers `NSApp.terminate(nil)` rather than calling it
  synchronously, which happens to make such a test *safe by default* (Swift
  Testing doesn't spin the run loop between statements, so the deferred
  block typically never runs during a synchronous test body) — but that
  safety is incidental to Fix B remaining intact, not guaranteed by the test
  itself. Prefer overriding `store.terminateHandler = {}` explicitly in any
  new test that can reach this state, the way
  `keyWindowFallbackResolvesToNilWhenNoWindowsRemain` now does, rather than
  relying on the deferral timing.
- **#0234 (multi-window support, in-progress) coordination.** Both fixes are
  multi-window-safe by construction, not by assumption of "at most one
  content window": `keyWindow`'s fallback is `store.windows.first`, not an
  index into a known-size array, and `terminateIfLastContentWindowGone`'s
  guards already iterate `windows`/`nsWindowMap` rather than assuming a
  single entry. Nothing in this fix narrows or widens the "terminate on last
  *content window*, not last *session*" semantics #0239 established: it
  changes only *when* the already-decided terminate call fires, never the
  decision inputs. A future multi-window change should preserve: (1)
  `terminateIfLastContentWindowGone`'s two guards firing off `windows`
  /`nsWindowMap` state, not a window count constant; (2) the deferred
  block's re-verification reading live `self.windows`/`self.nsWindowMap` at
  execution time, not a captured snapshot — this is what makes "a new window
  opened before the deferred turn ran" correctly abort instead of
  terminating past it.
- **The Beta build environment was broken, then fixed mid-issue.** The
  `TerminalSurface.swift` compile failure blocking `scripts/build-beta.sh`
  (stale `include/ghostty.h`/`module.modulemap` left over from #0286's
  header relocation) was found and fixed by the reviewer, outside this
  diff. If Beta builds break again with a similar "symbol not found despite
  identical header" signature, check for other stale files left behind by
  past header/layout moves before assuming a new regression.
- **Frame 0's exact trapping statement is now directly confirmed**, not
  merely inferred — see `## Notes` → "2026-08-07 — CONFIRMED by direct local
  reproduction, fully symbolicated". A Debug-configuration Beta build
  reproduced the crash twice with full Swift symbol names, trapping at
  `BattyCommands.keyWindow.getter`'s `Array` subscript via the exact chain
  this issue hypothesized. The 1.1.0 release binary's own dSYM is still
  missing and unrecovered, so it remains unconfirmed that the *original
  field crash* trapped through this exact `CommandGroup` closure specifically
  (an optimized release build can inline differently than Debug) — but the
  trapping construct itself and the surrounding mechanism are no longer
  inference.
- **The app now deliberately lives with `windows == []` for at least one
  extra main-run-loop turn after the last content window closes** (the
  `DispatchQueue.main.async` deferral in Fix B). This is a direct, known
  consequence of Fix B, not a side effect discovered later — and it widens,
  not narrows, the window during which `windows` can be read empty by
  whatever else runs in that turn. It's tolerable because process exit is
  imminent regardless (the deferred block terminates unless something
  legitimately intervened), but trap-capable reads of `windows[0]` remain
  reachable during that turn and were **deliberately left unfixed in this
  diff** — the reviewer is filing a follow-up issue to address them as a
  set rather than growing this diff further. **This inventory is not
  claimed complete** — it is everything a review pass plus a repo-wide grep

  trust this list as exhaustive:
  - `AppStateStore.swift:573` — `anyContentWindowRuntime() ?? windows[0]` in
