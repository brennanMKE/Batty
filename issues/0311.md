## Description

A field crash of the release build: **Batty 1.1.0 (20260805)**, `/Applications/Batty.app`, `co.sstools.Batty`, pid 51733, crashed **~3.9 seconds after launch** (launch 2026-08-06 23:38:51.3428, crash 23:38:55.2859) on **Thread 0, the main thread**, with `Exception Type: EXC_BREAKPOINT (SIGTRAP)`, `esr: 0xf2000001 (Breakpoint) brk 1`.

**This is a Swift runtime trap, not a memory-protection fault** — a `fatalError`, failed `precondition`/`assert`, force-unwrap of nil, out-of-bounds index, or similar deliberate `brk` instruction in Batty's own code path. That makes it far more tractable than a wild pointer: some specific statement decided to trap.

The stack (read bottom-up) shows the shape of the failure: the user closed a window, Batty's close observer synchronously called `NSApplication.terminate:`, AppKit's terminate path spun the runloop mid-teardown, SwiftUI flushed a pending transaction and re-evaluated the menu-bar `Commands` body against half-torn-down state, and something in that body trapped.

Hardware/OS: **`Mac16,12`, macOS `26.4.1 (25E253)`** — note this is a *different machine* from the Mac mini used for development (`Mac16,11`, macOS 26.5.1); possibly the MacBook Air. The ~4-second process lifetime is itself a clue: state restoration or an immediate window-close is in play.

## Mechanism

Three tiers of certainty here. Keep them separate.

**What the crash report establishes:** a Batty notification observer on the window-close path (frames 29–32) synchronously invoked `-[NSApplication terminate:]` (frame 28); AppKit's persistent-state teardown spun the runloop (frame 25); SwiftUI flushed a transaction and re-evaluated a `Commands` body (frames 5–14); the trap fired inside Batty code called from `CommandGroup.init(after:addition:)` (frames 0–2).

**What was verified in the current source tree** (matches the stack shape, though the crashed binary is 20260805 and cannot be symbolicated — see Notes):

- `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:161` — `NSApp.terminate(nil)` inside `private func terminateIfLastContentWindowGone()`, reached from `public func removeWindow(id:)` (`:138`), whose doc comment says "Called from the window-close teardown path". That is exactly frames 29–32.
- The re-evaluated commands body is `BattyKit/Sources/BattyKit/Commands/BattyCommands.swift`. It has exactly two `CommandGroup(after:)` sites: `:65` (`.sidebar`) and `:176` (`.windowArrangement`). Frame 1 is `CommandGroup.init(after:addition:)`, so one of these two closures is the frame-2 caller; frame 0 is code inside it.

**Hypothesis (leading, unproven):** the `Commands` body is being evaluated against half-torn-down app state — mid-`terminate`, after the last window's teardown has started — and some value it reads is in a state that never occurs during normal evaluation, tripping a trap (force-unwrap, precondition, or index). Which exact statement traps is unknown without the dSYM.

**Register hint — a lead to check first, explicitly unconfirmed:** the crashed thread state has `x25 = "type metadata for KeyboardShortcut"` and `x28 = _swiftEmptyArrayStorage`. The `CommandGroup(after: .sidebar)` site at `BattyCommands.swift:65-75` applies `.keyboardShortcut(shortcuts.keyboardShortcut(for: .toggleSidebar))`. However, that path was traced in the current source and looks nil-safe at every step: `ShortcutsStore.keyboardShortcut(for:)` (`ShortcutsStore.swift:65`) → `binding(for:)` (`:61`) uses `bindings[action] ?? action.defaultBinding`, and `ShortcutBinding.keyboardShortcut` (`ShortcutBinding.swift:71-78`) uses `key.first ?? " "`. So the register contents may be incidental — `KeyboardShortcut` metadata is plausibly live in registers during any commands-body evaluation. Do not present this as the cause; check it first, then move on.

## Steps to reproduce

Not reproduced. The suspected trigger, for someone to try (unverified):

1. On a machine where Batty restores a single window at launch, launch Batty 1.1.0 from `/Applications`.
2. Within a few seconds of launch — before doing anything else — close the window with the mouse (the red close button or an equivalent close control).
3. This drives `removeWindow` → `terminateIfLastContentWindowGone` → `NSApp.terminate(nil)` from inside the close-notification observer. The crash requires a pending SwiftUI transaction to be flushed during `_waitForPendingChangesToFinish`, which may be timing-sensitive — closing *very* soon after launch (while initial renders are still settling) is likely load-bearing.

The crash occurred on `Mac16,12` / macOS 26.4.1, not the development Mac mini; the window/display configuration there may matter.

## Expected behavior

Closing the last content window quits the app cleanly. Terminate is initiated from a stable point in the runloop, not synchronously from inside an `NSWindow` close-notification observer, so SwiftUI never re-evaluates the `Commands` body against mid-teardown state.

## Actual behavior

`NSApp.terminate(nil)` runs synchronously inside the window-close observer; AppKit's terminate path re-enters the runloop; SwiftUI re-evaluates `BattyCommands` mid-teardown and traps (`EXC_BREAKPOINT`), crashing instead of quitting.

## Notes

**Relation to the project's re-entrancy rules.** `docs/swiftui-observation-rules.md` forbids SwiftUI callbacks from synchronously calling responder-changing AppKit APIs because `NSHostingView` runs SwiftUI updates inside AppKit's layout pass. This crash is the mirror image: an **AppKit notification observer synchronously calling `terminate:`, which re-enters SwiftUI**. Note the standing warning (CLAUDE.md, the #0229 regression) against "fixing" such violations by hopping the call into a `Task` — a fix that merely defers `terminate` to the next runloop turn needs justification that it changes *ownership* of the call, not just its timing.

**Investigation blocker — no dSYM for the crashed binary.** Searched: `mdfind com_apple_xcode_dsym_uuids == d164cb47-89b6-37fc-90b6-23c6bcd5c6bd` returns nothing, `~/Library/Developer/Xcode/Archives` does not exist, and `dist/` is empty. The four Batty frames cannot be symbolicated to file:line, so the exact trapping statement is unknown. For later resolution if the dSYM surfaces:

- Binary UUID: `d164cb47-89b6-37fc-90b6-23c6bcd5c6bd` (Batty 1.1.0, build 20260805)
- Batty frame offsets: `+51236` (trap, frame 0), `+46664` (frame 2, commands body), `+304636` / `+305944` (frames 30/29, terminate path), `+1062472` / `+1063128` (frames 31/32, close observer)

This is a process gap: release builds should retain their dSYMs — without them every field crash report is this much harder. That likely warrants its own issue (not filed here).

**Not a memory crash.** At crash: `TOTAL 2.7G` virtual, but `MALLOC 97.4M` and writable regions 198.8M. This is unrelated to the #0285 graphics-memory umbrella; do not conflate them.

**Concurrent activity, recorded as observation only:** Thread 7 was deep in `AG::LayoutDescriptor` / `swift_conformsToProtocol` on `com.apple.root.utility-qos` — AttributeGraph building type layouts off the main thread. Probably benign/coincidental. Sparkle 2.9.1 was loaded and, given the app was ~4 seconds old, an update check was plausibly in flight; Sparkle is not implicated by the stack.
