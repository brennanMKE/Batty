## Description

Build the client half of tmux control mode: launch
`ssh <host> tmux -CC new -A -s <name>`, hold the connection, and parse
the control-mode protocol into typed Swift events. **No Batty UI
integration beyond whatever is needed to drive one Pane manually** —
the deliverable is a tested parser plus a live, observable connection,
not a feature.

This is the transport for the [#0341](0341.md) umbrella's recommended
option A. The rationale for choosing control mode over screen scraping
(it emits structured events like `%output`, `%layout-change`,
`%window-add` rather than drawing a screen, and iTerm2 proves the
shape in a Mac terminal app) is recorded in the umbrella and is not
repeated here.

**Not scheduled work.** Inherits #0341's status: staged for a future
major release, not queued.

The work splits cleanly, and the split is the point:

- **The parser is pure and offline.** Bytes in, typed events out, no
  I/O, no SSH, no `Process`, fully unit-testable in `BattyKitTests`
  from recorded transcripts. This is where the bulk of the risk lives
  and where nearly all the tests belong.
- **The connection is thin and impure.** Spawn `ssh`, feed its stdout
  to the parser, write commands to its stdin, notice when it dies.

Batty has no existing networking or subprocess-session layer to build
this on, so this issue also decides where such a thing lives. Note
that Batty's XPC work (#0269–#0279) established conventions for
dependency-free shared types in their own target
(`BattyKit/Sources/BattyXPCCore`), which is a reasonable precedent for
a self-contained protocol module even though the transport is
unrelated.

## Expected behavior

1. **Connect.** Given a host and a session name, Batty starts
   `ssh <host> tmux -CC new -A -s <name>` and reaches the control-mode
   handshake, or fails with a diagnosable error distinguishing "ssh
   could not connect", "authentication failed", "tmux not installed on
   the remote", and "tmux is too old for control mode".
2. **Parse.** The control-mode stream is decoded into typed events
   covering at minimum:
   - `%output <pane-id> <data>` — pane output, with tmux's octal
     escaping decoded back to raw bytes.
   - `%begin` / `%end` / `%error` — command reply framing, correlated
     back to the command that caused them.
   - `%layout-change`, `%window-add`, `%window-close`,
     `%window-renamed`, `%unlinked-window-*` — topology events.
   - `%session-changed`, `%exit`, `%client-detached` — lifecycle.
   - Unknown `%notification` lines — preserved and ignored, not fatal.
3. **Send.** Commands can be written to the session
   (`send-keys`, `resize-pane`, `capture-pane`, `list-panes`), and a
   command's reply is delivered back to its caller — the `%begin`/
   `%end` framing is what makes this possible and the parser must
   preserve the correlation.
4. **Survive the ugly cases.** Partial lines split across reads,
   very large `%output` payloads, binary bytes inside `%output`,
   non-UTF-8 sequences, and a mid-stream disconnect all produce
   defined behavior rather than a crash or a silent stall.
5. **Disconnect cleanly.** Tearing the connection down does not leave
   an orphaned `ssh` process, and the far-side tmux session survives
   (that persistence is the whole reason for choosing tmux).

## Acceptance criteria

1. A parser type in the `BattyKit` package that converts a control-
   mode byte stream into typed events, with **no I/O dependency** —
   constructible and drivable entirely from `Data` in a unit test.
2. `scripts/build.sh unit` passes with new `BattyKitTests` covering,
   at minimum: each event kind above; `%output` octal-escape decoding
   round-tripped against known bytes; `%begin`/`%end`/`%error`
   correlation including two commands in flight; a payload split
   arbitrarily across chunk boundaries producing the same events as
   the unsplit stream; binary and non-UTF-8 payloads; and an unknown
   notification being skipped without loss of the following events.
3. Test fixtures are **recorded transcripts from a real
   `tmux -CC` session**, checked in, not hand-written guesses at the
   format. A hand-written fixture proves the parser matches its
   author's belief about tmux, which is exactly the failure mode this
   project has been burned by.
4. A live connection to the Mac mini is demonstrated: connect, observe
   `%output` for a command run in the remote session, send `send-keys`
   and observe the resulting output, disconnect, and confirm the
   remote tmux session is still alive (`tmux ls` on the remote).
5. The remote's tmux version is checked at connect time and an
   unsupported version produces a clear error rather than a parse
   failure. Record the minimum version the parser targets.
6. Byte volume is bounded: a remote command producing sustained output
   (`yes`, a large `find`) does not grow Batty's memory without limit.
   #0285 is this project's standing lesson that unbounded per-session
   growth is easy to ship and expensive to retrofit.
7. Where the connection and parser live in the package layout is
   stated, with a one-line rationale, so #0344 is not guessing.

## Notes

- Credentials and host configuration are **the user's existing SSH
  setup** — `~/.ssh/config`, agent, keys. This issue must not
  introduce a Batty-managed credential store; that is a large security
  surface for no benefit here, and it would undercut the main reason
  option A was recommended.
- `%output` escaping: tmux escapes non-printable bytes in octal.
  Round-tripping this correctly is the single most likely place for a
  subtle bug — it corrupts exactly the escape sequences the terminal
  needs.
- Keep the parser's event vocabulary aligned with what #0345 will need
  from `%layout-change`. Parsing the layout string into a usable tree
  can live in either issue, but somebody has to own it; say which.
