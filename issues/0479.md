## Description

#0473 types a Project Tab's approved startup command into the shell when that shell sends its first OSC 7 working-directory report. If the shell never sends one, the command is never typed and nothing tells the user. The shell may have no Batty integration loaded, the integration may fail to load, or the shell may not be zsh or bash. The user approved the commands in the trust sheet and opened the Project, then got a bare prompt. No error appears, nothing shows on the Tab, and the only trace is that a log line is missing. This issue adds a bounded, event-driven "the shell never became ready" outcome that the user can see and act on, and corrects `Concepts.md` about which shells report OSC 7.

## Verified current behavior (on `issue/0473`, about to merge)

- `TerminalDelegateProxy.armStartupCommand(_:)` (`BattyKit/Sources/BattyKit/Runtime/TerminalDelegateProxy.swift:80-86`) stores the delivery in `pendingStartupCommand` (`:71`) until `terminalDidChangeWorkingDirectory` sets `hasReportedWorkingDirectory` (`:117`) and hands it to `StartupCommandDelivery.deliverOnNextMainTurn()` (`:120-122`). Its own doc comment says: "A shell that never emits OSC 7 never receives the command." Nothing else ever consumes, expires or reports `pendingStartupCommand`. `terminalDidAttachSurface` and `terminalDidClose` do not touch it.
- `AppStateStore.armStartupCommands(of:in:)` (`Runtime/AppStateStore+ProjectStartup.swift:152`) arms every non-blank command after `finishOpen` (`:122`) creates the Session. Nothing records which Tabs are still waiting.
- `TabRuntime.armStartupCommand(_:)` (`Runtime/TabRuntime.swift:162`, test seam `:167`) returns the `StartupCommandDelivery` (`Runtime/StartupCommandDelivery.swift`), whose `waitUntilFinished()` (`:87`) completes only once delivery has run.

**Which shells actually report OSC 7.** This is narrower than the bundled resources suggest:

- The integration libghostty actually sources is the `libghostty-spm` package's own bundle. `GhosttyRuntimeResources.configureEnvironment()` sets `GHOSTTY_RESOURCES_DIR` to it before `ghostty_init` (`BattyKit/.build/checkouts/libghostty-spm/Sources/GhosttyTerminal/Configuration/GhosttyRuntimeResources.swift:25`), and nothing in Batty overrides it (`docs/ssh-colors-and-terminfo.md`: "authoritative for the app's entire lifetime"). That bundle ships only `bash/` and `zsh/`. Both emit OSC 7 from the prompt hook: `zsh/ghostty-integration:64` and `bash/ghostty.bash:151`, both as `file://` URLs. The bash script returns early for non-interactive shells (`bash/ghostty.bash:107`).
- Batty also vendors a five-shell tree at `Resources/ghostty-runtime/ghostty/shell-integration/` (`bash`, `elvish`, `fish`, `nushell`, `zsh`). `scripts/bundle-ghostty-resources.sh` copies it into `Batty.app/Contents/Resources/ghostty/shell-integration/`. In that tree, fish (`fish/vendor_conf.d/ghostty-shell-integration.fish:232`), elvish (`elvish/lib/ghostty-integration.elv:188`), bash (`bash/ghostty.bash:244`) and zsh (`zsh/ghostty-integration:238`) emit OSC 7. Nushell's `nushell/vendor/autoload/ghostty.nu` does not: it contains only the `ssh` wrapper. **This tree is never sourced at runtime** (`docs/ssh-colors-and-terminfo.md`: "it is dead code at runtime"), so the fish and elvish OSC 7 emitters in it never run. #0400 tracks that regression.
- So today, fish, elvish, nushell and any other shell get no Batty integration at all. They report OSC 7 only if the shell does it natively or through the user's own config, and that is unverified per shell and version. Even zsh and bash report nothing when the integration fails to inject, for example when a user startup file resets `ZDOTDIR`, when the shell is non-interactive, or when the user's shell is `/bin/sh`.

**What `Concepts.md` says.** The `Project` entry on `issue/0473` (`Concepts.md:50`) says "Batty's zsh and bash integration emits OSC 7; a shell without it reports nothing unless the user's own configuration emits it, and then runs nothing." The zsh/bash part is correct. It does not say that the fish/elvish/nushell integrations found in the app bundle are inert. A reader who finds them there will reasonably conclude that fish users are covered, and they are not. The entry also documents "runs nothing" as if that were the intended end state.

**No other readiness signal exists.** `TerminalDelegateProxy` receives title, resize, focus, close, bell, desktop notification, working directory, command finished (OSC 133 D), surface attach/detach, open URL, clipboard and hover-link callbacks. Nothing reports prompt start (OSC 133 A), even though both live scripts emit it. Surface attach only means the pty exists, not that a shell is at a prompt.

## Steps to reproduce

1. In Batty Beta (Projects flag on), set the login shell to fish, or start zsh with integration disabled (for example, a `~/.zshenv` that resets `ZDOTDIR`).
2. Create a Project with one Terminal Tab whose startup command is `echo hello`, with "Run startup commands when the Project opens" on.
3. Open the Project and choose **Run Commands** in the trust sheet.

## Expected behavior

**1. Bounded wait, driven by an event and an injected clock.**

- When a Tab with an armed, undelivered startup command gets its surface (`terminalDidAttachSurface`), a readiness deadline starts. Measure it from attach, not from arming, so a Tab in a background Session is not penalised for never having been mounted. It runs on an injected `SchedulingClock` (`Runtime/SchedulingClock.swift`, `docs/async-test-seams.md` §1): `SystemClock()` by default in production, `TestClock` in tests. The interval is a named constant (suggested 10 s, long enough for a heavy `.zshrc`). No `asyncAfter`, `Timer` or `Task.sleep` outside the clock.
- If the first OSC 7 arrives before the deadline, behavior stays exactly as in #0473: one delivery, and the deadline is cancelled.
- If the deadline passes first, Batty **does not type the command blindly**. With no readiness report, the shell may be at a password, `sudo`, login-menu or TUI prompt that the user's startup files opened, and keystrokes typed there would be answered by that prompt instead of the shell. The Tab instead enters a **"startup command waiting"** state (item 2). The delivery stays armed: a late first OSC 7 (a slow shell) still delivers it exactly once and clears the state.
- If the shell exits (`terminalDidClose`) before any report, the delivery is disarmed and nothing is typed. Log it at `notice`.

**2. A non-modal signal on the Tab, with a user action.**

- `BattyTabChip` (`Views/BattyTabChip.swift`) shows a small indicator for a Tab in the waiting state. It must not steal focus, open a sheet, or move first responder. Its tooltip and accessibility label name the problem ("Startup command not run — the shell didn't report it was ready").
- Clicking the indicator (or a Tab context-menu item) shows the pending command with **Run Now** and **Dismiss**. **Run Now** delivers through the same `StartupCommandDelivery`, so delivery stays at most once per Tab per open: a later OSC 7 after Run Now must not re-send. **Dismiss** disarms the delivery and clears the indicator. Both are event-origin writes (a button), per `docs/swiftui-observation-rules.md`. The deadline firing is a clock event, not a view callback, and is allowed to write the observed waiting state.
- Not a Bell Feed entry. `Concepts.md` defines the Bell Feed as the list of terminal Bell events, and this signal is about one Tab.
- One `logger.notice` line per Tab that enters the waiting state, giving the Tab id and the reason (deadline, or shell exited).

**3. Concepts.md.** Rewrite the "Startup commands" bullet of the `Project` entry:

- The live integration is the one bundled in `libghostty-spm`, and it covers **zsh and bash only**.
- The fish, elvish and nushell integrations in the app bundle are not sourced (#0400). Shells other than zsh and bash report OSC 7 only natively or through the user's own config.
- When no report arrives, the Tab shows the waiting indicator with Run Now and Dismiss instead of silently running nothing.

Bump the document version line.

**4. Flag gate.** The deadline, the waiting state and the indicator exist only for Tabs armed by `armStartupCommands`, which already checks `featureFlags.projects` (`AppStateStore+ProjectStartup.swift:152-153`). The chip's indicator code path also reads `featureFlags.projects`. Append the new gate sites to `docs/feature-flags.md`. With the flag off, nothing renders and no clock is ever scheduled.

## Acceptance criteria

- Unit tests drive the real `TerminalDelegateProxy` path with a recording `StartupInputSink` and a `TestClock`. They use no sleeps, deadline polls or elapsed-time assertions (`AGENTS.md` "Asynchronous tests"). They await `TestClock.waitForSleepers` and `advance(by:)` and the delivery's completion signal:
  - attach, then OSC 7 before the deadline: one delivery, no waiting state, and nothing left scheduled on the clock (`pendingCount == 0`);
  - attach, then the deadline passes: zero deliveries and the Tab is in the waiting state;
  - waiting, then a late OSC 7: exactly one delivery and the waiting state clears;
  - waiting, then Run Now: exactly one delivery, and a later OSC 7 delivers nothing;
  - waiting, then Dismiss: zero deliveries, the state clears, and a later OSC 7 delivers nothing;
  - the shell closes before any report: zero deliveries, nothing left scheduled, no waiting state;
  - a Tab armed with no command, or a Project opened without running commands, never schedules a deadline.
- The deadline's start is tied to surface attach. A test arms without attaching, advances the clock past the interval, and observes no waiting state.
- Auto-naming still receives every pwd report (the #0473 composition is unchanged).
- `Concepts.md` matches item 3, and every file/line cited there is grep-verified.
- `./build.sh unit` passes and the new tests appear in its output.
- Manual check in Batty Beta: (a) zsh with integration → command runs and no indicator ever appears; (b) fish (or zsh with `ZDOTDIR` reset) → after the deadline, the indicator appears, Run Now runs the command once in the Tab's directory, and Dismiss clears the indicator. The indicator's look needs the user's visual sign-off, so mark `resolved`, not `closed`. Record in `## Gotchas` anything not verified.
- If the chip indicator gets a UI test, it runs only in the Tart VM (#0478's suite), never on the host.

- Typed-ahead input is buffered by the pty, so blind typing would usually "work". It is rejected here for the safety reason given in Expected behavior 1, not because it fails. The user's per-Tab Run Now is the explicit consent for typing without a readiness signal.

## Resolution notes

> 🟢 Resolved 2026-10-12 — A Project Tab whose shell doesn't report its working directory within 10 s of the surface attaching types nothing and shows an orange "startup command not run" indicator on its chip with Run Now / Dismiss (also in the Tab's context menu); a late report still delivers once. Concepts.md now says which shells report.

Owed to the user: the indicator's look, whether clicking it also selects the chip, and the manual Beta checks (zsh with integration never shows it; fish or a reset `ZDOTDIR` shows it and Run Now runs the command once in the Tab's directory).

## Root cause

#0473 delivers startup commands on the shell's first OSC 7 report. A shell that never sends one — any shell without Batty's zsh/bash integration — silently never ran the approved commands, with no signal to the user.

## Fix

- `TerminalDelegateProxy.armStartupCommand(_:clock:)` starts a readiness deadline (`StartupCommandReadiness.deadline`, 10 s) on an injected `SchedulingClock` when the surface attaches (`surfaceDidAttach()` from `terminalDidAttachSurface`), not at arming. Re-attaching doesn't restart it.
- Passing the deadline types nothing (the shell may be at a password, sudo or TUI prompt): the Tab enters a waiting state and one `notice` line is logged. A late OSC 7 still delivers once and clears it. Run Now delivers through the same `StartupCommandDelivery` (deferred to the next main turn, via the Tab's `TerminalViewState`), so a later report delivers nothing; Dismiss disarms. Shell close disarms with a log line and no waiting state.
- Every exit — report, Run Now, Dismiss, close, re-arm — goes through `takePendingStartupCommand()`, which cancels the deadline Task; the proxy's `deinit` also cancels it, and `StartupCommandDelivery.abandon()` releases waiters without typing.
- `TabRuntime.startupCommandWaiting` mirrors the state (written only from clock, delegate and button events); `AppStateStore.startupReadinessClock` defaults to `SystemClock()`.
- UI: `BattyTabChip` shows an orange warning-triangle `Menu` (`tab-startup-waiting`; header with the command, Run Now, Dismiss); the Tab context menu gains Run / Dismiss Startup Command. Flag-gated in `PaneView.startupWaiting(for:)`. Not a Bell Feed entry; nothing over the terminal body.
- `Concepts.md` (v0.7): only zsh and bash integrations load (from libghostty-spm's bundle) and report OSC 7; the bundled fish/elvish/nushell tree is not loaded (#0400); the waiting state.
- Docs: two `docs/feature-flags.md` gate-site rows; `docs/ui-features.md` identifier and coverage row.
