# 0371 — Layouts apply only Terminal Panes and cannot be saved, so there is no way to create or reuse a multi-kind Pane arrangement ("Workspaces")

| | |
|---|---|
| **Status** | open |
| **Module** | Session / Pane / Persistence |
| **Platform** | macOS |
| **First seen** | 2026-08-22 |

## Description

The Layout picker (`PaneLayout`, ten fixed presets) builds multi-Pane Sessions in one action, but every Pane it creates is a Terminal — `PaneLayout.apply(to:)` routes exclusively through `SplitTree.splitFocusedPane(direction:inheritingFrom:)` (`BattyKit/Sources/BattyKit/Model/PaneLayout.swift:141`), which has no `kind` parameter and is documented as terminal-only (`BattyKit/Sources/BattyKit/Model/SplitTree.swift:208-214`). Now that four non-terminal Pane kinds ship (`.gitStatus` #0304, `.processStatus` #0305, `.lmStudioDashboard` #0313, `.systemMetrics` #0314), there is no way to say "give me this arrangement *with these views in it*," and no way to save an arrangement the user has built by hand.

The user's request, verbatim:

> "We have a layouts feature. Now we want a workspaces features which is similar, but instead of just terminal panes it will allow the new views to be created instead. There would be a default set of reasonable workspaces like a terminal on the top with 2 below it dedicated to the new views. The user should also be able to save their current panes layout and views as a workspace they can select from a new workspace selector. Like layouts, we should only allow a new workspace to be selected when only 1 pane is present. We can also support creating a new session with a specific workspace selection. This would be done from the file menu and hotkeys."

And a follow-up clarification (2026-08-22), which materially narrows the scope:

> "Note the layout of these workspaces would not hard-code exact sizing details. If it calls for 1 pane on top split with 3 panes below each would be sized equally as they do now. The user can adjust sizing after the workspace is created."

**A Workspace therefore stores split topology and per-slot Pane kind, and nothing about geometry.** Applying one replays ordinary splits and inherits the sizing the app already produces for hand-made splits. There is no Workspace-owned sizing state, and no reason to consult the Workspace again once it has been applied — the resulting Panes are indistinguishable from hand-created ones and the user resizes them freely afterwards.

**Naming warning, read this before implementing:** "Workspace" is a loaded word in this repo and in `Concepts.md`. See "The name" below — it is a decision for the user, not something this issue settles.

## Naming decision (2026-08-27) — the term is "Workspace"

**Decided by the user: the saved, multi-kind Pane arrangement is called a
Workspace.** This settles Design question 1. It supersedes the filer's
recommendation in "The name" below — option 1 (generalize the existing **Layout**
concept, one term) and option 2 (a neutral third term such as "Preset" /
"Arrangement" / "Template") were both considered and both declined. Read that
section as the background that informed the choice, not as a live
recommendation.

**Layout and Workspace coexist — neither term replaces the other.**

- **Layout** keeps exactly its current meaning: the transient split geometry —
  the ten fixed `PaneLayout` presets that build an all-Terminal arrangement in
  one action, and the picker that applies them. Nothing about Layout is
  redefined by this decision.
- **Workspace** is the new concept built on top: a **saved, named, multi-kind
  arrangement** — split topology plus a `PaneContentKind` per slot, applied by
  replaying ordinary splits. It builds on the existing Layout mechanism,
  generalized to carry Pane kinds and to be saved and reused.

Design question 5 ("do Layouts and Workspaces coexist?") is therefore answered
at the vocabulary level: yes, two terms. Whether they share one picker sheet or
get two remains an implementation choice, and choosing "Workspace" as the
user-facing word does **not** by itself decide the type shape — generalizing
`PaneLayout` from an enum into a struct catalog is still on the table as the
mechanism.

### The two known costs of this name — both were raised when the choice was made

Workspace as a distinct concept requires an entry that disambiguates the two.**

and closes with the callout:

> is a *workspace grouping*. The actual *running shell process* is a **Terminal
> Session** (below).

Neither "Workspace" nor "Layout" is a defined term in `Concepts.md` today —

lowercase-w "workspace" gloss stops competing with the new capital-W term. That
is in scope here, not a follow-up. (The acceptance criteria below already require
the `Concepts.md` change; this pins what it has to say.)

**2. The name carries dead history from #0172 — accepted knowingly, not
overlooked.** `workspace.json`, `Workspace.swift`, `WorkspaceConversion.swift`,
`WorkspaceManager.swift`, `WorkspaceStore.swift`, and the Codable
`Session`/`Tab`/`SplitNode` snapshot types were **deleted by [#0172](0172.md)**
(resolved 2026-05-20). A future reader who greps the repo, `git log`, or
`issues/` for "workspace" will surface that removed machinery and the closed
tickets around it — `#0029`–`#0031`, `#0165`, `#0172`, and **[#0221](0221.md),
closed 2026-08-27 as a stale premise with this issue named as its live
successor** — interleaved with the new concept. That cost is real and permanent;
the user accepted it.

**The new Workspace concept is not a revival of that deleted persistence layer.**
What #0172 removed was *automatic, unrequested whole-app session restore*: save
every Session/Pane/Tab/cwd on quit, on every structural mutation, and on a
30-second timer, then reload it at launch. A Workspace here is a *user-authored,
explicitly invoked template* that builds on the existing Layout mechanism. It
stores split direction, nesting, and a kind per slot — **no ratios, no cwds, no
Tabs, no window frames, no running processes** — nothing auto-saves, nothing
auto-restores, and nothing is written back to it once applied. State that
distinction in the `Concepts.md` entry as well, so the next person who greps
does not have to re-derive it.

## How the Layouts feature actually works today (verified 2026-08-22 on `main`)

**Model.** `PaneLayout` (`BattyKit/Sources/BattyKit/Model/PaneLayout.swift:9`) is a `String`-backed `CaseIterable` enum of ten fixed cases (`singlePane` … `twoByTwoGrid`), each with a `name` (`:23`), a `paneCount` (`:38`), a hand-written thumbnail geometry (`layoutPanes`, `:56-125`), and an `apply(to:)` (`:132-209`).

**Application.** `apply(to:)` mutates the live `SplitTree` in place by replaying ordinary splits from the focused Pane:

```swift
public func apply(to tree: SplitTree) {
    guard tree.allPanes.count == 1 else { return }
    let primary = tree.focusedPane
    …
    tree.focusedPaneID = primary.id
}
```
(`PaneLayout.swift:132-134`, `:208`)

Every branch calls `tree.splitFocusedPane(direction:inheritingFrom: primary)` one to three times. There is **no stored geometry** — the presets deliberately pass no ratios, because same-axis equalization does the sizing. `PaneLayout.swift:147-149` states this outright: *"same-axis equalization (#0255) makes all three columns 1/3 each, so no explicit ratio is needed (it would be overridden anyway)."*

**Sizing mechanism (load-bearing for this issue).** Ratio *is* stored per interior node — `case split(id: UUID, direction: SplitDirection, ratio: Double, left:, right:)` (`SplitTree.swift:29`) — but `splitFocusedPane` overrides it: after insertion it runs `SplitTreeNode.rebalancingChain(containing:direction:in:parentIsDSplit:)` so *"every leaf in the contiguous same-direction chain that contains the new pane is re-equalized to an even 1/n fraction (#0255) … `ratio` no longer affects the final geometry of a same-axis split … A perpendicular split starts a fresh 50/50 axis"* (`SplitTree.swift:143-147`, implementation `:165-175`). Note the precise semantics: **equal within each same-direction sibling chain, 50/50 across a perpendicular boundary** — not equal *areas* across all Panes. "One on top, three below" gives the top Pane half the height and each bottom Pane a third of the other half. That is what hand-splitting produces today and is exactly what the clarification asks for. (`splitFullDimension` is the exception — it never chain-rebalances, `SplitTree.swift:189-192`.)

**Presentation.** `LayoutPickerView` (`BattyKit/Sources/BattyKit/Views/LayoutPickerView.swift:12`) is a 600×420 `.sheet` over a `LazyVGrid` of `PaneLayout.allCases` (`:20`, `:47`) with arrow-key/Return/Escape handling (`:76-81`). Its `activate()` (`:94-101`) applies to `windowRuntime.selectedSession?.tree`. It is presented from `SessionDetailView` (`BattyKit/Sources/BattyKit/Views/SessionDetailView.swift:78-80`), toggled by a `.battyToggleLayoutPicker` notification guarded on `isKeyWindow` (`:49-52`, the #0242 fan-out guard).

**Entry points — four of them, posting the same notification:**

| Surface | Site | Gated on one Pane? |
|---|---|---|
| Session menu, "Choose Layout…" | `BattyCommands.swift:100-106` | **Yes** — `.disabled(keyWindow?.selectedSession?.tree.allPanes.count != 1)` (`:106`) |
| Pane menu, "Layouts…" | `BattyCommands.swift:342-348` | **Yes** — same expression (`:348`) |
| Global shortcut (NSEvent monitor) | `BattyShortcuts.swift:190-191` | **No** |
| Command Palette | `CommandPaletteView.swift:279-280` | **No** |

### Requirement 5 verified, with a caveat that matters

The "only when 1 Pane is present" gate **does exist**, but it is enforced in two disconnected ways and leaks:

1. **Model-level, silent:** `guard tree.allPanes.count == 1 else { return }` (`PaneLayout.swift:133`) — the comment says *"Silently does nothing when the tree already has more than one pane."*
2. **UI-level, per menu item:** the two `.disabled(…allPanes.count != 1)` expressions above.

Because `BattyShortcuts`' NSEvent monitor bypasses SwiftUI's `.disabled` entirely (`docs/issue-work-obstacles.md:136-138`) and `CommandPaletteView.dispatch` posts unconditionally, **the picker still opens in a multi-Pane Session via the keyboard chord or the palette**, the user picks a preset, and nothing happens. That is tolerable-ish for a built-in Layout; it is worse for a Workspace the user just spent effort saving. Whatever this issue builds should not clone the leak — see Design questions.

## The name — background for the 2026-08-27 decision

**Settled 2026-08-27: the term is "Workspace" — see "Naming decision" above. Everything in this section is the background that informed that call; its recommendation is superseded and the two collisions it names are now accepted costs, documented there.**

**Recommendation (superseded): do not ship the user-facing term "Workspace" without a deliberate call.** Two independent collisions:

**1. `Concepts.md` already spends the word on Session.** `Concepts.md:43` defines Session as *"A named workspace, listed as one row in the Window's Sidebar,"* and `Concepts.md:55` adds the explicit gloss: *"a Batty **Session** is a *workspace grouping*."* Introducing a capital-W **Workspace** as a distinct top-level term would require re-glossing Session in the same document. `Concepts.md` is strict about one term per concept ("If a term is missing here, add it before using it") — and note **neither "Workspace" nor "Layout" is a defined term there today**; `Layout` appears only as the section heading "# Layout & UI primitives" (`Concepts.md:118`) over `Split` (`:120`) and `Sidebar` (`:135`). So *some* vocabulary work lands in `Concepts.md` either way.

**2. `#0172` deleted a different thing by that name.** `issues/0172.md` removed `Workspace.swift`, `WorkspaceConversion.swift`, `WorkspaceManager.swift`, `WorkspaceStore.swift`, and every doc mention of `workspace.json`. Its stated rationale: *"Workspace persistence was shipped as infrastructure for a feature (session restore) that was never planned."* `Concepts.md:271` still carries the scar (*"Corrects five `**Persisted:**` bullets … left over from #0172's Workspace-persistence removal"*).

**Does this feature overlap what `#0172` deleted? Partly, and the part that overlaps is the part `#0172`'s rationale did *not* object to.**

- **Genuinely different:** `#0172`'s Workspace was *automatic whole-app session restore* — `WorkspaceManager` saving every Session/Pane/Tab/cwd on quit, on every structural mutation, and on a 30-second timer (`issues/0030.md`), reloaded at launch. Nobody asked for it. This issue asks for *user-authored named templates*, explicitly invoked, that create fresh Panes. No auto-save, no auto-restore, no running processes recreated.
- **Genuinely overlapping:** the *conversion layer*. `WorkspaceConversion.swift` (143 lines of "live model → Codable snapshot") is precisely the machinery a "save my current arrangement" command needs. This issue re-introduces a narrow slice of it (topology + kinds only — no cwds, no Tabs, no ratios, no processes).

**Options, in the filer's order of preference:**

1. **Extend the existing Layout concept** rather than adding a term: a Layout gains an optional per-slot `PaneContentKind`, and the catalog gains user-saved entries alongside the ten built-ins ("Custom Layouts"). One term, one picker, one gate, one menu item, zero `Concepts.md` collisions. Cost: `PaneLayout` must stop being an enum (see below), and the ten existing presets become the `kind == .terminal` special case. **This is the recommendation** — "like Layouts, but slots can be non-terminal and the set is extensible" describes a generalization of Layout, not a sibling of it.
2. **A distinct concept under a different name** — "Preset", "Arrangement", "Template", "Scene". Keeps Layouts frozen; avoids both collisions; costs a second near-identical picker with identical gating.
3. **A distinct concept named "Workspace"** — the user's word, honored literally. Requires re-glossing Session in `Concepts.md:43`/`:55` and accepting that `git log`/`issues/` searches for "workspace" return `#0029`–`#0031`/`#0172`'s deleted auto-restore machinery for the life of the repo.

This issue uses "Workspace" throughout because that is the word the request used. *(2026-08-27: it is now also the decision — see "Naming decision" above.)*

## Behavior spec

1. **A Workspace is a named split topology with a `PaneContentKind` per leaf.** Structure and kinds only. It records which splits happen in which direction and in what nesting, and which kind occupies each resulting slot. It records **no ratios, no pixel sizes, no cwds, no Tabs, no window size.**
2. **Ship a small default set of reasonable topologies**, to be settled in design. The request offered two illustrations — "a terminal on the top with 2 below it dedicated to the new views" and "1 pane on top split with 3 panes below" — which are *examples of arbitrary topology*, not a specification; the count changed between the two messages. Do not pin the built-in set to either shape without asking.
3. **Save the current Session as a Workspace.** A command that reads the selected Session's live `SplitTree`, derives topology + per-leaf `kind`, prompts for a name, and persists it. Lossy by design — see 6.
4. **A Workspace selector**, modeled on `LayoutPickerView`: a sheet, keyboard-navigable, built-ins and user-saved entries distinguishable, with delete/rename for user entries.
5. **Gate application on exactly one Pane**, matching Layouts (`PaneLayout.swift:133`, `BattyCommands.swift:106`/`:348`) — but do not reproduce the silent no-op leak: the shortcut and palette paths must gate too, or the picker must show why it can't apply.
6. **Applying a Workspace produces exactly what hand-splitting produces.** Each split is an ordinary `splitPane`/`splitFocusedPane`, so `#0255` chain-equalization sizes every same-direction sibling group evenly and each perpendicular boundary starts at 50/50 (`SplitTree.swift:143-147`). **This means "Save current arrangement" is lossy: a user who hand-tunes their dividers, saves, and re-applies gets *equal* sizes back, not their tuned ones.** That is intended, and it is exactly the kind of thing that reads as a bug in the field — the save UI should probably say so in one line. Confirm the wording with the user.
7. **After application the Workspace is done.** The created Panes are ordinary Panes; the user resizes, splits, and closes them freely. Nothing writes back to the Workspace, nothing re-consults it, and there is no "Session is using Workspace X" association to maintain.
8. **New Session with a chosen Workspace**, from the **File menu** and via hotkeys. Note the asymmetry with today: the File menu currently holds only New Window / New Session / Open Quickly (`BattyCommands.swift:55-76`); the Layout picker lives in the **Session** menu (`:100-106`) and the **Pane** menu (`:342-348`). A File-menu placement is new ground, not an existing analogue.

## What is and isn't Codable today

| Type | Where | Codable? |
|---|---|---|
| `SplitDirection` | `LayoutModel.swift:5` | **Yes** (`Codable, Sendable, Hashable`) |
| `Pane` (value snapshot: `id`, `isHidden`, `kind`) | `LayoutModel.swift:15-44` | **Yes**, with lenient `kind` decoding (`:35-40`) |
| `PaneContentKind` | `BattyXPCCore/PaneContentKind.swift:28` | **Yes** — one string used as Codable raw value, CLI `--view` value, and wire value |
| `SplitTreeNode` | `SplitTree.swift:27-30` | **No** — `indirect enum` whose `.leaf` payload is `PaneRuntime` |
| `SplitTree` | `SplitTree.swift:96-99` | **No** — `@Observable final class` holding `PaneRuntime` graph |
| `PaneRuntime`, `TabRuntime`, `SessionRuntime` | `Runtime/` | **No** — live `@Observable` classes owning surfaces/lifecycles |

So the saved form needs a **new Codable topology type** — something like `indirect enum WorkspaceNode { case slot(PaneContentKind); case split(direction: SplitDirection, children: [WorkspaceNode]) }` — plus a converter from the live `SplitTree`. Crucially, **`ratio` is excluded** (clarification 2026-08-22), which is why this does not need `SplitTreeNode` itself to become Codable and keeps the re-introduced persistence surface genuinely small: direction, nesting, and a kind per leaf. That is a fraction of what `WorkspaceConversion.swift` carried before `#0172` deleted it.

`PaneLayout` being an `enum` is a structural blocker: user-defined entries cannot be enum cases. The catalog has to become a struct-with-identifier (built-ins as static values, user entries decoded from disk), and `layoutPanes`' hand-written thumbnail rectangles (`PaneLayout.swift:56-125`) have to be *derived* from the topology rather than hand-maintained — a saved Workspace has no author to hand-write them.

**Where saved Workspaces live.** The live precedent is `SessionNameCache`: `~/Library/Application Support/<Batty|Batty Beta>/session-name-cache.json`, resolved per bundle variant via `SessionNameCache.canonicalFileURL(fileManager:bundleIdentifier:)` (`BattyKit/Sources/BattyKit/Model/SessionNameCache.swift:104-113`, variant split at `:93-102`, added by `#0279` after Prod and Beta clobbered each other's file). Its write is atomic — temp sibling then `replaceItemAt`, falling back to `moveItem` (`:210-215`) — the same practice `#0030` specified for the deleted `WorkspaceStore` (`issues/0030.md`, "Acceptance criteria": *"Writes are atomic (write to a `.tmp` sibling, fsync, rename)"*). **Reuse `SessionNameCache`'s shape, including the per-variant directory split.** A workspaces file that ignores the variant split reproduces `#0279` exactly.

## Design questions (raised, not decided)

1. **The name.** ~~Blocking.~~ **Decided 2026-08-27: "Workspace"** — see "Naming decision" above. Note this settles the *vocabulary* only: whether the implementation extends `PaneLayout` (enum → struct catalog) or forks a parallel type is still open, and the decision explicitly leaves that mechanism on the table.
2. **Does a saved Workspace store `viewOptions`?** Two of the four kinds take creation parameters, carried on the wire as a single `viewOptions: [String: String]?` (`BattyXPCCore/PaneSplitPayload.swift:57`, decision recorded on `issues/0301.md:69`): `["path": "/abs/dir"]` for `.gitStatus` and `["pid": "1234"]` for `.processStatus` (`PaneSplitPayload.swift:34-51`). A saved Workspace must decide per key:
   - **`path`** — a stored absolute path rots the moment the user applies the Workspace in a different project. `docs/design/git-status-view.md` §1's resolution order (explicit path → source Pane's cwd → `$HOME`) is already implemented at `SplitTree.swift:274-281`; letting a Workspace slot simply *not* supply a path re-resolves to the new Session's cwd for free. Recommendation: **do not store `path`; re-resolve.** But say so explicitly rather than by omission.
   - **`pid`** — a stored pid is meaningless in a later session. `.processStatus` already has a mode B that follows the split-source Pane's active Tab when no pid is given (`SplitTree.swift:263-273`). Same recommendation.
   - If the answer is "never store options," say it in the model so a future kind's option doesn't silently start being persisted.
3. **What does "only 1 Pane" mean when that Pane is non-terminal?** Today the gate is `tree.allPanes.count == 1` with no kind check. A Session whose single Pane is a Git Status view would pass. Is applying a Workspace over it correct (the single Pane becomes the Workspace's primary slot — but of what kind?), or should the gate require a single **Terminal** Pane? `PaneLayout.apply` uses `tree.focusedPane` as `primary` and never changes its kind (`PaneLayout.swift:134`); a Workspace whose primary slot declares a kind would have to either mutate the existing Pane's kind or replace it — and `PaneRuntime.kind` drives content construction at `init` (`PaneRuntime.swift:90-96`, `:115`), so mutating it in place is not obviously supported.
4. **File menu vs. Session menu vs. Pane menu.** The request says File for "New Session with Workspace." Does the plain "apply a Workspace to this Session" item also move to File, or stay next to "Choose Layout…" in the Session menu? Splitting them across two menus is a discoverability cost; consolidating them changes where Layouts live.
5. **Do Layouts and Workspaces coexist as two pickers?** If option 2 or 3 of the naming decision wins, the app has two near-identical sheets with identical gating, two menu items, and two shortcut actions, differing only in whether slots carry a kind.
6. **Duplicate kinds within one Workspace.** `PaneContentKind.isSingletonPerSession` was designed (`docs/pane-kinds.md` §5) and deliberately not built (`PaneContentKind.swift:43-60`); `#0315`'s open question 5 still stands. A Workspace with two `.systemMetrics` slots is currently possible and unpoliced.
7. **Should the save UI state the sizing-is-not-saved rule?** See behavior spec 6.

## Acceptance criteria

- A named Workspace type exists whose persisted form carries split direction, nesting, and a `PaneContentKind` per leaf — and **no ratio, size, cwd, Tab, or process state**. Unit tests round-trip it, including a topology nested at least two levels deep.
- A small set of built-in Workspaces ships, with at least one placing a Terminal alongside two or more non-terminal kinds. The exact set is settled with the user before implementation.
- Applying a Workspace to a single-Pane Session produces the declared topology with the declared kind in each slot, and produces **the same tree shape and the same ratios as performing the equivalent splits by hand** — asserted against the `#0255` equalization rule, not against hard-coded numbers. `BattyUITests/LayoutTests.swift`'s `dumpSplitTree` S-expression assertions (`docs/ui-features.md:229-231`) are the existing precedent.
- Applying a Workspace when the Session has more than one Pane is prevented **on every entry point**, including the NSEvent shortcut monitor and the Command Palette — not only the two `.disabled` menu items. A unit test covers each dispatch path.
- "Save current Session as Workspace…" captures the live tree's topology and kinds, prompts for a name, and persists atomically to the per-variant Application Support directory (`SessionNameCache.canonicalFileURL` shape).
- Re-applying a Workspace saved from a hand-resized Session yields **equal** sizing per `#0255`, and a test asserts this rather than treating it as a defect.
- File menu items and shortcuts create a new Session with a chosen Workspace applied. Every new `ShortcutAction` case is wired in **all three** dispatch switches.
- `docs/shortcuts.md` and `BattyKit/Sources/BattyKit/Help/05-shortcuts.md` are updated in the same change for any new `ShortcutAction` case — `ShortcutDocsSyncTests` (`BattyKit/Tests/BattyKitTests/ShortcutDocsSyncTests.swift:42`) fails the pre-commit gate otherwise (`#0329`).
- `Concepts.md` gains the chosen term (see naming decision) — including, if "Workspace" is chosen, a correction to Session's gloss at `Concepts.md:43`/`:55`.
- `scripts/build.sh unit` passes.

## Gotchas

- **The three hand-copied `ShortcutAction` switches.** `ShortcutAction` is dispatched by `BattyCommands`, `BattyShortcuts` (an NSEvent monitor that **bypasses SwiftUI's `.disabled`**), and `CommandPaletteView.dispatch` — three independently maintained switches. `docs/issue-work-obstacles.md:131-148` records the cost: *"`#0315`'s review found an ungated path in round 1, another in round 2, and a third in round 3."* Two of the three are exhaustive with no `default:` so the compiler catches a missing arm; **the menu's kind list is hand-written and uncovered** (`:144-145`). Any new action here must be wired in all three, and the built-in Workspace list in the menu must be driven from the catalog, not retyped.
- **The gate leak this issue inherits if it copies Layouts verbatim.** `PaneLayout.apply`'s `guard … else { return }` (`PaneLayout.swift:133`) is a *silent* no-op, and two of four entry points do not gate. A user who saves a Workspace, hits the chord in a two-Pane Session, picks it, and sees nothing happen has hit a bug as far as they are concerned.
- **Lifecycle: applying a Workspace instantiates several non-terminal Panes at once.** Constructing a non-terminal `PaneRuntime` runs its conformer's real `setUp()` (`PaneRuntime.swift:90-96` — `contentFactory` defaults to `PaneRuntime.makeContent`, invoked at `:115`). Per `SplitTree.swift:223-227`, that means *"a real subprocess/HTTP poll for `.lmStudioDashboard`, a real sampling `Task` for `.systemMetrics`, a real `FSEventStream`/subprocess for `.gitStatus`, or `.processStatus`'s own polling."* A three-view Workspace starts three sets of background work in one action, and `#0285`'s resource-growth history (peak measured footprint 8.4 GB, `docs/pane-view-lifecycle.md:27`) is why that deserves a measurement rather than an assumption. Read `docs/pane-view-lifecycle.md` before implementing.
- **Tests must pass an inert factory.** Any test that builds a Workspace-applied tree must inject `contentFactory: { _ in nil }` — the explicit-override branch runs *first, unconditionally*, before any kind-specific resolution (`SplitTree.swift:237-241`: *"putting a kind-specific branch first would silently ignore an explicit override for that one kind, exactly the trap `#0304`'s own rebase onto this parameter hit"*). Without it, a unit test spawns real subprocesses and FSEvents watchers.
- **`docs/ui-features.md`'s Layout-picker section is stale.** `:251-253` documents accessibility identifiers `layout-picker.button` ("the toolbar button that opens the picker popover"), `layout-picker.row.<layoutName>`, and `menu.session.layout-picker`. **None of these strings exist anywhere in Swift source**, there is no toolbar button, and the picker is a `.sheet`, not a popover. Don't take that section as a description of the shipped UI; the invariants at `:227-238` are still accurate.
- **`PaneContentKind`'s own doc comment is stale.** `PaneContentKind.swift:23-27` says *"`.terminal` is the only kind that renders real content today. Every other case renders as a deliberately provisional placeholder"* — written for `#0315`, superseded by the `#0304`/`#0305`/`#0313`/`#0314` merges. `PaneView.swift:92-95` now switches all four non-terminal kinds to real views. `Concepts.md:63` carries the same stale claim. Worth correcting in passing.
- **`kind` decodes leniently to `.terminal`** when absent (`LayoutModel.swift:30-40`). A saved-Workspace format that omits a slot's kind will silently produce a Terminal rather than failing — decide whether that is the wanted behavior for this file or whether the topology format should be strict.
- **Per-variant Application Support directory.** `#0279`: Prod and Beta both resolved the same directory and clobbered each other's JSON via last-writer-wins whole-file saves. `SessionNameCache.resolvedDirectoryName(bundleIdentifier:)` (`:93-102`) is the fix; any new store must do the same.
- **The two illustrations in the request differ.** "a terminal on the top with 2 below it" (first message) vs. "1 pane on top split with 3 panes below" (clarification). Neither is the spec; the default set is a design decision.
