# 0710 — An agent can't resume waiting on a command once a `--wait` call returns, and can't ask a Pane's state

| **Target** | 1.5.0 |

## Description

Child of #0705. `pane split --wait` and `tab new --wait` return the command's exit status, but only to the call that started it. A command that waits on the user can run for minutes (a deploy, a login), longer than an MCP host's tool-call timeout or the `--timeout` the agent picked. Once that call returns `waitResult` timed out, nothing lets the agent wait again or find out later how the command ended.

## Expected behavior

- **`batty wait --tab <id> [--timeout S] [--json]`** and MCP **`tab_wait`** (name per the catalog's conventions): blocks until the command started in that Tab with `--command` exits and returns `exitCode`, `durationMs`, `waitResult` in the same shape `--wait` uses; returns immediately if it already exited. Times out cleanly, so it can be called again.
- **`batty pane state --pane <id> [--json]`** (or `tab state`) and MCP **`pane_state`**: whether the Tab's command is running or exited, its exit status, and, if #0709 ships detection, whether it is waiting for input.
- Exit status is retained for exited commands in Tabs that are still open, so a later query can read it.

## Acceptance criteria

1. Start with `--wait --timeout 1` on a slow command, let it time out, then `batty wait --tab <id>` returns the real exit status.
2. `wait` on an already-exited command returns at once; on a Tab with no `--command`, or an unknown id, it fails with the CLI's usual error and exit codes.
3. MCP tools have accurate descriptions stating that they only observe and never send input.
4. BattyKitTests cover the retained-status store and the CLI/MCP payloads.

## Relation

- Umbrella #0705; after #0709 so `pane_state` can include waiting-for-input. `docs/batty-cli-design.md` lists `batty wait <idle|done|blocked>` as deferred; this is the narrow command-exit form of it.
