# 0287 — Batty creates one ghostty_app_t per Tab, defeating Ghostty's shared glyph-atlas cache

| | |
|---|---|
| **Status** | open |
| **Module** | GhosttyKit |
| **Platform** | macOS |
| **First seen** | 2026-07-31 |

## Description

**The premise of this issue is now in tension with live measurement, and the settling experiment below is a hard gate before any refactor.** Both readings are recorded here; neither is silently discarded.

**The source-trace reading** (`issues/0285/investigation-source.md` §5): every Tab gets its own `ghostty_app_t`, and Ghostty's `App` owns `font.SharedGridSet` — the reference-counted shared glyph-atlas cache (symbols `.ref` / `.deref` / `.collection` confirmed in the vendored binary) — so N Tabs means N private atlas sets and zero sharing. The investigation put ~80% confidence on the per-App ownership edge, which could not be confirmed from the stripped static library.

**The live-measurement reading** (`issues/0285/investigation-live.md` §H2): atlases are confirmed **not shared** — 93 regions of exactly 1040 K (1024²×1 B grayscale + one 16 K page) and 94 of exactly 272 K (256²×4 B color + one 16 K page), byte-identical across samples. But the count is **3 × the layer count, not 1 per `ghostty_app_t`**: 93 atlases for 31 layers, i.e. per-surface instances replicated across the 3 frames in flight. If the atlas were owned per-`App` as the source trace inferred, ~26–31 would be expected, not 93. **On that arithmetic, consolidating controllers may not collapse the atlases at all** — the ownership looks per-*surface*.

**Payoff recalibration:** total glyph atlas is **119 MB of the 1090 MB graphics footprint (11%)** on the measured instance — real, but not the dominant chunk the source trace implied. The dominant costs scale with layer count (see #0288).

**Hard gate — run before any refactor:** open one new Tab against a running instance and check whether the 1040 K atlas count rises by **3** (per-surface ownership — this refactor won't reduce atlas memory) or by **0** (shared within the App — the refactor helps). The census command is in #0291 / `investigation-live.md` § Reproduction recipe. If the answer is "rises by 3", re-scope this issue: the app-per-Tab consolidation may still be worth doing for App-scoped threads and general hygiene, but its atlas claim is dead and the atlas duplication becomes an upstream (libghostty) issue.

**The code chain** (unchanged, all in Batty/wrapper source):

- `TabRuntime.init` unconditionally constructs a fresh `TerminalViewState` (`TabRuntime.swift:99`)
- → whose `init` unconditionally constructs a fresh `TerminalController` (`TerminalViewState.swift:76-84`)
- → whose `init` unconditionally calls `createApp()` (`TerminalController.swift:155`)
- → `ghostty_app_new` (`TerminalController+Config.swift:82`).

The shared-controller entry points already exist and are unused: `TerminalController.shared` (`TerminalController.swift:46`) and `TerminalViewState.init(controller:)` (`TerminalViewState.swift:86-88`).

**Why the per-Tab app exists today:** per-Tab state is expressed through the *controller's* config — the `BATTY_TAB_ID` / `BATTY_PANE_ID` / `BATTY_SESSION_ID` env vars, the `-c` command override, and `wait-after-command` (`TabRuntime.swift:143-209`). Those are controller-wide, so a naive shared controller would apply one Tab's env to all of them.

**Approach, if the gate passes** (after the #0286 bump to libghostty-spm 1.3.2): route ordinary Tabs through one shared `TerminalController`, moving `BATTY_TAB_ID` / `BATTY_PANE_ID` / `BATTY_SESSION_ID` from controller config into per-surface `TerminalSurfaceOptions.envVars` (new in 1.3.2). Keep a dedicated controller only for `-c` panes, which still need controller-level `command` + `wait-after-command` (see #0292; not a blocker).

## Expected behavior

If the gate shows atlas sharing within an App: ordinary Tabs share one `ghostty_app_t` (one `TerminalController`), atlas count stops scaling with Tab count, per-Tab identity env vars travel per-surface, `-c` panes keep working on dedicated controllers.

Acceptance **must include a measured before/after** showing the 1040 K / 272 K atlas region counts no longer scaling per Tab (measure with the #0291 census — region counts by size class, never RSS or footprint totals alone; see the umbrella's measurement trap).

## Actual behavior

One `ghostty_app_t` per Tab; 93 grayscale atlases + 94 color atlases for 26 Terminal Sessions on the measured instance (3.85 MB of unshared atlas per session); the 1040 K atlas count exactly tracks the IOSurface count (layers × 3).

## Notes

The two readings disagree on *ownership*, not on *duplication* — both agree no atlas is shared between two Terminal Sessions today. What the gate decides is whether the duplication is caused by Batty's app-per-Tab choice (fixable here) or by per-surface allocation inside Ghostty's renderer (an upstream issue regardless of how many Apps exist).

Secondary benefit that survives either outcome: consolidating controllers collapses any App-scoped or font-shaper-scoped threads from per-Tab to shared (live instance: 4.8 threads per Terminal Session, all created by Ghostty, multiplied by app-per-Tab).

**The gate experiment can run against the Beta build** — no need to touch the user's release instance: scheme `Batty (Beta)`, bundle id `co.sstools.Batty.beta` (`Configuration/Beta.xcconfig:4`), built with `SCHEME="Batty (Beta)" scripts/build.sh`; its distinct bundle id gives it separate UserDefaults and workspace persistence, so it can be launched, driven, and killed freely. Launch it, open a Tab, run the 1040 K atlas census, open one more Tab, run it again.
