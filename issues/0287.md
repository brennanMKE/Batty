## Description

**The premise of this issue is now in tension with live measurement, and the settling experiment below is a hard gate before any refactor.** Both readings are recorded here; neither is silently discarded.

**The source-trace reading** (`issues/0285/investigation-source.md` §5): every Tab gets its own `ghostty_app_t`, and Ghostty's `App` owns `font.SharedGridSet` — the reference-counted shared glyph-atlas cache (symbols `.ref` / `.deref` / `.collection` confirmed in the vendored binary) — so N Tabs means N private atlas sets and zero sharing. The investigation put ~80% confidence on the per-App ownership edge, which could not be confirmed from the stripped static library.

**The live-measurement reading** (`issues/0285/investigation-live.md` §H2): atlases are confirmed **not shared** — 93 regions of exactly 1040 K (1024²×1 B grayscale + one 16 K page) and 94 of exactly 272 K (256²×4 B color + one 16 K page), byte-identical across samples. But the count is **3 × the layer count, not 1 per `ghostty_app_t`**: 93 atlases for 31 layers, i.e. per-surface instances replicated across the 3 frames in flight. If the atlas were owned per-`App` as the source trace inferred, ~26–31 would be expected, not 93. **On that arithmetic, consolidating controllers may not collapse the atlases at all** — the ownership looks per-*surface*.

**Payoff recalibration:** total glyph atlas is **119 MB of the 1090 MB graphics footprint (11%)** on the measured instance — real, but not the dominant chunk the source trace implied. The dominant costs scale with layer count (see #0288).

**Hard gate — run before any refactor:** open one new Tab against a running instance and check whether the 1040 K atlas count rises by **3** (per-surface ownership — this refactor won't reduce atlas memory) or by **0** (shared within the App — the refactor helps). The census command is in #0291 / `investigation-live.md` § Reproduction recipe. If the answer is "rises by 3", re-scope this issue: the app-per-Tab consolidation may still be worth doing for App-scoped threads and general hygiene, but its atlas claim is dead and the atlas duplication becomes an upstream (libghostty) issue.

**The code chain** (unchanged, all in Batty/wrapper source):

- `TabRuntime.init` unconditionally constructs a fresh `TerminalViewState` (`TabRuntime.swift:99`)
- → whose `init` unconditionally constructs a fresh `TerminalController` (`TerminalViewState.swift:76-84`)
- → whose `init` unconditionally calls `createApp()` (`TerminalController.swift:155`)
- → `ghostty_app_new` (`TerminalController+Config.swift:82`).

The shared-controller entry points already exist and are unused: `TerminalController.shared` (`TerminalController.swift:46`) and `TerminalViewState.init(controller:)` (`TerminalViewState.swift:86-88`).

**Why the per-Tab app exists today:** per-Tab state is expressed through the *controller's* config — the `BATTY_TAB_ID` / `BATTY_PANE_ID` / `BATTY_SESSION_ID` env vars, the `-c` command override, and `wait-after-command` (`TabRuntime.swift:143-209`). Those are controller-wide, so a naive shared controller would apply one Tab's env to all of them.

**Approach, if the gate passes** (after the #0286 bump to libghostty-spm 1.3.2): route ordinary Tabs through one shared `TerminalController`, moving `BATTY_TAB_ID` / `BATTY_PANE_ID` / `BATTY_SESSION_ID` from controller config into per-surface `TerminalSurfaceOptions.envVars` (new in 1.3.2). Keep a dedicated controller only for `-c` panes, which still need controller-level `command` + `wait-after-command` (see #0292; not a blocker).

## Resolution notes

> 🟡 Resolved 2026-08-01 — **the gate refuted the premise. The refactor was not done and should not be done.** Recommend closing as won't-implement.

This issue proposed routing ordinary Tabs through a single shared `TerminalController`. It was deliberately gated on settling atlas ownership first, because a source trace and a live measurement disagreed. The gate ran; the atlas rationale is dead. No production code changed — the only deliverable is the experiment that settles it, plus this record.

## Root cause

The premise, not the code. The source trace inferred that Ghostty's `App` owns the `font.SharedGridSet` glyph-atlas cache — so one `ghostty_app_t` per Tab would defeat sharing and waste ~119 MB. It self-labelled that at ~80% confidence, unconfirmable from a stripped library, and "cheap to settle." The live measurement pointed the other way: 93 atlas regions for 31 layers, exactly 3 per *surface*. Because the measured instance ran one app per Tab, app count and surface count moved together and the data could not distinguish the two readings.

## Fix

No fix — a measurement.

**What was measured.** A committed in-process experiment (`BattyKit/Tests/BattyKitTests/AtlasOwnershipExperimentTests.swift`) holds the `ghostty_app_t` constant and varies only the surface count — the separation the originally-proposed Beta-build census could not achieve, because opening a Tab there creates an App and a surface together. One real `TerminalController` is created, then three real `ghostty_surface_t` surfaces are attached to *that same controller*, each on its own offscreen `NSWindow`/`AppTerminalView` so the production `viewDidMoveToWindow` path drives surface creation. `IOAccelerator (graphics)` regions of exactly 1040 K — the grayscale-atlas signature from `issues/0285/investigation-live.md` §H2 — are counted between steps.

**Result: the count grows with every surface added to an already-live App, plateauing at exactly 3 regions per surface (9 for 3), with the 272 K color atlas tracking identically.** Per-App ownership of the measured memory would have predicted zero growth for surfaces two and three. It matches the live instance exactly (96 atlas regions / 32 layers = 3.00).

**What it means: the 119 MB of glyph-atlas memory is per-surface renderer-side texture, allocated inside libghostty's per-surface Metal setup — not a per-App cache that Batty's Tab lifecycle controls. Routing ordinary Tabs through one shared `TerminalController` would not reclaim any of it.**

This does **not** disprove that `font.SharedGridSet` itself is App-owned. `SharedGridSet` is the CPU-side font-grid cache; `vmmap`'s `IOAccelerator` regions are GPU-visible texture memory. Each surface's Metal renderer may upload its own texture copy regardless of whether the CPU-side grid is shared — so both readings can be true at once. Either way the refactor's atlas rationale is dead, and the duplication is an upstream concern (see #0293).

## Review

Reviewed by claude-opus-5, approved first pass, having verified the experiment rather than the claim.

It confirmed the harness genuinely shares one app — `ghostty_app_new` has exactly one call site in the wrapper, `createSurface` opens with `guard let app else { return nil }` with no fallback and no `TerminalController.shared` path, and `TerminalViewState.init(controller:)` only stores the reference — so the "second app created implicitly" trap was avoided. It validated the counting predicate against the live process (harness predicate and the §H2 regex both return 96 on pid 9870 — exactly equivalent). It confirmed the in-memory backend changes nothing (`configureBackend` switches only `config.backend`; the in-memory surfaces produce the identical signature at the identical ratio as the live PTY-backed instance).

It also **explained the +2/+3 asymmetry** by sampling the test process externally: the trajectory is `0 → 2 → 3 → 6 → 9`, plateauing at exactly 9. The committed table's 0/2/5/8 is a sampling-phase artifact — each sample lands right after a 0.3 s pump when the newest surface has allocated 2 of its eventual 3 regions, and the third is credited to the next delta. Not perturbation; the steady state is 3.00 per surface.

## Gotchas

- **Untested — the App-scoped thread question.** The experiment says nothing about threads. The live instance showed ~4.8 threads per Terminal Session, all created by Ghostty and multiplied by app-per-Tab. Whether consolidating onto one controller collapses any of them was never measured, and the ceiling looks small (~2.8 MB of stack dirty pages across 125 threads). If that lever is worth chasing it needs its own measurement first — do not resurrect the refactor on this rationale without one.
- **Only GPU regions were counted.** Any malloc-side per-App cost (`ghostty_config_t`, the CPU-side `SharedGridSet`) is invisible to this experiment.
- **The experiment measures growth, never release.** It cannot distinguish "bounded per-surface cost" from "never reclaimed" — the same gap `investigation-live.md` flags for layers.
- **The committed table (0/2/5/8) is timing-dependent**; the steady state is 3 per surface. The test asserts `> 0` growth rather than exact deltas, which is the right call given the phase artifact.
- **This is the slowest test in the suite** (~5.8 s) and shells out to `vmmap` four times. `#require(state.surface != nil)` would fail rather than skip on a GPU-less host — fine for this project's hardware, but worth knowing if CI ever moves.

## Gate result (2026-08-01)

**The gate is settled: atlas ownership is per-surface, not per-App. The refactor's atlas claim is dead.**

Ran the decisive experiment in-process rather than against the Beta build, which turned out to be both cheaper and more conclusive: a Beta-build before/after (per the issue's original recipe) can't separate "new surface" from "new App" because opening a Tab always creates both together in the current code. An in-process unit test can hold the App constant and vary only the surface count.

**Method.** `BattyKit/Tests/BattyKitTests/AtlasOwnershipExperimentTests.swift` (committed) creates one real `TerminalController` (one `ghostty_app_t`) and attaches three real `ghostty_surface_t` surfaces to it — via the sandbox-safe in-memory I/O backend (`GHOSTTY_SURFACE_IO_BACKEND_HOST_MANAGED`, no PTY, no subprocess), each on its own offscreen `NSWindow`/`AppTerminalView` so `viewDidMoveToWindow` drives the same production surface-creation path `TerminalHostStore` uses. Between each surface it shells out to `/usr/bin/vmmap` against its own pid and counts `IOAccelerator (graphics)` regions of exactly `1040K` — the same grayscale-atlas signature `investigation-live.md` §H2 identified. `swift test --filter AtlasOwnershipExperimentTests` runs it standalone in ~5-6 s; it's also part of the normal `BattyKitTests` suite now (821 tests / 98 suites, up from 820/97).

**Measured (3 consecutive runs, byte-identical every time):**

| step | atlas (1040K) count | delta |
|---|---|---|
| baseline (no controller) | 0 | — |
| + surface A (new controller) | 2 | +2 |
| + surface B (**same** controller as A) | 5 | **+3** |
| + surface C (**same** controller as A, B) | 8 | **+3** |

Surface A's App and surface are both new, so its +2 can't isolate ownership. Surfaces B and C are the isolating cases: they attach to a controller that already has a live App and an existing atlas, and each **still allocates its own new atlas set** — +3 apiece, matching the live measurement's exact 3x-per-layer ratio (`investigation-live.md` §H2, 93 regions / 31 layers). If the atlas were owned by the App, B and C would have added 0. They didn't, reproducibly.

**Implication for the refactor:** routing ordinary Tabs through one shared `TerminalController` would **not** collapse glyph-atlas memory — each surface keeps allocating its own 1024² grayscale + 256² color atlas regardless of how many surfaces share an App. The atlas duplication is inside libghostty's per-surface renderer setup, not Batty's app-per-Tab choice. This confirms the source trace's ~80%-confidence inference was the wrong edge of the two readings; the live measurement's 3x-per-layer ratio was the accurate signal, just previously confounded.

**What the 119 MB actually is, and other levers:**

- It's `font.SharedGridSet`-adjacent Metal descriptor state allocated per `ghostty_surface_t` at surface-creation/first-render time (1024×1024×1 B + 16 K page grayscale, 256×256×4 B + 16 K page color), not a per-App cache that Batty's Tab lifecycle controls.
- The only levers that could shrink it are all upstream (libghostty-spm / libghostty itself): (a) an actual shared-atlas implementation keyed by font+size across surfaces within a process — the biggest possible win, but a real rendering-architecture change upstream, not a wrapper-level config; (b) a smaller atlas allocation for surfaces that don't need the full glyph coverage (e.g. hidden/background Tabs), which would need a new C API — nothing in `ghostty.h` currently exposes atlas sizing; (c) freeing/reusing atlas memory for occluded surfaces, which is what #0293 already tracks for the render-texture side and could plausibly extend to atlases if #0293's upstream ask lands.
- Given 119 MB / 1090 MB = 11%, and #0288 already addressed the larger layer-scaled cost (700 MB) by stopping non-visible Tabs from rendering, there's no Batty-side code change left to try here — reducing this further is entirely an upstream ask.

**Recommendation: re-scope or close.** Per the issue's own gate language: the atlas-sharing rationale for a shared-controller refactor is refuted. The secondary rationale — collapsing App-scoped/font-shaper-scoped threads from per-Tab to shared (4.8 threads/session on the live instance, multiplied by app-per-Tab) — still stands and wasn't tested here, but that's a much smaller, general-hygiene win, not the ~30%+-of-footprint payoff the issue originally described. Given #0286 (the libghostty-spm 1.3.2 bump this refactor also depends on) hasn't landed and the atlas payoff is gone, this doesn't look worth a full shared-controller refactor on its own — recommend closing with the atlas duplication redirected to an upstream/#0293-adjacent note, or re-scoping to a much smaller "collapse threads only" issue if the thread count is independently worth chasing. Leaving the status/close decision to the user per the project's never-infer-resolution rule.

## Notes

The two readings disagree on *ownership*, not on *duplication* — both agree no atlas is shared between two Terminal Sessions today. What the gate decides is whether the duplication is caused by Batty's app-per-Tab choice (fixable here) or by per-surface allocation inside Ghostty's renderer (an upstream issue regardless of how many Apps exist). **Settled 2026-08-01: per-surface, not per-App — see Gate result above.**

Secondary benefit that survives either outcome: consolidating controllers collapses any App-scoped or font-shaper-scoped threads from per-Tab to shared (live instance: 4.8 threads per Terminal Session, all created by Ghostty, multiplied by app-per-Tab).

**The gate experiment can run against the Beta build** — no need to touch the user's release instance: scheme `Batty (Beta)`, bundle id `co.sstools.Batty.beta` (`Configuration/Beta.xcconfig:4`), built with `SCHEME="Batty (Beta)" scripts/build.sh`; its distinct bundle id gives it separate UserDefaults and workspace persistence, so it can be launched, driven, and killed freely. Launch it, open a Tab, run the 1040 K atlas census, open one more Tab, run it again.
