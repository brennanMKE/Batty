# 0287 — Batty creates one ghostty_app_t per Tab, defeating Ghostty's shared glyph-atlas cache

| | |
|---|---|
| **Status** | open |
| **Module** | GhosttyKit |
| **Platform** | macOS |
| **First seen** | 2026-07-31 |

## Description

Every Tab gets its own `ghostty_app_t`. Ghostty's `App` owns `font.SharedGridSet` — the reference-counted shared glyph-atlas cache (symbols `.ref` / `.deref` / `.collection` confirmed present in the vendored binary) — so N Tabs means N private atlas sets and **zero atlas sharing** between Terminal Sessions. With 111 open Terminal Sessions that is 111 independent font-grid sets and 111 independent glyph atlases. This is the single best explanation for the #0285 measurements of **2,651 IOAccelerator regions averaging 0.53 MB (~1.4 GB)**, and for the footprint growing **+277 MB during pure scrolling** with no Pane/Tab lifecycle events: atlas growth is content-driven, not frame-driven, so scrolling novel content grows all the atlases in parallel and never gives the memory back. This is the headline fix of the umbrella.

The chain is unambiguous and entirely in Batty/wrapper source:

- `TabRuntime.init` unconditionally constructs a fresh `TerminalViewState` (`TabRuntime.swift:99`)
- → whose `init` unconditionally constructs a fresh `TerminalController` (`TerminalViewState.swift:76-84`)
- → whose `init` unconditionally calls `createApp()` (`TerminalController.swift:155`)
- → `ghostty_app_new` (`TerminalController+Config.swift:82`).

The shared-controller entry points already exist and are unused: `TerminalController.shared` (`TerminalController.swift:46`) and `TerminalViewState.init(controller:)` (`TerminalViewState.swift:86-88`).

**Why the per-Tab app exists today:** per-Tab state is expressed through the *controller's* config — the `BATTY_TAB_ID` / `BATTY_PANE_ID` / `BATTY_SESSION_ID` env vars, the `-c` command override, and `wait-after-command` (`TabRuntime.swift:143-209`). Those are controller-wide, so a naive shared controller would apply one Tab's env to all of them.

**Approach** (after the #0286 bump to libghostty-spm 1.3.2): route ordinary Tabs through one shared `TerminalController`, moving `BATTY_TAB_ID` / `BATTY_PANE_ID` / `BATTY_SESSION_ID` from controller config into per-surface `TerminalSurfaceOptions.envVars` (new in 1.3.2). Keep a dedicated controller only for `-c` panes, which still need controller-level `command` + `wait-after-command` — the wrapper cannot express those per-surface yet (see #0292; `-c` panes are rare and few, so this does not block the win).

## Relation

- Child of umbrella #0285.
- **Depends on #0286** (libghostty-spm 1.3.2 bump — supplies `TerminalSurfaceOptions.envVars`).
- #0292 tracks the upstream wrapper gap (`command` / `wait_after_command` per-surface) that would let `-c` panes join the shared controller too; it is explicitly **not** a blocker for this issue.
- The measurement harness in #0291 supplies the experiment that confirms or refutes this issue's premise (does IOAccelerator region count scale linearly per Tab from Tab #2 onward).

## Expected behavior

Ordinary Tabs share one `ghostty_app_t` (one `TerminalController`), so glyph atlases are shared across Terminal Sessions. Per-Tab identity env vars travel per-surface. `-c` panes keep working on dedicated controllers.

Acceptance **must include a measured before/after** showing IOAccelerator region count no longer scaling per Tab (measure with `phys_footprint`-based tooling, never RSS — see the umbrella's measurement trap).

## Actual behavior

One `ghostty_app_t` per Tab; every Terminal Session pays for its own glyph atlases; IOAccelerator regions scale with Tab count.

## Notes

**Open risk, recorded honestly:** that `App` owns `SharedGridSet` is Ghostty's documented architecture, and the type and its `.ref`/`.deref`/`.collection` symbols are confirmed present in the vendored binary — but the *ownership edge* could not be confirmed from a stripped static library. If the set turned out to be process-global in this Ghostty revision, this finding collapses to "N apps is wasteful but not the 1.4 GB". The source investigation puts ~**80% confidence** on the per-App reading. It is cheap to settle empirically: open N Tabs and observe whether IOAccelerator region count scales linearly from Tab #2 onward (linear scaling supports per-App atlases; a large fixed cost plus small per-Tab increments refutes it). Run that measurement (via #0291's harness or by hand) before or at the start of the refactor.

A secondary benefit: any App-scoped or font-shaper-scoped threads also collapse from per-Tab to shared (the investigation counted ~6 threads per Terminal Session, all created by Ghostty, multiplied by Batty's app-per-Tab choice).
