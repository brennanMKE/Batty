## Description

**Related to #0620.** #0620 moved the layout-probe fixtures onto `TestClock`. In `SystemMetricsPaneContentTests`, 17 of the 21 tests still start `SystemMetricsPaneContent`'s background sampling loop on the default `SystemClock()`. The loop ticks once right away, then every `sampleInterval` (1 s) of real time. These tests drive their own ticks with `refreshNow()` / `performTick()` and assert on sample counts, sampler counts or the snapshot. If a test suspends for more than 1 s under heavy host load, a real loop tick can land between its steps and add a sample it did not plan. #0620 recorded this in its `## Gotchas` and saw no flake from it.

Goal: every `SystemMetricsPaneContentTests` test that starts the loop injects a `TestClock`. The only ticks are then the ones the test drives, or the loop's first tick, which the test accounts for explicitly (`docs/async-test-seams.md` §1). Apply the same rule to the other status-pane content tests wherever they have the same gap (see Notes).

## Notes

- **The loop's first tick needs the planner's attention.** Those `sampleCallCount == 1` assertions pass today, so the loop's immediate first tick evidently doesn't run before them when the `@MainActor` `FakeSystemMetricsSampler` is in use. This is inferred, not traced: the test probably never truly suspends, so the loop task only runs after the test body. Tests whose sampler really hops executors (`ThreadRecordingSampler`, `GatedSampler`, both actors) do let the loop's first tick run mid-test, and `GatedSampler`'s doc comment says so. Switching to `TestClock` removes the 1 s re-ticks. It does not remove that first tick. A test that waits for the loop to park (`#expect(await clock.waitForSleepers(1))`, as `samplingLoopTicksOnlyWhenItsClockAdvances` does) will see that tick counted, so its expected counts must change to match. The planner should go through each test, not just swap the clock.
- Simplest change: give `makeContent` a `clock: SchedulingClock = TestClock()` parameter, as `GitStatusPaneContentTests.makeContent` does, and pass `TestClock()` in the four direct constructions. Adding `defer { content.tearDown() }` would end each loop in the test that started it.
- **The other status-pane content tests, checked:**
  - `ProcessStatusPaneContentTests`: every `async` test injects a `TestClock` (`samplingStopsWhileSuspendedAndResumesWhenShown`, `exitedBannerStillShowsLastSampleTime`, `repeatedUnavailableTicksDoNotRenotifyLastSeenReaders`, `cpuPercentReflectsSubstantialRealCoreUsage`). Many synchronous tests call `setUp(visible: true)` on the default `SystemClock()`. A synchronous `@MainActor` test never suspends, so the loop cannot tick during it. Those tests do leave a loop behind that samples a real pid until the content is released. That wastes some work but cannot flake the test. Moving them onto `TestClock` is optional cleanup.
  - `LMStudioDashboardPaneContentTests`: every test that starts the content sets `content.clock = TestClock()`. The only two that don't (`freshlyConstructedContentIsNotSetUpAndDoesNothing`, `tearDownFromNotSetUpIsSafeAndIdempotent`) never call `setUp`. No gap.
  - `GitStatusPaneContentTests`: `makeContent` defaults `clock` to `TestClock()`. `GitStatusPaneContent` has no periodic sampling loop; its clock drives the debounce and the teardown grace. Outside that file, `ProjectOpenTests` and `SplitTreeNonTerminalCWDTests` build `GitStatusPaneContent(directoryPath:)` only as factory content. No gap.
- Verification tier: fast (`./build.sh unit SystemMetricsPaneContentTests`, then the full `./build.sh unit`).

## Plan

Test-only change. No production code changes. One file: `BattyKit/Tests/BattyKitTests/SystemMetricsPaneContentTests.swift`.

### Premises checked against the code (2026-11-13)

- The issue's premises hold. `startActive()` runs `performTick()` first and then `clock.sleep(for: Self.sampleInterval)`, on whichever clock is injected.
- **Why the `sampleCallCount == 1` assertions pass today:** `FakeSystemMetricsSampler` is `@MainActor`. Calling its `sampleOnce()` from the `@MainActor` `performTick()` switches to the executor the test is already on, so it never actually suspends. The loop `Task`, which is also main-actor, can't run until the test body really suspends or returns. So the first loop tick of a fake-sampler test runs after the test body. Today that holds only because of how the executor switch works, and nothing in the tests pins it. The plan makes it explicit.
- **`defer { content.tearDown() }` is needed once the loop runs on a `TestClock`, not just tidier.** Inside the loop, `guard let self` binds `self` strongly for the whole iteration, including the `await clock.sleep(...)`. On `SystemClock` that sleep ends after 1 s and the loop drops the content. On a `TestClock` nobody advances, the sleep never ends, so the parked task would keep the content, its sampler and the ledger alive for the rest of the test process. `tearDown()` cancels the task, and `TestClock.sleep` resumes a cancelled sleeper at once, so the loop exits. When the defer runs before the loop's first iteration (fake-sampler sync tests), the task starts already cancelled and `while !Task.isCancelled` exits without ticking. `tearDown()` is idempotent and valid from `.active` and `.suspended`, per `tearDownIsIdempotent` and `PaneLifecycleController`.

### Approach

1. **`makeContent`** gets a third parameter, `clock: SchedulingClock = TestClock()`, as in `GitStatusPaneContentTests.makeContent`, and builds `SystemMetricsPaneContent(clock: clock)`. With this default, no test in the file runs on `SystemClock`, including the three that never start the loop (`createdHiddenNeverBuildsASamplerOrTicks`, `refreshNowIsANoOpWhileSuspended`, `snapshotStartsEmptyBeforeTheFirstTick`). Those three need no other change.
2. **The rule for the loop's first tick (decision):**
   - In an `async` test that asserts on samples, the test waits for the loop to park right after the `setUp(visible: true)` that starts it: `#expect(await clock.waitForSleepers(1))`. That is a real event. It returns after the loop's immediate first tick has sampled and the loop has parked on the clock. From then on, only ticks the test drives can land, so expected counts include that first tick on purpose.
   - In a test with no `await` between starting the loop and its assertions (every sync test, and `tearDownFromActiveStopsTicksSynchronously` up to its `tearDown()`), the loop can't run during the test. Those tests only get the clock and the defer, with no wait. They assert `createCount` or phase, which the loop's tick doesn't change, except `tearDownFromActive…`, covered below.
3. **Every test that starts the loop and doesn't already call `tearDown()` gets `defer { content.tearDown() }`** right after the content is built.

### ProcessStatus sync-test cleanup: declined (decision)

`ProcessStatusPaneContentTests` builds `ProcessStatusPaneContent(...)` directly at about 30 call sites and has no shared helper. Its loop sleeps *before* `guard let self`, so on `SystemClock` an abandoned loop wakes once, finds the content gone and exits: at most one extra real sample per test. On a `TestClock` with no `tearDown()`, each loop would instead park forever on a clock nobody advances. The sync tests can't suspend, so they can't flake from this. The swap would touch 30 call sites, and without a tearDown at each one it would trade a bounded 1 s of waste for tasks parked for good. Not worth it here. The implementer records this in `## Gotchas`. No other status-pane test file has the gap; see Notes.

## Resolution

`SystemMetricsPaneContentTests` no longer runs any test on `SystemClock`. `makeContent` takes `clock: SchedulingClock = TestClock()`, and the four direct constructions pass `TestClock()`. Every loop-starting test that did not already tear down gets `defer { content.tearDown() }`, so no loop stays parked on an unadvanced clock. The async tests that assert on samples wait for the loop to park (`#expect(await clock.waitForSleepers(1))`) and count its first tick explicitly: `createdVisibleBuildsASamplerAndTicks` 1 then 2, `hidingAnActivePaneStopsTicksImmediately` 2 (plus `pendingCount == 0` after the hide and `advance` firing 0), `refreshNowSamplesImmediatelyWhileActive` 2. `tearDownFromActiveStopsTicksSynchronously` gets a comment explaining why its zero holds. Test-only; no production changes.
