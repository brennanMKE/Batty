## Description

**Related to #0620.** #0620 moved the layout-probe fixtures onto `TestClock`. In `SystemMetricsPaneContentTests`, 17 of the 21 tests still start `SystemMetricsPaneContent`'s background sampling loop on the default `SystemClock()`. The loop ticks once right away, then every `sampleInterval` (1 s) of real time. These tests drive their own ticks with `refreshNow()` / `performTick()` and assert on sample counts, sampler counts or the snapshot. If a test suspends for more than 1 s under heavy host load, a real loop tick can land between its steps and add a sample it did not plan. #0620 recorded this in its `## Gotchas` and saw no flake from it.

Goal: every `SystemMetricsPaneContentTests` test that starts the loop injects a `TestClock`. The only ticks are then the ones the test drives, or the loop's first tick, which the test accounts for explicitly (`docs/async-test-seams.md` §1). Apply the same rule to the other status-pane content tests wherever they have the same gap (see Notes).

## Verified premises (2026-11-13, against `main` at the #0620 squash)

- `BattyKit/Sources/BattyKit/Runtime/SystemMetricsPaneContent.swift`: `public init(clock: SchedulingClock = SystemClock())`. `startActive()` runs `while !Task.isCancelled { await self.performTick(); await clock.sleep(for: Self.sampleInterval) }`. The first tick happens immediately, before any sleep, whichever clock is injected.
- `BattyKit/Tests/BattyKitTests/SystemMetricsPaneContentTests.swift` has 21 `@Test`s:
  - The `makeContent(ledger:processes:)` helper builds `SystemMetricsPaneContent()` on the real clock. `sweepRunsOffTheMainActor` and the three `sampleCompletingAfter…` tests build it directly, also on the real clock.
  - 17 tests start the loop with `setUp(visible: true)` or `setVisible(true)`: `tickPublishesProcessesSortedByTheCurrentSort`, `changingTheSortResortsWithoutSampling`, `sortIsKeptAcrossTicks`, `settingTheSameSortDoesNotNotifyProcessReaders`, `sortSurvivesHideAndShow`, `createdVisibleBuildsASamplerAndTicks`, `hidingAnActivePaneStopsTicksImmediately`, `showingASuspendedPaneBuildsAFreshSamplerAndRefreshesImmediately`, `hideThenShowDiscardsTheOldSamplerAndBuildsAFreshOne`, `redundantShowDoesNotRebuildTheSampler`, `tearDownFromActiveStopsTicksSynchronously`, `tearDownIsIdempotent`, `refreshNowSamplesImmediatelyWhileActive`, `sweepRunsOffTheMainActor`, `sampleCompletingAfterHideIsDiscarded`, `sampleCompletingAfterTearDownIsDiscarded`, `sampleCompletingAfterHideThenReshowIsDiscardedNotAppliedToTheNewGeneration`.
  - Three tests use the real clock but never start the loop: `createdHiddenNeverBuildsASamplerOrTicks`, `refreshNowIsANoOpWhileSuspended`, `snapshotStartsEmptyBeforeTheFirstTick`.
  - Only `samplingLoopTicksOnlyWhenItsClockAdvances` injects a `TestClock`.
  - Count-sensitive examples: `changingTheSortResortsWithoutSampling` captures `ledger.sampleCallCount` after `refreshNow()`, then asserts it is unchanged after `setProcessSort`. `createdVisibleBuildsASamplerAndTicks` and `refreshNowSamplesImmediatelyWhileActive` assert `sampleCallCount == 1`. `hidingAnActivePaneStopsTicksImmediately` asserts that only the one tick before the hide counted.
  - Only the `tearDown…` tests call `tearDown()`. In every other test the loop holds `self` weakly and stops at its next wake after the content is released.
- The probe fixtures in `StatusPaneLayoutConvergenceTests.swift` already use `SystemMetricsPaneContent(clock: TestClock())` (#0620).

## Notes

- **The loop's first tick needs the planner's attention.** Those `sampleCallCount == 1` assertions pass today, so the loop's immediate first tick evidently doesn't run before them when the `@MainActor` `FakeSystemMetricsSampler` is in use. This is inferred, not traced: the test probably never truly suspends, so the loop task only runs after the test body. Tests whose sampler really hops executors (`ThreadRecordingSampler`, `GatedSampler`, both actors) do let the loop's first tick run mid-test, and `GatedSampler`'s doc comment says so. Switching to `TestClock` removes the 1 s re-ticks. It does not remove that first tick. A test that waits for the loop to park (`#expect(await clock.waitForSleepers(1))`, as `samplingLoopTicksOnlyWhenItsClockAdvances` does) will see that tick counted, so its expected counts must change to match. The planner should go through each test, not just swap the clock.
- Simplest change: give `makeContent` a `clock: SchedulingClock = TestClock()` parameter, as `GitStatusPaneContentTests.makeContent` does, and pass `TestClock()` in the four direct constructions. Adding `defer { content.tearDown() }` would end each loop in the test that started it.
- **The other status-pane content tests, checked:**
  - `ProcessStatusPaneContentTests`: every `async` test injects a `TestClock` (`samplingStopsWhileSuspendedAndResumesWhenShown`, `exitedBannerStillShowsLastSampleTime`, `repeatedUnavailableTicksDoNotRenotifyLastSeenReaders`, `cpuPercentReflectsSubstantialRealCoreUsage`). Many synchronous tests call `setUp(visible: true)` on the default `SystemClock()`. A synchronous `@MainActor` test never suspends, so the loop cannot tick during it. Those tests do leave a loop behind that samples a real pid until the content is released. That wastes some work but cannot flake the test. Moving them onto `TestClock` is optional cleanup.
  - `LMStudioDashboardPaneContentTests`: every test that starts the content sets `content.clock = TestClock()`. The only two that don't (`freshlyConstructedContentIsNotSetUpAndDoesNothing`, `tearDownFromNotSetUpIsSafeAndIdempotent`) never call `setUp`. No gap.
  - `GitStatusPaneContentTests`: `makeContent` defaults `clock` to `TestClock()`. `GitStatusPaneContent` has no periodic sampling loop; its clock drives the debounce and the teardown grace. Outside that file, `ProjectOpenTests` and `SplitTreeNonTerminalCWDTests` build `GitStatusPaneContent(directoryPath:)` only as factory content. No gap.
- Verification tier: fast (`./build.sh unit SystemMetricsPaneContentTests`, then the full `./build.sh unit`).
