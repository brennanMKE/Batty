## Description

[#0551](0551.md) built the copying of a Shared Project's background image through an iCloud Drive folder, and it landed behind `sharedProjectImages`, on in Beta and off in Prod. No agent can run it against real iCloud Drive, so whether the design works at all is unproven. This issue finishes it: the user runs the real-Mac checks, the remaining gaps are closed, and the flag comes out. Child of [#0372](0372.md).

**The flag stays until U1 to U8 pass.** The items under "Can land before the checks" don't depend on them, but the flag removal, the Help text and the release-notes line do. Agents never read or list `~/Library/Mobile Documents`, and no build or test reaches it.

## The checks, which only the user can run

U1 to U8 are the "User checklist" table in the `## Plan` of [#0551](0551.md): two Macs on one Apple ID, both with iCloud Drive on, each running a `./build.sh package --sign` Beta. Routine builds, tests and the VM have no transport (`AppStateStore.defaultSharedImageTransport` needs the entitlement and a non-test process), so nothing else can stand in for them. Run U1 first. If a Project doesn't arrive at all, that is [#0503](0503.md)'s key-value backend, whose two-Mac sync is also unverified.

If a check fails, that table names what follows:

| Fails | Then |
|---|---|
| **U1 or U2** (Denied, or no prompt at all) | **Fallback A. The flag stays.** The transport becomes a ubiquity container, replacing only `ICloudDriveImageFolder` behind `SharedImageTransport`. Only the user can do the portal steps. Answer first whether changing a capability on an App ID affects installed builds. No one changes an App ID before then |
| **U2**, a Deny with no message | A bug here |
| **U3 or U4** | Fallback B: try the read path alone. If that fails too, Fallback A |
| **U5 or U6** | Fallback C: a neutral message after an hour |
| **U7 or U8** | A bug here |

Fallback A is scoped in #0551's Plan, and it needs its own plan once it is known to apply.

## Removing the flag

Only after the checks pass, and per `docs/feature-flags.md`. The list there is shorter than the work:

- **Delete** `BattyKit/Sources/BattyXPCCore/FeatureFlags.swift` and `FeatureFlagsTests`, as #0544 did (`6d977630`). `sharedProjectImages` is the only flag. Also remove `AppStateStore.featureFlags`, its init parameter, the `FeatureFlags` parameter of `sharedImageTransportFactory`, and the `isEnabled:` parameter of `defaultSharedImageTransport`.
- **Keep the transport gate.** `defaultSharedImageTransport` still needs the entitlement and a non-test process.
- **`ProjectStore.sharedImagesEnabled` stays,** though `docs/feature-flags.md` lists it as a gate site. It means "has a transport" (`AppStateStore.swift:147`), and a routine build still has none, so records must stay unchanged there. For the same reason `sharedImagesOffChangesNoRecordOrFile`, `mergeWithSharedImagesOffLeavesTheImageAlone` and `recordWithSharedImagesOffIsByteIdenticalToToday` keep testing something real and stay. `defaultSharedImageTransportNeedsEntitlementFlagAndNoTests` loses its flag dimension.
- **Move the flag to "Retired flags"** in `docs/feature-flags.md`.

U1 to U8 run on Beta, so Prod's own folder (`iCloud Drive/Batty/Project Backgrounds/`, from `SessionNameCache.resolvedDirectoryName()`) and its own key-value store are first used by the release itself. The plan should say how the release's checks cover that.

## Can land before the checks

### Decide whether a user-initiated pass may ask again for a waiting download

**This needs a decision, from the user if the plan can't settle it.** Today, while a digest keeps waiting, it asks once per launch.

In `Model/SharedProjectImages.swift`, `download(digest:outcome:)` requests only if `requestedDownloads.insert(digest).inserted`. A digest leaves that set only when it arrives (`applyArrival`) or when no Project is waiting for it (`runPass`). So if iCloud Drive drops a requested download:

- **The image waits until the next launch.** The retry loop keeps calling `state`, at up to 15-minute intervals, but `.notDownloaded` makes no second request.
- **Reopening the Project doesn't help.** `reconcileSharedImage` runs a user-initiated pass, the digest is still waiting, and so it makes no request. Opening the Project Editor or saving the Project is the same.
- **Nothing says a relaunch is the way out.** The state sets no message. The caption keeps reading "Waiting for Harbor from iCloud Drive."
- **The only control in that state makes it worse.** **Don't Use This Image**, once saved, publishes `imageRemoved: true`, which clears the image on the user's other Macs.

A file that comes down another way, such as a download started in Finder, is still picked up on the next pass.

What the decision has to allow for:

- **User-initiated passes** come from opening a Project (including focusing one already open), the Project Editor opening or changing selection, `upsert` and `setShared`. Retry and activation passes aren't user-initiated, and must not start asking.
- **`anEvictedFileRequestsADownloadOnce` conflicts as written.** `SharedImageWorld.pass()` defaults to `userInitiated: true`, so the test's two passes are user-initiated. If re-asking is allowed, it should pin the once-only rule on background passes, and a new test should cover the user-initiated request.
- **The mismatch path shares the set.** `readAndStore` asks through `requestedDownloads` too, so a copy that fails verification, after one request, shows "doesn't match" and doesn't ask again.
- **Repeating the request** is called harmless in #0551's `## Review`. That rests on reading, not on a real Mac.
- **The alternative** to re-asking is to tell the user, after some time, that relaunching may help. The two aren't exclusive.

U4 doesn't exercise this exact case, and a dropped download can't be forced on demand, so the fake transport is where it can be tested.

### Add a scope test that drives `BackgroundImagesModel.add`

In #0551's review, adding a direct upload to `BackgroundImagesModel.add` failed no test. No unit test calls that method at all. `libraryImageIsNeverUploaded` calls `BackgroundImageLibrary.add` directly, and `aLibraryScanMakesNoTransportCall` calls `refresh`. By reading, `add` makes no upload today, since it only calls `library.add` and `refresh`.

Add a test to `SharedProjectImagesScopeTests` that calls `w.appStore.backgroundImages.add(from:)` with the fake transport, asserts that it returned an entry so it can't pass vacuously, and then asserts no transport call and no image keys in any record. Re-apply the mutation to confirm the test fails.

### Test the `sharedImagesAvailable` wiring

`ProjectEditorWindowController.swift:66` passes `store.sharedProjectImages != nil`, and no test covers that line. `noCaptionWhereNothingCanFetchTheImage` covers only the model. Removing the argument would hide the caption on every build and fail no test, and hard-coding it true would show a routine Beta a "Waiting for ..." that can never finish.

**#0551's `## Gotchas` says this can't be tested because "unit tests don't build that window". That is wrong.** `ProjectEditorTests` already calls `ProjectEditorWindowController().prepare(store:selecting:)` and reads `controller.model`. `AppStateStore.sharedImageTransportFactory` takes a fake before the first read of `projectStore`. So a test can select a pending Shared Project with and without a transport, and compare `controller.model?.sharedImageCaption`.

## Measure re-reading the shared copy

Every pass reads and hashes the whole shared copy of each digest being uploaded whose state is `.local` (`Model/SharedProjectImages.swift:198`), off the main actor. Passes run each time Batty becomes active (`didBecomeActiveNotification`) once `folderWasReached` is set, so this repeats on every switch to Batty. Reads are capped by `ICloudDriveImageFolder.maxFileBytes` at 100 MB.

Whether that costs too much is measured on real Macs, using a large image and several Shared Projects. Nothing in the coordinator or the transport logs timing today, so the plan has to say how it is measured.

Don't change this unmeasured. Remembering a verified digest would stop a shared copy damaged later from being repaired until relaunch, which #0551 relies on, so any change has to keep `aDamagedSharedCopyIsReplaced` passing.
