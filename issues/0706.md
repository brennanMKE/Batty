## Description

Child of #0705. When a command needs the user to answer it (a `[y/N]` confirmation, `sudo`, a password, an interactive login such as `gh auth login`, an ssh host-key question), an agent in a Batty Pane should run it in a new Pane the user can type into and tell the user what to answer. Nothing in Batty's agent-facing text names this case, so an agent finds it, if at all, after piping answers in or asking the user to run the command somewhere they can't type.

## Expected behavior

The same guidance, worded for each surface:

1. **MCP instructions** (`BattyKit/Sources/batty/MCPInstructions.swift`). Add a `Hint` gated on `pane_split` having `command` (and `wait`, if gated per argument): roughly "A command that needs the user's input (a y/N prompt, sudo, a password, a login): run it with `pane_split` `command` (`wait: true` to get its exit status) and tell the user what to answer. Never pipe or type an answer to a confirmation for the user."
2. **Skill** (`.claude/skills/batty-cli/SKILL.md`). Add the use case to the frontmatter `description` (it's what an agent host shows the model at all times, so it decides whether the skill loads) and a short section with an example using `pane split -v --command … --wait --json`.
3. **`batty capabilities`**. The `pane split` one-liner mentions that it can run a command, with `--wait` for its exit status. Today it reads only "Split the calling/target pane, printing the new pane's id."
4. **Docs**: `docs/batty-cli-agent-workflows.md` gains the workflow.

## Acceptance criteria

1. All four surfaces carry the guidance, including "never answer a confirmation for the user".
2. The MCP hint drops out when `pane_split` lacks `command`, like the existing hints (tested through `applicableHints`).
3. The skill's `description` names interactive input explicitly.
4. Existing tests that pin the instructions text and the capabilities output are updated, not deleted.
