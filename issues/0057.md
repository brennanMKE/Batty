# 0057 — New sessions should inherit the focused pane's working directory

## Description

When a new session is created (sidebar "+" button, `Cmd-Option-N`, or `AppStateStore.addSession()` programmatically), the new session's single starter tab spawns its shell in the user's home directory — whatever the shell defaults to when no `workingDirectory` is set on `TerminalConfiguration`. The user's expectation is that creating a new session while focused inside `~/Developer/Batty` should give them a new session also starting in `~/Developer/Batty`, the same way `Cmd-T` (new tab) inherits the focused pane's CWD via `PaneRuntime.addTab(inheritingCWDFrom:)`.

This is a prerequisite for `#0058`'s CWD → session-name cache: that feature only works if the user's intended CWD lands in the first pane of the new session reliably. Today the new session has to be `cd`'d manually, which is friction in addition to making the auto-naming cache useless.

## Steps to reproduce

1. Open Batty. The default session opens at `~`.
2. In that session, `cd ~/Developer/Batty`.
3. Open the sidebar's "+" button (or `Cmd-Option-N`).
4. **Observed:** the new session's prompt is at `~` (or wherever the shell's startup logic landed it).
5. **Expected:** the new session's prompt is at `~/Developer/Batty`, mirroring the focused pane's CWD at the moment of session creation.

## Expected behavior

`AppStateStore.addSession(title:)` and the sidebar "+" path:

- Capture the currently-selected session's focused pane's active-tab CWD at the moment of session creation (`store.selectedSession?.focusedPane.activeTab.terminal.workingDirectory`).
- Pass that CWD into the new session's first `PaneRuntime` / first `TabRuntime` (or via `TerminalConfiguration.workingDirectory`) so the shell spawns there.
- Falls back to the user's `$HOME` (current behavior) only when there is no previously-selected session — i.e. cold launch with no sessions, which is a transient state since `AppStateStore.init` immediately creates a default session.

When the user invokes session-creation via a code path that doesn't have a "source" pane (e.g. a future "Reopen Closed Session" feature), the call site picks the CWD explicitly. The default-to-focused-pane logic lives at the `addSession()` entry point, not deeper in `SessionRuntime`.

## Actual behavior

`AppStateStore.addSession`:

```swift
@discardableResult
public func addSession(title: String? = nil) -> SessionRuntime {
    let resolvedTitle = title ?? "Session \(sessions.count + 1)"
    let session = SessionRuntime(title: resolvedTitle)   // ← no CWD passed in
    sessions.append(session)
    selectedSessionID = session.id
    return session
}
```

`SessionRuntime.init` → `SplitTree()` → `PaneRuntime()` → `TabRuntime()` — and `TabRuntime.init` takes a `workingDirectory: String?` but it isn't being threaded through from `addSession`. The shell falls back to its login-shell startup behavior, which is `$HOME` for most users.

## Notes

- The CWD source is `selectedSession?.focusedPane.activeTab.terminal.workingDirectory` — already published by the fork (`#0044`), already used by `PaneRuntime.addTab(inheritingCWDFrom:)` for the new-tab case. The same wiring applies here.
- One edge case: the workingDirectory string may not be available immediately on a freshly-spawned tab (the OSC 7 emit happens after the shell starts). In practice the *currently selected* tab will have been around long enough to have published one. If for some reason the value is nil, fall back to `$HOME` rather than blocking.
- The new-session command from the keyboard shortcut (`Cmd-Option-N`) goes through `BattyCommands.swift` → `store?.addSession()`. The fix is in `addSession`, so the keyboard path is covered automatically.
- The Bell Feed and similar restore paths don't create sessions — they jump into existing ones. No additional entry-point coverage needed.
- Concepts.md → Session does not currently spell out the CWD-inheritance rule. Update it alongside the fix.

## Acceptance criteria

- Creating a new session via the sidebar "+", `Cmd-Option-N`, or `AppStateStore.addSession()` with no `title` lands the first pane's shell in the focused pane's CWD.
- When there is no previously-selected session (cold-launch-style state), behavior falls back to `$HOME` (no crash, no error).
- The existing `Cmd-T` "new tab inherits focused pane's CWD" path (`PaneRuntime.addTab(inheritingCWDFrom:)`) is unchanged.
- A unit test or integration test exercises the CWD-inheritance path: spawn a session, set its focused pane's CWD to a known value, call `addSession`, assert the new session's first tab has the same `workingDirectory`.

## Notes on `#0058` dependency

`#0058` (auto-apply session name from a CWD cache) becomes meaningfully useful only after this lands. Without CWD inheritance the new session's first pane often starts at `$HOME`, which would match a "Home" cache entry and apply a useless name. Order: fix this first, then layer the cache on top.

## Out of scope

- Per-session "default CWD" configuration. The dynamic inheritance covers the common case.
- Inheriting other terminal state (env vars, history) from the source pane.
- Resolving symlinks or normalizing the captured CWD — pass the raw string through; downstream consumers (`#0058`) decide whether to canonicalize.

## Root cause

`AppStateStore.addSession(title:)` always constructed `SessionRuntime(title:)` with no extra arguments. That ran the default init chain `SessionRuntime.init` → `SplitTree()` → `PaneRuntime()` → `TabRuntime()` with `workingDirectory: nil`, so the new session's first shell spawned at libghostty's default (`$HOME`). The companion new-tab path (`PaneRuntime.addTab(inheritingCWDFrom:)`) already read the source tab's live cwd, but no equivalent capture existed at the session-creation entry point.

## Fix

In `AppStateStore.addSession(title:)`, capture the currently-selected session's focused pane active tab and read `terminal.workingDirectory` (the live OSC 7 value) with a fallback to `terminal.configuration.workingDirectory` (the configured spawn dir, useful before OSC 7 has fired). Pass the result into an explicit `TabRuntime(workingDirectory:)` and build the new session with `SessionRuntime(title:, tree: SplitTree(root: .leaf(PaneRuntime(tabs: [tab]))))`. When no session is selected, the captured value is nil and behavior matches the prior default (shell starts at `$HOME`). No new parameters added to `SessionRuntime.init`, `SplitTree.init`, or `PaneRuntime.init`.

## Files changed

- `BattyKit/Sources/BattyKit/AppStateStore.swift` — `addSession(title:)` now captures the focused pane's active tab cwd (with configuration fallback) and threads it into the new session's first `TabRuntime` via an explicit tree.
- `BattyKit/Tests/BattyKitTests/AppStateStoreSessionCWDTests.swift` — three new tests covering inheritance from the selected session, the no-selected-session fallback, and inheritance from the currently selected (not the first) session when several exist.
- `Concepts.md` — Session entry now documents the CWD-inheritance rule alongside Sidebar affordances.

## Gotchas

- `TerminalViewState.workingDirectory` is `internal(set)` to libghostty-spm, so tests can't write the live OSC 7 value directly. The implementation falls back to `terminal.configuration.workingDirectory` (publicly writable), which is what the tests exercise. In production the live value wins because it tracks the actual shell cwd after `cd`.
- The new code constructs `SplitTree(root: .leaf(PaneRuntime(tabs: [TabRuntime(workingDirectory: cwd)])))` explicitly. The previous shorthand `SessionRuntime(title: resolvedTitle)` relied on the chain of default inits — both paths are equivalent when `cwd == nil`, so the no-source-session case is unchanged.
