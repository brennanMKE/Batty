## Description

When you split to create a new pane, Batty halves the *current* pane, which leaves uneven sizes once there are three or more panes in a row/column. It should instead **evenly distribute all panes along that axis**: two panes → 50/50, a third → 1/3 each, a fourth → 1/4 each, and so on. Same behavior for both horizontal (width) and vertical (height) splits.

## Resolution notes

> 🟢 Resolved 2026-07-03 — after a split, the contiguous same-direction chain containing the new pane is re-equalized to 1/n; perpendicular splits still start a fresh 50/50 axis and manual drag-resize is unaffected. Ratio math verified by unit tests; the rendered result needs a visual glance.

**Visual sign-off:** the 1/n ratio math is proven by unit tests, but confirm the on-screen widths/heights look even (split 3–4 times; split after a drag-resize) before closing. `resolved`, not `closed`.

## Steps to reproduce

1. Open a session with one pane.
2. Split horizontally → two panes at 50/50 (correct so far).
3. Split one of them horizontally again to add a third pane.
4. Observe the three panes are **not** evenly sized.

## Expected behavior

- **Horizontal split** starting from 1 pane: the 2 panes are 50/50 by width. Adding a 3rd (same axis) re-balances to 1/3 each; a 4th to 1/4 each; and so on (1/n).
- **Vertical split**: identical, by height.
- Splitting along the same axis always yields equal fractions for every pane in that row/column.

## Actual behavior

`SplitTree.splitFocusedPane(direction:ratio:)` inserts a binary `split` node at a fixed `ratio: 0.5` (`BattyKit/Sources/BattyKit/Model/SplitTree.swift:79`), so it halves only the focused pane. In a binary tree, splitting one pane of an existing `[A | B]` (50/50) horizontally to add `C` nests as `split(0.5, split(0.5, A, C), B)` → **A=25%, C=25%, B=50%** instead of ~33% each. Every additional same-axis split compounds the unevenness.

## Notes / design considerations

The layout is a **recursive binary** `SplitTreeNode` (`leaf(Pane)` or `split(id, direction, ratio, left, right)`), so "1/n even" isn't a single ratio — it needs one of:

- **Ratio math on the binary tree:** when the focused pane's *parent* split is already the **same direction**, insert the new pane into that same-direction chain and recompute every ratio in the chain so all leaves along that axis are equal (1/n). When the parent is a different direction or the focused pane is the root leaf, create a fresh 50/50 split (today's behavior) — the new pane starts a new axis.
- **N-ary "row" grouping:** collapse a same-direction chain into a group with equal fractions. Bigger model change; `SplitTree` is deliberately binary, so prefer the ratio-math approach unless it gets unwieldy.

Points to decide during implementation:

- **Same-axis only.** Even distribution applies when adding a pane *along the same axis* as the row/column it joins. Splitting a pane *perpendicular* to its parent legitimately starts a new axis and should still be 50/50 within that sub-region.
- **Manual resizes.** If the user has drag-resized a divider (e.g. 70/30) and then splits, the requested behavior is to **re-equalize to 1/n** (the user said "adjust the size of both to evenly split all 3"). Manual drag-resize (Cmd-Ctrl-arrows / divider drag) must keep working afterward; only the split action forces equalization.
- **Closing a pane.** Out of scope for this issue, but note the mirror question for later: when a pane in an n-row closes, should the remaining panes re-equalize to 1/(n-1) or keep their ratios? Decide separately; don't expand this ticket.

Relevant code/guides: `BattyKit/Sources/BattyKit/Model/SplitTree.swift` (the tree + `splitFocusedPane`, ratio-carrying rebuild helpers, and the divider/resize paths), and `docs/view-hierarchy.md` for how the tree maps to the rendered splits. Add/keep unit tests: `SplitTree` is a pure value type, so the 1→2→3→4 ratio math (and the same-axis-vs-perpendicular distinction) is directly unit-testable without the UI.

## Root cause

`splitFocusedPane` always inserted a binary `split` node at `ratio: 0.5`, halving only the focused pane. In a binary tree, splitting one pane of `[A|B]` (50/50) nests as `split(0.5, split(0.5, A, C), B)` → 25/25/50 instead of even thirds; every additional same-axis split compounded the skew.

## Fix

After `splitFocusedPane` inserts the new pane, a recursive pass finds the **maximal contiguous same-direction chain** containing it and recomputes every ratio so all its leaves render at 1/n:
- `rebalancingChain(containing:direction:in:parentIsDSplit:)` locates the chain root (a same-direction split entered from a different-direction parent or the tree root) and rebalances the whole chain; a `parentIsDSplit` flag + a `.foundBelowBreak` result wrapper stop the rebalance at perpendicular boundaries so a different-axis chain is never disturbed.
- `countChainLeaves` treats a perpendicular subtree as **one opaque unit**, so a cross-direction subtree that's a member of a chain still gets exactly 1/n of the axis with its internals preserved.
- Perpendicular splits therefore start a fresh 50/50 axis; manual drag-resize (`updateRatio`) is untouched — only the split action equalizes. The `ratio:` parameter is now overridden by equalization on same-axis splits (kept for API compatibility, documented as inert).

## Gotchas

- **`ratio:` on `splitFocusedPane` is now inert** — equalization overrides it for same-axis splits, and a perpendicular split starts a fresh 50/50, so no path honors a custom split ratio anymore. It's kept for API compatibility and documented; a future cleanup could remove the parameter (touches the `inserting` helper + all callers).
- **Feeds #0256.** The "even 1/n" must count **visible** panes only once pane-hiding lands — the rebalance chain logic is the place to exclude hidden panes from the unit count.
- **Pane-close re-balancing is unchanged** (deliberately out of scope): closing a pane in an n-row does not re-equalize the survivors. Filed as the mirror question in Notes; decide separately.
