## Description

Phase 2 of the #0234 multi-window umbrella: introduce the `WindowRuntime` per-window state container around `AppStateStore` with **exactly one window and zero behavior change** — a pure refactor that creates the seam every later phase plugs into. Design source: `docs/multi-window-design.md` §5 (the per-window state model) and §1 (current state).

Scope:

- New `@Observable` `WindowRuntime` (`BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift`), named per the `SessionRuntime`/`PaneRuntime`/`TabRuntime` family, with a stable `id` (`WindowID` wrapping a `UUID`).
- Move per-window state and behavior out of `AppStateStore` into `WindowRuntime` per the design doc's table: `sessions`, `selectedSessionID`/`selectedSession`, session CRUD (`addSession`, `removeSession`, `renameSession`, `duplicateSession`, `moveSessions`, `selectSession(at:)`), the `closeTab(id:)` cascade, `pendingCloseRequest` + confirm/cancel, and `focusPane(id:)`/`focusPane(containingTabID:)`.
- `AppStateStore` keeps the global services (bell routing across windows, `bellFeed`, `nameCache`, `themeChrome`, AI naming, `notifier`) and gains `windows: [WindowRuntime]` + `windowRuntime(for:)`; with one window, every existing call site resolves to the single runtime.
- `BattyShortcuts`, `BattyCommands`, and the view layer re-target through the single `WindowRuntime`; sidebar visibility plumbing stays as-is in this phase (it moves per-scene in #0238).

This phase touches selection and focus flow, so `docs/swiftui-observation-rules.md` is binding and must be re-read before starting; equal-value `@Observable` writes re-invalidate (#0229 lineage) — preserve the existing idempotency guards (e.g. `focusPane(id:)`).

## Acceptance criteria

## Root cause

Not a bug — Phase 2 of the #0234 umbrella. Starting state: `AppStateStore.shared` was a singleton owning both global services and all per-window state (`sessions`, selection, session CRUD, close-tab cascade, focus), so no second window could have independent state. This phase introduces the per-window container without changing single-window behavior.

## Fix

Added `WindowID` (a `UUID` wrapper, distinct type so `WindowGroup(for:)`/`openWindow(value:)` can't collide) and `WindowRuntime` (`@Observable`, in the `SessionRuntime`/`PaneRuntime`/`TabRuntime` family). Moved per-window state and behavior into `WindowRuntime` per design doc §5: `sessions`, `selectedSessionID`/`selectedSession`, session CRUD, the close-tab cascade and `pendingCloseRequest` confirm/cancel, `focusPane(id:)`/`focusPane(containingTabID:)` (idempotency guard preserved verbatim), plus per-window bell helpers. `AppStateStore` keeps global services (`bellFeed`, `nameCache`, `themeChrome`, AI naming, `notifier`, cross-window bell routing) and gains `windows: [WindowRuntime]` (`@ObservationIgnored`) + `windowRuntime(for:)`; its former per-window properties are now computed forwarders to `windows[0]`, so every existing call site resolves to the single runtime unchanged.

## Gotchas

- **Computed forwarders and Observation:** reading `store.sessions`/`selectedSessionID`/`pendingCloseRequest` resolves to `windows[0]`'s stored `@Observable` properties, so views register as observers of `WindowRuntime` (not `AppStateStore`). `windows` is `@ObservationIgnored` deliberately — reactivity must flow through the runtime instance, and the array is a stable single element this phase.
- **Empty-rename / AI suggestion (accepted divergence, not a follow-up):** an empty-string `renameSession` now cancels an in-flight AI name suggestion where the old guard-ordering happened not to. Not user-visible (the title is unchanged either way and AI naming is best-effort), breaks no test, and arguably more correct. Documented here rather than filed as a ticket because there is no deferred work — it is settled behavior.
