## Description

Every Session row in the Sidebar looks the same: a generic
`rectangle.split.3x1` icon plus a title. With more than a handful of
Sessions, finding a specific one requires reading each title. A small,
stable color cue per row would let the eye jump straight to "the teal one"
without reading.

Proposed: tint the Session row's existing `rectangle.split.3x1` SF
Symbol — the `Label` icon in private `SessionRow`
(`BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift`),
immediately right of the DisclosureGroup chevron — with the Session's
assigned color, replacing its current `HierarchicalShapeStyle.secondary`
styling. The symbol is already in every row, so the color consumes no
additional row width; that is the reason for this choice over a
separate colored bar. Each Session automatically gets a different color
at creation. `Concepts.md` already anticipates this under Session →
Identity ("user-editable `title` (and optional icon/color)") — the color
half of that has never been built.

## Resolution notes

> 🟢 Resolved 2026-08-20 — every Session now gets a stable color from a
> fixed 10-color palette at creation, shown by tinting the Sidebar row's
> `rectangle.split.3x1` symbol instead of adding a colored bar.

The visual half is unverified: no headless check can confirm legibility
in light/dark, themed/unthemed, or on the selected row. That sign-off is
the user's, which is why this is `resolved` and not `closed`.

One deviation was carved out rather than fixed here and is tracked as
[#0340](0340.md): once every palette index is in use, Duplicate Session
can hand the copy the source's own index, contradicting this issue's
"a duplicate should get a fresh color". [#0336](0336.md) builds the
user-chosen-color half on top of this assigner.

## Root cause

Not a defect — a feature gap. Every Session row rendered the same
generic `rectangle.split.3x1` icon in `HierarchicalShapeStyle.secondary`,
so rows were distinguishable only by reading their titles.
`Concepts.md` → Session → Identity had anticipated an optional color
since the vocabulary was written, but nothing implemented it.

## Fix

`SessionColor`, a `public enum SessionColor: Int, CaseIterable, Sendable`,
holds the ten palette entries in assignment order and derives its
`Color` by reusing the package-internal `RGBColor(hex:)` already in
`Theme/ThemeChrome.swift`. `SessionRuntime` gained `var colorIndex: Int`
(a `var`, so #0336 can write it without restructuring) plus a pure
computed `sessionColor` reader. `WindowRuntime` gained an
`@ObservationIgnored` assigner cursor and `nextColorIndex()`, which
tallies live Sessions per index, picks the least-used, and breaks ties
by palette order starting after the last index handed out; it is wired
into all three creation sites. The Sidebar row's symbol now reads
`.foregroundStyle(session.sessionColor.color)` — a pure `body` read,
with the write confined to Session creation in `WindowRuntime`.

Three display questions the issue left open were settled: the color
persists on the selected row (no selection-state branch), the tint is
full strength rather than reduced-opacity, and the symbol stays the
outline `rectangle.split.3x1` rather than a `.fill` variant.

## Expected behavior

- Every Session row's `rectangle.split.3x1` symbol renders in that
  Session's assigned color instead of the current secondary gray.
- The color is assigned **once, when the Session is created**, and is
  stable for the Session's lifetime — it must not change on view rebuild,
  sidebar reorder, or when other Sessions are added or closed. Deriving
  the color from the row's position in the list is therefore wrong by
  construction.
- New Sessions cycle through a palette of 10 colors so adjacent Sessions
  differ; past 10 Sessions the palette wraps.
- The tinted symbol is legible against both the system sidebar material
  and a themed sidebar (`ThemeChrome.chromeBackground`), in light and
  dark appearance.

## Actual behavior

All Session rows are visually identical apart from their title text and
the bell-count badge.

## Where the assignment lives

- `SessionRuntime` (`BattyKit/Sources/BattyKit/Runtime/SessionRuntime.swift`)
  is the natural home: an `@Observable` class holding per-session
  UI-facing state (`title`, `localThemeName`, `isPaneListExpanded`). Add
  e.g. `let colorIndex: Int` (or a small enum), set in the initializer's
  callers.
- Assignment happens at the creation sites in `WindowRuntime`
  (`BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift`): the initial
  Session (~line 74), `addSession` (~line 91), and `duplicateSession`
  (~line 176 — a duplicate should get a fresh color, not the source's).
- Constraints from CLAUDE.md / `docs/swiftui-observation-rules.md`: view
  construction is pure — `SessionRow`/`body` must only *read* the stored
  color, never compute-and-write one. The layout model
  (`LayoutModel.swift`) stays pure value types; the color is Session-level
  runtime state, not layout, so it does not belong in `Pane`/`SplitTree`.
  The Surface registry is untouched — this is chrome only.
- Sessions are not persisted (`Concepts.md`: "Persisted: nothing"), so
  the assignment only needs in-memory stability. If Session persistence
  ever returns, the index is a trivially codable `Int`.

## Palette

Fixed fallback palette of 10: mid-lightness, high-chroma solids (Radix
scale-9 values) that hold up against both light and dark sidebar
backgrounds. Hues are spaced around the wheel, and the
listed order is the assignment order — consecutive Sessions get
hue-distant colors, and confusable pairs under red-green color-vision
deficiency (red/green, amber/lime territory) are separated by lightness
and never adjacent in assignment order.

| # | Name | Hex |
|---|---|---|
| 1 | Blue | `#3E63DD` |
| 2 | Orange | `#F76B15` |
| 3 | Green | `#30A46C` |
| 4 | Pink | `#D6409F` |
| 5 | Teal | `#12A594` |
| 6 | Red | `#E5484D` |
| 7 | Violet | `#8E4EC6` |
| 8 | Amber | `#FFB224` |
| 9 | Cyan | `#00A2C7` |
| 10 | Brown | `#AD7F58` |

Rationale: no two entries share both a hue neighborhood and a lightness
band; there is no neutral gray (which would read as "no color
assigned"). The color now lands on a glyph, not a sliver: an SF Symbol
at sidebar `Label` size is a larger, more legible colored area than a
3 pt bar would have been, but it is a thin-stroked outline glyph rather
than a solid fill, so the constraint shifts from "does the hue read at
3 pt" to "does the stroke hold contrast against the sidebar background
at body-text weight". The mid-lightness, high-chroma scale-9 values
remain a good fit for exactly that reason. Amber (`#FFB224`) and cyan
(`#00A2C7`) are the entries most worth checking against a light themed
sidebar — a thin stroke gives less area to carry a light hue.

## Theme integration (what is actually feasible today)

The user preference is theme-sourced colors, but not as a hard
requirement. Findings from the code:

- `GhosttyThemeDefinition` (libghostty-spm package) **does** expose a
  16-slot ANSI palette (`palette: [Int: String]`, hex), and every
  built-in Batty theme in
  `BattyKit/Sources/BattyKit/Theme/BattyThemeCatalog.swift` /
  `BattyThemes.swift` populates all 16 slots. So a multi-color source
  exists in the theme model.
- However, `ChromePalette`/`ThemeChrome`
  (`BattyKit/Sources/BattyKit/Theme/ThemeChrome.swift`) — the only path
  by which theme colors reach SwiftUI chrome — currently surface a
  **single** derived `accent` (cursor color, else ANSI 4). No multi-color
  palette reaches the views today; exposing one is new plumbing.
- Theme palettes are not designed for this job: the `palette` dict may be
  sparse for arbitrary user themes (the initializer defaults it to `[:]`),
  the light Batty themes duplicate slots 1–6 into 9–14 (≈6 distinct hues,
  not 10), slots 0/7/8/15 are near-background/near-foreground neutrals,
  and per-session theme overrides (`SessionRuntime.localThemeName`) mean
  "the current theme" is ambiguous across rows.

Recommendation: ship the fixed 10-color palette as the behavior. If
theme-derived colors are still wanted, do it as a follow-up: extend
`ChromePalette` to expose the usable ANSI slots and substitute them for
the fixed swatches only when the active *global* theme provides enough
distinct, sufficiently-saturated entries; otherwise fall back to the
fixed 10. The Session keeps its stable index either way — a theme switch
recolors the symbols consistently but never reshuffles which Session has
which slot.

## Assignment strategy

Round-robin with least-used preference, scoped to the Window:

1. On Session creation, count how many live Sessions in the Window use
   each palette index.
2. Pick the least-used index; break ties by palette order starting after
   the most recently assigned index (so consecutive creations walk the
   palette even after closures free up earlier slots).
3. Store the index on the new `SessionRuntime`; never reassign it.

With ≤10 Sessions every symbol color is unique; past 10 the palette
wraps and duplicates are unavoidable but stay maximally spread.

## Open questions

- Should the symbol also carry the color when the row is selected, or
  defer to the selection foreground?
- Should the tint be the full palette color, or the palette color at
  reduced opacity / as a hierarchical secondary variant, so the symbol
  does not out-shout the title text?
- Should the symbol stay `rectangle.split.3x1`, or is a fill variant
  (e.g. `rectangle.split.3x1.fill`) worth using so the color reads as a
  larger solid area?
- Should the color appear anywhere else — the Detail Area (tab chips,
  pane focus border), the Bell Feed rows, the window title bar? Proposed
  scope here is Sidebar-only.
- Should the color be user-overridable (e.g. a "Set Color" context-menu
  item next to Rename), fulfilling the rest of the `Concepts.md`
  "optional icon/color" note? Now filed as [#0336](0336.md).
- Should the Pane rows inside a Session's DisclosureGroup inherit a
  muted version of the Session's color, or stay unmarked?

## Acceptance criteria

- Each Session row's `rectangle.split.3x1` SF Symbol renders in the
  Session's assigned color.
- Ten consecutive new Sessions get ten different symbol colors; the
  eleventh reuses one.
- Reordering Sessions, renaming, closing a neighboring Session, or
  collapsing/expanding the sidebar does not change any existing Session's
  color.
- The tinted symbols are distinguishable from one another and legible
  against the sidebar in light and dark appearance, with and without a
  chrome theme applied.
- No writes to observed state from `body`/view construction
  (`docs/swiftui-observation-rules.md`); `scripts/build.sh unit` passes,
  with a unit test covering assignment stability and wrap-around.

## Gotchas

- `SessionRow` sits inside a `List(.sidebar)` whose row backgrounds are
  custom-painted by `SidebarRowBackground` when a theme is active
  (#0135). The tinted symbol is already row *content* — the `Label` icon
  inside the `HStack` — so no new layer is introduced and the custom
  row-background painting is untouched. The adjacent risk is instead
  selection state: `List(.sidebar)` selection tinting may recolor or
  vibrancy-blend the row's foreground when the row is selected, so the
  assigned color must be verified on the **selected** row too, not just
  unselected ones — an accent-tinted selected row can flatten the symbol
  to the selection foreground color.
- `Concepts.md` says to add missing vocabulary before using it — if the
  implementation names the concept (e.g. "Session color"), update
  `Concepts.md`'s Session → Identity entry in the same change.

- **The visual result is unverified.** No headless check reaches it.
  Before this moves to `closed`, confirm the symbol is legible and the
  colors distinguishable in light and dark appearance, with and without
  a chrome theme, and **on the selected row in the unthemed case** —
  `SidebarRowBackground` suppresses the system selection chrome only
  when a chrome theme is active, so in the default sidebar the native
  selection tinting is still live and could blend the symbol toward the
  selection foreground. Amber (`#FFB224`) and cyan (`#00A2C7`) are the
  entries most at risk against a light themed sidebar.
- `SessionColor.color` re-parses its hex string on every `body`
  evaluation and falls back to a neutral gray if a hex ever fails to
  parse — the one color the palette rationale says must never appear.
  All ten parse correctly today; nothing guards a future typo.
