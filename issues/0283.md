## Description

Third child of the #0257 umbrella. Per the transport amendment recorded there: `pane close` goes over XPC request/reply, not the one-way `batty://` scheme, because it must **report a real result** — closing a nonexistent pane id must exit `4`, not `0`. This is the second mutating XPC verb and should follow the pattern #0282 establishes.

**`pane close` is not `tab close`** *(terminology sweep, 2026-07-27 — this is the real ambiguity in the verb name, so the semantic is pinned here)*: a Pane may hold multiple Tabs, and `Concepts.md` defines pane removal as the consequence of closing the *last* Tab — there is no pane-level close in the code today (see the cascade below). `batty pane close` implements the **pane-level** semantic: it ends **every** Tab's Terminal Session in the target pane — not just the active one — and removes the pane's region from the split tree, with the sibling subtree taking over its space. Closing exactly one tab is #0257's separate `batty tab close [--tab <id>]` verb (no child filed yet), which removes the pane only when the closed tab was its last. An agent that wants the smaller operation must reach for `tab close`, not `pane close`.

## Grammar

```
batty pane close [--pane <id>]
```

- `--pane <id>` targets an explicit pane; otherwise the target resolves via #0281's chain (explicit flag → `BATTY_PANE_ID` env → focused pane).
- Exit codes per the `BattyXPCCore/XPCExitCode.swift` vocabulary (verified): `0` success, `1` CLI input error, `2` broker unreachable, `3` app unavailable, `4` request failed, `5` app terminated. **A nonexistent or stale pane id is a `4`, with a message on stderr.**

## Behavior rules (from #0257, binding)

- **Closing a pane in a background session must not steal focus or switch the active session.** Only the `focus` verbs do that.
- The result reported must reflect what the app actually did — success only when the pane existed and was closed.

## As-built starting points (verified against source 2026-07-26)

- **No pane-level close entry point exists today.** Close is a *tab* cascade: `WindowRuntime.closeTab(id:)` (`BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift`) removes the tab (with `cleanUpBellState`), and when the pane's tab list empties it calls `session.tree.removePane(id: pane.id)`; when that reports the tree emptied, it calls `removeSession(id:)`. A pane may hold multiple tabs, so "close pane" means ending every tab's Terminal Session in that pane — reuse or extract the existing cascade so surface teardown and bell-state cleanup go through the same path (the Surface registry is the single source of truth; leaked surfaces are the failure mode to guard).
- **`SplitTree.removePane(id:)` exists** (`BattyKit/Sources/BattyKit/Model/SplitTree.swift`, ~line 205) and returns `true` when the tree became empty; its doc comment says callers should treat that as "session is now empty and should be closed." It also reassigns the tree's `focusedPaneID` when the removed pane was focused — within-session, which is fine, but it must not propagate to `selectedSessionID` or app-level focus for a background target.
- **A confirmation path exists for the interactive close** and this verb must take a position on it: `WindowRuntime.requestCloseTab(id:)` checks `terminal.needsConfirmClose` and raises a `pendingCloseRequest` dialog when a process is still running. Whether an agent-driven `pane close` honors that confirmation (reply "confirmation pending"? fail? force-close?) is a design decision for the implementer to make explicitly and record — silently bypassing a guard the UI enforces should not happen by accident.
- **XPC wiring points** (all verified): verb in `BattyXPCCore/XPCVerb.swift`, dispatch in `AppXPCService.perform(_:reply:)`, CLI via the generalized `AppServiceClient.perform<Payload>` dance from #0274. The `pane` noun itself is introduced by #0282.

## Raised, not decided: closing the *last* pane

What happens when the target is the last pane in a session — does the session close (the existing cascade says yes: `removePane` → tree empty → `removeSession`)? And when it is the last pane of the last session? Is there a confirmation path an agent should trip? Note that **#0217** (open) records the app *silently quitting* when all shell processes exit, bypassing quit confirmation — an agent that closes panes one by one could walk the app into exactly that adjacent behavior. This issue must surface the chosen behavior in its resolution, but the decision is left to the implementer/user, not pre-made here.

## Binding constraints (copied — do not merely cross-reference)

- **Payloads are `Codable, Sendable` structs carried as JSON-encoded `Data`** inside the `@objc` protocols, `nonisolated` at type level; protocol requirements are `nonisolated func`; reply blocks `@escaping @Sendable`. Guard new payload types with off-actor round-trip helpers as `XPCContractTests` does, and assert raw decoded JSON keys (the #0274 `_0` lesson), not just round-trips.
- **Every Foundation-supplied handler closure gets `@Sendable`** — there is no compiler warning, and the failure is a silent `SIGTRAP` inside the very handler that would have logged the error.
- **`os.Logger` interpolation of a dynamic `String` defaults to `.private`** — add `privacy: .public` explicitly.
- **Verify isolation guards under a forced rebuild** (`rm -rf .build`); stale targets produced false "still builds" results twice on the XPC track.
- **Code-signing protocol:** never run `scripts/build.sh` for iteration (its `unit` path can't disable signing); use `cd BattyKit && swift test` and `xcodebuild … CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO`. The user's Developer ID certificate was revoked once by repeated signed local builds.
- **Mutations aimed at a background session must not steal focus or change the active session** — assert against the store (`selectedSessionID`, focused pane, active tab), not merely absence of a crash.

## Verification expectations

Follow the #0271/#0274 pattern:

- **Unit tests for the pure parts:** argument parsing (`--pane` UUID validation → exit 1 client-side); request/reply payload round-trips plus raw-JSON key assertions; close on a constructed tree (named pane removed, siblings' fractions correct, unknown id yields the failure result); the last-pane cascade behavior, whatever is decided, asserted explicitly.
- **Cross-session store assertions:** closing a pane in a non-active session mutates only that session's tree; `selectedSessionID`, the active session's focused pane, and every other session are unchanged.
- **Failure result:** `batty pane close --pane <nonexistent-uuid>` → CLI exit `4`, message on stderr, app-side public log line. This is the acceptance test for the transport decision itself.
- `cd BattyKit && swift test` and `xcodebuild … CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO` green; `otool -L` on `batty` still shows zero `@rpath` dependencies.
- **Needs the user's runtime sign-off** (do not disturb the running app; coordinate): from inside a pane, `batty pane split` then `batty pane close --pane <new-id>` round-trips; closing a background session's pane leaves the current view untouched; the stale-id exit `4` is observable; the last-pane behavior matches what was decided.
