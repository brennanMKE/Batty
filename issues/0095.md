## Description

UI regression tests for the terminal-host architecture that landed in `#0072` → `#0074` → `#0075`. This is the area where regressions are most expensive (losing a Claude Code session, killing a long build) and where the architecture is the most fragile (SwiftUI ↔ AppKit lifecycle bridge with a singleton-owned NSView).

Depends on `#0091` (UI test harness bootstrap) and explicitly on the sentinel-file pattern.

## What this issue ships

A `TerminalPersistenceTests` UI test class. Every test uses a **sentinel-file pattern** because XCUITest can't read terminal pixels.

### The sentinel pattern

Each test spawns a long-lived process via the shell:

```sh
# In tab 1, type:
(while true; do echo alive > /tmp/batty-ui-test-<uuid>-heartbeat; sleep 0.5; done) &
echo $! > /tmp/batty-ui-test-<uuid>-pid
```

The test then:

1. Navigates away (switch tabs / panes / sessions / collapse sidebar / etc.).
2. Waits a few seconds.
3. Reads `/tmp/batty-ui-test-<uuid>-pid` and checks if the process is still running via `kill -0 <pid>`.
4. Reads the heartbeat file's mtime; if it's recent, the loop is still alive.
5. Optionally navigates back and assertss the prompt is the same shell instance (e.g. the `$$` value matches a previously-recorded one).

### Tests

1. `switchTab_preservesTerminal` — start a loop in tab 1, `Cmd-T` to tab 2, wait 2s, return to tab 1, assert heartbeat is still writing.
2. `switchSession_preservesAllSessionTerminals` — start loops in sessions A and B, switch back and forth, assert both heartbeats survive.
3. `split_preservesExistingPane` — start a loop, `Cmd-D` to split, assert the original pane's loop survives.
4. `focusPaneArrow_doesNotRespawn` — start loops in both panes of a split, press `Cmd-Option-Arrow` to move focus, assert both loops keep writing.
5. `closeOtherTabsAndPanes_doesNotKillSurvivor` — open 3 tabs with loops, close 2, assert the survivor's loop is still writing.
6. `sidebarCollapseExpand_preservesTerminals` — start a loop, toggle sidebar via `Cmd-Control-S` several times, assert loop survives.
7. `windowResize_preservesTerminals` — drag the window to resize, assert the loop continues.

### Process count assertion

After a "should not respawn" navigation, the test runs:

```sh
pgrep -c /usr/bin/login > /tmp/batty-ui-test-<uuid>-login-count
```

before and after the navigation. The counts must match. A respawn shows up as a count increase. This is the regression test that would have caught `#0072` and `#0074` immediately.

### Log assertion

For the strongest signal, capture libghostty's `io_exec: started subcommand` log lines via `log stream --process Batty --predicate 'subsystem == "co.sstools.Batty"'` (or similar). Count occurrences during the test. A navigation that doesn't respawn shows zero.

This requires writing to a per-test log capture file and asserting the count. Heavier setup; recommend only for the most critical persistence test.

## Acceptance criteria

- All 7 tests pass on the current build (post-`#0075` Phase 2).
- A regression that re-introduces the `viewDidMoveToWindow` respawn behavior (`#0072`) fails tests 1, 3, 5, 6 — process counts will jump.
- A regression that breaks the persistent host (`#0075`) fails tests 1-4 — terminals go blank or processes die.
- A regression that disconnects the placeholder geometry from the host (`#0075` Phase 2 coord-space issue) shows as misplaced terminals during the test, caught by accessibility-identifier-based assertions where possible.

## Out of scope

- Testing the visual rendering of terminal contents (we can't read pixels).
- Performance benchmarks for navigation.
- Multi-window persistence (Batty is single-window per `#0063`).

## Notes

- This is the most valuable UI test class. The `#0072` → `#0074` → `#0075` chain demonstrates how easy it is to regress this architecture — three subagent dispatches before it worked. Locking it down with regression tests is the only way to confidently iterate on the terminal host in the future.
- The sentinel pattern is a workaround for libghostty's Metal-rendered terminal contents being opaque to XCUITest. If we ever switch to a host-managed PTY backend (mentioned in `#0073`'s notes), the tests could read terminal output directly.
- Long-running tests can time out CI runners — keep each test's wait under 5 seconds.
- Related: `#0072`, `#0074`, `#0075`.
