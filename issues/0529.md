## Description

User request (2026-10-19, verbatim): "Fix tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM so it is not slow."

The test is `LMStudioDashboardPaneContentTests.tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM()` (`BattyKit/Tests/BattyKitTests/LMStudioDashboardPaneContentTests.swift:686`). It spawns two real `/bin/sh` children that ignore `SIGTERM` (`LMStudioSIGTERMIgnoringFixture.makeProcess`, `LMStudioSIGTERMIgnoringFixture.swift:42`), calls `tearDown()`, proves via the closed `TestTeardownReapGate` that `tearDown()` returned while both children are alive, then opens the gate and awaits the real `SIGKILL` escalation.

## Current state (measured 2026-10-19 on `main` at `9aa221b2`)

### Timings

- **Alone:** `cd BattyKit && swift test --filter tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM` works. Three runs: 0.351 s, 0.353 s, 0.386 s (test duration; about 3 s wall including the incremental build).
- **In the full suite** (`cd BattyKit && swift test`, 2,588 tests / 289 suites): two runs reported this test at 23.143 s (run 23.240 s) and 21.758 s (run 21.858 s). In the second run it was the 2,577th of 2,588 tests to finish, and its duration was the longest of any test (median test duration 20.1 s). #0528 recorded 28.4 s for it under `./build.sh unit` (run 28.5 s).
- **Most of the full-suite number is not this test's own work.** #0528's event-stream investigation found nearly all 2,588 tests start in the first second and end at 20–23 s, because they queue for the main actor behind other `@MainActor` tests that block it on child processes. This test hops back to the main actor several times (two FIFO readiness awaits, `waitForParkedWaiter(2)`, `awaitPendingTeardownReapsForTesting()`), and each hop queues again, so it finishes near the end. Its intrinsic cost is the ~0.35 s above.

### Where the intrinsic time goes

- The test sets `content.teardownWaitBound = 0.2` (`LMStudioDashboardPaneContentTests.swift:706`; production default `0.5`, `LMStudioDashboardPaneContent.swift:91`).
- Once the gate opens, each detached reap task (`scheduleTeardownReap`, `LMStudioDashboardPaneContent.swift:795–806`) runs `reapAfterTerminate` (`LMStudioDashboardPaneContent.swift:827–847`). It polls `process.isRunning` with `Thread.sleep(forTimeInterval: 0.02)` until a **wall-clock** deadline of `bound` (`:828–831`). The children ignore `SIGTERM`, so it always waits the full 0.2 s. It then sends `SIGKILL` and polls again in 20 ms steps for up to `min(bound, 0.5)` (`:837–841`).
- So of ~0.35 s, about 0.2 s is a fixed real-time grace period the test can't skip, plus up to 20 ms of poll granularity on each side of the `SIGKILL`, plus spawning two shells. The two streams reap in parallel on separate detached tasks, so it's ~0.2 s, not 0.4 s.
- That is a real-time wait in a unit test. `AGENTS.md` "Asynchronous tests (binding)" says periodic or timed work is "driven through an injected clock or scheduler the test advances explicitly, not by letting real time pass". The test's own structural proof (closed `TeardownReapGate`, `docs/async-test-seams.md` §3) is already correct; only the escalation half still lets real time pass.
- `content.clock = TestClock()` is already set in the test, but `reapAfterTerminate` is `nonisolated static`, uses `Date()` and `Thread.sleep`, and doesn't consult `clock`.

## Expected behavior

- The test proves the same two things it proves today: `tearDown()` returns while both `SIGTERM`-ignoring children are alive (closed gate, waiters parked), and both children are eventually `SIGKILL`ed and reaped.
- The `SIGTERM` → `SIGKILL` grace period no longer passes in real time in the test. Candidate directions for the plan to choose between:
  1. **Injected grace-period seam.** Route the grace deadline through an injected seam the test controls, for example the existing `SchedulingClock` (`docs/async-test-seams.md` §1) or a small escalation hook, so the test advances past the grace period explicitly. `reapAfterTerminate` is `nonisolated static` and synchronous today, and the quit path (`waitForDeferredTeardown()`) must stay synchronous, so the plan has to say how a sync caller and an async seam coexist.
  2. **Event-driven exit.** Replace the `Thread.sleep` `isRunning` polls with an exit event (`Process.terminationHandler` or a `DispatchSource` process-exit source) so the post-`SIGKILL` wait ends on the event rather than at the next 20 ms tick. This only removes poll granularity; on its own it doesn't remove the grace period.
  3. **Bound of zero in the test.** `teardownWaitBound = 0` makes the escalation immediate. Cheapest, but the test would no longer show that a grace period exists before `SIGKILL`. If chosen, coverage for "waits the bound before escalating" must live in a test that drives an injected clock.
- Production behavior is unchanged: 0.5 s default grace, same logging, quit path still synchronous and bounded.
- No new sleeps, polls or timing assertions in tests (`AGENTS.md` "Asynchronous tests").
- The two in-scope `LMStudioDashboardWiringTests` siblings use the same seam.

## Acceptance criteria

- `cd BattyKit && swift test --filter tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM` reports well under the current ~0.35 s; the real `teardownWaitBound` grace period no longer appears in its runtime. Record before/after numbers in the resolution.
- The test still fails if `tearDown()` blocks on the reap (closed-gate proof intact) and still fails if a `SIGTERM`-ignoring child is never killed.
- The two `LMStudioDashboardWiringTests` siblings no longer spend `teardownWaitBound` in real time on the main thread.
- `./build.sh unit` passes. Record the full-suite run time before and after. Don't claim a suite-wide win from the per-test console duration; #0528 shows those durations mostly measure main-actor queueing.
