## Description

User request (2026-10-19, verbatim): "Fix tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM so it is not slow."

The test is `LMStudioDashboardPaneContentTests.tearDownReturnsPromptlyEvenWhenBothChildrenIgnoreSIGTERM()` (`BattyKit/Tests/BattyKitTests/LMStudioDashboardPaneContentTests.swift:686`). It spawns two real `/bin/sh` children that ignore `SIGTERM` (`LMStudioSIGTERMIgnoringFixture.makeProcess`, `LMStudioSIGTERMIgnoringFixture.swift:42`), calls `tearDown()`, proves via the closed `TestTeardownReapGate` that `tearDown()` returned while both children are alive, then opens the gate and awaits the real `SIGKILL` escalation.

## Resolution notes

> 🟢 Resolved 2026-10-19 — The `SIGTERM` → `SIGKILL` grace period now runs on an injected `SchedulingClock` (`TeardownReaper`), so the three `SIGTERM`-ignoring teardown tests advance it explicitly instead of waiting 0.2 s in real time, and the two wiring tests no longer block the main thread through it.

Carved-out scope, to be filed before the merge (the Plan's "Follow-ups"): `ProcessGitStatusScanner.reapAfterTerminate` and `ProcessGitStatusScannerTests` still measure the grace period in real time; `PendingTeardownReapRegistryTests` still register with the default `SystemClock()`.

## Root cause

`reapAfterTerminate` (in `LMStudioDashboardPaneContent` and, separately, in `PendingTeardownReapRegistry`) measured the SIGTERM → SIGKILL grace period with `Date()` and `Thread.sleep`, ignoring every injected clock. The three tests use `SIGTERM`-ignoring children, so each always waited the full `teardownWaitBound` (0.2 s) in real time. In the two wiring tests that wait ran on the main thread, through `waitForDeferredTeardown()` and `drainSynchronously()`.

## Fix

As planned. A new `TeardownReaper` holds one async reap. It races the grace sleep on an injected `SchedulingClock` against a 20 ms `Task.sleep` exit poll, sends `SIGKILL`, then waits up to `min(bound, 0.5)` in wall-clock time, which only runs out when the child survives `SIGKILL`. `reapBlocking` runs that reap on a detached task and waits on a semaphore, for the synchronous quit and drain paths. `LMStudioDashboardPaneContent` gained `teardownClock` (default `SystemClock()`). `PendingTeardownReapRegistry.register` gained `clock:`, defaulting to `SystemClock()`. Both private `reapAfterTerminate` copies are gone. Log messages and prefixes are unchanged, and production keeps the 0.5 s real grace period. `ProcessGitStatusScanner`'s copy is untouched; only stale doc-comment references were updated. The three tests inject a `TestClock` and advance 200 ms. The two wiring tests also hold a closed `TestTeardownReapGate`, and drive the clock from a detached task while the main actor is blocked. No deviations from the plan.

Round 2 (after the review bounce) changes comments and docs only. `LMStudioSIGTERMIgnoringFixture`'s doc comment now names `TeardownReaper.reap` instead of the deleted `LMStudioDashboardPaneContent.reapAfterTerminate`. The scanner's `reapAfterTerminate` doc comment in `GitStatusPaneContent.swift` no longer claims to mirror `TeardownReaper.reap` "exactly". It now says the two share the SIGTERM → bound → SIGKILL → bounded-poll shape, and that the scanner measures its grace period with `Date()` and `Thread.sleep`. `docs/async-test-seams.md` §5 item 3 now says the experiment mirrored the registry's then-`reapAfterTerminate`, whose loop now lives in `TeardownReaper.reap`. A repo grep (excluding `.build`, other worktrees and `issues/`) finds `reapAfterTerminate` only in references to `ProcessGitStatusScanner`'s copy, which still exists.

- **Most of the full-suite number is not this test's own work.** #0528's event-stream investigation found nearly all 2,588 tests start in the first second and end at 20–23 s, because they queue for the main actor behind other `@MainActor` tests that block it on child processes. This test hops back to the main actor several times (two FIFO readiness awaits, `waitForParkedWaiter(2)`, `awaitPendingTeardownReapsForTesting()`), and each hop queues again, so it finishes near the end. Its intrinsic cost is the ~0.35 s above.

### Where the intrinsic time goes

- The test sets `content.teardownWaitBound = 0.2` (`LMStudioDashboardPaneContentTests.swift:706`; production default `0.5`, `LMStudioDashboardPaneContent.swift:91`).
- Once the gate opens, each detached reap task (`scheduleTeardownReap`, `LMStudioDashboardPaneContent.swift:795–806`) runs `reapAfterTerminate` (`LMStudioDashboardPaneContent.swift:827–847`). It polls `process.isRunning` with `Thread.sleep(forTimeInterval: 0.02)` until a **wall-clock** deadline of `bound` (`:828–831`). The children ignore `SIGTERM`, so it always waits the full 0.2 s. It then sends `SIGKILL` and polls again in 20 ms steps for up to `min(bound, 0.5)` (`:837–841`).
- So of ~0.35 s, about 0.2 s is a fixed real-time grace period the test can't skip, plus up to 20 ms of poll granularity on each side of the `SIGKILL`, plus spawning two shells. The two streams reap in parallel on separate detached tasks, so it's ~0.2 s, not 0.4 s.
- That is a real-time wait in a unit test. `AGENTS.md` "Asynchronous tests (binding)" says periodic or timed work is "driven through an injected clock or scheduler the test advances explicitly, not by letting real time pass". The test's own structural proof (closed `TeardownReapGate`, `docs/async-test-seams.md` §3) is already correct; only the escalation half still lets real time pass.
- `content.clock = TestClock()` is already set in the test, but `reapAfterTerminate` is `nonisolated static`, uses `Date()` and `Thread.sleep`, and doesn't consult `clock`.

## Expected behavior

- The test proves the same two things it proves today: `tearDown()` returns while both `SIGTERM`-ignoring children are alive (closed gate, waiters parked), and both children are eventually `SIGKILL`ed and reaped.
- The `SIGTERM` → `SIGKILL` grace period no longer passes in real time in the test. Candidate directions for the plan to choose between:
  1. **Injected grace-period seam.** Route the grace deadline through an injected seam the test controls, for example the existing `SchedulingClock` (`docs/async-test-seams.md` §1) or a small escalation hook, so the test advances past the grace period explicitly. `reapAfterTerminate` is `nonisolated static` and synchronous today, and the quit path (`waitForDeferredTeardown()`) must stay synchronous, so the plan has to say how a sync caller and an async seam coexist.
  2. **Event-driven exit.** Replace the `Thread.sleep` `isRunning` polls with an exit event (`Process.terminationHandler` or a `DispatchSource` process-exit source) so the post-`SIGKILL` wait ends on the event rather than at the next 20 ms tick. This only removes poll granularity; on its own it doesn't remove the grace period.
  3. **Bound of zero in the test.** `teardownWaitBound = 0` makes the escalation immediate. Cheapest, but the test would no longer show that a grace period exists before `SIGKILL`. If chosen, coverage for "waits the bound before escalating" must live in a test that drives an injected clock.
- Production behavior is unchanged: 0.5 s default grace, same logging, quit path still synchronous and bounded.
- No new sleeps, polls or timing assertions in tests (`AGENTS.md` "Asynchronous tests").
- The two in-scope `LMStudioDashboardWiringTests` siblings use the same seam.

## Plan

Written 2026-10-19 (Phase 1). Premises checked against `issue/0529` at `8a338eb5`: line numbers, the `0.2` bounds, `reapAfterTerminate`'s `Date()`/`Thread.sleep` polls, and `content.clock` being ignored by the reap all match the description. Two corrections to the premises:

- The registry sibling (`registryDrainReapsATermIgnoringSubprocessLeftByAClosedPane`) spends its grace period in `PendingTeardownReapRegistry.reapAfterTerminate`, not the content's copy. `drainSynchronously()` runs it on the main thread. So that test can't be fixed without giving the registry the same seam. That much of the registry is in scope here. Its own `PendingTeardownReapRegistryTests` stay as they are (follow-up).
- Today, in the quit test and the registry test, the content's own detached reap tasks (open gate by default) race the synchronous path on the same processes. If only the synchronous path used the injected clock, the detached task would still run the real 0.2 s grace and could do the killing.

### Approach

Measure the SIGTERM → SIGKILL grace period on an injected `SchedulingClock`. Write one async implementation and have the synchronous quit and drain paths block on it. Production keeps `SystemClock`, so the real 0.5 s grace, the `SIGKILL` escalation, the post-`SIGKILL` bound and the log lines stay the same.

The async core must not block a cooperative-pool thread. A design where a `Thread.sleep` poll loop waits on a clock `Task` that needs a pool thread can deadlock once there are as many stuck reaps as cores. So exit-polling inside the async core uses `try? await Task.sleep(for: .milliseconds(20))`, a real-time poll interval for a `Process` with no async exit API. It is not the grace period, and the existing production code already polls at this interval.

### Files

1. **New `BattyKit/Sources/BattyKit/Runtime/TeardownReaper.swift`.** A `nonisolated enum TeardownReaper` with:
   - `static func reap(_ process: Process, bound: TimeInterval, label: String, clock: SchedulingClock, logger: Logger, logPrefix: String) async`:
     - If `!process.isRunning`, return at once without registering a sleeper.
     - Otherwise race `clock.sleep(for: .milliseconds(Int(bound * 1000)))` against an exit poll (`while process.isRunning && !Task.isCancelled { try? await Task.sleep(for: .milliseconds(20)) }`) in a `withTaskGroup`. Take the first result and `cancelAll()`. The clock sleeper is then removed on an early exit, so `TestClock.pendingCount` goes back to 0.
     - If the child is still running: log exactly as today, `kill(pid, SIGKILL)`, then poll `isRunning` with `Task.sleep(20 ms)` until it exits or a **real-time** deadline of `min(bound, 0.5)` passes. That deadline is reached only on the failure path ("still running after SIGKILL"), so it stays wall-clock and needs no test advance.
     - Same log messages as today, written as `"\(logPrefix): \(label) …"`.
   - `static func reapBlocking(…same parameters…)`: start `Task.detached(priority: .utility) { await reap(…); semaphore.signal() }`, then `semaphore.wait()`. Only synchronous callers use it (the quit path and the drain). The main thread waits on a semaphore, and the work runs on the pool without blocking a thread. Add a one-line why-comment on the bridge.
   - Passing in `logger`/`logPrefix` keeps each caller's Console category (`LMStudioDashboardPaneContent`, `PendingTeardownReapRegistry`) and its message prefix (`teardown:` and `drainSynchronously:`) unchanged.
