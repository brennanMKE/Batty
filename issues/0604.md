## Description

**High priority. Related to #0601 and #0602.** One Session switch makes 435 to 444 `_postWindowNeedsUpdateConstraints` requests with 4 Sessions and 651 to 660 with 16, measured with the #0601/#0602 layout probe. #0602 moved the selection side effects out of `SessionDetailView`'s `onChange`, and that removed only 4 to 45 requests per switch. So nearly all of the requests come from the selection change itself. `SessionDetailView` keeps every Session's `SplitContainerView` mounted in a `ForEach` and computes each Session's selected state in the parent body from the window-level `windowRuntime.selectedSessionID`. When the selection changes, the work spreads to every Session's subtree, not just the two Sessions whose selected state flipped. The Prod crash in #0601 had about 19 live Sessions, so this is the per-switch layout work that sits next to AppKit's update-constraints convergence cap (more passes than views in the window).

Goal: a Session switch invalidates only the Session being left and the Session being selected. The request count for 16 Sessions should be close to the count for 4, and a test should pin that scaling.

## Resolution notes

> 🟢 Resolved 2026-11-13 — Sidebar rows read a per-Session `SessionRuntime.isSelected` written only for the two Sessions a switch crosses, cutting the 16-vs-4 Session per-switch difference from 216 to 192; the remaining `List(selection:)` binding cost is a follow-up.

## Root cause

Confirmed by measurement (2026-11-13). After #0605 the detail column's per-switch work is flat (92 requests at 4 and at 16 Sessions). All of the Session-count scaling is in `SessionSidebarView`:

- Every row compared `session.id == windowRuntime.selectedSessionID` in the parent body's `ForEach` (the row's `accessibilityValue` and `SidebarRowBackground(isSelected:)`), so a switch re-ran every row. Keying those two reads on a constant cut the Sidebar-only count by 21 at 4 Sessions and 69 at 16 (attribution (a) → (b) under `## Notes`). Reading a per-Session fact instead, which still has to redraw the two rows a switch crosses, removes 24 of the 216 extra requests.
- The larger remainder belongs to the `List(selection:)` binding itself. With every row body reading nothing selection-dependent, a changing binding value still costs about 12 requests per row; a constant binding removes it. The parent body and the row bodies are not where that cost is: with the fix, a switch evaluates the parent body twice and only the two changed rows' bodies (twice each), at 4 and at 16 Sessions alike.

## Fix

- `SessionRuntime.isSelected` (observed, `public internal(set)`), written only by `WindowRuntime.applyTerminalVisibility`, beside `tree.isInSelectedSession`, for the (at most) two Sessions a selection change crosses. `init` and every `selectedSessionID` `didSet` already go through that function, so `addSession`, `addProjectSession`, `duplicateSession`, `removeSession`, `selectSession(at:)` and the Sidebar setter are all covered.
- The Sidebar's `ForEach` element is now `private struct SessionSidebarRow`, which reads `session.isSelected` for the row's value and background and computes `reminderState` in its own body. The parent passes plain values (`accent`, `sidebarFill`, `selectionTint`) and closures for its `@State` sheet triggers. `.tag(session.id as UUID?)` stays on the `ForEach` element; `List(selection:)`, `.selectionDisabled()` on Pane rows and the #0258 setter are unchanged.
- The WIP selected-Session-only mount is reverted: `AppStateStore`, `TabRuntime`, `TerminalHostStore`, `WindowRuntime`, `PaneView` and `SessionDetailView` match `main` apart from the `isSelected` writes. `Scratch0604MeasureTests.swift` is deleted.

Divergences from the plan:
- **No equality guard on the `isSelected` writes.** The plan said to guard because "`@Observable` notifies on equal-value writes". `AGENTS.md` (after #0618) says an equal `Equatable` write does not notify, so a `Bool` needs no guard; `reselectingTheSelectedSessionWritesNothing` pins that a re-selection fires nothing (the `didSet` returns early anyway).
- **Step 4 (`Equatable` row + `.equatable()`) is not landed.** `.equatable()` on the row crashes SwiftUI at hosting (`_DisclosureGroupContainer<...> may not have Body == Never`, `DynamicProperty.swift:380`). `Equatable` conformance without `.equatable()` measured no change, and the body counts above show the parent re-run already skips the unchanged rows, so there was nothing for it to save.
- **Scaling-test margin is 212, not 40** (orchestrator decision in advance): the measured 16-vs-4 difference after the fix is 192, plus 20. It still fails on the pre-fix code (216 > 212), but only by 4. The comment on `sessionCountMargin` names the remaining `List` binding cost.
- `rowIconName(for:)` became `fileprivate static` on `SessionSidebarView` so the row can call it. No unit test hosts a see-through Sidebar to check the row background trait (see Gotchas).
- The branch merged `main` at `b940f47d` (#0617) first, so the reverted files match current `main`.

### Premises checked (2026-11-13, against `main` sources)

- **Confirmed: `SessionSidebarView.body` depends on the window-level selection in three places.**
  - Each row's `accessibilityValue` (`SessionSidebarView.swift:179`) and each row's `SidebarRowBackground(isSelected:)` (`:188`) compare `session.id == windowRuntime.selectedSessionID` inside the `ForEach` closure.
  - `List(selection: sidebarSelection)` (`:93`) has a getter (`:286-289`) that returns `windowRuntime.selectedSessionID`.
  - So a switch re-runs the whole Sidebar body and the `ForEach` content for every row.
- **Confirmed: a re-run of the Sidebar body can't skip any row.** Each row gets values SwiftUI can't compare:
  - a fresh `DisclosureGroup(isExpanded: Binding(get:set:))`;
  - four closures passed to `SessionRow` (`onRename`, `onTheme`, `onSetColor`, `onBackground`);
  - `ReminderBadge`'s `onEdit` closure;
  - `PaneRow`'s `onBackgroundSettings` closure, once per Pane row.

  Each row's cell is therefore updated whenever the parent body runs. That fits the measured result: making `isSelected:` constant removed only 68 of 216 requests at 16 Sessions. **Hypothesis, not yet split apart:** the other ~168 come from the parent body still re-running every row through the `List` selection getter, or from `reminderState(for:)`, which reads the Bell Feed in the parent body. Implement step 2 measures this.
- **Confirmed: the parent body reads nothing else that changes on a plain switch.** It reads `windowRuntime.sessions`, `themeChrome`, `windowIsSeeThrough` and the sheet `@State`s.
  - The `didSet` (`WindowRuntime.swift:82-89`) writes `tree.isInSelectedSession`, which is `@ObservationIgnored`.
  - It calls `setVisible`, which is Pane content and not read by the Sidebar.
  - It writes the Bell Feed and `unseenBellCount` only when the selected Session has unseen entries, and the probe fixture has none.
- **Confirmed: a per-Session selected fact already exists, but views can't observe it.** `SplitTree.isInSelectedSession` (`Model/SplitTree.swift:177`) is `@ObservationIgnored` and is written only by `WindowRuntime.applyTerminalVisibility` (`WindowRuntime.swift:1043-1062`), for exactly the two Sessions a switch crosses. Its doc comment says no view reads it. The fix adds an observed sibling on `SessionRuntime` instead of changing that contract.
- **Confirmed: `SessionRuntime` is `@Observable`** (`Runtime/SessionRuntime.swift:7`). Rows already observe `session.unseenBellCount`, `title` and similar per-Session fields this way.
- **Confirmed: `session.id == windowRuntime.selectedSessionID` in `SessionRow`'s "Clear Session Theme" action** (`:536` on `main`) runs in an action, not in `body`. It stays.
- **Confirmed: the detail column's `ForEach` still compares against `selectedSessionID`** (`SessionDetailView.swift:265-266`). It measured flat, so it is out of scope. Leave it.
- **#0609** (Bell Feed counts scanned in view bodies) owns how `reminderState`/`unseenReminderEntries` are computed. This plan only moves the existing read from the parent body into the row's own body. It doesn't change the computation, and it must not touch #0609's scope.

### User checklist (Batty Beta)

1. With about 20 Sessions, switch with Cmd-1…9, Cmd-Shift-] and [, and by clicking rows. The highlight follows every time, and switching feels no slower.
2. Click a row, then use Up and Down arrows in the Sidebar. Selection moves Session to Session, skipping Pane rows.
3. With a themed or see-through window (Terminal Opacity 80), the selected row shows the subtle tint and only that row has it.
4. VoiceOver on a row reads "selected" or "unselected", plus unseen and Reminder state.
5. Expand a Session's Pane list, switch away and back. It stays expanded.

### Risks and open questions

- **The `List` selection binding may carry the remaining scaling** (the unattributed ~168). Step 4 bounds this to one attempt (an `Equatable` row), then a bail. Dropping `List(selection:)` needs the user's decision because of keyboard and VoiceOver regressions.
- **The row-trait move.** If `listRowBackground` or `.tag` behave differently from inside a custom view's body, the selection tint or selection could break. The design keeps `.tag` at the `ForEach` element and has a fallback for the background. `SidebarTests` in the daily run and checklist item 3 cover it.
- **A second selected fact.** `SessionRuntime.isSelected` and `SplitTree.isInSelectedSession` are written side by side in one function. A future write path that bypasses `applyTerminalVisibility` would desync both, so the doc comments name that function as the only writer.
- **A Bell Feed write during a switch** (when the selected Session has unseen entries) still invalidates rows through `reminderState`'s Feed scan. That is #0609's scope, and the probe fixture has no bells.
- **Confidence:** medium-high that step 3 removes the 68 from the `isSelected` reads and the row re-runs that come from the parent body. Medium on the remaining 168, until attribution (c)/(e) separates the `List` binding from the row re-runs. No user decision blocks the start.

## Current state (verified 2026-11-12 on `main` `9b299040`)

- `BattyKit/Sources/BattyKit/Views/SessionDetailView.swift`, `sessionStack`: `ForEach(windowRuntime.sessions) { session in SplitContainerView(tree: session.tree) ... }` applies three modifiers keyed on the window-level ID:
  ```swift
  .environment(\.isSelectedSession, session.id == windowRuntime.selectedSessionID)
  .opacity(session.id == windowRuntime.selectedSessionID ? 1 : 0)
  .allowsHitTesting(session.id == windowRuntime.selectedSessionID)
  ```
  The closure reads `windowRuntime.selectedSessionID`, so every switch re-runs `sessionStack` and the `ForEach` closure for every Session.
- The same `SessionDetailView` body also reads `windowRuntime.selectedSession` in about 20 places: `navigationTitle`, the toolbar split buttons' `.disabled`, the clipboard `confirmationDialog` (title, `presenting:`, actions), the `ContentUnavailableView` check, and the backdrop's `hasSelectedSession`. On `main` it also has the `onChange(of: windowRuntime.selectedSessionID)` and `onChange(of: windowRuntime.selectedSession?.tree.focusedPaneID)` handlers. On `issue/0602` the first handler and `onAppear` are deleted. So the toolbar and title also rebuild on every switch, which is a separate contributor from the `ForEach`.
- `BattyKit/Sources/BattyKit/Views/PaneView.swift` reads `@Environment(\.isSelectedSession) private var isSessionSelected` and passes `isVisible: tab.id == pane.activeTabID && isSessionSelected` to each `TerminalPlaceholderView`. `TerminalPlaceholderView` sends `isVisible` to the host in a `TerminalHostStore.Placement` from its geometry path and from `.onChange(of: isVisible)`. This is the path that hides and shows the terminal NSViews in the persistent host.
- `SessionSidebarView` also compares each row against `windowRuntime.selectedSessionID` (`isSelected:` and the row's `accessibilityValue`), so every sidebar row's body depends on the window-level ID too. The sidebar is a `List`, so it may or may not add to the probe's count; the planner should measure it rather than assume.
- `WindowRuntime.selectedSessionID`'s `didSet` already touches only the two Sessions involved: `applySelectionVisibility(deselecting:selecting:)` calls `setVisible(false)` on the previous Session's non-hidden Panes and `setVisible(true)` on the new one's, the latter only while `isWindowVisible`. The model side already scales with two Sessions. The view side does not.
- `SessionRuntime` is `@Observable` (`Runtime/SessionRuntime.swift`), so a per-Session observed property is available as a structural option.

Not yet established: whether the extra requests come from SwiftUI re-evaluating every `SplitContainerView`/`PaneView` body, from the modifier values being re-applied to every Session's hosting subtree even when unchanged, or mostly from the parent body's toolbar and title. The plan should split these apart with the probe before choosing a fix. For example, measure with the `ForEach` modifiers keyed on a constant, and with the toolbar removed.

## Expected behavior

- A Session switch re-renders only the Session being left and the Session being selected (detail subtrees and Sidebar rows), plus the window chrome that really depends on the selection (title, toolbar enablement, clipboard dialog).
- The probe's per-switch requests for 16 Sessions are close to those for 4. The plan should set the tolerance from before/after measurements, for example 16-Session max ≤ 4-Session max plus a small fixed margin, instead of the current ~18 requests per extra Session.
- Terminal behavior is unchanged: hidden Sessions' terminals stay hidden in the host, the selected Session's terminals show and take focus, and Panes in hidden Sessions stay suspended.

## Actual behavior

Per-switch requests grow linearly with the number of mounted Sessions (about 18 per extra one-Pane Session in the probe), because every Session's subtree depends on the window-level `selectedSessionID`.

## Constraints

Rewritten 2026-11-13 after the user's decision: **keep every Session mounted, and fix the Sidebar.** This replaces the 2026-11-12 "mount only the selected Session" decision.

- The detail column keeps its `ForEach` over every Session, with non-selected Sessions at `opacity(0)`. Terminals stay in the persistent AppKit host (`docs/view-hierarchy.md`), and nothing about terminal creation, wiring or visibility changes.
- A Sidebar row's selected state comes from a per-Session observed fact, `SessionRuntime.isSelected`. It is written by the model in `selectedSessionID`'s `didSet`, and only for the two Sessions that changed. The Sidebar body doesn't compare rows against `windowRuntime.selectedSessionID`.
- `List(selection:)` stays: keyboard navigation, type-select, VoiceOver selection semantics and the #0258 Pane-row guard are unchanged. Dropping it needs a new user decision.
- `docs/swiftui-observation-rules.md` is binding. No writes from `body` or layout-origin callbacks, no `Task` hop, and equal-value writes are guarded.
- #0609 owns how Bell Feed counts are computed. Don't duplicate it.
