# 0604 — A Session switch re-renders every mounted Session's views, so its layout work grows with the number of Sessions

| | |
|---|---|
| **Status** | open |
| **Module** | Session / Pane |
| **Platform** | macOS |
| **First seen** | 2026-11-12 |

## Description

**High priority. Related to #0601 and #0602.** One Session switch makes 435 to 444 `_postWindowNeedsUpdateConstraints` requests with 4 Sessions and 651 to 660 with 16, measured with the #0601/#0602 layout probe. #0602 moved the selection side effects out of `SessionDetailView`'s `onChange`, and that removed only 4 to 45 requests per switch. So nearly all of the requests come from the selection change itself. `SessionDetailView` keeps every Session's `SplitContainerView` mounted in a `ForEach` and computes each Session's selected state in the parent body from the window-level `windowRuntime.selectedSessionID`. When the selection changes, the work spreads to every Session's subtree, not just the two Sessions whose selected state flipped. The Prod crash in #0601 had about 19 live Sessions, so this is the per-switch layout work that sits next to AppKit's update-constraints convergence cap (more passes than views in the window).

Goal: a Session switch invalidates only the Session being left and the Session being selected. The request count for 16 Sessions should be close to the count for 4, and a test should pin that scaling.

## Current state (verified 2026-11-12 on `main` `9b299040`)

- `BattyKit/Sources/BattyKit/Views/SessionDetailView.swift`, `sessionStack`: `ForEach(windowRuntime.sessions) { session in SplitContainerView(tree: session.tree) ... }` applies three modifiers keyed on the window-level ID:
  ```swift
  .environment(\.isSelectedSession, session.id == windowRuntime.selectedSessionID)
  .opacity(session.id == windowRuntime.selectedSessionID ? 1 : 0)
  .allowsHitTesting(session.id == windowRuntime.selectedSessionID)
  ```
  The closure reads `windowRuntime.selectedSessionID`, so every switch re-runs `sessionStack` and the `ForEach` closure for every Session.
- The same `SessionDetailView` body also reads `windowRuntime.selectedSession` in about 20 places: `navigationTitle`, the toolbar split buttons' `.disabled`, the clipboard `confirmationDialog` (title, `presenting:`, actions), the `ContentUnavailableView` check, and the backdrop's `hasSelectedSession`. On `main` it also has the `onChange(of: windowRuntime.selectedSessionID)` and `onChange(of: windowRuntime.selectedSession?.tree.focusedPaneID)` handlers. On `issue/0602` the first handler and `onAppear` are deleted. So the toolbar and title also rebuild on every switch, which is a separate contributor from the `ForEach`.
- `BattyKit/Sources/BattyKit/Views/PaneView.swift` reads `@Environment(\.isSelectedSession) private var isSessionSelected` and passes `isVisible: tab.id == pane.activeTabID && isSessionSelected` to each `TerminalPlaceholderView`. `TerminalPlaceholderView` sends `isVisible` to the host in a `TerminalHostStore.Placement` from its geometry path and from `.onChange(of: isVisible)`. This is the path that hides and shows the terminal NSViews in the persistent host.
- `SessionSidebarView` also compares each row against `windowRuntime.selectedSessionID` (`isSelected:` and the row's `accessibilityValue`), so every sidebar row's body depends on the window-level ID too. The sidebar is a `List`, so it may or may not add to the probe's count; the planner should measure it rather than assume.
- `WindowRuntime.selectedSessionID`'s `didSet` already touches only the two Sessions involved: `applySelectionVisibility(deselecting:selecting:)` calls `setVisible(false)` on the previous Session's non-hidden Panes and `setVisible(true)` on the new one's, the latter only while `isWindowVisible`. The model side already scales with two Sessions. The view side does not.
- `SessionRuntime` is `@Observable` (`Runtime/SessionRuntime.swift`), so a per-Session observed property is available as a structural option.

Not yet established: whether the extra requests come from SwiftUI re-evaluating every `SplitContainerView`/`PaneView` body, from the modifier values being re-applied to every Session's hosting subtree even when unchanged, or mostly from the parent body's toolbar and title. The plan should split these apart with the probe before choosing a fix. For example, measure with the `ForEach` modifiers keyed on a constant, and with the toolbar removed.

## Measurements (from the #0602 implementer on `issue/0602`)

Probe: `SessionDetailLayoutConvergenceTests.sessionSwitchUpdateConstraintRequestsStayUnderCeiling(extraSessions:)` (exists on `issue/0602`, not yet on `main`). Per-switch `postNeedsUpdateConstraintsCalls` for the switches to Sessions `[1, 2, 3, 0]`, with each argument run **on its own**:

| | `extraSessions: 0` (4 Sessions) | `extraSessions: 12` (16 Sessions) |
|---|---|---|
| `main` sources | [444, 387, 342, 439] | [660, 627, 582, 655] |
| #0602 branch (effects moved to `didSet`) | [444, 366, 321, 439] | [660, 582, 537, 655] |
| #0602 branch, fixture with no bells, no Session Theme, no clipboard request | [435, 362, 317, 435] | [651, 578, 533, 651] |

Adding 12 Sessions adds about 216 requests per switch, about 18 per extra Session. Each extra Session has a single Pane.

**Measurement caveat:** the counts are stable only when one argument runs alone. Run with both arguments, or inside the full suite, the probe's `settle()` awaits interleave with other tests' main-actor work, and the same code reported [305, 301, 301, 311] for 4 Sessions and swung between [521, 517, 517, 516] and [660, 582, 537, 655] for 16. A ceiling or scaling test must be `.serialized`, or use one test per Session count.

## Expected behavior

- A Session switch re-renders only the Session being left and the Session being selected, plus the window chrome that really depends on the selection (title, toolbar enablement, clipboard dialog).
- The probe's per-switch requests for 16 Sessions are close to those for 4. The plan should set the tolerance from before/after measurements, for example 16-Session max ≤ 4-Session max plus a small fixed margin, instead of the current ~18 requests per extra Session.
- Terminal behavior is unchanged: hidden Sessions' terminals stay hidden in the host, the selected Session's terminals show and take focus, and Panes in hidden Sessions stay suspended.

## Actual behavior

Per-switch requests grow linearly with the number of mounted Sessions (about 18 per extra one-Pane Session in the probe), because every Session's subtree depends on the window-level `selectedSessionID`.

## Constraints

- Terminals stay in the persistent AppKit host (`docs/view-hierarchy.md`). `TerminalHostInstaller` and `TerminalHostView` are not restructured, and SwiftUI views still hold only `surfaceID`s. View rebuilds must not destroy surfaces.
- Non-selected Sessions stay mounted, so their placeholders keep reporting frames. Do not replace the `ForEach` with a view that mounts only the selected Session: unmounting would drop placeholder geometry and would also need a full checklist pass in `docs/terminal-pane-requirements.md`.
- Hidden Sessions' non-terminal content stays suspended through `setVisible`, driven from `WindowRuntime.applySelectionVisibility`, never from a view.
- `docs/swiftui-observation-rules.md` is binding. A per-Session `isSelected` (or similar) must be written by the selection action, `WindowRuntime.selectedSessionID`'s `didSet` or the code that changes the selection, never from `body`, `onChange` or a geometry callback. Write it only when the value changes, so that a switch writes exactly two Sessions.
- No `Task` hop to defer a write (#0229).

## Options (for the planner to evaluate)

1. **Per-Session observed selected state.** Add an `isSelected` property to `SessionRuntime` (or a small `@Observable` per-Session selection box). `WindowRuntime` sets it for the two Sessions in `selectedSessionID`'s `didSet`, and also on add, remove and initial selection. Move the `ForEach` body into a child view (for example `SessionLayerView(session:)`) that reads `session.isSelected` for the environment value, opacity and hit testing. The parent `ForEach` closure then doesn't read `selectedSessionID` at all, so a switch invalidates only the two child views whose `isSelected` changed.
2. **Narrow the parent body's reads.** Move the toolbar, title and clipboard dialog's `selectedSession` reads into small child views or computed sub-views, so a switch doesn't rebuild the whole `SessionDetailView` body. Combine this with option 1 if measurement shows the parent body contributes.
3. **Sidebar rows.** The same per-Session `isSelected` lets `SessionSidebarView` rows stop comparing against the window-level ID, if measurement shows the sidebar contributes. Selection binding semantics (#0258) must not change.

Keep `\.isSelectedSession` as the environment key PaneView reads, unless the plan finds a reason to change it. Its value just comes from the per-Session property instead of a parent-side comparison.

## Tests

- Bring the probe over from `issue/0602` (or from `main`, if #0602 has landed by then) and add a scaling test in `SessionDetailLayoutConvergenceTests`: measure per-switch requests for 4 and 16 Sessions in the same test, serialized, and assert that the 16-Session max is within a planner-justified margin of the 4-Session max. It must fail on the current code, which differs by about 216, and pass after. Record before and after numbers in `## Verification`.
- Unit tests for the per-Session selected state: exactly the two Sessions change on a switch, it is correct after `addSession`, `removeSession` of the selected Session, the initial selection and a reselect of the current Session (which writes nothing), and hidden Sessions' Pane content is still suspended (`setVisible(false)`). Use non-default fixtures (memory: "assert-unchanged" tests pass vacuously otherwise).
- Existing coverage that must keep passing: `PaneViewRenderTests`, the `SessionDetailLayoutConvergenceTests` convergence cases, and `WindowRuntimeSessionSelectionVisibilityTests`.
- UI coverage to re-run in the VM at the daily run: Session switching with Cmd-1..9 and from the sidebar, terminal focus after a switch, and file drop onto a Pane after a switch (`docs/terminal-pane-requirements.md` checklist).

## Notes

- #0601 identified `_postWindowNeedsUpdateConstraints` as AppKit's non-convergence guard: it throws once a window runs more update-constraints passes than it has views. Requests are not passes, and the probe saw every switch converge, so this issue does not claim a loop. It removes the per-Session scaling that makes a switch in a many-Session window do far more layout work than needed.
- #0602's restructure (selection effects in `didSet`) is parked on `issue/0602` at its bail point. If #0602 lands first, plan against that code. Its `SessionDetailView` no longer has the selection `onChange`.
