# 0309 — No keyboard shortcut types exit and Enter into the focused Terminal Session to quickly end the shell

| | |
|---|---|
| **Status** | open |
| **Module** | App / TerminalSurface |
| **Platform** | macOS |
| **First seen** | 2026-08-04 |

## Description

Feature gap: there is no keyboard shortcut that writes the literal text `exit` followed by a newline into the focused Terminal Session. The user wants to hit Cmd-X in a Terminal pane to quickly end the shell — which, per existing lifecycle rules, closes the tab/pane once the shell process exits.

Requested behavior, verbatim intent: "I'd like to hit Cmd-X to input `exit` with the Enter key in a Terminal pane to quickly exit."

## Expected behavior

With a Terminal pane focused, a single keyboard shortcut sends `exit\n` to that pane's Terminal Session, ending the foreground shell the same as typing `exit` and pressing Return.

## Actual behavior

No such shortcut exists. ⌘X currently reaches Edit ▸ Cut (see Open questions), which does nothing meaningful in a Terminal pane.

## Open questions

**⌘X collides with the standard macOS Cut shortcut — this needs the user's call before implementation.**

Batty already claims ⌘X: `BattyCommands.swift` replaces the `.pasteboard` command group and defines Edit ▸ Cut bound to `⌘X`, dispatching `NSText.cut(_:)` down the responder chain (`BattyKit/Sources/BattyKit/Commands/BattyCommands.swift`, the `CommandGroup(replacing: .pasteboard)` block). That Cut item is real and useful for editable text fields elsewhere in the window — sidebar Session rename, Tab rename, Settings fields — where `NSText.cut(_:)` resolves to the first responder's text view. Terminal panes themselves have no selection-cut: the terminal surface is not an `NSText`, so in a Terminal pane the existing ⌘X is effectively a no-op today (copy is the terminal-side pasteboard verb; there is nothing to cut from a read-only surface).

Options, laid out neutrally — none chosen:

1. **Claim ⌘X globally** for "type exit" — simplest, but Edit ▸ Cut loses its key equivalent, breaking cut in rename fields and Settings.
2. **Claim ⌘X conditionally** — behave as "type exit" only when a Terminal pane is first responder, fall through to `NSText.cut(_:)` otherwise. Precedent exists: `PasteDispatcher.handlePasteRequest` (`BattyKit/Sources/BattyKit/Views/PasteConfirmation.swift`) already forwards ⌘V to the standard `NSText.paste(_:)` when `isEditingTextField` detects an editable `NSTextView`/`NSTextField` first responder, and only routes to the terminal otherwise. The same responder check would work here. Cost: a system-standard chord silently changes meaning by focus context.
3. **Use a different chord** (e.g. something under ⌘⇧ or ⌃) and leave Cut untouched — least surprising, but not the chord the user asked for.

Secondary decisions to make at implementation time (raised, not decided):

- **Foreground process is not a shell.** If `vim`, `ssh`, a REPL, or any full-screen program is running, `exit\n` is just typed into that program (in vim it inserts text or errors; in ssh it exits the remote shell, not the local pane). Options: send unconditionally and accept that, or gate/confirm somehow. libghostty offers no cheap "is the foreground process a shell" check from the send path used here.
- **Menu item vs invisible key handler.** A real menu item (discoverable, shows the key equivalent, participates in the customizable-shortcut system — `ShortcutAction` / `ShortcutsStore` in `BattyKit/Sources/BattyKit/Shortcuts/` back nearly every existing chord and surface in Settings) versus a bare key handler nobody can discover or rebind. Existing convention strongly favors a `ShortcutAction` case plus a menu item, but ⌘X-vs-Cut interacts with this: a menu item's key equivalent is claimed window-wide by AppKit, which pushes toward option 2's responder-aware dispatch inside the action rather than SwiftUI-level shortcut swapping.

## Notes

Relevant code locations, verified read-only:

- **Menu commands / shortcuts** — `BattyKit/Sources/BattyKit/Commands/BattyCommands.swift` (SwiftUI `Commands` with `CommandGroup`/`CommandMenu`; wired from `Batty/BattyApp.swift`). Customizable chords live in `BattyKit/Sources/BattyKit/Shortcuts/ShortcutAction.swift` + `ShortcutsStore.swift`.
- **Send-text path into a live Terminal Session** — the paste flow is the model: `PasteDispatcher` resolves the focused terminal tab via `(store.keyWindowRuntime() ?? store.windows[0]).selectedSession?.focusedPane.activeTab` and calls `tab.terminal.send(text)` (`TerminalViewState.send(_:)` from the `GhosttyTerminal` product of `libghostty-spm`). `AppTerminalView.sendText(_:)` is the equivalent NSView-level wrapper ("Send raw UTF-8 text directly to the underlying pty, bypassing key translation"). Sending `"exit\n"` through the same path is the whole write side of this feature.
- Terminal lifecycle already handles shell exit → tab close, so no new teardown work is expected; this issue is purely input + shortcut routing.
