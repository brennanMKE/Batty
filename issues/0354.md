# 0354 — Closing an LM Studio dashboard pane can block the main actor for up to a second in waitBounded

## Description

`LMStudioDashboardPaneContent.waitBounded(for:label:)` waits for a terminated subprocess to actually exit by spinning `Thread.sleep(forTimeInterval: 0.02)` on the calling thread — the main actor — up to `teardownWaitBound` (0.5 s). Teardown runs it once per log-stream subprocess (`model-stream` and `runtime-stream`), so `closePane` on a dashboard pane whose `lms` processes are slow to die can beach-ball the app for roughly 1 second.

This was a deliberate, reviewed choice: the wait is bounded precisely so a wedged `lms` can never hang the main actor indefinitely, and synchronous teardown keeps the lifecycle contract simple. But 2 × 0.5 s of main-thread stall on a user-initiated close is user-visible jank, and it was deferred out of the #0313 review round as follow-up rather than blessed as final.

## Expected behavior

Pane close feels instant. The bounded wait (and the SIGTERM escalation it backs) happens off the main actor — e.g. terminate synchronously, then hand the "wait briefly, then SIGKILL" tail to a background task that owns the `Process` references — without weakening the guarantee that the subprocesses are actually reaped.

## Actual behavior

`closePane` on a dashboard pane synchronously blocks the main actor up to 0.5 s per stream (two streams) while waiting for the `lms log stream` subprocesses to exit.

## Resolution notes

> 🟢 Resolved 2026-09-23 — closing an LM Studio dashboard pane no longer blocks the main actor: `tearDown()` sends SIGTERM and finishes its lifecycle transition synchronously, and the bounded wait plus a new SIGKILL escalation run off the main actor. On quit, the wait runs synchronously so no `lms` child is orphaned.

## Root cause

`tearDown()` called `terminateModelStream/terminateRuntimeStream(boundedWait: true)`, each polling with `Thread.sleep` for up to `teardownWaitBound` (0.5 s) on the main actor — up to ~1 s per close. A child that ignored SIGTERM was only logged, never killed.

## Fix

- `tearDown()` still sends SIGTERM and moves the `PaneLifecycleController` to `.tornDown` before returning. `scheduleTeardownReap(for:label:)` runs `reapAfterTerminate` on a detached task: it waits for exit within the bound, sends SIGKILL if the child is still running, then re-polls `isRunning` so completion means the child has exited.
- Quit path: `DeferredTeardownWaiting` plus `WindowRuntime.tearDownAllPaneContentSynchronouslyForQuit()`, which `applicationWillTerminate` calls for every window, waits synchronously. Worst case is about 1.0 s per SIGTERM-ignoring stream, sequentially (two streams per dashboard); all SIGTERMs are sent before any wait. The window-close path stays non-blocking.
- `docs/pane-view-lifecycle.md` §5 gained an explicit, bounded exception for subprocess teardown; `docs/design/lmstudio-dashboard-view.md` §6/§7 corrected.

## Gotchas

- A reap scheduled by closing a window or pane less than about 1 s before quit is not reachable from the quit wait; a SIGTERM-ignoring child in that window would still be orphaned. Unlikely; not addressed.
