## Description

The user's framing, which is apt: the `batty` CLI essentially acts like an MCP server with tool calling — an agent's whole interaction with it is "discover what tools exist, learn their parameters, call them, read structured results." MCP solved the discovery half with `tools/list`: every tool carries a `name`, a `description`, and a JSON Schema `inputSchema` whose enum-valued parameters enumerate their allowed values. `batty capabilities` (#0384) built the roster but stopped at names: an agent can learn *that* `pane split` exists, and nothing else about it.

**What `capabilities --json` emits today** (verified by running the built binary, 2026-09-09): exactly three top-level keys — `cliVersion`, `exitCodes`, `verbs` (`BattyKit/Sources/BattyXPCCore/CapabilitiesPayload.swift:32-35`). Each of the 16 verb entries is `{name, abstract, aliases}` (`CapabilitiesPayload.swift:11-14`) — no parameters, no flags, no types, no constraints.

**Pane kinds appear zero times in that output.** Grep of the live JSON confirms it. The five kinds are a `String`-backed enum — `terminal`, `git-status`, `process-status`, `lm-studio-dashboard`, `system-metrics` (`BattyKit/Sources/BattyXPCCore/PaneContentKind.swift:28-41`, display names at `:64-71`). The only ways an agent learns them today:

- `batty pane split --help` — the kind list is string-interpolated into the `--view` flag's help text (`BattyKit/Sources/batty/PaneCommand.swift:86`), ArgumentParser's human formatting, not a contract.
- Guessing wrong — the client-side validator's exit-1 error enumerates the valid raw values (`PaneCommand.swift:38-43`).
- Since #0379, reading `kind` off existing Panes in `list --json` — which reveals only kinds already in use, never the full vocabulary.

**Consequently no flag is discoverable machine-readably.** Not `--unique` (#0383), not `--view`/`--pid`/`--path` (#0315), not `--no-wait` (`BattyKit/Sources/batty/NewSessionCommand.swift:45`, #0380), not `--json`, not `--pane`. Nor are the conflicts, which live only in imperative validation code inside `runLogic`:

- `--unique` requires a non-terminal `--view` (`PaneCommand.swift:125-129`).
- `--command` is rejected against any non-terminal `--view` (`PaneCommand.swift:131-134`).
- `--pid` is only valid with `--view process-status` (`PaneCommand.swift:137`).
- `--path` is only valid with `--view git-status` (`PaneCommand.swift:150-158`).

**The concrete cost is already on record.** #0383's implementation note (`issues/0383.md:52`): an app predating `--unique` silently ignores the flag and creates a duplicate Pane, and "there is no capability round trip the CLI can use to detect that case ahead of time (`batty capabilities`, #0384, describes only this CLI binary's own compiled-in surface, not the app's)." #0384's own Gotchas said the same at filing: "`capabilities` reports verbs but not flags — an agent still cannot discover that `list` accepts `--json`. … the obvious next increment if agent self-description is the goal." This issue is that increment.

## What MCP's `tools/list` actually specifies

For the analogy to be load-bearing rather than decorative (checked against the current spec revision, 2026-07-28, modelcontextprotocol.io/specification, on 2026-09-09):

- Each tool: `name` (unique id, 1–128 chars), optional `title` (human display name), `description`, **`inputSchema` — a JSON Schema object** (dialect defaults to 2020-12 unless `$schema` says otherwise) with `type: "object"`, `properties`, and `required`; optional `outputSchema` for structured results; optional `annotations`.
- Enum-valued parameters use JSON Schema's `enum` keyword: `"view": {"type": "string", "enum": ["terminal", "git-status", …]}` — exactly the shape the pane-kind gap needs.
- `annotations` (in the spec since revision 2025-03-26) carries behavioral hints: `readOnlyHint` (does not mutate), `destructiveHint` (modification may be irreversible), `idempotentHint` (safe to repeat with the same arguments), `openWorldHint` — hints, not guarantees, with worst-case defaults. These map almost one-to-one onto distinctions Batty's docs currently spell out in prose: `list`/`status`/`id` are read-only; `session close`/`pane close` are destructive; `pane hide`/`pane show` are idempotent (`docs/batty-cli-agent-workflows.md`, "idempotent: hiding an already-hidden Pane … succeeds quietly"); `pane split` without `--unique` is *not* idempotent, which is the entire lesson of #0383.
- Cross-parameter conflicts have no first-class JSON Schema-independent field in MCP; servers express them in `description` text or via JSON Schema composition (`allOf`/`not`). Whatever shape is chosen here, the four conflicts above must be stated *somewhere* machine-adjacent, not only in Swift validation code.

The analogous `batty capabilities --json` would give each verb entry an `inputSchema`-shaped `parameters` object (name, type, required, default, allowed values, help text) plus behavioral annotations — additively, keeping the existing three keys and `{name, abstract, aliases}` intact, since #0384 shipped that shape and scripts parse it.

## ArgumentParser already holds most of this — verified, with two gaps

This is largely a serialization problem, not new knowledge, and the claim was verified against the pinned ArgumentParser 1.8.2 (`BattyKit/Package.resolved`), not assumed:

- **A machine-readable dump already exists and runs.** Every ArgumentParser CLI has a hidden built-in `--experimental-dump-help` flag (checkout `Sources/ArgumentParser/Parsing/CommandParser.swift:147`). `batty pane split --experimental-dump-help` was run against the built binary on 2026-09-09 and emits `ToolInfoV0` JSON (`Sources/ArgumentParserToolInfo/ToolInfo.swift`): per argument it carries `kind` (positional/option/flag), `isOptional`, `isRepeating`, `names`, `preferredName`, `valueName`, `defaultValue`, `allValueStrings`/`allValues`, `allValueDescriptions`, `abstract`, `discussion`.
- **Gap 1 — `--view` is typed `String?`, so its enum values are invisible even to ArgumentParser.** In the dump, `view` has `allValues: null`: `allValueStrings` is populated only when the property is typed as a `CaseIterable` `ExpressibleByArgument` enum, and `PaneCommand.swift:87` declares `var view: String?`, validating by hand at `:38-43` instead. Retyping `--view` as `PaneContentKind` would move the vocabulary into ArgumentParser's own metadata — one plausible first step under any candidate below. (Contrast: `direction` *is* a real `EnumerableFlag` enum (`PaneCommand.swift:71-72`), yet the dump flattens it into two separate boolean flags `-h`/`-v` — a faithful schema wants one logical `direction` enum parameter, so even enum-typed flags need a mapping pass.)
- **Gap 2 — conflicts are invisible to any dump.** ArgumentParser has no declarative cross-flag constraint API; the four conflicts above are imperative Swift. No derivation can surface them; they need either schema composition, description text, or a small hand-maintained constraints table with a drift test.

## Expected behavior

`batty capabilities --json` (or an additive variant of it) tells an agent, machine-readably, everything it needs to call any verb correctly without reading `--help` prose or the source:

- Every parameter of every verb: name(s), kind, type, required/optional, default, help text.
- Every enum-valued parameter carries its allowed values — pane kinds and split direction are the two the user hit.
- The known cross-parameter conflicts are represented, not left in Swift validation code only.
- The roster stays **derived, not hand-maintained** — `CapabilitiesCommand.verbs()` walks `BattyCLI.configuration.subcommands` live (`BattyKit/Sources/batty/CapabilitiesCommand.swift:66-68`) precisely so a new verb cannot silently go unreported (#0384's pinned decision), and parameter reporting must preserve that property: a new flag added to a command must show up without anyone remembering to update a second list. Where hand-authored detail is unavoidable (conflicts, logical-enum mapping), a test must fail when it drifts from the parsed surface.
- The #0384 pins stand: static, no XPC round trip, exit 0 with Batty not running, additive JSON evolution. And the payload still describes *this CLI binary's* compiled-in surface, not the running app's (`issues/0383.md:52`) — closing the CLI-vs-app skew is #0403's territory, not this issue's.

## Candidate directions (deliberately not decided here)

Like #0332 and #0396, this files the property, not the mechanism:

1. **Serialize ArgumentParser's own metadata into `verbs[]`.** Walk each leaf command's argument set (the machinery behind `--experimental-dump-help`) and translate `ArgumentInfoV0`-shaped facts into an MCP-style `inputSchema` per verb, after retyping `--view` as `PaneContentKind`. Pro: derived by construction; a new `@Option` appears automatically. Con: the dump machinery is marked experimental upstream (serialization version 0) and `ToolInfoV0` lives in a separate `ArgumentParserToolInfo` module — pinning payload stability to an SPI-ish surface across ArgumentParser bumps needs a guard test; and the two gaps above still need hand-shaping (direction pair → one enum; conflicts).
2. **Just expose the raw dump** — document `--experimental-dump-help`, or wrap it as `capabilities --tools` passing through ToolInfo JSON. Cheapest. Con: the shape is ArgumentParser's, not MCP's; it is explicitly experimental and version-stamped by a third party; `--view`'s enum values are absent until retyped; conflicts absent entirely; and agents get a second JSON dialect to learn alongside the existing `capabilities` shape.
3. **Hand-authored JSON Schema per verb, drift-gated by test.** Each command contributes a small Codable schema; a unit test cross-checks every schema property against the live parsed surface (via the dump) in both directions, so a flag added without schema — or a schema entry for a removed flag — fails `./build.sh unit`. Pro: full MCP fidelity including conflicts and annotations (`readOnlyHint`/`destructiveHint`/`idempotentHint` map cleanly onto Batty's verb semantics). Con: the most authored text; the drift test is the only thing keeping it honest, and it must actually compare against the parser, not restate itself (#0384's Review noted a tautological-test hazard in exactly this file family).
4. **An actual MCP server** (`batty mcp serve` or similar) is deliberately **not** proposed here. The user's framing is "borrow from how MCPs define tool calls," not "become an MCP server"; the CLI-over-XPC transport already exists and works, and a second protocol surface is a much bigger commitment than a schema field. If that ever becomes worth it, this issue's schemas are the prerequisite either way.

Whichever direction: keep `{name, abstract, aliases}` and the three top-level keys byte-compatible, add fields additively, and state in the payload which JSON Schema dialect (2020-12, per MCP) the schemas follow if schemas are the shape chosen.

## Gotchas

- **`cliKind` is not drift-checked.** Re-declaring `pane split`'s real
  `-c/--command` option as `cliKind: .positional, names: []` passes all 38
  tests, because `assertNamesAreInvocable` gives positionals a free pass on an
  empty `names`. An agent following that schema would emit
  `batty pane split "npm test"` and get exit 64. Every shipped `cliKind` is
  correct today — this is drift-prevention, not a live defect. The fix is ~6
  lines in the same helper: `wrappedPropertyNames` already reads
  `type(of: child.value)`, so it can return the wrapper kind alongside the name
  and assert it matches the declared `cliKind`, closing the whole dimension
  rather than the positional case alone.
- **`enumValueNames` is inferable but not labelled.** `cliKind: "flag"` covers
  both `--unique` (a switch) and `direction` (a collapsed `EnumerableFlag`
  pair), disambiguated only by which of `names`/`enumValueNames` is populated —
  a convention documented in Swift doc comments the consumer never sees. It is
  derivable, and misreading `names: []` as "not passable" degrades to the
  default `horizontal` rather than producing a wrong invocation. A fourth
  `CLIKind` case (`enumFlag`) would label it, but note the compatibility
  wrinkle: adding an enum case later breaks a consumer switching exhaustively
  on `cliKind`, so it is cheaper now than after #0403 ships.
- **`properties` is an unordered JSON object, so positional *order* is
  unrecoverable.** Harmless today — no command has more than one positional —
  but a future verb with two would be uncomposable from the payload. The shape
  needs an `order`/index field before that happens.
- **No `outputSchema`.** `pane split` printing the new Pane id lives only in
  `abstract` prose, so #0403's central recipe — capture the id — is not
  machine-readable. MCP makes `outputSchema` optional and this issue scoped
  itself to signatures, so it is correctly out of scope; it is the obvious next
  increment, mirroring how #0384's Gotchas named this one.
- **The schemas are hand-authored, drift-gated by test — not derived.** A new
  flag does not appear automatically; a test goes red instead. That gate is
  real (set equality against Mirror-derived stored properties, failing in both
  directions), but the distinction matters for how far the payload can be
  trusted without the tests.
