## Description

Cmd-V paste with a payload containing newlines surfaces a confirmation sheet ("Paste 3 lines?") to avoid the classic `rm -rf` paste footgun (PRD §6.10).

**Acceptance criteria:**
- On Cmd-V, if the clipboard text contains a newline, present a sheet showing:
  - The line count.
  - A scrollable preview of the payload (first ~10 lines, truncated with ellipsis).
  - "Paste" and "Cancel" buttons.
- "Paste" injects the text via `ghostty_surface_text(...)`. "Cancel" does nothing.
- A Settings toggle controls strictness:
  - **Always confirm on multi-line paste** (default).
  - **Confirm only when payload contains shell metacharacters** (e.g. `;`, `|`, `&&`, `\n` followed by `rm`/`sudo`).
  - **Never confirm.**
- Single-line pastes never prompt.

## Notes

- The two strictness levels beyond "always" are nice-to-have; ship "always" first and add the more permissive options as part of this issue or a follow-up.
- This is a v1-must-have per PRD §6.10. Don't disable confirmation by default.

### Deferred — 2026-05-08

Cmd-V paste in Batty currently routes through GhosttyTerminal's built-in clipboard handling at the AppKit layer; SwiftUI-level interception via `.onPasteCommand` may not fire because the AppKit path takes the keystroke first. Properly intercepting paste needs either:

1. Wrapping `TerminalView` in a custom `NSViewRepresentable` so we can override paste at the AppKit level. Same blocker as `#0022` / `#0024`.
2. An upstream PR adding a paste-interceptor delegate or a public `sendText` we can call after our own confirmation.

Same upstream-vs-custom-wrapper decision as the rest of the delegate-plumbing group. Deferred until that decision is made.

In the meantime, the existing GhosttyTerminal paste behavior is the user-visible default — multi-line pastes go through directly, with the standard `rm -rf` footgun risk per PRD §6.10. Worth flagging in any user-facing release notes until this lands.

## Root cause

Paste went directly through libghostty, with no Batty-side opportunity to inspect the payload first. The two upstream fixes (custom NSViewRepresentable wrapper, or upstream PR exposing a paste interceptor) were both blocked. After #0044 made `TerminalViewState.send(_:)` public, intercepting the menu-level `Cmd-V` and injecting the result manually became viable.

## Fix

Replace the standard `.pasteboard` CommandGroup with a Batty-flavored Paste, route the payload through a strictness check, and surface a confirmation sheet for risky text.

- `PasteStrictness` enum — `alwaysOnMultiline` (default), `onShellMetacharacters`, `never`. `shouldConfirm(_:)` returns true based on the mode and a small dangerous-token list (`rm `, `sudo `, `dd `, ` > /`, ` | sh`, `&&`, `;`).
- `SettingsPreference.pasteStrictnessKey` + `resolvedPasteStrictness()` — UserDefaults-backed.
- `PasteDispatcher.handlePasteRequest(store:)` is the menu's action:
  - If the focused responder is an NSTextView/editable NSTextField, dispatch the standard `NSText.paste(_:)` selector via the responder chain so the user's TextField paste still works.
  - Otherwise, read `NSPasteboard.general.string(forType: .string)`, run `strictness.shouldConfirm`, and either call `tab.terminal.send(text)` directly or post `Notification.Name.battyRequestPaste` with a `PendingPaste` payload.
- `SessionDetailView.onReceive(.battyRequestPaste)` stores the pending paste in `@State`, presents `PasteConfirmationSheet` via `.sheet(item:)`. Confirm calls `PasteDispatcher.confirm` which calls `terminal.send`. Cancel clears the state.
- `PasteConfirmationSheet`: "Paste N lines?" headline, monospaced ScrollView preview (first 10 lines + "…(N more lines)"), Cancel/Paste buttons.
- `BattyCommands` replaces the `.pasteboard` group with our Paste plus Copy/Cut/Select-All as plain forwarders to the standard responder-chain selectors (so those menu items still exist with their canonical shortcuts).
- Settings General pane gains a strictness `Picker`.

## Gotchas

- **TextField Cmd-V works because we inspect `NSApp.keyWindow?.firstResponder`** before doing anything terminal-flavored. If the responder is `NSTextView` (used by SwiftUI's `TextField` underneath) or an editable `NSTextField`, we forward the standard `NSText.paste(_:)` action via `NSApp.sendAction` and the field gets the paste through the responder chain. Without this check, Cmd-V into the rename-session sheet would attempt to paste into the focused terminal instead.
- **The "shell metacharacters" mode is heuristic, not a safe sandbox.** It catches the common dangerous tokens but a determined paste-bomb could still slip through (e.g., `eval ...` in a heredoc). Treat it as a UX speed-bump, not a security boundary.
- **Strictness check runs against the pasteboard text, not after libghostty's bracketed-paste decoration.** That's the right level — we're protecting the user from what they're about to paste, not from what libghostty is going to wrap it with.
- **`PendingPaste` is a value type with a fresh UUID per construction.** SwiftUI's `.sheet(item:)` reuses the sheet only when the `Identifiable.id` is stable, so each request triggers a new sheet — desirable here because the user expects a fresh confirmation per Cmd-V.
- **Replacing `.pasteboard` CommandGroup means we own the menu items entirely.** That includes Copy/Cut/Select All — these are now plain forwarders. If we ever want anything terminal-specific for Copy (e.g., copy-on-select), this is where it'd live.
- **`.battyRequestPaste` is delivered to the SessionDetailView via NotificationCenter** rather than `@FocusedValue` because commands and view-local `@State` don't share a memory space (same pattern as #0026's `.battyToggleBellFeed`).
- **The OnShellMetacharacters mode requires multi-line plus a dangerous token.** A single-line paste of `sudo rm -rf` does NOT trigger confirmation — only multi-line that LOOKS like a script gets the prompt. Users who want stricter behavior should pick the alwaysOnMultiline mode (the default).
- **Paste continues to work even with the focus check failing in non-terminal app states** (e.g., the app menu is open but no window has key focus): the dispatcher's `forwardStandardPaste` selector goes through the standard responder chain.
