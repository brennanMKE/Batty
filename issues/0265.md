## Description

The throwaway prototype this ticket originally called for has been **built, outside this repo, and it succeeded**: the RemoteControl experiment app + CLI at `/Users/brennan/Developer/brennanMKE/RemoteControl` implemented *both* transports (URL scheme and XPC) end to end, with per-issue verification records. The user's verdict: "This worked really well and it is what we want to do." This ticket is therefore no longer a speculative evaluation — it is the **decision record plus port plan**. The original six evaluation questions are preserved below under "Predicted vs. found" with what the experiment actually answered.

**The decision is a hybrid — not "adopt XPC."** The experiment's findings doc is precise about this and the ticket must be too. Verbatim positions from `FINDINGS.md`:

- Keep the URL scheme for fire-and-forget commands; add XPC only for commands that genuinely need data back or streaming. "Do not replace the URL scheme with XPC wholesale — the machinery is real and it buys nothing for `open this path`."
- "Ship the URL scheme first because it is nearly free, and add the XPC layer when the first command genuinely needs a reply. **Do not build the broker speculatively.**"
- "Consider whether you need a session at all." Phase 2 request/reply delivered most of the value — real data back, real exit codes — for a fraction of Phase 3's long-lived-session complexity. If Batty has no streaming use case, "stopping at request/reply is a defensible and much cheaper endpoint."

## What this decides for #0257

#0257 Foundation §5 pinned: mutations over one-way `batty://`, topology reads from an app-written JSON snapshot (Option B), two-way channel deferred to Tier 3 as a *Unix socket*. This ticket's outcome maps onto that tiering cleanly:

- **Tier 0/1 mutations stay on `batty://`, unchanged.** The experiment confirmed the URL scheme "wins outright, and it is not close" for launch-if-not-running, and that fire-and-forget commands gain nothing from XPC.
- **Amends #0257 §5: the Tier 3 two-way transport is XPC** (broker launch agent + `NSXPCConnection`), not a raw Unix socket. XPC is what unblocks the deferred Tier 3 read verbs — `list`, `read`, `wait`, `send`/`send-key`, `events subscribe` — plus real exit codes for scripted use.
- **Honest caveat:** the raw Unix socket was never built head-to-head; the experiment compared URL scheme vs. XPC only (the word "socket" does not appear in `FINDINGS.md`). The decision rests on XPC's demonstrated properties plus the user's adoption call, not a socket bake-off.
- **Open question — Option B (the JSON topology snapshot).** Once request/reply exists, a live `list` reply may make the snapshot file redundant; alternatively Option B may stay worth keeping as the cheap path that works with no agent installed and no approval granted (every CLI command over XPC fails while `SMAppService` sits in `requiresApproval` — see traps below). If both exist, #0257's own guidance holds: shape them so the `list` reply reuses the snapshot's JSON schema verbatim. Raised here, **not decided**.
- **Sequencing, per the findings:** do not build the broker until the first command genuinely needs a reply. Start at request/reply; add long-lived sessions only when a concrete streaming feature demands push.

## What the experiment demonstrated (evidence)

**Capabilities.** Over XPC, typed request/reply (`remotectl status` returned the app's real pid, uptime, window count, client count out of the live process; round trip measured at 0.3 ms), distinct failure exit codes, streaming progress, app-initiated events, and long-lived sessions (verified 3+ minutes, 18 heartbeats; a 1 GB file hashed in 1 MiB chunks with progress streaming back and the final SHA-256 matching `shasum -a 256`; events fanning out to two concurrent sessions). The URL scheme can do none of that — but launches the app trivially, which XPC cannot.

**The sharpest illustration** — same app, same bad path:

```
$ remotectl open ~/NoSuchDirectory
remotectl: no such path: /Users/you/NoSuchDirectory      exit 4

$ remotectl open ~/NoSuchDirectory --via-url
opened remotecontrol://cli?action=open&param1=…          exit 0
```

Only the app can know the path does not exist. Over the URL scheme the CLI reports success anyway, because success only means LaunchServices accepted the URL — not a fixable defect; there is no reply channel to fix. This is the single strongest argument for the hybrid: exactly Batty's known limitation today (`docs/batty-cli-install.md` §"Known limitations": a `batty /valid/dir` reaching a running-but-broken Batty still exits 0).

**Cold start.** The app's XPC endpoint only exists once the app is running and has registered it, so reaching a not-running app is a five-step dance:

1. connect to the broker's Mach service (launchd starts the agent on demand),
2. ask the broker for the app's endpoint,
3. if `nil`, launch the app by bundle identifier,
4. **poll** the broker until the app registers (registration races launch),
5. open `NSXPCConnection(listenerEndpoint:)` directly — the broker is out of the path from here.

Measured with the app not running: **0.284 s total, one 250 ms poll** (RemoteControl #0010). The ~30-line bounded-poll loop is load-bearing: without the bound, a broken app hangs the CLI forever; without the retry, a nil endpoint immediately after launch reads as failure when it is normal.

**The health check.** `remotectl ping` reaches the broker **with the app never launched**, because launchd starts the agent on demand. `FINDINGS.md` calls it "the most valuable diagnostic in this repo": if it passes, launchd owns the name; if it fails, nothing app-side is worth looking at.

## Predicted vs. found (the six original questions)

The ticket as filed posed six questions the prototype had to answer. The reconciliation:

1. **Reachability (the gating question) — answered.** Confirmed: a plain app cannot publish a named Mach service (only launchd hands out receive rights), and an `NSXPCListenerEndpoint` is a live Mach right, not data — it cannot be written to a file or printed, only sent over an existing XPC connection. The answer is a **broker launch agent** shipped inside the app bundle (`Contents/Library/LaunchAgents/<label>.plist` with a `MachServices` key and a bundle-relative `BundleProgram`, no `RunAtLoad`), registered via `SMAppService.agent(plistName:)`, holding the app's anonymous-listener endpoint and handing it to the CLI via the five-step dance above. The user-visible cost the original ticket flagged is real: the agent appears in System Settings → General → Login Items & Extensions, with a possible approval step (see traps).
2. **Signing / notarization — partially answered.** The experiment ran local development signing only; its `docs/build-and-release.md` states "No notarization" explicitly. Verified: launchd refuses to start an improperly signed agent, and the agent must be signed with the same team identity as the app. **Not verified: whether the registration survives Hardened Runtime + notarization + stapling end to end.** This remains open for the Batty implementation ticket.
3. **Swift-native XPC ergonomics — the prediction was wrong, in a useful way.** The ticket anticipated `XPCListener`/`XPCSession` with `Codable` payloads to avoid the `@objc`/`NSSecureCoding` dance. The experiment never exercised that API. It used **`NSXPCConnection` with `@objc` protocols whose structured payloads cross as JSON-encoded `Data`**, which "keeps `NSSecureCoding` class allowlisting entirely out of the picture" and "cost nothing and saved a category of problem — worth repeating in Batty" (RemoteControl #0002). The payloads are still ordinary `Codable, Sendable` structs — testable without XPC, printable when something breaks — just carried inside `Data`. **The validated approach is the recommended one for Batty; the Swift-native API is not what got validated.**
4. **Peer validation — not answered.** `setPeerCodeSigningRequirement` (or any peer code-signing check) was never exercised; it appears nowhere in `FINDINGS.md` or the experiment's docs. Remains open for the implementation ticket.
5. **Cold start — confirmed as predicted.** Both mechanisms survive: the URL scheme wins launch outright; XPC needs the dance but completes it in 0.284 s. The predicted split — URL scheme for launch + fire-and-forget, XPC for request/response — is exactly the recommendation, now confirmed rather than assumed.
6. **Does it beat a plain Unix socket? — answered by decision, not comparison.** The socket was never prototyped. The user adopted the hybrid on the strength of what XPC demonstrated. The original ticket said a confident answer either way is success; this is that answer, with the caveat recorded honestly above.

## Traps that will bite Batty specifically

These get their own section because they are the expensive part. All are from the experiment's issue history, not speculation.

1. **The `@Sendable` SIGTRAP crash (RemoteControl #0016) — a near-certainty for Batty, and the single highest-value thing to carry over.** Batty builds with `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` (confirmed in `Configuration/Build.xcconfig`). On such a target, closures passed to `remoteObjectProxyWithErrorHandler`, `interruptionHandler`, and `invalidationHandler` inherit main-actor isolation, because Foundation types those parameters as plain non-`Sendable` closures. Swift emits an isolation assertion at the closure's entry; XPC calls it on its own queue; the process dies with `EXC_BREAKPOINT / SIGTRAP`. **There is no compiler warning — strict concurrency is fully satisfied.** The fix is marking each closure `@Sendable`. The worst part: the crash happens *inside the handler that would have logged the error*, so failures produce no output at all. Corollary that saved the experiment everywhere else: declare reply blocks in your own `@objc` protocols `@escaping @Sendable` from day one — that made the compiler enforce the right thing at every call site the project controlled, leaving only the Foundation-supplied handlers exposed.
2. **Lifecycle work is the actual project, not the transport.** "Connecting two processes is an afternoon"; the rest had to be handled explicitly: `interruptionHandler` vs `invalidationHandler` demand *different* responses (interruption = peer died, connection object reusable, re-register; invalidation = permanently dead, rebuild) — conflating them yields either a reconnect loop or a permanently dead connection. Broker restart under a running app must be detected and re-registered automatically. A CLI killed with `kill -9` leaves an orphaned session the app must reap via the connection's invalidation handler — there is no other signal. An app quitting mid-session must tell attached CLIs before invalidating. Two concurrent sessions need fan-out, and ending one must not disturb the other. And one-way calls give **no delivery confirmation** — `registerAppEndpoint` returns `Void` whether or not the broker received it, so confirmation must come from a subsequent round trip.
3. **`SMAppService` operational pain.** `.status` can report `.enabled` while launchd has no such service (observed directly after `launchctl bootout`), so the app cannot repair its own registration by trusting status — drive re-registration from a *failed call*, once per launch. State outlives builds and is keyed to the bundle, so multiple copies of the app on disk confuse launchd; recovering a wedged state can mean `sfltool resetbtm` and a reboot. `SMAppService.register()` can land in `requiresApproval`, requiring the user to enable the app under System Settings → General → Login Items & Extensions — **and until then every CLI command fails.** On the dev machine it went straight to `.enabled` with no prompt — explicitly not something to rely on, and it means the approval path cannot be reliably tested.
4. **Packaging traps.** `dstSubfolderSpec = 1` ("Wrapper") in a Copy Files phase is the `.app` **root**, not `Contents/` — getting it wrong fails signing with "unsealed contents present in the bundle root," which names neither the file nor the phase. Xcode does not sign Mach-O files a script phase drops into the bundle, and launchd refuses to start an improperly signed agent — surfacing as an opaque registration failure. And a binary in `Contents/Resources/bin/` is sealed as a *resource*, not nested code, so `codesign --deep --strict` never mentions it — it looks unsigned when it is not. That last one directly concerns Batty: `bin/batty` already lives exactly there.
5. **Sandboxing is a constraint, not a detail.** A sandboxed app can only use Mach service names prefixed with an app-group identifier. Batty is unsandboxed today (`ENABLE_APP_SANDBOX = NO`), so this is fine — but it is a design constraint to record in case sandboxing is ever revisited.

## Port plan (from FINDINGS "What would change when porting into Batty")

- **BattyKit owns** the shared protocol/message/service-name types (`XPCProtocols.swift`, `Messages.swift`, `ServiceNames.swift` equivalents) and the `batty` CLI target — the same split as `BridgeKit` in the experiment. The protocols must be shared, and BattyKit is already the shared library.
- **The app target owns** the agent embedding: the broker executable target, the two Copy Files phases, and `SMAppService` registration plus its status UI. None of it can live in the package, because `SMAppService.agent(plistName:)` resolves relative to the *calling* bundle.
- **Keep the CLI out of the Xcode package product graph — two distinct hazards here, and they must stay distinct.** `FINDINGS.md` (line 171) cites the first; `docs/batty-cli-install.md` records both. Verified against both repos and both Batty issues — these are different failure modes, and there is **no conflict** with the as-built account:
  1. **Build-graph hazard (#0249):** wiring the `batty` executable *product* as an Xcode package-product dependency pulls it into the `Batty (Prod)` scheme's build graph, after which the `xcodebuild` test runner can no longer resolve BattyKit's `Bundle.module` resource bundle and every `BattyKitTests` test crashes at launch (`unable to find bundle named BattyKit_BattyKit`) — this is what broke the unit-test gate (#0249's verification records "372 tests in 47 suites"; round 1 broke it, round 2 restored it). `swift test` does not reproduce it; only `scripts/build.sh unit` catches it. Fix (shipped): build `batty` from the package inside the `Embed CLI` Run Script phase, so the executable never enters the Xcode build graph. (RemoteControl earlier mischaracterized this as a "deadlock" — corrected in its #0027; it is a resource-bundle resolution failure.)
  2. **Link-dependency hazard (#0252):** the CLI target depending on the full `BattyKit` *library* transitively links Sparkle (plus libghostty, SlidingTabs, Textual) via `@rpath`; the embedded binary at `Contents/Resources/bin/batty` cannot reach `Contents/Frameworks/` and crashes at launch with `Library not loaded: @rpath/Sparkle.framework/...` — while appearing to work under `swift run`. Fix (shipped): the dependency-free `BattyCLICore` target. **Consequence for this port: the new shared XPC protocol/message/service-name types must land in a dependency-free target the CLI can link — `BattyCLICore` or a sibling with the same discipline — never in full `BattyKit`.**
- **Derive the launchd `Label` and plist filename from a single `ServiceNames` constant.** Four strings must be identical — plist filename, plist `Label`, `MachServices` key, and the name the code connects to — and any mismatch makes launchd *silently* decline to reserve the name, surfacing much later as an unexplained "connection invalid." "The four-strings-must-match problem is the plan's most expensive gotcha and deriving them halves the places it can go wrong."
- **Reuse the exit-code vocabulary:** `2` broker unreachable, `3` app unavailable, `4` request failed, `5` app terminated the session. It "is what makes the CLI scriptable, and it costs nothing to define up front."
- **Build the health check early.** The `batty ping` equivalent — reaching the broker with the app never launched — was "the most valuable diagnostic in this repo."
- **Port the app-side repair path (RemoteControl #0016):** never trust `SMAppService.status`; confirm registration with a round trip, not a return; repair by unregister-then-register driven from a failed call, guarded to run once per launch.
- **`log stream` with a shared subsystem across app, agent, and CLI** "was the only practical way to watch a handoff. Wire it in from the first commit, not when something breaks." Batty already has `Logging.subsystem` in BattyKit; the agent and CLI must join it.

## Improvements to port back into Batty (separate follow-up ticket recommended)

The experiment improved on Batty's own `CLIInstaller` in two ways `FINDINGS.md` (line 176) and RemoteControl #0027 name explicitly:

- **`isBundleDurable`** — refuses to install a symlink from a bundle under `/DerivedData/` or `/Build/Products/`. Batty has no equivalent, so launching from Xcode and clicking Install silently creates a link that breaks on the next clean build, surfacing much later as `command not found`.
- **A four-state install inspection** (`notInstalled` / `installedHere` / `installedElsewhere(String)` / `blockedByFile`) replacing `isInstalled() -> Bool` — lets the UI say *where* a stale link points and refuse to clobber a real file at the destination.

These are independent of the XPC decision and should be **their own follow-up ticket**, not folded into this one. Not filed yet — recorded here so the improvement isn't stranded in the prototype.

## Effort data (for budgeting the port)

From the experiment's per-issue work logs: **XPC cost roughly 5–6× the URL scheme** (~$52 for phases 1–4 vs. the URL-scheme baseline's transport work) and produced four times the bugs (four XPC-only bugs vs. one URL-scheme bug, all found by testing rather than review). Three caveats from the doc itself matter as much as the ratio:

- An earlier version of the table said "~$28" for XPC and **was wrong** — computed from a snapshot reported as a total. The real figure is about $52.
- The single most expensive line in the whole session ($27.43) was a **code-signing incident unrelated to the experiment** — repeated *signed* local builds against an Automatic-signing project. Avoidable entirely with `CODE_SIGNING_ALLOWED=NO` on repeated local builds. Directly actionable for whoever does the Batty port.
- **Cost tracked conversation length, not difficulty** — cache reads were 99% of billed tokens and 79% of cost; the same class of work cost $1.27–$2.11 early in a session and $11.33 late. For budgeting: the number to control is session length, not scope.

## Vendoring recommendation

`FINDINGS.md` closes (line 177) by pointing at the experiment's `docs/` folder as "the transferable form of everything above … a better starting point for the port than this file or the README." That folder holds four documents (~1,500 lines total), indexed by `/Users/brennan/Developer/brennanMKE/RemoteControl/docs/README.md`, each written explicitly for someone building a *different* app, marking what must be renamed and what can be copied verbatim:

- `xpc-cli-architecture.md` — the broker pattern, endpoint handoff, protocol trio, four-string rule, `SMAppService` repair path
- `cli-embedding-and-install.md` — CLI in a Swift package, embedding, signing, install action
- `swift-concurrency-and-xpc.md` — the `@Sendable` trap in full, `nonisolated` helpers, moving non-`Sendable` connections across isolation
- `build-and-release.md` — local install without notarization, the certificate-revocation hazard

**Recommendation: vendor copies** of these four docs plus `docs/README.md` and `FINDINGS.md` into Batty's `docs/` (e.g. `docs/xpc/`) when the implementation ticket starts. RemoteControl is a sibling checkout that could move or be deleted — it was throwaway by design — and the experiment's own hardest-won process lesson ("read the reference project's docs before implementing, not after"; it cost RemoteControl three divergences from Batty's already-solved CLI install) is precisely the failure mode that a vendored copy inside this repo guards against. **Not copied under this ticket** — this ticket changes no files besides itself.
