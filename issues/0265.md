## Description

Evaluate **XPC** as the request/response transport between the `batty` CLI and the running Batty app — learned by building a **separate throwaway experiment app + CLI outside the Batty repo**, before committing to anything in Batty itself. This is an **exploration/prototype ticket** in the #0254 mold, not a build commitment: the deliverable is a decision record, and no Batty app code changes under this ticket.

The question this answers is narrow and already framed: #0257 Foundation §5 **pins** the IPC decision — mutations go over the one-way `batty://` URL scheme, topology queries read an app-written JSON snapshot (Option B), and a two-way **Unix socket** is deferred to Tier 3. This ticket does **not** overturn that. It asks: *when Tier 3 arrives, should the two-way channel be XPC instead of a raw Unix socket?* XPC has never been properly evaluated for this — it appears exactly once in the tracker, as a one-line unexplored alternative in #0250's IPC notes ("local socket / `CFMessagePort` / XPC … more machinery, and needs its own launch-if-not-running story"). That line is the entire prior art; this ticket is the evaluation.

The user intends to hand this issue plus the companion doc `docs/batty-cli-install.md` to a separate Claude session to plan the prototype, so the sections below are written to brief someone with no prior context on Batty's CLI.

## Current state (the brief for a fresh reader)

Batty is a native macOS terminal multiplexer (unsandboxed, Hardened Runtime on, deployment target macOS 15.6+). It ships a CLI named `batty`:

- The CLI lives in the `BattyKit` Swift package at `BattyKit/Sources/batty/` (`BattyCLI.swift`, `SessionCommand.swift`), built on `swift-argument-parser`, embedded in the app bundle at `Contents/Resources/bin/batty`, and installed to `/usr/local/bin/batty` as a symlink via a privileged `NSAppleScript` step in Settings (#0249).
- Today the only verb is `batty [path]` (default `.`): the CLI resolves the path, builds a `batty://session?path=…` URL (`BattyKit/Sources/BattyCLICore/SessionURLBuilder.swift`), and opens it via `/usr/bin/open`. The app handles it in `BattyKit/Sources/BattyKit/Runtime/BattyURLHandler.swift` and creates a new Session rooted at that directory (#0250/#0251).
- The channel is strictly **one-way, fire-and-forget**. The CLI gets no response, no error, no ids back from the app.
- `docs/batty-cli-design.md` (§1.3 especially) surveys the herdr/supacode/cmux CLI + socket APIs and lays out the tiered plan; #0257 pins the concrete Tier 0 + Tier 1 argument surface on top of it.
- **`docs/batty-cli-install.md`** is the as-built record of how the CLI is built, embedded, installed, and invoked — the starting point for the prototype's own app+CLI plumbing. (Distinct from the older `docs/cli-tool-install.md`, which is a prescriptive survey of supacode's install approach, not an as-built record.)

## Why a two-way channel (the problems it would solve)

1. **No error reporting.** #0257 §2 concedes that with one-way IPC an unknown or stale target id "can only be logged app-side — the CLI can't see the failure." No real exit codes, no error text. An agent (Claude Code running inside a pane) chaining `batty` commands hits this constantly and can't tell success from silent failure.
2. **Two discovery gaps.** `batty pane show <id>` needs an id that a hidden pane can't supply (#0257 Notes), and `batty session new` prints only the *session* id — the pane and tab it creates are unaddressable. Both are currently answered indirectly by the Option B snapshot file, not by a channel that can just respond.
3. **Tier 3 needs request/response regardless.** The deferred verbs — `read` (screen contents), `wait`, `send`/`send-key`, `events subscribe` — cannot work fire-and-forget. Whatever transport Tier 3 uses, it must carry replies; the only open question is *which* transport.

## Questions the prototype must answer (success criteria)

The experiment app + CLI exist to answer these, in roughly this order — the first is gating:

1. **Reachability — the gating question.** An XPC service bundled in `Contents/XPCServices/` is reachable only from within the same app bundle, so an external `batty` binary at `/usr/local/bin` cannot connect to it. Confirm this, then determine what registration actually lets a standalone CLI process connect to a running GUI app: a launchd-registered Mach service via a LaunchAgent plist, `SMAppService.agent(plistName:)`, or something else. Document the user-visible cost plainly — a Login Items entry in System Settings, an install/uninstall story alongside the existing symlink installer. If nothing reasonable lets an external process connect, the evaluation ends there.
2. **Signing / notarization.** Batty is unsandboxed (`ENABLE_APP_SANDBOX = NO`) with Hardened Runtime on for notarization. Does the chosen registration survive notarization and stapling? Any entitlements required on the app or the CLI?
3. **Swift-native XPC ergonomics.** `XPCListener` / `XPCSession` in the XPC framework accept `Codable` message types directly, avoiding the `@objc` protocol + `NSSecureCoding` dance `NSXPCConnection` requires. Batty's layout model is already pure Codable value types (`Session`, `Pane`, `Tab`, `SplitNode`), and #0257 Option B deliberately shapes the snapshot JSON to become a future `list` response — so typed messages would be nearly free. Availability: the installed SDK's XPC swiftinterface marks both `XPCListener` and `XPCSession` `@available(macOS 14.0, *)`, within Batty's 15.6 floor — the prototype should still confirm against its own toolchain when it builds.
4. **Peer validation.** XPC can enforce a code-signing requirement on the connecting peer (e.g. `setPeerCodeSigningRequirement`); a Unix socket is protected only by filesystem permissions. Confirm the API and whether it works for an ad-hoc/dev-signed CLI during prototyping, or only for Developer ID-signed binaries.
5. **Cold start.** `batty ~/proj` currently launches Batty when it isn't running — the single best property of the URL scheme. Determine what XPC does when the app isn't running (launchd on-demand launch? error?), and whether `batty://` must be retained for the launch case regardless. The expected answer is that **both** mechanisms survive — URL scheme for launch + fire-and-forget mutations, XPC for request/response — and the prototype should confirm that split rather than assume it.
6. **Does it beat a plain Unix socket?** The honest comparison: typed Codable messages and peer signature validation vs. the install complexity (launchd plist, Login Items entry, registration lifecycle). A Unix socket in `~/Library/Application Support/Batty/` needs none of that machinery. If the socket is materially simpler for equal practical value, *that is a legitimate outcome of the experiment* — this ticket succeeds by producing a confident answer either way.

## Scope & deliverable

- **The prototype lives outside the Batty repo** — a minimal experiment app + CLI pair, built to learn, not to keep. Throwaway by design.
- **No Batty app code changes** under this ticket. Explicitly out of scope: the Tier 0/Tier 1 surface pinned in #0257, and building any real Batty XPC service.
- **Deliverable is a decision record:** a doc (suggest `docs/xpc-ipc-evaluation.md`) answering the six questions above with what the prototype actually demonstrated, plus a recommendation on whether to amend #0257 Foundation §5 to name XPC as the preferred Tier 3 transport over a raw Unix socket. If XPC wins, the Batty-side work becomes its own child ticket — no dangling follow-ups.
- **Governing constraint (#0254):** Batty stays simple and stays a first-class Mac app. A LaunchAgent plist and a Login Items entry in System Settings are real weight against that bar — the decision record must weigh them honestly, not wave them off.

## Notes

- The user's framing: "Perhaps I can first build a separate app as an experiment with creating a CLI which uses XPC to communicate." Keep the experiment that small — one listener in the app, one or two round-trip messages from the CLI (an echo and a typed Codable struct), then the registration/signing/cold-start probes.
- Keep the Option B snapshot schema in view: if XPC wins, its `list` reply should reuse that JSON shape verbatim, per #0257.
- Prototype learnings about launchd/`SMAppService` registration belong in the decision record even if XPC loses — they apply to any future helper-process work.
