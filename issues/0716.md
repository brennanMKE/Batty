## Description

With "Keep terminals running" on (#0696), a Sparkle update loses every Terminal Session. Sparkle replaces `Batty Beta.app`, including the embedded `BattyHost`, while the old BattyHost keeps running with its PTYs. The relaunched app's outgoing XPC check (`XPCHostChannelOpener` → `OutgoingCodeSigningEnforcement.apply` → `NSXPCConnection.setCodeSigningRequirement`) then rejects that old host with -67065 `errSecCSNoSuchCode`, because macOS validates a running process against the file at its path, and that file has changed. The app falls back to in-process PTYs and logs `restore: helper unavailable; 0 restored tabs start fresh`. The old host's terminals are lost when it later exits idle.

Fix it by having **BattyHost restart itself in place on update**: when its own executable has been replaced by a binary that satisfies the same code-signing requirement, it serializes its state to an fd, keeps the PTY masters open across `exec`, and execs the new BattyHost with `--resume <fd>`. The pid stays the same, so the shells remain its children and their exit codes are kept. The new image matches the file on disk, so the new app's check passes, and the app reattaches every Terminal Session.

**Done when #0715's runner reports `CHECK SPARKLE: PASSED`** for both the install-and-relaunch and the install-on-quit paths.

## Background

Evidence and analysis: #0696 Findings, "Restart quit without relaunching: sudden termination" → "Fix 2: an updated app can't adopt the previous build's BattyHost". In short:
- Field log: the new app (pid 69589) failed every connection to the old BattyHost (pid 61598, previous build, bundle replaced) with `-67065`, then `terminal helper connection: unavailable`.
- Reproduced with scratch binaries: `SecCodeCheckValidity` on a running process returns 0 before its binary is replaced, `errSecCSStaticCodeChanged` (-67034) after a same-team replacement, and fails to find the code when the directory is swapped. `kSecCSDynamicInformation` reports the *new* file's identity. No public API validates the running code's own signature without its file.
- Only the app → host direction fails. The old host validating the new app passes.
- The proposed design there (detect, hand over, re-check-in, refuse unknown state versions) is the starting point for this issue.

The BattyHost code (`BattyKit/Sources/BattyHost/main.swift`, `BattyHostCore`'s `HostSupervisor`/`PTYSession`/`ByteRing`, `HostProtocol`, the app's `HostClient`) exists only on `issue/0696`.

## Design (to be refined by the plan)

1. **Detect the replacement**, in the host:
   - a vnode `DispatchSource` on its executable and on the bundle path (`.delete`, `.rename`, `.write`, `.revoke`), since Sparkle swaps the whole `.app` and a watch on the old file's vnode alone may not fire;
   - plus `SecCodeCheckValidity(SecCodeCopySelf())` returning `errSecCSStaticCodeChanged` or a missing path, checked at the same points and when a client connects or fails to;
   - debounce until the new bundle is complete (Sparkle's install finishes), then re-resolve the executable by path.
2. **Check the new binary before exec**: it must satisfy the same requirement the host is held to (team identifier plus the host's signing identifier, from `PeerCodeSigningRequirement`), checked with `SecStaticCodeCheckValidity` on the path. If it doesn't, don't exec: keep running and log `.error`.
3. **Check compatibility before exec**: spawn the new binary in a probe mode (for example `--state-versions`) and read the state and protocol versions it accepts. The old image is gone once `exec` succeeds, so an incompatible new binary must be caught here, not after.
4. **Hand over**: serialize the registry (Terminal Session ids, child pids and pgids, master fd numbers, sizes, modes, client metadata, exit-pending and exited states with statuses, pending terminations and their escalation stage) and every ring buffer, with a **state version**, to an fd (a pipe or a memfd-like temp file, unlinked) passed across exec. Clear `FD_CLOEXEC` on the PTY masters and that fd, stop the dispatch sources without closing the fds, and `execv` the new path with `--resume <fd>`.
5. **Resume**: the new image reads and validates the state, rebuilds `PTYSession`s on the inherited masters, restarts child watching (`waitpid` still works: same pid, same children), re-arms timers from the serialized stage, and serves clients.
6. **Mach service check-in after exec**: the new image checks in `NSXPCListener(machServiceName:)` again (see Phase 0).
7. **App side**: while the host re-execs, the app retries the connection for a bounded time (injected clock, a few seconds; the plan sets the bound) instead of falling back to in-process PTYs on the first `-67065` or invalidation. The app can nudge the host to check itself; the nudge carries no data and is safe even unauthenticated, because the host acts only on its own check of the file on disk.

## Phase 0 spike, inside the VM (before any handover code)

**Question:** can a LaunchAgent registered through `SMAppService` (`BundleProgram`, `MachServices`, no `KeepAlive`) check its Mach service in again with `NSXPCListener(machServiceName:)` after the job's process calls `exec`?

- Build a minimal agent in the guest or as a host-built signed test binary, run it in the disposable VM through the #0715 runner's infrastructure (lease, clone, results folder), exec it in place, and connect from a client before and after.
- **If yes:** use the design above.
- **If no:** the fallback is to bootstrap over the Unix socket: the host listens on a per-user socket (in a directory only the user can reach), and the app verifies the peer by its `LOCAL_PEERTOKEN` audit token with a dynamic-code requirement check (`SecCodeCopyGuestWithAttributes` with `kSecGuestAttributeAudit`, then `SecCodeCheckValidity` with the same requirement). That passes once the running code matches the disk, which is true after the exec. The XPC Mach service stays for the first launch.
- **Record the result in this issue** (`## Findings`, with the run id, OS build and log lines) before writing Phase 1 code.

## Downgrade and incompatible versions

What happens when the new build's protocol or state version is older or otherwise not accepted (a downgrade, or a build from another branch)? **Start fresh safely, without orphaning shells**:
- The probe (design step 3) reports that the new binary can't take this state. The host does not exec.
- The old host logs `.error` with both versions, then shuts down every Terminal Session through the one termination routine from #0696 decision 3 (SIGHUP to the group, SIGTERM, SIGKILL, always reaped), and exits, so launchd can start the new host for the new app.
- The new app, after its bounded retry, starts fresh Terminal Sessions in the new host (not in-process), with its existing "helper unavailable" handling only if the new host can't start.
- If `exec` itself fails (the path vanished between check and exec), the old image is still running: log, keep serving, retry detection.
- If the resumed image rejects the state anyway (a bug), it must still not orphan anything: it owns the inherited masters and children, so it runs the termination routine over every inherited pid and closes every master before serving fresh. Unit-test this path.

The plan states exactly which versions are compared (wire `HostProtocolVersion`, a new state version) and the rule for each case.

## Decisions (user, 2026-11-21)

1. #0696 doesn't ship until a Sparkle update keeps every Session. 1.4.3 won't carry it.
2. **Relaxing the XPC code-signing check is rejected** for security reasons (accepting `errSecCSStaticCodeChanged`, or reading identity from dynamic info, would accept whatever file is on disk now, not the process answering).
3. The fix is a BattyHost restart in place with a state handoff across `exec`, keeping the pid so the shells stay its children.
4. Phase 0 spike inside the VM first; the Unix-socket bootstrap verified by `LOCAL_PEERTOKEN` audit token is the fallback if Mach service check-in after exec fails.
5. An incompatible or older version starts fresh safely, without orphaning shells.
6. Done when #0715 passes.

**Alternatives rejected in conversation** (the reasons are the filer's summary):
- **Handing the PTY master fds to a new host process via `SCM_RIGHTS`.** The new process isn't the shells' parent, so `waitpid` and exit codes are lost (#0696 decision 4 and U4 show exit codes to the user).
- **Same-user trust** (accepting any host running as the same user). Any process the user runs could pose as BattyHost and receive terminal input and output.
- **Pinned cdhash files** (the app trusting a cdhash recorded by the old build). It moves the trust root to a writable file and still doesn't prove which code is answering.
- **Relaxing the check** (decision 2).
