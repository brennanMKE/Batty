# 0542 — A failed read of projects.json starts the store empty with no backup, so a later save or iCloud merge can overwrite every saved Project

| | |
|---|---|
| **Status** | open |
| **Module** | Projects / Persistence |
| **Platform** | macOS |
| **First seen** | 2026-11-03 |

## Description

When `projects.json` exists but can't be read, `ProjectStore` starts empty and keeps no record that anything went wrong. If the next write succeeds, it replaces the file with only what's in memory and leaves no `projects.json.bak`, so every saved Project that isn't shared is lost. This has been in the code since #0471 and is in shipped 1.3.4.

**Release candidate for 1.3.5**, because it can lose user data. Nobody has reported it happening; a #0540 reviewer found it by reading the code, and this filing reproduced it against the real `ProjectStore` in a temp directory.

`ProjectStore.load` (`BattyKit/Sources/BattyKit/Model/ProjectStore.swift:317-352`) handles the three cases differently:

| State at load | Code | `projects` | `unreadableOriginal` | Protected? |
|---|---|---|---|---|
| Missing | `:318`, `fileExists` is false | empty | nil | Correct for a first run. Not protected if the file comes back before the save (see below). |
| **Exists, read fails** | `:320-325`, `Data(contentsOf:)` throws | empty | **nil** | **No.** |
| Exists, decode fails, a Project is dropped, or the version is newer | `:347`, `:348-351` | empty or partial | the file's bytes | Yes. |

Every safeguard keys off `unreadableOriginal`: the `.bak` in `save()` (`:303-308`), and the memory-only rule in `mergeRemote` (`:226`), `recordOpen`, `recordApproval` and `setShared`. A read failure has no bytes to keep, so all of them treat the store as healthy and empty. #0471 specified this protection for "corrupt JSON" only, and `ProjectStoreTests` has no read-failure case.

## Steps to reproduce

There's no in-app reproduction yet. A temporary test on an export of `main` (`2c61c5a1`) in a temp directory, never the real Application Support folder, used these sequences:

| Read failure | Then | Result on disk | `.bak` |
|---|---|---|---|
| Mode `000`, restored to `644` before the write | `upsert` succeeds | **`["New"]`; One, Two, Three lost** | none |
| Mode `000`, restored to `644` before the write | `mergeRemote` with a fake backend holding one shared record | **`["Shared"]`; One, Two, Three lost, with no user action** | none |
| ACL `deny read`, still in place at the write | `upsert` succeeds | **`["New"]`; all lost** | none |
| File descriptors exhausted at load (`EMFILE`), freed before the write | `upsert` succeeds | **`["New"]`; all lost** | none |
| Mode `000`, still in place at the write | `upsert` throws Cocoa error 513 from `replaceItemAt` | Intact | none |
| Mode `000`, still in place at the write | `mergeRemote`; save fails, logged and rolled back | Intact | none |
| Mode `200`, still in place at the write | `upsert` throws 513 | Intact | none |
| Parent directory mode `000` (`fileExists` is false, so it looks missing) | `upsert` throws 513 | Intact | none |

Controls, and the related missing-file case:

| State at load | Then | Result on disk | `.bak` |
|---|---|---|---|
| Corrupt file | `upsert` succeeds | `["New"]` | **original preserved** |
| Corrupt file | `mergeRemote` | Skipped, bytes unchanged | none needed |
| Missing, no file comes back | `upsert` succeeds | `["New"]`, correct | none needed |
| Missing, then restored before the write | `upsert` succeeds | **`["New"]`; restored file lost** | none |

Seed three Projects for each row, make the read fail, build a `ProjectStore(fileURL:)`, confirm it loads 0 Projects, then run the step shown and reload from a fresh store.

## Expected behavior

- A Project is never lost because a read failed. A write must not replace a `projects.json` this store never managed to read.
- `mergeRemote`, which runs with no user action, never writes over a file that wasn't read, as it already refuses to for a corrupt one.
- Once the file can be read again, its Projects come back.
- The missing case stays as it is for a first run: an absent file starts empty, and the first save creates it.

## Actual behavior

The store starts empty and logs one line (`projects load failed … starting empty`). It's built once and cached (`AppStateStore.projectStore`), so the Projects stay missing until the app quits, even if the file becomes readable. An empty list invites the user to create a Project, and that save destroys the rest.

## Notes

**The failure has to be one a replace gets past.** A file that stays denied by mode bits isn't overwritten, because `replaceItemAt` refuses it. So "a permissions error" isn't enough on its own: loss needs the read failure to clear before the write, or a failure that doesn't block replacing, as the ACL case shows. The read error isn't sticky in any way the write can see, which is why a transient failure is the dangerous one.

**The merge route needs no user action.** `ICloudKeyValueProjectSyncBackend` yields a change when it's built (`:79`) and on every external change (`:156`, `:160`), and `ProjectStore` calls `mergeRemote` for each. If the snapshot holds any record the empty list lacks, the merged list differs and is committed. In the repro the file then held only the shared record.

**What can be recovered.** Shared Projects can return through the next merge. Projects that were never shared exist only in this file. Time Machine aside, they're gone.

**What doesn't propagate.** A read failure doesn't reach other Macs: publishing and tombstoning act only on a specific Project being edited, and `delete` needs a Project in the list.

**The missing-then-restored row is the same gap, in a narrower form.** `save()` never checks whether the file changed since load. Reported on #0540 as "moved away and later restored". Whether to cover it here is the planner's call; a guard at write time would likely handle both.

**For the planner, not a decided design:** there are no bytes to copy to `.bak`, so the store needs a load state of its own for "exists, could not read". It could retry the read at save and merge time, adopting the Projects if the read succeeds and refusing the write if it doesn't. Tests can't use `FileManager` injection to force this, because `load` calls `Data(contentsOf:)` directly; the mode-`000`-then-restore sequence above works without a seam and without waiting.

**Shipped versions.** `v1.3.4` and `release/1.3` are the same commit (`92813f3e`). `ProjectStore.swift`, `ProjectSync.swift` and `ICloudKeyValueProjectSyncBackend.swift` are unchanged between it and `main`, so 1.3.4 has this bug. The fix follows the release-branch rule in `AGENTS.md`: `main` first, then `git cherry-pick -x` onto `release/1.3`. The shipped entitlements file carries `com.apple.developer.ubiquity-kvstore-identifier`, so the merge route applies to Prod. An installed Prod 1.3.0 build carries it too.

## Not verified

- **How often this happens.** No real occurrence is known, and nothing shows which transient failures a Mac actually hits on this file.
- **A real I/O error.** `EIO` wasn't simulated. The `EMFILE` case shows a non-permission read failure behaves the same, but the test forced it by filling the descriptor table; whether a running Batty reaches that limit wasn't measured. Nothing in `BattyKit/Sources` or `Batty/` calls `setrlimit`.
- **Why `replaceItemAt` refuses mode `000` and `200` but accepts an ACL denial.** Observed, not explained. Don't rely on it as protection, since it's undocumented behavior of the file manager.
- **The real app and real iCloud.** The merge route used a fake backend, and the launch-time ordering was read from the code, not run. For the launch-time merge to overwrite, the read failure must clear between load and the first merge attempt, which is very soon after. A later external change has much more room.
- **1.3.4 itself wasn't run.** The repro ran on `main`, whose relevant sources are identical to the tag.
