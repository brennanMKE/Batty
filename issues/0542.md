## Description

When `projects.json` exists but can't be read, `ProjectStore` starts empty and keeps no record that anything went wrong. If the next write succeeds, it replaces the file with only what's in memory and leaves no `projects.json.bak`, so every saved Project that isn't shared is lost. This has been in the code since #0471 and is in shipped 1.3.4.

**Release candidate for 1.3.5**, because it can lose user data. Nobody has reported it happening; a #0540 reviewer found it by reading the code, and this filing reproduced it against the real `ProjectStore` in a temp directory.

`ProjectStore.load` (`BattyKit/Sources/BattyKit/Model/ProjectStore.swift:317-352`) handles the three cases differently:

| State at load | Code | `projects` | `unreadableOriginal` | Protected? |
|---|---|---|---|---|
| Missing | `:318`, `fileExists` is false | empty | nil | Correct for a first run. Not protected if the file comes back before the save (see below). |
| **Exists, read fails** | `:320-325`, `Data(contentsOf:)` throws | empty | **nil** | **No.** |
| Exists, decode fails, a Project is dropped, or the version is newer | `:347`, `:348-351` | empty or partial | the file's bytes | Yes. |

Every safeguard keys off `unreadableOriginal`: the `.bak` in `save()` (`:303-308`), and the memory-only rule in `mergeRemote` (`:226`), `recordOpen`, `recordApproval` and `setShared`. A read failure has no bytes to keep, so all of them treat the store as healthy and empty. #0471 specified this protection for "corrupt JSON" only, and `ProjectStoreTests` has no read-failure case.

## Resolution notes

> 🟢 Resolved 2026-11-03 — A `projects.json` that can't be read now refuses writes and merges and tells the user, and its Projects come back with no relaunch once it can be read.

## Root cause

`ProjectStore.load` turned a read that threw into the same state as a first run: empty list, `unreadableOriginal` nil. Every safeguard keys off `unreadableOriginal`, so the store treated itself as healthy and empty, and the next successful write or merge replaced the file with only what was in memory. Confirmed by the failing-first runs below.

## Fix

`load` now just reads and classifies the result: `NSFileReadNoSuchFileError` is absent, any other throw is read failed. While a store isn't loaded, every mutator and `mergeRemote` re-reads first, so a transient failure heals with no relaunch. A read that still fails makes writes throw `ProjectStoreError.fileUnreadable(path:)` and makes merges skip. The picker, the Project Editor and the two `batty project` verbs retry and say the file can't be read.

Divergences from the plan:

- **Command-N in the picker.** The plan removed the New Project buttons only. The sheet's Command-N would still have offered it, so it now does nothing in the unreadable state and the footer hides its hint. The button stays enabled, so the chord still stops at the sheet instead of reaching File > New Session. This added `ProjectPickerModel.offersNewProject`.
- **One test beyond the plan: `aMergeWhileUnreadNeverTouchesTheList`.** With `mergeRemote`'s guard removed, `writeFile`'s guard still kept the file safe and rolled back, so the plan's named tests passed. The new test observes `projects` and fails on that transient write.

### Premises checked

Confirmed in the code unless noted.

- **Line numbers in the Description are stale.** #0540 moved them: `load` is `ProjectStore.swift:339-359`, the read-failure branch `:342-347`, the `.bak` `:325-330`, the merge guard `:248`.
- **"`ProjectStore.swift` and `ProjectSync.swift` are unchanged between 1.3.4 and `main`" is no longer true.** It was true at filing. #0540 changed both; `ICloudKeyValueProjectSyncBackend.swift` is still unchanged. The bug is in both versions.
- **"A read failure doesn't reach other Macs" is true for deletion, with one gap.** Nothing publishes an empty list, and `mergeRemote` never calls the backend. But `upsert` calls `publish` before `commit` (`:197-198`), so a new shared Project saved while the file is unread reaches iCloud even when the write then fails. The guard below goes first, so this stops too.
- **The issue's table leaves out two write routes.** `reorder([])` commits an empty list, and public `save()` writes whatever is in memory. `save()` has no production caller, and the editor's `moveProjects` returns early on an empty list, but the store must refuse both.
- **There is no existing unreadable-file surface.** `unreadableOriginal` is read only inside `ProjectStore`. A corrupt file logs one line and shows "No Projects yet". This plan adds a surface for the read failure only (see Scope).
- **`fileExists` is false under a mode `000` parent, as the table says, but the read tells them apart.** Measured on this Mac with `Data(contentsOf:)`:

| Case | Cocoa code | POSIX |
|---|---|---|
| Missing file, missing parent, dangling symlink | 260 | `ENOENT` |
| Mode `000` file, mode `000` parent | 257 | `EACCES` |
| Parent is a file | 256 | `ENOTDIR` |
| Path is a directory | 256 | `EISDIR` |

- **Tests can't force a read failure through `FileManager`.** Correct: `load` and `imagePathsInFile` both call `Data(contentsOf:)` directly. This plan adds a seam.

### Decisions

1. **Load has three outcomes, decided by the read itself.** `load` stops calling `fileExists` and just reads. `NSFileReadNoSuchFileError` (260) means absent, and anything else that throws means read failed. This removes the gap between the check and the read, and a mode `000` parent now counts as a failure instead of a first run. `ENOTDIR` counts as a failure too, which is the safe side, and a write there would fail anyway.
2. **A later save with the file still unreadable throws `ProjectStoreError.fileUnreadable(path:)` and writes nothing.** There are no bytes to back up. The file isn't touched, and the editor shows why. This replaces relying on `replaceItemAt` refusing, which the issue notes is undocumented and which an ACL gets past.
3. **Every write and merge re-attempts the read first, so a transient failure heals without a relaunch.** It costs one read, only while the store isn't in the loaded state. A loaded store never re-reads, so saves don't pick up new costs or new behaviour.
4. **Also retry when the picker or editor opens, and on the two `batty project` verbs.** Without this, Projects stay missing on a Mac with no iCloud until the user attempts a save, and the Expected behavior says they come back once the file can be read. A background timer or file watcher isn't worth it for a patch release.
5. **While the file is unread, the list stays empty and nothing is held in memory.** Merged shared records are not shown either. `commit` rolls back on failure and the guard stops the rest, so `projects` is always empty outside the loaded state, and a heal can simply replace the list. This is why a heal needs no reconciling.
6. **The heal happens before the mutator looks at `projects`.** `upsert` builds `updated` from `projects`, so a check inside `save()` would be too late: it would write the new list without the healed Projects. Each mutator's first line is the check. A heal also runs `mergeRemote`, since a change skipped while unread won't be re-sent.
7. **The missing-then-restored row is included.** The same check covers it: the absent state also re-reads before a write. If the file is still missing, it's a first run and the write goes ahead. If it's back, its Projects are adopted, or it's treated as read failed or corrupt, as a load would. It cost nothing extra. A true first run differs only by one failed read per write until the first save.
8. **A read-failed store whose file is then deleted becomes absent and behaves as a first run.** The file is gone, so nothing is left to protect, and refusing forever would leave the user stuck.
9. **No `.bak` in the read-failure state.** A heal leaves the file as it was until the next normal save, so none is needed. A corrupt file found on a retry follows the existing rule, with its bytes kept for `.bak`.
10. **The surface is the two empty states and the save error, with no banner and no Try Again button.** The picker and the editor say the file can't be read, name the path, and don't offer New Project from that state, because the empty list is what invites the destructive save. Reopening or saving retries. The other surfaces that list Projects just show none.
11. **`mayReferenceUnlistedImages` is true while read failed,** and `imagePathsInFile` reads through the seam. So `reclaim` removes nothing from a store that hasn't read its file, even if the file is readable by then and the store just hasn't retried. The editor's open heals first, so a normal close still reclaims, with the healed list.

- The decode-failure, dropped-Project and newer-version rules, including `unreadableOriginal` and the memory-only paths.
- A loaded store whose file later changes on disk. That's the existing last-writer behaviour with another running copy, not this bug.

## Expected behavior

- A Project is never lost because a read failed. A write must not replace a `projects.json` this store never managed to read.
- `mergeRemote`, which runs with no user action, never writes over a file that wasn't read, as it already refuses to for a corrupt one.
- Once the file can be read again, its Projects come back.
- The missing case stays as it is for a first run: an absent file starts empty, and the first save creates it.

## Actual behavior

The store starts empty and logs one line (`projects load failed … starting empty`). It's built once and cached (`AppStateStore.projectStore`), so the Projects stay missing until the app quits, even if the file becomes readable. An empty list invites the user to create a Project, and that save destroys the rest.

## Notes

**The failure has to be one a replace gets past.** A file that stays denied by mode bits isn't overwritten, because `replaceItemAt` refuses it. So "a permissions error" isn't enough on its own: loss needs the read failure to clear before the write, or a failure that doesn't block replacing, as the ACL case shows. The read error isn't sticky in any way the write can see, which is why a transient failure is the dangerous one.

**The merge route needs no user action.** `ICloudKeyValueProjectSyncBackend` yields a change when it's built (`:79`) and on every external change (`:156`, `:160`), and `ProjectStore` calls `mergeRemote` for each. If the snapshot holds any record the empty list lacks, the merged list differs and is committed. In the repro the file then held only the shared record.

**What can be recovered.** Shared Projects can return through the next merge. Projects that were never shared exist only in this file. Time Machine aside, they're gone.

**What doesn't propagate.** A read failure doesn't reach other Macs: publishing and tombstoning act only on a specific Project being edited, and `delete` needs a Project in the list.

**The missing-then-restored row is the same gap, in a narrower form.** `save()` never checks whether the file changed since load. Reported on #0540 as "moved away and later restored". Whether to cover it here is the planner's call; a guard at write time would likely handle both.

**For the planner, not a decided design:** there are no bytes to copy to `.bak`, so the store needs a load state of its own for "exists, could not read". It could retry the read at save and merge time, adopting the Projects if the read succeeds and refusing the write if it doesn't. Tests can't use `FileManager` injection to force this, because `load` calls `Data(contentsOf:)` directly; the mode-`000`-then-restore sequence above works without a seam and without waiting.

**Shipped versions.** `v1.3.4` and `release/1.3` are the same commit (`92813f3e`). `ProjectStore.swift`, `ProjectSync.swift` and `ICloudKeyValueProjectSyncBackend.swift` are unchanged between it and `main`, so 1.3.4 has this bug. The fix follows the release-branch rule in `AGENTS.md`: `main` first, then `git cherry-pick -x` onto `release/1.3`. The shipped entitlements file carries `com.apple.developer.ubiquity-kvstore-identifier`, so the merge route applies to Prod. An installed Prod 1.3.0 build carries it too.

## Not verified

- **How often this happens.** No real occurrence is known, and nothing shows which transient failures a Mac actually hits on this file.
- **A real I/O error.** `EIO` wasn't simulated. The `EMFILE` case shows a non-permission read failure behaves the same, but the test forced it by filling the descriptor table; whether a running Batty reaches that limit wasn't measured. Nothing in `BattyKit/Sources` or `Batty/` calls `setrlimit`.
- **Why `replaceItemAt` refuses mode `000` and `200` but accepts an ACL denial.** Observed, not explained. Don't rely on it as protection, since it's undocumented behavior of the file manager.
- **The real app and real iCloud.** The merge route used a fake backend, and the launch-time ordering was read from the code, not run. For the launch-time merge to overwrite, the read failure must clear between load and the first merge attempt, which is very soon after. A later external change has much more room.
- **1.3.4 itself wasn't run.** The repro ran on `main`, whose relevant sources are identical to the tag.
