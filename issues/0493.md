# 0493 — The Open Project picker shows every Project in one uniform 3-column grid, so the most-used Projects it now ranks first are no more prominent than the rest; it needs a top row of larger cards, gated on a design the user approves first

## Description

Since #0492 every Projects list ranks by recency: the Open Project picker, File ▸ Open Project ›, the Command Palette rows and `batty project list` all call `ProjectRecency.ranked`, and `Project.lastOpenedAt` is written on every successful open. The picker, though, still draws one uniform grid of equal cards, so the Projects ranked first look exactly like the ones ranked last. The user's direction (2026-10-12): "I would show a top row with bigger cards for the most used projects followed by smaller cards. When we get to that point we can work with proposed designs in a web page to decide details."

This issue carries #0492 §3 forward as its own child of #0469: a **two-tier picker**, a top row of larger cards for the Projects ranked first, then smaller cards for the rest. It is **design-gated**: no code is written until the user has chosen one of several proposed designs on a web page, and that choice is recorded here.

Ships on `main` for 1.3.0, behind the Projects flag. With the flag off the picker never presents, so nothing here is visible.

## Current code (verified on `main` at `c20dc37d`)

**Order.** `ProjectRecency.ranked(_:openProjectIDs:placement:)` (`BattyKit/Sources/BattyKit/Model/ProjectRecency.swift:14-33`) sorts most recently opened first, then never-opened Projects in store order, with equal dates keeping store order through the enumerated offset. `OpenPlacement` is `.last`, `.inPlace` or `.first`; `defaultPlacement` is `.last` (`:9`), so open Projects sink below closed ones. `ProjectPickerModel` ranks in `init` (`Model/ProjectPicker.swift:53-59`) and in `refreshed(projects:openProjectIDs:)` (`:64-71`), and the view calls `refreshed` on every render (`Views/ProjectPickerView.swift:53-56`, `:59`). The filter's tie-break is the ranked offset (`ProjectPicker.swift:187`).

**Layout.** `ProjectPickerView` is a fixed `720 × 520` sheet (`ProjectPickerView.swift:82`). Header (`:62-68`), filter field (`:91-119`), `Divider`, then the empty state or the grid, then the footer (`:171-189`). The grid is a `LazyVGrid` with `ProjectPickerModel.columnCount` (= 3, `ProjectPicker.swift:45`) `.flexible()` columns, 12 pt spacing and 16 pt padding (`ProjectPickerView.swift:121-139`), so every card is the same width, about 221 pt. `ProjectPickerCardView` (`:217-293`) is a 108 pt-tall thumbnail (`:288`), the Project symbol and name with the OPEN badge (`:224-239`), the `~` path and the summary line, with 10 pt padding, a 9 pt corner radius and a 2 pt accent border when selected (`:253-259`). About two rows are visible at once. The only grid test is the layout smoke test `ProjectPickerViewTests.theSheetLaysOutWithCardsAndWithTheEmptyState` (`BattyKit/Tests/BattyKitTests/ProjectPickerTests.swift:479-480`).

**Keyboard.** The filter field handles the four arrows, Return / Option-Return and Escape through `onKeyPress` (`ProjectPickerView.swift:100-110`); ⌘E and ⌘N are hidden buttons with key equivalents (`:201-214`). `ProjectPickerModel.move(_:)` (`ProjectPicker.swift:103-129`) is row-major over a uniform grid: left/right step by one, up/down use `index ± columnCount`, nothing wraps, and down from a column the short last row lacks lands on the last card. There is no Home/End. A two-tier grid with different column counts per tier breaks the `index ± columns` arithmetic. Unit tests: `selectionMovesOverTheGridWithoutWrapping` (`ProjectPickerTests.swift:171`), `downFromAColumnThePartialLastRowLacksLandsOnTheLastCard` (`:194`), `arrowKeysFollowTheRankedOrder` (`:86`).

**Scrolling.** `onChange(of: selectedID)` scrolls to the selected card (`ProjectPickerView.swift:140-142`). It fires only when the id changes, so a re-rank that moves the selected card (a Session opening or closing while the sheet is up) does not scroll to it (#0492 Gotchas).

**Identifiers** (`docs/ui-features.md:790-797`): root `project-picker.root` (a `.contain` element since #0484, `ProjectPickerView.swift:86-87`), `project-picker.filter`, `project-picker.hint`, cards `project-picker.card.<name>` (`:264`), OPEN badge `project-picker.open-badge.<name>` (`:237`), empty state `project-picker.empty` (`:168`) with `project-picker.new-project` (`:159`). There is no identifier for the grid itself.

**Pure cursor precedents.** `SessionColorGridCursor` (`Views/SessionColorPickerView.swift:13-78`): a 5-column swatch grid plus a full-width "Automatic" row below it, with vertical moves crossing between the two sections (down from the last swatch row lands on Automatic; up from Automatic returns to column 0 of the last row), all 44 transitions tested. `ProjectSymbolGridCursor` (`Model/ProjectSymbolGridCursor.swift:9`): a 6×6 grid, clamped, no wrap, 144 transitions tested. The two-tier picker cursor is the same kind of type with two sections of different column counts.

**UI-test seams.** `ProjectFixture.project(name:root:layout:preset:runStartupCommands:symbol:lastOpenedAt:id:)` (`BattyUITests/Support/ProjectsHarness.swift:31-54`) emits `lastOpenedAt` as an ISO 8601 string; `ProjectsCLITests.swift:36-38` seeds two Projects that way. `ProjectsUITestCase` (`:94`), `launchApp` (`:124`), `presentPicker` (`:227`), `filterPicker` (`:240`), `pressReturn` (`:253`), `waitForSessions` (`:447`). `ProjectsOpenTests` reads cards and badges by identifier. `ProjectsFlagOffTests.testFlagOffRemovesEveryProjectsEntryPointAndWritesNothing` already asserts that the seeded `projects.json` bytes are unchanged after launching and using the menus and palette (`BattyUITests/ProjectsFlagOffTests.swift:62`).

**Design artboard.** The approved picker artboard is `issues/0469/OpenProject.dc.html` (canvas: https://claude.ai/artifact/WoKFESyWFnQFkM64TF2P5o). It shows one uniform grid; this issue's design supersedes it for the picker only.

## Expected behavior

### 1. Layout: a top row of larger cards

What the user's direction fixes:

- A **top row of larger cards** for the Projects `ProjectRecency.ranked` lists first, followed by **smaller cards** for the rest, in the same order. Both tiers come from the one ranked list split at a count; there is no second ranking and no sorter other than `ProjectRecency`.
- Both tiers keep today's card content (thumbnail, symbol, name, OPEN badge, `~` path, summary). The larger cards may show more (a bigger thumbnail, a relative "Opened …" time) and the smaller cards less. The design decides.
- Cards keep `project-picker.card.<name>` and the OPEN badge keeps `project-picker.open-badge.<name>`, so `ProjectsOpenTests` keeps passing. Each tier's container is a `.contain` accessibility element (the #0484 pattern) with its own identifier: `project-picker.featured` and `project-picker.rest`. Document them in `docs/ui-features.md`.
- The placement of open Projects stays whatever `ProjectRecency.defaultPlacement` is. It is `.last` today; the design review confirms or flips it (open question 1), and the flip is the one-line change at `ProjectRecency.swift:9`, applied to every surface at once, never to the picker alone.

### 2. Keyboard: a pure two-tier cursor

- Selection moves across both tiers with the arrow keys. Return, Option-Return, ⌘E, ⌘N, Escape, click and double-click behave as today (`docs/ui-features.md:729-734`).
- The cursor math becomes a **pure type** (for example `ProjectPickerGrid` or `ProjectPickerCursor`), replacing `ProjectPickerModel.columnCount` and the `index ± columns` arithmetic in `move`, modeled on `SessionColorGridCursor` and `ProjectSymbolGridCursor`. It knows each tier's column count and the card count, maps up/down between tiers to the nearest column (clamped, no wrapping), keeps the short-last-row rule, and adds **Home** (first card) and **End** (last card). The view's `onKeyPress` handlers call the model; the model calls the cursor type. No arithmetic in the view.
- With fewer Projects than the top row holds, or with a filter active, the cursor's two-tier shape follows what the design decides (open questions 3 and 4); the type takes the tier shape as input rather than hard-coding it.
- After a re-rank moves the selected card (a Session opened or closed while the sheet is up), the view scrolls to it. Today it scrolls only when the selected id changes (`ProjectPickerView.swift:140-142`). The fix lives in the view, not the model.

### 3. The design gate (binding)

1. **Implementation does not start until the user approves a visual design.** The orchestrator, not the implementer, prepares the proposals: a web page (artifact) with several options, in the same form as the Projects canvas the user reviewed for #0469 (https://claude.ai/artifact/WoKFESyWFnQFkM64TF2P5o). Each option shows the two-tier grid at the sheet's size with realistic Projects (long names, `~` paths, an OPEN badge in each tier), the filtered state, the empty state and the keyboard focus ring. The page states the placement policy it assumes so the review decides that too.
2. The chosen option is **recorded in this issue before any code is written**: a `## Chosen design` section with the artifact link, the option name, the answers to the open questions below, and the artboards copied into `issues/0493/` as #0469 did into `issues/0469/`.
3. **An implementer dispatched without a `## Chosen design` section bails** per `issues/Issues.md` "When the implementer can't finish" and says so in its summary.
4. Until the design is chosen, the picker keeps today's uniform 3-column grid.

### 4. Flag off

Nothing new. The picker presents only with `featureFlags.projects` on (`docs/feature-flags.md`, the #0475 sites), and the cursor type has no I/O. No new gate site; add no row to `docs/feature-flags.md` unless the chosen design adds a new entry point.

## Open questions for the design review

Carried from #0492 and updated for what has landed. The proposal page answers these with options; the chosen answers go into `## Chosen design`.

1. **Placement of open Projects.** `.last` landed as `ProjectRecency.defaultPlacement` (`ProjectRecency.swift:9`) and is what every surface shows today: open Projects sink, keep recency order among themselves and keep their OPEN badge. Confirm it, or flip to `.inPlace` or `.first` for every surface at once (#0492 §1's table of trade-offs still applies).
2. **Top-row count and sizes.** How many large cards (3 at today's width, or 4 with a wider sheet), the large and small card sizes, and whether the sheet grows or becomes resizable. Today: a fixed `720 × 520` sheet (`ProjectPickerView.swift:82`), 3 columns (`ProjectPicker.swift:45`), cards about 221 pt wide, thumbnail 108 pt (`ProjectPickerView.swift:288`).
3. **Fewer Projects than the top row.** One tier only, or a padded top row. With one Project, a single large card or today's card?
4. **Filtering.** A typed query collapses to one uniform tier (simplest; the top row is a recency feature and a filter is a name feature), or keeps the tiers and filters each. The filter's tie-break is the ranked offset either way (`ProjectPicker.swift:187`).
5. **Keyboard.** Up from the lower tier's first row lands on the nearest top-row column; Down from the top row's last column lands where; Home and End; whether Left/Right cross the tier boundary. Today's `move` is uniform row-major with no Home/End (`ProjectPicker.swift:103-129`).
6. **Empty state and New Project….** The empty state as today (`project-picker.empty`, `project-picker.new-project`), or a "+ New Project…" card at the end of the lower tier in addition to the ⌘N hint.
7. **Card extras.** A relative time ("Opened 2 h ago") on large cards, on all cards, or none; whether the large thumbnail shows Tab counts per slot. A relative-time formatter takes an explicit `now: Date` and is tested with fixed dates; no `Date()` inside it (#0492's rule for the ranking function applies to formatting too).
8. **Frequency.** The ranking is recency only. If the review wants "most used" to mean *most often* (a frecency blend), that needs an `openCount` field recorded at the same write site (`ProjectStore.recordOpen`), starting at zero for every existing Project. Not recommended for the first version; a one-field, back-compatible addition later if recency alone proves wrong.

## Acceptance criteria

All of these apply **after** `## Chosen design` is recorded; none can be started before it.

**Unit tests** (`./build.sh unit`, all visible in the output, none waiting on time, per `AGENTS.md` "Asynchronous tests"):

- **Two-tier cursor:** the pure type is tested for every arrow from every cell on fixtures with a full top row and a partial last row, a top row only (fewer Projects than the top row holds), and a single-tier case if the design collapses the tiers under a filter. Specifically: Up from each lower-tier first-row column lands on the top-row column the design chose; Down from each top-row column lands on the chosen lower-tier cell; Down from the last reachable row is a no-op or lands on the last card per the short-last-row rule; Left/Right at the tier boundary do what the design chose; Home and End land on the first and last card from every cell. Fixtures use counts that differ between tiers so no assertion is vacuous.
- **Model:** `ProjectPickerModel` exposes which cards are featured and which are the rest, in ranked order, for a fixture whose store order differs from the ranked order and includes one open Project; the featured count follows the design; a filter yields the tier shape the design chose.
- The existing `ProjectPickerModelTests` keyboard tests are updated for the new cursor, not deleted; `ProjectPickerViewTests.theSheetLaysOutWithCardsAndWithTheEmptyState` still passes.

**VM UI tests**, only through `tools/run-ui-tests-vm.sh` / `./build.sh ui`, never on the host, in the #0478 style (`ProjectsUITestCase`, `ProjectsHarness`), seeding `lastOpenedAt` through `ProjectFixture.project(lastOpenedAt:)`:

- Seed at least one more Project than the top row holds, with `lastOpenedAt` values whose order differs from the seed order; present the picker; the `project-picker.card.<name>` elements under `project-picker.featured` are the most recent ones in order, and the rest are under `project-picker.rest`. Open the first; reopen the picker; with `.last` its card is now under `project-picker.rest` and carries `project-picker.open-badge.<name>` (with `.inPlace` or `.first`, assert whichever the review chose).
- Arrow keys cross from the top tier to the lower tier and back; Return opens the selected card (`waitForSessions`).
- Typing a filter narrows the cards as the review decided (one tier or two), and Escape restores both tiers.
- Flag off: `ProjectsFlagOffTests.testFlagOffRemovesEveryProjectsEntryPointAndWritesNothing` already asserts the seeded file's bytes are unchanged (`ProjectsFlagOffTests.swift:62`); extend it to select a Session before that assertion and to assert that `lastOpenedAt` never appears in the file. Nothing else in this issue is reachable with the flag off.
- Run the full `BattyUITests` suite on the branch head: `ProjectsOpenTests`, `ProjectsCLITests`, `ProjectsEditorTests`, `ProjectsSymbolTests` and `ProjectsFlagOffTests` stay green.

## Notes

- **Binding docs:** `docs/swiftui-observation-rules.md`. The picker's `model` getter is a pure read on every render (`ProjectPickerView.swift:53-56`) and only `base` (query and selection) is state, written from `onKeyPress` and tap handlers. The two-tier view keeps that: tier membership is derived in `body` from the ranked cards; nothing in `body`, `onAppear` or a geometry callback writes `base`. The scroll-after-re-rank fix in §2 must be an `onChange` keyed on something the model exposes (for example the selected card's tier and index), not a write from `body`. `docs/view-hierarchy.md` is unaffected: nothing here goes near the terminal host.
- **Why the orchestrator prepares the proposals.** The user asked to "work with proposed designs in a web page to decide details". The #0469 canvas was reviewed that way, and its artboards became `issues/0469/*.dc.html`. The same loop here keeps the implementer from guessing at sizes and counts the user has said they want to choose.
- **Why a pure cursor type.** `SessionColorGridCursor` exists because the inline math shipped broken in #0336's first review round. A two-section grid with different column counts is harder than either existing cursor, and every arrow from every cell is cheap to pin in a test.
- **Sequencing.** #0492 §1 (the recency model) landed first so that #0491 (Open Quickly Project rows) could consume `ProjectRecency.ranked` without waiting on this design review; #0492's Notes recorded that split as the orchestrator's option, and it was taken. #0490 (Sidebar Open Project button) presents the same picker and is unaffected by its layout.
- Line numbers were grepped on `main` at `c20dc37d` on 2026-10-13 and will drift when #0490 (`SessionDetailView`, `ProjectPickerView` presentation) and #0491 land.
