# 0246 — Summarize bell notifications with Foundation Models so they are distinguishable

| | |
|---|---|
| **Status** | open |
| **Module** | BellFeed / Session |
| **Platform** | macOS |
| **First seen** | 2026-06-17 |

## Description

Bell notifications currently look almost identical to one another, so a burst of them carries little information. The desktop notification's title is purely location — `Batty — {sessionTitle} › Pane {paneIndex} › {tabLabel}` (`BellNotifier.swift:54`) — and the body is `entry.message` or, when there's no OSC 9 message, the literal string `"Bell"` (`BellNotifier.swift:55`). The in-app Bell Feed entries share the same thin `message` field (`BellFeedStore.BellFeedEntry.message`). When several bells arrive from the same or similar tabs, the user can't tell them apart.

Use on-device **Foundation Models** to generate a short, human-readable summary of what each notification is actually about — the same class of use case as AI session naming (#0231 / #0232), and a natural reuse of that infrastructure.

## Proposal / open questions

- **Signal source:** summarize from the recent terminal output around the bell (the tail of the surface's scrollback for that tab) and/or the OSC 9 message, so the summary reflects what happened ("build failed: 3 errors", "tests passed", "npm install finished") rather than a generic "Bell".
- **Reuse #0232's pattern:** the existing `FoundationModelsNameSuggester` (tool-calling `LanguageModelSession`, on-device, async, availability-gated, memoized) is the template. Consider a sibling summarizer (e.g. `FoundationModelsNotificationSummarizer`) or a shared abstraction. Wire it through the existing `AppStateStore` AI-naming machinery (`nameSuggester`, in-flight task tracking) rather than inventing a new path.
- **Graceful fallback:** when Foundation Models is unavailable (older hardware/OS, model not ready) or declines, fall back to today's behavior (`entry.message` / "Bell"). Summarization must never block or delay the notification — generate async and update, or summarize before posting only within a tight budget.
- **Opt-in / privacy:** mirror the AI-naming opt-in (`SettingsPreference.autoNameWithAIKey`) with an equivalent setting for notification summaries; keep it on-device only.
- **Where the summary surfaces:** desktop `UNMutableNotificationContent` (title and/or body) and the in-app Bell Feed row. May warrant a new optional `summary: String?` field on `BellFeedEntry` (Codable migration — additive/optional, like the `windowID` headroom precedent).
- **Coalescing:** consider whether multiple rapid bells from one tab should be summarized as a group ("3 bells in {tab}: …") rather than individually — overlaps with any future notification coalescing.
