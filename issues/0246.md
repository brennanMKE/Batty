## Description

Bell notifications currently look almost identical to one another, so a burst of them carries little information. The desktop notification's title is purely location — `Batty — {sessionTitle} › Pane {paneIndex} › {tabLabel}` (`BellNotifier.swift:54`) — and the body is `entry.message` or, when there's no OSC 9 message, the literal string `"Bell"` (`BellNotifier.swift:55`). The in-app Bell Feed entries share the same thin `message` field (`BellFeedStore.BellFeedEntry.message`). When several bells arrive from the same or similar tabs, the user can't tell them apart.

Use on-device **Foundation Models** to generate a short, human-readable summary of what each notification is actually about — the same class of use case as AI session naming (#0231 / #0232), and a natural reuse of that infrastructure.

## Resolution notes

> 🟢 Resolved 2026-06-17 — On-device Foundation Models now summarizes each bell into a short phrase shown in the Bell Feed, behind a Notifications setting that is on by default. Summarization is fully async and never delays the bell; everything falls back to today's text when unavailable or off.

## Root cause

Feature gap: bell notifications carried only a location title and a thin `message` body (`entry.message` or the literal "Bell"), so a burst of bells was indistinguishable. No summarization existed and there was no setting to govern it.

## Fix

A sibling of the #0231/#0232 naming infrastructure, wired into the existing bell pipeline:

- **`NotificationSummarizer.swift`** (new): a `NotificationSummarizing` protocol seam (async, returns `String?`, never throws), `NotificationSummary.sanitize` (maxLength 120 for a short phrase, strips wrapping quotes and control chars, rejects NONE/empty/overlong — distinct from the 2–4-word name sanitizer), and `FoundationModelsNotificationSummarizer` gated `#if canImport(FoundationModels)` + `#available(macOS 26.0, *)` + per-call `SystemLanguageModel.default.availability`, with a `makeIfAvailable()` factory mirroring the name suggester. No tool-calling — the summary is the response text directly.
- **`BellFeedEntry`** gains an optional `summary: String?` (additive Codable; old persisted data decodes without it).
- **`BellFeedStore.updateSummary(_:forEntryID:)`** is the single async write-back path, keyed by entry id (window-agnostic — the bell feed is one shared store, no `windows[0]` assumption).
- **`AppStateStore`** gains `notificationSummarizer` and `scheduleSummarization(...)`, fired from `recordBellTick` / `recordDesktopNotification` **after** the entry is recorded and the OS notification posted, inside a `Task` — nothing in the bell path awaits the model. Gated on the toggle and a non-nil summarizer.
- **Settings:** new key `co.sstools.Batty.summarizeNotificationsWithAI`, **default true**, `resolvedSummarizeNotificationsWithAI()` following the #0233 pattern; toggle added to Settings → Notifications → Bell, disabled with a "Requires macOS 26" caption on older systems.
- **`BellFeedView`** row shows `entry.summary ?? entry.message`; `BattyApp` wires the live summarizer at launch.
- **Desktop notification: approach (a)** — the in-app Bell Feed gets the live AI summary (it updates observably); the desktop notification keeps today's text in v1, since re-posting after an async model call would flicker or double-alert. Replacing the desktop notification when the summary arrives is a small future delta.
- **Signal source:** OSC 9 message + tab/session context only. Surface scrollback wasn't readily accessible without significant new libghostty plumbing, so it's deferred (see Gotchas).

## Gotchas

- **The live model path needs manual sign-off** on a macOS 26 machine with Apple Intelligence enabled: trigger several bells (OSC 9 messages help) and confirm the Bell Feed rows show distinguishable summaries, and that toggling the setting off reverts to plain `message`/"Bell". Marked `resolved`, not `closed`.
- **Desktop notifications keep today's text in v1** (approach a) — only the in-app Bell Feed shows the AI summary. If desktop summaries are wanted, re-post with the same notification identifier when the summary arrives; flagged as a possible enhancement, not committed scope.
- **Scrollback as a richer signal is deferred** — there's no readily-accessible read API for a surface's scrollback tail without new libghostty C-API plumbing, so summaries use the OSC 9 message + tab/session context. A dedicated "surface scrollback tail API for summarization context" ticket would be the way to pursue the richer signal later.

## Proposal / open questions

- **Signal source:** summarize from the recent terminal output around the bell (the tail of the surface's scrollback for that tab) and/or the OSC 9 message, so the summary reflects what happened ("build failed: 3 errors", "tests passed", "npm install finished") rather than a generic "Bell".
- **Reuse #0232's pattern:** the existing `FoundationModelsNameSuggester` (tool-calling `LanguageModelSession`, on-device, async, availability-gated, memoized) is the template. Consider a sibling summarizer (e.g. `FoundationModelsNotificationSummarizer`) or a shared abstraction. Wire it through the existing `AppStateStore` AI-naming machinery (`nameSuggester`, in-flight task tracking) rather than inventing a new path.
- **Graceful fallback:** when Foundation Models is unavailable (older hardware/OS, model not ready) or declines, fall back to today's behavior (`entry.message` / "Bell"). Summarization must never block or delay the notification — generate async and update, or summarize before posting only within a tight budget.
- **Opt-in / privacy:** mirror the AI-naming opt-in (`SettingsPreference.autoNameWithAIKey`) with an equivalent setting for notification summaries; keep it on-device only.
- **Where the summary surfaces:** desktop `UNMutableNotificationContent` (title and/or body) and the in-app Bell Feed row. May warrant a new optional `summary: String?` field on `BellFeedEntry` (Codable migration — additive/optional, like the `windowID` headroom precedent).
- **Coalescing:** consider whether multiple rapid bells from one tab should be summarized as a group ("3 bells in {tab}: …") rather than individually — overlaps with any future notification coalescing.
