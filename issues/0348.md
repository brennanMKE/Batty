# 0348 — Double-clicking the pane drag handle in a two-pane Session does not swap the panes

| | |
|---|---|
| **Status** | open |
| **Module** | Split / Pane |
| **Platform** | macOS |
| **First seen** | 2026-08-21 |

## Description

When a Session's Split tree contains exactly two visible Panes, swapping them requires the full drag-and-drop gesture: press the pane drag handle, drag across to the other Pane's drop zone, release. With only two Panes there is exactly one possible swap, so the drag is unnecessary ceremony — a double-click on the drag handle unambiguously means "swap these two."

Requested behavior: double-clicking the pane drag handle while the Session has exactly two visible Panes swaps them in place. With three or more visible Panes the double-click is a no-op (the target is ambiguous) and drag-to-swap remains the only path.

Today the only swap path is the #0127 drag-and-drop flow: `paneDragHandle` in `PaneView.swift` is an `.onDrag` source that sets `PaneSwapDragState.shared`, and `PaneSwapDropZone` overlays appear on the non-source Panes; a successful drop calls `tree.swapPanes(id:with:)`. There is no menu command or keyboard shortcut for swapping. The drag handle currently has no click or double-click gesture attached.

## Steps to reproduce

1. Launch Batty and split the Session once (two Panes visible).
2. Double-click the pane drag handle (the dotted-square icon at the far right of a Pane's tab bar).

## Expected behavior

The two Panes trade places. The splitter direction and ratio are unchanged; each Pane keeps its Tabs, live Terminal Sessions, and focus state — nothing is torn down or recreated (same guarantee `SplitTree.swapPanes` already provides for the drag path). Focus stays on whichever Pane had it, now in its new position.

With three or more visible Panes, double-clicking the handle does nothing.

## Actual behavior

Double-clicking the drag handle does nothing at any Pane count. The only way to swap two Panes is the full drag-and-drop gesture.

## Notes

Verified code locations (all paths exist):

- **Drag handle**: `paneDragHandle` computed view in `BattyKit/Sources/BattyKit/Views/PaneView.swift` (~line 390) — the `squareshape.split.2x2.dotted.inside` image with `.onDrag { PaneSwapDragState.shared.startDrag(from: pane.id) … }`, accessibility identifier `pane-drag-handle.<uuid>`. It is rendered only when `hasSiblingPanes` (`tree.visiblePanes.count > 1`) is true, in the tab-bar chrome row — not over the terminal body.
- **Swap API**: `SplitTree.swapPanes(id:with:)` in `BattyKit/Sources/BattyKit/Model/SplitTree.swift` (~line 370) — swaps two leaf `PaneRuntime`s, leaving split structure and ratios untouched; no-ops on same-id or missing ids. Already covered by `BattyKit/Tests/BattyKitTests/SplitTreePanePositionTests.swift`.
- **Pane count**: `SplitTree.visiblePanes` (`root.visibleLeafPanes`) gives the cheap 2-pane test. Spec the condition on *visible* panes: with a third Pane hidden via the eye button, two visible Panes still constitute an unambiguous swap, so `tree.visiblePanes.count == 2` → swap those two. (Hidden panes are excluded — matching how `hasSiblingPanes` already decides whether the handle appears at all.)
- **Drag state**: `BattyKit/Sources/BattyKit/Views/PaneSwapDragState.swift` — observable singleton for the drag-in-flight state. A double-click swap should not touch it; the swap is immediate, no drop zones involved.

**Files likely touched**

- `BattyKit/Sources/BattyKit/Views/PaneView.swift` — add `.onTapGesture(count: 2)` (or equivalent) to `paneDragHandle`; update its `.help` text to mention double-click when two panes are visible.
- `BattyKit/Sources/BattyKit/Model/SplitTree.swift` — only if a convenience like "swap the two visible panes" is added; `swapPanes(id:with:)` itself needs no change.
- `BattyKit/Tests/BattyKitTests/SplitTreePanePositionTests.swift` (or a new test file) — model-level coverage if any SplitTree convenience is added.
- Possibly `BattyKit/Sources/BattyKit/Help/03-panes.md` — user-facing help mentions the drag-to-swap affordance.

**Gotchas / risks**

- **Gesture coexistence with `.onDrag`**: the handle is an `.onDrag` source (an AppKit dragging source under the hood), not a SwiftUI `DragGesture`, so `.onTapGesture(count: 2)` should coexist — but macOS may delay or swallow the second click while deciding whether a drag began. Verify manually that (a) double-click swaps, (b) a normal drag-to-swap still works from the same handle, and (c) a single click still does nothing surprising. `ThemeSelectorView.swift` already stacks `.onTapGesture(count: 2)` ahead of a single-tap gesture (~lines 126–131) — attach the double-tap *before* the single-purpose modifiers if ordering fights arise. Do not reach for `.simultaneousGesture` unless plain ordering fails.
- **`docs/swiftui-observation-rules.md` is binding**: the double-click handler is an event-origin write, so calling `tree.swapPanes` from the tap closure is safe — but the swap must happen directly in the gesture handler, never from `body`/`onChange` reacting to a flag, and never hopped into a `Task` (the #0229 lesson). The comment on `paneEyeButton` in `PaneView.swift` shows the expected pattern and phrasing.
- **`docs/terminal-pane-requirements.md`**: the handle lives in the tab-bar chrome row, above the terminal body, so the pointer-input z-order constraint is not directly implicated — but do not move the gesture onto the pane body or add any overlay to satisfy it, and run the doc's manual checklist (clicks, file drop, IME) before marking the work complete since the change touches `PaneView`.
- **Preservation guarantee**: `swapPanes` swaps `PaneRuntime` references inside the value-type tree; Terminal Sessions live in the Surface registry keyed by `surfaceID`, so nothing is recreated. Any implementation that rebuilds Panes instead of calling `swapPanes` is wrong.
- **3+ panes**: keep the no-op silent (no beep, no alert). The `.help` tooltip is the discoverability surface; don't add modal feedback for an ambiguous double-click.
- This is UI-gesture work the implementer cannot fully verify headlessly — manual verification of the double-click and the still-working drag path is required; note in Gotchas at resolve time what was and wasn't verified.
