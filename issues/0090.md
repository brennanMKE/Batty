# 0090 — Click-to-focus fails on the bottom pane after a vertical split

| | |
|---|---|
| **Status** | open |
| **Module** | Pane / Split |
| **Platform** | macOS |
| **First seen** | 2026-05-11 |

## Description

After `Cmd-Shift-D` (vertical split), clicking inside the **bottom** pane's terminal body does not focus it. The user has to click the bottom pane's chip (tab) to focus that pane. Horizontal splits (`Cmd-D`) work as expected — clicking either left or right pane's terminal body focuses it.

`#0060` shipped click-to-focus by observing `tab.terminal.isFocused` and routing through `AppStateStore.focusPane(id:)`. That fix landed but evidently doesn't cover the vertical-split bottom case.

## Steps to reproduce

1. Open a session.
2. `Cmd-Shift-D` — pane B appears below pane A. Pane B is focused.
3. Click inside pane A's terminal body (top pane).
4. **Expected:** pane A focuses (per `#0052`'s indicator).
5. **Actual:** with the user's repro, pane B's chip-click path works but pane A's body-click may not — and the bottom-pane case the user described is the opposite (clicking in the bottom pane fails to focus when it's not the focused pane).

The user's specific case: vertical split, focus is on top pane, click in bottom pane's terminal body, focus does not move. Have to click the chip.

## Hypotheses

1. The vertical split's bottom pane has some hit-testing issue — perhaps the placeholder from `#0075` (the persistent terminal host architecture) doesn't extend fully to the bottom pane's frame, leaving a gap that the click lands in.
2. The bottom pane's `TerminalSurfaceView` may not be receiving focus from libghostty's `becomeFirstResponder` path on click, so `tab.terminal.isFocused` doesn't flip.
3. The split-resize divider may be intercepting clicks that should reach the bottom pane.
4. The placement preference key may be reporting a stale frame for the bottom pane (geometry transmitted in screen vs window vs named-coord-space).

## Investigation

- Read `BattyKit/Sources/BattyKit/SplitContainerView.swift` and `BattyKit/Sources/BattyKit/PaneView.swift` to verify the click-to-focus observer is identical for top and bottom panes.
- Check `TerminalHostStore.updatePlacements` — is the bottom pane's frame correct? If the host's named coordinate space's origin is at the top, but the placement reports y-coordinates that are window-relative, the bottom pane's terminal may be positioned off-screen or partially out of the hit-test region.
- Test horizontal split's left/right click-to-focus — if both work, the issue is specific to the vertical case.

## Acceptance criteria

- After `Cmd-Shift-D`, clicking inside either pane's terminal body (top or bottom) focuses that pane. `#0052`'s indicator moves immediately.
- Same after `Cmd-D` for left/right panes (regression check).
- A UI test in `BattyUITests` covers both splits and both directions.

## Out of scope

- Splits beyond 2 panes (recursive splits introduce more frames to test; if those have similar issues, file separately).

## Notes

- The user explicitly mentioned this as a regression worth UI-test coverage. The regression test is part of `#0092` (UI tests: focus interactions).
- Related: `#0051`, `#0060` (the click-to-focus work), `#0075` (the terminal-host architecture that determines where each terminal gets positioned).
