# 0465 — With a leaked DEC 1000/1006 or 1003 mouse mode at an idle shell prompt, #0411's guard withholds only left clicks and drags, so each scroll-wheel notch still types `64;COL;ROWM` and each cell of bare mouse motion still types `35;COL;ROWM` into the line editor

## Description

#0411 (branch `issue/0411`, head `6f1c3b46` at filing time, not yet merged
and may still change) stops a *left click* from typing SGR mouse-report
fragments at a shell prompt whose Terminal Session has DEC mouse reporting
left on by a program that died without resetting it. Its
`TerminalClickFocusMonitor` matches
`[.leftMouseDown, .leftMouseDragged, .leftMouseUp]` only
(`BattyKit/Sources/BattyKit/Commands/TerminalClickFocusMonitor.swift:47` on
the branch) and returns `nil` for those when `StuckMouseReportGuard`
matches. Nothing on that branch, and nothing on `main`, looks at
`.scrollWheel`, `.mouseMoved`, or the right/middle buttons.

libghostty reports more than left clicks while a mouse mode is set:

- **Scroll wheel** is reported under *every* mode (1000, 1002, 1003) as a
  press of button 64 (up) or 65 (down), once per row of accumulated delta,
  and the viewport is deliberately *not* scrolled
  (`src/Surface.zig:3612-3631` at the pinned Ghostty commit; details in
  Notes). At a zsh prompt with `?1000h ?1006h` leaked, one wheel notch types
  `64;COL;ROWM`; a trackpad flick types a run of them.
- **Bare mouse motion** (no button held) is reported under mode 1003 as
  button code 3 + 32 = 35 (`src/input/mouse_encode.zig:204`, `:237`), once
  per cell the pointer crosses. With `?1003h ?1006h` leaked, moving the
  mouse across the Pane types `35;COL;ROWM` per cell.

Both reach the PTY through exactly the path #0411 diagnosed for clicks, so
the shell shows the tail after ZLE eats the unbound `ESC [ <` prefix
(`bindkey '^[[<'` is `undefined-key` in `zsh -f`; re-checked for this
filing). Pressing Return then runs the garbage.

This is Ghostty's documented behaviour, not a Batty regression: Ghostty.app
does the same in the same state. It is filed because #0411 chose to
mitigate the leaked-mode state in the host rather than wait for the user to
`reset`, and the mitigation covers one of the three event classes that
produce the symptom. The report is derived from code reading; the filer did
not run a Beta build for it. Target: after 1.2.0, on `main`, after #0411
lands. Several decisions below are the user's (Open questions); the filer
did not make them.

## Steps to reproduce

Beta only (`./build.sh`), never the user's Prod app. With a build that
includes `issue/0411`:

1. Open a Tab at a zsh prompt (`zsh -f` is enough).
2. Run `printf '\e[?1000h\e[?1006h'`. Left-click the Pane: nothing is typed
   (#0411's guard). Now roll the scroll wheel one notch up over the Pane,
   then one notch down. Observe the command line.
3. Press Ctrl-U to clear the line. Run `printf '\e[?1003h\e[?1006h'`. Move
   the mouse slowly across a few cells of the Pane without pressing
   anything. Observe the command line.
4. Run `printf '\e[?1000l\e[?1003l\e[?1006l'` (or `reset`) and repeat 2-3;
   the fragments stop.
5. Optional cross-checks: repeat 2-3 in Ghostty.app (expected identical,
   since the reporting lives in Ghostty), and inside `less --mouse` or
   `vim` with `:set mouse=a` (expected: the program consumes the reports and
   nothing is typed — that behaviour must survive any fix).

## Expected behavior

Pinned today only by `docs/terminal-pane-requirements.md:19-22` ("fire
xterm mouse-reporting sequences if the running program requests them";
"Scroll wheel scrolls the terminal buffer") and by #0411's own expected
behaviour ("Mouse reports reach the PTY only while the foreground program
has asked for them"). Whatever the Open questions decide, a fix must
deliver:

Acceptance criteria:

1. **Scope is decided and written down.** For each of scroll (buttons
   64-67, including horizontal 66/67 from `Surface.zig:3621-3628`), bare
   motion under 1003, and right/middle clicks (also reported;
   `AppTerminalView+Input.swift:165`, `:205` send them to the surface), the
   issue records whether Batty withholds it at a stuck prompt, and why. The
   filer expects scroll and motion to be in scope and right/middle to be
   decided by the user (Open question 3).
2. **At an idle shell prompt with a leaked mode, nothing is typed.** With
   `?1000h ?1006h`: a wheel notch and a trackpad flick type nothing. With
   `?1003h ?1006h`: mouse movement types nothing. "Idle shell prompt" is
   the same predicate #0411 uses (a lone shell-named foreground process
   group), ideally through the shared helper #0464 proposes rather than a
   third copy.
3. **Programs that own the mouse keep every report.** `less --mouse`,
   `vim` with `mouse=a`, `htop`, Claude Code and anything else whose
   foreground group is not a lone shell still receive scroll and motion
   reports exactly as today. No event a TUI relies on changes meaning.
4. **No per-event process lookup for motion.** `mouseMoved` fires
   continuously; the decision must not run `sysctl`/`proc_name` on every
   event. Cache per surface and invalidate on a defined trigger (mode flag
   change via `isMouseCaptured`, foreground pid change, or a bounded
   number of events — implementer's design), and prove the lookup count in
   a unit test by counting calls on the injected seam, not by timing.
5. **Scrollback behaviour at a stuck prompt is decided** (Open question 1)
   and the decision is reflected in `docs/terminal-pane-requirements.md`
   §1's scroll row (`:22`) and checklist item (`:87`).
6. **Tests.** Unit tests for the decision (event class × captured ×
   idle-shell × Shift) via `./build.sh unit`. UI tests in the Tart VM extend
   `BattyUITests/StuckMouseModeClickTests` (branch) with a scroll case and a
   motion case using its typed-command probe (`:28-36` on the branch: type
   `touch <sentinel>\n` after the gesture and assert the file appears, which
   fails if garbage preceded the command). `XCUIElement.scroll(byDeltaX:deltaY:)`
   and `XCUICoordinate.hover()` are the macOS XCTest gestures for the two
   cases; the filer has not confirmed either lands as an `NSEvent` the local
   monitor sees, so verify that first (see Testing notes).
7. `./build.sh`, `./build.sh unit` and the VM UI suite pass. No sleeps in
   tests.

## Actual behavior

Per code reading at the pinned libghostty-spm `a2565ccf`
(`BattyKit/Package.resolved`), Ghostty commit `c4e16970a` (`Ghostty.ref` in
both the checkout and the local package repo):

- With `?1000h ?1006h` leaked at a zsh prompt, each wheel notch up appends
  `64;COL;ROWM` and each notch down `65;COL;ROWM`; the viewport does not
  scroll. #0411's guard is not consulted — the monitor never sees
  `.scrollWheel`.
- With `?1003h ?1006h` leaked, each cell the pointer crosses appends
  `35;COL;ROWM` (deduplicated per cell by `mouse_encode.zig:106-110`, so a
  still mouse types nothing and a slow sweep across 40 columns types 40
  fragments). Link hover is already suppressed in this state
  (`Surface.zig:4640-4646`).
- With `?1002h` (button-event mode) only drags report motion
  (`mouse_encode.zig:193`), and #0411 already withholds `.leftMouseDragged`
  while a click is being withheld, so 1002 is covered for the left button.
- Shift does not bypass scroll reporting: `scrollCallback` has no `mods.shift`
  check before `mouseReport` (`Surface.zig:3612-3631`), unlike button
  presses (`:3943-3946`) and motion (`:4650-4656`). So "hold Shift to scroll
  the scrollback", which works in a TUI that owns the mouse, does not help
  at a stuck prompt either — Shift-scroll types `68;COL;ROWM` (64 + 4).

## Notes

### Where scroll and motion reach libghostty (grepped, not guessed)

Batty itself has no `scrollWheel`, `mouseMoved` or `sendMousePos` code:
`grep -rn 'scrollWheel\|mouseMoved\|sendMousePos\|sendMouseScroll' Batty
BattyKit/Sources` finds nothing. The whole path is in the pinned package
and in Ghostty:

| Step | Scroll | Motion |
|---|---|---|
| AppKit entry | `AppTerminalView.scrollWheel(with:)` — `BattyKit/.build/checkouts/libghostty-spm/Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView+Input.swift:255-265` (builds `TerminalScrollModifiers` from `hasPreciseScrollingDeltas` / `momentumPhase`) | `AppTerminalView.mouseMoved(with:)` — same file `:228-232`; `mouseDragged` (`:243`) and the right/other drags forward to it; `mouseExited` (`:237-241`) sends `(-1, -1)` |
| Package wrapper | `TerminalSurface.sendMouseScroll(x:y:mods:)` — `Surface/TerminalSurface.swift:116-126` → `ghostty_surface_mouse_scroll` (`:125`) | `TerminalSurface.sendMousePos(x:y:mods:)` — `:97-106` → `ghostty_surface_mouse_pos` (`:105`) |
| Ghostty | `Surface.scrollCallback` — `src/Surface.zig:3466`; report block `:3612-3631`: `for (0..|y.delta|) mouseReport(.four / .five, .press, self.mouse.mods, pos)`, `:3621-3628` the same for `.six / .seven` horizontally, then `return` with the comment "If mouse reporting is on, we do not want to scroll the viewport" (`:3629-3631`) | `Surface.cursorPosCallback` — `:4548`; report block `:4648-4668`: Shift bypass only "if there is a mouse button pressed so that movement reports are not affected" (`:4650-4656`), then `mouseReport(button, .motion, …)` with `button == null` when nothing is pressed |
| Encoding | `mouse_encode.zig:219-220` (`.four => 64`, `.five => 65`), SGR `ESC[<{code};{x};{y}M` at `:151`; scroll is always `.press`, so always `M`, never `m` | `:204` (`null` button → 3), `:237` (motion +32) → 35; mode gate `:190-196`: `.normal` drops motion, `.button` needs a pressed button, `.any` reports everything |

`isMouseReporting()` (`Surface.zig:3684-3687`) is `config.mouse_reporting
and flags.mouse_event != .none`; `ghostty_surface_mouse_captured`
(`src/apprt/embedded.zig:2180`, surfaced as `AppTerminalView.isMouseCaptured`
via `TerminalSurface.swift:132-135`) checks only the flag, which is what
#0411 reads. The flag is set by DECSET 9/1000/1002/1003
(`src/terminal/stream_terminal.zig:1611-1634`) and SGR format by 1006
(`:1639`), and cleared only by the matching DECRST or a full reset — #0411's
Notes cover that.

The local package repo's only scroll patch,
`Patches/ghostty/0010-fix-scroll-remainder-zeroing.patch`, edits the
pending-remainder arithmetic in `scrollCallback` (hunks at the two
`pending_scroll_*` assignments) and does not touch the report block.

### Why the host cannot just clear the mode

`ghostty.h:1217-1230` exports `ghostty_surface_mouse_captured`,
`_mouse_button`, `_mouse_pos`, `_mouse_scroll` and `_mouse_pressure`; there
is no call to reset a surface's mouse mode, and on the exec backend there
is no way to inject `ESC[?1000l` into the terminal's *output* parser
(writing it to the PTY would type it at the shell). That is the constraint
`StuckMouseReportGuard.swift:12-14` records and why #0411 withholds events
instead. The alternatives — a package/Ghostty API to reset the flag, or
Ghostty clearing mouse modes on an OSC 133 A prompt mark — are upstream or
package changes (Open question 4).

### What a host-side mitigation can look like

- The same local-monitor shape as #0411: add `.scrollWheel` and
  `.mouseMoved` to the matched set, hit-test to the `AppTerminalView`, and
  return `nil` when the guard matches. `mouseMoved` only reaches the view
  through its tracking area, but the local monitor sees every
  `.mouseMoved` in the app, so the hit test (already in
  `promoteFirstResponderIfNeeded`, branch `:79-101`) is what scopes it.
- For scroll, withholding alone leaves the viewport unscrolled, which is
  what Ghostty does today anyway in this state. If the user wants scroll to
  *work* at a stuck prompt, the host can translate the withheld wheel delta
  into Ghostty's own scroll actions through
  `AppTerminalView.performBindingAction(_:)`
  (`AppTerminalView+PublicInput.swift:69`) with `scroll_page_lines:N`
  (`src/input/Binding.zig:473-474`) or `scrollToRow` (`:84`). That is a
  feature on top of the guard; see Open question 1.
- The guard must keep #0411's Shift carve-out for clicks (`:52-55` on the
  branch) and decide the equivalent for scroll (Shift-scroll is reported
  too, see Actual behavior).

### Constraints

- `docs/terminal-pane-requirements.md` §1 (pointer input) and §5 (the
  AppKit z-order constraint): the Pane must keep routing pointer input to
  the AppKit terminal host; a local `NSEvent` monitor that returns `nil` is
  the shape #0229/#0411 already use to intercept an event before the view
  sees it. No SwiftUI gesture or overlay.
- `docs/swiftui-observation-rules.md`: the monitor runs in event context
  and writes no observed state; keep it that way (a per-surface cache is
  plain state on the monitor or the guard, not `@Observable`).
- Scroll events arrive at high rate with momentum; whatever the guard does
  per event must be O(1) with no process calls (criterion 4).

## Open questions

1. **Withhold scroll, or withhold-and-scroll?** Withholding a wheel event at
   a stuck prompt costs nothing the user has today — Ghostty already
   refuses to scroll the viewport while reporting is on
   (`Surface.zig:3629-3631`). But the user may *want* scrollback to work at
   a prompt whose mode is stuck, which means translating the delta into
   `scroll_page_lines:N` as described in Notes. That changes the Pane from
   "typing garbage" to "scrolling normally" and hides the stuck state
   entirely, which may or may not be desirable: the user never learns the
   Tab needs a `reset`, and the next TUI they start inherits whatever that
   program does with an already-set mode. Downsides of plain withholding:
   none found beyond the status quo. Downsides of translating: added code
   on a hot path, and momentum/precision deltas need the same accumulation
   Ghostty does (`Surface.zig:3480-3530`). User decision.
2. **Withhold motion under 1003?** Movement reports at a stuck prompt type
   a fragment per cell, which is worse than clicks (it happens without any
   deliberate action). Withholding `mouseMoved` from the surface also stops
   `cursorPosCallback`'s side effects — un-hiding a hidden pointer
   (`:4591`) and link-hover refresh — but hover is already suppressed in
   this state (`:4640-4646`), so the practical loss is nil. The filer sees
   no reason not to; confirming.
3. **Right and middle clicks?** Also reported (`2;COL;ROWM`, `1;COL;ROWM`).
   Right-click at a prompt is the copy/context menu in Batty
   (`AppTerminalView+Input.swift:165-180`, selection menu only when the
   click lands in a selection); middle-click is rarely used on a Mac. In or
   out of scope here?
4. **Mitigate in the host at all, or fix the state?** The whole family
   (#0411, this issue) exists because no API clears the mode. A one-line
   package export (`ghostty_surface_reset_mouse_mode`, or a more general
   "run this DECRST through the parser" entry point) would let Batty clear
   the flag the moment the guard first matches, and every event class is
   then handled by Ghostty as if the program had cleaned up. That is a
   libghostty-spm release plus a Batty pin bump, and it changes the
   terminal's state behind the shell's back. Alternatively Ghostty could
   reset mouse modes on an OSC 133 A prompt mark (shell integration), which
   would be an upstream conversation. Host-side withholding is the
   no-dependency path; the user may prefer the structural one.
5. **Gate on the shared helper (#0464) or on `StuckMouseReportGuard`
   directly?** If #0464 lands first, this issue consumes the helper; if
   not, it extends `StuckMouseReportGuard` with event-class parameters and
   #0464 absorbs it later. Sequencing is the orchestrator's call.
6. **Target release.** After 1.2.0 on `main`, per the filing instruction.
   #0411 covers the reported symptom (clicks); scroll and motion need a
   leaked 1003 or a deliberate wheel at a stuck prompt, which the user has
   not reported.

## Testing notes

- Unit tests: `./build.sh unit` on the host. Test the decision function
  with injected seams (captured flag, foreground pid, group members, name,
  event class, Shift) and count seam calls to prove criterion 4; never
  `Task.sleep` or wall-clock assertions.
- UI tests: **only inside the Tart VM** via `tools/run-ui-tests-vm.sh`,
  never on a host Mac — XCUITest's synthetic scroll and hover would land on
  whatever app is frontmost on the host (AGENTS.md "UI test automation",
  #0409). Commit first; the runner tests `git archive HEAD`. The filer did
  not run any UI test for this filing.
- Before relying on `XCUIElement.scroll(byDeltaX:deltaY:)` / `hover()` in
  the VM, confirm with a throwaway run that they produce `.scrollWheel` /
  `.mouseMoved` events the local monitor receives (hover in particular may
  deliver a single `mouseMoved` to the destination point, which is enough
  for one fragment under 1003 but not a sweep). If they do not, fall back
  to the typed-command probe after a `printf` that leaves the mode on and a
  single gesture, as the branch's click tests do.
- By-hand Beta checks for criterion 3 (`less --mouse`, `vim mouse=a`,
  Claude Code) go in `## Work log`; the VM has no TUI fixtures for them.
