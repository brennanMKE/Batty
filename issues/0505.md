## Description

`website/demo.html` plays a single `Demo.mp4` with a one-line caption ("A single-window session with sidebar, recursive splits, and tab strips per pane."). It predates Projects, Git Status, Process Status, Open Quickly, the Command Palette, per-Session themes and the `batty` CLI, so the page a visitor watches shows almost none of what 1.3.0 ships. The user wants it replaced by **nine short, high-energy clips**, one per headline feature, recorded inside the Tart VM by a script that can be re-run whenever the app changes, with Batty-styled text overlays and a title-plus-paragraph caption under each clip.

This issue builds three things: the recording pipeline (`tools/demo/`, one entry point, VM only), the host-side edit step (trim, speed-up, overlays, encode, posters), and the new `demo.html`. Deploying the result is a separate, user-approved step after the user has reviewed the clips.

**Order: starts after 1.3.0 ships** (#0504 removes the Projects flag; #0503 is the iCloud sync backend whose Shared checkbox clip 1 shows).

## User decisions (2026-10-14)

Recorded as given by the user.

- **Nine clips, each 30–90 s.** The demos should be "high energy because this is a fun app to use and will boost the user's productivity": fast pacing, no dead air, speed-ups instead of waits.
- **The nine clips:**
  1. **Projects (new in 1.3).** Open a saved Project from the picker. It comes up with its full layout, startup commands, a Git Status Pane and a second Tab. Then the Open now strip: switch to an open Project, and ⌥↩ to open another copy. Also tick Shared (iCloud sync, #0503).
  2. **Sessions and Sidebar.** One Session per repo, names taken from the folder or git branch, colors, rename, drag to reorder, switching.
  3. **Splits, Tabs and Layouts.** Apply a layout preset, drag a divider, add Tabs to a Pane, move focus between Panes from the keyboard.
  4. **Git Status Pane.** Edit a file in nvim and watch Git Status update live; a split from it opens in the repo folder.
  5. **Process Status and Follow by Name.** `cargo build` in tokio, then follow the process by name across a restart.
  6. **Bell Feed.** A long command in a background Session rings the bell; the feed shows it, and clicking the entry jumps to that Pane. Use linux `make defconfig` or similar.
  7. **Open Quickly and Command Palette.** Fuzzy-jump to a Tab in another Session, then run commands from the palette.
  8. **Themes.** Themes per window and per Session; switch live. (See "Verified facts": there is no per-window Theme.)
  9. **`batty` CLI remote control.** Script Sessions, Panes and Tabs from a shell.
- **Repos.** Shallow clones (`git clone --depth 1 --single-branch`) at `~/Developer/<owner>/<repo>` inside the VM:
  - brennanMKE/Batty
  - brennanMKE/laya-go
  - brennanMKE/ShortLinks
  - neovim/neovim
  - tokio-rs/tokio
  - torvalds/linux

  If a shallow linux clone is too slow, a sparse or partial checkout is acceptable as long as clip 6 still works.
- **Overlays.** Batty-styled text over each recording, added in the edit, explaining the feature. Colors and font come from the website CSS (see "Style").
- **Captions.** Each video on `demo.html` gets a caption: a title, then one paragraph with the fuller explanation.
- **Re-runnable.** One script under `tools/demo/` regenerates every clip end to end whenever the user wants to update them.
- **Recording.** Recording and UI driving happen only inside the Tart VM, never on the host (`AGENTS.md` "UI test automation"). The host only edits the files that come back.
- **Out of scope:** narration and audio. The clips are silent.

## Verified facts (2026-10-14, `main` at `e4ed8f22`)

- **The VM runner.** `tools/run-ui-tests-vm.sh` clones the shared golden (`tart-golden require --xcode 27.0`), boots it `--no-graphics --no-audio` with a read-only share holding `git archive HEAD` tarballs of Batty and SlidingTabs, builds `Batty Beta.app` ad-hoc signed (`CODE_SIGN_IDENTITY=- CODE_SIGN_STYLE=Manual DEVELOPMENT_TEAM=`, `:504`, `:523`), runs `tools/vm-guest-broker.sh`, then `test-without-building` with `-only-testing` filters, and pulls `$GUEST_RESULTS` back to `build/ui-tests/<run-id>/` with a bounded `tar` over `tart exec` (`pull_results`, `:479-488`). The guest runs arbitrary shell through `tart exec "$CLONE" /bin/zsh -lc` (`run_guest_step`, `:470-475`), so a guest-side setup step (clone repos, install tools, seed `projects.json`) fits the existing shape. The guest has network over NAT (SwiftPM resolves from GitHub on every run, `docs/ui-testing-vm.md` "Gotchas"). Test step bound: 2400 s guest, 2700 s host (`:517-525`).
- **Recordings already work.** XCTest records every UI test in the guest. `BATTY_UI_KEEP_RECORDINGS=1` keeps them for passing tests by editing the guest's copy of the scheme (#0448), and `tools/export-ui-recordings.sh` exports them from the `.xcresult` as `<Class>.<testMethod>.mp4` plus a `qlmanage` poster. A failing-only run of 25 recordings was 152 MB.
- **Gated test classes are an established pattern.** `ViewGalleryTests` (#0451) skips unless `BATTY_UI_GALLERY=1`, which the runner forwards as `TEST_RUNNER_BATTY_UI_GALLERY=1` only when a filter names the class (`:414-417`). It also skips unless `kern.hv_vmm_present == 1`. Its notes cover two things the demo scenes will hit too: the persistent "App Background Activity" and "Notifications may include alerts" banners must be closed before capture, and Dark appearance is set by driving System Settings (`defaults write -g AppleInterfaceStyle` does not work in the guest; `osascript` to System Events hangs on an Automation prompt).
- **Guest display.** `ViewGalleryTests` captures are 1024x768 (`docs/ui-testing-vm.md` "View gallery screenshots"). That is the golden's display today. Nothing in the repo sets a clone's display (`git grep 'tart set'` finds only a comment).
- **The CLI already works in the VM.** `tools/vm-guest-broker.sh` (#0419) bootstraps the built app's embedded `BattyBroker` into the guest's `gui/<uid>` launchd domain. The ad-hoc build has no Team ID, so the XPC peer requirement is skipped (`docs/ui-testing-vm.md` "Broker and CLI-driven tests"). `CLIRemoteControlTests` and `CLIViewPaneTests` pass in the VM (29/29, run `20261009-154250-31272`, cited in `docs/beta-demo-script.md`). The test runner itself is sandboxed and reaches the CLI through the guest-only `nc` relay on `127.0.0.1:47911`, but a shell inside a Batty terminal Pane is Batty's child, not the runner's, so it can run the embedded CLI directly.
- **`docs/beta-demo-script.md` §0's `--sign` requirement is about the host install**, where `SMAppService` rejects an unsigned Beta's broker plist (#0401) and the user must register the broker through Settings. The VM never goes through `SMAppService`; `vm-guest-broker.sh` uses `launchctl bootstrap` directly.
- **Themes.** The global Theme is app-wide across all windows. Per-window Themes are out of scope (`ThemePreference.swift:152-153`, citing `multi-window-design.md` §10). The per-Session override is `SessionRuntime.localThemeName`, set from `SessionThemeSelectorView` and not persisted (`docs/themes.md` §9). Clip 8 therefore shows the global Theme switched live across every window and a per-Session override that leaves other Sessions alone. `Concepts.md:175-176` still says Theme selection is app-wide only and per-Session overrides are out of scope; that text predates the override and is not this issue's to fix.
- **Projects UI.** The Open Project picker is a fixed 860 x 600 sheet with Recent and All Projects tiers and an "Open now" strip of chips for open Projects (#0500). Return on a chip switches to the open Session; ⌥↩ and the chip's `+` button (`project-picker.open-now.another.<name>`) open another copy. Shared appears as the `Shared` checkbox in the Project Editor (`project-editor.shared`) and as an `icloud` / `icloud.fill` toggle on picker cards and chips (#0501) (`docs/ui-features.md` "Project Editor" and "Open Project picker").
- **The current demo assets are not in git.** `website/demo.html` references `Demo.mp4` and `Demo.jpg` at the site root (also the page's `og:image` / `twitter:image`). Neither is tracked: `git ls-files website` lists only HTML, CSS, the appcast, icons and READMEs, and `.gitignore` ignores `Demo.mp4` and `Demo.jpg` by name (copies sit in `tools/`).
- **Deploy.** batty.sstools.co is Apache on `photon`, DocumentRoot `/var/www/vhosts/batty.sstools.co`. Deploy with `rsync -avz --exclude '.DS_Store' --exclude '*.swp' --exclude '*.bak' -e ssh website/ photon:/var/www/vhosts/batty.sstools.co/`, no `--delete`, after a `-n` dry run. `scripts/deploy-website.sh` uses `rsync --delete` and must not be used (it would delete every older DMG on the server).
- **Host tooling.** `ffmpeg` is not installed on the host (`command -v ffmpeg` is empty). The host is macOS 27.0 with Xcode 27, so AVFoundation, Core Animation, Core Text and `xcrun xcresulttool` are available without installing anything.

## Open questions, researched, with recommendations

### 1. Driving the UI

**Options.** (a) XCUITest "demo scenes": a new `DemoSceneTests` class in `BattyUITests`, one test per clip, run through the VM runner. (b) CLI-only scripting through the guest relay. (c) AppleScript or `cliclick`-style synthetic input in the guest.

**Recommendation: (a), with the CLI used inside scenes where it is the faster setup path.** XCUITest is the only option already proven in the guest. It runs unattended, can click, drag, type and press shortcuts, and finds elements by the accessibility identifiers `docs/ui-features.md` lists. Its recordings come back through the existing `.xcresult` path. (b) cannot click a picker card, drag a Sidebar row or a divider, so it cannot show clips 1-3, 7 or 8 on its own. (c) is ruled out: `osascript` to System Events hangs on an Automation prompt in the guest (`ViewGalleryTests` notes).

Shape:

- Gate `DemoSceneTests` exactly like `ViewGalleryTests`: skip unless `BATTY_UI_DEMO=1` (forwarded as `TEST_RUNNER_BATTY_UI_DEMO=1` only when a filter names the class) and unless `kern.hv_vmm_present == 1`. A plain UI run skips all nine.
- Scenes assert that each step happened (the Pane appeared, the bell entry exists), so a scene that drifted fails loudly instead of recording a broken demo.
- **Pacing lives in the scene, dead time is removed in the edit.** The scene does each step and waits for its visible result, with short fixed holds (0.4-1.0 s) where a viewer needs to read something. Long waits (`cargo build`, `make defconfig`) are recorded at real speed and sped up in the edit. These holds are UI-test choices, like `ViewGalleryTests`' CPU-baseline pauses, not unit-test waits; the `AGENTS.md` async-test rule governs unit tests.
- **Each scene writes a cue sheet.** As it runs, the scene records `{t, kind, text}` entries (scene start and end, "speed up from here to here", "show this callout now", "show this keycap") against the recording clock and attaches them as JSON (`demo.<clip>.cues.json`, `lifetime = .keepAlways`). The edit step reads cues instead of hard-coded timestamps, so a re-run where the build takes 40 s instead of 70 s still lines up.
- **Typing speed.** `typeText` into a terminal Pane is near-instant. Commands should be typed visibly but quickly (for example, per-character `typeText` with a short delay, or a whole line at once with a callout saying what was typed). Decide during implementation by looking at a recording.

### 2. Recording inside the guest

**Options.** (a) XCTest's built-in per-test screen recording (#0448). (b) `screencapture -v` started in the guest around each scene. (c) An AVFoundation / ScreenCaptureKit recorder in the guest.

**Recommendation: (a).** It already works in the guest, needs no TCC grant, starts and stops with each test, and has a tested export path (`tools/export-ui-recordings.sh`). (b) and (c) need the Screen Recording permission for whatever process runs them. A fresh clone has no grant, the golden must not be modified, and a TCC prompt in a headless guest would block the run. Fall back to (b) only if the XCTest recordings turn out to be too low in frame rate or quality for the site; check that on the first run (open questions for the implementer: the recording's frame rate, bitrate and whether it follows the display size).

**Display size.** 1024x768 is too small for a website demo. The demo run should set the **clone's** display before boot (`tart set "$CLONE" --display 1920x1080`, or 1440x900 if the guest GPU struggles) and zoom the Batty window to fill it. Only the disposable clone changes, never the golden. Verify that XCTest's recording follows the clone's display size.

**Getting clips back.** Unchanged from the runner: `BATTY_UI_KEEP_RECORDINGS=1` keeps passing tests' recordings, `pull_results` brings `UITests.xcresult` back to `build/ui-tests/<run-id>/`, and the host exports the `.mp4` files and cue sheets with `xcrun xcresulttool export attachments`. Nine recordings of 1-3 min each are a few hundred MB. Raise the pull bound for demo runs if the existing 600 s / 660 s (`KEEP_RECORDINGS`) is not enough.

**Runner changes.** Extend `tools/run-ui-tests-vm.sh` with an opt-in demo mode rather than writing a second runner. The user's standing authorization (`AGENTS.md`, 2026-10-05) covers this runner, and its lease, memory, sweep and cleanup handling is already hardened. Demo mode adds: the clone display setting; a bounded guest setup step before the build (repos, tools, fixtures, see below); and the larger pull bound. Without the switch the runner behaves exactly as it does today.

**Guest setup** (a script, for example `tools/demo/guest-setup.sh`, run through `run_guest_step` in the clone only):

- Shallow-clone the six repos to `~/Developer/<owner>/<repo>`.
- Install what the scenes run: a Rust toolchain for `cargo build` (rustup, minimal profile) and Neovim (a release tarball). The golden has Homebrew (`tart-guest-agent` runs from `/opt/homebrew/bin`, per `~/Developer/Homelab/cameron/tart-ui-test-vm.md`); confirm before relying on `brew install` in the clone. Nothing is installed on the golden.
- Seed the fixtures: a saved Project with a multi-Pane layout, startup commands, a Git Status Pane and a second Tab; a second and third Project so the picker's tiers and the Open now strip have content; and a small uncommitted change for clip 4. The Projects UI tests (#0478, `docs/ui-features.md` "Projects UI tests") write a `projects.json` before launch and point the app at it with `BATTY_UI_TEST_PROJECTS_FILE`; the demo scenes can do the same. The startup-command trust sheet (`project-startup-trust.run`) appears on first open and is itself worth a beat in clip 1.
- Put the embedded CLI on `PATH` for shells inside Batty Panes for clip 9 (a symlink in a user-writable directory plus a `PATH` line in the guest's `~/.zshrc`; `/usr/local/bin` needs admin).

**Clip 6 and linux.** `make defconfig` on macOS has three known hazards to check in the guest: the kernel tree has case-colliding paths, which a case-insensitive APFS volume checks out wrongly; the kernel requires GNU Make 4.0 or later while macOS ships 3.81; and `scripts/kconfig` must build with Apple clang. Try, in order: a case-sensitive APFS disk image (`hdiutil create -fs "Case-sensitive APFS"`) holding a shallow clone, plus GNU Make; then a partial clone (`--filter=blob:none --sparse`) whose non-cone sparse patterns include every `Kconfig*` file, `scripts/`, the top-level `Makefile` and `arch/*/configs`, since Kconfig sources files from across the tree. If neither works, fall back to another long command that ends in a bell (a tokio `cargo build --release` or a neovim `make`), as the user allowed ("or similar"), and record which one in the Work log.

### 3. Overlay and edit tooling

**Options.** (a) `brew install ffmpeg` on the host (needs the user's OK). (b) A small Swift command-line tool on the host using AVFoundation. (c) Do the edit in the guest (ffmpeg through the guest's Homebrew).

**Recommendation: (b).** A Swift tool (for example `tools/demo/DemoCut/`, a standalone SwiftPM executable that is not part of the app or BattyKit) does everything needed with system frameworks only:

- `AVMutableComposition` trims to the scene's start and end cues and uses `scaleTimeRange` for the speed-up ranges.
- `AVVideoCompositionCoreAnimationTool` with `CATextLayer` / `CALayer` draws the title card, lower thirds and keycap chips in the website's colors with SF Pro, which is the site's own font stack on Apple devices.
- `AVAssetExportSession` (or `AVAssetWriter` for bitrate control) writes H.264 MP4, and `AVAssetImageGenerator` writes the poster JPEG.

It needs no install and no approval, it lives in the repo with the script, and it is fast enough to re-cut overlays without another VM run. (a) is a reasonable alternative only if the user would rather approve a Homebrew install; ffmpeg's `drawtext` cannot easily match the site's chip styling. (c) puts editing in a disposable guest, so every overlay tweak costs a 15-minute VM run, and it still downloads ffmpeg on every clone.

### 4. Clip 9: the CLI in the VM

**Recommendation: record clip 9 in the VM with the ad-hoc build. It needs no signing change.** The CLI works in the guest today: `vm-guest-broker.sh` bootstraps the broker with `launchctl`, bypassing the `SMAppService` registration that fails for an unsigned or ad-hoc Beta on the host (#0401), and the CLI UI tests pass there. In the demo the shell runs inside a Batty terminal Pane, outside the test runner's sandbox, so it calls the embedded CLI directly without the `nc` relay. The guest-setup step only has to put it on `PATH` (question 2). The clip should use `batty-beta` (the Beta name) or an alias to `batty`; decide which reads better on the site, since the shipped Prod CLI is `batty`.

`AGENTS.md` allows Developer ID signing **only** through `./build.sh package --sign` and `scripts/release.sh`. Neither is needed here, and this issue proposes no other signing. The guest has no certificates and the VM build stays ad-hoc.

### 5. Clip 1: Shared

iCloud cannot work in the VM: the ad-hoc build embeds no provisioning profile and the guest has no Apple Account. The clip shows only the Shared checkbox (or the picker card's `icloud` toggle) being ticked, with an overlay saying the Project now syncs to the user's other Macs through iCloud. It does not show a second Mac or a synced result. Check on the first recording that ticking Shared in the ad-hoc guest build shows the ticked state and the `icloud` glyph with no error.

### 6. Output format and size

- **Video:** H.264 High profile, MP4 with `moov` at the front (fast start, `AVAssetExportSession.shouldOptimizeForNetworkUse = true`), 1920x1080 or 1280x720 at 30 fps, no audio track. Screen content compresses well; target **about 1 MB per 10 s, at most 8 MB per clip**, and at most about 50 MB for all nine. Pick the resolution after looking at legibility at phone width: terminal text at 1280x720 may be too small.
- **Poster:** one JPEG per clip, 1280 px wide, under 200 KB, taken from a frame that shows the feature (a `poster` cue), not frame 0.
- **Layout on the page:** `preload="none"`, `controls`, `playsinline`, `muted`; a 16:9 box (`aspect-ratio: 16 / 9`) so posters don't shift the layout; each clip a `<figure>` with a `<figcaption>` holding an `<h2>` title and a `<p>` paragraph. Single column at phone width with at least a 16 px side gutter (the site's own sections use 24 px, `style.css:106`), no horizontal scroll. Keep the CTA and footer. Update `og:image` / `twitter:image` to clip 1's poster.
- **Files:** `website/demo/NN-<slug>.mp4` and `website/demo/NN-<slug>.jpg`. Recommend keeping the media out of git, as the current `Demo.mp4` already is: add `website/demo/*.mp4` and `website/demo/*.jpg` to `.gitignore`, and treat `build/demo/<run-id>/` as the source of truth until the user approves a set. Ask the user if they would rather commit them.

### 7. Deploy

Through the existing manual deploy, never `scripts/deploy-website.sh`: copy the approved clips into `website/demo/`, then `rsync -avz --exclude '.DS_Store' --exclude '*.swp' --exclude '*.bak' -e ssh website/ photon:/var/www/vhosts/batty.sstools.co/` with no `--delete`, after a `-n` dry run. Verify afterwards with `curl -I` that each `.mp4` returns 200 with `Content-Type: video/mp4` and `Accept-Ranges: bytes` (Safari needs range requests to play). The old `Demo.mp4` / `Demo.jpg` stay on the server; nothing deletes them. **Deploying is a shared-state action: user-run or explicitly approved, after the user has reviewed the clips.**

## The script

`tools/demo/make-demos.sh` is the single entry point. Proposed stages, each re-runnable on its own:

1. **Record (VM).** `BATTY_UI_DEMO=1 BATTY_UI_KEEP_RECORDINGS=1 tools/run-ui-tests-vm.sh BattyUITests/DemoSceneTests` with demo mode on, optionally narrowed to one scene (`make-demos.sh record 04`). Commit first: the runner tests `git archive HEAD`.
2. **Export (host).** `xcresulttool export attachments` for the nine recordings and nine cue sheets into `build/demo/<run-id>/raw/`.
3. **Cut (host).** `DemoCut` reads each recording, its cue sheet and an overlay text file (`tools/demo/overlays/NN-<slug>.json`: title, callout strings, keycap labels), and writes `build/demo/<run-id>/NN-<slug>.mp4` and `.jpg`. `make-demos.sh cut <run-id>` re-cuts without re-recording.
4. **Check.** Reports each clip's duration (30-90 s), file size (8 MB cap) and resolution, and fails on any clip out of range.
5. **Stage (host, on request).** `make-demos.sh stage <run-id>` copies an approved set into `website/demo/`. It never deploys.

Caption text for `demo.html` and overlay text live in the repo next to the script, so wording changes are a text edit plus a re-cut.

## Acceptance criteria

- `tools/demo/make-demos.sh` runs end to end and produces **9 clips, each 30-90 s, with overlays**, plus a poster per clip, recorded only in the Tart VM.
- Each clip shows the steps listed under "User decisions" for its feature, with fast pacing and no dead air; long commands are sped up, not waited out.
- Overlays use the website's colors and font (see "Style").
- `website/demo.html` shows all 9 clips with posters and a title-plus-paragraph caption each, and works at phone width (no horizontal scroll, at least a 16 px side gutter).
- A plain `tools/run-ui-tests-vm.sh` run (no demo switch) is unchanged, and `DemoSceneTests` skips in it.
- No host UI test, no host UI scripting, no change to the golden image, no signing beyond the existing ad-hoc VM build.
- **The user reviews the clips before anything is deployed.** Deploy is user-run or explicitly approved.

## Notes for the implementer

- Read `AGENTS.md` "UI test automation" and `docs/ui-testing-vm.md` before touching the runner. One Batty VM at a time; parallel agents must not each start a run.
- `tools/` is not a restricted area, but `scripts/` and `Configuration/` are. Nothing here should need either.
- Use the canonical vocabulary in overlays and captions (Session, Pane, Tab, Split, Theme, Bell Feed, Project; `Concepts.md`).
- Close the guest's persistent notification banners before each scene (`ViewGalleryTests` does this).
- Window restoration is off (#0444): each launch opens one fresh window with one Session at `$HOME`. Each scene builds the state it needs.
- A scene that needs real-time process behavior (Process Status ticks, the bell after `make`) waits for the visible result, not for a fixed time, where an accessibility signal exists.
