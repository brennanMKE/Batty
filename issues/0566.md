## Description

A pending Reminder lives only in Batty's memory, so any quit drops it. That includes a Sparkle install-and-relaunch, a crash, a logout, or closing the last Window. A "Remind me to check on PRs" set for Tomorrow at 9:00 AM then never fires, and Batty gives no warning in most of those cases. This is the motivating use for Reminders (#0514): set a Session aside in the evening and get the notification the next morning. This issue makes a pending Reminder's notification survive a quit, and it says plainly what is lost when it can't survive. Targets 1.4.0. Parent: [#0514](0514.md).

## Verified facts (main `254cfb2a`)

- **Sessions do not survive a relaunch.** `Concepts.md:70`, Session → Persisted: "nothing". `Concepts.md:271`, Reminder → Persisted: "nothing. Reminders do not survive a relaunch because Sessions do not." Workspace persistence was removed in #0172, and window restoration is disabled (#0444).
- **No notification is scheduled ahead of time.** `BellNotifier.postReminder` (`BattyKit/Sources/BattyKit/Runtime/BellNotifier.swift:158-169`) adds a `UNNotificationRequest` with `trigger: nil` only when the in-app `ReminderScheduler` fires. `AppStateStore.fireReminder` calls it (`Runtime/AppStateStore+Reminders.swift:69`, gate at `:94`). The #0514 spec (Edge cases → Quitting Batty) rejected a calendar or interval trigger "because that notification would fire after quit for a Session that is gone". This issue revisits that decision.
- **The in-app state is a dictionary.** `ReminderScheduler.pending: [UUID: SessionReminder]` (`Runtime/ReminderScheduler.swift:31`), keyed by Session id. `SessionRuntime.reminder` (`Runtime/SessionRuntime.swift:66`) mirrors it. Set, edit and cancel go through `AppStateStore.setReminder` / `editReminder` / `cancelReminder` (`AppStateStore+Reminders.swift:13`, `:36`, `:50`). A Session close cancels through `WindowRuntime.removeSession` (`Runtime/WindowRuntime.swift:319-321`, via `reminderCancelHandler`). A Window close cancels through `AppStateStore.removeWindow` (`Runtime/AppStateStore.swift:451-455`).
- **The quit alert mentions Reminders, but only sometimes.** `QuitConfirmation.informativeText` (`Views/QuitConfirmation.swift:60-66`) appends "N pending reminder(s) will be cancelled." It does so only when the "Quit Batty?" alert is shown at all. The alert is skipped when Settings' Confirm Quit is off (`:43`) and in UI-test mode.
- **Closing the last Window quits without asking.** `removeWindow` cancels that Window's Reminders, then `terminateIfLastContentWindowGone` (`AppStateStore.swift:539-561`) calls `terminateHandler()` directly. So the quit alert, if it appears, already counts 0 Reminders. The Window-close prompt (`QuitConfirmation.windowNeedsConfirmClose`, `:97-105`) appears only for running processes and says nothing about Reminders.
- **Crashes, logout and Sparkle relaunches give no warning.** A crash or a forced termination never reaches the alert. Unverified: whether Sparkle's install-and-relaunch path goes through `applicationShouldTerminate`, and so through the alert. `SUEnableAutomaticChecks` is set in `Configuration/Info.plist:56`.
- **Notification taps resolve only against in-memory feed entries.** The `BellNotifier` delegate is installed from `RootWindowView`'s `.task { setUpNotifier() }` (`Views/RootWindowView.swift:67`, `:110-124`), not from the app delegate. `didReceive` (`BellNotifier.swift:194-210`) reads `userInfo[entryIdUserInfoKey]`. The handler acts only if `store.bellFeed.entries` contains that id. Apple requires the `UNUserNotificationCenter` delegate to be set before the app finishes launching to receive the response that launched it. A cold-launch tap therefore probably gets lost today.
- **The delegate shows every banner while Batty runs.** `willPresent` always answers `[.banner, .sound]` (`BellNotifier.swift:186-191`). A system-delivered scheduled Reminder and the in-app fire would therefore show two banners unless they are deduplicated.
- **The gates.** "Show system notifications" is checked in `fireReminder` against `store.preferences` (`AppStateStore+Reminders.swift:94`). "Play sound" is read inside `postReminder`. Authorization is requested once, from `setUpNotifier` (`BellNotifier.ensureAuthorization`, `:61-69`). Per-Session mute does not apply to Reminders.
- **A Project-backed Session knows its Project.** `SessionRuntime.projectID` (`SessionRuntime.swift:57`) is in-memory only. `AppStateStore.requestOpenProject(id:mode:...)` (`Runtime/AppStateStore+ProjectStartup.swift:44`) defaults to `.focusExistingOrOpen`, and the Project record itself is persisted (`Concepts.md:52`).
- **Wake handling exists only while running.** `ReminderScheduler.observeSystemEvents()` is wired at `Batty/BattyApp.swift:91`.

## What "surviving a quit" can mean

The Session itself cannot come back, so the Reminder's Session, Split tree and Bell Feed row are gone after a relaunch. What can survive is:

1. **The notification.** macOS can deliver it while Batty is not running. For "check on PRs", the note is most of the value.
2. **A way back.** For a Project-backed Session, clicking the notification can reopen (or focus) the Project. For a plain Session, a click can only bring Batty forward.

## Recommended approach

**(a) Schedule a real system notification when a Reminder is set.**
- Whenever a Reminder is set or edited, add a `UNNotificationRequest` with a non-nil trigger.
  - For `.wallClock` (Tomorrow), use `UNCalendarNotificationTrigger(dateMatching:repeats: false)` with the stored components, so local-time and DST semantics match the in-app scheduler.
  - For `.instant`, the plan should choose between a calendar trigger built from the resolved date and a `UNTimeIntervalNotificationTrigger`, and justify the choice (behavior across sleep and clock changes).
- Use a stable identifier derived from the Reminder, for example `reminder.<reminderID>`. Remove the pending request on cancel, on edit (when the id changes), on Session close, on Window close and when the in-app path fires.
- The scheduled content carries everything a cold launch needs in `userInfo`: Session title at set time, note, Reminder id, and `projectID` when there is one. No feed entry exists yet at that point, so a new userInfo key is needed alongside `entryIdUserInfoKey`.
- **Dedupe with the in-app fire path.** While Batty runs, the in-app scheduler stays authoritative: it records the Bell Feed row, posts or updates the banner, and removes the scheduled request. `willPresent` suppresses (`[]`) a scheduled Reminder that the system delivers while Batty runs. The plan should confirm which side wins when both fire in the same instant, and make sure the user sees exactly one banner. Reusing one identifier for both may suffice.
- **Gates.**
  - If "Show system notifications" is off when a Reminder is set, schedule nothing.
  - If the setting changes while Reminders are pending, add or remove the scheduled requests.
  - "Play sound" is captured at schedule time. Say so in docs.
  - If authorization was denied, scheduling is a silent no-op, as posting is today.
  - Authorization may not have been requested yet when the first Reminder is set, because it runs from a window `.task`. The plan should check for that.

**(b) Project-backed Sessions: reopen on click after a relaunch.**
- Move the `UNUserNotificationCenter` delegate setup to the app delegate (`applicationWillFinishLaunching` or earlier), so a tap that launches Batty is delivered.
- On a tap whose Reminder id is not in memory:
  - when `projectID` is set and the Project still exists, call `requestOpenProject(id:mode: .focusExistingOrOpen)`; the existing startup-command trust prompt still applies
  - otherwise, just activate Batty
- Optionally record a Bell Feed row in the reopened Session that carries the note. The plan decides; leaving the row out is acceptable.
- No new persisted file is needed if `userInfo` carries the data. The plan must justify any file it adds.

**(c) Tell the user what is lost.**
- Update the quit alert's line. Pending Reminders no longer "will be cancelled". Their notifications will still arrive, but their Sessions will close. Proposed text for the plan or user to refine: "N pending reminder(s) will still notify you, but their Sessions will close."
- When "Show system notifications" is off, nothing is scheduled, so keep the current "will be cancelled" text.
- Closing the last Window should not silently cancel scheduled notifications. Decide whether `removeWindow` on the app's last Window keeps the scheduled requests, so it behaves like a quit, or removes them, so it behaves like a Session close, and make the quit and last-Window paths consistent.
- Session close (`WindowRuntime.swift:378`, "Its reminder … will be cancelled.") still cancels, and now also removes the scheduled request.

**Open question for the user (the plan should surface it, not guess):** should a plain (non-Project) Session's Reminder notify after a quit, even though clicking it can't restore the Session? The recommendation is yes, because the note is the point. That reverses #0514's stated reason, so the user should confirm.

## Acceptance criteria

1. Setting a Reminder schedules exactly one pending system notification request. Editing it replaces that request, and cancelling it, closing its Session or the in-app fire removes it. No orphan requests remain (checked through the fake).
2. With Batty quit before the due time, macOS shows the Reminder banner at the due time with the Session title and note. Unit tests cover what can be tested; manual or VM verification covers delivery.
3. While Batty runs, a due Reminder produces one Bell Feed row and one banner, not two.
4. After a relaunch, clicking a Project-backed Reminder's notification opens or focuses that Project. Clicking a plain one activates Batty and does nothing else.
5. "Show system notifications" off means nothing is scheduled, and turning it off removes pending scheduled requests.
6. The quit alert's Reminder line matches what will actually happen. Closing the last Window and Cmd-Q behave the same way for scheduled Reminders.
7. `Concepts.md` (Reminder → Persisted), `docs/notifications.md` and the #0514 Gotcha are updated.

## Root cause

A pending Reminder lived only in `ReminderScheduler`'s memory, and its system notification was posted with `trigger: nil` only when the in-app scheduler fired. Any quit, relaunch, crash or last-Window close dropped it.

## Fix

Followed the plan. A pending Reminder is now also scheduled as a non-repeating `UNCalendarNotificationTrigger` request under `co.sstools.Batty.reminder.<reminderID>` (`ScheduledReminderNotification`). Instant Reminders use UTC-pinned components; Tomorrow Reminders use their wall-clock components unchanged. Set, edit, cancel, Session close and non-last Window close keep the request in sync. The last Window close keeps it, like Cmd-Q. `fireReminder` records the Reminder id in `remindersFiredThisLaunch`, removes the request and posts under the same identifier. `willPresent` suppresses a scheduled delivery while its Reminder is live (and calls `reevaluate()`), when it was already fired in-app this launch, or while system notifications are off. The instant trigger is rounded up to the next whole second so the in-app fire normally comes first; the fired-id set covers a system delivery that still lands just after it (round 1 review). The settings toggle removes all prefixed requests (off) or schedules every pending Reminder (on). Nothing is scheduled under the UI-test manual clock. Taps route through `AppStateStore.handleNotificationTap`: known entry → jump, existing Project → `requestOpenProject`, else activate and log a `notice`. The notifier moved from `RootWindowView.setUpNotifier` to `AppStateStore.installNotifier()`, called from `applicationWillFinishLaunching`. The quit alert says Reminders "will still notify you, but their Sessions will close." when they are scheduled.

Small deviations:
- The pure presentation rule is `ScheduledReminderNotification.shouldPresent(payload:isLiveReminder:alreadyFiredInApp:systemNotificationsEnabled:)`, not `presentationOptions`, since it returns `Bool`. `alreadyFiredInApp` was added in round 2. The store-side wrapper is `presentNotification(_:)`.
- `BellNotifier.entryIdUserInfoKey` and `reminderText` became `nonisolated`, and the new value types are `nonisolated`, so the delegate can parse `userInfo` off the main actor.
- Added `SettingsPreference.resolvedBellSound(defaults:)` (the plan asked to check for it; it didn't exist).
- Round 2 merged main (#0568). `commitReminderSheet` calls `editReminder`, which calls `setReminder`, so the sheet commit both remembers the Tomorrow time and schedules or replaces the system request; `aSheetCommitSchedulesAndReplacesTheSystemRequestAndRemembersTheTime` covers it.
- Merged main again for #0567 (`batty session remind`). The conflict in `AppStateStore+Reminders.swift` kept both sides: this branch's scheduling, settings and tap code, and main's `SessionRemindOutcome` / `remindSessionForXPC`. The CLI verb calls `setReminder` and `cancelReminder`, so a CLI set schedules or replaces the system request and a CLI cancel removes it (`cancelReminder` → `cancelReminderState(keepSystemRequest: false)`). `xpcSessionRemindSchedulesReplacesAndRemovesTheSystemRequest` covers it, starting from a GUI-set Reminder and a second Session's request that must survive. `docs/batty-cli-design.md`, `docs/batty-cli-agent-workflows.md`, the `batty-cli` skill and `docs/notifications.md` now say a CLI-set Reminder still notifies after a quit.

## Plan

Written 2026-11-09 against `issue/0566` at `569f2a61`. I re-checked every "Verified facts" bullet against the code; all hold. Two additions: (1) a Cmd-Q quit never runs `removeWindow` (`applicationWillTerminate` tears down Pane content only), so a quit leaves scheduled requests in place with no extra work; (2) `WindowRuntime.removeSession` clears `session.reminder` *before* calling `reminderCancelHandler`, so the handler must read the Reminder id from `reminderScheduler.reminder(forSessionID:)` before it cancels.

### Decisions

- **Open question, settled by the orchestrator (2026-11-09): yes, a plain non-Project Session's Reminder still notifies after a quit, relaunch or crash.** The note is the point ("check on PRs" at 9 AM). After a relaunch, clicking a Reminder whose Session is gone activates Batty, opens or focuses the Project when the Reminder carried a `projectID` that still exists, and logs a `notice` line in every fallback case. It never crashes or silently does nothing.
- **One identifier for both deliveries:** `co.sstools.Batty.reminder.<reminderID>` (`ScheduledReminderNotification.identifier(for:)`). The in-app post (`postReminder`) switches from `entry.id` to this identifier, so a post made with `trigger: nil` replaces the pending scheduled request, and replaces it in Notification Center too. `entryIdUserInfoKey` stays in the in-app post's `userInfo`, so the existing tap path still works.
- **Dedupe:**
  - *In-app fires first* (the normal case). `fireReminder` first removes the scheduled request, then posts with the same identifier. The system never delivers the scheduled one.
  - *System delivers first* (the in-app loop runs late, e.g. App Nap). `willPresent` returns `[]` for a scheduled Reminder payload whose `reminderID` is still pending in the live `ReminderScheduler`, and calls `reminderScheduler.reevaluate()`, which fires the in-app path at once. That path shows the one banner.
  - *Orphans.* A scheduled payload whose Reminder is **not** live (left over from an earlier launch, then delivered while this launch runs) is presented normally, because nothing else will show it.
  - The user sees exactly one banner in every case.
- **Trigger for `.instant`: `UNCalendarNotificationTrigger`, with components (year through second) taken from a Gregorian calendar pinned to UTC and `timeZone = UTC` set on the components.** I did not use `UNTimeIntervalNotificationTrigger` for three reasons:
  - Its behavior across sleep is undocumented.
  - It counts elapsed time rather than the absolute instant the in-app scheduler compares against.
  - A missed non-repeating calendar trigger is delivered on wake, like the in-app wake handling.

  Pinning UTC keeps the absolute instant, so a time-zone change does not move it, matching #0514's instant semantics.
- **Trigger for `.wallClock` (Tomorrow):** the stored components are passed through unchanged (year, month, day, hour, minute, no `timeZone`), so they float with the local zone exactly as the in-app scheduler's calendar provider does.
- **Closing the last Window behaves like a quit.** `removeWindow` on the last `WindowRuntime` cancels the in-app scheduler entries and purges the feed rows as today, but **keeps** the system requests, because the app then terminates. Closing a non-last Window, while Batty keeps running, is a Session close for each of its Sessions and **removes** their requests. Cmd-Q and last-Window close are now consistent: both keep the requests. If the quit is held by a dirty Project Editor, the kept requests are delivered as orphans and still route correctly.
- **Session close still cancels**, and it now also removes the scheduled request. The Session close-confirmation line "Its reminder … will be cancelled." stays accurate.
- **Rename is not resynced.** The scheduled content carries the Session title as of the last set or edit. While Batty runs, the in-app post uses the fire-time title and replaces the request, so #0514's "title at fire time" still holds while running. Only a post-quit delivery shows the older title. This goes in Gotchas and docs.
- **"Play sound" is captured at schedule time.** It is not resynced on toggle. Docs say so.
- **"Show system notifications" toggle:**
  - Turning it **off** removes *every* pending request with the `co.sstools.Batty.reminder.` prefix, orphans from earlier launches included, so nothing arrives after the user turned notifications off.
  - Turning it **on** schedules every live pending Reminder.
  - `willPresent` also returns `[]` for a scheduled payload while the setting is off.
- **Authorization:** the `BellNotifier`, its delegate and `ensureAuthorization()` move to the app delegate. The delegate is installed in `applicationWillFinishLaunching` and authorization is requested there too, so both happen before any Window exists and before any Reminder can be set. As today, scheduling without authorization fails silently; `center.add`'s completion handler logs the error at `.notice`.
- **UI-test manual clock:** when `reminderScheduler.manualClock != nil`, nothing is scheduled with the system (and a `debug` line is logged). A real calendar trigger computed from a frozen clock would otherwise put real banners in the VM's Notification Center.
- **No Bell Feed row is recorded in a Project Session reopened from a tap.** The issue allows leaving it out, and the notification already showed the note. **No new persisted file is added:** `userInfo` carries everything a cold-launch tap needs.
- **Quit alert text:** with system notifications on, it reads "N pending reminder(s) will still notify you, but their Sessions will close." With them off, it keeps "N pending reminder(s) will be cancelled." (and nothing is scheduled in that case).

### User checklist

1. In Batty Beta, set a Reminder in 2 minutes with a note, then Cmd-Q. The banner "Batty — Reminder: <Session>" with the note appears at the due time.
2. Click it with Batty quit. Batty launches and comes forward with a fresh Session; there's no crash.
3. Repeat from a Project-backed Session. The click opens that Project (after the trust prompt, if it has unapproved startup commands).
4. Set a 2-minute Reminder and keep Batty running. You get exactly one banner and one Bell Feed row. Clicking it jumps to the Session.
5. Set a Reminder, then close the only Window. The banner still arrives. With two Windows open, closing the one holding the Session cancels it, and no banner arrives.
6. Settings → Notifications: turn "Show system notifications" off with a Reminder pending. Then quit, and no banner arrives.
7. Cmd-Q with a Reminder pending and Confirm Quit on. The alert reads "1 pending reminder(s) will still notify you, but their Sessions will close."
8. Set Tomorrow at 9:00 AM, quit overnight. It arrives at 9:00 AM. If the Mac slept through 9:00, it arrives on wake. This last part is unverified (see Risks).

### Risks

- **Unverified Apple behavior:**
  - that `UNCalendarNotificationTrigger` honors a `timeZone` set on its components;
  - that a non-repeating calendar trigger missed during sleep is delivered on wake;
  - that a `trigger: nil` add under an identifier that is pending replaces it.

  The plan removes the pending request explicitly before posting anyway. Checklist items 1 and 8 cover the first two.
- **Cold-launch tap timing:** `didReceive` may run before the first Window's view exists. `requestOpenProject` targets `windows.first`, which `AppStateStore.init` seeds, and the trust sheet appears when the view mounts. That is unverified until the user runs checklist item 3.
- **Moving notifier setup into the app delegate** means authorization is requested at launch rather than at first Window. In practice that is the same moment.
