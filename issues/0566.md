# 0566 — Reminders are lost when Batty quits, relaunches or crashes

| | |
|---|---|
| **Status** | open |
| **Module** | Session / BellFeed / Persistence |
| **Platform** | macOS |
| **First seen** | 2026-11-09 |

## Description

A pending Reminder lives only in Batty's memory, so any quit drops it. That includes a Sparkle install-and-relaunch, a crash, a logout, or closing the last Window. A "Remind me to check on PRs" set for Tomorrow at 9:00 AM then never fires, and Batty gives no warning in most of those cases. This is the motivating use for Reminders (#0514): set a Session aside in the evening and get the notification the next morning. This issue makes a pending Reminder's notification survive a quit, and it says plainly what is lost when it can't survive. Targets 1.4.0. Parent: [#0514](0514.md).

## Verified facts (main `254cfb2a`)

- **Sessions do not survive a relaunch.** `Concepts.md:70`, Session → Persisted: "nothing". `Concepts.md:271`, Reminder → Persisted: "nothing. Reminders do not survive a relaunch because Sessions do not." Workspace persistence was removed in #0172, and window restoration is disabled (#0444).
- **No notification is scheduled ahead of time.** `BellNotifier.postReminder` (`BattyKit/Sources/BattyKit/Runtime/BellNotifier.swift:158-169`) adds a `UNNotificationRequest` with `trigger: nil` only when the in-app `ReminderScheduler` fires. `AppStateStore.fireReminder` calls it (`Runtime/AppStateStore+Reminders.swift:69`, gate at `:94`). The #0514 spec (Edge cases → Quitting Batty) rejected a calendar or interval trigger "because that notification would fire after quit for a Session that is gone". This issue revisits that decision.
- **The in-app state is a dictionary.** `ReminderScheduler.pending: [UUID: SessionReminder]` (`Runtime/ReminderScheduler.swift:31`), keyed by Session id. `SessionRuntime.reminder` (`Runtime/SessionRuntime.swift:66`) mirrors it. Set, edit and cancel go through `AppStateStore.setReminder` / `editReminder` / `cancelReminder` (`AppStateStore+Reminders.swift:13`, `:36`, `:50`). A Session close cancels through `WindowRuntime.removeSession` (`Runtime/WindowRuntime.swift:319-321`, via `reminderCancelHandler`). A Window close cancels through `AppStateStore.removeWindow` (`Runtime/AppStateStore.swift:451-455`).
- **The quit alert mentions Reminders, but only sometimes.** `QuitConfirmation.informativeText` (`Views/QuitConfirmation.swift:60-66`) appends "N pending reminder(s) will be cancelled." It does so only when the "Quit Batty?" alert is shown at all. The alert is skipped when Settings' Confirm Quit is off (`:43`) and in UI-test mode.
- **Closing the last Window quits without asking.** `removeWindow` cancels that Window's Reminders, then `terminateIfLastContentWindowGone` (`AppStateStore.swift:539-561`) calls `terminateHandler()` directly. So the quit alert, if it appears, already counts 0 Reminders. The Window-close prompt (`QuitConfirmation.windowNeedsConfirmClose`, `:97-105`) appears only for running processes and says nothing about Reminders.
- **Crashes, logout and Sparkle relaunches give no warning.** A crash or a forced termination never reaches the alert. Unverified: whether Sparkle's install-and-relaunch path goes through `applicationShouldTerminate`, and so through the alert. `SUEnableAutomaticChecks` is set in `Configuration/Info.plist:56`.
- **Notification taps resolve only against in-memory feed entries.** The `BellNotifier` delegate is installed from `RootWindowView`'s `.task { setUpNotifier() }` (`Views/RootWindowView.swift:67`, `:110-124`), not from the app delegate. `didReceive` (`BellNotifier.swift:194-210`) reads `userInfo[entryIdUserInfoKey]`. The handler acts only if `store.bellFeed.entries` contains that id. Apple requires the `UNUserNotificationCenter` delegate to be set before the app finishes launching to receive the response that launched it. A cold-launch tap therefore probably gets lost today.
- **The delegate shows every banner while Batty runs.** `willPresent` always answers `[.banner, .sound]` (`BellNotifier.swift:186-191`). A system-delivered scheduled Reminder and the in-app fire would therefore show two banners unless they are deduplicated.
- **The gates.** "Show system notifications" is checked in `fireReminder` against `store.preferences` (`AppStateStore+Reminders.swift:94`). "Play sound" is read inside `postReminder`. Authorization is requested once, from `setUpNotifier` (`BellNotifier.ensureAuthorization`, `:61-69`). Per-Session mute does not apply to Reminders.
- **A Project-backed Session knows its Project.** `SessionRuntime.projectID` (`SessionRuntime.swift:57`) is in-memory only. `AppStateStore.requestOpenProject(id:mode:...)` (`Runtime/AppStateStore+ProjectStartup.swift:44`) defaults to `.focusExistingOrOpen`, and the Project record itself is persisted (`Concepts.md:52`).
- **Wake handling exists only while running.** `ReminderScheduler.observeSystemEvents()` is wired at `Batty/BattyApp.swift:91`.

## What "surviving a quit" can mean

The Session itself cannot come back, so the Reminder's Session, Split tree and Bell Feed row are gone after a relaunch. What can survive is:

1. **The notification.** macOS can deliver it while Batty is not running. For "check on PRs", the note is most of the value.
2. **A way back.** For a Project-backed Session, clicking the notification can reopen (or focus) the Project. For a plain Session, a click can only bring Batty forward.

## Recommended approach

**(a) Schedule a real system notification when a Reminder is set.**
- Whenever a Reminder is set or edited, add a `UNNotificationRequest` with a non-nil trigger.
  - For `.wallClock` (Tomorrow), use `UNCalendarNotificationTrigger(dateMatching:repeats: false)` with the stored components, so local-time and DST semantics match the in-app scheduler.
  - For `.instant`, the plan should choose between a calendar trigger built from the resolved date and a `UNTimeIntervalNotificationTrigger`, and justify the choice (behavior across sleep and clock changes).
- Use a stable identifier derived from the Reminder, for example `reminder.<reminderID>`. Remove the pending request on cancel, on edit (when the id changes), on Session close, on Window close and when the in-app path fires.
- The scheduled content carries everything a cold launch needs in `userInfo`: Session title at set time, note, Reminder id, and `projectID` when there is one. No feed entry exists yet at that point, so a new userInfo key is needed alongside `entryIdUserInfoKey`.
- **Dedupe with the in-app fire path.** While Batty runs, the in-app scheduler stays authoritative: it records the Bell Feed row, posts or updates the banner, and removes the scheduled request. `willPresent` suppresses (`[]`) a scheduled Reminder that the system delivers while Batty runs. The plan should confirm which side wins when both fire in the same instant, and make sure the user sees exactly one banner. Reusing one identifier for both may suffice.
- **Gates.**
  - If "Show system notifications" is off when a Reminder is set, schedule nothing.
  - If the setting changes while Reminders are pending, add or remove the scheduled requests.
  - "Play sound" is captured at schedule time. Say so in docs.
  - If authorization was denied, scheduling is a silent no-op, as posting is today.
  - Authorization may not have been requested yet when the first Reminder is set, because it runs from a window `.task`. The plan should check for that.

**(b) Project-backed Sessions: reopen on click after a relaunch.**
- Move the `UNUserNotificationCenter` delegate setup to the app delegate (`applicationWillFinishLaunching` or earlier), so a tap that launches Batty is delivered.
- On a tap whose Reminder id is not in memory:
  - when `projectID` is set and the Project still exists, call `requestOpenProject(id:mode: .focusExistingOrOpen)`; the existing startup-command trust prompt still applies
  - otherwise, just activate Batty
- Optionally record a Bell Feed row in the reopened Session that carries the note. The plan decides; leaving the row out is acceptable.
- No new persisted file is needed if `userInfo` carries the data. The plan must justify any file it adds.

**(c) Tell the user what is lost.**
- Update the quit alert's line. Pending Reminders no longer "will be cancelled". Their notifications will still arrive, but their Sessions will close. Proposed text for the plan or user to refine: "N pending reminder(s) will still notify you, but their Sessions will close."
- When "Show system notifications" is off, nothing is scheduled, so keep the current "will be cancelled" text.
- Closing the last Window should not silently cancel scheduled notifications. Decide whether `removeWindow` on the app's last Window keeps the scheduled requests, so it behaves like a quit, or removes them, so it behaves like a Session close, and make the quit and last-Window paths consistent.
- Session close (`WindowRuntime.swift:378`, "Its reminder … will be cancelled.") still cancels, and now also removes the scheduled request.

**Open question for the user (the plan should surface it, not guess):** should a plain (non-Project) Session's Reminder notify after a quit, even though clicking it can't restore the Session? The recommendation is yes, because the note is the point. That reverses #0514's stated reason, so the user should confirm.

## Acceptance criteria

1. Setting a Reminder schedules exactly one pending system notification request. Editing it replaces that request, and cancelling it, closing its Session or the in-app fire removes it. No orphan requests remain (checked through the fake).
2. With Batty quit before the due time, macOS shows the Reminder banner at the due time with the Session title and note. Unit tests cover what can be tested; manual or VM verification covers delivery.
3. While Batty runs, a due Reminder produces one Bell Feed row and one banner, not two.
4. After a relaunch, clicking a Project-backed Reminder's notification opens or focuses that Project. Clicking a plain one activates Batty and does nothing else.
5. "Show system notifications" off means nothing is scheduled, and turning it off removes pending scheduled requests.
6. The quit alert's Reminder line matches what will actually happen. Closing the last Window and Cmd-Q behave the same way for scheduled Reminders.
7. `Concepts.md` (Reminder → Persisted), `docs/notifications.md` and the #0514 Gotcha are updated.

## Test ideas

Unit tests go in `BattyKit/Tests/BattyKitTests/`. They use a fake scheduling seam rather than the real `UNUserNotificationCenter` (extend `BellNotifying`, or add a `ReminderNotificationScheduling` protocol), `TestClock`, and isolated `UserDefaults` per `docs/isolate-userdefaults-in-tests.md`. No sleeps (AGENTS.md "Asynchronous tests").

- `settingAReminderSchedulesOneSystemRequest`
- `editingAReminderReplacesItsScheduledRequest`
- `cancellingOrClosingTheSessionRemovesTheScheduledRequest`
- `closingTheWindowRemovesOrKeepsScheduledRequestsPerDecision`
- `inAppFireRemovesTheScheduledRequestAndPostsOnce`
- `tomorrowReminderUsesACalendarTriggerWithItsWallClockComponents`: pinned calendar and time zone, including the DST case from #0514.
- `systemNotificationsOffSchedulesNothing`, and `turningSystemNotificationsOffRemovesPendingRequests`. Use a non-default fixture: start with a request scheduled.
- `scheduledUserInfoCarriesProjectIDForAProjectBackedSession`
- `tapOnUnknownReminderWithProjectIDOpensTheProject`, and `tapOnUnknownReminderWithoutProjectIDOnlyActivates`. Make the tap routing a pure function that takes the userInfo and a store.
- `willPresentSuppressesAScheduledReminderWhileRunning`
- `quitConfirmationTextDescribesScheduledReminders`, and the "notifications off" variant (`QuitConfirmation.informativeText`).

Manual or VM check: set a 2-minute Reminder, quit Batty, and confirm the banner appears. Then click it with Batty quit and confirm Batty launches. For a Project Session, the Project opens.
