## Description

A **system-wide** metrics view: thermal state for the Mac plus the metrics `top` typically shows — CPU, memory, load average, process list — presented the way a native Mac app can rather than as a TUI. In the user's words:

> "create another issue for a view which shows thermals for the Mac along with other metrics typically shown by the `top` command."

Like #0304, #0305, and #0313 it is **design-gated per the #0301 umbrella**: visual designs are drafted and approved by the user before implementation starts; no move to implementation on an unapproved design.

**Not a duplicate of #0305.** #0305 is a Process Status view focused on a *single selected app or process* rather than the whole system; this view is the whole-system counterpart. They are complementary — Activity Monitor's overview versus its per-process inspector — and will likely share sampling infrastructure; whichever ships first should factor its sampler for reuse by the other.

## What is established vs what needs investigation

**Established (verified in this tree, 2026-08-07):**

- Batty already has footprint-sampling machinery from the #0285 memory work: `FootprintReader` reads `phys_footprint` via `task_info(mach_task_self_, TASK_VM_INFO)` (`BattyKit/Sources/BattyKit/Runtime/FootprintReader.swift`), driven by `FootprintMonitor` (`BattyKit/Sources/BattyKit/Runtime/FootprintMonitor.swift`). Both are own-process only — `mach_task_self_` is the one task port every process gets for free — but the reader/monitor pattern is a starting point for a sampler.
- **The RSS measurement trap is binding.** `ps -o rss` under-reported Batty's real footprint by **29×** on the original #0285 report and **7×** on a later instance (`issues/0290.md`, "Never measure this app with RSS"), because RSS excludes compressed and swapped pages. Any memory number this view shows must come from `phys_footprint` (or an equivalent compressed-aware counter), never RSS — including per-process numbers in the process list, where the same trap applies to every row.
- Batty is unsandboxed (`ENABLE_APP_SANDBOX = NO`, per CLAUDE.md), which widens the API options — but does **not** grant root.
- Reading *another* process's stats is restricted even unsandboxed: #0305 records a live `task_for_pid` failure from Batty's own log and the spike it requires (`proc_pidinfo` / `proc_pid_rusage` / shelling out). A whole-system process list hits that same wall multiplied across every row; this view inherits #0305's spike findings rather than redoing them.

**Needs investigation (before any design work — a design premised on unavailable data is a known failure mode for this project):**

- **Thermals are the genuinely uncertain part.** `powermetrics` requires root, which a user-level app cannot assume; the #0313 reference doc's "not supported" note points at `powermetrics`/`ioreg` for GPU/memory utilization for the same reason. Options to evaluate empirically:
  - `ProcessInfo.processInfo.thermalState` — public and notification-driven (`thermalStateDidChangeNotification`), but coarse: nominal / fair / serious / critical only.
  - `ioreg` / IOKit — what temperature or power keys are actually readable without elevation on Apple silicon.
  - SMC access via IOKit — historically how third-party temperature apps work; needs a spike to establish what a notarized, hardened-runtime app can read on current macOS.
- **The issue's first deliverable is therefore an availability spike**: establish exactly which thermal and system metrics are obtainable without elevated privileges, and bound the designs to those. Only after that does the visual-design phase start.

### The spike — and the two reversals it took to get right

This issue's first deliverable was an availability spike, because "a design premised on unavailable data is a known failure mode for this project." It took three rounds, and **both blocking findings were design decisions justified by claims that measurement reversed.**

**Reversal 1 — numeric temperatures were wrongly ruled out.** Round 1's spike concluded SMC key reads fail unprivileged, theorised an Apple-silicon transport difference (`AppleSMCKeysEndpoint`/`RTBuddyEndpointService`), and the design removed temperature and fan display — asserting in the mockup that this was "unavailable on this Mac, by design — not a bug."

The reviewer re-ran the probe and read real values. Two bugs, found by the implementer on re-verification and independently reproduced by the reviewer:

- Swift's hand-rolled `SMCParamStruct` measures `size=76 stride=76 align=4`; the equivalent C struct is **80** bytes (`keyInfo` at 28, `data32` at 44, `bytes` at 48). Swift reuses trailing padding C cannot. A 76-byte buffer returns `0xe00002c2`.
- `0xe00002c2` is **`kIOReturnBadArgument`** at `IOReturn.h:102` — one line below the `kIOReturnNotPrivileged` (`0x2c1`) the document itself quoted from that same header.
- Fixing the size alone still failed with `kSMCKeyNotFound` until a second bug surfaced: unswapped native `UInt32` key assignment.

With both fixed, all candidate keys read: `Tp09`, `Te05`, `Tg05`, `TW0P`, `FNum=1`, `F0Ac=1000 RPM`, `F0Mx=4900 RPM`, at ~0.14 ms per key. Intel-era `TC0P` fails cleanly, corroborating that key names are model-specific.

**Reversal 2 — the persistent connection was justified backwards.** Having established SMC access works, the design held the `io_connect_t` open across ticks because "the connection, not the individual key reads, is the expensive-to-repeat part." Measured over 200 iterations: a full `IOServiceGetMatchingService` + `IOServiceOpen` + `IOServiceClose` cycle costs **~0.054 ms** against **~0.129 ms** for a single `readBytes` — roughly **3× cheaper than one key read**. That single claim was the sole basis for an apparatus of open hooks, explicit closes on both hide paths, a double-close guard and a close-race guard. The design now opens and closes per tick, holds nothing between ticks, and the apparatus is gone.

**Other spike findings**, all reproduced by the reviewer:

- `powermetrics` as uid 501: exit 1, "must be invoked as the superuser." Confirmed, not assumed.
- `ProcessInfo.thermalState` works at 0.00012 ms/call. A real notification firing was **not** observed in a 5 s idle window — recorded as unverified rather than asserted.
- Non-thermal system metrics (`getloadavg`, `host_processor_info`, `host_statistics64`, `hw.memsize`, `kern.memorystatus_vm_pressure_level`) are all free and sub-millisecond.
- **The whole-system process sweep costs 0.13 ms to enumerate ~803 pids and 1.3–2.2 ms to sample them all**, cross-checked against `footprint` and `ps` with exact matches. That number is what justifies showing the full list rather than a top-N.
- `proc_name` fails for **280 of ~803** pids, spanning **213 distinct root-owned daemons** — the boundary is plain process ownership, not anything Batty-specific. An earlier draft wrongly attributed all failures to `/usr/bin/login`, which is only the largest single bucket at 26.
- `proc_pidpath` fails for **pid 0 (`kernel_task`)**, which `proc_listallpids` returns — so a per-row "never blank" guarantee needs a third hardcoded fallback.

### The three decisions, for the user to accept or redirect

1. **Metrics and fidelity** — `thermalState`'s four coarse states *and* numeric SMC temperatures and fan RPM, now that the spike proved them readable. Per-core plus aggregate CPU, compressed-aware memory breakdown, load average, and a **full, un-truncated, sortable process list** rather than top-N, because the measured sweep cost does not justify truncating.
2. **Sampling interval** — fixed at 1 s, matching Activity Monitor and #0305. Adaptive and configurable were both rejected as unjustified complexity against a measured cost of roughly 0.5% of the interval.
3. **Hidden-pane history** — discarded entirely on hide. Re-sampling is too cheap for kept history to buy perceptible continuity, and discarding makes "zero cost while suspended" literal. The named consequence: CPU% reads "—" for one tick after each show, because the delta baseline restarts. That is expected, not a bug to fix later.

**Two caveats carried forward rather than resolved:** SMC access has not been re-verified inside the signed, notarized, hardened-runtime app bundle, and SMC key names are model-specific.

### Shared with #0305

The per-pid libproc sampling primitive is genuinely shared — task info, rusage, the name/path fallback tier, argv. Whole-machine metrics (thermal, aggregate CPU, memory, load average) are #0314-only. Whichever of the two implements first factors that primitive for the other.

### Review

`claude-opus-5`, three rounds. Every round found something, and the first two found design decisions resting on false premises — the failure mode the design-first gate exists to catch. Round 3 swept every place the removed apparatus had been described to confirm no half-removed residue survived, and independently re-measured the connection cost at 0.0536 ms/cycle against the design's stated 0.050.

Two nits accepted rather than spending a fourth round: `docs/README.md`'s blurb says the view "holds no kernel handle at any time, including while active", which overshoots — it holds one for the ~3.4 ms of each sweep, and §6's own wording ("never held for longer than one tick") is the precise version. And §4 says "all three of §3's categories" where §3 and §6 both say four.

## Design-phase questions (to answer in the design phase, not decided here)

1. **Which metrics, at what fidelity?** Load average, CPU per core vs aggregate, memory pressure vs raw footprint sums, top-N process list vs full list, and whether thermal display is the coarse four-state `thermalState` or something richer if the spike finds it.
2. **Sampling interval** — and whether it is fixed, user-configurable, or adaptive (e.g. slower when nothing changes).
3. **Hidden-pane history** — does a hidden pane keep its history (so re-showing has continuity) or discard it (so hiding truly costs zero memory growth)? Open question; #0303's contract governs whichever is chosen.

## The #0303 lifecycle matters more here than for any other view

A metrics pane polls continuously by definition — this is the canonical recurring-work case #0303 exists to govern. It must demonstrably stop sampling when hidden and release on close, **observably** (log evidence, a counter, a footprint delta — not an assertion). Given #0285 was an unbounded-memory-growth umbrella, a monitoring pane that itself leaks memory or burns CPU would be a bad joke; the design should state its own resource budget.
