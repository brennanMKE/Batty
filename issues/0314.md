## Description

A **system-wide** metrics view: thermal state for the Mac plus the metrics `top` typically shows — CPU, memory, load average, process list — presented the way a native Mac app can rather than as a TUI. In the user's words:

> "create another issue for a view which shows thermals for the Mac along with other metrics typically shown by the `top` command."

Like #0304, #0305, and #0313 it is **design-gated per the #0301 umbrella**: visual designs are drafted and approved by the user before implementation starts; no move to implementation on an unapproved design.

**Not a duplicate of #0305.** #0305 is a Process Status view focused on a *single selected app or process* rather than the whole system; this view is the whole-system counterpart. They are complementary — Activity Monitor's overview versus its per-process inspector — and will likely share sampling infrastructure; whichever ships first should factor its sampler for reuse by the other.

## What is established vs what needs investigation

**Established (verified in this tree, 2026-08-07):**

- Batty already has footprint-sampling machinery from the #0285 memory work: `FootprintReader` reads `phys_footprint` via `task_info(mach_task_self_, TASK_VM_INFO)` (`BattyKit/Sources/BattyKit/Runtime/FootprintReader.swift`), driven by `FootprintMonitor` (`BattyKit/Sources/BattyKit/Runtime/FootprintMonitor.swift`). Both are own-process only — `mach_task_self_` is the one task port every process gets for free — but the reader/monitor pattern is a starting point for a sampler.
- **The RSS measurement trap is binding.** `ps -o rss` under-reported Batty's real footprint by **29×** on the original #0285 report and **7×** on a later instance (`issues/0290.md`, "Never measure this app with RSS"), because RSS excludes compressed and swapped pages. Any memory number this view shows must come from `phys_footprint` (or an equivalent compressed-aware counter), never RSS — including per-process numbers in the process list, where the same trap applies to every row.
- Batty is unsandboxed (`ENABLE_APP_SANDBOX = NO`, per CLAUDE.md), which widens the API options — but does **not** grant root.
- Reading *another* process's stats is restricted even unsandboxed: #0305 records a live `task_for_pid` failure from Batty's own log and the spike it requires (`proc_pidinfo` / `proc_pid_rusage` / shelling out). A whole-system process list hits that same wall multiplied across every row; this view inherits #0305's spike findings rather than redoing them.

**Needs investigation (before any design work — a design premised on unavailable data is a known failure mode for this project):**

- **Thermals are the genuinely uncertain part.** `powermetrics` requires root, which a user-level app cannot assume; the #0313 reference doc's "not supported" note points at `powermetrics`/`ioreg` for GPU/memory utilization for the same reason. Options to evaluate empirically:
  - `ProcessInfo.processInfo.thermalState` — public and notification-driven (`thermalStateDidChangeNotification`), but coarse: nominal / fair / serious / critical only.
  - `ioreg` / IOKit — what temperature or power keys are actually readable without elevation on Apple silicon.
  - SMC access via IOKit — historically how third-party temperature apps work; needs a spike to establish what a notarized, hardened-runtime app can read on current macOS.
- **The issue's first deliverable is therefore an availability spike**: establish exactly which thermal and system metrics are obtainable without elevated privileges, and bound the designs to those. Only after that does the visual-design phase start.

### The spike — and the two reversals it took to get right

This issue's first deliverable was an availability spike, because "a design premised on unavailable data is a known failure mode for this project." It took three rounds, and **both blocking findings were design decisions justified by claims that measurement reversed.**

**Reversal 1 — numeric temperatures were wrongly ruled out.** Round 1's spike concluded SMC key reads fail unprivileged, theorised an Apple-silicon transport difference (`AppleSMCKeysEndpoint`/`RTBuddyEndpointService`), and the design removed temperature and fan display — asserting in the mockup that this was "unavailable on this Mac, by design — not a bug."

The reviewer re-ran the probe and read real values. Two bugs, found by the implementer on re-verification and independently reproduced by the reviewer:

- Swift's hand-rolled `SMCParamStruct` measures `size=76 stride=76 align=4`; the equivalent C struct is **80** bytes (`keyInfo` at 28, `data32` at 44, `bytes` at 48). Swift reuses trailing padding C cannot. A 76-byte buffer returns `0xe00002c2`.
- `0xe00002c2` is **`kIOReturnBadArgument`** at `IOReturn.h:102` — one line below the `kIOReturnNotPrivileged` (`0x2c1`) the document itself quoted from that same header.
- Fixing the size alone still failed with `kSMCKeyNotFound` until a second bug surfaced: unswapped native `UInt32` key assignment.

With both fixed, all candidate keys read: `Tp09`, `Te05`, `Tg05`, `TW0P`, `FNum=1`, `F0Ac=1000 RPM`, `F0Mx=4900 RPM`, at ~0.14 ms per key. Intel-era `TC0P` fails cleanly, corroborating that key names are model-specific.

**Reversal 2 — the persistent connection was justified backwards.** Having established SMC access works, the design held the `io_connect_t` open across ticks because "the connection, not the individual key reads, is the expensive-to-repeat part." Measured over 200 iterations: a full `IOServiceGetMatchingService` + `IOServiceOpen` + `IOServiceClose` cycle costs **~0.054 ms** against **~0.129 ms** for a single `readBytes` — roughly **3× cheaper than one key read**. That single claim was the sole basis for an apparatus of open hooks, explicit closes on both hide paths, a double-close guard and a close-race guard. The design now opens and closes per tick, holds nothing between ticks, and the apparatus is gone.

**Other spike findings**, all reproduced by the reviewer:

- `powermetrics` as uid 501: exit 1, "must be invoked as the superuser." Confirmed, not assumed.
- `ProcessInfo.thermalState` works at 0.00012 ms/call. A real notification firing was **not** observed in a 5 s idle window — recorded as unverified rather than asserted.
- Non-thermal system metrics (`getloadavg`, `host_processor_info`, `host_statistics64`, `hw.memsize`, `kern.memorystatus_vm_pressure_level`) are all free and sub-millisecond.
- **The whole-system process sweep costs 0.13 ms to enumerate ~803 pids and 1.3–2.2 ms to sample them all**, cross-checked against `footprint` and `ps` with exact matches. That number is what justifies showing the full list rather than a top-N.
- `proc_name` fails for **280 of ~803** pids, spanning **213 distinct root-owned daemons** — the boundary is plain process ownership, not anything Batty-specific. An earlier draft wrongly attributed all failures to `/usr/bin/login`, which is only the largest single bucket at 26.
- `proc_pidpath` fails for **pid 0 (`kernel_task`)**, which `proc_listallpids` returns — so a per-row "never blank" guarantee needs a third hardcoded fallback.

### The three decisions, for the user to accept or redirect

1. **Metrics and fidelity** — `thermalState`'s four coarse states *and* numeric SMC temperatures and fan RPM, now that the spike proved them readable. Per-core plus aggregate CPU, compressed-aware memory breakdown, load average, and a **full, un-truncated, sortable process list** rather than top-N, because the measured sweep cost does not justify truncating.
2. **Sampling interval** — fixed at 1 s, matching Activity Monitor and #0305. Adaptive and configurable were both rejected as unjustified complexity against a measured cost of roughly 0.5% of the interval.
3. **Hidden-pane history** — discarded entirely on hide. Re-sampling is too cheap for kept history to buy perceptible continuity, and discarding makes "zero cost while suspended" literal. The named consequence: CPU% reads "—" for one tick after each show, because the delta baseline restarts. That is expected, not a bug to fix later.

**Two caveats carried forward rather than resolved:** SMC access has not been re-verified inside the signed, notarized, hardened-runtime app bundle, and SMC key names are model-specific.

### Shared with #0305

The per-pid libproc sampling primitive is genuinely shared — task info, rusage, the name/path fallback tier, argv. Whole-machine metrics (thermal, aggregate CPU, memory, load average) are #0314-only. Whichever of the two implements first factors that primitive for the other.

## Design-phase questions (to answer in the design phase, not decided here)

1. **Which metrics, at what fidelity?** Load average, CPU per core vs aggregate, memory pressure vs raw footprint sums, top-N process list vs full list, and whether thermal display is the coarse four-state `thermalState` or something richer if the spike finds it.
2. **Sampling interval** — and whether it is fixed, user-configurable, or adaptive (e.g. slower when nothing changes).
3. **Hidden-pane history** — does a hidden pane keep its history (so re-showing has continuity) or discard it (so hiding truly costs zero memory growth)? Open question; #0303's contract governs whichever is chosen.

## The #0303 lifecycle matters more here than for any other view

A metrics pane polls continuously by definition — this is the canonical recurring-work case #0303 exists to govern. It must demonstrably stop sampling when hidden and release on close, **observably** (log evidence, a counter, a footprint delta — not an assertion). Given #0285 was an unbounded-memory-growth umbrella, a monitoring pane that itself leaks memory or burns CPU would be a bad joke; the design should state its own resource budget.

### Resolution notes

Every metric and fidelity decision follows the approved design (§2/§7): coarse `thermalState` chip *and* numeric SMC temperature/fan tiles, per-core + aggregate CPU, compressed-aware memory breakdown with a pressure chip, full un-truncated sortable process list with the three-tier name fallback and "—" (never `0`) for permission-denied rows, fixed 1-second sampling, and discard-on-hide for every piece of delta state. Nothing in the design was found unbuildable as drawn; no metric the phase-1 spike ruled out is shown here.

Before writing any BattyKit source, every low-level technique the design's spike used — `host_processor_info`, `host_statistics64`, `getloadavg`, libproc (`proc_listallpids`/`proc_pidinfo`/`proc_pid_rusage`/`proc_name`/`proc_pidpath`), and the classic SMC struct-method protocol (raw 80-byte hand-offset buffer, native-order key packing) — was independently re-run as a throwaway `swift <file>.swift` script on this implementation's own machine before being ported into the package. All of it reproduced the design doc's findings on this machine, including real SMC temperature/fan reads (`Tp09 = 40.0°C`, `F0Ac = 1000.0 RPM`, `FNum = 1`) and `TC0P` failing cleanly (`kSMCKeyNotFound`) — the same numbers and outcomes `docs/design/system-metrics-view.md` §1.4 recorded.

### Fix

- **Shared sampling primitives** (factored for #0305's reuse, per the design's §5 commitment — whichever view ships first factors the shared sampler):
  - `ProcessMetricsReader` (`BattyKit/Sources/BattyKit/Runtime/ProcessMetricsReader.swift`) — `ProcessSample`, `sample(pid:) -> ProcessSample?`, `sampleAll() -> [ProcessSample]`. Stateless libproc reads; `nil` fields mean "denied," never a fabricated `0`; pid 0 hardcodes `"kernel_task"`; `ESRCH` distinguishes "exited" (returns `nil`) from `EPERM` (returns a sample with `nil` task-info fields).
  - `ProcessCPUDeltaTracker` (`ProcessCPUDeltaTracker.swift`) — per-pid CPU% from two `ProcessSample` reads, via `MachTimebase`-converted tick deltas. Caller-owned per §5's "each view needs its own previous-tick baseline."
  - `SystemCPUReader`/`CoreCPUDeltaTracker` (`SystemCPUReader.swift`) — per-core `host_processor_info` ticks and their own delta tracker (`#0314`-only, not shared with `#0305`).
- **`#0314`-only whole-machine readers**: `SystemMemoryReader` (`SystemMemoryReader.swift` — `host_statistics64` + `hw.memsize` + `kern.memorystatus_vm_pressure_level`), `SystemLoadReader` (`SystemLoadReader.swift` — `getloadavg`), `SMCThermalReader` (`SMCThermalReader.swift` — per-tick open/read/close `AppleSMC` connection, exactly matching §6's "cheaper to reopen than to hold" correction: no connection field, no held handle between ticks).
- **`SystemMetricsSampler`** (`SystemMetricsSampler.swift`) — one `sampleOnce()` call per tick combining all of the above into a `SystemMetricsSnapshot` (`SystemMetricsSnapshot.swift`); owns the two delta trackers, so discarding the whole sampler instance discards both baselines at once.
- **`SystemMetricsPaneContent`** (`SystemMetricsPaneContent.swift`) — the model-owned `PaneContentLifecycle` conformer (`@MainActor @Observable`), following `FootprintMonitor`'s existing `Task`-loop-with-injectable-provider pattern. `setUp`/`setVisible`/`tearDown` drive a `PaneLifecycleController`; only an `.applied → .active` transition starts the 1s `Task` and (re)builds a fresh `SystemMetricsSampler` — the sampler, and both its delta maps, are discarded (`sampler = nil`) on every hide/teardown and rebuilt from scratch on the next show, per §4's "discard, not keep."
- **`SystemMetricsPaneView`** (`BattyKit/Sources/BattyKit/Views/SystemMetricsPaneView.swift`) — the real view: thermal + pressure chips, a 5-tile metrics grid (CPU aggregate, memory used, compressed, CPU temperature, fan), per-core bars, a segmented memory bar with legend, a load-average row, and a sortable, virtualized (`List`) full process table with a "Copy PID"/"Reveal in Finder" context menu.
- **Wiring**: `PaneRuntime` (`PaneRuntime.swift`) gained `content: (any PaneContentLifecycle)?`, constructed for `.systemMetrics` panes and `setUp`-called at `init`. `WindowRuntime.hidePane`/`showPane`/`closePane` (`WindowRuntime.swift`) each gained one `pane.content?.setVisible(...)`/`.tearDown()` call, unconditional on kind (a `nil` content is a no-op) — this is the general, kind-agnostic wiring `docs/pane-view-lifecycle.md` §5 left as "phase 2's wiring question, shared across every non-terminal kind," done once here rather than per-kind. `PaneView.nonTerminalBody` (`PaneView.swift`) now casts `pane.content as? SystemMetricsPaneContent` and renders `SystemMetricsPaneView`, falling back to the placeholder for every other (still-unapproved) kind.

### What was deliberately not built (design deviations, honestly scoped)

- **"Watch in Process Status" row action (§7 item 7)** — not built. It depends on a pid-targeting parameter on a `process-status` pane that doesn't exist yet (`#0305` hasn't landed its own pane-creation shape). Building it now would mean guessing at an interface another in-flight issue owns. "Copy PID" and "Reveal Executable in Finder" (§7 item 8) are built.
- **SMC key resolution is a best-effort candidate list** (`Tp09`/`Tp0T`/`Tp01`/`Tp05`/`TC0P` for temperature), not a per-model table or a runtime discovery pass — the design's own §1.4 names both as real, unresolved future work, not required for this round.

- **`showPane`'s asymmetry, carried forward as designed, not fixed here**: unlike the terminal path (which relies on a placeholder remount to re-report visibility), `showPane` now explicitly calls `pane.content?.setVisible(true)` — the design (§6) left this as an open wiring choice between "explicit call" and "remount," and an explicit call was chosen as the only option available to a conformer that isn't torn down/rebuilt by SwiftUI churn.

### Review round 1 (2026-08-21) — request changes, addressed

Reviewer confirmed the build/tests independently (BUILD SUCCEEDED, 1103 in 128 suites), mutation-tested the discard-on-hide claim (held), and confirmed the SMC protocol, per-tick open/close, never-RSS compliance, and terminal-path isolation. Three blocking findings, three cheap ones, plus two scope-increase messages that arrived mid-round (a sibling issue's reviewer found two more teardown gaps shared across all four non-terminal kinds; #0305's reviewer found a process-enumeration bug in this issue's own shared reader). All addressed in this round; none deferred.

**1. Teardown wired to `closePane` only — `removeSession`/`closeTab` bypassed it, and (found in the same round by a sibling review) so did `windowWillClose`/`applicationWillTerminate`.** `docs/pane-view-lifecycle.md`'s own "closePane is the single choke point" claim was false in this tree. Fixed by funnelling all five pane-removal paths (`closePane`, `removeSession`, `closeTab`'s pane-removal branch, `RootWindowView.windowWillClose`, `BattyAppDelegate.applicationWillTerminate`) through one `WindowRuntime` helper (`tearDownNonTerminalContent(in:)` / the public `tearDownAllPaneContent()`), idempotent per pane. The doc's false claim is corrected in the same commit, not left standing for the next non-terminal kind to inherit.

**Reconciled construction shape, decided across all three in-flight non-terminal-view branches:** `PaneRuntime.content: (any PaneContentLifecycle)?` (this issue's own name/type) plus a new `PaneRuntime.makeContent(for:)` — an exhaustive, no-`default:` switch, so a future `PaneContentKind` case is a compile error here rather than a silently-`nil` gap — and an injectable `contentFactory` parameter on `PaneRuntime.init` so test code can supply an inert conformer instead of triggering a real one's real background work (a live sampling `Task`, in this kind's case) as a side effect of construction. `setUp` still runs synchronously inside `init`, unchanged.

**2. The CPU tile fabricated `0.0%`/`0 cores` on every pane-creation and every hide→show tick.** `CoreCPUDeltaTracker`'s correct "no baseline yet" `nil` was laundered into a plausible-looking `0` by `SystemMetricsSampler`, read as a real measurement on a busy machine. Fixed: `CPUReading.aggregatePercent`/`perCorePercent` are `Double?`/`[Double]?`; the view renders "—"; `coreCount` is tracked separately from the raw tick read so the "N cores" sub-label stays correct on the same no-baseline tick. Pinned by a new test asserting the first `sampleOnce()` has a nil aggregate and the second a real one.

**3. `UInt32(integer_t)` traps past `Int32.max`.** `processor_info_array_t` is signed `Int32`; a plain `UInt32(_:)` init traps once a tick counter's bit pattern reads negative (~250 days uptime at the reviewer's measured tick rate). Fixed with `UInt32(bitPattern:)`.

**Cheap fixes taken in the same round:** `mach_host_self()`'s owned send right was never deallocated in `SystemCPUReader`/`SystemMemoryReader` (verified leaking the port refcount 2 → 1002 over 1000 calls) — now deallocated. `SMCThermalReader.readFloat` accepted any key reporting `dataSize == 4` with no check that the SMC driver had actually typed it as a float — now gated on `dataType == "flt "`/`"ui8 "` plus a shared sanity range. `SystemMemoryReader.current()` now checks `hw.memsize`'s sysctl return code (a failure previously left `totalBytes` fabricated at `0`). `SystemMetricsPaneView` gates its whole dashboard on `snapshot.sampledAt != nil` — the field whose entire job is distinguishing "no sample yet" from "sampled" was never read by the view, so `.empty` rendered a full, plausible-looking dashboard of zeros under a green "Thermal: Nominal" chip before the first real sample ever landed.

**Escalated finding — process list ~12x undercount.** `ProcessMetricsReader.listAllPIDs()` divided `proc_listallpids`'s filled-buffer return by `MemoryLayout<pid_t>.size`, treating a pid *count* as a byte count — silently enumerating roughly 1/12th of the machine's real process count (62 of 716, independently reproduced by #0305's reviewer running this exact code, and again here before writing the fix: 181 vs. the corrected 727). Fixed by adopting #0305's own `allPids()` shape (per the reviewer's cross-branch comparison), except pid 0 is kept, not filtered, since `sample(pid:)`'s hardcoded `"kernel_task"` fallback depends on it. Pinned by a regression test that cross-checks against a second, independent `proc_listallpids` call built directly in the test.

**Shared-infrastructure doc updates for #0305**: `ProcessCPUDeltaTracker`/`MachTimebase`'s doc comments now name #0305 as an adopting client — that issue's own CPU% math had treated mach-absolute-time ticks as nanoseconds directly, under-reporting a single-core-pegging process by ~42x, and adopts this shared, correct conversion instead.

Not disputed: every finding held up under independent re-verification on this machine before the corresponding fix was written (the pid-count bug reproduced a ~4x-worse undercount than the buggy code's own first-run numbers, and the negative-tick trap reproduced directly via `UInt32(Int32(-1))`).
