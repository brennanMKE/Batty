## Description

The Open Project picker, File ▸ Open Project ›, the Command Palette's "Open Project: <name>" rows and `batty project list` all list Projects in **store order**: the order of `projects.json`, which is the order the user arranges in the Project Editor's list. Nothing records when a Project is used. `Project.lastOpenedAt` exists, round-trips and is preserved by the editor's Save, but no code path ever sets it (#0472 Gotchas: "`openProject` does not update `lastOpenedAt`"). So a user with a dozen Projects scans the same grid every time, and the picker has no basis for a "most used" tier.

The user's direction (2026-10-12): "For listing projects we can use LRU logic which adjusts for which projects are already opened. I would show a top row with bigger cards for the most used projects followed by smaller cards. When we get to that point we can work with proposed designs in a web page to decide details."

This issue has two parts:

1. **A shared recency model**, used by the picker, the File menu submenu, the palette rows, the CLI list, and #0491's Open Quickly Project rows. One stored field, one write site, one pure ranking function.
2. **A two-tier picker layout** (a top row of larger cards, then smaller cards), **gated on a visual design the user approves first**, in the same way the Projects canvas was reviewed (#0469).

Ships on `main` for 1.3.0, behind the Projects flag. With the flag off nothing here exists and nothing reads or writes Project usage data.

## Expected behavior

### 1. The shared recency model

**What is recorded, when, where.**

- **Field:** the existing `Project.lastOpenedAt: Date?`. No new file and no new field. It is already in `projects.json`, already optional on disk, already preserved by the editor's Save and already round-trip tested. A missing value means **never opened**. No `ProjectsFile.version` bump: older Beta builds already decode and preserve the key (#0471 ignores unknown fields, and this one is known).
- **Why not a separate file:** a usage sidecar (say `project-usage.json`) would need its own load, save, backup-on-corruption, per-variant path and flag gate, and an id join on every list. `projects.json` is written only on explicit user actions today (Save, Save as Project, trust approval); opening a Project is an explicit user action, so recording the open there keeps that rule. Update the `Concepts.md` Project "Storage" bullet (`:48`) to say the last-opened time is written when the Project is opened, and bump the version line (`:285`).
- **Write site: exactly one.** `AppStateStore.openProject(id:mode:contentFactory:fromCli:)`, after the open has succeeded, on both return paths: the create path (`wasCreated: true`) and the focus-existing path (`wasCreated: false`). It calls a new `ProjectStore.recordOpen(id:at:)` that sets `lastOpenedAt` on that Project and saves through `commit`. Not in `requestOpenProject` (the trust sheet's cancel path must not count, and `finishOpen` already funnels into `openProject`), and not in `finishOpen` (the UI-test driver bypasses it). A failed open (`.featureDisabled`, `.unknownProject`, `.noWindow`, a tree-build throw) records nothing.
- **A failed usage write never fails the open.** Follow `finishOpen`'s approval-hash pattern: log the error and return the `ProjectOpenResult` anyway. The Session exists; a stale timestamp is the lesser harm.
- **Clock:** `AppStateStore` gains `@ObservationIgnored var projectUsageClock: () -> Date = Date.init`, a settable seam with a production default like `startupReadinessClock` (`AppStateStore.swift:114`), using `SessionNameCache`'s closure shape rather than `SchedulingClock` (nothing sleeps here). Production never sets it; tests assign a closure returning fixed `Date(timeIntervalSince1970:)` values.
- **Editor interaction.** `ProjectEditorViewModel.save()` already copies the stored `lastOpenedAt` (`:716`), so opening a Project while its editor is open neither loses the new date on the next Save nor dirties the draft (`isDirty` compares the draft against its baseline, `:174-177`, and the draft is not rewritten by the store). Add a test for the second half; the first is `saveKeepsTheApprovalAndOpenDateWrittenAfterTheEditorLoaded`.

**What counts as a use: every successful open from any entry point, including focusing an already-open Project.**

- "Any entry point" is automatic because the write site is `openProject`: picker (Return and Option-Return), File ▸ Open Project ▸ <name>, the palette rows, Save & Open from the editor, `batty project open`, the Sidebar button (#0490), Open Quickly (#0491), and the UI-test driver.
- **Focusing counts.** The user asked for *least-recently-used*, not least-recently-created. Choosing a Project in the picker, the menu, the palette or the CLI is the same gesture whether Batty then creates a Session or switches to one, and the user does not know which it will be. If focusing did not count, a Project kept open all day and switched to twenty times would sink below one opened once this morning, which is the opposite of "most used". It also keeps the CLI honest: `batty project open X` from an agent is a use of X.
- **What does not count:** selecting a Project-backed Session in the Sidebar, with Cmd-1…9, or through Open Quickly's existing Session › Tab rows. Those are Session actions, they do not go through `openProject`, and writing `projects.json` from the selection flow would put a file write inside the focus/selection path that `docs/swiftui-observation-rules.md` keeps event-only. Saving or editing a Project is not a use either.

**Ordering: most recently used first.**

1. Projects with a `lastOpenedAt`, descending by that date.
2. Then Projects never opened (`lastOpenedAt == nil`), in **store order**, which is the order the user arranged in the Project Editor. A fresh install therefore lists exactly as today until the first open.
3. **Tie-break** for equal dates (possible for seeded or hand-edited files; real writes carry fractional seconds): store order. Implement the tie-break with an explicit enumerated offset, as `ProjectPickerModel.filtered` does (`:185`), not by relying on `sorted` being stable.

**Adjusting for already-open Projects.** The function takes `openProjectIDs` and a placement:

| Placement | Behavior | For | Against |
|---|---|---|---|
| `.last` (open Projects sink) | Open Projects move below every closed one, keeping recency order among themselves; they keep the OPEN badge / check mark / `open` marker. | The picker's job is to open something. A Project the user just opened is by definition the most recent, so with no adjustment the top row of larger cards would fill with Projects that are already open, which is the one thing the user does not need from it. Switching among open Sessions already has the Sidebar, Cmd-1…9 and Open Quickly. | The list visibly reorders when a Session opens or closes; a Project the user wants to "open another copy" of (Option-Return) is at the bottom. |
| `.inPlace` (no adjustment) | Pure recency; the OPEN badge is the only signal. | Stable; simplest to explain. | The top tier shows what is already open. |
| `.first` (open Projects rise) | Open Projects first, then the rest by recency. | A quick switcher. | Duplicates the Sidebar; the picker's hint already says "Switch to the open …". |

**Recommendation: `.last`, the same placement on every surface**, so the picker, the File menu, the palette rows, the CLI table and Open Quickly agree. The final call is the design review's (open question 1 below); the placement is a parameter so flipping it is a one-line change, and the surfaces must not each pick their own.

**The pure function.** New `Model/ProjectRecency.swift`:

```swift
enum ProjectRecency {
    enum OpenPlacement: Sendable { case last, inPlace, first }
    static let defaultPlacement: OpenPlacement = .last   // the review may change it

    /// `projects` in the order the user arranged them; returns them in
    /// the order every Projects list shows them.
    static func ranked(
        _ projects: [Project],
        openProjectIDs: Set<UUID>,
        placement: OpenPlacement = defaultPlacement
    ) -> [Project]
}
```

- No I/O, no clock, no `AppStateStore`. It ranks stored dates, so it needs no notion of "now"; tests build fixtures with explicit `Date(timeIntervalSince1970:)` values. The injected clock belongs to the **recording** seam above. If the chosen design shows a relative time on cards ("Opened 2 h ago"), that formatter takes an explicit `now: Date` parameter and is tested the same way; do not put `Date()` inside either.
- It is the **only** sorter. Every surface below calls it; none sorts by date on its own.

### 2. Surfaces that consume it

- **Picker.** `ProjectPickerModel` applies `ProjectRecency.ranked` to the Projects it is given, in `init` and in `refreshed(projects:openProjectIDs:)`, so the live refresh the view does on every render (`ProjectPickerView.swift:42-45`) re-ranks when a Session opens or closes. The filter's tie-break (`:185`) becomes "ranked order" instead of store order. The initial selection is the first ranked card. Rename and update the two store-order tests.
- **File ▸ Open Project ›.** `ProjectFileMenuModel.make` ranks before mapping. The check mark stays. Update `listsProjectsInStoreOrderThenDividerChooseAndNew`.
- **Command Palette.** `allCommands` loops the ranked list, so with an empty query the rows come out most-recent-first; a typed query still re-sorts by fuzzy score as today. Extend `ProjectPaletteEntryTests.flagOnListsOneEntryPerProjectAndThePicker` with fixtures whose store order differs from the recency order.
- **CLI.** `projectListReplyForXPC` ranks, so `batty project list` prints most-recent-first and its help text ("in the order Batty lists them") stays true. `ProjectListEntry` and the `--json` shape are unchanged; the timestamp is not exported. No CLI docs claim store order (`git grep -n order` over `.claude/skills/batty-cli/SKILL.md`, `docs/batty-cli-*.md` finds nothing about Projects), so none change.
- **Open Quickly (#0491).** Calls the same function; owns its own row shape and whether an open Project's row is shown at all next to its Session rows.
- **Project Editor list: unchanged.** It stays in store order with drag and Move Up / Down, because it is where the user *authors* that order, and a list that re-sorts itself under a drag would fight the drag. Say so in `docs/ui-features.md`.
- **UI-test seeding.** `ProjectFixture.project(...)` gains `lastOpenedAt: String? = nil`, emitted as the ISO 8601 string the driver already decodes.

### 3. Picker layout: a top row of larger cards (design-gated)

What is fixed by the user's direction:

- A **top row of larger cards** for the Projects ranked first, followed by **smaller cards** for the rest, in the same order. Both tiers come from one `ProjectRecency.ranked` list split at a count; there is no second ranking.
- Both tiers keep today's card content (thumbnail, color dot, name, OPEN badge, path, summary); the larger cards may show more (a bigger thumbnail, a relative "Opened …" time) and the smaller cards less.
- Cards keep `project-picker.card.<name>` and the OPEN badge keeps `project-picker.open-badge.<name>`, so `ProjectsOpenTests` keeps passing; each tier's container gets its own identifier (proposed `project-picker.featured` and `project-picker.rest`), documented in `docs/ui-features.md`.
- Selection moves across both tiers with the arrow keys; Return, Option-Return, ⌘E, ⌘N, Escape, click and double-click behave as today.
- The cursor math becomes a **pure type** (for example `ProjectPickerGrid`, replacing `columnCount` and the `index ± columns` arithmetic in `move`), modeled on `SessionColorGridCursor` (`Views/SessionColorPickerView.swift:13-78`). It knows each tier's column count and maps up/down between tiers to the nearest column, clamped, no wrapping, with the short-last-row rule kept.

What the design review decides (open questions 2–7 below): how many cards the top row holds, the two card sizes, breakpoints (the sheet is a fixed `720 × 520` today; the design may widen it or make it resizable), how filtering interacts with the tiers, keyboard navigation details, where the empty state and the New Project… affordance go, and what happens when there are fewer Projects than the top row holds.

**The gate (binding).**

1. **Implementation of this section does not start until the user approves a visual design.** The orchestrator, not the implementer, prepares the proposals: a web page (artifact) with several options, in the same form as the Projects canvas the user reviewed for #0469 (https://claude.ai/artifact/WoKFESyWFnQFkM64TF2P5o). Each option shows the two-tier grid at the sheet's size with realistic Projects (long names, `~` paths, an OPEN badge in each tier), the filtered state, the empty state, and the keyboard focus ring; the page states the placement policy it assumes (§1) so the review decides it too.
2. The chosen option is **recorded in this issue before any code is written**: a `## Chosen design` section with the artifact link, the option name, the answers to open questions 1–7, and the artboards copied into `issues/0492/` as #0469 did. An implementer dispatched without that section bails per `issues/Issues.md` "When the implementer can't finish" and says so.
3. Until the design is chosen, the picker keeps today's uniform 3-column grid; §1 changes only its order.

### 4. Flag off

With `featureFlags.projects == false` nothing here exists and nothing reads or writes Project usage data:

- `openProject` throws `.featureDisabled` before reading the store (`AppStateStore.swift:1288-1291`), so `recordOpen` is never reached and `lastOpenedAt` is never written. The usage clock is a plain closure that is never called.
- `ProjectRecency.ranked` has no I/O and is called only from sites that are already gated: `ProjectPickerModel` (built only by the picker, which never presents), `ProjectFileMenuModel.make` (returns nil), `CommandPaletteView.allCommands` (inside `if store.featureFlags.projects`), `projectListReplyForXPC` (returns nil).
- `projects.json` is never opened, read or created, as #0471 guarantees.

## Acceptance criteria

**Unit tests** (`./build.sh unit`, all visible in the output, none waiting on time, per `AGENTS.md` "Asynchronous tests"):

- **Ranking** (`ProjectRecencyTests`), every fixture with store order that differs from the recency order so no assertion is vacuous:
  - store order `[A, B, C]`, dates `C > A`, `B` nil → `[C, A, B]`;
  - never-opened Projects keep store order among themselves: `[A, B, C]` all nil → `[A, B, C]`, and `[A, B, C]` with only `B` opened → `[B, A, C]`;
  - equal dates keep store order: `A` and `C` share a date, `B` is later → `[B, A, C]`;
  - `.last`: `[A, B, C]` with `C > B > A` and `C` open → `[B, A, C]`; two open Projects keep recency order among themselves;
  - `.inPlace` leaves `[C, B, A]`; `.first` gives `[C, B, A]` when `C` is open and `[A, C, B]` when `A` is open;
  - an id in `openProjectIDs` that matches no Project is ignored;
  - the result is a permutation: same count, same ids.
- **Recording** (`ProjectOpenTests` pattern, `contentFactory: { _ in nil }`, a temp `fileURL`, the usage clock injected):
  - `openProject` with `.openNew` writes `lastOpenedAt == clock()` to the store and to disk (reload through a fresh `ProjectStore`); a second open with a later clock value overwrites it;
  - `.focusExistingOrOpen` on an already-open Project returns `wasCreated == false` **and** writes the new date;
  - an unknown id, and `.noWindow`, write nothing (the fixture's Project starts with a non-nil `lastOpenedAt`, so "unchanged" is not vacuous);
  - a store write failure (`RecordingFileManager` from `ProjectStoreTests.swift:219`, made to fail the write) leaves the Session created and the result returned;
  - flag off: `openProject` throws `.featureDisabled`, `projectStoreIsConstructed` is false, the clock closure was never called (count its calls);
  - the editor: a dirty draft stays dirty with the same `isDirty` value, and a clean draft stays clean, after `openProject` writes a new date for the Project it is editing.
- **Decode, back-compatible** (`ProjectTests` pattern):
  - a `projects.json` written before this change (no `lastOpenedAt` keys) loads every Project with nil and ranks in store order;
  - `"lastOpenedAt": "yesterday"` decodes to nil, logs, and **keeps the Project** (today it is dropped; this is the leniency fix from "Current code");
  - `"lastOpenedAt": 7` (not a string) decodes to nil and keeps the Project;
  - the existing fractional and whole-second tests still pass, and a written date reloads equal through `ProjectsFile.encoder` / `decoder`.
- **Surfaces:** the picker, File-menu, palette and XPC-list tests above, each with a fixture whose store order differs from the ranked order and with one open Project, asserting the ranked order and that the badge / check / `isOpen` still marks the open one.
- **Two-tier cursor** (after the design is chosen): the pure grid type is tested for every arrow from every cell on a fixture with a full top row, a partial last row, and a single-tier case (fewer Projects than the top row holds).

**VM UI tests**, only through `tools/run-ui-tests-vm.sh` / `./build.sh ui`, never on the host, in the #0478 style (`ProjectsUITestCase`, `ProjectsHarness`), **after the design is chosen**:

- Seed three Projects with `lastOpenedAt` values whose order differs from the seed order; present the picker; the card identifiers under the top-tier container are the most recent ones in order, and the rest follow. Open the first; reopen the picker; with `.last` its card is now in the lower tier and carries `project-picker.open-badge.<name>` (with `.inPlace` it keeps its place; assert whichever the review chose).
- Arrow keys cross from the top tier to the lower tier and back; Return opens the selected card.
- Typing a filter narrows the cards as the review decided (one tier or two), and Escape restores both tiers.
- Flag off (`launchApp(flagOff: true)`): add to `ProjectsFlagOffTests.testFlagOffRemovesEveryProjectsEntryPointAndWritesNothing` that the seeded file's bytes are unchanged after launching, selecting Sessions and quitting, and that no `lastOpenedAt` appears in it.

## Open questions for the design review

The orchestrator's proposal page answers these with options; the chosen answers go into `## Chosen design`.

1. **Placement of open Projects:** `.last` (recommended), `.inPlace`, or `.first`; the same everywhere.
2. **Top-row count and sizes.** How many large cards (3 at today's width, or 4 with a wider sheet), the large and small card sizes, and whether the sheet grows or becomes resizable. Today: `720 × 520`, cards about 221 pt wide, thumbnail 108 pt.
3. **Fewer Projects than the top row.** One tier only, or a padded top row. With one Project, a single large card or today's card?
4. **Filtering.** A typed query collapses to one uniform tier (simplest; the top row is a recency feature, and a filter is a name feature), or keeps the tiers and filters each.
5. **Keyboard.** Up from the lower tier's first row lands on the nearest top-row column; Down from the top row's last column lands where; Home/End.
6. **Empty state and New Project….** The empty state as today (`project-picker.empty`), or a "+ New Project…" card at the end of the lower tier in addition to the ⌘N hint.
7. **Card extras.** A relative time ("Opened 2 h ago") on large cards, on all cards, or none; whether the large thumbnail shows Tab counts per slot.
8. **Frequency.** The ranking is recency only. If the review wants "most used" to mean *most often* (a `frecency` blend), that needs an `openCount` field recorded at the same write site, which starts at zero for every existing Project. Not recommended for the first version; a one-field, back-compatible addition later if recency alone proves wrong.
