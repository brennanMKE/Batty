## Description

Depends on [#0335](0335.md), which gives every Session an automatically
assigned color from a fixed 10-color palette and tints the Sidebar
Session row's `rectangle.split.3x1` SF Symbol with it. That assignment is machine-chosen and
permanent — the user cannot say "this Session is the red one". This issue
adds an explicit per-Session color choice that overrides the automatic
assignment and sticks.

The affordance belongs on the Sidebar Session row's context menu, next to
the existing Rename / Set Session Theme items — this is exactly the
follow-up #0335's Open questions parked ("Should the color be
user-overridable (e.g. a 'Set Color' context-menu item next to Rename)").
`Concepts.md` → Session → Identity already anticipates a user-editable
color; #0335 builds the automatic half, this issue builds the editable half.

## Resolution notes

> 🟢 Resolved 2026-08-20 — a Session's color can now be pinned by the
> user from a keyboard-operable swatch picker on the Sidebar row's
> context menu, overriding [#0335](0335.md)'s automatic assignment.

Everything visual is unverified — rendering, VoiceOver, and real
keyboard focus cannot be reached headlessly. That sign-off is the
user's, which is why this is `resolved` and not `closed`; the checklist
is in Gotchas below.

A chosen color does **not** survive relaunch. That is by design per this
issue's Persistence section, not a defect to report later.

## Root cause

Not a defect — the editable half of a feature. #0335 shipped automatic
per-Session colors with no way for the user to say "this Session is the
red one", which #0335's Open questions had parked for this issue.

## Fix

`SessionRuntime` gained `colorOverride: Bool` beside `colorIndex`,
mirroring the `titleOverride` (#0089) precedent this issue named. That
shape was chosen over a layered `explicitColorIndex: Int?` because
`colorIndex` is already the single resolved value every read site uses,
so the assigner needed **no changes at all** — `nextColorIndex()` tallies
`colorIndex` regardless of provenance, and explicit picks therefore count
toward the in-use tally for free.

`WindowRuntime` gained `setSessionColor(id:to:)` (validates the index,
inequality-guarded, sets both fields) and `resetSessionColor(id:)`
(clears the override only, leaving `colorIndex` untouched so the color
does not visibly jump on reset). `SessionColorPickerView` is a 260pt
swatch-grid sheet presented from `SessionSidebarView` keyed by
`@State coloringSessionID`, following the established
`renamingSessionID` / `themingSessionID` shape. Grid navigation lives in
`SessionColorGridCursor`, a pure `Equatable, Sendable` value type using
a clamp policy at the edges.

Five open questions were settled: reset keeps the current index rather
than re-deriving; Duplicate Session still always gets a fresh automatic
color and is never born pinned; the swatch grid shipped rather than the
submenu alternative; Command Palette access and cross-relaunch
persistence are both out of scope.

Reviewed by `claude-opus-5` across three rounds (the workflow pins
reviewers to `claude-opus-4-8`; the model actually used is recorded
here). A fresh reviewer each round.

Round 1 requested changes on two picker defects: the swatch grid
rendered with **no ring at all** for an automatically-colored Session
(the common case), because "which color the Session has" and "where the

the cursor math into a testable type, making swatches real `Button`s,

Rounds 1 and 2 each verified and upheld the runtime side independently:
`nextColorIndex()` byte-for-byte unchanged, and stickiness holding
structurally because `colorIndex` is written in exactly three places,
none reachable from `removeSession`, `moveSessions`, `renameSession`, or
any theme path.

## Relation

- Depends on: [#0335](0335.md) — automatic per-Session colors in the
  Sidebar, shown by tinting the Session row's SF Symbol. #0335 defines the 10-color palette, the palette order, the
  storage location on `SessionRuntime`, and the least-used round-robin
  assigner this issue must interoperate with. Do not restate or redefine
  any of those here; nothing in this issue should land before #0335 does.

## Expected behavior

- Right-clicking a Session row in the Sidebar offers a color affordance
  (proposed: `Set Color…`, placed in the same group as `Rename`).
- The user can pick any of the 10 palette colors from #0335 for that
  Session. The picker shows which color the Session currently has, whether
  that color came from the automatic assigner or a previous explicit
  choice.
- The picker also offers a way to return the Session to automatic
  assignment (proposed: an "Automatic" entry in the same picker, plus a
  `Reset Color` context-menu item shown only while an explicit color is
  set — mirroring the existing `Reset Name` and `Clear Session Theme`
  items, both of which appear conditionally).
- **The explicit choice is sticky.** Once set, no later automatic
  assignment may reclaim, reassign, or shift that Session's color — not
  when other Sessions are created or closed, not on reorder, not on
  Duplicate Session, not on theme change. Only the user changes it again,
  or resets it to automatic.
- **Duplicates are allowed when the user asks for them.** The picker must
  not disable, hide, or warn about a color another Session already uses.
  Two Sessions both explicitly set to Blue is a legal state.
- **The automatic assigner still avoids collisions.** #0335's least-used
  round-robin counts live Sessions per palette index; explicitly chosen
  colors count as in use in that tally, so a newly created Session prefers
  an index no Session holds — automatically or explicitly — before
  repeating one.

## Actual behavior

Nothing exists yet: with #0335 alone, a Session's color is whatever the
assigner picked at creation and there is no user-facing control for it.
The Session row context menu (`SessionRow` in
`BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift`) currently
offers only Rename, Reset Name, Set Session Theme…, Clear Session Theme,
Mute/Unmute Notifications, and Close.

## Where this attaches in the code

Everything named here was read, not assumed:

- **Context menu** — `private struct SessionRow` in
  `BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift` owns the
  `.contextMenu { … }` block. The new item goes here.
- **Sheet-presentation pattern to copy** — the Session Theme item is the
  closest precedent and should be followed literally: `SessionRow` takes an
  `onTheme: () -> Void` closure; the parent `SessionSidebarView` holds
  `@State private var themingSessionID: UUID?`, derives a
  `themingBinding: Binding<SessionRuntime?>` from it, and presents
  `.sheet(item: themingBinding) { session in SessionThemeSelectorView(…) }`.
  `Rename` uses the same shape (`onRename` → `renamingSessionID` →
  `.sheet(item: renamingBinding)` → `RenameSessionSheet`). A color picker
  should add `onSetColor` → `coloringSessionID` → a third `.sheet(item:)`.
- **Mutation routing** — two patterns coexist in that menu and both are
  legitimate. Actions with side effects beyond the Session object route
  through `WindowRuntime` (`windowRuntime.renameSession(id:to:)`,
  `windowRuntime.clearSessionName(id:)`,
  `windowRuntime.removeSession(id:)`, in
  `BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift`), which
  `AppStateStore` mirrors with shims that locate the owning window via
  `windowOwning(sessionID:)`. Purely Session-local toggles write the
  `SessionRuntime` property directly from the menu action
  (`session.notificationsMuted.toggle()`, `session.localThemeName = nil`).
  Because the automatic assigner is Window-scoped (#0335 counts live
  Sessions in the Window), a `WindowRuntime.setSessionColor(id:to:)` /
  `resetSessionColor(id:)` pair is the better fit — it keeps the assigner's
  bookkeeping and the override in one place and is unit-testable without a
  view.
- **Storage** — `SessionRuntime`
  (`BattyKit/Sources/BattyKit/Runtime/SessionRuntime.swift`) is the
  `@Observable` class holding per-Session UI state (`title`,
  `titleOverride`, `localThemeName`, `isPaneListExpanded`,
  `notificationsMuted`). #0335 proposes storing the automatic assignment
  there as `let colorIndex: Int`. That `let` must become writable, or gain
  a companion — the automatic-vs-explicit distinction has to be
  representable, since the assigner's collision math and the "Reset Color"
  affordance both need to know which Sessions are pinned. `SessionRuntime`
  already has the exact precedent: `titleOverride: Bool` marks a
  user-pinned title so auto-derivation paths skip the rewrite (#0089). A
  `colorOverride: Bool` beside `colorIndex`, or a single
  `explicitColorIndex: Int?` layered over the automatic index, expresses
  the same idea; the implementer should pick one with #0335's shipped shape
  in hand.
- **Palette source of truth** — the 10 colors, their order, their names,
  and their hex values are defined by #0335. This issue adds no colors and
  changes no hues; the picker renders whatever type #0335 introduces.

## Picker UI

A compact swatch grid, not a list — the content is 10 colors and one
"Automatic" entry, which fits a small panel with no search field. The
existing `SessionThemeSelectorView` (620×500, search field, scrolling
grid) is the wrong scale to copy verbatim; copy its *presentation* pattern
and its keyboard handling, not its dimensions.

- Grid of 10 filled swatches (proposed 5×2), each showing its palette color.
- The Session's current color is visibly selected (ring/checkmark), and the
  UI distinguishes "Blue, automatically assigned" from "Blue, chosen by
  you" — otherwise Reset Color looks like a no-op.
- An "Automatic" entry returns the Session to assigner control. When
  chosen, the Session re-enters the automatic pool; whether it keeps its
  current index or is re-derived immediately is an open question below.
- Keyboard navigable: arrow keys move the selection across the grid, Return
  commits, Escape cancels. `SessionThemeSelectorView` does this with
  `.onKeyPress(.upArrow/.downArrow/.return/.escape)` and a
  `selectedIndex` — the same approach works for a 2-D grid with left/right
  added.

## Accessibility

- Every swatch needs an accessible name — the color names from #0335's
  palette (Blue, Orange, Green, Pink, Teal, Red, Violet, Amber, Cyan,
  Brown), not "Color 1". Color alone is not an accessible label, and
  red/green swatches are indistinguishable to a chunk of users; the name is
  the only thing that disambiguates them.
- The selected swatch must expose its selected state to VoiceOver
  (`.accessibilityAddTraits(.isSelected)`), not just draw a ring.
- The picker must be operable without a pointer end-to-end: open from the
  context menu, move with arrows, commit with Return, dismiss with Escape.
- User-facing strings (`Set Color…`, `Reset Color`, `Automatic`, the
  color names) go through `String(localized:)` like the rest of the menu —
  the catalog is `Batty/Localizable.xcstrings`.

## Persistence

**A user-chosen Session color will not survive app relaunch.** This is a
known limitation of this issue, not an oversight to design around.

- `Concepts.md` → Session says "Persisted: nothing" — the ordered Session
  list, each Session's Split tree, and everything in it are in-memory only.
  Workspace persistence (`workspace.json`) was built and then removed in
  #0172; nothing serializes Session state today.
- `SessionRuntime`'s comparable fields say so explicitly in code:
  `localThemeName` is documented "Not persisted — resets to nil on every
  launch", `isPaneListExpanded` likewise.
- The one thing that *does* persist across launches is the Session **name**
  cache — `~/Library/Application Support/Batty/session-name-cache.json`,
  keyed by working directory (`SessionNameCache`). A color cache keyed the
  same way is a plausible future mechanism, but it is a separate design
  decision and is out of scope here (see Open questions).

So: choose Blue, quit, relaunch — the Session comes back with whatever the
automatic assigner gives it. State that plainly in the implementation's
Gotchas too, so it isn't reported as a bug later.

## Acceptance criteria

- The Sidebar Session row context menu offers a color affordance that opens
  a swatch picker for that Session.
- Picking a color retints that Session's row symbol in the Sidebar
  immediately.
- The chosen color survives: creating new Sessions, closing other Sessions,
  reordering the Sidebar, renaming, collapsing/expanding the Sidebar, and
  switching themes.
- Two Sessions can hold the same explicit color; the picker never blocks or
  warns about it.
- With one Session explicitly set to palette index N, a newly created
  Session prefers an index no live Session holds before reusing N.
- Resetting a Session to automatic returns it to assigner control and the
  Reset affordance disappears.
- Every swatch has an accessible name matching its palette color name, and
  the picker is fully keyboard-operable.
- `scripts/build.sh unit` passes, with unit tests covering: explicit color
  survives subsequent automatic assignments; explicit colors count toward
  the assigner's in-use tally; reset returns the Session to automatic.

## Open questions

- On "Automatic", should the Session keep the index it currently shows, or
  be re-derived immediately from the least-used rule (which may visibly
  change its symbol color the instant the user resets it)?
- Should Duplicate Session copy the source's explicit color, or always get
  a fresh automatic one? #0335 specifies a duplicate gets a fresh color;
  an explicit choice arguably reads as part of the Session's identity the
  user is duplicating. (Note: Duplicate Session is currently reachable only
  from the Command Palette — `extra:duplicateSession` in
  `BattyKit/Sources/BattyKit/Views/CommandPaletteView.swift` — not from the
  Sidebar context menu, despite what `Concepts.md` → Session's "Sidebar
  affordances" line says.)
- Should the chosen color persist across relaunch via a CWD-keyed cache
  like `SessionNameCache`, or wait for general Session persistence to
  return? Filing that as its own issue if wanted.
- Should the color picker also be reachable from the Command Palette (a
  "Set Session Color" command acting on the selected Session), or is the
  context menu enough for v1?
- Is a submenu of 10 named color items an acceptable simpler alternative to
  a swatch-grid sheet? It is keyboard-navigable and accessible for free,
  but shows no color preview at rest.

## Gotchas

- **The write itself is safe; where it is written from is the risk.**
  Per `docs/swiftui-observation-rules.md`, a menu-action write to
  `@Observable` state is an event-origin write with an explicit owner and
  trigger — exactly the sanctioned category, the same as the existing
  `session.notificationsMuted.toggle()`. What is forbidden is computing or
  normalizing the color anywhere in view construction: `SessionRow.body`,
  the swatch view's `body`/`init`, a computed helper `body` calls, or a
  `ViewModifier.body` must only *read* the stored color. #0335 already
  states this for the automatic case; the override must not smuggle a
  "resolve effective color" write back into `body`.
- **Do not fix a mutate-during-update violation with a `Task` hop.** If
  the picker's commit path ever trips "Modifying state during view update",
  restructure which code owns the write — deferring it into a `Task`
  trades a crash for a race (the #0229 click regression, documented in the
  observation-rules case study).
- **`@Observable` notifies on every write, equal values included.** Picking
  the color a Session already has still invalidates every dependent view.
  Follow `WindowRuntime.setSelectedSession(id:)`'s pattern and guard the
  assignment with an inequality check.
- **Dependency granularity.** Pass the resolved color (or its index) down
  into the swatch/row views rather than handing them the whole
  `SessionRuntime`; a child that reads unrelated `SessionRuntime`
  properties re-evaluates on every title, bell-count, and theme write.
- **Sheet presentation from a context menu.** The existing pattern presents
  the sheet from `SessionSidebarView`, keyed by a `@State` session id — not
  from inside `SessionRow`'s `.contextMenu`. Attaching a `.sheet` to a
  context-menu button's own view is unreliable on macOS because the menu's
  host view goes away when the menu dismisses; follow the established
  `renamingSessionID` / `themingSessionID` shape.
- **Row rendering constraint carries over from #0335.** The color lives
  on the `rectangle.split.3x1` symbol, which is already row *content* —
  the `Label` icon inside the `HStack` — so no new layer is introduced
  and `SidebarRowBackground`'s custom row-background painting (#0135)
  stays untouched. The adjacent risk is selection state:
  `List(.sidebar)` selection tinting may recolor or vibrancy-blend the
  row's foreground when the row is selected, so a user-chosen color must
  be verified on the **selected** row too. Nothing in this issue should
  change the background layering.

- **A chosen color does not survive relaunch.** `SessionRuntime` is
  in-memory only, like `localThemeName` and `isPaneListExpanded`. By
  design per this issue's Persistence section — not a bug.
- **Nothing visual was verified.** The app was never launched. Before
  this moves to `closed`, check: the ring is visible the instant the
  sheet opens, including for a Session that was never explicitly
  coloured (this was round 1's defect); swatches show no default button
  chrome after the `Button` migration, in light and dark; keyboard
  end-to-end with no pointer (arrows preserve the column, Down from the
  bottom row reaches Automatic, Up from Automatic lands on index 5,
  Return commits, Escape cancels); VoiceOver announces each swatch by
  colour name and the current one as selected; a chosen colour is
  legible on the **selected** Sidebar row, where `List(.sidebar)`
  selection tinting is still live in the unthemed case (carried over
  from #0335 / #0135); stickiness across create, close, reorder,
  rename, collapse, and theme switch; and that two Sessions can hold the
  same colour with no warning.
- **`Reset Color` looks like a no-op by design.** It leaves the colour
  unchanged and only re-enters assigner control, so the sole visible
  feedback is the menu item disappearing.
- **`@Test(arguments:)` needs `nonisolated` on its argument table.** The
  argument expression is evaluated outside actor isolation, while the
  package defaults new types to `MainActor` — without it the build fails
  with "Main actor-isolated static property cannot be accessed from
  outside of the actor". A real Swift 6 constraint, not a workaround.
- **A parameterized suite's pass line hides its case count.** xcodebuild's
  formatter rolls all 44 cases into one summary line, so a suite that
  ran zero cases can still read as success. `xcrun xcresulttool get
  test-results tests` enumerates them individually.
