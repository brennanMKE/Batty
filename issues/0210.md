# 0210 — libghostty-spm pin 2694c40 unbuildable: upstream binary asset returns 404

| | |
|---|---|
| **Status** | open |
| **Module** | GhosttyKit / Build |
| **Platform** | macOS |
| **First seen** | 2026-05-22 |

## Description

The project cannot build at the current `libghostty-spm` pin. Swift Package Manager fails graph resolution before any source is compiled because the binary asset referenced by `brennanMKE/libghostty-spm@2694c40` has been removed from the upstream `Lakr233/libghostty-spm` releases page.

Both of these fail identically:

```
xcodebuild -scheme Batty -destination 'platform=macOS' build
scripts/run-ui-tests.sh BattyUITests/...
```

with:

```
failed downloading 'https://github.com/Lakr233/libghostty-spm/releases/download/storage.1.0.1779090382/GhosttyKit.xcframework.zip'
which is required by binary target 'libghostty': badResponseStatusCode(404)
```

This blocks **every** issue that requires building or running tests — including all eight currently open failing-UI-test issues (#0173, #0174, #0175, #0178, #0179, #0180, #0185, #0186). Those issues will all bail at the build step until this is resolved.

## Root cause

`Batty` pins `libghostty-spm` to `brennanMKE/libghostty-spm@2694c40bd1b8f110ad4e6714e0ab7b04ee1f858f` (set in commit `fee517f`, "Update libghostty-spm pin to 2694c40"). The `Package.swift` at that revision declares a `.binaryTarget` whose URL hard-codes:

```
https://github.com/Lakr233/libghostty-spm/releases/download/storage.1.0.1779090382/GhosttyKit.xcframework.zip
```

That release no longer exists on `Lakr233/libghostty-spm`. The currently available storage releases there are `storage.1.1.2`, `storage.1.1.4`, and `storage.1.1.5` — the timestamped `storage.1.0.*` releases appear to have been pruned. The `brennanMKE/libghostty-spm` fork has no releases of its own, so it cannot fall back to a mirrored asset.

SPM does not consult any local cache when the download fails; it errors out during graph resolution. Manually populating `SourcePackages/artifacts/libghostty-spm/libghostty/GhosttyKit.xcframework` in Batty's DerivedData from another working DerivedData folder does **not** unblock the build.

## Steps to reproduce

1. Clean checkout (or any checkout at HEAD as of 2026-05-22).
2. Run `xcodebuild -scheme Batty -destination 'platform=macOS' build`.
3. Observe `badResponseStatusCode(404)` for the binary target download.

## Possible fixes

This needs a user decision — pick one:

- **Republish the asset upstream**: ask Lakr233 to restore `storage.1.0.1779090382` (unlikely to be quick or in our control).
- **Mirror the asset on `brennanMKE/libghostty-spm`**: cut a release on the fork with the same `GhosttyKit.xcframework.zip` (matching the existing checksum `4871c6a2813f54d264250c91230faae30177d230b1e1cdc3b19fd620a8daea63`) and update the fork's `Package.swift` `.binaryTarget` URL to point at the fork's release. Then bump the Batty pin to the new fork revision.
- **Move forward to a current upstream**: rebase `brennanMKE/libghostty-spm` on top of an upstream commit whose `Package.swift` references a live asset (e.g. `storage.1.1.5`), or update the fork's `.binaryTarget` URL + checksum to the `storage.1.1.5` asset directly. Validate the C ABI hasn't shifted in ways that break our `GhosttyKit` bindings.
