## Description

Copy Ghostty's terminfo database and shell-integration scripts into `Batty.app/Contents/Resources/` so libghostty's runtime can find them. Without these resources, shell integration silently degrades (Kytos's writeup flags this as a common gotcha — `batty-getting-started.md` §4).

**Acceptance criteria:**
- After a build, `Batty.app/Contents/Resources/terminfo/78/xterm-ghostty` exists (the sentinel file libghostty looks for).
- `Batty.app/Contents/Resources/ghostty/shell-integration/...` exists with bash/zsh/fish helpers.
- The app can launch a shell and the `$TERM` value resolves cleanly inside that shell (verify by typing `echo $TERM` after M1 is in).

## Notes

- Implement as an Xcode Run Script build phase that copies from the GhosttyKit xcframework (or the Ghostty source tree if Path B). The script must be deterministic and idempotent.
- Add a smoke test or build-time check that the sentinel file is present in the bundle output — silent absence is the failure mode we're protecting against.
- Source: `batty-getting-started.md` §4 step 4 ("Copy Ghostty's resource tree into your app bundle").

### Investigation 2026-05-08 — bailing for now

Inspected the resolved `libghostty-spm` artifacts and source checkout in DerivedData (`SourcePackages/artifacts/libghostty-spm/libghostty/GhosttyKit.xcframework` and `SourcePackages/checkouts/libghostty-spm/`). **The xcframework does not ship terminfo or shell-integration files.** The macOS slice contains only `Headers/ghostty.h`, `Headers/module.modulemap`, and `libghostty.a` — no `terminfo/`, no `ghostty/shell-integration/`, no resource bundles in any platform slice.

The libghostty-spm Sources/ tree has four Swift libraries (`GhosttyKit`, `GhosttyTerminal`, `ShellCraftKit`, `GhosttyTheme`) but none of them carries terminfo or shell-integration scripts. `ShellCraftKit/Definition/SandboxShell.swift` etc. are pure Swift session helpers, not bundled scripts.

There is no automated way to populate `Batty.app/Contents/Resources/terminfo/78/xterm-ghostty` from the current SPM dependency.

#### Implications

- Without bundled terminfo, `$TERM` inside a Batty surface will fall back to whatever libghostty defaults to (likely `xterm-256color`). Shell programs work; some advanced Ghostty features (256-color extensions, kitty keyboard protocol, etc.) may degrade silently.
- Without bundled shell-integration, libghostty's cwd-tracking, prompt-marking, and similar shell-integration-driven features won't work. Drag-drop and basic typing/output still work.

#### What this issue actually needs

To make this issue resolvable as written, terminfo + shell-integration must be sourced from somewhere. Three viable paths:

1. **Vendor from upstream Ghostty source.** Clone `ghostty-org/ghostty`, copy `terminfo/` and `src/shell-integration/` into the Batty repo (or as a sibling submodule), set up a Copy Files build phase to drop them into `Batty.app/Contents/Resources/`. Most work but full feature parity. Pinning to a specific commit avoids drift.
2. **Pull from a Homebrew-installed Ghostty at build time.** If `/Applications/Ghostty.app/Contents/Resources/` exists on the build machine, `cp -R` from there. Brittle and machine-dependent; not appropriate for a release build.
3. **File an upstream request** asking `libghostty-spm` to include the resource directories alongside the xcframework. Cleanest long-term but blocks on someone else.

#### What I'd do next

## Root cause

`libghostty-spm` ships only the `libghostty.a` xcframework — none of the runtime resources libghostty needs to enable shell integration and `xterm-ghostty` terminfo. Without bundling those, `$TERM` falls back to `xterm-256color` and shell-integration features (cwd reporting, command-finished markers) silently degrade.

## Fix

Vendor the resources from upstream Ghostty and copy them into the app bundle at build time via a Run Script phase.

- Resources vendored to `Resources/ghostty-runtime/` at the repo root, with `ATTRIBUTION.md` documenting MIT license retention and the bump procedure (the agent copied from the locally-installed `/Applications/Ghostty.app`'s bundle; future bumps can pull from a Ghostty build matching the libghostty-spm pin). Placing them outside `Batty/` avoids Xcode's filesystem-synchronized group flattening the directory layout.
- `scripts/bundle-ghostty-resources.sh` is the Run Script body. Uses Xcode env vars (`SRCROOT`, `TARGET_BUILD_DIR`, `UNLOCALIZED_RESOURCES_FOLDER_PATH`) with standalone defaults for manual invocation. `cp -f` the single terminfo file; `rsync -a --delete` the shell-integration tree so removed upstream files don't linger. Sentinel check fails the build if the canonical file is missing post-copy.
- `Batty.xcodeproj` gains a `PBXShellScriptBuildPhase` named "Bundle Ghostty Resources" on the Batty target, with `inputPaths` covering the script + vendored tree (so the sandbox grants read access) and `outputPaths` flagging the sentinel terminfo file (so Xcode does dependency analysis on it).
- `ENABLE_USER_SCRIPT_SANDBOXING = NO` set on the Batty target's Debug and Release configs in `project.pbxproj`. The default of YES under Xcode 26 prevents the script from writing into the bundle Resources directory because it has to `mkdir` subdirectories. Pinned per-target rather than via `Build.xcconfig` so the change stays narrowly scoped and doesn't affect tests or other targets.

## Files changed

- `Resources/ghostty-runtime/` (new) — 8 vendored files: terminfo + 5 shell-integration scripts + ATTRIBUTION.md.
- `scripts/bundle-ghostty-resources.sh` (new) — Run Script body.
- `Batty.xcodeproj/project.pbxproj` — new `PBXShellScriptBuildPhase` entry; `ENABLE_USER_SCRIPT_SANDBOXING = NO` on Batty target's Debug + Release.

## Gotchas

- **Vendored files have to be updated when libghostty-spm pins to a newer Ghostty.** The `ATTRIBUTION.md` includes the bump command. There's no automation for this; a stale terminfo / shell-integration tree won't break the build but may cause silent shell-integration drift if Ghostty changes its OSC protocol or wire format.
- **The script uses `rsync --delete` on shell-integration** so deletions from upstream propagate. It does NOT `rsync --delete` on terminfo because there's only one file we care about — if Ghostty later ships additional terminfo entries we want, add them to the script.
- **`ENABLE_USER_SCRIPT_SANDBOXING = NO` was the right knob to flip.** With the sandbox on, even with declared `inputPaths` and `outputPaths`, the script couldn't `mkdir` the output subdirectories (the sandbox grants write access to declared output files but not to the directories that contain them). Disabling on the Batty target only keeps the broader project default unaffected.
- **Xcode flagged "Run script build phase will be run during every build because the option to run the script phase \"Based on dependency analysis\" is unchecked".** This is harmless — the script is fast (rsync of ~80KB) and idempotent. The `alwaysOutOfDate = 1` flag in the phase definition is what causes the notice. If perf matters later, switch to dependency-analysis mode and ensure every output path is declared.
- **`Build.xcconfig` was intentionally NOT modified** per the CLAUDE.md restriction. The sandbox setting lives in the target's `XCBuildConfiguration` entries inside `project.pbxproj` instead.
- **PR-pushed builds and notarized DMGs:** the Run Script phase fires identically in Debug, Release, and via `xcodebuild archive`, so `scripts/release.sh` produces a notarizable bundle with the resources intact. No additional release-pipeline changes required.
