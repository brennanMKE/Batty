## Description

Switching themes (View → Theme menu) currently only repaints the terminal contents — which makes sense, because terminal colors are controlled by Ghostty and the `.ghostty` theme file. But the window chrome around the terminal (window background, tab bar, sidebar, dividers, focus borders, popovers) stays at the system default appearance regardless of theme.

The visual mismatch breaks the illusion of a themed app — a Mocha or Tokyo Night terminal sitting inside a default-gray macOS window looks like two unrelated apps stacked on top of each other. A themed terminal should have themed chrome.

## Acceptance criteria

- When the active theme changes (View → Theme, or any other entry point that swaps the Ghostty theme), the chrome around the terminal updates to match:
  - Window background color (the area visible behind panes, the gap around splits)
  - Tab bar background and chip background
  - Sidebar background and selected-row tint
  - Split dividers
  - Focus border on the focused pane
  - Pane-swap drop-target highlight (`#0127`) — should still read as an accent, but adapted to the theme palette
- The theme switch is **live** — no restart, no window-close-and-reopen required.
- Default behavior (no theme selected, or a "System" theme option if one exists) falls back to the standard macOS adaptive chrome (light / dark per system appearance).
- The chrome derives from the same `.ghostty` theme file that drives terminal colors — single source of truth. No separate "chrome theme" picker.
- Readable in both light and dark themes; in particular, text and icons on the chrome should maintain contrast against the themed background.

## Out of scope

- Authoring new themes or extending the `.ghostty` theme file format. If the file already exposes a foreground/background/accent that the chrome can read, use those; if it doesn't, this issue stays scoped to "wire what's available" and a separate issue covers extending the schema.
- Theming the macOS title bar / traffic-light buttons themselves. macOS gives limited control there; what we can do is set window background and let the title bar adapt (`titlebarAppearsTransparent`, `backgroundColor`, etc.).
- Theming non-Batty windows (Settings, About). Those can stay system-native; the work here is the main terminal window's chrome.
- The bell-feed popover and other transient surfaces — nice-to-have, but if they're not trivially themable, defer to a follow-up.

## Notes

- The Ghostty theme file format includes colors like `background`, `foreground`, `selection-background`, `cursor-color`, plus the 16 ANSI colors and (sometimes) `palette` entries. Window chrome wants `background` (window/pane fill), `foreground` (chrome text/icons), and probably one of the ANSI colors or a derived accent for highlights.
- Look at where the active theme is currently loaded and applied to Ghostty surfaces — that hook is the natural place to also publish a `ThemeChrome` value (or similar) that SwiftUI views observe.
- SwiftUI's `.preferredColorScheme(_:)` won't be enough on its own — it switches between system light/dark variants but doesn't apply arbitrary background colors. The work is likely to publish a `@Observable` chrome palette and have key chrome views read from it (`SessionSidebarView`, `PaneView`'s tab bar background, `SplitContainerView` dividers, focus-border overlay, etc.).
- Watch out for hardcoded `Color.gray`, `Color(.windowBackgroundColor)`, `Color.accentColor` references in the chrome views — those are the things that need to flow through the new palette instead.
- Test against at least one light theme and one dark theme to confirm contrast holds in both directions. Mocha (dark) and one of the lighter Ghostty themes are a reasonable pair.
- Related: `#0127` pane-swap drop highlight currently uses `Color.accentColor`. It should probably read from the themed accent so it doesn't clash with the rest of the chrome.

## Root cause

What was missing: the theme application path stopped at the libghostty surface. `AppStateStore.applyThemeToAllSurfaces(_:)` walked every tab and called `controller.setTheme(_:)`, which repainted the terminal canvas, but nothing fed the same `.ghostty` color slots into the SwiftUI chrome. Every chrome view that needed a color hardcoded `Color.accentColor`, `Color.gray.opacity(...)`, `Color(nsColor: .windowBackgroundColor)`, or `Color(nsColor: .separatorColor)`, so the chrome stayed on the standard macOS adaptive palette no matter which theme was selected. The fix is plumbing — there was no single-source-of-truth palette to read from.

## Fix

Introduced `ThemeChrome` (`@Observable`, `@MainActor`) that holds a `ChromePalette` derived from a `GhosttyThemeDefinition`. The palette publishes optional colors for window/chrome background, primary and muted chrome foreground, accent, divider, tab active/inactive fills + strokes, and the sidebar selection tint. Every slot is `Color?` — `nil` means "fall back to the system default", which lets chrome views keep their pre-theming look when no theme is selected or a theme file lacks a needed slot.

Source-color mapping:

- `windowBackground` / `chromeForeground` ← theme `background` / `foreground` (required; if missing or malformed, the palette degrades to all-`nil` defaults).
- `chromeBackground` ← `background` shifted 6% toward `foreground` so the chrome reads as a layer above the canvas without sliding into a different hue family.
- `accent` ← `cursor-color` first (the theme author's explicit highlight), then ANSI 4 (blue, the conventional accent), then ANSI 6 (cyan). Skips red/green/yellow because those carry semantic meaning in terminal output. A WCAG contrast check (≥ 1.5 against the background) skips washed-out candidates; falls back to foreground if every option is too low-contrast.
- `divider` ← foreground at 18% alpha — legible across both dark and light themes without a separate tone choice.
- Tab strokes pick the higher-contrast of (accent, foreground@50%) against the active-tab fill so a beige accent over a beige tab on a light theme still has a visible outline.

`AppStateStore.applyThemeToAllSurfaces(_:)` now calls `themeChrome.update(from: theme)` after pushing the libghostty repaint, so the chrome and the terminal flip in lockstep with no view rebuilds and no surface teardown. The chrome is seeded at `AppStateStore.init` from the persisted theme name in `UserDefaults`, so the first window already has the right chrome at launch.

`RootWindowView` publishes the `ThemeChrome` via `EnvironmentValues.themeChrome`, and a small `WindowChromeApplier` `NSViewRepresentable` pushes the themed `windowBackground` onto the hosting `NSWindow` with `titlebarAppearsTransparent = true` so the title bar adapts; reverting to a non-themed palette restores the system title-bar material. Chrome views (`SessionSidebarView`, `SessionDetailView`, `PaneView`, `BattyTabChip`, `SplitContainerView`) read the palette and substitute themed colors for the hardcoded ones, falling back to their previous defaults when the env value is `nil`.

The pane-swap drop highlight from `#0127` was rewritten to thread `accentColor` through the `PaneSwapDropTarget` modifier so it shares the themed accent with the rest of the focus chrome.

## Gotchas

- Visual contrast in both light and dark themes is the headline check that can only be done interactively — switch between Mocha (dark) and any light-background theme (e.g. one of the `3024 Day` / Solarized Light variants) and confirm the sidebar, tab bar, dividers, focus borders, and window background all follow without any unreadable text. The contrast-pick logic for the active-tab stroke and the accent legibility guard are best-effort but only a human can sign off on the result.
- The **bell-feed popover** (`BellFeedView`) is intentionally untouched — its `Color.accentColor` dot for unseen entries currently still uses the system accent. Popovers are AppKit-vibrant surfaces; theming them properly is a follow-up. Other transient surfaces (CommandPalette, OpenQuickly, RenameTabSheet, settings) are similarly out of scope per the issue.
- The title bar adapts via `titlebarAppearsTransparent = true` + `window.backgroundColor = themed`. The traffic-light buttons themselves stay system-native (out of scope). Reverting the picker to "Default" restores `titlebarAppearsTransparent = false` so the title bar gets its vibrant material back.
- `WindowChromeApplier.updateNSView` dispatches the actual `NSWindow` mutation onto the next runloop tick. The first call happens before SwiftUI has attached the `NSView` to a window, so a synchronous read of `nsView.window` returns `nil` and silently no-ops. The dispatch makes the cold-launch case work without adding a polling loop.
- `ChromePalette(theme:)` returns `.default` (all `nil`) when `background` or `foreground` is unparseable. Every chrome view tolerates `nil` slots, so a partial/broken theme degrades to the existing macOS adaptive defaults rather than rendering a black-on-black surface.
- The catalog default (`TerminalTheme.default`) used by `TabRuntime.activeTheme()` when the picker is on "Default" doesn't flow into `ThemeChrome` — there's no `GhosttyThemeDefinition` to derive from, so the chrome stays in its system-default state. That matches the acceptance criterion that "Default" falls back to the standard macOS adaptive chrome.

## Re-resolution (round 2)

The round-1 re-resolution misread "make the selection not look like a colored block" as "leave the slot empty and let SwiftUI handle it". Setting `sidebarSelectionTint = nil` only told `SidebarRowBackground` not to paint a custom tint; it didn't suppress anything. SwiftUI's `.sidebar` list style still painted its own selection chrome — a fixed dark gray rectangle that ignores the surrounding sidebar background — so on every themed sidebar (red, navy, green, olive) the selected row read as a gray block sitting on top of the themed background.

This round suppresses the system selection chrome by attaching `.listRowBackground(themed sidebar bg)` to every row (not just the selected one) when a theme is active. With every row already declaring its own background, the system has nothing left to paint and the selected row's background visually matches the unselected rows. Selection is now indicated entirely by row content: a 3pt themed-accent stripe along the inner left edge of the selected row, a semibold title, and an accent-tinted icon. On the "Default" theme path (no themed `chromeBackground`), the modifier skips `listRowBackground` entirely so SwiftUI's system selection chrome continues to apply as before.

### Files changed

- **`BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift`** — `SidebarRowBackground` now takes the themed sidebar background and applies `.listRowBackground(_:)` to every row when present (not only the selected row), which is what actually suppresses the system selection paint. `SessionRow` gains `isSelected` / `themed` flags and renders a leading 3pt accent stripe, a semibold title, and an accent-tinted icon when selected on a themed surface. The unused `rowBackground(for:)` helper that returned the v1 selection tint is removed.

### Tests changed

- None. The existing `sidebarSelectionTintIsAlwaysNil` test still passes (the slot in `ChromePalette` is unchanged — the round-2 work moved entirely into `SessionSidebarView`). SwiftUI selection chrome and overlay rendering aren't cleanly unit-testable, so no new test was added for the stripe.

### Gotchas

- Visual sign-off is still the user's. Verify on red, navy, green, olive, and Mocha that the selected row's background matches the surrounding sidebar (no gray block) and the accent stripe + bold title + tinted icon read as "selected". Verify on the "Default" theme that selection still has a visible indicator (system default chrome).
- The suppression mechanism is `.listRowBackground(_:)` on every row, not on the selected row alone. Applying it only to the selected row would let the system selection paint through on the *non-selected* rows of any theme that doesn't perfectly match the system gray — which is what bit round 1.
- `sidebarSelectionTint` is now effectively dead in `ChromePalette` (always `nil`, never read). Left in the type so a future "subtle themed tint" experiment can flip the slot back on without a schema change; if it becomes obvious the slot will never be used again, it can be deleted in a follow-up.

## Re-resolution (round 3)

Hypothesis A was the source: `SplitContainerView`'s `DraggableSplitView` painted a single `Rectangle().fill(themeChrome.divider)` spanning the entire pane height for every horizontal split. Each pane's tab bar (chrome strip) sits at the top of its `PaneView` body, so the full-height divider cut through every chrome strip and read as the offending vertical line above the tab bars.

`PaneView` now publishes its chrome strip height via a new `ChromeStripHeightPreferenceKey` (a `.background` `GeometryReader` on the chrome `HStack`). `DraggableSplitView` observes the preference and renders the horizontal divider as a vertical `VStack` of two rectangles: the top chunk (height = the observed chrome strip height) is filled with `themeChrome.chromeBackground` so it merges seamlessly with the chrome bands on both sides; the rest is filled with the existing divider color. Drag affordance, hit-testing, and resize cursor are unchanged because the gesture/`contentShape` modifiers are applied to the whole divider group. Vertical dividers stay a single body-colored rule — in a vertical split each pane's chrome sits at its own top edge so the horizontal divider never intersects a chrome strip.

### Files changed

- **`BattyKit/Sources/BattyKit/Views/PaneView.swift`** — adds a `.background` `GeometryReader` on the tab-bar `HStack` that publishes the chrome strip height via `ChromeStripHeightPreferenceKey`.
- **`BattyKit/Sources/BattyKit/Views/SplitContainerView.swift`** — defines `ChromeStripHeightPreferenceKey`, observes it on `DraggableSplitView`, and splits the horizontal divider into a top chrome region (painted with `chromeBackground`) and a body region (painted with the divider color). Vertical divider stays a single body-colored rule.

### Tests changed

No new tests. Preference-key bubble-up and divider painting are SwiftUI layout behavior that isn't cleanly unit-testable; all 268 existing tests still pass.

### Gotchas

- Visual sign-off remains the user's. Verify with four horizontally-split panes (no vertical lines through the chrome band above the tab bars), four vertically-split panes (chrome band on each pane still reads cleanly), and at least one nested layout (e.g., a vertical split containing a horizontal split). Re-check focus border and pane-swap drop highlight still render on the focused/targeted pane.
- The preference key uses `max()` to reduce. If a future change introduces panes with different chrome strip heights (it shouldn't — they all use the same `SlidingTabBar`), the divider will paint the taller height as chrome, which is the safer side to err on.
- When no theme is active, `chromeBackground` is `nil` and the chrome region falls back to the divider color — preserving the pre-#0135 look on the "Default" theme so nothing visual changes for that path.
- The chrome strip height is read from the `HStack` that hosts the `SlidingTabBar`, not from the `SlidingTabBar` itself. If a future change adds further padding around the tab bar (or replaces the bar with a taller toolbar), the preference still measures the correct chrome extent because it observes the same view whose background paints `chromeBackground`.
