# 0347 — Replay `capture-pane` history on attach so an attached Pane is not blank

| | |
|---|---|
| **Status** | open |
| **Module** | TerminalSurface / Pane |
| **Platform** | macOS |
| **First seen** | 2026-08-21 |

## Description

tmux control mode's `%output` carries the **live stream only**.
Attaching to an existing session therefore shows an empty Pane until
something prints — the shell's history, the output of the long build
the user attached specifically to check on, all of it invisible. To a
user this reads as broken even though the connection is healthy.

The fix is to ask tmux for the existing history explicitly, with
`capture-pane -p -S -` (all history) or a bounded `-S -<N>`, and
replay it into the Pane's surface through
`InMemoryTerminalSession.receive(_:)` before live output starts.

Small and self-contained, but it is the difference between a remote
Pane that is *correct* and one that is *usable*. [#0344](0344.md) and
[#0346](0346.md) both look broken without it.

The architecture lives in [#0341](0341.md) and is not restated here.

**Not scheduled work.** Inherits #0341's status: staged for a future
major release, not queued.

### Why it is not just "run one command"

Three things make this harder than it sounds:

1. **Ordering.** Live `%output` can arrive while the `capture-pane`
   reply is still in flight. Those bytes must land *after* the
   replayed history, not interleaved into it — otherwise the Pane
   shows the future before the past.
2. **The pre-attach drop.** `InMemoryTerminalSession.receive(_:)`
   silently drops data when the session has no surface yet: it guards
   on `InMemoryTerminalSurfaceAccess.enqueueWrite(_:)`, which returns
   `false` while `surface` is `nil`, and logs a "dropped" line. A
   history replay issued at attach time is exactly the traffic most
   likely to hit that window. #0342's acceptance criterion 5 owns the
   general fix; this issue is its most demanding consumer.
3. **Volume.** `-S -` on a long-lived session can be megabytes of
   escape-sequence-laden text arriving in one reply, parsed and
   rendered in one go. #0285 is this project's standing lesson about
   per-session cost that nobody measured until it was 8.4 GB.

Note also that `InMemoryTerminalSession.readViewportText()` is **not**
a solution to any part of this: its own doc comment states it reads
exactly the visible rows and ignores scrollback. It reads *out* of a
local surface; this issue is about getting history *in* from a remote.

## Expected behavior

1. Attaching to an existing remote Pane shows its recent history
   immediately, not a blank Pane.
2. History appears before live output, in the correct order, with no
   interleaving and no duplicated lines at the seam.
3. Colors, cursor positioning, and other escape sequences in the
   replayed history render correctly — `capture-pane -e` preserves
   escape sequences and plain `-p` does not, so the flags chosen must
   match what the surface needs.
4. Scrolling back in an attached Pane reaches the replayed history,
   so the Pane's scrollback is genuinely populated rather than just
   its viewport.
5. A very long history does not stall the UI or balloon memory. A
   bounded default with a stated limit is acceptable and probably
   correct; unbounded-by-default is not.
6. If the capture fails or the remote does not support the flags used,
   the Pane still attaches and works — it just starts empty, with the
   failure logged. History replay must never be able to prevent an
   attach.

## Acceptance criteria

1. Attaching to a tmux session with existing output shows that output
   in the Batty Pane, verified against what the same session shows in
   a terminal on the remote.
2. Output produced *during* the attach handshake appears after the
   history, in order, with no duplication at the boundary — verified
   deliberately, by generating output on the remote while attaching.
3. Escape sequences in the history render correctly: attach to a
   session whose history contains colored output and a full-screen
   program's leftovers, and confirm it does not render as literal
   escape text or as stripped plain text.
4. Replayed history is reachable by scrolling back in the attached
   Pane.
5. The default history depth is bounded, the bound is stated, and
   attaching to a session with a very large history completes in a
   stated time without a visible hang.
6. A failed or unsupported `capture-pane` degrades to an empty-but-
   working Pane, logged, never a failed attach.
7. `scripts/build.sh unit` passes with new `BattyKitTests` covering
   the ordering guarantee — history bytes and concurrently-arriving
   live bytes fed to the mapping layer produce the correct final byte
   sequence — driven from recorded fixtures, not a live remote.
8. The pre-attach drop cannot lose replayed history: a test that
   issues the replay before the surface attaches and asserts the
   content renders once the surface exists.

## Notes

- `capture-pane` flags worth settling explicitly: `-p` (to stdout),
  `-S -` / `-S -<N>` (start line), `-E` (end line), `-e` (include
  escape sequences), `-J` (join wrapped lines). `-e` versus plain `-p`
  is the one that decides whether colors survive; `-J` changes how
  wrapped lines re-render at a different width and is worth thinking
  about given that the attaching client's width may differ.
- The reply arrives inside #0343's `%begin`/`%end` framing, so the
  parser's command-reply correlation is what makes it retrievable at
  all.
- Reconnect after a drop (#0346) is a second consumer of this path,
  and a harder one: some history was already rendered locally, so a
  naive full replay duplicates it. Decide whether reconnect replays
  at all, and record the answer even if the implementation is
  deferred.
