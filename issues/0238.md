## Description

Phase 5 of the #0234 multi-window umbrella: restore the **window set** across relaunch, per `docs/multi-window-design.md` §6. Important scope correction recorded there: workspace persistence was removed in #0172 ("never a planned feature") — there is no `workspace.json` and no `WorkspaceManager`, so this phase restores windows, not session contents. There are no single-window workspace files in the field to migrate.

Scope:

- Window count, frames, displays, and zoom restore via macOS window restoration through the `WindowGroup` scene (#0237); each restored window's presented `WindowID` re-materializes its `WindowRuntime` through the same lazy `windowRuntime(for:)` path New Window uses. No Batty code stores frames.
- Sidebar visibility becomes per-window: `@SceneStorage` replaces the single `SidebarPreference.hiddenKey` read in `Views/RootWindowView.swift`; the first window seeds from the legacy global key so existing users keep their hidden/shown state; the `toggleSidebar` shortcut flips the key window's state.
- Restored windows open with one fresh session each (cwd `$HOME`), matching launch behavior today — sessions/panes/tabs/shells are deliberately not restored (#0172 stands).
- A restored window whose display is gone lands wherever macOS places it (system behavior, not overridden).

## Acceptance criteria

- Quit with N windows on multiple displays → relaunch reopens N windows at their frames (on the original displays when present), each with its own sidebar state and a fresh session.
- Single-window users see today's exact behavior: one window, old frame, fresh `Session 1`, sidebar state preserved (legacy-key seed verified).
- `scripts/build.sh unit` passes; UI suite (including relaunch-shaped tests) passes.
