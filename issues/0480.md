## Description

When a non-content Batty window (Settings or Help) is the key window, menu key equivalents run against the content window behind it, which the user can't see. ⇧⌘X Exit Shell types `exit` into a terminal behind Settings. ⌘V pastes into it when the Settings responder isn't a text field. ⌘T, ⌘D, splits, focus moves and resizes all change a Session the user isn't looking at. This bug is already in shipped 1.2 and was found while reviewing #0474. It is not a Projects feature and is not behind the Projects flag. **It is a candidate for `git cherry-pick -x` onto `release/1.2` after it lands on `main`** (AGENTS.md "Release branches").

**Mechanism.** `BattyShortcuts.handle` declines every chord when the key window isn't a registered content window (`BattyKit/Sources/BattyKit/Commands/BattyShortcuts.swift:34`, `guard appStore.keyWindowIsContentWindow() else { return false }`). This gate was added for #0196, where ⌘W in Settings closed the background Tab and quit the app. Once the monitor declines, AppKit sends the event to the main menu. The SwiftUI menu items in `BattyCommands` resolve their target through `keyWindow` (`BattyCommands.swift:61`, `store.keyWindowOrFirstRegistered()`), which calls `AppStateStore.defaultTargetWindow()` (`AppStateStore.swift:944`). Its #0439 policy falls back to the **most recently key content window** (`recentlyKeyWindowIDs`, `AppStateStore.swift:130`) when no content window is key. Paste and Exit Shell go through `AppStateStore.focusedTerminalTab` (`AppStateStore.swift:988`), which uses the same resolver. So the #0196 gate stops the monitor but not the menu.

**This contradicts #0453's documented intent.** #0453 kept this behavior on purpose: "when another window such as Settings has focus, the menu shortcut is what runs it" (`issues/0453.md:72`; the same wording is in the comment at `BattyCommands.swift:236-239`). The fix has to weigh that intent command by command (see "Per-command decision" below). It must not just block everything.

## Steps to reproduce

1. Open Batty with one window and one Session, with a shell at a prompt.
2. Press ⌘, to open Settings. Click a non-text control, such as a pane button in the Settings toolbar, so that no text field is first responder.
3. Press ⇧⌘X. Close Settings: the shell behind it has exited.
4. Reopen Settings. Copy some text and press ⌘V with no text field focused. Close Settings: the text was typed into the terminal. With paste strictness set to confirm, the paste is dropped instead (see Actual behavior).
5. Reopen Settings and press ⌘T, then ⌘D. Close Settings: the Session behind it gained a Tab and a split.
6. Repeat steps 3–5 with Help (⌘?) as the key window.

## Expected behavior

While Settings or Help is key, a menu chord never changes terminal content or Session layout that the user can't see. Commands that mean "act on the front window" act on the Settings/Help window or do nothing. Commands that make sense from anywhere in the app keep working, as #0453 intended, where this issue decides they should.

## Per-command decision (implementer proposes, reviewer checks)

The resolution must record a decision for each row, with a reason. Suggested starting point:

- **Destructive or invisible terminal-content actions: block when an auxiliary window is key.** This covers Exit Shell, Paste-to-terminal, Close Tab, New Tab, splits/Open View, focus, resize, and Tab/Session selection. Nobody expects these to reach through Settings.
- **⌘W → `NSApp.keyWindow?.performClose(nil)`** when an auxiliary window is key, so ⌘W closes Settings/Help whatever the menu-matching order. This is what #0196 intended.
- **Paste → `PasteDispatcher.forwardStandardPaste()`** (the standard `NSText.paste(_:)` action) when an auxiliary window is key. Text fields in Settings (Shortcuts recorder excepted, font family fields, etc.) still paste, and nothing reaches the terminal.
- **⌘N New Session: decide explicitly.** Option A: keep it. It's a "from anywhere" command like New Window, but it should then bring the target content window forward so the result is visible. Option B: block it like the others. #0453's "from Settings the menu runs it" intent is strongest for Open View and New Session, so whichever you choose, write down why.
- **Open View (⌘G/J/Y/E):** this is the case #0453 named. Blocking it reverses #0453's documented decision. If blocked, update `BattyCommands.swift:236-239`, the matching resolution note in `issues/0453.md` stays as history, and update `docs/shortcuts.md` / `BattyKit/Sources/BattyKit/Help/05-shortcuts.md` where they describe it. If kept, bring the target window forward so the new Pane is visible.
- **Notification toggles (Open Quickly, Sidebar, Layout picker, Theme selector, Bell Feed):** today these do nothing. Either leave them inert (record that) or bring the most recently key content window forward and then toggle. Don't make them act on a hidden window.

## Reference design (from the #0474 review)

#0474 narrows its own gate to the Project Editor window only, and hands the Settings/Help case to this issue. Treat the design below as a reference, not a mandate:

- **Classifier.** Walk `sheetParent` to the top-level window first. Then classify `NSApp.keyWindow` as *auxiliary* when it is **not** a registered content window (`nsWindowMap`) **and** `canBecomeMain == true`. This excludes non-activating panels and popovers, whose chords should keep today's behavior. Write this as a pure function over an `NSWindow?` plus the registry so it can be unit-tested.
  - **Open question: NSOpenPanel.** A titled `NSOpenPanel` reports `canBecomeMain == true`, so the classifier would call it auxiliary. Example: the standalone panel in Git Status ▸ Change Directory… (`GitStatusPaneView.swift:473-484`, `panel.begin`, not a sheet). That's probably the right result, since ⌘V in its path field should go to the panel, not the terminal. Confirm it and record the decision. Sheet-presented panels resolve through `sheetParent` to their content window and are not auxiliary.
  - Verify `canBecomeMain` empirically for the SwiftUI `Settings` scene window and the `Window("Batty Help", id: "help")` window (`Batty/BattyApp.swift:55-73`). Don't assume it.
- **Gate at action time only, never in menu enablement.** Don't compute `.disabled(...)` from a gated resolver. `NSApp.keyWindow` and `nsWindowMap` aren't observed, and `recentlyKeyWindowIDs` is `@ObservationIgnored` (`AppStateStore.swift:130`). SwiftUI therefore has nothing to re-evaluate the `Commands` body on, and items can stay disabled after the user returns to a content window. Keep enablement on `keyWindow` / `defaultTargetWindow()` as now, and check the classifier inside each action closure (or in one shared helper the closures call).
- **Don't change `defaultTargetWindow()`.** Its #0439 fallback is correct for XPC/CLI verbs, the Command Palette and `batty://` URLs, which must keep resolving a window when Settings is key. The fix is only in the menu-action layer: `BattyCommands` and `PasteDispatcher`/`ExitDispatcher` at their menu entry points. `ExitDispatcher.sendExit` is also called from `BattyShortcuts.swift:195` and `CommandPaletteView.swift:287`, both of which only run with a content window key. Put the gate at the `BattyCommands` call site (`BattyCommands.swift:512`), or make it harmless for them.
- Keep `BattyShortcuts.swift`'s `keyWindowIsContentWindow()` gate. #0196 still needs it. Update its comment and `docs/shortcuts.md:222-227` if the explanation of what happens after the monitor declines changes.

`docs/swiftui-observation-rules.md` is binding here. The action closures are event-origin, and the change must not add writes from `body` or from layout/focus-origin callbacks.

## Root cause

When the key window isn't a content window, `BattyShortcuts.handle` declines the chord (#0196). AppKit then routes it to the main menu. The `BattyCommands` action closures resolve their target through `keyWindowOrFirstRegistered()` → `defaultTargetWindow()`. Under the #0439 policy, that falls back to the most recently key content window, which the user can't see. Paste and Exit Shell resolve through `focusedTerminalTab`, which uses the same resolver.

## Fix

- `AppStateStore`:
  - `static isAuxiliaryWindow(_:isContentWindow:)` walks `sheetParent ?? parent` to the top-level window. It counts as auxiliary when it is `.titled`, is not a `.nonactivatingPanel`, and is not a registered content window.
  - It reads the style mask, not the `canBecomeMain` the issue proposed. A never-shown titled window reports `canBecomeMain == false`, so a classifier built on it couldn't be unit-tested with real windows.
  - Instance `isAuxiliaryWindow(_:)`, `auxiliaryWindowIsKey`, and an `@ObservationIgnored keyWindowProvider` seam.
  - `menuTargetWindow(...)` takes `auxiliaryWindowIsKey:`, and `focusedTerminalTab` is gated on it.
  - `defaultTargetWindow()` and `keyWindowOrFirstRegistered()` are unchanged. `projectEditorIsKey` (#0474) is now subsumed by `auxiliaryWindowIsKey`. The overlap is harmless, and the name is kept so the code still matches `release/1.2` for the pick.
- `BattyCommands`: action closures use `actionWindow`, and `.disabled(...)` still reads `keyWindow`, so enablement is never gated. When an auxiliary window or the Project Editor is key, ⌘W calls `performClose`. `postToContentWindow` declines.
- `ExitDispatcher`: an injectable `sendText` seam. Production behavior is unchanged.
- Docs: `docs/shortcuts.md` has a new section, "When Settings or Help is key (#0480)", and corrects the Open View and monitor notes. `Help/05-shortcuts.md` gains a paragraph.
