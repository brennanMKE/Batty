# 0387 — Hidden Terminal Sessions keep full-size GPU drawables allocated, so a window showing 2 Panes still holds graphics memory for every open session

| | |
|---|---|
| **Status** | open |
| **Module** | TerminalSurface / GhosttyKit |
| **Platform** | macOS |
| **First seen** | 2026-08-31 |

## Description

Every Terminal Session holds a full, Pane-sized triple-buffered swap chain for the life of the process, on screen or not. `setSurfaceVisible(false)` stops the *rendering* and frees *nothing*. On a fresh sample of the running release instance today (pid 41541), 17 Terminal Sessions with **one window on screen** carried a 833 MB `phys_footprint` of which **578 MB (69%) is graphics** — and with at most 2 Panes visible, roughly **510 MB of that belongs to Panes the user cannot see**.

```
Footprint 833 MB, 17 Terminal Sessions, 1 window on screen
  IOAccelerator (graphics)   255 MB  326 regions
  MALLOC_SMALL               196 MB
  IOSurface                  171 MB   71 regions
  Owned unmapped (graphics)  152 MB  409 regions
  graphics subtotal          578 MB  = 69% of footprint
```

The `vmmap` drawable histogram makes the ownership unambiguous — every large IOSurface size arrives in a multiple of three:

```
3 × 1360K   3 × 2080K   3 × 2176K   3 × 2320K   3 × 2384K
6 × 2976K   6 × 3568K   6 × 3632K   3 × 3744K   3 × 3856K
9 × 4576K   3 × 6208K
```

**51 large surfaces = 17 triple-buffered swap chains for 17 Terminal Sessions — a clean 1:1.** #0288 already removed the *duplicate* layers (July: 31 layers for 26 sessions, 22 sharing one geometry only 2 Panes could occupy). What remains after that fix is the per-session floor: one correctly-sized, correctly-counted swap chain per session, resident whether or not anything is drawing into it.

**This issue is an experiment, and should be run as one.** A legitimate outcome is "this does not work" or "the reflow cost is unacceptable" — recorded with evidence, that is a valid resolution. Do not force a shipped behavior change if the measurement says no.

## Expected behavior

Hiding a Pane, switching Sessions, or switching Tabs releases most of the hidden Terminal Session's GPU footprint. Restoring it repaints correctly, with intact scrollback and no flash of stale or blank content.

## Actual behavior

Hiding changes nothing about allocation. `TerminalHostStore` sets `view.isHidden = true`, calls `view.setSurfaceVisible(false)`, and **leaves `view.frame` at its last visible size** — so the swap chain, glyph atlases, and render textures stay at full Pane dimensions until the Session is closed. The only lever that reclaims graphics memory today is closing Sessions, which is not a fix.

## The proposed approach — shrink the hidden surface, don't free it

A drawable is `width × height × 4`. #0293's own evidence established that **a resize swaps the drawable pool 1:1** — measured there: six 820×962 drawables freed, six 934×962 allocated, net surface count unchanged. So an embedder can *shrink* a hidden surface's swap chain without any upstream change. Shrinking a chain to, say, 64×64 turns ~30 MB of drawables into a few hundred KB.

### Verified mechanics (checked against the tree on 2026-08-31 — read this before starting)

- **The transition hook already exists.** `BattyKit/Sources/BattyKit/Runtime/TerminalHostStore.swift` computes `Self.effectiveSurfaceVisible(placementVisible:windowVisible:)` (defined at `:370`) and calls `view.setSurfaceVisible(_:)` at **three** sites, not one: `updatePlacements` (`:406`), `setPlacement` (`:433`), and `setWindowOcclusionVisible` (`:462`). *(The measurement attachment cites only `:406`; all three are the same transition and all three must be handled, or a window-occlusion round-trip will restore a shrunken surface without re-growing it.)*
- **Nothing in the app has ever tried this.** `grep` for `setSize` and `maximumDrawableCount` across `BattyKit/Sources` and `Batty/` returns **zero hits**. Confirmed.
- **No new API is required, and no upstream change is required.** The attachment's framing — that `ghostty.h` has `ghostty_surface_set_occlusion` and `ghostty_surface_free` "with nothing in between" — is true only of *resource-release* API. It is not true of resize: `ghostty_surface_set_size` sits literally on the next line (`ghostty.h:1134-1135`). More usefully, the embedder never needs to call it directly:

  ```
  AppTerminalView.setFrameSize(_:)  →  core.synchronizeMetrics()
      →  surface.setContentScale(x:y:)
      →  surface.setSize(width: bounds.w × scale, height: bounds.h × scale)   // ghostty_surface_set_size
      →  CAMetalLayer.drawableSize follows
  ```

  (`libghostty-spm` @ `b146b73`, `Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView+Lifecycle.swift:144`, `Sources/GhosttyTerminal/Surface/TerminalSurfaceCoordinator.swift:141-173`.) `layout()` and `viewDidChangeBackingProperties()` route the same way. **So the shrink is one assignment: write a small `view.frame` on the hide transition, and write the real frame back on the restore.** `TerminalHostStore` already writes `view.frame` — just only on the visible branch (`:390-397`). Note that `TerminalSurface.setSize` and `AppTerminalView.fitToSize()` are both package-internal (no `public`), so the frame path is not merely the convenient route, it is the only one available without an upstream patch.
- **`setSurfaceVisible(false)` provably frees nothing.** `TerminalSurfaceCoordinator.setDisplayVisible(_:)` (`:212`) sets occlusion and stops the display link. That is its entire body. No size change, no deallocation.

## Risks — prove these absent, do not assume them

**A shrink is a resize, and a terminal resize reflows.** `synchronizeMetrics` recomputes `TerminalViewportMetrics` (columns × rows) from the new pixel size, so shrinking a hidden surface genuinely reshapes its grid. The failure modes to disprove:

1. **Scrollback corruption or loss.** Reflowing to a tiny grid and back may not round-trip. This is the single sharpest risk in the issue.
2. **Wrong-sized restore.** The Session comes back at the shrunken grid, or at a stale geometry, or the running TUI never learns the real size.
3. **Bad repaint on restore** — a flash of stale or blank content, or a visible reflow settle, on every Session/Pane switch. The restore must look instantaneous.
4. **SIGWINCH storms.** Every hide/show now resizes the PTY; a full-screen TUI (vim, htop, tmux) in a background Pane will see churn it previously did not.
5. **Cost of the swap itself.** Freeing and reallocating a swap chain on every Pane switch may cost more in latency than it saves in bytes.

If any of these cannot be made acceptable, **say so with the measurement that shows it and resolve the issue as a negative result.** That outcome has real value: it converts item 1 of the attachment's recommended work into a settled question and promotes #0293's upstream ask from "cheaper alternative available" to "only remaining path".

## Test protocol (binding — specified by the user)

- **All testing uses the Beta build.** `./build.sh` and `./build.sh package` — Beta is `build.sh`'s default scheme (`build.sh:42`, `BETA_SCHEME="Batty (Beta)"`), building `Batty Beta.app` under `co.sstools.Batty.beta`. Prod is release-only (`./build.sh release`). **Never test against the Prod app the user runs from `/Applications`.** *(Note: `CLAUDE.md` and `issues/Issues.md` both still describe `./build.sh` as invoking `Batty (Prod)`. That is stale — the script itself is authoritative and defaults to Beta.)*
- **Exercise the transition this fix hooks.** Create **several Sessions and several Panes**, then measure as **the selected Session and the selected Pane change**. Also cover the window-occlusion round trip (Cmd-H, minimize, full cover by another window) — that is the `:462` call site.
- **Measure `phys_footprint`, never RSS.** `ps -o rss` under-reported by **5.4×** on the last sample and **29×** on the original #0285 report.

  ```sh
  PID=$(ps -Ao pid=,comm= | awk '/Batty Beta\.app\/Contents\/MacOS\/Batty Beta$/{print $1; exit}')
  footprint -p $PID | head -14
  vmmap $PID | grep '^IOSurface'      # drawable histogram; sizes come in 3s per swap chain
  ps -Ao pid=,ppid=,comm= | awk -v p=$PID '$2==p' | wc -l   # Terminal Session count
  ```

- **Use the existing tooling rather than reinventing it.** `tools/memsample.sh` is the #0291 harness (see `tools/README.md` for its four experiment recipes) and already does before/after diffing by geometry class, not just totals. `TerminalMetalMetricsLogger` (`BattyKit/Sources/BattyKit/Runtime/TerminalMetalMetricsLogger.swift`) has in-process hooks that log per-surface `contentsScale` and `drawableSize` and can name a surface's owner — use it to confirm *which* surfaces shrank.

### Acceptance

A measured before/after showing the **graphics subtotal falling** as Sessions and Panes are hidden, with **scrollback intact** and **correct repaint on restore**.

**Baseline to beat** (2026-08-31, pid 41541, release instance): 17 Terminal Sessions, 1 window on screen, **833 MB footprint**, **578 MB graphics (69%)**, 51 large IOSurfaces = 17 swap chains, **~34 MB graphics per Terminal Session**. Prior points on the same curve: 1,433 MB / 28 sessions / 76% graphics (2026-08-30) and 1,472 MB / 26 sessions / 74% graphics (2026-07-31, the umbrella's stated baseline).

A negative result is accepted *only* with the same rigor: the numbers that show the shrink didn't take, or the artifact that shows the reflow damage.

## Notes

### Out of scope: MALLOC_SMALL is 196 MB and nothing bounds it

The same sample shows **MALLOC_SMALL at 196 MB across 17 Terminal Sessions — ~11.5 MB per Session**, almost certainly scrollback buffers. Nothing in the codebase sets a scrollback limit: `grep -i scrollback` across `BattyKit/Sources` and `Batty/` returns only documentation prose (`Help/02-sessions.md`, `Help/04-tabs.md`, `Help/07-themes.md`) and two unrelated doc comments in `PaneRuntime.swift` and `TerminalHostStore.swift`. No configuration, no cap, no eviction.

**This is explicitly out of scope for #0387** — recorded here so the observation isn't lost. It is worth its own issue if the user wants it pursued, and it is a different mechanism from the graphics floor this issue attacks.
