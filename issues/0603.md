## Description

**Small. Related to #0601** (found in its review round 2). `AppStateStore.openProject`'s create branch builds the Project's split tree with `isSessionSelected: true` regardless of whether the target window can be seen. So a status Pane it opens (System Metrics, Process Status, Git Status, LM Studio dashboard) starts sampling even when the window is occluded, minimized or hidden, and keeps sampling until the window's next occlusion transition. This is wasted work only: no resume is missed, because `WindowRuntime.setWindowVisible(true)` resumes the Pane anyway when the window becomes visible.

## Current state (verified 2026-11-12 on `main` `783fa123`)

- `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift`, `openProject(id:mode:contentFactory:fromCli:)`: the create branch calls `ProjectTreeBuilder.build(project:contentFactory:isSessionSelected: true, checkBackground:)`. Its doc comment says "The tree is built with `isSessionSelected: true` and the Session is selected in the same synchronous call, so every Pane is visible at creation."
- `ProjectTreeBuilder.build` (`Model/ProjectTreeBuilder.swift`) passes `isSessionSelected` down to each `PaneRuntime`, whose `init` calls `content?.setUp(visible: !isHidden && isSessionSelected)` (`Runtime/PaneRuntime.swift`).
- `WindowRuntime.addProjectSession(_:tree:background:)` then sets `selectedSessionID`. Its `didSet` runs `applySelectionVisibility(deselecting:selecting:)`, whose selecting branch calls `setVisible(true)` only `if isWindowVisible`, and never calls `setVisible(false)` on the newly selected Session. So nothing suspends the Panes that `setUp(visible: true)` started.
- `openProject` calls `activateWindow(target)` only when `fromCli || auxiliaryWindowIsKey`. Activation usually makes the window visible, and the occlusion callback then reconciles. When it doesn't run, or the window stays covered, the new Session samples until the next `windowDidChangeOcclusionState`.
- #0601 closed the same gap for the other creation paths: `WindowRuntime.createPane` passes `isSessionSelected: isWindowVisible`, and `AppStateStore.splitPane` passes `window.selectedSessionID == session.id && window.isWindowVisible`. `openProject` is the one creation path left.

## Expected behavior

A Project opened into an occluded window creates its non-terminal Panes suspended, and they resume when the window becomes visible.

## Notes

- Likely fix: pass `target.isWindowVisible` as `isSessionSelected` in `openProject`'s `ProjectTreeBuilder.build` call (the Session is selected in the same call, so selection is already true), and update the doc comment. `isWindowVisible` is `@ObservationIgnored` and written only by `setWindowVisible(_:)`.
- The focus-existing branch (`mode == .focusExistingOrOpen` with the Project already open) creates no Panes and goes through `setSelectedSession(id:)`, which `applySelectionVisibility` already gates. It needs no change.
- `SplitTree.splitFocusedPane` and `splitFullDimension` also pass `isSessionSelected: true`, but they always make terminal Panes (`makePane`'s default `kind: .terminal`), which have no `PaneContentLifecycle` content. Terminal occlusion goes through `TerminalHostStore.setWindowOcclusionVisible`. So they are not affected.
- Test: extend `BattyKit/Tests/BattyKitTests/WindowRuntimeOcclusionVisibilityTests.swift` (it already has `splittingAViewPaneWhileOccludedStartsSuspended` and `creatingAViewPaneWhileOccludedStartsSuspended`) or the Project open tests with something like `openingAProjectWhileOccludedStartsItsViewPanesSuspended`: occlude the target window with `setWindowVisible(false)`, open a Project whose layout has a non-terminal Pane via `openProject(id:contentFactory:)` with a recording content double, and assert the content was set up not visible. Then `setWindowVisible(true)` resumes it once. Add a control with the window visible so the test isn't vacuous.
- Fast tier only (`./build.sh unit`); no UI-visible change.

## Resolution

`AppStateStore.openProject`'s create branch now builds the Project's tree with `isSessionSelected: target.isWindowVisible`, so a Project opened into an occluded, minimized or hidden window starts its non-terminal Panes suspended, and `WindowRuntime.setWindowVisible(true)` resumes them. The doc comment and `docs/pane-view-lifecycle.md` (the Window occlusion row, and the stale `createPane` sentence) now say so.
