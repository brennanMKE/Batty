# 0154 — Add diagnostic logging for drag-and-drop code paths

| | |
|---|---|
| **Status** | open |
| **Module** | DragDrop / Pane / TerminalSurface |
| **Platform** | macOS |
| **First seen** | 2026-05-20 |

## Description

Drag-and-drop in Batty has regressed repeatedly (see [[0127]] and [[0143]]) and the current log output does not surface enough information to diagnose why. When a user reports that a file drop from Finder is ignored, that a pane-swap drag does not initiate, or that the swap drop zone fails to highlight, the only relevant line in the running session log is a single `drop ignored: no terminal under point ...` debug message from `TerminalHostView.performDragOperation` — and even that fires only after AppKit has already decided to route the drop to the host. Everything that happens before that decision (registration, drag entry, hover transitions, source UUID, `PaneSwapDragState` lifecycle, drop-zone overlay materialization, SwiftUI `.onDrop` callbacks) is invisible.

The recent session log the user pasted is a concrete example: the user performed drag-and-drop actions but the only DnD-relevant line in the entire output is silence. There is no way to tell from logs alone whether the drag source ever fired, whether AppKit ever offered the drag to either the terminal NSView or the SwiftUI overlay, which view claimed it, what UTTypes were on the pasteboard, or why the operation ended where it did.

This issue is **not** a fix for any specific drag-and-drop bug. It is the prerequisite for diagnosing the next one. Add structured `OSLog` output along every drag-and-drop code path so future regressions can be diagnosed from a session log without re-instrumenting the code each time.

## Scope — what to log

### File-drop path (AppKit-level, `TerminalHostView`)

For each of the `NSDraggingDestination` overrides, emit a single concise log line:

- `registerForDraggedTypes` at init — log the registered types so it is obvious from a startup log that the host is wired up as a drop target.
- `draggingEntered` — log: has-file-URL (Y/N), pasteboard types present, drag location in host coords, resolved hover tab id (or `nil`), returned `NSDragOperation`.
- `draggingUpdated` — log only on **hover-tab transitions** (don't spam every mouse-move). When the hover tab changes from A → B, log the transition with both ids; when it changes to `nil`, log "left all terminal subviews".
- `draggingExited` — log: previous hover tab id (or `nil`).
- `prepareForDragOperation` — log: has-file-URL (Y/N), returned bool.
- `performDragOperation` — log: drop location, resolved tab id, URL count, success/failure. Keep the existing "no terminal under point" line but reformat it to match the new structured style. On success, log the joined path string length (not the contents — paths may be sensitive).

### Pane-swap drag-source path (SwiftUI, `PaneSwapDragState` + `paneDragHandle`)

- `PaneSwapDragState.startDrag(from:)` — log: source pane id, whether a previous drag was still active (indicates leaked state), monitor installation success.
- `PaneSwapDragState.endDrag()` — log: source pane id (the one being cleared), whether end was triggered by the mouse-up monitor, the 30-second timer, the drop callback's `defer`, or an explicit cancel. Capture the trigger via a small enum so the message is unambiguous.
- `paneDragHandle.onDrag` closure — log when the closure fires (this is the only positive confirmation that SwiftUI's drag gesture activated) and the pane id passed into the `NSItemProvider`.
- The 30-second fallback timer firing — distinct log message at `notice` level, since this firing means something went wrong with the primary cleanup paths.

### Pane-swap drop-target path (SwiftUI, `PaneSwapDropZone`)

- Overlay materialization — log when a `PaneSwapDropZone` appears for a given pane id (the `isDragging && sourcePaneID != pane.id` condition becoming true) and when it disappears. This proves the overlay actually mounted, separate from whether it received the drop.
- `.onDrop` callback fired — log: target pane id, provider count, the loaded UUID string (or "load failed" / "not a UUID"), whether the source/target match short-circuited the swap.
- `tree.swapPanes` invocation — log: source id, target id (post-validation, just before the actual call).

### Pane-handle hover (low priority — keep out unless cheap)

Hover-driven `NSCursor.openHand.push/pop` from `paneDragHandle.onHover` is not in scope. Cursor changes are visually self-evident and would flood logs.

## How to log

- Use `os_log` via `Logger` from `OSLog`, following the existing project convention (`nonisolated private let logger = Logger(subsystem: Logging.subsystem, category: "<Filename>")` at the top of each file). `TerminalHostView` already has one — extend it. `PaneView.swift` does not — add one.
- Category strings match the filename so Console.app filters group cleanly.
- Use **`debug`** level for the high-volume per-event lines (drag entered, drop zone mounted, hover transitions) so they are filterable out of release builds. Use **`info`** level for one-shot lifecycle events (`startDrag`, `endDrag`, registration). Use **`notice`** for unexpected fallback paths (30-second timer firing, drop ignored because no terminal under point, UUID parse failure).
- Use the structured `Logger` format with `privacy: .public` on UUIDs, type identifiers, and counts. **Do not** log file paths or pasteboard string contents at `.public` — those are user data; use `.private` or omit.
- Prefix each message with a short stable tag so users can grep:
  - File-drop lines: `file-drop:` (e.g. `file-drop: entered hover=<uuid> op=.copy`)
  - Pane-swap lines: `pane-swap:` (e.g. `pane-swap: drop on=<uuid> source=<uuid> swap=true`)
- Keep each line single, terse, key=value. Avoid multi-line messages — they are hard to grep.

## Out of scope

- Fixing any specific drag-and-drop bug. The next reported drag-and-drop failure will be filed as its own issue and diagnosed with the help of these logs.
- Adding signposts (`OSSignposter`) or `os_log` formatters. Plain `logger.debug/info/notice` is sufficient for visual log inspection — signpost instrumentation is a separate concern.
- Logging the contents of dropped text or file paths beyond a length / count. Those are user data.
- Telemetry / counters that survive process exit.

## Acceptance criteria

- Running the app, opening a Finder window, and dragging a file across two different panes produces log lines that show (a) the drag entered the host, (b) which tab the hover resolved to, (c) the hover transitioning to the other pane when crossed, (d) whether the drop succeeded or was rejected.
- Initiating a pane-swap drag from a grip handle produces log lines that show (a) `startDrag` fired with the source pane id, (b) drop-zone overlays mounted on each non-source pane, (c) on drop, the source/target ids and whether the swap was applied or short-circuited (self-drop).
- Cancelling a pane-swap drag with Escape (no drop) produces log lines that show the 30-second fallback timer firing and clearing state — or, if the global mouse-up monitor handles cancellation first, that path logs the cancellation reason.
- All new log calls compile cleanly and pass `xcodebuild -scheme Batty -destination 'platform=macOS' build`.
- No `print()` or `NSLog()` introduced.
