# 0365 — `AppConnectDance.resolveEndpoint`'s injection seams are untested, and the target they live in is unreachable from the test target

| | |
|---|---|
| **Status** | open |
| **Module** | App |
| **Platform** | macOS |
| **First seen** | 2026-08-22 |

## Description

#0361 round 2 gave `AppConnectDance.resolveEndpoint` three injection seams —
`resolveAppBundle`, `launch`, and `isAppRunning` — precisely so the
duplicate-launch defect could be pinned down by a test. **No test uses any of
them.** `NoEndpointRegisteredDecision` is tested in isolation, which covers the
pure decision but not the wiring, and the wiring is where the bug lived: the
property that `resolveEndpoint` must never call `launch` while a process at the
resolved bundle path is running is asserted nowhere.

The reason turns out to be structural rather than an oversight, and that changes
the shape of the fix — see "Why no test uses them" below.

## Expected behavior

The seams #0361 added are exercised by tests that assert, at minimum:

- app running, no endpoint registered → `launch` is **never** called, and the
  failure is `.appRunningUnregistered` (exit `6`).
- app not running, no endpoint registered → `launch` **is** called exactly once,
  with the URL `resolveAppBundle` returned.
- `resolveAppBundle` fails → neither `launch` nor `isAppRunning` is called, and
  the failure is `.appBundleUnresolved` (exit `7`).
- `launch` returns `false` → the poll bound is short-circuited rather than burnt
  (the behavior its comment claims).

## Actual behavior

Zero tests reference `resolveAppBundle`, `launch`, or `isAppRunning` as
injection points. The only #0361 test touching this area is
`NoEndpointRegisteredDecisionTests`, which calls
`NoEndpointRegisteredDecision.action(isAppRunning:)` directly.

## Why no test uses them

`AppConnectDance`, `AppBundleLocator`, `RunningAppChecker`, and `SessionCommand`
all live in the **`batty` executable target**. `BattyKitTests` declares
`dependencies: ["BattyKit"]` (`BattyKit/Package.swift`) and imports only
`BattyKit` / `BattyXPCCore` — it cannot import an executable target, so none of
those types are reachable from a test at all.

That is why #0361's testable pieces are all the ones that were *extracted into*
`BattyXPCCore`: `NoEndpointRegisteredDecision`, `AppBundleResolution` (a pure
function of already-resolved strings), `BrokerReconnectBackoff`. The seams left
behind in the executable target are, as things stand, decorative — they make the
code look injectable without making it testable.

So the fix is not "write a test"; it is a structural choice, and worth deciding
deliberately:

- Move `AppConnectDance` (and the collaborators it needs) into a library target
  the test target can depend on — mirroring how `AppBundleResolution` was already
  split out of `AppBundleLocator`.
- Or add a small library target for the connect dance that the `batty`
  executable links, leaving only `@main` and argument parsing in the executable.
- Or add a separate test target that depends on the executable target's sources,
  if SwiftPM's constraints allow it here.

Whichever is chosen, note that `BattyKit` links libghostty and Sparkle, and
`BattyCLICore`/`BattyXPCCore` exist specifically to stay dependency-free so the
CLI and broker (which sit outside `Contents/Frameworks/` reach) do not
transitively drag those in — see the comments in `BattyKit/Package.swift`. Any
new home for `AppConnectDance` must preserve that discipline.

## Notes

### Scope grew in round 3 without the coverage catching up

Round 3 added a seventh consumer of the same injection-seam pattern:
`SessionCommand.openURL` now takes its own
`resolveAppBundle: () -> Result<URL, AppBundleLocator.Failure>` parameter and
targets the resolved bundle by path via `open -a`. That is the CLI's
most-typed verb — bare `batty` and `batty <path>` both route through it — and it
is equally unreachable from tests.

*Correction to the report that prompted this issue:* it described
`SessionCommand.openURL` as "a seventh call site" of `resolveEndpoint`. It is
not — `openURL` never calls `resolveEndpoint`. Verified call sites of
`resolveEndpoint` are six, all XPC verbs:

```
BattyKit/Sources/batty/ListCommand.swift:34
BattyKit/Sources/batty/StatusCommand.swift:19
BattyKit/Sources/batty/NotifyCommand.swift:67
BattyKit/Sources/batty/PaneCommand.swift:160
BattyKit/Sources/batty/PaneCommand.swift:222
BattyKit/Sources/batty/SessionInfoCommand.swift:48
```

`openURL` is instead a **seventh consumer of `AppBundleLocator.resolve()`**
through the same seam pattern. The point the report was making survives the
correction — the untested surface grew in round 3, and it grew on the verb users
type most — but "seventh call site of `resolveEndpoint`" should not be repeated
as written.
