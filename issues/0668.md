## Description

Child of #0660. When an agent runs a command where the user can watch it (`pane split -c`, `tab new -c` from #0667), it gets the new id back immediately and then learns nothing: not when the command finished, not whether it succeeded. Add `--wait [--timeout S]` to both: block until the command exits and report its exit status, the way `server start --wait` already blocks until a server listens or exits.

### Current state

- `pane split -c` sets the Tab's `command` to the given string, replacing the shell (`BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:429-458`). With no shell, shell integration never runs, so no OSC 133 `D` (command finished, with exit code) is emitted for it.
- Batty already receives OSC 133 `D`: `TerminalDelegateProxy.terminalDidFinishCommand(exitCode:durationNanos:)` (`BattyKit/Sources/BattyKit/Runtime/TerminalDelegateProxy.swift:236-238`) → `TabRuntime`'s `onCommandFinished` and `addCommandFinishedObserver` (`TabRuntime.swift:223-238`), which the Server Pane's terminal backend already uses to notice its server exiting (`BattyKit/Sources/BattyKit/Runtime/ServerBackend.swift:168`).
- The Server Pane runs its command by starting the user's shell and typing the command into it, not with `command` (`TerminalTabServerBackend`, `BattyKit/Sources/BattyKit/Runtime/ServerBackend.swift:112`), so it gets OSC 133 events.
- `server start --wait --timeout S` is the precedent for a blocking acknowledged XPC call with a timeout (`BattyKit/Sources/batty/ServerCommand.swift:119-123`; exit 4 on timeout).
- Shell integration exists only for bash and zsh at the pinned libghostty (#0400), so fish, elvish and nushell users get no OSC 133.

## Root cause

Feature work. `-c` replaced the shell with the command, so no shell integration ran and no OSC 133 D (exit status) was ever emitted; the CLI got the new id back immediately and nothing else. `TabRuntime`'s command-finished observers also dropped libghostty's duration.

## Fix

As planned. `--wait` creates an ordinary shell Tab (no `command`), arms the single-line command through `armStartupCommand` (the Server Pane / Project startup path), and `CommandWaiter` replies on the first OSC 133 D after the delivery's new `willType` event. Supporting pieces: `StartupCommandDeliveryEvent` (`willType`/`refused`/`abandoned`), `TabRuntime.addCommandFinishedEventObserver` (exit code + duration; the old observer wraps it), `TerminalHostStore` release observers (Tab closed), `AppXPCConnectionRegistry.onUnregister` (a killed CLI cancels the app-side wait; `perform` captures `NSXPCConnection.current()` and forwards to `perform(_:connectionID:reply:)`). Refusals (unsupported shell, hidden Pane for `tab new`, multi-line, non-terminal kind, `--unique`) happen app-side before anything is created. `paneSplit` now reads `storeProvider()` and always returns `tabID` for a new terminal Pane; `pane split` gained `--json`. CLI mapping in `CommandWaitCLI` (decision 4).

Small deviations:
- `CapabilitiesConstraintPayload.requires(...)` now takes `allowedValues: [String]?`; nil documented as "any value" (used by `wait` → `command`).
- `TabNewPayloadTests.replyDecodesWhenALaterBuildAddsFields` used `exitCode` as its "unknown future field"; that key is now real, so it uses `futureField`.
- `timeout` has no schema `minimum` (the payload's `minimum` is `Int`, and the bound is exclusive); the CLI rejects `<= 0`.
- Claim commit came after the code commits rather than first.

Round 2 (after the round-1 bounce). One pure validator, `WaitTimeout` (new, `BattyXPCCore/WaitTimeout.swift`), accepts a timeout only when it is finite, greater than 0, and at most `WaitTimeout.maximumSeconds` = 86400 s (one day: longer than any tool call should block, far inside `Duration`'s range). `WaitTimeout.duration(_:)` converts only an accepted value, through `Int64` milliseconds, so it cannot trap. The CLI checks it in `validate()` on `pane split`, `tab new`, `server start` and `server attach` (usage error, exit 64, `--timeout must be a positive number of seconds` / `--timeout must be at most 86400 seconds`), and `CommandWaitCLI.validationError` uses it too. The app never trusts the wire value: `commandWaitResponse` refuses an out-of-range `waitTimeoutSeconds` with `ok:false "wait timeout must be …"` before any Pane or Tab is created, and `runCommandWait` now takes the checked `Duration`. Plain JSON cannot carry infinity or NaN (`JSONDecoder` rejects `1e999`), so those arrive only as a malformed request; `1e300` decodes and is now refused instead of trapping. **Orchestrator decision: the pre-existing `server start/attach --wait` path, which had the identical `Int(timeout * 1000)` trap, is fixed here** rather than filed separately: `serverResponse` refuses an out-of-range timeout before starting or attaching, and `firstStateLeavingStarting` returns nil at once for one. `CapabilitiesPropertyPayload` gained an optional `maximum` (emitted as JSON Schema `maximum` in MCP tool schemas and enforced by MCP argument validation, `MCPArgumentError.aboveMaximum`); every `--timeout` advertises `maximum: 86400` and states the bound in its description. Still no `minimum`, because the lower bound is exclusive. `releaseTerminalView`'s doc comment is back on its own declaration (the release-observer members now sit above it), and its idempotence line says observers run on every call.

## Expected behavior

- `pane split -c CMD --wait [--timeout S]` and `tab new -c CMD --wait [--timeout S]` (default timeout 600 s) start the user's shell, type `CMD` into it (the Server Pane's mechanism), and reply when OSC 133 `D` arrives for that command, with `{paneID, tabID, exitCode, durationMs}`. The CLI exits 0 when the command exited 0, and prints the reply either way; a non-zero command exit is reported in the reply, and the CLI exits 4 with `command exited N`.
- Without `--wait`, `-c` keeps today's behavior (command in place of the shell, held open after exit).
- After the command, the Tab keeps its shell at a prompt, so the user can scroll and keep working there.
- Timeout: exit 4 with "still running after S seconds", and the command keeps running.
- No shell integration (fish and others): fail fast with a clear error before typing anything, rather than waiting forever. Recommended detection: the resolved shell's basename is not `bash` or `zsh`.
- The CLI's request is cancelled if the CLI process is killed; the command keeps running.
- Through MCP the tool call blocks for the same duration; MCP cancellation (`notifications/cancelled`) ends the wait, not the command.

### Decisions (with reasons)

1. **XPC shape: one blocking request/reply, no run id and no separate wait verb.** This follows the `server start --wait` precedent (`AppXPCService.serverResponse`, `firstStateLeavingStarting`). `NSXPCConnection` has no reply timeout of its own. The only bound is the CLI's `XPCOnce.wait(timeout:)`, so the CLI passes `timeout + 10` s and the app enforces the real timeout on its injected clock. A streaming reply would add a second protocol shape for no gain, because there is exactly one result. A `wait <runID>` verb would let an agent wait again after a timeout, but it needs run bookkeeping and expiry, which 1.5.0 doesn't need. It can be filed later if agents ask.
2. **CLI killed → the wait is cancelled and the command keeps running.** `perform` captures `NSXPCConnection.current()`'s `ObjectIdentifier` synchronously, before its `Task`. The registry gains an unregister-handler hook that cancels that Task. The waiter removes its observers and replies `ok:false "wait cancelled: client disconnected"` into the dead connection, which also gives the test a completion signal. Nothing is sent to the Tab. **Tab or Pane closed during the wait** → `waitResult: tabClosed`. **Batty quits** → existing `appTerminating`, exit 5.
3. **Timeout:** `--timeout S`, a positive `Double`, default **600**. Valid only with `--wait`. When it passes, the app replies `ok:true` with the ids and `waitResult: timedOut`, and the command keeps running. If the line was never typed by then (no OSC 7 from the shell), the result is `shellNotReady`.
4. **Exit codes.** A wait outcome is always an `ok:true` reply carrying the ids, so the CLI prints the reply (`--json`) or the id (plain) in every case. It then maps the outcome:
   - `exited` with 0 → exit 0.
   - `exited` with N → stderr `batty: command exited N`, exit 4.
   - `exited` with no code → `batty: command finished without an exit status`, exit 4.
   - `timedOut` → `batty: still running after S seconds`, exit 4.
   - `shellNotReady` → `batty: not started after S seconds: the shell has not reported ready (shell integration missing?)`, exit 4.
   - `notStarted` (Dismissed, the shell exited first, or input refused) → `batty: the command was not run`, exit 4.
   - `tabClosed` → `batty: the tab closed before the command finished`, exit 4.

   Refusals before anything is created (unsupported shell, hidden Pane, multi-line command, `--wait` without a command) are `ok:false` failures, exit 4. The CLI never exits with the command's own status: 4 stays "request failed" in `capabilities`' exit-code table, and the status is in the JSON.
5. **Unsupported shell:** refused app-side, **before the Pane or Tab is created**, because only the app knows the resolved shell (Settings default shell, then `$SHELL`). The check is a pure `CommandWaitShell.supportsShellIntegration(_:)`: take the first whitespace-separated token, strip a leading `-`, and accept the basename only if it is `bash` or `zsh`. Everything else is refused, including `env …`, `sh`, fish, elvish and nu. Message: `--wait needs bash or zsh; the default shell is <basename>, which has no shell integration in Batty`.
6. **Hidden Pane** (`tab new --wait` into a Pane with `isHidden`): refused, `pane is hidden; show it with batty pane show before using --wait`. Batty does not un-hide it, because that would be a visibility side effect the caller didn't ask for. `pane split --wait` always creates a new visible Pane.
7. **`-c` without `--wait`:** unchanged. The command runs in place of the shell, with `wait-after-command`. With `--wait`, the Tab is an ordinary shell Tab (no `command`), the line is armed through `armStartupCommand`, and the shell stays at a prompt afterwards.
8. **Which D counts:** the first D after the line was typed. The waiter registers its D observer before arming and ignores every D until the delivery's `willType` event. `willType` fires synchronously in the same main turn, immediately before `runLine`. A D for our line can arrive only on a later `ghostty_app_tick` turn, so the order is race-free.
9. **Reply fields** (all optional, so older readers still decode):
   - `TabNewReply` gains `exitCode: Int?`, `durationMs: Int?` (libghostty's `durationNanos / 1_000_000`) and `waitResult: CommandWaitResult?`.
   - `PaneSplitReply` gains `tabID: UUID?`, set on every created terminal Pane, not only with `--wait`, plus the same three fields.
   - `CommandWaitResult` is a `String` enum: `exited`, `timedOut`, `shellNotReady`, `notStarted`, `tabClosed`.
   - Requests gain `wait: Bool?` and `waitTimeoutSeconds: Double?`, the field names `ServerStartRequest` uses.
10. **`pane split --json`** is added. Without it an agent cannot see `exitCode`. Side effect: the MCP catalog now appends `--json` to `pane_split`, so its tool output becomes JSON instead of a bare id, the same as `tab_new`. That is acceptable and more useful.
11. **MCP:** no new code. The tool call blocks for the CLI's run. On `notifications/cancelled`, `SubprocessToolRunner` sends SIGTERM to the CLI. Its XPC connection then invalidates and decision 2 cancels the app-side wait, so the command keeps running. MCP clients apply their own tool-call timeouts, and the limits vary by client (not verified here). So the `wait` property description tells the agent to pass a `timeout` below its client's limit. Exit 4 reaches the agent as `isError` with the stderr line and the JSON stdout, which includes `exitCode` (`MCPServer.finishCall`).
12. **Feature flag: none, matching #0667's decision 1.** `--wait` is a finished option on two ungated verbs. Gating one option inside an ungated verb would need a second schema and a second command type for #0669 to undo. This overrides acceptance criterion 3 and **needs the user's nod**.
