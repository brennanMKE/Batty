# 0632 — The DMG opens as a plain window with two icons, with no artwork guiding the drag to Applications

| | |
|---|---|

## Description

When a Batty DMG is mounted, Finder shows a plain white window with the app and an Applications link. Nothing tells the user to drag one onto the other. Polished Mac apps use a designed window instead: background artwork with an arrow and "Drag to Applications" text, icons placed exactly, and a fixed window with no toolbar or sidebar. User request, verbatim:

> "Create an issue to improve the .dmg to be on par with the apps which go much further with what can be done with a .dmg image."

Earlier context from the user:

> "I mean to add more design to the output. Some apps have some artwork in the .dmg that shows when it is mounted directing the user to drag the app to Applications. How could we do this?"

Neither DMG path passes a background image today. The Release path tries to lay out the window but often falls back to no layout, and the Beta path never lays it out.

## Current behavior (verified against `9ae0f2d5`)

Both DMG paths use `create-dmg` 1.3.0 (Homebrew, `/opt/homebrew/bin/create-dmg`). Its default output format is `UDZO`. Neither `dmgbuild` nor `appdmg` is installed on this Mac.

**Release — `scripts/release.sh`**

- `scripts/release.sh:86-93` requires `create-dmg` and `fileicon`.
- `scripts/release.sh:461-469` uses the built `AppIcon.icns` from the app bundle as the volume icon and the DMG file icon.
- `scripts/release.sh:489-502` (`create_release_dmg`) passes `--volname "Batty"`, `--volicon "$APP_ICON"`, `--window-pos 200 120`, `--window-size 600 400`, `--icon-size 100`, `--icon "$APP_NAME.app" 175 190`, `--hide-extension "$APP_NAME.app"`, `--app-drop-link 425 190` and `--no-internet-enable`. **It passes no `--background`**, so even a successful layout is a white window.
- `scripts/release.sh:487-488, 504-511`: the layout step runs Finder AppleScript, which can fail with `Can't get disk (-1728)`. The script then retries with `--skip-jenkins`, which skips the layout entirely: no window size, no icon positions, no hidden extension. A shipped release DMG can therefore have no layout at all, and the log only shows a warning.
- The order after creation is: `codesign` the DMG (`:514-515`), notarize (`:520`), staple and validate (`:525-526`), `spctl` assess (`:529`), rename to `Batty-<sha>.dmg` (`:532`), then `fileicon set` the DMG file icon (`:538-539`). `fileicon` writes only to the DMG file's resource fork and extended attributes, so the signature and the staple stay valid (`:534-537`).

**Beta — `scripts/build-beta.sh`** (`./build.sh package --sign --notarize`, #0506)

- `scripts/build-beta.sh:293-294`: volume name `Batty Beta`, and the work file is `dist/Batty Beta.dmg`.
- `scripts/build-beta.sh:447-465` **always** passes `--skip-jenkins` (`:450-452` explains why: the same -1728 failure). It passes `--volname`, `--volicon`, `--icon-size 100`, `--app-drop-link 425 190` and `--no-internet-enable`, but no `--window-size`, `--icon` position, `--hide-extension` or `--background`. Beta DMGs never get a layout. The `--icon-size` and `--app-drop-link` coordinates are ignored without the Finder step.
- `scripts/build-beta.sh:498` sets the DMG file icon with `fileicon`, ignoring failure.

**The two paths disagree.** The window geometry is written in two places, and the Beta path has a subset of the Release options. There is no shared layout definition.

**Hand-made test DMGs** (the developer's `hdiutil create` from a folder holding the app and an `/Applications` symlink) have no `.DS_Store` either, so they open as a default icon-view window.

**Verification:** `scripts/verify-dmg.sh` (228 lines) checks stapling (`:44`), DMG `spctl` (`:52`), the DMG signature (`:64`), a quarantined-copy `spctl` (`:77`), and then mounts the image (`:87`) to check the app's signature, entitlements and notarization, and each nested Mach-O. It checks nothing about the window layout.

**Artwork:** `Artwork/` holds `AppIcon.png`, `AppIcon-original.png` (1024²), `AppIcon-glow1.png`, `AppIcon-glow2.png` (1254²) and `BattyLogo.png` (1024²). There is no DMG background artwork.

**Likely cause of -1728 (unconfirmed):** `create-dmg` drives Finder through `osascript`. That needs the calling process (the terminal running the script) to have Automation permission for Finder, and it needs Finder to have noticed the freshly attached volume. Either can fail on a headless or new machine, or in the VM. Any Finder-scripted approach has the same weakness.

## What well-designed app DMGs do (requirements and options)

These are the features to consider. The plan picks which ones to build, after the user answers the open questions below.

1. **Background artwork** with an arrow from the app to Applications and short text such as "Drag Batty to Applications". Provide it at 1x and 2x and combine them into one HiDPI TIFF (`tiffutil -cathidpicheck bg.png bg@2x.png -out background.tiff`), so it is sharp on Retina displays. The background sits in a hidden `.background/` folder on the volume.
2. **Exact icon placement and size.** The app and the Applications link sit on the arrow's two ends, at an icon size (for example 128) that matches the artwork. Text size and label position are set to match.
3. **A fixed window.** Hide the toolbar, sidebar, path bar and status bar. Fix the window position and a content size that matches the background (for example 660×400 points), and set the icon view so there is no scrolling or grid snapping.
4. **A custom volume icon** (`.VolumeIcon.icns`), as today, plus the DMG file icon set by `fileicon` after stapling, as today.
5. **Hidden `.app` extension** on the app icon.
6. **Dark mode.** Finder does not swap a DMG background for dark mode, and icon labels are drawn in the system label colour. The artwork must keep the labels readable in both appearances: use a mid-tone or tinted background with a label plate, or put labels on a light area of the art. The visual check below covers both appearances.
7. **Optional licence agreement (SLA)** shown before mounting. `dmgbuild` can embed one. Many apps leave it out, because it adds a click and the licence is already in the app.
8. **A Beta variant** visually marked "Beta": a ribbon or tint on the background, and the Beta app icon. It should be built from the same layout as Release, with only the art and names changed.
9. **One shared layout definition** used by both `release.sh` and `build-beta.sh`: for example, one `dmgbuild` settings file with variant parameters, or a shared helper script. Geometry should be defined once.
10. **Deterministic, headless creation with no Finder and no AppleScript**, so it works on any Mac, over SSH and in the Tart VM, and never silently falls back to an unstyled DMG. Options to compare:
    - **`dmgbuild`** (Python): writes `.DS_Store` and the background alias directly with its `ds_store` and `mac_alias` modules. It does not need Finder. It supports background images (PNG/TIFF, HiDPI), icon positions and size, window rect, hidden toolbar/sidebar/status bar, hidden extensions, a volume icon, licences (SLA), and formats `UDZO`/`UDBZ`/`ULFO`/`ULMO`. The cost is a Python dependency, which must be pinned (a venv or `pipx` with a fixed version), and a check that it supports macOS 27.
    - **`create-dmg`** (current): supports `--background`, but every layout feature depends on Finder AppleScript. The -1728 failure and the silent `--skip-jenkins` fallback are the problem. Keeping it would need a fix for the Automation/timing cause and a hard failure instead of a fallback.
    - **`appdmg`** (Node): writes `.DS_Store` without Finder, but it adds a Node dependency and has been unmaintained for years.
    - **A committed template `.DS_Store`**, copied onto a hand-built volume: no dependency, but the file is opaque binary. It also stores an alias to the background that is tied to the volume name, so each variant needs its own, and it is hard to review.
11. **Compression format and size.** `ULFO` (lzfse, macOS 10.11+) or `ULMO` (lzma, macOS 10.15+) give smaller files than the current `UDZO`, and Batty requires macOS 15.6+, so both are safe. Record the before and after sizes. Sparkle's appcast `length` comes from the DMG via `scripts/appcast-item.sh`, so it needs no change.
12. **Signing order is unchanged.** Create the DMG, `codesign`, notarize, staple, `spctl`, rename, then `fileicon`. `scripts/verify-dmg.sh` must still pass on the new DMG. If the plan adds a layout check to `verify-dmg.sh` (for example that `.DS_Store` and `.background/` exist on the mounted volume), it must be read-only and work headless.
13. **Visual acceptance evidence.** A screenshot of the mounted DMG window, captured **inside the Tart VM**, never on the host, in both light and dark appearance. Attach it to this issue as `0632/dmg-light.png` and `0632/dmg-dark.png`.

## Constraints

- **`scripts/` is a restricted area** (`AGENTS.md`, "Restricted areas"). This request gives the user's confirmation to change `scripts/release.sh`, `scripts/build-beta.sh` and `scripts/verify-dmg.sh`, and to add DMG layout files under `scripts/`, for this issue's purpose only. **It does not authorize running `scripts/release.sh` or notarizing.** The implementer must get the user's go-ahead each time before either. Test the DMG layout with an unsigned or locally signed DMG (`./build.sh package --sign` without `--notarize`, or `--notarize --no-submit`) first.
- **`Artwork/` is user-curated.** Before anything is committed to `Artwork/` or used by the scripts, present the background artwork options to the user for a choice: a design canvas with 3–4 background options, each shown at the real window size with the icons in place, in light and dark appearance, plus the Beta variant. Commit only the option the user picks, at 1x and 2x, with its source file.
- **No UI scripting on the host** (`AGENTS.md`, "UI test automation"). Don't run `osascript`/System Events against Finder on the host to lay out or screenshot the DMG. The headless tool needs none, and screenshots come from the VM.
- **Developer ID rules apply** (`AGENTS.md`). DMG signing keeps the existing Manual identity. Never pass `-allowProvisioningUpdates` and never touch certificates.
- New tool dependencies (for example a pinned `dmgbuild`) are checked for in the scripts' preflight with a clear install message, like the existing `create-dmg`/`fileicon` checks, and documented in `scripts/RELEASE.md`. `scripts/preflight.sh` (#0100) and the credentials/replication notes (#0306) should list them too.

## Acceptance criteria

- [ ] A mounted Release DMG opens to a fixed-size window, with no toolbar, sidebar or status bar, showing the chosen background artwork, the Batty icon (extension hidden) and the Applications link at the art's marked positions.
- [ ] A Beta DMG opens to the same layout, visibly marked "Beta", with the Batty Beta name and icon.
- [ ] Both are produced from one shared layout definition. No window geometry or icon coordinates are written in two places.
- [ ] DMG creation uses no Finder and no AppleScript, and never falls back silently to an unstyled DMG. If the layout can't be applied, the script fails.
- [ ] The background is sharp on a Retina display (HiDPI TIFF or equivalent), and the labels are readable in both light and dark appearance.
- [ ] `scripts/verify-dmg.sh` passes on a signed, notarized, stapled DMG from the new path (run only with the user's go-ahead for notarization). The DMG file icon is still set after stapling.
- [ ] The DMG format decision (`UDZO`/`ULFO`/`ULMO`) is recorded, with before and after sizes.
- [ ] VM screenshots of the mounted window in light and dark mode are attached under `issues/0632/`.
- [ ] `scripts/RELEASE.md` describes the new DMG step and its dependency.
- [ ] The chosen artwork (source plus 1x/2x exports) is in `Artwork/`, only after the user picked it.

## Open questions for the user

1. **Artwork direction.** Should the background match the app icon's glow style, be a minimal flat background with an arrow, or be terminal-themed (for example a dark terminal-window motif with the "drag" instruction typed out)? The plan should produce a canvas of 3–4 options to pick from before committing anything.
2. **Beta variant.** Should the Beta DMG have its own marked artwork (a ribbon or tint), or use the same art with only the name and icon changed?
3. **Licence agreement (SLA).** Should one show before mounting, or not? The recommendation is no, unless there is a legal reason.
4. **Tool choice.** Is the recommendation, `dmgbuild` (pinned Python dependency, fully headless), acceptable? Or should Batty stay on `create-dmg` and fix the Finder step, or use a committed template `.DS_Store` to avoid any new dependency?
5. **Compression.** Switch to `ULFO`/`ULMO` for a smaller download, or keep `UDZO`?
6. **Target release.** Should this land on `main` for the next minor, or also be cherry-picked to `release/1.2` for the next patch release?
