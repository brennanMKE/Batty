## Description

The second concrete non-terminal view: a **Process Status view** — similar to Activity Monitor, but focused on a single selected app or process rather than the whole system. Like #0304 it is design-gated per the #0301 umbrella: visual designs are drafted and approved by the user before implementation starts.

Phase 2 has not started and must not start until the user approves.** Status stays `in-progress`, not `resolved` — #0301's acceptance criteria require the design-first gate to have actually held, and the user's approval is that gate. Deliverables: `docs/design/process-status-view.md` and `docs/design/process-status-view.html` (six states: pinned healthy, following-a-terminal healthy, exited tombstone, permission unavailable, no process selected, high-churn mid-sample with disclosures expanded).

### The feasibility spike — the thing that could have invalidated the design

Run first, as throwaway scripts kept out of the repo, and **independently reproduced by the reviewer**:

- **`task_for_pid` fails for every target.** `kr=0` for self; `kr=5` (`KERN_FAILURE`) for same-uid Finder, an interactive same-uid zsh, and root `launchd`. Same-uid does not help. This matches the `0x5` already in Batty's own log.
- **libproc works without a task port, and is cheap.** `proc_pidinfo`, `proc_pid_rusage`, `PROC_PIDLISTFDS`, `PROC_PIDFDVNODEPATHINFO`, `proc_pidpath`, `sysctl(KERN_PROCARGS2)` all return in 0.001–0.18 ms; a full core sample is ~0.03 ms. Child discovery has no direct call — it means enumerating ~820 pids and filtering `pbi_ppid` — at 0.3–1.5 ms.
- **Numbers cross-checked against independent tools.** Finder's `phys_footprint` matched Apple's own `footprint` CLI exactly; resident size matched `ps -o rss` exactly.
- **No shell fallback needed.** `ps` costs 65 ms/call and `top -l 1` costs 400 ms — three to five orders of magnitude worse than libproc, with no capability gap to justify it.
- **Failure modes are distinguishable at the kernel**: an exited pid gives `ESRCH`, a different-uid process gives `EPERM`. The tombstone and permission-denied states key off those directly rather than inferring.
- **Scope is honestly same-uid only — and that bites in Batty's own architecture.** Batty's pty session leader is a root-owned `/usr/bin/login`, so the permission wall is reachable in ordinary use, not hypothetical.

The `task_for_pid`-allow entitlement route is recorded as **carried from the issue text, not spike-verified** — testing it would need a signing change.

### The three decisions, for the user to accept or redirect

1. **Which process** — two modes. *Pinned* (CLI `--pid`) tombstones on exit and never guesses a successor. *Following a terminal* (the default) re-resolves `foregroundPid` every tick rather than freezing at creation, which removes successor bookkeeping entirely and also sidesteps the sibling-erosion problem #0304 hit, since it binds to a Tab id rather than a position in the split tree.
2. **What it shows** — bounded strictly by the spike. CPU%, `phys_footprint` and resident memory, thread count and open-file count sampled every tick; full fd paths, child list and full command line as on-demand disclosures, because those are a different cost class. No process control — no kill, no renice, not even stubbed.
3. **Refresh** — 1 second, a UX choice rather than a cost constraint. `tearDown()` is a plain `Task.cancel()`; no subprocess is spawned anywhere in this design, so none of #0304's bounded-wait `Process.terminate()` machinery is needed.

### Review

`claude-opus-5`, two rounds.

## Design-phase questions (to answer in the design phase, not decided here)

1. **Which process, selected how?** Options to lay out: the foreground process of a sibling terminal Pane — the 1.3.2 libghostty-spm bump (#0286) exposes `foregroundPid` (`tcgetpgrp` on the pty) and `ttyName` as public `TerminalView` properties, and #0297 records them as reachable via `TabRuntime.terminalNSView` (capture deferred there, not implemented) — versus an explicit process picker, versus a pid/name supplied by the CLI at creation. The design also has to answer what the view does when the selected process exits (follow the successor foreground process? show a tombstone?).
2. **What it shows.** CPU, memory footprint, thread count, open files, child processes — and which of these are worth the cost of sampling (open files and child-process trees are much more expensive to enumerate than CPU/memory).
3. **Refresh cadence.** Sampling is a direct, recurring compute cost — exactly the kind of cost the #0303 lifecycle exists to govern. The design must state the visible-refresh interval, and per #0303 the sampler suspends entirely while the Pane is hidden and tears down on close.

## Feasibility risk: reading another process's stats is restricted (settle this first)

This is the one question that can invalidate the whole design late, so it must be settled early, empirically:

- Inspecting **another** process's memory requires a Mach task port, and `task_for_pid` is restricted on modern macOS even for an unsandboxed app running as the same user. This is not hypothetical for Batty: the session that filed this issue observed exactly that failure in Batty's own log — `Unable to obtain a task name port right for pid 607: (os/kern) failure (0x5)`.
- #0290's `FootprintReader` does **not** generalise: it reads **the app's own** `phys_footprint` via `task_info(mach_task_self_, TASK_VM_INFO)` (`BattyKit/Sources/BattyKit/Runtime/FootprintReader.swift`, verified 2026-08-04) — `mach_task_self_` is the one task port every process gets for free. There is no existing Batty code that reads another process's memory.
- The design must therefore establish, with a small spike before any mockup is treated as buildable: whether libproc calls that skip the task port (`proc_pidinfo`, `proc_pid_rusage`) return what the view needs for same-user processes; whether shelling out to `ps`/`footprint`/`top` is the pragmatic fallback and at what sampling cost; whether any entitlement could help (the `task_for_pid`-allow route is effectively private/dev-only and likely a dead end for a notarized app); and whether the feature is honestly scoped to processes the user owns.

Whatever the spike finds bounds question 2 above — the metrics shown must be the metrics actually obtainable.

## Fix

**`ProcessInspector`** (`BattyKit/Sources/BattyKit/Runtime/ProcessInspector.swift`)
— a dependency-free wrapper over the libproc/sysctl calls the phase-1
spike proved obtainable for a same-uid target without a Mach task port:
`PROC_PIDTASKINFO` + `proc_pid_rusage`/`RUSAGE_INFO_V4` for core metrics
(resident size, `phys_footprint`, thread count, cumulative CPU time),
`proc_pidpath`/`proc_name` for identity, `sysctl(KERN_PROCARGS2)` for full
argv, and on-demand-only `PROC_PIDLISTFDS`/`PROC_PIDFDVNODEPATHINFO` and
`proc_listallpids`-based child enumeration. Failures are classified from
the kernel's own errno (`ESRCH`/`EPERM`), matching the design's insistence
on real kernel signals over inferred state.

Re-verifying these calls against a live process while implementing (not
just trusting the design doc's transcribed numbers) surfaced two
API-shape traps neither the design doc nor the original spike narrative
called out explicitly:

- **`proc_listallpids`'s return value is a *pid count*, not a byte
  count** — every other `proc_pidinfo` flavor in this file returns bytes
  filled, and dividing this one by the descriptor stride (the naturally
  consistent-looking thing to do) silently truncated the process list to
  roughly a quarter of its real size.
- **`PROC_PIDLISTFDS`'s zero-buffer size-probe call reports the fd
  *table capacity*, not the count of descriptors actually open** — for
  the same process at the same instant, the probe and a real fetch's
  returned byte count disagreed by more than 10x. Fixed by allocating a
  generously-sized buffer directly and trusting the real fetch's return
  value, never the probe.

Both were caught by writing and running a disposable Swift probe script
against this machine before wiring the calls into `BattyKit` — the same
methodology the phase-1 spike itself used — rather than transcribing the
design doc's numbers on faith.

**`ProcessStatusPaneContent`**
(`BattyKit/Sources/BattyKit/Runtime/ProcessStatusPaneContent.swift`) — the
model-owned `PaneContentLifecycle` conformer. Implements both selection
modes: `.pinned(pid)` (tombstones on `ESRCH`, never guesses a successor)
and `.followingTab(tabID)` (re-resolves `foregroundPid` every tick via an
injected `tabLookup` closure, tombstoning only when the lookup itself
misses — the followed tty going away, not any single command exiting
within it). `setUp(visible:)` never starts work it would immediately
suspend; `setVisible(false)` cancels the 1s sampling `Task` with nothing
left running or open; `setVisible(true)` resumes and refreshes
immediately; `tearDown()` is synchronous and idempotent. No subprocess
anywhere — every call is synchronous and sub-millisecond, so the sampling
loop runs directly under this package's `MainActor` default isolation,
with no dispatch-queue hop.

**Model/wire wiring**:

- `PaneRuntime` gains `processStatusContent` (non-nil exactly when `kind
  == .processStatus`) and calls `setUp(visible: !isHidden)` exactly once,
  at construction — the one visibility fact knowable that early.
- `SplitTree.makePane` resolves the new pane's initial target: an
  explicit pid pins mode A; otherwise mode B follows the split-source
  pane's active Tab, matching the design's "previously-focused Pane's
  active Tab." A `tabLookup` closure threaded from
  `SplitTree.splitPane(id:...)` (which has `self` in scope) lets the
  content resolve tabs anywhere in the tree by id on every tick, without
  holding a strong `TabRuntime` reference — the same by-id pattern
  `WindowRuntime` already uses.
- `PaneSplitRequest` gains an optional `processStatusPid` field (`nil`
  omits the JSON key, matching `kind`'s existing convention).
  `batty pane split --view process-status --pid <pid>` threads it end to
  end through `AppServiceClient` → `AppXPCService` →
  `AppStateStore.splitPane`. `--pid` is rejected client-side (exit `1`)
  for any other `--view` kind. This is new CLI surface beyond what the
  design document scoped to phase 2 (it deliberately left the exact verb
  shape to `#0315`, already resolved without a `--pid` flag) — added here
  because mode A (the tombstone-on-exit case) is otherwise unreachable
  from the CLI, and the design explicitly names both modes as
  first-class.
- `WindowRuntime.hidePane`/`showPane`/`closePane` call
  `setVisible(false)`/`setVisible(true)`/`tearDown()` on a
  `.processStatus` pane's content at the same choke points the terminal
  path already uses (`docs/pane-view-lifecycle.md` §5 — teardown's call
  site is `closePane`, not a view's `onDisappear`). `showPane`'s explicit
  call is a deliberate departure from the terminal path's own asymmetry
  (which relies on `TerminalPlaceholderView`'s remount): a plain model
  object has no equivalently cheap remount to piggyback on, so this
  follows `hidePane`'s more robust shape instead, per the design
  document's own explicit permission to do so.

**View**: `ProcessStatusPaneView`
(`BattyKit/Sources/BattyKit/Views/ProcessStatusPaneView.swift`) — header
(name/pid, mode indicator, state chip, "Choose Process…"), always-on core
metrics, a copyable command-line row, on-demand disclosures (open files,
child processes — fetched only when expanded, never per tick, per the
design's O(fd count)/O(system size) cost distinction), and first-class
exited/permission-denied/no-selection banners. The permission-denied
banner shows only what §1.6 proved obtainable at that tier (executable
path + a basename-derived display name) — never a process name or
command line from the metrics tier, which is the exact class of defect
phase-1 review caught in the original mockup (displaying data the spike
had proved unobtainable). "Choose Process…" offers "Follow a Terminal
Pane…" (this session's terminal panes) and "Pick a Running Process…"
(`ProcessInspector.allSameUserProcesses()`), both calling
`content.retarget(to:)`; a child-process row's "Watch this instead"
pivots the pane to mode A pinned on that child. `PaneView.body`'s
kind-switch routes `.processStatus` to this view; `nonTerminalBody` was
factored into a shared `nonTerminalShell(content:)` helper so the
drag-handle/eye-button/click-to-focus chrome stays identical across every
non-terminal kind. Every other kind is unaffected.

## Review

**Round 1: `claude-opus-5` — REQUEST CHANGES.** Confirmed the build and
1100/122 test results, re-ran the kernel measurements independently
rather than accepting the narrative (which is what surfaced the top
finding), confirmed both libproc API-shape fixes from the first
implementation round were real and correct, cleared
`docs/swiftui-observation-rules.md` compliance entirely, judged the
permission-denied path genuinely §1.6-faithful, and rated the
`samplingStopsWhileSuspendedAndResumesWhenShown` rewrite sound. The
findings were all in the numbers the view displays:

- **B1 (blocking, fixed).** `ri_user_time`/`ri_system_time` are mach-
  absolute-time ticks, not nanoseconds — the previous code divided the
  raw value by `1_000_000_000` directly, under-reporting CPU% by ~42x on
  this machine (independently re-measured by the reviewer: `numer=125
  denom=3`; a process pegging one core read 2.4% instead of the correct
  99.97%). Fixed with a `MachTimebase` conversion in `ProcessInspector`,
  confirmed via a direct busy-loop CPU-value test — the first test in
  this issue to assert an actual CPU number rather than merely "some
  `Double` got set," which is exactly the gap that let this ship.
- **B2 (blocking, fixed).** The CPU-delta baseline wasn't keyed by pid,
  so mode B's tick-to-tick pid changes could delta one process against
  another's accumulated total. Now keyed by pid; a pid change resets the
  baseline instead of computing a cross-process delta.
- **B3 (not fixed here, by design).** Session-close teardown is shared
  across all four pane kinds and owned by #0314, which merges first —
  explicitly deferred to the rebase.
- **B4 (blocking, fixed).** `startSampling()` only guarded `runState`
  before the immediate sample, not after — a target that tombstoned on
  its very first sample still went on to schedule the periodic `Task`,
  which re-detected the same exit a tick later. Fixed with a second
  guard; regression-tested via the `isSamplingTaskAlive` testability
  hook, not just by re-reading state after a wait.
- **B5 (blocking, fixed).** The exited banner asserted a fabricated exit
  timestamp (`Date()` at detection time) instead of the design's own
  "timestamp of the last successful sample." `RunState.exited` no longer
  carries a Date at all; the view reads `snapshot?.capturedAt` directly,
  labelled "last seen."
- **S1/S2/S3/S5 (should-fix, all fixed).** `openFileCount` is now
  `Int?` (a failed read no longer renders as a plausible `0`); the fd
  listing no longer caps allocation at a hardcoded 4096 and instead
  grows from the (over-reporting, therefore safe-as-an-upper-bound)
  probe; `errno` is cleared before every call this file classifies by
  errno; the always-per-tick core-metrics path now calls a count-only
  helper instead of the full path-resolving listing.
- **S4 (should-fix, fixed).** The running-process picker enumerated the
  whole process table as a plain statement inside a computed property
  that `body` re-evaluated every second. Replaced the nested `Menu` with
  a `Button` whose action populates an `@State` cache exactly once, on
  an actual click, presented via `.popover`.
- **F1 (security-adjacent, fixed now rather than deferred).**
  `parseProcArgs2` only decremented its remaining-argv counter for a
  non-empty argument, so a process invoked with a zero-length argv
  element left the parser one terminator short of `argc` and it kept
  consuming bytes into the environment block immediately following argv
  in the same buffer — appending environment strings onto a copyable
  "Copy Command Line." Fixed by decrementing on every terminator;
  pinned with two hand-built `KERN_PROCARGS2`-shaped buffers.
- **`--pid`/`processStatusPid` scope addition: approved, with two
  caveats**, both addressed: a `pid > 0` validation was added
  client-side (previously `--pid 0` and negatives surfaced as a
  confusing permission-denied state instead of a CLI parse error), and
  the reviewer noted a fifth flat per-kind wire field is the wrong
  long-term shape — recorded on #0301 for a future `viewOptions`
  generalization, not this issue's to solve.
- **Test gaps closed:** a direct CPU-value assertion (not just "non-nil"),
  a direct `Task`-liveness check via `isSamplingTaskAlive` (proving a
  regression that silently removed `stopSampling()` from the hide path
  would be caught — round 1 found the existing behavioral test alone
  would not have caught it), and a legacy-JSON decode test for
  `processStatusPid`'s absence.
- **Filed as follow-ups, not fixed here (per the reviewer's own
  triage):** F2 (`.unexpected(errno:)` freezing the pane under a green
  "Running" chip), F3 (disclosures rendering in `.exited`), F4
  (`isAlive(pid:)` conflating `EPERM` with `ESRCH`), F6 (`tabLookup`'s
  default `{ _ in nil }`), and the empty `.help("")` tooltip in
  `ProcessStatusPaneView`.

One test (`cpuPercentReflectsSubstantialRealCoreUsage`, added to close
the CPU-value test gap) needed a follow-up fix of its own during this
round: burning CPU inline inside the `@MainActor`-isolated test body
blocked that single serial queue for its whole 1.2s duration, which
starved every other MainActor-isolated test running in the same
parallel batch — observed directly as a previously-stable timing test
flaking only after this test was added. Moved the busy loop to a
detached `Task` (off MainActor); stable across 7+ subsequent full-suite
runs (`swift test` and `scripts/build.sh unit`) afterward. Also lowered
the test's own pass threshold from >40% to >10% after a legitimate
~39.5% reading under real multi-process contention on this shared
machine — still ~4x clear of what B1's bug would have produced (~1-2%).

## Review round 2

**`claude-opus-5` — one BLOCKING finding, everything else confirmed
correct by independent measurement.** The reviewer confirmed the build/
test results, independently re-measured B1 (2.40% as-ns vs. 99.92%
tick-converted, `numer=125 denom=3`) and confirmed no second uncorrected
conversion site remained, and confirmed B2/B4/B5/S1-S5 and the `--pid`
client-side validation all held.

- **F1 was not fully fixed.** Round 1's fix (decrement `remaining` on
  every terminator, including a zero-length argument's) handled a
  zero-length argument at index ≥ 1 but not at index 0: the padding-skip
  loop after the exec path consumed *every* consecutive NUL, so a
  genuinely empty `argv[0]`'s own terminator was indistinguishable from
  padding and got eaten, overrunning into the environment block by one
  slot regardless. Neither round-1 fixture caught it because both placed
  their zero-length argument at index ≥ 1 — "a hand-built buffer only
  proves what this implementer's own model of the format predicts," per
  the review. **Reproduced against a real kernel buffer** (`posix_spawn`
  with `argv = {"", "x"}` and a marker secret in the environment,
  verbatim `parseProcArgs2` run over the real `KERN_PROCARGS2` output) —
  fixed using the kernel's real 8-byte-alignment rule for where argv
  begins relative to the exec-path region, verified across ten exec-path
  lengths by the reviewer. Regression test derives its buffer from an
  actually-spawned process (`posix_spawn`, since `Foundation.Process` has
  no way to set a literal empty `argv[0]`) reading back through the real
  `commandLine(pid:)` path, not a copy of the parser — the two existing
  hand-built fixtures (covering index ≥ 1) still pass unchanged.
- **Filed, not to be fixed here:** `coreMetricsCpuTimeIsPlausibleAfter-
  ConversionNotOffByAMachTimebaseFactor`'s bounds are too loose to
  detect a unit-conversion regression on their own (passed under the B1
  mutation) — the two other B1 tests (the direct `MachTimebase`
  conversion pin, and the real busy-loop CPU-value assertion) cover it;
  this test's own looseness is a separate follow-up, deliberately not
  tightened here.

`#0314` (squash `aca515a`) and `#0313` (squash `b6ae529`) landed on
`main` while this issue was in review, each building shared
non-terminal-Pane infrastructure this issue had built its own
first-mover copy of. Rebased `issue/0305-2` onto `main` twice (once per
merge) and reconciled:

- **`MachTimebase`** — deleted this issue's own duplicate (identical
  implementation) in favor of `#0314`'s (`ProcessCPUDeltaTracker.swift`).
  `ProcessInspector.CoreMetrics` now carries raw mach ticks
  (`cpuTicksUser`/`cpuTicksSystem`) instead of a pre-converted
  `cpuTimeNanoseconds`, so it can feed the shared tracker directly.
- **`ProcessCPUDeltaTracker`** — deleted this issue's own hand-rolled
  pid-keyed CPU-delta baseline (`previousCPUSample`/`computeCPUPercent`)
  in favor of an owned `ProcessCPUDeltaTracker` instance, fed one
  `ProcessSample` per tick via a thin `cpuPercent(for:)` wrapper.
  Verified before deleting, not assumed, that the shared tracker retains
  all four properties the hand-rolled version had: `MachTimebase`
  conversion, pid-keyed baseline reset, the monotonic guard, and
  baseline reset on exit/`EPERM`.
- **`PaneRuntime.content`** — deleted this issue's own `processStatusContent`
  stored property and every `pane.kind == .processStatus` gate in
  `WindowRuntime` in favor of `#0314`'s kind-agnostic `content: (any
  PaneContentLifecycle)?`, with `PaneView` dispatching via `as?`
  alongside `#0314`'s `SystemMetricsPaneContent` cast and `#0313`'s
  `LMStudioDashboardPaneContent` cast in the same `if`/`else if` chain.
  Verified before deleting that `setUp(visible:)` still runs at
  `PaneRuntime.init` and that `showPane`'s explicit `setVisible(true)`
  call is present in `main`'s `WindowRuntime` — both preconditions held.
- **`allPids()`** — now keeps pid 0, matching `#0314`'s
  `ProcessMetricsReader.listAllPIDs()` exactly, confirmed lossless (pid 0
  is root-owned with ppid 0, so it can never match
  `children(ofPid:)`/`allSameUserProcesses()`'s filters).
- **`contentFactory` threading** — `#0313` added an injectable
  `contentFactory` parameter to `SplitTree.makePane`/`splitPane` and
  `AppStateStore.splitPane` (defaulting to the real `PaneRuntime.makeContent`)
  specifically so test code can suppress a real conformer's `setUp()`.
  This issue's own `.processStatus` construction (resolving mode A/B's
  target from `processStatusPid`/the split source, plus the tree's
  tab-lookup closure) needed reconciling with that mechanism: the
  parameter's default was changed from a concrete closure to `nil`,
  distinguishing "no override — resolve automatically per kind" (falling
  through to the `.processStatus`-specific resolution, or
  `PaneRuntime.makeContent` for every other kind) from "caller explicitly
  overrode it" (always honored outright, even for `.processStatus`, so
  `contentFactory: { _ in nil }` reliably suppresses real construction
  regardless of kind). A concrete default value can't be distinguished
  from an explicitly-passed identical one, which is why this couldn't
  stay a non-optional parameter the way `PaneRuntime.init`'s own
  `contentFactory` still is.
- **Four pre-existing test sites patched.** `#0313`'s reviewer enumerated
  three call sites (`CommandPaletteViewActionTests`,
  `SplitTreeTargetedSplitTests`, `AppStateStoreStatusPayloadTests`) that
  construct a `.processStatus`-kind pane as an arbitrary non-terminal
  fixture, through the default factory, never closed — each now a real
  1s sampling `Task` leak now that this conformer exists. An independent
  sweep of the whole test suite found a fourth
  (`RequestCloseTabTests`). All four fixed with `contentFactory: { _ in
  nil }`, plus a permanent `#expect(pane.content == nil)` regression
  check at each site (mutation-tested: stripping one site's argument
  made the suite fail immediately, at the exact call site, rather than
  pass silently — the coordinator's own warning that a missed site
  leaves the suite green while leaking).
- **Four other, genuinely-real-conformer-needing test sites** (three in
  `AppStateStorePaneSplitTests` verifying mode A/B target resolution,
  one in `ProcessStatusPaneLifecycleWiringTests` ending with the pane
  resumed/active) gained explicit `store.closePane(...)` teardown at
  their end, rather than relying on ARC + the sampling `Task`'s
  weak-`self` capture to eventually stop it — `docs/pane-view-lifecycle.md`
  §5's own binding lesson ("a log line claiming teardown happened is not
  evidence it happened," generalized to "ARC eventually collecting it is
  not the same as tearing it down deterministically") applied to test
  code, not just production code.
- **Not a real leak, verified rather than assumed:** this issue's own
  conformer spawns no subprocess at all (confirmed by grep — the only
  `Task` in `ProcessStatusPaneContent.swift` is the sampling loop itself,
  no `Process(`/`posix_spawn`), unlike `#0304`'s Git Status scanner. A
  coordinator message describing this round characterized this issue's
  conformer as spawning "real scanner subprocesses" — that description
  does not match this issue's actual code; flagging the discrepancy
  rather than silently either accepting or ignoring it.

suite-count growth beyond #0305's own tests is `#0314`'s and `#0313`'s,
inherited via rebase, not authored here). `Configuration/Active.xcconfig`
read `#include "Prod.xcconfig"` before and after every build/test run
across all rounds; no `Batty.xcodeproj/project.pbxproj` residue afterward.

Ran the full suite repeatedly across both rounds (both via `swift test`
directly in `BattyKit/` and via `scripts/build.sh unit`) to confirm
stability, not just a lucky pass:

- **Round 1 (implementation):** one timing-sensitive test
  (`samplingStopsWhileSuspendedAndResumesWhenShown`) flaked once under
  full parallel-suite load (its fixed `Task.sleep` windows raced against
  cooperative-thread-pool contention from other tests' synchronous
  subprocess spawns) and was rewritten to poll for the expected state
  change within a generous timeout instead of trusting a fixed sleep
  duration; stable across three subsequent full-suite runs afterward.
- **Round 2 (review round 1's fixes):** adding a real CPU-burning test
  (for the B1 regression check) made that *same* timing test flake again
  — the busy loop, run inline inside an `@MainActor`-isolated test body,
  blocked the single MainActor queue for 1.2s and starved every other
  MainActor-isolated test in the same parallel batch. Fixed by moving
  the loop to a detached `Task` (off MainActor) and widening the
  polling timeout; stable across 7+ subsequent full-suite runs (`swift
  test` ×4, `scripts/build.sh unit` ×2, plus the final verification run)
  afterward, including one legitimate ~39.5%-under-contention CPU
  reading that prompted lowering that test's own pass threshold from
  >40% to >10% (still ~4x clear of what B1's bug would have produced).

Every `ProcessInspector`/`ProcessStatusPaneContent` test runs against
real processes (this test binary itself, `launchd`, and short-lived
spawned/exited children) rather than mocks — including live evidence
that sampling actually stops while a pane is suspended and actually
resumes on show, checked by letting real wall-clock time pass across the
1-second cadence rather than trusting that `setVisible` was called
(`docs/pane-view-lifecycle.md` §5's "a log line claiming teardown
happened is not evidence it happened," generalized to show/hide); a
direct CPU% value assertion against a real busy-looping process (closing
review round 1's test-gap finding for B1); and two hand-built
`KERN_PROCARGS2` buffers pinning the argv/environment boundary directly
(F1).

## Gotchas

- **Cannot verify visually or with UI tests.** This implementer's
  environment has no way to run the app or `scripts/run-ui-tests.sh`.
  Everything above is verified by unit test against real kernel state,
  not by looking at the rendered pane. The manual checklist below is
  owed, not performed.
- **`docs/terminal-pane-requirements.md` §6's manual checklist is owed,
  not run.** This is the second issue (after #0315) to touch
  `PaneView.body`'s kind-switch and the first to add real (non-
  placeholder) interactive content — a `Menu`, `DisclosureGroup`s, and
  buttons — inside a non-terminal pane's body, sitting inside a
  `contentShape(Rectangle())`/`.onTapGesture` container
  (`nonTerminalShell`). Nothing in this implementation round could
  exercise pointer input, click-to-focus-vs-click-a-button priority, or
  the terminal-pane regression checklist in a **mixed-kind session**.
  Needs a manual pass on both a **terminal** pane and a **terminal pane
  alongside a `process-status` pane** before this is truly done, per
  `docs/pane-kinds.md` §6's binding obligation (inherited from #0315,
  which already ran the mechanism-level check; this issue owes the
  per-combination check for its own new interactive content).
- **`--pid` CLI plumbing is new scope beyond what `docs/design/
  process-status-view.md` itself resolved** — that document explicitly
  left the exact verb shape to `#0315`, which shipped without a `--pid`
  flag. **Review round 1 approved keeping it**, with two caveats both
  now addressed: a `pid > 0` client-side validation (`--pid 0` and
  negatives previously surfaced as a confusing permission-denied state
  instead of a CLI parse error), and a note — recorded on `#0301`, not
  this issue — that a fifth flat per-kind wire field on `PaneSplitRequest`
  is the wrong long-term shape; the next kind needing its own creation
  option should trigger a generalization to a `viewOptions` payload.
- **Not fixed on this branch: session-close never tearing down the
  sampler (review round 1's B3).** Confirmed real, but deliberately
  deferred — it's shared across all four pane kinds and `#0314` owns the
  fix (it merges first). Will be inherited via rebase, not fixed here.
- **Rebase plan once `#0314` lands (from review round 1), recorded so it
  isn't lost between rounds:** delete `computeCPUPercent`/
  `previousCPUSample` in favor of `#0314`'s shared per-pid CPU-delta
  tracker (a single-pid map entry is the degenerate case); delete
  `processStatusContent` and its `pane.kind == .processStatus` gates in
  `WindowRuntime` in favor of `#0314`'s kind-agnostic `PaneRuntime.content:
  (any PaneContentLifecycle)?` with ungated lifecycle calls and
  `PaneView` dispatching via `as?` — this turns the `WindowRuntime` diff
  from a merge conflict into a no-op. `ProcessInspector.allPids()` (with
  its `proc_listallpids` pid-count-not-byte-count fix) is expected to
  **survive and replace** `#0314`'s own whole-system enumeration, per
  the reviewer's cross-issue note; `commandLine`/`listOpenFileDescriptors`/
  `children(ofPid:)`/`allSameUserProcesses()`/`SampleFailure` survive as
  the single-pid adapter layered over `#0314`'s shared reader.
- **The non-selected-Session visibility fact is still not wired**,
  matching `docs/pane-view-lifecycle.md` §5's own acknowledged open item:
  a `.processStatus` pane created into a background (non-selected)
  Session's split tree still starts its 1s sampler immediately (`setUp`
  only reads `!isHidden`, not session selection). This is a pre-existing
  gap this issue inherits rather than introduces — no model-level signal
  for "is my Session selected" exists yet to read from `PaneRuntime.init`.
- **Session/window occlusion is not folded into visibility.** Matches
  `docs/pane-view-lifecycle.md` §2's own scope note — a background
  window's visible-but-occluded `.processStatus` pane keeps sampling.
  Same open item the lifecycle design document itself left for a future
  kind to resolve, named there rather than solved here.
- **CPU% clamps to `activeProcessorCount × 100`** rather than a flat
  100 — a multi-threaded target can legitimately exceed one core's worth
  of CPU. Worth a second look in review since the design document doesn't
  specify this clamp explicitly.
- **Gesture-conflict risk between the pane-level `.onTapGesture`
  (click-to-focus) and the view's own interactive controls (`Menu`,
  `DisclosureGroup`, buttons) is unverified.** This is the same shell
  #0334 already uses for the placeholder, which had no interactive
  content to conflict with; `ProcessStatusPaneView` is the first real
  test of that combination and it could only be checked headlessly (it
  compiles and the view logic is unit-tested), not interactively.
- **Filed as separate follow-ups by the reviewer, not fixed on this
  branch:** `.unexpected(errno:)` freezing the pane under a stale green
  "Running" chip instead of surfacing the anomaly (F2); disclosures
  still rendering in the `.exited` state (F3); `isAlive(pid:)` conflating
  `EPERM` with `ESRCH` (F4); `tabLookup`'s silent `{ _ in nil }` default
  (F6); and the empty `.help("")` tooltip on a metric tile with no
  `detail` (`ProcessStatusPaneView.metricTile`). None of these are
  addressed in this round — they're recorded here only so the branch
  history shows they were seen and deliberately deferred, not missed.
