## Description

The second concrete non-terminal view: a **Process Status view** — similar to Activity Monitor, but focused on a single selected app or process rather than the whole system. Like #0304 it is design-gated per the #0301 umbrella: visual designs are drafted and approved by the user before implementation starts.

### The feasibility spike — the thing that could have invalidated the design

Run first, as throwaway scripts kept out of the repo, and **independently reproduced by the reviewer**:

- **`task_for_pid` fails for every target.** `kr=0` for self; `kr=5` (`KERN_FAILURE`) for same-uid Finder, an interactive same-uid zsh, and root `launchd`. Same-uid does not help. This matches the `0x5` already in Batty's own log.
- **libproc works without a task port, and is cheap.** `proc_pidinfo`, `proc_pid_rusage`, `PROC_PIDLISTFDS`, `PROC_PIDFDVNODEPATHINFO`, `proc_pidpath`, `sysctl(KERN_PROCARGS2)` all return in 0.001–0.18 ms; a full core sample is ~0.03 ms. Child discovery has no direct call — it means enumerating ~820 pids and filtering `pbi_ppid` — at 0.3–1.5 ms.
- **Numbers cross-checked against independent tools.** Finder's `phys_footprint` matched Apple's own `footprint` CLI exactly; resident size matched `ps -o rss` exactly.
- **No shell fallback needed.** `ps` costs 65 ms/call and `top -l 1` costs 400 ms — three to five orders of magnitude worse than libproc, with no capability gap to justify it.
- **Failure modes are distinguishable at the kernel**: an exited pid gives `ESRCH`, a different-uid process gives `EPERM`. The tombstone and permission-denied states key off those directly rather than inferring.
- **Scope is honestly same-uid only — and that bites in Batty's own architecture.** Batty's pty session leader is a root-owned `/usr/bin/login`, so the permission wall is reachable in ordinary use, not hypothetical.

The `task_for_pid`-allow entitlement route is recorded as **carried from the issue text, not spike-verified** — testing it would need a signing change.

### The three decisions, for the user to accept or redirect

1. **Which process** — two modes. *Pinned* (CLI `--pid`) tombstones on exit and never guesses a successor. *Following a terminal* (the default) re-resolves `foregroundPid` every tick rather than freezing at creation, which removes successor bookkeeping entirely and also sidesteps the sibling-erosion problem #0304 hit, since it binds to a Tab id rather than a position in the split tree.
2. **What it shows** — bounded strictly by the spike. CPU%, `phys_footprint` and resident memory, thread count and open-file count sampled every tick; full fd paths, child list and full command line as on-demand disclosures, because those are a different cost class. No process control — no kill, no renice, not even stubbed.
3. **Refresh** — 1 second, a UX choice rather than a cost constraint. `tearDown()` is a plain `Task.cancel()`; no subprocess is spawned anywhere in this design, so none of #0304's bounded-wait `Process.terminate()` machinery is needed.

### Review

`claude-opus-5`, two rounds.

Round 1 re-ran the decisive spike itself rather than accepting it — reproducing `kr=5` on the same targets and Finder's `phys_footprint` to within ordinary drift — then found the defect this phase exists to catch: **the mockup's permission-denied state displayed data the spike had proved unobtainable.** It showed `/usr/bin/sudo apt-get update`, attributing the argv to `proc_pidpath` sitting behind a looser permission tier. `proc_pidpath` returns a path, never argv; argv needs `KERN_PROCARGS2`, which the design's own §1.6 recorded as `EINVAL` for a different-uid target. Being wrong about the boundary *in the state whose entire job is showing the boundary* would have misled the approval decision.

Round 2 re-verified the corrected claim against two independent root pids, confirming `proc_pidpath` succeeds exactly where `proc_name` is denied — which is what makes the header's basename fallback honest — and found no new defect, breaking a pattern that had held for the previous several issues.

## Design-phase questions (to answer in the design phase, not decided here)

1. **Which process, selected how?** Options to lay out: the foreground process of a sibling terminal Pane — the 1.3.2 libghostty-spm bump (#0286) exposes `foregroundPid` (`tcgetpgrp` on the pty) and `ttyName` as public `TerminalView` properties, and #0297 records them as reachable via `TabRuntime.terminalNSView` (capture deferred there, not implemented) — versus an explicit process picker, versus a pid/name supplied by the CLI at creation. The design also has to answer what the view does when the selected process exits (follow the successor foreground process? show a tombstone?).
2. **What it shows.** CPU, memory footprint, thread count, open files, child processes — and which of these are worth the cost of sampling (open files and child-process trees are much more expensive to enumerate than CPU/memory).
3. **Refresh cadence.** Sampling is a direct, recurring compute cost — exactly the kind of cost the #0303 lifecycle exists to govern. The design must state the visible-refresh interval, and per #0303 the sampler suspends entirely while the Pane is hidden and tears down on close.

## Feasibility risk: reading another process's stats is restricted (settle this first)

This is the one question that can invalidate the whole design late, so it must be settled early, empirically:

- Inspecting **another** process's memory requires a Mach task port, and `task_for_pid` is restricted on modern macOS even for an unsandboxed app running as the same user. This is not hypothetical for Batty: the session that filed this issue observed exactly that failure in Batty's own log — `Unable to obtain a task name port right for pid 607: (os/kern) failure (0x5)`.
- #0290's `FootprintReader` does **not** generalise: it reads **the app's own** `phys_footprint` via `task_info(mach_task_self_, TASK_VM_INFO)` (`BattyKit/Sources/BattyKit/Runtime/FootprintReader.swift`, verified 2026-08-04) — `mach_task_self_` is the one task port every process gets for free. There is no existing Batty code that reads another process's memory.
- The design must therefore establish, with a small spike before any mockup is treated as buildable: whether libproc calls that skip the task port (`proc_pidinfo`, `proc_pid_rusage`) return what the view needs for same-user processes; whether shelling out to `ps`/`footprint`/`top` is the pragmatic fallback and at what sampling cost; whether any entitlement could help (the `task_for_pid`-allow route is effectively private/dev-only and likely a dead end for a notarized app); and whether the feature is honestly scoped to processes the user owns.

Whatever the spike finds bounds question 2 above — the metrics shown must be the metrics actually obtainable.
