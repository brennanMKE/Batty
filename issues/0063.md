## Description

`Cmd-N` is the macOS-wide convention for "new window" / "new document" / equivalent primary creation action. Batty doesn't bind it to anything. Today's session-creation shortcut is `Cmd-Option-N`, which is a non-standard chord that users won't reach for instinctively.

Per `PRD.md`, Batty is single-window by default — there's no "new window" concept the way Safari has. The natural mapping is `Cmd-N` → "New Session" (today's `Cmd-Option-N`). Sessions are the closest analog to "new document" in Batty's model: a fresh sidebar entry with its own pane and tab.

## Steps to reproduce

1. Press `Cmd-N`. Nothing happens.
2. The File menu doesn't currently expose a "New …" entry that documents the binding.

## Expected behavior

`Cmd-N` opens a new session — same effect as today's `Cmd-Option-N`. Either:

- **Rebind:** Change "New Session" from `Cmd-Option-N` to `Cmd-N`. Drop `Cmd-Option-N` entirely.
- **Both:** Keep `Cmd-Option-N` as a secondary binding; add `Cmd-N` as the primary.

Recommend the **rebind** — fewer shortcut paths is less to remember, and the `Cmd-N` convention is strong enough that any user who already learned `Cmd-Option-N` will be happy to switch.

If we ever add multi-window support (`PRD.md` says single-window by default, but doesn't prohibit additional windows), `Cmd-N` should remain "new session in the current window" and `Cmd-Shift-N` could become "new window." Or `File → New Window` could be added with its own shortcut. Defer until that feature is on the table.

## Implementation guidance

In `BattyCommands.swift`, change:

```swift
Button("New Session") {
    store?.addSession()
}
.keyboardShortcut("n", modifiers: [.command, .option])
```

to:

```swift
Button("New Session") {
    store?.addSession()
}
.keyboardShortcut("n", modifiers: .command)
```

Also surface this under the File menu instead of just the Session menu — Cmd-N at the File-menu level is what users look for. Use `CommandGroup(after: .newItem) { ... }` or `CommandGroup(replacing: .newItem) { ... }` so the shortcut shows up where users expect.

Note: doing this depends on `#0062` (menu shortcut routing) being resolved, because otherwise the binding will be silently disabled when the terminal has focus.

## Acceptance criteria

- `Cmd-N` from any focus state opens a new session.
- The shortcut appears in the menu bar's File (or Session) menu next to "New Session."
- Old `Cmd-Option-N` no longer fires (clean rebind, no orphaned binding).
- Documented in `PRD.md`'s Keyboard Shortcuts section / `Concepts.md` if either lists shortcuts.

## Out of scope

- Multi-window "New Window" support. Track separately if requested.
- Configurable shortcuts (user-defined chord bindings) — not v1.

## Notes

- Discovered alongside `#0062`. The two together make hotkeys feel broken: `Cmd-W` doesn't fire because of the focused-value gap (`#0062`); `Cmd-N` doesn't fire because nothing binds it. Each has a different fix.
- Related: `#0057` (CWD inheritance on new session — done; this issue inherits that behavior automatically since it routes to the same `addSession`).

## Root cause

`BattyCommands` only exposed "New Session" inside its own `CommandMenu("Session")` with a `Cmd-Option-N` chord. No command replaced the standard File-menu `newItem` slot, so the macOS-default `Cmd-N` had nothing to fire and the File menu showed no "New …" entry where users instinctively look for it.

## Fix

Added a `CommandGroup(replacing: .newItem)` whose single button is "New Session" with `keyboardShortcut("n", modifiers: .command)`. The button under `CommandMenu("Session")` still calls `store.addSession()` for discoverability, but its `keyboardShortcut` was dropped so the shortcut lives in one place and there's no duplicate-binding ambiguity.

## Files changed

- `BattyKit/Sources/BattyKit/BattyCommands.swift` — added a File-menu `newItem` replacement that binds `Cmd-N` to `store.addSession()`; removed the `Cmd-Option-N` modifier from the Session-menu entry.

## Gotchas

- `PRD.md` (lines 134, 183) and `Concepts.md` (line 34) still describe `Cmd-N` as opening an additional window — a deferred multi-window feature. This fix repurposes `Cmd-N` for "New Session" per this issue's recommendation; if/when multi-window support lands, those docs and this binding will need to be reconciled (likely moving "new window" to `Cmd-Shift-N` or a `File → New Window` entry). Left the PRD/Concepts wording alone here to avoid pre-committing to a multi-window design.
- `Cmd-Shift-N` is currently bound to "Toggle Bell Feed" (`BattyCommands.swift` line ~90), which would conflict with a future "new window" shortcut on that chord. Out of scope for this issue; flag when multi-window work begins.
- `#0062` (menu shortcut routing while terminal has focus) is still required for `Cmd-N` to fire reliably when a Terminal Surface owns key events. Verifying this fix end-to-end depends on `#0062` also being resolved.
