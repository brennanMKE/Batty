## Description

Document how to cut a v1 release, and produce the ship checklist that gates v1.0 against PRD §12's success criteria. This is the M10 capstone.

**Acceptance criteria:**
- `Scripts/RELEASE.md` (or the equivalent section in CLAUDE.md) covers:
  - How to bump version + build number.
  - How to run the signed-and-notarized build (#0037).
  - How to publish the appcast (#0038).
  - How to write release notes.
- A `Ship-v1.md` (or section in PRD.md) explicitly enumerates the PRD §12 success criteria as a checklist, each with a place to mark "verified".
- The first release built via this process passes Gatekeeper on a clean Mac that's never seen Batty before.

## Notes

- Don't ship until PRD §12's five success criteria all hold.
- This issue is administrative — most of the build work landed in #0037 / #0038. The deliverable here is documentation + verification.

## Root cause

`scripts/release.sh` and friends existed but had no narrative documentation. PRD §12's success criteria were enumerated in the spec but not surfaced as a per-release verification checklist.

## Fix

Two new docs.

- `scripts/RELEASE.md` — end-to-end checklist for the release pipeline. Covers one-time setup (Developer ID cert, `Batty-notary` keychain profile via `scripts/setup-keys.sh`, future Sparkle EdDSA key), the per-release step sequence (version bump → sanity build → `release.sh` → `verify-dmg.sh` → clean-Mac smoke → tag → appcast → release notes), and a troubleshooting section for the common spctl/notarytool/Gatekeeper failure modes.
- `Ship-v1.md` — explicit checklist gating v1.0.0 on the PRD §12 success criteria (5 rows), plus build/distribution gates (B1–B7) and a functional sanity matrix covering sessions, splits, tabs, IME, drag-drop, bell feed, themes, settings, paste, quit, about, and restore. Each row has a "Verified" cell to fill in. Known-limitations section enumerates what v1 deliberately doesn't ship so the release notes can cite them honestly.

## Files changed

- `scripts/RELEASE.md` (new) — release-pipeline narrative.
- `Ship-v1.md` (new) — v1.0.0 ship gate checklist.

## Gotchas

- **The "first release passes Gatekeeper" AC item is documentation only.** Actually verifying it requires running `scripts/release.sh` (user-gated per CLAUDE.md) and testing on a clean Mac — both steps are owned by the user, not the agent. The checklist's `B5` row is the place that gets ticked when verified.
- **Sparkle appcast specifics intentionally vague.** Hosting URL, signing approach, and channel structure all depend on #0038's implementation, which hasn't landed. The release doc lists the appcast step but doesn't prescribe the appcast format yet — update once #0038 ships.
- **`Ship-v1.md` includes a "Known limitations" section** so the release notes can quote it directly. Worth keeping it accurate as the v1 freeze approaches; in particular #0003 (terminfo bundling), #0007/#0008 (superseded by GhosttyTerminal adoption), and the per-tab close-confirmation gap from #0036 are the things the user is most likely to ask about post-release.
- **Version-bump location.** Both `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` live in `Configuration/Build.xcconfig`. CLAUDE.md flags Build.xcconfig as a restricted area, so the user should make those bumps directly rather than asking the agent.

## Verification

- Both files render cleanly as markdown.
- `xcodebuild` and `swift test` were not affected by these doc-only additions.
- The release-pipeline-passes-Gatekeeper acceptance criterion is **deferred to first actual v1 release** — that step requires user execution per CLAUDE.md's "do not run release.sh autonomously" rule.
