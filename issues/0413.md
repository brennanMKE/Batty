# 0413 — No test drives a running Batty through the `batty` CLI, so "the CLI reliably controls the app" is unproven for every verb and every non-terminal view kind

| | |
|---|---|
| **Status** | open |
| **Module** | Testing / App / Pane |
| **Platform** | macOS |
| **First seen** | 2026-09-23 |

## Description

The goal for this release is that the `batty` CLI reliably controls the Batty Mac app, now that Panes can host non-terminal views. Nothing proves it today. The CLI's unit tests and the app's model tests pass, but no test runs a real `batty` binary against a running Batty and checks what then appears **on screen**. #0333 shows why that gap matters. There, `batty pane split --view git-status` and `--view system-metrics` both exited `0` with new pane ids, and `batty list --json` reported the right three-Pane topology, yet the window showed one terminal Pane filling the whole content area. Every unit-level check was green and the user-visible result was wrong.

This issue adds a **VM-only UI test suite** (run through #0412's runner, never on a host) with these steps:

1. Launch Batty Beta.
2. From the test process, run the CLI binary embedded in *that* launched bundle.
3. Assert, through accessibility identifiers, that each verb produced the on-screen result it claims. Do the same for topology read back through `list`, `status` and `session info`.

## Current state (verified 2026-09-23)

**The CLI surface.** The subcommands are listed in `BattyKit/Sources/batty/BattyCLI.swift`, with nouns in `SessionInfoCommand.swift`, `PaneCommand.swift` and `TabCommand.swift`.

| Verb | Transport |
|---|---|
| `new [<path>]` (default subcommand; `--no-wait`) | `batty://` URL through `/usr/bin/open`. Unless `--no-wait` is passed, it snapshots topology over XPC first, then polls `list` until exactly one new Session with the matching path appears (#0380, `NewSessionCommand.swift`). |
| `ping` | Broker (`BrokerPingClient.swift`) |
| `status` | XPC `status` |
| `list [sessions\|panes\|tabs]` (`--json`, `--include-dimensions`) | XPC `list` |
| `session info` (`--session`, `--json`, `--include-dimensions`) | XPC `sessionInfo` |
| `session focus [<id>]` | XPC `sessionFocus` |
| `session close` (`--session`) | XPC `sessionClose` |
| `pane split` | XPC `paneSplit` |
| `pane close` (`--pane`) | XPC `paneClose` |
| `pane focus [<id>]` | XPC `paneFocus` |
| `pane hide` (`--pane`) | XPC `paneHide` |
| `pane show <id>` (id required) | XPC `paneShow` |
| `tab focus [<id>]` | XPC `tabFocus` |
| `notify` (`--title`, `--body`, `--sound`, `--tab`) | XPC `notify` |
| `id` | Environment only, no app round trip (`IDCommand.swift`) |
| `capabilities` | Local, no XPC (#0384, `CapabilitiesCommand.swift`) |

`pane split` takes a direction flag (horizontal by default), `-c/--command`, `--pane`, `--view`, `--pid`, `--path` and `--unique`. `XPCVerb.swift` also defines `watch`, but no CLI subcommand calls it.

**Other facts the suite depends on:**

- **`--view` kinds.** `PaneContentKindArgument.swift` makes `PaneContentKind` (`BattyXPCCore/PaneContentKind.swift`) the `--view` argument directly, so the accepted values are exactly its raw values: `terminal`, `git-status`, `process-status`, `lm-studio-dashboard` and `system-metrics`.
- **Exit codes** (`BattyXPCCore/XPCExitCode.swift`, and the table in `docs/batty-cli-agent-workflows.md` "Failure handling"):

  | Code | Meaning |
  |---|---|
  | `0` | success |
  | `1` | local validation |
  | `2` | broker unreachable |
  | `3` | app unavailable |
  | `4` | the app rejected the request (stale or unknown target, or a refusal) |
  | `5` | session terminated |
  | `6` | app running but unregistered |
  | `7` | app bundle unresolved |
  | `64` | invalid syntax |

  Documented refusals that return `4` (`.claude/skills/batty-cli/SKILL.md` §6–7): `pane hide` on a Session's only visible Pane, `pane close` on the app's last Pane or a Tab that needs confirmation (`XPCVerb.paneClose` doc comment), and `session close` on the last Session or an unconfirmed Tab close. Exit `4` from `batty new` means its poll timed out, not that the app rejected the request, and retrying creates a second Session.
- **The CLI's target and variant.** The embedded CLI lives at `<App>.app/Contents/Resources/bin/batty`, copied there by the "Embed CLI" build phase, and the broker lives beside it at `Contents/Resources/bin/BattyBroker`. `AppBundleLocator` resolves the target bundle from the CLI's own executable path. The variant is compiled in: `-DBATTY_VARIANT_BETA` when the bundle id is `co.sstools.Batty.beta`. The Beta install name is `batty-beta` (`docs/batty-cli-install.md`, `docs/beta-demo-script.md`).
- **Accessibility identifiers the suite can assert on** (grep of `accessibilityIdentifier(` under `Batty/` and `BattyKit/Sources`):
  - Sidebar: `session-sidebar`, `session-row.<session title>` (keyed by **title**, not id), `pane-row.<paneID>`.
  - Per-Pane chrome: `pane-close-button.<paneID>`, `pane-eye-button.<paneID>`, `pane-eye-toggle.<paneID>`, `pane-drag-handle.<paneID>`, `pane-drop-zone.<paneID>`, `tab-bar.<paneID>`.
  - Terminal Panes: `pane-terminal.<paneID>`.
  - Non-terminal content: `git-status.*`, `process-status-view`, `system-metrics-pane`, `lmstudio-dashboard`, `pane-placeholder.<kind>`. **These are not keyed by pane id**, so tying a content view to the id the CLI returned means going through the pane-id-keyed chrome (for example, `pane-close-button.<id>` and the content inside the same Pane's frame). Whether that is enough, or the content views need id-scoped identifiers, is a design question for the implementer.
  - Bell Feed: `bell-feed.list`, `bell-feed-entry.<entryID>`.
- **UI coverage of CLI-driven behavior is none.** A grep of `BattyUITests/` finds no `Process` launch, no `Contents/Resources/bin` path, no `batty://` URL and no `--view`. Existing tests seed state in-process through `BattyUITestHarness.launchBatty(script:)`, which passes `BATTY_UI_TEST_SCRIPT` to `UITestDriver` (`BattyKit/Sources/BattyKit/Testing/UITestDriver.swift`, with intents such as `createSession`, `splitHorizontal` and `createPane`). For example, `NonTerminalPaneCloseTests` creates its `system-metrics` Pane through `createPane`, not the CLI. That path skips the CLI, the broker, XPC, `AppXPCService` and URL dispatch entirely.
- **The docs say it too.** `docs/beta-demo-script.md` says outright: "Nothing in this script has been run against a live app. Every step is written from source and unit tests."

## Scope

A new UI test class (or a small set of classes) in `BattyUITests/`. It runs only inside the #0412 VM. Each test does the following:

1. Launch Batty Beta with the existing harness (`BATTY_UI_TEST_MODE=1`, temp home).
2. Resolve the launched bundle's `Contents/Resources/bin/batty`.
3. Run it with `Process` from the test process, capturing stdout, stderr and the exit code.
4. Assert on the app's accessibility tree.

The first test must first establish that the CLI is talking to **the same process** XCUITest launched, by matching `status --json`'s `pid` (and `bundlePath`) against the launched app. #0333's own notes suspect its report was two app instances (#0361), so a suite that doesn't pin this can't tell a view-layer bug from a wrong-process artifact.

**Per verb, the on-screen result:**

1. **`new <tempdir>`.** Exit `0`, line 1 is a Session id and line 2 its `focusedPaneID`, and a `session-row.<title>` appears in the Sidebar. Cover `--no-wait` separately: exit `0`, then a Session eventually appears.
2. **`pane split` with no `--view` and with `--view terminal`.** A new `pane-terminal.<returnedID>` exists with a non-zero frame, and the two Panes share the split: the frames don't overlap and together roughly fill the parent. Cover both split directions.
3. **`pane split --view <kind>` for each of `git-status`, `process-status`, `lm-studio-dashboard` and `system-metrics`.**
   - The Pane's chrome (`pane-close-button.<returnedID>`) exists with a non-zero frame, and that kind's content identifier is inside it.
   - The originating terminal Pane no longer fills the whole content area. This is #0333's exact failure.
   - Cover `--path` for `git-status`, `--pid` for `process-status`, and `--unique` (a second call returns the existing id and no new Pane appears).
   - `lm-studio-dashboard` has no LM Studio server in the guest. Assert that the Pane and its disconnected state appear, not that it has live data.
4. **`pane close`.** The Pane's identifiers disappear and its sibling takes over the space. The last-Pane refusal gives exit `4` and changes nothing on screen.
5. **`pane hide` / `pane show <id>`.**
   - Hide: the Pane leaves the split area, stays listed as hidden in `list --json`, and its Sidebar row shows it as hidden.
   - Show: the Pane returns with a non-zero frame.
   - Hiding a Session's only visible Pane gives exit `4`.
6. **`session focus` / `pane focus` / `tab focus`.** Focus and selection actually move. Check the selected Sidebar row, the focused Pane (whatever accessibility state marks it, which is to be determined; `TerminalPlaceholderView`'s label reflects `isPaneFocused`) and the selected Tab chip. Include a target in a **non-selected** Session.
7. **`notify --title … --body …`.** A new `bell-feed-entry.*` appears in `bell-feed.list`, attributed to the targeted Tab. An unknown `--tab` gives exit `4` and adds no entry.
8. **`list` / `status` / `session info` against the screen.** After each mutation above, the `list --json` topology must match what is on screen: the Session count equals the Sidebar Session rows, and each Session's visible (non-hidden) Pane ids equal the set of on-screen pane-id-keyed identifiers. Hidden Panes are flagged, not counted as visible. This is the check that would catch #0362.
   - `id` run from the test process has no `BATTY_*` environment, so assert its documented behavior in that case. Separately, run `id` *inside* a Terminal Session (for example through a Pane's `-c` command writing to a sentinel file, as the harness's sentinel helpers do) and check it reports that Pane's ids.
9. **Exit codes for bad targets.** A well-formed but unknown UUID for `--pane`, `--session` and `--tab` on each mutating verb gives `4`. A malformed UUID or an invalid `--view` value gives `1` or `64`, whichever the CLI documents. In every case, nothing on screen changes.

**Reliability:**

- **Rapid sequential verbs.** `new` immediately followed by `pane split --pane <returned paneID>`, with no sleep. `docs/batty-cli-agent-workflows.md` explains why `batty new` polls: dispatching the URL "only proves LaunchServices accepted it". It also records a residual cold-launch window where `batty new ~` can report the default Session's id. Run a burst of several `pane split` calls back to back and check every returned id is on screen.
- **Repeated split/close cycles** (for example 20 rounds, mixing terminal and non-terminal kinds). Afterwards the topology and the screen are back to the starting Pane count, with no leaked or orphaned Panes in `list --json` or the Sidebar.
- **Calls targeting a non-selected Session.** `pane split` / `pane close` / `notify` aimed at a background Session take effect there. They do **not** switch the selected Session (the `XPCVerb.sessionFocus` doc comment calls `session focus` the "one sanctioned exception"). The change is visible after `session focus`.

**Coverage reporting.** The suite writes out (as test output, and recorded in the resolution) a per-verb table: covered and passed, covered and failed, or not covered with the reason.

## Dependency on the broker (#0401)

Every verb except `id` and `capabilities` depends on the broker. So does `new`'s confirmation poll, unless `--no-wait` is passed. #0401 established that the *unsigned* Beta package's broker can't register (`SMAppService` → `errSecCSResourcesNotFound`). The guest builds ad hoc (#0412, Open question 4), and whether that registers is unknown. If the broker can't register in the guest:

- The suite must **fail, or skip with an explicit label**, for every verb it could not exercise, naming the cause (broker registration and the exit code seen, for example `2` or `6`).
- It must **never pass silently**. A test that returns early without an `XCTSkip` carrying the reason counts as a defect in this issue's own deliverable.

Whichever way this goes, the finding is recorded here and on #0401.

## Open questions (not answered here)

1. Can the UI test runner process `exec` a binary inside the app bundle under test? **Answered by #0419: it can exec it, but the runner is App Sandboxed (`com.apple.security.app-sandbox`) and the child inherits that, so the CLI cannot reach the broker (exit 2) even with the broker up.** #0419 added a guest-only loopback relay (`127.0.0.1:47911`, `tools/vm-guest-cli-relay.sh`) that runs the embedded CLI outside the sandbox; `BrokerReachabilityTests` shows the usage (send tab-separated arguments with `nc`, read output plus a final `__EXIT__ <status>` line). The relay splits arguments on tabs, so an argument cannot contain a tab; anything needing one would need a length-prefixed argv.
2. `batty new` dispatches a `batty://` URL through `/usr/bin/open`. In the guest, does LaunchServices route it to the DerivedData copy XCUITest launched? Both variants share the `batty://` scheme (`SessionCommand.swift`, the #0279 note).
3. Does registering the broker in a fresh guest raise an "Allow in the Background" / Login Items prompt that needs a human? #0412's success criteria forbid any prompt in the guest.
4. Do the non-terminal content views need pane-id-keyed accessibility identifiers for reliable assertions? This would be a production change.

## Expected behavior

A VM run of the new suite shows each verb's result on screen and in `list --json`, together, for terminal Panes and every `--view` kind. It also gives a truthful per-verb coverage table. Any mismatch between CLI output and the screen fails a named test.

## Notes

- Test scaffolding like this is the reason #0412 exists. Don't run any of it on a host, not even "just once": the CLI-driven tests launch Batty under XCUITest, which is exactly the #0409 hazard.
- Failures this suite finds (a #0333 reproduction on a post-#0361 build, a #0362 count mismatch, a leaked Pane) are filed as their own issues and linked here. Fixing them isn't in scope.
- **Accessibility identifiers needed (2026-09-23):** none of Process Status's run-state UI in `BattyKit/Sources/BattyKit/Views/ProcessStatusPaneView.swift` has an accessibility identifier. That covers the header state chip (`stateChip`, `:151`, with its "Running" / "Exited" / "Permission Unavailable" / "Unavailable" chips), each of the banners (`exitedBanner` `:292`, `permissionDeniedBanner` `:309`, `unavailableBanner` `:326`, including #0356's new `.unavailable` state) and the `noSelectionState` placeholder (`:343`). The only identifiers in the file are `process-status-view`, `process-status.choose-process` and `process-status.running-process-picker`. To check a `--view process-status` Pane's state from XCUITest, the suite has to add them first: for example `process-status.state-chip` with the run state (`running` / `exited` / `permissionDenied` / `unavailable`) as its accessibility value, plus one identifier per banner (such as `process-status.banner.unavailable`). Matching on the visible chip text would break under localization.
