## Description

Visual feedback while a drag is hovering over a Pane: a subtle accent border (or inset glow) on the target Pane to confirm the drop will land here. Removed on `draggingExited` and `performDragOperation`.

**Acceptance criteria:**
- During a drag with file URLs over a Pane, the Pane shows a clear "I'll accept the drop" highlight.
- The highlight disappears immediately on drop or cancel.
- Highlight does not interfere with rendering (no flickering, no resize jitter).
- Multiple Panes during the same drag (e.g. moving the cursor across split borders) hand off the highlight cleanly.

## Notes

- Implementation can be a CALayer border overlay added/removed in `draggingEntered`/`draggingExited`, or a SwiftUI overlay driven by an `@State` from the NSView via a delegate. Either is fine.
- Match the system accent color for consistency.
- If the drag has no `.fileURL` types, don't show the highlight — saves the user from a misleading affordance for unsupported drags.

### Deferred — 2026-05-08

Depends on `#0022` landing (the drag destination registration is what fires `draggingEntered` / `draggingExited`). Without `#0022`'s text-injection unblock, there's no drag handler to wire visual feedback into. Deferring with the same notes as `#0022`.

## Root cause

The drop overlay shipped in #0022 used `isTargeted: nil`, so SwiftUI tracked the drag-over state internally but never surfaced it to a binding the view could react to. No state, no visual.

## Fix

- `PaneView` gains a single `@State private var isDragHovering: Bool = false`. The active tab's `.onDrop` binds `isTargeted: $isDragHovering`; background tabs bind `.constant(false)` so a drag traversing tabs inside a pane only ever lights up the active one.
- An `.overlay` on the surface ZStack renders a 2pt `Color.accentColor` `RoundedRectangle.strokeBorder` whose opacity is driven by `isDragHovering` with a 120ms `easeOut` crossfade. `allowsHitTesting(false)` so the border never swallows a click.

Cross-pane handoff is automatic: each `PaneView` owns its own `@State`, so the source pane sees `isTargeted=false` and the destination pane sees `isTargeted=true` as the cursor crosses split borders.

## Files changed

- `BattyKit/Sources/BattyKit/PaneView.swift` — added `@State isDragHovering`; bound it on the active tab's `.onDrop`; added the accent-bordered overlay with crossfade.

## Gotchas

- **`isTargeted` only fires for matching drags.** Because the drop registration is `[.fileURL]`, SwiftUI flips `isTargeted` to true only when the dragged item carries a file-URL provider. A drag of e.g. plain text from another app won't show the highlight, which matches the issue's "saves the user from a misleading affordance" note.
- **The 2pt border is an inset stroke (`strokeBorder` not `stroke`),** so the highlight stays inside the pane bounds and doesn't cross into adjacent panes via the SplitContainer divider gap. Switching to `stroke` would produce a 1pt halo on the outside, which we don't want.
- **The accent color follows system tint.** No theme integration yet — if a user's terminal theme is bright orange and they pick blue as the system accent, the highlight will be blue. Tradeoff: matching the system accent is the most common macOS-app convention; matching the terminal background makes the affordance harder to see when the bg is similar. Revisit only if a user complains.
