## Description

Child of #0705. An agent only uses Batty if something tells it Batty is there. Today that's the `batty-cli` skill and the `batty mcp` server, installed by `batty agent install` (or Settings → AI Agents, #0666), or a note the user writes by hand. In the 2026-11-21 session neither was installed, and the agent knew about Batty only from the user's private `~/.claude/CLAUDE.md`.

Claude Code can load context automatically in ways that apply **only inside Batty**:

- A **SessionStart hook**: a command that runs when a session starts; whatever it prints is added to the model's context. It can check `BATTY_SESSION_ID`/`BATTY_PANE_ID` and print a short Batty brief only when they are set, so sessions outside Batty see nothing.
- A **Claude Code plugin** can bundle that hook with the skill and the MCP server, so one install gives all three.
- `claude --append-system-prompt` works only when Batty launches `claude` itself, and a CLAUDE.md `@import` loads in every session, including outside Batty; neither is preferred.

## Expected behavior

- `batty agent install` (and the Settings → AI Agents flow) also installs, for Claude Code, a SessionStart hook that prints a short brief when `BATTY_*` is set: that the session is in a Batty Pane, which `batty` binary to use, the MCP server if configured, and the #0706 guidance (interactive commands in a Pane, never answer a confirmation for the user, close what you open). Silent outside Batty.
- The plan decides between writing the hook into `~/.claude/settings.json` and shipping a Claude Code plugin that bundles hook, skill and MCP config; and what the equivalent is for Codex, Cursor and OpenCode where they have one (or records that they don't).
- `--dry-run` shows the hook like the other installs; uninstall/reinstall is idempotent and never clobbers the user's other hooks or settings.

## Acceptance criteria

1. In a fresh Claude Code session in a Batty Pane, with no CLAUDE.md note, the brief is in context; outside Batty it isn't.
2. Installing twice leaves one hook; existing user hooks and settings are preserved byte for byte outside the added entry.
3. The brief's text is generated from the same source as #0706's guidance, so the two can't drift.
4. Tests cover the settings merge (empty file, existing hooks, malformed JSON refused, not overwritten).
