## Description

`SystemCPUReader` calls `host_processor_info(…, PROCESSOR_CPU_LOAD_INFO, &numCpus, &cpuInfo, &numCpuInfo)` and then iterates `0..<Int(numCpus)` indexing `cpuInfo` with stride `CPU_STATE_MAX` — but never checks that `numCpuInfo >= numCpus * CPU_STATE_MAX` before doing so. The two out-parameters are independent kernel-reported values; the indexing arithmetic silently assumes their relationship. If the kernel ever reports fewer `integer_t`s than `numCpus * CPU_STATE_MAX` implies, the loop reads past the end of the mapped buffer — an out-of-bounds read in a 1 Hz hot path.

This is a cheap defensive guard, not a redesign: one comparison after the call, returning the "unavailable" result (as the reader already does for a non-`KERN_SUCCESS` return) when the invariant doesn't hold.

## Expected behavior

The reader validates `numCpuInfo` against `numCpus * CPU_STATE_MAX` (guarding the exact indexing it performs) and bails to its failure path on mismatch.

## Actual behavior

The buffer is indexed on the assumed relationship with no check; a mismatch would be an out-of-bounds read.

## Notes

Verified code location (branch `issue/0314-2`, pending merge at filing time): `BattyKit/Sources/BattyKit/Runtime/SystemCPUReader.swift` — `numCpuInfo` declared and filled at the `host_processor_info` call; the per-core loop `for index in 0..<Int(numCpus)` with `stride = Int(CPU_STATE_MAX)` follows with no validation between them. (The deallocation path already uses `numCpuInfo` for the byte count, so the correct total is in hand.)

## Resolution notes

> 🟢 Resolved 2026-09-23 — `SystemCPUReader` now checks that `host_processor_info`'s buffer holds `numCpus × CPU_STATE_MAX` entries before reading it; a short buffer is reported as a failed read ("—" in the pane), never an out-of-bounds read.

## Root cause

`currentTicks()` indexed `cpuInfo` at `core * CPU_STATE_MAX + state` for `0..<numCpus` without comparing against `numCpuInfo`; the two counts are independent kernel out-parameters.

## Fix

Parsing moved into pure `SystemCPUReader.parseCoreTicks(numCpus:rawTicks:)`, which returns nil unless `numCpus > 0` and the buffer is long enough. `currentTicks()` copies the kernel buffer into an array (after the unchanged `vm_deallocate` defer is registered) and maps nil to `[]`, the same result as the existing non-`KERN_SUCCESS` path. Downstream, `[]` makes `percentages(for:)` return nil, so the pane shows "—" and recovers cleanly two ticks after a good read.
