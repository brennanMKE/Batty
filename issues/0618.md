## Description

**Doc-only.** `AGENTS.md` tells every agent "`@Observable` notifies on every write, including equal-value writes." On this toolchain that is false for `Equatable` properties: the `@Observable` setter checks `shouldNotifyObservers` and skips an equal write. `docs/swiftui-observation-rules.md` ("Which equal writes notify depends on the property's type") states the correct rule, and `BattyKit/Tests/BattyKitTests/ObservationEqualWriteSemanticsTests.swift` pins all four cases (`equalWriteToEquatablePropertyDoesNotNotify`, `reassigningSameInstanceToClassReferenceDoesNotNotify`, `nonEquatableStructNotifiesOnEveryWrite`, `nilToNilOnOptionalClassReferenceNotifies`). Several code comments repeat the wrong claim as the reason a guard exists. The guards themselves are still right — the rules doc keeps store-level idempotence because it stops a re-asserted mutator's *other* side effects — only the stated reason is wrong. Agents read `AGENTS.md` first, so the wrong rule there mis-steers every audit and plan (it was the premise of a constraint in #0604).

A whole-value equal write to any of them doesn't notify.
- In-place mutations notify even when nothing changes. A scratch `@Observable` checked with `withObservationTracking` on this toolchain: `d[1] = 1` (same value) notifies, `a.removeAll { false }` notifies, `p[0].x = 0` (same value) notifies, and `o?.x = 0` through an optional struct notifies. A whole-dictionary `d = [1: 1]` with the same value doesn't. So `BellFeedStore.setVerdict` (`ratingVerdicts[id] = verdict`) and `ProjectEditorViewModel.setTheme` (`draft?.theme = value`) really do need their guards to avoid a notification. Only the stated reason is wrong there.
- `selectedSessionID`'s `didSet` and `focusedPaneID`'s `didSet` already return early on an equal value, so the guards in `setSelectedSession` and `focusPane` change neither notification nor side effects. They keep the call sites idempotent and keep `focusPane`'s debug log quiet.
