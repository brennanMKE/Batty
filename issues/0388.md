# 0388 — Non-visible Panes keep their Metal swap chains because occlusion is signalled but the hidden Pane's layer-backed view is retained

## Description

Drive libghostty's occlusion API from Batty's own Session/Pane model so that **any surface not in the visible layout releases its Metal swap chain, while its PTY, terminal state, and scrollback stay live.** Do not change PTY lifecycle. Do not free surfaces.

This is the replacement for **[#0387](0387.md)**, which attacked the same footprint through resize (shrink the hidden surface so its drawables reallocate smaller) and was archived `wontfix`: the supplied specification rules that approach out by name, and review had independently blocked on the same reflow concern.

The full specification is attached — **[Release GPU resources for non-visible Panes — spec](0388/ReleaseViewResources.md)** — and is the source of truth for detail this issue summarizes. Everything below stands on its own for an implementer, but read the attachment before writing code.

### What is actually allocated

Each libghostty surface holds two independent pools:

- **Terminal state (CPU)** — the per-surface `PageList` holding screen plus scrollback, roughly 12+ bytes per cell with every on-screen cell preallocated, so Pane *width* drives cost more than printed content. **Not affected by occlusion.** (This is the MALLOC_SMALL ~196 MB / ~11.5 MB-per-Session figure already recorded in #0387's Notes and in the umbrella — out of scope here, see *Out of scope* below.)
- **Renderer state (GPU / unified memory)** — the per-surface `SwapChain`. On Metal `swap_chain_count = 3`, and each `FrameState` holds its own uniforms buffer, cell text buffer, cell background buffer, grayscale atlas texture, color atlas texture, and render target. Three copies per Pane. **This is what occlusion reclaims.**

### The API, verified against the pinned libghostty

```c
void ghostty_surface_set_occlusion(ghostty_surface_t, bool);
```

The call path is `ghostty_surface_set_occlusion` → `Surface.occlusionCallback` → renderer-thread `.visible` mailbox message → `Renderer.setVisible(false)` → `releaseGpuResources()`, which deinits the whole swap chain. It is rebuilt lazily on the next `drawFrame`. Side effects of `visible = false`, all desirable here: render-thread QoS drops to `.utility`; `updateFrame` is skipped entirely (no cell rebuilding); the cursor blink timer disarms; Kitty graphics animations pause and resume when visibility flips back; the terminal mode 2033 visibility report is emitted if the running program enabled it.

For the embedded apprt `apprt.must_draw_from_app_thread` is false, so `releaseGpuResources` runs on the render thread automatically. **Do not port the GTK pattern of calling release manually.**

## Why the existing occlusion work reclaimed nothing — the crux

**#0288 already signals occlusion, and the memory did not move.** The 2026-08-31 sample in #0387 still found 51 large IOSurfaces for 17 Terminal Sessions — 17 full-size triple-buffered swap chains, a clean 1:1 — with at most 2 Panes on screen. The 2026-08-30 measurement found the same shape at 18 sessions. #0288 removed the *duplicate* layers; it did not free the per-Session floor underneath them.

The attached spec's item 5 explains why, and it points at Batty, not at libghostty:

> **Do not keep layer-backed views for hidden panes.** Remove the hosting view from the view hierarchy rather than setting `isHidden = true` or zero opacity. A retained `CAMetalLayer` and its IOSurfaces are AppKit-side allocations that libghostty does not own and will not free.

**Batty does exactly the disallowed thing.** `BattyKit/Sources/BattyKit/Runtime/TerminalHostStore.swift` adds every `AppTerminalView` to the window's host once (`host.addSubview(view)`, `:180`) and thereafter only toggles `view.isHidden` (`:177`, `:394-398`, `:426-430`). The **only** `removeFromSuperview()` in the file is on the teardown path, `releaseTerminalView(forTabID:)` (`:289`), which also frees the surface and the PTY. So a hidden Pane's view — and its `CAMetalLayer`, and that layer's IOSurfaces — stays attached and retained for the life of the Session.

**Leading hypothesis, test it first:** the renderer may well already be releasing its GPU resources on `set_occlusion(false)` exactly as documented, while Batty's own retained `CAMetalLayer` keeps the IOSurfaces alive on the AppKit side. That would explain the entire measurement, it is consistent with everything #0288 did and did not achieve, and **it is cheap to test** — detach one hidden Pane's hosting view and re-sample `vmmap`'s IOSurface histogram before building anything else.

## The visibility predicate

A surface is visible **if and only if all three** hold:

1. Its Window's `occlusionState` contains `.visible`
2. Its Session is the active Session in that Window
3. Its Pane is present in the active Session's current layout — not a hidden Tab, not collapsed, not zoomed out of view

Anything else is `visible = false`. Upstream's macOS app wires occlusion at *window* granularity only (`macos/Sources/Features/Terminal/BaseTerminalController.swift`, `syncSurfaceTreeOcclusionState()` — one flag applied to every surface in the window), which is why hidden Tabs and non-visible Splits stay marked visible there. Batty needs per-Pane resolution.

## Implementation

### 1. Single source of truth

One resolver that computes visibility for a Pane from Batty's model, and one `syncOcclusion()` that walks **all** surfaces and applies it. **Do not scatter `set_occlusion` calls at individual event sites** — today's three separate `setSurfaceVisible` call sites in `TerminalHostStore` (`:406`, `:433`, `:462`) are exactly the shape that lets one path restore a state another path just changed.

Triggers that must call `syncOcclusion()`:

- `NSWindow.didChangeOcclusionStateNotification`
- Active Session change
- Tab selection change
- Split create, close, resize, zoom, unzoom
- Pane moved between Sessions or Windows
- Window miniaturize / deminiaturize
- App hide / unhide
- Session restore completion

### 2. Track last-applied state per Pane

Keep an `isSurfaceVisible: Bool` on the Pane's view model and skip the call when unchanged. `occlusionCallback` early-returns on a no-op, but the mailbox round trip and the mode 2033 check are not free, and these events fire in bursts during resize and drag.

**Initialize it to `false`, not `true`,** so the first sync after surface creation is always applied.

### 3. Get the initial state right — the highest-value correctness detail

A surface created into a hidden Tab, or restored from a persisted Session, **must be marked non-visible before or immediately after creation.** Otherwise it allocates a full swap chain it never draws with, and nothing frees it until the user happens to reveal and re-hide that Pane. Call the resolver as part of surface creation, not only from notification handlers.

The wrapper cooperates here: at the pinned revision `TerminalSurfaceCoordinator` applies its current visibility to a freshly built surface (`newSurface.setOcclusion(effectiveSurfaceVisible)`, `TerminalSurfaceCoordinator.swift:137`). Batty's job is to make sure the correct value has already reached the coordinator by then.

### 4. Pane moves across Windows

When a Pane is dragged to another Window its window-level visibility can change without any notification firing on the destination. **Re-run `syncOcclusion()` on both source and destination Windows** after the move completes. Upstream tracks `isWindowVisible` on the view specifically to restore occlusion state after a drag; Batty needs the same, keyed on the fuller predicate above.

### 5. Do not keep layer-backed views for hidden Panes

See *the crux* above. Removing the hosting view from the view hierarchy is a change to `TerminalHostStore`'s hide path, and it interacts with the placement/frame cache and with `effectiveSurfaceVisible(placementVisible:windowVisible:)` deriving visibility from `!view.isHidden` (`:365`, `:404`, `:447`) — that derivation has to survive the switch to detach/reattach, and the reasoning in the doc comment at `:355-370` about why `placements` is *not* the input explains why it must not simply be swapped back for `placements[id].isVisible`.

## Explicit non-goals

- **Do not free and recreate surfaces.** `termio` and the PTY are owned by `Surface`; `ghostty_surface_free` takes both down. The spec also records an open **use-after-free** on that path: `SwapChain.deinit` waits only on the frame semaphore, not on the deferred main-queue present block or the Core Animation transaction flush, so Metal can present a freed IOSurface after renderer teardown. Filed against iOS, but the code is the shared renderer teardown path.
- **Do not resize hidden Panes to shrink buffers.** `ghostty_surface_set_size` would shrink render targets and cell buffers, but it triggers reflow and destroys the Pane's layout and scrollback wrapping. Not acceptable. **This is precisely what #0387 did, and why it was archived.**
- **Do not touch scrollback limits in this change.** See *Out of scope*.

## Known hazard carried forward from #0387 — the render-ordering trap

`CAMetalLayer` only reallocates its drawable pool when something calls `nextDrawable()`, and in this stack that happens only through libghostty-spm's `tick() → surface.draw()`. But at the pinned revision:

- `TerminalSurfaceCoordinator.scheduleTickIfNeeded()` refuses to schedule that render once its `canRenderFrame` gate is false (`Sources/GhosttyTerminal/Surface/TerminalSurfaceCoordinator.swift:351-355`), where `canRenderFrame == effectiveSurfaceVisible && isAttached()` and `effectiveSurfaceVisible == isDisplayVisible && isApplicationActive` (`:379-385`).
- `tick()` re-checks the same gate through `shouldRenderFrame(at:)` (`:344-349`) when an already-scheduled render *executes*.

So **any scheme that mutates layer geometry and then marks the surface non-visible silently updates the `CALayer` property while freeing nothing.** It looks correct in every observable place except `vmmap`. #0387 burned a whole review round on this. It matters here too: `isAttached()` is part of the gate, so detaching the hosting view (item 5) also stops renders — sequence the detach and the occlusion call deliberately, and verify with `vmmap`, not with the layer's reported `drawableSize`.

## Verification

Build a repro: **one Window, one Session, N Panes with only 2 visible**, and fill several hidden Panes with heavy scrollback.

**Measure `phys_footprint`, never VM size and never RSS.** Scrollback compression uses `MADV_FREE_REUSABLE` on Darwin, which lowers resident memory while leaving virtual allocations in place, so VM size will not move. (`ps -o rss` under-reported by 5.4× on the 2026-08-30 sample and 29× on the original #0285 report — binding for every child of that umbrella.)

Expected results:

- Occluding a Pane drops footprint by the swap-chain cost: 3 frames of (atlas textures + cell buffers + render target sized to the Pane)
- Revealing an occluded Pane rebuilds the swap chain on the next `drawFrame` **with no visible flash and no stale frame**
- Terminal content in an occluded Pane is **current on reveal** — meaning the PTY kept reading
- Cursor blink and any Kitty graphics animation resume on reveal

Regression checks: Pane drag between Windows, Session restore at launch, zoom and unzoom, Window miniaturize and restore.

### Test protocol (binding)

- **All testing uses the Beta build.** `./build.sh` defaults to the Beta scheme (`BETA_SCHEME="Batty (Beta)"`); Prod is release-only (`./build.sh release`). **Never test against the Prod app the user runs from `/Applications/Batty.app`.** *(`CLAUDE.md` and `issues/Issues.md` both still describe `./build.sh` as invoking `Batty (Prod)`; the script is authoritative and defaults to Beta.)*
- Create **several Sessions and several Panes**, and measure as **the selected Session and the selected Pane change** — that is the transition this work hooks. Cover the Window-occlusion round trip too (Cmd-H, minimize, full cover by another window).
- Use the existing tooling rather than reinventing it: `tools/memsample.sh` is the #0291 harness (see `tools/README.md`) and already diffs before/after by geometry class, not just totals. `TerminalMetalMetricsLogger` (`BattyKit/Sources/BattyKit/Runtime/TerminalMetalMetricsLogger.swift`) logs per-surface `contentsScale` and `drawableSize` and can name a surface's owner — use it to confirm *which* surfaces released.

```sh
PID=$(ps -Ao pid=,comm= | awk '/Batty Beta\.app\/Contents\/MacOS\/Batty Beta$/{print $1; exit}')
footprint -p $PID | head -14
vmmap $PID | grep '^IOSurface'      # drawable histogram; sizes come in 3s per swap chain
ps -Ao pid=,ppid=,comm= | awk -v p=$PID '$2==p' | wc -l   # Terminal Session count
```

**Baseline to beat** (2026-08-31, release instance, pid 41541): 17 Terminal Sessions, 1 Window on screen, **833 MB footprint**, **578 MB graphics (69%)**, 51 large IOSurfaces = 17 swap chains, **~34 MB graphics per Terminal Session**.

## Out of scope

The spec's *Follow-up work, separate change* section is **explicitly not part of this issue** — renderer occlusion does not touch terminal state, and mixing the two would make the measurement unreadable. Recorded here so it isn't lost; **it likely deserves its own issue** if the user wants it pursued:

- Confirm the pinned libghostty has `scrollback-compression` (default `true`), which transparently compresses non-viewport pages for a reported 70–90% physical memory reduction on those pages. Idle scheduler is `Compression` in `src/renderer/Thread.zig`, on a 250 ms idle timer after renderer wake.
- Consider a lower `scrollback-limit-lines` for background or archived Sessions. Prefer the lines limit over the bytes limit; the bytes limit varies unpredictably with Pane width.
- Pin a recent libghostty. There was a large scrollback leak from non-standard page allocation that agent CLIs provoked heavily by emitting multi-codepoint graphemes into primary-screen scrollback — fixed upstream, but older tags are exposed.

This is the same ground as the **MALLOC_SMALL 196 MB across 17 Terminal Sessions (~11.5 MB per Session)** observation already recorded in #0387's Notes and in the umbrella: nothing in the codebase sets a scrollback limit — no configuration, no cap, no eviction.

### Prior art

Both known downstreams implemented per-pane occlusion independently, which is a signal this is the right shape and that upstream will not do it for you:

- **Rootshell** (commercial Ghostty-based Mac terminal), build 138: hidden tabs release their Metal swap-chain resources and restore on show; restored tabs and tmux control-mode panes start with the correct visibility.
- The **Windows Ghostty fork** lists renderer occlusion for hidden tabs, zoomed-out splits, and minimized windows as an added feature.

## Investigation findings (2026-08-31) — the premise is refuted

**Measured on a Beta build; the Prod app was never disturbed.** Scenario: one
window, 6 Sessions, Session 1 split into 2 Panes (7 Panes total), 2 visible,
5 hidden and filled with heavy scrollback.

### The swap chains do not respond to occlusion

| Condition | IOSurfaces | Layers |
|---|---|---|
| Shipped code, Panes hidden 20 s+ | 21 | 7 |
| Hidden Panes' `AppTerminalView`s forcibly `removeFromSuperview()`'d, surface and PTY left intact, 90 s+ | 21 | **unchanged** |
| Whole app hidden via Cmd-H (every Pane occluded), 20 s+ | 21 | **unchanged** |

Every geometry is a clean triple (672×416 ×15, 334×416 ×6) — one
`swap_chain_count = 3` per Pane, hidden or not.

### Occlusion delivery was confirmed at runtime, not inferred

Debug logging was added at all three `TerminalHostStore` call sites and the
values observed live via `log stream` (Beta pid 40706):

| Tab | Role | Last logged `effective` |
|---|---|---|
| AD21 | visible | `true` |
| E800 | visible (the split) | `true` |
| 0FAC / 1980 / 5EDB / FE16 / 9BF5 | hidden | `false` |

A `vmmap` sample taken immediately after still showed 21 IOSurfaces. On
Cmd-H, `setWindowOcclusionVisible` logged `effective=false` for **all 7** tabs
at 17:52:48.828 — and the sample taken right after was still 21. Restoring
the window flipped only the two visible tabs back to `true`.

This distinction matters because #0387 was undone by exactly the inverse
mistake: a call chain that read correctly end to end while the effect never
happened. Here the effect *is* delivered and the memory still does not move.

### What this rules out

- **Spec item 5 (the retained `CAMetalLayer` holds the IOSurfaces) is
  refuted.** Detaching the hosting view — the mechanism the spec wants
  shipped, and which `docs/view-hierarchy.md` forbids outside the tab-close
  path — changed nothing. Shipping it would have broken a guarded invariant
  for no measured benefit.
- **Batty's occlusion signalling is already per-Pane and correct.**
  `PaneView.swift:238` computes `tab.id == pane.activeTabID && isSessionSelected`,
  and all three `TerminalHostStore` sites derive from live state through one
  shared `effectiveSurfaceVisible(placementVisible:windowVisible:)`.
- **`isApplicationActive` is not a confound.** `setApplicationActive(_:)` has
  zero callers on the AppKit path in the pinned checkout (the only callers are
  UIKit-only), so it never leaves its `true` default on macOS and Cmd-H
  reaches the surface solely through `setWindowOcclusionVisible`.

### What remains open, but costs nothing today

The spec calls correct initial occlusion state at surface creation "the
highest-value correctness detail". Every observed `created terminal view for
tab X` was followed by its first occlusion apply within 6–9 ms with the
correct value — but that is because **no current code path creates a surface
into an already-hidden state**: every new Session/Tab becomes active
immediately, and restore-at-launch was removed in #0172. So the failure mode
is *unexercised*, not disproven. It becomes live again if session restore or
background Tab creation returns.

### Consequence

No Batty-side change — consolidation, detach, or otherwise — reclaims this
memory at the pinned libghostty revision. The remaining path is **#0293**'s
upstream ask, whose reviewed draft at `issues/0293/upstream-issue.md` has
never been submitted. The umbrella #0285 anticipated exactly this outcome.

### Adjacent finding, worth its own issue

Fresh Beta launches were hanging with **zero windows** because
`NSApplication`'s own state restoration
(`_reopenWindowsAsNecessaryIncludingRestorableState`,
`hasPersistentStateToRestore=1`) stalled before any Batty code ran — confirmed
by a live `log stream` showing the restoration attempt and then silence.
`open -n <App> --args -ApplePersistenceIgnoreState YES` works around it
reliably. This is adjacent to **#0386** and may mean that issue's diagnosis is
incomplete: the same flag surfaced in both investigations.
