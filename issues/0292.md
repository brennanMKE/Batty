## Description

The C API already supports everything needed to run every Tab on one shared `ghostty_app_t`: `ghostty_surface_config_s` carries per-surface `command`, `env_vars` / `env_var_count`, `wait_after_command`, `working_directory`, and `font_size` (`ghostty.h:479-496` @ 1.3.2; verified against `BattyKit/.build/artifacts/libghostty-spm/libghostty/GhosttyKit.xcframework/macos-arm64_x86_64/Headers/libghostty/ghostty.h` — the earlier `452-469` citation was against a stale 1.2.2 header). But the libghostty-spm wrapper at 1.3.2 wires up only `env_vars`, `font_size`, and `working_directory` (`TerminalController+Surface.swift:22-40` @ 1.3.2) — **not `command` and not `wait_after_command`**.

The consequence for Batty: after #0287 moves ordinary Tabs onto a shared controller, `-c` panes (#0282) must stay on dedicated per-pane controllers, because their `command` override and `wait-after-command` can only be expressed at controller (app-config) level (`TabRuntime.swift:143-209`). Adding the two missing fields to `TerminalSurfaceOptions` and `createSurface` is small and additive — the C struct already carries both — and would let `-c` panes join the shared controller too.

This is an **upstream contribution**: file the ask at github.com/Lakr233/libghostty-spm. This Batty issue tracks the upstream ask and the follow-up dependency bump that adopts it.

## Root cause

`ghostty_surface_config_s` carries per-surface `command` and `wait_after_command` (verified at `ghostty.h:479-496`, fields at `:490` and `:494`), but libghostty-spm's `TerminalSurfaceOptions` exposes only `backend`, `fontSize`, `workingDirectory`, `envVars`, and `context`, and `createSurface` never populates the two command fields. An embedder that needs a per-Tab command override must therefore give each such Tab its own `ghostty_app_t`, since `command` is only expressible through app-level config.

## Fix

`issues/0292/upstream-issue.md` — a self-contained write-up for github.com/Lakr233/libghostty-spm: the C-API evidence, the exact gap in `createSurface`, why an embedder cannot work around it in its own tree, and a spelled-out patch shape (two new properties, `withCString`-scoped `command` population, `isEquivalent` updated, `waitAfterCommand` as `Bool?` written only when set so it preserves whatever `ghostty_surface_config_new()` established).

## Review

Round 1 blocked on five items, two of which were substantive. Every `ghostty.h` citation had been taken from a **stale 1.2.2 header** left in DerivedData from before #0286, while the draft stated in bold that it reported against 1.3.2 — the struct is at 479-496, not 452-469. Round 2 approved after the reviewer personally re-verified every header line against the correct 1,227-line file and confirmed provenance by a fingerprint: 1.3.2 carries 98 `GHOSTTY_API` prefixes, 1.2.2 carries zero, so the quoted declarations could only have come from 1.3.2.

## Expected behavior

`TerminalSurfaceOptions` exposes `command` and `waitAfterCommand`, `createSurface` populates the corresponding `ghostty_surface_config_s` fields, and Batty (after a bump to the release containing the change) moves `-c` panes onto the shared controller.

## Actual behavior

Per-surface `command` / `wait_after_command` are unreachable through the wrapper; any pane needing them needs its own `ghostty_app_t`, with its own glyph-atlas set and threads.
