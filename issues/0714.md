## Description

An automated test can't drive a Sparkle update in Batty Beta: every step (update found, download, "Install and Relaunch") waits for a click in Sparkle's standard UI. The Sparkle update VM test (#0715) needs the update to install and relaunch on its own, so the VM run doesn't depend on XCUITest clicks.

Add a **Beta-only auto-confirm hook**: an environment variable or launch argument that, **only in a Beta build and only when it is set**, makes Sparkle check, download, install and relaunch with no UI. Prod ignores it completely. With the hook unset, a Beta behaves exactly as today.

This gets its own issue so it is reviewed on its own, even though #0715 is its only user. The #0715 implementation may carry it if the orchestrator chooses, but this issue's acceptance and review still apply.

## Root cause

Starting state (feature work): `UpdaterController` always built `SPUStandardUpdaterController`, whose standard user driver waits for a click at every step (update found, ready to install). Nothing let an automated run install an update without UI.

## Resolution notes

> 🟢 Resolved 2026-11-21 — A Beta-only `BATTY_BETA_SPARKLE_AUTO` hook drives a headless `SPUUpdater` with a no-UI user driver, armed at launch and triggered by a distributed notification; Prod and an unhooked Beta build the standard updater exactly as before.

- **Comment claims** grepped and true ("variant checked first", "Creates the updater at launch only when…", "Never calls `retryTerminatingApplication`", the type doc comment).

## Fix

Followed the plan. A custom `SPUUserDriver` (`SparkleAutoConfirmUserDriver`) drives a headless `SPUUpdater`, used only when `SparkleAutoConfirm.backend(mode:hasFeedURL:)` returns `.headless`, which needs the Beta bundle id, `BATTY_BETA_SPARKLE_AUTO` set to exactly `relaunch` or `onquit`, and a non-empty `SUFeedURL`. Otherwise the `.standard` branch builds `SPUStandardUpdaterController(startingUpdater: hasFeedURL, updaterDelegate: nil, userDriverDelegate: nil)`, as before. `UpdaterController.armAutoConfirmIfRequested()` (called from `applicationDidFinishLaunching`) creates `shared` at launch only when the hook is set.

The contract #0715 depends on is exactly the plan's "The contract #0715 depends on" section: variable `BATTY_BETA_SPARKLE_AUTO` (`relaunch` | `onquit`), set with `open --env BATTY_BETA_SPARKLE_AUTO=relaunch -a "/Applications/Batty Beta.app"`; trigger: distributed notification `co.sstools.Batty.beta.sparkle-auto.check`, posted after `sparkle-auto: armed mode=…`; log subsystem = bundle id, category `SparkleAutoConfirm`, every line prefixed `sparkle-auto: ` with the messages listed in the plan.

Decisions:
- **Triggered check, not launch-time check (orchestrator accepted the plan's deviation).** With the hook active the app arms the headless updater at launch and checks only when the distributed notification arrives, because #0715 must set up Sessions and a baseline before the update installs.
- No Prod log line: Prod ignores the hook completely.

Deviations from the plan:
- Swift imports two driver methods under renamed names: `show(_:reply:)` (permission request) and `showReady(toInstallAndRelaunch:)`. The non-async completion-handler overloads were used for the rest.
- `SparkleAutoConfirm` is declared `nonisolated public enum` (not per-member `nonisolated`), so its nested `Mode`/`Backend` `Equatable` conformances are usable from nonisolated tests.
- `BattyKit/Package.swift` needed no change: the tests import Sparkle transitively.
- If `SPUUpdater.start()` throws, the controller falls back to a non-started `SPUStandardUpdaterController` and logs `start failed`, as planned.

## Plan

Planned 2026-11-21 against `main` at `ed866903`. Sparkle is 2.9.1 (`BattyKit/Package.resolved`); every Sparkle API named below was checked in its headers under `BattyKit/.build/artifacts/sparkle/.../Headers/`.

### Premises checked

- `UpdaterController` is as the issue says. It is used only through `UpdaterController.shared.isConfigured` and `.checkForUpdates()` (`Commands/BattyCommands.swift:288-290`, `Views/CommandPaletteView.swift:124-129`); nothing reads its public `controller` property. `shared` is created lazily, the first time the menu or the Command Palette touches it.
- `Configuration/Info.plist` sets `SUEnableAutomaticChecks = true`, so Sparkle never asks the "check automatically?" permission question in any build. `SUFeedURL` and `SUPublicEDKey` come from `SU_FEED_URL` / `SU_PUBLIC_ED_KEY`, which `Beta.xcconfig` blanks.
- `ServiceNames.Variant(bundleIdentifier:)` (`BattyXPCCore/ServiceNames.swift`) returns nil for nil or unknown ids; `FeatureFlags.resolved(bundleIdentifier:environment:)` is the pattern to copy.
- `open --env VAR=value` exists on this host's `open` (checked with `open -h`) and sets the variable in a LaunchServices-launched app's environment. It applies only when `open` launches a new process, not when it activates a running one.
- `applicationShouldTerminate` (`Batty/BattyApp.swift:122`) can defer termination for a Project Editor question (`handleTerminateRequest`). Sparkle's install-and-relaunch sends a quit event, so a dirty Project Editor would hold the install. That is a #0715 harness concern (don't leave a Project Editor dirty), noted below; the hook does not bypass the quit path.

### Design decision: a custom `SPUUserDriver` driving an `SPUUpdater`, not delegates

The standard user driver always shows its own windows for a user-initiated check, an update found and "ready to install"; `SPUStandardUserDriverDelegate` can only influence scheduled-check reminders, and `SPUUpdaterDelegate` can't answer the driver's prompts. Sparkle 2's documented headless route is `SPUUpdater(hostBundle:applicationBundle:userDriver:delegate:)` with our own `SPUUserDriver` (a `@MainActor` protocol). It replies to every prompt in code, has no UI to fall back to, and is used only when the hook is active, so the standard path stays byte-for-byte as today.

### Deviation from the issue: the check is triggered, not run at launch

The issue says the hook checks the feed once at launch. #0715 can't use that: its steps 9 to 11 launch A with the hook, then set up Sessions and record a baseline, and only then trigger the update. A launch-time check would install B before any Session exists. So with the hook active the app **arms** the headless updater at launch and **checks when told to**, through a distributed notification. No scheduled-check wait and no permission prompt either way. No UI, no CLI verb, no menu item (progressive disclosure is untouched: nothing exists unless the env var is set in a Beta).

### The contract #0715 depends on (binding names)

- **Environment variable:** `BATTY_BETA_SPARKLE_AUTO`. Exact, case-sensitive values:
  - `relaunch` → `.installAndRelaunch`: download, then install and relaunch (reply `.install` at "ready to install").
  - `onquit` → `.installOnQuit`: download and stage, then reply `.dismiss` at "ready to install", so Sparkle installs when the app quits, with no relaunch (header: "Note the update may still be installed automatically after the application terminates").
  - Anything else (unset, empty, `1`, `Relaunch`, padded) → hook off. In a Beta, a set-but-unrecognized value logs one `.error` (`sparkle-auto: ignored: unrecognized value "<v>"`) and behaves exactly as unset.
- Honored only when `Bundle.main.bundleIdentifier` is `co.sstools.Batty.beta` **and** `SUFeedURL` is non-empty. Beta with the hook set and an empty feed: one `.error` (`sparkle-auto: ignored: SUFeedURL is empty`), then today's behavior.
- **Prod (`co.sstools.Batty`), nil or unknown bundle id:** ignored completely, no log line (the optional Prod notice is left out: "ignores completely" is simpler to prove).
- **How to set it:** `open --env BATTY_BETA_SPARKLE_AUTO=relaunch -a "/Applications/Batty Beta.app"` on a not-running app. Not `launchctl setenv` (it leaks into the app Sparkle relaunches and every later launch) and not `--args` (not read). The relaunched B starts without the variable and runs the standard driver; with `SUEnableAutomaticChecks = true` it shows no permission prompt, and B's feed holds nothing newer, so it shows nothing.
- **Trigger:** distributed notification named `co.sstools.Batty.beta.sparkle-auto.check` (no object, no userInfo), observed only while the hook is active. Post from the guest with no TCC grant:
  `osascript -l JavaScript -e 'ObjC.import("Foundation"); $.NSDistributedNotificationCenter.defaultCenter.postNotificationNameObjectUserInfoDeliverImmediately("co.sstools.Batty.beta.sparkle-auto.check", $(), $(), true)'`
  Post it only after the `armed` line appears. A post while a Sparkle session is in progress logs `.error` and is ignored; there is no retry loop.
- **Log lines** (subsystem = the app's bundle id, category `SparkleAutoConfirm`, every message `.public`, every message starts `sparkle-auto: `). `.notice` unless marked:
  - `sparkle-auto: armed mode=relaunch|onquit` (headless updater started; ready for the trigger)
  - `sparkle-auto: start failed: <domain> <code> <description>` (`.error`; the attempt ends, no updater runs)
  - `sparkle-auto: check requested`
  - `sparkle-auto: check ignored: session in progress` (`.error`)
  - `sparkle-auto: permission request answered: automatic checks off` (should never happen given `SUEnableAutomaticChecks`; handled so it can't block)
  - `sparkle-auto: update found version=<displayVersionString> build=<versionString> stage=notDownloaded|downloaded|installing`
  - `sparkle-auto: no update: <description>`
  - `sparkle-auto: downloading`
  - `sparkle-auto: extracting`
  - `sparkle-auto: ready to install`
  - `sparkle-auto: installing and relaunching` (relaunch mode reply)
  - `sparkle-auto: staged for install on quit` (onquit mode reply)
  - `sparkle-auto: installing applicationTerminated=<true|false>`
  - `sparkle-auto: installed relaunched=<true|false>`
  - `sparkle-auto: error: <domain> <code> <description>` (`.error`; acknowledged, the attempt ends)
  - `sparkle-auto: dismissed`
  - `sparkle-auto: ignored: unrecognized value "<v>"`, `sparkle-auto: ignored: SUFeedURL is empty` (`.error`, Beta only)

  #0715 waits on these with `log stream --predicate 'subsystem == "co.sstools.Batty.beta" AND category == "SparkleAutoConfirm"'` (or `log show` after the fact), never by sleeping.

2. **Add `BattyKit/Sources/BattyKit/Updater/SparkleAutoConfirmUserDriver.swift`** — `final class SparkleAutoConfirmUserDriver: NSObject, SPUUserDriver` (`@MainActor`, the protocol is `NS_SWIFT_UI_ACTOR`). `init(mode: Mode, log: @escaping (OSLogType, String) -> Void)`; the default sink used by `UpdaterController` writes to the file's `Logger` with `privacy: .public`. The sink receives the message **without** the prefix and the driver adds `logPrefix` itself, so tests see exactly what is logged. Each callback logs its line from the list above and replies at once:

   - `showUserInitiatedUpdateCheck(cancellation:)` → nothing (no log; `check requested` is logged by the controller).

   - `showDownloadInitiated` → `downloading`; `showDownloadDidStartExtractingUpdate` → `extracting`.
   - `showReadyToInstallAndRelaunch` → `ready to install`, then the mode's line, then reply `readyToInstallChoice(mode:)`.
   - `showInstallingUpdate(applicationTerminated:retryTerminatingApplication:)` → log only; **never** call `retryTerminatingApplication` (no retry loop).
   - `showUpdateNotFound(error:acknowledgement:)` → `no update`, acknowledge. `showUpdaterError(_:acknowledgement:)` → `.error`, acknowledge. `showUpdateInstalledAndRelaunched(_:acknowledgement:)` → log, acknowledge. `dismissUpdateInstallation` → `dismissed`.
   - Use the non-async (completion-handler) overloads; if Swift only offers the `async` forms for the `NS_SWIFT_ASYNC(2)` methods, implement those and log before returning.

## Background

- `UpdaterController` (`BattyKit/Sources/BattyKit/Updater/UpdaterController.swift`) wraps `SPUStandardUpdaterController(startingUpdater: hasFeedURL, updaterDelegate: nil, userDriverDelegate: nil)`. The updater only starts when `SUFeedURL` in `Info.plist` is non-empty.
- `Configuration/Beta.xcconfig` blanks `SU_FEED_URL` and `SU_PUBLIC_ED_KEY`, so a Beta never starts Sparkle today. #0715 adds opt-in build settings (`BATTY_BETA_FEED_URL`, `BATTY_BETA_ED_PUBLIC_KEY`) so a test package carries a feed and a throwaway key. This hook only matters in such a package.
- The variant is known at runtime from the bundle identifier: `ServiceNames.Variant(bundleIdentifier:)` (`.beta` is `co.sstools.Batty.beta`), the same way `FeatureFlags.resolved` and `AgentIntegrationModel` decide.

## Expected behavior

- With the hook set in a Beta whose `SUFeedURL` is non-empty:
  - At launch the app checks the feed once (no scheduled-check wait, no first-launch "check automatically?" prompt).
  - When an update is found, it downloads, then installs and relaunches with no window, sheet or alert from Sparkle.
  - A second mode installs **on quit** instead: it downloads and stages the update, then installs when the app quits, with no relaunch. #0715 uses it to cover Sparkle's install-on-quit path.
  - Every step (found, downloaded, installing, relaunching, staged for quit, any error) is logged at `.notice` or `.error` with a fixed prefix (for example `sparkle-auto:`), so the harness can wait on log lines instead of sleeping.
  - Any Sparkle error is logged and ends the attempt; the hook never retries forever or falls back to the standard UI.
- With the hook unset, or in Prod (`co.sstools.Batty`) with it set: behavior is exactly today's. Same `SPUStandardUpdaterController` construction, same delegates (none), no extra check at launch, no log line beyond one `.notice` in Prod saying the hook was ignored (optional, plan decides).

## Approach (the plan decides the details)

- A custom `SPUUserDriver` that answers every prompt (permission request, update found, download progress, ready to install) without UI, or the standard driver plus `SPUUpdaterDelegate`/`SPUStandardUserDriverDelegate` hooks. Sparkle 2's `SPUUpdater` with a custom user driver is the documented way to run headless. The plan picks one and says why.
- A pure decision function, for example `SparkleAutoConfirm.mode(bundleIdentifier:environment:arguments:) -> Mode?` (`nil`, `.installAndRelaunch`, `.installOnQuit`), so the gate is unit-tested without Sparkle. `UpdaterController.init` reads it once.
- The name of the variable is the plan's choice. Suggested: `BATTY_BETA_SPARKLE_AUTO=relaunch|onquit`. #0715's harness launches the app with it (`open --env`, `launchctl setenv` in the guest, or `--args`; the plan checks which reaches a LaunchServices-launched app). Sparkle's relaunched app does not need the hook.
- No new menu item, Settings row, CLI verb or visible UI (AGENTS.md "progressive disclosure"). This is a test seam only.

## Acceptance criteria

- [ ] With the hook set in a Beta package built with a test feed (#0715), Sparkle installs and relaunches with no UI; the "install on quit" mode stages the update and installs it at quit.
- [ ] With the hook unset, a Beta constructs the updater exactly as today (no custom driver, no launch-time check).
- [ ] **Prod ignores the hook.** A unit test proves the decision function returns `nil` for the Prod bundle id with every hook value set, and for an unknown or `nil` bundle id. A second test proves the Beta bundle id with the variable unset or with an unrecognized value returns `nil`.
- [ ] Unit tests cover each recognized value for the Beta bundle id.
- [ ] If the custom user driver has logic of its own (what it replies to each callback), it is unit-tested through an injected reply sink, with no Sparkle network activity and no sleeps (AGENTS.md "Asynchronous tests").
- [ ] `./build.sh` and `./build.sh unit` pass. The Release archive check builds (Sparkle generics and a new class at `-O`).
