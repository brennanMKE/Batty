# 0357 — Process Status disclosure sections show measured-looking zeros for dead processes and stale zeros before first expansion

| | |
|---|---|
| **Status** | open |
| **Module** | Pane |
| **Platform** | macOS |
| **First seen** | 2026-08-21 |

## Description

Two related honesty problems in `ProcessStatusPaneView`'s disclosure sections:

1. **Disclosures render in the `.exited` state.** The `runState` switch shows `disclosures` in both the `.running` and `.exited` branches. Expanding "Open Files" or "Child Processes" on a dead pid calls `content.openFiles()` / `content.childProcesses()`, which mask the failed read as an empty measurement: `ProcessInspector.listOpenFileDescriptors(pid:) ?? []`. The user sees "Open Files (0)" — a confident, measured-looking zero — for a process that no longer exists and cannot be inspected.
2. **Collapsed labels always read "(0)" until first expanded.** The counts in the `DisclosureGroup` titles come from local `@State` arrays (`openFiles`, `childProcesses`) that are only populated by the `.onChange(of: isExpanded)` handlers. Before the first expansion the label says "Open Files (0)" even while the metrics row above it shows a real nonzero `openFileCount` from the same snapshot — the pane contradicts itself on screen.

The on-demand loading itself is correct and deliberate (design §3.4: never per-tick); the defects are the `?? []` masking and the label's data source, not the laziness.

## Expected behavior

In the `.exited` state the disclosures are hidden or explicitly marked unavailable — never a fabricated "(0)". A failed read (`nil` from the inspector) is distinguished from a genuine empty result. Collapsed labels either show the snapshot's real count (`openFileCount` for files), a neutral "…", or no count — anything but a wrong number.

## Actual behavior

Dead-pid expansion yields "Open Files (0)" / "Child Processes (0)" via `?? []`; collapsed labels read "(0)" until first expanded regardless of the true counts.
