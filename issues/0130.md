# 0130 — Move the Textual Swift package dependency from the Xcode project into BattyKit

| | |
|---|---|
| **Status** | resolved |
| **Module** | Build / GhosttyKit |
| **Platform** | macOS |
| **First seen** | 2026-05-18 |

## Description

The `Textual` Swift package (`https://github.com/gonzalezreal/textual.git`) is currently declared as an `XCRemoteSwiftPackageReference` at the Xcode project level (`Batty.xcodeproj/project.pbxproj`) and linked directly into the `Batty` app target's Frameworks build phase. Every other third-party SPM dependency in this project (`libghostty-spm`, `SlidingTabs`, `Sparkle`) flows through `BattyKit/Package.swift`. Textual is the odd one out.

Move it to `BattyKit/Package.swift` so package dependencies are managed in one place — the BattyKit `Package.swift` is the canonical manifest for everything Batty links against.

## Acceptance criteria

- `Textual` is declared as a `.package(url: "https://github.com/gonzalezreal/textual.git", …)` entry in `BattyKit/Package.swift`'s `dependencies` array, pinned to whatever version the Xcode project currently resolves to (preserve the same resolved version — don't silently upgrade).
- The `BattyKit` target lists `.product(name: "Textual", package: "textual")` in its dependencies.
- The `XCRemoteSwiftPackageReference "textual"`, the `Textual` package product reference, and the `Textual in Frameworks` build file are all removed from `Batty.xcodeproj/project.pbxproj`.
- The single current import site (`Batty/Help/HelpSuccessPaneView.swift:4` — `import Textual`) still resolves. Two viable paths:
  - **(preferred)** Move `HelpSuccessPaneView.swift` (and any tightly-coupled Help views) into `BattyKit` so the `import Textual` happens inside the package that owns the dependency.
  - **(fallback)** Keep `HelpSuccessPaneView.swift` in the app target and re-export Textual from BattyKit via `@_exported import Textual` so the app target reaches it transitively through `import BattyKit`.
- `xcodebuild -scheme Batty -destination 'platform=macOS' build` passes cleanly with no warnings about duplicate package references.
- `Package.resolved` (both the Xcode project's copy and BattyKit's) reflects the move — Textual should appear under BattyKit's resolved set, not the Xcode project's.

## Root cause

Textual was added to the Xcode project via Xcode's "Add Package Dependency…" UI rather than by hand-editing BattyKit's manifest, leaving it as the only third-party SPM dependency not declared in `BattyKit/Package.swift`.

## Fix

- Added Textual to `BattyKit/Package.swift` dependencies (pinned to revision `5b06b811c0f5313b6b84bbef98c635a630638c38`) and added `.product(name: "Textual", package: "textual")` to the BattyKit target.
- Moved all Help views (`HelpView`, `HelpSuccessPaneView`, `HelpSidebarView`, `HelpErrorPaneView`, `HelpCatalog`, `HelpSection`, `HelpLoadError`) from `Batty/Help/` into `BattyKit/Sources/BattyKit/Views/Help/`. `HelpView` made `public`; others remain internal.
- Moved all `.md` resource files from `Batty/Help/` to `BattyKit/Sources/BattyKit/Help/` and added `.copy("Help")` resource rule to BattyKit target. Updated `HelpView` to use `Bundle.module` and `HelpSuccessPaneView` to resolve the base URL via `Bundle.module.resourceURL`.
- Removed all Textual entries from `Batty.xcodeproj/project.pbxproj` (PBXBuildFile, PBXFrameworksBuildPhase, packageProductDependencies, packageReferences, XCRemoteSwiftPackageReference section, XCSwiftPackageProductDependency entry).

## Files changed

- `BattyKit/Package.swift`

- `BattyKit/Sources/BattyKit/Help/` (8 new .md files)

## Gotchas

- Build was verified with `xcodebuild ... CODE_SIGN_IDENTITY=- CODE_SIGNING_REQUIRED=NO build` — UI sign-off of the Help window content not verified headlessly.

## Notes

- BattyKit is the right home: `Package.swift` already pulls in `libghostty-spm`, `SlidingTabs`, and `Sparkle`, so there's an established pattern. Keeping Textual at the project level was likely accidental — probably added via Xcode's "Add Package Dependency…" UI rather than by hand-editing the manifest.
- The only consumer today is the Help view, which renders Markdown content from the bundled `01-overview.md` … `08-drag-and-drop.md` files. Moving the Help renderer into BattyKit alongside the rest of the UI surface is consistent with where `SessionSidebarView`, `RenameTabSheet`, etc. already live.
- Watch for the Help markdown resources — they're currently in `Batty/Help/*.md` and presumably bundled via the app target. If `HelpSuccessPaneView` moves into BattyKit, the `.md` resources need to move too (or the view needs a `Bundle` parameter so the app can pass `Bundle.main`).
- Verify the resolved Textual version before and after the move (`xcodebuild -resolvePackageDependencies` then diff the `Package.resolved` files). A version bump should be a separate, intentional decision.
