## Description

Pull in libghostty via the prebuilt `libghostty-spm` Swift Package (Path A from `batty-getting-started.md` §4). Without `GhosttyKit` linked, no Terminal Session can be created — every subsequent issue depends on this.

**Acceptance criteria:**
- `xcodebuild -scheme Batty -destination 'platform=macOS' build` resolves and builds the package.
- `import GhosttyKit` compiles in a Swift file in the `Batty` target.
- A trivial smoke check (`ghostty_app_new` or equivalent) links cleanly. A unit test in `BattyTests` is enough; nothing needs to render yet.

## Notes

- Prefer the prebuilt xcframework path now; we can switch to building from source (Path B) later if we need to pin a specific libghostty commit or patch its C API.
- Carbon, Metal, and MetalKit linker frameworks may be required at the app target level; verify after adding the package and add explicitly if the SPM package doesn't pull them in.
- Pin to a specific package version once we know which surface API surface we rely on. The libghostty C API is pre-1.0 and explicitly in flux (PRD §11).

## Root cause

Greenfield setup: libghostty had not yet been linked into the project. `import GhosttyKit` did not resolve, so no Terminal Session work could begin.

## Fix

Declared `libghostty-spm` (https://github.com/Lakr233/libghostty-spm) as a dependency of the local `BattyKit` Swift package and re-exported `GhosttyKit` from `BattyKit`. The Xcode `Batty` app target now consumes `BattyKit` (not `GhosttyKit` directly) so all third-party dependencies are declared in `BattyKit/Package.swift` rather than in `project.pbxproj`. A smoke file in the `Batty` target references `ghostty_config_new` to force linker resolution at build time.

## Files changed

- `BattyKit/Package.swift` — added `platforms: [.macOS(.v15)]`, declared the libghostty-spm dependency pinned to `exact: "1.0.1777879537"`, and added `.product(name: "GhosttyKit", package: "libghostty-spm")` to the `BattyKit` target.
- `BattyKit/Sources/BattyKit/BattyKit.swift` — replaced placeholder content with `@_exported import GhosttyKit` so consumers of `BattyKit` see GhosttyKit symbols transitively.
- `BattyKit/Package.resolved` — new; pins the package graph (libghostty-spm 1.0.1777879537, MSDisplayLink 2.1.0).
- `Batty.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved` — new; the workspace-level lock Xcode reads when resolving for the app target.
- `Batty.xcodeproj/project.pbxproj` — added an `XCSwiftPackageProductDependency` for `BattyKit` referencing the existing local package, a matching `PBXBuildFile`, registered the build file in the `Batty` target's Frameworks build phase, and listed the product dependency in the `Batty` target's `packageProductDependencies`.
- `Batty/GhosttySmoke.swift` — new; minimal `@MainActor enum GhosttySmoke` that captures `ghostty_config_new` as a function value to force linking of a libghostty C symbol.

## Gotchas

- **Version pinning strategy.** libghostty-spm tags follow `1.0.<unix-timestamp>` (e.g. `1.0.1777879537`). The "1.0" prefix is cosmetic; functional changes ride the timestamp. `.upToNextMajor` would silently accept any future tag, which is the opposite of what the issue notes ask for given the pre-1.0 C API churn. Pinned with `exact:` instead so version bumps are explicit.
- **Product name is `GhosttyKit`.** Confirmed against the upstream `Package.swift` — the package also exports `GhosttyTerminal`, `GhosttyTheme`, and `ShellCraftKit`, but only `GhosttyKit` is needed for the C-API surface this issue scopes to.
- **Pbxproj id strategy.** Existing object ids are 24-hex with prefix `26D543…`. Used `26AA0001000000000000000{1,2}` for the two new objects so they are visually distinct and don't risk collision with anything Xcode generates. Xcode may rewrite these on first open; that's fine.
- **`ENABLE_APP_SANDBOX = YES`** is currently set in the per-target Debug/Release configs even though `CLAUDE.md` says it should be `NO` for an unsandboxed terminal. Out of scope for this issue; flagging here. The smoke build still passes because nothing runs sandboxed code yet.
- **Xcconfig warning.** Build emits `SDK condition on SDKROOT is unsupported, so the SDKROOT[sdk=macos*] assignment at the project-xcconfig level will be ignored.` — pre-existing, unrelated to this change.
- **Two `Package.resolved` files.** The package-level one (`BattyKit/Package.resolved`) and the workspace-level one (`Batty.xcodeproj/.../swiftpm/Package.resolved`) are both produced and identical for now. Both are committed so the package graph is reproducible whether resolved via SPM CLI or Xcode.
