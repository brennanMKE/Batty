# 0577 — Settings has no way to add a background catalog URL, so users can't browse Background Sets hosted anywhere but the Batty website

| | |
|---|---|
| **Status** | open |
| **Module** | Settings |
| **Platform** | macOS |
| **First seen** | 2026-11-11 |

## Description

Let users add their own Background Catalog URLs in Settings. Each is an `https` URL to a JSON file in the #0574 format. Batty checks every catalog regularly, shows each URL's state and errors beside it, and lists its sets in the Background Images window's Browse view next to the built-in catalog. Child of [#0574](0574.md). Depends on [#0576](0576.md) for the fetcher, parser, caches, download pipeline and Browse UI. Targets 1.4.0.

User request (2026-11-11, part): "And in Settings we'd allow users to add their own URL to a .json file for background image sets. The URLs for json files in Settings should be checked regularly."

A user URL is untrusted input from an unknown server, so this issue also sets the limits and decoding rules that #0576's pipeline enforces for every catalog, built-in included.

> **Amended 2026-11-11 by the Plan.** This Description predates #0574 decisions 8 to 12 (PNG or JPEG, select-to-download into the hosted store, the simplified `sets` / `name` / `images` format with no `schemaVersion`, ids, `sha256` or sizes, identity = resolved full-size URL). Where it disagrees with `## Plan` → "Amendments to the Description", the Plan wins.

## Root cause

Feature work. After #0576, `HostedBackgroundsModel` listed only the built-in catalog (`HostedBackgroundsDependencies.catalogURLs` defaulted to it and nothing overrode it), nothing checked catalogs on a schedule, and Settings had no way to add a URL. `HostedImageStore` had no way to drop a catalog's records, and the decode and `URLSession` paths had no seams to prove the limits by test.

## Fix

Followed the Plan (including the Amendments table and "image title is required"; #0581 has landed, so `aCatalogWithAnUntitledImageIsRefusedNamingTheTitlePath` is enabled).

- `BackgroundCatalogURLs.normalize` / `BackgroundCatalogURLRefusal` (pure). Preferences: `backgroundCatalogURLsKey` (array of strings), `backgroundCatalogsAutoCheckKey` (default on).
- `HostedBackgroundsModel`: `userCatalogURLs` (observed, written only by add/remove), `catalogURLs`, `scheduledCatalogURLs`, `catalogRows`, `loadCatalogRows()`, `isAddingCatalog`, `addCatalog(_:)`, `removeCatalog(_:)`. `HostedCatalogState` gains `lastChecked`, `failingSince`, `unreachableSince(now:)` (7 days, fetch failures only). `update` ignores URLs no longer listed and `performRefresh` returns after its fetch if the catalog was removed, so a removal racing a refresh leaves no cache and no row. The `catalogURLs` dependency closure is gone.
- `BackgroundCatalogCacheState.failingSince` (optional; set on the first error, cleared by a success or `store`).
- `HostedImageStore.removeRecords(for:)` (never deletes `Hosted/<digest>/`) and an `importImage` seam; `URLSessionBackgroundCatalogFetcher(protocolClasses:)` seam. `HostedThumbnailLoader` already had a `decode` seam, so it needed no change.
- `BackgroundCatalogScheduler` (30 s launch delay, then every 24 h on the injected clock, one catalog at a time, reads the toggle each tick), started from `AppStateStore.startBackgroundCatalogChecks()` in `BattyAppDelegate`'s first-quiescence closure. It does not start in a UI-test launch (any `BATTY_UI_TEST_*` variable) without a catalog fixture folder.
- `BackgroundCatalogsSettingsSection` below the Background section in Settings → Appearance, with the accessibility ids from the Plan. `BackgroundSetsView` headers: "Batty" for the built-in, host, or host + path when two catalogs share a host.
- `FixtureBackgroundCatalogFetcher` serves `https://<host>/<path>` from `<dir>/hosts/<host>/<path>`; UI fixture helpers `writeHostedCatalog` / `writeHTML`.
- Help (`11-backgrounds.md`) and `website/privacy.html` updated (not deployed).

Divergences:
- **Test seam not in the Plan:** `HostedBackgroundsModel.onCatalogForgotten`, called once `removeCatalog` has dropped the URL and before it awaits a running refresh. `removingDuringARefreshLeavesNoCacheAndNoRow` releases the held fetch from it, so the race is ordered by an event, not by polling.

## Gotchas

- `hasBrowsed` is read from defaults, not observed; the built-in row's Check Now re-enables on the next render after the first Browse (the Browse's own refresh changes the row state, which re-renders it).
- Visual sign-off for the Settings section (row layout, status colors, the relative "checked" text) is the user's.
- The status line's relative time is computed in `body` from `Date()` and doesn't tick on its own. It updates when the row's state changes or Settings is reopened.
- The website change is not deployed; it goes out with the release.

## Settings UI

- **Where:** Settings → Appearance, in a new **Background Catalogs** section below the existing **Background** section (`TerminalBackgroundSettingsSection` in `BattyKit/Sources/BattyKit/Views/SettingsView.swift`).
- **List:** the built-in catalog first, labelled "Batty (built in)", with no Remove. Then the user's URLs in the order added. Each row shows the catalog's `name` (or the host until the first fetch), the URL, and a state: *Checking…*, *Up to date · checked 2 h ago*, or an error (below). Each row has a Check Now button.
- **Add:** a text field and Add button. **Validation on add**, before anything is saved:
  1. It parses as a URL with scheme `https` and a host. Anything else ("Only https:// URLs can be added") is refused, including `http`, `file`, `data`, and a URL with user info (`user:pass@`). Private and local hosts are open question 2.
  2. It is not already in the list, compared after normalizing (lowercased scheme and host, no default port, no fragment).
  3. Batty fetches it once, and it must parse as a valid catalog within the limits below. The error is shown inline and nothing is saved until it passes. A catalog with a newer `schemaVersion` may be added, with its "needs a newer version" state.
- **Remove:** deletes the URL, its cached catalog and its cached thumbnails. Images already downloaded from it **stay in the library**, along with their uses. Only the user's Remove in Background Images deletes them (Concepts.md `## Background Images`). The download records for that URL are dropped, so the same image added back later shows as Not downloaded.
- **Storage:** the URL list is in `UserDefaults` under a new `SettingsPreference` key, `co.sstools.Batty.backgroundCatalogURLs` (`BattyKit/Sources/BattyKit/Settings/SettingsPreferences.swift`), as an array of strings, per variant like every other preference. Per-URL refresh state (validators, last checked, last error) lives in #0576's cache folder, not in `UserDefaults`. Tests isolate `UserDefaults` per `docs/isolate-userdefaults-in-tests.md`.
- **Limit:** at most 20 user URLs.

## Regular refresh

- **When:** at launch (30 s after the first Window is up, so it doesn't compete with startup), then every **24 hours** while Batty runs, plus Check Now and the Browse view's own refresh (#0576, at most once per 10 minutes). One catalog is fetched at a time.
- **Conditional requests:** each catalog is fetched with `If-None-Match` (stored `ETag`) and `If-Modified-Since` (stored `Last-Modified`). A `304` only updates "checked at". A server that sends neither header is fetched in full each time, which is acceptable at this rate.
- **What a refresh fetches:** the catalog JSON only. It never fetches a full-size image (#0574 decision 5) and doesn't prefetch thumbnails. Thumbnails load when Browse shows them.
- **Timer:** driven by the injected `SchedulingClock` (`BattyKit/Sources/BattyKit/Runtime/SchedulingClock.swift`, `docs/async-test-seams.md`). Unit tests advance `TestClock` and never wait on real time.
- **Backoff:** a failed refresh keeps the last good copy and shows the error. Batty retries at the next scheduled check, and doesn't hammer the server. After 7 consecutive daily failures the row reads "Unreachable since <date>". The URL is never removed automatically.
- **Privacy:** before 1.4.0 the user decides whether launch fetches wait until Browse has been opened once, and whether there's a toggle to stop automatic checks (#0574 open question 2). Build both behind one setting so either answer is a default change.

## Limits (all catalogs, built-in included)

| What | Limit | When exceeded |
|---|---|---|
| Catalog JSON | 1 MB, stopped while streaming, not after the full download | "Catalog is larger than 1 MB" |
| Sets / images | 50 sets, 100 images per set, 1,000 images per catalog | rejected as invalid |
| Strings | lengths per #0574 | rejected as invalid |
| Thumbnail file | 2 MB, and at most 1024 px on its longest side by header | that cell shows a placeholder |
| Full-size file | 50 MB, and at most 8192 px on its longest side by header | the download fails and keeps nothing |
| Redirects | 5, `https` only | the request fails |

The 8192 px bound only limits the decode. The importer still downsamples to `TerminalBackgroundImageImporter.maxPixelSize` (4096), because libghostty aborts above 16384 px. Byte limits are enforced on the stream: past `bytes` (when declared) or past the limit, the transfer is cancelled.

## Decoding safely

- **The header comes first.** Batty reads the type and pixel size with `CGImageSourceCopyPropertiesAtIndex` before decoding any pixels, the way `TerminalBackgroundImageImporter.isWithinPixelLimit` already does, and refuses anything that isn't `public.png` or is over the limit. This stops a small file that declares an enormous image.
- **Thumbnails** are decoded only with `CGImageSourceCreateThumbnailAtIndex` and a max pixel size (`BackgroundImageThumbnailer.maxThumbnailPixelSize`), with `kCGImageSourceShouldCache: false` on the source, as `BackgroundImageThumbnailer.downsample` does.
- **Full-size files** are decoded only by `TerminalBackgroundImageImporter.importImage`, through `BackgroundImageLibrary.add(from:)`, which re-encodes to a Batty-owned PNG. Hosted bytes never reach libghostty.
- **Off the main actor.** All decoding happens off the main actor, in the library actor, the thumbnailer actor or a background task.
- **Text from a catalog** (names, titles, credits) is shown as plain `Text`, never as Markdown or a link. The only link is `homepage`, which must be `https`. Control characters are stripped before display.
- **A JSON parse failure** of any kind is an error state, never a crash. Use `JSONDecoder` into value types, with no `try!`.

## Errors shown per URL

Each row shows its own error, short and specific, and the other rows are unaffected: "Not found (404)", "Server error (5xx)", "Can't reach host", "Certificate not trusted" (no override is offered), "Not a background catalog: <first bad path>", "Catalog is larger than 1 MB", "This catalog needs a newer version of Batty", and "Redirected to a non-https URL". Browse shows a broken catalog's last good copy, with the same message on its section header. If it has none, the section shows only the message.

## Tests (unit, BattyKit)

- Add validation: `http://`, `file://`, user info, a duplicate after normalization, the 21st URL, a URL whose body is over 1 MB, and an invalid catalog are each refused with the right message, and nothing is written to the isolated `UserDefaults`. A valid one is saved.
- Remove: drops the URL, its cache folder and its download records, and the library folder for a downloaded image still exists afterwards.
- Refresh: with `TestClock`, advancing 24 h triggers exactly one conditional fetch per catalog. A `304` keeps the cache and its validators are sent. A failure keeps the last good copy and sets the error.
- Limits: an over-limit header (a small PNG declaring 20000 × 20000) is refused without a pixel decode, which a decode-counting fake proves. A body that streams past the limit is cancelled.
- No sleeps or polling (AGENTS.md "Asynchronous tests").

## Open questions

1. Is 24 hours right, or should user catalogs be checked less often (weekly) than the built-in one?
2. Should private and local addresses (`localhost`, `10.x`, `192.168.x`, `.local`) be allowed, for a catalog on the user's own NAS? Allowing them is convenient. Refusing them stops a catalog URL being used to probe the local network. Proposed: allow them, since the user typed the URL.
3. Should a catalog hosted somewhere other than batty.sstools.co need a confirmation on add ("Batty will contact <host> regularly")?

*All three are decided in `## Plan` → "Decisions this plan makes": 24 hours for every catalog; private and local hosts allowed; no confirmation, a caption instead.*

## Acceptance criteria

1. Settings → Appearance → Background Catalogs lists "Batty (built in)" with no Remove button.
2. Adding `http://example.com/catalog.json` is refused with "Only https:// URLs can be added". Adding an https URL that returns HTML is refused with "Not a background catalog". Adding a copy of the Batty catalog hosted elsewhere is accepted, and its sets appear in Background Images → Browse.
3. After the server's copy changes, Check Now shows the new images in Browse. Leaving Batty running past the next daily check does the same without a click.
4. Removing a URL whose image was downloaded and set as the app-wide background leaves the background in place, and the image is still in My Images.
5. Taking the server offline shows "Can't reach host" on that row only, and Browse keeps showing that catalog's last copy.

### Premises checked (on `issue/0576`)

- `HostedBackgroundsModel` (`Model/HostedBackgroundsModel.swift`) already keys everything by catalog URL. Its catalog list comes from `HostedBackgroundsDependencies.catalogURLs`, a closure defaulting to `[BackgroundCatalog.builtInURL]`; no test overrides it. `browseAppeared()` loads cached copies and calls `refresh(_:)` for each URL; `refresh(_:)` coalesces one refresh per URL and already sends `If-None-Match` / `If-Modified-Since` from `BackgroundCatalogCache.state(for:)` when a copy is held, records `lastRefresh` (so Browse's 10-minute throttle counts scheduled checks), and maps errors to `HostedCatalogProblem`.
- `update(_:_:)` **appends** a state for any URL it hasn't seen, and `performRefresh` writes the cache after its `await`s. A refresh still running when its catalog is removed would therefore re-create the row and the cache folder. The Plan closes this (model step 4).
- `BackgroundCatalogCache.removeAll(for:)` exists and removes the catalog's whole folder (`catalog.json`, `state.json`, `thumbnails/`). `BackgroundCatalogCacheState` holds `etag`, `lastModified`, `lastChecked`, `lastError`.
- **There is no `HostedImageRecords.removeAll(catalogURL:)`.** #0576's plan promised one, but the simplified format (decision 12) made `hosted-images.json` records `{url, digest, fetchedAt}` keyed only by the full-size URL, with no catalog URL. This issue adds `HostedImageStore.removeRecords(for:)` keyed by full-size URLs (below).
- The hosted store's copies live in `BackgroundImages/Hosted/<digest>/`, and `BackgroundImageLibrary.scan()` skips promoting a digest only while that folder exists (`isHosted`). A use (app-wide, Project, Pane) keeps its own copy. So **deleting a hosted copy folder would make the next scan promote a use's digest into My Images**; Remove must keep the hosted copy files (also #0574 decision 11: freeing hosted copies is out of scope for 1.4.0).
- `SettingsPreference.backgroundCatalogsBrowsedKey` (`co.sstools.Batty.backgroundCatalogsBrowsed`) is set by `browseAppeared()`; `hasBrowsed` reads it.
- `HostedFetchError.message(host:)` gives the per-row error strings, `BackgroundCatalogError.message` the parse ones. `BackgroundSetsView` already renders one section per `hosted.catalogs` entry, headed by `state.host` when there is more than one.
- `HostedImageStore.fetch` reads the header (`HostedImageHeader.read`, PNG IHDR directly) and refuses over-limit dimensions before calling its private `TerminalBackgroundImageImporter.importImage`; `HostedThumbnailLoader.finish` checks the header before its private `decode(file)`. Neither has a seam to count decodes yet.
- `URLSessionBackgroundCatalogFetcher` builds its own ephemeral `URLSession` lazily, with no injection point for a stub `URLProtocol`.
- `FixtureBackgroundCatalogFetcher` serves only `https://batty.sstools.co/backgrounds/<rest>` and throws `.unreachable` for anything else.
- `website/privacy.html` (on `main`) says Batty makes "no catalog request until you first open the hosted-sets browser" and checks catalogs "from time to time". Adding a URL fetches before that, so the page needs one sentence changed (below).
- The app's launch work runs from `BattyAppDelegate.applicationDidFinishLaunching` (`Batty/BattyApp.swift`), which calls `LaunchWindowGuard.installAtFirstQuiescence { … openContentWindowIfMissing … }`, the point where the first Window is up.

### Decisions this plan makes (the issue's open questions)

1. **Interval: 24 hours for every catalog**, built-in and user alike. Weekly would leave a user-hosted catalog stale for days after its owner updates it; at one small conditional request per catalog per day, 24 h costs nothing.
2. **Private and local hosts are allowed** (`localhost`, `10.x`, `192.168.x`, `.local`). The user typed the URL, a NAS-hosted catalog is a real use, and `https` is still required, so it needs a certificate the Mac trusts. No address-range check.
3. **No confirmation on add.** The section's caption states it once: "Batty checks each catalog at launch and once a day, unless automatic checks are off."
4. **"Unreachable since <date>"** shows when a catalog's checks have failed continuously for **7 days or more** (`now − failingSince ≥ 7 × 24 h`), which is 7 daily checks. It applies to fetch failures (`HostedFetchError`), not to an invalid body, which keeps its "Not a background catalog: …" message. Time-based rather than a count, so repeated Check Now clicks can't trip it.
5. **Scheduled checks** cover the built-in catalog only once `hasBrowsed` is true, and every user URL regardless (the user asked for it by adding it). Adding a URL does **not** set the browsed flag.
6. **Check Now and Browse still fetch with automatic checks off** (user actions). The toggle stops only the launch and 24-hour checks.
7. **Normalization** of a stored URL: trim whitespace, lowercase scheme and host, drop port 443, drop the fragment; keep path and query as typed (paths are case-sensitive). The normalized form is what's stored and compared.
8. **An add that is still fetching** disables the Add button; there is never a second add in flight.
9. **Removing a catalog while one of its images is being fetched** for a pick leaves that fetch to finish: the user picked it.

None of these needs the user; they're recorded here so the reviewer can check them.

### Files to add (`BattyKit/Sources/BattyKit/`, header `// FileName.swift`, file-scoped `logger` only where it logs)

1. **`Settings/BackgroundCatalogURLs.swift`**: pure, `nonisolated` helpers.
   - `enum BackgroundCatalogURLs { static let maxUserCatalogs = 20; static func normalize(_ text: String) -> Result<URL, BackgroundCatalogURLRefusal> }`. Refuses: empty after trimming; not parseable; scheme not `https`; missing or empty host; any `user` or `password`. Then normalizes per decision 7 (rebuild with `URLComponents`).
   - `enum BackgroundCatalogURLRefusal: Error, Equatable, Sendable { case notHTTPS, duplicate, tooMany, fetch(String) }` with `message`: "Only https:// URLs can be added", "This catalog is already in the list", "You can add up to 20 catalogs", and the fetch/parse message as given. Empty input and a URL with user info also use `notHTTPS`'s message (the Description's rule: "Anything else … is refused").
2. **`Model/BackgroundCatalogScheduler.swift`**: `@MainActor final class BackgroundCatalogScheduler`.

### Risks

- **Remove race.** `performRefresh` writes the cache after awaits; steps 2 and 3 of `removeCatalog` plus the `update`/`performRefresh` guards are what stop a removed catalog reappearing. `removingDuringARefreshLeavesNoCacheAndNoRow` must fail with either guard reverted.
- **Scheduler under UI tests.** It must never start in a UI-test launch without the fixture folder, or a long UI run could reach the website.
- **`URLProtocol` stubs** are process-global per class; keying by a per-test host keeps parallel tests independent.
- **Size.** Moderate: three new source files, one view, model additions, four seams, six test suites, one UI test class. If the implementer bails, split: URL helpers, preferences, cache/store changes and model add/remove with their tests first; then the scheduler and launch hook; then the Settings view, fixture and UI tests.
