# 0513 — A late LM Studio stream termination callback discards the handle to a newly spawned stream

| | |
|---|---|
| **Status** | open |
| **Module** | LM Studio Dashboard pane |
| **Platform** | macOS |
| **First seen** | 2026-10-14 |

## Description

`terminateModelStream(boundedWait:)` sets `modelStreamProcess = nil` synchronously, but the dying process's `terminationHandler` hops to the main actor through a `Task`, so `handleModelStreamTermination` can run arbitrarily later. If a show happens in that window, `spawnModelStream` sees `modelStreamProcess == nil`, launches a replacement and stores it — and then the *old* process's handler runs and unconditionally does `modelStreamProcess = nil`, throwing away the live replacement's handle and consuming the shared `expectingModelStreamExit` flag. `runtimeStreamProcess` has the identical shape.

Consequences: the replacement is unreachable, so a later `tearDown()`/`stopActiveWork` cannot terminate it (a leaked `lms` subprocess with live `readabilityHandler`s), and `pollModelsOnce`'s reconnect branch (`if modelStreamProcess == nil { spawnModelStream(...) }`) can spawn a duplicate on top of it.

Found by an external review of `v1.1.0..ad239f9e` — review id `20261014T193749Z-Batty-883c427`, finding 3 of 5 (medium, correctness, confidence high).

## Steps to reproduce

1. Open an LM Studio Dashboard pane with the `lms` CLI available, so both streams spawn.
2. Hide the pane and show it again quickly enough that the terminating process's main-actor `Task` has not run yet.
3. Tear the pane down and check for a surviving `lms` child process.

## Expected behavior

A termination callback only ever clears state belonging to *that* process. A replacement spawned after the old one was terminated stays reachable and is terminated at teardown.

## Actual behavior

`BattyKit/Sources/BattyKit/Runtime/LMStudioDashboardPaneContent.swift:619-627` (`handleModelStreamTermination`) and `:729-737` (`handleRuntimeStreamTermination`) clear the stored handle with no identity check, and consume a process-agnostic `Bool` expectation flag.

## Notes

- Fix: make both the stored-handle clear and the expectation lookup identity-keyed. The handler takes the `Process` it belongs to and only nils the stored handle when it is still that process; the two `expecting…StreamExit` booleans become one `Set<ObjectIdentifier>` of processes this type deliberately terminated, so the expectation is consumed by the right exit instead of by whichever exit arrives first.
- The set cannot leak: a handle is only stored after `try process.run()` succeeds, so `terminationHandler` is guaranteed to fire exactly once per registered process and remove its entry.
- Keeps round-1 fix S2 intact — the expectation is still recorded inside `terminate…Stream` after its `guard`, never by the caller.
