# 0719 — After an app update the batty CLI can't reach the broker until the broker is restarted

| | |
|---|---|
| **Status** | open |
| **Module** | App / Build |
| **Platform** | macOS |
| **First seen** | 2026-11-22 |
| **Target** | 1.5.0 |

## Description

After Sparkle replaces the app, the `BattyBroker` started by the old build keeps running. The new app and the new `batty` CLI then reject it on their outgoing code-signing check with -67065, so `batty ping` and every other CLI and MCP call fail. The app can't register its endpoint either. Nothing recovers on its own: in the VM it worked again only after `launchctl kickstart -k gui/<uid>/co.sstools.Batty.beta.broker`. A user who has turned on the CLI or MCP in Settings would hit this after every update until they log out or restart the broker by hand.

It is the same failure as #0716's, aimed at the broker instead of BattyHost. The broker is `RunLoop.main.run()` with no idle exit ("it stays alive to answer requests until launchd stops it", `BattyKit/Sources/BattyBroker/main.swift`). Its launchd job (`Configuration/co.sstools.Batty{,.beta}.broker.plist`: `BundleProgram`, `MachServices`, no `KeepAlive`) is started on demand and outlives the app, so an update never replaces the running broker. Since #0278, every outgoing connection from the app and the CLI calls `OutgoingCodeSigningEnforcement.apply` → `NSXPCConnection.setCodeSigningRequirement`. That check fails for a process whose bundle on disk has been replaced (#0716 Background: macOS validates a running process against the file at its path).

**This probably affects shipped Prod, and has since 1.1.0.** The broker (#0270, `afc69d71`) and the outgoing check (#0278, `43710679`) are both first contained in `v1.1.0`, and the broker's lifetime and the check are the same on `release/1.4`. It is a bug against 1.1.0 if the plan confirms it on a Prod-shaped install (see "A field case that disagrees" and Things to verify). Only users who opted in to the CLI broker in Settings (#0270, SMAppService registration) are affected.

Onquit mode (`onquit/guest/logs/stream.log`) is the same: old broker pid 831, new app pid 1814, `09:10:41.543 … xpc_support_check_token … status: -67065` while `BattyBroker[831]` logs `app endpoint registered`.

The harness step is `tools/vm-guest-sparkle.sh` `trigger` on `issue/0715`. If `wait_ping 60` fails, it logs `WARNING: broker-restarted`, runs `launchctl kickstart -k "gui/$uid/co.sstools.Batty.beta.broker"`, and waits again. That was the plan's open question 3, decided by the orchestrator as "one restart with a warning".

**VM caveat.** The guest bootstraps the broker with `launchctl bootstrap` and a `Program` path (`tools/vm-guest-broker.sh`), not through SMAppService. So the app's repair path was skipped (`notRegistered`). For a real user, SMAppService reports `.enabled`, and `AppXPCCoordinator.attemptRepairIfNeeded` runs `unregister()` + `register()` once per launch after "broker unreachable". That may restart the broker and heal the app side, though nothing has tested it. It does nothing for a CLI call made before the app has launched and repaired.

## A field case that disagrees

The user's MacBook diagnostics (`~/Gibson/Batty/2026-11-21-beta-pty-host-no-restart/README.md`, Secondary findings 2) show a stale Beta broker: `BattyBroker` pid 76387, running since Wed Nov 11 21:25:42 and mapping an older 1.67 MB binary, while the on-disk binary is 4.2 MB (`processes.txt`, `launchctl-list.txt`: `76387 0 co.sstools.Batty.beta.broker`). A Prod `BattyBroker`, pid 19138, was also running. The Beta bundle was replaced at 18:33 on Nov 21.

That stale broker was **accepted**, not rejected: in `timeline-filtered.txt`, app pids 74487, 78212 and 78241 each log `AppXPCCoordinator: endpoint registered and confirmed — pid 76387` (19:34:40, 19:35:20, 19:35:37). The -67065 lines from pid 69589 in the same file are all paired with `HostClient: terminal helper connection: unavailable`, which is the BattyHost failure (#0716), not the broker. The diagnostics have no CLI lines. So the stale-broker evidence confirms that **the broker outlives an app replacement in the field**, but it does **not** show the field client rejecting it. The plan has to explain the difference between this case and the VM, where the bundle was replaced by Sparkle. Possible factors: how the bundle was replaced (Sparkle's swap versus another install method), SMAppService `BundleProgram` versus the VM's `Program`, or a code-signing cache.

## Expected behavior

After any app update (Sparkle install-and-relaunch, install-on-quit, or a manual replace of the bundle), the first `batty` CLI or MCP call and the new app's endpoint registration reach a broker that is running the new binary, with no user action. That holds whether or not the app has been launched since the update.

Approaches for the plan to weigh (not decided here):
- The broker notices its own executable or bundle has been replaced and exits, so launchd starts the new one on the next connection. It doesn't need to hand any state over, because the broker holds only the app's endpoint, which the app registers again. This is much simpler than #0716's exec handover, but shares its detection (vnode source on the executable and bundle, `SecCodeCheckValidity(SecCodeCopySelf())`).
- The broker exits when idle, or when the registering app connection is invalidated with no other clients. Check the impact on `batty` latency and on #0361's reconnect logic.
- The new app, on -67065 or "broker unreachable" at launch, restarts the broker job (`launchctl kickstart -k` equivalent, or the SMAppService unregister/register repair, which already exists for `.enabled`). This doesn't help a CLI call made before the app launches.
- The CLI, on a -67065-style rejection, asks launchd to restart the job once. Check whether that's allowed and safe.

A broker that keeps running after an update must never be trusted because its signature is ignored. The fix must not weaken the #0278 outgoing check.

## Acceptance criteria

- **#0715 runner:** in both modes, `batty ping` succeeds after the update without the harness's `launchctl kickstart -k`. The `broker-restarted` fallback in `tools/vm-guest-sparkle.sh` is removed, or turned into a failing check (`broker-stale`). No `WARNING: broker-restarted` appears. Record the run id. If #0715 hasn't merged when this lands, note the dependency in #0715.
- The new app logs `endpoint registered and confirmed — pid <new broker pid>` after an update without a 60 s gap.
- The #0278 outgoing check is unchanged: a broker signed by another team is still rejected (the existing #0278 tests still pass).
- Unit tests for the decision logic, with injected clocks or detectors and no sleeps (AGENTS.md "Asynchronous tests"). For example, "executable replaced → exit" or "app sees -67065 at launch → restart broker once per launch".
- Progressive disclosure: nothing new appears for users who never turned on the CLI. No broker is registered or started for them.
- If the plan confirms Prod is affected, the fix is cherry-picked to `release/1.4` for a patch release, per AGENTS.md "Release branches", and the changelog says the CLI no longer needs a restart after an update.

## Things to verify

- **Whether shipped Prod is affected.** Update a Prod-shaped install whose broker is registered through SMAppService from one signed build to the next, in the VM (#0715 runner or a variant of it), and run `batty ping` before launching the new app and after. That answers both the field discrepancy above and whether `attemptRepairIfNeeded` heals the app side.
- Why the MacBook's stale broker (pid 76387) passed the app's check while the VM's (pids 824 and 831) failed.
- Whether a Sparkle update with the app's standard `SPUStandardUpdaterController` (Prod) differs from the #0714 headless driver here. It shouldn't, because both replace the bundle the same way.
- That MCP (`batty mcp`) goes through the same CLI→broker path and recovers the same way.
- That a broker exiting while a CLI call is in flight produces the existing "unreachable" exit codes, not a hang.
- Grep every comment the fix touches for claims about broker lifetime. `BattyBroker/main.swift` says it "stays alive to answer requests until launchd stops it", and `docs/xpc/xpc-cli-architecture.md` describes "What the broker must not be".
