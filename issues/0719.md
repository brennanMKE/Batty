## Description

After Sparkle replaces the app, the `BattyBroker` started by the old build keeps running. The new app and the new `batty` CLI then reject it on their outgoing code-signing check with -67065, so `batty ping` and every other CLI and MCP call fail. The app can't register its endpoint either. Nothing recovers on its own: in the VM it worked again only after `launchctl kickstart -k gui/<uid>/co.sstools.Batty.beta.broker`. A user who has turned on the CLI or MCP in Settings would hit this after every update until they log out or restart the broker by hand.

It is the same failure as #0716's, aimed at the broker instead of BattyHost. The broker is `RunLoop.main.run()` with no idle exit ("it stays alive to answer requests until launchd stops it", `BattyKit/Sources/BattyBroker/main.swift`). Its launchd job (`Configuration/co.sstools.Batty{,.beta}.broker.plist`: `BundleProgram`, `MachServices`, no `KeepAlive`) is started on demand and outlives the app, so an update never replaces the running broker. Since #0278, every outgoing connection from the app and the CLI calls `OutgoingCodeSigningEnforcement.apply` → `NSXPCConnection.setCodeSigningRequirement`. That check fails for a process whose bundle on disk has been replaced (#0716 Background: macOS validates a running process against the file at its path).

**This probably affects shipped Prod, and has since 1.1.0.** The broker (#0270, `afc69d71`) and the outgoing check (#0278, `43710679`) are both first contained in `v1.1.0`, and the broker's lifetime and the check are the same on `release/1.4`. It is a bug against 1.1.0 if the plan confirms it on a Prod-shaped install (see "A field case that disagrees" and Things to verify). Only users who opted in to the CLI broker in Settings (#0270, SMAppService registration) are affected.

## Plan

Planned 2026-11-22 against `main` at `c4ab3334` (#0715 merged, so the runner is on `main`). The `build/sparkle-tests/` results were deleted with the #0715 worktree, so the evidence used is what's quoted in this issue and in `issues/0715.md`.

### Premises checked

- `BattyKit/Sources/BattyBroker/main.swift` is as the issue says: it resumes `NSXPCListener(machServiceName:)`, then `RunLoop.main.run()`, with no exit path. Its comment claims "it stays alive to answer requests until launchd stops it". `Configuration/co.sstools.Batty{,.beta}.broker.plist` has `BundleProgram`, `MachServices` and no `KeepAlive`. `release/1.4`'s `BattyBroker/` is identical to `main`'s (`git diff main release/1.4 -- BattyKit/Sources/BattyBroker` is empty), so 1.1.0 through 1.4.2 behave the same.
- The outgoing requirement (`PeerCodeSigningRequirement`) is `anchor apple generic and certificate leaf[subject.OU] = "<team>"`. It accepts an Apple Development **or** a Developer ID leaf from the same team.
- **CLI connections to the broker are per call.** `BrokerPingClient` and `BrokerAppEndpointClient` open, ask and finish on reply, interruption or invalidation. Then the CLI (and `batty mcp`) talks to the app's endpoint directly. So a broker exit never strands a long-lived CLI or MCP connection. A call in flight when the broker exits gets interruption/invalidation, which these clients already map to `reachable: false` (`XPCExitCode.brokerUnreachable` = 2), not a hang.
- The app side (`AppXPCCoordinator`) already handles a broker that dies: `.interruption` → "retrying registration on the existing connection", which launchd satisfies by spawning a new broker on demand, as the VM's post-kickstart log shows (`endpoint registered and confirmed — pid 1993`). Invalidation → new connection, with #0361's budget and backoff.
- The repair path (`attemptRepairIfNeeded`: unregister then register, once per launch) only runs when `SMAppService` reports `.enabled`. In the VM the broker was bootstrapped with `launchctl bootstrap` and a `Program` path (`tools/vm-guest-broker.sh`), so the state was `notRegistered` and repair was skipped, as logged.

### Why the MacBook's stale broker was accepted and the VM's was rejected

The VM result follows from #0716's Background. Sparkle moves the old bundle away and deletes it. The running broker's executable is unlinked, so the client's check of that process can't find its code: -67065 `errSecCSNoSuchCode`.

The field broker (pid 76387, started Wed Nov 11 21:25, mapping a 1.67 MB binary) is best explained by **it not running from `/Applications/Batty Beta.app` at all**:
- `processes.txt` shows only the relative `Contents/Resources/bin/BattyBroker` (from `BundleProgram`), so its bundle can't be read from the evidence. The diagnostics have `lsof` for BattyHost only, not the broker.
- `batty-restart-diag.txt` lists 13 `DerivedData/…/Debug/Batty Beta.app` copies with the Beta bundle id. A Debug Beta run from Xcode can register the broker through Settings, and `SMAppService` keys the registration to that bundle's path.
- Those Debug builds are Apple Development–signed by team XV8BAAVZ6V, which the team-only requirement accepts. Their files were never replaced, so the running broker's code is intact on disk and the check passes.
- BattyHost pid 61598 did run from `/Applications` (replaced at 18:33), so it failed the same check. That matches "both from one app, only one rejected".

That is a strong hypothesis, not a proof. The confirming read-only check for the user (on the MacBook, no relaunch needed): `launchctl print gui/$(id -u)/co.sstools.Batty.beta.broker | grep -iE 'path|program|bundle'` and `lsof -p <broker pid> | grep txt`. Neither the fix nor the VM verification depends on the answer. If the broker was running from `/Applications`, the next likely factor is that the old bundle survived somewhere (moved, not deleted), which also leaves the code intact. The fix below is correct in every case, because a broker whose own file still exists unchanged passes the check and needs no restart.

Consequence for Prod: a 1.1.0–1.4.2 user who turned on the CLI in Settings, registered from `/Applications/Batty.app`, has a broker whose executable Sparkle deletes. That is the VM case. Every CLI or MCP call fails with -67065 until something kills the old broker. The new app's launch probably heals the **app** side: `SMAppService` reports `.enabled`, so `attemptRepairIfNeeded` unregisters, which boots the job out, and registers again. That is unverified, because the VM can't register through `SMAppService` (below). CLI calls made before the new app has launched and repaired fail either way. **So Prod is affected since 1.1.0, for CLI opt-in users**, with a severity between "until the app relaunches" and "until logout", depending on the repair.

### Fix chosen: the broker exits when its own executable is replaced

The broker holds only the app's endpoint, which the app registers again on interruption. So it can just exit, and launchd starts the new binary on the next connection. That is simpler than #0716's exec handover, which has to keep PTYs.

- **Detection:** a vnode `DispatchSource` on the broker's own executable, opened `O_EVTONLY` at start, with the event mask `[.delete, .rename, .revoke, .write]`.
  - Sparkle's swap removes the old bundle, which unlinks the executable → `.delete`. This fires whether or not the file is still open or mapped.
  - An in-place overwrite → `.write`. Renaming the file itself → `.rename`. An unmounted volume → `.revoke`.
  - Moving the *whole bundle* (an ancestor rename) fires nothing. That's fine: the file is intact, so the check passes and no restart is needed.
  - No `SecCodeCheckValidity` backstop. Every case the watch misses is one where the code on disk is intact and the check passes, so the backstop would add code without fixing anything.
- **On the first event:** log `.notice` "executable replaced (<event>) — exiting so launchd starts the new broker on demand", cancel the source, and `exit(0)`. No debounce: an early exit only costs a relaunch, and launchd resolves `BundleProgram`/`Program` at the next spawn. A connection arriving in the instant between the old bundle's removal and the new one's arrival is impossible with Sparkle's swap, which puts the new bundle in place before deleting the old. A manual delete-then-copy could make one spawn fail, which the app's #0361 backoff and the CLI's next call absorb.
- Exit status 0. There's no `KeepAlive`, so launchd doesn't respawn on exit. It respawns only on demand. A long-lived job exiting doesn't trip launchd's 10 s spawn throttle.
- A broker from a build **before** this fix has no watch, so the first update *to* a fixed build still leaves that old broker. For `SMAppService` users the app's existing `.enabled` repair is the transition path. Nothing new is added for it (see Open question 2). After that one update, every later update self-heals.
- **Rejected:**
  - Idle exit, or exit when the registering app connection drops. With #0696's "Keep terminals running", CLI calls from kept terminals can arrive while no app is connected, and the broker would still be stale whenever a client was connected across the swap. It also adds a timer policy for no gain.
  - App `launchctl kickstart -k` on -67065. It doesn't help a CLI call before the app launches, and the app already has the repair path for real registrations.
  - CLI-side restart. The CLI can't restart an `SMAppService` job it doesn't own cleanly, and it would add a second actor that restarts launchd jobs.
  - Anything that relaxes #0278's check (#0716 decision 2).
- **Overlap with #0716:** #0716 needs the same detection for BattyHost but restarts in place. The watcher goes in `BattyXPCCore` so #0716 (on `issue/0696`) can reuse it (`ExecutableReplacementWatcher`) and add its own debounce and validity check on top. Note this in `## Fix` so #0716's plan picks it up.

### Files

1. **New `BattyKit/Sources/BattyXPCCore/ExecutableReplacementWatcher.swift`**: `public nonisolated final class ExecutableReplacementWatcher: @unchecked Sendable` (guard state with the source's serial queue).
   - `public static let eventMask: DispatchSource.FileSystemEvent = [.delete, .rename, .revoke, .write]`.
   - `public static func ownExecutablePath() -> String?`: absolute path of the running image via `proc_pidpath(getpid(), …)` (`import Darwin`). Don't use `CommandLine.arguments[0]`, which is relative under `BundleProgram` (the field `ps` shows `Contents/Resources/bin/BattyBroker`).
   - `public init(path: String, queue: DispatchQueue, onReplaced: @escaping @Sendable (DispatchSource.FileSystemEvent) -> Void)`.
   - `public func start() throws`: `open(path, O_EVTONLY)`. On failure, throw a `POSIXError` with errno. Make the source with `eventMask`. The event handler reads `source.data`, calls `onReplaced` **once** (a `fired` flag on the queue), then cancels. The cancel handler closes the fd.
   - `public func cancel()`.
   - File-scoped `logger` with category `ExecutableReplacementWatcher`, logging start (path) and the event at `.notice`.
   - A doc comment stating the invariant above: an ancestor rename doesn't fire, and that's intended because the code on disk is then unchanged.

## Root cause

`BattyBroker` started on demand and never exited. An app update deletes (Sparkle) or overwrites the bundle it was launched from, so the running broker's code is gone from disk, and every client's #0278 outgoing code-signing check rejects it with -67065 (`errSecCSNoSuchCode`) until something kills it. Nothing did: no `KeepAlive`, no exit path. Affected since 1.1.0 for CLI/MCP opt-in users.

## Fix

The broker exits when its own executable is replaced; launchd starts the new binary on the next connection and the app re-registers its endpoint on the interruption. The #0278 check is unchanged.

- New `ExecutableReplacementWatcher` in `BattyXPCCore` (for #0716 to reuse on `issue/0696`; it adds its own debounce/validity check on top). API:
  - `static func ownExecutablePath() -> String?` (`proc_pidpath`, not `argv[0]`, which is relative under `BundleProgram`).
  - `static var eventMask` = `[.delete, .rename, .revoke, .write]`; `static func describe(_:) -> String` for logs.
  - `init(path:queue:onReplaced:)` (production vnode source, `O_EVTONLY`) and `init(path:source:onReplaced:)` with an injected `FileEventSource` (protocol: `start(handler:) throws`, `cancel()`); `VnodeFileEventSource` is the public default.
  - `start() throws` (`POSIXError` when the file can't be opened), `cancel()`, `isCancelled`. The callback runs at most once, on the first event, and the watch then cancels itself. An ancestor rename (moving the whole bundle) fires nothing, by design: the code on disk is intact.
- Divergence from the plan: the plan's queue-guarded `fired` flag became an `NSLock` (the injected source may call back from any thread), and the event source is a protocol so tests can drive it synchronously. `eventMask` is a computed `static var` because `DispatchSource.FileSystemEvent` isn't `Sendable` under strict concurrency.
- `BattyBroker/main.swift`: after `listener.resume()`, starts the watcher on a dedicated serial queue; the handler logs `.notice` "executable replaced (<event>) — exiting so launchd starts the new broker on demand" and `exit(0)`. If the path can't be resolved or `start()` throws, it logs `.error` and keeps serving as before.
- Runner: `tools/vm-guest-sparkle.sh` `trigger` writes `after/broker.txt` (`fresh` or `broker-stale`, with `FAIL-MARK: broker-stale` and one `kickstart -k` only so the snapshot can finish; nothing goes to `warnings.txt`). `snapshot` records `broker-pid.txt` (baseline and after). `tools/sparkle-update-check.py` adds check `broker-fresh` (last in `CHECK_ORDER`): fails on `broker-stale` or an unchanged broker pid; a missing `after/broker.txt` is an input error (exit 2).
- Docs: `docs/xpc/xpc-cli-architecture.md` (broker lifetime paragraph), `docs/ui-testing-vm.md` (Sparkle checks list).

## Expected behavior

After any app update (Sparkle install-and-relaunch, install-on-quit, or a manual replace of the bundle), the first `batty` CLI or MCP call and the new app's endpoint registration reach a broker that is running the new binary, with no user action. That holds whether or not the app has been launched since the update.

Approaches for the plan to weigh (not decided here):
- The broker notices its own executable or bundle has been replaced and exits, so launchd starts the new one on the next connection. It doesn't need to hand any state over, because the broker holds only the app's endpoint, which the app registers again. This is much simpler than #0716's exec handover, but shares its detection (vnode source on the executable and bundle, `SecCodeCheckValidity(SecCodeCopySelf())`).
- The broker exits when idle, or when the registering app connection is invalidated with no other clients. Check the impact on `batty` latency and on #0361's reconnect logic.
- The new app, on -67065 or "broker unreachable" at launch, restarts the broker job (`launchctl kickstart -k` equivalent, or the SMAppService unregister/register repair, which already exists for `.enabled`). This doesn't help a CLI call made before the app launches.
- The CLI, on a -67065-style rejection, asks launchd to restart the job once. Check whether that's allowed and safe.

A broker that keeps running after an update must never be trusted because its signature is ignored. The fix must not weaken the #0278 outgoing check.

## Review

Round 1: code approved; VM verification pending (orchestrator). Round 2 (same reviewer): VM run `20261122-021932-45348` passed `broker-fresh` in both modes → resolved. Approved without code changes.

- **Watcher.** `O_EVTONLY` fd, mask `[.delete, .rename, .revoke, .write]`, fire-once under `NSLock` (handler cancels the source; later events and post-`cancel()` events are dropped). The fd closes in the cancel handler; `deinit` cancels; the broker keeps the watcher in a `main.swift` top-level global, so it lives for the whole process. `proc_pidpath` with a `4 * MAXPATHLEN` buffer gives an absolute path whatever `argv[0]` is.
- **False `.write`.** A scratch kqueue probe on an ad-hoc signed copy of `/bin/ls` with the same mask saw no event for `cat`, `touch`, `xattr -w`/`-c` (quarantine), `chmod`, `codesign -v` or `mdimport`. Only a real data write (in-place overwrite or re-sign) fires. A false fire costs little anyway: the broker exits, the app re-registers on the interruption (`AppXPCCoordinator` "broker connection interrupted — … retrying registration"), and the next CLI call starts a new broker.
- **`exit(0)` and launchd.** Both broker plists have no `KeepAlive` and no `RunAtLoad`, so an exit is never respawned on its own; launchd starts the broker only on the next connection. An in-flight CLI call sees an interrupted connection, which is the existing "unreachable" path. Each exit needs a new event on the new binary's own vnode, and Sparkle's swap is atomic, so there is no crash loop and no restart storm. A non-atomic manual copy may leave a short window where launchd can't spawn `BundleProgram`; the next call works.
- **Runner.** `broker-fresh` is not vacuous: the default fixture passes, while `broker-stale` and an unchanged pid each fail as the first failing check, and a missing `after/broker.txt` exits 2. One soft spot, not blocking: if `launchctl print` yields no pid, `read_optional` returns `""` and the pid half of the check is skipped. `broker.txt` is still required, and it is the primary signal.
- **Tests.** There are no sleeps. `EventRecorder.first()` uses `asyncAfter(TestBounds.hangGuard)` only as a failure bound, and the continuation is nilled under the lock, so it can't resume twice. The real-file tests watch real vnodes, and the fake-source tests drive delivery synchronously. Nit: tests without `defer` leave their empty temp `root` behind.
- **Claims.** The comments in `main.swift`, the watcher doc comment and `docs/xpc/xpc-cli-architecture.md` match the code (mask, exit path, re-register on interruption, no `RunAtLoad`).
- **Cherry-pick to `release/1.4`.** `BattyBroker/main.swift` there is byte-identical to `main`'s. `TestBounds.hangGuard` and `BattyXPCCore` imports in tests exist there. `git apply --check` of the `BattyKit/` and `docs/xpc/` hunks passes in the `release-1.4` worktree. The `tools/sparkle-update-check*.py` and `tools/vm-guest-sparkle.sh` files don't exist on `release/1.4`, and `docs/ui-testing-vm.md` lacks the Sparkle checks list, so those hunks must be dropped, as the Fix section says.
