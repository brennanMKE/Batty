# 0046 — Closing the last tab in a pane should cascade through pane and session teardown

| | |
|---|---|
| **Status** | open |
| **Module** | Tabs / Pane / Session |
| **Platform** | macOS |
| **First seen** | 2026-05-11 |

## Description

There's no way to tear down a pane or a session by closing tabs. Once a pane has only one tab left, the chip's close button disappears and `Cmd-W` becomes a no-op for that path. If a session has only one pane and that pane has only one tab, the session is permanently stuck open — the only escape is the sidebar's right-click → Close.

The user-visible symptom: the chip "x" is gated by `pane.tabs.count > 1` in `PaneView`, and `PaneRuntime.removeTab` early-returns when only one tab remains. `SessionRuntime.closeFocusedTab` cascades tab → pane (when the tree has multiple panes) but stops there — it never closes the session.

## Expected behavior

Closing tabs should cascade all the way through containment so the user can dismantle a session entirely from the chip / Cmd-W:

1. Close a non-last tab → just remove the tab (current behavior).
2. Close the last tab in a pane that isn't the only pane → collapse the pane (current behavior via `#0021`).
3. Close the last tab in the only pane of a session → close the session.
4. Close the only tab of the only pane of the only session → either keep one default empty session as the floor (matches `AppStateStore.removeSession`'s existing recover-from-empty behavior) or fully close the window. Pick one and document.

## Actual behavior

- The chip's "x" is hidden via `onClose: pane.tabs.count > 1 ? ... : nil` in `BattyKit/Sources/BattyKit/PaneView.swift:24-25`. The last tab in a pane has no visible close affordance.
- `PaneRuntime.removeTab(id:)` early-returns on `tabs.count <= 1` (`BattyKit/Sources/BattyKit/PaneRuntime.swift:39-45`).
- `SessionRuntime.closeFocusedTab()` cascades only down to "remove the focused pane" when there are siblings; never falls through to "close the session" (`BattyKit/Sources/BattyKit/SessionRuntime.swift:24-31`).
- `Cmd-W` (`BattyCommands` → "Close Tab") routes through `closeFocusedTab` so it inherits the same dead-end.

## Acceptance criteria

- The chip "x" stays visible on the last tab in any pane. Tapping it triggers the cascade.
- `Cmd-W` on the last tab cascades the same way.
- `PaneRuntime.removeTab` (or a new equivalent) is callable on the last tab; the orchestration to collapse the pane / close the session lives at the appropriate layer above (most likely `AppStateStore` or `SessionRuntime`).
- `AppStateStore` handles the empty-session-list case the way it already does for explicit `removeSession`: re-create a default empty `SessionRuntime` rather than leaving the app with zero sessions.
- Manual verification: in a single-session, single-pane, single-tab workspace, close the tab and confirm the empty-state placeholder (or fresh session) appears as expected.

## Notes

- Per `Concepts.md` → Session / Pane / Tab, this is the natural cascade. The current dead-end exists because each level was implemented independently and the layer-above-the-pane part was never wired up.
- `#0021` shipped the tab → pane collapse half; this issue is the pane → session half plus the chip-button gating.
- Close-confirmation (`#0036`) interacts with this: if a tab has a running process and the user is closing it as the last tab in the last pane, the confirm prompt should fire **before** the session-close cascade. The quit-time prompt doesn't help here because the app stays running.
- Watch for the active-tab fallback path in `PaneRuntime.removeTab` — `tabs[max(0, index - 1)].id` is fine when there are siblings but goes out of bounds when removing the only tab. Either guard the index calculation or remove that line entirely for the last-tab path.
