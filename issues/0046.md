# 0046 — Closing the last tab in a pane should cascade through pane and session teardown

## Description

There's no way to tear down a pane or a session by closing tabs. Once a pane has only one tab left, the chip's close button disappears and `Cmd-W` becomes a no-op for that path. If a session has only one pane and that pane has only one tab, the session is permanently stuck open — the only escape is the sidebar's right-click → Close.

The user-visible symptom: the chip "x" is gated by `pane.tabs.count > 1` in `PaneView`, and `PaneRuntime.removeTab` early-returns when only one tab remains. `SessionRuntime.closeFocusedTab` cascades tab → pane (when the tree has multiple panes) but stops there — it never closes the session.

## Expected behavior

Closing tabs should cascade all the way through containment so the user can dismantle a session entirely from the chip / Cmd-W:

1. Close a non-last tab → just remove the tab (current behavior).
2. Close the last tab in a pane that isn't the only pane → collapse the pane (current behavior via `#0021`).
3. Close the last tab in the only pane of a session → close the session.
4. Close the only tab of the only pane of the only session → either keep one default empty session as the floor (matches `AppStateStore.removeSession`'s existing recover-from-empty behavior) or fully close the window. Pick one and document.

## Actual behavior

- The chip's "x" is hidden via `onClose: pane.tabs.count > 1 ? ... : nil` in `BattyKit/Sources/BattyKit/PaneView.swift:24-25`. The last tab in a pane has no visible close affordance.
- `PaneRuntime.removeTab(id:)` early-returns on `tabs.count <= 1` (`BattyKit/Sources/BattyKit/PaneRuntime.swift:39-45`).
- `SessionRuntime.closeFocusedTab()` cascades only down to "remove the focused pane" when there are siblings; never falls through to "close the session" (`BattyKit/Sources/BattyKit/SessionRuntime.swift:24-31`).
- `Cmd-W` (`BattyCommands` → "Close Tab") routes through `closeFocusedTab` so it inherits the same dead-end.

## Acceptance criteria

- The chip "x" stays visible on the last tab in any pane. Tapping it triggers the cascade.
- `Cmd-W` on the last tab cascades the same way.
- `PaneRuntime.removeTab` (or a new equivalent) is callable on the last tab; the orchestration to collapse the pane / close the session lives at the appropriate layer above (most likely `AppStateStore` or `SessionRuntime`).
- `AppStateStore` handles the empty-session-list case the way it already does for explicit `removeSession`: re-create a default empty `SessionRuntime` rather than leaving the app with zero sessions.
- Manual verification: in a single-session, single-pane, single-tab workspace, close the tab and confirm the empty-state placeholder (or fresh session) appears as expected.

## Notes

- Per `Concepts.md` → Session / Pane / Tab, this is the natural cascade. The current dead-end exists because each level was implemented independently and the layer-above-the-pane part was never wired up.
- `#0021` shipped the tab → pane collapse half; this issue is the pane → session half plus the chip-button gating.
- Close-confirmation (`#0036`) interacts with this: if a tab has a running process and the user is closing it as the last tab in the last pane, the confirm prompt should fire **before** the session-close cascade. The quit-time prompt doesn't help here because the app stays running.
- Watch for the active-tab fallback path in `PaneRuntime.removeTab` — `tabs[max(0, index - 1)].id` is fine when there are siblings but goes out of bounds when removing the only tab. Either guard the index calculation or remove that line entirely for the last-tab path.

## Root cause

Each level (Pane, SplitTree, Session) was implemented as a self-contained primitive that refused to enter an "empty" state, but no orchestrator above them stitched the cascade together. `PaneRuntime.removeTab` early-returned on `tabs.count <= 1`; `SplitTree.removeFocusedPane` early-returned on `allPanes.count <= 1`; `SessionRuntime.closeFocusedTab` cascaded tab→pane but never pane→session. The visible symptom (chip "x" disappearing) was `PaneView` correctly hiding the close affordance because the underlying primitive wouldn't honor it.

## Fix

Move the cascade into `AppStateStore` and let the lower-level primitives be unguarded.

- `PaneRuntime.removeTab(id:)` no longer guards on `tabs.count > 1`. The pane is allowed to become empty briefly; the active-tab fallback only runs when `tabs` is non-empty after removal.
- `SplitTree.removePane(id:) -> Bool` returns `true` when the tree becomes empty (the removed pane was the only one). Callers treat that as "session is now empty and should be closed."
- `AppStateStore.closeTab(id:)` is the canonical orchestrator: locates the pane that owns the tab, calls `pane.removeTab`, cascades to `session.tree.removePane` if the pane went empty, cascades to `removeSession` if the tree went empty. `removeSession` already restores a single default session when the list would otherwise be empty, so the floor is one always-open default session per AC item 4.
- `AppStateStore.closeFocusedTab()` is a convenience wrapper for `Cmd-W`'s path that resolves the currently-focused tab id and delegates.
- `PaneView`'s `DefaultTabChip` always passes an `onClose` (no longer gated on `tabs.count > 1`); the closure routes through `appStore.closeTab(id:)` when injected via environment, falling back to `pane.removeTab(id:)` for preview/test contexts where the store isn't available.
- `BattyCommands` "Close Tab" now calls `store.closeFocusedTab()`; the disabled predicate simplifies to "no selected session" since the cascade handles every other case.
- `SessionRuntime.closeFocusedTab()` is unchanged but is now effectively dead code from the in-product paths; left in place because it's a sensible in-session helper for callers that don't have an `AppStateStore` reference.

## Files changed

- `BattyKit/Sources/BattyKit/PaneRuntime.swift` — removed the count > 1 guard from `removeTab`; guarded the active-tab fallback against an empty `tabs` array.
- `BattyKit/Sources/BattyKit/SplitTree.swift` — new `removePane(id:) -> Bool`.
- `BattyKit/Sources/BattyKit/AppStateStore.swift` — new `closeTab(id:)` orchestrator + `closeFocusedTab()` convenience wrapper.
- `BattyKit/Sources/BattyKit/PaneView.swift` — chip `onClose` no longer gated; routes through the store when present.
- `BattyKit/Sources/BattyKit/BattyCommands.swift` — Cmd-W goes through `store.closeFocusedTab()`; removed the unused `canCloseFocusedTab` helper.
- `BattyKit/Tests/BattyKitTests/CloseTabCascadeTests.swift` (new) — 5 tests covering non-last close, last-tab-with-sibling-pane, last-tab-of-only-pane, last-tab-of-last-session (default restoration), and the `closeFocusedTab` wrapper.

## Gotchas

- **Pane.tabs precondition vs. the empty-briefly state.** `Pane` (the Codable struct) enforces `!tabs.isEmpty` at construction, but the runtime `PaneRuntime` is allowed to be empty between `pane.removeTab` and `session.tree.removePane` in the cascade. The empty state is never observable to `WorkspaceConversion.Pane(from runtime:)` because the cascade always removes the empty pane before yielding control back to anyone who could serialize it. If someone introduces a serialization path that runs mid-cascade, the precondition would trip — keep that in mind.
- **The active-tab fallback `tabs[max(0, index - 1)].id` is now guarded by `!tabs.isEmpty`** because removing the last tab leaves `tabs` empty and accessing index 0 would crash. The fallback only runs when there's still a sibling.
- **The "restore a default session when the list would be empty" behavior comes from `removeSession`,** not from `closeTab` itself. Don't duplicate the restoration here — let `removeSession` handle it. If `removeSession`'s recovery semantics ever change, `closeTab`'s last-session path inherits the new behavior.
- **`SessionRuntime.closeFocusedTab` is now unused by product code** but stays public. It does the in-session cascade (tab → pane when siblings exist) without reaching session level. Useful when a caller doesn't have an `AppStateStore`; consider removing in a cleanup pass if no one adopts it.
- **`#0036`'s close-confirmation is NOT invoked from this cascade.** The quit-time prompt is the only confirmation path right now; per-tab close-confirm is still pending the libghostty `CommandStart` signal. A future close-confirm hook should fire from `closeTab` before the actual removal, with the "last tab in last session" case being the most likely place to want a prompt.
