## Description

On a fresh app launch, opening a 3rd session caused a custom theme to be applied automatically. New sessions should have no theme pre-applied. The current design persists the global theme choice across launches via `UserDefaults` and re-applies it to every new session when it first becomes selected, which the user experiences as stale state bleeding into new sessions.

## Steps to reproduce

1. Launch the app and pick a theme from the Theme Selector (global pick → saved to `UserDefaults`).
2. Quit the app.
3. Launch the app again — first session appears.
4. Open a 2nd session, then a 3rd session.
5. Select the 3rd session.

## Expected behavior

- A newly created session starts with no theme applied — it should look like a fresh terminal (system default chrome).
- The global theme preference, if it exists, should only apply if the user explicitly activates it for a session, not automatically on every new session selection.
- Each session has a unique ID generated at creation time. Session IDs and session-level state (local theme name, title override, etc.) are **not** persisted or reloaded across app launches.

## Actual behavior

The 3rd session immediately shows the custom theme that was chosen globally in a previous launch. The theme is sourced from `UserDefaults` key `co.sstools.Batty.themeName` (written by `ThemeSelectorView.selectTheme()`) and re-applied via `applyActiveSessionTheme()` → `applyThemeToAllSurfaces()` every time a session is selected.

Additionally, `applyThemeToAllSurfaces()` applies the theme to **all** sessions simultaneously — not just the newly selected one — so switching to any session with a local theme clobbers the terminal appearance of every other open session.

## Notes

**Source of the persistence:**
`ThemePreference.activeTheme()` (`ThemePreference.swift:11`) reads `UserDefaults.standard` key `co.sstools.Batty.themeName`. `ThemeSelectorView.selectTheme()` (`ThemeSelectorView.swift:141`) writes it on every global theme pick. This key is never cleared.

**`applyActiveSessionTheme()` fallback** (`ThemePreference.swift:35-42`):
```swift
public func applyActiveSessionTheme() {
    if let localName = selectedSession?.localThemeName, ... {
        applyThemeToAllSurfaces(theme)  // session-local
    } else if let globalTheme = ThemePreference.activeTheme() {
        applyThemeToAllSurfaces(globalTheme)  // ← fires for every new session
    }
}
```
Called from `SessionDetailView.configuredStack` on every `onChange(of: store.selectedSessionID)` and `onAppear`. New sessions always take the `else` path, triggering the persisted global theme.

**Workspace vs. UserDefaults:** `WorkspaceManager` already skips loading the workspace file on launch (`"skipped (launch starts fresh)"`), so session IDs are not reused across launches. The persistence vector is solely `UserDefaults`, not the workspace file.

**Session-local themes are already non-persistent:** `SessionRuntime.localThemeName` is a plain `var` with no `@AppStorage` or save call — it resets to `nil` on every launch. The bug is the global fallback, not the local property.

**Design question:** Whether the global theme should apply to brand-new sessions at all is a product decision. One clean option: only apply a theme to a new session if `localThemeName` is explicitly set; do not fall back to the global preference automatically. The global theme preference would still exist (for sessions that opt in) but would not be injected silently into every new session.

## Root cause

Three sources of unintended theme bleed:

1. `TabRuntime.init()` called `Self.activeTheme()` which read the persisted `UserDefaults` global theme and applied it to every new tab at creation time.
2. `applyActiveSessionTheme()` fell back to `ThemePreference.activeTheme()` (UserDefaults) when the selected session had no `localThemeName`, injecting the old global theme into every new session on selection.
3. `applyActiveSessionTheme()` called `applyThemeToAllSurfaces()`, which applied the theme to every open session simultaneously rather than just the selected one.

## Fix

- `TabRuntime.init()` uses `TerminalViewState(theme: .default)` — new terminals always start with the system default appearance. The private `activeTheme()` helper that read UserDefaults is removed.
- `AppStateStore.init()` initializes `themeChrome` with `ThemeChrome()` (nil palette / system default) rather than seeding from `ThemePreference.activeTheme()`. The persisted key is still written by the global selector and read by `BattyCommands` for the Clear Theme menu item, but it no longer bleeds into the initial chrome on every launch.
- `applyActiveSessionTheme()` no longer has a global-theme fallback. Sessions with no `localThemeName` call `themeChrome.update(from: nil)` to reset the window chrome to the system default.
- `SessionDetailView.configuredStack.onAppear` now calls `applyActiveSessionTheme()` so the initial session gets the same chrome-reset path that `onChange` provides for every subsequent session switch.
- Added `applyTheme(_ theme:, to session:)` helper that applies a theme to one session's surfaces only. `applyActiveSessionTheme()` uses this helper. `applyThemeToAllSurfaces()` is kept for the global `ThemeSelectorView`, where applying to all currently-open sessions is the user's explicit intent.
- `SessionThemeSelectorView.selectTheme()` and `moveSelection()` now call `applyTheme(_:to:)` instead of `applyThemeToAllSurfaces()`.

## Files changed

- `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift` — `ThemeChrome()` default init; no longer seeds from UserDefaults
- `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift` — `TerminalViewState(theme: .default)`; removed `activeTheme()`
- `BattyKit/Sources/BattyKit/Theme/ThemePreference.swift` — rewrote `applyActiveSessionTheme()`; added `applyTheme(_:to:)`
- `BattyKit/Sources/BattyKit/Views/SessionDetailView.swift` — `onAppear` calls `applyActiveSessionTheme()`
- `BattyKit/Sources/BattyKit/Views/ThemeSelectorView.swift` — `SessionThemeSelectorView` uses `applyTheme(_:to:)`

## Gotchas

The `setTheme()` call only works after a libghostty surface is connected. `TerminalViewState(theme:)` is the pre-surface path (bakes theme into config), and `setTheme()` is the post-connect path. Since sessions now always start with `.default` and themes are only applied via explicit user picks (at which point surfaces are already connected), the ordering problem no longer arises.

`AppStateStore.init()` must NOT seed `themeChrome` from UserDefaults — if it does, Session 1's chrome will always be themed on app launch because `onChange(of: selectedSessionID)` doesn't fire for the initially-selected session (the value was already set before the view appeared). The `onAppear` fix handles this, but it's a subtle invariant: `onAppear` is the first safe call point for `applyActiveSessionTheme()` on the initial session.
