# 0147 — New sessions auto-apply persisted global theme; theme not scoped per session

| | |
|---|---|
| **Status** | open |
| **Module** | Theme / Session |
| **Platform** | macOS |
| **First seen** | 2026-05-19 |

## Description

On a fresh app launch, opening a 3rd session caused a custom theme to be applied automatically. New sessions should have no theme pre-applied. The current design persists the global theme choice across launches via `UserDefaults` and re-applies it to every new session when it first becomes selected, which the user experiences as stale state bleeding into new sessions.

## Steps to reproduce

1. Launch the app and pick a theme from the Theme Selector (global pick → saved to `UserDefaults`).
2. Quit the app.
3. Launch the app again — first session appears.
4. Open a 2nd session, then a 3rd session.
5. Select the 3rd session.

## Expected behavior

- A newly created session starts with no theme applied — it should look like a fresh terminal (system default chrome).
- The global theme preference, if it exists, should only apply if the user explicitly activates it for a session, not automatically on every new session selection.
- Each session has a unique ID generated at creation time. Session IDs and session-level state (local theme name, title override, etc.) are **not** persisted or reloaded across app launches.

## Actual behavior

The 3rd session immediately shows the custom theme that was chosen globally in a previous launch. The theme is sourced from `UserDefaults` key `co.sstools.Batty.themeName` (written by `ThemeSelectorView.selectTheme()`) and re-applied via `applyActiveSessionTheme()` → `applyThemeToAllSurfaces()` every time a session is selected.

Additionally, `applyThemeToAllSurfaces()` applies the theme to **all** sessions simultaneously — not just the newly selected one — so switching to any session with a local theme clobbers the terminal appearance of every other open session.

## Notes

**Source of the persistence:**
`ThemePreference.activeTheme()` (`ThemePreference.swift:11`) reads `UserDefaults.standard` key `co.sstools.Batty.themeName`. `ThemeSelectorView.selectTheme()` (`ThemeSelectorView.swift:141`) writes it on every global theme pick. This key is never cleared.

**`applyActiveSessionTheme()` fallback** (`ThemePreference.swift:35-42`):
```swift
public func applyActiveSessionTheme() {
    if let localName = selectedSession?.localThemeName, ... {
        applyThemeToAllSurfaces(theme)  // session-local
    } else if let globalTheme = ThemePreference.activeTheme() {
        applyThemeToAllSurfaces(globalTheme)  // ← fires for every new session
    }
}
```
Called from `SessionDetailView.configuredStack` on every `onChange(of: store.selectedSessionID)` and `onAppear`. New sessions always take the `else` path, triggering the persisted global theme.

**Workspace vs. UserDefaults:** `WorkspaceManager` already skips loading the workspace file on launch (`"skipped (launch starts fresh)"`), so session IDs are not reused across launches. The persistence vector is solely `UserDefaults`, not the workspace file.

**Session-local themes are already non-persistent:** `SessionRuntime.localThemeName` is a plain `var` with no `@AppStorage` or save call — it resets to `nil` on every launch. The bug is the global fallback, not the local property.

**Design question:** Whether the global theme should apply to brand-new sessions at all is a product decision. One clean option: only apply a theme to a new session if `localThemeName` is explicitly set; do not fall back to the global preference automatically. The global theme preference would still exist (for sessions that opt in) but would not be injected silently into every new session.
