## Description

Dragging a file from Finder onto a running terminal (e.g. Claude Code, a shell prompt) does not paste the file's path. The cursor shows the "no" / circle-slash drop indicator and the path is silently dropped. The behavior worked in the previous `TerminalSurfaceView`-based architecture and regressed when `#0075` moved the terminal NSView into a persistent `TerminalHostView` that sits on top of the SwiftUI tree.

## Root cause

`PaneView` wires `.onDrop(of: [.fileURL], …)` on the SwiftUI `TerminalPlaceholderView`. SwiftUI registers the drop type on its hosting NSView. But after `#0075`:

- The `TerminalHostView` (an `NSView`) is added as a subview of the SwiftUI hosting view via `TerminalHostInstaller`.
- The `AppTerminalView` (the actual rendered terminal) is a subview of the host, sized to fill the placeholder's frame.
- Neither `TerminalHostView` nor `AppTerminalView` calls `registerForDraggedTypes(_:)`.

AppKit's drag-and-drop dispatcher walks the deepest NSView at the cursor that has registered for the dragged type. With the AppKit terminal subviews on top and neither registered, AppKit rejects the drop. SwiftUI's `.onDrop` is never reached — drag-and-drop does NOT fall through an AppKit subview to a SwiftUI sibling underneath. (Click-events `hitTest` and drag-and-drop use different dispatch paths.)

Confirming evidence:

```
$ grep -rn 'registerForDraggedTypes\|draggingEntered\|performDragOperation' \
    BattyKit/Sources/BattyKit/TerminalHostView.swift \
    ../libghostty-spm/Sources/GhosttyTerminal/Platform/AppKit/AppTerminalView*.swift
(no output)
```

## Steps to reproduce

1. Open Batty. Start any process in a tab (a shell prompt is enough; `claude` is the user's repro).
2. From Finder, drag any file over the terminal area.
3. **Observed:** the cursor shows the "no-drop" indicator. Releasing does nothing.
4. **Expected:** the cursor shows the "copy" indicator with a green plus. Releasing inserts the path (shell-quoted) at the terminal's cursor.

## Fix

Move drop-target registration from the SwiftUI placeholder to the `TerminalHostView`. The host knows which `AppTerminalView` subview the drop landed on and which `TabRuntime` it corresponds to, so it can route the bytes through `terminal.send(...)` directly — same code path the existing `PaneView.handleFileDrop` uses.

### Implementation

In `TerminalHostView`:

1. In `init`, call `registerForDraggedTypes([.fileURL])` (using `NSPasteboard.PasteboardType` for the URL type).
2. Override `draggingEntered(_:) -> NSDragOperation` to return `.copy` when the pasteboard has at least one file URL. Use this entry point to set the host's hover-flag state if we want an accent border (or move the existing SwiftUI accent overlay to fire off this signal — see Open question below).
3. Override `draggingExited(_:)` to clear the hover state.
4. Override `prepareForDragOperation(_:) -> Bool` to return `true`.
5. Override `performDragOperation(_:) -> Bool` to:
   - Pull the file URLs out of the pasteboard.
   - Convert the drop point (in window coords) to host-local coords via `convert(_:from:)`.
   - Walk the visible subviews to find the one whose frame contains the point. That's the terminal NSView that received the drop.
   - Find the corresponding `TabRuntime` by reverse-looking-up `TerminalHostStore.shared.terminalViews` (the existing `[UUID: AppTerminalView]` keyed by tab id; expose a helper like `tabID(for: AppTerminalView) -> UUID?`).
   - Call into a new helper on `TerminalHostStore` (or directly on `TabRuntime`) that shell-quotes the paths via `ShellQuote.joinPaths(_:)` and sends through `terminal.send(...)`.
   - Return `true`.

### Removing the now-redundant SwiftUI path

The `.onDrop` modifier on `TerminalPlaceholderView` in `PaneView` no longer does anything useful — it lives on a view that AppKit never asks about for drops. Delete it. Move the `isDragHovering` state (and the accent-border overlay that animates on it) so it's driven by the host's drag callbacks. Probably easiest: the host posts a `NotificationCenter` event with the active tab's id on `draggingEntered`/`Exited`, and `PaneView` observes via `.onReceive` for ITS tab. Or: add a `@Published`-like flag on `TabRuntime` (`isDragHovering: Bool`) that the host writes and the view reads. Pick whichever is cleaner.

### Tests

- Model-level: a fake `TerminalHostStore` can be told "the drop landed at point X" and asserted that the right `TabRuntime` was identified and `terminal.send` was called with shell-quoted paths.
- Visual / manual: drag a file from Finder onto a Claude Code session; the path appears at the prompt. Multi-file drag joins with spaces.

## Open questions

- **Accent border on drag-over.** The existing border lives on the SwiftUI side (`.overlay { RoundedRectangle.strokeBorder(...).opacity(isDragHovering ? 1 : 0) }` in `PaneView`). Either move the cue to the AppKit side (`TerminalHostView` draws a border on `draggingEntered`) or keep it SwiftUI-side and route the hover state up via notification / model property. The notification path is the smallest change.
- **Multi-pane drops.** When the user has split panes, the drop should target the pane under the cursor, not the focused pane. The host's `hitTest`-style point→view lookup handles this naturally.
- **Cross-tab drops to a hidden tab.** Should dragging onto pane A while tab 2 is hidden focus tab 1 instead? In v1, only the active tab in the focused pane is visible at the drop point, so the question only matters if multiple terminals overlap — they don't. Skip.

## Acceptance criteria

- Drag a file from Finder over the terminal area: cursor shows the copy indicator; releasing inserts the shell-quoted path at the cursor and a trailing space.
- Drag multiple files: paths are joined with spaces, each quoted.
- Drag onto a non-focused pane: that pane's terminal receives the path, focus moves to it (consistent with click-to-focus from `#0060`).
- Drag onto a non-active tab area: noop (the tab isn't visible; drop should be a no-op or focus that tab first — pick one; v1 noop is fine).
- The accent-color border still flashes during drag-hover.
- Regression check: dragging onto the sidebar or chip bar does NOT paste a path (those areas have their own drop semantics, or none).

## Out of scope

- Dropping plain text content (only file URLs).
- Dropping to start a new tab / new session at the dropped folder's path.
- Inter-pane drag of an existing tab.

## Notes

- The existing `PaneView.handleFileDrop` and `ShellQuote.joinPaths(_:)` helpers are reusable as-is. The work is moving the call site, not changing the shell-quoting or send logic.
- This is a small, focused fix once you understand the dispatch mismatch. The harder part is just remembering that SwiftUI's `.onDrop` and AppKit's `registerForDraggedTypes` don't compose when an AppKit subview is over a SwiftUI drop target.
- `docs/view-hierarchy.md` should note this constraint after the fix lands — anyone touching the terminal-host layering needs to know that AppKit-on-top means AppKit owns the drop-target registration too.
- Related: `#0072`, `#0074`, `#0075` (the persistent-host chain).

## Root cause

After `#0075` moved the live terminal NSView into a persistent
`TerminalHostView` that sits as an AppKit subview *on top of* the
SwiftUI `TerminalPlaceholderView`, the drop target registered by
SwiftUI's `.onDrop` lived on the wrong layer. AppKit dispatches drags
to the deepest view at the cursor whose `registerForDraggedTypes`
includes a matching type. With the host (and its `AppTerminalView`
subviews) sitting above the SwiftUI drop target and neither
registered, AppKit rejected the drag at the host. Drag-and-drop does
not fall through to a SwiftUI sibling underneath — `hitTest` and
drag dispatch use different paths.

## Fix

Move drop-target registration onto `TerminalHostView`. The host
registers `.fileURL` in `init` and overrides the four drag entry
points (`draggingEntered`, `draggingUpdated`, `draggingExited`,
`prepareForDragOperation`, `performDragOperation`). On a drop, it
converts the drop point to host-local coords, walks visible
`AppTerminalView` subviews to find the one under the cursor, looks
up the matching `TabRuntime` via the new
`TerminalHostStore.tabID(for:)` / `tabRuntime(forTabID:)` helpers,
and sends the shell-quoted paths through `terminal.send(...)` — the
same code path the previous SwiftUI `.onDrop` used.

The accent-color hover border now reads from a new
`TabRuntime.isDragHovering` flag that the host writes from
`draggingEntered/Updated/Exited` and clears in the `defer` of
`performDragOperation`. `PaneView` consumes the active tab's flag for
its existing overlay. The SwiftUI `.onDrop` modifier and the now-dead
`handleFileDrop` / `loadFilePaths` / `loadFilePath` helpers are
deleted; `import UniformTypeIdentifiers` goes with them.

## Files changed

- `BattyKit/Sources/BattyKit/TerminalHostView.swift` — registers
  `.fileURL`, adds drag-entry/exit/update/prepare/perform overrides,
  hit-tests `AppTerminalView` subviews at the drop point, and routes
  to the resolved `TabRuntime.terminal.send(...)`. Manages the
  `dragHoverTabID` invariant so a tab whose hover state was set is
  always cleared on the matching exit/drop.
- `BattyKit/Sources/BattyKit/TerminalHostStore.swift` — adds a weak
  `[UUID: WeakTabRuntime]` map populated alongside the existing
  `terminalViews` dictionary, plus `tabID(for:)` and
  `tabRuntime(forTabID:)` lookups used by the host's drop routing.
  `releaseTerminalView(forTabID:)` clears the new map too.
- `BattyKit/Sources/BattyKit/TabRuntime.swift` — adds
  `isDragHovering: Bool` (default `false`). `@Observable` makes this
  participate in SwiftUI invalidation automatically.
- `BattyKit/Sources/BattyKit/PaneView.swift` — removes the
  `.onDrop`, the `@State isDragHovering`, the static
  `handleFileDrop` / `loadFilePaths` / `loadFilePath` helpers, and
  the unused `import UniformTypeIdentifiers`. The accent-color
  overlay opacity now binds to `pane.activeTab.isDragHovering`.

## Gotchas

- AppKit-on-top means AppKit owns the drop-target registration too.
  This constraint should be added to `docs/view-hierarchy.md` next to
  the existing notes on the host's `hitTest` behavior.
- The host's `performDragOperation` uses
  `pasteboard.readObjects(forClasses: [NSURL.self], options: [.urlReadingFileURLsOnly: true])`
  instead of the `NSItemProvider.loadItem(forTypeIdentifier:)`
  continuation dance the old SwiftUI path needed — AppKit's
  pasteboard API hands us the URLs synchronously, so the helper is
  smaller.
- `TerminalHostStore.tabRuntimes` is weakly held; if a tab is
  released between drag-enter and drop, `tabRuntime(forTabID:)`
  returns `nil` and the drop becomes a noop. That's the correct
  behavior for the corner case.
- **Not visually verified.** A subagent context can't drag from
  Finder. The following still need user confirmation: the cursor
  shows the copy/green-plus indicator on hover; the accent border
  fades in on `draggingEntered` and out on exit/drop; releasing
  inserts a shell-quoted path at the prompt; multi-file drags join
  with spaces; drops over a non-focused pane target that pane's
  terminal (not the focused one); drops outside any terminal subview
  are a noop; drops onto the sidebar / chip bar still don't paste.
