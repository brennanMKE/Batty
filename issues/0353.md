# 0353 — The system-metrics readers emit no logging, so sensor and syscall failures are undiagnosable silent dashes

## Description

None of the system-metrics reader files declare a logger: `SMCThermalReader.swift`, `SystemCPUReader.swift`, `SystemLoadReader.swift`, `SystemMemoryReader.swift`, `ProcessMetricsReader.swift`, and `SystemMetricsSampler.swift` contain zero `Logger` references (verified by grep — every count is 0). When an SMC read fails, `host_statistics64` returns non-success, or `host_processor_info` errors, the failure collapses into a `nil`/`unavailable` value that the view renders as "—", with nothing in Console.app. A user report of "temperature shows a dash" is undiagnosable: there is no way to tell key-not-found from connection-refused from a protocol error without rebuilding with instrumentation.

`CLAUDE.md` mandates the file-scoped logger pattern (`nonisolated private let logger = Logger(subsystem: Logging.subsystem, category: "<Filename>")`) for any file that needs to emit logs; these files need to and don't.

Logging discipline matters here because the failure paths are *expected* on some machines (the SMC reader's own doc comment says a key not resolving "is an expected, not exceptional" outcome): the fix should log failures at an appropriate level **once per distinct cause**, not once per 1 Hz tick — a dash on a Mac with no exposed temperature key must not become 86,400 log lines a day.

## Expected behavior

Each reader logs its failure paths with enough detail to distinguish causes (which key, which syscall, what return code), rate-limited or once-per-transition so steady-state unavailability stays quiet after the first report.

## Actual behavior

All failures are silent; the UI shows "—" and Console shows nothing.
