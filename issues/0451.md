## Description

The user wants to review the UI/UX of the four non-terminal view Panes — Git Status, Process Status, System Metrics and LM Studio Dashboard (`PaneContentKind` in `BattyKit/Sources/BattyXPCCore/PaneContentKind.swift`; views in `BattyKit/Sources/BattyKit/Views/GitStatusPaneView.swift`, `ProcessStatusPaneView.swift`, `SystemMetricsPaneView.swift`, `LMStudioDashboardView.swift`) — from screenshots captured in the Tart VM (`docs/ui-testing-vm.md`, `tools/run-ui-tests-vm.sh`, `tools/export-ui-recordings.sh`). Nothing in the suite produces such captures today. The only footage of these views is the per-test screen recording that `BATTY_UI_KEEP_RECORDINGS=1` keeps for `BattyUITests/CLIViewPaneTests.swift` (#0448), and those recordings are not usable for design review:

- **The window is small and the view Pane gets a fraction of it.** The recordings are 1024x768 (`mdls` on `build/ui-tests/20261009-162038-54093/recordings/CLIViewPaneTests.*.mp4` reports `kMDItemPixelWidth = 1024`, `kMDItemPixelHeight = 768`), and the app window in them is about 895x493 points, measured off the exported poster frame. `CLIViewPaneTests` splits the single terminal Pane once (`pane split --view <kind>`, default horizontal), so the view Pane gets roughly half of a ~650-point-wide content area, with the Sidebar taking the rest of the window.
- **The git fixture is nearly empty.** `BattyCLI.makeGitRepository` (`BattyUITests/Support/BattyCLIHarness.swift`) writes a `.git` directory by hand (`HEAD`, `config`, empty `objects`/`refs`) plus one `untracked-file.txt`, without running `git` — its own doc comment says the sandboxed runner may not be able to. The resulting Git Status view shows one group, "Untracked Files (1)" (`fileGroup` renders `DisclosureGroup("\(title) (\(entries.count))")`), and nothing of the "Conflicted", "Staged Changes" and "Changes" groups, the ahead/behind label (`aheadBehindLabel`, only shown when `hasUpstream` and ahead or behind > 0), the operation banner (`git-status.operation-banner`, e.g. "Merge in progress — N conflicts"), the diff peek (`git-status.diff-peek`), long paths, or a branch with commits.
- **Process Status and System Metrics are captured on their first tick.** Neither view retains history — `SystemMetricsPaneContent` documents "zero retained history (`snapshot` is replaced wholesale each tick, never appended to)" at a 1 s `sampleInterval`, and `ProcessStatusPaneContent` samples on a 1 s `samplingInterval` with per-pid CPU delta baselines — so there is no chart to fill in, but the first sample is not representative either: CPU percentages need a prior baseline, the Process Status disclosure sections (children, open files) load lazily, and `--pid` is only exercised against the app's own pid, not a busy child.
- **A macOS banner covers the top right of the screen.** The poster frame of `testSplitGitStatusRendersTheFixtureRepository` shows the "App Background Activity — 'BattyBroker' can run in the background. You can manage background activity in Login Items & Extensions." notification over the menu bar corner. It is raised when `tools/vm-guest-broker.sh` bootstraps the embedded broker's LaunchAgent into the guest's `gui/<uid>` domain (#0419). `docs/ui-testing-vm.md` and #0412 previously recorded guest prompts as "unconfirmed — a non-modal banner would not show up in the results"; this is that banner, now observed.
- **Recordings are video only.** The result bundle carries no still-image attachments; `tools/export-ui-recordings.sh` filters `xcresulttool export attachments` to `*.mp4` and generates one `qlmanage` poster per recording, scaled to 800 px, which is the only still available.

## Expected behavior

A new UI test class (suggested name `BattyUITests/ViewGalleryTests.swift`) whose purpose is producing review screenshots, not asserting behavior beyond "the view rendered". For each view kind it:

1. Launches Batty through `BattyUITestHarness.launchBatty()` and opens the view with the real embedded CLI through the same relay harness `CLIViewPaneTests` uses (`BattyCLI.connect`, `BattyCLI.runExpectingSuccess(["pane", "split", "--view", ...])`).
2. Enlarges the window to fill the 1024x768 VM display and gives the view Pane a large share of it. There is no CLI verb for window size or Pane zoom (`TopologyPayload.swift` notes that no zoom concept exists in the runtime model) and no split-ratio flag on `pane split` (only `--horizontal`/`--vertical`, see `PaneCommand.swift`), so the implementer picks a mechanism: the standard Window > Zoom menu item or a window-corner drag through XCUITest for the window; collapsing the Sidebar (Cmd-B, already driven in `WindowRestorationTests.testToggleSidebarAffectsOnlyKeyWindow`) and/or dragging the Split divider from coordinates as `SplitDividerDragTests` does (the divider carries no accessibility identifier) for the Pane share. `batty list --json --include-dimensions` reports each Pane's `frame`/`visibleRect`, which can confirm the achieved size.
3. Puts realistic content in front of the view, then waits on a rendered-state signal already exposed through accessibility identifiers (`git-status.snapshot`, `git-status.file.<path>`, `system-metrics-refresh-button` which only appears once a first sample has landed, `process-status-view`, `lmstudio-connection-pill.<state>`) rather than a fixed sleep where one exists. AGENTS.md's no-sleep rule is binding for unit tests; a UI test may need a bounded wait where the signal is "the second tick has happened", and the issue leaves that to the implementer with the bound documented.
4. Attaches full-window `XCUIScreenshot`s as `XCTAttachment` with `lifetime = .keepAlways` and descriptive names (e.g. `gallery.git-status.light`, `gallery.git-status.narrow.dark`).

States to cover:

- **Git Status** on a repository built with real `git`, with staged, modified, deleted, renamed and untracked files, several commits, a long path (deep directory plus a long file name), and a named branch; ideally a configured upstream so the ahead/behind label renders. The sandboxed XCUITest runner may not be able to exec `git` (the `makeGitRepository` caveat; #0419 records the runner as App Sandboxed), but a terminal Pane's `--command` script runs unsandboxed inside the app — `BattyCLI.makeScript` writes a script the Pane runs as `/bin/sh <path>` (quarantine makes direct execution fail), and `testAgentInsideAPaneOpensGitStatusUniquelyTwice` already uses this to run the CLI from inside a Pane with a sentinel file to await. The fixture script can build the repository the same way, then the test opens `--view git-status --path <repo>`.
- **Git Status not-a-repository state** (`git-status.not-a-repo`, already exercised by `testSplitGitStatusWithNonRepositoryPathShowsNotARepository`).
- **Process Status** following the terminal's foreground process (whole-system view), and pinned with `--pid` to a deliberately busy child process started by a `--command` script, captured after a sample with a CPU baseline (second tick or later), with the disclosure sections expanded if they are reachable through accessibility.
- **System Metrics** after the first sample has landed (`system-metrics-refresh-button` present, `system-metrics-waiting` gone) and at least one further tick so per-core utilization is non-trivial; the "Sampling system metrics…" waiting state is worth one capture of its own.
- **LM Studio Dashboard** disconnected state (the guest has no LM Studio server; `testSplitLMStudioDashboardRendersDisconnected` asserts the pill is not `.connected`).
- **Light and Dark appearance** for each, if reachable. Batty follows the system appearance (`AppearanceObserver` observes `NSApp.effectiveAppearance`) and stores one theme per appearance (`ThemePreference`: TokyoNight for Dark, TokyoNight Day for Light). There is no appearance intent in `UITestDriver` and the Settings "Appearance" tab is font/surface appearance, not Light/Dark. Options include a test-mode launch argument or environment variable the app honours by setting `NSApp.appearance`, or `-NSRequiresAquaSystemAppearance` for the Light side only; the golden guest runs Light (visible in the poster frames). If Dark cannot be reached without a product change, capture Light only and say so.
- **Narrow Pane**: each view in a small split (the view Pane at roughly a quarter of the content width, or whatever the divider drag yields), since layout at small widths is the likeliest UX problem. `ProcessStatusPaneView` declares `.frame(minWidth: 260, minHeight: 320)` on its picker sheet, which is one known lower bound.

The background-activity banner must not be over the app window in any capture. Options: capture only after the banner has auto-dismissed (it is a transient banner, not a persistent alert), dismiss it via its accessibility element in the Notification Center process, or have the capture wait until no `NSNotificationCenter`-style banner element is present on screen; if none is feasible, the issue should record why.

An export path for the stills: either extend `tools/export-ui-recordings.sh` or add a sibling tool (e.g. `tools/export-ui-screenshots.sh`) that runs `xcresulttool export attachments --filter '*.png'`, maps each exported UUID-named file back to its attachment name from `manifest.json` (the recordings script already does this mapping for `.mp4`), and writes `build/ui-tests/<run-id>/screenshots/<attachment-name>.png`.

### Acceptance

A VM run of the new class (`tools/run-ui-tests-vm.sh BattyUITests/ViewGalleryTests`, through the standing authorization in AGENTS.md) produces one named PNG per view state listed above, exported to `build/ui-tests/<run-id>/screenshots/`, at the VM display's full resolution (1024x768, the window filling it), with no notification banner over the app window, and `docs/ui-testing-vm.md` / `tools/README.md` say how to run and export it.

## Actual behavior

No test attaches screenshots. The only captures are the `CLIViewPaneTests` recordings described above, and their 800 px posters, which show a ~895x493 window with a half-width view Pane, a one-file git fixture, first-tick metrics, and the background-activity banner.

## Notes

- Verified against the code on 2026-10-09: recording dimensions (`mdls`), the poster frame (`build/ui-tests/20261009-162038-54093/recordings/CLIViewPaneTests.testSplitGitStatusRendersTheFixtureRepository.poster.png`), `makeGitRepository`, `makeScript`, the Git Status group titles and identifiers, `SystemMetricsPaneContent`'s no-history budget and 1 s interval, `ProcessStatusPaneContent`'s 1 s interval, `PaneCommand`'s split flags, `TopologyPayload`'s zoom note, `AppearanceObserver`/`ThemePreference`, `UITestDriver`'s intent list, and `tools/export-ui-recordings.sh`'s `*.mp4` filter.
- `XCTAttachment.lifetime = .keepAlways` set in code should survive a run without `BATTY_UI_KEEP_RECORDINGS=1`; the scheme attribute that variable injects (`userAttachmentLifetime`) only sets the default for attachments that do not set a lifetime. The implementer should confirm this in the first VM run rather than assume it, since #0448's verification tested the scheme attribute, not an explicit per-attachment lifetime.
- A screenshot of the whole screen (`XCUIScreen.main.screenshot()`) includes the banner, the Dock and the desktop; a screenshot of the window element (`app.windows.firstMatch.screenshot()`) crops to the window and sidesteps the banner only if the banner does not overlap the window. With the window zoomed to fill the display, it will overlap, so dismissal or waiting is needed either way.
- The Git Status fixture needs `git` in the guest. The golden image has Xcode (the runner builds the app there), so `/usr/bin/git` resolves through the Command Line Tools shim; the implementer should check the first run's output for `xcode-select` errors.
- The relay never carries `BATTY_*` environment, so every CLI call from the test names its target Pane explicitly (`BattyCLIHarness.swift` header). A `--command` script run inside a Pane does carry it.

### Open questions

- Should `ViewGalleryTests` be excluded from the normal full-suite run (it adds launches, a real `git` fixture and image attachments to the bundle, on top of a ~10 min suite), run only on request via a filter, or be cheap enough to stay in? The implementer should measure its cost in the VM and propose, not decide, in the resolution notes.
- Whether the Dark appearance needs a small test-mode hook in the app (a launch argument the product already ignores outside `BATTY_UI_TEST_MODE`) or can be reached without touching product code.
- Whether the background-activity banner can be suppressed at its source — e.g. by `tools/vm-guest-broker.sh` bootstrapping the agent earlier so the banner has expired before the test phase starts — instead of each test waiting it out.
