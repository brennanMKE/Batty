## Description

Newly created Terminal Sessions and newly split panes are not receiving keyboard focus. After creating a new session, the user cannot type a command into it until they click into the pane. After splitting a pane, clicking on a sibling pane to focus it also does not consistently work.

These two symptoms likely share a single root cause in how first-responder status is assigned to `TerminalSurfaceView` when the surface is first inserted into the window's view hierarchy, and how click-to-focus is wired on existing panes when the split layout changes.

## Steps to reproduce

1. Launch Batty.
2. Create a new session (sidebar "+" or `Cmd-N`).
3. Without clicking anywhere, try to type a shell command.
4. From the focused pane, create a horizontal or vertical split.
5. Click on the new sibling pane (or back on the original) to try to focus it and type.

## Expected behavior

- A new session's initial pane should be first responder immediately on appear — typing should go straight to the shell.
- After a split, the newly created pane should take focus automatically, and clicking any visible pane should make it first responder so keystrokes go to that pane's surface.

## Actual behavior

- New session appears but keystrokes are dropped (or routed elsewhere) until the user clicks inside the pane.
- After splitting, click-to-focus on sibling panes is unreliable — focus stays on whichever pane held it before the split, or click events do not promote the clicked pane to first responder.

## Notes

- Both symptoms are likely the same bug — file as one issue and split later only if the root causes turn out to be unrelated.
- Likely areas to investigate:
  - `TerminalSurfaceView` (NSViewRepresentable) — `makeNSView` / `updateNSView` and whether `window?.makeFirstResponder(_:)` is called when a new surface is added.
  - Pane creation paths for new sessions vs. splits — whether both call into the same focus-promotion helper.
  - Click / mouseDown handling on the pane's NSView — `acceptsFirstResponder`, `becomeFirstResponder`, and whether `mouseDown(with:)` requests first responder before forwarding to libghostty.
  - See `docs/view-hierarchy.md` for the surface-registry / persistent AppKit host rules that govern how surfaces are reparented; focus assignment must respect that lifecycle.

## Root cause

Two related first-responder gaps with one shape: AppKit does not auto-promote a clicked or freshly-mounted `AppTerminalView` to its window's first responder, and the upstream libghostty-spm `AppTerminalView.mouseDown(with:)` only forwards the mouse position and button press to its `TerminalSurface` — it never calls `window.makeFirstResponder(self)`.

- **Click-to-focus on sibling panes:** clicking on a sibling pane's terminal sends `sendMousePos` and `sendMouseButton` to that surface but leaves the window's first responder pointed at the previously focused pane, so keystrokes continue flowing there. The `windowDidBecomeKey` observer in libghostty-spm only takes effect when `firstResponder === self`, so nothing inside the surface ever bridges the gap.
- **New session no focus on appear:** `SessionDetailView.onChange(of: store.selectedSessionID)` and the new pane's `TerminalPlaceholderView.onAppear` both call `TerminalSurfaceFocuser.focusWhenReady`, but the helper ran one attempt synchronously and then retried once after 50ms. A brand-new session's `AppTerminalView` walks three independent runloop turns before keystrokes can land — placeholder mount creates the view as `isHidden = true`; the placeholder reports its frame via the `PreferenceKey` flow; `TerminalHostStore.updatePlacements` then unhides it. The single 50ms retry could race past the unhide pass, and even when the focus call landed in time, AppKit silently refuses to deliver key events to a hidden view, so a successful `makeFirstResponder` on a still-hidden view became a no-op.

## Fix

- Add `TerminalClickFocusMonitor`, a `@MainActor` singleton-style enum that installs a single `NSEvent.addLocalMonitorForEvents(matching: [.leftMouseDown])` at app launch. On every left mouse-down it hit-tests the window root, walks up to the nearest `AppTerminalView` ancestor, and calls `window.makeFirstResponder(terminal)` if it is not already first responder. The event is returned unmodified, so the libghostty mouse-down path still runs. Started from `BattyAppDelegate.applicationDidFinishLaunching` alongside the existing key-event monitor.
- Expand `TerminalSurfaceFocuser.focusWhenReady` to retry on a 16/50/150/400 ms back-off and to treat a hidden match as "not ready" so the promotion is deferred until `TerminalHostStore.updatePlacements` has unhidden the view. `focus(terminal:)` now reports success/failure so the back-off loop terminates as soon as a visible view is promoted, and a `[weak terminal]` capture ensures a closed/replaced surface does not keep the retry task alive.

The model-side focus follow-up (`tree.focusedPaneID`, the focus-border overlay, the `markActiveTabSeen` bell cascade) is unchanged — it is driven by `PaneView.onChange(of: tab.terminal.isFocused)`, which fires from libghostty's focus delegate the moment `becomeFirstResponder` runs.

## Files changed

- `BattyKit/Sources/BattyKit/Commands/TerminalClickFocusMonitor.swift` — new file. The local `NSEvent` mouse-down monitor that walks the hit-tested view and promotes any `AppTerminalView` ancestor to first responder.
- `BattyKit/Sources/BattyKit/Commands/TerminalSurfaceFocuser.swift` — `focus(terminal:)` returns a `Bool`, skips hidden matches; `focusWhenReady(terminal:)` retries on a staggered schedule with a `[weak terminal]` capture; the rationale for both is documented inline.
- `Batty/BattyApp.swift` — `BattyAppDelegate.applicationDidFinishLaunching` calls `TerminalClickFocusMonitor.start()` next to the existing key-event monitor.

## Gotchas

- `AppTerminalView` is declared `public final class` in libghostty-spm, so the only way to interpose on `mouseDown` from the Batty side is at the event-monitor level — subclassing is closed off. Anyone tempted to "just" override the mouse path will need to revisit `libghostty-spm` itself.
- `NSWindow.makeFirstResponder` on an `isHidden` `NSView` succeeds at the responder-chain level but key events are not dispatched to a hidden view. Without the new "skip hidden matches" guard, the focuser could report success while the user kept typing into the void — exactly the original symptom in a different costume. Treat `isHidden` as a hard signal to wait for the next placement pass.
- The click monitor uses `.leftMouseDown` only. Right-clicks and middle-clicks are left alone so a context-menu invocation on a sibling pane does not steal focus from whatever the user was typing into — revisit only if a future bug reports right-click focus surprises.
- This is a UI-timing fix; it was verified by the `xcodebuild -scheme Batty -destination 'platform=macOS' build` pass and the full `BattyKit` test suite (220 tests). The interactive behaviors — new-session keystrokes landing immediately, click-to-focus on sibling panes promoting correctly — could not be exercised headlessly and need a Mac-app sanity check before closing.
