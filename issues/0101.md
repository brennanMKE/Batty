# 0101 — Terminal view doesn't fill its pane on cold launch (resize works around it)

| | |
|---|---|
| **Status** | open |
| **Module** | TerminalSurface / Pane |
| **Platform** | macOS |
| **First seen** | 2026-05-12 |

## Description

On cold launch, the terminal NSView for the default session's only pane renders at a smaller frame than the pane area it should fill. The tab strip sits at the correct width, but the terminal area below the chips is a rectangle roughly half the available width and three-quarters the height, with empty dark-gray space to the right and below. Dragging to resize the window by even one pixel forces a layout pass and the terminal snaps to fill correctly from that point on. Subsequent navigation (Cmd-T, Cmd-D, sidebar collapse) does not regress; only the first paint is affected.

The bug is mis-sized geometry, not a missing NSView or a zero-size host. The NSView is in the host, the PTY is running (shell prompt is visible), input works inside the visible terminal box. Just sized wrong on first paint.

This is a SwiftUI ↔ AppKit timing issue in the `#0075` persistent-host architecture: the `TerminalPlaceholderView`'s first `GeometryReader`-emitted `Placement` doesn't match the placeholder's eventual size, and the placement preference doesn't re-fire because the placeholder's own SwiftUI frame never changes after settling — only the underlying NSView's frame ends up wrong.

## Steps to reproduce

1. Quit Batty completely.
2. Relaunch from Xcode or Finder.
3. **Observed:** the default session's terminal area is a rectangle smaller than the pane. Empty gray space surrounds it.
4. **Workaround that proves the bug:** resize the window by one pixel via the drag handle. The terminal snaps to fill correctly.

Also reproduces after a clean build + run.

## Hypotheses

In rough order of likelihood:

### 1. First placement frame is stale

`TerminalPlaceholderView` reports `proxy.frame(in: .named(TerminalHostInstaller.coordinateSpaceName))`. On the first SwiftUI layout pass the named coordinate space may not be fully registered (it's declared on the outer ZStack in `SessionDetailView`; the placeholder is several levels deep inside `PaneView`). The first emitted frame could be `.zero` or a frame in the pre-layout coordinate system.

`TerminalHostStore.updatePlacements` then applies that stale frame to the `AppTerminalView`. SwiftUI's next pass produces a settled frame and should re-fire the preference — but the second emission may be dropped if `PreferenceKey.reduce` collapses identical-looking maps, or if the placeholder's frame in SwiftUI hasn't actually changed between passes.

### 2. Host's own frame is stale

`TerminalHostView.init(frame: .zero)` plus `autoresizingMask = [.width, .height]` should make the host grow to fill its parent — but only after the parent has a non-zero size. If `TerminalHostInstaller.makeNSView` runs before SwiftUI's hosting view has settled, the host's frame stays small for one render cycle. Even if subviews are positioned correctly within the host, the host's clip would cut them off.

The fact that resize fixes this is consistent: a resize triggers `layout()` on the entire view tree, including the host, which then takes its parent's full size.

### 3. AppTerminalView's autoresize is disabled

In `TerminalHostStore.terminalView(for:)`:

```swift
view.autoresizingMask = []
view.translatesAutoresizingMaskIntoConstraints = true
```

The view explicitly opts OUT of autoresizing — placements are pushed manually via `updatePlacements`. If the first placement was stale (per hypothesis 1) and a corrected one never fires, the AppTerminalView is stuck at the bad frame.

### 4. `Window` scene initial sizing

`#0063` switched from `WindowGroup` to `Window`. `Window`'s default sizing creates the SwiftUI hosting view before the NSWindow has settled to its final frame. The first SwiftUI layout pass runs against a temporarily-undersized window; the NSView sized against that frame ends up too small.

## Investigation plan

1. **Add a debug log** in `TerminalHostStore.updatePlacements` printing the placements map (count + each frame) every time it fires. Re-run from cold launch and capture how many calls fire before the user can see the window. If the first call has wrong frames and no second call follows, hypothesis 1 is confirmed.

2. **Override `TerminalHostView.layout()`** with a one-time log of the host's frame. Compare against the placement frames. If the host's frame is smaller than expected for one pass, hypothesis 2.

3. **Check `TerminalHostInstaller.makeNSView`** — does it set up the host to track its container's bounds via constraints or autoresize? `NSViewRepresentable` doesn't auto-bind frames; the wrapper must do it.

## Suggested fixes, in order

### Fix A — re-emit placement via `.onGeometryChange`

In `TerminalPlaceholderView`, observe size changes with `.onGeometryChange(for: CGSize.self) { $0.size } action: { ... }` (macOS 14+) and republish the placement when the size settles. A SwiftUI `.task { }` after first appearance can also force a fresh body evaluation.

### Fix B — frame layout via constraints inside the host

Switch `AppTerminalView`'s frame management from manual to constraint-based. Pin all four edges to the host with constants captured from the latest placement; activate once and mutate the `constant` values in `updatePlacements`. Constraint-based layout participates in AppKit's resize chain and would correctly recompute even if a placement is missed.

### Fix C — autoresize the host against its parent

Set up the host with explicit constraints to its parent so the host fills the SwiftUI container even before any placement fires. Subviews continue to be placed manually. Doesn't fix subview-level stale placements but eliminates hypothesis 2.

### Fix D — fall back to filling the host when only one terminal is visible

If only one tab is visible in one pane, set the visible AppTerminalView's autoresizingMask to `[.width, .height]` and pin to the host's bounds. Multi-pane layouts still use the placement system. This is a hack but cheap and would unblock the cold-launch experience while a real fix lands.

### Fix E — debounce / coalesce

Hold the first placement map for one runloop cycle and apply the second, third, ... (whichever is most recent in a window). Avoid this if A or B work — it papers over the missed-signal rather than fixing it.

## Acceptance criteria

- Cold-launch the app. The default session's terminal area fills the available pane space (chips at top, terminal below filling the rest, no empty gray).
- Same after `Cmd-N` for additional sessions.
- Same after `Cmd-T` for additional tabs.
- Same after `Cmd-D` / `Cmd-Shift-D` for splits.
- Window resize from any starting size updates both terminal and chrome smoothly.
- No regression in tab/pane switching (the host architecture must continue to preserve PTYs across navigation — `#0072` / `#0075`).
- A UI test (or model-level assertion) covers cold-launch frame correctness, ideally as part of `#0091`'s harness.

## Out of scope

- Persisting window size or pane ratios across launches.
- Tuning the resize animation curve.
- Multi-window initialization (single-window per `#0063`).

## Notes

- "Resize fixes it" is the strongest signal that this is a layout-settling timing issue, not a placement-correctness or host-attachment issue.
- This is a one-time cost paid by the `#0075` design: SwiftUI's eager layout has to deliver a correct geometry preference before the host can position the AppTerminalView. The simple representable (pre-`#0072`) had SwiftUI sizing the NSView directly, which sidestepped this — which is why naive AppKit-in-SwiftUI usually "just works" at launch.
- Don't pursue Fix E (debounce) without trying A through C first.
- Related: `#0072`, `#0074`, `#0075` (the persistent-host chain), `#0066` (cold-launch first-responder race — different but adjacent timing concern).
