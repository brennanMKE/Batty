# 0340 — Duplicating a Session can hand the copy the source's own color once every palette index is in use

| | |
|---|---|
| **Status** | open |
| **Module** | Session |
| **Platform** | macOS |
| **First seen** | 2026-08-20 |

## Description

`WindowRuntime.duplicateSession(id:)` asks `nextColorIndex()` for the
copy's palette index, relying on the source Session still being counted
as "in use" to steer the pick elsewhere. That holds only while some
palette index is unused. Once every index in `SessionColor`'s 10-color
palette is held by at least one live Session, the usage tally no longer
distinguishes the source from anything else, and the round-robin
tie-break can land on the source's own index — so the duplicate comes out
the same color as the Session it was duplicated from, which is exactly
the case a duplicate's color is supposed to disambiguate.

Carved out of [#0335](0335.md) during review; see Relation.

## Steps to reproduce

1. In one Window, create Sessions until all 10 palette indices are in use
   (the Window bootstraps with one Session at index 0, then nine
   `addSession()` calls walk indices 1 through 9).
2. Duplicate the Session holding palette index 0.
3. Compare the copy's Sidebar color mark with the source's.

## Expected behavior

A duplicated Session gets a color other than its source's whenever any
other palette index is at least as lightly used — #0335's design notes
state it directly: "`duplicateSession` … a duplicate should get a fresh
color, not the source's" (`issues/0335.md:59-60`).

## Actual behavior

The copy is assigned the source's index, so source and copy render with
the same Sidebar color while other equally-used indices were available.

## Relation

- Carved out of [#0335](0335.md) during that issue's Opus review round.
  #0335 shipped the assigner this issue modifies —
  `WindowRuntime.nextColorIndex()` and the `duplicateSession` call site —
  so this defect does not exist on `main` until #0335 lands. The
  reviewer classed it non-blocking: past 10 Sessions color collisions
  are unavoidable in a 10-color palette, and "a duplicate never matches
  its source" is not in #0335's acceptance criteria.
- [#0336](0336.md) will add user-chosen Session colors on top of the
  same assigner. Whoever fixes this should check the interaction: once a
  user can pin a Session to a specific color, "skip the source's index"
  has to compose with whatever #0336 does about explicitly-chosen
  indices, and the two changes touch the same tie-break.

## Verified trace

Read from `git show issue/0335:BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift`
(not on `main` yet) and confirmed by replaying `nextColorIndex()`'s exact
arithmetic. The reviewer's trace holds as stated.

`nextColorIndex()` (lines 101-118 on the branch):

```swift
let minCount = counts.min() ?? 0
var chosen = (lastAssignedColorIndex + 1) % paletteCount
for step in 0..<paletteCount {
    let candidate = (lastAssignedColorIndex + 1 + step) % paletteCount
    if counts[candidate] == minCount {
        chosen = candidate
        break
    }
}
```

State: a Window whose 10 Sessions hold indices 0 through 9 exactly once
each, with `lastAssignedColorIndex == 9`. That state is the natural
result of creating ten Sessions in a row — `init` seeds the first Session
at index 0 and sets `lastAssignedColorIndex = 0` (lines 80-89), and the
nine following `addSession()` calls hand out 1 through 9.

Duplicate the Session holding index 0: `counts` is all 1s, so
`minCount == 1`; the scan starts at candidate `(9 + 1) % 10 == 0`;
`counts[0] == 1 == minCount`, so it breaks immediately with
`chosen == 0` — the source's own index.

It is not limited to the exactly-ten case. Any state where every palette
index is in use reproduces it whenever the cursor's first candidate
happens to be the source's index. With eleven Sessions (indices 0-9 plus
a second holder of 0, `lastAssignedColorIndex == 0`), duplicating the
Session that holds index 1 yields index 1 the same way.

The comment at the call site (lines 213-215) is what encodes the
too-strong assumption:

```swift
// Fresh color, not the source's — the source is still in `sessions`
// while `nextColorIndex()` tallies usage, so it naturally counts as
// "in use" and the least-used pick tends to land elsewhere.
```

"Tends to land elsewhere" is true only while some index sits below the
source's usage count. At saturation the tally gives the source no
protection at all, because every index ties.

## The existing test cannot catch this

`BattyKit/Tests/BattyKitTests/SessionColorAssignmentTests.swift:105-111`
(`duplicateSessionGetsAFreshColorNotTheSources`) passes by construction,
so it is not a guard against this bug:

```swift
let window = makeWindow()
let source = window.sessions[0]
let duplicate = window.duplicateSession(id: source.id)
```

`makeWindow()` returns a one-Session Window. That Session holds index 0
at count 1 while every other index is at count 0, so `minCount == 0` and
the source's index is the one value the scan can never select. The test
would still pass with the tie-break unchanged no matter how the
saturated case behaves.

## Proposed fix (not a mandate)

The reviewer's suggestion: pass the source's index into the tie-break and
skip it when any *other* index ties at `minCount` — falling back to the
source's index only when it is genuinely the sole least-used option, so
behaviour is unchanged in the non-saturated case and no caller can be
handed an out-of-range index. Whoever implements it should weigh that
against alternatives (for example, excluding the source from the usage
tally, which is a different and probably wrong shape — it would make the
source's index look *less* used and attract the pick).

## Acceptance criteria

- Duplicating a Session in a Window where every palette index is in use
  produces a color index different from the source's, so long as at
  least one other index is tied at the minimum usage count.
- Non-saturated behaviour is unchanged: the existing
  `SessionColorAssignmentTests` cases still pass unmodified.
- **A new test exercises the saturated-palette case specifically** —
  build the ten-Sessions-holding-0-through-9 state described above,
  duplicate the Session holding index 0, and assert the copy's index
  differs from the source's. This is required, not optional: the existing
  `duplicateSessionGetsAFreshColorNotTheSources` cannot fail on this bug,
  so a fix without a saturated-case test is unguarded. Confirm the new
  test name appears in the `scripts/build.sh unit` output and that it
  fails before the fix.
- If ten Sessions in one Window turns out to be awkward to construct in a
  unit test, note that `WindowRuntime.init` accepts a pre-built
  `sessions:` array — but check what `lastAssignedColorIndex` is in that
  path before relying on it (the non-empty branch, lines 90-92, does not
  set the cursor).
