# 0570 — The one-minute `.timeLimit` on the Project startup and XPC suites counts MainActor queueing, so a loaded full unit run fails tests that never hung

| | |
|---|---|
| **Status** | open |
| **Module** | Testing / Projects |
| **Platform** | macOS |
| **First seen** | 2026-11-09 |

## Description

On 2026-11-09 a full `./build.sh unit` on `issue/0567` failed. That branch doesn't touch Project startup or `TabRuntime`. The reported failure was `ProjectStartupReadinessTests/awaitingADismissedOrClosedDeliveryReturns()` exceeding its 60 s time limit. The caller reports that this run stopped at 217 tests. An immediate re-run passed all 3400.

The test did not hang. Every await in it completes synchronously or on one clock tick. The log shows the whole MainActor was saturated: dozens of unrelated `@MainActor` tests finished at the same instant, about 72 s after they started. The test's own body ran after the limit had already fired. The cause is the suite-level `.timeLimit(.minutes(1))` trait. It measures wall-clock time from when a test is *started*, and that includes the time the test waits in line for the shared MainActor during a 3400-test parallel run. Even the passing re-run took 31.8 s for this test, more than half its limit, for a body that does no real waiting. It is the only wall-clock bound in the target that does not go through `TestBounds.hangGuard`, and it sits right at that same 60 s value.

## Evidence

Failing log: `.claude/worktrees/issue-0567/build/checks/unit-20261109-002042-93054.log`. Passing re-run: `unit-20261109-002315-98494.log` (same folder).

- The test started at log line 4989, at about 00:20:59. At 00:21:59 (line 41813) the time limit fired. It fired at the same instant for **62** tests, all in the only two files with a `.timeLimit` trait: 34 in `ProjectStartupTests.swift` and 28 in `ProjectXPCTests.swift`. That includes every test in `ProjectStartupReadinessTests` (lines 41813–41829).
- 134 tests across unrelated suites, such as Reminder and Bell Feed tests, finished "after 72.x seconds" at 00:22:11, passes and failures alike. More than 2500 tests took 20 s or longer. Early in the run, trivial tests already took 10–14 s (for example line 12565, `refreshNowSamplesImmediatelyWhileActive() passed after 10.388 seconds`).
- From 00:21:30.69 to 00:21:52.72 the main thread (tid 290226279) logged nothing for 22 s. Only three `generic_renderer: created display link` lines from other threads appear, at roughly 7 s intervals (lines 34901–34903). Some test was creating real libghostty surfaces and renderers while the main thread was blocked. That stall falls entirely inside this test's 60 s window.
- This test's own log lines appear only after the limit, at 00:22:11: `startup command disarmed: … reason=shell exited before reporting readiness` (from the `closedTab` half of the test, `TerminalDelegateProxy.swift:205-209`), followed directly by `✘ Test awaitingADismissedOrClosedDeliveryReturns() failed after 72.172 seconds` (line 58387). The body got far enough to close the second tab, so it was waiting for the MainActor, not for a signal that never came.
- Passing re-run: `awaitingADismissedOrClosedDeliveryReturns() passed after 31.820 seconds` (line 58046), in a 32.8 s run of 3400 tests.

## Why the test itself cannot hang

`BattyKit/Tests/BattyKitTests/ProjectStartupTests.swift:778-794`:

- `clock.waitForSleepers(1)` (`TestClock.swift:190-209`) resumes the instant the deadline Task registers. That Task is started synchronously by `attach` → `surfaceDidAttach` → `startReadinessDeadline` (`TerminalDelegateProxy.swift:139-144`, `168-175`). The wait is bounded by `TestBounds.hangGuard` (60 s, `TestBounds.swift:26`).
- `passDeadline` (`ProjectStartupTests.swift:641-645`) advances by exactly the deadline. It then awaits the Task, which needs one MainActor turn to run `readinessDeadlineDidPass`.
- `dismissWaitingStartupCommand()` → `dismissStartupCommand()` → `abandon()` → `finish()` runs synchronously (`TabRuntime.swift:235-237`, `TerminalDelegateProxy.swift:155-157`, `StartupCommandDelivery.swift:105-122`). So `isFinished` is already true, and `waitUntilFinished()` returns at once (line 113).
- `closedTab` is never attached, so it schedules no deadline. `terminalDidClose` abandons the delivery synchronously (`TerminalDelegateProxy.swift:205-209`), so the second `waitUntilFinished()` also returns at once.

No continuation is left unresumed, and no clock is left un-advanced. The order of the dismiss or close and the await doesn't matter either, because `finish()` sets `isFinished` before any await.

One latent weakness: `waitForSleepers`'s Bool result is discarded. If registration ever took longer than its own 60 s bound, `passDeadline` would advance zero sleepers and `await task?.value` would wait forever. That path doesn't apply here, because the suite limit fired first at the same 60 s.

## Recommendation

Keep the hang guard and stop it from counting queue time. Don't add sleeps and don't reorder the test.

1. Remove `.timeLimit(.minutes(1))` from the five suites that carry it: `ProjectStartupTests.swift:112`, `:330`, `:648`, `:906`, and `ProjectXPCTests.swift:87`. No other suite in the target has one. Every other suite relies on per-await hang guards routed through `TestBounds.hangGuard`, as `docs/async-test-seams.md` and #0443 require. That is the rule this trait breaks.
2. Make the awaits in those suites that have no bound of their own bounded, so a real regression still fails instead of hanging. Wrap `delivery.waitUntilFinished()`, `passDeadline`'s `await task?.value`, and `drainMainQueue()` in `awaitBounded` (`AwaitBounded.swift`) and `#expect` its result. Also `#expect(await clock.waitForSleepers(1))` instead of discarding the Bool, so a missed registration fails at that line rather than as an unattributed timeout. Do the same for the unbounded awaits in the `ProjectXPCTests` suite.
3. If a suite-wide backstop is still wanted, make it clearly larger than the hang guard plus observed queueing (for example `.timeLimit(.minutes(5))`), so it can only ever catch a true hang that a per-await guard missed.

Out of scope here, though worth a separate issue if it recurs: find which test blocks the main thread for about 22 s while creating real renderers, and why trivial `@MainActor` tests queue for 10–70 s in a full run.

## Acceptance criteria

- No `.timeLimit` trait in `BattyKit/Tests/` is at or below `TestBounds.hangGuard` (`grep -rn timeLimit BattyKit/Tests`).
- Every `await` in `ProjectStartupTests.swift` and `ProjectXPCTests.swift` is either itself bounded by `TestBounds.hangGuard` (through `awaitBounded`, `waitForSleepers`, or an equivalent) with its result asserted, or provably returns synchronously. No sleeps, polling or timing assertions are added.
- `./build.sh unit` passes, and `./build.sh unit ProjectStartupReadinessTests` and `./build.sh unit ProjectXPCTests` pass on their own.
