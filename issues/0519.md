# 0519 — The VM runner's log capture cannot support the `docs/view-hierarchy.md` §6 signal audit: debug lines are never stored, early info lines are evicted, and the libghostty PTY-spawn line is outside the predicate

| **Module** | Testing |
| **Platform** | macOS |
| **First seen** | 2026-10-16 |

## Description

The #0240 multi-window regression pass was meant to check the `docs/view-hierarchy.md` §6 "Common debugging signals" per window, from the VM run's logs. For example: `created terminal view` exactly once per tab, `released terminal view` exactly once per closed tab, `created host` / `released host` once per content window, no `io_exec: started subcommand` outside tab creation. The logs the runner keeps cannot answer those questions.

`tools/run-ui-tests-vm.sh` collects the app's log once, after the test step finishes (lines 604–608):

```
log show --last 30m --info --debug --style compact \
  --predicate 'subsystem BEGINSWITH "co.sstools.Batty"' > guest-state/app-info.log
```

It has three gaps.

1. **Debug lines are never stored on the guest.** Passing `--debug` to `log show` only displays debug entries that are already in the store. The guest never turns on debug persistence for the app subsystem (no `log config` anywhere in `tools/`). Most of the §6 signals are logged at `.debug` (`BattyKit/Sources/BattyKit/Runtime/TerminalHostStore.swift`):
   - `created host for window` (line 126)
   - `released host for window` (line 146)
   - `created terminal view for tab` (line 185)
   - `released terminal view for tab` (line 292)
   - the `AppTerminalView ... still referenced` probe (line 334)
   - `focus skipped` (`TerminalSurfaceFocuser.swift:98`)

   Both #0240 runs' `app-info.log` files contain **zero** debug-level lines, and zero `created terminal view` / `released terminal view` lines. Only `attached host to window` (`TerminalHostView.swift:73`, `.info`) and the `TabRuntime ... still referenced` notice (`.notice`) appear.
2. **The capture misses the start of the run.** The window is a fixed `--last 30m` taken at the end, and info-level entries live only in the in-memory buffer, which evicts them.
   - Run `20261016-181007-64163`: tests started at 01:12:15 and ran to about 01:52. Default-level lines begin at 01:22:56, cut off by the 30-minute window. Info-level lines begin only at 01:39:22.
   - Run `20261016-185336-94049`, a 10-minute run: tests started at 01:55:25, but info-level lines begin at 01:58:15.

   So even the `.info` `attached host to window` count is truncated for most of each run.
3. **The PTY-spawn signal is outside the predicate.** libghostty's `io_exec: started subcommand` comes from libghostty's own logging, not from a `co.sstools.Batty*` subsystem. `libghostty.a` carries the `com.mitchellh.ghostty` identifier. So `subsystem BEGINSWITH "co.sstools.Batty"` never matches it. Both runs' `app-info.log` contain zero `io_exec` / `started subcommand` lines. The implementer should confirm the exact subsystem/category libghostty uses on the guest before writing the predicate.

The opt-in `BATTY_UI_FULL_APP_LOG=1` capture (`process == "Batty Beta"`, lines 613–619) has the same `--last 30m` window and the same lack of debug persistence.

## Expected behavior

A VM run keeps enough of the app's log to audit every §6 signal for the whole run, per app process and per window:

- debug-level `co.sstools.Batty*` lines;
- info-level lines from the first launch onward;
- the libghostty PTY-spawn line.

A checker reports violations of the §6 expectations.

## Actual behavior

Debug lines are absent, info lines are truncated to roughly the last 10–15 minutes, and the libghostty line is filtered out. The §6 audit for #0240 could not be done from run artifacts.

## Notes

Directions to evaluate (not conclusions):

- **Persist debug on the guest.** Before the test step, enable persistence for the app subsystem on the guest, e.g. `sudo log config --subsystem co.sstools.Batty.beta --mode "level:debug,persist:debug"`, and the same for libghostty's subsystem once confirmed. Reset it afterward, or rely on the clone being disposable. The guest is a throwaway clone, so this does not touch the golden image (AGENTS.md forbids that).
- **Collect the whole run.** Record the guest's start timestamp before the test step and use `log show --start "<ts>"` instead of `--last 30m`. Alternatively, run `log stream --level debug` on the guest for the duration of the test step and write it to a file in `$GUEST_RESULTS`. Bound it the same way as every other guest step.
- **Widen the predicate** to include libghostty's subsystem (or `process == "Batty Beta" AND (subsystem BEGINSWITH "co.sstools.Batty" OR subsystem == "<ghostty subsystem>")`), so the file stays small.
- **Add a checker** (e.g. `tools/check-view-hierarchy-signals.sh` or a small script) that groups lines by app PID and window/tab UUID and flags:
  - a tab with more than one `created terminal view`;
  - a released tab with no `released terminal view`, or more than one;
  - a window with more than one `attached host to window` or `created host`;
  - a `created host` with no matching `released host` when the window closed;
  - `io_exec: started subcommand` lines beyond the number of tabs created;
  - repeated `TabRuntime ... still referenced` notices (see #0520).

  The runner can run it at the end and write a summary next to `app-warnings.log`.

Keep `app-info.log` bounded in size. The full-process log is opt-in because it runs to hundreds of thousands of lines (#0444).

## Acceptance criterion

A VM run of `MultiWindowTests` plus `MultiWindowCLITests` on `main` produces:

- a log artifact with `created terminal view`, `released terminal view`, `created host`, `released host` and `attached host to window` lines from the run's first launch onward;
- libghostty `started subcommand` lines;
- a checker summary that reports the §6 expectations per window, passing on a clean run.

`docs/ui-testing-vm.md` documents the new artifacts and the checker.
