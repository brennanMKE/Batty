# 0642 — `TestClockTests/waitForSleepersWorksForALowerPrioritySleeper` fails under heavy host load because its `.background` task can starve past the hang guard

| | |
|---|---|
| **Status** | open |
| **Module** | Testing |
| **Platform** | macOS |
| **First seen** | 2026-11-15 |
| **Priority** | medium |

## Description

`TestClockTests/waitForSleepersWorksForALowerPrioritySleeper` (`BattyKit/Tests/BattyKitTests/TestClockTests.swift:128-138`) fails in full `./build.sh unit` runs when the host is heavily loaded, and passes on rerun. It failed in two separate full runs on 2026-11-15 during the #0636 reviews, at a load average of about 88, and passed on the immediate rerun both times (`issues/0636.md`, `## Verification`: "failed again under load, the second time in two reviews of this branch"). It also failed on 2026-11-09 with the message "waitForSleepers(1) never reached its threshold" (`unit-20261109-003236-29450.log`, recorded in `issues/0569.md` `## Verification`). That is the message `requireSleepers` records when `TestClock.waitForSleepers(1)` returns false, which means the 60 s hang guard expired before the sleeper registered.

The test does not wait for time in the way `AGENTS.md` "Asynchronous tests (binding)" forbids. Its success depends on something close to it, though: the scheduler must start a `.background` task within a fixed wall-clock bound. On macOS, background QoS is the one priority the system throttles on purpose. Under contention it may run only on efficiency cores, or not at all for long stretches. So the hang guard, which should only ever catch a regression, is what decides the outcome on a loaded host. By `docs/async-test-seams.md` §4, an expiry that survives at `TestBounds.hangGuard` is "a signal bug to root-cause, not a reason to go higher".

## The test

```swift
@Test func waitForSleepersWorksForALowerPrioritySleeper() async {
    let clock = TestClock()
    let task = Task(priority: .background) {
        await clock.sleep(for: .seconds(1))
    }
    guard await requireSleepers(1, on: clock, cancelling: [task]) else { return }
    #expect(clock.pendingCount == 1)

    await clock.advance(by: .seconds(1))
    await task.value // completing is the "fired" signal
}
```

- `requireSleepers` (`:52-64`) awaits `clock.waitForSleepers(1)`, with `bound` defaulting to `TestBounds.hangGuard` (60 s, `TestBounds.swift:26`).
- `waitForSleepers` (`TestClock.swift`) is a real event: it resumes under the lock from inside `register(id:duration:continuation:)` the instant the threshold is met. Its timeout is a `DispatchWorkItem` on `DispatchQueue.global(qos: .utility).asyncAfter(deadline: .now() + bound)`, a higher QoS than the sleeper's task.
- The sleeper registers only once the `.background` task first runs and reaches `withCheckedContinuation`. The test has no other dependency on scheduling order.

## Is it compliant with the async-test rules?

- **In form, yes.** There is no `Task.sleep`, polling or elapsed-time assertion on the success path. The test awaits a completion signal (`waitForSleepers`, then `task.value`), the bound is a hang guard, and a failed wait cancels the task and returns instead of hanging (`requireSleepers` follows §4's "never continue past a failed readiness wait").
- **In effect, no.** Whether the test passes depends on how fast the scheduler starts a deliberately throttled QoS class, measured against wall-clock time. That breaks the rule's intent that the bound is "a failure guard, never the mechanism the test relies on". It also contradicts the claim in `docs/async-test-seams.md` (around lines 70-85) and in `TestClock`'s doc comment that `waitForSleepers` "works regardless of priority". The *clock* is priority-independent, but this test of it is not: its timeout runs at `.utility`, while the work it waits for runs at `.background`.
- `Task(priority: .background)` appears nowhere else in `BattyKit/Tests` (`grep -rn "priority: .background" BattyKit/Tests`), so this is the only test with this exposure.

## Expected behavior

The test checks what it was written to check, that `waitForSleepers` is a real registration event with no reliance on relative scheduling between priorities. It passes on a loaded host whenever `TestClock` is correct, and fails only when `TestClock` regresses.

## Actual behavior

At a load average of about 88, the `.background` task does not reach `register` within 60 s. `waitForSleepers` returns false, `requireSleepers` records "waitForSleepers(1) never reached its threshold", and the test fails. On the rerun it passes.

## Notes

- **Candidate fixes, for the planner.** (a) Run the sleeper at `.low` or `.utility`. Both are still lower than the test's own priority, so the "lower-priority sleeper" property stays covered, but the system does not throttle them the way it throttles `.background`. (b) Keep `.background`, and instead prove the property structurally: start the task, then make the test depend only on the registration event, for example by awaiting a signal the task sends just before it calls `sleep(for:)` with no bound below the hang guard. That still leaves the starvation exposure, so (a) is probably the smaller and more honest change. Raising `TestBounds.hangGuard` is not a fix (`docs/async-test-seams.md` §4). Whichever is chosen, update the doc claim "works regardless of priority" to match what the test actually shows.
- **Other failures in the same runs.** In the second 2026-11-15 run, 24 tests hit hang-guard timeouts in suites that the #0636 diff did not touch, including `GitStatusPaneContentTests`, `SharedProjectImagesTests`, `LMStudioDashboardPaneContentTests` and `PendingTeardownReapRegistryTests`. The full rerun passed (4146 tests). That pattern looks like #0443's MainActor queueing under extreme load rather than separate bugs. It is out of scope here. If it recurs at a normal load, it needs its own issue with run ids.
- **`ProcessFollowByNameTests/theRealEnumeratorFindsAUniquelyNamedProcessAndItsReplacement`** (`ProcessFollowByNameTests.swift:723`) also failed once under load on 2026-11-15 and passed alone. It goes through `ProcessInspector.firstSameUserProcess(named:)`, which inherits the `allPids()` truncation in #0516 when many processes start between the probe and the fill, as they do during a loaded parallel test run. It is tracked by #0516 and not duplicated here.
- The 2026-11-15 run logs were in the #0636 worktree, which was removed after the merge, so no run ids for them are recorded here. Per `issues/Issues.md` "Known flaky tests", add the test to that list once two run ids are captured.
- Verification for the fix: the fast tier, plus a filtered `./build.sh unit TestClockTests` run. Since the failure needs heavy load, the planner should also say how to reproduce it on purpose (for example under a deliberate CPU-load run like #0443's "Work notes" diagnostic) and show the fixed test passing under the same load.
