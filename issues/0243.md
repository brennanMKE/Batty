# 0243 — Changing the global theme does not re-theme terminal panes in any window

## Description

Multi-window regression: picking a new theme in the (global) theme selector no longer changes the terminal pane colors — not in the current active window, and not in the other open window. The selection appears to take (UserDefaults is written) but the live surfaces are not recolored.

## Steps to reproduce

1. Open two windows (Shift-Cmd-N).
2. Open the theme selector (Cmd-T) in the key window and pick a different theme.

## Expected behavior

Every window's terminal panes that follow the global theme immediately recolor to the chosen theme.

## Actual behavior

Neither window's terminal panes change color.

## Notes

- Root cause is the `windows[0]`-only forwarding shim. `AppStateStore.applyThemeToAllSurfaces(_:)` (the global-theme path used by `ThemeSelectorView.selectTheme`) iterates `self.sessions`, and `AppStateStore.sessions` is defined as `windows[0].sessions` (`AppStateStore.swift:200`). So only the first window's surfaces are ever re-themed. When the key window is the second window (the common case right after Shift-Cmd-N, and the picker now opens only in the key window per #0242), the surfaces the user is looking at are never touched, so it reads as "nothing changed."
- `applyGlobalThemeForCurrentAppearance()` (system Light/Dark switch) routes through the same `applyThemeToAllSurfaces`, so appearance-driven re-theming has the same one-window limitation.
- The per-session apply path (`applyTheme(_:to:)`, used by `SessionThemeSelectorView` and by `SessionDetailView`'s `applyActiveSessionTheme(for:)` on session switch) is *not* affected — it operates on the session passed in.
- `themeChrome` is a single app-wide instance shared by every `RootWindowView`, and per-window themes are out of scope (`docs/multi-window-design.md` §10), so the fix is purely to fan the surface `setTheme` calls across all windows' sessions.
- Same regression class as #0240 (Phase 7) and #0242; once #0240's UI suite can run, add multi-window coverage asserting a global theme change recolors surfaces in every window.

## Root cause

`AppStateStore.applyThemeToAllSurfaces(_:)` — the global-theme path invoked by `ThemeSelectorView.selectTheme`/`moveSelection` and by `applyGlobalThemeForCurrentAppearance()` — iterated `self.sessions`. After the #0235 multi-window refactor, `AppStateStore.sessions` is a forwarding shim defined as `windows[0].sessions` (`AppStateStore.swift:200`), so only the first window's surfaces were ever re-themed. With two windows open and the picker now opening only in the key window (#0242), the key window is commonly the *second* window, whose surfaces were never touched — so the change appeared to do nothing in the window the user was looking at.

## Fix

Apply the global theme across every window's sessions: iterate `windows.flatMap { $0.sessions }.filter { $0.localThemeName == nil }` instead of the `windows[0]`-only `sessions` shim, then `setTheme` on each tab's controller. The shared `themeChrome` update is unchanged — `themeChrome` is a single app-wide instance and per-window themes are explicitly out of scope (`docs/multi-window-design.md` §10), so the global theme is app-wide by design. The per-session path (`applyTheme(_:to:)`) was already correct and is untouched.

## Verification

`scripts/build.sh unit` — build succeeded; **337 unit tests in 40 suites passed**, including the new `CrossWindowBehaviorTests.applyThemeToAllSurfacesRethemesEveryWindow()`. That test opens a second window, applies two distinct catalog themes via `applyThemeToAllSurfaces`, and asserts every tab's `controller.theme` in *both* windows matches — it fails against the pre-fix `windows[0]`-only loop (the second window's controllers keep their initial theme) and passes after the fix. `TerminalController.setTheme` records `controller.theme` even without a live render surface (the surface/app config pushes are guarded out), which is what makes this observable in a unit test.

## Files changed

- `BattyKit/Sources/BattyKit/Theme/ThemePreference.swift` — `applyThemeToAllSurfaces` now iterates all windows' sessions rather than the `windows[0]` shim.
- `BattyKit/Tests/BattyKitTests/CrossWindowBehaviorTests.swift` — added `applyThemeToAllSurfacesRethemesEveryWindow()` regression test.

## Gotchas

- The fix is verified behaviorally by a unit test, but a final visual confirmation is still worth a glance when the app is next run: open two windows, change the global theme, and confirm both windows' terminal panes recolor. Marked `resolved`, not `closed`.
- The `themeChrome` chrome update inside `applyThemeToAllSurfaces` still keys off `selectedSession` (= `windows[0]`'s selected session). That is acceptable today because chrome is a single app-wide instance and per-window themes are out of scope; if per-window theming is ever added (currently §10 out-of-scope), the chrome ownership and this condition must move per-window too.
