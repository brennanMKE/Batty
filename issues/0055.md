# 0055 — Workspace restoration on launch is not normal terminal-app behavior

| | |
|---|---|
| **Status** | open |
| **Module** | Persistence / App |
| **Platform** | macOS |
| **First seen** | 2026-05-11 |

## Description

When Batty launches, it reads `workspace.json` and rebuilds every session, pane, split, and tab from the previous run. That means relaunching after a quit restores a window full of dead shells with stale prompts, last-login banners that don't match the current session, and (for any tab that had a running process at quit time) an empty post-mortem state where the shell has restarted but the user's mental context for what was in that tab is gone.

This is not the convention for terminal apps:

- **macOS Terminal.app** opens a single fresh window with a single fresh shell on launch.
- **iTerm2** opens a single fresh window unless the user has explicitly enabled "Restore window arrangement" (off by default).
- **Ghostty** opens a single fresh window on launch.
- **Alacritty / kitty / wezterm** open a fresh window on launch.

Auto-restoration makes sense for editor / browser / IDE apps where document state is the user's work product. For a terminal app, the "documents" are running shell processes — they can't actually be restored (the PTYs are gone), and the visual rebuild only mimics the surface appearance of what was there. The result is a relaunch that *looks* like the previous run but isn't.

## Steps to reproduce

1. Open Batty. Open several sessions, create splits and tabs, type some commands.
2. Quit Batty (`Cmd-Q`).
3. Relaunch Batty. **Observed:** every session, pane, and tab is restored, each with a freshly-spawned shell. The user is staring at a layout they no longer wanted, full of empty-shell prompts.
4. **Expected (matching platform convention):** a single window with a single fresh session, one pane, one tab, one shell prompt. Just like Terminal.app.

## Expected behavior

On launch:

- Open a single fresh window with a single session, a single pane, a single tab, a single shell prompt.
- Do **not** rehydrate the prior layout by default.

If a user wants to revisit a previous layout, they can use existing tools: `Cmd-Z` won't help (closed-window restoration is its own feature), but a future "Reopen Last Session" command or even just `workspace.json` left on disk for the curious is fine.

If we want to be conservative we can keep `workspace.json` writes happening (cheap, no user-visible effect) and only stop *reading* it on launch. That preserves the option to add an explicit "Restore Previous Layout" menu item later without retooling the persistence layer. Alternatively, gate read on a Settings toggle ("Restore previous layout on launch") that defaults to **off**.

## Actual behavior

`WorkspaceManager` (in `BattyKit/Sources/BattyKit/WorkspaceManager.swift`) loads `workspace.json` from Application Support on init and feeds it into `AppStateStore` to rebuild the session list. This was deliberate from the milestone-7 persistence work (`#0036` / `#0042` family), where workspace-restoration was treated as a v1 feature. It pre-dates the realization that the workspace-restoration pattern is wrong for terminal apps specifically.

## Notes

- `workspace.json` writes happen on a 30s timer and at `applicationWillTerminate`. Those can stay; the bug is the **read**, not the write.
- Quickest fix: in `WorkspaceManager`, bypass the load step (or short-circuit it behind an off-by-default `UserDefaults` toggle), and start with a fresh `AppStateStore()`. The `AppStateStore()` no-arg init already creates a single default session — that's the desired launch state.
- A Settings toggle ("Restore previous layout on launch") is the right v2 escape hatch. v1 can just turn the read off; we add the toggle when someone asks.
- If we keep writes, decide what to do with the file when the user has the feature off: leaving it untouched is fine; the file just accumulates as a record of the most-recent quit-time state. Trimming or deleting it adds complexity for no win.
- Bell-feed persistence is a separate axis. Currently bell-feed entries are part of the workspace and so also get restored. Decide whether to keep restoring the *bell feed* even when not restoring the *layout*. Probably no — the bell feed is meaningless without the surfaces it references. v1: drop the whole `workspace.json` read; everything resets.
- **Don't delete `WorkspaceManager` / `WorkspaceStore` / the persistence model.** The plumbing is correct and there's value in keeping the write path alive (cheap diagnostic snapshot, easy to re-enable). Just stop reading on launch.
- The Concepts.md "Workspace" entry mentions persistence as a v1 feature. Update it to clarify that workspace persistence is a write-only diagnostic by default, with optional layout-restore behind a setting.

## Acceptance criteria

- Quit-and-relaunch produces a single window with one fresh session, one pane, one tab. Matches Terminal.app / Ghostty / iTerm2 (default).
- `workspace.json` writes continue (or are removed entirely — either is fine for v1, but removing is more drastic). No regression in the bell-feed write path if that's coupled.
- If a Settings toggle is added, it defaults to **off**.
- No console errors or empty-state crashes when `workspace.json` exists from a prior run but isn't being read.
- Existing persistence-layer unit tests still pass (they exercise the write/load layer, not the launch read decision).

## Out of scope

- Building the "Reopen Closed Tab / Closed Session" feature.
- Removing the persistence layer wholesale.
- Adding the Settings UI for an opt-in restore (defer until needed; v1 just turns off the default behavior).
- Migrating any existing user's `workspace.json` (the file is harmless on disk; no migration needed).
