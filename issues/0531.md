## Description

Implementers and reviewers run `./build.sh`, `./build.sh unit` and `./build.sh ui-typecheck`, and all xcodebuild output streams to the terminal and into the agent's context. Issues.md then tells them to "read the output, don't just check the exit code". In the user's experiment, implementer test runs plus log reads made up about 40% of implementer tool calls. Almost all of that output is noise on success, and on failure the useful part is a few lines.

User direction (2026-10-19, verbatim):

> "Instead of reading the full log we should have the script capture the result which should return with an exit code which indicates success or failure. The last few lines should also have text in all caps indicating success or failure. When it is a success we don't have any further log analysis to do. When it fails tests we need to grep just the lines which have the warnings or errors and pass those to Haiku for summary. This would be feedback to the implementer."

> "Make this change. We should also consider how we handle the build log. We also do not need the full log going into the context. On success we can just pass it through. For failures we can also grep out relevant lines. Revise the build script to do this as well."

**Goal:** keep build and test logs out of agent context. The implementer acts on the exit code, an ALL-CAPS result line, and a short failure digest summarized by Haiku.

Related: #0528 (verification-tier tooling: fast/slow unit split, VM build-only and sharding). The two touch the same `build.sh` cases and the same Issues.md sections. Whichever lands second adopts the other's conventions.

## Current state (verified 2026-10-19 on `main` at `e7d47641`)

- **`build.sh`** (`zsh`, `set -euo pipefail`):
  - `ui-typecheck` is dispatched *before* the `Active.xcconfig` snapshot and `EXIT` trap, on purpose, so that it never rewrites `Active.xcconfig`. It runs `xcrun swiftc -typecheck`, not xcodebuild, so it produces no `.xcresult` and no test counts. Its digest can only come from grep (`error:` / `warning:`).
  - The `Active.xcconfig` restore lives in the `EXIT` trap (`restore_active_xcconfig`), which captures `$?` and re-`exit`s with it. Any new summary or digest step must not clobber that status, and must not break the restore on Ctrl-C or failure.
  - `unit` runs `xcodebuild test … -only-testing:BattyKitTests`, with no `-resultBundlePath` and **no way to pass a test filter**. The "zero-tests filter" acceptance case below needs a filter argument (e.g. `./build.sh unit <Suite/test>`). #0528 may add one too, so coordinate.
  - A plain `./build.sh` has no `build` case. `ACTION` defaults to `build` and falls into the `*)` passthrough, which runs `xcodebuild` with the remaining args. With no args that is xcodebuild's implicit build. Capturing build output means giving `build` its own case, or teaching the passthrough to capture.
  - `ui`/`test` `exec` `tools/run-ui-tests-vm.sh`, and `package` `exec`s `scripts/build-beta.sh`. `scripts/` is a restricted area (AGENTS.md), so `package` and `release` should stay pass-through unless the user approves otherwise.
- **`tools/run-ui-tests-vm.sh`** already ends with `==> RESULT: TEST SUCCEEDED` / `==> RESULT: TEST FAILED (exit N)`, followed by a `grep … | tail -20` of the test log, a crash-report count, a warnings count, and the result-bundle and log paths. It exits with the xcodebuild status. Precondition failures go through `fail()` → `exit 1`, which can't be told apart from a test failure.
- **`tools/worklog.py`** times only VM runs (`VM_COMMAND`, matched to a result containing `==> RESULT:` or `Executed N tests` via `VM_SUMMARY`). Rows have one `VM` column. Builds and unit runs aren't measured. A `claude -p` call made from inside `build.sh` never appears in the subagent transcript, so its cost has to come from a file the script writes.
- **`issues/Issues.md`** Phase 2 step 5 says "Read the output, don't just check the exit code", and "Verification tiers" says to quote the unit `Test run with N tests … passed` line. Both assume the agent reads the full log.

## Proposed design (user-approved; the plan settles the open details)

1. **Captured output, short tail.** For `build`, `unit` and `ui-typecheck`, `build.sh` writes the full tool output to `build/checks/<stage>-<timestamp>.log` (`build/` is already gitignored), not the terminal. It ends with about 5 lines or fewer: stage, counts (tests run / failed; compile errors), duration, log path, and a final ALL-CAPS line:
   - `CHECK UNIT: PASSED`
   - `CHECK UNIT: FAILED (3 tests, 1 compile error)`
   - `CHECK UNIT: ERROR (no tests ran)`

   Exit codes: **0** pass, **1** build or test failure, **2** could not run (zero tests ran, no test summary, missing tool). An opt-out (`--verbose` or an env var such as `BATTY_CHECK_VERBOSE=1`) streams the full log for humans. `Active.xcconfig` restore must keep working on every exit path. `ui-typecheck` must still never touch it. Whether `release`, `package`, `run` and arbitrary passthrough actions capture is for the plan to decide. Default: leave them streaming.
2. **Failure digest, on failure only.** Write `<log>.failures.txt`:
   - test failures from the result bundle (`-resultBundlePath`, `xcrun xcresulttool get test-results tests`), checked against Swift Testing output, since BattyKitTests uses `import Testing`;
   - compile errors via grep (`error:`, `** BUILD FAILED **`, `** TEST FAILED **`);
   - `warning:` lines only for files changed vs `main` (`git diff --name-only main...HEAD` plus the working tree).

   Dedupe, cap at about 60 lines, and print the digest (or the Haiku summary) instead of the log.
3. **Haiku summary (option A, default).** On failure, pipe the digest to `claude -p --model haiku --output-format json` with a fixed prompt: for each failure, the test or `file:line`, the likely cause in one line, and the evidence. Print the summary. Append Haiku's cost and usage, with stage, timestamp and log path, to `build/checks/haiku-usage.jsonl`. **Degrade gracefully:** when `claude` is missing, unauthenticated, times out, or fails, print the raw digest, and leave the exit code unchanged. An env var (e.g. `BATTY_CHECK_SUMMARY=0`) disables it, so the experiment can compare against **option B**: the orchestrator dispatches a Haiku subagent that runs the checks and relays its summary to a fresh implementer.
4. **VM runner.** `tools/run-ui-tests-vm.sh` adopts the same final ALL-CAPS line (e.g. `CHECK UI: PASSED` / `FAILED (N tests)` / `ERROR (<precondition>)`), exit 2 for precondition failures, and the same digest from `UITests.xcresult`. The plan decides how far to go. Keep `==> RESULT:` (or update `worklog.py`'s `VM_SUMMARY` in the same change), so VM timing doesn't silently stop matching.
5. **`tools/worklog.py`.** Time `./build.sh` (build), `unit` and `ui-typecheck` calls by stage, the same way as VM runs (tool_use to tool_result, background-aware). Count Haiku summaries and sum their cost from `haiku-usage.jsonl` within the transcript's time window, then fold that into the row cost or a separate column. Add Build / Unit / UI columns, and update the work-log table header in Issues.md to match.
6. **Issues.md.** Rewrite Phase 2 step 5, Phase 3 step 3 and "Verification tiers". Agents read only the tail, the result line and the digest, never the full log. "Zero tests ran" is now exit 2 and `CHECK …: ERROR`, so the script enforces "compilation is not verification" instead of the reader. `## Verification` quotes the ALL-CAPS line, the counts line and the log path. New tests are confirmed by name with a filtered run or from the `.xcresult`, not by reading the log. Also document the opt-out switches.

## Acceptance

A verification subagent, working in a scratch worktree, exercises each case and confirms the exit code, the result line, the digest size (≤ ~60 lines), and that **no full log reaches stdout**:

- [ ] passing `./build.sh` → exit 0, `CHECK BUILD: PASSED`
- [ ] injected compile error → exit 1, `CHECK BUILD: FAILED (…compile error…)`, digest names the `file:line`
- [ ] passing `./build.sh unit` → exit 0, `CHECK UNIT: PASSED` with the test count
- [ ] injected failing unit test → exit 1, digest names the test and its assertion
- [ ] unit filter that matches zero tests → exit 2, `CHECK UNIT: ERROR (no tests ran)`
- [ ] `ui-typecheck` pass and fail, and `Active.xcconfig` untouched (mtime unchanged)
- [ ] Haiku unavailable (`claude` not on `PATH`, or `BATTY_CHECK_SUMMARY=0`) → raw digest printed, exit code unchanged
- [ ] Haiku available → summary printed, one line appended to `build/checks/haiku-usage.jsonl`
- [ ] `--verbose` streams the full log
- [ ] `Active.xcconfig` restored after a failure and after Ctrl-C
- [ ] `tools/worklog.py` on a transcript containing these runs reports Build / Unit / UI time and Haiku count/cost

## Review notes

Round 2 review, 2026-10-19 (Opus, medium). **Bounced.** The reviewer's runs matched the draft: `./build.sh` exited 0 with `CHECK BUILD: PASSED`. `./build.sh unit` exited 0 with `CHECK UNIT: PASSED (2588 tests)` (`build/checks/unit-20261019-144221-68072.log`). An injected failing Swift Testing test exited 1 with `FAILED (1 test, 0 compile errors)` and a digest naming the test, its assertion and its `file:line`. An injected compile error exited 1 with `FAILED (1 compile error)`, a one-bullet Haiku summary and one `haiku-usage.jsonl` line. `Active.xcconfig` (Prod) was restored after every run. Three defects block resolution.

1. **`tools/check-report.py` `classify()`: a passing run can still report FAILED.** Grep-counted "compile errors" override a clean tool result. Unit logs contain about 9 to 128 runtime `…, error: Error Domain=…` / `Underlying error: …` lines from the xctest process, and interleaved writers split them at arbitrary points. The round-2 `OTHER_ERROR_NOISE` exclusion catches only the one split that happened (`error: Error Domain=`). Reproduced offline: the passing log `unit-20261019-144221-68072.log` plus one appended line `error: The data couldn't be read because it isn't in the correct format.`, run with `--rc 0` and its passing `.xcresult` (2588 passed), gives `CHECK UNIT: FAILED (0 tests, 1 compile error)` and exit 1. **Required:** the tool's exit status and structured results decide the outcome, not the log regex. For `unit`/`ui`: `rc == 0` with xcresult `total > 0` and `failed == 0` is PASSED, whatever the log grep finds. For `build`/`ui-typecheck`: `rc == 0` is PASSED. Grep-derived errors only label and populate the digest when `rc != 0`. xcodebuild and swiftc cannot exit 0 after a compile error. The `rc != 0` cases must never yield PASSED, as now. Also, a `unit` run whose build failed with no recognised error line (`rc != 0`, `total == 0`, `** BUILD FAILED **` / `The following build commands failed:` present) should be FAILED (exit 1), not `ERROR (no tests ran)`. Then drop `OTHER_ERROR_NOISE`, or keep it only for the digest. The Gotchas line saying the regex "must stay anchored or passing runs turn FAILED" should no longer be true. Satisfied when the offline repro above gives `PASSED (2588 tests)`, exit 0.
2. **`tools/worklog.py`: `./build.sh ui-typecheck` is classified as a VM run.** `VM_COMMAND`'s `build\.sh ui)\b` matches `build.sh ui-typecheck`, because `\b` falls between `ui` and `-`. It is tested before `check_stage`, so a foreground ui-typecheck run is dropped from Build (its `CHECK UI-TYPECHECK` line doesn't match `VM_SUMMARY`), and a background one is counted under UI. Check: `VM_COMMAND.search("cd /x && ./build.sh ui-typecheck")` is truthy. On the round-1 implementer transcript `agent-ab360bf662e68edb1.jsonl`, the row shows `UI 1 (0.4m)` although that session ran no VM. **Required:** make `build.sh ui` match only the `ui` action (e.g. `build\.sh ui(?=\s|$|[;&|)])`), so ui-typecheck reaches `check_stage` and lands in Build. Satisfied when that transcript reports UI `—` and the ui-typecheck run is in Build.
3. **`tools/run-ui-tests-vm.sh` header and `docs/ui-testing-vm.md` say the last line is "always" `CHECK UI: …`.** That is false for `set -e` aborts that bypass `fail()`: `tart-golden require` (before the trap), `git archive`, `tart-lease acquire` and `tart clone`. These exit non-zero with no CHECK line. **Required:** either have `cleanup()` print `CHECK UI: ERROR (exit $rc)` when `CHECK_LINE` is empty and `rc != 0`, and exit 2 for those paths so the 0/1/2 contract holds, or narrow the "always" wording in both places. The first is preferred.

Not blocking: `==> RESULT:` is kept, so `VM_SUMMARY` still matches. The Haiku call sends only the capped digest, from a temp cwd with tools disabled, never changes the exit code, and `BATTY_CHECK_SUMMARY=0` disables it. The Issues.md Work log header matches the 15-column row worklog.py prints.

## Resolution notes

> 🟢 Resolved 2026-10-19 — `./build.sh` (build), `unit` and `ui-typecheck` capture their output to `build/checks/`, print a short tail ending in an ALL-CAPS `CHECK <STAGE>:` line with exit 0/1/2 decided by exit status and `.xcresult` counts, and on failure print a Haiku-summarized digest; the VM runner ends with the same `CHECK UI:` line.

Non-blocking follow-ups for the orchestrator to file (found in round 3 review):

1. **`tools/worklog.py` misses plain builds run with a redirect.** `CHECK_COMMAND` accepts a bare `./build.sh` only when it is followed by end, `;&|\n)`, so `./build.sh 2>&1 | tail -4` (the usual agent form) matches nothing: `command_stages("./build.sh 2>&1 | tail -4")` is `set()`. On `agent-acff7f3c6ca830997.jsonl` (round-3 implementer) the row shows Build `—` although it ran two plain builds. `./build.sh unit 2>&1 | tail` is counted. Fix: allow redirections (`\s+\d*>&?\S+`) after `build.sh` and its `--verbose`.
2. **`tools/worklog.py` `VM_COMMAND` matches lines inside heredocs.** The `\n` alternative lets any heredoc line that contains a runner path count as a VM command. On the same transcript a `python3 - <<'EOF'` edit of `worklog.py` itself was counted as `UI 1 (0.0m)`, because its printed output matched `VM_SUMMARY`. Rare (it needs a heredoc mentioning the runner plus matching output), but it inflates UI counts.

## Root cause

Feature work. `build.sh` streamed every xcodebuild/swiftc line to the terminal, had no result line and no digest, and `unit` had no filter and exited 0 when zero tests ran. Its `EXIT`-trap restore of `Active.xcconfig` also did not run on Ctrl-C (zsh skips `EXIT` traps on uncaught signals).

## Fix

Implemented as planned:

- New `tools/check-report.py` classifies a captured log (plus `.xcresult` for unit/ui), prints a ≤ 4-line tail ending `CHECK <STAGE>: PASSED|FAILED|ERROR (…)`, exits 0/1/2, writes `<log>.failures.txt`, and on FAILED summarizes the digest with `claude -p --model haiku` (degrades to the raw digest; records usage in the main checkout's `build/checks/haiku-usage.jsonl`). Prunes to the newest 10 runs per stage.
- `build.sh`: `--verbose`/`BATTY_CHECK_VERBOSE`, `run_check` helper, new `build)` case, `unit [Suite[/test()] …]` filters with `-resultBundlePath`, `ui-typecheck` captured (still before the xcconfig snapshot), INT/TERM/HUP traps.
- `tools/run-ui-tests-vm.sh`: preconditions exit 2 with `CHECK UI: ERROR (…)`; `grep | tail -20` replaced by the check-report digest; final `CHECK UI:` line printed last from `cleanup()`; `==> RESULT:` kept.
- `tools/worklog.py`: Build/Unit/UI timing, Haiku join and cost, 15-column row, `total_cost`.
- Docs: Issues.md (Phase 2 steps 4–5, Phase 3 step 3, Verification tiers, Daily UI run, Measuring, Work log header), AGENTS.md, docs/ui-testing-vm.md.

Deviations: non-located error lines are matched only when the line starts with `error:` or a tool prefix (`ld:`, `xcodebuild:`, `clang:` …), not anywhere after whitespace — the plan's looser regex counted 8 runtime `os_log` lines (`…, error: Error Domain=…`) in a passing unit log as compile errors. The ERROR fallback digest skips indented xcodebuild env-dump lines and, for `no tests ran`, leads with an explanatory line. Scenario 2's path in the plan is wrong: `Logging.swift` lives at `BattyKit/Sources/BattyKit/Util/Logging.swift`.

Round 2 (acceptance-verifier defects D1–D5):

- D1: `LOCATED_ERROR`/`LOCATED_WARNING` accept repo-relative paths, which is what `swiftc` prints when `ui-typecheck` invokes it directly. Changed-file matching handles both forms.
- D2: `build.sh`'s HUP/INT/TERM traps now call `on_signal`, defined before the `ui-typecheck` block. While `run_check` owns a stage (`CHECK_STAGE`), `on_signal` prints `CHECK <STAGE>: ERROR (interrupted)` and then exits 129/130/143, so the `Active.xcconfig` restore still runs. `ui-typecheck` gets the same traps.
- D3: the digest drops the `Building workspace …` and `(N failures)` framing. It includes the `The following build commands failed:` list only when no error line was found, as with linker or signing failures. Otherwise the list just repeats the compile errors.
- D4: `ERROR (no tests ran)` prints only its explanatory line, plus any changed-file warnings. The generic fallback skips simulator and Xcode chatter (`DVTErrorPresenter`, `CoreSimulator`, …).
- Also: a bare `error: Error Domain=…` fragment left by interleaved xctest NSError logging is no longer counted as a compile error. It turned up once in a full `./build.sh unit` run during round 2.
- D5: `.gitignore` ignores `tools/__pycache__/`.

Round 3 (review notes 1–3):

- `check-report.py`: the outcome now comes only from the exit status and, for `unit`/`ui`, the `.xcresult` counts. Error lines are not collected at all when `rc == 0`, because neither xcodebuild nor swiftc exits 0 after a compile error. Log-derived test counts (used only when no `.xcresult` exists) cannot overrule `rc == 0` either. A `unit` run with `rc != 0`, no tests and a `** TEST BUILD FAILED **` / `The following build commands failed:` marker is `FAILED (build failed)`, not `ERROR (no tests ran)`. `OTHER_ERROR_NOISE` is gone. The new `tools/check-report-selftest.py` (stdlib) runs 13 offline classification cases from tiny inline logs with a stubbed `.xcresult`, including the reviewer's case.
- `worklog.py`: `VM_COMMAND` matches `build.sh ui` only when `ui` is followed by whitespace, `;&|)` or the end, so `ui-typecheck` falls through to the check stages. The `UI 1` on the round-1 transcript actually came from a different call: `./build.sh unit; …; python3 tools/check-report.py --stage ui …`, whose result held both `CHECK UNIT` and an offline `CHECK UI` line. Foreground runs now credit only the CHECK stages the command itself invokes (`command_stages`).
- `run-ui-tests-vm.sh`: `finish_check_line` runs from an `early_exit` trap, installed before `tart-golden require`, and later from `cleanup()`. A non-zero exit that set no `CHECK_LINE` prints `CHECK UI: ERROR (aborted, exit N)` and exits 2. `tart-golden require` failures get their own labelled line. Interrupts are recognised by an `INTERRUPTED` flag that the HUP/INT/TERM traps set, not by the status, because `git` exits 129 on a usage error. They print `CHECK UI: ERROR (interrupted)` and keep 129/130/143. Those traps now sit next to `early_exit`, so they also cover the preflight. The header and `docs/ui-testing-vm.md` state this contract.

### Files and approach

**1. `tools/check-report.py` (new, Python 3 stdlib, executable).** Classifies a run, prints the tail, writes the digest and calls Haiku. All of the logic lives here, so the zsh stays thin and a log can be re-checked offline.

```
tools/check-report.py --stage {build,unit,ui-typecheck,ui} --log PATH --rc N
                      [--xcresult PATH] [--duration SECS]
```

Repo root = `git -C <log dir> rev-parse --show-toplevel`. The shared root is the parent of `git rev-parse --path-format=absolute --git-common-dir`, which is the main checkout even from a worktree.

**Parse:**
- **Compile errors:** lines matching `^(/\S[^:]*):(\d+):(\d+): (fatal )?error: (.+)$`, deduped by `(path, line, message)`. Also non-located errors matching `(^|\s)(error|fatal error):\s`, such as `ld: error:`, `xcodebuild: error:` and SwiftPM's `error:`, minus lines already counted. The compile-error count is the number of unique entries.
- **Failed commands:** up to 10 lines after `The following build commands failed:`, stopping at a blank line. These feed the digest only and cover linker and signing failures.
- **Tests** (`unit`, `ui`), when `--xcresult` exists: `total = totalTestCount`, `failed = failedTests`, `skipped = skippedTests`. Each `testFailures[]` entry becomes `<targetName>/<testIdentifierString>: <failureText>`.
- **Swift Testing check:** lines matching `^✘ Test (.+?) recorded an issue at (\S+?):(\d+):\d+: (.+)$` add `file:line` evidence. Also used as a fallback for the count and for failures when the bundle is missing or unreadable: `✔/✘ Test run with (\d+) tests? … (passed|failed)`. Then XCTest `Executed (\d+) tests?, with (\d+) failures?` (take the last one) and `Test Case '…' failed` lines.
- **Warnings:** `^(/\S[^:]*):\d+:\d+: warning: .+$`, kept only when the repo-relative path is in the changed set. The changed set is `git diff --name-only main...HEAD`, skipped if `main` doesn't resolve, plus `git diff --name-only HEAD` plus `git ls-files --others --exclude-standard`. Deduped. On a pass only the count is shown.

**Classify** (exit codes):

| Outcome | Condition | Exit | Final line |
|---|---|---|---|
| PASSED | `rc == 0` and no compile errors; for `unit` and `ui` also `total > 0` and `failed == 0` | 0 | `CHECK BUILD: PASSED` / `CHECK UI-TYPECHECK: PASSED` / `CHECK UNIT: PASSED (2588 tests)` / `CHECK UI: PASSED (5 tests)` |
| FAILED | compile errors > 0, or failed tests > 0, or `rc != 0` for `build` / `ui-typecheck` | 1 | `CHECK UNIT: FAILED (3 tests, 1 compile error)`. For `build`/`ui-typecheck`: `CHECK BUILD: FAILED (2 compile errors)`, or `(xcodebuild exit 65)` when no error lines were found. Pluralize correctly: `1 test`, `1 compile error`. |
| ERROR | `unit`/`ui` with no compile errors and no failures, but `total == 0` (whatever `rc` is): `(no tests ran)`. Or `rc != 0` with no failures and no compile errors: `(exit N, no test summary)`. Or `rc` in 129/130/143: `(interrupted)`. | 2 | `CHECK UNIT: ERROR (no tests ran)` |

**Stdout, in order.** Nothing else from the log is printed.
1. On FAILED or ERROR only: the failure block (below).
2. `==> <stage>: <counts>`. For `unit`/`ui`: `2588 tests, 0 failed, 3 skipped; 0 compile errors; 1 warning in changed files`. For `build`/`ui-typecheck`: `0 compile errors; 1 warning in changed files`.
3. `==> <duration>s · log <repo-relative log path>`. On failure, add `· digest <path>.failures.txt`.
4. The ALL-CAPS line, always last. Its format is fixed: `CHECK <STAGE>: (PASSED|FAILED|ERROR)( \(.*\))?`, with `STAGE` in `BUILD|UNIT|UI-TYPECHECK|UI`.

**Digest** (FAILED and ERROR): in order, compile errors (`file:line:col: error: msg`), failed-command lines, test failures (xcresult entries, each followed by its Swift Testing `✘ … recorded an issue at file:line: …` line when one matches the test name), then changed-file warnings. Dedupe exact lines and truncate each to 300 characters. Write the full deduped digest to `<log>.failures.txt`. If ERROR has no digest lines (e.g. exit N with no summary), use the last 15 non-blank log lines that match `error|failed|cannot|unable|denied|not found` (case-insensitive), or the last 5 log lines if none match. The printed digest is capped at **60 lines**, followed by `… N more lines in <failures.txt>` when cut.

**Haiku summary.** Runs on FAILED only, never on PASSED or ERROR. It is on by default and off with `BATTY_CHECK_SUMMARY=0`.
- Command: `claude -p "<PROMPT>" --model haiku --output-format json --tools "" --no-session-persistence`. The digest (the capped 60 lines) goes on stdin.
  - `cwd` is a fresh `tempfile.mkdtemp()`, so the project `CLAUDE.md`/`AGENTS.md` aren't loaded.
  - `env` is a copy with `CLAUDECODE` removed, in case the nested CLI refuses to start inside a session.
  - Timeout `BATTY_CHECK_SUMMARY_TIMEOUT`, default 90 s.
- PROMPT (exact text):

  > You are summarizing a failed build or test run of Batty, a macOS Swift app, for the engineer who has to fix it. Standard input holds the error lines extracted from the log (compile errors as file:line:col, failing tests with their assertion text, and warnings in changed files). For each distinct failure write exactly one bullet: `- <test name or file:line> — <likely cause, one line> — evidence: "<shortest quoted fragment of the input line>"`. Merge failures that share one cause into one bullet that lists every test or location. Use only what the input shows; do not guess at code you cannot see, suggest refactors, or add any introduction or closing text. At most 15 bullets.

- **Success** means exit 0, the JSON parses, `is_error` is false and `result` is non-empty. Print `==> failure summary (haiku; raw digest: <failures.txt>)` and then `result`, capped at 40 lines.
- **Any other outcome** (`claude` not on `PATH`, nonzero exit, timeout, bad JSON, `is_error`) prints `==> haiku summary unavailable (<reason>); raw digest:` and then the capped digest. With `BATTY_CHECK_SUMMARY=0` the reason is `disabled`. The exit code and the final line never depend on Haiku.

Using the shared root means every worktree writes to one file in the main checkout, which is gitignored. Fields: `{"ts": ISO8601, "stage", "log": <absolute log path>, "worktree": <repo root>, "ok": bool, "cost_usd": total_cost_usd, "duration_ms", "usage": usage, "model": first key of modelUsage or "haiku"}`.

**Pruning.** After writing, keep the newest 10 runs per stage in the worktree's `build/checks/` and delete older `<stage>-*.log`, `*.failures.txt` and `*.xcresult`. Never touch `haiku-usage.jsonl`.

### User checklist

- Run `./build.sh` and `./build.sh unit` in a terminal and confirm the short tail reads well. `--verbose` should still give the old streaming behavior.
- Look at one Haiku summary from a deliberately failing test and judge whether it helps an implementer more than the raw digest. That is the option A vs B experiment; set `BATTY_CHECK_SUMMARY=0` for B.

### Open questions (non-blocking; defaults chosen)

- **Exit codes:** `./build.sh ui-typecheck` and the VM runner change their exit codes. Precondition failures and missing tools move from 1 to 2, and VM test failures move from xcodebuild's 65 to 1. No caller depends on the old values (grep shows only docs). `docs/ui-testing-vm.md`'s historical "exit 65" record stays as history.
- **Haiku cost:** the summary is added into the row's Cost, and also shown in its own Haiku column.
