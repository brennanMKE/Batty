# 0531 — `./build.sh` streams full build and test logs into agent context, with no result line or failure digest to act on

| | |
|---|---|
| **Status** | open |
| **Module** | Testing / Build / Docs |
| **Platform** | macOS |
| **First seen** | 2026-10-19 |

## Description

Implementers and reviewers run `./build.sh`, `./build.sh unit` and `./build.sh ui-typecheck`, and all xcodebuild output streams to the terminal and into the agent's context. Issues.md then tells them to "read the output, don't just check the exit code". In the user's experiment, implementer test runs plus log reads made up about 40% of implementer tool calls. Almost all of that output is noise on success, and on failure the useful part is a few lines.

User direction (2026-10-19, verbatim):

> "Instead of reading the full log we should have the script capture the result which should return with an exit code which indicates success or failure. The last few lines should also have text in all caps indicating success or failure. When it is a success we don't have any further log analysis to do. When it fails tests we need to grep just the lines which have the warnings or errors and pass those to Haiku for summary. This would be feedback to the implementer."

> "Make this change. We should also consider how we handle the build log. We also do not need the full log going into the context. On success we can just pass it through. For failures we can also grep out relevant lines. Revise the build script to do this as well."

**Goal:** keep build and test logs out of agent context. The implementer acts on the exit code, an ALL-CAPS result line, and a short failure digest summarized by Haiku.

Related: #0528 (verification-tier tooling: fast/slow unit split, VM build-only and sharding). The two touch the same `build.sh` cases and the same Issues.md sections. Whichever lands second adopts the other's conventions.

## Current state (verified 2026-10-19 on `main` at `e7d47641`)

- **`build.sh`** (`zsh`, `set -euo pipefail`):
  - `ui-typecheck` is dispatched *before* the `Active.xcconfig` snapshot and `EXIT` trap, on purpose, so that it never rewrites `Active.xcconfig`. It runs `xcrun swiftc -typecheck`, not xcodebuild, so it produces no `.xcresult` and no test counts. Its digest can only come from grep (`error:` / `warning:`).
  - The `Active.xcconfig` restore lives in the `EXIT` trap (`restore_active_xcconfig`), which captures `$?` and re-`exit`s with it. Any new summary or digest step must not clobber that status, and must not break the restore on Ctrl-C or failure.
  - `unit` runs `xcodebuild test … -only-testing:BattyKitTests`, with no `-resultBundlePath` and **no way to pass a test filter**. The "zero-tests filter" acceptance case below needs a filter argument (e.g. `./build.sh unit <Suite/test>`). #0528 may add one too, so coordinate.
  - A plain `./build.sh` has no `build` case. `ACTION` defaults to `build` and falls into the `*)` passthrough, which runs `xcodebuild` with the remaining args. With no args that is xcodebuild's implicit build. Capturing build output means giving `build` its own case, or teaching the passthrough to capture.
  - `ui`/`test` `exec` `tools/run-ui-tests-vm.sh`, and `package` `exec`s `scripts/build-beta.sh`. `scripts/` is a restricted area (AGENTS.md), so `package` and `release` should stay pass-through unless the user approves otherwise.
- **`tools/run-ui-tests-vm.sh`** already ends with `==> RESULT: TEST SUCCEEDED` / `==> RESULT: TEST FAILED (exit N)`, followed by a `grep … | tail -20` of the test log, a crash-report count, a warnings count, and the result-bundle and log paths. It exits with the xcodebuild status. Precondition failures go through `fail()` → `exit 1`, which can't be told apart from a test failure.
- **`tools/worklog.py`** times only VM runs (`VM_COMMAND`, matched to a result containing `==> RESULT:` or `Executed N tests` via `VM_SUMMARY`). Rows have one `VM` column. Builds and unit runs aren't measured. A `claude -p` call made from inside `build.sh` never appears in the subagent transcript, so its cost has to come from a file the script writes.
- **`issues/Issues.md`** Phase 2 step 5 says "Read the output, don't just check the exit code", and "Verification tiers" says to quote the unit `Test run with N tests … passed` line. Both assume the agent reads the full log.

## Proposed design (user-approved; the plan settles the open details)

1. **Captured output, short tail.** For `build`, `unit` and `ui-typecheck`, `build.sh` writes the full tool output to `build/checks/<stage>-<timestamp>.log` (`build/` is already gitignored), not the terminal. It ends with about 5 lines or fewer: stage, counts (tests run / failed; compile errors), duration, log path, and a final ALL-CAPS line:
   - `CHECK UNIT: PASSED`
   - `CHECK UNIT: FAILED (3 tests, 1 compile error)`
   - `CHECK UNIT: ERROR (no tests ran)`

   Exit codes: **0** pass, **1** build or test failure, **2** could not run (zero tests ran, no test summary, missing tool). An opt-out (`--verbose` or an env var such as `BATTY_CHECK_VERBOSE=1`) streams the full log for humans. `Active.xcconfig` restore must keep working on every exit path. `ui-typecheck` must still never touch it. Whether `release`, `package`, `run` and arbitrary passthrough actions capture is for the plan to decide. Default: leave them streaming.
2. **Failure digest, on failure only.** Write `<log>.failures.txt`:
   - test failures from the result bundle (`-resultBundlePath`, `xcrun xcresulttool get test-results tests`), checked against Swift Testing output, since BattyKitTests uses `import Testing`;
   - compile errors via grep (`error:`, `** BUILD FAILED **`, `** TEST FAILED **`);
   - `warning:` lines only for files changed vs `main` (`git diff --name-only main...HEAD` plus the working tree).

   Dedupe, cap at about 60 lines, and print the digest (or the Haiku summary) instead of the log.
3. **Haiku summary (option A, default).** On failure, pipe the digest to `claude -p --model haiku --output-format json` with a fixed prompt: for each failure, the test or `file:line`, the likely cause in one line, and the evidence. Print the summary. Append Haiku's cost and usage, with stage, timestamp and log path, to `build/checks/haiku-usage.jsonl`. **Degrade gracefully:** when `claude` is missing, unauthenticated, times out, or fails, print the raw digest, and leave the exit code unchanged. An env var (e.g. `BATTY_CHECK_SUMMARY=0`) disables it, so the experiment can compare against **option B**: the orchestrator dispatches a Haiku subagent that runs the checks and relays its summary to a fresh implementer.
4. **VM runner.** `tools/run-ui-tests-vm.sh` adopts the same final ALL-CAPS line (e.g. `CHECK UI: PASSED` / `FAILED (N tests)` / `ERROR (<precondition>)`), exit 2 for precondition failures, and the same digest from `UITests.xcresult`. The plan decides how far to go. Keep `==> RESULT:` (or update `worklog.py`'s `VM_SUMMARY` in the same change), so VM timing doesn't silently stop matching.
5. **`tools/worklog.py`.** Time `./build.sh` (build), `unit` and `ui-typecheck` calls by stage, the same way as VM runs (tool_use to tool_result, background-aware). Count Haiku summaries and sum their cost from `haiku-usage.jsonl` within the transcript's time window, then fold that into the row cost or a separate column. Add Build / Unit / UI columns, and update the work-log table header in Issues.md to match.
6. **Issues.md.** Rewrite Phase 2 step 5, Phase 3 step 3 and "Verification tiers". Agents read only the tail, the result line and the digest, never the full log. "Zero tests ran" is now exit 2 and `CHECK …: ERROR`, so the script enforces "compilation is not verification" instead of the reader. `## Verification` quotes the ALL-CAPS line, the counts line and the log path. New tests are confirmed by name with a filtered run or from the `.xcresult`, not by reading the log. Also document the opt-out switches.

## Acceptance

A verification subagent, working in a scratch worktree, exercises each case and confirms the exit code, the result line, the digest size (≤ ~60 lines), and that **no full log reaches stdout**:

- [ ] passing `./build.sh` → exit 0, `CHECK BUILD: PASSED`
- [ ] injected compile error → exit 1, `CHECK BUILD: FAILED (…compile error…)`, digest names the `file:line`
- [ ] passing `./build.sh unit` → exit 0, `CHECK UNIT: PASSED` with the test count
- [ ] injected failing unit test → exit 1, digest names the test and its assertion
- [ ] unit filter that matches zero tests → exit 2, `CHECK UNIT: ERROR (no tests ran)`
- [ ] `ui-typecheck` pass and fail, and `Active.xcconfig` untouched (mtime unchanged)
- [ ] Haiku unavailable (`claude` not on `PATH`, or `BATTY_CHECK_SUMMARY=0`) → raw digest printed, exit code unchanged
- [ ] Haiku available → summary printed, one line appended to `build/checks/haiku-usage.jsonl`
- [ ] `--verbose` streams the full log
- [ ] `Active.xcconfig` restored after a failure and after Ctrl-C
- [ ] `tools/worklog.py` on a transcript containing these runs reports Build / Unit / UI time and Haiku count/cost
