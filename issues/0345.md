# 0345 — Mirror the tmux window layout onto the Split tree, bidirectionally

| | |
|---|---|
| **Status** | open |
| **Module** | Split / Pane |
| **Platform** | macOS |
| **First seen** | 2026-08-21 |

## Description

Extend [#0344](0344.md)'s single remote Pane to a whole remote
Session: map the tmux window layout onto Batty's Split tree in both
directions. Remote layout changes restructure the Batty Session;
local layout changes — including divider drags — become tmux commands
that round-trip.

**This is where layout authority moves off the local machine**, and
that is the hard part. For a remote-backed Session, tmux owns the
split tree; Batty's `SplitTree` becomes a mirror of it rather than the
source of truth. #0341's Hard problem 4 states the consequences; this
issue owns resolving them.

**Not scheduled work.** Inherits #0341's status: staged for a future
major release, not queued.

### The two directions

**Remote to local.** `%layout-change` (and `%window-add`,
`%window-close`, `%unlinked-window-*`) arrive **unsolicited from the
network** and must restructure `SplitTree`. Nothing in Batty has this
shape today — every Split-tree mutation currently follows directly
from a local command. #0341's Hard problem 3 is binding here:
event-origin writes are allowed, they need an explicit owner, they
must never come from view construction, and they must not be hopped
into a `Task` to silence a mutate-during-update warning (the #0229
trap).

`SplitTree` is `@Observable`
(`BattyKit/Sources/BattyKit/Model/SplitTree.swift`) and `@Observable`
notifies on **every** write including equal-value writes, so a naive
"rebuild the whole tree on every `%layout-change`" implementation
invalidates the entire Session's view tree on every remote event.
Diffing the incoming layout against the current tree and writing only
what actually changed is a requirement, not an optimization.

**Local to remote.** Splitting, closing, and resizing Panes become
tmux commands. Resizing is the sharp one: [#0338](0338.md) shipped the
divider-drag fix, whose path is
`DraggableSplitView`'s `DragGesture` → `SplitDividerMath.ratio(...)` →
`onRatioChange` → `SplitTree.updateRatio(forSplitID:to:)`
(`BattyKit/Sources/BattyKit/Views/SplitContainerView.swift`,
`BattyKit/Sources/BattyKit/Model/SplitTree.swift`, which also holds
the sole 0.05–0.95 clamp). For a remote-backed Session that write is
a **prediction**, and the two obvious policies both have a cost:

- **Optimistic** — apply locally, send `resize-pane`, reconcile when
  `%layout-change` arrives. Smooth, but a disagreeing remote makes the
  divider snap back — visually the same failure #0338 was filed to
  fix, from an entirely different cause. #0338's actual root cause
  (a coordinate space that moved because every `onChanged` re-placed
  the divider) is a direct warning about this feedback shape.
- **Authoritative** — do not move the divider until the remote
  confirms. Correct, but the drag is only as smooth as the SSH round
  trip, and #0344's latency measurement is what says whether that is
  tolerable.

Choosing between them, and proving the choice does not reintroduce
#0338's symptom, is the core of this issue.

## Expected behavior

1. Attaching to a tmux window with several panes produces a Batty
   Session whose Split tree has the same shape and proportions.
2. Splitting a pane on the remote (from another client, or by a
   program) appears in Batty as a new Pane in the right place,
   without the user doing anything.
3. Closing a pane on the remote removes the corresponding Batty Pane
   and collapses its Split, matching Batty's existing collapse
   behavior.
4. Splitting or closing a Pane in Batty performs the same operation on
   the remote, and the resulting `%layout-change` agrees with what
   Batty already shows — no visible re-shuffle after the round trip.
5. Dragging a divider resizes both the Batty Panes and the remote tmux
   panes, and the divider tracks the pointer without jitter or
   snap-back.
6. Pane identity is stable across layout changes. A Pane keeps its
   Batty identity — focus, Tab state, scroll position — when the tree
   restructures around it. Tracking by tmux pane id (`%0`, `%1`), not
   by position, is what makes this possible.
7. A layout tmux can express but Batty cannot (or vice versa) degrades
   visibly and predictably rather than producing a wrong tree.

## Acceptance criteria

1. A multi-pane tmux window attaches and renders with matching
   structure and proportions; each Batty Pane shows the correct tmux
   pane's output.
2. Remote-initiated split, close, and resize each update the Batty
   Session correctly, verified by driving them from a second tmux
   client on the remote while Batty is attached.
3. Local split, close, and divider-drag each update the remote
   correctly, verified by `tmux list-panes` on the remote.
4. **The #0338 symptom does not return.** Dragging a divider in a
   remote-backed Session tracks the pointer smoothly, with no
   jitter and no snap-back. Verify by hand — #0338's review
   established that its unit tests cannot catch the class of bug
   (hand-authored stable-space points are precisely what the buggy
   code never received), so a green suite is not evidence here.
   State which policy (optimistic or authoritative) was chosen and
   why.
5. `scripts/build.sh unit` passes with new `BattyKitTests` covering
   the layout mapping as a **pure function** — tmux layout string in,
   expected `SplitTree` shape out, and back — driven from recorded
   layout strings, not a live remote. Include at least: a two-pane
   horizontal, a two-pane vertical, a nested three-pane, a
   restructure that must preserve pane identity, and a layout Batty
   cannot represent.
6. **Equal-value writes are not emitted.** Demonstrate that applying
   an unchanged `%layout-change` produces no `SplitTree` writes.
   `@Observable` notifies on every write, so this is observable and
   testable, and it is the difference between a usable feature and
   one that redraws the Session on every keystroke.
7. Every network-driven write to `SplitTree` has a named owner outside
   view construction, and no `Task` hop was used to avoid a
   mutate-during-update warning. `docs/swiftui-observation-rules.md`
   is binding; #0229 is the case study.
8. The Batty-to-tmux concept mapping is written down — specifically
   what happens to Batty **Tabs**, which have no direct tmux
   equivalent inside a window. This is #0341's Open question 2 and
   this issue cannot ship without answering it.

## Notes

- `SplitTreeNode` is a `public indirect enum` with `.leaf(PaneRuntime)`
  and `.split(id:direction:ratio:left:right:)`; `SplitTree` holds
  `root` and `focusedPaneID`. tmux layout strings are a different
  shape (nested cell geometry with absolute sizes and offsets), so the
  mapping is a real conversion, not a rename.
- Focus is bidirectional too, and easy to forget: tmux has an active
  pane, Batty has `focusedPaneID`. Deciding whether they are slaved
  together belongs here.
- tmux windows versus Batty Tabs is the messiest part of the mapping.
  Do not paper over it; a wrong choice here is expensive to undo once
  #0346's UX is built on it.
