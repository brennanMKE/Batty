## Description

The user's Prod Batty 1.3.3 (build 20261027) crashed on 2026-11-12 at 19:29:06 PST after about 16 days of uptime, killing every live Terminal Session. AppKit raised an NSException from `-[NSWindow(NSDisplayCycle) _postWindowNeedsUpdateConstraints]` and the app aborted (`EXC_CRASH` / `SIGABRT`). This is the same exception family as #0229: something dirtied window constraints while AppKit was inside a display-cycle pass. The trigger chain is different. In #0229 it was an `@Observable` write flushed during `_NSViewLayout`. Here it is a hit test for the cursor update, which made SwiftUI update a `ScrollView`'s graph state. No Batty frames are symbolicated, so the responsible view is not known.

### What the exception actually is (new evidence, read in this re-plan)

- The VM run's `app-warnings.log` (`build/ui-tests/20261112-195921-26678/app-warnings.log`, lines 683-688) gives the exception text: **"The window has been marked as needing another Update Constraints in Window pass, but it has already had more Update Constraints in Window passes than there are views in the window."** AppKit logs this first, with "Future marking as needing Update Constraints in Window might be ignored", and raises `NSGenericException` on the next marking, 30 ms later.
- The Prod report (`issues/0601/Batty-2026-11-12-192909.ips`) throws from the same instruction: `-[NSWindow(NSDisplayCycle) _postWindowNeedsUpdateConstraints] + 1716` in both reports. The Prod `.ips` has no message text, and the unified log no longer holds pid 15207's lines (checked with `log show`). So the Prod message is inferred from the identical throw site, not read.
- **So `_postWindowNeedsUpdateConstraints` is AppKit's non-convergence guard, not a "you may not dirty constraints now" check.** Marking constraints dirty mid display cycle is legal; AppKit just runs another pass. It throws only after a window has run more update-constraints passes than it has views, i.e. some participant re-dirties constraints on every pass and never settles. With about 19 live Terminal Sessions the Prod window had many hundreds of views, so the loop ran hundreds of passes. The hit test in the Prod stack is the **last requester after the cap**, not the cause. The `HostingScrollView` that made that request is a suspect, not a culprit: whichever view asks next after the cap gets the throw.
- Round 1 failed because its premise was wrong. It removed the last requester and added a new participant, a frame-writing `tile()`/`viewDidLayout()` pair around an `NSHostingView`, that did not converge.
- `docs/swiftui-observation-rules.md` rule 1 ("Mid-pass, AppKit answers with an NSException") is right in effect, because a synchronous constraint-dirtying call from a SwiftUI callback is the usual way to build such a loop. But it misstates the mechanism. The docs step below corrects the wording without weakening the rule.

### Options evaluated

**(a) Keep SwiftUI `ScrollView`, change how observed snapshot writes reach it.** Rejected.
- A write from a main-actor `Task` between events marks the hosting view `needsUpdateConstraints` through `NSHostingView.setNeedsUpdate`. AppKit's next `NSDisplayCycleFlush` runs its layout observer (`__NSWindowGetDisplayCycleObserverForLayout_block_invoke`, seen in the VM stack), and that brings the graph up to date. In a graph that converges, the cursor-update hit test later finds nothing dirty, and `updateViewGraph` is a no-op. That the Prod hit test found the column graph dirty *and* the window already over the cap means layout had ended without converging.
- No change to when or how writes arrive (coalescing, `withTransaction`, CATransaction tricks, run-loop modes) can make a non-converging loop converge. At most it changes which requester takes the throw. Retiming writes is also exactly the `Task`-hop "fix" the binding rules forbid.

**(b) A fixed AppKit host that never resizes an `NSHostingView` from layout.** Rejected.
- A scroll host has to give the document its content's height, so some code must turn SwiftUI's measured height into an AppKit frame or constraint on every content change. That is a layout feedback loop Batty would own and have to prove converges for every content state, scroller style and width. The SwiftUI `ScrollView` already *is* that loop, written and tuned by Apple.
- Sizing the hosting view once to a large or ideal frame breaks the scroll extent: wrong scroll length, empty space, clipped content.
- `safeAreaRegions = []` (macOS 13.3+) would stop the `invalidateSafeAreaInsets` path seen in the VM crash. But any frame change of an `NSHostingView` with `sizingOptions = []` still re-proposes size to its graph, and the scroller-toggle and width feedback stays.
- Round 1 also showed the non-crash cost of a second hosting view. Menus and popovers inside it, accessibility frames and element discovery all regressed in the UI suite. The user is skeptical of this direction, and the evidence agrees.

**(c) Chosen: revert round 1, keep SwiftUI `ScrollView`, and find the looper with a convergence probe before changing any view.** Plus pause status sampling for occluded windows.
- Since the exception is a loop guard, the fix has to remove the specific non-converging participant. The evidence does not identify it: no Batty frames, and the hit test is only the last requester.
- The probe (step 2) is a unit-test harness. It hosts each status view, alone and inside a `NavigationSplitView` like production, sweeps sizes and scroller styles, ticks the content like a sampler does, and asserts every settle converges.
- If the probe finds a non-converging configuration, the fix targets that cause, and that configuration becomes the regression test. If it finds none, the implementer bails with the results rather than guess (step 5).
- Pausing sampling for occluded, minimized or hidden windows is real user value. It cuts the hours of exposure (status Panes no longer re-render in a window nobody can see), but it is not the crash fix.

## Root cause

**Not found. The loop that tripped AppKit's cap in Prod is not reproduced.** Round 2 found and fixed one demonstrated violation of the binding rules and one dead layout-origin write. Neither is shown to be the Prod loop.

What the exception is (from the re-plan, confirmed here): `_postWindowNeedsUpdateConstraints` raises AppKit's convergence guard, "more Update Constraints in Window passes than there are views in the window". The hit test in the Prod stack is the last requester after the cap, not the cause.

What the probe found (`LayoutConvergenceProbe`, round 2):
- **AppKit's cap fires in the unit-test harness.** An unbounded `ConstraintLoopControl` with no breaker raised `NSGenericException` ("…more Layout Window passes than there are views in the window") from the display cycle's `layoutIfNeeded()` and killed the test process. So a real loop in any hosted tree fails the run.
- **No Batty configuration probed loops.** None of these reached the cap or failed to settle in three rounds:
  - the real `NavigationSplitView { SessionSidebarView } detail: { SessionDetailView }` tree with terminal Panes, splits, two-Tab Panes and 4 or 16 mounted Sessions, across window sizes and every Session switch;
  - all four status views in that tree (System Metrics, Process Status, LM Studio disconnected, Git Status) with sampler ticks, in both scroller styles;
  - each status view alone (root tier) at widths 200/400/720, eight heights around the scroll boundary, both scroller styles and three ticks.
- **Round 1's host does not loop in the probe either.** With `StatusPaneScrollView` restored, `systemMetricsPaneConverges()` and `statusPanesConvergeInTheSessionDetailTree()` passed (split-tier requests rose from 88 to 364 per settle, but it settled). Round 1 crashed in the VM, so the offline harness does not cover the conditions of that crash. This is a reason to doubt "no loop" as a statement about the live app.
- **Suspect 1, terminal placement: the premise was false (fixed).** `docs/swiftui-observation-rules.md` sanctioned `TerminalHostStore.setPlacement`, called from `TerminalPlaceholderView`'s `onGeometryChange` inside SwiftUI's layout pass, as "plain frame writes on the frame-based (not Auto Layout) `TerminalHostView`". In fact `TerminalHostView` has `translatesAutoresizingMaskIntoConstraints = false`, and each `AppTerminalView` was added with `translatesAutoresizingMaskIntoConstraints = true`. In a 4-Session window the host held 32 constraints for those subviews, and the terminal views held none of their own. Every placement frame write (and every un-hide) marked 5 views up to the detail column's `NSHostingView` as needing update constraints, from inside layout. `AppTerminalView` itself (libghostty-spm `Platform/AppKit/`) has no constraint, `translatesAutoresizingMaskIntoConstraints`, hosting-view, safe-area or `addSubview` code (grep). Its `setFrameSize`/`layout()` overrides call `core.fitToSize()`/`requestImmediateTick()`, and `updateTrackingAreas` only rebuilds its tracking area. So the constraint dirtying came from Batty's autoresizing-mask setting, not from libghostty.
- **Suspect 2, `SessionDetailView`'s `splitDetailToolbarSafeInsetTop` write: dead (removed).** No reader exists (grep: only the setter and the `EnvironmentValues` declaration). Removing it changed a Session switch's requests by 2. It does not loop in the probe. It was also #0420's candidate 5 for "Geometry action is cycling".
- **Suspect 3, `PaneView`'s `frameInSession` / `paneWidth` / `paneHeight`: converges.** Left unchanged. These values are read in `body`, not dead.
