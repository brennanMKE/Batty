# 0601 — Prod Batty 1.3.3 aborts with an uncaught NSException when a cursor-update hit test makes a SwiftUI ScrollView dirty window constraints during the display cycle

| | |
|---|---|

| **Module** | Window / Sidebar / Pane |
| **Platform** | macOS |
| **First seen** | 2026-11-12 |

## Description

The user's Prod Batty 1.3.3 (build 20261027) crashed on 2026-11-12 at 19:29:06 PST after about 16 days of uptime, killing every live Terminal Session. AppKit raised an NSException from `-[NSWindow(NSDisplayCycle) _postWindowNeedsUpdateConstraints]` and the app aborted (`EXC_CRASH` / `SIGABRT`). This is the same exception family as #0229: something dirtied window constraints while AppKit was inside a display-cycle pass. The trigger chain is different. In #0229 it was an `@Observable` write flushed during `_NSViewLayout`. Here it is a hit test for the cursor update, which made SwiftUI update a `ScrollView`'s graph state. No Batty frames are symbolicated, so the responsible view is not known.

## Steps to reproduce

Unknown. The app had been running since 2026-10-27 12:15. What the user was doing at the moment of the crash is not recorded. The stack starts from a cursor update, so mouse movement over the window, or a window or view change under a stationary pointer, is a plausible trigger. That is not confirmed.

## Expected behavior

Hit testing and cursor updates never crash the app. No SwiftUI view in the window dirties constraints from inside AppKit's display cycle.

## Actual behavior

The app aborts with an uncaught NSException. Every Terminal Session is lost.

## Notes

### Observed facts (from the crash report)

- Batty 1.3.3 (20261027), `co.sstools.Batty`, `/Applications/Batty.app` (Prod). macOS 27.0 (26A428). Incident `74C6DA34-6FD4-47CC-AA35-F676D1E6CCBF`. Original at `~/Library/Logs/DiagnosticReports/Batty-2026-11-12-192909.ips`.
- Launched 2026-10-27 12:15, crashed 2026-11-12 19:29:06 PST. 111 threads, about 876 MB malloc.
- `EXC_CRASH (SIGABRT)`, "Abort trap: 6". `abort()` follows an uncaught NSException, rethrown by `objc_exception_rethrow` in `-[NSView _hitTestForContext:...]`.
- The main binary shows only as `Batty ?+0` at `App.main`. No Batty or BattyKit frames are symbolicated in either the faulting stack or the exception backtrace.
- Thread names: 19 each of `renderer`, `io`, `io-reader`, `io-gather` and `cf_release`, so about 19 live Terminal Sessions. Two `CVDisplayLink` threads. A `WebCore: Scrolling` thread also exists. No Batty source imports WebKit, so it comes from a system or framework component. Only the main thread was doing anything relevant.

**Faulting thread 0 (main), bottom to top:**
`CA::Transaction::flush` → `NSDisplayCycleFlush` → `displayCycleUpdateStructuralRegions` → `-[_NSTrackingAreaAKManager setCursorForMouseLocation:]` → `-[NSThemeFrame _performHitTestForContext]` → `-[NSView _hitTestForContext:]` (rethrow) → `abort`.

So: while the display cycle updated structural regions, AppKit hit-tested the window to set the cursor. The hit test went through an `NSHostingView`, then an `NSSplitView`, then an `AppKitPlatformViewHost` (an `NSViewRepresentable` host), then another `NSHostingView`. Asking a hosting view for its responder node forced a lazy AttributeGraph update. That update reached a SwiftUI `ScrollView` (`HostingScrollView` / `ScrollViewHelper`). It opened an async transaction, which called `setNeedsUpdateConstraints:`, and AppKit raised because the window was mid display cycle.

### Relation to #0229 and the observation rules

- #0229 and its audit #0230 hit the same throw site, `_postWindowNeedsUpdateConstraints`. There, the cause was an `ObservationGraphMutation.apply` (an `@Observable` write, a focus write) flushed while AppKit was inside `_NSViewLayout`. The fixes changed when and where that focus write happens. See `docs/swiftui-observation-rules.md`, "AppKit interop hazards in Batty" and "Case study: #0229 / #0230".
- This crash has no `ObservationGraphMutation` in the exception backtrace. The graph update was pulled by a hit test (`responderNode` getter), not pushed by a model write, and the pass is `displayCycleUpdateStructuralRegions` / cursor update, not `_NSViewLayout`. The binding rule still applies ("`NSHostingView` runs SwiftUI updates inside AppKit's layout pass"). The difference is that the SwiftUI update here was started by AppKit's own hit test.
- Whether a Batty state write made the scroll view's graph dirty just before the hit test cannot be told from this report. That write could have been a valid event-origin write. What failed is the lazy update run during hit testing.

### Hypotheses (unverified)

- **Which ScrollView.** The path runs `NSHostingView` → `NSSplitView` → `AppKitPlatformViewHost` → `NSHostingView` → `HostingScrollView`. The main window's `NavigationSplitView` (`BattyKit/Sources/BattyKit/Views/RootWindowView.swift`) is backed by an `NSSplitView`. The Help window's `NavigationSplitView` (`Views/Help/HelpView.swift`) is too. The Sidebar's `List` (`SessionSidebarView.swift`) is NSTableView-backed on macOS, and `HostingScrollView` is not what it uses, so it is a weaker candidate. SwiftUI `ScrollView`s that can sit under the main window's split view include:
  - `GitStatusPaneView.swift` (vertical and a horizontal `ScrollView`)
  - `ProcessStatusPaneView.swift`
  - `SystemMetricsPaneView.swift`
  - `LMStudioDashboardView.swift`
  - other `ScrollView`/`List` users under `BattyKit/Sources/BattyKit/Views/` (Command Palette, Open Quickly, Theme selector, Layout picker, Running Process picker, Project sheets). Those are usually in sheets, overlays or other windows, so they are less likely to be under the main window's `NSSplitView`.
  - The `AppKitPlatformViewHost` → `NSHostingView` step fits a status-view Pane hosted inside an AppKit container under the detail column. This is not confirmed.
- **Why now.** Long uptime and about 19 sessions may raise the odds, for example through timer-driven status Pane refreshes that keep scroll content dirty. A cursor update can then land at the wrong moment. Unverified.
- **Possibly upstream.** The whole chain is SwiftUI/AppKit internals on macOS 27.0 (26A428). It may be a framework bug that Batty's view structure only exposes. A fix might still be possible on Batty's side: avoid a SwiftUI `ScrollView` whose graph is still dirty when a hit test arrives, or change how the status Pane views are hosted.
