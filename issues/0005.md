## Description

Implement the layout containers from `Concepts.md` as Codable Swift types so every later module has a stable vocabulary. These are the model layer — no view code, no libghostty calls.

**Acceptance criteria:**
- `Session`, `Pane`, `Tab`, and `SplitNode` exist as Swift types matching the shapes described in `Concepts.md` and `PRD.md` §6.2.
- `SplitNode` is an `indirect enum` with `.leaf(Pane)` and `.split(direction:, ratio:, left:, right:)` cases.
- Each container has a stable `id: UUID`, and Tab references its surface via `surfaceID: UUID`.
- All four types are `Codable` and round-trip cleanly through JSONEncoder/JSONDecoder. Verify with a test in `BattyTests`.
- All four types are `Sendable`-compatible (Swift 6 / MainActor default; explicit `Sendable` conformance where it makes sense).

## Notes

- Don't bake in any UI or libghostty types here — these models must be pure value types so persistence (#0029+) can serialize them safely.
- Tab title resolution (focused-surface process → cwd → user override) lives at the view layer; the model just stores an optional override.
- Keep `bellCount` / `lastBellAt` / `unseenBellCount` on the model — they're persisted state, not view state.

## Root cause

The project had no model layer — every later issue (sidebar, splits, persistence, themes, bell feed) needs a stable vocabulary of value types to anchor against. Without these, the layout tree, persistence schema, and bell aggregation would all reinvent their own types.

## Fix

Added `Batty/LayoutModel.swift` with five types:

- `SplitDirection` — `enum { horizontal, vertical }`. String-raw-value Codable.
- `SplitNode` — `indirect enum` with `.leaf(Pane)` and `.split(direction:, ratio:, left:, right:)`. Codable synthesis works because `.split`'s associated values are all labeled. Two helper extensions: `firstPane` for traversal and `contains(paneID:)` for membership checks.
- `Tab` — id, surfaceID, optional titleOverride, lastKnownCWD, lastSetTitle, plus persistent bell state (bellCount, unseenBellCount, lastBellAt, lastBellMessage).
- `Pane` — id, ordered tabs, activeTabID, unseenBellCount. Init has a precondition that `tabs` is non-empty; `activeTabID` defaults to `tabs[0].id` when not supplied.
- `Session` — id, title, optional icon (SF Symbol name), root SplitNode, focusedPaneID, unseenBellCount.

A `Session.makeDefault(title:)` static helper produces a coherent single-pane single-tab session for "new session" code paths.

All five types conform to `Codable, Sendable, Hashable, Identifiable` (where `id` makes sense — SplitNode has no id and skips Identifiable). Sendable conformance is automatic because all stored properties are themselves Sendable value types.

Tests in `BattyTests/LayoutModelTests.swift` round-trip every type through JSONEncoder/JSONDecoder and verify the helpers. 7 new tests, all passing alongside the existing example test.

## Gotchas

- **`SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` collides with XCTest.** The project sets MainActor as the default actor isolation for all targets. XCTestCase's superclass methods (`setUpWithError`, `tearDownWithError`) and synthesized inits are nonisolated, so subclass overrides got an implicit MainActor isolation that didn't match. Symptom: build failures like `Main actor-isolated initializer 'init(invocation:)' has different actor isolation from nonisolated overridden declaration`. Fix: marked the test classes themselves as `nonisolated` (`nonisolated final class BattyUITests: XCTestCase`). This was a pre-existing breakage that prevented any test run; resolving it was a prerequisite for verifying #0005's tests. The same fix may be needed on any future XCTest subclass added to the project. (The Swift Testing tests in `BattyTests` don't have this problem because Swift Testing doesn't subclass an XCTestCase-style base.)
- **Codable synthesis for indirect enums** worked automatically here because `.split`'s associated values are all labeled. If a future case is added with unlabeled associated values, manual `init(from:)`/`encode(to:)` may be needed.
- **`SDK condition on SDKROOT is unsupported`** warning surfaces in every build because of `SDKROOT[sdk=macos*] = macosx` in `Build.xcconfig`. This is a pre-existing config quirk (the conditional doesn't apply at the project-xcconfig level). Not blocking; a separate clean-up issue can address it later.
- **Commit `5acdd83` accidentally also includes `BattyKit/*` scaffolding** — those files were already staged by the user at the time of commit and got bundled in. The `BattyKit` scaffolding is empty stub files (a side-package being set up to consume libghostty-spm and SlidingTabs), unrelated to #0005's work. The commit message under-describes the diff but the LayoutModel additions are correctly described.
