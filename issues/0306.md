## Description

There is no single command that answers, up front, "can this machine produce a release right now?" — and the credentials a release depends on are scattered across machine-local stores (login keychain, `~/.appstoreconnect/`) with no documented way to replicate them to a second Mac or back them up. The gap surfaced concretely: a release attempt was blocked when `xcrun notarytool history --keychain-profile Batty-notary` failed with "No Keychain password item found". The credential exists (if at all) only in the login keychain of whichever machine created it — `notarytool store-credentials` writes a machine-local generic-password item that does not sync. The user works across a **MacBook Air** and a **Mac mini** and had no way to see, ahead of time, which machine was actually release-capable. The failure surfaced late, mid-attempt, as a confusing error rather than as an up-front check.

In the user's words:

> "I want a script which checks the integrity of everything we need for creating releases. And if I need to replicate what I have stored on my MacBook Air to this Mac mini we will do that. And I need a backup system for it as well."

State of the Mac mini, verified 2026-08-04:

- Developer ID Application identity **present** with private key — `security find-identity -p codesigning -v` lists `Developer ID Application: Brennan Stehling (XV8BAAVZ6V)` (find-identity only lists cert+key pairs, so the key is there too).
- `Batty-notary` notarytool keychain profile **absent** — `xcrun notarytool history --keychain-profile Batty-notary` fails.
- `~/.appstoreconnect/` **does not exist** — the ASC API key `.p8` that `scripts/setup-keys.sh` reads is not on this machine.

So the Mac mini can sign but cannot notarize; the missing pieces presumably live only on the MacBook Air. Nothing reports this until `release.sh` (or a raw `notarytool` call) dies on it.

**Note on scope:** `scripts/` is a restricted area per `CLAUDE.md`, but the user has **explicitly authorized adding this script**.

## Deadline context

The user intends to push from this machine, pull on the MacBook Air, and cut a local release there for a couple of days of testing. The check script's first job is therefore to answer **which machine is release-capable right now** — run it on both, get a pass/fail verdict per item on each, and know immediately where the release must happen and what needs to move.

## Expected behavior

Three deliverables.

### 1. An integrity check script

A single command (e.g. `scripts/check-release-integrity.sh`) that reports pass/fail per item, run *before* starting a release, covering everything the release pipeline actually depends on. The real dependency list, verified from `scripts/release.sh`, `scripts/preflight.sh`, `scripts/verify-dmg.sh`, `scripts/tag-release.sh`, `scripts/appcast-item.sh`, `scripts/deploy-website.sh`, `scripts/setup-keys.sh`, `scripts/SPARKLE.md`, and `scripts/SparkleSetup.md`:

- **Developer ID Application identity matching `SIGN_IDENTITY` / `TEAM_ID`** (`release.sh:21-23`: profile `Batty-notary`, team `XV8BAAVZ6V`, identity `Developer ID Application: Brennan Stehling (XV8BAAVZ6V)`), **including its private key**. Use `security find-identity -p codesigning -v` (an *identity* is cert + key; `find-certificate` would pass on a cert-only keychain, which fails late at codesign time).
- **Certificate expiry** — report the not-after date and warn inside a lead window. Context for why this deserves a dedicated check: this project's Developer ID certificate was **revoked once already** (repeated signed local builds against the Automatic-signing configuration, during the #0265 umbrella work — see #0270 "$27.43 certificate-revocation incident", #0278, #0281, #0273; re-imported 2026-07-26). Cert validity cannot be assumed stable here.
- **The `Batty-notary` notarytool keychain profile** (`release.sh:21,49-57`, `setup-keys.sh:3`) — probe with `notarytool history`, exactly the call that failed.
- **The ASC API key file** `~/.appstoreconnect/AuthKey_DWLP54ACTJ.p8` (`setup-keys.sh:4-6`) — its presence is what makes the notary profile *re-creatable* on this machine; check it separately from the profile.
- **Third-party tools**: `create-dmg` and `fileicon` (`release.sh:32-40`).
- **Xcode toolchain**: `xcodebuild`, `xcrun notarytool`, `xcrun stapler`, `codesign`, `spctl`, `hdiutil`, `/usr/libexec/PlistBuddy`, `xmllint` (used by `preflight.sh`'s appcast gate), `rsync` (used by `deploy-website.sh`). Verified by tool tally across the scripts; `ditto` is *not* used anywhere in the pipeline.
- **Sparkle EdDSA private key** — lives in the **login keychain under account `Batty`** (`generate_keys --account Batty`, per `SparkleSetup.md`); `sign_update --account Batty` is invoked by `appcast-item.sh:88`. Releasing technically completes without it (`release.sh:329-336` treats the appcast item as best-effort), but the release **cannot be advertised to Sparkle clients** without it, so for practical purposes it is release-critical. Probe it non-destructively (e.g. `generate_keys --account Batty -p` succeeds and matches `SU_PUBLIC_ED_KEY` in `Configuration/App.xcconfig` — a mismatch means updates would ship unverifiable).
- **`Configuration/Active.xcconfig` includes `Prod.xcconfig`** — per #0280, a release cut while it points at Beta silently produces the wrong product (`Batty Beta.app` / `co.sstools.Batty.beta` from the Prod scheme, measured 2026-08-03). `preflight.sh` does not check this today. **This is the highest-value single check in the list.**
- **Clean working tree, on `main`, in sync with `origin/main`, and `MARKETING_VERSION` sanity** (bumped past the newest appcast item) — `preflight.sh` already implements these gates; reuse or invoke rather than duplicating.

Relationship to `scripts/preflight.sh`: preflight already covers cert-in-keychain, notary profile, create-dmg, fileicon, versions, appcast, and tree state — but the credential checks are **warn-level** (`preflight.sh:266-290`), it runs a full build by default (slow for a "can I even start?" question), and it knows nothing about cert expiry, the `.p8` file, the Sparkle *private* key, or `Active.xcconfig`. Whether the new checks extend preflight or stand alone as a fast credentials-focused script is an implementation decision — but the outcome must be a fast, no-build command whose per-item pass/fail output answers "is this machine release-capable" at a glance.

### 2. Replication between machines

Document (and where scriptable, script) what can and cannot move between the MacBook Air and the Mac mini — stated precisely:

- **The notary keychain profile cannot be exported.** It is a machine-local keychain item; it can only be re-created. The good news: this project **already uses the ASC API key form** — `setup-keys.sh` runs `notarytool store-credentials` with `--key ~/.appstoreconnect/AuthKey_DWLP54ACTJ.p8 --key-id DWLP54ACTJ --issuer <UUID>`, and `release.sh`'s own error text (`release.sh:50-56`) prescribes the same form. So replication is: copy the `.p8` to `~/.appstoreconnect/` on the target machine, run `scripts/setup-keys.sh`, done. (Had the profile been created from an Apple ID + app-specific password instead, it would have to be re-entered by hand on every machine — the `.p8`-based flow is strictly better and is the recommended one; keep it.)
- **The Developer ID certificate + private key** move as a password-protected `.p12` exported from Keychain Access (or `security export`), imported into the target's login keychain. Xcode's Accounts pane can also re-issue, but a Developer ID *distribution* cert's key should travel as a `.p12`, not be re-created (re-issuing multiplies certs and has already caused trouble on this account).
- **The Sparkle EdDSA private key** exports via `generate_keys --account Batty -x batty-sparkle.key` and imports on the other machine via `generate_keys --account Batty -f batty-sparkle.key` — already documented in `scripts/SparkleSetup.md`, which also says to back up the exported key. Confirm the export exists somewhere retrievable; if it was never exported, do it as part of this work.

### 3. A backup system

Define what must be backed up, where, and how to restore:

- **The three irreplaceable files**: the ASC API key `.p8` (Apple lets you download it exactly once), the Developer ID `.p12`, and the exported Sparkle private key. Of these, **losing the Sparkle private key is the most severe**: `SUPublicEDKey` is baked into every shipped app, so without the matching private key, existing installs can never be offered a verifiable update again — ever. The `.p8` and `.p12` are recoverable through Apple with friction; the Sparkle key is not recoverable at all.
- Recommend a storage location the user controls — a password manager or an encrypted volume — without prescribing a specific product. Include the restore procedure for each item (setup-keys.sh for the profile, Keychain import for the `.p12`, `generate_keys -f` for the Sparkle key).
- **The check script must report when each item was last verified** (e.g. a small local state file it stamps on each passing run), so silent expiry or a deleted keychain item does not go unnoticed between releases — "last confirmed good on this machine: <date>" per item.

## Actual behavior

- No integrity check exists; release capability is discovered when `release.sh` (or a manual `notarytool` call) fails mid-attempt with "No Keychain password item found".
- `preflight.sh` warns (does not fail) on missing credentials, checks neither cert expiry nor the Sparkle private key nor the `.p8` nor `Active.xcconfig`, and runs a full build by default.
- No replication procedure is written down; the `.p8`, the notary profile, and (presumably) the Sparkle key exist only on the MacBook Air, and the Mac mini's gaps were only established by manual probing today.
- No backup exists for the `.p8`, the `.p12`, or the Sparkle private key.
