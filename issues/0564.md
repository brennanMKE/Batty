## Description

When a Tab closes while its AI Tab-name suggestion (#0260) is still running, the on-device model call keeps going to the end. Only one close path cancels it: `AppStateStore.closeTab(id:)`. Its only production caller is the shell-exit callback. Every close the user starts runs through `WindowRuntime` and skips the cancel: the chip's ×, the Close Tab menu item, ⌘W, Close Other Tabs, closing a Pane, closing a Session and closing a Window. The AI Session-name suggestion (#0231) has the same gap. The Bell Feed summarization (#0246) is never cancelled on any path.

The effect is wasted work, not wrong names. Each stray request runs a full `LanguageModelSession` turn on the on-device model. A Tab-name turn can also call `readFile` on files in the closed Tab's folder. The `Task` and the model session stay alive until the model answers. No case found renames the wrong Tab or Session, and no entry stays in the task dictionaries after the request finishes. A late Tab suggestion can, though, write `aiSuggestedName` onto a `TabRuntime` that has already left its Pane.

The fix is one per-Tab teardown funnel that every close path calls. Today each path repeats its own subset of cleanup steps: Bell state, terminal view release, non-terminal content teardown, and (on one path) AI cancellation. #0559 just added the same Bell cleanup to Close Other Tabs, one path at a time.

## Verified (main `04e3fa11`)

### The cancel exists in one place

- `AppStateStore.closeTab(id:)` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:1598`) calls `cancelTabNameSuggestion(forTabID:)` (`:2595`) and then `WindowRuntime.closeTab`.
- `AppStateStore.removeSession(id:fromCli:)` (`:1550`) calls `cancelNameSuggestion(forSessionID:)` (`:2440`) and then `WindowRuntime.removeSession`.
- Neither cancel is private to `WindowRuntime`, and `WindowRuntime` has no hook back to the store for this. Its one store hook is `reminderCancelHandler` (`WindowRuntime.swift:111`, installed at `AppStateStore.swift:431` and `:1335`).

### Who reaches those wrappers

`AppStateStore.closeTab` has one production caller: `PaneView`'s `tab.terminal.onClose` (`Views/PaneView.swift:292`–`295`), which fires when the Tab's process exits. Every other Tab-removal path goes straight to `WindowRuntime`:

|---|---|---|---|---|

| Chip ×, chip menu Close Tab | `PaneView.swift:219`, `:678` | `AppStateStore.requestCloseTab` (`:1627`) → `WindowRuntime.requestCloseTab` (`:543`) → `WindowRuntime.closeTab` (`:474`) | no | no |

So the finding understates it. `closeTab` cancels only when the shell exits, not when the user closes the Tab.

### What a stray Tab-name suggestion does

`scheduleTabNameSuggestion` (`AppStateStore.swift:2601`) starts `Task { [weak self, weak tab] … }`, keyed by Tab id in `tabNameSuggestionTasks`.

- **Leaked task / model session:** yes, for the length of one model turn. `FoundationModelsNameSuggester.suggestName` (`ProjectName/SessionNameSuggester.swift`) builds a new `LanguageModelSession` per request, with a `ReadFileTool` scoped to the Tab's folder. Nothing cancels it, so it runs to the end, typically a few seconds, and can read up to two or three files. Closing a Window with many Tabs that just `cd`'d into project folders queues one such turn per Tab.
- **Stored entry:** cleared when the task finishes (`self.tabNameSuggestionTasks[tabID] = nil` runs before the `aiSuggestedName` write). It lasts only as long as the model turn. The memo write (`nameSuggestionMemo[cwd]`) is keyed by folder, and it is still useful to other Tabs in that folder.
- **Write to a dead `TabRuntime`:** possible. The `weak tab` is non-nil while anything still holds the object. `TerminalHostStore.releaseTerminalView`'s own diagnostic comment (`Runtime/TerminalHostStore.swift:319`–`324`) says SwiftUI is expected to keep a just-closed Tab's `TabRuntime` alive for a render pass or two. `applySuggestedTabName` (`:2628`) checks only `titleOverride` and the cwd, which a closed Tab still passes, so it can set `aiSuggestedName` on a Tab that is no longer in any Pane. This is an `@Observable` write that nothing visible reads. It's harmless today, but it's a write the code shouldn't make.
- **Wrong Tab renamed:** no. The task applies to the captured object, and Tab ids are fresh UUIDs. No path found re-adopts a closed Tab's id: there is no undo-close, and no Tab move or tear-off between Panes or Windows.

### What a stray Session-name suggestion does

`scheduleNameSuggestion` (`:2450`) captures `[weak self]` and the Session id. `applySuggestedName` (`:2480`) looks the Session up across `windows` and returns when it's gone. So there's no dead-object write and no wrong rename, but the same model turn runs on, for every close path except `batty session close`. The `nameSuggestionTasks` entry is cleared on completion.

### Bell Feed summarization

`scheduleSummarization` (`:2893`) starts one `Task` per Feed row and never cancels it. Closing the Tab, Pane, Session or Window, and visiting the Tab (#0556), removes the row through `cleanUpBellState` (`WindowRuntime.swift:1262`) or the visit prune. The model turn still finishes, and `bellFeed.updateSummary` (`BellFeedStore.swift:333`) then no-ops because the row is gone. With capture on (#0523), the record is still written, with `feedRowText` nil. `summarizationTasksForTesting` holds the `Task` (it's populated in production too) until the next `scheduleSummarization` call prunes it by row membership (`:2934`). A row whose Tab closes is therefore a full model turn spent on a summary nobody can see.

## Effect

- **User:** none visible today. No stale or wrong names. A late write to a closed Tab's `aiSuggestedName` isn't rendered.
- **Resources:** an on-device model turn per in-flight request, finishing after the user closed what it was for. That means CPU and Neural Engine time plus memory for the `LanguageModelSession`. A Tab-name turn can also read up to two or three files in a folder the user has left. The worst case is closing a Window, or a Session with many Tabs, right after they all reported a new cwd, or right after a burst of bells. Cost scales with Tab count.
- **Maintenance:** every close path has its own list of teardown steps, and they disagree: #0559 (Bell cleanup missing from Close Other Tabs) and #0314's review round 1 (non-terminal teardown missing from `closeTab`/`removeSession`) were the same class of bug. The next per-Tab resource will be missed on some path too.

## Recommended fix

Add one per-Tab teardown funnel that every Tab-removal path calls, for example `WindowRuntime.tearDownClosedTabs(_ tabIDs: Set<UUID>)`. It should:

1. call `cleanUpBellState(forTabIDs:)`;
2. call `TerminalHostStore.shared.releaseTerminalView(forTabID:)` for each id (where the path doesn't already do it through `PaneRuntime`);
3. call a store-installed handler, `tabsClosedHandler: ((Set<UUID>) -> Void)?`, wired in the same two places as `reminderCancelHandler` (`AppStateStore.swift:431`, `:1335`). Its store side cancels `tabNameSuggestionTasks` for each id and cancels every summarization `Task` whose Feed row belongs to those Tabs.

Add a Session-level counterpart, called from `WindowRuntime.removeSession` and from the Window-close path, that cancels `nameSuggestionTasks[sessionID]`. Then drop the now-redundant cancels from the `AppStateStore.closeTab` / `removeSession` wrappers.

Call sites to route through the funnel: `WindowRuntime.closeTab`, `closeOtherTabs(in:keeping:)`, `closePane`, `removeSession`, and `RootWindowView.windowWillClose`. That last one becomes "for every Session in the Window, run the Session teardown", rather than its own list. The #0556 visit prune should also cancel the summarization `Task` for the rows it removes. Rows can be removed without the Tab closing, so the summarization cancel is best keyed by row id and called from wherever rows are removed, with the Tab funnel as one caller.

For summarization cancellation to be real, keep the `Task` handles in a production dictionary, not only in `summarizationTasksForTesting`. Cancellation already produces `NotificationSummarizationResult(failure: .cancelled)`, so #0523 capture records keep working.

Also guard `applySuggestedTabName` against a Tab that has left its Pane. The cancel should make this unreachable, but a check costs one lookup.

### Decisions

1. **Owner: `WindowRuntime` holds the funnel, the store holds the AI state.** All five structural steps live on `WindowRuntime`, and the store's wrappers aren't on most paths, so the funnel must be on `WindowRuntime`. It reaches the store through two new `@ObservationIgnored` hooks, the same shape as `reminderCancelHandler` (`WindowRuntime.swift:111`).
2. **The funnel covers per-Tab state that isn't structural: Bell rows and AI work.** It does not release terminal views or tear down non-terminal content. Those two steps belong to the structural removal. `closeTab` and `closeOtherTabs` release inside `PaneRuntime`, and the preview fallbacks rely on that. Moving release into the funnel would free surfaces before the Tab leaves `pane.tabs` on those two paths, for no gain. `docs/view-hierarchy.md` already documents release per path. The funnel always runs first, where `cleanUpBellState` runs today, so the order on every path becomes: funnel (Bell rows, then AI cancel), then release / content teardown, then structural removal. That keeps the existing Bell → release order exactly as it is.
3. **Summarization is cancelled from `BellFeedStore`, keyed by row id, not from the Tab funnel.** Rows leave the Feed in four ways: `removeEntries(matchingTabIDs:)` (Tab funnel *and* the #0556 visit prune), `removeReminderEntries(forSessionID:)`, and cap eviction in `record(_:)`. A store-installed hook in those three methods catches every one of them, including cap eviction (the issue doesn't mention it) and any future removal. The funnel gets summarization cancel for free through `cleanUpBellState`.
4. **The summarization registry becomes production state.** Rename `summarizationTasksForTesting` to `summarizationTasks`. On row removal the hook **cancels the handle and leaves it in the dictionary**. The existing membership prune in `scheduleSummarization` drops it on the next bell. This keeps the documented contract of `summarizationTaskForTesting(entryID:)` ("nil means never scheduled", `AppStateStore.swift:2911` doc and `docs/async-test-seams.md` §4), and the dictionary stays bounded by `BellFeedStore.cap` plus one batch.
5. **Session counterpart:** a `sessionClosingHandler: ((UUID) -> Void)?` hook, called from `removeSession` (which every Session-removal path reaches, cascades included) and from the new Window-close teardown. The store side calls `cancelNameSuggestion(forSessionID:)`. Then drop the now-redundant cancels from the `AppStateStore.closeTab` / `removeSession` wrappers.
6. **Window close becomes one `WindowRuntime` method**, `tearDownForWindowClose()`, holding today's `windowWillClose` steps 1–3 plus the AI cancels. `windowWillClose` calls it and keeps steps 4–6 (`releaseHost`, `unregisterNSWindow`, `removeWindow`). Unit tests can then run the real sequence instead of re-typing it (`CrossWindowBehaviorTests.swift:235` re-types it today). It does **not** call `removeSession` per Session. That would mutate `selectedSessionID` and fire `onAllSessionsClosed` → `closeWindowCallback` from inside `windowWillClose`. Reminder cancel and Reminder-row purge stay in `AppStateStore.removeWindow` (`:449`), unchanged.
7. **`applySuggestedTabName` guard: check that the Tab was released, not that it is still placed.** A placement lookup (`windows…locate(tabID:)`) would break the 11 `TabAutoNamingTests` that name detached `TabRuntime()`s that are in no Pane. `TerminalHostStore.releasedTabIDs` is the existing "this Tab closed" record. Every close path inserts into it, and #0535 already gates view creation on it. Add an internal `TerminalHostStore.isReleased(tabID:) -> Bool` and `guard !TerminalHostStore.shared.isReleased(tabID: tab.id)` as the first line of `applySuggestedTabName`. `applySuggestedName` (Session) already looks the Session up and needs nothing.
8. **Skip the model when cancelled before start.** Both naming `Task` bodies get `guard !Task.isCancelled else { return }` as their first statement, before `await suggester.suggestName`. A close in the same main-actor turn as the `cd` report then never builds a `LanguageModelSession` or reads a file. Summarization gets no early return, so the #0523 capture log still writes one `summary` record per scheduled summarization (status `cancelled`).
