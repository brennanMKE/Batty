# 0564 — `theRealEnumeratorPrefersTheLongestRunningProcessOfAName` still flakes under load after #0516, because it compares two separate live process-table walks

| | |
|---|---|
| **Status** | open |
| **Module** | Testing / Process Status pane |
| **Platform** | macOS |
| **First seen** | 2026-11-05 |

## Description

`ProcessFollowByNameTests.theRealEnumeratorPrefersTheLongestRunningProcessOfAName()` failed again during a full `./build.sh unit` run (3313 tests) on `issue/0561`. That branch doesn't touch `ProcessInspector` or this suite. The suite passed alone (30 tests), and a full re-run passed. The failure is the same one #0516 recorded on 2026-10-14. The #0516 fix (`86c022fc`, retry `allPids()` on a saturated buffer) has been on `main` since then, so buffer saturation was not the only cause, or not the cause at all.

The test calls the real enumerator twice, back to back, against the live host process table. It expects both walks to see the same two `sleep` children. Under a full parallel unit run the host process table churns heavily (the failing pid, 99870, sits just under macOS's pid ceiling of 99998, so pids were about to wrap). The second walk found neither child, even though the first walk had just listed both.

It does not break the letter of `AGENTS.md` "Asynchronous tests": it has no sleeps, no polling and no timing assertions. It does depend on global, unsynchronized host state that parallel tests mutate, which is the same source of unreliability that rule exists to remove. `firstSameUserProcess(named:)`'s ordering can be proved with no real processes. One real-process smoke test can stay, but it must not compare two snapshots.

The failure may also point at a real production gap. `allPids()` returns `[]`, without logging, when either `proc_listallpids` call returns `<= 0`. Callers can't tell a failed syscall from "no processes", so a Mode C pane would briefly report Waiting for a running process, as #0516 described.

## Evidence

- Check log `build/checks/unit-20261105-163643-95788.log`, branch `issue/0561` (only this test's lines were read):
  ```
  ✘ Test theRealEnumeratorPrefersTheLongestRunningProcessOfAName() recorded an issue at ProcessFollowByNameTests.swift:675:9: Expectation failed: ProcessInspector.firstSameUserProcess(named: name) == listed.first?.id
  ↳   ProcessInspector.firstSameUserProcess(named: name) → nil
  ↳   listed.first?.id → 99870
  ✘ Test theRealEnumeratorPrefersTheLongestRunningProcessOfAName() failed after 37.537 seconds with 1 issue.
  ```
  Only one issue was recorded. So `listed.count == 2` (`:674`) and `listed.first?.id == older.processIdentifier` (`:676`) both passed. Both children were alive and correctly named in the first walk, and the first walk ordered them correctly. Only the second walk (`firstSameUserProcess`) came back empty, and it missed **both** pids at once. The "37.537 seconds" duration is shared by many unrelated tests on neighbouring log lines, so it reflects batched result reporting on a loaded host, not this test's own runtime.
- Earlier occurrence: #0516, `Test-Batty (Beta)-2026.10.14_17-52-06--0700.xcresult`, same line and the same shape (`→ nil` against `listed.first?.id → 2505`).
- The test (`BattyKit/Tests/BattyKitTests/ProcessFollowByNameTests.swift:655-677`) spawns two copies of a uniquely named `/bin/sleep 300` through `ChildProcessFixture`. It then calls `ProcessInspector.allSameUserProcesses()` and `ProcessInspector.firstSameUserProcess(named:)`. Each call does its own `allPids()` walk plus its own `proc_pidinfo(PROC_PIDTBSDINFO)` per pid (`BattyKit/Sources/BattyKit/Runtime/ProcessInspector.swift:377-412`). Nothing ties the two walks to one snapshot.
- `allPids(listAllPIDs:)` (`ProcessInspector.swift:473-507`) has two silent empty returns: `guard probeCount > 0 else { return [] }` and `guard actualCount > 0 else { return [] }`. Neither logs `errno`. `bsdInfo(pid:)` (`:509-517`) likewise maps any `proc_pidinfo` failure to `nil`. Losing both pids at once fits a whole-walk failure (an empty `allPids()`) better than two independent per-pid failures. But nothing in the code or the log can show which happened, because neither path records anything.
- No test in `BattyKit/` sends a group signal (`killpg`, `kill(-pgid)`, `kill(0, …)`, `pkill`, `killall`). `ChildProcessFixture` kills only its own `Process` objects. A stray kill of both children is therefore unlikely, but a stale-pid `kill` from another suite after pid reuse can't be ruled out completely.
- The sibling test `theRealEnumeratorFindsAUniquelyNamedProcessAndItsReplacement()` (`:615-653`) has the same exposure. It asserts `firstSameUserProcess(named:) == first.processIdentifier` right after the spawn, against a live walk.

## Steps to reproduce

1. Run `./build.sh unit` (the full suite) on a busy host, ideally with other builds running.
2. It fails rarely: once in about ten runs on 2026-10-14, and once on 2026-11-05. `./build.sh unit ProcessFollowByNameTests` on its own passes.

## Expected behavior

The test passes regardless of host load, and the ordering logic is proved deterministically.

## Actual behavior

On a loaded host, `firstSameUserProcess(named:)` sometimes returns `nil` microseconds after `allSameUserProcesses()` listed both children.

## Notes

Recommended fix, for the planner to confirm:

1. **Make the ordering test pure.** Split `firstSameUserProcess(named:)` into the live walk and a pure selection over records, e.g. `static func firstProcess(named:in: [RunningProcess]) -> pid_t?`, which uses `RunningProcess.listOrder`. Then test "longest-running, then lowest pid" with synthetic records: equal start seconds with different microseconds, equal start times with different pids, and case-sensitive name matching. The existing `allPids(listAllPIDs:)` seam plus an injected per-pid `bsdInfo` reader would also work. The pure split is smaller and needs no fake `proc_bsdinfo`.
2. **Keep one real-process smoke test, with a single walk per assertion.** Spawn the two children, then assert only `firstSameUserProcess(named: name) == older.processIdentifier`. That is one enumeration, compared against the pid the test owns, with no second snapshot to disagree with. Apply the same pattern to `theRealEnumeratorFindsAUniquelyNamedProcessAndItsReplacement`. Don't add a retry or a poll to the test: that would be "passing by waiting".
3. **Make the production failure visible.** In `allPids(listAllPIDs:)`, log `errno` when the probe or the fill returns `<= 0` instead of returning `[]` silently. Consider retrying the walk once in that case, or returning an optional, so that `firstSameUserProcess(named:)` and the Mode C sampler can treat a failed walk as "unknown, keep the current state" rather than "process gone". The fake-`listAllPIDs` tests in `ProcessInspectorAllPidsTests` can cover this deterministically. If the smoke test in step 2 ever fails again, the new log line will show whether the walk failed or the children really vanished.
4. #0516 is still `open` on `main`, although its fix `86c022fc` landed on 2026-10-14. That issue's claim that "the test is correct and the code under it is wrong" no longer holds on its own: the test still fails with that fix in place. Whoever works this issue should reconcile the two, and should not close #0516 (only the user closes issues).

Related: #0516 (allPids saturation retry), #0494 and #0498 (follow-by-name and its tests), `docs/async-test-seams.md`.
