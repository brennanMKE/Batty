## Description

Cmd-V of any multi-line clipboard content (e.g. a wrapped shell command copied from another terminal) brings up a "Paste N lines?" confirmation sheet before the bytes reach the terminal. Stated reaction: "I hate this. It should just paste without this confirmation."

The behavior is intentional — `SettingsPreference.defaultPasteStrictness` defaults to `PasteStrictness.alwaysOnMultiline`, which prompts whenever the clipboard contains a newline. A user can change this via Settings → Paste Confirmation → "Never confirm", but the default friction is unwelcome.

## Steps to reproduce

1. Copy a multi-line command from anywhere (e.g. the wrapped `xcodebuild ... Debug ...` line shown in the attached screenshot).
2. Click into a Batty terminal pane and press Cmd-V.

## Expected behavior

The clipboard contents are pasted into the terminal immediately, without a confirmation sheet.

## Actual behavior

A "Paste N lines?" sheet appears with Cancel / Paste buttons, requiring an extra click before the paste lands.

## Notes

- Three modes exist (`alwaysOnMultiline`, `onShellMetacharacters`, `never`) — see `BattyKit/Sources/BattyKit/SettingsPreferences.swift:85`.
- `onShellMetacharacters` is a tempting middle ground, but it still blocks ordinary multi-line pastes containing `;` or `&&` (very common in shell one-liners), so it would surprise users who reach for Batty exactly to paste a sequence of commands. `.never` matches Terminal.app / iTerm2 default behavior.
- Users who want the safety net can flip Settings → Paste Confirmation back to "Always confirm multi-line" or "Confirm only with shell metacharacters" — the picker and persisted-key wiring are unchanged.

## Root cause

`SettingsPreference.defaultPasteStrictness` was set to `PasteStrictness.alwaysOnMultiline.rawValue`, so a fresh install would prompt on every paste containing a newline (`text.contains("\n")` in `PasteStrictness.shouldConfirm`). The default was conservative for a v1 ship; in practice it intercepts ordinary multi-line shell command pastes that the user expects to land directly.

## Fix

Switch the default to `PasteStrictness.never.rawValue` so first-launch users get zero-friction pastes — matching Terminal.app and iTerm2. The picker, the `pasteStrictnessKey` UserDefaults entry, and the three-mode enum stay untouched; users who already chose a strictness keep their setting, and anyone who wants the prompt back can re-select it in Settings → Paste Confirmation.

Also realigned the parse-failure fallback in `resolvedPasteStrictness()` from `.alwaysOnMultiline` to `.never` so the behavior is consistent if `UserDefaults` ever contains an unrecognised rawValue.

## Files changed

- `BattyKit/Sources/BattyKit/SettingsPreferences.swift` — `defaultPasteStrictness` now `PasteStrictness.never.rawValue`; `resolvedPasteStrictness()` fallback realigned to `.never`.
