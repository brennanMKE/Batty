## Description

`ProcessInspector.isAlive(pid:)` is implemented as `bsdInfo(pid: pid) != nil`. `bsdInfo` fails — returns `nil` — on both `ESRCH` (the pid no longer exists) and `EPERM` (the pid exists but this process cannot read it). So `isAlive` answers `false` for a live root-owned process, which is exactly the case `ProcessInspector`'s own error model was built to distinguish: its `InspectionError` maps `ESRCH` → `.processNotFound` and `EPERM` → `.permissionDenied` as separate outcomes, and `ProcessStatusPaneContent` treats them as distinct states (`.exited` vs `.permissionDenied`).

There is **no production caller today** — the sampling path uses `coreMetrics` and gets the three-way distinction through `InspectionError` — so this is a latent trap, not a live bug: the first future caller that uses `isAlive` for its obvious purpose ("is this pid still around?") will misclassify privileged processes as exited.

The issue's job is a decision, not just a patch. Two acceptable resolutions:

1. **Delete `isAlive`.** No caller exists; the `Result`-based API already answers the question correctly. Cheapest, and removes the trap entirely.
2. **Make it three-valued** (alive / gone / alive-but-unreadable — or return the existing `InspectionError` via `Result<Void, InspectionError>`), so the signature cannot express the conflation.

A doc comment warning is *not* an acceptable resolution — the method name promises a boolean answer the syscall cannot deliver.

## Root cause

`isAlive(pid:)` was `bsdInfo(pid:) != nil`, and `bsdInfo` returns nil for both `ESRCH` and `EPERM`. Its only caller was its own test. The Process Status pane's sampling already distinguishes the cases through `coreMetrics` (`SampleFailure.permissionDenied` vs `.processNotFound`).

## Fix

Deleted `isAlive(pid:)` and `ProcessInspectorTests.isAliveDistinguishesARealPidFromABogusOne`. The private `bsdInfo(pid:)` helper stays (still used by `children(ofPid:)` and `allSameUserProcesses()`).
