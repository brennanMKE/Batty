## Description

Child of #0646. An agent working in some other project, inside a Batty Pane, has no way to find out it is in Batty or how to drive it. The guidance exists, but only in this repo, and it is stale. Add three things: a built-in stdio MCP server (`batty mcp`), the agent guidance packaged in the app bundle with a one-step installer, and a short snippet Batty can offer to add to a project's `AGENTS.md`/`CLAUDE.md`.

Feature request from the user (Brennan), 2026-11-17.

### Current state (checked against `main` at `3b5735c3`)

- **Per-verb schemas already exist.** `batty capabilities --json` emits `verbs[]`, each with an MCP-shaped `inputSchema` (`CapabilitiesVerbPayload.inputSchema`, `BattyKit/Sources/BattyXPCCore/CapabilitiesPayload.swift`; property shape in `CapabilitiesInputSchemaPayload.swift`, #0402). The verb roster is walked from `BattyCLI.configuration.subcommands` (`CapabilitiesCommand.swift`), and each command supplies its schema through `CapabilitiesDescribable`. The schemas are hand-authored per command, not derived from ArgumentParser, and `CapabilitiesInputSchemaTests`' Mirror-based drift oracle keeps them honest. Each property carries Batty-specific keys beyond JSON Schema (`cliKind`, `names`, `enumValueNames`, `cliRequired`) that say how to spell it on a command line, and each schema has a `conflicts` list of cross-parameter constraints (`CapabilitiesConstraintPayload`). Each verb also carries MCP-style `annotations` (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`; `CapabilitiesAnnotationsPayload`). The verb roster today: `new`, `ping`, `status`, `list`, `session info|focus|close|remind`, `pane split|close|focus|hide|show`, `tab focus`, `project list|open`, `id`, `notify`, `capabilities`.
- **The CLI talks to the app** over a launchd broker plus a direct anonymous XPC endpoint (`docs/batty-cli-design.md` §1.3); `batty new` uses the `batty://` URL scheme. The CLI binary ships at `Contents/Resources/bin/batty` and is symlinked to `/usr/local/bin/batty` (Prod) or `batty-beta` (Beta) (`docs/batty-cli-install.md`).
- **The skill** is `.claude/skills/batty-cli/SKILL.md` plus `install.sh` (#0403, #0404). `SKILL.md` line 8: "Authored against Batty CLI `1.1.0`"; the app is `1.4.0`. Its frontmatter lists the four status-view kinds but not, for example, `project`, `session remind` or `session close` changes made since. `install.sh` copies into Claude Code, OpenCode, Cursor and Codex skill directories. The only way to get it is the `git clone --branch v<version>` recipe plain-text `batty capabilities` prints (`CapabilitiesCommand.skillInstallLines`). The app bundle carries no copy.

## Expected behavior

### 1. `batty mcp`: a stdio MCP server

- `batty mcp` (or the name the user picks; see Open questions) speaks MCP over stdin/stdout and exposes **one tool per CLI verb**.
- Each tool's `name`, `description`, `inputSchema` and `annotations` are generated at runtime from the same `CapabilitiesVerbPayload` list `batty capabilities --json` builds. There is no second, hand-maintained tool list, so the tools cannot drift from the CLI. The Batty-specific property keys are either stripped or kept as JSON Schema annotations; the `tools/list` output must validate against the dialect `CapabilitiesPayload.jsonSchemaDialect` declares.
- A tool call runs the same code path as the matching CLI verb (same validation, same XPC request, same exit-code meaning), and returns the verb's `--json` output where it has one. A non-zero exit maps to an MCP tool error carrying the exit code and stderr text.
- Verbs that only make sense for a human or that would recurse (`mcp` itself, the installer verb below) are not exposed as tools.
- Target resolution follows the existing order (explicit flag, then `BATTY_*` environment, then focused element). An MCP server launched by an agent inside a Batty Pane inherits that Pane's `BATTY_*` environment, so "my Pane" keeps working.
- New verbs added later (including #0648's `server` verbs) become tools with no MCP-specific work.

### 2. Guidance shipped with the app

- The app bundle carries the current agent guidance: the `batty-cli` skill (updated, see 3) and an MCP server entry pointing at the bundled CLI, packaged as a **Claude Code plugin**.
- `batty agent install` (name to be confirmed) and a Settings button install it for the detected agent hosts. For Claude Code this installs the plugin; for the other hosts `install.sh` already covers, it installs the skill and, where the host supports MCP, the server entry. A `--dry-run` shows what would change. Re-running is safe and upgrades in place. Nothing is installed without the user running the command or pressing the button.
- Prod and Beta install under names that do not collide, and each points at its own CLI (`batty` vs `batty-beta`).
- The `batty capabilities` plain-text install recipe points at the bundled installer instead of a `git clone`.

### 3. The skill is brought up to date

- `SKILL.md`'s "authored against" and minimum versions are updated to the current CLI, and its recipes are re-checked against the live `inputSchema` of every verb.
- It teaches the new rule once #0648 ships: **when you start a dev server, start it with `batty server start`, or `batty server attach` it if it is already running. Do not open a browser yourself. Let Batty place the Server Pane where the user's Settings say; pass `--split` only when the user asked for a specific placement.**
- `docs/batty-cli-agent-workflows.md` gets the same rule and an MCP section.

### 4. Project snippet

- Batty can offer to add a short block to a project's `AGENTS.md` (or `CLAUDE.md` when that is the file the project uses) telling agents they run inside Batty, that `batty`/`batty-beta` is on `PATH`, and to use it to show servers and status. The offer comes from the installer verb (for example `batty agent install --project DIR`) and from Settings. It never edits a file without the user confirming. It is idempotent: a marked block is replaced, not duplicated.

## Acceptance criteria

- `batty mcp`'s `tools/list` lists exactly the verbs `batty capabilities --json` lists (minus the excluded ones), with identical parameter names, types and enums. A unit test pins this against the capabilities payload, so a verb added to the CLI without a tool, or the reverse, fails the test.
- A unit test drives `initialize`, `tools/list` and one `tools/call` (for example `id` or `capabilities`, which need no running app) through the stdio transport, using piped handles and awaited replies, with no sleeps (`AGENTS.md`, "Asynchronous tests").
- The app bundle contains the plugin and skill. `batty agent install --dry-run` lists the destinations for each detected host. A real install followed by a fresh Claude Code session in an unrelated directory shows the skill and the Batty MCP tools.
- `SKILL.md` no longer says `1.1.0`, and every recipe in it works against the current CLI.
- The snippet offer writes a marked block once and replaces it on re-run.

## Open questions

1. **Grammar.** `docs/batty-cli-design.md` §4 keeps the noun set to session/pane/tab/window (plus the approved `project`). Is `batty mcp` acceptable as a top-level verb, and is the installer `batty agent install`, `batty mcp install`, or something else?
2. **Plugin install mechanism.** Install the bundled plugin through Claude Code's own plugin commands (for example, registering the bundle's plugin directory as a local marketplace), or write the skill and an MCP entry into `~/.claude` directly? The first keeps Claude Code in charge of enable/disable; the second needs no `claude` binary on `PATH`. The plugin path inside a signed, notarized bundle must stay read-only; check whether the host copies it or references it in place, since an app update replaces the bundle.
3. **Schema fidelity.** Strip the Batty-only keys from `inputSchema` for MCP, or keep them? Cross-parameter conflicts (`CapabilitiesInputSchemaPayload.conflicts`) have no first-class MCP field (#0402); fold them into the tool `description`?
4. **Which verbs are tools.** Should `new` (one-way, URL scheme, no acknowledgement) be a tool, given it cannot report success the way XPC verbs do?
5. **Snippet wording and location.** The exact text, and whether to prefer `AGENTS.md` when both files exist (this repo's `CLAUDE.md` just imports `AGENTS.md`).
6. **Settings placement** of the install button and the snippet offer.

## Root cause

Feature work. The starting state: Batty had no MCP server, the `batty-cli` skill lived only in this repo (and said `1.1.0`), and the only install path was a `git clone` of a release tag. An agent outside the repo had no way to learn it was inside Batty.

## Fix

Followed the four plan steps, one commit each (`b5a2c333`, `0e83ff39`, `4fa72fe1`, `2e6af0ea`).

1. **Flag and `batty mcp`.** `FeatureFlags.agentIntegration` (on in Beta) plus `FeatureFlags.current` for the CLI. `BattyCLI.subcommands(for:)` adds `MCPCommand` and `AgentNounCommand` only with the flag on. `MCPToolCatalog` turns `capabilities` verbs into tools (decisions 6 to 9). `MCPServer` (actor) speaks newline-delimited JSON-RPC (decision 10). `SubprocessToolRunner` re-executes the same binary.
2. **Bundle, installer, snippet.** New "Embed Agent Guidance" build phase (`26B100060000000000000006`, after Embed Broker). `AgentGuidanceIdentity`, `AgentGuidanceInstaller` and `ProjectAgentSnippet` in `BattyCLICore`. `batty agent install [--dry-run] [--project DIR] [--yes]`.
3. **Settings.** `AgentIntegrationModel` and an "AI Agents" section after "Command-Line Tool", with `DialogButtonRow` confirmation sheets (#0654 convention).
4. **Skill and docs.** SKILL.md authored against `1.5.0`, new §9 on MCP, `agent install` as the preferred refresh. Docs, `Concepts.md` and `docs/feature-flags.md` updated.

Divergences from the plan:
- **Claude Code re-runs.** Probed with a temporary `CLAUDE_CONFIG_DIR` and `HOME`: `claude plugin marketplace add` on an existing marketplace and `claude plugin install` on an installed plugin both exit 0 and load in place. So the installer always runs add then install; there are no `marketplace update` / `plugin update` branches.
- **Strict-JSON miss is `manual`, not a failure.** A Cursor or OpenCode config that isn't strict JSON is left untouched and reported as a manual step with the entry to paste (outcome `.manual`), so it doesn't fail the install.
- **Config files are backed up and numbers kept exact.** Merged MCP configs are read and written as Codable JSON with `Decimal` numbers, so `0.2` stays `0.2`, and the previous file is copied to `AgentGuidanceBackups/<stamp>/<host>/` first. The plan didn't ask for either; see Gotchas for why.
- **Home directory.** The CLI and the Settings model use `$HOME` before `homeDirectoryForCurrentUser`, which ignores `$HOME`.
- **No injected `FileManager`.** The installer uses `FileManager.default` against injected directories; tests use temp trees.
- **App Support folder** is `Batty` / `Batty Beta` (`SessionNameCache.resolvedDirectoryName`), the per-variant naming the plan pointed at, not the bundle id.
- **`AgentSkillFlagDriftTests`** now builds its verb table with the flag on, so `agent install --dry-run` in SKILL.md is checked rather than rejected.
- **Unparseable input / EOF.** On stdin EOF the server cancels in-flight calls, and cancelled calls get no reply (MCP cancellation rule).

### Premises checked

- **Verb roster** in "Current state" matches `BattyCLI.configuration.subcommands` today (19 leaf paths, `CapabilitiesCommand.leafArchetypeByVerbPath`).
- **Stale premise:** Open question 4 says `new` "cannot report success". Since #0380 `batty new` confirms the new Session over XPC and prints `sessionID`/`paneID` (`--json`), unless `--no-wait`. So `new` can be a tool.
- `SKILL.md` line 8 says `1.1.0`. `MARKETING_VERSION` is `1.4.0` (`Configuration/App.xcconfig:49`). Confirmed.
- **No CLI flag plumbing today.** `FeatureFlags` has only `sharedProjectImages`, and has no CLI `current`. `BattyCLI.subcommands(for:)` was removed with the Projects flag (#0504). Both come back here, following the #0477 precedent (`git show 6f4acab8`).
- **Property keys are kebab-case CLI names** (`"no-wait"`, `"include-dimensions"`). They are valid MCP property names as they are. Every verb has **at most one positional** property today. The argv builder relies on that, and a test pins it.
- `CapabilitiesPropertyPayload.defaultValue` is always a string (`"false"` for booleans), so the MCP translation must re-type it.
- **Bundle reads.** The CLI binary has no `Info.plist`. It finds its bundle from `Bundle.main.executableURL` three levels up (`resolveAppVersion()`, `SessionCommand.swift:18`). The installer finds `Contents/Resources/AgentGuidance/` the same way.
- **`claude` plugin CLI**, checked on this host's `claude plugin --help`: `plugin marketplace add <path>`, `marketplace update [name]`, `plugin install <plugin>@<marketplace>` (default scope `user`, `--json`), `plugin update`, `plugin validate <path>`. `CLAUDE_CONFIG_DIR` points Claude Code at another config root, which the implementer uses to probe safely (see Step 2).
- **Restricted areas: none needed.** Embedding goes through a new build phase in `Batty.xcodeproj/project.pbxproj`, which is not restricted. `scripts/release.sh` archives through `xcodebuild`, so it runs the new phase unchanged. `Configuration/Build.xcconfig` is untouched. The app target already has `ENABLE_USER_SCRIPT_SANDBOXING = NO`, and the phase still declares its input and output paths.

### Decisions (open questions 1–6, plus ones the issue implies)

1. **Grammar: `batty mcp` and `batty agent install`.** `mcp` is a top-level app-level verb like `capabilities`, not a noun. `agent` is a new noun with one verb, `install`. `batty mcp install` would wrongly suggest it installs only the MCP entry, when it also installs the skill and the project snippet. `docs/batty-cli-design.md` §1.1 records `agent` as an approved sixth noun scoped to agent integration, with the same "deliberate" wording `project` got. *Needs user sign-off at review; renaming is a mechanical change.*
2. **Plugin install mechanism: Claude Code's own plugin commands, from a user-owned copy.** The bundle is read-only and Sparkle replaces it, so Claude Code never references it. `batty agent install` stages a local **marketplace** at `~/Library/Application Support/<app bundle id>/AgentPlugin/` (the same per-variant folder naming as `ProjectStore`/`SessionNameCache`). It then runs `claude plugin marketplace add <dir>` (or `marketplace update <name>` when already added) and `claude plugin install <plugin>@<marketplace>` (or `plugin update` when already installed). Claude Code keeps enable/disable. The app looks for `claude` on `PATH`, then in `~/.local/bin`, `~/.claude/local`, `/opt/homebrew/bin` and `/usr/local/bin`, because a launchd-started app's `PATH` lacks `~/.local/bin`. If `claude` isn't found, the installer stages the marketplace anyway and prints the two exact commands for the user to run. It doesn't write into `~/.claude` behind Claude Code's back.
3. **Plugin manifests are generated at install time; the bundle carries the guidance source.** The bundle carries `Contents/Resources/AgentGuidance/skills/batty-cli/SKILL.md`, copied from `.claude/skills/batty-cli/SKILL.md`, which stays the single source. The installer writes `marketplace.json`, `plugin.json` and `.mcp.json` into the staged marketplace. This keeps every variant, version and absolute-path decision in tested Swift, and keeps per-machine paths out of the signed bundle. The acceptance line "the app bundle contains the plugin and skill" is met as "the skill, plus everything needed to generate the plugin". *Flag at review if the user wants a literal static plugin tree in the bundle.*
4. **Prod/Beta names never collide:**

   | | Prod | Beta |
   |---|---|---|
   | marketplace | `batty-local` | `batty-beta-local` |
   | plugin and MCP server key | `batty` | `batty-beta` |
   | Claude Code skill | `batty-cli` (namespaced `batty:batty-cli`) | `batty-cli` (namespaced `batty-beta:batty-cli`) |
   | skill dir for other hosts | `batty-cli` | `batty-beta-cli` (frontmatter `name:` rewritten when staged) |
   | MCP `command` | absolute path of that variant's bundled `Contents/Resources/bin/batty`, resolved when installing | same |

   The MCP `command` is never the `PATH` symlink, which may not be installed. Moving the app means re-running install, which the output says.
5. **Other hosts (Codex, Cursor, OpenCode), using the same detection rules as `install.sh`.**
   - **Skill:** copied to the same global dirs `install.sh` uses (`~/.config/opencode/skills`, XDG-aware; `~/.cursor/skills`; `$CODEX_HOME/skills` and `~/.agents/skills`). It is not copied to `~/.claude/skills`, because Claude Code gets the plugin.
   - **MCP entry, Cursor and OpenCode:** written only into **strict-JSON** config files (`~/.cursor/mcp.json` → `mcpServers.<key>`; `<XDG>/opencode/opencode.json` → `mcp.<key>` as `{"type":"local","command":[cli,"mcp"],"enabled":true}`). Only Batty's own key is replaced. A file that doesn't parse as strict JSON (for example JSONC) is left untouched, and the entry is printed instead.
   - **MCP entry, Codex:** printed as a TOML block, never written, because Foundation can't round-trip TOML safely.
   - The repo's `install.sh` stays as the git-clone path and is not changed.
6. **Schema fidelity:** for MCP, strip the Batty-only keys (`cliKind`, `names`, `enumValueNames`, `cliRequired`, and the object-level `conflicts`). Keep `type`, `description`, `enum`, `minimum` and `default`, with `default` re-typed to the property's JSON type, plus the object `required` array. Each `conflicts[].description` is appended to the tool `description` as a "Constraints:" list. The Batty keys are still what builds argv; they just aren't sent.
7. **The `json` property is not a tool parameter.** Every tool call passes `--json` when the verb has a `json` property, unless the call sets a parameter that a `mutuallyExclusive` conflict pairs with `json` (`new`'s `no-wait`). That rule is generic over `conflicts`. The acceptance test pins "identical parameter names, types and enums" **except `json`**.
8. **Which verbs are tools:** every verb `batty capabilities --json` lists, except `MCPToolCatalog.excludedVerbPaths = ["mcp", "agent install"]`. `new`, `id` and `capabilities` are included. #0648's `server …` verbs become tools with no MCP-specific code. Tool name = verb path with spaces → `_` (`pane_split`), which satisfies MCP's `^[A-Za-z0-9_.-]{1,64}$`.
9. **Tool execution: re-exec the same binary.** A `tools/call` runs `Bundle.main.executableURL` (the very `batty` serving MCP) as a child process. The child gets the built argv, inherits the server's environment (so the Pane's `BATTY_*` reach it) and its cwd. Validation, XPC, exit codes and stdout are therefore the verb's own, with no second code path. Commands print with `print`/`fputs` and throw `ExitCode`, so running in-process would need stdout capture, which is the wrong trade. Argv form:
   - options as `--long=value`, so a value starting with `-` is safe;
   - boolean flags present only when `true`;
   - an enum-flag as its `enumValueNames[value].last`;
   - the positional last, after `--`.

   Result mapping:
   - exit 0 → `content:[{type:"text", text: stdout}]`;
   - non-zero → `isError: true`, with text `exit <code>: <meaning from CapabilitiesPayload.exitCodes>` followed by stderr, then stdout when non-empty (`status --json` reports failures on stdout).

   No `structuredContent` and no `outputSchema`: verbs have no declared output schemas yet.
10. **Protocol scope:** newline-delimited JSON-RPC 2.0 on stdin/stdout, with nothing else ever written to stdout (diagnostics go through `Logger`). It handles:
    - `initialize`: echoes the client's `protocolVersion` if supported, else answers with the latest. The supported set is `["2026-07-28", "2025-11-25", "2025-06-18", "2025-03-26"]`, newest first; 2026-07-28 is the revision #0402 shaped against. `capabilities: {tools: {listChanged: false}}`, `serverInfo {name: <plugin key>, version: cliVersion}`, and a short `instructions` string (you may be inside Batty; tools mirror the CLI; omitted targets resolve to your own Pane via `BATTY_*`).
    - `notifications/initialized`, ignored.
    - `ping` → `{}`.
    - `tools/list`, no pagination.
    - `tools/call`.
    - `notifications/cancelled`, which terminates that call's child process.

    Unknown method → `-32601`, unparseable line → `-32700` (id `null`), unknown tool name → `-32602`. Argument validation failures (unknown key, wrong JSON type, value outside `enum`, missing `required`) come back as `isError` tool results, so the model can correct itself. Notifications never get replies. `serve` returns on stdin EOF, after cancelling in-flight calls.
11. **Feature flag `agentIntegration`, on in Beta, off in Prod.** Per `AGENTS.md` "Release branches", #0646 is unfinished until all three children land. It gates three things: the `mcp`/`agent` CLI verbs (absent from the tree, so absent from `--help`, `capabilities` and MCP), the Settings section, and the capabilities install recipe. Bundling `SKILL.md` stays unconditional, because a file nothing reads is inert. Remove the flag in the release that ships #0646. #0648/#0649 may reuse this flag instead of adding their own; **if a sibling lands a different flag first, the implementer merges onto it** (orchestrator's call).
12. **Project snippet.**
    - **File choice:** `AGENTS.md` when it exists and either there's no `CLAUDE.md` or `CLAUDE.md` contains `@AGENTS.md`. Else `CLAUDE.md` if it exists (Claude Code wouldn't see an un-imported `AGENTS.md`). Else create `AGENTS.md`.
    - **Block:** delimited by `<!-- batty:begin -->` / `<!-- batty:end -->`, with one shared marker for both variants. Re-running replaces the block. Text outside the markers is preserved byte for byte. A file with an unmatched marker is refused, not edited.
    - **Wording:** variant-neutral, since project files are shared through git:
      - "This project is often worked on inside Batty (macOS terminal multiplexer). When `BATTY_PANE_ID` is set you are in a Batty Pane; drive Batty with `batty` (`batty-beta` in Batty Beta) — run `batty capabilities` first."
      - Show status in Batty Panes (`batty pane split --view git-status --unique`) rather than printing it.
      - Use `batty notify` to get the user's attention.
      - The `server` rule, **only if #0648 has merged** by implement time (see Step 4).
