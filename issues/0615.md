# 0615 — BattyCommands finds its target window through untracked state, so menu enablement can stay stale after a key-window change

| | |
|---|---|
| **Status** | open |
| **Module** | App / Window |
| **Platform** | macOS |
| **First seen** | 2026-11-12 |
| **Priority** | medium |

## Description

**HIGH. Related to #0601.** The main-menu `BattyCommands` body resolves "the key content window" through `store.keyWindowOrFirstRegistered()`, which reads `NSApp.keyWindow` and the `@ObservationIgnored` `nsWindowMap`, `recentlyKeyWindowIDs` and `windows`. None of that is observed, so switching key between two content windows, or opening or closing one, invalidates nothing: menu enablement and labels (Pane commands disabled on `allPanes.count != 1`, the Projects menu's open checkmarks) stay computed for the previous target until some unrelated observed write re-runs the body. At the same time the body over-tracks: it re-runs on every bell (#0609), every divider tick (#0607) and every Session switch. Its own doc comment (`BattyCommands.swift:63-71`) already acknowledges the staleness.

## Current state (verified 2026-11-12 on `main` `ce66ca6a`)

- `BattyKit/Sources/BattyKit/Commands/BattyCommands.swift:61`: `private var keyWindow: WindowRuntime? { store.keyWindowOrFirstRegistered() }`.
- `Runtime/AppStateStore.swift:1199-1201` (`keyWindowOrFirstRegistered` → `defaultTargetWindow()`), `:1097-1101` (`keyWindowRuntime` reads `NSApplication.shared.keyWindow` and `nsWindowMap`), `:300`, `:308`, `:360` (`nsWindowMap`, `recentlyKeyWindowIDs`, `windows` are all `@ObservationIgnored`).
- `BattyCommands.swift:73-78` (`projectFileMenu` reads `store.openProjectIDs`), `AppStateStore.swift:1509-1511` (`openProjectIDs` iterates the ignored `windows`; it does track each existing window's `sessions` and `projectID`, but not window add/remove).
- Enablement/labels from `keyWindow`: `BattyCommands.swift:224`, `:514` (`.disabled(keyWindow?.selectedSession?.tree.allPanes.count != 1)`), `:692`; Bell Feed: `:326`.

## Rule violated

- `docs/swiftui-observation-rules.md`, "Two-way model ↔ AppKit sync": one authority per fact. Here "which content window is key" lives only in AppKit and in ignored bookkeeping.
- swift-guidance `swiftui-observation.md`: a fact a view depends on must be observed; computed reads through ignored state under-track.

## Evidence

- **Proven:** the reads are untracked (key window) or broad.
- **Inferred:** that the staleness is user-visible. Check manually or in the VM: two windows with different Pane counts, switch key, open the Pane menu.

## Fix direction

- Add an observed `keyContentWindowID: WindowID?` on `AppStateStore`, written only by `handleWindowDidBecomeKey` and window unregister (event-origin, `Equatable`, write only on change). `keyWindowOrFirstRegistered()` reads it first. Or publish the `WindowRuntime` with `.focusedSceneValue` and read `@FocusedValue` in `BattyCommands`.
- Then read narrow facts in the body (e.g. a per-window `paneCount`), so bells and divider ticks don't re-run the menu (#0607, #0609 cover the broad sources).

## Tests

- New in `AppStateStoreFocusTests` or a new `KeyContentWindowObservationTests`: `keyWindowChangeNotifiesKeyContentWindowReaders()` — two registered windows, post `didBecomeKey` for the second; `withObservationTracking` on the key-window read must fire (fails before: nothing observed changes). `unregisteringTheKeyWindowNotifiesReaders()`. `sameWindowBecomingKeyAgainDoesNotNotify()`.
- Keep passing: the #0439 default-target-window tests, `MultiWindow*` unit tests.
- UI, at the daily VM run: `BattyUITests/MultiWindowTests`, `AuxiliaryWindowShortcutTests`.
