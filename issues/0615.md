## Description

**HIGH. Related to #0601.** The main-menu `BattyCommands` body resolves "the key content window" through `store.keyWindowOrFirstRegistered()`, which reads `NSApp.keyWindow` and the `@ObservationIgnored` `nsWindowMap`, `recentlyKeyWindowIDs` and `windows`. None of that is observed, so switching key between two content windows, or opening or closing one, invalidates nothing: menu enablement and labels (Pane commands disabled on `allPanes.count != 1`, the Projects menu's open checkmarks) stay computed for the previous target until some unrelated observed write re-runs the body. At the same time the body over-tracks: it re-runs on every bell (#0609), every divider tick (#0607) and every Session switch. Its own doc comment (`BattyCommands.swift:63-71`) already acknowledges the staleness.

## Plan

**Land after #0616.** `issue/0616` (resolved, not yet merged) changes only `BattyCommands.selectTheme` (`:729-736`) and adds a few lines to `AppStateStore.swift`; no overlap with this plan, but the implementer runs `git merge main` first if #0616 has landed. #0609 (plan only) changes `bellFeed.unseenCount` to a stored value; `BattyCommands.swift:326` needs no change here either way.

### Decision: an observed `keyContentWindowID`, not `@FocusedValue`

- `.focusedSceneValue` / `@FocusedValue` goes nil whenever a non-content scene is key. Settings and Help are SwiftUI scenes, and the Project Editor is an AppKit `NSWindowController` window whose effect on SwiftUI's focused-scene tracking is undocumented. Today's contract (`menuTargetWindow`'s doc comment, `AuxiliaryWindowGateTests`, `AuxiliaryWindowShortcutTests`) is that **enablement** keeps following the content window behind an auxiliary window while **actions** go nowhere. `@FocusedValue` would change that contract, or behave differently per auxiliary window kind.
- A `Commands` body can't be unit-tested; a store property can, with `withObservationTracking`.
- `BattyShortcuts`, CLI/XPC and Command Palette already resolve through the store. `@FocusedValue` would add a second authority for "which Window is the target."
- Writing the observed id from `handleWindowDidBecomeKey` is event-origin: an `NSWindow.didBecomeKeyNotification` observer, not SwiftUI update code. `contentWindowBecameKey(_:)` already writes observed state from there (`applyChrome(for:)`), so this follows an existing writer.

### Files and approach

1. **`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift`**
   - Add an observed stored property near `recentlyKeyWindowIDs` (`:308`):
     ```swift
     public private(set) var keyContentWindowID: WindowID?
     ```
     Doc comment (the *why*, no issue numbers): the content window menus target, observed so a `Commands` body that reads it re-runs when key moves between content windows or one closes. It stays on the last key content window while Settings, Help, the Project Editor or another app is key. Written only from window events, never from `registerNSWindow` or `openWindowRuntime`, which can run inside a SwiftUI update (`viewDidMoveToWindow`, `RootWindowView.init`'s `runtimeForPresentedWindow`).
   - **Writers (event-origin only), each assigning only when the value differs** (`WindowID` is `Equatable`, but write `if new != keyContentWindowID { keyContentWindowID = new }` explicitly so it doesn't depend on toolchain behavior):
     - `contentWindowBecameKey(_ id:)` (`:1149`): after `noteContentWindowBecameKey(id)`, set `keyContentWindowID = id` **only if `windows` contains `id`** (put it after the existing `guard let window = …`, before `applyChrome`). Callers: the `didBecomeKey` handler and `WindowLifecycleController`'s off-pass block (`RootWindowView.swift:168`), which already exists to catch a window that was key before it registered.
     - Do **not** add the write to `noteContentWindowBecameKey` or `registerNSWindow`. `registerNSWindow` runs from `RegistrarNSView.viewDidMoveToWindow`, whose safety argument (`WindowIDRegistrar.swift:52-66`) depends on writing only ignored state. Keep it that way.
     - New `private func refreshKeyContentWindowID()`: `let next = recentlyKeyWindowIDs.last { id in nsWindowMap.values.contains(id) && windows.contains { $0.id == id } }`, then assign if different. Call it at the end of `unregisterNSWindow` (after `nsWindowMap.removeValue`, before `terminateIfLastContentWindowGone()`) and in `removeWindow(id:)` after `windows.removeAll` (before the termination call). Both run from `WindowDelegate.windowWillClose`, a delegate callback. Result: closing the key window moves the id to the window that was key before it, and closing the last window sets it to nil. Closing a non-key window leaves it unchanged (the recomputation gives the same id, so nothing is written).
   - Add the read API for view bodies, next to `keyWindowOrFirstRegistered()`:
     ```swift
     public var keyContentWindow: WindowRuntime? {
         if let id = keyContentWindowID, let window = windows.first(where: { $0.id == id }) { return window }
         return defaultTargetWindow()
     }
     ```
     It **must read `keyContentWindowID` first, unconditionally**. That read is the dependency. If any untracked tier ran first and returned early (as `defaultTargetWindow()`'s `NSApp.keyWindow` tier does), the body would track nothing and stay stale. The `defaultTargetWindow()` fallback covers launch before any content window has been key, and unit tests. When the first window becomes key, nil → id notifies. Doc comment: for view and `Commands` bodies; imperative callers (actions, CLI, XPC, palette actions) keep `defaultTargetWindow()` / `keyWindowOrFirstRegistered()` / `menuTargetWindow()`. Those read `NSApp.keyWindow` directly, which is more precise in the one-turn gap between a window registering already key and its lifecycle block running.
   - Leave `keyWindowOrFirstRegistered()` and `defaultTargetWindow()` unchanged; they have ~20 imperative callers and the #0439 tests pin their order. Update `keyWindowOrFirstRegistered()`'s doc comment so it stops calling itself "the `WindowRuntime` that `BattyCommands.keyWindow` targets". It is now the imperative counterpart of `keyContentWindow`.
   - **`openProjectIDs` and window removal.** Add `private(set) var closedWindowCount = 0` (observed, internal), incremented in `removeWindow(id:)` only when a runtime was actually removed (check `windows.contains { $0.id == windowID }` before `removeAll`). `openProjectIDs` reads it first: `_ = closedWindowCount`, with a one-line comment that `windows` is ignored and this is what makes a window close re-run the Projects menu. Window *add* needs no tracking: a new Window opens with a fresh Session that has no `projectID`, and Projects open into the target Window (`ProjectOpenPresenter`), whose `sessions` are already tracked. Don't make `closedWindowIDs` observed: `runtimeForPresentedWindow` reads it from `RootWindowView.init`, so the scene body would start depending on it.

## Fix

- `AppStateStore.keyContentWindowID: WindowID?` is observed. It has two writers, both event-origin and both write only on change. `contentWindowBecameKey(_:)` writes it, guarded on the id having a runtime. Since #0612 this is the one-line hook whose only caller is the `didBecomeKeyNotification` handler. The close path writes it through the new private `refreshKeyContentWindowID()`, called from `unregisterNSWindow` and `removeWindow(id:)`, which picks the most recently key window that is still registered, or nil. `registerNSWindow` and `openWindowRuntime` don't write it.
- `keyContentWindow` is the read API for bodies. `BattyCommands.keyWindow` and `closeItemIsEnabled` now use it. It reads `keyContentWindowID` first, which is the dependency.
- `openProjectIDs` reads a new observed `closedWindowCount`, bumped in `removeWindow(id:)` only when a runtime was actually removed. A Window closing now re-runs the Projects menu.
- **Departure from the plan:** `keyContentWindow` prefers the actually-key content window (`keyWindowRuntime()`) after the id read, then uses the id, then `defaultTargetWindow()`. The plan's lifecycle off-pass block, which caught a window that was already key when it registered, was removed in #0612. Writing the id from registration would break the observation rules. Preferring the real key window makes every re-run of the body exact. The id still drives invalidation. With Settings, Help or the Editor key, `keyWindowRuntime()` is nil, so the id keeps enablement on the content window behind them, as before.
- Doc comments: `BattyCommands.keyWindow` / `actionWindow`, `keyWindowOrFirstRegistered()` (now "the imperative counterpart"), `closeItemIsEnabled`. Also `docs/multi-window-design.md` "Focus routing".

## Gotchas

- **Plan premise corrected:** `openWindowRuntime` does not make a Window with no Session. `WindowRuntime.init` seeds "Session 1" when `sessions` is empty. The close-item test sets `b.selectedSessionID = nil` instead.
- A window that is already key when it registers never posts the `didBecomeKey` the handler sees, so `keyContentWindowID` stays on the previous window until the next key event. `keyContentWindow` returns the real key window whenever the body re-runs, but nothing observed forces that re-run at registration. Whether a `WindowGroup` window can be key before its content attaches is the same open inference #0612 noted. The UI test opens Window 2 and checks enablement, which would catch it. The read order trades one stale phase for another rather than removing it: if Window 2 registers already key, the menu is right for Window 2 whenever the body re-runs, but switching back to Window 1 writes nothing (`keyContentWindowID` is still Window 1's id), so the body is not invalidated and keeps Window 2's enablement until the next observed write. The UI test's Cmd-` step would catch that too. If the daily run shows it, the fix is an event-origin key-change signal that changes on every content-window key event, not a write from registration.
