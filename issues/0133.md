# 0133 — Add entitlements and usage descriptions for terminal-app permission model

| | |
|---|---|
| **Status** | resolved |
| **Module** | Build / App |
| **Platform** | macOS |
| **First seen** | 2026-05-16 |

## Description

Batty currently ships with no `.entitlements` file and no permission-related usage-description keys in `Configuration/Info.plist`. The app is unsandboxed (`ENABLE_APP_SANDBOX = NO`) so general POSIX networking and unrestricted-path filesystem access already work, but two real problems remain:

1. **Hardened Runtime defaults break some shell workloads.** Without an entitlements file the default Hardened Runtime restrictions apply to every child process. Common cases that break: JIT-using interpreters (Node, modern Python, JVMs), tools that load unsigned dylibs (lots of Homebrew binaries with third-party plugins), and anything that relies on `DYLD_*` environment variables (debug builds, `DYLD_LIBRARY_PATH` overrides, `asan`).
2. **TCC prompts for protected paths have generic text.** When a shell inside Batty first touches `~/Desktop`, `~/Documents`, `~/Downloads`, a removable volume, or a network volume, macOS prompts and attributes the prompt to Batty.app (responsible-process attribution from the child shell). Without `NS*UsageDescription` keys the prompt uses generic system text; with them, the prompt can say something Batty-specific that helps the user decide.

Entitlements cannot pre-grant TCC-protected paths — that's a user grant via the system prompt (or Full Disk Access in System Settings → Privacy & Security). The work here is to make sure (a) child processes don't get killed by Hardened Runtime, and (b) the prompts that do appear are clear about who's asking and why.

## Acceptance criteria

- A `Batty.entitlements` file exists, wired via `CODE_SIGN_ENTITLEMENTS` in `Configuration/Build.xcconfig` (the only authorized place for build settings).
- The entitlements file contains the Hardened Runtime relaxations needed for terminal child processes (see "Proposed entitlements" below).
- `Configuration/Info.plist` includes `NS*UsageDescription` strings for the file-system locations and local-network access a terminal commonly hits.
- Signed and notarized builds still pass `scripts/verify-dmg.sh` — none of the new entitlements break notarization.
- A short note in `docs/` (or an addition to an existing doc) explains why each entitlement is on and what would break if it were removed, so the next reviewer doesn't blanket-prune the file.

## Proposed entitlements

Start with the minimal pair and grow only when a real shell workload breaks:

```xml
<!-- Minimal start -->
<key>com.apple.security.cs.allow-jit</key>                          <true/>
<key>com.apple.security.cs.allow-dyld-environment-variables</key>   <true/>

<!-- Add when needed (broader surface; document the trigger) -->
<key>com.apple.security.cs.allow-unsigned-executable-memory</key>   <true/>
<key>com.apple.security.cs.disable-library-validation</key>         <true/>
```

Reference shipping terminals (iTerm2, Alacritty, Ghostty) carry the full set. The conservative path is to start with the first pair and only add the second pair when a concrete workload demands it — record the trigger workload in the docs note so the entitlement isn't on for an unknown reason.

## Proposed Info.plist usage descriptions

```xml
<key>NSDesktopFolderUsageDescription</key>
<string>Batty needs access to your Desktop so shell commands you run can read and write files there.</string>
<key>NSDocumentsFolderUsageDescription</key>
<string>Batty needs access to your Documents so shell commands you run can read and write files there.</string>
<key>NSDownloadsFolderUsageDescription</key>
<string>Batty needs access to your Downloads so shell commands you run can read and write files there.</string>
<key>NSRemovableVolumesUsageDescription</key>
<string>Batty needs access to removable volumes so shell commands you run can read and write files there.</string>
<key>NSNetworkVolumesUsageDescription</key>
<string>Batty needs access to network volumes so shell commands you run can read and write files there.</string>
<key>NSLocalNetworkUsageDescription</key>
<string>Batty needs local-network access so shell commands you run can reach devices on your local network (mDNS, Bonjour, intranet services).</string>
```

Wording can be tightened during implementation. Mention "shell commands you run" so the user understands the prompt comes from work *inside* Batty, not Batty itself reaching out.

## Out of scope

- Full Disk Access — that's a manual user grant in System Settings; nothing to declare or ship.
- AppleEvents / Automation entitlements (`com.apple.security.automation.apple-events`) — only relevant if Batty starts scripting other apps. Defer.
- Camera / Microphone / Contacts / Calendar / Photos usage descriptions — terminals rarely hit these; add only if a real workload appears.
- Switching to App Sandbox. `CLAUDE.md` is explicit that Batty is unsandboxed by design.
- `get-task-allow` for debugger attach — useful in Debug builds, must never ship in Release/notarized builds. Out of scope unless we add per-configuration entitlements.

## Notes

- The release pipeline (`scripts/release.sh`) signs with Hardened Runtime enabled — the entitlements file must be valid or signing will fail. Verify with `scripts/verify-dmg.sh` after the first signed build.
- `Configuration/Build.xcconfig` is a restricted file per `CLAUDE.md` — confirm with the user before adding `CODE_SIGN_ENTITLEMENTS` to it.
- Entitlements changes don't affect already-running installs until the user relaunches. Existing TCC grants for `Batty.app` survive entitlement changes; new usage-description text only appears on prompts that haven't been answered yet.
- If we later support a "diagnostic mode" with `get-task-allow` for debugger attach, that needs a separate `Batty.debug.entitlements` and per-configuration wiring.
- Related: `#0027` (multi-window) and any future `#0xxx` introducing in-app scripting (AppleEvents) would expand this set; for now those are deliberately deferred.
