# Issue #0145: Add Watch Action for Session/Pane/Tab Events

**Status:** open  
**Created:** 2026-08-10  
**Components:** CLI (batty), BattyKit  

---

## Summary

Add a persistent `watch` action to the CLI that maintains an XPC connection with the Batty app and reports real-time events for all changes to sessions, panes, and tabs.

## Motivation

Currently the CLI is purely synchronous — each command opens a connection to Batty via XPC, does one action, and disconnects. Agents that need to react to UI changes (session created/destroyed, pane split/closed, tab added/removed) must poll `batty list --json` repeatedly. Polling is wasteful (network + JSON serialization on every request) and unreliable at short intervals, so a dedicated watch channel is needed.

## Proposed Behavior

### 1. New Command: `batty watch`

```bash
# Start watching for topology changes (Ctrl-C to exit)
batty watch

# Watch and filter by event type:
batty watch --events session,pane

# Watch with JSON output for automation
batty watch --json

# Watch and trigger a shell command on each event:
batty watch --on-change 'echo "topology changed: $(date)"'
```

### 2. Event Types

The watch channel reports the following events as they happen:

```json
// Session created (new session opened)
{
  "event": "session.create",
  "timestamp": "2026-08-10T15:30:00Z",
  "session": {
    "id": "...",
    "type": "main | new",
    "name": "...", 
    "path": "/Users/brennan/Developer/Batty"
  }
}

// Session closed (session destroyed)
{
  "event": "session.destroy", 
  "timestamp": "2026-08-10T15:30:01Z",
  "session": {
    "id": "...",
    // session may be partially populated or absent after destruction
  }
}

// Pane split (new pane created within session)
{
  "event": "pane.split",
  "timestamp": "2026-08-10T15:30:02Z",
  "sessionID": "...",
  "parentPaneID": "...",

    "id": "...",

  "event": "pane.close",

  "sessionID": "...",

}

// Tab add (new tab within pane)
{
  "event": "tab.add",
  "timestamp": "2026-08-10T15:30:04Z",
  "sessionID": "...",
```

### 3. Connection and Reconnection

The watch command should:
- Maintain a persistent XPC connection with the Batty broker
- Auto-reconnect if the broker becomes temporarily unavailable
- Gracefully handle broker restarts (session info may be lost during restart)

### 4. Filtering Options

```bash
# Watch only specific event types
batty watch --events session,pane

# Filter by session ID (e.g., monitoring one project)
batty watch --session <id>

# Filter by pane ID (e.g., monitoring one specific pane)  
batty watch --pane <id>

# Output only when changes occur (suppress initial topology)
batty watch --changes-only
```

### 5. Shell Integration

```bash  
# Pipe events to jq for real-time filtering
batty watch --json | jq '.[] | select(.event == "pane.split")'

# Trigger scripts based on events
batty watch --on-change 'python3 /path/to/script.py'

# Integrate with tmux or other multiplexers
batty watch --on-change 'tmux display-message "Batty: {{.event}}"'
```

## Implementation Considerations

### XPC Channel Design

- Use the existing broker connection infrastructure
- Add a long-lived "watch" channel that sends events over XPC as they occur
- Support both single-event notifications and full topology snapshots (for initial state)

### Performance Impact

- Minimal CPU impact — events are only sent when changes actually occur
- Memory footprint is small (just the connection + a small event queue)
- Network bandwidth is negligible compared to polling

### Security Considerations

- The watch channel should only expose data the user can already see in the UI
- No additional permissions needed beyond what `batty` already requires  
- Events should not include sensitive data (e.g., terminal contents)

### Backward Compatibility

- `batty watch` is a new command — doesn't affect existing commands
- The JSON event format is versioned and can evolve without breaking clients

## Acceptance Criteria

1. `batty watch` starts a persistent connection and reports events in real-time
2. All event types work correctly: session create/destroy, pane split/close, tab add/remove/rename
3. Focus changes are reported accurately
4. Filtering by event type, session ID, and pane ID works correctly
5. The watch command auto-reconnects on broker restart
6. JSON output format is clean and parseable by automation tools

## Use Cases

### Agent Activity Monitoring
```bash
# Watch for session creation to know when new workspaces are ready
batty watch --json | jq 'select(.event == "session.create")'

# React to pane close events to trigger cleanup
batty watch --on-change 'npm run clean-after-pane-close'

# Monitor for project sessions only
batty watch --session $(pwd-hash) | jq 'select(.event == "pane.split")'
```

### Dashboard Integration  
```bash
# Show real-time activity in a dashboard
batty watch --json | jq -r '"\(.event) at \(.timestamp)"'
```

### Debugging Layout Issues
```bash
# Capture all changes to reproduce a layout issue  
batty watch --json > /tmp/layout-changes.json &
# ... perform actions ...
kill %1
cat /tmp/layout-changes.json  # for analysis
```
