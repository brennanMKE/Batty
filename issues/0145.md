# 0145 — Vertical splits: GeometryReader side effects and drag-and-drop follow-up

| | |
|---|---|
| **Status** | open |
| **Module** | Pane / Split |
| **Platform** | macOS |
| **First seen** | 2026-05-19 |

## Description

Vertical splits exhibit strange layout behavior caused by `GeometryReader` in `DraggableSplitView` (`SplitContainerView.swift:66`). Once the GeometryReader is eliminated, drag-and-drop with vertical splits must be re-verified — the overlay strategy from #0143 may behave differently when pane frames are computed by a proper `Layout` conformance versus the current GeometryReader.

## Two linked problems

### Problem 1 — GeometryReader in `DraggableSplitView`

`DraggableSplitView.body` is wrapped in a top-level `GeometryReader` that measures available space and uses it to compute explicit `.frame(width:height:)` values for both child panes. This is the most disruptive `GeometryReader` pattern in SwiftUI:

- `GeometryReader` expands to fill all proposed space, ignoring its children's ideal sizes.
- It forces explicit frames on children, overriding SwiftUI's natural size negotiation.
- In vertical splits, the expansion can produce incorrect or jittery layout when the view tree is rebuilt (session switch, pane addition, window resize).

This is Site 4 from issue #0141, which flagged it as "Hard / possibly keep" because `onGeometryChange` is a side-effect hook and cannot drive layout the same way. The correct replacement is a custom `Layout` conformance.

### Problem 2 — Drag-and-drop re-verification needed after migration

The #0143 fix uses `PaneSwapDropZone` overlays that appear over each non-source pane when a drag starts. These overlays are sized and positioned by SwiftUI based on the pane's frame. If pane frames are computed incorrectly by the current `GeometryReader` (particularly in vertical splits), the drop zone overlay may not cover the correct region — the drop target could appear in the wrong position or at the wrong size.

Once the `GeometryReader` is replaced with a proper `Layout`, pane frames will be laid out by SwiftUI's native geometry system. At that point, the drag-and-drop behavior in vertical splits must be smoke-tested to confirm:

- Drop zone overlays appear at the correct position and size over vertical split panes.
- Swapping vertically-split panes works and animates correctly.
- The divider drag (resize) still functions after the `Layout` migration.

## Fix direction

### Step 1 — Replace `GeometryReader` with a custom `Layout`

Implement a `SplitLayout: Layout` that:
- Accepts exactly three subviews: left child, divider, right child (for both `.horizontal` and `.vertical` directions).
- Reads the proposed size and apportions it: `leftLength = (totalLength - dividerThickness) * ratio`, `rightLength = remainder`. No `GeometryReader` needed.
- For `.horizontal`: places left child at `(0, 0)` with `(leftLength, height)`, divider at `(leftLength, 0)` with `(dividerThickness, height)`, right child at `(leftLength + dividerThickness, 0)` with `(rightLength, height)`.
- For `.vertical`: analogous with height axis.
- Exposes `ratio` as a `@Binding` — the `DragGesture` on the divider updates it, `Layout.placeSubviews` uses it to recompute positions without a `GeometryReader` in the loop.

Custom `Layout` conformances are available on macOS 13+. Batty targets macOS 15.6, so no back-deployment needed.

### Step 2 — Re-verify drag-and-drop in vertical splits

After the `Layout` migration, manually test:
- [ ] Vertical split: drag grip handle → drop zone overlay covers the correct pane region.
- [ ] Vertical split: drop on target pane → panes swap with spring animation.
- [ ] Vertical split: divider drag still resizes panes smoothly.
- [ ] Horizontal split: no regression (verify same checklist).
- [ ] File drop from Finder onto a vertically-split terminal pane still works.
