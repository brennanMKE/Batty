## Description

Once [#0373](0373.md) lands, background image and opacity are settable — but only globally. The user wants them settable **per Pane**, from the sidebar, in their own words:

> "We will need some way to change these settings for a pane. A gear icon could be placed next to the eye icon used for toggling the visibility of a pane which brings up a view much like the theme selector which allows the user to set the opacity of the terminal and also set the image which also can have opacity."

And the goal the whole batch serves:

> "Ultimately with both issues implemented the user should [be] able to tint an image and still see through to other apps or the desktop on a Mac."

So: a gear control in each Pane row of the Session sidebar, sitting next to the existing eye toggle, presenting a sheet modelled on the Theme Selector, offering terminal background opacity, image selection, and image opacity for **that Pane**.

## Resolution notes

> 🟢 Resolved 2026-11-03 — A gear on each terminal Pane's Sidebar row opens a sheet that sets that Pane's background image and opacity live, for every Tab in the Pane now and later, surviving appearance changes, behind a flag that is on in Beta and off in Prod; the desktop does not show through until #0539.

## Root cause

Feature work. After #0373 a background could be set only through app-wide preference keys, with no UI and no per-Pane level. `applyAppearanceToAllSurfaces` also built one configuration for every Tab, which would have wiped any Pane-level value.

## Fix

- **Model.** `PaneRuntime.backgroundOverride` (`nil` follows, non-nil is complete) fans out through `TabRuntime.setBackgroundOverride`, which uses the Tab's own builder, so per-Tab lines survive. `addTab` passes the override to new Tabs. A non-terminal Pane ignores it, and a new Split follows rather than inherits.
- **Resolution.** `TerminalBackgroundSettings.effective(pane:appWide:)` is the shared function for #0375 and #0376.
- **Replace hazard.** `applyAppearanceToAllSurfaces` builds one configuration per Pane, so an override survives an appearance change. #0538 is not fixed and stays open.
- **Bad images.** `TerminalBackgroundImageImporter` re-encodes the chosen file to an 8-bit sRGB PNG capped at 4096 px, and the override stores the copy's path. A file ImageIO can't decode shows an inline error and changes nothing.
- **Sheet.** `PaneBackgroundSettingsView` applies every control live. All writes come from control bindings, buttons or the importer's result: no `onChange`. The only `Task` is the real import, which is held in `@State`, cancelled on disappear, and checks cancellation before writing.
- **Flag.** `FeatureFlags.terminalBackgrounds`, on in Beta and off in Prod. With it off there is no gear, the sheet can't present, no override can exist and no image file is touched. Gate sites are in `docs/feature-flags.md`.
- **See-through to the desktop** is out of scope and filed as [#0539](0539.md). The flag can't come off until it lands.

Divergences from the plan:

- The importer also drops `"` and `\\` from the copy's name, because the path is written into a quoted config value. The plan dropped control characters only.
- The name is bounded to 200 UTF-8 bytes rather than 200 characters, because a filesystem name is limited in bytes. `aLongMultibyteNameStillImports` is added for this.
- `PaneBackgroundEditor.update` is a no-op while following, so an import finishing after the user returned to following can't create an override. `editorUpdateIsIgnoredWhileFollowing` is added for this.
- Slider values are rounded to the 0.05 grid in the setter, so config lines don't carry floating-point noise. Each slider also gets an accessibility identifier.
- `issues/0372.md` is untouched: its #0539 row is already on `main`.

### Measured: what libghostty does with a bad image

ImageIO here is `CGImageSourceCreateThumbnailAtIndex` plus a draw.

| File | ImageIO | `ghostty_surface_new` |
|---|---|---|
| Valid PNG, JPEG; 16-bit, gray, Display P3, interlaced PNG; gray, CMYK, progressive JPEG | decodes | OK |
| PNG with last 12 bytes (`IEND`) gone | decodes | OK |
| GIF, HEIC | decodes | OK, no image (#0373) |
| JPEG with 200 corrupted bytes mid-file | decodes | OK |
| 0-byte, random bytes, 40-byte PNG, PNG with bad `IHDR` CRC | **refuses** | `NULL` |
| **PNG with one flipped bit, or 200 corrupted bytes** | **decodes** | **`NULL`** |
| **PNG or JPEG cut to 50%; JPEG missing `EOI`** | **decodes** | **`NULL`** |
| 8192x4096, 12000x9000, 16384x200 PNG | decodes | OK |
| **20000x200 or 16385x200 PNG** | decodes | **The process aborts** (exit 134, `MTLTextureDescriptor has width (20000) greater than the maximum allowed size of 16384`) |

- **Oversize is the sharpest case, and #0373 listed it as unmeasured.** The abort also happens when a live surface receives the config through `ghostty_surface_update_config`, so one wide image can kill **every Terminal Session in the app**. No Xcode or `MTL_*` variable was set, so this isn't a debug-layer artefact of the harness.
- A live surface given a bit-flipped PNG survives (exit 0). The `NULL` case therefore hits new Tabs: an empty Pane with no shell.
- **Every ImageIO-decodable fixture, re-encoded by ImageIO to a fresh 8-bit sRGB PNG with the long edge capped at 8192, created a surface**: 20 of 20, including the bit-flipped, truncated and 20000-wide ones. A checker can't match libghostty's stricter decoder from outside. Re-encoding removes the mismatch.

### Decisions

**The wholesale-replace hazard.** `applyAppearanceToAllSurfaces` keeps its current shape but builds one configuration **per Pane** inside the loop, from `TerminalBackgroundSettings.effective(pane: pane.backgroundOverride, appWide: …)`. This depends on nothing from #0538: the override survives whichever lines that builder still drops.

The Pane fan-out must **not** use that builder, or the sheet would spread #0538 to every Pane the user touches. It goes through the Tab's own builder (`TabRuntime.setBackgroundOverride`), so `keybind = clear`, `command`, `copy-on-select` and `env BATTY_*` stay. As a side effect, a fan-out repairs a Tab already degraded by #0538. That is not this issue's fix.

*Overlap with #0538:* both touch the same few lines of that loop, and the conflict is small. #0538's fix can't simply call the Tab builder, because `TabRuntime` reads font and cursor from `.standard` while the appearance tests write `store.preferences`; that is its problem to solve. Once fixed, the per-Pane configuration here disappears, because the Tab already knows its override, and this issue's tests keep guarding it. **#0374 does not fix #0538** and #0538 stays open. It's a shipped bug on its own release path.

**The undecodable-image hazard: #0374 carries the guard.** Whichever issue ships the first picker owns it, and #0375 adopts it. The picker never hands libghostty the user's file. A new actor `TerminalBackgroundImageImporter` re-encodes it into a Batty-owned PNG with the long edge capped at **4096**, and the override stores that path. The cap is below the measured 16384 abort and limits VRAM, since upstream keeps one copy per terminal: 4096x3072 is about 50 MB per Tab. This also covers a source file that later goes bad or disappears: the copy doesn't change, and a missing copy is benign (#0373). A file ImageIO can't decode gets an inline error, and the override doesn't change.

A truncated image that ImageIO partly decodes shows as a partial picture. That's acceptable: it's visible, and it's safe.

**See-through to the desktop: follow-up [#0539](0539.md).** It's a separate job, for these reasons:

- It takes `window.isOpaque = false`, a clear `window.backgroundColor` (`RootWindowView.swift:320-326`, set today to an opaque color or `nil`), and the band at `SessionDetailView.swift:305-308`. It also has to deal with every other opaque surface in the window: the tab bar and Pane header `chromeBackground` (`PaneView.swift:249,434,624`) and the themed Sidebar.
- It's a window-level fact, derived from every Pane in the window, so it needs an owner and a declared writer of its own (`docs/swiftui-observation-rules.md`). A Pane with no override is affected too.
- On macOS, fully transparent pixels of a non-opaque window can pass clicks to the app underneath. That's from memory, not measured. At `background-opacity = 0` it would break the first requirement in `docs/terminal-pane-requirements.md`.
- None of it can be proven by unit test. It needs a run in the real app, which this tier doesn't have.

What this issue delivers without it is real: an image and opacity composited over the Theme's window color. The sheet's caption says that, so it doesn't promise the desktop.

**The follow-up is filed as [#0539](0539.md)**, as a child of #0372, blocked by this issue, and behind the same flag. Suggested title: *"A semitransparent Pane composites over the Theme's window color, so the desktop never shows through, because the window and its chrome are opaque"*. **The umbrella isn't finished, and the flag can't come off, until it lands**, since it's the user's headline goal.

**Release rule: on `main` behind a new flag.** See "`release/1.3`" below.

**Other decisions, recorded here for the resolution notes:**

- **Override shape: all-or-nothing.** A `TerminalBackgroundSettings?` on the Pane: `nil` follows, non-nil is complete. Switching to custom seeds from the current effective value, which then stops following. #0376 should match this.
- **"None" is not "follow".** A custom override with `imagePath == nil` hides an app-wide image for this Pane.
- **Fit and position are exposed**, because no other UI can set them until #0375 and `contain` is rarely wanted in a narrow Split. `background-image-repeat` isn't exposed; `TerminalBackgroundSettings` has no such field.
- **Legibility.** No `minimum-contrast`, for the reason above. Instead the first image picked on a Pane sets image opacity to **0.35**, a tint, while replacing an image keeps the current value. The gear lives in the Sidebar, so an unreadable Pane can always be reset. #0375 owns any app-wide answer.
- **`background-opacity-cells`.** Not coupled, since #0372 assigns that decision to #0375. A caption says that programs painting their own background stay opaque.
- **A new Split follows.** It doesn't inherit its parent's override, because the setting is "for that Pane".
- **Not persisted**, like `localThemeName`. `Pane.snapshot()` and Save as Project don't carry it.
- **The picker stays PNG and JPEG**, as the issue asks. Re-encoding would make HEIC safe, and that's a one-line change if wanted later.

## A Pane is not a Terminal Session — the fan-out this issue must get right

**This is the shape of the most likely bug in this issue. Do not gloss it.**

Per `Concepts.md`, a **Pane** holds one or more **Tabs**, and each Tab owns its own **Terminal Session** (surface) with its own `TerminalConfiguration`, built at `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:172-246` when the Tab is created. There is no per-Pane configuration object to write to.

So a "per-Pane background" must:

1. **Apply to every Tab currently in the Pane** — a fan-out over `pane.tabs`, calling `setTerminalConfiguration` on each, the way `applyAppearanceToAllSurfaces()` fans out at `SettingsPreferences.swift:190-198`.
2. **Apply to every Tab created *later* in that Pane.** The override has to live on the Pane (a stored property on `PaneRuntime`, mirroring how `SessionRuntime.localThemeName` lives on the Session at `SessionRuntime.swift:21`) and be read by `TabRuntime`'s builder at Tab-init time. If the setting is only pushed to the Tabs that existed when the sheet was open, then the next `Cmd-T` opens a Tab with no background and the feature looks broken at random. **State this in the resolution notes and cover it with a test**: set a Pane background, create a new Tab in that Pane, assert its `renderedConfig` carries the background lines.
3. **Not apply to a non-terminal Pane.** `applyAppearanceToAllSurfaces()` filters `where pane.kind == .terminal` (`SettingsPreferences.swift:191`) because a non-terminal Pane's `tabs` holds one structural placeholder `TabRuntime` whose `TerminalController` was never attached to a rendered surface (#0315 review round 1, finding 3). Either apply the same filter, or hide the gear entirely on non-terminal Pane rows — the latter is probably better UX, since a Git Status Pane has no terminal background to set.

## Scope resolution

With [#0375](0375.md) (app-wide) and [#0376](0376.md) (per-Session) also on the table, there will be up to three levels. The intended chain, narrowest wins:

**Pane override → Session override → app-wide default**

This should mirror how `localThemeName` resolves today, including the "follows the broader level" semantics:

- `ThemePreference.effectiveTheme(localThemeName:isDark:)` (`BattyKit/Sources/BattyKit/Theme/ThemePreference.swift:76-86`) is the resolution function: use the local name if it is set and names a real Theme, else fall through to the global slot.
- `nil` means **follow**, not "no background". A Pane with no override must pick up *later* changes at the Session or app-wide level automatically — that is exactly what `ThemePreference.swift:158` does when it filters `windows.flatMap { $0.sessions }.filter { $0.localThemeName == nil }` before applying a new global Theme, so overridden Sessions are skipped and following ones are updated.
- Conversely, an override must be **sticky**: a Pane with a background set must survive the next app-wide change. Combined with the wholesale-replace hazard below, that means the app-wide path cannot blindly overwrite; it has to consult the resolution chain per Pane.

Whichever of #0374/#0375/#0376 lands first should establish the resolution function and the other two adopt it, rather than each growing its own fallback logic.

## The wholesale-replace hazard

Documented in full in [#0372](0372.md); restated here only as it bites this issue. `setTerminalConfiguration` **replaces** the whole override set rather than merging, and Batty builds that set in two independent places — `TabRuntime.swift:172-246` and `SettingsPreferences.swift:170-198`.

The concrete failure: the user sets a background on one Pane, then changes the font size in Settings. `applyAppearanceToAllSurfaces()` runs, rebuilds a configuration from app-wide preferences only, and pushes it to **every** Tab in every window — wiping the Pane override. A Pane override must survive that. The fix is that the app-wide builder must resolve per-Pane rather than build one configuration for all of them, or the two must share one resolution helper. Cover it with a test.

## Notes

- **Legibility.** `minimum-contrast` is available (`withMinimumContrast`, `TerminalConfiguration.swift:190` in the SPM checkout). Whether the sheet exposes it, sets it implicitly when an image is present, or ignores it is a decision this issue should make and record — a user can otherwise produce an unreadable Pane with two slider drags.
- **`background-opacity` affects default-background cells only.** A TUI painting its own cells (vim, htop) stays opaque unless `background-opacity-cells` is also set. Users who set opacity on a Pane running vim and see no change are hitting this, not a bug. Decide whether the sheet couples the two.
- **The themed window background still paints behind everything.** `SessionDetailView.swift:217-220` paints `themeChrome?.windowBackground` behind the terminal host, so a semitransparent Pane composites over the theme's window color, **not** over the desktop. The user's stated goal — "still see through to other apps or the desktop" — requires that band to be transparent too, along with the `NSWindow`'s own opacity. This issue must confront that: setting `background-opacity` alone will *not* show the desktop. Either this issue makes the window background transparent when any surface is semitransparent, or it explicitly defers that to a follow-up ticket (file it, don't leave it as a sentence — see `issues/Issues.md`, "No dangling follow-ups").
- **Verification.** Unit-testable parts: the resolution chain, the fan-out to existing Tabs, the new-Tab inheritance, and survival of `applyAppearanceToAllSurfaces()` — all assertable through `renderedConfig` the way [#0373](0373.md) establishes. The sheet's appearance and the actual rendering are not; mark `resolved`, not `closed`, and say in `## Gotchas` what could not be verified. A UI test for the gear button's presence and its sheet presentation is worth adding, addressed via the accessibility identifier.
