## Description

Once [#0373](0373.md) lands, background image and opacity are settable — but only globally. The user wants them settable **per Pane**, from the sidebar, in their own words:

> "We will need some way to change these settings for a pane. A gear icon could be placed next to the eye icon used for toggling the visibility of a pane which brings up a view much like the theme selector which allows the user to set the opacity of the terminal and also set the image which also can have opacity."

And the goal the whole batch serves:

> "Ultimately with both issues implemented the user should [be] able to tint an image and still see through to other apps or the desktop on a Mac."

So: a gear control in each Pane row of the Session sidebar, sitting next to the existing eye toggle, presenting a sheet modelled on the Theme Selector, offering terminal background opacity, image selection, and image opacity for **that Pane**.

## Where the control goes

The Pane row is `PaneRow` in `BattyKit/Sources/BattyKit/Views/SessionSidebarView.swift:285`. Its `body` (`:326-362`) is an `HStack(spacing: 6)` laid out as: label → `Spacer()` → unseen-bell badge (`:335-342`) → eye `Button` (`:346-356`).

The gear goes into that trailing group beside the eye. Match the eye's presentation exactly — `Image(systemName:)` at `.font(.system(size: 10, weight: .semibold))`, `.frame(width: 18, height: 18)`, `.buttonStyle(.borderless)`, a `.help(…)` string, and an `.accessibilityIdentifier` following the same pattern (`pane-eye-toggle.<uuid>` → `pane-background-settings.<uuid>`), so UI tests can address it.

Two layout facts to respect:

- The row is already crowded at narrow sidebar widths — label, an optional bell badge, and now two 18pt controls. Check the label's `.lineLimit(1)` truncation still leaves something readable.
- The row has an `.onTapGesture { activate() }` on a `.contentShape(Rectangle())` (`:358-361`) which selects the Session and focuses the Pane. A `Button` inside it does not trigger that gesture (the eye already proves this), but confirm the gear behaves the same and does not also activate the row.

Note that #0362 (open) is investigating a Pane-count discrepancy that also touches this sidebar's Pane rows. Coordinate if both are in flight.

## The sheet

Modelled on the Theme Selector, per the user. The relevant precedent is `SessionThemeSelectorView` — presented from this same file as a `.sheet(item:)` off a context-menu binding (`SessionSidebarView.swift:123-129`), and reworked in [#0363](0363.md) to open on the *currently active* value with the shared `ActiveOutline` highlight (`BattyKit/Sources/BattyKit/Views/ActiveOutline.swift`).

Carry those lessons over:

- **Open showing the Pane's current state**, not a blank or defaulted form. #0363's whole defect was a selector that opened on entry 0 instead of the active value.
- **Reuse `ActiveOutline`** (`.activeOutline(_:cornerRadius:color:)`) for any "this is the current selection" marking, rather than hand-rolling a second outline. It exists precisely so these don't drift.
- **Make "follows the broader scope" a visible, selectable state**, not the absence of a selection — the same problem `SessionThemeSelectorView` has with `localThemeName == nil`. The user must be able to *clear* a Pane override and go back to inheriting, and must be able to see which state they are in.

Controls the sheet must offer, all for the selected Pane:

- **Terminal background opacity** — `background-opacity`.
- **Image selection** — a picker restricted to the formats [#0373](0373.md) confirmed. Plus a "None" affordance that clears the Pane's image.
- **Image opacity** — `background-image-opacity`, so the image can be dialled down to a tint.

Fit / position / repeat are optional here; the app-wide UI in [#0375](0375.md) owns the full set. Decide and record whether the Pane sheet exposes them or inherits them.

**Live preview matters.** These are visual settings whose only useful feedback is the terminal itself. Apply changes to the Pane's surfaces as the controls move, not on a Done button — `setTerminalConfiguration` reapplies in place without tearing down the surface or the PTY, so this is cheap. Its equal-value early-return means a slider that stops moving stops costing anything.

## A Pane is not a Terminal Session — the fan-out this issue must get right

**This is the shape of the most likely bug in this issue. Do not gloss it.**

Per `Concepts.md`, a **Pane** holds one or more **Tabs**, and each Tab owns its own **Terminal Session** (surface) with its own `TerminalConfiguration`, built at `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift:172-246` when the Tab is created. There is no per-Pane configuration object to write to.

So a "per-Pane background" must:

1. **Apply to every Tab currently in the Pane** — a fan-out over `pane.tabs`, calling `setTerminalConfiguration` on each, the way `applyAppearanceToAllSurfaces()` fans out at `SettingsPreferences.swift:190-198`.
2. **Apply to every Tab created *later* in that Pane.** The override has to live on the Pane (a stored property on `PaneRuntime`, mirroring how `SessionRuntime.localThemeName` lives on the Session at `SessionRuntime.swift:21`) and be read by `TabRuntime`'s builder at Tab-init time. If the setting is only pushed to the Tabs that existed when the sheet was open, then the next `Cmd-T` opens a Tab with no background and the feature looks broken at random. **State this in the resolution notes and cover it with a test**: set a Pane background, create a new Tab in that Pane, assert its `renderedConfig` carries the background lines.
3. **Not apply to a non-terminal Pane.** `applyAppearanceToAllSurfaces()` filters `where pane.kind == .terminal` (`SettingsPreferences.swift:191`) because a non-terminal Pane's `tabs` holds one structural placeholder `TabRuntime` whose `TerminalController` was never attached to a rendered surface (#0315 review round 1, finding 3). Either apply the same filter, or hide the gear entirely on non-terminal Pane rows — the latter is probably better UX, since a Git Status Pane has no terminal background to set.

## Scope resolution

With [#0375](0375.md) (app-wide) and [#0376](0376.md) (per-Session) also on the table, there will be up to three levels. The intended chain, narrowest wins:

**Pane override → Session override → app-wide default**

This should mirror how `localThemeName` resolves today, including the "follows the broader level" semantics:

- `ThemePreference.effectiveTheme(localThemeName:isDark:)` (`BattyKit/Sources/BattyKit/Theme/ThemePreference.swift:76-86`) is the resolution function: use the local name if it is set and names a real Theme, else fall through to the global slot.
- `nil` means **follow**, not "no background". A Pane with no override must pick up *later* changes at the Session or app-wide level automatically — that is exactly what `ThemePreference.swift:158` does when it filters `windows.flatMap { $0.sessions }.filter { $0.localThemeName == nil }` before applying a new global Theme, so overridden Sessions are skipped and following ones are updated.
- Conversely, an override must be **sticky**: a Pane with a background set must survive the next app-wide change. Combined with the wholesale-replace hazard below, that means the app-wide path cannot blindly overwrite; it has to consult the resolution chain per Pane.

Whichever of #0374/#0375/#0376 lands first should establish the resolution function and the other two adopt it, rather than each growing its own fallback logic.

## The wholesale-replace hazard

Documented in full in [#0372](0372.md); restated here only as it bites this issue. `setTerminalConfiguration` **replaces** the whole override set rather than merging, and Batty builds that set in two independent places — `TabRuntime.swift:172-246` and `SettingsPreferences.swift:170-198`.

The concrete failure: the user sets a background on one Pane, then changes the font size in Settings. `applyAppearanceToAllSurfaces()` runs, rebuilds a configuration from app-wide preferences only, and pushes it to **every** Tab in every window — wiping the Pane override. A Pane override must survive that. The fix is that the app-wide builder must resolve per-Pane rather than build one configuration for all of them, or the two must share one resolution helper. Cover it with a test.

## Notes

- **Legibility.** `minimum-contrast` is available (`withMinimumContrast`, `TerminalConfiguration.swift:190` in the SPM checkout). Whether the sheet exposes it, sets it implicitly when an image is present, or ignores it is a decision this issue should make and record — a user can otherwise produce an unreadable Pane with two slider drags.
- **`background-opacity` affects default-background cells only.** A TUI painting its own cells (vim, htop) stays opaque unless `background-opacity-cells` is also set. Users who set opacity on a Pane running vim and see no change are hitting this, not a bug. Decide whether the sheet couples the two.
- **The themed window background still paints behind everything.** `SessionDetailView.swift:217-220` paints `themeChrome?.windowBackground` behind the terminal host, so a semitransparent Pane composites over the theme's window color, **not** over the desktop. The user's stated goal — "still see through to other apps or the desktop" — requires that band to be transparent too, along with the `NSWindow`'s own opacity. This issue must confront that: setting `background-opacity` alone will *not* show the desktop. Either this issue makes the window background transparent when any surface is semitransparent, or it explicitly defers that to a follow-up ticket (file it, don't leave it as a sentence — see `issues/Issues.md`, "No dangling follow-ups").
- **Verification.** Unit-testable parts: the resolution chain, the fan-out to existing Tabs, the new-Tab inheritance, and survival of `applyAppearanceToAllSurfaces()` — all assertable through `renderedConfig` the way [#0373](0373.md) establishes. The sheet's appearance and the actual rendering are not; mark `resolved`, not `closed`, and say in `## Gotchas` what could not be verified. A UI test for the gear button's presence and its sheet presentation is worth adding, addressed via the accessibility identifier.
