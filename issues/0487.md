# 0487 — A terminal split from a Git Status or other non-terminal Pane does not inherit a working directory

| | |
|---|---|
| **Status** | open |
| **Module** | Pane / Split |
| **Platform** | macOS |
| **First seen** | 2026-10-12 |
| **Target release** | 1.2.1, built from `release/1.2` (user-authorized exception to the fix-on-`main`-first rule, 2026-10-12; see "Release") |

## Description

User report (2026-10-12), verbatim:

> If I split out a new pane from a Git Status view it does not carry path to the current directory like a terminal view does. This may impact all new view types.

Confirmed, and it does affect every non-terminal kind. A split taken while a `.terminal` Pane is focused starts the new shell in that Pane's active Tab's working directory (`Concepts.md`, Pane › Splitting: "The new Pane is born with one Tab containing one fresh Terminal Session in the parent Pane's cwd"). A split taken while a Git Status, Process Status, System Metrics or LM Studio Dashboard Pane is focused starts the new shell with **no** working directory at all, so it lands wherever libghostty's default takes it — in practice `$HOME`. A Git Status Pane is the worst case because it visibly *has* a directory (the repository it is showing, with a "Change Directory…" picker), and the new terminal ignores it.

**Root cause (verified on `release/1.2` at `13c168d6`).** Every split path ends in the private `SplitTree.makePane(inheritingFrom:...)` (`BattyKit/Sources/BattyKit/Model/SplitTree.swift:331-375`), and its cwd inheritance reads only the source Pane's *active Tab's terminal*:

```swift
guard let sourceTab = source?.activeTab else { ... }                  // :369
let cwd = sourceTab.terminal.workingDirectory
    ?? sourceTab.terminal.configuration.workingDirectory               // :372-373
return PaneRuntime(tabs: [TabRuntime(workingDirectory: cwd, command: command)])
```

A non-terminal Pane does have an `activeTab` — #0315 kept one structural placeholder `TabRuntime` on every Pane regardless of `kind` (`PaneRuntime.kind`'s doc comment, `Runtime/PaneRuntime.swift`; `Concepts.md` Tab › Exception) — but that Tab is never rendered and never gets a Terminal Session, so `terminal.workingDirectory` (OSC 7) is never reported and `terminal.configuration.workingDirectory` was never set (`PaneRuntime.init` builds it as a bare `TabRuntime()`). Both reads are `nil`, the new `TabRuntime` is created with `workingDirectory: nil`, and `TabRuntime.init` (`Runtime/TabRuntime.swift:127-145`) then leaves `terminal.configuration.workingDirectory` unset. libghostty-spm skips `config.working_directory` entirely for a `nil` value (`TerminalController+Surface.swift:105-118` in the vendored package), so the shell starts in libghostty's default, which Batty's own docs describe as `$HOME` (`PaneRuntime.makeContent`'s doc comment: "`$HOME` — the resolution-order fallback of last resort"; `Concepts.md` Session › CWD inheritance). The directory the Git Status Pane is actually showing, `GitStatusPaneContent.directoryPath` (`Runtime/GitStatusPaneContent.swift:643`, reachable as `source.content as? GitStatusPaneContent`), is never consulted.

`docs/pane-kinds.md:140-142` states the premise that produced this: "a Git Status pane has no cwd to inherit in the same sense". That is true of the placeholder Tab and false of the Pane — the Pane's content holds exactly the directory the user means.

**Every split path routes through `makePane`, so one fix covers all of them.** Each caller passes the focused Pane with no kind check:

- ⌘D / ⇧⌘D → `tree.splitFocusedPane(direction:inheritingFrom: tree.focusedPane)`; ⌥⌘D / ⌥⇧⌘D → `tree.splitFullDimension(...)`: the NSEvent monitor in `Commands/BattyShortcuts.swift:133-147` (default chords at `Shortcuts/ShortcutAction.swift:106-113`).
- Pane menu › Split Horizontally › Terminal, Split Vertically › Terminal, Split Full-Height Column, Split Full-Width Row: `Commands/BattyCommands.swift:292-296`, `:331-335`, `:369-383`.
- The toolbar buttons `toolbar.split-horizontal` / `toolbar.split-vertical` (Option-click for the full-dimension variants): `Views/SessionDetailView.swift:177-203`.
- Command Palette "Split …" entries: `Views/CommandPaletteView.swift:227-239`.
- CLI `batty pane split [-h|-v] [--pane <id>] [--command …]` (`BattyKit/Sources/batty/PaneCommand.swift:55-102`) → XPC → `AppStateStore.splitPane(id:...)` (`Runtime/AppStateStore.swift:565-583`) → `SplitTree.splitPane(id:...)` (`SplitTree.swift:418`) → `makePane(inheritingFrom: targetPane, ...)`. `--pane` can name a non-terminal Pane explicitly, and `BATTY_PANE_ID`/focused-pane fallback resolves to one whenever it is focused.
- Layouts (`PaneLayout.apply(to:)`, `Model/PaneLayout.swift:131-144`) split from `tree.focusedPane` when the Session has exactly one Pane; that Pane is non-terminal only after the user closes the terminal sibling of a status view, an edge case but the same code path.
- `UITestDriver` `.splitHorizontal` / `.splitVertical` intents (`Testing/UITestDriver.swift:116-131`) — the same calls, used by the UI-test harness.

**Every non-terminal kind on `release/1.2`, what it holds, and what a split from it gets today** (`PaneContentKind`, `BattyKit/Sources/BattyXPCCore/PaneContentKind.swift:28-41`):

| Kind | Directory the Pane holds | What ⌘D from it starts in today |
|---|---|---|
| `git-status` | `GitStatusPaneContent.directoryPath` — frozen at creation from CLI `--path`, else the source Tab's cwd, else `$HOME` (`docs/design/git-status-view.md` §1 "Resolution order"); changed only by "Change Directory…" (`GitStatusPaneView.swift:85`, `:236-248`, `presentChangeDirectoryPanel` `:472-481` → `content.changeDirectory(to:)`, `GitStatusPaneContent.swift:997`) | nothing (`$HOME`) — the repository directory is ignored |
| `process-status` | none of its own. `ProcessStatusPaneContent.Target` is `.pinned(pid)` or `.followingTab(UUID)` (`Runtime/ProcessStatusPaneContent.swift:28-36`; `target` is `public private(set)` at `:117`); a followed Tab has a cwd, reachable through the private `tabLookup` (`:165`) | nothing (`$HOME`) |
| `system-metrics` | none (`SystemMetricsPaneContent.swift` has no directory or path state) | nothing (`$HOME`) |
| `lm-studio-dashboard` | none (`LMStudioDashboardPaneContent.swift` has no directory or path state) | nothing (`$HOME`) |

**Open View from a non-terminal Pane has the same defect, in two shapes.** The typed splits — ⌘G/⇧⌘G Git Status, ⌘J/⇧⌘J Process Status, ⌘Y/⇧⌘Y LM Studio Dashboard, ⌘E/⇧⌘E System Metrics (`ShortcutAction.swift:121-136`), the same kinds in the Pane menu's top-level "Open View" section (`BattyCommands.swift:230-256`, #0453) and its Split Horizontally / Split Vertically submenus (`:303-321`, `:342-363`), and the Command Palette (`CommandPaletteView.swift:245-259`) — all call `WindowRuntime.createPane(kind:direction:)` (`Runtime/WindowRuntime.swift:588-597`) → `tree.splitPane(id: tree.focusedPaneID, kind:...)` → `makePane`'s non-terminal branch (`:341-367`):

- A **Git Status** Pane opened from a non-terminal Pane resolves `sourceCWD` from the same placeholder Tab (`:360-362`), gets `nil`, and monitors `$HOME` — so ⌘G from a Git Status Pane showing `~/Developer/Batty` opens a second Git Status Pane on `$HOME`, not on the same repository.
- A **Process Status** Pane opened from a non-terminal Pane is created as `.followingTab(source.activeTabID)` (`:354`) — it follows the placeholder Tab. `resolveTarget()` (`ProcessStatusPaneContent.swift:366-375`) finds the Tab but `terminalNSView` is `nil` (no surface was ever created), returns `.noSelection`, and the Pane sits on "No process selected" forever, with no indication that it is following a Tab that can never run anything.

**Other "new from here" paths are already kind-gated and are not part of this bug.** ⌘T is dispatched through `focusedTerminalPane` (`BattyShortcuts.swift:120-129`) and `PaneRuntime.addTab(inheritingCWDFrom:)` refuses on a non-terminal Pane (#0332), so there is no new-Tab path from a non-terminal Pane. A new Session (`WindowRuntime.addSession`, `WindowRuntime.swift:185-206`) also inherits only from `focusedTerminalPane` (#0332 B3), so ⌘N from a Git Status Pane starts in `$HOME`; that is a deliberate decision recorded in that method's comment, and this issue leaves it alone (see Notes for the follow-up question).

**Tests and seams that exist.** `SplitTreeCWDTests` (`BattyKit/Tests/BattyKitTests/SplitTreeCWDTests.swift`, three tests) covers terminal→terminal inheritance only; `WindowRuntimeCreatePaneTests` and `AppStateStorePaneSplitTests` drive `createPane`/`splitPane` with `contentFactory: { _ in nil }`; `GitStatusPaneContentTests` has `RecordingScanner`/`RecordingWatcher` and a `makeContent(scanner:…)` helper (`:136`, `:26`, `:179-187`) for constructing a real `GitStatusPaneContent` without an `FSEventStream`; `ProcessStatusPaneContentTests` injects `coreMetricsProvider`. `SplitTree.focusHistory` (`SplitTree.swift:149`, `private(set)`, most-recent-first, de-duplicated) is **not seeded at construction** (`:168-175`), so a Session's original Pane is absent from it until focus has moved away from and back to it — a fallback that reads only `focusHistory` would miss the most common case (one terminal Pane, split a Git Status off it, split a terminal off that). UI: `CLIViewPaneTests` has `launch()` (`BattyUITests/CLIViewPaneTests.swift:27`), `splitViewAndAssertRendered` (`:41`) and `testSplitGitStatusRendersTheFixtureRepository` (`:96-116`) which opens Git Status on `BattyCLI.makeGitRepository(in:)` with `--path`; ⌘D is typed as `app.typeKey("d", modifierFlags: [.command])` (`KeyboardShortcutTests.swift:37`); `BattyUITestHarness.waitForFile(at:timeout:)` (`Support/BattyUITestHarness.swift:131`) waits for a file the shell writes; `SessionCwdRenameTests` clicks the `pane-terminal.<id>` element before typing a shell command. `batty list --json` already carries each Tab's `workingDirectory` (`TopologyTabPayload.workingDirectory`, `BattyXPCCore/TopologyPayload.swift:59`, built from the `tab.workingDirectory` mirror at `XPC/TopologyPayloadBuilder.swift:188`), but the UI-test `CLITopology.Pane` decoder keeps only `tabIDs` (`Support/BattyCLIHarness.swift:33-42`). The UI-test app runs with `BATTY_UI_TEST_TEMP_HOME` (`BattyUITestHarness.swift:27`), so today's fallback lands in a temp home that is never the fixture repository.

## Steps to reproduce

1. In a terminal Pane, `cd ~/Developer/Batty` (any git repository).
2. Press ⌘G (or Pane › Split Horizontally › Git Status). The Git Status Pane shows that repository and has focus.
3. Press ⌘D (or click `toolbar.split-horizontal`, or Pane › Split Horizontally › Terminal, or run `batty pane split --pane <git-status pane id>`).
4. In the new terminal, run `pwd`.

Variant: at step 3 press ⌘G again, or ⌘J.

## Expected behavior

**Rule (decided here): a split inherits the directory of the Pane it was split from, where "the Pane's directory" is defined per kind, and kinds with no directory of their own inherit the directory of the most recently focused terminal Pane in the same Session.** Precedence, resolved once at creation (frozen, like every other cwd inheritance in Batty):

1. **`.terminal` source** — unchanged: the active Tab's `terminal.workingDirectory`, else `terminal.configuration.workingDirectory`. `SplitTreeCWDTests` stays green verbatim.
2. **`.gitStatus` source** — `GitStatusPaneContent.directoryPath`, which is the repository directory at creation and the user's choice after "Change Directory…". Use `directoryPath`, not `repositoryToplevelOrDirectoryPath` (`GitStatusPaneContent.swift:971`): when the Pane was opened on a subdirectory of a repository, the shell the user asked for is in that subdirectory, the same way a terminal split inherits the shell's cwd rather than its repository root.
3. **`.processStatus` source whose target is `.followingTab(id)`** — the followed Tab's cwd (`terminal.workingDirectory ?? terminal.configuration.workingDirectory`), when the Tab still resolves. Decision on the question raised for this issue: yes, a Process Status Pane following a Tab should pass that Tab's directory on. The Pane was created *from* that Tab (`makePane` builds `.followingTab(source.activeTabID)`), the view's whole content is that Tab's foreground process, and when the user splits from it the only directory the view can mean is the one that process is running in. A `.pinned(pid)` or `nil` target has no Tab and falls through to 4.
4. **Any non-terminal source with nothing above** (`.systemMetrics`, `.lmStudioDashboard`, a pinned/empty Process Status, a followed Tab that no longer resolves) — the active Tab's cwd of the **most recently focused terminal Pane in the same Session**: walk `focusHistory` most-recent-first for a `kind == .terminal` Pane, and because `focusHistory` is not seeded at construction (see Description), fall back to the first `.terminal` Pane in the tree's depth-first order (`allPanes`). Hidden Panes count — a hidden terminal still has a shell with a cwd, and hiding is not a reason to forget where the user works.
5. **Nothing found** (a Session whose only Panes are non-terminal) — today's behavior: `workingDirectory: nil`, the shell's default.

Why "most recently focused terminal in the same Session" and not the alternatives: it is the directory the user was last working in before they opened the status view, which is also the directory that status view itself was resolved from (`docs/design/git-status-view.md` §1 step 2, "the previously-focused Pane's active Tab's working directory") and the rule `addSession` already follows for a new Session's first shell. "The Session's directory" is rejected because a Session has no directory on `release/1.2` — `TopologySessionPayload.path` (`TopologyPayload.swift:199-204`) is a derived projection of the first leaf Pane's first Tab's cwd for naming, and that Tab is often not where the user is working in a multi-Pane Session; on `main` a Project-backed Session does have a root folder, and that is noted under "Release" as a possible refinement for the port, not a requirement. "Today's default" is rejected because `$HOME` is never what a user splitting inside a project Session means.

**The same resolved directory feeds the typed-view paths**, because `makePane` is the one place all of them meet:

- A **Git Status** Pane created from a non-terminal source monitors the resolved directory (precedence 2–5 above) when no CLI `--path` was given, so ⌘G from a Git Status Pane opens on the same repository (or whatever "Change Directory…" picked), and ⌘G from a System Metrics Pane opens on the most recently focused terminal's cwd. CLI `--path` still wins (`git-status-view.md` §1 step 1 is unchanged).
- A **Process Status** Pane created from a non-terminal source, with no `--pid`, follows the same Tab the directory came from — the followed Tab of a Process Status source, else the most recently focused terminal Pane's active Tab — instead of the placeholder Tab. When there is no such Tab, the target is `nil` ("No process selected"), which is the honest version of what happens today. `.followingTab` of a real terminal Tab and `.pinned` semantics are unchanged.
- Terminal-to-terminal inheritance, `--command`, `--unique`, `isSessionSelected`, `contentFactory` precedence (an explicit factory still wins outright — `makePane`'s doc comment on why the `if let contentFactory` check runs first) are all unchanged.

Implementation shape (suggested, not prescribed): one internal, pure-ish resolver on `SplitTree` — e.g. `static func inheritedSource(from source: PaneRuntime?, in tree: SplitTree?) -> (workingDirectory: String?, tab: TabRuntime?)` — called from `makePane` for every kind, with the per-kind reads done by casting `source.content` (`as? GitStatusPaneContent` for `directoryPath`, the way `SessionProjectCapture.swift:59` on `main` already does; `as? ProcessStatusPaneContent` for `target`, resolving the followed Tab through the tree's own `tabLookup`). Keep `makePane` the single owner of the decision so a new `PaneContentKind` gets the fallback for free and only has to opt into step 2/3 if it holds a directory. Log the resolved directory and which step produced it at `.info` through the file's existing `logger`.

## Actual behavior

Step 4 prints `$HOME` (`/Users/<user>`), not the repository directory the Git Status Pane is showing. The ⌘G variant opens a second Git Status Pane on `$HOME`; the ⌘J variant opens a Process Status Pane stuck on "No process selected". The same happens from System Metrics, LM Studio Dashboard and Process Status Panes, and from the CLI when `--pane` names (or the focused-pane fallback resolves to) a non-terminal Pane.

## Notes

- Scope is the split and Open View paths from a non-terminal Pane. Not in scope: ⌘N / `addSession` from a non-terminal Pane (deliberately `focusedTerminalPane`-only since #0332 B3; if the user wants a new Session from a Git Status Pane to start in its repository, that is a separate issue and should reuse the resolver this one adds), the Git Status Pane's own "Change Directory…" flow, and any change to how a Git Status Pane picks its directory when opened from a *terminal* Pane (`git-status-view.md` §1 is unchanged for that case).
- `docs/swiftui-observation-rules.md` is binding but barely touched here: every write happens inside `makePane` at creation, from an event-origin call (a keystroke, a menu item, an XPC verb). Do not resolve the directory lazily from a view, and do not hop the resolution into a `Task`.
- Read `terminal.workingDirectory` (the live libghostty value) rather than the `TabRuntime.workingDirectory` mirror inside the resolver: `makePane` is an event-driven read, exactly the case `TabRuntime.swift:35-55` lists as correct for the raw property, and it matches what the terminal branch at `:372-373` already does. The mirror is for views.
- The resolved directory is frozen at creation, like every other cwd inheritance in Batty. The new shell's cwd is then its own; a later "Change Directory…" in the Git Status Pane does not move an already-split terminal.
- `focusHistory` is `@ObservationIgnored private(set)` and `internal`, so `makePane` (a static on `SplitTree`) can read it directly when handed the tree; `splitFocusedPane`/`splitFullDimension`/`splitPane` all have `self` in hand. `tabLookup(for:)` already demonstrates the `[weak tree]` shape if the resolver is stored rather than called inline.
