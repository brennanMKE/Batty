## Description

A full `./build.sh unit` run can fail in `MCPServerTests` (the `batty mcp` stdio server tests from #0647/#0657) because one test exceeds the suite's `.timeLimit(.minutes(1))`, even though the change under test has nothing to do with MCP. Each of those tests sends one or two JSON-RPC lines and reads one or two replies through a scripted runner; it should finish in milliseconds. Taking over 60 s means a test is waiting on something shared and starved, not doing work. This makes unrelated issue branches fail the per-commit unit tier.

## Steps to reproduce

1. Load the host heavily (on 2026-11-18: several concurrent issue-worktree builds plus a Tart VM, load average about 80–99).
2. Run `./build.sh unit` (whole BattyKitTests) in a worktree that does not touch MCP code.
3. Seen in the #0665 and #0663 worktrees: `CHECK UNIT: FAILED`, with one `MCPServerTests` test over its time limit. It was a different test in each run.

## Expected behavior

- Every `MCPServerTests` test finishes far inside its guard, even under heavy load and with the rest of BattyKitTests running in parallel. The 60 s limit stays a hang guard, not something load can reach.
- No test in the suite spawns a real process. A `ScriptedRunner`/`SuspendingRunner` is enough, and the tests already use them.
- No serve loop or test body depends on a contended shared executor: not the main actor, and not a process-wide serial reader shared by every concurrently running server.
- A hang fails at the await that hung, within a bounded guard, and names it. It does not surface only as a suite-wide timeout.

## Actual behavior

Under load, one test takes more than 60 s and fails on the time limit. Alone (`./build.sh unit MCPServerTests`, 18 tests) and in later full runs at lower load, the suite passes.

## Likely causes (to confirm in the plan)

Real processes are not involved. Every `MCPServerTests` test injects `ScriptedRunner` or `SuspendingRunner` (`BattyKit/Tests/BattyKitTests/MCPServerTests.swift:45-79`). Only `SubprocessToolRunnerTests` spawns children (`/bin/sh`, `/usr/bin/env`), through `SubprocessToolRunner` (`BattyKit/Sources/batty/MCPToolRunner.swift:19-110`). That runner already drains its pipes on `DispatchQueue.global()` and resumes through `terminationHandler`, so it does not block the main actor. The likely causes are in the harness and the server's input loop:

1. **`FileHandle.bytes` in the serve loop.** `MCPServer.serve` reads stdin with `for try await byte in input.bytes` (`BattyKit/Sources/batty/MCPServer.swift:97`). On Darwin, Foundation's `FileHandle.AsyncBytes` is believed to do blocking `read(2)` calls behind a shared internal I/O executor. Every test starts its own server (`MCPHarness.init`, `MCPServerTests.swift:89-102`), and Swift Testing runs the 18 tests in parallel. If those reads share one serial reader, or tie up cooperative-pool threads, then while one server waits for input on an idle pipe, the others cannot read. Under load the tests then run in series behind each other, which fits "a different test each run". Confirm how `AsyncBytes` is implemented, or reproduce it: run N harnesses concurrently with one deliberately idle input.
2. **The test bodies run on the main actor.** The package sets `.defaultIsolation(MainActor.self)` for every target, tests included (`BattyKit/Package.swift:5-8`, `:100-110`). `struct MCPServerTests` is not `nonisolated` (`MCPServerTests.swift:121-122`). Each `await harness.reply()`, `await harness.close()` and runner-stream await therefore resumes on the main actor, which the rest of BattyKitTests' main-actor tests share. The harness's synchronous pipe writes (`send`/`sendRaw`, `:104-110`) also run there. `MCPHarness` and `PipeLineReader` are already `nonisolated`; the suite is not.
3. **The cooperative pool is crowded by blocking tests elsewhere.** AGENTS.md has tests that block on child processes made `nonisolated` (for example `ProcessGitStatusScannerTests`), so their blocking runs on cooperative-pool threads. Each `MCPServer` actor, its `serve` task (`Task.detached`, `MCPServerTests.swift:99`) and each `tools/call` `Task` (`MCPServer.swift:182`) need a pool thread to make progress. When load is high and blocked threads hold the pool, those tasks wait.
4. **Unbounded awaits and leaked fixtures.** `reply()` awaits `reader.next()` with no bound of its own (`MCPServerTests.swift:112-115`). A starved test hangs until the suite-wide 60 s limit, and the failure does not say which await stalled. When a `#require` throws, `close()` is skipped, so that test's serve task and pipes stay alive for the rest of the run. Every harness also leaves `output`'s write end open, so its `readabilityHandler` dispatch source is never torn down (`:15-36`). Leaked readers add contention to point 1.

## Recommended direction (the plan may refine it)

- Make `MCPServerTests` (and `MCPLineFramerTests`) `nonisolated`, so no test body hops to the main actor.
- Give `MCPServer` an input source that does not go through `FileHandle.bytes`. One option is a readability-handler or `DispatchIO`-driven `AsyncStream<Data>`, like `PipeLineReader`, owned by each server and fed into `MCPLineFramer`. Another is to inject an `AsyncSequence` of bytes or lines, so tests can drive `serve` with no pipes at all. Production `batty mcp` keeps reading real stdin.
- Make teardown run on every path: `close()` or a `defer`/scoped helper that also closes the output pipe and finishes the reader.
- Give each `reply()`/runner-stream await its own short failure guard (well under the suite limit) that records which await hung. Per AGENTS.md "Asynchronous tests", the guard is only a failure bound, never the mechanism the test relies on. Keep `.timeLimit(.minutes(1))` as the outer hang guard.

## Root cause

Confirmed (plan-phase repro, and the mutation check below): Foundation's `FileHandle.bytes` reads through one process-wide serial reader. A server blocked reading its idle input pipe starves every other `FileHandle.bytes` iterator in the process, so the ~20 parallel `MCPServerTests` servers formed a convoy, each link costing a main-actor turn. Under heavy load that convoy passed the 60 s suite limit.

## Fix

- `MCPInput.chunks(from:)` reads each handle through its own `readabilityHandler` (POSIX `read`, EINTR retry, EAGAIN wait, EOF/error finishes, `onTermination` clears the handler; never closes the handle). `MCPServer.serve(input:output:)` wraps a new generic `serve(chunks:output:)`; `MCPLineFramer` and `MCPCommand` are unchanged.
- Divergence from plan: a dispatch read source never fires at end of a regular file, so `regularFileIsReadToEndOfFile` hung (and `batty mcp < file` would have). For a regular file (`fstat` `S_IFREG`) `MCPInput` reads with a plain loop on a global queue instead; regular-file reads never wait on a writer.
- Tests: suite is `nonisolated` with `.timeLimit(.minutes(2))` (the orchestrator accepted the plan's 2-minute limit, so the 60 s `TestBounds.hangGuard` per-await guards fire first and name the hung step); every reply/signal await is bounded through new `awaitBoundedValue` and named; `MCPHarness.withHarness` closes on every path, and `close()` is idempotent and also closes the output pipe.

## Plan

### Cause, confirmed (2026-11-18, plan phase)

Likely cause 1 is confirmed by reproduction, and it is the root cause. **Foundation's `FileHandle.bytes` reads through one process-wide serial reader.** While one `AsyncBytes` iterator is blocked in `read(2)` on an idle pipe, every other `FileHandle.bytes` iterator in the process is starved, whatever the fd. The implementation is opaque: the SDK `.swiftinterface` shows only `_AsyncBytesBuffer.reloadBufferAndNext()`, so the evidence comes from a standalone repro (scratch `repro.swift`, built `-O`, macOS 27 / Xcode 27, 12 CPUs):

- Start N detached `for try await b in pipe.fileHandleForReading.bytes` loops. Write one line to pipes 1..N-1 and leave pipe 0 idle. After 3 s, **0/7 lines are delivered (N = 8) and 0/1 (N = 2)**. All lines arrive the instant pipe 0 is written. N = 2 on 12 cores rules out cooperative-pool exhaustion: the reader is serial.
- The same setup with a per-handle `readabilityHandler` feeding an `AsyncStream<Data>` delivers **7/7 within 1 s** while pipe 0 stays idle.

In `MCPServerTests` each test starts its own server, and after answering its last line every server goes back to a blocking read on its idle input pipe. It holds the shared reader until its test runs `close()`. So every other running server can read nothing until that test gets a main-actor turn (cause 2: the suite is main-actor-isolated) to receive its reply and close its pipe. The roughly 20 parallel tests form a convoy, and each link costs one main-actor turnaround. At low load that is milliseconds: `./build.sh unit MCPServerTests` passed 20 tests, and the slowest took 0.023 s. Under heavy load, main-actor turns take seconds (#0443 measured delays of up to about 19 s), so the convoy passes 60 s. Whichever test is last in line fails, which is why a different test failed each run. Causes 2 and 4 amplify the convoy but do not cause it: no real wakeup is lost. Cause 3 is a side issue, because the shared reader serializes even with an idle pool. `MCPServer.serve` (`MCPServer.swift:92`) is the only `FileHandle.bytes` use in the repo.

Production `batty mcp` runs one server per process, so it never hits the convoy. It still changes, because the tests must exercise the production input path, and a serial global reader is a hazard for anything else in the process.

### Files

1. **New `BattyKit/Sources/batty/MCPInput.swift`**: `nonisolated enum MCPInput` with `static func chunks(from handle: FileHandle) -> AsyncStream<Data>`. Each call owns its reader, and nothing is shared between servers:
   - Set `handle.readabilityHandler`. In the handler, read with POSIX `read(handle.fileDescriptor, buf, 64 KiB)`, retrying on `EINTR`. Do not use `availableData`, which raises an ObjC exception on a read error, and do not use `read(upToCount:)`, which can wait to fill the count. `n > 0` yields `Data(buf[0..<n])`. `n == 0` (EOF) sets the handler to `nil` and calls `continuation.finish()`. `n < 0` with `EAGAIN` returns and waits for the next event. Any other `n < 0` logs through the file logger and finishes the stream.
   - `continuation.onTermination` sets `handle.readabilityHandler = nil`, so a cancelled consumer tears down the dispatch source.
   - Do not close the handle. The caller owns it, and in production it is stdin.
   - Add a file-scoped `logger` per AGENTS "Logging" (category `MCPInput`).
2. **`BattyKit/Sources/batty/MCPServer.swift`**:
   - Add `func serve<Input: AsyncSequence>(chunks: Input, output: FileHandle) async where Input.Element == Data`. It is the current body with the byte loop replaced by `for try await chunk in chunks { for byte in chunk { if let line = framer.append(byte) { handle(line:output:) } } }`. Keep `framer.finish()` at the end, then the existing catch/log and the cancel-and-await of in-flight calls.
   - Keep `serve(input: FileHandle, output: FileHandle)` as a one-line wrapper: `await serve(chunks: MCPInput.chunks(from: input), output: output)`. This leaves `MCPCommand.swift` unchanged and `MCPLineFramer` unchanged, which keeps the #0657 framing semantics.
   - Update the doc comment on `serve` if it changes. Do not mention the tests.
3. **`BattyKit/Tests/BattyKitTests/AwaitBounded.swift`**: add a value-returning sibling, `nonisolated func awaitBoundedValue<T: Sendable>(bound: TimeInterval = TestBounds.hangGuard, _ operation: @escaping @Sendable () async -> T) async -> T?`. Build it like `awaitBounded`, from `ResumeOnce<T?>` and a `DispatchWorkItem` timeout on `.global(qos: .utility)`. Keep the operation's `Task` and cancel it when the timeout wins, so an `AsyncStream` iterator stuck in `next()` is released. The success path is the operation finishing. The timeout is a failure guard only, so this is not a sleep.
4. **`BattyKit/Tests/BattyKitTests/MCPServerTests.swift`**:
   - `MCPServerTests` → `@Suite(.timeLimit(.minutes(2))) nonisolated struct MCPServerTests`, and `MCPLineFramerTests` → `nonisolated struct`. The outer limit goes from 1 to 2 minutes, a deliberate change from the issue text. Per `docs/async-test-seams.md` §4, every per-await guard uses the shared `TestBounds.hangGuard`, which is 60 s, and no new short literal is added. The suite limit must therefore be longer than 60 s, or the suite limit fires first and the hung step is never named. The time limit stays only the outer hang guard.
   - `PipeLineReader.next(bound: TimeInterval = TestBounds.hangGuard) async -> String?` routes through `awaitBoundedValue`. It returns `nil` on a timeout or EOF, and the harness reports which.
   - `MCPHarness.reply(_ step: String, sourceLocation: SourceLocation = #_sourceLocation) async throws -> MCPJSONValue` becomes `try #require(await reader.next(), "no reply for \(step) within \(TestBounds.hangGuard)s", sourceLocation: sourceLocation)`, followed by the decode. Every call site passes a short step name, for example `"initialize"`, `"first ping (id 7)"`, `"ping after cancel"`.
   - Bound the runner-stream awaits in `cancelledNotificationCancelsTheInFlightCall` too. Use a small helper, such as `MCPHarness.awaitSignal(_ stream: AsyncStream<Void>, _ step: String, sourceLocation:)`, that uses `awaitBoundedValue` and `#require`s a non-nil value, with steps `"runner started"` and `"runner saw cancellation"`. Iterate the stream inside the helper with `for await _ in stream { return }`, not a shared iterator captured across tasks.
   - **Teardown on every path:** add `static func withHarness<T>(runner:flags:environment:_ body: (MCPHarness) async throws -> T) async throws -> T`. It runs `body` in `do`/`catch`, always awaits `harness.close()` before returning or rethrowing, and wraps every test, including the private `initializeInstructions` helper. `close()` must be idempotent and complete:
     1. `try? input.fileHandleForWriting.close()`.
     2. Await `serving.value` through `awaitBounded`. On a timeout, call `Issue.record("serve did not return after input closed")` and cancel `serving`.
     3. `try? output.fileHandleForWriting.close()`, so `PipeLineReader` sees EOF, clears its handler and finishes its stream.
     A second call is harmless: the closes are `try?` and awaiting a finished `Task` returns immediately. `finalLineWithoutNewlineIsProcessedAtEndOfFile` still closes mid-test and then reads its reply. That works because the reply line is buffered in the `AsyncStream` before EOF finishes it. `serveReturnsWhenInputCloses` keeps its explicit `close()`.
   - Keep every test on `ScriptedRunner`/`SuspendingRunner`. No real process is spawned. Real-child coverage stays in `SubprocessToolRunnerTests`.

### Tests

New:
- `MCPServerTests.idleInputOnOneServerDoesNotStallAnother`: the regression test for the root cause.
  1. Harness A sends `ping` id 1 and awaits its reply. That reply is a real event proving A's serve loop is running and has gone back to reading its now-idle input.
  2. Without closing A, harness B sends `ping` id 2. `B.reply("ping on B while A idles")` must arrive.
  3. Close both.
  Against the old `FileHandle.bytes` serve, B's reply cannot arrive while A idles, so the test fails at that named `#require` after the guard. **The implementer must prove this as a mutation check.** Temporarily point the FileHandle wrapper back at a `FileHandle.bytes` loop, run only this test, see it fail at the named step, revert, and record the result in `## Verification`. If ordering lets it pass against the old code (B's read could have won the reader), state that, and strengthen the test by starting K idle harnesses (for example 4) that each answered one ping before B.
- `MCPInputTests` (new file `BattyKit/Tests/BattyKitTests/MCPInputTests.swift`, `nonisolated`):
  - `pipeChunksArriveAndFinishAtEndOfFile`: write bytes to a `Pipe`, close the write end, collect `MCPInput.chunks(from:)` through `awaitBoundedValue`, and assert that the concatenated data matches and the stream finishes.
  - `regularFileIsReadToEndOfFile`: same check for a temporary file opened with `FileHandle(forReadingFrom:)`, because stdin can be a redirected file. Use a temporary directory and clean it up.
  - `cancellingTheConsumerClearsTheReadabilityHandler`: cancel the consuming task and assert `handle.readabilityHandler == nil` once the cancelled task's `value` has been awaited. `onTermination` runs synchronously on cancellation, before `value` returns.

Existing tests guarding the area, all of which must still pass unchanged in substance (only the `reply(step)`/`withHarness` wrapping changes):
- `MCPServerTests` (all 18 functions, 20 cases), including the #0657 framing set: `rawLineSeparatorInsideAStringIsOneMessage` (U+2028/U+2029/NEL), `loneCarriageReturnMidLineIsNotAMessageBoundary`, `crlfTerminatedLineIsParsed`, `finalLineWithoutNewlineIsProcessedAtEndOfFile`, and `serveReturnsWhenInputCloses`.
- `MCPLineFramerTests` (3).
- `SubprocessToolRunnerTests`, `MCPToolCatalogTests`, `MCPInstructionsTests`.
