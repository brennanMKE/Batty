## Description

`scripts/build-beta.sh` builds into its own DerivedData tree (`BUILD_ROOT="$REPO/beta-build"`, `DERIVED_DATA="$BUILD_ROOT/DerivedData"` — `scripts/build-beta.sh:81-82`, passed as `-derivedDataPath` at `:192`). That tree accumulates build products that `xcodebuild` no longer manages, and when a dependency relocates an emitted header, the stale copy shadows the new one and breaks the Beta build — while Prod continues to build fine.

Verified on 2026-08-07, during #0311's reproduction attempt:

- The Beta build failed with `cannot find 'ghostty_surface_foreground_pid' in scope` and `cannot find 'ghostty_surface_tty_name' in scope`, both in the vendored `Sources/GhosttyTerminal/Surface/TerminalSurface.swift` (libghostty-spm package source).
- Root cause: **#0286's bump to libghostty-spm 1.3.2 moved the vendored header from `include/ghostty.h` to `include/libghostty/ghostty.h`** (the namespaced-xcframework-headers change #0286's Notes flagged as a possible import-path break). The Beta products directory kept **both layouts**: a stale `beta-build/DerivedData/Build/Products/Debug/include/ghostty.h` and a stale `include/module.modulemap`, both dated **May 27** (the 1.2.2 era), alongside the correct `include/libghostty/{ghostty.h,module.modulemap}` pair dated **Jul 27**. The compiler resolved the un-namespaced stale header first and got 1.2.2 declarations — which lack the two 1.3.x symbols above.
- **Prod was unaffected**: the default DerivedData tree has only the namespaced `Debug/include/libghostty/` pair.
- Deleting the two stale files made `scripts/build-beta.sh` succeed. **That was a manual fix to a gitignored build tree; nothing in the repo prevents recurrence** — the next dependency that renames or relocates an emitted header will do this again. (As of filing, `beta-build/DerivedData/Build/Products/Debug/include/` contains only the correct `libghostty/` pair.)

**Impact.** The Beta build path was broken from #0286's header relocation (landed 2026-08-01) until 2026-08-07 without anyone noticing, because Prod builds fine and the pre-commit gate exercises Prod. It surfaced only when it blocked the reproduction attempt on #0311 — the single most valuable piece of evidence on that issue — for an entirely unrelated reason. Beta is what gets exercised during development (UI tests run against it; #0311's repro needed it), so a silently broken Beta removes the main safety net.

## Resolution notes

> 🟢 Resolved 2026-08-08 — `scripts/build-beta.sh` now wipes `beta-build/DerivedData` whenever the resolved package pins change, detected by hashing three pin inputs against a stamp file in the gitignored build tree.

Approach 3 of the three the issue listed, chosen by the user along with explicit go-ahead to modify `scripts/build-beta.sh` (and only that file). It targets the actual trigger — a dependency changing — instead of paying a full rebuild on every Beta build.

## Root cause

`xcodebuild` does not clean build products it no longer manages. `build-beta.sh` builds into a long-lived DerivedData tree, so when #0286 relocated libghostty's emitted header from `include/ghostty.h` to `include/libghostty/ghostty.h`, the stale un-namespaced copy stayed and the compiler resolved it first — yielding 1.2.2 declarations against a 1.3.2 pin. Prod was unaffected because its default DerivedData tree only ever had the namespaced pair. The pre-commit gate exercises Prod, so nothing caught it for six days.

## Fix

A guard in `scripts/build-beta.sh`, placed after the `Active.xcconfig` snapshot and `EXIT` trap are armed so every failure path still restores the environment:

- Hashes the concatenation of three pin inputs — `BattyKit/Package.swift`, `BattyKit/Package.resolved`, and `Batty.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved` — with `shasum -a 256`, in fixed array order.
- Compares against `beta-build/.package-resolved-stamp`.
- On a match, skips and keeps the tree. On a mismatch **or a missing stamp**, `rm -rf`s the whole `$DERIVED_DATA`, then writes the new hash.
- Hard-fails with `exit 1` and a stderr message if any pin input is missing, rather than letting an empty hash compare equal and silently skip.

The clean is the whole DerivedData tree rather than just `Build/Products/.../include/`, because it is gated by a rare event and a narrower clean would leave stale `.swiftmodule`s and module-cache entries for any dependency change that isn't a header relocation.

## Review

Reviewer: `claude-opus-5`, two rounds. Round 1 found that the first cut would have failed at exactly the job it was built for.

The guard originally hashed only the xcodeproj `Package.resolved` — but #0286's own Gotchas record that `xcodebuild -resolvePackageDependencies` resolves into DerivedData and **does not write back** to that file; it is hand-maintained. The reviewer showed from git history that the two resolved files diverge in both directions: `86c16c7` (#0212, a real libghostty pin switch) touched the xcodeproj file but not `BattyKit/Package.resolved`, while `464d232` (#0250) touched `BattyKit/Package.resolved` but not the xcodeproj file. The second shape is what `swift package resolve` produces and is the natural bump sequence — and in that shape the guard would have compared equal and skipped, **permanently**, since nothing rewrites that file automatically.

It also extracted the block into a harness and drove five states, finding that a missing pin-input file left the computed hash empty, compared equal to an empty stored hash, took the skip branch, and — if a stamp already existed — wrote an empty stamp that disabled the guard from then on.

Round 2 verified both fixes, and went past the prescription: rather than assume round 1's three-file suggestion was complete, it checked that no *fourth* tracked file can move a pin (`project.pbxproj` declares no `XCRemoteSwiftPackageReference`; `Batty.xcworkspace/xcshareddata/` does not exist; every other `Package.resolved` on disk is inside a gitignored checkout). It confirmed hard-fail is defended in depth — `set -euo pipefail` makes the `cat`-through-`shasum` abort anyway if a file vanishes between the pre-check and the hash — and ran the real script end to end.

## Verification

Both fixes were demonstrated in both states, not just asserted.

- **First run / no stamp** — cleaned, `BUILD SUCCEEDED`, `include/` afterward containing only the correct `libghostty/{ghostty.h,module.modulemap}` pair.
- **Unchanged rerun** — skipped the clean, incremental build in ~8.5s.
- **F1's specific case** — a change to `BattyKit/Package.swift` alone, leaving the xcodeproj file untouched (the `464d232` shape that was previously invisible), fired the guard. The reviewer independently confirmed the union hash differs for a change to `BattyKit/Package.resolved` alone as well.
- **F2's case** — with a pin input moved away, the script exited 1, emitted both stderr lines, invoked no `xcodebuild`, left the stamp untouched, and still restored `Active.xcconfig` to Prod via the trap.
- **Full run by the reviewer** — skip branch, `BUILD SUCCEEDED`, product at `beta-build/Products/Batty Beta.app`, exit 0, `Active.xcconfig` restored, `project.pbxproj` not dirtied. `xcodebuild -showBuildSettings` for `Batty (Prod)` then resolved `PRODUCT_NAME = Batty` — the environment was genuinely put back.

`scripts/build.sh unit` — **969 tests in 112 suites passed**, `** TEST SUCCEEDED **`. `zsh -n scripts/build-beta.sh` clean. After all the perturbation runs, `git status --porcelain` is empty and `BattyKit/Package.swift`, both `Package.resolved` files, and `project.pbxproj` are byte-identical to `main`.

## Gotchas

- **The xcodeproj `Package.resolved` is hand-maintained, not build-maintained.** `xcodebuild -resolvePackageDependencies` resolves into DerivedData and never writes back to it (#0286). Any future logic that treats it as the authoritative pin record will be wrong; that assumption is exactly what this issue's first cut got wrong.
- **Two residual gaps are accepted and documented in the script's comment.** Range-pinned dependencies (`Sparkle` and `swift-argument-parser` use `from:`) can re-resolve to a new version with no repo file changing, and `SlidingTabs` is a local `path:` package *outside* the repo — hashing it would force a clean on every local edit. If either ever relocates an emitted header, the stale-products hazard returns with no signal.
- **If Xcode ever materializes `Batty.xcworkspace/xcshareddata/swiftpm/Package.resolved`**, that becomes a fourth pin input this guard will not see. It does not exist today.
- **Never pipe `build-beta.sh` through `head`.** SIGPIPE kills the script before its `EXIT` trap runs, leaving `Configuration/Active.xcconfig` switched to Beta — which then silently poisons the next Prod build. This bit the implementer during verification. Redirect to a file instead.

## Steps to reproduce

The specific instance was fixed manually, so this is the general recurrence recipe, not a currently failing state:

1. Build Beta via `scripts/build-beta.sh` at a dependency revision that emits header X into the products `include/` directory.
2. Bump the dependency to a revision that relocates or renames that header (e.g. into a namespaced subdirectory).
3. Build Beta again without cleaning `beta-build/DerivedData`.

## Expected behavior

A Beta build after a dependency bump compiles against exactly the headers the pinned revision emits, or fails loudly pointing at the stale-products condition — never silently compiles against a previous revision's header.

## Actual behavior

`xcodebuild` does not clean build products it no longer manages, so the abandoned header layout persists in `beta-build/DerivedData/Build/Products/.../include/` and shadows the current one, producing "cannot find symbol in scope" errors in vendored package sources that look like a new regression.

## Notes

- **Fix directions (options, not a decision):**
  1. Have `build-beta.sh` clear the products `include/` directory (or the whole products dir) before building.
  2. Detect the stale-layout condition (e.g. both `include/ghostty.h` and `include/libghostty/ghostty.h` present) and fail or clean with a message — narrow, but only covers this dependency.
  3. Clean the Beta DerivedData whenever the resolved package revision changes (compare `Package.resolved` against a stamp file in `beta-build/`).
- **The hazard is general, not libghostty-specific**: `xcodebuild` will not clean build products it no longer manages, so *any* dependency that relocates or renames an emitted header can leave a shadowing copy behind in a long-lived custom DerivedData tree.
- **Open question, unverified:** #0286's own verification records a successful Beta runtime test on 2026-08-01, after the bump. Either that Beta build took a different path than `scripts/build-beta.sh`'s DerivedData tree, or the header-resolution order is unstable across incremental states. Not investigated; what is verified is the failure observed 2026-08-07, the stale files' dates and locations, and that deleting them fixed the build.
- **`scripts/` is a restricted area per CLAUDE.md** — implementing any of the above needs the user's explicit go-ahead before touching `scripts/build-beta.sh`.

## Relation
