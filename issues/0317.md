# 0317 — scripts/build-beta.sh retains stale build products across dependency header-layout changes, silently breaking Beta builds

| | |
|---|---|
| **Status** | open |
| **Module** | Build |
| **Platform** | macOS |
| **First seen** | 2026-08-07 |

## Description

`scripts/build-beta.sh` builds into its own DerivedData tree (`BUILD_ROOT="$REPO/beta-build"`, `DERIVED_DATA="$BUILD_ROOT/DerivedData"` — `scripts/build-beta.sh:81-82`, passed as `-derivedDataPath` at `:192`). That tree accumulates build products that `xcodebuild` no longer manages, and when a dependency relocates an emitted header, the stale copy shadows the new one and breaks the Beta build — while Prod continues to build fine.

Verified on 2026-08-07, during #0311's reproduction attempt:

- The Beta build failed with `cannot find 'ghostty_surface_foreground_pid' in scope` and `cannot find 'ghostty_surface_tty_name' in scope`, both in the vendored `Sources/GhosttyTerminal/Surface/TerminalSurface.swift` (libghostty-spm package source).
- Root cause: **#0286's bump to libghostty-spm 1.3.2 moved the vendored header from `include/ghostty.h` to `include/libghostty/ghostty.h`** (the namespaced-xcframework-headers change #0286's Notes flagged as a possible import-path break). The Beta products directory kept **both layouts**: a stale `beta-build/DerivedData/Build/Products/Debug/include/ghostty.h` and a stale `include/module.modulemap`, both dated **May 27** (the 1.2.2 era), alongside the correct `include/libghostty/{ghostty.h,module.modulemap}` pair dated **Jul 27**. The compiler resolved the un-namespaced stale header first and got 1.2.2 declarations — which lack the two 1.3.x symbols above.
- **Prod was unaffected**: the default DerivedData tree has only the namespaced `Debug/include/libghostty/` pair.
- Deleting the two stale files made `scripts/build-beta.sh` succeed. **That was a manual fix to a gitignored build tree; nothing in the repo prevents recurrence** — the next dependency that renames or relocates an emitted header will do this again. (As of filing, `beta-build/DerivedData/Build/Products/Debug/include/` contains only the correct `libghostty/` pair.)

**Impact.** The Beta build path was broken from #0286's header relocation (landed 2026-08-01) until 2026-08-07 without anyone noticing, because Prod builds fine and the pre-commit gate exercises Prod. It surfaced only when it blocked the reproduction attempt on #0311 — the single most valuable piece of evidence on that issue — for an entirely unrelated reason. Beta is what gets exercised during development (UI tests run against it; #0311's repro needed it), so a silently broken Beta removes the main safety net.

## Steps to reproduce

The specific instance was fixed manually, so this is the general recurrence recipe, not a currently failing state:

1. Build Beta via `scripts/build-beta.sh` at a dependency revision that emits header X into the products `include/` directory.
2. Bump the dependency to a revision that relocates or renames that header (e.g. into a namespaced subdirectory).
3. Build Beta again without cleaning `beta-build/DerivedData`.

## Expected behavior

A Beta build after a dependency bump compiles against exactly the headers the pinned revision emits, or fails loudly pointing at the stale-products condition — never silently compiles against a previous revision's header.

## Actual behavior

`xcodebuild` does not clean build products it no longer manages, so the abandoned header layout persists in `beta-build/DerivedData/Build/Products/.../include/` and shadows the current one, producing "cannot find symbol in scope" errors in vendored package sources that look like a new regression.

## Notes

- **Fix directions (options, not a decision):**
  1. Have `build-beta.sh` clear the products `include/` directory (or the whole products dir) before building.
  2. Detect the stale-layout condition (e.g. both `include/ghostty.h` and `include/libghostty/ghostty.h` present) and fail or clean with a message — narrow, but only covers this dependency.
  3. Clean the Beta DerivedData whenever the resolved package revision changes (compare `Package.resolved` against a stamp file in `beta-build/`).
- **The hazard is general, not libghostty-specific**: `xcodebuild` will not clean build products it no longer manages, so *any* dependency that relocates or renames an emitted header can leave a shadowing copy behind in a long-lived custom DerivedData tree.
- **Open question, unverified:** #0286's own verification records a successful Beta runtime test on 2026-08-01, after the bump. Either that Beta build took a different path than `scripts/build-beta.sh`'s DerivedData tree, or the header-resolution order is unstable across incremental states. Not investigated; what is verified is the failure observed 2026-08-07, the stale files' dates and locations, and that deleting them fixed the build.
- **`scripts/` is a restricted area per CLAUDE.md** — implementing any of the above needs the user's explicit go-ahead before touching `scripts/build-beta.sh`.

## Relation

- Caused by the header relocation in **#0286** (libghostty-spm 1.2.2 → 1.3.2, namespaced xcframework headers), whose Notes flagged the import-path break risk.
- Discovered while unblocking the Beta reproduction for **#0311**; that issue's Gotchas record the reviewer's manual fix and advise checking for stale files on any "symbol not found despite identical header" Beta failure.
