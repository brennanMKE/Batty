## Description

Settings → Appearance shows a single Theme picker whose section header reads "Theme (Dark)" or "Theme (Light)" depending on the appearance the Settings window is currently displaying. In Dark mode the user can only set the Dark theme; there is no way to configure the Light theme without switching the whole system to Light. Both per-appearance slots already exist in storage (`ThemePreference.darkDefaultsKey` / `lightDefaultsKey`, from #0241) — only the UI is one-at-a-time.

Show both pickers at once: a "Light" theme picker and a "Dark" theme picker, each reading/writing its own slot, so the user can configure both regardless of the current system appearance.

## Steps to reproduce

1. With the system in Dark mode, open Settings → Appearance.
2. Observe a single "Theme (Dark)" picker; there is no Light theme picker.

## Expected behavior

The Appearance tab shows separate Light and Dark theme pickers, both editable at any time. Changing the picker for the appearance currently displayed re-themes live surfaces; changing the other appearance's picker persists the choice and takes effect when the system switches to that appearance.

## Actual behavior

Only one Theme picker is shown, bound to the current appearance's slot; the other appearance's theme can't be set from here.

## Notes

- Current code: `AppearanceSettingsView` (`SettingsView.swift:106`) uses `themeBinding` (`colorScheme == .dark ? $darkThemeName : $lightThemeName`) and `themeLabel` to drive a single picker (`SettingsView.swift:120-171`).
- Live apply must be appearance-aware: `applyThemeToAllSurfaces` should fire only when the edited slot matches the current `colorScheme`; the off-appearance slot just persists (the existing `AppearanceObserver` → `applyGlobalThemeForCurrentAppearance()` path applies it on the next appearance switch).

## Fix

Replaced the single appearance-dependent picker (and its `themeBinding`/`themeLabel` helpers) in `AppearanceSettingsView` with a `"Theme"` section containing two always-visible pickers — "Light" (bound to `lightThemeName`) and "Dark" (bound to `darkThemeName`) — built from a shared `themePicker(_:selection:appliesNow:)` helper. `appliesNow` is `colorScheme == .light` / `.dark` for the respective row, so only the slot matching the appearance currently displayed calls `store.applyThemeToAllSurfaces` on change; the other slot just persists via `@AppStorage` and is applied by `AppearanceObserver` when the system switches to that appearance.

## Verification

`scripts/build.sh unit` — build succeeded; **337 unit tests in 40 suites passed**, no regressions and no dead-code warnings (the removed `themeBinding`/`themeLabel` and the still-used `colorScheme` are clean). This is a SwiftUI Settings view, so the layout/behavior is not unit-testable — visual confirmation is the user's (below).

- `BattyKit/Sources/BattyKit/Views/SettingsView.swift` — `AppearanceSettingsView` now shows both Light and Dark theme pickers via a `themePicker` helper; removed the single-slot `themeBinding`/`themeLabel`.
