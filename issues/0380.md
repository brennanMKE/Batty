## Description

`batty new [<path>]` (and its bare alias `batty <path>`) is the only shipped mutation that acknowledges nothing. `NewSessionCommand.run()` (`BattyKit/Sources/batty/BattyCLI.swift`) builds a `batty://` URL and hands it to `/usr/bin/open`; exit 0 means LaunchServices accepted the URL, not that a Session exists. Nothing is printed. Every other agent-facing mutation — `pane split` (#0282), `pane close` (#0283), `notify` (#0284) — went to XPC precisely so the caller could tell success from a stale id, and `pane split` prints the new Pane id for chaining. Session creation, the *first* step of any agent workflow, is the one step that still leaves the caller blind.

The project already concedes this. `docs/batty-cli-agent-workflows.md` ships a **~50-line zsh snapshot-and-poll script** (`batty list --json` before, `batty new`, then up to 50 polls at 0.1 s with a `jq` slurpfile diff to find a Session whose `path` matches and whose id is new), and the doc's own "Current limitations relevant to agents" section says: "`new` is the only shipped mutation without an app acknowledgement or returned object ID. Use the snapshot-and-poll pattern above." Every agent integrating with Batty is expected to reimplement that script, correctly, including its `mktemp`/`trap` cleanup and its jq expression.

**The poll belongs inside the CLI.** All the machinery already exists: `AppConnectDance`, `BoundedPoll` (`BattyKit/Sources/BattyXPCCore/BoundedPoll.swift`), and the `list` topology verb. The CLI should do what the doc tells the agent to do, once, in Swift, and print the answer.

## Expected behavior

`batty new <path>`:

1. Snapshots topology over XPC (`list`) when the broker answers.
2. Dispatches the `batty://` URL exactly as it does today.
3. Polls `list` until a Session appears whose `path` matches the resolved directory and whose id was not in the snapshot.
4. Prints the new **Session id** on line 1 and its **`focusedPaneID`** on line 2.
5. `--json` prints `{"sessionID": "…", "paneID": "…"}` instead.

So `session_id=$(batty new ~/proj | head -1)` replaces the whole shipped script.

## Pinned decisions

These are settled; an implementer should build them as written rather than re-deciding:

- **Do not add a `sessionNew` XPC verb.** The `batty://` URL scheme keeps its one unmatched capability — launching the app when it is not running (#0265: "wins outright, and it is not close"; reaffirmed in #0257's transport amendment, which explicitly kept `session new` on the URL scheme). Creation stays on one code path; the acknowledgement is a *read*, and XPC already does reads.
- **Bounded poll of roughly 5 s**, reusing `BoundedPoll` rather than a hand-rolled loop — the same budget the doc's script uses (50 × 0.1 s).
- **`--no-wait` restores today's fire-and-forget behavior** for scripts that genuinely do not care, and for the interactive `batty .` habit.
- **Do not invent new exit codes.** When the app was not running and XPC never comes up within the budget, exit with the existing transport vocabulary from `BattyXPCCore/XPCExitCode.swift` (`2` broker unreachable, `3` app unavailable, `4` request failed, `5` app terminated, `6` running but unregistered, `7` bundle unresolved).
- **Degraded path is explicit, not silent:** when the pre-dispatch XPC snapshot is unavailable but `open` succeeded, print nothing on stdout, write a one-line note to stderr saying the Session was created but could not be identified, and exit 0. Document that case in `docs/batty-cli-agent-workflows.md`.
- **Round 3 review (B1): ambiguity between the cold-launch default Session and the requested-path Session is resolved by counting *simultaneously visible* candidates, not by a tiebreak.** A cold launch creates two Sessions (the default `Session 1`, usually at `$HOME`, plus the requested one — #0251), so `batty new ~` (or bare `batty`/`batty .` run from home) can make both qualify against the empty pre-launch snapshot at the same time. `NewSessionResolver.findNewSessions` returns every qualifying Session; `NewSessionCommand.pollForNewSession` treats exactly one as a match, zero as "keep polling," and more than one as "keep polling, then report the ambiguity explicitly (exit `4`, distinct message) if it never resolves" rather than guessing. Two more-thorough alternatives were considered and declined for this issue:
  - **`TopologyWindowPayload.selectedSessionID` as a tiebreak** (`addSession` sets it to the URL-created Session) — declined. Round 3 believed pairing this with the guard would additionally close the *sequential* ordering (the default Session's path resolving before the requested Session even appears in topology, or the URL being dropped outright, #0251); round 4 review's probe test disproved that — `selectedSessionID` still equals the default Session's id in exactly that window, since nothing has run yet to reassign it, so the filter would not have excluded it. Declining it therefore rests only on it being unable to fully close the gap without also tracking cross-snapshot state (e.g. "has this window's session count grown"), which is a bigger change than a same-snapshot filter and was not attempted.
  - **A client-supplied token in the `batty://` URL, echoed back in topology** — the fully robust fix, and the one that would also close the "two agents racing on the same path" caveat in `docs/batty-cli-agent-workflows.md` and the sequential-ordering residual above. Declined as out of scope for this issue: it is a transport-shape change (a new query parameter and a topology field to carry it back), not a fix to the matching logic `#0380` already owns. File it as its own issue if the residual below turns out to matter in practice.
- **Round 4 review (B1): the simultaneous-collision guard above is accepted as narrowing, not closing, the cold-launch `$HOME` defect — documented, not deepened, this round.** `NewSessionCommand.pollForNewSession`'s guard only ever sees one `list` response at a time; it cannot distinguish "the default Session's path resolved first, and the requested Session hasn't appeared in topology yet" from "the default Session's path resolved first, and there never will be a requested Session" (URL dropped, #0251) — both leave the default Session as the sole, unambiguous-looking match at that instant, so it is still returned as if it were the answer. Reviewer offered two equally acceptable fixes: extend the guard (declined above, since the specific extension proposed does not actually close the gap) or document the residual honestly. This round took the second: comments and doc prose that overstated the guard's coverage (`NewSessionResolver.findNewSessions`'s doc comment, `NewSessionCommand`'s `.notRunningYet` comment, `docs/batty-cli-agent-workflows.md`) were corrected to say "simultaneous" explicitly, and this pinned decision + `## Gotchas` record the residual. A structurally sound close (e.g. additionally requiring the owning window to already contain more than one Session before trusting a single match, so the guard never fires before the requested Session has at least been created) was reasoned through but not implemented — untested beyond source-level reasoning, and broadening scope beyond what round 4 asked for. File it as a follow-up if the residual proves to matter in practice.

## Notes

- **Matching by path is not sufficient on its own** — the user may already have a Session on that directory, and the doc's script handles this by diffing against the pre-dispatch snapshot's id set. Keep that: match on "path equal **and** id not in the snapshot". This is also why the snapshot has to be taken *before* the URL dispatch.
- `TopologySessionPayload.path` is the Session's anchor working directory and is **optional** — it is `nil` until it resolves. A Session can therefore appear in the poll before its path does; keep polling rather than matching a `nil` path, and let the bound expire rather than returning the wrong Session.
- The path the CLI matches against must be the same resolved absolute path it puts in the URL (`resolvePath(path)`), not the user's raw argument.
- **First launch is the slow case.** When the app is not running, `open` triggers a cold launch, XPC registration, and broker handoff before any `list` can answer; the ~5 s budget covers a warm app comfortably and a cold launch marginally. If the bound proves too tight in practice, record the new number as a judgment call rather than making the poll unbounded.
- **Update the docs in the same change.** `docs/batty-cli-agent-workflows.md`'s snapshot-and-poll section becomes "this is what `batty new` does for you"; the "Current limitations" bullet quoted above is deleted. Note that [#0368](0368.md) is separately correcting stale content in that same file (its exit-code table stops at `5`, missing `6` and `7`) — coordinate so the two edits do not collide.

## Gotchas

Two things genuinely need a live, signed app to learn — nobody with launch
access has run either against this branch yet:

- **A real cold-launch timing trial** (quit Batty, run `batty ~`, observe)
  would answer the one question source reading can't: which lands first in
  practice, the default `Session 1`'s OSC 7 report or the requested
  Session's own creation/OSC 7 — i.e. does a cold `batty ~` normally
  *succeed* (both resolve close enough together that the guard's ambiguity
  path catches them, or the requested Session's path simply wins the race)
  or normally *exit `4`* on the ambiguity path, or (the accepted residual,
  see the round-4 pinned decision above) occasionally return `Session 1`'s
  id outright. The 150 × 0.1 s cold-launch budget (~166 s true worst case,
  corrected in round 3 review) is also unverified against a real cold
  launch end to end — it's a judgment call from `AppConnectDance
  .resolveEndpoint`'s own cold-start reference point, not a measurement.
- **The degraded path (`fetchPreDispatchState` -> `.degraded`) against an
  actually-disabled broker Login Item.** Its branches are exercised in code
  review and by construction (mirrors `AppConnectDance`'s own
  `NoEndpointRegisteredDecision` reuse), not by an observed run where the
  broker is genuinely unreachable or the app is genuinely running but
  unregistered.

Everything else round 4 review checked — the ambiguity-guard dispatch
itself (`matches.count` 0/1/>1), the endpoint-never-seen timeout, the
broker-unreachable-vs-app-unavailable distinction — is now covered
in-process by `NewSessionCommandTests.swift` via `pollForNewSession`'s
injected `fetchTopology` parameter (#0380 round 4 review, B2); it does not
need a live app.

- **B1's cold-launch `$HOME` collision is only half closed, and that's a
  pinned decision, not an oversight — see "Round 4 review (B1)" above.**
  The guard correctly handles the default Session and the requested
  Session being visible *simultaneously* (unit-tested at the resolver
  layer: `returnsBothCandidatesWhenAColdLaunchDefaultSessionCollidesWithTheRequestedPath`,
  and end to end via `pollForNewSession`'s
  `matchesCorrectSessionOnceAmbiguityResolves` /
  `staysAmbiguousUntilTheBoundExpires` tests). It does not close the
  *sequential* case — the default Session's path resolving, and being the
  only visible match, before the requested Session appears in topology at
  all (or ever, if the URL is dropped, #0251) — which
  `NewSessionCommandTests.singleTransientDefaultSessionMatchIsStillReturned`
  demonstrates still returns the wrong id. Narrower than the pre-`#0380`
  behavior's total silence, but not closed.
- **Manual check worth running once a live app is available — read the
  designed outcomes first, since only one of three is a bug:** quit Batty,
  run `batty ~` (or bare `batty` from `$HOME`), and see which of three
  outcomes happens. (1) The printed Session id is the newly created one —
  the common case, and success. (2) Exit `4` with the "multiple sessions
  matched" message — also success: the guard caught the ambiguity and
  correctly declined to guess. (3) The printed id is `Session 1`'s — the
  accepted residual above, not a fresh regression; still worth recording
  if observed, since it confirms the residual is reachable in practice and
  not just in theory.
- **`batty capabilities`' machine-readable exit-code roster is now slightly stale for `new`.** `CapabilitiesPayload.standardExitCodes` (from `#0384`) describes exit `4` as "Delivered to the app, which replied with a failure" — true for every other verb, but not for `new`'s poll-timeout case (nothing was delivered to or rejected by the app; the poll simply never confirmed the Session, or saw more than one candidate). `docs/batty-cli-agent-workflows.md` documents the exception in prose; the machine-readable roster agents are told to trust (`batty capabilities --json`) does not. No verb-roster change is needed (`CapabilitiesCommand.verbs()` reads command abstracts live), but `standardExitCodes`' exit-`4` description is worth revisiting under `#0384` if this becomes confusing in practice — flagging here rather than editing that already-resolved issue's file directly.
