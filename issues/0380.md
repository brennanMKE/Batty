# 0380 — `batty new` returns no Session id and no confirmation, so scripted Session creation needs a fifty-line poll workaround

| | |
|---|---|
| **Status** | open |
| **Module** | App / Session |
| **Platform** | macOS |
| **First seen** | 2026-08-27 |

## Description

`batty new [<path>]` (and its bare alias `batty <path>`) is the only shipped mutation that acknowledges nothing. `NewSessionCommand.run()` (`BattyKit/Sources/batty/BattyCLI.swift`) builds a `batty://` URL and hands it to `/usr/bin/open`; exit 0 means LaunchServices accepted the URL, not that a Session exists. Nothing is printed. Every other agent-facing mutation — `pane split` (#0282), `pane close` (#0283), `notify` (#0284) — went to XPC precisely so the caller could tell success from a stale id, and `pane split` prints the new Pane id for chaining. Session creation, the *first* step of any agent workflow, is the one step that still leaves the caller blind.

The project already concedes this. `docs/batty-cli-agent-workflows.md` ships a **~50-line zsh snapshot-and-poll script** (`batty list --json` before, `batty new`, then up to 50 polls at 0.1 s with a `jq` slurpfile diff to find a Session whose `path` matches and whose id is new), and the doc's own "Current limitations relevant to agents" section says: "`new` is the only shipped mutation without an app acknowledgement or returned object ID. Use the snapshot-and-poll pattern above." Every agent integrating with Batty is expected to reimplement that script, correctly, including its `mktemp`/`trap` cleanup and its jq expression.

**The poll belongs inside the CLI.** All the machinery already exists: `AppConnectDance`, `BoundedPoll` (`BattyKit/Sources/BattyXPCCore/BoundedPoll.swift`), and the `list` topology verb. The CLI should do what the doc tells the agent to do, once, in Swift, and print the answer.

## Expected behavior

`batty new <path>`:

1. Snapshots topology over XPC (`list`) when the broker answers.
2. Dispatches the `batty://` URL exactly as it does today.
3. Polls `list` until a Session appears whose `path` matches the resolved directory and whose id was not in the snapshot.
4. Prints the new **Session id** on line 1 and its **`focusedPaneID`** on line 2.
5. `--json` prints `{"sessionID": "…", "paneID": "…"}` instead.

So `session_id=$(batty new ~/proj | head -1)` replaces the whole shipped script.

## Pinned decisions

These are settled; an implementer should build them as written rather than re-deciding:

- **Do not add a `sessionNew` XPC verb.** The `batty://` URL scheme keeps its one unmatched capability — launching the app when it is not running (#0265: "wins outright, and it is not close"; reaffirmed in #0257's transport amendment, which explicitly kept `session new` on the URL scheme). Creation stays on one code path; the acknowledgement is a *read*, and XPC already does reads.
- **Bounded poll of roughly 5 s**, reusing `BoundedPoll` rather than a hand-rolled loop — the same budget the doc's script uses (50 × 0.1 s).
- **`--no-wait` restores today's fire-and-forget behavior** for scripts that genuinely do not care, and for the interactive `batty .` habit.
- **Do not invent new exit codes.** When the app was not running and XPC never comes up within the budget, exit with the existing transport vocabulary from `BattyXPCCore/XPCExitCode.swift` (`2` broker unreachable, `3` app unavailable, `4` request failed, `5` app terminated, `6` running but unregistered, `7` bundle unresolved).
- **Degraded path is explicit, not silent:** when the pre-dispatch XPC snapshot is unavailable but `open` succeeded, print nothing on stdout, write a one-line note to stderr saying the Session was created but could not be identified, and exit 0. Document that case in `docs/batty-cli-agent-workflows.md`.

## Notes

- **Matching by path is not sufficient on its own** — the user may already have a Session on that directory, and the doc's script handles this by diffing against the pre-dispatch snapshot's id set. Keep that: match on "path equal **and** id not in the snapshot". This is also why the snapshot has to be taken *before* the URL dispatch.
- `TopologySessionPayload.path` is the Session's anchor working directory and is **optional** — it is `nil` until it resolves. A Session can therefore appear in the poll before its path does; keep polling rather than matching a `nil` path, and let the bound expire rather than returning the wrong Session.
- The path the CLI matches against must be the same resolved absolute path it puts in the URL (`resolvePath(path)`), not the user's raw argument.
- **First launch is the slow case.** When the app is not running, `open` triggers a cold launch, XPC registration, and broker handoff before any `list` can answer; the ~5 s budget covers a warm app comfortably and a cold launch marginally. If the bound proves too tight in practice, record the new number as a judgment call rather than making the poll unbounded.
- **Update the docs in the same change.** `docs/batty-cli-agent-workflows.md`'s snapshot-and-poll section becomes "this is what `batty new` does for you"; the "Current limitations" bullet quoted above is deleted. Note that [#0368](0368.md) is separately correcting stale content in that same file (its exit-code table stops at `5`, missing `6` and `7`) — coordinate so the two edits do not collide.
