# 0546 — Closing a window's last Session revives its runtime with a new Session, so a quit held for the Project Editor never finishes and the app stays running with no windows

## Description

With unsaved Project Editor edits, closing the last content window holds the quit (#0481). Closing the editor afterwards should finish that quit. Instead every window goes away and the app keeps running, with only its menu bar left. This is a real product bug, not a test defect.

**Blocks 1.3.5.** It fails on `release/1.3` at `b95e088c` and on `main` at `c3ee2772`. It has not shipped: `v1.3.4` doesn't contain #0539, the likely cause. Fix on `main` first, then cherry-pick to `release/1.3`. Needs the **UI confirmation** tier: the implementer and the reviewer each re-run the failing test below.

## Steps to reproduce

1. Open Batty with one window holding one Session with one Tab.
2. File > Edit Projects, select a Project and change its name without saving.
3. Bring the content window forward and press Cmd-W. The Tab, Session and window close, and the app stays open for the editor, as intended.
4. With the editor key, press Cmd-W and choose **Discard Changes**.

## Expected behavior

The editor closes and the app quits.

## Actual behavior

The editor closes and no windows remain, but the app is still running 20 seconds later.

## Notes

### Established from the logs and code

From `guest-state/app-info.log` in the `main` run, abridged:

```
06:30:43.181 [WindowRuntime] removeSession all sessions gone; invoking onAllSessionsClosed
06:30:43.182 [RootWindowView] windowWillClose windowID=3972EC10-...
06:30:43.182 [AppStateStore] unregisterNSWindow: registered content windows remaining=0
06:30:43.182 [AppStateStoreQuit] terminateIfLastContentWindowGone: holding the quit; the Project Editor has unsaved edits
06:30:43.182 [AppStateStore] removeWindow windowID=3972EC10-...; remaining windows=0
06:30:43.182 [AppStateStoreQuit] terminateIfLastContentWindowGone: holding the quit; the Project Editor has unsaved edits
06:30:43.210 [AppStateStore] windowRuntime: creating new runtime for windowID=3972EC10-...
06:30:43.218 [TerminalHostView] file-drop: registered types=public.file-url
06:30:43.220 [ThemePreference] applyActiveSessionTheme: session=Session 1 ...
06:30:43.909 [AppServiceClient] list -> windows=1 sessions=1
```

- 28 ms after the window is removed, the closed window's id gets a new `WindowRuntime`. The `list` call comes from the test's `BattyCLI.topology()`, and shows one window and one Session with no content window open. The same sequence is in the `release/1.3` solo run.
- After Discard the log has no `scheduling termination` and no `applicationShouldTerminate` line. So `NSApp.terminate` is never called. This isn't a hang during termination, and it doesn't reach `handleTerminateRequest`.
- `WindowRuntime.init` seeds a `Session 1` whenever it is given `sessions: []` (`WindowRuntime.swift:126`), and has since #0235. So the runtime that `windowRuntime(for:)` creates is not empty.
- `terminateIfLastContentWindowGone` guards on `windows.allSatisfy { $0.sessions.isEmpty }` and returns without logging when that's false (`AppStateStore.swift:461`). When `projectEditorDidClose` re-runs the check, the revived Session fails that guard.
- The doc comment on `AppStateStore.initialWindowID` depends on the opposite. It says a revived runtime "is created with `sessions: []`", so it "does not cancel termination", and warns "Revive with a session attached and the app would instead stay alive headless." The comment's premise is false, and this bug is the outcome it warns about.
- The screen recording in the solo run's `UITests.xcresult` shows no windows and the Batty Beta menu bar after Discard.

### Inferred, not yet proven

- **The trigger is #0539 (`f98b6109` on `main`, `03c6aa43` on `release/1.3`).** It made `RootWindowView.body` call `store.isWindowSeeThrough(windowRuntime)`, which reads `window.sessions`. That is the only observed read of Sessions that #0539 added to this body. So removing the last Session invalidates the body. The re-evaluation builds `SessionSidebarView(store:windowID:)` and `SessionDetailView(store:windowID:)`, whose inits call `store.windowRuntime(for: windowID)` (since #0237), and that recreates the runtime removed moments earlier. #0539 also added the same call to `RootWindowView.init`. No log says which init ran.
- **#0544 is why Prod would get it.** `isWindowSeeThrough` starts with `guard featureFlags.terminalBackgrounds`, so the read was Beta-only until #0544 removed the flag.
- **#0540 and #0542 look uninvolved.** #0540 added `projectBackgrounds.reclaim` to `projectEditorDidClose`, before the guard, and it doesn't affect the check. #0542 added only `retryLoadIfNeeded` to `ProjectEditorWindowController.prepare` on this path. This is by elimination. Neither has been ruled out by a run without it.

To prove the trigger, run the filter above at `f98b6109^` and at `f98b6109`, each from its own detached worktree. That wasn't done when filing. The retained logs can't answer it, because the only retained results of this test are the three failures above. The last recorded pass found is `20261013-042323-50982` in #0496, 2026-10-13.

### Check these too

Neither is established, and the fix should settle both:

- **Closing the last Tab with no editor open.** `terminateIfLastContentWindowGone` schedules the quit with `DispatchQueue.main.async`, and its deferred block re-checks the same guard. The revival came 28 ms after the close in this run, so the deferred block probably wins and the app quits. Nothing confirms that. In all three shards of the Release-tier run, the log's only `requesting window close` line is from this test, so the suite appears not to exercise the ordinary path of closing the last Tab of the last window.
- **Two windows, closing all of one window's Tabs.** The same revival would leave a phantom runtime with a Session for the closed window. `batty list` would report it, and closing the other window would then fail the guard and leave the app running with no windows.

Whether the revived Session starts a shell is also unknown. The log shows a new `TerminalHostView` but no `attached host to window` line.
