## Description

With unsaved Project Editor edits, closing the last content window holds the quit (#0481). Closing the editor afterwards should finish that quit. Instead every window goes away and the app keeps running, with only its menu bar left. This is a real product bug, not a test defect.

**Blocks 1.3.5.** It fails on `release/1.3` at `b95e088c` and on `main` at `c3ee2772`. It has not shipped: `v1.3.4` doesn't contain #0539, the likely cause. Fix on `main` first, then cherry-pick to `release/1.3`. Needs the **UI confirmation** tier: the implementer and the reviewer each re-run the failing test below.

## Root cause

`windowRuntime(for:)` treated an id it couldn't find as a window being opened, and a window that has just closed looks the same. After `removeWindow`, SwiftUI rebuilds views for the closed id, which created a new `WindowRuntime`. `WindowRuntime.init` seeds a Session, so the revived runtime failed `terminateIfLastContentWindowGone`'s guard. #0539 made this reachable by making `RootWindowView.body` read `window.sessions`. Confirmed by the plan's runs at `f98b6109^` and `f98b6109`, and by the fix-reverted run below.

## Fix

Followed the plan. The store records closed ids in `closedWindowIDs`. `runtimeForPresentedWindow(_:)` returns `nil` for a closed id, and only `RootWindowView.init` calls it, keeping the result in `@State`. `SessionSidebarView` and `SessionDetailView` now receive the runtime. `WindowLifecycleController` and `WindowDelegate` use the lookup-only `existingWindowRuntime(for:)`. `windowRuntime(for:)` is now the internal `openWindowRuntime(for:)`. `fallbackWindowID` replaces `seedWindowID`. Terminate logic is unchanged, there are no `Task` hops, and #0539's read stays.

Small choices the plan left open:

- `removeWindow` replaces `fallbackWindowID` only when `windows` is empty and the fallback is itself closed, so removing an unknown id doesn't change it.
- `WindowRuntime.closeWindowCallback`'s doc claimed a "no-op default that logs a warning", which doesn't exist. It now says the callback is `nil` until the view tree is live.

Checked by reading and by the run above:

- **Revival.** The only production callers are `RootWindowView.init` for `runtimeForPresentedWindow`, and `runtimeForPresentedWindow` for `openWindowRuntime`. The other lookups can't create. `WindowRuntime(` is otherwise built only in `AppStateStore.init`.
- **Closed ids.** `removeWindow` has one production caller, `windowWillClose`. `closedWindowIDs` grows by one UUID per closed window, is never cleared, and dies with the process, so relaunch can't be blocked. `openWindow(value:)` only receives `windowIDForNewWindow()`, which is fresh, a live id or `fallbackWindowID`. While `windows` is empty, `fallbackWindowID` is never closed, because every `removeWindow` re-establishes that.
- **`@State`.** Nothing writes the scene's `$windowID` binding, so a scene doesn't change id. `windows`, `closedWindowIDs` and `fallbackWindowID` are `@ObservationIgnored`.
- **Close teardown.** A `nil` runtime in `windowWillClose` means an earlier close already released those Tabs. `releaseHost`, `unregisterNSWindow` and `removeWindow` still run. On the close-button path the kept tree still holds Sessions, and `TerminalHostStore.terminalView` refuses released tabs (#0535), so a late body can't start a shell.

Non-blocking: the `windowIDForNewWindow` doc comment still calls `initialWindowID` "the runtime `init` already seeded". During a held quit it is `fallbackWindowID`, with no runtime yet. It predates this diff's wording, and the behaviour is right and tested.

### Root cause

`windowRuntime(for:)` treats an id it can't find as a window being opened. A window that has just closed looks exactly the same, and SwiftUI can re-evaluate views for it after `removeWindow`. `WindowRuntime.init` seeds a Session, so the revived runtime fails the quit guard. #0539 made this reachable by making `RootWindowView.body` depend on `window.sessions`, but any later body re-evaluation or `ContentView.body` pass could do the same.

### Approach

The store learns which ids have closed. Only `RootWindowView.init` resolves a presented id, and everything below it receives the runtime rather than looking it up.

**`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift`**

- Add `@ObservationIgnored private var closedWindowIDs: Set<WindowID>`. `removeWindow(id:)` inserts into it.
- Replace `seedWindowID` with `@ObservationIgnored private var fallbackWindowID: WindowID`, seeded in `init`. `removeWindow` assigns a fresh `WindowID()` when `windows` becomes empty. `initialWindowID` stays `windows.first?.id ?? fallbackWindowID`, a pure read that is stable between closes. So New Window and a default scene during a held quit get an id that was never closed, and `windowIDForNewWindow()` needs no change.
- Add `func existingWindowRuntime(for:) -> WindowRuntime?`, lookup only.
- Add `func runtimeForPresentedWindow(_:) -> WindowRuntime?`: `nil` for a closed id, otherwise find or create. It is the only entry point for view code.
- Rename `windowRuntime(for:)` to `func openWindowRuntime(for:) -> WindowRuntime`, internal rather than public. The rename makes every old call site a compile error, so no caller keeps the old meaning unnoticed. Its doc says it is not for view code. Only `runtimeForPresentedWindow` calls it in production.
- Rewrite the `initialWindowID` doc comment: delete the false "created with `sessions: []`" invariant and the #0316 text about reusing the seed id. Update the mentions of `windowRuntime(for:)` near lines 439 and 1229.

**`BattyKit/Sources/BattyKit/Views/RootWindowView.swift`**

- `@State private var windowRuntime: WindowRuntime?`, set with `_windowRuntime = State(initialValue: store.runtimeForPresentedWindow(windowID))`. `@State` keeps the first value for the scene's life. A later init for a closed id computes `nil` and SwiftUI discards it, so the closing window keeps its tree and no view churns during the close. A comment should say this, since it is the non-obvious part.
- `body` is `if let windowRuntime { content(windowRuntime) }`, with today's body moved into a helper. The `nil` branch is reached only if something presents a closed id, and renders nothing.
- Pass `windowRuntime` to `SessionSidebarView` and `SessionDetailView`.
- `WindowLifecycleController.updateNSView`: `if let runtime = appStore.existingWindowRuntime(for: id), runtime.closeWindowCallback == nil`.
- `WindowDelegate.windowShouldClose`: use `existingWindowRuntime`, and allow the close when it is `nil`.
- `WindowDelegate.windowWillClose`: use `existingWindowRuntime`, and still run host release, `unregisterNSWindow` and `removeWindow` when it is `nil`.

**`SessionSidebarView.swift`, `SessionDetailView.swift`:** `public init(store:windowRuntime:)`. Neither takes a `WindowID` any more, so neither can look one up.

**Comments and docs:** `WindowRuntime.swift:100`, `Batty/BattyApp.swift:94`, `docs/multi-window-design.md` (lines 189-191, 216, 249), and a short note in `docs/view-hierarchy.md` §2 on who resolves the runtime and why a closed id stays closed.

### Decisions

- **Tombstones, not view code that never creates.** `openWindow(value:)` and the `WindowGroup` default deliver only an id. Creating the runtime before `openWindow` would leave a phantom with a Session when `openWindow` focuses an existing window, and the default-scene path has no event handler to own the write. `defaultValue` can't write either, because it is re-evaluated (seen in every log). Creation therefore stays in `RootWindowView.init` for a never-seen id, as it does today. It writes only `@ObservationIgnored` state.
- **No retained closed runtime.** Returning the old runtime for a closed id would keep the API non-optional, but `windowWillClose` leaves Sessions attached on the close-button path, so it would leak them.
- **Keep #0539's read in `RootWindowView.body`.** The fix doesn't depend on avoiding it, and the prototype proved that. Moving it into a narrower view would be a tidy-up with its own risk on a release blocker. The broad dependency is real, so leave a follow-up if it shows up in profiling.
- **No `Task` or deferred hop anywhere,** per `docs/swiftui-observation-rules.md`. `closedWindowIDs` and `fallbackWindowID` are written only from `removeWindow`, in `windowWillClose`.
- **Terminate logic unchanged.** With no revival, its guards are correct as written.

- `terminateIfLastContentWindowGone` guards on `windows.allSatisfy { $0.sessions.isEmpty }` and returns without logging when that's false (`AppStateStore.swift:461`). When `projectEditorDidClose` re-runs the check, the revived Session fails that guard.
- The doc comment on `AppStateStore.initialWindowID` depends on the opposite. It says a revived runtime "is created with `sessions: []`", so it "does not cancel termination", and warns "Revive with a session attached and the app would instead stay alive headless." The comment's premise is false, and this bug is the outcome it warns about.
- The screen recording in the solo run's `UITests.xcresult` shows no windows and the Batty Beta menu bar after Discard.

### Inferred, not yet proven

- **The trigger is #0539 (`f98b6109` on `main`, `03c6aa43` on `release/1.3`).** It made `RootWindowView.body` call `store.isWindowSeeThrough(windowRuntime)`, which reads `window.sessions`. That is the only observed read of Sessions that #0539 added to this body. So removing the last Session invalidates the body. The re-evaluation builds `SessionSidebarView(store:windowID:)` and `SessionDetailView(store:windowID:)`, whose inits call `store.windowRuntime(for: windowID)` (since #0237), and that recreates the runtime removed moments earlier. #0539 also added the same call to `RootWindowView.init`. No log says which init ran.
- **#0544 is why Prod would get it.** `isWindowSeeThrough` starts with `guard featureFlags.terminalBackgrounds`, so the read was Beta-only until #0544 removed the flag.
- **#0540 and #0542 look uninvolved.** #0540 added `projectBackgrounds.reclaim` to `projectEditorDidClose`, before the guard, and it doesn't affect the check. #0542 added only `retryLoadIfNeeded` to `ProjectEditorWindowController.prepare` on this path. This is by elimination. Neither has been ruled out by a run without it.

To prove the trigger, run the filter above at `f98b6109^` and at `f98b6109`, each from its own detached worktree. That wasn't done when filing. The retained logs can't answer it, because the only retained results of this test are the three failures above. The last recorded pass found is `20261013-042323-50982` in #0496, 2026-10-13.

### Check these too

Neither is established, and the fix should settle both:

- **Closing the last Tab with no editor open.** `terminateIfLastContentWindowGone` schedules the quit with `DispatchQueue.main.async`, and its deferred block re-checks the same guard. The revival came 28 ms after the close in this run, so the deferred block probably wins and the app quits. Nothing confirms that. In all three shards of the Release-tier run, the log's only `requesting window close` line is from this test, so the suite appears not to exercise the ordinary path of closing the last Tab of the last window.
- **Two windows, closing all of one window's Tabs.** The same revival would leave a phantom runtime with a Session for the closed window. `batty list` would report it, and closing the other window would then fail the guard and leave the app running with no windows.

Whether the revived Session starts a shell is also unknown. The log shows a new `TerminalHostView` but no `attached host to window` line.
