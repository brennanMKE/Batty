# 0230 — Audit tab/pane state flow against SwiftUI Observation rules and fix the #0227/#0229 regression class

## Description

The fixes for [[0227]] and [[0229]] each introduced regressions in the tab/pane
path: #0229's deferral fix (`1a0db6a`, currently on `main`) broke
click-to-select on unfocused panes, and the underlying focus feedback loop /
mid-layout crash class is still unresolved. Rather than another spot fix,
review **all** code that handles tabs, panes, and focus against
`docs/swiftui-observation-rules.md` (binding) and bring it into compliance, so
observable-write feedback loops can't form and AppKit layout can't be
re-entered mid-pass.

## Long Description

**The rules doc is the contract.** `docs/swiftui-observation-rules.md` was
written from the #0229 post-mortem and revised against an external review
brief. The subagent working this issue must read it in full before reading any
code, and apply its checklist ("Checklist before touching a state-flow path")
to every change. Key rules in play:

- View construction is pure; `onChange`/`onAppear` writes are audited by
  *what flipped the observed value* (event-origin vs layout/focus/geometry-origin).
- No constraint-dirtying or responder-changing AppKit calls
  (`makeFirstResponder`, `addSubview`) synchronously from SwiftUI-driven
  callbacks — `NSHostingView` runs updates inside `-[NSView layout]`.
- Two-way model ↔ AppKit sync (e.g. `focusedPaneID` ↔ `firstResponder`)
  needs a declared direction per path and a **structural** echo dead-end
  (programmatic-change token / source check). Equality guards alone are
  insufficient — the #0229 loop ping-pongs between *different* values.
- No `Task { @MainActor }` hops to relocate illegal writes — that caused the
  click regression.

**Review scope (at minimum):**

- `BattyKit/Sources/BattyKit/Views/PaneView.swift` — all `onChange` handlers
  (`isFocused`, `isPaneFocused`, `activeTabID`, `bellCount`), `onAppear`
  focus calls, computed properties read by body
- `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift` — `focusPane(id:)`
  and every other `focusedPaneID` / `activeTabID` writer
- `BattyKit/Sources/BattyKit/Commands/TerminalSurfaceFocuser.swift` — the
  retry ladder (stale-target re-promotion is the suspected loop fuel; ladder
  steps need a "still the target?" staleness check)
- `BattyKit/Sources/BattyKit/Commands/TerminalClickFocusMonitor.swift` — the
  AppKit-initiated direction; its synchronous model follow-up must keep
  winning its ordering
- `BattyKit/Sources/BattyKit/Views/TerminalPlaceholderView.swift` — body side
  effects and geometry plumbing (stay within the sanctioned exceptions
  documented in `docs/view-hierarchy.md`)
- `SplitTree` focus mutation and Cmd-Option-arrow routing
- The #0227 change (`92fd814`) — the pwd-delegate wiring in `PaneView.task`
  and `handleWorkingDirectoryChange`, reviewed against the same rules

## Acceptance criteria

1. Clicking an unfocused pane focuses it (model + first responder + accent
   border). **Manual user sign-off required — the harness click tests cannot
   verify this** (they fail even on known-good builds).
2. `testCmdOptionArrowsMoveFocusAcrossHorizontalSplit` and
   `…VerticalSplit` pass with no crash and no idle stall.
3. `testCmdDFocusesNewPane` and `testCmdShiftDFocusesNewPane` stay green
   (they catch the focus-drag-back regression mode).
4. No unbounded `chipTitle` re-evaluation during focus moves (bounded burst
   around the move is normal; see #0229 Verification for the measured
   baseline).
5. Every focus-flow sync path has a declared direction and a structural echo
   dead-end, per the rules doc — documented in the resolution's `## Fix`.
6. #0227's auto-naming behavior is unregressed (`scripts/build.sh unit`
   includes its coverage; TabRename UI tests if touched).
