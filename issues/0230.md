## Description

The fixes for [[0227]] and [[0229]] each introduced regressions in the tab/pane
path: #0229's deferral fix (`1a0db6a`, currently on `main`) broke
click-to-select on unfocused panes, and the underlying focus feedback loop /
mid-layout crash class is still unresolved. Rather than another spot fix,
review **all** code that handles tabs, panes, and focus against
`docs/swiftui-observation-rules.md` (binding) and bring it into compliance, so
observable-write feedback loops can't form and AppKit layout can't be
re-entered mid-pass.

## Resolution notes

> 🟢 Resolved 2026-06-04 — removed the `isFocused`-echo model write (the
> feedback edge behind #0229's loop/crash and the click regression) and gave
> each focus-sync direction a single declared writer: clicks write the model
> in `TerminalClickFocusMonitor`; programmatic promotion is deferred off the
> layout pass and generation-guarded in `TerminalSurfaceFocuser`. All 8
> `PaneFocusTests` pass — including the 4 click tests failing since
> 2026-05-30. On branch `0230-observation-audit`; real-world click
> verification is the user's sign-off.

## Root cause

The model write for click-to-focus was *inferred* from
`TerminalViewState.isFocused` flips in `PaneView.onChange`. A live trace
(debug logging on every `focusPane` transition + first-responder promotion)
showed that inference is unsound: **libghostty flips `isFocused` on existing
surfaces when a new surface is created.** After every Cmd-D split, the old
pane's spurious flip reverted `focusedPaneID` to the old pane — with no
responder change at all.

At pre-#0229 baseline this was masked: the new pane's promotion echo
re-fixed the model a few ms later, so the revert was invisible — an
accidental, self-healing ping-pong. That same edge, fed by stale retry-ladder
re-promotions in the 2-pane Cmd-Option-arrow case, is what escalated into
the unbounded invalidation loop and the mid-layout NSException crash of
#0229. The two prior fixes failed because they re-timed or damped the edge
instead of removing it: the Task deferral (`1a0db6a`) reordered the race and
broke clicks; an idempotence-guard-only attempt left the different-value
ping-pong alive (crash reproduced).

The 4 `testClickIn…` failures dating to 2026-05-30 were this bug, not
environment sensitivity: each click test splits first, and the churn revert
broke the test's post-split focus precondition.

## Fix

Per `docs/swiftui-observation-rules.md` ("two-way sync needs a single
authority"), each direction now has exactly one declared writer and the echo
edge is deleted, not damped:

| Path | Direction | Writer | Context |
|---|---|---|---|
| User clicks a terminal | AppKit → model | `TerminalClickFocusMonitor` promotes first responder AND synchronously writes the model via new `AppStateStore.focusPane(containingTabID:)` | event dispatch — never layout |
| Cmd-Option-arrows / splits / layout presets / bell jump / chip select | model write | existing event-handler call sites (unchanged) | event dispatch |
| Model → AppKit follow-up | promotion | `TerminalSurfaceFocuser.focusWhenReady`: every `makeFirstResponder` now runs on a fresh main-actor turn (never inside `NSHostingView`'s layout pass), guarded by a monotonic generation token so superseded promotions can never fire late | next turn |
| `isFocused` flip → model | — | **deleted** — a comment in `PaneView` marks the absence as deliberate | — |

Event-origin handlers (`bellCount`, `lastDesktopNotificationAt`, #0227's
pwd-delegate wiring) were audited and left unchanged — no feedback edge.
`TerminalPlaceholderView`'s body side effect and frame placement stay within
the sanctioned `view-hierarchy.md` exceptions.

## Gotchas

- **libghostty flips `isFocused` on *other* surfaces when a surface is
  created.** Observed directly in the #0230 trace (old tab's flip ~10 ms
  after `created terminal view` for the new tab, no responder change). Any
  future logic keyed on `isFocused` transitions must assume churn, not
  user intent.
- **The baseline code was accidentally correct.** The churn revert was
  healed by the promotion echo a few ms later. Removing *either* half
  (deferral, generation token) without removing the inference broke focus
  in a different way each time. If focus behavior regresses again, check
  for a reintroduced `isFocused`-keyed model write before re-timing
  anything.
- **The 4 click UI tests are real coverage again.** They were dismissed as
  environmental for a week while correctly detecting this bug. Treat a
  `testClickIn…` failure as a focus-model bug until proven otherwise.
- **Not verified by me:** real-world click feel and IME/keyboard routing
  after focus changes — the harness now covers the model outcome, but
  visual/manual sign-off (acceptance criterion 1) is the user's. #0229's
  symptoms should be re-tested against this branch before its own
  resolution is decided (it remains `in-progress`, reserved by the user).

## Long Description

**The rules doc is the contract.** `docs/swiftui-observation-rules.md` was
written from the #0229 post-mortem and revised against an external review
brief. The subagent working this issue must read it in full before reading any
code, and apply its checklist ("Checklist before touching a state-flow path")
to every change. Key rules in play:

- View construction is pure; `onChange`/`onAppear` writes are audited by
  *what flipped the observed value* (event-origin vs layout/focus/geometry-origin).
- No constraint-dirtying or responder-changing AppKit calls
  (`makeFirstResponder`, `addSubview`) synchronously from SwiftUI-driven
  callbacks — `NSHostingView` runs updates inside `-[NSView layout]`.
- Two-way model ↔ AppKit sync (e.g. `focusedPaneID` ↔ `firstResponder`)
  needs a declared direction per path and a **structural** echo dead-end
  (programmatic-change token / source check). Equality guards alone are
  insufficient — the #0229 loop ping-pongs between *different* values.
- No `Task { @MainActor }` hops to relocate illegal writes — that caused the
  click regression.

**Review scope (at minimum):**

- `BattyKit/Sources/BattyKit/Views/PaneView.swift` — all `onChange` handlers
  (`isFocused`, `isPaneFocused`, `activeTabID`, `bellCount`), `onAppear`
  focus calls, computed properties read by body
- `BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift` — `focusPane(id:)`
  and every other `focusedPaneID` / `activeTabID` writer
- `BattyKit/Sources/BattyKit/Commands/TerminalSurfaceFocuser.swift` — the
  retry ladder (stale-target re-promotion is the suspected loop fuel; ladder
  steps need a "still the target?" staleness check)
- `BattyKit/Sources/BattyKit/Commands/TerminalClickFocusMonitor.swift` — the
  AppKit-initiated direction; its synchronous model follow-up must keep
  winning its ordering
- `BattyKit/Sources/BattyKit/Views/TerminalPlaceholderView.swift` — body side
  effects and geometry plumbing (stay within the sanctioned exceptions
  documented in `docs/view-hierarchy.md`)
- `SplitTree` focus mutation and Cmd-Option-arrow routing
- The #0227 change (`92fd814`) — the pwd-delegate wiring in `PaneView.task`
  and `handleWorkingDirectoryChange`, reviewed against the same rules

## Acceptance criteria

1. Clicking an unfocused pane focuses it (model + first responder + accent
   border). **Manual user sign-off required — the harness click tests cannot
   verify this** (they fail even on known-good builds).
2. `testCmdOptionArrowsMoveFocusAcrossHorizontalSplit` and
   `…VerticalSplit` pass with no crash and no idle stall.
3. `testCmdDFocusesNewPane` and `testCmdShiftDFocusesNewPane` stay green
   (they catch the focus-drag-back regression mode).
4. No unbounded `chipTitle` re-evaluation during focus moves (bounded burst
   around the move is normal; see #0229 Verification for the measured
   baseline).
5. Every focus-flow sync path has a declared direction and a structural echo
   dead-end, per the rules doc — documented in the resolution's `## Fix`.
6. #0227's auto-naming behavior is unregressed (`scripts/build.sh unit`
   includes its coverage; TabRename UI tests if touched).
