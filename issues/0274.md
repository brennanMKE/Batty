## Description

Final scheduled step of the XPC track under umbrella #0265: the topology **read verbs** #0257 deferred to Tier 3 — `batty list [sessions|panes|tabs] [--json]` and `batty session info [--json]` — now carried over XPC request/reply instead of the raw Unix socket #0257 originally penciled in (#0265 amends #0257 §5: the Tier 3 two-way transport is XPC).

**Gate — need, not schedule:** this child starts only when the read verbs are *actually needed* (the driving use case in #0257: an agent inside a pane asking "what's around me"). Blocked on #0271 (request/reply channel) and on #0257's groundwork (the `BATTY_*` context env vars, client-generated ids, and `whoami` — none of which exists in the codebase yet per `docs/batty-cli-install.md` §"Known limitations"). Do not build ahead of #0257.

## The decision this child must resolve (raised in #0265, not decided)

**Does the Option B JSON topology snapshot survive alongside a live `list` reply?**

- **Case for dropping it:** once request/reply exists, a live `list` answers the same question with no staleness and no snapshot-writing machinery in the app.
- **Case for keeping it:** the snapshot works **with no agent installed and no approval granted** — every CLI command over XPC fails while `SMAppService` sits in `requiresApproval` (see #0270), and the snapshot path has no such dependency. It is the cheap degraded mode.
- **If both exist**, #0257's own guidance holds: shape them so the `list` reply **reuses the snapshot's JSON schema verbatim** (#0257 Option B anticipated exactly this: "shape the JSON so a future socket's `list` response reuses it verbatim").

Record the decision and rationale in this issue and reflect it back into #0257 and the umbrella.

## Scope

1. `batty list` — windows → sessions (id, name, path, active) → tabs → pane tree (split axis, hidden, zoomed, focused), per #0257 Option B's shape, including each tab's pty device path and the app's pid if the snapshot schema is adopted.
2. `batty session info [--json]` — the calling/target session's slice.
3. The Option B keep/drop/share-schema decision above, implemented.
4. Closes #0257's known awkwardness: `pane show <id>` has no id-discovery path until a listing exists (hidden panes appear in the listing).
5. Exit codes per the #0269 vocabulary; `--json` output stable enough to script against.

## Traps that apply here (copied)

- **Message payloads stay `Codable, Sendable` structs as JSON-encoded `Data`** inside the `@objc` protocols (#0269 discipline) — the layout model (`Session`, `Pane`, `Tab`, `SplitNode`) is already pure Codable value types, so the reply payload is nearly free; do not embed view or libghostty types.
- **Reply blocks `@escaping @Sendable`;** any new Foundation-supplied handler closure gets `@Sendable` (the #0272 audit extends to code added here).
- **Reads must not mutate:** `list`/`info` aimed at a background session must not steal focus or switch the active session (#0257's cross-session rule for mutations applies doubly to reads).
- If the snapshot is kept: atomic write (temp + rename), debounced; it is a derived, disposable runtime artifact — *not* Workspace persistence.

## Out of scope

- Live screen reads, `wait`, `send`/`send-key`, `events subscribe`, sidebar activity pills — these need streaming or push, which is **explicitly deferred at the umbrella level; no child exists for it by design.** If one of these becomes genuinely needed, file a new child under #0265 then.
- Tier 0/1 mutation verbs (#0257's own scope) and any change to their `batty://` transport.

## Verification expectations

Follow the #0257 pattern:

- Unit-test the reply payload encode/decode and the `--json` output shape; if the snapshot is kept, unit-test snapshot encode/decode and the atomic write/read round-trip; cross-session reads leave selection and focus untouched (assert on the store, not just absence of crash).
- `scripts/build.sh unit` and `scripts/build.sh` green; `otool -L` on `batty` still shows zero `@rpath` dependencies.
- Live end-to-end (`batty list --json` against a running app with a multi-session, split, hidden-pane layout matching reality) needs the user's runtime sign-off, like #0250/#0251.
