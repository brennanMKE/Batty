## Description

**Unconfirmed report.** While working #0447 in the Tart VM, the
implementer observed, in the app's accessibility tree, a Sidebar Session
row whose identifier read `session-row.<title>-session-row.<title>` once
that Session had an unseen-bell badge. The observation was not captured
in a result bundle and no attachment shows it; #0447's Gotchas record it
as "Not confirmed from the result bundles" (`issues/0447.md:95`). The
first acceptance step below is to reproduce it, and if it does not
reproduce this issue should be closed by the user with that finding, not
fixed.

If it is real, three things follow, each verified against `main` at
`d97e6b18`:

1. **It contradicts the comment that justifies not using `.contain` on
   the row.** `SessionSidebarView.swift:75-81` says: "SessionRow has no
   child that needs its own identifier (no Button, nothing else already
   carries one), so the fold-into-a-leaf behavior this identifier would
   otherwise trigger is harmless here — `.contain` isn't needed." The
   identifier is applied to the `SessionRow` label content
   (`SessionSidebarView.swift:98`) with no `.accessibilityElement(children:)`
   modifier. But `SessionRow`'s body (`:255-273`) has two `Text` leaves,
   not one: the title inside a `Label` (`:258`) and, when
   `session.unseenBellCount > 0`, a second `Text(verbatim:
   "\(session.unseenBellCount)")` badge (`:265-272`) with a `.help(...)`
   tooltip. The badge is exactly a child that appears only in the
   state where the doubled identifier was seen. The sibling `PaneRow`
   already learned this lesson: `SessionSidebarView.swift:63-72` applies
   `.accessibilityElement(children: .contain)` before
   `pane-row.<uuid>` because "SwiftUI on macOS folds PaneRow's HStack
   into a single accessibility leaf and this identifier spreads to every
   child", citing the tab bar's `tab-chip.<title>` precedent
   (`PaneView.swift:219-225`).

2. **It breaks exact-match lookups.**
   - `BattyUITestHarness.sessionRow(named:)`
     (`BattyUITests/Support/BattyUITestHarness.swift:202-207`) builds
     `"session-row.\(title)"` and queries `app.collectionViews.cells[identifier]`
     then `.matching(identifier: identifier)` — both exact. It has 27
     call sites across 11 files (`grep -rn "sessionRow(named"
     BattyUITests`): `BattyUITests.swift`, `CLIRemoteControlTests.swift`
     (`:88`), `DragDropTests.swift`, `FuzzyFinderTests.swift`,
     `SessionCwdRenameTests.swift`, `SidebarTests.swift`,
     `TabChipRenderingTests.swift`, `TabRenameTests.swift` (`:132`,
     `:137`, `:157-158`), `TerminalPersistenceTests.swift`,
     `ThemeTests.swift` and the harness itself.
   - `BattyScreen.mismatch(between:in:)`
     (`BattyUITests/Support/BattyCLIHarness.swift:399-404`) collects
     `identifiers(withPrefix: "session-row.")` (`:350-352`, a prefix
     match that would still *find* a doubled row) and compares the
     `Set<String>` for equality with `Set(topology.sessions.map {
     "session-row.\($0.name)" })`. A doubled identifier is a different
     string, so `rows != expectedRows` and every
     `BattyScreen.expectMatches` after a bell lands in a background
     Session would fail with "Sidebar Session rows ... != topology
     Sessions ...". `CLIRemoteControlTests.swift:570` compares the same
     prefix set's *count* to `sessionCount`, which a doubled identifier
     would not disturb.
   - Documentation promises the exact form: `BattyUITests/README.md:47`
     ("`session-row.<title>` — A row in the session sidebar, keyed by the
     visible title") and `docs/ui-features.md:144`, `:322`, `:467`,
     `:538`.

   Today none of those exact-match tests fails because none of them puts
   an unseen badge on a row before looking it up. The one test that does
   both is new in #0447 and works around it.

3. **#0447's new test matches by prefix instead of fixing or
   confirming it.** `CLIBackgroundSessionTests.rowValue(_:in:)`
   (`BattyUITests/CLIBackgroundSessionTests.swift:34-43`) carries the
   comment "With an unseen badge the row's identifier is doubled
   ("session-row.X-session-row.X"), so match it by prefix" and uses
   `NSPredicate(format: "identifier BEGINSWITH %@", "session-row.\(name)")`.
   It is used by `testPaneFocusAimedAtABackgroundSessionSwitchesTheSession`
   (`:75`, `:81`), `testTabFocusAimedAtABackgroundSessionSwitchesTheSession`
   (`:114`) and `testNotifyToABackgroundSessionIsUnseenAndCollapses`
   (`:166`). A prefix match on `session-row.Session 1` also matches
   `session-row.Session 10`, so the workaround is itself fragile; it is
   also the only place in the suite that encodes the doubled form, so if
   the identifier is later fixed the comment becomes wrong silently
   (the predicate keeps passing).

#0447 added `rowAccessibilityValue(for:isSelected:)`
(`SessionSidebarView.swift:19-26`) precisely because "The numeric badge
is folded into the row's single accessibility element, so this is the
only place it is readable" — that is, #0447 relied on the fold the
comment at `:75-81` describes while also observing the fold producing a
doubled identifier. Both cannot be the whole story; reproducing settles
it. Target: after 1.2.0, on `main`.

## Actual behavior

Per #0447's Gotchas (`issues/0447.md:95`): a Sidebar row showing an unseen
badge was seen with a doubled identifier. Per the code: the row's
identifier is applied with no `.contain` to a view that has two `Text`
leaves when the badge is present (`SessionSidebarView.swift:98`,
`:258`, `:266`), and the only test exercising that state matches by
prefix (`CLIBackgroundSessionTests.swift:36-39`).

## Notes

### Why `.contain` is the likely fix, and what it costs

`PaneRow` (`SessionSidebarView.swift:71-72`) and the tab chips
(`PaneView.swift:219-225`, per the comment at `:63-70`) both solved the
"identifier spreads to every child" problem with
`.accessibilityElement(children: .contain)`. Applying it to the Session
row label would stop the fold. The costs, each a question for the
implementer to check in the VM rather than assume:

- `BattyUITestHarness.sessionRow(named:)` first tries
  `app.collectionViews.cells[identifier]` (`:204`). With `.contain`
  the identifier may land on a group element rather than the cell; the
  `.descendants(matching: .any)` fallback (`:206`) still finds it, but
  `click()` on a container vs. a cell is what the 27 call sites rely on
  for selection, drag (`DragDropTests`), and context menus
  (`docs/ui-features.md:467`: "The sidebar right-click context menu must
  open on `session-row.<title>`").
- #0447's `rowAccessibilityValue` assumed the badge is *not* separately
  readable. With `.contain`, the badge `Text` becomes its own element
  (unlabelled, value "3"); either hide it
  (`.accessibilityHidden(true)`) so the value string stays the single
  source, or give it an identifier (`session-row-badge.<title>`) and let
  tests read it directly. Either way the value string should keep
  working so `CLIBackgroundSessionTests` does not have to change twice.
- The `.help(...)` on the badge (`:271`) is a tooltip; whether it
  contributes to the fold is unknown to the filer.

An alternative that avoids `.contain` entirely is
`.accessibilityHidden(true)` on the badge `Text` alone, which removes
the second leaf from the fold while leaving the row a single cell.
Which is better depends on what step 1 shows.

### What might explain a doubled string

The filer has no documented SwiftUI behaviour to cite for identifiers
concatenating with `-`. The pattern is consistent with the row being
folded into one leaf whose identifier is assembled from two children
that each inherited `session-row.<title>` (the comment at `:63-70` says
the identifier "spreads to every child"); a `Label` plus a second `Text`
would give two. That is a hypothesis, not a finding; reproducing with
the tree attachment is the only way to know.

### Constraints

- `docs/swiftui-observation-rules.md`: accessibility modifiers are view
  construction; no observed-state writes are involved, so this is safe
  to change in `body`.
- Identifiers are a public contract for the UI suite
  (`BattyUITests/README.md:53-54`: "keep them stable"). Do not rename
  `session-row.<title>`.
- No new toolbar buttons or UI; this is accessibility-only.

## Open questions

1. **If confirmed, `.contain` or hide the badge?** See Notes; the
   implementer should pick after seeing the tree, and the user may have
   a preference about VoiceOver reading the count as a separate element.
2. **Should the badge get its own identifier** (`session-row-badge.<title>`)
   so tests assert the count without parsing the value string? #0447
   chose the value string; adding an identifier is additive. User call.
3. **Is `BattyUITestHarness.sessionRow(named:)`'s cell-first lookup
   worth keeping** once the row is a `.contain` group? If the fallback
   path always wins, simplify it; if `cells[...]` still matches, leave
   it. Decide from the VM tree, not from reasoning.
4. **Does `docs/ui-features.md:145`'s `session-row-title-source`
   accessibilityValue exist?** `grep -rn session-row-title-source
   BattyKit/Sources Batty` finds nothing; the row's value is
   `"selected|unselected[, N unseen]"`. Out of scope unless the
   implementer is already editing that doc section; flagged so the
   reviewer does not cite the doc as the contract.
