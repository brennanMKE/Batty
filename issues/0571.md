# 0571 — Batty has no Scratch Pad Pane for holding and editing text before pasting it into a terminal

| | |
|---|---|
| **Status** | open |
| **Module** | Pane |
| **Platform** | macOS |
| **First seen** | 2026-11-11 |

## Description

Add a new non-terminal Pane kind, **Scratch Pad** (`scratch-pad`). It holds plain, editable, multi-line text in a monospaced font, so the user can park text and shape a command (join lines, fix quoting, swap arguments) before copying it into a terminal Pane. It edits like any macOS text view: selection, copy, cut, paste, select all, undo and redo. It has **no saving of any kind**. The text is ephemeral: it lives only while the Pane is open.

User request (2026-11-11, verbatim): "I have an idea for new custom view. It would be helpful to have a scratch pad where I can hold onto some text and even edit it to format commands I may paste into terminal. Create an issue for this feature. This scratch pad will not allow for saving the text."

Follow-up (2026-11-11, verbatim): "this text content will be ephemeral and we should even allow the CLI tool to access it with read/write access, so create a 2nd issue to update CLI tool." CLI read/write access is tracked separately in [#0572](0572.md), which depends on this issue.

This is new feature work for `main` (targets 1.4.0), not a 1.3.x fix. It follows the pattern of the existing view Panes: Git Status #0304, Process Status #0305, LM Studio Dashboard #0313, System Metrics #0314, plumbing #0315, menus and shortcuts #0331/#0453. The Markdown Viewer ([#0527](0527.md), still open) is the closest filed sibling and lists the same plumbing.

**Read before implementing:** `docs/view-hierarchy.md`, `docs/pane-kinds.md` (esp. §2 and §3), `docs/pane-view-lifecycle.md`, `docs/terminal-pane-requirements.md`, `docs/swiftui-observation-rules.md`, `docs/themes.md`.

## Decisions

1. **No saving.** No file is written or read. No Save, Save As, Open, Export, Revert or "Reveal in Finder". No autosave, no `NSDocument`, no `UserDefaults` or Application Support storage of the text. The only ways text leaves the Pane are the clipboard, drag, and (in #0572) the CLI.
2. **Ephemeral lifetime.** The text lives only as long as the Pane is open. Closing the Pane discards it. Quitting or relaunching Batty discards it, and a crash loses it. This matches the rest of the layout: Concepts.md `## Pane` says "**Persisted:** nothing; in-memory only."
3. **The text lives in the model, not in the view.** The text belongs to a `PaneContentLifecycle` conformer (`ScratchPadPaneContent`) owned by the Pane's `PaneRuntime.content`, the same place `GitStatusPaneContent` and `SystemMetricsPaneContent` live. It must not be `@State` or `NSTextView`-only state. Two reasons: hiding a Pane or switching Sessions must not lose the text, and #0572's XPC verbs must be able to read and write it through `AppStateStore` with no view on screen. A write from outside (#0572) must show up in the open editor. An edit in the editor must be readable from outside without waiting for a focus change.
4. **Plain text only.** No rich text, no syntax highlighting, no smart quotes, smart dashes, auto-correct, or text replacement. These silently corrupt shell commands (`"` → `"`, `--` → `—`). Tabs and trailing whitespace are kept as typed.

## Expected behavior

### 1. Pane kind and plumbing

- New case `PaneContentKind.scratchPad = "scratch-pad"` in `BattyKit/Sources/BattyXPCCore/PaneContentKind.swift`, `displayName` `"Scratch Pad"`. The one raw string is the Codable `Pane.kind`, the CLI `--view` value and `TopologyPanePayload.kind` (`docs/pane-kinds.md` §5). Because `batty pane split --view` is typed as `PaneContentKind` (`BattyKit/Sources/batty/PaneCommand.swift:72`) and its capabilities enum is `PaneContentKind.allCases` (`PaneCommand.swift:539`), `batty pane split --view scratch-pad` and `--view scratch-pad --unique` work from the new case alone.
- New `ScratchPadPaneContent: PaneContentLifecycle` in `BattyKit/Sources/BattyKit/Runtime/`, returned by `PaneRuntime.makeContent(for:)` (`BattyKit/Sources/BattyKit/Runtime/PaneRuntime.swift:101`). It owns the text. It has no background work, so suspend and teardown are trivial, but it still obeys `docs/pane-view-lifecycle.md` §3–§5. Teardown drops the text.
- New `ScratchPadPaneView`, reached from a new branch in `PaneView.nonTerminalContent` (`BattyKit/Sources/BattyKit/Views/PaneView.swift:453`), and the `.scratchPad` case added to the non-terminal arm of `PaneView.body`'s kind switch (`PaneView.swift:100`).
- Adding the case breaks every exhaustive `switch` over `PaneContentKind`. As of this filing that includes `PaneContentKind.displayName`, `PaneRuntime.makeContent(for:)`, `PaneView.body`, and the Projects switches in `ProjectDraft.swift:134`, `SessionProjectCapture.swift:120`, `ProjectEditorViewModel.swift:362` and `:660`, `ProjectTreeBuilder.swift:95`, and `ProjectEditorView.swift` (glyph, color and blurb at lines 16/26/37, plus 718 and 780). Let the compiler find them, and don't add a `default:`. A Project that captures a Scratch Pad stores only the kind, never the text (decision 2).

### 2. Entry points

Copy the System Metrics wiring at each site:

- **View menu → Open View** section (`BattyKit/Sources/BattyKit/Commands/BattyCommands.swift` ~line 345) and the horizontal/vertical split submenus that list the view kinds (~lines 430 and 471).
- **Shortcut actions** `splitHorizontalScratchPad` / `splitVerticalScratchPad` in `BattyKit/Sources/BattyKit/Shortcuts/ShortcutAction.swift`, dispatched in `BattyKit/Sources/BattyKit/Commands/BattyShortcuts.swift` (~line 166) and the Command Palette (`BattyKit/Sources/BattyKit/Views/CommandPaletteView.swift` ~line 430). Default bindings are an open question (below). They may be unbound.
- **CLI** `batty pane split --view scratch-pad` (free from §1). Reading and writing the text from the CLI is #0572.
- Help (`BattyKit/Sources/BattyKit/Help/`), Concepts.md `## Pane` "Purpose" list, and `docs/ui-features.md` name the new kind.

### 3. Editor

- Monospaced font. Use the terminal's configured font family and size if that's easy to reach, else the system monospaced font.
- Multi-line, wraps or scrolls horizontally (open question), with a vertical scroller.
- Standard macOS editing: click-to-place, selection, Cmd-C/X/V/A, Cmd-Z / Cmd-Shift-Z undo and redo, find (Cmd-F) if the text view gives it for free.
- Colors follow the active Theme (background, foreground, selection, caret), and repaint live on a Theme change like the other view Panes (`docs/themes.md`).
- Empty state: a placeholder line such as "Type or paste text here. Nothing is saved." so the user learns decision 2 up front.
- Click into the Pane focuses it (`tree.focusedPane`) and makes the text view first responder, so keystrokes go to the text view and not to a terminal.

### 4. Keyboard and clipboard routing (checked against the code)

- **Paste.** The app replaces the Edit menu's pasteboard group (`BattyCommands.swift:291`). Cmd-V calls `PasteDispatcher.handlePasteRequest` (`BattyKit/Sources/BattyKit/Views/PasteConfirmation.swift:74`). It falls back to the standard AppKit paste when there is no `store.focusedTerminalTab` or when the first responder is an `NSTextView` (`isEditingTextField`, `PasteConfirmation.swift:109`). A focused Scratch Pad therefore gets a plain paste with no paste-confirmation sheet. Verify this rather than assume it, and add a unit test if the seam allows.
- **Copy / Cut / Select All** in that same group use `NSApp.sendAction(#selector(NSText.copy(_:)) …)`, so they reach the text view through the responder chain.
- **Undo / Redo.** The `.undoRedo` group is not replaced, so the text view's undo manager should handle Cmd-Z. Verify it, since the terminal path may intercept keys differently.
- **App shortcuts win.** `BattyShortcuts.handle` (`BattyKit/Sources/BattyKit/Commands/BattyShortcuts.swift:20`) is a local `NSEvent` monitor that consumes any bound shortcut "regardless of which view holds first responder". Only the Settings shortcut recorder is exempt (line 24). So Cmd-W closes the Scratch Pad Pane (`WindowRuntime.closeFocusedTab()` closes a non-terminal Pane itself, #0334), Cmd-D splits, and so on. None of the default bindings in `ShortcutAction.swift` use Cmd-Z/C/X/V/A, but Cmd-Shift-X is the default for `exitShell` (`ShortcutAction.swift:168`). Decide whether that is acceptable inside a text editor (open question).
- **Cmd-T** does nothing on a focused non-terminal Pane (`BattyShortcuts.swift:124`, gated on `focusedTerminalPane`). No change needed.

### 5. Terminal Pane requirements

The Scratch Pad shares `PaneView` and the detail area with terminal Panes, so `docs/terminal-pane-requirements.md` applies as `docs/pane-kinds.md` §3 "Item by item" scopes it:

- §4's `.allowsHitTesting(false)` rule for pane chrome overlays applies unchanged.
- **Drag and drop is a live hazard.** One `TerminalHostView` fills the whole detail area and registers `.fileURL` drags (`BattyKit/Sources/BattyKit/Views/TerminalHostView.swift:58`). A file dragged onto the Scratch Pad may be routed to the host instead of the text view (`docs/pane-kinds.md` §3). Text drags (`.string`) are not registered on the host today. Dropping text from another app into the Scratch Pad must insert it. Dropping a file must either insert its path or do nothing; it must never paste into a terminal.
- After the change, re-run the `docs/terminal-pane-requirements.md` §6 checklist on a **terminal** Pane beside an open Scratch Pad: click, select, scroll, type, IME, file drop. The terminal must behave as before.
- Focus flow must follow `docs/swiftui-observation-rules.md`. Making the text view first responder on click must not happen synchronously inside a SwiftUI update or layout pass. Hop through the event, not a `Task`.

## Open questions (for the user)

1. **Send to terminal.** Should the Scratch Pad have a "Send to Terminal" action (button and/or shortcut) that pastes the selection, or the whole text, into the most recently focused terminal Pane in the same Session? The building blocks exist: `PasteDispatcher` sends through `tab.terminal.send(_:)` with the paste-strictness confirmation, and Projects startup commands paste then press Return (`BattyKit/Sources/BattyKit/Runtime/StartupCommandDelivery.swift`). Sub-questions: paste only, or paste and Return? Does it go through the paste-confirmation check? *Recommendation:* defer to a follow-up. Ship copy/paste only, which is what was asked.
2. **Closing a non-empty Scratch Pad.** Cmd-W closes the Pane today with no prompt, and the text is gone (decision 2). Options: (a) no prompt, (b) confirm only when non-empty, (c) no prompt but an undoable close. Also: should a non-empty Scratch Pad count in the quit confirmation? *Recommendation:* (a) for v1, since the placeholder says nothing is saved. Revisit if users lose text.
3. **One per Session, or many?** `PaneContentKind` has no `isSingletonPerSession` (see the comment in `PaneContentKind.swift`). `--unique` already finds an existing one from the CLI. Allow several.
4. **Wrap or scroll?** Long commands read better wrapped. Editing columns reads better unwrapped. *Recommendation:* wrap, with no toggle in v1.
5. **Default shortcuts.** Cmd-letter combos are mostly taken in `ShortcutAction.swift`. Ship unbound (reachable from the menu, Command Palette and CLI), or pick a binding?
6. **Cmd-Shift-X** (`exitShell`'s default binding, `ShortcutAction.swift:168`) is consumed by the app even inside the text view. Fine, or should text-view focus exempt some shortcuts?
7. **Split inheritance.** A terminal split from a Scratch Pad has no directory to inherit. It falls back to the most recently focused terminal Pane's directory in the Session, as Concepts.md `## Pane` describes for non-terminal Panes. Confirm.

## Acceptance criteria (user-verifiable in Batty Beta)

1. View → Open View lists **Scratch Pad**. Choosing it splits the focused Pane and shows an empty Scratch Pad with the "nothing is saved" placeholder. The Command Palette has the same entries.
2. `batty-beta pane split --view scratch-pad` from a terminal Pane opens one and prints its id. `batty-beta list --json` shows the Pane with `"kind": "scratch-pad"`.
3. Typing, selecting, Cmd-C, Cmd-X, Cmd-V, Cmd-A, Cmd-Z and Cmd-Shift-Z all work in the Scratch Pad. Paste never shows the paste-confirmation sheet and never lands in a terminal.
4. Typing `"` and `--` gives straight quotes and two hyphens, never curly quotes or a dash.
5. Text pasted from the Scratch Pad into a terminal Pane runs as typed.
6. Hiding the Pane and showing it again, or switching to another Session and back, keeps the text.
7. Closing the Pane, then opening a new Scratch Pad, gives an empty one. Quitting and relaunching Batty leaves no Scratch Pad text anywhere. No file appears in Application Support or `UserDefaults` for it.
8. No menu, button or shortcut offers Save, Open or Export for the Scratch Pad.
9. Switching Theme repaints the Scratch Pad live.
10. A terminal Pane next to a Scratch Pad still passes the `docs/terminal-pane-requirements.md` §6 checklist. Dragging a file onto the Scratch Pad never sends anything to a terminal.
