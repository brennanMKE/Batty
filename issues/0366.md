# 0366 — An unnecessary `Task { @MainActor }` hop in the broker backoff retry opens a redundant-reconnect window

| | |
|---|---|
| **Status** | open |
| **Module** | App |
| **Platform** | macOS |
| **First seen** | 2026-08-22 |

## Description

**Benign today — do not over-scope this.** The behavior it can produce is already
absorbed downstream, and nothing user-visible depends on the fix. It is filed
because the hop is unnecessary, and removing it closes a small window for free.

`AppXPCCoordinator.scheduleBackoffRetry` builds a `DispatchWorkItem` whose body
immediately hops through `Task { @MainActor }`:

```swift
let workItem = DispatchWorkItem { @Sendable [weak self] in
    Task { @MainActor [weak self] in
        self?.retryAfterBackoff()
    }
}
…
DispatchQueue.main.asyncAfter(deadline: .now() + interval, execute: workItem)
```

The work item is dispatched on `DispatchQueue.main`, so its body already runs on
the main thread — the `Task { @MainActor }` buys nothing, and it breaks the one
property the surrounding design relies on: cancellability.

`SingleSlotRetryScheduler.clear()` (via `cancelPendingBackoffRetry()`) cancels the
`DispatchWorkItem`. Once the work item has fired, its `Task` is already
enqueued and `DispatchWorkItem.cancel()` cannot stop it. So in the narrow window
between the work item running and the `Task` being scheduled, a confirmed
re-registration's `cancelPendingBackoffRetry()` is a no-op and one redundant
`connectToBroker` runs after re-registration has already succeeded.

That redundant connect is harmless: `BrokerConnectionSignalAdmission` discards
signals from a superseded generation, which is exactly the guard #0272 put in
place. Removing the hop simply means the cancel actually cancels.

## Expected behavior

`cancelPendingBackoffRetry()` reliably prevents a pending backoff retry from
running, with no window in which a cancelled retry still fires.

## Actual behavior

A backoff retry that has already begun executing cannot be stopped, so one
redundant `connectToBroker` can run after a confirmed re-registration. It is
discarded downstream and has no observable effect.

### Location

`BattyKit/Sources/BattyKit/XPC/AppXPCCoordinator.swift:341-344` (the
`DispatchWorkItem` / `Task` block), with `DispatchQueue.main.asyncAfter` at
`:352`, `cancelPendingBackoffRetry()` at `:362`, and its callers at `:133`

*Correction to the report that prompted this issue:* it cited lines `339-341`.
The actual range on the branch is `341-344`. Re-verify before editing — line
numbers will shift again once the branch is squashed.

### The fix is likely one line

Drop the inner `Task { @MainActor … }` and mark the work item's body
`@MainActor` — `asyncAfter(deadline:execute:)` on `DispatchQueue.main` already
guarantees main-thread execution. Note `CLAUDE.md`'s standing rule that a `Task`
hop is not a way to launder an isolation problem; this is the same rule pointing
the other direction.

Sanity-check the `@Sendable` annotation while there: the closure captures `self`
weakly and does nothing off-main, so tightening isolation should not require new
`Sendable` conformances.
