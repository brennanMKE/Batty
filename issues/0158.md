| | |
|---|---|
| **Status** | resolved |

## Description

The existing `BattyUITests` target ([[0091]]–[[0095]]) is too thin to catch the class of regression that has been hurting us. [[0157]] (tab rename silently dropped) and the drag-and-drop series ([[0102]], [[0143]], [[0144]], [[0156]]) all slipped through because nothing in CI exercised those paths. The current harness can drive keyboard shortcuts and assert on accessibility identifiers, but it cannot scripts complex setups (3 sessions, swap panes between them), cannot drive drag-and-drop, and has no path for asserting on internal model state when the UI surface is opaque (libghostty Metal rendering is invisible to XCUITest).

This issue builds the foundation that the area-specific test suites (the [[0159]]–[[0169]] series filed alongside it) depend on. Two pieces:

1. A **launch-argument scripted-action driver** that lets a test set up arbitrary app state in one synchronous burst before assertions begin.
2. A **drag-and-drop test harness** with two operating modes: an *intent-level* mode that exercises the model and SwiftUI state paths without going through `NSDraggingSession`, and an *AppKit-level* mode that uses `XCUIElement.press(forDuration:thenDragTo:)` to drive real drag sessions for the small set of tests that need full-fidelity drag-routing coverage.

## Why this matters — failure modes the foundation must support

| Failure mode | Example regressions | What the foundation must enable |
|---|---|---|
| Bug only appears with N sessions / M panes in a specific layout | [[0156]] (cross-session drop), [[0090]] (vertical-split click) | Scripted setup of arbitrary session/pane/layout state in one launch |
| Bug lives in the SwiftUI model-write path (not the drag mechanics) | [[0157]] (rename), [[0142]] (home-dir tab title) | Intent dispatcher that exercises the same code paths the UI calls |
| Bug lives in AppKit drag-routing / z-order | [[0102]], [[0143]], [[0144]] | Real `press(forDuration:thenDragTo:)` drag through NSDraggingSession |
| Bug requires reading terminal pixels | All terminal-content assertions | Existing sentinel-file pattern (keep) |

## Part 1 — Scripted-action launch-arg driver

### Surface

App reads `BATTY_UI_TEST_SCRIPT` env var early in `BattyApp.init` (alongside the existing `BATTY_UI_TEST_MODE`). The value is a JSON-encoded array of intents. A `UITestDriver` runs them sequentially on the main actor *before* the first window is presented, via the same `AppStateStore` dispatcher that real menu items and shortcuts call.

```jsonc
[
  { "intent": "createSession", "name": "Work" },
  { "intent": "applyLayout", "layout": "twoByTwoGrid" },
  { "intent": "createSession", "name": "Notes" },
  { "intent": "selectSession", "name": "Work" }
]
```

### Initial intent vocabulary

Keep it small; grow it per consumer issue.

- `createSession(name:?)` — same path as `Cmd-Option-N`.
- `selectSession(name:)` — same path as sidebar click.
- `closeSession(name:)` — same path as sidebar context menu close.
- `renameSession(from:, to:)` — same path as sidebar rename.
- `applyLayout(layout:)` — same path as the layout picker; layout names match the enum.
- `createTab` — Cmd-T.
- `closeActiveTab` — Cmd-W (without the close-confirmation prompt).
- `renameActiveTab(to:)` — sets `titleOverride` via the same path as the Rename Tab sheet's `onCommit`.
- `resetActiveTabTitle` — clears `titleOverride`.
- `splitHorizontal` / `splitVertical` — Cmd-D / Cmd-Shift-D.
- `focusPane(at:)` — index in `tree.allPanes` iteration order.
- `swapPanes(at:_, with:_)` — direct call to `tree.swapPanes`. Bypasses NSDraggingSession deliberately; the AppKit drag path has its own test mode (Part 2).
- `applyTheme(name:)` — same path as View → Theme menu.
- `applyThemeToActiveSession(name:)` — per-session override.
- `dropFileURLs(_:ontoPaneAt:)` — same path as `TerminalHostView.performDragOperation` after URL extraction; sends shell-quoted text via `terminal.send`.

Each intent maps 1:1 to a method on `AppStateStore` (or `tree` / `pane` for fine-grained ones). Adding an intent is a one-method-and-one-enum-case change; consumers do not edit a giant switch.

### Implementation sketch

- New file: `BattyKit/Sources/BattyKit/Testing/UITestDriver.swift`. Gated behind `#if DEBUG` is *not* the right gate (UI tests run against the Beta release-ish build); gate behind the env var presence at *runtime* so production launches never enter the driver.
- Logger category `"UITestDriver"`, tag prefix `ui-test:`. Log every intent before and after dispatch with the intent name and key parameters. This makes test failures debuggable from Console.app the same way the [[0154]] logging does for DnD.
- Drive intents synchronously on the main actor. The driver awaits each intent before dispatching the next so observers (workspace save, theme apply, etc.) settle in order.
- Surface errors via a sentinel file at a known path (`/tmp/batty-ui-test-driver-error-<uuid>`). The test harness polls for it before its first assertion; presence means the script failed and the test should fail with the error contents.

### Harness extension

`BattyUITestHarness.launchBatty(script:)` overload that JSON-encodes an array of intents into `BATTY_UI_TEST_SCRIPT`. Existing `launchBatty()` keeps working unchanged.

## Part 2 — Drag-and-drop test harness

Two modes; tests pick the one appropriate to what they're verifying.

### Mode A — intent-level drop (model/SwiftUI state)

For tests of "drag from pane A onto pane B causes the right model mutation": use the `swapPanes` intent from Part 1. Fast, deterministic, covers everything *up to* the NSDraggingSession boundary. This is what most DnD tests should use.

### Mode B — AppKit-level real drag (drag-routing fidelity)

For tests of "drag actually reaches the right NSDraggingDestination": use `XCUIElement.press(forDuration:thenDragTo:)` on the `pane-drag-handle.<paneID>` accessibility element, dropping onto the `pane-terminal.<paneID>` target. This is the only path that exercises:

- AppKit z-order between SwiftUI overlays and `TerminalHostView` (the [[0143]] failure mode).
- SwiftUI `.onDrag` gesture initiation under contention with `SlidingTabBar` gestures (the [[0127]] re-opening failure mode).
- File-drop routing from `NSDraggingDestination` on the terminal NSView (the [[0144]] failure mode — at least for the drop-target side; the *source* side is Finder, which the test can't drive).

### File-drop AppKit-level test

The Finder-side of the drop can't be tested. The drop-destination side can: build an `NSDraggingSource` programmatically inside the test (an `NSPasteboardItem` with a file URL), dispatch a drag to the terminal NSView's accessibility frame, assert the file path appears in the shell prompt via the sentinel pattern (`echo $READLINE` after typing input is one option; simpler may be: send a `cat > /tmp/sentinel; CR` first, then drop, then close stdin, then check sentinel). This is fiddlier than Mode A but unavoidable for full coverage of the file-drop path.

If the in-process drag construction is too brittle, fall back to a *macOS Shortcut* or `osascript`-driven Finder drag — acceptable since this category of test will be small (5-10 cases, not hundreds).

## Out of scope

- Replacing the existing sentinel-file pattern for terminal output (it works and is not the bottleneck).
- A full DSL for test scripts beyond the flat intent list (YAGNI — flat JSON is enough for the foreseeable suite).
- Cross-process drag simulation from Finder/other apps (covered by the AppKit-level drop test inside the app itself).
- Test reporting / coverage tooling beyond what `xcodebuild test` already produces.

## Acceptance criteria

- `BATTY_UI_TEST_SCRIPT` accepts a JSON array of intents and dispatches them through `AppStateStore` before any assertions can begin.
- The initial intent vocabulary listed under Part 1 is implemented and exercised by at least one test in the [[0159]]–[[0169]] series.
- `XCUIElement.press(forDuration:thenDragTo:)` driving `pane-drag-handle.<id>` → `pane-terminal.<id>` produces a pane swap reliably (timing tolerances tuned for headless CI).
- A programmatic in-process file drop to `TerminalHostView` is demonstrated by at least one Mode-B test.
- `ui-test:` log lines appear in Console.app for every dispatched intent (visible per [[0154]]).
- Build + test passes: `xcodebuild -scheme 'Batty (Beta)' -destination 'platform=macOS' test`.

## Notes

- Build with `'Batty (Beta)'`, not the stale `Batty` from CLAUDE.md.
- This issue blocks [[0159]]–[[0169]] but the area issues can have their test cases drafted in parallel — the driver / harness work is the only path-clearing.
- The intent surface should grow conservatively. When a test wants to do something new, add the intent if it represents a real user action; do not add intents that exist only to make a test possible (those are usually a sign the test is asserting at the wrong level).
