## Description

Child of #0646. Add a new non-terminal Pane kind, the **Server Pane**, and CLI verbs to start or attach a dev server and show it. Today an agent that starts `go run .` either leaves it in a terminal with no summary of whether it is up, or opens a browser on its own. The user builds Go websites often; that is the main use case.

Feature request from the user (Brennan), 2026-11-17.

### Current state (checked against `main` at `3b5735c3`)

- Pane kinds (`PaneContentKind`, `BattyKit/Sources/BattyXPCCore/PaneContentKind.swift`): `terminal`, `git-status`, `process-status`, `lm-studio-dashboard`, `system-metrics`. The status-view kinds are created with `batty pane split --view <kind>`; kind-specific options travel in `PaneSplitRequest.viewOptions: [String: String]?` (decided in #0301, "Decisions"), with friendly per-kind CLI flags (`--path`, `--pid`).
- `batty pane split -c <command>` already runs a command in a new terminal Pane. There is no `tab new` verb (`docs/batty-cli-agent-workflows.md`, "Current limitations").
- `--unique` (#0383) finds an existing visible Pane of the requested kind and creates nothing. It matches on kind alone: `PaneCommand.swift` says "`viewOptions` differences (`--path`/`--pid`) do not defeat the match." A port-keyed match is new behavior.
- Per-process sampling exists: `ProcessMetricsReader` (libproc: `proc_pidinfo`, `proc_pid_rusage`, `proc_pidpath`, `proc_listallpids`) backs Process Status and System Metrics. Nothing in `BattyKit/Sources` finds which process listens on a TCP port.
- Split direction on the wire is `horizontal` / `vertical` (`SplitDirection`, `LayoutModel.swift`; CLI `-h`/`-v`). There is no Settings preference for where CLI-created Panes go.

## Root cause

Feature work. Batty had no Pane kind for a dev server and no CLI verb to start or attach one; nothing in `BattyKit/Sources` found a port's listener, and agents either left servers unsummarized in a terminal or opened a browser themselves.

## Gotchas

- **Plan premise false: `foregroundPid` is always nil.** `TerminalView.foregroundPid` (libghostty-spm) is a stub on the pinned Ghostty 1.3.1, so there is no `tcgetpgrp` value to record. Stop in start mode targets the **listener's** process group, and only after `ServerJobResolver` proves it is a job of this Tab's shell (round 2, see Fix). Stop before anything listens has nothing to signal and just records Stopped; a command that never listens is stopped from its terminal. The scan covers every same-user pid in both modes, so a foreign listener is shown but not signalled. Without OSC 133, exit is seen only as the listener disappearing (state back to Starting).
- **Tab shell identity (round 2).** `/bin/zsh` and other platform binaries hide their environment from `KERN_PROCARGS2`, so `BATTY_TAB_ID` identifies only non-platform shells (Homebrew fish or bash). For zsh the shell is found by start time: the only Batty `login` child started after the Tab was created. If two Tabs spawn shells at the same moment (Project open, Session restore) while a Server Pane's terminal is created, the shell is ambiguous and Stop refuses for that Pane's life. Restart from a refused Pane is also refused. Closing its terminal and running `server start` again makes a new Tab and a new baseline. This is fail-safe, not a crash. The baseline uses wall-clock `gettimeofday`, the same clock as `p_starttime`, so a clock step backwards between baseline and spawn would also refuse.
- `ProcessInspector` is main-actor (package default isolation), so `ListeningPortScanner` has its own nonisolated libproc fd listing instead of reusing `fetchFileDescriptors`. EPERM is not logged through `FailureLogGate`; unreadable pids are skipped silently.
- `ServerPaneContent` takes `startsBackendOnSetUp: false` from the store: the backend's Tab lookup only succeeds once the terminal Pane exists, which is after the Server Pane is created (and set up).
- `ProcessGroupStopperRealProcessTests` are `@MainActor` (the stopper is main-actor); the blocking `waitpid` runs in a detached task. The first fixture version raced (signal before the grandchild existed, 30 s EOF waits and one false pass); the grandchild now prints "ready" itself.
- `Batty/Localizable.xcstrings` was not edited: the build does not extract into it and it holds only 19 strings, so new strings fall back to their English source like the other recent features.
- `pane split -c` is used in the attach UI test to run the external server, because the sandboxed UI-test runner can't host a listening server itself.
- **Unverified:** Visual sign-off on the Server Pane (design doc is "drafted for user approval") and the `docs/terminal-pane-requirements.md` §6 checklist with a Server Pane beside terminal Panes are the user's (User checklist above). Nothing exercised a real `go run .` or the expvar section against a live server.
- **Shell re-lookup after the cached shell exits (reviewer, non-blocking).** Once the Tab's shell is found it is cached by pid and start time. If that shell exits while its Tab is still reported available (before the next tick records "Stopped, terminal closed"), the next Stop looks the shell up again by start time and could settle on a different Batty shell spawned after the baseline. Stop would then signal only a job of that other, newer Batty Tab, and only if it holds the port. Ghostty closes the surface when its shell exits, so the window is short. A follow-up could refuse instead of re-locating once a shell has been found. Fixed by #0658: Stop now refuses instead of re-locating.
- **For the user:** approve the design (`docs/design/server-pane-view.md` is "drafted for user approval"); run the `docs/terminal-pane-requirements.md` §6 checklist with a Server Pane beside terminal Panes; try a real `batty-beta server start --port 8083 -- go run .` (Listening, metrics, expvar sparklines, Stop, Restart). The concurrent-shell-spawn limitation above (Stop refused for that Pane's life when another shell spawns at the same moment) is by design and fail-safe.

The finding below is blocking because Stop can signal processes Batty didn't start.

### Blocking

1. **Start-mode Stop can kill a process group that has nothing to do with the Server Pane's Tab** (`ServerPaneContent.performTick`, `TerminalTabServerBackend.stopTarget`, `SystemPortListenerScanner.jobGroup`).
   - In start mode the listener comes from `scanner.listeners(port:)`, which scans **every same-user pid** (`sameUserPids()`). Stop then calls `killpg(getpgid(listener))`, escalating to SIGKILL. The only protection is the group of the leader's parent.
   - Nothing checks that the listener descends from the shell in the Server Pane's own terminal Tab. If the port is already held, or gets taken while the Pane is Starting (after a crash plus Restart, or during a slow `go run` compile), the Pane adopts the other process and Stop signals its whole group.
   - **Concrete case.** An agent such as Claude Code runs in a Batty Tab as job group C. Its Bash tool has already started `go run .` on 8083, and that server shares group C because a non-interactive shell has no job control. The agent then runs `batty server start --port 8083 -- go run .`. The scan finds the agent's server, and `jobGroup` returns pgid C with only the agent's parent zsh protected. `batty server stop --port 8083`, or the reuse/Restart path, SIGINTs, SIGTERMs and then SIGKILLs the agent itself. The same thing happens to a server started in Terminal.app, or to an Electron app's helper that shares the app's group (the whole app is signalled).
   - **What would satisfy it.** In start mode, Stop (and preferably listener adoption too) only targets a group tied to this Pane's Tab. For example:
     - (a) Record the Tab's shell pid when the terminal Pane is created, by diffing Batty's descendant shells or reading the login child of the surface, and require that the job leader's parent **is** that shell. The shell's `proc_bsdinfo.e_tpgid` then gives the foreground job group in place of the stubbed `foregroundPid`.
     - (b) Any equivalent check that the listener descends from that Tab's shell and is in a group other than the shell's.

     A listener that fails the check should show as Listening with no Stop (the "not ours" case, like `listening(pid: nil)`), and be logged. Add unit tests on the fakes with a pinned name, e.g. `stopRefusesAListenerNotDescendedFromTheTabShell` and `listenerInAnotherJobGroupIsNotAdopted`.

Exclude `getpid()` (and refuse a root that is an ancestor of Batty) in `tree`/`signal`, and add a test.

  - A `-c` command Tab (`TabRuntime.applyShellAndAppearancePreferences`, `wait-after-command = true`) **replaces** the shell. Its process cannot be re-run in the same Tab without respawning the surface, and there's no API for that. A shell Tab with a typed-in command (`TabRuntime.armStartupCommand`, `StartupCommandDelivery`, `TerminalInputSink.runLine`) keeps the shell, so the command can be stopped and typed again. Restart in the same Tab needs this route.
  - `TerminalDelegateProxy.onCommandFinished(exitCode:durationNanos:)` (OSC 133 D) already delivers each command's exit code. `TabRuntime` uses it as a single closure, wired in `init` to `receiveCommandFinished()`. `tab.terminalNSView?.foregroundPid` (`tcgetpgrp`) gives the Tab's foreground process group, as Process Status uses it.
- Precedent for the design gate: Process Status, Git Status, System Metrics and LM Studio were all built against designs marked "not yet approved" (`PaneContentKind.swift` doc comments). Visual sign-off happens when the user checks a `resolved` issue.

### Decisions (open questions 1-9, decided per the user's "complete every #0646 child" instruction)

1. **Grammar: a new noun, `batty server start|attach|stop|restart`.** Folding this into `pane split --view server` doesn't work: `start` needs a trailing `-- <command…>`, a working directory and a terminal Pane as well as the view, and `stop`/`restart` act on a running process, not on a Pane. The noun is approved the same way `project` was (#0469). `docs/batty-cli-design.md` §1.1 records `server` as the sixth noun, with this reason. Recommendation for #0649: `batty server serve <dir>` under this noun rather than a top-level `serve`, which #0649's planner decides.
2. **Restart for attached servers: only with `--command`.** `attach` takes `--command <text>` and `--cwd <dir>` (default: the CLI's cwd). Without `--command` there is no Restart. Batty never runs a command it recovered from another process's argv. Running recovered argv needs a trust prompt like Projects', and an agent can pass the command it already knows. The recovered command line (`ProcessInspector.commandLine(pid:)`) is shown read-only in the Pane as information. Restart of an attached server with a command stops the external process, then runs the command in a new terminal Pane under the Server Pane. From then on the Pane behaves as if `start` had created it.
3. **Port detection: libproc, in-process, no `lsof`.** `PROC_PIDLISTFDS`, then `proc_pidfdinfo(PROC_PIDFDSOCKETINFO)` for each socket fd, matching `soi_kind == SOCKINFO_TCP`, `tcpsi_state == TSI_S_LISTEN` and `insi_lport` (network byte order) equal to the port.
   - Candidates: in `start` mode, the Tab job's process group (`proc_listpids(PROC_PGRP_ONLY, pgid)`). In `attach` mode, every same-uid pid.
   - Cadence: once a second while the server is starting. Once a listener is found, only that pid is re-checked each tick, with a full re-scan only when it disappears.
   - The whole-table scan runs off the main actor in a detached task, with a generation counter so stale results are dropped (the #0350 pattern, `docs/pane-view-lifecycle.md` §4).
   - A listener owned by another user (`EPERM`, for example root): the scan finds no pid. If the HTTP probe answers, the Pane shows **Listening, owned by another user** with no PID, metrics or Stop.
4. **Which PID: metrics on the listener, Stop on the Tab's job.** CPU, memory and uptime come from the listener's pid (the compiled child under `go run .`). Uptime is from its kernel start time (`ProcessInspector.listedIdentity`). Memory uses `physFootprintBytes`, never RSS (#0290). In `start` mode, Stop signals the Tab job's process group: the `tcgetpgrp` value that differs from the shell's own pgid, recorded just before the command is typed. In `attach` mode, Stop signals the listener pid and its descendants (a `pbi_ppid` walk), never a process group, because an external process's group may hold its parent shell.
5. **HTTP probe.**
   - URL: `http://localhost:<port>/` unless `--url` is given. `--url` sets both the displayed URL and the probed URL, so it can carry a path or `https`.
   - What counts as "answering": any HTTP response, any status. The status is shown, for example `200` or `404`.
   - Timeout: 2 s, using an ephemeral `URLSession`.
   - HTTPS: self-signed certificates are accepted **only when the host is loopback** (`localhost`, `127.0.0.1`, `::1`). Other hosts use default trust evaluation.
   - Cadence: on the transition to listening, then every 5 s while the Pane is visible. A failed probe after a success shows "Not responding" while the state stays Listening.
   - No `--health-url`. `--url` covers it.
6. **Where the command runs: a new terminal Pane.** `start` creates a Server Pane next to the target Pane in the placement direction, then a terminal Pane **below the Server Pane**: summary on top, logs underneath. A new Tab in the caller's Pane is rejected, because it would replace the agent's own Tab on screen. No `tab new` verb is needed. Keyboard focus stays on the calling Pane: `tree.focusedPaneID` is restored after the two splits, in the same synchronous event-origin turn. An agent's terminal keeps the keyboard.
7. **`--unique` is always on for `start` and `attach`, keyed on (Session, port).** There is no flag and no opt-out. Two servers can't share a port, so a second Pane for the same port is never right. Hidden Server Panes match too, and are shown again (`WindowRuntime.showPane`).
   - Re-running `start` for a port that already has a Pane: reuses that Server Pane and its terminal Tab, replaces the stored command and cwd with the new ones, and restarts.
   - If that Tab is gone: makes a new terminal Pane under the Server Pane.
   - If the Pane was attach-mode: converts it, stopping the external process first.
   - Re-running `attach` for a port that already has a Pane: returns the existing Pane and changes nothing.
8. **Identity: one Server Pane per port per Session.** When the terminal Tab is closed by hand (its shell gets SIGHUP), the Server Pane stays and shows **Stopped, terminal closed**. Restart makes a new terminal Pane under it.
9. **Stop escalation:** SIGINT, then wait up to 5 s; SIGTERM, then up to 3 s; then SIGKILL.
   - "Alive" means any non-zombie pid is left in the target set (`proc_listpids(PROC_PGRP_ONLY)` plus a `pbi_status != SZOMB` check, or the descendant walk in attach mode).
   - The wait polls aliveness every 250 ms on the injected `SchedulingClock`. In start mode it ends at once when the Tab's `onCommandFinished` arrives.
   - **Closing the Server Pane does not stop a terminal-backed server.** The terminal Pane owns the process, and closing that Pane already goes through Batty's running-process confirmation. Closing never kills anything silently.
   - `tearDown()` cancels an in-flight Stop. Signals already sent stay sent.
   - A backend without a terminal (#0649's in-app server) declares `stopsOnTearDown = true`, and for it closing the Pane stops the server.

Further decisions the issue leaves open:

- **Placement setting:** Settings › General › "Server Panes: Open to the Right / Open Below", default Right, stored in `co.sstools.Batty.serverPanePlacement`. The issue's third option, "a new Tab", is dropped. A non-terminal Pane cannot be a Tab (`docs/pane-kinds.md` §1), and the terminal half already gets its own Pane (decision 6). `--split right|down` overrides the setting per call (right → `.horizontal`, down → `.vertical`). The setting is shown only with the flag on.
- **State names** (`ServerPaneContent.State`):
  - `starting`: the command has been typed, or attach is waiting, and nothing is listening yet. Attach to a port with no listener shows **Not listening** and keeps scanning.
  - `listening(pid?, httpStatus?)`
  - `stopping`
  - `stopped(exitCode?, reason)`: reason is `requested` or `terminalClosed`.
  - `crashed(exitCode?)`: the process exited without a Stop. Exit 0 without a Stop displays "Exited (0)"; any other code, or none, displays "Crashed".
- **Exit detection:** event-driven through the Tab's `onCommandFinished` (exit code from OSC 133 D). The fallback for shells without integration is a tick-time check that the foreground pgid is back to the shell's, which gives a nil exit code. Exit is an event, so a hidden Server Pane still records a crash. Only probes, scans, metrics and stats stop while hidden (`docs/pane-view-lifecycle.md` §4).
- **Restart in start mode:** Stop, wait for the job to finish (or the escalation to end), then type the command again with `TerminalInputSink.runLine` in the same Tab. No Project-style trust prompt. The command comes from the CLI the user or agent just ran, like `pane split -c`, which has none.
- **Command text:** `server start --port N -- <args…>`. One argument after `--` is used verbatim as shell text, so `-- "go run . | tee log"` works. Several arguments are POSIX-quoted one by one and joined. The CLI sends `workingDirectory` = its own cwd, made absolute client-side, as `--path` is today.
- **Stats:**
  - `/debug/vars` on the server's origin (scheme, host, port), or `--stats-url`. Polled every 2 s while visible and listening.
  - A 404, a non-JSON body or a connection error at `/debug/vars` hides the section and stops polling until the next listening transition. An explicit `--stats-url` that fails shows one muted line, "Stats unavailable: <reason>".
  - A non-loopback `--stats-url` host is labeled in the section header ("Stats from <host>").
  - Parsing flattens JSON objects to dotted keys. Numbers are numeric leaves (`Bool` excluded); strings and bools are text. Arrays are skipped, except `cmdline`, which is joined as text.
  - `memstats` is reduced to an allow-list: `Alloc`, `HeapAlloc`, `HeapInuse`, `HeapObjects`, `Sys`, `NumGC`, `PauseTotalNs`.
  - At most 24 numeric series and 60 samples each, in a ring buffer. A sparkline is drawn only for a series whose value has changed. Constants are plain values.
- **`--wait [--timeout S]`** (default 60 s) on `start`/`attach`: the app replies once the state leaves `starting` or the bound passes, on the injected clock, following the `projectOpen` waiter pattern in `AppXPCService`.
  - Exit `0` when listening.
  - Exit `4` with "server exited (code N)" on crash.
  - Exit `4` with "timed out; still starting" on timeout.
  - The CLI's XPC timeout is `timeout + 5`.
  - Without `--wait` the reply is immediate, and `pid`/`url` are filled in only if already known.
- **Creation is CLI-only in this issue.** No menu, Command Palette or Project slot creates a Server Pane: it needs a port and a command. `pane split --view server` is refused by the CLI, which hides the kind, and by `AppXPCService` ("use batty server start/attach"). Save Session as Project captures a Server Pane as an empty terminal slot, with a capture note ("Server views aren't saved in Projects").
- **Feature flag `serverPane`:** on in Beta, off in Prod, with a CLI `current` and a UI-test force-off override.
  - With the flag off, the `server` noun is absent from the CLI tree (`BattyCLI.subcommands(for:)`, the #0477 pattern removed by #0504, restored), so `--help` and `capabilities` never mention it.
  - The four XPC verbs reply `ok: false` "server panes are not available in this build".
  - The Settings row is hidden.
  - `.server` never appears in `--view` values.
- **For #0649:** the Pane's monitoring (listener scan, probe, metrics, stats) is separate from how the server runs. A `ServerBackend` protocol carries that difference. #0649 adds its in-app static server as a third backend, with no change to the view or the monitor.

## Expected behavior

### `batty server start`

```sh
batty server start --port 8083 -- go run .
```

- Runs the command in a terminal Tab, so its logs stay visible and the user can interact with it, and shows a Server Pane for it in the same Session.
- The Server Pane shows:
  - **State:** starting, listening, crashed (or stopped). Starting until something listens on the port; then an HTTP probe of the URL confirms it answers. Crashed when the process exits without a Stop.
  - PID, uptime, CPU and memory (reusing `ProcessMetricsReader`; never RSS, per #0290), the URL, and the last exit code.
  - **Open in Browser**: opens the URL in the default browser.
  - **Restart**: Batty knows the command, so it stops the process and runs the same command again in the same terminal Tab.
  - **Stop**: SIGINT to the process group; escalate to SIGTERM, then SIGKILL, if it does not exit within a bound.
- Prints the Server Pane's id (and, with `--json`, the Pane id, the terminal Tab id, the URL and the PID once known).

### `batty server attach`

```sh
batty server attach --port 8083
```

- For a server started elsewhere: finds the process listening on the port and shows a Server Pane for it, with state, PID, metrics, URL and Open in Browser.
- Restart appears only when the launch command is known (see Open questions). Stop is available for a process the user owns.

### Stats

- When the server exposes Go's standard `expvar` endpoint (`/debug/vars`), the Server Pane reads it on an interval and shows the counters, with small charts for values that change (for example `memstats` heap, GC count, goroutines if published, and any app-defined vars).
- `--stats-url <url>` points at any other JSON endpoint instead. Numeric leaves are shown and charted; non-numeric values are listed.
- No endpoint, or a 404 at `/debug/vars`: the stats section is hidden, not an error.

### Placement

- A Settings option for where a new Server Pane appears: a split to the right, a split below, or a new Tab. The default is to the right.
- `--split right|down` overrides it per call, mapping onto the existing `horizontal`/`vertical` split directions.
- `--unique` (on by default for `server start`/`attach`, or opt-in; see Open questions) is **keyed on port**: re-running `batty server start --port 8083 -- go run .` reuses the existing Server Pane for 8083 (and its terminal Tab), restarting the server there, instead of adding Panes.

### Documentation and rules

- This work must respect `docs/pane-kinds.md` (kind lives on the Pane; one view per non-terminal Pane; the terminal-host boundary in §3), `docs/view-hierarchy.md` (the persistent AppKit terminal host; the terminal Tab this runs the command in is an ordinary terminal Tab), `docs/terminal-pane-requirements.md` (the new Pane must not break pointer input, keyboard, file drop, text drop or IME in neighboring terminal Panes; run its manual checklist) and `docs/swiftui-observation-rules.md` (sampler and probe results are written from their own event sources, never from `body` or layout-origin `onChange`). `docs/pane-view-lifecycle.md` (#0303) governs setup, teardown and show/hide: a hidden Server Pane stops its probes and stats polling.
- The visual design is drafted under `docs/design/` and approved by the user before implementation (#0301's design-first gate), like `docs/design/process-status-view.md`.
- `Concepts.md` gains the Server Pane under Pane; the `batty-cli` skill and `docs/batty-cli-agent-workflows.md` gain the start/attach recipes (#0647 carries the agent rule).
- `batty capabilities --json` lists the new verbs with full `inputSchema`, and `CapabilitiesInputSchemaTests` covers them.
- Behind a feature flag (`FeatureFlags`, Beta on / Prod off) until the release that ships it.

## Acceptance criteria

- `batty server start --port N -- <cmd>` creates a terminal Tab running `<cmd>` and a Server Pane placed per Settings or `--split`. The Pane moves starting → listening once the port answers, and to crashed with the exit code when the process dies.
- Restart runs the same command again in the same Tab; Stop ends the whole process group (a `go run .` child server does not survive Stop).
- `batty server attach --port N` shows a Server Pane for a process started outside Batty, without Restart unless the command is known.
- A server exposing `/debug/vars` shows its counters; `--stats-url` works for another JSON endpoint; a server with neither shows no stats section and no error.
- Re-running `server start` for the same port reuses the existing Server Pane and Tab.
- Unit tests cover state transitions, port-keyed reuse, process-group stop and escalation, expvar parsing and the probe, with injected clocks and fake port/probe sources, and no sleeps (`AGENTS.md`, "Asynchronous tests"; `docs/async-test-seams.md`).
- The `docs/terminal-pane-requirements.md` manual checklist passes with a Server Pane next to terminal Panes. A UI test covers creating and closing a Server Pane, checked with `./build.sh ui-typecheck`.

## Open questions

1. **Grammar.** `server` would be a new noun; `docs/batty-cli-design.md` §4 keeps the set to session/pane/tab/window (plus `project`). Approve `batty server start|attach|stop|restart`, or fold it into `pane split --view server --port …`?
2. **Restart command for attached servers.** Options: read the process's argv and cwd (`sysctl KERN_PROCARGS2`, works for the user's own processes) and offer Restart only after the user confirms it; accept `--command` on `attach`; or never restart attached servers. Running a command recovered from another process's argv needs a trust step like Projects' startup-command trust prompt.
3. **Port detection method and its permissions.** libproc (`proc_pidfdinfo` with `PROC_PIDFDSOCKETINFO` over each pid's fds) needs no extra permission for the user's own processes and no subprocess; `lsof -iTCP:N -sTCP:LISTEN` is simpler but spawns a process per check. A connect probe alone tells "something listens" but not which PID. Which, how often, and what to show for a listener owned by another user (root)?
4. **Which PID.** `go run .` starts a compiled child; the listener is the child, not the PID the Tab started. Track the listener's PID for metrics and the Tab's process group for Stop?
5. **HTTP probe.** Which path (`/`, or a `--health-url`), what counts as up (any response, or 2xx/3xx), and HTTPS with self-signed certificates.
6. **Where the command runs.** "New Tab" placement: a new Tab in the calling Pane, or a new terminal Pane? There is no `tab new` verb yet; this may need one.
7. **`--unique` default.** On by default for `server start` (the user's "re-running reuses its view"), or opt-in like `pane split --unique`?
8. **Server Pane identity.** One Server Pane per port per Session, or per Window? What happens when the terminal Tab is closed by hand: the Server Pane shows stopped, or closes too?
9. **Stop escalation bound** and whether Stop on Pane close is automatic (closing the Server Pane stops the server?) or asks.

## Notes

- Network access: the probe and stats polling hit `localhost` only by default. `--stats-url` to a non-local host should be allowed but clearly shown.
- The app is unsandboxed and Hardened Runtime stays on (`AGENTS.md`), so libproc reads of the user's own processes work, as Process Status already does.
- The reverse-proxy idea for servers without stats is deferred on #0646; do not build it here.
