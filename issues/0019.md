## Description

Make the divider between two children of a Split draggable. Live preview while dragging; the ratio is written back into the `SplitNode` model. Mirrors `Concepts.md` → Split → "Resized by".

**Acceptance criteria:**
- Each split divider responds to mouse drag with the appropriate cursor (resize-left-right or resize-up-down).
- Dragging updates the ratio in real time; child views resize live without flicker.
- Ratio is clamped to a sensible range (e.g. 0.1–0.9) so a Pane can't be made invisible.
- The new ratio writes back to the model so it persists (M7) and survives session-switching.
- Resizes nest correctly: dragging the divider of an inner split doesn't disturb outer splits.

## Notes

- This likely requires a custom split container (not `HSplitView`/`VSplitView`) — flag if you discover SwiftUI's built-ins can do live ratio updates well enough.
- Snap-to-50%-when-near-the-middle is a nice-to-have — leave for follow-up if it complicates this issue.
- Verify drag works correctly when the window is being resized at the same time (edge case, but real with multi-monitor setups).

### Deferred — 2026-05-08

`#0017` shipped with `HSplitView` / `VSplitView` from SwiftUI, which give the user a draggable divider for free but **don't persist the ratio back into the model** (the split's `ratio` associated value on `SplitTreeNode.split` is stored but unused at the view layer; HSplitView keeps its own internal divider position and resets it whenever the tree restructures).

A proper fix needs a custom split view: `GeometryReader` + `DragGesture` + a writable path back into `SplitTreeNode`. That requires:

1. Adding a stable `id: UUID` to the `SplitTreeNode.split` case so a specific split can be addressed when its ratio updates.
2. A `SplitTree.updateRatio(forSplitID:to:)` method that walks the tree, replacing the matching `.split` with a new one carrying the updated ratio.
3. A custom `DraggableSplitView` taking `direction`, current `ratio`, and a `(Double) -> Void` callback. Internally `GeometryReader` for the available length, `HStack`/`VStack` with explicit child sizes, a 4pt-wide divider with cursor + drag gesture. Drag-start captures the current ratio; drag-changed adds `translation / totalLength` to the captured ratio, clamped to [0.1, 0.9]; drag-ended releases.
4. Replacing `HSplitView`/`VSplitView` in `SplitNodeView` with the custom view.

This is non-trivial enough that I'd rather land it with an eye on the actual interaction (drag feel, snap behavior, edge cases at minimum widths) — and that's a visual verification I can't do autonomously. Deferring.

In the meantime, the user can drag dividers via the SwiftUI default; the position just doesn't persist across tree mutations or app launches.

### What's left

Implement the four steps above. Persistence of the ratio per-split also feeds #0030 (workspace serialization) — `WindowState.sessions[…].tree` needs to carry the per-split id and ratio when this issue lands.

## Phase 2 fix — `8e313d4`

All four steps landed:

1. **`SplitTreeNode.split` case got a stable `id: UUID`.** Updated all pattern matches (`firstLeafPaneID`, `firstLeafPane`, `findPane`, `allLeafPanes`) and constructors (`inserting`, `removingPane`). Insertion generates a fresh UUID; collapse preserves the existing id; the model→runtime persistence converter (#0030's `WorkspaceConversion.swift`) generates a new UUID on load.
2. **`SplitTree.updateRatio(forSplitID:to:)`** walks the tree, replaces the matching `.split` case with a new one carrying the updated ratio. Clamps to `[0.05, 0.95]` so a pane can't be made invisible. The walker (`SplitTreeNode.updatingRatio`) is purely functional — it reconstructs unchanged subtrees preserving their ids so SwiftUI's diff sees minimal change.
3. **`DraggableSplitView`** (private to `SplitContainerView.swift`) replaces `HSplitView` / `VSplitView`:
   - `GeometryReader` measures available length per render.
   - Children get explicit widths/heights computed from `ratio × usable`.
   - A 4pt-thick `Rectangle` between them serves as the drag handle, fills with `Color(nsColor: .separatorColor)`.
   - `.onHover` pushes/pops `NSCursor.resizeLeftRight` / `.resizeUpDown` depending on direction.
   - `DragGesture(minimumDistance: 0, coordinateSpace: .local)` with `onChanged` capturing the start ratio on first call (via `@State dragStartRatio`), computing `startRatio + (translation / totalLength)`, forwarding via `onRatioChange`. Clamping happens in `updateRatio`, not in the view.
4. **`SplitNodeView`** dispatches to `DraggableSplitView` at split nodes, passing the split's `id` so its `onRatioChange` callback can route to `tree.updateRatio(forSplitID: id, to: newRatio)`.

Persisted ratio: each save (`#0030` cadence) reads the current tree's split ratios via `SplitNode(from: SplitTreeNode)`. Each load (`#0031`) reconstructs `SplitTreeNode.split(id: UUID(), ratio: persistedRatio, ...)`. The id changes on each load (new UUID), but ratio is preserved.

`xcodebuild build` passes; 44 BattyKit tests still passing.

## Gotchas

- **Visual verification needed.** Drag a divider and confirm: position updates live (no jump on release), text rendering doesn't flicker, cursor changes to the appropriate resize cursor on hover, splits at any nesting depth all drag independently. Quit and relaunch — the ratios should restore from `workspace.json`. `xcodebuild build` passes; resolved-not-closed.
- **Each split's id regenerates on load.** The persisted `SplitNode` has no `id` (it's a Codable value type), so the `SplitTreeNode.init(from: SplitNode)` converter generates a fresh UUID. Within a session the id is stable so drags route correctly; across sessions the id is forgotten. This is fine because `updateRatio(forSplitID:to:)` doesn't need cross-session id stability — the id only addresses the right split *during* an active drag.
- **`@State dragStartRatio` in `DraggableSplitView` may be lost** if SwiftUI tears down and re-creates the view during a drag. In practice, the view's position in the tree is stable while the user is holding a drag, so SwiftUI preserves the state. If a drag ever produces glitches, the fix is `@GestureState` instead of `@State`.
- **Snap-to-50% near the middle** is not implemented. Easy to add via `let snapped = abs(newRatio - 0.5) < 0.02 ? 0.5 : newRatio` in the gesture handler. Deferred.
- **No animation** on programmatic ratio changes (e.g., from a Cmd-Ctrl-arrow keyboard resize when `#0020` lands). Currently the ratio just jumps. Easy to add `.animation(.easeInOut(duration: 0.15), value: ratio)` later.
- **`HSplitView` / `VSplitView` are gone.** Their built-in macOS divider drag behavior (with whatever default snapping/resize cursor logic they had) is replaced by ours. If our implementation diverges from macOS conventions in subtle ways, the user will tell us.
