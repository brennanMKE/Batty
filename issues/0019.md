# 0019 — Draggable split dividers with live ratio updates and persistence

| | |
|---|---|
| **Status** | open |
| **Module** | Split |
| **Platform** | macOS |
| **First seen** | 2026-05-08 |

## Description

Make the divider between two children of a Split draggable. Live preview while dragging; the ratio is written back into the `SplitNode` model. Mirrors `Concepts.md` → Split → "Resized by".

**Acceptance criteria:**
- Each split divider responds to mouse drag with the appropriate cursor (resize-left-right or resize-up-down).
- Dragging updates the ratio in real time; child views resize live without flicker.
- Ratio is clamped to a sensible range (e.g. 0.1–0.9) so a Pane can't be made invisible.
- The new ratio writes back to the model so it persists (M7) and survives session-switching.
- Resizes nest correctly: dragging the divider of an inner split doesn't disturb outer splits.

## Notes

- This likely requires a custom split container (not `HSplitView`/`VSplitView`) — flag if you discover SwiftUI's built-ins can do live ratio updates well enough.
- Snap-to-50%-when-near-the-middle is a nice-to-have — leave for follow-up if it complicates this issue.
- Verify drag works correctly when the window is being resized at the same time (edge case, but real with multi-monitor setups).

### Deferred — 2026-05-08

`#0017` shipped with `HSplitView` / `VSplitView` from SwiftUI, which give the user a draggable divider for free but **don't persist the ratio back into the model** (the split's `ratio` associated value on `SplitTreeNode.split` is stored but unused at the view layer; HSplitView keeps its own internal divider position and resets it whenever the tree restructures).

A proper fix needs a custom split view: `GeometryReader` + `DragGesture` + a writable path back into `SplitTreeNode`. That requires:

1. Adding a stable `id: UUID` to the `SplitTreeNode.split` case so a specific split can be addressed when its ratio updates.
2. A `SplitTree.updateRatio(forSplitID:to:)` method that walks the tree, replacing the matching `.split` with a new one carrying the updated ratio.
3. A custom `DraggableSplitView` taking `direction`, current `ratio`, and a `(Double) -> Void` callback. Internally `GeometryReader` for the available length, `HStack`/`VStack` with explicit child sizes, a 4pt-wide divider with cursor + drag gesture. Drag-start captures the current ratio; drag-changed adds `translation / totalLength` to the captured ratio, clamped to [0.1, 0.9]; drag-ended releases.
4. Replacing `HSplitView`/`VSplitView` in `SplitNodeView` with the custom view.

This is non-trivial enough that I'd rather land it with an eye on the actual interaction (drag feel, snap behavior, edge cases at minimum widths) — and that's a visual verification I can't do autonomously. Deferring.

In the meantime, the user can drag dividers via the SwiftUI default; the position just doesn't persist across tree mutations or app launches.

### What's left

Implement the four steps above. Persistence of the ratio per-split also feeds #0030 (workspace serialization) — `WindowState.sessions[…].tree` needs to carry the per-split id and ratio when this issue lands.
