## Description

When more than one Session exists, a pane-swap drag started in the currently selected session can land on a drop zone belonging to a pane in a **different**, non-visible session. The `tree.swapPanes(source, target)` call then runs against the active session's `SplitTree`, where the target pane id does not exist — the existing guard in `SplitTree.swapPanes` (BattyKit/Sources/BattyKit/Model/SplitTree.swift:137) silently returns, the swap never happens, and the user sees nothing change. The drag *appears* to succeed (mouse-up, drop-zone unmount, drag preview dismissed) but the layout does not update.

Discovered via the [[0154]] diagnostic logs. Concrete trace from a 2-session repro (Session 1 with 3 panes in `mainLeftTwoRight`, Session 2 with 4 panes in `twoByTwoGrid`):

```
pane-swap: startDrag source=A0448D55-... (Session 2)
pane-swap: drop-zone mounted pane=941A0FF2-... ← Session 2
pane-swap: drop-zone mounted pane=4AF56B46-... ← Session 2
pane-swap: drop-zone mounted pane=1DC512A8-... ← Session 2
pane-swap: drop-zone mounted pane=9DD5B499-... ← Session 1 (!)
pane-swap: drop-zone mounted pane=93EAFA2A-... ← Session 1 (!)
pane-swap: drop-zone mounted pane=6E516DE2-... ← Session 1 (!)
pane-swap: swap source=A0448D55 target=6E516DE2 ← target is Session 1
```

Six drop zones mounted for a drag in a four-pane session — three of them belong to the non-visible Session 1. The macOS DnD system routed the drop to one of the Session 1 zones (whichever was topmost at the cursor in AppKit's z-order), and `tree.swapPanes` then dropped it on the floor.

## Steps to reproduce

1. Launch the app (single empty session is fine).
2. In Session 1, pick a multi-pane layout (e.g. `mainLeftTwoRight`).
3. Create Session 2 (Cmd-N or sidebar `+`).
4. In Session 2, pick the 4-pane (`twoByTwoGrid`) layout.
5. Drag a pane in Session 2 onto another pane in Session 2.
6. Repeat several times in different orderings — eventually one drop lands on a phantom Session 1 drop zone and visibly does nothing.

The failure is intermittent because it depends on which session's drop overlay ends up topmost at the cursor's screen location, which depends on view-mount order. The logs are deterministic — when `swap source=X target=Y` is followed by no layout change, look up whether `Y` is in the active session's tree.

## Expected behavior

Dragging a pane in Session N can only ever drop onto another pane in Session N. Drop zones for non-active sessions must not exist or must not be drop-targetable during a drag started in a different session.

## Actual behavior

Drop zones mount on **every** pane in every session whenever any drag is active (because `PaneSwapDragState.shared.isDragging` is process-global with no session/tree scoping). Cross-session drops are accepted by SwiftUI's `.onDrop`, but `SplitTree.swapPanes` silently no-ops because the target id isn't in the source pane's tree.

## Root cause

Two compounding facts:

1. **`PaneSwapDragState.shared` is process-global.** It tracks `isDragging` and `sourcePaneID` but no tree / session scoping. `PaneSwapDropZone.body` therefore mounts whenever `isDragging && sourcePaneID != pane.id` is true — that condition is true for every non-source pane in every session, not just every non-source pane in the *current* session.
2. **SwiftUI keeps the pane views of non-selected sessions alive** in the view hierarchy. The drop-zone overlays for those panes are hit-testable by AppKit's DnD dispatch even when the session isn't visible, because the underlying NSViews still exist with non-zero bounds in window coordinates.

The second fact is the deeper architectural reality (mirrors the persistent AppKit terminal host design described in `docs/view-hierarchy.md`) and is not something to fight; the fix belongs at the drop-zone-filter level.

## Fix — chosen approach (2026-05-20)

**Both** filter the drop zones by tree membership **and** surface the silent no-op in `SplitTree.swapPanes` as a notice log.

### A. Filter `PaneSwapDropZone` by tree membership

`PaneSwapDropZone` already takes the pane's `SplitTree` as a parameter (it calls `tree.swapPanes` on drop). Add a tree-membership check to the mount predicate: the zone exists only when **the drag's source pane is in the same tree as the drop-zone's pane**.

Concretely, in `PaneView.swift` where the conditional `.overlay` is applied:

```swift
let dragState = PaneSwapDragState.shared
if dragState.isDragging,
   let sourceID = dragState.sourcePaneID,
   sourceID != pane.id,
   tree.findPane(id: sourceID) != nil    // ← new
{
    PaneSwapDropZone(...)
}
```

`tree.findPane(id:)` already exists (SplitTree.swift:30) and is `O(n)` over the leaves — fine for the small tree sizes Batty cares about. The check runs once when the drag starts (`isDragging` flips on, drop-zone overlays evaluate their condition); it does not run per-mouse-move.

This is the structurally correct fix: the drop zone only exists where a swap is semantically possible. Cross-session drops become impossible at the SwiftUI layer, without needing to plumb session IDs through `PaneSwapDragState`.

### B. Log the silent no-op in `SplitTree.swapPanes`

Currently the guard at line 137 returns silently when either pane id isn't found in this tree. Add a `notice`-level log naming both ids and which one was missing. This is the defensive log that would have surfaced the bug immediately if it had been there during [[0154]]'s diagnostic pass; worth keeping for any future weirdness where the tree state diverges from caller expectations.

Add a file-scoped logger to `SplitTree.swift` following the project convention (`nonisolated private let logger = Logger(subsystem: Logging.subsystem, category: "SplitTree")`) and import `OSLog`.

Log line shape (note prefix tag `split-tree:` — distinct from `pane-swap:` and `file-drop:` so it groups cleanly in Console):

```
split-tree: swapPanes no-op missing=A id=<uuid> other=<uuid>
split-tree: swapPanes no-op missing=B id=<uuid> other=<uuid>
split-tree: swapPanes no-op reason=same-id id=<uuid>
```

Privacy `.public` on UUIDs (consistent with the rest of the diagnostic logging from [[0154]]).

## Out of scope

- Cross-session pane drag is **explicitly not supported** per [[0127]] ("Cross-session pane drag. Pane swap stays within the current session for v1."). The fix is to *prevent* the cross-session drop, not to make it work.
- Restructuring how SwiftUI mounts non-selected session views. That's an architectural change with broad implications; the targeted drop-zone filter is the minimal correct fix.
- Multi-window support — the same fix carries forward if/when multi-window lands ([[0027]]) because tree-membership is window-agnostic.

## Acceptance criteria

- With two sessions open, each with multiple panes, dragging a pane in Session A never produces a drop-zone mount log line for any pane in Session B. The `pane-swap: drop-zone mounted` count during a drag in an N-pane session is exactly `N − 1`.
- `tree.swapPanes` with a missing id produces a `notice` log line naming the missing side and both ids.
- All existing pane-swap behavior in single-session use continues to work unchanged.
- Build passes `xcodebuild -scheme 'Batty (Beta)' -destination 'platform=macOS' build`.

## Root cause

`PaneSwapDragState.shared` is process-global, so the `isDragging && sourcePaneID != pane.id` predicate that gates `PaneSwapDropZone` evaluated true for every non-source pane in every session — not just the active one. SwiftUI keeps non-selected sessions' pane views (and their backing NSViews) alive, so AppKit's drop dispatch routed cross-session drops to whichever phantom zone was topmost; `SplitTree.swapPanes` then silently no-op'd because the target id wasn't in the source pane's tree.

## Fix

Two-part change matching the issue's chosen approach:

- `PaneSwapDropZone` mount predicate now additionally requires the drag's source pane to live in this drop-zone's `SplitTree`, so cross-session zones are never mounted.
- `SplitTree.swapPanes` splits the collapsed guard into three branches and emits `notice`-level `split-tree:` logs that name the specific no-op cause (`same-id`, `missing=A`, `missing=B`) with both ids `.public`. Behavior on bad input is unchanged — just observable now.

## Files changed

- `BattyKit/Sources/BattyKit/Views/PaneView.swift` — added the `tree.root.findPane(id: sourceID) != nil` clause to the `PaneSwapDropZone` overlay condition.
- `BattyKit/Sources/BattyKit/Model/SplitTree.swift` — added file-scoped `SplitTree` logger (and `import OSLog`); split `swapPanes` guard into three branches with a notice log on each.

## Gotchas

- The spec wrote `tree.findPane(id:)`; the real API lives on `SplitTreeNode`, so the call site is `tree.root.findPane(id:)`. Semantically identical.
- `PaneSwapDragState` is `@Observable` and read inside the `.overlay` closure, so SwiftUI tracks `isDragging` / `sourcePaneID` and re-evaluates the overlay when the drag starts and ends. `tree` is `@Bindable` on `PaneView`, so the new `findPane` clause re-evaluates whenever the tree changes too. No additional wiring needed to make the predicate reactive.
- This is a multi-session UI fix; the regression mode is intermittent (depends on AppKit z-order). Interactive verification is mandatory. The user should check:
  - With two sessions open (each multi-pane), during a drag in Session A the `pane-swap: drop-zone mounted` log count equals `N − 1` for Session A panes only — no Session B panes appear.
  - Single-session pane swap still works end-to-end (drag handle → drop → layout updates).
  - The new `split-tree: swapPanes no-op` logs do **not** fire on legitimate single-session swaps. They should fire only when something unexpected wires up — e.g. if a regression re-introduces the cross-session-drop path, the `missing=B` line will surface it immediately.
- Built incidentally rewrote `Batty (Beta).xcscheme` (BuildableName flip); reverted before commit. Did not touch `project.pbxproj`.
