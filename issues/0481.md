## Description

The Project Editor (#0474) asks Save / Discard / Cancel when the user closes its window or switches Projects with unsaved edits, but **quitting the app throws the edits away without asking**. That happens on ⌘Q, and also when the last content window closes while the editor is still open, because Batty quits automatically once no content window is left. Two ⌘W edge cases in the editor's Close-item handling are also wrong: with a sheet over the editor (the Root folder `NSOpenPanel`, or an alert), ⌘W targets the sheet rather than the editor, and with no content window open ⌘W cannot close the editor through the menu at all.

Found while reviewing #0474 just before it merged. Everything here is behind the Projects flag (#0470), because the editor exists only with the flag on.

## Steps to reproduce

Batty Beta, with the Projects flag on:

1. File ▸ Edit Projects…, select a Project, and change its name. Do not save.
2. Press ⌘Q. Batty quits. On relaunch the name change is gone, and no prompt was shown. (With "Confirm before quitting" on and terminals open, the only prompt is the existing "Quit Batty?" alert, which says nothing about the editor.)
3. Relaunch and repeat step 1. Then close every Session in the content window, or close the content window itself, so that the editor is the only window left. Batty quits on the next run-loop turn and the edit is lost.
4. With the editor key, click **Choose…** next to Root folder so the open panel is up, then press ⌘W. The editor window is not the window that gets closed.
5. With the editor key and no content window open, open the Tab menu: **Close Tab** is disabled, so ⌘W does nothing, though the window's close button still works. Today the automatic quit in step 3 makes this state short-lived. It becomes an ordinary state once the app stays alive while the editor is open (option (a) below).

## Expected behavior

- **⌘Q with a dirty editor** asks the same Save / Discard / Cancel question that closing the window asks, before anything quits:
  - **Save** saves and lets the quit continue. If the save fails, for example on an empty or duplicate name, the quit is cancelled and the editor shows its save error.
  - **Discard** lets the quit continue.
  - **Cancel** cancels the quit and leaves the editor as it was.
  - Use `applicationShouldTerminate` returning `.terminateLater` and calling `NSApp.reply(toApplicationShouldTerminate:)` when the user answers, or an equivalent, so the question can be the editor's own sheet or dialog and not a nested `runModal`. Bring the editor window front first so the question is visible.
  - Decide and record how this composes with the existing `QuitConfirmation` "Quit Batty?" alert. The suggested order is the editor question first, then the existing alert only if the quit is still going. The user must never see a prompt for the editor after they already confirmed "Quit".
  - A clean editor, or no editor, changes nothing: quitting behaves exactly as it does today.
- **The automatic quit when the last content window closes** does not silently discard edits. Pick one and record it in the resolution:
  - (a) Keep the app running while the editor is open. Quit only when the editor closes too, which already asks about unsaved edits.
  - (b) Go through the same question as ⌘Q.

  Note that `terminateHandler` defaults to `NSApp.terminate(nil)`, which goes through `applicationShouldTerminate`, so the ⌘Q fix may already cover (b). Whichever is chosen, the result must be deliberate and tested, not a side effect. Under (a), also decide whether a *clean* editor keeps the app running.
- **⌘W with a sheet over the editor** closes or asks about the editor window, not the sheet. Use the editor window that `AppStateStore.isProjectEditorWindow` already finds by walking `sheetParent`. If a modal sheet blocks closing, ⌘W does nothing rather than acting on the sheet. Record which of these happens.
- **⌘W with no content window** still closes the editor (asking first if it is dirty). The Close item's enablement must not depend only on a content window having a selected Session while the editor is key. Keep the #0474 reasoning about stale enablement in mind: enablement that reads key-window state can go stale when nothing observed changes. Choose a form that stays correct, and say why in the resolution.
- **Flag off:** nothing changes. `applicationShouldTerminate` and the automatic quit behave exactly as they did before #0474, and nothing constructs `ProjectEditorWindowController.shared`'s window or model, or any `ProjectStore`. Add the new gate site, if there is one, to the `docs/feature-flags.md` site list.
- **UI-test mode:** `QuitConfirmation.isInUITestMode` bypasses the quit alert so XCUITest's teardown `terminate()` doesn't hang. A dirty editor at teardown must not hang the run either. Decide whether UI-test mode bypasses the editor question too, and make the #0478-style test below able to see the prompt anyway, for example through a narrower override.

## Acceptance criteria

- **Unit tests** (`./build.sh unit`, no waiting on time; see `AGENTS.md` "Asynchronous tests"). Drive them through the view model and injectable seams, not a real `NSApp.terminate`:
  - a quit request against a dirty `ProjectEditorViewModel` produces a pending question;
  - each of Save, Save-that-fails, Discard and Cancel produces the right terminate reply, delivered through an injected reply hook;
  - a clean editor and no editor reply "terminate now" without asking;

  - with the flag off, the quit path never touches the editor controller;
  - the ⌘W resolution picks the editor window when the key window is a sheet over it (`isProjectEditorWindow`'s `sheetParent` walk), and ⌘W is enabled with no content window while the editor is key.
- **VM UI check** in #0478's style (Tart VM only, `tools/run-ui-tests-vm.sh`, never on the host). Make an edit in the editor, then:
  - press ⌘Q and assert the Save / Discard / Cancel prompt appears; choose Cancel and assert the app and the edit survive;
  - with no content window open, press ⌘W and assert the editor closes (or prompts).

  Waits use `waitForExistence` and expectations as failure guards only, with no `sleep`. If a step can't be made reliable in XCUITest, record it as a manual check with the user instead of adding a flaky test. Name the run's `build/ui-tests/<run-id>/` directory in the resolution. Put any new accessibility identifiers in `docs/ui-features.md`.
- `./build.sh` and `./build.sh unit` pass.

## Notes

All locations below are on the `issue/0474` branch as reviewed.

- **The editor's existing unsaved-changes flow.** `ProjectEditorWindowController.windowShouldClose` (`BattyKit/Sources/BattyKit/Views/ProjectEditorWindowController.swift:101-105`) returns false and calls `model.requestNavigation(.closeWindow)` when the model is dirty.
  - `ProjectEditorViewModel.requestNavigation` (`BattyKit/Sources/BattyKit/Model/ProjectEditorViewModel.swift:332`) parks the navigation in `pendingNavigation`. `resolveUnsaved(_:)` (`:345`) performs, saves-then-performs, or drops it, and a failed save drops it.
  - The view shows the question as a `.confirmationDialog` bound to `pendingNavigation` (`BattyKit/Sources/BattyKit/Views/ProjectEditorView.swift:79-88`).
  - A quit can reuse this by adding a navigation case (for example `.terminate`) whose perform step replies to the pending terminate request, or with an equivalent completion hook. The Save-fails and Cancel paths must then reply "cancel".
- **The quit path.**
  - `BattyAppDelegate.applicationShouldTerminate` (`Batty/BattyApp.swift:113-125`) consults only `QuitConfirmation.shouldQuitOrPrompt` (`BattyKit/Sources/BattyKit/Views/QuitConfirmation.swift:19`). That returns true immediately in UI-test mode, when confirm-quit is off, or when no terminal Tabs are open, and otherwise runs a modal "Quit Batty?" alert.
  - Nothing consults the editor.
- **The automatic quit.**
  - `AppStateStore.terminateIfLastContentWindowGone()` (`BattyKit/Sources/BattyKit/Runtime/AppStateStore.swift:359`) runs from `removeWindow` (`:276`, call at `:287`) and `unregisterNSWindow` (`:858`, call at `:864`). It checks only `nsWindowMap`, which holds content windows. The editor is deliberately never registered there (controller doc comment, `ProjectEditorWindowController.swift:17-20`).
  - It quits through `terminateHandler` (`:146`, default `NSApp.terminate(nil)`) one run-loop turn later. The open editor doesn't count as a window that keeps the app alive.
- **The ⌘W handling.** The Tab menu's Close item (`BattyKit/Sources/BattyKit/Commands/BattyCommands.swift:516-533`):
  - calls `NSApp.keyWindow?.performClose(nil)` when `store.projectEditorIsKey`. `projectEditorIsKey` (`AppStateStore.swift:983`) walks `sheetParent` through `isProjectEditorWindow` (`:976`), but `performClose` is then sent to the raw key window, which is the sheet. Resolve the editor window after the walk, either by having `isProjectEditorWindow` return the window or through `ProjectEditorWindowController.shared.window`, guarded so the flag-off path never constructs the controller.
  - is `.disabled(keyWindow?.selectedSession == nil)`. `keyWindow` is `store.keyWindowOrFirstRegistered()`, a content window, so with no content window the item is disabled even while the editor is key.
- **Related.** #0480 covers other menu shortcuts acting on the hidden content window while Settings or Help is key. That is a separate gap: #0474 already routes menu actions away from the content window while the editor is key (`menuTargetWindow`). Don't fold it in here.
- **Observation rules** (`docs/swiftui-observation-rules.md`). The quit question is raised from an event (the terminate request or the window-close path), never from `body` or `onChange`. Don't hop the reply into a `Task` to dodge an update-cycle warning. Restructure which code owns the write instead.

## Resolution notes

> 🟢 Resolved 2026-10-12
>
> - **⌘Q:** with unsaved Project Editor edits, ⌘Q now asks Save / Discard / Cancel first. The "Quit Batty?" alert follows only if the quit is still going ahead.
> - **Last content window:** closing it while the editor holds unsaved edits keeps Batty running. Batty quits once the editor closes, and closing the editor asks about the edits.
> - **⌘W:** it closes the editor, after asking, even with no content window open. With a sheet over the editor, it does nothing.

Owed to the user:
- **Manual check in Batty Beta:** turn "Confirm before quitting" on and leave terminals open. Make the editor dirty, press ⌘Q and choose Discard. The "Quit Batty?" alert should appear and both its buttons should work. Then repeat with Save.
- **Manual check:** press ⌘W while the editor's Root folder chooser is open (see Gotchas).

## Root cause

- `BattyAppDelegate.applicationShouldTerminate` consulted only `QuitConfirmation`, so nothing asked the editor.
- `terminateIfLastContentWindowGone` counted only content windows, so the open editor never held the automatic quit.
- The Close item sent `performClose` to the raw key window, which is the sheet when one is over the editor.
- The Close item was disabled whenever no content window had a selected Session, which includes the case where there is no content window at all.

## Fix

**Decisions**

- **Automatic quit: option (a), only when the editor has unsaved edits.**
  - `terminateIfLastContentWindowGone` holds the quit and sets `quitWhenEditorCloses`. It checks before scheduling and again in the deferred block.
  - `ProjectEditorWindowController.windowWillClose` → `AppStateStore.projectEditorDidClose()` re-runs the check against live window state, so a content window that has reappeared stops the quit.
  - A clean editor doesn't hold the quit; behaviour is unchanged.
  - Option (b) was rejected because Cancel would leave a running app with no window.
- **Order of questions:**
  - The editor's question comes first, as its own `confirmationDialog` through a new `ProjectEditorNavigation.terminate`. Then the existing alert.
  - `applicationShouldTerminate` → `store.handleTerminateRequest(reply:)` returns `.terminateLater` and replies through an injected hook (`NSApp.reply(toApplicationShouldTerminate:)`).
  - Discard replies "go" without touching the draft, so if the alert is then cancelled, the edits are still there.
  - Each of these replies "cancel", exactly once: a failed Save, Cancel, the window closing, a replacing navigation, or a second ⌘Q. A second ⌘Q also dismisses the question.
  - If a sheet is already on the editor, the quit is cancelled immediately rather than left hanging in `.terminateLater`.
- **UI-test mode:**
  - The editor question is skipped so XCUITest teardown can't hang.
  - `BATTY_UI_TEST_PROMPT_EDITOR_ON_QUIT=1` turns it back on, and is honoured only in UI-test mode (`QuitConfirmation.promptsEditorOnQuit(environment:)`).
- **⌘W behind a sheet:** `closeProjectEditor(from:)` walks `sheetParent` to the editor. While a sheet is up it does nothing, and it never closes the sheet. The editor check runs before #0480's auxiliary-window branch.
- **⌘W with no content window:** `closeItemIsEnabled` is true when there is no content window. Otherwise it requires a selected Session.
  - It makes the same `keyWindowOrFirstRegistered()` read the item made before, so it adds no new key-window dependency. The no-window branch reads nothing observed.
  - A stale value is harmless. A stale true dates from a moment when a content window with a selected Session existed. A stale false needs a content window with no selected Session, which is transient.
- **Flag off:**
  - `openProjectEditorModel()` returns nil before `ProjectEditorWindowController.shared` is read, so the quit path behaves as before #0474.
  - The new gate site is listed in `docs/feature-flags.md`.

## Gotchas

- **Incorrect premise in this issue:** the Root folder chooser is not a sheet. `ProjectEditorPanels.chooseDirectory` uses `NSOpenPanel.runModal()`, so the panel has no `sheetParent`. If ⌘W reaches the menu while it is key, the auxiliary branch sends `performClose` to the panel; it never closes the editor or a Tab. Whether the menu item fires at all during a modal session is unverified.
- **Closing the content window in UI tests:**
  - `batty session close` refuses to close the last Session.
  - Clicking a background window is unreliable in the VM.
  - The test therefore selects "Session 1" from the Window menu and presses ⌘W. That breaks if the launch Session's name changes.
- **Follow-up candidate:** #0480's auxiliary branch sends `performClose` to the raw key window. With a sheet over Settings or Help, ⌘W targets the sheet instead.
