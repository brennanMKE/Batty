## Description

`AGENTS.md` now has a binding section, "Asynchronous tests" (added in `ba5171d5` on the user's instruction). It says no unit test may pass by waiting. That rules out `Task.sleep`, `Thread.sleep`, `usleep`, `asyncAfter`, poll-until-deadline loops, and assertions on elapsed wall-clock time. A test asserts only after the code under test signals completion. If the code has no completion signal, add one: a returned `Task`, a callback, an event stream, or an injected clock or scheduler. `BattyKit/Tests/` has about 84 sites that break this rule, spread across 14 files. This umbrella issue lists them all, says what event-based replacement each one needs, and proposes child issues by area so the work can run in parallel worktrees.

These waits are how #0423 happened. A fixed window or deadline is tuned against one machine's load. Under `./build.sh unit` running in parallel from several worktrees, the `@MainActor` executor falls behind. Then a sleep ends before the work finishes, and the test fails for no code reason. Or a "nothing happened" window closes before a leaked task would have fired, and the test passes for no code reason. #0424 swapped one fixed sleep for a readiness file. That file is still found by a `Thread.sleep` poll. #0426 dealt with the other cross-run hazard, shared `UserDefaults`.

The companion rule applies too: every await still needs an upper bound, so a regression fails instead of hanging. That bound is a failure guard. The test must not rely on it to work.

### Audit item: turn-bounded `awaitTerminalStatePublish`

`TerminalStatePublishing.swift:44-63` waits up to 20 main-queue turns (`DispatchQueue.main.async` hops) for `TerminalViewState`'s deferred publish. It has 74 call sites in 13 files. ## UI tests (listed separately; not in scope for the BattyKit children)

`BattyUITests/` has no raw `Thread.sleep`/`sleep(`/`usleep`. It routes waits through `BattyUITestHarness` (`Support/BattyUITestHarness.swift`):

- `waitFor(_:timeout:)` (`:55-70`): a predicate poll spinning `RunLoop.current.run(until: +50ms)` to a deadline. There are 98 call sites. The doc comment explains why `XCTNSPredicateExpectation` was rejected (~1Hz fixed cadence). Plus 133 `waitForExistence` calls.
- `pause(_ seconds:)` (`:76-78`): an unconditional fixed wait. It's called at `PaneSidebarTests.swift:72` (0.5s), `:130` (1s), `:149` (0.5s) and `SessionCwdRenameTests.swift:77` (0.5s).

UI tests are XCTest and may use expectations. The only prescription here is to replace the four fixed `pause` calls with element or predicate expectations (`waitForExistence`, `waitFor`) on the state each one is really waiting for. Then delete `pause`. Whether the `waitFor` poll itself should change is left to whoever works that change. UI tests run only in the Tart VM (`AGENTS.md` "UI test automation").

## Production seams needed

Each of these is a test-only seam, and none may change production behaviour. The default must be the production clock or scheduler, set explicitly at the production construction site. It must not be a test default that silently applies in the app (the #0359 lesson).

- **Injected clock/scheduler** for `LMStudioDashboardPaneContent` (models poll, `lms ps` poll, respawn delay, stale-in-flight window), `GitStatusPaneContent` (debounce and any deferred work), and `ProcessStatusPaneContent` (sampling cadence, and the `now` fed to `ProcessCPUDeltaTracker`). Use one shared protocol so the three children don't invent three, and file it first in whichever child lands first.
- **Completion events**: LM Studio parsed-line/poll-applied/stream-termination-handled, Git Status scan-handled, and stream-process-launched where launch isn't already synchronous with the factory call.
- **Test-controlled reap gate** in the teardown paths (`LMStudioDashboardPaneContent`, `ProcessGitStatusScanner`), so "returns without blocking" is proved structurally.
- **Exposed summarization task** from `AppStateStore.scheduleSummarization`.
- **A readiness helper** for child processes (`readabilityHandler` + continuation, or a FIFO where stdout is taken), shared by the scanner, reap-registry and LM Studio fixtures.

## Notes

- Follows #0423 (the flakes these waits cause), #0424 (a fixed sleep swapped for a still-polled readiness file), and #0426 (the other cross-run test hazard, shared `UserDefaults`). The rule is `AGENTS.md` "Asynchronous tests (binding)", added in `ba5171d5`.
- Not counted as violations: `Date()` passed as an explicit timestamp to pure code (`ProcessCPUDeltaTrackerTests`, `BellFeedStoreTests`, `TabRuntimeBellTests`, `PaneHideTests`), `Process.waitUntilExit()` on children that exit by themselves, and `exec sleep 60` in child command lines (that's the child's lifetime, not a test wait).
