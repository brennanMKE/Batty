# 0062 — Menu keyboard shortcuts (Cmd-W, etc.) don't fire when the terminal has focus

| | |
|---|---|
| **Status** | resolved |
| **Module** | App / TerminalSurface |
| **Platform** | macOS |
| **First seen** | 2026-05-11 |
| **Closed** | 2026-05-11 |
| **Commit** | 3d283c4 |

## Description

User reports that menu-bound keyboard shortcuts — `Cmd-W` to close the focused tab in particular — don't fire while a terminal pane has first responder. The menu items are visible in the menu bar, but pressing the shortcut does nothing visible (the tab does not close, no console error).

Hypothesis: `BattyCommands` reads its `AppStateStore` via `@FocusedValue(\.appStateStore)`. That focused value is published by `RootWindowView` via `.focusedSceneValue(\.appStateStore, store)`. SwiftUI's focused-value system propagates UP from a focused SwiftUI view to the scene. When the terminal surface (an `NSViewRepresentable` wrapping libghostty's `AppTerminalView` NSView) holds AppKit first responder, **SwiftUI's focus state is not bridged** — no SwiftUI view is considered focused — and `@FocusedValue` resolves to `nil`. Each menu item is `.disabled(store?.selectedSession == nil)`, so a `nil` store disables every command, and `Cmd-W` falls through to the terminal surface (which doesn't bind it to anything visible).

This explains why `#0051` could earlier observe `Cmd-D` *firing on the wrong pane* (so it must have been firing) and yet, in this session, the user reports nothing works. The earlier repro was likely when the sidebar (a normal SwiftUI list) was focused — SwiftUI focus is intact, the focused value propagates, the menu is enabled. Once the user types into a pane, focus drops into the NSView and the menu disables itself silently.

## Steps to reproduce

1. Open Batty. Click in the terminal pane to give it focus.
2. Open the Tab menu — note the "Close Tab" menu item appears **disabled** (greyed out).
3. Hit `Cmd-W`. Nothing happens (or the keystroke goes to the shell).
4. Click in the sidebar (anywhere that takes SwiftUI focus). Open the Tab menu — "Close Tab" is now **enabled**.
5. `Cmd-W` from the sidebar context fires the action.

Other menu shortcuts (`Cmd-T`, `Cmd-D`, `Cmd-Option-N`, `Cmd-Shift-N`, `Cmd-Option-Arrow`) likely behave the same way.

## Expected behavior

Menu shortcuts work *regardless of which view holds first responder*, matching every other macOS app. The terminal surface is where the user spends almost all of their time, so requiring sidebar focus to use `Cmd-W` is a non-starter.

## Implementation guidance

Cleanest fix: stop relying on `@FocusedValue` for the store. The store is a process-wide singleton via `WorkspaceManager.shared.store`. `BattyCommands` can resolve the store directly from the singleton:

```swift
public struct BattyCommands: Commands {
    private var store: AppStateStore { WorkspaceManager.shared.store }
    ...
}
```

Drop the `@FocusedValue` property; drop the `.focusedSceneValue` modifier on `RootWindowView` if nothing else relies on it. The `@Environment(\.appStateStore)` chain that `PaneView` and other views use is unaffected — that one works fine because it's a view-tree environment, not a focus-driven one.

A subtler alternative: keep `@FocusedValue` and add an explicit SwiftUI focus bridge on the terminal surface via `.focusable()` + `@FocusState`. That's a larger refactor and pulls focus state into Batty's model. Avoid unless we have a real reason to need per-window stores later.

## Acceptance criteria

- With keyboard focus inside a terminal pane, all menu commands that should be available (Close Tab, New Tab, Split Horizontally / Vertically, Focus Pane Arrow, New Session, Toggle Bell Feed) are enabled in the menu bar.
- Pressing each shortcut from terminal focus fires the action.
- `Cmd-W` specifically closes the focused tab (and cascades to remove pane / session as today's `closeTab(id:)` already handles).
- No regression in commands invoked from sidebar focus.
- A test or manual checklist exercises each shortcut from terminal focus.

## Notes

- This is a long-standing latent bug. It became visible only after `#0050`/`#0052`'s tab/focus work landed and the user started actively using non-sidebar shortcuts.
- The Settings window uses `@Environment(\.appStateStore)` (view-tree env), so it is unaffected.
- After the fix, `RootWindowView` no longer needs `.focusedSceneValue(\.appStateStore, store)` — can drop it.
- Related: `#0063` (Cmd-N not bound to anything; separate but discovered in the same session). `#0054` (Cmd-W with busy confirmation — depends on this; you can't add confirmation to a shortcut that doesn't fire).

## Out of scope

- Multi-window support with per-window stores. The singleton fix forecloses that; if we ever want multiple windows we redesign.
- Per-shortcut bypass when terminal has focus (e.g., letting `Cmd-A` go to the shell). Today's pasteboard shortcuts already replace defaults; libghostty's `performKeyEquivalent` handles the fall-through correctly when the menu doesn't intercept.

## Root cause

`BattyCommands` resolved its `AppStateStore` via `@FocusedValue(\.appStateStore)`, populated by `RootWindowView` through `.focusedSceneValue(\.appStateStore, store)`. SwiftUI's focused-value system only propagates from a focused **SwiftUI** view up to the scene. When the libghostty NSView (an `NSViewRepresentable` wrapping `AppTerminalView`) holds AppKit first responder, no SwiftUI view is considered focused, the focused value resolves to `nil`, every menu item gates itself behind `store?.selectedSession == nil`, and shortcuts like `Cmd-W` silently fall through to the terminal. The bug was invisible whenever the sidebar (a normal SwiftUI list) had focus — which masked it until users started reaching for menu shortcuts mid-terminal-session.

## Fix

Stop relying on `@FocusedValue` for the store. `BattyCommands` now resolves the store from the process-wide singleton:

```swift
private var store: AppStateStore { WorkspaceManager.shared.store }
```

The property type changed from `AppStateStore?` to `AppStateStore`, so every `store?.foo` callsite drops the optional chain and every `.disabled(store?.foo == nil)` becomes `.disabled(store.foo == nil)`. `RootWindowView` no longer needs `.focusedSceneValue(\.appStateStore, store)` and `FocusedValues.swift` no longer needs the `FocusedAppStateStoreKey`. The view-tree `\.appStateStore` environment key remains — `PaneView`, `SettingsView`, and `BattyApp` use it via `@Environment`, which is unaffected by AppKit focus.

## Files changed

- `BattyKit/Sources/BattyKit/BattyCommands.swift` — dropped `@FocusedValue(\.appStateStore)`, added singleton-backed computed `store`, removed optional chaining and the `.disabled(store == nil)` guards that are no longer meaningful.
- `BattyKit/Sources/BattyKit/RootWindowView.swift` — removed `.focusedSceneValue(\.appStateStore, store)`. `.environment(\.appStateStore, store)` stays.
- `BattyKit/Sources/BattyKit/FocusedValues.swift` — removed the `FocusedAppStateStoreKey` and its `FocusedValues.appStateStore` accessor; kept the `EnvironmentValues.appStateStore` env key.

## Gotchas

- No automated test covers SwiftUI Command focus behavior — the acceptance criteria are a manual checklist. From a terminal pane with focus: each of `Cmd-W`, `Cmd-T`, `Cmd-D`, `Cmd-Shift-D`, `Cmd-Option-Arrow`, `Cmd-Option-N`, `Cmd-Shift-N`, `Cmd-Option-1..9`, `Cmd-1..9` should fire its menu action and the menu items should appear enabled in the menu bar.
- This forecloses multi-window support with per-window stores. If we ever add multiple windows, the singleton approach needs to be revisited — likely via an `NSApp.keyWindow`-aware lookup or a different focus bridge.
- libghostty's `performKeyEquivalent` still gets first crack at most key events; the menu only intercepts keystrokes that match a registered shortcut. So shell shortcuts like `Cmd-A` (currently bound to Select All) and `Cmd-V` (Paste) continue to behave as they did pre-fix — this issue only changes the *menu-item enabled state*, not the responder-chain routing.
