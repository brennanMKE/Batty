# 0349 — Non-terminal Pane content in a non-selected Session never suspends

| | |
|---|---|
| **Status** | open |
| **Module** | Pane / Session |
| **Platform** | macOS |
| **First seen** | 2026-08-21 |

## Description

`PaneContentLifecycle.setVisible(false)` is only ever called from `WindowRuntime.hidePane(id:)` (with the symmetric `setVisible(true)` in `showPane(id:)`). Switching to a different Session unmounts the Pane's SwiftUI view silently — `SessionDetailView`'s `isSelectedSession` environment write is a pure SwiftUI environment value, not a call into `WindowRuntime` or `AppStateStore` — so the content object is never told it stopped being visible. `docs/pane-view-lifecycle.md` §5 explicitly flags this as an open wiring question ("the non-selected-Session fact … has no equivalent model-level function today … remains an open wiring question this document flags rather than answers").

The gap affects all four non-terminal view kinds, but the cost is wildly uneven. A system-metrics sampler ticking in a background Session is cheap. An LM Studio dashboard in a non-selected Session keeps **two `lms log stream` subprocesses, a 1 Hz HTTP poll of `/api/v1/models`, and a 3 s `lms ps --json` fork** running indefinitely — and `lms ps` costs ~130–160 ms per fork by the design's own measurement on this machine. This is the highest-value lifecycle follow-up in the batch.

## Expected behavior

Deselecting a Session delivers `setVisible(false)` to every non-terminal Pane content in it (and re-selecting delivers `setVisible(true)`), through a model-level call site — not `View.onDisappear`, which is not guaranteed to fire on every unmount path. Background-Session dashboards suspend their subprocesses and polls the same way hidden Panes already do.

## Actual behavior

Only `hidePane` suspends content. A Session switch leaves every non-terminal content object in its `.active` state forever; the LM Studio dashboard's subprocesses, HTTP poll, and periodic forks keep running with no visible Pane anywhere.

## Notes

Verified code locations (on branches pending merge at filing time; paths are stable):

- `setVisible(false)` call sites: `WindowRuntime.hidePane(id:)` only (`BattyKit/Sources/BattyKit/Runtime/WindowRuntime.swift`, `pane.nonTerminalContent?.setVisible(false)` in the non-terminal branch; `showPane` mirrors it). Verified on `issue/0313-2` and `issue/0314-2` — no other production caller exists.
- The non-selected-Session fact: `SessionDetailView` `.environment(\.isSelectedSession, …)`; read in `PaneView`. No model-level hook fires on selection change.
- `docs/pane-view-lifecycle.md` §5 (on `main`) — the "open wiring question" language; also flags the hide/show asymmetry (hide is an explicit direct call, un-hide is remount-driven) that the fix should keep in mind.

The fix likely wants a model-level selection choke point (e.g. wherever `selectedSessionID` changes on `WindowRuntime`) that sweeps the outgoing Session's panes with `setVisible(false)` and the incoming one's with `setVisible(true)`. `setVisible` is idempotent by contract, so overlapping with the remount-driven path is safe.
