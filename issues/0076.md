## Description

Start a `docs/` folder at the repo root and seed it with a comprehensive view-hierarchy guide. This is foundational documentation — when a new contributor (or a future subagent) needs to understand how Batty's UI fits together, this should be the first thing they read after `CLAUDE.md`, `PRD.md`, and `Concepts.md`.

The view hierarchy is non-trivial because Batty has both a **model hierarchy** (Workspace → Window → Session → Pane → Tab → Terminal) and an **AppKit/SwiftUI hybrid layer** that pulls the live terminal NSViews out of SwiftUI's rebuild churn into a single persistent host (per `#0075`). Anyone touching the terminal/pane/window paths needs to understand both.

## What `docs/view-hierarchy.md` must cover

### 1. The model hierarchy (already mostly in `Concepts.md`, but recap)

- **Workspace** — top-level persistence object (write-only per `#0055`).
- **Window** — single instance per `#0063`. Currently exactly one `NSWindow`.
- **Session** — sidebar entry. Has a `SplitTree` of panes and a selected pane.
- **Pane** — leaf of the split tree. Has a list of `TabRuntime`s and an `activeTabID`.
- **Tab (`TabRuntime`)** — owns one `TerminalViewState` (libghostty's model) and a long-lived `AppTerminalView` (the NSView).
- **Terminal session** = the running PTY + libghostty surface. Lifetime bound to the `TabRuntime`, not to any view.

Diagram this as ASCII or a Mermaid graph. Show that one Window can hold many Sessions, each Session has a tree of Panes, each Pane has a stack of Tabs, each Tab has one Terminal.

### 2. The SwiftUI view tree

- `BattyApp` (Scene) → `Window` (singular, not `WindowGroup`, per `#0063`).
- `ContentView` → `RootWindowView` → `NavigationSplitView`.
- Sidebar column: `SessionSidebarView` (List of sessions, `+` button as `.safeAreaInset` per `#0065`).
- Detail column: `SessionDetailView` — outer ZStack:
  - `TerminalHostInstaller` (NSViewRepresentable hosting the persistent `TerminalHostView` from `TerminalHostStore.shared`).
  - SwiftUI chrome: `SplitContainerView` per session, with `.opacity` toggles for selected/non-selected sessions.
- `SplitContainerView` → recursive `SplitNodeView` → leaves are `PaneView`.
- `PaneView` → `VStack` of `SlidingTabBar` (chips) + a ZStack containing per-tab content.
  - Each tab's content: a `TerminalPlaceholderView` (transparent, reports geometry via PreferenceKey).
  - `.opacity` + `.allowsHitTesting` toggles for the active tab.
- `TerminalPlaceholderView` never hosts the AppTerminalView — it only reports where the host should position the terminal.

Show this as a tree/indented list. Cross-link to file paths under `BattyKit/Sources/BattyKit/`.

### 3. The terminal host architecture (the load-bearing section)

This is the part that justifies the doc's existence. After `#0072` → `#0074` → `#0075` Phase 2, the architecture is:

- `TerminalHostStore.shared` (singleton) owns one `TerminalHostView` NSView for the app's lifetime.
- The host is added to the SwiftUI tree via `TerminalHostInstaller` (`NSViewRepresentable` whose `makeNSView` returns the SAME singleton instance every call).
- Each `TabRuntime.terminalNSView` is an `AppTerminalView` added to the host **once** and **never reparented**.
- SwiftUI's per-pane `TerminalPlaceholderView` reports its frame in a named coordinate space via `TerminalPlacementPreferenceKey`.
- `TerminalHostStore.updatePlacements(...)` translates those frames into `frame` updates and `isHidden` toggles on the matching subviews of the host.

Explain why this design exists: SwiftUI tears down `NSViewRepresentable` hosts on rebuild. Pre-`#0075`, that destroyed the underlying PTY. The persistent-host design keeps the NSView at the singleton's lifetime, never letting SwiftUI's churn touch it.

Cross-reference `docs/nsviewrepresentable-state-persistence.md` (after the move) and CLAUDE.md's surface-registry rule.

### 4. Rules of the road for anyone touching the terminal path

Quote and restate the strict rules from the persistence guide:

- Never call `removeFromSuperview()` on an `AppTerminalView` outside the tab-close path.
- Never replace the `subviews` array of the host.
- Never recreate a tab's `AppTerminalView` while the `TabRuntime` is alive.
- `updateNSView` is a no-op or only mutates properties — never adds/removes subviews.
- The placeholder is empty by design — don't put SwiftUI content inside it expecting to overlay the terminal.

### 5. Lifecycle of a terminal NSView

A timeline diagram:

1. `TabRuntime.init` creates the `TerminalViewState`. `terminalNSView` is nil.
2. First time the placeholder appears, `TerminalHostStore.terminalView(for:)` lazily creates the `AppTerminalView` and adds it to the host.
3. `viewDidMoveToWindow(host's window)` fires inside libghostty — display link starts, PTY spawns.
4. Subsequent navigation: only `frame` and `isHidden` change. The NSView never leaves the host. `viewDidMoveToWindow` does NOT fire again.
5. On `closeTab(id:)`, `TerminalHostStore.releaseTerminalView(forTabID:)` removes the NSView from the host. `viewDidMoveToWindow(nil)` fires; libghostty tears down the surface, PTY closes.

### 6. Common debugging signals

- `created terminal view for tab …` (TerminalHostStore log) — should fire exactly once per tab.
- `released terminal view for tab …` — exactly once per closed tab.
- `attached host to window` — should fire once at app launch. If it fires more than once, the singleton isn't being preserved.
- `focus skipped: no AppTerminalView matched the requested terminal state` — a brief one at cold launch is expected; persistent ones during navigation indicate the host attach is broken.
- libghostty's `io_exec: started subcommand` — should only fire on tab create. If it fires during navigation, the persistence is broken.

## Root cause

Not a bug — a foundational documentation gap. The view-hierarchy
architecture established by `#0072` -> `#0074` -> `#0075` (Pattern 3
persistent terminal host, geometry probe via PreferenceKey, single
mutator `TerminalHostStore.updatePlacements(_:)`) was distributed across
file-header doc comments, `nsviewrepresentable-state-persistence.md`,
and tribal knowledge in the issues themselves. A new contributor (or a
fresh subagent) had no single entry point for "how do these pieces fit
together?".
