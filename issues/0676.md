# 0676 — Something in full unit runs kills ProcessFollowByNameTests' freshly spawned children; no test may signal a process it didn't start

| | |
|---|---|
| **Status** | open |
| **Module** | Testing / Pane |
| **Platform** | macOS |
| **First seen** | 2026-11-18 |
| **Target** | 1.5.0 |
| **Priority** | high |

## Description

In full `./build.sh unit` runs, the child each `ProcessFollowByNameTests` real-enumerator test spawns is already dead right after `Process.run()` returns. `kill(pid, 0)` gives `ESRCH` and `isRunning` is false. Run alone, both tests pass. The #0675 implementer found this (see `issue/0675:issues/0675.md`, `## Gotchas`). Swapping the `/bin/cat` child for a copied `/bin/sleep 86400` failed the same way, so the child's own lifetime is not the cause.

The most likely explanation is that something else in the run signals these children. That is a safety bug as well as a flaky test. Unit tests run on the host (`AGENTS.md`), so a test that signals processes it didn't start could just as well hit the user's own processes, including a live Batty and its Terminal Sessions (compare #0409). Find the signaller, or rule it out with evidence, and add a guard so a stray signal fails a test instead of killing something.

## Steps to reproduce

1. Check out `issue/0675` (both tests are `nonisolated async` there, and every expectation carries `walkDiagnostic`).
2. Run `./build.sh unit`.
3. `ProcessFollowByNameTests/aSeededFollowOfTheSecondRealProcessShowsThatProcess()` and `…/theRealEnumeratorFindsAUniquelyNamedProcessAndItsReplacement()` fail at the `#require(…isRunning…)` right after `fixture.run(process)`, and the diagnostic shows `kill0=-1/errno 3` (`ESRCH`).
4. Run `./build.sh unit ProcessFollowByNameTests`: both pass.

On `main`, where the tests are `@MainActor` and use a copied `sleep 300`, the same test failed once in the #0664 review re-run, at an unknown line.

## Expected behavior

- The children live until the test's `ChildProcessFixture` kills them.
- No test, and no BattyKit code a test reaches, sends a signal to anything but a process the test spawned itself. Where a group signal is used, the target is a group the test created (`POSIX_SPAWN_SETPGROUP`), never the test runner's group, group 0 or 1, or a pid or pgid the test did not get from its own spawn.

## Actual behavior

The children have already exited and been reaped when the test first checks them. The termination reason and status were not captured, so whether a signal killed them is still unproven.

## Notes

### Facts established while filing (read-only, 2026-11-18)

- **Foundation `Process` children get their own process group.** A probe that spawned `/bin/cat` through `Process` printed `child pgid == child pid`, which is not the parent's `getpgrp()`. So the follow tests' children are group leaders of their own groups. A signal to the runner's group (`kill(0, …)`, `killpg(getpgrp(), …)`) cannot reach them. It would also have killed the runner, which survives. Only a `kill(childPid, …)` or `killpg(childPid, …)` can reach them, or an out-of-process kill by pid or name.
- **Raw `posix_spawn` children do share the runner's group.** `ServerJobOwnershipTests.systemTableRecordsASpawnedChild` (`ServerJobOwnershipTests.swift:143`) asserts `record?.pgid == getpgrp()`. This doesn't explain the follow-test deaths, but every `posix_spawn` fixture without `POSIX_SPAWN_SETPGROUP` is exposed to any runner-group signal.
- **An audit of BattyKit sources and BattyKitTests found no in-process signaller that targets an arbitrary pid, pgid or name.** Every real `kill`/`killpg`/`terminate()` targets a pid the same test or content spawned. The grep covered `kill(`, `killpg(`, `.terminate()`, `.interrupt()`, `SIGTERM`/`SIGKILL`/`SIGINT`, `pkill`/`killall`, `waitpid(-1`/`wait4`, `setpgid`/`setsid`, and `SystemProcessSignaller`/`ProcessGroupStopper` uses. No test reads a pid from a process-table scan and then signals it. So the plan must verify the "a test signals them" hypothesis, not assume it.

### Suspects, most likely first

1. **`ProcessGroupStopperRealProcessTests`** (`ProcessGroupStopperTests.swift:160`–`254`) is the only test that drives the production `SystemProcessSignaller` (`ProcessGroupStopper.swift:121`–`131`, `killpg(pgid, sig)`) with real signals.
   - The target is `fixture.pid` from its own `POSIX_SPAWN_SETPGROUP` spawn, which is correct.
   - On the failure path of `interruptEndsAGoRunStyleParentAndChild` (`:228`–`232`), `stop.cancel()` runs, then `cleanUp` sends `killpg(fixture.pid, SIGKILL)` (`:218`) and reaps.
   - The stopper `Task` can still be between `check()` and `signaller.signal(...)` (`ProcessGroupStopper.swift:66`–`82`), so it can send `killpg` to a pgid that has already been reaped.
   - `ProcessGroupStopper.refusal` (`:91`–`94`) blocks only pgid ≤ 1, Batty's own group and its ancestors' groups. It does nothing about a stale pgid.
   - macOS allocates pids in sequence, so reuse within milliseconds is unlikely. This is still the one place where a real group signal can outlive its target's reap.
2. **Kill-after-`isRunning` checks:**
   - `ChildProcessFixture.killAndReap` (`ChildProcessFixture.swift:57`–`61`) and `TeardownReaper` (`TeardownReaper.swift:47`–`53`) each send `kill(process.processIdentifier, SIGKILL)` after a `process.isRunning` check.
   - Foundation reaps on its own queue before `isRunning` flips, so the pid can be reaped in between and the `kill` then lands on a stale pid. This path is also shared through `PendingTeardownReapRegistry.shared` (`PendingTeardownReapRegistry.swift:47`).
   - Many tests run in parallel, and `issue/0675` makes `ChildProcessFixture` `nonisolated`, so these kills now run concurrently on pool threads.
   - Low probability for the same pid-reuse reason, but it is a real time-of-check-to-time-of-use (TOCTOU) gap.
3. **Real signaller defaults in `ServerPaneContent`.** `ServerPaneContent.init` defaults to `SystemProcessSignaller()`, `SystemPortListenerScanner()` and `SystemProcessTable()` (`ServerPaneContent.swift:116`–`130`), and so does the production factory `AppStateStore.makeServerContent` (`AppStateStore.swift:204`–`205`).
   - `WebPreviewPaneTests.openInBattyShownOnlyForAllowedListeningURLs` (`WebPreviewPaneTests.swift:361`, `:368`) builds two contents on real port 1 with all three real defaults.
   - The backend is in-process today, so `tearDown` and stop never signal (`ServerPaneContent.swift:206`–`208`). A terminal backend, or a regression in that check, would resolve a real listener and process group on the host and `killpg` it.
   - Every other server test injects `FakeProcessSignaller`. Make this one inject it too.
4. **An out-of-process killer.** Other worktrees' builds and test runs, agents, and Tart and LM Studio tooling all run on the same host and user.
   - The children's full path contains `…/batty-0486-<uuid>/bt0486-xxxxxx`. A `pkill -f batty` style pattern would match them but not the runner, whose path has `Batty`/`BattyKit`.
   - Nothing in this repo does that. `build.sh:306` is `pkill -x "Batty Beta"`, an exact name match, and `tools/run-ui-tests-vm.sh` kills only pids it recorded. Host tooling outside the repo has not been checked.
   - Memory-pressure kills (jetsam) during the memory-signal protocol are a non-test alternative, and should show up in the unified log.
5. **Not a signal at all.** The child may exit on its own at once, for example:
   - an exec or code-signing (AMFI) kill of the freshly copied binary under load;
   - for the `cat` variant, an inherited-fd or stdin problem.
   
   The `sleep 86400` result makes stdin unlikely but doesn't rule out the rest. `ProcessInspectorTests.openFileDescriptorCountGrowsPastItsInitialCapacityWhenNeeded` (`ProcessInspectorTests.swift:349`) opens 1500 fds in the shared test process at the same time. That would make `run()` throw rather than kill a child, but it belongs in the same check.

### What to do first

Capture *why* the child died before changing anything else. Set a `terminationHandler` before `run()` that records `terminationReason` and `terminationStatus`, and add them to `walkDiagnostic`:
- `.uncaughtSignal` with 9 or 15 confirms a signal and names it;
- `.exit` with a status points at suspect 5.

On a signal, also capture the unified log around the failure: `log show --last 5m --predicate 'eventMessage CONTAINS "<pid>"'`, plus any `jetsam`/`AMFI`/`kernel` lines. That can tell an in-process signal from an external or kernel one.

## Acceptance criteria

1. **Identify the signaller**, or rule out a signal with captured evidence (termination reason and status, and the log lines), and record the cause in `## Fix`. If the cause is outside the repo, name it and say which suspect it was.
2. **No test signals anything but processes it spawned:**
   - Every real `kill`/`killpg`/`terminate()` in BattyKitTests, and in BattyKit code that tests reach with real signallers, targets only a pid or pgid the same test got from its own spawn.
   - Group signals go only to groups the test created with `POSIX_SPAWN_SETPGROUP`, never to `getpgrp()`, 0 or 1.
   - No real signal goes after that test has reaped the target. Fix suspect 1's cancel path so it awaits the stopper `Task` before `cleanUp`, or otherwise ensures no signal follows the reap.
   - Close suspect 2's gap. For example, kill only while Foundation hasn't reaped yet, or reap with `waitpid` on a pid the test owns.
   - `WebPreviewPaneTests` injects `FakeProcessSignaller`, a fake scanner and a fake process table.
3. **A guard catches a stray signal.** At least one of these, and preferably both:
   - A canary test. It spawns a long-lived child in its own process group and one in the runner's group, each trapping every catchable signal and reporting it on a pipe. It holds them for the whole run (for example, a suite that starts first and checks last, or a check in a shared fixture's teardown), and fails with the signal name if either child is signalled or dies before the check. An unexpected death shows up as EOF on the pipe.
   - A test-build assertion in one shared signalling seam that `TeardownReaper`, `SystemProcessSignaller` and `ChildProcessFixture` all go through. It records `Issue.record` (or fails a precondition in tests) when the target pid or pgid is not in a registry of pids that tests spawned. It must have no effect in production.
4. Both `ProcessFollowByNameTests` real-enumerator tests pass in 3 consecutive full `./build.sh unit` runs. Their diagnostics include `terminationReason`/`terminationStatus` from now on.
5. Tests follow `AGENTS.md` "Asynchronous tests" and `docs/async-test-seams.md`: no sleeps, and child death is awaited as an event (pipe EOF, termination handler), not by polling.
