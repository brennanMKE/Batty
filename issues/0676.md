## Description

In full `./build.sh unit` runs, the child each `ProcessFollowByNameTests` real-enumerator test spawns is already dead right after `Process.run()` returns. `kill(pid, 0)` gives `ESRCH` and `isRunning` is false. Run alone, both tests pass. The #0675 implementer found this (see `issue/0675:issues/0675.md`, `## Gotchas`). Swapping the `/bin/cat` child for a copied `/bin/sleep 86400` failed the same way, so the child's own lifetime is not the cause.

The most likely explanation is that something else in the run signals these children. That is a safety bug as well as a flaky test. Unit tests run on the host (`AGENTS.md`), so a test that signals processes it didn't start could just as well hit the user's own processes, including a live Batty and its Terminal Sessions (compare #0409). Find the signaller, or rule it out with evidence, and add a guard so a stray signal fails a test instead of killing something.

## Root cause

Confirmed, not a signal from any test. On this branch (on top of `issue/0675`), the step 1 death report in a full run (`build/checks/unit-20261118-213018-68728.log`) showed both follow-test children `died after 38 ms: uncaughtSignal 9 (Killed: 9)`, with `ppid` = the runner and their own pgid, and an in-process `SecStaticCodeCheckValidity` of the copy returning 0. The unified log had no AMFI/jetsam kernel line, but `ReportCrash` wrote `~/Library/Logs/DiagnosticReports/bt0486-356a96-2026-11-18-213131.ips` for the pid: `"exception": {"type": "EXC_CRASH", "signal": "SIGKILL (Code Signature Invalid)"}`, `codeSigningID com.apple.cat`, validation category 1 (platform).

So it is suspect 5: the kernel SIGKILLs a copy of an Apple **platform binary** (`/bin/cat`, and `/bin/sleep` on `main`) run from a path outside the system volume, a few tens of ms after exec. The static signature is intact, so an on-disk check passes. The test only passes when it checks `isRunning` before the kill lands, which it wins when run alone and loses under full-run load. There were 367 `bt0486-*` crash reports from today alone, including `com.apple.sleep` ones from other worktrees running `main`, which explains the one-off #0664 failure there.

## Fix

- **Branch base:** per the orchestrator, `issue/0676` was rebased onto the unmerged `issue/0675`; it carries #0675's commits followed by #0676's. Squash them separately.
- **The cause:** `ProcessFollowByNameTests.uniqueCatCopy` re-signs the copy ad hoc (`/usr/bin/codesign --force --sign -`), making it a non-platform binary that runs from anywhere. After this, no `com.apple.cat` `bt0486` reports appeared in any run.
- **Evidence kept:** `ChildProcessFixture.run` installs a chained `terminationHandler` and records spawn time, ppid/pgid, and termination reason/status; `deathReport(for:)` reports it. `walkDiagnostic` adds the death report, the copy's size and codesign status, the failure time, and a `logger.error` line.
- **Signal seam:** new `ProcessSignal` (hard refusals: pid ≤ 0, group ≤ 1, own group, returning `EINVAL`; `send(_:to: Process)` sends only while running and while `pbi_ppid == getpid()`; nil-in-production `audit` hook). `SystemProcessSignaller`, `TeardownReaper`, `GitStatusPaneContent` and `LMStudioDashboardPaneContent` route through it. `ProcessGroupStopper.stop` checks `Task.isCancelled` right before each signal.
- **Test audit:** `SignalAudit.swift` adds `SpawnedProcessRegistry`, the audit predicate (`SignalAudit.verdict`, pure and injectable), `TestChildSpawner`/`OwnedChild`, `TrapCanary`, the run-wide `SignalCanary` and the `.auditsSignals` trait, applied to the suites the plan lists. Every test `kill`/`killpg`/`terminate()` now goes through the seam. `ProcessGroupStopperRealProcessTests` awaits the cancelled stop task before `cleanUp`. `WebPreviewPaneTests` injects the fake signaller, scanner and table and asserts nothing was sent.
- **Deviations:**
  - `aRefusedSignalIsNeverDelivered` uses `SignalAudit.blockForTesting` rather than swapping the global hook, since the hook is shared by parallel tests.
  - `anotherTestsChildIsRecordedAsAViolation` checks the pure predicate with string test ids, because `Test.ID` cannot be constructed.
  - `aCanaryEndedBySIGKILLReportsItFromItsWaitStatus` asserts the `waitpid` status from `reap()`.
  - `Sources/batty` (CLI target) is excluded from the source scan and not routed (see Gotchas).
  - No scratch worktree was needed: this branch already contains #0675, where the bug reproduced.

## Gotchas

- **The cause was outside any test's code: the kernel's code-signing enforcement.** `SecStaticCodeCheckValidity` returns 0 for the doomed copy, and the unified-log predicate in the plan found no kernel line. The `.ips` crash report (`SIGKILL (Code Signature Invalid)`) was the decisive evidence. Never copy an Apple platform binary to run it (now in `docs/async-test-seams.md` section 7).
- **`main` still has the bug** (copied `/bin/sleep`). It goes away when #0675 and #0676 land, since the re-signing is in the shared `uniqueCatCopy`.
- **A new problem found and fixed during verification.** `TestChildSpawner` first spawned without `POSIX_SPAWN_CLOEXEC_DEFAULT`, so the long-lived canaries inherited other tests' pipe write ends. `ChildLifetimeTests.aHeldChildExitsWhenItsStdinCloses` failed in 2 of 3 runs before the fix. Spawned children now get only the fds they are given, plus stderr.
- `TestChildSpawner` resets signal dispositions and the mask. A non-interactive `sh` cannot trap a signal that was ignored or blocked when it started, which made the first canary attempt miss `SIGUSR1`. The canary blocks in `wait` on a background `cat`, not in a foreground `read`, because a trap only runs after a foreground command returns.
- `Sources/batty` (`AppBundleLocator.swift:88`, `MCPToolRunner.swift:112`) still calls `.terminate()`. That is the CLI target; `ProcessSignal` is internal to BattyKit and no BattyKitTests test reaches those sites.
- For evidence, I grepped the captured full log once for the death-report line; the digest truncated it.
- Remaining surface: `TeardownReaper` still polls with `Task.sleep` in production (pre-existing, out of scope).
- Optional: `sudo eslogger signal` was not needed, because the evidence named the cause.

**`ProcessFollowByNameTests.walkDiagnostic`**

**How to read the evidence.** After any full run where a follow test fails, run within minutes:

- `ls -t ~/Library/Logs/DiagnosticReports /Library/Logs/DiagnosticReports | head`, looking for `JetsamEvent-*` and for `.ips` files named after the `bt0486-*` copy.

Then match the evidence to a cause:

| Evidence | Cause |
|---|---|
| `.exit`, status 0 | The child exited by itself. A `cat` child got EOF on stdin, so some other test closed the write end of its pipe (a double `close` of an fd number it doesn't own). This is a new suspect 6, mainly for the `cat` variant on `issue/0675`. |

### Step 2: one signalling seam, audited in tests (`#0676 Route every signal through ProcessSignal`)

**New `BattyKit/Sources/BattyKit/Runtime/ProcessSignal.swift`** (`nonisolated enum ProcessSignal`, logger per `AGENTS.md`):
- `send(_ sig: Int32, toPid:) -> Int32`, `send(_ sig: Int32, toGroup:) -> Int32` and `send(_ sig: Int32, to process: Process) -> Int32`. Each returns 0 or an errno.
- **Hard refusals, in production too, returning `EINVAL`:** pid ≤ 0, pgid ≤ 1, and pgid `== getpgrp()`. `kill(0/-1, …)` is never meaningful for Batty.
- The `Process` variant closes suspect 2:
  - It sends only if `process.isRunning` **and** `proc_pidinfo` shows `pbi_ppid == getpid()` right before `kill`.
  - Once Foundation has reaped the pid, it is either gone (`ESRCH`) or reused by a process whose parent isn't us. Either way, nothing is sent.
  - The residual case is reuse by another of our own children, which needs a full pid wrap in microseconds. Document it in the doc comment as the one remaining window.
- `kill(pid, 0)` probes are not signals and stay as they are.
- **Test hook:** `static var audit: (@Sendable (Target, Int32) -> Bool)?`, guarded by a lock and reachable only through `@testable import`.
  - It is consulted after the hard refusals and before the real `kill`/`killpg`. Returning `false` means refuse (`EPERM`, nothing sent).
  - It is **nil in production**, so there is no behaviour change there. State this in the doc comment, and verify the claim by grep: nothing in `Sources/` sets it.

**Route these through the seam:**
- `SystemProcessSignaller.signal`: both the `killpg` path and the tree `kill` path.
- `TeardownReaper.reap`: `kill(…SIGKILL)` becomes `ProcessSignal.send(SIGKILL, to: process)`.
- `GitStatusPaneContent.swift:312`/`:320` and `LMStudioDashboardPaneContent.swift:523`/`:716`: `process.terminate()` becomes `ProcessSignal.send(SIGTERM, to: process)`.
- Every test-target site listed above.

**`ProcessGroupStopper.stop`:**
- Add `if Task.isCancelled { return .refused("cancelled") }` immediately before `signaller.signal(target, sig)`, after `check()`.
- **The real fix for suspect 1 is in the test:** `ProcessGroupStopperRealProcessTests.interruptEndsAGoRunStyleParentAndChild` must `stop.cancel()` and then `_ = await stop.value` (bounded with `awaitBoundedValue`) **before** `cleanUp`. That way no stopper signal can follow the test's `waitpid`.
- Apply the same ordering wherever a test cancels a stop `Task` that holds a real signaller.

**New `BattyKit/Tests/BattyKitTests/SignalAudit.swift`** (test target, `nonisolated`, lock-protected):
- **`SpawnedProcessRegistry`.** Each entry is pid → (`Test.current?.id`, spawn instant, own-group flag, reaped flag).
  - Entries are added by `ChildProcessFixture.run` and by the new `TestChildSpawner`.
  - They are marked reaped by `TestChildSpawner.reap` and by the fixture's termination handler.
- **`TestChildSpawner`** replaces the hand-rolled `posix_spawn` code in `ProcessGroupStopperRealProcessTests.spawn`/`cleanUp`, `PlainShellKeyRewriteTests.spawnSleeper`, `ServerJobOwnershipTests:130` and `ProcessInspectorTests:318`.
  - It is a `posix_spawn` helper with an `ownGroup:` flag. `ServerJobOwnershipTests` keeps `ownGroup: false`, because it asserts `pgid == getpgrp()`.
  - It returns an `OwnedChild` with `pid`, `signal(_:)` (refused once reaped, so it never signals after its own `waitpid`), and an async `reap()` that runs `waitpid` off the main actor and returns the raw wait status.
- **`SignalAudit.ensureInstalled()`** is idempotent. It sets `ProcessSignal.audit` to a predicate that permits a target only when:
  - the pid is in the registry and not reaped, or, for a production-spawned child (LM Studio, git scanner), its `pbi_ppid == getpid()`;
  - for a group, the pgid is a registered own-group, un-reaped leader, or a live direct child of ours that leads its own group.

  When `Test.current` is non-nil and differs from the entry's test id, it records a violation too. Every refusal or violation:
  - appends to `SignalAudit.violations` (with `Thread.callStackSymbols`, target, signal and `Test.current`);
  - logs at `.error`;
  - calls `Issue.record` when a current test exists;
  - **refuses the send**, so a stray signal fails a test instead of killing something.
- **Where it is installed:** `ChildProcessFixture.init`, `TestChildSpawner`, and a `TestScoping` suite trait `.auditsSignals`. Apply the trait to every suite that drives a production signal path with a real child: `ProcessGroupStopperRealProcessTests`, `LMStudioDashboardPaneContentTests`, `LMStudioDashboardWiringTests`, `ProcessGitStatusScannerTests`, `PendingTeardownReapRegistryTests`, `ChildProcessReadinessTests` and `ProcessFollowByNameTests`.

**`WebPreviewPaneTests.openInBattyShownOnlyForAllowedListeningURLs`** injects `FakePortScanner`, `FakeProcessSignaller` and `FakeProcessTable` into both contents. After `tearDown`, assert `signaller.sent.isEmpty`.

### Step 3: run-wide canaries (`#0676 Signal canaries`)

**In `SignalAudit.swift`, `SignalCanary.shared`** is a `static let`, started on first `ensureInstalled()`. It holds two `TestChildSpawner` children:
1. a `/bin/sh` in **its own group**, copied to `$TMPDIR/batty-0486-<uuid>/bt0486-canary`. The path matches the follow tests' path, to catch a pattern-based external kill.
2. a plain `/bin/sh` in **the runner's group** (`ownGroup: false`).

Each one:
- runs `for s in HUP INT QUIT ABRT USR1 USR2 ALRM TERM PIPE; do trap "echo $s; exit 0" $s; done; echo ready; while read -r _; do :; done`;
- has its stdin on a pipe the runner holds, so it exits when the runner dies;
- has stdout on a pipe, read as an event: readiness through `ChildProcessReadiness.waitForData`, and a caught signal as its name on the pipe.

A death from an uncatchable signal shows up as EOF. The canary is reaped only by us, so `waitpid` gives the exact `WTERMSIG`.

`SignalCanary.check() -> [String]` is non-blocking: it tries a non-blocking read of each pipe, and `waitpid(WNOHANG)`. It is called from:
- `ChildProcessFixture.killAndReapAll`;
- `OwnedChild.reap`;
- the canary suite.

Any finding is `Issue.record`ed with the signal name.

## Notes

### Facts established while filing (read-only, 2026-11-18)

- **Foundation `Process` children get their own process group.** A probe that spawned `/bin/cat` through `Process` printed `child pgid == child pid`, which is not the parent's `getpgrp()`. So the follow tests' children are group leaders of their own groups. A signal to the runner's group (`kill(0, …)`, `killpg(getpgrp(), …)`) cannot reach them. It would also have killed the runner, which survives. Only a `kill(childPid, …)` or `killpg(childPid, …)` can reach them, or an out-of-process kill by pid or name.
- **Raw `posix_spawn` children do share the runner's group.** `ServerJobOwnershipTests.systemTableRecordsASpawnedChild` (`ServerJobOwnershipTests.swift:143`) asserts `record?.pgid == getpgrp()`. This doesn't explain the follow-test deaths, but every `posix_spawn` fixture without `POSIX_SPAWN_SETPGROUP` is exposed to any runner-group signal.
- **An audit of BattyKit sources and BattyKitTests found no in-process signaller that targets an arbitrary pid, pgid or name.** Every real `kill`/`killpg`/`terminate()` targets a pid the same test or content spawned. The grep covered `kill(`, `killpg(`, `.terminate()`, `.interrupt()`, `SIGTERM`/`SIGKILL`/`SIGINT`, `pkill`/`killall`, `waitpid(-1`/`wait4`, `setpgid`/`setsid`, and `SystemProcessSignaller`/`ProcessGroupStopper` uses. No test reads a pid from a process-table scan and then signals it. So the plan must verify the "a test signals them" hypothesis, not assume it.

### Suspects, most likely first

1. **`ProcessGroupStopperRealProcessTests`** (`ProcessGroupStopperTests.swift:160`–`254`) is the only test that drives the production `SystemProcessSignaller` (`ProcessGroupStopper.swift:121`–`131`, `killpg(pgid, sig)`) with real signals.
   - The target is `fixture.pid` from its own `POSIX_SPAWN_SETPGROUP` spawn, which is correct.
   - On the failure path of `interruptEndsAGoRunStyleParentAndChild` (`:228`–`232`), `stop.cancel()` runs, then `cleanUp` sends `killpg(fixture.pid, SIGKILL)` (`:218`) and reaps.
   - The stopper `Task` can still be between `check()` and `signaller.signal(...)` (`ProcessGroupStopper.swift:66`–`82`), so it can send `killpg` to a pgid that has already been reaped.
   - `ProcessGroupStopper.refusal` (`:91`–`94`) blocks only pgid ≤ 1, Batty's own group and its ancestors' groups. It does nothing about a stale pgid.
   - macOS allocates pids in sequence, so reuse within milliseconds is unlikely. This is still the one place where a real group signal can outlive its target's reap.
2. **Kill-after-`isRunning` checks:**
   - `ChildProcessFixture.killAndReap` (`ChildProcessFixture.swift:57`–`61`) and `TeardownReaper` (`TeardownReaper.swift:47`–`53`) each send `kill(process.processIdentifier, SIGKILL)` after a `process.isRunning` check.
   - Foundation reaps on its own queue before `isRunning` flips, so the pid can be reaped in between and the `kill` then lands on a stale pid. This path is also shared through `PendingTeardownReapRegistry.shared` (`PendingTeardownReapRegistry.swift:47`).
   - Many tests run in parallel, and `issue/0675` makes `ChildProcessFixture` `nonisolated`, so these kills now run concurrently on pool threads.
   - Low probability for the same pid-reuse reason, but it is a real time-of-check-to-time-of-use (TOCTOU) gap.
3. **Real signaller defaults in `ServerPaneContent`.** `ServerPaneContent.init` defaults to `SystemProcessSignaller()`, `SystemPortListenerScanner()` and `SystemProcessTable()` (`ServerPaneContent.swift:116`–`130`), and so does the production factory `AppStateStore.makeServerContent` (`AppStateStore.swift:204`–`205`).
   - `WebPreviewPaneTests.openInBattyShownOnlyForAllowedListeningURLs` (`WebPreviewPaneTests.swift:361`, `:368`) builds two contents on real port 1 with all three real defaults.
   - The backend is in-process today, so `tearDown` and stop never signal (`ServerPaneContent.swift:206`–`208`). A terminal backend, or a regression in that check, would resolve a real listener and process group on the host and `killpg` it.
   - Every other server test injects `FakeProcessSignaller`. Make this one inject it too.
4. **An out-of-process killer.** Other worktrees' builds and test runs, agents, and Tart and LM Studio tooling all run on the same host and user.
   - The children's full path contains `…/batty-0486-<uuid>/bt0486-xxxxxx`. A `pkill -f batty` style pattern would match them but not the runner, whose path has `Batty`/`BattyKit`.
   - Nothing in this repo does that. `build.sh:306` is `pkill -x "Batty Beta"`, an exact name match, and `tools/run-ui-tests-vm.sh` kills only pids it recorded. Host tooling outside the repo has not been checked.
   - Memory-pressure kills (jetsam) during the memory-signal protocol are a non-test alternative, and should show up in the unified log.
5. **Not a signal at all.** The child may exit on its own at once, for example:
   - an exec or code-signing (AMFI) kill of the freshly copied binary under load;
   - for the `cat` variant, an inherited-fd or stdin problem.
   
   The `sleep 86400` result makes stdin unlikely but doesn't rule out the rest. `ProcessInspectorTests.openFileDescriptorCountGrowsPastItsInitialCapacityWhenNeeded` (`ProcessInspectorTests.swift:349`) opens 1500 fds in the shared test process at the same time. That would make `run()` throw rather than kill a child, but it belongs in the same check.

### What to do first

Capture *why* the child died before changing anything else. Set a `terminationHandler` before `run()` that records `terminationReason` and `terminationStatus`, and add them to `walkDiagnostic`:
- `.uncaughtSignal` with 9 or 15 confirms a signal and names it;
- `.exit` with a status points at suspect 5.

On a signal, also capture the unified log around the failure: `log show --last 5m --predicate 'eventMessage CONTAINS "<pid>"'`, plus any `jetsam`/`AMFI`/`kernel` lines. That can tell an in-process signal from an external or kernel one.

## Acceptance criteria

1. **Identify the signaller**, or rule out a signal with captured evidence (termination reason and status, and the log lines), and record the cause in `## Fix`. If the cause is outside the repo, name it and say which suspect it was.
2. **No test signals anything but processes it spawned:**
   - Every real `kill`/`killpg`/`terminate()` in BattyKitTests, and in BattyKit code that tests reach with real signallers, targets only a pid or pgid the same test got from its own spawn.
   - Group signals go only to groups the test created with `POSIX_SPAWN_SETPGROUP`, never to `getpgrp()`, 0 or 1.
   - No real signal goes after that test has reaped the target. Fix suspect 1's cancel path so it awaits the stopper `Task` before `cleanUp`, or otherwise ensures no signal follows the reap.
   - Close suspect 2's gap. For example, kill only while Foundation hasn't reaped yet, or reap with `waitpid` on a pid the test owns.
   - `WebPreviewPaneTests` injects `FakeProcessSignaller`, a fake scanner and a fake process table.
3. **A guard catches a stray signal.** At least one of these, and preferably both:
   - A canary test. It spawns a long-lived child in its own process group and one in the runner's group, each trapping every catchable signal and reporting it on a pipe. It holds them for the whole run (for example, a suite that starts first and checks last, or a check in a shared fixture's teardown), and fails with the signal name if either child is signalled or dies before the check. An unexpected death shows up as EOF on the pipe.
   - A test-build assertion in one shared signalling seam that `TeardownReaper`, `SystemProcessSignaller` and `ChildProcessFixture` all go through. It records `Issue.record` (or fails a precondition in tests) when the target pid or pgid is not in a registry of pids that tests spawned. It must have no effect in production.
4. Both `ProcessFollowByNameTests` real-enumerator tests pass in 3 consecutive full `./build.sh unit` runs. Their diagnostics include `terminationReason`/`terminationStatus` from now on.
5. Tests follow `AGENTS.md` "Asynchronous tests" and `docs/async-test-seams.md`: no sleeps, and child death is awaited as an event (pipe EOF, termination handler), not by polling.
