## Description

Batty updates a Tab chip's running-command name (for example "Claude" when `claude` starts) from the OSC 2 title, and clears it when OSC 133 D reports the command finished. Both updates come only from two `.onChange`s in `TabRunningCommandObserver` (`BattyKit/Sources/BattyKit/Views/PaneView.swift:812`). They are keyed on `tab.terminal.title` and `tab.terminal.lastCommandDurationNanos`. `tab.terminal` is a Combine `ObservableObject` (`TerminalViewState`, from libghostty-spm) held as a plain `let` on the `@Observable` `TabRuntime`. Observation doesn't track its `@Published` writes, so these observers compare only when something else happens to re-render `PaneView`. This is the cause [#0561](0561.md) found for BEL intake (`.onChange(of: tab.terminal.bellCount)`). The #0561 implementer noted this observer as a follow-up in that issue's `## Gotchas`
- **VM run on `issue/0563` (`6143ac6e`), run `20261105-171835-90863`: 29 of 29 passed** across `TabChipRenderingTests`, `TabRenameTests`, `PaneSidebarTests`, `BellFeedTests`, `FuzzyFinderTests` and `SessionCwdRenameTests/testSessionNameTracksCdIntoAndOutOfProjectDir`, including the new `TabChipRenderingTests/testOSCTitleRenamesAnIdlePaneChipWithoutInteraction`.
.

What the user sees: in a Pane where nothing else changes, the Tab chip, the sidebar Pane row and the Open Quickly row keep the old name after a TUI starts or exits. They update only on the next unrelated re-render: a click, a focus change, a resize, a `cd`, or a sibling Tab changing. A hidden Pane has no `PaneView`, so its Tabs never update while hidden. Because `onChange` doesn't fire for the initial value when the view mounts, a title change that happened while the Pane was hidden is never turned into a running-command name at all.

## Evidence (on `main`)

- **The observer** (`PaneView.swift:805-823`), applied to every terminal Tab at `PaneView.swift:279`:
  ```swift
  .onChange(of: tab.terminal.title) { tab.refreshRunningCommandFromTitle() }
  .onChange(of: tab.terminal.lastCommandDurationNanos) { tab.recordCommandFinishedIfNeeded() }
  ```
  `onChange` compares only when `PaneView.body` is re-evaluated. `tab.terminal.title` registers no Observation dependency, so a title publish never triggers that re-evaluation. #0561's Plan §1 confirmed that no BattyKit view subscribes to the Combine object (no `ObservedObject`, `StateObject`, `EnvironmentObject`, or `onReceive` on it).
- **What it drives:** `TabRuntime.refreshRunningCommandFromTitle()` and `recordCommandFinishedIfNeeded()` (`TabRuntime.swift:471-498`) are the only writers of `TabRuntime.runningCommandDisplayName`, apart from `init`. Its only reader is `TabTitleFormatter.chipTitle(for:)` (`Util/TabTitleFormatter.swift:19`). That function feeds:
  - the Tab chip title and its accessibility identifier (`PaneView.swift:213`, `:229`, `:627`, `:738`);
  - the sidebar Pane row label (`SessionSidebarView.swift:611`);
  - Open Quickly rows (`OpenQuicklyView.swift:163`);
  - Process Status pane labels (`ProcessStatusPaneView.swift:179`, `:370`);
  - the CLI/XPC topology `title` (`XPC/TopologyPayloadBuilder.swift:187`), which is read on demand, so it gets the stale `runningCommandDisplayName`.
- **No command-duration notification exists.** `lastCommandDurationNanos` has no reader outside this observer. Its only job is to clear the running-command name. `lastCommandExitCode` has no readers.
- **The same staleness in views that read the title directly**, with no observer at all:
  - `TabTitleFormatter.chipTitle` falls back to `stripShellPromptPrefix(tab.terminal.title)` (`TabTitleFormatter.swift:22`). A chip showing an OSC 2 title (`vim - file.txt`, `htop`, an ssh host) doesn't change when the title changes, until an incidental re-render.
  - `BellFeedView` builds the row's path label from `tab.terminal.title` (`BellFeedView.swift:180-181`). An open Bell Feed popover shows the old Tab name.
  - The `RenameTabSheet` placeholder reads `tab.terminal.title` (`PaneView.swift:174`). It is evaluated when the sheet opens, so the effect is minor, but it should use the same mirror.
- **Non-view readers are fine.** These read the live value on demand, from event or command code: `WindowRuntime.runningLabel` (`WindowRuntime.swift:1262`), `AppStateStore.tabLabel` (`AppStateStore.swift:2785`), and the bell-capture title (`AppStateStore+BellCapture.swift:69`, `AppStateStore.swift:2718`). They see a value at most one main-queue turn old (`publishSoon`). No change is needed.
- **The delegate already sees both events.** `TerminalDelegateProxy.terminalDidChangeTitle(_:)` (`TerminalDelegateProxy.swift:172`) and `terminalDidFinishCommand(exitCode:durationNanos:)` (`:209`) only forward to `state`. `state` defers the write with `publishSoon` (`TerminalViewState+Delegate.swift:58-62`, `:119-124` in the libghostty-spm checkout).
- **Other `tab.terminal.<published>` reads in views:** a grep of `BattyKit/Sources` for `.terminal.` found nothing else. `TabTitleFormatter` already reads the `workingDirectory` mirror rather than `terminal.workingDirectory` (#0260).

## Steps to reproduce

1. Open a Session with one terminal Pane and leave the mouse still.
2. Run `claude` (or another TUI that `TUIAppRegistry.displayNameFromTitle` knows) in a directory other than `~`.
3. Don't touch the window. The chip keeps the directory or shell title instead of the TUI's name.
4. Quit the TUI. The chip keeps the TUI's name until something else re-renders the Pane.
5. In a second Pane, run `sleep 5; claude`, then hide that Pane (eye toggle) before the 5 s pass. Show it again once `claude` is up. The chip doesn't show the TUI's name until the title changes again while the Pane is visible.

Not reproduced in the app by the filer. The steps come from the code path. A shell whose precmd also emits OSC 7 re-renders through the #0260 `workingDirectory` mirror when the directory changes, which hides the bug in step 4 for some setups.

## Expected behavior

The chip, sidebar row, Open Quickly row and Bell Feed label change on the same main turn libghostty reports the title or command-finished event, whether the Pane is visible, idle or hidden.

## Actual behavior

They change only on the next unrelated re-render of `PaneView`, and never for a title that changed while the Pane was hidden.

## Recommended fix

Do what #0561 did for bells (and #0227/#0436 did for pwd): deliver from the delegate callback into Observation-tracked state on `TabRuntime`, using the callback's arguments, with no `Task` or `DispatchQueue.main.async` hop.

1. **`TerminalDelegateProxy`:** add `onTitleChange: ((String) -> Void)?` and `onCommandFinished: ((_ exitCode: Int?, _ durationNanos: UInt64) -> Void)?`. Call them synchronously in `terminalDidChangeTitle` and `terminalDidFinishCommand`, after forwarding to `state`. Their doc comment must say what `onWorkingDirectoryChange`'s says: `state` hasn't been written yet (`publishSoon`), so consumers use the arguments and never read `terminal.title` back (#0436).
2. **`TabRuntime`:** install both in `init`, next to `onStartupWaitingChange`. No store wiring is needed: unlike bells, nothing here goes through `AppStateStore`.
   - Add an Observation-tracked mirror `public internal(set) var terminalTitle: String`, the #0260 pattern for `workingDirectory`. Seed it from `terminal.title` and write it only when the value changes (an equal-value write still notifies).
   - Change `refreshRunningCommandFromTitle()` to take the title (`refreshRunningCommand(fromTitle:)`), keeping its set-only rule.
   - Change the command-finished path to clear `runningCommandDisplayName` directly when the callback fires. Delete `lastObservedCommandDurationNanos` and `recordCommandFinishedIfNeeded()`.
3. **Views:** `TabTitleFormatter.chipTitle` (`:22`), `BellFeedView` (`:180-181`) and the `RenameTabSheet` placeholder (`PaneView.swift:174`) read `tab.terminalTitle`. Update the comment at `TabTitleFormatter.swift:11-13` so it covers both mirrors.
4. **Delete `TabRunningCommandObserver`** and its `.modifier` at `PaneView.swift:279`.
5. **Docs:** extend the rule #0561 adds to `docs/swiftui-observation-rules.md` (an `onChange` keyed on a Combine `@Published` reached through a plain `let` fires only on incidental re-renders) with this case. Update `TerminalStatePublishing.swift`'s doc comment if it still names title or command-finished as a production reader of the published value.
6. **Tests** (no sleeps, per AGENTS.md "Asynchronous tests"), driven through `tab.terminalDelegate.terminalDidChangeTitle(_:)` / `terminalDidFinishCommand(exitCode:durationNanos:)`, with no view mounted:
   - a known TUI title sets `runningCommandDisplayName` and `chipTitle` synchronously, before the `TerminalViewState` publish lands (assert `tab.terminal.title` is still the old value, then `awaitTerminalStatePublish` and expect no second change);
   - command-finished clears it synchronously, including twice in a row with the same duration (today's delta guard drops the second);
   - an unknown title doesn't clear it (the set-only rule);
   - `terminalTitle` changes, and `chipTitle` follows it, for a non-registry title;
   - migrate `TabRuntimeRunningCommandTests` to the delegate entry point.
   Use a non-default fixture in each "unchanged" assertion.
7. **Order:** plan this after #0561 lands on `main`. It touches the same files (`TerminalDelegateProxy.swift`, `TabRuntime.swift`, `PaneView.swift`, `docs/swiftui-observation-rules.md`, `TerminalStatePublishing.swift`) and should reuse #0561's pattern and doc wording.

### 0. Premises checked

- **Confirmed: the cause.** `TabRunningCommandObserver` (`PaneView.swift:804-816`, applied at `:265`) is the only production caller of `refreshRunningCommandFromTitle()` and `recordCommandFinishedIfNeeded()` (`TabRuntime.swift:494`, `:511`). It keys on `tab.terminal.title` / `tab.terminal.lastCommandDurationNanos`, which are Combine `@Published` (libghostty-spm `TerminalViewState.swift:14`, `:28`) and not Observation-tracked. No view subscribes to the Combine object.
- **Confirmed: no existing mirror covers the title.** #0260 mirrors only `workingDirectory` (`TabRuntime.swift:54-74`). #0227 drives `SessionRuntime`'s title from the pwd callback. A grep for `terminalTitle|liveTitle|oscTitle` in `BattyKit/Sources` and `Batty/` finds nothing. A new mirror is needed.
- **Confirmed: the delegate sees both events.** `TerminalDelegateProxy.terminalDidChangeTitle(_:)` (`:183`) and `terminalDidFinishCommand(exitCode:durationNanos:)` (`:226`) only forward to `state`, which defers the write with `publishSoon` (libghostty-spm `TerminalViewState+Delegate.swift:58-63`, `:119-124`).
- **Confirmed: the write context is safe.** Both actions come through `TerminalCallbackBridge.handleAction` (libghostty-spm `InMemory/TerminalCallbackBridge.swift:30-91`). That is the same path as `RING_BELL`, which #0561's plan traced to `ghostty_app_tick`. The tick is driven by the wakeup hop, the display-link tick or `OccludedSurfaceTicker`, never by a SwiftUI update or layout pass. So a synchronous `@Observable` write here is event-origin, the same as `bellCount` (#0561) and `workingDirectory` (#0436). `OccludedSurfaceTicker` also keeps a hidden Pane's actions flowing (#0288), so the callbacks fire while the Pane is hidden.
- **Wrong in the issue: "Non-view readers are fine … No change is needed."** That was true before #0561. Bell intake now runs synchronously inside the BEL/OSC delegate callback. So `AppStateStore.tabLabel(for:tabIndex:)` (`AppStateStore.swift:2811-2819`, which feeds the banner title and the #0297 decision record), `scheduleSummarization(… tabTitle: location.tab.terminal.title …)` (`:2748`) and the bell-capture `tabTitle` (`AppStateStore+BellCapture.swift:69`) all read `terminal.title` inside a callback. That is the #0436 trap. A TUI that sets OSC 2 and then rings in the same burst, which is common for agents finishing a turn, gets a banner labelled with the *previous* title, because the title's `publishSoon` hasn't landed. Pointing these readers at the mirror fixes it, since the mirror is written synchronously by the earlier title callback. They are included below.
- **Wrong in the issue: the `recordCommandFinishedIfNeeded` doc comment's claim** (`TabRuntime.swift:507-509`): "with oh-my-zsh's precmd the title-driven path already clears". The title path is set-only, so a prompt title never clears. The command-finished event is the *only* clear path. The new doc comment must say so, not repeat the claim.
- **Partly wrong in the issue: "a grep of `BattyKit/Sources` for `.terminal.` found nothing else."** That holds for *views*. The non-view reads are the ones above, plus `WindowRuntime.runningLabel(for:)` (`WindowRuntime.swift:1271-1277`, the close-confirmation message, read on demand). Other `tab.terminal.<published>` reads in views: none besides the three the issue lists (`TabTitleFormatter.swift:22`, `BellFeedView.swift:180-181`, `PaneView.swift:174`). The `terminal.workingDirectory` reads in `WindowRuntime`/`PaneRuntime`/`AppStateStore` are on-demand split/new-tab cwd inheritance and are out of scope.
- **Mount-time case.** The fix covers it with nothing extra. `runningCommandDisplayName` and `terminalTitle` are written in the callback whether or not a `PaneView` exists. When a hidden Pane is shown, its fresh `PaneView.body` calls `chipTitle`, which reads the current Observation-tracked values. No `onChange` initial-value problem remains, because no `onChange` is involved. The Sidebar Pane row of a hidden Pane, which is visible while the Pane is hidden, now also updates live. `TabRuntimeRunningCommandTests` and `TabTitleMirrorTests` below drive the delegate with no view mounted, which is exactly the hidden-Pane case.

The last two survive because the explicit guards were redundant. Round 2 checked the toolchain (Apple Swift 6.4, swiftlang-6.4.0.34.1). `swiftc -typecheck -Xfrontend -dump-macro-expansions` on an `@Observable` class shows the generated setter is `guard shouldNotifyObservers(_s, newValue) else { _s = newValue; return }` around `withMutation`, where the `Equatable` overload of `shouldNotifyObservers` is `lhs != rhs` (and `AnyObject` is `!==`; unconstrained is `true`). A runtime check agreed: an equal `String` or `String?` assignment didn't fire `withObservationTracking`'s `onChange`, a different value did, and an in-place mutation through `_modify` (`m.s.append("")`) still fired, because `_modify` calls `willSet`/`didSet` unconditionally. The guards in `receiveTitleChange(_:)` and `receiveCommandFinished()` were therefore removed in round 2. A doc comment on `receiveTitleChange` records why. The two tests stay, with doc comments saying they pin the macro's equal-write skip, so they now fail if the toolchain starts notifying on equal writes. This departs from the Plan's table.
