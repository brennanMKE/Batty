## Description

In the full Tart-VM UI run on `main` @ `1752688f` (run id `20261006-003524-26742`, results under `build/ui-tests/20261006-003524-26742/`), 25 of 75 tests failed, and the 25 are exactly every test in alphabetical order from `SettingsTests` to the end: `SettingsTests` (3), `SidebarTests` (3), `SplitDividerDragTests` (1), `TabChipRenderingTests` (4), `TabRenameTests` (6), `TerminalPersistenceTests` (1), `ThemeTests` (3), `WindowRegistrationRaceTests` (2), `WindowRestorationTests` (2). Every test before that point passed, the last of them being `SessionCwdRenameTests.testSessionNameTracksCdIntoAndOutOfProjectDir` (22.1 s).

All 25 fail the same way and at the same place: `BattyUITestHarness.launchBatty()` launches `co.sstools.Batty.beta` successfully, then `app.windows.firstMatch.waitForExistence(timeout: 10)` returns `false` (for example `SettingsTests.swift:30`, `XCTAssertTrue failed`). The app process is alive, has a full menu bar, and has **no window at all**. None of the 25 failures is the test's own assertion; they never get that far.

The previous full run (`20260923-191103-94702`, 73 tests, 2026-09-24) had 7 failures and none of this shape: the same `SettingsTests` through `WindowRestorationTests` classes all passed there, in the same alphabetical position. So this is a regression introduced since then, and the evidence points at **state carried from one app launch to the next within a run**, not at any of the 25 tests themselves. The suite runs 76 launches of the same app in one guest; the first 51 opened a window, and the 25 after `SessionCwdRenameTests` did not.

## Premises checked (at `1752688f`)

- `BattyUITestHarness.launchBatty()` (`BattyUITests/Support/BattyUITestHarness.swift:18`) sets only `BATTY_UI_TEST_MODE=1` and `BATTY_UI_TEST_TEMP_HOME=<runner NSTemporaryDirectory()>` in the launch environment and calls `app.launch()`. No launch argument resets `UserDefaults` or saved application state, so **everything the app persists in the guest survives from one launch to the next for the whole run.**
- `BATTY_UI_TEST_TEMP_HOME` is set by the harness but nothing under `Batty/` or `BattyKit/Sources/` reads it (grep). The only consumer of the test-mode flag is `QuitConfirmation.isInUITestMode` (`BattyKit/Sources/BattyKit/Views/QuitConfirmation.swift:15`), which bypasses the quit prompt.
- `SessionCwdRenameTests` (`BattyUITests/SessionCwdRenameTests.swift`) launches, clicks the terminal Pane, types `cd <projectDir> && printf 'HOST=…' > <sentinel>`, waits for the Session row to rename to `BattyCdProbe`, types `cd <plainDir>`, waits for the row to read `Session 1`, then `app.terminate()` runs from the `defer`. `tearDownWithError` then deletes both directories. Both directories live under the runner's `NSTemporaryDirectory()`.
- `BattyAppDelegate.applicationShouldTerminate` (`Batty/BattyApp.swift`) calls `store.nameCache.save()` before returning `.terminateNow`. `SessionNameCache` (`BattyKit/Sources/BattyKit/Model/SessionNameCache.swift`) persists to a file under Application Support and reloads it in `init` on the next launch. This is one persisted artifact that only the cwd test can populate with a project-derived name for a directory that no longer exists.
- The first content Window comes from `WindowGroup(for: WindowID.self) { … } defaultValue: { AppStateStore.shared.initialWindowID }` in `Batty/BattyApp.swift`. There is no `defaultLaunchBehavior`, `isRestorable`, `NSQuitAlwaysKeepsWindows` or `ApplePersistenceIgnoreState` handling anywhere in `Batty/` or `BattyKit/Sources/` (grep), and the "Quit and Keep Windows" alternate menu item is present in the captured hierarchy, so AppKit state restoration is active with its defaults.
- Code merged to `main` since the 2026-09-24 full run that touches the launch/window path: #0436 (`AppStateStore` cwd handling, `TabRuntime`, `TerminalDelegateProxy`, `PaneView`, `TopologyPayloadBuilder`), #0437 (`WindowIDRegistrar` deferred registration retry, `RootWindowView`, `AppStateStore`), #0439 (`defaultTargetWindow`, `AppStateStore`, `RootWindowView`, `ContentView`, `AppXPCService`), #0417 (`SessionSidebarView`). #0443/#0440/#0441/#0442 touched unit tests and docs only.
- `tools/run-ui-tests-vm.sh` accepts several test specs (`for spec in "$@"; do TEST_FILTER_ARGS+=(-only-testing:"$spec")`), and `./build.sh ui` forwards its arguments to it, so a two-class run is possible.

## Steps to reproduce

Only inside the Tart VM, never on a host Mac (AGENTS.md, #0409).

1. `./build.sh ui` on `main` @ `1752688f` (or later).
2. Observe every test from `SettingsTests` onward fail at `app.windows.firstMatch.waitForExistence(timeout: 10)`.

A cheaper probe that isolates the carryover: `./build.sh ui BattyUITests/SessionCwdRenameTests BattyUITests/SettingsTests` (xcodebuild runs classes alphabetically, so the cwd test goes first). Compare with `./build.sh ui BattyUITests/PaneSidebarTests BattyUITests/SettingsTests` as the control.

## Expected behavior

Every launch of `co.sstools.Batty.beta` during a UI run opens one content Window within the harness's 10 s, regardless of what the previous test did or left behind. The full VM suite shows no run of consecutive launch-time failures.

## Actual behavior

After `SessionCwdRenameTests` completes, every subsequent launch in the same guest comes up with a menu bar and no Window, and all 25 remaining tests fail before their first real assertion.

## Open questions

These are candidates to investigate, not conclusions. The fix should name which one it was and show the mechanism, not just make the launches work again.

1. **Is it `SessionCwdRenameTests` specifically, or any launch past some count?** The 2026-09-24 full run passed `SettingsTests` onward at the same position, with `SessionCwdRenameTests` having never launched the app, which favors the cwd test. The two-class probe above answers this directly.
2. **What persisted artifact carries across?** Candidates, in rough order of suspicion: the `SessionNameCache` file saved on terminate (the only state the cwd test uniquely writes, and it points at a deleted directory); AppKit saved application state for `co.sstools.Batty.beta` after a termination while the Terminal Session's shell was in a directory that was then deleted; `UserDefaults` written by the #0437/#0439 window-targeting changes (`WindowIDRegistrar`, `defaultTargetWindow`); a leftover process or modal from the shell the cwd test left behind. Reading the guest's `~/Library/Saved Application State/co.sstools.Batty.beta.savedState/`, `~/Library/Application Support/Batty Beta/` (where `SessionNameCache.canonicalFileURL` puts the cache for the beta bundle id), and `defaults read co.sstools.Batty.beta` right after a failing launch (the runner would need to export them alongside `app-warnings.log`) should settle this.
3. **Why does a bad persisted artifact suppress the default Window rather than crash?** `crashes/` is empty and the main thread keeps running. If SwiftUI believed it restored a window (or decided not to open the default one), nothing in the app would notice: `AppStateStore` only terminates when the *last registered* content Window goes away, and with none ever registered it idles forever. If that is the mechanism, the app side needs a guard that opens a Window when none is restored, independent of the test fix.
4. **Should the harness isolate state per launch?** Even once the root cause is fixed, the UI suite has no protection against the next carryover: no `-ApplePersistenceIgnoreState YES`, no defaults reset, no per-test Application Support directory. Whether that belongs in this issue or a follow-up is for the implementer to decide, but it must not be used as the *only* fix, because it would hide a real user-facing launch bug.

## Root cause

AppKit persistent-UI state restoration fed SwiftUI a window identifier it could never map back, and AppKit counted that as "restored", so SwiftUI did not open the default window. Evidence from run `20261006-025555-53522` (`guest-state/app-all-processes.log`, `NonTerminalPaneCloseTests` + `SessionCwdRenameTests` + `SettingsTests`):

- Pid 4548 (first launch) and pid 4607 (the cwd launch) log `-[NSApplication _reopenWindowsAsNecessaryIncludingRestorableState:...] shouldRestoreState=1 hasPersistentStateToRestore=0`.
- Pid 4607 lived long enough (22 s) for AppKit's deferred save: it logs `-[NSPersistentUIManager flushAllChanges] ... writing records` at 09:57:58.5, about 15 s after launch. Shorter-lived launches are killed before that flush and never persist anything, which is why only the long cwd test arms the trap.
- Every later launch (pids 4661, 4702, 4703) logs `hasPersistentStateToRestore=1`, then `restoreWindowWithIdentifier: identifier=SwiftUI.PresentedWindowContent<BattyKit.WindowID, ...OpenWindowHookInstaller...-1-AppWindow-1` handled by `SwiftUI.AppWindowsController`, and the completion arrives with `window=0x0 error=(null)`: no window was restored and no error was raised.
- Those launches then report `nsWindows=0 registeredContentWindows=0 runtimes=1` at +1 s and +4 s (the temporary `launchWindowState` log), and no `TerminalHostView: attached host to window` line.
- The saved identifier embeds `(unknown context at $<address>)` because the content view type's background modifier was a `private struct OpenWindowHookInstaller`; Swift prints a private type's runtime context as an address, and ASLR makes it different in every process. The same address leaked into the `NSWindow Frame ...` and `NSSplitView Subview Frames ...` defaults keys (one new pair per launch, never read back).

Why the earlier runs passed or failed as they did: the cwd test alone, or any class alone, never produced the failing state in a probe because the trap needs a launch that lives past the ~15 s flush followed by another launch. The 25 failures in the original run are every launch after the first long-lived one.

## Fix

The fix is a product guard that does not depend on AppKit's restoration mechanism (`44addbb4`), plus two retained supporting changes and a second-layer harness change.

- `LaunchWindowGuard` (`BattyKit/Sources/BattyKit/Util/LaunchWindowGuard.swift`): `BattyAppDelegate.applicationDidFinishLaunching` installs a one-shot main run-loop observer that fires the first time the loop is about to wait (pending launch work, including SwiftUI's own default window, has been drained). If `AppStateStore.launchNeedsContentWindow` (no registered content window) is still true, it performs the "New Window" menu item, the only path to the scene's `openWindow` action while no window exists.
- `AppStateStore.windowIDForNewWindow()`: while no content window is registered it returns `initialWindowID` (the runtime `init` seeded), otherwise a fresh `WindowID()`. Both New Window call sites (`BattyCommands.NewWindowButton`, `OpenWindowHookInstaller`) use it, so the guard opens the seeded runtime instead of a phantom second one (#0251), and `openWindow(value:)` focuses an existing window with the same value rather than duplicating it.
- `.restorationBehavior(.disabled)` on the content `WindowGroup` and the Help `Window`, and `OpenWindowHookInstaller` no longer `private` (its runtime type name carried a per-launch address into the AppKit window identifier and the window-frame defaults keys; confirmed gone in run `20261006-030238-61396`). Neither stopped the failure by itself; they are kept because with a stable identifier a restored window could otherwise come back with a stale `WindowID` and an empty lazily-created runtime next to the seeded one, and because the frame keys no longer grow by a pair per launch.
- Harness (`851f2de9`, separate commit, second layer only): `BattyUITestHarness` launches the app with `-ApplePersistenceIgnoreState YES`. It was added after the product guard alone had been verified, so it does not mask a product failure.
- `tools/run-ui-tests-vm.sh`: pulls a small bounded `guest-state/` (defaults, saved-state and Application Support listings, name cache, the app subsystem's log), retries SwiftPM resolution once, and takes an opt-in `BATTY_UI_FULL_APP_LOG=1` for the full per-process log where this root cause was found.

Tried and reverted or insufficient, with the run that showed it:

- `.restorationBehavior(.disabled)` plus the de-privatized type: repro run `20261006-030238-61396` still failed (the key lost its address, but `flushAllChanges ... writing records` still ran and later launches still logged `hasPersistentStateToRestore=1` with no `restoreWindowWithIdentifier` call at all).
- `NSWindow.isRestorable = false` on every window (content windows in `registerNSWindow`, others via `didBecomeKey`/`didBecomeMain` observers): repro run `20261006-032757-73148` still failed identically. Reverted.
- No app-delegate "should restore state" veto exists in the macOS 27 SDK headers (`NSApplication.h`, `NSWindow.h`), and `NSQuitAlwaysKeepsWindows` only governs quit-time behavior, not the kill-based exits the UI tests use, so neither was tried.

## Gotchas

- Where AppKit stores the persistent-UI record is unverified. It is not `~/Library/Saved Application State/co.sstools.Batty.beta.savedState` (the listing reports that missing); `app-all-processes.log` shows it going through the `com.apple.appkit.restoration_storage` XPC service, and its contents were never captured.
- Why `hasPersistentStateToRestore=1` suppresses the default window even when no window is restored is inferred from the logs, not from AppKit documentation. The inference matches every run: the suppression appeared exactly after a launch lived past the ~15 s `flushAllChanges`, and the guard's "no content window" log line fired on exactly the launches that had previously failed.
- The guard performs the "New Window" menu item found by its localized title (`BattyCommands.newWindowMenuTitle`, which is `ShortcutAction.newWindow.displayName`, the same "New Window" key `NewWindowButton`'s `Button("New Window")` resolves), so a title that stops matching makes the guard log an error and do nothing. `LaunchWindowGuardTests` covers the missing-item path.
- That SwiftUI's own default window exists by the first run-loop quiescence is an observation (run `20261006-033829-79840`: the guard fired on exactly the 25 poisoned launches and none of ~50 normal ones), not an API guarantee. The guard also treats an existing window whose identifier starts with `SwiftUI.PresentedWindowContent` as a content window, a prefix taken from the identifiers AppKit logged in `restoreWindowWithIdentifier`; it is covered by a unit test with a synthetic identifier, not a real SwiftUI window.
- No end-to-end test exercises the guard: the harness passes `-ApplePersistenceIgnoreState YES` to every launch, and a test that reproduces the poisoned state needs a launch that lives past AppKit's ~15 s flush with no completion signal to await (AGENTS.md bars waiting for a duration). Follow-up proposed: a UI test hook that lets the app signal that the persistent-UI record has been written (or an injectable flush trigger), then relaunch without the flag and assert a window appears.
- Real-user implication: a long-running Batty that is killed or crashes after AppKit's flush (and on the next user launch) could previously come back with a menu bar and no window. The guard now opens one. `.restorationBehavior(.disabled)` means no window state is restored on top of it.
- Not verified by hand: the guard on a real (non-VM) launch; the window it opens is created by the same SwiftUI `openWindow(value:)` path as File > New Window.
- **#0238 regression, by user decision (2026-10-09):** `.restorationBehavior(.disabled)` stays, so Batty no longer restores its window set: window count, frames, displays and per-window `@SceneStorage` (`RootWindowView`'s `sidebarHidden`, which still works as in-process per-window state but is no longer persisted across launches, so it is not dead code). `issues/0238.md` and `docs/multi-window-design.md` §4/§6 now say so. Could #0238's frame restoration have worked in the field? Probably not: the content view's background modifier has been the `private struct OpenWindowHookInstaller` since #0237 (June 2026), and a private type's runtime context prints as `(unknown context at $<address>)`, an address that differs per process under ASLR. That text was in the saved window identifier and in the `NSWindow Frame ...` / `NSSplitView Subview Frames ...` defaults keys (one new pair per launch in the VM, never read back), so a saved record could not match the next launch's window. Verified only on the VM's Debug-configuration Beta build; a Release build was not inspected, and no manual field check of window restoration was done.

## Resolution

AppKit's persistent-UI record (written by `NSPersistentUIManager` about 15 s after launch) made
every later launch report state to restore, and SwiftUI then skipped its default content window,
leaving a menu bar and no window. Neither SwiftUI's scene restoration opt-out nor
`NSWindow.isRestorable = false` stopped the record, so the fix is mechanism-independent:
`LaunchWindowGuard` checks at the first run-loop quiescence after launch and, if no content
window exists, performs New Window for the seeded `initialWindowID` (no phantom runtime, #0251).
Window restoration stays disabled by user decision (gives up #0238's window-set restoration);
`OpenWindowHookInstaller` is no longer `private`, so window identifiers and frame-autosave keys
no longer embed a per-launch address. The UI harness launches with
`-ApplePersistenceIgnoreState YES` as a second layer. Verified in the Tart VM: the guard alone
fixes the repro and fires only on poisoned launches; the full suite passes except #0445's two
