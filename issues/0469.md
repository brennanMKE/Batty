## Description

Umbrella for **Projects**, the 1.3.0 headline feature and the first feature built behind a feature flag under `AGENTS.md` "Release branches" (flag on in Batty Beta, off in Prod; with it off the feature is invisible and inert: no menu, Command Palette, Sidebar or CLI entry points, no reads or writes of the feature's files). A Project defines a Session once (its name, root folder, Session color, Pane arrangement, what each Pane shows, and each Terminal Tab's directory and startup command) so the user can open it in one action, ready to work.

The user approved a visual design on 2026-10-12 (canvas: https://claude.ai/artifact/WoKFESyWFnQFkM64TF2P5o, artboards attached below). It replaces the "A: launcher only" recommendation in the earlier research doc (`projects-proposals.md`, attached). That doc is still the best map of the code Projects plugs into, but its §2 recommendation and its "no startup commands" guardrail are superseded by the user's choice.

This issue tracks the children and owns the acceptance criteria for the feature as a whole. It holds no code of its own.

## The approved design

**A Project** is:

- a **name**, a **root folder**, and a **Session color**;
- a **Layout**: one of the existing `PaneLayout` presets, or a topology copied from the current Session;
- **per-Pane configuration**: each Pane's kind, which is one of Terminal, Git Status, Process Status, System Metrics or LM Studio (`PaneContentKind`);
  - a **Terminal** Pane has one or more Tabs, each with an optional title, a working directory relative to the root, and an optional startup command;
  - a **Git Status** Pane has a repository folder relative to the root;
  - the other kinds have nothing to configure;
- a per-Project **"Run startup commands when the Project opens"** toggle.

Pane sizes are **not** stored. Panes open at equal sizes per the #0255 equalization rule, as #0371 specified, and the user resizes them freely afterwards.

**Surfaces:**

1. **Project Editor** (artboard 1). A Projects list on the left with "+ New Project…". A header with Name, Root folder plus "Choose…", and Session color swatches. A Layout strip of preset thumbnails plus "Copy from current Session". A clickable pane preview. A right inspector for the selected Pane: a kind picker, then for a Terminal a Tabs editor (title, working directory `root/…`, startup command `$ …`, "+ Add Tab", remove ×), or for Git Status a repository folder. The footer has the run-commands toggle, Cancel, Save, and Save & Open.
2. **Open Project picker** (artboard 2). A sheet like the Layout picker, with a filter field and a grid of Project cards. Each card shows a pane thumbnail colored by kind, the name, the path, "N panes · N tabs · N startup commands", and an OPEN badge when a Session from that Project is open. Return opens the Project in a new Session, or switches to the open one. Option-Return opens another copy. The footer hints are "⌥↩ Open another copy", "⌘E Edit" and "⌘N New Project…".
3. **Opening a Project** (artboard 3). This creates a new Session titled with the Project name (title pinned) and colored with the Project color. It builds the Panes with their kinds and Tabs in their directories, then types each startup command into its Tab's shell once the shell is ready. The Tab stays open at the prompt after the command exits. The Sidebar row shows a small folder glyph marking a Project-backed Session.
4. **Startup command trust** (artboard 4). The first time a Project's commands would run, and again whenever any command changes, a sheet titled "Run N startup commands for "<name>"?" lists each command with its Pane and Tab. It offers "Open Without Running" or "Run Commands", plus a "Don't ask again until the commands change" checkbox, which stores an approval hash of the command set.
5. **Entry points** (artboard 4):
   - File ▸ **Open Project ›**, a submenu listing Projects (a check mark on Projects with an open Session), then Choose Project… and New Project…;
   - File ▸ **Save Session as Project…** and File ▸ **Edit Projects…**;
   - the Sidebar Session context menu gains **Save as Project…**, which captures Panes, kinds, Tab working directories and titles, then opens the editor;
   - the Command Palette gains **Open Project: <name>** entries and **Save Session as Project…**;
   - the CLI gains `batty project list` and `batty project open <name>` (`batty-beta` in Beta).
   - **No new keyboard shortcuts** (no new `ShortcutAction` cases) while the feature is flagged. See `projects-proposals.md` §4.3 for why.
6. **Storage**: a per-variant `~/Library/Application Support/<Batty|Batty Beta>/projects.json`. These are user-authored records written only on explicit user action, the `SessionNameCache` precedent. This is not a revival of #0172's automatic whole-app restore.

## Acceptance criteria (whole feature)

- In **Batty Beta** every surface above works as the artboards show, with the code-level deviations recorded under "Design vs. code" below resolved as noted there.
- In **Prod**, with the flag off, Projects is **invisible and inert**. Each child names its own gate sites, and together they cover all of these:
  - no File menu items, no Sidebar context item or glyph, no Command Palette entries, no Project Editor window or Window-menu entry;
  - no `batty project` subcommand, and nothing about projects in `batty capabilities`; the app rejects any project XPC verb as unknown;
  - `ProjectStore` is never constructed and `projects.json` is never opened, read or created.
- Every gate site reads one grep-able symbol (#0470), so removing the flag in the release that ships Projects means deleting that symbol and fixing the compile errors. #0470 records the site list, and each child appends to it.
- No new `ShortcutAction` case is added while the feature is flagged.
- `Concepts.md` defines **Project**, and `PRD.md` explicitly puts per-Project startup commands in scope (#0470).
- Opening a Project never touches `TerminalHostStore`/`AppTerminalView` directly. It goes through the existing Session/`SplitTree` creation paths (`docs/view-hierarchy.md`). Every observed-state write originates from an event such as a menu, palette, sheet button, XPC request or terminal delegate callback, never from `body`/`onAppear`/geometry callbacks (`docs/swiftui-observation-rules.md`).
- No unit test waits on time (`AGENTS.md` "Asynchronous tests").
- `./build.sh unit` passes after every child. The VM UI suite passes after #0478. A Release archive (`./build.sh release archive …`) builds before 1.3.0 is cut (`AGENTS.md` test strategy).
- The flag-removal issue for the 1.3.0 release is filed when this umbrella's children resolve. That issue removes the flag, adds shortcuts if the user wants them, and adds the Help page (see open question 2).

## Design vs. code: deviations to resolve during implementation

Found while verifying the design against `main` at `dfd7d39a`. None of them changes the design's intent.

1. **Session colors.** The editor artboard shows six swatches (orange, blue, teal, purple, pink, gray). `SessionColor` (`BattyKit/Sources/BattyKit/Runtime/SessionColor.swift:13-24`) has ten: blue, orange, green, pink, teal, red, violet, amber, cyan, brown. It has no gray. The editor must offer the real ten-color palette (reusing `SessionColorPickerView`'s swatches if practical) and store a `SessionColor` value, not a hex.
2. **Layouts.** The artboard's Layout strip shows seven presets. `PaneLayout` (`Model/PaneLayout.swift:9-19`) has ten (it adds `threeRows`, `mainRightTwoLeft`, `mainBottomTwoTop`). The strip shows all ten, driven from `PaneLayout.allCases`.
3. **LM Studio label.** The design says "LM Studio". `PaneContentKind.displayName` is "LM Studio Dashboard" (`BattyXPCCore/PaneContentKind.swift:69`). Use `displayName` so labels stay consistent with the Pane menu, unless the user asks otherwise.
4. **File menu mock-up.** Artboard 4's File menu shows "New Tab ⌘T" and "Close Tab ⌘W". The real File menu (`Commands/BattyCommands.swift:66-87`, `CommandGroup(replacing: .newItem)`) holds New Window, New Session and Open Quickly, and Tab items live in the Tab menu (`:470`). The Projects items go into the real File group. Nothing moves.
5. **Sidebar context-menu labels.** The artboard shows "Rename Session…" and "Session Color ›". The real menu (`Views/SessionSidebarView.swift:274-308`) reads Rename / Reset Name / Set Color… / Reset Color / Set Session Theme… / … / Close. Only "Save as Project…" is new. Existing labels are untouched.
6. **Picker footer chords ⌘E / ⌘N.** These are in-sheet key handlers, not `ShortcutAction`s. ⌘N is also the global New Session chord (`ShortcutAction.newSession`). The `BattyShortcuts` NSEvent monitor returns early when the key window is not a content window (`Commands/BattyShortcuts.swift:34`, `keyWindowIsContentWindow()`), but a `.sheet` is attached to the content window. #0475 must verify which handler wins and make ⌘N inside the picker mean New Project…, not also create a Session.
7. **The Project Editor as a separate window.** The only non-content `Window` scene today is Help (`Batty/BattyApp.swift:55-68`). A SwiftUI `Window` scene is listed in the Window menu, which would leak the feature in Prod. #0474 must make the editor's scene (or AppKit window) absent when the flag is off.

## Open questions for the user (non-blocking; defaults in parentheses)

1. **Theme per Project.** Should a Project also remember a Session theme (`SessionRuntime.localThemeName`)? (Default: no. The design has no theme field.)
2. **Help content.** Should a Projects Help page ship in Beta only, or wait until the flag is removed? `Help/` is bundled into both variants. (Default: wait. The flag-removal issue adds `Help/` content.)
3. **Startup commands for non-active Tabs.** All of a Pane's Tabs mount their placeholders (`Views/PaneView.swift:249-250`, `ForEach(pane.tabs)`), so every Tab's shell spawns, but only once its Session is selected and mounted (`docs/view-hierarchy.md` "First mount" timeline). (Default: commands run in every Tab as soon as each shell is ready, which happens right after open because the new Session is selected.)

## Notes

- **#0371 (Workspaces).** Projects delivers #0371's core: a saved multi-kind Pane topology, applied by replaying ordinary splits with equal sizing, captured from the current Session. #0472 generalizes `PaneLayout.apply` to carry a kind per slot, and #0476 builds the capture converter. #0371 stays open for the parts Projects does not cover: standalone named Workspaces applied to an *existing* single-Pane Session, and the gate leak on the shortcut and palette paths. The cross-reference is recorded in #0371's Notes.
- **#0172 squaring.** A Project stores Tabs, working directories and commands, which #0371 deliberately excluded. It stays outside #0172's objection because it is user-authored, explicitly invoked, never auto-saved, never captures live state on quit or on a timer, and never auto-restores at launch. The `Concepts.md` entry (#0470) must say so.
- **PRD non-goal squaring.** `PRD.md` §3 lists "A scripting/config language à la tmux's `.tmux.conf`" as a non-goal, and `projects-proposals.md` §2 had ruled startup commands out on that basis. The user approved startup commands. They are literal lines typed into a shell, not a language. #0470 records the decision in `PRD.md`, and the trust prompt (#0473) is the safety line #0247 asked any per-project setting to respect.
- **CLI noun set.** `docs/batty-cli-design.md:38` fixes the nouns as `session`, `pane`, `tab`, `window`. `project` is a deliberate fifth noun approved with this design. #0477 updates that doc.
