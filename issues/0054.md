# 0054 — Cmd-W should close the active tab, with confirmation if a process is running

| | |
|---|---|
| **Status** | open |
| **Module** | Tabs / TerminalSurface |
| **Platform** | macOS |
| **First seen** | 2026-05-11 |

## Description

`Cmd-W` is already bound to "Close Tab" in the Tab menu (`BattyCommands.swift` line 150). The behavior gap is that it closes immediately, with no check for whether a foreground process is running. Matching macOS Terminal.app / iTerm2 / Ghostty's behavior, the close should:

- **Close immediately** when the tab is idle (no foreground process beyond the shell itself — just a prompt waiting for input).
- **Prompt for confirmation** when the tab is busy (a long-running command, a TUI like `vim` / `htop` / `ssh`, or any non-shell process group in the foreground). The confirmation should name what would be lost ("Closing this tab will end ssh.") and offer Close / Cancel.

This protects against the common foot-gun of `Cmd-W` near `Cmd-S` / `Cmd-Q` killing a running build, dropping an SSH session, or losing unsaved changes in a TUI editor.

## Steps to reproduce

1. Open a tab. At the bare shell prompt, hit `Cmd-W` — the tab should close instantly. (Currently does.)
2. Run `sleep 60` (or `vim`, `ssh somewhere`, `npm run dev`, etc.) in a tab. Hit `Cmd-W`. **Expected:** confirmation prompt naming the running command. **Actual:** tab closes silently, killing the process. The shell's SIGHUP delivery to the foreground process is the only signal to anything important running there.

## Expected behavior

`Cmd-W` semantics:

| Foreground state | Behavior |
|---|---|
| Bare shell prompt (no command running) | Close tab immediately. |
| Foreground command running (sleep, vim, ssh, etc.) | Show modal confirmation: "Close tab? `<command>` is still running." Buttons: **Close** (destructive) and **Cancel** (default). |
| Multiple commands queued (`sleep 1; sleep 2`) | Treat as busy. The shell parent doesn't matter; the foreground process group is the signal. |

The confirmation should default to **Cancel** so a panicked second `Cmd-W` keystroke doesn't blow through it. (Cancel as the safe default; Close as the destructive option.)

Optional setting: a "Don't ask again for this tab" checkbox, or a global preference "Always confirm tab close" / "Never confirm tab close." Defer until the user complains; the per-tab "don't ask again" especially adds state-management complexity.

## Actual behavior

`AppStateStore.closeFocusedTab` → `closeTab(id:)` → `pane.removeTab(id:)` → tab destroyed; the underlying `TerminalViewState` and its libghostty surface get torn down; any foreground process gets SIGHUP via the PTY closing. No confirmation, no warning.

## Notes

### Signal source: "is something running?"

The core requirement is a per-tab "is a foreground process running" signal. Available paths:

1. **`tcgetpgrp(ptyFd) != shellPid`** — the POSIX-standard way. The PTY's foreground process group ID is the shell's PID when the shell is the foreground; it changes when the shell forks and assigns a new pgid to a child. Requires libghostty to expose either the PTY fd or a derived "is the foreground process the shell?" boolean. The fork (`brennanMKE/libghostty-spm` branch `batty-delegates`) is the place to add this if it doesn't exist.
2. **OSC 133 prompt-start / prompt-end** — when shell integration is active (Ghostty's `shell-integration` scripts source-in to zsh/bash/fish), the shell emits OSC 133 markers around commands. `TerminalSurfaceCommandFinishedDelegate` was added in the fork (`#0044`); a companion `TerminalSurfacePromptDelegate` for command-start would give us "running now" without process-table introspection.
3. **`ps -t <tty>` polling** — slow, ugly, requires shelling out. Avoid.

Path 1 is the closest to "always works regardless of shell integration." Path 2 is what tells us *what* is running (the command name for the dialog), but requires shell integration to be set up. The cleanest v1 design uses both: path 1 for the boolean, path 2 (when available) for the command name in the message.

`TerminalViewState` already has the surface; whatever signal we expose ends up there. Until the fork adds it, this issue is **blocked on a libghostty wrapper change** the same way `#0044` was. File the upstream change as a sibling issue when starting work.

### Process-name fallback

If we have the boolean ("busy") but not the command name (no OSC 133), the dialog text degrades to: "A process is still running in this tab. Close anyway?" Worse, but still useful.

### Close paths to cover

`Cmd-W` is one entry point. There are several others, all of which should go through the same gate (or share a `closeFocusedTabWithConfirmation` helper):

- `Cmd-W` (Tab menu "Close Tab")
- Chip × button (tab chip close affordance)
- Chip context menu "Close Tab"
- Chip context menu "Close Other Tabs" — should confirm if *any* of the to-close tabs are busy (one dialog summarizing the busy ones, not N dialogs).
- Closing the last tab in a pane / the last pane in a session — already cascades via `AppStateStore.closeTab(id:)`; the confirmation gate should fire *before* the cascade.
- Window close (`Cmd-Shift-W` or red-button) — out of scope here; that's a window-level confirmation tracked separately if needed.

### Per-tab "busy" tracking

`TabRuntime` can hold an `isBusy: Bool` that mirrors the signal from `TerminalViewState`. Drive it from `terminal.foregroundProcessID` (or whatever the fork exposes); update via `.onChange` like the existing bell tracker. Then `closeTab` checks `tab.isBusy` and either closes or raises confirmation.

### Confirmation UI

A SwiftUI `.confirmationDialog` is the lightweight choice. For a single-tab close, default-cancel; Close button has destructive role. For "Close Other Tabs" with multiple busy ones, the dialog title can say "Close N tabs? M are still running." with the list in the body.

## Acceptance criteria

- `Cmd-W` on a bare-prompt tab closes immediately (existing behavior; must not regress).
- `Cmd-W` on a tab running a long command (e.g. `sleep 30`) raises a confirmation dialog.
- The dialog names the running command when shell integration is active; falls back to a generic message otherwise.
- Cancel keeps the tab open and leaves the running process untouched.
- Confirm closes the tab; the running process receives SIGHUP via PTY close as it does today.
- The chip × button and the context-menu close paths use the same confirmation gate (no bypass).
- "Close Other Tabs" with one or more busy siblings raises a single summary confirmation, not N dialogs.
- Default focus in the dialog is Cancel.

## Out of scope

- Window-level "Close window with running tabs" confirmation — track separately if/when it becomes a problem.
- A preference to suppress the confirmation. Add it only if a user explicitly asks.
- Detection of "modified buffer" in TUIs (e.g. unsaved `vim`). Out of scope — vim's own quit hook handles that; we just don't blow the connection away without asking.
- Restoring a closed tab (a la `Cmd-Shift-T`). Separate feature; tracked elsewhere if requested.

## Suggested implementation sketch

1. Land `terminal.isForegroundProcessShell` (or equivalent) in the libghostty-spm fork. File as a sibling issue.
2. Add `TabRuntime.isBusy: Bool` driven from `terminal` via `.onChange` in `PaneView`.
3. Refactor close paths so they all call `AppStateStore.requestCloseTab(id: UUID)` (new method) which checks `isBusy` and either calls the existing `closeTab(id:)` immediately or signals a confirmation that the view layer presents.
4. Add a `pendingCloseConfirmation: PendingClose?` (`@Observable` on `AppStateStore`) that the root window view's `.confirmationDialog` reads.
5. Wire `Cmd-W`, chip ×, context-menu close, and Close Other Tabs to `requestCloseTab`.
