# 0330 — README's build instructions name a nonexistent scheme and open the project instead of the workspace

| | |
|---|---|
| **Status** | open |
| **Module** | Docs |
| **Platform** | macOS |
| **First seen** | 2026-08-08 |

## Description

`README.md:27` tells a new contributor to run `xcodebuild -scheme Batty -destination 'platform=macOS' build`. There is no scheme named `Batty` — the shared schemes are `Batty (Prod)` and `Batty (Beta)` (`Batty.xcodeproj/xcshareddata/xcschemes/`), and `CLAUDE.md` warns about this exact trap ("The actual scheme is `Batty (Prod)`, not `Batty`"). Verified by actually running the README's command from the repo root: it exits 65 with

```
xcodebuild: error: The project named "Batty" does not contain a scheme named "Batty".
```

So the very first command the project's front page gives a reader fails.

The next line is stale too: `README.md:28` says `open Batty.xcodeproj`, but since #0220 the guidance is to open `Batty.xcworkspace` — the workspace owns the BattyKit package, and opening the bare project leaves `BattyKitTests` missing from the Test Navigator (the workspace-sole-owner rule in `CLAUDE.md`). And the README never mentions `scripts/build.sh`, the documented canonical build wrapper, which picks the right scheme and the workspace for you.

## Steps to reproduce

1. Clone the repo, `cd` into it.
2. Run the README's build command: `xcodebuild -scheme Batty -destination 'platform=macOS' build`.

## Expected behavior

The Building section gives commands that work: `scripts/build.sh` as the primary path (it wraps `xcodebuild` with the `Batty (Prod)` scheme and the workspace), and `open Batty.xcworkspace` for Xcode work.

## Actual behavior

`xcodebuild` fails with "does not contain a scheme named 'Batty'" (exit 65), and the `open` line steers readers to the `.xcodeproj`, which hides `BattyKitTests` from the Test Navigator.

## Notes

- **A near-miss that does not rescue the command:** a lowercase `batty` scheme does exist — it's the BattyKit package's CLI executable product (`BattyKit/Package.swift:20-21`) and shows up in a workspace-level `xcodebuild -list`. But the README's command (no `-workspace`/`-project`) resolves the bare `Batty.xcodeproj`, whose only schemes are `Batty (Prod)` and `Batty (Beta)`, so it fails regardless.
- **Everything else in the README checked out.** Requirements are current: "macOS 15.6 or later" matches `MACOSX_DEPLOYMENT_TARGET = 15.6` in `Configuration/Build.xcconfig`; no architecture restriction is set, so "Apple Silicon or Intel" holds. The shortcut claims at lines 12, 14, and 15 (`Cmd-Option-1–9` for tabs, `Cmd-Shift-L` layout, `Cmd-Shift-T` theme) all match `ShortcutAction.defaultBinding` — #0328 already corrected this file. No missing first-run prerequisite: GhosttyKit resolves as a package dependency (`libghostty-spm`), so clone-and-build needs no extra fetch step.
- **One marginal line, flagged not asserted as a defect:** `README.md:17` says "every action has a shortcut; fully customizable in Settings." The positional `Cmd-1..9` / `Cmd-Option-1..9` pair is swappable but not freely rebindable, and `Cmd-C`/`Cmd-V` are fixed — the in-app Help's own shortcuts page opens by disclaiming "the few combos that aren't yours to remap." Marketing shorthand vs. inaccuracy is the implementer's judgment call.
