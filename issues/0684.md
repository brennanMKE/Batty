## Description

Child of #0680. `batty capabilities --json` is the source of truth for every verb and its `inputSchema` (`.claude/skills/batty-cli/SKILL.md:15-20`), but an agent without Batty installed, or a person reading ahead, can't see it. Publish it as `docs/cli/capabilities.json` and render a human and agent-readable reference from it at `docs/cli/index.html` and `docs/cli/index.md`.

### Current state (checked against `main` at `3a7c12ec`)

- `CapabilitiesCommand.buildPayload(flags:)` (`BattyKit/Sources/batty/CapabilitiesCommand.swift:75`) builds a `CapabilitiesPayload` (`BattyKit/Sources/BattyXPCCore/CapabilitiesPayload.swift:49-57`: `cliVersion`, `verbs`, `exitCodes`, `jsonSchemaDialect`); each verb has `name`, `abstract`, `aliases`, `inputSchema`, `annotations` (lines 11-21).
- The verb list depends on `FeatureFlags` (`agentIntegration`, `serverPane`) until #0669/#0670 remove them, so a Beta and a Prod build list different verbs today.
- No `website/docs/cli/` exists.

## Expected behavior

1. `website/docs/cli/capabilities.json` is committed: the `--json` output, pretty-printed with sorted keys. It is regenerated at each release from that release's Prod build (step added to `website/README.md` "Per-release workflow" by this issue).
2. `tools/build-cli-reference.py` (stdlib Python, `python3 -I`, with `--check` and a self-test) renders `website/docs/cli/index.md` and `website/docs/cli/index.html` from the JSON: grouped by noun, each verb with its abstract, aliases, parameters (name, type, enum values, default, required) from `inputSchema`, its annotations, and the exit-code table. The pages state the `cliVersion` they were generated from.
3. **Drift test.** A BattyKit unit test builds the payload in-process with all flags on (or with no flags, once #0669/#0670 land) and compares it with the committed JSON, ignoring `cliVersion`. It fails, naming the regenerate command, when a verb is added, removed or changed without regenerating. The plan picks the module that can see `buildPayload` (the `batty` executable target is not importable; move the builder or the test accordingly, without changing `--json` output, #0384).
4. `docs/cli/` stays in `website/.deploy-hold` (#0681) until #0688.

## Acceptance criteria

1. `./build.sh unit` passes, and editing any verb's abstract or schema without regenerating fails the drift test.
2. `python3 -I tools/build-cli-reference.py --check` exits 0; `tidy -e -q website/docs/cli/index.html` reports no errors.
3. The reference pages list every verb in `capabilities.json`, and nothing else.
4. `batty capabilities --json` output is unchanged by this issue (diff before and after on a Beta build).

### Decisions

1. **Where the JSON comes from: the real CLI's own `--json` stdout, never a Python re-serialization.** The file has to match `batty capabilities --json` byte for byte. Python's `json.dumps` formats differently from `JSONEncoder` (`"key" : value`), so Python never re-encodes it. There are two sources:
   - **Pre-release (default, SwiftPM only, no app build):** `swift run --package-path BattyKit --scratch-path BattyKit/.build/cli-reference -Xswiftc -DBATTY_VARIANT_BETA batty capabilities --json`. `BATTY_VARIANT_BETA` makes `ServiceNames.current == .beta`, so `FeatureFlags.current` has every flag on. That is the 1.5.0 surface once #0669/#0670 remove `agentIntegration` and `servers`. A separate `--scratch-path` matters because the Xcode "Embed CLI" phase and `./build.sh unit` build in `BattyKit/.build` with other flags, and sharing that directory would force full rebuilds both ways.
   - **Release (#0688):** `--cli /Applications/Batty.app/Contents/Resources/bin/batty`, the shipped Prod CLI, used verbatim. Its `cliVersion` is real.
2. **`cliVersion` on the pre-release path.** The swift-run CLI reports `"unknown"`, so on that path the generator requires `--cli-version X.Y.Z`. It replaces the value on the single line matching `^  "cliVersion" : "unknown",$` (it must match exactly once, else exit 2), which gives the same bytes `JSONEncoder` would write. With `--cli`, `--cli-version` is refused (exit 2): the release JSON keeps what the Prod build reports. The implementer generates with `--cli-version 1.5.0` (the issue's Target), and the pages say "Batty 1.5.0".
3. **All release flags on, stated in the pages.** Until #0688 regenerates from the Prod build, the pages' version line reads "Batty 1.5.0 command-line reference", with no Beta note. Everything listed ships in Prod in 1.5.0, and the folder is held until then.
4. **Drift test: bytes, ignoring only `cliVersion`.** The test builds the payload in-process with every flag on, sets `cliVersion` to the committed file's value, encodes it with the same encoder `run()` uses, appends `"\n"` (what `print` adds) and compares bytes with the committed file. To make sure both paths use the same encoder settings, `run()`'s inline encoder moves into one helper (Files 1). `--json` output does not change.
5. **Generator: one stdlib Python script, `tools/build-cli-reference.py`, as the issue specifies**, with the #0682 SwiftPM pattern used only to *obtain* the JSON (decision 1). There is no new Swift executable target, because it couldn't import `batty`.

### Files

1. **`BattyKit/Sources/batty/CapabilitiesCommand.swift`.** Add `static func jsonText(_ payload: CapabilitiesPayload) throws -> String`, which holds the `JSONEncoder` with `[.prettyPrinted, .sortedKeys, .withoutEscapingSlashes]` and UTF-8 decoding now inline in `run()`. `run()` calls it in place of the inline encoder: same `guard`/`fputs`/`ExitCode.failure` behavior, same `print(text)`. No other change, and none to `buildPayload`/`verbs`/annotations.
2. **New `tools/build-cli-reference.py`** (stdlib, `python3 -I`, same layout and argparse style as `build-backgrounds-page.py`). Repo root comes from `Path(__file__).resolve().parent.parent`.
   - **Usage:** `build-cli-reference.py [--check] [--refresh-json (--cli-version X.Y.Z | --cli PATH)] [--json PATH] [--out DIR]`. Defaults: `--json website/docs/cli/capabilities.json`, `--out website/docs/cli`.
   - **`--refresh-json`** obtains the JSON per decision 1 (`subprocess.run([...], check=False, capture_output=True)`, exit 2 with stderr on failure). It validates that the result parses with `json.loads`, has `cliVersion`, `verbs`, `exitCodes` and `jsonSchemaDialect`, and that verb names are unique. It applies decision 2 and writes the bytes to `--json`. Then it renders.
   - **Default mode** renders `index.md` and `index.html` from the committed JSON and prints `wrote`/`unchanged` per file. Pages are written with a trailing `\n`, mode 0644.
   - **`--check`** renders in memory, writes nothing, prints each differing or missing file, and exits 1 with `run python3 -I tools/build-cli-reference.py to regenerate`. It exits 0 when everything matches. `--check` together with `--refresh-json` is a usage error (exit 2). `--check` never builds Swift: the JSON↔code link is the unit test's job.
   - **Rendering model** (shared by the two outputs, so they can't disagree):
     - Verbs are grouped by noun, meaning the first word of a multi-word `name`. Single-word verbs (`new`, `ping`, `status`, `list`, `id`, `notify`, `capabilities`, `mcp`) go in a first group headed "Top-level commands". Groups and verbs keep the JSON's order, which is the CLI tree order.
     - For each verb: the heading `` `batty <name>` ``, its abstract, aliases (omitted when empty), annotation hints as a short line (`read-only`, `destructive`, `idempotent`, `open-world`, listing the true ones; "none" when none are true), then a parameter table.
     - Parameter table columns: Parameter (the `names` joined by ", ", or `<name>` for `positional`), Kind (`cliKind`), Type, Required (`cliRequired`), Default, Allowed values (`enum`, with `enumValueNames` aliases in parentheses), Range (`minimum`–`maximum` when present), Description. Rows are sorted by property key for determinism. When there are no parameters, the text reads "No parameters." `conflicts` render as a bullet list of their `description` strings under the table.
     - Then the exit-code table (code, meaning), a line naming the `jsonSchemaDialect`, and a link to `capabilities.json`.
   - **`index.md`:** an H1 `Batty command-line reference`, the line `Generated from \`batty capabilities --json\`, Batty <cliVersion>. Machine-readable copy: [capabilities.json](capabilities.json).`, a short intro (run `batty capabilities --json` locally for the installed build's exact surface, and `batty-beta` in Batty Beta), then the groups with `##` noun and `###` verb headings. Pipes in table cells are escaped as `\|`. Links back to [Docs](../index.md).
   - **`index.html`:** the site's look, from the `backgrounds.html` skeleton: doctype, `<meta charset>`, viewport, `<title>CLI reference — Batty</title>`, description, favicon/icon links and `<link rel="stylesheet" href="../../css/style.css">`. It uses `<body class="page">`, a `page-header` with `<a class="back" href="../index.html">← Docs</a>` and the H1, and `<main class="prose">` with the same content as `index.md` (`<h2 id="noun-…">`/`<h3 id="verb-…">` with stable slug ids, `<table>`s). The footer is `backgrounds.html`'s nav with `../../` prefixes. It adds no "Docs" footer link (#0688 does that) and no og/twitter image tags. All text goes through `html.escape`. It must pass `tidy -e -q`. No new CSS unless a table needs it. If it does, add a small `.cli-reference table` rule to `website/css/style.css` (one stylesheet, per the site house rules).
   - Self-test hook: `render(payload: dict) -> dict[str, str]` and `apply_cli_version(text, version) -> str` are importable functions. `main(argv)` returns an exit code.
3. **New `tools/build-cli-reference-selftest.py`** (stdlib, follows `build-backgrounds-page-selftest.py`'s pattern of loading the script by path). It covers these cases:
   - A fixture payload with a top-level verb, a two-verb noun and a verb with every property field renders each verb exactly once in both outputs, grouped as described.
   - Pipe escaping in Markdown, and HTML escaping of `<`/`&`.
   - `apply_cli_version` replaces exactly one line, and exits or raises on zero or two matches.
   - `--check` exits 1 on a modified page and 0 on fresh output, using temp directories with `--json`/`--out`.
   - `--check` with `--refresh-json` exits 2.
   - `--cli` with `--cli-version` exits 2.
   - Duplicate verb names are rejected.
4. **New `website/docs/cli/capabilities.json`, `website/docs/cli/index.md` and `website/docs/cli/index.html`,** produced by `python3 -I tools/build-cli-reference.py --refresh-json --cli-version 1.5.0`. They are never hand-edited.
