## Resolution notes

> 🟢 Resolved 2026-11-12 — Session-selection side effects (focus, mark-seen, Theme, clipboard denial) now run in `WindowRuntime.selectedSessionID`'s `didSet` and the close/hide actions instead of in view `onChange` handlers flushed inside `NSHostingView.layout`; the per-switch layout request count barely moved, and that cost is filed separately.

## Description

**High priority. Related to #0601.** Every Session switch writes observed state from inside `NSHostingView.layout`, because the switch's side effects run in `SessionDetailView`'s `onChange(of: windowRuntime.selectedSessionID)` instead of in the code that changed the selection. #0601's layout probe measured about 450 `_postWindowNeedsUpdateConstraints` requests per converging Session switch with 4 Sessions and about 690 with 16, all from `ObservationGraphMutation.apply` flushed inside `NSHostingView.layout`. The selection `onChange` side effects account for about 155 of them. Requests are not passes, and the probe saw every switch converge, so this is not a proven loop. But it is the kind of layout-time write volume that sits next to AppKit's convergence cap, which #0601's Prod crash hit.

The user's direction: **views only react to observed state; state writes belong in the action that changes the selection (event origin), not in an `onChange` that reacts to it.** The goal is to move the side effects into the selection actions, cut the per-switch request count, and pin the lower count with a test.


## Root cause

Every Session switch ran its side effects from `SessionDetailView`: `.onChange(of: windowRuntime.selectedSessionID)` (and `.onAppear`) focused the selected Session's terminal, marked its active Tab seen, applied the Session Theme to its surfaces and the chrome, and denied the previous Session's pending clipboard request; `.onChange(of: …focusedPaneID)` and `PaneView`'s `.onChange(of: pane.activeTabID)` marked seen again on focus moves. SwiftUI flushes those handlers inside `NSHostingView.layout`, so each switch wrote observed state (Bell Feed entries, unseen counts, `themeChrome.palette`, `pendingClipboardConfirmation`) from inside AppKit's layout pass. `ThemeChrome.update(from:)` also wrote `palette` unconditionally, so even a switch between two Sessions with the same Theme invalidated every chrome-reading view.

**What the measurement showed:** these writes were only a small part of the per-switch layout request volume. With the side effects moved, a switch still issues 435-660 `_postWindowNeedsUpdateConstraints` requests (see Verification). The bulk of the per-switch cost is the selection change itself re-rendering every mounted Session's views (every Session stays mounted at `opacity(0)`), not the side effects or their timing. #0601's attribution of about 155 requests to the `onChange` side effects does not hold in this fixture: before the change they cost about 9 to 45 per switch. The orchestrator is filing that cost as a separate issue.

## Fix

The orchestrator chose to land the restructure on its own merits (the user's direction: writes belong in the action that changes the selection, views only react), with a loose regression guard instead of a tight ceiling, after the plan's 80-request bail point was hit.

- **One funnel.** `WindowRuntime.selectedSessionID`'s `didSet` now calls `applySelectionEffects(deselecting:)` after `applySelectionVisibility`: deny the previous Session's pending clipboard request (#0390 B3; a removed Session is skipped), focus the selected Session's `focusedPaneAnyKind.activeTab` through the new `focusTerminal` seam (production default `TerminalSurfaceFocuser.focusWhenReady`, which defers the responder change; no new `Task`), `markActiveTabSeen()` (passive, #0556), and `selectionThemeHandler` (installed by `AppStateStore.installWindowHooks`). Every production writer is event-origin, so the writes run synchronously in the action, outside SwiftUI's update.
- **Arrange first, select last** in `jumpToTab`, `jumpToBellEntry`, `addProjectSession`, `activatePaneFromSidebar`, `AppStateStore.focusPaneForXPC` and `focusTabForXPC`, so the effects see the final focused Pane and active Tab. Visit and event behaviour is unchanged. The `focusPaneForXPC` comment that called the order "not observable" is rewritten, and the `selectedSessionID` doc comment states the rule.
- **Theme.** `ThemeChrome.update(from:)` assigns the palette unconditionally, as on `main`; an equal palette doesn't re-notify because `ChromePalette` is `Equatable` and `@Observable` skips equal writes (round 2 removed a redundant guard that claimed otherwise). New `AppStateStore.applySelectionTheme(for:)` themes the selected Session's surfaces in whichever window changed and the chrome only when that window is `defaultTargetWindow()`. New `contentWindowBecameKey(_:)` (records the key window, then `applyChrome(for:)`), called by `handleWindowDidBecomeKey` and by `WindowLifecycleController`'s existing off-pass block when the window is already key. `applyThemeToAllSurfaces` and `applyGlobalThemeForCurrentAppearance` read the chrome Session from `defaultTargetWindow()` instead of the `windows[0]` shim. Behaviour change: with two windows, making the other window key re-chromes to its selected Session.
- **Passive focus moves.** New `notePassiveFocusMove(in:since:)` at the end of `closeTab`, `closeOtherTabs`, `closePane` and `hidePane`, on the branch where the Session survives. It goes through `passiveFocusHandler`, which marks only in the default target window (the policy of the former `AppStateStore.markActiveTabSeen()`, removed in round 2 with no production caller left). **Deviation from the plan:** it also requires that the Session is the selected one and that its focused Pane or active Tab actually moved (a before/after `focusSnapshot`). This matches the deleted `onChange` handlers, which fired only on a real change, and keeps closing a background Tab, or a Pane in another Session, from marking the selected Tab seen.
- **Views.** Deleted `SessionDetailView`'s `.onAppear` calls, both `onChange` handlers and `focusSelectedSessionTerminal()`, and `PaneView`'s mark-seen `onChange(of: pane.activeTabID)`. The two `focusWhenReady` handlers and the bell-flash handler in `PaneView` stay.
- **Build warnings.** The 4 warnings in changed files were pre-existing `#ImplicitStrongCapture` warnings in `PaneView`'s `.task(id: tab.id)` closure (inner `[weak appStore, weak pane]` / `[weak appStore, weak tab]` against an implicit strong outer capture). Fixed with an explicit outer capture list `[appStore, pane, tab]`; the inner weak captures still break the cycle through the stored callbacks.
- **Docs.** `docs/notifications.md` (mark-seen call sites and file table), `docs/pane-view-lifecycle.md` §5, `docs/swiftui-observation-rules.md` (worked example of "restructure which code owns the write"), `docs/themes.md` and `docs/ui-features.md` (chrome follows the default target window, `applySelectionTheme`).
- **No existing test needed changing.** The plan expected tests that write `selectedSessionID` directly and then assert a bell is still unseen to break; none did.

## Plan

Written 2026-11-12 against `issue/0602` at `9b299040`. Premises in "Current state" were checked in code and hold, with three additions found while planning:

- **`ThemeChrome.update(from:)` writes `palette` unconditionally** (`Theme/ThemeChrome.swift`). Every Session switch therefore invalidates every chrome-reading view in every window, even when the palette is unchanged. `ChromePalette` is already `Equatable`.
- **Several selection paths write the selection *before* they arrange the target Session's focused Pane and active Tab**: `jumpToTab`, `jumpToBellEntry`, `addProjectSession` (focused slot and hidden Panes after the write), `activatePaneFromSidebar`, `AppStateStore.focusPaneForXPC` and `focusTabForXPC`. Today that order is harmless because the side effects run later in `onChange` and see the final state. A model-side hook runs at the moment of the write, so these paths must arrange first and select last (step 2).
- **The initial focus is already covered without `SessionDetailView.onAppear`.** `PaneView`'s terminal `.onAppear` calls `focusWhenReady` for the focused Pane's active Tab of every Session it mounts (`isPaneFocused` is per tree, not per selection). A new window's only Session has no bells, no pending clipboard request and no Session Theme. So the only initial effect that needs a new home is the app-wide chrome for a new window that became key (step 4).

### Design: one funnel, `selectedSessionID`'s `didSet`

The side effects run in `WindowRuntime.selectedSessionID`'s `didSet`, after `applySelectionVisibility`, through one private method `applySelectionEffects(deselecting:)`.

Why the `didSet` and not one `select…` method that every path calls:
- Every write reaches it: the 12 production paths listed in "Current state", the `AppStateStore.selectedSessionID` shim, `UITestDriver`, and the about 100 direct `selectedSessionID =` writes in unit tests. A method would need `private(set)` to be enforced, which breaks all of those tests, and without it a new path can skip the effects silently.
- It has `oldValue`, which the #0390 B3 clipboard deny needs.
- It already is the documented choke point for selection visibility (#0349, `docs/pane-view-lifecycle.md` §5). The new effects follow the same rule.
- It runs synchronously in the writer's context. Every production writer is event-origin: sidebar `List` binding setter, menu and shortcut handlers, Command Palette and Open Quickly actions, Bell Feed clicks, XPC verbs, URL handler, `removeSession` and `openProject`. None runs in `body`, `onChange`, `onAppear` or geometry callbacks (grep of `Views/`, 2026-11-12).

The cost of the `didSet` is ordering: it fires on the write, not at the end of the action. Step 2 fixes that by making the write the last model edit in each path.

`applySelectionEffects(deselecting previousID: UUID?)` does, in this order:
1. **Clipboard deny (#0390 B3):** if `previousID` is still in `sessions` and has `pendingClipboardConfirmation`, call `cancelPendingClipboardConfirmation(pending)`. A removed Session is skipped, as today, where `store.session(id: old)` also misses it.
2. **Focus:** `selectedSession?.focusedPaneAnyKind.activeTab` → `focusTerminal(tab)`. Move the `focusedPaneAnyKind` comment (#0332 B4) from `SessionDetailView.focusSelectedSessionTerminal()` along with it. `focusTerminal` is a new `@ObservationIgnored var focusTerminal: (TabRuntime) -> Void = { TerminalSurfaceFocuser.focusWhenReady(tab: $0) }`. It is a test seam with the production default, so behaviour is unchanged. `focusWhenReady` only bumps a static, non-observed `generation` and starts its generation-guarded `Task`. No `makeFirstResponder` runs synchronously, which is the model-initiated direction `docs/swiftui-observation-rules.md` "Two-way model ↔ AppKit sync" prescribes. No new `Task` is added.
3. **Mark seen:** `markActiveTabSeen()`, the passive mark (#0556). It is not `visitFocusedTab()`, so `removeSession` reselecting a neighbour still only marks seen. The paths that are visits keep calling `visitFocusedTab()` after the write, as today. Running both is idempotent.
4. **Theme:** `selectionThemeHandler?(self)`, a new `@ObservationIgnored var selectionThemeHandler: ((WindowRuntime) -> Void)?` installed by `AppStateStore.installWindowHooks(on:)` next to the existing handlers. A bare `WindowRuntime` in a unit test has no theme work, as with the other handlers.

When `selectedSessionID` becomes nil (last Session removed), steps 2 to 4 find no Session and do nothing, the same as today's `applyActiveSessionTheme(for: nil)` early return.

### Multi-window theme rule

`themeChrome` is app-wide. **The chrome follows the selected Session of `defaultTargetWindow()`** (key content window, else most recently key, else newest registered, else `windows.first`; #0439). Terminal surfaces are per Session, so they are themed whichever window the selection changed in.

- New `AppStateStore.applySelectionTheme(for window: WindowRuntime)` (in `Theme/ThemePreference.swift`'s `AppStateStore` extension), plus an `isDark:` overload for tests like the existing ones. It resolves `ThemePreference.effectiveTheme(override: window.selectedSession?.themeOverride, …)`. If a theme results, it calls `applyTerminalTheme(theme, to: session)`. Then, only if `defaultTargetWindow() === window`, it calls `themeChrome.update(from: theme)` (nil resets, as today). This replaces what `applyActiveSessionTheme(for:)` did from the view. Keep `applyActiveSessionTheme(for:)`; the Sidebar's "Clear Session Theme" button and tests use it.
- **Key-window change hook:** new internal `AppStateStore.contentWindowBecameKey(_ id: WindowID)`, which calls `noteContentWindowBecameKey(id)` and then `applyChrome(for:)`. `applyChrome(for:)` is chrome only: `themeChrome.update(from:)` with that window's selected Session's effective theme. `handleWindowDidBecomeKey(_:)` (the app-wide `didBecomeKeyNotification` observer, event-origin) calls it instead of `noteContentWindowBecameKey` directly. The test calls `contentWindowBecameKey` directly, as `noteContentWindowBecameKey` is tested today, because `NSApp.keyWindow` can't be driven headlessly.

### User checklist (Batty Beta)

- Switch Sessions by Sidebar click, Cmd-1..9, Open Quickly, Bell Feed row and `batty-beta session focus`. Each time you can type into the new Session's terminal at once, with no click.
- Ring a bell in a background Session's non-focused Pane, then switch to that Session by Cmd-number: the bell on the focused Tab clears, and the bell on the other Pane stays.
- Give one Session a Session Theme and switch to and from it: the Sidebar and Tab bar chrome follow. With two windows whose selected Sessions have different Themes, clicking between the windows switches the chrome to the key window's Session (new behaviour).
- Cmd-N while the current Session has a Session Theme: the new window's chrome is the global Theme.
- Close a Tab or Pane so focus lands on a Tab with an unseen bell: it is marked seen in the key window. In a background window (CLI `pane close`), it stays unseen.
- A clipboard-read prompt (`printf '\e]52;c;?\a'`) left open while switching Sessions is denied, not left pending.

- **Chrome now follows the key window** (behaviour change), and `didBecomeKeyNotification` now writes `themeChrome`. - **Passive mark-seen in a non-key window narrows** (step 5) from "owning window" to "default target window" for close-driven focus moves.
- **The request drop may be smaller than #0601's 155 attribution**, because moved writes coalesce rather than disappear. The bail point covers this.

- `SplitContainerView.swift` `onGeometryChange` → `@State containerLength`. View-local, read only by divider-drag math.

**Event-origin and view-local (fine as they are):**

- `PaneView.swift` `onChange(of: pane.tabs.map(\.bellCount).reduce(0, +))` → `triggerBellFlash()` (the doc's own example of a routine event-origin flip), and `onChange(of: pane.activeTabID)` / `onChange(of: isPaneFocused)` → `TerminalSurfaceFocuser.focusWhenReady(tab:)` (deferred to a `Task`).
- `SettingsView.swift`: `fontSize`, `cursorStyle`, `cursorBlink` → `applyAppearance()`; the theme `selection` → applies the theme; `systemNotifications` → `store?.systemNotificationsSettingChanged()`; `capture` → `Task { await refresh() }`. All flipped by user input in the Settings window, not the main window. Moving them into the control bindings' setters would match the direction of this issue, but they are low-risk.
- Scroll-position and query-reset handlers in sheets and overlays: `CommandPaletteView`, `OpenQuicklyView`, `ThemeSelectorView` (two views), `RunningProcessPickerView`, `ProjectPickerView`, `ProjectSymbolPicker` (`cursor` → `syncSelection()`, `filter` → `reload()`, `isPresented` → focus), `ReminderSheet` (note truncation and `draft.choice = .custom`), `BackgroundImagesView` (`gridFocused`). All write view-local state from user input.

Out of scope here, but worth a later pass with the same lens: the `ReminderSheet` and `SettingsView` handlers, which could be binding setters.
