# 0602 — Session-selection side effects run as onChange state writes inside NSHostingView layout instead of in the actions that change the selection

| | |
|---|---|
| **Status** | open |
| **Module** | Session / Window |
| **Platform** | macOS |
| **First seen** | 2026-11-12 |
| **Priority** | high |

## Description

**High priority. Related to #0601.** Every Session switch writes observed state from inside `NSHostingView.layout`, because the switch's side effects run in `SessionDetailView`'s `onChange(of: windowRuntime.selectedSessionID)` instead of in the code that changed the selection. #0601's layout probe measured about 450 `_postWindowNeedsUpdateConstraints` requests per converging Session switch with 4 Sessions and about 690 with 16, all from `ObservationGraphMutation.apply` flushed inside `NSHostingView.layout`. The selection `onChange` side effects account for about 155 of them. Requests are not passes, and the probe saw every switch converge, so this is not a proven loop. But it is the kind of layout-time write volume that sits next to AppKit's convergence cap, which #0601's Prod crash hit.

The user's direction: **views only react to observed state; state writes belong in the action that changes the selection (event origin), not in an `onChange` that reacts to it.** The goal is to move the side effects into the selection actions, cut the per-switch request count, and pin the lower count with a test.

## Current state (verified 2026-11-12 on `main` `44405368`)

`BattyKit/Sources/BattyKit/Views/SessionDetailView.swift`, `configuredStack`:

- `.onAppear` calls `focusSelectedSessionTerminal()`, `windowRuntime.markActiveTabSeen()` and `store.applyActiveSessionTheme(for: windowRuntime.selectedSession)`.
- `.onChange(of: windowRuntime.selectedSessionID)` calls the same three, then (#0390 round 2, B3) cancels the previous Session's `pendingClipboardConfirmation` via `previousSession.cancelPendingClipboardConfirmation(pending)`.
- `.onChange(of: windowRuntime.selectedSession?.tree.focusedPaneID)` calls `windowRuntime.markActiveTabSeen()`.

What each side effect writes:

- `focusSelectedSessionTerminal()` (private, same file) calls `TerminalSurfaceFocuser.focusWhenReady(tab:)` (`Commands/TerminalSurfaceFocuser.swift`). That bumps the static `generation` and starts a `Task`, so the responder change itself is already off the layout pass.
- `WindowRuntime.markActiveTabSeen()` (`Runtime/WindowRuntime.swift`) calls `markSelectedSessionReminderEntriesSeen()`, marks Bell Feed entries seen via `bellFeed.markSeen(id:)` / `decrementUnseen(for:)`, and zeroes `unseenBellCount` on the Tab, Pane and Session. All observed.
- `AppStateStore.applyActiveSessionTheme(for:)` (`Theme/ThemePreference.swift`) calls `applyTheme(_:to:)`, which runs `applyTerminalTheme` and writes `themeChrome.update(from:)`, or `themeChrome.update(from: nil)` when there is no theme. `themeChrome` is app-wide, not per window.

`WindowRuntime.selectedSessionID` already has a model-side choke point: its `didSet` calls `applySelectionVisibility(deselecting:selecting:)` when the value changes. Every write below passes through it.

### Every path that changes the selection

In `WindowRuntime` (`Runtime/WindowRuntime.swift`):

- `addSession(...)` — `selectedSessionID = session.id` (New Session from `BattyCommands`, `BattyShortcuts`, the Sidebar "+" button and the Command Palette; and `AppStateStore.addSession(title:workingDirectory:)`, which `BattyURLHandler` calls for `batty new`).
- `addProjectSession(_:tree:background:)` — used by `AppStateStore.openProject`'s create branch.
- `removeSession(id:fromCli:)` — reselects a neighbour when the selected Session closes.
- `duplicateSession(id:)` — Command Palette, `AppStateStore.duplicateSession(id:)`.
- `selectSession(at:)` — Cmd-1..9 (`BattyShortcuts`, `BattyCommands`), `AppStateStore.selectSession(at:)`.
- `selectSessionFromSidebar(id:)` → `setSelectedSession(id:)` — the Sidebar `List` selection binding (`SessionSidebarView`), then `visitFocusedTab()`.
- `activatePaneFromSidebar(sessionID:paneID:)` → `setSelectedSession(id:)` — Sidebar Pane row tap.
- `setSelectedSession(id:)` — also called by `AppStateStore.openProject`'s focus-existing branch, `focusSessionForXPC`, `focusPaneForXPC`, `focusTabForXPC` (CLI focus verbs).
- `jumpToTab(sessionID:tabID:)` — Open Quickly (`OpenQuicklyView`), `AppStateStore.jumpToTab`.
- `jumpToBellEntry(_:)` and `jumpToReminderEntry(_:)` — Bell Feed clicks (`SessionDetailView`), `AppStateStore.jumpToBellEntry`, Reminders (`AppStateStore+Reminders.swift`).
- `init` sets it for the first Session (no `didSet` there, by Swift rules).

Outside `WindowRuntime`: `AppStateStore.selectedSessionID`'s setter (test/UI-test shim, `windows[0]`) and `UITestDriver` write it directly.

The Command Palette has no "switch to Session" command of its own today; it changes the selection through `addSession`, `duplicateSession` and the Open Project picker.

## Expected behavior

- The selection side effects (focus the selected Session's terminal, mark the active Tab seen, apply the active Session's theme, deny the old Session's pending clipboard confirmation) run in the action that changes the selection, synchronously and outside SwiftUI's update. A model-side hook every path reaches, such as `selectedSessionID`'s `didSet` next to `applySelectionVisibility`, or one `WindowRuntime` method that every path above calls, avoids repeating them at each call site. The plan picks one and says why.
- `SessionDetailView` no longer writes state in `onChange(of: selectedSessionID)`. The `focusedPaneID` `onChange` gets the same treatment where focus changes come from actions (see Notes).
- The per-switch `postNeedsUpdateConstraintsCalls` measured by `SessionDetailLayoutConvergenceTests`' probe drops, and a test pins the new count with a ceiling, so a regression that brings the writes back into layout fails.

## Notes

### Constraints for the plan

- Read `docs/swiftui-observation-rules.md` first; it is binding. Do not move any write into a `Task` to get it out of layout (the #0229 click regression). Moving it to the event-origin action is the fix.
- `themeChrome` is app-wide while `selectedSessionID` is per window. Today the chrome follows whichever `SessionDetailView` last fired its `onChange`. The plan must say which window's selection drives the theme in multi-window use (likely the key window, plus a key-window change hook), and keep `MultiWindow*` behaviour.
- `markActiveTabSeen` vs `visitFocusedTab` (#0556): `selectSessionFromSidebar` and `activatePaneFromSidebar` already call `visitFocusedTab()`, which removes Bell Feed rows. The `onChange` path only marks rows seen. Keep that split: moving `markActiveTabSeen` must not turn a passive selection (for example, `removeSession` reselecting a neighbour) into a visit that removes rows.
- The initial `onAppear` call handles a new window's first Session, where `init` sets `selectedSessionID` without `didSet`. That needs an event-origin home too (window registration or the window's first appearance in `WindowLifecycleController`), not a view `onAppear` write.
- The #0390 B3 clipboard deny must still see the *old* Session. A `didSet` has `oldValue`, so it fits there.
- `TerminalSurfaceFocuser.focusWhenReady` already defers to a `Task` with its own retry ladder, so calling it from the action does not call `makeFirstResponder` synchronously.

### Measurement

- `BattyKit/Tests/BattyKitTests/SessionDetailLayoutConvergenceTests.swift`, `sessionDetailTreeConvergesAcrossSizesAndSessionSwitches(extraSessions:)` (arguments `0` and `12`) switches with `fixture.windowRuntime.selectSession(at:)` and settles with `LayoutConvergenceProbe.settle()`. `SettleResult.postNeedsUpdateConstraintsCalls` is the count (`LayoutConvergenceProbe.swift`). Today it is only reported, not bounded (#0601 Verification).
- Add a test that records the per-switch `postNeedsUpdateConstraintsCalls` before and after, and asserts a ceiling on it (the new measured value plus a margin the plan justifies). The test's fixture must actually run the side effects: a Session with unseen bells and a Session theme override, so "fewer requests" is not vacuous because the side effects were no-ops.
- Keep the existing guards passing: `WindowRuntimeSessionSelectionVisibilityTests`, `WindowRuntimeOcclusionVisibilityTests`, the Bell Feed and #0556 visit tests, the #0390 clipboard tests, and the theme tests.

### Audit of other `onChange` / `onGeometryChange` / `onPreferenceChange` writes in `BattyKit/Sources/BattyKit/Views/`

39 sites across 14 files (grep, 2026-11-12). Classified by what flips the value and what the handler writes:

**Same problem as this issue (observed-model writes reacting to model state; move to the action):**

- `SessionDetailView.swift` `onChange(of: windowRuntime.selectedSession?.tree.focusedPaneID)` → `windowRuntime.markActiveTabSeen()`. `focusedPaneID` is written by focus actions, but also by first-responder promotion (the #0229/#0230 shape), so this one may be focus-origin. Audit who writes `focusedPaneID` and route the mark-seen through the writers.
- `PaneView.swift` `onChange(of: pane.activeTabID)` → `appStore?.markActiveTabSeen()`. Same shape for Tab switches inside a Pane: `activeTabID` is written by `PaneRuntime` (`addTab`, close, `selectNextTab`, `selectPreviousTab`, ...), the Tab bar selection binding in `PaneView`, `jumpToTab` and `jumpToBellEntry`.
- `RootWindowView.swift` `onChange(of: columnVisibility)` → writes `sidebarHidden` (`@SceneStorage`), and `onChange(of: sidebarHidden)` → writes `columnVisibility` under `withAnimation`. This is a two-way sync between view-local state, guarded by an equality check. It is not a model write, but it is a ping-pong pair; note it, don't change it here.

**Geometry-origin writes (the danger zone, already known):**

- `TerminalPlaceholderView.swift` `onGeometryChange` and `onChange(of: isVisible)` → `TerminalHostStore.shared.setPlacement(...)`. #0601 made this frame-only and guarded it with `terminalPlacementWriteMarksNoViewAsNeedingUpdateConstraints`; it is the documented exception in `docs/swiftui-observation-rules.md`.
- `PaneView.swift` `onGeometryChange` → `@State frameInSession`, `paneWidth`, `paneHeight`. View-local `@State`, which then feeds `.preference(key: PaneFramePreferenceKey.self, ...)`.
- `SessionDetailView.swift` `onPreferenceChange(PaneFramePreferenceKey.self)` → `session.paneFrames.frames = newFrames`. `PaneFrameTracker` (`Commands/PaneFocus.swift`) is not `@Observable`, so this does not notify. #0601 measured no count change from it.
- `SplitContainerView.swift` `onGeometryChange` → `@State containerLength`. View-local, read only by divider-drag math.

**Event-origin and view-local (fine as they are):**

- `PaneView.swift` `onChange(of: pane.tabs.map(\.bellCount).reduce(0, +))` → `triggerBellFlash()` (the doc's own example of a routine event-origin flip), and `onChange(of: pane.activeTabID)` / `onChange(of: isPaneFocused)` → `TerminalSurfaceFocuser.focusWhenReady(tab:)` (deferred to a `Task`).
- `SettingsView.swift`: `fontSize`, `cursorStyle`, `cursorBlink` → `applyAppearance()`; the theme `selection` → applies the theme; `systemNotifications` → `store?.systemNotificationsSettingChanged()`; `capture` → `Task { await refresh() }`. All flipped by user input in the Settings window, not the main window. Moving them into the control bindings' setters would match the direction of this issue, but they are low-risk.
- Scroll-position and query-reset handlers in sheets and overlays: `CommandPaletteView`, `OpenQuicklyView`, `ThemeSelectorView` (two views), `RunningProcessPickerView`, `ProjectPickerView`, `ProjectSymbolPicker` (`cursor` → `syncSelection()`, `filter` → `reload()`, `isPresented` → focus), `ReminderSheet` (note truncation and `draft.choice = .custom`), `BackgroundImagesView` (`gridFocused`). All write view-local state from user input.

Out of scope here, but worth a later pass with the same lens: the `ReminderSheet` and `SettingsView` handlers, which could be binding setters.
