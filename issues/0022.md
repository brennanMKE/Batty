## Description

Make `TerminalSurfaceNSView` a drag destination for file URLs. When the user drops one or more files from Finder (or any source producing file URLs), insert their POSIX-quoted paths at the cursor, space-separated, with a trailing space (PRD §6.12). This is a hard-required v1 feature — it's how the user shares screenshots/videos with Claude Code.

**Acceptance criteria:**
- `TerminalSurfaceNSView.registerForDraggedTypes([.fileURL])` is called.
- `draggingEntered`, `draggingUpdated`, `prepareForDragOperation`, `performDragOperation`, `draggingExited` are implemented.
- On a successful drop, file URLs are extracted from the pasteboard and converted to POSIX-quoted shell paths via a small `shellQuote(_ path: String) -> String` helper.
- The resulting string (paths space-separated with trailing space) is fed into the surface via `ghostty_surface_text(...)` — same entry point as paste.
- Confirmed manually: dropping a screenshot named like `Screenshot 2026-05-08 at 12.34.56.png` (with U+202F) inserts a single-quoted path that, when Enter'd, the shell can `cat`/`open`/etc. successfully.

## Notes

- POSIX shell quoting: prefer single-quotes and escape internal single-quotes via `'\''`. Don't try to be clever about backslashes — single-quoting handles everything.
- libghostty has no concept of drag-and-drop; this is entirely AppKit-level.
- Browser-dragged URLs (Safari) are **out of scope** for v1 (PRD §6.12) — only `.fileURL` types.
- Drag-over highlight is #0023.

## Revised approach — 2026-05-08

With `GhosttyTerminal` providing `TerminalView` (an `NSView` typealias) and `TerminalSurfaceView` (the SwiftUI wrapper), there's no longer "our own NSView" to register drag-drop on. Two viable paths:

1. **Subclass `TerminalView` (`AppTerminalView`)** in `BattyKit` and add `NSDraggingDestination` conformance there. Override `registerForDraggedTypes`, `draggingEntered`, `performDragOperation`, and emit text via `terminalView.surface?` or whatever GhosttyTerminal exposes for sending text. Use the subclass instead of the bare `TerminalView` in our SwiftUI hierarchy.
2. **Wrap `TerminalSurfaceView` in a SwiftUI overlay** that uses `.onDrop(of: [.fileURL], …)` modifier. Simpler, but the drop target sits *over* the terminal and intercepts events; need to check it doesn't block keyboard focus.

Path 2 is cleaner and aligns with "use what's available." Try it first; fall back to subclassing if the overlay interferes with focus / mouse events.

For text injection, `GhosttyTerminal` likely exposes a `send(_:)` or similar on its surface controller. If not, drop down to `BattyKit`'s re-exported `GhosttyKit` and call `ghostty_surface_text(surface, ...)` against the underlying `ghostty_surface_t` if the wrapper exposes it.

**Revised acceptance criteria:**
- File-URL drop on a terminal pane inserts POSIX-quoted paths via whatever `send-text` API `GhosttyTerminal` exposes (or `ghostty_surface_text` directly if needed).
- Implementation lives in `BattyKit` so it composes with `TerminalSurfaceView` cleanly.
- Verified manually with a screenshot drop from Finder containing `Screenshot 2026-05-08 at 12.34.56.png` (U+202F narrow no-break space test).

### Deferred — 2026-05-08

GhosttyTerminal's `TerminalSurface.sendText(_:)` is **internal**, not public. Same applies to the underlying `ghostty_surface_t` handle — no public accessor on `TerminalViewState` or `TerminalController`. There is no path to inject text into a running surface from BattyKit's side without one of:

1. **Subclass `AppTerminalView`** and reach into `superclass.surface` via internal-access tricks (Swift won't let us; the property is internal).
2. **Wrap `TerminalView` ourselves** in a custom `NSViewRepresentable` and bypass `TerminalSurfaceView` entirely. We'd lose what `TerminalSurfaceView` provides for free (Metal sizing, IME, key events, the @Observable state) unless we re-implement the bridging.
3. **Open an upstream PR** to make `TerminalSurface.sendText` public, or add a `TerminalController.sendText(_:)` / `TerminalViewState.send(_:)` shim.

Option 3 is the right long-term fix — same shape as the delegate plumbing gap from `#0016` / `#0024`. Deferring this issue and the same group (#0023, #0024, #0025, #0026, #0027, #0028, #0035, #0036's close-confirm half) until the upstream story for "host code can send text and observe more delegate events" is settled.

In the meantime, the user can paste with Cmd-V (system clipboard works through GhosttyTerminal's built-in handling), so file paths are usable manually after a copy.

## Root cause

Two-part gap:

1. No public path from a SwiftUI consumer to inject text into a running surface — `TerminalSurface.sendText(_:)` was `internal` and `TerminalViewState` had no `send` forwarder. Closed by #0044.
2. `TerminalSurfaceView` (the SwiftUI wrapper from GhosttyTerminal) doesn't expose `NSDraggingDestination` itself, so the AppKit-style "register the view as a drop target" approach wasn't reachable from BattyKit code.

## Fix

Path 2 from the original revised approach: a SwiftUI `.onDrop` overlay layered onto `TerminalSurfaceView` inside `PaneView`. The overlay only activates on the active tab so background tabs in a multi-tab pane don't intercept drops.

- `BattyKit/Sources/BattyKit/ShellQuote.swift` — `ShellQuote.posix(_:)` single-quotes the path and escapes any internal single-quote via the standard `'\''` dance. `ShellQuote.joinPaths(_:)` returns `"'a' 'b' "` (note the trailing space so the user can keep typing without a separator step).
- `PaneView.handleFileDrop(_:into:)` — kicks off a `Task { @MainActor }` that loads each `NSItemProvider`'s file URL via `withCheckedContinuation`, preserves drop order, and finally calls `terminal.send(joined)`. Loading is sequential — typical drops are 1–5 files, and crossing actor boundaries via a `TaskGroup` would have been more concurrency machinery than the use case warrants and immediately tripped Swift 6 sendable diagnostics on `NSItemProvider`.
- `BattyKit/Tests/BattyKitTests/ShellQuoteTests.swift` — covers plain paths, embedded single quote escaping, the U+202F narrow-no-break-space case from macOS Screenshot/Recording filenames, and the empty/single/multi `joinPaths` cases.

## Files changed

- `BattyKit/Sources/BattyKit/ShellQuote.swift` (new) — POSIX single-quoting helper with multi-path joiner.
- `BattyKit/Sources/BattyKit/PaneView.swift` — `import UniformTypeIdentifiers`; `.onDrop(of: [.fileURL], ...)` per `TerminalSurfaceView`, gated on active tab; `handleFileDrop` / `loadFilePaths` / `loadFilePath` static helpers that bridge the synchronous `.onDrop` return to async URL loading.
- `BattyKit/Tests/BattyKitTests/ShellQuoteTests.swift` (new) — 7 tests covering the quoting edge cases.

## Gotchas

- **`.onDrop` returns `Bool` synchronously, but `NSItemProvider.loadItem` is async.** The `Task { @MainActor }` returns control immediately; the actual `terminal.send` happens once the providers resolve. Returning `true` from `.onDrop` is what tells AppKit "I accept this drop"; the visible insert lags by however long item-loading takes (typically <50ms for local files).
- **Sequential vs parallel loading.** First attempt used `withTaskGroup` for parallel loading. Swift 6 strict concurrency under `defaultIsolation(MainActor)` flagged `NSItemProvider` as task-isolated when sent into a group task — the diagnostic is real (NSItemProvider isn't `Sendable`). Sequential loading sidesteps the issue and is fine for the typical 1–5-file drop. If drag performance becomes an issue with large drops, the right fix is a single off-actor helper that takes `[NSItemProvider]` and returns `[String]` — not a per-provider task group.
- **Drop ordering follows the providers' array order, not the visual order on the source side.** SwiftUI's `.onDrop(perform:)` provides `[NSItemProvider]` in pasteboard order, which Finder generally preserves as the user-selected order. Tested by hand once UI sign-off lands.
- **Paste-confirmation (#0035) is unaffected.** `terminal.send(_:)` injects directly via `ghostty_surface_text` — the same entry point that paste uses inside libghostty. When #0035 lands, dropped multi-line content (rare for file paths but possible) should be subject to the same confirmation; that wiring belongs in #0035, not here.
- **Drag-over highlight (#0023) is intentionally not implemented here.** `.onDrop(isTargeted: nil)` means we don't observe the targeted state; that's the next issue's job. When #0023 lands it'll switch to `isTargeted: $isDragHovering` and add a visual treatment.
- **Browser-dragged URLs (Safari, etc.) intentionally don't work.** `[.fileURL]` filters out non-file URL providers per PRD §6.12. If we ever want to allow text URLs (Safari's `public.url`), that's a follow-up after a small UX decision (just paste the URL string? prefix with `curl -O`? always file-prompt?).
