## Description

#0529 moved the SIGTERM → SIGKILL grace period of `LMStudioDashboardPaneContent` and `PendingTeardownReapRegistry` onto an injected `SchedulingClock`, through the new `TeardownReaper` (`reap` / `reapBlocking`). It deliberately left two things on real time and named them as follow-ups in its Plan and Resolution notes. They share one fix (adopt `TeardownReaper` with an injected clock), so they are filed together:

1. **`ProcessGitStatusScanner` still has its own `reapAfterTerminate`**, which measures the grace period with `Date()` and `Thread.sleep`. Its three SIGTERM-ignoring tests wait out the full bound in real time, and two of them do it on the main thread.
2. **`PendingTeardownReapRegistryTests` still register with the default `SystemClock()`**, so their drains wait out the real 0.2 s bound per entry, on the main thread.

Line numbers below are at `issue/0529` tip `d7fbc2df`, which is the code that will be on `main` once #0529 is squash-merged. The scanner and the registry tests are unchanged by #0529 apart from one doc comment.

## Current state (measured 2026-10-19)

### 1. `ProcessGitStatusScanner` (`BattyKit/Sources/BattyKit/Runtime/GitStatusPaneContent.swift`)

- `reapAfterTerminate` (`:349–369`) polls `process.isRunning` with `Thread.sleep(forTimeInterval: 0.01)` until a wall-clock `Date()` deadline of `bound` (`:350–353`), sends `SIGKILL`, then polls again for up to `min(bound, 0.5)` (`:360–363`). This is the same shape as `TeardownReaper.reap`, but its own copy; its doc comment (`:335–348`) now says so.
- Callers: the detached reap task in `scheduleTeardownReap` (`:371–394`, call at `:381`), and the synchronous quit path `waitForPendingTeardownSynchronously()` (`:329–334`, call at `:332`), which runs it on the calling thread.
- `scheduleTeardownReap` registers with the registry without a clock (`:376`, `registry.register(process:label:bound:)`), so a registry drain of a scanner entry also uses the real `SystemClock()`.
- `ProcessGitStatusScanner.init` (`:272`) takes `teardownWaitBound`, `teardownReapRegistry` and `reapGate`, but no clock.

### 2. `PendingTeardownReapRegistryTests` (`BattyKit/Tests/BattyKitTests/PendingTeardownReapRegistryTests.swift`)

- `register(process:label:bound:clock:)` already takes a clock after #0529 (`PendingTeardownReapRegistry.swift:70`, default `SystemClock()`), and `drainSynchronously()` (`:106`) runs each entry through `TeardownReaper.reapBlocking(… clock: entry.clock …)` (`:114`), one after the other.
- The tests don't pass a clock: `drainSynchronouslyKillsAndReapsARegisteredSigtermIgnoringProcess` (`:80`, register at `:95`, `bound: 0.2`) and `drainSynchronouslyReapsEveryRegisteredEntryIndependently` (`:109`, register at `:127`, `bound: 0.2`). The drains run sequentially, so the second test waits about 2 × 0.2 s. The struct is main-actor isolated by default, so `drainSynchronously()` blocks the main thread for that time.

Measured with `cd BattyKit && swift test --filter <test>`, alone, 3 runs each (worktree at `issue/0529`):

- `drainSynchronouslyKillsAndReapsARegisteredSigtermIgnoringProcess`: 0.240 / 0.255 / 0.238 s
- `drainSynchronouslyReapsEveryRegisteredEntryIndependently`: 0.458 / 0.468 / 0.474 s
- The whole suite (5 tests): 0.788 / 0.766 / 0.779 s

### Why it matters

- `AGENTS.md` "Asynchronous tests (binding)": timed work is "driven through an injected clock or scheduler the test advances explicitly, not by letting real time pass".
- Four of these five tests block the main thread for the grace period. #0528 found that main-actor blocking by `@MainActor` tests is what stretches every other test's reported duration in the full suite, and named `ProcessGitStatusScannerTests` as one of the blockers.

## Expected behavior

- `ProcessGitStatusScanner`'s private `reapAfterTerminate` is gone. The detached reap uses `TeardownReaper.reap` and the quit path uses `TeardownReaper.reapBlocking`, with an injected `SchedulingClock` (default `SystemClock()`), passed to `registry.register(…, clock:)` as well. This follows the `LMStudioDashboardPaneContent.teardownClock` pattern from #0529.
- Production behavior is unchanged: the 0.3 s default bound, the `SIGKILL` escalation, the bounded post-`SIGKILL` wait, and the `teardown:` log lines and Console category.
- The three scanner tests and the two registry tests inject a `TestClock` and advance it past the bound, with the same driver-task pattern #0529 used for the synchronous paths (`docs/async-test-seams.md` §1). They keep their real SIGTERM-ignoring children and readiness handshakes.
- Coverage is not weakened: each test still proves the child is `SIGKILL`ed and reaped (`kill(pid, 0) != 0` where it checks today), the closed-gate proofs stay, and at least one scanner test proves the child is still alive while the grace sleeper is pending (the "a grace period exists" check #0529 added for LM Studio).
- No new sleeps, polls or timing assertions in tests.

## Acceptance criteria

- `grep -rn reapAfterTerminate BattyKit/Sources` finds nothing.
- The five tests above no longer spend their bound in real time. Record before/after `swift test --filter` numbers against the baselines above.
- Mutation checks: skipping the `SIGKILL`, or sending it without waiting for the bound, makes a scanner test fail.
- `./build.sh unit` passes. Don't claim a suite-wide win from per-test durations (#0528).
