## Description

#0529 moved the SIGTERM → SIGKILL grace period of `LMStudioDashboardPaneContent` and `PendingTeardownReapRegistry` onto an injected `SchedulingClock`, through the new `TeardownReaper` (`reap` / `reapBlocking`). It deliberately left two things on real time and named them as follow-ups in its Plan and Resolution notes. They share one fix (adopt `TeardownReaper` with an injected clock), so they are filed together:

1. **`ProcessGitStatusScanner` still has its own `reapAfterTerminate`**, which measures the grace period with `Date()` and `Thread.sleep`. Its three SIGTERM-ignoring tests wait out the full bound in real time, and two of them do it on the main thread.
2. **`PendingTeardownReapRegistryTests` still register with the default `SystemClock()`**, so their drains wait out the real 0.2 s bound per entry, on the main thread.

Line numbers below are at `issue/0529` tip `d7fbc2df`, which is the code that will be on `main` once #0529 is squash-merged. The scanner and the registry tests are unchanged by #0529 apart from one doc comment.

### Why it matters

- `AGENTS.md` "Asynchronous tests (binding)": timed work is "driven through an injected clock or scheduler the test advances explicitly, not by letting real time pass".
- Four of these five tests block the main thread for the grace period. #0528 found that main-actor blocking by `@MainActor` tests is what stretches every other test's reported duration in the full suite, and named `ProcessGitStatusScannerTests` as one of the blockers.

The detached reap uses `TeardownReaper.reap` and the quit path uses `TeardownReaper.reapBlocking`, with an injected `SchedulingClock` (default `SystemClock()`), passed to `registry.register(…, clock:)` as well. ## Root cause

#0529 moved the grace period of `LMStudioDashboardPaneContent` and `PendingTeardownReapRegistry` onto an injected `SchedulingClock` through `TeardownReaper`, but `ProcessGitStatusScanner` kept its own `reapAfterTerminate` (wall-clock `Date()` deadline, `Thread.sleep` polls), and `PendingTeardownReapRegistryTests` registered with the default `SystemClock()`. All five SIGTERM-ignoring tests therefore waited out the real bound.

## Fix

- `ProcessGitStatusScanner` gains an init-injected `teardownClock: SchedulingClock = SystemClock()`. `scheduleTeardownReap` passes it to `registry.register(…, clock:)` and runs `await TeardownReaper.reap(…, clock:, logger:, logPrefix: "teardown")` in its detached task; `waitForPendingTeardownSynchronously()` calls `TeardownReaper.reapBlocking(…)`. `reapAfterTerminate` is deleted (`grep -rn reapAfterTerminate BattyKit/Sources` is empty). The production caller (`GitStatusPaneContent.init`'s default scanner) keeps the real clock.
- As planned, the "did not exit within bound; sending SIGKILL" log moves from `.warning` to `.error`, matching `TeardownReaper`. Exit poll is now 20 ms, not 10 ms.
- Tests inject `TestClock` and advance by exactly the bound: the scanner's deferred-reap test checks no sleeper while the gate is closed, a sleeper after opening, the child still alive before the advance, dead after. The quit-path test now uses a closed gate and a fresh registry, so only the synchronous path can reap, driven from a detached task while the main actor blocks. The registry tests use one-step and (sequential) two-step drivers.
- Docs: `TeardownReaper` doc, `docs/async-test-seams.md` §1 (scanner and five proving uses) and §3 (code sample and mutation name).
