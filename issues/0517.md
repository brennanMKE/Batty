# 0517 — A Project's symbol and color are limited to 36 curated SF Symbols and the 10-color Session palette

| | |
|---|---|
| **Status** | open |
| **Module** | Projects / Session / Sidebar |
| **Platform** | macOS |
| **First seen** | 2026-10-16 |

## Description

Feature request. The Project Editor only offers a fixed set of 36 SF Symbols and the 10 `SessionColor` swatches. The user wants to pick **any** SF Symbol, through a picker that filters by name, and **any** color, through the standard macOS color picker.

## User request (2026-10-16, verbatim)

> I'd like to update the Projects feature to support selecting any SF Symbol and color. What I want to do is include a button which brings up a picker for the SF Symbols which allows me to filter by name. For colors bring up the standard color picker UI.

## Current state (verified on main `380528e1`)

**Symbol.** `ProjectSymbol` (`BattyKit/Sources/BattyKit/Model/ProjectSymbol.swift`) is an append-only `String` enum of 36 cases. Its raw value is a stable key (`folder`, `ai`, `macApp`, ...), **not** the SF Symbol name, and that key is what gets persisted. `systemName` maps each key to an SF Symbol name. `resolvedSystemName` falls back to `folder.fill` when the running OS doesn't ship the name, checked with `NSImage(systemSymbolName:accessibilityDescription:)`. The editor field is `ProjectSymbolPicker` (`Views/ProjectSymbolPicker.swift`), a button that opens a popover with a 6x6 `LazyVGrid` of `ProjectSymbol.allCases`. `ProjectSymbolGridCursor` drives the arrow keys, and the field owns the keyboard while the popover is up, because the popover window does not reliably become key. There is no name filter.

**Color.** `Project.color` is a `SessionColor` (`Runtime/SessionColor.swift`). That is the fixed 10-case `Int` palette (Radix scale-9 hexes, #0335), also append-only. `ProjectColorSwatches` (`Views/ProjectEditorView.swift`, about line 423) draws the 10 swatches with left and right arrow stepping.

**Persistence (`projects.json`, version 1).** `Project.encode` writes `"color": <Int raw>` and `"symbol": "<key>"`. `Project.init(from:)` is lenient: an unknown or non-`Int` color decodes to `.blue`, and an unknown or non-string symbol decodes to `.folder`. Both log an error and keep the Project (covered by `ProjectSymbolTests`).

**iCloud sync.** `ProjectSyncRecord` (`Model/ProjectSync.swift`) carries `color: SessionColor` and `symbol: ProjectSymbol`. It uses the **synthesized** `Codable`. `ICloudKeyValueProjectSyncBackend.decode` uses `try?`, so a record with an unknown color raw or symbol key fails to decode as a whole and is treated as absent on that Mac. The record is not decoded with a fallback.

**Every reader of the symbol:**
- the Sidebar row, through `SessionRuntime.projectSymbol`, `SessionSidebarView.systemName(projectSymbol:)`, the row accessibility value, and `AppStateStore.applyProjectSymbol(of:)` on save
- the Open Project picker cards (`ProjectPickerView.swift`, two sites, about lines 373 and 522) and `ProjectPicker`'s card model
- the Project Editor list row and the Symbol field
- the File menu's Projects list (`ProjectFileMenu`, `BattyCommands.swift:120`)
- Open Quickly Project rows (`OpenQuicklyView.swift:400`)
- `ProjectDraft`, `ProjectEditorListEntry` and `ProjectSyncRecord`

**Every reader of the color:**
- `WindowRuntime.addProjectSession` seeds the Session's `colorIndex: project.color.rawValue` and calls `setSessionColor(id:to:)`. `setSessionColor` rejects any index outside `SessionColor.allCases`.
- `SessionRuntime.colorIndex: Int` / `sessionColor` tints the Sidebar row icon. The same palette drives `WindowRuntime`'s least-used round-robin assigner and the per-Session `SessionColorPickerView` (#0336).
- `SessionProjectCapture` (Save Session as Project) captures `session.sessionColor` into the new Project.
- the picker cards, the editor list row, the Symbol field tint, Open Quickly rows, `ProjectDraft` and `ProjectSyncRecord`.

**CLI / XPC / schema.** Neither appears there. `ProjectListEntry` (`BattyXPCCore/ProjectPayload.swift`) has only `id`, `name`, `rootPath`, `paneCount` and `isOpen`. `batty project` (`Sources/batty/ProjectCommand.swift`) has no color or symbol option, and no JSON schema mentions either. No CLI change is needed unless the implementer chooses to add one, which is out of scope here.

**Feature flag.** The Projects flag was removed by #0504 (resolved), and Projects shipped in `v1.3.0` (`release/1.3` exists). This work is new feature work on `main` for the next minor. Per AGENTS.md "Release branches", it must stay behind a feature flag until the release that ships it. With the flag off, the editor shows today's curated grid and 10 swatches. Note that a flag-off build may still **read** Projects written by a flag-on build (see Backward compatibility).

## Expected behavior

1. **Symbol button and picker.** The Project Editor's Symbol field stays a button showing the current symbol, tinted in the Project color. It opens a picker (sheet or popover) with:
   - a name filter field, focused on open, that does case-insensitive substring matching on the SF Symbol name (for example `flame` matches `flame`, `flame.fill`, `flame.circle`);
   - a scrollable, lazily built grid of matching symbols. It shows the symbol name on hover or help, and the selected symbol is marked;
   - keyboard operation equal to today's: arrows move, Return or Space chooses, Escape cancels. Focus returns to the field on close. Keep the existing `project-editor.symbol` / `project-editor.symbol.chip` accessibility identifiers, or update `BattyUITests/ProjectsSymbolTests.swift` to match;
   - optionally, the 36 curated symbols shown as a "Suggested" section when the filter is empty.
2. **Any SF Symbol.** macOS has **no public API to enumerate SF Symbols**, so the implementer must ship a name list. The likely approach is a bundled resource in BattyKit, such as a plain-text or JSON list of names generated from the SF Symbols app or its catalog. At load, filter it through `NSImage(systemSymbolName:accessibilityDescription:)`, so that only symbols the running OS (15.6+) actually draws are offered. Record in the issue how the list was produced and how to regenerate it. Do not read private system bundles (`CoreGlyphs`) at runtime.
3. **Any color.** The color control uses the standard macOS color panel, either SwiftUI `ColorPicker` (which drives `NSColorPanel`) or `NSColorPanel` directly. Any opaque color can be stored. Whether the 10 palette swatches stay next to it as quick picks is an open question below; keeping them is the recommended default.
4. **Arbitrary values everywhere.** Every reader listed above draws the chosen symbol and color. That includes the Sidebar row of a Session opened from the Project and the Sidebar row updated on save through `applyProjectSymbol`.
5. **Graceful fallback.** A stored symbol name the running OS doesn't ship draws `folder.fill`, as `resolvedSystemName` does today. A color that can't be read falls back to the default.

## Backward compatibility (decide, then record the decision here)

- **Old files must load unchanged.** A `projects.json` with `"symbol": "<key>"` and `"color": <Int>` keeps decoding to the same symbol and color. The legacy keys must map to their SF Symbol names, for example `ai` to `sparkles`. Don't reinterpret a legacy key as an SF Symbol name. Some keys happen to equal real symbol names, such as `network`, `link`, `checklist` and `calendar`. Others name a different glyph: the `folder` key draws `folder.fill`, and `map` draws `map.fill`.
- **Downgrade and older-peer safety, flagged as the main design decision.** Shared Projects sync through iCloud to Macs that may still run 1.3.x, and a user may also downgrade.
  - If the new values replace the existing `symbol` and `color` keys (for example `"symbol": "flame.fill"`, or a hex string in `color`), a 1.3.x `Project` decoder silently falls back to `folder` and `.blue`. Its next save then **overwrites** the user's choice.
  - Worse, a 1.3.x `ProjectSyncRecord` decode **fails outright**, so the shared Project disappears on that Mac.
  - Recommended direction: keep writing the legacy `symbol` and `color` keys with the nearest legacy value (`folder` and the nearest palette entry, or the exact entry when one was picked). Add new optional keys, for example `symbolName: String` and `customColor: "#RRGGBB"`, that take precedence when present. 1.3.x ignores the new keys on decode. A 1.3.x save still drops them, which is acceptable and should be documented.
  - Apply the same approach to `ProjectSyncRecord`. Keep `projects.json` at `version: 1` unless the implementer finds a reason to bump it. A bump makes 1.3.x keep the original file "until the next save" (`ProjectStore` load).
- **Session color relationship, flagged.** A Project applies its color to the Session it opens, but `SessionRuntime.colorIndex` is an index into the 10-color palette. `setSessionColor` rejects anything else, and the round-robin assigner, `SessionColorPickerView` and `SessionProjectCapture` all assume the palette. Options:
  - (a) Give `SessionRuntime` an optional custom color, with an RGB override, that wins over `colorIndex` for drawing. The assigner keeps counting palette indices, and the Session color picker's "Automatic" or palette choice clears the override. This is the recommended option.
  - (b) Snap the Project's custom color to the nearest palette entry for the Session. This contradicts the request.

  Whichever is chosen, Save Session as Project must round-trip a custom Session color back into the Project.
- **CLI and schema.** No change is needed today, because nothing exposes symbol or color there. If `batty project list --json` later grows these fields, it should expose the SF Symbol name and a hex color, not internal keys.

## Constraints

- Feature-flagged per AGENTS.md "Release branches": on in Beta, off in Prod. With the flag off there is no new UI. A flag-off build must still decode files written with the new keys without losing them. Use the encode approach above.
- `docs/swiftui-observation-rules.md` is binding for the picker:
  - Filter text, cursor and presentation state are view-local `@State`.
  - Draft writes go through `ProjectEditorViewModel` setters, from event handlers only, never from `body`, `onChange` of layout-origin values, or a representable update.
  - The `ColorPicker` binding's `set` must not write an equal value back into the `@Observable` draft on every panel tick. `@Observable` notifies even on equal writes.
  - Don't call `NSColorPanel` / `makeFirstResponder` APIs synchronously from SwiftUI update callbacks.
- Filtering a several-thousand-name list must stay responsive. Build the validated list once, off the per-keystroke path, and render the grid lazily.
- Localization: the symbol list is SF Symbol names, which are not localized. The new UI strings go in the string catalog.

## Acceptance criteria

- [ ] The Symbol button opens a picker with a name filter field. Any SF Symbol available on the running OS can be found by name and chosen, by mouse or keyboard.
- [ ] The color control opens the standard macOS color panel, and the chosen arbitrary color is stored and drawn.
- [ ] The Sidebar row of a Session opened from the Project, the picker cards, the editor list, the File menu and Open Quickly all show the chosen symbol and color.
- [ ] A 1.3.0-format `projects.json` loads with identical symbols and colors, and saving it without edits leaves the legacy keys intact.
- [ ] A Project with custom values decodes on the legacy decoders, simulated in tests by decoding with only the legacy keys, into the documented fallback instead of being dropped. A `ProjectSyncRecord` with custom values also decodes on a legacy-shaped decoder.
- [ ] Unit tests (`./build.sh unit`) cover:
  - round-tripping a custom symbol name and color;
  - legacy key to SF Symbol name mapping for all 36 cases;
  - unknown or unavailable symbol name fallback;
  - malformed color fallback;
  - sync-record round trip and old-peer decode;
  - Session custom-color application and Save Session as Project round trip;
  - the symbol catalog loader filtering out names `NSImage` rejects.
- [ ] Hidden behind the feature flag in Prod builds.
- [ ] UI tests in `ProjectsSymbolTests` still pass in the Tart VM, or are updated with the new identifiers.

## Open questions

1. Keep the 10 palette swatches as quick picks next to the color panel button, or replace them entirely? Recommended: keep them.
2. Show the 36 curated symbols as a "Suggested" section when the filter is empty? Recommended: yes.
3. Should the per-Session color picker (`SessionColorPickerView`, #0336) also gain the system color panel, for symmetry? Out of scope unless the user asks.

## Notes

- `ProjectSymbol`'s doc comment says that the raw value being a key rather than the SF Symbol name is deliberate, so that `systemName` can change without a migration. A free-form symbol name gives that up for custom picks. That is why the recommendation keeps the legacy key alongside the name.
- The `SessionColor` doc comment says the palette is append-only because `Project` persists the raw value. That stays true under the recommended approach.
