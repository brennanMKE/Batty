## Description

> **Decision (user, 2026-11-04), replacing "goes into Settings":** "Implement the image manager as a separate window much like Layouts and Projects so users can see a thumbnail of each image. It can also double as a picker when the user is selecting or adding an image to a terminal pane."

Batty keeps its own copies of background images in three folders with three cleanup rules, and nothing shows the user what it holds, what each image is used for or how much space they take. A separate window should show them, and the same content is what the user picks from when choosing an image for a Pane, Session, Project or the app-wide default. Child of [#0372](0372.md).

The first report said "We probably need an image manager which goes into Settings." It also said this depends on [#0551](0551.md). **Neither stands:** it is a window, and it doesn't wait for #0551 (see "What #0551 adds later" in the Plan).

**Main only, not 1.3.5.** 1.3.5 is a patch that is close to shipping. This lands on `main` and ships in the next minor release.

### Decisions

| Question | Decision | Why |
|---|---|---|
| Which window is the model | `ProjectEditorWindowController`'s shape: an AppKit `NSWindow` created on demand, process-global, never registered as a content window. **Not a `Window` scene.** | A declared scene always exists and would sit in the Window menu while closed (the controller's own doc comment). Cmd-W already works: `closeAuxiliaryWindow` covers any titled unregistered window. **Layouts isn't a window** (see "Premises corrected"); from it the plan takes the thumbnail grid and its keyboard handling. |
| What the picker is | The same SwiftUI view, `BackgroundImagesView`, with `mode: .manage` in the window and `mode: .pick` in a **sheet** over whatever asked. "Choose…" in `TerminalBackgroundControls` opens the sheet and its `.fileImporter` moves into the view. | A sheet stays modal to the override sheet, Settings or the Project Editor that asked, so Cancel and Done keep their meaning and no routing between windows is needed. The override sheets make this a sheet on a sheet, which SwiftUI supports but nothing in this repo does yet (`ProjectSymbolPicker` is one level, and the file panel is AppKit's). The new UI tests and the user checklist cover it. If it misbehaves, stop and report rather than moving the picker to the window. |
| Adding from disk | Stays, as **Add from File…** in both modes. It imports into the library. In `.pick` mode the added image is then picked and the sheet closes, so choosing a file is one step more than today. | The user asked for adding in the picker. |
| Where a library image lives | A **fourth folder**, `BackgroundImages/`, beside `projects.json` (Application Support/`<variant>`/), same `<digest>/<name>.png` layout, with a new `.keepAll` cleanup: only the user's Remove deletes from it. | Outside `TerminalBackgrounds/` (`.allButRetained`) and `ProjectBackgrounds/` (`reclaim`), so neither can touch it. Per-variant and per-test store, as `ProjectBackgrounds/` is. |
| Cover or merge the folders | **Neither merge nor migrate.** Each use keeps its own copy in its own folder. A pick adopts from the library into that scope's folder. | No stored path changes, so `AppWideBackgroundGate` and `checked(_:)` keep their directory rules, and older Batty reads everything it read before and never sees the new folder. `copyItem` normally clones on APFS, so copies cost little; nothing relies on that. |
| Images already saved | A scan **promotes** valid copies from the app-wide folder, `ProjectBackgrounds/` and **this process's** Caches folder into the library. Scans run only when the window or picker opens. | A row must not vanish when an app-wide pick or `reclaim` cleans its only copy. Nothing touches the folders until the feature is used. Other processes' Caches folders are never read, so another running copy's or a dead process's images don't appear. |
| One digest in several folders | **One row per digest.** Name from the library's file, first by sort order if there are several. Size counted once per row and once in the footer total. | The bytes are the same. |
| Remove, not in use | Confirm, then delete that digest's folder from the library and every source. | Otherwise a promoted copy comes back at the next scan. |
| Remove, in use | Confirm, **listing every use**, then clear each use **before** deleting files. | See "What Remove does". Refusing would make the user hunt down each use; leaving paths behind is the silent break. |
| Remove while Projects can't be trusted | **Refuse with a message**, removing nothing, when `mayReferenceUnlistedImages` is true, or when `projects.json` exists and `imagePathsInFile()` is nil, or names this digest for a Project missing from the list (another running copy saved it). | Same rule as `reclaim`: a leak is cheaper than a lost image. |
| Thumbnails | A dedicated actor, downsampling from the file URL with a header check first (see step 1). | Off the main actor, no retained full bitmap, nothing over `maxPixelSize` decoded. |
| iCloud status | **Left out.** | It needs #0551's storage. |
| Feature flag | **None.** See "Release". | |

**What Remove does**, on the main actor, in this order. A failure at any step stops before files are deleted:

1. **Saved Projects** (including Shared): a new `ProjectStore.clearBackgroundImage(digest:)` sets each matching Project's path to nil and keeps fit, position and opacities. It is device state, like `recordApproval`: no `modifiedAt` stamp, no backend publish, and `commit` errors throw. The Project then opens as "Custom, no image", the same as pressing **None**, with no warning. A Shared Project changes on this Mac only, because the path never syncs. `replacingDefinition` keeps the nil through later merges.
2. **Open Project Editor:** `ProjectEditorViewModel.backgroundImageWasRemoved(digest:)` clears the path in the baseline and the draft and sets `backgroundImageState` to `.none`, so a clean editor stays clean. If only the draft named it, the draft keeps the other edits and gets a `captureNotes[.background]` saying the image was removed.
3. **App-wide:** `AppWideBackgroundEditor.removeImage()`, then `gate.refreshImageState()`. It pushes to every surface.
4. **Sessions and Panes in every Window:** `setBackgroundOverride(current.withImagePath(nil))`, the path **None** takes, so live surfaces lose the image through the existing whole-set reconfigure rather than keeping it. A Session's `projectBackgroundSeed` gets the same change, so `SaveSessionAsProject` doesn't read the removal as the user's edit.
5. **Delete** the digest's folder from the library and every source, off the main actor.
6. **Report and notify:** an inline message says what changed ("Removed Harbor. 1 Project and 2 Panes now have no image."). Any folder that couldn't be deleted is named instead, and the row stays. Post `.battyBackgroundImagesDidChange`.

Matching is **by digest, not by path**, because a Session's override can name the Project folder's copy and a Pane's the Caches copy of the same picture.

**How each caller reaches the picker.** `TerminalBackgroundControls` gains `images: BackgroundImagesModel`; `onPickedFile` and `onFileError` become `onPickedLibraryImage: (String) -> Void`. The caller then adopts through the importer it already holds:

| Caller | Importer | Scope's folder | Cleanup it triggers |
|---|---|---|---|
| Settings → Appearance | `store.appWideBackgroundImageImporter`, with `retaining` as today | `TerminalBackgrounds/` | `.allButRetained`, as today |
| Pane and Session sheets | `store.backgroundImageImporter` | Caches `<pid>` | `.deadProcessFolders`, as today |
| Project Editor sheet | `model.backgrounds.importer`; the view model's own `setBackgroundOverride` adopt then sees a path already in its folder | `ProjectBackgrounds/` | none; `refreshDate` protects it from `reclaim` |

Entry points to the window: **File → Background Images…** directly after Edit Projects…, a Command Palette entry, and **Manage Images…** in Settings' Background section. No toolbar button and no shortcut.

**Release.** `AGENTS.md`'s flag is for unfinished features. This lands as one squash commit with every entry point working, and the next release cut from `main` (the next minor, 1.4.0 by the "Release branches" rule) is the one meant to ship it, so nothing unfinished reaches `main`. A flag would also have to keep both today's `.fileImporter` and the picker alive in an already shipping control. **Costs:** a 1.4.0 without this means a revert, and later `release/1.3` cherry-picks touching `TerminalBackgroundControls` or `BackgroundOverrideSettingsView` won't apply cleanly.

**What #0551 adds later.** Nothing here reads iCloud. If #0551 takes its suggested shape (the iCloud folder as transport, verified local copy in `ProjectBackgrounds/`), downloaded images appear with no change here, because that folder is already a source. #0551 then adds:

- a status field on `BackgroundImageEntry`, set without reading an evicted file;
- a stated rule for what Remove does to a Shared Project's record and shared copy, since a re-download would otherwise bring the row back. `BackgroundImageUse.project` carries `isShared` so the confirmation can already say "this Mac only".

### User checklist

1. File → Background Images… opens one window; again brings it forward; Cmd-W closes it; it's in the Window menu only while open.
2. Thumbnails look right, including a wide image, and the window opens without a beachball with several 4096 px images.
3. Upgrade: your existing app-wide and Project images appear without doing anything, and your terminals and Projects look the same.
4. Choose… from a Pane gear, a Session, Settings and a Project: pick one, then Add from File…; the terminal updates and Cancel restores.
5. Remove an image used by a Pane, a Project and the app default: the confirmation lists all three, the picture leaves the live terminal, a new Tab has a shell and no picture, Settings shows None, the Project opens with no picture and no warning.
6. Remove with the Pane sheet still open behind, then Cancel: no picture comes back and new Tabs work.
7. Beta and Prod show separate images.

### Open decisions, with what the plan assumes

No blockers. These are worth a look because they're costly to change later:

- **No feature flag.** See "Release". If 1.4.0 should be able to ship without this, say so before implementing; a flag means keeping both paths in `TerminalBackgroundControls`.
- **The library keeps images until the user removes them,** including ones promoted from a Project that has since replaced its image. Today's automatic cleanup still applies to the per-use copies, not to the library. The alternative, automatic expiry, would repeat the "row disappeared" problem.
- **Remove clears a Project's image rather than leaving a warning,** and doesn't touch the Project's fit or opacity. A Project with an image removed therefore hides any app-wide image, as **None** does today.

### Premises corrected

- **Layouts is not a window.** `Layouts…` posts `.battyToggleLayoutPicker` and `LayoutPickerView` is a sheet on the content window. Only the Project Editor is a window, and the Open Project picker is also a sheet. The plan takes the window from the first and the grid from the second.
- **The pixel limit only holds on the import route.** The table below reads as though the gate protects app-wide paths, but it checks shape and digest and nothing at all checks a Pane path. Today that's safe because every path comes from `importImage`; `adopt` into those folders needs the check `adoptImage` adds.
- **A Session's override isn't always in Caches.** A Project's seed names the `ProjectBackgrounds/` copy, so uses must match by digest.
- **`AppWideBackgroundGate`'s memo is a smaller hazard than stated.** Once the stored path is nil, `settings()` returns before consulting it. The refresh stays, as a precaution. The larger stale state is Settings' local `snapshot`, which the first report didn't list.
- **`imagePathsInFile()` is nil for an absent file,** so `reclaim`'s guard can't be reused as is for Remove.

## The need

The window shows the background images Batty holds for app-wide, Session, Pane and Project use:

- a thumbnail of each;
- what uses each;
- its size on disk;
- add and remove.

Whether an image is in iCloud waits for #0551. Removing an image in use gives a clear result and never a silent break.

## Questions from the first report

Each is settled in the Plan. They stay here as the record of the hazards the plan had to answer.

**Cover the folders or merge them**

A manager has to cover all three folders or merge them, and each choice raises questions.

- **Covering them:** the same picture can sit in several folders, because `adopt` copies between them with the same digest. Is that one row or several? Are sizes counted once or per copy? Names can differ for one digest.
- **Merging them:** the app-wide path in `UserDefaults` and paths in `projects.json` are absolute and need migrating. `AppWideBackgroundGate` and `checked(_:)` each accept only their own folder. Prod and Beta must stay separate. Older Batty reading a migrated path would report the image as rejected.
- **`.allButRetained` conflicts with a library.** The first app-wide pick of a launch deletes every other app-wide folder, so images can't be kept there for later.
- **`reclaim` conflicts with "add".** An image added to `ProjectBackgrounds/` that nothing names yet is removed about a day later. Added images need their own store or an entry in the keep-set.
- **Pane and Session copies are short-lived.** They end with the process, so should they appear at all? If they do, the rows disappear on relaunch, and another running copy's folder or a dead process's leftover would show up too.

**What "uses" can be known**

- App-wide and saved Projects can be read from storage. Session and Pane overrides are in the running process only, so another running copy of the same variant can't be seen. `reclaim` has the same limit (#0540 Gotchas).
- A Shared Project's use on another Mac can't be seen from here, apart from what the key-value records name.

**Removing an image in use**

Decide what each use does, and tell the user first:

- **Live terminals:** per #0540 Gotchas (from reading the source, not measured), an existing surface keeps showing the image after its file is removed, and a new Tab or Split in that Session gets no image and a working shell. So "removed" doesn't make it disappear unless the Pane is also reconfigured. Remember that `setTerminalConfiguration` replaces the whole override set (#0372, "The wholesale-replace hazard").
- **App-wide:** Settings already says "Image not found. Choose it again.", but `AppWideBackgroundGate` memoizes by path, so the manager must call `refreshImageState()` or builders keep passing the removed path.
- **Project:** the Sidebar's warning and the editor's warning already cover a missing image. Does removal also clear the Project's stored background?
- **Shared Project:** does removal change the record for every Mac, or only this Mac's copy? This Mac's copy, until #0551 sets its rules for removal and for older Batty.

**Cost of showing it**

- Copies can be 4096 px PNGs, so thumbnails and digests can't be computed on the main actor. A thumbnail must never trigger a download of an evicted iCloud file. `docs/swiftui-observation-rules.md` applies to anything the list writes.

## Root cause

Not a bug: a missing feature. Batty held background images in three folders with three cleanup rules, and no surface showed what it held, what used each image or how much space they took. Choosing an image only ever opened a file panel.

## Fix

- **Library:** `BackgroundImageLibrary`, an actor over a new `BackgroundImages/` folder beside `projects.json` with a `.keepAll` cleanup. A scan, run only when the window or picker opens, promotes valid copies from the app-wide, Project and this process's Pane folders. No stored path changes.
- **Pixel check:** `TerminalBackgroundImageImporter.adoptImage` carries the check the encode gives the import route. `isWithinPixelLimit` moved out of `ProjectBackgroundLibrary`, unchanged in behaviour.
- **Thumbnails:** `BackgroundImageThumbnailer` hashes, reads the header, then downsamples from the URL off the main actor. Nothing over the limit decodes.
- **Uses and Remove:** `AppStateStore+BackgroundImages` finds uses by digest from memory, refuses by the `reclaim` trust rule, and clears Projects, the open editor, app-wide, Sessions (with their seeds) and Panes before any file is deleted. `ProjectStore.clearBackgroundImage` is device state.
- **Window and picker:** `BackgroundImagesView` in `.manage` (`BackgroundImagesWindowController`, an on-demand `NSWindow`) and `.pick` (a sheet from `TerminalBackgroundControls`). Entry points are File → Background Images…, the Command Palette and Settings' Manage Images….

**Choices the plan left open or that differ from it:**

- `AppStateStore.backgroundImages` is a `lazy var` rather than set in `init`, because its closures capture `self`. Building it still touches no files, and it stays a `var` so tests can replace it.
- `BackgroundOverrideEditor.cancel()` drops a path only if it is **copy-shaped** (digest folder), its file is gone, and the holder doesn't report it as saved (new `BackgroundOverrideHolder.isSavedImagePath`, false by default, true for the editor's baseline path). The plan's plain `fileExists` check would have broken two tests the plan requires to stay green: `cancelOverAStoredBadPathLeavesTheDraftClean`, and the Pane and Session cancel tests, which use made-up paths.
- `ProjectStore` gained `fileNamesImageTheListDoesNot(digest:)` for the trust rule. It also refuses when a listed Project's in-memory entry doesn't name the image but the file's does, not only for a Project missing from the list, because the clear would overwrite that saved value.
- `BackgroundImagesModel` takes a `notificationCenter`, so the notification test can't see other parallel tests' posts.
- Added identifiers beyond the plan's list: `background-images.confirm-remove`, `background-images.empty-add`.
- The grid's column count comes from a `GeometryReader` local rather than stored state, so a resize writes nothing observed.
- The grid's `ScrollView` holds keyboard focus itself, not a hidden rectangle as in `LayoutPickerView`. The first VM runs showed why: a zero-size holder whose focus was set from inside the `GeometryReader` never took it, **Add from File…** kept the focus ring, and arrow keys selected nothing. The focus writes are now on the root: `.onAppear`, and `.onChange(of: model.entries.isEmpty)` for the first open of a launch, when the grid doesn't exist until the scan finishes. Who flips that: `entries`, written after the scan's `await`, so it isn't layout- or focus-origin. Only `@FocusState` is written, and nothing here calls AppKit. `.defaultFocus` asks for the grid over the first button when the window opens.
- **The cell has no accessibility value.** Plan step 3 gave `.cell.<name>` a value of `usable`, `rejected`, `missing` or `loading`. It shipped without one: the modifier never reached the accessibility tree (see Verification), so review removed it. Accessibility tools get the state from the cell's children: "Can't be used" as text, or the progress indicator while loading. Tests prove a thumbnail by its pixels.
- `BackgroundImagesWindowController.windowDidBecomeKey` re-reads the uses from memory, with no scan, so a use changed in another window shows when the user comes back. This is a delegate callback, an event, and `uses` is written only on change.

**After the first VM run:**

- **Six failures, one test bug.** `waitForUsable` read `cell.value`, but XCUITest sees no value on the cell, a `.contain` container. The check now counts the fixture's own colour in a screenshot of the cell, which is stricter: it proves that image was drawn, not only that its state was usable. `BackgroundImageFixture.color(named:)` gives the test the colour.
- **One product bug.** Arrow keys selected nothing on the first open, and **Add from File…** kept the focus ring. See the grid's focus bullet above.

## Gotchas

- **What the VM runs don't cover.** They ran in the guest only, so the plan's User checklist is still the visual sign-off. Not exercised: Add from File… (no test drives the file panel), picking from the Session and Settings pickers (their tests only open them), arrow keys on a later open and in the picker, Return to pick, Esc to cancel, the Delete key, Remove of an image a live Pane or the app default is using, and thumbnails of wide or 4096 px images.
- **Not seen on a real display.** Every run was in the guest, so nobody has yet seen thumbnail quality or colour on a real display, a wide or 4096 px image, the sheet over a sheet, the focus behaviour outside the guest, or the window's feel in light and dark. The grid has no focus ring by design, so only the selection outline shows where the arrow keys act. VoiceOver hasn't been run on the cells.
- **Run-time warning, not from this branch.** Each VM run logs one "Geometry action is cycling between duplicate values" near its start. Review confirmed the same single line in `20261103-183428-60135` and `20261103-222833-4598` under the main checkout's `build/ui-tests/`. Both ran on 2026-11-03, before this issue was filed, so this code can't have caused them. The diff adds no `onGeometryChange`. Its source is still unknown. None of these runs logs "Modifying state during view update" or "tried to update multiple times per frame".
- **Another running copy of the same variant** can't have its Sessions and Panes seen, so Remove can delete a file that copy shows. Its live surfaces keep the picture, and new Tabs get a shell with no picture (#0540).
- **The uses line can still lag while the window stays key.** A use changed with this window key, say by a sync merge or the CLI, shows only when the window next becomes key or reopens. Remove isn't affected: `prepareRemoval` and `remove` re-read the uses, so the confirmation and the clear are current. The picker sheet has no such refresh and reads the uses when it opens.
- **A lingering `projects.json.bak` blocks every Remove, indefinitely.** Nothing in Batty deletes it. `ProjectStore.writeFile` is the only writer, on the first save after a load that dropped Projects, hit a newer version or couldn't decode; a later such save overwrites it. There is no `removeItem` for it, no restore or cleanup UI, and no mention in Help. So once one exists, `mayReferenceUnlistedImages` stays true across launches until the user deletes the file by hand, and every Remove gets a refusal saying Batty "can't read all of your saved Projects". That text doesn't name the file, so the user has no way to clear it. `reclaim` is stopped by the same check, with only a log line. The rule is unchanged, as a leak is cheaper than a lost image. Whether to clear or name the backup needs its own issue, to be filed before the merge. Follow-up: [#0553](0553.md).
- **A pick can outlive Cancel.** A click in the picker waits for the thumbnailer's check before it calls back. A Cancel in that gap, possible only while the cell is still loading, closes the sheet and the pick still applies. Not reproduced.
- **Messages in the model outlive the sheet:** a removal or error message stays until the next add or removal. Cosmetic.
- **`Batty/Localizable.xcstrings` is unchanged.** The plan expected new keys to merge at build, but the command-line builds left the catalog untouched, so the new strings aren't in it yet. Xcode adds them the next time it builds the app; English shows correctly from the source keys meanwhile.
