# 0552 — Settings has no image manager, so the background images Batty holds can't be seen, added or removed in one place

| | |
|---|---|
| **Status** | open |
| **Module** | Settings / Theme / Projects |
| **Platform** | macOS |
| **First seen** | 2026-11-04 |

## Description

Batty keeps its own copies of background images in three folders with three cleanup rules, and nothing shows the user what it holds, what each image is used for or how much space they take. Settings should have a place for that. Child of [#0372](0372.md). Depends on [#0551](0551.md), which decides where shared images live.

> "We probably need an image manager which goes into Settings."

**Not in 1.3.5 by default.** 1.3.5 is a patch that is close to shipping, and this builds on #0551's new storage. That is the orchestrator's default, not a user decision, and the user may override it.

## The need

A place in Settings to see the background images Batty holds for app-wide, Session, Pane and Project use:

- a thumbnail of each;
- what uses each;
- its size on disk;
- whether it's in iCloud;
- add and remove.

Removing an image in use gives a clear result and never a silent break.

## Where the images are today

Checked against `TerminalBackgroundImageImporter`, `ProjectBackgroundLibrary` and `AppStateStore`.

| Used by | Folder | Lifetime and cleanup | Who checks a path |
|---|---|---|---|
| Pane and Session overrides | `defaultDirectory()`: `Caches/<bundle id>/TerminalBackgrounds/<pid>/` | `.deadProcessFolders`: on the first import of a launch, removes sibling folders whose name isn't a live process. Overrides aren't persisted, and Caches can be purged | Nothing after the import |
| App-wide default | `appWideDirectory()`: `Application Support/<variant>/TerminalBackgrounds/` | `.allButRetained`: on the first import of a launch, removes every folder but the one in use | `AppWideBackgroundGate`, by shape and digest, bound to this folder, with a memo per path |
| Projects | `ProjectBackgroundLibrary.directory(forProjectsFile:)`: `ProjectBackgrounds/` beside `projects.json` | `.unreferenced`: `reclaim` on Project Editor close, for folders nothing names and over a day old | `checked(_:)`, by shape, digest and pixel size, bound to this folder |
| Shared Projects | Set by #0551 | Set by #0551 | Set by #0551 |

## Questions

**Where it sits**

- A section of Settings → Appearance, beside the Background section (`appearance-background.*`), or its own tab next to General, Appearance, Shortcuts, Notifications and Advanced? Thumbnails in a list may not suit the Appearance form.

**Cover the folders or merge them**

A manager has to cover all three folders or merge them, and each choice raises questions.

- **Covering them:** the same picture can sit in several folders, because `adopt` copies between them with the same digest. Is that one row or several? Are sizes counted once or per copy? Names can differ for one digest.
- **Merging them:** the app-wide path in `UserDefaults` and paths in `projects.json` are absolute and need migrating. `AppWideBackgroundGate` and `checked(_:)` each accept only their own folder. Prod and Beta must stay separate. Older Batty reading a migrated path would report the image as rejected.
- **`.allButRetained` conflicts with a library.** The first app-wide pick of a launch deletes every other app-wide folder, so images can't be kept there for later.
- **`reclaim` conflicts with "add".** An image added to `ProjectBackgrounds/` that nothing names yet is removed about a day later. Added images need their own store or an entry in the keep-set.
- **Pane and Session copies are short-lived.** They end with the process, so should they appear at all? If they do, the rows disappear on relaunch, and another running copy's folder or a dead process's leftover would show up too.

**What "uses" can be known**

- App-wide and saved Projects can be read from storage. Session and Pane overrides are in the running process only, so another running copy of the same variant can't be seen. `reclaim` has the same limit (#0540 Gotchas).
- A Shared Project's use on another Mac can't be seen from here, apart from what the key-value records name.

**Removing an image in use**

Decide what each use does, and tell the user first:

- **Live terminals:** per #0540 Gotchas (from reading the source, not measured), an existing surface keeps showing the image after its file is removed, and a new Tab or Split in that Session gets no image and a working shell. So "removed" doesn't make it disappear unless the Pane is also reconfigured. Remember that `setTerminalConfiguration` replaces the whole override set (#0372, "The wholesale-replace hazard").
- **App-wide:** Settings already says "Image not found. Choose it again.", but `AppWideBackgroundGate` memoizes by path, so the manager must call `refreshImageState()` or builders keep passing the removed path.
- **Project:** the Sidebar's warning and the editor's warning already cover a missing image. Does removal also clear the Project's stored background?
- **Shared Project:** does removal change the record for every Mac, or only this Mac's copy? It depends on #0551's rules for removal and for older Batty.

**Do pickers choose from it**

- Does `TerminalBackgroundControls` gain a way to choose from the library beside **Choose…**? A pick has to reach the scope's own folder, through `adopt` or a merged store. Today only `ProjectBackgroundLibrary` has `adopt` sources.

**Cost of showing it**

- Copies can be 4096 px PNGs, so thumbnails and digests can't be computed on the main actor. A thumbnail must never trigger a download of an evicted iCloud file. `docs/swiftui-observation-rules.md` applies to anything the list writes.

## Verification

- The folders are injected, so unit tests use test directories and never the real Caches, Application Support or iCloud Drive (`docs/isolate-userdefaults-in-tests.md` for the defaults side).
- New UI goes behind identifiers with UI tests, type-checked with `./build.sh ui-typecheck`. The daily run exercises them first. Visual sign-off is the user's.

## Release and flag

- Lands on `main`, not on `release/1.3`. See the default in the Description.
- `AGENTS.md` "Release branches" and `docs/feature-flags.md` apply if it lands before the release that ships it: with the flag off, no Settings entry point and no reads of these folders beyond what exists today.
- `BattyKit/Sources/BattyKit/Help/11-backgrounds.md` and `docs/ui-features.md` change with the code.
