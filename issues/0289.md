# 0289 — releaseTerminalView(forTabID:) logs "released" but does not deterministically free the surface

| | |
|---|---|
| **Status** | open |
| **Module** | GhosttyKit |
| **Platform** | macOS |
| **First seen** | 2026-07-31 |

## Description

Terminal Session teardown is correct but not deterministic, and its log line is misleading. `TerminalHostStore.releaseTerminalView(forTabID:)` (`TerminalHostStore.swift:184-191`) drops its dictionary entries, calls `view.removeFromSuperview()`, and logs "released terminal view" — but `removeFromSuperview` only stops the display link and drops focus (`AppTerminalView+Lifecycle.swift:94-97`); **it does not free the surface**. The real `ghostty_surface_free` happens whenever ARC drops the last reference to the `TabRuntime`: `AppTerminalView` deallocates → `TerminalSurfaceCoordinator.deinit` (`:262-271`) → `tearDownSurface` (`:273-293`) → `surface?.free()` (`:283`) → `ghostty_surface_free` (`TerminalSurface.swift:239-245`); and `ghostty_app_free` follows via `TerminalController.deinit` (`TerminalController.swift:258-264`).

Two specific gaps make the deferral fragile:

- `releaseTerminalView` leaves `tab.terminalNSView` set (`TabRuntime.swift:73`), and never calls the available explicit teardown `core.freeSurface()` (`TerminalSurfaceCoordinator.swift:257-260`).
- SwiftUI may still hold the `TabRuntime` after close: `TerminalPlaceholderView.tab` (`TerminalPlaceholderView.swift:23`), `PaneView` (`:522`), and `@State private var renamingTab` (`PaneView.swift:19`). In the ordinary case those clear within a render pass or two, but a stuck reference (e.g. a rename sheet left open on a closed tab) silently keeps a whole ghostty app + surface + PTY + ~48 MB alive with no log line to show for it.

Additionally, three close paths never go through `removeTab` at all and rely purely on subtree deallocation: `WindowRuntime.closePane` (`WindowRuntime.swift:314-334`), `WindowRuntime.removeSession` (`WindowRuntime.swift:117-137`), and `RootWindowView.windowWillClose` (`RootWindowView.swift:195-198`).

Because the "released" log fires before any actual teardown, the log described in `docs/view-hierarchy.md` §6 is **not evidence a surface was freed**.

**Framing: this is not believed to be leaking today.** The #0285 source investigation audited the retain graph and found it clean (weak delegate at `TerminalSurfaceCoordinator.swift:19`, `[weak self]` in all platform hooks at `AppTerminalView.swift:69-94`, `Unmanaged.passUnretained` into C, weak `tabRuntimes` at `TerminalHostStore.swift:64, 261-264`, `retainedBridges` balanced at `TerminalController+Surface.swift:41` / `TerminalSurfaceCoordinator.swift:288`, weak `TerminalViewState.surface`, no reopen/undo stack anywhere). The work here is to make teardown **deterministic and verifiable** — nil the back-reference, free explicitly via `core.freeSurface()`, log from the real teardown point — closing a class of future leak and making the logs trustworthy.

## Relation

## Expected behavior

Closing a Tab (via any close path — `removeTab`, `closePane`, `removeSession`, window close) deterministically frees the surface at close time, and a log line fires from the actual teardown point (`tearDownSurface` or equivalent), so the log is evidence of the free.

## Actual behavior

The free is deferred to ARC; the "released terminal view" log fires before teardown; a lingering SwiftUI reference can keep the surface, app, and PTY alive indefinitely with nothing in the logs.

## Notes

The investigation's confidence levels, carried over: confidence this is *currently* leaking — **low**; confidence it is worth doing — **high**.

`docs/view-hierarchy.md` §6 should be corrected as part of this work, since it presents the "released" log as teardown evidence.
