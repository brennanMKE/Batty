## Description

Reminders (#0514) can only be set from the GUI: the Session menu, the Sidebar context menu and the Command Palette. An agent running in a Pane can't set its own Session aside with "remind me at 9am to check PRs", and a script can't read whether a Session has a pending Reminder. Add a `batty session remind` verb, and add pending-Reminder fields to the `batty list` / `batty session info` JSON. #0514's "CLI" section recommended this follow-up once the model and scheduler settled; they have. Targets 1.4.0, with no feature flag (#0514: "A later CLI follow-up does not count as 'unfinished' and needs no flag"). Parent: [#0514](0514.md).

## Root cause

Feature work. Reminders (#0514) had only GUI entry points: no XPC verb, no CLI command, and no Reminder field in the topology payloads `batty list` / `session info` return.

## Fix

Followed the plan. A new `sessionRemind` XPC verb (`BattyXPCCore/SessionRemindPayload.swift`: request with an `after` / `tomorrow(time?)` / `cancel` action, the duration and `HH:MM` parsers, and bounds pinned to `ReminderSpec`) dispatches to `AppStateStore.remindSessionForXPC`, which resolves the focused-Session fallback, always calls `setReminder` (never the sheet's edit path) or `cancelReminder`, and maps failures to unknown session / no session / out of range. `batty session remind` validates the grammar locally (usage exit, nothing sent), prints `Reminder set for <absolute time>[ — note]`, or the reply as JSON with `--json`; cancel prints nothing. `TopologySessionPayload` gained an optional `reminder` (`TopologyReminderPayload`, ISO 8601 UTC dates), omitted when nil, built with the scheduler's calendar threaded through `topologyPayload(reminderCalendar:)`. Plain-text `list` / `session info` append ` reminder=<dueAt>`. New `remind` capabilities archetype (non-idempotent, non-destructive).

- The default-Tomorrow accessor is named `AppStateStore.tomorrowReminderSpec` (orchestrator's coordination with #0568), not `defaultTomorrowReminderSpec`. It returns `ReminderSpec.defaultTomorrow` for now.

## Proposed grammar

```
batty session remind [--session <id>] (--in <5m|90m|1h30m> | --tomorrow [--at 09:00] | --cancel) [--note <text>]
```

- **Exactly one of** `--in`, `--tomorrow` or `--cancel`. `--at` requires `--tomorrow`, and `--note` is invalid with `--cancel`. These are validation errors (ArgumentParser `validate()`), so nothing is sent.
- **`--in` duration.** Accepts `Nm`, `Nh` and `NhMm`, resolved to minutes. It must lie within `ReminderSpec.minMinutes...maxMinutes`, 1 minute to 7 days (`BattyKit/Sources/BattyKit/Model/SessionReminder.swift:57-58`).
- **`--at HH:MM`** is 24-hour, 0-23 and 0-59. When omitted, it uses the same default the GUI uses. That is 9:00 today, or the remembered time once [#0568](0568.md) lands. The plan should decide whether the CLI reads the remembered time or stays fixed at 09:00, and document the choice.
- **`--note`** is normalized by `SessionReminder.normalizedNote`: trimmed, capped at 500 characters.
- **`--session`** resolution matches `session info` / `session close`: flag, then `BATTY_SESSION_ID`, then the focused Session. Use `resolveTargetSessionID(flag:)` (`BattyKit/Sources/batty/SessionInfoCommand.swift:29`).
- **Output.** On success, print the resolved due time, for example "Reminder set for Tue, Nov 10 at 9:00 AM". With `--json`, if the verb family supports it, return `{sessionID, reminderID, dueAt, note, kind}`. `--cancel` on a Session with no Reminder succeeds quietly (idempotent, like `pane hide`).
- **Exit codes.** An unknown or stale Session id, or "no session to target", returns `XPCExitCode.requestFailed` (4, `BattyXPCCore/XPCExitCode.swift:25`). Broker and app failures map the same way as every other verb.

Setting a Reminder replaces any existing one, the same as the GUI (one per Session). It records no feed entry and posts nothing until it fires.

## Acceptance criteria

1. `batty session remind --in 15m` sets a 15-minute Reminder on the calling Session. The Sidebar badge appears, and it fires exactly as a GUI-set one does.
2. `batty session remind --tomorrow --at 09:00 --note "check PRs"` sets a wall-clock Tomorrow Reminder with that note, and the output shows the absolute due time.
3. `--cancel` removes a pending Reminder. Run again, it succeeds without error.
4. Invalid combinations and out-of-range values fail validation with a clear message. An unknown `--session` exits 4.
5. `batty list --json` and `batty session info --json` include a `reminder` object for a Session that has one, and omit it (or give `null`) otherwise.
6. `batty capabilities` lists `session remind` with its input schema.
7. The docs and the skill describe the verb and the agent use case.

## Plan

Planned 2026-11-09 against `569f2a61`. All file pointers in the issue were checked and hold, with these corrections: the `batty` CLI target does **not** depend on `BattyKit` (only `BattyCLICore`, `BattyXPCCore`, ArgumentParser), so it cannot use `ReminderSpec` or `ReminderFormat`; `SessionRuntime.topologyPayload(isActive:includeDimensions:)` (`XPC/TopologyPayloadBuilder.swift:53`) has no calendar in hand, so one must be threaded in; no topology payload has a `Date` field today, and the CLI's `JSONEncoder`s use the default date strategy (seconds since 2001), so dates go over the wire as ISO 8601 strings.

### Decisions (open questions settled)

1. **Tomorrow default time is resolved app-side through one accessor.** `--tomorrow` without `--at` sends `tomorrow(time: nil)`; the app resolves it with a new `AppStateStore.defaultTomorrowReminderSpec: ReminderSpec` (returns `ReminderSpec.defaultTomorrow` today). #0568 repoints that one accessor at the remembered time. If #0568 has already landed with its own observed property when this is implemented, the accessor returns `.tomorrow(hour:minute:)` from that property instead. The CLI never reads app preferences.
2. **The CLI does not write the remembered Tomorrow time** (#0568's recommendation: a script's choice should not change the GUI default). It calls `setReminder`, never the sheet path.
3. **Set, not edit.** Every non-cancel call goes through `setReminder(_:note:forSessionID:)` (replace, fresh `createdAt`, fresh id). `editReminder`'s keep-the-date rule is a sheet behavior and is not used.
4. **Bounds live in `BattyXPCCore` too.** `SessionRemindRequest.minMinutes = 1`, `maxMinutes = 10_080`. A unit test pins them equal to `ReminderSpec.minMinutes/maxMinutes`, so they can't drift. The app still re-validates (`setReminder` returns nil -> failure reply).
5. **`--json` is supported** (the Session verb family has it on `info`). It prints the encoded `SessionRemindReply`: `{"sessionID": ..., "reminder": {id, dueAt, note, kind, createdAt}}`; `--cancel --json` prints `{"sessionID": ...}` (no `reminder` key). Nested rather than flat so it is the same `reminder` object `list`/`session info` carry.
6. **Plain-text output.** Set: `Reminder set for Tue, Nov 10 at 9:00 AM` (plus ` — <note>` when there is one), formatted in the CLI from `dueAt` with the same style as `ReminderFormat.absolute` (`weekday(.abbreviated).month(.abbreviated).day().hour().minute()`) in the CLI's current calendar/locale. Cancel: prints nothing, exit 0, whether or not a Reminder was pending.
7. **`batty list` / `session info` plain text** append ` reminder=<dueAt ISO 8601>` to the session line when a Reminder is pending (end of line, so existing field order is unchanged). No glyph.
8. **`--at` grammar:** `H:MM` or `HH:MM`, 24-hour, hour 0-23, minute exactly two digits 0-59. Rejects `9`, `9am`, `24:00`, `09:60`, `9:5`.
9. **`--in` grammar:** `^\d+m$`, `^\d+h$`, `^\d+h\d+m$` (lowercase only). In the compound form minutes must be 0-59 (`1h90m` rejected; use `150m`). Total must be in 1...10080; digit strings that overflow `Int` are rejected, not trapped. No `d`/`s` units.
10. **Capabilities archetype:** new `"remind"` archetype, `readOnlyHint: false, destructiveHint: false, idempotentHint: false` (worst case: `--in` moves the due time each call), `openWorldHint: false`; `"session remind": "remind"` in `leafArchetypeByVerbPath`.
11. **Exit codes:** validation errors -> ArgumentParser's usage exit (64), nothing sent. Unknown/stale id, no session to target, out-of-bounds spec rejected by the app -> `XPCExitCode.requestFailed` (4), message `batty: request failed — <reason>`. Broker/app failures map exactly as `SessionCloseCommand`.
