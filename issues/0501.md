## Description

The user's request (2026-10-13), verbatim:

> There is 1 more addition we need to make to the Projects feature. We want to mark some as shared while some will be local. And we shoudl be able to toggle a checkbox with each card to do this. Basically shared projects will be iCloud synced with the app so we need to make sure we are ready to share with iCloud. Create this new issue.

Today every Project is local: `Project` has no notion of shared or local, every Projects surface treats the one `projects.json` as the whole truth, and that file mixes the Project's **definition** (name, root, color, symbol, Layout, Tabs, commands) with **per-device state** (`lastOpenedAt`, `approvedCommandsHash`) in one record. Nothing about it is ready to sync: there is no sync-safe record shape, no rule for what happens when two Macs edit one Project, no portable form of a root path that lives under one Mac's home directory, and no signing or entitlement support for any iCloud mechanism (the app is a Developer ID, notarized, unsandboxed app with a two-key entitlements file).

This issue is **phase (a)** of a two-phase plan, decided below (D11): it adds the per-Project **shared/local flag**, the **checkbox on every card and in the editor**, the **storage split** between synced definition and device-local state, the **portable path** and **merge** rules as pure, unit-tested code, and a **sync backend abstraction** whose only implementation here is local-only. It leaves the data on disk in the one `projects.json`, with two new optional keys. **Phase (b)**, the real iCloud backend, is described under `## Notes` as a follow-up to file once the user has signed off on the signing, entitlement and provisioning changes listed under `## iCloud readiness`; those touch restricted areas (`Configuration/`, `scripts/`) and the Apple developer account, so they are listed here as needing the user's sign-off, not as agent work.

Ships on `main` for 1.3.0, behind the Projects flag. With the flag off nothing here is visible, `ProjectStore` is never constructed, and `projects.json` is never opened.

## Decisions

### D1. The flag: `Project.isShared`, default local

- `Project` gains `isShared: Bool`. Absent in the file decodes to `false`; every Project written before this issue is therefore local. New Projects from the editor's New Project, from Save Session as Project and from the editor's "Copy from current Session" all start **local**.
- Why local by default: a Project's root path and Tab directories are this Mac's paths, its startup commands are trust-sensitive (#0473), and syncing a record the user never chose to share would be a surprise. Sharing is an explicit, per-Project, opt-in choice, in the spirit of "records are written only on explicit user action" (`Concepts.md`, Project, Storage).
- The term in the UI and in `Concepts.md` is **Shared** (the opposite is **Local**). A shared Project is one the user has marked to sync through iCloud to their other Macs; until phase (b) lands the flag is stored and shown but nothing leaves the Mac, and the design doc says so.

### D2. The storage split: definition vs. device state

Every Project record is partitioned into two groups of fields. This partition is the sync contract, and it is enforced by types, not by convention.

| Group | Fields | Syncs (phase b) |
|---|---|---|
| **Definition** | `id`, `name`, `rootPath` (portable form, D3), `color`, `symbol`, `layout`, `runStartupCommandsOnOpen`, `modifiedAt` (new) | yes, when `isShared` |
| **Device state** | `lastOpenedAt`, `approvedCommandsHash` | never |
| **Membership** | `isShared` | implied by presence in the shared set, never a field of the synced record |

- `Project.modifiedAt: Date?` is new. `ProjectStore` sets it from an injected clock on every **definition** write (`upsert`, the new `setShared`), and **not** on `recordOpen`, which touches device state only. It is the last-writer-wins key (D8). Absent in the file decodes to `nil`, which the merge treats as older than any date.
- `lastOpenedAt` stays per-device (D4). `approvedCommandsHash` stays per-device: the trust approval (#0473) is consent the user gave on *this* Mac for commands that run on *this* Mac. If it synced, approving a command set on Mac A would let the same commands run unprompted on Mac B. It must not sync, and the merge must never copy it.
- A new value type, `ProjectSyncRecord` (`BattyKit/Sources/BattyKit/Model/ProjectSync.swift`), is the synced shape: exactly the Definition row above, `Codable`, `Sendable`, `Equatable`, with the root in portable form. `Project.syncRecord(home:)` produces it; `Project.init(syncRecord:home:)` builds a shared Project from one with nil device state. A `ProjectSyncRecord` has no `isShared`, no `lastOpenedAt` and no `approvedCommandsHash`, so the compiler, not a review, keeps device state out of the payload.
- The file stays `projects.json`, version **1**, with the two new optional keys `isShared` and `modifiedAt` on each Project. No version bump: the keys are additive, and `Project.init(from:)` (`Model/Project.swift:281-311`) reads a keyed container and ignores keys it does not know, so a file written by this build loads in a build without this issue (verified by reading the decoder; a unit test pins that an unknown key is ignored, see Acceptance criteria). The `ProjectsFile.currentVersion` newer-version preservation (`Model/ProjectStore.swift:223-226`) is untouched.

### D3. Paths: portable root in the sync record, missing-folder state on the card

- In memory and in `projects.json`, `rootPath` stays **absolute**; the decoder's rejection of a non-absolute root (`Project.swift:285-288`) and `Project.resolve` (`:266-275`) are untouched.
- In the **sync record only**, a root under the home directory is written **home-relative** with a `~/` prefix: `/Users/brennan/Developer/Batty` becomes `~/Developer/Batty`; a root exactly equal to home becomes `~`; a root outside home (`/Volumes/Work/x`, `/opt/x`) is written as is. A pure `PortablePath` enum (`Model/PortablePath.swift`) does both directions with an explicit `home:` parameter and no filesystem access: `encode(absolute:home:)` and `decode(portable:home:)`. Only a leading `~/` (or a bare `~`) is expanded; `~user/...` forms are not. Tab `workingDirectory` and Git Status `repositoryPath` are already relative to the root (`Project.swift:13-14`, `:29-30`) and need no change.
- A Project whose root does not exist on this Mac (a shared Project from another Mac, or a local one whose folder was deleted) is a **normal, visible Project in a missing-folder state**, not an error and not hidden: its picker cards show a `Folder not found` caption in the path row (`exclamationmark.triangle`, identifier `project-picker.missing-root.<name>`), and the Open Quickly row, File menu and palette are unchanged. Opening it still fails as today with `ProjectOpenError.rootMissing` (`Model/ProjectTreeBuilder.swift:59-60`, message `The Project folder "…" no longer exists.`), and the Project Editor still refuses to save it until the root exists (`Model/ProjectEditorViewModel.swift:145-146` checks the folder). The existence check is **injected** into `ProjectPickerModel` as a `(String) -> Bool` closure (default `FileManager.default.fileExists(atPath:isDirectory:)` requiring a directory) so unit tests never touch the filesystem and `body` reads a precomputed card field rather than calling `FileManager`.

### D4. Recency is per-device and does not sync

`lastOpenedAt` stays in `projects.json` on the Mac that opened the Project and never enters the sync record. Reasons: recency ranks the picker, File menu, palette, CLI and Open Quickly (#0492) by what *this person on this Mac* opened recently; an open on another Mac reordering this Mac's picker would be surprising; and every recency write would otherwise become a sync write (a KVS write per open). `ProjectRecency.ranked` (`Model/ProjectRecency.swift:14-33`) is unchanged, and a Project that arrives from another Mac ranks as never opened until it is opened here.

### D5. Where the checkbox goes

One control, the same identifier scheme on every card, always its own click target:

- **Large (Recent) card** (`ProjectPickerCardView`, `.large`, `Views/ProjectPickerView.swift:309-363`): a `Toggle` with `.checkbox` style labelled `Shared`, trailing on the **summary** row (`:343-349`), right-aligned after `N panes · N tabs · N startup commands`.
- **Compact (All Projects) card** (`.compact`): the same toggle, trailing on the **path** row (`:337-342`), after the `~` path.
- **Open now strip chip** (#0500, the 36 pt chip with symbol, name, OPEN badge, `↩ switch` caption and the `+` button): the same toggle between the `↩ switch` caption and the `+` button. The chip keeps `project-picker.card.<name>`.
- **Project Editor**: the header row (`Views/ProjectEditorView.swift:359-397`: Name, Root folder, Session color, Symbol) gains a fifth column, `Sharing`, holding a checkbox `Shared` bound to the draft (`ProjectDraft.isShared`, new). It is part of the draft: toggling it makes the draft dirty, Save writes it, Cancel reverts it, and the unsaved-changes question (#0481) covers it. The editor's Projects list row (`:280-304`) shows a small `icloud` glyph after the name for a shared Project (`accessibilityHidden`; the checkbox is the test seam).
- **Identifiers**: picker `project-picker.shared.<name>` on all three card kinds; editor `project-editor.shared`. Each toggle carries `accessibilityLabel("Shared")` and `help` text `Shared Projects sync with iCloud`.
- **Click target.** The toggle is a control inside a card whose body has `onTapGesture` (select) and `onTapGesture(count: 2)` (open) (`ProjectPickerView.swift:176-180`). A click on the checkbox must flip the flag and do nothing else: no selection change, no open, no sheet dismissal. SwiftUI gives the inner control precedence over the ancestor gestures, and the VM test pins it. A double-click on the checkbox toggles twice (net no change) and must not open the Project.
- **Write path.** The picker's `onAction` contract is *dismiss first, then act* (`ProjectPickerView.swift:22-24`; `SessionDetailView` acts in `onDismiss`, `Views/SessionDetailView.swift:104-113`). The checkbox must not go through it, because the sheet stays up. `ProjectPickerView` gains a separate `onSetShared: (UUID, Bool) -> Void` closure, which `SessionDetailView` wires to `store.projectStore?.setShared(id:_:)`. The write is event-origin (a click), it is immediate and persisted (an explicit user action, like `recordOpen`), and the card re-renders because `projects()` is read on every render (`:36-37`, `:53-56`). No `ProjectPickerAction` case is added.
- Shared cards also show a small `icloud` glyph beside the symbol (`accessibilityHidden`), so the state is readable at a glance without finding the checkbox.

### D6. `ProjectStore.setShared(id:_:)`

A new store method: flips `isShared`, sets `modifiedAt` from the store's clock, saves through `commit` (rollback on failure as `upsert` does, `Model/ProjectStore.swift:181-191`), throws `unknownProject` for an unknown id. While the file could not be fully loaded (`unreadableOriginal != nil`), it follows `recordOpen`'s rule (`:169-179`): memory only, logged, no rewrite of a file the user has not explicitly saved. `upsert` also sets `modifiedAt` on every call. The editor's `save()` already copies `approvedCommandsHash` and `lastOpenedAt` from the stored Project (`Model/ProjectEditorViewModel.swift:720-723`); it keeps doing so, and `isShared` comes from the draft.

### D7. The backend abstraction, local-only here

- `ProjectSyncBackend` (`Model/ProjectSync.swift`), a `@MainActor` protocol: `isAvailable: Bool`; `snapshot() -> [UUID: ProjectSyncEntry]`; `publish(_ record: ProjectSyncRecord)`; `withdraw(id:)` (unshare: the entry is removed); `tombstone(id:deletedAt:)` (delete: the entry becomes a tombstone); and `changes: AsyncStream<Void>` the store awaits to re-merge. `ProjectSyncEntry` is `.record(ProjectSyncRecord)` or `.tombstone(deletedAt: Date)`.
- `LocalOnlyProjectSyncBackend`: `isAvailable == false`, keeps entries in memory, never touches disk or the network, exposes its call log for tests. It is the only backend in this issue, and `ProjectStore.init` takes `backend: (any ProjectSyncBackend)? = nil`; `AppStateStore.projectStore` (`Runtime/AppStateStore.swift:95-101`) passes nil, so production behaviour is byte-for-byte today's plus the two keys. Phase (b) swaps in the iCloud backend behind the same protocol.
- `ProjectStore` routes every definition write of a shared Project through the backend when one is present (`publish` on `upsert`/`setShared(true)`, `withdraw` on `setShared(false)`, `tombstone` on `delete`), and applies `ProjectSyncMerge` on `changes`. With `backend == nil` none of that runs. The merge is the only path that writes `projects.json` from a non-user event, and it only ever runs on a backend change, which cannot happen with the local-only backend; `Concepts.md` records that this is the one sanctioned exception to "written only on explicit user action" and that it is inert until phase (b).

### D8. Conflict rule: last writer wins per Project

`ProjectSyncMerge.apply(remote: [UUID: ProjectSyncEntry], to local: [Project], home: String, now: Date) -> [Project]` is a pure function:

1. **Unknown id, record:** insert as a shared Project with nil `lastOpenedAt` and nil `approvedCommandsHash`, root decoded with `PortablePath`.
2. **Known id, record:** if `remote.modifiedAt > local.modifiedAt` (a nil local date is older than any date), replace the **definition** fields and keep the device state; equal or older is ignored. `isShared` becomes `true`.
3. **Known id, tombstone:** delete the local Project **only if it is still shared**; a Project the user has since made local on this Mac is kept. A tombstone for an unknown id is ignored.
4. **Known shared id, absent from the remote set** (withdrawn on another Mac): the local Project becomes **local** and is kept. Nothing is ever deleted by absence; only a tombstone deletes.
5. **Name collision:** names are unique case-insensitively (`ProjectStore.swift:134`, the CLI opens by name). An incoming record whose name collides with a *different* local Project gets a numeric suffix on this Mac (`Name 2`, `Name 3`, …) and is logged. The rename is local; the next merge sees a known id and applies rule 2 (the suffix is re-applied if the remote name still collides).
6. **Idempotent:** applying the same remote set twice yields the same result as once.

"Last writer" is the Mac whose definition write carries the later `modifiedAt`; clocks are assumed roughly in sync, which is acceptable for a record one person edits on their own Macs. There is no field-level merge: a Project is replaced whole. Tombstones older than 30 days are pruned by the backend in phase (b), not here.

### D9. Feature flag

Everything is behind `FeatureFlags.projects`. `ProjectStore` is still built only inside `AppStateStore.projectStore` past the flag (`Runtime/AppStateStore.swift:92-101`); the backend, when one exists, is built in the same place, so with the flag off no store, no backend, and no file access exist. The toggles live inside the picker and the editor, which do not present with the flag off (`docs/feature-flags.md` rows for #0474 and #0475). **No new gate site**: append "and the sync backend (#0501)" to the existing #0471 row in `docs/feature-flags.md` rather than adding a row.

### D10. Out of scope here

- No `batty project list` column or JSON field for `shared`; `ProjectListEntry` (`BattyKit/Sources/BattyXPCCore/ProjectPayload.swift:14-30`) is unchanged. Phase (b) may add `"shared"` to `--json` together with a sync status.
- No Open Quickly, File menu, palette or Sidebar change: only the picker cards and the editor get the control.
- No iCloud entitlement, capability, profile or container in this issue (see `## iCloud readiness`).

### D11. Two phases, and why

Phase (a) is this issue. Phase (b) is the iCloud backend. The split is the better choice because: phase (b) cannot be verified without entitlement, provisioning and release-script changes in restricted areas that need the user's sign-off and an Apple developer account action (an App ID capability and a Developer ID provisioning profile); a restricted entitlement with no matching profile can stop the app launching (the VM's ad-hoc-signed test build is the immediate hazard, see readiness §4); and everything above (flag, checkbox, record split, portable path, merge, backend protocol) is pure, testable and reviewable on its own. Landing both together would put a signing change nobody can test on the host into the same review as a UI change.

## iCloud readiness (research record, 2026-10-13)

### 1. What is available to a Developer ID app

Batty is unsandboxed, signed with a Developer ID Application certificate, notarized, and distributed outside the Mac App Store. The older guidance that iCloud containers need Mac App Store signing (a 2015 Apple Developer Forums thread quoting the then-current iCloud Design Guide: "iCloud entitlements are available only to apps submitted to the App Store or to the Mac App Store") is **superseded**. Apple's current *Supported capabilities (macOS)* reference table, read from the page's HTML on 2026-10-13, lists under the **Developer ID** column as supported: **iCloud: CloudKit**, **iCloud: iCloud documents**, **iCloud: iCloud key-value storage**, App groups, Push notifications, Keychain sharing, Associated domains (not supported for Developer ID: Game Center, In-App Purchase, Sign in with Apple, among others). Apple's *Developer ID* support page says: "Applications can also take advantage of advanced capabilities such as CloudKit and push notifications." and "If your application utilizes a Developer ID provisioning profile to support advanced capabilities, then that profile is also evaluated, both at app installation time and at every app launch." and "Developer ID provisioning profiles generated after February 22, 2017, are valid for 18 years from the creation date, regardless of the expiration date of your Developer ID certificate." and "if your Developer ID provisioning profile expires, the app will no longer launch."

So all three mechanisms are available, and all three require the same two account-side things: the **iCloud capability on the App ID** and a **Developer ID provisioning profile** embedded in the app (`Contents/embedded.provisionprofile`). Apple's *Enable app capabilities* help page: "Provisioning profiles that contain a modified App ID become invalid. You'll need to regenerate the provisioning profiles that use that App ID." and "Enabling a capability will affect provisioning profiles for all eligible platforms."

### 2. The three mechanisms, weighed

| | iCloud key-value storage (`NSUbiquitousKeyValueStore`) | CloudKit (`CKContainer`, private database) | iCloud Drive ubiquity container (a file under `~/Library/Mobile Documents/…`) |
|---|---|---|---|
| Entitlements | `com.apple.developer.ubiquity-kvstore-identifier` = `$(TeamIdentifierPrefix)$(CFBundleIdentifier)` | `com.apple.developer.icloud-services` = `CloudKit`, `com.apple.developer.icloud-container-identifiers`, `com.apple.developer.icloud-container-environment` = `Production` | `com.apple.developer.icloud-services` = `CloudDocuments`, `com.apple.developer.ubiquity-container-identifiers` |
| Account-side setup | capability on the App ID; profile | capability with "Include CloudKit support", a container, a schema deployed to Production in the CloudKit dashboard; profile | capability, a container; profile |
| Granularity | per key; the server keeps the latest value per key | per record, with change tokens, zones, subscriptions | one file; conflicts become `NSFileVersion`s to resolve |
| Limits | **1 MB total per app per user, 1,024 keys, 1 MB per value, 64-byte UTF-8 key** (Apple's iCloud Design Guide, "Designing for Key-Value Data in iCloud"); over-quota writes fail and post `NSUbiquitousKeyValueStoreDidChangeExternallyNotification` with `NSUbiquitousKeyValueStoreQuotaViolationChange` | the user's iCloud quota | the user's iCloud quota; needs iCloud Drive turned on |
| Code surface | a dictionary, `synchronize()`, one notification with reasons (server change, initial sync, quota violation, account change) | `CKRecord` mapping, error handling, retry, account status, schema | `NSFileCoordinator`, `NSMetadataQuery`, conflict versions |
| Conflict behaviour | the server rejects a write that races a recent remote change and posts the external-change notification; the app re-reads and may write again, which is per-key last-writer-wins in practice | per record, with `serverRecordChanged` to resolve | whole-file versions |

**Size check against the KVS budget.** A measured sample (a 4-Pane, 6-Tab Project with six startup commands, serialized compactly with the Definition fields of D2 and a `~`-relative root) is **1,330 bytes**; a single-Pane Project is **336 bytes**. At 1,100 bytes average the 1 MB quota holds about **950 shared Projects**, and the 1,024-key cap allows about 1,000 entries; a key of `project.<uuid>` is 44 bytes, under the 64-byte limit. A user shares tens of Projects, not hundreds, so the budget is roomy, but the backend must encode compactly (no pretty printing), must handle the quota-violation reason, and the design doc must state the ceiling.

**Recommendation: iCloud key-value storage for phase (b).** It fits the data (small records, per-Project last-writer-wins maps onto per-key latest-wins), it has the smallest code and account-side surface (no CloudKit schema or dashboard, no iCloud Drive dependency), it is in Apple's supported-for-Developer-ID list, and it needs exactly one entitlement key whose value derives from the bundle identifier, so Prod and Beta separate automatically (§3). The `ProjectSyncBackend` abstraction (D7) exists so CloudKit can replace it without touching the store or the merge if the record count or size ever approaches the quota, or if per-record subscriptions are wanted. CloudKit is the fallback, not the first choice; the ubiquity container is not recommended (whole-file conflicts, iCloud Drive required).

### 3. Prod and Beta containers

Separate, and automatically so: `$(TeamIdentifierPrefix)$(CFBundleIdentifier)` gives `XV8BAAVZ6V.co.sstools.Batty` and `XV8BAAVZ6V.co.sstools.Batty.beta`, two independent key-value stores, for the same reason Application Support is split per variant (#0279). A Beta build must never write into the shared set a Prod build reads, and the user's Beta Projects stay Beta's. If CloudKit is ever used instead, the container id follows the same rule (`iCloud.$(PRODUCT_BUNDLE_IDENTIFIER)`) and needs two containers in the dashboard. Both App IDs need the capability, and the Beta build, signed with Apple Development under automatic signing, needs its development profile regenerated with the capability (Xcode does that when the capability is declared on the target).

### 4. Changes needing the user's sign-off (phase b; not agent work)

`Configuration/` and `scripts/` are restricted areas (`AGENTS.md`), and the account-side steps are the user's. Listed so phase (b) can be filed against a decided list:

1. **Apple developer account.** Enable the iCloud capability (key-value storage; "Include CloudKit support" only if CloudKit is chosen) on the App IDs `co.sstools.Batty` and `co.sstools.Batty.beta`. 3. **`Batty.xcodeproj/project.pbxproj`.** Xcode records the capability under the target's `SystemCapabilities` when it is added in Signing & Capabilities. Tracked, and distinct from the Prod/Beta product-name residue `AGENTS.md` says to discard; this part is meant to be committed.
4. **`Configuration/Build.xcconfig`.** Possibly nothing: `CODE_SIGN_STYLE = Automatic` plus `-exportArchive` with `signingStyle = automatic` lets Xcode manage the Developer ID profile. If automatic management does not embed the profile, `PROVISIONING_PROFILE_SPECIFIER` for the Release configuration is the manual route. Decide at phase (b) by inspecting the exported app for `Contents/embedded.provisionprofile`.
5. **`scripts/release.sh`.** The re-sign step (`:188-206`) re-signs the app with its extracted entitlements and must keep `embedded.provisionprofile` in place and the new entitlement in the signature; add a verification that the profile is embedded and that `codesign -d --entitlements -` shows the kvstore key. **`scripts/verify-dmg.sh`** and **`scripts/preflight.sh`**: assert the embedded profile exists and report its expiry (18 years from creation), since Gatekeeper evaluates it at every launch and an expired profile stops the app launching.

7. **Flag off (D9).** Nothing new reachable; no new gate site, the #0471 row amended.
8. **Observation rules.** Every write originates from a click (the toggles) or a store call; `body` reads `projects()` as today and precomputed card fields; no `FileManager` call in `body`; no `onAppear`/geometry writes (`docs/swiftui-observation-rules.md`).
