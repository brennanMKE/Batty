# 0408 — Focus on new-Tab creation is guarded on `isPaneFocused`, so the tab-strip "+" and Duplicate Tab in a non-focused Pane activate a Tab keyboard focus never follows — and no test at any level pins that a new Tab can be typed into

| | |
|---|---|
| **Status** | open |
| **Module** | Pane / Tabs / TerminalSurface |
| **Platform** | macOS |
| **First seen** | 2026-09-12 |

## Description

Every focus trigger for a newly created Tab is gated on the Pane already
being the focused Pane. `PaneView` wires three
`TerminalSurfaceFocuser.focusWhenReady(tab:)` triggers per Tab —
`.onAppear` (`PaneView.swift:315-318`), `.onChange(of: pane.activeTabID)`
(`:319-322`), and `.onChange(of: isPaneFocused)` (`:323-326`) — and all
three guard on `isPaneFocused` (`tree.focusedPaneID == pane.id`,
`PaneView.swift:55-57`). `PaneRuntime.addTab(inheritingCWDFrom:)`
(`PaneRuntime.swift:152`) appends the Tab and sets `activeTabID = tab.id`
(`:160-161`) but never touches focus, model-level or AppKit-level.

Two shipping entry points can create a Tab in a Pane that is not focused,
and for both the new Tab becomes that Pane's active Tab while
`tree.focusedPaneID` and the window's first responder stay wherever they
were:

- the tab-strip "+" button (`PaneView.swift:199`, `onAdd:` on
  `SlidingTabBar`), and
- the chip context menu's Duplicate Tab (`PaneView.swift:639-641`).

Both run `pane.addTab(...)` directly on the runtime, bypassing
`activeIDBinding` (`PaneView.swift:662-674`) — the binding setter is the
path that *does* call `appStore.focusPane(id: pane.id)` when a user
selects a chip in another Pane. So the app already has the precedent that
clicking a chip in Pane B moves Pane focus to B, while clicking "+" in
Pane B (a stronger gesture: create *and* activate) moves nothing.
`TerminalClickFocusMonitor` does not close the gap either: it promotes
only clicks that hit-test into an `AppTerminalView` (the "+" button and
chips are SwiftUI chrome, not the terminal), and it deliberately ignores
right-clicks (#0132 Gotchas), which is how the Duplicate Tab menu is
reached.

No user-reported failure prompted this issue. It was filed from a coverage
question — "is new-Tab focus behavior tracked anywhere?" — and the answer
is: the focused-Pane path is (see #0132 below), the non-focused-Pane path
has never been filed, and **no test at any level asserts that a newly
created Tab receives keyboard focus** (see Notes).

## Steps to reproduce

Derived from code reading, not from a user report — the interactive
outcome is unverified in a running app.

1. Split so the Session has two visible terminal Panes, A (focused) and B.
2. Click the "+" in Pane B's tab strip (or right-click a chip in Pane B
   and choose Duplicate Tab).
3. Observe where the new Tab appears, where the focus border sits, and
   where typing lands.

## Expected behavior

Not pinned anywhere today — that is part of the gap. The two candidate
readings, both defensible:

- **Focus follows creation:** creating a Tab is at least as strong an
  intent signal as selecting one, and chip selection in a non-focused Pane
  already moves Pane focus there via `activeIDBinding` →
  `appStore.focusPane(id:)`. Under this reading the new Tab should end up
  focused and typeable, matching #0066's acceptance criterion for the
  focused-Pane case ("typing lands in the new tab's shell").
- **Focus stays put:** background-Pane mutations should never yank the
  keyboard away (the same principle behind the `isPaneFocused` guard that
  #0066 added deliberately, "so background tabs and non-focused panes do
  not yank focus").

Whichever is chosen should be stated, made consistent with chip-click
behavior, and pinned by a test.

## Actual behavior

Per code reading: the new Tab is appended and becomes `activeTabID` in
Pane B, so Pane B's visible surface swaps to the new shell — but
`tree.focusedPaneID` still names Pane A, the focus border stays on A, no
`TerminalSurfaceFocuser` call is ever made for the new Tab (all three
triggers fail their `isPaneFocused` guard, and the guard's own `onChange`
never fires because nothing wrote `focusedPaneID`), and keystrokes
continue to land in Pane A.

## Notes

**Entry-point audit** — every `addTab` call site in the app, and whether
it can target a non-focused Pane:

| Call site | Route | Can target a non-focused Pane? |
|---|---|---|
| `PaneView.swift:199` (tab-strip "+") | `pane.addTab(inheritingCWDFrom: pane.activeTab)` on the Pane that owns the strip | **Yes** — the strip renders in every visible Pane |
| `PaneView.swift:639-641` (Duplicate Tab) | `pane.addTab(inheritingCWDFrom: tab)` on the chip's Pane | **Yes** — reached by right-click, which `TerminalClickFocusMonitor` ignores |
| `BattyShortcuts.swift:130` (⌘T via the NSEvent monitor) | `window.selectedSession?.focusedTerminalPane?.addTab(...)` | No — `focusedTerminalPane` (`SessionRuntime.swift:211-214`) returns the focused Pane or `nil` |
| `CommandPaletteView.swift:221` (palette New Tab) | same `focusedTerminalPane` route | No |
| `BattyCommands.swift:438` (menu-bar New Tab) | `keyWindow?.selectedSession?.focusedTerminalPane?.addTab()` | No |
| `UITestDriver.swift:91` (test hook) | `focusedTerminalPane` route | No (test-only) |

So the keyboard/menu/palette paths are safe from this by construction —
the gap is reachable only through the two in-Pane mouse affordances.
There is no XPC/CLI Tab-creation verb today, and a hidden Pane cannot be
targeted: its `PaneView` never mounts (`SplitContainerView.swift:61-63`
renders `Color.clear` for a hidden leaf, the fact #0405's review
established), and `focusedTerminalPane` cannot name a hidden Pane under
#0256's invariant.

**Where #0132 stops and this issue starts.** #0132's title says new
Sessions and new split Panes, but its re-opened section explicitly folded
in the new-Tab path ("Repeat with a new tab in the current pane (`Cmd-T`
or the `+` button on the tab bar)") and its acceptance criterion covers
typing reaching the new Tab. What #0132 fixed, though, is the *focused*-
Pane path: the delegate-identity lookup bug meant `focusWhenReady` found
no view even when it ran. It never removed or questioned the
`isPaneFocused` guards, so a "+" click in a *non-focused* Pane never runs
the focuser at all — before or after #0132. #0066 is where the guards
came from, and there they are documented as deliberate protection against
background Panes stealing focus; #0066's scope was initial/launch focus
plus ⌘T in the focused Pane, and it never considered creation *from* a
non-focused Pane's own chrome.

**Test coverage today: none pins new-Tab focus, at any level.**

- `BattyKit/Tests/BattyKitTests/TerminalSurfaceFocuserTests.swift` covers
  only the early-return predicates of `focus(tab:)` (no `terminalNSView`,
  no window, hidden) — per #0132's own resolution note, the promotion
  path needs an attached `NSWindow` and is "exercised interactively, not
  in unit tests."
- `BattyUITests/KeyboardShortcutTests.swift` `testCmdTCreatesNewTab`
  (#0179) asserts only that the tab-chip count grows after ⌘T.
- `BattyUITests/LifecycleTests.swift` `testCmdTCreatesTabAndCmdWClosesIt`
  (#0185) asserts only chip counts across ⌘T/⌘W.

Neither UI test types into the new Tab or asserts anything about focus or
first responder, and nothing anywhere asserts a model-level property like
"after creating a Tab via path X, `focusedPaneID` names the Pane it was
created in." That model-level half *is* unit-testable (it needs no
`NSWindow`), whatever the chosen semantics turn out to be.

**Adjacent divergence found during the audit, one sentence's worth:**
`BattyCommands.swift:438` is the only production call site that invokes
`addTab()` with no `inheritingCWDFrom:` argument, so a mouse-click on the
Tab ▸ New Tab menu item spawns at the shell default instead of the active
Tab's cwd — diverging from ⌘T (which `BattyShortcuts.handle` consumes
before the menu ever sees it, and which does inherit), from the palette,
and from both in-Pane affordances, and from the rule #0016/#0057 pinned
and `Concepts.md` (Session, "mirroring the way Cmd-T inherits cwd within
a Pane") restates. Nothing in #0057/#0061 or the code comments marks the
omission deliberate. Fixing or filing it separately is the implementer's
call; recorded here so the audit isn't lost.

**Constraints on the fix space** (from
`docs/swiftui-observation-rules.md`, which is binding for any change to
focus flow):

- The clean shape is an event-origin write: the "+" / Duplicate Tab
  button actions are user-event handlers, exactly where a
  `focusPane(id:)`-style model write is legitimate — the same shape
  `activeIDBinding`'s setter already uses for chip selection.
- Loosening the `isPaneFocused` guards on the `onChange`/`onAppear`
  triggers instead would be the dangerous shape: `activeTabID` also flips
  from non-user churn (e.g. `jumpToTab`/`jumpToBellEntry` write
  `pane.activeTabID` on Panes that are not yet focused), and #0066 added
  the guard precisely so background flips don't yank focus. Any change
  there has to audit *what flips the observed value*, per the doc.
- Do not reach for `Task { @MainActor }` hops to sequence the focus write
  — the doc prohibits it explicitly (the #0229 click regression).
- `AppStateStore.focusPane(id:)` is the idempotent store mutator the doc
  itself holds up for re-assertable focus writes.

The decision of which Expected-behavior reading wins is deliberately left
open here; whichever way it goes, the deliverables are the stated
semantics, consistency with chip-click focus, and a test that pins it.
