## Description

Running `batty <path>` (e.g. `batty .` or `batty /Users/brennan/Developer/brennanMKE/NeoPager`) is supposed to make the running Batty app create a new Session whose first Pane's terminal starts in that directory (the #0250 feature). In practice it **opens a new window with a terminal still rooted at the shell default (`$HOME`/passwd), not at the requested path** — the session-at-path is effectively not created where the user can see it, and the cwd is wrong.

## Resolution notes

> 🟢 Resolved 2026-06-23 — root cause was a phantom `WindowID`: the SwiftUI `WindowGroup` default minted a different `WindowID` than the seeded `windows[0]`, so the app-global `addSession` shim dropped the session into a window the user never saw. Aligned the default with `windows[0].id`.

**Needs your runtime sign-off.** The live `batty <path>` → selected-session-at-path round-trip can't be verified headlessly. The window-targeting fix is confirmed by reasoning + unit tests; the working-directory symptom is expected to be fixed by the same change (it was the phantom window showing a default `$HOME` session, not a separate cwd bug — see Gotchas), but only a runtime check confirms it.

This is a bug in what #0250 delivered. The model-level wiring is unit-tested and passes (`AppStateStore.addSession(workingDirectory:)` carries the path), so the failure is in the integration between the URL handler, the window the session lands in, and the actual ghostty surface spawn — none of which the #0250 unit tests exercised (they can't spawn a real surface or window headlessly).

## Steps to reproduce

1. Build/run the app (the `batty://` scheme must be registered — see #0250 testing notes).
2. From a terminal in some project dir, run `batty .` (or `batty <abs-path>`).
3. Observe: a new window appears; its terminal's cwd is `$HOME`, not the path.

## Actual behavior

- A new (empty/default) window opens rather than a Session being added to the current window's sidebar.
- The terminal's working directory is the passwd default (`/Users/brennan`), not the requested path.

## Expected behavior

- `batty <path>` adds a new Session to the **front/key** window (or, if no window is open, opens one) and **selects** it, so the user sees it.
- That Session's first Pane/Tab terminal spawns its shell **in the requested directory**.

## Notes — investigation so far (orchestrator)

Two distinct suspected root causes; the implementer should confirm both with the running app (this needs runtime observation — the GUI can't be exercised headlessly):

**1. Wrong window target (the dominant "new window" symptom).**
`BattyAppDelegate.application(_:open:)` → `BattyURLHandler.handle(url, store: AppStateStore.shared)` → `store.addSession(workingDirectory:)` → `(keyWindowRuntime() ?? windows[0]).addSession(...)` (`AppStateStore.swift:233-234`).
- `AppStateStore.shared.init` seeds `windows = [window]` (`AppStateStore.swift:178-192`) with **no** sessions.
- The on-screen SwiftUI `WindowGroup(for: WindowID.self)` window (in `Batty/BattyApp.swift`) is associated with its own `WindowRuntime` via `windowRuntime(for:)` — which may **not** be `windows[0]`.
- When the URL is delivered (especially on cold launch, before any window is key), `keyWindowRuntime()` is likely nil, so the session is appended to `windows[0]` — a runtime that isn't the window SwiftUI shows. Net effect: the session is "created" in a phantom runtime, and SwiftUI separately opens a fresh empty window.
- Likely fix direction: the URL handler must target the window the user will actually see — bring an existing window to front and add+select the session there, or open exactly one window and add the session to *its* runtime. Inspect `windowRuntime(for:)`, `RootWindowView`, `OpenWindowHookInstaller`, and how `WindowID` ↔ `WindowRuntime` map. Ensure the new session is selected (`selectedSessionID`).

**2. Working directory not honored at surface spawn (confirm independently).**
The package path *looks* complete: `TabRuntime.init` sets `terminal.configuration.workingDirectory` (`TabRuntime.swift:63-64`); `TerminalHostStore.terminalView(for:windowID:)` sets `view.configuration = tab.terminal.configuration` (line 135) **before** `host.addSubview(view)` (line 139) where the surface spawns; `TerminalController.finalizeSurface` sets `config.working_directory` from `configuration.workingDirectory` before `ghostty_surface_new` (`libghostty-spm …/TerminalController+Surface.swift:85-95`).
- So if the value survives to spawn, the surface *should* start at the path. Cmd-T "CWD inheritance" may actually rely on libghostty's native parent-inheritance rather than this explicit `configuration.workingDirectory` option, meaning **the batty path may be the first real user of the explicit option** — and it may be unwired in some way (e.g. the value is nil at spawn, the coordinator's `configuration` didn't sync before `viewDidMoveToWindow`, or a default config is applied after).
- The `config: default working directory src=passwd` log line refers to the config *file* default and may be a red herring (the surface `working_directory` C-string is a separate field) — confirm with the running app whether the terminal actually lands in the path once the windowing bug (#1) is fixed, since the wrong-window bug alone could explain the wrong cwd (the user may be seeing a *default* session in the spurious new window).

**Verification reality:** the true end-to-end check (run `batty .`, see a session at the path in the front window) requires the running GUI app and is the user's sign-off. Add whatever unit coverage is feasible for the windowing-target logic; do not claim the cwd is fixed without a runtime check.

## Root cause

A phantom `WindowID`. `AppStateStore.init` seeds `windows = [window]` with a freshly-minted `WindowID` (call it WID-A). `BattyApp`'s `WindowGroup(for: WindowID.self)` used `defaultValue: { WindowID() }`, minting a *different* ID (WID-B) for the first on-screen window. When that window's views called `store.windowRuntime(for: WID-B)`, a *second* `WindowRuntime` was created (`windows[1]`), and WID-A's `windows[0]` stayed a phantom that no NSWindow ever presented. The app-global `addSession` shim (`keyWindowRuntime() ?? windows[0]`) therefore dropped the `batty://` session into the phantom `windows[0]`, while the user kept looking at WID-B's window (which showed its own default `Session 1` rooted at `$HOME`). That single defect produced *both* reported symptoms — "new empty window" and "wrong cwd."

## Fix

Align the SwiftUI window identity with the seeded runtime so there's exactly one window/runtime on the normal path:
- `BattyApp` now uses `AppStateStore.shared.initialWindowID` (= `windows[0].id`) for both the `WindowGroup` `defaultValue` and the content-closure nil-coalesce, instead of `WindowID()`. SwiftUI's first window presents `windows[0].id`, and `windowRuntime(for:)` returns the already-wired seeded runtime (no duplicate, `onAllSessionsClosed` preserved).
- `AppStateStore` gains `initialWindowID` and `anyContentWindowRuntime()` (key window → any registered content window → nil); the `addSession` shim now targets `anyContentWindowRuntime() ?? windows[0]`, so a `batty://` open with no key window (cold start) still reaches the real window. The new session is selected (`selectedSessionID`) so it's visible.

The working-directory plumbing was already structurally complete (`TabRuntime.init` → `TerminalHostStore` `view.configuration` → `TerminalController.finalizeSurface` `config.working_directory` → `ghostty_surface_new`); no change needed there once the session lands in the visible window.

## Gotchas

- **The wrong-cwd symptom was a side effect of the phantom window, not a separate bug.** The user was seeing WID-B's default `Session 1` (born at `$HOME` per `WindowRuntime.init`), while the path-rooted session sat unseen in the phantom `windows[0]`. If a runtime check *still* shows the wrong cwd after this fix, then there is a genuine second bug in the explicit `configuration.workingDirectory` → surface path (re-open this issue with that finding).
- **Latent restoration-phantom (pre-existing, not introduced here):** on state restoration SwiftUI presents the persisted `WindowID`, which won't match the freshly-seeded `windows[0].id`, so a phantom `windows[0]` can reappear. This diff doesn't change that path (it was already pass-through), and it's out of scope for the `batty <path>` repro — but it's worth its own ticket if/when multi-window state restoration becomes a real feature.
- `anyContentWindowRuntime()`'s no-key-window fallback picks an unordered `nsWindowMap.values.first`; fine for the single-window `batty` case and strictly better than the old unconditional `windows[0]`. A future multi-window scenario may want a deterministic front-most pick.
