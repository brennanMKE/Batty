## Description

In #0412's first full Tart-VM run (run id `20260923-191103-94702`), this test failed at `BattyUITests/WindowRestorationTests.swift:72`:

```
XCTAssertTrue failed - Key window's sidebar must collapse after Cmd-B
```

The test does four things:

1. It launches, measures the Sidebar width (the `> 50 pt` assertion passed) and opens a second window with Shift-Cmd-N. The count `>= 2` passed, and so did the second window's Sidebar-exists check.
2. It presses Cmd-B.
3. It waits up to 5 s for `BattyUITestHarness.sidebar(in: app)` to become non-hittable or narrower than half its original width. **This is where it failed.**
4. It never reaches the check that the original window's Sidebar is still expanded.

In the same run, the related single-window and multi-window tests passed:

- `SidebarTests.testCmdBCollapsesAndExpandsSidebar`: Cmd-B collapses the Sidebar with one window.
- `MultiWindowTests` 3/3, including `testNewWindowHasIndependentSidebar`.
- `WindowRestorationTests.testNewWindowHasOneFreshSession`.

So Cmd-B works, and a second window with its own Sidebar works. The failure is specific to "Cmd-B with two windows, observed through an app-global lookup".

## Two hypotheses

1. **The test's element lookup picks the wrong window.** At step 3 the test uses the *app-global* `sidebar(in: app)`, which returns `app.collectionViews["session-sidebar"].firstMatch` or its fallbacks (`BattyUITests/Support/BattyUITestHarness.swift:130-136`). The comment at `WindowRestorationTests.swift:67-69` assumes that `firstMatch` "resolves to the frontmost window's element". The same test's doc comment (`:33-35`) also says XCUI orders `app.windows` by creation order. If `firstMatch` resolves in creation order in the guest, `frontSidebar` is the *original* window's Sidebar. That Sidebar correctly stays expanded, and the assertion fails even though the app behaved correctly. Scoping the lookup to `app.windows.element(boundBy: 1)` would remove the dependency. The helper already exists as `sidebar(in window:)`, `:142-148`, and the test uses it at `:57`.
2. **Real behavior in the guest.** The new window isn't key in a headless guest, or Cmd-B isn't routed to it. Then no Sidebar collapses, or the original one does. `RootWindowView`'s key-window guard for the toggle (#0238) would then be doing something unexpected under the guest's window server.

The run's artifacts don't tell these apart.

## Expected behavior

The test passes in the VM and truly checks that only the key window's Sidebar collapses.

## Notes

- The test passed on the host in #0238 ("2/2 passing, confirmed twice", `issues/0238.md:50`). That host run used the old `scripts/run-ui-tests.sh` path on a machine with a real display.
- First diagnostic, in the VM only (`AGENTS.md` "UI test automation"): run `./build.sh ui BattyUITests/WindowRestorationTests/testToggleSidebarAffectsOnlyKeyWindow` with both windows' Sidebar widths logged before and after Cmd-B, using the per-window helper for each. That settles hypothesis 1 immediately.
- If hypothesis 1 holds, fix the test only and leave the `.xcresult` evidence in the issue. If hypothesis 2 holds, it's a real Window-module defect and `docs/view-hierarchy.md` applies.
