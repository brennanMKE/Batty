## Description

In #0412's first full Tart-VM run (run id `20260923-191103-94702`), this test failed at `BattyUITests/WindowRestorationTests.swift:72`:

```
XCTAssertTrue failed - Key window's sidebar must collapse after Cmd-B
```

The test does four things:

1. It launches, measures the Sidebar width (the `> 50 pt` assertion passed) and opens a second window with Shift-Cmd-N. The count `>= 2` passed, and so did the second window's Sidebar-exists check.
2. It presses Cmd-B.
3. It waits up to 5 s for `BattyUITestHarness.sidebar(in: app)` to become non-hittable or narrower than half its original width. **This is where it failed.**
4. It never reaches the check that the original window's Sidebar is still expanded.

In the same run, the related single-window and multi-window tests passed:

- `SidebarTests.testCmdBCollapsesAndExpandsSidebar`: Cmd-B collapses the Sidebar with one window.
- `MultiWindowTests` 3/3, including `testNewWindowHasIndependentSidebar`.
- `WindowRestorationTests.testNewWindowHasOneFreshSession`.

So Cmd-B works, and a second window with its own Sidebar works. The failure is specific to "Cmd-B with two windows, observed through an app-global lookup".

## Two hypotheses

1. **The test's element lookup picks the wrong window.** At step 3 the test uses the *app-global* `sidebar(in: app)`, which returns `app.collectionViews["session-sidebar"].firstMatch` or its fallbacks (`BattyUITests/Support/BattyUITestHarness.swift:130-136`). The comment at `WindowRestorationTests.swift:67-69` assumes that `firstMatch` "resolves to the frontmost window's element". The same test's doc comment (`:33-35`) also says XCUI orders `app.windows` by creation order. If `firstMatch` resolves in creation order in the guest, `frontSidebar` is the *original* window's Sidebar. That Sidebar correctly stays expanded, and the assertion fails even though the app behaved correctly. Scoping the lookup to `app.windows.element(boundBy: 1)` would remove the dependency. The helper already exists as `sidebar(in window:)`, `:142-148`, and the test uses it at `:57`.
2. **Real behavior in the guest.** The new window isn't key in a headless guest, or Cmd-B isn't routed to it. Then no Sidebar collapses, or the original one does. `RootWindowView`'s key-window guard for the toggle (#0238) would then be doing something unexpected under the guest's window server.

The run's artifacts don't tell these apart.

## Expected behavior

The test passes in the VM and truly checks that only the key window's Sidebar collapses.

## Root cause

**Note (review round 1, `c9bb6ac5`): the "creation order" resolution mechanism claimed below
is false — corrected in "Review round 1" further down. The identifier-collision premise (two
windows' `List`s sharing the literal identifier `"session-sidebar"`) is still accurate; only
the claim about *which* window an ambiguous app-global query resolves to was wrong.**

Hypothesis 1, believed confirmed by static reading before any VM run (later found incomplete —
see "Review round 1"). `SessionSidebarView.swift:89` applies
`.accessibilityIdentifier("session-sidebar")` to the top-level `List`, once per
`SessionSidebarView` instance — so with two windows open, two distinct AX elements in the
app both carry the identical identifier `"session-sidebar"`. `BattyUITestHarness.sidebar(in:
app)` (`BattyUITestHarness.swift:130-136`) queries `app.collectionViews["session-sidebar"]`
app-globally and takes `.firstMatch`, which is ambiguous between the two windows' Sidebars.
~~The test's own class doc comment (`WindowRestorationTests.swift:33-35`) already states the
resolving rule: XCUI orders `app.windows` (and, by extension, an app-global descendant query)
by creation order, not z-order/key-window — so `firstMatch` always resolves to the *original*
window's Sidebar (boundBy:0), regardless of which window Cmd-B actually affected.~~ **False —
that class doc comment (and `#0238.md:62`, which made the same "creation order" claim) is
itself contradicted by the VM logs; see "Review round 1" below. `app.windows` element order
reflects neither creation order nor a stable z-order in this guest.** The inline comment at
the old `WindowRestorationTests.swift:68-70` asserted the opposite ("resolves to the frontmost
window's element") with no citation, contradicting the class's own (also wrong) doc comment
two lines above it in the same file — both were wrong, just in different directions.

~~This matches every observed symptom: the original window's Sidebar never collapses (Cmd-B
correctly targets only the key/new window), so waiting for `frontSidebar` — which resolved to

interpretation of "why round 1 failed" does not survive review round 1 either — see below; the
identifier-collision problem was real, but "creation order" was not the actual resolution rule,
so the specific claim about which window `frontSidebar` pointed to in round 1 cannot be trusted
as stated.** The related passing tests (`SidebarTests.testCmdBCollapsesAndExpandsSidebar`,
`MultiWindowTests`, and this same test's own earlier `newWinSidebar` check at line 60, which
already uses the per-window `sidebar(in: window:)` overload) never exercise this app-global

**Ruled out: hypothesis 2 (real routing bug).** `RootWindowView.swift:59-66`'s
`.battyToggleSidebar` handler already gates correctly:
`guard AppStateStore.shared.keyWindowRuntime()?.id == windowID else { return }` — every
window's `RootWindowView` receives the notification (posted with `object: nil` from
`BattyShortcuts.run(_:appStore:)`), but only the one whose `windowID` matches the current key
window's runtime acts on it. This is unrelated to the failure and needed no change.

**Also checked and ruled out: the #0417 DisclosureGroup-folding mechanism.** #0417 found that
an `accessibilityIdentifier` applied to a `DisclosureGroup { content } label: { … }` as a
whole leaks into its `content` closure's descendants (`pane-row.*`, overridden by the parent
`session-row.*` identifier) because DisclosureGroup's List/NSOutlineView bridging doesn't
respect closer-wins nesting for AX identifiers. `sidebar(in:)` here resolves only the
top-level `List`'s own `"session-sidebar"` identifier (`SessionSidebarView.swift:89`, applied
directly to the `List`, not nested inside any `DisclosureGroup`) — it never reads a
`pane-row.*`/`session-row.*` identifier and never touches anything under the
`DisclosureGroup`. `List` also renders to a native `NSTableView`/`NSOutlineView`, which is
already a genuine AX container (unlike the plain `HStack` folding case documented at
`PaneView.swift:219-225`), so the single-window identifier `"session-sidebar"` resolves
correctly and unambiguously within one window — the passing `newWinSidebar` check at line 60
already proves this per-window resolution works. #0417's fix (`.accessibilityElement(children:
.contain)` / moving the identifier onto `SessionRow`) is not needed for this issue; no change
was made to `SessionSidebarView`'s `PaneRow`/`SessionRow` accessibility.

## Review round 1 (request changes) — `c9bb6ac5`

The reviewer read the VM logs directly (the "interrupting element" trace `xcodebuild` prints
when a click is obstructed) and found that `app.windows`'s element order in this guest is
**neither creation order nor z-order in the naive sense claimed by rounds 1–3, nor by
`#0238.md:62`** (that line's claim is contradicted by this evidence; `issues/0238.md` itself is
left unedited per the coordinator, since that issue is closed history, not this one).
SwiftUI's `WindowGroup(for: WindowID.self)` names each window internally as it is created —
`...-1-AppWindow-1` for the launch window, `...-1-AppWindow-2` for the Shift-Cmd-N window — and
these names appear verbatim in the xcodebuild log whenever XCUITest reports on a window (e.g.
the "Check for interrupting elements affecting ... Window" trace during a click). Reading that
trace across runs 2 and 3:

- Run 2, t≈4.76s: `Click Window (Element at index 1)` → interrupting-element check identifies
  `AppWindow-1` (the *original* window) as the element actually at that screen position, with
  `AppWindow-2` (the new window) reported as the covering "interrupting element". So
  `boundBy:1`, before any click, resolved to the *original* window.
- Run 2, t≈6.44s (after the first click and after Cmd-B): `Click Window (Element at index 0)`
  → resolves to `AppWindow-1` again. The first click raised the original window to the front,
  and it stayed there through the second lookup.
- Run 3: the same `boundBy:1` click again resolves to `AppWindow-1`, reproducing the exact same
  misdirection.
- `MultiWindowTests`' `app.windows.element(boundBy: 1).click()` (#0237) is the same pattern and
  is suspected of the same misdirection — not fixed here, filed separately by the coordinator.

**Conclusion:** `boundBy:` indices cannot be trusted to mean "the new window" (or any specific
window) at all in this guest — not before a click, and not reliably after one either. Every
prior round's interpretation of *which* window a `boundBy:`-indexed lookup pointed to was
unverified guesswork, and in the two cases the logs can actually confirm (runs 2 and 3), that
guess was wrong. **Run 1 is consistent with the product working correctly**: with no click at
all, Cmd-B most likely toggled the real new window while the test's `boundBy:1` lookup watched
the original — the very first, unmodified test's failure was plausibly a pure test bug from the
start, not evidence of a focus-timing gap needing a click-based workaround.

### Reasoning through the three ways Cmd-B could misbehave (coordinator's item 4)

The round-4 fix (below) identifies the new window and the original window by their own AX
`identifier`, captured before the ambiguity exists, then checks each one's sidebar directly —
no index, no click. Given that:

1. **Cmd-B does nothing.** The new window's sidebar (`frontSidebar`, identified by its own
   identifier) stays expanded — `!frontSidebar.exists || frontSidebar.frame.width <
   expandedWidth / 2` reads false, and the "Key window's sidebar must collapse" assertion times
   out and fails. Caught.
2. **Cmd-B toggles the wrong (original) window.** The new window's sidebar never collapses —
   same failure as case 1, at the same assertion. Separately, the original window's sidebar
   (`origSidebar`) would collapse instead of staying expanded, so even if case 1's assertion
   were somehow skipped, `origSidebar.exists && origSidebar.frame.width > expandedWidth / 2`
   would also fail. Caught (doubly).
3. **Cmd-B toggles both windows.** The new window's sidebar collapses, so the first assertion
   passes correctly. The original window's sidebar collapses too, so
   `origSidebar.exists && origSidebar.frame.width > expandedWidth / 2` reads false and the
   "Original window's sidebar must remain expanded" assertion fails. Caught.

All three failure modes are caught because each assertion is now scoped to a window identified
by its own identity, resolved once and reused, rather than by a `boundBy:` index that this
guest does not keep stable or meaningful.

## Fix, round 4

Rewrote `testToggleSidebarAffectsOnlyKeyWindow` to identify windows by AX `identifier`, never by
`boundBy:` index:

- Capture the original window's `identifier` via `app.windows.firstMatch.identifier` before the
  second window exists (only one window is present, so this is unambiguous).
- After Shift-Cmd-N, find the new window by scanning `app.windows.allElementsBoundByIndex` for
  the element whose `identifier` differs from the captured original — plain Swift iteration,
  no `NSPredicate`, no `.descendants(matching: .any)`.
- Resolve stable per-window element references with `app.windows.matching(identifier:)` (an
  exact identifier match, per the coordinator's instruction — no `MATCHES`).
- Replaced the click with a wait: poll until the new window (by identity) is
  `app.windows.element(boundBy: 0)` — i.e. actually frontmost — before dispatching Cmd-B,
  rather than forcing it with a click that (per Review round 1) reliably raised the wrong
  window in this guest.
- Both post-toggle checks now use `!exists || width < half` (collapsed) /
  `exists && width > half` (expanded) — dropped `isHittable` entirely (not just for the
  original window, as round 3 did, but for the new window's check too), since hittability
  depends on cross-window occlusion, which is unrelated to whether a given window's own sidebar
  actually collapsed.

No production code touched.

## Review round 2 (pre-VM, comment-only) — request changes

A second review pass, before spending a VM run, found the *code* sound but several doc-comment
claims in round 4 still wrong or overstated:

1. **Z-order claim overcorrected.** Round 4's class doc said `app.windows` order "cannot be
   trusted at all... neither creation order nor a stable z-order" — but the round-4 *code*
   itself relies on `app.windows.element(boundBy: 0)` meaning "frontmost" (the wait-for-frontmost
   check). The accurate statement, matching both the code and the run 2/3 evidence: `app.windows`
   **is** z-ordered (frontmost first) in this guest, so `boundBy:0` is the frontmost window at
   any given instant — what's unsound is treating a captured index as a stable reference to a
   *particular* window across a reorder (e.g. a click), which is what every prior round's
   misdirection actually was.
2. **"never a `.descendants(matching: .any)` query" was false.** `BattyUITestHarness.sidebar(in:)`
   (`:142-148`) itself falls back to `window.descendants(matching: .any).matching(identifier:
   "session-sidebar")` when the `.collectionViews`/`.outlines` lookups don't exist. That fallback
   is an exact identifier match, not a `MATCHES` predicate, so the SIGABRT gotcha (which is
   specifically about `MATCHES` evaluated against a non-string AX value) doesn't apply to it —
   but the doc comment's blanket "never" claim was wrong. Fixed by resolving `newWinSidebar` and
   `origSidebar` **before** Cmd-B is dispatched, while both sidebars still exist in their normal
   expanded state, so `sidebar(in:)`'s existence-based branching picks the specific
   `.outlines`/`.collectionViews` query at construction time; the same live `XCUIElement`
   reference is then polled after the toggle (XCUIElement properties re-resolve on every access,
   so this doesn't go stale).
3. **"tracked separately" needed citations, and one was wrong.** `MultiWindowTests`' misdirected
   click is now filed as **#0438** (`MultiWindowTests.testNewWindowHasIndependentSidebar` clicks
   the original window instead of the new one). The new-window-key gap is **#0437**, and it is
   *not* "a freshly `openWindow`-created window is not guaranteed to be `NSApp.keyWindow` the
   instant its content is accessible" as round 4 said — #0437's actual mechanism is that
   `WindowIDRegistrar`'s registration of the new window into `AppStateStore.nsWindowMap` is
   deferred one main-queue turn and **never retried**; if the view's `window` is still nil when
   that deferred block runs, the window may never be registered until some later, unrelated
   `updateNSView` call. `keyWindowRuntime()` — which both `BattyShortcuts` and `RootWindowView`'s
   toggle handler depend on — reads that map, not AX/window-server frontmost status. This test's
   wait for AX frontmost (`boundBy:0` by identity) does **not** close that race: a window can be
   genuinely frontmost by AX while still absent from `nsWindowMap`. If #0437 reproduces, this
   test can still see Cmd-B dropped entirely — that would be a real #0437 reproduction, not a
   reason to add another workaround here.

## Fix, round 6

VM run 5 failed at the window lookup itself: `matching(identifier:)` with SwiftUI's
auto-generated window identifier (`SwiftUI.PresentedWindowContent<…>-1-AppWindow-1`) throws
because XCUITest caps string identifiers in a query at 128 characters. The app assigns no
identifier of its own to windows, so both lookups now use
`app.windows.matching(NSPredicate(format: "identifier == %@", id)).firstMatch` — the workaround
the XCTest error names. An equality predicate on a string is not the `MATCHES`-on-non-string
SIGABRT case in `docs/ui-testing-vm.md`. Window identity, the frontmost wait, and both
sidebar checks are unchanged. Commit `580f56f8`.
