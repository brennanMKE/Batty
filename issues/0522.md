# 0522 — `SettingsTests` assumes a single content Window and finds Settings by window index, and no UI test covers Settings or the global Theme with two content Windows open

## Description

`BattyUITests/SettingsTests.swift` finds the Settings Window by counting Windows and by index. That only works while exactly one content Window exists, and one of its assertions cannot tell which Window it found.

- **Line 36, `testCmdCommaOpensSettings`.** `waitFor({ app.windows.count >= 2 }, ...)` treats "any second Window" as Settings. The comment above it says so: "Assert any second window appears."
- **Lines 58 and 63, `testSettingsWindowCanBeDismissed`.** `app.windows.count >= 2` stands for "Settings opened", and `app.windows.count < 2` for "Settings closed". This test does identify the content Window by `identifier` (line 49, checked at line 67), which is the right pattern.
- **Lines 86 and 91, `testSettingsDefaultsToGeneralPane`.** After `app.windows.count >= 2`, it takes `let settingsWindow = app.windows.element(boundBy: 1)` and asserts only `frame.width > 200`. `app.windows` is z-ordered, frontmost first (see the `WindowRestorationTests` doc comment and #0438). So after Cmd-, the frontmost Window, index 0, is most likely Settings, and index 1 the content Window. The content Window is also wider than 200 pt, so the assertion passes whichever Window index 1 resolves to.

With a second content Window open, `count >= 2` is true before Settings opens, and `count < 2` never becomes true after it closes. All three tests would then pass or fail for the wrong reasons.

Nothing covers Settings or the global Theme with two content Windows:

- **Settings with two content Windows.** No test opens Settings while two content Windows exist and checks that it opens once, that Cmd-W closes Settings and not either content Window, and that both content Windows keep their Tabs. This is the multi-window form of #0196 / #0480.
- **Global Theme across Windows.** #0243 fixed `AppStateStore.applyThemeToAllSurfaces(_:)`, which iterated only `windows[0]`'s sessions. Its Notes asked for exactly this: "once #0240's UI suite can run, add multi-window coverage asserting a global theme change recolors surfaces in every window". `ThemeTests` has no multi-window test. Its global-theme test (`testApplyGlobalThemeDoesNotCrash`) applies a theme through the `applyTheme` driver intent and checks only that the Session row still exists. `UITestDriver` has no way to read back which theme a given Window's surfaces are using.

**Out of scope.** Per-window Theme isolation. Theme is app-wide by design (`docs/multi-window-design.md` §10, "Per-window themes"; `Concepts.md` § Theme). The per-Session override (`applyThemeToActiveSession`) is a separate path and already has its own test.

## Expected behavior

- `SettingsTests` finds the Settings Window by a stable identifier or title, not by `windows.count` or `boundBy:`, and passes the same way with one or two content Windows open.
- A test opens two content Windows, opens Settings, and asserts:
  - one Settings Window;
  - Cmd-W closes only Settings;
  - both content Windows (looked up by `identifier`) still exist with their Tab counts unchanged.
- A test opens two content Windows, applies a global Theme, and asserts that the Theme reached the terminal surfaces in **both** Windows, including a Window that is not key.

## Actual behavior

The Settings tests rely on there being exactly one content Window. `testSettingsDefaultsToGeneralPane`'s Window assertion passes whichever Window it resolves to. There is no multi-window coverage for Settings or the global Theme, so a regression of #0243 would pass the suite.

## Notes

- **Settings Window identity.** First check what accessibility identifier and title the SwiftUI `Settings` scene's Window has on the guest. `SettingsView` (`BattyKit/Sources/BattyKit/Views/SettingsView.swift`) sets no `accessibilityIdentifier`; it is a `TabView` with General, Appearance, Shortcuts, Notifications and Advanced items. If the scene's identifier isn't stable, add one in `SettingsView`, or match by title. Use an exact match. Avoid `MATCHES` against non-string AX values (`docs/ui-testing-vm.md` "Known limits").
- **Theme observability.** The Theme test needs something it can read per Window. For example, an accessibility value on the terminal host or placeholder that exposes the applied theme name, set only from the code path that applies the theme, or a CLI query if one exists. Any new test seam must not change production behaviour (AGENTS.md).
- **Window identity.** Capture each content Window's `identifier` before opening the next one, and look them up with `BattyUITestHarness.window(withIdentifier:in:)`, as `WindowRestorationTests` does. Do not use `app.windows.element(boundBy:)`; #0438 is that bug in `MultiWindowTests`.

## Acceptance criterion

`SettingsTests` contains no `windows.count` comparisons or `boundBy:` lookups for Settings. A VM run includes and passes:

- the updated `SettingsTests`;
- a Settings-with-two-content-Windows test;
- a global-Theme-reaches-both-Windows test that fails when `applyThemeToAllSurfaces` is reverted to iterate only the first Window's sessions (checked once by hand and recorded in the Work log).
