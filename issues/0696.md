# 0696 — Experiment: a LaunchAgent helper (BattyHost) owns each Session's PTY so Sessions survive app quit, crash and update

| | |
|---|---|
| **Status** | open |

| **Target** | 1.6.0 |

## Description

**Experiment, Beta only, never merged to `main` without a later user decision.** Today the app process owns every Terminal Session's PTY master, so quitting, crashing or updating Batty sends SIGHUP to every shell and the user starts over. An app update is the worst case: every Sparkle update throws away all running work.

The experiment moves PTY ownership into a per-user LaunchAgent, **BattyHost**, embedded in `Batty Beta.app`. The app becomes a client: on launch it reconnects to the helper and reattaches each Terminal Session as it was, with its current screen. The protocol is designed so a later remote client (a MacBook reaching a Mac mini over Tailscale, see #0695) can use the same frames; the remote client itself is out of scope.

User request (2026-11-19): "Create a branch to experiment with the beta build to run a launchd helper which would hold onto the PTY for each terminal session so it would be possible to restart the Batty app and reattach each session exactly as it was. This would support app upgrades which are typically very disruptive because you have to start over with everything."

The user's brief is attached as [`0696/batty-pty-host-experiment.md`](0696/batty-pty-host-experiment.md) and is the source for architecture, protocol v1, phases, questions and acceptance criteria. **Read it in full.** This issue records how it is adapted to the Batty repo.

## Changes from the brief (user direction, 2026-11-19)

- **Not a separate Xcode project.** The brief says "a throwaway prototype in its own Xcode project, not a change to the Batty codebase". The user now wants it **in the Batty repo, on an experiment branch, built and run as Batty Beta** (`./build.sh`, `./build.sh package [--sign]`). The brief's "Changes to the real Batty repo" out-of-scope line no longer applies.
- **Branch.** Work happens on `issue/0696` in its own worktree, per `issues/Issues.md`. Unlike a normal issue, **the branch is not squash-merged to `main` when the review passes.** It stays an experiment branch until the user decides, in words, to merge it, rework it, or drop it. Only filing and notes commits for this issue go to `main`.
- **Feature flag.** If any of it is ever merged, it sits behind a new `FeatureFlags.ptyHost` (`BattyKit/Sources/BattyXPCCore/FeatureFlags.swift`, recipe in `docs/feature-flags.md`): on in Beta, off in Prod, a UI-test force-off override, and gate sites recorded in `docs/feature-flags.md`. With the flag off, nothing about BattyHost is visible or active: the helper is not registered, nothing connects to it, and every surface uses today's `.exec` backend. Build the flag on the branch from the start, so the flag-off path is the unchanged app.
- **Progressive disclosure (`AGENTS.md`, binding).** Even in Beta, BattyHost is **opt-in from Settings** (for example Settings › Advanced › "Keep terminals running when Batty quits"), off by default. Registering a new LaunchAgent makes macOS show a "background item added" notification and may need approval in System Settings › General › Login Items. That must happen only after the user turns the setting on, never at launch (#0674). The `.requiresApproval` guidance is shown in that Settings row, not as a launch sheet or banner.
- **Names.** Batty's real bundle IDs are `co.sstools.Batty` / `co.sstools.Batty.beta` (`ServiceNames.Variant.appBundleIdentifier`), so the brief's `co.sstools.batty.host` becomes e.g. label `co.sstools.Batty.beta.host`, Mach service `co.sstools.Batty.beta.host.xpc`, plist `co.sstools.Batty.beta.host.plist`, and the logging subsystem follows `Logging.subsystem`. Add these to `ServiceNames` next to the broker's names, with per-variant helpers.
- **Vocabulary.** The brief's "session" is a Batty **Terminal Session** (`Concepts.md`); a Batty **Session** is the workspace grouping. The helper's registry holds Terminal Sessions keyed by the Tab's id; `clientMetadata` carries the Window/Session/Pane/Tab placement the app needs to rebuild the layout.

## Precedent already in the repo

Batty already ships a LaunchAgent the same way the brief describes, which lowers the risk of the packaging part:

- `BattyBroker` (`BattyKit/Sources/BattyBroker`) is built by the "Embed Broker" Run Script phase into `Contents/Resources/bin/BattyBroker` (`ServiceNames.agentBundleProgram`) and signed there with the app's identity (`codesign --options runtime`, `--timestamp` only for `ACTION=install`), the same as the embedded CLI.
- Its plist is at `Contents/Library/LaunchAgents/co.sstools.Batty.beta.broker.plist`, registered through `SMAppService.agent(plistName:)` by `BrokerAgentController` (`BattyKit/Sources/BattyKit/Settings/BrokerAgentController.swift`), which already maps `SMAppService.Status` including `.requiresApproval`.
- Mach-service XPC with code-signing checks between app, broker and CLI is in `BattyKit/Sources/BattyKit/XPC/` and `docs/batty-cli-design.md` §1.3.

BattyHost should copy this pattern (a SwiftPM executable in `BattyKit`, an embed phase, a second plist) rather than invent a new one.

## Phase 0 result (verified by the filer, 2026-11-19): libghostty can render a PTY it doesn't own

Mostly answered already, with no libghostty changes. The vendored `Lakr233/libghostty-spm` carries a host-managed termio backend (`Patches/ghostty/0002-host-managed-io.patch` adds `src/termio/HostManaged.zig`), exposed in Swift as `TerminalSessionBackend.inMemory(InMemoryTerminalSession)` through `TerminalSurfaceOptions.backend` (default `.exec`). Batty uses only `.exec` today; nothing in `Batty/` or `BattyKit/Sources` references `InMemoryTerminalSession`.

What `InMemoryTerminalSession` (`BattyKit/.build/checkouts/libghostty-spm/Sources/GhosttyTerminal/InMemory/InMemoryTerminalSession.swift`) provides:

- **Output in:** `receive(_ data:)` enqueues bytes onto a per-session serial queue that calls `ghostty_surface_write_buffer` (the same `io.processOutput` path PTY bytes take). Bytes that arrive before a surface attaches are buffered (1 MiB cap, oldest dropped) and flushed on attach.
- **Keystrokes out:** the `write:` handler gets everything the surface would write to a PTY (key encoding, paste, and the terminal's own query replies), with LNM CR→CRLF applied as `Exec` does. `sendInput(_:)` injects bytes straight to the handler.
- **Resize out:** the `resize:` handler gets `InMemoryTerminalViewport` (cols, rows, pixel and cell sizes), deduplicated; `suppressesPixelOnlyResizes` optionally drops pixel-only changes. The helper turns it into `TIOCSWINSZ`.
- **Exit:** `finish(exitCode:runtimeMilliseconds:)` calls `ghostty_surface_process_exit` after all earlier bytes, which drives the normal "Process exited" path.
- **Replay ordering:** `waitForPendingOutput()` blocks until all received bytes are parsed, including their writeback. `readViewportText()` reads the visible grid.
- **Separately, in the C API:** `ghostty_surface_write_buffer_replay` (`Patches/ghostty/0011-replay-response-suppression.patch`) parses bytes as history and drops the protocol responses they cause. Ring-buffer replay needs this: without it, replayed DA/DSR/OSC queries make the surface send answers into the live shell as if the user typed them. `InMemoryTerminalSession` does **not** expose it yet (`receive` always uses `write_buffer`), so the experiment needs a small Swift addition, or a patch to the package, for a `receiveReplay(_:)`.

Not lost: titles (OSC 0/2), bell (BEL), OSC 9/777 desktop notifications, OSC 7 pwd, OSC 133 prompt marks and `COMMAND_FINISHED`, OSC 52 clipboard and its confirmation, progress reports, mouse reporting and mouse shape, links, scrollback and selection. All of these come from ghostty's shared stream handler and the runtime action callbacks (`TerminalCallbackBridge.handleAction`), which run the same way for either backend, because the host-managed backend only replaces the PTY transport.

Gaps, which the experiment must close in the helper or the client:

1. **Everything the `.exec` backend does at spawn is skipped.** `command`, `working-directory`, `env` (Batty's `BATTY_TAB_ID`/`BATTY_PANE_ID`/`BATTY_SESSION_ID` from `TabRuntime`), `TERM=xterm-ghostty` plus `TERMINFO`/`GHOSTTY_RESOURCES_DIR`, and **shell-integration injection** (Batty's MIT shell-integration scripts via `shell-integration`/`shell-integration-features`, see `SettingsPreferences`) are applied only by `termio.Exec`. The helper must reproduce them when it spawns, or OSC 133, `COMMAND_FINISHED`, `jumpToPrompt`, close-confirmation and the `ssh-env` feature stop working. Also `wait-after-command` and `abnormal-command-exit-runtime` (Project startup commands) become the client's job.
2. **Process identity.** `foregroundPid` and `ttyName` are stubs that are nil for every backend on the pinned Ghostty 1.3.1, so nothing is lost there, but any Batty code that finds a Tab's processes (`ServerJobOwnership` matches `BATTY_TAB_ID` in process environments; the process-status view) must now see shells whose parent is BattyHost, not the app. Check those still work.
3. **Exit details.** `HostManaged.childExitedAbnormally` is a no-op, so the abnormal-exit banner text comes only from what the client passes to `finish`.
4. **Focus reporting.** `HostManaged.focusGained` is a no-op. Check whether focus-in/out (CSI I/O, mode 1004) still reaches the program through the write handler.
5. **Replay is bytes, not state.** The surface rebuilds state by parsing. A raw ring buffer that starts mid-sequence or mid-alternate-screen can garble the screen (brief Phase 3).

So Phase 0 is not a blocker. The brief's instruction stands: **report this Phase 0 result to the user and wait for their go-ahead before writing Phase 1 code.**

## Scope

Brief Phases 0–4, adapted:

1. **Phase 0.** Confirm the findings above with a small proof on the branch: one Tab on `.inMemory`, fed by a PTY the app opens itself through the shim, in Beta behind `ptyHost`. Report to the user.
2. **Phase 1, helper owns PTYs.**
   - `PTYShim`: a C target in `BattyKit` with `forkpty` + `execve` (argv, envp, cwd, winsize in; master fd and pid out), `setsid` and controlling-tty setup in the child, async-signal-safe between fork and exec. No `fork` from Swift.
   - `HostProtocol`: a Swift target in `BattyKit` shared by app and helper. Framing is a 4-byte big-endian length, a 1-byte type and a payload; message set and heartbeat as in the brief's protocol v1 table; a version constant.
   - `BattyHost`: a SwiftPM executable embedded like `BattyBroker` (a new "Embed Host" phase), with its plist in `Contents/Library/LaunchAgents/`, `BundleProgram`, `MachServices`, and no `KeepAlive`. It spawns login shells with the gap-1 environment, keeps masters open on dispatch sources, ignores SIGPIPE, keeps a 2 MB raw ring buffer per Terminal Session, reaps children and keeps the exit status, keeps the registry (with `clientMetadata`), stays alive while any Terminal Session exists, logs with `os_log`, and applies backpressure (stops reading a master while the client socket is full).
   - XPC bootstrap: the app connects to the Mach service, both sides check the other's code signature (`setCodeSigningRequirement`), and the helper returns a connected Unix socket as a `FileHandle`. All traffic after that goes over the socket.
   - Client: with `ptyHost` on and the Settings opt-in on, `TabRuntime` creates `.inMemory` surfaces wired to the socket. The output frame goes to `receive`, the write handler sends input, the resize handler sends resize, and exit calls `finish`. Replay uses `write_buffer_replay`. With the opt-in off, `.exec` as today.
3. **Phase 2, reattach on launch.** On launch: register (only if opted in), connect, `hello`, `listSessions`, rebuild Windows/Sessions/Panes/Tabs from `clientMetadata`, attach every live Terminal Session, show the replay, and resume streaming. Run the brief's survival tests: `top` plus `sleep 600; echo done` across a normal quit, `kill -9` of the app, and output generated while the app is gone.
4. **Phase 3, snapshot quality.** Raw replay with vim or htop and with the ring overflowed. Then try ghostty's VT layer headless in the helper and compare.
5. **Phase 4, simulated update.** Replace `Batty Beta.app` on disk the way Sparkle does, then relaunch. Record the helper PID across it, the agent's state, and what calling `SMAppService.register()` again does. Test a protocol mismatch (a v2 app against a v1 helper): the app shows a clear "helper needs restart" state and doesn't crash.
6. **Debug info.** The helper PID, protocol and helper versions, the registry, and a "Kill helper" action. Put it in an existing diagnostics or Settings surface, or a Debug menu item, not a new always-visible control.

Stretch: Phase 5 (helper handoff of master fds over `SCM_RIGHTS`, with reaping after reparenting) and Phase 6 (several clients and the input lease).

Out of scope, as in the brief: network transport and remote authentication, restoring across reboot or logout, and Prod.

## Risks and constraints

- **Developer ID signing (binding, `AGENTS.md`).** The embedded helper is signed exactly as `BattyBroker` is, by the build phase with the identity the build already uses. A Developer ID-signed Beta comes only from `./build.sh package --sign` with the committed manual profiles in `Configuration/Profiles/`. **Never** use `-allowProvisioningUpdates` or `-allowProvisioningDeviceRegistration`, never use Automatic signing for a Developer ID build, never touch Xcode Accounts, certificates, profiles or Keychain identities. If the helper turns out to need a new provisioning profile, a restricted entitlement, or an App Group, **stop and ask the user** rather than working around it. No notarization without the user's go-ahead each time.
- **Restricted areas.** Any change to `Configuration/Build.xcconfig` or `scripts/` needs the user's confirmation first. A new build phase in `Batty.xcodeproj` is allowed; changes to the existing signing settings are not.
- **SMAppService approval.** Registration can return `.requiresApproval` and macOS shows a background-item notification. Both must happen only after the user turns on the Settings opt-in (progressive disclosure). Note what the user has to click, for the eventual Help text.
- **Terminal features lost through the in-memory surface** (gaps 1–5 above). Every regression found goes into `## Findings` with a note on whether the helper can fix it. Run the `docs/terminal-pane-requirements.md` checklist on an `.inMemory` Tab (pointer input, keyboard, file drop, text drop, IME).
- **Surface registry and host rules.** The `TerminalHostStore` and Surface registry rules in `docs/view-hierarchy.md` §4 still apply: a surface is created once per Tab and not destroyed by view rebuilds. Reattach creates new surfaces for Terminal Sessions the helper already owns.
- **Two Batty Beta instances, and Prod.** Prod must never talk to the Beta helper. Variant-specific names prevent it; check it.
- **Testing.** Unit-test `HostProtocol` framing, the ring buffer, the registry and backpressure in `BattyKitTests` with no sleeps (`AGENTS.md` "Asynchronous tests"; drive heartbeats with an injected clock). The shim and helper spawn real children, so those tests must be `nonisolated` and await readiness through a pipe. **UI tests in the Tart VM may not be able to exercise a LaunchAgent**: `SMAppService` registration and approval inside the VM's test user are unproven. Survival and update tests are expected to be manual on the host with Batty Beta, run by the user or with their consent (memory: never restart the running app without asking). Record what could and couldn't be automated.
- **Shell environment under launchd.** The helper's environment is launchd's minimal one. Login shells fix `PATH`, but check `LANG`, `SSH_AUTH_SOCK` and similar against an `.exec` Tab.

## Acceptance

From the brief, against Batty Beta with `ptyHost` on and the Settings opt-in on:

- Phases 0 through 4 done, and the Phase 0 report given to the user before Phase 1 code.
- Quitting or crashing Batty Beta never kills a Terminal Session.
- After a relaunch, every live Terminal Session is visible, in its Window/Session/Pane/Tab place, and usable within 1 second.
- No unbounded memory growth in the helper under sustained output (`yes` for 10 minutes).
- With the flag off, or the opt-in off, Batty behaves exactly as today: no agent registered, no helper process, and `.exec` surfaces.
- `./build.sh` and `./build.sh unit` pass on the branch, and the Release archive check builds (the helper adds a target compiled at `-O`).
- The brief's seven "Questions to answer" (its `EXPERIMENT_RESULTS.md`) are answered in a `## Findings` section of this issue, with PIDs and logs as evidence, instead of a separate file. Question 7 also says whether and how the branch should reach `main`.
