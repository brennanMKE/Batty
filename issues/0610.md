# 0610 — PaneView writes its frame and size to @State from onGeometryChange, so every resize re-runs every mounted PaneView body to feed an unobserved tracker

## Description

**HIGH. Related to #0601 and #0604.** Each `PaneView` writes `frameInSession`, `paneWidth` and `paneHeight` to `@State` from `onGeometryChange`, and its own `body` reads all three: `frameInSession` in a `.preference(PaneFramePreferenceKey)`, `paneWidth` through `chipMaxWidth`/`charBudget` for the tab strip, `paneHeight` in the drag preview. So every frame change is a layout-origin write that re-runs the whole `PaneView.body` (tab bar, `ForEach` of placeholders, overlays, `.task`/`onChange` re-registration), then the preference reduction and `SessionDetailView`'s `onPreferenceChange`, all inside `NSHostingView.layout`. The preference only feeds `SessionRuntime.paneFrames`, a plain class no view observes, read only by the keyboard command `focusPane(adjacent:)`. Window resize, sidebar toggle and divider drag move every Pane, and because every Session stays mounted (#0604), a window resize does this for every Pane of every Session, hidden ones included.

### Premises checked

All of the issue's "Current state" lines hold at `b940f47d`, with the line numbers shifted by about 1. Extra findings:
- `charBudget` (`PaneView.swift:79-82`) is **dead**. Nothing reads it, and it is the only user of `approxCharWidth`, `chipChromeWidth`, `charBudgetMin` and `charBudgetMax`. `PaneView.truncate(_:limit:)` is also unused in production, but `PaneViewTruncateTests` covers it. Keep it.
- `paneHeight` is read only in `paneDragPreview`, and `paneWidth` only in `chipMaxWidth` and `paneDragPreview`.
- `onPreferenceChange` replaces the whole dict, so today a closed or hidden Pane (unmounted, see `SplitNodeView`'s `isHidden` arm) silently drops out of `paneFrames`. A direct write loses that for free, so removal must be explicit.
- A split rebuilds the split Pane's `PaneView`. `SplitNodeView` returns `AnyView`, and a `.leaf` becomes a `DraggableSplitView` at that position. So for one `pane.id`, the old instance's `onDisappear` and the new instance's first `onGeometryChange` can run in either order. A plain "remove on disappear" could delete the new instance's fresh entry. `PaneViewRenderTests.splitRerendersTheHostedTreeWithAllottedNonDegenerateGeometry` exercises exactly this, because it needs the split Pane's frame after the split. The fix: an owner token per view instance (below).
- There is precedent for writing unobserved storage from `onGeometryChange`: `TerminalPlaceholderView`'s `onGeometryChange` calls `TerminalHostStore.reportFrame(_:forTabID:)` (`docs/swiftui-observation-rules.md` ~l.168).
- Other `paneFrames` users: `BellFeedVisitTests.setSideBySideFrames` assigns `paneFrames.frames` directly, so `frames` must stay settable from `@testable` code. `SplitTree.swift:131,189` comments cite `paneFrames` as precedent. They stay accurate.

### Files and approach

1. **`BattyKit/Sources/BattyKit/Commands/PaneFocus.swift`**
   - `PaneFrameTracker`: keep `frames` (change it to `public internal(set) var frames`). Add a private `owners: [UUID: UUID]` (paneID to the token of the view instance that last recorded it), plus:
     - `func record(_ frame: CGRect, for paneID: UUID, owner: UUID)`: sets `frames[paneID]` and `owners[paneID]`. Skip the write when both are unchanged; it is cheap either way.
     - `func remove(paneID: UUID, owner: UUID)`: removes the entry only when `owners[paneID] == owner`, so a stale instance's disappear can't delete its successor's entry.
     - One `///` line on the class saying why it stays unobserved: `focusPane(adjacent:)` reads it on demand, and making it observable would re-run views on every resize.
   - Delete `PaneFramePreferenceKey`.
   - Add `extension EnvironmentValues { @Entry var paneFrameTracker: PaneFrameTracker? = nil }`, the same `@Entry` style as `WindowSeeThrough.swift:9`. It must be `nonisolated`/`Sendable`-clean under the package's isolation. If `@Entry` with a non-Sendable class default complains, follow the `EnvironmentPaneAllottedSizeKey` pattern in `SplitContainerView.swift` instead.
   - `focusPane(adjacent:)` is unchanged.

2. **`BattyKit/Sources/BattyKit/Views/SessionDetailView.swift`** (`sessionStack`, ~l.258-266): replace `.onPreferenceChange(PaneFramePreferenceKey.self) { … }` with `.environment(\.paneFrameTracker, session.paneFrames)`. Keep `.coordinateSpace(name: "session")`.

Attach it to a `Color.clear` background as today, so the measured rect is still the post-`.frame(allottedSize)` pane rect. This writes no observed state, so it invalidates no body. Add a short comment saying exactly that, and that the token handles the split rebuild ordering.

The chip closure keeps the current modifier order exactly (`.frame(width:)` stays before the accessibility and context-menu modifiers). The `.accessibilityElement(children: .contain)` and `.accessibilityIdentifier("tab-bar.<uuid>")` stay on the `SlidingTabBar` inside the strip. `paneDragHandle` and `paneEyeButton` stay in `PaneView`'s `HStack`.
   - Drag preview: replace `paneDragPreview`'s `paneWidth`/`paneHeight` reads. Pass a small `PaneDragPreview` view (private struct, same file) the title, fill, text color and accent, plus `paneID` and `tracker`. Its own `body` reads `tracker?.frames[paneID]?.size ?? .zero` and applies the existing clamps (`max(160, min(w*0.5, 360))`, `max(96, min(h*0.5, 240))`). The `onDrag(preview:)` builder runs inside `PaneView.body`, but the preview view's own body runs when SwiftUI renders the preview at drag start. So it reads the current size and adds no dependency, because the tracker is unobserved. With no tracker (tests or previews) the preview falls back to the 160x96 minimum.

### User checklist

- Split a Session into a 2x2 grid. Cmd-Option-arrow moves focus to the expected neighbor in all four directions, also after resizing the window, dragging a divider and toggling the sidebar.
- Close or hide a Pane, then Cmd-Option-arrow from its neighbor: focus never jumps to the gone Pane.
- Many Tabs in a narrow Pane: chips shrink evenly and don't overflow into the neighbor; the drag handle and eye button stay visible. One Tab in a wide Pane is capped at the old width.
- Drag a Pane's swap handle: the drag preview is about half the Pane's size (clamped), not the minimum box.
- Window resize with many Sessions open feels no worse (ideally smoother).

## Resolution

- `PaneView` no longer holds `paneWidth`, `paneHeight` or `frameInSession` in `@State`. Its `onGeometryChange` writes the session-space frame straight into the unobserved `PaneFrameTracker` (`record(_:for:owner:)`), reached through a new `paneFrameTracker` environment value that `SessionDetailView` injects per Session. `onDisappear` calls `remove(paneID:owner:)`; the per-instance owner token stops a split's stale instance from deleting its successor's entry. `PaneFramePreferenceKey` and the `onPreferenceChange` are gone.
- The tab strip moved into `PaneTabStrip` (`Views/PaneTabStrip.swift`), which owns its own `@State stripWidth` and computes chip width (`chipWidth(stripWidth:tabCount:)`, same math as before with the drag-handle/eye-button reservations falling out of the measurement). The dead `charBudget` and its constants are deleted.
- The drag preview is a `PaneDragPreview` view that reads the Pane's size from the tracker when it renders.
- `docs/swiftui-observation-rules.md`: one paragraph on where geometry lives.

## Rule violated

- `docs/swiftui-observation-rules.md`, "What counts as SwiftUI-driven update code": `onGeometryChange` writes are audited by origin; these are geometry-origin writes to state the same body reads.
- Same doc, dependency granularity: one fact (width) invalidates the whole body.
- swift-guidance `swiftui-observation.md` / `performance.md`: keep geometry state in the smallest view that uses it; don't round-trip geometry through preferences into state when a direct write to unobserved storage will do.

## Evidence

- **Proven:** the writes, the reads and the unobserved tracker. It converges (nothing feeds back). #0602's audit classed this as "view-local @State, fine"; the body reads it, so it is not free.
- **Inferred:** the magnitude per resize frame across many Sessions. Measure with the probe.

## Fix direction

- Delete `frameInSession`, the `PaneFramePreferenceKey` emission and `onPreferenceChange`. Write the frame straight into the unobserved tracker from `onGeometryChange` (for example `session.paneFrames.record(pane.id, frame)`, passing the tracker down), or compute frames on demand in `focusPane(adjacent:)`. A write to unobserved storage from `onGeometryChange` invalidates nothing. Remove a Pane's entry when it closes.
- Move the width dependence into a small child view (e.g. `PaneTabStrip`) that owns its own `@State paneWidth` from its own `onGeometryChange`, so a width change re-evaluates only the strip. Read `paneHeight` only in the drag preview (or lazily at drag start).
