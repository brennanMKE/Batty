# 0393 — Modified keys are mis-encoded at the shell prompt, so Shift-Enter prints a literal `;2;13~` report instead of running the command

| | |
|---|---|

| **Platform** | macOS |
| **First seen** | 2026-09-02 |

## Description

**Modifier-key encoding is broken in Batty for at least some modifier + key combinations, and it is a class of bug, not a single key.** The reported instance is **Shift-Enter**: at a plain zsh prompt it prints literal garbage onto the command line instead of running the command. The user also reports misbehaviour with the **Option modifier and the arrow keys**, so the issue is scoped to modifier-key encoding generally. Apple's Terminal.app runs the command on Shift-Enter, and that is the behaviour the user expects.

After a few Shift-Enter presses the terminal "gets into a bad state" and further keys misbehave.

## Steps to reproduce

1. Launch Batty, open a Pane with a zsh prompt.
2. Type any command.
3. Press **Shift-Enter**.
4. Repeat a few times.

Also (second, possibly distinct case): press **Option-Left / Option-Right / Option-Up / Option-Down** at the prompt and inside a TUI.

## Expected behavior

Shift-Enter runs the command, exactly as Terminal.app does. No printable characters are inserted into the line editor. Modified keys generally either perform their action or emit an encoding the running application actually understands.

## Actual behavior

Observed by the user:

```
➜  ~ printf '\033]52;c;?\a'
➜  ~ 52;c;cHJpbnRmICdcMDMzXTUyO2M7P1xhJw==;2;13~;2;13~;2;13~;2;13~
```

Each trailing `;2;13~` is one Shift-Enter press (four presses, four repeats). Nothing runs; the text accumulates on the line.

**Reading the two halves of that line — they are different things, and only the second is this bug:**

- `52;c;cHJpbnRmICdcMDMzXTUyO2M7P1xhJw==` is the **correct** OSC 52 reply to the query the user typed on the line above. The base64 decodes to `printf '\033]52;c;?\a'` — the user's own clipboard contents. Querying OSC 52 from a bare shell prompt always lands the answer on the ZLE input line, because nothing is reading it. **Not a defect; ignore it when triaging.**
- `;2;13~` **is** the bug.

## Notes

### What `;2;13~` actually is (corrects the initial hypothesis)

The remainder is consistent with **`ESC[27;2;13~`** — xterm's **`modifyOtherKeys` mode 2** report, whose form is `CSI 27 ; <modifier> ; <codepoint> ~`. The leading `ESC[27` is absorbed by ZLE's keymap lookup (`ESC[` is a bound prefix), and the unmatched remainder self-inserts. `2` is the Shift modifier; `13` is CR.

It is **not** a `CSI 13;2~` report, and it is **not** the Kitty keyboard protocol (that form ends in `u`, not `~`).

Verified in the Ghostty source the Beta build links (`/Users/brennan/Developer/brennanMKE/libghostty-spm/References/ghostty-upstream`, ref `c4e16970a803b170e352432424f44192cb59f3ac`, 2026-08-25):

- `src/input/key_encode.zig:472` emits `"\x1B[27;{};{}~"`.
- It is gated at `src/input/key_encode.zig:418` on `opts.modify_other_keys_state_2`.
- That option is fed from the terminal's own flag at `src/input/key_encode.zig:66` (`.modify_other_keys_state_2 = t.flags.modify_other_keys_2`).
- `src/terminal/Terminal.zig:109` declares `modify_other_keys_2: bool = false` — **off by default**.
- `src/terminal/stream_terminal.zig:445-447` is the only place it flips on: an application writing `CSI > 4 ; 2 m` (`other_keys_numeric`).

**So the terminal is in `modifyOtherKeys` mode 2 at a bare zsh prompt.** No Batty config default turns that on; some application must have set it and never reset it. That is also the most likely explanation for the reported "bad state" — the mode persists after the app that enabled it exits, and zsh does not reset it. Terminal.app does not implement `modifyOtherKeys` at all, which is why the same keypress "just works" there.

### `keybind = clear` — real, worth fixing, but *not* the mechanism for Shift-Enter

The reported hypothesis was that `keybind = clear` swept away a Ghostty default `shift+enter` binding. **The `clear` call is real and confirmed, but the `shift+enter` default it supposedly removed does not exist.**

Confirmed in the tree at `BattyKit/Sources/BattyKit/Runtime/TabRuntime.swift`, inside `applyShellAndAppearancePreferences(to:)` — line numbers hold exactly as reported:

```swift
// TabRuntime.swift:237-244
builder.withCustom("keybind", "clear")
builder.withCustom("keybind", "cmd+c=copy_to_clipboard")
builder.withCustom("keybind", "super+left=text:\\x01")
builder.withCustom("keybind", "super+right=text:\\x05")
builder.withCustom("keybind", "super+backspace=text:\\x15")
builder.withCustom("keybind", "alt+left=text:\\x1bb")
builder.withCustom("keybind", "alt+right=text:\\x1bf")
builder.withCustom("keybind", "alt+backspace=text:\\x1b\\x7f")
```

Those **seven** restored bindings are the complete list — nothing else in the app emits a `keybind` directive (verified by grep across all Swift sources). The stated intent is the comment immediately above, at `TabRuntime.swift:232-236`: *"Drop libghostty's default Cmd-\* bindings (new_window, close_surface, new_tab, new_split, goto_split, etc.) so they fall through to our menu via performKeyEquivalent."* Runtime confirmation exists in the app's log: `config: config has 'keybind = clear', all keybinds cleared` (also cited in `issues/0309.md:47`).

But grepping Ghostty's default keybind table at ref `c4e16970a`, the **only** `enter` defaults are:

- `src/config/Config.zig:7005` — ctrl/super + enter → `toggle_fullscreen`
- `src/config/Config.zig:7012` — ctrl/super + shift + enter → `toggle_split_zoom`

Both are exactly the menu-conflicting class Batty means to drop. **There is no `shift+enter` default for `clear` to have removed.** A patch of the form `keybind = shift+enter=text:\r` would still *work* — it would intercept the key before the encoder ever runs — but it would be treating the symptom, and it would not touch Option-arrows or any other modified key.

`keybind = clear` is nonetheless indiscriminate and worth auditing as part of this issue. It landed in **#0062** (`027b9f9`, 2026-05-11, *"Clear libghostty's default Cmd-\* bindings so our menu wins"*); the `super`/`alt` restorations came later in **#0106** (`db2ca2d` / `f2232cf`, 2026-05-14). Its side effects are already documented in `docs/shortcuts.md:270-287` and `docs/shortcuts.md:524-527`.

### Ruled out: Batty's own NSEvent key monitor

Batty's local `NSEvent` monitor at `Batty/BattyApp.swift:68` routes through `BattyShortcuts.handle(event)`. That path logs `dispatching action …` at `BattyKit/Sources/BattyKit/Commands/BattyShortcuts.swift:107`, and **no such line appears in the log when Shift-Enter is pressed**. The key reaches libghostty untouched. **Do not re-investigate this path.**

### Distinct sub-case: Option/Alt + arrows

The Option-arrow report is probably a *different* failure from Shift-Enter and should be investigated separately. Batty explicitly rebinds `alt+left` / `alt+right` to `text:\x1bb` / `text:\x1bf` (readline word-motion), so those keys never reach the encoder at all. Candidate faults there:

- The set is **incomplete** — there is no `alt+up` / `alt+down` binding, so those *do* fall through to the encoder and will emit `modifyOtherKeys` / CSI-u reports under the same conditions as Shift-Enter.
- `\x1bb` / `\x1bf` is right for a readline/ZLE prompt but **wrong inside a TUI** that wants the real `ESC[1;3D` / `ESC[1;3C` modified-arrow sequence. A hard `text:` binding takes the choice away from the application.
- `super+left`/`super+right`/`super+backspace` → `\x01`/`\x05`/`\x15` have the same shape of problem.

## Scope and verification for whoever fixes this

1. **Establish the full inventory of what `keybind = clear` removes at the pinned Ghostty revision.** This is the core of the work; without it any fix is guesswork. Then split that inventory into (a) the `Cmd-*` menu-conflicting bindings Batty genuinely wants gone, and (b) everything discarded by accident. Replace `clear` with targeted unbinds, or re-add the full set of non-conflicting defaults. **A one-key `shift+enter=text:\r` patch is the wrong shape** — it hides the class behind its first reported instance.
2. **Determine who enables `modifyOtherKeys` mode 2 and whether Batty should reset it.** This is the actual mechanism behind the reported symptom. Find what emits `CSI > 4 ; 2 m` in the user's session, and decide whether pane/session reset should clear `Terminal.flags.modify_other_keys_2`.
3. **Test matrix:** Shift / Ctrl / Alt / Cmd × Enter, all four arrows, Backspace, Tab — at a plain zsh prompt **and** inside a TUI (`vim`, `less`). **Terminal.app is the reference for expected behaviour**; diff against it. Include the "run a TUI, quit it, then press Shift-Enter" ordering, since mode state surviving an application exit is the suspected trigger.
4. **Testing is Beta-only.** `./build.sh` defaults to Beta; Prod is `./build.sh release`. **Never touch the user's Prod app at `/Applications/Batty.app`.**

## Resolution

- Root cause confirmed: libghostty's `function_keys.zig` sends `ESC[27;<mod>;13~` for Shift- and Ctrl-Return unconditionally, the same as upstream Ghostty. A plain shell's line editor does not understand it and prints the tail.
- New `BattyKit/Sources/BattyKit/Commands/PlainShellKeyRewrite.swift`, called from the key monitor in `Batty/BattyApp.swift`. It rewrites Shift- or Ctrl-Return (and keypad Enter) to a plain Return only when all of these hold: the first responder is `AppTerminalView`, no IME text is marked, the foreground process group's leader is bash, zsh or another sh-family shell, and that group has no other member. Programs started from an interactive shell (Claude Code, vim, less) lead their own process group, so they still receive the modified key.
- The key code and modifiers are checked first, so plain typing never reaches the `proc_*` calls. The group size comes from `proc_listpgrppids` into a real buffer, which returns a pid count.
- Option-arrows, Tab and Escape modifiers, Shift-Enter over ssh and the `keybind = clear` inventory are #0462.

## Gotchas

- Not checked by hand: Shift- and Ctrl-Enter at zsh and bash prompts in Beta; Shift-Enter in Claude Code (must still insert a newline), vim and fish; IME composition with Return; plain typing, clicks and file drop. The VM test covers only zsh at a prompt.
- The check fails closed: with `setopt nomonitor`, or a plugin that leaves helper processes in the shell's process group, the garbage still appears.
- fish is not in the shell list; it handles the sequence itself.
- Non-blocking leftovers: the posix_spawn test's `defer` kills an already-reaped pid; a comment says "zsh/bash readline" though zsh uses ZLE.
