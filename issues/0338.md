## Description

Dragging the divider between two Panes to resize them does not track the pointer smoothly — the divider resists the drag and rapidly jumps back and forth between positions. User report (verbatim): "When I resize a pane, like when I have 2 panes stacked horizontally, and I drag to resize it resists and jumps back and forth a lot. It should be smooth. I suspect there is some view state changes firing too often which violates SwiftUI rules."

The report describes two stacked Panes, but the divider drag code path in `DraggableSplitView` is shared by both Split directions (`.horizontal` — side-by-side, vertical divider; `.vertical` — stacked, horizontal divider), so both orientations are affected. See Notes for the confirmed mechanism.

## Root cause

`DraggableSplitView`'s divider `DragGesture` was declared
`coordinateSpace: .local` — the coordinate space of the divider
`Rectangle` itself. Every `onChanged` write re-places the divider via
`SplitLayout.placeSubviews` (through `onRatioChange` -> `SplitTree.
updateRatio(forSplitID:to:)`), so the `.local` space moved under the
pointer mid-drag: the next event's `value.translation` collapsed back
toward zero (start location and current location, both re-expressed
in the now-shifted local space, nearly coincide), snapping the
divider back, then a large translation on the following event jumped
it forward past the pointer. Direction-independent — both
`.horizontal` and `.vertical` splits select `translation.width` /
`.height` from the same moving space. Matches the issue's confirmed
mechanism in Notes exactly; no other cause found.

## Fix

Rooted a stable `.named` coordinate space (a per-`DraggableSplitView`-
instance `UUID`, `dividerCoordinateSpaceID`) on the container
`GeometryReader` in `SplitContainerView.swift` via
`.coordinateSpace(.named(dividerCoordinateSpaceID))`. That
`GeometryReader`'s own frame is set by the *parent* split's layout,
not by this split's own `ratio`, so it stays fixed for the whole
drag — unlike the divider `Rectangle`, which moves every time
`onRatioChange` fires. The divider's `DragGesture` now uses
`coordinateSpace: .named(dividerCoordinateSpaceID)` instead of
`.local`.

Factored the ratio math out of the gesture closure into a pure,
testable function:

```swift
enum SplitDividerMath {
    static func ratio(
        direction: SplitDirection,
        startRatio: Double,
        startLocation: CGPoint,
        currentLocation: CGPoint,
        containerLength: CGFloat
    ) -> Double
}
```

`DraggableSplitView.divider`'s `onChanged` now calls
`SplitDividerMath.ratio(...)` with `value.startLocation` /
`value.location` (both stable once the coordinate space is stable) in
place of the old `startRatio + (translation / containerLength)`
inline computation. `SplitTree.updateRatio(forSplitID:to:)` remains
the single clamp point (0.05–0.95) — untouched.

**The blocking finding, and why it mattered.** Round 1 measured — rather

this bug. The reviewer replayed the tests' exact inputs through a
verbatim reimplementation of the pre-fix formula and all seven passed

```
OLD formula on the test's inputs -> ratios: [0.5, 0.525, 0.5625, 0.6, 0.65]
monotonic non-decreasing: true; last>first: true
```

`DragGesture.Value.translation` is defined as `location - startLocation`
in whatever space the gesture reports, so `startRatio + translation/containerLength`
and `startRatio + (currentLocation - startLocation)/containerLength` are
identical arithmetic. The defect was never in the arithmetic — it was in
which space the two points are expressed in, and hand-authored
stable-space points are precisely what the buggy code never received.
The tests are worth keeping (they lock the arithmetic contract,
cross-axis no-op, and zero-length guard) but the "regression coverage"
labeling was false and was corrected. Left uncorrected, a later session
grepping for #0338 coverage would find a green suite and conclude the
regression was fenced when it was not.

Round 2 found the corrected understanding had not reached
`BattyUITests/SplitDividerDragTests.swift`, whose comments still claimed
the per-step checks catch snap-back "mid-drag" — structurally false,
since `boundaries` is sampled only after each `press(forDuration:thenDragTo:)`
returns. Round 3 approved.

Residual nits, recorded rather than spending a fourth round:

## Steps to reproduce

1. Launch Batty with a single Pane.
2. Split it (Cmd-D for a horizontal Split, or Cmd-Shift-D for a vertical Split) so the Session shows two Panes with a divider between them.
3. Press down on the Split divider and drag steadily toward one side.

## Expected behavior

The divider follows the pointer continuously; the two Panes resize smoothly for the whole drag.

## Actual behavior

The divider oscillates: it moves with the pointer, snaps back toward its starting position, jumps forward again, and repeats — visible back-and-forth jitter throughout the drag.

## Notes

Confirmed mechanism (high confidence), in `BattyKit/Sources/BattyKit/Views/SplitContainerView.swift`:

- The divider's drag gesture is declared as `DragGesture(minimumDistance: 0, coordinateSpace: .local)` (line 179). `.local` is the coordinate space of the divider `Rectangle` itself — a view that *moves* as a consequence of the drag.
- `onChanged` (lines 180–186) computes `newRatio = startRatio + (delta / containerLength)` from `value.translation` and calls `onRatioChange`, which writes `tree.updateRatio(forSplitID:to:)` (line 83, clamped 0.05–0.95 in `SplitTree.swift` line 311). The ratio write re-runs `SplitLayout.placeSubviews`, which re-places the divider at the new position.
- Because the divider has now moved under the pointer, the gesture's local coordinate space has moved with it: the next event's `value.translation` (location minus start location, both expressed in the divider's local space) collapses back toward zero. `newRatio = startRatio + ~0` snaps the divider back to its start position; the pointer is then far from the divider in local space again, producing a large translation and a jump forward. The loop repeats — the classic moving-local-coordinate-space feedback oscillation, matching the reported "resists and jumps back and forth".

This is direction-independent: `delta` is taken from `translation.width` or `translation.height` per `SplitDirection`, but both go through the same moving `.local` space.

What it is *not*: the ratio write itself happens in a gesture `onChanged`, which is an event-origin write and is permitted by `docs/swiftui-observation-rules.md` — the reporter's suspicion of an observation-rule violation is understandable but the writes-per-drag-event pattern is fine; the defect is where the translation is measured. `containerLength` (fed by `onGeometryChange`, line 158) is the fixed container's length along the axis and does not change during the drag, so it is not part of the loop.

Candidate fix direction (for the implementer to verify): measure the drag in a coordinate space that does not move with the divider — e.g. a `.named` coordinate space on the `GeometryReader` container (or derive the ratio directly from `value.location` in that container space) — instead of the divider's `.local` space. Secondary effect worth watching while testing: each spurious ratio write also re-places the AppKit terminal hosts via `PaneView`'s frame reporting (`PaneView.swift` lines 157–164), so the oscillation makes terminal content thrash too; a correct fix should leave one smooth stream of monotonic ratio updates. Per `docs/terminal-pane-requirements.md`, verify divider hover cursors and pane pointer input still work after the change.
