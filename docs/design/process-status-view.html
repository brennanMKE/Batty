Process Status view — visual design (#0305, phase 1)

Mockup of the second non-terminal Pane kind (process-status), read-only, focused on one selected app or process rather than the whole system. Switch between the six states below — the four on the right are the hard states this review should scrutinize most: an exited process, a metric made unavailable by permissions, no sibling terminal to inherit a target from, and a high-churn process mid-sample with the disclosure groups open. Every metric shown here was proved obtainable, at the cost noted, by a real feasibility spike — see docs/design/process-status-view.md §1 for the exact commands and numbers, and the rest of that document for the reasoning behind every other choice.

This process is running as root. CPU, memory, threads, open files, and command line can't be read for a process you don't own — this will clear automatically once the foreground process changes.
1A concrete, reachable edge case, not a hypothetical — the spike found this exact permission boundary inside Batty's own architecture: its pty session leader (/usr/bin/login) is root-owned even though it's a child of Batty's own process. Interactive sudo periodic daily (or any other sudo invocation) in a followed terminal hits the identical wall for as long as it runs.
2Only the executable path resolves (/usr/bin/sudo above) — proc_pidpath sits behind a looser permission tier than PROC_PIDTASKINFO/proc_pid_rusage, confirmed by the spike against root's own launchd, but it returns a path, never a command line. There is no dedicated command-line row in this state because KERN_PROCARGS2 fails EINVAL for a different-uid target — the same permission boundary as the metrics, not the looser one. The process name "sudo" shown in the header is derived as the path's basename, not a successful proc_name call — that call is denied here too. The view shows exactly what it can, nothing more.
